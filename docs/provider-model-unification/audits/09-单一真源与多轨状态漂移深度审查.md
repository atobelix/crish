## 一、审查重点 1：LocalStorage 孤岛是否 100% 铲除？

### 结论：【绝对未铲除，铲除率为 0%】

### 1.3 核心发现：IPC 命令未注册与回退平铺降级自毁（Data Corruption Trap）

在审计 `modelsCatalogIpc.ts` 与 Rust 后端交互时，发现了一个足以造成**数据严重损坏与结构退化**的重大隐患：

1. **Rust Tauri 命令未注册**：
   - 在前端 [`apps/crish-desktop/src/api/modelsCatalogIpc.ts:83,159`](file:///c:/Software/conex/apps/crish-desktop/src/api/modelsCatalogIpc.ts#L83) 中：
     ```typescript
     // 读取
     const res = await invokeTyped<ReadModelsYamlWire>('models_yaml_read', {});
     // 写入
     const res = await invokeTyped<{ success: boolean; writtenPath?: string }>('models_yaml_write', { tree });
     ```
   - 检查 Rust 后端 [`apps/agent-workbench/src-tauri/src/main.rs:200-212`](file:///c:/Software/conex/apps/agent-workbench/src-tauri/src/main.rs#L200-L212)：
     ```rust
     builder = builder.invoke_handler(tauri::generate_handler![
         "workbench_read_models_yaml",
         models_yaml::workbench_read_models_yaml
     ]);
     builder = builder.invoke_handler(tauri::generate_handler![
         "workbench_validate_models_yaml",
         models_yaml::workbench_validate_models_yaml
     ]);
     builder = builder.invoke_handler(tauri::generate_handler![
         "workbench_save_models_yaml",
         models_yaml::workbench_save_models_yaml
     ]);
     ```
   - **Rust 端根本没有注册 `models_yaml_read` 和 `models_yaml_write`！** 这意味着前端调用该命令时恒返回 `status: 'missing'`。

2. **降级逻辑导致配置严重损毁（自毁性平铺回退）**：
   - 在 `writeModelsYamlIpc` 收到 `missing` 后，执行了后备兼容分支（[`modelsCatalogIpc.ts:172-222`](file:///c:/Software/conex/apps/crish-desktop/src/api/modelsCatalogIpc.ts#L172-L222)）：
     ```typescript
     // 2. 若 models_yaml_write 命令未注册，回退尝试序列化后写入 workbench_save_models_yaml
     const flatModels: any[] = [];
     for (const [vendorId, provider] of Object.entries(tree.providers || {})) {
       for (const m of provider.models || []) {
         flatModels.push({
           model: m.id,
           vendor: vendorId,
           ...
         });
       }
     }

     const lines: string[] = ['models:'];
     for (const m of flatModels) {
       lines.push(`  - model: "${m.model}"`);
       lines.push(`    vendor: "${m.vendor}"`);
       if (m.vendorDisplayName) lines.push(`    vendorDisplayName: "${m.vendorDisplayName}"`);
       if (m.displayName) lines.push(`    displayName: "${m.displayName}"`);
       if (m.contextWindow != null) lines.push(`    contextWindow: ${m.contextWindow}`);
       if (m.maxOutputTokens != null) lines.push(`    maxOutputTokens: ${m.maxOutputTokens}`);
       if (m.protocol) lines.push(`    protocol: "${m.protocol}"`);
     }

     await invokeTyped('workbench_save_models_yaml', { content: lines.join('\n') + '\n' });
     ```
   - **致命问题**：
     1. 该回退直接将整个 v2 树状结构强行拆解成 v1 的 `models:` 平铺列表，**永久丢弃了供应商根级的 `baseUrl`、`apiKey`、`headers`、`compat` 等核心连接属性**！
     2. 在拼接 `lines` 的循环中，**完全漏掉了 `pricing`、`capabilities`、`thinking`、`modalities`**（代码中计算了 `pricing`，但拼接时根本没有 `lines.push` 价格和能力）！
     3. 一旦触发该写入，用户磁盘上的 `~/.conex/models.yaml` 将被覆盖为一个丧失全部高级特性的残疾 v1 文件。

### 2.3 设置面板修改模型后，主界面模型列表响应式刷新实测

对以下两个典型场景进行执行时序推演与状态链路审计：

#### 场景 A：用户在设置面板的常规 UI 表单中新增或修改模型并保存
1. 用户在 `ModelConfigEditor` 中修改了参数并保存，触发 `saveConfig`（[`useModelConfigSession.ts:186`](file:///c:/Software/conex/apps/crish-desktop/src/components/settings-models/useModelConfigSession.ts#L186)）；
2. 调用 `applyMetaForModel`（[`modelsIpcHelpers.ts:66`](file:///c:/Software/conex/apps/crish-desktop/src/components/settings-models/modelsIpcHelpers.ts#L66)），将改动写穿进 LocalStorage `crish_model_meta_v1`，并通过 `emitUiEvent('model-meta-changed')` 广播；
3. 主界面 `ModelBadgePickerMenu` 挂有 `useModelMetaTick()`，收到广播后驱动 `useMemo` 重新计算 `profiles` 和 `filteredGroups`；
4. **刷新表现**：修改属性/开关模型时，主界面能产生假象式的刷新；
5. **但是（致命缺陷）**：如果用户在设置界面中**删除了某个模型**（点击垃圾桶图标触发 `removeModelFromProfile`，[`ModelList.tsx:257`](file:///c:/Software/conex/apps/crish-desktop/src/components/settings-models/ModelList.tsx#L257)）：
   - `removeModelFromProfile` 内部调用 `saveProfiles(list)`（[`profileStorePersistence.ts:252`](file:///c:/Software/conex/apps/crish-desktop/src/api/provider-profiles/profileStorePersistence.ts#L252)）；
   - `saveProfiles` **仅广播 `profiles-changed`，没有广播 `model-meta-changed`**；
   - 而 `ModelBadgePickerMenu.tsx:61-65` **根本没有监听 `profiles-changed`**（它只依赖 `metaTick`）；
   - **结果**：已删除的模型在主界面聊天卡片下拉菜单中依然存在，必须强刷页面才能消失！

#### 场景 B：用户在 YAML 编辑器（`YamlConfigEditorModal`）或外部编辑器修改 `~/.conex/models.yaml` 并保存
1. 用户在 YAML 模态框中保存，调用 `workbench_save_models_yaml`，Rust 写入磁盘并执行 `reload_live_catalog()`；
2. 随后调用 `ensureModelsCatalogLoaded(true)`，更新前端 `modelsCatalogStore` 并触发 `emitUiEvent('models-catalog-changed')`；
3. **但是**：
   - `useChatModelPicker.ts` 没监听 `models-catalog-changed`；
   - `ChatHeaderControls.tsx` 没监听 `models-catalog-changed`；
   - `ModelBadgePickerMenu.tsx` 没监听 `models-catalog-changed`；
   - `ComposerFusedTrigger.tsx` 没监听 `models-catalog-changed`；
   - 它们全部死死盯住 LocalStorage（`listPickerProfiles` / `loadProfiles` / `getModelMeta`）；
4. **结果**：**瞬时响应式刷新率为 0%**！用户在 YAML 中新增的供应商和模型，主界面下拉菜单完全看不到，因为 LocalStorage 中根本没有这些数据。双轨彻底断裂！

## 三、审查重点 3：数据结构是否存在多轨转换漂移？

### 3.1 字段命名撕裂：`contextWindow` vs `contextLength`
- **YAML 真源与 Store 契约**：[`modelsCatalogTypes.ts:134`](file:///c:/Software/conex/apps/crish-desktop/src/api/modelsCatalogTypes.ts#L134)、[`models_yaml.rs:97`](file:///c:/Software/conex/apps/agent-workbench/src-tauri/src/models_yaml.rs#L97) 规范命名为 `contextWindow`；

- **隐患现场**：
  在 `modelsCatalogQuery.ts` 的 `modelToCatalogSpec` 中：
  ```typescript
  // modelsCatalogQuery.ts:72
  contextWindow: m.contextWindow,
  ```
  导出的兼容规格 `CatalogModelSpec` 只有 `contextWindow`，没有映射 `contextLength`。旧业务代码如果按习惯读取 `spec.contextLength`，将直接得到 `undefined`，导致前端误认为无上下文限制或退回写死的 128K 兜底。

### 3.4 价格字段双轨不同步与单价覆盖风险
- **树状 Schema 命名**：`input`, `output`, `cacheRead`, `cacheWrite`（单位 per 1M tokens）；

- **转换逻辑漏洞**（[`modelsCatalogQuery.ts:76-87`](file:///c:/Software/conex/apps/crish-desktop/src/api/modelsCatalogQuery.ts#L76-L87)）：
  ```typescript

        inputPerMTok: m.pricing.input ?? m.pricing.inputPerMTok,
        outputPerMTok: m.pricing.output ?? m.pricing.outputPerMTok,
        cacheReadPerMTok: m.pricing.cacheRead ?? m.pricing.cacheReadPerMTok,
        cacheWritePerMTok: m.pricing.cacheWrite ?? m.pricing.cacheWritePerMTok,
  ```

### 3.5 门面全局检索跨厂商串线（Cross-Provider Hijacking）
- **文件路径**：[`apps/crish-desktop/src/api/modelsCatalogQuery.ts:108-119`](file:///c:/Software/conex/apps/crish-desktop/src/api/modelsCatalogQuery.ts#L108-L119)
- **代码证据**：
  ```typescript
  export function findCatalogModel(modelId: string): CatalogModelSpec | undefined {
    const target = (modelId || '').trim().toLowerCase();
    if (!target || !globalCatalogAccessor) return undefined;

    const state = globalCatalogAccessor();
    // 盲目获取匹配到的第一个 provider 的 entry！
    const entry = state.globalModelIndex.get(target)?.[0];
    if (entry) {
      return modelToCatalogSpec(entry.providerId, entry.provider, entry.model);
    }
    ...
  }
  ```
- **致命逻辑断层**：
  在 v2 Provider-Centric 架构下，模型是挂载在具体 Provider 下的。不同 Provider 完全可以包含同名模型（例如官方直连 OpenAI 的 `gpt-4o` 与第三方中转站的 `gpt-4o`，甚至官方 DeepSeek 与硅基流动代理的 `deepseek-chat`）。
  `findCatalogModel(modelId)` 接口只传 `modelId`，直接从 `globalModelIndex` 截取 `[0]`。如果系统配置了两个提供商，用户在会话中选择的是 Provider B 的模型，业务层调 `findCatalogModel` 却永远拿到 Provider A 的上下文窗口、协议与单价！这构成严重的**跨服务商模型参数劫持**。

## 六、收敛与重构实施方案（SSOT 净收敛路线）

为了彻底消灭双轨、确立单一物理真源（SSOT），必须执行刚性物理收敛，拒绝任何过渡兼容补丁：

### 阶段 1：Rust 内核与 IPC 强契约对齐（根除自毁与协议断层）
1. **统一协议枚举**：
   - 检查并对齐 `ModelsYamlProtocol`：在 Rust [`models_yaml.rs:29-38`](file:///c:/Software/conex/apps/agent-workbench/src-tauri/src/models_yaml.rs#L29-L38) 与前端 [`modelsCatalogTypes.ts:11-15`](file:///c:/Software/conex/apps/crish-desktop/src/api/modelsCatalogTypes.ts#L11-L15) 中，将 Google 协议明确统一为双向兼容或正式对齐（建议双向兼容 `google/generate-content` 与 `google/interactions`，并在 serde 中使用 alias）。
2. **正式注册 IPC 命令**：
   - 在 `main.rs` 中为 Tauri 注册 `models_yaml_read` 与 `models_yaml_write`，直接挂接原生 `models_yaml::*` 处理函数；
   - **立即删除** `modelsCatalogIpc.ts` 中将 v2 强行拼装成残缺 v1 平铺 YAML 的自毁回退代码！失败必须抛出明确错误，禁止伪装降级。
3. **补齐热重载广播**：
   - 在 Rust `save_models_yaml_at` 落盘成功后，通过 Tauri `app_handle.emit_all("models-yaml-reloaded", ...)` 广播系统级事件。

### 阶段 2：前端 LocalStorage 物理铲除与数据无损迁移
1. **冷启动一次性迁移（One-Shot Migration）**：
   - 编写幂等迁移器：若检测到 `localStorage.getItem('crish_provider_profiles_v1')` 且尚未完成 YAML 统一迁移：
     - 将 `crish_provider_profiles_v1`（包含其下 models）与 `crish_model_meta_v1`（上下文、展示名、能力位、思考档位、单价）深度整合成标准 `ModelsYamlTree` (v2)；
     - 写入 `~/.conex/models.yaml`；
     - 物理调用 `localStorage.removeItem('crish_provider_profiles_v1')` 与 `localStorage.removeItem('crish_model_meta_v1')`；
     - 写入迁移完成标记。
2. **全面拔除 LocalStorage 读写调用**：
   - 废除 `profileStorePersistence.ts` 中的 `loadProfiles()` / `saveProfiles()`；
   - 废除 `modelCatalogMeta.ts` 中的 `loadMap()` / `saveMap()`；
   - 将 `providerProfiles.ts` 与 `modelCatalog.ts` 的所有门面查询直连 `modelsCatalogStore.getState()`。

### 阶段 3：组件消费层全面接入 Store 响应式驱动
1. **封装真正的 `useModelsCatalog` Hook**：
   - 基于 `useSyncExternalStore`，通过 `modelsCatalogStore.subscribe` 封装直接返回当前可用供应商与模型列表的响应式 Hook；
2. **改造 `useChatModelPicker` 与 `ModelBadgePickerMenu`**：
   - 摒弃对 `listPickerProfiles()` 的 LocalStorage 直读；
   - 直接从 `useModelsCatalog()` 获取启用的供应商与模型；
   - 当 `models-catalog-changed` 触发时，主界面下拉列表瞬时响应式重绘。
3. **改造 `ComposerFusedTrigger`**：
   - 思考档位与模型能力直接订阅 `modelsCatalogStore`；
   - 切换思考档位时，若需按模型持久化，通过 `modelsCatalogStore.updateModel` 原子更新并防抖写入 `models.yaml`。

### 阶段 4：修补多轨转换与跨厂商串线
1. **消灭接口命名歧义**：
   - 将旧接口中的 `contextLength` 统一为 `contextWindow`，或在类型声明中明确废弃 `contextLength`；
2. **重构 `findCatalogModel` 增加 Provider 范围**：
   - 将签名重构为 `findCatalogModel(modelId: string, providerId?: string): CatalogModelSpec | undefined`；
   - 优先依据 `providerId::modelId` 联合主键精确检索，彻底杜绝多供应商同名模型的跨厂商串线问题。

## 报告验收结论
本专项审计已正面、穷尽地审查了目标文件域。事实确凿表明：**当前系统表面上拥有 v2 树状 Store，实则骨子里 100% 依赖 LocalStorage 孤岛运作**。必须按照上述路线进行断腕式的单轨净收敛，拔除全部遗留 LocalStorage，打通从 UI 到 `~/.conex/models.yaml` 的单一真源（SSOT）闭环。
