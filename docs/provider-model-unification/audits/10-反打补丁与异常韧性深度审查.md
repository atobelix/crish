## 一、审计背景、职责定位与审查基准

在 Conex 系统进行“供应商与模型能力全线接通”架构重构后，系统引入了存量配置自动迁移引擎（`migration.rs`）、四维双币微元定点计费引擎（`pricing.rs`）以及 Tauri 宿主端的数据真源读写装配链路（`models_yaml.rs`）。

本审计以 **Anti-Hack & Resilience Auditor（反打补丁与异常韧性审计专家）** 角色，直面以下核心底线要求：
1. **反打补丁铁律**：严禁为了让旧代码或前端跑通而加入未经验证的兼容 Shim、手拼字符串降级补丁或双轨映射；
2. **防灾真实性与零丢失不变量**：任何自动迁移必须做到物理级防灾备份（Disaster Recovery Backup）真实可信，在格式损坏或极端异常下原文件必须绝对保持不动，不可逆破坏零容忍；
3. **高韧性计算与防溢出**：计费微元定点计算必须覆盖极大值、负数单价、非有限浮点数及阶梯重叠，消除任何潜在 panic 与回绕截断；
4. **测试资产去伪存真**：测试用例必须真实覆盖生产代码，严禁在测试文件中自行复制一份实现（Test Stand-in）制造“全绿假象”。

### 3.1 语法严重破损时 `ensure_migrated` 的行为与原文件安全保护

#### 【审查问题】
当 `models.yaml` 存在严重语法错误（如格式破损）时，`ensure_migrated` 的行为是怎样的？是否会误将破损文件覆盖？是否能妥善保留原文件供用户手工排查？

#### 【穿透结论】
- **明确结论**：当 `models.yaml` 存在严重语法破损时，`ensure_migrated` **100% 能够安全拦截并返回错误，绝不会误将破损文件覆盖，原始破损文件得到完全无损的保留**。
- **宿主协同表现**：Tauri 宿主层 `read_models_yaml_at` 捕获该错误后，仅记录 warning 日志，将磁盘原文件完整读入并透传给 YAML 诊断器，提取带行号与列号的错误信息，原样返给前端编辑器供用户人工排查修复。

#### 【具体 行号:代码 证据】
1. **语法解析短路拦截**（`crates/agent-provider/src/migration.rs:68-71`）：

### 3.2 备份时间戳精度、碰撞自增机制与写盘权限失败报错

#### 【审查问题】
备份文件生成的时间戳精度是否足以应对高频写入？备份文件写盘权限失败时是否有清晰的报错？

#### 【穿透结论】
1. **时间戳精度与高频冲突防御**：
   - 时间戳为秒级精度（`%Y%m%d_%H%M%S`）。
   - 代码实现了**碰撞自增后缀循环（`_1`, `_2`, ...）**，在单进程环境下能应对 1 秒内的高频写入；
   - 但在多进程/极端高并发下，存在 **TOCTOU（Time-of-Check to Time-of-Use）文件竞态**。
2. **写盘权限失败与严格报错**：
   - 若备份文件写盘因权限不足或磁盘满失败，`fs::copy` 返回 `std::io::Error`，被封装为 `MigrationError::Io(e)`；
   - 包含底层清晰的操作系统错误提示（如 `Permission denied (os error 5)`）；
   - 备份失败会直接中断流程，绝不会继续修改原始文件。

#### 【具体 行号:代码 证据】
1. **冲突碰撞自增机制**（`crates/agent-provider/src/migration.rs:193-207`）：
   ```rust
   193:         let timestamp = Self::current_local_timestamp();
   194:         let file_stem = source.file_stem().and_then(|s| s.to_str()).unwrap_or("models");
   195:         let ext = source.extension().and_then(|s| s.to_str()).unwrap_or("yaml");
   196:         let backup_file_name = format!("{}.{}.bak.{}", file_stem, timestamp, ext);
   197:         let mut backup_path = source.with_file_name(&backup_file_name);
   198:
   199:         if backup_path.exists() {
   200:             let mut counter = 1;
   201:             while backup_path.exists() {
   202:                 let backup_file_name = format!("{}.{}_{}.bak.{}", file_stem, timestamp, counter, ext);
   203:                 backup_path = source.with_file_name(backup_file_name);
   204:                 counter += 1;
   205:             }
   206:         }
   207:
   208:         fs::copy(source, &backup_path)?;
   ```
2. **字节大小严格校验，防截断写入**（`crates/agent-provider/src/migration.rs:210-218`）：
   ```rust
   211:         let backup_size = fs::metadata(&backup_path)?.len();
   ```

3. **报错清晰性**（`crates/agent-provider/src/migration.rs:25-26`）：

### 3.3 迁移落盘的 Windows 平台非原子替换风险与 capabilities 遗漏缺陷

在对 `migration.rs` 的逐行穿透中，发现了两个值得严肃整改的深层缺陷：

#### 缺陷 A：Windows 平台非原子替换风险
- **代码位置**：`crates/agent-provider/src/migration.rs:164-168`
  ```rust
  164:         if let Err(_e) = fs::rename(&tmp_path, config_path) {
  165:             // Windows 平台容灾：若目标已存在导致 rename 失败，先移除原目标再 rename
  166:             let _ = fs::remove_file(config_path);
  167:             fs::rename(&tmp_path, config_path)?;
  168:         }
  ```
- **根因分析**：在 Windows 平台上，`std::fs::rename` 当目标文件已存在时会返回 `AlreadyExists` / `AccessDenied`。代码采用“先 `remove_file` 再 `rename`”的补丁策略。如果在 `remove_file` 成功之后、第二次 `rename` 执行之前，发生进程崩溃、电源断电或被反病毒软件锁定，原目标文件已不存在，而新文件仍留在 `.tmp`，导致物理文件瞬间断裂。
- **正解**：应当对齐 `conex-fs` 中的 3 阶段原子写入（先 rename 为旧 `.bak`，再 rename `.tmp` 到原名，成功后清理 `.bak`，失败时回滚恢复）。

#### 缺陷 B：存量 v1 迁移严重遗漏 `capabilities` 字段（数据降级）
- **代码位置**：`crates/agent-provider/src/migration.rs:370-380`
  ```rust
  370:                 let mut model_spec_map = serde_json::Map::new();
  371:                 model_spec_map.insert("id".to_string(), json!(model_id));
  372:                 model_spec_map.insert("displayName".to_string(), json!(display_name));
  373:                 model_spec_map.insert("contextWindow".to_string(), json!(context_window));
  374:                 model_spec_map.insert("maxOutputTokens".to_string(), json!(max_output));
  375:                 model_spec_map.insert("modalities".to_string(), modalities);
  ...
  381:                 // 若原模型已有价格定义，予以保留
  382:                 if let Some(pricing) = m.get("pricing") {
  383:                     model_spec_map.insert("pricing".to_string(), pricing.clone());
  384:                 }
  ```
- **根因分析**：在组装新版 `model_spec_map` 时，代码迁移了 `id`, `displayName`, `contextWindow`, `maxOutputTokens`, `modalities`, `thinking`, `pricing`, `protocol`，**却完全遗漏了 `capabilities` 对象（包含 `tools: bool`, `image: bool`, `video: bool`）**！
- **后果**：如果用户在旧版中手动配置了 `capabilities: { tools: true, image: true }`，迁移执行后该字段被直接丢弃，导致模型的高级能力标志在升级后静默丢失。虽然有 `modalities`，但 `capabilities` 契约丢失违反了“零丢失迁移（Zero-Loss Invariant）”承诺。

## 四、审查专项 2：四维双币定点计费引擎的极端数据韧性

### 4.1 超大 Token 数（数十亿至 `u64::MAX`）与负数单价的定点防溢出穿透

#### 【审查问题】
如果遇到输入 Token 或输出 Token 极其庞大（例如数十亿甚至超过 `u64::MAX`）或传入负数单价时，定点计算是否有 panic 风险？

#### 【穿透结论】
1. **Panic 风险评估：绝对零 Panic 风险**。
   - 所有输入进行了严密的非有限浮点数（`NaN`、`Infinity`）与负数过滤，负数与非有限单价短路返回 0；
   - 缓存读取扣减使用 `saturating_sub`，总费用累加使用 `saturating_add`；
   - 乘算全部提升至 `u128` 宽位定点空间进行；
2. **精度缺陷发现：缺失 `.min(u64::MAX as u128)` 饱和截断，存在数值回绕风险**。

#### 【具体 行号:代码 证据】
1. **输入单价与浮点数合法性短路保护**（`crates/agent-provider/src/pricing.rs:369-373, 379-384`）：
   ```rust
   369:     pub fn tokens_to_micros(tokens: u64, rate_per_1m: f64) -> u64 {
   370:         if tokens == 0 || !rate_per_1m.is_finite() || rate_per_1m <= 0.0 {
   371:             return 0;
   372:         }
   ...
   379:     pub fn f64_to_micros(val: f64) -> u64 {
   380:         if !val.is_finite() || val <= 0.0 {
   381:             return 0;
   382:         }
   383:         (val * 1_000_000.0).round() as u64
   384:     }
   ```
   **分析**：任何负数、`NaN`、`+∞`、`-∞` 均在第一行立即被捕获并归零，绝无可能带入后续乘法，杜绝了浮点到整数转换的未定义行为与崩溃。

2. **宽位乘算与截断对比**：
   - 生产代码（`crates/agent-provider/src/pricing.rs:374-375`）：
     ```rust
     374:         let product = (tokens as u128) * (rate_micros as u128);
     375:         ((product + 500_000) / 1_000_000) as u64
     ```
   - 对应魔鬼测试（`crates/agent-provider/tests/devil_cases_tests.rs:189-192`）：
     ```rust
     189:             let product = (tokens as u128) * (rate_micros as u128);
     190:             let result = (product + 500_000) / 1_000_000;
     191:             result.min(u64::MAX as u128) as u64
     ```
   - **穿透发现**：生产代码在第 375 行**直接执行 `as u64` 强制截断**！
     若 `tokens = u64::MAX` 且单价为 $100.0/1M：
     $product / 10^6 \approx 1.84 \times 10^{21} > u64::MAX (1.84 \times 10^{19})$。
     在 Rust 中，`u128 as u64` 属于两补码截断（低 64 位截取），**不会引发 panic，但会导致费用从天文数字回绕（Wrap-around）变成极小的随机数值**！
     同理，按张计费模式 `pricing.rs:266`：
     `let total_micros = (image_count as u128 * rate_micros_per_image as u128) as u64;`
     同样缺少 `.min(u64::MAX as u128)` 饱和钳制。

3. **下溢与上溢饱和保护**（`crates/agent-provider/src/pricing.rs:323, 330-333`）：
