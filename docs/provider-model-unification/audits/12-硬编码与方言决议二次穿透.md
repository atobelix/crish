## 一、总裁决

Wave 4 之后，**表面接线已发生，运行时真源与出站方言并未兑现「杜绝硬编码、杜绝 token 样式盲目猜测」**。

相对 06 审计，下列事项**确实变了**：

1. `assemble_thinking_dialect` 不再是「函数存在、生产零调用」——`build_chat.rs` / `build_responses.rs` 已引用它，且 `ChatCompletionsRequestOptions` 已新增 `thinking_map` / `thinking_format` 字段。
2. `messages_compat.rs` 的 `WireCompat::is_deepseek` 确已去掉 `url.contains("deepseek")`。
3. `compat.rs` 新增 `resolve_*_from_compat` / `resolve_*_with_compat`，并在网关判定里「vendor 名优先、URL 兜底」。
4. `protocol.rs` 新增 `LIVE_CATALOG` / `live_catalog()` / `reload_live_catalog()`。
5. `models.default.yaml` 仍是空 `providers: {}`；前端 `api/modelsAutofillBaseline.ts` 只是 `services/` 的重导出，不是第二份字典实现。

下列事项**没有变，或只换成了更隐蔽的假收敛**：

1. 生产出站仍由 `url.contains` + `model.starts_with` 主导厂商/缓存/协议键；`EngineProviderConfig` 依然没有 `vendor` / `protocol` / `compat` / `thinking`。
2. 生产 `HttpProviderCall::request_options` **从不填充** `thinking_map` / `thinking_format` / `vendor`。Chat / Responses 即使调用了 `assemble_thinking_dialect`，也是 `thinking_map=None` + 默认 OpenAI 方言，yaml 拍平字典进不了出站 JSON。
3. Anthropic / Gemini 两条原生出站**完全不走** `assemble_thinking_dialect`，继续用硬编码 `budget_tokens` / `thinking_level` 换算表。
4. `live_catalog()` 标了 `#[allow(dead_code)]`，保存 yaml 会 `reload_live_catalog()`，但协议路由、思考白名单、缓存策略、上下文窗口全部仍读 `bundled_catalog()`（`catalog.json` 编译期静态表）。
5. `resolve_*_with_compat`、`to_chat_messages_with_compat` 带真实 `WireCompat`、`build_reasoning_wire`、`sanitize_outbound_messages`、`build_endpoint_url` 均未进入生产发送链。
6. 注释多处写「已根除 URL 盲猜 / 彻底废除 MODEL_SERIES / 100% 由字典驱动」——对照实现，属于假收敛。

**总裁决：未兑现。Wave 4 把「花瓶函数」焊进了 Chat/Responses builder，但生产入参仍为空，四条出站仍是多套硬编码换算表；`catalog.json` 仍是运行时真源。不得以单测绿或注释「已根除」关账。**

### 问题 1 · 生产厂商决议仍由 URL 子串 + 模型前缀盲猜主导

**证据**：`crates/agent-provider/src/request/vendor.rs:182-214`

```rust
pub fn infer_reasoning_vendor(base_url: Option<&str>, model: Option<&str>) -> ReasoningVendor {
    let url = base_url.unwrap_or("").to_ascii_lowercase();
    let model = model.unwrap_or("").to_ascii_lowercase();
    if url.contains("anthropic") || model.starts_with("claude") { return ReasoningVendor::Anthropic; }
    if url.contains("deepseek") || model.starts_with("deepseek") { return ReasoningVendor::Deepseek; }
    if url.contains("generativelanguage.googleapis.com")
        || url.contains("gemini")
        || model.starts_with("gemini") { return ReasoningVendor::Gemini; }
    if url.contains("openai")
        || model.starts_with("gpt")
        || model.starts_with("o1")
        || model.starts_with("o3")
        || model.starts_with("o4") { return ReasoningVendor::Openai; }
    // qwen / glm / kimi 仅模型前缀
    ReasoningVendor::Auto
}
```

同构复制：

- `crates/agent-provider/src/models/behavior.rs:310-359` `infer_vendor`（再加 minimax / grok / kimi / glm / dashscope / qwen）
- `crates/agent-provider/src/request/cache_policy.rs:564-605` `infer_cache_capability`

**生产调用**：

- `apps/agent-workbench/src-tauri/src/engine_provider/protocol.rs:78-89` `catalog_vendor` → `infer_reasoning_vendor(base_url, model)`
- 同文件 `effective_protocol` / `max_tokens_field` / `responses_supported` / `effective_context_window` 全部吃这个猜出来的 vendor
- `apps/agent-workbench/src-tauri/src/engine_provider.rs:243-247` `reasoning_content_mode`：URL 里有 `deepseek` 才 `Require`，否则 `Omit`

**为何违规**：铁律要求协议与方言只依赖显式 `vendor` / `protocol` / `compat`。用户走自建反代（`https://ai.mycompany.com`）或 OpenAI-compatible 网关转发 Claude/DeepSeek 时，盲猜必然错轨。`messages_compat.rs:11-12,71` 注释宣称「url.contains("deepseek") 已被彻底根除」，只对 `WireCompat::is_deepseek` 局部成立，生产主干仍在猜。

**建议收敛**：`EngineProviderConfig` 补齐 yaml 的 `providerId` / `protocol` / `compat`；删除生产路径上的 `infer_reasoning_vendor` / `infer_vendor` URL 分支。未知厂商应显式失败或走 yaml 声明，而不是 `Auto` 再猜。

### 问题 3 · Chat 出站：注释写「100% 字典驱动」，无 map 时回落到硬编码 OpenAI effort

**证据**：`crates/agent-provider/src/request/build_chat.rs:49-150`

显式分支（`thinking_format` 或 `thinking_map` 有值）才把 yaml 字典交给 `assemble_thinking_dialect`。生产两者皆 `None`，走兜底：

- `vendor == Anthropic` → `reasoning_effort_object`（硬编码 budget / adaptive 前缀表）
- 其余 → `assemble_thinking_dialect` 且 `format=OpenAiEffort`、`thinking_map=None`
- 若还带 `thinking_intensity`，再被 `infer_thinking_capability(model)` + `resolve_thinking_params` **覆盖**（`build_chat.rs:122-149`），即 MODEL_SERIES 前缀表重新掌权

`to_openai_str`（`vendor/dialect.rs:106-113`）在无字典时把档位粗暴折叠：

| 用户档位 | 出站字符串 |
| --- | --- |
| Minimal / Low | `"low"` |
| Medium | `"medium"` |
| High / X-High / Max | `"high"` |

**为何违规**：铁律「严禁把用户档位粗暴映射成固定字符串而不读 yaml thinking map」。生产 Chat 路径正是这条。单测 `test_anti_dead_feature_flattened_thinking_map_driven`（`build_chat.rs:280-294`）只证明「手工塞 map 时 builder 会读」——生产从不塞。

**建议收敛**：生产必须带上 yaml `thinking` 与 `compat.thinkingFormat`。无 thinking 字段的模型不应发送任何 reasoning 键。删除 `infer_thinking_capability` 对请求体的覆盖。禁止无 map 时 Max→`"high"`。

### 问题 4 · Responses 出站：无 format 时一律 `reasoning.effort`，DeepSeek/Qwen/Anthropic 方言被吞

let format = opts.thinking_format.map(|tf| match tf {

**建议收敛**：format 必须来自 yaml `compat.thinkingFormat`（或与其同构的运行时字段）。未声明则不注入思考键。禁止把 Anthropic/Gemini/Zai 映射进 OpenAI nested。

### 问题 5 · Anthropic 出站零调用 `assemble_thinking_dialect`，budget 表硬编码且与 dialect 表互相矛盾

**证据 A**：`crates/agent-provider/src/request/build_anthropic.rs:124-128,277-299`

```rust
fn anthropic_thinking_object(opts: &AnthropicRequestOptions) -> Option<Value> {
    // 只用 thinking_budget / thinking_to_budget_tokens / effort_to_budget_tokens
    Some(json!({ "type": "enabled", "budget_tokens": budget }))
}
```

`AnthropicRequestOptions`（同文件 57-74）没有 `thinking_map` / `thinking_format`。

**证据 B**：两套硬编码预算刻度不一致

| 档位 | `vendor_wire.rs:21-32` `effort_to_budget_tokens`（Anthropic 生产实际走这条） | `dialect.rs:116-126` `to_anthropic_budget`（assemble 单测走这条） |
| --- | ---: | ---: |
| Low | 1024 | 2048 |
| Medium | 2048 | 8192 |
| High | 4096 | 16384 |
| XHigh | 8192 | 32768 |
| Max | 16384 | 64000 |

**证据 C**：自适应代际在 Anthropic 生产轨上是死代码。`catalog.json` 对 `claude-fable-5` 等写 `thinkingFormat: "thinking_adaptive"`（`catalog.json:43-50`），`is_adaptive_thinking_model` 只被 `reasoning_effort_object` / `reasoning_effort_headers_for_model` 使用。生产 Anthropic body 永远 `type: enabled` + `budget_tokens`，从不发 `type: adaptive`。

**为何违规**：token 样式来自编译期刻度，不读 yaml。同一「High」在两条代码路径是 4096 与 16384 两种猜测。方案要求 TitleCase→wire 字典；Anthropic 的 wire 应是用户字典里的数字字符串（或显式 budget 字段），不是第二套魔法表。

**建议收敛**：Anthropic 轨改为调用 `assemble_thinking_dialect(AnthropicBudget, thinking_map)`。删除 `effort_to_budget_tokens` 生产调用。自适应形态由 yaml `compat` / `thinking` 字典声明，不由 `claude-opus-4-7` 前缀表猜测。

### 问题 6 · Gemini 出站零调用 `assemble_thinking_dialect`，且枚举层把 Gemini 错映成 OpenAI effort

**证据 A**：`crates/agent-provider/src/request/build_gemini.rs:45-47,88-96`

### 问题 10 · `live_catalog` 热重载是空操作，`catalog.json` 仍是运行时真源

**证据**：

| 符号 | 位置 | 生产角色 |
| --- | --- | --- |
| `BUNDLED_CATALOG` / `bundled_catalog()` | `protocol.rs:63-73` | `ModelCatalog::bundled()` ← `include_str!("catalog.json")` |
| `LIVE_CATALOG` / `live_catalog()` | `protocol.rs:35-53` | `#[allow(dead_code)]`，全仓无生产读取 |
| `reload_live_catalog()` | `protocol.rs:56-61`；`models_yaml.rs:479` 保存时调用 | 写入一块无人读的 RwLock |
| Tauri state | `main.rs:990-994` | `app.manage(ModelCatalog::bundled())` |
| 协议路由 | `protocol.rs:112-128` | `resolve_wire_protocol(bundled_catalog(), ...)` |
| 思考白名单 | `thinking.rs:86-91` | `describe_model(bundled_catalog(), catalog_vendor(...), ...)` |
| 缓存策略 | `engine_provider.rs:147-148` | `build_cache_policy(Some(bundled_catalog()), base_url, model, ...)` |
| 上下文窗口 | `protocol.rs:187-191` | `bundled_catalog().context_window_for(infer_vendor(...))` |
| 缓存 TTL | `engine_build.rs:944-946` | `cache_ttl_for_provider_model(Some(bundled_catalog()), infer_vendor(...))` |

`protocol.rs:63-67` 注释仍写：「内置表即当前数据真源」。`catalog.rs:346-357` 把 `bundled()` 标成「单测与离线回落」，与发送层实际用法相反。

## 五、给主控总结

Wave 4 把 06 的「花瓶」焊进了 Chat/Responses builder，并加了 live_catalog / compat 优先 API / thinking_map 字段。**发送层一张入参表都没填。** 注释与单测在局部制造「已根除」观感，生产仍是：

1. **厂商与协议**：`url.contains` + `starts_with` + `catalog.json` mode 短名。
2. **思考**：Chat/Responses 默认 OpenAI effort 字符串折叠；Anthropic/Gemini 各用一套硬编码刻度，且两套 Anthropic budget 互相矛盾；yaml 拍平字典进不了出站。
3. **真源**：`catalog.json` bundled 单例仍是路由/白名单/缓存/窗口的运行时真源；`live_catalog` 是死代码；预填库文件隔离合格，128K 与 catalog.json 从侧门泄漏。
4. **假通用清单**（函数在、单测绿、生产不走或走了但入参为空）：`assemble_thinking_dialect` 的字典分支、`live_catalog`、`resolve_*_with_compat`、`WireCompat::from_compat`、`to_chat_messages_with_compat`、`build_reasoning_wire`、`sanitize_outbound_messages`、`build_endpoint_url`、`build_anthropic_headers`、`is_adaptive_thinking_model`（Anthropic 生产轨）。

主控若派实现轮，逻辑顺序应当是：**补 EngineProviderConfig 真源字段 → 发送层改读 live yaml 快照 → 四条出站只留 assemble_thinking_dialect（含 Anthropic/Gemini 变体）且必须带 thinking_map → 删除 URL/前缀生产分支与重复组装器**。在字段断头路还在时继续加「兼容兜底」只会增加多轨。
