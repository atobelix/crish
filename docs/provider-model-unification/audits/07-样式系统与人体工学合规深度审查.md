## 二、输入框与焦点态红线深度核查 (AGENTS.md §13)

### 2.1 阴影与描边硬性指标量化

`AGENTS.md` §13 明确规约：
> “默认不要重阴影：输入框、搜索框、composer 等默认不要加厚重 `box-shadow`，保持干净、扁平、轻量。处于 active / focused 时，**禁止**粗、深、实心黑边（例如直接用 `var(--text-primary)` 或厚重 `0 0 0 1px` 黑环）。”

在 6 个核心审计文件域中：
1. **输入框裸写阴影审查**：
   - 审查结论：**全域 0 裸写输入框阴影**。
   - 证据：`ModelConfigPanel.tsx`、`ModelThinkingEditor.tsx`、`ModelPricingEditor.tsx`、`ProviderProfileForm.tsx` 中所有文本输入与密码输入均统一使用 `import { Input } from '../ui'`，没有出现任何原生 `<input>` 或私有自定义带阴影类名。
2. **样式表 `box-shadow` 审查**：
   - 在 `ModelsSettingsTab.module.css` 全文中，所有 `box-shadow` 均绑定至低空微阴影 Token：
     - `第 19 行`：`.modelsSplit { box-shadow: var(--shadow-sm); }`
     - `第 93 行`：`.mrlItem.isActive { box-shadow: var(--shadow-sm); }`
     - `第 224 行`：`.mrdConfirmPopup { box-shadow: var(--shadow-sm); }`
     - `第 486 行`：`.cascadeList { box-shadow: none; }`
     - `第 497 行`：`.cascadeFlyout { box-shadow: var(--sep-shadow); }`
   - 不存在任何作用于表单输入框或激活边框上的硬阴影，完全符合设计规范。

### 2.2 原子控件集成度与焦点灰度混入比 (3%~10%)

审查各组件消费的底层 `ui/Input` 焦点行为契约（`apps/crish-desktop/src/components/ui/Input/Input.module.css`）：

```css
/* apps/crish-desktop/src/components/ui/Input/Input.module.css:55-63 */
/* 焦点激活态：锁定恒定同一灰度（~8%微调），无论 hover 与否完全零色差，严禁 box-shadow 粗描边环 */
.input:focus,
.input:focus-visible,
.input:focus:hover,
.input:focus-visible:hover {
  outline: none;
  background: var(--bg-card);
  box-shadow: none;
  border-color: color-mix(in srgb, var(--border-color) 92%, var(--text-primary) 8%);
}
```

- **证据核对**：
  - `Input.module.css:61`：`box-shadow: none;` —— 根绝任何发光描边环或扩散阴影；
  - `Input.module.css:62`：`border-color: color-mix(in srgb, var(--border-color) 92%, var(--text-primary) 8%);` —— 混入比例精确为 **8%**。
  - 对标 `AGENTS.md` §13：“灰色加深混入文本色不超过约 **10%**（例如 90%/10% 为上限量级）；常规元素优先约 **3%–6%**”。8% 严格处于安全界限内，肉眼可辨但保持柔和，绝无刺眼黑框。
- **衍生芯片组件微交互审查**：
  在 `ModelsSettingsTab.module.css:695-697` 中，多模态交互芯片在 hover 时的边框强化同样遵守此项规范：
  ```css
  .mrdModalityChip:hover {
    background: var(--tint-hover);
    color: var(--text-primary);
    border-color: color-mix(in srgb, var(--border-color) 90%, var(--text-primary) 10%);
  }
  ```
  精准使用 10% 混入比例，呈现沉稳有节制的交互反馈。

### 2.3 焦点态在深浅主题下的表现对齐

深色模式（`html[data-theme='dark']`）下：
- `--border-color` 在 `tokens.css` 中自动切换为暗部低对比基线；
- `color-mix(in srgb, var(--border-color) 92%, var(--text-primary) 8%)` 动态计算产生的高对比度增量在深色底板上保持数学对偶，不会产生眩光与发白过爆现象。

### 3.2 现代 `hsl(... / a)` 与 `color-mix` 运用深度剖析

`ModelsSettingsTab.module.css` 广泛且规范地落地了现代 CSS Color Module Level 4 语法：

```css
/* apps/crish-desktop/src/components/settings-models/ModelsSettingsTab.module.css:623-630 */
.mrdSubSection {
  display: flex;
  flex-direction: column;
  gap: var(--space-2, 8px);
  padding: 8px 10px;
  background: hsl(var(--surface-secondary-raw, 220 14% 96%) / 0.35);
  border: 1px solid var(--border-subtle);
  border-radius: var(--button-radius, 6px);
}

:global(html[data-theme='dark']) .mrdSubSection {
  background: hsl(var(--surface-secondary-raw, 220 14% 12%) / 0.4);
}
```

- **斜杠透明度典范**：`hsl(var(--surface-secondary-raw, 220 14% 96%) / 0.35)` 优雅解耦了基础色相饱和度明度通道与透明度通道；
- **自适应暗部增益**：暗色模式下透明度微调至 `0.4`，确保次级内嵌微卡片在深浅背景下具有绝对纯净的光学深度。
- **状态混色典范**：
  - `第 699-700 行`：
    ```css
    .mrdModalityChipActive {
      background: color-mix(in srgb, var(--brand, #10b981) 12%, transparent);
      border-color: color-mix(in srgb, var(--brand, #10b981) 40%, transparent);
      color: var(--brand, #10b981);
    }
    ```
    通过 `color-mix` 与 `transparent` 进行比例稀释，彻底告别了手工调配十六进制 Alpha 的粗糙做法。

### 3.3 散落裸写 HEX/预设色违规取证（#10b981 / #fff）

尽管在 CSS 模块中表现优异，但在 TSX 组件层却出现了多处**裸写 HEX 颜色回退值与内联颜色硬编码**，构成 Token 纯度违规：

1. **违规点 1：图标颜色裸写 `#10b981` 降级**
   - `ModelConfigPanel.tsx:153`：`color: 'var(--brand, #10b981)'`
   - `ModelModalitiesEditor.tsx:84`：`style={{ color: 'var(--brand, #10b981)' }}`
   - `ModelThinkingEditor.tsx:93`：`style={{ color: 'var(--brand, #10b981)' }}`
   - `ModelPricingEditor.tsx:57`：`style={{ color: 'var(--brand, #10b981)' }}`
   - **问题定位**：在 Design Token 体系中，品牌翡翠绿的 SSOT 变量为 `var(--brand)` 或 `var(--accent-primary)`，其 HSL 真实源为 `hsl(160 84% 39%)`。四处组件直接裸写十六进制 `#10b981` 作为 fallback，违背了色彩空间统一原则。
2. **违规点 2：保存按钮内联裸写 `#fff`**
   - `ModelConfigPanel.tsx:299`：`color: '#fff'`
   - **问题定位**：系统严格定义了强调色前景文字 Token：`var(--text-on-accent, hsl(0 0% 100%))`。硬编码 `#fff` 绕过了 Token 体系，造成样式资产治理断层。

## 六、交互噪音与深层状态机断层穿透

### 6.1 思考能力“双重开关（Dual Switch）”造成的界面跳跃与自杀隐患

#### 痛点现场复现
1. 在 `ModelConfigPanel.tsx` 抽屉底部的 `CapEditor` 中，包含能力矩阵全套开关：
   `[工具调用] [图像理解] [视频理解] [思考推理]`（`ModelConfigPanel.tsx:244-281`）；
2. 当开启“思考推理”时，`cfgDraft.thinkingEnabled` 变为 `true`，`ModelThinkingEditor` 渲染；
3. 然而，在 `ModelThinkingEditor.tsx:97-102` 的头部，居然**又重复渲染了一个总开关**：
   ```tsx
   <Switch
     size="sm"
     checked={enabled}
     label={enabled ? '已开启' : '已关闭'}
     onCheckedChange={onEnabledChange}
   />
   ```
4. **致命的人体工学瑕疵**：
   - 用户在 `ModelThinkingEditor` 头部点击关闭该开关；
   - `onEnabledChange(false)` 被触发，`cfgDraft.thinkingEnabled` 被置为 `false`；
   - 由于外层是 `{cfgDraft.thinkingEnabled && <ModelThinkingEditor ... />}`, 整个 `ModelThinkingEditor` 组件**连带该开关自身瞬间自杀式 Unmount**；
   - 用户看到屏幕猛烈抖动闪缩，刚刚点击的开关凭空消失；
   - 若用户想重新打开思考配置，必须把视线移到底部操作栏，重新在 `CapEditor` 里寻找“思考”复选框！
5. **根因与改进方案**：
   - 违反单一真理源（SSOT）原则：同一属性不应由两个相邻开关重复控制；
   - 彻底移除 `ModelThinkingEditor.tsx` 内部的 Switch 开关，将思考能力的启闭权 100% 归并于底部的能力矩阵 `CapEditor`；`ModelThinkingEditor` 仅纯粹负责呈现档位映射表。

### 6.2 多模态芯片与 Capabilities 双向同步状态流

审查 `ModelModalitiesEditor.tsx` 与 `ModelConfigPanel.tsx` 的联动：
- `ModelModalitiesEditor.tsx:54-59`：当用户在多模态矩阵中点击勾选/反选 `image` 或 `video` 模态时，通过 `onSyncCaps` 实时向上传递：

- **审查判定**：双向状态保持了绝对的一致性（Bidirectional Invariance），无状态滞后与死锁问题。
