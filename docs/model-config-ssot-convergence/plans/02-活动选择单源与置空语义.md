## 2. 目标态

### 2.1 活动选择唯一源（INV-2）

**唯一源** = localStorage 的**一对**键，**成对读写、成对清除**：

```
crish_active_provider_id  ┐
                          ├─ 必须同时存在才构成有效活动选择
crish_active_model_id     ┘
```

**物理删除 AppSettings 的 `defaultProvider` / `defaultModel` 承载**：
- `persistSelectionToAppSettings`（`profileStoreActivation.ts:99-119`）**整个函数删除**。
- `profileStoreActivation.ts:183` 的调用点删除。
- `clientApi.types.ts:63-64` 的 `defaultProvider` / `defaultModel` 字段：**先确认无其他写入者**（见 §5 未确认 3）再删除；若有其他写入者，一并切除。
- `clientApiDefaultSettings.ts:9-10` 的默认空串同步删除。

**约束**：`crish_settings` 中若有**用户可见**的「默认模型」设置项，其 UI 入口与语义须一并移除（该概念被 U1 取代：无「默认模型」，只有「当前活动模型」或「未配置」）。

### 2.2 成对清除（修复问题 5）

`profileActiveSelection.ts` 新增成对 API，**替代**散落的单独调用：

```ts
/** 一次性读取完整活动选择。两者缺一即视为「未配置」。 */
export function getActiveSelection(): ModelRef | null;

/** 成对写入。禁止单独写其中一个。 */
export function setActiveSelection(ref: ModelRef): void;

/** 成对清除。关闭/删除供应商、停用/删除模型、检测到失效时调用。 */
export function clearActiveSelection(): void;
```

- 保留 `getActiveProfileId` / `getActiveModelId` **仅供展示读取**，但**禁止**单独调用 `setActive*` / `clearActive*`（负向断言，见 §4）。
- `clearActiveModelId` / `clearActiveProfileId` 两个单独导出：**物理删除**，全部改调 `clearActiveSelection()`。

### 2.3 关闭/删除供应商 → 成对清除

| 位置 | 现状 | 目标 |
| --- | --- | --- |
| `profileStorePersistence.ts:207-224` `setProfileEnabled` | `clearActiveProfileId(); clearActiveModelId();` | `clearActiveSelection();`（**唯一清除点**） |
| `profileStorePersistence.ts:193-205` `removeProfile` | 同上 | `clearActiveSelection();` |
| `profileStorePersistence.ts` 的模型删除/停用路径 | 若有 | 同上 |

**同时**：删除模型、停用模型（`modelsCatalogStore.removeModel` / 设为 `enabled:false`）时，若该模型是当前活动选择 → `clearActiveSelection()`。**这取代** `resolveActiveModelAfterMetaChange` 的「同厂商找下一个」逻辑（问题 6/8）。

### 2.4 失效检测统一入口（取代自愈）

**删除** `resolveActiveModelAfterMetaChange`（`ModelsSettingsTab.tsx:64-96`）及其 effect（`:199-222`），改为**单一失效检测**：

```ts
/**
 * 校验当前活动选择是否仍然有效：provider 存在且 enabled、model 存在且 enabled。
 * 无效 → clearActiveSelection()（不查找替代）。
 * 返回是否发生了清除，供 UI 显示引导。
 */
export function reconcileActiveSelection(): { cleared: boolean };
```

- 调用时机：`models-catalog-changed` 事件后（yaml 变了）、`profiles-changed` 事件后（供应商档案变了）。
- **禁止**任何「找同厂商下一个模型」的替代逻辑 —— 直接清除。
- 与 `sanitizeGhostActiveModel`（`profileActiveSelection.ts:62-73`）合并：后者只处理「已知旧种子 id」，前者处理全部失效情形。合并后保留一个函数。

### 2.5 切断反馈回路（修复问题 7）

`ChatHeaderControls.tsx` 的 `useModelSelection`：

| 位置 | 现状 | 目标 |
| --- | --- | --- |
| `:109` | `settingsDefault: appSettings?.defaultModel` 作为解析候选 | **删除该候选**。候选只剩 `storedModel` / `engineModel`（且都须带 providerId，见 W1）。 |
| `:121` | effect 依赖 `appSettings?.defaultModel` | 依赖改为**活动选择变更事件**（`model-changed` 已覆盖）。**禁止**以 settings 字段作为重解析触发源。 |
| `:137-144` | `onUiEvent('model-changed')` 内直接 `setEngineModel`/`setActiveProfileId` | 改为**重新读取** `getActiveSelection()` 后设置（不信任事件载荷），避免载荷与存储不一致。 |
| `resolveHeaderModelFromCatalog`（`:54-92`） | `:80-89` 同厂商首个模型回落 | **删除该回落**：`profileId` 存在但精确校验失败 → 返回 `{ profileId, model: '' }`（显示未配置）。 |

**回路的物理断点**：删除 `persistSelectionToAppSettings` 后，「写回 AppSettings → `appSettings?.defaultModel` 变化 → 重解析」这条边**不存在了**。

### 2.6 置空后的 UI 表现（U1 / N2）

- 活动选择为 `null` → 对话界面模型徽标显示「**未配置模型**」（复用既有 `needsModelSetup` 语义，见 `profileStoreActivation.ts:246-247` 的 `needsModelSetup`）。
- 设置页「全局默认模型」控件（`ModelsSettingsTab.tsx:417-435`）显示**空态 + 引导**，不再显示上一个失效值。
- **禁止**：自动选中任一模型、显示失效的旧值、把 `settingsDefault` 当候选。

## 4. 验收断言

### A 源码形状
- `profileStoreActivation.ts` 中 `persistSelectionToAppSettings` grep = 0。
- `profileStoreActivation.ts` 中 `defaultModel` / `defaultProvider` grep = 0。
- `clientApi.types.ts` / `clientApiDefaultSettings.ts` 中 `defaultModel` / `defaultProvider` grep = 0。
- `profileActiveSelection.ts` 中单独导出的 `setActiveProfileId` / `setActiveModelId` / `clearActiveModelId` / `clearActiveProfileId` grep = 0（只剩 `setActiveSelection` / `clearActiveSelection` / `getActiveSelection`）。
- `ModelsSettingsTab.tsx` 中 `resolveActiveModelAfterMetaChange` grep = 0。
- `ChatHeaderControls.tsx` 中 `settingsDefault` grep = 0。
- `ChatHeaderControls.tsx` 中 `listLivePickerEntries().find` 形式的同厂商首个回落 grep = 0。

### B 本会话真跑测
- **核心负向用例**（本战役最重要的一条）：两供应商 A、B 都含 `same-model`；激活 (A, `same-model`)；关闭 A → 断言：
  - `getActiveSelection()` 返回 `null`；
  - `reconcileActiveSelection()` 报告 `cleared: true`；
  - **不**返回 `{ providerId: 'b', modelId: 'same-model' }`。
- 单测：`activateProfileModel(A, m)` 后，AppSettings **未**被写入（断言 `clientApi.updateSettings` 未被调用）。
- 单测：`clearActiveSelection()` 后 `getActiveSelection()` = `null`，且 `getActiveProfileId()` / `getActiveModelId()` 均 = `null`。
- 单测：停用当前活动模型 → `clearActiveSelection()` 被调用（**不**切到同厂商下一个）。
- 单测：`resolveHeaderModelFromCatalog({ profileId: 'a', storedModel: '不存在' })` → 断言返回 `{ profileId: 'a', model: '' }`（**不**回落到 a 的首个模型）。
- **既有测试必须同步更新**（否则会假绿）：
  - `ModelsSettingsTab.liveRead.test.ts:68-107`（4 个用例断言「同厂商下一个」/「nextActive null」）→ 全部改为断言「一律清除」。
  - `ChatHeaderControls.catalog.test.tsx:155-167` → 断言「置空」。
  - `providerProfiles.test.ts:983-991`（`stored_model_match`）→ 删除或改断言（W1 已删该分支）。

### C 真实宿主用户路径
- **同名模型置空剧本**（`00-总方案.md` §8 剧本 1）：真机建 A、B 同名模型，激活 A 的，关闭 A → 观察对话界面显示「未配置模型」，**不**自动切到 B。
- **反复开关剧本**：连续关闭/启用供应商 5 次 → 断言徽标不抖动、无 A/B 来回跳。
