## 2. 目标态

### 2.1 `loadProfiles` 破坏性回退根除（修复问题 28）

**现状**：
```ts
} catch {
  sanitizeGhostActiveModel([]);
  return [];
}
```

**问题**：这是用户**全部** provider 配置的读取入口。任何 JSON 解析失败 → 静默返回空列表 + 清活跃标记。UI 表现为「无任何服务商配置」，用户配置被隐藏；若后续 `saveProfiles` 被触发，会用 `[]` **覆盖磁盘**。

**目标态**：
```ts
} catch (e) {
  // 显式错误态：不返回 []，不碰活跃标记
  reportConfigLoadFailure({ source: 'profiles', error: e });
  throw new ProviderConfigLoadError('服务商配置读取失败', { cause: e });
}
```

**配套要求**：
1. **禁止**在 catch 内调用 `sanitizeGhostActiveModel`（它会清活跃标记 = 破坏性副作用）。
2. 调用方（`loadProfiles` 的消费者）必须处理该异常 —— UI 显示明确错误（「配置读取失败，请检查配置文件」）+ **禁止**自动降级为空配置。
3. **禁止**在读取失败后允许写入（否则 `[]` 会覆盖磁盘）。写入路径须先确认「读取成功」。

**裁决**：`loadProfiles` 的返回类型从 `ProviderProfile[]` 变为「成功值 | 抛错」。若调用点过多，可引入 `loadProfilesResult(): { ok: true; profiles } | { ok: false; error }`，**但禁止**保留返回 `[]` 的旧签名。

### 2.2 Rust 侧解析失败显式化（修复问题 29/30）

| 位置 | 现状 | 目标 |
| --- | --- | --- |
| `config/profile.rs:66` | `serde_json::from_str(&text).unwrap_or_default()` | 解析失败 → 返回 `Err`（或 `Option::None` 且调用方显式处理），**禁止**静默退化默认态（会导致后续覆盖写回）。 |
| `config/credentials.rs:325` | `.read(&path)…?.unwrap_or_default()` | 读失败 → 区分「文件不存在（合法空）」与「读失败（异常）」；后者返回 `Err`。 |

**约束**：文件**不存在** = 合法初始态（返回默认/空）；文件**存在但损坏** = 异常（返回 `Err`）。二者语义必须区分。

### 2.3 `let _ =` 吞错（修复问题 31）

`config/provider.rs:262`：`let _ = self.credential_store.clear(&self.secret_path);`

**问题**：清除失败被吞，而紧接着 `direct_key_cleared=true` 已落盘 → 状态不一致（标记说清了，实际凭据还在）。

**目标**：清除失败 → 返回 `Err`，**不写** `direct_key_cleared=true`。**禁止**先写标记再吞错。

### 2.4 假成功根除（修复问题 33）

`profileStoreActivation.ts:196-198`：引擎状态核验失败 → 乐观返回 `ok: true`。

**目标**：核验失败 → 返回 `ok: false, error: 'engine_verify_failed'`，**或**返回 `ok: true` 但带**明确的** `warning: 'unverified'`（让 UI 能区分「确认生效」与「未确认」）。

**裁决**：采用后者（返回 `ok: true` + `warning: 'unverified'`），因为切换本身可能已成功，只是无法核验；但 UI **必须**能区分。**禁止**静默返回与「已确认生效」无法区分的 `ok: true`。

**注**：`profileStoreActivation.ts:116-118`（问题 32）在 W2 中已随 `persistSelectionToAppSettings` 一并删除。本维只需确认其消失。
