## 0. 评审视角与总体结论

**总体结论（三条）**：

1. **6 份方案对维度的「再拆细」总体正当、一致，无互相矛盾到不可合并之处**；所有提出拆细的方案都遵守了「禁止弄粗」纪律（没有一份方案把维度合并变粗，方案 D 明言「保留全部 14 维不合并不弄粗」，方案 F 全部为再拆细/新增）。唯一新增维度（方案 E 的 T5 完整性）与基线 14 维框架的 00-summary 缺口一致（18 审计 P0/P1 未入任何维度），**建议采纳**。
2. **轮次冲突的根因不是「顺序标错」，而是「各家执握不同的依赖面」**（A 从时间线、B 从核心循环、C 从能力层、D 从撤回/插件、E 从前端、F 从横切治理），各自给出的执行轮天然不同。它们之间**真实存在的、必须优先裁决的依赖排序分歧**集中在 5 处：T2 与 C1a、T1 与 P1、R1 的位置（压轴 vs 前移）、V1 与 T4 是否同文件合批、E1 是否有迁移前置。本评审逐一给出合并裁决（见 §3.2）。
3. **工作量失衡主要来自两个方向**：T2（持久化轨收敛）被所有方案判为「全战役最危险」，但在基线 14 维里它只占一维、却被拆成三步（剥镜像→删轨→删死层），是一份超重维度；V1/F1（尤其方案 C 拆出四段：F1-α/β/γ、V1-α/β/γ/δ）被拆到很细。**终版维度清单应把「按原子搬移批次拆子项」保留为「子段」而非「独立维度」**，否则轮次数膨胀到不可调度（见 §4）。

### 关于「15 维改叫 17 维」的说明

不把 T1a/b、T2 三段、C1a-d、P1 α/β、V1 α-δ、F1 α-γ、R2 a/b 计为独立维度。理由（反过度设计与可调度性）：

1. 这些是**同一个概念的完成工序**，不是**不同概念**（协调纪律 §零.1「推进单位是领域概念」）。
2. 若把每个子段升维，轮次数会达 20+，超出主控「每轮 5–12 Agent」的可调度粒度，且大量子段属**串行删除工序**（T2 三段、C1 四段），独立成轮只会空耗审计位。
3. 维度间合并（把 T5 并进 F1、把 X1a/b 并进 X1）都是**概念不同**（完整性 vs 原子化、未接线 vs 命名），合并会弄粗，违反纪律。

**建议的最终里程碑口径**：主控调度时以「15 维 + 每维内子段」为单位，子段用于**平衡 Agent 数量与工作量**（附录 B §6），不用于膨胀轮次编号。

## 3. 合并后的执行批次方案（③ 合并后的执行批次方案）

### 3.1 先裁决 5 处跨方案依赖分歧

（这些是本评审对「批次表」的直接输入，§1 各表已标注）

1. **C1a 与 T2 的先后**（A vs B）：A 认为 C1 可全程并行（在 T1a 后）；B 明确 C1a（压缩编排外置）**必须 T2 后**（压缩记录落库/重放依赖 conex-db 唯一落点）。**采纳 B**：C1a 排 T2 之后；但 B 也指出 C1b/C1d 不需要 T 层，可提前并行。
2. **P1 与 T1**（A/C 一致）：P1-α 的 ToolCategory 真类别、I1 的 context-state 依赖 T1 类型落地。**采纳**：P1/I1 在 T1 打底后。
3. **R1 的位置**（A 压轴 vs C/D/E 前移）：**折中裁决**：R1 不在最早也不在最后。R1 六步中的①事件+②停 run+③回滚（依赖 T1/C1/P1 类别轴）可在能力层中段推进；④投影刷新依赖 V1 投影链。因此 **R1 的主体放在 V1 收口之后、与 F1/E2 同收口批**，但 **R1 的「事件类型 + seq 定位原语」随 T1 先行定义**（不做事后补）。采纳 C「R1 依赖 T1 不依赖 T4」与 E「R 在 T4/V1 后」的交集：**R1 依赖 T1/P1/C1（硬）+ V1（软投影）**。
4. **V1 与 T4 是否合批**：采纳 E，同批推进不跨轮（见批次表 R5）。
5. **E1 有无迁移前置**：采纳 D（无迁移；删前真跑复核 G1），击败 E 的「先迁 settings-extensions」。

## 5. 执行轮设计校验结论（⑤ 轮次设计校验结论）

对照 6 份方案轮次，校验三条硬纪律（协调纪律 §四）：

### 5.1 并行按概念互不相交 ✅

- 所有合法并行对都落在「不同概念 + 不同文件域」：T1a∥C1d∥F1-α（crates/定义 ∥ session-loop ∥ 前端 ui）；T1b∥T2-1∥I1-α（mobile ∥ 前端持久化 ∥ session-loop 队列）；P1∥I1-β∥V1-δ（审查 ∥ 注入 ∥ 渲染）；R2-a∥F1-β∥E1（编辑 ∥ 原子化 ∥ 插件）。
- **不合法并行已被排除**：C1a 不与其同批涉及 conex-db 的写放大并行（B 裁决）；R1 六步内串行不拆并行（先停后截原子性）；T2 三段严格串行（先删后改）；E2 不先于 E1（清场前置）。
- **边界修正**：方案 A 的「V1 与 R2 前半并行」（A 轮7）与方案 C 的「F1-β 等 V1-δ」、方案 D 的「R2-a 提前」在合批后已合并遵守；方案 E 的「T4 与 V1 同批」已采纳（R5）。

### 5.2 完成定义 = 功能 + 负产出 ✅

- 每批都显式列出「**功能验收 + 负产出（删除/收敛）**」。关键：R1（撤回）是「新建能力 + 负产出少」的轮——按纪律「纯新增领域且无旧路径可删的，须主控预先注明豁免」。**R1 轮需主控在任务书中预先声明豁免条款或补一个删除动作**（如 kill_all 语义文档化 + tool-update 变体收口归此批，方案 B/C 建议的删 tool-update 死契约），否则 R6 按「无删除不算完成」会被挂起。⚠️ **这是一个必须预先处理的轮次设计点**。
- 方案 F 的公式（硬删除指标 + grep 零命中 + 净删除行数 + 门禁）作为 R0 后每轮的固定校验，采纳。

### 5.3 每轮嵌入审计位 ✅

- 批次表每批 ≥1 审计位（①a 完成定义/假收敛 + ①b 度量表或①c 连通），与 02-细化版任务书硬化条款 6 一致。方案 B 的「C1b 壳层装配真跑」、方案 D 的「G1–G6 真跑复核」、方案 E 的「CDP 9222 验收」、方案 F 的「审计位回填度量 Δ」均应写入对应批任务书。

### 5.4 X1 穿插是否与功能轮冲突

- **不冲突，正确穿插**。方案 F 论证最充分：X1 分「R0 前置（脚本校准）」+「R6 前 P0/P1 低风险波次」+「R8 集中冲刷（P2/P3/P4 高 import 联动）」。
- **唯一需注意的冲突点**：X1 的 P2 批（w5bStrict/w5bSkeleton，12+ import）须在相对的前端模块（note-paper/workspace）稳定后做，故排在功能轮中后段而非 R3；P3 批（w6 轨 Skeleton）依赖 E1 对 note_w4c/w6 的死活裁决，故在 R8（E1 之后），符合「贴目标模块稳定节点」。
- X1 与功能轮文件域有轻微重叠（波次文件常即 T2/V1 的删除对象），需用「审计位去重 + D0 删除清单」避免同一波次文件被 X1 与功能维各改一次（方案 F §3.3 正交证）。
