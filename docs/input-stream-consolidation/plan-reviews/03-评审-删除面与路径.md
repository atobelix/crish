## 0. 评审视角与总体结论

**总体结论（三条）**：

1. **6 份方案绝大部分删除项归属维度一致、未出现「同一对象被不同方案各自计为净删除重复累加」的实质性重复计数**。一个对象被多方案「点到」，几乎都是「主改方独占 + 他方在引用/对齐段顺带点名」的共享归属，而非各方案都把净行数算进自己口袋。唯一**确凿的归属冲突**是 `shared-types/permissions.ts` 死类型族——方案 B（02）在 E2 段（D-E2-1）列为删除主张，方案 C（03）在 P1 段（§6 #3）列为删除，方案 F（06）又记在 P1/09 下。同一文件被三个方案挂到两个维度（P1 vs E2），必须主控定夺归属。
2. **框架基线 `plans/01-细化版` E1 的「先迁 settings-extensions 消费」前置，是方案 04 已正确修正的口径错误**。本评审**实查**确认 `settings-extensions/pluginRegistryAdapter.ts` 只 import 外部 npm 包 `@crish/plugin-import-claude-codex`、`buildInstalledExtensions.ts`/`useExtensionMarket.tsx` 的数据源来自 `listPluginCardStates()`，**不 import `src/plugins` 任何符号**；全树 `src/plugins` import 边为 0（仅 plugins 目录自举 + 测试）。因此删除 `src/plugins` **无迁移前置**，方案 04 的「直接删」裁定正确，其余方案照抄基线的「先迁再用」表述应统一为「直接删」。
3. **净删除行数量级（源码形状估计）≈ 6,000–8,500 行**，大头是死层（`src/plugins` ~2,347 行、`messageUserProjection`+调试 ~850 行、`append_session_messages` 死库 + 陪葬、`note_w4c_contribute` ~896 行、手写消息类型 + 重放解析）。但其中**相当一部分「删除」其实是「收敛/降级/拆段」而非整文件删**（双存储冗余副本、折叠重分组、Tiptap 拆分、C1 压缩编排外置），真正的无争议死层整删约 4,000 行为主。删除裁决前所有「零命中」都必须过一次真跑作机器证据（review §23.5）。

## ③ 证据一致性核对

### 3.1「settings-extensions 消费 src/plugins」是**误读**——方案 04 修正正确（本会话实查）

- 框架基线 `plans/01-细化版:79` 与方案 05（:142/:211）、01（:279）均写「先迁移 settings-extensions 消费（useExtensionMarket/buildInstalledExtensions——主控已亲验存在引用）再删 src/plugins」。
- **实查反驳**：`apps/crish-desktop/src/components/settings-extensions/pluginRegistryAdapter.ts:13` import 的是外部 npm 包 `@crish/plugin-import-claude-codex`（独立 third-party 包），**非 `src/plugins`**；`buildInstalledExtensions.ts:8` import `PluginCardState` 自 `./pluginRegistryAdapter`，`useExtensionMarket.tsx:25,33` import 自 adapter + buildInstalledExtensions。整条 settings-extensions 插件卡片链**不 import `src/plugins` 任何符号**。全树 `from '.../plugins` import 边仅命中 plugins 自身（自举）+ `markdownPlugins`（同名异物）。
- **结论**：`src/plugins` 是**零外部消费死层、无迁移前置**，方案 04 的「直接删」正确；其余方案/框架的「先迁再用」表述应统一更正为「直接删」。✅ 与 audit 16 §④ D1「import 边=0」一致。

### 3.2 `persist_plugin.rs`「双实现疑似」——实为 newtype ARC 转发，**非重复实现**

- audit 15 §③ gap3 与 00 草案 §1 标「persist_plugin.rs 疑似双实现 on_committed_expect（:71 与 :226）」。
- **实查**：`persist_plugin.rs:71` 是 `impl PersistencePlugin for WorkspaceStore` 的真实 CAS 实现；`:212-233` 是 `impl PersistencePlugin for SharedWorkspaceStore`——newtype 包装（:178 注释「因 orphan rule 不能直接 impl PersistencePlugin for Arc<WorkspaceStore>」），其 `:227 on_committed_expect` 只是 `self.0.on_committed_expect(...)` 转发。**不是双实现**而是孤儿规则下的 ARC 代理。
- **结论**：方案 04 G7「:227 ARC 转发若被误当重复实现删除，CAS 生产失效」判定成立——**此文件 NOT 一个删除面，R2/15 无需「清理双实现」**，归为「澄清，变更删除面则删除」项。⚠️ 删除面总表不列此文件。

### 3.3 `append_session_messages` 登记面——审计一致，但登记面清理需主控定夺

- 方案 01 R3 提出「append_session_messages 是『登记先行 registered=false』注册面一部分，直接删可能破坏登记面不变量」。

- **结论**：审计与方案 **不一致点不存在于「是否死层」**（一致：死库函数，无命令/manifest/前端调用），仅存在于「清理登记面注释是否连同库函数一起清」。主控裁决：清函数 + 修注释为「已删除」即可，无需保留占位。✅ 实质一致。
