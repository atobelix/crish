## 1. 模型不变量（✅ 已由审计确认）

1. **一切皆文本节点**：会话内所有内容（用户/系统注入/状态/工具调用/工具结果/思考/AI 正文/截断标记）都是带类型标记的文本节点 `{ id, seq, ts, type, text, meta }`。证据：message.rs 块类型（01 审计）；缺口：缺 context-state / injection / truncate 类型（02 审计）。
2. **唯一时间线（事件流为骨架）**：事件流只追加、seq 单调、记录唯一；message-start/delta/end 已是事件；engine 只写 events 表（01 审计 ✅）。**推论：任何「删除」都是逻辑截断（新事件），不是物理删除**（§2.4 撤回设计）。**例外反例（收敛目标）**：crish-mobile `eventsDao.ts:148`（`DELETE ... sequence<?`）与 `cachePolicy.ts:206`（窗口物理删除）破坏只追加（10 审计）。
3. **投影派生**：消息表、前端消息类型、展示视图都是事件流的投影，不是第二事实源（01/04 审计 ✅）。
4. **单路径**：每个概念只有一条主路径；并行实现一律收敛或删除（收敛版纪律）。
5. **核心循环不知道扩展**：核心只暴露「事件出 + 钩子/注册表入」，永远不反向依赖具体功能（待 09 审计细化规则）。
6. **节点有状态生命周期（✅ 13/14 审计确认）**：内容分「进行中（ongoing）」与「终态（settled）」两态——**进行中由增量事件表达**（delta/progress，背压 Delta 级可丢、NoPersist 不落库，展示层消费），**终态由必达事件表达**（end/result，Critical 级落库，事实源）。展示规则按类型分派：thinking/工具输出可流式展示；写文件等过程**有状态但不流式展示**（只展示状态/进度）。现状基础（主控侦察）：`BackpressureLevel`(Delta/Soft/Critical) + `PersistenceLevel`(NoPersist) 已存在（events.rs:183-238）；`ToolProgressUpdate` → tool-progress 事件已存在（tool_events.rs:112）；前端 `streamingStore byKey` 中间态已存在（streamingStore.ts:37）；`write_paths` 声明状态机已存在但**无进度流**（write_paths_state.rs）。

**14 审计确认（执行过程状态）**：

- **run「进行中」无事件**：RunStatus 9 态只在 runs 表落库（runs.rs:20-35），过渡历史不进事件流，唯一出站 = 终态 `run-terminal`（events.rs:612-620）；前端靠 `activeRuns` 轮询派生「在跑」——**无法从事件流重放 running→awaiting→completing**。落点建议：新增 `run-state-changed`（Delta 可丢）或前端从现有事件派生（二选一，主控定夺）；
- **tool-update 是空转死契约**：`ToolUpdate` 变体存在但无执行器发射，`event_policy` 无显式分支落入默认 Persist（与 NoPersist 注释矛盾）——**接入发射或删变体，二选一收口**；
- **审批挂起 = 「进行中」正面范例**（approval-requested 先发防死锁 → 超时 Expired 引擎权威落库 → run awaiting-approval → 前端 pending_approvals）——**统一模型「进行中状态节点」的模板**；
- **pty 判为非时间线外部域**（用户终端，workbench:// 侧信道，不进事件流不落库）；AI 命令走后台任务域（task 终态落库、output/heartbeat NoPersist，事实源 = 日志文件）；
- **写文件不新增进度事件**（14 建议，反过度设计）：ongoing 由 tool-start 承担、tool-end + 工具角色消息收口即可；claim 是内存并发控制非展示态。

**13 审计确认（流式与增量状态）**：

- **text/thought 已完整事件化 ✅**：DeltaSink 实时轨 → `message-delta`（Delta+NoPersist+Soft，桥可丢）→ 前端 eventParser → onChunk/onThought → batcher → streamingStore.byKey → view model → 组件；`message-end`（Critical 永不丢）全文兜底恢复增量丢失；**thought 由 message-delta 携带**（ThoughtDelta→Thought block）——「进行中=增量事件」在正文/思考上已成立；
- **tool-update 前端零 UI 消费**：`onToolUpdate`（toolHandlers.ts:25-30）显式空实现，tool-progress 文本无展示落地——「工具运行中」非真流式；
- **tool-update 落库语义错位**：= Critical+Persist（engine-events.json:318-320，event_policy catch-all），**是落库的**，与不变量 6「进行中=增量=NoPersist」相悖（tool_events.rs 注释「不进消息历史」指对话缓存前缀，易误导）——**收口时必须修正为 NoPersist 或删除**；
- **前端无统一「节点状态维度」**：streamingStore 是 text/thinking/tools 三个独立字段，无类型化节点 {type, state: ongoing|settled}；ThinkingTimer/ThoughtOutline/run 中间态全是前端私有态（非事件流驱动）——**统一节点模型重构的落点**；
- **双轨撕裂风险**：onChunk 回调 vs message-end 兜底 diff，丢帧窗口内 UI 可能跳变（G1–G7 缺口清单在 13 审计文档 §④）。

7. **编辑保护（✅ 15 审计确认）**：被编辑的对象（草稿/消息/笔记块/设置）处于「编辑会话」时，必须与后端状态有失效契约——**对象提交/失效后，编辑面立即失效**，禁止「UI 还在编辑、后端已发送/已覆盖」的撕裂。**落点（15 审计）**：对象版本契约（对象级 rev 对齐 CT-01 乐观并发）+ 编辑会话事件（open→commit/invalidate，**进行中维度的独占子类，不可丢**）+ 失效传播（引擎截断/撤回/远端合并 → invalidate 编辑中对象）；复用 write_paths 状态机与 lease_guard 作「编辑持有」先例，**不新增全局锁**。**与不变量 6 对称**：引擎侧 ongoing（流式/运行）与用户侧 ongoing（编辑中）冲突语义须统一。

**15 审计确认（编辑保护与状态一致性）**：

- **前端无「编辑会话」抽象**：`StrictContentRowLeaf.tsx:133 dirtyRef` 是**开环脏标**（置 true 永不复位，叶与投影永久脱节）；草稿快照（slashSendDraftManager.ts:18）是一次性瞬态、发送即毁——均非持久编辑持有；
- **CAS 真身 = CT-01**：乐观并发 CAS 在 `conex-doc-collab/persistence.rs:64-72` + `conex-workspace-store/persist_plugin.rs:71-121`（`WHERE doc_meta.rev=?` → affected==0 → `PersistError::Conflict`，已接 emit_commit + P-H2 回滚）；**注意 `cas.rs` 是内容寻址 blob 存储、非并发控制（命名撞词）**；`persist_plugin.rs` 疑似双实现 `on_committed_expect`（:71 与 :226）需核唯一接线；
- **死枚举**：`MessageSnapshots.ts:124` 的 `operation:'edit'` 无生产写入方（回滚面留位无人接线）；产品无「编辑已有消息正文」能力（唯一状态迁移 = completed→processing(regenerate)）；
- **场景 1 竞态残留**：双 follow_up 机制并存（useSlashSend enqueueFollowUpMessage ∥ composer onSend 队列），`editQueuedMessage` 移回编辑时 drain（useChatComposerProps.ts:473）仍可能抢跑发送队首——**编辑中 vs 后端队列竞态窗口仍在**（drainLock 只防重入不防抢跑）；
- **失效传播缺失**：collab sink（intentBridge.ts:253-312）对 conflict 仅透传 `{ok:false,reason}` 无本地乐观撤销/合并；设置页 profiles 一次加载、refresh 仅手动——外部变更不失效 cfgDraft，陈旧草稿 LWW 覆盖。

## 3. 前端架构原则（✅ 12 审计已确认 · 11 组件审计待收）

1. **单一数据流**：事件流 → 投影 store（唯一）→ view model（纯函数派生）→ 原子组件（纯渲染）。
2. **原子组件模型**：原子层（纯 props、禁 store、token 化样式）→ 业务复合层 → 页面壳；组件只消费 view model，不直接读事件/store。
3. **前端类型收敛**：全部从 generated 绑定派生，禁止手写第 N 套消息类型（01 审计：现 7 层形态）。
4. **状态归属**：业务状态进投影 store；UI 瞬态（输入框/悬停/折叠）留在局部；禁止全局 store 存 UI 瞬态（review.md §4）。

**12 审计实证（现状反例 → 收敛方向）**：

- **上帝 store 仍在**：`layoutStore.ts:141-185` 单实例混装布局 chrome + 会话域（sessions/messages）+ legacy workspace 三域（T11 只拆了 terminal/worker/permission/settings）；
- **消息双份存储**：`EngineEvent → streamingStore（中间态 byKey）→ streamMessageViewModel 投影合并 → 组件`，run 收口再 `commitStreamToSession` 写回 `layoutStore.messages`——同一正文/工具在两个 store 各存一份，靠 `queueMicrotask clearStream` 时序闭环防撕裂（review.md §4 多源真相典型表现）；
- **storeAccess 三份**：`store/storeAccess.ts`（读面）∥ `api/storeAccess.ts`（编排）+ `api/store-access/componentAccess.ts`（过渡读面，自证补齐后删）；
- **展示投影双实现**：timelineNormalizer（主渲染）∥ messageUserProjection/UserView（旁路，复核 04）；
- **收敛目标**：单一时间线投影 store（事件流派生 + 派生选择器 + 局部 UI 态）；streamingStore 消息部分与 layoutStore 消息部分合并；删除面 = componentAccess、UserView 旁路、legacy open-tabs 双写、7 层消息类型。

### 3.1 前端核心 vs 扩展划分（草案 · 待 16–19 审计实证）

**前端核心（最小完整产品 · 无任何扩展也必须完整可用）**：

- 会话域：会话列表/打开/切换/删除/持久化（投影 store 消费）；
- 时间线渲染：投影链（事件 → 投影 store → view model → 组件）+ 消息流 + 流式状态（不变量 6）；
- 输入域：composer 输入/发送/停止/撤回入口 + 编辑保护（不变量 7）；
- 审批交互：allow/deny/ask 的用户界面；
- 设置基础：入口 + 主题切换 + 模型选择；
- 原子组件基座：ui/ 原子层 + token + **完整性三件套（错误边界/空态/降级态）**；
- **完整性不变量：核心 UI 不得 import 任何插件/扩展；扩展缺失/加载失败时核心界面完整**（待 18 审计验证现状）。

**前端扩展（可插拔 · 缺失时核心仍完整）**：

- 展示归类（工具折叠行/图标/目的描述，D4 承载）；
- 富文本/编辑器能力（Tiptap/block-paper）；
- markdown 渲染、follow-up、导入导出、浏览器/电脑工具 UI、通知；
- 可定制面：主题定制、布局定制（layout-tree）、provider profiles、权限配置（待 17 审计厘清）；
- 插件轨：PluginRegistry 承载的 contribute（slash/block-view/widget/keymap，B 轨待收口）。

**划分准则（与 §7 判定一致）**：核心 = 参与「会话时间线」渲染与输入闭环的必需 UI + 完整性三件套；扩展 = 有独立策略/可配置/缺失不影响时间线闭环；**边界模糊时判扩展**。

## 5. 架构设计方向（草案）

1. **分层**：事件核心（crates，唯一事实源）→ 投影/服务层（从事件派生，可插拔）→ 壳层（IPC 薄层，禁止业务逻辑——现状 src-tauri 105k 行为反例，列入收敛目标）→ 前端（投影消费 + 原子组件）。
2. **依赖方向**：核心 ← 投影 ← 扩展 ← 壳；禁止反向（review.md §1）。
3. **插件化边界**：扩展点 A/B/C/D 是插件可承载面；Rust 侧用 ToolRegistry + 统一门面（05 审计 ✅ 现成等价物）。

## 7. 抽象纪律（反「抽象层太多」· ✅ 已有反例实证）

**问题不是缺抽象，是表示层爆炸**——同一概念在代码里被复制成多套类型/分类，每套都自称「抽象」：

| 反例（实证）                                                                                                                                           | 证据               |
| ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------ |
| 同一条消息 7 层类型形态（Rust AgentMessage / SessionMessage / HistoryMessage + TS SessionMessage / MessageTimelineBlock / HistoryMessage + generated） | 01 审计            |
| 插件机制 4 套互不接线的类型/路径（plugin-sdk 运行面 / 轻量 Plugin / CrishPlugin / Rust ContributeViewRegistry）                                        | 05 审计 + 主控亲验 |
| 权限判定 2 套发散分类（引擎 dangerous+模式 vs 前端正则表）+ 4 处互不调用的命令判定                                                                     | 03 审计            |
| 死类型残留（PermissionBehavior 无实活；shared-types/permissions.ts 接口族零消费）                                                                      | 03 审计            |

**五条抽象纪律**：

1. **一个概念一种类型**：跨边界（Rust↔TS）契约一律 generated 绑定派生，禁止手写第 N 套；类型定义只存在于唯一权威处（现状：conex-types + scripts/generate-engine-bindings.mjs）。
2. **接口两实现法则**：抽象接口只在**已有 ≥2 个真实实现**时才成立；单一实现一律直接用具体类型（反例：PermissionBehavior 死类型 = 抽象过早；正例：DSH session-persistence 有 jsonl/sqlite 双实现 → 抽象合理）。
3. **分层上限三层**：核心 → 投影/服务 → 扩展/壳；每层必须有**真实消费者**，禁止为「未来」建层、禁止为对齐而加中间层。
4. **优先事件 + 注册表，避免 trait/继承树**：跨功能协作走「事件出 + 注册表入」（数据驱动）；只有行为变体才用策略/接口。
5. **新抽象必须可立即删除**：无消费者 = 死类型 = 删除候选（每轮收敛度量表追踪）；合入前 grep 零消费者即退回。

**核心 vs 扩展判定准则**（供 08 盘点分类与详案使用）：

- **核心**：参与「时间线推进」（产生/消费节点、推进 seq）且任何会话都必须存在的逻辑（输入/请求构建/流式/工具执行/裁决/事件落库）。
- **扩展**：有独立策略语义、可配置可替换、或只消费时间线不推进时间线的逻辑（注入时机/提交时机/审查/撤回/压缩/汇总/标题/展示归类/通知……）。
- **边界模糊时判扩展**：宁可外置后证明必须核心，不可塞进核心后难以拆出。
