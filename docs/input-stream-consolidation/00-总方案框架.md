# 00 · 统一输入流收敛战役 · 总方案框架（草案）

> 状态：**草案，待用户确认两个决策点后进入详案阶段**（见 §6）。
> 性质：本文件是「统一输入文本流」概念收敛的总纲；按收敛版纪律，所有条目只谈逻辑顺序，不含时间/优先级；执行轮次必须含删除动作。

---

## 1. 战役目标

围绕「**所有内容皆为带类型标记的输入文本 + 唯一时间线**」这一统一模型，收敛 Conex 的消息/事件/会话时间线/权限/展示/插件六个概念域：

- **单路径**：每个概念只保留一条主路径，删除并行实现与死层；
- **唯一时间线**：会话内一条事实流，记录唯一、幂等；
- **插件化边界**：注入时机、提交时机、审查策略、展示归类全部成为扩展点，不混入主逻辑。

---

## 2. 概念模型（愿景形式化）

### 2.1 节点与时间线

```
节点 Node = { id, seq, ts, type, text, meta }
时间线 Timeline = 会话内唯一、只追加、seq 单调、记录唯一（id 幂等）
```

- `type` 是唯一的类型标记（user / system-injection / context-state / tool-call / tool-result / thinking / assistant-text …）；
- `text` 是唯一的载荷（**一切皆文本**）；
- `seq` 由事件层统一取号（现状：conex-db events 表 sequence 已存在）。

### 2.2 来源四类

| 来源         | 定义                                                                 | 产生时机                                        |
| ------------ | -------------------------------------------------------------------- | ----------------------------------------------- |
| 静态注入     | 系统提示词、agent 文件等预加载文本；目的：省解释成本、让 AI 了解环境 | 会话开始/恢复时装载                             |
| 动态状态注入 | 模型名、命令权限、思考模式等用户实时切换的状态                       | 挂到用户下一次提交（或即时通知——扩展点 A）      |
| 用户命令     | 用户输入                                                             | 提交时机可选（即时插队 / 汇总后队列——扩展点 B） |
| AI 产出      | 思考、工具调用、正文                                                 | 流式产生                                        |

### 2.3 扩展点与派生层

- **扩展点 A（注入时机）**：状态切换 → 即时提交 vs 挂用户下一条命令（现状已有半成品：steering nudge 走 PendingNudgeChannel 排入下一条用户消息队列）；
- **扩展点 B（提交时机）**：即时插队（等 AI 完成当前输出后提交）vs 正常队列（现状已有雏形：chat-bridge auto follow-up queueing）；
- **扩展点 C（审查策略）**：工具调用执行前按工具类别分类判断是否需要审查（allow / deny / ask）；
- **展示投影**：时间线的纯逻辑归类（连续工具调用折叠行、工具调用目的描述、官方命令类型图标）；
- **不变量**：时间线唯一、记录唯一、文本是唯一载荷。

### 2.4 时间线操作：撤回（Retraction）设计草案（✅ 审计 10 已验证）

撤回是对时间线的**截断操作**，不是消息删除：

1. 用户在 UI 对某个 user 节点发起撤回 → 定位该节点 seq 为截断边界；
2. 停止当前 run（**成熟可复用**：L0–L3 控制总线 control.rs:30 → 安全点 safe_point.rs:119 → aborted 收场 → `RunTerminalStatus::Cancelled`；子代理级联停止 = orchestrator kill_all，已有集成测试），**先停后截**，保证截断后无新写入；
3. 发出 `timeline-truncate` 事件（携带 boundary seq）——**事件流只追加不变量保持**：旧事件保留（审计/恢复/重放），投影层在 boundary 后重建；**注意：全仓零先例，须新建事件类型**（10 审计）；
4. 副作用回滚策略（扩展点 D）：按工具类别分类——文件写入类走 **conex-fs/trash.rs 写前快照回滚**（snapshot/restore_force，现成底座但未被撤回调用）；git 类走 revert 门禁（revert_guard 仅审批门禁，非文件回滚）；**工具缺「可回滚性」标记**（ToolCategory 恒 Internal），需新建「类别 → 回滚策略」注册表；**与 D3 权限注册表共用「工具类别」轴**；
5. 投影刷新：前端时间线从事件流重放至 boundary（先例：compaction cut_point / 前端 withdrawMessage，但非按 seq、不落事件、不联动停 run——需升级）；
6. 文本回收：被撤回的用户消息文本退回 composer（**注意：draft 快照发送成功后即清除，须从 boundary 对应 user 消息取回文本回填**，10 审计）。

**扩展点 D（撤回策略）**：不同消息类型/工具类别可插拔撤回策略；撤回本身是插件可承载的操作。

**并发边界（10 审计）**：流式中/工具批执行中/审批挂起中的取消传播均已覆盖（L3 可立即打断、工具批 abort 竞速、审批竞速有裁决）；**注意**：kill_all 对子代理终态归一为 failed 而非 cancelled（撤回语义需评审）；审批已批准待执行项由 D 策略裁决。

**只追加不变量例外（收敛目标）**：crish-mobile `eventsDao.ts:148`（DELETE sequence<?）与 `cachePolicy.ts:206`（窗口物理删除）破坏只追加——撤回依赖历史时不可重放，须收敛（或显式降级为「已淘汰不可审计」）。

## 5. 核心决策（待用户确认 ①）

**决策：事件流为唯一时间线骨架，文本节点为事件的规范载荷形态。**

- 事件 = 骨架（时序、幂等、审计、恢复）；
- 节点 = 内容（一切皆文本，type 标记分派）；
- session_messages 表与前端全部消息类型降级为「从事件流派生的投影」；
- 不另建消息时间线（现状 message-start/delta/end 已是事件，无分叉理由）。

## 6. 维度框架与逻辑顺序（待用户确认 ②）

| 维度          | 做什么（含删除面）                                                                                                                    | 依赖     |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| D1 统一时间线 | 事件流唯一事实源；删 localStorage 轨 / RustDb 前端轨 / 前端 ≥5 套手写消息类型（改 generated 派生）；session_messages 明确为投影缓存   | 起点     |
| D2 注入文本化 | 静态注入（系统提示词/agent 文件/steering）统一为注入节点产生器；新增 context-state 节点（模型名/权限/思考模式，挂用户提交，扩展点 A） | D1       |
| D3 权限注册表 | 工具类别 → 审查策略（allow/deny/ask + 询问规则）单一路径；commandPermissions + approval_router + exec_verdict 合一                    | D1       |
| D4 展示投影   | 投影层从统一时间线派生（去 ModelView 中间态）；折叠工具行/目的描述/官方图标转为插件承载面                                             | D1       |
| D5 插件边界   | plugin-sdk 承载扩展点 A/B/C；评估 Rust 侧插件运行时；四个官方插件收编                                                                 | D2/D3/D4 |

**逻辑顺序**：D1 → D2 → D3 → (D4 ∥ D5)。**验收口径**：概念路径数 = 1；前端消息类型零手写重复；未接线标记清零；事件流是唯一写入路径；每轮完成定义含删除动作（收敛版纪律）。

> 撤回能力横跨 D1（时间线截断）/ D3（回滚按类别）/ D4（投影刷新）/ D5（撤回策略插件化），设计见 §2.4，专项审计见 analysis/10。
