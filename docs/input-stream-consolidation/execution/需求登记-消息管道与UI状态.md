## 二、UI 状态与显示设计

### A. AI 最终总结区的「半动态挂载」

- 用户未发下一条消息时，最终总结行 = **半动态挂载态**：后台任务可能继续发消息、子 agent 跑完后回传消息——最终区可能被追加/更新。
- 模型对应：不变量 6（ongoing/settled）——总结区在「用户下一条消息到达前」视为 ongoing 的接收区；节点追加时投影刷新该区。
- 建议落地：V1（展示投影归一）后评估，属投影层规则（总结区 = 可追加容器，非终态块）。

### B. 组件状态化显示

- 计划模式 / goal 模式 / 任务列表：显示有状态——**状态标记完成 → 可隐藏/折叠**（无显示必要）。
- **子 agent 例外**：即使被关闭（completed），**仍须显示在 UI 中，仅状态标记为完成**（用户需要看到「曾派发过哪些子 agent」）。
- 模型对应：不变量 6（状态生命周期）+ 投影层显示策略注册表（节点类型 × 状态 × 显示规则）。
- 建议落地：V1/D4 投影层 + 显示策略注册表（E2 登记）。

### C. 通知组件状态机

| 形态                        | 行为                                                                                   |
| --------------------------- | -------------------------------------------------------------------------------------- |
| 临时通知（自动消失）        | 定时消失（现有 Toast 体系）                                                            |
| 临时通知（状态判定消失）    | 如总结结尾处的通知——随总结区状态变化消失                                               |
| 动态组件（首 token 慢动画） | AI 首 token 延迟时显示动画（暗示「没问题，只是延迟高」），首 token 到达即消失          |
| 动态组件（网络重试）        | 重试中显示；**成功即不显示（即使失败后成功也不显示）**——只对用户可见的持续失败保留提示 |
| 其它                        | 后续按需扩展（状态机：pending → visible → resolved 即消失 / failed-persistent）        |

- 模型对应：通知 = 独立状态带（配置/偏好投影类似——不进消息 seq）；状态机 = 前端通知域。
- 建议落地：T5（完整性与容错）或 R9 后前端小战役；**网络重试「成功即消失」语义**与 18 审计（离线/重连多层可见面）衔接。

### D. UI 按钮行（小需求）

- 只在**用户消息下方** + **每轮 AI 最终总结区**显示操作行（复制/基础信息等），防止大量按钮行。
- 模型对应：投影层显示策略（哪些节点显示操作行）。
- 建议落地：V1 投影层规则。
