## 1. 方案总览

### 1.1 整体修复路径一句话

> **先以「事件流 → 单一投影 store → view model → 原子组件」为前端铁律骨架，把前端 7 层消息类型从根上单源化（T3）、把两个 store 双份消息合并成单一时间线投影 store（T4）、再把投影归一为单一渲染主路径（V1）、最后把原子化基础设施与完整性三件套钉死（F1）——前端收敛先行，再回头托住 Rust 侧，最终以「最小共享面」把移动端与桌面端拉回同一事件流契约。**

### 1.2 核心主张（本方案角度）

1. **前端是本次战役问题密度最高的战场**（analysis/01 7 层消息类型、12 消息双份、storeAccess 三份、04 双投影、11 上帝组件/门禁破功）；前端收敛不是「跟 Rust 侧平行的第四条线」，而是**把「事件流 = 唯一时间线骨架」从前端消费侧真正落地的前置**。前端收敛在先，Rust 侧 `session_messages` 降级、事件类型扩展、撤回等才有可信的展示端承接面。

2. **收敛总顺序 = 「类型单源化 → 投影 store 合并 → 投影归一 → 原子化 S0」**（T3 → T4 → V1 → F1），其成立的关键在于每一步都**先删后建、删除即收敛**，避免在旧 7 层类型 / 双份存储 / 双投影之上叠加新抽象。这条顺序的依赖关系我认可，但**有两点必须前置修正**（见 §3.1）。

3. **「最小共享面」不是「尽量少共享」，而是「只共享该共享的」**：跨端（desktop/mobile）真正该共享的只有三样——事件流 wire 契约（device-protocol/engine 生成面，已达成）、generated 类型作为事件体唯一解析权威（mobile 补 `parseEngineEvent`）、共享投影原语（事件→投影的 transport 无关纯函数）。**共享的边界必须划在「纯逻辑 + 契约」层，绝不划在「组件本体」层**（RN/Web 无法直接复用 DOM 原子组件，19 审计 §5.3）。

4. **完整性三件套（错误边界 / 空态 / 降级态）是前端核心的准入门槛，但它有两个当前被忽视的前置缺口**：P0 引擎崩溃无 UI 感知 + 孤儿 run 收割（18 审计差距 2/3/4）、P1 markdown 渲染失败空白消息体（16 差距 1）。**「完整性单维」应列入 14 维框架，置于 F1 原子化之前或与之并行**——因为「原子组件基座 + 完整性三件套」是草案 §3.1 前端核心的定义之一（草案 :103）。

5. **前端收敛不依赖 Rust 侧的 T2/C1/P1/I1 等维度全部完成**：T3/T4/V1/F1 全部是**前端本地**的形状收敛（类型别名、store 合并、投影归一、门禁清零），其输入就是当前已在用的 generated parser 与已产生的事件流。**它可以与 Rust 侧绝大多数维度并行**（见 §4 批次）；唯一需要 Rust 侧前置的是 **T1 事件模型扩展（context-state / injection / truncate 新类型）**——但那是 T1 提供新能力，不阻塞前端 T3/T4/V1/F1 的收敛。

## 2. 对 14 维框架的验证与调整

### 2.1 前端四维的关系推演（T3/T4/V1/F1 顺序是否成立）

**结论：T3 → T4 → V1 → F1 的顺序整体成立，但不是「严格串行」，而是「T3 = 一切的先决性基座，T4/V1/F1 在 T3 底座之上有独立拆解，F1 可提前并行启动 S0 门禁清零」。**

| 环节                  | 本质                     | 依赖                   | 推演                                                                                                                                                                                                           |
| --------------------- | ------------------------ | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **T3 类型单源化**     | 消息类型的「权威唯一」   | 无（generated 已在用） | 必须最先。7 层类型（01 §②.3）不先收敛，T4 合并 store 用的就是第 8 套 types 定义、V1 归一投影用的还是手写 DTO。T3 定下「store 消息直接是事件投影」后，T4/V1 才站得住。                                          |
| **T4 单一投影 store** | 状态存储的「唯一入口」   | T3                     | 在 T3 的类型底座上，把 streamingStore 消息部分 + layoutStore 消息部分合并为单一时间线投影 store；同时消解三份 storeAccess。它是状态面的收敛。                                                                  |
| **V1 展示投影归一**   | 渲染过程的「主路径唯一」 | T3 + T4                | 在单一投影 store 之上，渲染只吃 timelineNormalizer（轨 A）单一投影；删 UserView 旁路（轨 B）。它是渲染面的收敛，吃 T4 的产物。                                                                                 |
| **F1 原子化 S0**      | 渲染结构的安全上限       | T3（弱相关）           | 拆上帝组件、门禁清零、输入契约化。它主要受组件层线数/原子层规则驱动，与 T4 的 store 合并有部分重叠（MessageContent/ChatAssistantMessageRow 的 store 直连要随 T4 一并上移到壳层），但 S0 门禁清零本身可提前做。 |

**关键点**：我**反对**把 T4 与 V1 在「合并双 store」这一个动作上硬拆成两个批次执行——它们共享同一个「MessageContent 渲染期 view model 合并」载体（MessageContent.tsx:132-166 的 `applyStream*` 投影 + `commitStreamToSession` 时序闭环），T4 把两个 store 合掉、V1 把渲染主路径定成单一投影，**在同一个文件改动里同时完成才是净删除最大、双投影残差最少的方式**。详见 §3.3/§3.4。

### 2.2 是否需要新增维度

**需要。14 维框架在「前端完整性 / 可定制 / 多端共享面」三个面上覆盖明显不足**，建议做三等调整（只增细，不合并变粗）：

1. **新增「完整性与容错」维度（建议命名为 T5，紧跟 T4 之后、F1 并行）**：
   - 内容：18 审计差距 P0（引擎崩溃 UI 感知 + 孤儿 run 收割）+ P1（markdown 渲染失败空白消息体）+ 顶层 boundary 降级（差距 6）+ 全局 uncaught 错误呈现（差距 5）+ `invokeCmd` 迁移（差距 7）。
   - 理由：草案 §3.1 把「完整性三件套」列进前端核心定义（草案 :103）；18 审计确认错误边界覆盖充分但**缺「引擎崩溃感知 / 孤儿 run」两个 P0 兜底面**。这不是「边缘补丁」，而是「核心 UI 在任何情况下完整可用」这一不变量（18 审计基准）的实质落点。当前 14 维里完全无此维度，属结构性缺口。
   - 维度再细拆（禁止弄粗）：
     - T5-a 引擎崩溃感知：新增 engine-crashed / engine-status-changed 事件（真存活心跳）+ 前端 errorStore 呈现「引擎已崩溃」态 + 重连/重启入口（18 差距 2）。
     - T5-b 孤儿 run 收割：Rust 侧 JoinError → 收割标记 run 失败，补终态事件/写 lastError；前端能识别中断 run（18 差距 4 / 11 审计 ref orphan run）。
     - T5-c markdown 空白消息体次优回退：完成态渲染失败给「渲染失败」占位或纯文本次优回退（可作纯前端 fallback，且**不泄漏源码**——16 的约束要产品裁决但可给默认纯文本降级）。
     - T5-d 顶层边界与全局错误：main.tsx 边界失败降级修复、全局 error/rejection → errorStore + 全屏错误面（18 差距 5/6）。
     - T5-e `invokeCmd` 迁移到 `invokeTyped`（18 差距 7，消灭静默 Fail-Open）。

2. **mobile 投影原语共享 / mobile 事件体类型化**（19 审计 §5.1 收敛动作 2/3）放到 **T4 维度内作为一个专属小项**（T4 已有「抽共享投影原语」），但单列一个「mobile 侧未接线处置」子项。理由：这不是一个新的独立维度，它是 T4「单一投影 store」的**多端投影**，且 mobile 侧当前 events 表**未 live 接线**（19 §3.1：事件持久化尚未触发，物理删除反例是「已建契约 + 未接线执行器」），不能把它当成「mobile 要改一堆代码」的独立战役——而是「接入事件持久化时按 core 模型修正」的一次性处置点。

3. **可定制面**：17 审计确认前端核心可定制面仅 4 项（主题二元 / 模型选择 / 基础布局 / 审批交互），且**定制状态不进会话时间线**。这不需要新增维度，但需要在**所有前端相关维度（尤其 E1/V1/F1）里显式施加一条约束**：不得把主题/布局/权限/快捷键状态塞进消息事件流（冒牌污染「唯一时间线」模型）。把它作为「横切纪律」写进 T3/T4 的验收断言即可。

### 2.3 其他调整意见

1. **修正 T3 的「改类型别名或删」走向**：01 审计确认 store 里的 `SessionMessage` 是「投影缓存」，而非纯类型别名。T3 若只做「类型别名（`type SessionMessage = generated.AgentMessage`）」会导致工具字段/投影字段（toolCalls/toolCallResults/timeline）丢失——**SessionMessage 是个超集**（01 §②.3 含 sender + toolCalls + toolCallResults + blocks + timeline），它不等价于 generated `AgentMessage`。因此 T3 的正确语义是：**事件解析（sessionEventHydrate / onMessageEnd）统一走 generated parser，store 里的 `SessionMessage` 保留但**仅从 generated 派生**（字段用 generated 事件投影填充），**删除手写事件解析器**（P6），**类型定义单一权威**在生成的契约层。这比「别名删定义」更诚实。

2. **修正 01 对 T2 的归类**：T2（持久化轨收敛：localStorage 轨 / RustDb 前端轨 / append_session_messages）被我视为**Rust 侧 D1 维度主导**，但其【前端 session-persistence 剥离镜像接入点】子任务强依赖前端类型收敛；我建议把它明确为「Rust 侧主导 + 前端收口执行」，并在本方案的批次里与 T3 绑同批（见 §4）。

3. **T4 与 E1（插件轨收口）有边界**：E1 删 `src/plugins` 死代码。T4 的「单一投影 store」与 E1 的「插件轨收口」不冲突（死插件轨无人消费、不碰投影链），但**E1 必须先处理 settings-extensions 的 useExtensionMarket 消费（主控已亲验存在引用）**，否则删 `src/plugins` 会破坏设置页。我在 §4 批次中把 E1 放在前端收敛之后作为清理轮，避免与 T4 争同批人。

## 3. 维度方案（本角度主控：前端相关维度）

> 覆盖格式：核心问题（证据）→ 做什么 → 删什么 → 依赖 → 验收建议。
> 标注：[形状] = 源码形状推断；[验] = 已被前序审计真跑/锚定；[需真跑] = 需本方案执行期真跑确认。

### T3 · 前端消息类型单源化（打底层 · 先决性）

- **核心问题**：同一条消息在前后端有 7 层类型形态（Rust AgentMessage / Rust SessionMessage / Rust HistoryMessage / TS SessionMessage / TS MessageTimelineBlock / TS HistoryMessage / generated AgentMessage）[01 §②.3 P1]；`sessionEventHydrate.ts:39-60` 事件重放水合**绕过 generated parser 手写解析**，与实时流的 generated 严格解析**两条解析路径同一事件流**[01 P6、:90]；`onMessageEnd` 最终把流式消息转换回手写 `SessionMessage` 落 store [01 P2]，使 generated 类型未成 store 主类型。
- **做什么**：
  1. `sessionEventHydrate.ts` 的 `agentEventFromOrchestrator` / `blockText` 改走 generated `parseEngineEvent` 派生 store 消息；`onMessageEnd`（messageHandlers.ts:88-147）直接由 `EngineEnvelope<'message-end'>` 的 generated `AgentMessage` 派生，删手写转换 [01 §④/§⑤]。
  2. 前端 timeline `MessageTimelineBlock`（store/types.ts:348-377）与 Rust `AgentMessageBlock`（message.rs:100-126）**归一**：以 generated `AgentMessageBlock` 为唯一块权威，前端 image/step_start/step_end 这 3 个**前端扩展块**（01 §②.3）要么并通过 generated（评估），要么**显式收敛为前端投影装饰**（不冒充事件块类型）。
  3. 类型定义单一权威 = `crates/conex-types` → `scripts/generate-engine-bindings.mjs` → `packages/shared-types/src/generated/engine`；前端不再手写第 N 套消息类型。
- **删什么**：手写事件重放解析器（`agentEventFromOrchestrator`/`blockText`）；前端手写消息类型定义（`HistoryMessage`/`MessageTimelineBlock`/`SessionMessage` 中的手写部分降为「从 generated 派生的投影缓存」）；P2 的 onMessageEnd 手写转发。
- **依赖**：无前序（generated 已在 live 流式链路用）。
- **验收建议**：`rg 'interface (HistoryMessage|MessageTimelineBlock)' apps/crish-desktop/src` 输出为空（会话 store 类型保留为派生，不重复定义）；`rg -l 'agentEventFromOrchestrator|blockText' apps/crish-desktop/src` 输出为空；typecheck + vitest 快层绿。

### T4 · 单一投影 store + 投影原语（打底层 · 状态面收敛）

- **核心问题**：同一 assistant 消息正文在 `streamingStore.byKey`（热/中间态）与 `layoutStore.messages`（持久投影）**两个 store 各存一份**，靠 `MessageContent.tsx:138-166` 的 `applyStream*` 投影合并 + `commitStreamToSession`（helpers.ts:197-235）`queueMicrotask clearStream` 时序闭环防撕裂 [12 §④.3]；storeAccess **三份**（store/storeAccess ∥ api/storeAccess ∥ api/store-access/componentAccess）[12 §④.2]；store facade 消费不唯一，组件直连 `useStreamingStore`（MessageContent.tsx:138、ChatAssistantMessageRow.tsx:178）[11 §⑤]。mobile 端事件→投影映射（eventReducers/eventMappers/FeedBridge）与桌面 chat-bridge 是**两套平行实现**[19 §④]。
- **做什么**：
  1. 合并 `streamingStore` 消息部分 + `layoutStore` 消息部分 → 单一时间线投影 store：以事件流为唯一写入源，派生一份「时间线投影」；`streamingStore` 降为「同一投影 store 的中间帧缓存」或被并入 [12 §⑤.1]。**同时**把 `MessageContent`/`ChatAssistantMessageRow` 内嵌的 `useStreamingStore` 读取**上移到页面壳层**，复合层只收「已合并的 view model」（11 §⑥ S5）。
  2. 消解三份 storeAccess → 保留 `store/storeAccess`（读面）+ `api/storeAccess`（编排）**二面**，删 `api/store-access/componentAccess` 过渡门面；待 `store/storeAccess` 补齐 sessions/layout-tree/workspace-shell/streaming/draft 导出后删 [12 §⑤.2、componentAccess.ts:13-14]。
  3. **共享投影原语**（19 §5.1）：把 mobile `eventReducers`/`eventMappers` 的 transport 无关纯函数部分 + 桌面事件消费映射抽入 shared 包（候选 `shared-utils` 或新建 `shared-projection`），两端共用「事件→store 分派」逻辑；**同时** mobile 事件体从「容错 readString」收敛到 `generated/engine/parser` 结构校验（消除类型化过弱，不重建第二套消息类型）[19 §3.2/§5.1]。
  4. **mobile events 表物理删除反例处置**（[形状] 当前未 live 接线）：接入事件持久化时按 core 模型改造成「逻辑截断/墓碑」语义，或**明确「缓存回收不算时间线删除」**并以「经桌面 events.resume 续传补充」为架构级解法 [19 §5.3/§3.1、10 审计]。
- **删什么**：`api/store-access/componentAccess.ts`（过渡读面，≥116 行）[12 §⑤ 删除面]；`streamingStore` 作为独立 store（若并入则删/降为内部缓存，保留 byKey 中间帧可接受）[12 §⑤ 删除面]；双份消息正文/工具的冗余副本（**保留热缓冲语义**——16 审计确认其是设计内必需桥）。
- **依赖**：T3（store 消息已从 generated 派生后，T4 合并的才是同一类型）。
- **验收建议**：`check:store-facade` / `check-store-writes` 绿；`componentAccess` 零引用；消息正文存储副本 = 1（热缓冲除外）；mobile 与桌面共用的投影原语包有可指认的消费方（两端各 ≥1 真实实现，符合抽象纪律「接口两实现法则」）；typecheck + vitest 绿。

### V1 · 展示投影归一（渲染面收敛）

- **核心问题**：展示投影**双轨**——真实渲染走 timelineNormalizer（轨 A，MessageContent:227 → buildAssistantTimelineCached），UserView（messageUserProjection.ts ~809 行，轨 B）仅 `silentComplete`/调试面板/测试消费，两套投影对同一消息各算一遍 [04 §①/§② P1]；timelineNormalizer（timelineNormalizer.ts:33 normalizeAssistantTimeline）与 streamMessageViewModel（streamMessageViewModel.ts:138-151 applyStreamToolsToMessage 的 block 补齐）**重复同一「tool_call 块对齐」规则**，流式路径叠套两次 Aligned [04 P2]；折叠有双源——投影层 `buildToolRenderItems` 生成 `{kind:'group'}`，渲染端 `flattenRenderTools`（ChatToolCallBlock.tsx:58-65）又展平重分组（parallelGroup）[04 P5/Q2]；「官方命令类型图标」整体缺失（ToolCallHeader 只有状态图标）[04 P3]。
- **做什么**：

## 5. 风险与需真跑验证点

1. **T4 合并双 store 的时序闭环风险（queueMicrotask clearStream）**：`commitStreamToSession`（helpers.ts:197-235）靠 `queueMicrotask clearStream` 防白屏时序闭环。合并双 store 时，必须**保留这个「热缓冲即时态 + 终态投影」的桥语义**（13 审计确认这是设计内必需桥），不能简单删 clearStream。**[需真跑]**：合并后高频流式 + run 收口时 UI 不出现 text 空窗/跳变（13 G3 丢帧窗口）。建议用 CDP 9222 真跑一个长对话 + 多工具交错的流式，观察流式合并与收口瞬态。

2. **V1 删 UserView 的 silentComplete 行为**：UserView 唯一剩下的生产价值是 `silentComplete`（04 Q1）。删旁路前必须先迁 silentComplete 为「单消息可见性直接判定」，**[需真跑]** 验证 silent-complete metric 仍被记录、行为测试（silentComplete.test.ts）绿。删错 silent 判定是静默回归，属高风险。

3. **F1 输入契约化对子 agent 与主对话的影响**：`ComposerField`（textarea）已用于子 agent（InlineAgentPanel），主对话的 Tiptap 契约化后必须保证**两套实现行为一致**（L2/L3 停止、onSend、draft 水合、onPaste/files）。**[需真跑]**：Tiptap 禁用后主对话发送/停止完整可用；子 agent 输入不受影响。

4. **CDP 9222 真跑验收项**（遵循 AGENTS.md §15：只针对 Tauri WebView2 9222）：
   - T3 后水合重放改走 generated parser → 历史长会话 reload 后消息完整、块类型正确；
   - T4 后单投影 store → 长会话流式 + 工具批 + 收口无跳变；
   - V1 后折叠行真折叠（不再展平重分组）、原因描述正确；
   - T5 后人为触发 run panic → 孤儿 run 被收割、引擎崩溃态呈现；
   - F1 后 Tiptap 禁用的主输入兜底可用。

5. **mobile events 表物理删除反例**：当前 [形状] 未 live 接线（19 §3.1），**接入事件持久化时必须**先按 core 模型改逻辑截断或明示「缓存回收不算时间线删除」，否则反例实跑。这是「未接线 → 将来接入即踩坑」的时序风险，需在批次 E 一次性处置，不拖到 mobile 独立战役。

6. **«engineReady 假就绪»修法**：T5 的引擎崩溃感知需 Rust 侧 `core_get_status` 补真探活心跳（18 差距 2）；但在同一进程架构下「引擎崩溃 = 整个 Tauri 进程死亡」不适用，需澄清产品预期（18 差距 3：重启 = 整个 Tauri 重启）。**[需真跑]**：界定「run 崩溃（进程活）」与「进程整体挂」两条路径各自的 UI 感知面，避免过度设计。
