## 1. 方案总览

**整体修复路径一句话**：以「能力层四维 = 权限归一的引擎权威 + 单一注入/提交队列 + 单一展示投影链 + 原子化门禁落地」为主线，先让能力层四个概念各自收敛到单一路径（P1 审查权威归引擎、I1 队列/注入单源、V1 投影单链、F1 组件原子化门禁清零），再回灌到 T 层（时间线/投影 store）与 C 层（核心循环瘦身）的既有依赖面。

**本方案核心主张（≤5 条）**：

1. **权限的「单一权威」在引擎、不在注册表**（修正 00-总方案 §3 的「工具类别→策略注册表」表述）：03 审计证明代码中**不存在按 `ToolCategory` 做安全判定**——生产路径 `ToolCategory` 恒 `Internal`（`executing_tools.rs:71`），引擎只用 `dangerous` 标记 + `PermissionMode` 三态 + `decide_with_redline`。能力层收敛目标是**消除前端二次决策**（`shouldAutoApproveCommand` 自动放行），而非新建按类别判定的注册表。即「P1 的删除面主要是前端自动放行与死类型」，对 `ToolCategory` 只做「接线真类别或明确降级为展示投影标签」二选一（防过度设计）。

2. **「下一轮会话注入」是 orchestrator `PendingMessageQueue`，不是 steering nudge**（修正 02 §⑤ 问题⑤、00 §3 传播误差）：`PendingMessageQueue` 已接线到 run_idle 续 run 边界（`drain_pending_to_inject_messages`），是 context-state 节点的现成载体；`PendingNudgeChannel`/`drain_nudges` 生产零接线，属「接线或删」的半成品。I1 的队列归一 = 以 `PendingMessageQueue` 为唯一「下一条用户消息」语义，收敛 session-loop 侧 `AgentInputQueue.followUp`。

3. **V1 的 canonical 是 `timelineNormalizer`（轨 A），UserView 是旁路删除对象**（修正 00 §3 把 messageUserProjection 当 canonical 的虚假对位）：渲染主路径是 `buildAssistantTimelineCached`；`messageUserProjection`/`UserViewDebugPanel` 仅 silentComplete + 调试 + 测试消费。V1 的核心动作是**先迁 silentComplete 改单消息可见性判定、再删旁路**，并把折叠裁决点从渲染端 `flattenRenderTools` 上移回投影层。

4. **F1 必须再拆为三个子段**（门禁修复 → 上帝组件拆分 → 输入契约化），不能作为单一「原子化 S0」批次：「门禁修复」是纯机械（修 Dialog/Menu + 测试面扫描缺口）可作零风险打底；「上帝组件拆分」（InlineAgentPanel 621 / TiptapEditorField 477）涉及渲染与状态迁移，须放在 V1 投影单链（去 store 直连）之后做才不冲突；「输入契约化」（ChatComposer.tsx:194 Tiptap 硬编码 → 契约 + textarea 兜底）是 16 审计的可选增强，依赖「核心输入契约」先定义，建议作为 F1 收尾或单独轮次。

5. **能力层与 T/C 层的依赖方向明确**：P1 与 I1 **依赖 T1 的事件类型扩展**（`ToolCategory` 真类别、context-state 节点、reasoning_effort 下发都需要新/真实类型）、但不依赖 T4 投影 store 完成；V1 **依赖 T4**（单一投影 store 合并后投影链才有统一数据源）；F1 的原子化渲染依赖 T3（消息类型单源化）与 V1（投影单链）。故能力层应拆在 T1/T2/T3 打底之后、T4 可并行，而非全部垫后。

## 2. 对 14 维框架的验证与调整

依据任务书：我有权验证与调整，可**再拆细**，禁止弄粗。以下按我的能力层视角逐条给结论。

### 2.1 P1 拆分合理性：合理，但需缩小「判定权威」口径

- **认可 P1 整体**：权限审查是能力层概念最集中的一处，前端/引擎两套发散 + 3 处死/重复类型（`PermissionBehavior`/`permissions.ts`/`evaluate_command`）是收敛高价值点。
- **细化调整（拆细）**：P1 建议拆为两子段，因为「引擎侧」与「前端侧」改动互不依赖、可并行：
  - **P1-α 引擎审定权归一**：`exec_verdict.rs` 命令判定收敛为单一链（消 `PermissionDecisionEngine::evaluate_command` 双路径）；`ToolCategory` 接线真类别（或显式降级为投影标签）；`PermissionBehavior/PermissionDecision` 死类型删除；决策类型统一 `ApprovalDecision`。
  - **P1-β 前端自动放行下线**：`shouldAutoApproveCommand` 自动 approve 分支删除 → 默认展示审批卡片；白名单仅作「批准记忆（remember）」不做放行判定。
- **依赖核实**：P1 依赖 **T1**（`ToolCategory` 真类别需要 message/event 类型真实落地）与 **C 层**的 `exec_verdict`/`hooks`（call_verdict 与 tool.pre 双通道合一，是 C 层 hooks 面的事）。P1 **不阻塞**也不依赖 T4 投影 store。

### 2.2 I1 拆分合理性：合理，但「双队列」的收敛目标要写准

- **认可 I1 整体**：动态状态注入无通道 + reasoning_effort 半连通 + 双队列并存，是能力层注入侧核心问题。
- **细化调整（拆细）**：I1 拆为两子段：
  - **I1-α 队列归一 + context-state 通道**：以 `PendingMessageQueue` 为唯一「下一条用户消息」语义，删/冻结未接线的 `PendingNudgeChannel` 直通 + `drain_nudges` 汇入主队列；新增 context-state 节点（T1 定义类型 → 复用 PendingMessageQueue 作为注入载体）。
  - **I1-β reasoning_effort 真下发**：`ConnectionLifecycle` 透传 thinking level → `ProviderRequest.reasoning_effort`；同时生成 context-state 文本节点挂提交。
- **依赖核实**：I1 依赖 **T1**（context-state 节点类型、metadata.kind 枚举化）与 **T2**（队列是时间线输入侧，依赖 D1 统一时间线把队列的注入文本事件化）。I1 **不依赖** V1/T4。

### 2.3 V1 拆分合理性：合理，依赖 T4 成立

- **认可 V1 整体**：双投影 + 折叠半实现 + 图标缺失 + 组件去 store 直连，是展示投影收敛目标。
- **细化调整（拆细）**：V1 依赖清单里包含了「删 UserView 旁路」，而删 UserView 又依赖「先迁 silentComplete」。建议 V1 拆为：
  - **V1-α silentComplete 单消息化**（前置，独立小段）：silentComplete 从整套 `projectSessionMessageToUserView` 改为只算单消息 `visibleText/tools/thinkingPreview`，不再依赖 UserViewDto + hiddenBuckets。
  - **V1-β 删 UserView 旁路 + 调试面板**（在 V1-α 后）：`messageUserProjection`（~809 行）收敛/删除 + UserViewDebugPanel 随删。
  - **V1-γ 折叠裁决点单源化**：`flattenRenderTools` 不再展平投影 group；`buildToolRenderItems` 的折叠成为唯一裁决点。
  - **V1-δ 组件去 store 直连**：`MessageContent.tsx:138`/`ChatAssistantMessageRow.tsx:178` 的 `useStreamingStore` 读取上移页面壳层或改由投影 store 派生选择器供数。
- **依赖核实**：V1 **依赖 T4**（单一投影 store 合并后，投影链才有统一数据源与派生选择器）；V1-δ 的「去 store 直连」直接依赖 T4 提供派生选择器。**一致性确认**：14 维框架已把 V1 排在 T1–T4 打底之后，与我的依赖判断一致。唯一补充：V1-α 可在 T4 完成前独立做（silentComplete 是旁路，不受主链合并影响）。

### 2.4 F1 拆分合理性：**不合理——建议按「门禁修复 → 上帝组件拆分 → 输入契约化」再拆**（任务书允许我调整）

- 14 维框架把 F1 作为单一「原子化 S0」，但 11/16 审计证明其内部至少三段工作性质完全不同、依赖关系各异的子域：
  - **F1-α 门禁修复**（零风险打底）：修 `ui/Dialog/Dialog.tsx`、`ui/Menu/Menu.tsx` 原子层违规（`useLayerRegistration` 下沉 ui/ 内部私有）+ `check-ui-layer.mjs` 测试面扫描缺口。纯机械、无行为变化，可独立首选执行。
  - **F1-β 上帝组件拆分**：拆 `InlineAgentPanel`（621 有效行）+ `TiptapEditorField`（477 有效行）两当前 VIOLATION。**涉及渲染与状态迁移，须在 V1-δ（去 store 直连）之后做**，否则拆出的子组件仍是 store 直读、拆分无意义甚至更散。
  - **F1-γ 输入契约化**：`ChatComposer.tsx:194` 硬编码 `<TiptapComposerField>` → 定义「核心输入契约」（`value/onChange/onSend/onStop(L2)/onForceStop(L3)/onPaste/onFiles/draft/aria`）+ textarea `ComposerField` 兜底变体。属 16 审计判定的**可选增强**，富文本是扩展、纯文本是核心。依赖「核心输入契约」先定义，建议放 F1 收尾或独立轮次。
- **依赖核实**：F1-α 无前置依赖；F1-β 依赖 T3/V1；F1-γ 依赖 F1-α（门禁先绿）+「Tiptap 解耦判定」（需主控确认 Tiptap 是否作可替换增强 vs 直接降级 textarea）。

## 3. 维度方案（P1 / I1 / V1 / F1）

### 3.1 P1 权限审查归一

#### 核心问题（证据 → 触发项）

1. **前端二次决策（关键）**：`commandPermissions.ts:357-479` 自建 `HARDLINE/DESTRUCTIVE/EXTERNAL/NETWORK/WRITE/SAFE_READ` 正则表 + `classifyShellRisk`（:607-636）+ `shouldAutoApproveCommand`（:657-661）；`approvalHandlers.ts:66-96` 命中即 fire-and-forget 直发 `core_approve_tool`（:77-79）。用户永不见审批卡片，且是「算法替用户决定」。03 §③ P1/P2。
2. **引擎命令判定双路径（P5）**：`exec_verdict.rs:104-113`（`revert_policy.gate_verdict_command`）∥ `permission.rs:196-287`（`PermissionDecisionEngine::evaluate_command`/`tools/shell.rs:228-241`）重复判定命令文本，无单一事实源。
3. **ToolCategory 恒 Internal（P3）**：`executing_tools.rs:71` 硬编码 `category: ToolCategory::Internal`，工具定义无 category 字段，裁决不读类别。
4. **死类型/坏缩写（P4）**：`PermissionBehavior/PermissionDecision`（`events.rs:38-59`）仅定义/roundtrip 使用；`permissions.ts`（`RuntimePermissionPolicy`/`ApprovalHandler`/`PermissionRule`）接口族零消费；实活权威是 `ApprovalDecision`（`events.rs:289`）。
5. **安全底线好**：引擎 `run_approval.rs:135-145` resolve 的 pending 校验防伪造是**反向证词**——本方案删前端自动放行不破坏审计不可伪造（引擎 Deny 不出 approval-requested，前端无从放行）。

#### 做什么

- **P1-α（引擎审定权归一）**：
  - 消 `PermissionDecisionEngine::evaluate_command`（`permission.rs:196-287`）或并入 `decide_command_with_revert`（`permission.rs:135-151`）单一命令判定链；`command_allowed_for_task_type`（`readonly.rs:159-182`）明确为「spawn 时工具裁剪」独立层，不参与每命令判定。

  - 删 `PermissionBehavior/PermissionDecision`（`events.rs:38-59`）；决策类型统一 `ApprovalDecision`。
- **P1-β（前端放行下线）**：
  - 删 `approvalHandlers.ts` 的自动 approve 分支（`shouldAutoApproveCommand` 命中也走审批卡片展示）；`onToolStart` 文案「白名单自动允许」改掉。
  - 白名单降级为「批准记忆（remember）」；`classifyShellRisk` 若仍用于展示分级可保留，但**不做 allow 判定**。

#### 删什么（★ 能力层删除面，详见 §6）

### 3.2 I1 注入与队列（动态状态注入 + 队列归一）

#### 核心问题（证据 → 触发项）

1. **动态状态注入零通道（问题①，最高优先级）**：前端模型/权限/思考切换只写 localStorage + `emitUiEvent('profiles-changed')`（`profileStore.ts:94-108,129-139`），不产生 AgentEvent、不写时间线节点；`ConnectionLifecycle.ts:340-443` 把 permissionMode/budgetDifficulty/systemPrompt 当 IPC 参数下发，无文本化认知。
2. **reasoning_effort 有字段无来源（问题⑦）**：`ProviderRequest.reasoning_effort`（`provider.rs:155`）唯一赋值点在 `streaming.rs:347-351`（tool-promise 自愈 / thinking_budget=0 → Off），用户思考档位永不到达；`directFetchBridge.ts:73-107` 是降级轨非产品主轨。
3. **双「下一条用户消息」队列（问题②/⑤ + 08 §④-2）**：session-loop `AgentInputQueue.followUp`（turn_complete.rs:192 消费）∥ orchestrator `PendingMessageQueue`（run_idle.rs 消费）。
4. **nudge 通道半成品未接线（问题②）**：`PendingNudgeChannel.enqueue/enqueue_reason` 生产零调用；`drain_nudges` 壳层零命中；`resource.rs:636` 自述「T-AB-18 接线」。
5. **注入类型标记缺失（问题⑥）**：`metadata.kind`（`runtime-steering`/`nudge`/`diagnostic`/`steering`）散落字符串魔法值，无枚举常量；`message.rs` 缺 context-state/injection 角色。

## 5. 风险与需真跑验证点

> 全部为源码形状下的推断，真跑验证项显式标注。

### 5.1 权限归一的前端自动放行行为变化（高风险，须真跑）

- **风险**：删 `shouldAutoApproveCommand` 自动放行后，原本被白名单静默放行的命令会弹审批卡片，**用户体验变化**（高频安全命令每轮问询）。
- **需真跑**：
  1. ⚠ 确认引擎对「白名单安全命令」的 `call_verdict` 是否本就判 Allow（若引擎已 Allow，前端自动放行只是白做功，删除无感）；若引擎判 NeedsApproval，删除后才暴露问询 → 需补「批准记忆 remember」让用户首次批准后记住。

### 5.2 注入节点对 provider 请求的影响（中风险，须真跑）

- **风险**：context-state 节点注入 ProviderRequest.messages，可能改变模型对上下文的消费（多一段状态文本），或与现有 `reasoning_effort Off` 自愈路径冲突。

  2. ⚠ context-state 注入后，下一轮模型输出不受异常扰动（跑一个切换模型→续聊的回归，断言输出正常）。
  3. ⚠ `PendingMessageQueue.replace_or_enqueue` 的 group_id 去重防重复注入（并发切两次状态只注入一次）。
