## 1. 方案总览

### 1.1 核心矛盾与平衡主张

**矛盾**：战役要「让核心简洁」，但 core 已经由 8 个 handler + 三横切（error/steering/abort）构成精简骨架（07 审计：`dispatch_once` 仅 ~33 行）。真正复杂度在 handlers/mod.rs（2,364 行 / 按 07 口径 1,740 code）里被揉在一起的**横切子系统编排面**，以及 LoopState 上的 ~14 个外围字段（07/00-核心逻辑模型草案 §2）。若把每个子系统都抽象成新 trait/新 mod，会落入「为对齐而加中间层」的反过度设计红线。

**平衡**：核心简洁与扩展承载不是「零和」。二者通过**一条纪律**统一：

1. **分层上限 = 三层，且核心只认知「接口」不认知「实例」**（对齐 00-核心逻辑模型草案 §7 抽象纪律）：核心 `AgentSessionLoop` 经 `SessionLoopOptions`/`with_*` 认知的只有 `dyn` trait / 注册表接口；一切**具体策略实例**（BackupMiddleware、RecoverySteeringStrategy）都归壳层注入。这不新增层，只是把「已经存在但放错位置的装配」搬回正确侧。
2. **外置 = 纯结构搬移，保留语义**（07 §6.3 建议 4）：把 handlers/mod.rs 的压缩/预算/摘要/cache 编排面拆出去，是**平移代码**，不是新写一套。用现有 handler 测试海做回归锚点，`cargo test -p session-loop` 保持绿即为搬移正确。
3. **补缝只补「缺缝面」，不造新抽象**：只有三个真缺缝（compaction 编排 / cache_tracker / summary 触发面），且都已有算法面 trait（`CompactionEngine`/`Summarizer`/`CompactionPolicy`）——补的是「触发编排面」这一层 trait，不是再造一套压缩模型。
4. **统一门面是为了灭掉「多套互不接线的扩展轨」，不是为了加强制运行时**：ToolRegistry+register_runtime+MCP 已经是 Rust 工具接入的现成等价物（05/08/09 审计）；E2 要做的只是把「engine 侧插件运行时」这三块聚合为一个**门面 + 文档登记**，把已经天然可插拔的域显式登记为扩展点，同时删掉死轨（contribute B 轨、note_w4c_contribute、plugin-sdk `Plugin` 接口、permissions.ts 死类型）。
5. _*before_* 覆盖式扩展是借鉴而非照抄_*：Pi 的 `before_*` 事件可返回 Result 覆盖是「事件反射式扩展」；但 Conex 的生产路径是 **Rust trait + 注册表**（ToolMiddleware before/on_definition 已具备拦截+改写的形状，ApprovalGate 已具备决策形状），不需要为 A/B/C/D 新造一套 before_* 事件总线。before_* 的语义（可拦截、可改写、可返回结构化结果）**已经内建在现有缝里**，E2 只需把这些缝**登记为统一门面的能力**，而非新增扩展管道。

### 1.2 对战役全局的推断（本 Agent 视角）

以核心循环为主线推演全局，各层的逻辑关系：

```
T 层（打底：事件模型 + 持久化 + 类型单源 + 投影 store）
   ↓ 事件流是核心循环的唯一真实出站（message-start/delta/end、tool-*），
   │  C1 外置压缩编排依赖 T1 事件模型扩展(TimelineTruncate/context-state)吗？
   │  → 部分依赖：压缩编排外置本身不新增事件类型（ContextCompressionStart/End 已存在），
   │    但压缩回调/后台登记的 Load 端若要把压缩记录落库重放，依赖 T1 的 registry_drift 与
   │    T2 的持久化轨收敛（事件模型 + conex-db 是唯一落点）。
   ↓
   ● C1 核心循环瘦身（本方案主战场）
   │   压缩编排面外置 + 两条反向依赖移出 + 三缺缝补 + streaming/exec_batch 弱缝拆段
   │   └ 为 P1(权限)/I1(注入队列)/V1(展示)/E2(扩展门面) 提供「干净进核心的入口」
   ↓
   ┌──────── P 层（能力：P1 权限 / I1 注入队列）────────────┐
   │  P1 归一审判决：依赖 C1 完成「exec_verdict 判点与策略表外置」后才能真正按类分派        │
   │  I1 队列归一：依赖 C1 不改变 AgentInputQueue 三环；context-state 进 A 扩展点             │
   └─────────────────────────────────────────────────────────┘
   ↓
   V1 展示投影 + F1 原子化（前端）   ← 前端投影从统一时间线派生，不强依赖 C1（可并行）
   ↓
   E1 插件轨收口 + E2 Rust 扩展门面（前端死轨删除 + Rust 统一门面登记）
   ↓
   R1 撤回 + R2 编辑保护（横跨 D1/D3/D4/D5；依赖 T1 事件类型 + C 审查策略表 + 投影层）
```

**结论**：C1 是「核心层给其余维度让路」的**前置净化**，应在 T 层打底后、P1/I1 之前执行。C1 内部再细化顺序（见 §4）。

## 2. 对 14 维框架的验证与调整

> 14 维框架：T1/T2/T3/T4 + C1 + P1/I1/V1/F1 + E1/E2 + R1/R2 + X1。以下逐维给出「本 Agent 视角的验证/调整」，重点处理 C1/E2，其它维度只给意见（不越权改详案）。

### 2.1 C1 是否再拆成 C1a/C1b/C1c？——**建议拆，且应再拆一个 C1d**

原框架把 C1 压成「压缩编排外置 + 两条反向依赖移出 + streaming 拆段」三项。**建议按迁移批次拆成子项**，因为每项的「真跑验证面」与「批内依赖」不同：

| 子项                                  | 内容                                                                                                           | 理由（真跑验证面不同）                                                                                                               |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **C1a 压缩编排面外置**                | handlers/mod.rs 压缩/预算/摘要/cache 编排面 + LoopState 对应字段收进独立 mod                                   | 回归锚点 = 现有压缩 handler 测试海（T-32/T-33/T-36/E2）；搬移后 `cargo test -p session-loop` 必须绿；`handlers/mod.rs` 行数下降 ≥300 |
| **C1b 反向依赖移出**                  | `BackupMiddleware` 出 `SessionLoopOptions::default()`；`RecoverySteeringStrategy` 出 `AgentSessionLoop::new()` | 回归锚点 = 壳层（engine/agent-workbench）装配真跑 + `cargo test -p session-loop`（默认装配空链/空策略 Vec）；涉及壳层注入点，见 §5.2 |
| **C1c 缺缝面补**                      | compaction 编排 trait / cache_tracker trait / summary 触发面收口                                               | 依赖 C1a 先把编排面搬出，才谈「缝的形状」；否则是先定义缝再搬移，顺序反了                                                            |
| **C1d streaming/exec_batch 弱缝拆段** | `streaming.rs::handle` 消费后分类段抽 `consume_classify`；`exec_batch` 并发编排抽 BatchPlanner/Runner          | 07 §6.2 标注为「弱缝、低风险、先做」与「中缝、secondary」——既是拆段，也是**最小真跑**回归（审批/并发/取消语义）                      |

> **是否再拆更细？** 不建议把 C1a 再拆（压缩编排面里 6 件事——估算/clamp/预检/apply/事件/后台登记——是「同一个子系统」，拆得过碎会制造新的职责缠结）。C1a 内部按 6 件事的**逻辑顺序**平移即可，但作为一个**原子搬移批次**（保证一次搬完、一次跑绿）。

### 2.2 E2 门面形态：ToolRegistry+register_runtime+MCP 统一门面 vs before_* 覆盖式

_*我的选择：ToolRegistry + register_runtime + MCP 统一门面（作为 canonical），before_* 覆盖式只作「语义借鉴」不新增扩展管道。_*

理由（证据）：

1. **Rust 侧现成等价物已存在且部分接线**（05 §⑤ / 08 §② 16/27 / 09 §② 2.1）：`ToolRegistry`（registry.rs:23，register_runtime:49，list_definitions 定义改写链:162）、`McpToolAdapter→Tool`（mcp/）、`register_plugin_server`（mcp/mod.rs:60，并入 unified registry）+ conex-browser-tools / conex-computer-tools 真实消费 `register_runtime`。这是**已具备扩展点形状**的缝（09 §⑤「优」级），只缺「统一门面 + 显式登记」。
2. _*before_* 覆盖式扩展（Pi 借鉴）在 Conex 已内建_*：`ToolMiddleware` 有 `before_execute/on_definition/on_result/on_error`，`ApprovalGate` 出 Approved/Denied/Expired，`SteeringStrategy` 产出 InjectMessage/InterventionRequired——这正是 Pi before__「可拦截、可返回结构化结果」的 Rust 等价值，且形状已被生产消费。**再建一套 before_* 事件总线 = 第五条互不接线的扩展轨，直接违反抽象纪律与反过度设计红线。*_
3. _*但 before_* 给我们一条重要语义启示_*：我们缺的不是「before_* 管道」，而是「扩展点**可注册贡献面**」（09 §④ 4.3：A 缺内容产生器注册表、B 缺提交时机 kind 贡献、C 缺类别→策略注册表、D 全新缝）。这四个「贡献面」不是新事件总线，而是**注册表 + 现成缝的显式登记**。

> ⚠️ **一个诚实的不确定点**：`HookRegistry`（14 事件，hooks.rs）目前产品装配面 `SessionLoopProducer` 是否真实注入 hooks `[待真跑]`。09 审计用「grep 仅 loop_runner 注释」判定「产品装配不实装配 hooks」，但若壳层经动态装配接入 hooks，则 E2 的「HookRegistry 作生命周期事件广播 canonical」需要补一次真跑（DevTools 或断点 inspect `SessionLoopOptions.hooks`）。这不影响「选 ToolRegistry+register_runtime 统一门面作工具接入 canonical」这一结论——因为工具接入不依赖 hooks。

## 3. 维度方案

> 本节至少覆盖 14 维框架的 **C1 四个子项 + E2** 每个子项（原框架要求至少 C1/E2 每子项）。每子项给：核心问题（带证据）→ 做什么 → 删什么 → 依赖 → 验收建议（可执行断言，含 cargo test 名）。

### 3.1 C1a 压缩编排面外置

- **核心问题（证据）**：handlers/mod.rs 把状态机公共态（LoopState）+ 预算钳制/估算 + 压缩全套 + dispatch/check_control + 事件辅助全揉在同一文件（07 §4.1：2,364 行 / 1,740 code；07 §4.2 清单 1：压缩触发编排面 ~590 行内嵌：估算 `estimate_context`:313 / clamp `clamp_max_tokens`:284 / 强制 `compact_with_llm_guard`:487 / 摘要重试 `maybe_retry_pending_summary`:557 / apply `apply_compaction`:602）。LoopState 上 ~14 个外围字段（budget/compaction_policy/summarizer/last_compaction_at/compactions_this_run/compression_retries/cache_tracker/summary_dispatch/summary_coordinator/pending_summary_retry/turn_usage…）把核心可变状态撑大。算法面已在 `conex-compaction` crate，但**编排面没拆出**——最典型结构债。
- **做什么**：
  1. 新开 `crates/session-loop/src/loop/compaction_dispatch.rs`（仿 `summary_dispatch.rs` 成功先例），把估算/预算/clamp/预检/强制压缩/stub/事件广播/后台登记/待重试快照整体平移过去。
  2. 定义统一 `CompactionTrigger` 入口（Preflight/UserBoundary/Overflow），装载 `estimate_context`+`clamp_max_tokens`+`compact_with_llm_guard`+`maybe_retry_pending_summary`+`apply_compaction`，保持既有语义**纯结构搬移**（07 §6.3 建议 4）。
  3. LoopState 的压缩/预算/摘要/cache 字段收进**子结构**（如 `CompactionRuntime`），LoopState 只留一个 `compaction: CompactionRuntime` 组合引用，或经 `Option` 挂载（对齐 07 §6.2 建议「状态字段收进 BudgetState 子结构」）。
- **删什么**：handlers/mod.rs 内 ~590 行压缩编排代码（搬到 compaction_dispatch.rs 后原位置删除）；LoopState 上分散的 ~14 个外围字段收敛为 1–2 个子结构字段。
- **依赖**：**C1a 排 T2 之后**（压缩记录落库/重放依赖 conex-db 唯一落点确立）；T1 不阻塞（压缩事件类型已存在）。
- **验收建议（可执行断言）**：
  - `cargo test -p session-loop` 全绿（压缩编排搬移后不破坏既有 handler 测试海——这是搬移正确性的硬锚点）。

## 5. 风险与需真跑验证点

### 5.1 压缩外置的回归面（handlers/mod.rs 590 行牵动的测试）

- **风险**：handlers/mod.rs 压缩编排只搬移会牵动**大量压缩/预算/摘要测试**（T-32/T-33/T-36/E2 系列，mod.rs 自带 tests mod 1,098+ 行）。若搬移不彻底、字段引用断链，`cargo test -p session-loop` 大面积红。
- **缓解**：
  1. **纯结构搬移纪律**：搬移 = 平移代码，**不改语义、不改字段名**（除非一并收敛子结构），用现有测试海做回归锚点。搬移前记录测试基线，搬移后必须全绿才宣称完成。
  2. 先抽 `consume_classify` 等弱缝（C1d）验证「拆段 → 测试绿」流程可信，再动压缩编排（高风险的搬）。
- **真跑验证点**：
  - `cargo test -p session-loop`（压缩/预算/摘要全测试）。
  - 若涉及压缩阈值/触发顺序运行时行为（07 声明部分 `[待验证]`：重试时序、压缩触发阈值、delta 顺序），需补一次真跑冒烟：`cargo test -p session-loop` 里已含阈值类测试；若仍缺运行态冒烟，主控用 DevTools/断点 inspect 一次真实 run 触发压缩。

- **风险**：`BackupMiddleware` 移出 `SessionLoopOptions::default()` 后，若壳层（engine/agent-workbench 的 `SessionLoopProducer` / `core_run_commands.rs`）没补 `with_middleware(BackupMiddleware)`，会导致**生产缺失写前自动备份**，且 cargo test 可能不暴露（测试可能自建 middleware）。这是**安全相关**（写文件备份），不能静默丢。

  3. 关键：**C1b 验收断言必须有壳层装配面的真跑**，不能只依赖 `cargo test -p session-loop`。
- **真跑验证点**：

  - `cargo test -p session-loop` 中若存在直接依赖默认 BackupMiddleware 的测试，改为显式注入后重跑。
