## 0. 一句话方案总览

**整体修复路径**：以「可测量、可拒绝、每轮必删」三条横切红线为骨架，把 X1 命名卫生做成**穿插于 T1–R2 各功能轮之间的独立「卫生冲刺」轮次**（而不是单轮一次性大改），并用一台修订过的收敛度量脚本（修误报/漏报口径）+ 每轮固定审计勾稽 + 删除门作为「别让执行轮跑偏、度量不虚报」的机器护栏。

## 1. 核心主张

> 不从「哪个维度重要」出发，而从「怎么保证执行轮偏不跑、度量报不虚」出发，反推治理机制。

### 主张 1 · X1 以「卫生冲刺轮」穿插，不并入、不孤立、不最后才做

波次命名清理不是 V1/F1 的附属动作，也不是收尾轮最后的大清洗。它应做成 **2–3 轮独立的「X1 卫生冲刺」**，穿插在 T1–T4 打底层与 C1 核心层之后、P1/I1/V1/E1 能力轮之间、以及 R1/R2 收口前。理由见 §3.1（重命名必须贴着目标模块「该轮已真跑绿」的节点做，避免在模块尚未稳定时反复改 import 链）。

### 主张 2 · 度量是「同口径重复测量」，先给脚本做一次校准，再谈 Δ

当前 `check-convergence-metrics.mjs` 存在**两处口径 bug（一漏一报）**：漏 `w5bSkeleton.ts`/`w5bStrict.ts`（camelCase 尾缀不匹配 `[._-]`，12+ 生产引用却没入波次计数）、误报 `note_w4c_contribute/*`（路径内 `_w4c_` 子串命中 `([._-])w\d+` —— 令同目录 5 个文件被算成 5 个波次文件，analysis/06 §⑤ 又错误断言此目录「不存在」，审计依据与脚本口径互相矛盾）。**任何 Δ 汇报都不可信，直到先用修订版脚本锁死「每轮该报哪些数字」的同一口径**。详见 §3.2。

### 主张 3 · 每轮「无删除不算完成」落到一个可执行的原子判定公式，而非口号

删除不交给整轮末尾的叙事汇报，而是**内嵌为每轮审计位（①a）的固定检查项**：1 个「硬删除」指标（波次命名文件数 / 概念路径数 / 未接线标记 Δ，明确指标为该轮目标）+ 1 个「grep 零命中」机器断言 + 1 个「净删除行数 > 0」。三个都必须真跑、附命令输出，才有资格宣称该轮完成。具体公式见 §3.4。

### 主张 4 · 删除裁决权永远在主控，但「删除候选证据库」由每轮审计位增量补、由度量脚本去重

review.md §23「删除裁决权在主控 + 亲自验证」不可动摇。方案新增的是：把 08 删除清单从「一次性产出一张表」改成「**每轮审计位增量 append + 主控裁决后从度量脚本排除**」的活清单，防止 X1 之外的维度（T2/T4/P1/V1）在删除时重复人工数数、也防止删除后旧路径借尸还魂无人追踪。

### 主张 5 · 用 Pi 的「先验证再派生」与 DSH 的「模型可见 ⟺ 已落日志」对冲「度量虚报」

度量脚本是静态 grep，无法证明功能活着。因此横切治理引入**第二道动态防虚报闸**：每轮涉及删除的路径，在删除前由审计位复跑一次「源码形状 grep 零命中」**并**跑一个最小可运行断言（该模块真跑绿/该 import 链真编过）。Pi 的 `validateRecordLog` 拒腐门禁（20 审计§9.1）与 DSH 的「已落日志才能可见」硬不变量（21 审计§3）正是这种「不静默吞、宁可过拒」思路——我们把它迁移到删除纪律上：**grep 有命中就不许宣称删除完成**。

### 3.2 收敛度量脚本修订（防「度量不虚报」的第一闸）

**核心问题**：脚本两处口径 bug 导致 Δ 不可信。

**（一）波次正则误报（false positive）**：

- 脚本 `waveRe = /(^|[\\/._-])(w\d+[a-z]?[._-]|...)/` 用 `full path OR basename` 匹配，导致路径子串 `note_w4c_contribute/` 里的 `_w4c_` 命中 `([._-])w\d+[._-]`，把同目录 5 个文件全部误计为波次命名。**修法**：只匹配 `basename`（`f.split('/').pop()`），不用 full path；或显式对目录名单独判定（目录 `note_w4c_contribute` 本身是波次命名残留可另计，但文件不逐个计入）。

**（二）波次正则漏报（false negative）**：

- `w5bSkeleton.ts`/`w5bStrict.ts`（camelCase：`w5b` 后接大写 S，`[._-]` 不匹配）未被计入，但它们是 12+ 生产引用的真波次残留。**修法**：波次正则增加 `w\d+[a-z]?[A-Z]` 或 `w\d+[A-Za-z]{2,}` 变体（覆盖 `w5bSkeleton`/`w5bStrict`/`note_w6e_skeleton` 等），并在「误报修正」后用 basename 口径重跑锁基线。

**（三）marker 指标分母不清**：脚本 `rg -c` 数的是**匹配行数**（实测 2709），analysis/06§② 数的是 **token 数（2867）**。两者分母不同，做 Δ 时必须显式声明口径；建议脚本改为输出两列（token 数 + 文件数），段落注释写清「token 数=§22 口径、行数=参考」。**不统一口径则纵向 Δ 全无效**。

**做什么**：改 `scripts/check-convergence-metrics.mjs` 三处（波次 basename-only、补 camelCase 变体、marker 双口径），并新增 `trackedRuntimeArtifacts` 对 `git rm --cached` 后文件消失的确认逻辑（或提示用 `git ls-files` 复核）。
**删什么**：删除 full-path 匹配逻辑（或降级为「目录级提示」，不计入 count）。
**依赖**：无。
**验收**：`node scripts/check-convergence-metrics.mjs` 波次 `count` 覆盖全部实际 36+2 命名文件（含 w5bStrict/w5bSkeleton），不再把 note_w4c_contribute 5 文件逐文件误计；marker 输出双口径列。

### 3.3 删除候选证据库（执行治理机制，D0）

**核心问题**：review.md §19.08/§23 要求 08 删除清单「只列证据、主控裁决、删后 grep 零命中」，但没有可持续载体，导致每轮重新数数、且 X1 与各功能维度删除口径互相重复。

**做什么**：在 `docs/input-stream-consolidation/execution/00-删除清单.md` 建一张活清单，列为 `候选对象 | 证据(file:line) | 建议动作(删/重命名/保留) | 归属维度 | 主控裁决 | 完成证据(grep/门禁) | 日期`。每轮审计位（①a）增量 append，**同一对象不重复登记**（用度量脚本输出做去重键）。
**删什么**：无（仅文档维护）。
**验收**：清单在每轮完成后有增量；凡 `主控裁决=删` 的行必须带「grep 零命中 + 门禁绿」完成证据才能划 ✓；出现重复登记视为审计位事故（记 §18）。

### 3.4 「无删除的轮次不算完成」的落地公式

落地为**可执行的轮级原子判定**，而非整轮末尾叙事：

```
轮次完成 = (该轮定义的目标实现完成)
       AND  该轮含 ≥1 个「硬删除」指标达成
            └─ 硬删除：波次命名文件数下降 ≥1（X1 轮）
                     或 概念路径数下降 ≥1（T2/T4/P1/V1 轮）
                     或 未接线标记 Δ 为负（X1a 轮）
       AND  每个删除目标 grep 零命中（附命令输出，review.md §23.5）
       AND  净删除行数 > 0（删 − 增）
       AND  typecheck/cargo/vitest 相应门禁绿
```

- **X1 轮**：硬删除 = 波次命名文件数下降 ≥1。
- **T2/T4/P1/V1 功能轮**：硬删除 = 概念路径数下降 ≥1（该维去 dual-path/dead-layer）。
- **X1a 未接线清零轮**：硬删除 = 未接线标记 Δ 为负。
- **防线**：若某功能轮本轮判断「无物可删」，则要么并入一个可删的旁边任务，要么该轮**不算完成**、结转至下一轮合并完成——绝不因「功能做对了」豁免删除条款（对齐 01-细化版 §6.5 + review §15.4）。

## 4. 风险与需真跑验证点

### 4.1 重命名对 import 链的影响面

- **高风险**：`w5bStrict.ts`/`w5bSkeleton.ts`（12+ importers）、`w6_a_s.rs`/`w6_d_s.rs`（`pub mod` + 轨钉测试引用 + Skeleton 语义）。
- **中风险**：`packages/block-paper/src/` 波次测试（同包内互引）。
- **低风险**：`tests/e2e/webview/w6*-spec.ts`、`golden_w2a_deepen.rs`、`*_tests_batch.rs`（isolated test 文件名）。
- **验证方式**：P2 必须真跑 `npm run typecheck` + `npx vitest run`；P3 必须真跑 `cargo test -p conex-doc-collab`。**绝不凭「改名应该没问题」断言**（review §15.4 改名≠收敛）。

### 4.2 度量脚本口径（波次正则误报/漏报）

- 已实测：漏 `w5bSkeleton/w5bStrict`（camelCase）、误报 `note_w4c_contribute/*`（full-path `_w4c_` 子串）、marker 行数/token 数分母不一致。
- **必须先修订脚本（§3.2）并重跑锁基线，才允许任何 Δ 汇报**；否则「波次=0」成为不可能诚实达到的数字或轻易虚报。

### 4.3 未接线标记清零的推进策略

- 未接线 2709 中 Top 为 conex-browser（snapshot 高发）与 agent-workbench server 层——多为**过渡待接线注释**。清零策略：**不做一刀切删注释**，而是分三类：
  1. 对应功能已接线/已删 → 注释改写为定稿或删除；
  2. 对应功能仍半连通 → **不得改注释伪装已接**（违反 §15.2 半连通诚实性），应留给对应功能轮收口；
  3. 对应功能确死 → 随死层删除一起清。
- **红线**：未接线清零轮必须以「接线/删除真实发生」为硬删除依据，禁止为指标跌而删注释掩盖未接线事实（诚实性高于指标）。

### 4.4 其他需真跑验证点

- `note_w4c_contribute` 存在性（audit 06 断「不存在」，实测存在）——主控 E1 前亲自复核。
- `exec_batch.rs` 是否真实功能性批执行（决定改名/保留）。
- `git ls-files` 6 个 db 是否仍被运行写（R0 需先解禁 + 补 .gitignore 子目录锚定）。
