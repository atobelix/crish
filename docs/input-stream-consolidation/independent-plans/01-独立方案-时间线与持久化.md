## 一、方案总览

**整体修复路径一句话**：先把「唯一时间线」这条脊梁彻底立稳——让事件流成为唯一写入路径、把三条互相打架的持久化轨收敛成一条、把 7 层消息类型坍塌到 generated 派生——再以这条脊梁为地面，依次立起注入、权限、投影、插件、撤回、编辑等能力层，每一轮结束都带走至少一条死路径。

**核心主张（独立判断）**：

1. **T1（事件模型扩展）不是「纯新增」，是全局的地基门**：`TimelineTruncate` / `context-state` / `injection` 三类节点类型一旦确定，撤回（R1）、动态状态注入（I1）、静态注入文本化（D2）的三条支线都必须在同一类型域上说话。谁先立类型、谁定义 payload，谁就锁定了后续所有消费方。因此 T1 必须**最先、且一次定型**，不得边用边改。

2. **T2（持久化轨收敛）是全战役最危险的一步，必须按「剥 → 删 → 验」三拍走**：从代码实证看，localStorage 不是死层，而是 SQLite 的**活动镜像 + 失败回退 + 降级戳**（`sessionRustDbSql.ts:218-234` 主控亲验）。直接删会损失降级/镜像/迁移能力，且 `sessionLocalStorage.ts`、`migrateFromLocalStorage.ts`、`sessionQuota.ts`、`sessionAgentsTruncation.ts`、`sessionPersistence.ts` **互相 import**（grep 实证），牵一发动全身。**必须先剥镜像接入点 → 真跑验证降级路径不再被依赖 → 再删轨与死层**。

3. **T3（消息类型单源化）必须同 T2 绑定推进，避免「先删后建」空窗**：`SessionMessage`（store 主型，50 文件/242 次）与 `session_messages` 投影表强绑定；删类型的同时 localStorage/RustDb 双轨还在读它。若 T2 先删、T3 后改，中间态会出现「没有主类型可写」的断层。故 T2 内第二拍「删 RustDb 死层」须以 T3 的类型坍塌为前置，或在 T2 完成后立刻进入 T3（不可跨轮长途）。

4. **T4（单一投影 store）是 T3 的上一级出口，但不应在这个方案的打底层一次做完**：streamingStore 热缓冲是设计内必需桥（16 审计），不是冗余；真正的删点是 storeAccess 三份归一 + UserView 旁路 + 消息双份中的持久副本。T3 把 7 层类型塌成 generated 之后，T4 才能干净合并——**T3 是 T4 的使能者，二者是同一批的两拍，不是一个维度可以跳过的**。

5. **「唯一时间线」的边界必须显式限定到引擎/桌面 events 表；移动端是镜像/缓存消费者，不是放大地图**：19 审计已证明 mobile events 表当前未 live 接线（`dbBootstrap.ts` 未接事件持久化），其 `deleteOlderThan`/`runCleanup` 是**已建契约 + 尚未接线的缓存回收执行器**，不是运行期时间线删除。因此收敛方向不是「强行让 mobile 全量保留事件」，而是「mobile 的事实源 = 桌面 daemon 续传（events.resume），本地表仅是有限缓存」，并在**接入事件持久化的那一刻**就按逻辑截断语义落地——避免反例实跑后再修。

## 二、对 14 维框架的验证与调整

### 2.1 T1–T4 拆分是否合理

**合理，且打底层这四维确实是可以先于所有能力层独立完成的地基**。但有几处需再拆或需在相邻维度间补一条依赖：

- **T1 建议再拆为 T1a / T1b 两拍**：T1a = 类型定义 + registry_drift + generated 再生成（纯契约层，无消费方）；T1b = mobile `parseEngineEvent` 补位 + 事件体类型化（19 审计 §5.1 的「补钙」）。**理由**：T1a 是纯 Rust→TS 契约动作，其它 Agent 的能力层（撤回 R1、注入 I1）需要等 T1a 落地；而 T1b 是移动端改造，可与能力层并行。把两件事并在一个「T1」里会让并行调度变粗。
- **T2 必须按「剥镜像 → 删轨道 → 删死层」拆成三步**（这正是任务书提示的疑点，我确认成立）：
  - **T2-1 剥镜像**：先改 `sessionRustDbSql.ts` 的 saveSessionBody 不再写 LS 镜像（`:218-220`）、invoke 失败不再回退 LS（`:234`）、不再打降级戳（`:236`），并核对 migrateFromLocalStorage 的入口是否还需要 LS 轨。
  - **T2-2 删轨道**：localStorage 轨（sessionLocalStorage 及其镜像/降级/迁移）和 RustDb 前端皮的**确无存活面**的部分删除。
  - **T2-3 删死层**：`conex-db::append_session_messages` 死库函数及其陪葬测试/bench（upgrade_e2e / stress_write / db_write / tests.rs:371 / tests_migrations.rs:437）。
  - 之所以必须分三步：三者的**删除安全前置不同**。镜像剥除需要「SQLite 为绝对主存」这一前提被真跑验证；轨道删除需要「不再有任何消费方 import localStorage」被 grep 验证；死层删除只需确认无 Tauri 命令/无 manifest/无前端调用。混为一步则无法在任一步失败时准确定位回滚面。
- **T3 建议从「类型单源化」中析出「重放水合归一」**：01 审计 P6 指出 `sessionEventHydrate` 用 `agentEventFromOrchestrator`/`blockText` 手写解析、绕过 generated parser。这一条与其说是“类型定义”问题，不如说是「事件读路径双实现」问题（实时流用严格 parser、重放用手写宽容 parser）。我建议把它列为 T3 的独立验收点，或者并入 T3 与 T2 的接缝，但必须**显式点名**，否则容易漏删。
- **T4 需进一步拆分出「投影原语下沉」**：19 审计 §5.1 指出 mobile eventReducers/eventMappers 的纯函数部分与 desktop chat-bridge 是两套平行实现。这部分（跨端投影原语）与「单一投影 store」（desktop 内部 streamingStore∥layoutStore 合并）**不是同一个动作**：前者是跨端共享，后者是桌面内部合并。建议 T4 拆为 T4-desktop（单一投影 store + storeAccess 归一）与 T4-mobile（投影原语下沉 + 事件体类型化，即 T1b 汇入）两拍，可并行。

### 2.2 其它维度的调整意见

（以下为对 14 维框架的补充/修正意见，供主控合并时取舍；本方案主体仍按 T1–T4 打底 → 能力层 → 撤回 → 横切的顺序。）

- **C1（核心循环瘦身）与 T 打底层无硬依赖，可并行**，但建议在 T1a 之后开始，避免两类一起动 events.rs/handlers 的并发语义漂移。C1 的 `BackupMiddleware`/`RecoverySteeringStrategy` 移出核心是两个「反向依赖硬编码」缺口（09 审计），本质是抽象纪律问题，不是时间线问题，可独立推进。
- **P1（权限归一）依赖 T1 的 context-state 类型**（权限模式变成 context-state 节点的载荷来源），但 P1 的 ToolCategory 真值化与「类别 → 回滚策略」注册表**还依赖 D3/10 审计的「可回滚性」标记**——这一块我建议明确归入 R1（撤回回滚的执行器），P1 只做审查策略单一路径。避免 P1 与 R1 各自建一套类别轴（abstract 纪律 1「一个概念一种类型」）。
- **I1（注入与队列）的「双队列收敛」应为 P1 之前或 P1 同轮**：双队列（AgentInputQueue.followUp ∥ PendingMessageQueue）是 08 审计指出的「B 扩展点前置收敛」，它同时是 context-state 节点（扩展点 A）的注入载体。如果 T1 定了 context-state 类型、但没有先把队列归一，则 context-state 挂载没有确定落点。建议 I1（至少其队列归一部分）紧随 T2 之后，不必等 P1。
- **V1（展示投影归一）依赖 T4**（单一投影 store 是 timelineNormalizer 的消费基础）。**V1 是能力层中最后进的**，因为展示是「投影从统一时间线派生」的末端。
- **E1（插件轨收口）与时间线无依赖**，可全程并行，但须把「ContributeViewRegistry 双实现死层」「src/plugins 零 import 死代码」等点单列删除面。
- **R1（撤回）是全局的验收试金石**：它横跨 D1（截断）/D3（回滚）/D4（投影刷新）/D5（策略插件化）。R1 的**硬件前置是 T1a（TimelineTruncate 类型）**，但 R1 真正的复杂度在「先停后截」的边界冻结与「类别→回滚」注册表——这两块依赖 C1 的停止链完整 + P1 的类别轴。**R1 应放在能力层收口后，作为压轴之一**，不应太早。
- **R2（编辑保护）同理，依赖 T3**（编辑会话事件基于节点 id）。R2 的 dirtyRef 开环脏标、双 follow_up 竞态是独立可修的，但「失效传播（撤回→invalidate 编辑中对象）」依赖 R1 语义，故 R2 与 R1 邻。

### 2.3 逻辑顺序建议（综合）

```
打底层（先，串行，收敛版可两轮左右）：
  T1a（类型定案）→ T1b∥T2-1（轨剥除 + mobile 补钙）
  → T2-2（删 ls/RustDb 无存活面） → T2-3（删 append 死层）→ T3（类型坍塌 + 重放归一，衔接 T2）
  → T4-desktop ∥ T4-mobile（投影 store 合并 + 投影原语下沉）

能力层（打底后，部分与打底并行）：
  C1 ∥ E1（核心瘦身 + 插件轨，可与 T 并行）
  I1（队列归一部分紧随 T2）→ P1（权限单一路径）
  V1（最迟，依赖 T4）

撤回与编辑（压轴）：
  R1（依赖 T1a + C1 + P1）→ R2（依赖 T3 + R1）

横切：X1 改名/卫生全程可并行穿插。
```

> 关键判据：打底层四维是「唯一时间线」的结构件，**必须在任何能力层之前基本立稳**；同时打底层内部有严格的「类型→解析→存储→投影」递进。概念互不相交原则下的并行仅限：T1b∥T2-1（不同文件域）、C1∥E1（不同域）、T4-desktop∥T4-mobile（不同端）。

## 三、维度方案（核心覆盖 T1–T4；其它简略但点名问题）

### T1 事件模型扩展（地基门）

**核心问题（带着 analysis/ 证据）**：

- `TimelineTruncate` 事件类型全仓零命中（10 审计 `crates/conex-types/events.rs` 无此变体；grep `timeline-truncate/Retraction` 仅出现在 docs）。
- `context-state`/`injection` 节点类型不存在：`AgentMessageRole` 仅 System/User/Assistant/Tool（02 审计 `message.rs:15-24`）；`AgentMessageBlock` 仅 text/thought/tool-call/tool-result（`message.rs:100-126`）。
- 注入/状态依赖 `metadata.kind` 字符串魔法值（`runtime-steering`/`nudge`/`diagnostic`/`steering`），无常量枚举（02 审计 `nudge.rs:100,120,162`、`steering_queue.rs:91`、`streaming.rs:338`）。

**做什么**：

- 在 `crates/conex-types/src/events.rs` 新增 `AgentEvent::TimelineTruncate { boundary_seq, session_id, ... }` 变体，并接入会话事件持久化白名单（对齐 `is_non_persistent`/`is_round_domain_event` 判断面，见 `orchestrator/events.rs:36,134`）。
- 在 `message.rs` 补 `context-state` / `injection` 角色或块类型；把 `metadata.kind` 魔法字符串收敛为枚举常量 `AgentMessageMetadataKind::{Nudge/Steering/ContextState/Diagnostic}`（02 审计问题⑥）。
- `registry_drift` 同步；运行 `scripts/generate-engine-bindings.mjs` 再生成 `packages/shared-types/src/generated/`（parser.ts/events.ts/types.ts）。
- mobile 补 `parseEngineEvent`（generated parser）给事件体加结构校验（19 审计 §5.1）。

**删什么**：无新增删除（纯新增类型）；但建议顺手清理 `command_manifest.rs:13/:66` 已过期的「append_session_messages 已登记未接线」注释（这是一条诚实句漂移，见 T2-3）。

**依赖**：无（打底最前）。
**验收建议（可执行断言）**：

- `cargo test -p conex-types registry_drift` 绿。
- `packages/shared-types/src/generated/engine/parser.ts` 包含 `TimelineTruncate` + `context-state` 类型，且 `rg 'context-state|TimelineTruncate' packages/shared-types/src/generated` 非空。
- `npm run typecheck` 绿。
- rustc 编译通过。

### T2 持久化轨收敛（危险且最重要，三步走）

**核心问题（带着 analysis/ 证据）**：

- **localStorage 不是死层，是活动镜像 + 失败回退 + 降级戳**：`sessionRustDbSql.ts:209-237` saveSessionBody 在 SQLite 成功后仍 `lsSaveSessionBody` 写镜像（`:218-220`），invoke 失败回退 LS（`:234`）+ `markDegradedSession`（`:236`），成功清降级戳 `clearDegradedSession`（`:223`）。（主控亲验，01 审计 §2.4）。
- `sessionPersistence.ts:61` re-export 16 个 localStorage 导出，是活动依赖（01 审计 §2.4）。
- `sessionLocalStorage.ts` 本身又 import `sessionRustDb`（grep 实证 `sessionLocalStorage.ts:64`），存在互相引用。
- **RustDb 前端轨存活面待细化**：`sessionRustDb.ts` 门面 + Wire/Fallback/Sql/Hydrate ×4 实现 + 门面 import 来自 `sessionRustDbSql`/`sessionRustDbHydrate`（grep 实证 `sessionRustDb.ts:44,50`），被 `sessionPersistence.ts:71`、`ConnectionLifecycle.ts:410`、`migrateFromLocalStorage.ts:35` 真实消费——**不是全部可删**，其中带「写竞态防线/版本 CAS」的 Sql/Hydrate 是 SQLite 前端 API 面，删除会断主存写入。
- `conex-db::append_session_messages`（`messages.rs:107-167`）死库函数：无 Tauri 命令 / 无 manifest / 无前端调用；陪葬测试 = `tests.rs:371,407`、`tests_migrations.rs:437,448`、`upgrade_e2e.rs:416`、`stress_write.rs:268`、`benches/db_write.rs:50`。

**做什么**：

- **T2-1 剥镜像**：改 `sessionRustDbSql.ts` saveSessionBody —— 成功路径删 LS 镜像写、失败路径删 LS 回退与降级戳；核对并清理 `clearDegradedSession`/`markDegradedSession` 及相关降级通道。同步评估 `migrateFromLocalStorage.ts:221` 的 `cleanupLegacyLocalStorageSessionsGuarded` 是否还依赖 LS 轨。
- **T2-2 删轨道（存活面真跑核实后）**：删除 `sessionLocalStorage.ts`（及其镜像/降级/迁移逻辑）与 RustDb 前端皮中确无存活面的部分（Fallback 的 LS 回退，若 T2-1 后无调用则删）。**保留 SQLite 前端 API 皮（Sql/Hydrate/Wire 转换层），因为它们承载的是 conex-db 主存写入**——不是删除目标。
- **T2-3 删死层**：删除 `conex-db::append_session_messages` 死库函数 + 其全部陪葬测试/bench。注意 `append_session_messages` 在 `command_manifest.rs:66` 是「登记先行 registered=false」的设计占位（多份 feature-gap/rust-rewrite 文档把它定为有意识的三端对齐登记面，e.g. docs/feature-gap-analysis/audit/A8-死代码与未接线专项审计.md:113），**若主控认同「登记先行」惯例，则删除库函数后应同步把 manifest/注释口径清理为「已删除」，避免留一个空壳占位**——这条我要区别于 01 审计「直接删死函数」，因为它是登记面的一部分，需由主控裁决是否连登记面一起清。

**删什么**（详列见下方删除面汇总）：sessionLocalStorage.ts、LS 镜像/降级/迁移链、RustDb Fallback（视 T2-1 后存活面）、append_session_messages 死层 + 陪葬测试、command_manifest 过期注释。

**依赖**：T1 类型（不强制，但 T1a 后跑更稳）；T2-2 依赖 T3 的类型坍塌使能删除投影主型依赖。
**验收建议（可执行断言）**：

- `rg -l 'sessionLocalStorage|lsSaveSessionBody|markDegradedSession|clearDegradedSession' apps/crish-desktop/src` 输出为空。
- `rg 'append_session_messages' crates apps packages` 输出为空。
- 真跑：`npm run test`（vitest 快层）+ `cargo test --workspace` 绿。
- **真跑降级路径**：模拟 `save_session_body` invoke 失败，断言「不再自动回退 LS」且前端进入可感知的降级提示（而非静默 LS 回退）；再模拟 SQLite 成功，断言「不再写 LS 镜像」。

### T3 前端消息类型单源化

**核心问题（带着 analysis/ 证据）**：

- 同一消息 7 层类型形态（01 审计 P1）：Rust AgentMessage / Rust SessionMessage(`lib.rs:138`) / Rust HistoryMessage(`history.rs:17`) / TS SessionMessage(`store/types.ts:385`) / TS MessageTimelineBlock(`store/types.ts:348`) / TS HistoryMessage(`historyMessages.ts:6`) / generated AgentMessage。
- 前端 timeline `MessageTimelineBlock`（含 image/step_start/step_end，字段 content）与 Rust `AgentMessageBlock`（text/thought/tool-call/tool-result，字段 text）**不同构**（01 P3）。
- `sessionEventHydrate` 绕过 generated parser 手写宽容解析 `agentEventFromOrchestrator`/`blockText`（01 P6，`sessionEventHydrate.ts:39-60`）——实时流/重放两套解析并存。
- Rust hydrate `resolve_blocks` 需宽容回退（`session-loop/src/hydrate.rs:120-135`），数据两套 schema。

**做什么**：

- 以 generated `AgentMessage`/`AgentMessageBlock` 为唯一 canonical；TS `SessionMessage`/`MessageTimelineBlock`/`HistoryMessage` 改为类型别名/直接派生。
- `onMessageEnd`（`messageHandlers.ts:88-147`）与 `sessionEventHydrate` 统一改走 generated parser 直接派生 store 消息，删手写转换。
- 消除 Rust hydrate `resolve_blocks` 的宽容回退（统一 schema 后不再需要）。

**删什么**：手写消息类型定义、事件重放手写解析器（P6）、Rust hydrate 宽容回退分支。
**依赖**：T2（投影轨收敛，删类型前先确认投影读写目标）；T1a（generated 再生成）。
**验收建议**：

- `rg 'interface (SessionMessage|HistoryMessage|MessageTimelineBlock)' apps/crish-desktop/src --glob '!**/*.test.*'` 输出为空（类型别名除外）。
- `rg 'agentEventFromOrchestrator|blockText' apps/crish-desktop/src` 输出为空。
- `npm run typecheck` + vitest 绿。

### T4 单一投影 store

**核心问题（带着 analysis/ 证据）**：

- 消息双份存储（12 审计）：`streamingStore.bvKey` 热缓冲 ∥ `layoutStore.messages` 持久副本，同一正文/工具在两个 store 各存一份。
- storeAccess 三份：`store/storeAccess.ts`(读面) ∥ `api/storeAccess.ts`(编排) + `api/store-access/componentAccess.ts`(过渡读面)。
- 跨端投影双实现：mobile eventReducers/eventMappers ∥ desktop chat-bridge（19 审计 §4）。

**做什么**：

- 单一投影 store：合并 streamingStore 消息部分（保留热缓冲语义，16 审计确认其为设计内必需桥）与 layoutStore 消息部分。
- storeAccess 三份归一：删 `api/store-access/componentAccess.ts`。
- 投影原语下沉：抽 mobile eventReducers/eventMappers 纯函数部分 + desktop transport 无关的事件消费映射入 shared 包（候选 shared-utils 或新建 shared-projection），两端共用（19 审计 §5.1）。

**删什么**：`api/store-access/componentAccess.ts`、双存储冗余持久副本、跨端两套平行事件消费映射（收敛为共享原语）。
**依赖**：T3（7 层类型塌成 generated 是合并的前置）。
**验收建议**：

- `node scripts/check-store-facade.mjs` / `check-store-writes` 绿。
- `rg 'componentAccess' apps/crish-desktop/src` 输出为空。
- 消息正文存储副本 = 1（热缓冲除外）——以 grep store 写入点唯一为准。
- mobile 事件类型化改造后 `rg 'readString\('` 数目显著下降（结构校验接管）。

## 七、诚实边界与待验证清单

- 本方案所有「存活面」「死层」判定基于**源码形状 + grep 引用**；未真跑任何端到端。以下列为**标注待验证**：

  - mobile events 表当前未 live 接线的断言（19 审计「dbBootstrap 未接」为源码形状，接入轮需复核）。
  - R1 撤回「先停后截」原子性（需真跑端到端）。
- 依赖 DRY：本方案对 14 维框架的调整（T1 拆分、T2 三步、T4 拆端、R1 接收类别轴）是为了**让时间线/持久化主线与兄弟 Agent 的能力层对齐**，不新增任何抽象层，遵守抽象纪律 3「分层上限三层」。
