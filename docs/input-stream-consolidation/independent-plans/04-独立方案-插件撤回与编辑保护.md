## 0. 本方案的三条核心取证修正（先读，影响前面维度结论）

方案生成前我这轮直接读源码核实了三处 **audit 结论需修正/澄清** 的事实，它们改变 E1 的执行顺序与 R1/R2 的依赖假设：

1. **`src/plugins` 是「零外部消费者的死层」且无迁移前置**（修正 audit 05/16 的「settings-extensions 消费」说法）。
   - 实证：`apps/crish-desktop/src/components/settings-extensions/buildInstalledExtensions.ts:29` 的 `plugins: PluginCardState[]` 是 **函数入参**，其数据源来自 `pluginRegistryAdapter.listPluginCardStates()`（`useExtensionMarket.tsx:206`）；而 `pluginRegistryAdapter.ts` 全文件**只 import 外部 npm 包 `@crish/plugin-import-claude-codex`**（`pluginRegistryAdapter.ts:13`），**不 import 本仓 `src/plugins` 任何符号**。
   - 全仓 grep：`from '.../plugins/...'` 在 `apps/crish-desktop/src` 仅命中 `src/plugins/` **自身**（`index.ts:22-31` 的自举）。`usePluginStore`/`PluginRegistry`/`renderView`/`CrishPlugin` 除 plugins 目录自身与 `PluginRegistry.test.ts` 外**零生产引用**。
   - 结论：**不存在「须先迁 settings-extensions 消费」的前置**。`settings-extensions` 的「插件卡片」走的是独立第三路径（外部 import 包 manifest + localStorage），与 `src/plugins` 死层**互不接线**。E1 可直接删 `src/plugins` 整目录，**无需先迁移**。
   - 依据 detail：audit 05 §② P4「三套插件面互不接线」本身是对的（settings adapter / src/plugins / contribute 轨确实三套隔离），但 00-总方案 §3.1 与 01-分维度把「settings-extensions 消费 src/plugins」写成删除前置是**误读**——消费关系其实不存在。

2. **`kill_all` 的撤回终态语义已基本解决（事件层 Cancelled 已成生产真值）**（修正 audit 10 的「待评审 failed vs cancelled」推测）。
   - 实证：`crates/orchestrator/src/lifecycle.rs:256-261` 自 LK-07 R-14 起，`kill_all` 在把 `session_agents` 行 status 归一为 `failed`（`:245-255`）**同时**直发 `subagent-ended(status=cancelled)` 事件（`emit_killed_ended`，`:511-519`，`SubagentEndStatus::Cancelled`）。
   - 即：**DB 行字段 = failed，事件（投影/UI 的事实源）= cancelled**。撤回关停子代理时前端看到的终态事件已是 `cancelled`，与撤回语义一致。
   - 残留不一致（R1 需处理）：row 字段 `failed` 与事件 `cancelled` 双写不一致。撤回的**投影事实源**是事件（够用），但若有人读 `session_agents` 表会看到 `failed`。R1 应把该「row=failed / event=cancelled」的差异记为**已知双写约定**并在撤回收口统一（见 R1 §「kill_all 终态语义」）。

3. **`persist_plugin.rs` 的 `on_committed_expect` 不是双实现，是必要的 ARC 转发守护**（澄清 audit 15 的「疑似双实现需核唯一接线」）。
   - 实证：`persist_plugin.rs:227-234` 是 `SharedWorkspaceStore` 的 trait 覆写，注释明确「**必须覆写转发**——否则 trait 默认会经 `on_committed` 静默回退纯 LWW，CAS 在生产路径失效」。它是**转发到唯一定权实现**（`:71`），不是第二份 CAS 逻辑。
   - 结论：R2 不把此行当重复面删除/合并；它恰恰是编辑保护 CAS 在生产路径生效的**正确性守护**，保留。

> 三处修正的可靠性：均为 `grep` + 单文件精读的**源码形状**证据；grep 对「动态 import / 反射注册」不可见（`src/plugins` 自举、pluginRuntime 动态 import 已覆盖），若另有隐式消费应补真跑验证（见 §7 G1）。

## 1. 方案总览

**整体修复路径一句话：** 以「**先删死的插件轨（E1，无迁移）→ 再建撤回这条唯一写作路径（R1，事件→停→回滚→投影→回填）→ 最后补上编辑保护这个不变量 7 的独占子面（R2）**」为主线推进 14 维，撤回/编辑所需的类型（T1）、时间线（T1/T2/T3）、类别轴（P1）先行打底，其余维度作为支撑线穿插。

**核心主张（≤5）：**

1. **插件轨收敛是「纯删除 + 无迁移」**：`src/plugins` 整目录为**零外部消费死层**（§0-1 实证），`settings-extensions`/`plugin-sdk`/`ContributeViewRegistry` 三条路径本就不接线；E1 的执行顺序是「**先批量删、后清引用外壳**」而非「先迁移再删」。唯一需先落的是 plugin-sdk `index.ts` 的 `Plugin`/`definePlugin` 轻量接口从入口移除（P2-1），避免删 `src/plugins` 后留下误导性 API。

2. **撤回（R1）是「只追加不变量」在会话内的唯一允许的写入例外形态**：它靠新增 `TimelineTruncate` **事件**（而非物理删）表达，六步中「**停 run**」「**发截断事件**」两步的顺序不可颠倒（§2.4「先停后截」），回滚/投影/回填在此之后按 boundary 语义收口。R1 依赖 T1（事件类型）、P1（类别轴）打底，也依赖 T2/T3（时间线唯一化）才可重放到 boundary。

3. **R2 编辑保护不是撤回的平级能力，是撤回/远端合并的「失效传播下行面」**：R2 的 `invalidate` 主线（截断/撤回 → 使编辑中对象失效）**依赖 R1 先落地 `timeline-truncate` 事件可被前端订阅**；因此逻辑顺序 R1 → R2，而非倒序。R2 同时做四件事：编辑会话抽象、dirtyRef 开环修复、双 follow_up 竞态归一并、设置页失效订阅。

4. **删除面是收敛的净收益**：`src/plugins`（10 文件 + 测试）、`note_w4c_contribute`（5 文件含 W4C 测试）、plugin-sdk `Plugin`/`definePlugin` 轻量接口、`MessageSnapshots.operation:'edit'` 死枚举、Rust `tool-update` 死契约或 EventPolicy 收敛、波次命名文件，全部为可 grep 零命中的删除候选。**「源码形状零命中」是删除完成的标准机器证据，但删除裁决前必须过一次真跑**（见 §7 G1-G2）。

5. **撤回的「文本回填」「快照语义」「边界冻结」三处是本方案新增的实现重点**，且都落在**已被现有底座覆盖 80%** 的复用点上（停止=L3 成熟、回滚=trash.rs snapshot/restore_force 现成、投影=withdrawMessage 升级、回填=composer draft set 接口复用）——贯彻「收敛而非新建」。

### 2.2 E1 插件轨收口的执行顺序（验：先迁 settings-extensions 再删？）

**裁定：不需要「先迁 settings-extensions」。** settings-extensions 的插件卡片消费的是外部 `@crish/plugin-import-claude-codex`，与 `src/plugins` 无关（§0-1）。`src/plugins` 可直接删。

但 E1 内部仍有一个顺序：

1. **先移 plugin-sdk 入口**：把 `packages/plugin-sdk/src/index.ts:4-17` 的 `Plugin`/`definePlugin` 轻量接口移除（收敛到 shared-types `PluginLifecycle`），**这是删 `src/plugins` 的一个前置符号清理**（`CrishPlugin` 与 `Plugin` 三套接口归一），避免删 `src/plugins` 后 plugin-sdk 残留误导接口。
2. **再删 `src/plugins` 整目录**（index/PluginRegistry/usePluginStore/types + 四插件 + PluginRegistry.test.ts）。
3. **再清 Rust `note_w4c_contribute`**（5 文件 + lib.rs re-export），**保留下「拒写句柄」语义**：audit 05 P5 建议「保留拒写句柄并入 W6-E-S 统一表」。我的裁定：本战役 R1 的「类别→回滚策略注册表」才是统一表；`note_w4c_contribute` 的拒写句柄（`CONTRIBUTE_FORBIDDEN_WRITE`）语义若无人消费可一并删，若 P1 类别轴用到则提升为 P1 的「权限/回滚共用句柄表」元素（二选一，见 E1 §）。

### 2.3 R1 撤回六步的实现顺序（事件→停 run→回滚→投影→文本回填）

**裁定：总体遵循 §2.4 六步，但「事件与停 run」的原子提交是本方案强调的关键。**

### 2.4 R2 编辑保护与 R1 的先后

**裁定：R2 的「失效传播」依赖 R1 截断事件，故 R2-b（撤回/截断 → invalidate）在 R1 之后**；但 R2-a（编辑会话抽象、dirtyRef 修复、双 follow_up 归一、设置失效订阅）**不依赖 R1，可前置并行**。

- 失效传播是否依赖 R1 截断？**是**。R2 的「撤回/截断 → invalidate 编辑中对象」必须订阅 `timeline-truncate` 事件（R1 产出）。若 R2-b 先行，则无截断事件可订阅。这是 R1→R2 顺序的最硬依赖。
- 但 R2 的价值不等 R1：dirtyRef 开环（StrictContentRowLeaf）、双 follow_up 竞态（useChatComposerProps drain 抢跑）、设置页无失效订阅，这三个缺陷**现在就可修**，与撤回事件无关。故拆 R2-a/R2-b 两段。

### 2.5 其他维度调整意见

- **T2（持久化轨收敛）与 R1 深度耦合**：R1 撤回依赖「事件流唯一可重放」（T1/T2/T3 打底）。T2 的 `session_messages` 表是投影缓存（可先删后插重建），**这不破坏撤回**，反而是撤回「投影按 boundary 重建」的正确承载（audit 10 §③-2 已证）。T2 应明确「events 表只追加是撤回重放的承载、session_messages 是投影可重写」两级语义。
- **T3（前端消息类型单源化）是撤回「从事件取回文本回填」的前提**：只有消息类型从 generated 派生、消息可经事件流呈现时，撤回才能从 boundary 对应事件稳定取回 text。故 T3 不得晚于 R1-⑤。
- **P1（类别轴）同时喂两个注册表**：权限（allow/deny/ask）与回滚策略（可回滚性/回滚方式）。P1 只做一次 ToolCategory 生产真值，R1 的「类别→回滚」注册表与权限注册表**共用同一类别轴**（audit 10 §③缺口3）。**P1 必须先行**，否则 R1 回滚无类别可依。
- **V1（投影归一）与 R1 的「投影重放至 boundary」共用一条投影链**：建议 V1 的 timelineNormalizer 定为投影主路径，R1 的投影刷新直接消费它，避免两头实现。可用「V1 ∥ R1」并行。
- **E2（Rust 扩展门面）应排在 E1 之后**：E1 删除死插件轨后，E2 才有干净的「ToolRegistry+register_runtime+MCP」唯一门面可登记扩展点 A/B/C/D 承载面。E1 是 E2 的前置清场。
- **I1（双队列归一）为 R2 的双 follow_up 归一提供语义锚**：R2 的「双 follow_up 竞态关闭」依赖 I1 先把客户端两条 follow_up 路径归一为一条（composer onSend 队列 ∥ useSlashSend enqueueFollowUpMessage）。故 R2-a 若涉及 follow_up 归一，应依赖 I1 或在 I1 后做。

## 3. 维度方案

> 本方案至少覆盖 E1/R1/R2 三个维度，且对 R2 拆 a/b 两段；结构与 `plans/01-分维度框架-细化版.md` 一致（做什么/删什么/文件域/验收入口），每维度附加「依赖」与「可执行断言」。

### 3.1 E1 插件轨收口

**核心问题（带证据）**

- `src/plugins` 整目录为死层：全仓 `grep "from '.../plugins/'"` 仅命中 plugins 自身（index.ts:22-31 自举）；`usePluginStore`/`PluginRegistry`/`renderView`/`CrishPlugin` 除 plugins 目录与 `PluginRegistry.test.ts` 外零生产引用（§0-1 实证；audit 16 §④ D1 亦证「核心 UI 对 src/plugins import 边 = 0」）。
- 四官方插件为隔离死代码：`plugin-browser`/`plugin-computer-use`/`plugin-follow-up`/`plugin-markdown-editor` 的 `activate` 只挂 DOM CustomEvent（audit 05 §②），其能力已有真身（浏览器/电脑走独立引擎桥、follow-up 走 `followUpSuggestions.ts`、markdown 走 `core_md_render`，audit 16 X1-X5 实证）。同名撞车误导维护（audit 16 E4/E5）。
- `note_w4c_contribute`（Rust ContributeViewRegistry）为双实现死层：与 plugin-sdk TS `ContributePointRegistry` 同构，生产零消费（仅 lib.rs re-export + W4C 测试，§0；audit 05 P5）。注意其「拒写句柄」安全语义需处置（见下）。
- plugin-sdk `Plugin`/`definePlugin` 轻量接口误导性：三套插件接口并存（plugin-sdk Plugin ∥ CrishPlugin ∥ shared-types PluginLifecycle，audit 05 P2），hooks 用 `unknown` 无 payload 绑定（P3）。

**做什么**

### 3.2 R1 撤回实现（六步）

**核心问题（带证据）**

- 撤回能力现有底座 80% 具备、缺 4 个接线点（audit 10 全篇）：停 run 成熟（L3/safe_point/kill_all）、trash.rs snapshot/restore_force 现成但**未被撤回调用**、`timeline-truncate` **全仓零先例**、draft 快照成功即清（撤回无法回填）。
- 工具无「可回滚性」标记：`ToolCategory` 恒 Internal（conex-types/tool.rs:11-14），`exec_single/exec_batch` 无 revertible 元数据（audit 03/10）。
- `withdrawMessage`（sessionMessageActions.ts:93-137）只做**前端 message 数组物理截断**，不落事件、不按 seq、不联动停 run——是撤回的「残缺先例」，撤回需升级为「事件 + boundary + 停 run + 回滚 + 重放 + 回填」。
- kill_all 行字段 failed / 事件 cancelled 双写不一致（§0-2 实证）。

**做什么（六步实现顺序）**

1. **事件类型打底**：在 `conex-types/events.rs` 新增 `AgentEvent::TimelineTruncate { session_id, boundary_seq, reason }` + 会话事件持久化白名单接入（audit 10 §②步骤2 缺口）；引擎侧新增「user 消息 id → boundary seq」定位原语。
2. **停 run**：UI 撤回入口 → 复用 `runControl.dispatch(L3)`（runControlClient.ts:104）/ 或新增独立 `retract` wire → 主 run 走 L3 force_cancel/AbortSignal（safe_point.rs:119-152）→ aborted→Cancelled（end.rs + run.rs:644）；**先对会话 running 子代理 `kill_all`**（lifecycle.rs:200）。撤回 reason 打 `retraction:<seq>`。**「先停后截」原子性**：L3 收口 + `timeline-truncate` 发射置于同一提交/同一边界 seq（audit 10 §④缺口1），保证截断后无新写入。
3. **回滚**：建「工具类别 →（可回滚性/回滚策略）」注册表（扩展点 D，**与 P1 权限注册表共用类别轴**）；对 boundary 之后执行过的写类工具输出路径调 `TrashService.snapshot`+`restore_force`（S10b 写前快照语义）；git 类回滚复用 `RevertPolicy` 审批门禁（revert_guard.rs:117-132）再执行；只读类无操作。审批在途工具：撤回优先 abort，已批准未执行/已执行项按类别策略（audit 10 §④ 并发缺口2）。
4. **投影刷新**：前端从事件流重放至 boundary（T2/T3 保证事件可重放）；`withdrawMessage` 升级为「消费 `timeline-truncate` 事件，投影按 boundary 重建」而非物理截数组（与 V1 投影链共用）。
5. **文本回填**：从 boundary 对应 user 消息取回 text → `setComposerDraft`（layoutStore/sessionCrudActions）→ 附配件 `setAttachments`（useSlashSend.ts:211）；草稿快照需保留到可撤回窗口或从消息历史取回（audit 10 缺口4）。
6. **kill_all 终态语义统一**：将「row=failed / event=cancelled」双写约定显式落文档，驳回撤项目统一以事件（cancelled）为投影事实源（§0-2）。

**删什么**：无（新建能力；`withdrawMessage` 从其物理截断语义改造，不新增第二条撤回路径）。移动端 `eventsDao.ts:148`/`cachePolicy.ts:206` 物理删除为**只追加反例**——按 00-核心模型 §1 反例处置：要么改为逻辑截断剪枝，要么显式降级为「已淘汰不可审计」并排除出撤回重放假定（audit 10 §③/§⑤ 两可，本方案建议显式降级 + 移动端不参与撤回重放，标注需主控定夺）。

**依赖**：T1（事件类型）、T2/T3（事件流唯一可重放）、P1（类别轴 → 回滚注册表）、V1（投影链）。

**验收建议（可执行）**
