### 2.3 零消费核实（任务书第 4 项）

`shared-types/src/permissions.ts` 三个接口族 **grep 仅命中定义文件 + index.ts re-export（`index.ts:139-143`）**，无任何 `.ts`/`.tsx` 产品消费。`apps/crish-desktop` 的 `ApprovalHandler`（`api/chat-bridge/ApprovalHandler.ts`）是同名**不同物**——前端审批 UI 实现，import 来自 `./chat-bridge/ApprovalHandler`，与 shared-types `permissions.ts:36` 的 `ApprovalHandler` 接口**无类型关联**（经 index re-export 的 PermissionRule/ApprovalHandler/RuntimePermissionPolicy 全为死类型）。

**结论（核实成立）**：`PermissionRule` / `ApprovalHandler` / `RuntimePermissionPolicy` = **核心循环不可知的死类型接口**，与 03 审计确认的 `PermissionBehavior(allow/deny/ask)` 死类型同族。

### 2.4 核心循环「永远不应知道」的具体功能名单（反向依赖基线）

核心循环 `AgentSessionLoop` 当下未直接内嵌的具体功能清单（这些是否应被视为「核心不应该知道」，见 §④ 禁止反向依赖规则）：

- 四官方插件（markdown-editor/browser/computer-use/follow-up）**不在**核心循环认知面（05 审核 P1）；
- 具体工具实现（read/write/search/shell 等 33 内置）经由 `ToolRegistry` 解耦，核心仅认知「注册表接口」；
- `BackupMiddleware`（写前自动备份）是唯一**在核心循环默认装配的实例中间件**（`loop_options.rs:251`）——注意：这既是核心认知，也是「写前备份」这一**具体功能**被核心循环默认认知的反向依赖嫌疑（见 §⑤清理建议）。

## ③ A/B/C/D 承载差距分析

### A · 注入时机（状态切换 → 即时提交 vs 挂下一条命令）

**现有相关缝**：`AgentInputQueue` 三环（`input.rs:163`）、`PendingNudgeChannel`（`steering/nudge.rs:182`）、编排层 `PendingMessageQueue`（`orchestrator/steering_queue.rs:111`）、plugin-sdk `Plugin.hooks.onSessionStart`（05 审计已确认不承载）。

**承载结论**：注入时机应承载于 **AgentInputQueue 三环 + PendingNudgeChannel/编排层队列**，而非插件 View 轨或 hook 生命周期事件。现状已具雏形（nudge 排下一条用户消息，`steering/nudge.rs` 注释 D8）。

**差距**：

- 缺「注入内容产生器」的类型化**贡献面**：现状 steering 注入是 `RecoverySteeringStrategy` 硬编码 + `PendingNudgeChannel` 内建 nudge；`context-state` 节点（模型名/权限/思考模式，00-总方案 D2）无「内容产生器注册表」表达。
- 三环提交时机是**核心内置枚举**（Force/Steer/FollowUp），非插件可注册的扩展面——扩展点 A 若要让第三方贡献「注入时机策略」，需新增贡献类型（见 §④）。

### B · 提交时机（即时插队 vs 正常队列）

**现有相关缝**：`AgentInputQueue` 三环（`input.rs:169` force/steer/followUp 即三档提交时机）、`InputEnqueueMode`（`input.rs:189`）、编排层 `PendingMessageQueue::transfer_follow_up / drain_nudges`（`steering_queue.rs:220,228`）。

**承载结论**：提交时机本身**已有核心内建三档**（force/steer/followUp），这是核心循环对「提交时机」的正确表达；缺的是**把这三档对外暴露为可扩展贡献面**——现状 `InputEnqueueMode` 是硬枚举，第三方插件无法声明新的「插队策略」kind。plugin-sdk `contribute/types.ts:14` 的 4 kind **无任何 `submit_policy` 类**（05 审计 B 已确认）。

**差距**：核心循环内建三档齐全，但**对外注册面缺失**——没有「提交时机策略贡献」接口/贡献类型。

### C · 审查策略（工具类别 → allow/deny/ask）

**现有相关缝**：

- Shell/权限硬接点：`agent-tools/permission.rs:78`（decide 三态）、`permission.rs:96`（decide_with_redline）、`permission.rs:113`（decide_command）、`permission.rs:135`（decide_command_with_revert）、`permission.rs:196`（PermissionDecisionEngine::evaluate_command 集中在 `permission.rs:197-287`）；
- 核心循环侧：`exec_verdict.rs:99`（ToolExecutor::call_verdict）、`approval_router.rs`、`exec_batch.rs`;
- 工具定义仅 `dangerous` / `fatal_on_error` 布尔标记（`definition.rs:40,46`），**无「工具类别」字段**；`conex_types::tool::ToolCategory` 存在（`tool_events.rs:55` ToolStart 携带 category），但 03 审计确认生产硬编码 Internal。
- shared-types `permissions.ts:4`（PermissionBehavior）与 `permissions.ts:52`（RuntimePermissionPolicy）为死类型（§② 4）。

**承载结论**：审查策略的**判点**在核心循环执行管线（`exec_verdict.rs` 的 `call_verdict` → `permission.rs`），但**策略配置表**（工具类别 → allow/deny/ask）是硬表，无插件可扩展注册面。延伸：`permissions.ts` `PermissionRule`/`RuntimePermissionPolicy` 接口族**其实正中此缝缺口**——它们定义了「按 request 判定决策」的可插拔形状，但**零消费**，恰恰说明「审查策略注册面」缺失。

**差距**：

- 缺持久化的「工具类别 → 策略」注册表（00-总方案 §3.1 D3 收敛目标；05 审计 C 指出 ToolCategory 生产硬编码 Internal）；
- `permissions.ts` 的 `PermissionRule` / `RuntimePermissionPolicy` 是**现成的可插拔接口形状，但挂在死层**——要么收编为真实注册面类型真源，要么删除（§⑤）。

### D · 撤回策略（按工具类别回滚）

**现有相关缝**：**无统一撤回/截断缝**。仅有回滚构件散点：`agent-tools/src/revert.rs`（RevertPolicy）、`revert_guard.rs`、`conex-fs/src/trash.rs:145`（trash_file）、`agent-tools/tools/delete.rs:30`（trash_service）。`00-总方案 §2.4` 明确撤回是**待建**设计（审计 10 验证），非现状。

**承载结论**：撤回策略（扩展点 D）**当前无任何缝承载**。其设计（00-总方案 §2.4 步骤 4）与 C3/D3 权限注册表共用「工具类别」轴，且撤回本身是「插件可承载的操作」——这意味着扩展点 D **需要一个全新贡献缝**：`timeline-truncate` 事件（步骤 3）+ 按类别的副作用回滚策略注册（步骤 4）。

**差距**：完全缺注册面/接口/事件。新增 `TimelineTruncate` 事件（出站）与「回滚策略贡献」注册面（入站）。

## ④ 核心扩展 API 最小形态建议（含禁止反向依赖规则）

### 4.1 核心循环应暴露什么（出：事件；入：钩子/注册表）

**核心循环（`AgentSessionLoop`）最小外部面（现状已具备的核心 shape，收敛目标）**：

- **出（事件）**：`AgentEvent` 流（`conex-types/events.rs`：message-start/delta/end、tool-batch、steering-evaluated、hook-outcome、runtime-steering）——这是核心循环向外广播的**唯一**事实源；`DeltaSink`/`LiveEventSink`（`loop_runner.rs:227,232`）是它的实时投影出口。
- **入（钩子/注册表，均经 `SessionLoopOptions` + `with_*` 注入）**：
  - `ToolRegistry`（`registry.rs:23`）——工具注册/列表/定义改写链；经 `register_runtime`,`add_definition_transformer` 后置扩展；
  - `ToolMiddleware` 链（`middleware.rs:95`）——执行前/后/失败/定义四钩子；
  - `HookRegistry`（`hooks.rs:410`）——14 生命周期事件广播（observe/on，`shared-types/hooks.ts` 冻结契约 `hooks.ts:40`）；
  - `SteeringStrategy`（`steering/mod.rs:157`）——纠偏评估；
  - `ApprovalGate`（`tool_events.rs:148`）——审批裁决；
  - `TurnEndHook`/`RecoveryHook`（`loop/mod.rs:117,146`）——turn.end / 错误恢复同步裁决；
  - `AgentInputQueue` 三环（`input.rs:163`）——提交时机入站。

### 简洁性评估：hooks.rs 等缝是「核心缠结」还是「干净抽象」？

**评估结论（源码形状）**：

- **HookRegistry（`hooks.rs:1728` 行）——倾向「干净抽象偏膨胀」**：它本身是合理的事件总线抽象（14 事件、observe/on、fail strategy、hook-outcome 观测镜像），**但 1,728 行中大量为测试**（`hooks.rs:329` 起几乎全部为测试；生产部分核心是 dispatch 分发 ~`hooks.rs:582-747`）。它不缠结核心（核心经 `loop_options.hooks` option + `with_hooks` 注入，默认 None 不装配），是**干净但过重**的缝——测试/文档占比高，值得拆分（hooks.rs 主体 + hooks_test 独立文件）而非功能改动。
- **ToolMiddleware（`middleware.rs`）——干净抽象**：4 钩子 + 超时配置，接口克制、无核心缠结。唯一问题在实例默认装配（R3）。
- **SteeringStrategy——干净抽象但装配点缠结**：trait 干净，但 `RecoverySteeringStrategy::default()` 被硬编码进核心 `new()`（`loop_runner.rs:63`），是**装配面缠结**（R5）。
- **approval/exec_verdict——判点是核心正道**：`ApprovalGate` trait 解耦正确，但 `permissions.ts` 的同族接口是死层，形成「概念在 Rust 有正解、在 TS 挂死层」的双轨。

**「哪些 hook 保留、哪些移出核心」**：

- **保留在核心**：session/turn/tool.pre/tool.post/tool.error（`HookEventKind` 中与核心生命周期强相关的 6 个）、model.beforeRequest/afterResponse（E1 只挂钩不补源，`hooks.rs` 注释）、subagent.*（M7 发射面）；
- **保留但归引擎侧**（非核心循环直接广播）：context.compact.*、error.occurred（由压缩子系统/编排层补源，`hooks.rs:93,91` 明确「只挂钩不补源」）；
- **移出核心**：无——`HookRegistry` 本身不内嵌具体 hook 实现，故核心循环**不应移出**任何 hook；需要移出的是**实例中间件与具体策略**（R3/R5），而非 hook 类型。HookRegistry 作为事件广播面应保留，但**瘦身**（拆测试、文档收拢）。
