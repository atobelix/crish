**崩溃→白屏路径分析**：

- 渲染阶段异常（render/生命周期抛错）被边界捕获，不白屏 ✅。
- **未被覆盖的例外**：(a) 顶层 boundary 自身模块加载失败降级分支（main.tsx:84-90）兜底为裸 `<App/>`，App 内再次抛错则白屏；(b) **事件回调 / `addEventListener` / `setTimeout` 中被抛出的异常不触发 error boundary**（React 语义）——由 `window.onerror` + `unhandledrejection`（`TelemetryMonitor.ts:30-36`）作全局兜底捕获，但**只记日志不呈现**（改用户可见提示仍需 errorStore UI 消费）✅/⚠️。
- **全局 uncaught 错误呈现面缺失**：全局 error/rejection 只进 `telemetryMonitor` JSONL（写 `logs/telemetry_runtime.jsonl`），无「全屏友好错误页」；若顶层边界之外的模块级异常（如 store 初始化）抛出但不在 React 渲染树内，用户可能看到半错乱而非友好提示。

**结论**：错误边界覆盖充分（13 处 + 顶层），核心 UI 层（侧栏/工作区/输入区/消息列表/单消息）均具边界。白屏风险主要来自「事件回调异常不触发边界」与「顶层 boundary 自身加载失败」两个边角。

## ④ 扩展缺失容错评估

### 4.1 插件注册/激活失败

- `PluginRegistry.activate`（plugins/PluginRegistry.ts:64-112）：`activate` 抛错 → `status='error'`、`reg.error` 记录、**强制 dispose 已绑定资源**（:96-102）、打日志再 throw——**不破坏宿主 UI** ✅。
- `plugins/index.ts:44` 模块顶层 `registerOfficialPlugins()`（自举注册）——但 `register` 仅写入 Map（需 manifest.id，否则 throw），**register 不 throw 于普通插件**；且**注册≠自动激活**，四大官方插件均需经 usePluginStore/设置页手动激活，激活失败被上述 catch 捕获。
- 风险点：`registerOfficialPlugins` 在模块加载顶层执行，若任一官方插件 `manifest.id` 缺失会 `throw` 导致**该 plugins 模块 import 失败**；但 chat 核心路径不 import `plugins` index（需核实），故不影响核心 UI。**plugin-markdown-editor 为目录 index.ts（非 `plugin-markdown-editor.ts`），`plugins/index.ts:22` re-export 目录正确。**

### 4.2 设置-扩展页加载失败

- `SettingsExtensionsTab.tsx`：lazy 子页（Skills/Mcp）包 `Suspense`(fallback「加载…」) + `AppErrorBoundary`（:87-101）；`loadError` 时渲染 `ext-empty` 提示（:176-180）——**隔离于核心 UI** ✅。

### 4.3 markdown 渲染器/编辑器缺失对 chat 的影响（关键发现）

- **chat 编辑器不依赖任何插件**：`ChatComposer` → `TiptapComposerField` → `TiptapEditorField`（独立 `@tiptap/react` + StarterKit）；`plugin-markdown-editor` 仅注册不激活，其唯一监听器 `crish:markdown-editor:open` 面向**文档标签页**，与 chat composer/chat-message-row **零 import**。→ **编辑器插件缺失对 chat 零影响**。
- **markdown 渲染失败 → 已完成消息体为空**（潜在完整性问题）：
  - `AsyncMarkdownBlock.tsx:68-78` 流式分支：纯文本 + caret，零 IPC ✅（仅流式期间）；
  - 完成态 `AsyncMarkdownBlock.tsx:80-91`：`useAsyncMarkdownHtml` 失败返回 `{html:'',loading:false}` → `el.innerHTML=''`（:62）→ **空消息体**。测试断言此为空容器（`AsyncMarkdownBlock.test.tsx:86`「完成态无 rustHtml → 空容器（不泄漏源码）」）——**有意不把源码泄入 DOM**；
  - Rust `core_md_render` missing → `parseMarkdownToHtmlAsync` 回退 worker pool；worker 也失败 → `.catch` 置 loading=false、html 保持 `''`。失败不入缓存，滚动重挂载自动重试（后端恢复自愈）。
  - **结论：markdown 渲染失败时聊天整体可用、不白屏，但失败的那条已完成消息正文不可读（空白）**——是非崩溃但「内容完整性」受损的降级点，建议权衡「不泄漏源码」约束，增加「渲染失败」占位或纯文本次优回退。

### 4.4 汇总

扩展缺失/失败均**不导致核心 UI 白屏**；编辑器与 chat 解耦彻底。唯一内容级缺口是 markdown 渲染失败的空白消息体（见 ⑥-差距 1）。

## ⑤ IPC/引擎故障容错评估

### 5.1 IPC invoke 三态（命令不存在 / 报错）

- `tauriInvoke.ts`：`invokeResult`（ok/missing/error 三态宽松）+ `invokeTyped`（ok/missing/带 kind/message/raw 结构化）。`invokeCmd` 为宽松 `T|null`（`@deprecated`）。
- `TauriTransport`（transport/tauriTransport.ts）：
  - `call`（:158-167）：`resolveTauriCommand` 清单未注册 → `{status:'missing'}`（**显式 missing，不 invoke**）；`error` 视为暂态重试一次；
  - `request`（:181-194）：命令不在 manifest registered → `throw "Tauri command not available"`；超时抛 `Tauri request timeout`；
  - `initCommandManifest`（:142-144）：启动拉取 `core_list_commands`，失败回退内置快照，不一致仅 logger.warn（幽灵回归门禁，不崩）。
- **命令不存在判别**：`isMissingCommandMessage`（tauriInvoke.ts:55-59）正则识别 missing；前端 `TelemetryMonitor.flush` 对 `missing` 显式 `logInternalError`（TelemetryMonitor.ts:123-129）——**不再静默**。
- 缺漏：`invokeCmd`（deprecated）把 missing/error 都吞为 null，旧调用方可能静默降级（review.md §6 Fail-Open 分叉风险候选）。

### 5.2 引擎崩溃 / 恢复

- **进程模型**：引擎 core crates 与 Tauri 壳/WebView **完全同进程**（进程内核心 IPC，`main.rs:5`）。无独立引擎守护进程 → 无「引擎进程重启」层。需要区分三种"崩溃"：run 循环内业务 panic（杀 run 任务、进程活、IPC 活）、任意线程 panic（panic hook 落盘 crash-*.log）、进程整体挂/被杀（**无看门狗拉起、无自动重启**）。
- **run 崩溃隔离**：每个 run 经 `run_launch.rs:767-776` `tauri::async_runtime::spawn(drive_run_loop(...))` 启动，句柄入 `ActiveRun::driver`（`run_core.rs:68-72,90-100`）、**被 detach**（drop 即 detach）；tokio 任务 panic → 由 runtime 捕获成 JoinError，**进程不死、IPC 仍活**。`drive_run_loop` 内部**无 catch_unwind**，全程 `Ok/Err` 返回式错误处理（`run_idle.rs:1237-1355`），produce 内 panic 冒泡到 tokio 任务边界被兜住。
- **panic hook**：`main.rs:638-639` 安装 `conex_telemetry::install_panic_hook_with_crash_dir(Some(<app_dir>/logs))` → 任何线程 panic 落盘 `logs/crash-YYYYMMDD-HHMMSS-<thread>.log`（`crates/conex-telemetry/panic_hook.rs:48-116`）。**记录型 hook**：记录 + 崩溃文件 + **转发前 hook**（panic_hook.rs:88），**不做 catch_unwind 救回**、不重启、不 kill。其余异步任务（timers/cron/watchdog tick）多用 `catch_unwind` + JoinHandle 自兜底「记日志不炸引擎」（`timers.rs:699-741`、`sched.rs:703-884`）。
- **命令层**：Tauri 自带「单次命令 panic → 仅该请求返回错误、进程存活」隔离（框架行为，无自定义 catch_all）；锁访问用「锁中毒恢复」`unwrap_or_else(|e| e.into_inner())`（B1-5 约定，engine_build.rs:435-445）减少锁内 panic 面。
- **watchdog 名不副实**：`src-tauri/src/watchdog.rs` 是「Agent 任务空闲兜底唤醒器」——子代理等待超 N 分钟无事件唤醒 → 注入 steering 条目让 AI 自查（REQ-C05），**不是进程存活监控、不做引擎重启**。`wake_watcher.rs` 同理为 run 唤醒跟踪。**引擎崩溃→UI 感知路径缺失**。
- **engineReady 是「假就绪」**：`core_get_status`（`core_query_commands.rs:290-340`）→ `engine_ready()` → `engine_build.rs:427-429` `EngineHandle.ready`，仅指 **provider 配置三件套（baseUrl/model/apiKey）齐备**，**非运行时健康探针**；崩溃后设进程存活 `engineReady` 仍 true（**误报**）；grep 无 `engine-crashed`/`engine-status-changed` 事件，引擎失败只经普通 run 事件（`run-failed`/`runtime-error`/`run-terminal`）+ `lastError` 传达，且这些仅当 run 以 Err 主动收口才产生。
- **子系统的优雅降级**：DB 打开失败 → 内存库 + `db_ready=false`（main.rs:606-622，`core_get_status` 如实反映，不阻塞启动）；笔记库失败 → `note.unwired`；多端服务 bind 失败 → 仅关多端能力；`restart_server`（main.rs:1214）是多端本地服务重建非引擎重启。→ **非白屏** ✅。
- **盲区（孤儿 run）**：run 任务 panic 时 `finalize_failed` 不执行 → 不产生终态事件、不写 lastError、不从 activeRuns 移除、审计 worker 不排空 → run 变「卡死/孤儿」条目，前端从 `core_get_status.activeRuns` 仍看到它占用但无线索。建议源码面补「JoinError → 收割标记 run 失败」兜底。

### 5.3 可观测性（§10）

- 结构化日志：`logger`（LoggerService）+ `conex_telemetry`（文件层 + stderr 双通道，main.rs:631-637）；panic 结构化 `tracing::error!(target:"panic")`（panic_hook.rs:68-74）+ crash 文件独立落盘。
- 错误集中面：`errorStore`（ErrorStore.ts）code 去重 + classifyError + telemetry 上报；UI 组件可订阅 activeErrors。
- 全局未捕获：`TelemetryMonitor` `window.error` + `unhandledrejection` → telemetry JSONL（TelemetryMonitor.ts:30-36,85-98）；flush 失败回写入 buffer 防丢。
- 健康探针缺口：`core_get_status` 本轮询判定 engineReady/dbReady，但**无真探活心跳**、无 crash→UI 呈现链（crash.log 是死文件，`logDir` 只暴露路径）。

### 正面结论

- 错误边界覆盖充分（13 处 + 顶层），核心会话四态（加载/空/降级/断流）均有显式呈现面。
- **核心 UI 完整性不依赖任何扩展** ✅：chat 编辑器与插件解耦、消息渲染失败不白屏、空态引擎离线反映草稿、`index.html` 首屏零依赖。
- 引擎 run 崩溃由 tokio detached 任务隔离（IPC 不死）；子系统（DB 等）优雅降级不白屏。
- IPC 三态 + 命令清单 + 暂态重试 + missing 显式落协查，命令不存在不再静默。
- message-end 终态兜底（核心不变量 6）在前端已就绪（实时流 + reload/hydrate 双路径），增量丢失可恢复。

### 优先级建议

1. **P0（完整性兜底）**：差距 2/3/4 —— 引擎崩溃可感知 + 孤儿 run 收割（直接影响「引擎离线/流式中断」下的核心完整性，且是源码可判的收口点）。
2. **P1（内容完整性）**：差距 1 —— markdown 渲染失败空白消息体的次优回退（需产品裁决泄漏约束）。
3. **P2（可观测性/边角）**：差距 5/6/7/8 —— 全局错误呈现、顶层边界降级、`invokeCmd` 迁移、无日期 fallback 清点。
