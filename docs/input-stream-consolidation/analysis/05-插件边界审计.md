## ⑤ Rust 侧插件运行时评估 + 对 00-总方案 §3 映射表的核实与修正

**任务书问：Rust 侧插件运行时是否值得评估？现在有没有等价物？**

**结论（源码形状）：Rust 侧已有「引擎侧插件运行时」的现成骨架，但分三块、未聚合成「插件运行时」入口：**

| Rust 能力                                                                                         | 位置                                      | 是否为插件运行时组成                                                   |
| ------------------------------------------------------------------------------------------------- | ----------------------------------------- | ---------------------------------------------------------------------- |
| `ToolRegistry` + `register_runtime`（&self 后置注册）+ `Tool` trait + E4 定义改写链               | `registry.rs:49,119`、`definition.rs:141` | ✅ 工具注册/扩展面（插件工具并入的核心）                               |
| `mcp::register_plugin_server`（插件 mcpServers 接入）+ `McpRegistryShell`（同 registry 内外暴露） | `mcp/mod.rs:60`、`mcp/shell.rs:49`        | ✅ MCP = 现成的引擎侧插件工具通道（外部 server 工具并入统一 registry） |
| `note_w4c_contribute::ContributeViewRegistry`                                                     | `note_w4c_contribute/execute.rs:33`       | ❌ 死码，不构成（见 P5）                                               |
| 权限矩阵（`note_action_matrix.rs` NOTE_ACTION_MATRIX、`note_permission.rs`）                      | 上述文件                                  | ✅ 审查策略表的现成形态（扩展 C 可扩展的雏形，见③C）                   |

**即：Rust 侧插件运行时的「等价物」已存在且部分接线**（`register_plugin_server` 有 conex-browser-tools / conex-computer-tools 真实消费：`conex-browser-tools/src/tools/mod.rs:105` 调 `register_runtime`；`crates/agent-tools/tests/mcp_bridge.rs:257` 验证 E5）。缺的是**统一暴露为「插件运行时」门面**，以及**把扩展点 A/B/C（注入/提交/审查策略）显式建模为插件贡献面**——目前 A/B 在 Rust+TS 均无插件轨道（见③A/③B），C 有硬表但无可扩展注册面。

**对 00-总方案 §3「插件」行（:63）的核实与修正：**

> 原文：「插件：plugin-sdk（contribute points：SlashItem/BlockView/Widget/Keymap + registerFlavour + 权限面）+ crish-desktop/src/plugins/（PluginRegistry + 官方四插件…）—— canonical：统一插件运行时，承载扩展点 A/B/C——扩边界」

**核实：**

1. ✅ **plugin-sdk contribute points 真实存在**且形状与映射一致（4 kind + registerFlavour + 权限面，见 §②）。
2. ❌ **「统一插件运行时」目前不存在**：plugin-sdk 运行时装在**引擎侧**（Rust 消费方是 agent-core/agent-tools，且 `CRISH_ALLOW_UNSAFE_PLUGIN_IMPORT` 默认关闭 `plugin-loader.ts:253`，即**默认不执行任何第三方插件代码**）；前端 crish-desktop 用的 `CrishPlugin` 微内核与 plugin-sdk **完全不接线**；settings adapter 又是第三条。三套并存 ≠ 统一运行时。
3. ❌ **「承载扩展点 A/B/C」是未来态**：当前代码 A（注入时机）在 steering nudge / PendingNudgeChannel（会话层，非插件）；B（提交时机）在 chat-bridge queueing（非插件）；C（审查策略）在 Rust 硬矩阵（非插件可扩展）。**plugin-sdk 现无任何 contribute kind / 接口表达 A/B/C**（见③表）。
