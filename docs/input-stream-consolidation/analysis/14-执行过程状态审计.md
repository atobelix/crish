## ③ 缺口的详细说明（现状「过程状态」哪些没事件化）

### ③.1 run「进行中」没有独立的事件节点（只有终态事件化的两端）

- run 的「进行中」状态**不产生出站事件**。今天 run 状态可观测的落点是：
  1. **终态** `run-terminal`（`:612-620`）——必达落库，这是唯一进入事件流的「run 状态变化」；
  2. **引擎内内存态**：`RunHandle.status`（`run.rs:269-293`）+ `RunStateMachine.state`（`run.rs:113-115`）；
  3. **壳层轮询快照**：`list_active_runs_impl` → `ActiveRunSummary`（`run_approval.rs:423-434,459-486`）经 `core_get_status`（`core_query_commands.rs:337`）→ 前端 `useEngineState` 轮询（约 4s，`useEngineState.ts:104-110`）。
- **缺口**：没有 `run-state-changed(running/awaiting-approval/completing/cancelling)` 这类「进行中」事件。前端看到 run 已启动只能靠 agent-start + turn-start/tool-start 等**下游证据**推断「在跑」，无法区分「正在推理」「正在等审批」「正在收口」。这使得「进行中过程状态」在前端是**派生/推断**态，而非事件化的可追溯态。
- **落库语义不对称**：`runs.status` 列是逐态 `update_run_status` 落库的（`persist.rs:424-441`），但**未作为事件**进入 events 表——状态历史只能从 runs 表 `updated_at` 猜，无法从事件流重放还原「was-running」过渡。这与统一模型「事件流是唯一事实源、runs 表是投影」存在张力（见 §④）。

### ③.2 工具「进行中」= 事件化但**批收口广播**，非实时轨；进度增量 NoPersist 且当前未真正发射

- **批收口语义**：`tool_events.rs:16-29` 头注明确——工具事件是 `execute_batch` 全部返回后**一次性翻译广播**，非逐事件实时推送；`R-16` 裁决「不建实时工具轨」。
  - 后果：**tool-start/tool-end 在引擎侧是批量生产的**，前端收到一批 tool-start 时工具可能早已执行完毕。中间态（`tool-start 已发 / tool-end 未发`）主要靠**时间戳 sorting** 与前端 `EventRouter` 因果缓冲（`EventRouter.ts:175-225`）去凑。
- **ToolProgress / AgentEvent::ToolUpdate**：存在变体（`tool_events.rs:110-113` → `executing_tools.rs:360-371`），但：
  - **当前没有执行器真正发射** `ToolProgress`（grep 全仓只在 `executing_tools.rs` 翻译层消费 `ToolEvent::ToolProgress`；生产 `exec_single`/`exec_batch` 均未 push 该事件项）。即 **tool-update 是空转的死契约**（想用没有源）。
  - 且 `event_policy`（`events.rs:1313-1414`）**未给 `ToolUpdate` 显式分支**——落入末尾默认族 `Persist + Critical`（`:1408-1412`），与本应「Delta+NoPersist 展示面事件」（`executing_tools.rs:361-363` 注释）不符。`tasks/output` 有显式 NoPersist 分支，`tool-update` 没有——**契约缺口**。
- **审批挂起**：这部分是事件化的最完整子域——`approval-requested` 先发（防死锁，`tool_events.rs:5-8`）、`approval-resolved` 超时 Expired 由引擎权威落库（G-9）、approve/deny 壳层路径落事件。挂起期间 run CPU 态 = awaiting-approval，前端 `pending_approvals` 轮询补充实时对账（`useEngineState`）。**审批挂起 = 唯一有专用「进行中事件」的过程。**
- **批进度（exec 批处理的进度展示）**：`ToolBatchStart`/`ToolBatchEnd` 只带**摘要级** calls/results（`executing_tools.rs:206-262,414-422`），无「批内当前完成 N/总数」的实时进度字段。批级「进行到第几个」不可观测（只能停在前端 tool-end 计数）。

### ③.3 命令运行：用户终端（pty）完全不在事件流；AI shell/bg 任务事件化但进度部分 NoPersist

- **关键区分**：`pty/session.rs` 的 `portable_pty` 是**桌面工作台用户终端**：创建 shell（`build_shell_command` 拉 pwsh/powershell/bash，`:249-336`），输出经 `app_reader.emit("workbench://pty-output", ...)`（`:472-558`）走 **Tauri `workbench://` 侧信道**。**它不进 AgentEvent 流、不落库**，是用户手动终端，与 AI 执行无关。
  - 三态 `PtyLivenessState`（Active/Detached/Dead）是**引擎内部态**，靠 GC 定时巡检（`is_gc_eligible` `:146-163`）驱动，前端通过订阅 `workbench://` 事件 + `useRuntimePanelData` 合并展示（`workspace/useRuntimePanelData.ts`）。**终态 pty-exit 仅侧信道广播，不落库、不入时间线。**
- **AI 命令（shell_command/shell_redirect）→ 后台任务域**：这是真正与 AI 执行相关的命令过程，且**事件化最完整**：
  - 终态 4（task-started/completed/failed/killed）= **Critical + Persist**（`events.rs:1350-1358`）——落库；
  - 增量（task-output / task-heartbeat）= Delta + **NoPersist**（事实源 = 任务日志文件 / `.samples.jsonl`，`events.rs:1295-1299,1340-1358`）；
  - task-suspicious = Soft + NoPersist（`events.rs:1345-1349`）。
  - **缺口（可持续性描述）**：`shell_command` 实时输出**只走 task-output 事件**（NoPersist 增量，可丢）；而**终态快照/尾部日志的事实源是 `<task_id>.log` 文件**（`background.rs:73-75,137-142`，`bg_log.rs`）。这意味着「后台任务的进行中日志流」**不是单一事实源**：实时行在 `TaskOutput` 事件、持久历史在日志文件、终态事件在 events 表——三处要前端 `bgTasks` 轮询（`useEngineState.ts:42`）+ `read_log` + task-output 实时三路拼接。**需真跑确认**尾部实时性（轮询 vs 事件驱动）。

### ③.4 写文件过程：确认无任何进度/状态事件（全引擎内部态/函数态）

- **write_paths 声明记账**（`write_paths_state.rs`）纯内存互斥：claim 在同一锁区间检测+插入（防 TOCTOU `:196-223`）、RAII 守卫 Drop 释放、TTL 60s 过期清扫。**无落库、无事件、前端不可见**——冲突只以 `tool.write_path_conflict` 错误回 AI（`WritePathConflict::into_tool_error` `:94-97`）。
- **atomic_write**（`conex-fs/atomic_write.rs`）：`AtomicWriteTx` 内部五态（`:22-45,97-100`）是**纯同步函数状态机**（事务达成，非异步进度），不产出任何事件；`write_temp`/`backup_existing`/`commit` 同步串行（`:103-161`），调用方拿到的只有完成后的 `Ok(())`。
- **write_file 工具**（`fs.rs:302-366`）：经 `check_write_allowance_for_ctx` → `claim_write_guard` → 配额 → `std::fs::write` 一次性同步写完（`:345-346`，**未走 atomic_write**），结果经 tool-end 事件 + tool 角色消息。**无写入进度/逐字节/逐块状态事件**。
- **确认结论（与任务预测一致）**：**写文件过程没有任何进度/状态事件**——它是「持续性状态但不流式展示」的典型。原因：写文件是**单次原子落盘**（无多步异步进展），且声明记账（claim）是**并发控制**而非「进行中展示」语义。统一模型若要表达「该文件正在被写」，只能依赖**前置的 tool-start 事件（已事件化）+ 写前快照/声明（内部态）**，无法区分「已 claim 正在写」vs「已写完」。

## ④ 对核心模型「节点状态维度」的验证与建议

### ④.1 验证：统一模型「进行中状态节点」目前是**没有事件化的层级**

模型 §1 不变量（一切皆文本节点）与 §3 前端原则（单一数据流）都假设事件流能承载过程状态。但现状证明：

1. **run「进行中」是引擎内部态（`RunHandle.status`）+ 壳层轮询快照（activeRuns），非事件**——违反不变量 2「engine 只写 events 表」的**扩展**：runs.status 虽是 events 旁路落库，但其过渡历史（running→awaiting→completing）不落在事件流，无法从事件流重放。
2. **工具「进行中」是批收口广播 + 时间戳模拟**（`tool_events.rs:16-29`），`ToolUpdate` 进度变体**无执行器发射**。
3. **写文件「进行中」完全不存在**（无事件、claim 是并发控制非展示态）。

### ④.2 建议：落点 = 「状态事件（进行中）+ 状态字段（终态/挂起）」混合，且优先级按「是否可派生」收敛

按统一模型「优先事件 + 注册表，避免 trait/字段」（00 §7 纪律 4）与「前端只派生」（§3.1），给出落点建议：

| 过程状态                   | 现状                                            | 建议落点                                                                                                                                                                                                                                                                                                                                       | 理由                                                                                                                                                                                                 |
| -------------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| run 进行中状态变化         | 引擎内部态 + 轮询                               | **新增 `run-state-changed` 非终态事件（Delta 可丢级，不落库可参照 task-output）**，或复用现有 `agent-start`+`runtime-*` 推断                                                                                                                                                                                                                   | 「正在推理/等审批/收口」是用户可见且需可追溯的进行中态；纯前端派生依赖多事件猜测，脆弱。若成本顾虑，最小方案 = 前端从现有事件（turn-start/tool-start/approval-requested）派生，不给 run-state 加字段 |
| run 终态                   | run-terminal（已事件化）                        | 保持                                                                                                                                                                                                                                                                                                                                           | 已是权威终态事件                                                                                                                                                                                     |
| 工具批/单工具              | tool-start/end（已事件化）                      | 保持；**批内进度建议给 `ToolBatchStart.calls` 加可选的当前完成计数或 emit 批级 `tool-update` 汇总**                                                                                                                                                                                                                                            | 批级「N/total」可派生（数 tool-end），也可最小化不加字段                                                                                                                                             |
| 工具进度增量               | ToolUpdate 死契约（未发射）                     | **要么接线发射（给工具定义 `progress_callback`），要么删除该变体**（反退避 + 抽象纪律 5：零消费者=删候选）。若保留，`event_policy` 必须给 ToolUpdate 加显式 `Delta+NoPersist` 分支（当前落入默认 Persist，契约错误）                                                                                                                           | 现状契约与实现不符，违反「类型契约单一权威」（00 §7 纪律 1）                                                                                                                                         |

| 用户终端 pty               | workbench:// 侧信道（非事件流）                 | **明确声明为「非时间线外部域」**——它不属于 AI 会话时间线，建议不强行并入事件流（符合「核心不反向依赖具体功能」）。若需跨端可见再评估                                                                                                                                                                                                           | pty 是用户手动终端，非 AI 执行，强行事件化属过度设计                                                                                                                                                 |

| **写文件声明/原子写/写入** | 无事件                                          | **建议**：不新增「写入进度事件」；写文件过程的「进行中」由**tool-start 事件 + 声明 claim**承担，进度/结果以 **tool-end + tool 角色消息**收口。满足用户「代码写入是持续性状态但不流式展示，只展示状态/进度」——即展示层在 tool-start/end 卡片上显示「写文件…完成」即可，**不引入逐块进度事件**（避免过度设计；写文件是单次原子落盘，无流式实质） | 用户明确定义「写文件只展示状态/进度」= 已有 tool-start/end 足够；核验确认无现成缺口需补事件                                                                                                          |

### ④.3 反退避备注（不为「有状态」而强行事件化）

统一模型若引入「进行中状态节点」维度，**不应**为「有状态」这一个抽象而新增一类 node。已事件化的过程（审批挂起/工具批/bg 任务）保持事件化；**真正缺的是 run 级进行中事件（可最小化）与 tool-update 契约的二选一收口**；写文件与 pty 明确判为「非时间线强事件化域」，只在前端派生展示。

### ④.4 需真跑确认清单

- `shell_command` 后台任务日志尾部实时性（轮询 read_log vs task-output 事件驱动）；
- `ToolUpdate` 是否确无任何工具发射（静态 grep 零命中，需 e2e 佐证）；
- `approval` 超时 Expired 在真实并发批下是否如代码所示权威落库并让 run 从 awaiting-approval 收敛回 running；
- 恢复后 in-flight run 全部 `interrupted` 是否符合生产预期（`restore.rs:5-12`）。
