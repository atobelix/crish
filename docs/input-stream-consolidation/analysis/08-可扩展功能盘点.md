# 08 · 可扩展功能盘点（统一输入流收敛战役）

> 性质：本维度的唯一输出文档（类型 B · 只读审计）。
> 目标：为「所有内容皆为带类型标记的输入文本 + 唯一时间线」战役提供**可扩展功能全景**——逐项判定哪些能力已经天然可插拔、哪些硬编码在核心路径、各自应挂到哪个扩展点。
> 扩展点口径（对齐 `docs/input-stream-consolidation/00-总方案框架.md` §2.3/§2.4）：
>
> - **A 注入时机**：状态切换 → 即时提交 vs 挂用户下一条命令；
> - **B 提交时机**：即时插队 vs 正常队列（AgentInputQueue.followUp / PendingMessageQueue 现存的「下一条用户消息」落地）；
> - **C 审查策略**：工具调用执行前按工具类别分类判断是否需审查（allow / deny / ask）；
> - **D 撤回策略**：按消息类型/工具类别可插拔撤回/回滚；
> - **新**：战役未定义，需新增。
>
> **审计边界声明**：本文为**源码形状审计**（读代码定位功能与接线点，标注"已接线/只挂钩/死类型/伪数据"等形状证据），**不含真跑验证**；"可运行"类结论均为源码可追踪的接线证据，未经运行态冒烟验证。

---

## ① 方法

- **范围**：`crates/`（24 个 crate，Rust 内核）、`apps/crish-desktop/src/`（Tauri 前端 React）、`packages/`（共享 TS 包）。
- **手段**：
  1. 以战役扩展点 A/B/C/D + 「新」为锚，对每个功能定位 `文件:行号` 实现与接线；
  2. 判断**耦合度**：紧 = 逻辑内联在 session-loop/orchestrator 主循环，无法关闭；松 = 独立 crate/模块但有固定调用；零 = 基本独立、可整体移植；
  3. 判断**现有扩展机制**：插件（PluginRegistry/ContributePointRegistry/ToolRegistry/HookRegistry）/ 接口（trait 注入）/ 配置（session_meta/字段）/ 无；
  4. 给出**建议扩展点**与**动作**（保留 / 外置 / 删除）。
- **证据分级**：本文引用 `文件:行号` 均为读码定位；标注"自然可插拔"的特质有 trait/注册表/接口可依；`shared-types/permissions.ts` 等多处与前序审计（01–06）结论交叉验证。
- **排除**：本地 dev/mock/测试辅助文件不计入功能盘点；跨端移动端（apps/crish-mobile）不在本次范围。

## ③ 按扩展点分组的归纳

### 扩展点 A（注入时机）

- **现有承载**：静态注入 `ContextInjector`（M1 注入点）+ steering nudge 走 `PendingNudgeChannel`（已排入下一条用户消息）+ HookRegistry `tool.pre/turn.start/session.start`（on 模式可携带控制信号，可注入）。
- **欠缺**：**动态状态注入无通道**——模型名/权限/思考模式（reasoning_effort 有字段无极源）完全散在前端 settings，不落时间线（扩展 02）。
- **建议**：A 已是"注入节点产生器"落地面；新增 `context-state` 节点并挂 A；动态状态切换复用 PendingMessageQueue（现状仅 kind:"steering"）。
- **插承载能力交叉验证（packages/plugin-sdk）**：**部分可承载**——`tool.pre`/`turn.start`/`session.start` hooks + on 控制信号 `modifiedInput`（shared-types/hooks.ts）结构已在，但**无宿主把插件改写接到 IO 管线**（脚本插件 A 轨与主循环接线缺口）。

### 扩展点 B（提交时机）

- **现有承载**：`AgentInputQueue.followUp`（followUp 环仅 idle 注入）∷ `PendingMessageQueue`（下一条用户消息）双轨并存（02 审计确认）。
- **欠缺**：plugin-sdk **无 message.commit / output.pre / text.submit hook**，无法在 TS 侧承载 B。
- **建议**：收敛双轨为单一扩展点 B 队列；B 的承载面在 **Rust 主循环 input.rs / orchestrator steering_queue.rs**，而非插件。
- **插承载能力交叉验证（packages/plugin-sdk）**：**不可承载**——无 message.commit / output.pre / text.submit hook；View 轨刻意禁写句柄（contribute/types.ts 投影-only）。

### 扩展点 C（审查策略）

- **现有承载**：`call_verdict`（tool_events PermissionMode + dangerous + revert_policy C3 门）→ `Arc<dyn ApprovalGate>` → `ApprovalDecision`。HookRegistry `tool.pre on` 可 Block 是**第二个审查通道**（两套并存）。
- **欠缺**：工具类别（`ToolCategory`）**仅作事件载荷**，不参与裁决分派（27→07 断言：生产硬编码 Internal；裁决不按类别分类）。`permissions.ts` 死类型须删。
- **建议**：收敛为**单一「工具类别 → 审查策略」注册表**（D3）；类别轴与撤回策略 D 共用；HookRegistry tool.pre 与 call_verdict 判定点合一，避免双权威。

### 扩展点 D（撤回策略）

## ④ 硬编码在核心路径的功能重点清单

**「硬编码」判据**：逻辑内联在 session-loop/orchestrator 主循环、无法按开关关闭、无注册表/接口分派的。

1. **权限审计分派（部分硬编码）** — `exec_single.rs:67-165` / `exec_verdict.rs:99-125`：`PermissionMode` + `dangerous` + revert_policy 组合在 `call_verdict` 内联判定，**不按 `ToolCategory` 分派**；`ToolCategory` 只进事件载荷（`conex-types/src/tool.rs:14-29`），不参与裁决。这是 D3 收敛的核心对象。

2. **提交时机双队列（硬编码 + 双轨）** — `input.rs` AgentInputQueue（Force/Steer/FollowUp 三环）与 orchestrator `PendingMessageQueue` 两套并存、互不接线。B 扩展点须在此收敛为单一队列。

3. **注入时机：动态状态注入完全缺失** — context-state 节点概念零通道；reasoning_effort 只是 `ProviderRequest` 字段无来源。属战役新增面（非既有硬编码，但现状散在前端）。

4. **工具展示归类（硬编码映射表）** — `tool-presentation/`（toolHumanDescriptions / toolDomainDescriptions / toolCardPresenter / timelineNormalizer）为前端硬编码表，非插件承载；`messageUserProjection`（UserView）是旁路投影候选（04 审计 ~400 行非渲染主路径）。D4 收敛目标。

5. **markdown/IME（包内固化，非插件）** — `editor-kit/src/ime/`（ImeMachine/imeMatrix）+ markdown 引擎在共享包内，编辑器 hook 才走插件；IME 矩阵本身非插件化（有 contract 测试锁定）。

6. **session_messages 写放大（持久化硬编码前端轨）** — 前端 sessionRustDb* / localStorage 双轨全量先删后插写 `session_messages`；`conex-db::append_session_messages` 为未接线死层（01 审计）。D1 收敛对象。

7. **安全点控制接线在核心循环** — `safe_point.rs:79-152` `apply_safe_point_control`（ForceCancel/CooperativeStop/SoftInject）在主循环调用、内联落环（虽逻辑已模块化，但接线点紧绑 session-loop）。
8. **插件承载面断层（可插拔能力缺口）** — plugin-sdk 仅 **A 部分可承载**（tool.pre/turn.start 改写 `modifiedInput`，但无宿主接线）；**B/D 完全不可承载**（无 message.commit/output.pre/undo/retract hook）。即战役指望插件运行时承载 A/B/C/D 的设想，当前 **B/D 无抓手**，必须在 Rust 侧新增钩子/注册表；`ContributePointRegistry`（View 轨）与 `PluginRegistry`(壳)零接线。

## ⑤ 优先级建议（逻辑顺序 · 非时间/优先级排序）

> 只谈**先外置哪些收益最大**的逻辑依赖顺序，不含工作量与时间排期。

1. **先收敛「评审权威」归一到 C 扩展点** — 权限分派现为 `call_verdict` + HookRegistry tool.pre + permissions.ts 死类型三套并存；`ToolCategory` 未被裁决使用。把「工具类别 → 审查策略」做成单一注册表，是 D3 起点，也让 C 真正可按类别扩展。

2. **再收敛「双提交队列」到 B 扩展点** — AgentInputQueue.followUp 与 PendingMessageQueue 双轨合并。此事与 D1（统一时间线）耦合最紧（队列是时间线的输入侧），应在权限注册表收敛之后、与 D1 共用一段。

3. **补「动态状态注入」context-state 节点到 A 扩展点** — 依赖前置的 D2 注入文本化（静态注入统一为注入节点产生器），补齐后 A 才完整。此步收益 = 消除前端 settings 散落状态源。

4. **把「工具展示归类」外置到 D4 插件承载面** — 依赖前面 D1/D3 稳定后（投影层从统一时间线派生再去中间态）。收益 = 解锁折叠/目的描述/图标成为可插拔 contribute，而非硬编码映射表。

5. **最后固化「撤回策略」D 扩展点** — 撤回横跨 D1/D3/D4/D5，须等前三者落地、run 取消路径+截断持久化验证（审计 10）后单独推进。收益 = 回滚/截断成为按类别可插拔操作。

6. **登记「新扩展域」为常设插件接口面** — 工具接入（注册表）、压缩/摘要（Summarizer）、子代理（Spawner）、定时/后台（Timer/Background）、MCP 这些**已天然可插拔**的域，收益 = 只缺"显式登记为扩展点"与文档化，改动最少、立即固化战役边界。
