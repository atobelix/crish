### 2.2 tokens.css（实测 844 行 / 538 处 `--x:` 声明）

- **行数纠正**：任务书「1000+ token」；实测 tokens.css 844 行、538 个顶层 `--x:` 声明。因声明跨多行 + 每 token 含多条 CSS 属性，若按「token 定义+引用合计」可超千，但源码单文件为 844 行。**11 审计口径「1000+ token」需复核口径（声明数 vs 引用数）**，本文以「844 行 / 538 声明」为准。
- **亮暗结构性契约**：`:root, html[data-theme='default'], html[data-theme='light']`（亮底）与 `html[data-theme='dark']`（暗底）两大块。暗色块集中覆盖约 40 个核心 token：
  - 背景族：`--bg-primary/secondary/tertiary/card/elevated/workspace`（tokens.css:518-526）
  - 文本族：`--text-primary/secondary/tertiary`（:527-532）
  - 边框/分隔：`--border-color/subtle`、`--hairline*`（:553-563）
  - 控件/侧栏：`--control-soft-*`、`--sidebar-*`、`--focus-ring-*`（:565-596）
  - 语义色：`--accent-*`、`--color-*`、`--text-on-*`、`--ui-text-*`（:598-641、:696-701）
  - 语法高亮 `--syntax-*`、终端 `--terminal-*`、阴影 `--shadow-*`（:663-719）
  - `color-scheme: dark`（:718）
- **dark 覆盖契约**：dark 不是「仅有亮色的第 2 套」，而是依赖 `tokens.css` 的 `data-theme='dark'` 完整 re-declare 核心面 + `themeStore.applyPersonalization` 运行时注入的皮肤变量（`--accent-green-light-adaptive` 等）。皮肤缺失时 `applyPersonalization` else 分支会 `style.removeProperty` 回退 tokens.css 默认（themeStore.ts:770-790）。
- **额外密度/形态轨道**：`[data-ui-size]`（small/medium/large）、`[data-shell-chrome]`、`html[data-perf-tier]`（:723-888）与主题正交。

### 2.3 明暗切换（dark 覆盖契约）与用户可定制现状

- **切换实现**：`applyTheme` 在 `html` + `body` 同时设 `data-theme` 并 toggle `theme-dark/theme-light` class（themeStore.ts:71-91）；切主题时若当前皮肤不在目标主题预设集内，自动回退到该主题首皮肤（SettingsAppearanceTab.tsx:99-105，含 DARK_SKIN_IDS / LIGHT_SKIN_IDS 双清单）。
- **用户可定制项（已落地）**：
  1. 浅/深二元切换（`crish-theme-changed` 事件广播）；
  2. 13 皮肤预设 + custom 自定义（背景/文本双色）；
  3. 全局亮度 -5..+4、字号 12-18px；
  4. 智能时光温感自动过渡（auto-time-transition，按时刻切亮暗 + 色温）、氛围色彩融合（vibrant）；
  5. 字体（FontSettingsSection：ui/mono 字族、连字、字号）。
- **定制宽度大但核心面窄**：二元 `theme`（default/dark）是「最小产品核心」，皮肤/亮度/时光过渡/自定义色均落在扩展可配置面。

### 2.4 主题体系小结

主题是**全局横切可定制面**：运行时把 40 个核心 token + 皮肤变量注入 `documentElement.style`，因前端 94% 样式 token 化（11 审计），主题改动对**几乎所有组件**渲染生效。这是「定制影响核心渲染」的最强案例——主题不是局部"个性化皮肤"，而是改变全局视觉基座。但**内部仍是投影**：真源 `settingsStore.appSettings.theme` → themeProjection → DOM，符合草案 §3「单一数据流 + 投影派生」，未违反不变量 3。

### 3.2 布局树定制能力（源码形状）

- **树模型**：`LayoutLeaf`（面板，含 tabs/activeTab/**sessionId** 多会话绑屏）与 `LayoutBranch`（严格二叉，direction horizontal|vertical，splitRatio[0.1,0.9]）；`LayoutTree { root, version }`（types.ts:9-44）。参考 VSCode SerializableGrid。
- **结构操作（推历史）**：`splitLeaf` / `mergeBranch` / `moveLeaf` / `resetTree` / `setTree` / `commitDrop` / `setTreeWithDock`；焦点操作不推历史（setActiveLeaf/setActiveTab）；resize 支持 commit=false 拖拽手势 → pushHistory 前置（layoutTreeStore.ts:105-179、:445-449）。
- **拖拽/分屏/标签**：
  - 拖拽集中化：`setDraggedSource → setActiveDropZone → commitDrop → applyDrop`（纯函数），operations.ts:603；dropDetection.ts 计算 drop zone；
  - 分屏：`splitLeaf`/`moveLeaf`（operations.ts:107,153）；
  - 标签：`addTabToLeaf`/`removeTabFromLeaf`/`setLeafActiveTab`（operations.ts:498-553）；
  - resize：`resizeBranch` + `treeResizeClamp` hook 像素级钳制。
- **undo/redo**：`past/future` 历史栈（MAX_HISTORY=50），只存 tree 快照（layoutTreeStore.ts:451-473）。
- **持久化**：window-scoped `crish-layout-tree-v1::windowId`（`layoutTreeStorageKey()`，多窗口隔离，layoutTreeStore.ts:73-84）；`partialize` 仅持久化 tree + activeLeafId + toolColumnCollapsed（:483-487）；迁移 `migration.ts` + `migrateScopedStorageKeyIfNeeded`。
- **冷启动 restore 策略**：`validateRestorableLayoutTree` 多单元树校验 + `crish_restore_last_workspace` opt-in 开关；默认（restore=false）强制 clean 单 chat（layoutTreeStore.ts:497-515、layoutRestorePolicy.ts）。

### 3.3 workspace-shell 与 binary-tree 的分工

- **workspace-shell = TabSurface / dock 写主**：openTabs、activeTabId、per-tab rightDock；走 `openOrFocusSession`/`activateTab`/`closeTab`/`reorderSessionTab`/`updateRightDock`（workspaceShellStore.ts:262-582）。它**不**拥有 tree 几何（split/merge 归 layoutTreeStore），只做 shell↔tree 投影（bindActiveChatLeafSession / applyDockToTree / ensureAdapterShape）。
- **反向投影去回环**：`registerTreeDockSync` 订阅 tree 变更 → `syncShellDocksFromTree`；投影期间置 `isTreeDockProjectionSuppressed` 屏蔽互触发（workspaceShellStore.ts:625-652）。
- **binary-tree = 消费层**：BinaryTreeWorkspace 是 `layout-tree` 树几何的唯一渲染主入口（App.tsx:65,292），内部经 `flattenToRenderList`（FlatPanel/FlatBranch）渲染。

### 3.4 「定制布局」是核心还是扩展？

- **结论（源码倾向）：布局定制属「核心可定制面」，但宽度是扩展的。**
- **核心内核（草案 §3.1「时间线渲染 + 输入闭环」需要的基础）**：单 chat 分屏、标签、基础分割——「设置基础」之外，工作区呈现基本形态需要最少一个面板可容纳会话；`createDefaultTree('chat')` 冷启动即此核心（types.ts:176-181）。
- **扩展面**：多会话绑屏（leaf.sessionId）、多 unit dock、任意深度尺寸恢复、拖拽 reorder、复杂分屏——即 workspace-shell + binary-tree 的完整能力，属于「缺失时核心仍完整可用」的可插拔扩展（草案 §3.1 明列「布局定制」为扩展）。
- **现状定位**：workspace-shell 已经把「标签生命周期」写成必装编排（`.shell` 是 compositionRoot 必装件），布局树的 split/merge 几何则与 shell 深度耦合投影。**从「前端核心=最小完整产品」看，直接开箱即用的默认单面板布局即可构成核心；全部高级布局能力均为扩展可定制面。**

## ⑤ 定制 vs 核心关系分析

### 5.1 三类定制对核心渲染的影响半径

| 定制项                                       | 影响半径                                       | 是否改核心渲染                     | 归类                                   |
| -------------------------------------------- | ---------------------------------------------- | ---------------------------------- | -------------------------------------- |
| 主题二元切换（default/dark）                 | 全局（40 token + color-scheme）                | **是**：改全部组件视觉基座         | 核心可定制面                           |
| 皮肤预设 / 自定义色 / 亮度 / 时光过渡 / 字体 | 全局（注入 root CSS var，覆盖 94% token 组件） | **是**：改全部组件渲染（不同强度） | 扩展可定制面（核心容缺）               |
| UI 密度 / shell-chrome                       | 全局 API 形态                                  | 局部（布局/密度，非语义）          | 扩展                                   |
| 布局树（layout-tree 分屏/标签）              | 工作区 chrome                                  | **局部改编排，不改原子组件内部**   | 核心内核对起 + 高级扩展                |
| provider-profiles 模型                       | 引擎侧生效 + 显式模型                          | 影响「哪会话跑哪模型」，非通用渲染 | 核心（模型选择）+ 扩展（profile 管理） |
| 权限策略 / 命令白名单                        | 审批/执行判点 + 审批 UI                        | 局部（C 审查策略）                 | 核心（审批交互）+ 扩展（策略表）       |
| 快捷键改键                                   | 输入/导航入口                                  | 局部（keymap）                     | 核心（发送键）+ 扩展（导航键）         |

**关键结论**：

- **全局横切定制 = 主题**（唯一改变几乎所有组件渲染的定制）。它必须走 token 投影、单一写端、可回退默认——现状已满足（themeProjection + removeProperty 兜底）。
- **布局定制不改变原子组件渲染**：一颗 `chat` leaf 无论摆在左上还是右分屏，其内部渲染一致；布局改的是「是什么面板、多大、在哪个窗口」，属编排层。因此布局是「核心内核对起（默认单面板保证完整产品）」+「高级能力扩展」。
- provider/profiles、permissions、shortcuts 的**通用面属核心**（模型选择、审批交互、发送键永需存在），**策略/管理宽度属扩展**——与草案 §3.1 判定准则（「扩展 = 有独立策略/可配置/缺失不影响时间线闭环」）一致。

### 5.2 定制状态 vs 投影 store 的关系（是否进时间线？）

- **现状：全部定制状态都**不**进入会话消息时间线**。**时间线（events 表）只装会话正文/事件节点**；主题（themeStore LS + settingsStore.appSettings）、布局（layoutTreeStore window-scoped LS）、权限（commandPermissions LS + permissionModes）、快捷键（configService + engine settings）、provider（LS + DPAPI）全部是**用户偏好 / 配置态**，独立于事件流。
- **这些定制状态经由投影 store 派生到渲染**：
  - 主题：`settingsStore.appSettings.theme → themeProjection → DOM`（§2.1）；
  - 布局：`layoutTreeStore.tree → BinaryTreeWorkspace flatten → 渲染` + `registerTreeDockSync` 反投影 shell（§3.3）；
  - 配置：`clientApi.saveSettingsEx → 引擎 → 事件回灌 settingsStore → 投影`（§4.2）。
- **定性结论**：定制状态是「配置/偏好投影」，**与不变量 3（投影派生）同构但不等价于会话投影**——它不是从 `events` 表派生，而是从「引擎设置/本地偏好」派生。因此它**不进消息时间线**是正确边界：用户改主题不应产生 `message` 节点、不应进会话 seq。
- **深化**：引擎侧若把 `config_*` 写成「配置事件」（区别于会话消息事件），可让配置修改可回放/可重放；但当前模型草案把「唯一时间线」限制为「会话消息/事件流」，配置面是**独立配置域**。建议在草案 §6 决策点明示：**配置事件不进会话时间线，属独立配置事件带（若需要历史/撤销）或本地偏好（现状）**。避免在收口时把主题/布局塞进消息事件流而污染消息模型。

### 5.3 现状风险/观察（源码形状）

1. **主题写端已收敛但个性化仍 7 个裸 LS 键**：二元主题走统一单写端（themeProjection），但个性化（skin/customBg/customFg/fontSize/brightness/...）仍散落 7 个 `crish_theme_*`/`crish_font_size_adjust` 等 LS 键——未走统一 key/value 配置网关，属「投影不完整」残留（不违背不变量，但与「单一配置网关」理想有距离）。
2. **commandPermissions 前端正则表 vs 引擎 TrustZone 双语义**（03 审计已指）：commandPermissions.ts 自身 `ShellRiskLevel` 注释「对齐引擎 TrustZone 语义，不依赖 daemon 包」——仍是前端自维护风险分级，审查判定存在双发散风险（对应草案 §7 反例「权限判定 2 套发散发散分类」）。收口时审核危险等级收敛到引擎权威。
3. **布局 store 与 shell 深度耦合投影回环已显式断环（isTreeDockProjectionSuppressed）**：投影双向但抑制互触发，是 12 审计后已收敛的良好样本，可作扩展机制先例。

## ⑥ 划分建议（可定制面 vs 扩展面）

> 依据草案 §3.1 前端核心 vs 扩展划分 + §7 判定与「边界模糊判扩展」。核心 = 参与会话时间线渲染与输入闭环 + 完整性三件套；扩展 = 有独立策略/可配置/缺失不影响时间线闭环。

### 6.1 明确为「核心可定制面」（最小完整产品必须、无插件也可用）

1. **主题二元切换（default/dark）**——草案 §3.1「设置基础：主题切换」。建议保持**二元 token 投影 + 单一写端 + 默认回退**为内核；换肤/亮度等**宽度**外移到扩展。
2. **模型选择（provider 级别）**——草案 §3.1「设置基础：模型选择」。默认 profile + 单一默认模型即核心；多 profile/扫描/自定义 baseUrl 为扩展。
3. **基础布局（默认单面板 + 标签切换）**——核心渲染最少工作区形态；`createDefaultTree('chat')` 即核心内核对起。
4. **审批交互基础（allow/deny/ask UI）**——草案 §3.1「审批交互」。

### 6.2 明确为「扩展可定制面」（核心经容缺，缺失时核心 UI 完整）

1. **皮肤预设 / 自定义色 / 亮度 / 时光过渡 / 字体 / 密度 / shell-chrome**——全部经 token 注入，属强可配置视觉扩展。
2. **布局定制高级能力**：多会话绑屏、多 unit dock、任意深树、拖拽重排、尺寸持久化恢复、undo/redo 完整栈——workspace-shell + layout-tree 完整能力（草案 §3.1 明列「布局定制」为扩展）。
3. **provider profiles 管理**：多服务商、模型扫描、baseUrl 自定义、密钥 DPAPI。
4. **权限策略/命令白名单**：permissionMode → C 审查策略扩展；白名单真源应收敛到引擎（去前端自维护正则表风险）。
5. **快捷键改键**（导航/面板导航键 + 自定义键位）；发送键(enter/ctrlEnter) 因为贴近输入闭环可视为核心边角，但改键 UI 整体可扩展。

### 6.3 建议落地为「划分契约」（可入库到草案 §3.1 收口）

- **核心可定制面仅 4 项**（主题二元 / 模型选择 / 基础布局 / 审批交互基础）。
- **一条原则**：**任何定制只要「缺失（或恢复默认）后核心时间线渲染与输入闭环仍完整可用」即判扩展**；与草案 §7「宁可外置后证明必须核心，不可塞进核心后难以拆出」一致。
- **配置状态带**：主题/布局/权限/快捷键/provider 均为**独立配置域，不进会话消息时间线**；如需历史/撤销，建议配置事件独立带（草案 §6 决策点明示），**禁止**塞入消息事件流而污染「唯一时间线」模型。
- **收敛方向（呼应前序 11/12）**：
  - 主题个性化 7 个裸 LS 键 → 收编统一配置网关（若可行）；
  - 权限风险分级收敛到引擎权威（CommandPermissions 前端表职责收窄为「展示/交互」，判定真源移引擎）。

### 6.4 一页速览（划分全景）

```
核心可定制面（4）           扩展可定制面（可插拔/缺失核心仍完整）
  ① 主题二元切换              ① 皮肤/自定义色/亮度/时光过渡/字体/密度/形态
  ② 模型选择（默认 profile）   ② 布局高级能力：多会话绑屏/多 unit/任意深树/尺寸恢复
  ③ 基础布局（默认单面板）      ③ provider profiles 管理 / 模型扫描 / 自定义 baseUrl
  ④ 审批交互基础              ④ 权限策略/命令白名单（收敛到引擎）
                             ⑤ 快捷键改键（导航/面板）
   ── 以上全部不进入会话消息时间线（独立配置域）──
```
