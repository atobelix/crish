## ① 未来形态（我们的核心模型定论 · 来自 00-核心逻辑模型草案）

- **七不变量**：一切皆文本节点 / 唯一时间线（事件流为骨架，只追加+逻辑截断）/ 投影派生 / 单路径 / 核心不知道扩展 / 节点状态生命周期（ongoing=增量事件可丢，settled=必达事件落库）/ 编辑保护（版本契约+编辑会话事件+失效传播）；
- **核心七步链**：输入→备轮→请求构建→流式→工具执行→裁决→收场（dispatch_once 33 行，缝面已定）；
- **前端核心 vs 扩展**：核心六域（会话/时间线渲染/输入/审批/设置基础/原子基座+完整性三件套）；扩展五面（展示归类/编辑器/工具 UI/可定制/插件轨）；
- **扩展点 A/B/C/D** + 抽象纪律五条（类型收敛/两实现法则/三层上限/事件+注册表优先/新抽象可删）。

## ② 当前形态（现状实证 · 来自 analysis/01–19）

- 事件流骨架已成立（engine 只写 events），但**同一概念 2–7 条并行路径**（消息 7 层类型、插件 4 套、权限 2 套、storeAccess 3 份、双队列）；
- 核心循环干净但**压缩编排 590 行内嵌** + 两条反向依赖硬编码 + 三个缺缝面；
- 前端原子化基础设施存在但**门禁失守**（S0 清零待做）；上帝 store/消息双份存储/投影双实现；
- 状态维度：text/thought 已事件化；run 进行中无事件；tool-update 死契约；写文件无进度（合理）；
- 撤回：停 run 可复用，timeline-truncate 零先例须新建；编辑保护无会话抽象（dirtyRef 开环）。

## ③ DSH 核心设计模型（⏳ 审计 21 深挖中 · 已知要点）

- **会话事件 = 唯一事实源**：KNOWN_SESSION_EVENT_TYPES 校验 + write-behind 批量落盘 + revision 幂等（session-persistence/coordinator.ts）；投影从事件派生（session-projection）；
- **217 叶子包 + cordis DI 装配**：契约包（session-persistence）+ 实现包（jsonl/sqlite）分离；ui-* 一特性一包；
- **扩展机制**：hooks（onUserMessage 等）+ tool 注册 + skill/goal/todo 包（⏳ 清单待 21）；
- **前端**：ui-primitives + ui-* 包，投影消费模式（⏳ 待 21）；
- 已有 ACP 包（packages/acp）、i18n 体系、website/examples。

## ④ Pi 核心设计模型（✅ 审计 20 已确认）

- **不是「唯一事件流 + 投影」，是三轨并存**（务实承认数据/排程/UI 三种关注装不进一条时间线）：
  - `Entry` 流：带类型 / `parentId` 分支树 / 全局 `seq` 的数据事实；
  - `LaneRecord` 日志：`operation_started/step_attempt/tool_started/queue_*` 等排程控制记录；
  - `SessionSnapshot`：UI 权威快照（revision 去重，前端丢弃过期版本）；
- **`reduceLaneState`（reducer.ts）= 我们的「投影」等价物且更强**：纯函数，先跑 `validateRecordLog` 硬性拒腐（单开操作/连续 attempt/工具序位/无重复调用/abort 后不入队）——**凡正常写入不可能产生的状态一律判 corruption 而非修复**，正是我们「唯一时间线重放」缺的「先验证再派生」门禁；
- **`buildSessionContext`（session/context.ts）= 「分支路径 → LLM 消息」浓缩投影**：沿 parentId 从 leaf 回溯，折叠 compactionSummary/branchSummary 成消息、按 seq 派生 effective 模型/思考/工具配置——最接近我们「时间线 + 派生」的直接先例；
- **协议非 ACP/MCP，是自研 framed-CBOR + TypeBox**：服务端「快照为真 + `session_progress` 增量 + revision 去重」向前端同步；「invoke 结果 = 最新快照 + 广播快照」可借鉴；
- **扩展点**：`before_*` 事件可**返回结构化覆盖**（比只读事件桥更近「可扩展能力」）；输入队列分 `steer/followUp/nextRun` 三态 + 空转 drain 点；`writer_leases + fence` 写者租借保证时间线串行写权；
- **注意**：AgentHarness 类方法多为 `HarnessNotImplemented` 骨架；coding-agent（JSONL SessionManager）与 harness（抽象 SessionStorage 后端）**同一仓库两套会话模型**（反面教材：我们也存在双队列/双 store 同类问题）。

## 可借鉴清单（✅ 20 已回填 Pi 项 · 21 待收）

1. **Pi `validateRecordLog` 拒腐** → 投影前「先验证再派生」门禁（我们唯一时间线重放缺的）；
2. **Pi 快照权威 + revision 去重** → 检查点在时间线上的规范位置（M2），别只靠事件重放；
3. **Pi `before_*` 覆盖式扩展点** → 比只读事件桥更近「可扩展能力」（扩展点 A/B/C/D 的承载形态候选）；
4. **Pi writer_leases + fence** → 时间线串行写权保证（我们 events 表 single-writer 的显式化）；
5. **Pi 输入队列三态（steer/followUp/nextRun）+ 空转 drain** → 扩展点 B 的时机语义先例；
6. ⏳ Pi branch-summarization / DSH 会话分支 → 「撤回/分支/rewind」统一语义（模型层缺口 M1）；
7. ⏳ Pi skills / DSH skill 包 → 「技能/能力包」扩展形态（对比 plugin-sdk B 轨死层）；
8. ⏳ DSH session-persistence-jsonl → 「时间线可移植格式」（P5）；
9. ⏳ Pi telemetry conformance / DSH runtime-diagnostics → 遥测契约（E1）；
10. ⏳ Pi evals / DSH spec 组织 → 行为级评估（E2）；
11. ⏳ DSH cordis 装配 → 壳层装配收口（两条反向依赖移出的目标形态）；
12. ⏳ Pi framed-CBOR 快照同步 → 我们的 IPC 契约形态（E3 协议面候选）。

**模型层对照问题（待用户定夺）**：Pi 承认「数据/排程/UI 三轨装不进一条时间线」——我们的模型主张「一切皆文本节点 + 唯一事件流（类型标记区分）」。两者是否冲突？倾向：**我们的类型标记（node.type）天然支持三轨合一**（data 类节点 / control 类节点 / snapshot 类节点同流不同型），Pi 的分轨是「无类型化单流」下的务实妥协；但 Pi 的「快照权威」提示我们：**投影缓存（session_messages 等）应显式快照化 + revision 去重**，而非每次全量重放。

## 结论

- **模型层最该补的**：M1 会话分支/树语义（把撤回/截断/rewind/压缩统一成「时间线操作族」）——这是当前模型唯一的语义空洞；
- **最值得借鉴的**：Pi 的 branch-summarization 与 skills、DSH 的 session-persistence-jsonl 与装配模式（⏳ 审计确认后定夺）；
- **工程面**：遥测契约与行为级评估是第二层回归保护（对应你「测试和门禁成阻力」的痛点——评估层可以替代部分脆性单测）。
