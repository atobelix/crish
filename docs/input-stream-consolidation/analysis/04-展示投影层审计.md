### 关键前置发现（影响整体结论）

**展示投影层存在「双轨」**：项目里实际上有 **两条不同语义的投影链**，与任务书假设「ModelView→UserView」单链不同：

| 轨                                                               | 输入                                                        | 输出                                                      | 消费方                                                                    | 是否渲染主路径          |
| ---------------------------------------------------------------- | ----------------------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------- | ----------------------- |
| **轨 A：timelineNormalizer / toolCardPresenter（展示投影真身）** | store 的 `SessionMessage`（blocks/toolCalls/text/thinking） | `AssistantTimelineItem[]` / `ToolRenderItem[]` / 展示标签 | **`MessageContent` 渲染路径**（messageUserProjection 之外的真正渲染管线） | ✅ 是                   |
| **轨 B：messageUserProjection（UserView 投影）**                 | `SessionMessage` / `EngineLikeBlock`                        | `UserViewDto`（messages + hiddenBuckets + stats）         | 仅 `silentComplete.ts`（流收口判定）+ `UserViewDebugPanel` 调试 + 测试    | ❌ 否（不在渲染主路径） |

**结论先行**：任务书所述「Project→UserView→组件」投影链中，「组件」实际吃的是 **轨 A** 的 `AssistantTimelineItem[]`，**不是**轨 B 的 `UserViewMessage`。UserView 轨（messageUserProjection）是可独立删除的**旁路投影层**，其主要生产价值目前仅剩 `silentComplete` 的单消息判定。详见 §③/§④。

## ③ 问题清单

### P1 【关键·结构债】展示投影是「双轨」，messageUserProjection（UserView）不在渲染主路径

- 证据：
  - 渲染主路径：`MessageContent.tsx:227` → `buildAssistantTimelineCached`（轨 A）→ `TimestampItems[]` → `MessageToolCallsSection.tsx:22` → `ChatToolStack`（`ChatToolCallBlock.tsx:220`）→ `CompactToolRow`。
  - `messageUserProjection`（轨 B）的**生产消费方仅 3 处**：`api/silentComplete.ts:18`（`projectSessionMessageToUserView`）、`components/settings/SettingsProfileTab.tsx:12`（`isUserViewDebugEnabled`）、`components/settings/UserViewDebugPanel.tsx`（调试面板）。其余全部为测试文件（`messageUserProjection.test.ts`、`systemInvariants.test.ts`、`silentComplete.test.ts`、`messageRenderIdentity.test.ts`）。
  - 渲染层从未 import `messageUserProjection`：grep `UserViewDto|projectSessionMessagesToUserView|projectEngineBlocksToUserView` 在组件/渲染目录**零命中**。
- 影响面：UserView 是**既成事实的旁路投影层**——为某次审计/调试目标新增的 DTO 集合（stats/hiddenBuckets/分类断言），未接渲染。它不产生用户可见差异，但延续了「手写第 ≥5 套消息类型」的局面（UserViewMessage/UserViewToolCard 又是一套新形状，`messageUserProjection.ts:48-93`）。
- 建议方向：① 若 D1 的目标是「事件流派生 UserView 供渲染」，需**先接渲染**（否则 UserView 成了死层）；② 若 UserView 仅保留 silentComplete 语义，则**只需单消息**的 `visibleText/tools/thinkingPreview`，不必保留整套 UserViewDto + hiddenBuckets + stats + 分类断言；③ 二选一后删除另一套。裁决权归主控（review §23）。

### P2 【结构债·重复投影逻辑】timelineNormalizer 与 streamMessageViewModel 块对齐逻辑重叠

- 证据：
  - `timelineNormalizer.ts:33` `normalizeAssistantTimeline` 负责「blocks 缺 tool_call 时注入 / 缺 text 块时补偿」。
  - `streamMessageViewModel.ts:138-151` `applyStreamToolsToMessage` **自己也重算一遍** tool_call block 补齐：`if (!inBlocks.has(tc.id)) blocks.push({type:'tool_call', id:tc.id})`。
  - 且 `MessageContent.tsx:147-166` 先 `applyStreamToolsToMessage` 又把结果显示给 `buildAssistantTimelineCached`（后者内部走 `buildAssistantTimeline`，再次用 blocks+tools 对齐）。
- 影响面：同一「tool_call 块与 toolCalls 对齐」规则在两处实现（+ buildAssistantTimeline 第三次消费），规则漂移风险；流式路径叠套了两次对齐。
- 建议方向：把「streaming tools → tool_call blocks 补齐」与 normalizeAssistantTimeline 合并为一个纯函数（或让 applyStreamToolsToMessage 复用 normalizeAssistantTimeline 的注入规则），消除双实现。

### P3 【半连通·归类硬编码】「官方命令类型图标」既不在展示层、也不在组件内——**整体缺失**（而非硬编码）

- 证据：全仓 `src` 无任何「工具命令类型 → 图标」映射实现。
  - `ToolCallHeader.tsx:142-171` 的 `toolIcon` 是**按状态**（running→spinner；success→`CheckCircle2`；error→`XCircle`；else→`CircleDot`），**非按命令类型**（shell/编辑/网络/note…）。
  - `tool-presentation/*`（toolDomainDescriptions 等）只产出中文字符串标签，不产出图标 token。
  - 00-总方案 §2.3 明确列出「官方命令类型图标」为展示投影三要素之一（另两个：连续工具调用折叠行、工具调用目的描述）。
- 影响面：总方案愿景项在 D4 域**未落地**；若按愿景推进，这是从零新增（易落入过度设计，需主控裁决是否真需要类型图标 vs 现状状态图标已够）。
- 区分：**工具调用目的描述**已实现（P4）；**连续工具调用折叠行**部分实现但被渲染端展平（P5）；**官方命令类型图标**整体缺失。

### P4 【已实现·归类位置正确】「工具调用目的描述」在纯展示层（toolHumanLabel/toolLabelFromArgs）

- 证据：`toolHumanDescriptions.ts:17` `toolHumanLabel`（AI explanation 意图取信，经 `isHumanExplanation`/`isGenericExplanationSpam` 过滤后输出）+ `toolDomainDescriptions.ts:11` `toolLabelFromArgs`（13 类工具参数→中文语义标签）。二者均只 import `tool-presentation` 内部与 `toolFeedback` 的 isShellToolName/isEditToolName，无 store 依赖。
- 判定：实现位置**正确**（纯展示投影），符合「展示归类成扩展点」方向。`CompactToolRow.tsx:72/146` 只是消费它的标签，未硬编码语义。**建议保留**。
- 备查：`toolFeedback.ts:8` `isShellToolName` / `:53` `isEditToolName` 是工具域分类的**重复判定源**，被 `followUpSuggestions.ts`、`ToolCallInputPane.tsx`、`toolDomainDescriptions.ts` 多方引用 —— 是「工具类别」概念的一个次 canonical（可并进统一工具注册表，见 §⑤ 备注）。

### P5 【半连通·折叠行】「连续工具调用折叠行」在投影层生成但被渲染端展平——折叠处于「半实现 / 假接线」

- 证据：
  - 投影端：`timelineNormalizer.ts:152` `buildToolRenderItems` 会把连续 inspect 工具产出 `{kind:'group', tools, label:'… · N 步'}`（:164-172 注释「避免 N 步汇总头」）。
  - 渲染端：`ChatToolCallBlock.tsx:58-65` `flattenRenderTools` **把 group 重新拆回单条工具**，`renderToolStackItems` :177-218 再按 `turnId`+`startedAt≤200ms` 重组成 `parallelGroup`（「Parallel（N）」），完全绕开了投影端的 group 折叠。
- 影响面：`buildToolRenderItems` 的两类折叠（连续 inspect 折叠 / 同轮并行分组）与渲染端 `parallelGroup`（同轮并行分组）**语义重复且互相覆盖**——投影产出的 group 被展平，渲染端按另一套 key（turnId/startedAt）再折叠。存在 double-grouping 残差且 `label`（「N 步」）从未被消费（`ToolRenderItem['group']` 的 label 在 flattenRenderTools 时被丢弃）。
- 建议方向：折叠/分组的**唯一裁决点**应下沉到投影层（timelineNormalizer），渲染端只消费 `ToolRenderItem[]`（不再 flatten 重分组）。否则至少注明 `group` 的 label 是死字段，收敛为单路径。

### P6 【状态管理·范围】「展开态」硬编码在组件层（expandedTools），不在投影

- 证据：`CompactToolRow.tsx:32-50` 依赖 `props.expandedTools`/`onToggleTool`（来自 `ChatToolStackProps`，由 `ChatAssistantMessageRow`/`useChatMessageState` 装配为 UI state）。`toolCardPresenter.ts:56-71` `isToolRowDefaultOpen=false`+`resolveToolRowOpen` 只给默认值。
- 判定：这是**交互瞬态**，按其性质本应放组件/局部 state（review §4 禁止高频交互态写入全局 store）。**现状正确，不构成问题**——仅提示：若 D4 要「展示归类成插件扩展点」，展开默认策略（isToolRowDefaultOpen）可作为扩展点候选，但不强求。

## ⑤ 对 00-总方案 §3 映射表的核实与修正

> 针对 `00-总方案框架.md:62`「展示归类」行与 §2.3「展示投影」的核对。

**总方案原表（展示归类行）**：

> `messageUserProjection（ModelView→UserView，hiddenBuckets: thinking/tool_raw/system/nudge）+ tool-presentation/（toolCardPresenter/toolHumanDescriptions/toolDomainDescriptions/timelineNormalizer）+ chat-tool-call/（CompactToolRow/ToolCallHeader）`；canonical = 投影层保留，从统一时间线派生 | 动作 = 收敛中间态。

### 核实结果（以代码为准）

1. **总方案把 messageUserProjection 当作 canonical 投影层，与实际渲染主路径不符**：真实渲染由 **timelineNormalizer（轨 A）** 驱动；`messageUserProjection`（轨 B/UserView）**不渲染**。若按 D4「投影层保留」把 messageUserProjection 定为 canonical，将固化一条纯旁路层。
   - **修正建议**：投影层 canonical 应记为 `timelineNormalizer（buildAssistantTimeline/Cached + buildToolRenderItems + normalizeAssistantTimeline）+ toolCardPresenter/tool-presentation`（轨 A）；UserView（messageUserProjection）降级为「silent-complete 单消息判定 + 调试」的非 canonical 旁路，列入收敛/删除候选（并非新增）。
2. **hiddenBuckets 分类并非渲染侧的展示归类**：kind=thinking/tool_raw/system/nudge/system_nudge 全部只在 messageUserProjection 内部产生并被它的调试面板消费；**渲染层不消费 hiddenBuckets**。总方案把 hiddenBuckets 计为展示归类的实现载体，属**虚假对位**。
   - 修正建议：若愿景要「AI 多看内容进桶可分类」，需明确 hiddenBuckets 谁来消费（现无渲染消费）。否则它只是审计/调试概念，不应记入渲染层 canonical。
3. **「展示归类三要素」实测落地情况**（00-总方案 §2.3）：
   - ✅ 工具调用目的描述：`toolHumanLabel`/`toolLabelFromArgs`（toolHumanDescriptions/toolDomainDescriptions）已实现，位置正确。
   - ⚠️ 连续工具调用折叠行：投影端生成 `group` 但被渲染端展平重分组——**半实现/假接线**（§③ P5）。
   - ❌ 官方命令类型图标：**整体缺失**，无任何命令类型→图标映射（ToolCallHeader 只有状态图标）。
4. **与 §3 其它行的一致性**：本域结论与「前端手写消息类型 ≥5 套、删手写定义改 generated 派生」一致——SessionMessage/MessageToolCall（store/types.ts）、UserViewMessage/UserViewToolCard（messageUserProjection.ts）、AssistantTimelineItem/ToolRenderItem（toolPresentationTypes.ts）、StreamToolLive（streamingStore）、MessageTimelineBlock（store/types.ts）计 ≥5 套，均未走 generated。若 D1 收敛类型，D4 的投影输入输出类型也随之收敛。
