# 16 · 前端核心功能边界审计（核心模型 vs 扩展模型）

> 战役：统一输入流收敛 · 文档 16
> 审计范围：**只读**审计 `apps/crish-desktop/src`（React 前端），不涉 Rust 引擎。
> 背景：统一输入流收敛要求**显式区分「前端核心模型」与「扩展模型」**——最基本的界面功能在**无任何扩展时也必须完整可用**，扩展功能可插拔、缺失时界面仍完整。
> 参考：核心逻辑模型草案 `docs/input-stream-consolidation/00-核心逻辑模型草案.md` §3 前端原则；前序审计 11（组件原子化）、12（状态数据流）、04（展示投影）、08（可扩展功能盘点）、05（插件边界）。
> 遵守纪律：只读审计；只写本分配文档；区分「源码形状」与「真跑验证」（本文全部结论为源码/grep/import 链推断，**未经运行验证**）。

## ① 方法

- **只读取证**：对 `apps/crish-desktop/src`（1268 个 `.ts/.tsx` 文件）做目录盘点 + `read`/`grep`/`glob` 交叉核证；引用统一 `文件路径:行号`。
- **依赖边审计**：用 `grep` 全树扫描 `import … plugins|PluginRegistry|usePluginStore|registerOfficialPlugins|settings-extensions|plugin-browser|plugin-computer-use|plugin-follow-up|plugin-markdown|contribute|Contribute`，逐条判定「主 UI 是否 import」。
- **并行子审计**：拆 4 个视角分头取证（会话生命周期 / 时间线投影链 / 输入-发送-停止-审批-主题 / 扩展-通知-错误-空态），再与主取证合流，互为印证。
- **判定口径**（沿用 00 草案 §7 核心 vs 扩展判定准则）：
  - **核心** = 参与「时间线推进」且任何会话都必须存在的 UI 能力（开/列/切/删会话、渲染时间线、输入/发送/停止、审批、设置入口、主题、错误可见）。
  - **扩展** = 可配置可替换、或只消费时间线不推进时间线的 UI 能力（markdown 渲染、工具展示归类、follow-up、导入导出、浏览器/电脑工具 UI、富文本编辑器、通知、自定义布局）。
  - **边界模糊判扩展**（宁可外置后证明必须核心，不塞进核心后难拆）。

**一处与既有审计的订正**：12 审计曾断言「同一正文/工具在 `streamingStore` 与 `layoutStore.messages` 双份存储」。本次核实 `store/sessionStore.ts:1-27` 明示 sessionStore 是 layoutStore **同一 zustand 实例的 facade**（非第二真相源），`storeOwnership.ts` SESSION_OWNERSHIP 唯一写主。真正的「双缓冲」是 **`streamingStore.byKey`（热、非持久）↔ `session.messages`（持久终态）**，由 `MessageContent` 渲染期 view model 桥接——这是**设计内必需桥**，不是冗余双存储。本文按该更正口径展开。

## ④ 核心 → 扩展依赖边清单（含缺失后果）

**总判：核心 UI 对 `src/plugins/*` 的 import 依赖边为 0。** 全树 `grep` 结果（`apps/crish-desktop/src/plugins` 自身与 `settings-extensions/pluginRegistryAdapter` 及其测试外）**没有任何主 UI 文件** import `plugins/*`/`PluginRegistry`/`usePluginStore`/`registerOfficialPlugins`/`plugin-browser`/`plugin-computer-use`/`plugin-follow-up`/`plugin-markdown`。故「任一插件缺失/加载失败」**不会破坏核心界面**——因为没有消费方。

### 6.2 建议的核心/扩展切分线

1. **把「主输入编辑器」从扩展域拉回核心契约，但解耦 Tiptap**：
   - 定义核心输入契约（`value/onChange/onSend/onStop(L2)/onForceStop(L3)/onPaste/onFiles/draft 水合/aria`）。`TiptapComposerField` 实现该契约（作为**可替换的富文本变体**），核心默认可回落到 `ComposerField`（textarea）同一契约实现 → 消除 G1。
   - 判定：**输入/发送/停止本身是核心**（走 `core_run_task`/`core_run_control`，§② C8）；**富文本排版能力是扩展**（slash/mention/代码块 UI）。

2. **把「展示归类」外置为注册表（D4 目标）**：`tool-presentation/*` 改为「核心只消费归类结果，归类策略由注册表承载」；默认内置一套（现启发式即默认实现），插件可覆盖 → 消除 E3、对齐 00 草案「展示归类」外置。

3. **follow-up 收敛到单轨并外置**：删除死插件 `plugins/plugin-follow-up`；保留内置启发式为默认实现，暴露为可扩展点（`FollowUpSuggestions` 类型 + 注册），消除 E4。

4. **命名去撞车 / 死代码清理**：`src/plugins/*` 如无落地计划应收敛删除（符合 00 草案「接口两实现法则/新抽象可删除」）；浏览器/电脑 UI 只保留内置实现 + 引擎桥，改掉与死插件同名误导（E5）。

5. **核心投影收敛到单链**：以 `MessageContent` 渲染期 merge（§② C6）为主，`messageUserProjection`/UserView 旁路（E6）合并或显式降级为调试通道，消除 G5。

6. **审批/错误/主题/设置入口维持核心**：`core_approve_tool`/`core_deny_tool`（C9）、`core_run_control`（C8）、`themeStore`+`themeProjection`（C11）、`openSettings`（C10）、`errorStore`+`AppErrorBoundary`（C12）均已核心且独立，**不添加任何扩展依赖**。

7. **设置「扩展」tab 只保留真扩展管理**：`SettingsPanel.tsx:96-102` 中 `plugins/skills/mcp` 三 tab 收敛为单一「扩展」入口（或独立懒加载），核心/扩展 tab 边界显式化，消除 E2。
