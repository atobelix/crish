## ③ 问题清单

### 问题①（最高优先级）：动态状态注入完全没有进时间线的通道

**证据**

- 前端模型/权限/思考切换 → 只写 `localStorage` + `emitUiEvent('profiles-changed')`（`profileStore.ts:94-108,129-139`），而 `emitUiEvent` 是 UI 事件，**不产生引擎 `AgentEvent`、不写会话事件/消息**。
- 主路径请求装配：`chat-bridge/ConnectionLifecycle.ts` `createStreamSession`（:340-443）把 `permissionMode`、`budgetDifficulty`（由 defaultThinkingLevel 映射，:360-365）、`systemPrompt` 作为 `startRunTask` 的 **IPC 参数**直接下发，往返于引擎请求体，**不写入任何时间线节点/事件**。
- 引擎侧 `build_request`（`session-loop/src/loop/handlers/streaming.rs:330-361`）造 `ProviderRequest` 时 `reasoning_effort`：
  - 仅当「最后一条消息是 tool-promise 自愈 / `thinking_budget=0`」才 `Some(Off)`（:347-351）；
  - 其余恒 `None`（:350）。
- `SessionLoopOptions` 无 `reasoning_effort` 字段（`run/run_launch.rs:583-642` 装配面清楚看到 options 从不携带思考档位）。
- `EngineProviderConfig`（`engine_provider.rs:64-77`）只有 base_url/api_key/model/endpoint/stream/extra，**无 effort 字段**。
- `ProviderRequest.reasoning_effort` 字段本身存在且契约测钉死（`run_loop.rs:999` `reasoning_effort_field_propagates_through_request` 断言 Some/None 透传），但**仅测试构造 + tool-promise 自愈路径**消费；用户思考档位**从未到达该字段**（须真跑核验：产品 UI 切 high → 抓 provider 请求体是否出现 `reasoning_effort:"high"`——按源码形状判断为否）。
- `directFetchBridge.ts:73-107` 的 `buildThinkingParams` 确实把 `defaultThinkingLevel` 映射进请求体 `reasoning_effort`——但该模块文件头自述「**非产品 SoT，仅降级**」（directFetchBridge.ts:4-11），产品主轨 `streamViaEngine` 走 `chat-bridge/ConnectionLifecycle.ts`，不走此路径。

**影响面**

- 用户切换思考模式/模型/权限后，引擎当前轮与后续轮读不到该状态的「文本化认知」；模型只会按固定 effort 思考。
- 「状态变化」无法在任何会话时间线/审计/恢复中回放——切换发生在请求参数层，是**瞬时、无痕**的，违反「所有内容皆为带类型标记的输入文本 + 唯一时间线」。
- 权限模式同理：`permissionMode` 只作为 run-task IPC 参数，不产生时间线节点。

**建议方向**

- 新增 `context-state` 节点（`role` 或 `metadata.kind` 标记，如 `kind:"context-state"`），把「模型名 / 权限 / 思考模式」切换渲染为一段文本，**挂到用户下一次提交**（扩展点 A：即时 vs 挂下一条队列），并作为 `AgentMessage` 进入 `ProviderRequest.messages`（text 载荷 + 元数据标记），不单独占 wire system_prompt。
- 复用 §4-问题⑤ 的 `PendingMessageQueue`（已接线到下一 run 边界）作为注入载体，或新造同构的 context-state 队列。

### 问题②：nudge 通道（PendingNudgeChannel）是「半成品可复用机制」，但未接线

**证据**

- `PendingNudgeChannel` 完整实现了 enqueue / enqueue_into_input_queue(followUp) / drain_all / nudge-enqueued 事件（`steering/nudge.rs:182-317`），并有测试验证「排 followUp 环 → idle promote → 成为下一条用户角色消息」（`nudge.rs:417-444`）。
- orchestrator 侧 `PendingMessageQueue::drain_nudges`（`orchestrator/src/steering_queue.rs:228`）能把 nudge 通道转入跨 run steering 队列（按 reason 去重）。
- **但生产路径零接线**：
  - `PendingNudgeChannel::enqueue_reason/enqueue` 仅在 `nudge.rs` 自身测试被调；
  - `PendingMessageQueue::drain_nudges` 在壳层 `apps/agent-workbench/src-tauri/` grep 零命中；
  - `resource.rs:316-319,636` 自述「PendingNudgeChannel 实例在 orchestrator 的 PendingMessageQueue 内部，壳层无访问入口 → 生产路径 None（通知文本经 tracing 留痕），T-AB-18 接线」。
- 当前 steering 生产路径实际走的是 **inject-message 注入当前 run**（steering_evaluation.rs:73-75 / prepare_turn.rs:103-105），并非 D8 裁决的「run 内不注入、排入下一条用户消息」。

**影响面**

- 「nudge 挂下一条用户消息」的机制**已成型但未通电**；若 D2 要以 nudge 通道作为注入时机扩展点 A 的载体，当前不可用。
- 存在**双队列并存**：session-loop 的 `AgentInputQueue.followUp`（被 turn_complete.rs:192 `promote_follow_up` 消费）+ orchestrator 的 `PendingMessageQueue`（被 run_idle.rs 消费）——两条「下一条用户消息」语义载体未打通。

**建议方向**

- 收敛：明确把「下一条用户消息」定义为 orchestrator `PendingMessageQueue`（已接线），session-loop 侧 steering 在需要跨轮/挂下一条时经 `PendingMessageQueue::drain_nudges` 汇入，删掉或冻结未接线的 `PendingNudgeChannel` 直接通道（或补接线）。
- 需真跑核验：run 内 empty-response steering 注入的 System 消息确实出现在当前对话尾部（source 形状成立）。

### 问题③：steering inject-message 实际注入当前 run，与 D8「run 内不注入」裁决冲突

**证据**

- `SteeringCoordinator::apply`（`steering/mod.rs:352-360`）`conversation.push(Arc::new(message.clone()))`——**追加到当前 run 对话**。
- 触发点：`loop/handlers/steering_evaluation.rs:73-75`（empty-response）、`loop/handlers/prepare_turn.rs:103-104`（after-tools/before-turn）直接 `state.steering.apply(... &mut state.conversation)`。
- 而 `steering/mod.rs:21` 自述 **D8：nudge 一律不注入当前 run；注入走 nudge::PendingNudgeChannel**——源码注释宣称与行为不符（steering inject-message 与 nudge 是两个机制，inject-message 注入当前 run 是**预期设计**，但文档口径让人以为纠偏都走 nudge 通道）。

**影响面**

- 概念口径混乱：inject-message（当前 run）vs nudge（下一条用户消息，未接线）混在同一 steering 子系统，审计/收敛难。
- inject-message 注入 System 到当前对话尾，属于「事件流 + 当前对话」，实际已经在时间线（RuntimeSteering 事件 + System 消息），这一点是**正向的**（唯一已进时间线的注入通道）。

**建议方向**

- 区分两语义并写清：recovery 纠偏（工具错误/空响应）→ 当前 run 注入（inject-message，已进事件流）；主动提醒（后台任务/状态变化）→ 下一条用户消息（PendingMessageQueue）。不要混为一谈。

### 问题④：钩子 model.* / subagent.* 「只挂钩不补源」，状态变化的可观测面缺位

**证据**

- `hooks.rs:11-14,54-57,93-100` 明确 `model.beforeRequest` / `model.afterResponse` / `subagent.start/end` 四变体「只挂钩不补源」，生产无发射点（`engine_channels.rs` 仅作事件面，未接线到 provider 请求）。
- `HookOutcome` 观测事件（hooks.rs:570-577）存在，但需 `set_outcome_sink` 接线。

**影响面**

- 即便要做「模型切换即记入时间线」，`model.beforeRequest` 可承载（内含 `provider_id`/`model`），但当前未接线，无法观测模型切换何时发生。

**建议方向**

- 把 `model.beforeRequest` 发射点接到 `HttpProviderCall`（engine_provider）请求构建处——模型名/effort 是这些事件的载荷字段，可补齐「模型切换可观测」，并作为 context-state 节点的候选数据源。**无需新增事件变体**，复用既有 hook 面。

### 问题⑤：已接线的「挂下一条用户消息」是 orchestrator PendingMessageQueue，可作 context-state 载体

**证据**

- `PendingMessageQueue`（`orchestrator/src/steering_queue.rs`）+ 各 `QueuePendingSink`（timers.rs:142-151 / sched.rs:212 / watchdog / wake_watcher / task_event_consumer / workflow_commands / subagent_spawner）→ 已实际把后台事件写成跨 run steering 条目。
- 消费：`run/run_idle.rs:228,308,393` 在 idle-resume / goal-continue / 续 run 时 `drain_pending_to_inject_messages`（:534）把条目变 User 消息 `{kind:"steering"}` 注入下一 run（:564-573），并为每次续 run 计数（:1564 `inject_messages`）。
- 该机制**已通电**（定时器到期、watchdog、子代理终态等会触发续 run 并注入文本）。

**影响面**

- D2 的动态状态注入可以直接复用这条已接线的「下一条用户消息边界」通道：状态切换 → `PendingMessageQueue.replace_or_enqueue`（按 group_id 去重，天然防重复注入）→ 下一 run 边界作为 User 文本注入，同时它**进入对话 `ProviderRequest.messages`**（text 载荷），从而进时间线（message-start/end 事件）——正好满足「带类型标记的输入文本」。
- 需注意：该队列 `into_user_message` 元数据目前只有 `{kind:"steering"}`（steering_queue.rs:89-93），context-state 需另设 kind（如 `context-state`）区分展示。

### 问题⑥：类型标记缺失——注入/状态只有 `role` + `metadata.kind` 字符串约定，无常量类型

**证据**

- `AgentMessageRole`（`conex-types/src/message.rs:15-24`）仅 System/User/Assistant/Tool，无 injection / context-state / nudge 角色。
- 注入/状态靠 `metadata.kind`（`runtime-steering` / `nudge` / `diagnostic` / `steering`）散落字符串（nudge.rs:100,120,162、steering_queue.rs:91、binary 恒 `tool-promise-recovery` 在 streaming.rs:338）。
- `AgentMessageBlock`（message.rs:100-126）只有 text/thought/tool-call/tool-result，无 state/injection 块类型。

**影响面**

- 「一切皆文本 + 带类型标记」中的**类型标记**目前不统一（role+metadata.kind 双轨、字符串魔法值、无枚举常量化）。前端 `messageUserProjection.ts`（:29-30,116,472-491）已有 `nudge`/`system_nudge` hidden bucket 消费这些 shape，但常量定义在两处（前端 `EngineLikeBlock` 手工类型 + Rust metadata 字符串），无 generated 派生。

**建议方向**

- D2 应产出：注入/状态的 canonical **类型常量**（如 `AgentMessageMetadataKind::Nudge/Steering/ContextState/Diagnostic`），并在 Rust + 前端 generated 派生对齐；新增 `context-state` 类型（问题①的落点）。

### 问题⑦：`reasoning_effort` 契约字段是「有字段无来源」的半连通

**证据**

- `ProviderRequest.reasoning_effort`（`provider.rs:155`）+ 契约测 `run_loop.rs:999` + `engine_provider/thinking.rs` 全套 vendor 映射/校验/白名单/请求体写入到位。
- 但字段唯一赋值点在 `streaming.rs:347-351`（tool-promise 自愈 / thinking_budget=0 → Off），**用户思考模式永不进入**。
- `agent-provider` 侧 `build_chat.rs:50-51`、`build_anthropic.rs:142` 已能消费 `reasoning_effort` 产出 wire，`engine_provider` 侧 `thinking.rs` 已验证（`engine_provider_tests.rs:219-227`）。

**影响面**

- 「思考模式切换」的**传输管道全部就绪**（前端→run-task→ProviderRequest→vendor→wire），唯一缺的是把用户的 thinking level 这条链路从 `ConnectionLifecycle` 的 `budgetDifficulty`（当前只映射成 easy/normal/hard 预算难度）升级为**真正的 reasoning_effort 下发** + context-state 文本节点。这是一个「只差最后接线」的收缩，不是新建。

**建议方向**

- 在 `RunTaskOptions`/`createStreamSession` 增加 `reasoningEffort` 透传（或复用 `thinkingLevel`），引擎 `build_request` 读取并入 `ProviderRequest.reasoning_effort`；同时生成 `context-state` 文本节点挂提交。契约测 `run_loop.rs:999` 已具备验收基础。
