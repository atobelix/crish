## ③ mobile 与核心模型差距清单

### 3.1 事件流「只追加」反例（10 审计复证 + 精化）

核心模型不变量 2：「**任何『删除』都是逻辑截断（新事件），不是物理删除**」。mobile 在**本地 SQLite 事件镜像**上存在物理删除设计：

1. **`eventsDao.ts:148-156 deleteOlderThan`** —— `DELETE FROM events WHERE session_id=? AND sequence < ?`（每会话窗口物理删除）。源码形状确认（10 审计反例点）。

2. **`cachePolicy.ts:166-230 runCleanup`** —— 容量清理执行器：
   - 每会话保留 `eventsPerSession=5000`（`cachePolicy.ts:24`），超窗调用 `DELETE ... sequence < keepFloor`（`:225`）或保留 0 条时 `DELETE ... WHERE session_id=?`（`:212`）；
   - 全局兜底 `eventsGlobal=50000`（`:25`）进一步收缩。

3. **`eventsDao.ts:158-162 deleteBySession`** —— `DELETE FROM events WHERE session_id=?`（会话删除级联语义）。

**关键精化（区别于桌面）**：桌面的事件删除语义是「引擎侧逻辑截断（新 truncate 事件）+ 前端投影删除」，而 mobile 的 events 表是**本地离线镜像（cache 性质）**，其物理删除是「**窗口化缓存的容量管理**」，不是「时间线语义删除」。这从语义层面削弱了反例的严重度，但**设计契约仍与「事件表只追加」相悖**：

- 当 events 表被当作「事件流本地事实源」供 resume 追平/续传时（`listAfter`/`latestSequence` 游标语义，`feedBridge.resumeSession`），物理剪掉旧 sequence 会让「游标只升不降」的续传在断线长窗口后**无法从 0 全量重建**——旧事件已物理消失，无法重放。
- 这与 core 模型「事件流可重放」的核心承诺冲突。

**[源码形状接线现状]**：`migrations.ts` v1 已建 events 表；`eventsDao` / `cachePolicy.runCleanup` 目前**仅在测试中接线**（`dbBootstrap.ts` 只 `configureSqlitePersistence(settings/notification)`，未接 events 表落地与清理触发器）。即「物理删除反例」当前是**已建的契约 + 尚未 live 接线的执行器**；一旦后续接入事件持久化并启用 runCleanup，反例会实跑。**建议主控在接入事件持久化时即按 core 模型修正**，而非等反例实跑后再修。

### 3.2 消息类型：mobile 无手写消息类型（正面差异）

桌面被 01 审计点名「同一条消息 7 层类型形态」。**mobile 反而没有手写消息类型**：

- mobile 不编译 `SessionMessage`/`MessageTimelineBlock` 之类对象；它把引擎事件当作 `EventEnvelopeFrame`（`eventReducers.ts:11-24`，只声明 `type/runId/sequence/schemaVersion/sessionId` 信封字段 + 索引签名），事件体字段**平铺顶层，容错读取**（`readString/readNumber/readRecord/readBool`，`eventReducers.ts:51-78`）。
- 展示层直接渲染 raw event：`EventRow`/`EventFeed`（`presentation/components/blocks/EventFeed.tsx:38`）逐 type 分派；会话列表预览经 `sessionPreview.ts` 直接提取正文（`message-end.blocks[].text`、`message-delta.text`）。
- `domain/types/domain.ts` 明确遵守「组合纪律」（M5 §1.3）：契约类型（`PermissionRequest`/`DirEntry`/`ApprovalChannel`）从 `shared-types/src/generated` 引用，本地只加附加字段（`FileEntry`/`ApprovalItem`）。

**评价**：mobile 在「前端类型收敛」上反而比桌面更贴近 core 模型纪律（不手抄契约）。但它走了**另一个极端——几乎放弃类型安全**：事件体全靠容错 `readString('text')` 等运行时字符串读取，undefined 即宽容回退，**无编译期结构校验**。这是「类型化过弱」而非「类型化重复」。收敛建议见 §5。

### 3.3 投影（store/UI 结构）

**mobile 的投影模型**（源码形状）：

- **权威 = `eventStore.windows`**（`eventStore.ts:18-21`）：每会话一个 `EventWindow`（`eventReducers.ts:36-43`），内含 ring buffer `entries`（上限 500，`FEED_RING_MAX`，`eventReducers.ts:33`）+ `lastSeq` 游标 + `truncatedCount`。
- **derived store**：`sessionStore`（会话索引，来自 `session.updated*`）、`approvalStore`（审批待办，由 events 派生，`approvalMappers/approvalReducers`）、`filesStore`/`filesCache`、`notificationStore`、`settingsStore`、`connectionStore`。
- **接线层**：`FeedBridge`（`adapters/wiring/feedBridge.ts`）监听 `events.push`/`events.resume.*`/`session.*` → `mapDeviceFrame` → `dispatchIngestActions`；重连对账（`handleProjection`：resume/full-replay/fresh/cleanup）。
- **view-model 层**：每屏 `useXxxVm`（`adapters/viewmodels/useDashboardVm.ts`、`useApprovalListVm.ts`…），状态×命令投影 → `presentation/` 组件。
- **持久化**：`configureSqlitePersistence`（settings/notification 落库）；events 表存在但**未接入**（见 3.1）。

**与 core 模型对照**：

- ✅ **网络故障/重连处理先进**：`resume`/`full-replay`/`cleanup` 对账 + 游标只升不降 + feed ring buffer，比桌面的事件消费架构更贴近「事件流 → 投影」理想（12 审计桌面痛点：双 store 消息双份、storeAccess 三份——mobile 没有这些）。
- ⚠️ **ring buffer 500 条剪裁**（`appendFeed` throw oldest + `truncatedCount`）是**内存投影的物理裁剪**：超窗即丢最旧。这在「有界内存展示」上合理（13 审计认同有界），但与「事件流完整可重放」冲突——mobile 靠 `events.resume`（从桌面重拉）来补全，所以内存裁剪**不破坏事实源**（事实源在桌面 events 表），只要续传游标仍在。**这是 mobile 与桌面的本质差异**：mobile 的本地 events 存储只是镜像/缓存，事实源在桌面 daemon。
- ⚠️ **`deleteOlderThan` 若启用会破坏「从本地重建」能力**（见 3.1），但与「经 resume 从桌面重建」路径相权衡。

### 3.4 引擎连接（mobile 连哪、mock-daemon 是什么）

**mobile 不直接连引擎**——它是一台**远程伴侣客户端**，通过 `device-protocol.json`（`crates/conex-types/contracts/device-protocol.json`，唯一真源）连**桌面 daemon**：

- **桌面 daemon** = `agent-workbench/src-tauri/src/server/*`（`mod.rs`：进程内嵌 axum HTTP + WS，默认 loopback `127.0.0.1:8765`；配对模式重绑 `0.0.0.0:8765`）。`main.rs:980-1000` 装配：`CoreStateBackend`（直调 `*_impl`）+ `FanOutEmitter`（挂 `core_event_bridge` 汇聚点，引擎全事件流双通道：webview + 跨端广播）。模块：`ws.rs`(R1-05 事件端点)、`fanout.rs`、`router.rs`(REST `/v1/**` + WS)、`backend.rs`/`core_backend.rs`(桥接)、`pair_endpoint.rs`/`pairing.rs`(配对)、`gateway.rs`/`limiter.rs`。
- **mobile 连线形态**：`network/WsGateway.ts`（帧编解码，`parseDeviceMessage` 引 generated device parser）、`WsEnvelope.ts`（信封类型，禁止手抄协议）、`network/ReconnectingWsClient.ts`、`network/signer.ts`（HMAC）、`domain/repositories/*`（命令面，响应类型走 generated device/types）。
- **协议契约（跨端唯一真源）**：`crates/conex-types/contracts/device-protocol.json` → 生成面 `packages/shared-types/src/generated/device/*`（types/parser/kinds/events/errors/commands/capabilities）。**无第二套手抄协议**（WsEnvelope 头注释明确禁止）。

**`scripts/mock-daemon` 是什么**（源码形状）：

- **纯测试基建，不进生产代码**（`scripts/mock-daemon/README.md:3`「纯测试基建，不进生产代码」）。
- 按 device-protocol.json 生成的 **WS 夹具服务器**，复制桌面 daemon 的握手/订阅/推送/续传/审批命令，供 mobile 连接层**联调**（配对 → 握手 → 订阅 → 收夹具事件 → 收回执 → 断线重连续传；`README.md:9-11`）。
- 实现：`server.ts`/`connection.ts`/`commands.ts`/`state.ts`/`envelope.ts` + `fixtures/*`（approval/run/cache 三个夹具场景）。
- 与真实 daemon 的关系：mock **不验签、明文 ws、不落盘、内存态**（`README.md:88-94` 明确边界）；真实桌面 daemon 才有 HMAC 验签 + wss TLS（D5 红线）。

**定性**：mock-daemon 是「**协议契约的联调夹具**」，不是 mobile 应该长期依赖的本体；mobile 生产面向 = 真实桌面 daemon。mock 的价值 = 隔离桌面未就绪时移动端先行联调。

## ⑤ 收敛方向建议

### 5.0 先澄清「三端不是同一类 app」

关键认知：**crish-desktop 与 crish-mobile 不是「同一产品的两个平台壳」，而是「引擎的两种消费形态」**：

|                   | crish-desktop                     | crish-mobile                                                  |
| ----------------- | --------------------------------- | ------------------------------------------------------------- |
| 引擎关系          | **同进程宿主**（桌面即引擎进程）  | **远程客户端**（连桌面 daemon）                               |
| 事件事实源        | 本地 events 表（Rust `conex-db`） | **远端**桌面 daemon events 表（经 device-protocol 镜像/续传） |
| 我/主控的核心定位 | 完整工作区 + 编辑器 + 扩展        | 审批遥控 + 监控 + 轻量会话查看                                |

因此「mobile 定位为同核心模型的不同壳」**不完全成立**——mobile 根本不是「壳」，它是**消费同一事件流的一个独立进程客户端**。它已经共享了「事件流契约」= `device-protocol.json` → `shared-types/generated/device` + `engine`。

### 5.1 mobile 定位建议：**「同核心模型的异步远端投影消费者」，而非「独立演化」**

推荐方向（供决策）：

- **主张**：mobile 应定位为**「核心模型（事件流契约 + created 类型 + 投影原语）的远端消费者」**，**共享事件流契约 + 类型 + 投影逻辑，UI 各自**。理由：
  1. mobile 已在共享最正确的东西：`device-protocol` / `engine` 契约（generated）。
  2. mobile 的事件消费逻辑（eventReducers/eventMappers/FeedBridge → derived stores）与桌面 chat-bridge 是重复面，但**各自绑定到不同的传输**（远程 WS/信封 vs 本地 broadcast）——**共享的应是「事件→投影」的纯逻辑 + 契约**,而非 transport。
  3. mobile 无手写消息类型，天然贴合「前端类型收敛」纪律；只需把「容错 readString」收敛为「generated 契约结构」。

- **独立演化（反面）**：若让 mobile 独立演化，则事件解析/映射/续传逻辑会继续与桌面分叉，重新制造 7 层类型式漂移。**不推荐**。

**具体收敛动作（最小集）**：

- **共享「事件→投影」纯函数层**：把 mobile `eventReducers`（ring buffer/游标/去重/过滤，纯函数）+ `eventMappers`（type→route）与桌面的事件消费逻辑中**transport 无关的部分**抽入某个 shared 包（候选 `shared-utils` 或新建 `shared-projection`），两端共用。产出一个「统一事件消费/投影原语」——这是收敛战役 §3「单一时间线投影」的多端落实。
- **事件体类型化（mobile 关键改法）**：mobile 目前 `readString('text')` 容错读取是类型化过弱。收敛到 `generated/engine/parser`（`parseEngineEvent`，桌面已用）可为事件体提供结构校验，消除「undefined 静默回退」的隐性风险，同时避免重建第二套消息类型。

### 5.2 agent-workbench 定位建议：**「调试/开发宿主壳」，不并入 desktop**

- **主张**：agent-workbench 应定位为「**引擎宿主 + 调试/开发壳**」，**保持独立，但不得扩散业务逻辑**。
- 依据：
  1. **它已经是「壳」**：`dev/build` 脚本委托 crish-desktop 前端（`package.json:9-10`）；自己的 `src/` 只有 `workbench-contract` 契约类型、`background-tasks`、`task-controller`、`tauri-command-registry`（调试型）。
  2. **它是移动端 daemon 的宿主**：`src-tauri/src/server/*` 的多端网关 + `main.rs` 装配在 workbench 壳内。**并入 desktop 会让「远程 daemon 网关」与「desktop 前端」耦合**，破坏「壳层薄、业务逻辑在核心/投影」的分层（core 模型 §5：壳层禁止业务逻辑）。
  3. 但 00 草案点名 **src-tauri 105k 行是「壳层禁止业务逻辑」的反例**（`00-核心逻辑模型草案.md §5`）。收敛方向是**把多端 daemon / 命令桥接视为「扩展/服务层」而非壳层业务逻辑**——daemon 网关应作为独立服务组件（可独立测试、独立启停），而非散在 Tauri 命令注册里；`server/` 模块已是良好隔离（`mod.rs:26-29` 注明「除 conex-types 与 fanout 外零 crate:: 内部引用」）。

- **mobile + workbench 的关系**：workbench 托管 daemon，mobile 消费 daemon —— 二者通过 `device-protocol` 契约天然对偶，无需合并。

### 5.3 多端收敛的最小共享面建议

收敛战役应对多端收敛的落点建议（按共享优先级）：

1. **事件流契约（已达成，保持 + 固化）**：`device-protocol.json` + `engine-events.json` → `shared-types/generated/device` + `engine`。**这是当前唯一、且正确的共享面，必须继续保持为唯一真源**（禁第二套）。
2. **generated 类型（已达成，扩展用法）**：mobile 补用 `parseEngineEvent`（从 `generated/engine/parser`）给事件体加结构校验；两端统一事件信封解析。
3. **投影层（待收敛，最大收益）**：mobile `eventReducers`/`eventMappers` 的纯函数部分 + 桌面事件消费映射，抽成**共享投影原语**（transport 无关）。这是收敛「事件流 → 投影 store → view model → 原子组件」链条里 mobile 当前已经做对、桌面反而更散的部分。
4. **原子组件基座（待评估）**：mobile 有 `presentation/components/ui/*`；桌面有 `ui/` 原子层。跨 RN/Web 无法直接复用 DOM 原子组件，但**设计 token/样式契约**与**投影 view-model 的 shape** 可共享。评估是否下沉「视图模型 shape 契约」（如 `AssistantTimelineItem` 的跨端共享抽象）而非共享组件本体。

**不建议在多端强行共享**：block-paper/editor-kit（桌面编辑器域，mobile 无此能力）、shared-utils（当前仅桌面用，mobile 无用例，不强行引入）。

## ⑥ 决策建议

供主控与用户定夺，按「效果完整度 → 正确性 → 可验证性 → 与已锁定契约一致」排序。

1. **mobile 定位 = 「同核心模型的远端事件流消费者」**（异步、经 device-protocol 连桌面 daemon）。**不独立演化**，否则事件/投影逻辑再度分叉。✅ 与核心模型不变量 1/2/3（事件流唯一事实源、投影派生、单路径）一致。

2. **接入共享投影原语**：把 mobile `eventReducers`/`eventMappers` 纯函数部分与桌面事件消费映射抽入 shared 包（候选 `shared-utils` 或新建 `shared-projection`），两端共用「事件→store 分派」逻辑。**最大收敛收益**，且 mobile 这段代码已经是「投影派生」的正确范例，值得作为多端共享基准。

3. **mobile 事件体类型化（补钙）**：mobile 从「容错 readString」收敛到 `generated/engine/parser` 结构校验。消除「类型化过弱」，同时不重建第二套消息类型。

4. **agent-workbench = 「引擎宿主 + 调试/开发壳」**，**保持独立、不并入 desktop**；但将 `src-tauri` 中多端 daemon/命令桥接归入「服务/扩展层」削减「壳层业务逻辑」反例（00 草案 §5 点名 105k 反例的收口方向）。

5. **mobile events 表物理删除反例处置**：
   - 维持「本地 events 表是**镜像/缓存**，事实源在桌面 daemon」的语义，同时 `deleteOlderThan` / `runCleanup`（events 窗口物理删除）**在接入事件持久化时改造成「逻辑截断/墓碑」语义或明确「缓存回收不算时间线删除」**；
   - 更优先的**架构级解法**：mobile **不要**把「离线可用」建立在「本地 events 表完整重放」上——改用**桌面 daemon 续传（events.resume）为补充**，本地 events 表仅作有限缓存（它已是该语义）。

6. **共享面优先级落地**：事件流契约（保持不变）＞ generated 类型（mobile 补 parseEngineEvent）＞ 投影原语（新收敛）＞ 原子 view-model shape 契约（评估下沉，不共享 RN/Web 组件本体）。block-paper/editor-kit/shared-utils 当前**不强行为 mobile 引入**。
