# Pi Agent 核心设计模型审计

> 战役：`input-stream-consolidation`（统一输入流收敛）
> 参考仓库：`reference/pi`（earendil-works/pi-mono）
> 性质：**只读源码形状审计**，未运行真机验证（未 `npm run build` / `npm test` / 起服务）。所有结论基于 `packages/` 源码静态阅读，标注为「源码形状」；涉及行为性断言已尽量以文件内守卫逻辑为准。
> 目标：提炼 Pi 的核心设计模型（agent 运行时 / 事件-消息-reducer / 会话持久化 / 扩展机制 / 协议服务器 / 前端结构），与我们的「事件流唯一时间线 + 投影派生」模型对比，产出可借鉴清单。
> 日期：2026-09

---

## 0. 一句话结论（TL;DR）

Pi **不是**严格「唯一事件流 + 投影派生」，而是三套并存、职责分明的存储/事件模型：

1. **`SessionStorage`（Entry 流 + LaneRecord 日志双写）**——这才是与我们的「唯一时间线」最接近的部分；
2. **纯函数 `reduceLaneState` 做「派生投影」**——等价于我们的投影，但只重建 **单条 lane 的编排状态**（不是全部会话 UI 状态），且带强校验（`validateRecordLog` 拒腐）；
3. **协议层走「快照为真 + 增量 progress」**（`SessionSnapshot` + `TranscriptProgress`），而非重放事件流。

核心差异一句话：**Pi 把「会话树数据」与「一回排程的控制日志」分开持久化（entries vs records），投影只负责控制状态，UI 靠服务端主动广播快照**；我们的「唯一事件流 + 投影」则把两者都追求收敛为一条带类型的时间线。Pi 的多源（entry 流 / record 日志 / 快照 / JSONL 会话文件并存）反而暴露了「单一时间线」在实操中会被拆解的分布压力。

## 2. Agent 运行时轮转

### 2.1 低层循环 `agent-loop.ts`（`runLoop`，agent-loop.ts:155-275）

轮转结构是**两层循环**，不是单层「输入→工具→状态→输出」：

- **内层 `while (hasMoreToolCalls || pendingMessages.length) `**：一轮 = 注入排队消息 → `streamAssistantResponse()`（调 LLM 拿到 `AssistantMessage`）→ 若含 toolCall 则执行一批工具 → 把 `toolResult` 消息 push 进 context → `prepareNextTurn`（可换模型/thinking/上下文）→ `shouldStopAfterTurn` 判断是否提前停 → 重取 `getSteeringMessages()`。`hasMoreToolCalls` 即为「还要不要再来一个 assistant 回合」的终止信号。
- **外层 `while(true)`**：内层因无工具、无 steering 而要停时，再查 `getFollowUpMessages()`；有则注入继续，无则 `break` 结束。

**输入注入三类、语义不同**（types.ts:244-257）：

- `prompt`（初始，进入 `runAgentLoop`）
- `getSteeringMessages`（运行中插队，**当前回合的工具调用不跳过**）
- `getFollowUpMessages`（agent 本要停下时才喂，继续新一轮）
- `pendingMessages`（启动时先查一次，防「排队时用户已输入」）

这对应我们的「输入流可随时插入 + 对正在运行的轮转做 steer」——非常接近我们的「统一输入流 + 时间线插入」诉求。

**状态管理**：低层循环是无状态的纯交互——所有状态持有在`AgentContext`/`config`（回调集合）里，事件经 `emit`（`AgentEventSink`）流出；`AgentEvent` 是扁平事件联合（types.ts:428-443）：`agent_start/end`、`turn_start/end`、`message_start/update/end`、`tool_execution_start/update/end`。**它是「事件源」但不是「重放源」**——事件仅用于 UI，不驱动重放；持久化由上层 harness 负责。

**终止语义**：`stopReason`（`stop`/`length`/`toolUse`/`error`/`aborted`/`deferred`）决定单回合收敛；`shouldStopAfterTurn` 与 followUp 队列决定 run 级终止；`section 2.2` 的 harness 又加一层「run 定型为 completed/aborted/failed」。

### 2.2 高层 harness `harness/agent-harness.ts`

- 面向并发/排队：每个 `AgentLane`（lane=车道）串行跑 `run/compaction/navigation` 三类操作，带 `steer/followUp/nextRun` 三个输入队列（`QueueMode: all | one-at-a-time`）。
- 提供 `ResultValue<…, Rejected>` 信封（`agent-harness.ts:105-131`），错误均编码为 `TaggedError`（`*Rejected`），不靠 throw——**可组合、可恢复、可区分**。
- **注意**：当前 `AgentHarness` 类的方法绝大多数是 `unavailable`（抛 `HarnessNotImplemented`）——即**接口/骨架已完整定义，调度内核未实装**（源码形状；与 `reducer.ts` 的完整实现形成反差）。真正的排程内核（`reduceLaneState` + 单写者 record 协议）在 `reducer.ts` 已可见其模型。

### 2.3 `stream-fn.ts`

极薄的依赖注入点：`setDefaultStreamFn/getDefaultStreamFn`（stream-fn.ts:11-19）。`StreamFn: (model, context, options?) => AssistantMessageEventStream`，契约是**不得 throw、不得拒 promise**，失败必须编码为事件流 + 最终 `AssistantMessage.stopReason="error|aborted"`（types.ts:28-32）。这是「低层引擎不依赖提供商目录」的解耦手段。

## 3. 事件 / 消息 / reducer 模型

### 3.1 事件层

**两类事件**：

- 低层低粒度：`AgentEvent`（agent-loop 流出，用于 UI/监视）。
- 高层进程事件：`HarnessEvent = RunStartEvent | RunEndEvent`（harness/events.ts:15），经 `HarnessEventBus`（监听器 + `watch()` 快照缓冲，events.ts:37-102）。
- 服务器推送：`ServerEvent = server_snapshot | session_snapshot | session_progress | session_removed`（schemas.ts:400-410）。
- coding-agent 扩展事件：极丰富联合 `ExtensionEvent`（约 30 类），覆盖 lifecycle/tool/模型/输入/会话。

**事件≠唯一事实**：Pi 的事件是「通知/观察」，不是「重放源」。真正的持久化事实在 `Entry` 与 `LaneRecord`（见 §4），UI 真值走 **快照广播**。

### 3.2 消息/消息类型（`harness/messages.ts` + `types.ts`）

- `AgentMessage = Message | CustomAgentMessages[keyof]`（types.ts:325），即标准 `user/assistant/toolResult` 联合 **+ 应用可扩展的自定义 role**（通过 TS `declare module` 声明合并，messages.ts:54-61）。
- 内置自定义 role：`bashExecution`、`custom`、`branchSummary`、`compactionSummary`。
- `convertToLlm`（messages.ts:124-167）把自定义消息**投影回 LLM 能吃的 `Message[]`**：bashExecution→user、custom→user、branchSummary→user（块状 `<summary>`）、compactionSummary→user；无 LLM 代表的（如 UI-only notification）直接过滤。
- **增量/流式表达**：`AssistantMessage.status ∈ streaming|complete|error|aborted` + `TranscriptProgress.item_started/assistant_delta/item_updated/item_finished`（schemas.ts:204-231）。协议层快照仍然是权威，progress 只是「已标准化增量」供前端平滑渲染。

### 3.3 reducer（`harness/reducer.ts`）——核心可借鉴点

`reduceLaneState(input: LaneReductionInput): LaneReductionResult`（reducer.ts:506-667）是**纯函数**：给定有界恢复切片（`RecordLogSlice` + 当前 leaf + 自有 entries + 配置 entries + 默认值），重建单个 lane 的完整编排状态 `LaneState`（openOperation / step / toolBatch / pendingSteer / pendingFollowUp / pendingWrites / pendingNextRun / deferred / overflowRecoveryUsed / newestOwn / targets / terminalFailure）。

关键设计：

1. **先 `validateRecordLog()` 拒腐**（reducer.ts:312-390）：对 `records` 按 seq 排序做不变量校验——单开操作、记录不得晚于 finish、attempt 连续、toolCall 与 assistant 序位一致、无重复工具调用、provisioned 条目与持久化内容一致、defer 句柄存在、abort 后不得入队。「单写者协议不可能产生的状态」判断为 **corruption 并抛 `RecordLogCorruption`，拒绝修复/继续**（reducer.ts:18-34 注释）。这是与「事件流重放」最大的差异红利：**它把恢复逻辑的输入约束做成硬不变量，腐化立即可见**。
2. **`deriveEffectiveConfiguration`**（reducer.ts:400-427）：按 seq 扫 flow 条目（`model_change`/`thinking_level_change`/`active_tools_change`/assistant 消息）投影出**有效模型/思考/工具配置**——这是比「派生 UI 状态」更细的「派生运行配置」。
3. 显式 `overflowRecoveryUsed`：识别「上下文溢出 → 压缩 → 重试当前回合」的恢复路径（reducer.ts:587-593）。

**结论：Pi 的 reducer 等价于「我们的投影」，但它只投影到「单 lane 排程可恢复状态」并做腐化门禁**，而我们把「投影」用于整个会话的 UI/派生状态。Pi 的「reducer 输入自带完整校验」是值得我们投影层强化的。

## 4. 会话持久化 / 快照 / 压缩 / 分支

### 4.1 存储模型（harness/session/types.ts + sqlite 迁移）

**每 session 两套互不相同的持久化对象**：

```
Entry   （数据/事实，按 seq 单调）——"时间线/事件"
    └─ type: message | model_change | thinking_level_change
              | active_tools_change | compaction | branch_summary | custom
    └─ 携带: id, seq(共享序列), parentId(所属 lane 的 leaf), timestamp
    └─ message/model_change/... 都带自身语义负载

LaneRecord（控制/排程日志，按 seq 单调）——"操作日志"
    └─ type: operation_started | abort_requested | operation_finished
              | step_attempt | tool_started | queue_enqueued
              | queue_cancelled | write_deferred | usage
    └─ 携带: id, seq, lane, timestamp(多态, 某些带 runId/target/attempt)
```

- **Entry 流有 `parentId`** → 天然形成**分支树**（`findEntriesOnBranch({start, stopAt*})` 沿 parentId 回溯）；`seq` 是**跨类型共享、全局单调**的（types.ts:14-20）。
- sqlite schema（001_initial.sql）：
  - `entries(session_id, seq, id, parent_id, type, timestamp, payload)`，PK `(session,id)`、UNIQUE `(session,seq)`；
  - `records(session_id, seq, id, lane, run_id, type, op_kind, timestamp, payload)`，PK `(session,id)`、UNIQUE `(session,seq)`；
  - **`branch_entries(session_id, branch_id, entry_id, entry_seq, entry_type, custom_type)`** ——「派生分支缓存」，注释明言「parent 链才是 canonical，此表仅为廉价分支扫描」（001_initial.sql:43-56）——**这就是我们「投影缓存」的直接先例**；
  - `branch_tips`、`lanes(leaf_id, open_operation_id)`、`lane_moves`、`facts`（全局 name/label）、`session_stats`、`session_sequences`、**`writer_leases(owner_id, fence, expires_at_ms)`**（每次会话写租借 + fence 防过期写者越权）。

**这是「事件追加日志 + 派生缓存 + 写者租借」的成熟落点**，与我们的「唯一时间线 + 投影派生」高度同源。

### 4.2 快照/检查点（server/sessions.ts + snapshots.ts + protocol）

- 服务端 `LiveSessionManager` 持有 `runtime`，`runtime.snapshot()` 生成 `SessionSnapshot`（`phase/model/thinkingLevel/transcript/revision/queuedSteer...`，schemas.ts:241-258）。
- `broadcastSnapshot`（sessions.ts:293-298）在**每次运行时变更事件后**主动向其连接的连接推送 `session_snapshot`。
- `ServerSnapshotPublisher`（snapshots.ts）给**所有 ready 连接**广播 `server_snapshot`（含 serverId/协议版本/revision/sessions/models），`revision` 递增去重。
- **协议层：快照是权威（comments 明言 "Snapshots remain authoritative"），`session_progress` 只是增量**（schemas.ts:204）。

### 4.3 压缩（harness/compaction/compaction.ts）

- 触发：`shouldCompact`（threshold 判断）+ `reserveTokens` + `keepRecentTokens`（compaction.ts:248-250）。
- `prepareCompaction`/`findCutPoint` 确定切点，切点符合语义：不砍 toolResult、优先保持在 user 消息、可「split turn」（前缀单独摘要、后缀保留）。压缩结果写一个 **`compaction` Entry**，带 `summary/retainedTail/tokensBefore/details`.
- 摘要提示词是「结构化 context checkpoint」（Goal/Constraints/Progress/KeyDecisions/NextSteps/CriticalContext），`UPDATE_SUMMARIZATION_PROMPT` 支持**迭代式续写**（前一次 summary + 新消息）。
- `buildSessionContext`（session/context.ts:45-57）在投影时把**历史压缩为一个 `compactionSummary` 消息 + 保留 tail**，等价于“把一段历史折叠进单条时间线条目”。
- **overflow recovery**：上下文溢出时压缩后重试当前回合（reducer 的 `overflowRecoveryUsed`）。

### 4.4 分支摘要（harness/compaction/branch-summarization.ts）

- 分支（branch）概念：`moveLane/要`把 leaf 移到更早条目做新分支，改用 `branch()`/`branchWithSummary()`（session-manager.ts:1355-1395）。
- `collectEntriesForBranchSummary`（branch-summarization.ts:82-111）：找**新旧 leaf 的公共祖先**（commonAncestor），收集被放弃分支的 entries。
- `generateBranchSummary` 生成结构化分支摘要，写 `branch_summary` Entry（记录 `fromId`）。
- 回访时这些 summary 被重新投影成 `branchSummary` 消息进 LLM 上下文（session/context.ts:81-83）。

## 5. 扩展机制（skills 与 tools）

### 5.1 Skills（harness/skills.ts）

- **Skills = 可加载的 Markdown + YAML frontmatter 指令块**（不是代码插件）：`loadSkills` 递归扫描目录，识别每目录 `SKILL.md` 或根级 `.md`（skills.ts:49-175），frontmatter 提供 `name/description/disable-model-invocation`。
- 忽略文件（`.gitignore/.ignore/.fdignore`）参与裁剪；返回诊断（非法元数据/读取失败）。
- 形式：`Skill = { name, description, content(正文), filePath, disableModelInvocation }`；调用时 `formatSkillInvocation` 把它变成一个带 `<skill name=...>` 标签的能力说明注入提示词（skills.ts:38-41）。
- **Skills 是「静态能力账本」**：内容是给模型看的知识/规范，**本身不含可执行逻辑**；可执行能力由 Tools 承担。

### 5.2 Tools（types.ts:386-409 AgentTool）

`AgentTool extends Tool`，额外：`label`、`prepareArguments`(兼容 shim)、`execute(toolCallId, params, signal, onUpdate)`→Promise，`executionMode: sequential|parallel`。工具执行支持**流式部分结果**（`onUpdate`，types.ts:383-384）与 `terminate` 提前终止整批。

### 5.3 自扩展（coding-agent）

「自扩展」= `ExtensionAPI`（core/extensions/types.ts:1198-1437）注册能力 + 订阅事件：

- **注册**：`registerTool`（TypeBox schema + 渲染工厂）、`registerCommand`、`registerShortcut`、`registerFlag`、`registerProvider`（可注入模型提供商）、`registerMessageRenderer`/`registerMarkdownTransformer`/`registerEntryRenderer`。
- **订阅**：`api.on(type, handler)` 覆盖项目信任/会话/上下文/请求头/响应/回合/消息/工具/模型/输入等 ~30 类事件，handler 可**返回结构化的覆盖结果**（如 `ToolCallEventResult`, 扩展可得返回值）。
- **UI 扩展面极广**：`ExtensionUIContext` 可自定义 header/footer/editor/overlay/autocomplete/theme/widget。
- 事件**可取消/可改写**（session_before_fork/compact/tree、tool_call、message_end、before_agent_start 均支持返回值），形成「观察 + 拦截 + 替换」三层。

**对照**：Pi 的 skills ≈ 我们的「静态可扩展能力」（知识与规范注入）；Pi 的 tools + registerTool ≈ 我们的「可执行扩展点」；但 Pi 的「订阅可拦截事件的扩展 SDK」比我们更接近「事件反射式扩展点」。**我们的「带类型扩展点」若想对齐，应参考其 `before_*` 事件可返回 Result 的拦截语义，而非只用后置通知。**

## 6. 协议与服务器

### 6.1 协议层（packages/protocol）

- **不是 ACP，不是 MCP**（grep 无命中）。是**自研 framed-CBOR + TypeBox 校验**：
  - `framing`：4 字节大端长度前缀 + 64KB 块累积，`FrameDecoder` 增量拆帧（framing.ts:58-165）。
  - `codec`：CBOR 编解码前后各过一遍 `TypeBox` schema 校验（`Check`），并带 protocol value 消毒（codec.ts:41-53）。
  - `schemas`：TypeBox 定义全部消息（ClientHello / RequestEnvelope / ResponseEnvelope / EventEnvelope / Command / CommandResult / ServerEvent），`PROTOCOL_VERSION=1`。
- **契约形态**：`Client → Request(Command) → Server → Response(CommandResult 携带最新 Snapshot)` + 服务器**异步 `Event(server_snapshot/session_snapshot/session_progress)` 推送**。命令：`list/create/attach/detach/prompt/steer/abort/set_model/set_thinking`。
- 与我们的 **IPC commandMap / 事件桥**对照：Pi 是「命令→响应（携带快照）+ 主动事件」线性模型，**无 request 对应也能靠事件推进 UI**；我们的 `IPC commandMap` 求值调用、`事件桥` 推状态——形态相近，但 Pi 把「invoke 结果=最新快照」与「快照广播带 revision 去重」做了统一，值得借鉴。

### 6.2 服务器编组（server/connection.ts / listener.ts / protocol.ts / sessions.ts / snapshots.ts）

- `ByteConnection` + `ConnectionState(awaitingHello→handshaking→ready→closing)`；握手校验 `ClientHello.version`.
- `LiveSessionManager`：session 的**惰性 open、活跃连接绑定、无连接且 idle 时 dispose**（sessions.ts:320-345）；`operationCount` 守卫并发 dispose。
- 快照作为每次变更的「事实如何传到前端」的唯一通道（非事件重放）。

## 7. 前端 / UI 结构

### 7.1 `packages/tui`：底层终端组件库

纯组件原语：`box / text / stack / v-stack / h-stack / spacer / editor / input / scroll-view / select-list / settings-list / markdown / loader / image / truncated-text` 等（39 个 .ts）。**无业务，只有绘制与布局**——Rust/render 层解耦。

### 7.2 `coding-agent/modes/interactive`：产品级转录 UI

大量「按语义」组件：`assistant-message / bash-execution / branch-summary-message / compaction-summary-message / custom-message / custom-entry / skill-invocation-message / tool-execution / splash-selector / footer / model-selector / session-selector / tree-selector / trust-selector / diff...`。**组件化程度高，每种 Entry/Message 类型都有独立 render 组件**。

### 7.3 `packages/client`：前端-服务端状态同步

`ClientState`（state.ts）是**快照缓存 + revision 去重**：`applyServerSnapshot / applySessionSnapshot` 用 `revision` 丢弃过期快照（state.ts:100-113），`restoreSessionSnapshot` 支持失活 session 回填。事件：`session_progress` 为增量，`session_snapshot` 为权威。`SessionHandle`（session-handle.ts）把命令调用封装成 `prompt/steer/abort/...` 返回最新 `SessionSnapshot`——**调用即取回真值**。

## 8. 与「事件流唯一时间线 + 投影」模型的异同

| 维度                       | Pi Harness                                                                                               | 我们的「唯一事件流时间线 + 投影」                               | 异同                                                                                              |
| -------------------------- | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| **单一事实源**             | **不是唯一**：Entry 流（数据）+ LaneRecord 日志（控制）+ BranchCache（派生）+ Snapshot（UI）并存         | 设为目标：一切皆带类型标记的输入文本 + 唯一时间线，投影派生全部 | ✗ Pi 把「数据事实」「控制日志」「派生缓存」「UI 快照」分列四套持久化                              |
| **reducer 是否等价于投影** | **是，但更窄更强**：`reduceLaneState` 只投影单个 lane 的排程可恢复状态，且先 `validateRecordLog` 拒腐    | 投影派生「整个会话的派生状态」                                  | △ Pi 的 reducer 是「投影」的子集但加腐化门禁——**这是可为我们的投影层借鉴的「先验证再派生」**      |
| **append-only 时间线**     | Entry 是 append-only 树（`parentId` 建分支、`seq` 全局单调）                                             | 唯一时间线 append-only                                          | ✓ 同构，**分支树 = parentId 链**最贴近我们的「时间线分叉」诉求                                    |
| **输入流语义**             | `steer/followUp/nextRun` 三类队列 + run 时注入（getSteering/FollowUp）                                   | 统一输入流 + 时间线插入                                         | △ Pi 把「运行中插队」「停下后继续」「开局预提交」分成三类——我们的统一流需要类似的**插入时机语义** |
| **服务端与前端同步**       | 快照权威 + 增量 progress + revision 去重                                                                 | 事件桥推状态                                                    | ✗ Pi 不重放事件流，直接发整快照；我们在做事件流时亦可保留「快照 + revision」兜底                  |
| **扩展点**                 | skills（静态账本）+ registerTool/Command/Provider/...（运行时注册）+ subscribe 事件**可拦截返回 Result** | 带类型扩展点 + 事件桥                                           | △ 我们缺 `before_*` **可拦截并返回覆盖**的扩展语义                                                |
| **恢复/崩溃**              | `findOpenOperations(limit:2)` 判定 idle/suspended/corrupt + writer lease + fence                         | 时间线重放                                                      | ✓ Pi 的「租借 + fence + 腐化门禁」值得引入我们的持久化                                            |

**本质差异**：Pi 务实承认「一条时间线装不下排程、UI 与数据三种关注」，于是拆成 entries（数据）/records（控制）/cache（派生）/snapshot（UI）；我们理论上是把它们全收敛到「唯一带类型输入流」。**借鉴方向不是照抄四套，而是承认「投影前先验证、快照为真、控制日志与数据分离」是成熟系统在单一时间线下仍需保留的防护**。

## 9. 可借鉴清单（3–5 项）

1. **`validateRecordLog` 先校验再审，腐化即拒**（harness/reducer.ts:312-390）
   把「单写者恢复协议能产生的状态」做成硬不变量（单开操作/连续 attempt/tool 序位一致/无重复调用/abort 后不入队），恢复前逐项校验，**凡是不可能由正常写入产生的状态一律判 corruption 而非修复**。理由：我们的「唯一时间线重放」天然缺这道门禁；加入它能让时间线本身的脏数据在投影前被显式暴露，而不被静默派生掩盖。

2. **`SessionSnapshot` 权威 + `TranscriptProgress` 增量 + `revision` 去重**（packages/protocol/schemas.ts:204-258 + client/state.ts）
   前端同步不用「重放事件流」，而以「快照为真、增量 progress 平滑」。理由：即便我们坚持事件流为内部事实源，前端吞吐与重连一致性仍受益于「一次性发权威快照 + revision 去重 + 增量更新」。

3. **`before_*` 事件可返回结构化覆盖（拦截 + 替换）**的扩展点（coding-agent/core/extensions/types.ts）
   扩展 SDK 订阅事件时，许多 handler 返回 `{ cancel }` / `{ content, isError }` / `{ systemPrompt }` 等**结构化结果**，使扩展既能观察又能拦截改写。理由：比「只发事件、只读」的桥更接近真正的「可扩展能力注册」，且与我们的「带类型扩展点」天然契合。

4. **输入队列分 `steer / followUp / nextRun` 三态 + 空转 Drain 点**（agent/agent-loop.ts:170-274 + Harness 队列）
   区分「运行中立即插队」「运行要停才续跑」「下一 run 预提交」三种插入时机，并在 agent 自然停点统一 drain。理由：我们「统一输入流 + 时间线插入」需要先在**时机语义**上定型，否则流上所有输入都只能按同一优先级塞进去。

5. **`writer_leases + fence` 写者租借，防并发/过期写越权**（sqlite/001_initial.sql:117-122 + repo.ts）
   每次会话写需租借（owner+fence+expiry），`fence` 阻止过期 owner 在接管后继续写。理由：多 Agent / 多会话并行编辑同一时间线时，单一时间线的**串行写权必须物理保证**，租借+fence 是比「乐观并发控制」更硬的兜底。
