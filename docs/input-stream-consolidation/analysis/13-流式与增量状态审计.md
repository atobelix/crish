## ② 增量事件链路图（文字版）

### 2.1 message-delta 全链路（引擎 → 前端 → 组件）

```
【引擎侧】
session-loop streaming.rs:handle(:40)
  ├─ 实时轨（T09.1 双轨）：TextDelta/ThoughtDelta 逐帧到
  │    delta_to_message_event(:605)  →  AgentEvent::MessageDelta{block: Text|Thought}
  │    delta_sink.push（DeltaSink 实时桥，streaming.rs:117-129）
  │      └─ app:engine.rs BridgeDeltaSink → buffer.rs EventBuffer（DropClass=Soft）
  │           ↓ 立即 flush（bridge_priority 丢帧：高水位丢最早 delta 旧帧）
  │           ↓ 信封{type,runId,sequence:None,...} → TauriEmitter emit("workbench-run-event")
  └─ 收口轨：MessageEnd 后 commit_message_with_deltas(:581)
       → emit_message_deltas(:628) 逐块补发收口 message-delta（Text/Thought）
       → 经 LoopState.events → orchestrator drive → EventQueue.push
          （is_non_persistent → 不落库、不等待，events.rs:208-214；但照常入桥缓冲）
       → 同样广播到 workbench-run-event（03 §5.3 同构信封）

【前端侧】
apps/agent-workbench (tauri) --workbench-run-event--> frontend transport.onMessage
  → ConnectionLifecycle.ts:335 (state.unsub = transport.onMessage(onMessage))
  → chat-bridge/EventRouter.onMsg → dispatchEvent → engineDispatchTable
  → handlers/eventParser.ts:138 'message-delta' 归一化（+ 兼容 'text-delta' 别名 :145）
  → handlers/messageHandlers.ts:54 onMessageDelta
      └─ block.type='thought' → callbacks.onThought(assistantThought)（独立累积）
      └─ 否则 → callbacks.onChunk(deltaToSend)（正文增量拼接态）
  → hooks/chat-stream/useRunStreamingAssistant.ts（这些 callbacks 即流钩子）
      ├─ onChunk → renderBuffer.push / textBatcherRef.push
      ├─ onThought → thinkingBatcherRef.push
  → hooks/chat-stream/useStreamBatchers.ts（3 个 batcher：48ms interval 合并）
      ├─ textBatcher(:43)  → store/setStreamText     (streamingStore.ts:126)
      ├─ thinkingBatcher(:57)→ store/setStreamThinking(streamingStore.ts:138)
      └─ toolBatcher(:75)  → store/setStreamTool      (streamingStore.ts:157)
  → store/streamingStore.ts byKey[sessionId::messageId]（中间态 :124）
  → components/chat-message/MessageContent.tsx:138 useStreamingStore
      └─ applyStreamTextToMessage / applyStreamToolsToMessage (streamMessageViewModel.ts:21/67)
          └─ 与 SessionMessage 合并成展示视图模型
  → 正文组件 / 思考折叠（TimelineThoughtSection）
```

**关键结论**：引擎 `message-delta` 事件（实时轨 + 收口轨都被事件化发射）→ 前端确实有完整事件化链路到 streamingStore。但**正文/思考的「显示」最终是经 `onChunk`/`onThought` 回调喂给 batcher**，而非组件直接订阅事件——事件是被回调化后注入 store 的。`message-end` 经 `onMessageEnd`（messageHandlers.ts:88）做终态整段合并兜底。

### 2.2 message-end 全文兜底与增量丢失恢复

- **丢帧语义**：`buffer.rs` `DropClass::Soft` **唯一** = message-delta（buffer.rs:24-26、registry_drift 锁定）。高水位先丢最早 Soft 旧帧；`message-end` 是 `Critical`（永不丢，buffer.rs:242-256）。
- **兜底**：前端 `onMessageEnd`（messageHandlers.ts:88-147）收到 `message-end` 全文（`msg.blocks` + `content`），按 turnIndex 分段合并（G4），然后 `callbacks.onChunk(addedDelta)`——增量若在桥层被丢弃，此处以全文 diff 形式补到 `assistantText`，从而恢复。
- **事件策略**：`message-delta` = `Delta(可丢) + NoPersist(不落库) + Soft(桥丢帧)`（events.rs:1292/1317-1321）。`message-end` = `Critical + Persist + Critical`（catch-all :1406-1412）。

### 2.3 thought（思考）流现状

- **引擎**：思考确实是**流式增量**的——`delta_to_message_event(:612)` 把 `ProviderStreamEvent::ThoughtDelta` 映射为 `AgentEvent::MessageDelta { block: Thought, ... }`；收口轨 `emit_message_deltas` 同样逐 thought 块补发。**message-delta 携带 thought** ✔（events.rs:850-855 events_roundtrip 也覆盖了 thought block 硬依赖）。
- **前端**：`onMessageDelta` 遇 `block.type==='thought'` 走 `callbacks.onThought`（独立 `assistantThought` 累积，messageHandlers.ts:63-67），喂 `thinkingBatcher` → `setStreamThinking` → `byKey.thinking`。`onMessageEnd` 再把终态 thought 整段补合并（messageHandlers.ts:98-115）。
- **展示**：`ChatAssistantMessageRow.tsx:178-180` 读 `byKey.thinking`；`TimelineThoughtSection.tsx` 渲染思考折叠区，`isLive` 时展示 `ThinkingTimer`（秒表，ThinkingTimer.tsx:13-34）并自动追尾吸底（TimelineThoughtSection.tsx:65-73）；`ThoughtOutline`（thoughtWorker 产出大纲，非流式主线）做大纲导航。
- **交错**：**源码形状**来看，正文与思考在前端是**分域存储**（`text` 与 `thinking` 是 streamingStore 条目两个独立字段），**不是同一时间线交错体**；展示时 `timelineNormalizer`（04 审计轨 A）在 `SessionMessage` 层把 thought 块、text 块、tool 块交错成 `AssistantTimelineItem[]` 序列，但**实时流的 thinking 与 text 是分别累积的**，thinking 不会出现在 text 流的中间位置（先 thinking 段、后 text 段/或平行区）。真实交错形状（真跑未验）。

### 2.4 工具进度 ToolProgressUpdate

- **产生点**：`exec_single.rs:420-433` 将 `ToolProgress::Text/Custom` 入进度缓冲 → `ToolEvent::ToolProgress{call_id, update}`（tool_events.rs:110-113，`update: ToolProgressUpdate`，:112）；`executing_tools.rs:360-371` 翻译为 `AgentEvent::ToolUpdate`。
- **载荷**：`ToolProgressUpdate`（tool.rs:146-153）含 `text/json/metadata`；`metadata.kind` 字面量 `tool-progress`（Text 映射）/ `tool-args-delta`（**reserved 未发射**）/ `content-blocks`（reserved，engine-events.json:269-284）。
- **事件策略（重要）**：tool-update = `Critical + Persist + Critical`（engine-events.json:318-320；event_policy catch-all）。**不是 Delta+NoPersist**。「不进消息历史」指不进对话缓存前缀（executing_tools.rs:361-363 注释），但事件体**照常落 events 表**——tool-update 是**落库的**，与 task-output（Delta+NoPersist）等其它增量不同。
- **前端消费**：`onToolUpdate`（toolHandlers.ts:25-30）是**显式空实现**——tool-update 的 `update.text`（tool-progress）**没有任何 UI 落地**；只有 `tool-args-delta` 的预留解析器 `partialToolArgs.ts` 存在但未接线。**工具行的「运行中」状态来自 `tool-start`→`onToolStart`→`callbacks.onToolStart`→`upsertToolCall(status:'running')`（streamCallbacksInternals.ts:404-427 + useRunStreamingAssistant.ts:217-219），不是 tool-update。**

## ③ 状态生命周期盘点表

| 内容             | ongoing 表示（进行中）                                                                                                                                                                         | settled 表示（终态）                                                                                                                                                      | 落库语义                                                                                                                                                   |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **正文 text**    | 引擎实时轨 `message-delta.block.text`（Delta+NoPersist+Soft）→ 桥可丢 → 前端 `onChunk`→`byKey.text`（48ms batch）                                                                              | `message-end` 全文（Critical+Persist）→ 前端 `onMessageEnd` 整段合并 / `commitStreamToSession`（helpers.ts:197）写会话                                                    | delta 不落库；message-end 落库（events 表全文）                                                                                                            |
| **思考 thought** | 引擎 `message-delta.block.thought`（同 Delta 矩阵）→ 前端 `onThought`→`byKey.thinking`                                                                                                         | `message-end` 全文 thought 块合并（messageHandlers.ts:98-115）→ `updateMessageThinking`                                                                                   | delta 不落库；终态 thought 随 message-end 落库                                                                                                             |
| **工具 tool**    | **两源**：① `tool-start`（Critical+Persist）→ `byKey.tools[id]`（StreamToolLive，running 态，streamingStore.ts:15-25）for 渲染；② `tool-update` 进度（Critical+Persist）→ **前端空实现不展示** | `tool-end`（Critical+Persist）→ `onToolEnd`→`commitToolPatchToSession` 写终态 status（success/error）+ `clearStreamTool`（useStreamBatchers.ts:82-85 即时态直通 session） | tool-start/end/update 全落库；中间运行态 rows 仅存在前端 streamingStore（`applyStreamToolsToMessage` 保证不覆盖已落库终态，streamMessageViewModel.ts:105） |
| **run 级**       | `runs` 表 status ∈ {queued, initializing, running, awaiting-approval, completing, cancelling}（conex-db runs.rs:40-52；schema.rs:89）；agent-run 事件 `agent-start`（Critical+Persist）        | `runs.status` ∈ {completed, failed, cancelled}；`run-terminal`（Critical+Persist，唯一终态事件，orchestrator lib.rs:7）                                                   | run 行随状态机更新落库（`INSERT OR REPLACE`, runs.rs:126）；agent-start/end、run-terminal 事件全部落库                                                     |

**NoPersist（不落库）事件清单**（event_policy，events.rs:1291-1313）：

- **message-delta**（+ thought-delta，Delta+NoPersist+Soft）
- subagent progress（Delta+NoPersist+Critical）、subagent message/tool（Soft+Persist，落库）
- task-output / task-heartbeat（Delta+NoPersist）、task-suspicious（Soft+NoPersist）
- timer-fired/cron-fired（Critical+NoPersist）、timer-cancelled（Soft+NoPersist）
- D-03 观测九事件（steering-evaluated 等，Delta+NoPersist）

**结论**：只有「增量事件（delta / progress 类）」走 NoPersist；text/thinking 增量不落库，工具进度 `tool-update` 虽属增量**却意外落库**（不符合 NoPersist 语义，见缺口 G3）。

## ⑤ 对核心模型「节点状态维度」的验证与建议

### 5.1 现状基础（模型不变量 6 ◀ 已验证部分）

- ✅ **增量/终态二分已有落地**：`BackpressureLevel(Delta/Soft/Critical)` + `PersistenceDecision(Persist/NoPersist)` + `DropClass(Soft/Critical)` 三决策单点（events.rs:183-243 → `event_policy` :1313）。text/thought 增量 = Delta+NoPersist（可丢不落库），终态 message-end = Critical+Persist（必达落库）——**正是「进行中=增量事件、终态=必达事件」的引擎侧二分**。
- ✅ **进行中由增量事件表达**：message-delta（text/thought）实时轨 + 收口轨双轨事件化，前端 streamingStore byKey 是增量中间态（streamingStore.ts:37）。
- ✅ **终态由必达事件表达**：message-end 全文兜底、Critical 不丢；run-terminal 唯一终态事件。
- ⚠️ **部分成立**：thinking/正文/工具运行态三者的「ongoing」在前端都以 streamingStore 中间态表示；但**工具进度不展示**（G1）、**工具增量却落库**（G2）。

### 5.2 主要缺口（模型「节点状态维度」落地差距）

1. **缺统一的「节点」抽象**：当前是事件 + 前端分域字段（text/thinking/tools 各自 store 字段），没有统一节点 `{type, state(ongoing|settled)}`。模型的「节点有状态生命周期」需要通过统一节点结构承载三类内容的 ongoing 态。
2. **工具进度的展示缺口**：引擎有 `ToolProgressUpdate` 增量事件（S1），但前端无 UI 消费——**工具「进行中」没有真正流式**，只取决于 tool-start 占位。这是统一模型「工具输出可流式展示」的最大落地缺口。
3. **工具增量落库语义错位**：tool-update 当前 Persist，与「增量=NoPersist」的模型相悖，需决策归并（Delta 类还是保持 Critical 类）。

### 5.3 建议（供详案执行参考，非本文落地）

1. **统一节点状态模型**：把 streamingStore 的 `byKey` 从「text/thinking/tools 三字段」重构为「`nodes: Array<Node{id, seq, ts, type, state: ongoing|settled, payload}>`」，增量事件按节点 seq 写入，解决 G3/G4 的撕裂与分域。
2. **工具进度消费接线**：前端 `onToolUpdate` 落地展示 `update.text`（tool-progress），把 tool 行「运行中」从占位升级为真进度；同时把 `tool-update` 持久化决策按模型归一到 NoPersist（G1/G2）。
3. **run 级进中间态事件化**：将 runs 状态机（awaiting-approval / completing / cancelling 等）以事件形式（Critical）广播，前端 `msg.status` 改成事件驱动（G6）。
4. **思考展示态事件化**：thinking 已事件流式化；`ThinkingTimer` 时长属可派生量（可由 thought 首帧/末帧时间戳派生），`ThoughtOutline` 可后置为投影（G5 属展示衍生，允许保留前端派生但需声明非事实源）。
5. **写文件过程**：为有状态非流式过程补「进度类」tool-update（或独立 progress 事件），承载不变量 6「写文件等过程有状态但不流式展示（只展示状态/进度）」的展示面（G7）。
