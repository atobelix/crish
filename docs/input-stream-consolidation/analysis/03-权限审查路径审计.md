## ③ 问题清单

### P1（关键）前端 commandPermissions 与引擎 approval **重复/冲突**：两套风险分类引擎并存

- **证据**：
  - 引擎命令风险分类：`conex_sandbox::semantics::analyze` + `CommandGatekeeper` + `PermissionDecisionEngine::evaluate_command`（`agent-tools/src/permission.rs:196-287`；`tools/shell.rs:228-241`）；命令回退护栏 `revert_policy.gate_verdict_command`（`exec_verdict.rs:104-113`）。
  - 前端命令风险分类：`commandPermissions.ts` 自建 `HARDLINE/DESTRUCTIVE/EXTERNAL/NETWORK/WRITE/SAFE_READ` **正则表**（`:357-479`）+ `classifyShellRisk`（`:607-636`）+ `shouldAutoApproveCommand`（`:657-661`）。
- **影响面**：两套分类可能**结论分歧**。若前端正则把某命令判为「白名单命中且非硬拒绝」而引擎语义分类判定为危险需问询（NeedsApproval）→ 前端自动放行 `core_approve_tool`（`approvalHandlers.ts:78-79`），用户永不见审批卡片。前端正则与引擎语义层**无契约对齐**（前端不依赖 `conex_sandbox` 分类逻辑），是发散风险面。
- **建议方向**：D3 收敛为「**引擎唯一决策权威 + 用户唯一裁决**」。前端 `shouldAutoApproveCommand` 自动放行应删除或降级为「仅对引擎已标 `T0` 安全项」；白名单应作为**批准记忆（remember）**而非**放行判定**。⛔ 须主控裁决 + 删除走 §23。

### P2（关键）绕过审查的路径：前端直发 `core_approve_tool`，依赖引擎 pending 校验兜底

- **证据**：`approvalHandlers.ts:78-79` 前端 fire-and-forget `core_approve_tool`；引擎 `approvalHandlers.ts` 注释承认「引擎若队列无此项会静默忽略」（`ApprovalHandler.ts:59-61`）；引擎兜底为 `run_approval.rs:135-145` resolve 前 pending 校验（非 pending → NotFound）。
- **影响面**：
  - **不构成裁决绕过**：引擎判决 Deny（plan 写类 / 红线）**不会发出 approval-requested**（`exec_single.rs:86`、`decide_with_redline:102-104`），前端无法对未问询的工具放行；前端只对其关注到的 approval-requested 响应。
  - **但存在「前端先于引擎权威裁决」的高度竞态面**：前端收到 approval-requested 即认为「引擎要问用户」，随即用**前端自认为安全**的结论自动 approve，这是「算法替用户决定」而非「用户批准」。竞态：若引擎随后（超时/ABORT）变化，前端已发的 approve 成为先到裁决，覆盖预期中的用户拒绝窗口。
- **建议方向**：删除前端自动放行分支，改为默认「展示审批卡片」，让用户在 UI 明确批准。`onToolStart` 文案「白名单自动允许」掩盖了裁决主体不是用户的事实。

### P3（重要）「按工具类别分类判断」落点现状：**引擎不按 category 决策**，category 近乎观赏字段

- **证据**：
  - 引擎决策仅用 `dangerous` 标记 + `permission_mode` + 红线，**未读 `ToolCategory`**（`exec_verdict.rs:99-125`）。
  - `ToolCategory`（`conex-types/src/tool.rs:14-29`，Terminal/Filesystem/Network/Mcp/Skill/Agent/Internal）**只随事件透传**（`exec_single.rs:33` / `exec_batch.rs:204` / `exec_verdict.rs:214` 均为 ToolStart 事件构造）。
  - **生产路径 category 恒为 `Internal`**：`loop/handlers/executing_tools.rs:62-74` 构造 `ToolBatchCall` 时硬编码 `category: ToolCategory::Internal`，未从工具注册表读真实类别。
  - 工具定义（`agent-tools/src/definition.rs`）只有 `dangerous`/`fatal_on_error`，**无 category 字段**。
- **影响面**：00-总方案 §3/§6 说 D3 = 「工具类别 → 审查策略（allow/deny/ask + 询问规则）」，但**代码中不存在按类别判定**。「类别」目前仅是展示投影标签（tool-presentation），参与不了安全决策。
- **建议方向**：要么给 `ToolDefinition` 加 `category` 并在 `call_verdict` 接线（category→策略归约表），要么在 D3 总案中把 D3 的判定键从「类别」改写为「危险标记 + 模式矩阵 + 任务类型裁剪」的**真实现状**（见 ③ P5），删除「按类别允许/拒绝」的落点预期。

### P4（重要）`PermissionDecision`/`PermissionBehavior`（events.rs 与 permissions.ts）为**死类型/双轨抽象**：与实活 `ApprovalDecision` 并存

- **证据**：
  - Rust：`conex-types/src/events.rs:38-59` `PermissionBehavior`(allow/deny/ask)/`PermissionDecision` **只在**定义、`lib.rs:41-42` re-export、`conex-types/tests/events_roundtrip.rs:1500` 使用；**审批实活事件用 `ApprovalDecision`**(approved/denied/expired，`events.rs:289-298`)，非 `PermissionBehavior`。
  - 前端：`packages/shared-types/src/permissions.ts:4-60` `PermissionBehavior`/`PermissionDecision`/`PermissionRule`/`ApprovalHandler`/`RuntimePermissionPolicy` **接口声明零消费**（全仓 grep `RuntimePermissionPolicy|ApprovalHandler|requestApproval|PermissionRule` 在 apps 命中 0）。
  - `PermissionDecision.behavior` 还被前端 `chat-bridge/ApprovalHandler.ts:44-48` 当作**旧版兼容解析**（`behavior:allow/deny/ask` 对象形态），但引擎实发是字符串三值 + 嵌套对象兼容（`approvalHandlers.ts`）。双层解析兼容 = 死形态残留。
- **影响面**：00-总方案 §3/§61 引用 `events.rs:38-59` 作为「PermissionBehavior(allow/deny/ask)/PermissionDecision」唯一权威，**与实活路径不符**（实活权威为 `ApprovalDecision`）。若照 §3 改，会引入第二套决策类型。
- **建议方向**：D3 收敛为单套决策类型 = `ApprovalDecision`（approved/denied/expired）；删除/废弃 `PermissionBehavior==allow/deny/ask` 与 `permissions.ts` 的 `RuntimePermissionPolicy` 接口族（无消费）。须主控确认 + §23 删除。

### P5（影响评估）决策权威点多处、缺少单一注册表

- **证据**：同一「命令是否放行」判定存在于 ≥3 处：
  1. 执行器 `call_verdict` → `revert_policy.gate_verdict_command`（`exec_verdict.rs:104-113`）；
  2. shell 工具内部 `PermissionDecisionEngine::evaluate_command`（`permission.rs:196-287`；`tools/shell.rs:241`）；
  3. 分支任务类型命令白名单 `command_allowed_for_task_type`（`readonly.rs:159-182`，按 task_type 前缀/分类）。
     再加前端正则 `classifyShellRisk`（P1）。= **4 处命令分类，互不调用（仅 `decide_command_with_revert` 内部有红线/回退链 1 处），无单一事实源注册表**。
- **影响面**：违反「单路径 / 删死层 / 收敛」战役目标；多套判定易漂移。
- **建议方向**：D3 以 `decide_command_with_revert`（`permission.rs:135-151`）为命令判定唯一链，消 `PermissionDecisionEngine::evaluate_command` 或将其并入同链；`command_allowed_for_task_type` 明确为「spawn 时工具裁剪」独立层，不参与每命令判定。

### P6（§9 安全点）`ctx.ask` 未接线时的 fail-closed 行为不一致

- **证据**：
  - 命令面：`tools/shell.rs:279-284` `ctx.ask=None` → 返 `tool.requires_approval`（fail-closed，需上层重试审批）。
  - 执行器入口：`exec_single.rs:161-173` 审批未启用且 `permission_mode.is_some()` 显式时 → `ApprovalRequired` 透传；`is_none()` → 落入 `_` 分支**直接执行**（`exec_single.rs:174-177`）。两条路径 fail-closed 语义不一致。
- **影响面**：模式为 None（壳层未显式下传）时，`call_verdict` 一律 NeedsApproval（`exec_verdict.rs:123`），且 `approval_enabled` 取决于壳层布尔——需确认壳层是否总是传模式。
- **建议方向**：统一「无审批基础设施 → 拒绝」为全局 fail-closed（对齐 computer-tools 的 `approval.rejected` 缺门拒绝，guard_chain.rs:497-524）。

### P7（§6 错误治理）错误码穿透一致性

- **证据**：`exec_verdict.rs:161-174` `classify_tool_error` 把 `tool.requires_approval`→`ApprovalRequired`、`tool.approval_expired`→`ApprovalExpired`、`tool.user_denied`→`UserDenied`；`ToolErrorKind` 的 `is_never_fatal` 把这些排除在 fatal 外（`exec_verdict.rs:80-81`）。⚠ 未真跑验证错误分类在事件桥的逐类型映射。
- **影响面**：审批错误非致命喂回模型，语义正确；但依赖 `is_never_fatal` 覆盖全，若有遗漏会变 fatal。
- **建议方向**：保持；真跑 e2e 补审批 reject/expired 链路断言（§7 审计意图 7.4）。

### 竞态结论（对应任务的「前端直接 approve-tool 与引擎 deny 的竞态」）

- **无 deny 绕过**（引擎 deny 不出 approval-requested，前端无从放行）；
- **存在 approve 超车竞态**（前端自动 approve 在引擎裁决权威前先落地），但引擎 `resolve` 的 pending 校验把「非待审批」或「已过期」的 approve 兜成 NotFound（`run_approval.rs:135-145`），**不破坏审计不可伪造**（§9「Plan Deny / 批写 token」意图正面）。
- 结论：安全底线（不可伪造）靠引擎 `resolve` pending 校验守住；**UX 侧自动放行**是主要需收敛项（P1/P2）。
