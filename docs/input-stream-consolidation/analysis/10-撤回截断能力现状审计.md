## ③ 「事件流只追加」不变量反例检查结果

**判定：引擎侧 `events` 表成立（core = 只追加），但有明确反例在**移动端 cache** 层与**迁移/重建**路径。**

- **引擎侧（canonical）成立**：
  - `crates/conex-db/src/events.rs:13-34` `append_event`（INSERT 追加）；`:40-127` `query_events[_by_run]`（SELECT 只读）；`:131-158` `reserve_sequence` 用 **MAX 语义只抬高不回退**（`events.rs:139` `COALESCE(MAX(sequence),0)+1`）；`:162-180` `seed_sequence` 同样 MAX-only。
  - events 表定义：`schema.rs:150-155`（`PRIMARY KEY(session_id, sequence)` + `FOREIGN KEY ... ON DELETE CASCADE`）。**唯一删除路径 = 整会话删除 `delete_session`（sessions.rs:131）级联**，非「会话内截断」。
  - orchestrator 事件面：`orchestrator/src/events.rs` 只有 `push` / `append_event` / `push_terminal_best_effort` / `push_at_best_effort`（:189,245,281）；无 DELETE/truncate。revert 相关字面量（restore.rs/persist.rs 的 `events.truncate(limit)` 是 **Vec 内存裁剪**，非 events 表 SQL 删除）。
  - 会话内 append-only 不变量（P1）在 conversation 层登记：`loop/loop_runner.rs:257-260`（水合点是 4 追加点之一，之后只增不改）；`loop/invariants.rs:1-15`（I1：compaction 是唯一前缀重写点）。→ **对话消息内存面与 events 表面同时守住只追加**。

- **反例（violation）**：
  1. **移动端 `crish-mobile` 事件表物理删除**（最直接反例）：
     - `apps/crish-mobile/src/db/dao/eventsDao.ts:148-162`：`deleteOlderThan(sessionId, beforeSequence)` = `DELETE FROM events WHERE session_id=? AND sequence<?`；`deleteBySession` = 按会话全删。
     - `apps/crish-mobile/src/db/cachePolicy.ts:206-230`：per-session 窗口清扫（保留最近 keepCount，`DELETE ... AND sequence < keepFloor`）+ 全清。→ **移动端 events 表可被窗口淘汰物理删除**，若移动端被纳入「唯一时间线（事件流骨架）」则违反只追加。
       （对照 `docs/multi-device/plans/M5-mobile-engineering.md:1126`：5 千条/session 缓存窗口计划——是设计内的 cache 淘汰，但**没有与「审计/恢复/重放」语义协调**；撤回设计若依赖事件流重放历史，需确认移动端是否仍保留完整事件。）
  2. **`session_messages`（投影表）先删后插重建**：`crates/conex-db/src/messages.rs:52-104` `save_session_body`（DELETE WHERE session_id → INSERT 全量）；`import.rs:91`（导入 DELETE session_messages）；`agents.rs:211`。01 审计已证这正是「engine 只写 events、不写 session_messages」的原因——投影表本身非只追加，**这恰好支持「截断 = 投影重写」方向**（截图 boundary 后重建投影），但与「events 只追加」是两个不同表，需在方案里分清。
  3. **迁移/重建重写**：`migrate_steps.rs`（events_v3 / runs_v3 等 DROP+重建，迁移期 ON DELETE CASCADE），属一次性迁移非运行期撤回，不构成常态反例但需在「事件流骨架」迁移论断里留意。

- **结论**：若「唯一时间线 = events 表只追加」要成为撤回的承载（旧事件保留、投影 boundary 后重建），**必须处理移动端 `eventsDao.ts`/`cachePolicy.ts` 的窗口删除**——撤回依赖的历史可能在移动端被 cache 淘汰。桌面/引擎侧当前无会话内 events 删除，撤回截断可以纯靠新增 `timeline-truncate` 事件实现。

**并发缺口汇总**（撤回专用）：

1. **「先停后截」的原子性**：L3 stop 与截断/重放之间无「边界冻结」事务——撤回需保证 stop 收口后、重放前不再有事件/消息写入（现状 run 收口后自然停写，但 `timeline-truncate` 事件本身与 stop 不是同一提交单元）。
2. **审批在途**的已批准但未执行项：abort 竞速已覆盖等待，但「已批准待执行」的语义需由扩展点 D 回滚策略回答。
3. **子代理**：kill_all 已可级联，但归一 `failed` 与撤回语义（`cancelled`）不一致需评审；且撤回若边界在某子代理完成后，需判断该子代理是否在截断范围内。
4. **移动端**：若撤回依赖事件重放，移动端 `cachePolicy` 窗口删除的历史不可重放（§③ 反例 1）。

## ⑤ 对总方案 §2.4 设计的验证与修正建议

**已验证成立（可直接复用）**：

- 步骤 1「复用 `RunTerminalStatus::Cancelled` 路径」**成立且成熟**：control 总线 L0–L3（control.rs）→ 安全点（safe_point.rs）→ aborted 收场（end.rs）→ `map_agent_end_to_terminal` 映射 Cancelled（run.rs:644）；前端停止→IPC 全链路已通（ComposerField → streamStop → runControlClient → `core_run_control`），用户取消静默收口语义就绪。
- 子代理级联停止**已具备**：orchestrator `kill_all`（lifecycle.rs:200）就是「撤回关停 running 子代理」的可复用原语，且已有集成测试（kill_all.rs）覆盖批量 L3 投递 + FlowScheduler 清理。

**需新增（缺口）**：

1. **`timeline-truncate` 事件类型**：全仓 zero 命中；需在 `conex-types/events.rs` 新增变体 + 会话事件持久化白名单接入，且**必须是新事件而非物理删除**（引擎侧 events 表当前无会话内删除，正支撑「只追加截断」方向）。
2. **节点 seq → boundary 定位原语**：当前无「user 消息 id → events sequence」反查；撤回需在引擎侧解析 boundary seq。
3. **副作用回滚（扩展点 D）缺执行器与元数据**：`TrashService.snapshot/restore_force`（conex-fs/trash.rs）已具备「文件写类回滚」能力但**未被撤回调用**；`revert.rs/revert_guard.rs` 只是**git 回退的审批门禁**而非回滚执行器；**工具无「可回滚性」标记**（ToolCategory 恒 Internal，03 审计已证「按类别分类」代码中不存在）。→ 需建「工具类别 → 可回滚性/回滚策略」注册表（D3 共用类别轴）。
4. **文本回退 composer 缺数据源**：`slashSendDraftManager` 的草稿快照**成功发送后即清除**（useSlashSend.ts:209），撤回时被撤回 user 消息原文不在草稿快照；需从 boundary 对应消息取回文本回填（或把草稿快照保留到可撤回窗口）。
5. **「先停后截」原子性与边界冻结**：L3 stop、截断事件、投影重放需同一「边界 seq」语义，避免 stop 后又写入/重放越界。

**对 §2.4 措辞的修正建议**：

- §2.4「副作用回滚文件写入类走 revert/trash 回滚（revert_guard / conex-fs trash）」：措辞需修正——**conex-fs trash 是回滚存储/恢复底座（可复用）**，但 **`revert_guard.rs` 是 git 回退的审批门禁，不是回滚执行器**；自动回滚走大面积 git 回退时应**再次过 C3/C4 门禁**，与「撤回即回滚」两层语义要分开。
- §2.4「投影层在 boundary 后重建」与「事件流只追加」可成立，但若移动端仍在统一时间线内，**必须先处理 `crish-mobile` 事件窗口物理删除**（§③ 反例 1）否则重放历史不可得；建议把「唯一时间线」限定到引擎/桌面 events 表，移动端 cache 窗口明确为「已淘汰不可审计」的降级语义或改为只追加剪枝（无物理删除）。
