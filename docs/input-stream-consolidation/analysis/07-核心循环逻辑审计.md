## ① 范围与方法

### 1.1 审计目标

收敛战役的总目标是：**核心循环逻辑简洁、优雅、可扩展**——一切周边能力（注入/提交时机/权限/展示/撤回）都应成为扩展点，不混入主循环。本审计回答五个问题：

1. 核心轮转骨架是什么（每一步在哪个文件:函数）；
2. 外围功能在哪介入主循环、耦合多紧、有没有抽象缝；
3. 核心代码是否可读、哪些逻辑本可外置却被硬编码；
4. 现存循环扩展缝各是什么形状、被谁消费；
5. 什么是 MUST stay core、什么应移出、建议用什么缝。

### 1.2 代码域（只审 crates/）

| crate                   | 域                                | 本审计关注                                                                                       |
| ----------------------- | --------------------------------- | ------------------------------------------------------------------------------------------------ |
| `crates/session-loop`   | 主循环内核                        | **核心**：loop/、handlers/、以及 hooks/steering/tool_exec/stream/tool_events/approval 等外围模块 |
| `crates/orchestrator`   | 会话树 / flow / rewind / 审批装配 | session.rs（**实为会话树模块**，见 ②b）、steering_queue、approval 装配                           |
| `crates/agent-provider` | 请求构建 / wire 协议              | request/**（仅 `streaming.rs::build_request → ProviderCall` 的消费链）                           |

### 1.3 方法

- 逐个核心 handler 精读，勾勒轮转链与其真实介入点（文件:行）。
- 对外围模块读文档头 + 关键函数，判定挂接点与耦合度。
- 行数口径用 `Get-Content` 实测（total 行，含测试；code 为剔除空行与 `//` 注释后的有效行，供 §17.1 上帝文件表参考）。
- **本会话为只读源码形状审计，未跑 `cargo test`。** 所有「真跑验证」结论均标注 `[待验证]`，未标注处为源码形状判定。

## ② 核心循环骨架（文件:函数链）

### 2.0 先纠正一个命名陷阱（影响任务书理解）

任务书点名 `orchestrator/src/session.rs` 为「核心循环」组成部分。**此处发现命名错位**：

- `orchestrator/src/session.rs` **不是**会话运行循环的驱动器，而是**会话树 + conversation-rewind 计划**的数据结构模块：`SessionTree`（append/fork/move_leaf，session.rs:324-683）、`plan_conversation_rewind`（:912）、`execute_rewind`（:1089）。它只提供**会话历史的组织模型**，不驱动轮转。
- 真正的轮转驱动器在 **`crates/session-loop`**（`AgentSessionLoop` + 状态机 + 8 个 handler）。orchestrator 的角色是**装配与持久化**（经 `engine.rs`/`lifecycle.rs` 把 options/tool_exec_ctx/approval/hooks 注入 loop）。

> **结论**：核心轮转骨架的物理归属是 `session-loop`；`orchestrator` 是装配壳与历史模型。这个澄清对战役的「注入/提交时机」两类扩展点定位很重要——它们在 session-loop 的 handler 内部，不在 orchestrator/session.rs。

### 2.2 主线七步（输入 → 请求构建 → 流式 → 工具执行 → 裁决 → 收场）

`loop_exec.rs::run`（:22）的 `while !done { dispatch_once }`（:133-149）按状态机路由到 8 个 handler，构成**不可再简化的核心轮转骨架**：

| 步骤       | 状态(s)          | 文件:函数（handler）                           | 职责                                                                                                                       |
| ---------- | ---------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 1 输入     | AwaitingInput    | `loop/handlers/awaiting_input.rs:14 handle`    | 安全点 → dequeue（force/steer）→ 无输入 NO_INPUT 收场，有输入 `record_message`+InputReady                                  |
| 2 备轮     | PreparingTurn    | `loop/handlers/prepare_turn.rs:37 handle`      | 安全点 → 消费 pending（hold→压缩→append）→ turn-start → steering(after-tools/before-turn) → 压缩预检 → TURN_PREPARED       |
| 3 请求构建 | （streaming 内） | `loop/handlers/streaming.rs:330 build_request` | 组装 `ProviderRequest`（对话/工具快照/max_tokens 钳制/system/session_id/思考档位）→ 调 `provider.stream`                   |
| 4 流式     | Streaming        | `loop/handlers/streaming.rs:40 handle`         | consume 聚合 + 实时 delta 双轨 → response 分类（Message/Empty/StreamError）                                                |
| 5 工具执行 | ExecutingTools   | `loop/handlers/executing_tools.rs:40 handle`   | 取工具调用 → `ToolExecutor.execute_batch`（:84）→ 结果 record → fatal 判定 → steering 计数重置                             |
| 6 裁决     | TurnComplete     | `loop/handlers/turn_complete.rs:33 handle`     | turn-end → abort/error 收敛 → turn.end 钩子 → maxTurns → toolCallCount→NEXT_TURN / idle→INPUT_AVAILABLE / 默认 SHOULD_STOP |
| 收场       | converge         | `loop_exec.rs:301 converge`                    | agent-end 事件 + RunOutcome（reason/error/messages/events/cache_stats/provider_error）                                     |

### 2.3 三条横切支线（error / steering / abort）

- **流错误阶梯**：`streaming.rs` StreamError 分支（:159,:253）→ `loop/handlers/stream_error.rs:55 handle` 按 `ProviderErrorKind` 路由到 `stream_error_retry.rs:86 transient_retry`（瞬态退避+熔断）、`stream_error_recover.rs`（length 阶梯 + 压缩阶梯）、`stream_error_fatal.rs`（降级 fatal）。
- **空响应 steering**：`streaming.rs` Empty 分支（:233）→ `SteeringNeeded` → `loop/handlers/steering_evaluation.rs:26 handle`（预算耗尽 stop / intervention stop）。
- **安全点 / abort / 控制意图**：`mod.rs check_control`（:1162）在**每个 handler 起始**与 stream/tool 批结束被调用；`streaming_aborted`（streaming.rs:272）是 abort 收场统一路径。

### 2.4 请求构建链路（骨架第 3 步的完整消费链）

```
streaming.rs:build_request(:330)                    # session-loop 组装 ProviderRequest
  → provider.rs:ProviderRequest(:126)               # trait 契约（不依赖 agent-provider）
  → provider.rs:ProviderCall::stream(:200)          # 真实适配层实现
      → agent-provider/request/build.rs facade(:26) # build_chat/build_responses
      → agent-provider/request/build_chat.rs        # chat-completions 请求体
      → agent-provider/request/build_responses.rs   # Responses API + affinity headers
```

> **关键隔离点**：session-loop 经 `ProviderCall` trait 与 agent-provider 解耦（provider.rs:4-22），`stream.rs`（self-built consume 等价层，stream.rs:1-22）自建本地等价类型。这是一个**已存在的、干净的抽象缝**。

### 4.2 核心里「本可外置却被硬编码」清单

1. **压缩触发编排面全在 `<handlers/mod.rs>`（:270-862）**：估算 + clamp + 预检 + 边界压缩 + apply_compaction（含 cache tracker 复位、块元数据、后台任务登记、事件广播、钩子广播）。这是一个 ~590 行的**内嵌子系统**，揉在「handler 公共态」模块里。算法面已在 `conex-compaction` crate，但**编排面没从 handlers/mod.rs 拆出**——最典型的结构债（§17.3 职责缠结：state + clamp + compaction + dispatch + safety 全部同文件）。
2. **`cache_tracker`/预算/摘要状态字段直接落在 `LoopState`**（mod.rs:126-180，约 14 个外围字段：budget/compaction_policy/summarizer/last_compaction_at/compactions_this_run/compression_retries/cache_tracker/summary_dispatch/summary_coordinator/pending_summary_retry/turn_usage…）。核心可变状态被外围功能撑大。
3. **`streaming.rs::handle` 单函数职责过载**（:40-262）：请求构建 + 流消费 loop + delta 双轨 + cache usage + usage 槽位 + 响应分类 + abort 复查 + 分类分派。可视作「半拆分」——消费聚合已拆到 stream.rs，但 handler 仍打包了 6 件事。
4. **`exec_single.rs`/`exec_batch.rs` 审批 + 裁决 + 中间件 + 幂等 + 并发 + 取消同一批**：`execute_batch`（exec_batch.rs:137）集分组/审批逐个 await/信号量并发/取消/事件序列于一身（~330 行）。审批本身已缝化为 `ApprovalGate`，但批量并发编排仍内嵌。

### 4.3 可读性结论（源码形状）

- **骨架干净**：8 个 handler 各司一职，`dispatch_once`（loop_exec.rs:162）极简（~33 行），状态机驱动清晰。**主循环是精简的**。
- **不动点混乱**：真正的复杂度不在「循环驱动」而在「压缩/预算/cache_tracker 这些横切子系统被内嵌到 handler 公共态与 mod.rs」。战役若要「让核心简洁」，主战场是 **handlers/mod.rs + LoopState 的外围字段瘦身**，而非 loop_exec/handler 本身。
- **无上帝 handler**：最长的 streaming.handle 虽职责多，但可读；真正的"上帝"是 handlers/mod.rs 与 LoopState。

### 5.1 缝的质量判定

- **优**：ProviderCall（请求隔离）、DeltaSink/LiveEventSink（实时轨）、ApprovalGate（审批）、ToolMiddleware（工具横切）、SteeringStrategy（注入策略）——都是 trait/中间件/事件，**已具备扩展点形状**。
- **中**：HookRegistry 已事件化但**发射点分散在 6+ 处**（turn/compact/session/error），缺一个「生命周期事件槽」统一收口。
- **缺**：compaction 与预算的**编排面没有缝**（只有算法面 conex-compaction 有 trait）；cache_tracker 无 trait（硬编码字段）；summary_dispatch 触发面内嵌 core。

## ⑥ 保留 / 移出建议

### 6.1 MUST stay core（不可移动）

| 要素                                                                                                                    | 理由                           |
| ----------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| 状态机 + dispatch_once + run while 循环（loop_exec.rs）                                                                 | 轮转本身就是骨架               |
| 8 个 handler 的顺序编排（awaiting→prepare→stream→exec→complete）                                                        | 与状态机强绑定                 |
| `LoopState.conversation` 的 4 个追加点纪律（record_message / commit_message_with_deltas / steering apply / compaction） | 请求前缀字节稳定性不变量（P1） |
| 安全点 check_control + streaming_aborted（L1/L2/L3 优先级）                                                             | 中断/协作停止是循环内建能力    |
| 错误阶梯的「路由入口」stream_error.rs:handle（瞬态/length/payload/其余）                                                | 错误分类是流式主路径的组成部分 |
| ProviderCall / DeltaSink / turn 事件序列（message-start/delta/end 成对）                                                | 冻结契约，跨 crate             |

### 6.2 应移出（候选 + 建议缝形态）

| 候选移出项                                                                      | 现状位置                                                   | 建议缝形态（对齐战斗纪律：扩展点，不新建架构）                                                                                                                                                                |
| ------------------------------------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **压缩触发编排面**（估算/clamp/预检/边界/apply/事件/后台登记）                  | handlers/mod.rs:270-862 + LoopState 压缩字段               | 独立 mod `compaction_dispatch.rs`（像 summary_dispatch 那样拆出），保留 `compact_agent_messages` 的 conex-compaction 算法面；给「触发点」定义统一 `CompactionTrigger` 入口（Preflight/UserBoundary/Overflow） |
| **预算/上下文估算 + max_tokens 钳制**                                           | mod.rs:274-338 + streaming.rs clamp                        | 抽纯函数模（clamp/estimate 已纯函数，仅移到独立文件）；状态字段从 LoopState 收进 `BudgetState` 子结构                                                                                                         |

### 6.3 对战役的指向性建议

1. **主战场是 handlers/mod.rs + LoopState 瘦身**，不是 loop_exec/handler 骨架。战役「让核心简洁」可用「挑出 #1 压缩编排面 + #5 hook 单点 作为首批减负」落地。
2. **口径澄清**：`orchestrator/src/session.rs` 是会话树/rewind，不是轮转驱动；实现波不要误改它来实现「提交时机扩展点」——提交时机在 session-loop 的 awaiting_input/prepare_turn/turn_complete 的输入队列消费点。
3. **已具备缝的（provider/approval/middleware/steering/delta）不要再新造**；缺缝的（compaction 编排/cache/预算）才需补缝。
4. 建议的每个移出项都**保留既有语义，纯结构搬移**（对齐「只搬移不改行为」先例），以便用现有 handler 测试海做回归锚点。
