## 1. 做什么（新增/修复清单）

### 概念目标（本维度收敛到的单路径形态，一句话）

> 「下一条用户消息」只有**一条**跨 run 语义载体（orchestrator `PendingMessageQueue`，已接线 run_idle 边界）；用户**状态切换**（模型名/权限/思考模式）经 **context-state 节点**在**下一次用户提交边界**注入时间线（扩展点 A）；steering nudge 的半成品通道删除；`metadata.kind` 魔法字符串枚举化；**思考档位**经 `ReasoningEffort` 真下发到 provider 请求（I1-β）。

### 1.1 I1-α ①　双队列归一（核心收敛）

**现状（源码核实）**：

- 两条「下一条用户消息」语义载体并存，但是**两级流水**而非完全平行：
  - orchestrator `PendingMessageQueue`（`orchestrator/src/steering_queue.rs`）= **跨 run 语义队列**（canonical）。已接线到 run_idle 续 run 边界：`run_idle.rs:228,308,393` 调 `drain_pending_to_inject_messages`（`run_idle.rs:534-574`）把条目批量转成 User 消息注入下一 run。产生侧全部经 `replace_or_enqueue`（按 group_id 去重）落点：timers.rs / sched.rs / watchdog.rs / wake_watcher.rs / task_event_consumer.rs / workflow_commands.rs / subagent_spawner.rs。
  - session-loop `AgentInputQueue`（`session-loop/src/input.rs`）= **run 内三环环形缓冲**（Force/Steer/FollowUp），是主循环消费面的适配层；`PendingMessageQueue::transfer_follow_up`/`transfer_into_input_queue`（steering_queue.rs:206-222）把跨 run 条目迁入 `AgentInputQueue.followUp` 环。

**收敛方向**：`PendingMessageQueue` 是唯一「下一条用户消息」的**规范语义**（canonical）；`AgentInputQueue`（三环）收敛为**纯适配/消费面**，不再承担「下一条用户消息」的**政策**语义，只承担「当前 run 主循环如何消化」的执行语义。**不新建第三队列**（禁止项 1）。

**具体动作（先删后改）**：

1. **删除 steering nudge 半成品的直接通道**（决策点 9，见 §2）：
   - `PendingNudgeChannel::enqueue_into_input_queue`（`nudge.rs:305-316`）生产零接线，删除（含陪葬测试 `nudge.rs:417-457` 的 `nudge_enqueues_into_next_user_message_queue` / `nudge_enqueues_into_steer_ring`）。
   - `PendingMessageQueue::drain_nudges`（`steering_queue.rs:228-242`）壳层零命中，删除（连同 `PendingNudgeChannel` 依赖导入）。
   - `PendingNudge`/`PendingNudgeChannel` 结构若删除后仅测试引用，一并删除（见 §2 证据）；保留 `PendingNudgeChannel::enqueue`/`enqueue_into_input_queue` 的**回调面语义**仅在确有第二消费者时再恢复（现无）。
2. **AgentInputQueue 收敛为适配层**：明确 `InputEnqueueMode::{Steer, FollowUp}` 仅供 `PendingMessageQueue` 适配端 + 主循环安全点消费，不再作为「外部注入策略入口」暴露给壳层；`enqueue_follow_up`/`enqueue_force` 等公共 API 仅保留主循环内部使用，外部「下一条用户消息」一律走 `PendingMessageQueue`。
3. **运行时归一**：shell（orchestrator）统一消费 `PendingMessageQueue`（已是现状），删除任何直接在 `AgentInputQueue` 上挂「跨 run next message」的入口残留（grep 核实当前只剩 `transfer_follow_up` 一条适配桥，保留之，其余清理）。

### 1.1 I1-α ②　context-state 节点接入（扩展点 A）

**现状（源码核实）**：

- 动态状态注入**零时间线通道**：前端 `profileStore.setActiveProfileId/setActiveModelId`（`provider-profiles/profileStore.ts:94-135`）只写 localStorage + `emitUiEvent('profiles-changed')`（`:135`），不产生 `AgentEvent`、不写会话事件/消息（analysis/02 问题①）。
- `chat-bridge/ConnectionLifecycle.ts createStreamSession`（`:340-443`）把 `permissionMode`/`budgetDifficulty`/`systemPrompt` 当 IPC 参数下发，不写入任何时间线节点。
- `AgentMessageRole`（`conex-types/src/message.rs:15-24`）仅 System/User/Assistant/Tool；`AgentMessageBlock`（message.rs:100-126）仅 text/thought/tool-call/tool-result——**缺 context-state 类型**（00-核心模型不变量 1 缺口）。

**做什么**：

- **类型**（依赖 T1a，禁止另造节点——禁止项 3）：在 T1a 新增 `context-state` 节点类型（`AgentMessageRole` 或 `AgentMessageBlock::State` 新变体 + `metadata.kind` 枚举变体 `ContextState`）。本详案**不定义 payload 细节**（归属 T1a 类型定案），只声明消费契约：context-state 是一段**用户可见的状态快照文本**（含模型名/权限/思考档位），携带 `metadata.kind = context-state`。
- **产生器**：前端 `provider-profiles`（`profileStore.ts`）在 `setActiveProfileId/setActiveModelId` 及权限/思考模式切换处，**新增** context-state 文本产生逻辑（渲染「当前已切换到模型 X / 权限 Y / 思考档位 Z」）。
- **注入载体**（复用已接线的 `PendingMessageQueue`，扩展点 A）：context-state 产生后经 `PendingMessageQueue.replace_or_enqueue`（group_id = `context-state` 去重，防连切两次重复注入）排入跨 run 队列 → 下一 run 边界 `drain_pending_to_inject_messages`（run_idle.rs:534）按 User 文本注入时间线 → message-start/end 事件进入会话 seq。
- **不占 wire system_prompt**：context-state 以 `ProviderRequest.messages` 的 text 载荷进入（进对话 seq），不单独拼 system_prompt（analysis/02 建议方向 78）。

**与 17 审计纪律的边界（关键，禁止项 2）**：context-state 是**感知注入**（状态变更告知 AI，进 seq、进时间线），而**配置/偏好本身**（主题/布局/权限策略/provider profile 的存储）是**独立配置带，不进消息 seq**（analysis/17 §5.2/§6.3：17 审计明确「配置事件不进会话时间线，禁止塞进消息事件流行污染唯一时间线」）。I1 只把「状态**切换发生**」这一感知注入 seq；**不**把配置文件/偏好整体塞进消息流。二者不混。

### 1.1 I1-β　reasoning_effort 真下发

**现状（源码核实）**：

- agent-provider 侧**全套已就绪**：`ProviderRequest.reasoning_effort`（`session-loop/src/provider.rs:155`）、`ReasoningEffort` 枚举、vendor 映射/wire 写入/白名单校验（`agent-provider/src/request/`、`engine_provider/thinking.rs`，`engine_provider.rs:159,197,278`）。
- **但产品链路断**：
  1. 前端 `ConnectionLifecycle.ts:360-365` 把 `defaultThinkingLevel` 映射成 **`budgetDifficulty`**（easy/normal/hard），作为 IPC 参数下发——**不是 reasoning_effort**。
  2. `SessionLoopOptions`（`loop_options.rs`）**无 `reasoning_effort` 字段**（全文核实）。
  3. `build_request`（`streaming.rs:330-361`）`reasoning_effort` 仅当 `is_zero_thinking_budget` 才 `Some(Off)`，否则恒 `None`（`:347-351`）。
- 契约测 `run_loop.rs:999` `reasoning_effort_field_propagates_through_request` 已钉死字段透传，可作为验收基础（现为「字段形状」测，**非产品链路测**）。

**做什么**：

1. **`SessionLoopOptions` 增 `reasoning_effort: Option<ReasoningEffort>` 字段**（缺省 None = 现状行为，向后兼容）。壳层装配面（`run_launch.rs` / run-task）把思考档位注入。
2. **`build_request`（streaming.rs:330**）读 `state.options.reasoning_effort`：非零思考预算时用**用户档位** `Some(effort)`；`is_zero_thinking_budget`（tool-promise 自愈/thinking_budget=0）仍覆盖为 `Off`（保留现有语义）。
3. **壳层 run-task 契约**：run-task 参数新增 `reasoningEffort`（或复用 `thinkingLevel` 语义通道），`ConnectionLifecycle.createStreamSession` 从 `defaultThinkingLevel` 映射**用户思考档位 → `ReasoningEffort`**（minimal/low/medium/high/xhigh ↔ ReasoningEffort 档位），替换现在只映射 `budgetDifficulty` 的做法；`budgetDifficulty` 若仍被其它面消费则保留为独立预算参数，**不得与 reasoning_effort 混为一谈**（analysis/02 问题⑦ / build_chat.rs:59「消除 budgetDifficulty 语义混淆」）。
4. **context-state 联动**：思考档位切换同时生成 context-state 节点（I1-α②），告知模型「思考模式已切换」，二者同批（I1-β 依赖前端 provider-profiles）。

**诚实边界**：budgetDifficulty（预算难度）与 reasoning_effort（思考档位）是两个概念。I1-β 不是把 budgetDifficulty 改名，而是**新增/接通真正的 reasoning_effort 通道**；`budgetDifficulty`（如仍被 max_tokens 预算等独立消费）保留其独立语义，但作为**思考档位代表**的角色由 `reasoningEffort` 取代。具体字段落点与 run-task 契约归属执行期确认（源码形状层面 run-task 接收方在壳层 Tauri command，需执行期核）。

## 6. 禁止项（红线 · 违反即退回）

1. **不新建第三队列**：不引入新的「下一条用户消息」容器；context-state 复用 `PendingMessageQueue`（即 `nudge.rs`/steering 不再另建直通队列）。
2. **不把配置塞进消息流**（17 审计纪律）：context-state 是感知注入（进 seq），**配置/偏好本身不进 seq**；状态切换的「发生」进时间线、配置存储留在独立配置带，二者不得混。禁止把主题/布局/权限策略 provider 配置文件整体塞进 `messages`。
3. **不绕过 T1a 类型定义另造节点**：context-state 类型、kind 枚举、generated parser 一律由 T1a 定案；I1 只消费，不另造手写类型/解析器（抽象纪律 1/3）。
4. **队列归一只做收敛、不展开可注册 kind**（plan-review ④#4 / 03 §2.4）：context-state/nudge/steering 用固定枚举变体，不建「可插拔 kind 注册表」空抽象（抽象纪律 5）。
5. **不把 budgetDifficulty 当 reasoning_effort 改名**：两者是不同语义；I1-β 接通真正的 `reasoning_effort` 通道，预算难度若独立消费则保留独立语义（build_chat.rs:59「消除语义混淆」）。
6. **nudge 删除不得误删 `runtime_steering_text`/`build_steering_message`/`diagnostic_message`**：这些是**当前 run 注入**（recovery 纠偏）正用组件，是正向机制（analysis/02 问题③：进事件流），仅删「跨 run nudge 直通」半成品。
