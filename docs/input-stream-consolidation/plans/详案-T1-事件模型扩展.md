## 0. 一句话概念目标

在事件类型层**一次定型**三类「带类型标记」承载，为撤回（R1）、动态状态注入（I1）、静态注入文本化（D2）三条支线提供**同一类型域**的地基：TimelineTruncate 作为**独立事件变体**出站，context-state 与 injection 作为**AgentMessage 节点的来源标记**（类型化 `metadata.kind`），全部经既有事件流骨架（append-only + seq 单调）承载，**不新建任何并行事件**、不动现有 57 变体语义、不改前端消费逻辑（T1 只管类型层）。

### 1.1 裁决建议（2 份 main 裁决 + 1 份结构裁决）

#### 裁决 1（必答项）：AgentMessageRole 是否扩展？

**裁决：不扩展 `AgentMessageRole`。**

- **证据**：`message.rs:15-24` 现状仅 System/User/Assistant/Tool，serde lowercase，wire 值 `system|user|assistant|tool`（registry enums `AgentMessageRole`，registry_drift.rs:491 锁定值数 = 4）。02 审计问题⑥ 指出「注入/状态只有 role + metadata.kind 字符串，无常量类型」——**缺口在「来源/类型标记」维度，不在「对话角色」维度**。
- **理由**：role 是 LLM wire 对话角色（决定 provider 消息语义）；注入/状态是**来源/类型标记**，与 role 是**正交的两个维度**（同一 message 既可以是 System role 也可以是 `kind:injection` 来源）。把 context-state/injection 塞进 role 会造成：wire 值不合法（serde lowercase 只接受固定值）、provider 侧语义混叠、且与非生成的自由字符串冲突。
- **落点**：新增 `AgentMessageMetadataKind`（来源标记维度），与 role 并存；**不动 4 角色 wire 值**（符合「不动现有 57 变体语义」禁止项）。前端 `EngineLikeBlock`/`messageUserProjection` 既有的 `nudge`/`system_nudge` 消费面（02 审计）将来接 generated 常量，非本轮（D2/D4/V1）。

#### 裁决 2（结构裁决）：context-state / injection 是否作为独立事件？

**裁决：不独立成事件——作为 AgentMessage 节点来源标记（metadata.kind）。**

- context-state：02 问题① 明确「新增 context-state 节点，挂到用户下一次提交，作为 AgentMessage 进入 ProviderRequest.messages」——它是**消息流节点**，走 message-start/end 与用户正文同源同一时间线（不变量 1「一切皆文本节点」）。若独立成 `ContextState` 事件又另发 message 事件 = **同一内容两条路径**（违反不变量 4、禁止项「第二条路径」）。
- injection：`RuntimeSteering`（events.rs:563-569）**已经是 injection 出站事件**（02 问题③ 确认 steering inject-message 已进时间线）。新增 `Injection` 事件与 `RuntimeSteering` 平行 = **新建并行事件类型**（违反禁止项）。
- 因此 T1 只定义**来源标记类型**（枚举 + schema），注入/发射由 I1（context-state 挂提交）、D2（静态 injection 文本化）、R1（TimelineTruncate 出站）消费。

#### 裁决 3（required 兜底）：三事件是否默认 required？

**裁决：TimelineTruncate 默认 required（对齐 21 审计借鉴 1 + plan-review 02）；context-state / injection 因走既有 message 事件（已 required），仅 metadata.kind 值是**名称**非新类型，无版本兜底问题，直接持「消息级宽容读取」既有语义（mobile 未知 kind 静默跳过，MessageKind::Unknown 语义）。**

- 基于：21 审计 §9.1「新事件默认 required；reader 遇到不认识的 required 事件必须拒重建而非静默跳过」。`timeline-truncate` 是 R1 撤回的**语义关键事件**，旧 reader 若静默跳过会破坏撤回重放基准——必须 over-refuse。

### 1.2 事件/节点 schema 草案（详案必须给出）

> wire 字段命名 = serde camelCase = registry 字段名（03 §1 契约）。所有字段含解释。

#### （a）`TimelineTruncate`（新增 AgentEvent 变体，事件域 `retraction`）

```
AgentEvent::TimelineTruncate {          // type = "timeline-truncate"
  session_id: String,                   // 必填：会话归属（协议硬约束，registry_drift 全局断言）
  run_id: String,                       // 必填：事件体自带 runId（对齐 run-terminal 先例，events.rs:612-620；
                                        //       R1 撤回收场的 run；与信封 runId 同值，emit 层注入值覆盖）
  boundary_seq: u64,                    // 必填：截断边界 sequence（重放只到此前；事件流只追加不物理删）
  reason: TimelineTruncateReason,       // 必填：截断原因（新枚举，见下）
  target_message_id: String,            // 必填：被撤回的 user 消息稳定 id（R1 文本回填数据源）
  timestamp: String,                    // 必填：ISO8601
  // 可选：
  // restored_text: Option<String>?     // 不需要——被撤回原文由 R1 从 target_message_id 对应节点取回（10 审计）
  //                                    //   不在此载荷冗余（避免第二份事实源）
}
```

- **seq 归属**：TimelineTruncate 自身占一个会话内连续 sequence（emit 层 reserve_sequence 取号，与其它事件同构）。boundary_seq 是「截断到哪」，TimelineTruncate 自身的 seq 在其后。两者关系：`TimelineTruncate.sequence > boundary_seq`。R1 定义「防越界不变量」：boundary_seq 之前的旧事件保留、之后的重放忽略。
- **backpressure/persist**：Critical + Persist + Critical（必达落库）。在 `event_policy`（events.rs:1313-1414）加入独占分支，不落 catch-all（catch-all 也恰好是 Critical+Persist+Critical，但**必须显式声明**避免隐含，对齐 DSH ignorable 显式语义）。

新增枚举：

```
enum TimelineTruncateReason {           // wire = kebab-case
  UserRequested,                        // 用户 UI 主动撤回
  ErrorRollback,                        // 错误回滚触发的截断（扩展点 D 预留）
}
```

#### （b）context-state 节点（AgentMessage 来源标记，走 message-start/delta/end）

```
AgentMessage {
  id: String,                           // 稳定 id（R1 可据此反查 boundary seq）
  role: "user",                         // 维持 User（来源维度在 metadata.kind）
  created_at: String,
  blocks: [ { type: "text", text: "<状态切换说明文本>" } ],  // 正文文本块（不新增块类型，裁决 2）
  metadata: { kind: "context-state", ... },                  // 类型化标记（裁决 1）
}
```

- kind 常量：`AgentMessageMetadataKind::ContextState`（wire `"context-state"`）。
- **负载建议**（I1 定义，T1 只给 schema 位）：context-state 文本拟渲染如「[上下文状态] 模型已切换为 X / 权限模式 Y / 思考档位 Z」，作为感知注入告知 AI（00-核心模型 §3.2「感知注入进 seq」）。
- **seq 归属**：context-state 随其所挂的 message-start（下一条用户提交）在流中占 seq；不单独占 seq（挂到 PendingMessageQueue 下一条 run 边界，02 问题⑤/独立方案 03）。

#### （c）injection 来源标记（AgentMessage metadata.kind 家族）

- kind 常量：`AgentMessageMetadataKind::{Steering, Nudge, Diagnostic, Injection}`（wire：`steering` / `nudge` / `diagnostic` / `injection`）。
- 现有魔法字符串对应表（02 问题⑥）：`nudge.rs:100,120,162`（`runtime-steering`/`nudge`/`diagnostic`）、`steering_queue.rs:91`（`steering`）、`binary`（`tool-promise-recovery`，streaming.rs:338）。**T1 只定义枚举位**；「把魔法字符串替换为枚举 `as_str()`」归 **I1-α**（independent-plans/03 §5.7 表：`metadata.kind` 魔法字符串 → 枚举化，I1）。T1 **不改现有字符串写法**（避免动前端消费）。
