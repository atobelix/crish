## 1. 做什么（新增/改造清单）

### 1.0 概念边界（先定「投影唯一主路径」语义，防误删 silent-complete 行为）

依据 04 §① + 00 不变量 4「单路径」：前端当前对同一消息有**两条投影链**——轨 A `timelineNormalizer`（渲染真身，MessageContent.tsx:227 → `buildAssistantTimelineCached`）与轨 B `messageUserProjection`/UserView（非渲染旁路，仅 silentComplete 判定 + 调试面板 + 测试消费）。V1 的收敛不是「A/B 二选一保留」，而是：

| 轨                                     | 语义                                           | 处置                                                                                           |
| -------------------------------------- | ---------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 轨 A timelineNormalizer（渲染主路径）  | 唯一渲染真身                                   | **保留 + 归一（折叠单源、去重复对齐）**                                                        |
| 轨 B messageUserProjection（UserView） | 非渲染旁路 DTO（stats/hiddenBuckets/分类断言） | **删除**；其**唯一忠实产品** `silentComplete` 判定**迁移为「单消息可见性直接判定」，行为保留** |

**关键契约（禁止项）**：`silentComplete` 是「run 完成但用户可见内容为空」的 dev/度量告警，不是渲染路径。V1 只做「消费迁移」，**不删除 silent-complete 行为、不删 `recordSilentComplete` metric**（controlMetrics.ts:132-135）；`checkAndAlertSilentComplete` 时序告警（streamCallbacksInternals.ts:249-264）原样保留。删除的是 `messageUserProjection` 的整套 UserViewDTO/hiddenBuckets/classify 投影基础设施，非 silent 判定功能。

### 1.1 V1-α silentComplete 单消息化（迁移消费后，T4 后执行）

**现状（[静态]）**：`silentComplete.ts:18-21` 依赖 `messageUserProjection` 的 `projectSessionMessageToUserView`/`UserViewDto`/`UserViewMessage`；`isSilentCompleteFromSessionMessage`（:119-128）经 `projectSessionMessageToUserView` 拉 UserViewMessage 判定。而判定所需**仅为单条 assistant 消息的 `visibleText`/`thinkingPreview`/`tools` 可见度**，无需整套 UserViewDto/hiddenBuckets/stats/EngineLikeBlock（04 Q1 结论）。

**做什么**：把 silent 判定改为**直接从 `SessionMessage` 判定可见性**，消灭对 `projectSessionMessageToUserView` 的投影依赖：

```
新纯函数（放 silentComplete.ts，替代对 messageUserProjection 的消费）：
  computeAssistantVisibility(msg: SessionMessage): {
    visibleText: string;        // 剥思考占位后的正文（含 blocks text 回退，语义对齐 :261-268）
    thinkingPreview: string;    // 剥占位思考后的 preview（截断，语义对齐 :270-289）
    hasTools: boolean;          // msg.toolCalls 去重后是否有可见工具
  }
```

- `isSilentCompleteUserViewMessage`/`isSilentCompleteFromUserView` 依赖 UserView DTO——在**迁移完成、`messageUserProjection` 待删前**先重构 `silentComplete.ts` 内函数为 **`isSilentCompleteFromSessionMessage` + 新 `computeAssistantVisibility`** 单路判定；对外统一入口 `isSilentComplete` 只保留 `SessionMessage` 分支（删 `UserViewMessage`/`UserViewDto` 分支；对外函数签名仍提供，避免一次改面过大）。
- **不删行为**：`alertSilentComplete`（记 `recordSilentComplete` metric + dev console.warn once）、`checkAndAlertSilentComplete` 调用点（streamCallbacksInternals.ts:256）**原封不动**。
- **顺序约束**：V1-α 的**消费迁移**可在 T4 前完成（只动 silentComplete.ts 自身纯函数，不依赖 T4 产物）；但**删除 messageUserProjection 文件**须等 V1-β 且 T4 已交付（T4 不碰该 API）。

### 1.3 V1-γ 折叠单源裁决 + 命令类型图标最小映射

#### 1.3.1 折叠/分组唯一裁决点下沉投影层（轨 A single source）

**现状双折叠源（[静态] 04 P5/Q2）**：

- **投影端**：`timelineNormalizer.buildToolRenderItems`（:152-200）把连续 inspect 工具产出 `{kind:'group', tools, label:'… · N 步'}`（:164-172）。
- **渲染端**：`ChatToolCallBlock.tsx:58-65` `flattenRenderTools` **把 group 拆回单条**，丢弃 `label`；`renderToolStackItems`（:177-218）再按 `turnId`+`startedAt≤200ms` 重组成 `parallelGroup`（「Parallel（N）」）。→ 投影产出的 group 被展平、label 死，折叠语义双源且互相覆盖。

**做什么（折叠单源）**：

1. **投影层为唯一裁决点**：`buildToolRenderItems` 作为**唯一**产出 `ToolRenderItem[]` 的地方，把**连续 inspect 折叠**与**同轮并行分组**两类语义都收进投影层（在 `buildAssistantTimeline`/`buildToolRenderItems` 内完成，保持纯函数）。
2. **渲染端不再展平/重分组**：
   - 删 `ChatToolCallBlock.tsx:58-65` `flattenRenderTools`。
   - 删 `renderToolStackItems` 内 `parallelGroup` 重分组逻辑（:185-216 的 turnId/staredAt 折叠），改为**直接消费 `ToolRenderItem[]`**：`single` → `CompactToolRow`；`group` → **渲染为标题行 + 组内子行展开列表**，复用并**复活 `label`**（`${toolHumanLabel(last)} · ${n} 步` 作为折叠头文案）。
   - 批量审批栏 `renderToolsWithBatchBars` 保留，但遍历单位为**投影已给出的单条/组内条目**，不再按渲染端自造顺序重组。
3. **`ToolRenderItem['group']` 的 `label` 从死字段变成真实渲染文案**（04 Q2 二选一的「真折叠」支线）。
4. **签名缓存**：`timelineSignature`/`buildAssistantTimelineCached`（timelineNormalizer.ts:321-396）对 folding 变化已由 `blocksProj`/`toolsProj` 覆盖（tool_call id / name / status 进签名）——折叠判定逻辑若只依赖 `isInspectTool`/`toolHasDisplayableResult`（status/name），现有签名已能命中；**新增的组结构变化（如 fold 阈值）需核对是否会击穿签名缓存**（见 §7 R3，真跑验证折叠闭合前端形状）。

#### 1.3.2 官方命令类型图标最小映射（决策 12 · toolDomainDescriptions 基础）

**现状（[静态] 04 P3）**：全仓 `src` 无「命令类型 → 图标」映射；`ToolCallHeader.tsx:142-171` 的 `toolIcon` 仅按**状态**（running→spinner / success→CheckCircle2 / error→XCircle / else→CircleDot）。`tool-presentation/*` 只产中文字符串标签，不产图标 token。

**做什么（最小映射，防过度设计）**：

1. 在 `tool-presentation/` 新增**一个纯函数 + 一个最小图标键表**（决策 12 裁决「实现最小图标映射」）：
   - `tool-presentation/toolCommandType.ts`（新）：`toolCommandType(tc): ToolCommandKind`，复用 `toolDomainDescriptions` 的**域判定逻辑**（shell / network / mcp / task / read / write / edit / workspace / delete / list / search / subagent / timer / note / misc 等，与 13 类域对齐），纯函数、无 store 依赖、无 React 依赖（只出 kind）。
   - `tool-presentation/toolCommandIcon.ts`（新或并入 toolCardPresenter）：`ToolCommandKind → lucide IconComponent` 的最小表（每 kind 一个图标，如 shell→Terminal、edit→FileEdit、network→Globe、search→Search、note→NotebookPen、write→FilePlus、delete→Trash2、timer→Timer、subagent→Bot、read→FileSearch、list→FolderOpen、task→ListChecks、mcp→Plug、misc→Wrench）。
   - **图标 token 只放展示层**（tool-presentation），组件端 `ToolCallHeader` 消费；不接入其它判断（安全判定仍归引擎权威，见决策 4）。
2. **`ToolCallHeader` 图标策略改为「类型图标 + 状态修饰」**：类型图标常驻（命令类语义），运行/成功/失败状态用现有角标/颜色/晶片叠加（保留状态图标逻辑，不删）。**不推倒重做**，仅把 `toolIcon` 的 `else` 分支从固定 `CircleDot` 改为 `toolCommandIcon(kind)` 为主、状态要素补充。
