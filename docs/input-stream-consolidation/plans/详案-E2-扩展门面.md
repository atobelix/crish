## 1. 做什么（4 项逐条）

### ① ToolRegistry + register_runtime + MCP 统一门面（现成等价物显式登记为扩展点入口 + 评估 mcp::register_plugin_server 生产装配）

- **目标形态**：`ToolRegistry`（registry.rs:23）是 Rust 工具接入的唯一登记面（register：:40、register_runtime &self 后置注册：:49、list_definitions 定义改写链：:162）。MCP 工具经 `McpToolAdapter` 适配为 `Tool` 后并入同一 registry。**E2 不做新 class/新组件**——门面 = 文档登记 + 收敛「引擎侧插件运行时 = ToolRegistry + register_runtime + register_plugin_server」这一 canonical 入口。所有外部工具（内置 33 个 / 浏览器 `browser_*` / 电脑 `computer_*` / MCP `mcp_<server>__<tool>`）都经 `register_runtime` &self 后置注册并入运行集。
- **关键文件域**：`crates/agent-tools/src/registry.rs`、`crates/agent-tools/src/mcp/mod.rs`（register_plugin_server）、`apps/agent-workbench/src-tauri/src/engine_build.rs`（装配面：`register_plugin_mcp_server` :654 + `browser_attach_mcp_server_config` :682）。
- **改动性质**：**登记 + 门面化**；`register_plugin_server` 生产装配需一次**评估结论落文档**（见下方评估框）。

### ② 扩展点 A/B/C/D 承载面登记表（可指认承载面 = 文档 + 代码登记）

> 每个扩展点给「现状承载缝 | 待补登记 | 归属维度」。见 §1 末尾的**统一登记表**。

- **A 注入时机（AgentInputQueue 三环 + context-state 类型）**：承载缝 = `AgentInputQueue` 三环（input.rs:163，Force/Steer/FollowUp）+ `PendingNudgeChannel`（steering/nudge.rs:182，D8 合规用 `InputEnqueueMode::FollowUp` 将 nudge 排下一条）+ 编排层 `PendingMessageQueue`（orchestrator/steering_queue.rs:111）。**待补登记**：动态状态注入 `context-state` 节点（模型名/权限/思考模式，00 草案 §4 A 行「缺内容产生器贡献面」）——该**类型由 I1/T1 承载**（I1-α context-state 挂用户提交、T1 事件类型扩展），E2 只把「内容产生器注册表」作为 A 承载面的**登记名**落实（依赖 I1 把 context-state 落成真实类型/通道后再登记，本详案不超前实现）。
- **B 提交时机（输入队列三档——不新增 kind，接口两实现法则）**：承载缝 = `AgentInputQueue` 三环 + `InputEnqueueMode`（input.rs:71：force/steer/followUp）。**裁决（independent-plans/02 §3.5-3 + 内核 §7 纪律 2）**：三档是**唯一实现**，`InputEnqueueMode` **保持枚举、暂不新增可注册 kind**——第三方可扩展 kind 属「为『未来』建抽象」，违反接口两实现法则与反过度设计红线。E2 只登记「B = 核心已内建三档队列」这一承载面，配一语句说明「如需第三方提交策略 kind，须待 ≥2 真实实现出现再抽象」（纪律保持不破）。
- **C 审查策略（exec_verdict 单一链——P1 已建）**：承载缝 = `exec_verdict.rs:99` `ToolExecutor::call_verdict` → `approval_router` → `permission.rs` 三态（decide/decide_command/decide_command_with_revert）+ `Option<Arc<dyn ApprovalGate>>`（tool_events.rs:148）。**PendingMod 差异（源码形状核实）**：`ToolCategory`（conex-types/tool.rs:14）**仅作事件载荷**，`executing_tools.rs:71` 生产硬编码 `ToolCategory::Internal`，不参与裁决分派——这正是 P1「工具类别 → 策略注册表」要修的缺口（P1 主导，E2 提供注册面接口形状）。E2 登记 C = `exec_verdict` 判点作为单一审查链承载面，并在登记表注明「类别轴依赖 P1 完成后才真正分派」。`permissions.ts` 死类型族（shared-types/src/permissions.ts:4,31,36,52）由 **P1 删除**（总计划框架 §3 决策 2：唯一归属 P1，E2 不重复计数）。
- **D 撤回策略（类别 → 回滚注册表——R1 建）**：承载缝 =**待建**（09 §③ D：当前无统一撤回/截断缝）。E2 登记 D = 「类别 → 回滚策略注册表」为 R1 的**入站承载面**，出站为 `TimelineTruncate` 事件（T1 承载）。R1 六步（含类别注册表、trash.rs 回滚底座、边界冻结机制）由 R1 主导；E2 只在前置依赖到位后把 D 登记进统一门面表，**不超前实现回滚注册表**。trash.rs（conex-fs/src/trash.rs:145 `trash_file`）为现成回滚底座，登记为 D 的**动作素材**。

### ③ before_* 覆盖式只作语义借鉴（拦截/改写已内建 ToolMiddleware/ApprovalGate/SteeringStrategy——不新造事件总线）

- **目标形态**：Pi `before_*` 事件「可拦截、可改写、可返回结构化结果」的语义，Conex **已内建**（00 草案 §2.1 核心缝面）：
  - `ToolMiddleware`（middleware.rs:95）四钩子 `on_definition/before_execute/on_result/on_error`——**执行前拦截/改输入、执行后改输出**，即 Pi `before_*` 的拦截+改写等价物；
  - `ApprovalGate`（tool_events.rs:148）产出 `Approved/Denied/Expired`——即 Pi 审批决策的 Rust 等价物；
  - `SteeringStrategy`（steering/mod.rs:157）产出 `InjectMessage/InterventionRequired`——即 Pi 可返回结构化覆盖的等价物。
- **E2 动作**：把这些**已内建**缝登记为统一门面的「能力条目」，**明确禁止**再为 A/B/C/D 新造一套 `before_*` 事件广播管道。理由（独立方案 02 §1.1-5）：新造一条 before_* 事件总线 = **第五条互不接线的扩展轨**（已有 plugin-sdk 运行面 / plugin-sdk Plugin 接口 / CrishPlugin / settings-adapter / Rust ContributeViewRegistry 前车之鉴 05 §③ P1-P6），直接违反抽象纪律（00 草案 §7）与反过度设计红线。**改写的承载面就是 ToolMiddleware 的 before_execute / on_definition。**
- ⚠️ **诚实边界**：`HookRegistry`（hooks.rs:410，14 事件 observe/on）是否被 `SessionLoopProducer` 生产装配 `[待真跑]`（09 §② 2.1 判定「默认 None 不装配」，产品装配面经 engine_build 实证无 `with_hooks` 注入）。E2 对 HookRegistry 作「引擎生命周期事件广播 canonical」登记时，需主控补一次真跑（DevTools/断点 inspect `SessionLoopOptions.hooks`）确认生产是否装配——若未装配则不强制（工具接入 canonical 不依赖 hooks），若已装配则纳入门面登记范围。**不影响本研究的主结论**（工具接入 canonical = ToolRegistry+register_runtime 已实证）。

### ④ 壳层装配收口（参考 DSH cordis 装配：C1b 移出的 BackupMiddleware/RecoverySteeringStrategy 注入点登记为装配面）

- **目标形态**：C1b（详案-C1 §1.C1b）已将 `BackupMiddleware` 移出 `SessionLoopOptions::default()`（loop_options.rs:251）→ 壳层 `run/run_launch.rs:605` 显式注入；`RecoverySteeringStrategy::default()` 移出 `AgentSessionLoop::new()`（loop_runner.rs:62-65）→ 壳层 `engine_build.rs` `SessionLoopProducer` 注入。**E2 把这些壳层注入点登记为「装配面」**，参考 DSH《21 审计》§4 的 cordis 装配语义（把「核心不认知具体实例、实例由壳层注入」这一纪律在 E2 门面文档固化）。
- **关键文件域**：`apps/agent-workbench/src-tauri/src/run/run_launch.rs`（:605 tool_middleware 注入点）、`apps/agent-workbench/src-tauri/src/engine_build.rs`（SessionLoopProducer :1318、produce :1363、with_options :1519-1521、steering 注入点）。
- **改动性质**：**登记**（C1b 已做搬移；E2 只固化装配面清单并纳入顶层验收），不重复搬移。

### plugin-sdk A 轨（`Plugin`/`definePlugin` 轻量约定）go/no-go 去留裁决建议

- **现状（源码形状核实）**：`packages/plugin-sdk/src/index.ts:4-19` 定义 `Plugin` 接口（hooks 用 `unknown` 入参 `onSessionStart/onSessionEnd/onToolCall/onMessage`）+ `definePlugin` 恒等函数。与 shared-types `PluginLifecycle`、crish-desktop `CrishPlugin` **三套并存且语义重叠**（05 §② 表、§③ P2）。
- **裁决建议**：**从产品入口** `index.ts` **移除 `Plugin`/`definePlugin` 轻量约定**（归 E1 删除），统一到 shared-types 契约 + ContributePointRegistry（前端 View 轨由 D4/E1 收口）。E2 的 A 轨评估结论：**该轻量预定不承载「注入内容产生器」职责**（05 §③ A：`onSessionStart` 只签名不绑定，无「往时间线插 context-state」意图；08 §③ A：A 承载在 Rust 队列 + 内容产生器注册表，不在 TS 轻量接口）。故 **A 轨删除不损失任何 A/B/C/D 承载能力**——这是 E2 明确给出 go/no-go 的依据。
- ⚠️ 若 E1 保留 contribute View 轨（D4 主导），E2 不越权；本详案只裁决「`Plugin`/`definePlugin` 轻量约定 go = 删」。

## 3. 依赖与逻辑顺序

### 3.1 E1 先于 E2（先删死轨再立门面——避免第五条轨）

- **为什么**：04 独立方案 §E2 明确「E1 删除死插件轨后，E2 才有干净的 ToolRegistry+register_runtime+MCP 唯一门面可登记」。若 E2 先立门面，会撞上 note_w4c_contribute / plugin-sdk B 轨 / `Plugin` 轻量约定等死轨，门面登记就变相「第五条互不接线的扩展轨」。**顺序：E1（R7）删除 → E2（R8）登记/门面化。**
