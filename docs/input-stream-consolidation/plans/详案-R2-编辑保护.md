## 1. 做什么（新增/修复清单）

### 概念目标（本维度收敛到的单路径形态，一句话）

> 所有**可编辑物**（笔记块正文叶 / 草稿 / 设置表单项）在编辑期内都持有**本地编辑会话**（open→commit/invalidate，携带对象级 `rev` 对齐 CT-01）；当引擎侧撤回/截断（R1 `TimelineTruncate` 事件）或 collab 远端合并冲突发生时，订阅端对「有编辑会话的对象」发射 `invalidate`——**对象失效后编辑面立即失效**，杜绝「UI 还在编辑、后端已发送/已覆盖」的撕裂。

### 1.1 R2-a ①　编辑会话抽象（open → commit/invalidate 生命周期，前端侧）

**现状（源码核实）**：前端**不存在**「编辑会话」抽象；唯一保护是 `StrictContentRowLeaf.tsx:133` 的 `dirtyRef`（开环、永不复位）与 `slashSendDraftManager.ts:18` 的一次性瞬态快照。后端已有三类可复用先例（analysis/15 §④）：`write_paths_state.rs` 的声明记账/Rail 模式（编辑持有去中心化，**非全局锁**）、`conex-db/src/lease_guard.rs` 的编辑租约、CT-01 `doc.rev` 版本契约。

**做什么**：

1. **新增前端唯一「编辑会话」轻量抽象**（`apps/crish-desktop/src/api/editSession/`），形态 = 对象 id → 会话状态：
   - `open(objectId, baseRev)`：声明持有。无竞态则建立会话（记录 `baseRev`）。
   - `commit(objectId)`：提交并**失效**——推进 `rev`、清会话、广播失效（订阅方刷新）。替换 `dirtyRef=true`/`clearDraftSnapshot` 的一次性清空。
   - `invalidate(objectId, reason)`：对象被远端/引擎撤回/截断/合并冲突 → 对该 id 的会话发失效（见 R2-b）。
   - 会话表**携带对象级 `rev`**（与 CT-01 的 doc.rev 对齐，analysis/15 §④「版本契约」）；提交时带 `expect_rev`，不符 → 冲突上报，不静默 LWW（对齐 `persistence.rs PersistError::Conflict`）。
   - **复用而非新建**：本抽象只做「声明+冲突拒绝」记账（对齐不变量 7「复用 write_paths/lease_guard 先例，不新增全局锁」），模板读 `write_paths_state.rs WritePathRegistry`（analysis/15 §④），但抽象到「节点 id」而非「文件路径」。
2. **编辑会话事件「不可丢且独占」**（核心模型不变量 7 行、00-核心逻辑模型草案.md 与不变量 6 对称）：编辑行为是「进行中维度的独占子类」——open/commit/invalidate **是必达事件**，不是可丢的增量事件。前端本内以 store/session 级**事件总线**承载（内存态即可，**不进消息时间线 seq**，见禁止项 3 与 17 审计纪律：编辑/定制状态属独立带）。
3. **不改后端**：本抽象是**前端侧**编辑持有态；CT-01 的 CAS 检测在 `conex-doc-collab/persistence.rs` 已是「检测并报错」语义（:3-6、:64-72），前端据此上报 conflict。R2 不新增 Rust 端锁/单写面。

**目标形态**：编辑块对象统一走 `editSession.open→commit/invalidate`，任何地方不再出现裸 `dirtyRef.current = true` 作开环脏标。

### 1.1 R2-a ②　dirtyRef 开环脏标修复（StrictContentRowLeaf.tsx:133）

**现状（源码核实，核心缺陷）**：`StrictContentRowLeaf.tsx:133` `dirtyRef`（`useRef(false)`）在 `:172`（runCommit 成功）、`:188`（onCompositionEnd）、`:197`（onInput）全部 `dirtyRef.current = true`，**永不复位**；`:140` 投影刷新 effect 在 `dirtyRef.current` 时跳过写 `el.textContent`。后果（analysis/15 §2.3）：叶与投影永久脱节——本地一次编辑后，远端合并/元数据更新/回退**永远**无法再同步该叶，直到重挂载复位。无版本/CAS 比对。

**做什么**：

1. **删除裸 `dirtyRef.current = true` 的开关逻辑**（:172/:188/:197），改为经编辑会话生命周期**受控**：
   - 首次合法 onInput/onCompositionEnd → `editSession.open(blockId, baseRev)`。
   - commit 走 `commitProductMdPrefixFromLeaf` 成功后 → `editSession.commit(blockId)`（**显式复位 dirty** + 推进 rev），叶重新可被投影刷新写入。
2. **投影刷新 effect 改为「dirty = 会话仍 open 则跳过，会话已 commit/invalidate 则放行」**：`:136-147` 的条件从「裸 dirtyRef」改为「存在未关闭的编辑会话」（`editSession.isOpen(blockId)`）。
3. **保留 composing 双守卫/commitInFlight**（:128-131）不变；这些是防重入机制，非脏标。
4. **component 测**：新增「本地编辑 commit 成功后，投影再次刷新能写入该叶」断言（dirty 后投影可重覆盖），对齐 independent-plans/04 §3.3 R2-a 验收。

> 关闭点：`dirty` 只在「编辑会话已 commit/invalidate」时复位。这与 1.1① 的 commit 语义绑定——**编辑会话关闭即复位**。

### 1.1 R2-a ③　双 follow_up 竞态关闭（composer 队列 ∥ useSlashSend，drain 防抢跑）

**现状（源码核实，竞态残留）**：两条「运行中发 follow_up」路径并存（analysis/15 §2.1 场景 1 竞态残留 + §⑤ 收敛度量）：

- `useChatComposerProps.ts` composer `onSend`（:442-466）：`queueMode && isProcessing` → `enqueueMessage`（清输入入队）+ `runControl.followUp`。
- `useSlashSend.ts`（:157-182）：`isAiBusy` → `decideSendWhileRunning==='follow_up'` → `enqueueFollowUpMessage`（:165）+ `runControl.followUp`。

**竞态窗口**：`editQueuedMessage`（useChatComposerProps.ts:420-429）把队内消息**移回输入框**编辑；若此刻 processing 恰结束，drain effect（:470-484）仍取 `queuedMessages[0]` 发送——用户正在输入框编辑的这项**不被发送也不被清空**，且 `drainLockRef`（:469）**只防重入、不防抢跑**。

**做什么（依赖 I1 队列归一）**：

1. **先确认 I1 已归一 follow_up 唯一入口**（前置）：I1（详案-I1 §1.1①）把「跨 run 下一条用户消息」收敛到 orchestrator `PendingMessageQueue`，composer 队列与 useSlashSend 的 follow_up 归一条调用面。R2-a ③ 在**该唯一入口之上**关竞态，不另造第三条。
2. **关闭 drain 抢跑窗口**：drain effect（:470-484）发送 `queuedMessages[0]` 前，**校验队首项是否在被编辑**：
   - 若「编辑会话正 open 于该消息（被 editQueuedMessage 移回输入框的原 id 仍是当前编辑会话对象）」→ **跳过本次 drain 该队首**，不抢发；等用户提交/会话关闭后再 drain。
   - 组件级实现：`editQueuedMessage` 移回输入框时**关闭**该消息的「可 drain」标记；drain 读该标记决定是否送。
3. **同源归一**：composer `onSend` 的 follow_up 分支（:447-453 `import compositionRoot...runControl.followUp`）与 useSlashSend 的 `enqueueFollowUpMessage` 底层**共用同一 `runControl.followUp` + 队列归一后的单一入队**，不再两个队列容器（双 follow_up = 1 的概念已由 I1 归一；R2 只收 docker 竞态）。
4. **竞态测试**：`editQueuedMessage` 后 processing 结束 → 断言 drain 不抢发被编辑项（`queuedMessages[0]` 与编辑中 id 冲突时被跳过），对齐 04 §4.2 + 02-总计划 R2-a。

### 1.1 R2-a ④　设置页 cfgDraft 失效订阅（useModelProfilesState）

**现状（源码核实）**：`useModelProfilesState.ts:46-48` `profiles` 一次 `loadProfiles()`；`:74` `cfgDraft`（未保存配置草稿）；`:92-99 refresh()` 仅手动重载+重选；`openConfigFor`（:229-244）从 `getModelMeta` 一次性快照进 `cfgDraft`。**无外部变更订阅**：模型激活/权限/密钥被其它 tab/窗口/Rust 端变更时，已打开的 `cfgDraft`/`keyDraft` **不失效**，保存时用陈旧草稿整体覆盖（LWW，analysis/15 §2.4）。

**做什么**：

1. **订阅外部变更 → 失效**：`useModelProfilesState` 增加对「profiles 外部变更/活动模型/密钥变更」事件源的订阅（复用前端已有的事件面，如 `emitUiEvent('profiles-changed')` / 新增 `profiles-invalidated` 事件）。触发条件：
   - 有未保存 `cfgDraft`/`keyDraft`/`nameDraft` → **提示用户**（「配置已被外部修改」），不静默覆盖；用户确认后重载或丢弃草稿。
   - 无未保存草稿 → 直接 `refresh()` 重载。
2. **`saveConfig`（:251-256）带对象级 rev/核对**：保存前对 `selected`+`configOpenId` 校验外部是否已变更（比对加载时快照），避免陈旧 LWW 覆盖（对齐 review.md §11 缓存失效 + analysis/15 §④ "设置表单 refresh 改订阅失效"）。
3. **`openConfigFor`（:229-244）/`handleManualAdd`（:211-227）建立的 `cfgDraft` 挂到编辑会话**：R2-a① 抽象的 open，外部失效时走 invalidate。
4. **组件测**：外部模型变更 → `cfgDraft` 失效/提示（组件测断言），对齐 04 §3.3 R2-a 验收。

### 1.1 R2-a ⑤　MessageSnapshots 'edit' 死枚举处置（裁决：删）

**现状（源码核实）**：`MessageSnapshots.ts:124` `operation: 'withdraw' | 'regenerate' | 'archive' | 'batch-pin' | 'edit'` 的 `'edit'` **无生产写入方**（grep 全仓仅定义处，无 save/接线；analysis/15 §2.2 gap1 + §⑤ "死枚举删或接线二选一"）；产品无「编辑已有消息正文」能力（唯一迁移 completed→processing(regenerate)，StatusTransitionGuard）。

**裁决建议**：**删除 `'edit'` 枚举**（独立方案 04 §3.3 R2-a 5 裁定 + 抽象纪律 5「零消费者=删候选」）。理由：

- 产品现在不接线、未来「消息正文重编辑」属扩展时机；先留位 = 悬空死枚举。
- R2-a ⑤ 删除后，`MessageSnapshots` 的 `operation` union 收敛为 4 个实际写入方。
- 若未来开放消息重编辑，回滚面可再引入 `'edit'`（analysis/15 §②gap 1 建议已留恢复语义，删枚举不损回滚面本身）。

> 注意：这与 R2-a① 的编辑会话抽象**不冲突**——编辑会话管「编辑中的块/草稿/设置」持有态；`MessageSnapshots` 管「消息撤回/regenerate 的快照回滚」。`'edit'` 死后没有编辑会话给它接线，删。

### 1.2 R2-b ⑥　失效传播：撤回/截断（R1 timeline-truncate 订阅）→ invalidate 编辑中对象

**现状（源码核实，缺口）**：R1 的 `timeline-truncate` 事件在 crates 全仓**零命中**（grep `TimelineTruncate` 无匹配），撤回只走前端 `withdrawMessage`（sessionMessageActions.ts:93-137，物理截数组，不写事件、不按 seq、不联动停 run）。前端**无截断/撤回 → 编辑中对象 invalidate 的广播**（analysis/15 §2.2 gap2 + §④ invalidate）。

**做什么（硬依赖 R1 先落地 `TimelineTruncate` 事件可供会话时间线订阅）**：

1. **订阅 R1 `timeline-truncate` 事件**（R1 六步第 4 步「投影重放到 boundary」的消费接口之一）：前端会话时间线在收到 `TimelineTruncate { boundary_seq }` 时：
   - 遍历当前存活的**编辑会话**，凡对象 id 的 seq ≥ boundary_seq（即被截断范围内）→ 发 `invalidate(objectId, 'truncate')`。
   - 语义（对齐 analysis/15 §④）：对象仍在 DOM → **提示重新确认**（「该内容已被撤回/截断」）；对象已被撤回 → **丢弃编辑会话**（composer 文本回填由 R1 步骤 5 处理，不在此重复）。
2. **`withdrawMessage`（sessionMessageActions.ts:93-137）收口联动**：当撤回/截断导致编辑中消息被截断时，`withdrawMessage` **跳过正在编辑 id 的提示**并走 `invalidate`（对齐 analysis/15 §②gap2「无编辑会话无效化广播」的补点）。
3. **collab conflict 本地乐观撤销/合并**（`packages/block-paper/src/leaves/intentBridge.ts:253-312` `createCollabApplySink`）：
   - 现状：对 apply 冲突仅透传 `{ok:false, reason}`，`submitIntent` 返回 `{ok:false, code:'sink_reject'}`（:181-188），无本地乐观树/无写回撤销（analysis/15 §2.3）。
   - 目标：`createCollabApplySink` 在 `applied.ok === false`（尤其 reason 含冲突/rev 不符）时，对**对应编辑会话**发 `invalidate`，UI 展示冲突并让用户重新确认/丢弃本地编辑；**不承诺自动合并**（「无需合并」，后端仍是权威真相源，冲突即提示）。
   - **Rust 侧验证面**：`crates/conex-doc-collab`（session.rs:375-402 `emit_commit` → `on_committed_expect` → `PersistError::Conflict`；session_apply.rs:247、session_undo.rs:116-117 P-H2 回滚）已实现 CAS 检测——R2 只读确认冲突错误经 IPC/applyOps 链回传前端带 `conflict` 标识（persistence.rs:52 `Conflict { expect }` Display 含 `conflict`），前端据此触发 invalidate。
4. **R2-b 验收（可执行，含测试）**：模拟 `timeline-truncate`/远端 conflict 事件 → 断言「有编辑会话对象」收到 invalidate、UI 立即失效（无 UI 继续编辑已失效对象）。
