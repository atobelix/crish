## 3. 依赖与逻辑顺序

### 3.1 C1a 须 T2 后（评审 02 §3.1-1 裁决 · 主控已采纳）

- **为什么**：压缩编排外置的「后台任务登记 + Load 端恢复（压缩记录落库/重放）」依赖 conex-db 唯一落点确立。若 T2（持久化轨收敛）未完成，C1a 把「后台登记 + 落库」外置时会撞上 localStorage/RustDb 前端双轨写放大（评审 02 §3.1-1、独立方案 02 §4.1）。因此 **C1a 排在 T2 之后（R4，R2/R3 已含 T2）**。
- **C1a 与 T1**：不阻塞（压缩事件类型 ContextCompressionStart/End 已在 events.rs；C1a 不新增事件类型）。

### 3.2 C1b 与 C1a 顺序

- **C1b 尾随 C1a（同批 R4 内串行，评审 02 §1.2）**：
  - C1a 先搬压缩编排（原子批一次搬完跑绿）；C1b 的反向依赖移出紧随其后；
  - 二者独立面：C1a 是 handlers 编排搬移、C1b 是 loop_options/loop_runner 装配面搬移，**文件域基本不重叠**（C1a 主触 loop/handlers + compaction_dispatch；C1b 主触 loop_options/loop_runner + 壳层）。故可同批串行、由不同 Agent（C1a 独占重 Agent + C1b/C1c 合并，评审 02 §4 工作量均衡建议）。
  - ⚠️ C1b 不能先于 C1a 的前提不成立但建议保持顺序：C1a 把 LoopState 子结构定型后再动默认装配，减少 `with_middleware` 签名联动的耦合面。

### 3.3 C1c 依赖 C1a（先搬移才有缝的形状）
