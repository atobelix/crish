## 1. 做什么（新增/改造清单）

### 1.0 概念目标（一句话）

> **同一事件流只有「一条解析路径 + 一套类型权威」**：实时流与重放水合统一走 generated 契约解析；前端 store 消息类型统一从 generated 派生（保留超集投影字段，非简单别名）；手写第 N 套消息类型与手写事件解析器清零。

### 1.1 事件解析统一走 generated parser（保留 chat-bridge eventParser 为权威）

**现状（[验]）**：

- 实时流单入口：`api/chat-bridge/handlers/eventParser.ts:355` `parseBridgeEvent` 先走 generated 严格 `parseEngineEvent`（`eventParser.ts:365`），失败再走宽容归一器 `ENGINE_NORMALIZERS`（`:343`）；被 `EventRouter.onMsg`（`EventRouter.ts:246`）与 `dataPlaneRouter` 消费。**这是权威解析面，保留。**
- 重放水合：`api/sessionEventHydrate.ts:39-60` `agentEventFromOrchestrator` + `blockText` + `:62-78 toolResult` 手写宽容解析 → `projectEventsToMessages`（`:155-405`）→ SessionMessage。**绕过 generated parser，是第二条解析路径（analysis/01 P6）。**

**语义差异（本方案设计必须覆盖）**：重放事件来自 `core_read_session_events`，形状为 `{ type:'runtime-event', payload:{ event:{...} } }` 信封（[验]：`sessionEventHydrate.test.ts:340-701` 全覆盖 + `sessionEventHydrate.ts:40-44`），且内层事件**缺 sessionId**（仅 message-delta/tool-start 等有 timestamp，message-end 无 sessionId）。而 `parseBridgeEvent`/`parseEngineEvent` 对 message-end 要求 `message` 必填、对 message-delta/tool-start 多数要求字段；`runtime-event` 信封不在 `ENGINE_NORMALIZERS` 内（[静态] grep `runtime-event` in handlers = 零命中）。因此**不能简单把 replay 裸 event 直接塞进 parseBridgeEvent**——必须补一个「信封解包」步骤。

**做什么（分三步，先解包信封、再进权威解析、最后投影装饰）**：

1. **信封解包收敛**：删除 `sessionEventHydrate.ts` 内的 `agentEventFromOrchestrator`（`:39-52`），把它收敛为 `chat-bridge` 域的一个**纯信封解包函数**（新放 `api/chat-bridge/handlers/eventEnvelope.ts` 或并入 `eventParserShared.ts`），只做 `runtime-event → inner event` 的 `type/payload/event` 别名抽取，**不做字段级内容解析**。此解包函数与 `resolveEventType`（`eventParser.ts:89-97`，type/event/kind 别名）语义合并——即统一「信封 type 抽取」这一个小职责到 chat-bridge 域。**解包 ≠ 解析**：解包只负责揪出内层 event 对象交给解析面，不读取 message/block 字段。
2. **内层 event 统一走 `parseBridgeEvent`**：解包出的内层 event（缺 sessionId 的宽容形态）交给现有 `parseBridgeEvent`——它的归一层 `ENGINE_NORMALIZERS` 本就为「缺信封字段」形态设计（`eventParser.ts:6-10` 注释「生成解析器覆盖不了的前端宽容形态（缺 sessionId/timestamp 等）」），且 `parseEngineEvent` 对缺 sessionId 失败后落归一层。`projectEventsToMessages` 因此改从 `EngineEnvelope`（generated `EngineEvent`）读 `event.message.blocks` / `event.block` / `event.call` 等，**不再手写字段级宽容**。
3. **保留语义不变量**：projectEventsToMessages 的 id 稳定 / 幂等 / turnIndex 分段（`sessionEventHydrate.ts:170-405`）是**投影层语义**，与「解析层」分离——不得因换解析而丢。即：**解析换 generated，投影语义保留**（见 §2「不降级」）。

**验收**：`rg 'agentEventFromOrchestrator|blockText' apps/crish-desktop/src` 为空（`blockText` 统一用 `eventUtils.ts:14` 或生成的 block 结构；见 §1.3）。

### 1.2 前端 store 消息类型从 generated 派生——明确 SessionMessage 超集处理（禁止简单别名）

**现状（[验]）**：

- generated `AgentMessage`：`packages/shared-types/src/generated/engine/types.ts:74-82`（`id/role/createdAt/blocks/metadata?/clientMessageId?/content?`）。
- generated `AgentMessageBlock`：`types.ts:110` = `Text{type:'text',text}` | `Thought{type:'thought',text,redacted?}` | `ToolCall{type:'tool-call',id,toolName,input}` | `ToolResult{type:'tool-result',toolCallId,toolName,output,isError}`。
- 前端 `SessionMessage`：`apps/crish-desktop/src/store/types.ts:385-433`（`id/sender/text/thinking/thinkingTurns/timestamp/toolCalls/toolCallResults/blocks/streamTextOffset/thinkingTime/images/errorDetail/precomputedHtml/cacheMetrics/status`）。
- **超集证据**：`SessionMessage` 的 `sender`(=role 语义)、`text`(≠generated `content`)、`toolCalls`/`toolCallResults`/`thinkingTurns`/`blocks`/`cacheMetrics`/`errorDetail`/`precomputedHtml` 等**大量字段在 generated `AgentMessage` 中不存在**（[静态] 对照 types.ts:74-82 vs store/types.ts:385-433）。

**结论（采纳 plan-reviews/01 ②#5 + independent-plans/05 §2.3.1）**：`type SessionMessage = generated.AgentMessage` 是**错误方案**——会丢超集字段，属「纯别名降级」。精确方案如下。

**超集字段的派生方式：扩展接口（interface extends）做投影装饰结构，事件投影填充**：

```
// 权威契约：generated
import type { AgentMessage, AgentMessageBlock } from '.../generated/engine';

// 前端投影装饰结构（不是第二套事件类型，是「事件派生投影」的展示形状）
export interface SessionMessage // 删原手写字段体，改为：
  extends Pick<AgentMessage, 'id' | 'clientMessageId' | 'metadata'> {
  // —— 事件投影字段（保持超集，前端专有；不改事件 schema）——
  sender: 'user' | 'assistant';        // 由 role 投影（tool/system 不回投 store）
  text?: string;                       // 由 message-end content / text blocks 投影
  thinking?: string;                   // 由 thought blocks 投影
  thinkingTurns?: Array<{...}>;        // 投影装饰（前端结构化思考分段）
  timestamp: number;                   // 由事件 timestamp 投影
  status?: SessionMessageStatus;       // 前端生命周期态（queued/processing/completed/error）
  toolCalls?: MessageToolCall[];       // 由 tool-start/end 投影（前端工具行）
  toolCallResults?: SessionMessageToolCallResult[];  // 工具结果回执投影
  blocks?: MessageTimelineBlock[];     // 由 AgentMessageBlock 投影装饰（见 §1.3）
  streamTextOffset?: number;           // 流式切分偏移（展示投影）
  thinkingTime?: number;
  images?: MessageImageRef[];          // 前端图片索引
  errorDetail?: { message: string; kind: string; technical?: string };
  precomputedHtml?: string;            // markdown 缓存投影
  cacheMetrics?: MessageCacheState | null;  // 消息级缓存指标投影
  // blocks 派生后还与生成契约保持「可溯源」：保留 AgentMessageBlock → 投影块的映射函数
}
```

**派生路径（禁止类型别名，用「投影填充」）**：新增纯函数 `projectAgentMessageToSessionMessage(agent: AgentMessage): SessionMessage`（放 `api/chat-bridge/handlers/` 或 `api/messageProjection.ts`），由 live 路径（`messageHandlers.onMessageEnd`）与 replay 路径（`projectEventsToMessages`）共用——把 generated `AgentMessage.blocks` 逐块 `projectAgentMessageBlock` → 前端 `MessageTimelineBlock`。**两条路径共用同一投影函数，杜绝各写一套。**

**类型权威单一**：`SessionMessage` 的**结构定义唯一**放在 `store/types.ts`（前端投影装饰接口）；其**来源字段**（id/role/blocks 等）从 generated 派生。**禁止**在 `layoutStore`/`streamingStore`/`historyMessages` 等处复制第二份 `SessionMessage` 字段体。`layoutStore` 现有 re-export（`layoutStore.ts:122-137` `export type { SessionMessage, ... } from './types'`）保留为**别名转发**（合法，别名转发不是第 N 套定义）。

## 3. 依赖与逻辑顺序
