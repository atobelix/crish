## 1. 做什么（5 项逐项）

### 1.1 ① 清 plugin-sdk 入口接口（保留 A 轨给 E2 评估）

**问题（analysis/05 §② P2/P3）**：`Plugin`/`definePlugin` 轻量接口与 `CrishPlugin`、shared-types `PluginLifecycle` **三套并存**；hooks 全用 `unknown` 无 payload 绑定（误导性「通用插件接口」，与真实引擎运行面对不齐）。

**实证（源码形状）**：

- `packages/plugin-sdk/src/index.ts:3-19` 顶部定义 `interface Plugin`（4 行 `name/version/description/hooks/permissions`，hooks 用 `unknown:10,12`）+ `definePlugin`（17-19）。
- 全仓 grep：`definePlugin` / `interface Plugin`（plugin-sdk 专属轻量约定）在 `apps/` 产品代码 **零命中**（本会话实查 grep `definePlugin|@crish/plugin-sdk` 于 `apps` 输出为空）。
- shared-types `PluginLifecycle`（`packages/shared-types/src/plugin.ts:67,107`）是 **type 真源**（engine 生命周期契约），plugin-sdk 已 re-export `manifest/manifest.ts:10`。

**做什么**：从 `packages/plugin-sdk/src/index.ts` **移除顶层 `Plugin` 接口 + `definePlugin`**（:3-19），收敛到 shared-types `PluginLifecycle`。**保留**其下的 A 轨运行面——即 `registry/*`（`PluginRegistry` 引擎侧运行时）、`api/plugin-api.ts`、`hooks/lifecycle.ts`、以及 contribute View 轨库与 `registerFlavour`——原样不动，交 E2（Rust 扩展门面）评估能否承载扩展点 A/B/C 贡献面。**本详案仅删入口误导接口，不评估 A 轨去留**（归 E2）。

### 1.2 ② 删 `apps/crish-desktop/src/plugins/` 整目录

**问题（analysis/05 §② P1 / §③ P1；analysis/16 §④ D1、G2/G3）**：`src/plugins` 是隔离死代码子系统——PluginRegistry + 四官方插件 + usePluginStore + index 门面 + 自身测试，产品 UI import 边 = 0。

**实证（源码形状，本会话实查）**：

- 全仓 grep `src/plugins` / `from '.../plugins` / `usePluginStore` / `registerOfficialPlugins` / `PluginRegistry` 于 `apps/crish-desktop/src`：**仅命中 `src/plugins/` 目录自身**（`index.ts:18-25` re-export、`index.ts:27-31` 自举）与 `PluginRegistry.test.ts`（:4,6,14,18,268-294）。
- `plugins/index.ts:36-44`：`registerOfficialPlugins()` 自举 `registerOfficialPlugins()` 注册四插件，但 **无任何消费方调用** `registerOfficialPlugins()`（grep 产品代码零命中入口导出）。
- 四插件 `activate` 只挂 DOM CustomEvent（audit 05 §②：browser / computer-use / markdown-editor / follow-up），无 UI 渲染、无引擎联动；其能力已有真身：浏览器/电脑走独立引擎桥（`browserSessionApi`/`computerSessionApi`）、follow-up 走 `api/followUpSuggestions.ts`、markdown 走 `core_md_render`（audit 16 X1-X5 实证）。

**做什么**：整目录删除 `apps/crish-desktop/src/plugins/`（9 文件：`index.ts`、`PluginRegistry.ts`、`PluginRegistry.test.ts`、`usePluginStore.ts`、`types.ts`、`plugin-browser/`、`plugin-computer-use/`、`plugin-follow-up/`、`plugin-markdown-editor/`）。

### 1.4 ④ `slashCatalog` 假数据处置（裁决建议）

**实证（源码形状，本会话实查）**：

- `slashCatalog` 实存于 **`packages/block-paper/src/chrome/slashCatalog.ts`（72 行）**——**不在 E1 文件域**（E1 文件域见 §4，只覆盖 `apps/crish-desktop/src/plugins`、`crates/agent-tools/note_w4c_contribute`、`packages/plugin-sdk/src`）。
- `DEFAULT_SLASH_CATALOG`（:18-27，8 项硬编码）+ `filterSlashCatalog`（:51-72），被 `SlashMenuModel.ts` 消费（`block-paper/src/chrome/SlashMenuModel.ts:35`）；文件头 :4 自承「假数据；不接线真实 flavour 注册表」。
- `registerFlavour` 注册表是 plugin-sdk contribute 轨的能力（`packages/plugin-sdk/src/contribute/flavours.ts`、`registry.ts:227`）——即 slashCatalog 与 flavour 注册表两头都是 **plugin-sdk / block-paper 的 View 展示投影域**（analysis/08 §31 / 00-核心逻辑模型草案 D5）。

**裁决建议（二选一，本详案主张 A）**：

- **方案 A（推荐 · 本详案）**：`slashCatalog` **不接 flavour 注册表**，维持「内置默认目录 + 过滤」纯展示语义，仅在 `slashCatalog.ts` 文件头把「假数据」批注改为「**内置默认目录**（产品当前无 flavour 注册表宿主；若 E2 落地 registerFlavour，再渐进接线）」——即**不删不接，明示为产品内置默认面**。理由：`slashCatalog` 是 `filterSlashCatalog` 的**函数数据源**，被 `SlashMenuModel` 真实消费（非死层），其「假数据」仅指「未接 flavour 注册表」而非「无消费」；把 8 项目录接 flavour 注册表会让「项目目录」依赖「插件注册表」，把非插件的项目默认目录错误地架到插件机制上（违反反过度设计——本身是纯静态默认目录，不需要动态注册表）。
- **方案 B（放弃）**：删除 `slashCatalog` 的 `DEFAULT_SLASH_CATALOG` → 接 flavour 注册表。理由放弃：`slashCatalog` **不在 E1 文件域**；接 flavour 注册表是 E2「registerFlavour 宿主接线」的责任，且把非插件目录架上插件机制属过度设计；`SlashMenuModel` 需保持「零插件依赖也能用」的内置默认（对齐 16 §「核心不依赖扩展」）。
- **归属**：`slashCatalog` 的**实体改动**留给 E2（或 D4 展示投影）统一裁定，**E1 轮只出裁决建议、不动 `packages/block-paper`**。

### 1.5 ⑤ plugin-sdk B 轨（ContributePointRegistry 无宿主消费）收口

**问题（analysis/05 §③ P4；评审 01 决策 D12）**：plugin-sdk `ContributePointRegistry`（`contribute/registry.ts:75`）**是库、无产品前端宿主**——settings adapter、src/plugins、contribute 轨三套插件 UI 面互相隔离，contribute 轨无前端接线点注释（`pluginRegistryAdapter.ts:89` PLUGIN_RUNTIME_HOOK 接线点只是注释，未接线）。

**实证（源码形状）**：

- plugin-sdk 运行时面（`registry/*`、`api/plugin-api.ts`、`hooks/lifecycle.ts`）= **引擎侧插件运行时**雏形（分析 05 §②），有 `CRISH_ALLOW_UNSAFE_PLUGIN_IMPORT` 安全门控——这是 E2 要评估的 **A 轨**，**保留**。
- ContributePointRegistry View 轨（`contribute/registry.ts`）= 无前端宿主接线（前端 crish-desktop 的三个设置/插件面均不消费它）。

**B 轨收口裁决**：**A 轨保留给 E2 评估，B 轨（ContributePointRegistry 无宿主消费部分）在 E1 不做物理删除**，但**明确「B 轨在有宿主前不新增消费/不接线、不作为可点路径」**：

- plugin-sdk 的 `Plugin`/`definePlugin` 入口（§1.1）已从 index.ts 移除——这是对 B 轨的关键隔离：插件作者不再经误导性轻量接口进入。
- `ContributePointRegistry` 库本身**保留**（因 plugin-sdk 的 View 轨库与 `registerFlavour` 一并保留给 E2 评估；`slashCatalog` 将来接 flavour 注册表也要靠它）。
- **定义**：B 轨 = 「ContributePointRegistry 作为未接线扩展宿主的状态」；**E1 收口动作 = 从所有入口与文档移除「B 轨是可用可点路径」暗示，把它降为「待 E2 决定宿主的有库无宿主库」**；不把任何新代码接进它，不建第二个宿主。若 E2 判定无宿主 => 连 B 轨库一并删（归属 E2，本详案不占）。
