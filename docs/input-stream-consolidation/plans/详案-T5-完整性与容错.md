## 1. 做什么（5 项逐项）

### 1.1 ① 引擎崩溃感知（T5-a · 决策 6 承载点）

**问题（18 §5.2 / 溢出 3）**：`engineReady` 是「假就绪」——`engine_build.rs` 的 `EngineHandle.ready` 仅指 provider 配置三件套（baseUrl/model/apiKey）齐备，非运行时健康探针；进程崩溃后 `core_get_status.engineReady` 仍 true（误报）。无 `engine-crashed` 事件。watchdog.rs 是「子代理 idle 唤醒器」，**不是进程存活监控**。当前进程内架构（crates 与 Tauri 壳/WebView 同进程，main.rs:5）下「引擎崩溃」只有两种现实形态：**A. run 内业务 panic（进程活）** 与 **B. 进程整体挂/被杀（无监视、无法自探）**。

**探活机制设计（三选一为主、辅以兜底；禁止过度设计）**：

- **主机制（推荐 · 前端主导的心跳）**：以 `fetchEngineLiveStatus` 既有轮询为心跳底座，修改其判定语义——当 `transport.isReady()` 且 `transport.request('core_get_status')` 在既定超时（现 8s）内**连续 N 次（默认 2 次）失败/超时**，即视为「引擎探活失败」。前端经 `errorStore.connectionStatus` 从 `connected/recovering` 迁移到一个**新的错误码/域**（如 `engine:crash-probed`，映射到接口呈现「引擎无响应 / 引擎已崩溃」+ 重连/重启入口）。**这是纯前端形状改动**（engineStatus.ts + bootstrap-services.ts 映射 + ErrorStore 类型 + RuntimePanel/状态条呈现），不新增 Rust 事件、不改核心循环。
  - **为什么选前端主导**：进程内架构下「崩溃」无跨进程监视者；前端是唯一能确认「我还在、命令没回」的观察者。前端心跳天然区分「run 崩溃（进程活、心跳仍 ok）」与「进程挂（心跳连续失败）」——这正对应 18 所述两条路径。
  - **防误报**：仅当 `transport.isReady()` 为 true（确认命令面已建立）才升高警戒；瞬时抖动沿用 TauriTransport 现有「error 视为暂态重试一次」（tauriTransport.ts call:158-167），心跳累计 N 次才判死，避免 keep-alive 短暂断连误报（18 §3.3）。

- **辅机制（Rust 侧 · crash 桥，轻量）**：panic_hook（crates/conex-telemetry/src/panic_hook.rs）当前只写 `crash-*.log` + `tracing::error!(target:"panic")`（死文件，logDir 仅暴露路径）。**最小增强**：在 panic hook 转发链上，把「最后一次崩溃文件名 + 时刻」写进一个进程内共享原子标记（`Mutex<Option<CrashMarker>>`，挂在 `core_get_status` 的 State 上）；前端心跳轮询时一并读取 `core_get_status.lastCrash`，发现较上次查询新增崩溃文件 → `errorStore` 记录「检测到一次引擎崩溃（crash-xxx.log）」+ 崩溃现场可访问（完整路径即 logDir）。这**不改死文件为活监视**，只是把「死文件」变成「前端可读的崩溃台账」。**注意**：本辅机制属壳层 `src-tauri` 只读触点，必须逐一确认不在核心循环加逻辑（§6 禁止项）。

- **不做的**：不把 watchdog.rs 改造成「进程监视器」（§6 禁止项）；不做 `engine-crashed` 事件类型（决策 6）。

**呈现面**：

- 引擎 section 状态点（RuntimePanel）+ 离线 ribbon（ChatStatusRibbons engineOk=false 既有面）复用/扩展一个「引擎已崩溃」文案分支；
- 新增/复用一个「重连」动作（已有 ConnectionLifecycle 重连能力，`restart_server` 是多端服务重建**非引擎重启**，故 UI 只给「自动重连 / 查看崩溃日志」入口，**不给**「重启引擎」按钮——进程内架构重启=整个 Tauri 重启，超出本战役范围，明示为产品待决，不做）。

### 1.2 ② 孤儿 run 收割（T5-b · run panic 无终态事件 → 收割机制）

**问题（18 §5.2 溢出 4）**：run 任务经 `run_launch.rs:767-771` `spawn(drive_run_loop(...))`，句柄存 `ActiveRun::driver`（run_core.rs:68-72,90-100，`set_driver`），**drop 即 detach**、收口不 await。`drive_run_loop` 内部无 `catch_unwind`；produce 内 panic 冒泡到 tokio 任务边界被兜住，但此时 `finalize_failed` 不执行 → 不产生终态事件、不写 lastError、**不从 activeRuns 移除** → 卡死/孤儿条目占用。

**收割机制设计（Rust 侧 · orchestrator/shell 层，非核心循环）**：

- **周期性收割器（推荐）**：在既有 `core_get_status.addActiveRuns`（run_core.rs 的 activeRuns 数据源）读取路径/或一个低频 tokio 周期任务（复用 watchdog spawn 类似的 exist 骨架，但**不复用 watchdog 语义**）上，对每个 `ActiveRun::driver` 调 `JoinHandle::is_finished()`（run_core.rs:95 注释已确认「is_finished——已收口/已取消均成立」，正是判据）。
  - 若 `driver.is_finished() == true` 且该 run 仍留在 activeRuns 中（即脱出点没有正常收口）→ 判定为**孤儿 run** → 调用既有 `finalize_failed(state, active, "<panic> 任务已中断，无终态收口")`（run_launch.rs:10-124，正是「drive 错误分支兜底」路径，现只缺触发时机）补写 lastError / 终态事件 / 移除 activeRuns + 排空审计 worker。
  - **语义铁律**：**必须严格区分「正常已收口撤销」与「真孤儿」**——`is_finished` 为真可能来自正常 cancel 后的短窗口残留。为防把「刚正常收口、正在从 activeRuns 移除」误判为孤儿，收割判定需要**去抖**：`is_finished` 连续 `M 轮`（默认 2 轮，与心跳同一低频周期 ~60s）仍停留 → 才收割。**禁止**在核心循环加探活（§6）。
- **启动时收割（补充）**：`core_get_status` 初始化/`startup` 路径对重启后残留的 in-flight runs 表条目处理，复用 run_snapshot.rs:7 auto-resume 已有的 `interrupted` → steering 恢复机制（D2/E1），不重复造收割器；本项只补「启动时把**无对应当前驱动任务的** in-flight 条目标记 interrupted」。

**前端识别**：前端从 `fetchEngineLiveStatus().activeRuns` 已能看到收割结果（run 消失/变 interrupted 终态）。前端补一条「run 被中断」识别：当某 run 从 activeRuns 消失且事件流内既有 `run-terminal(interrupted)` 事件时，正常消费；无事件即 silent（心跳兜底见 §1.1）。

### 1.3 ③ markdown 空白回退（T5-c · 完成态渲染失败 → 占位/纯文本次优回退）

**问题（18 溢出 1 / AsyncMarkdownBlock.tsx:80-91）**：完成态 `useAsyncMarkdownHtml` 失败返回 `{html:'', loading:false}` → `el.innerHTML=''`（:62）→ 完成消息体空白。测试断言是有意「不把源码泄入 DOM」（AsyncMarkdownBlock.test.tsx:86「完成态无 rustHtml → 空容器（不泄漏源码）」）。

**设计（纯前端 fallback，不违反泄漏约束）**：

- `useAsyncMarkdownHtml` 需要暴露一个**失败标志**（现只返回 `{html, loading}`）。增强为 `{ html, loading, failed?: boolean }`：Rust `core_md_render` missing + worker fallback 也失败（`.catch` 前置 loading=false、html 仍 ''）时置 `failed=true`（markdownRenderAsync.ts 内既有失败路径）。
- `AsyncMarkdownBlock` 完成态分支：当 `failed === true` 且 `html === ''` 时，回退渲染**纯文本**（`<pre className="md-text-fallback">{text}</pre>`，保持 `data-streaming="false"` 属性与既有测试语义兼容）。文本直接显示原文——这是「内容完整性优先」的次优回退，**不把 markdown 源码当作 HTML 注入 innerHTML**（源码以纯文本节点渲染，浏览器不会解析为 HTML，零 XSS、满足「不泄漏源码可读性」的产品意图中可读的最低要求）。

**产品裁决点（明示）**：审计曾提「是否泄漏源码」需产品裁决。本详案取**默认纯文本降级**（18 建议的默认值），理由：空白消息体比「源码只读」对完整性伤害更大；纯文本 div 渲染不注入 innerHTML 故无安全回溯。若有更严格产品意图（如显示占位「内容渲染失败」而非原文），仅需替换为占位文案，结构不变。

### 1.4 ④ 顶层边界 + 全局错误（T5-d · 顶层 boundary 加载失败降级裸 App 修复 + 全局 uncaught 呈现面）

**问题（18 溢出 5/6）**：

- 顶部：`main.tsx:84-90` 动态 import AppErrorBoundary 失败 → `root.render(<App/>)`（**裸 App**），App 内再抛错即白屏。
- 全局：`TelemetryMonitor`（services/TelemetryMonitor.ts:30-36）`window.error` + `unhandledrejection` **只记 JSONL 不呈现**；React 渲染树之外的模块级异常（如 store 初始化）用户可能看到半错乱而无提示。

**设计**：

- **顶层边界降级修复（main.tsx）**：`AppErrorBoundary` chunk 加载失败时，**不回到裸 App**，改为渲染一个**内联静态错误面**（复用 main.tsx:60-64「应用启动失败」同一套内联 HTML fallback 的构造，不外链任何 chunk）——即移除「第 2 个 render 裸 App」分支，改成 `root.render(<内联Fallback/>)`。若仍需挽救性渲染，可靠的是在没有 boundary 时仅渲染隔离的骨架 + 显式 window 错误登记，但**白屏风险必须消除**：裸 `<App/>` 分支是白屏点，必须改。
- **全局错误呈现面**：增强 `TelemetryMonitor`/或新增一个轻量 `GlobalErrorSink`，在 `window.onerror`/`unhandledrejection` 回调里，除 `logError` 外，把错误写入 `errorStore` 的一个**非阻塞全局错误槽位**；由顶层 `AppErrorBoundary` 的 `fullscreen` variant 或一个**常驻全局错误横幅**（复用 `CircuitBreakerBanner`/`SetupHintBanner` 类似形态）消费展示「发生一次未预期的错误」+ 可展开详情 + dismiss。不打断正常渲染（不弹模态阻塞交互），只是可见地告知。
- **不重复**：既有 `AppErrorBoundary` 的 13+3 处边界覆盖已充分（18 §②），本次**不新增边界层级**，只补「顶层失败」与「React 树外」两个边角。

## 6. 禁止项（硬化约束）

1. **不把 watchdog.rs 改造成进程监控**（超出范围）——除非确需（需产品/主控另行裁决进程内架构下「自动重启=整个 Tauri 重启」；本详案默认不做）。watchdog 保持「子代理 idle 唤醒器」语义不动。
2. **不在核心循环（session-loop `handlers`/`loop_exec` 七步链、streaming/turn_complete 等）加任何探活逻辑**——T5 属**壳层 + 前端**面；Rust 触点只允许在 `src-tauri` 壳层与 orchestrator 外层只读判定，禁止侵入核心内嵌。
3. **不新增 run 生命周期事件类型**（决策 6）：run 终态用既有 `run-terminal`，前端派生；崩溃感知独立探活。
4. **不新增 `engine-status-changed` / `engine-crashed` 事件**：探活结果走既有 `engine:connection:change` + `errorStore.connectionStatus` 承载，避免制造第二个连接真源。
5. **不把「重启引擎」按钮做成 UI 入口**（进程内架构下重启=整进程重启，超出战役；错误面只给「重连/查看崩溃日志」）。
6. **markdown 回退禁止注入 HTML 源码**（延续 16 的「不泄漏源码」约束的最低线）：纯文本以文本节点渲染，不 `innerHTML` 注入源码。
7. **禁止反过度设计**（AGENTS.md §8）：心脏只做「前端心跳 + 崩溃台账 + 收割器 + 回退 + 迁移」5 项，不引 SharedArrayBuffer/进程外守护/Rust 侧成体系 watchdog 等。
