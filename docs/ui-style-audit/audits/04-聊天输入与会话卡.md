# 04 · 聊天输入侧与会话卡样式一致性审计（chat-composer / chat-card）

- 审计人：A4（前端样式审计员）
- 日期：2026-08-21
- 范围：`apps/crish-desktop/src/components/chat-composer/` 与 `apps/crish-desktop/src/components/chat-card/` 全部 `.module.css` 及对应 TSX 的视觉相关逻辑
- 判据：仓库根 `AGENTS.md` §12（Tooltip）、§13（输入框焦点态，含 `data-empty-kind="session-empty"` 全页空态例外）、§14（色彩空间与现代 CSS 语法）；token 唯一真源 `apps/crish-desktop/src/styles/tokens.css`；层级真源 `apps/crish-desktop/src/styles/z-index.css`
- 方法：只读代码逐文件核对；所有悬空 token 均经全 src 范围 grep 验证「无任何定义点」后才判定为悬空

---

## ① 总评

**结论：焦点态合规度高，token 化骨架良好，但存在一条「悬空 token 族」导致的静默样式失效，以及弹层/徽条两大战线的规格碎片化。**

好的方面：

1. **§13 核心条款全部落位**：composer 主卡片与容器聚焦混入精确 6%、全页空态精确 5%，且 `box-shadow: none` 贯穿输入链路（ChatComposer.module.css:772、787、1057）；空态特例通过 `data-empty-kind={emptyKind}` 真实接线（ChatComposer.tsx:403）。
2. **Tooltip 合规**：两目录所有可交互控件均使用自定义 `<Tooltip>`，未发现原生 `title=` 悬停提示（测试还显式断言了这一点，ComposerField.stop.test.tsx:4、84）。
3. **颜色主体走 token + color-mix**：ribbons、队列面板、目录树、空态卡基本零硬编码色，暗色主题随 token 自动适配。

坏的方面（按严重度）：

1. **悬空 token 族（🔴）**：`--sem-error` / `--sem-warn` 在 ChatComposer.module.css 出现 11 次、全仓无定义点——权限审批条的高风险徽章、过期计时器、附件删除 hover、停止按钮 hover 的语义红**全部静默失效**（回落继承色）。另有 3 个无 fallback 的 z-index 悬空（`--z-card-footer` / `--z-scroll-fab` / `--z-sticky-bar`），层级保障归零。
2. **同一 composer 内三套弹层设计语言（🟡）**：FusedTrigger 菜单走 `--sep-*` 面板体系、Plus/权限菜单走 `--bg-card`+自绘 rgba 阴影、斜杠菜单走 `--bg-elevated`+直角扁平，互不一致。
3. **ribbons 徽条规格碎片化（🟡）**：圆角 lg/xl 混用、内边距四套、边框三种来源、danger 色四种拼法（其中两种是死 token）。
4. **畸形 transition 简写模式（🟡）**：`var(--transition-micro, 120ms) ease` 把完整时长+缓动 token 再拼一个 `ease`，替换后出现双 timing function，整条声明失效——本范围内 9 处 hover 过渡静默不生效（该模式全仓 68 处，属系统性）。

| # | §13 条款 | 判定 | 证据与说明 |
|---|---------|------|-----------|
| 1 | 默认不要重阴影 | ✅ 通过 | `.composerCard` 默认 `box-shadow: none`（ChatComposer.module.css:772），`:focus-within` 仍显式 `box-shadow: none`（同文件 787）；fallback 容器 `.container` 同样处理（1049–1059）；Tiptap 富文本域 `outline/box-shadow: none`（TiptapEditorField.module.css:32–33、47–50）；筛选输入框聚焦 `box-shadow: none`（ChatMsgFilterBar.module.css:48）；重命名输入 `box-shadow: none`（SessionInlineRename.module.css:20）。唯一附带阴影的是计划进度条顶部 `0 -2px 10px var(--shadow-color, rgba(0,0,0,0.02))`（ChatComposer.module.css:323），2% alpha 极轻且不在输入框本体，不算违规 |
| 2 | 禁止粗/深/实心黑边 | ✅ 通过 | 全范围未发现对输入框使用 `var(--text-primary)` 实色边或 `0 0 0 1px` 黑环；激活态一律走 `color-mix(border-color, text-primary)` |

| 4 | 全页空态落地输入混入 ≤5% | ✅ 通过 | `.composerCard[data-empty-kind='session-empty']:focus-within` 精确 5%（ChatComposer.module.css:791–798）；`.container[data-empty-kind='session-empty']` 同样 5%（1061–1067）；属性由 ChatComposer.tsx:403 `data-empty-kind={emptyKind}` 注入，链路真实有效 |
| 5 | 空态不得加生硬 border-color 过渡动画 | ⚠️ 漂移 | `.composerCard` 基础声明含 `transition: border-color var(--transition-fast, 120ms ease)`（ChatComposer.module.css:773），`.container` 同（1044）——该元素即空态落地输入本体，§13 明确要求空态不加 border-color 过渡。120ms ease 属柔和实现、非「生硬」，但按条文口径仍应移除或对 `[data-empty-kind='session-empty']` 显式关闭。同类：`.renameInput` 也带 border-color 过渡（SessionInlineRename.module.css:23，且因下文 Y5 的畸形写法实际未生效） |

**补充发现（token 未消费）**：tokens.css 已提供现成的焦点边框 token——`--focus-ring-subtle`（恰为 6% 混入，tokens.css:111–115）与 `--focus-ring-strong`（恰为 10% 上限量级，116–120）。但 composer 卡片、容器、筛选框、目录树按钮全部在各自文件里手抄同一行 `color-mix(in srgb, var(--border-color) 94%, var(--text-primary) 6%)`（ChatComposer.module.css:782–786、1052–1056、1082–1086；ChatMsgFilterBar.module.css:46；ComposerDirTree.module.css:51–52），共 5 处重复。应改为消费 token，避免未来调阈值时五处漂移。

## ③ 问题清单

### 🔴 违规（功能性失效 / 违反 token 唯一真源）

**R1. `--sem-error` / `--sem-warn` 悬空 token，语义色大面积静默失效**

全 `apps/crish-desktop/src`（含 ts/tsx/css）grep 验证：两个变量**无任何定义点**。`var()` 无 fallback 时属性在计算值阶段失效，回落继承/初始值：

| 位置 | 受损表现 |
|------|---------|
| ChatComposer.module.css:142 | 权限审批条高风险徽章不变红（回落文字色） |
| ChatComposer.module.css:178、182、187 | 审批倒计时橙色警示/闪烁/过期红全部失效 |
| ChatComposer.module.css:276、280 | 「拒绝」按钮文字与 hover 底色失效 |
| ChatComposer.module.css:589–590 | 计划进度条「终止」按钮 hover 危险色失效 |
| ChatComposer.module.css:752 | 附件/文件卡删除钮 hover 红底失效 |
| ChatComposer.module.css:1017–1018 | 发送位「停止」圆钮 hover 危险色失效 |
| PermissionModeMenu.module.css:92 | `var(--sem-warn, #d97706)` 靠硬编码 fallback 渲染——实际显示的正是这个未登记色 |

另 ChatComposer.module.css:61–64 的 `--sem-warn-soft` 同样无定义（靠内联 color-mix fallback 兜住）。修复方向：在 tokens.css 将其定义为 `--color-error` / `--color-warning` 的别名，或全量迁移到 `--color-*` 体系。

**R2. 三个 z-index 悬空且无 fallback，层级保障归零**

`styles/z-index.css` 只定义了 base/dock/sticky/chrome/sidebar/resizer/dropdown/popover/drawer/modal/toast/tooltip（z-index.css:3–26）；以下引用全部落空为 `z-index: auto`：

- ChatCard.module.css:57 —— `.chatFooter { z-index: var(--z-card-footer) }`
- ChatStatusRibbons.module.css:6 —— 回到底部 FAB `z-index: var(--z-scroll-fab)`
- ChatMsgFilterBar.module.css:12 —— 吸顶筛选栏 `z-index: var(--z-sticky-bar)`

吸顶栏与 FAB 失去显式层级后只能靠 DOM 顺序兜底，消息流内的定位元素滚动时可能压过它们。应在 z-index.css 补充这三个档位（或改用现有 `--z-dock`/`--z-chrome`）。

**R3. 硬编码截图取色，绕开 token 真源**

PermissionModeMenu.module.css:95–97：`[data-perm-mode='full'] { color: #c25e2e; /* 经典赤褐色/珊瑚橙，精确匹配截图 */ }`。问题：① 绕开 tokens.css 唯一真源；② 固定色不适配暗色主题；③「精确匹配截图」属 §7 反对的像素补偿式补丁手法。应登记为新 token（如 `--perm-full-fg`）并给暗色档。

**Y4. danger 语义色四种拼法并存**

`--sem-error`（死，ChatComposer.module.css 多处）/ `--accent-red`（ChatQueuePanel.module.css:92–93）/ `--danger-color`（PlanGoalRibbons.module.css:91、SetupHintBanner.module.css:74）/ `--status-error`（死，SubagentHeaderPanel.module.css:135–136、159，靠 fallback `#ef4444` 渲染——与 `--accent-red` hsl(0,55%,55%) 不是同一个红）。相邻组件各说各话。

**Y5. 畸形 transition 简写：`var(--transition-micro, 120ms) ease` 导致过渡整体失效**

`--transition-micro` 的值是完整的 `100ms ease-out`（tokens.css:357），代入后变成 `… 100ms ease-out ease`——双 timing function 使整条 transition 声明计算值阶段失效，hover 过渡静默消失。本范围内 9 处：

- SessionInlineRename.module.css:23、47、69
- SubagentHeaderPanel.module.css:18–19、64、88
- UnitChromeActions.module.css:89–90、176–177、218–219

该模式全仓 68 处（含 ui/Button、ui/Menu、ui/Select 等基元），建议系统性清理为 `var(--transition-micro)`。

**Y6. 其余悬空/死 token（有 fallback 兜底，视觉暂稳但掩盖漂移）**

- `--font-sub`：ComposerFusedTrigger.module.css:44、83（fallback 13px）
- `--z-dropdown-menu`：ComposePlusMenu.module.css:8、PermissionModeMenu.module.css:114、ComposerFusedTrigger.module.css:110——且全仓 fallback 各不相同（此处 300；SmartExpandablePanel.module.css:354 为 310；ModelsSettingsTab.module.css:1167 为 2000），同名层在不同组件解析出不同数值
- `--line-height-normal`（无 fallback）：ChatStatusRibbons.module.css:165、187、209——tokens 只有 tight/ui/body/relaxed/none/dense/compact/base，没有 normal
- `--radius-card`：ChatComposer.module.css:632；`--bg-surface`：同文件 857、878、900、918；`--bg-composer`：771；`--text-on-brand`：950、994——四个变量全仓无定义，永远吃 fallback
- `--sep-submenu-radius`：ProjectPickerMenu.module.css:98——tokens.css 无此变量（只有 radius-outer/inner/item/btn/badge/pill）

**Y7. 硬编码尺寸/颜色绕过 token**

- SubagentHeaderPanel.module.css:9（`border-radius: 6px`）、12、108、117、145（字号 12/12/10/11px 裸值）、46（keyframes 内 `rgba(16,185,129,0.6)` 绿色辉光，明暗主题同色）

**Y8. 对接曲率失配：16px 肩线骑到 22px 圆角上**

计划进度条 `border-radius: 16px 16px 0 0`（ChatComposer.module.css:322）与计划徽条 docked 态 `16px 16px 0 0`（PlanGoalRibbons.module.css:29）都 dock 到外圆角 22px 的 `.composerCard`（:770）顶边上，肩部曲率 16≠22，接缝处出现可见错位。应从 composer 半径派生（如 `calc(var(--composer-radius) - Npx)`），而非第三组魔术数。

**Y9. §14 口径：旧式 rgba 散落**

功能代码大量使用 `color-mix/hsl()` 达标，但 fallback 与阴影里散落旧式 `rgba(r,g,b,a)`：PermissionModeMenu.module.css:27、33、39、77、82、167、172、179；ComposerFusedTrigger.module.css:24、62、102、154、159、166；UnitChromeActions.module.css:94、182、198、223；SubagentHeaderPanel.module.css:24、46 等。§14 要求优先 `hsl(h s l / a)` 斜杠透明度写法，建议随 token 化一并清理。

**Y10. `--composer-footer-bg` 定义了却无人消费**

tokens.css:64（light transparent）、640（dark = bg-secondary）两处定义，全仓 grep 零消费点；composer 页脚区实际用的是 `--chat-footer-fade` 渐变（ChatCard.module.css:55）与 `data-composer-footer` 属性挂名（ChatComposer.tsx:417）。要么接线要么删档，避免「以为有 token 管」的错觉。

**Y11. 失真的 fallback 值掩盖真实 token**

`var(--radius-md, 8px)`（SetupHintBanner.module.css:8，真值 6px）、`var(--radius-sm, 6px)`（ChatMsgFilterBar.module.css:28，真值 4px）——fallback 只在 token 缺失时生效，但写了错误兜底值会让回归排查误判，建议统一删掉或写对。

### 🔵 建议

**B1. 弹层表面统一**：为 composer 五个浮层（Plus/权限/思考/斜杠/目录树）定一组 `--menu-bg / --menu-radius / --menu-shadow / --menu-item-h / --menu-iconbox` 级联 token（或统一收敛到 `--sep-*` 体系），一处调全局生效。

**B2. 补齐 token 族谱**：z-index.css 增补 `--z-scroll-fab / --z-sticky-bar / --z-card-footer / --z-dropdown-menu`；tokens.css 增补 `--line-height-normal` 别名、`--status-error` 别名、`--font-sub`；或反向把使用点改成现有档位。二选一，消除「引用名与定义名两张皮」。

**B3. 焦点边框消费现成 token**：②节补充发现——5 处手抄 6% color-mix 应改为 `var(--focus-ring-subtle)`；renameInput 8% 收敛到同一 token（SessionInlineRename.module.css:27）。

**B4. composer 三入口按钮规格互比拉齐**：加号钮 32×32 有底（ChatComposer.module.css:856–875）、语音/统计钮 32×32 有底（:895–914）、权限盾牌 icon-only 24×24 无底（PermissionModeMenu.module.css:51–70），图标 13px vs 14px（stroke-width 均 1.75）。若 24px 是刻意的「次级入口」设计，建议在 CSS 注释与本审计留痕固化；否则统一到 28 或 32 一档。

**B5. 空态英雄标题字号入 token**：`clamp(22px, 3.2vw, 34px)`（ChatEmptyState.module.css:71）是范围内唯一游离于 `--font-size-*` 体系外的显示级字号，建议增设 display 档。

**B6. dropMask 底色优先级与卡片对齐**：遮罩用 `var(--bg-elevated, var(--composer-bg))`（ChatComposer.module.css:1264），而卡片本体是 `--composer-bg` 优先（:771）——拖拽遮罩盖在卡片上时会比卡片底更亮一档，建议统一为 `--composer-bg` 优先。

**B7. 权限菜单入场动画是死引用**：`animation: cds-popover-enter …`（PermissionModeMenu.module.css:127、144）所引 keyframes 全仓无定义，动画从未播放。补 keyframes 或删除声明。

## ④ Top 问题小结

1. **R1 悬空语义色（最高优先）**：`--sem-error/--sem-warn` 11 处引用零定义，审批条的红色警示链路（高风险徽章/过期计时器/拒绝按钮/停止钮 hover）整体哑火——这是用户安全感知直接相关的视觉失效，不是纯审美问题。
2. **R2 层级裸奔**：三个无 fallback 的 z-index 让吸顶筛选栏、回底 FAB、聊天页脚失去堆叠保障，属于「今天没坏、改版就坏」的隐性雷。
3. **Y1+Y2+Y3 一致性主战场**：composer 弹层三套语言、菜单项三套规格、ribbons 四套拼法——建议以「弹层 token 组 + 徽条规格表」一次性收口，而不是逐处微调。
4. **Y5 畸形 transition**：一行错误写法让 9 处（全仓 68 处）hover 过渡静默失效，修复成本极低、收益面极大。
5. **§13 本体成绩好**：6%/5% 混入精确落位、零重阴影、空态例外真实接线；仅需清掉空态上的 border-color 过渡（②#5）并把 5 处手抄混入改为消费 `--focus-ring-subtle`。

> 审计依据全部来自代码静态阅读；所有「无定义」结论均经过全 src 目录 grep 双向验证（先查定义、再查全部引用点）。
