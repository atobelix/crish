## 一、现状与根因穿透

基于对 `crates/conex-sandbox/`、`crates/agent-tools/`、`crates/conex-fs/`、`apps/agent-workbench/` 及 `crates/session-loop/` 的全面源码穿透，当前安全与互斥体系存在 8 大根本性架构断裂：

```
                      【当前架构表面功夫与断裂全景】
  
  [模型生成 Shell 命令] 
         │
         ├──► powershell -ec <base64> ──► is_ps_encoded_command_flag 漏判 -ec/-en ──► 标为 Normal ──► 【红线直接穿透放行！】
         │
         ├──► python -c "import os..." ──► 伪递归当 Shell 分段 (import, os) ────────► 标为 Indirect ──► 【无删除目标直接放行！】
         │
         ├──► Push-Location C:\ ────────► CD_COMMANDS 漏收录 Push-Location ────────► 标为 Normal ──► 【进程工作目录漂移！】
         │
         ├──► Get-Content C:\id_rsa ────► 仅校验参数 cwd，不检命令 AST 路径 ────────► 子进程执行 ──► 【工作区外任意文件泄露！】
         │
         └──► rm -rf / (FullAccess) ───► FullAccess 显式跳过回收站重定向 ─────────► 外壳真删 ──► 【数据物理毁灭不可恢复！】

  [文件写/删并发互斥]
         ├──► Run A (主 Agent) ─────► WritePathRegistry::new() [独立内存实例] ──┐
         │                                                                   ├─► 【互斥完全失效，跨 Run 盲写覆盖！】
         └──► Run B (子 Agent) ─────► WritePathRegistry::new() [独立内存实例] ──┘
         
         └──► 单 Run 内并行工具 ───► 共用 holder = run_id ──► c.holder != holder 为假 ──► 【同 Run 并行写互斥失效！】
                                └──► 先完成工具 Drop ──► release_holder(run_id) ────► 【提前抹除正在运行工具的声明！】
```

### 1.1 BC10-1: PowerShell 编码命令缩写不解码，红线载荷被全量放行
- **代码坐标**：
  - `crates/conex-sandbox/src/semantics.rs:567-583`（`is_ps_encoded_command_flag`）
  - `crates/conex-sandbox/src/semantics.rs:643-650`、`989-997`（仅在命中时升 Redline）
  - `crates/conex-sandbox/src/semantics.rs:2085-2104`（测试仅锁定了 `-e`、`-enc`、`-enco`，完全遗漏 `-ec` 与 `-en`）
  - `crates/agent-tools/src/tools/shell_invoke.rs:12-29`、`64-78`（外壳二次包装发生于门禁之后）
- **表面表现与假象**：
  代码表面实现了针对 Base64 编码命令的检测函数 `is_ps_encoded_command_flag`，并在文档中声称“覆盖 EncodedCommand 全变形”。
- **架构根因穿透**：
  函数判定逻辑存在严重的逻辑短路缺陷：
  ```rust
  if "encodedcommand".starts_with(flag_name) {
      if flag_name == "e" || flag_name.starts_with("enc") || flag_name.starts_with("enco") {
          return true;
      }
  }
  ```
  在 Windows PowerShell 的参数绑定规范中，只要传入的前缀能唯一确定参数名（且不与 `-ExecutionPolicy` 的 `-ex` 冲突），解析器即合法接受。`-ec` 与 `-en` 均为官方支持的标准缩写。
  然而上述逻辑中，虽然 `"encodedcommand".starts_with("ec")` 为真，但后续硬编码的 `flag_name == "e" || flag_name.starts_with("enc")` 均为假，导致函数直接返回 `false`。
  漏判后，内层 Base64 载荷未被解码，提取不到内层 AST，命令分类退化为 `Normal`。在 `FullAccess` 模式下直接免审批放行，即便内含 `Format-Volume` 或删盘指令，红线门禁完全失效。

### 1.2 BC10-2: 解释器 `-c`/`-e` 的非 Shell 载荷伪递归，动态执行逃逸
- **代码坐标**：
  - `crates/conex-sandbox/src/semantics.rs:61-83`（`INDIRECT_COMMANDS` 包含 `node`/`python`/`python3`）
  - `crates/conex-sandbox/src/semantics.rs:989-1025`（`extract_inner_commands` 提取逻辑，注释注明已移出 `-e`）
  - `crates/conex-sandbox/src/semantics.rs:1205-1221`（递归分类落入 `Indirect`）
  - `crates/conex-sandbox/src/lib.rs:122-133`（门禁放行条件）
- **表面表现与假象**：
  间接命令表中登记了 `python` 和 `node`，声称能对其脚本执行进行安全递归审计。
- **架构根因穿透**：
  架构上混淆了 **Shell 脚本语言** 与 **高级宿主解释器语言（Python/JS）** 的语法边界：
  1. 对于 `python -c "import os; os.system('rm -rf /')"`，提取出的 Python 代码被强行送入 Shell 分段解析器（`analyze_depth`），按 `;` 拆分为 `import os` 与 `os.system(...)` 两个“Shell 命令”。这两个段既不匹配系统删除命令，也不匹配危险命令表，内层被判为 `CommandClass::Normal`。
  2. 外层根据 `!inner.segments.is_empty()` 将整体粗暴标记为 `CommandClass::Indirect`。
  3. `lib.rs:129-131` 规定：仅当 `overall_class == Indirect && !delete_targets.is_empty()` 时才升级为 `RequiresApproval`。由于 Python 语句中不存在 Shell 识别出的 `delete_targets`，该条件不成立，门禁直接返回 `Allowed`！
  4. 对于 `node -e`，`-e` 甚至被硬编码移出提取逻辑，根本不发生任何内层检查，直接作为普通命令 `Allowed` 放行。

### 1.3 BC10-3: CD 家族别名漏防与间接嵌套穿透，进程初始工作目录漂移
- **代码坐标**：
  - `crates/conex-sandbox/src/semantics.rs:88-92`（`CD_COMMANDS`）
  - `crates/conex-sandbox/src/semantics.rs:1231-1236`（段首命令名匹配）
  - `crates/agent-tools/src/tools/shell_redirect.rs:367-386`（`intercept_cd_shape`）
  - `crates/agent-tools/src/tools/shell.rs:294-297`（执行点拦截）
- **表面表现与假象**：
  提供了 `intercept_cd_shape`，声称“强制引导使用 `Cwd` 参数，阻断 `cd` 命令”。
- **架构根因穿透**：
  1. 白名单硬编码缺失：`CD_COMMANDS` 仅定义了 `&["cd", "set-location", "sl", "pushd", "popd"]`。注释虽然声称已覆盖 PowerShell 别名，但 PowerShell 官方原生 Cmdlet `Push-Location` 和 `Pop-Location` 竟然不在列表中！
  2. 间接调用与复合链穿透：`intercept_cd_shape` 仅检查最外层单段是否为 `CdShape`。若命令形如 `cmd /c "cd /d D:\ & ..."` 或 `powershell -Command "cd ..; ..."`，外层为 `cmd` 或 `powershell`（属于 `Indirect`），内层的 `cd` 无法向上传递改变外层的 `CommandClass`，导致拦截器直接返回 `None` 放行。
  3. 后续同进程相对路径污染：宿主外壳采用 `[scriptblock]::Create` 执行用户脚本，一旦 `Push-Location` 漏网执行，宿主进程目录被永久篡改，后半段命令在未经工作区校验的外部路径肆意读写。

### 1.4 BC10-4: 放行后的 Shell 读写工作区外绝对路径，符号链接 Fail-Open 隐患
- **代码坐标**：
  - `crates/agent-tools/src/tools/shell_exec.rs:52-55`（仅设 `current_dir(cwd)`）
  - `crates/conex-sandbox/src/lib.rs:148-193`（门禁仅校验 `cwd`，不校验命令行参数）
  - `crates/agent-tools/src/tools/mod.rs:341-404`（`resolve_workspace_path`）
  - `crates/agent-tools/src/tools/mod.rs:416-419`（`has_escaping_symlink_below_root`）
- **表面表现与假象**：
  文件工具层对工作区路径校验完备（解析符号链接、阻断 `..` 越界），声称沙箱具备工作区边界防御。
- **架构根因穿透**：
  Shell 执行与文件工具存在巨大的边界断层：
  1. 进程级校验缺失：`run_command_maybe_background` 仅将子进程的工作目录绑定为 `cwd`，并没有对命令行 Token 中的文件路径参数进行 AST 提取与工作区归属性扫描。模型执行 `Get-Content C:\Users\xxx\.ssh\id_rsa` 或 `Out-File C:\Windows\Temp\payload.bat` 时，全部以子进程操作系统权限穿透工作区。
  2. 符号链接检查 Fail-Open：在 `tools/mod.rs:416-418` 中：
     ```rust
     let rel = match norm_path.strip_prefix(&norm_root) {
         Ok(r) => r,
         Err(_) => return false, // 致命：strip_prefix 失败时默认为未逃逸！
     };
     ```
     在 Windows 系统中，若规范化路径存在大小写差异（如 `c:\` 与 `C:\`）导致 `strip_prefix` 失败，函数直接返回 `false`（视为安全放行），造成符号链接穿透逃逸。

### 1.5 BC10-5: 写路径互斥锁多实例割裂、单 Holder 覆盖与短命 TTL 悬挂
- **代码坐标**：
  - `apps/agent-workbench/src-tauri/src/run/run_launch.rs:737, 956, 1016-1025`（多注册表实例割裂）
  - `crates/session-loop/src/exec_single.rs:419`（`write_claim_holder: Some(ctx.run_id.clone())`）
  - `crates/session-loop/src/loop/handlers/executing_tools.rs:80-92`（批处理并行执行）
  - `crates/agent-tools/src/write_paths_state.rs:198-203`（冲突判定跳过同 holder）
  - `crates/agent-tools/src/write_paths_state.rs:106-115`（Drop 全量清除 holder 声明）
  - `crates/agent-tools/src/write_paths_state.rs:27-28`（硬编码 60s TTL）
- **表面表现与假象**：
  代码中存在 `WritePathRegistry`，实现了 `claim`、`check_conflict` 与 `WriteClaimGuard`，单元测试全绿。
- **架构根因穿透**：
  在真实生产运行期，该互斥机制在三层维度上全面瓦解：
  1. **注册表实例完全割裂**：主 Agent Run 在 `run_launch.rs:956` 创建一份 `WritePathRegistry`；每个子 Agent Run 在 `run_launch.rs:1016-1025` 又各自独立 `new` 一份。它们在内存中完全隔离，父 Run 与子 Run、子 Run 与子 Run 之间对同一文件的并行写完全互不知晓！
  2. **同 Run 内部 Holder 粗化导致冲突跳过**：在单 Run 执行上下文中，`exec_single.rs:419` 将 `write_claim_holder` 统一设为 `run_id`。当模型在单轮生成多个并行的 `write_file` 操作同一文件时，`write_paths_state.rs:202` 判断 `c.holder != holder` 为假，直接判定不冲突并刷新声明，导致并行写入交错覆盖。
  3. **RAII 级联误删（Cascading Purge）**：`WriteClaimGuard::drop` 调用的是 `release_holder(&self.holder)`。当两个并行写操作同一文件的任务（A 和 B）运行，A 先执行完毕触发 Drop，会将该 holder（即整个 `run_id`）名下的**所有路径声明无差别全部清空**，使得任务 B 在后续写入期间完全暴露在无保护状态下。
  4. **TTL 悬挂与脱保**：硬编码 60s 超时且无运行时心跳续期机制，执行耗时操作时锁提前释放。

### 1.6 BC10-6: 任务类型（TaskType）命令执行策略与执行链断层
- **代码坐标**：
  - `crates/agent-tools/src/readonly.rs:149-188`（`command_allowed_for_task_type`）
  - `crates/agent-tools/src/context.rs:130-170`（`ToolContext` 缺少任务类型字段）
  - `crates/agent-tools/src/tools/shell.rs:240-335`（`prepare` 未接入任务类型）
  - `apps/agent-workbench/src-tauri/src/run/run_launch.rs:820-836`（仅裁剪工具名）
- **表面表现与假象**：
  `readonly.rs` 中精心编写了 `command_allowed_for_task_type`，对 `commit` 限制仅允许 `git`，对 `implementation` 限制仅允许 `CommandClass::Normal`，并配有单元测试。
- **架构根因穿透**：
  代码注释明确声明：“本函数不参与每命令放行判定”。执行链条彻底断裂：
  1. 引擎在子 Agent 启动时仅裁剪了工具名称（如去除 `write_file`，保留 `shell_command`）；
  2. `ToolContext` 中根本没有传递 `task_type` 字段；
  3. `shell_command` 的 `prepare` 与 `execute` 判定完全不感知当前执行主体的任务类型。`commit` 代理可以调用 `shell_command` 执行任意复杂的 Node/Python/PowerShell 脚本或工作区外写入，任务类型隔离形同虚设。

### 1.7 BC10-7: FullAccess 模式物理删除逃逸与回收站绕过
- **代码坐标**：
  - `crates/agent-tools/src/tools/shell.rs:275-292`（`permission_mode != FullAccess` 才重定向）
  - `crates/agent-tools/src/tools/shell_redirect.rs:167`
  - `crates/conex-fs/src/trash.rs:200-257`
- **表面表现与假象**：
  产品宣称“所有删除操作统一接管至回收站，具备完整审计与撤回恢复能力”。
- **架构根因穿透**：
  `shell.rs:278` 存在致命豁免判断：
  ```rust
  if ctx.permission_mode != PermissionMode::FullAccess {
      if analysis.overall_class == CommandClass::DeleteShape || analysis.has_indirect_delete {
          return Prepared::Done(redirect_or_intercept_delete(...));
      }
  }
  ```
  架构设计严重混淆了 **权限审批放行（Authorization）** 与 **数据安全护栏（Safety Guardrail）** 的概念。
  `FullAccess` 模式的语义应是“无需人工弹窗确认即可执行安全操作”，而非“授权绕过回收站直接物理销毁文件”。在此模式下，任何 `rm` 或 `Remove-Item` 均穿透回收站直调 OS Shell，造成数据物理灭失且无法生成撤回快照。

### 1.8 BC10-8: 幂等守卫无持久化底座与跨进程失效
- **代码坐标**：
  - `crates/agent-tools/src/idempotency.rs:10-12, 128-142`
  - `crates/session-loop/src/loop/loop_options.rs:107`（默认关闭）
  - `crates/session-loop/src/loop/loop_runner.rs:199-201`
  - `crates/agent-tools/src/executor_run.rs:41-42`
- **表面表现与假象**：
  提供了 `IdempotencyStore` trait 与 `ToolIdempotencyGuard`，具备 `check`、`record`、`should_execute` 接口。
- **架构根因穿透**：

  2. 即便显式开启，生产代码仅调用 `ToolIdempotencyGuard::new()`，内部存储为纯内存 `HashMap`，未挂接 `conex-db`；
  3. 一旦应用崩溃、重启或发起新 Run，内存中的幂等指纹全部丢失，导致对重试或恢复工具调用的去重能力彻底归零。

## 二、架构重构设计与核心契约

为从根本上根除上述架构断裂，本方案构建四大核心支柱：
1. **多宿主语法 AST 分词与语义展开引擎（MultiHostShellEngine & ShellAST）**
2. **工作区级全局路径分级互斥锁状态机（WorkspacePathMutexManager）**
3. **基于预写日志（WAL）与两阶段提交的回收站事务守卫（TrashTransactionGuard）**
4. **工具权限决策矩阵与 TaskType 执行链刚性拦截器（TaskTypeEnforcementPipeline）**

```
                       【重构后统一安全防御与互斥架构】

   ┌────────────────────────────────────────────────────────────────────────┐
   │ 1. MultiHostShellEngine: AST 解析、参数消歧、Base64 解码、解释器审查      │
   └───────────────────────────────────┬────────────────────────────────────┘
                                       ▼
   ┌────────────────────────────────────────────────────────────────────────┐
   │ 2. TaskTypeEnforcementPipeline: 任务类型（Commit/Impl 等）硬性契约阻断  │
   └───────────────────────────────────┬────────────────────────────────────┘
                                       ▼
   ┌────────────────────────────────────────────────────────────────────────┐
   │ 3. Canonical Path Boundary Guard: 绝对路径与符号链接越界 Fail-Closed 校验│
   └───────────────────────────────────┬────────────────────────────────────┘
                                       ▼
   ┌────────────────────────────────────────────────────────────────────────┐
   │ 4. Universal Trash Interceptor: 全权限模式强制进回收站（杜绝物理直删）   │
   │    TrashTransactionGuard: WAL 预写日志 + 目录 Merkle 校验和 + 崩溃自愈  │
   └───────────────────────────────────┬────────────────────────────────────┘
                                       ▼
   ┌────────────────────────────────────────────────────────────────────────┐
   │ 5. WorkspacePathMutexManager: 工作区全局单例、细粒度分级锁 (IS/IX/S/X)  │
   │    以 Canonical Path 为唯一键、ToolCall 粒度持有、动态心跳租约         │
   └────────────────────────────────────────────────────────────────────────┘
```

### 2.1 模块一：多宿主命令行 AST 分词与语义展开引擎

彻底废弃脆弱的字符串 `split_whitespace`、正则表达式匹配与前缀死字符比对，在 `conex-sandbox` 中构建具备词法分析、抽象语法树（AST）构建与深层展开能力的专业解析引擎。

#### 2.1.1 语法解析与 AST 数据契约

```rust
// crates/conex-sandbox/src/ast.rs

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum HostShellFlavor {
    PowerShell,
    Cmd,
    Posix,
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub enum QuoteStyle {
    None,
    Single,
    Double,
    Backtick,
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct ShellToken {
    pub text: String,
    pub raw: String,
    pub quote: QuoteStyle,
    pub span: (usize, usize),
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub enum RedirectOp {
    Output,        // >
    Append,        // >>
    Input,         // <
    StderrToStdout,// 2>&1
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct Redirection {
    pub op: RedirectOp,
    pub target: ShellToken,
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct SimpleCommand {
    pub command: ShellToken,
    pub args: Vec<ShellToken>,
    pub redirects: Vec<Redirection>,
    pub env_assignments: Vec<(String, String)>,
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub enum PipelineOp {
    Pipe,          // |
    And,           // &&
    Or,            // ||
    Sequence,      // ; or \n
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub enum CommandNode {
    Simple(SimpleCommand),
    Subshell(Vec<PipelineSegment>),
    ScriptBlock(Vec<PipelineSegment>),
    PolyglotPayload {
        interpreter: String,
        code: String,
        source_flag: String,
    },
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct PipelineSegment {
    pub node: CommandNode,
    pub op_after: Option<PipelineOp>,
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct ShellAst {
    pub flavor: HostShellFlavor,
    pub root_pipelines: Vec<PipelineSegment>,
}
```

#### 2.1.2 参数消歧展开引擎（ShellParamDisambiguator）

针对 Windows PowerShell 的参数前缀缩写机制，建立精确的消歧状态机，系统化拦截 `-ec`、`-en`、`-encodedcommand` 等全量变体，并执行自动解码：

```rust
// crates/conex-sandbox/src/disambiguator.rs

pub struct ShellParamDisambiguator;

impl ShellParamDisambiguator {
    /// 规范化 PowerShell 参数全名（解析前缀唯一绑定）
    pub fn resolve_powershell_param(arg: &str) -> Option<ResolvedPsParam> {
        let stripped = arg.strip_prefix('-').or_else(|| arg.strip_prefix('/'))?;
        let (flag_name, inline_val) = match stripped.split_once([':', '=']) {
            Some((k, v)) => (k.to_lowercase(), Some(v.to_string())),
            None => (stripped.to_lowercase(), None),
        };

        if flag_name.is_empty() {
            return None;
        }

        // PowerShell 官方参数消歧表
        if "encodedcommand".starts_with(&flag_name) {
            // 唯一性约束：'e' 在不冲突情况下绑定至 EncodedCommand；'en', 'enc', 'enco' 均唯一确定
            if flag_name == "e" || flag_name.starts_with("en") {
                return Some(ResolvedPsParam::EncodedCommand(inline_val));
            }
        }
        if "executionpolicy".starts_with(&flag_name) && flag_name.starts_with("ex") {
            return Some(ResolvedPsParam::ExecutionPolicy(inline_val));
        }
        if "command".starts_with(&flag_name) && flag_name.starts_with("c") {
            return Some(ResolvedPsParam::Command(inline_val));
        }
        if "file".starts_with(&flag_name) && flag_name.starts_with("f") {
            return Some(ResolvedPsParam::File(inline_val));
        }

        None
    }

    /// 解码 UTF-16LE Base64 载荷并递归生成内层 AST
    pub fn decode_powershell_encoded_command(payload: &str) -> Result<String, SandboxError> {
        let clean = payload.trim().trim_matches(['"', '\'']);
        let decoded_bytes = base64::engine::general_purpose::STANDARD
            .decode(clean)
            .map_err(|e| SandboxError::MalformedPayload(format!("Base64 decode failed: {e}")))?;
        
        if decoded_bytes.len() % 2 != 0 {
            return Err(SandboxError::MalformedPayload("Invalid UTF-16LE byte sequence".into()));
        }

        let u16_chars: Vec<u16> = decoded_bytes
            .chunks_exact(2)
            .map(|chunk| u16::from_le_bytes([chunk[0], chunk[1]]))
            .collect();

        String::from_utf16(&u16_chars)
            .map_err(|e| SandboxError::MalformedPayload(format!("UTF-16LE decode failed: {e}")))
    }
}
```

### 2.2 模块二：工作区级全局路径分级互斥锁状态机（WorkspacePathMutexManager）

彻底拔除按 Run 独立创建的 `WritePathRegistry`，在工作区单例层建立基于真实 Canonical Path 的多粒度分级读写锁树（Hierarchical Path RwLock）。

#### 2.2.1 锁模式与兼容性矩阵

采用数据库经典的多粒度意向锁模型（Intent Lock）：
- **IS (Intent Shared)**：意向读锁。在读取叶子节点前，对其所有祖先目录加 IS 锁。
- **IX (Intent Exclusive)**：意向写锁。在写入/删除叶子节点前，对其所有祖先目录加 IX 锁。
- **S (Shared Read)**：共享读锁。读取文件或遍历目录时，锁定目标节点。
- **X (Exclusive Write)**：排他写锁。写入文件、覆盖文件或删除目录/文件时，排他锁定目标节点。

```
              【多粒度分级锁兼容矩阵 (Compatibility Matrix)】

            ┌────────┬────────┬────────┬────────┬────────┐
            │ 请求\持有│   IS   │   IX   │   S    │   X    │
            ├────────┼────────┼────────┼────────┼────────┤
            │   IS   │   OK   │   OK   │   OK   │   NO   │
            ├────────┼────────┼────────┼────────┼────────┤
            │   IX   │   OK   │   OK   │   NO   │   NO   │
            ├────────┼────────┼────────┼────────┼────────┤
            │   S    │   OK   │   NO   │   OK   │   NO   │
            ├────────┼────────┼────────┼────────┼────────┤
            │   X    │   NO   │   NO   │   NO   │   NO   │
            └────────┴────────┴────────┴────────┴────────┘
```

**关键设计断言**：
- 当 A 写入 `/workspace/src/main.rs` 时，对 `/workspace` 和 `/workspace/src` 施加 **IX 锁**，对 `/workspace/src/main.rs` 施加 **X 锁**。
- 若 B 试图删除目录 `/workspace/src`，B 需要对 `/workspace/src` 请求 **X 锁**。由于该节点已存在 A 的 **IX 锁**，且 `X` 与 `IX` 互斥，B 立即被拦截冲突！
- 若 C 并行读取 `/workspace/src/main.rs`，C 请求 `S 锁`，与 A 的 `X 锁` 互斥，C 被排队或返回冲突。

#### 2.2.2 核心数据结构与唯一真理源契约

```rust

use std::path::{Path, PathBuf};
use std::sync::Arc;
use tokio::sync::{Mutex, RwLock};

#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub enum LockMode {
    IntentShared,     // IS
    IntentExclusive,  // IX
    Shared,           // S
    Exclusive,        // X
}

#[derive(Debug, Clone, PartialEq, Eq, Hash)]

    pub session_id: String,
    pub run_id: String,
    pub tool_call_id: String, // 细化到单次工具调用，杜绝同 Run 内部碰撞跳过！

pub struct LockGrant {
    pub holder: LockHolderId,
    pub mode: LockMode,
    pub granted_at_ms: i64,
    pub expires_at_ms: i64,
}

#[derive(Debug, Default)]
pub struct PathTreeNode {
    pub grants: Vec<LockGrant>,
    pub children: HashMap<String, Box<PathTreeNode>>,
}

/// 工作区全局单例路径互斥管理器
pub struct WorkspacePathMutexManager {
    workspace_root: PathBuf,
    default_lease_ms: u64,
    root_node: RwLock<PathTreeNode>,
    active_leases: Mutex<HashMap<String, tokio::task::JoinHandle<()>>>,
}

pub struct PathLockTicket {
    manager: Arc<WorkspacePathMutexManager>,
    holder: LockHolderId,
    canonical_paths: Vec<PathBuf>,
    modes: Vec<LockMode>,
}

impl Drop for PathLockTicket {
    fn drop(&mut self) {
        // 精确释放本次 ToolCall 占用的锁，绝不触碰其他并行 ToolCall 的锁！
        let mgr = Arc::clone(&self.manager);
        let holder = self.holder.clone();
        let paths = self.canonical_paths.clone();
        tokio::spawn(async move {
            mgr.release_locks(&holder, &paths).await;
        });
    }
}
```

#### 2.2.3 规范化路径真理源与防死锁设计

1. **唯一真理源（Canonicalization Boundary）**：
   所有进入互斥状态机的路径，必须在入口完成无损规范化：
   - 解析全链路软链接 / Junction（`safe_canonicalize`）；
   - 剥离 Windows UNC `\\?\` 前缀；
   - Windows 平台大小写严格折叠为统一小写；
   - 验证目标物理路径严格属于 `workspace_root`。
2. **防死锁字典序加锁（Deadlock-Free Ordering）**：
   在单次工具调用需要批量锁定多条路径时（如 `multi_replace` 或批量重命名），先对所有规范化路径进行升序排序（Lexicographical Order），然后按照自顶向下、由前至后的绝对顺序依次加锁，彻底杜绝环形等待死锁。
3. **动态心跳租约（Dynamic Heartbeat Renewal）**：
   摒弃静态 60s 倒计时。工具执行期间，后台常驻 15s 间隔心跳 Task 对当前持有租约持续续期（Renew Lease）；当且仅当进程意外崩溃或工具执行严重挂死时，60s 无心跳才会自动熔断释放，兼顾强安全性与长耗时任务支持。

```rust
    pub fn verify_execution(
        ctx: &ToolContext,

        tool_args: &serde_json::Value,
```

## 五、立体验证与验收用例设计

依据《立体验证纪律》（禁止单一检查冒充验收），设计四层立体验证网络：

```
                             【四层立体验证网络】

   [层级 1: 编译与类型门禁]  ──► cargo check + clippy 零警告拦截
   [层级 2: 纯逻辑穷举单测]  ──► AST 缩写消歧、Polyglot 审计、CD 穿透、Merkle 校验
   [层级 3: 极端并发与故障]  ──► 跨 Run 资源争用、同 Run 并行写、断电崩溃恢复
   [层级 4: 端到端现场验收]  ──► Tauri 桌面真实宿主、PowerShell 真实执行、回收站撤回
```

### 5.1 层级 1：静态编译与类型门禁
- **检查命令**：
  ```bash
  cargo clippy --workspace --all-targets -- -D warnings
  cargo test --workspace --no-run
  ```
- **通过准则**：
  零编译错误，零 Clippy 警告。

### 5.2 层级 2：核心纯逻辑穷举单元测试
1. **PowerShell 参数消歧与解码全变体矩阵**：
   - 测试用例覆盖：`-e`、`-E`、`-ec`、`-EC`、`-en`、`-enc`、`-enco`、`-EncodedCommand`、`/ec`、`/e:`、`-ec:payload`、`-EncodedCommand=payload`。
   - 验证断言：内嵌 `rm -rf /` 或 `Format-Volume` 的 Base64 载荷，在上述全部参数形式下均能 100% 解码并标记为 `CommandClass::Redline`。
2. **多语言解释器（Python/Node）动态求值审查**：
   - 输入 `python -c "import os; os.system('rm -rf /')"`，断言分类升级为 `CommandClass::Redline`；
   - 输入 `python -c "import urllib.request; ..."`，断言分类升级为 `CommandClass::Dangerous`（触发人工审批），绝不允许落入 `Allowed`；
   - 输入 `node -e "require('child_process').execSync('dir')"`，断言分类为 `CommandClass::Redline`。
3. **CD 家族与间接嵌套穿透拦截**：
   - 测试用例：`Push-Location C:\`、`pop-location`、`cmd /c "cd /d D:\ & dir"`、`powershell -Command "Push-Location ..; ls"`；
   - 验证断言：全部精准返回 `TOOL_CD_BLOCKED` 错误，引导参数 `Cwd`。
4. **工作区边界与符号链接 Fail-Closed 测试**：
   - 测试 Windows 盘符大小写不一致（`c:\workspace` vs `C:\workspace`）下的符号链接解析；
   - 验证断言：即便前缀大小写异常，解析失败时恒定拒绝，无穿透。

### 5.3 层级 3：极端并发与故障注入测试
1. **跨 Run 写路径互斥冲突断言**：
   - 构造主 Agent Run 与子 Agent Run 同时向 `WorkspacePathMutexManager` 请求写锁 `/workspace/src/lib.rs`；
   - 验证断言：后发起者严格返回 `tool.write_path_conflict`，携带占用者的具体身份与租约时刻。
2. **同 Run 单轮内多工具并行写冲突断言**：
   - 构造单次 Assistant 消息包含两个并行的 `write_file` 指向同一目标文件；
   - 验证断言：二者持有不同的 `tool_call_id`，第二笔声明必然被互斥锁拦截，禁止同 Run 内部互相穿透。
3. **父子目录分级锁冲突断言（IX vs X）**：
   - 线程 1 声明写入 `/workspace/src/deep/file.rs`（获得 `/workspace/src` 的 IX 锁）；
   - 线程 2 声明删除目录 `/workspace/src`（请求 `/workspace/src` 的 X 锁）；
   - 验证断言：线程 2 立即检测到锁冲突并拒绝，保护正在写入的文件。
4. **崩溃自愈与 WAL 回滚断言（故障注入）**：
   - 构造 5 个文件的批量删除事务；
   - 在暂存第 3 个文件后，强行终止事务线程（模拟断电崩溃）；
   - 调用 `TrashService::recover_dangling_transactions()`；
   - 验证断言：第 1、2 个已暂存文件被 100% 自动原子移回工作区，工作区 MD5 校验和与初始状态一致，无孤儿文件遗留。

### 5.4 层级 4：端到端现场与真实宿主验收
1. **FullAccess 模式真实 Shell 删除撤回验收**：
   - 在桌面端设置 `permissionMode = "full-access"`；
   - 调用 `shell_command` 执行 `rm unwanted_file.txt`；
   - 验证现场：命令执行成功，但工作区文件被安全移入应用回收站，`meta.json` 包含该文件的 SHA-256 校验和与 entryId；
   - 调用撤回恢复接口，文件原样恢复且哈希完全匹配。
2. **Commit 子 Agent 越权阻断真实验收**：
   - 启动一个 `task_type = "commit"` 的子 Agent；
   - 发送指令调用 `shell_command` 执行 `npm run build` 或 `echo "hacked" > README.md`；
   - 验证现场：执行管道立即阻断并报错：“Commit 子 Agent 严格限制仅能执行 git 家族命令”，指令未产生任何文件系统副作用。
3. **长期长耗时操作动态心跳续期验收**：
   - 启动一个持有写锁且执行长达 90 秒的大文件处理任务；
   - 验证现场：在第 65 秒时，锁状态依然处于 Active 状态，未被 60s 静态超时提前释放；在任务正常结束后，锁立即被干净释放。
