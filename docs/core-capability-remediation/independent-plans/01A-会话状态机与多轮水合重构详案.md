# 会话状态机与多轮水合重构详案（A轨：核心状态机闭环、单源真理水合与因果有序性）

> **方案标识**：01A（核心能力系统性整改战役 · 方向一 A轨独立方案）  
> **设计视角**：状态机严格闭合回路、多轮历史单源真理（SSOT）、Token 用量全链路保真与并发因果屏障  
> **基线对齐**：`docs/backend-core-capability/analysis/01-会话状态机与回合主路径.md`  
> **设计原则**：坚决杜绝补丁式修补，做对的事情，大改动大重构；非必要不兼容，无用胶水代码物理拔除。

## 一、现状与根因穿透（Deep-Dive Root Causes & Code Path Mapping）

基于对 `crates/session-loop`、`crates/conex-types`、`crates/agent-provider`、`apps/agent-workbench` 及 `apps/crish-desktop` 的穿透式源码审计与动态链路跟踪，当前核心会话状态机、多轮水合与回合流转主路径存在多项致命架构缺陷。以下对审查识别的核心问题进行逐项代码级根因穿透与因果链还原：

---

### 1.1 桌面多轮水合暴力截断上一轮助手回复（BC01-4）

- **故障现象**：在多轮对话中，从第二轮开始，送入大模型的上下文历史中，上一轮模型的 Assistant 完整回复（包括其文本、思考过程及工具调用）被彻底抹杀。大模型看到的上下文蜕化为连续的多个用户提问（`[User_1, User_2]`），导致模型出现“严重失忆”，无法延续上一轮的对话内容与执行结论。
- **精准代码路径**：
  1. `apps/crish-desktop/src/api/chat-bridge/streamSession.ts:177`：
     ```typescript
     const body = await loadSessionBody(safeSessionId);
     history = buildHistoryMessages(body, { excludeId: userClientMessageId });
     ```
     前端向后端发送当前新用户提问前，调用 `buildHistoryMessages` 并显式排除了当前正在发送的新消息 `userClientMessageId`。因此传入后端的 `history` 数组是以“上一轮 Assistant 最终回复”结尾的已完成对话序列：`[User_1, Assistant_1, ..., User_N-1, Assistant_N-1]`。
  2. `apps/agent-workbench/src-tauri/src/run/run_history.rs:416-422` & `run_launch.rs:1205`：
     前端历史非空时，强制选择 `HistorySource::Frontend`，调用 `session_loop::hydrate::hydrate_history(payload)`。
  3. `crates/session-loop/src/hydrate.rs:323-330`：
     ```rust
     fn truncate_to_last_user(messages: &mut Vec<Arc<AgentMessage>>) {
         match messages
             .iter()
             .rposition(|message| message.role == AgentMessageRole::User)
         {
             Some(last_user) => messages.truncate(last_user + 1),
             None => messages.clear(),
         }
     }
     ```
     `hydrate.rs:55` 在主入口中直接调用 `truncate_to_last_user(&mut messages)`。在输入序列为 `[User_1, Assistant_1]` 时，最后一个 User 消息是 `User_1`（下标 0），`truncate(0 + 1)` 直接将 `Assistant_1` 从序列中物理抹除！
  4. `crates/session-loop/src/hydrate.rs:424-426` 批注妄称：
     *“截断尾部非 user 只约束‘纯历史形态’的协议合法性，因为 run 还会追加新用户消息收尾”*。
     该设计逻辑存在严重倒错：既然 `run(new_user_message)` 即将在尾部追加全新的 User 消息，那么送入水合的前序历史就**天然应当且必须**以 Assistant（或其产生的 Tool 结果）收尾！强行在此处把前序 Assistant 截掉，导致模型收到的完整历史变成了 `[User_1, User_2]`，犯下致命的对话破坏。
- **架构断裂本质**：设计者混淆了**“整个模型请求上下文的尾部合法性（必须以当前最新的 User 提问结尾）”**与**“前置已完成历史的自然形态（通常以 Assistant 结论结尾）”**，在不该截断的中间边界上执行了破坏性的截断操作。

### 1.2 工具真实输出丢失并篡改为 TOOL_OUTCOME_UNKNOWN 假报错（BC01-5）

- **故障现象**：在包含工具调用的多轮对话中，水合后的下一轮上下文里，模型上一轮发起的工具调用依然存在，但其真实返回结果（如文件内容、终端命令输出）完全丢失，被篡改为 `TOOL_OUTCOME_UNKNOWN` 并且 `is_error` 被标记为 `true`。模型误以为自己上一轮执行的所有工具全部发生未知异常，进而产生幻觉、反复重试已成功的操作或向用户道歉。
- **精准代码路径**：
  1. `apps/crish-desktop/src/hooks/agentStreamCallbacks.ts:175-194` (`onToolSuccess`) 及 `197-204` (`onToolError`)：
     前端桌面端在工具执行完成时，将真实输出保存在消息对象内部 `m.toolCalls` 数组中对应项的 `output` 字段上（`tc.status = 'success'`, `tc.output = displayOut || output`），根本不维护 `m.toolCallResults` 独立字段。
  2. `apps/crish-desktop/src/api/chat-bridge/historyMessages.ts:147-150`：
     前端构造器将 `msg.toolCalls` 原样序列化为 `tool_calls_json`。由于 `msg.toolCallResults` 为 `undefined`，`tool_call_results_json` 字段保持 `undefined`。
  3. `crates/session-loop/src/hydrate.rs:194-203`：
     ```rust
     #[derive(Debug, Deserialize)]
     #[serde(rename_all = "camelCase")]
     struct LegacyToolCall {
         id: String,
         name: String,
         #[serde(default)]
         arguments: Option<String>,
     }
     ```
     Rust 侧仅解析了 `id`、`name`、`arguments`，将序列化在 JSON 里的 `output` 和 `status` 字段彻底当成未知字段丢弃！
  4. `crates/session-loop/src/hydrate.rs:178-190`：
     `synthesize_blocks` 尝试从 `tool_call_results_json` 中提取结果，但该字段为 `None`，因此未能生成任何 `AgentMessageBlock::ToolResult` 块。
  5. `crates/session-loop/src/hydrate.rs:346-405`：
     `repair_orphan_tool_calls` 扫描到 Assistant 上存在 ToolCall 但未配对 ToolResult，盲目判定所有工具调用皆为“孤儿调用”，强行生成合成 Tool 消息：
     `output: "outcome unknown after history hydration: TOOL_OUTCOME_UNKNOWN"`, `is_error: true`。
- **架构断裂本质**：前后端契约断裂。生产端数据早已统一挂载在 `MessageToolCall.output` 上，而后端水合代码仍固守过时的双 JSON 假设（`tool_calls_json` + `tool_call_results_json`），且孤儿自愈逻辑在缺乏信息时不校验调用自身是否携带结果，暴力生成假错误向 LLM 投毒。

### 1.3 无工具回合将 turn_index 归零导致同一 Run 助手正文覆盖（BC01-3）

- **故障现象**：在同一次 Run 中，当首轮纯文本回复生成结束，且后续队列中已有提问（follow-up 或安全点已排队的待运行输入）继续推进时，状态机将回合计数器 `turn_index` 重置为 0。第二轮回复开始时发射的 `TurnStart` 下标再次为 1。桌面端前端在处理助手消息收口时，使用 `turnIndex` 作为分段数组下标（`segs[turnIndex] = piece`），导致第二轮助手生成的正文直接将第一轮正文覆写消失。
- **精准代码路径**：
  1. `crates/session-loop/src/loop/handlers/turn_complete.rs:187-200`：
     ```rust
     let promoted = state.input_queue.promote_follow_up();
     if promoted > 0 || state.input_queue.has_runnable_pending() {
         dispatch(state, E::InputAvailable)?;
         return Ok(HandlerOutcome::continue_run());
     }
     ```
  2. `crates/conex-types/src/transition.rs:172-178`：
     ```rust
     S::TurnComplete => match event {
         E::InputAvailable => Ok(AgentTransition::with_effect(
             S::AwaitingInput,
             AgentTransitionEffect {
                 reset_all_counters: true,
                 ..AgentTransitionEffect::none()
             },
         )),
     ```
  3. `crates/session-loop/src/state.rs:91-95`：
     ```rust
     if effect.reset_all_counters {
         self.context.turn_index = 0;
         self.context.tool_call_count = 0;
         self.context.steering_count = 0;
     }
     ```
     `reset_all_counters` 将 `self.context.turn_index` 硬编码归零！
  4. `crates/session-loop/src/loop/handlers/prepare_turn.rs:66`：
     下一轮执行 `state.machine.context().turn_index.saturating_add(1)`，得到的 `turn_index` 依然是 `0 + 1 = 1`！
  5. `apps/crish-desktop/src/api/chat-bridge/handlers/messageHandlers.ts:187-193`：
     前端依据事件中的 `turnIndex` 维护 `state.turnAuthoritativeTexts.set(turnIndex, piece)` 以及 `segs[turnIndex] = piece`，下标碰撞导致第一轮权威正文被第二轮直接覆盖。
- **架构断裂本质**：状态机概念混淆。在同一个 Run 的生命周期内，`turn_index` 代表物理因果时钟，必须具备**严格单调自增性**。将“跨 Run/全新会话初始化”的归零逻辑错误地施加在同 Run 内部由排队输入推进的后续回合上。

### 1.4 准备回合重进导致 TurnStart/TurnEnd 终态断裂与 Usage 抹杀（BC01-1）

- **故障现象**：在同一次 Run 中，因长度升级（`Length` 阶梯升级）、空响应重试、Tool-Promise 动作自愈、工具批后插队输入或转向评估完成而重新进入准备回合时，上一轮的 `TurnStart` 永远无法等到匹配的 `TurnEnd`；且上一轮实际消耗的 Token 用量（`budget_state.turn_usage`）在重进时被无条件置为 `None`，导致用量统计严重失真，事件日志中出现孤儿 `TurnStart`。
- **精准代码路径**：
  1. `crates/session-loop/src/loop/handlers/no_tool_calls.rs:64, 71, 119`、`executing_tools.rs:156`、`steering_evaluation.rs:39, 90`：
     分别派发 `E::NoProgressContinue`、`E::InputAvailable`、`E::SteeringComplete`。
  2. `crates/conex-types/src/transition.rs:140, 151, 163`：
     上述转移全部直接跳转至 `S::PreparingTurn`，直接绕过了 `turn_complete.rs` 的正常收口逻辑。
  3. `crates/session-loop/src/loop/handlers/prepare_turn.rs:66-80`：
     ```rust
     let turn_index = state.machine.context().turn_index.saturating_add(1);
     state.budget_state.turn_usage = None; // 上一轮用量被直接清空丢弃！
     let start_event = AgentEvent::TurnStart { ... };
     state.emit_event(start_event);
     state.current_turn_index = Some(turn_index); // 覆写槽位，前序 TurnStart 彻底失联成孤儿！
     ```
- **架构断裂本质**：状态机转移图缺乏闭环不变量。重进准备回合在逻辑上开启了新的模型请求回合，但系统未在前序回合离开时（或新回合进入前）履行 `TurnEnd` 结算义务，破坏了 `TurnStart`/`TurnEnd` 严格 1:1 的配对契约。

### 1.5 安全点无条件补发伪 TurnEnd 与软注入双重终态、强停工具结果越界（BC01-2）

- **故障现象**：
  1. 在流式结束、工具执行前后及回合收口的安全点，只要外部存在任何控制动作（甚至包括无害的 L1 `SoftInject` 软注入用户消息），系统就会提前发射一条 `usage: None` 的虚假 `TurnEnd`。而在软注入场景下，循环根本不会中断，随后的正常收口会再次发射一条携带真实 Usage 的 `TurnEnd`，造成“单回合双终态”。
  2. 当强停发生在 `ExecutingTools` 入口时，虚假 `TurnEnd` 率先发出，随后合成的未决工具中断结果（`AgentMessageRole::Tool`）才落入对话树，导致工具结果排在轮次闭合之后，因果倒置。
- **精准代码路径**：
  1. `crates/session-loop/src/loop/handlers/mod.rs:537-540`：
     ```rust
     emit_missing_turn_end(state);
     match action { ... }
     ```
     `check_control` 在识别 `action` 具体语义之前，无条件调用 `emit_missing_turn_end`！
  2. `crates/session-loop/src/loop/handlers/mod.rs:467-477`：
     `emit_missing_turn_end` 将 `usage` 硬编码为 `None`，不取 `budget_state.turn_usage` 中的真值。
  3. `crates/session-loop/src/loop/handlers/mod.rs:558-569`：
     `SoftInject` 仅把消息入队，返回 `Ok(None)` 继续执行，导致下游 `turn_complete.rs:41-55` 再次发射真实的 `TurnEnd`。
  4. `crates/session-loop/src/loop/handlers/executing_tools.rs:49-62`：
     `check_control` 提前清空轮次槽位发射 `TurnEnd`，随后 `synthesize_and_record_interrupted_calls` 才把合成的 Tool 消息记录进 `conversation`。
- **架构断裂本质**：控制流检查与生命周期状态机严重耦合且因果倒置。`check_control` 将“轮次终止清理”置于“控制意图类型判定”之前；并且把工具中断结果这种“轮次内部收尾资产”置于“轮次结束事件”之后。

### 1.6 历史图片与多模态块在水合时丢失（BC01-6）

- **故障现象**：历史消息中的多模态图片、图文混排块在水合时无法保留，或者由于无法反序列化回 `AgentMessageBlock` 而被整体降级为纯文本，导致多轮会话中的视觉线索完全丧失。
- **精准代码路径**：
  1. `crates/conex-types/src/message.rs:136-157`：`AgentMessageBlock` 枚举仅有 `Text`、`Thought`、`ToolCall`、`ToolResult` 四个变体，完全缺失 `Image` 变体。
  2. `crates/session-loop/src/hydrate.rs:130-143`：反序列化前端带有 `type: "image"` 的时间线结构时必然失败，警告日志后回退到纯文本合成，图片数据物理蒸发。

### 1.7 准备与转向评估相位协同停止空转导致附带消息丢弃（BC01-7）

- **故障现象**：在 `PreparingTurn` 或 `SteeringEvaluation` 相位触发 `CooperativeStop` 时，状态机处于空分支不推进行为，却直接向外层返回 `stopped`。附带随停止动作抽走的待注入控制消息仅被丢入内存中的 `input_queue`。由于外层壳层每个 Run 均销毁并重建 `AgentSessionLoop` 实例，这些内存消息随之永久丢失。
- **精准代码路径**：`crates/session-loop/src/loop/handlers/mod.rs:436-451` 对该两相为空实现 `{}`，`handlers/mod.rs:551-556` 直接返回 `Some(EndDecision::stopped(state))`。

### 1.8 待处理输入保存与删除无序并发导致已消费消息幽灵复活（BC01-8）

- **故障现象**：用户发送消息入队时异步派发 `spawn_pending_input_save`（执行 `INSERT OR REPLACE`），消息被消费时异步派发 `delete_pending_input`（执行 `DELETE`）。两者均为无顺序保证的独立 `tokio::spawn` 协程。在高频或高 I/O 延迟下，若删除操作先于保存操作提交，已被消费的消息会被后提交的保存操作重新写回 SQLite 表，导致软件重启时发生已回答消息的“幽灵复活”重复执行。
- **精准代码路径**：`crates/session-loop/src/loop/loop_runner.rs:343-367` 与 `handlers/mod.rs:252-267`。

## 二、架构重构设计与核心契约（A轨详案）

A轨重构方案秉持**“状态机闭合回路、单源真理水合、全链路用量保真与并发因果屏障”**的架构原则，进行根本性重塑，绝不搞过渡胶水层。

```
│   [前端与持久化数据源]                                  [水合单源真理流水线 (hydrate.rs)]        │
```

### 2.1 全生命周期状态机闭环与单调因果时钟架构

#### 2.1.1 状态转移表拓扑重构（`crates/conex-types/src/transition.rs`）
彻底切断从 `ExecutingTools` 越级跳转至 `PreparingTurn` 的旁路。任何已发射 `TurnStart` 的回合，离开执行态时**必须且只能进入 `TurnComplete`**：

```rust
// crates/conex-types/src/transition.rs

// ── executing-tools ──
S::ExecutingTools => match event {
    // 正常完成工具批，推进至收口
    E::ToolsComplete => Ok(AgentTransition::plain(S::TurnComplete)),
    // 【核心重构】：即使存在排队可用输入（force/steer），也必须先推进至 TurnComplete 结算当前回合！
    // 彻底切断直跳 PreparingTurn 的短路旁路，保证 TurnEnd 不丢失
    E::InputAvailable => Ok(AgentTransition::plain(S::TurnComplete)),
    E::Abort => Ok(AgentTransition::with_end_reason(S::TurnComplete, Aborted)),
    E::Error => Ok(AgentTransition::with_end_reason(S::TurnComplete, Error)),
    _ => Err(TransitionError::Undefined { state, event }),
},

// ── turn-complete ──
S::TurnComplete => match event {
    // 【核心重构】：当前回合收口后，若检测到后续输入可用，流转至 AwaitingInput
    // 严禁 reset_all_counters！turn_index 保持单调递增，仅重置工具调用与转向计数
    E::InputAvailable => Ok(AgentTransition::with_effect(
        S::AwaitingInput,
        AgentTransitionEffect {
            turn_index_increment: false,
            reset_tool_call_count: true,
            set_tool_call_count: None,
            reset_all_counters: false, // 彻底禁用归零！
        },
    )),
    E::NextTurn => Ok(AgentTransition::plain(S::PreparingTurn)),
    E::MaxTurnsReached => Ok(AgentTransition::with_end_reason(S::Done, MaxTurns)),
    E::ShouldStop => Ok(AgentTransition::plain(S::Done)),
    E::Abort => Ok(AgentTransition::with_end_reason(S::Done, Aborted)),
    E::Finish => Ok(AgentTransition::plain(S::Done)),
    _ => Err(TransitionError::Undefined { state, event }),
},
```

#### 2.1.2 单 Run 内 `turn_index` 严格单调递增不变量
在 `crates/session-loop/src/state.rs` 中，移除 `reset_all_counters` 对 `turn_index` 的抹除，确立单 Run 内部回合时钟不可逆原则：
- **定理 1（回合时钟单调性）**：$\forall t_1 < t_2$，在单次 Run 生命周期内必定满足 $\text{turn\_index}(t_1) \le \text{turn\_index}(t_2)$。
- **实现契约**：同 Run 内不论经历多少次工具迭代、多少条排队追加输入（follow-up），`turn_index` 永不回滚、永不归零。前端消息分段依据严格递增的 `turnIndex` 在 `segs[turnIndex]` 中开辟独立插槽，彻底根除正文覆盖。

#### 2.1.3 `TurnStart(N)` 与 `TurnEnd(N)` 严格 1:1 成对发射与 Usage 保全契约
在 `crates/session-loop/src/loop/handlers/prepare_turn.rs` 入口处建立守卫断言：
1. **重进准备回合自愈**：当因长度升级（`NoProgressContinue`）、转向重新评估（`SteeringComplete`）重新进入 `prepare_turn` 时，检查 `state.current_turn_index`。
2. 若 `state.current_turn_index` 为 `Some(unclosed_index)`，表明前序尝试已触发 `TurnStart` 但绕过了 `turn_complete`。此时必须在开启新一轮前，**原地补发前序回合的 `TurnEnd`**：
   ```rust
   if let Some(prev_turn) = state.current_turn_index.take() {
       let end_event = AgentEvent::TurnEnd {
           session_id: state.machine.context().session_id.clone(),
           turn_index: prev_turn,
           timestamp: conex_shared::time::now_iso_utc(),
           tool_call_count: state.machine.context().tool_call_count,
           // 必须提取已经产生的真实 Token 用量，绝对不允许静默清空抹杀！
           usage: state.budget_state.turn_usage.take(),
       };
       state.emit_event(end_event);
   }
   ```
3. 随后，新回合执行单调步进 `turn_index = turn_index + 1`，发射新回合的 `TurnStart(N+1)`，并将 `current_turn_index` 置为 `Some(N+1)`。
4. **效果**：无论经历多少次重试与恢复阶梯，事件序列恒为：
   `TurnStart(1) -> [Streaming] -> TurnEnd(1, usage_1) -> TurnStart(2) -> [Streaming] -> TurnEnd(2, usage_2)`。

#### 2.1.4 安全点控制检查（`check_control`）因果分流与强停工具结果优先闭环
重构 `crates/session-loop/src/loop/handlers/mod.rs` 中的 `check_control` 与 `emit_missing_turn_end`：
1. **控制动作分流前严禁提前收口**：删除函数首部的盲目 `emit_missing_turn_end` 调用。
2. **区分动作语义**：
   - `SoftInject`：属于异步入队操作，循环继续进行。**绝对不发射 `TurnEnd`**，避免单回合双终态。
   - `ForceCancel` / `CooperativeStop`：属于终结动作。此时在状态机转向退出时统一补发闭合。
3. **强停工具结果优先入账**：在 `executing_tools.rs` 中，若遭遇中断强停，**必须先执行 `synthesize_and_record_interrupted_calls` 将中断工具结果写入 `conversation`，随后再调用 `emit_missing_turn_end` 闭合当前回合**。确保工具结果在因果时间线上严格处于回合内部。
4. **真实用量提取**：`emit_missing_turn_end` 内部使用 `state.budget_state.turn_usage.take()` 提取真实消耗，严禁硬编码 `None`。

```rust
/// 头部协议清洗：剔除序列最开头的孤儿 Tool 结果或非法 Assistant 碎片，
/// 确保对话序列第一条非 System 消息必须为合法的 User 消息。
fn sanitize_conversation_head(messages: &mut Vec<Arc<AgentMessage>>) {
    let first_valid_idx = messages.iter().position(|m| {
        m.role == AgentMessageRole::User || m.role == AgentMessageRole::System
    });
    match first_valid_idx {
        Some(idx) if idx > 0 => {
            tracing::warn!(dropped_count = idx, "hydrate: 剔除头部孤儿非用户消息碎片");
            messages.drain(0..idx);
        }
        None => {
            // 整个序列无任何 User/System 消息，清空回退
            messages.clear();
        }
        _ => {}
    }
}
```

```rust
fn synthesize_blocks(entry: &HistoryMessage) -> (Vec<AgentMessageBlock>, Vec<AgentMessage>) {
    let mut blocks = Vec::new();
    let mut companion_tool_messages = Vec::new();

    if let Some(text) = entry.text.as_deref().filter(|t| !t.is_empty()) {
        blocks.push(AgentMessageBlock::Text { text: text.to_string() });
    }
    if let Some(thinking) = entry.thinking.as_deref().filter(|t| !t.is_empty()) {
        blocks.push(AgentMessageBlock::Thought { text: thinking.to_string(), redacted: None });
    }

    let tool_calls = parse_hydrated_tool_calls(entry);
    let explicit_results = parse_tool_call_results(entry);

    for call in &tool_calls {
        // 1. Assistant 消息上记录 ToolCall 块
        blocks.push(AgentMessageBlock::ToolCall(ToolCallBlock {
            id: call.id.clone(),
            tool_name: call.name.clone(),
            input: parse_arguments(&call.arguments),
        }));

        // 2. 匹配真实输出：优先从 call.output 取值，次从 tool_call_results 取值
        let matched_output = call.output.clone().or_else(|| {
            explicit_results
                .iter()
                .find(|r| r.id == call.id)
                .and_then(|r| r.output.clone())
        });

        if let Some(output_text) = matched_output {
            let is_error = call.status.as_deref() == Some("error")
                || explicit_results.iter().find(|r| r.id == call.id).and_then(|r| r.is_error).unwrap_or(false);

            // 生成运行时完全对齐的 AgentMessageRole::Tool 独立结果消息
            companion_tool_messages.push(AgentMessage {
                id: format!("tool-result-{}", call.id),
                role: AgentMessageRole::Tool,
                created_at: iso8601_from_epoch_millis(entry.timestamp),
                blocks: vec![AgentMessageBlock::ToolResult {
                    tool_call_id: call.id.clone(),
                    tool_name: call.name.clone(),
                    output: ToolOutput::text(output_text),
                    is_error,
                }],
                metadata: None,
                client_message_id: None,
                content: None,
            });
        }
    }

    (blocks, companion_tool_messages)
}
```

  3. `assert_eq!(tool_res.blocks[0].output_text(), "文件真实内容ABC");`
  4. 绝不包含 `"TOOL_OUTCOME_UNKNOWN"` 字符串！

#### 用例 U-03：真孤儿调用的降级自愈幂等性
- **输入**：`Assistant` 历史消息，声明了 `id: "c2"` 的 ToolCall，但 `output` 明确为 `None`，且无任何后续结果。

### 5.3 多轮端到端完整业务场景验收（E2E Integration Tests）

#### 用例 E-01：两轮完整问答上下文穿透验收
- **轮次 1**：用户提问“1 + 1 等于几？”，助手回答“1 + 1 等于 2”。
- **轮次 2**：用户提问“再加上 3 呢？”，后端水合前序历史。
- **请求 Wire 抓包断言**：
  发送给底层大模型 Provider 的 Wire Payload（`to_chat_messages` 结果）必须精确呈现为：
  ```json
  [
    {"role": "user", "content": "1 + 1 等于几？"},
    {"role": "assistant", "content": "1 + 1 等于 2"},
    {"role": "user", "content": "再加上 3 呢？"}
  ]
  ```
  绝对不允许出现 `assistant` 消息丢失变成 `[user, user]` 的情况！

- **轮次 1**：用户提问“读取 config.json 并告诉我版本”，模型发起 `read_file` 工具调用并成功获取内容 `{"version": "2.0.0"}`，模型最终回答“版本是 2.0.0”。

  2. `Tool` 消息状态为正常成功，绝对无 `TOOL_OUTCOME_UNKNOWN`。
  3. 模型在第二轮正常识别到刚才的版本号为 2.0.0 并进行修改，未发生重复读取或未知错误告警。
