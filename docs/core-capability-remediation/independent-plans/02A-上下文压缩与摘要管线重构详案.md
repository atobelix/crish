## 一、执行摘要与核心突破目标

在当前 Conex / Crish 系统的上下文压缩（Context Compaction）与历史摘要（Summary Pipeline）实现中，存在严重的**“单次运行虚标、跨轮全文复活、代数硬编码冲突、关键字段静默清空、上下文找回工具全盘未接线”**等虚假实现与契约断裂：

1. **“空壳压缩”与全文复活（BC05-1）**：
   在单次运行中，压缩虽然在内存中替换了 `state.conversation`，但既不产生 `MessageStart` / `MessageEnd` 事件，也不将改写后的会话写回底层的 `session_messages` 物理表。桌面端下一次发送消息时，前端从 SQLite 重新装载全量原始消息（`loadSessionBody`），并通过 `history` 参数送给引擎；引擎历史选择器（`resolve_history_source`）优先选用非空的前端历史，导致上一轮刚压缩的内容被全文读回，模型再次看到超窗历史并重复触发压缩。
2. **压缩代数固定为 1 导致的主键冲突与静默丢弃（BC05-3）**：
   `CompactionEngine` 内部将压缩代数硬编码为 `let generation: u32 = 1`，产生的块 ID 永远是 `compacted-summary-1-{fold}`。跨 Run 发生第二次压缩时，由于前端历史复活导致折叠计数重置，块 ID 再次生成为 `compacted-summary-1-1`。底层的 `INSERT OR IGNORE INTO compression_blocks` 命中 `(session_id, block_id)` 复合主键冲突，静默忽略插入。第二次及以后的丢弃集合、摘要状态、Token 指标被全盘丢失，块表永远停留在首次压缩快照。
3. **Critical Context 契约断裂与关键信息静默蒸发（BC05-6）**：
   AI 摘要提示词严格要求 `criticalContext` 为 JSON 数组（逐字保留路径、符号、命令、错误串），但校验器只检查字段存在性，Markdown 渲染器却使用 `string_field(doc, "criticalContext")`（要求为字符串）。模型诚实输出数组时，渲染器将其强行解析为字符串失败并退化为空串，导致 `## Critical Context` 标题下内容全为空白，原历史中的精准错误串与命令在摘要链中静默丢失。
4. **上下文检索与解压工具全盘假实现（BC11-4）**：
   `search_context` 与 `decompress_context` 工具已被注册并暴露给模型，但在执行器 `exec_single.rs:424` 中，`compression_store` 被硬编码为 `None`。全仓库没有任何针对 `CompressionContextStore` 的生产实现，导致模型调用该工具必报 `common.unsupported`，压缩块对于模型而言彻底变成“只进不出”的黑洞。
5. **周边防御机制形同虚设（BC05-2, BC05-4, BC05-5）**：
   会话级摘要协调器绕过了重试尝试窗口护栏（BC05-2）；附件上下文预算钳制函数 `clamp_attachments_to_budget` 停留在内部模块，未接入回合准备流水线，且 IPC 入站直接丢弃了桌面附件（BC05-4）；压缩预算缺乏“低于阈值直接原样返回”的早退机制，且一压就强行砍到 2 万 Token，小窗口下预算减为负数导致紧急预检失效（BC05-5）。

本方案对上述全链路问题进行**穿透性重构**，确立如下核心目标：
- **物理闭环的事件与双写持久化（BC05-1）**：压缩完成强制派发标准的 `MessageStart` / `MessageEnd` 事件，原子重写 SQLite 的 `session_messages` 表（基于已有的 Diff Shrink 机制物理收拢历史），确保下一次桌面打字读回的是真实压缩后的会话。
- **会话级连续单调递增的代际真相源（BC05-3）**：拔除硬编码代数 1，以数据库事件计数与会话元数据为唯一事实源（SSOT），实现跨 Run 连续递增的 `generation`（1, 2, 3...），彻底根除 `(session_id, block_id)` 主键冲突。
- **类型宽容且确定性的 Critical Context 投影（BC05-6）**：重写 `summary_to_markdown`，全面支持字符串、数组、对象键值等任意合法形式的 Critical Context，杜绝空标题与关键上下文丢失。
- **真实的 SQLite 压缩块生产实现与完整工具注入（BC11-4）**：基于 `conex-db` 真实落地的 `compression_blocks` 和 `events` 表，提供 `DbCompressionContextStore` 生产实现，拔除 `compression_store: None`，实现基于关键字索引的高性能 `search_context` 和基于事件流回放的无损 `decompress_context`。
- **守卫贯通与滑窗精准化（BC05-2, BC05-4, BC05-5）**：将重试护栏接入会话级协调器；将附件预算钳制接入 IPC 与回合准备流水线；重构压缩切割点算法，实现预算内无感早退与平滑动态滑窗。

## 二、现状穿透与根因剖析 (Deep Root Cause Analysis)

### 2.1 BC05-1 根因：压缩只活在单次运行内存中，下一轮桌面 run 读回全文

```
[运行期压缩发生]
       │
       ▼
[compaction_dispatch.rs: apply_compaction]
  1. state.conversation = plan.messages (仅内存替换)
  2. emit_event(ContextCompressionEnd) (仅发压缩事件)
  3. 零 MessageStart / 零 MessageEnd !
  4. 零 SQLite session_messages 改写 !
       │
       ▼ (Run 结束)
[run_idle.rs: collect_idle_run_close]
  state.session_history.store(...) (仅写引擎内存缓存 SessionHistoryCache)
       │
       ▼ (用户在前端打字发起下一轮 run)
[streamSession.ts]
  1. body = loadSessionBody(sessionId)  <── 从 SQLite 读取未压缩的全部原始消息!
  2. history = buildHistoryMessages(body)
  3. startRunTask({ ..., history })    <── 前端将庞大全量历史下发给引擎!
       │
       ▼
[run_history.rs: resolve_history_source]
  match history {
      Some(h) if !h.is_empty() => (HistorySource::Frontend, h), <── 优先选前端!
      _ => cached,                                             <── 内存缓存被完全无视!
  }
       │
       ▼ (结果)
[下一轮 Run] 模型再次看到未压缩的全文，直接击穿上下文窗口，再次触发压缩！
```

- **代码事实定位**：
  - `crates/session-loop/src/loop/compaction_dispatch.rs:487`：`let prev_conversation = std::mem::replace(&mut state.conversation, plan.messages.clone());`，仅在内存中替换了当前运行的对话。
  - `crates/session-loop/src/loop/compaction_dispatch.rs:682-688`：广播 `AgentEvent::ContextCompressionEnd`，但没有为生成的摘要消息调用 `record_message`，也没有产生 `MessageStart` 和 `MessageEnd` 事件。
  - `crates/session-loop/src/loop/handlers/mod.rs:248-280`：只有 `record_message` 才会向事件流广播 `AgentEvent::MessageStart` 与 `AgentEvent::MessageEnd`，压缩管线与消息事件流完全脱节。
  - `apps/crish-desktop/src/api/chat-bridge/handlers/compressionHandlers.ts:32-67`：前端的 `onContextCompressionEnd` 仅仅向界面添加了一个提示性质的 `contextInjection`（“系统 · 上下文压缩完成”），**完全没有修改前端 Zustand Store 中的 `session.messages`**！
  - `apps/crish-desktop/src/api/chat-bridge/streamSession.ts:174-177`：在下一次发送时，前端通过 `loadSessionBody(safeSessionId)` 从 SQLite 的 `session_messages` 表读取历史消息，并由 `buildHistoryMessages` 组装为 `history`。
  - `apps/agent-workbench/src-tauri/src/run/run_history.rs:416-423`：`resolve_history_source` 的逻辑明确为：只要传入的 `history` 非空，就采用 `HistorySource::Frontend`，引擎内部的 `SessionHistoryCache` 仅在前端历史为空时作为兜底。
  - `apps/agent-workbench/src-tauri/src/run/run_launch.rs:1612-1617`（手动压缩 `/compact`）：同样只调用了 `state.session_history.store(session_id, replaced)`，没有改写 SQLite，也没有向前端同步新消息列表。
- **机制与深层断裂**：
  历史管理割裂为两个互不通信的世界：
  1. **前端与 SQLite 持久化世界**：以 `session_messages` 表为中心，前端是该表的唯一写者（通过 `saveSessionBody`），读路径也依赖该表。
  2. **引擎内核内存世界**：压缩发生后，只更新了内存变量 `state.conversation` 和临时内存缓存 `SessionHistoryCache`。
  因为压缩没有在事件层发出 `MessageEnd`，前端时间线投影机制没有收到任何“生成了一条摘要消息，且前序 N 条消息已归档”的信号；因为压缩没有物理写回 `session_messages`，导致数据库中的会话正文仍然停留在压缩前的初始状态。两层断裂相乘，导致下一次运行必然将已丢弃的消息复活。

### 2.2 BC05-3 根因：压缩代数固定为 1，主键冲突导致后续压缩全部被静默丢弃

- **代码事实定位**：
  - `crates/conex-compaction/src/engine.rs:369`：
    ```rust
    // generation 本轮以 1 占位（R-K：V2 由会话代数 SessionContextMeta.last_compaction_generation 注入）
    let generation: u32 = 1;
    let fold_index = chain_count + 1;
    let block_id = format!("compacted-summary-{generation}-{fold_index}");
    ```
    代数直接写死为常量 `1`。
  - `crates/session-loop/src/loop/compaction_dispatch.rs:506-507`：
    `tracker.apply_external_generation(plan.generation);`，使用写死的 `plan.generation` 反向校准缓存跟踪器，导致缓存跟踪器的代数被反复拨回 `1`。
  - `crates/session-loop/src/loop/compaction_dispatch.rs:515-516`：
    `let block_id = format!("compacted-summary-{}-{}", plan.generation, plan.fold_index);`，块 ID 永远是 `compacted-summary-1-{fold_index}`。
  - `crates/orchestrator/src/session.rs:226`：
    ```rust
    meta.last_compaction_generation = Some(meta.last_compaction_generation.unwrap_or(0) + 1);
    ```
    会话元数据虽然在事件落库时递增代数，但该值从未注入回 `CompactionEngine`。
  - `crates/conex-db/src/blocks.rs:161-196`：
    ```sql
    INSERT OR IGNORE INTO compression_blocks (
        session_id, block_id, ...
    ) VALUES (?1, ?2, ...)
    ```
    `compression_blocks` 的主键为 `(session_id, block_id)`。
  - `crates/orchestrator/src/blocks.rs:125-132`：
    ```rust
    let generation = u64_field("generation")
        .map(|g| g as u32)
        .or_else(|| db.count_compression_events(session_id).ok().map(|c| c as u32))
        .unwrap_or(1);
    ```
    优先使用事件载荷 `details.generation`（该值来自 `plan.generation`，恒为 `1`），兜底的 `count_compression_events` 永远无法执行。
- **机制与深层断裂**：
  当发生跨 Run 压缩时：
  1. 第 1 次压缩（Run 1）：生成块 `compacted-summary-1-1`，成功插入 `compression_blocks`。
  2. 第 2 次压缩（Run 2）：由于 BC05-1 导致 Run 2 读取全文，链消息 `compacted-summary` 不在历史中，`chain_count` 算得 `0`，`fold_index = 0 + 1 = 1`。加上 `generation` 硬编码为 `1`，生成的块 ID **再次成为 `compacted-summary-1-1`**！
  3. `INSERT OR IGNORE` 检查到 `(session_id, "compacted-summary-1-1")` 已存在，**直接静默忽略插入并返回 `Ok(())`**！
  4. 结果：第 2 次压缩的被丢弃消息列表、新的摘要内容、Token 指标在数据库索引中被全盘吞没，块表永远停留在第 1 次压缩的记录上。

### 2.3 BC05-6 根因：提示词要求 criticalContext 为数组，Markdown 投影只认字符串

- **代码事实定位**：
  - `crates/conex-compaction/src/ai_summary.rs:100`：
    ```rust
    out.push_str("- criticalContext：关键上下文数组——精确路径 / 符号 / 命令 / 错误串必须逐字保留，不可改写（可空）\n\n");
    ```
    摘要提示词明确且强制要求模型输出**数组**。
  - `crates/conex-compaction/src/summary_document.rs:20-33`：
    `SUMMARY_REQUIRED_FIELDS` 包含 `"criticalContext"`。
  - `crates/conex-compaction/src/summary_document.rs:89-91`：
    `validate_summary_document` 仅检查了 `droppedIds` 必须为数组，对 `criticalContext` 未做类型校验，模型输出数组时顺利通过校验，标记 `summary_is_llm = true`。
  - `crates/conex-compaction/src/summary_document.rs:95-97` 与 `:241-242`：
    ```rust
    fn string_field<'a>(doc: &'a serde_json::Value, key: &str) -> &'a str {
        doc.get(key).and_then(|v| v.as_str()).unwrap_or("")
    }
    // ...
    out.push_str("\n## Critical Context\n");
    out.push_str(string_field(doc, "criticalContext"));
    ```
    Markdown 渲染函数使用 `string_field` 提取内容，当值为数组时，`v.as_str()` 返回 `None`，最终输出 `""`！
- **机制与深层断裂**：
  提示词契约、数据结构校验契约与渲染契约三者严重脱节：
  - 提示词说：“请给我输出一个数组”。
  - 模型听话输出了 `["error: connection reset", "file: src/main.rs:100"]`。
  - 渲染器却说：“我只认字符串，不是字符串我就当你没给”。
  结果导致生成的 Markdown 摘要中，`## Critical Context` 标题下空无一物。原文已被压缩裁剪丢弃，而保留段中只剩下一个空标题，导致关键错误串、文件路径与重要符号被**静默蒸发**，后续轮次模型失去关键上下文。

### 2.4 BC11-4 根因：压缩块只读契约未注入，search/decompress 工具每调必错

- **代码事实定位**：
  - `crates/session-loop/src/exec_single.rs:424`：
    ```rust
    let tool_ctx = ToolContext {
        // ...
        background: ctx.background.clone(),
        log_root: ctx.log_root.clone(),
        compression_store: None, // <── 写死为 None!
        note_backend: ctx.note_backend.clone(),
        tool_call_id: Some(call.id.clone()),
    };
    ```
    在构造单次工具执行上下文 `ToolContext` 时，`compression_store` 被硬编码写死为 `None`。
  - `crates/agent-tools/src/tools/search_context.rs:92-96` 与 `decompress_context.rs:100-104`：
    ```rust
    let Some(store) = &ctx.compression_store else {
        return Err(ToolError::new(
            codes::COMMON_UNSUPPORTED,
            "compression store 未注入：压缩块检索服务未装配（引擎侧注入 CompressionContextStore 后可用）",
        ));
    };
    ```
    只要字段为 `None`，无条件报错 `common.unsupported`。
  - `crates/agent-tools/src/compression_store.rs:54-72`：
    仅声明了 `CompressionContextStore` trait，全仓库没有任何连接 `conex-db` 的生产实现。
- **机制与深层断裂**：
  `compression_blocks` 表在 `conex-db` 中早已建立且实现了索引存储，工具层的 `search_context` 与 `decompress_context` 也已声明并注册给模型，但执行器链路中缺少组装线，中间没有实现适配器把 `LocalDb` 的块表能力桥接给 `CompressionContextStore`，直接导致模型看到工具有却无法使用。

### 2.5 BC05-2, BC05-4, BC05-5 根因：护栏脱节、附件丢失与滑窗粗暴

- **BC05-2（协调器绕过窗口尝试护栏）**：
  - `crates/session-loop/src/loop/summary_coordinator.rs:159-197`：会话级协调器的 `try_trigger` 仅检查了单飞句柄与全局并发上限 `ACTIVE_SUMMARY_TASKS`，漏掉了 `SummaryRetryGate`。
  - 生产环境 `run_launch.rs:1143` 始终注入会话级协调器，使得 `summary_dispatch.rs` 中设计的 8次/30分钟 低功耗窗口护栏在生产运行中被完全绕过。
- **BC05-4（附件上下文预算函数未接入）**：
  - `crates/session-loop/src/attachment_budget.rs:31` 定义了 `clamp_attachments_to_budget` 并实现了 Head-Tail 二次截断，但该函数只有测试调用。
  - `apps/crish-desktop/src/api/chat-bridge/streamSession.ts:216-218` 发送了 `attachments`，但 `apps/agent-workbench/src-tauri/src/run/run_launch.rs:380-435` 的 `RunTaskOptions` 结构体缺少该字段，反序列化时被直接丢弃；`prepare_turn.rs` 也从未调用附件预算钳制。
- **BC05-5（估算与真实窗口脱节，无早退且一压即砍至 2 万 Token）**：
  - `crates/conex-compaction/src/engine.rs:305-336`：`compact_agent_messages_with_stub_policy` 未检查 `tokens_before <= budget_tokens`，缺乏早退逻辑。
  - 切割点算法 `find_cut_point_inner` 默认保留 20000 Token（`cut_point.rs:11`）。窗口高达 128k 或 200k 时，刚超触发线就被强行砍到 2 万，历史信息损失极其严重。
  - 当窗口极小时（如 16k），`budget_tokens` 被减为 0，紧急收紧逻辑因 `0 < 20000` 而被跳过，导致超窗请求原样放行，随后引发供应商 400 报错。

### 3.2 攻坚重点 1：端到端真实持久化闭环（MessageEnd 与正文重写）

#### 3.2.1 契约重构：压缩摘要作为权威消息发射事件
在压缩执行完毕点位（`compaction_dispatch.rs: apply_compaction`），生成的摘要节点不再只是内存变量中的一个幽灵节点，而是被正式接纳为当前会话的一等公民消息（First-Class AgentMessage）。

- **事件发射顺序**：
  1. 发射 `AgentEvent::ContextCompressionStart`；
  2. 构造摘要消息 `summary_message: Arc<AgentMessage>`：
     - `id`: `block_id`（形如 `compacted-summary-{generation}-{fold}`）；
     - `role`: `AgentMessageRole::Assistant`；
     - `blocks`: `vec![AgentMessageBlock::Text { text: summary_markdown }]`；
     - `metadata`: 注入结构化标识：
       ```json
       {
         "isCompactedSummary": true,
         "summary": {
           "blockId": "compacted-summary-1-1",
           "generation": 1,
           "state": "committed",
           "droppedIds": ["m1", "m2", "m3"]
         }
       }
       ```
     - `content`: `Some(summary_markdown)`。
  3. 通过 `state.emit_event` 发射 `AgentEvent::MessageStart` 与 `AgentEvent::MessageEnd`；
  4. 替换 `state.conversation = plan.messages`；
  5. 发射 `AgentEvent::ContextCompressionEnd`。

#### 3.2.2 数据库物理重写与有界收拢
在 `apply_compaction` 内部，或通过会话收口/压缩钩子（`HookEvent::ContextCompactEnd`），执行底层数据库的原子重写：
- **原子事务**：调用 `LocalDb::rewrite_session_messages_on_compaction(session_id, plan.messages)`：
  1. 将 `plan.messages` 中除 `System` 提示词外的所有有效消息映射为 `SessionMessage` 序列（第 0 项为摘要消息，随后为保留段的原始消息）；
  2. 利用已有的 `save_session_body_conn` 算法：
     - `INSERT ... ON CONFLICT(session_id, seq) DO UPDATE`：覆写前 `N` 个槽位；
     - `DELETE FROM session_messages WHERE session_id = ? AND seq >= N`：物理删除已被压缩移走的旧消息；
     - 更新 `sessions.message_count = N`，并自增 `body_version`。
- **前端实时与持久化对齐**：
  桌面端在接收到带有 `isCompactedSummary: true` 的 `message-end` 事件及 `context-compression-end` 时：
  - 前端事件投影层（`sessionEventProjection.ts`）自动将该消息投影为时间线上的摘要卡片，并标记前序 `droppedIds` 处于折叠隐藏状态；
  - 下一轮 `streamSession.ts` 调用 `loadSessionBody` 时，读取到的已经是只包含摘要卡片与保留段的权威消息集合，彻底根除全文复活。

### 3.3 攻坚重点 2：全局连续递增的压缩代数真相源（SSOT）

#### 3.3.1 消除代数漂移与主键冲突

- **数据契约变更**：
  1. `CompactionPolicy` 与 `CompactionConfig`：增加 `current_generation: u32` 字段。
  2. `CompactionEngine::compact_agent_messages_with_stub_policy`：
     废除内部 `let generation: u32 = 1;`，签名接收 `generation: u32` 参数：

### 3.4 攻坚重点 3：Critical Context 契约对齐与全格式渲染引擎

#### 3.4.1 Schema 校验与宽容解析契约
在 `crates/conex-compaction/src/summary_document.rs` 中：
1. 校验器 `validate_summary_document` 保持对 `criticalContext` 字段的存在性检查，但允许其类型为 `Array` 或 `String` 或 `Object`。
2. 渲染器 `summary_to_markdown` 重构为确定性多态解析：

```rust
/// Critical Context 多态渲染器
fn push_critical_context(out: &mut String, doc: &serde_json::Value) {
    let Some(val) = doc.get("criticalContext") else {
        return;
    };
    match val {
        // 契约正规态：数组形式（逐条渲染为无序列表）
        serde_json::Value::Array(items) => {
            for item in items {
                match item {
                    serde_json::Value::String(s) => {
                        let trimmed = s.trim();
                        if !trimmed.is_empty() {
                            out.push_str("- ");
                            out.push_str(trimmed);
                            out.push('\n');
                        }
                    }
                    serde_json::Value::Object(map) => {
                        // 兼容对象条目：{ "path": "...", "desc": "..." }
                        let mut parts = Vec::new();
                        for (k, v) in map {
                            if let Some(str_val) = v.as_str() {
                                parts.push(format!("{k}: {str_val}"));
                            }
                        }
                        if !parts.is_empty() {
                            out.push_str("- ");
                            out.push_str(&parts.join(", "));
                            out.push('\n');
                        }
                    }
                    _ => {}
                }
            }
        }
        // 兼容态：纯文本字符串
        serde_json::Value::String(s) => {
            let trimmed = s.trim();
            if !trimmed.is_empty() {
                for line in trimmed.lines() {
                    let l = line.trim();
                    if !l.is_empty() {
                        if !l.starts_with('-') && !l.starts_with('*') {
                            out.push_str("- ");
                        }
                        out.push_str(l);
                        out.push('\n');
                    }
                }
            }
        }
        _ => {}
    }
}
```

3. 渲染后的 Markdown 格式保障：
   无论模型返回纯字符串列表、键值对象列表还是紧凑文本，`## Critical Context` 节下方必定逐行呈现精确的原样信息（绝对路径、Git SHA、异常堆栈），绝不丢失字符。

### 3.5 攻坚重点 4：生产级 CompressionContextStore 落地与工具链装配

#### 3.5.1 `DbCompressionContextStore` 生产实现
在 `crates/conex-db/src/compression_store.rs` 实现 `agent_tools::compression_store::CompressionContextStore`：

```rust
use std::sync::Arc;
use agent_tools::compression_store::{BlockContent, BlockHit, CompressionContextStore};
use crate::{DbFailure, LocalDb};

#[derive(Debug, Clone)]
pub struct DbCompressionContextStore {
    db: Arc<LocalDb>,
}

impl DbCompressionContextStore {
    pub fn new(db: Arc<LocalDb>) -> Self {
        Self { db }
    }
}

impl CompressionContextStore for DbCompressionContextStore {
    fn search_blocks(
        &self,
        session_id: &str,
        query: &str,
        limit: usize,
    ) -> Result<Vec<BlockHit>, String> {
        let rows = self.db.search_compression_blocks(session_id, query, limit)
            .map_err(|e| format!("search_blocks db failure: {e}"))?;
            
        Ok(rows.into_iter().map(|r| BlockHit {
            block_id: r.block_id,
            generation: r.generation,
            height: r.height,
            summary: r.summary,
            dropped_count: r.dropped_message_ids.len(),
            state: r.state.as_str().to_string(),
        }).collect())
    }

    fn decompress_block(
        &self,
        session_id: &str,
        block_id: &str,
    ) -> Result<Option<BlockContent>, String> {
        let Some(block) = self.db.get_block(session_id, block_id)
            .map_err(|e| format!("get_block failure: {e}"))? else {
            return Ok(None);
        };

        if block.dropped_message_ids.is_empty() {
            return Ok(Some(BlockContent {
                block_id: block_id.to_string(),
                text: block.summary,
            }));
        }

        // 事件流回放重组原文（无损原始字节）
        let raw_text = self.db.reconstruct_dropped_messages_text(session_id, &block.dropped_message_ids)
            .map_err(|e| format!("reconstruct messages failure: {e}"))?;

        Ok(Some(BlockContent {
            block_id: block_id.to_string(),
            text: raw_text,
        }))
    }
}
```
