### 1. BC08-1：Gemini 请求打到一次性 `:generateContent`，回答被 SSE 分帧静默吞没

- **代码位置**：
  - `apps/agent-workbench/src-tauri/src/engine_provider/protocol.rs:432-436`（Gemini 请求 URL 固定拼装为 `{base}/models/{model}:generateContent`）；
  - `apps/agent-workbench/src-tauri/src/engine_provider.rs:567`（HTTP 200 成功响应无视 Content-Type，一律送入 `stream_frames(response, read_options, abort_handle)`）；
  - `crates/agent-provider/src/request/build_gemini.rs:75-136`（请求体完全不带 `stream` 字段，且端点名不是流式端点）；
  - `crates/agent-provider/src/sse/frame.rs:247-264`（`parse_frame_body` 仅收集 `data:` 行，整段 JSON 导致 `data_lines` 为空返回 `Ok(None)`）；
  - `crates/agent-provider/src/sse/frame.rs:116-126`（EOF 残留解析后仍无 SSE 数据帧）；
  - `crates/agent-provider/src/parse/gemini_core.rs:247-256`（`finish()` 判定 `!self.emitted_content && !self.saw_terminal`，报空流错误 Stop）；
  - `apps/agent-workbench/src-tauri/src/engine_provider_tests.rs:214-218`（错误地将 `:generateContent` 作为单测硬断言锁定）。
- **根因穿透**：
  - **端点契约漂移**：Google Gemini REST API 官方规范明确规定，流式请求端点必须为 `:streamGenerateContent?alt=sse`；而非流式整段响应端点为 `:generateContent`。代码在流式接口 `HttpProviderCall::stream` 中错误使用了非流式端点。
  - **传输分帧层假设单一化**：`stream_frames` 强制将所有响应当成 SSE 流（`text/event-stream`）处理。当服务端按 `:generateContent` 契约返回 `Content-Type: application/json` 整段文档时，分帧器找不到 `data:` 前缀，解析器产出 0 个事件，在 EOF 时误判为“未收到任何内容事件即结束”的空流错误，模型回答、思考、工具调用与 usage 彻底丢失。

### 2. BC08-5：Anthropic 丢弃消息里的 System 角色，中途转向纠偏被静默丢弃

- **代码位置**：
  - `crates/session-loop/src/steering/nudge.rs:98-114`（运行时构建的转向消息角色为 `AgentMessageRole::System`，挂载在 `context.messages` 列表中）；
  - `crates/agent-provider/src/request/build_anthropic.rs:507-509`（`to_anthropic_messages` 处理到 `AgentMessageRole::System` 时直接 `{}` 空操作跳过）；

### 3. BC08-6：Gemini 将「指定某工具」降级为 ANY 任意工具且丢失调用 ID

- **代码位置**：
  - `crates/agent-provider/src/request/build_gemini.rs:526-536`（`ToolChoice::Function { .. }` 与 `ToolChoice::Required` 一律映射为 `"ANY"`，完全没有输出 `allowedFunctionNames`）；
  - `crates/agent-provider/src/request/build_gemini.rs:373-386`（助手历史 `AgentMessageBlock::ToolCall` 序列化为 `functionCall` 时，仅包含 `name` 和 `args`，完全丢弃 `call.id`）；
  - `crates/agent-provider/src/request/build_gemini.rs:418-425`（工具响应 `AgentMessageBlock::ToolResult` 序列化为 `functionResponse` 时，丢弃 `tool_call_id`）；
  - `crates/agent-provider/src/parse/gemini_core.rs:196-198`（解析时若服务端未回传 id，直接合成 `gemini_fc_{count}`，与历史消息中的真实 id 脱节）。
- **根因穿透**：
  - **模式降级与白名单丢失**：Gemini 规范中，强制调用指定函数必须使用 `{ mode: "ANY", allowedFunctionNames: ["tool_name"] }`。构建器直接丢掉了白名单，导致模型收到的是“必须调用某个函数”，而非“必须调用这一个”，模型可随意换调其他工具。
  - **ID 全生命周期断裂**：Gemini 2.0+ 与规范 API 已原生支持 `functionCall.id` 与 `functionResponse.id`。构建层因历史旧代际假设而丢弃 ID，迫使下游配对只能按函数名加顺序计数猜测；一旦同名工具多次并发调用或重试交替，响应结果发生致命错配。

### 4. BC02-2：已有增量后再失败被伪装成成功 Stop，导致截断工具照样执行

- **代码位置**：
  - `crates/session-loop/src/stream.rs:205-216`（`ConsumeStopReason` 枚举仅有 `Stop`, `ToolCall`, `Length`, `Aborted` 四种，**根本没有 `Error` 变体**）；
  - `crates/session-loop/src/stream.rs:435-445`（`has_content` 为 true 时，即便原始终止原因为 `StopReason::Error`，只要 `tool_calls` 非空就强制改为 `ToolCall`，否则一律落入 `ConsumeStopReason::Stop`）；
  - `crates/session-loop/src/loop/handlers/streaming.rs:185-199`（流中读取 `Err(classified)` 时，若已有内容则合成一条 `Stop { reason: Error, usage: None }` 并退出消费循环）；
  - `crates/session-loop/src/loop/handlers/streaming.rs:284-330`（只对 abort 做了工具中断合成；当 stop reason 为 `ToolCall` 或 `Stop` 时，无条件 `commit_message_with_deltas`，随后进入 `HasToolCalls` 派发真实工具执行，或调用 `no_tool_calls::handle` 正常收工）；
  - `crates/session-loop/src/stream.rs:622-640` 与 `:1112-1131`（单测 `text_then_error_stop_yields_message` 和 `thought_with_error_stop_yields_message` 竟将“有内容 + 错误 Stop $\to$ 成功 Stop”锁为行为契约）。
- **根因穿透**：
  - **虚假的成功兜底**：设计者误将“保留部分文本以便用户查看（Partial Salvage）”等同于“将整个回合当成成功完成”。当模型吐出 5 个字或生成了半截 `tool-call` 参数后连接断开或被服务端 500 截断时，系统不仅伪造成功，更致命的是将截断、未校验的脏工具调用直接派发给操作系统的命令执行器或文件系统，引发灾难性的系统副作用。

### 5. BC02-1 与 BC02-3：无正文错误被折叠为 Unknown fatal，429/超时脱离退避阶梯

- **代码位置**：
  - `crates/session-loop/src/stream.rs:427-432`（无内容且有 error 时，直接调用 `classify_stream_error(&message)`，完全丢弃 `aggregate.error_kind`）；
  - `crates/session-loop/src/stream.rs:606-613`（`classify_stream_error` 硬编码 `ProviderErrorKind::Unknown`、`retryable: false`、`retry_after_ms: None`）；
  - `crates/session-loop/src/stream.rs:397-399`（`ConsumeBuilder::is_empty` 判定条件为 `self.pushed == 0`）；
  - `crates/session-loop/src/loop/handlers/streaming.rs:185-188`（只有 `builder.is_empty()` 才能保留原始 `ClassifiedStreamError`）；
  - `apps/agent-workbench/src-tauri/src/engine_provider.rs:560-566`（开启诊断，首块字节先发射 `StreamFrameEvent::Diagnostic(SseFirstByte)`，导致 `builder.pushed` 变为 1）；
  - `crates/session-loop/src/loop/handlers/stream_error.rs:70-86`（分派逻辑明确：只有 RateLimit/ServerError/Timeout/Network 进重试，Unknown 直接 fatal）。
- **根因穿透**：
  - **分类抹除胶水层**：服务端通过合法错误帧回传的 429 RateLimit 或 503 ServerError（已带有精确 `error_kind` 与 Retry-After），在消费层被 `classify_stream_error` 无差别清洗为 `Unknown` 且不可重试，直接阻断退避阶梯。
  - **诊断事件污染判空逻辑**：`is_empty` 检查事件总数而非有效载荷。首字节网络诊断事件导致 `pushed > 0`，随后的网络断开或超时被判定为“流已产出”，转入合成 Stop 路径，再次被折叠为 `Unknown`，导致线上最常见的“刚连上就超时”百分之百直接崩溃。

### 6. 其他关联缺陷穿透（BC08 与 BC02 深度关联）

- **BC08-2（流中途错误不收尾丢失工具与 usage）**：`apps/agent-workbench/src-tauri/src/engine_provider/stream.rs:129-138` 在读取错误或坏帧时直接 `finished = true` 返回 `Err`，不调用 `parser.finish()`。解析器内部累计的工具增量与用法统计被彻底丢弃。

## 二、重构原则与全景架构设计

### 1. 核心设计原则

1. **绝对杜绝补丁式修补**：严禁在 `classify_stream_error` 里增加 `if kind == ...` 的魔术补丁，必须从根源彻底打通传输、分帧、解析、聚合与消费五层数据通路；
2. **非必要不兼容**：物理拔除将 `Error` 伪装成 `Stop`、将错误折叠为 `Unknown`、将指定工具降级为 `ANY` 的所有伪兼容代码与错误单测，违背正确性契约的历史断言全部重写；
3. **真实协议全保真**：出站请求严格对齐供应商官方标准（Gemini 流式端点、Anthropic 转向时序、工具 choice 精确限定、ID 全生命周期追踪）；
4. **强隔离与安全第一**：流式过程中一旦检测到致命错误或截断，已产生的未决工具调用一律物理阻断，绝不允许脏调用出舱执行；
5. **立体验证纪律**：拒绝脱水 Mock 糊弄，必须在端到端与极端真实故障下履行立体化验证。

### 2. 全景重构架构图

## 三、五大核心攻坚重点详案与数据契约

### 1. 彻底根治 Gemini 请求打到一次性 `:generateContent` 被吞没（BC08-1）

#### 1.1 端点规范化拼装（URL 侧单一真源）

在 `apps/agent-workbench/src-tauri/src/engine_provider/protocol.rs` 中重构 `provider_url_for`：

```rust
pub(crate) fn provider_url_for(
    config: &EngineProviderConfig,
    protocol: WireProtocol,
    is_streaming: bool,
) -> String {
    let base = build_endpoint_url(protocol.protocol_kind(), &config.base_url);
    match protocol {
        WireProtocol::Gemini => {
            let action = if is_streaming {
                "streamGenerateContent?alt=sse"
            } else {
                "generateContent"
            };
            if base.contains('?') {
                // 若基址已携带 query 参数（如 API Key 代理网关），安全拼接
                format!("{base}/models/{}:{action}&alt=sse", config.model)
            } else {
                format!("{base}/models/{}:{action}", config.model)
            }
        }
        _ => base,
    }
}
```

- **契约保证**：在 `HttpProviderCall::stream` 发起调用时，`is_streaming` 恒为 `true`，请求准确打向 Google 官方 SSE 端点；在历史非流式或探测路径下，使用 `generateContent`。

#### 1.2 响应管道双模自适应（Dual-Mode Transport Adapter）

在 `crates/agent-provider/src/transport/mod.rs` 与 `apps/agent-workbench/src-tauri/src/engine_provider.rs` 中拔除“只要 200 OK 就无脑按 SSE 读”的错误逻辑，引入响应类型自适应管道：

```rust
pub enum ResponseTransportStream {
    /// 真实 SSE 流（Content-Type: text/event-stream 或分块 chunked SSE）
    Sse(Pin<Box<dyn Stream<Item = Result<StreamFrameEvent, SseReadError<reqwest::Error>>> + Send>>),
    /// 单帧整段 JSON 响应（Content-Type: application/json 或代理网关一次性响应）
    SingleFrameJson(Option<StreamFrameEvent>),
}
```

- **实现机制**：
  1. 检查 HTTP 响应头 `Content-Type`：
     - 若包含 `application/json`（或非 `text/event-stream` 且 `content-length` 明确）：启动整段读取通道，异步读取 `response.text().await`；
     - 构造成单帧 `StreamFrameEvent::Frame(SseFrame { data: Some(full_json_body), .. })`；
     - 包装为单次产出的 Stream，交付给下层 `http_stream_next`。
  2. 若包含 `text/event-stream`：交付给标准 `stream_frames` 执行增量 SSE 读取。
  3. **容错机制**：如果请求打到 `:generateContent` 或兼容代理将流式压平为整段 JSON，该自适应管道均能将完整的 JSON 交付给 `GeminiParser`。

#### 1.3 `GeminiParser` 整段与增量解析同轨

`GeminiParser::push_frame` 现已具备解析完整 `candidates[].content.parts[]` 与 `usageMetadata` 的能力。在单帧模式下：
1. `push_frame(&full_json_frame)` 立即解出全部 `TextDelta`、`ThoughtDelta`、`ToolCall`；
2. 随后流自然结束，触发 `parser.finish()`；
3. `saw_terminal` 被正确置为 true，`finish()` 产出携带完整 usage 的 `Stop { reason: StopReason::Stop }` 事件；
4. 彻底终结“Gemini 流空响应：未收到任何内容事件即结束”的历史假崩溃。

### 2. 修复 Anthropic 请求跳过 System 角色导致转向丢失（BC08-5）

#### 2.1 架构原理与 Anthropic 协议约束

- Anthropic Messages API 的核心约束：
  1. 顶层 `system` 参数：支持单个纯文本字符串，或结构化内容块数组 `[ { "type": "text", "text": "...", "cache_control": ... } ]`；
  2. `messages` 数组：角色**仅且必须**为 `user` 与 `assistant`，且必须交替出现，绝不允许 `system` 角色直接出现在 `messages` 数组中。

#### 2.2 双轨保真投影设计

为了既不违反 Anthropic API 校验（杜绝 400 报错），又能让模型在确切的时序位置感知中途转向（Steering），采取**双轨系统时序投影机制**：

```rust
// 位于 crates/agent-provider/src/request/build_anthropic.rs

/// 1. 顶层 system 字段组装：汇聚全局静态 system_prompt 与前置全局系统消息
fn build_anthropic_system_blocks(
    context: &RequestBuildContext,
    bp_plan: &BreakpointPlan,
) -> Option<Value> {
    let mut blocks: Vec<Value> = Vec::new();

    // (a) 全局系统提示词
    if let Some(prompt) = context.system_prompt.as_deref().map(str::trim).filter(|s| !s.is_empty()) {
        let mut obj = json!({ "type": "text", "text": prompt });
        if bp_plan.system {
            obj["cache_control"] = json!({ "type": "ephemeral" });
        }
        blocks.push(obj);
    }

    if blocks.is_empty() {
        None
    } else {
        Some(Value::Array(blocks))
    }
}

/// 2. 消息序列保真投影：将中途注入的 System / Steering 消息投射为保时序的 user 指令块
fn to_anthropic_messages(
    context: &RequestBuildContext,
    bp_plan: &BreakpointPlan,
) -> Vec<Value> {
    let mut result: Vec<Value> = Vec::new();

    for message in context.messages {
        let msg = message.borrow_message();
        match msg.role {
            AgentMessageRole::User => {
                let content = user_anthropic_content(msg);
                push_alternating(&mut result, &json!({ "role": "user", "content": content }));
            }
            AgentMessageRole::Assistant => {
                let content = assistant_anthropic_content(msg);
                push_alternating(&mut result, &json!({ "role": "assistant", "content": content }));
            }
            AgentMessageRole::Tool => {
                let content = tool_result_anthropic_content(msg);
                push_alternating(&mut result, &json!({ "role": "user", "content": content }));
            }
            AgentMessageRole::System => {
                // 【核心攻坚修复】：中途注入的运行时转向/系统纠偏绝不丢弃！
                // 投射为带有严格上下文标识的 user 提示，经 push_alternating 与前后上下文融合
                let text = msg.text();
                if !text.trim().is_empty() {
                    let wrapped_steering = json!({
                        "type": "text",
                        "text": format!("[System Directive / Runtime Steering]\n{}", text.trim())
                    });
                    push_alternating(
                        &mut result,
                        &json!({ "role": "user", "content": [wrapped_steering] }),
                    );
                }
            }
        }
    }
    result
}
```

- **时序保真收益**：
  - 会话中途由 `session-loop` 触发的 `build_steering_message(reason, count)`，被以明确的系统指令标签挂载在对话历史的当前位置；
  - 依赖 `push_alternating` 的内置机制：若前面紧邻的是工具响应（user 块），则将该转向内容无缝追加到该 user 消息的 `content` 数组末尾；若前面是 assistant 消息，则作为新的 user 轮次注入；
  - 既完全合规 Anthropic 严格的交替协议，又彻底杜绝转向丢失，模型在下一次推理时 100% 能够感知并执行纠偏指令。

按照立体验证纪律，本方案设计了覆盖静态契约、纯逻辑单元测试、协议边界及现场真实调用的立体测试矩阵。

### 1. 核心纯逻辑单元测试（Unit Verification）

- **TC-GEMINI-URL-01：Gemini 流式端点与参数拼接测试**
  - **输入**：`EngineProviderConfig` 配置 Gemini 模型 `gemini-2.5-pro`，分别请求流式与非流式 URL。
  - **断言**：流式 URL 必须精确匹配 `https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-pro:streamGenerateContent?alt=sse`；非流式 URL 匹配 `:generateContent`；带代理 Query 参数时 `&alt=sse` 语法合法。
- **TC-GEMINI-JSON-02：整段 JSON 响应自适应消费测试**
  - **输入**：模拟服务端返回 `Content-Type: application/json` 的整段 JSON 文档（含 `candidates`、`content.parts` 与 `usageMetadata`）。
  - **断言**：流式自适应管道产出单帧；`GeminiParser` 产出完整的 `TextDelta`、`ThoughtDelta`、`ToolCall`；`finish()` 产出携带完整 usage 的 `Stop`；消费层成功收下完整回复，零丢回答。
- **TC-ANTHROPIC-STEER-01：运行时 Steering 消息时序保真投射测试**
  - **输入**：对话上下文包含 `[User, Assistant, ToolResult, Steering(Nudge)]`。
  - **断言**：构建出的 Anthropic wire messages 角色严格保持 `user/assistant` 交替；Steering 消息作为带 `[System Directive / Runtime Steering]` 标签的内容块挂载在最后的 `user` 块中；顶层 `system` 字段仅包含全局提示词；上游校验 100% 通过。
- **TC-GEMINI-TOOL-01：指定工具 Choice 与 ID 保全测试**
  - **输入**：构建指定工具 `ToolChoice::Function { name: "execute_sql".into() }`，并提供带 id 的历史工具调用。
  - **断言**：`toolConfig.functionCallingConfig.mode` 为 `"ANY"`，`allowedFunctionNames` 严格包含 `["execute_sql"]`；出站 `functionCall` 与 `functionResponse` 中的 `id` 完整保留无缺失。
- **TC-STREAM-ISOLATE-01：有增量后错误强隔离与工具熔断测试**
  - **输入**：流式事件序列依次推入 `TextDelta("部分回答")`、`ToolCall { tool_name: "rm_rf" }`、`Stop { reason: Error, error_kind: Timeout }`。
  - **断言**：`consumed.stop_reason()` 严格为 `Some(ConsumeStopReason::Error)`；`streaming.rs` 捕获该错误并立即调用 `synthesize_and_record_interrupted_calls`；该 `rm_rf` 工具调用**绝对未被派发执行**；状态机转入错误终止。
- **TC-STREAM-RETRY-01：首字节诊断后 429 顺畅进入退避阶梯测试**
  - **输入**：流式连接先推入 `ProviderDiagnostic(SseFirstByte)`，随后底层网络断开报错 `ClassifiedStreamError { kind: RateLimit, retry_after_ms: 2000 }`。
  - **断言**：`has_salvageable_content()` 返回 false；原始 `RateLimit` 错误无损保留；成功触发 `transient_retry`，消费 2000ms 等待，未被折叠为 Unknown fatal。

### 2. 极端边界与竞态测试（Boundary & Race Verification）

- **TC-RACE-SSE-01：坏帧与多段 JSON 粘连截断容错**
  - **输入**：同一块数据包含 `data: {"valid": 1}\n\r\ndata: {bad json}\n\n`。
  - **断言**：`split_frames` 优先将有效帧切出并交由上游消费，不因后续坏帧导致前面已就绪的帧被清空丢弃。
- **TC-RACE-ABORT-01：流式消费与用户强停竞争**
  - **输入**：模型正在高速吐出正文与工具调用，用户突然触发 `AbortSignal::abort()`。
  - **断言**：消费循环立即 break，工具调用被安全标记为 `TOOL_ABORTED_BEFORE_DISPATCH`，正文按 partial salvage 留存，状态机稳定收敛为 Aborted。

### 3. 端到端现场真实场景验收（E2E Field Verification）

- **SCENARIO-E2E-01：Gemini 真实多轮对话与流式回答验收**
  1. 配置 Google Gemini 官方 API Key；
  2. 发送一个需要长篇思考与代码编写的复杂提示词；
  3. **验收标准**：
     - 请求准确打向 `:streamGenerateContent?alt=sse`；
     - 桌面端平滑展示实时打字机流式增量；
     - 思考块与代码块清晰分离，usage 准确记录，最终回合完整展示。
- **SCENARIO-E2E-02：Anthropic 运行时死循环纠偏验收**
  1. 使用 Claude 模型执行可能引发连续工具重试的任务；
  2. `session-loop` 触发 `build_steering_message`；
  3. **验收标准**：
     - Claude 在随后的请求中完整接收到了投射的转向消息；
     - 模型立即改变行为模式退出死循环，界面无任何 400 协议报错。
- **SCENARIO-E2E-03：真实网络断开现场工具阻断验收**
  1. 发起一个调用关键写工具（如修改本地文件）的请求；
  2. 在模型正文吐出一半且工具入参刚刚开始传输时，拔掉网络或终止 mock 服务；
  3. **验收标准**：
     - 系统坚决停止，界面显示错误收场（而非假成功）；
     - 本地文件**绝对未被修改**，截断的工具调用被拦截记录在审计日志中。
