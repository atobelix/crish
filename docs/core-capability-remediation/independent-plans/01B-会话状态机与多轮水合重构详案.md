# 会话状态机与多轮水合重构详案（B轨：状态机对称性、协议单轨化与并发安全）

> **方案标识**：01B（核心能力系统性整改战役 · 方向一 B轨独立方案）  
> **设计视角**：状态机转移对称性、多轮历史消息契约解耦、单轨全保真协议与高并发安全  
> **基线对齐**：`docs/backend-core-capability/analysis/01-会话状态机与回合主路径.md`  
> **核心原则**：坚决杜绝补丁式修补，做对的事情，架构净收敛；非必要不兼容，无用胶水代码物理拔除。

## 一、现状与根因穿透（Deep-Dive Root Causes & Code Path Mapping）

通过穿透阅读 `session-loop`、`conex-types`、`agent-workbench` 壳层与桌面端桥接源码，当前核心会话状态机与多轮水合机制存在多处深层断裂与设计违例，具体现状与根因如下：

### 1.1 循环重进绕过 TurnComplete 导致 TurnStart/TurnEnd 不对称与 Token Usage 丢失 (BC01-1)
- **现象**：同一次 `run` 中，因长度升级（`length-escalation`）、空响应继续（`empty-response continue`）、工具批后排队输入（`has_runnable_pending`）、转向评估完成（`SteeringComplete`）或流错误恢复而重新进入准备回合时，系统会发射新的 `TurnStart`，但前一轮的 `TurnEnd` 永远不会发射；前一轮已记录的 Token 用量（`turn_usage`）在准备回合入口被直接抹杀。
- **精准代码路径**：
  - `crates/session-loop/src/loop/handlers/prepare_turn.rs:66-80`：无条件计算 `turn_index.saturating_add(1)` 并发射 `AgentEvent::TurnStart`，随后直接将 `state.budget_state.turn_usage = None`，并用新下标覆写 `state.current_turn_index = Some(turn_index)`。此处没有调用 `emit_missing_turn_end`。
  - `crates/session-loop/src/loop/handlers/no_tool_calls.rs:64, 71, 119`：遇到长度阶梯或 Tool-Promise 恢复时，直接 `dispatch(state, E::NoProgressContinue)`。
  - `crates/session-loop/src/loop/handlers/executing_tools.rs:155-159`：工具批完成后，若队列中有待处理输入，直接 `dispatch(state, E::InputAvailable)`。
  - `crates/session-loop/src/loop/handlers/steering_evaluation.rs:39-41, 90`：转向注入完成或预注入短路，直接 `dispatch(state, E::SteeringComplete)`。
  - `crates/conex-types/src/transition.rs:140, 151, 163`：上述事件在转移表中均直接转移回 `PreparingTurn`，状态机缺乏显式的“回合收口闭环”。
- **架构断裂根因**：状态机混淆了“同一回合内的模型重试（Retry/Escalation）”与“开启新回合（New Turn）”。如果开启新回合，必须经过 `TurnComplete` 闭合前一回合并结算 Usage；如果属于当前回合内的重试，则不应发射新的 `TurnStart`。当前实现两头落空，既发射了新的 `TurnStart`，又跳过了 `TurnEnd`，破坏了 `TurnStart`/`TurnEnd` 严格 1:1 成对发射的不变量。

### 1.2 安全点 check_control 盲目补发伪 TurnEnd 与软注入双重终态、强停工具结果越界 (BC01-2)
- **现象**：流式传输结束、工具批执行前后与回合收口处，只要安全点检测到控制动作，就会先发一条 `usage: None` 的虚假 `TurnEnd`。如果是 `SoftInject`（软注入），循环并未终止，后续正常走完 `turn_complete` 时会再次发射第二条携带真实 Usage 的 `TurnEnd`（单回合双终态）。当在 `ExecutingTools` 入口触发 L3 强停时，虚假 `TurnEnd` 先发出，随后合成的中断工具消息才落库，导致工具结果脱离回合生命周期。
- **精准代码路径**：
  - `crates/session-loop/src/loop/handlers/mod.rs:537-540`：`check_control` 在匹配具体动作之前，无条件调用 `emit_missing_turn_end(state)`。
  - `crates/session-loop/src/loop/handlers/mod.rs:467-477`：`emit_missing_turn_end` 中将 `TurnEnd.usage` 硬编码为 `None`，完全忽视 `budget_state.turn_usage` 中可能已存在的提供商真实用量。
  - `crates/session-loop/src/loop/handlers/mod.rs:558-569`：`SoftInject` 仅把消息入队并返回 `Ok(None)`（表示继续执行），造成下游 `turn_complete.rs:35-55` 再次发射 `TurnEnd`。
  - `crates/session-loop/src/loop/handlers/executing_tools.rs:49-62`：`check_control` 提前发射 `TurnEnd`，随后 `synthesize_and_record_interrupted_calls` 才将合成的 Tool 结果追加进 `conversation`。
- **架构断裂根因**：控制意图与状态机转移解耦失准。`check_control` 错误地将“检查控制意图”等同于“当前回合立即中断退出”。`SoftInject` 本质是无害的异步消息注入，根本不是终止信号；而强停情况下的工具合成属于当前回合的清理动作，因果时序必须发生在发射 `TurnEnd` 之前。

### 1.3 TurnComplete.InputAvailable 误重置 turn_index 导致同 Run 助手正文覆盖 (BC01-3)
- **现象**：当纯文本回复回合结束且队列中有 follow-up 消息或排队输入时，循环继续执行下一轮输入，但状态机将 `turn_index` 归零。下一回合 `PreparingTurn` 发出的 `TurnStart` 下标再次为 `0 + 1 = 1`。前端桌面在处理助手消息收口时以 `turnIndex` 作为分段键，同一下标导致第二轮助手的正文直接覆写第一轮正文，历史内容丢失。
- **精准代码路径**：
  - `crates/session-loop/src/loop/handlers/turn_complete.rs:187-200`：无工具调用且有可用输入时，触发 `dispatch(state, E::InputAvailable)`。
  - `crates/conex-types/src/transition.rs:172-177` 与 `crates/session-loop/src/state.rs:91-95`：`TurnComplete + InputAvailable` 的上下文 effect 包含 `reset_all_counters: true`，硬编码将 `self.context.turn_index = 0`。
  - `apps/crish-desktop/src/api/chat-bridge/handlers/messageHandlers.ts:186-193`：前端直接使用 `state.turnAuthoritativeTexts.set(turnIndex, piece)` 与 `segs[turnIndex] = piece`，为绝对覆盖写。
  - `apps/crish-desktop/src/api/chat-bridge/eventDedupe.ts:123-152`：无序号时去重键退化为 `turn-start:m:turn-N`，第二轮的 `turn-start` 被当作重复事件丢弃。
- **架构断裂根因**：状态机转移设计混淆了“跨会话冷启动/全新 Run 的计数器复位”与“同一 Run 内后续回合的流转推进”。`AgentSessionLoop` 单次运行生命周期内，`turn_index` 必须具备严格单调自增语义，任何在 Run 执行中间将回合计数器清零的行为都是逻辑错误。

### 1.4 历史水合盲目截断最后一个 User 导致上一轮 Assistant 答复湮灭 (BC01-4)
- **现象**：在桌面端发起第二轮及后续对话时，前端调用 `buildHistoryMessages(body, { excludeId: userClientMessageId })` 排除了当前正在发送的新用户消息，因此传入的历史以“上一轮 Assistant 回复”结尾。然而后端的 `hydrate_history` 强行执行 `truncate_to_last_user`，直接将尾部的 Assistant 消息连同其工具调用完全裁掉。新用户消息在进循环后追加，导致送给大模型的上下文变成了 `[..., User(N-1), User(N)]`，上一轮 Assistant 的回答在模型眼中从未存在过。
- **精准代码路径**：
  - `apps/crish-desktop/src/api/chat-bridge/streamSession.ts:177`：显式传入 `excludeId: userClientMessageId`，确保历史载荷只包含已完成的历史。
  - `crates/session-loop/src/hydrate.rs:323-330`：`truncate_to_last_user` 扫描最后一个 `AgentMessageRole::User`，执行 `messages.truncate(last_user + 1)`，直接将尾部所有的 Assistant、ToolResult 截断抛弃。
  - `crates/session-loop/src/hydrate.rs:424-426`：注释妄称“截断只约束纯历史形态... run 还会追加新用户消息”，与调用端传入排除新消息后的历史事实完全冲突。
- **架构断裂根因**：对“对话进模型的协议合法性”与“历史快照水合边界”产生了严重概念混淆。发送给模型的完整对话在追加当前输入后确实必须以 User 结尾，但“前置已完成历史”天然应当以 Assistant 或其配对的 Tool 结果结尾。在历史装配入口对前序历史做向后截断，导致多轮上下文发生致命截断性失忆。

### 1.5 工具真实输出在 toolCalls.output 被丢弃并篡改为 TOOL_OUTCOME_UNKNOWN (BC01-5)
- **现象**：前端在工具执行成功后，将真实输出保存在 `toolCalls[].output` 字段上，并不填充 `toolCallResults`。当多轮对话水合时，Rust 侧通过简陋的 `LegacyToolCall` 结构反序列化，该结构仅声明了 `id/name/arguments`，导致 `output` 被 serde 彻底丢弃；同时由于 `tool_call_results_json` 为空，水合出口处的自愈逻辑 `repair_orphan_tool_calls` 将这些工具调用判定为孤儿，强行合成错误码为 `TOOL_OUTCOME_UNKNOWN`、`is_error: true` 的虚假 Tool 消息，向模型投毒。
- **精准代码路径**：
  - `apps/crish-desktop/src/hooks/agentStreamCallbacks.ts:175-194`：`onToolSuccess` 更新 `tc.status = 'success'` 与 `tc.output = displayOut || output`，从未写入 `toolCallResults`。
  - `apps/crish-desktop/src/api/chat-bridge/historyMessages.ts:147-150`：仅当 `msg.toolCallResults` 存在时才序列化 `tool_call_results_json`。
  - `crates/session-loop/src/hydrate.rs:194-203`：`LegacyToolCall` 仅包含 `id`, `name`, `arguments`，完全无视 `output` 和 `status`。
  - `crates/session-loop/src/hydrate.rs:360-392`：由于未解析出对应结果，生成合成消息，输出固定文案 `"outcome unknown after history hydration: TOOL_OUTCOME_UNKNOWN"`，并将 `is_error` 置为 `true`。
- **架构断裂根因**：双轨数据契约与假想协议模型漂移。生产端真实数据流已经演进为“工具调用与输出同在 `MessageToolCall` 闭环”，水合代码却依然死守一套脱节的遗留双表假设，并在发现不匹配时不提取可用字段，反而粗暴覆写为错误状态。

### 1.6 AgentMessageBlock 缺失 Image 变体导致多模态时间线结构全损 (BC01-6)
- **现象**：用户在历史多轮中发送的图片、或时间线交错块在经过多轮水合后，图片直接丢失，块结构反序列化失败回退为纯文本。
- **精准代码路径**：
  - `crates/conex-types/src/message.rs:136-157`：`AgentMessageBlock` 的 tagged enum 仅支持 `text` / `thought` / `tool-call` / `tool-result`，根本没有 `image` 变体。
  - `crates/session-loop/src/hydrate.rs:130-143`：反序列化前端时间线块（带有 `type: 'image'` 或 snake_case 标签）必然失败，触发降级警告并回退到 `synthesize_blocks`，图片数据被无情丢弃。
- **架构断裂根因**：多模态契约断层。后端核心类型库未将多模态图片视为一等公民内容块，未建立统一的跨端 Block 映射标准。

### 1.7 瞬时相位协作停止空转导致附带消息永久丢弃 (BC01-7)
- **现象**：在 `PreparingTurn` 或 `SteeringEvaluation` 期间触发协同停止（`CooperativeStop`）时，`drive_machine_to_stop` 留空不推进状态机，但外围却将附带的纠偏消息放进内存的 `input_queue` 并宣告 `stopped`。由于桌面壳层每次 `run` 均重建 `AgentSessionLoop` 实例，这些内存消息随实例销毁而彻底消失。
- **精准代码路径**：
  - `crates/session-loop/src/loop/handlers/mod.rs:436-451`：针对 `PreparingTurn | SteeringEvaluation` 为空分支 `{}`。
  - `crates/session-loop/src/loop/handlers/mod.rs:551-556`：直接返回 `Some(EndDecision::stopped(state))`。
- **架构断裂根因**：状态机终态收敛不闭环，且将持久化的控制消息寄托在临时生命周期的内存输入队列中。

### 1.8 pending_inputs 无序并发双写导致已消费用户消息幽灵复活 (BC01-8)
- **现象**：消息入队时异步调用 `spawn_pending_input_save`（执行 `INSERT OR REPLACE`），消息消费时异步调用 `delete_pending_input`（执行 `DELETE`）。由于均为独立的非阻塞 Tokio Task，当删除操作先完成、保存操作后完成时，已被消费的用户消息被重新写回数据库，导致软件重启后重复回放已回答的问题。
- **精准代码路径**：
  - `crates/session-loop/src/loop/loop_runner.rs:343-367`：使用 `tokio::spawn` 异步写入。
  - `crates/session-loop/src/loop/handlers/mod.rs:252-267`：使用 `tokio::spawn` 异步删除，两次并发调用互无顺序屏障与版本锁。
- **架构断裂根因**：异步 I/O 缺乏因果依赖与原子序约束，盲目使用 fire-and-forget 协程替代有序持久化状态机。

### 2.1 统一单轨全保真消息与工具协议（Single-Track Protocol）

彻底拔除 `LegacyToolCall` 与 `LegacyToolCallResult`，消除前端与后端之间由命名风格（kebab-case vs camelCase vs snake_case）和字段割裂导致的信息丢失。

#### 2.1.1 核心数据结构定义 (`crates/conex-types/src/message.rs`)
在 Rust 核心层确立统一、多模态支持且宽容兼容命名的 `AgentMessageBlock`：

```rust
use serde::{Deserialize, Serialize};
use crate::tool::ToolOutput;

/// 工具调用块（单轨标准）
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
#[serde(rename_all = "camelCase")]
pub struct ToolCallBlock {
    pub id: String,
    pub tool_name: String,
    /// 结构化入参（JSON 对象或原始字符串包装）
    pub input: serde_json::Value,
}

/// 工具执行结果块（单轨标准）
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
#[serde(rename_all = "camelCase")]
pub struct ToolResultBlock {
    pub tool_call_id: String,
    pub tool_name: String,
    pub output: ToolOutput,
    #[serde(default)]
    pub is_error: bool,
    /// 多模态工具输出图片列表（可选）
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub images: Option<Vec<String>>,
}

/// 图片多模态内容块（一等公民支持）
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
#[serde(rename_all = "camelCase")]
pub struct ImageContentBlock {
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub url: Option<String>,
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub data: Option<String>,
    pub mime_type: String,
}

/// 统一消息内容块定义
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
#[serde(tag = "type")]
pub enum AgentMessageBlock {
    /// 正文文本块
    #[serde(rename = "text", alias = "Text", rename_all = "camelCase")]
    Text { text: String },

    /// 思考链推理块
    #[serde(rename = "thought", alias = "Thought", alias = "thought_log", rename_all = "camelCase")]
    Thought {
        text: String,
        #[serde(default, skip_serializing_if = "Option::is_none")]
        redacted: Option<bool>,
    },

    /// 工具调用块（支持 tool-call 与 tool_call 别名）
    #[serde(rename = "tool-call", alias = "tool_call", alias = "ToolCall", rename_all = "camelCase")]
    ToolCall(ToolCallBlock),

    /// 工具结果回执块（支持 tool-result 与 tool_result 别名）
    #[serde(rename = "tool-result", alias = "tool_result", alias = "ToolResult", rename_all = "camelCase")]
    ToolResult(ToolResultBlock),

    /// 图片块（支持多模态历史）
    #[serde(rename = "image", alias = "Image", rename_all = "camelCase")]
    Image(ImageContentBlock),
}
```

#### 2.1.2 前端载荷契约对齐 (`apps/crish-desktop/src/api/chat-bridge/historyMessages.ts`)
在前端重构 `HistoryMessage` 构造器，使其直接输出完整 blocks 并保全工具执行结果：
- 当消息中存在 `blocks` 时，原样保留并序列化为 `blocks_json`。
- 保留 `toolCalls` 的全量信息（包含 `output`、`status`、`arguments`），不再假定存在独立无用的 `toolCallResults`。
- 如果包含图片附件或 `contentParts`，将其打包为标准 `ImageContentBlock` 放入 `blocks`。

### 2.2 水合安全边界与幂等修补状态机 (`crates/session-loop/src/hydrate.rs`)

重构 `hydrate.rs`，将其定位为**“无损还原已完成历史上下文、确保大模型输入严格前缀合规”**的单一职责模块。

#### 2.2.1 彻底废除 `truncate_to_last_user`
- **设计裁决**：历史水合函数接收的是会话过去的已完成历史（Prior History），它的合法尾部必定是上一轮模型的 `Assistant` 回复（及其 Tool 结果）。
- **废除逻辑**：物理移除 `truncate_to_last_user` 函数及其实体调用。
- **替代方案：`sanitize_conversation_head`**：仅对历史序列头部做合规性清洗——剔除开头的孤儿 Tool 结果或非法 System 碎片，确保历史序列的第一条消息必定为合法的 `User` 消息（满足 LLM 协议首条必须为 User 的硬约束）。

#### 2.2.2 真实工具输出提取与孤儿自愈状态机
彻底重写 `resolve_blocks` 与 `synthesize_blocks`，优先读取 `toolCalls[].output`：

struct UnifiedHistoryToolCall {
    id: String,
    name: String,
    #[serde(default)]
    arguments: Option<String>,
    #[serde(default)]

    #[serde(default)]
    status: Option<String>,

/// 单条历史记录解析：块解析优先，合成解析保真
fn resolve_blocks(entry: &HistoryMessage) -> Vec<AgentMessageBlock> {
    // 1. 尝试直接按标准 AgentMessageBlock 序列反序列化
    if let Some(json) = entry.blocks_json.as_deref() {
        if let Ok(blocks) = serde_json::from_str::<Vec<AgentMessageBlock>>(json) {
            if !blocks.is_empty() {
                return blocks;
            }
        }
    }
    // 2. 规范合成解析：不丢弃任何 output
    synthesize_blocks_unified(entry)
}

fn synthesize_blocks_unified(entry: &HistoryMessage) -> Vec<AgentMessageBlock> {
    let mut blocks = Vec::new();
    if let Some(text) = entry.text.as_deref().filter(|t| !t.is_empty()) {
        blocks.push(AgentMessageBlock::Text { text: text.to_string() });
    }
    if let Some(thinking) = entry.thinking.as_deref().filter(|t| !t.is_empty()) {
        blocks.push(AgentMessageBlock::Thought { text: thinking.to_string(), redacted: None });
    }

    // 提取并配对工具调用与输出
    let parsed_calls = parse_unified_tool_calls(entry);
    for call in &parsed_calls {
        // 工具调用块
        blocks.push(AgentMessageBlock::ToolCall(ToolCallBlock {
            id: call.id.clone(),
            tool_name: call.name.clone(),
            input: parse_arguments(&call.arguments),
        }));

        // 如果调用对象自身带有 output，立即生成配对的 ToolResultBlock！
        if let Some(out) = &call.output {
            let is_err = call.status.as_deref() == Some("error");
            blocks.push(AgentMessageBlock::ToolResult(ToolResultBlock {
                tool_call_id: call.id.clone(),
                tool_name: call.name.clone(),
                output: ToolOutput::text(out.clone()),
                is_error: is_err,
                images: call.images.clone(),
            }));
        }
    }
    blocks
}

#### 2.2.3 真正的孤儿自愈（Orphan Healing）守卫
仅当 Assistant 消息中声明了 `ToolCall`，但在整个上下文（或同条消息）中既无内部 `output`、也无独立的 `ToolResult` 消息时，才判定为“跨 Run 崩溃导致的孤儿调用”。合成规则：
- 生成 `AgentMessageRole::Tool` 消息，错误码 `TOOL_INTERRUPTED_ORPHAN`。
- 绝不使用模糊的 `TOOL_OUTCOME_UNKNOWN` 覆盖已成功产出的内容。
- **自愈幂等性**：对已经拥有 `ToolResult`（或已自愈）的记录进行差集校验，保证 $\mathcal{H}(\mathcal{H}(m)) = \mathcal{H}(m)$。

### 2.3 严格对称的生命周期状态机与事件配对不变量

重塑会话状态机转移表与处理器，恢复状态转移图的对称性与 Usage 精确性。

#### 2.3.1 生命周期核心不变量（Core Invariants）
1. **不变量 INV-01（事件成对）**：每个 `TurnStart(N)` 对应且仅对应一个 `TurnEnd(N)`。系统处于活跃状态时，`current_turn_index` 记录当前打开的轮次。
2. **不变量 INV-02（Usage 不丢失）**：Provider 报告的 Usage 绑定在产生它的 Turn 内；`turn_complete` 消费 `turn_usage.take()` 发射；任何非正常提前闭合（如强停）必须从 `budget_state.turn_usage` 提取已产生的用量，严禁硬编码 `None`。
3. **不变量 INV-03（单 Run 内 TurnIndex 严格自增）**：单次 `AgentSessionLoop::run` 生命周期内，`turn_index` 单调自增（1, 2, 3...）。同 Run 内部由排队输入或 follow-up 触发的继续流转，绝对不将 `turn_index` 重置为 0。
4. **不变量 INV-04（因果闭包）**：所有导致模型重新调用的转移路径（如工具执行完成有后续输入），必须显式闭合前一回合（发射 `TurnEnd`），再开启新回合（发射 `TurnStart`）。

#### 2.3.3 安全点控制检查分流 (`crates/session-loop/src/loop/handlers/mod.rs`)
重构 `check_control` 与 `emit_missing_turn_end`：

```rust
pub(crate) fn check_control(state: &mut LoopState) -> Result<Option<EndDecision>, LoopError> {
    let (action, drained) = {
        let mut bus = state.control_bus.lock().unwrap_or_else(|e| e.into_inner());
        let action = apply_safe_point_control(&mut bus, Some(&state.abort_signal));
        let trace = if state.abort_signal.is_aborted() { Vec::new() } else { bus.take_trace() };
        (action, trace)
    };

    let Some(action) = action else {
        return Ok(None);
    };

    // 发射控制意图事件...
    emit_control_intent_events(state, &drained);

    match action {
        crate::safe_point::ControlAction::ForceCancel { reason } => {
            // L3 强停：真正收敛退出，此时才闭合未完成的 Turn！
            emit_missing_turn_end(state);
            dispatch(state, E::Abort)?;
            Ok(Some(EndDecision::aborted_with_diagnostic(state, reason)))
        }
        crate::safe_point::ControlAction::CooperativeStop { pending_messages, .. } => {
            // L2 协同停止：真正收敛退出，此时才闭合未完成的 Turn！
            emit_missing_turn_end(state);
            for message in pending_messages {
                // 持久化待处理输入，防内存丢弃（解决 BC01-7）
                state.input_queue.enqueue_steer(message);
            }
            drive_machine_to_stop(state)?;
            Ok(Some(EndDecision::stopped(state)))
        }
        crate::safe_point::ControlAction::SoftInject { steer_messages, follow_up_messages } => {
            // 【核心重构】：L1 软注入是流式继续，绝不调用 emit_missing_turn_end！
            // 严禁发射虚假 TurnEnd，完全由后续正常业务流程收口
            for message in steer_messages {
                state.input_queue.enqueue_steer(message);
            }
            for message in follow_up_messages {
                state.input_queue.enqueue_follow_up(message);
            }
            Ok(None)
        }
    }
}

/// 孤儿 Turn 补发：必须提取真实的已产生 Usage，严禁硬编码 None
pub(crate) fn emit_missing_turn_end(state: &mut LoopState) {
    let Some(turn_index) = state.current_turn_index.take() else {
        return;
    };
    let end_event = AgentEvent::TurnEnd {
        session_id: state.machine.context().session_id.clone(),
        turn_index,
        timestamp: conex_shared::time::now_iso_utc(),
        tool_call_count: state.machine.context().tool_call_count,
        // 提取真实的累计用量，绝不能清空吞没
        usage: state.budget_state.turn_usage.take(),
    };
    state.emit_event(end_event);
}
```

### 2.4 并发安全与持久化无序竞争消除 (BC01-8 & BC01-7)

#### 2.4.1 Pending Inputs 单调世代锁（Monotonic Generation Barrier）
彻底解决 `spawn_pending_input_save` 与 `record_message` 删除操作的并发竞态。
- 在 `AgentInputQueue` 中，为进入队列的每条用户输入分配单调递增的原子 `generation: u64`。
- 数据库 `pending_inputs` 表增加 `generation INTEGER NOT NULL DEFAULT 0` 列。
- **写入语义**：`INSERT OR REPLACE INTO pending_inputs(id, session_id, run_id, payload, generation) VALUES (?, ?, ?, ?, ?)`。
- **删除语义（CAS 屏障）**：`DELETE FROM pending_inputs WHERE id = ? AND generation <= ?`。
- **顺序执行通道**：在 Rust 壳层，将会话级的 pending 输入持久化变更收敛至专属有序 mpsc 通道，彻底消除无序 `tokio::spawn` 导致的幽灵复活。

#### 2.4.2 瞬时相位协同停止的持久化保全
在 `PreparingTurn` 与 `SteeringEvaluation` 阶段遇到 `CooperativeStop` 时：
- `drive_machine_to_stop` 完善分支，将机器推进至 `Done`（通过 `dispatch(E::Abort)` 或新增平滑停止事件）。
- 抽取的待注入消息不仅放入内存队列，同时同步持久化入数据库 `pending_inputs`，确保下次启动时依然可被恢复管理器装载。
