## 一、现状与根因穿透

基于只读代码审查与调用链推演，本方向存在的 7 项核心缺陷（BC03-1 至 BC03-7）揭示了当前控制流、进程生命周期、事件冻结与存储撤回之间严重的架构断裂与假实现：

### 1. BC03-1：L3 强停停不掉正在跑的工具进程与孤儿泄漏

- **代码位置**：
  - `apps/agent-workbench/src-tauri/src/run/run_launch.rs:1431`（UI 强停先打 `abort_signal.abort()` 再向总线入队）；
  - `crates/session-loop/src/exec_single.rs:283`（执行上下文解构时直接丢弃 `_abort_token`）；
  - `crates/session-loop/src/exec_single.rs:391`（每次单工具执行均无条件新建孤立的 `let abort_token = AbortToken::new()`，与 run 级 `AbortSignal` 毫无物理关联）；
  - `crates/session-loop/src/exec_single.rs:572-578`（`race_execution` 在 `abort_signal.wait_aborted()` 抢占后直接丢掉 execute future，既不调用 `abort_token.abort()`，也不触发下游清理）；
  - `crates/agent-tools/src/tools/shell_exec.rs:59, 241`（命令执行显式设置 `.kill_on_drop(false)`，宣称由外部显式杀进程）；
  - `crates/agent-tools/src/tools/shell_exec.rs:367-369`（流式状态机单步只读取 `r.abort_token.is_aborted()`，由于令牌未中止，该分支永远不触发）；
  - `crates/agent-tools/src/tools/shell_exec.rs:569-604`（`terminate_process_tree` 在 Windows 下同步拉起外部 `taskkill.exe /PID <pid> /T /F`，高负载下极易超时失败；在 Unix 下仅调用 `kill -TERM <pid>`，**仅给单个 PID 发信号，完全不杀子孙进程**）；
  - `crates/orchestrator/src/lifecycle.rs:225-228` 与 `apps/agent-workbench/src-tauri/src/run/run_core.rs:1132-1142`（子代理 `kill_all` 仅调用 `request_subagent_force_cancel` 向目标 run 的控制总线入队，**既不置位 `AbortSignal`，也不触发正在执行的工具批中断**）。
- **根因穿透**：
  - **抽象断裂**：Run 级控制（`AbortSignal`）、执行器级调度、工具级取消令牌（`AbortToken`）三者完全分裂。执行器认为丢弃 Future 就是“取消”，但操作系统进程由底层 Tokio Command 持有；因 `kill_on_drop(false)`，Future 被销毁后 OS 进程完全脱壳存活。
  - **跨平台进程管理薄弱**：完全没有使用 OS 原生进程组或作业对象机制。Windows 依赖脆弱的 `taskkill` 子进程，Unix 甚至只给根进程发信号，孙进程（例如构建工具拉起的 node/python/cargo）百分之百沦为孤儿进程滞留后台。

### 2. BC03-2：安全点短路丢弃终止原因，只入队强停被推迟到批后

- **代码位置**：
  - `crates/session-loop/src/safe_point.rs:124-128`（`apply_safe_point_control` 在检测到 `signal.is_aborted()` 时，直接短路返回 `Some(ControlAction::ForceCancel { reason: None })`，完全不调用 `bus.drain_as_action()`）；
  - `crates/session-loop/src/control.rs:370`（`request_force_cancel` 仅将意图推入队列，没有任何副作用）；
  - `crates/session-loop/src/loop/handlers/executing_tools.rs:49, 102, 148`（安全点仅在工具批开始前 `:49` 与工具批结束后 `:148` 执行，批执行过程中只依赖 `AbortSignal`）；
  - `crates/session-loop/src/loop/handlers/mod.rs:500, 542`（abort 抢占时放弃追踪 intent 轨迹，直接以 `reason: None` 构造收场诊断）；
  - `apps/agent-workbench/src-tauri/src/run/run_launch.rs:1435`（UI 明确传入的终止原因 `"ui-force-cancel"` 在入队后因前置 `abort()` 触发的短路而被彻底遗弃）。
- **根因穿透**：
  - **总线消费时序错误**：设计者误以为 `AbortSignal` 只是“快速唤醒器”，却在状态机判定中将 `AbortSignal` 设置为最高优先级且截断总线 drain。导致先 `abort()` 再入队的规范 UI 调用，其 reason 永远被短路吞没。
  - **只入队调用方失控**：子代理 kill 等只调用 `request_force_cancel` 的路径无法打断当前执行中的 `execute_batch`，必须傻等长达数十秒的命令超时才进入批后安全点。

### 2.1 跨平台操作系统级进程树硬性收割机制（OS-Level Process Group Reaper）

彻底废除依赖外部命令（如 Windows `taskkill.exe` 或 Unix 单进程 `kill`）的脆弱做法，将所有工具进程严格纳入操作系统内核级控制容器中。

#### 2.1.1 核心数据结构与契约定义

在 `crates/agent-tools/src/process_reaper/` 建立全新的内核级收割模块：

```rust
// crates/agent-tools/src/process_reaper/mod.rs

use std::path::Path;
use std::process::Stdio;
use tokio::process::Child;

/// 跨平台进程树容器句柄
pub struct ProcessTreeGuard {
    pid: u32,
    #[cfg(windows)]
    job_handle: windows_sys::Win32::Foundation::HANDLE,
    #[cfg(unix)]
    pgid: i32,
    terminated: std::sync::atomic::AtomicBool,
}

impl ProcessTreeGuard {
    /// 在指定平台创建具有级联强杀保证的进程树
    pub fn spawn_guarded(mut cmd: tokio::process::Command) -> std::io::Result<(Self, Child)>;

    /// 显式硬性收割（强行杀死作业对象/整个进程组）
    pub fn terminate_now(&self) -> std::io::Result<()>;

    /// 查询进程组内是否还有活跃进程
    pub fn is_alive(&self) -> bool;
}

impl Drop for ProcessTreeGuard {
    fn drop(&mut self) {
        // RAII 铁律：只要守卫离开作用域（例如 Future 被 drop、超时、主程序异常），
        // 必须立刻触发物理硬杀，绝不留下任何孤儿进程！
        let _ = self.terminate_now();
    }
}
```

#### 2.1.2 Windows 平台：Kernel Job Object 物理闭环

- **机制**：
  1. 调用 Windows API `CreateJobObjectW(ptr::null_mut(), ptr::null_mut())` 创建匿名 Job 对象。
  2. 配置扩展限制信息 `JOBOBJECT_EXTENDED_LIMIT_INFORMATION`，置位 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`。这保证了即使宿主崩溃或句柄关闭，Windows 内核调度器会自动强行收割挂入该 Job 的全部进程及其子孙进程。
  3. 使用 `child_cmd.creation_flags(CREATE_SUSPENDED | CREATE_NO_WINDOW)` 以挂起状态拉起子进程（或使用 Windows 10+ 嵌套 Job 机制）。
  4. 调用 `AssignProcessToJobObject(job_handle, child.as_raw_handle())` 挂入。
  5. 恢复子进程主线程执行。
  6. **显式强停**：调用 `TerminateJobObject(job_handle, 1)`，内核直接将退出码 1 广播至该 Job 下的所有树形节点，耗时 $<1\text{ms}$，零外部进程开销。

#### 2.1.3 Unix 平台：Process Group 与两阶段级联收割

- **机制**：
  1. 在 `Command` spawn 前配置 pre_exec：
     ```rust
     #[cfg(unix)]
     unsafe {
         cmd.pre_exec(|| {
             // 将子进程设置为其所在新进程组的 Leader
             if libc::setpgid(0, 0) != 0 {
                 return Err(std::io::Error::last_os_error());
             }
             Ok(())
         });
     }
     ```
  2. 获取生成的子进程 `pid`，其即为进程组 ID `pgid = pid as i32`。
  3. **显式强停**：
     - 第一阶段：向整个进程组发送优雅中断 `libc::kill(-pgid, libc::SIGTERM)`。
     - 宽限期检查（50ms 轮询）：若进程组已全部退出则收工。
     - 第二阶段：若仍有存活，无条件硬杀 `libc::kill(-pgid, libc::SIGKILL)`。

#### 2.1.4 信号与令牌双向桥接（Signal-Token Bidirectional Bridge）

消除 `AbortSignal`（Run级）与 `AbortToken`（Tool级）的脱节：

```rust
// crates/session-loop/src/safe_point.rs

impl AbortSignal {
    /// 将 Run 级信号绑定至工具级 Token，实现原子级联联动
    pub fn bind_tool_token(&self, token: &agent_tools::context::AbortToken) {
        if self.is_aborted() {
            token.abort();
            return;
        }
        let token_clone = token.clone();
```

#### 2.2.2 状态转移与原子检验

```rust
impl SessionFreezeRegistry {
    /// 步骤 1：申请进入收敛冻结态（原子 CAS，杜绝并发撤回碰撞）
    pub fn begin_freezing(&self, session_id: &str, token: &str, timeout_ms: u64) -> Result<(), FreezeError> {
        let mut map = self.state.write();
        match map.get(session_id) {
            Some(SessionFreezeState::Unfrozen) | None => {
                let deadline_ms = conex_shared::time::unix_millis() as u64 + timeout_ms;
                map.insert(session_id.to_string(), SessionFreezeState::Freezing {
                    token: token.to_string(),
                    deadline_ms,
                });
                Ok(())
            }
            Some(SessionFreezeState::Freezing { token: cur, .. }) |
            Some(SessionFreezeState::Frozen { token: cur, .. }) => {
                Err(FreezeError::AlreadyFrozen { token: cur.clone() })
            }
        }
    }

    /// 步骤 2：收敛完成，确立硬性序号上界
    pub fn lock_frozen_sequence(&self, session_id: &str, token: &str, frozen_seq: u64) -> Result<u64, FreezeError> {
        let mut map = self.state.write();
        let current = map.get_mut(session_id).ok_or(FreezeError::NotFrozen)?;
        match current {
            SessionFreezeState::Freezing { token: cur, .. } if cur == token => {
                let truncate_seq = frozen_seq + 1;
                *current = SessionFreezeState::Frozen {
                    token: token.to_string(),
                    frozen_seq,
                    truncate_reserved_seq: truncate_seq,
                };
                Ok(truncate_seq)
            }
            _ => Err(FreezeError::TokenMismatch),
        }
    }

    /// 事件写路径统一硬性门禁（单个锁周期内原子判定）
    pub fn validate_event_write(
        &self,
        session_id: &str,
        event: &AgentEvent,
        proposed_seq: u64,
        token: Option<&str>,
    ) -> Result<(), PersistError> {
        let map = self.state.read();
        let Some(st) = map.get(session_id) else {
            return Ok(());
        };

        match st {
            SessionFreezeState::Unfrozen => Ok(()),
            SessionFreezeState::Freezing { .. } => {
                // 收敛期仅放行已在运行的 run 发送其自身终态（以使其能够安全收敛）
                if matches!(event, AgentEvent::RunTerminal { .. } | AgentEvent::AgentEnd { .. }) {
                    Ok(())
                } else {
                    Err(PersistError::retraction_freeze(proposed_seq, 0, event_type_name(event)))
                }
            }
            SessionFreezeState::Frozen { token: valid_token, frozen_seq, truncate_reserved_seq } => {
                // 物理上界铁律：
                // 1. 唯一允许 sequence > frozen_seq 的事件，必须且只能是携带正确 token 的 TimelineTruncate 本身！
                if let AgentEvent::TimelineTruncate { .. } = event {
                    if token == Some(valid_token.as_str()) && proposed_seq == *truncate_reserved_seq {
                        return Ok(());
                    }
                }
                // 2. 其它任何事件，如果序号大于 frozen_seq，无论是否叫 RunTerminal，统统无条件硬性击毙！
                if proposed_seq > *frozen_seq {
                    return Err(PersistError::retraction_freeze(proposed_seq, *frozen_seq, event_type_name(event)));
                }
                Ok(())
            }
        }
    }

    /// 撤回事务完成或回滚时释放
    pub fn release(&self, session_id: &str, token: &str) -> Result<(), FreezeError>;
}
```

```rust
    /// 撤回物理修补：在原子事务中截断指定目标消息之后的所有历史消息
    pub fn truncate_session_messages_after(
        &self,
        session_id: &str,
        target_message_id: &str,
    ) -> Result<usize, DbFailure> {
        let s_id = session_id.to_string();
        let m_id = target_message_id.to_string();
        self.write_blocking(move |conn| {
            let tx = conn.transaction().map_err(|e| DbFailureKind::Sqlite(e))?;
            
            // 1. 获取目标消息的行序号 seq

                rusqlite::params![s_id, m_id],
                |row| row.get(0),
            ).optional().map_err(|e| DbFailureKind::Sqlite(e))?;

            let Some(t_seq) = target_seq else {
                return Err(DbFailureKind::NotFound(format!("目标消息 {m_id} 不存在")));
            };

            // 2. 删除目标消息之后的所有消息
            let deleted = tx.execute(
                "DELETE FROM session_messages WHERE session_id = ?1 AND seq > ?2",
                rusqlite::params![s_id, t_seq],
            ).map_err(|e| DbFailureKind::Sqlite(e))?;

            // 3. 修正 sessions 表的 message_count 与递增 body_version
            tx.execute(
                "UPDATE sessions 
                 SET message_count = (SELECT COUNT(*) FROM session_messages WHERE session_id = ?1),
                     body_version = body_version + 1,
                     updated_at = strftime('%Y-%m-%dT%H:%M:%fZ', 'now')
                 WHERE id = ?1",
                rusqlite::params![s_id],
            ).map_err(|e| DbFailureKind::Sqlite(e))?;

            tx.commit().map_err(|e| DbFailureKind::Sqlite(e))?;
            Ok(deleted)
        })
```

   - 彻底删除该常量。协调器配置为预算的唯一来源，杜绝“协调器配了 3 次但策略在 1 次时就擅自终止”的欺骗性实现。
5. **拔除续 Run 野蛮文本粘合拼接**：
   - 物理拔除 `run_idle.rs:1212-1232` 中把消息数组用 `\n` 强行拼接并塞给单一 `prompt` 的代码，全面替换为结构化 `AgentInputQueue` 注入。

## 五、立体验证与验收用例设计

依据立体验证纪律（禁止单一检查冒充验收），本重构方案设计了包含**单元测试、极端并发竞态、真实环境端到端现场验收**的完整测试矩阵。

### 1. 单元测试与状态机性质验证

- **TC-PROC-01：Windows Job Object 级联硬杀验证**
  - **用例**：通过 `shell_exec` 拉起一个 PowerShell 脚本，该脚本内部启动 3 个子进程（例如 `cmd /c ping 127.0.0.1 -n 100` 以及嵌套 node 脚本）。
  - **断言**：触发 `ProcessTreeGuard::terminate_now()` 或直接 drop 守卫；通过 Windows API 枚举系统进程表，断言根进程、子进程、孙进程在 50ms 内**全部消失**，零孤儿泄漏。
- **TC-PROC-02：Unix Process Group 级联硬杀验证**
  - **用例**：在 Unix 环境下启动一个派生多个后台子进程的 bash 脚本。
  - **断言**：调用终止后，向该 `pgid` 发送 `0` 信号（`libc::kill(-pgid, 0)`），断言返回 `ESRCH`（进程组彻底消亡）。
- **TC-FREEZE-01：冻结序号绝对不可越界验证**
  - **用例**：将会话置为 `Frozen { frozen_seq: 100 }`。并发派生 10 个线程尝试写入各种事件（包括普通事件、`RunTerminal`、`AgentEnd`、以及通过尽力落库路径的事件），其分配序号均为 101。
  - **断言**：除携带匹配 Token 的 `TimelineTruncate` 外，**其余所有 10 次写入必须全部返回 `PersistError::RetractionFreeze`**，events 表记录数严格保持不变。
- **TC-RETRACT-01：SQLite 物理行级撤回原子性验证**
  - **用例**：向 `session_messages` 写入 10 条消息（seq 1~10，id 为 m1~m10）。对 m5 执行 `truncate_session_messages_after(session_id, "m5")`。
  - **断言**：数据库中仅剩 m1~m5（共 5 行）；`sessions.message_count` 自动更新为 5；`sessions.body_version` 递增；查询 m6~m10 返回 `NotFound`。
- **TC-STEER-01：ToolLoop 重复调用检测与预算不被提前归零**
  - **用例**：模拟模型连续 3 轮产出完全相同的工具调用 `read_file("a.txt")`，每次执行均成功返回（`is_ok() == true`）。
  - **断言**：计数器不被 `all_ok` 归零；第 3 轮评估时准确触发 `SteeringAction::InterventionRequired`；`steering-evaluated` 事件中 `remaining_budget` 与实际消耗一致。

### 2. 极端并发与时序边界测试

- **TC-RACE-01：并发双重撤回碰撞（FREEZE3）**
  - **用例**：同时由两个并发任务对同一会话发起 `prepare_retraction`。
  - **断言**：第一个撤回正常进入 `Freezing` 并执行；第二个撤回在 `begin_freezing` 阶段原子失败，精确返回 `RetractionError::Busy`，绝不允许双重冻结或双写截断边界。
- **TC-RACE-02：撤回收敛期间工具执行中途强停**
  - **用例**：工具正在执行一个耗时 10 秒的长命令；此时撤回发起，触发 `stop_run`。
  - **断言**：`AbortSignal` 与 `AbortToken` 同时激活；底层子进程在 100ms 内被 Job Object / Process Group 强行收割；`wait_converged` 在 $<200\text{ms}$ 内迅速收敛成功，绝不触发 15 秒超时。
- **TC-RACE-03：子代理深层并发撤回收割**
  - **用例**：父会话下运行着 3 个子代理，且每个子代理正在执行 shell 命令。对父会话发起撤回。
  - **断言**：所有 3 个子代理的控制总线收到信号，底层进程树全部收割，3 个子代理均收敛至 `failed/cancelled`，最终父会话顺利完成截断。

### 3. 端到端现场真实验收（E2E Field Verification）

- **SCENARIO-E2E-01：UI 强停现场硬性验证**
  1. 启动桌面应用，发送提示词让 Agent 运行一个长时间的后台构建命令（如深度循环生成文件的脚本）；
  2. 打开操作系统任务管理器/进程监视器（Process Explorer），确认该命令派生了深层进程树；
  3. 点击 UI 上的 **Stop (强停)** 按钮；
  4. **验收标准**：
     - UI 立即呈现取消收场，收场诊断中准确显示终止原因（如 `"ui-force-cancel"`，非 None）；
     - 操作系统任务管理器中，由该命令拉起的**所有进程树节点瞬间消失**，CPU 占用立即归零；
     - 刷新页面后状态机保持终止状态，无二次唤醒。
- **SCENARIO-E2E-02：时间线撤回重启防复活验收**
  1. 发送消息 A $\to$ Agent 回复 $\to$ 发送消息 B $\to$ Agent 回复并修改了文件 `foo.txt`；
  2. 针对消息 A 执行**撤回**；
  3. 观察 UI：消息 B 及其后续回复消失，`foo.txt` 自动通过回收站快照恢复原状；
  4. **杀掉应用进程并重启**；
  5. 重新进入该会话（触发本地 SQLite Phase 1 水合）；
  6. **验收标准**：
     - 会话历史严格停留在消息 A，消息 B **绝对没有死灰复燃**；
     - `events` 表中 `timeline-truncate` 记录的 `boundary_seq` 严格等于消息 A 对应的序号；
     - 工作区文件状态与消息历史完全吻合。
