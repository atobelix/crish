## 二、架构重构设计与核心契约

为彻底解决上述深层缺陷，必须坚决摒弃“打补丁”、“加 if 判断”的临时兼容方案，重构建立**统一、刚性、不可绕过的纵深防御体系**。

```mermaid
flowchart TD
    CMD["原始 Shell 命令行 / 工具入参"] --> S1["阶段一：命令 AST 解码与内联审计"]
    S1 --> |提取 Base64 并 UTF-16LE/UTF-8 解码| S1_1["解码明文"]
    S1 --> |提取 Python/Node 内联脚本并审计系统调用| S1_2["提取内嵌命令与破坏性 API"]
    
    S1_1 & S1_2 & CMD --> S2["阶段二：路径围栏与系统敏感目录审查"]
    S2 --> |扫描命令中所有绝对路径| S2_1{"命中系统关键目录?"}
```

```rust
pub fn is_ps_encoded_command_flag(arg: &str) -> bool {
    let lower = arg.to_lowercase();
    let stripped = match lower.strip_prefix('-').or_else(|| lower.strip_prefix('/')) {
        Some(s) => s,
        None => return false,
    };
    let flag_name = stripped.split(['=', ':']).next().unwrap_or(stripped);
    if flag_name.is_empty() {
        return false;
    }
    
    // 1. 驼峰前缀缩写表（PowerShell 参数绑定 Acronym matching）：
    // -ec, -eco, -ecom, -ecomm, -ecomma, -ecomman, -ecommand

        return true;
    }
    
    // 2. 连续前缀唯一匹配（-e* 系列中唯一非 -ExecutionPolicy 的分支）：
    // -e, -en, -enc, -enco, -encod, -encode, -encoded, -encodedc, ...
    if "encodedcommand".starts_with(flag_name) {
        // 排除 -ex 开头（唯一指向 ExecutionPolicy）
        if !flag_name.starts_with("ex") {
            return true;
        }
    }
    
    false
```

```rust
/// Base64 编码载荷提取与解码器
pub fn extract_and_decode_ps_payload(args: &[String]) -> Result<Option<String>, SemanticError> {
    for (idx, arg) in args.iter().enumerate() {
        if is_ps_encoded_command_flag(arg) {
            let lower = arg.to_lowercase();
            let stripped = lower.strip_prefix('-').or_else(|| lower.strip_prefix('/')).unwrap();
            
            // 提取载荷字符串：支持 `-ec:BASE64`, `-ec=BASE64`, `/ec:BASE64` 或下一个参数
            let payload_opt = if let Some(pos) = stripped.find([':', '=']) {
                Some(arg[pos + 2..].trim())
            } else {
                args.get(idx + 1).map(|s| s.as_str())
            };
            
            let Some(payload) = payload_opt else {
                return Err(SemanticError::MalformedEncodedCommand("缺少 Base64 载荷".into()));
            };
            
            // 解码 Base64
            let decoded_bytes = base64::engine::general_purpose::STANDARD
                .decode(payload.trim())
                .or_else(|_| {
                    // 宽容尝试 URL_SAFE
                    base64::engine::general_purpose::URL_SAFE.decode(payload.trim())
                })
                .map_err(|e| SemanticError::MalformedEncodedCommand(format!("非法 Base64: {e}")))?;
            
            // PowerShell 原生 EncodedCommand 为 UTF-16LE 编码
            if decoded_bytes.len() % 2 == 0 {
                let u16_chars: Vec<u16> = decoded_bytes
                    .chunks_exact(2)
                    .map(|chunk| u16::from_le_bytes([chunk[0], chunk[1]]))
                    .collect();
                if let Ok(utf16_str) = String::from_utf16(&u16_chars) {
                    return Ok(Some(utf16_str));
                }
            }
            
            // 防御性回退：兼容 UTF-8 编码
            if let Ok(utf8_str) = String::from_utf8(decoded_bytes) {
                return Ok(Some(utf8_str));
            }
            
            return Err(SemanticError::MalformedEncodedCommand("无法解码为 UTF-16LE 或 UTF-8 文本".into()));
        }
    }
    Ok(None)
}
```

- **语义层整合**：在 `analyze_depth` 中，若提取到解码明文，立即将解码后的脚本送入 `analyze_depth(&decoded, depth + 1)`，其产生的 `overall_class`（如 `Redline`、`DeleteShape`、`Dangerous`）直接向外层传递！
- **审批呈现**：在 `SemanticAnalysis` 中新增 `decoded_payload: Option<String>` 字段。当需要用户确认时，审批通道展示的是解码后的真实命令明文，彻底终结黑盒审批。

```rust
pub enum WriteClaimHolder {

        run_id: String,
```

## 五、立体验证与验收用例设计

按照立体验证纪律，必须在单元测试、极端并发竞态与端到端现场环境中完成全量闭环验证。

### 5.1 核心逻辑穷举单元测试（Unit Tests）

#### 用例 1：PowerShell Base64 编码命令全缩写与深度解码拦截
- **测试输入**：
  1. `powershell.exe -ec VwByAGkAdABlAC0ATwB1AHQAcAB1AHQAIABoAGUAbABsAG8A`（正常明文）
  2. `powershell.exe -ec cm0gLXJmIC8=`（Base64 包含 `rm -rf /` 红线）
  3. `pwsh -en:cm0gLXJmIC8=`（冒号连接与 `-en` 缩写）
  4. `powershell /ec:cm0gLXJmIC8=`（斜杠前缀）
  5. `pwsh -ec "Format-Volume -DriveLetter C"`（Base64 包含格式化红线）
- **断言**：
  - 1 号命令被正确解码为 `Write-Output hello`，分类为 `Normal`；
  - 2, 3, 4, 5 号命令均被深度解码并准确识别出红线，分类必须为 `CommandClass::Redline`；在 `GatekeeperResult` 中返回 `Blocked`！

#### 用例 2：解释器（Python/Node）内联代码审查
- **测试输入**：
  1. `python -c "import os; os.system('rm -rf /')"`
  2. `python3 -c "import shutil; shutil.rmtree('C:\\Windows')"`
  3. `node -e "require('child_process').execSync('del /f /q C:\\*')"`
  4. `node -e "const fs = require('fs'); fs.rmSync('/var/data', {recursive: true})"`
- **断言**：
  - 1, 3 号命令提取出内层 Shell 调用，识别出红线与破坏性操作，判定为 `Redline` 或 `DeleteShape`；
  - 2, 4 号命令识别出原生破坏性 API，判定为 `DeleteShape` 并触发删除接管，绝不放行为 `Allowed`！

#### 用例 3：CD 形态与工作目录篡改全阻断
- **测试输入**：
  1. `Push-Location D:\`
  2. `cmd /c "cd /d D:\ && dir"`
  3. `powershell -Command "cd C:\; whoami"`
  4. `pwsh -wd C:\Sensitive -Command "Get-Process"`
- **断言**：
  - 全部命令在 `shell.rs` 的 `intercept_cd_shape` 中被精准拦截，返回 `TOOL_CD_BLOCKED` 错误，并引导用户使用 `Cwd` 参数。

#### 用例 4：命令行绝对路径围栏审查
- **测试输入**：
  1. `Get-Content C:\Users\orange\.ssh\id_rsa`
  2. `cat /etc/shadow`
  3. `Set-Content -Path D:\out_of_workspace\hacked.txt -Value "data"`（假设 workspace 为 `C:\Software\conex`）
- **断言**：
  - 1, 2 号命令命中系统核心敏感目录物理红线，直接返回 `TOOL_COMMAND_BLOCKED`；
  - 3 号命令试图向工作区外写文件，工作区边界检查硬阻断，拒绝执行。

#### 用例 5：任务类型（TaskType）执行链刚性门禁
- **测试环境**：注入 `task_type = "commit"` 的上下文。
- **测试输入**：
  1. `git status`
  2. `git commit -m "feat: test"`
  3. `npm test`
  4. `powershell -c "Write-Output 1"`
- **断言**：
  - 1, 2 号命令放行执行；
  - 3, 4 号命令在 `call_verdict` 与 `shell.rs` 均被刚性拦截，返回 `PermissionDenied: 任务类型 [commit] 严格禁止执行非白名单命令`。

#### 用例 6：FullAccess 下 Shell 删除 100% 进回收站
- **测试环境**：设置 `permission_mode = PermissionMode::FullAccess`。
- **测试输入**：`Remove-Item -Recurse -Force ./temp_data`。
- **断言**：
  - 执行结果必须返回 `deleted_files` JSON 结构；
  - 检查工作区文件已被移除，但回收站目录中完整生成了备份文件与快照；
  - 返回结果中必须包含可用于恢复的 `entryId`，严禁底层物理抹除！

### 5.2 极端并发与时序测试（Concurrency & Race Conditions）

#### 用例 7：同 Run 内并行写同一文件严格互斥（Parallel Tool Calls 竞态测试）
- **执行规程**：
  1. 模拟一个 Run 分发了 2 个并行的 `write_file` 工具调用，分别对应 `call_1` 和 `call_2`，两者的目标路径均为 `C:/workspace/common.rs`。
  2. 同时触发执行。
- **断言**：
  - 仅有一个调用成功获取 `WriteClaimGuard`；
  - 另一个调用立即返回 `tool.write_path_conflict` 错误，详细标明占用者为 `ToolCall { run_id, tool_call_id: "call_1" }`；
  - 彻底杜绝两个工具互相覆盖、文件内容损坏的问题。

#### 用例 8：跨 Run / 子代理写路径并发互斥
- **执行规程**：
  1. 主 Run 与子代理 Run 并发请求写入同一个文件 `C:/workspace/config.json`。
- **断言**：
  - 由于两者共享同一个会话级 `WritePathRegistry` 单例，后到达的请求必然被互斥锁阻断，返回明确的冲突结构化错误。

#### 用例 9：Guard Drop 精准释放测试
- **执行规程**：
  1. 同一 Run 内 `call_1` 声明写入 `file_a.rs`，`call_2` 声明写入 `file_b.rs`。
  2. `call_1` 执行完毕并 Drop 其 Guard。
- **断言**：
  - 检查注册表中 `file_a.rs` 的锁已释放；
  - `file_b.rs` 的锁**完好无损地保留**，直到 `call_2` 正常结束；
  - 杜绝旧实现中 `release_holder` 将 `call_2` 的锁一并清空的恶性 Bug。
