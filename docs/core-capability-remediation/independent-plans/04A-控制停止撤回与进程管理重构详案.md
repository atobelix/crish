## 一、执行摘要与核心突破目标

在当前 Conex/Crish 系统中，控制总线（ControlBus）、安全点（SafePoint）、工具中止令牌（AbortToken）、进程生命周期以及时间线撤回（Retraction）机制之间存在严重的**架构断层与逻辑割裂**，导致以下高危故障频发：
1. **L3 强停杀不掉正在执行的工具进程（BC03-1）**：UI 点击强停或调用终止命令后，前端界面将工具调用状态改写为已取消，但操作系统底层的 Shell、Python、Node 等子进程仍继续在后台存活并写入磁盘；
2. **子代理 kill 无法打断正在执行的工具批（BC03-2）**：子代理终止请求仅向控制总线入队，未触发底层的 `AbortSignal`，必须等待整批工具全部执行完毕后才能在批后安全点看见强停；
3. **安全点短路导致用户终止原因丢失（BC03-2）**：安全点在检测到 `AbortSignal` 已置位时直接返回 `reason: None`，未排空控制总线，导致用户或 UI 输入的强停原因与诊断轨迹全部丢失；
4. **时间线撤回（Retraction）为“纯前端内存截断假象”（BC03-5）**：撤回操作仅在前端 Zustand Store 中切内存数组并回滚磁盘文件，未物理下推到底层 SQLite 的 `session_messages` 表，导致应用刷新或会话重新水合（Hydrate）后被撤回的消息全部“僵尸复活”；
5. **事件流冻结边界失效与序号越界（BC03-3）**：撤回冻结后，由于放行了所谓的终态撤离事件（`RunTerminal`、`AgentEnd`）且尽力落库路径未读冻结注册表，导致 `sequence > frozen_seq` 的事件仍被写入，且对外的截断边界错用了日志尾序号；
6. **撤回超时导致副作用残留且仅单 Run 收敛（BC03-4）**：撤回协议先下发强停再等待收敛，超时后强停状态无法复位，且等待循环仅随机检查 `HashMap` 迭代的第一个 Run，漏掉会话内其它并行 Run。

本方案针对上述 7 大问题（BC03-1 ~ BC03-7）进行**穿透性根因治理与全链路重构**，实现：
- **物理关联的中断网**：构建 `AbortSignal` 到工具级 `AbortToken` 的双向直通物理绑定；引入进程树级 RAII 强杀守卫 `ProcessTreeGuard`，坚决废除普通执行路径下的 `kill_on_drop(false)`，确保 Tokio Future 取消或 Run 强停时操作系统进程树立即物理终结；
- **抢占式子代理强停**：`ForceCancelSink` 同步广播目标 Run 的 `AbortSignal`，工具批中竞速立即生效；
- **原因保全的安全点控制总线**：重写 `apply_safe_point_control`，前置排空总线聚合动作，保留 `ControlIntent` 完整轨迹与人类可读原因；
- **物理下推的撤回事务引擎**：撤回操作原子下推至 SQLite 存储层，执行物理有界收缩（`DELETE FROM session_messages WHERE session_id = ? AND seq > ?`），同步更新元数据版本与消息计数，彻底杜绝僵尸消息复活；
- **刚性事件冻结门禁**：彻底废除 `RunTerminal` / `AgentEnd` 的越界放行白名单，所有收敛必须在冻结读点前完成，冻结期除自身 `TimelineTruncate` 外零越界写入；
- **单一真理源 Steering 预算与检查点对齐**：统一协调器与策略层预算门限，纠正成功工具批的清零时序，修复检查点叶子覆盖与恢复输入环断裂。

## 二、现状穿透与根因剖析 (Deep Root Cause Analysis)

### 2.1 BC03-1：L3 强停与底层进程脱钩之根因

```
[UI / 外部调用] ──> abort_signal.abort() (AtomicBool = true)
                         │
                         ▼
        [exec_single.rs: race_execution]
         tokio::select! {
             _ = sig.wait_aborted() => None,   <── Future 被丢弃 (Drop)!
             res = execute => Some(res),
         }
                         │ (Drop execute)
                         ▼
          [agent-tools: shell_exec.rs]
          1. child_cmd.kill_on_drop(false)     <── Tokio Child 被 drop 时不发信号!
          2. r.abort_token 未被 abort!         <── exec_single 丢弃了 _abort_token!
          3. 进程树 (taskkill / SIGKILL) 零触发  <── 操作系统子进程成为孤儿进程继续运行!
```

- **代码坐标**：
  - `apps/agent-workbench/src-tauri/src/run/run_launch.rs:1209`：L3 强停先调用 `abort_signal.abort()`，再向控制总线入队；
  - `crates/session-loop/src/exec_single.rs:283-284`：`let (tool_ctx, approval_channel, mw_ctx, exec_ctx, _abort_token) = self.build_execution_contexts(...)`，创建出的 `_abort_token` 被前缀下划线直接忽略丢弃；
  - `crates/session-loop/src/exec_single.rs:391`：每次执行前新建独立对象 `let abort_token = AbortToken::new()`，该对象与传入的 `abort: Option<&AbortSignal>` 之间**没有任何物理监听或触发绑定**；
  - `crates/session-loop/src/exec_single.rs:572-579`：`race_execution` 在 `sig.wait_aborted()` 上 `select!`，一旦信号触发直接返回 `None` 并将 `execute` Future 丢弃（Drop），但**从未调用 `abort_token.abort()`**；
  - `crates/agent-tools/src/tools/shell_exec.rs:59-61`（同步路径）与 `:241-244`（流式路径）：均显式配置 `.kill_on_drop(false)`；
  - `crates/agent-tools/src/tools/shell_exec.rs:367-370`：流式状态机推进中仅在 `r.abort_token.is_aborted()` 为真时才调用 `kill_child`。但外层 `race_execution` 发生 drop 后流式状态机不再被轮询，且令牌本身从未被置位，显式杀进程分支永远无法执行。
- **深层断裂**：
  架构上存在两个孤立的“取消世界”：Run 级 `AbortSignal`（属于 `session-loop` 状态机）与工具执行级 `AbortToken`（属于 `agent-tools` 执行上下文）。执行器丢弃 Future 以为取消完成，而 Shell 工具以为未被中止且因 `kill_on_drop(false)` 不在 Drop 时清理。即使开启了 Tokio 原生的 `kill_on_drop(true)`，Tokio 也仅向顶级命令发出终止信号，在 Windows 上派生的 `cmd.exe /c python script.py` 中，`python.exe` 仍会脱壳孤儿存活。

### 2.2 BC03-2：安全点短路丢因与子代理 kill 延迟之根因

- **代码坐标**：
  - `crates/session-loop/src/control.rs:370` 与 `:328-336`：`request_force_cancel` 与 `request_subagent_force_cancel` 仅将 `ControlIntent` 推入总线队列；
  - `apps/agent-workbench/src-tauri/src/run/run_core.rs:1131-1143`（`ForceCancelSink`）：子代理强停只调用 `run.control_bus.request_subagent_force_cancel`，**漏掉了 `run.abort_signal.abort()`**；
  - `crates/session-loop/src/loop/handlers/executing_tools.rs:102`：工具批在执行期间只将 `AbortSignal` 交给 `exec_single`，不轮询 `control_bus`；
  - `crates/session-loop/src/safe_point.rs:123-128`：
    ```rust
    if let Some(signal) = abort_signal {
        if signal.is_aborted() {
            return Some(ControlAction::ForceCancel { reason: None });
        }
    }
    ```
    当信号已被触发时，直接短路返回 `reason: None`，未执行 `bus.drain_as_action()`，也未调用 `bus.take_trace()`；
  - `crates/session-loop/src/loop/handlers/mod.rs:500-542`：主循环在处理中止动作时，使用安全点返回的 `reason`（此处为 `None`）生成最终诊断事件，导致 UI 传入的 `ui-force-cancel` 等原因彻底丢失。
- **深层断裂**：
  - **子代理 kill 无法打断**：`ForceCancelSink` 以为往总线投递了强停就万事大吉，但正在跑的工具批不查总线只查 `AbortSignal`，导致强停被滞后到整批工具耗尽才执行。
  - **原因丢失**：UI 路径先调用 `abort_signal.abort()` 再投递总线；安全点却把信号判定置于总线排空之前，导致短路发生，总线中携带的人类可读原因与可观测性 Trace 永远留在队列中被丢弃。

  - `crates/orchestrator/src/events.rs:309-329` 与 `:356-370`：`push_terminal_best_effort` 与 `push_at_best_effort` 完全不读 `self.freeze` 注册表；

  冻结协议的目标是确立一个“绝对不再增长的事件序列上界 `frozen_seq`”。但由于白名单机制错误放行了 `RunTerminal` 和 `AgentEnd`，且尽力落库路径未接入冻结检查，后台收口或审计任务在冻结后依然能写入 `sequence = frozen_seq + 1`，使得随后生成的 `TimelineTruncate` 被推迟到 `frozen_seq + 2`，打破了“`TimelineTruncate.sequence == frozen_seq + 1`”的核心不变式。

### 2.4 BC03-4：撤回超时副作用残留与单 Run 等待盲区之根因

- **代码坐标**：
  - `crates/session-loop/src/retraction.rs:204-210`：先调用 `stop_run`（副作用：置位 `AbortSignal` 且不可逆），然后调用 `wait_converged`；
  - `apps/agent-workbench/src-tauri/src/retraction_commands.rs:221-244`：从 `active_runs`（`HashMap`）中过滤当前会话的 Run，使用 `main_run_id = Some(run_id.clone())` 仅记录遍历到的第一个 Run；
  - `apps/agent-workbench/src-tauri/src/retraction_commands.rs:252-284`：`wait_converged` 只轮询 `main_run_id` 对应的单只 Run 句柄，一旦超过 15 秒返回 `ConvergeTimeout`；
  - `crates/session-loop/src/retraction.rs:216`：超时后直接报错退出，此时会话未进入冻结，但所有 Run 均已被打上强停信号且无法复位。
- **深层断裂**：
  撤回流程属于分布式协作，对正在运行的多个 Run 缺乏事务隔离。`HashMap` 的无序性导致等待目标随机，其余并发 Run 在后台可能仍在继续写入；一旦超时，系统处于“已停机但未截断、不可回滚、不可重试”的死锁状态。

```
[用户刷新页面 / 切换会话 / 重启应用]
        │
        ▼
   [sessionActivateHydrate.ts: Phase 1]
   load_session_body(sessionId) ──> 从 SQLite session_messages 读取
        │

```

- **代码坐标**：
  - `crates/session-loop/src/retraction.rs:192`、`:234`、`:248`：`boundary` 被计算为目标消息起始 seq，但在构造 `TimelineTruncate` 与返回 `RetractionOutcome` 时，却把 `boundary_seq` 赋值成了 `frozen_seq`（日志尾），将“截断上界”与“目标起点”完全混淆；

  - `apps/crish-desktop/src/store/sessionMessageActionsCore.ts:151-155`：
    ```ts
    const idx = sess.messages.findIndex((m) => m.id === targetMessageId);
    if (idx === -1 || idx + 1 >= sess.messages.length) return;
    ```

    前端完全忽略传入的 `boundarySeq`，纯粹在 JavaScript 内存中按 ID 查找切除数组；

## 三、架构重构设计与核心契约 (Architecture & Core Contracts)

### 3.1 进程生命周期与物理终止网（RAII 守卫与信号级联）

#### 3.1.1 `AbortSignal` 与 `AbortToken` 物理绑定协议

彻底消除 `exec_single.rs` 中新建空令牌和下划线忽略的现象，建立双向直通机制：
- 在 `ToolContext` 中传递的 `abort_token` 必须与 Run 级 `AbortSignal` 强关联；
- 提供 `AbortSignal::bind_token(&self, token: &AbortToken)`，内部启动轻量监听任务或在信号触发时同步触发 `token.abort()`；
- `race_execution` 退出时不再单向丢弃 Future，必须在 `select!` 中触发 `abort_token.abort()` 并等待底层清理完成。

```rust
// crates/session-loop/src/exec_single.rs 重构设计
impl ToolSingleExecutor {
    fn build_execution_contexts(
        &self,
        call: &ToolBatchCall,
        ctx: &ToolExecCtx,
        options: &ToolBatchOptions,
        abort: Option<&crate::safe_point::AbortSignal>,
        approval: &Option<Arc<dyn ApprovalGate>>,
    ) -> (
        ToolContext,
        Option<Arc<ApprovalChannel>>,
        ToolExecutionContext,
        AbortToken,
    ) {
        let abort_token = AbortToken::new();
        // 核心契约：将 run 级 AbortSignal 与底层 AbortToken 物理绑定
        if let Some(signal) = abort {
            let token_clone = abort_token.clone();
            let signal_clone = signal.clone();
            // 绑定：一旦 AbortSignal 触发，立即将 AbortToken 置位
            tokio::spawn(async move {
                signal_clone.wait_aborted().await;
                token_clone.abort();
            });
        }
        
        let tool_ctx = ToolContext {
            session_id: ctx.session_id.clone(),
            abort_token: abort_token.clone(),
            // ... 其余字段保持单一真理源
        };
        (tool_ctx, approval_channel, mw_ctx, abort_token)
    }
}
```

#### 3.1.2 进程树级 RAII 强杀守卫 `ProcessTreeGuard`

在 `agent-tools/src/tools/shell_exec.rs` 中彻底剔除普通的 `kill_on_drop(false)`。除显式转为后台任务（`adopt_child`）交由 `BackgroundTaskManager` 接管外，所有同步与流式执行的子进程一律由 `ProcessTreeGuard` 包裹：

```rust
// crates/agent-tools/src/tools/process_guard.rs (新建)
pub struct ProcessTreeGuard {
    child: Option<tokio::process::Child>,
    pid: Option<u32>,
    disarmed: bool,
}

impl ProcessTreeGuard {
    pub fn new(child: tokio::process::Child) -> Self {
        let pid = child.id();
        Self {
            child: Some(child),
            pid,
            disarmed: false,
        }
    }

    /// 显式移交所有权（仅用于转后台 adopt_child 路径）
    pub fn disarm(mut self) -> tokio::process::Child {
        self.disarmed = true;
        self.child.take().expect("child must be present")
    }

    /// 物理杀死整棵进程树（跨平台实现）
    pub async fn kill_tree(&mut self) {
        if let Some(pid) = self.pid.take() {
            let _ = terminate_process_tree(pid);
        }
        if let Some(mut child) = self.child.take() {
            let _ = child.kill().await;
            let _ = child.wait().await;
        }
    }
}

impl Drop for ProcessTreeGuard {
    fn drop(&mut self) {
        if self.disarmed {
            return;
        }
        // 当 Future 被 tokio::select! 丢弃时，Drop 同步执行树杀兜底
        if let Some(pid) = self.pid.take() {
            let _ = terminate_process_tree_sync(pid);
        }
        if let Some(mut child) = self.child.take() {
            let _ = child.start_kill();
        }
    }
}
```

- **跨平台树杀规范**：
  - Windows：使用 `taskkill /PID <pid> /T /F`，强制级联终止全部衍生进程；
  - Unix / macOS：派生进程时设置 `process_group(0)`，终止时向进程组 `kill(-pgid, SIGKILL)` 发送硬信号，确保 Shell 派生的 Python/Node 等多级子孙进程无一遗漏。

#### 3.2.2 安全点排空优先与原因保全状态机

彻底重写 `crates/session-loop/src/safe_point.rs` 中的 `apply_safe_point_control`。严禁在检测到 `is_aborted()` 时直接短路返回空原因，必须先排空总线获取聚合动作：

```rust
// crates/session-loop/src/safe_point.rs 重构设计
pub fn apply_safe_point_control(
    bus: &mut ControlBus,
    abort_signal: Option<&AbortSignal>,
) -> Option<ControlAction> {
    let is_aborted = abort_signal.map(|s| s.is_aborted()).unwrap_or(false);
    
    // 无论信号是否置位，首先排空总线聚合动作，确保 intent 和 trace 不丢失
    let drain_action = bus.drain_as_action();

    match drain_action {
        ControlDrainAction::ForceCancel { reason, .. } => {
            Some(ControlAction::ForceCancel { reason })
        }
        ControlDrainAction::CooperativeStop { reason, pending_messages, .. } => {
            if is_aborted {
                // 若信号已被置位，提升为 ForceCancel，但保留 reason
                Some(ControlAction::ForceCancel {
                    reason: reason.or_else(|| Some("aborted_with_stop_intent".into())),
                })
            } else {
                Some(ControlAction::CooperativeStop { reason, pending_messages })
            }
        }
        ControlDrainAction::SoftInject { steer_messages, follow_up_messages, .. } => {
            if is_aborted {
                Some(ControlAction::ForceCancel {
                    reason: Some("aborted_with_pending_inject".into()),
                })
            } else {
                Some(ControlAction::SoftInject { steer_messages, follow_up_messages })
            }
        }
        ControlDrainAction::None => {
            if is_aborted {
                // 总线无意图但信号置位，给与明确的默认标记
                Some(ControlAction::ForceCancel {
                    reason: Some("aborted_by_signal".into()),
                })
            } else {
                None
            }
        }
    }
}
```

同时在主循环安全点消费前，无条件执行 `bus.take_trace()` 并广播发射 `control-intent` 事件，确保从入队到消费的观测链路闭合。

### 3.3 物理下推的时间线撤回（Retraction）事务引擎

#### 3.3.1 撤回六步原子事务重构

```
Step 1: [定位与校验]
  - 校验 session 存在，根据 target_message_id 在 session_messages 表精确定位 target_seq。
  - 获取 target_boundary_seq（被保留或被截断的界标序号）。

  - 扫描 active_runs 中属于该 session 的【全部】活跃 Run 及子代理。
  - 同时触发 abort_signal.abort() 并向各自控制总线投递 ForceCancel("retraction:<seq>")。
  - 并行 await 收集所有 Run 的收敛终态（join_all 带 15s 统一超时）。

Step 3: [锁定与安全快照]
  - 冻结读点：读取当前 events 表 MAX(sequence) 作为 frozen_seq。
  - 激活 SessionFreezeRegistry，严格拒绝任何非 TimelineTruncate 事件写入。
  - 收集回滚计划（文件快照与修改集）。

Step 4: [数据库物理下推 (SQLite Atomic Shrink)]
  - BEGIN IMMEDIATE 事务：
    1. DELETE FROM session_messages WHERE session_id = ?1 AND seq > ?2;
    2. UPDATE sessions SET message_count = (SELECT COUNT(*) FROM session_messages WHERE session_id = ?1),
                           body_version = body_version + 1
       WHERE id = ?1;
  - COMMIT; (持久层彻底消除僵尸消息)

Step 5: [文件副作用物理回滚]
  - TrashService 执行已收集快照的回滚操作。

Step 6: [截断事件发射与解冻]
  - 发射 AgentEvent::TimelineTruncate { 
        boundary_seq: target_boundary_seq,  // 修复：必须是目标界标序号！
        target_message_id,
        truncated_seq_range: (target_boundary_seq + 1, frozen_seq)
    }
  - 释放 SessionFreezeRegistry 冻结锁。
```

#### 3.3.2 SQLite 存储层物理收缩契约

在 `crates/conex-db/src/messages.rs` 中新增具有事务保障的撤回下推方法：

```rust
// crates/conex-db/src/messages.rs 新增物理下推契约
impl LocalDb {
    /// 时间线撤回物理收缩：
    /// 1. 严格有界删除 target_seq 之后的全部消息行；
    /// 2. 原子重算 message_count；
    /// 3. 自增 body_version 强制前端缓存失效。
    pub fn retract_session_messages_physical(
        &self,
        session_id: &str,
        target_seq: i64,
        retain_target: bool,
    ) -> Result<usize, DbFailure> {
        let session_id = session_id.to_string();
        self.write_blocking(move |conn| {
            let tx = conn
                .transaction_with_behavior(rusqlite::TransactionBehavior::Immediate)
                .map_err(|e| DbFailure::new(DbFailureKind::Io, format!("tx begin: {e}")))?;

            let sql = if retain_target {
                "DELETE FROM session_messages WHERE session_id = ?1 AND seq > ?2"
            } else {
                "DELETE FROM session_messages WHERE session_id = ?1 AND seq >= ?2"
            };

            let deleted_rows = tx
                .execute(sql, rusqlite::params![session_id, target_seq])
                .map_err(|e| DbFailure::new(DbFailureKind::Io, format!("delete retracted messages: {e}")))?;

            // 更新会话元数据（message_count 绝对同步，body_version 递增）
            tx.execute(
                "UPDATE sessions 
                 SET message_count = (SELECT COUNT(*) FROM session_messages WHERE session_id = ?1),
                     body_version = COALESCE(body_version, 0) + 1,
                     updated_at = datetime('now')
                 WHERE id = ?1",
                rusqlite::params![session_id],
            ).map_err(|e| DbFailure::new(DbFailureKind::Io, format!("update session metadata: {e}")))?;

            tx.commit()
                .map_err(|e| DbFailure::new(DbFailureKind::Io, format!("tx commit: {e}")))?;

            Ok(deleted_rows)
        })
    }
}
```

#### 3.3.3 全 Run 并行收敛等待契约

```rust
// apps/agent-workbench/src-tauri/src/retraction_commands.rs
async fn wait_all_converged(
    &self,
    session_id: &str,
    target_run_ids: &[String],
) -> Result<(), RetractionError> {
    if target_run_ids.is_empty() {
        return Ok(());
    }

    let deadline = Instant::now() + Duration::from_millis(CONVERGE_TIMEOUT_MS);
    loop {
        let mut all_terminal = true;
        {
            let active = self.state.active_runs.lock().unwrap_or_else(|e| e.into_inner());
            for run_id in target_run_ids {
                if let Some(run) = active.get(run_id) {
                    let handle = Arc::clone(&run.handle);
                    drop(active); // 释放锁再 await
                    if !handle.lock().await.is_terminal() {
                        all_terminal = false;
                        break;
                    }
                    // 重新加锁继续下一轮判定
                    break;
                }
            }
        }

        if all_terminal {
            return Ok(());
        }
        if Instant::now() > deadline {
            return Err(RetractionError::ConvergeTimeout);
        }
        tokio::time::sleep(Duration::from_millis(50)).await;
    }
}
```
