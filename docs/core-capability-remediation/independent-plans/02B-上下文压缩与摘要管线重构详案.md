## 一、现状与根因穿透（Path:Line 深度审判）

通过对 `crates/conex-compaction/` 全库、`crates/session-loop/` 的压缩与摘要协调器、`apps/agent-workbench/` 运行调度层以及前端 `crish-desktop` 历史加载链路的深层静态审计与动态拓扑追踪，证实当前上下文压缩与摘要系统处于**“内存有效、跨 Run 失效、估算严重失真、护栏分叉悬空、工具截断撕裂、代际反复冲突”**的严重亚健康状态。

```
                    【当前上下文压缩断裂拓扑】
[Run N 运行时]
  ├─ 预检/边界压缩 ──> 生成 plan.messages ──> 仅替换内存 state.conversation (内存生效)
  ├─ 产生新摘要 ──────> 仅广播 ContextCompressionEnd 事件 (未写 MessageEnd / 未写入 session_messages)
  ├─ 块表索引写入 ────> 写入 compression_blocks (generation 硬编码 1，跨 Run 发生主键冲突)
  └─ 后台摘要重试 ────> 绕过 RetryGate 护栏 ──> 成功后不写回对话 ──> Stub 永驻 ──> 重复摘要风暴

[Run N+1 启动时]
  ├─ 桌面发起 Run ───> loadSessionBody 从 SQLite 读取未压缩全文 ──> 发送完整 history
  ├─ 历史源判定 ─────> resolve_history_source 见 Frontend history 非空 ──> 丢弃 Cache 缓存
  └─ 模型请求 ───────> 重新全量装配已被压缩过的历史 ──> 压缩彻底失效！再次超窗！
```

### 2.1 高保真无依赖快速 Token 估算引擎（FastBpeTokenizer）

彻底重写 `crates/conex-compaction/src/tokens.rs`，消除将标点空格算作 1 token 及 CJK 算作 1 token 的粗暴逻辑，引入对齐主流 LLM 分词器（cl100k_base / o200k_base / Claude / Gemini）的高保真零外部依赖快速分词算法。

#### 2.1.1 核心算法规则与权重模型

1. **ASCII 单词与连续字符**：
   - 英文单词与连续字母数字串：按约 4.0 字符折算 1 Token（`ceil(len / 4.0)`）。
2. **空白序列折叠（Whitespace Folding）**：
   - 连续空格、Tab、换行符（如代码缩进 2~4 空格、`\r\n`）在现代 BPE 中均为单 Token。
   - 规则：连续空白字符按每 4 个字符计 1 Token（`div_ceil(4)`），禁止逐字符计费。
3. **CJK 统一表意字符与全角标点精准加权**：
   - CJK 表意文字（`U+4E00..=U+9FFF`）、平假名、片假名、谚文：统计基准标定为 **1.45 Token/字符**（以固定点数运算 `chars * 148 / 100` 或每 2 字符 3 Token 保守结算）。
   - 全角标点符号（`，`、`。`、`！`、`：` 等）：按 1.2 Token 折算。
   - Emoji 与代理对字符：按 2.5 Token 折算。
4. **多字符代码与 JSON 复合符号聚类**：
   - 针对 JSON 与代码常见符号簇（如 `": "`、`", "`、`{"`、`}]`、`!=`、`===`、`->`），识别为单个 Token，彻底消除 JSON 序列化带来的 300% Token 虚假高估。
5. **单条消息 Framing 固定开销**：
   - 每条 `AgentMessage` 在序列化为 Provider Wire 协议时，包含不可消除的角色边界标记（ChatML 格式形如 `<|im_start|>role\n...<|im_end|>\n`）。
   - 契约规定：每条消息基础开销计 **4 Tokens**；包含工具调用的消息追加 **8 Tokens** 协议封包开销。
6. **思考块（Thought Blocks）计费契约**：
   - 明确策略开关：若思考块将通过 wire 协议发送给模型（如当前 Run 内部上下文），计入 Token；若水合逻辑或协议层剔除思考块，则估算时自动跳过，保证估算与模型真实输入 100% 镜像对称。

```rust
// crates/conex-compaction/src/tokens.rs 核心重构接口

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct TokenizerConfig {
    pub message_framing_tokens: usize,
    pub tool_framing_tokens: usize,
    pub include_thoughts: bool,
}

impl Default for TokenizerConfig {
    fn default() -> Self {
        Self {
            message_framing_tokens: 4,

        }
    }
}

/// 高保真快速文本 Token 计数（零依赖状态机）
```

### 2.2 双阈值水位模型与自适应滑动窗口调度（Dual-Watermark Adaptive Scheduler）

彻底废除以硬编码 `KEEP_RECENT_TOKENS_DEFAULT = 20_000` 与 `window - reserve` 粗暴触发的旧机制，建立科学的动态水位控制模型。

#### 2.2.1 水位模型数学定义

设模型的有效可用窗口为：
$$W_{\text{avail}} = \text{context\_window} - \text{reserve\_tokens}$$
（`reserve_tokens` 保证输出预留，默认 4096，大生成任务可配）。

1. **常规线（Regular Watermark, 默认 85%）**：
   $$\text{Threshold}_{\text{regular}} = 0.85 \times W_{\text{avail}}$$
   - **行为**：**非阻塞异步预热**。在回合结束或空闲时检测，若达到 85%，由会话级协调器在后台拉起异步摘要任务。当前 Run 主任务不中断、不等待。后台摘要成功后平滑注入。
2. **临界线（Critical Watermark, 默认 95%）**：
   $$\text{Threshold}_{\text{critical}} = 0.95 \times W_{\text{avail}}$$
   - **行为**：**同步硬防御门禁**。在构建请求发送给 Provider 前检测。若估算值达到 95%，主流程必须同步阻塞执行压缩，防止 400 Context Overflow。
   - 若 LLM 摘要器不可用或超时，触发 **Emergency AST Pruning**（紧急 AST 剪枝）：
     - 阶段 1：对保留段中超大 `ToolResult` 实施基于语法结构的智能首尾截断（`tool_output.rs`）；
     - 阶段 2：若依然超标，紧急收敛保留回合数至 `min_recent_turns = 1`；
     - 阶段 3：生成确定性硬防御占位摘要，确保上下文 Token 严格回落到 80% 安全线以下。
3. **预算内早退断言（Early Exit Rule）**：
   - 若当前总 Token $\le \text{Threshold}_{\text{regular}}$（且无未完成 stub），`CompactionEngine` 必须立即返回 `NoopPlan`，**严禁对未超限的会话执行破坏性截断**。

#### 2.2.2 动态自适应滑动窗口（Adaptive Keep Recent Budget）

淘汰死硬的 20,000 Token 尾部保留逻辑，根据模型总窗口动态自适应计算保留预算：
$$\text{keep\_recent\_tokens} = \text{clamp}\left(W_{\text{avail}} \times 0.35, \, 4\,000, \, 40\,000\right)$$
- 小窗口模型（16k/32k）：保留 4,000 ~ 9,000 Tokens，留出充裕空间给历史摘要和后续生成。
- 大窗口模型（128k/200k/1M）：保留 30,000 ~ 40,000 Tokens，充分利用长窗口上下文。
- 完整回合下限 `min_recent_turns` 默认保持 2 回合。

### 2.3 原子级 ToolBatch 语义分块与双向闭包安全切割（Atomic ToolBatch Bidirectional Closure）

针对工具调用与回执被切开导致的语法断裂与孤儿报错，重构 `crates/conex-compaction/src/cut_point.rs`，建立**以“交互轮次（TurnBatch）”为原子单元的不可分割截断机制**。

#### 2.3.1 TurnBatch 状态机与原子边界

在智能体对话中，消息在物理上是线性的，但在语义上构成不可分割的原子批（TurnBatch）：
1. **UserTurn**：单个用户输入消息。
2. **AssistantToolTurn**：助手发起调用的消息（包含 1..N 个 `ToolCall`），以及后续紧随的所有对应的 `ToolResult` 消息。

```
[原始消息线性序列]
Msg 0: System
Msg 1: [compacted-summary-1-1] (历史折叠链，下界 fold_start)
Msg 2: User: "请帮我重构代码"                       <--- TurnBatch 0
Msg 3: Assistant (ToolCall: id_A, id_B)           <--- TurnBatch 1 (开始)
Msg 4: ToolResult (tool_call_id: id_A)             │
Msg 5: ToolResult (tool_call_id: id_B)             <--- TurnBatch 1 (结束)
Msg 6: User: "请继续运行测试"                       <--- TurnBatch 2
Msg 7: Assistant (ToolCall: id_C)                 <--- TurnBatch 3 (开始)
Msg 8: ToolResult (tool_call_id: id_C)             <--- TurnBatch 3 (结束)
```

#### 2.3.2 严格双向闭包算法

1. **倒推定位与初筛**：从末尾向前累计 Token，直到满足 `keep_recent_tokens` 与 `min_recent_turns`，获得初步切割点下标 `raw_cut`。
2. **原子向后对齐（Snap to TurnBatch Boundary）**：
   - 检查 `raw_cut` 是否落在一个 `AssistantToolTurn` 的中间（例如落在了 Msg 4 或 Msg 5）。
   - 若落在中间，根据下界安全性向前或向后对齐：
     - **向前闭包扩展**：将 `cut` 移动到该批次起始的 Assistant 消息下标（例如 Msg 3），确保保留段包含完整的调用与回执！
     - 检查扩展后的 `cut` 是否越过历史折叠链下界 `fold_start`。若越过且无处可切，则向后收缩到该批次结束后的下一轮 User 消息（Msg 6）。
3. **双向无孤儿数学证明**：
   - 切割点永远只能是某个 `TurnBatch` 的起始下标。
   - 保留段 `messages[cut..]` 中的每个 `ToolResult`，其 `ToolCall` 必定存在于保留段中（无孤儿回执）。
   - 保留段 `messages[cut..]` 中的每个 `ToolCall`，其 `ToolResult` 也必定位于保留段中（无未决悬挂调用）。
   - 丢弃段 `messages[..cut]` 送入 LLM 摘要器时，也同样是完整的工具交互上下文，摘要器绝不会看到“只有回执没有调用”的残缺 prompt。

### 2.4 统一样式摘要协调器与漏桶护栏（Unified CompactionCoordinator & Leaky-Bucket Guard）

物理拔除 `crates/session-loop/src/loop/summary_dispatch.rs` 与 `summary_coordinator.rs` 之间的双轨分叉代码，合并为单一事实源的 `CompactionCoordinator`。

#### 2.4.1 单一协调器生命周期与并发契约

1. **会话级单飞（Single-Flight per Session）**：
   - 每个 `session_id` 维护一个 `Arc<SessionCoordinatorEntry>`，持有当前活跃的后台任务句柄 `JoinHandle`。
   - 若当前会话已有摘要任务正在运行，新的触发请求（无论是预检还是边界检查）直接幂等忽略，严禁并发打架。
2. **全局并发信号量（Global Semaphore）**：
   - 全局最多允许 **2 个并发摘要任务**（`MAX_CONCURRENT_SUMMARY_TASKS = 2`），防止多会话同时超窗打爆 Provider 速率限制或本地 CPU。
3. **内置漏桶/滑动窗口护栏（Leaky-Bucket Retry Gate）**：
   - 护栏逻辑直接固化在协调器核心，无论通过何种路径触发，必须通过检查：
     - 窗口期：30 分钟（`WINDOW_MS = 1_800_000`）。
     - 窗口内最大尝试次数：8 次（`MAX_ATTEMPTS = 8`）。
     - 若耗尽，进入休眠状态，等待窗口滑动或用户显式发送新输入重置。
4. **全闭环完成回调（Closed-loop Atomic Mutation）**：
   - 彻底废除回调参数为 `None` 的半吊子设计。后台摘要任务成功产出 `(rendered_markdown, summary_json)` 后，必须执行原子回调：
     1. 更新数据库 `compression_blocks` 表（`summary_json`、`summary`、`state = 'committed'`）；
     2. 向数据库 `session_messages` 表更新对应的 `compacted-summary` 消息正文；
     3. 刷新内存中活跃的 `state.conversation` 与 `SessionHistoryCache`，将 stub 替换为真实 markdown；
     4. 清除 `pending_summary_retry` 待重试标记。彻底终结重复摘要风暴！

### 2.5 存储层原子落盘与跨 Run 连续性闭环（Atomic Storage & Cross-Run Continuity）

彻底解决下一轮 Run 重新读回未压缩全文（BC05-1）以及代数写死导致的主键冲突（BC05-3）。

#### 2.5.1 会话代数（Generation）自增闭环

1. **单真理来源**：
   - 会话代数以 SQLite `session_meta` 中的 `last_compaction_generation` 为唯一真理来源。
   - `CompactionEngine` 压缩方法必须接收当前的 `generation: u32` 参数，禁止在引擎内部写死 `let generation = 1;`！
2. **单调自增生成**：
   - 每次执行压缩前，读取 `current_gen = session_meta.last_compaction_generation.unwrap_or(0)`。
   - 本次压缩代数严格为：`next_gen = current_gen + 1`。
   - 块 ID 格式保持为：`compacted-summary-{next_gen}-{fold_index}`。
   - 在同一个数据库事务中，写入 `compression_blocks` 表，并原子更新 `session_meta` 的 `last_compaction_generation = next_gen`。
   - **绝对杜绝 `(session_id, block_id)` 冲突**，`INSERT` 必然成功。

#### 2.5.2 压缩消息入库与前端加载对齐

1. **摘要消息物理落盘**：
   - 在 `apply_compaction` 内部，通过 `record_message` 生成一条真实的 `AgentMessage`：
     - `id`: `compacted-summary-{next_gen}-{fold_index}`
     - `sender`: `"assistant"`
     - `status`: `"completed"`
     - `text`: `rendered_markdown`
     - `blocks`: `[AgentMessageBlock::Text { text: rendered_markdown }]`
   - 发送 `MessageStart` 与 `MessageEnd` 事件，使该消息被写入 SQLite `session_messages` 表。
2. **被压缩历史的物理隔离与加载投影**：
   - 被压缩丢弃的消息并不粗暴物理删除（保留用户审计与查看历史诉求），而是在 `session_messages` 表中将其标记为 `compacted_block_id = block_id`（或在 `compression_blocks` 记录其 id 集合）。
   - **前端与后端历史加载（SSOT）**：
     - 重构 `apps/crish-desktop/src/api/chat-bridge/historyMessages.ts`：
       在 `buildHistoryMessages` 构建送给模型的上下文时，以最新的 `compacted-summary` 消息为锚点，**自动忽略所有位于该压缩块之前的被压缩旧消息**！
     - 即使前端重新通过 `loadSessionBody` 加载全量消息，下发给后端的 `history` 也**天生已经是压缩后的形态**（System -> compacted-summary -> 保留尾部）！
     - 后端 `resolve_history_source` 无论是选前端 history 还是选后端 Cache，内容 100% 保持一致，彻底根除跨 Run 重新读回全文的顽疾。

#### 2.5.3 `/compact` 手动命令与后台自动预检统一

- 桌面端输入 `/compact` 触发的 `core_compact_now` 命令与后台自动预检彻底共用相同的核心执行管道：
  - 调用相同的 `FastBpeTokenizer`；

## 五、立体验证与验收用例设计

按照仓库“立体验证纪律（7.1节）”，本重构方案覆盖单测、极端状态机测试与真实桌面端现场验收。

### 5.1 纯逻辑与算法单元测试（Unit Tests）

1. **分词器保真度对比测试（Tokenizer Precision Benchmark）**：
   - **用例 1（CJK 字符加权）**：输入包含 1,000 个中文字符的段落，验证 `count_tokens_fast` 结果在 `1,300 ~ 1,600` 之间，严禁出现老算法等于 1,000 的严重低估。
   - **用例 2（JSON 结构与代码空格）**：输入包含多层嵌套 JSON（20 个键值对）及缩进代码的字符串，验证其计数结果与老算法相比压缩 `40% ~ 60%`，与实际 tiktoken cl100k_base 误差 $\le 8\%$。
   - **用例 3（消息开销）**：构建包含 10 条空文本消息的列表，验证其 Token 计数严格包含 $10 \times 4 = 40$ 的 framing 开销。
2. **TurnBatch 原子闭包截断穷举测试（CutPoint Closure Exhaustion）**：
   - **用例 1（多工具调用批次保护）**：构造一个 Assistant 消息同时发起 5 个并发工具调用（`call_1` ~ `call_5`），后跟 5 条 `ToolResult`。将保留预算设置在第 3 条 Result 处，断言算法**绝不会在此处切断**，而是自动向前扩展将整个 Assistant 消息及全部 5 条 Result 完整保留在尾部。
   - **用例 2（孤儿回执防御）**：构造数据异常序列（回执先于调用），验证算法拒绝产生语法非法截断，优雅回退为放弃压缩（返回 `None`）。
   - **用例 3（折叠链下界保护）**：在存在 3 个历史折叠链的情况下，无论预算多紧张，验证切割点严格保持在 `fold_start` 之后，绝不侵蚀历史摘要链。
3. **水位判定与自适应滑动窗口测试（Watermark & Budget Tests）**：
   - **用例 1（预算内早退）**：当估算 Token 占用仅为窗口的 50% 时，调用 `compact_agent_messages`，断言返回 `NoopPlan`，消息条数、ID 100% 未发生改变。
   - **用例 2（小窗口与大窗口自适应保留）**：
     - 在 16k 窗口下，验证保留预算自适应计算为 4,000 Tokens；
     - 在 200k 窗口下，验证保留预算自适应计算为 40,000 Tokens。

### 5.2 状态机与并发极端场景测试（State Machine & Concurrency Tests）

1. **重复摘要风暴拦截测试（Anti-Storm Gate Test）**：
   - 构造一个持续产生 stub 的失败场景，模拟用户连续快速输入 20 条消息。
   - 验证 `CompactionCoordinator` 内置的 `SummaryRetryGate` 在达到 8 次尝试后立即阻断后续后台 spawn，计数器严格受限，且在 30 分钟窗口过后才释放新配额。
2. **全局并发信号量挤压测试（Global Concurrency Limiting）**：
   - 启动 5 个并发会话同时进入超窗状态触发后台摘要。
   - 监控全局原子计数器 `ACTIVE_SUMMARY_TASKS`，断言任意物理时刻处于 active 的任务数 $\le 2$。
3. **代数自增单调性与数据库无冲突测试（Monotonic Generation Persistence）**：
   - 在同一个会话中连续触发 5 次跨 Run 压缩。
   - 校验 SQLite 数据库中的 `compression_blocks` 表，5 条记录全部成功持久化（`generation` 分别为 1, 2, 3, 4, 5），无任何 `PRIMARY KEY` 冲突或丢弃。
