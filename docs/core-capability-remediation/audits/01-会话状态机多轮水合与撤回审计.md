## 二、 维度一：核心会话多轮水合与单源历史保真深度审计

### 2.1 物理删除 `truncate_to_last_user` 与单源保真契约

在历史实现中，水合模块曾错误地假定“每次任务调用必须以 User 消息结尾”，从而通过 `truncate_to_last_user` 函数将尾部已生成的 Assistant 消息以及 Tool 调用产物强行截断丢弃。这导致多轮对话恢复时模型丧失对自身前一轮回复的记忆，构成严重的反退避破口（BC01-4）。

#### 源码穿透核查（`crates/session-loop/src/hydrate.rs:23-25, 48-68`）

1. **截断逻辑根除**：核查全仓代码，`truncate_to_last_user` 函数已被彻底从源码中物理删除，无任何保留或条件编译宏残留：
   ```rust
   // crates/session-loop/src/hydrate.rs:23-25
   //! 5. 单源历史契约（01A/01B 重构）：物理彻底删除向后截断 truncate_to_last_user，
   //!    已入库历史以 Assistant/Tool 结尾完全合法且天然应该保留；
   //!    仅保留 sanitize_conversation_head 剔除首条合法用户消息前的非法碎片；
   ```
2. **水合主流程单源保留**：
   ```rust
   // crates/session-loop/src/hydrate.rs:48-68
   pub fn hydrate_history(history: Vec<HistoryMessage>) -> Vec<Arc<AgentMessage>> {
       let mut messages: Vec<Arc<AgentMessage>> = Vec::new();
       for entry in history {
           match entry.sender.as_str() {
               "user" => {
                   if let Some(msg) = hydrate_user(&entry) {
                       messages.push(Arc::new(msg));
                   }
               }
               "assistant" => {
                   for msg in hydrate_assistant(&entry) {
                       messages.push(Arc::new(msg));
                   }
               }
               _ => {}
           }
       }
       sanitize_conversation_head(&mut messages);
       repair_orphan_tool_calls(&mut messages);
       messages
   }
   ```
3. **头部协议清洗（`sanitize_conversation_head`）**：仅向前扫描第一个 `AgentMessageRole::User` 消息，丢弃在此之前的非法孤儿 Assistant 或 Tool 碎片，满足底层 LLM 协议“第一条非系统消息必须为 User”的刚性契约，对尾部完全放行：
   ```rust
   // crates/session-loop/src/hydrate.rs:544-573
   fn sanitize_conversation_head(messages: &mut Vec<Arc<AgentMessage>>) {
       let first_user_idx = messages.iter().position(|m| m.role == AgentMessageRole::User);
       match first_user_idx {
           Some(idx) => {
               if idx > 0 {
                   let mut kept = Vec::with_capacity(messages.len());
                   let mut found_user = false;
                   for m in messages.drain(..) {
                       if m.role == AgentMessageRole::User {
                           found_user = true;
                       }
                       if found_user || m.role == AgentMessageRole::System {
                           kept.push(m);
                       }
                   }
                   *messages = kept;
               }
           }
           None => messages.clear(),
       }
   }
   ```

### 2.3 `repair_orphan_tool_calls` 孤儿自愈与幂等性防护

3. **幂等性保障**：由于已配对的调用绝不会进入合成逻辑，多次重复调用 `repair_orphan_tool_calls` 时长度与内容保持严格恒定（通过 `test_true_orphan_tool_call_self_healing_and_idempotency` 验证）。

## 三、 维度二：会话状态机时钟（`turn_index`）与终态成对守卫深度审计

### 3.1 状态机时钟单调性与防归零防护

在多轮会话或单次 Run 内部包含多个工具调用回合时，前端通过 `turn_index` 区分不同回合的思考与正文增量。若状态机在回合结束或新输入到达时将 `turn_index` 归零，前端将误认为同一个 turn 被重放，导致历史消息被覆写或 UI 闪烁。

#### 源码穿透核查（`crates/conex-types/src/transition.rs` 与 `crates/session-loop/src/state.rs`）

1. **转移表副作用规范（`transition.rs:172-181`）**：
   当状态机处于 `TurnComplete` 且接收到 `InputAvailable` 时，显式配置 `reset_all_counters: false`：
   ```rust
   // crates/conex-types/src/transition.rs:172-181

           S::AwaitingInput,
   ```

### 3.2 `TurnStart` 与 `TurnEnd` 严格 1:1 成对发射与用量统计

在长会话与复杂转向重试场景下，若前一回合因 `NoProgressContinue` 或 `SteeringComplete` 重进 `preparing-turn`，容易遗漏前序回合的 `TurnEnd` 事件，导致前端处于永久 streaming 状态，且前一回合消耗的 Token 用量丢失。

#### 源码穿透核查（`prepare_turn.rs`、`turn_complete.rs`、`handlers/mod.rs`）

1. **`prepare_turn` 入口自愈守卫（`crates/session-loop/src/loop/handlers/prepare_turn.rs:38-54`）**：

### 4.1 撤回边界序号 `boundary_seq` 准确性确定

用户在前端点击撤回某条 User 消息时，系统必须精确截断到该消息所对应的事件边界，严禁拿当前事件流的尾部序号冒充截断边界。

#### 源码穿透核查（`retraction_commands.rs:176-204` 与 `retraction.rs:193-197`）

1. **反查事件流最新 `message-start`**：
   ```rust

       if let Ok(envelope) = serde_json::from_str::<AgentEventEnvelope>(&row.payload) {

               if message.id == target_message_id {
                   found = Some(row.sequence as u64);
               }
           }
       }
   }
   Ok(found)
   ```
2. **Fail-Closed 保护**：若 `target_message_id` 不存在，立即返回 `RetractionError::NotFound`，绝不进入冻结态或误截断其他内容。

### 4.2 会话级冻结隔离与并发互斥（FREEZE1/FREEZE3）

#### 源码穿透核查（`crates/session-loop/src/retraction.rs:173-255`）

撤回协议通过八步严格原子编排执行：
1. **定位**：反查确认 `boundary_seq`；
2. **互斥**：检查 `freeze.is_frozen(session_id)`，拒绝并发冲突（`RetractionError::Busy`）；
3. **停 Run**：对会话内所有活跃 Run 投递 L3 `force_cancel` 并 `kill_all` 子代理；
4. **收敛网等待**：`wait_all_converged` 等待会话内所有 Run 句柄进入终态；
5. **读稳定点**：读取当前 events 表最大序号 `frozen_seq = MAX(sequence)`；
6. **激活会话级冻结**：注册 `freeze.freeze(session_id, token, frozen_seq)`，任何非撤离写入（`> frozen_seq`）将被 `orchestrator` 的 `EventQueue` 刚性拦截；
7. **收集回滚计划并落库 `TimelineTruncate`**：在冻结期收集 `TrashService` 写前快照；成功后发射 `TimelineTruncate` 事件（`sequence = frozen_seq + 1`，`boundary_seq = boundary`）；
8. **释放冻结**：落库确认后安全释放令牌。

### 4.3 SQLite 消息持久层物理下推事务（`truncate_session_messages_after`）

过去的撤回仅在内存或事件流中打标，导致应用重启或重新打开会话水合时，被撤回的后续消息重新从 SQLite 中读出并显示（死灰复燃）。现在的实现将截断动作物理下推至 SQLite 存储引擎层。

#### 源码穿透核查（`crates/conex-db/src/messages.rs:100-110, 302-384`）

```rust
// crates/conex-db/src/messages.rs:302-384
pub fn truncate_session_messages_after_conn(
    conn: &mut rusqlite::Connection,
    session_id: &str,
    target_message_id: &str,
) -> Result<usize, DbFailure> {
    // 1. 获取目标消息在 session_messages 表中的行序号 seq
    let target_seq: Option<i64> = conn
        .query_row(
            "SELECT seq FROM session_messages WHERE session_id = ?1 AND id = ?2 ORDER BY seq DESC LIMIT 1",
            rusqlite::params![session_id, target_message_id],
            |row| row.get(0),
        )
        .optional()
        .map_err(|e| DbFailure { ... })?;

    let Some(target_seq) = target_seq else {
        let existing_count: i64 = conn
            .query_row("SELECT COUNT(*) FROM session_messages WHERE session_id = ?1", rusqlite::params![session_id], |row| row.get(0))
            .unwrap_or(0);
        if existing_count == 0 { return Ok(0); }
        return Err(DbFailure {
            message: format!("目标消息 {target_message_id} 在会话 {session_id} 的 session_messages 中不存在"),
            kind: DbFailureKind::Other("truncate_target_not_found".to_string()),
        });
    };

    truncate_session_messages_after_seq_conn(conn, session_id, target_seq)
}

pub fn truncate_session_messages_after_seq_conn(
    conn: &mut rusqlite::Connection,
    session_id: &str,
    target_seq: i64,
) -> Result<usize, DbFailure> {
    // 自愈补建会话行
    conn.execute(
        "INSERT OR IGNORE INTO sessions (id, title, updated_at) VALUES (?1, '', strftime('%s','now') * 1000)",
        rusqlite::params![session_id],
    )?;

    // 1. 物理删除目标序号之后的所有消息行
    let deleted = conn.execute(
        "DELETE FROM session_messages WHERE session_id = ?1 AND seq > ?2",
        rusqlite::params![session_id, target_seq],
    )?;

    // 2. 原子重算 sessions 表的 message_count，自增 body_version，更新 updated_at
    conn.execute(
        "UPDATE sessions
         SET message_count = (SELECT COUNT(*) FROM session_messages WHERE session_id = ?1),
             body_version = COALESCE(body_version, 0) + 1,
             updated_at = strftime('%s','now') * 1000
         WHERE id = ?1",
        rusqlite::params![session_id],
    )?;

    Ok(deleted)
}
```
