## 二、L3 强停物理终止进程树与 AbortToken 物理绑定审计

### 2.1 `exec_single.rs`：Run 级 AbortSignal 与 AbortToken 双向物理绑定

在过去的实现中，存在工具执行上下文与会话级中止信号脱节的问题：工具内部持有局部的 `AbortToken`，而当 Run 级收到 L3 强停（`AbortSignal`）时，工具无法感知，导致正在运行的子进程、流式管道或长轮询持续挂死。

本次审计核查代码实现（[exec_single.rs:415-428](file:///c:/Software/conex/crates/session-loop/src/exec_single.rs#L415-L428)）：
```rust
let abort_token = AbortToken::new();
// BC03-1 / 04A / 04B：将 Run 级 AbortSignal 与工具级 AbortToken 物理绑定
if let Some(signal) = abort {
    if signal.is_aborted() {
        abort_token.abort();
    } else {
        let sig_clone = signal.clone();
        let tok_clone = abort_token.clone();
        tokio::spawn(async move {
            sig_clone.wait_aborted().await;
            tok_clone.abort();
        });
    }
}
```

#### 关键机制核验：
1. **即时与异步双重保证**：执行上下文构造时，首先检查 `signal.is_aborted()`。若已触发，则以 $O(1)$ 直接同步置位 `abort_token.abort()`；若未触发，启动轻量 `tokio::spawn` 异步等待 `sig_clone.wait_aborted()`，一旦信号广播立即级联置位 `tok_clone.abort()`。
2. **审批通道物理接线（[exec_single.rs:434-442](file:///c:/Software/conex/crates/session-loop/src/exec_single.rs#L434-L442)）**：
   在需要审批的路径中，`ApprovalChannel::new` 同时接收了 `abort.cloned()` 与 `abort_token.clone()`。在 [approval.rs:88-106](file:///c:/Software/conex/crates/session-loop/src/approval.rs#L88-L106) 中，`is_aborted` 与 `wait_aborted` 对两者取联合（OR）语义：
   ```rust
   fn is_aborted(&self) -> bool {
       self.abort_token.is_aborted()
           || self.abort.as_ref().map(|s| s.is_aborted()).unwrap_or(false)
   }
   ```
   无论是批级信号还是会话令牌触发，审批等待均即时唤醒并退出，杜绝死锁。
3. **竞速执行硬性拦截（[exec_single.rs:613-634](file:///c:/Software/conex/crates/session-loop/src/exec_single.rs#L613-L634)）**：
   ```rust
   match abort {
       Some(sig) => tokio::select! {
           biased;
           _ = sig.wait_aborted() => {
               tool_ctx.abort_token.abort();
               None
           }
           result = tokio::time::timeout(timeout, execute) => {
               if result.is_err() {
                   tool_ctx.abort_token.abort();
               }
               Some(result)
           }
       }, ...
   }
   ```
   采用 `tokio::select!` 的 `biased;` 偏置语法，优先判定 `wait_aborted()`。不仅自己返回 `None` 走向取消收场，还反向确保调用 `tool_ctx.abort_token.abort()`，保证工具内部的流式读取和子进程守卫立即收到终止通知。
4. **无空令牌与无丢失判定**：`abort_token` 统一由 `AbortToken::new()` 实例化并克隆进 `ToolContext`，不存在 `Option<AbortToken>` 留空分支，全生命周期引用计数由 `Arc` 安全持有。

### 2.2 `shell_exec.rs`：`kill_on_drop(false)` 拔除与 `ProcessTreeGuard` 深度审计

#### 1. `kill_on_drop` 语义彻底修复
在历史版本中，部分普通子进程创建为了防止异常 Drop 误杀设置了 `kill_on_drop(false)`，导致进程在外部取消或异常崩溃时脱离宿主变成系统孤儿僵尸进程。
* **同步路径**（[shell_exec.rs:288-292](file:///c:/Software/conex/crates/agent-tools/src/tools/shell_exec.rs#L288-L292)）：
  ```rust
  // BC03-1：废除普通分支的 kill_on_drop(false)，同步路径置为 true
  if mode == ShellMode::Daemon || mode == ShellMode::AutoBackground {
      child_cmd.kill_on_drop(false);
  } else {
      child_cmd.kill_on_drop(true);
  }
  ```
* **流式路径**（[shell_exec.rs:487-488](file:///c:/Software/conex/crates/agent-tools/src/tools/shell_exec.rs#L487-L488)）：
  ```rust
  // BC03-1：废除普通分支的 kill_on_drop(false)，置为 true
  .kill_on_drop(true);
  ```
核查确认：仅有在显式声明为后台守护任务（`Daemon` / `AutoBackground`）并且将进程所有权成功移交（adopt）给 `BackgroundTaskManager` 的转移点（[shell_exec.rs:335, 416](file:///c:/Software/conex/crates/agent-tools/src/tools/shell_exec.rs#L335)），才显式调用 `guard.disarm()` 并解除限制；所有常规执行路径均被设置为 `kill_on_drop(true)`。

#### 2. 跨平台 `ProcessTreeGuard` 物理进程树硬杀守卫
针对 Windows 下 `taskkill /F /T` 存在进程启动延迟、子进程可能逃逸以及 Unix 下孤儿孙进程无法级联被杀的系统级顽疾，设计并落地了 `ProcessTreeGuard`（[shell_exec.rs:91-254](file:///c:/Software/conex/crates/agent-tools/src/tools/shell_exec.rs#L91-L254)）。

* **Windows：匿名内核作业对象（Job Object）**
  * 在子进程 spawn 完成获取 PID 后，立即调用 Win32 原生 API `CreateJobObjectW(NULL, NULL)` 创建未命名作业对象；
  * 配置 `JOBOBJECT_EXTENDED_LIMIT_INFORMATION`，将 `LimitFlags` 写入 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE (0x2000)`；
  * 通过 `OpenProcess` 取得目标子进程句柄并调用 `AssignProcessToJobObject` 将其加入作业对象；
  * **硬杀威力**：一旦调用 `terminate_now()` 或 Guard 触发 `drop()`，立即执行 `TerminateJobObject(job, 1)`。Windows 内核会在 $<1\text{ms}$ 级别直接硬杀该作业对象下的整棵进程树（包括由 cmd/powershell 派生的 Python、Node、npm 等所有孙进程），即使主进程死锁，只要句柄随进程关闭，内核也会自动清理整个作业对象。
* **Unix：进程组 Leader 与 -PGID 信号**
  * 在 `child_cmd.pre_exec` 中通过 `setpgid(0, 0)` 将子进程设置为其所属新进程组的 Leader；
  * 终止时，向 `-PGID` 投递 `SIGKILL (9)`，瞬间广播抹杀整个进程组的所有派生进程；
  * 结合 `terminate_process_tree` 作为备用通道重试收尾。
* **RAII 兜底（[shell_exec.rs:240-254](file:///c:/Software/conex/crates/agent-tools/src/tools/shell_exec.rs#L240-L254)）**：
  ```rust
  impl Drop for ProcessTreeGuard {
      fn drop(&mut self) {
          if !self.disarmed {
              self.terminate_now();
          } else { ... }
      }
  }
  ```
  只要任务未显式 disarm 并转交后台管理器，任何异常 unwinding、超时退出或取消 drop 都会触发 `terminate_now()`，彻底消灭孤儿进程。

  ```rust
  pub fn broadcast_abort(&self, subagent_run_id: &str) -> bool {
      let mut triggered = false;
      if let Ok(map) = self.signals.read() {
          if let Some(sig) = map.get(subagent_run_id) {
              sig.abort();
              triggered = true;
          }

      if self.control.broadcast_abort(subagent_run_id) {
  ```

## 三、安全点 Trace 与用户终止原因保全审计

安全点检查位于 Provider 流消费结束与工具批执行等生命周期交界处（[crates/session-loop/src/safe_point.rs](file:///c:/Software/conex/crates/session-loop/src/safe_point.rs)）。

### 3.1 排空总线优先于短路判定原则
**核心隐患防范**：历史设计中，若先检查 `abort_signal.is_aborted()` 为 true 就直接短路返回，会导致由前端 UI、用户交互或外部系统投递进 `ControlBus` 的控制意图（`ControlIntent`）及其携带的人类可读中止原因被丢弃，更会导致审计追踪流（`bus.take_trace()`）丢失关键事件记录。

**当前代码实现（[safe_point.rs:158-167](file:///c:/Software/conex/crates/session-loop/src/safe_point.rs#L158-L167)）**：
```rust
pub fn apply_safe_point_control(
    bus: &mut ControlBus,
    abort_signal: Option<&AbortSignal>,
) -> Option<ControlAction> {
    let is_aborted = abort_signal.map(|s| s.is_aborted()).unwrap_or(false);
    let signal_reason = abort_signal.and_then(|s| s.reason());

    // 无论信号是否置位，首先排空总线聚合动作，确保 intent 和 trace 不丢失
    let drain_action = bus.drain_as_action();
    ...
```
* **绝对单真理消费**：无论 `abort_signal` 当前是否已处于中止态，必须先执行 `bus.drain_as_action()`。该调用将总线内累积的所有意图排空并归档到内部 Trace 列表（`bus.trace`）。
* **单测刚性守卫（[safe_point.rs:478-503](file:///c:/Software/conex/crates/session-loop/src/safe_point.rs#L478-L503)）**：
  在 `drain_priority_over_short_circuit_preserves_reason_and_trace` 测试中，同时设置总线 `request_force_cancel("ui-force-cancel", "ui")` 与 `signal.abort()`，断言返回的有效原因依然是 `"ui-force-cancel"`，并且 `bus.take_trace()` 长度严格等于 1，验证了即使信号抢先触发，总线内的轨迹也绝不丢失。

### 3.2 拒绝出现 `reason: None` 与多级回退保全
在 [safe_point.rs:168-230](file:///c:/Software/conex/crates/session-loop/src/safe_point.rs#L168-L230) 中，针对所有动作匹配分支建立了无死角的原因保全闭环：

```rust
match drain_action {
    ControlDrainAction::ForceCancel { reason, .. } => {
        let effective_reason = reason
            .or(signal_reason)
            .or_else(|| {
                if is_aborted {
                    Some("aborted_by_signal".into())
                } else {
                    Some("force_cancel".into())
                }
            });
        Some(ControlAction::ForceCancel {
            reason: effective_reason,
        })
    }
    ControlDrainAction::CooperativeStop { reason, pending_messages, .. } => {
        if is_aborted {
            // 提升为 ForceCancel，但保留原始 stop reason
            let effective_reason = reason
                .or(signal_reason)
                .or_else(|| Some("aborted_with_stop_intent".into()));
            Some(ControlAction::ForceCancel {
                reason: effective_reason,
            })
        } else {
            Some(ControlAction::CooperativeStop { reason, pending_messages })
        }
    }
    ControlDrainAction::SoftInject { steer_messages, follow_up_messages, .. } => {
        if is_aborted {
            let effective_reason = signal_reason.or_else(|| Some("aborted_with_pending_inject".into()));
            Some(ControlAction::ForceCancel {
                reason: effective_reason,
            })
        } else {
            Some(ControlAction::SoftInject { steer_messages, follow_up_messages })
        }
    }
    ControlDrainAction::None => {
        if is_aborted {
            let effective_reason = signal_reason.or_else(|| Some("aborted_by_signal".into()));
            Some(ControlAction::ForceCancel {
                reason: effective_reason,
            })
        } else {
            None
        }
    }
}
```

#### 保全判定分析：
1. **显式原因优先**：总线中携带的用户自定义原因（如 `"用户点击停止按钮"`）处于最高优先级；
2. **信号原因次级保全**：若总线未传原因，但 `abort_signal.abort_with_reason("custom reason")` 携带了原因，则使用信号原因；
3. **确定性标识兜底**：在纯匿名中止场景下，根据触发上下文分别回退至 `"aborted_by_signal"`、`"force_cancel"`、`"aborted_with_stop_intent"`、`"aborted_with_pending_inject"`；
4. **穷举断言**：在全部匹配分支中，只要产出 `ControlAction::ForceCancel`，其内部字段 `reason` 恒为 `Some(String)`，数学上消灭了 `ForceCancel { reason: None }`。

```rust
        token: String,
        frozen_seq: u64,
        truncate_reserved_seq: u64,
    },
}
```

* **Phase 1（Freezing 收敛期）**：向各 Run 发送 L3 强停，等待并发执行中的流安全收口。在此窗口期，为使当前 Run 能够正常发射自身结束标志以安全退场，仅放行自身序号范围内的终态事件（`RunTerminal` 与 `AgentEnd`），阻断其它一切新请求；
* **Phase 2（Frozen 严格物理锁死期）**：当全部 Run 确认终态收敛后，读取数据库当前的 MAX(sequence) 确立严格不可逾越的物理边界 $S_{\text{frozen}}$，同时将预留写入序号锁定为 $S_{\text{truncate}} = S_{\text{frozen}} + 1$。

### 4.2 彻底拔除越界白名单与事件写门禁核查
在重构前，代码中曾存在伪撤离白名单，允许 `RunTerminal` 或 `AgentEnd` 跨过冻结边界越界写入，导致撤回后时间线在截断点之后依然能收到旧 Run 的终态污染事件，破坏了撤回单调性。

**重构后实现（[freeze.rs:362-367](file:///c:/Software/conex/crates/session-loop/src/freeze.rs#L362-L367)）**：
```rust

}
```
`RunTerminal` 与 `AgentEnd` 被彻底从撤离事件白名单中拔除！

**写门禁刚性拦截实现（[freeze.rs:288-334](file:///c:/Software/conex/crates/session-loop/src/freeze.rs#L288-L334)）**：
```rust
SessionFreezeState::Frozen {
    token: valid_token,
    frozen_seq,
    truncate_reserved_seq,
} => {
    // 物理上界铁律：
    // 1. 唯一允许 sequence > frozen_seq 的事件，必须且只能是携带正确 token 的 TimelineTruncate 本身！
    if matches!(event, conex_types::events::AgentEvent::TimelineTruncate { .. }) {
        if token == Some(valid_token.as_str()) && proposed_seq == *truncate_reserved_seq {
            return WriteVerdict::Allow;
        }
    }
    // 2. 其它任何事件，如果序号大于 frozen_seq，无论是否叫 RunTerminal / AgentEnd，统统无条件硬性阻断！
    if proposed_seq > *frozen_seq {
        return WriteVerdict::Reject {
            frozen_seq: *frozen_seq,
        };
    }
    WriteVerdict::Allow
}
```

## 六、综合审计结论

经过对 `session-loop`、`agent-tools`、`orchestrator` 核心源码及测试现场的深度审计，得出以下确定性结论：

1. **进程管理零孤儿泄漏**：
   通过彻底拔除普通同步与流式执行的 `kill_on_drop(false)`，结合 Windows 匿名 Job Object（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）与 Unix PGID SIGKILL 的 `ProcessTreeGuard`，实现了对子进程及其所有后代孙进程的内核级 RAII 级联强杀。
2. **信号与令牌刚性穿透**：
   `exec_single.rs` 将会话 Run 级 `AbortSignal` 与工具级 `AbortToken` 进行了双向监听与原子绑定，审批通道与流式状态机零轮询响应中止通知，彻底消灭了空令牌与信号丢弃。
3. **控制观测完整保全**：
   安全点执行严格遵循“先排空总线、后判定短路”的原则，保证了用户意图与 Trace 轨迹的 100% 入队；多级原因回退机制从根本上杜绝了 `reason: None`。
4. **撤回物理上界绝对锁死**：
   两阶段冻结守卫成功清除了 `RunTerminal` 与 `AgentEnd` 的越界后门，确立了 $S_{\text{frozen}}$ 严格单调上界，唯独放行携带合法令牌且严格位于 $S_{\text{frozen}} + 1$ 的 `TimelineTruncate`，保证了时间线撤回时空维度的绝对自洽。
