### 2.1 彻底拔除硬编码 `generation = 1`

在历史实现中，`CompactionEngine` 内部在组装新摘要块时存在写死 `generation = 1` 的隐患，导致无论会话经历了多少轮压缩，生成的块 ID 恒为 `compacted-summary-1-1`。

当前实现（[`crates/conex-compaction/src/engine.rs:43-59, 387-412`](file:///c:/Software/conex/crates/conex-compaction/src/engine.rs#L43-L59)）彻底消除了该问题：
1. **结构与构造器扩展**：`CompactionEngine` 引入 `generation: Option<u32>` 字段，并提供 `new_with_generation(max_tokens, gen)` 与 `with_generation(gen)` 链式注入接口；
2. **块 ID 生成逻辑**：
   ```rust
   // crates/conex-compaction/src/engine.rs:387-412
   let chain_count = messages[..cut]
       .iter()
       .filter(|m| m.id.starts_with("compacted-summary"))
       .count();
   let generation: u32 = self.generation.unwrap_or_else(|| {
       // 未显式注入时：沿用链中最新既有摘要块的 generation，或默认为 1
       messages[..cut]
           .iter()
           .filter(|m| m.id.starts_with("compacted-summary"))
           .filter_map(|m| {
               let parts: Vec<&str> = m.id.split('-').collect();
               if parts.len() >= 4 {
                   parts[2].parse::<u32>().ok()
               } else {
                   None
               }
           })
           .next_back()
           .unwrap_or(1)
   });
   let fold_index = chain_count + 1;
   let block_id = format!("compacted-summary-{generation}-{fold_index}");
   ```
3. **单调自增验证**：单元测试 [`test_explicit_generation_generates_correct_block_id`](file:///c:/Software/conex/crates/conex-compaction/src/engine.rs#L793) 证实，注入 generation=3 时，生成的块 ID 准确为 `compacted-summary-3-1`，且消息元数据 `metadata.summary.generation` 与 `plan.generation` 100% 保持为 3。

  ```rust
  pub(crate) fn next_generation(&self, conversation: &[Arc<AgentMessage>]) -> u32 {
      let mut max_gen = self.current_generation;
      for m in conversation {
          if m.id.starts_with("compacted-summary") {
              let parts: Vec<&str> = m.id.split('-').collect();
              if parts.len() >= 4 {
                  if let Ok(g) = parts[2].parse::<u32>() {
                      max_gen = max_gen.max(g);
                  }
              }
          }
          if let Some(meta) = &m.metadata {
              if let Some(g) = meta
                  .get("summary")
                  .and_then(|s| s.get("generation"))
                  .and_then(|v| v.as_u64())
              {
                  max_gen = max_gen.max(g as u32);
              }
          }
      }
      max_gen + 1
  }
  ```

```typescript
export function anchorHistoryToLatestSummary(
  messages: readonly SessionMessage[] | undefined | null

  if (!messages || messages.length === 0) return [];

  let lastSummaryIdx = -1;

      msg &&

  }

  }

    } else {

      const isCompacted =
        msg.id.startsWith('compacted-summary') ||
        Boolean((msg.metadata as Record<string, unknown> | undefined)?.isCompactedSummary);
      if (isSystem || isCompacted) {
        result.push(msg);
      }
    }
  }
  return result;
}
```

## 六、 维度五：FastBpeTokenizer、双阈值水位与双向原子截断

### 6.1 FastBpeTokenizer 与 CJK 1.45 加权机制

大模型分词器（BPE / SentencePiece）处理中文字符时，一个汉字通常拆分为 1~2 个 Token（平均约 1.35 ~ 1.55 Tokens）。若按传统 1 字符 = 1 Token 计算，在长中文对话场景下将产生高达 30%~50% 的严重低估，极易导致实际发送给 Provider 时突发 400 Context Overflow。

在 [`crates/conex-compaction/src/tokens.rs`](file:///c:/Software/conex/crates/conex-compaction/src/tokens.rs) 中：
1. **CJK 表意文字加权**：
   ```rust
   // crates/conex-compaction/src/tokens.rs:184-187, 203-205
   } else if is_cjk(ch) {
       cjk_points += 145;
       i += 1;
   }
   if cjk_points > 0 {
       tokens += cjk_points.div_ceil(100);
   }
   ```
   1000 个汉字估算为 1450 Tokens，单元测试 [`test_cjk_145_weighting`](file:///c:/Software/conex/crates/conex-compaction/src/tokens.rs#L295) 确证 4 汉字折算为 6 Tokens（$4 \times 1.45 = 5.8 \to 6$）；
2. **全角标点与 Emoji**：全角标点按 1.20 加权（120 points），Emoji 符号按 2.50 加权（250 points）；
3. **空白折叠与符号聚类**：连续空格/制表符按 4 字符 1 Token 折叠；聚类 2~4 字符的复合符号（如 `": "`、`","`、`{"`、`===`、`::` 等），避免 JSON 格式产生 300% 虚假高估；
4. **Wire Framing 协议开销**：单条消息基础 Framing 4 Tokens（`<|im_start|>role...<|im_end|>`），工具调用/回执追加 8 Tokens 协议封包开销，估算完全贴合真实 Wire 成本。

### 6.2 85% / 95% 双阈值水位调度模型

在 [`crates/conex-compaction/src/thresholds.rs`](file:///c:/Software/conex/crates/conex-compaction/src/thresholds.rs)：
- **`UnderBudget`（$< 85\%$）**：会话在预算安全区内，直接平滑早退，不触发任何压缩，保护大模型前缀 KV Cache 命中率；
- **`Regular`（$85\% \sim 95\%$）**：触发后台异步预热摘要任务，不阻塞当前轮次回复；
- **`Critical`（$\ge 95\%$）**：同步硬防御门禁，在消息发出前执行确定性物理压缩截断，坚决阻止 400 Context Window Exceeded。

### 6.3 TurnBatch 双向完整性原子截断闭包算法

工具调用与工具回执在上下文交互中具有强因果依赖。若切割点不慎落在 `ToolCall` 与 `ToolResult` 之间，或者切在并发调用（ToolBatch）的中途，大模型 API 将因收到孤儿 `ToolResult` 或未闭合的 `tool_call_id` 抛出 400 校验异常。

[`crates/conex-compaction/src/cut_point.rs:32-126`](file:///c:/Software/conex/crates/conex-compaction/src/cut_point.rs#L32-L126) 实现了双向完整性闭包算法 `enforce_tool_batch_closure`：
1. **向前闭包（Result $\to$ Call）**：若保留段内存在孤儿 `ToolResult`，循环向前回溯直到覆盖产生该调用的 Assistant 消息（索引 $j \ge fold\_start$）；
2. **向后闭包（Call $\to$ Results）**：若保留段内声明了某些 `call_id`，但其对应的部分 `ToolResult` 落在丢弃段（$real\_idx < cut$），算法立即向前扩展 `cut` 直至完全包含这组 `ToolResult`；
3. **不可分批原子性**：测试 [`test_turn_batch_no_orphan_calls_across_generations`](file:///c:/Software/conex/crates/conex-compaction/tests/cut_point_tests.rs#L684) 证实：当预算仅能容纳批次中第二个回执及后续消息时，算法不会将批次从中间切开，而是原子闭包将前序调用整体拉入保留段，或者安全放弃压缩。
