# 诊断方向 07：可观测性与运维

## 检查目标
评估日志体系、监控指标、健康检查、可调试性和生产运维能力。

## 检查清单

### 7.1 日志体系
- [ ] 是否有结构化日志（JSON 格式、log levels）而非纯 console.log/error/warn
- [ ] 日志级别（debug/info/warn/error/fatal）是否正确使用
- [ ] 敏感信息过滤——SecretRedactor 是否覆盖日志输出的所有调用点
- [ ] daemon 写 stdout 是否与 WebSocket 数据流混合
- [ ] 前端日志是否有循环缓冲区用于事后排查
- [ ] 各组件的日志输出格式是否统一

### 7.2 指标监控
- [ ] RuntimeMetricsCollector 的 snapshot 是否周期 flush
- [ ] 是否有 Prometheus 端点或 OpenTelemetry 导出（当前缺失）
- [ ] 关键业务指标：tool 调用频率、token 消耗、会话持续时间、provider 错误率
- [ ] 指标是否有可视化仪表盘
- [ ] daemon 端 `lifecycle.recordError` 是否替代了 console.error

### 7.3 健康检查
- [ ] daemon 是否有 HTTP/WebSocket 健康检查端点（当前仅 WebSocket `get-status`）
- [ ] `get-status` 是否反映各组件真实健康状态（provider 连通性、event store 可用性）
- [ ] 前端 daemon 不可用时的降级 UI 提示
- [ ] Tauri shell 对 daemon sidecar 的健康轮询

### 7.4 追踪与调试
- [ ] 请求链路是否有唯一 Trace ID（当前 `sessionId` 被复用为 `traceId`）
- [ ] 分布式追踪：WebSocket 消息 → orchestrator → runtime → provider 调用是否可追溯
- [ ] 错误报告中包含足够的上下文（sessionId、runId、事件序列号）
- [ ] JSONL 事件存储是否可作为审计日志和调试依据
- [ ] 是否有审计日志查询/导出工具

### 7.5 部署与运维
- [ ] daemon 进程管理（systemd/PM2/内置守护）
- [ ] Dockerfile / docker-compose 用于容器化部署（当前缺失）
- [ ] JSONL 文件是否有轮转和大小限制（当前缺失——单文件无限制增长）
- [ ] 配置变更是否支持热重载
- [ ] 是否有数据备份机制（事件存储、配置文件）
- [ ] daemon 是否仅记录最近一次错误（`recentError` 覆盖，缺乏持久化错误历史）
- [ ] Docker 容器化支持

## 检查方法
- `rg "console\.(log|warn|error|info)" packages/ -g "*.ts" | grep -v "\.test\." | head -40` 统计日志使用
- 审查 RuntimeMetricsCollector 的 snapshot/export 数据流向
- 审查 daemon 启动后的端口暴露情况
- 检查 `.env.example` 等运维文档是否存在
- 搜索 traceId/requestId/correlationId 的生成与传递
