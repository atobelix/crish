# 诊断方向 04：性能与资源利用

## 核心原则
- **性能为王**：一切有利于性能提升的改进均可纳入考量
- **CPU 优先**：优化以 CPU 热点路径为主
- **GPU 为辅**：高收益场景可追加 GPU 优化（如编码、并行计算）
- **设备一致性**：低/中/高设备的表现必须一致，不允许高端独占优化

## 检查清单

### 4.1 CPU 热点路径
- [ ] LLM token 流向管道的完整链路中，哪些步骤消耗 CPU（序列化、反序列化、投影、脱敏）
- [ ] context-compression 的全量序列化频率——每次 token 估算是否全量遍历，`messageTokenCache` / `blockCharCache` 的命中率
- [ ] provider-gateway 的 route 克隆——`cloneRouteOffer` 等是否在每次请求都做 deep clone
- [ ] 数据查找复杂度——session、tool、run 查找是否 O(1)（Map/Record vs Array.find）
- [ ] 数组操作链——热路径中 filter/map/reduce 链是否创建过多中间数组
- [ ] JSON 序列化/反序列化——`JSON.parse`/`stringify` 在热路径上的调用频率和数据量
- [ ] Token 估算的缓存命中率（`messageTokenCache` WeakMap 是否有效）
- [ ] immer proxy 开销——简单赋值是否误走了 immer 的 proxy 链路

### 4.2 低中高设备一致性
- [ ] 大型会话（1000+ messages）在前端中低端设备上的滚动/渲染性能
- [ ] 虚拟列表在低端设备上是否降级为普通列表
- [ ] 渐增渲染（incremental rendering）在慢 CPU 上的表现
- [ ] LLM 流式响应的渲染帧率在低端设备上是否可接受
- [ ] 大量 tool call 输出的渲染是否具备懒加载/分页机制
- [ ] 前端 bundle 体积是否导致中低端设备加载过慢
- [ ] Web Worker 在低端设备上的创建耗时与内存开销

### 4.3 渲染性能
- [ ] Zustand store selector 粒度——是否因过粗 selector 导致不必要重渲染
- [ ] React.lazy 拆分粒度——每个 icon 单独拆分的网络开销是否合理
- [ ] CSS 模块数量对首屏渲染的影响
- [ ] 图片/字体资源的懒加载与预加载策略
- [ ] 消息列表使用虚拟滚动还是全量渲染

### 4.4 内存管理
- [ ] 无界增长的数据结构（Set、Map、数组）在长运行周期中的增长情况
- [ ] 事件监听器的注册与取消是否完全配对
- [ ] Web Worker 池的创建策略（懒加载 vs 预创建、销毁策略）
- [ ] pending request map 在 WebSocket 断连时是否彻底清理
- [ ] WeakMap/WeakRef/WeakSet 的使用是否能覆盖关键缓存场景
- [ ] BoundedMap / LruMap 的淘汰策略是否适配实际访问模式

### 4.5 I/O 效率
- [ ] localStorage 操作是否在同步上下文中阻塞主线程
- [ ] JSONL 事件存储的写入是否使用批量/缓冲机制（JsonlAppendBatcher flush 间隔）
- [ ] 文件读取是否使用流式接口处理大文件
- [ ] 网络请求（LLM API）的并发控制与连接复用
- [ ] daemon 端 JSONL 文件是否有轮转和大小限制

### 4.6 缓存策略
- [ ] LLM API 响应的缓存（相同 prompt 是否可 cache hit）
- [ ] 上下文压缩结果的跨会话缓存（`structuredSummaryCacheKey` 已生成但从未读取）
- [ ] 前端 API 调用是否有 SWR/stale-while-revalidate 策略
- [ ] 数据获取是否有去重（deduplication）机制防止并行重复请求
- [ ] shared-utils 缓存工具（BoundedMap、LruMap）在核心路径上的覆盖率

### 4.7 Bundle 与加载性能
- [ ] lucide-react 的导入方式 (`import * as` vs 命名导入) 是否支持 tree-shaking
- [ ] highlight.js 的语言子集是否最小化
- [ ] 字体包数量（inter、jetbrains-mono、ibm-plex-sans、ibm-plex-mono）是否全部必要
- [ ] 构建产物是否有 size-limit / bundle 分析
- [ ] 代码拆分（manualChunks）策略是否对中低端设备友好

## 检查方法
- 在低/中/高三档设备上运行典型操作录制性能 profile
- 使用 Chrome DevTools Performance 录制：发送消息、切换会话、打开大型会话
- 在 daemon 热路径插入性能计数器
- 使用 `--inspect` 堆快照分析内存泄漏
- bundle visualizer 分析重复代码与大型依赖
- 数据结构复杂度审计：对所有 O(n) 查找操作做标记
- 在 CI 中加入性能回退检测
