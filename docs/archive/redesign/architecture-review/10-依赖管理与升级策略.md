# 诊断方向 10：依赖管理与升级策略

## 检查目标
评估第三方依赖健康状况、版本管理策略、升级路径及依赖中的潜在风险。

## 检查清单

### 10.1 依赖健康状况
- [ ] 所有依赖的 current vs latest 版本差距（`npm outdated`）
- [ ] 直接依赖数量是否可控
- [ ] Dev dependencies 误放：`@types/dompurify` 在 dependencies（应为 devDependencies）
- [ ] 低维护风险依赖：`@chenglou/pretext@0.0.8`

### 10.2 大型依赖审查
- [ ] lucide-react 导入方式：`import * as Lucide` (53 处) vs `import { ChevronDown }` (1 处)——tree-shaking 失效
- [ ] highlight.js：已正确使用 core + 9 个语言子集，无需替换
- [ ] 字体包数量：inter + jetbrains-mono 必要，ibm-plex-sans + ibm-plex-mono 是否必要
- [ ] immer 是否可部分替换为原生 immutable 操作
- [ ] dompurify 是否仍被使用（存在于依赖但未搜索到引用）

### 10.3 版本策略
- [ ] lock file 存在（package-lock.json + Cargo.lock）
- [ ] 版本范围是否过于宽松（`^x.y.z`）
- [ ] 内部包版本引用不统一：
  - `"file:../xxx"`（多数）
  - `"*"`（agent-runtime → decision-engine）
  - `"0.1.0"`（decision-engine → shared-types）
- [ ] `ws` 库版本不一致（根 `^8.21.0` vs agent-daemon `^8.18.0`）

### 10.4 安全漏洞
- [ ] Dependabot/Renovate 配置（当前缺失）
- [ ] `npm audit` / `cargo audit` 结果
- [ ] 间接依赖中的 ws CVE
- [ ] `@modelcontextprotocol/sdk` 新依赖需监控

### 10.5 升级路径
- [ ] TypeScript 7 升级的 breaking changes 评估（`erasableSyntaxOnly`、`isolatedDeclarations`）
- [ ] React 19 新 API 利用：`use()`、`useActionState`、`useOptimistic`（当前未使用）
- [ ] Vite 7 → 8 升级兼容性
- [ ] Zustand 5 API 适配确认（`create` 默认导出变更）

### 10.6 内部依赖管理
- [ ] 内部包版本一致性（全部 `0.1.0`，无冲突）
- [ ] `file:` 引用统一改为 `workspace:` 协议
- [ ] 共享类型变更的波及面控制

## 检查方法
- `npm outdated` / `npm audit` 在根和各 package 运行
- 审查每个依赖在源码中的 import 频率
- 计算依赖安装大小
- 审查 package.json 的 dependencies vs devDependencies 分类
- 搜索 Renovate/Dependabot 配置是否存在
- `Get-ChildItem -Path "apps/crish-desktop/src" -Filter "*.tsx" -Recurse | ForEach-Object { Select-String -Path $_.FullName -Pattern 'import.*\*.*Lucide' }` 统计
