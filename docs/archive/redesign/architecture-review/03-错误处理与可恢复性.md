# 诊断方向 03：错误处理与可恢复性

## 检查目标
评估系统各层的错误处理策略、异常传播路径、故障恢复机制和容错设计。

## 检查清单

### 3.1 空 catch 块审计
- [ ] 全局搜索 `catch { }`、`catch { /* */ }`、`catch () => {}` 模式，统计每处的业务合理性
- [ ] 所有 `.catch(() => {})` Promise 链末端
- [ ] 空 catch 是否有注释说明为什么可以静默吞掉
- [ ] 是否存在必须记录日志但被 silent 吞掉的场景
- [ ] 检测命令：`rg "catch\s*\{" packages/ -g "*.ts" | grep -v "node_modules\|dist"`

### 3.2 错误类型体系
- [ ] 是否一致使用 `CrishError` 层次结构（code/category/retryable/metadata）
- [ ] 是否存在 `throw new Error("...")` 替代 `throw new ProviderError(...)` 的情况
- [ ] 检测命令：`rg "throw new Error" packages/ -g "*.ts" | grep -v "\.test\."`

### 3.3 错误传播路径
- [ ] WebSocket 连接错误的传播——从网络断开到前端 UI 提示的完整链路
- [ ] LLM 调用失败是否影响会话可用性——是局部失效还是会话整体崩溃
- [ ] 组件渲染错误是否有 Error Boundary 兜底且可恢复
- [ ] EventBus handler 异常是否影响其他监听器——`emit()` 中的 `console.error` 是否足够

### 3.4 故障恢复
- [ ] WebSocket 断线重连后的 session 状态恢复
- [ ] daemon sidecar crash 后自动重启及 orchestrator 状态重建
- [ ] 前端 localStorage 损坏后的降级行为
- [ ] JSONL 事件存储损坏/缺失的处理——是否有校验和恢复
- [ ] 会话 checkpoint/rollback 机制的可靠性（JSONL 损坏场景测试）

### 3.5 超时处理
- [ ] LLM 请求超时后的重试策略（退避算法、最大重试次数）
- [ ] WebSocket 心跳超时检测与断线判定（ConnectionManager vs daemonClient 两套策略是否冲突）
- [ ] 工具执行超时后的取消链路
- [ ] OperationQueue 的 pending operation 是否有超时兜底
- [ ] 用户操作超时（如 tool approval 等待）的反馈

### 3.6 全局异常兜底
- [ ] `window.onerror` / `window.onunhandledrejection` 处理器
- [ ] daemon 进程的 `process.on('uncaughtException')` / `process.on('unhandledRejection')`
- [ ] Tauri Rust 端的 panic 恢复
- [ ] 以上兜底仅记录日志而不影响进程存活
- [ ] ServiceRegistry 启动时序——单 service 启动失败是否阻塞整个系统
- [ ] `bootstrap-services.ts` 中 fire-and-forget 的 `.catch(() => {})` 是否合理

### 3.7 关键路径恢复验证
- [ ] `beforeunloadFlush` 在页面关闭时是否完整持久化
- [ ] EventStore 的 `afterSequence` 恢复逻辑是否正确处理中断
- [ ] daemon 端 `messageTasks` 的 Promise 失败是否被处理
- [ ] `CrossTabCoordinator` leader 选举失败 / 瞬断的恢复

## 检查方法
- grep 搜索 `catch {`、`catch () {`、`.catch(` 等模式，标注每处的合理性
- 模拟 WebSocket 断线、daemon 重启、localStorage 清空等场景测试恢复逻辑
- 审查 Error Boundary 的层级覆盖——哪些组件没有独立 Error Boundary
- 审查 `CrishError` 层次在各包的引用一致性
