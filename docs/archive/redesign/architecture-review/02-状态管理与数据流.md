# 诊断方向 02：状态管理与数据流

## 检查目标
评估前端状态管理架构、前后端状态同步机制、数据流向的合理性，以及状态一致性问题。

## 检查清单

### 2.1 前端状态架构
- [ ] Zustand store 划分：layoutStore 管理 workspace + session + settings + diffs + telemetry 是否应拆分
- [ ] 4-store 双向同步风险：bootstrapStores 的 syncLayoutToSession/syncSessionToLayout 等 6 个同步函数是否导致状态震荡
- [ ] activeSyncs Set 防循环机制是否覆盖所有回写路径
- [ ] Zustand selector 精度：是否存在因 selector 返回新对象/数组导致的不必要重渲染
- [ ] immer 中间件开销：简单赋值操作是否误走了 proxy 链路
- [ ] store 的 persist 策略——哪些状态应持久化、哪些可重建
- [ ] barrel store/index.ts 的导入是否导致所有 store 被同时加载

### 2.2 前后端状态同步
- [ ] UI session state vs daemon event store 数据一致性保障
- [ ] 会话 metadata 在 UI/daemon/event store 三个副本间谁为真相源
- [ ] 同步冲突时谁优先
- [ ] 离线/重连后的状态恢复逻辑
- [ ] SessionSyncService 的 localVersion 冲突策略是否覆盖所有字段类型
- [ ] 前端三层状态架构（Zustand → localStorage → disk mirror）的同步延迟

### 2.3 事件驱动数据流
- [ ] EventBus 是全局单例还是可隔离实例——是否可测试
- [ ] EventBus `EventHandler: (payload: any)` 无类型约束的风险
- [ ] 事件订阅取消机制是否在所有 useEffect 中使用
- [ ] 跨标签页通信（CrossTabCoordinator）的 leader 瞬断间隙状态同步
- [ ] leader 选举是否有租约机制，还是仅靠心跳刷新

### 2.4 数据一致性保障
- [ ] 前端 optimistic update 失败后的回滚机制
- [ ] 操作序列号/版本号机制避免陈旧覆盖（SessionSyncService）
- [ ] daemon 端 EventStore 的 afterSequence 恢复逻辑
- [ ] 写冲突检测（tool approval 等并发场景）
- [ ] data 校验在边界层统一做还是分散在各消费者中
- [ ] OperationQueue 按 session 隔离的 FIFO 是否有超时兜底

### 2.5 存储冗余审计
- [ ] localStorage keys 清单：crish_session_index_v1, crish_session_body_v1:*, crish_active_session_v1, crish_session_disk_mirror_v1
- [ ] 同一份数据（如 session list）在多少个存储位置存在副本
- [ ] storage quota 超限的降级策略
- [ ] 页面关闭前 beforeunloadFlush 的数据完整性

## 检查方法
- 追踪一次用户操作的完整数据流（键入消息 → store → localStorage → daemon → event store → 回显）
- 绘制 store 间 import 依赖图，标注循环依赖
- 在 bootstrapStores 的 subscribe 回调中插入计数器，测量单次外部操作触发的 store 更新级联次数
- 审查 EventBus 的 emit/on 调用，检查事件名规范性和 payload 类型安全
