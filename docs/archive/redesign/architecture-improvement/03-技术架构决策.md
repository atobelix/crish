# 技术架构决策（Architecture Decision Records）

> 本文记录方案中涉及的关键架构决策，每个 ADR 包含：背景、决策、后果、替代方案。

---

## ADR-001：配置契约表作为唯一真相源

| 字段 | 内容 |
|------|------|
| **状态** | **已批准** |
| **背景** | UI 上每个可配置项的写入目标和生效时机不明确，存在多处 dead code、fake wiring 和双轨配置。子 agent 经常发明新的 localStorage key 而不文档化。 |
| **决策** | 建立全局配置契约表（`docs/CONFIG-CONTRACT.md`），统一使用写入目标枚举：`UI-ONLY` / `LS` / `ENGINE-CONFIG` / `ENGINE-SCOPED` / `ENGINE-RUN` / `ENGINE-WORKFLOW` / `ENGINE-MCP` / `DEAD` / `HONEST-HIDE`。任何改设置的 PR 必须对照本表。 |
| **后果** | - 正：所有配置路径可追踪，子 agent 无法新增 `crish_*` key 而不更新契约表<br>- 负：需要维护额外的文档 |
| **替代方案** | 无正式契约，继续当前模式 → 拒绝（已证明不可持续） |

## ADR-002：保持 UI JSONL 为会话真相源（不统一为 daemon-only）

| 字段 | 内容 |
|------|------|
| **状态** | **已批准（产品策略）** |
| **背景** | 当前 UI 会话正文（JSONL）为真相源，daemon event store 仅补充元数据。有人提议统一为 daemon 作为唯一真相源。 |
| **决策** | 保持现有产品策略：UI JSONL 为主，daemon 补元数据。不统一为 daemon-only。 |
| **后果** | - 正：离线可用，local-first，daemon crash 不影响已存会话<br>- 负：需要维持三副本一致性策略（UI/daemon/event store）<br>- 需文档化此决策，防止子 agent 误改 |
| **替代方案** | daemon-only → 拒绝（产品策略明确） |

## ADR-003：技能 ID 使用 stableId 算法与 runtime 对齐

| 字段 | 内容 |
|------|------|
| **状态** | **已批准（方案 A）** |
| **背景** | 桌面端使用 `skill-file:${filePath.normalized}` 作为技能 ID，与 runtime 的 `stableId("skill", \`${skill.name}:${skill.filePath}\`)` 不一致，导致技能启用/禁用无效。 |
| **决策** | 桌面生成 id 时与 runtime 一致：ut 使用 `stableId("skill", name:filePath)` 生成 ID。共享算法抽到 `@crish/shared-utils` 或 desktop 复制同一 hash 实现并加单测对照。 |
| **后果** | - 正：桌面与 runtime 技能 ID 一致，启用/禁用真实生效<br>- 负：需迁移旧 localStorage key（`crish_skill_activation_v1`） |
| **替代方案** | **方案 B：** 文件发现记录在 merge 时用 path 做二次键 → 拒绝（改 runtime 合并策略，风险大） |

## ADR-004：规则通过 scoped-context 接真实引擎

| 字段 | 内容 |
|------|------|
| **状态** | **已批准** |
| **背景** | 当前 `SettingsPanel` 保存规则到 `crish_settings` only，`run-task` 仅传递 `prompt, sessionId, permissionMode, cwd`，规则未对模型生效。 |
| **决策** | 规则默认接真实引擎（scoped-context），不是仅文案诚实。用户保存规则时同时写入 `upsert-scoped-context`（id: `rule:desktop:global` / `rule:desktop:project`, kind: `rule`）。 |
| **后果** | - 正：规则对模型真实生效，可验证<br>- 负：规则过长可能撑爆 context，需上限截断（如 8k 字符）+ UI 提示 |
| **替代方案** | 仅文案诚实（"规则当前未接入引擎"）→ 拒绝（产品要求规则接真） |

## ADR-005：MCP 仅做诚实 UI，不做完整配置注入

| 字段 | 内容 |
|------|------|
| **状态** | **已批准** |
| **背景** | MCP 的 `start-mcp-server` / `stop-mcp-server` 在 `McpLifecycleManager` 中无此方法，真 MCP 仅在 run 路径拉起。UI 上存在可点击但永远失败的假控件。 |
| **决策** | 本阶段只做诚实 UI：正式模式隐藏或 disabled 启停按钮 + 解释文案。完整配置注入（4.2.2）仅在产品明确要求时单独做。 |
| **后果** | - 正：UI 诚实反映引擎能力，用户不再被假控件误导<br>- 负：功能降级感知，需文案妥善解释 |
| **替代方案** | 实现完整 MCP 配置注入 → 延迟（超出当前阶段范围） |

## ADR-006：commandPermissions 采用 S1 持久化策略

| 字段 | 内容 |
|------|------|
| **状态** | **已批准（默认推荐）** |
| **背景** | commandPermissions 当前仅 Zustand 内存，刷新丢失；与引擎审批策略关系不清。 |
| **决策** | 采用 S1（持久化-only）：写入 `localStorage crish_command_permissions_v1`，UI 标明 "仅影响本机审批快捷放行"。不在当前阶段接引擎审批。 |
| **后果** | - 正：刷新后白名单保持，实现成本低<br>- 负：不与引擎审批策略联动 |
| **替代方案** | S2（移除）→ 备选；S3（真接引擎）→ 超出范围 |

## ADR-007：新增 runtime-api 接口包

| 字段 | 内容 |
|------|------|
| **状态** | **建议** |
| **背景** | 关键服务（DaemonClient、EventBus、ProviderGateway、AgentRuntime、SessionStore）缺少正式接口定义，测试时难以 mock，依赖具象类而非接口。 |
| **决策** | 建议新增 `@crish/runtime-api` 包（或类似命名），统一定义核心服务的 SPI 接口。各包依赖接口而非具象实现。 |
| **后果** | - 正：模块解耦，测试易 mock，接口版本化管理<br>- 负：初期增加抽象层成本 |
| **替代方案** | 不新增接口包，在各包内定义接口 → 可接受但不利于共享和统一管理 |

## ADR-008：日志系统采用 pino 替换 console.log

| 字段 | 内容 |
|------|------|
| **状态** | **建议** |
| **背景** | 当前大量使用 `console.log/error/warn`，无结构化日志，secret redactor 覆盖不完整，daemon stdout 与 WS 数据流混合。 |
| **决策** | 建议引入 `pino` 作为结构化日志库（JSON 格式、log levels、性能优秀）。daemon 端统一 JSON 格式日志，日志写入文件与 WS 数据流分离。 |
| **后果** | - 正：结构化日志可被日志系统消费，敏感信息可统一过滤，日志级别可控<br>- 负：需要迁移大量现有 `console.*` 调用 |
| **替代方案** | `consola` → 功能相似但生态不如 pino；`winston` → 较重；保持 `console.*` → 拒绝（无法满足可观测性需求） |

## ADR-009：内部包引用统一为 workspace: 协议

| 字段 | 内容 |
|------|------|
| **状态** | **建议** |
| **背景** | 当前内部包引用格式混乱：`"file:../xxx"`（多数）、`"*"`（agent-runtime → decision-engine）、`"0.1.0"`（decision-engine → shared-types）。 |
| **决策** | 全部内部包引用统一为 `workspace:*` 协议，依赖安装时由 npm/pnpm/yarn 自动解析。 |
| **后果** | - 正：依赖解析统一，lock 文件一致，减少 phantom dependency 风险<br>- 负：需要 monorepo 工具（pnpm workspaces 或 npm workspaces）支持 |
| **替代方案** | 保持 `file:` 引用 → 可接受但不如 `workspace:` 语义清晰 |

## ADR-010：协议验证器按领域拆分（schema.ts 拆分）

| 字段 | 内容 |
|------|------|
| **状态** | **建议** |
| **背景** | `schema.ts` 文件过大，validators/common.ts 1730 行，验证器未按领域拆分，导致碰撞和编辑困难。registry 已存在但实现文件分散。 |
| **决策** | 将 `schema.ts` 按能力领域拆分为：`base.ts`、`inbound.ts`、`outbound.ts`、`session.ts`、`workflow.ts`、`status.ts`、`provider.ts`、`rewind.ts`。Registry 保持不变为唯一入口。 |
| **后果** | - 正：每文件职责单一，降低合并冲突，新消息类型的验证器添加更清晰<br>- 负：迁移期间需保持兼容导出 |
| **替代方案** | 合并为更大文件 → 拒绝（已太大）；用代码生成自动拆分 → 可选但初期成本高 |

## ADR-011：生产态继续使用 Node.js，保留 Bun 为长期候选

| 字段 | 内容 |
|------|------|
| **状态** | **已批准** |
| **背景** | 评估 daemon sidecar 主线是否应从 Node.js/tsx 迁移到 Bun。 |
| **决策** | 当前不将 daemon sidecar 主线从 Node.js/tsx 迁到 Bun。Bun 保留为实验性 runtime 候选，需通过完整 benchmark 后方可进入生产候选。生产态以 Node 兼容产物为主（`esbuild --platform=node --format=esm --packages=external`）。 |
| **后果** | - 正：现有 ws、fs、child_process、AbortSignal 和测试保持兼容<br>- 负：cold start 和单文件分发不能立即从 Bun 受益 |
| **替代方案** | 立即迁移到 Bun → 拒绝（兼容性未验证，风险过高） |

## ADR-012：OpenTelemetry 用于可观测性

| 字段 | 内容 |
|------|------|
| **状态** | **建议** |
| **背景** | 当前缺少统一的可观测性标准。RuntimeMetricsCollector 的 snapshot 未周期 flush，缺少分布式追踪和 Prometheus 端点。 |
| **决策** | 建议集成 OpenTelemetry SDK，生成唯一 Trace ID（不再复用 `sessionId`），RuntimeMetricsCollector 周期 flush 到 OTEL，添加 Prometheus 端点。 |
| **后果** | - 正：标准化的可观测性，与生态兼容，分布式追踪<br>- 负：增加依赖和运行时开销 |
| **替代方案** | 自研 metrics 系统 → 拒绝（重新发明轮子）；使用 Prometheus client 直接导出 → 可接受但缺少 tracing |

## ADR-013：消息列表使用虚拟滚动

| 字段 | 内容 |
|------|------|
| **状态** | **建议** |
| **背景** | 当前消息列表使用全量渲染，大型会话（1000+ messages）在中低端设备上的滚动/渲染性能不可接受。 |
| **决策** | 建议使用 `react-window` 或等效方案实现虚拟滚动，确保大型会话在中低端设备上流畅渲染。 |
| **后果** | - 正：大型会话渲染性能显著提升，内存占用降低<br>- 负：需处理可变高度消息项，滚动复原逻辑变复杂 |
| **替代方案** | 全量渲染 + 分页加载 → 可行但用户体验不如虚拟滚动平滑 |

## ADR-014：UI 能力门闩（list-capabilities）

| 字段 | 内容 |
|------|------|
| **状态** | **建议** |
| **背景** | 当前 UI 无法区分引擎能力的实际状态（implemented/experimental/backend-not-wired/unsupported），未接线能力以假可点击状态出现。 |
| **决策** | 建议添加 `list-capabilities` 能力探测，UI 根据 capability state 显示相应的交互状态。能力目录包括 MCP、workflow、scoped-context、artifacts 等。 |
| **后果** | - 正：UI 诚实反映引擎能力，减少用户困惑<br>- 负：增加一次启动时的 capability 探测请求 |
| **替代方案** | 硬编码能力列表 → 拒绝（难以跟随引擎变化） |

## ADR-015：JSONL 事件存储添加轮转和大小限制

| 字段 | 内容 |
|------|------|
| **状态** | **建议** |
| **背景** | JSONL 事件文件当前无轮转和大小限制，单文件无限制增长，长期运行可能导致磁盘空间耗尽和性能下降。 |
| **决策** | 建议添加 JSONL 文件大小限制（如 100MB/file）和轮转机制（保留最近 10 个文件）。写入使用批量缓冲机制。 |
| **后果** | - 正：磁盘使用可控，事件读取性能稳定<br>- 负：轮转期间的事件读取需要跨文件合并逻辑 |
| **替代方案** | 保持单文件 → 拒绝（不可持续）；使用数据库替代 JSONL → 架构变动过大 |
