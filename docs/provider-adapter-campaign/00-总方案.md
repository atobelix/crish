### 逻辑依赖图

```
R1 数据载体层（独立根，全并行）：
   G2(档位映射载体) → G6(wire 改名，依赖 G2 载体)
   G3(配置/凭据/env 多供应商)    G4(协议路由纯函数)    G5(compat 纯函数)
        │
R2 协议面（依赖 R1 载体）：G7-a(anthropic/gemini 构建) · G5 序列化 compat · G8-a(描述面接口)
        │
R3 接线主干（依赖 R1+R2）：G1(ProviderRequest 扩展 + HttpProviderCall 能力面补全)
        │
R4 校验面（依赖 R1+R3）：G8-b(请求拒绝) · G6 完整 wire 方言 · 一致性回归闸
        │
R5 边缘与回归（依赖前四轮）：G7-b(边缘解析器) · 全量门禁
        │
R6 收尾：关闭报告 + 毒点沉淀 + 基线闭环
```

关键依赖说明：

1. **G6 依赖 G2 数据载体**（`00-问题基线.md:81`）：wire 改名是档位映射的「值」，须先扩展载体；
2. **G8-a（描述面）可早建**（R2），**G8-b（请求拒绝）须落在真实请求面**（R4，依赖 R3 接线主干）——采纳乙的拆分；
3. **G7-a（协议构建）依赖 R1 载体**（协议路由/序列化 compat 先行），G7-b（边缘解析器）独立；
4. 轮次间是逻辑依赖/数据流/验收次序，**不是优先级**——G1-G8 优先级相同。

## 五、结果汇总与验证机制（闭环输入输出契约 · 可复用）

### 5.1 轮次小结格式（主控每轮末写 `execution/roundN-*.md`）

```markdown
- <遗留跨轮依赖：哪些载体/接口供下一轮消费>

## 基线变化

- cargo test --workspace 绿/红清单（与轮前基线对比）
```

### 5.2 闭环契约

- **契约输入**：上一轮小结登记的公开接口/数据结构（档位映射类型、`ProviderConfigStore` 映射键、`WireProtocol` 枚举、`ProviderRequest.reasoning_effort` 字段类型、描述接口签名）。派单前主控核对实际代码（`git diff` + 编译）。
- **契约输出**：每轮末列出公开面清单；改动契约的轮次必须显式登记。
- **wire 字节形状契约登记（M8）**：跨轮会改 wire 字节的请求体形状必须入本节清单——消息序列化形状（T2.2/T2.3 与 R4 T4.2/T4.3）：空 assistant content 写 `""`、`reasoning_content` 模型级强制键规则、developer role 出现条件、wire 改名与 off disabled 的请求体形状。
- **usage 归一化形状（S-B1）**：登记 usage 归一化契约——`input = prompt - cached - write`，reasoning 从 completion 拆分；作为 R3 T3.4 与 R2 T2.5 的共享受验锚。
- **变更顺序纪律**：`reasoning_effort_tiers` 类型变更在 R1 后只追加不删改语义；`ProviderRequest` 字段只增不减（`#[serde(default)]` 兼容）；前端档位单源 = 描述接口（R5 收敛后前端不再自造档位表）。
- **证据可信**：验收断言一律真跑测试 + 粘贴 stdout；不以文件存在充当证据。

### 5.3 闭环迭代（多轮复用）

每轮输出（小结 + 契约登记 + 测试基座）作为下一轮派单输入；跨轮共享问题基线（`00-问题基线.md` 只追加）；任何一轮验证失败 → 回退该轮任务单元重派（不降级不变式）。
