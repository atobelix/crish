## 三、必须修改项清单（5 项）

### M1 · R2 与 R5 的 Agent 数低于 5 下限且未说明

- 证据：计划 `00-总方案.md:100` 为 R2 建议 **4** Agent（4 单元）；`:149` 为 R5 建议 **3** Agent（3 单元）。两者均非收尾轮（收尾是 R6，`:153`）。计划自身在 `:68` 明确「每轮 5-12 个 Agent（收尾轮不保底）」，与 附录B§2「收尾前最好不低于 5」要求 → R2/R5 均不满足。
- 影响：违反方案自述的派遣纪律边界；R5 又是「全量回归 + 不变式核对表初稿」的合闸轮，3 Agent 承担 I1-I6 收敛存在单点风险。
- 修复建议（择一）：① 细化 R2/R5 单元（R5 的全量回归可拆「Rust 回归」「前端门禁」「不变式核对表」为独立 Agent），使单元→Agent 数 ≥5；② 或将 R2 并入 R1 的尾部（R1 7 Agent + R2 部分），或明确把 R2 裁定为低冲突且由主控**亲自**收口的轮次并在方案注明豁免理由。禁止以「不用那么多人」静默绕过。

### M2 · R1 同文件并发写漏标：`config.rs` 由 T1.2/T1.3/T1.4 三方并发写

- 证据：`00-总方案.md:84` 冲突注意只写「T1.1 与 T1.6 若都动 catalog.rs 注意同文件串行标注」；但 T1.2（`:77`）、T1.3（`:78`）、T1.4（`:79`）三个单元的文件域**全部是 `config.rs`**（配置 map / 凭据 `secret_path_for` / env `first_env_value`）。
- 影响：三个并行 Agent 同时改 `config.rs`，按「同文件串行」纪律（`AGENTS.md:178`）是不被允许的，会导致合入冲突或互相覆盖。
- 修复建议：在 R1 派单模板（`:178` 冲突注意）把 config.rs 三个子面标注为「拆函数面串行或同 Agent 顺序完成」，或把 T1.3/T1.4 并入 T1.2 成为一个「config.rs 单 Agent」，与 T1.x 的 catalog.rs 单文件约束对等处理。

### M3 · R2 同文件并发写漏标：`messages.rs` 由 T2.2/T2.3 双写

- 证据：`00-总方案.md:100` R2 的 Agent 数建议后没有冲突注意；但 T2.2（`:96`，空 content `""` + reasoning_content 强制键）与 T2.3（`:97`，system→developer role 接入消息序列化）的文件域都是 `crates/agent-provider/src/request/messages.rs`。
- 影响：两 Agent 并发改 `messages.rs`，且都触及 `to_chat_messages` 序列化路径，属同一函数簇。
- 修复建议：R2 派单把 T2.2/T2.3 标注「同一文件 messages.rs 拆函数面串行」或合并为单单元；参考 R4 T4.1-T4.5 的 vendor.rs 串行标注（`:134`）的做法补齐。

### M4 · R3 同文件并发写漏标：`engine_provider.rs` 由 T3.2/T3.3/T3.5 三方并发写

- 证据：`00-总方案.md:117` 只标注「T3.2 与 T3.3 同文件串行」；但 T3.5（`:115`，会话亲和头 seam）文件域是「adapter + build_responses.rs」，其中 adapter 即 `engine_provider.rs`（`HttpProviderCall` 所在文件），与 T3.2（`:112`）同为 `engine_provider.rs`；T3.3（`:113`）也写 engine_provider.rs。
- 影响：`engine_provider.rs` 在 R3 被 T3.2/T3.3/T3.5 三个单元争用，仅标了其中两个，T3.5 漏标。
- 修复建议：把 T3.5 纳入「T3.2/T3.3/T3.5 同写 engine_provider.rs，拆函数面串行」的统一标注；或明确 T3.5 只新增独立头 seam 函数不与 T3.2 的 `HttpProviderCall.stream` 路径重叠并注明。

### M5 · 契约登记缺「消息序列化形状」，跨轮 wire 形状存在漂移风险

- 证据：`00-总方案.md:217` 契约输入清单 = 档位映射类型 / ProviderConfigStore 键 / WireProtocol / ProviderRequest.reasoning_effort / 描述接口签名；`5.2 变更顺序纪律`（`:219`）也只点名 `reasoning_effort_tiers` 与 `ProviderRequest`。但：
  - T2.2（`:96`「空 content `""`」，`messages.rs:146-148` 现状为 null）与 T2.3（`:97` system→developer）改变消息 wire 形状；
  - R4 T4.2/T4.3 又改 wire 字节（改名 `{medium:"high"}`、off→`thinking.type:"disabled"`）。
- 影响：消息序列化的 wire 形状被 R2 与 R4 两处跨轮改动，属典型契约，却未列入「对下一轮输入」契约清单，漂移时无登记可对账。
- 修复建议：在 §5.2 契约输入清单（`:217`）补「消息序列化形状（空 content 策略、developer role 触发条件、reasoning_content 键模型）」，并在 §5.1 小结格式（`:208`）的契约登记段显式要求 R2/R4 登记消息形状变更。

## 四、建议修改项清单（7 项）

### S1 · usage 归一化形状与事件流 event shape 未登记契约

- T3.4（`00-总方案.md:114`）usage 归一化后形状（prompt=cached 剥离、reasoning 拆分）与 T3.3（`:113`）流中 `error_kind` 补全的 event shape，被前端费率 / 主循环 consume 消费，均未入 §5.2 契约清单（`:217`）。建议补齐登记（可并入 M5 一并做，或单独在 R3 小结登记）。

### S2 · T4.3 单独成单元偏小，建议并入 T4.5

- T4.3（`00-总方案.md:130`，deepseek off → `thinking:{type:"disabled"}`）仅加一个 vendor 分支，工作量远小于同轮 T4.1/T4.5，单独一个 Agent 浪费（附录B§6 工作量均衡）。建议并入 T4.5（wire 方言矩阵，`:132`）或归入 T4.1（拒绝路径）由同一 Agent 完成。

### S3 · T3.2 偏大且与 T3.3 存在 `error_kind` 功能重叠

- T3.2（`00-总方案.md:112`）「HttpProviderCall 能力面补全：思考档位消费、描述接口消费、协议路由、error_kind」是 R3 最大单元（且 engine_provider.rs 本身是 800 行热文件）。其父括号含「error_kind」与 T3.3（`:113`，G1-c error_kind 补全）功能重复。建议把 T3.2 切成「思考透传 + 描述接口 + 协议路由三处同轨」与「流中 error_kind 透传」两个边界，后者归 T3.3，避免两 Agent 各自实现 error_kind。

### S4 · G1 子面缺 T3.5 锚点

- `00-总方案.md:31` G1 只列 a/b/c/d 四子面（reasoning 字段 / HttpProviderCall 补全 / error_kind / usage），但 R3 有 T3.1-T3.5 五单元（`:111-115`），T3.5（会话亲和头 seam）无 G1 子面编号。建议把 T3.5 标为 G1-e 或明确归入 G1-b，保证每单元可溯源到 G 子面（对齐 `00-问题基线.md:16` G1 内容里含会话亲和头）。

### S5 · T4.5「选 2-3 方言」与 G5-c 覆盖的收尾归属需明确

- T4.5（`00-总方案.md:132`）说「按 02:106-108 覆盖矩阵选 2-3 高频」，但分析 `02-思考强度与vendor层对比.md:98,106-108` 列出开关型（qwen/zai/together）+ 嵌套型（openrouter/ant-ling）+ 字符串型（string-thinking）共 6 种。若只做 2-3，需在收尾报告明确「未做方言」的归属（列入 G5-c 完成证据？还是显式遗留？），避免 G5-c 被部分完成后仍宣称关闭（效果锁红线）。

### S6 · R3 输出「校验触点」表述过泛

- R3 对下一轮输入（`00-总方案.md:120`）承诺「真实请求面上的校验触点（R4 拒绝路径落点）」，但实际拒绝校验入口函数（`resolve_reasoning_level`）在 R4 T4.1（`:128`）才建。建议把 R3 交付物具体化为「adapter 请求校验入口（hook/seam）签名」，否则 R4 的「落点」依赖不明确。

### S7 · 前端 profile 契约对齐的前置依赖可提前声明

- T5.2（`00-总方案.md:146`）与 T4.1's 描述接口数据源（R2 T2.4 `:98`）有依赖，但 R5 很晚才消费描述接口。建议在 §二 依赖说明补一句「R5 前端档位面板数据源 = R2 描述接口」，避免执行期才发现前端收敛被 R2 交付物阻塞。属轻量补强。
