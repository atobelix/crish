# 00 · 多模型适配战役问题基线

> 战役工作区：`docs/provider-adapter-campaign/`
> 性质：入库战役文档。根目录放 00-总方案、问题基线、汇总索引；`analysis/` `plan-reviews/` `execution/` `independent-plans/` 仅允许战役根下再嵌一层。
> 纪律：本文件只追加不删除；评审/修改产物按约定落子目录；所有问题**优先级相同**，方案仅按逻辑依赖排序。

## 一、战役目标

系统性完善 Conex 多模型适配（`crates/agent-provider` + `session-loop` 接线面），使软件获得与 DeepSeek Harness（`reference/deepseek-harness`）同级别的多供应商能力面：多协议、多供应商注册、模型级思考强度档位、能力描述与请求校验分离、主循环真实接线。

## 二、上一轮评估结论（2026-08 主控调研，证据见各条目文件:行号）

### G1 · 主循环接线存在但能力面受限（原「未接线」表述经主控勘察修正）

`session-loop` 与 `agent-provider` 之间是 trait 解耦（`crates/session-loop/src/provider.rs:1-22`）；**真实生产适配层已存在**：`HttpProviderCall`（`apps/agent-workbench/src-tauri/src/engine_provider.rs:387`，`impl ProviderCall` at :513）——真实调用 `classify_provider_error`（:556-597/:725-731）、chat+responses 双轨构建与解析（:463-468/:628-632）、缓存策略与亲和头（:435-441/:505-509）、Abort 强穿透（:602-614）。主循环经 `streaming.rs:74` 调用。

**受限面（修正后的 G1 内容）**：

1. `ProviderRequest` 无 reasoning/thinking 字段（`session-loop/src/provider.rs:69-91`）→ 思考强度无法从主循环携带，`vendor.rs` 的 effort/intensity 注入在适配层无消费点（`request_options` 只填 `reasoning_content` mode，engine_provider.rs:426-451）；
2. 适配层仅接 chat/responses 双轨（`HttpStreamParser` 二态，engine_provider.rs:657-661）；anthropic/gemini 解析器已实现但未接入适配层；
3. 单提供方投影：`EngineProviderConfig` 单 base_url/model/api_key（`config_profile_apply` 每次覆盖生效配置）；
4. 重试归主循环阶梯（`stream_error_retry.rs`），适配层只分类——设计合理，但流中错误 `error_kind` 恒 None（engine_provider.rs:785-788，agent-provider 未升级）待补。

### G2 · 模型级思考档位白名单无消费端

`ModelCatalogEntry.reasoning_effort_tiers`（`crates/agent-provider/src/models/catalog.rs:141`）只有定义与测试（`catalog_tests.rs:529`），vendor 归一化走系列级能力表（`vendor_capability.rs:106`），模型级特例（如 qwen3-8-max 白名单）未生效。

### G3 · 单提供方配置层，无多供应商注册（前端多轨 vs 引擎单轨断链）

`ProviderConfig` 单 `provider_id`/`base_url`/`model`/`api_key_ref`（`config.rs:95-110`）；对比 DeepSeek Harness 模型设置页 35+ 提供方并存（`reference/deepseek-harness/apps/web/tests/snapshots/models-settings/empty.expected.md:25-60`）。catalog 数据模型已支持多通道（`provider` 字段），配置面未跟上。

**A3 分析补充**：配置/凭据/env 三处单例——`ProviderConfigStore` 单份配置、单 `api_key_ref`+`default.dpapi`、固定 `CRISH_*` env，无法多供应商并存；缺 DSH `models` 整体替换模式（`llm-pi-ai` profile）；条目级 baseUrl（pi-ai 每模型条目带 baseUrl）与 `input` 模态多值列表也缺失。

**主控勘察补充（2026-08 确认）**：前端已有完整多 profile 体系（`apps/crish-desktop/src/api/provider-profiles/`：`profileCatalog.ts` DEFAULT_PROFILES/KNOWN_PROFILE_LABELS、`profileValidation.ts`、`profileStore.ts` activateProfileModel/createCustomProfile/upsertProfile/saveProfileKey/saveProfileBaseUrl/addModelToProfile），Tauri 命令 `config_get`/`config_update`/`config_profile_apply` 已登记（`apps/agent-workbench/src/core/tauri-command-registry.ts:67-73`）；但 `clientApi.ts:798` 明写「真实配置轨 = providerProfiles + update-config；引擎仅 OpenAI-compatible」。→ G3 精确表述：**前端多 profile 与引擎单提供方断链**，改造面是引擎侧对齐前端 profile 契约（活跃 profile 选择 → 每 profile 独立端点/凭据/模型目录），而非从零造注册表。

**再补充（profileCatalog 实证）**：前端 DEFAULT_PROFILES **已预置 `opencode-go` profile**（`id: 'opencode-go'`、`baseUrl: 'https://opencode.ai/zen/go/v1'`、`models: ['deepseek-v4-flash']`，`apps/crish-desktop/src/api/provider-profiles/profileCatalog.ts`），另有 opencode-zen/deepseek/qwen/openai/anthropic/flowbit 等默认 profile。→ 前端早已为 opencode-go 就位，引擎多提供方支持是断链缺口；战役完成后引擎应能直接服务该 profile。

### G4 · 模型级协议路由消费端待确认

catalog 有 `mode: "chat"|"responses"|"both"`（`catalog.rs:59`）与 `supports_responses`（`catalog.rs:136`），但请求构建按全局 `Endpoint`（`config.rs:44-53`）；对比 pi-ai 每模型条目 `api` 字段（opencode-go 同 provider 下 v4-flash 走 completions、grok-4.5 走 responses）。

**A1 分析补充**：`mode` 字段至今未被请求构建消费；适配层路由靠全局 `Endpoint` + `supports_responses` 二元开关（`engine_provider.rs:276-278`），单全局 endpoint 无法表达同 profile 多协议。

### G5 · compat 探测面窄

`infer_reasoning_vendor`（`request/vendor.rs:180-213`）仅按 baseUrl/model 关键字推断 7 厂商；对比 pi-ai `detectCompat`（URL/provider → supportsStore / thinkingFormat / maxTokensField / requiresReasoningContentOnAssistantMessages 等宽 compat 面）。

**A2 分析补充**：wire 方言覆盖不全——Conex 仅 dict 型注入，缺 qwen `enable_thinking`、zai `thinking:{type}`、openrouter 嵌套 `reasoning:{effort}`、off 的显式 `thinking.type:"disabled"`（pi-ai openai-completions.js:590-592、DSH llm-deepseek README.md:44）。

### G6 · wire 改名语义缺失

思考档位只有白名单（tiers），无 pi-ai `thinkingLevelMap` 的 wire 拼写映射（如 `max:"ultra"` 网关词汇场景）。

**A2 分析补充**：pi-ai 改名真实影响请求字节——`max:"ultra"`（zai）、`low:"high"/medium:"high"`（GLM-5.2 档位合并）、`off:"none"`（hy3/cerebras）。另发现 **anthropic-beta 头过度发送**：Conex `reasoning_effort_headers`（`request/vendor.rs:298-314`）对 adaptive 新代际模型也发 `interleaved-thinking-2025-05-14` 头，pi-ai 对 forceAdaptiveThinking 模型明确跳过（anthropic-messages.js:641）。

### G7 · 边缘协议未覆盖

解析器仅 chat / responses / anthropic / gemini（`parse/mod.rs`）；pi-ai 另有 azure-openai-responses / mistral-conversations / openai-codex-responses / bedrock。

**A1 分析补充（协议接线断层）**：4 个解析器已实现，但真实适配层 `HttpProviderCall` 只接 chat 与 responses 两轨（`engine_provider.rs:628-631`、解析器枚举仅两态 :658-661）；`AnthropicParser`/`GeminiParser` 在 `apps/` 生产路径零引用，且**没有 anthropic/gemini 请求体 builder**——「解析能力」远超「接线能力」。

**A1 序列化细节补充**：空 assistant content 序列化为 `null`（`messages.rs:146-148`），DSH/pi-ai 要求 `""`；usage 未做 cached/write/reasoning 拆分归一（`consume/mod.rs:789-799` 逐字段透传，依赖默认 Included 语义）；恒 `MaxTokensField::MaxTokens`（`engine_provider.rs:446`）与恒 `role:system`（`messages.rs:444-451`），缺 `max_completion_tokens` 与 developer role compat。

### G8 · 能力描述与请求校验分离语义待核查

DeepSeek Harness 语义：`resolveModel` 描述能力不因坏配置抛错（单模型坏配置不藏整个提供方），请求路径以 `UNSUPPORTED_REASONING_EFFORT` 在网络 I/O 前拒绝（`reference/deepseek-harness/packages/llm/llm-pi-ai/README.zh.md:115`）。Conex 现状（`resolveReasoningLevel` 拒绝 vs 描述路径）需对比核查。

## 四、流程编排约定（本战役固定）

1. 对比分析（多 Agent 并行，产出 `analysis/NN-*.md`）→ 主控汇总
2. 主控输出 `00-总方案.md` v1
3. 双评审 Agent 并行评审（产出 `plan-reviews/`）→ 主控最终确认
4. 派 Agent 按评审意见修改方案 → 定稿
5. 按定稿方案多轮执行：每轮 5-12 个 Agent（按实际需求灵活，不强制占满），同父 ≤12、同时存活 ≤16、深度仅 1
6. 每轮输出作为下一轮输入（闭环迭代）；执行产物落 `execution/`，轮次内部分工在方案中定义
7. 只有主控可提交 git；子 Agent 改动留工作区
