# 02 · 多模型适配战役独立总计划（乙）

> 战役工作区：`docs/provider-adapter-campaign/`
> 性质：独立总方案（乙），与 `independent-plans/` 下其它独立计划并存，由主控合并为 `00-总方案.md` 定稿。
> 纪律：本方案**只含逻辑执行顺序**，不含时间安排、人员分配、优先级排序——G1–G8 全部同权，轮次差异仅是逻辑依赖与验收次序，不是重要度差异。
> 视角声明：本计划在轮次划分上与 `00-总方案.md` 草案不同（草案把 G2+G6、G3+G4+G5 各捆一轮）；本计划按「数据载体 → 协议面 → 接线主干 → 校验面 → 边缘与收尾」的**自上而下五层**拆 6 轮，理由与取舍见 §4 各轮「串并行依据」。

### 2.2 逻辑依赖图（本计划以数据/验收次序为边，非重要度）

```
层1 数据载体            G2 ──┐(共享档位载体)
   (无适配器)           G6 ──┴┐
                       G3 ───┐│(resolve(provider_id) 供适配器)
                       G4 ───┼┤(resolve_wire_protocol 供适配器与 builder)
                       G5 ───┼┤(compat 数据供 build_*.rs)
                              ││
层2 协议面(依赖层1)      anthropic/gemini builder(接 G4 路由、G5 compat)
                       G8·描述面只读接口(读 G2/G6 载体 + catalog 能力位)
                              │
层3 接线主干(依赖层1+2)  G1 生产 impl ProviderCall(消费 G3 resolve / G4 路由 /
                       G5 描述 / reasoning 透传)
                              │
层4 校验面(依赖层1+3)   G8·请求侧拒绝(经 adapter 请求路径校验, 依赖描述面)
                       G6 完整 wire 方言集成 + anthropic-beta 头收敛
                              │
层5 边缘与收尾(依赖层2)  G7 扩展边缘解析器 + 全量回归 + 关闭报告
```

- **必须串行**的理由：
  1. **G2/G6 与 G6 的 wire 消费、G8·描述面共享同一档位载体**，载体扩展（层1）必须先于任何消费它的人（层2+）——否则并行 Agent 读旧字段。
  2. **G4 路由函数（层1）必须先于 anthropic/gemini builder 与 adapter**——builder/adapter 都要按 `resolve_wire_protocol` 输出切 URL/body/parser 三件套（`analysis/01:124-126`）。
  3. **G3 的 `resolve(provider_id)`（层1）必须先于 G1 adapter 的每次调用决议**——adapter 需 per-provider 解析端点/凭据（`analysis/04:205`）。
  4. **G8·请求侧拒绝（层4）必须先有 G1 adapter（层3）与 G8·描述面（层2）**——拒绝发生在请求构建出口、对照对象是描述面能力。
- **可并行**的理由：
  - 层1 内部 G2/G6、G3、G4、G5 **互不依赖**（各自独立数据域与纯函数），同轮并行；唯 G2 与 G6 因为共享档位载体，合为一个任务单元（见 §4 轮1·单元1），避免双 Agent 编辑同字段分脑。
  - 层3 内部（G1 的请求装载 / 凭据决议 / HTTP 层 / SSE 映射 / 分类接线 / 亲和头）可拆多个单元并行，但因都落在**同一适配层文件簇**（`engine_provider.rs` 域），按「同文件串行」纪律在轮内分先后或由主控分配互不重叠的文件域，见 §6 派单纪律。

## 3. 顶层执行架构（可复用闭环模板）

战役执行骨架，本计划与 `00-总方案.md:32-46` 对齐，但把「每轮闭环」记为可复用契入点：

```
阶段 A 问题识别  → analysis/NN-*.md（已完成）
阶段 B 方案产出  → independent-plans/*（本文件）+ 另一独立计划
阶段 C 方案评审  → 2 评审 Agent 并行（plan-reviews/）
阶段 D 方案定稿  → 主控合并 00-总方案.md，经 D 派修改 Agent 改稿
────────────────────────── 阶段 A–D 为方案层、只读；──────────────────────────
阶段 E 执行层：R1→R2→…→R6 每轮 = 【派单 → 并行执行 → 主控核对验收断言
        → 写轮次小结 → 小结作为下一轮输入】，闭环迭代（§7 契约）
阶段 F 验证层：全不变式绿 → 关闭报告（§9）
```

### 3.1 每轮固定 5 阶段子循环（可复用模板）

```
(1) 派单：主控按本轮任务单元分配 Agent，每 Agent 一份「派单书」（§6 骨架）
(2) 执行：并行执行，改动留工作区（子 Agent 不提交）
(3) 收口：主控核对每单元的验收断言（真跑测试），不合格重派
(4) 小结：主控写 execution/round{N}.md（轮次小结格式 §7.1）
(5) 移交：小结 + 工作区改动作为下一轮输入（闭环输入输出契约 §7.2）
```

### 3.2 Agent 数量与派遣约束

- 每轮 Agent 数 = 该轮任务单元数（一单元一 Agent，保证工作均衡），**⊂ [5,12]**；单元小于 5 时合并相邻同域单元或减少轮次 Agent 数（附录 B：收尾前最好不低于 5，收尾轮不保底）。
- 深度仅 1，子 Agent 无派发能力；同父 ≤12、同时存活 ≤16。
- 探索类子 Agent（评审/分析）最多写一份文档且由主控分配写作任务；子 Agent 一律不提交 git、不回撤、不 `reset --hard`/`checkout .`/`restore`。
- 空返回重派纪律（附录 B §4）：1–3 次接续原会话、4–6 次拆分或换新 Agent，任务量不变。

## 4. 轮次设计（6 轮）

> 每轮列：目标 / 任务单元（=Agent 数） / 串并行依据 / 验收断言 / 输出物。Agent 数建议 = 单元数。所有验收断言均为「真跑 `cargo test`」级，禁止「文件存在」式验收。

### 轮 1 · 数据载体与纯函数层（无适配器依赖）

**目标**：把「档位载体、多供应商配置、协议路由纯函数、compat 探测纯函数、wire 改名载体」这些**地基数据**先落地并测绿，供后续所有层消费。本轮的胜利标准是「后续任何层都不需要再动数据模型」，只做消费与接线。

**任务单元（4 个 Agent）**：

- **单元1 · 档位载体 + wire 改名载体（G2+G6，合单元）**：把 `reasoning_effort_tiers: Option<Vec<String>>`（`crates/agent-provider/src/models/catalog.rs:141`）扩展为「档位 → Option<wire 拼写>」映射（`BTreeMap<String, Option<String>>`，值 None=隐藏不支持档），保留旧 `Vec` 解析兼容（值同规范名），并把 G6 的 wire 拼写承载其上。落点收敛在 `reasoning_effort_object`（`request/vendor.rs:227-293`）与 `normalize_reasoning_effort`（`request/vendor_wire.rs:12-18`）。
  - 验收：新增测试——`reasoning_effort_tiers={high:"high",max:"max",low:None}`，选 `low`→归一化不发（或降级，语义见轮4/层4）；选 `high`→wire `"high"`；`{medium:"high"}` 改名映射→请求体 `reasoning_effort:"high"`（wire 字节断言，对齐 `analysis/02:70`）。旧 `catalog_tests.rs:586` 解析断言保留绿。
- **单元2 · 多供应商配置 store（G3/配置）**：`ProviderConfigStore::config` 从单 `ProviderConfig`（`config.rs:181`）改为 `BTreeMap<String, ProviderConfig>`（键=provider_id）；`load` 读 `provider-config.json` 顶层映射（旧单对象用 `{"openai-compatible":{...}}` 包装兼容）；`resolve()` 新增 `resolve(provider_id)`，保留无参 `resolve()` 默认 `openai-compatible` 语义防破坏既有调用方（`analysis/03:181-184`）。
  - 验收：`load({a:{...},b:{...}})` 后 `resolve("a")`/`resolve("b")` 各自返回独立快照，base_url/model/api_key 互不串扰；`save()` 原子写回映射。
- **单元3 · 凭据 per-provider 引用 + env per-provider（G3/凭据+env，合单元）**：`secret_path_for` 按 provider_id 求引用名（`secrets/{provider_id}/{ref}.dpapi` 或 `secrets/{provider_id}.dpapi`，替代单一 `default.dpapi`，`config.rs:263-278`）；`first_env_value` 接受 provider 维度（`{P}_API_KEY`/`{P}_BASE_URL`/`{P}_MODEL`/`{P}_ENDPOINT` 扫描，再回退 `CRISH_*`，`config.rs:30-37,303-308`）；`CredentialStore`（`credentials.rs`）实现不动。
  - 验收：provider `a`、`b` 各写密钥落盘到各自文件互不覆盖；设 `OPENAI_API_KEY`+`DEEPSEEK_API_KEY` 时 `resolve("openai")` 取前者、`resolve("deepseek")` 取后者；无 provider env 回退 `CRISH_*`（对齐 `analysis/03:190,196`）。
- **单元4 · 协议路由纯函数 + compat 探测纯函数（G4+G5，合单元，只做函数与测试不接线）**：新增纯函数 `resolve_wire_protocol(catalog, vendor, model, endpoint) -> WireProtocol{Chat|Responses|Anthropic|Gemini}`（消费 `mode`/`supports_responses`，`catalog.rs:59,136`；废弃全局 `Endpoint` 为唯一判据）；`resolve_max_tokens_field`/`supports_developer_role`/`requires_reasoning_content_on_assistant` 等 compat 宽面探测（URL/provider → 字段名/角色/方言，对齐 `detectCompat`，`analysis/01:134-136`）。
  - 验收：fake catalog 条目（`mode:"anthropic"`）断言 `resolve_wire_protocol` 输出 `Anthropic`；同 provider 下 chat 模型与 responses 模型各自解析到正确协议互不影响（参数化覆盖四协议，对齐 `analysis/01:126`）；base_url 含 moonshot → `resolve_max_tokens_field` 返回 `MaxCompletionTokens`。

**串并行依据**：G2/G6、G3、G4/G5 三个数据域互相独立，无任何互相消费关系，故全并行；本轮全部为 agent-provider 内纯数据/纯函数改动，**零适配器依赖**，可独立验证。G2 与 G6 共享档位载体、G4 与 G5 共享「路由+compat 描述」，故各合为单单元，规避同文件分脑。

**输出物**：工作区改动 + `execution/round1.md` 小结 + 本轮数据载体契约快照（供后续层引用）。

### 轮 2 · 协议面构建与描述面（依赖轮1载体）

**目标**：把轮1的路由与 compat 变成「能发出多协议请求的 build_*.rs 与 edge 解析器」，并把 G8 的**描述面只读接口**落地（不依赖 adapter，依赖轮1档位载体）。

**任务单元（4 个 Agent）**：

- **单元1 · anthropic/gemini 请求构建 + 接线（G7 前半 + G4 消费）**：为 `request/build` 增加 `build_anthropic_request_body` / `build_gemini_request_body`（对齐既有 chat/responses 的 compactObject 风格）；`HttpStreamParser` 增加 `Anthropic`/`Gemini` 两个变体（`engine_provider.rs:658-661`）；请求头增加 `anthropic-version` / Gemini `x-goog-api-key` 差异化头组装。URL/body/parser 三件套由轮1单元4的 `resolve_wire_protocol` 统一驱动（对齐 `analysis/01:30-31` 的「三件套同轨」铁律，`engine_provider.rs:259-262`）。
  - 验收：anthropic 轨端到端 mock（MockServer 回 `message_start→content_block_delta→message_stop`），断言请求体含 `system`+`messages`、`anthropic-version` 头、`thinking.budget_tokens`；gemini 轨 mock `candidates[].usageMetadata` 断言 `usage` 归一正确（`analysis/01:131`）。既有 chat/responses 测试回归为绿。
- **单元2 · 消息序列化加固 + 消息层级 compat（G5 消费）**：空 assistant content 由 `content:null`（`messages.rs:146-148`）改为轨可控（DeepSeek/网关轨发 `""`，其余保留 null）；`developer` role（reasoning + 支持时 system→`role:"developer"`，否则 system/user-prefix，`analysis/01:135`）；（可选）tool result 无内容加 `(no output)` 占位（`analysis/01:147`）。
  - 验收：DeepSeek fake 模型纯思考 assistant 轮 → wire 含 `reasoning_content:""`；非 DeepSeek 纯思考轮不带键；空文本 assistant 在 DeepSeek 轨序列化为 `content:""`（非 null）；既有 `deepseek_invariants.rs` 与 `system_role.rs` 测试保持绿（`analysis/01:136,140`）。
- **单元3 · G8·描述面只读接口（G8 前半）**：把 `infer_thinking_capability`（`vendor_capability.rs:158-170`）+ catalog 能力位（`catalog.rs:137-141`）+ 轮1档位载体合并成稳定的「模型能力描述」（档位白名单 + 默认档 + 是否支持 reasoning），暴露为只读接口，供 UI 档位面板/目录/请求校验三处消费（`analysis/04:94`）。
  - 验收：catalog 声明 `supports_reasoning_effort=false` 的模型 → 描述接口返回「不支持 reasoning」，同 provider 下 A 模型坏配置时 B 模型仍可被描述（对齐 `llm-pi-ai/README.zh.md:115`，不藏整个提供方）；描述接口对某模型只报告指定档位集，未覆盖档位不出现（`analysis/04:95-96`）。

**串并行依据**：三单元都消费轮1，但彼此不互相消费（anthropic/gemini builder 吃 G4 路由；消息序列化吃 G5 compat；描述面吃档位载体），故并行。它们都落后于轮1（数据是定稿前提），构成自上而下的第 2 层。

**输出物**：工作区改动 + `execution/round2.md` + 多协议请求构建契约快照 + 描述面接口契约。

### 轮 3 · 主循环接线主干（G1，依赖轮1+2）

**目标**：让 `session-loop` 走真实生产适配层——本计划把这一层做成**单轮多单元并行**，因为 G1 虽是「一个问题」，但落在适配层文件簇的多个互不重叠域上，可拆 4 个单元。这是闭环真正打通的轮次。

**任务单元（5 个 Agent）**：

- **单元0 · `ProviderRequest` 扩展 + persistence**：`ProviderRequest` 增加 `reasoning_effort: Option<ReasoningEffort>`（`provider.rs:69-91`），`build_request` 从会话态填充（`loop/handlers/streaming.rs:304-331`）；流中 `error_kind` 在 `Stop` 补全（`stream.rs:149-162` 已预留，`engine_provider.rs:785-788` 待升级）；会话 metadata 记档位（`analysis/04:127-130,139-140`）。
  - 验收：`ProviderRequest{reasoning_effort:Some(High)}` 经 chat 序列化后请求体含 `reasoning_effort:"high"`；`None`/`Off` → 不含任何 reasoning/thinking 参数（逐字节对比，对齐 `analysis/04:140-141`）。
- **单元1 · 生产 `impl ProviderCall`：请求装载 + HTTP 发送层**：把 `ProviderRequest`（含新 reasoning）映射为 agent-provider 请求构建（chat/responses 双轨 + 轮2 anthropic/gemini），完成序列化（返回流 `'static`、不借用 request，`provider.rs:22,128`）；HTTP 发送层 + 请求头注入（含会话亲和头族 seam）。
  - 验收：`::stream()` 返回流为 `'static` 不借用 request（crate 级测试锁定「请求体在返回流前序列化」）；请求头含会话亲和头（`session_id` 非空注入 session 头，为空不注入，对齐 `analysis/04:194`）。

## 8. 风险与兜底

### 8.1 空返回重派（默认视为供应商网络问题，非任务失败）

- 先核查是否已落盘（空返回常已实际完成）→ `git status` 检查并行 Agent 是否已误伤/已提交。
- 未落盘：1–3 次 → 优先原 `task_id` **接续**原会话（先判最终状态：已落盘则核查收尾；复读无产出则重新派发而非继续接续）；4–6 次 → **拆分或换新 Agent** 重新分发，**总任务量不变**。主控按当前情况动态调整（附录 B §4、`LOGIC_PLAN_NO_RETREAT.md`）。
- 禁止因空返回擅自缩短提示词或砍任务范围；任务过大才拆单文档/单文件粒度重派。

### 8.2 测试失败

- 一个单元的红灯 → 先判定是「实现问题」还是「契约漂移」：
  - 实现问题 → 该单元回轮重派（按 §8.1 接续，不降级）。
  - 契约漂移（上一轮契约被本改动破坏）→ **以维护不变式为最高优先**：报主控裁决是回退上一轮契约还是推进，绝不静默改不变量。
- 既有不变量测试（`deepseek_invariants.rs`、`system_role.rs`、`vendor_tests.rs`、`catalog_tests.rs`）红灯 = 视为**回归事故**，立即回该单元，先修红灯不推进下一轮。

### 8.3 契约漂移 / 双实现漂移

- 前端 `defaultThinkingLevel` 档位集（`['off','low','medium','high']`，`clientApi.ts:77`）与 `agent-provider` 静态表档位（`minimal/.../xhigh/max`，`vendor_capability.rs:12-29`）的**双实现漂移**（`analysis/04:229`）：本计划以 `agent-provider` 描述面（R2 单元3）为**权威真源**，UI 档位面板改读描述面；消除前端契约测试「自洽假说」非能力真值的问题。此属跨维改动，R6 收尾时核对前端链路已统一。
- 任何「同能力两个实现」若被 review.md 毒点审计发现，按 `AGENTS.md` 附录 B §7 由主 Agent 追加改进建议文档（不动 review.md 源）。

### 8.4 探索/评审子 Agent 引用外部 vs 内部（审计模式）

- 本战役 `00-问题基线.md:53-61` 明确采用**参考外部模式**（用户给了 DSH/pi-ai 对比方向）。评审/审计子 Agent 可参考 `reference/` 与外部软件。
