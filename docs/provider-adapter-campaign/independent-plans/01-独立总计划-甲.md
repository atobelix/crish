## 〇、文档自用说明（本文档结构如何被复用）

本文档既是**单次战役的总计划**，也是**后续多轮次迭代的模板**：

- §一「战役不变式」是每轮验收的**最高口径**，任何轮次不得降级。
- §二「问题清单与逻辑依赖图」是**任务的来源**——每轮的目标必须能溯源到一个或多个 G 编号。
- §三「轮次设计」是**执行骨架**：轮次之间是逻辑依赖/数据流/验收次序关系，不是重要度排序；轮次内子任务可拆可合、Agent 数按需（5–12）。
- §四「派单模板」是**主控 → 子 Agent 的提示词骨架**，每轮复用，只替换任务单元/产出/验收。
- §五「结果汇总与验证机制」是**闭环输入输出契约**：每轮小结是下一轮的派单输入。
- §六「风险与兜底」定义**空返回/测试失败/契约漂移**的处理路径。
- §七「收尾条件」定义战役关闭标准。

## 三、轮次设计

### 3.0 编排总则（每轮通用）

1. **每轮 5–12 个 Agent**（AGENTS.md 附录 B§2），按该轮任务单元实际拆分数决定，不强制占满；同时存活 ≤16、同父 ≤12、深度仅 1（子 Agent 无派发能力）。
2. 每轮内子任务**文件冲突注意**：同文件串行（派单时标注冲突文件；主控按 `git status` 与产出路径协调）。**所有子 Agent 改动留工作区，不提交**（附录 B§1；只有主控提交）。
3. 每轮先跑一次**基线**（`cargo test --workspace` + 相关 crate 专项），记录绿/红清单，作为该轮回退基线。
4. 每轮结束主控核对验收断言（**真跑测试**）→ 写轮次小结（`execution/roundN-*.md`）→ 下一轮以小结为输入派单。
5. 探索类子 Agent 最多 1 份文档、由主控分配写作（AGENTS.md §4.5）；实现类子 Agent 直接写代码+测试，不在文档上重复。
6. 测试资产保护铁律（AGENTS.md §9）：`reference/markdown-editor/` 与 `tests/e2e` 5 个 markdown-editor 专项 spec **禁止删除**；本战役不触碰前端 markdown-editor 域（仅类型检查覆盖 01/02/03/04 所属 Rust 内核 + 前端 profile 契约）。

### 5.2 闭环契约：输入/输出显式化

- **契约输入（下一轮派单的依赖契约）**：上一轮已**定稿的数据结构 schema**（如 `reasoning_effort_tiers` 新类型、`ProviderConfigStore` 映射键、`WireProtocol` 枚举、`ProviderRequest.reasoning_effort` 字段类型）。改动这类契约的轮次，必须在小结中**显式登记**，供下一轮对齐导入。
- **契约输出（本轮的交付物）**：可被后续轮 `import`/`use` 的公开接口（trait、函数、枚举、纯函数如 `resolve_wire_protocol`/`normalize_*_usage`/`resolve_reasoning_level`）。每轮末列出公开面清单，下一轮在派单前核实其签名可用。
- **跨轮数据流**：
  - R1 产出 → 公共测试基座 + `reasoning_effort` 字段（R3 前端档位用 + R4 前端消费）。
  - R2 产出映射载体 → R3 前端档位渲染的档位源（若前端读）→ R4 收敛。
  - R1 描述接口 → R3 前端档位面板 → R4 UI 收敛。
  - R3 多提供方配置 + 协议路由 → R4 边缘协议接入 + 前端 profile。
- **证据可信**：验收断言一律是 `cargo test` / 指定测试名 / wire 字节断言（子 Agent 回报粘贴 stdout），不以「文件存在」或「我觉得可以」充当证据。契约漂移比对靠 `git diff` + 既有测试回归（见 §6.3）。

### 5.3 变更顺序纪律（防契约半途漂移）

- **catalog `reasoning_effort_tiers` 类型变更**发生在 R2-T2.1，之后任何轮不得再改其**键/值语义**（只允许加字段，即 AGENTS.md §4「只追加」精神迁移到数据结构）。若必须改，须先跑 `catalog_tests.rs` + `deepseek_invariants.rs` 确认无破坏，并在 R2 小结登记后由 R3/R4 派单导入。
- **`ProviderRequest` 字段**在 R1-T1.1 登记后，R3/R4 只增不减（`#[serde(default)]` 保持向后兼容）。
- 前端「双实现漂移」（`defaultThinkingLevel` vs Rust 静态表，`04:229`）在 R4-T4.3 收敛为**单源 = 描述接口**，收敛后前端不再自造档位表。

## 六、风险与兜底

### 6.1 子 Agent 空返回

处置路径（AGENTS.md 附录 B§4）：

1. **1–3 次空返回**：优先用 `task_id` **接续**原 Agent 会话；先判最终状态——任务已实际落盘 → 仅核查收尾；Agent 复读无产出 → 重新派发（不复读）。
2. **4–6 次空返回**：可**拆分**任务（单文件/单函数粒度）或**换新 Agent** 重新分发，**总任务量不变**（不擅自砍范围/缩提示词）。
3. 每次空返回先 `git status` + 核查文件是否已落盘（空返回常已实际完成）；并行 Agent 是否已误伤/已提交（本战役只有主控提交，子 Agent 不提交，故主要核查「并行 Agent 是否改了同文件」——若有，报主控协调，不回撤）。
4. 主控有权按当前情况动态调整派单（附录 B§4 末句）。

### 6.2 验收断言测试失败

1. 断言落在**该子 Agent 自身文件域**：Agent 自修自测再报；主控不代修（避免双源）。
2. 断言失败波及**其它并行 Agent 文件域**（契约/共享文件冲突）：主控裁决归属，回退到最近一次该文件域的提交前工作区状态（仅受影响文件精确 edit 修复，**禁止全局回撤** AGENTS.md §3.2）。
3. **回归失败**（`cargo test --workspace` 中非本任务测试变红）：视作「破坏既有契约」，不做补丁（不 `--no-verify`），先定位是哪个契约/文件变动所致 → 回退改动或补测试钉住再进下一断言，直至全绿。
4. 任何验证失败**不降级不变式**（§一 I1–I5 不下调）。

### 6.3 契约漂移

1. **检测**：每轮派单前，主控核对上一轮小结登记的「公开接口/数据结构契约」与实际代码（`git diff` + 编译）。不一致即为漂移。
2. **处置**：若漂移来自上一轮未完成项 → 回退该任务单元，重派；若来自跨轮错误假设 → 修正本轮派单输入；若契约本身需演进 → 走 §5.3 变更顺序纪律（先回归验证、再只追加）。
3. **防漂移硬化**：把关键契约（WireProtocol 枚举、reasoning_effort_tiers 新类型、ProviderConfigStore 映射键）写成**类型/单测**而非仅文档——编译与序列化测试在漂移时最先暴露，其次是对照既有专项测试（`deepseek_invariants`、`system_role`、`parse_*`、`config`）回归。

### 6.4 参考外部引用与实现不可对齐

- pi-ai `dist/` 非入库（`04:227`）：不能逐字对线私有实现细节，只对齐其「按 compat 开关切 wire 拼写」「每模型 `api` 路由」等**语义**，等价实现落 Conex 的 Rust 结构。若某方言语义不明，以 `reference/opencode/` + `reference/DeepSeek-Reasonix/` 既有先例为准（`00-问题基线.md:53-61`）。
- 若发现分析文档未覆盖的新 gap（维度外问题），子 Agent 上报主控，主控可**动态加派子 Agent** 分析（附录 B§8），但不改问题基线本文件（只追加）。
