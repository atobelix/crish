# 能力描述与主循环接线层对比（Conex vs DeepSeek Harness）

> 战役：Conex 多模型适配战役 · 参考外部模式
> 维度：能力描述与主循环接线层（`ProviderCall` trait 契约 / DSH `resolveModel`+`resolveCallConfig` 分离 / 能力元数据消费链 / 错误分类与重试 / 请求头与会话亲和）
> 输出类型：只读对比分析 + 修复建议（唯一交付文件，中文，UTF-8 无 BOM）
> 基线问题编号：**G1 = 主循环未接线**；**G8 = 能力描述与请求校验分离语义待核查**

---

## 0. 结论先行

- **接线现状存在真实缺口（对应 G1）**：`ProviderCall` trait 契约已冻结 v1（`crates/session-loop/src/provider.rs:13-22,130-139`），但**全仓没有一个生产 `impl ProviderCall`**——只有 `TestProvider`/`Arc<TestProvider>`（`crates/session-loop/src/testing/mod.rs:156-227`）与 run_loop 测试里的 `ArcTestProvider`（`crates/session-loop/tests/run_loop.rs:66-74`）。真实适配层（把 `agent-provider` 请求构建 / HTTP / SSE 解析 / 分类 / 重试包装为 `stream()`）只在注释里约定待 B4/B6 实现。这是主循环侧「契约在、接上线缺」的冻结面。
- **能力描述面（resolve）与请求校验面（resolveCallConfig）在 Conex 尚未分离为两条显式路径（涉及 G8）**：`agent-provider` 的 vendor 归一化走的是**降级式**（`vendor.rs:319-346` `normalize_thinking_intensity` 对不支持档位**降级/钳制**），而 DSH 的契约是请求路径**绝不降级**——不在能力中的档位在网络 I/O 前以 `UNSUPPORTED_REASONING_EFFORT` 拒绝（`llm/src/index.ts:746-761`）；描述路径则是**宽容**（resolveModel 对拿不下的档位报「无默认值」而非抛错，`llm/llm-pi-ai/README.zh.md:115`）。Conex catalog 能力位（`catalog.rs:137-141`）确实存在 `supports_reasoning/supports_reasoning_effort/reasoning_effort_tiers`，但**没有任何消费链把它接到主循环请求侧**——`ProviderRequest` 无 reasoning 字段，`build_request` 不注入，UI 层无法按模型读档位。三者各自存在但互不接线。
- **能力元数据消费链断在发送侧**：DSH 全链（adapter resolveModel → `reasoning.efforts/defaultEffort` → `ModelSelect.tsx` 面板渲染 + 记入会话 → `prepareCall` 校验 → serializer 落请求体）。Conex 现状：`ProviderRequest` 无 reasoning（`provider.rs:70-91`）、`stream.rs` 事件层只有 `thought` 增量收取没有 effort 消费、UI 只有**应用级** `defaultThinkingLevel`（`clientApi.ts:77,135`）且只有降级直连路径用它（`directFetchBridge.ts:70-104,151-153`）；主 run 路径根本不带 effort。
- **错误分类覆盖 Conex 已超过 DSH**：Conex 13 类收敛（`error.rs:166-205`）完备覆盖 429/401/400/5xx/超时/abort/网络，重试 `should_retry`（`retry_decision.rs:131-168`）仅瞬态类、指数退避+Retry-After+60s 预算，与 DSH `httpErrorCode`（`adapter.ts:138-149`）+ llm-retry 同级。差距在**接线**：`stream()` 尚未调用 classify/retry，`orchestrator/recovery.rs` 阶梯 1 只是**镜像重试语义**（`recovery.rs:8-15`），需真实 `stream()` 才能把分类喂进主循环。
- **会话亲和头 Conex 只有单一 `x-grok-conv-id`**（`build_responses.rs:107-117`），DSH 有多头族 + pi-ai `sessionAffinityFormat`（`thinkingLevelMap`/`compat` 同源 `openai-completions` dialect 分发）。差距是「只有一种头、且未与主请求头合并路径打通」。

## 1. 接线现状：`ProviderCall` 契约 vs 全仓生产实现缺失（G1）

### 1.1 契约面（已冻结）

| Conex 现状                                                                                                                                                                       | 证据                                             |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| `ProviderCall` trait，签名 `async fn stream<'a>(&self, &ProviderRequest<'a>) -> Result<ProviderEventStream, ClassifiedStreamError>`                                              | `provider.rs:129-139`                            |
| 流式语义冻结 v1：流前 Err→重试阶梯；流中 Err→有内容保留收场/无内容进重试；每流恰好一个 stop；取消协作（partial salvage）；`'static` 返回流不借用 request；逐事件增量             | `provider.rs:13-22,117-129`；`stream.rs:294-316` |
| `ProviderRequest` 载荷：`messages: &'a [Arc<AgentMessage>]`、`tools: Vec<ToolSchema>`、`max_tokens: Option<u32>`、`system_prompt: Option<&'a str>`、`session_id: Option<String>` | `provider.rs:69-91`                              |
| 注释明写真实适配层是「B4/B6 集成时实现」                                                                                                                                         | `provider.rs:4-5`                                |
| 消费处（`loop/`）：`streaming.rs` 里 `provider.stream(&request).await`；`build_request` 只填 messages/tools/max_tokens/system_prompt/session_id                                  | `loop/handlers/streaming.rs:74,304-331`          |

### 1.2 生产实现缺失（无）

- 全仓 `impl ProviderCall` 仅测试替身：`TestProvider`（`testing/mod.rs:156-216`）、`impl ProviderCall for Arc<TestProvider>`（`testing/mod.rs:219-227`）、run_loop 的 `ArcTestProvider`（`run_loop.rs:66-74`）。
- 没有任何 crate 把 `agent-provider` 的 `provider_stream`/`classify_provider_error`/request 构建包装为 `stream()`。
- 会话亲和头、reasoning 归一化、缓存键等 `agent-provider` 已有能力，**都没有被 `ProviderRequest` 消费**——因为请求构造面（`build_request`）根本不在 `agent-provider` 上。

### 1.3 DSH 对应做法（参考基线）

DSH 的 adapter 是**传输-only**（`adapter.ts:3-9`），连接事实经 thunk 每操作解析（`DeepSeekAdapterOptions.options`）、凭据经 `resolveApiKey`，一个实例服务所有注册模型（`adapter.ts:151-169`）。Conex 没有对等的「用一个 trait 实例服务全部模型、每调用解析配置/凭据」的适配层实体，只有契约与替身。

### 1.4 差距结论

| 维度     | 差距                                                                                                                                                                                                                                                                                                              |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| G1 接线  | **主循环未接线**：`ProviderCall` 契约冻结面明确，但生产 `impl` 缺失。这是 G1 的实证：契约在、接上线不在。                                                                                                                                                                                                         |
| DSH 对比 | Conex 的 `ProviderCall` 更接近 DSH `LlmAdapter.stream`（同是 transport-only、同用 `ClassifiedStreamError` 上抛已分类错误）。但 DSH 有**注册表/registration**（`prepareCall` 绑定 registration，`llm/src/index.ts:779-813`），Conex 的 `stream()` 无 registration 概念——多可供方/多注册/凭据按次解析的能力面缺位。 |

### 1.5 修复建议（逻辑改造点 + 验收断言，标注 G1）

- **建议点 A（G1）**：新增生产 `impl ProviderCall`（建议放 `crates/agent-provider` 或新增 adapter crate），把 `agent-provider` 的请求构建（chat-completions / responses 双轨，`build.rs`/`build_responses.rs`）、HTTP 发送、SSE 解析、`classify_provider_error`、`provider_stream`（重试）包装为 `stream()`。
  - 验收断言 A1：`cargo test` 层面新增一个「生产 adapter 含重试」集成测试，输入 `RetryPolicy{max_retries:1}` 时首次 `stream()` 返回流前 Err（429 类）后第 2 次成功，第 1 次不产出任何事件。
  - 验收断言 A2：`loop/mod.rs` 主循环换用该生产 adapter（替代 `TestProvider`）跑通回环：SSE 事件 → `ProviderStreamEvent` 逐事件流出（禁止聚合），`stream.rs` 的 `consume` 输出 Message + metadata。
  - 验收断言 A3：`::stream()` 返回流为 `'static` 且不借用 `ProviderRequest`（已有契约），生产实现用 crate 级测试锁定「请求体在返回流前序列化」。

## 2. 能力描述 / 请求校验分离语义（G8 核查）

### 2.1 对照关键：DSH 是两条路径、两套失败语义

| 路径                                          | DSH 做法                                                                                                                                                                                                                                                                                                                                            | 失败语义                                                                          |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| **描述（resolveModel）**                      | 描述能力**永不因坏配置抛错**：单模型拿不下的 profile 档位 → 报「没有默认值」，绝不抛错，坏配置暴露在被执行处而非被描述处（`llm-pi-ai/README.zh.md:115`）                                                                                                                                                                                            | 一个配错的 profile 字段**不得藏掉整个提供方**（否则连支持该档位的模型也一并消失） |
| **请求校验（resolveCallConfig/prepareCall）** | `requested.reasoningEffort` 不在 `info.reasoning.efforts` → `UNSUPPORTED_REASONING_EFFORT`，**网络 I/O 前拒绝，不降级、不钳制**（`llm/src/index.ts:746-761`；`RESOLVE_CALL` 文档 `llm/src/index.ts:720-732`）；adapter defaults materialize（`defaultEffort`/`defaultMaxTokens` 落 config，`llm/src/index.ts:740-742`）；`LlmCallConfig` 会话级记录 | 明确拒绝                                                                          |

关键设计：`reasoning` 是 **per-MODEL 能力**，同一提供方下各模型接受的档位不一致，所以提供方级控件无法表达（`ProviderEditor.tsx:14-18` 明确注释「effort 是 per-MODEL 能力」）。resolveMode 抛错会让整个提供方从基于它构建的模型目录消失。

### 2.2 Conex 现状核查

| 面                        | Conex 现状                                                                                                                                                                                | 证据                                                                                                                                                                    |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **归一化（vendor 行为）** | **降级式**：`normalize_thinking_intensity`——档位不在 `capability.levels` 时降级（xhigh→high、minimal→low、其余取最大支持档位），`Off`/不支持思考 → `None`                                 | `request/vendor.rs:319-346`                                                                                                                                             |
| **能力表推断**            | `infer_thinking_capability(model)` 最长前缀命中 `MODEL_SERIES_CAPABILITIES`（OpenAI/Anthropic/Gemini/DeepSeek/Qwen/GLM/Kimi），未命中 → `NO_THINKING`                                     | `request/vendor_capability.rs:158-170`，表 `:106-156`                                                                                                                   |
| **catalog 能力位**        | `catalog.rs:137-141`：`supports_reasoning`、`supports_reasoning_effort`、`reasoning_effort_tiers: Option<Vec<String>>`                                                                    | `crates/agent-provider/src/models/catalog.rs:134-153`                                                                                                                   |
| **wire 注入**             | `resolve_thinking_params(capability,intensity,endpoint)` 产出 vendor 原生字段（`reasoning.effort`/`reasoning_effort`/`thinking.budget_tokens`/`generation_config.thinking_level`）        | `request/vendor.rs:348-390`                                                                                                                                             |
| **主循环请求侧**          | `ProviderRequest` **无 reasoning 字段**；`build_request` 不注入 effort                                                                                                                    | `provider.rs:69-91`；`loop/handlers/streaming.rs:324-331`                                                                                                               |
| **UI**                    | 只有**应用级** `defaultThinkingLevel`（`clientApi.ts:77,135,311-312,447`；`chatInvariants.test.ts:103-119` 断言档位集 `['off','low','medium','high']` 默认 `'medium'`），**非 per-model** | `apps/crish-desktop/src/api/clientApi.ts:77,447`；`apps/crish-desktop/src/__tests__/chatInvariants.test.ts:103-119`（注意：这是**前端契约自洽测试**，不是能力目录真值） |

**核查结论（回答 G8）**：

1. **Conex 已有「描述面 vs 请求面」的素材，但未分离成两条显式路径**：
   - 描述面素材：`vendor.rs/infer_thinking_capability` + `vendor_capability.rs` 静态表 + `catalog.rs` 能力位。这些**可以**支撑「描述一个模型支持哪些档位」，但当前**没有**暴露为一个被 UI/目录/consum 消费的只读描述接口（对应 DSH `info.reasoning.efforts`）。
   - 请求面素材：`resolve_thinking_params` + `reasoning_effort_object` 是「给定 effort 产出 wire」的**单点换算**，但当前**没有**「该校验是否支持」的拒绝语义——它直接落在 `normalize_thinking_intensity` 的降级上。
2. **坏配置行为现状**：
   - **描述侧（能力位/静态表）**：`catalog.rs` 的能力位是**数据**而非判定；配置了 `supports_reasoning_effort=false` 或 `reasoning_effort_tiers` 不含某档位的模型，**没有任何消费点因此拒绝或降级**——它只是躺在目录 JSON 里。即：描述面「坏配置」既不抛错也不隐藏（因为根本没被读）。
   - **请求侧（vendor 归一化）**：当前归一化是**降级式**（`vendor.rs:319-346`）。对一个能力表说不支持 `reasoning_effort=X` 的模型，现状会把 X **钳到** `capability.levels.last()` 或 None（不发送），**不会拒绝**。这与 DSH 的「请求路径拒绝、不降级」**相悖**——`normalize_thinking_intensity` 事实上扮演了「隐式钳制」，会掩盖选中的无效档位，让 provider 拿到模型不接受的参数（或静默不发）。
   - **纯未知模型**：一个 catalog/静态表未覆盖的模型 → `infer_thinking_capability` 返回 `NO_THINKING`（`vendor_capability.rs:159-169`）。此时请求侧 `normalize_thinking_intensity` 直接返回 `None`（`vendor.rs:322-323`）——即**静默不发思考参数**，不会拒绝也不会问询。DSH 对无 `reasoning` 元数据的模型是「完全不公开 reasoning 能力、提供方默认项」且**显式请求无效档位会拒绝**（`llm-pi-ai/README.zh.md:113-115`）。

**核心缺口（G8）**：Conex **缺少「描述面坏配置不隐藏提供方 / 请求面坏配置在网络 I/O 前拒绝」这两个语义的接线**。素材齐全（能力位、静态表、wire 换算），但：a) 无「描述只读接口」（近似 DSH `resolveModel`）；b) 请求侧用降级代替拒绝；c) `ProviderRequest` 无 reasoning 透传，两条面都没有主循环触达点。

### 2.3 修复建议（G8）

- **建议点 B（G8）**：新增「描述面只读接口」——把 `infer_thinking_capability` 结果 + `catalog` 能力位合并成稳定的「模型能力描述」（档位白名单 + 默认档位 + 是否支持 reasoning），供 3 处消费：UI 档位面板、目录服务、请求校验。
  - 验收断言 B1：对一个 catalog 声明 `supports_reasoning_effort=false` 的模型，描述接口返回「不支持 reasoning」，**不因该模型配错而隐藏同提供方其它模型**（对齐 `llm-pi-ai/README.zh.md:115`「坏配置暴露在被执行处而非描述处」）。断言用单测锁定：同 provider 下 A 模型坏配置时，B 模型仍可被描述。
  - 验收断言 B2：描述接口对某模型报告指定档位集（如仅 `['low','medium','high']`），未覆盖档位**不出现**（对齐 DSH `efforts` 白名单语义）。
- **建议点 C（G8）**：请求侧**从降级改为拒绝**——把「校验 effort 是否在能力内」从 `normalize_thinking_intensity` 的钳制中拆出，变成一条独立的校验路径（近似 `resolveCallConfig`），在网络 I/O 前以分类错误拒绝。
  - 验收断言 C1：对声明 `reasoning_effort_tiers=['low','medium','high']` 的模型请求 `max` → 请求路径返回**拒绝**分类（对应 DSH `UNSUPPORTED_REASONING_EFFORT`），**不改写**为 `high`；错误码收敛到 `conex-types` 13 类内新增一个 reasoning 域错误或复用 `InvalidRequest`。
  - 验收断言 C2：对能力表未知（`NO_THINKING`）的模型，显式请求任意非空 effort → 拒绝；省略 effort → 不发送思考参数（保留提供方默认，对齐 `llm-pi-ai/README.zh.md:113`）。
  - 验收断言 C3：保留一个「明确允许降级」的显式开关位（默认关闭），避免破坏既有 `normalize_thinking_intensity` 的调用方——但**默认路径走拒绝**。
- **建议点 D（跨维度）**：`ProviderRequest` 增加 reasoning 档位字段（见 §3）。

## 3. 能力元数据消费链对比

### 3.1 DSH 全链（reference 基线）

```
adapter.resolveModel → LlmResolvedModelInfo.reasoning = { efforts[], defaultEffort? }
   ↓ (注册表校验) llm/src/index.ts:675-717  INVALID_MODEL_REASONING 拦截空/重复/未知默认档位
ModelSelect.tsx 按 model.reasoning 渲染 effort 面板（effortChoices，:90-102）
   + selection 记入 per-session ModelDirectory（:8-12,181-203）
prepareCall → resolveCallFor 校验（:734-768）→ 请求在网络 I/O 前拒绝
adapter serializer 落请求体：header 记录（adapter.ts:283-295）+ 凭据/连接每请求快照
```

关键点：effort 是 **per-MODEL** 粒度（`ProviderEditor.tsx:14-18`）；选择记入**会话**但不污染提供方级 config；`INVALID_MODEL_REASONING` 在注册表层面校验 metadata 合法性（`llm/src/index.ts:675-717`）。

### 3.2 Conex 现状

| 链环节               | Conex 现状                                                                                                                  | 证据                                                                                                                                             | 是否缺失                                    |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------- |
| **能力公布（描述）** | 存在素材：`infer_thinking_capability`（静态表）+ `catalog.rs` 能力位                                                        | `vendor_capability.rs:106-170`；`catalog.rs:137-141`                                                                                             | **未接线**：无被 UI/consum 消费的只读描述面 |
| **UI 档位选择**      | 只有应用级 `defaultThinkingLevel`（非 per-model）；无 effort 面板                                                           | `clientApi.ts:77,135,311-312,447`；`crish-desktop/chatInvariants.test.ts:103-119`                                                                | **缺失**：无 DSH 式每模型档位选择器         |
| **模型选择 UI**      | 有 provider 级模型列表：`settings-models/ModelsSettingsTab.tsx` + `ModelBadgePickerMenu.tsx`，`providerProfiles`（LS 存储） | `apps/crish-desktop/src/components/provider/ModelBadgePickerMenu.tsx`；`apps/crish-desktop/src/components/settings-models/ModelsSettingsTab.tsx` | **缺档位**：只有模型无 effort 维度          |
| **请求携带**         | `ProviderRequest` 无 reasoning 字段；`build_request` 不注入                                                                 | `provider.rs:69-91`；`loop/handlers/streaming.rs:304-331`                                                                                        | **缺失（核心断点）**                        |
| **wire 换算**        | 有 `resolve_thinking_params`/`buildThinkingParams`，但后者仅降级直连路径在用                                                | `request/vendor.rs:348-390`；`crish-desktop/directFetchBridge.ts:70-104,151-153`                                                                 | **主 run 未用**                             |
| **会话记录**         | 无 reasoning 档位的会话/请求级持久化（metadata 只在 `stream.rs` 收口写 usage/thought，无 effort）                           | `stream.rs:446-507`                                                                                                                              | **缺失**                                    |

**能力元数据消费链的断点逐一确认**：

- 能力公布→：静态表/能力位存在但无人消费（`router` 直连桥接有自己的 `buildThinkingParams` 穷举档位，与 Rust 静态表**双实现漂移**）。
- →UI 档位选择：无 per-model effort 控件；即使有 `defaultThinkingLevel`，也不是模型粒度（对齐粒度缺失：DSH effort 是 per-model，Conex 是 app-level）。
- →请求携带：`ProviderRequest` 无字段，主循环无法携带。
- →会话记录：`stream.rs` metadata 无 effort 维度。

### 3.3 修复建议

- **建议点 D（G8 + G1）**：`ProviderRequest` 增加 `reasoning_effort: Option<ReasoningEffort>`（引入 `ReasoningEffort` 枚举或复用 `agent-provider` 的档位类型），`build_request` 从会话态填充。
  - 验收断言 D1：`ProviderRequest { reasoning_effort: Some(High) }` 经生产 adapter 的 chat-completions 序列化后请求体含 `reasoning_effort: "high"`（对齐 `reasoning_effort_object` wire）。
  - 验收断言 D2：`reasoning_effort: None` 或 `Off` → 请求体不含任何 reasoning/thinking 参数（逐字节对比，对齐 `llm-pi-ai`「off 通过省略表示」）。
- **建议点 E（G8）**：UI 提供**每模型** effort 选择（对齐 DSH `ModelSelect`），档位集合与默认值来自描述面只读接口（§2.3 建议点 B）；选择写入 `session_meta` + 请求负载，不改提供方级 config。
  - 验收断言 E1：对能力描述只有 `['low','medium','high']` 的模型，UI effort 面板只渲染这三项 + 提供方默认，不渲染 `minimal/xhigh/max`。
  - 验收断言 E2：选中档位经 run 进入请求负载，并在 `ProviderRequest` 快照断言中可查（复用 `run_loop.rs:139-141` 的 `request_*` 断言形态扩展一个 `request_reasoning_effort`）。
- **建议点 F（G1）**：主循环 `build_request` 需要知道当前会话/配置的模型能力——建议在 `AgentSessionLoop` 构造或 run 启动时注入「模型能力表 + 当前档位决议」，而非让 adapter 自行猜测，避免与 UI 双源（对齐 DSH「权威元数据在 adapter，描述经由 resolveModel 单源」）。

### 4.1 对比表

| 分类状态码覆盖 | 13 类收敛：abort/413/Cloudflare/401-403/402/404-405-415/400-422/429/5xx/超时/网络/流协议/未知（`error.rs:89-164,219-330`）                               | AUTH(401/403)/QUOTA/409→?/429/400→CONTEXT_WINDOW_EXCEEDED or INVALID_REQUEST/≥500→SERVER/其余 HTTP_n（`adapter.ts:138-149`）      | **Conex 更全**（DSH 把 context window 只归到 400，Conex 用消息模式 + 400/422 判定）；Conex 还支持 422、Cloudflare、端点 404/405/415 细分 |

### 4.2 缺失分类覆盖核查

- 429/401/400/5xx/超时/abort：Conex `classify_provider_error` 全覆盖 ✓
- 分类→重试决策在 Conex 是**两个独立函数**（`classify_provider_error` + `should_retry`），DSH 是 adapter 内 `httpErrorCode` → llm-retry 同包。Conex 已有「分类与收口分离」（`retry.rs:9-10`「context_length 由上层压缩处理，00 D5」），比 DSH 更结构化。

### 4.3 修复建议

- **建议点 G（G1）**：让 `stream()` 真实调用 `classify_provider_error` + `provider_stream`（重试），并把分类结果透传到 `ClassifiedStreamError`（流前）与 `Stop{error_kind}`（流中，`stream.rs:149-162` 已预留）。
  - 验收断言 G1：生产 adapter 对 HTTP 429 响应 → `stream()` 流前返回 `ClassifiedStreamError{kind:RateLimit, retryable:true, retry_after_ms:…}`；对 HTTP 401 → `kind:Auth, retryable:false`（对齐 `error.rs:104-109` 与 `should_retry` 判定）。
  - 验收断言 G2：`stream()` 中途收到 `malformed-frame` → 流条目 `Err(Stream)` 且 `retryable` 按 13 类默认（`error.rs:154-158` + `stream.rs:149-162`），验证 `orchestrator/recovery.rs` 阶梯 1 与 `agent-provider` 分类**同真源**（消除镜像漂移，`recovery.rs:12-14` 已声明测试锁定）。

### 5.2 多提供方场景差距

- DSH 的头族设计（user-id/session-id/compact + attribution）是**为多供方 + 遥测归因**设计的；Conex 的 `x-grok-conv-id` 是格罗克单体粘性路由语义，不通用。pi-ai 的 `compat` dialect 分派（`sessionAffinityFormat` 对应 `openai-completions` 的 dialect 检测）说明**不同提供方需要不同会话亲和表达**。
- 现状 Conex 中 `affinity_http_headers` 依赖 `CachePolicy`（`build_responses.rs:112`），且只在理论 http 发送层调用；主 loop 走 `stream()`，找不到注入点。

### 5.3 修复建议

- **建议点 H（G1）**：在 `ProviderCall` 生产实现中定义「请求头注入 seam」，让会话亲和头族可按提供方适配注入（对齐 `attributionHeaders` + `x-deepseek-harness-*`）。
  - 验收断言 H1：生产 adapter 的请求头含会话亲和头（`session_id` 非空时注入 session 头）；`session_id` 为空时不注入（对齐 `adapter.ts:289-291` 的 `options.sessionId !== undefined` 守卫）。
  - 验收断言 H2：`ProviderRequest` 的会话亲和语义至少覆盖「会话一致 → 头稳定」，多提供方可经 seam 切换头族（K=V 集合由提供方决议，而非硬编码单头）。
  - 验收断言 H3：缓存会话亲和（`affinity_http_headers` 的 `x-grok-conv-id`，`build_responses.rs:107-117`）与遥测/亲和头合并后仍可通过既有 `build_chat_completions_request_body` 序列化契约单元验证（不破坏请求体 JSON 形状）。

## 6. B4/B6 适配层要实现的最小面（回答「把 agent-provider 包装为 ProviderCall 需要哪些环节」）

基于 §1-5，真实适配层把 `agent-provider` 包装为 `ProviderCall::stream` 需要的最小环节（逻辑面，不含工期）：

1. **请求面装载**：把 `ProviderRequest`（messages/tools/max_tokens/system_prompt/session_id + 新增 reasoning_effort §3）映射为 `agent-provider` 的 `RequestBuildContext` / `ChatCompletionsRequestOptions`（chat + responses 双轨，`build.rs`/`build_responses.rs`），完成请求体序列化（返回流为 `'static`、不借用 request，`provider.rs:22,128`）。
2. **凭据/配置/能力决议**：每调用解析（对齐 DSH 的 thunk + `resolveApiKey`，`adapter.ts:74-86`)——端点 + 能力表（描述面 §2.2 建议点 B）+ 会话亲和头（§5.3 建议点 H）在一次快照内冻结。
3. **HTTP 发送层**：chat-completions / responses 双端点 + 请求头注入（`build_responses.rs:107-117` + §5.3）。Conex 现状欠 reqwest 发送层的 `stream()` 触发点（G1）。
4. **SSE 解析 → 事件映射**：把「parseSse」等价物映射为逐事件 `ProviderStreamEvent`（text/thought/tool-call/diagnostic/stop，`stream.rs:120-197`），满足「逐事件流出、禁止聚合」（`provider.rs:126-128`）。
5. **错误分类 + 重试闭环**：`classify_provider_error`（`error.rs:219-330`）把 HTTP/SSE/transport 错误分类 → 流前 `Err(ClassifiedStreamError)` / 流条目 `Err`；`provider_stream`（`retry.rs:10-13`）指数退避仅瞬态类（§4.3 建议点 G），与 `orchestrator/recovery.rs` 阶梯 1 同真源。
6. **规则对齐**：chat 轨 reasoning 走 `resolve_thinking_params`；responses 轨**不注入** reasoning（`build_responses.rs:34-35` 已声明「vendor 注入 chat 专有面」）；缓存口径 `CacheAccounting`（Anthropic/Gemini 系 Excluded，`stream.rs:67-79`）显式传递。

## 8. 需标注的风险与依赖

- **`llm-pi-ai` 的 `sessionAffinityFormat`/`detectCompat` 引用**：任务引用的 `reference/deepseek-harness/packages/llm/llm-pi-ai/dist/api/openai-completions.js detectCompat` 在该仓库内**不存在**（dist 非入库），等价 source 是 `llm-pi-ai/src/catalog.ts` 的 `resolveModelCompat`（`thinkingFormat`/`supportsReasoningEffort`，`catalog.ts:372-411`）与 `src/config.ts:188-221`；`openai-completions` 的 dialect 分派在 pi-ai SDK 内部（vendored），Conex 侧只能等价对齐其「按 compat 开关切 wire 拼写」语义，无法对齐其私有实现细节。
- **G8 的「坏配置不藏整个提供方」在 Conex 现状是「坏配置被完全忽略」**——能力位数据存在但不被读取，故现状既**不会**藏（符合 DSH 目标效果）也**不会**拒绝（请求侧反而降级静默放行）。修复时应以「拒绝 + 不藏」为目标，而非照搬 DSH 的「resolveModel 不抛错」字面——Conex 现状根本没有 resolveModel，需从零建立描述面。
- **`defaultThinkingLevel` 的档位集（`['off','low','medium','high']`）与 `agent-provider` 静态表档位（`minimal/low/medium/high/xhigh/max`，`vendor_capability.rs:12-29`）不一致**——前端契约测试（`chatInvariants.test.ts:103-119`）是自洽假说，不是能力真值；修复时须消除双实现漂移（建议点 F）。
- 本分析为只读，未修改任何产品代码，交付唯一文档 `docs/provider-adapter-campaign/analysis/04-能力描述与接线层对比.md`（UTF-8 无 BOM），未提交 git。
