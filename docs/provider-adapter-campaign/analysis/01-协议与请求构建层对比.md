# 01 · 协议与请求构建层对比

> 战役：Conex 多模型适配（参考外部模式）
> 对比维度：协议覆盖 / 模型级协议路由 / 字段名兼容 / 流式与 usage / 消息序列化
> 对比对象：Conex `crates/agent-provider/` + 接线层 `apps/agent-workbench/src-tauri/src/engine_provider.rs`
> 参考外部：`@earendil-works/pi-ai`（node_modules）与 DeepSeek Harness（`reference/deepseek-harness/`）
> 设计定稿文档：`docs/provider-adapter-campaign/00-问题基线.md`（G4/G5/G6/G7 编号沿用）
> 全部证据为 `文件路径:行号`；仅产出本分析文档，不修改任何产品代码、不提交 git。

---

## 0. 总体结论（先行）

1. **协议面本身已具备四个解析器**（chat / responses / anthropic / gemini），但**真实请求链路 `HttpProviderCall` 只接了 chat 与 responses 两轨**（`engine_provider.rs:628-631`），anthropic / gemini 解析器与 **anthropic / gemini 请求构建**完全没有接线到实时 dispatch。Conex 是「协议解析能力 > 协议接线能力」，pi-ai 是「每模型配置即驱动协议」，DSH 直连是「单协议封装」。
2. **模型级协议路由在 Conex 是「全局 endpoint + 二元 chat/responses 分流」**，pi-ai 是「每模型 `api` 字段」；Conex 的 `mode` 字段（`catalog.rs:59`）至今未被请求构建消费。
3. **字段名兼容与 developer role 需要 per-vendor/per-model 的 compat 面**，Conex 目前只有 `ReasoningVendor` 与 `MaxTokensField` 三枚举，缺少 pi-ai `detectCompat` 的完整探测面（system/developer role、空 content、requiresReasoningContentOnAssistantMessages 等）。
4. 流式与 usage：Conex 双段超时/abort 已健壮，但 usage 的口径归一（completion_tokens 已含 reasoning、cached ↔ cache_write 拆分）与 pi-ai 存在口径差异。
5. 消息序列化：Conex `to_chat_messages` 已将 assistant content 做纯字符串、空文本用 `None→null`；pi-ai 强调「空 content 用 `""` 而非 `null`」与「纯文本 string 而非块数组」，这正是 DeepSeek 官方 serialize 也强调的（`serialize.ts:87-95`）。

以下逐维度对比。

| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| catalog 每条目有 `mode: "chat"\|"responses"\|"both"` 字段（`catalog.rs:59`）与 `supports_responses: bool`（`catalog.rs:136`），并有 `supports_responses_for` 查询（`catalog.rs:279-282`）                                  | pi-ai 每模型条目顶层 `api` 字段即协议路由：opencode-go.json 中 `deepseek-v4-flash`→`"api":"openai-completions"`、`grok-4.5`→`"api":"openai-responses"`、`minimax-m3`/`qwen3.7-max`→`"api":"anthropic-messages"`（opencode-go.json）；`Models.getModel`→`streamSimple` 按其 api 分发 | **路由按键不同**：pi-ai 用**每模型** `api`；Conex 用**全局** `Endpoint` + `supports_responses`。`mode` 字段虽存在但**至今未被请求构建消费**——它是「死配置」 |

**差距结论（具体）**：

- **缺什么**：一个「模型（或 profile）→ 协议」的可表达映射，能支持同一 provider 下多协议并存、且请求构建/URL/解析器随之一致切换。
- **影响什么**：前端已预置 `opencode-go` profile（`00-问题基线.md:24`），其下 `deepseek-v4-flash` 走 completions、`grok-4.5` 走 responses；Conex 全局 endpoint 无法在同一 profile 内为不同模型切换响应不同协议。且 `mode` 字段语义悬空，`supports_responses` 被双重借用。
- **证据在哪**：`catalog.rs:59`（mode 定义）、`catalog.rs:136`（supports_responses 定义）、`config.rs:44-53`（全局 Endpoint）、`engine_provider.rs:276-278`（responses 轨判定）、`engine_provider.rs:315-328`（vendor 闭包导致 Grok/MiniMax 无法路由）。
- **涉及基线**：**G4**（`00-问题基线.md:26-27`）。

| Conex 现状（文件:行号）                                                                                                                                                                                                                                       | pi-ai / DSH 做法（文件:行号）                                                                                                                                                                                                                                                                                                                                                                                 | 差距结论                                                                                                                                                                                                                                       |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `MaxTokensField` 三枚举 `MaxTokens / MaxCompletionTokens / MaxOutputTokens`（`build.rs:53-57`），chat 轨用 `max_tokens`/`max_completion_tokens`/`max_output_tokens`（`build.rs:62-64`）；responses 轨硬编码 `max_output_tokens`（`build_responses.rs:85-87`） | pi-ai `compat.maxTokensField` 二值：`max_tokens` / `max_completion_tokens`（openai-completions.js:1151），`detectCompat` 按 URL 判三元 provider（chutes/moonshot/cloudflare-gateway/together/nvidia/ant-ling→`max_tokens`，否则 `max_completion_tokens`；openai-completions.js:1141），构建时二选一（openai-completions.js:531-538）。opencode-go.json `deepseek-v4-flash.compat.maxTokensField:"max_tokens"` | Conex 三枚举**已具备切换能力但不按模型决定**——`HttpProviderCall.request_options` 恒 `MaxTokensField::MaxTokens`（`engine_provider.rs:446`），未读取 catalog `mode`/能力位或模型级 `maxTokensField`。pi-ai 是「每模型/每 URL 探测后决定字段名」 |

## 4. 流式与 usage

| Conex 现状（文件:行号）                                                                                                                                                                                                                                                                | pi-ai / DSH 做法（文件:行号）                                                                                                                                                                                                                                                                                                                                                                                             | 差距结论                                                                                                                                                                                                             |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SSE 帧层通用 `SseParser`/`read_sse`（`sse/frame.rs`、`sse/reader.rs:158-211`）；双段超时 first-byte / idle（`sse/reader.rs:101-110`、`223-247`）；abort 经 watch 中断挂起 read，错误上抛不静默（`sse/reader.rs:213-248`）。真实流走 `stream_frames` 真增量（`transport/mod.rs:73-79`） | pi-ai 走各协议 SDK 的流式；OpenAI SDK 自动 `stream:true` + `stream_options:{include_usage:true}`（openai-completions.js:518,526）；Anthropic `message_start` 初始 usage + `message_delta` 覆盖（anthropic-messages.js:386-394,537-561）；Gemini `usageMetadata` 逐帧覆盖（google-vertex.js:169-176）。DSH 直连 `stream:true` + `stream_options:{include_usage:true}`（serialize.ts:177），idle watchdog（adapter.ts:227） | 帧层/超时/abort 已对齐且更彻底（双段超时）。**usage 归一口径有差**                                                                                                                                                   |
| chat 轨 usage：`parse_usage` 直接透传 provider 字段（chat.rs）；消费聚合 `ProviderUsage{prompt_tokens, completion_tokens, ...}`（consume/mod.rs:330-339）                                                                                                                              | pi-ai `parseChunkUsage`：`input = max(0, prompt_tokens - cached_tokens - cache_write_tokens)`、`cacheWrite` 单列、`reasoning = completion_tokens_details?.reasoning_tokens`（openai-completions.js:1057-1082）；Anthropic `useage.totalTokens = input+output+cacheRead+cacheWrite` 逐项非空覆盖（anthropic-messages.js:386-394,535-562）                                                                                  | pi-ai **显式做了「prompt 已含 cache 的剥离」**（Included 语义）与 reasoning 拆分；Conex 依赖会话消费侧默认 Included（`engine_provider.rs:384-386` 注释），chat 轨未显式剥离 cached 才得到 cache_read 口径            |
| responses 轨：终态 `response.completed` 携带完整 usage，不注入 stream_options（`build_responses.rs:28-29`）                                                                                                                                                                            | pi-ai responses usage 从 `response.usage` 解析并 applyServiceTierPricing（openai-responses-shared.js:416-436）                                                                                                                                                                                                                                                                                                            | responses 轨不注入 stream_options 已与官方对齐；但缺少 pi-ai 的「reasoning_tokens 从 output_tokens_details 拆分、cache_read/cache_write 从 input_tokens_details 拆分」归一口径（openai-responses-shared.js:420-427） |

**差距结论（具体）**：

- **缺什么**：与 pi-ai 一致的 usage **归一化库**（cached↔cache_write 单列语义、reasoning 从 completion/output 内拆分、total 口径重算、serviceTier 乘价）。
- **影响什么**：会话计数与前端费率在「prompt 含缓存」的 provider（Included 语义）下 cache_read 被重复计入 prompt，成本与 token 数据不准；OpenAI Responses `reasoning_tokens` 未拆分，思考 token 与正文 token 混在一个字段。
- **证据在哪**：pi-ai openai-completions.js:1057-1082（parseChunkUsage 剥离语义）、openai-responses-shared.js:420-427（input_tokens_details/output_tokens_details 拆分）；Conex `engine_provider.rs:384-386`（依赖默认 Included）、`consume/mod.rs:789-799`（逐字段透传，无拆分逻辑）。

## 5. 消息序列化细节

| Conex 现状（文件:行号）                                                                                                                                                                                                                                                                                                    | pi-ai / DSH 做法（文件:行号）                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | 差距结论                                                                                                                                                                                                                                                                                                             |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| assistant content：`to_chat_messages` 中文本 join 成 `ChatContent::Text`（纯字符串，`messages.rs:240-291`），空文本→`content: None`→序列化 `null`（`messages.rs:146-148`）；`ReasoningContentMode::{Omit,Include,Require}`（`messages.rs:44-54`），DeepSeek 工具轮必带 `reasoning_content`（`engine_provider.rs:494-499`） | pi-ai assistant **content 纯字符串**（非块数组）——openai-completions.js:878-885 明确注释「块数组非标准，DeepSeek V3.2/NVIDIA 会镜像递归嵌套」；只在有 thinking 且有 `requiresThinkingAsText` 时改成 `[{type:text}]`（openai-completions.js:852-858）；**空 content 用 `""` 而非 `null`**（openai-completions.js:836-839 `requiresAssistantAfterToolResult ? "" : null`，且 DeepSeek 系列 924-928 强制 `reasoning_content:""`）。DSH serialize.ts:95 同样「Text-less turns send "" — NEVER null」 | Conex 空 assistant content 发 `null`（`messages.rs:146-148`）；DSH 明确坚持 `""`，两者冲突。Conex `Require` 模式只在 DeepSeek 工具轮回传 reasoning，pi-ai 的 `requiresReasoningContentOnAssistantMessages` 是所有 assistant（含纯思考轮）强制 `reasoning_content:""`；Conex 无「纯思考轮（无工具轮）也要带键」的语义 |
| 思考回传：`ReasoningContentMode::Include` 有思考才带，`Require` 无思考也带空串（`messages.rs:187-192`），但 `engine_provider.rs:496-498` 只对 DeepSeek 用 `Require`，其余 `Omit`                                                                                                                                           | pi-ai：仅 DeepSeek compat `requiresReasoningContentOnAssistantMessages:true` 时所有本模型 assistant 强制 `reasoning_content`（openai-completions.js:924-928）；非 DeepSeek 有 thinking 时 map 到 `[thinkingSignature]=...`（openai-completions.js:869-875）                                                                                                                                                                                                                                      | DeepSeek 工具轮正确。但 **pi-ai 的强制键面向「模型」而非「vendor」**，且扩展到纯思考轮；Conex 以 vendor 维度（DeepSeek）而非模型维度触发，且 `Include` 在非 DeepSeek 下不强制键                                                                                                                                      |
| tool_calls：`arguments` 用 canonical JSON（`messages.rs:249-253`），id 消毒（`sanitize_tool_call_id`）；Responses input items 顺序 reasoning→message→function_call（`messages.rs:384-405`）                                                                                                                                | pi-ai tool_calls：`arguments: JSON.stringify(block.arguments)`（openai-completions.js:904），toolResult 恒带 text（image→占位，`(no output)`，openai-completions.js:956）。DSH serialize.ts:99-100 `toolCalls.length>0 && reasoning.length>0 ? {reasoning_content}`                                                                                                                                                                                                                              | 结构与 canonical 对齐更严格，但**空 tool result** 的占位语义：DSH 用 `(no output)`（serialize.ts:136）、pi-ai 用 `(no output)` 占位；Conex `stringify_tool_output` 空→`""`（messages_content.rs:54），未加占位文案                                                                                                   |
| user 多模态 content parts：`ChatContent::Parts`（`messages.rs:58-61`），image_url（`messages.rs:91-98`）                                                                                                                                                                                                                   | pi-ai user 多模态转 `[{type:text},{type:image_url,image_url:{url:'data:...'}}]`（openai-completions.js:810-832）；Responses 用 `input_image`（openai-responses-shared.js:116-119）                                                                                                                                                                                                                                                                                                               | 基本对齐；DEEPCHECK/Conex 对 inline data-url 的 strip 是增量能力（messages_content.rs:59-80）                                                                                                                                                                                                                        |
| reasoning_detail：Conex 只有 `reasoning_content` 单键                                                                                                                                                                                                                                                                      | pi-ai 另有 `reasoning_details`（由 tool_calls 的 thoughtSignature 解析，openai-completions.js:909-922）                                                                                                                                                                                                                                                                                                                                                                                          | pi-ai 在 tool-call 上回传 `reasoning_details`（结构化思考签名），Conex 无此通道                                                                                                                                                                                                                                      |

**差距结论（具体）**：

- **缺什么**：①「空 content 用 `""` 而非 `null`」的 **assistant 无内容消息硬化策略**；②「assistant 纯思考轮（无工具轮）也强制 `reasoning_content` 键」的模型级语义；③ tool result 无内容时的占位文案。
- **影响什么**：Conex 空 assistant 轮发 `content:null`，与该 wire 轨上「DeepSeek 会 400」的既有教训（`messages.rs:265-277` 已内置 Wire-Only 角色交替防 400）同一风险面但只防了「连续 assistant」没防「null content」；纯思考轮若按 `Omit` 会缺键被拒。
- **证据在哪**：`messages.rs:146-148`（空→null）、`messages.rs:187-192`（Require 仅 DeepSeek 且依赖 vendor 维度）、`engine_provider.rs:494-499`（vendor 维度判定）、pi-ai openai-completions.js:836-839/924-928、DSH serialize.ts:87-100。
- **涉及基线**：与 **G5**（compat 面窄）重叠；与 **G6**（wire 改名语义）部分重叠。

## 7. 修复建议（逻辑改造点 + 验收断言；不涉工期/人员/优先级）

> 只描述「先把架构改成什么样、验收怎么断言」，不排工期。以下聚焦协议与请求构建层的逻辑改造点。

### R1 · 建立「模型级协议路由」单一真源（对治 G4）

- **逻辑改造点**：让 `mode`（`catalog.rs:59`，`"chat"|"responses"|"both"`）成为协议路由键，废弃全局 `Endpoint` 作为唯一判据。在 agent-provider 增加一个纯函数 `resolve_wire_protocol(catalog: &ModelCatalog, vendor, model, endpoint: Option<Endpoint>) -> WireProtocol`，返回 `Chat | Responses | Anthropic | Gemini` 之一；`HttpProviderCall` 的 URL、请求体 builder、解析器三处**统一由此函数输出决定**（对齐既有「三件套同轨」铁律 `engine_provider.rs:259-262`）。`endpoint==Responses && mode` 冲突时以目录 `supports_responses` 裁决并显式诊断。
- **验收断言**：为 catalog 新增 fake 条目（`mode:"anthropic"` + fake vendor），断言 `resolve_wire_protocol` 输出 `Anthropic`、URL 落到 messages 端点、请求体含 `thinking`、解析器为 `AnthropicParser`，三处一致（参数化测试覆盖 four protocols）。同 provider 下两个模型（一个 chat、一个 responses）各自解析到正确协议，互不影响。
- 涉及基线：**G4**。

### R2 · 完成 anthropic/gemini 请求构建与接线（对治 G7）

- **逻辑改造点**：为 request/build 增加 `build_anthropic_request_body` / `build_gemini_request_body`（对齐既有 chat/responses 的 compactObject 风格），并在 `HttpStreamParser` 增加 `Anthropic(AnthropicParser)` / `Gemini(GeminiParser)` 两个变体（`engine_provider.rs:658-661`）。请求头侧增加 `anthropic-version`、Gemini `Authorization` 与 `x-goog-api-key` 的差异化头组装，复用 `reasoning_effort_headers`（vendor.rs:298-314）的 pattern。
- **验收断言**：对 anthropic 轨做端到端 mock（MockServer 回 `message_start→content_block_delta→message_stop`），断言请求体含 `system`+`messages`、`anthropic-version` 头、`thinking.budget_tokens`，且 `consume` 产出 Message；对 gemini 轨 mock `candidates[].usageMetadata`，断言 `usage` 归一正确。原有 chat/responses 测试回归为绿。
- 涉及基线：**G7**。

### R3 · per-model maxTokensField 与 system/developer role compat（对治 G5 核心）

- **逻辑改造点**：把 `MaxTokensField` 的选择从「恒 `MaxTokens`」（`engine_provider.rs:446`）改为「按模型/URL 探测」。在 agent-provider 增加 `resolve_max_tokens_field(vendor, model, base_url) -> MaxTokensField`，默认 `MaxTokens`，特定网关（OpenAI/moonshot 系）落到 `MaxCompletionTokens`（对齐 pi-ai useMaxTokens 判据 openai-completions.js:1141）。请求构建层增加 `developer` role：当 `reasoning && supports_developer_role` 时 system→`role:"developer"`（对齐 pi-ai:787-789），否则维持 system/user-prefix。
- **验收断言**：`ChatBoolean` 化测试：base_url 含 moonshot → body 用 `max_completion_tokens`；reasoning + openrouter 前缀模型 → system 消息序列化为 `role:"developer"`；非 reasoning 模型 → `role:"system"`。既存 system_role 测试（`tests/system_role.rs:45-130`）仍绿。

### R4 · 空 content 策略与 reasoning_content 强制键的模型级化（对治 G5）

- **逻辑改造点**：把「assistant 空文本 → `content:None`（null）」（`messages.rs:146-148`）改为可配置：DeepSeek/部分网关轨发 `""`、其余保留 `null`；并让 `ReasoningContentMode::Require` 的触发从「vendor==DeepSeek」（`engine_provider.rs:494-499`）改为「模型 compat `requires_reasoning_content`」，覆盖纯思考轮（无工具轮也要带键）。
- **验收断言**：DeepSeek fake 模型：纯思考 assistant 轮 → wire 含 `reasoning_content:""`；非 DeepSeek fake 模型：纯思考轮不带键。空文本 assistant 在 DeepSeek 轨序列化为 `content:""`（非 `null`）。既有 `deepseek_invariants.rs` 测试（`request/deepseek_invariants.rs:198`）保持绿。

### R5 · usage 归一化库（对治口径偏差）

- **逻辑改造点**：把「逐字段透传」（`consume/mod.rs:789-799`）改为按协议归一：chat 轨 `prompt`=Included 时从 `prompt_tokens` 剥离 cached 得到非缓存输入（对齐 pi-ai parseChunkUsage openai-completions.js:1069）；从 `completion_tokens_details.reasoning_tokens` 拆分 reasoning；Responses 轨从 `input_tokens_details.cached_tokens` / `output_tokens_details.reasoning_tokens` 拆分。在 agent-provider 增加 `normalize_chat_usage` / `normalize_responses_usage` 纯函数。
- **验收断言**：构造 `{prompt_tokens:100, prompt_tokens_details:{cached_tokens:40, cache_write_tokens:10}, completion_tokens_details:{reasoning_tokens:5}}`，断言归一后 `prompt=50(100-40-10)`、`cache_read=40`、`cache_write=10`、`reasoning=5`、`completion=completion_total`；Responses 同构参数化用例通过。

### R6 · 消息序列化细节对齐（合并于 R4 或在序列化层独立）

- **逻辑改造点**：tool result 无内容时加占位文案（`(no output)`，对齐 DSH serialize.ts:136 与 pi-ai:956），避免空串混淆；保留 canonical JSON + id 消毒；评估是否引入 `reasoning_details`（结构化思考签名回传，对齐 pi-ai:909-922）——若发起方需要跨轮结构化思考则接，否则作为后续项。
- **验收断言**：空 tool 输出的 tool 消息 wire 含 `(no output)`；既有 tool_calls canonical 序列化测试保持逐字节稳定（`messages_tests.rs`）。

> **备注**：R1/R2 是「协议接线」主干，R3/R4/R5 是「字段兼容与口径」；建议 R1/R2 先行（打通多协议主干），再以 R3-R6 补齐差异。各验收断言均可在 agent-provider 单测 / `tests/` mock 级完成，无需真实模型流量。
