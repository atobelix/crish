# Runtime Correctness Repair 总方案

## 目标

按既有软件审查结论修复运行时命令路由、工作区授权、恢复状态一致性、外部会话导入诊断和 Markdown 有序列表起始编号问题。保持原契约效果，不缩减功能；每项修复都要有针对性回归证据。当前实现轮按用户指定顺序收口前五项，未完成的审查发现继续留在队列中。

## 修复顺序与验收断言

### 1. 移动端 WebSocket 命令路由

- `runTask`、`runControl`、`cancelRun` 通过现有后端能力执行，并保持既有错误映射与控制级别语义。
- 未注册的 `searchSessions` 明确返回 unknown-command；不得静默成功或伪造结果。
- 回归覆盖有效命令、非法参数、缺失/终态 run、未注册命令和配对状态限制。
- 文件域：`apps/agent-workbench/src-tauri/src/server/ws.rs` 与对应后端测试。

### 2. 工作区授权边界

- 新的授权根只能来自 Rust 侧原生目录选择器返回值；IPC 不接受 renderer 提供的路径作为新授权依据。
- 最近项目和默认应用根只允许复授权；任意路径字符串必须被拒绝，授权失败须向用户可见。
- 单选、多选、取消、手动 recent 路径、项目切换和启动恢复均遵守同一规则；多选必须全量验证后原子登记。
- Rust command registry、command manifest、前端快照和类型/调用点保持一致。
- 文件域：`apps/agent-workbench/src-tauri/src/workspace.rs`、命令注册/清单及相关 `apps/crish-desktop/src` 调用点。

### 3. Recovery 状态与 fork 失败一致性

- 持久化失败时，`needs_user` 和通知状态不得先在内存中翻转。
- fork spawn 失败不得在 `SessionTree` 留下孤儿节点；重试不得因候选叶子 ID 冲突失败。
- acknowledge 的通知元数据与确认事件须有可解释、可验证的失败语义；不得把事件写失败静默变成不可重试状态。
- 测试覆盖存储失败、spawn 失败后树形状态不变、同一协调器重试和 acknowledge 失败窗口。
- 文件域：`crates/orchestrator/src/recovery.rs` 与 recovery coordinator 测试。

### 4. 外部会话扫描诊断与缓存

- 区分成功但无结果、部分来源失败和全部失败；来源 warning/error 对用户可见。
- TTL 过期缓存不得在首屏作为可导入结果显示；请求竞态不得让过期扫描覆盖当前界面或缓存；自定义导入根变化必须参与缓存有效性判断。
- Claude Code 与 Codex 可能存在相同会话 ID；列表 key、选择项和忙碌状态必须按 source + ID 区分。
- 扫描数据仍按来源标识，缓存只接受完整且与当前根匹配的扫描结果。
- 文件域：`apps/crish-desktop/src/api/import/`、外部会话导入 UI 与对应测试。

### 5. Markdown 有序列表编号往返

- 有序列表的 `start` 与连续项目编号经过 AST lowering、assemble、序列化和重新解析后保持一致。
- 覆盖非 1 起始、默认起始、段落分隔和无序列表；嵌套列表断言遵循当前 parser 已锁定的真实结构边界，不借此扩展嵌套列表语义。
- 文件域：`crates/conex-md-ast/` 对应 parser、assemble、serializer 与 golden 测试。

## 当前审查队列中保留的后续问题

以下问题不因本轮先修前五项而关闭：编辑器输入法 composition 期间 blur、全量文档扫描造成的长文性能、UTF-16 与 Unicode 索引边界、CompositionPatchBuffer 状态处理，以及尚未处理的 UI 英文标签。主控需在本轮验收后按原审查证据继续调度。
