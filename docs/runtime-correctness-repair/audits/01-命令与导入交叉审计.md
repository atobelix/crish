# 命令与外部导入交叉审计

## 审计范围

对照 [`00-总方案.md`](../00-总方案.md) 第 1 项移动端 WebSocket 命令路由及第 4 项外部会话扫描与缓存，检查当前工作区中的服务分发、来源扫描、缓存和工作台状态。这里只读检查实现和已有测试；本审计没有运行测试或构建，也没有修改源代码。

## 发现

### 确定缺陷：两个来源均不可读时，工作台仍把结果标成“部分”失败

- 触发条件：Claude Code 和 Codex 的扫描根目录都不可读，扫描没有返回任何会话。
- `detect.ts` 会把根目录读取失败分别记为 warning 并返回空结果：Claude 位于 `packages/plugin-import-claude-codex/src/detect.ts:417-422`，Codex 位于 `:493-498`。`scan.ts` 再把 `result.warnings` 全部转成 `kind: 'warning'`，见 `apps/crish-desktop/src/api/import/scan.ts:84-92`、`:121-128`。
- 工作台只在有任一 `kind === 'error'` 时显示“扫描未能完整完成”；其余所有 issue 都显示“部分目录或文件未能读取”，见 `apps/crish-desktop/src/components/extensions-surface/ExternalSessionsWorkbench.tsx:315-324`。因此两来源都不可读时会显示“部分”而不是“全部来源不可用”。空列表文案虽会提示“暂时无法确认是否存在会话”（`:409-429`），但状态标题仍错误地把全量失败归为部分失败。
- 影响：用户不能从状态区区分“仅一个来源/部分目录失败”和“两个来源均未能扫描”，不符合总方案要求区分部分来源失败与全部失败（`docs/runtime-correctness-repair/00-总方案.md:32-36`）。
- 测试边界：已有测试分别覆盖单个 Claude 根目录 warning（`apps/crish-desktop/src/api/import/importSessions.test.ts:97-119`）和工作台收到一个 `kind: 'error'`（`apps/crish-desktop/src/components/extensions-surface/ExternalSessionsWorkbench.test.tsx:69-94`），没有覆盖两个来源均以 warning 失败的真实组合。

### 风险推断：过期缓存仍会首屏显示，且扫描期间可以尝试导入旧条目

- 触发条件：同一组自定义根目录下存在超过 10 分钟的缓存，且本次真实扫描尚未完成。
- `getOrScanExternalSessions` 的缓存复用检查了 `CACHE_TTL_MS`（`apps/crish-desktop/src/api/import/externalSessionCache.ts:110-116`），但 `loadExternalSessionsFromCache` 只检查缓存结构和根目录指纹，不检查时间（`:75-80`）。工作台初始化时立即把该缓存放入 `detected`（`apps/crish-desktop/src/components/extensions-surface/ExternalSessionsWorkbench.tsx:45-49`）。挂载后虽会启动扫描（`:191-195`），扫描开始时保留现有 `detected`（`:138-149`），所以过期条目仍留在列表。
- 导入按钮的禁用条件只含预览解析和当前导入状态（`apps/crish-desktop/src/components/extensions-surface/SessionPreviewPane.tsx:133-140`）；工作台点击后直接对条目调用 `importDetectedSessions`，没有等待扫描完成（`apps/crish-desktop/src/components/extensions-surface/ExternalSessionsWorkbench.tsx:230-247`）。因此慢扫描期间，用户可以对旧缓存条目发起预览或导入。
- 影响是条件性的：源文件已删除时，旧条目可能在预览/导入时失败；文件已变化时，映射层重新读取该路径（预览入口 `SessionPreviewPane.tsx:42-58`），可能按缓存中的标识展示当前文件内容。代码没有显示这种情况必然造成错误数据，故列为风险推断；当前实现也可能是有意采用 stale-while-revalidate，但没有在 UI 上标出缓存过期或禁止旧条目导入。
- 测试边界：缓存测试覆盖新旧并发写入、部分结果不缓存、根目录切换和扫描中根目录改变（`apps/crish-desktop/src/api/import/externalSessionCache.test.ts:51-159`），没有验证过期缓存的首屏水合、扫描期间的旧条目导入或过期缓存与扫描失败的组合。

### 确定缺陷（需跨来源 ID 相同才触发）：列表和选择状态没有包含来源

- 触发条件：Claude Code 与 Codex 返回相同的 `sourceSessionId`。来源适配保留 `id = meta.sourceSessionId` 和单独的 `source` 字段（`apps/crish-desktop/src/api/import/types.ts:98-115`），两来源合并时不会给 ID 加来源前缀（`apps/crish-desktop/src/api/import/scan.ts:52-58`）。
- 工作台 React key 只用 `item.id`（`apps/crish-desktop/src/components/extensions-surface/ExternalSessionsWorkbench.tsx:441-445`）；选择状态写入裸 ID（`:445-452`），再用 `find(s => s.id === selectedSessionId)` 取第一条（`:221-228`）。导入忙碌状态同样只按 `item.id` 标记（`:230-245`、`:517`）。
- 影响：两个来源的相同 ID 会导致重复 React key；选择第二条也会解析成列表中的第一条，且导入忙碌标记可能同时命中两条。已导入映射本身按 `source + sourceSessionId` 区分（`:69-87`），但没有消除上述工作台状态冲突。
- 这是由现有代码结构确定、但需跨来源 ID 相同才触发的边界缺陷；工作区没有对应的双来源同 ID UI 测试。当前 `ExternalSessionsWorkbench.test.tsx:200-271` 的 collision 用例测试的是同一 Claude 来源下“会话 ID 与父目录 UUID”冲突，不是不同来源共享会话 ID。

### 审计债务：WS 回归测试未覆盖 L1 和真实终态样本

- 已确认三个已登记命令均有 dispatcher 分支，并通过共同的 `run_remote_command` 完成反序列化、后端调用、错误码映射和序列化：`apps/agent-workbench/src-tauri/src/server/ws.rs:1173-1211`、`:1264-1301`。`runControl` 直接复用 `ApiBackend::run_control`；后端再走现有 `run_control_impl`，按 runId 查活动 run，见 `apps/agent-workbench/src-tauri/src/server/core_backend/api.rs:203-222`、`apps/agent-workbench/src-tauri/src/run/run_launch.rs:1345-1354`。
- 命令分发测试使用移动端 `remote.<command>` 帧，覆盖 L0/L2/L3、无效 level、后端错误码透传、runTask/cancelRun 响应和 searchSessions unknown（`ws.rs:3647-3803`）。配对态连接被认证门拒绝（`:1003-1016`、`:3806-3826`）。当前协议清单把 C27 `searchSessions` 标为 `registered:false` 且允许 `cmd.unknown`（`packages/shared-types/src/generated/device/commands.ts:38`）；`remote_whitelist.rs:263-279` 仍把它列为 M6 白名单名，但 dispatcher 明确返回 unknown，符合本轮未注册命令契约（`ws.rs:1243-1250`）。`runTask`、`runControl`、`cancelRun` 三个已注册 Session 命令没有留下同一分发断层。
- 覆盖缺口：移动端 runControl 测试没有发送 L1 `soft_inject`（只发送 L0/L2/L3，`ws.rs:3657-3667`）；新增后端测试名称写“缺失或已终态”，但实际只传入一个不存在的 runId（`apps/agent-workbench/src-tauri/src/server/core_backend/tests/session_ops.rs:23-39`）。因此现有测试没有分别锁定 L1 wire 映射和“确实存在过、现在已终态”的目标状态；这是验证债务，不据此推断实现错误。
- 这些测试在本次审计中只做了源码检查，未运行。

## 已覆盖与未覆盖边界

已覆盖的实现断言：

- WS 已登记 Session 命令 `runTask`、`runControl`、`cancelRun` 进入既有后端；`searchSessions` 维持 `cmd.unknown`。配对态请求被认证门拒绝，非法枚举和后端业务错误也分别有断言。
- 外部扫描按来源独立返回 sessions/issues；底层目录 warning、扫描初始化异常、单来源成功/失败、完整扫描缓存、部分结果不缓存、自定义根指纹和扫描期间根变化重试均有代码或测试覆盖。`metaToDetected` 保留来源 ID 与来源类型。
- 工作台为异步扫描维护 request ID，过时响应不会更新该组件当前视图（`ExternalSessionsWorkbench.tsx:138-149`）；缓存自身也只让最新、根目录未变且无 issues 的扫描写入（`externalSessionCache.ts:124-143`）。但现有并发测试只断言缓存最终值，没有 UI 级乱序响应测试。

本轮未覆盖或未执行：

- 两来源同时以 warning 失败时的错误状态文案；过期缓存首屏显示及其在扫描中的可导入性；跨来源重复 ID 的 React key/选择行为。
- runControl L1 wire 路径与真实已终态 run 测试；没有检查真实桌面宿主下的外部文件系统权限、导入现场表现或 UI 视觉效果。
- 本审计未运行 Rust/TypeScript 测试、编译、CI 或宿主现场验证；文中“已有测试”仅表示工作区存在相应测试代码，不代表本轮执行通过。
