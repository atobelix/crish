# AFFiNE monorepo：复杂度 / 工程 DX / 心智负担 / 依赖体量 — 缺点清单

> **范围**：`reference/markdown_compare/AFFiNE`（v0.27.0 镜像）
> **立场**：冷血只谈代价；不做人身攻击；路径与数字为证据。
> **对照**：本产品栈固定 **Tauri + TS + RS**；目标更易用、性能更好；**不会整仓复制 Electron monorepo**。
> **基线**：相对「块编辑 + 协同」的常规实现（单编辑内核 + 一层应用壳 + 单一状态/UI 栈 + 单一安装路径），评估 AFFiNE 是否达到约 **3×** 复杂度。

## 2. 缺点清单（现象 → 证据 → 对「自研块工作区」的风险）

### D1. 微包爆炸：BlockSuite 一功能一 workspace

- **现象**：attachment / paragraph / slash-menu / brush 等各自独立 `package.json`；`@blocksuite/affine` 仅是聚合入口，依赖列表长达 70+ workspace 包；每个块还拆 `store` / `view` 子导出。
- **证据**：`blocksuite/affine/all/package.json:12-81`（依赖全集）；`exports` 中每个 block 的 `./blocks/*/store|view`（同文件 ~102 行起）；根 `tsconfig.json` references 逐包列出（:52-117）。
- **风险**：若自研照抄「一功能一包」，类型检查图、CI 缓存键、import 路径与版本对齐成本线性膨胀；**加一个块类型 = 加一个包 + 改 references + 改聚合入口**。对「块工作区」而言，包边界应跟**演进与测试边界**对齐，而不是跟 Notion 块类型表对齐。

### D2. 应用壳「巨石 core」与编辑器「粉尘包」并存

- **现象**：编辑器极度碎片化，但产品前端 `@affine/core` 是单体巨石：desktop/mobile 双树、dialogs/pages、AI、PDF、peek-view、quota、cloud 等挤进同一包；`exports` 还是 `"./*": "./src/*"` 式开放路径。
- **证据**：`packages/frontend/core/package.json:6-8`；目录 `src/desktop/`（dialogs 约 239 文件）、`src/mobile/`、`src/modules/`（60+ 模块）；`modules/index.ts:73+` 的 `configureCommonModules` 串行注册几十个模块。
- **风险**：自研若同时「内核拆太碎 + 壳装太满」，新人既找不到「改块」入口，又改任何产品功能都要在巨石里绕 DI/modules。**边界应清晰且对称**：编辑内核 vs 工作区壳分层，但每层内部避免两个极端。

### D3. React + Lit 双 UI 运行时与桥接层

- **现象**：应用壳 React 19；BlockSuite / AI 面板大量 `LitElement`；存在专用桥接（文件名甚至拼写为 `lit-adaper`）、`useLitPortalFactory`、portal 注入。
- **证据**：`packages/frontend/core/package.json` 同时依赖 `react`/`react-dom` 与 `lit`（:75,82-83）；`blocksuite/block-suite-editor/lit-adaper.tsx`；`blocksuite-editor.tsx` 从 `./lit-adaper` 引入编辑器；core 内 AI widgets 直接 `import { LitElement } from 'lit'`。
- **风险**：双虚拟 DOM / 双生命周期 = 双倍调试面（焦点、IME、事件冒泡、样式隔离、SSR/测试）。自研若再叠 React 壳 + 另一套块渲染框架，**性能叙事（「比 AFFiNE 更快」）会被桥接税抵消**。应单一 UI 宿主，扩展用协议而非第二框架。

### D4. 自研 DI / Framework 叠加多层状态原语

- **现象**：`@toeverything/infra` 自带 Framework（Service/Entity/Scope/Store）、LiveData、自研 ORM、op 消息；应用层同时残留 jotai；BlockSuite 侧还有 `@preact/signals-core`；存储/同步大量 rxjs。
- **证据**：`packages/common/infra/src/`（framework/livedata/orm/op）；`@affine/core` deps：`jotai`、`rxjs`、`@preact/signals-core`（core `package.json:40,71-72,89`）；UI 中 `useLiveData` / `useService` 遍布。
- **风险**：同一「读状态 → 渲染」路径可能跨 3～4 套语义（atom / LiveData / signal / Observable）。**心智负担不是文档能抹平的**——是并发改动时的隐性竞态与「该在哪写副作用」。自研应 **一种权威状态模型**（最好贴近 Rust 内核事件），前端只做投影。

### D5. 桌面构建：双次 yarn、改 hoist、清 node_modules

- **现象**：打 Electron 安装包需要：先默认 yarn 构 core → **改 `nmMode`/`nmHoistingLimits`** → **全树删 node_modules 再装** → 再 `package`/`make`。Windows 步骤与 Unix 分叉。
- **证据**：`docs/building-desktop-client-app.md:25-29,66-88`；Yarn Berry 与 Electron builder 限制的显式承认（:25 链到 yarnpkg/berry#4804）。
- **风险**：任何「复制 Electron monorepo 桌面流水线」对 Tauri 产品是**纯结构债**。即便只借鉴前端，也会把「可复现构建」变成仪式。**本产品桌面路径必须单一安装图、单一原生壳（Tauri）**。

### D6. 入门摩擦：Windows 符号链接、双工具链、文档过期

- **现象**：Windows 必须 Developer Mode + `core.symlinks true`；Node **与** Rust 都是硬前置；原生 NAPI 首次编译「可能很久」；官方 BUILDING **声明可能过时**；Node 主版本锁在 22.x 补丁窗口。
- **证据**：`docs/BUILDING.md:3-6,20-21,69-81,83-91`；`package.json` engines（:18-20）；desktop 文档同样过期警告。
- **风险**：贡献/自建镜像环境失败率高；对内协作则「能跑起来」成为隐性门槛。自研文档与 `engines` 应宽而真；**Windows 路径不得依赖 symlink 才能 clone**。

### D7. 定制 CLI + 生成式 monorepo 骨架

- **现象**：日常入口不是标准 `yarn workspace X run`，而是 `yarn affine` / `af`（`@affine-tools/cli`）；`postinstall` 跑 `affine init` + husky；根 `tsconfig` references **禁止手改**、由 `yarn affine init` 生成。
- **证据**：根 `package.json:20-24,37`；`tools/cli/README.md`；`tsconfig.json:48-50`。
- **风险**：工具链知识垄断在内部 CLI；新人离线排查困难；CI 与本地脚本绑定生成物。自研 monorepo 若需要编排，应优先 **标准 package manager + 少量脚本**，避免「第二个构建系统」。

### D8. Lint / 类型检查资源墙

- **现象**：ESLint 直接申请 **16GB** 堆；同时 oxlint + eslint + prettier 三道；typecheck 为 `tsc -b` 全 composite 图。lint-staged 对每个 TS 文件再跑带 16GB 的 eslint。
- **证据**：根 `package.json:25-36,39-50`；`eslint.config.mjs` 挂 project 级 parserOptions（:46-52）。
- **风险**：笔记本级机器无法舒适贡献；pre-commit 变慢导致绕过门禁的压力（本仓库铁律禁止 `--no-verify`，但结构本身在制造绕过诱因）。自研应 **按包增量 lint/typecheck**，禁止「全仓 eslint 需 16G」级配置进入默认路径。

### D9. 依赖体量与 resolutions / patch 面

- **现象**：core 直接依赖面极宽（GraphQL、Sentry、Typst wasm、mermaid、shiki、katex、socket.io、yjs、radix 全家、emotion、vanilla-extract…）；根 `resolutions` 用 nolyfill 替换大量 polyfill，并 **patch yjs**、pragmatic-dnd、tinykeys 等。
- **证据**：`packages/frontend/core/package.json:10-97`；根 `package.json:97-189`；`.yarn/patches/` 五份（含 `yjs-npm-13.6.21-*.patch`）。
- **风险**：
  1. 安装体积与供应链审计成本；
  2. **对协同核心库打 patch** = 上游升级即回归雷；
  3. 与「性能更好」目标冲突的重型前端依赖（图表/排版/WASM 预览）若默认进编辑热路径，首包与内存必劣。
     自研应对协同层 **零 patch 或 patch 进自有 fork 并有测试围栏**；重型预览一律惰性/进程外。

### D10. 多端同仓：Electron + Web + Capacitor iOS/Android

- **现象**：`packages/frontend/apps/` 并列 web / electron / electron-renderer / mobile / ios / android / mobile-shared；iOS 树含大量 Swift/GraphQL 生成代码；core 内再分 `desktop/` 与 `mobile/` 页面与对话框。
- **证据**：apps 目录结构；`packages/frontend/core/src/desktop` vs `mobile`；ios 下 `Packages/AffineGraphQL` 等。
- **风险**：抽象层为「全平台最大公约数」服务，桌面 Tauri 路径会被移动端/Electron 约束拖慢。**本产品不应把移动端壳放进块工作区 MVP 仓**；协议可跨端，实现仓应可剪。

### D11. 存储栈分叉：nbstore 多后端 + v1 兼容

- **现象**：`@affine/nbstore` 导出 idb / idb/v1 / sqlite / sqlite/v1 / cloud / broadcast-channel / worker client|consumer；Electron helper 仍见 nbstore v1 路径。
- **证据**：`packages/common/nbstore/package.json:7-18`；`packages/frontend/apps/electron/src/helper/nbstore/v1/`。
- **风险**：「块 + 协同」本可一条存储语义；多后端 + 版本并行会制造迁移与一致性边角。自研应用 **单一权威存储（Rust）+ 明确 schema 版本**，前端只做适配，不并行维护 v1 树。

### D12. 测试矩阵横向膨胀

- **现象**：`tests/` 下 affine-local / cloud / cloud-copilot / desktop / desktop-cloud / mobile / blocksuite 等多套 Playwright 工程 + fixtures/snapshots；blocksuite e2e 自带大量 snapshot JSON。
- **证据**：`tests/*/package.json` 与目录树；`tests/blocksuite/snapshots/` 体量。
- **风险**：测试是资产（应保留正确性），但 **按产品分叉复制 E2E 工程** 会让「改一个选择逻辑」触发多配置。自研宜 **分层门禁**（内核单测 / 编辑契约 / 少量端到端），避免 7 套前端 e2e 包名并列成为默认模板。

### D13. 产品模块拓扑强迫「全量配置」心智

- **现象**：打开编辑器相关功能前，需理解 Framework 的 configure* 链（workspace → doc → editor → feature-flag → …）；模块间 service/store/entity 命名惯例是内部 DSL。
- **证据**：`packages/frontend/core/src/modules/index.ts` 全量 `configure*Module`；infra `framework/core/components/{service,entity,scope,store}.ts`。
- **风险**：块工作区业务逻辑被框架仪式绑架；单元测试要先搭 Framework。自研优先 **纯函数/显式依赖注入到边界**，避免「全家桶 DI 容器」成为写业务的前置条件。

### D14. Electron 进程模型本身的复杂度税（相对 Tauri）

- **现象**：main / helper / preload / renderer / background-worker / popup / shell 多入口；安全 open-external、redirect-proxy、updater、recording 等堆在 Electron 主进程。
- **证据**：`packages/frontend/apps/electron/src/main|helper|preload`；`building-desktop-client-app.md:17-23`。
- **风险**：若「学习 AFFiNE」时把 Electron 分层一并内化，会与已锁定的 **Tauri** 栈错位，产生无效设计。IPC 与权限模型应直接按 Tauri 命令/事件设计，**不要移植 Electron 进程拓扑**。

## 3. 复杂度是否达到「正常选型 3×」？

### 3.1 什么叫「正常选型 1×」（本评估的分母）

针对 **块编辑 + 多人协同** 的常规、可交付架构：

| 层       | 1× 形态                                                 |
| -------- | ------------------------------------------------------- |
| 编辑内核 | 1 个库（或 monorepo 内 2～4 包：model / view / collab） |
| 应用壳   | 1 个前端应用 + 可选 thin desktop shell                  |
| UI       | **一种** 组件模型                                       |
| 状态     | **一种** 主模型（+ 协同 CRDT/OT 本身）                  |
| 存储     | 一种本地 + 一种同步协议                                 |
| 构建     | 一次 `install`、一次 `dev`/`build`                      |
| 原生     | 0～1 个 native 边界（SQLite 等）                        |

### 3.2 分维度倍率（粗估，非工期）

| 维度                          | 相对 1×     | 说明                                                  |
| ----------------------------- | ----------- | ----------------------------------------------------- |
| 包/工程图                     | **~4–6×**   | 70 级 BlockSuite 包 + 110+ tsc references + 多 app 包 |
| UI/运行时                     | **~2×**     | React + Lit + 桥接                                    |
| 状态/DI                       | **~3×**     | Framework+LiveData+jotai 残留+signals+rxjs            |
| 平台面                        | **~3–4×**   | Web + Electron 多进程 + Capacitor 双移动端            |
| 构建/DX 路径                  | **~3×**     | 双 hoist 安装、自定义 CLI、生成 references、窄 Node   |
| 依赖/补丁面                   | **~2–3×**   | 重依赖 + resolutions 海 + yjs patch                   |
| 存储兼容                      | **~2×**     | 多 impl + v1 并行                                     |
| **编辑+协同「概念内核」本身** | **~1.5–2×** | Yjs/BlockSuite 领域复杂度真实存在，但被上述工程壳放大 |

### 3.3 结论

- **就「工程结构 + DX + 心智 + 依赖」整体**：**达到并超过「正常选型 3×」**（综合约 **3–5×**，视是否计入移动端/Electron 全矩阵）。
- **就「块模型 + 协同算法」纯粹领域**：**未到 3×**，大约 **1.5–2×** 常规协作编辑器——真正昂贵的是 **微包 monorepo 形态、双 UI、自研 DI 全家桶、多端同仓与桌面二次安装**。
- 对本产品的含义：对标 AFFiNE **应吸收领域问题清单**（块操作、选区、协同冲突、离线），**禁止吸收其工程倍率**；否则「性能与易用更好」在装依赖与过桥接阶段就已经输了。

## 4. 本产品应**避免复刻**的结构债

下列条目是「看到 AFFiNE 很完整就想抄目录」时最危险的债。每条对应上文缺点编号。

| #   | 避免复刻的结构                                                | 替代原则（对齐本产品栈）                                                                                                          |
| --- | ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| A   | **一 Block 类型一 npm package**（D1）                         | 块类型用注册表/插件接口扩展；包按 **稳定性与测试边界** 切（如 `editor-core` / `collab` / `blocks-builtin`），不按 UI 积木切 70 包 |
| B   | **React 壳 + Lit 内核双栈**（D3）                             | 单一 UI 宿主；块视图同一套渲染与事件模型；扩展用数据协议 + TS API，不引入第二组件运行时                                           |
| C   | **自研 Framework/LiveData/ORM 全家桶作为业务默认**（D4、D13） | 权威状态在 **Rust 会话/文档引擎**；TS 侧薄投影；禁止业务代码先学 DI DSL                                                           |
| D   | **Electron 多进程拓扑与双 hoist 桌面构建**（D5、D14）         | **Tauri** 单壳；一次依赖图；原生能力走 `invoke`/事件，不复制 main/helper/preload 三套 TS                                          |
| E   | **Web+Desktop+iOS+Android 同仓强耦合**（D10）                 | 块工作区核心仓只保桌面/Web 所需；移动端若需要则另仓或晚绑定，避免 core 内 desktop/mobile 双倍页面树                               |
| F   | **根 tsconfig 百级 references 靠 CLI 生成**（D7）             | 少包、可手维护的 project references；或 bundler 路径映射，避免「init 才能 typecheck」                                             |
| G   | **ESLint 16GB / 全仓 project lint 默认路径**（D8）            | 分层门禁；oxlint/rustc 快路径；按变更包检查                                                                                       |
| H   | **对 yjs（或等价协同核）运行时 patch**（D9）                  | 协同核可替换或 vendor 清晰；升级路径有契约测试，不靠 yarn patch 静默改行为                                                        |
| I   | **nbstore 式多后端 + v1 永久并行目录**（D11）                 | Rust 单一存储语义 + 显式 migration；前端适配层可换，不并存两套 schema 树                                                          |
| J   | **「开放 `exports: ./*` 的巨石 core」**（D2）                 | 明确公共 API 面；内部模块不默认成为外部 import 面，防止依赖蜘蛛网                                                                 |
| K   | **产品能力默认全部进编辑热路径**（D9 重依赖）                 | Typst/Mermaid/PDF/AI 等 **惰性与进程外**；编辑首屏只保留块与协同必需                                                              |
| L   | **以「文档可能过期」为常态的构建说明**（D6）                  | 构建步骤进可执行脚本/CI 真源；README 链到脚本而非手抄分叉的 Windows/Unix 散文                                                     |

### 4.1 允许借鉴的方向（边界，防止误读）

- 块/选区/协同的 **问题分解** 与测试资产组织思路（问题清单，不是目录拷贝）。
- 「扩展点」思想（ext-loader / store vs view 分离的**概念**）——用更粗粒度实现。
- 对性能敏感路径（索引、SQLite）下沉 native 的 **意图**——在本产品即 **Rust 内核**，而非 NAPI 碎片多 crate 无序生长。

## 5. 对「自研块工作区」的总风险摘要

1. **最大税不在协同算法，在 monorepo 工程学**：微包 + 巨石壳 + 自定义 CLI + 多端，把 1× 领域做成 3×+ 仓库。
2. **双 UI 与多层状态** 直接威胁「比 AFFiNE 更好用/更快」的产品承诺。
3. **Electron/双 install 路径** 与已锁定 Tauri 栈冲突；学习迁移时必须主动丢弃。
4. **依赖与 patch 面** 会把性能与安全基线变成持续救火。
5. 正确姿态：**领域问题对标、工程形态反标**——结构债清单（§4）作为设计评审否决项，而不是 backlog「以后再学 AFFiNE 目录」。
