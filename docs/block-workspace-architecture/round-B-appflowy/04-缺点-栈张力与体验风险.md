# AppFlowy：栈张力 / DX / 编辑精致度 / 体量 / AGPL / 体验短板 — 缺点清单

> **范围**：`reference/markdown_compare/AppFlowy`（含根 `LICENSE`；前端约 v0.11.4）
> **立场**：冷血只谈代价；不做人身攻击；路径与数字为证据；无法从本树证实的标【观察】。
> **对照**：本产品栈固定 **Tauri + TypeScript + Rust**；**不会**选 Flutter 作主 UI；目标 Notion 的块与交互皮 + Rust 内核，并在性能/体验上超过参考产品。
> **基线**：相对「块编辑 + 协同」的常规实现（单编辑内核 + 一层应用壳 + **一种** UI 语言 + 单一安装路径），评估 AppFlowy 是否达到约 **3×** 工程复杂度。

## 2. 缺点清单（现象 → 证据 → 对「自研块工作区」的风险）

### D1. Flutter 主 UI 与「Tauri + TS 扩展生态」结构性互斥

- **现象**：产品壳、块渲染、slash menu、database 网格/看板/日历、AI 聊天 UI **全部是 Dart/Flutter Widget**。扩展点天然落在 Flutter 插件与 `BlockComponentBuilder` 注册，而不是 npm/TS 协议。README 写「single codebase written in Flutter and Rust」；本仓另有 cargo-make 任务指向 `appflowy_tauri` / `appflowy_web`（**本镜像树内未见对应目录**，仅有路径常量与 makefile 残片）——说明跨栈第二前端曾被考虑或并行，进一步暴露「心在 Rust、脸在 Flutter」与 Web/TS 路径的裂缝。
- **证据**：`README.md:126-133`；`lib/plugins/document/presentation/editor_configuration.dart`（`Map<String, BlockComponentBuilder>`）；`frontend/Makefile.toml:51-53`（`TAURI_BACKEND_SERVICE_PATH` / `WEB_BACKEND_SERVICE_PATH`）；`frontend/scripts/makefile/tauri.toml:1-7`。
- **风险（对本产品）**：从 AppFlowy **复用 UI/块视图** 几乎为零价值——语言、组件模型、打包与插件市场全不互通。若仍幻想「借鉴 Flutter 桌面原生感再包一层 TS」，会制造**第三运行时**。**已定 Tauri+TS 的正确姿态是：只抽 Rust 领域问题与数据面教训，丢弃 Flutter 面。**

### D2. 双语言 + 双生成管线的 DX 税（Flutter 钉死 × cargo-make × protoc）

- **现象**：贡献者必须同时会 Flutter/Dart **与** Rust；Windows 安装脚本会把本机 Flutter **强制切到 3.27.4**；还要 `cargo install cargo-make`、protoc / `protoc-gen-dart`、全局 pub 工具。日常构建不是「一种 package manager」，而是 **cargo-make 任务图** 叠加 `flutter` / `build_runner` / protobuf 生成。
- **证据**：`install_windows.sh:22-46,49-67,97-99`；`Makefile.toml:1-14,22-53`；`scripts/makefile/protobuf.toml`（install_flutter_protobuf / Windows `protoc-gen-dart`）；`appflowy_flutter/Makefile`（`dart run build_runner`）。
- **风险**：入门失败率高；版本漂移即全员对齐 Flutter 补丁；生成代码成为「看不见的第三源码树」。自研若复制「事件 IDL 全量 protoc 双端生成 + 自定义 make 生态」，会把 Tauri 的 `invoke` 简单路径做成 AppFlowy 级仪式。

### D3. 编辑内核外置 + 应用层巨型插件补丁面（精致度结构性风险）

- **现象**：核心编辑器 `appflowy_editor` **不在 monorepo 内**，以 git pin 依赖；产品仓再堆 **320 文件级** `editor_plugins` 定制 slash、表格、移动端工具条、AI writer、mention…。版本对齐靠 commit hash，升级 = 跨仓协调。
- **证据**：`pubspec.yaml:185-194`；`editor_plugins/` 目录规模；`editor_configuration.dart:53-56`（缺 builder 则 error block）。
- **风险**：
  1. **精致交互（选区、IME、拖拽预览、嵌套块）** 的 bug 落在外仓时，应用仓只能绕；
  2. 产品特性与内核版本强耦合，长期形成「fork 依赖 + dependency_overrides 森林」；
  3. 对本产品：若把「Notion 级编辑精致度」押在**外置、另一语言**的编辑器上，跨仓钉死会变成永久体验债。应 **编辑契约与实现同栈可调试**（TS 热路径 + Rust 权威模型），避免「UI 在 A 仓、行为在 B 仓 pin」。

### D4. 编辑器树模型 vs 后端扁平文档：TransactionAdapter 永久税

- **现象**：官方注释写死——编辑器是 **树**，后端是 **flat**；每次 transaction 必须 `transactionToBlockActions` / external text delta 拆分后经 `DocumentService` 打到 Rust。协同侧再叠 `DocumentCollabAdapter` 多版本同步策略。
- **证据**：`editor_transaction_adapter.dart:16-19,54-55`；`document_collab_adapter.dart` 全文分层。
- **风险**：双模型 = 双份不变量。任何「看起来像 Notion 的块操作」都要过适配层，延迟、丢操作、选区错位的根因难定位。自研若再搞「前端树 + 后端另一套块表 + 手写 adapter」，精致度上限被适配税封顶。**权威模型应唯一**（倾向 Rust），前端投影而非双向重构。

### D5. 协同路径未闭合：syncV2「Not fully implemented」+ 退回全量 diff/forceReload

- **现象**：`DocumentCollabAdapter` 明确：
  - `syncV1`：强制重载（开发用）；
  - `syncV2`：注释 **「Not fully implemented yet」**，Insert/Remove 分支为空 `break`；
  - `syncV3`：整文档 diff 再 apply；
  - 另有 `forceReload` 清空子节点重灌。
- **证据**：`document_collab_adapter.dart:31-49,45-71,73-96,113-124`。
- **风险**：对「超过 Notion/AFFiNE 的实时协同体验」而言，这是**硬伤级结构**：远程增量事件未完整落到编辑器操作，只能靠 diff/重载兜底 → 选区跳动、大文档闪烁、冲突表现不可控。【观察】用户侧「协同偶发丢字/整页刷新感」类反馈常与此类架构同源，但本轮未跑产品实测。
  本产品目标若含多人实时，**禁止**把「半实现增量 + 全量 diff 兜底」当作默认同路径；协同操作必须有契约测试与闭合 apply。

### D6. 块交互精致度缺口（源码自曝）

- **现象**（非 exhaustive）：
  - 拖拽反馈对 table / multi-image / file / database 等类型 **不渲染真预览**，只放文字 placeholder（「unable to render … without provider/context」）；
  - columns 块 **不支持** block actions 与 selection（注释直说）；
  - toggle 在 mobile 对 enter **assert false**；
  - sub_page 存在 `TODO(Mathias): Handle mobile tap`；
  - 旧 `table` 与 `simple_table` **两套**表格相关插件并存（迁移/双路径气味）。
- **证据**：`draggable_option_button_feedback.dart:86-106`；`simple_column_block_component.dart:156` 一带；`toggle_block_shortcuts.dart:167`；`sub_page_block_component.dart:233`；`editor_plugins/table/` vs `simple_table/`。
- **风险**：Notion 级「拖一块就有可信预览、列与嵌套可选可转」在这些分支上仍是**未完成面**。宣传 Notion 替代时，精致度短板会集中暴露在拖拽/表格/多列/移动端快捷键。自研验收必须把这些列成**魔鬼用例**，而不是抄插件目录。

### D7. 桌面/移动双树 UI 与能力分叉

- **现象**：`lib/mobile/` 约 **184** dart 与 `workspace/`、`plugins/` 桌面路径并行；database cell 存在 desktop_grid / mobile_grid / desktop_row_detail / mobile_row_detail 多套 skeleton；编辑器 mobile_toolbar_v3 整棵独立菜单树。
- **证据**：`lib/mobile/` 规模；`plugins/database/widgets/cell/` 下 desktop_* / mobile_* 分叉；`editor_plugins/mobile_toolbar_v3/`。
- **风险**：同一产品语义维护 **≥2 套交互实现**；修桌面不修移动、修移动破坏桌面。本产品块工作区若默认「先桌面 Tauri」，**不应**在核心仓复制 AppFlowy 式 mobile 双树；协议可跨端，实现仓可剪。

### D8. 体量：产品能力全量进单一 Flutter 应用

- **现象**：单一 `appflowy` 应用同时塞：文档编辑、Database（grid/board/calendar）、AI chat、搜索、云账号/发布、多平台打包（windows/macos/linux/android/ios runner）。Rust 侧 database2 源文件 **172+**，Flutter database 插件树同样巨大。图标与 i18n 资源规模可观（icons 数百 SVG、translations 三十余语言 JSON）。
- **证据**：`lib/plugins/` 列表（document/database/ai_chat/trash…）；`flowy-database2/src` 规模；`resources/flowy_icons`、`resources/translations`；`pubspec.yaml` 依赖面（chat UI、math、tex、unsplash、board git 依赖…）。
- **风险**：「Notion 替代」产品定义迫使 **全能仓**；编译、测试分片（9 个 desktop runner）、心智与二进制体积同步膨胀。【观察】安装包/内存相对 Tauri 轻壳往往更重（Flutter 引擎 + 全功能），本镜像无安装产物，体感需实测。
  自研应 **编辑+协同核心可独立交付**，Database/AI/发布为惰性模块，禁止默认全量热路径。

### D9. AGPL-3.0：复制、链接与「网络提供服务」传染面

- **现象**：根 `LICENSE` 全文为 **GNU Affero GPL v3**。关键条款：
  - 修改后的版本通过网络向用户提供交互时，必须向用户提供 **Corresponding Source**（§13 Remote Network Interaction）；
  - 对覆盖作品的传播/修改受 copyleft 约束；与专有栈「静默嵌代码」不兼容。
- **证据**：`LICENSE:1-12,42-48,540-551`；`README.md:16,147-149`。
- **风险（对本产品，工程与法务双面）**：
  1. **不可**把 AppFlowy 源码（含 Flutter 插件与 rust-lib 大段）直接链进闭源/宽松许可的商业桌面而不履行 AGPL 义务——需法务确认；默认假设为 **高传染**。
  2. 即便「只读学习」，衍生若构成 modified version 并 SaaS 化，§13 触发源码提供义务。
  3. 子包内多处 `packages/*/LICENSE` 仍是 **「TODO: Add your license here.」**（`appflowy_ui`、`flowy_infra` 等）——仓库许可声明 **不整齐**，二次分发审计成本上升。
  4. 本产品已选 Tauri+TS+RS，正确策略是 **思想/问题清单级借鉴，零源码搬运**；协同可参考 yrs/collab **概念**，实现自研或选兼容许可依赖。

### D10. 依赖 overrides 森林与供应链脆弱性

- **现象**：`dependency_overrides` 用 git commit 钉死 editor、plugins、window_manager、auto_updater（多 path）、cache_manager、url_protocol、reorderable_tabbar、file_picker 版本锁定等；另有 `appflowy_board`、`calendar_view`、`emoji_mart` 等 git 依赖。维护者个人 fork（如 LucasXu0）在关键路径上出现多次。
- **证据**：`pubspec.yaml:19-21,39-42,176-252`。
- **风险**：上游消失、force-push、或 Flutter 升级即雪崩；安全审计无法只看 pub.dev 版本号。自研应 **少 override、少私人 git pin**；关键路径 vendor 进 monorepo 并有测试围栏。

### D11. 扩展生态与社区贡献模型偏离「TS 插件市场」

- **现象**：官方价值主张写 Community-driven extensibility，但实现载体是 Flutter/Rust；贡献文档指向 Flutter 基础与外部 GitBook。没有 npm 式「装一个块扩展」的主路径；企业/黑客「building blocks」叙事与 **Dart 插件成本** 不对齐当今前端扩展生态。
- **证据**：`README.md:135-144`；`frontend/appflowy_flutter/README.md:29-31`（建议具备 Flutter 基础）。
- **风险**：对本产品「**TS 扩展生态**」硬需求，AppFlowy **不是正参照**而是 **反参照**：扩展应是 TS API + 能力清单 + 沙箱，而不是「会 Flutter 才能写块」。

### D12. 构建与多产物矩阵（Flutter 桌面壳 + 历史 Tauri/Web 脚本）

- **现象**：cargo-make 同时维护 desktop / mobile / docker / tauri / web 任务；crate-type 在 staticlib/cdylib 间按平台切换并要求同步改 podspec 与 `ffi.dart`（Makefile 内长注释）。Windows 另有 bitsdojo_window；Mac/Linux window_manager git 钉。
- **证据**：`Makefile.toml:33-48,60+`；`pubspec.yaml:35-36,144-147,202-206`；`scripts/makefile/*.toml`。
- **风险**：平台矩阵本身合理，但 **第二套 Web/Tauri 生成路径与主 Flutter 产品并行** 造成文档与真实入口漂移（本树无 `appflowy_tauri` 目录却有清理任务）。自研桌面路径必须 **单一壳（Tauri）**，禁止「主栈 + 影子栈」makefile 遗产。

### D13. 相对 Notion / AFFiNE 的体验与品类短板（有证 + 观察）

| 短板                                                 | 性质             | 证据 / 说明                                                                                                  |
| ---------------------------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------ |
| 官方不宣称功能与设计超过 Notion                      | **有证**         | `README.md:141-144`「We do not claim to outperform Notion… at least for now」                                |
| 协同增量 apply 未完成                                | **有证**         | `document_collab_adapter.dart:45-49` syncV2 未完成；Insert/Remove 空                                         |
| 拖拽/列块/部分块类型交互残缺                         | **有证**         | D6 引用                                                                                                      |
| 无独立白板/无限画布品类（AFFiNE 的 edgeless 向）     | **有证（缺失）** | 本树 `lib/` 无 whiteboard/edgeless 产品模块；「canvas」命中多为 Flutter `Canvas` 绘制或 `canvasColor` 主题色 |
| 编辑精致度（IME、大规模文档、嵌套表）整体对标 Notion | **【观察】**     | 需产品实测与对比用例；架构上 adapter + 外置 editor 不利极致打磨                                              |
| 默认安装体积 / 内存 vs Tauri 轻壳                    | **【观察】**     | 无本轮 benchmark；Flutter 引擎 + 全能功能暗示偏重                                                            |
| Database 重、白板/自由布局轻                         | **【观察】**     | 代码体量向 database/document 倾斜；与 AFFiNE「文档+画布」双核不同                                            |

对「超过 Notion/AFFiNE」的产品目标：AppFlowy 提供的是 **Rust 本地优先 + 文档/数据库宽度** 的参考，**不是**编辑精致度或画布协同的上限样板。以其为「体验天花板」会系统性低估竞品。

### D14. 状态与 DI：GetIt + 大量 Bloc 的应用层复杂度

- **现象**：启动 `DependencyResolver` 用 **GetIt** 注册云、用户、folder、clipboard 等；文档/数据库普遍 **flutter_bloc**；另有 provider、event_bus、talker 等。不是「一种状态模型」，而是服务定位 + 多 Bloc 面。
- **证据**：`startup/deps_resolver.dart:45-58`；`pubspec.yaml` 中 `get_it` / `flutter_bloc` / `provider` / `event_bus`。
- **风险**：与 AFFiNE 的「自研 Framework 全家桶」不同形态，但同样 **业务前置框架仪式**。自研应权威状态在 Rust，TS 薄投影，避免再叠第三套全局 GetIt 式隐式图。

## 3. 复杂度是否达到「正常选型 3×」？

### 3.1 分母：1×「块编辑 + 协同」常规形态

| 层         | 1× 形态                                  |
| ---------- | ---------------------------------------- |
| 编辑内核   | 1 个库（model/view/collab 可 2～4 包）   |
| 应用壳     | 1 个前端 + thin desktop shell            |
| UI 语言    | **一种**（对本产品 = TS/WebView 或等价） |
| 状态       | **一种** 主模型 + 协同层                 |
| 跨语言边界 | 0～1 道（如 Tauri command），契约稳定    |
| 构建       | 一次 install、一次 dev/build             |
| 平台       | 先桌面，移动可选后绑                     |

### 3.2 分维度倍率（粗估，非工期）

| 维度                  | 相对 1×     | 说明                                                             |
| --------------------- | ----------- | ---------------------------------------------------------------- |
| 语言/UI 运行时        | **~2×**     | Flutter 引擎 + Dart 生态；与目标 Tauri+TS **正交**，迁移成本另计 |
| 跨语言与 codegen      | **~3×**     | dart-ffi + protobuf 全事件面 + cargo-make + build_runner         |
| 文档模型双表示        | **~2×**     | 树编辑器 ↔ flat/yrs 后端 + TransactionAdapter                    |
| 协同闭合度债          | **~2×+**    | 多 sync 版本并存、增量未完成 → 维护与测试面放大                  |
| 产品功能面            | **~3–4×**   | 文档+Database 全家桶+AI+云+多端                                  |
| 桌面/移动 UI 双树     | **~2×**     | mobile/ 与 desktop 路径并行                                      |
| 依赖/pin 面           | **~2×**     | overrides 与多 git fork                                          |
| 构建矩阵              | **~2.5×**   | Flutter 多 OS + 历史 Tauri/Web 任务 + crate-type 分叉            |
| **编辑+协同概念内核** | **~1.5–2×** | collab/yrs、块、database 领域真实存在                            |

### 3.3 结论

- **就「工程结构 + DX + 跨语言生成 + 全能产品面」整体**：达到约 **3×** 正常选型（综合约 **3–4×**，若计入移动双树与 Database 全矩阵可更高）。
- **就「块模型 + 协同算法」纯粹领域**：约 **1.5–2×**——真正贵的是 **Flutter 锁定、FFI/Protobuf 仪式、双文档模型、半闭合协同、外置 editor pin、全能仓**。
- **相对本产品已定栈**：AppFlowy 的 Flutter 面是 **负资产**；Rust 心可参考问题分解，但 **dart-ffi 事件总线形态不必复刻**（Tauri 命令/事件更贴 TS 扩展）。
- **与 round-A AFFiNE 对照**：AFFiNE 税在 TS monorepo 微包与双 UI（React+Lit）；AppFlowy 税在 **语言隔离 + FFI 生成 + 编辑/协同适配层**。两者都 ≥3× 工程壳，病灶不同，**都不可整仓模仿**。

## 5. 总风险摘要

1. **最大战略错位**：Flutter 主 UI 与本产品 **Tauri+TS 扩展** 目标互斥；学 AppFlowy UI = 学一套用不上的语言与生态。
2. **最大体验技术债**：树/flat 双模型 + 协同增量未闭合 + 外置 editor pin → **精致度与实时协同双杀**。
3. **最大工程税**：cargo-make × protobuf × Flutter 钉版本 × 全能仓 × 移动双树 ≈ **3×+** 正常选型。
4. **最大法务雷**：根 **AGPL-3.0** + 网络条款；子包 LICENSE TODO；默认 **禁止源码级复用**。
5. **正确姿态**：**领域问题对标、工程与 UI 形态反标**；§4 避免清单作为设计评审否决项，而不是「以后用 Flutter 重写一版插件」。
