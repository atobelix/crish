# Crish 多 Agent 协同修复方案 · 总览

> 本文档是 `docs/multi-agent-repair/` 系列文档的总览（第 00 章）。
> 供主调度 Agent 与各轮子 Agent 在动手前阅读，统一对整体方案、执行模型与纪律的理解。

## 1. 方案定位

Crish 是桌面 AI Agent 工作台，技术栈为：Tauri 壳（`apps/crish-desktop`）＋ React 前端 UI（`apps/agent-workbench`）＋ Rust 引擎（`crates/` 下 `session-loop`、`orchestrator`、`agent-provider`、`agent-tools`、`conex-db` 等 crate）。

本次多 Agent 协同修复的目标，是通过多轮并行修复，把当前代码库推进到"可构建、可测试、可治理、可调度"的状态。整体收敛到五条主线，所有问题同等优先，各轮只按逻辑依赖排序，不按优先级排序：

| 主线 | 说明 | 主要落点 |
| --- | --- | --- |
| 迁移收尾 | 完成向 Rust 引擎 + React 前端的迁移中未收尾的部分，消除残留的死代码、占位实现与断裂引用 | `apps/`、`crates/`、根配置 |
| 契约层 | 以 `conex-types` 为枢纽，固化 crate 之间、Tauri IPC 之间、前端与引擎之间的类型契约，杜绝跨层"各说各话" | `crates/conex-types`、IPC 层、前端类型 |
| 引擎内核 | 修复并夯实 `session-loop`（会话循环）与 `orchestrator`（编排器）的内核逻辑，作为引擎的骨架与运转中枢 | `crates/session-loop`、`crates/orchestrator` |
| 治理固化 | 把质量门禁固化为脚本与钩子（构建、lint、typecheck、测试），让后续每一轮修复都能被自动化验证 | 根 `package.json`、`Cargo.toml`、husky、CI |
| Agent 调度功能 | 在工程收敛的前提下，实现本方案所依赖的"多 Agent 并行调度"能力本身（R7 落地） | `crates/orchestrator` 调度模块 |

这五条主线不是独立串行执行，而是按逻辑依赖嵌入到第 4 节定义的 8 个轮次中：契约层与治理固化是地基，迁移收尾与引用修复是清除障碍，Agent 调度功能是最终产物。

## 2. 闭环迭代模型

每一轮修复都遵循同一条完整逻辑链路，轮与轮之间首尾相接，形成闭环：

```
问题识别 → 任务分解 → Agent 分配 → 并行修复 → 结果汇总 → 验证门禁 →（输出成为下一轮输入）
```

各环节的职责与产物：

| 环节 | 职责 | 产物 |
| --- | --- | --- |
| 问题识别 | 依据上一轮输入（问题清单、遗留问题、新发现）与当前代码库状态，识别本轮要处理的问题范围 | 本轮问题清单（条目含：编号、文件域、现象、处理方式） |
| 任务分解 | 把问题清单拆成可并行、文件域互斥的任务包，每个任务包对应一个子 Agent | 任务包集合（每个任务包含任务集与独占文件域声明） |
| Agent 分配 | 按第 3 节的分配规则，把任务包分配给本轮 Agent；按需分配，不必占满上限 | 本轮 Agent 名单及其任务包、文件域清单 |
| 并行修复 | 各 Agent 在自己独占的文件域内独立修复，不做轮内跨 Agent 沟通，冲突交给轮次报告 | 各任务包修复结果（改动文件清单、自验证记录） |
| 结果汇总 | 汇总所有 Agent 的修复结果，整理为轮次报告 | 轮次报告（格式见第 5 节） |
| 验证门禁 | 运行本轮触达的门禁（构建、lint、typecheck、测试），判定本轮是否通过 | 验证结果（通过/未通过、失败明细） |
| 输出成为下一轮输入 | 轮次报告中的"未完成、新发现、遗留问题、验证结果"合并进下一轮问题清单 | 下一轮的问题清单（增量） |

闭环要点：

- 轮内各 Agent 之间不互相依赖、不互相等待；任何轮内阻塞都降级为"未完成"，写入轮次报告，由下一轮承接。
- 验证门禁是每轮修复的自然终点，不单独占用一轮；只有全仓级、跨轮的最终验证（R6）才单独成轮。
- 一轮的输出不是"成功"或"失败"二元结论，而是"状态 + 增量信息"：下一轮只看轮次报告，不需要回溯各 Agent 的中间过程。

## 3. Agent 分配规则

所有轮次必须遵守以下分配纪律：

1. 每轮最多 12 个 Agent。上限是资源约束，不是目标；按需分配，任务少则少开 Agent，不必占满。
2. 同轮各 Agent 的文件域必须互斥。分配任务包时，先划定文件域再做拆分；同一文件在轮内只允许被一个 Agent 写入。文件域互斥检查在"任务分解"环节完成，写入本轮 Agent 名单。
3. "文件所有权"纪律：一个文件在同一轮内只有一个所有者（owner）。尤其注意共享元文件——
   - `package.json`（仓库根）每轮只能有一个 Agent 编辑；
   - `Cargo.toml`（根工作区）每轮只能有一个 Agent 编辑；
   - 各 crate 的 `Cargo.toml`、前端各包的 `package.json` 同理按文件归属划定唯一所有者；
   - 涉及共享文件的改动（如新增依赖、更新脚本）由该轮的唯一所有者统一执行，其他 Agent 把需求写入轮次报告，由下一轮的所有者承接。
4. 轮间文件可转移所有权：上一轮遗留的、落在共享文件上的改动，在下一轮开始时按任务包重新划定唯一所有者，不允许两轮同时残留对同一文件的未完成编辑。
5. 文件域的划分以"目录 + 文件"为粒度，推荐以 crate（`crates/*`）与前端模块（`apps/agent-workbench/src/*`、`apps/crish-desktop/*`）为单位，便于冲突扫描。
6. 全局纪律引用：删除铁律与混乱上报流程见 `05-协同操作约束与安全.md` 顶部（最高优先级）。

## 4. 轮次总览表

| 轮次 | 目标 | 任务集 | 并行依据 | 输出产物（下一轮输入） |
| --- | --- | --- | --- | --- |
| R0 问题识别与基线 | 建立可复现的基线：全仓构建、测试、lint 的状态快照与问题清单 | 全仓扫描、基线记录、问题按文件域归类——由第一波只读审计完成，无独立执行手册，证据见本总览与各手册问题识别节 | 按 crate 与应用目录分片扫描，互不触碰 | 基线报告；问题清单（R1 起各轮按需认领） |
| R1 迁移收尾 | 完成迁移的静态收尾：清死依赖与垃圾文件、修陈旧断言、已删包引用清零 | T1 package.json 收尾；T3 Rust 依赖域收尾（删 conex-ipc/tokio-tungstenite 死依赖）；T4 command-registry 断言修复；T5a workbench 引用修复（CLI 收尾）；T17 零风险卫生 | 前端 / Rust 依赖域 / 测试断言 / 根目录文档文件域互斥；package.json 归 T1、根 Cargo.toml members 归 T3 唯一编辑 | 轮次报告；清理后的包清单与 Rust 依赖图、零死引用 workbench、干净根目录与文档位 |
| R2 守门与深度清理 | 固化质量门禁（knip 死代码门禁、性能基线自动回写），清除死代码与命名残留 | T2 启用 knip；T8 死代码清理；T16 性能基线自动回写；T18 commandMap 双命名空间清理 | T2 需 R1 的 T1/T5a 终态为扫描面；T8 依赖 T2 的零引用报告；T16/T18 分域独立并行 | 轮次报告；knip 门禁、死代码清零、性能基线自动回写、命令映射命名空间终态 |
| R3 契约与引擎内核地基 | 固化 `conex-types` 契约（生成链路）与引擎内核骨架（ToolContext、域 store、依赖规则） | T6 契约生成链路；T9 Tool::execute 引入 Context；T11 layoutStore 状态级拆分；T14 depcruise 微观规则 | 四条线写集两两不相交，全程并行；生成产物落点冻结只读 | 轮次报告；生成类型与解析器、ToolContext 新签名、4 个域 store、≥10 条微观依赖规则 |
| R4 契约消费与治理 | 各层按契约改造，治理门禁落地（分派表、审批事件、workspace.lints、conex-db 拆分） | T7 EventRouter 重构；T10 权限规则引擎；T13 workspace.lints 填充；T15 conex-db 拆分 | 四条线写集两两不相交，全程并行；T13 与 R1 T3 串行（根 Cargo.toml 同文件）、T15 与 R1 T1 串行（package.json 同文件） | 轮次报告；分派表与单 schema、真实审批事件链、lint 基线、conex-db 拆分终态 |
| R5 架构决策与文档 | 把已定型的结构固化为文档：ADR、架构文档重写（以代码为真源） | T12 持久化方案 ADR + 崩溃一致性测试；T5b 架构文档重写 | 文档域与测试域互斥，两个 Agent 并行；不触碰共享元文件 | 轮次报告；ADR 与崩溃一致性测试、daemon 语义清零的文档集 |
| R6 终验门禁 | 全量验证收敛：构建、lint、typecheck、测试全绿；残留回归确认 | T19 全量回归门禁（吞并 R0–R5 全部验收项；小修仅限门禁阻塞项） | 禁止并行：门禁命令先后依赖，单一执行者（只读验证域可给观察 Agent 分片） | 终验报告；残留问题清单（映射重开轮次，作为 R7 的前置约束） |
| R7 Agent 功能实现 | 落地多 Agent 调度功能，使本方案的执行能力成为产品能力 | 执行手册见 `04-Agent功能需求设计.md`（含 C1–C10 能力规格与可测验收断言）；调度器、事件契约、恢复重试、压缩配额等能力 | 按功能子模块分片，文件域互斥（见 04 号文档第 3 节依赖图） | 可运行的多 Agent 调度能力；验收报告 |

> 注：T5 拆分为 T5a（R1 引用修复）与 T5b（R5 架构文档重写），两半分属不同轮次、文件域互斥。

轮次之间的依赖逻辑（只讲逻辑顺序，不排优先级）：

- R0 是唯一入口，其余各轮都依赖 R0 的问题清单。
- R1 与 R2 无相互依赖，但都依赖 R0；R2 的 T2 需以 R1 的 T1/T5a 终态为扫描面，两者在各自文件域内推进。
- R3 依赖 R1/R2 的结果（地基要落在干净的地面上），且 R3 的契约定稿是 R4 的前提。
- R4 消费 R3 契约并固化治理；R4 落地后，R5 的文档以 R3/R4 的产物为描述对象。
- R6 是 R1–R5 全部产物的汇验，通过与否决定 R7 是否在收敛的地基上动工。
- R7 是最终轮，产出 Agent 调度功能本体。

## 5. 每轮输出的标准化格式

每一轮（R0 基线轮除外，它输出基线报告）结束时，主调度 Agent 必须生成轮次报告。该报告是下一轮的输入，格式固定为以下模板，逐项填写，不得省略：

```markdown
# 轮次报告：R{n}

## 轮次元信息
- 轮次：R{n}
- 本轮 Agent 数：{n} / 12
- 任务包数：{n}
- 门禁执行结果：{通过 / 未通过}

## 一、已完成
- 任务包编号｜文件域｜改动摘要｜自验证情况（每项一行）

## 二、未完成
- 任务包编号｜文件域｜未完成原因｜承接建议（每项一行）

## 三、新发现
- 问题条目（编号、文件域、现象、处理方式建议；不包含在本轮任务包内的问题）

## 四、遗留问题
- 条目编号｜文件域｜现象｜建议承接轮次（含共享文件上的待办改动需求）

## 五、验证结果
- 验证域：{构建 / lint / typecheck / 测试}
- 通过项：{列表}
- 失败项：{列表}（含命令输出定位）
- 结论：{本项验证是否通过}

## 六、输出到下一轮的问题清单
（由主调度 Agent 把"二、未完成""三、新发现""四、遗留问题"合并、去重、编号，作为下一轮输入）
```

填写要求：

- "已完成 / 未完成"按任务包填写，与分配时的任务包一一对应，便于审计。
- "新发现"只登记本轮范围之外、但在修复过程中发现的问题，不插入本轮任务包。
- "验证结果"按验证域逐项列出，失败项必须给出可复现的定位信息（命令与错误位置）。
- 下一轮只依据本报告与上一轮问题清单行动，不回溯 Agent 中间过程。
