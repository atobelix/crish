## 0. 结论先行

**一句话**：Crish 的门禁结构完整度不低于任何参考项目（3 层 CI + clippy 基线 + knip + depcruise 11 规则 + 双结构门禁脚本），差距集中在**量化与自动化**——190 条 clippy 基线是文档不是脚本、knip warn 级拦不住导出面膨胀、depcruise 17 环挂着无人断。治理收尾的核心不是"再立新门禁"，而是**把既有基线与缺口补进机器**：I1 先立 ratchet（新增告警 > 0 即失败），I2/I3 在护栏内清零，I8 收口量化缺口。

**三条总原则**（贯穿本方案全部任务）：

1. **存量可留、增量必零**（ratchet 哲学）：190 条存量只准按基线清单逐条消除，不许躺平也不许一刀切清零；新增告警从 I1 起被脚本拦截（jcode `check_warning_budget.sh` 的 `--update` 语义：提升基线必须显式、有意的清理）。
2. **自然内化、不另起炉灶**：所有新脚本挂在现有门禁体系上扩展——`check-clippy-baseline.mjs` 直接消费 T13 文档的 `BASELINE_LIST_START/END` 标记区，`check-crate-size.mjs` 是 `check-conex-db-size.mjs` 的泛化，`clippy.toml` 禁令与 01 方案 S11 共用同一文件域；禁止为完成任务临时造平行通道。
3. **豁免必须写理由**（grok 模式）：任何 allow / 豁免登记必须带原因注释（`clippy-workspace-T13.md:83-95` 的 §3.2 格式），不留裸 allow；本方案所有豁免决策落文档、可复核。

**范围**：本方案只写逻辑执行顺序与任务分解，不写时间/人员/优先级；轮次编排（I1–I3 + I8 收口）与 00 总览呼应，编排见 00-总览与轮次编排.md。

### G1 clippy 基线 ratchet 脚本（新增告警 > 0 即失败）

- **目标**：把「新增告警必须为 0」从 T13 文档约定变成 CI 事实（jcode 预算脚本语义，ref-analysis 04 G1/Top 1）。
- **文件域**：`scripts/check-clippy-baseline.mjs`（新增）+ 根 `package.json`（scripts 位）+ `.github/workflows/ci-mid.yml`（clippy job 接线）+ `docs/multi-agent-repair/基线记录/clippy-workspace-T13.md`（标记区维护）。
- **内容**：
  0. **基线清理前置（I0-02 修正）**：先清理 T13 `BASELINE_LIST_START/END` 标记区中 daemon_discovery.rs 相关 **30 条僵尸条目**（模块已随 d82f7468 删除；实测 30 条，非原任务书预估 26 条），再脚本化比对——否则基线含已删文件条目，脚本比对必红；清理后基线计数 190 → 160（以 workbench 恢复编译后复跑校准为准，见 `reports/I0-02-遗留域核对.md` §1）。
  1. 解析 `cargo clippy --workspace --all-targets` 输出：按「消息文本 + `--> 文件:行:列`」归一键，忽略行号只留文件（行号变动不应算新增）。

  3. `--update` 语义：把当前 clippy 输出全量重写回标记区（git diff 可见），提升基线必须显式执行（jcode 只许降不许升）。

### G2 disallowed-methods 禁令（禁裸 `Command::spawn` / `fs::remove_*`）

- **目标**：把组织级安全约定下沉为编译器（grok `clippy.toml:21-26` 模式，ref-analysis 04 G2/Top 2）；「不需要人记规则，clippy 替你守；豁免必须写理由」。
- **文件域**：`clippy.toml`（新增，**写入与 CI 接线归 01 方案 S11**，本任务只产出清单与评审）+ 各 crate 豁免处（`#[allow]` + 理由注释）。
- **内容**：
  1. **禁令清单定义**：
     - 禁 `std::process::Command::spawn` 及全家（`Command::output`/`Command::status` 视评审结论）：子进程必须经命令门禁/进程注册面（`crates/conex-sandbox/src/lib.rs:20-50` CommandGatekeeper、agent-workbench 的 daemon 进程注册）；理由：未 enroll 子进程脱离会话存活（grok 同款禁令理由）。
     - 禁裸 `std::fs::remove_file` / `remove_dir` / `remove_dir_all`：删除必须走删除接管接口（01 方案 S3 `delete_file`/`delete_dir`，8 工具变 10）；理由：删除可恢复的前提是删除前有快照（ref-analysis 04 1a）。**接线时点：删除工具落地（01 方案 I2）后生效**，此前存量豁免暂留。
  2. **存量命中清单**：先跑一次 `cargo clippy --workspace`（临时在 clippy.toml 加禁令后）输出全量命中，登记为豁免评审表（每处：位置 / 命中禁令 / 是否经门禁 / 处置：改写 or 豁免+理由）。
  3. **豁免评审流程**（对齐 T13 §3.2 豁免记录格式）：经 CommandGatekeeper 的调用豁免（注释注明门禁路径）；裸调用改写为经门禁路径；无法改写的带理由豁免并登记。
  4. **与 01 方案协同**：评审表交付 01 S11 写入 clippy.toml；本方案验收以评审表齐备为准，接线验收见 01 S11。
- **验收命令**：
  - 评审表齐备（每处命中均有处置结论）；
  - 01 S11 接线后：新代码直接 `Command::spawn` → `cargo clippy --workspace` 报错（禁令拦截验证）；
  - 存量豁免后 `cargo clippy --workspace --all-targets` exit 0、0 新增。
