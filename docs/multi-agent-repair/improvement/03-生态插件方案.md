## 0. 结论先行

**一句话**：Crish 的插件体系是"**声明面完备、引擎零接线**"（14 钩子与 24 引擎事件之间无桥、
registerTool/registerMcpServer 无消费方、SkillLoader.toTool 与 McpClientBridge 均未接入运行集），
本方案用 6 个任务（E1–E6）在 **I8 生态单轮**内补齐"事件面 → 运行时 → 官方插件"三段链路（I8 前段 E1+E2、中段 E3/E4/E5 并行、终验段 E6，编排见 00-总览），采用
**"Rust 引擎内分派 + TS 插件经事件桥观察"双轨架构**——这是 Tauri 壳 + Rust 引擎 + TS UI
三层结构下跨语言成本最低、且与既有 `EventBridge` / `HookRegistry` / 依赖注入面完全合拍的方案。

**三条总原则**（贯穿本方案全部任务）：

1. **不新建机制，只接线既有资产**：事件分派复用 `hooks.rs` 的 HookRegistry（扩展变体而非
   另起炉灶，06 文档:5-7 头注已声明演进方向）；工具改写复用 ToolMiddleware 链（加第 4 钩子
   `on_definition`）；MCP 复用 `bridge.rs` 的 McpClientBridge；技能复用 plugin-sdk 的
   SkillLoader.toTool——全部是"已有代码接上电"，不造新抽象。
2. **插件错误不杀死 run，超时默认放行**：沿用 06 文档已定的 "propagate 不中断会话" 原则，
   补齐 kimi 的"超时默认 allow"语义（runner.ts:72,111,117）与 opencode 的"错误进事件流"
   （`runtime-error`）两环，插件永远是降级通道而非关键路径。
3. **第一代官方插件 = 内置 TS 插件包，不提前开大面**：参考 kimi-datasource（纯声明包 +
   SKILL.md 式使用说明）与 opencode internalPlugins（内置即插件，`plugin/index.ts:65-82`）
   两种先例的组合——官方导入插件以纯函数 + manifest 声明交付，UI/文件系统能力留在宿主层，
   不要求第一代插件运行时支持 UI 回调（ref-analysis 03 步 3 评估的减法）。

**范围**：本方案只写逻辑执行顺序与任务分解，不写时间/人员/优先级；生态任务全部落在
**I8 单轮**（00-总览口径：I7 为多 Agent 联测、I8 为生态 + 治理收口 + 终验、无 I9），
编排见 00-总览。

关键事实（本方案所有决策的锚点）：

- **Rust 引擎与 Tauri 壳同进程**，TS UI 与引擎跨语言（IPC/事件桥）；引擎热路径
  （审批后 → 工具执行前）不允许阻塞等待跨语言回调——这决定了 E2 的"双轨"架构。
- **事件桥已存在**（`engine.rs` core_event_bridge / EventBridge）：24 引擎事件已能流向
  TS 侧，插件钩子可搭便车，不新造 IPC。
- **插件声明面全部在 TS**（manifest/TrustGate/14 钩子/PluginAPI 双重校验），loader 动态
  import TS 模块——插件生态资产天然是 TS 形态；而 `plugin-sdk` 的 SkillLoader 用了
  `node:fs`（Node 语义），webview 环境没有 Node——依赖注入面（plugin-api.ts:6-8
  "依赖全注入"）正好是解法，E2 补 fs 适配层即可。

### 2.4 失败策略与超时默认值统一表（E1/E2 共用，冻结）

| 事件 | 默认 mode | observe 默认 timeoutMs | on 默认 timeoutMs | 超时行为 | propagate 失败行为 |
| --- | --- | --- | --- | --- | --- |
| `session.start` | observe | 1000 | 2000 | 吞掉 + 计数 | 记录日志，会话照常启动 |
| `turn.start` / `turn.end` | observe | 1000 | 1000 | 吞掉 + 计数 | 记录日志，收场流程继续（06 已定） |
| `tool.pre` | observe | 1000 | 2000 | **降级放行**（kimi 守门者不可用放行优先） | 该工具调用以执行失败结果收场，批继续（06 已定） |
| `tool.post` / `tool.error` | observe | 1000 | 1000 | 吞掉 + 计数，不改变结果 | 记录日志，结果保持 |
| `context.compact.start` / `context.compact.end` | observe | 1000 | 1000 | 吞掉 + 计数 | 记录日志，压缩流程继续 |
| `session.end` | observe | 1000 | 1000 | 吞掉 + 计数 | 记录日志，收场继续 |
| `model.beforeRequest` / `model.afterResponse` | observe | 1000 | 1000 | 吞掉 + 计数 | 记录日志，请求照发 |
| `subagent.start` / `subagent.end` | observe | 1000 | 1000 | 吞掉 + 计数 | 记录日志 |
| `error.occurred` | observe | 1000 | 1000 | 吞掉 + 计数 | 记录日志 |

统一规则：
1. **observe = 广播**（现有 dispatch 语义），handler 失败按注册 failStrategy 处置；
2. **on = 串行 + 控制信号**（`HookControlSignal`：continue/stop/block/modifiedInput/
   modifiedOutput），第一版控制信号仅在 Rust 侧原生 handler 有效（见 3.3）；
3. **超时 = 虚拟失败**，语义等同于该 handler 返回 Err（按 failStrategy 处置），且
   tool.pre 的 on 模式超时**固定降级为放行**（kimi runner.ts:117）；
4. **插件错误事件化**：任何 handler 失败（超时/Err/加载失败）除按策略处置外，统一发
   `runtime-error` 诊断事件（opencode publishPluginError 语义，`plugin/index.ts:135-137`）。

### 2.5 matcher 过滤（kimi 借鉴，不改事件面）

`tool.pre` / `tool.post` / `tool.error` 的注册描述附 `matcher`（工具名正则，默认 `*` 全量）。
桥接层过滤而非事件面改动（ref-analysis 03 2.4）：Rust `HookRegistry` 的注册条目增加
`matcher: Option<&str>` 字段，dispatch 时对 `tool_name` 做正则匹配，不匹配的条目跳过；

## 3. 插件运行时架构决策（E2 的成果物，先给决策再分配任务）

### 3.1 决策：Rust 引擎内分派 + TS 插件经事件桥观察（双轨）

```
引擎热路径（Rust，同步、可携带控制信号）
  HookRegistry（session-loop/hooks.rs）── Rust 原生 handler
    遥测/审计/审批类内置扩展点（与 ToolMiddleware 链共享点位）
        │
        │ 同一事件点位同时发 24 事件（EventBridge 已存在，engine.rs:585）
        ▼
Tauri 事件桥（Rust → TS）
        │
        ▼
TS 插件运行时（webview 进程，plugin-sdk loader 宿主）
  事件转发 → 插件 hook bus（observe 模式分发 / on 模式串行）
  插件注册表状态（installed/enabled/activated）→ ExtensionCard 展示
        │
        └─ on 模式控制信号回写：仅 tool.pre 第一版支持
              TS → Tauri command → Rust 竞速窗口合并（异步，超时默认放行）
```

- **引擎内 Rust 钩子分派**：保留并扩展 `HookRegistry`（同步 handler → `async_trait`），
  作为引擎原生扩展点（中间件/遥测/审计直接挂 Rust 侧）；
- **TS 插件**：在 webview 进程内运行（与 UI 同进程），`plugin-sdk` loader 动态 import
  TS 模块（第一版官方插件内置打包，第三方动态加载 Phase 2）；事件经既有 EventBridge
  转发，插件 handler 收到 payload 与 Rust 侧同一事件点位、同一语义；
- **纯 Rust 插件（cdylib + 版本化 trait）**：明确否决。理由见 3.2。

### 3.2 理由（为什么这个设计适合 Crish 三层结构）

1. **同进程但跨语言，同步回调面不可行**：Tauri 壳与 Rust 引擎同进程，但 TS 插件在
   webview，跨语言唯一通道是 IPC/事件（异步）。引擎热路径（审批后 → 工具执行前）不允许
   阻塞等待 IPC 往返——**同步控制面（tool.pre 的 Block、on 模式控制信号）只能留在 Rust
   侧**；TS 侧插件承担观察 + 异步策略，二者通过同一事件点位、共享 24 事件载荷。
2. **插件生态资产是 TS，纯 Rust 插件第一代成本失衡**：manifest/TrustGate/14 钩子/
   PluginAPI/loader 全部在 plugin-sdk（TS），且 loader/store/trust-gate 已 100% 测试覆盖；
   纯 Rust 插件需要新 ABI、cdylib 构建链、trait 版本化与安全边界，与禁令 18 的
   restricted/full 两级信任模型冲突面大（ref-analysis 03 步 1 评估）。资产在哪，运行时
   就在哪。
3. **事件桥是搭便车而非新造**：`engine.rs` 的 EventBridge 已把引擎事件送到 TS 侧
   （core_event_bridge，engine.rs:585），插件钩子复用该通道，不引入第二套 IPC。
4. **依赖注入面已存在**：plugin-api.ts:6-8 明示"依赖全注入、不直接 import agent-core/
   agent-tools/agent-mcp"——webview 环境没有 node:fs 的问题，正是用注入面解决的
   （loader 的 fs 依赖替换为 Tauri fs 适配层，见 E2 内容）。
5. **双轨共享事件面，职责清晰**：Rust 侧 = 程序化策略层（同步、可拦截）；TS 侧 =
   插件生态层（观察、异步、UI 可见）。与 06 文档 "ToolMiddleware = 链式扩展面 /
   HookRegistry = 广播观察面" 的分工表述完全同构，不引入第三种语义。

### 3.3 控制信号回写路径（on 模式第一版范围）

- `on` 模式**第一版仅支持 `tool.pre` 的 block 信号回写**：TS 插件返回
  `{ type: 'block', reason }` → Tauri command 写回 → Rust 在 tool.pre 竞速窗口内合并
  （超时默认放行，2.4 表）。tool.pre 的 stop/modifiedInput 与其余事件的 on 信号
  **降级为"串行观察 + 日志记录回写意图"**，不改变执行语义——避免跨语言同步面失控。
- Rust 原生 handler 不受此限：`HookAction`（Continue/Block）保持同步语义，中间件链
  （Proceed modified_input / Replace / Block）保持完整改写能力。
- 该限制写入 plugin-sdk 类型注释与文档（HookOnHandler 的 JSDoc 标注"控制信号仅
  tool.pre 第一版生效"），防止插件作者误用。

### 3.4 manifest 双轨收敛决策

- **现状**：`packages/plugin-sdk/src/manifest/manifest.ts`（entrypoints/engineVersion/
  declaredHooks 14 类型化）与 `packages/shared-types/src/plugin.ts`（entry/declaredAgents/
  minHostVersion/declaredHooks: string[]）结构不同；且 `shared-types/src/index.ts` 未导出

### 3.5 超时默认策略

## 5. 轮次划分（全部落 I8 单轮，编排见 00-总览）

### 5.1 I8 前段：插件运行时地基（E1 + E2）

  事件无桥、shared-types hooks 域缺失（HookPayloadMap 悬空）、loader 无宿主、manifest
  双轨漂移。本段目标：事件面（E1 第一批）+ 运行时（E2）落地，使插件在 TS 侧可装载、
  事件在 Rust → TS 间可流动。
- **任务分解**：E1（hook 事件面补齐，第一批 6 事件 + 映射表冻结 + matcher + 超时）；
  E2（插件运行时接线，manifest 收敛 + loader fs 注入 + 激活链路 + 事件桥 + trust-gate 校验）。
- **Agent 分配**（2 个，文件域互斥）：
