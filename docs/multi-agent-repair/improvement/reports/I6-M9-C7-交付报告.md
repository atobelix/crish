## 1. 阶梯设计（四级恢复阶梯）

| 阶梯 | 触发 | 落地（recovery.rs） | 边界 |
| --- | --- | --- | --- |
| 阶梯 1 自动重试（引擎内） | provider 流网络类错误 | `ladder1_decision`：瞬态分类（`ProviderErrorKind` 直判，镜像 retry.rs 决策表）+ 指数退避（750ms 起 / 8s 封顶 / 60s 总预算）+ `RecoveryRetryPolicy`（默认与 retry.rs 逐项一致） | 只处理瞬态类（rate-limit/5xx/网络/超时）；auth/quota/context_length 不上行本阶梯；流已产出内容不重试；重试不计入 run 失败、不留痕（测试断言 events 为空） |
| 阶梯 2 主 agent 激活（软注入） | 阶梯 1 预算/次数耗尽上行 | `escalate`：steering 条目入 `PendingMessageQueue`（group_id=`recovery-<run_id>` 原位替换去重、is_steering 受保护位）+ 通知**落库**（`recover_notifications`，pending 位）+ `recovery-escalated`/`recovery-steering` 事件留痕 | 通知落库保证重启后主 agent 仍可见（C7 边界 3）；主 agent 注入激活指令的 L1 steer 环由引擎侧经 M8 通道送达（本模块只写队列与通知）；`acknowledge` 关闭 pending，重启不重排 |
| 阶梯 3 重分配/fork | 主 agent 决定不等待 | `fork_and_reassign`：`SessionTree::fork`（冻结接口）派生新叶子 → `read_branch_path` 产出工作流路径落 `subagent_path_json`（新 run 行）→ spawner 启动新 run 承接同一目标 → 原 run 置 failed（runs 表 `recovery-fork` 原因）→ `recovery-fork` 事件留痕；**fork 三态上下文继承**（02 Top 6）：同窗（≤24h）且注入 ≤ 窗口 80% → Verbatim 字节级、超窗/超占比 → Summarized（C9 摘要位，M10 实装前记录模式）、空内容 → New | 幂等：同指纹同源 run 重复 fork 返回既有记录（不重复 spawn、不重复计数）；受 Episode 预算与并发预算（引擎侧 RecursionGuard）双重约束；fork 粒度整 run 目标（Q4 暂定） |
| 阶梯 4 上报用户 | 阶梯 3 后仍失败 / 预算超限 | `report_to_user`：`UserReport`（卡在哪一步 + 各阶梯尝试记录 + 建议怎么办）→ `recovery-report` 事件留痕 + run 标记需用户介入（`recover_needs_user`，UI 可观察位） | 上报前全部重试/重分配留痕（events 表）作为用户决策依据；05 手册第 5 节第 4 级语义 |

**协调器接线**：`RecoveryCoordinator`（session_id + `Arc<dyn RecoveryStore>` +
队列 + 会话树 + spawner），入口三方法——`on_subagent_run_failure`
（阶梯 1→2 自动决策，预算超限时跳过阶梯 2 直落阶梯 4）、`fork_and_reassign`
（阶梯 3，超预算内部转阶梯 4）、`report_to_user`（阶梯 4）；`acknowledge`
与 `restore_steering_notifications` 供引擎侧确认与重启恢复。引擎侧
（apps/agent-workbench）按模块头「接线契约」调用，属本任务文件域外。

## 2. 恢复预算制（01 Top 5，Reasonix Auto Guard 借鉴）

- **操作指纹**：`fingerprint(subagent_id, task)` = FNV-1a 64 位哈希
  （十六进制 16 位）——同子代理定义 + 同任务共享一个 Episode 预算，
  不同任务不互相消耗（测试锁定稳定性与唯一性）；
- **Episode 预算**：每会话每指纹最多恢复 N 次（阶梯 3 fork 次数），
  默认 3，可配 `recover_max_episodes`（session_meta 键）；计数落
  `recover_episodes`（JSON 映射），重启恢复不重放授权（预算跨重启
  一致，测试锁定）；
- **超预算即停**：预算耗尽后 `on_subagent_run_failure` 不再产生阶梯 2
  通知、`fork_and_reassign` 不再 fork——一律 `recovery-budget-denied`
  留痕后直接阶梯 4 上报用户（测试锁定：limit=1 时第 2 次 fork 直落
  阶梯 4）；
- **幂等**：同指纹同源 run 重复 fork 返回既有记录、同 run 重复升级
  steering 原位替换、acknowledge 二次确认无变更、重启后 pending 通知
  不重复入队。

## 3. 测试

**recovery.rs 单元测试 23 个**：阶梯 1 决策表（镜像 retry.rs 13 类）、
退避序列 750/1500/3000/6000/8000 封顶、预算耗尽上行、已产出内容上行、
次数耗尽上行、默认不重试、指纹稳定性与唯一性、Episode 上限与超限
`BudgetExceeded`、预算 JSON 往返 + 坏 JSON 宽容、fork 三态判定（含 80%
与 24h 边界含等号）、三态 wire 名、steering 条目形状与分组去重、协调器
逐级（阶梯 1 预算内无留痕 / 阶梯 2 落库 / 激活载体 + acknowledge /
重启保留 pending / fork 路径与留痕 / fork 幂等 / 预算超限直落阶梯 4 /
预算超限跳过阶梯 2 / 重启恢复预算 / 阶梯 4 报表内容 / 缺源叶子结构化
拒绝 / spawn 失败不计数）。
