### 1.2 四条主线与关系（为什么是这个顺序）

按 `ref-analysis/04-创新点与治理全景.md` 第 3 节的关系图，四条主线存在严格的依赖链：

```
主线四：治理收尾（地基线）—— clippy 190 清零 / ratchet 脚本化 / knip 收紧 / G1-G7 缺口
        │ 地基：所有功能代码进门禁合入（门禁不闭环，任何主线合入都扯皮）
        ▼
主线一：安全监控（事故驱动线，第二地基）—— 删除接管接口 + C3/C4 审批门禁 + 高危命令监控
        │ 运行期风险面：多 Agent 上线前的必要前置（C3/C4 审批基础设施）
        ▼
主线二：多 Agent 调度（最大投入线）—— C1-C10：Tool Context → 权限 → run_subagent
        │ → 事件契约 → 调度器 → 恢复 → 压缩/配额
        ▼
主线三：生态（插件/hook，最后启动）—— TS 面收口 + hook 桥 + 官方插件试点
```

依赖逻辑（本阶段轮次编排的依据）：

1. **主线四（治理收尾）是其余三条的地基**：C1–C10 与删除接管都要写代码进门禁；I1 先落地 ratchet 脚本（G1/G7/G5），让「新增告警必须为 0」从 T13 的文档约定变成 CI 事实，此后每一轮合入都被机器守门——这正是 jcode「预算 = 只许降不许升」与 grok「disallowed-methods 禁令」教给我们的（`ref-analysis/04` §2.3 G1/G2）。
2. **主线一（安全监控）是主线二的前置风险面**：多 Agent 上线 = 更多并发写操作 = 更高误删/误回退概率。`04-Agent功能需求设计.md` §4 实现顺序第 2 步「权限引擎」（C3/C4）排在调度器（第 5 步）之前（`04:376`）；删除接管接口（05 §13 预留能力）作为旗舰应在 `run_subagent` 工具上线前落地。因此 C3/C4 审批基础设施（I3 交付）是 I4 起 run_subagent 写操作挂靠的审批通道。
3. **主线二（多 Agent 调度）为主线三提供挂接面**：插件/hook 依赖稳定的事件契约（C8 事件信封）与工具面；没有 Rust 侧 subagent 事件发射，hook 无处挂（`ref-analysis/03` §3.2 的 hook 桥前提是 Rust 侧事件完备）。因此 I7 先补齐事件源与 24→14 事件映射表，I8 才启动 hook 桥。
4. **主线三（生态）最后启动**：`ref-analysis/03` 已定「步 1 插件运行时 → 步 2 hook 桥 → 步 3 官方插件试点」，且第一版不做 UI 回调；在主线二稳定前启动插件线会两头不靠。

## 2. 闭环迭代模型

### 2.1 六环节模型（沿用 00-方案总览 §2）

本阶段每一轮遵循与主修复阶段完全相同的闭环链路：

```
问题识别 → 任务分解 → Agent 分配 → 并行修复 → 结果汇总 → 验证门禁 →（输出成为下一轮输入）
```

| 环节 | 职责 | 产物 |
| --- | --- | --- |
| 问题识别 | 依据上一轮输入（改进问题清单、遗留问题、新发现）与当前代码库状态，识别本轮要处理的问题范围 | 本轮问题清单（条目含：编号、文件域、现象、处理方式） |
| 任务分解 | 把问题清单拆成可并行、文件域互斥的任务包，每个任务包对应一个子 Agent；轮内依赖以「串行交接」表达，不跨轮等待 | 任务包集合（任务集 + 独占文件域声明 + 轮内交接序） |
| Agent 分配 | 按第 3 节分配规则分配；按需分配，不必占满上限 | 本轮 Agent 名单及其任务包、文件域清单 |
| 并行修复 | 各 Agent 在自己独占的文件域内独立修复，不做轮内跨 Agent 沟通；轮内依赖的交付物按交接序传递 | 各任务包修复结果（改动文件清单、自验证记录） |
| 结果汇总 | 汇总所有 Agent 的修复结果，整理为轮次报告；核对 git 提交状态（每轮结束立即提交） | 轮次报告（格式见第 5 节） |
| 验证门禁 | 运行本轮触达的门禁（构建、lint、typecheck、测试、ratchet 脚本），判定本轮是否通过 | 验证结果（通过/未通过、失败明细） |
| 输出成为下一轮输入 | 轮次报告中的「未完成、新发现、遗留问题、验证结果」合并进下一轮问题清单 | 下一轮的问题清单（增量） |

闭环要点（与 00-方案总览 一致，另有两点强化）：

- 轮内各 Agent 互不依赖、互不等待；任何轮内阻塞降级为「未完成」，写入轮次报告，由下一轮承接。
- 验证门禁是每轮修复的自然终点，不单独占用一轮；只有全仓级、跨轮的最终验证（I8）才单独成轮。
- **强化 1（轮内串行交接）**：轮内依赖允许在轮内后段交付（如 01 方案 I2 的 B1 先交付 API、B2/B4 后段消费），但必须写进任务包的交接序；交接未成的交付物一律按「未完成」处理，不拖到轮后。
- **强化 2（合入门禁前置）**：I1 起 ratchet 脚本（G1）与 clippy `--all-targets` 口径在 CI 生效，任何轮次的合入都被机器守门；「新增告警必须为 0」不再依赖人读 T13 文档。

### 2.3 轮次之间的依赖逻辑（总览）

- I0 是唯一入口，其余各轮都依赖 I0 的改进问题清单。

## 3. Agent 分配规则与提交纪律

所有轮次（I0–I8）必须遵守以下纪律：

1. **每轮最多 12 个 Agent**。上限是资源约束，不是目标；按需分配，任务少则少开 Agent（参考 R6 只开 2 个）。一轮 ≤12 包含只读观察 Agent。
2. **同轮各 Agent 的文件域必须互斥**。任务分解时先划定文件域再做拆分；同一文件在轮内只允许一个 Agent 写入。文件域互斥检查在「任务分解」环节完成，写入本轮 Agent 名单。
3. **共享元文件唯一所有者**：
   - 根 `package.json`、根 `Cargo.toml`（含 workspace members）、`clippy.toml`、CI 配置（`ci.yml`/`ci-mid.yml`/`ci-slow.yml`）每轮只能有一个 Agent 编辑；
   - 新增依赖、新 crate 登记等共享改动由该轮唯一所有者统一执行，其他 Agent 把需求写入轮次报告，由下一轮所有者承接。
4. **能力级文件所有权沿用 04 §4 互斥约定**（本阶段全局纪律，01 方案已引用）：
   - `crates/session-loop/src/tool_events.rs`、`tool_exec.rs`（审批判定与注入路径）：**C3 独占**（01 方案 S6）；C4 只读经判定钩子挂载；
   - `crates/orchestrator/src/session.rs`（SessionTree）：**C6 独占**；C1（read_branch_path）、C7（fork）只读引用冻结接口；
   - `crates/orchestrator/src/restore.rs`：**C1 独占**；C6/C7 只读；
   - `apps/agent-workbench/src-tauri/src/engine.rs` build_context：**C10 主体独占**；C1/C2 只读经注入点挂载；
   - `crates/conex-compaction/src/lib.rs`：**C9 独占**；
   - `crates/orchestrator/src/steering_queue.rs`：**C7 独占写入**、C8 只读消费；`crates/session-loop/src/control.rs`（L1 steer 环）：**C8 独占**、C7 经其通道注入；
   - `session_meta`：各能力独占自己声明的键命名空间（C4 `revert_*`、C5 `explore_docs_*`、C6 `flow_on_failed`/编排声明、C8 `dispatch_*`、C9 `compact_*`、C10 `system_reinject_*`、删除接管 `trash_*`）；
   - conex-db 表结构（session_agents / session_agent_messages / session_meta / events）：只读复用既有接口，**C6 为唯一写面**（新增表/列先登记 C6 统一落盘）。
5. **每轮结束立即 git commit（提交纪律，05 §12）**：
   - **子 Agent 只提交自己文件域**：提交粒度按任务包划分，commit message 带轮次与任务包编号（如 `feat(security): I2-S3 delete takeover service`）；禁止跨域混提、禁止替他人文件域提交；
   - 轮末由主调度 Agent 核对 `git status` 干净、`git log` 与任务包一一对应；未提交项按「未完成」写入轮次报告；
   - 共享元文件的改动由该轮唯一所有者提交，其他 Agent 不得代提；
   - 理由：2026-08-02 误删事故证明「提交 = 恢复的前提」（05 §12.4）；本阶段所有删除、回退类操作本身受 I3 起生效的 C3/C4 门禁约束。
6. **轮间文件可转移所有权**：上一轮遗留的、落在共享文件上的改动，在下一轮开始时按任务包重新划定唯一所有者，不允许两轮同时残留对同一文件的未完成编辑。
7. **全局纪律引用**：删除铁律与混乱上报流程见 `05-协同操作约束与安全.md` 顶部（最高优先级）；安全基线见 `docs/rust-rewrite/31-security-baseline.md`（fail-closed 原则）。

## 5. 每轮输出的标准化格式

每轮（I0 除外，它输出基线报告）结束时，主调度 Agent 必须生成轮次报告。格式沿用 `00-方案总览.md` 第 5 节的模板，逐项填写，不得省略：

```markdown
# 轮次报告：I{n}

## 轮次元信息
- 轮次：I{n}
- 本轮 Agent 数：{n} / 12
- 任务包数：{n}
- 门禁执行结果：{通过 / 未通过}

## 一、已完成
- 任务包编号｜文件域｜改动摘要｜自验证情况（每项一行）

## 二、未完成
- 任务包编号｜文件域｜未完成原因｜承接建议（每项一行）

## 三、新发现
- 问题条目（编号、文件域、现象、处理方式建议；不包含在本轮任务包内的问题）

## 四、遗留问题
- 条目编号｜文件域｜现象｜建议承接轮次（含共享文件上的待办改动需求）

## 五、验证结果
- 验证域：{构建 / lint / typecheck / 测试 / ratchet / depcruise / knip}
- 通过项：{列表}
- 失败项：{列表}（含命令输出定位）
- 结论：{本项验证是否通过}

## 六、输出到下一轮的问题清单
（由主调度 Agent 把「二、未完成」「三、新发现」「四、遗留问题」合并、去重、编号，作为下一轮输入）
```

填写要求（在 00-方案总览 §5 基础上的本阶段补充）：

- 「已完成 / 未完成」按任务包填写，与分配时一一对应，便于审计；每项标注提交 commit（提交纪律第 5 条）。
- 「验证结果」按验证域逐项列出；本阶段新增验证域：ratchet（`check-clippy-baseline.mjs`）、depcruise、knip、`cargo clippy --workspace --all-targets`；失败项必须给出可复现的定位信息。
- 下一轮只依据本报告与上一轮问题清单行动，不回溯 Agent 中间过程。
- I0 的报告为基线复核报告（不套用本模板）：含门禁快照、遗留清单逐条复核结果、工作区收口结论、改进问题清单全量编号。
