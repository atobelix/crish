## 0. 一句话结论

**Crish 的七个独有想法方向全部成立，无一在参考项目中有完整等价物**（部分有要素级先例）；其中「删除接管 + 自动备份」「事件背压分级丢帧」「半溯源持久化」是差异化最强的三条，评分 ≥ 9。**治理门禁方面 Crish 的结构不比参考项目差（3 层 CI + clippy 基线 + knip + depcruise 11 规则），差距在「预算式 ratchet 量化守门」与「安全类 lint 禁令」两类机制**：jcode 的 8 道预算 ratchet 与 grok 的 disallowed-methods 是 Crish 最该学的东西。四条主线中，**治理收尾是其余三条的地基**（所有功能代码都要过门禁进库），安全监控是事故驱动的第二地基（2026-08-02 误删事故），多 Agent 调度是最大投入线，生态线最后启动。

### 1a. 删除接管接口（9/10，方向成立，实现面坑最多）

**参考等价物**：01 篇已确认两参考项目均无「回收站语义」。Reasonix 的两个要素值得抄：
- 删除/移动以**工具**形式暴露并统一归类（`internal/permission/permission.go:862-869`，`IsFileMutationTool`）——权限规则按工具名覆盖，不按命令文本匹配；
- checkpoint 快照的**反向语义**（`internal/checkpoint/checkpoint.go:28-33`）：`FileSnap.Content == nil` 表示「编辑前该文件不存在 → 恢复时执行删除」；反过来被删除的文件因快照留存编辑前内容，可被 `RestoreCode` 还原。**「删除可恢复」的前提就是「删除前有快照」**，这正是 Crish「无论用户是否同意都自动暂存备份」的数据结构先例。

**坑（按实现面排列）**：
1. **「极端危险 100% 拦截」不能靠正则**：`conex-sandbox` 现用正则拦 `rm -rf /`（`crates/conex-sandbox/src/lib.rs:20-50`），正则可被等价变形绕过（`rm -rf -- ./`、路径拼接）。拦截必须基于**工具级白名单判定**（删除只能走删除工具，工具内部判定目标域），而不是命令文本扫描。
2. **回收站语义的平台空缺**：send2trash 在 Windows/macOS 有系统回收站，但在容器/CI/无桌面环境下无回收站可送。需降级路径：自建隔离目录（如 `.crish-trash/`）作为回收站，并保证该目录本身被 git 跟踪或纳入快照，否则「两者皆无的删除不做」（05 §12.5）会在无回收站环境直接锁死所有删除。
3. **未跟踪文件无 git 历史**：git 跟踪文件的删除可 `git checkout` 恢复，未跟踪文件必须靠删除前快照留存内容——Reasonix 的 `Content == nil` 语义正好覆盖此面，Crish 快照结构应照此设计（快照记录「删除前内容」，恢复时按需重建或删除）。
4. **备份爆炸与留存策略**：每次删除都 stash/快照会产生无限增长。需要留存窗口 + 轮转（参考 Reasonix checkpoint 目录轮转思路），并允许用户显式「清空回收站」。
5. **用户路径与 AI 路径的一致性**：若用户自己在 UI 里的删除不走同一接口，会出现「AI 删的可恢复、用户删的不可恢复」的怪圈。UI 删除同样应接回收站语义（或至少提供统一恢复入口）。

**建议**：把「删除工具化」作为 C3 权限引擎的前置步骤落地——注册 `delete_file` / `delete_dir` 内置工具（agent-tools 由 8 工具扩为 9+），删除实现内部走「快照 → 移入回收站/隔离目录 → 登记 events 表」三步；「极端危险」判定用目标域白名单（严禁路径清单：仓库根、`~`、系统盘）而非正则。此条是 05 §13 产品化声明的最直接落点。

### 1b. 连续 git 回退频率护栏（8.5/10，设计已闭环，防误伤即可）

**参考等价物**：无。01 篇已确认 Reasonix 靠 deny 规则覆盖 git 危险命令（`permission.go:192-270`）、pi 的 `CRITICAL_BASH_PATTERNS` 不含 git 回退——两家都没有「按面积/频率触发审批」的 git 专项门禁。C4 的「时窗内第二次必审批」是 Crish 独有设计，且由 2026-08-02 事故（R1-R5 成果因「工作区误删 + 回基线 + 空壳提交」几乎全丢，见 `05:260-269`）驱动，动机真实。

**坑**：
1. **误伤合法流程**：二分排查（bisect 式「回退—验证—再回退」）会被第二次必审批打断。缓解：C4 已设计 600s 时窗归零（`04:138`），时窗内密集回退本来就该慢下来；可在 UI 上提供「本轮会话放行 N 次回退」的显式用户授权，把审批从「每次点」降为「点一次授权一批」，但**默认必须逐次审批**。
2. **计数语义要严**：只统计实际发起回退的调用（C4 第 5 条已设计「纯查询不计数」，`04:142`）；fork 子分支不继承计数（Q8 暂定，`04:435`）——需在实现时验证「换会话绕过」是否真能被 C3 面积阈值兜住，否则要考虑会话族共享计数。
3. **与 C3 的关系**：C4 叠加在 C3 审批通道上（`04:113`），实现顺序上 C3 是前提，C4 只是会话级计数 + 判定钩子，不能变成第二个审批通道实现。

**建议**：按 04 §2 设计原样实现；补一条验收断言「时窗内第 2 次小额回退（面积低于 C3 阈值）也触发审批」（`04:150` 已有）；把「连续回退视为高危场景」的语义同步进提示词指引（C2 的 git 回退谨慎指引，`04:77-80`）。

### 1c. 探索类 agent 文档配额（7.5/10，方向对，但「文档」定义与配额粒度需收紧）

**参考等价物**：无。pi 的 quota 仅指 provider token 配额（`packages/coding-agent/src/task/types.ts:222`、`modes/components/status-line.ts:426`），opencode 无文档配额概念。探索类 agent 的产出物失控是 Crish 协同手册（05 §7）用提示词约束的现实问题，配额化是正确方向。

**坑**：
1. **「文档」的定义边界**：C5 定义「入库的独立文档实体」（`04:158`），但实现时需要可判定的标准——扩展名白名单 + 路径域（如 `docs/**`）？若探索 agent 把文档写成普通消息里的长文本，配额形同虚设；若把结果写进自己的 run 目录（`.agent-runtime/`），算不算文档？建议：配额只作用于「声明为文档实体的落盘文件」（扩展名 + 目录域双重判定），run 内中间产物不算。
2. **配额粒度（Q2，`04:429`）**：按会话计数是合理默认，但 agent 定义变更后可开新会话绕过——单机单会话场景风险低，未来多会话并行探索时需要会话族共享配额。
3. **配额值 1 是否过严**：真实调研任务常需要「设计方案 + 分析报告」两份文档。建议默认值保持 1（配额语义是「探索结果默认以消息汇报，落盘必须主 agent 指派」），但凭证机制允许主 agent 显式追加配额（`explore_docs_quota` 键可配，`04:162` 已设计）。
4. **凭证协议复杂度**：C5 的「配额凭证由主 agent 在注入内容中给出」（`04:163`）是对的——比「子 agent 自报角色」可信，因为角色字符串可伪造；实现时凭证应绑定 run id 防转借。

**建议**：实现时把「文档判定规则」写进提示词协议层（与 C2 共用注入通道），验收断言补一条「以消息形式汇报的探索结果不消耗配额」。

### 1d. 工具幂等守卫（8/10，只对声明幂等的工具生效，否则是新的丢数据源）

**参考等价物**：弱。pi 的 `file-recorder.ts`（`packages/coding-agent/src/tools/file-recorder.ts:5`，按相对路径去重的记录器）与 browser attach 的「幂等重连是常见路径」（`browser/attach.ts:98`）最接近；Reasonix 的 idempotent 仅出现在资源清理（`internal/acp/service.go:436/1740`）。**没有任何参考项目做「同域同参工具调用去重」**——这是 Crish 最前沿但也最需要自制约束的想法。

**坑**：
1. **「去重」可能吞掉合法调用**：`append`、`write` 等非幂等工具绝不能进守卫；即使用 `mkdir -p` 这类语义幂等工具，第二次调用可能带着用户新意图（比如先删后建同路径）。**守卫只适用于工具清单里显式声明 `idempotent: true` 的工具**，且重复命中时返回「缓存结果 + 已去重标记」而不是静默不返回。
2. **去重窗口**：run 级去重会误伤长任务里的合法重复调用（如两次 `run_tests`）；建议窗口 = 短时窗（秒级）或「结果已返回且未发生任何写操作之间」。会话级去重只适用于纯读工具。
3. **与并行隔离的冲突（P0.1）**：两个子 agent 并发调同域同参工具，幂等守卫变成隐式锁，与「子 agent 无共享可变状态」（`04:27`）的隔离承诺冲突。守卫的 key 域必须限定为「同 run 内」，跨 run 去重只能用于纯读工具。
4. **key 的规范化**：同参去重要求参数规范化的确定性（路径大小写、相对绝对路径归一），否则同一调用产生两个 key——规范化的成本常被低估。

**建议**：落地为「读工具短时窗去重」起步（比如 `read_file` 同路径 5 秒内返回缓存 + 标记），写工具先不做；工具 schema 增加 `idempotent` 声明字段，守卫只认声明。这条建议列入 C 系列扩展的开放问题，不抢 C3/C6 的排期。

### 1e. 事件背压丢帧分级（9/10，与 Crish 既有事件分类天然对齐，实现成本低）

**参考等价物**：要素级。pi 在 `eval.ts:361` 明确「无 payload 的事件 bump-and-drop」（队列挤压时丢弃无载荷事件，只保留最新语义）；Reasonix 在消息层丢部分文本/推理（`internal/agent/interrupted_recovery.go:94-99`，`DroppedPartialText/DroppedPartialReasoning` 留痕）。两者都没有显式的三档分级，但「丢帧必须留痕、terminal 语义不丢」的直觉一致。

**Crish 现状对齐**：`conex-db/src/events.rs:43-49` 已存在持久化分类——`message-delta` / `thought-delta` 为**非持久化事件**（ADR 第 2.2 节确认是设计意图，`ADR/持久化方案.md:37`）。即 Crish 已有「delta 类可丢」的既有语义，背压分级是把「可丢」从「不落库」扩展到「背压时连在途帧也可丢」，改动面小、语义自洽。

**坑**：
1. **分类必须静态可判定**：Delta（message-delta/thought-delta 流式帧）→ Soft（steering 通知、进度事件）→ Critical（run-terminal、审批请求、subagent 事件）。分类写进事件注册表（conex-types 的 event registry），不许运行时拍脑袋分类——`crates/conex-types/tests/registry_drift.rs` 的漂移护栏正好扩展用于此。
2. **丢帧后的 UI 自愈**：delta 被丢后前端流式显示会缺段，UI 必须有点位刷新机制（丢帧后前端主动 re-sync 最新状态），否则「丢帧」表现为「显示 bug」。
3. **terminal 必达的实现**：Critical 类不能靠「丢了就完了」，背压到顶时应转为**生产侧阻塞**（暂缓产生新事件）而不是丢弃 Critical；丢帧计数必须落 metrics（保留透明性，用户可见「已丢 N 帧」）。
4. **与审批事件的关系**：审批请求属于 Critical，被丢等于用户永远不批——C3 的 60s 超时拒绝语义（`04:114`）可兜底，但背压场景下应优先保审批通道。

**建议**：作为 C8 事件契约（`04:264`，信封对齐 `EventRouter.ts:475/488/500`）的配套设计同步落地：三档分类入事件注册表、每档背压上限可配、丢帧计数落库。

### 1f. 审批等待可 abort 取消（8/10，竞速语义需要显式建模）

**参考等价物**：弱。pi 的执行器有完整 abort 基建：`withAbortTimeout` + `AbortSignal` + `ToolAbortError`（`packages/coding-agent/src/task/executor.ts:96-121`），abort 后工具以 `ToolAbortError` 终止并保留 `doneAborted` 状态（`executor.ts:282-290`）——但这是「执行中取消」，不是「审批等待中取消」。Reasonix 未在 permission/guardian 包中发现审批取消路径（审批超时拒绝是共性兜底）。**审批等待的 abort 是 Crish 独有需求**（来源：主 agent 经 L3 强停打断一切，`04:28` P0.2「每个审批都挂到 ControlBus 可达」）。

**坑**：
1. **悬空审批（竞速核心坑）**：审批请求已发到 UI，用户正在看，agent 先 abort 了 → 用户后点「同意」会作用于已取消的请求。必须有 approval-id 关联 + 撤销语义：abort 时把请求标记为 cancelled（UI 同步置灰），用户后来的裁决按无效裁决处理并落 events。
2. **abort ≠ deny 的语义区分**：abort = 请求方取消，deny = 用户拒绝。落库的审批结果必须三态（approved / denied / cancelled-by-requester），否则审计链无法回答「这个操作到底为什么没执行」。
3. **与崩溃恢复的关系**：`awaiting-approval` 态 run 在崩溃恢复时置 failed（`ADR/持久化方案.md:148`）；abort 应定义为一种**用户可见的终态**（区别于 failed），恢复路径与审计语义需扩展。

**建议**：C3 审批请求带上 approval-id；abort 经 ControlBus L3 路径写入该 id 的 cancelled 状态；前端按 id 撤销 UI 卡片。验收断言补「abort 后用户再批准，断言请求状态为 cancelled、操作不执行、events 落库」。

### 1g. 半溯源持久化（9/10，已决议，保持「不迁移」并把触发条件登记为监控项）

**参考等价物**：opencode V2 `commitDurableEvent`（先事件后状态、重启重放重建状态）与 pi 同事务投影（投影在写事件的事务内更新）都是**全事件溯源**；Crish 的「快照 + 审计事件 + 游标调和」是差异化选择，且 ADR 已给出完整论证：引擎不承载用户可见真相、无多消费者/时间旅行需求、恢复语义已闭环（T12.1–T12.8 崩溃一致性测试）、「崩溃后不续跑 provider」三家共识（`ADR/持久化方案.md:58-71`）。

**坑**（不是实现坑，是治理坑）：
1. **触发条件必须持续监控**：ADR §7 的四个触发条件（消息正文上移引擎、跨端同步/时间旅行、provider 续跑需求、无法容忍的不一致）要进产品 backlog 定期复核，否则「半溯源」会变成「默认方案」而非「有意决策」。
2. **快照规模成本**：快照双文件 + checksum（`restore.rs:42/272-292/425-449`）在会话规模增大时成本线性上升——需要快照频率策略（不是每次事件都落快照，增量流已承担差异）。
3. **游标调和依赖序列单调**：seed 预热 + TOCTOU 守卫（`schema.rs:24`）已闭环，但任何未来「跨进程取号」需求都会破坏单调性——这是触发重评估的信号之一。

**建议**：维持决议；把 ADR §7 触发条件写进 improvement/ 系列的产品监控清单；新增能力一律先回答「是否触发切换条件」再落库设计（与 04 的「三问模板」同构）。

**依赖逻辑**：
- **主线四是其余三条的地基**：C1-C10 与删除接管都要写代码进门禁，门禁本身不闭环，任何主线都会在合入时扯皮（jcode 在 CI 注释里明确写了这个教训：`uninlined_format_args` 的 allow 注释——「没有 merge-queue 时，main 上的 lint 违规会打破所有人的构建」，`reference/grok-build/Cargo.toml:396-406`）。
- **主线一是主线二的前置风险面**：多 Agent 上线 = 更多并发写操作 = 更高误删/误回退概率。04 §4 实现顺序第 2 步「权限引擎」正是主线一的 C3/C4，排在调度器（第 5 步）之前（`04:376`）。删除接管接口作为主线一的旗舰能力，应在 run_subagent 工具上线前或同批落地。
- **主线二为主线三提供挂接面**：插件/hook 依赖稳定的事件契约（C8 事件信封）与工具面；没有主线二的「事件发射」，hook 无处挂（03 篇 §3.2 的 hook 桥前提是 Rust 侧事件完备）。
- **主线三最后启动**：03 篇已定「步 1 插件运行时 → 步 2 hook 桥 → 步 3 官方插件试点」，且明确第一版不做 UI 回调（`03 篇`：避免第一代插件运行时承载 UI/文件系统能力）——在主线二稳定前启动插件线会两头不靠。

### 3.2 各主线详解

#### 主线一：安全监控（删除接管 + C3/C4 + 高危命令监控）

- **核心价值**：防数据丢失（2026-08-02 事故驱动的产品化，`05:260-269`）；把提示词纪律（05 §0/§2/§12/§13）变成引擎强制（删除只能走接口、回退必须审批、连续回退需同意）。
- **关键产出**：删除接管工具（快照 + 回收站 + 100% 拦截）；C3 大面积回退审批（ApprovalGate 扩展 + CommandPolicy 兜底）；C4 连续回退计数（session_meta 持久化）。
- **参考先例**：Reasonix 权限引擎（deny 优先 + 复合命令逐段判定，`permission.go:192-300`）与 checkpoint 反向快照（`checkpoint.go:28-33`）；grok disallowed-methods 禁令（安全约定下沉为 lint，`clippy.toml:21-26`）；pi AbortSignal 基建（`executor.ts:96-121`，供审批 abort 参考）。
- **依赖**：无前置依赖（可在治理收尾的 G2 禁令同步推进）；与主线二共享 `tool_events.rs`/`tool_exec.rs` 独占写面（04 §4 文件域互斥：C3 独占，C4 只读挂载）。

#### 主线二：多 Agent 调度（C1-C10）

- **核心价值**：把「可运行的多 Agent 调度」变成现实（04 §1.1：现状运行资产为零）；这是 Crish 相对参考项目最强的产品叙事（主 agent 唯一编排者 + L0-L3 控制总线 + 会话树 fork 的组合是独有设计，01/02 篇已确认）。
- **关键产出**（按 04 §4 顺序）：Tool Context 注入通道 → 权限引擎 → run_subagent 工具 → 事件契约（信封对齐 EventRouter）→ 依赖图调度器 + 三模式等待 → 恢复阶梯 → AI 压缩摘要 + 文档配额。
- **参考先例**：grok 工作流 journal（可重放确定性编排 + 预算跨重启不重复扣，`engine.rs:505-523`）；jcode TaskGraph（分解→并行→合成 + gate 逐条点名审计，`jcode-swarm-core/src/lib.rs:449-499`）；Reasonix scheduler + 写路径声明；pi 子代理提示词协议与 worktree 隔离（P0.1 升级参照）。
- **依赖**：主线一（权限引擎是第 2 步）；主线四（门禁保证合入质量）。

#### 主线三：生态（插件/hook）

- **核心价值**：可扩展性——第三方能力不烧主线二的内核复杂度；hook 事件面让用户/团队可观测与自动化。
- **关键产出**：插件运行时（TS 面收口 + Rust 引擎接线）→ hook 桥 → 官方插件试点（03 篇拟议路线）。
- **参考先例**：opencode 插件运行时（定义改写 + 执行包裹 + trigger 顺序执行输出原地改写）；kimi manifest 三段加载管线 + 「不支持的运行时字段显式报不支持」（前向兼容）；grok hooks runner（spawn 子进程 + 超时）。
- **依赖**：主线二的事件契约（hook 挂接点）；主线四的稳定性。

#### 主线四：治理收尾（clippy / 环 / knip 收紧）

- **核心价值**：还清质量债 + 把门禁从「文档基线」升级为「机器 ratchet」；直接决定其他三条主线合入时的摩擦成本。
- **关键产出**：190 条 clippy 存量清零（agent-workbench 189 条 dead_code 为主，`clippy-workspace-T13.md:85-90`）；G1-G7 缺口落地（ratchet 脚本、disallowed-methods、panic 基线、machete、行数门禁泛化、CI 口径统一）；knip warn→error 收紧（`knip.config.ts:74-79`）。
- **参考先例**：jcode 8 道预算 ratchet（`ci.yml:48-83`）；grok 集中式 workspace.lints + allow-with-reason 模式（`Cargo.toml:387-411`）。
- **依赖**：无前置依赖，可与主线一并行启动（两者都不碰调度核心）。
