### 1.4 并行修复要点

#### T12（Agent-A）：持久化方案 ADR 与崩溃一致性测试

**决策问题**：崩溃后持久化与恢复，维持"快照 + 审计事件 + 游标调和"（现状），还是迁移"事件溯源"？

**决策树**（按顺序逐问下钻，任一分支命中即终止）：

```
问题 1：引擎持久化是否承载"用户可见真相"（消息正文）？
├─ 否（现状：消息正文与本地会话列表以 crish-desktop 本地状态/持久化为用户可见真相，
│       引擎侧只持久化会话元数据与运行事件投影，用于补标题/id/审批/工具卡片）
│   └─ 维持快照方案。理由：快照 + 审计事件链 + 游标调和已覆盖引擎侧全部恢复语义，
│        消息重建不属引擎职责，事件溯源没有可换取的新能力。
└─ 是（未来需求：消息正文上移到引擎、跨端同步、时间旅行重放）
    └─ 迁移事件溯源。理由：需要 message 事件全量落库 + 投影重建，快照方案无法满足。

问题 2（仅当问题 1 走"否"时继续）：是否要求崩溃后恢复 provider 续跑？
├─ 否（三家共识：崩溃后不续跑 provider 工作——打断路径只需写审计事件 + run 终态落库，
│       不需要 provider 工作流 checkpoint 与续跑语义）
│   └─ 维持快照方案。打断路径（restore.rs:558-574）与终态唯一（run.rs terminal_sent）
│        正是该共识的代码化，方案与共识自洽。
└─ 是（需求变化，与三家共识冲突）
    └─ 迁移事件溯源。需记录 provider 工作流 checkpoint 事件；该分支触发前必须重新
         论证共识本身是否被推翻。

问题 3（仅当问题 1、2 均走"否"时继续）：现状缺口是"缺测试"还是"架构缺陷"？
├─ 缺口仅为崩溃一致性测试缺失（现状：恢复路径有断言锚点但未覆盖杀进程全流程）
│   └─ 维持快照方案 + 补崩溃一致性测试（本任务产出）。
└─ 存在无法容忍的不一致（快照与事件对不上、恢复丢数据、cursor 口径漂移）
    └─ 迁移事件溯源（先修复方案再谈测试）。
```

**参考基准**（写入 ADR 的"参考与依据"节）：

- pi：同事务投影——投影在写事件的事务内更新，投影与事件一致性由同一事务保证；若未来切事件溯源，投影层采用该模式；
- opencode V2：事件溯源，`commitDurableEvent` 事件提交即持久化，先事件后状态；事件溯源侧的提交路径参考实现；
- 三家共识："崩溃后不续跑 provider 工作"——决策前提输入，写 ADR 时作为"决策约束"登记，并注明其代码落点（打断路径审计事件、run 终态落库、不假装可回放）。

**决议**（预期结论，写 ADR 时按实际论证定稿）：维持快照方案；`message-delta` 不落库与"恢复不重建消息"确认为设计意图而非缺口；迁移事件溯源的条件登记为 ADR 中的"未来切换条件"（问题 1/2/3 走"是"分支的触发条件）。

**ADR 产出**：`docs/architecture/persistence-snapshot-vs-event-sourcing-adr.md`（沿用现有 ADR 命名规范），结构含：决策问题、现状证据（含上述代码引用）、决策树、决议、未来切换条件、参考与依据、影响面与回退路径。

**崩溃一致性测试产出**（`crates/orchestrator/tests/` 或既有测试文件的扩展，测试文件归属 Agent-A）：

| 测试项 | 断言内容 | 复用锚点 |
| --- | --- | --- |
| T12.1 杀进程恢复 | 任意 run 状态（queued/init/running/approval/cancelling）下进程被杀，重启恢复后：cancelling→cancelled、其余→failed；审计事件逐条落库 | restore.rs:820-827 状态映射 |
| T12.2 审计序列连续性 | 被打断 run 的审计事件序列连续无空洞 | restore.rs:843-849 `audit_seqs == vec![1..=N]` |
| T12.3 cursor 口径 | 打断路径 cursor = 审计事件前会话最大已落库序列（sequence-1 语义） | restore.rs:558-560、:837-842 |
| T12.4 半写快照回退 | 快照写一半崩溃，恢复读到旧快照 + 增量重放，不丢已提交事件 | SNAPSHOT_TYPE 双快照机制（restore.rs:42） |
| T12.5 取号单调 | 恢复后 `session_sequence` 取号不重复、不回落 | conex-db lib.rs:1818-1832；upgrade_e2e.rs:216-284、migrations.rs:439-506 |
| T12.6 终态唯一 | 恢复后 run-terminal 不重复发出（terminal_sent 跨恢复成立） | run.rs:272-273 |
| T12.7 写失败不假装可回放 | 事件存储写失败时 end_reason 落 `event-store-write-failed`，不产生"已持久化"假象 | run.rs:278-279 |

### 2.2 任务分解

| --- | --- | --- |
| T19 | 全量回归门禁：按下方命令序列顺序执行；吞并 R0–R5 全部任务验收；修复门禁暴露的残留（仅限门禁阻塞项）；输出终验报告与完成态机检清单核验结果 | 全仓（只读为主；小修仅限门禁阻塞的直接原因文件） |

- 第 5 项在排除历史文档后必须零命中：任何产品代码/脚本/配置引用已删除包即为残留，登记并修复；
- 第 6 项 knip 未使用项按"未使用项清单"逐条核验：属于残留死代码的修复，属于误报的登记豁免理由；
- 命令 1–4 任一项失败：先定位失败原因——若为残留引用/死代码等门禁阻塞项，执行小修；若指向架构性缺陷，**不得在本轮硬改**，按第 4 节闭环规则回对应轮次重开；
- 小修权限边界：只修"命令失败的直接原因文件"，修复后重跑该命令直至通过；不顺手清理、不重构、不扩面。

### 2.5 结果汇总

- 主调度 Agent 生成 R6 终验报告：
  - 门禁状态：T19 六项命令逐项 通过/未通过（失败项附命令输出定位）；
  - 吞并验收：R0–R5 各任务验收项的复核结果表；
  - 残留清单：终验发现的问题逐条登记（编号、文件域、现象、归属轮次映射、重开状态）；
  - 完成态机检：第 3 节"完成态可机检定义清单"8 条逐条核验结果；
- 终验结论不写"全部通过/全部失败"二元结论，写"门禁状态 + 残留清单 + 重开轮次映射"；
- 残留问题清单作为后续轮次的前置约束输入（若存在后续轮次）。

## 4. 附：终验残留问题的闭环规则（提醒）

- 终验时若发现残留问题，问题应回到对应轮次重开，形成闭环：登记问题 → 映射到产生该问题的轮次 → 重开该轮次问题清单（按该轮次的纪律与文件域重新分配）→ 修复后复验 → 回到 R6 重跑门禁；
- 严禁在终验轮内硬改架构：门禁小修只限"命令失败的直接原因文件"，架构性残留一律回轮重开；
- 闭环的判定标准：残留问题在重开轮次的报告中标记为"已完成"，且其验收项在重跑 T19 时通过；
- 终验报告中的残留清单逐条保留重开映射，不允许以"影响小"为由丢弃登记。
