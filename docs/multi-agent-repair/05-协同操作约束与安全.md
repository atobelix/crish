# 协同操作约束与安全手册

> 适用范围：参与 Crish 多 Agent 协同修复方案的所有 Agent（主 Agent 与各子 Agent）。
> 优先级：本手册为协同执行层面的强制约束，与方案文档（00–04 全部方案文档）冲突时，以本手册的安全红线为准。
> 本手册侧重"怎么操作才安全"，具体分工与流程见对应方案文档。

---

## 0. 删除铁律（最高优先级，任何人不得触碰）

> 本节与第 2 节同属最高优先级约束。**任何 Agent 违反本节规则，视为重大违规，立即停止该 Agent 当前工作并上报。**

1. **禁止物理删除**：任何文件/目录的删除，必须先移入 Windows 回收站。严禁 `git rm`、`Remove-Item -Force`、`del`、`rm -rf`、`os.remove` 等物理删除手段（绕过回收站导致文件不可恢复）。
2. **推荐方式**：
   - Python send2trash 库（`pip install send2trash` 后执行 `python -c "import send2trash; send2trash.send2trash(r'<路径>')"`）；
   - 或 PowerShell Microsoft.VisualBasic.FileIO 的 `FileSystem.DeleteFile` / `DeleteDirectory`（带 `SendToRecycleBin` 选项）。
3. **git 删除语义**：回收站删除后 `git status` 显示工作区 deleted；若文件是 git 跟踪且删除有意，用 `git add -u` 暂存删除记录（仅记录意图，不物理删除）；误删可从回收站还原，或用 `git checkout HEAD -- <file>` 恢复单个文件（单文件恢复允许；大面积回退仍须用户同意，见第 2 节）。
4. **批量删除**：逐个送回收站，报告中登记回收站条目清单（路径 + 是否 git 跟踪）。
5. **git mv 例外**：`git mv` 是移动操作非删除（保留提交历史），允许使用。

## 1. Checkpoint 优先恢复规则

**核心原则：能恢复就不重做。**

1. **优先使用 Checkpoint 恢复**
   - 当前文件或当前会话存在 checkpoint 时，任何 Agent 必须先尝试从 checkpoint 恢复，而不是从头开始重建。
   - 适用场景：任务中断、会话被压缩、工具失败、Agent 状态丢失等。

2. **Checkpoint 查找位置（按优先级）**
   - `.agent-runtime/` 目录：Agent 运行时快照，本轮工作的中间产物、决策记录、输出物。
   - Orchestrator 快照：编排器（主 Agent 侧）保存的任务状态与轮次快照。
   - Git：分支上的提交记录、stash、以及 `git reflog` 中可找回的历史状态。

3. **恢复失败的降级路径**
   - 一级降级：换一个 checkpoint 来源（如 `.agent-runtime/` 失效则尝试 orchestrator 快照，再尝试 git）。
   - 二级降级：基于任务记录重建上下文（任务描述、上一轮输出、验证结果），重新执行任务。
   - 三级降级：报告主 Agent，由主 Agent 决定重新分配任务或调整方案。**禁止**在恢复失败时擅自扩大操作范围（如直接回退代码）。

4. **恢复后必做动作**
   - 校验恢复出的状态与 checkpoint 记录一致（对比文件清单、摘要值）。
   - 恢复完成后向主 Agent 汇报"基于哪个 checkpoint 恢复、恢复了什么、是否完整"。

## 2. Git 操作安全规则（本手册最高优先级约束）

> 本节为本手册最高优先级的约束。**任何 Agent 违反本节规则，视为重大违规。**

### 2.1 子 Agent 执行 git 回退必须谨慎

- 若 git 暂存区/目标状态是**很久之前**的（时间跨度大、期间已有大量他人变更），**优先尝试修复单个文件**，不要整体回退。
- 单文件修复示例：
  ```bash
  # 查看影响面
  git status
  git diff -- <file>
  # 单文件回到目标版本
  git checkout -- <file>     # 工作区文件恢复
  git restore --source=<ref> -- <file>   # 从指定引用恢复单个文件
  # 恢复后在该文件上重做变更
  ```
- 单文件修复仍失败时，才可以考虑更小范围的多文件回退，并逐级报备（见 2.4）。

### 2.2 大面积回退必须获得用户明确同意

- **大面积 git 回退**（多文件、跨目录、整分支回退）**必须获得用户明确同意，否则不允许执行**。
- "用户明确同意"指：用户在对话中直接确认同意该操作。Agent 自己判断"应该没问题"、或主 Agent 单方面批准，**都不算**。

### 2.3 连续 git 回退属高危场景

- 同一会话内**第二次** git 回退，**同样需要用户再次明确同意**（即使第一次已同意过）。
- 连续回退意味着前一次回退可能不完整或引发新问题，默认视为高危场景，必须放慢、报备、确认。

### 2.4 Git 危险命令清单

以下命令**默认禁止直接执行**，必须按 2.1–2.3 流程评估并取得授权：

| 命令 | 危险点 |
| --- | --- |
| `git reset --hard` | 丢弃工作区与暂存区全部改动，不可逆 |
| `git checkout <旧ref>` | 大面积切换到旧状态，可能覆盖他人工作 |
| `git clean -f` | 删除未跟踪文件，不可恢复 |
| `git stash drop` | 删除 stash 记录，可能丢失未完成工作 |
| `git revert --no-commit` | 批量撤销且不提交，易遗留未审查变更 |
| 其他任何批量丢弃/覆盖类操作 | 同上，先问再动 |

### 2.5 安全操作路径（标准流程）

1. **先确认影响面**：执行 `git status`、`git diff`、`git log`，搞清楚要动什么、会波及谁。
2. **小面积单文件修复**：优先 `git checkout -- <file>` / `git restore` 单个文件后重做变更。
3. **需大面积回退时报备主 Agent**：由主 Agent 向用户申请明确同意；用户同意后，由指定 Agent 一次性执行并当场验证。
4. **执行后验证**：回退后必须运行相关验收命令，确认修复生效且未破坏相邻功能。

## 3. 文件所有权纪律

1. **同一文件同一轮只能一个 Agent 编辑**
   - 任何文件在某一轮任务中只能分配给一个 Agent 写/改；其余 Agent 只读。
   - 需要改他人文件时，向主 Agent 申请所有权转移（上一轮结束时交接）。

2. **包级文件每轮单一所有权**
   - `package.json`、根 `Cargo.toml` 等包级文件，每轮只能有一个 Agent 持有编辑权，避免依赖冲突与锁文件乱掉。
   - 包级文件的变更必须在轮末输出中声明（改了什么、为什么）。

3. **文件域互斥表**
   - 主 Agent 在每轮开始时维护一张"文件 → 所属 Agent"互斥表，随轮末汇总物同步发布。
   - 子 Agent 开工前先查互斥表，发现自己被分配的文件与表冲突，立即停下报备主 Agent。
   - 示例格式：

| 文件/目录 | 本轮所有权 | 状态 |
| --- | --- | --- |
| `src/xxx.py` | 子Agent-A | 读写 |
| `src/yyy.py` | 子Agent-B | 读写 |
| `package.json` | 子Agent-A | 读写（本轮唯一持有） |
| `docs/` | 无 | 只读（除明确分配的写作任务） |

## 4. 并行与汇总规则

### 4.1 并行执行先决条件

同一轮内多个子 Agent 并行，必须同时满足：

- **文件域互斥**：各自的文件域不重叠（见第 3 节互斥表）。
- **依赖已满足**：任务 A 需要任务 B 的输出时，B 必须已完成或同轮先交付，A 不得在缺失依赖时空转或猜测。
- 不满足任一条时，任务串行化或交由主 Agent 调整轮次。

### 4.2 轮末汇总物格式

每个子 Agent 在轮末必须输出统一格式的汇总物（markdown 小节即可）：

```
## 轮末汇总：<Agent 名> / <任务名>
- 目标：<本轮目标原文>
- 完成：<已完成的条目，逐条列出>
- 未完成：<未完成的条目与原因>
- 新发现：<新问题、新风险、对方案的修正建议>
- 遗留：<留给下一轮/他人的事项、文件交接>
- 验证结果：<验收命令与输出摘要>
```

### 4.3 每轮输出作为下一轮输入

- 下一轮以"上一轮各 Agent 的轮末汇总物"为输入，格式固定为：**完成 / 未完成 / 新发现 / 遗留 / 验证结果** 五个部分。
- 下一轮开始前，主 Agent 先消费上一轮汇总：已完成的进归档，未完成的重新分配，新发现的纳入风险清单，遗留的明确交接。
- 没有上一轮汇总物时，视作无输入，任务从 checkpoint 或任务描述重建（见第 1 节）。

## 5. 故障恢复阶梯（针对子 Agent 自身）

子 Agent 遇到故障按以下阶梯逐级恢复，**不跳级、不擅自越权**：

1. **第一级：自动重试（退避）**
   - 网络波动、工具瞬时失败导致工作停止：先自动重试，复用 `crates/agent-provider/src/retry.rs` 指数退避（750ms 起、8s 封顶、总预算 60s），只处理瞬态类错误（rate-limit / 5xx / 网络 / 超时）。
   - 重试恢复后，继续原任务并记录一次故障日志；重试不改变任务语义、不计入任务失败（对齐 04 能力 C7 阶梯 1）。

2. **第二级：主 Agent 注入提示词激活**
   - 自动重试失败：上报主 Agent，主 Agent 注入提示词（携带任务目标、上下文、当前进度）激活子 Agent 继续任务。
   - 对齐 04 能力 C7 阶梯 2（L1 steer 软注入；通知必须落库，重启后仍可见）。

3. **第三级：重新分配或 fork 工作流记录**
   - 激活仍失败：主 Agent 重新分配任务，或 fork 该子 Agent 的工作流记录后重试。
   - **fork 工作流记录 = 基于已有的任务记录/输出物重建上下文，不做任何破坏性操作**（不删文件、不改他人代码、不做 git 回退）。
   - 对齐 04 能力 C7 阶梯 3（SessionTree.fork + subagent_path_json 留痕，原任务置失败并留事件）。

4. **第四级：上报用户**
   - 以上全部失败：子 Agent 如实汇报"卡在哪一步、试过什么、建议怎么办"，由用户决策。
   - 对齐 04 能力 C7 阶梯 4（上报前保留全部重试与重分配留痕）。

## 6. 主 Agent 编排约定

1. **可编排 Agent 流**
   - 允许部分 Agent 完成后才启动另一些（如：先评审，后整理；先构建，后验证）。明确依赖关系即可。

2. **分配子 Agent 后的三种策略**
   - 等待全部完成：适合强依赖的多任务轮次。
   - 定时器：设定期限，到期未完成则介入检查。
   - 并行做自己的事：主 Agent 在等待期间处理编排、汇总、上下文管理等事务。

3. **子 Agent 执行期间可注入提示词**
   - 主 Agent 可在子 Agent 运行中注入提示词（补充信息、纠正方向、紧急叫停），子 Agent 必须响应注入并继续。

4. **尽量等所有子 Agent 结束后再规划下一步**
   - 未收齐本轮全部子 Agent 结果前，不轻易开启下一轮大规模规划；个别子 Agent 长期无响应时按第 5 节阶梯处理。

## 7. 探索类 Agent 文档配额

1. 探索类 Agent（调研、分析、勘察类）**最多写一份文档**，且**必须由主 Agent 分配写作任务**才允许写。
2. 未获分配的探索类 Agent **不得主动写第二份文档**（包括补充文档、分析报告等）。
3. 探索结果默认以"汇报/汇总物"形式返回（见第 4 节），只有主 Agent 明确指派时才落盘为文档。
4. 文档落盘后受文件所有权纪律约束（第 3 节）。

---

## 8. 验证纪律

1. **每个任务完成必须跑其验收命令**
   - 任务交付前，执行该任务对应的验收命令（测试、构建、lint、类型检查等），不允许跳过。

2. **不能只报告"完成了"**
   - 必须贴出验证输出摘要：命令名、关键输出、通过/失败结论。摘要不完整视为未验证。

3. **失败时回退到该任务的局部修复**
   - 验证失败时，先做该任务的局部修复（改本任务的文件、重跑验收），**不要越过验收**直接宣布完成，也不要因此扩大化地整体回退代码（见第 2 节）。
   - 局部修复仍无法通过时，按第 5 节阶梯上报。

## 9. 上下文压缩说明

1. **主 Agent 的对话压缩使用 AI 压缩文档格式**，模板固定包含以下字段：
   - **目标**：当前整体目标与阶段
   - **已完成**：已完成的任务与验证结果
   - **待办**：未完成任务与责任人
   - **决策**：已作出的关键决策与理由
   - **文件清单**：当前涉及的文件、所有权与状态

2. **压缩模板必须传递到下一次对话**：新对话开始时，以压缩文档作为上下文起点，按模板恢复"目标/已完成/待办/决策/文件清单"。

3. **用户安装的 MCP / skill / agent 文件在压缩后必须重新注入**，这部分**独立于压缩预算**，不占用压缩内容的篇幅上限。
   - 即：即使压缩文档本身被限长，MCP/skill/agent 的注入也不可省略。

4. 压缩后若发现 checkpoint 可用（第 1 节），优先用 checkpoint 校验压缩文档内容。

## 10. 禁例清单（红线）

以下行为**一律禁止**，违反即停止该 Agent 当前工作并上报：

1. **不执行用户明确拒绝的 git 操作**：用户说"不要"就是不要，任何形式的规避、变通、拆分成小步执行都属违规。
2. **不删他人任务文件**：任何文件删除（含 `git clean`、文件系统删除）超出自己本轮文件域的一律禁止。
3. **不修改包级文件，除非是本任务指定所有权**：`package.json`、根 `Cargo.toml` 等只有被本轮任务明确指定所有权的 Agent 才能修改。
4. **不静默吞掉验证失败**：验证失败必须如实汇报并进入局部修复流程（第 8 节），禁止以"应该没问题""之前测过"等理由略过。
5. 附则：以上红线与用户明确指令冲突时，以用户指令为准；与方案文档冲突时，以本手册为准。

## 11. 状态混乱处理流程

当发现状态与预期不符时（并行改动、删除结果与报告不一致、门禁异常），按以下流程处理：

1. **先停止操作**：状态与预期不符时立即停止当前操作，不继续执行后续步骤，不擅自"补一下"。
2. **核对证据**：依次核对 `git status`、`git diff`、回收站条目清单、文件存在性（`Test-Path` / `ls`），逐项比对。
3. **无法解释时上报**：核对后仍无法解释的，立即在当前汇报点向主 Agent 报告，附证据（命令输出、文件清单、时间线）。
4. **等待系统性决断**：由主 Agent 重新分配分析 Agent 调查，形成系统性决断后再继续操作。
5. **禁止擅自扩大操作**：状态混乱期间禁止连续 git 回退、批量删除等扩大化操作（见第 0 节、第 2 节）。
