# ADR：持久化方案（快照 + 审计事件 + 游标调和 vs 事件溯源）

- **状态**：已决议（Accepted）
- **日期**：2026-08-02
- **责任方**：`crates/orchestrator`（restore.rs / persist.rs / run.rs / events.rs）
- **关联**：`04-Agent功能需求设计.md` C1（checkpoint 优先恢复）；`05-协同操作约束与安全.md` §1（checkpoint 优先恢复规则）
- **验证锚点**：`crates/orchestrator/tests/crash_consistency.rs`（T12.1–T12.8 崩溃一致性测试）

---

## 1. 决策问题

崩溃后引擎侧持久化与恢复，维持「快照 + 审计事件 + 游标调和」（现状），还是迁移「事件溯源」？

问题拆解为三个子问题：

1. 引擎持久化是否承载「用户可见真相」（消息正文）？
2. 是否要求崩溃后恢复 provider 续跑（provider 工作流 checkpoint 与续跑语义）？
3. 现状缺口是「缺测试」还是「架构缺陷」？

---

## 2. 现状证据

### 2.1 现状方案：快照 + 审计事件 + 游标调和

| 构件 | 代码落点 | 说明 |
| --- | --- | --- |
| 全量状态快照 | `crates/orchestrator/src/restore.rs:42`（`SNAPSHOT_TYPE`）、`restore.rs:272-292`（`StateSnapshot`，checksum 校验，双文件模型） | 快照文件 = 主文件 + `.prev` 备份；保存走 tmp + rename 原子写（`restore.rs:425-449`）；损坏时回退上一完好备份（`restore.rs:408-423`） |
| 审计事件 | `restore.rs:558-574` 打断路径：先取序列号，cursor 取 `sequence-1` 后 `update_run_status` 落库，再 `append_event` 写 `run-interrupted`（previousStatus 审计字段） | 终态变化可追溯；测试锚点 `restore.rs:831-849`（`audit_seqs == vec![1..=N]`） |
| 游标调和 | `run.rs:249-264` `RunHandle.cursor` = 事件序列游标（已分配的最大 sequence），终态游标落库（T08.4） | 恢复后 seed 预热按库内 `max(sequence)+1` 对齐，取号单调不回退 |
| 事件基座 | `crates/conex-db/src/events.rs:72-99`（`reserve_sequence` 会话级原子取号）、`schema.rs:171`（`session_sequence` 表）、`schema.rs:24`（`UNIQUE(session_id, sequence)` TOCTOU 守卫） | 已是溯源形状：序列分配、run 终态唯一（`run-terminal` 唯一终态事件）、并发取号有测试锚定（`crates/conex-db/tests/upgrade_e2e.rs:216-284`、`tests/migrations.rs:439-506`） |
| 恢复流程 | `restore.rs:515-638`（`RestoreManager::restore`） | 快照加载（损坏回退）→ runs 全量扫描 → in-flight 打断 → 增量流重放 → pending FIFO 恢复 |

### 2.2 已知缺口（本轮确认为设计意图，非架构缺陷）

- **message-delta 不落库**：`events.rs:43-49` 持久化分类——message-delta / thought-delta 为非持久化事件，不阻塞 drive loop（05 §2.8：orchestrator.test.ts:93-189 语义）。
- **恢复只重放 `session-leaf-moved`**：`restore.rs:594-617` 增量流只重放会话树叶子移动（`SESSION_LEAF_MOVED_EVENT`），**不重建消息**。

消息正文与本地会话列表以 crish-desktop 本地状态/持久化为用户可见真相；引擎侧只持久化会话元数据与运行事件投影（补标题 / id / 审批 / 工具卡片）。「恢复不重建消息」因此是引擎职责边界的结果，不是缺陷。

## 3. 候选方案

### 方案 A：维持快照 + 审计事件 + 游标调和（现状）

- 全量快照（双文件 + checksum 回退）承担冷启动恢复的主体；增量事件流补快照后的差异；游标（sequence）跨恢复单调调和。
- 消息正文不落库，恢复不重建消息。

### 方案 B：迁移事件溯源

- 全部领域事件（含 message-start / message-end）落库，投影由事件重放重建；快照降级为投影优化手段（与快照方案共存或纯事件流）。
- 参考实现：opencode V2 的 `commitDurableEvent`（事件提交即持久化，先事件后状态，重启重放投影）；pi 的同事务投影（投影在写事件的事务内更新，投影与事件一致性由同一事务保证）。

## 4. 决策约束（三家共识）

**共识：「崩溃后不续跑 provider 工作」**——打断路径只需写审计事件 + run 终态落库，不需要 provider 工作流 checkpoint 与续跑语义。

代码落点（共识的代码化）：

| 共识要求 | 代码落点 |
| --- | --- |
| 打断只写审计事件 + 终态 | `restore.rs:558-574`（`run-interrupted` 审计事件，previousStatus 落库） |
| run 终态唯一、可追溯 | `run.rs:272-273`（`terminal_sent` 终态事件唯一性）、`events.rs:284-296`（`build_run_terminal` 唯一终态事件） |
| 不假装可回放 | `run.rs:278-279`（`EVENT_STORE_WRITE_FAILED_REASON`）、`events.rs:200-226`（终态事件尽力落库，失败不假装已持久化） |
| 不续跑 provider 工作 | 恢复路径（`restore.rs:515-638`）无 provider 工作流 checkpoint 读取、无续跑注入 |

该共识为决策前提输入；若未来推翻共识，本 ADR 第 9 节触发条件成立，需重开论证。

## 6. 决议

**推荐路线：维持方案 A（快照 + 审计事件 + 游标调和），不迁移事件溯源。**

- 决策树三个问题当前均走「否」分支：引擎不承载用户可见真相；三家共识否决 provider 续跑；现状缺口仅为测试缺失而非架构缺陷。
- 事件基座已按溯源形状构建（会话级原子取号、终态唯一、审计事件链），保留「未来可切事件溯源」的结构基础；本次不做实现改造。

### 6.1 理由

1. **职责边界**：消息正文属前端可见真相（crish-desktop 本地持久化），引擎侧持久化只服务「补标题 / id / 审批 / 工具卡片 / 会话树」。事件溯源需要 message 全量落库 + 投影重建，在本职责边界内没有可换取的新能力。
2. **无多消费者 / undo 需求**：单进程单 UI，无跨端同步、无时间旅行、无多消费者重放需求；事件溯源的主要收益（可重放、多投影、审计完整）在现有审计事件链下已部分获得，而成本（全量消息落库、投影维护、迁移改造）现无人买单。
3. **恢复语义已闭环**：崩溃后 in-flight run 打断为 interrupted（cancelling→cancelled、其余→failed），审计事件逐条落库且序列连续，pending 输入 FIFO 恢复，快照损坏回退 `.prev` 且不丢已提交事件——方案 A 的全部恢复语义已有代码与测试锚点（本 ADR 配套的 T12.1–T12.8 补全崩溃一致性覆盖）。
4. **决策约束自洽**：三家共识「崩溃后不续跑 provider 工作」在方案 A 中为最小代价实现；事件溯源不能减少该约束的成本（provider 工作流 checkpoint 无论何种方案都不做），反而引入事件全量落库的成本。

### 6.2 明确为非缺口的项（设计意图确认）

- `message-delta` 不落库（非持久化事件，05 §2.8 语义）；
- 恢复只重放 `session-leaf-moved`、不重建消息（引擎职责边界）。

## 8. 决策影响

### 8.1 对恢复语义

- **in-flight run 打断为 interrupted**：queued / initializing / running / awaiting-approval 崩溃恢复 → `failed`（`INTERRUPTED_REASON = "daemon-restarted"`）；cancelling → `cancelled`。逐 run 写 `run-interrupted` 审计事件（previousStatus 落库），cursor 回填 `sequence-1`（T08.4）。
- **blocked 与终态保真**：blocked 类（Failed + goal-blocked 等 reason）与其它终态记录原样保留，不打断、不追加审计事件。
- **pending 输入 FIFO 恢复**：创建时间升序（含 id 决胜），崩溃前未消费的输入不丢失。
- **快照回退**：主快照损坏/半写 → 回退 `.prev`；两者皆坏 → 全量重放；均不丢已提交事件（run 表 + events 表为权威数据源，快照只是加速）。
- **序列单调**：恢复后 `session_sequence` 经 seed 预热按 `max(sequence)+1` 对齐，取号不重复、不回落。
- **终态唯一跨恢复成立**：恢复流程不重发 `run-terminal`；终态记录在 store 中原样存在，恢复后再驱动返回 `TerminalImmutable`。
- **写失败不假装可回放**：事件存储写失败 → run 标记 `failed(event-store-write-failed)`，终态事件尽力发出但不产生「已持久化」假象。

### 8.2 对 R7 C1（checkpoint 优先恢复）的支持方式

C1（04 §2）的检查点**不是本 ADR 讨论的「provider 工作流续跑」**：C1 检查点 = 会话树叶子节点的结构化 payload（目标 / 已完成步骤 / 文件清单 / 下一步），恢复 = 读叶子 payload 注入「检查点摘要 + 目标剩余部分」后**续跑同一 run 实例**（`subagent_run_id` 不变），且引擎在安全点采集、只读不写。

方案 A 对 C1 的支持方式（无需迁移事件溯源）：

1. **检查点载体**：检查点内容写入会话树叶子节点 payload（`crates/orchestrator/src/session.rs` 会话树），叶子移动经 `session-leaf-moved` 事件持久化并随增量流重放（`restore.rs:594-617`）——快照 + 增量重放已保证叶子（含检查点 payload）在崩溃后可达。
2. **恢复接线**：`restore.rs` 恢复路径（C1 独占写面）在 in-flight run 打断为 interrupted 后，由 C1 逻辑读取叶子 payload 判定检查点有效性，注入恢复输入；run 记录仍在 run 表中保持同一 `run_id`（续跑不新建实例）。
3. **损坏降级**：C1 的「检查点解析失败 → 降级从最近完整消息重放」与方案 A 的「快照损坏回退 `.prev`」同构，均为「能恢复就不重做、坏了就降级不 panic」——两条降级链互相独立、互不干扰。
4. **不触发切换条件**：C1 的检查点是提示词协议层结构，不是「消息正文上移引擎」（消息正文仍以前端为真相），也不要求崩溃后自动续跑（C1 是主 agent 决定续跑，非恢复流程自动续跑）——因此 C1 落地不触发第 7 节任何切换条件。
