## 二、逐条证据

### 1. `sessionRustDbFallback.ts` —— **不可切：前提不成立**

文件自述（`:1-10`）：
> 「当 Tauri invoke 不可用（浏览器 / 旧壳 / 测试 missing 状态）时，所有 API 降级到 localStorage 同步读写。保证 dev / test 环境与渐进迁移期不阻塞。」

import 方（事实）：
```
sessionRustDbHydrate.ts:27   ← from './sessionRustDbFallback'
sessionRustDbLegacyCleanup.ts:18
sessionRustDbSql.ts:36
```

即：它**不是**一条与 Rust DB 并列的"旧产品轨道"，而是**同一套 API 在无 Tauri 宿主时的同步实现**（复用 `parseSessionMessage` / `safeParseJson` 等同一解析器，属同契约）。把它当"遗留孤岛"物理删除会直接砍掉浏览器/dev/test 运行能力。

**二选一的显式决策（不可回避）**：
- **(a) 产品只支持 Tauri 宿主**：删除回退，**同时**删除浏览器 dev 目标（`tauri.conf.json` 的 `devUrl` 与 `createSsrGlobals.ts` 等 SSR/web 垫片）。这是"单轨"的彻底解。
- **(b) 保留双宿主**：保留回退，但必须把它**钉死为同一契约的实现**（当前已基本如此），并在文档中声明"双宿主"是有意架构，而非迁移残留。

当前状态既没做 (a) 也没声明 (b)，属"多轨并存且无人声明"——**这正是红线 2 要消除的状态**，但消除方式不等于删除文件。

### 2. `sessionLocalStorage.ts` —— **可切，需先补**

- 经 `api/sessionPersistence.ts:61` 从 hub 导出 → 是公开持久化 API 的一部分，非内部实现细节。
- `SESSION_BODY_PREFIX`（`crish_session_body_v1:`）的引用**如今只在测试**（`migrateFromLocalStorage.test.ts:26,105,111,167,200,252-288`）。
- 与 `sessionRustDb` 的编排关系：`sessionAgentsTruncation.ts:5`、`sessionQuota.ts:5-6` 注释表明二者互相 import（`sessionLocalStorage` 编排调用 `sessionRustDb` 的 `persistAllSessionsRust`）。

**切除前提（必须先完成）**：逐项证明 Rust DB 轨覆盖 `lsLoadSessionIndex / lsSaveSessionIndex / lsLoadSessionBody / lsSaveSessionBody / lsLoadSessionAgents / lsSaveSessionAgents / lsLoadActiveSessionId / lsSaveActiveSessionId / lsLoadFolderOrder / lsSaveFolderOrder` 全部 10 个函数的对应能力；随后删除该模块 + hub 导出 + 其测试，并以负向断言（模块不存在）替代。

### 3. zustand persist（`crish_session_store_v1`）—— **可切，需同步处理 LS 导入面**

- `store/sessionStore.ts:49` `withPersist(...)`，`:63` key = `crish_session_store_v1`，`partialize`（`:64-70`）含 **`sessions`（全量消息）** → 与 Rust DB 双写。
- `withPersist` 是 zustand `persist` 的薄包装（`store/middleware/withPersist.ts:22-37`），默认存储即 localStorage。
- **但**：`api/localStorageApi.ts:46` 有 `'crish_session_store_v1': { ... }` 条目 → LS 导入特性会读它。

**结论**：这是**真正可以立刻切除的冗余双写**（渲染不读它），但切除必须同时决定 LS 导入特性的去留；否则保留读面就会出现"读一个已经没人写的 key"的新形态死代码。

### 4 + 5. 迁移与历史清理 —— **可切，需先定终期**

- `migrateFromLocalStorage.ts:106` 一次性 `localStorage → SQLite`；`:178` 失败仅 `console.warn` 后下次重试（**fail-open**）；`:211` 迁移后**保留 LS 数据 30 天**。
- 测试断言迁移后源键被删（`:252-253`、`:287-288` `toBeNull()`），说明"删源"是既有的设计意图，30 天保留与之矛盾。
- 无日落期残留的具体形态：**30 天保留窗口** + `sessionRustDbLegacyCleanup.ts` 的持续清理职责。

**处置**：迁移成功即删源（去掉 30 天窗口），迁移完成一个版本周期后删除迁移脚本本身 + 历史清理模块，由负向断言（两模块不存在）替代。

## 五、本次核实对方案的修正

| 原方案条目 | 修正 |
|---|---|
| §五「`sessionRustDbFallback.ts` 属旧轨，物理删除」 | 改为**不可切**；须先做"单宿主 vs 双宿主"的显式架构决策 |
| §五「30 天 LS 保留 → 删除」 | 保留但**明确为终期**：迁移成功即清，一个版本周期后删迁移脚本 |
| §五「zustand persist 直接移除」 | 追加前置：同步决定 LS 导入特性去留 |
| §五 会话三轨"物理切除"整体 | 三轨中**只有 1.5 轨是纯冗余**（persist 双写 + LS 主体），另一轨是**能力**而非债务 |

**这一条修正的意义**：原方案把"多轨"全部当作债务。核实后发现其中一轨承载了非 Tauri 宿主的运行能力——**删除它不是在还债，是在砍功能**。红线 2 的目标（单一权威源）应当通过"明确声明宿主边界"或"统一契约"达成，而不是无差别物理删除。
