## ② 逐维度评审裁决

### 2.1 渲染实例：独立 Chromium 胜出（01/02/04 立场），否决 WebView2

裁决：**独立 Chromium 进程 + CDP screencast 帧渲染进 React canvas + 面板内输入经 CDP Input 转发**；HWND 嵌入仅作 Windows 延迟增强。

否决 03 的 WebView2 主方案，四点硬伤：

1. **与登录态导入硬需求冲突，且 03 的论证是循环论证**：03 先选 WebView2，再以「WebView2 不识别 Chrome profile」否决 profile 复制——但「Chrome/Edge 用户数据导入」正是项目硬需求（02 §7 产品主线、04 §2 决定性理由）。选 WebView2 恰恰制造了导入能力天花板（storage_state 无 sessionStorage/IndexedDB/扩展，03 §7 自己承认），然后又把该天花板当作 WebView2 的合理性。因果倒置。
2. **WebView2 CDP 是「官方但无稳定 SLA」面**：03 §1 自己列了握手 Origin/token 行为漂移风险；01 §1 引微软文档「部分命令不支持、API 可能变更」。快照（getFullAXTree/captureSnapshot）与 Input 全量注入依赖完整 CDP，协议子集化即能力不确定。
3. **隐性双轨**：03 用 BrowserController trait 做 WebView2 + Chromium 双后端——同一产品维护两条渲染管线（z-order/焦点/握手/生命周期各一套），正是 03 自己否决「双轨通道」的同构结构（03 §2 称双轨 3 倍+）。
4. **MCP 兼容论证不绑定 WebView2**：03 的核心卖点是 chrome-devtools-mcp attach 共享端口——但 chrome-devtools-mcp 原生 launch/attach 系统 Chrome（`browser.ts:77-79` attach、`:231-246` launch），独立 Chromium 下该兼容性 100% 保留。03 把「MCP 兼容」与 WebView2 强绑定是虚假排他。

补充：03 说「独立 Chromium 需 SetParent 嵌入（弱）」——低估了 screencast 流方案（01/02）：页面经帧流画进 canvas，根本不需要窗口嵌入，用户输入经 CDP Input 转发，内嵌体验与原生窗口无关。这条论证前提不成立。

CfT 首选 + 系统 Chrome/Edge 回退采纳 04 的分发策略（版本钉死 = CDP 行为可控，运维友好）。

### 2.2 控制通道：CDP 单轨，否决注入桥（含感知面）

裁决：**CDP 唯一控制通道**。否决 03 的「注入事件桥补感知」——理由：

1. 03 §2 自认注入桥的维护面（navigation 重注入、跨域 iframe、页面污染、CSP）是 3 倍陷阱，它只是把「执行双轨」换成「感知单桥」，维护成本仍在（skyvern page.py:1168-1198 的重注入模式就是证据）。
2. **用户干预检测有零注入替代**：01/02 的面板模式（screencast + 输入转发）中，用户输入必经转发层，检测是免费的；CDP 端 `Page.frameNavigated`/焦点事件可补全局信号。注入桥的唯一动机（CDP 不回传用户物理输入）在面板输入转发架构下消解。
3. 页面内任何注入都是可探测面（03 §1 自己也承认扩展可被检测），安全视角（04）与反检测视角都不利。

### 2.3 Rust CDP 客户端：自写薄客户端（4:0 共识，重点论证）

裁决：**自写薄客户端**，采纳 agent-browser `client.rs` 架构骨架（ws_tx + AtomicU64 id + pending oneshot map + broadcast 事件 + PendingGuard + keepalive）。专项分析见 §3.1。

### 2.4 感知快照：DOM 简化树主（01/02 胜出），AX 辅助，截图按需

裁决：**DOM 简化树为主通道 + AX 补充复合控件属性/表单值 + 截图按需（vision 兜底）**。专项分析见 §3.2。

### 2.5 定位与执行：四案合流

裁决：**index（backendNodeId）主定位 + data-\* 标记执行前校验 + getContentQuads 实时坐标 + Input 真实事件 + 语义锚点重定位兜底（上限 3 次）+ 失败分类报告**。01 的「坐标备 + JS click 兜底」降为最末级兜底（JS click 仅 Input 不可用时的降级路径）。专项分析见 §3.3。

### 2.6 协同模型：令牌软互斥（04 内核）+ 面板转发检测 + 指示条/接管（02 UI）+ 版本失效（01/03 事件面）

裁决：

- **内核机制**：04 的 generation 令牌（执行前申请、执行后双校验、用户活动递增吊销）优于 02 的操作锁（阻塞语义 + 额外锁协议）与 03 的纯乐观（无同字段竞态收敛）。令牌是纯状态校验，零阻塞、可急停、崩溃后归零。
- **用户活动检测源**：必须是面板输入转发路径（01/02 架构免费提供）。04 的「独立窗口 focus/输入事件」检测残缺——独立 Chromium 窗口下拿不到用户键盘/鼠标输入（OS hook 才可，3 倍+），这是 04 的隐性缺口（§4.4）。检测源裁决为 01/02 的面板模式，不是 04 的窗口模式。
- **页面变化感知**：01 的「快照失效广播」+ 03 的 snapshotVersion 合一（事件总线广播 → 快照版本失效 → 动作前校验版本）。否决 02 的「每次动作前强制完整 re-snapshot」（每次动作多付一次全量采集的 token/延迟；事件驱动失效 + 版本校验是严格更强的方案）。
- **UI 层**：采纳 02 的指示条（预告 + 取消）、接管横幅（恢复/重新指示）、审批附动作前截图 + 高亮、动作日志时间轴。01 的「记录用户干预 + 报页面被修改」与 02 的「拒绝执行让 AI 重看」合流为「版本不一致 → 拒绝 + 反馈」。
- **冲突语义总原则**（02 §6.4，采纳）：永远偏袒用户，AI 永远先重看再行动，不猜测不回滚不静默覆盖。

### 2.7 数据导入：面板内登录主 + 最小文件集复制 + 书签/历史直读，App-Bound 约束必须显式处理

裁决：02 的「面板内登录主路径」是四份中唯一把它当第一路径的方案，也是协同模型的免费产物（用户登录一次 → AI 继承会话），成本为零且体验最优，**必须作为线一**。01/04 都漏了这条（各只列复制 + storage_state），是它们的共同缺口。

复制线采纳 02+04 合并版：04 的最小文件集（仅 Cookies/Local Storage/Session Storage；显式排除 Login Data/History/Web Data/Bookmarks/Thumbnails）+ 02 的同家族 exe 启动 + `Network.getAllCookies` 回读校验（Chrome 127+ App-Bound 加密唯一正确应对——**只有 02 处理了 App-Bound**；01 的「同用户复制不破坏 DPAPI」论断在 App-Bound 时代不成立，01 需修正；04 只做排除列表、未提同家族 exe 约束，也是缺口）。

否决 03 的 storage_state 主路径：覆盖不全（无 sessionStorage/IndexedDB/扩展）+ 明文 JSON 即会话凭据文件（04 论证）+ 运行时注入触发站点检测。仅保留为「跨会话持久化可选通道」，且默认关闭、导出走 DPAPI 加密 + 审批（04 立场）。专项分析（实施顺序与风险）见 §3.4。

### 2.8 工具集：browser_\* 挂 agent-tools（4:0），MCP 补深作二期增强

裁决：采纳 01 的 ~16 工具清单（含 01 独有的「MCP 桥自动复用」亮点：注册后零工作进入外部 IDE 工具面）+ 04 的 dangerous 分级（evaluate 默认 Deny、剪贴板默认拒绝、截图敏感域自动模糊、登录/支付提交 Ask）+ 02 的「工具执行统一走锁-锚定-审计管线、不允许绕过」约束。03 的 chrome-devtools-mcp 插件补深（lighthouse/trace 等）确属低成本生态红利，但**与自研工具共享端口会引入多客户端 enable 竞争与双入口选型噪音**（03 §8 风险自承），列入二期增强而非一期。

### 2.9 安全：04 为底 + 02 身份校验，采纳其验收门槛

裁决：04 的安全面（随机端口 + loopback + ACL + 31 基线登记 + 审计脱敏 + 急停 + 沙箱保留 + 生命周期管理 + 验收门槛清单）是四份最完整，全盘采纳；补 02 的「连接后身份 token 校验」（防同机进程抢占端口）与「审批附动作前截图 + 高亮」（02 §6.3）。01/03 的安全设计均是其子集。

### 2.10 Computer Use 二期：02 共享管线 + 04 安全门槛，否决 03 缩范围

裁决：**一期按 02 的组件边界抽象（帧源 trait + 输入注入 trait + 前端 props 契约，成本一个 trait），二期整机操作（Windows）按 04 的门槛立项**（会话显式开启 + 全动作审批 + 禁用键集合 + 全局急停 + 与浏览器线硬隔离互斥）。01 的「完全并行独立」低估了帧渲染/指示条/接管 UI/日志的复用价值（01 §10 只承认共享审批审计，把前端四件套算作零复用），否决其并行策略；03 把「电脑操作二期」缩成「浏览器内视觉主控」是对需求的擅自缩减（03 §10 自己也承认远期整机需求以外部窗口承载），否决。xcap/enigo 版本锁定放二期（01 做法）。

### 2.11 crate 划分：2 crate，否决 02 的 5 分与 03 的双后端 trait

裁决：`crates/conex-browser`（cdp/snapshot/element/action/session/policy/profile 子模块，**不依赖 agent-tools**，保持纯核心可单测）+ `crates/conex-browser-tools`（工具面，依赖 agent-tools 注册/审批/审计）。01/03 的 2 crate 优于 02 的 5 crate（core/session/snapshot/tools/import 拆太碎，crate 间 API 摩擦 > 内聚收益，Rust 惯例下单 crate 多模块即可）；03 的 BrowserController trait 在单后端裁决下属 YAGNI（内部留一个启动器抽象即可，不对外暴露）；04 的单 crate 把 tools 并入核心、污染「核心不依赖 agent-tools」的纯净性，否决。

## ③ 专项裁决

### 3.1 Rust CDP 客户端：自写薄客户端 vs chromiumoxide

**结论：自写，四份一致，我确认并给出量化与握手分析。**

| 比较项 | 自写薄客户端 | chromiumoxide |
|---|---|---|
| 工作量 | 01：1500-2500 行；03：800-1200 行（域子集差异）；实测量级 ≈ 1-2 周 | 接线即用，但域覆盖不全（Accessibility 等需手写补） |
| 类型覆盖 | 只写用到的域：核心 8 域（Browser/Target/Page/Runtime/DOM/DOMSnapshot/Accessibility/Input/Network/Session，01 §3.2）+ Storage/Emulation/Log 按需补（登录态读写、视口模拟） | 全协议生成但部分域缺失/滞后，且抽象绑定库的 session 建模 |
| 握手差异 | 独立 Chromium 裁决下 WebView2 的 Origin/wsHeaders 兼容问题**直接消失**（03 的 wsHeaders 担忧是 WebView2 特有，chrome-devtools-mcp 连系统 Chrome 也无此问题）；仅需 keepalive + 重连 + 宽容解析 | 无法透传握手参数，被库锁死 |
| 测试面 | mock WS 服务端单测（agent-browser `browser.rs:2627` 的 `127.0.0.1:0` 先例）+ 对齐 agent-browser 320 单测量级；e2e `#[ignore]` 串行 | 库行为不可 mock，只能对真实浏览器测 |
| 审计/审批/急停 | 唯一发送层 = 天然挂点（04 §4 决定性理由）；abort_token 精确穿透到 pending 命令（02 §3 理由 3） | 命令封装在库内，逐命令侵入式改库 |
| 依赖面 | 仅 tokio-tungstenite + serde_json（B9 评审面最小） | hyper/tokio 大栈 + 上游停滞风险 |

**裁决**：自写。工作量上限 2500 行（含类型建模）在 agent-browser 蓝本对照下是「有参考答案的工程量」，无研究型风险。类型建模方式：**手写**（01/04 路线，agent-browser `cdp/types.rs` 蓝本），03 的 build.rs 从 `cdp-protocol/*.json` 生成可作可选优化——但协议 JSON 文件入库引入构建期依赖与版本管理成本，一期手写更稳。**双层路由必须内建**（browser-level WS + target session 嵌套，browser-use CDPSession 模型）：这是 screencast 客户端与 AI 命令客户端并存（Chrome 原生多客户端）的前提，也是 02/03 强调的协同事件扇出的基础。测试面采纳 04 的「发送层挂幂等/审批/急停钩子」单测口径。

### 3.2 感知快照：AX 主 vs DOM 简化树主 vs 混合

**结论：DOM 简化树主（01/02），AX 补充，截图按需。2:2 之争我裁定 01/02 胜出，理由按权重排序：**

1. **定位闭环长度（决定性）**：DOM 简化树的 index = backendNodeId 直作模型编号 → `DOM.resolveNode` O(1) 精确命中（01 §4.4）；AX 树无坐标，定位需「AX 节点 → backendDOMNodeId → 反查 getBoxModel」二次跳转（02 §4 证据、04 §5 自认），且 AX role+name 重定位是语义模糊匹配，重名歧义（04 §5 批评别人语义定位的缺陷同样适用 AX 重定位）。
2. **clickable 覆盖（功能性）**：browser-use 的 `ClickableElementDetector`（事件监听器检测覆盖 Vue/React onClick + interactive_tags + ARIA role + label/span 包装识别）是多年实战调优资产；AX 树对无 a11y 语义的 div 按钮丢失（03 §4 自己承认）。主通道丢交互元素 = AI 无法操作真实站点的高频控件，这是 AX 主方案不可接受的功能缺口。
3. **协同「可指向」需求（产品性）**：高亮框渲染到帧上需要元素坐标（02 §4 理由 1），DOM 简化树天然携带 bounds，AX 需反查。
4. **token 成本实测口径**：过滤后的简化树（paint order + bbox 传播剔除）与 AX 树同为「文本为主」结构，量级差异在 2 倍内；叠加 100KB/3 万 token 截断上限（01 §8 工具节流）与 compact/depth 选项后两者均受控。03 的「AX token 最省」优势不足以覆盖前三条。
5. **隐私面（04 的唯一有效论点）**：AX 节点少、自动忽略装饰——但 DOM 简化树同样在采集后做密码脱敏（01 §4.7）+ 快照截断，且「页面内容不可信」前缀（01 §9）。隐私差异可工程消解，不构成否决主通道的理由。

**实现路径裁决采纳 01 的工程亮点**：采集用 CDP 原生 `DOMSnapshot.captureSnapshot`（协议级、零页面注入），只移植 browser-use 的**算法**（clickable/paint order/bbox/index 分配）作为纯函数处理协议数据——不照抄 browser-use 的注入 JS 采集脚本（02 方案），避免页面污染与反检测面；AX 仅补复合控件属性与表单当前值（serializer.py:1230-1267 同款职责）。

**实现量**：serializer 算法移植 ≈ 1300+ 行 Python 语义 → Rust 纯函数 + fixture 断言翻译，1-2 倍，有逐行对照参考。实现成本高于 AX 直接抄 agent-browser（常规），但换回的是定位闭环与交互覆盖，属「一次投入、长期免维护」项。**snapshotVersion 必须在快照数据结构一期内置**（03 §4 唯一不可省的建议，01 遗漏——后期加版本号要改快照序列化格式与工具契约）。

### 3.3 元素定位：index / ref / backendNodeId / data-\* 标记可靠性对比

**结论：backendNodeId 直作 index（可靠性最高）为主，data-\* 标记作执行前毫秒级校验，语义锚点作失效降级。**

| 机制 | 可靠性 | 失效模式 | 适用角色 |
|---|---|---|---|
| backendNodeId（快照内直作 index） | 高：快照生命周期内唯一、O(1) `DOM.resolveNode` 精确命中 | 跨导航/页面重渲染后失效（需重快照） | **主定位**（01 方案） |
| 快照纯序号 index（与 backendNodeId 映射表） | 同 backendNodeId（本质相同，02/03 的 ref/uid 均此模型） | 同左 | 与上合一，无需区分 |
| data-\* 标记（`data-agent-browser-located`，04） | 高（快照内）；执行前 `querySelector` 毫秒级存在性/可见性校验 | SPA 重渲染清除标记（窗口期毫秒级）；可被页面脚本探测 | **执行前校验层**（04 增量采纳：防「index 在但节点已换」的静默错点） |
| 坐标中心（getContentQuads） | 中：受滚动/遮挡影响 | 布局漂移 | 执行坐标取点，不承担定位语义 |
| 语义锚点（role+name+文本片段+相对位置，02） | 中：重名歧义 | 重定位成本高 | 失效降级路径（01 的「上一快照文本+role 摘要重定位」同款，上限 2-3 次） |
| CSS selector | 差：页面改版即失效 | — | 不用（03 自己也排） |
| JS `el.click()` | 定位准但事件 untrusted | 登录/支付站点拒绝 | 最末级兜底（01 立场） |

**裁决**：五层合流各司其职（见 2.5）。可靠性排序：backendNodeId ≈ data-\*（快照内）> 坐标 > 语义锚点 > CSS selector。04 的 data-\* 标记与 01 的 backendNodeId 不冲突（agent-browser 本身两者并用：resolveNode 定位 + 标记校验），合并后无重复职责。执行统一用 CDP Input 真实事件（4:0 共识），**任何方案都不做坐标魔术补偿**（04 引 AGENTS.md 红线，全体遵守）。

### 3.4 数据导入三路径：实施顺序与风险（含 Chrome 127+ App-Bound）

**实施顺序**：① 面板内登录（零成本，协同模型产物，第一）→ ② profile 最小文件集复制（与快照/动作并行开发，**必须早于真实站点 e2e**）→ ③ 书签/历史直读（独立小模块，任意时间，rusqlite 复用 conex-db）→ ④ attach 高级选项（最后，有前置条件）。

**风险排序与处置**：

| 风险 | 等级 | 处置（采纳来源） |
|---|---|---|
| App-Bound 加密（Chrome 127+）：cookie 加密绑定启动 exe 身份 | **高** | 必须**同家族 exe**（Chrome profile → Chrome exe、Edge profile → Edge exe，02 §7）；启动后 `Network.getAllCookies` 回读校验，失败域名引导面板内重登（02）；**01 的「同用户复制不破坏 DPAPI」论断失效需修正**；04 未提同家族约束需补 |
| 复制文件锁（WinError 32） | 中 | browser-use `_is_chrome_profile_lock_error` 检测 + 「请关闭 Chrome」提示 + 回退面板登录（01/04 同有） |
| 密码/历史/自动填充误入 AI 面 | 高（隐私） | 最小文件集 + 显式排除（04）；复制前确认对话框明示「密码与历史不会导入」（04） |
| 复制目标 ACL 与会话清理 | 中 | `%LOCALAPPDATA%\Crish\browser-sessions\<id>` 私有目录 + ACL 收紧 + 会话结束删除（04） |
| storage_state 明文落盘 = 会话凭据文件 | 中 | 默认不导出；导出走 DPAPI 加密 + 审批 + 审计（04）；仅作跨会话持久化可选通道 |
| attach 前置条件高 | 中 | DevToolsActivePort 自动发现只适用「我方启动的实例」；attach 用户日常浏览器需用户手动开调试端口——**02 的「零成本接管」叙事需修正**，定位为高级用户选项 |

**结论**：三路径按 ②→① 的互补关系实现（复制保证存量登录态、面板登录保证增量），attach 降级为可选，storage_state 收敛为加密可选通道。03 的 storage_state 主路径被彻底否决。

| attach 前置条件交代 | —（不主张 attach） | ❌ 低估（「零成本接管」与「需用户开调试端口」自相矛盾） | — | — |

### 4.3 P0 验证项（阶段 0/1 必过，不过即叫停对应方案）

1. **screencast 帧延迟实测**：本地 loopback 帧延迟 < 300ms 可接受；高动态页面帧率不承诺——决定协同体验可行性根基（02 风险 1）。
2. **App-Bound 复制冒烟**：Chrome profile 最小文件集 → 同家族 exe 启动 → `Network.getAllCookies` 回读目标站点 cookie 可解密；异家族 exe 对照应失败——决定导入方案可行性（02）。
3. **DOMSnapshot.captureSnapshot 采集实测**：目标站点（登录页/表单密集页）采集耗时 < 500ms、token 量 < 30k——验证快照主通道性能预算。
4. **定位全链路冒烟**：backendNodeId → resolveNode → data-\* 标记 → Input 点击，在 React/Vue SPA 站点验证含标记校验窗口（04 验收 3 扩展）。
5. **面板输入转发 + IME**：中文输入法合成 + `Input.insertText` 兜底专项测试（仓库 IME 测试资产惯例）。
6. **多客户端并存**：screencast 客户端 + AI 命令客户端同端口并发互不干扰。
7. **policy 门禁三检查点**：导航前/重定向逃逸打回/新标签关闭 + NavigationBlocked 审计事件（04 验收 1）。
8. **急停/令牌**：运行中急停 → pending 全取消 + 令牌失效 + 浏览器存活（04 验收 3）。
9. **导入排除断言**：Login Data/History/Web Data 不进入复制目标目录 + 目录 ACL 断言（04 验收 4）。
10. **崩溃恢复**：浏览器进程 kill → 事件上报 + 自动重启 + 令牌归零重观察（04 验收 5 扩展）。
