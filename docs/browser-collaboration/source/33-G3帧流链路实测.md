## 4. 发现的问题与修复（真实链路 bug ×3 + 并行冲突 ×1 + 测试适配 ×1）

### 问题 1（E6 首挂根因 A）：Chrome 151 帧元数据协议漂移——浮点尺寸 + frameNumber 缺失

- **现象**：E6 断言"尺寸合理"失败：`1280x0`（deviceHeight=0）；`frameNumber` 恒缺省。
- **根因**（CDP 原始报文实证，诊断脚本直连 headed/headless Chrome 抓取）：
  1. `metadata.deviceHeight` 实测为**浮点值 633.6000366210938**（旧协议整数）——`parse_frame` 用 `as_u64()` 对浮点返回 None → 落 0；
  2. `frameNumber` 字段实测**不再发送**——`as_u64().unwrap_or(0)` 使帧序号恒 0，帧泵去重表 `(session, frame)` 把首帧后的**全部帧误判为重复丢弃** → 帧流实际只能收到 1 帧。
- **修复**（`src/cdp/bus.rs::parse_frame`）：尺寸按浮点解析取整（`as_f64().round()`）；帧序号缺省回退帧时间戳毫秒（秒级浮点 → 毫秒整数，帧间隔 ~100ms 保证唯一）。
- **回归测试**：`bus_frame_chrome151_float_metadata_missing_frame_number`（浮点高度取整 633.6→634、无 frameNumber 回退时间戳、相邻帧序号互异防去重误杀、旧协议 frameNumber 仍优先）。

### 问题 2（E6 首挂根因 B）：Chrome 151 帧事件 `params.sessionId` 为 JSON 数字 + ack 参数类型敏感

- **现象**：帧能收到但 ack 全失败（`AckFailed: 参数无效[Page.screencastFrameAck]：Invalid parameters`）→ Chrome 收不到 ack → 停发新帧。
- **根因**（CDP 原始报文 + 双形态对照实验实证）：
  1. `screencastFrame.params.sessionId` 实测为 **JSON 数字 `1`**（旧协议字符串）——`parse_frame` 的 `as_str()` 返回 None → ack 会话回退信封会话 → ack 用错值；
  2. **Chrome 151 对 ack 参数类型敏感**：对照实验（同浏览器实例）——ack `{"sessionId":"1"}`（字符串）第 3 帧后停滞；ack `{"sessionId":1}`（数字）持续产帧。字符串化回传同样被拒。
- **修复**（`src/cdp/bus.rs` + `src/cdp/domains.rs` + `src/frames/session.rs`）：`FrameChunk.ack_session` 与 `ScreencastFrameAckParams.session_id` 由 `String` 改为 **`serde_json::Value`**——原始形态无损透传（数字保持数字、字符串保持字符串），缺省仍回退信封会话（旧协议兼容）。
- **回归测试**：`bus_frame_numeric_session_id_parsed_for_ack`（数字 1 保持数字形态）；domains.rs 序列化断言补充数字形态；既有 `frames_ack_uses_params_session_id`（字符串形态）保持通过。

### 问题 3（E5 回归面）：并行冲突合并残留——`remove_ephemeral` 调用丢 `.await` 成静默 no-op

- **现象**：`crates/conex-browser/src/browser/mod.rs` 处于 git stash pop 冲突（UU）且被并行 Agent 重构中间态破坏：`on_driver_panic`/`cleanup_profile`/`prepare_profile` 被 sync 化，而 `profile.rs` 的 `remove_ephemeral`/`import_copy` 仍为 async——`let _ = remove_ephemeral(&dir);` 变成**丢弃 future**（profile 实际不删除，E5 profile_removed 断言与 crash_loop_aborts_after_3 均受影响），且编译失败（`?` 应用于非 Result）。
- **修复**（`src/browser/mod.rs`，恢复 async 链）：
  - `prepare_profile`/`cleanup_profile`/`on_driver_panic` 恢复 `async fn`，4 处 `cleanup_profile()` 调用与 `import_copy(...)`/`remove_ephemeral(...)` 补 `.await`；
  - **stop() 无驱动分支重构**：清理收集放守卫块内、`remove_ephemeral().await` 放守卫块外（MutexGuard 跨 await 非 Send；初版用 `tokio::spawn` 异步派发引入"stop 返回时清理未完成"竞态，被 crash_loop_aborts_after_3 捕获后改为本结构）；
  - 三处 stash 冲突标记按"upstream（M5 加固 async 版）"合并（外部 Agent 冲突解决误取旧 sync 版）。
- **回归测试**：既有 `crash_loop_aborts_after_3`、`graceful_stop_waits_natural_exit_without_double_poll` 等 browser 模块 122 用例全绿。
- 说明：该文件属并行 Agent 文件域，本 Agent 仅做恢复编译与语义修复（async 链与 HEAD 的 profile.rs 签名及 M5 注释一致），未做任何设计改动；报告已记录，供主控协调。

### 问题 4（测试适配）：headless 下 screencast 帧近停 → 帧流用例改 headed 离屏

- **现象**：E6 在 headless=new 下收到首 3 帧后 pacing 窗口 0 帧（间隔样本 0）。
- **根因**：headless 页面视口不可见 → JS 定时器节流（~1s/次）→ 页面变化频率低于 ack 持住 → Chrome "无变化不产帧"（S0-01 实测语义）→ 帧流近停；CSS 动画在 headless 合成器亦不稳定。
- **处理**（测试侧）：`E2eEnv::launch_with_mode(EngineMode::HeadedOffscreen)`（离屏定位，页面可见性与真实面板一致）；E6-E9 使用，E1-E5 保持 headless 不变。产品架构层面：面板场景页面可见，不受节流影响，非产品缺陷。
