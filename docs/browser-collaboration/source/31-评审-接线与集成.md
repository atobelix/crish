### P1（高，3 项）

**F1. 子代理 implementation 类型拿到全部 browser_* 工具（fail-open 排除缺口）**
- 证据：`crates/agent-tools/src/readonly.rs:121`（implementation → `|_| true` 全工具集）；`apps/agent-workbench/src-tauri/src/core_run_commands.rs:3116-3118`（仅剔除 run_subagent，未追加 browser_ 前缀剔除）；27 方案 §3 明确要求「若未排除 → 同处追加过滤闭包」——未落地；run_subagent 工具 schema 允许 task_type=implementation（`crates/agent-tools/src/tools/subagent.rs:696`）。
- 影响：implementation 子代理可调用 navigate/snapshot/console/network 等 15 个非 dangerous 工具（不经审批）→ ①读取共享浏览器当前页内容（含主 run 的用户登录态页面）→ 隐私泄漏面；②导航/切标签直接改写主 run 正在操作的页面 → 跨 run 干扰；交互 8 工具仍受工具层审批门控（S4），危害被部分兜底。
- 修复建议：在剔除 run_subagent 的同一 filter_registry 闭包追加 `!name.starts_with("browser_")`（fail-closed，一行）；同步补「子代理 list_definitions 无 browser_*」断言（27 §5 验收口径）。

**F2. estop 桥对子代理 run 无条件装配 → 子代理 abort 污染主 run 浏览器操作**
- 证据：`core_run_commands.rs:3259-3263` 位于 run_task_impl 通用装配段，子代理 run 同通道启动（`subagent_spawner.rs:349-368` 经 launcher → core_run_task）；`browser/mod.rs:214-223` cancel_estop 置急停旗 + 取消当前令牌；急停旗仅随下一 run 启动/浏览器重启复位（`browser/mod.rs:403-404`）。
- 影响：子代理 run 被取消（L3/超时/kill_all）→ cancel_estop → ①主 run 在途 CDP 命令被取消（CdpError::Cancelled → `tool.browser.cancelled`）；②急停旗置位 → **主 run 本 run 剩余全部 browser_* 命令被 EmergencyStop 拒绝**，且同 run 内无复位点 → 浏览器操作整段失效，直到下一 run 启动。多 run 并发共享 estop 周期虽在 27 §6 P1 登记，但「子代理取消即瘫痪主 run 浏览器」这一具体故障链未在登记口径内。
- 修复建议：装配处按 `subagent_config.is_none()` 门控（仅主 run 挂 watcher/reset）；或引入 owner 隔离令牌（27 §6 P1 提级）；至少补一条「子代理 abort 不影响主 run 浏览器」集成测试。

**F3. 面板「急停（强制）」无真实强制语义 + launching 期可长时间无响应**
- 证据：`useBrowserSession.ts:148`（kill = stopSession = browser_stop）；`browser_commands.rs:55-63`（Graceful）；`conex-browser/browser/mod.rs:400-429`（stop 等驱动收尾，wait_or_kill 5s 后杀树）；`BrowserSlot::start` 的 Launching 分支立即返回而 `start_and_connect_locked` 持会话锁（`browser/mod.rs:398-418`）→ launching 中 kill 等待锁直至首启结果（超时上限 ~40s，`browser/mod.rs:385-396`）；26 联调遗留 1：优雅分支未发 Browser.close（`browser/mod.rs:936-937` 注释）。
- 影响：用户对挂死浏览器的「强制急停」实为优雅停止（最长 5s+ 等待）；launching 中点击急停可能数十秒无反馈且 busy 锁死按钮。急停是用户安全出口，语义失效风险不可接受。
- 修复建议：①命令面新增 force 停止（StopReason::Force）或 browser_stop 增加 `force: bool` 参数（前端 kill 传 true）；②引擎 stop 包超时（如 15s）返回结构化错误；③UI 文案据实改为「强制停止（最长等待 Ns）」或隐藏 launching 态 kill（改为允许再次 start）。

### P2（中，7 项）

**F4. stop 无硬超时 + 前端 busy 无超时 → 面板可永久锁死**
- 证据：`conex-browser/browser/mod.rs:427-429`（stop await 驱动任务，无 timeout）；`useBrowserSession.ts:72-80`（runOperation 无 timeout）；Windows 环境已知进程回收竞态（28 文档 §6.2）。
- 修复建议：stop 调用包 `tokio::time::timeout`（如 15s）→ Err 结构化「停止超时（进程可能残留，见日志）」；前端 runOperation 增加超时兜底复位 busy。

**F5. attach_emitter 转发任务 `Err(_) => break`：broadcast Lagged 即永久停发**
- 证据：`browser/mod.rs:343-353`。
- 影响：事件速率极低下 Lagged 概率小，但任何一次 recv 错误（含 Lagged）即终止转发 → 面板状态从此卡死且无恢复路径（无重挂机制）。
- 修复建议：`Err(RecvError::Lagged(_)) => continue`，仅 `Closed` break；转发任务死亡时补 tracing error。

**F6. BrowserManager Drop `try_lock` 失败跳过杀树 → 应用退出时浏览器进程泄漏**
- 证据：`conex-browser/browser/mod.rs:1072-1081`。
- 影响：退出时若驱动任务恰持锁（Tauri managed state drop 与 tokio runtime 收尾时序不保证），try_lock 失败 → 不杀 → 受管 Chrome 残留（下次启动孤儿清扫兜底，`browser/mod.rs:342-344`，但窗口期内残留）。
- 修复建议：Drop 内改用 pid 快照独立字段（不依赖锁）或短暂重试（如 100ms×3）后 kill_sync；或 main.rs 退出钩子显式 `slot.stop()` 兜底（27 §2.1 声明「退出钩子不重复接线」——若保留该声明则 Drop 必须做强）。

**F7. 面板 URL 陈旧 + crashed 无诊断原因（可观测性）**
- 证据：`browser/mod.rs:453-478`（emit 仅在 StateChanged；ProcessEvent.error 字段未进载荷）；`browser/mod.rs:446-450`（current_url 读 nav_stack 活动标签，但无导航事件推送）。
- 影响：运行中导航后面板「当前页面」不更新；崩溃后用户无原因提示。
- 修复建议：①forwarder 增加对导航类事件的 url 推送（或在 status 事件后附带 url 刷新）；②载荷增 `reason?` 字段透传 ProcessEvent.error。

**F8. 前端挂载竞态：status 查询与事件订阅并行，中间事件丢失 / stale 覆盖**
- 证据：`useBrowserSession.ts:83-113`。
- 影响：窗口极小（listen 注册与 status 响应之间的状态迁移，如用户立刻点启动），可导致状态回退（旧 idle 覆盖新 launching）。
- 修复建议：先 `listenBrowserStateEvent` 再 `fetchBrowserStatus`（或 status 返回后丢弃已过时事件：事件带单调序号比对）。

**F9. 惰性启动失败无冷却/退避**
- 证据：`browser/mod.rs:313-326`（每次工具调用失败后，下次调用重新走完整 start_and_connect_locked；CfT 下载回退链每次重走）。
- 影响：启动环境故障（如 Chrome 缺失）时每个 browser_* 工具调用都触发一次完整启动尝试，拖慢 run 且无上限。
- 修复建议：BrowserSlot 内记最近失败时间，冷却期内直接返回 not_ready（如 10s）；或依赖 manager 崩溃预算并透传剩余预算。

**F10. MvpDomainGate 对主机名（非 IP 字面量）不做解析校验：`http://localhost`、内网主机名放行**
- 证据：`conex-browser-tools/src/gate.rs:15-17`（遗留注记）+ `gate.rs:205-216`（仅字面量匹配，localhost 域名走 allow_host 且白名单空默认放行）。
- 影响：SSRF/localhost 探测面（工具可导航到 `http://localhost:<port>` 任意本机服务）；IP 字面量阻断被主机名绕过。属 MVP 已知遗留，但引擎接线已将其设为唯一门禁（engine.rs:1242），建议排期落地 DNS 解析级校验（27 §6/17 §4.3 步骤 3）。

### P3（低，8 项）

**F11. browserSessionApi.ts 头注释「未纳入 core_list_commands」与事实矛盾（已纳入 95/91 清单）**
- 证据：`browserSessionApi.ts:10-12` vs `commandManifest.rs:182-184` + `commandManifest.ts:168-170`。
- 修复建议：更新注释；消费面可走 `isRegisteredCommand` 校验（对齐 B5 口径），或明示「绕过清单校验是刻意设计 + 理由」。

**F12. 启动失败后 ever_started 仍置 true → 面板显示 'stopped' 而非 'idle'**
- 证据：`browser/mod.rs:410`（start 尝试即置 ever_started）；`:268-279` status 映射。
- 修复建议：启动失败回滚 ever_started（或语义上接受 stopped——建议明确）。

**F13. Stopping 态调用 browser_start 返回 "starting"（前端显示「启动中」与实际相悖）**
- 证据：`browser/mod.rs:245`。
- 修复建议：Stopping 返回专用状态串（契约扩展需双端同步）或前端按事件纠正（现有事件可纠正，低影响）。

**F14. StartPayload.reason 为自由字符串，无结构化 code**
- 证据：`browser_commands.rs:31-42`。
- 修复建议：P1 增强时给 error 载荷加 code 字段（对齐 CoreError 协议）。

**F15. browser_commands 测试缺口：stop 失败（Err reject）与 degraded 槽命令面未覆盖**
- 证据：`browser_commands.rs:76-159`（仅 start_payload 映射 + idle 契约）。
- 修复建议：补 stop Err 映射与 manager=None 时三条命令的契约测试。

**F16. 用户显式停止后，运行中 run 的下一个 browser_* 调用惰性重启浏览器（停止意图被工具推翻）**
- 证据：`browser/mod.rs:313-326`。
- 修复建议：产品裁决（推荐：stop 后本 run 内工具返回「已停止，需用户重新启动」），或文档明示自动重启语义。

**F17. estop watcher 常驻泄漏（正常结束的 run 不释放任务）**
- 证据：`browser/mod.rs:676-681`。
- 修复建议：AbortSignal 增加「run 结束」通知（或 watcher 内 select run 完成信号）；内存影响小，可 P1 处理。

**F18. 多 run 并发共享浏览器实例影响评估（27 §6 P1 登记复核）**
- 证据：`core_run_commands.rs:3257-3258` 注释自认 + 27 §6。
- 修复建议：与 F1/F2 一并按「run 归属（owner）」方案解决（27 §6 登记的 owner 字段 P1 提级为 MVP 必做项之一）。

## 8. 总评

- **契约面：高质量**。三条命令/事件/状态串双端逐字一致且有测试与动态镜像守门（95/91 一致性成立）；错误形状分工明确（start 载荷化、stop reject 化）且前端三态处理闭环。
- **失败路径：主流闭环，两个硬缺口**。E5（停止无超时）与 E6（急停无强制语义）是面板安全出口层面的未闭环项；E9（转发任务死亡）是事件面单点故障。
- **生命周期：单 run 语义正确**（estop 周期复位/令牌轮换有测试锁定），但**多 run/子代理交互是最大薄弱面**（F1/F2/F18），27 §6 P1 登记口径低估了「子代理 abort 瘫痪主 run 浏览器」的具体故障链。
- **安全：审批链设计成立**（工具层 dangerous + PermissionMode + ApprovalGate 单一判定点，AllowAll 未引入漏洞），但子代理 implementation 类型 fail-open 是明确的方案背离；域名门禁的 DNS 解析遗留需排期。
- **竞态：双启动/端点漂移/busy 互斥完备**；转发任务死亡与前端挂载竞态需修补。
- **可观测：基础达标**（结构化状态事件 + tracing），URL 陈旧与 crash 无原因是 MVP 接受但应登记的缺口。

**优先级建议**：P1 三项（F1/F2/F3）应在 MVP 收口前解决；F2 与 F1 修复成本均为个位数行数，但需配套集成测试；F3 涉及命令契约扩展，需双端同步。P2 按「安全出口（F3/F4）> 事件面（F5）> 退出收口（F6）> 可观测（F7/F8）> 冷却（F9）> 门禁（F10）」顺序排期。
