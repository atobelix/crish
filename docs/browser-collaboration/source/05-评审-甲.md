## ② 逐维度评审与裁决（含各方案硬伤）

### 2.1 渲染实例与用户可见方案

四家对「独立 Chromium 进程」的事实认定一致（01 §1.2 理由 1-6、02 §1 结论、04 §2 结论），分歧只有 03 一家选 WebView2。WebView2 的否决是多重硬伤叠加，不是口味问题：

1. **与硬需求直接冲突**：WebView2 user-data-folder 与 Chrome profile 格式不互通，03 自己的 §7 表格也标注「profile 复制 ❌ 不可行」，被迫退到 storage_state——该路径只能带 cookies/localStorage，SSO（OAuth 弹窗态依赖 localStorage 域隔离）、IndexedDB、扩展数据、第三方 cookie 复现困难，「导入 Chrome/Edge cookie 与用户数据」只满足一半。
2. **CDP 受限子集**：微软明确标注 WebView2 DevTools 协议「部分命令不支持、API 可能变更」；而快照核心命令（`Accessibility.getFullAXTree`、`DOMSnapshot.captureSnapshot`）与 Input 域执行全部依赖完整 CDP。把 AI 操作可靠性的底线押在「可能变更」的面上，且 03 无回退（WebView2 就是唯一后端），是控制面可靠性赌注。
3. **双后端双维护**：Win WebView2 + macOS/Linux Chromium 两套 BrowserController，而独立 Chromium 单后端三平台统一（01 理由 4）。WebView2 换到的唯一好处（原生内嵌 UI、零帧延迟、原生 IME）在独立 Chromium 侧可由 screencast + 二期 HWND 嵌入覆盖。
4. **进程面隔离弱**：与主 webview 共享 WebView2 runtime 进程面，崩溃隔离与沙箱独立性弱于独立子进程（04 §2 论证）。

**用户可见方案裁决：CDP screencast 帧流渲染进 React 面板（01/02），否决截图轮询与独立窗口主路径。** 关键理由：screencast 模式下用户输入经 CDP Input 转发，**用户与 AI 共用一条输入通道，用户活动在 Rust 侧天然可见**——冲突检测零成本，且不需要注入桥（03 为此引入的页面注入维护面全部不必要）；同时指示条/高亮框与帧同屏叠加，是协同体验的根基（02 §6.3）。截图轮询帧率个位数、延迟数百毫秒，只能作静态兜底与动作日志前后截图（02 §6.6 恰好用它）。04 的「独立窗口」路径用户输入绕过我方控制面，用户活动只能靠页面内监听感知，与 03 的注入桥同病。

### 2.2 控制通道 / CDP 客户端（共识区）

四家全部裁决 CDP 单轨 + 自写薄客户端（tokio-tungstenite + serde_json，agent-browser client.rs 蓝本），否决 chromiumoxide（维护停滞 + 抽象绑死）、外部 daemon（版本/审计不可控）、Node 桥（双运行时）。这是全局选型中最稳固的共识。04 补充的强制要求必须采纳：**唯一命令出口（sender 层）统一挂审计（脱敏）、审批、急停、超时钩子**——这是安全视角决定性的（04 §4），自写客户端才做得到。03 的 build.rs 从 cdp-protocol JSON 生成协议类型是可采纳的效率项。

### 2.3 感知快照（重大分歧）

| 立场 | 方案 | 核心论据 | 致命弱点 |
|---|---|---|---|
| DOM 简化树主 | 01/02 | index=backend_node_id 直连定位；clickable 检测覆盖无语义 div；带 bounds 天然支撑帧上高亮；参考资产最厚（browser-use serializer 1300 行可逐行移植） | 树大、token 偏高（需截断）；采集依赖页内 JS（需 isolated world） |
| AX 树主 | 03/04 | 语义稳定、token 省、agent-browser 有成熟实现 | 无 a11y 语义的 div 点击器系统性漏检（03 自己承认）；高亮/定位需 backendDOMNodeId 反查多一跳；商业站点（Vue/React onClick）正是目标场景 |

**裁决：DOM 简化树主 + AX 辅助 + 截图按需（01/02）。** 理由：
1. 本产品核心动作是「精确点击/填写」，模型无视觉能力，文本快照必须携带可操作的定位载体（index → resolveNode 直连）与可渲染的 bounds（高亮框画到帧上，02 理由 1）。
2. AX 主方案在目标站点形态（商业 SPA，div+onClick 常见）上有系统性盲区；03 的方案名为「AX 主 + DOM 补」，实则两路都要写全，复杂度并不比 DOM 主更省，还多了主从错位。
3. 04 的「data-* 原生标记」思路（与 AGENTS.md 严禁补丁精神一致）保留为定位辅助：index 解析 + 执行前实时校验目标存在性/可见性/可交互性。

风险对冲（全部并入最佳方案）：快照大小上限 100KB/3 万 token 截断（01）+ 密码字段 value 一律不回传（01/04 共识）+ depth/compact 选项（03）+ 采集用浏览器侧原生命令（DOMSnapshot.captureSnapshot）为主，clickable 检测 JS 必须在 isolated world 执行且白名单不可参数化（03/04 共识）。

### 2.4 协同冲突处理（重大分歧，见 §③ 专项裁决）

四家方案在「单实例双控制面」上完全共识，在冲突原语上分四派：busy 互斥（01）/ 操作锁+抢断（02）/ 纯版本失效（03）/ 软令牌（04）。裁决为**以 04 软互斥令牌为内核的四合一**，详见 §③。

### 2.5 数据导入（重大分歧，见 §③ 专项裁决）

主路径三派：整目录复制（01）/ 面板内登录+attach（02）/ storage_state（03）/ 最小文件集复制（04）。裁决为**面板内引导登录主 + 最小文件集复制迁移 + storage_state 加密可选**，详见 §③。

### 2.6 工具集 / 安全（共识区 + 择优合并）

工具集四家共识挂 agent-tools 注册面（复用审批三态 permission.rs:63 / audit / abort_token context.rs:104，均已核对存在）。**采纳 03 的 chrome-devtools-mcp 插件补深**（register_plugin_server 已存在，`--browserUrl` attach 模式零改造，lighthouse/performance 等深调试不自研——03 §8 的分工矩阵正确，且可避免 3 倍重实现）。**采纳 04 的权限分级细节**：browser_evaluate 默认 Ask（isolated world）、clipboard 默认 Deny、cookies 读取 Ask、截图敏感域自动拒绝、下载进隔离目录。否决 02 的「browser_click 等仅 Normal」过宽口径。

安全面四家共识度高（随机 loopback 端口 + DevToolsActivePort + 域名白名单三检查点 + block_ip 默认开 + 审批审计脱敏 + 急停），04 最全。采纳 04 全套 + 01 的「禁裸 JS 工具」+ 03 的「会话令牌/端口不进日志」+ 04 的「对齐 31 基线登记评审」。

### 2.7 Computer Use 二期

需求原文明确「电脑操作（Computer Use）为二期」。01 独立 crate（xcap/enigo + computer.py 坐标缩放）、02 共享管线增量、04 独立 crate + 安全门槛，三者实质兼容；**03 缩界为「仅浏览器内视觉主控」直接不满足需求**（其价值可保留为二期的一个模式选项）。裁决：采纳 02 的一期前瞻（帧渲染/输入转发/接管/审批/日志抽象为数据源无关组件，一个 trait + 前端接口契约的成本）+ 04 的立项安全门槛（会话显式开启 + 全动作审批 + 禁用键集合 + 全局急停 + 浏览器/桌面会话互斥）+ 01 的独立 crate 划分。

### 2.8 crate 划分

采纳 01 的两 crate 方案：`conex-browser`（cdp/browser/snapshot/action/session/import 子模块，**不依赖 agent-tools**，纯净可单测）+ `conex-browser-tools`（browser_* 工具面，依赖 agent-tools）。否决 02 的 5 crate（划分过碎拖慢迭代，03 亦提示此风险）与 04 的单 crate（tools 与 core 混装，agent-tools 依赖污染核心可测性）。二期 `conex-computer` 平级独立（01/04）。

## ③ 已知分歧专项裁决

### 裁决 1：渲染实例 — 独立 Chromium 进程（否决 WebView2）

**裁决：A. 独立 Chromium 进程（CfT 首选 + 系统 Chrome/Edge 回退）。**

- **数据导入是硬需求且只有此路**：WebView2 profile 不互通（03 自认）；App-Bound 加密（Chrome 127+）进一步要求「同家族 exe 启动」才能解密——这条在 WebView2 上连尝试的资格都没有。
- **CDP 完整性**：快照（AX/DOMSnapshot）与 Input 域执行依赖完整 CDP，WebView2 是受限子集 + 官方「可能变更」，不可作为 AI 操作可靠性的底座。
- **单后端三平台**：screencast 是纯 CDP 层方案，一套 Rust 代码跑 Windows/macOS/Linux；WebView2 方案 Windows 一套、其他平台另一套。
- **参考资产复用**：browser-use / agent-browser / chrome-devtools-mcp 全部建立在「独立 Chromium + CDP」上，无一行可复用于 WebView2。
- **对否决项（WebView2）的说明**：其唯一真实优势是「原生内嵌、零帧延迟、原生 IME」的 Windows 内嵌体验。该优势在 screencast 主路径下以 P0-2（帧率/延迟实测）与 P0-3（IME 转发验证）对冲；若 P0 实测不达标，以二期 HWND 嵌入（P1，Windows 增强）升级，而非选型期回到 WebView2——因为 WebView2 的两条否决理由（导入不互通、CDP 受限）在任何实现期都无法消除。
- CfT 与 ABE 的交互是 01 未识别的坑：CfT 是独立二进制，Chrome 127+ 的 App-Bound 密钥绑定 Chrome 签名身份，**系统 Chrome profile 复制后交给 CfT 启动很可能解密失败**。裁决：导入向导强制「同家族 exe」（Chrome profile → 系统 Chrome、Edge profile → Edge），CfT 只承担全新会话/引导登录，不承担导入源。

### 裁决 2：用户可见方案 — CDP screencast 帧流渲染进 React 面板

**裁决：A. CDP screencast 帧流（Page.startScreencast）→ React canvas 为主路径；窗口嵌入（HWND）仅作 Windows P1 增强；截图轮询直接否决。**

| 方案 | 帧率/延迟 | 用户输入 | 用户活动感知 | 跨平台 | 复杂度 |
|---|---|---|---|---|---|
| screencast 帧流（选） | loopback 100-300ms，可调 maxFrameRate | CDP Input 转发（与 AI 同一通道） | **Rust 侧转发点天然可见，零成本** | 三平台同一代码 | 1-2 倍 |
| HWND 嵌入（Win） | 零延迟 | 原生输入 | 绕过 CDP，需注入桥 | 仅 Windows | 1-2 倍（P1） |
| 截图轮询（否决） | 数百 ms/帧、个位数帧率 | 无法承载手输文字 | 同 screencast（转发） | 三平台 | 常规但体验不达标 |
| 独立窗口用户直操（04） | 零延迟 | 原生输入 | 绕过 CDP，需注入桥 | 三平台 | 1-2 倍（但协同同屏断裂） |

决定性理由（02 的核心洞察）：**单输入通道 = 冲突处理只有一个关注点**。用户与 AI 同走 CDP Input，任何用户输入在进入页面之前就被 Rust 侧记录，令牌递增、接管判定零成本；无需 03/04 为「感知用户活动」而引入页面注入桥。同屏叠加（高亮框、指示条、审批截图）也只有帧渲染做得到。HWND 嵌入一旦启用就失去该性质（用户输入绕过 CDP），因此只作为 Windows 体验增强的 P1 候选，且必须在 P0-3（IME）实测后决策。

### 裁决 3：感知快照 — DOM 简化树主 + AX 辅助 + 截图按需

**裁决：B. DOM 简化树主（browser-use serializer 移植，backend_node_id 直作 index）+ AX 辅助（复合控件/表单值）+ 截图按需（vision 未来）。否决 AX 树主（03/04）、否决视觉主（当前模型无视觉）。**

理由已在 §2.3；补充否决说明：
- 03 的「AX 主 + DOM 增强补全」实为两路全写，主从错位——clickable 检测（browser-use ClickableElementDetector，覆盖 Vue/React onClick）正是 DOM 侧能力，AX 补不了漏检的 div 点击器；
- 04 的「AX + backendNodeId 反查」定位可行但高亮/重定位多一跳，且 AX 节点裁剪后与像素对不上（02 理由 1），协同场景的「用户要看 AI 指哪里」体验依赖 bounds，DOM 简化树天然携带。
- AX 的价值（role/name 语义、表单当前值、复合控件虚拟化）作为 DOM 树的补充字段并入，不另立主通道（01 已如此设计）。

### 裁决 4：协同冲突处理 — 软互斥令牌 + abort 抢断 + 快照版本失效（四合一）

**裁决：以 04 的软互斥令牌（generation counter）为内核，吸收 02 的 abort 抢断与接管 UX、03 的快照版本号、01 的 busy 指示灯（降级为 UI 状态）。**

| 原语 | 语义 | 来源 |
|---|---|---|
| 软互斥令牌 | 用户任何输入/导航/焦点变化 → counter++ → 吊销全部 pending AI 动作；AI 动作「申请 → 执行前检查 → 执行后核对」双校验 | 04 |
| abort 抢断 | 接管时取消在途 CDP 命令（agent-tools 既有 abort_token，context.rs:104；自写客户端 PendingGuard 天然支持） | 02 |
| 快照版本失效 | snapshotVersion 单调递增，页面任何变化（用户/脚本/定时器/AI 自身）→ +1；动作前校验版本 + 目标存在性 + 位置漂移（三重校验），失效 → 拒绝 +「页面已变化，重新快照」 | 03 |
| busy 指示 | busy 仅作指示条 UI 状态，不做互斥语义 | 01 |

否决说明：
- **否决纯 busy 互斥（01）**：不拦截、不取消在途——用户介入后 AI 导航/提交类动作仍会执行并可能覆盖用户正在看的状态，靠事后校验层发现是「处理事故而非预防事故」，且浪费 token。
- **否决纯版本号（03）**：无在途取消——AI 慢动作（多步填表）在用户接管后继续产生副作用；且版本号依赖注入桥，在 attach/窗口直操模式下不可靠。
- **否决纯操作锁（02 的锁 + 释放即抢断已接近令牌）**：缺「执行后校验」维度（用户输入与 AI 动作毫秒级竞态时，AI 的收尾动作可能覆盖用户最后输入——04 的双校验专治此症）。
- 用户输入在 screencast+转发模式下 Rust 侧可见 → 令牌递增零成本；页面自变（脚本/定时器）用动作前目标校验兜底，MutationObserver 注入仅作 UI 刷新增强（address bar/加载态），不承载冲突语义。

### 裁决 5：数据导入主路径 — 面板内引导登录为主 + 最小文件集复制迁移 + storage_state 加密可选

**裁决：主路径 = 面板内引导登录（02）；一次性迁移 = 最小文件集 profile 复制（04 文件集 + 02 同家族 exe + ABE 回读校验 + 显式确认）；跨会话持久化 = storage_state 加密落盘（04，默认关）；attach 降级为高级/实验、默认关。**

| 路径 | 裁决 | 理由 |
|---|---|---|
| 面板内引导登录 | **主路径** | 协同模型免费午餐（02 §7 线一）：用户与 AI 同实例，用户面板内登录一次，cookie 直接写入实例持久 profile，AI 继承会话，覆盖 SSO/IndexedDB/第三方 cookie 全量——storage_state 永远做不到的完整性；零复制零加密风险。03 也认可「引导登录是最优主路径」（其 §7），两家殊途同归 |
| profile 整目录复制（01） | **否决为主路径，收缩为最小文件集** | 隐私面：密码/历史/自动填充进 AI 可读面不可接受（04）；ABE 后整目录复制并不比最小集更可靠；「同用户复制不破坏 DPAPI」已过时 |
| 最小文件集复制（04） | **迁移向导采纳** | 仅 Cookies + Local Storage + Session Storage，显式排除 Login Data/History/Web Data；同家族 exe 启动 + `Network.getAllCookies` 回读校验（02 设计），失败域名引导面板内重新登录；WinError 32 锁检测 + 显式确认对话框 |
| storage_state（03） | **否决为主路径** | 覆盖不全（SSO/IndexedDB 缺口）+ 明文 JSON 落盘即凭据文件（04）；仅作跨会话持久化可选通道，必须加密（DPAPI/AES-GCM）+ 审批 + 审计，默认关 |
| attach（02 线二） | **降级为高级/实验，默认关** | 体验诱人但安全面最差：用户浏览器开调试端口、CDP 无 token 认证、用户输入不可感知需注入桥；04 威胁模型下不可作主路径。一期不做，列为后续增强（若要启用，需「显式开启 + 会话令牌 + 域限制 + 注入桥」全套门槛） |
| 书签/历史直读 | **共识采纳** | 只读 + 复制副本读取（02 E 项），面板增值功能，无争议 |
