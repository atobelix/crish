# 24-红队-否决复审（RT-2：否决决策复审）

> 角色：红队 Agent（RT-2）。复审对象：选型轮被否决的四项候选方案——WebView2 内嵌、独立窗口直操、注入脚本桥为主通道、截图轮询。
> 复审依据：**最终方案的自身设计**（08-最终总文档、09-方案敲定、15-协同模型与冲突处理、16-数据导入与持久化，及 05/06/07 三份评审的原否决出处），而非最初方案时期的假设。
> 立场：重新审判，不和稀泥；每项给「原理由 → 新事实 → 结论」三段式。
> 只写本文件，其余只读。

## 0. 复审方法声明

- 新事实一（16 维度）：数据导入主路径已从「profile 复制」改为「**面板内引导登录**」——用户直接在面板登录，cookie 由浏览器实例自行加密落盘受管 profile，零解密、零互通依赖（16 §1.1/§0.1）。profile 复制降级为「迁移路径」，且当前方案自身承认其失败概率（App-Bound FamilyMismatch → 引导登录兜底，16 §4.3/§4.4）。
- 新事实二（15 维度）：**快照版本失效机制**已内建——页面状态变化（导航/DOM 重写/布局变化/输入注入）推进 snapshotVersion，AI 持旧版本快照的动作校验失败 → 重快照（15 §5.1/§5.2）。此机制的事件源全部是 **CDP 浏览器级事件**（Page/DOM），不依赖面板输入转发层。
- 现状核对：Tauri 2 壳（Windows 默认 WebView2 主 webview，`apps/agent-workbench/src-tauri/Cargo.toml`），仓库无子 webview 使用先例；`agent-tools` 有 AbortToken（`context.rs:33-52`）、PermissionMode 三态（`permission.rs:18-27`）、审计 sink——复用面与维度 15 §4.1 描述一致。
- 结论分级：**维持否决 / 部分撤销（降级为受限登记项）/ 翻案**，各附权重变化（原否决的杀伤力在最终方案语境下还剩多少）。

## ① 逐否决项复审

### 1. WebView2 内嵌（否决项 A）

**原理由**（05 §2.1、06 §2.1、07 ②.1，汇总为三条）：
1. profile 格式与 Chrome 不互通 → 数据导入硬需求无法满足（复制路径被迫退到 storage_state，覆盖不全）；
2. CDP 受限子集、无稳定 SLA → 快照（DOMSnapshot/AX）与 Input 域执行依赖完整 CDP，可靠性押注在「可能变更」面上；
3. 与主应用共享 WebView2 运行时面 → 崩溃隔离与沙箱独立性弱于独立子进程。

**新事实（16 维度）**：
- 数据导入主路径 = 引导登录：登录动作完全发生在受管实例内部，cookie 由浏览器自行加密落盘，引擎与前端不接触、不复制 cookie 明文（16 §1.1 关键点）。该路径**零 profile 互通依赖**——WebView2 有自己的 user-data-folder 持久化目录，用户在其中登录 → cookie 落盘 → 重启保留（16 §1.4 的 Storage.getCookies 校验流程可原样套用）。**引导登录与 WebView2 完全兼容**，且 16 §1.1 要求的「账号/密码/2FA 走用户真实输入」在 WebView2 原生输入下天然满足。
- profile 复制已非主路径，且当前方案自身的复制路径就有失败概率（同家族约束 + 回读三分支，16 §4.3/§4.4），失败即引导登录兜底。也就是说：**当前方案里复制只是「尽力而为的便利路径」，WebView2 上该便利路径缺失，但硬需求（导入登录态）由引导登录 + storage_state 两条路继续满足**——缺失的是「从 Chrome 一键迁移存量登录态」的便利性，不是能力本身。

**结论**：
- 否决理由①：杀伤力从「方案级致命（3/3）」**降为「迁移便利性缺口（1/3）」**。部分撤销成立。但注意残余面：从用户日常 Chrome/Edge 迁移存量登录态时，WebView2 只能走 storage_state（无 sessionStorage/IndexedDB/SSO 弹窗态，16 §5.1 自认盲区）或引导登录（用户重输密码/2FA），体验劣于当前方案的「同家族复制 + 回读校验」（多数情况可读）。这是中等产品缺口，不再是方案级否决理由。
- 否决理由②：**维持，且是本次复审后 WebView2 否决的实质核心**（见 §③ 能力对照表）。理由重心修正：问题不在于「受限子集（假设）」而在于「**无 SLA + runtime 不可钉版本（事实）**」——当前方案对协议漂移的核心缓解是 CfT 版本钉死（09 D-1、04 §2 理由 3：版本钉死可审计、无自动更新、行为可控）；WebView2 Evergreen runtime 随系统更新，域行为漂移不可预知、不可回滚。若 Input 域实测不可用，输入转发方案整体死亡；若可用，仍有「下季度 runtime 升级行为漂移」的不可管理风险。选型期不应把 AI 操作可靠性押在「待实测 + 可能变更」的面上。
- 否决理由③：**降级为权衡项（1/3）**。事实核对：主应用 UI（React 前端）本身就运行在 Tauri 主 webview = WebView2（`apps/agent-workbench` 现状），「与 WebView2 runtime 共存」是主应用已接受的事实；子 webview 用独立 environment + 独立 user-data-folder 时进程树与主 webview 分开（03 §0/§1），渲染进程崩溃有 ProcessFailed 事件可接管重启（对齐维度 10 崩溃重启语义）。残余风险 = 共享 runtime 二进制 → runtime 升级面，与理由②同源。
- **综合：维持否决，但否决的实质依据从「①导入不互通 + ②CDP 受限」重构为「②CDP 无 SLA + 不可钉版本」单一主因；①③降级为功能缺口与权衡项。** WebView2 复合方案相对当前方案的具体对照见 §③。

### 2. 独立窗口直操（否决项 B）

**原理由**（09 D-2、09 §2 专项裁决、05 裁决 2、06 §2.6）：
- 用户输入绕过 CDP 控制面 → 「协同同屏断裂」「令牌机制失效」；04 方案自认检测源残缺（独立窗口拿不到用户键盘/鼠标输入，OS hook 才可，3 倍+）。

**新事实（15 维度版本失效机制）**：
- 版本推进事件源全部是 CDP 浏览器级事件：`Page.frameNavigated` 即时 +1、`DOM.documentUpdated` 200ms 聚合、布局变化（快照对比检出）推进（15 §5.1 表格）。这些事件**不依赖面板输入转发层**，独立窗口模式下同样可达。
- 用户操作分两类，版本机制覆盖情况不同（关键区分「感知」的两个层次）：

| 用户操作类型 | 独立窗口下的信号 | 版本失效覆盖？ | 面板转发模式下的信号（15 §5.1/§3.4） |
|---|---|---|---|
| 导航（点链接/地址栏） | `Page.frameNavigated` | ✅ 覆盖（事后） | 转发层信号 + 版本推进 |
| 点击按钮/表单提交（产生 DOM 变化） | `DOM.documentUpdated` / 布局变化 | ✅ 覆盖（事后，200ms 聚合） | 转发层信号 + 版本推进（即时） |
| 纯打字（value 为 property 非 attribute，不产生 DOM 结构变化） | **无 CDP 事件** | ❌ 盲区 | 转发层「用户输入注入成功 → 即时 +1」（15 §5.1） |
| 纯滚动（15 §5.1 明确「滚动不推进，靠 DOM 变化兜底」） | 无（懒加载除外） | ❌ 盲区（懒加载由布局变化兜底） | 转发层 wheel 注入 → 即时 +1 |
| hover / 拖拽未落点 | 无 | ❌ 盲区 | 转发层信号 → revoke + 版本推进 |

- 事中感知（吊销/abort）：吊销链的**信号源是面板输入转发层**（15 §3.4 触发链 ①「面板捕获原生用户事件」），独立窗口下该源不存在 → `revoke()` 永不触发（除 SessionEnd/急停按钮）→ `seq_abort.abort()` 不联动 → AI 在途动作（type 分块/慢速填表/wait_for）**执行到完成为止**。15 §3.4 ⑨ 的「吊销先于用户事件注入、杜绝同帧竞态」保证失效——因为不存在「用户事件注入」这一步。
- 令牌机制的残余价值：AI 侧的 `validate`（epoch 匹配）与执行后校验仍有效（防吊销后重获、防结果作废静默），但**吊销触发面退化为只有急停**。令牌不解决感知缺失——它消费信号，不生产信号。

**结论**：
- 「协同断裂」表述**不成立**——版本失效机制确实覆盖了「产生页面变化的用户操作」的事后感知（AI 下一个动作被 Stale 拒绝 → 重快照，15 §5.2/§5.3），AI 不会基于明显过期的页面无限操作下去。
- 但否决理由**核心成立且应维持**，理由修正为：**abort 抢断（四合一中的「事中中止」）依赖输入信号源，独立窗口下该源缺失 → 协同从「实时互斥 + 在途中止」降级为「乐观并发 + 事后重试」**；叠加两类盲区（纯打字/纯滚动/不产生 DOM 变化的输入不可感知）。用户接管体验（产品信任核心：用户一摸键盘 AI 立即停）受损，且 AI 在用户正在输入的字段注入内容的风险（04 方案仅以焦点检查部分缓解，独立窗口下焦点信息也需额外探测）无法根除。
- 残留问题（用户操作与 AI 在途动作竞态）**不由令牌机制解决**——令牌需要吊销信号，独立窗口无信号。唯一现实解法是注入感知桥（页面内监听回传，恢复信号源）或 OS hook（04 自认 3 倍+）。
- **维持否决（不翻案）**。若要翻案，翻案路径依赖注入桥恢复信号源，成本转移回否决项 C（见 §⑤ 路径 B）。

### 3. 注入脚本桥为主通道（否决项 C）

**原理由**（09 D-3、05 §2.2、06 §2.2）：注入桥合成事件 `isTrusted=false`（执行通道致命伤）；navigation 重注入/跨域 iframe/页面污染/CSP/可探测面 = 维护面 3 倍陷阱；04 方案（维度 3 d）以「协议自研 3 倍+」否决注入桥通道。

**新事实（15 维度「事件总线 + 快照」已内建）**：快照版本失效依赖 CDP 浏览器级事件（§② 已论证），不依赖注入桥；面板转发模式下用户输入感知免费（转发层信号）。

**分通道评估**（核心：注入桥的「执行通道」与「感知通道」代价不同，必须分开审判）：

| 评估项 | 作为执行通道（合成事件执行点击/输入） | 作为感知通道（只读监听：输入/变化 → 回传） |
|---|---|---|
| isTrusted | **致命**：合成事件 untrusted，登录/支付站点拒绝（03 §5 理由 2 自认）；hover 态/原生事件顺序不可复现 | 不适用（只读上报不合成事件） |
| 与 CDP Input 的关系 | 与「AI 输入走 CDP Input 真实注入」（08 §3.5）重复且劣化 | 与版本机制**互补**：版本覆盖「页面变化」，感知桥覆盖「输入级事件」（打字/hover/滚动盲区） |
| 维护面（重注入/iframe/CSP/探测面） | 全量保留 | 保留，但减去「事件合成 + 与 CDP 一致性」约一半 |
| 在当前方案下的价值 | **零**（独立 Chromium CDP 完整，P0-1 验证注入可信事件） | ≈ 零增量（面板转发免费信号已覆盖输入级感知） |
| 在翻案模式下的价值 | 无（依旧不成立） | **唯一现实路径**（独立窗口/WebView2 原生输入时，OS hook 3 倍+） |
| 代价评级 | **3 倍维持** | **3 倍 → 1-2 倍**（只读监听 + 重注入管线 + 回传通道；skyvern domUtils 模式为参考，06 §2.2） |

**结论**：
- 执行通道：**维持否决**（isTrusted + 与 CDP 重复 + 3 倍代价，无任何新事实改变此判定）。
- 感知通道：**部分撤销**——从「否决注入脚本桥（整体）」修正为「否决注入桥作为执行通道/主通道；**注入桥作为感知增强登记为受限选项（默认关）**」。当前方案（面板转发）下不启用（免费信号已覆盖）；仅当翻案为独立窗口/WebView2 原生输入模式时启用（恢复吊销信号源 + 补盲区）。注意：07 评审 §②.2 已如此裁决（「注入事件桥默认关（可选增强）」），但最终敲定文档 09 D-3 与总文档 08 未显式保留该登记——本复审要求补登记（见 §⑤ 路径 C）。

### 4. 截图轮询（否决项 D）

**原理由**（05 裁决 2 / 09 D-2）：帧率个位数、延迟数百毫秒，无法承载手输文字，体验不达标。

**新事实**：无——最终方案未改变帧渲染要求（08 §3.3 screencast 帧流 8-15fps、P0-2 ≤120ms；截图按需仅作调试回显，13 维度）。截图轮询既不能满足交互帧率（>120ms 目标），也不能承载输入转发（无真实输入语义）。

**结论**：**维持否决，无新事实冲击。** 唯一补充：截图轮询在最终方案中的定位与 13/08 一致——「按需截图（调试回显/视觉模型就绪后）」，此定位已实现，无需变更。

## ② WebView2 复合方案对照（输入延迟/IME/复杂度/沉浸感）

WebView2 内嵌 + 原生输入 +（CDP 或注入感知）复合方案 vs 当前方案（screencast + 面板输入转发）：

| 维度 | 当前方案 | WebView2 复合方案 | 相对结论 |
|---|---|---|---|
| 用户输入延迟 | 帧渲染 + 转发双跳（P0-2 待验证，目标 ≤120ms，08 §3.3） | 零转发（原生 webview 直接命中） | **WebView2 优** |
| 中文 IME | 隐藏输入框桥接（12 维度，P0-3 高风险项） | 原生 IME（P0-3 风险面整体消失） | **WebView2 优** |
| 沉浸感/跟手 | 帧流 8-15fps 显示（交互期升帧） | 原生渲染，零丢帧 | **WebView2 优** |
| 用户输入感知 | 转发层免费信号（15 §3.4 触发链，零成本） | 无免费信号：版本事件（事后）+ 可选注入感知桥（1-2 倍） | **当前方案优** |
| AI 输入（CDP Input） | P0-1 验证可信注入；CfT 钉版本 | 同命令，但域可用性与行为随 Evergreen runtime 漂移（无 SLA） | **当前方案优** |
| 帧流管线（canvas/帧率控制/ack pacing） | 12 维度一整维实现 | 不需要（原生渲染） | **WebView2 省一整维** |
| 子 webview 管理 | 无 | z-order/焦点/DPI 坑（03 §1 自认） | **当前方案优** |
| 崩溃隔离/进程面 | 独立 Chromium 进程 + 沙箱 | 共享 WebView2 runtime 二进制；environment 隔离进程树 | **当前方案优** |
| 版本可控性 | CfT 版本钉死（09 D-1） | Evergreen 不可钉 | **当前方案优（决定性）** |
| 跨平台 | 单后端三平台同一代码（05 裁决 1） | Windows WebView2 + 其他平台 Chromium 双后端 | **当前方案优** |
| 参考资产复用 | browser-use/chrome-devtools-mcp/agent-browser 100% 复用 | 零复用 | **当前方案优** |
| 复杂度 | 1-2 倍（S0 验证后收敛，09 §5） | 省帧流/转发，但增双后端 trait + 子 webview 管理 + 感知面补充；相对当前方案净 ≈ -0.5 ~ +0.5 倍 | 接近打平，省的是体验层、加的是可靠性与跨平台层 |

**综合结论**：WebView2 复合方案的强项（输入/IME/沉浸感）**恰好落在当前方案的风险面**（P0-2 帧延迟、P0-3 IME）；其弱项（CDP SLA/跨平台/参考资产）**恰好是当前方案的强项**。维持否决的实质依据是「② CDP 无 SLA + 不可钉版本」——这一条在当前方案的 CfT 钉版本缓解下是可管理的风险，在 WebView2 下是不可管理的风险。**若 P0-2/P0-3 实测不达标，WebView2 复合方案（Windows 专案）比 05 裁决 1 的「HWND 嵌入 P1」更完整的备选**（HWND 嵌入仍需保留帧流给 AI 侧/高亮叠加，WebView2 直接免帧流）——登记为 P1，且须以 S0 WebView2 CDP 实测为前提（见 §⑥）。

| Storage.*（getCookies/DOMStorage） | storage_state 导出（16 §5.2）、重启保留校验（16 §1.4） | 预期可用 | 待实测 |
| Target.* | 多标签（15 §7.1） | 预期可用 | 待实测 |

**读法**：能力表的「待实测」项决定了复合方案能否成立，而「无 SLA + Evergreen 不可钉版本」是**无论实测结果如何都存在**的结构性风险——这正是维持否决的硬核。快照（Runtime/DOM/Accessibility）域若实测可用，则「快照用 DOM/Runtime 域是否足够」的答案是：足够覆盖感知面（当前方案快照主链路本就依赖 DOMSnapshot/AX，这些是 DevTools 基础功能）；真正的生死项只有 Input 域——它与「输入转发方案」绑死，无降级余地。

## ④ 独立窗口直操复审（补：否决理由逐条对账）

| 原否决表述 | 复审裁定 | 依据 |
|---|---|---|
| 「用户输入绕过 CDP 控制面」 | ✅ 事实成立 | 无转发层即无信号源（15 §3.4 触发链 ① 缺失） |
| 「协同同屏断裂」 | ⚠️ 表述修正 | 版本失效机制提供「事后感知」（15 §5.1），AI 不会无限基于过期快照操作；断裂的是「事中中止」而非全部协同 |
| 「令牌机制失效」 | ⚠️ 表述修正 | 令牌的校验/epoch 语义仍有效；失效的是「吊销信号生产」（revoke 永不触发），abort 抢断退化为仅急停可用 |
| 「04 检测源残缺（OS hook 才可，3 倍+）」 | ✅ 维持 | 无新事实推翻；版本事件仅覆盖页面变化类，输入级盲区仍在 |

**裁决：维持否决**。翻案条件明确为「注入感知桥恢复吊销信号源 + 焦点探测」，成本 1-2 倍 + 维护面，且换取的是产品信任体验降级下的「独立窗口」形态——不划算，不作翻案。

## ⑤ 最终立场（维持/翻案清单 + 最小修正路径）

### 5.1 清单

| # | 否决项 | 立场 | 说明 |
|---|---|---|---|
| 1 | WebView2 内嵌 | **维持否决**（理由重构） | 否决实质从「①导入不互通 + ②CDP 受限」重构为「**② CDP 无 SLA + Evergreen 不可钉版本**」单一主因；①降级为迁移便利性缺口（1/3），③降级为权衡项（1/3） |
| 2 | 独立窗口直操 | **维持否决**（理由修正） | 「协同断裂/令牌失效」修正为「abort 信号源缺失 → 实时互斥降级为乐观并发 + 事后重试；输入级盲区存在」；版本失效机制覆盖事后感知，故表述修正但不翻案 |
| 3 | 注入桥执行通道 | **维持否决** | isTrusted=false + 与 CDP Input 重复 + 3 倍代价，无新事实冲击 |
| 4 | 注入桥感知通道 | **部分撤销**（登记为受限选项，默认关） | 代价 3 倍 → 1-2 倍；当前方案下增量 ≈ 0，翻案模式下是唯一现实路径；07 §②.2 已如此裁决但 09 D-3 未保留，需补登记 |
| 5 | 截图轮询 | **维持否决** | 无新事实；「按需截图」定位已在 13/08 实现 |

### 5.2 最小修正路径（若推翻/若启用备选）

- **路径 A（WebView2 复合方案 → P1 备选，不推翻现案）**：触发条件 = P0-2（帧延迟）或 P0-3（IME）实测不达标。改动面 = 渲染层替换（帧流 + 输入转发 → Tauri 子 webview + 原生输入）+ 感知层补充（版本事件 + 可选注入感知桥）+ 双后端 trait（03 的 BrowserController 复活，Windows 条件编译）；**复用面为零**——CDP 客户端（11 维度）、快照（13）、动作（14）、协同（15）、导入（16 §1 引导登录原样套用，managed profile 目录语义 → WebView2 user-data-folder）、安全（17，token/门禁/审计全复用）。复杂度增量 ≈ +0.5 倍。前提：S0 固化 WebView2 CDP 实测（见 §⑥）。
- **路径 B（独立窗口翻案 → 不建议）**：需注入感知桥（只读监听，恢复 revoke 信号源）+ 焦点探测（防向用户输入字段注入）；令牌机制降级为「事件驱动吊销」（受注入桥可靠性与重注入窗口影响，导航瞬间存在信号空洞）。若产品坚持「大屏独立窗口」，登记为「面板 + 独立窗口双模式，独立窗口默认关」。
- **路径 C（注入桥感知通道登记 → 文档层补登记，零代码影响）**：09 D-3 加注「注入桥仅作感知增强登记（默认关），启用条件 = 独立窗口/WebView2 原生输入模式」；08 §3.2 或 15 §5.1 补「版本推进（浏览器级事件）与感知桥（输入级事件）的互补边界」。此修正使 07 评审已裁但未落地的结论回到文档权威面。
