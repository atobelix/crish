# 红队审计：隐含假设与过度设计（RT-3）

> 角色：红队 Agent RT-3（隐含假设审计）
> 审计对象：S0-S10 实施链、9 维度文档（10-18）、40 项裁决（22）
> 视角：最少可行产品（MVP）。唯一目标 =「软件内 AI 操作浏览器、用户可见、可共同操作」。
> 输出：隐含假设清单 → 40 项裁决分类 → MVP 切片 → 复杂度红线复核 → 最终立场。
> 纪律：只写本文件；其余文档只读。

---

## 0. 一句话结论

方案是**自洽但超重**的：核心产品假设（同屏双向协同）被当成了需求本身，而它实际是体验增强；由此派生出的多标签（R-1 per-tab 版本）、输入转发全套（帧渲染/IME 桥/虚拟指针）、导入全家桶（书签/历史/复制迁移/storage_state）、evaluate 安全工程，四块在 MVP 目标下全部可砍或可降级——砍完后 S0-S10 缩为 9 步，且 40 项裁决中约 21 项（52%）的「文档自洽修补」不再需要发生。

## 1. 隐含假设清单（假设 → 证据 → 判定）

### H-1 「用户必须与 AI 同屏操作同一个浏览器」（D-2 面板帧渲染 + 输入转发）

**证据**：08 §1.1 目标「用户可随时手动操作、接管同一实例（双向协同）」；D-2 裁决（09 表 1）否决独立窗口直操；09 §2 专项裁决「面板输入转发是协同闭环的必要条件，独立窗口直操使 AI 无法感知用户操作，令牌机制失效」。

**审计**：这个假设由三件东西拼成：①用户可见（AI 做了什么）②用户可接管（打断 AI）③**AI 可感知用户操作**（用户动过什么，AI 继续干不冲突）。①② 是功能必需，③ 是精细协同假设——没有一条用户研究/需求文档验证用户真的需要「AI 感知我每一次点击」，更轻的满足方式：

| 需求面 | 方案（面板+转发） | 更轻替代 |
|---|---|---|
| ① 用户可见 | screencast 帧流 → canvas | **受管实例以可见窗口运行**（headed），AI 操作窗口自然在前台；或面板只读回放（低帧率，无需输入转发） |
| ② 用户可接管 | 输入转发 + 令牌吊销链 | 窗口直操 = 天然接管；AI 动作前版本校验（用户操作引起的 DOM 变化/导航已推进版本 → 重快照）兜底 |
| ③ AI 感知用户操作 | 面板事件 → 吊销链 | **MVP 不承诺**。粗粒度协同（动作前校验 + 每次动作后重快照）即可 |

**判定：部分推翻**。输入转发是「精细双向协同」的必要条件，但精细协同是增强项不是 MVP 必需。screencast 帧流 + 媒体 WS + 输入归一化 + IME 桥 + 虚拟指针 + 坐标映射（维度 12 整块）是方案中最大的复杂度块；MVP 采用可见窗口 + 版本失效兜底，面板交互推迟二期。D-2 否决独立窗口的核心理由（令牌失效）只在承诺③时才成立——MVP 不承诺③。

### H-2 「多标签页」（MAX_TABS=8、per-tab 版本、预算分摊）

**证据**：08 §3.6 多标签；15 §7.1-7.3（MAX_TABS=8、INACTIVE_BUDGET_FACTOR=0.25、8MB LRU、事件订阅分摊）；**R-1 裁决（22 §1）per-tab version 四文档联动**；M-9（15 §7.3 预算分摊）。

**审计**：多标签的全部理由（15 §7.3 裁决依据）是「调研 3-5 标签、电商比价 3-4、对照编辑 2」——这是**对典型任务的臆测**，不是验证过的用户画像。多标签的直接代价：

- R-1（per-tab 版本 + global_epoch + 跨标签事件隔离）是 22 号文档「高严重度」裁决，牵动 11/13/14/15 四份文档的接口签名；
- TabRegistry、标签切换吊销（15 §7.2）、非活跃降级订阅、预算分摊 2.75 单位、`tab.limit_exceeded` 错误码（U-12）——一组自洽但昂贵的机制；
- 会话恢复（H-3）的复杂度几乎全部由多标签派生。

**判定：推翻（首版）**。单标签 MVP 下版本号退化为会话级单值（正是 R-1 否决的形态——对单标签它完全够用），R-1/M-9/U-12 整项消解。多标签推迟二期，与「AI 完成单任务」的首版定位一致。

### H-3 「会话恢复 / 导航栈恢复」（崩溃重启保留标签）

**证据**：10 §6.4（nav_stack.json、崩溃自动重启、P0-6 验收锚点）；15 §8.1-8.3（持久化开关、PanelStateSnapshot、三级回退）；R-2（sessions/managed 双层目录 + trash 语义）；U-7（崩溃快照 vs 会话恢复分工）；16 §7（profile_meta/persist）。

**审计**：拆成两件事——

1. **崩溃自动重启**：进程可靠性，必须保留（P0-6）。但「保留导航栈」在单标签下 = 恢复一个 URL（内存里有 last_url），nav_stack.json + 多标签恢复 + 三级回退全部不需要。
2. **会话持久化（persist 开关）**：登录态保留有真实价值（引导登录后重启不重登），但实现被做成了双层目录（sessions/ 临时 + managed/ 受管 + staging 原子化 + trash/直删双路径 + U-11 消除运行时迁移）——一套**删除策略的完备性工程**，与「保留登录态」这个需求之间隔着两层抽象。

**判定：部分推翻**。崩溃重启保留（降级为单 URL 恢复）；面板状态恢复（标签/URL 序）随多标签推迟；持久化保留「persist 开关 + 单层 profile 目录」，R-2 的双层分层与 trash 语义延后到多标签/受管资产场景再说。

### H-4 「导入完整用户数据」（书签/历史直读导入、profile 复制迁移、storage_state）

**证据**：08 §3.7（书签 JSON + 历史 SQLite 独立入口）；16 §2-§6（discovery 三平台路径表、copy 白名单复制 + 锁检测 + staging 原子化、verify 回读三分支 + App-Bound 判定、storage_state 导出/导入、bookmarks.rs/history.rs + conex-db 新表 + WebKit 时间戳换算）；P0-4（App-Bound 实证仍为待验证项）。

**审计**：方案自己已声明主路径 = 面板内引导登录（16 §0.1，零解密零隐私面）。在引导登录主路径下逐项算账：

- **书签/历史导入**：新表（conex-db）、SQLite 只读辅助、时间戳换算、去重合并、向导三步——AI 协同场景下用户可以直接地址栏输入/让 AI 搜索，边际价值低。**砍，推迟二期。**
- **profile 复制迁移**：App-Bound 加密兼容**仍是待验证假设**（P0-4 未实证、08 §7 风险表列「高」）——为一套成功率不确定的路径投入锁检测、staging 原子化、回读三分支、同家族矩阵、向导 UI，是典型的「为自洽而修补」。**砍，推迟二期，且以 P0-4 实证结果为立项前提。**
- **storage_state 导入/导出**：标准 JSON + 内存传递 + 双确认授权——在引导登录面前是第三备胎。**砍，推迟二期。**

**判定：推翻（首版）**。数据导入 MVP 只保留引导登录 + persist 开关。16 维度 9 个文件砍剩 1-2 个。

### H-5 「evaluate 受限白名单」（首版需要 JS 求值能力）

**证据**：17 §3（__crish_read 白名单代理 + 三层校验 + constructor 链检查 + isolated world）；R-6（22 §1，撤销双轨、唯一设计）；U-8（富文本/图片粘贴**已砍**，仅保留纯文本 insertText + 文件路径兜底）；17 §2.3（evaluate capability 默认关，任何模式 Deny）。

**审计**：关键事实——**evaluate 在默认配置下就是不可用的**（capability 未开 → 全模式 Deny，17 §2.3）。方案为一把默认上锁的枪配了完整安全工程（静态词法 + 隔离世界 + 运行时 constructor 链检查 + 结果预算），而首版核心用例（导航/点击/输入/滚动/快照）没有一个依赖它：

| evaluate 声称的场景 | 实际依赖 |
|---|---|
| select_option | `DOM.resolveNode` + `Runtime.callFunctionOn`（CDP 原语，非 evaluate 工具） |
| 拖放路径 B（drop zone） | 构造 DataTransfer 派发 drop——首版可返回「请手动操作」（路径 A 已覆盖 file input 场景） |
| 文件路径粘贴兜底 | 首版砍掉，手动粘贴 |
| 快照滚动位置/监听器探测 | 引擎内置白名单表达式（T-4 监听器探测本就默认关闭），不经工具层 evaluate |

**判定：推翻（首版）**。工具面 `browser_evaluate` 整块推迟二期。砍掉后 R-6 整项（22 号文档最复杂的安全设计）、SensitiveCapabilities.evaluate、三层校验实现、eval 逃逸测试面全部消解，且**安全性净提升**（无求值面 = 无求值漏洞）。

### H-6 「外部 MCP attach 同一端点」（S9）

**证据**：08 §3.8/§4 S9（MCP 经 --browserUrl attach）；17 §5.2-5.3（只读能力集 R-12、会话级开关、命名空间隔离）；R-12。

**审计**：价值 = 「获得生态深工具（调试/性能）」。但 chrome-devtools-mcp 类工具本身就能连任何浏览器，用户完全可以在自己的日常浏览器上跑调试工具；attach 到受管实例的增量价值 = 让外部工具看到 AI 正在操作的页面——**低频场景**。代价：会话开关、启动参数注入、只读能力集强制（R-12 又是一轮安全修补）、命名空间验证。**判定：推翻（首版）**，S9 推迟二期，R-12 随之消解。

| # | 假设 | 证据 | 判定 |
|---|---|---|---|
| H-7a | 帧延迟 ≤120ms 是硬指标 | P0-2、08 §5 | 只对交互式面板成立；MVP 窗口方案/只读回放下 120ms 不再是门禁 |
| H-7b | 「崩溃 30s 内 3 次重启上限」等可靠性参数需要完整状态机 | 10 §6.4 | 保留（进程管理本来就该做），但单标签下状态机分支减半 |

## 2. 40 项裁决分类（R-1~R-12 + U-1~U-12 + T-1~T-16）

> 分类口径：**A** = 真问题修补（提升正确性/安全）；**B** = 文档自洽性修补（只为消除跨文档矛盾，不提升产品）；**C** = 过度设计（增加复杂度但边际价值低）。

### 2.4 汇总

| 系列 | A 真问题修补 | B 文档自洽 | C 过度设计 |
|---|---|---|---|
| R（12） | 8 | 2 | 2 |
| U（12） | 3 | 9 | 0 |
| T（16） | 6 | 10 | 0 |
| **合计（40）** | **17（42.5%）** | **21（52.5%）** | **2（5%）** |

**结论**：半数以上裁决（B 类 21 项）是跨文档协调成本——它们不是坏决策，而是**方案规模膨胀的直接税**：9 份文档 × 多轮评审 × 每处参数要全局唯一，必然产生大量「消除矛盾」劳动。C 类虽只有 2 项，但 R-1 是最高杠杆：它牵动 4 份文档、为 H-2 服务，MVP 砍多标签即整项消解。**若按 §3 砍到 MVP，预计 B/C 类裁决中约 12 项不再需要发生。**

## 3. 最小可行切片（MVP）

**唯一目标**：软件内 AI 操作浏览器；AI 操作用户可见；用户可打断/可共同操作（粗粒度）。

### 3.1 必须保留（最小集）

| # | 模块 | 来源 | 保留理由（MVP 口径） |
|---|---|---|---|
| M1 | 受管 Chromium 实例（CfT/系统回退、随机端口、隔离 profile、崩溃自动重启-恢复单 URL） | 10（简化） | 承载全部操作，隔离 profile 是安全底线；崩溃重启是可靠性 |
| M2 | 自研 CDP 薄客户端 + 单长连接 + 事件总线（会话级版本号） | 11（简化） | 单通道原则 + 审计/急停挂点；版本号退化为会话级单值（砍 R-1 per-tab） |
| M3 | 可见性：**headed 可见窗口 + 指示条/状态条**（或只读低帧率回放，二选一） | 12（替换） | 用户可见 = 窗口在前台/面板回放；**不做输入转发、不做媒体 WS、不做 IME 桥、不做虚拟指针** |
| M4 | 感知快照：DOM 简化树 + AX 辅助 + 预算截断（单标签） | 13（简化） | AI 操作的前提；砍 getEventListeners 通道（T-4 已默认关）、绘制序过滤可关、closed shadow 降级（T-5 保留） |

## 5. 最终立场

**对方案**：架构主线（受管独立实例 + CDP 单通道 + 自研客户端 + 结构化感知优先 + 复用 agent-tools 安全面）是正确的，D-1/D-3/D-4/D-5/D-9 五个决策维持。但方案把**体验增强当成了需求**，为「完整产品」而不是「验证产品」设计：

1. **最大的隐含假设是 H-1**（同屏双向协同）：它派生了维度 12 整块 + R-10 + 令牌吊销链的精细形态。MVP 用可见窗口 + 版本失效兜底即可达成「用户可见、可共同操作」的粗粒度闭环，且完全兼容二期升级到面板方案（窗口方案与面板方案共享实例与快照，只差一层渲染与转发）。
2. **第二大的隐含假设是 H-2**（多标签）：R-1 的 per-tab 版本是方案里牵动最广的裁决，砍多标签后版本机制、预算分摊、标签恢复、tab 错误码一起消解。
3. **导入全家桶（H-4）与 evaluate（H-5）是纯增重**：一个把 0.3 倍的主路径做成了 3 倍模块（唯一超标项），一个为默认关闭的能力配了全量安全工程。
4. **40 项裁决的构成本身就是证据**：52% 的裁决是文档自洽性修补——一套设计评审体系运转良好的标志，但也说明方案文档量已到「维护成本 > 设计收益」的拐点。砍到 MVP 后重新跑一轮评审，预计 B 类裁决需求减半。

**给主 Agent 的建议（按收益排序）**：
1. 首版按 §3.1 的 8 模块落地，实施链 M0-M8；
2. S0 spike 砍掉帧延迟 120ms 与 App-Bound 两项未实证门禁（前者随输入转发推迟，后者随复制迁移推迟）；
3. 将「复杂度红线」从决策否决工具升级为**内部模块收敛工具**，先用于快照（13）与导入（16）；
4. 二期立项按 §3.2 清单排序，第一个立项项是「面板输入转发 + 精细协同」——它才是产品差异化的真正所在。
