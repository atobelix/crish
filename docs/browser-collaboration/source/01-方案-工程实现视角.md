# 软件内 AI 协同浏览器 — 全局选型方案（工程实现视角）

- 视角：工程实现（落地可行性 / 依赖成熟度 / 构建复杂度 / 可测试性）
- 产出：2026-08-08，Agent 独立完成，仅此一份
- 复杂度标注约定：**常规**（业界标准做法）/ **1-2 倍**（需自研或集成复杂度高于常规）/ **3 倍+**（直接放弃）

---

## 0. 一句话结论

> **在 Tauri 壳内启动独立 Chromium 进程（spawn chrome.exe --remote-debugging-port），CDP 作为唯一 AI 控制通道，画面用 CDP screencast 流式渲染到 React 面板（Windows 可选 HWND 嵌入优化）；Rust 侧自写最小 CDP 客户端（不引 chromiumoxide），快照算法移植 browser-use 的 DOM 简化树（clickable 检测 + paint order + backend_node_id index）；Chrome profile 整目录复制实现登录态导入；browser_* 工具族挂 agent-tools 注册面走既有审批/审计管线；Computer Use 作为独立二期 crate 与浏览器线并行。**

复杂度总体评估：主链路约为「常规 iframe 方案」的 **1-2 倍**，无任何 3 倍+ 项；相比全自研渲染引擎（CEF 嵌入）低一个数量级。

## 1. 渲染实例：独立 Chromium 进程嵌入（screencast 流）为主

### 1.1 候选对比

| 候选 | 渲染保真 | 操作第三方页面 | 登录态导入 | CDP 完整性 | 构建/维护复杂度 | Windows/mac/Linux 一致性 |
|---|---|---|---|---|---|---|
| A. Tauri 子 WebView2 | 高（Edge 内核） | 可 | 差（user data 格式与 Chrome 不兼容） | **受限子集**（微软标注 API 可能变更） | 常规（wry 多 webview 需自绘布局） | 仅 Windows；macOS 用 WKWebView 差异巨大 |
| B. 独立 Chromium 进程 + screencast 流 | 高（真 Chrome） | 可 | **优（--user-data-dir 直用）** | **完整** | 1-2 倍（自管进程生命周期 + 视频帧解码） | 三平台统一（同一套 CDP/screencast 逻辑） |
| C. iframe 改造（现状 PreviewCard） | 中 | **不可**（X-Frame-Options/CSP/sandbox 限制） | 不可（三方上下文无 cookie） | 无 | 常规 | 统一 |
| D. CEF（cef-rs 替换 wry） | 高 | 可 | 可 | 完整 | **3 倍+**（Windows 上 C++/native 构建链，跨平台铺开成本爆炸） | 差（CEF 官方放弃非 Win/mac 主力维护，Linux 需自行编译） |

### 1.2 结论与理由

**选 B**：独立 Chromium 进程嵌入，画面主走 CDP screencast（`Page.startScreencast`），Windows 上可追加 HWND 嵌入（`SetParent`）作低延迟优化。

理由（工程视角逐条）：
1. **复用所有参考资产**：browser-use（`browser_use/browser/session.py` 用 cdp_use 直连 CDP）、agent-browser（Rust CDP daemon + dashboard screencast 流）、chrome-devtools-mcp（attach/launch 双模式）全部建立在「独立 Chromium + CDP」之上，无一行代码可复用于 WebView2。
2. **登录态导入是硬需求**：Chrome/Edge profile 的 `--user-data-dir` 直用是唯一零成本路径（browser-use `profile.py` 的复制方案，见 §7）。WebView2 有自己的 user data folder 格式，与 Chrome profile 不互通（候选 A 的硬伤）。
3. **CDP 完整性**：WebView2 的 DevTools 协议是受限子集（微软文档明确「部分命令不支持、API 可能变更」），而快照算法（`Accessibility.getFullAXTree` / `DOMSnapshot.captureSnapshot`）与 Input 注入都要完整 CDP。
4. **跨平台一致性**：screencast 是纯 CDP 层方案，三平台同一套 Rust 代码；HWND 嵌入只作为 Windows 增强（可延迟到二期）。macOS/Linux 无 SetParent 等价物，故不把 HWND 嵌入作为主路径。
5. **否决 A 的附加理由**：Tauri 2 多 webview 布局需自绘原生合成，且 WebView2 runtime 为独立组件，用户机器缺失时体验不可控。
6. **否决 D（CEF）**：Windows 上引入 Chromium 自编译/二进制分发链，macOS/Linux 支持差，复杂度远超 3 倍红线。

降级策略：Chrome/Edge 均未安装时，引导安装或使用 Chrome for Testing 自动下载（agent-browser `install` 命令同款，`cli/src/install.rs`）。

**复杂度：1-2 倍**（进程管理 + 帧流渲染是主要增量；无 3 倍项）。

## 2. AI 控制通道：CDP 单轨

### 2.1 候选对比

| 候选 | 实现面 | 覆盖面 | 风险 | 与 §1 的耦合 |
|---|---|---|---|---|
| A. CDP（完整协议） | WebSocket JSON 命令/事件 | 快照/输入/导航/网络/截图全量 | 需自己管 session 与事件分发（见 §3） | 与「独立 Chromium」天然匹配 |
| B. 注入脚本桥（content script + postMessage） | 页面内注入 JS | 仅同源可控页面；第三方页面受 CSP/sandbox 阻断 | 注入被页面 CSP 拒、检测到自动化特征 | 与 iframe（候选 C）绑定，随 §1 决策失效 |
| C. 双轨（CDP + 注入） | 两者都做 | 全量 + 页面内 hook | 维护两套控制面，状态一致性难保证 | 需两条渲染路径 |

### 2.2 结论与理由

**选 A：CDP 单轨**。§1 已选定独立 Chromium，CDP 完整可用，注入桥的动机（绕 WebView2/iframe 限制）不复存在。browser-use（`session.py` 的 CDPSession/Target 模型）、agent-browser（`cli/src/native/cdp/`）、skyvern（`webeye/cdp_connection.py`）三家均以 CDP 为唯一控制面，佐证该路线成熟。

注入脚本仅在「用户操作旁路检测」（页面内监听 `pointerdown` 作为协同冲突信号，§6）时作为**可选增强**，不作为控制通道，不做双轨维护。

**复杂度：常规**。

## 3. Rust CDP 客户端：自写最小客户端（借鉴 agent-browser）

### 3.1 候选对比

| 候选 | 依赖成熟度 | 覆盖面 | 可控性/可测试性 | 风险 |
|---|---|---|---|---|
| A. chromiumoxide | 中（0.7.x，维护活跃度中等，大版本 API 破坏史） | 类型化覆盖不全，新 domain 需手写 | 低（类型系统绑定自身节奏） | 上游停滞即被锁死；版本升级成本高 |
| B. 自写最小客户端（WS + id/pending map + broadcast 事件） | —（tokio-tungstenite + serde_json，均为顶级成熟依赖） | 只写本方案用到的 domain（~8 个） | 高（纯 Rust 单测 300+ 可行，agent-browser 已验证 320 单测） | 事件类型需自建模（工作量可控） |
| C. 外包进程（复用 agent-browser / chrome-devtools-mcp 二进制 daemon） | 高（现成） | 全量 | 低（跨进程 IPC、schema 版本绑定外部二进制） | 分发/版本/安全审计不可控；多一层进程间协议 |

### 3.2 结论与理由

**选 B：自写最小客户端**，直接借鉴 agent-browser `cli/src/native/cdp/client.rs`（436 行）：`ws_tx + next_id(AtomicU64) + pending: HashMap<u64, oneshot::Sender> + event_tx: broadcast::Sender`，reader 循环分发响应/事件（client.rs:29-150），附 keepalive ping（WS_KEEPALIVE_INTERVAL_SECS=30）与取消清理守卫（PendingGuard，client.rs:48-71）。

理由：
1. **铁证可落地**：agent-browser 的 Cargo.toml（cli/Cargo.toml:13-37）不依赖任何 CDP 库，仅 tokio-tungstenite + serde_json + futures-util，产出 320 单测 + 18 e2e（AGENTS.md 测试节），证明自写路线工程量可控、可测试性极佳。
2. **chromiumoxide 否决**：其类型化 domain 覆盖与上游维护节奏不可控，且本项目只需 Browser/Target/Page/Runtime/DOM/Accessibility/Network/Input/Session 约 8 个 domain，用库反而被其抽象约束（session 生命周期、事件类型都要迁就库的建模）。
3. **可测试性**：CDP 层可对 mock WS 服务端做单元测试（agent-browser 已有 `127.0.0.1:0` mock listener 先例，browser.rs:2627）。
4. **审计/安全可控**：自写层可在统一入口做命令白名单与审计钩子（§9）。

**复杂度：1-2 倍**（vs 直接引库为常规；自写约 1500-2500 行含类型建模）。

## 4. 感知快照：DOM 简化树（browser-use serializer 移植）为主，AX 辅助，视觉按需

### 4.1 候选对比

| 候选 | 信息密度 | Token 效率 | 定位可用性 | 实现成本 | 代表实现 |
|---|---|---|---|---|---|
| A. AX 树（Accessibility.getFullAXTree） | 中（缺布局/文本细节） | 高 | 中（靠 AX 属性重定位） | 常规 | agent-browser snapshot.rs:313-319 |
| B. DOM 简化树（DOMSnapshot.captureSnapshot + getContentQuads + AX 补充 + paint order） | **高**（含 bounds/可滚动/复合控件/可见文本） | 中（经 paint order/bbox 过滤后可接受） | **高（backend_node_id 直作 index）** | 1-2 倍 | browser-use `dom/serializer/serializer.py` |
| C. 视觉混合（滚动截图 + 坐标） | 高（像素级） | 低（截图占 context） | 中（坐标点击，需缩放） | 1-2 倍 | skyvern（webeye/browser_state.py 滚动截图）、computer-use |

### 4.2 结论与理由

**选 B 为主，A/C 为辅**：快照主体移植 browser-use serializer 管线（serializer.py:110-161 的五步流水线），AX 树用于补充复合控件属性与表单当前值（serializer.py:1230-1267），截图（`Page.captureScreenshot`）作为按需工具（vision 模式，agent-provider 已具备 `supports_vision` 能力位 catalog.rs:127 与 `image_url` 多模态 part messages.rs:61）。

移植要点（证据与理由）：
1. **clickable 检测**：`ClickableElementDetector.is_interactive`（clickable_elements.py:6-200）——CDP JS 事件监听器检测（`has_js_click_listener`，覆盖 Vue/React onClick）、interactive_tags 白名单、ARIA role 集合、label/span 包装表单控件识别、search 类名启发式。这是 browser-use 多年调优的核心资产，**逐条移植而非重写**。
2. **paint order 过滤**：`PaintOrderRemover`（paint_order.py:146）+ RectUnion 矩形并集，剔除被覆盖文本/元素（modal 遮挡场景）。
3. **bbox 传播过滤**：`_filter_tree_recursive`（serializer.py:785-820）——a/button/combobox 的 bounds 向下传播，99% 包含阈值剔除嵌套冗余（例外：表单控件/带 aria-label/带 role 的保留）。
4. **index 分配**：`_allocate_selector_index`（serializer.py:645-654）——**backend_node_id 直接作模型 index**，碰撞时用 synthetic index（`_reserve_backend_node_ids` 先遍历登记）。这是定位可靠性的关键：index → `DOM.resolveNode(backendNodeId)` → 精确命中，无需模糊匹配。
5. **shadow DOM 支持**：serializer.py:463-473（fragment 节点递归）、复合控件虚拟化（input range/number/color/file、select options、details、audio/video，serializer.py:163-347）。
6. **iframe 跨域**：逐 frame 独立 session 采集（agent-browser snapshot.rs:591 `resolve_iframe_frame_id` 同款思路），上限 max_iframes=100 / 深度 5（profile.py:668-676）。
7. **密码脱敏**：password 字段的 value/valuetext 禁止入快照（serializer.py:1220-1227），对接 §9 安全基线。

**复杂度：1-2 倍**（算法移植是最大工程项，但全部有参考实现可抄，无未知研究点）。

## 5. 元素定位与操作执行：index 定位 + 真实 Input 事件，双层失败重试

### 5.1 候选对比

| 方案 | 精确度 | 真实性（站点反自动化） | 失败模式 | 实现成本 |
|---|---|---|---|---|
| A. index（backend_node_id）→ resolveNode → Input.dispatchMouseEvent 真实事件 | 高（节点级命中） | 高（真实输入管线） | 节点失效需重取快照 | 常规 |
| B. 坐标（bounds 中心点）→ Input 事件 | 中（受布局偏移/滚动影响） | 高 | 遮挡/动画期点击错位 | 常规 |
| C. JS 点击（el.click()） | 高（节点级） | 低（可被检测，触发行为不完整） | 不触发部分框架事件 | 常规（作为兜底） |
| D. AX 属性重定位（role+name 查找） | 中 | 中 | 重名歧义 | 中 |

### 5.2 结论与理由

**选 A 主 + B 备 + C 兜底**：与 §4 的 index 设计一体两面。
- 主路径：`index → DOM.resolveNode({backendNodeId}) → DOM.getContentQuads 取中心 → Input.dispatchMouseEvent(mousePressed/mouseReleased)`（agent-browser interaction.rs:990 `dispatch_click` 同款真实事件派发）。
- 文本输入：`Input.insertText`（IME 安全，避开中文输入法合成问题，仓库已有 IME 专项测试文化）或 `Input.dispatchKeyEvent` 逐键（agent-browser char_to_key_info 键盘映射，interaction.rs:1115，与 playwright 布局对齐）。
- 键盘：`Input.dispatchKeyEvent` + 修饰键组合（interaction.rs:318）。
- 滚动：`Runtime.evaluate window.scrollBy` + 可滚动容器定位（快照的 isScrollable 标记）。
- 文件上传：`DOM.setFileInputFiles`（CDP 原生，无系统对话框）。

失败重试（双层）：
1. 执行层：单次动作失败（目标失效/超时）→ 重新采集快照 → 用「上一快照的文本+role 摘要」模糊重定位（browser-use `max_failures` 语义）→ 最多 2 次重试。
2. 校验层：动作后 200-500ms 采状态差分（URL/表单值/AX 属性变化），无变化即报错回读（skyvern `test_input_text_readback.py` 同款 readback 思路）。

**复杂度：常规**（全部是 CDP 原生命令组合，无自研算法）。

## 6. 协同模型：单实例双控制面 + 事件总线 + busy 互斥 + 快照失效通知

### 6.1 候选对比

| 方案 | 体验 | 冲突处理 | 实现成本 |
|---|---|---|---|
| A. 单实例双控制面（用户直接在视窗操作 + AI 走 CDP，同一实例） | 最好（所见即 AI 所操作） | 需 busy 锁 + 变化检测 | 1-2 倍 |
| B. 双实例镜像（用户浏览器 + AI 无头实例，状态同步） | 差（不同步，登录态分裂） | 简单但无意义 | 1-2 倍且体验劣 |
| C. 单实例但互斥串行（AI 操作期间禁止用户输入） | 中（打断协作感） | 简单 | 常规 |

### 6.2 结论与理由

**选 A**：物理上只有**一个** Chromium 实例 + **一个** user-data-dir（§1/§7），AI 与用户天然共享登录态与页面。控制面：
- 用户面：直接操作嵌入视窗（screencast 交互或 HWND 嵌入的原生输入）。
- AI 面：CDP 命令（§5）。
- 事件面：Rust 侧 CDP 事件（`Page.frameNavigated` / `Page.loadEventFired` / `Target.attachedToTarget` / `Input` 域不可见用户物理输入）→ 事件总线（借鉴 browser-use `browser/events.py` 的 BrowserStateRequestEvent/NavigationStartedEvent 等事件族）→ 前端订阅刷新 URL/title/loading/帧流。

冲突处理规则（工程可落地的最小完备集）：
1. **busy 互斥**：AI 工具执行期间置 busy（工具面全局锁，agent-tools 既有 executor 层可挂）；busy 时用户操作不拦截（桌面应用无法也不应拦截物理输入），但记录「用户干预」事件。
2. **快照失效通知**：任何一方触发导航/大变更 → 事件总线广播 → AI 侧缓存快照标记失效，下次动作前强制重采（browser-use watchdog 思想，`dom_watchdog.py`）。
3. **用户干预撤销**：AI 动作后校验失败（§5 校验层）时，若检测到用户干预事件，报「页面被用户修改，请重试」而非盲重试。
4. **AI 操作指示**：动作前高亮——CDP 注入临时 outline 样式（或 `DOM.setHighlightConfig` 原生高亮），动作后清除；screencast 帧在 React 层叠加高亮框（前端纯组件，零页面侵入）。

**复杂度：1-2 倍**（事件总线与状态同步是主要增量；无 3 倍项）。

## 7. 数据导入：profile 整目录复制（主） + storage_state（辅） + 书签/历史直读（增值）

### 7.1 候选对比

| 方案 | 覆盖范围 | 复杂度 | 风险 |
|---|---|---|---|
| A. profile 整目录复制（copytree 到临时目录 + Local State） | cookie/登录态/书签/历史/扩展全量 | 常规（browser-use profile.py:838-893 完整实现可抄） | Windows 文件锁（WinError 32）需专门处理 |
| B. storage_state JSON（cookies/localStorage/sessionStorage） | 仅 cookie + web storage | 常规 | 缺书签/历史/登录态完整性；需运行时注入 |
| C. 书签/历史 SQLite 直读（Bookmarks/History 文件） | 书签/历史 | 常规（rusqlite 已有 conex-db 封装） | 与 A 配合才有意义 |

### 7.2 结论与理由

**选 A 主 + B 辅 + C 增值**：

A 直接移植 browser-use `_copy_profile`（profile.py:838-893）：
- 源：`<User Data>/<profile_directory>`（支持 `Default` / `Profile 1` / Edge 的对应目录，profile_directory 字段）。
- 复制到 `tempfile.mkdtemp(prefix='browser-use-user-data-dir-')` 等价目录，忽略 `Singleton*` / `*.lock` / `*-journal` / `LOCK` 瞬态文件（profile.py:30-36, 89-91）。
- 同时复制 `Local State`（含加密 key 归属信息）。
- **Windows 锁处理**：`_is_chrome_profile_lock_error`（profile.py:94-113）识别 WinError 32 / 共享冲突 → 明确报错「请关闭 Chrome」而非静默失败。这是 Windows 落地的关键坑，参考实现已完整给出。
- 复制完成后 `--user-data-dir=<temp_dir>` 启动（§1），Chrome 用本机 OS 用户加密 key 解密 cookie（同用户复制不破坏 DPAPI）。

B（storage_state）作为「轻量会话」入口：不复制 profile，只导出 cookies/localStorage JSON 运行时注入（`Network.setCookies` + 脚本 set localStorage）。

C（书签/历史直读）：从复制后的 `Bookmarks`（JSON）/ `History`（SQLite）读出，供前端地址栏/历史面板展示——conex-db 已有 rusqlite 封装可复用；仅读展示，不写回原 profile（杜绝污染用户真实数据）。

**复杂度：常规**（A 有完整参考实现，C 是简单 SQLite 读取）。

## 8. 工具集：browser_* 工具族挂 agent-tools 注册面

### 8.1 设计

挂 agent-tools 既有架构（ToolDefinition 声明 / Tool trait 执行 / Registry.register，definition.rs:30, registry.rs:40），新增约 16 个工具（命名对齐社区惯例）：

| 分组 | 工具 | 危险级 |
|---|---|---|
| 导航 | `browser_navigate` / `browser_back` / `browser_forward` / `browser_reload` / `browser_wait_load` | navigate 与 wait_load 标 dangerous（重定向/耗时可观） |
| 交互 | `browser_click` / `browser_double_click` / `browser_hover` / `browser_type` / `browser_press_key` / `browser_scroll` / `browser_select_option` / `browser_check` | 默认需审批（表单提交类动作可订阅） |
| 感知 | `browser_snapshot`（返回 DOM 简化树，token 上限可控）/ `browser_screenshot`（vision 按需） | 常规 |
| 会话 | `browser_new_tab` / `browser_close_tab` / `browser_switch_tab` / `browser_get_url` / `browser_backend_id_resolve`（内部） | 常规 |

要点：
1. **复用审批/审计**：危险标记走 ToolDefinition 既有字段 → permission.rs `decide` / `decide_command`（permission.rs:78,113）→ 审批后执行 → audit.rs `security_audit_event`（audit.rs:109）落库（conex-db）。**不新建审批体系**，浏览器工具只是普通工具的 dangerous 变体。
2. **快照工具节流**：`browser_snapshot` 输出大小上限（如 100KB/3 万 token），超限截断（skyvern prompt_truncation 同思路）。
3. **密码脱敏在工具层再兜底**：type 工具的参数值不写审计详情（敏感参数脱敏，skyvern `secret_redaction.py` 思路）。
4. **与 MCP 桥复用**：browser_* 工具注册后自动进入既有 MCP 工具面（register_plugin_server / bridge），外部 IDE 也能调用，零额外工作。

**复杂度：常规**（纯装配，无新架构）。

## 9. 安全：随机端口 + active port 文件 + 127.0.0.1 + 域名白名单 + 审批审计 + 脱敏

| 项 | 方案 | 证据/理由 |
|---|---|---|
| 调试端口 | `--remote-debugging-port=0`（随机）启动后读 `<user-data-dir>/DevToolsActivePort`（chrome-devtools-mcp browser.ts:84-103 的解析逻辑直接照搬）；**禁止固定 9222**（browser-use profile.py:28 特意避开默认端口，防本机其他工具嗅探） | 每次会话新端口 + active port 文件解析，零端口冲突 |
| 绑定地址 | Chrome 默认绑定 127.0.0.1（loopback），启动参数再显式 `--remote-debugging-address=127.0.0.1` | 拒绝局域网暴露 |
| 域名白名单 | 移植 browser-use allowed_domains/prohibited_domains（profile.py:617-624）：`*.domain` 模式匹配、100+ 条自动转 set O(1)、禁止 TLD 通配；导航前拦截（`Page.navigate` 前校验 + Network 域拦截兜底） | 这是 AI 浏览器防越权的核心 |
| IP/私网拦截 | `block_ip_addresses`（profile.py:625-628）：禁 IP 直连（含 localhost/私网），防 SSRF 式内网探测 | 与 sandbox crate 的语义对齐 |
| 审批审计 | §8：全部 browser_* 工具走既有 PermissionMode 审批 + audit 事件落库 | 复用 agent-tools，零新增 |
| 凭据脱敏 | 快照层 password value 不出树（serializer.py:1220-1227）；工具参数脱敏；profile 目录权限 0700 | 三层兜底 |
| 注入防护 | 快照文本标记「页面内容不可信」前缀（browser-use system prompt 既有惯例）；`browser_evaluate` 类裸 JS 工具**不开放**给 AI（规避任意代码执行面），页面脚本仅白名单能力（表单值读取） | 高风险工具一刀切收紧 |
| 扩展隔离 | 启动参数 `--disable-extensions`（默认），仅导入 profile 时按需 `--load-extension` 且逐项审批 | 默认最小权限 |

**复杂度：常规**（全部是参数与既有管线配置，无自研密码学/沙箱）。

## 10. Computer Use（电脑操作）二期：独立层，Windows 优先

### 10.1 候选对比

| 方案 | 覆盖 | 成本 | 风险 |
|---|---|---|---|
| A. 独立层（crates/conex-computer-use）：全屏截图 + 全局输入注入，与浏览器线**完全并行** | 任意桌面应用 | 1-2 倍 | Windows API 细节（DPI/多显示器） |
| B. 复用浏览器 CDP 抽象（把页面快照/Input 命令抽象成「桌面版」） | 桌面 + 浏览器 | 2 倍（抽象层设计成本） | 抽象过早，两类语义差异大（页面 DOM vs 像素坐标） |
| C. 不做（纯浏览器） | — | 0 | 二期需求缺失 |

### 10.2 结论与理由

**选 A：独立 crate，Windows 先落地**。

Windows 实现要点：
1. **截图**：xcap crate（Windows Graphics Capture API，无需系统对话框，支持窗口/屏幕区域捕获）或 windows-sys 直调 `IDXGISwapChain` 抓帧；全屏截图 → 传给 vision 模型（agent-provider image_url 已通）。
2. **输入注入**：enigo crate（已封装 SendInput/mouse/keyboard 序列，支持坐标点击与按键）或 windows-sys 直调 `SendInput`。全局注入无需管理员权限（非驱动级）。
3. **坐标缩放**：直接照搬 computer.py `scale_coordinates`（computer.py:268-291）：目标分辨率匹配（16:9 等常见比例 ±2% 容差）→ `x_scaling_factor` 双向换算（API↔屏幕）。截图传给模型用缩放后尺寸，模型返回坐标再放大回物理屏。
4. **动作空间**：computer.py 的动作枚举（mouse_move/left_click/left_click_drag/right_click/double_click/scroll/keypress/type/wait/screenshot，computer.py:23-42）作为工具契约，与 §8 browser_* 工具并列注册。
5. **与浏览器线关系**：共享的只有「工具注册/审批/审计管线」（§8）与「截图→vision 模型」通道；不共享快照算法（桌面无 DOM）、不共享 CDP 客户端。两线互不依赖，风险隔离。

难度评估：**中高**。主要坑：DPI 缩放感知（`GetDpiForWindow` / 每显示器独立 DPI）、多显示器坐标空间（负坐标象限）、无头/锁屏状态输入失效、遮挡窗口层级。预计一期不做，二期以 Windows 为唯一目标（macOS 用 CGEvent / AX API 后续追加）。

**复杂度：1-2 倍**（独立交付，不影响浏览器主链路）。

## 11. 技术栈与 crate 划分、依赖评审注意点

### 11.1 crate 划分

```
crates/conex-browser/           # 新 crate：浏览器核心
  ├─ cdp/                       # 自写最小 CDP 客户端（WS 连接/命令/事件/重连）
  ├─ browser/                   # 进程启动（spawn chrome/edge）、active port 解析、
  │                             #   user-data-dir 管理、profile 复制（§7）
  ├─ snapshot/                  # DOMSnapshot/AX 采集 + browser-use serializer 移植（§4）
  ├─ action/                    # 定位解析 + Input 事件执行 + 重试校验（§5）
  ├─ session/                   # 会话模型/事件总线/协同互斥（§6）
  └─ import/                    # profile 复制、storage_state、书签/历史读取（§7）
crates/conex-browser-tools/     # browser_* 工具族（挂 agent-tools 注册面，§8）
apps/agent-workbench/src-tauri/ # 壳侧：browser 进程生命周期、screencast 帧转发、HWND 嵌入
apps/crish-desktop/             # 前端：BrowserPanel 组件（替换/并列 PreviewCard）、帧流渲染
crates/conex-computer-use/      # 二期：截图 + SendInput + 坐标缩放（§10）
```

依赖方向：conex-browser ← conex-browser-tools ← agent-tools（工具注册）；conex-browser 不依赖 agent-tools（核心保持纯净，可单测）；壳与前端只依赖 conex-browser 的公开 API（命令/事件两个接口面）。

### 11.2 依赖评审注意点

| 依赖 | 结论 | 理由 |
|---|---|---|
| tokio-tungstenite | ✅ 采用（自写客户端基石） | agent-browser 同款；rustls-tls-webpki-roots 免系统证书依赖 |
| serde/serde_json | ✅ 已有（workspace） | — |
| chromiumoxide | ❌ 不采用 | §3 |
| image（截图编码/缩放） | ✅ 采用 | agent-browser 同款，vision 上传需 JPEG 编码（token 控制） |
| rusqlite | ✅ 复用 conex-db | 书签/History 直读（§7C） |
| xcap/enigo（二期） | ⏳ 二期评审 | 需验证 Windows 版本兼容与维护活跃度，二期再锁版本 |
| tauri 多窗口/多 webview API | ⚠️ 最小化使用 | screencast 只需**现有单 webview** + React 视频/画布渲染；HWND 嵌入属 Windows 增强，用 `window.hwnd()` + 原生 window-sys，不引入 wry 自定义布局 |

### 11.3 构建与测试策略

- 测试分层（对齐 agent-browser 验证过的模型）：
  1. CDP 客户端：mock WS 服务端单测（agent-browser browser.rs:2627 同款 `127.0.0.1:0` listener）；
  2. 快照算法：**纯函数**单测（serializer 移植保持无 IO 纯函数形态，browser-use 已有大量 fixture 断言可翻译成 Rust 测试）；
  3. e2e：`#[ignore]` 标记 + 串行执行（agent-browser e2e 约定），CI 单独 job 跑 Chrome 实例全链路；
  4. 前端：BrowserPanel 组件单测（帧流/事件订阅 mock）。
- 门禁：cargo test --workspace（新增套件并入 73 基线）、npm run typecheck、快层 coverage 维持 45/70/65/45 口径。

**复杂度：1-2 倍**（核心 crate 自研面集中但结构清晰）。
