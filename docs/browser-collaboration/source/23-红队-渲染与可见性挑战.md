### 1.2 核心结论（红队立场：挑战 D-1/D-2 的"无先例"假设）

**结论 1：路线 A（帧流 + 输入转发）不是无先例路线——有两家生产实现（agent-browser、skyvern），机制与我们方案 12 高度同构。** 这一条**推翻了"无先例 = 高风险"的隐含假设**，但同时暴露了两个更尖锐的问题（见结论 2/3）。

**结论 2：没有任何先例做过"真协同"（用户与 AI 并发操作 + 冲突处理）。** agent-browser 的 input 消息只用于"用户活动计数"（`is_user_input_message_type`），无令牌/吊销/版本失效机制；skyvern 是 `take-control`/`cede-control` **互斥切换**（用户拿控制权时 Agent 事件被丢弃，`cdp_input.py:367-376`），根本没有"AI 正在动、用户同时接管"的冲突语义。本项目 D-6（软互斥令牌 + abort 抢断 + snapshotVersion + 接管）是**超出全部先例的差异化能力**——这意味着：风险不来自"帧流+转发"本身（有先例），而来自"帧流+转发+真并发协同"的组合（无先例）。这是本轮挑战发现的**唯一真实风险点**，D-1/D-2 本身无罪，但必须明确：协同机制（D-6）才是无先例实验区。

**结论 3：公开实现全部回避了中文 IME 场景——这是"输入转发"路线最硬的公开痛点证据。**
- skyvern `useCdpInput.ts:336-353`：仅 `keyDown/rawKeyDown/keyUp` + 单字符 `text`，**无 composition 事件处理、无隐藏输入框桥、无 insertText**——中文合成输入在 skyvern 的 cdp_input 通道下不可用（合成期 key 为 "Process"/229 会被当作普通键转发，产生双输入或空输入）。
- agent-browser `viewport.tsx:57-71,360-398`：`KEY_INFO` 查表 + `e.key.length === 1` 才带 text，**同样无 composition 处理**；且键盘仅在 canvas 获焦时转发（`viewport.tsx:385-398`）。
- 两个先例都在**绕开**中文 IME，而不是解决它。方案 12 §3.7 的"隐藏输入框桥 + compositionend → insertText"因此是**全行业首个完整设计**——设计完备（兼容矩阵、229 兜底、surrogate pair），但**零实测背书**。这一条把 P0-3（IME 实测）从"常规验证项"升级为"全方案最大单点风险"，Go/No-Go 判据必须前置该实测（见 §④）。

**结论 4：CDP screencast 在业界被定位为"实验/录制"面，无一家把它当核心交互 UI 的帧率/延迟依据。** chrome-devtools-mcp 标 experimental + 要 ffmpeg；browser-use 只用来录 MP4；skyvern/agent-browser 虽实时流但**无公开端到端延迟指标**（skyvern 直接 ack 不控帧率靠丢帧，agent-browser 靠客户端 ack pacing 但无数字）。**方案中"120ms 帧延迟"没有任何外部数据可引用，是纯假设——必须 S0 实测，不能用业界"共识"背书。** 这是 D-2 的第二个硬风险点（第一个是 IME）。

**结论 5：业界"用户可见"的主流答案是 headed 窗口直操（browser-use）——但那是"AI 自动化工具"形态（用户是观众/验收者，不是协同者）。** 本项目 08 §1.1 的目标明确是"双向协同"（用户可随时手动操作、接管同一实例），产品定位不同，headed 窗口直操的"用户输入绕过控制面"缺陷对协同产品是致命的（正是 D-2 否决独立窗口的理由）。**业界主流不可直接套用，此条不构成对 D-2 的反驳。**

**结论 6：skyvern 保留了 VNC streaming 备选模式**（`BrowserSessionStream.tsx:73-80` 提示 "use-vnc-streaming"）——证明帧流方案在远程/特殊环境有已知替代需求，但 VNC 是远程容器场景（帧流跨网络推流），本地桌面 loopback 场景下 VNC 无优势，**不构成对本地帧流方案的否定**。

## ② 三路线对比矩阵

> 路线 A：帧流 + 输入转发（当前 D-2）
> 路线 B：WebView2 内嵌原生输入（评审已否决，本轮重新压测）
> 路线 C：独立窗口贴附（SetParent 类技术）原生输入（D-2 否决项的"窗口版"，本轮新增挑战对象）

| 维度 | A 帧流+转发 | B WebView2 内嵌 | C SetParent 窗口贴附 |
|---|---|---|---|
| **输入延迟（用户→页面）** | 前端事件 → WS（loopback）→ Rust → CDP → 页面。事件归一化 + 双 WS 一跳，本地实测基准合理估计 **5-20ms**（no-wait 发送无往返等待，12 §4.1 对齐 agent-browser `send_command_no_wait`）；**标不确定：无外部数据，S0 必测** | **0-2ms**：原生输入直进子 webview 渲染进程，无中间层 | **0-2ms**：原生输入直进贴附窗口 |
| **所见一致性（用户所见 vs AI 所见）** | 同一实例同一帧流，但 8-15fps 档位下帧间隔 67-125ms + JPEG 编解码 10-30ms，端到端**100-300ms**（05 评审已估，12 §8 预案承压 120ms 目标）；AI 动作后用户看到的画面有明确延迟 | **完美一致**：同一渲染表面，零延迟，所见即所是 | **完美一致**：真窗口，零延迟 |

| **一期复杂度红线合规** | 1-2 倍（08 §3.3） | 表面 1-2 倍，实为需求层不可行 | Windows 局部 2-3 倍，跨平台 3 倍+ 出局 |

### 矩阵裁决（红队立场）

- **路线 B 的否决在本轮压测下成立且增强**：我找不到任何推翻"profile 不互通 + CDP 受限"的证据；反而新增一条——先例核实显示**没有任何浏览器自动化生态构建在 WebView2 上**（browser-use / chrome-devtools-mcp / agent-browser / skyvern / playwright-mcp 全部是独立 Chromium + CDP），参考资产零复用（05 裁决 1 复核属实）。
- **路线 C 是被 09 否决项"独立窗口直操"的贴附变体，输入面上与独立窗口等价**（用户输入不经过控制面）——它换取的"原生输入"优势同时摧毁了协同核心（即时接管 + 单通道冲突检测），且仅 Windows 可做。**比 B 更差，出局。**
- **路线 A 的弱点被精确定位为两项**：① IME（无先例背书）；② 帧延迟指标（无外部数据）。两项都是"实测可裁决"项，不是"原理性错误"项。这是维持 D-1/D-2 的唯一正当理由：**弱点可测、可判、有降级预案**（§④）。

## ③ 挑战"输入转发"必要性

### 3.1 挑战命题的重述

挑战方主张：AI 不需要"感知用户输入事件"才能协同——用户点击后页面变化会推进 snapshotVersion，AI 下次动作前版本校验即自然看到变化；若如此，输入转发（延迟 + IME + 复杂度的最大来源）是否值得？

### 3.2 裁决：命题混淆了"感知面"与"执行面"，输入转发是执行面的必要条件

**感知面（AI 知道发生了什么）——挑战成立，转发非必需。** snapshotVersion + 重快照机制（D-6）确实完整覆盖"用户操作后的状态感知"：用户点击 → 页面变化 → `bump(InputInjected)` → AI 持有旧版本快照的动作被拒 → 重快照。**若产品只是"AI 操作 + 用户旁观"，输入转发可以整个砍掉**（帧流保留、输入层删除，AI 侧零损失）。

**执行面（用户能做什么）——挑战不成立，转发是唯一路径。** 产品目标（08 §1.1）是"用户可随时手动操作、接管同一实例"。在"面板内呈现浏览器"的形态约束下（D-2 已否决独立窗口/截图轮询），用户操作面板内实例**只有两条路**：
1. 面板捕获 → 转发注入（路线 A，输入在控制面内）；
2. 让输入绕过控制面直达实例（路线 B/C，代价见矩阵：D-7 落空 / 单平台 / 注入桥维护面）。

**"感知"论证恰好反向证明了转发的必要性**：版本失效是**事后检测**（页面已经变了才 bump）。而软互斥令牌的**即时吊销**（用户点击的瞬间中止 AI 在途动作、防止多步填表继续产生副作用）依赖"用户输入事件在 Rust 侧可见"——05 评审裁决 4 已论证纯版本号"无在途取消"是否决项。没有输入转发，唯一能拿到"用户输入事件"的手段是页面注入监听（isTrusted 陷阱 + 维护面，被 D-3 否决）或 OS 级 hook（3 倍+ 红线）。**输入转发不是感知手段，是即时接管的执行手段。**

### 3.3 代价核算（值得吗）

| 成本项 | 量级 | 抵消收益 |
|---|---|---|
| 输入延迟 | 5-20ms（loopback no-wait，§②） | 零等待接管：用户点击 → 吊销 AI 在途动作 → 800ms 内完成过渡（12 §5.1），无注入桥 |
| IME 复杂度 | 全链路最大单项（隐藏输入框 + 状态机 + 兼容矩阵，12 §3.7） | 换回：中文/日文/表情输入可用 + 与 AI type 通道共用 insertText 单管线（12 §3.7 选型表） |
| 单通道架构收益 | — | 冲突检测只有一个关注点（05 裁决 2："单输入通道 = 冲突处理只有一个关注点"）；令牌递增零成本；审计零死角 |

**结论：值得，但边界必须写死——若二期产品形态退化为"AI 自动化为主、用户仅为验收者"（如 browser-use 形态），输入转发应可整体拆卸（InputLayer 独立挂载，帧流保留），架构上不许把输入层与帧渲染耦合死。** 这是本轮红队对 12 维度文档提出的唯一结构性修正建议（见 §⑤）。

## ④ Go/No-Go 判据与降级路径

### 4.1 Go 判据（路线 A 值得保留的量化门槛，全部实测驱动）

| # | 判据 | 指标 | 验证时机 | 来源 |
|---|---|---|---|---|
| G-1 | 帧延迟 | 端到端（页面事件 → 面板可见）均值 **≤120ms**（Base 8fps 档）；交互档（15fps）≤150ms | S0（P0-2 前置实测，先于架构冻结） | 08 §5 S0 / 12 E2 |
| G-2 | 输入延迟 | 用户点击 → 页面收到事件 **≤30ms**（loopback 基准，no-wait 注入） | S4 e2e（E3 扩展：加时间戳埋点） | 12 E3 |
| G-3 | 中文 IME | 微软拼音输入"你好世界"全流程通过：候选窗跟随点击点、完整上屏、Esc 取消不注入、无双输入、无悬置；兼容矩阵抽测（搜狗/手写）无回归 | **S0（P0-3，与 G-1 同前置）** | 12 E5 / 09 P0-3 |
| G-4 | 接管延迟 | 用户输入 → AI 在途动作收到中止 ≤ **800ms**（= TOKEN_MIN_STABLE_WINDOW） | S8 e2e（E7） | 12 §5.1 |
| G-5 | 实现工作量 | S4 前后端（帧泵 + WS + canvas + 输入层 + IME）≤ **3 人周**；超期即触发降级评审 | S4 阶段门禁 | 12 §9 |

**G-1/G-3 为硬门槛**（任一失败即 No-Go 触发降级）；G-2/G-4/G-5 为软门槛（不达标进降级评审而非直接否决）。

### 4.2 No-Go 降级路径（按顺序执行，不跳级）

1. **帧延迟 120-200ms（轻微超标）** → 12 §8 预案：quality 60→50、maxWidth 1600→1024、Base 档 8→6fps、确认 Burst 升帧路径生效；复测。
2. **帧延迟 >200ms（重度超标）** → **Windows 升级 HWND 嵌入为主路径（05 P1 预案提前）**。红队必须明示代价：HWND 嵌入下用户输入绕过 CDP，协同检测源降级为"事后版本失效"（失去即时接管），D-6 令牌语义改为软降级（不保证 800ms 中止）；macOS/Linux 维持帧流主路径（平台分化）。此路径**不是切路线 B/C**（B 的 D-7 硬伤不可消解，C 单平台出局），而是路线 A 的窗口化变体。
3. **IME 失败（G-3）** → 先查 12 §3.7 兜底链（229 键流计数、Esc 取消、兼容矩阵补测）；仍失败 → 评估 CDP 实验域 `Input.imeSetComposition`（无 SLA，仅作受限增强）；最终兜底 = 接受"页面内无合成预览 + 候选窗贴面板"的已知损失（12 §3.7 已列），仅当候选窗完全不可用才触发 HWND 路径。
4. **工作量超红线（G-5）** → 裁剪项按序砍：Burst 档（拖拽升帧）→ 丢帧统计上报 → 虚拟指针动画 → 面板内联预览（本就是后续增强）；不砍安全项（token/Origin 校验/审计）。

### 4.3 判据的信服逻辑

路线 A 的三个弱点（帧延迟、IME、协同无先例）全部可以**在架构冻结前用 G-1/G-3 实测裁决**，且每条都有明确降级阶梯——这是"维持一个弱点的方案"与"维持一个死局的方案"（B/C）的分界线。红队立场：**凡不可实测裁决的缺陷应否决，凡可实测裁决且有降级路径的缺陷可放行**。

## ⑤ 最终立场

### 立场：维持 D-1/D-2（有条件），附两条结构性修正

**维持理由（红队被说服的判据）：**

1. **先例反证了"无先例"恐惧**：帧流 + 输入转发有 agent-browser（dashboard canvas + ack pacing + no-wait 注入）与 skyvern（生产级 cdp_input + take-control 协议）两条可对照实现，方案 12 的机制与二者同构——复杂度评估有实数可依，非拍脑袋。
2. **B/C 的否决在本轮压测下全部成立且增强**：B 的"profile 不互通 + CDP 受限"是需求层死局（且全行业无 WebView2 生态）；C 是独立窗口否决项的贴附变体（输入绕过控制面 + 仅 Windows），无任何新论据可复活。
3. **A 的弱点被精确定位为"可实测裁决"项**：IME（G-3）与帧延迟（G-1）都不是原理性错误，是量化验证项；全部先例绕开 IME 恰恰说明这是 A 路线的唯一真实赌注——所以把它列为**硬门槛、前置 S0**，不妥协。
4. **输入转发必要性论证修正后成立**：它是"即时接管"执行面的必要条件（版本失效只能事后检测，无法吊销在途动作），不是感知面的必要条件；感知面论证（挑战命题）本身正确，但它证明的是"输入转发可拆"而非"输入转发可省"。

**两条结构性修正（不推翻 D-1/D-2，要求写入维度 12）：**

- **修正 1（拆装性）**：InputLayer 必须独立挂载（props 契约级解耦，`interactive` 开关语义对齐 skyvern `controllable`），允许"帧流保留 + 输入层禁用"的产品形态（AI 自动化模式 / 审批观看模式）。防止输入转发复杂度绑架只读场景。**代价约等于一个布尔开关，收益是让 D-2 的两个子决策（帧渲染/输入转发）可独立裁决——G 判据因此可分别执行。**
- **修正 2（协同先例风险显式化）**：D-6 的"真并发协同"（用户与 AI 同时活跃 + 毫秒级竞态收敛）超出全部先例，应在 S8 前安排专项 spike（05 P0-8 竞态注入测试提前），并把"最坏结果 = 用户最后输入胜出"写为可测试断言，而不是默认成立。

**不做的事：** 不切路线 B（D-7 硬伤不可消解）、不切路线 C（单平台 + 输入绕过控制面）、不把 HWND 提前（仅作为 G-1 重度失败的降级阶梯，且明示其协同语义降级代价）。
