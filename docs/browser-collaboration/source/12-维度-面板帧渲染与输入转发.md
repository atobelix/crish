## 1. 总体数据流与传输选型

### 1.1 双通道架构（本次裁决）

| 通道 | 承载内容 | 频率量级 | 技术选型 |
|---|---|---|---|
| 媒体通道（面板专用 WebSocket） | 帧流下行（raw JPEG 二进制）+ 输入上行（鼠标/键盘/合成文本/升帧请求/视口尺寸） | 8-20fps 帧 + 输入事件流 | **专用 WS**：loopback 随机端口 + 会话 token（握手 header 传递，R-10）校验 |
| 控制通道（Tauri 事件/IPC） | 面板状态（idle/ai-busy/paused/…）、AI 动作文本、导航/标签/URL、暂停/接管命令 | 秒级低频 | 既有 Tauri invoke + `listen()`（复用 tauriTransport 模式） |

```
┌─ React 面板（BrowserPanel）─────────────────────────────────┐
│  PreviewToolbar / PreviewHistoryPanel（保留既有壳）          │
│  FrameCanvas（canvas 帧渲染）      InputLayer（事件捕获）     │
│  VirtualCursor（虚拟指针）         IndicatorBar（指示条/接管） │
└──────────┬──────────────────────────────────┬───────────────┘
           │ WS（二进制帧 + JSON 输入消息）     │ Tauri invoke/事件（低频控制面）
┌──────────┴──────────────────────────────────┴───────────────┐
│ Rust 引擎（conex-browser crate）                            │
│  FramePump（ack pacing 帧泵）→ InputPipeline（统一注入管线）  │
│  PanelController（暂停/接管/状态机）→ 维度 15 令牌接线         │
│  CDP 客户端（维度 11 自研薄客户端，发送层互斥保序）           │
└──────────────────────────┬──────────────────────────────────┘
                           │ CDP（loopback 随机端口 + token）
                     受管 Chromium 实例（D-1）
```

### 1.2 传输选型理由（Tauri event vs WebSocket）

| 判据 | Tauri event（`emit`/`listen`） | 专用 WS（本次选用） |
|---|---|---|
| 帧体积 | base64 字符串经 JSON 序列化，膨胀 33% | WS 二进制消息传 raw JPEG，零膨胀 |
| 背压 | fire-and-forget，webview IPC 无背压，帧洪泛可致队列无界 | TCP 流控天然背压，帧泵可感知慢消费 |
| 全双工保序 | 输入上行需另走 invoke（串行化、每事件往返） | 同一连接双工，socket 互斥保序（press 不会越过 release） |
| 业务隔离 | 帧流与业务事件共用总线，互相干扰 | 媒体通道独立，断流不影响主事件总线 |
| 先例 | 仓库 tauriTransport 承载运行事件（JSON 载荷） | agent-browser daemon WS（input_mouse/input_keyboard 消息同构，见 reference/agent-browser/cli/src/native/stream/websocket.rs:616-666） |
| 复杂度 | 低（复用既有） | 中（新增 WS 服务器，Rust 侧约 1 个子模块） |

**结论**：帧流下行与输入上行走专用 WS（媒体通道）；状态/命令走 Tauri 控制通道。理由：二进制免膨胀、背压可控、输入双工保序、与主事件总线隔离，且 agent-browser 已有同构先例可参照。控制面保持 Tauri（低频 JSON，复用既有 tauriTransport/EventBus 设施）。

### 1.3 连接与安全（对齐 D-9 与 R-10）

- 监听 `127.0.0.1`，随机端口（`TcpListener::bind("127.0.0.1:0")` 取实际端口）。
- URL 形如 `ws://127.0.0.1:<port>/panel`（**token 不进 URL**）；升级握手时经**自定义 header**（如 `X-Panel-Token`）传递 token 并校验（R-10 裁决），失败即关连接。
- **token 语义（R-10）**：帧 WS 与 CDP 命令通道**共用会话 token**（`SessionToken`，uuid v4，维度 10 §7.1，对齐 21-C4 对「同源派生未定义」的闭合）；token 生命周期与面板会话绑定，关闭面板即失效；端口与 token 经 Tauri invoke 返回给前端（`browser_panel_open`，**前端仅持有内存引用——不落日志/本地存储/错误上报**）。
- **Origin 校验（R-10）**：握手时校验 `Origin` 头，仅放行应用自身 origin（`tauri://localhost` / 应用标识），不匹配即拒绝握手并关连接。
- 断线重连：指数退避（500ms 起步 ×2，上限 5s），重连仍经 header 携带同一 token；重连成功前输入转发暂停、面板显示重连条。
- **日志纪律（R-10）**：端口、WS path、token 不出现在任何日志/事件/错误上报（单测与 e2e 回归断言，§7 E14）。
- 前端 WS 客户端复用 ConnectionManager 的连接生命周期管理模式（新建 PanelSocket 实例，不污染主连接）。

## 2. 帧流管线

### 2.1 startScreencast 参数与帧率控制

CDP `Page.startScreencast` 参数（协议实测确认，无显式 fps 字段）：

| 参数 | 取值 | 说明 |
|---|---|---|
| format | `"jpeg"` | PNG 仅作调试备用，默认 JPEG |
| quality | 60（可调 50-75） | JPEG 质量，帧延迟超标时优先降质量 |
| maxWidth / maxHeight | 1600 × 1000（上限） | 帧图最大像素；实际帧 = 视口 CSS 尺寸 × pageScaleFactor |
| everyNthFrame | 1 | 每帧都发，节流交给 ack pacing（见下） |

**帧率控制 = ack pacing**（协议无 fps 参数）：Chrome 在收到 `Page.screencastFrameAck(sessionId)` 后才产生下一帧，因此 Rust 帧泵持住 ack 即可精确控帧率：

```rust
// conex-browser/src/screencast/pump.rs（帧泵核心逻辑）
loop {
    let evt = screencast_rx.recv().await?;            // Page.screencastFrame 事件
    let seq = frame_seq += 1;
    ws_tx.send(FrameMsg::binary(seq, &evt.data)).await; // base64 → raw bytes，WS 二进制下行
    let hold = 1000 / fps(fps_level).await;           // 档位换算的 ack 延迟
    tokio::time::sleep(Duration::from_millis(hold)).await;
    cdp.send("Page.screencastFrameAck", json!({ "sessionId": evt.sessionId })).await;
}
```

- 一帧在途（未 ack）时 Chrome 不会发新帧，天然无双帧并发/乱序。
- 帧事件重复防御：记录已 ack 的 `sessionId`，重复事件直接丢弃（防 CDP 重放）。

**重连/崩溃重启后的帧流恢复（R-9-3/M-3 契约）**：帧泵订阅维度 11 的 `ConnectionRestored` 事件（重连恢复清单第 9 项重启 `startScreencast` 后广播）→ 以原帧率/质量档位重启 `Page.startScreencast` 并重新开始 ack pacing（旧 sessionId 序列作废）；恢复完成前输入转发保持暂停、面板显示重连条（§1.3）。

### 2.2 帧数据格式与 Rust → 前端传输

- CDP 事件 `Page.screencastFrame`：`data`（base64 JPEG 字符串）+ `metadata`（`pageScaleFactor`、`deviceWidth/deviceHeight`（DIP）、`scrollOffsetX/Y`、`timestamp`）+ `sessionId`。
- Rust 侧 base64 解码一次 → raw JPEG 字节。
- WS 二进制帧格式（定长头 + 变长负载，全部小端）：

```
偏移 0-3   seq: u32          帧序号（前端丢帧统计/诊断用）
偏移 4-7   width: u32        帧图宽度 px
偏移 8-11  height: u32       帧图高度 px
偏移 12+   JPEG 原始字节
```

- 前端 `onmessage` 收到 `ArrayBuffer` → 解析头 → `new Blob([jpeg], {type:'image/jpeg'})` → `createImageBitmap` 异步解码（不阻塞主线程）。

### 2.3 前端 canvas 绘制（尺寸自适应 / DPR / 缩放）

```tsx
// FrameCanvas.tsx 核心渲染循环（简化）
const ctx = canvasRef.current.getContext('2d')!;
let pending: Frame | null = null;        // 渲染队列深 1（丢帧策略见 2.4）
let rendering = false;

function onFrame(f: Frame) { pending = f; schedule(); }

function schedule() {
  if (rendering) return;                 // rAF 循环进行中，新帧直接覆盖 pending（丢旧帧）
  rendering = true;
  requestAnimationFrame(async () => {
    const f = pending; pending = null;
    if (f) {
      const bmp = await createImageBitmap(f.blob);
      const dpr = window.devicePixelRatio || 1;
      const cssW = container.clientWidth, cssH = container.clientHeight;
      if (canvas.width !== cssW * dpr || canvas.height !== cssH * dpr) {
        canvas.width = cssW * dpr;       // DPR 自适应：物理像素
        canvas.height = cssH * dpr;
      }
      ctx.setTransform(dpr, 0, 0, dpr, 0, 0);
      ctx.drawImage(bmp, 0, 0, cssW, cssH);  // 等比填满（object-fit: contain 同语义）
      bmp.close();
      lastRenderedSeq = f.seq;
    }
    rendering = false;
    if (pending) schedule();             // 积压则继续消费（仍是最新优先）
  });
}
```

- 显示缩放：`object-fit: contain` 语义，画布 CSS 尺寸随容器（面板 resize 由 ResizeObserver 驱动，参照既有 ResizeObserverManager）；帧图与显示区比例不同时以最小缩放比居中留黑边。
- 面板 resize 后经 WS 上行 `viewport` 消息通知 Rust（见 §2.6）。

### 2.4 帧去重与丢帧策略

| 层级 | 策略 |
|---|---|
| Rust 帧泵 | ack pacing 保证单帧在途，天然无重发；重复 `sessionId` 事件丢弃 |
| 前端接收 | 队列深 1：新帧到达直接替换未渲染的旧帧（未解码帧零成本丢弃） |
| 前端渲染 | 每 rAF 只消费 1 帧；解码（createImageBitmap）与绘制分离，解码慢不阻塞 rAF 循环 |
| 丢帧判据 | `pending` 被替换即视为丢帧（计数上报诊断）；不重传、不追赶——画面永远追最新 |

### 2.5 交互期升帧触发规则

| 档位 | fps | ack 延迟 | 触发条件 |
|---|---|---|---|
| Base | 8 | 125ms | 面板静止且无 AI 动作 |
| Interactive | 15 | 67ms | 用户交互（pointerdown/move/wheel/键入）；AI 动作序列执行中（维度 15 动作开始/结束事件驱动） |
| Burst | 20（上限） | 50ms | 拖拽中、连续滚动（wheel 流）、AI 拖放/动画回显 |

- 前端升帧请求：InputLayer 检测到交互时发送 `input_active` 消息（节流 100ms，避免洪泛）；Rust 侧 `FpsLevel::Interactive`，拖拽/连续 wheel 升 `Burst`。
- 回落：Rust 侧静止计时器，2s 无输入且无 AI 动作 → 回落 Base。
- 帧率可调：设置项（quality/fps 上限）经控制通道下发，运行时生效（重启帧泵）。

### 2.6 坐标映射（锁定 1:1，O(1) 换算）

- 面板激活时下发 `Emulation.setDeviceMetricsOverride`：`width/height` = 面板内容区 CSS 尺寸、`deviceScaleFactor = 1`、`mobile = false`（对齐 D-1 启动参数无节流降级）。此后 `pageScaleFactor = 1`、帧图 = 视口 CSS 像素，**坐标映射为单一比例换算**：
  - 面板 CSS 坐标 → 页面 CSS 坐标（viewport 相对）：`page_x = panel_x × (viewport_w / img_w)`，`viewport_w` = 面板内容区宽（setDeviceMetricsOverride 值）。
- 帧图尺寸变化（页面视口变化/页面缩放）由 `viewport` 消息与帧头尺寸双重校准，前端缓存当前比例。
- 不使用 `metadata.offsetTop/scrollOffset` 动态换算（锁 1:1 后恒为 0/0）；`scrollOffsetX/Y` 仅留作诊断。
- 面板 resize：resize 防抖 150ms → WS `viewport` 消息 → Rust 重发 setDeviceMetricsOverride → 新帧尺寸自然更新。

## 3. 输入转发（用户 → 浏览器）

### 3.1 前端事件捕获与归一化

- InputLayer 覆盖画布区域（absolute 定位，z-index 高于 canvas 低于 IndicatorBar），监听：`pointerdown/pointermove/pointerup`、`wheel`、`keydown/keyup`（挂在隐藏输入框上）、`contextmenu`、`dragstart/dragover/drop`、`compositionstart/update/end`、`blur`。
- 统一阻止浏览器默认行为（`preventDefault` on wheel/contextmenu/drag），防止 webview 自身滚动/菜单/拖拽劫持。
- 坐标归一化：`event.clientX/Y` 相对画布容器 → 面板 CSS 坐标 → §2.6 换算为页面坐标 → WS 上行。
- 修饰键归一化：前端维护按键按下状态集合（`ctrl/shift/alt/meta`），每个事件计算 CDP 修饰键位（`1=Alt 2=Ctrl 4=Meta 8=Shift`）；`window.blur` 时补发已按住修饰键的 keyUp 并清空状态（防 sticky 修饰键）。

### 3.2 鼠标映射表（Input.dispatchMouseEvent）

前端 `MouseEvent`/`PointerEvent` → WS `input_mouse` → Rust 组参数：

| 前端事件 | CDP `type` | button | buttons | clickCount | deltaX/deltaY |
|---|---|---|---|---|---|
| pointermove | `mouseMoved` | 当前按压键（无则 `none`） | 位掩码 | 0 | 0 |
| pointerdown(左) | `mousePressed` | `left` | `1` | 按 §3.5 | 0 |
| pointerdown(右) | `mousePressed` | `right` | `2` | 1 | 0 |
| pointerdown(中) | `mousePressed` | `middle` | `4` | 1 | 0 |
| pointerup | `mouseReleased` | 释放键 | 位掩码更新 | 按 §3.5 | 0 |
| wheel | `mouseWheel` | `none` | 当前位掩码 | 0 | 归一化后的像素增量（§3.4） |
| 侧键（button 3/4） | `mousePressed/Released` | `back` / `forward` | `8` / `16` | 1 | 0 |

- `buttons` 位掩码：`1=左 2=右 4=中 8=back 16=forward`，多键同按取并集。
- 修饰键位：`modifiers`（§3.1 归一化结果）。
- 事件序保真：WS 上行按前端产生顺序发送，Rust 侧统一经发送层 socket 互斥（press 先于 release 送达，不会交错）。
- 右键菜单：`mousePressed(right)` + `mouseReleased(right)` 触发页面 DOM contextmenu（渲染进帧可见）；前端 `contextmenu` 事件 preventDefault 后仍完整转发。
- **触摸输入**：触摸屏/触控板多点触控一期映射为鼠标语义（pointer 事件已覆盖大部分点击/滚动场景），真触控手势（捏合/双指）列入后续增强（评审 20 12-7）。

### 3.3 键盘映射表（Input.dispatchKeyEvent）与文本注入策略

**策略裁决**：用户路径对可打印字符转发真实键盘事件（`keyDown` 携带 `text`，浏览器事件本身携带 key/code/VK，无查表误差）；控制键与组合键转 `keyDown+keyUp`；IME 合成文本走 `insertText`（§3.7）。

| 前端事件 | CDP 参数 |
|---|---|
| keydown（可打印，非合成期） | `type=keyDown`，`key/code/windowsVirtualKeyCode/nativeVirtualKeyCode` 直取浏览器事件，`text=unmodifiedText=字符`，`modifiers`，`autoRepeat=e.repeat` |
| keyup | `type=keyUp`，`text` 置空 |
| keydown（控制键） | `type=keyDown+keyUp`（Enter `text="\r"`、Tab `text="\t"`、Space `text=" "`、Backspace/Delete/Arrow*/Home/End/PageUp/PageDown/Escape 无 text） |
| 组合键（Ctrl/Cmd/Alt/Shift + 键） | `type=keyDown+keyUp`，`modifiers` 置位，**text 置空**（命令和弦不做文本插入，Ctrl+A 全选语义正确） |

- 关键参数注意（对齐 agent-browser interaction.rs 既有实现与注释）：
  - 省略字段不发 `null`（CDP 收到 null 字符串整个命令失败，agent-browser websocket.rs:572-577 注释明示）。
  - `windowsVirtualKeyCode` 用事件原生值（浏览器已按布局给出）；AI 路径查表用 Playwright USKeyboardLayout 对照（agent-browser interaction.rs:1115-1220 已有实现并通过 parity 测试，可直接移植）。
  - `location`：数字小键盘键置 3（`e.location === 3`）。
- 键盘事件只在前端隐藏输入框获得焦点时转发（§3.6 焦点管理）。

### 3.4 滚动归一化

- `wheel` 事件 `deltaMode` 归一化为像素：`0` 直接用；`1`（行）×16；`2`（页）×视口高度。
- rAF 合并：同一帧内多次 wheel 的 delta 累加为一次 `mouseWheel` 注入（高频触控板洪泛收敛）。
- `ctrl+wheel` 保留 ctrl 修饰位 → Chrome 原生页面缩放行为（CDP 注入同样触发）。
- 触控板双指滚动在 webview 内即为 wheel 事件，走同一路径，无单独实现。

### 3.5 拖拽与点击判定（前端状态机）

- 拖拽：`mousePressed(left)` → 连续 `mouseMoved`（`buttons=1`）→ `mouseReleased`；无需额外命令（CDP 鼠标拖拽即 press+move+release 序列）。
- 点击判定：press 与 release 位移 < 5px 且间隔 < 500ms → 单击，`clickCount=1`；双击：二次单击间隔 < 500ms → `clickCount=2`；三击类推。超过阈值 → 后续事件 `clickCount=1` 重新起算。
- 拖出面板（pointer capture 丢失）时补发 `mouseReleased` 兜底（防页面按钮 stuck 按下）。

### 3.6 焦点管理与虚拟指针

- **页面焦点模型由信任输入自然维持**：CDP 注入的点击（isTrusted=true）会正常驱动页面 focus/blur，无需额外 DOM 操作。
- **虚拟指针**（VirtualCursor 组件）：absolute 定位的 cursor 图标 div，位置 = 最后一次注入的鼠标坐标（随 `mouseMoved` 实时更新），保证用户可见"鼠标在页面哪里"（页面自身光标不渲染进帧）。AI 动作期间光标变为高亮/闪烁态（操作点可见性，§5）。
- **隐藏输入框**（IME/键盘载体，§3.7 详述）：点击面板任意处 → 虚拟指针定位 + 隐藏输入框 `focus()`（位置同步到点击点下方，为 OS IME 候选窗定位）；面板失焦（点击聊天区等）→ 隐藏输入框 `blur()` → 键盘事件暂停转发（防误注入），再次点击面板恢复。
- **键盘注入前置**：dispatchKeyEvent 前保证最近一次 mouseMoved 已送达（WS 保序天然满足，press→键盘序列顺序即用户操作顺序）。

### 3.7 IME 策略裁决（开放问题 2 关闭）

**裁决结论：隐藏输入框桥接 + compositionend 直接注入文本（Input.insertText）**。中文输入法全流程（候选窗、双拼、手写、软键盘）由操作系统 IME 在面板层完成，页面只接收最终确认文本。

**方案形态（输入管线中的 IME 事件流）**：

```
用户点击面板文本框
  → InputLayer: pointerdown → 虚拟指针定位 → 隐藏输入框 focus()（OS IME 激活）
  → compositionstart          → 清空本地缓冲，进入合成期
  → keydown(keyCode 229)      → 不转发（合成键不属页面）
  → compositionupdate("你")   → 缓冲 = "你"（可选：面板内内联预览）
  → compositionupdate("你好") → 缓冲 = "你好"
  → compositionend            → WS input_text { text: "你好" }
                              → Rust Input.insertText("你好")
                              → 页面 input 值更新（页面焦点由先前点击维持）
  → 合成期结束，后续普通按键恢复 §3.3 转发
```

**选型对比与否决项**：

| 方案 | 结论 | 理由 |
|---|---|---|
| 隐藏输入框桥接 + insertText | **选定** | OS IME 全流程零重实现（候选窗/双拼/手写/软键盘全部可用）；与 AI type 通道天然一致（同为 insertText）；兼容矩阵最广（见下） |
| 合成事件逐键经 CDP 转发（keyDown 229 + char 事件模拟） | 否决 | CDP 无可靠合成事件注入面；isComposing/229 语义在页面端不可靠，双输入风险高 |
| `Input.imeSetComposition`（CDP 实验域） | 否决 | `experimental=True` 无 SLA；要求客户端自实现候选引擎/词库，复杂度红线外（09-敲定 §5 声明） |
| 页面内注入 IME polyfill 脚本 | 否决 | 注入桥 isTrusted=false 陷阱（D-3 已否决注入桥主通道），且无法接住 OS IME 候选窗 |

**关键实现细节**：

- 隐藏输入框：离屏 `<input>`（单行）/`<textarea>`（多行，`data-ime-bridge` 标记），CSS 定位到点击点下方约 20px 处（OS IME 候选窗出现在该处，用户视觉上候选窗贴着面板点击点）；`autocomplete=off`、无边框透明。
- 合成期阻断：`compositionstart` 至 `compositionend` 期间，keydown/keyup **一律不转发**（防双输入）；compositionupdate 只更新缓冲。
- compositionend 注入：整串文本一次 `insertText`（避免逐字符切分破坏 surrogate pair——emoji/生僻字）。
- 兜底：个别 IME 不发 compositionend（只发 keyCode 229 键流）——keydown(229) 计数超 3 次且无 composition 事件且 500ms 无更新 → 视为合成悬置，缓冲清空重置（防缓冲泄漏）。
- 合成取消（Esc）：compositionend 文本为空 → 不注入，缓冲清空。
- 已知损失（记录在案）：合成过程中页面侧无内联候选预览（候选窗由 OS IME 显示于面板层）；确认式输入（逐候选上屏）不受影响。
- 面板内内联预览（可选增强）：compositionupdate 时将缓冲渲染为画布上方半透明浮层，与 OS 候选窗并行——S4 不做，列为后续增强。

**IME 兼容矩阵（目标形态）**：

| 平台/输入法 | 关键行为 | 本方案适配 |
|---|---|---|
| Windows 微软拼音 | composition 事件完整，候选窗跟随隐藏输入框 | 直接支持 |
| Windows 搜狗/微信/QQ 输入法 | 同上（均为 TSF 合成） | 直接支持 |
| Windows 微软五笔/手写 | 手写候选窗在面板层 | 直接支持 |
| macOS 系统拼音/双拼 | composition 完整；候选窗位置跟随焦点 | 直接支持（候选窗贴隐藏输入框） |
| Linux fcitx5 / ibus | composition 完整；部分输入法无候选窗跟随 | 直接支持；定位损失可接受 |
| 硬件键盘直输（无 IME） | 无 composition，普通 keydown | §3.3 直接转发 |

## 4. 输入转发（AI → 浏览器）与并发协调

### 4.1 共用注入管线（函数级共用）

用户与 AI 的注入共用**同一发送管线与命令枚举**，差异仅在"语义 → InputCmd"的映射层：

```rust
// conex-browser/src/input/pipeline.rs —— 唯一注入面（单通道保证所见一致）
pub enum InputCmd {
    Mouse { event_type: MouseEventType, x: f64, y: f64, button: MouseButton,
            buttons: u32, click_count: u32, delta_x: f64, delta_y: f64, modifiers: u32 },
    Key { event_type: KeyEventType, key: Option<String>, code: Option<String>,
          text: Option<String>, windows_virtual_key_code: u32,
          native_virtual_key_code: u32, auto_repeat: bool, modifiers: u32, location: u32 },
    InsertText { text: String },
}

pub struct InputPipeline { tx: mpsc::Sender<InputCmd> }   // 消费者：发送层 socket 互斥保序

impl InputPipeline {
    pub async fn dispatch(&self, cmd: InputCmd) -> Result<(), InputError>;
}

// 入口 A：用户（面板 WS 输入消息 → InputCmd，映射见 §3）
// 入口 B：AI（browser_* 工具经 agent-tools 执行器 → InputCmd，映射见维度 14 动作执行）
```

- 发送层：所有命令经同一 socket 互斥发送且**不等待 CDP 响应**（agent-browser websocket.rs:609-615 注释：等待响应会把整条读循环串行化，鼠标扫过拖住点击；保序由互斥 + 顺序调用保证）。
- AI 工具映射（维度 14 定义，此处引用）：`click/hover/drag` → `Mouse`；`key` → `Key`（名称查表 Playwright USKeyboardLayout）；`type` → 可打印走 `InsertText` 分块 + 控制键走 `Key`（agent-browser interaction.rs:239-305 同策略）。
- **函数级共用含义**：两端发到同一个 `InputPipeline`，注入到同一页面会话——用户与 AI 所见、所操作是同一真实实例（D-2 单实例双控制面）。

### 4.2 并发协调（引用维度 15 令牌机制）

| 场景 | 机制 | 接口（既有设施） |
|---|---|---|
| 用户输入抢断 AI | 用户事件到达 → `abort_token.abort()` 吊销在途动作 | `AbortToken`：crates/agent-tools/src/context.rs:33（`is_aborted()`/`abort()`；执行器每步自查，executor.rs:187-209） |
| 用户暂停 AI 队列 | 暂停标志 → 队列消费者每步前检查 | 维度 15 队列消费端 + 本面板 `PanelController.pause`（§5.2） |
| AI 动作中用户不动 | AI 持软互斥令牌正常执行 | 维度 15 令牌语义 |
| 版本失效 | 注入动作落地后 `bump(tab_id, InputInjected)`（R-1 即时 +1）；AI 持旧版本快照动作 → 重快照 | 维度 11 `bump(tab_id, reason)`（per-tab 版本面） |

- 注入落地点推进版本：`InputPipeline.dispatch` 成功 → 调用维度 11 `bump(tab_id, reason: InputInjected)`（R-1：用户输入注入即时 +1，任何来源的注入都推进——用户与 AI 统一；**不直接改版本号**，聚合/导航优先逻辑归维度 11 单一权威）。
- 用户交互信号（`input_active`）同时是接管信号：WS 收到任意 `input_mouse/input_keyboard/input_text` → Rust 侧上报维度 15 事件总线，由 `CollaborationCoordinator` 触发吊销链（**吊销链唯一入口，T-12**；PanelController 仅呈现 `user-taking-over` 状态投影，不直接 abort）。
- 令牌抖动防护：接管后 AI 不自动重试，由用户显式恢复（最小稳定窗由维度 15 定义）。

## 5. 指示条 / 接管层

### 5.1 指示条状态机

| 状态 | 含义 | 进入条件 | 退出条件 |
|---|---|---|---|
| `idle` | AI 空闲，用户可自由操作 | 初始化/动作链结束 | AI 动作开始 → `ai-busy` |
| `ai-busy` | AI 动作序列执行中 | AI 工具开始执行（维度 15 动作开始事件） | 动作链结束 → `idle`；用户点击暂停 → `paused`；用户输入 → `user-taking-over` |
| `paused` | AI 队列挂起 | 用户点击暂停（或接管后 AI 未恢复） | 用户点击恢复 → `idle`（或重新触发 AI） |
| `user-taking-over` | 用户已接管，AI 在途被吊销 | 面板收到用户输入事件且 AI 在途 | 800ms 过渡后 → `idle`（过渡时长 = 维度 15 `TOKEN_MIN_STABLE_WINDOW` 常量，T-12；AI 未恢复时展示"已暂停 AI"提示） |

```
        ┌──────────┐  AI 动作开始   ┌──────────┐
        │   idle   │──────────────→│  ai-busy │
        └──┬───────┘               └────┬─────┘
           │ ▲  用户交互（接管）          │ 用户点击暂停
           │ │                          ▼
           │ │                      ┌──────────┐
           │ └────── 800ms 过渡 ─── │user-     │
           │                       │taking-   │←────────────┐
           │  AI 队列恢复/结束       │over      │             │
           └──────▲─────────────┘    │ 用户点击恢复/暂停中    │
                  └──────────────────┴──────────┐            │
                                          ┌──────────┐       │
                                          │  paused  │───────┘ 用户点击恢复
                                          └──────────┘
```

### 5.2 暂停与接管实现（Rust 侧）

```rust
// conex-browser/src/panel/controller.rs
pub struct PanelController {
    status: Arc<Mutex<PanelStatus>>,
    pause_tx: tokio::sync::watch::Sender<bool>,      // 暂停标志（AI 队列消费端订阅）
    abort_token: AbortToken,                          // 吊销在途标志（agent-tools::context::AbortToken；经维度 15 Coordinator 注入——吊销链唯一入口为 15 的 Coordinator，T-12）
    fps: Arc<AtomicU8>,                               // 帧率档位（§2.5）
}

impl PanelController {
    pub fn pause(&self);            // pause_tx.send(true) → 指示条 paused；AI 队列挂起（消费端每步检查）
    pub fn resume(&self);           // pause_tx.send(false) → 指示条 idle；AI 队列恢复消费
    pub fn takeover(&self);         // 前端接管请求 → 转发维度 15 Coordinator（吊销链唯一入口，T-12）；本控制器仅状态投影 user-taking-over
    pub fn on_user_input(&self);    // 用户事件到达：上报维度 15 事件总线（吊销由 15 Coordinator 执行）；本控制器仅状态迁移投影
}
```

- **职责边界（T-12/U-9③）**：`PanelController` 仅做 UI 呈现——状态投影与按钮命令（暂停/恢复/接管请求）转发，**不直接触发吊销或状态迁移**；**吊销链唯一入口为维度 15 的 `CollaborationCoordinator`**（revoke → abort → cancel → 版本推进 → 状态切换，对齐 15 §3.4/§6.4）。

- **暂停 = 挂起 AI 动作队列**：队列消费者在每步执行前检查 pause watch（订阅 `pause_tx`），暂停期间不取出新动作；**在途单个动作不被吊销**（可自然完成，避免半截状态），完成后停住等待。
- **接管 = 吊销在途（吊销链唯一入口为维度 15 的 Coordinator，T-12/U-9③）**：PanelController 收到接管请求后转发维度 15 `CollaborationCoordinator`（本控制器仅呈现层动作）→ 维度 15 执行吊销链（revoke → abort → cancel → 版本推进 → 状态切换，15 §3.4）→ 执行器 `is_aborted()` 检查（agent-tools/src/executor.rs:187）→ 工具返回中止错误 → 状态 `user-taking-over`（800ms = 维度 15 `TOKEN_MIN_STABLE_WINDOW` 常量）→ 展示"AI 已暂停"。
- 状态变更经控制通道 Tauri 事件下行（`browser:status`，含 `aiActionText`）。

## 6. 剪贴板 / 拖放 / 上传桥

### 6.1 剪贴板（分级，授权后）

| 场景 | 实现 | 授权 |
|---|---|---|
| 页面内复制（Ctrl+C）/剪切/粘贴到系统剪贴板 | 用户键盘路径经 §3.3 转发，页面自身处理剪贴板（CDP 信任输入视为用户手势；系统剪贴板由浏览器进程直接读写） | 无需桥（天然闭环） |
| 面板外复制 → 粘贴进页面（文本） | 面板"粘贴"按钮：前端读系统剪贴板（授权）→ WS `input_text` → `Input.insertText` | 剪贴板读权限 + 审批记录（维度 17 剪贴板默认拒绝策略） |
| 富文本/图片粘贴 | `Browser.grantPermissions(clipboard-read)` + 受限 `Runtime.evaluate(navigator.clipboard.read)` → 页面内粘贴 | 危险级审批（维度 17 分级；命令名以 11 §3.3 为准，19-L1 修正 setPermission 笔误） |

- 权限颗粒：前端读剪贴板需用户显式触发（按钮点击 = 授权动作），全程落审计（脱敏）。
- 页面侧剪贴板权限缺失（非 secure context）时，面板显示兜底按钮走文本级 insertText 路径。

### 6.2 拖放（双路径）

- 面板捕获 `dragenter/dragover/drop`（阻止默认行为），drop 时经 Tauri 拖放事件拿到**文件绝对路径**（webview 拖放事件可获取文件路径，对齐 Tauri v2 拖放 API）+ 落点坐标（§3.1 归一化）。
- **路径 A（file input）**：`drop` 坐标 → 快照定位目标（backendNodeId 索引，依据维度 13）→ `DOM.setFileInputFiles { files: [绝对路径], backendNodeId }` → 页面正常收到 change 事件（isTrusted、真实文件）。优先路径。
- **路径 B（drop zone，无 file input）**：受限 `Runtime.evaluate` 构造 `DataTransfer { files }` 派发 drop 事件（isTrusted=false 但 files 内容真实；多数上传区可接受）。
- 授权流程：**拖放动作本身即显式意图**（用户主动拖入 = 授权）；路径 A 记审计（文件路径脱敏），路径 B 需额外审批（evaluate 敏感面，维度 17）。

### 6.3 上传

- 面板工具栏"上传"按钮 → Tauri 原生文件对话框 → 路径 → 与路径 A 同一 `DOM.setFileInputFiles` 管线（上传属 dangerous 操作，审批后执行，维度 17）。

| # | 验收项 | 通过标准 |

## 8. 风险与预案

| 风险 | 等级 | 预案 |
|---|---|---|
| 帧延迟超 120ms | 中 | 质量 60→50、maxWidth 降到 1024、Base 档降 6fps；解码已在主线程外（createImageBitmap）；WS 直连无中间跳 |
| 输入抖动（高频 mousemove/触控板洪泛） | 中 | 前端 rAF 合并 + Rust no-wait 发送（不等待 CDP 响应）+ 发送层互斥保序 |
| IME 兼容差异（候选窗定位/合成事件缺失） | 中 | 全收敛 compositionend 文本注入；229 键流计数兜底；兼容矩阵见 §3.7；矩阵外输入法列入已知损失记录 |
| 合成期页面内联候选预览缺失 | 低 | 已知损失；OS 候选窗位于面板层；面板内预览浮层列为后续增强 |
| 修饰键 sticky（窗口切换丢 keyup） | 低 | window.blur 补发 keyUp + 状态清空 |
| 帧乱序/重复 | 低 | ack pacing 单帧在途天然有序；Rust 端 sessionId 去重 + 前端最新帧优先 |
| 面板 resize 期间坐标漂移 | 低 | viewport 消息 + 帧头尺寸双重校准；resize 防抖 150ms |
| WS 断连/降级 | 低 | 指数退避重连 + token 重校验；期间暂停输入转发；控制面独立不受影响 |
| 高交互页面输入卡顿 | 中 | Burst 升帧 + everyNthFrame=1；质量与分辨率按 §2.1 自适应 |
| 拖放路径 B（drop zone）isTrusted=false | 低 | 仅本地文件内容真实；路径 A 优先；路径 B 审批兜底（维度 17） |
