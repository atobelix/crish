# 软件内 AI 协同浏览器——全局选型方案（生态 / 演进视角）

> 视角：最看重与 MCP 生态对齐（复用现有 MCP 桥与 chrome-devtools-mcp attach 能力）、行业趋势（Playwright 内置 MCP、CDP 生态、agent-browser 的 Rust CDP daemon 先例）、长期可演进性（视觉模型升级、跨平台、Computer Use 二期）。
> 复杂度基准：不考虑成本；「达到常规选型 3 倍以上复杂度的方案直接放弃，1–2 倍可稍加考虑」。每个决策均标注复杂度等级。

---

## 一句话结论

**以「Tauri 子 WebView2（独立环境 + 随机高位端口 remote debugging）为 Windows 渲染实例、Rust 自写薄 CDP 客户端为唯一控制通道、CDP 端口同时服务自研 `browser_*` 工具与 chrome-devtools-mcp 插件 attach」为主方案；macOS/Linux 降级为独立 Chromium（Chrome for Testing）后端；快照走「AX 文本树为主 + DOM 注入增强 + 视觉帧可选」双通道；协同靠「注入事件桥 + 快照版本号 + 操作前校验」；Computer Use 二期不碰整机控制，只把一期预留的 screencast 视觉帧 + 坐标级输入升级为「浏览器内视觉主控模式」。**

一句话说明为什么这样选：**CDP 是同时满足「自研工具」「MCP 生态 attach」「行业工具全兼容」的唯一公共协议面**，WebView2 是 Windows 上唯一能同时给出「原生内嵌 UI + 官方 CDP 端口」的渲染实例，而本仓库（Rust 引擎 + MCP 桥 + 审批面）恰好能让 chrome-devtools-mcp 以「插件」身份零改造接入。

## 0. 总体架构（文字草图）

```
┌────────────────────────────── Tauri 主窗口 ──────────────────────────────┐
│ React 前端（apps/crish-desktop）                                          │
│  ├─ 工作区 UI（主 webview）                                                │
│  └─ BrowserCard：地址栏/工具栏 + 页面视图                                   │
│       └─ Tauri 子 WebView2（独立 environment + 独立 user-data-dir）        │

│                    │  ws://127.0.0.1:<port>                                │
├────────────────────────── Rust 内核 ──────────────────────────────────────┤
│ crates/conex-browser-core（新）                                            │
│  ├─ CdpClient（自写，tokio-tungstenite，借鉴 agent-browser cdp/client.rs）│

│  ├─ SnapshotBuilder（AX 树序列化 + DOM 注入增强 + 视觉帧）                  │
│  └─ 注入事件桥（页面内监听 → MutationObserver/input 事件 → 回传 Rust）      │

│  └─ browser_* 工具面（定义+执行，挂 agent-tools 注册表与审批面）            │
│ crates/agent-tools（已有）                                                 │
│  ├─ ToolRegistry / permission.rs 三态审批 / audit.rs                       │
│  └─ mcp/bridge.rs（已有 McpClientBridge）                                  │
│       └─ register_plugin_server(chrome-devtools-mcp, stdio)                │
│            └─ chrome-devtools-mcp --browserUrl http://127.0.0.1:<port>     │
```

两个控制面（AI 与用户）操作的是**同一个**渲染实例（WebView2 页面）；「AI 操作可见」由 CDP 合成事件自然驱动页面（用户直接看到页面变化）；「用户手动操作可被 AI 感知」由注入事件桥回传。chrome-devtools-mcp 与自研工具共享同一 CDP 端口但走**独立 target session**，互不干扰执行上下文。

## 1. 渲染实例

### 候选对比

| 候选 | Windows 支持 | 官方 CDP 端口 | 扩展支持 | 内嵌 UI | 跨平台 | 生态对齐 | 复杂度 |
|---|---|---|---|---|---|---|---|
| Tauri 子 WebView2 | ✅ 一等公民 | ✅ 官方 remote-debugging 文档路径 | ❌ 不支持扩展 | ✅ 原生子 webview | ❌ 仅 Windows（WKWebView/webkit2gtk 无 CDP） | 中（Chromium 内核，DevTools 协议兼容） | 常规–1 倍 |
| 独立 Chromium（CfT） | ✅ | ✅ 完全官方 | ✅ | 弱（独立窗口，需 SetParent 嵌入） | ✅ | ✅ 与全部参考项目 100% 一致 | 1 倍 |
| iframe（现状） | ✅ | ❌ | ❌ | ✅ | ✅ | ❌（X-Frame-Options/CSP 阻断，无协议面） | 常规（但能力天花板低） |
| CEF（Rust 封装 cef-rust） | ✅ | ✅ | ✅ | ✅ | ✅ | ❌（Rust 绑定维护差） | **3 倍+，放弃** |

### 结论

**Windows 主方案：Tauri 子 WebView2**（独立 CoreWebView2Environment：独立 user-data-dir + `additional_browser_args("--remote-debugging-port=<随机高位端口>")`）。**macOS/Linux 降级：独立 Chromium 后端**（同一 Rust 内核，换 BrowserController 实现）。

### 理由

1. **Windows 是主战场**（任务约束），WebView2 是 Windows 上唯一同时满足「原生内嵌（无独立窗口、无标题栏）」+「官方 CDP 端点」的渲染实例。微软官方远程调试文档明确支持通过环境参数开 `--remote-debugging-port`，chrome-devtools-mcp 的 `--browserUrl` attach 模式（`reference/chrome-devtools-mcp/src/browser.ts:77-79`）与 `wsHeaders`（`browser.ts:72-76`，用于 WebView2 CDP 握手不携带 Origin 的兼容）正好配套。
2. **现有产品结构直接复用**：PreviewCard 已有完整的地址栏/工具栏/历史/书签 React 侧实现（`apps/crish-desktop/src/components/workspace/PreviewCard.tsx:64-87`），WebView2 无自己的浏览器 UI，正好由既有工具栏接管；iframe 的 X-Frame-Options/CSP 阻断（`PreviewCard.tsx:151-167` 的 loadError 路径）被彻底根除。
3. **独立 WebView2 环境隔离调试面**：子 webview 用独立 environment（Tauri 2 的 `WebviewWindowBuilder` 支持 per-webview `data_directory` + `additional_browser_args`），调试端口只暴露浏览器子 webview 的 target，不污染主应用 webview（详见 §9 安全）。
4. **降级路径清晰**：macOS WKWebView 与 Linux webkit2gtk 均无 CDP 面，全平台统一独立 Chromium 会使 Windows 也放弃内嵌 UI（复杂度 3 倍化），故只做「Windows WebView2 / 其他平台独立 Chromium」双后端，接口收敛为 `BrowserController` trait。
5. agent-browser 已验证「Rust 直接起 Chrome + CDP」路线可行（`cli/src/native/cdp/chrome.rs`、`--engine` 可切 Lightpanda：`cli/src/native/cdp/lightpanda.rs`），降级后端照搬其成熟做法，不需发明。

### 风险

- WebView2 CDP 属「官方但未列入稳定 SLA」的能力，随 WebView2 runtime 更新可能有行为漂移（如握手 Origin 策略、token 要求）；缓解：CDP 客户端预留 `wsHeaders`/`extraOriginHeaders` 透传（chrome-devtools-mcp 已示范），并把「端口不可用」检测纳入会话启动探活。
- WebView2 不支持 Chrome 扩展：adblock/反检测扩展不可用。一期不需要（目标站点为正常业务站点）；若未来需要，走注入脚本/代理层，不升级为扩展方案（复杂度红线）。
- 子 webview 嵌入的层级（Tauri 2 子 webview 与主 webview 的 z-order/输入焦点）有已知坑：用户点击、键盘焦点要在子 webview 与主 UI 间正确切换。缓解：BrowserCard 内独占焦点管理 + 提交前专项 e2e 验证（复用 tests/e2e 的 keyboard-navigation 门禁思路）。

## 2. AI 控制通道（重点）

### 候选对比

| 候选 | chrome-devtools-mcp attach | 事件感知（用户操作） | trusted 输入事件 | 页面上下文（DOM 级） | DevTools 级能力（网络/trace/screencast） | 复杂度 |
|---|---|---|---|---|---|---|
| 纯 CDP | ✅ 天然（同一端口） | ❌ 用户真实输入不产生 CDP 事件 | ✅ Input 域 | 有限（需 Runtime.evaluate 间接） | ✅ 全部 | 常规 |
| 注入脚本桥（页面内 JS + WS） | ❌ 不识别 | ✅ 原生监听（click/input/mutation） | ❌ 页面内合成事件 untrusted | ✅ 原生 | ❌ 无 | 常规–1 倍 |
| **CDP 主 + 注入事件桥辅助（推荐）** | ✅ | ✅ | ✅ | ✅ | ✅ | 1–2 倍 |
| 双轨平行（两套完整通道） | 部分 | ✅ | ✅ | ✅ | ✅ | **3 倍+，放弃** |

### 结论

**CDP 为主控制通道，注入脚本桥仅作「协同感知面」辅助**（监听用户输入与页面变化回传，不承载操作执行）。自研工具与 chrome-devtools-mcp 都走同一 CDP 端口，MCP 兼容自然达成，不需要任何桥接层。

### 理由（MCP 兼容如何自然达成——核心论证）

1. **一个端口、两个客户端、互不干扰**：chrome-devtools-mcp 以 stdio MCP 插件形式经现有 `McpClientBridge` + `register_plugin_server`（`crates/agent-tools/src/mcp/mod.rs:51-52`、`bridge.rs:676-678` 的 `mcp_<server>__<tool>` 命名）接入，其 `--browserUrl http://127.0.0.1:<port>`（`browser.ts:77-79`）attach 我们的 WebView2。CDP 的 browser-level WebSocket 允许多客户端各建独立 target session；自研工具与 MCP 插件的执行上下文天然隔离。**MCP 兼容 = 打开一个调试端口 + 注册一个插件**，零适配成本，且随 chrome-devtools-mcp 上游演进自动获得新工具（lighthouse/memory/performance 等，`tools/tools.ts:30-46` 全工具面）。
2. **行业趋势佐证**：Playwright 官方 MCP 已把「playwright-core 内置 MCP 工具」作为默认发布物（`reference/playwright-mcp/index.js:18` 一行 `require('playwright-core/lib/coreBundle')`）——工具面收敛到浏览器内核是共识，我们「自研薄工具面 + 生态 MCP 补深」正对齐该趋势；agent-browser 也证明 Rust 侧直接吃 CDP 是产品级可行路线（`cli/src/native/cdp/client.rs`）。
3. **为什么需要注入桥补协同感知**：CDP 不会把「用户真实鼠标/键盘输入」作为事件下发（Input 域只回显合成事件），AI 要感知「用户抢了操作」，唯一可靠路径是页面内事件监听（pointerdown/click/input/mutation）回传——这正是 skyvern 的 domUtils.js 注入（`reference/skyvern/skyvern/webeye/utils/page.py` 反复重注入 domUtils.js 的模式）与 browser-use 的 DOM 增强（`browser_use/dom/service.py:89-155` 隐藏元素/可视性分析）证明可行的路径。
4. **不做双轨的原因**：如果自研工具走注入桥、MCP 走 CDP，同一操作会有两套执行路径（trusted/untrusted 事件差异、状态不一致），且所有注入桥实现细节（跨域 iframe、shadow DOM、navigation 重注入、页面崩溃恢复）都要自研维护——这是 3 倍复杂度陷阱。注入桥收敛为「只上报事件、不执行操作」，把全部副作用收敛到 CDP 单一路径。

### 风险

- WebView2 CDP 的 WebSocket 握手可能拒绝带 Origin 的连接（puppeteer 连 WebView2 的已知问题），需按 chrome-devtools-mcp 的 wsHeaders 模式（`browser.ts:49-51`）在客户端侧透传；自写客户端天然可控这一点。
- 注入桥脚本在 navigation 后失效，需在每次 `Page.loadEventFired` 后重注入（skyvern `page.py:1168-1198` 有成熟的重注入/重试模式，直接借鉴）。
- 两个 CDP 客户端同时启用同一能力域（如 Runtime）时的 enable 竞争：chrome-devtools-mcp 与自研客户端都以独立 session 运行则无冲突；若确需共享 session 的功能（极少），以「先到先得 + 失败重试」处理。

## 3. Rust CDP 客户端

### 候选对比

| 候选 | 维护活跃度 | 与 WebView2 握手兼容（Origin/headers） | 多客户端 session 并存 | 体积/依赖 | 与仓库风格匹配 | 复杂度 |
|---|---|---|---|---|---|---|
| chromiumoxide | 低（近两年基本停滞） | 差（无 wsHeaders 透传） | 差（抽象绑定单连接） | 大（全协议域 + 内部 actor 化） | 中 | 常规（但演进是死路） |
| **自写薄客户端（推荐）** | 自研可控 | ✅ 完全可控 | ✅ 自设计 | 极小（tokio-tungstenite + serde_json） | ✅ Rust 原生 | 常规 |
| 代理复用 agent-browser 代码 | 依赖上游（vercel-labs，版本漂移快） | ✅ | ✅ | 中（需 fork 锁定） | 中 | 1 倍 |

### 结论

**自写薄 CDP 客户端**（crate：conex-browser-core），协议类型从 agent-browser 的 `cdp/types.rs` 与 `cdp-protocol/*.json`（browser_protocol.json/js_protocol.json）提取所需子集，客户端骨架直接参考其 `cdp/client.rs`（436 行：tokio-tungstenite + `PendingMap` oneshot + `broadcast` 事件扇出 + `PendingGuard` 取消清理，`client.rs:15-46`、`52-71`）。

### 理由

1. **需要面极窄**：只需要 ~15 个域（Browser/Target/Page/Runtime/Input/Accessibility/DOM/Emulation/Network/Storage/Cookie/Performance/Page.screencast 等），chromiumoxide 的「全协议生成 + actor 架构」对我们是负资产（升级协议要等上游，而我们的需求面自写约 800–1200 行）。
2. **WebView2 握手特殊性必须自控**：`wsHeaders`、Origin 策略、`max_message_size=None`（`client.rs:98-102`）这类兼容点，第三方 crate 不提供透传，自写一行属性的事，chromiumoxide 里是改库。
3. **多客户端并存是本期刚需**（§2）：我们的客户端要支持「同端口下自研 session + 为 MCP 预留的空间」，自写才能按需设计 session 分配；chromiumoxide 的连接抽象不支持。
4. **agent-browser 是活证据**：它整库不依赖 chromiumoxide，纯 tokio-tungstenite 完成 launch/navigate/snapshot/点击/网络全链路，并有 320 单测 + 18 e2e（`AGENTS.md` 测试节），证明该路线成熟度足够。
5. 从 `cdp-protocol/*.json` 生成 Rust 类型可用 build.rs（agent-browser 的 `build.rs` 已示范），避免手写协议类型，同时保持薄（只生成用到的域）。

### 风险

- 自写意味着 CDP 协议演进（Chrome 每季度新增域）需自行跟进；缓解：只跟进用到的域，且浏览器侧 pin 版本（WebView2 随 Windows 更新，不主动追新），用 `Browser.getVersion` 上报版本做兼容探活。
- 事件协议（`Page.*` 等）解析错误要容错：未知事件字段一律忽略而非报错（agent-browser `CdpEvent` 的宽容解析模式）。

## 4. 感知快照（AX / DOM / 视觉混合）

### 候选对比

| 候选 | token 效率 | 交互元素覆盖 | 视觉模型升级演进 | 实现成本 | 复杂度 |
|---|---|---|---|---|---|
| 纯 AX 文本树 | 最优 | 中（无 a11y 语义的 div 点击器丢失） | 弱（无视觉信息） | 低 | 常规 |
| AX + DOM 注入增强 | 优 | 优（clickable 检测补全） | 中 | 中 | 1 倍 |
| 纯视觉（截图+坐标） | 差（token 高） | 中（依赖模型视觉） | 强 | 中 | 1 倍 |
| **AX 主 + DOM 增强 + 视觉帧可选（推荐）** | 优 | 优 | **强（视觉帧即插即用）** | 中 | 1–2 倍 |

### 结论

**快照产出抽象为双通道**：`browser_snapshot` 输出「AX 文本树（默认）+ DOM 注入补全的可交互元素 + 稳定 uid」；`browser_screenshot` / `browser_screencast_start` 输出视觉帧（PNG/JPEG，可选传模型）。快照接口预留 `include_visual` 参数，视觉模型升级后无需改工具面，只需改模型侧调用策略——与 browser-use 的 `use_vision: "auto"`（`browser_use` 文档 Agent All Parameters 节）完全同构。

### 理由（演进路径为本维度核心）

1. **AX 树是行业共识的第一通道**：chrome-devtools-mcp `take_snapshot`（`src/tools/snapshot.ts:12-44`，a11y 树 + uid + 优先于 screenshot 的提示文案）、agent-browser `snapshot.rs`（`INTERACTIVE_ROLES`/`CONTENT_ROLES` 角色过滤 + `ref_id` 映射，`snapshot.rs:11-66`）均以 AX 为主；我们的实现以 agent-browser 的序列化器为蓝本（含层级/名称/checked/disabled/value_text 字段裁剪，`snapshot.rs:86-100`）。
2. **DOM 注入增强补 AX 盲区**：browser-use 的 `ClickableElementDetector` + `paint_order_filtering`（`browser_use/dom/service.py:89-155`）证明「无语义的 div 按钮/隐藏交互元素」必须靠 DOM 侧判断；注入桥（§2）同时承担「采集增强信息」职责，一份注入脚本两用。
3. **视觉帧是二期 Computer Use 的接口预留**：`Page.startScreencast`（chrome-devtools-mcp `src/tools/screencast.ts` 已有完整实现示范）输出 JPEG 帧流；一期就把帧流转发通道建好（Rust → 前端预览与模型共用一个帧源），二期视觉主控模式只需消费同一条流。
4. **快照版本号**：每次快照生成 `snapshotVersion`（单调递增），页面变化（注入桥事件）使版本失效——这是 §6 冲突处理与「操作前校验」的基础设施，必须一期内置。

### 风险

- AX 树在巨型页面（数千节点）token 爆炸：实现 depth/compact 选项（agent-browser `SnapshotOptions.compact/depth`，`snapshot.rs:77-84` 已示范），默认裁剪到交互元素 + 上下两级。
- 注入增强脚本与页面冲突（全局污染）：脚本必须以隔离方式注入（命名空间包裹），并在快照后移除副作用（browser-use `remove_highlight` 清理模式）。
- 视觉帧带宽：screencast 默认 320ms 帧间隔 + JPEG 低质量，只有模型请求时才全帧。

## 5. 元素定位与操作执行

### 候选对比

| 候选 | 稳定性（动态页面） | 事件真实性 | 实现成本 | 复杂度 |
|---|---|---|---|---|
| CSS selector | 差（页面改版即失效） | 中（selector + click()） | 低 | 常规 |
| uid 索引（AX/DOM 快照内引用） | 优（快照内稳定） | 中 | 中 | 常规 |
| **uid 引用 + 快照校验 + CDP Input 坐标点击（推荐）** | 优 | **优（trusted 事件）** | 中 | 常规–1 倍 |
| 视觉坐标（纯像素） | 差（布局漂移） | 优 | 中 | 1 倍（二期再用） |

### 结论

**定位用快照内 uid（ref_id）解析到 DOM 节点 → `DOM.getBoxModel` 取坐标 → CDP `Input.dispatchMouseEvent` 执行**；键盘/表单走 `Input.dispatchKeyEvent` + `Input.insertText`；页面内 `element.click()` 仅作兜底（Input 域不可用时的降级路径）。坐标执行前做「快照版本 + 元素存在 + 位置未漂移」三重校验。

### 理由

1. **定位稳定性**：uid 是快照内的逻辑引用（agent-browser 的 `ref_id ↔ backend_node_id` 映射，`element.rs:9` 的 `resolve_ax_session/RefMap`），不依赖 CSS 文本，动态页面重渲染后只需重新快照；chrome-devtools-mcp 同样以「snapshot uid」为执行前提（`snapshot.ts` 的 uid 语义），生态内一致。
2. **执行真实性**：CDP Input 域产生的是浏览器级 trusted 事件，能触发 hover 态、原生事件顺序、站点反自动化检测相对友好；页面内 JS `.click()` 是 untrusted 合成事件，被部分站点（登录按钮/支付）拒绝——这是必须用 Input 域的核心原因，agent-browser `interaction.rs` / `actions.rs` 全链路均走 CDP Input。
3. **坐标层是二期预留**：坐标级 `mouse_move/mouse_down/mouse_up/mouse_wheel` 工具（agent-browser mcp.rs 已定义 `agent_browser_mouse_move` 等，`mcp.rs:71-74`）一期直接纳入 browser_* 工具族，二期视觉主控模式（Computer Use）直接复用，不需要新执行层。

### 风险

- 坐标点击对「元素位置变化」（懒加载、滚动）敏感：三重校验不通过即返回「页面已变化，请重新快照」，不做坐标猜补（零容忍「魔术数字补偿」红线）。
- 跨域 iframe 内元素：CDP 需先 `Target.attachToTarget` 或走 frame session；一期支持「主 frame + 同源 iframe」，跨域 iframe 标记为受限能力（browser-use `cross_origin_iframes` 参数默认关闭同款取舍）。

## 6. 协同模型：单实例双控制面

### 候选对比

| 候选 | 用户可手动介入 | AI 感知用户操作 | 冲突处理 | 复杂度 |
|---|---|---|---|---|
| 独立实例（AI 用独立浏览器，用户用另一个） | 否（看不到 AI 动作） | 否 | 无需 | 常规（但产品目标不满足） |
| 单实例 + 轮询状态 | 是 | 差（延迟/粒度） | 弱 | 常规 |
| **单实例 + 注入事件桥 + 快照版本校验（推荐）** | 是 | **是（即时）** | **强（版本失效重来）** | 1–2 倍 |
| 操作锁（AI 执行时冻结用户输入） | 受限（与产品目标冲突） | 否 | 强 | 常规 |

### 结论

**单实例、双控制面、无锁协作**：AI 操作经 CDP 合成事件驱动同一页面（用户全程可见可打断）；用户操作经注入桥（pointerdown/click/input/scroll/mutation 监听）即时回传；每次 AI 操作执行前校验快照版本与元素位置，版本失效（无论因用户介入还是页面自变）则返回「重新快照」错误。

### 理由

1. **产品目标就是「用户和 AI 共同操作」**：操作锁方案（AI 执行期间屏蔽用户输入）直接违背需求；轮询方案感知粒度差（用户快速连续输入无法收敛）；注入桥是唯一能拿到「页面真实变化」的路径（CDP 不回传用户输入，见 §2 理由 3）。
2. **冲突语义收敛为「快照版本」一个概念**：无论是用户点击、页面定时器还是 AI 自身上次操作导致的 DOM 变化，注入桥统一上报 → 版本号 +1 → 所有持旧版本快照的操作一律拒绝。这套「乐观并发 + 失败重来」与浏览器自动化生态（browser-use 的 `test_action_loop_detection`、paint order 校验同精神）一致，且实现面小（一个计数器 + 一个校验函数）。
3. **AI 操作可见性免费获得**：CDP Input 事件在页面内就是真实输入，页面即时响应，无需额外「演示」层；如需更强的可见性（AI 操作高亮），一期在注入脚本里加「操作前高亮类」（browser-use `highlight_elements` 同款），成本极低。
4. 事件同步的失败模式（用户操作与 AI 操作恰好同帧）：以「AI 操作原子性」兜底——单次 browser_act 只做一件事，双事件竞争时页面行为由浏览器决定，AI 侧下次快照自然收敛。

### 风险

- 注入桥漏报（页面重写 DOM 不触发 mutation、或用户操作发生在注入脚本失效窗口）：缓解 = 每次操作前「目标元素存在性 + 快照版本」双查，漏报只导致一次失败重试，不造成错误状态。
- 用户连续操作导致版本频繁失效，AI 进度停滞：缓解 = 版本失效不报错，返回「页面已变化」软信号，模型重新快照（成本可控，token 有上限保护）。

## 7. 数据导入（Chrome/Edge 数据）

### 候选对比

| 候选 | 覆盖面 | 风险（用户数据） | WebView2 可行性 | 实现成本 | 复杂度 |
|---|---|---|---|---|---|
| profile 目录复制 | 全（cookie/登录态/扩展） | 高（锁文件、密码 vault、误操作） | ❌ **不可行**（WebView2 不识别 Chrome profile） | 低 | 常规（但被 WebView2 否决） |
| **storage_state（cookies + localStorage 导出/导入）** | 登录态 | 低（显式、可审计） | ✅ 走 CDP Storage/Network 域 | 中 | 常规 |
| 书签/历史解析导入 | 书签历史 | 低 | ✅ 解析 Chrome/Edge Bookmarks JSON + History SQLite | 中 | 常规–1 倍 |
| 引导登录（首登后保存 storage_state） | 新站点 | 无 | ✅ | 低 | 常规 |

### 结论

**storage_state 为主（cookies/localStorage 经 CDP `Network.getAllCookies` / `Network.setCookies` + `Storage` 域导入导出）+ 书签/历史解析导入（Chrome/Edge 的 `Bookmarks` JSON 与 `History` SQLite 只读解析）+ 引导登录兜底**。**放弃 profile 复制**（WebView2 后端不可能，且是用户数据高危操作）。

### 理由

1. **渲染实例（§1）直接否决 profile 复制**：WebView2 使用自有 user-data-dir，不识别 Chrome/Edge profile 目录；即便在 macOS/Linux Chromium 后端可行（browser-use `user_data_dir` 直连、agent-browser `--profile`），也要求用户**先退出 Chrome**（browser-use 文档明示）且复制整个 profile 违反「不碰用户原始数据」原则——只在降级后端作为可选高级项，默认关闭。
2. **storage_state 是生态标准**：Playwright storage_state、browser-use `storage_state` 参数、agent-browser `--state` 参数（`connection.rs:448` DaemonOptions 的 `state` 字段）均为同语义；实现有充分先例，且导出物是明文 JSON，可审计、可撤回。
3. **引导登录是最优主路径**：browser-use 的推荐做法（Real Browser 登录一次 → 保存 profile/state），我们做成「browser_auth_save / browser_auth_login」（agent-browser mcp.rs 已有 `agent_browser_auth_save`/`auth_login`，`mcp.rs:120-121`）——让用户在弹出的浏览器内登录目标站点，然后自动保存 storage_state，后续会话秒级恢复。不碰 Chrome/Edge 数据却能达到同等效果。
4. 书签/历史：Chrome/Edge 的 `Bookmarks` 为 JSON、`History` 为 SQLite，只读解析成本低，且直接复用 PreviewCard 现有的书签/历史面板（`PreviewCard.tsx:89-101`）。

### 风险

- cookies 中的 HttpOnly/Secure 属性经 CDP 导出导入时需保持原样（同域校验）；SSO 站点（OAuth 弹窗态）依赖 localStorage 域隔离，需全域导出而非仅目标域。
- 用户主浏览器数据（密码 vault、DPAPI 加密 cookie）不可读，属预期内能力边界，UI 上明示「不导入密码」。

## 8. 工具集：browser_* 工具族 + MCP 并存/冲突管理

### 候选对比

| 候选 | 与 MCP 生态关系 | 命名冲突 | 权限差异管理 | 复杂度 |
|---|---|---|---|---|
| 完全自研全量工具面 | 竞争（重复造轮子） | 无 | 统一 | 3 倍（重实现 lighthouse/memory/trace） |
| 完全不自研（全走 MCP 插件） | 依赖上游工具定义 | 无 | MCP 面审批弱 | 常规（但高频路径不可控、跨后端依赖） |
| **自研高频闭环 + MCP 补深（推荐）** | 互补分工 | 前缀隔离 | 双轨审批适配 | 常规–1 倍 |

### 结论

**自研 `browser_*` 工具族覆盖「感知—决策—执行—校验」闭环**（约 18 个：navigate/go_back/forward/reload/snapshot/act/click/type/scroll/wait/screenshot/screencast_start/stop/tabs/console/network/evaluate/extract）；**深度调试能力（lighthouse/performance/memory/trace/heap）不自研，由 chrome-devtools-mcp 插件以 `mcp_cdm__*` 提供**（`mcp_<server>__<tool>` 命名已隔离，`bridge.rs:677-678`）。

### 分工矩阵

| 能力 | 提供方 | 命名 | 权限模型 |
|---|---|---|---|
| 导航/快照/点击/输入/滚动/等待 | 自研 | `browser_navigate` / `browser_snapshot` / `browser_act` … | 引擎三态审批（§9） |
| 视觉帧（截图/流） | 自研 | `browser_screenshot` / `browser_screencast_start/stop` | 只读 |
| 标签/控制台/网络观察 | 自研 | `browser_tabs_*` / `browser_console` / `browser_network_*` | 只读 + 需审批（拦截类） |
| 数据导入 | 自研 | `browser_auth_*` / `browser_import_*` / `browser_state_*` | dangerous（写用户数据） |
| Lighthouse/性能 trace/内存堆/深调试 | MCP 插件（chrome-devtools-mcp） | `mcp_cdm__lighthouse_*` 等 | 经插件注册表，dangerous 默认 false，`requires_approval` 由插件注解（readOnlyHint）映射 |
| 极深能力（WebMCP 页内工具） | MCP 插件（`webmcp.ts` 的 `execute_webmcp_tool`） | `mcp_cdm__execute_webmcp_tool` | 需审批（页面内执行代码） |

### 理由

1. **命名冲突零风险**：`browser_` 前缀与 MCP 桥的 `mcp_<server>__` 前缀（`bridge.rs:676-678` 测试用例 `mcp_files__read`、`mcp_my_server__read` 证明命名空间隔离）天然不重叠；`browser_act` 这类复合动作不存在于 chrome-devtools-mcp 工具集（其是单动作：click/type 等），即使功能重叠也只是「同目标双入口」，由权限/描述引导模型选型。
2. **工具面规模对齐生态先例**：chrome-devtools-mcp slim 集（`slim/tools.ts`：screenshot/navigate/evaluate/…，97 行）与 agent-browser 的 ~120 个 `agent_browser_*` 工具（`mcp.rs:23-121`）证明「精而全」的可裁剪工具面是行业标准形态；我们的 18 个自研工具是两者的交集裁剪 + `browser_act` 复合动作（对齐 browser-use 的「一次 act 多字段」思想：`max_actions_per_step`）。
3. **深度工具不自研的生态理由**：lighthouse 的 DevTools 前端捆绑（`src/third_party/lighthouse-devtools-mcp-bundle.js`）与 trace-processing 解析（`src/trace-processing/parse.ts`）是 Google 持续维护的重资产，重实现即 3 倍复杂度红线；以「注册即用」的插件方式获取，且随 chrome-devtools-mcp 版本升级自动获得修复（我们已具备插件版本管理基础设施：`register_plugin_server`）。
4. **权限差异管理**：自研工具精确打标（dangerous/只读），走现有三态引擎（`permission.rs:78-80`）；MCP 工具经 `adapt_tool_list` 进注册表（`bridge.rs:700-706`），由插件注解映射危险等级；策略（confirm-actions/smart/none，agent-browser `action_policy` 语义）作为全局开关统一生效，避免「两套权限世界观」。

### 风险

- chrome-devtools-mcp 与自研工具同时 attach 时，其 daemon 机制（`src/daemon/daemon.ts`）若被用户以独立进程启动会起第二个 Chrome——必须固定以「`--browserUrl` attach 模式」配置插件（`browser.ts:77-79`），禁止其自带 launch 路径。
- 工具描述冲突导致模型选型混乱：`browser_act` 与 `mcp_cdm__click` 并存时，在工具描述中明示「首选 browser_act，深调试才用 mcp_cdm__*」（工具路由提示词约定，属于文档层而非代码层）。

## 9. 安全（端口、域名白名单、审批）

### 结论与设计

| 面 | 决策 | 理由/证据 |
|---|---|---|
| 端口 | 随机高位端口（49152 起），仅绑定 127.0.0.1；端口文件写会话目录（对齐 agent-browser `get_port_for_session`，`connection.rs:377-385`） | 固定端口被抢占/被探测；agent-browser 已验证 hash 端口 + 文件覆盖机制 |
| 端点暴露 | WebView2 子 webview 用**独立环境**（独立 user-data-dir + 独立调试端口），主应用 webview 不共享端口；target 列表过滤 `asset.localhost`/`localhost:5174` 等主 UI target | 防止 CDP 面泄漏到应用自身页面（`tauri.conf.json:24-30` CSP 已限制 connect-src，端口面同样要隔离） |
| 域名白名单 | `allowed_domains` / `prohibited_domains`（browser-use 语义，含通配规则与 TLD 通配禁用）；默认不设限，配置开启 | 对齐 browser-use 文档（`allowed_domains` 参数规格）；导航前校验（agent-browser `policy.rs` + `DaemonOptions.allowed_domains`，`connection.rs:456`） |
| 审批 | 复用三态引擎（`permission.rs`）：`browser_*` 精确打标；策略化审批（confirm-actions/smart/none）控制**何时弹窗**（默认 smart：导航/快照/只读自动，输入/下载/导入弹窗，写用户数据 dangerous）；红线不可豁免（`permission.rs:9-11`） | 现有审批面零改造接入；「smart」策略对齐 agent-browser `confirm_actions` 与 browser-use 的 `action_policy` |
| 凭据/数据 | storage_state 文件存用户目录（`.crish-profiles/`），文件权限 0600；cookie 读写工具标记 dangerous + 审批；审计日志（现有 `audit.rs`）记录全部 browser 工具调用含 URL | 数据导入是高价值攻击面，导出物即「登录态等价物」，必须显式审批 + 落审计 |
| CDP 客户端验证 | 会话令牌（随机 secret）仅经内核与 Tauri 进程内传递，`/json/list` 拉取 target 时验证 | 纵深防御：端口本身 loopback-only，防其他进程嗅探 |
| 注入脚本 | 无 `--disable-web-security`、无 `--allow-file-access`（agent-browser 默认关闭同款）；注入脚本命名空间隔离 | 页面内脚本不引入额外特权 |

### 风险

- WebView2 调试端口随环境共享的风险（若无法做到 per-webview 独立环境）：回退方案 = 与主 webview 共用端口但用 targetFilter 严格过滤（chrome-devtools-mcp 的 `targetFilter` 机制，`browser.ts:24-44` 已示范）。
- 域名白名单误配置导致站点不可用：白名单为空 = 不限制（默认宽松），与限制模式分开配置，避免「默认拒绝」误伤本地开发站点。

## 10. Computer Use（电脑操作）二期

### 生态定位对比

| 候选 | 生态对齐 | 与本产品形态契合 | 难度 | 复杂度 |
|---|---|---|---|---|
| Anthropic computer-use-demo 路线（整机截图 + 坐标输入） | 与 Claude API 工具 schema 对齐（`tools/computer.py:294-425` 多版本 ComputerTool） | 差（无 DOM、无浏览器内上下文、整机权限） | 高（屏幕采集/缩放/无障碍树/系统权限） | **3 倍+，放弃** |
| OpenAI CUA 路线（云端 VM + 屏幕流） | 闭源 API | 差（依赖外部 VM） | 高 | 3 倍+，放弃 |
| **浏览器内视觉主控模式（一期预留接口）** | 工具 schema 对齐 computer use 语义（screenshot 帧 + 坐标动作），行为域限定浏览器 | **优（就在产品内）** | 低（CDP 已覆盖全部执行面） | 常规–1 倍 |

### 结论

**二期 = 「浏览器内 Computer Use」模式，不做整机电脑操作**。一期把两项基础设施建成（两者都是 CDP 一个域的事）：(a) `Page.startScreencast` 视觉帧流（`browser_screencast_*` 工具，chrome-devtools-mcp `screencast.ts` 全实现可参考）；(b) 坐标级输入工具（`browser_mouse_move/click/wheel` + `browser_act_coordinates`，agent-browser `mcp.rs:71-74` 已定义同类）。二期只需在模型侧切换为「帧 + 坐标动作」协议（坐标按 screencast 帧缩放，参考 computer-use-demo `scale_coordinates`，`computer.py:268-293`），工具面零新增。

### 理由

1. **生态对齐的正确粒度**：Anthropic/OpenAI 的 computer use 是「整台电脑」代理，其价值（任意桌面应用）与我们的产品（软件内浏览器）不重叠；但**工具 schema 语义（screenshot 帧 + 坐标动作 + 缩放约定）应当对齐**——这保证未来若接入 Claude/OpenAI 的 computer-use API 或类模型，只需换消息格式，工具执行层不变。
2. **一期零成本留接口**：screencast 与坐标输入本来就该做（快照维度 §4 与执行维度 §5 都需要），二期是「纯模型侧工作」而非新系统，符合「3 倍复杂度红线」管理。
3. **明确不做整机的理由**：屏幕采集（Windows 上 GPU 捕获、多屏、DPIAware 缩放）、整机无障碍树（UI Automation）、系统级输入注入（焦点/权限弹窗）是一个全新安全与兼容域，且与浏览器场景无复用；真需要时（远期）以「外部 Chromium 窗口模式」（§1 降级后端已有）承载，仍不碰系统级。

### 风险

- 视觉主控在截图不清晰的场景（视频/动画站点）精度下降：兜底 = 模式切换回 AX 文本快照（双通道设计 §4 保证随时可切换）。
- 坐标缩放（DPR/窗口尺寸变化）造成偏差：screencast 帧带 viewport 元数据 + `scale_coordinates` 同款换算，操作前校准。

## 11. 技术栈与 crate 划分

### 结论

新增 **2 个 crate**（不新增语言运行时；全部 Rust，与仓库栈一致）：

| crate | 职责 | 关键依赖 | 复杂度 |
|---|---|---|---|
| `crates/conex-browser-core` | CdpClient（连接/session/事件扇出）+ CDP 协议类型（build.rs 从 `cdp-protocol/*.json` 生成子集）+ SnapshotBuilder（AX 序列化 + 注入脚本采集）+ 注入事件桥 + BrowserController trait（WebView2/Chromium 双后端实现）+ storage_state/书签导入 | tokio, tokio-tungstenite, serde_json, futures-util | 常规–1 倍 |
| `crates/conex-browser-tools` | browser_* 工具定义与执行（挂 agent-tools ToolDefinition/注册表/审批/审计）；会话管理（端口分配、生命周期、快照版本、操作锁语义）；BrowserSession 供工具上下文注入 | conex-browser-core, agent-tools, conex-types | 常规 |

架构要点：

1. **BrowserController trait 是跨平台降级缝**（§1）：`WebView2Controller`（Windows，读环境端口）/ `ChromiumController`（macOS/Linux + 独立 Chromium，走 DevToolsActivePort 发现，`browser.ts:84-111` 的端口文件机制），Rust 内核与前端工具面只面对 trait。
2. **端口与生命周期归内核**：Rust 内核负责起/停 WebView2（经 Tauri 事件或配置下发端口），前端只消费状态（工具栏/页面视图）。Tauri 侧改动面 = 子 webview 创建参数（`data_directory` + `additional_browser_args`）+ 一个 IPC 通道上报端口。
3. **MCP 插件装配零改动**：chrome-devtools-mcp 经现有 `register_plugin_server`（`mcp/mod.rs:51`）注册，配置为 `--browserUrl http://127.0.0.1:<port>`；唯一新增的是「插件配置模板」，随会话启动填充端口。
4. **测试策略**：core 层协议解析与快照序列化走单测（agent-browser 320 单测模式）；执行链路走 e2e（`#[ignore]` + 串行，agent-browser `e2e_tests.rs` 模式），并挂入仓库既有前端门禁体系（tests/e2e 专项 spec 扩展：browser 面板操作、AI 操作可见性、双控制面冲突）。

### 风险

- 两个 crate 的边界（core 纯协议/会话 vs tools 工具面）若划分过细会拖慢迭代：维持「core 无 agent-tools 依赖、tools 依赖 core」单向依赖，避免循环。
- WebView2 控制器只在 Windows 编译（`#[cfg(target_os = "windows")]`），CI 跨平台构建需条件编译保护（agent-browser 的 windows-sys 条件依赖同款，`Cargo.toml:42-43`）。

## 12. 关键决策点清单与复杂度汇总

| # | 决策点 | 结论 | 复杂度 |
|---|---|---|---|
| 1 | 渲染实例 | Tauri 子 WebView2（Windows，独立环境+调试端口）；macOS/Linux 独立 Chromium 降级 | 1–2 倍 |
| 2 | AI 控制通道 | **CDP 单一控制通道**（自研工具与 chrome-devtools-mcp 共享端口、独立 session）；注入脚本桥仅作协同感知 | 1–2 倍 |
| 3 | Rust CDP 客户端 | **自写薄客户端**（借鉴 agent-browser cdp/client.rs，build.rs 生成协议类型）；否决 chromiumoxide | 常规 |
| 4 | 感知快照 | AX 文本树主 + DOM 注入增强 + 视觉帧可选（双通道，snapshotVersion 基础设施一期内置） | 1–2 倍 |
| 5 | 元素定位/执行 | 快照 uid → getBoxModel 坐标 → CDP Input 域 trusted 事件；执行前三重校验 | 常规–1 倍 |
| 6 | 协同模型 | 单实例双控制面无锁；注入事件桥回传 + 快照版本失效重来 | 1–2 倍 |
| 7 | 数据导入 | storage_state（CDP cookies/localStorage）+ 书签历史解析 + 引导登录；否决 profile 复制 | 常规–1 倍 |
| 8 | 工具集 | 自研 browser_* 18 工具闭环 + chrome-devtools-mcp 插件补深；前缀隔离、双轨审批适配 | 常规–1 倍 |
| 9 | 安全 | 随机高位 loopback 端口 + 独立环境隔离 + 白名单可选 + 三态审批 + 凭据文件 0600 + 审计 | 常规 |
| 10 | Computer Use 二期 | 浏览器内视觉主控模式（一期预留 screencast + 坐标输入接口）；否决整机 computer use | 常规–1 倍 |
| 11 | crate 划分 | 新增 conex-browser-core + conex-browser-tools，单向依赖，条件编译跨平台 | 常规 |

**整体复杂度评估：约 1.5 倍**（各维度 1–2 倍，无 3 倍项）。核心杠杆：CDP 公共协议面一箭三雕（自研工具 / MCP attach / 二期视觉主控），渲染与控制面的高难度选项（CEF、双轨、profile 复制、整机 computer use、全量自研深调试工具）均在红线检查中被否决。
