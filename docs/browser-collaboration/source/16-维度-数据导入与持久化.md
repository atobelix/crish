## 0. 范围、原则与模块布局

### 0.1 范围

本维度落地四条数据通道与一条生命周期规则：

| 通道 | 定位 | 说明 |
|---|---|---|
| 面板内引导登录 | **主路径** | 用户在面板浏览器内手动登录，cookie 直接落于受管 profile；零解密、零隐私面 |
| 最小文件集 profile 复制 | 迁移路径 | 用户显式选择来源浏览器与目标 profile，仅复制必要文件（Cookies/书签/Local State 等），**显式排除**密码库/历史/表单数据 |
| storage_state 导入/导出 | 辅助通道 | 标准 JSON，默认不落盘（内存传递），导出需显式授权 |
| 书签/历史独立导入 | 独立入口 | 书签 JSON 解析 + 历史 SQLite 只读读取（conex-db 复用），与登录态导入解耦 |

生命周期规则（R-2 裁决，与维度 10 §4 一致）：受管 profile 持久化开关（`persist` 唯一存于 `profile_meta.json`，用户选择保留后重启保留登录态）；临时 profile（`sessions/<uuid>/`）用完即删——**直接删除，不走 conex-fs trash**（非用户资产）；受管 profile（`managed/<name>/`）是用户资产，删除**走 conex-fs trash**（trash.rs:26-29 铁律）。

### 0.2 边界声明（明确不做）

- 不导入密码（Login Data 显式排除，快照/日志脱敏）；
- 不整目录复制来源 profile；
- storage_state 不默认落盘、不作为登录态主通道；
- 不触碰来源目录（复制为只读源，回写禁止）；
- 下载管理归维度 17（受管目录 + 授权打开，见 17 §7.1），本维度不涉及（对齐评审 19-L6）。

## 1. 引导登录路径（主路径）

### 1.1 流程（面板内登录）

**首启一次性隐私告知（合规 C6，21 评审 L11）**：面板首次启用时展示一次性告知——「AI 可读取面板浏览器内的快照/截图/表单值（密码字段脱敏）；数据仅存本地、不上传；你随时可停止 AI 操作」。与 18 §7.1 风险确认弹窗同构，仅一次不重复打扰。

```
面板浏览器启动（临时或受管 profile，见 §7）→ 用户在面板内导航到目标站点
→ 用户经面板输入转发层完成登录（账号/密码/2FA/验证码均走用户真实输入，见维度 12）
→ Chromium 自身将 Set-Cookie 写入受管 profile 的 Cookies 库（本引擎零解密参与）
→ 登录成功后引擎检测到 cookie 落盘 → 面板弹出「保留登录态？」开关
→ 用户选择后，结果写入 profile_meta.json（§7.1）
```

关键点：登录动作完全发生在受管实例内部，cookie 由 Chromium 自行加密落盘（OS 级加密，加密密钥存于该受管 profile 的 `Local State`），引擎与前端**不接触、不复制、不展示 cookie 明文**。此路径天然规避 App-Bound / DPAPI / 平台加密差异。

### 1.2 登录态落盘位置

- 目录（R-2 布局，与维度 10 §4.1 一致）：受管 profile 统一根 `<data_root>/conex/browser/managed/<profile_name>/`（Windows：`%LOCALAPPDATA%\conex\browser\managed`；macOS：`~/Library/Application Support/conex/browser/managed`；Linux：`$XDG_DATA_HOME/conex/browser/managed`，缺省 `~/.local/share`）；临时 profile 位于 `<data_root>/conex/browser/sessions/<session-uuid>/`（引导登录默认，见 §7.4）；
- cookie 库：`<profile_name>/Default/Cookies`（新版 Chrome/Edge v132+ 迁移到 `<profile_name>/Default/Network/Cookies`，启动器按存在性处理，见 §3.3）；
- 加密密钥：`<profile_name>/Local State` 的 `os_crypt.encrypted_key`（由 Chromium 首次启动自动生成）。

### 1.3 持久化开关 UI 与存储

- **UI**：登录成功（cookie 非空）后，浏览器面板底部弹出非阻塞提示条：「已登录 xx —— 保留登录态，下次启动继续使用？[保留] [仅本次]」。仅"保留"需用户显式点击；不点击默认不保留。
- **存储**：引擎侧 `profile_meta.json` 的 `persist` 字段（布尔，见 §7.1）——**唯一权威，撤销 panel-state.json 双源（R-2）**。前端 UI 不单独持久化开关状态；面板 UI 状态（标签/URL 序）另存 `panel-state.json`（纯 UI，不承载持久化开关）；会话索引（`session_meta`）仅记录 profile 关联关系。
- **保留动作**（R-2）：`persist=true` → profile 成为**受管 profile**，落于 `managed/<profile_name>/` 并写入 `profile_meta.json`（含 persist 与来源信息）；若引导登录发生在临时 profile（`sessions/<uuid>/`），保留动作将该 profile 目录整体迁入受管分层（写入 profile_meta.json 后，随会话结束的临时直删不再适用于它）；引擎维护"最近使用的持久 profile"引用，供重启后恢复。
- **降级动作**：`persist=false`（仅本次）→ 临时 profile 随会话结束**直接删除**（非用户资产，不走 trash，对齐维度 10 §4.4）；受管 profile 的用户主动删除（"忘记此登录"）走 **conex-fs trash**（用户资产，§7.3）。

### 1.4 重启保留验证流程

```
应用重启
→ persist.rs 读取 profile_meta.json，取出 persist=true 的 profile
→ 以该 profile 目录启动受管浏览器（--user-data-dir=<managed/profile_name>，见维度 10）
→ CDP 连接后导航到该 profile 上次最后访问站点（session_meta 记录）或用户常用站点
→ Storage.getCookies 校验：返回非空 且 存在匹配当前站点域的持久 cookie（expires > 0）
   - 通过 → 正常恢复，面板显示已登录
   - 失败 → 引导重新登录（§1.1），并提示「上次保留的登录态已失效」
```

校验失败分支同时记录审计事件（`browser.auth_restore_failed`），不静默。

## 2. 来源发现（discovery.rs）

### 2.1 三平台用户数据目录探测表

`discover_user_data_dirs()` 按平台枚举以下路径，返回存在的 `BrowserSource { family, browser_name, user_data_dir }`：

| 平台 | 浏览器 | 用户数据目录（Windows：`%LOCALAPPDATA%` 展开） |
|---|---|---|
| Windows | Chrome | `%LOCALAPPDATA%\Google\Chrome\User Data` |
| Windows | Chrome Canary | `%LOCALAPPDATA%\Google\Chrome SxS\User Data` |
| Windows | Edge | `%LOCALAPPDATA%\Microsoft\Edge\User Data` |
| Windows | Edge Beta/Dev/Canary | `%LOCALAPPDATA%\Microsoft\Edge Beta\User Data` 等（Beta/Dev/Canary 变体） |
| Windows | Chromium | `%LOCALAPPDATA%\Chromium\User Data`（存在则列出） |
| macOS | Chrome | `~/Library/Application Support/Google/Chrome` |
| macOS | Chrome Canary | `~/Library/Application Support/Google/Chrome Canary` |
| macOS | Edge | `~/Library/Application Support/Microsoft Edge` |
| macOS | Chromium | `~/Library/Application Support/Chromium` |
| Linux | Chrome | `~/.config/google-chrome` |
| Linux | Chromium | `~/.config/chromium` |
| Linux | Edge | `~/.config/microsoft-edge` |

实现要点：

- 路径来自 `reference/browser-use/browser_use/browser/chrome.py:10-35`（Chrome 系）并补充 Edge 家族；`family` 字段（`Chrome` / `Edge` / `Chromium`）是回读校验"同家族"分支的关键输入（§4.3）；
- 探测用 `std::path::Path::exists()` + 确认存在 `Local State` 或任意 profile 子目录（防误报空目录）；
- 全部探测只读，不创建目录。

### 2.2 profile 列表读取（Local State info_cache）

`list_profiles(user_data_dir) -> Vec<ChromeProfile>`：

- 读取 `<user_data_dir>/Local State`（JSON）→ `profile.info_cache`（dict：profile 目录名 → 信息对象）；
- 输出字段（对照 `chrome.py:95-126`）：

| 字段 | 来源 | 说明 |
|---|---|---|
| `directory` | info_cache 键 | `Default` / `Profile 1` / `Profile 2` … |
| `display_name` | `name` → 回退 `user_name` → 回退 `directory` | 列表展示名 |
| `is_using_default_name` | info_cache 值 | 用于 UI 标注「未重命名」 |
| `family` / `user_data_dir` | 探测结果携带 | 供复制与回读校验 |

- 解析容错：`info_cache` 缺失/非 dict/JSON 解析失败 → 返回空列表（不报错），UI 提示「未发现可用的浏览器 profile」并提供自定义目录入口（§2.3）；
- 仅列出**存在对应 profile 目录**的项（`<user_data_dir>/<directory>` 存在且含 `Cookies` 或 `Bookmarks` 任一文件），避免列出已删除的残留项。

### 2.3 自定义目录选择

- UI 提供「选择浏览器数据目录…」按钮（Tauri 原生目录选择器）；
- 校验：目录含 `Local State` 或含 profile 子目录（`Default/` 等），否则拒绝并提示；
- 选中后走与系统探测相同的 `list_profiles` / 复制 / 回读校验链路（family 未知时标记 `FamilyUnknown`，回读校验按"先试 CfT，失败再试同目录来源推断"处理）。

## 3. 最小文件集复制（copy.rs，迁移路径）

### 3.1 文件清单（含/排除表）

以 `<user_data_dir>/<profile_dir>`（如 `Default`）为源，白名单复制；白名单之外一律不复制：

| 类别 | 文件/目录 | 决策 | 理由 |
|---|---|---|---|
| 必须 | `Local State`（用户数据目录根） | **复制** | 含 `os_crypt.encrypted_key` 与 profile 索引；cookie 解密与 profile 列表依赖（参照 `profile.py:882-886` 的 Local State 复制） |
| 必须 | `Cookies`（profile 内） | **复制** | 登录态核心（SQLite） |
| 必须 | `Network/Cookies`（profile 内） | **存在则复制** | Chrome/Edge v132+ 将 cookie 库迁移至此；两个路径按存在性各复制一份，不合并 |
| 建议 | `Bookmarks`（profile 内） | **复制** | 书签 JSON；独立导入入口亦可用（§6.1），复制使迁移一次性完成 |
| 可选 | `Preferences`（profile 内） | 复制 | 站点偏好/语言；不影响登录态；不复制也行（走默认值） |
| 排除 | `Login Data` / `Login Data For Account` | **显式排除** | 密码库（隐私铁律，敲定 D-7） |
| 排除 | `History` / `History-journal` | **显式排除** | 浏览历史隐私面大；历史走独立入口（§6.2） |
| 排除 | `Web Data` | **显式排除** | 表单自动填充（Autofill）等敏感数据 |
| 排除 | `Visited Links`、`Sync Data`、`Extension State`、`Extensions`、`Local Extension Settings`、`Extension Cookies` | 排除 | 同步/扩展面非登录态必需，体积大且隐私面广 |
| 排除 | `Cache`、`Code Cache`、`GPUCache`、`DawnCache`、`ShaderCache`、`GrShaderCache`、`Service Worker/CacheStorage`、`IndexedDB`、`File System`、`blob_storage` | 排除 | 缓存/离线存储，非登录态必需；IndexedDB 属 storage_state 覆盖盲区但涉及站点离线数据，明确不迁移（隐私最小化） |
| 排除 | 会话面：`Session Storage`（可选排除） | 排除 | 会话存储不过期/不稳定，导入易产生异常状态 |
| 跳过 | 瞬态锁文件：`Singleton*`、`*.lock`、`LOCK`、`LOCKFILE`、`*-journal`、`*-wal`、`*-shm` | 复制时跳过 | 运行时文件/未清理日志（模式集对照 `profile.py:30-36,89-91`）；`*-wal/*-shm` 跳过意味着**源库必须干净退出**，见 §3.2 |

复制策略为**白名单**（只复制上表"必须/建议/可选"项），而非"复制全部再排除"——即使未来来源新增未知敏感文件也不会被带入，隐私面最小。

### 3.2 锁检测（来源浏览器运行中判定）

复制**前**执行 `detect_running(user_data_dir) -> RunningStatus`：

- 主判据（锁文件）：`<user_data_dir>` 下存在 `SingletonLock` / `SingletonCookie` / `SingletonSocket`（Chromium 系任一平台都会创建，Windows/macOS/Linux 通用）→ `Running`；
- 辅助判据（Windows 兜底）：源目录出现 `*-wal` 且 `*-shm` 伴生（未干净退出的 SQLite 残留）→ 提示「浏览器可能未完全退出」；
- 辅助判据（进程探测兜底，仅提示不阻断）：`chrome.exe`/`msedge.exe` 进程存在但锁文件缺失（僵尸锁场景）→ UI 询问「检测到浏览器进程，是否确认已关闭？」；
- 结果：

| 状态 | 处理 |
|---|---|
| `Running`（锁文件存在） | **阻断复制**，UI 提示「请先完全关闭 Chrome/Edge（包括后台进程与托盘）」，不进入复制（对应 `profile.py:874-881` 的锁冲突语义——参考实现是复制中报错，我们前置到复制前，体验更可控） |
| `NotRunning` | 继续复制 |
| `Uncertain`（仅进程探测命中） | 用户确认后继续 |

补充规则：复制过程中若仍出现 `WinError 32`（文件被占用，Windows 共享冲突）等 `PermissionError`，中止复制、trash 目标目录、回到 `Running` 分支提示（对照 `profile.py:94-113` 的锁错误识别）。

### 3.3 复制流程

**复制前确认对话框（合规 C1/C2，21 评审 M10）**：进入复制前必须展示——① **cookie 域清单预览**（来源库只读统计 Top N 域名 + 总数，仅列域名不含值）；② **显式告知「密码与历史不会迁移」**（Login Data/History 显式排除，迁移后目标站点不会自动填充密码）；③ 文件清单（§3.1 白名单项）。用户确认后才开始复制。

```
1. 目标目录构建：managed/<profile_name>/            # R-2 布局；profile_name 默认取源 profile 名，可用户命名
2. 锁检测（§3.2）通过；复制前确认对话框（上文）通过
3. 原子化复制（M-10）：先复制到 managed/.staging/<tmp>/（同文件系统内）
   a. 复制 <user_data_dir>/Local State → staging/Local State
   b. 复制 <user_data_dir>/<profile_dir>/Cookies → staging/<profile_dir>/Cookies
      （同法处理 Network/Cookies、Bookmarks、Preferences，存在才复制；跳过瞬态模式）
4. 结构校验（staging 内）：Local State 存在 且 至少一个 cookie 库存在
   - 通过 → rename 到 managed/<profile_name>/（同目录 rename 原子性，不产生部分可见目标）
   - 不通过 → 清理 staging（直删，非用户资产）并标记 Failed
5. 记录 profile_meta.json：source（family/browser_name/user_data_dir/profile_dir/display_name）、
    复制文件清单、时间戳、状态 = Copied
6. 进入回读校验（§4）
```

> 原子化说明（M-10）：复制过程对目标 `managed/<profile_name>/` 不可见（仅 staging 内可见），rename 是同一文件系统内的原子改名——中断（进程被杀/锁冲突）时目标目录不会出现半成品；残留 staging 由下次启动的清理扫描兜底（§3.4）。

目标目录结构：

```
managed/<profile_name>/
  profile_meta.json          # 引擎侧元数据（§7.1）
  Local State
  Default/                   # 或原 profile_dir 名（保留原名，Preferences 中引用一致）
    Cookies
    Bookmarks
    Preferences
```

要点：

- 复制仅对源**只读**：不修改、不删除来源任何文件（源 mtime 不变）；
- profile 目录名**保留原名**（`Default`/`Profile 1`），避免 `Preferences` 内部路径引用错位；
- 目标目录创建于受管独立目录（`<data_root>/conex/browser/managed/`），与来源完全隔离；
- `managed/.staging/` 为瞬态目录：不在 profile 列表、不参与生命周期恢复，仅复制中间态用。

### 3.4 复制后清理

- **staging 清理（M-10）**：复制中断（进程被杀/锁冲突/校验不通过）→ 清理 `managed/.staging/` 残留（**直删**——staging 是瞬态中间态，非用户资产）；下次启动时 persist.rs 扫描 `.staging/` 下残留目录兜底清理；
- 复制阶段失败（staging 结构校验不通过/锁冲突）→ 目标 `managed/<profile_name>/` **未产生**（原子化保证），仅清 staging，无需 trash；
- 回读校验进入"不可读"分支（§4.4）→ 该目录已在 `managed/` 下（用户资产语义）→ 保留目录但标记 `Disabled`（供用户改选同家族二进制重试），用户确认放弃后走 `conex-fs` trash（`trash.rs` 铁律，不直接 `remove_dir_all`）并通知用户回收站位置；
- 复制成功的目录不做额外清理（`Singleton*`/`*-wal` 等瞬态文件本就不被复制）。

## 4. 回读校验（verify.rs）

### 4.1 校验方法

> **S0 实证修订（2026-08-09，S0-02 报告）**：本机 Chrome 151（≥127）实测——cookie 值仅按 Windows 用户级加密（DPAPI），**未发现 app_bound_encrypted_key**；跨家族复制（Chrome→Edge 147）后 CDP 回读同样成功（3/3）。即：**"回读失败 ⇒ App-Bound"的判据在本机不成立**，原 §4.3 的 `FamilyMismatch` 判定条件不可依赖。修订如下：
>
> 1. **前置检测替代后置回读**：复制/启动前检查来源 `Local State` 是否存在 `app_bound_encrypted_key` 字段——存在 ⇒ App-Bound 加密启用（cookie 绑定来源 exe 家族）⇒ 提示"同家族可迁移、跨家族不可行"，并据此决定是否执行复制（用户确认）。
> 2. 回读校验保留为**数据完整性兜底**（检测复制损坏/权限问题），不再作为家族判据：`N_db > 0` 且 `N_cdp = 0` 时归类 `Unreadable`（数据不可用），引导面板内登录，不提示"需同家族"。
> 3. 跨机器/凭据失效场景（不同 Windows 用户复制）仍会导致解密失败——保留 `Unreadable` 分支兜底。
> 4. P0-4 结论更新：App-Bound 启用与否以 `app_bound_encrypted_key` 存在性为准（S0 实证），实现层增加该字段检测（verify.rs）。

**判据核心：DB 行数对比 + CDP 实读**（数据完整性兜底，家族判定前置化）：

```
0. 前置检测：来源 Local State 含 app_bound_encrypted_key ⇒ App-Bound 启用（家族约束提示，用户确认后继续）
1. 复制完成 → 以只读方式（conex-db open_readonly，SQLITE_OPEN_READ_ONLY）打开目标 Cookies 库
   → 统计持久 cookie 行数 N_db（expires_utc > 0）
2. 以复制出的 profile 启动受管浏览器（--user-data-dir=<managed/profile_name>，见维度 10）
   → CDP Storage.getCookies（或 Network.getAllCookies）→ 统计返回的持久 cookie 数 N_cdp
3. 实读抽样：对校验站点（§4.2）发起请求（CDP Network 域记录请求头），
   确认 Cookie 头携带该校验 cookie（若站点可达）
```

> 说明：受管实例自身负责解密（用目标 `Local State` 的密钥）。复制损坏/权限问题/跨机器凭据失效时浏览器静默丢 cookie → `N_cdp ≈ 0` 而 `N_db > 0`，此即"数据不可用"的精确信号。

### 4.2 校验站点选择

- 优先级：用户上次在该来源登录的站点（若有记录）→ 用户从候选清单选择（常用站点如 github.com 等）→ 默认取 cookie 库中 `host_key` 非本机的、行数最多的域作为抽样域（仅用于请求头验证，不导航）；
- 校验站点仅用于判定，不注入脚本、不触碰页面内容。

### 4.3 结论分类（`VerifyResult`）

| 结论 | 判定条件 | 含义 |
|---|---|---|
| `Readable` 可读 | `N_cdp > 0` 且（抽样成功或请求头携带目标 cookie） | 解密成功，登录态可用 |
| `Unreadable` 数据不可用 | `N_db = 0`（无持久 cookie），或 `N_db > 0` 且 `N_cdp ≈ 0`（复制损坏/权限/跨机器凭据失效），或目标启动失败 | 无登录态可迁移或数据不可用 → 引导面板内登录 |

> 修订说明：原 `FamilyMismatch`（需同家族）分类撤销——S0 实证本机 App-Bound 未启用且跨家族回读成功，"家族"判定移至 §4.1 前置检测（`app_bound_encrypted_key` 存在性），回读不再承担家族判据。App-Bound 启用时的跨家族迁移由前置检测在复制前拦截。

结论与中间数据（`N_db`、`N_cdp`、校验站点、采样行数）写入 `profile_meta.json.verify_result`（验收 S3 要求"回读校验结论落盘"）。

### 4.4 三类结论的引导分支

```
Readable
  → 提示「登录态迁移成功」，进入 §7.1 持久化开关流程（保留/仅本次）
  → 用户确认后立即以该 profile 恢复会话

FamilyMismatch（需同家族）
  → UI 提示：「该浏览器的登录态加密绑定 Chrome/Edge 家族，当前运行的浏览器无法解密。
      请使用与来源同家族的浏览器重试。」
  → 提供按钮「用同家族浏览器重试」（来源 family=Chrome → 改用系统 Chrome 二进制启动；
     来源 family=Edge → 改用系统 Edge；CfT 仅用于首次尝试或来源为 CfT 家族）
  → 重试仍 FamilyMismatch → 降级为 Unreadable 分支
  → 用户也可直接选择「改用面板内登录」（跳 §1.1）

Unreadable
  → 提示「无法迁移该浏览器的登录态」，引导进入面板内登录（§1.1）
  → 复制 profile 标记 Disabled，用户确认后 trash 删除
```

同家族约束矩阵（写入导入向导文案）：

| 来源 | 可成功迁移的运行实例 |
|---|---|
| Chrome / Chrome Canary | 系统 Chrome（同家族）；CfT 视实测（S0 P0-4 结论而定） |
| Edge 及变体 | 系统 Edge（同家族） |
| Chromium（开源） | 一般无 App-Bound 绑定，CfT / 系统 Chrome 均可尝试 |
| 自定义目录 | 先 CfT 尝试，失败按目录内 `Local State` 特征推断家族再重试 |

## 5. storage_state 辅助通道（storage_state.rs）

### 5.1 格式说明（标准 JSON，Playwright 兼容）

```json
{
  "cookies": [
    {
      "name": "sessionid",
      "value": "abc123",
      "domain": ".example.com",
      "path": "/",
      "expires": 1750000000,
      "httpOnly": true,
      "secure": true,
      "sameSite": "Lax"
    }
  ],
  "origins": [
    {
      "origin": "https://example.com",
      "localStorage": [ { "name": "theme", "value": "dark" } ]
    }
  ]
}
```

- `expires`：-1 表示会话 cookie（导入时移除该字段，对照 `storage_state_watchdog.py:252-264` 的归一化处理）；`sameSite` 取值 `Strict`/`Lax`/`None`；
- `origins` 为可选；`sessionStorage` 与 IndexedDB **不在**本格式面内（辅助通道定位，覆盖盲区已知）。

### 5.2 导出接口（需显式授权）

- 引擎侧 `export_storage_state(session) -> StorageState`：CDP `Storage.getCookies`（取全量 cookie，对照 `session.py:1427-1470` 的字段归一化）→ 可选 `DOMStorage` 域按 origin 聚合 localStorage；
- **授权**：导出属于敏感动作，走既有审批面（`dangerous=true`）：面板内"导出登录态"按钮 → 授权对话框（说明将导出 N 个 cookie，含域名列表）→ 确认后才执行；
- **默认不落盘**：导出结果以内存 JSON 返回前端（用户可粘贴保存）；**仅当用户显式选择"另存为"**（授权对话框内的二级确认）才写盘；引擎不创建任何 storage_state 缓存文件；
- 会话内重导出次数、导出 cookie 数量计入审计（脱敏，不含 value）。

### 5.3 导入接口

- 入口：导入向导的「从 storage_state 导入」步骤，用户粘贴 JSON 或选择文件（选择文件同样需显式确认）；
- 解析校验：JSON 合法、大小上限 10MB、字段白名单（未知字段丢弃）、cookie 数量上限 5000（超限提示分批）；
- 注入：cookie 走 CDP `Network.setCookies` 批量注入；localStorage 走 `Page.addScriptToEvaluateOnNewDocument` 注入恢复脚本，**按 origin 作用域守卫**（脚本内先校验 `window.location.origin` 再 `setItem`，对照 `storage_state_watchdog.py:270-308`），防跨站污染；
- 注入完成后读取回验（getCookies 对比注入数），失败回滚并提示。

### 5.4 不落盘保证（强制面）

- `StorageState` 仅在引擎内存与 Tauri command 参数间传递；
- 日志/审计/事件负载一律不输出 cookie `value`（脱敏为长度 + 域）；
- 写盘仅存在 §5.2 显式"另存为"路径；会话删除时若存在用户保存文件（用户自行选择路径，非引擎托管）不负责删除，但引擎侧不保留任何副本。

## 6. 书签/历史导入（bookmarks.rs / history.rs，独立入口）

### 6.1 书签导入（JSON 解析）

- 来源：`<profile>/Bookmarks`（JSON，Chrome/Edge 原生格式）或导入向导中用户指定文件；
- 结构：`{"roots": {"bookmark_bar": {...}, "other": {...}, "synced": {...}}}`；节点 `{"type": "folder" | "url", "name", "url", "children": [...]}`，folder 递归；
- 解析实现：`bookmarks.rs` 递归遍历 → 扁平化条目 `BookmarkItem { folder_path: Vec<String>, name, url }`；跳过无效节点（缺 name/url）、`type` 异常容错；
- **导入目标**：面板书签侧栏库（本地 SQLite 新表 `imported_bookmarks`，归 conex-db 管理，与浏览器数据解耦）；
- **冲突合并策略**：按 `(folder_path, name, url)` 唯一键去重——已存在跳过（幂等）；同名不同 URL 保留两条；根目录映射为"导入书签"顶层文件夹（`bookmark_bar`→「书签栏」、`other`→「其他书签」、`synced`→「同步书签」）；
- 数量上限：默认 10000 条，超限 UI 明示并分批导入（每批 1000 事务内提交）；
- 导入全程无网络请求（书签为纯数据），审计记录条数与顶层目录名。

### 6.2 历史导入（SQLite 只读读取，conex-db 复用）

- 来源：`<profile>/History`（SQLite，浏览器私有库）；**conex-db 新增只读辅助** `open_readonly(path)`（`SQLITE_OPEN_READ_ONLY | SQLITE_OPEN_URI`），打开后仅 SELECT，绝不写来源库；
- 读取 SQL：

```sql
SELECT u.url, u.title, v.visit_time
FROM visits v JOIN urls u ON u.id = v.url
WHERE v.visit_time > ?                -- WebKit 微秒时间戳（1601-01-01 UTC 起）
ORDER BY v.visit_time DESC
LIMIT ?;
```

- 时间戳换算：`unix_secs = webkit_us / 1_000_000 - 11_644_473_600`（1601→1970 偏移，对照 WebKit epoch 语义）；无效 URL 行丢弃；
- **读取前置条件**：来源浏览器需已关闭（§3.2 锁检测复用）；运行中读取会命中 WAL/锁 → 提示先关闭（读取前检查 `*-wal` 存在性，提示数据可能不完整）；
- 默认导入范围：最近 90 天、最多 10000 条（UI 明示实际数量后可调）；
- **冲突合并策略**：目标表 `imported_history` 按 `(url, visit_time)` 唯一键去重（幂等重导）；同 URL 多次访问保留多条（历史语义）；
- 隐私提示：导入前确认对话框「将导入最近 N 条浏览历史（域名列表预览）」；确认后导入，审计记录数量。

### 6.3 独立入口与向导编排

- 导入向导分三步：**① 登录态**（引导登录 / profile 复制 / storage_state 三选一）→ **② 书签**（可跳过）→ **③ 历史**（可跳过）；②③ 可单独触发（面板设置区常驻入口），不与登录态绑定；
- ②③ 与 ① 互不阻塞：书签/历史导入失败不影响登录态结果，反之亦然。

## 7. 持久化与清理（persist.rs）

### 7.1 profile_meta.json（受管 profile 元数据）

```
managed/<profile_name>/profile_meta.json
{
  "profile_id": "uuid7",               // 内部唯一标识（目录名 = profile_name，用户可命名）
  "origin": "guided_login" | "copied" | "storage_state",
  "source": {                          // origin=copied 时记录
    "family": "Chrome" | "Edge" | "Chromium" | "unknown",
    "browser_name": "Google Chrome",
    "user_data_dir": "…",              // 仅存路径，不存内容
    "profile_dir": "Default",
    "display_name": "个人"
  },
  "persist": false,                    // 持久化开关，唯一存于此（R-2，撤销 panel-state.json 双源）
  "verify_result": { "conclusion": "readable", "n_db": 128, "n_cdp": 128, "checked_at": "…" },
  "created_at": "…",
  "last_used_at": "…",
  "state": "active" | "disabled" | "trashed"
}
```

- 写入时机：创建（复制/首次引导登录保留）、校验结论落盘（§4.3）、持久化开关变更、删除；
- meta 不含任何 cookie/密码内容（路径与判定数字），隐私最小化；
- 目录布局（R-2，与维度 10 §4.1 一致）：受管 profile 唯一根 `managed/<profile_name>/`；临时 profile（`sessions/<uuid>/`）无 meta，不适用本节。

### 7.2 受管 profile 持久化开关

| 开关 | 行为 |
|---|---|
| `persist=false`（默认） | 不保留登录态：临时 profile（`sessions/`）随会话结束**直接删除**（R-2，非用户资产）；受管 profile（`managed/`）仅被动等待用户决定，用户主动删除才触发清理（§7.3） |
| `persist=true` | 重启保留：启动时按 §1.4 恢复；生命周期跟随"忘记此登录"（用户主动删除 → **conex-fs trash**，用户资产） |
| 切换时机 | §1.3 登录后提示条；设置区「浏览器登录态」管理列表（列出各持久 profile 与来源，可逐项"忘记"） |

### 7.3 临时 profile 用完即删

- 触发：面板关闭、会话超时（默认 30 分钟无活动，可配）、应用退出；
- 删除方式（R-2）：临时 profile（`sessions/<uuid>/`）**直接删除**（`remove_dir_all`），**不走 conex-fs trash**——这是运行期受管目录而非用户资产，与 AGENTS.md 会话产出目录清理语义不同，需在代码注释与评审中显式区分（对齐维度 10 §4.4）；受管 profile（`managed/`）的删除（"忘记此登录"/用户确认放弃）才走 **conex-fs trash**（`trash.rs:26-29` 铁律，回收站可还原并通知用户清理结果与位置）；
- 崩溃兜底：进程被杀导致的残留临时目录，下次启动时由 persist.rs 扫描 `sessions/` 下无锁文件且目录 mtime 超 24h 的孤儿目录并直删（对齐维度 10 §4.4 孤儿清扫与仓库会话孤儿清理模式）；`managed/.staging/` 残留扫描一并处理（§3.4）。

### 7.4 导入 profile 与会话 profile 的关系

| 类型 | 目录（R-2） | 来源 | 生命周期 | 用途 |
|---|---|---|---|---|
| 会话 profile（临时） | `sessions/<session-uuid>/` | 引擎创建（uuid） | 无 meta，会话结束**直接删除**（不走 trash） | 引导登录默认、普通浏览会话 |
| 受管 profile（持久） | `managed/<profile_name>/` | profile 复制 / 用户选择保留的登录 | `persist` 存 profile_meta.json；用户主动删除走 trash | 迁移登录态、长期登录 |
| 同会话互斥 | — | 一个浏览器实例同一时刻绑定一个 profile 目录 | 禁止多实例共享同一 profile（锁冲突） |

- 复制 profile 直接落 `managed/`（用户资产语义），默认 `persist=false` 挂起，回读 `Readable` + 用户确认后转 `persist=true`（§4.4）；
- 引导登录默认在临时 profile（`sessions/`）进行；用户选「保留」→ 转为受管 profile（§1.3 保留动作）；
- 面板状态（标签/URL）随会话恢复：受管 profile 的 `session_meta` 记录最后站点，供 §1.4 恢复；`panel-state.json`（纯 UI）不承载持久化开关（R-2）。

| E-5 | 锁冲突提示 | 来源浏览器运行中触发复制 | 复制被阻断，UI 提示关闭浏览器；不产生目标目录残留 |
| E-6 | 回读三分支 | 构造 可读 / 需同家族 / 不可读 三类来源（App-Bound 实证见 S0 P0-4） | 结论分别落盘（profile_meta.verify_result）；需同家族 → 提示 + 同家族二进制重试；不可读 → 引导面板内登录 |
| E-7 | storage_state 往返 | 导出（授权）→ 新会话导入 | cookie/localStorage 生效；默认路径无任何落盘文件；日志无 cookie value |
| E-8 | 书签导入 | 导入 Bookmarks JSON → 重复导入 | 目录树正确（书签栏/其他书签/同步书签）；重复导入幂等 |
| E-9 | 历史导入 | 只读打开 History → 导入 → 再次读取来源库 | 时间倒序、数量正确；来源库字节级未变（hash 对比）；运行中来源提示关闭 |
| E-10 | 持久化清理 | ① 临时 profile 会话结束（仅本次）；② 受管 profile "忘记此登录"；③ 复制中断（kill 进程注入） | ① `sessions/` 目录直删（非 trash）；② `managed/` 目录走 trash（回收站可还原）+ 通知用户清理结果与回收站位置；③ `managed/.staging/` 残留被清理、目标 `managed/<name>/` 无半成品（M-10） |

S0 前置验证（本维度相关）：P0-4（profile 最小文件集复制 + 回读校验，含高版本 App-Bound 实证）必须在 S3 实施前完成，回读判定阈值（`N_db`/`N_cdp` 对比）依据实证校准。

## 9. 风险与预案

| 风险 | 等级 | 影响面 | 预案 |
|---|---|---|---|
| 高版本浏览器 App-Bound 加密导致复制后 cookie 不可读 | 高 | 迁移路径主风险 | 回读校验三分支（§4.3）+ 同家族二进制重试 + 面板内登录兜底；同家族约束写入向导文案 |
| Chrome/Edge 版本迁移 cookie 库路径（v132+ `Network/Cookies`） | 中 | 复制与读取 | 按存在性双路径复制；启动器与回读校验均按存在性探测 |
| 来源库 WAL 残留（未干净退出）导致复制出残缺库 | 中 | 复制结果 | 锁检测含 `*-wal/*-shm` 判据；校验前只读统计行数与预期一致性 |
| 锁文件误判（僵尸锁/后台进程） | 低 | 复制可用性 | 进程探测兜底 + 用户确认；复制中 WinError 32 中止并回引导 |
| 大书签/大历史导入超限 | 低 | 导入体验 | 数量上限 + 分批事务 + UI 明示 |
| storage_state 明文落盘泄漏（误操作） | 中 | 隐私 | 默认不落盘（强制面）；导出双确认授权；日志脱敏 |
| 跨平台差异（Windows 文件锁语义、macOS 锁文件缺失） | 中 | 锁检测 | 主判据（Singleton*）+ 平台兜底（进程探测/DB 残留），结论归类为 Uncertain 交由用户确认 |
| 引导登录被站点风控拦截 | 中 | 主路径可用性 | 面板转发 = 真实输入（isTrusted=true，维度 12）；域名门禁不干预登录页面；风控场景提示用户手动操作 |
| 持久 profile 泄漏（用户共用机器） | 低 | 隐私 | 持久化默认关闭、仅显式开启；"忘记此登录"一键 trash |
