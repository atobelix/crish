**(b) 新工具 `computer_verify_state`（感知类，dangerous=true，默认审批可配免审，对齐 06 §2.2 感知 4 类）**

注册面：`conex-computer-tools` 工具清单 13 → 14（`ALL_TOOL_NAMES` 常量与注册数断言同步更新，tools.rs:992-1204 + lib.rs）。输入 schema：

```json
{
  "type": "object",
  "properties": {
    "predicates": {
      "type": "array",
      "minItems": 1,
      "maxItems": 8,
      "description": "AND 组合谓词（1-8 个）"
    },
    "repeat_until_stable": {
      "type": "object",
      "properties": {
        "max_polls": { "type": "integer", "minimum": 1, "default": 3 },
        "interval_ms": {
          "type": "integer",
          "minimum": 100,
          "maximum": 5000,
          "default": 500
        },
        "stable_samples": { "type": "integer", "minimum": 1, "default": 1 }
      }
    },
    "include_screenshot": { "type": "boolean", "default": false }
  },
  "required": ["predicates"],
  "additionalProperties": false
}
```

谓词设计（对齐 cua-driver contract/README.md:57-67「1-8 个 ANDed 谓词，绑定窗口；satisfied 是唯一成功终态，unknown 永不提升」+ 我们 UIA 数据面）：

| 谓词                                   | 字段                                                      | 语义                                                                                                     | unknown 触发                    |
| -------------------------------------- | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------- |
| `window_exists`                        | `title_contains: string`                                  | 活动窗口标题包含子串                                                                                     | 感知失败（无活动窗口/UIA 故障） |
| `element_exists`                       | `role?`, `name_contains?`                                 | 窗口级 UIA 树内存在匹配元素                                                                              | 感知失败；树截断致搜索不完整    |
| `element_value`                        | `role?`, `name_contains?`, `value_eq?`, `value_contains?` | 元素值匹配（value 为 UIA ValuePattern 读回，密码框已被数据面抑制为 `<password>`，perception.rs:393-408） | 元素不在树；值不可读            |
| `element_enabled` / `element_selected` | `role?`, `name_contains?`, `expect: bool`                 | 启用/选中态匹配                                                                                          | 元素不在树；模式不可用          |

三态合成（纯函数，可单测）：

- 任一谓词评估失败（无法判定）→ 该项 `unknown`；
- 全部可判定且全满足 → `satisfied`；
- 任一可判定且不满足 → `unsatisfied`（**不因其它项 unknown 而升级**）；
- 有界轮询：重复采样 `stable_samples` 次连续 `satisfied` 才算成功终态；超时或轮询耗尽 → 最后一次合成态（unknown 保持 unknown）。

返回形状：

```json
{
  "ok": true,
  "state": "satisfied" | "unsatisfied" | "unknown",
  "results": [ { "predicate": "element_value", "verdict": "satisfied|unsatisfied|unknown", "detail": "..." } ],
  "samples": 2,
  "stable": true,
  "perceptionVersion": N,
  "screenshot": { ... } | null
}
```

**(c) 三态消费点（循环侧，不建引擎规划器）**

- **模型侧（主消费）**：verify_state 作为工具进模型 schema；模型在「动作后」调用验证后置条件——`satisfied` → 前进；`unsatisfied` → 重试/换路；`unknown` → 不当作成功（cua-driver「treat unverifiable as unknown, not failure and not success」）。这是 54 §2.1 契约语义的消费面。
- **bench 侧（复用）**：R9d 的 evaluate 函数可直接复用同一谓词合成逻辑（同一纯函数，bench 不重复实现）。
- **引擎侧**：不自动调 verify（54 §5.2 裁决：不建引擎规划器；效果锁是「给模型结构化事实」，不是引擎代模型验证）。

#### 1.2.2 改造方案

**(a) 会话内分块循环加 stop 自查（桌面线，对齐浏览器线 keyboard.rs:366-373）**

`conex-computer` 注入后端 `type_text_inner`（action.rs:722-731）块间检查 `EmergencyStop` 旗：

```rust
fn type_text_inner(&self, text: &str) -> Result<(), InjectError> {
    let mut enigo = self.enigo.lock().expect("注入后端锁损坏");
    let chunks = chunk_text(text, TYPING_GROUP_SIZE);
    let mut delivered = 0usize;
    for chunk in &chunks {
        if self.stop.as_ref().is_some_and(|s| s.stopped()) { break; }  // 块间自查
        enigo.text(chunk).map_err(...)?;
        delivered += chunk.chars().count();
        thread::sleep(Duration::from_millis(TYPING_DELAY_MS));
    }
    if delivered < text.chars().count() && self.stop...stopped() {
        return Err(InjectError::Interrupted { delivered, total });
    }
    Ok(())
}
```

- 注入后端（enigo 后端）构造时持有 `Arc<EmergencyStop>`（ComputerSession 装配面注入；`stop=None` 时跳过自查，语义不变——守卫链测试用 mock 装配不受影响）。
- 新增 `InjectError::Interrupted { delivered, total }` 变体（消息携带已送达计数）；`SessionError` 增加对应映射面（action.rs 错误域，error.rs:66-84 映射表扩展）。

**(b) 工具面 partial 形状（machine-readable）**

`computer_type` 执行路径（tools.rs:222-234）：

- 成功：不变（`{ok:true, typedChars, perceptionVersion}`）；
- 块间自查中断：返回**结构化错误载荷**——错误码保持 `tool.computer.cancelled`（语义：急停/取消，不计重试额度，error.rs:36-41），错误消息承载 `partial:{delivered}/{total}`，**并扩展 CrishError 载荷携带 `partial` 字段**（`{code, message, partial: {deliveredChars, totalChars}}`——crish-error 载荷扩展需 conex-types 出站形状加可选字段，向后兼容）。

> 为什么 Err 而非 Ok：cancelled 语义已被模型与守卫链消费（急停不计重试额度、拒绝型收口），改为 Ok 会破坏既有权重；在 Err 载荷上加 `partial` 字段保持「中断」语义不变、补「已送达事实」。拒绝型错误（approval.rejected 等）与 cancelled 均保持机器可读（R10 验收「拒绝型错误仍机器可读」同源）。

**与 effect 契约（R9e）的关系**：partial 是 effect 五态之一（`partial: {delivered_count}`，54 §2.1）；落地顺序上 partial 字段先于完整 effect 枚举（低侵入），effect 枚举随后覆盖。

### 1.5 R9e effect 分布作为动作级评估指标

- 现状：工具返回形状无 effect 字段（全部 `{ok:true, perceptionVersion:N}`，tools.rs:216-330）；「注入成功」与「动作生效」不可区分（54 §2.2 最大差距）。
- 改造：R9a/b 落地后，动作类工具返回形状扩展 `effect` 枚举 + `evidence` 列表（对齐 54 §2.1 五态）：
  - `confirmed`（有回读证据：光标回读一致 / UIA 值回读一致 / 版本推进——T4c/T5c 已验证回读路径，49 §2）；
  - `partial`（R9b 已送达计数）；
  - `unverifiable`（到达执行器但无可信回读——**当前 ok:true 的真相化替换**，`unknown` 语义，54 §2.1「not failure and not success」）；
  - `suspected_noop`（可选，有 UIA 前后对比无变化证据时）；
  - `refused`（映射现有拒绝型错误码：approval.rejected / not_enabled / elevated_window / exclusive——已有且机器可读）。
- 消费：bench report.rs 统计 `effect_distribution`（confirmed 率 / unverifiable 率 / partial 率 / refused 率），定位「循环在哪一步断」（感知没看见？动作没生效？计划错了）——cua-bench 结构上没有、我们实现 effect 后独有的诊断维度（54 §4.2 项 3）。

### 2.2 改造方案

#### 2.2.1 stdio server 进程形态：Tauri 壳内子命令（推荐）vs 独立二进制

| 维度     | 壳内子命令（推荐）                                                                                                                                                                                                             | 独立二进制（crates/conex-computer-mcp）                                      |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| 装配复用 | main() 最早分支 `std::env::args().get(1)=="computer-mcp"` → 走 stdio 主循环，**复用 engine_build 装配**（ToolRegistry + ComputerSlot + ApprovalGate + EmergencyStop 共享实例）                                                 | 需重新装配 ToolRegistry + ComputerSlot + RealComputerSession（引擎装配复制） |
| 安全面   | **共享进程级安全面**：同一开启态/互斥门/急停旗/审批门——外部客户端调用受同一套六道守卫约束（形态优势，55 §3.1）                                                                                                                 | 审批门不同实例，与主应用安全面割裂                                           |
| 分发     | 单二进制（随 Tauri 应用分发）                                                                                                                                                                                                  | 新增 workspace bin，需独立发布路径                                           |
| 风险     | `windows_subsystem = "windows"`（main.rs:1）下 stdio 需验证：GUI 子系统进程的**重定向** stdout 可写（子进程管道不受控制台影响），但需测试断言；release 构建同样可用（这是产品能力不是调试工具，与 dev_mcp 的 debug-only 区分） | 无此风险，但失去共享安全面                                                   |
| 结论     | **一期采用**。主循环不构建 tauri Builder/window，仅取进程级装配（引擎初始化顺序：telemetry → LocalDb → ComputerSlot → registry）；启动失败（如 DB 不可用）→ stderr 显式错误 + 退出码，不静默                                   | 登记为远期（「不启动主应用独立使用」场景），不做                             |

**装配面落点**：`apps/agent-workbench/src-tauri/src/` 新增 `computer_mcp.rs`（子命令主循环 + 装配），main() 入口分派；注册面（command_registry!）**不加命令**（stdio 不是 IPC 命令面，manifest 无需登记——与 dev_mcp 的命令查询面区分）。

#### 2.2.2 认证与开关（对齐 dev_mcp.rs 先例 + stdio 进程边界差异说明）

- **开关（强制）**：env `CRISH_COMPUTER_MCP=1`（精确匹配，复用 dev_mcp.rs:35-37 `env_flag` 模式）**或**命令行显式 `computer-mcp` 子命令（外部客户端 mcpServers 配置 `args: ["computer-mcp"]` 即隐式显式启动——**两者等价视为显式授权**；env 未设且未显式子命令 → 拒绝启动并 stderr 报错）。
  - 注意：`StdioServerParameters` 支持 env 字段（Codex/Cursor config 均可带 env），env 开关可被客户端配置传递。
- **token 认证**：stdio 无网络面——**进程边界即认证**（谁能拉起进程谁能调），与 dev_mcp 的 TCP socket token 面（dev_mcp.rs:57-71）性质不同，文档须诚实声明：stdio 认证 = 显式开关 + 进程边界；若未来需更强隔离（远程/共享场景），走 TCP + token（dev_mcp 先例）或 loopback-only 网络面，**一期不做**。
- **release 构建**：允许（产品能力），但默认关闭（env 门控）；与 dev_mcp 的 `#[cfg(debug_assertions)]` 隔离形成对照——stdio server 是产品面、dev_mcp socket 是调试面。
- **权限模式映射**（对齐 cua-driver 三档 + 我们 PermissionMode，permission.rs:19-27）：env `CRISH_COMPUTER_MCP_MODE`：`ask`（默认）/ `bounded` / `full-access`（需显式设置，对齐 permission.rs:29-43「未知值安全默认 ask，永不静默 full-access」）。

#### 2.2.3 审批桥接方案对比（外部客户端路径的 ctx.ask 缺口）

**背景**：工具守卫⑤ `approve()`（tools.rs:139-198）要求 ctx.ask 送用户；外部客户端调用无引擎 run 上下文，`ToolContext` 由 MCP server 层构造。两个候选：

| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A：挂起到宿主面板** | MCP server 持有 `ComputerSlot.approval()`（conex_computer::ApprovalGate 共享实例，computer/mod.rs:230）；ask 通道实现 = `gate.require_approval` → Pending → 发射审批请求事件（宿主 UI 弹窗）→ 用户裁决经**新增命令**（`computer_approve(id, allow)` / `computer_deny`）→ `gate.settle` → 通道收口 | 与主应用同一审批门（一次一票/急停联动/并发拒绝全部复用，security.rs:345-401）；用户可见完整载荷（type 明文等）                    | 依赖：① ComputerSlot 增裁决命令面（现只有 enable/disable/estop/status 4 命令，computer_commands.rs:1-19；`core_approve_tool` 是 run 键的 ApprovalGateImpl 门，**不是** computer 门——不能复用，需新增并登记 command_manifest）；② 宿主 UI 审批弹窗（复用 ComputerPanel 或通用审批面板）；③ 宿主不在线（外部客户端独立调用时）→ 审批悬挂 → 需超时语义（Pending 超时 → 拒绝收口，对齐 48 冒烟「急停后只接受拒绝」） |

#### 2.2.4 工具 schema 语义标注（readOnly/destructive/idempotent 三标注）

- **扩展点**：`ToolDefinition`（definition.rs:30-47）新增三布尔字段（serde default，**向后兼容**，既有构造点零改动）：

- **初始标注**（computer_* 13 工具）：注入 8 = destructive=true / idempotent=false（click/move 幂等性由会话+参数哈希键已有，06 §3.2——idempotent 标注按「重复执行物理副作用」判，注入类 false）；感知 4 + verify_state = read_only=true；estop = destructive=true（中止不可逆）。浏览器线/笔记工具由各自维度补标注（本维度只定义扩展点与 computer_* 初值）。

  - **不保护边界**：同用户任意代码（若模型/提示注入逃逸到任意代码执行，审批/急停/提权拒绝全部可被绕过——需 OS 级隔离，非本产品范围）；一句话声明「不承诺对抗同用户恶意进程」；
  - **fullaccess 模式边界**（R10 配套）：`CRISH_COMPUTER_MCP_MODE=full-access` 是「显式授权的免审批」——等价于用户亲手操作桌面；边界声明：该模式不豁免红线语义（permission.rs:9-12「红线先行，任何模式下 Deny」）与提权拒绝（守卫⑥不受审批影响，tools.rs:417-421 守卫③/④先于审批⑤）；
  - **截屏边界**：截屏仅回显/模型上下文，不落盘、不入审计（18 文档 R10 现有声明归档进本节）。
- **依赖**：与 R10 权限模式面同轮写（fullaccess 边界声明依赖模式定义，permission.rs:19-27 已存在，无阻塞）。
