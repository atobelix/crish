## 一、审计总览与方法论

桌面端 AI 工作台（Crish / Conex）具有**超长单次运行周期（数小时至数天不关窗）**、**高频多会话并发流式输出（~31Hz 帧率）**、**多工作区/分屏标签页频繁挂载卸载**以及 **WebView2 + Tauri 双层事件桥接**四大特征。在此运行模型下，任何微小的单会话残留、异步监听卸载竞态、无界模块级缓存或热路径同步 `localStorage` 序列化，都会随运行时间线性或超线性累积，最终表现为内存膨胀（Memory Bloat）、GC 停顿加剧、滚动/输入掉帧乃至后台 Rust PTY 子进程孤儿化。

本次审计对 `apps/crish-desktop/src/**` 与 `packages/**` 进行了全量静态与数据流追踪，围绕以下四个正交维度展开：

1. **模块级缓存、单例容器与会话逐出/删除级联闭环**：盘点全仓所有模块级 `new Map`、`new Set`、全局数组、单例 Registry 及 LRU 缓存，逐一核查其容量上界、字节计量准确性、淘汰算法（LRU vs 断崖式 `.clear()`），以及在**会话软逐出（Soft Eviction）**与**会话硬删除（Hard Delete）**两条生命周期路径上的清理接线完整性。
2. **Tauri IPC / 原生窗口异步监听竞态（Async Unlisten Race）与 Store 订阅生命周期**：逐一核查 `@tauri-apps/api/event` 的 `listen()`、`getCurrentWindow().onResized()` / `onFullscreenChanged()`、Fanout 广播桥以及 Zustand Store 订阅在 `useEffect` 与单例服务中的挂载/卸载时序安全性。
3. **DOM 引用驻留、Observer / 定时器 / Web Worker / ObjectURL 生命周期闭环**：排查 `ResizeObserver`、`MutationObserver`、`IntersectionObserver`、`setTimeout` / `setInterval` / `requestAnimationFrame`、`LayerStackManager` 事件快照、隐藏终端写入门闩（`PtyWriteGate`）及 `WorkerPool` 中的闭包引用与 Detached DOM 驻留。
4. **主线程高频同步 `localStorage` I/O 与大对象 JSON 序列化阻塞**：追踪流式输出、状态变更、日志记录、模型/会话切换热路径上的同步 `localStorage.getItem` / `setItem` 与 `JSON.parse` / `JSON.stringify` 调用链。

### 第一类：会话软逐出（Soft Eviction）与硬删除（Hard Delete）级联断链及全局缓存驻留泄漏

#### F-09-01：`MessageSnapshots` 字节账本严重失真（漏算全量 `SessionMessage[]`）且会话软逐出未清理，击穿 5MB 预算并使消息逐出失效

- **精确位置**：
  - [`apps/crish-desktop/src/api/MessageSnapshots.ts:116-135`](file:///c:/Software/conex/apps/crish-desktop/src/api/MessageSnapshots.ts#L116-L135)（`SnapshotEntry` 结构定义）
  - [`apps/crish-desktop/src/api/MessageSnapshots.ts:175-192`](file:///c:/Software/conex/apps/crish-desktop/src/api/MessageSnapshots.ts#L175-L192)（`estimateBytes` 仅统计 `delta.inserted`）
  - [`apps/crish-desktop/src/api/MessageSnapshots.ts:244-256`](file:///c:/Software/conex/apps/crish-desktop/src/api/MessageSnapshots.ts#L244-L256)（`push` 压入全量 `messages.slice()` 却只按 `delta` 记账）
  - [`apps/crish-desktop/src/store/sessionStateActions.ts:141-158`](file:///c:/Software/conex/apps/crish-desktop/src/store/sessionStateActions.ts#L141-L158)（`evictSessionMessagesInState` 未清理 `MessageSnapshots`）
- **关键代码证据**：
  ```ts
  // apps/crish-desktop/src/api/MessageSnapshots.ts:175-192
  private estimateBytes(delta: MessageDelta): number {
    let bytes = 64; // base overhead per entry
    for (const msg of delta.inserted) {
      bytes += (msg.id?.length ?? 0) * 2;
      bytes += (msg.text?.length ?? 0) * 2;
      bytes += (msg.thought?.length ?? 0) * 2;
      // ...
    }
    return bytes;
  }

  // apps/crish-desktop/src/api/MessageSnapshots.ts:244-256
  const delta = this.computeDelta(messages, nextMessages);
  const bytes =
    options?.heightSnapshot !== undefined
      ? this.estimateBytesWithHeights(delta, options.heightSnapshot)
      : this.estimateBytes(delta);
  const entry: SnapshotEntry = {
    delta,
    timestamp: Date.now(),
    bytes,
    messages: messages.slice(), // <--- 实际驻留变更前全量 SessionMessage[] 浅拷贝！
    ...(options?.scrollOffset !== undefined && { scrollOffset: options.scrollOffset }),
    ...(options?.heightSnapshot !== undefined && { heightSnapshot: options.heightSnapshot }),
  };
  ```
- **泄漏链路推导与定量评估**：
  1. **账本失真 100~1000 倍**：当用户在包含 400 条消息（约 2MB 文本与工具调用输出）的会话中执行「撤回最后 1 条消息」或「重生成」时，`messages`（变更前 400 条）比 `nextMessages`（变更后 398 条）多出 2 条消息，`computeDelta(messages, nextMessages)` 计算出的 `delta.inserted` 仅包含被撤回的 2 条消息（约 1KB）。然而 `entry.messages = messages.slice()` 将完整的 **400 条消息引用（2MB）** 存入了 `SnapshotEntry`。由于后续流式生成通过 Immer 生成新的 `SessionMessage` 对象引用，旧快照中的 `entry.messages` 逐渐与当前会话解耦成为独立驻留副本。10 层快照即可驻留 **20MB**，而 `this.totalBytes` 账本仅记录约 **10KB**，`MAX_TOTAL_BYTES = 5MB` 的全局预算形同虚设。
  2. **软逐出失效**：当后台会话被 `evictSessionMessagesInState`（`sessionStateActions.ts:141-158`）软逐出（`sess.messages = []`）以释放内存时，`MessageSnapshots` 中该会话的 `entry.messages` 依然强引用着完整的 `SessionMessage[]` 数组，导致 GC 根本无法回收被逐出会话的消息体！
- **根治方案设计**：
  1. **账本如实计量或纯 Delta 化**：在 `estimateBytes` 中必须对 `entry.messages` 全量消息列表进行字节累加（或彻底移除 `entry.messages` 全量冗余，仅保留真正被删除/覆盖的差量消息切片）。
  2. **软逐出联动清理**：在会话软逐出（`evictSessionMessagesInState`）时，同步调用 `messageSnapshots.clear(sessionId)` 释放该后台会话的撤回快照栈。

## 四、架构级根治路线图与防回归门禁设计

为彻底终结「每新增一个模块级 Map 就要手动去 `SessionCoordinator` 补一行清理、每写一个 `useEffect` 监听就要手写 `disposed` 布尔锁」的脆弱模式，建议按以下四个架构原语统一收口：

### 4.1 统一会话生命周期级联协议（`SessionLifecycleRegistry`）

在 `apps/crish-desktop/src/store/sessionLifecycleRegistry.ts` 建立中心化生命周期钩子注册表，由 `sessionCrudActions.ts` 的底层原语直接驱动（从而无论调用方走 `SessionCoordinator.deleteSessionCascade` 还是直调 `sessionStore.deleteSession` / `evictSessionMessages`，均 100% 触发）：

```ts
export interface SessionLifecycleSubscriber {
  /** 会话消息被软逐出（内存释放但会话保留） */
  onSoftEvict?: (sessionId: string) => void;
  /** 会话被永久硬删除 */
  onHardDelete: (sessionId: string) => void;
}
```

### 4.2 异步监听器安全挂载原语（`useSafeAsyncListen` & 代际令牌）

针对 Tauri `listen()` 与 `win.onResized()` / `onFullscreenChanged()` 返回 `Promise<UnlistenFn>` 的特性：

1. 在 `apps/crish-desktop/src/hooks/useIpcListener.ts` 旁提供通用 `useSafeAsyncListen(subscribeFn: () => Promise<() => void>, deps)` Hook，内部封装 `disposed` 标志与解析后二次校验（`if (disposed) { unlisten(); return; }`），替掉 `AppBootstrap.ts` 等散落的手写异步 `useEffect`。
2. 对 `WindowResizeBridge` 与 `ptySessionApi` 等单例类的异步 `connect()` / `ensureTauriListen()`，强制引入 `connectEpoch` 代际计数或解析后状态复查（`if (!this.connected) unlisten()` / `checkCleanupUnlisten(entry)`）。

### 4.3 模块级缓存有界化与平滑 LRU 契约

1. 废除 `timelineCache.ts` 与 `markdownRenderLite.ts` 中的整表 `.clear()` 断崖式淘汰，统一替换为 `@crish/shared-utils` 的 `LruCache<K, V>` 或 Map 头部逐条淘汰。
2. 对 `MessageSnapshots.ts` 修正 `estimateBytes` 使之包含快照消息体真实字节数，确保 5MB 预算刚性生效。

1. 在 `withPersist.ts` 中对 `partialize` 产出的切片增加顶层字段浅比较（Shallow Equal Short-Circuit）：当流式帧仅更新 `sessions` / `tokenUsage` 而未触碰 `partialize` 关注的持久化字段时，直接跳过 `JSON.stringify` 与 `localStorage.setItem`。
