## 一、判准深化：真兼容 vs 伪兼容的最高物理分水岭再审视

在 Conex / Crish 现代化桌面生产力架构的持续演进中，伴随着从早期单体 Store 到物理分立状态拓扑、从全树调和到原生双轨直通推流（StreamDirect）、从粗粒度全局挂起到细粒度窗格级动画隔离的深度跃迁，系统代码库中沉淀了大量在不同重构波次中引入的过渡代码。

如果缺乏对「兼容性」本质的科学判准，极易陷入两种极端错误：

1. **伪兼容泛滥**：将过渡期的临时内存代理、废弃方法桩和旧版参数当作“安全垫”长期保留，导致代码库臃肿、类型系统被 `any` 或逃逸索引签名侵蚀、运行时每次属性访问产生无谓开销；
2. **冒进破坏真兼容**：在清理历史代码时未能识别系统核心资产边界，误触用户本地持久化存储、加密凭据或未保存草稿，造成灾难性的用户数据丢失。

为此，本审计再次重申并深化确立真兼容与伪兼容的绝对物理分水岭：

```
+------------------------------------------------------------------------------------------------------------------------+
|                                        真兼容 vs 伪兼容 最高物理分水岭决策矩阵                                         |
+-------------------+----------------------------------------------------+-----------------------------------------------+
| 核心判准维度      | 真兼容 (True Compatibility · 100% 捍卫)            | 伪兼容 (Pseudo-Compatibility · 物理拔除)      |
+-------------------+----------------------------------------------------+-----------------------------------------------+
| 核心守护目标      | 用户数字资产主权，跨设备/跨进程/跨版本永续无损     | 迁就代码库内部历史调用习惯，掩盖架构断层      |
| 物理存储边界      | SQLite 磁盘介质、Windows DPAPI 存储槽、本地草稿    | 纯前端内存运行时、React 组件 Props、内部类别名|
| 典型技术载体      | SQLite 3-Way Merge 写屏障、DPAPI 凭据迁移、草稿字典| Proxy 动态属性代理、多叉树死层、通配符挂起    |
| 运行时性能影响    | 离散低频：仅在冷启动、磁盘 I/O 水合与持久化时触发  | 高频热路径：每毫秒流式追加与每次渲染反复扣税  |
| 引用同一性        | 严格维护数据结构纯度，不可变引用确定性             | 彻底破坏 Object.is，每次读取返回全新浅复制对象|
| 类型系统安全性    | 精确强类型映射，强类型序列化/反序列化守卫          | 充斥 [key: string]: unknown 索引签名与 as any |
| 架构演进价值      | 系统持久性基石，任何重构轮次严禁削弱               | 阶段性过渡脚手架，重构闭环后必须彻底物理切除  |
| 最高工程裁决      | 【100% 保留与捍卫，0 丢失 0 截断 0 覆写】          | 【全仓深度排查，坚决物理切除，杜绝伪兼容】    |
```

### 1.1 用户数字资产的“绝对不丢”防线（真兼容）

真兼容的核心是**对用户数据主权的绝对尊重**。在本地优先（Local-First）桌面架构下，用户的所有思考痕迹与产出均属于绝对不可侵犯的资产：

1. **SQLite 3-Way Merge 增量写屏障（0 丢失捍卫）**：
   - **代码锚点**：`apps/crish-desktop/src/api/session-persistence/sessionDeltaWriteBarrier.ts:97-248`、`sessionRustDbHydrate.ts:282-320`、`crates/conex-db/src/sessions.rs:38-84`
   - **集合论无损合并证明**：设磁盘迟到水合快照集合为 $D$（Disk），当前现场活跃内存集合为 $M$（Memory / Live）。
     - **差集保留（$M \setminus D$）**：用户在冷启动延迟水合或降级期间新建的会话（Live 独有）100% 强行保留置顶，绝不被迟到的磁盘骨架清空；
     - **交集无损深度合并（$M \cap D$）**：同一会话在两端均存在时，通过 `mergeMessagesById(diskMsgs, liveMsgs)` 进行消息 ID 级去重合并，补全磁盘历史旧消息的同时，绝对保留流式尾部最新产生的 Token 与思维链；用户显式修改的标题（`titleSource === "user"`）强制胜出，杜绝被磁盘陈旧自动标题回退覆写；
     - **全集求并（$M \cup D$）**：最终生成会话列表为 `[...normalizedNewSessions, ...mergedDiskSessions]`；
     - **细粒度写屏障防护**：`shouldBlockWrite` 刚性拦截 `full_session_index` 空骨架覆写与 `orphan_cleanup` 孤儿误删，唯独永远放行 `single_session_delta` 单会话增量落盘；
     - **后端 ACID 约束**：`upsert_session_entry` 采用 `ON CONFLICT(id) DO UPDATE`，彻底消除 `INSERT OR REPLACE` 误发 `ON DELETE CASCADE` 导致级联删除历史消息的隐患。

2. **Windows DPAPI 凭据安全迁移（0 凭据遗失保障）**：
   - **代码锚点**：`apps/crish-desktop/src/api/provider-profiles/migrateLegacyProfiles.ts:1-100`、`rustProfileStore.ts`
   - **安全屏障协议**：系统坚决禁止“先删后迁”的脆弱逻辑。明文 API Key 必须经由 Rust `config_profile_apply` 导入 Windows DPAPI 安全凭据槽；只有收到 Rust 返回 `status === "ok"`、`persistence === "persisted"` 且 `hasKey === true` 的物理落盘确认后，才执行从 `localStorage` 中剥离明文密钥（`stripApiKey`）；在开发模式或降级模式下绝对保留明文且不打迁移完成标记，确保凭据 100% 可恢复。

3. **多窗格离线草稿持久化（跨崩溃/重启 100% 原位还原）**：
   - **代码锚点**：`apps/crish-desktop/src/store/sessionDraftActions.ts:50-81, 135-206`、`sessionStore.ts:76-96`
   - **复合作用域隔离**：草稿状态树采用 `${paneId}::${sessionId}` 复合作用域，左窗格与右窗格的草稿互不踩踏；
   - **哨兵态与原子转正**：未选择会话时自动进入 `PENDING_DRAFT_SESSION_ID = "__pending_draft__"` 哨兵模式，UI 稳定呈现专属欢迎态；用户输入时通过 `partialize` 将 `composerDrafts` 严格持久化至 `crish_session_store`；首条消息发送时启动原子转正（`commitDraftIfNeeded`），毫秒级完成 ID 移交与附件挂载，草稿内容 1 字节不丢。

### 1.2 内部多版本迭代产物的性能毒性（伪兼容）

与用户数字资产相反，存在于前端内存中、用于讨好历史废弃代码的伪兼容层，构成了严重的系统性能瓶颈与架构隐患：

1. **Proxy 动态属性代理**：通过 `createSessionsByIdCompatibilityProxy` 拦截属性访问，每次读取均执行 `createCompatibleSessionView` 浅拷贝对象，彻底破坏 `Object.is` 引用短路机制，每秒引发 1,200 次垃圾对象分配，诱发 V8 Minor GC 停顿与 React 全树级联重渲染；
2. **多叉树算法死层（`buildGitTree`）**：在概览面板改动呈现已改为线性列表后，仍保留复杂的树形递归构建与节点压缩算法，徒增 CPU 计算与内存开销；
3. **全局通配符挂起（`ResizeObserverManager.setSuspended`）**：使用 `'*'` 通配符挂起所有视口尺寸监听，直接误杀后台正在流式推流的独立会话窗格，破坏分屏隔离架构；
4. **废弃组件壳与孤儿测试（`AddProviderMenu` 等）**：业务调用已清零，却仍保留空桩代码和配对单测，掩盖了代码库真实状态，虚耗 CI 运行时间。

### 2.1 领域一：UI 视图层废弃多叉树结构与过时 Props 清剿

#### 2.1.1 `buildGitTree` 多叉树算法死层深度排查与收敛

- **代码锚点**：`apps/crish-desktop/src/api/gitTreeHelpers.ts:63-246`
- **问题本质与病灶穿透**：
  在早期 Git 变更视图中，变更文件曾采用目录树多叉结构进行展示。随着产品设计全面收敛为高效的扁平变动列表（`OverviewChangesList`），生产 UI 视图层已彻底停用树形结构。然而在 `gitTreeHelpers.ts` 中，依然遗留了长达 180+ 行的多叉树构建代码：
  - `GitTreeBaseNode`、`GitTreeFolderNode`、`GitTreeFileNode`、`GitTreeNode`；
  - `buildGitTree(files, options)` 递归多叉树构造函数；
  - `compactTreeFolders` 单子节点目录折叠压缩算法；
  - `normalizeDepth` 节点深度递归重标定算法。
- **算法开销与内存浪费推导**：
  `buildGitTree` 对每个文件路径执行斜杠分割（`split('/')`），从虚拟根节点逐层遍历查找或创建中间目录节点，并在最后执行全树递归排序（`localeCompare`）与递归深拷贝折叠。
  在 $N$ 个变更文件、平均目录深度 $D$ 的场景下：
  - **时间复杂度**：$O(N \cdot D + N \log N)$，每次文件状态变更均重复执行全量树构建；
  - **空间分配**：为每个目录与文件分配独立的中间结构体（`totalFiles`、`totalAdditions`、`totalDeletions`、`children: []`），在 1,000 个变动文件场景下瞬间在堆中产生逾 3,500 个瞬态对象；
- **单轨替代与现状收敛**：
  当前生产视图（`OverviewChangesList` / `WorkspaceGitChangesView`）已 100% 收敛至基于 `GitStatusFile` 线性数组直接渲染，配合无状态纯函数微条度量计算：
  ```ts
  // 唯一保留的 SOTA 纯函数度量：apps/crish-desktop/src/api/gitTreeHelpers.ts:41-61
  export function calculateDiffStatBars(
    additions: number,
    deletions: number,
    maxBars: number = 5
  ): DiffStatBarsResult {
    const safeAdd = Math.max(0, additions || 0);
    const safeDel = Math.max(0, deletions || 0);
    const total = safeAdd + safeDel;
    if (total === 0 || maxBars <= 0) {
      return { addBars: 0, delBars: 0, emptyBars: maxBars > 0 ? maxBars : 0 };
    }
    const addBars = Math.min(maxBars, Math.round((safeAdd / total) * maxBars));
    const delBars = Math.min(
      maxBars - addBars,
      Math.round((safeDel / total) * maxBars)
    );
    const emptyBars = Math.max(0, maxBars - addBars - delBars);
    return { addBars, delBars, emptyBars };
  }
  ```
  `buildGitTree` 及其附属算法已打上 `@deprecated` 刚性印记，全仓生产调用量已确认为 **0**（仅存量单元测试引用）；本次审计明确其为死算法层，后续构建应彻底物理拔除。

### 2.2 领域二：`OverviewCard` 复合对象订阅与 SOTA 细粒度 `useSessionAgents` 标量单轨重构

#### 2.2.1 复合对象订阅的性能击穿现场

在重构前，总览面板 `OverviewCard.tsx` 存在典型的状态过度订阅问题：

```ts
// 重构前高危代码：OverviewCard.tsx:50-53
const session = useSessionStore((s) =>
  scopedSessionId ? s.sessionsById[scopedSessionId] || null : null
);
```

当系统处于 100 Token/s 高速推流状态时：

1. 后端不断向 `scopedSessionId` 对应的会话注入增量消息分片；
2. Store 触发 Mutation 更新，`s.sessionsById[scopedSessionId]` 引用发生改变；
3. `useSessionStore` 的浅比对 `Object.is(prev, next)` 彻底失效；
4. `OverviewCardInner` 发生强制重渲染；
5. 其子组件 `<OverviewHeader session={session} />`、`<AgentSection agents={session?.agents || []} />`、`<ChangesSection />` 全部被级联重绘！
