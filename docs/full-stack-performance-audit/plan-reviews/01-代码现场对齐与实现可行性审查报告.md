# 一、执行摘要与审查总体裁决结论

## 1.1 审查全景与宏观裁决

作为【Reviewer-01：代码现场对齐与实现可行性首席审查官】，本审查基于真实代码库（`apps/crish-desktop/src/`、`packages/`、`crates/`）的物理文件、符号定义与执行时序，对《前端性能全景优化总方案》（`00`）及 10 份实施详案（`01` ~ `10`，共计 14,156 行）进行了全面、透彻的现场穿透审查。

### 核心审查裁决：

1. **理论高度与病灶穿透力：极度优秀（Outstanding）**  
   方案准确命中了 Conex / Crish 长期存在的重大系统性性能断层，如：
   - Part 02 `StreamTextBatcher` 全文长度度量导致 8000 字符后水位线永久失效并退化为同步强刷；
   - Part 03 `FlowScrubber` 导轨挂载 3 类 Observer（含全子树 MutationObserver）并调用 `marked.Lexer` 词法解析整篇 Markdown；
   - Part 04 `WorkerPool` 任务超时未调用 `worker.terminate()` 导致底层僵尸线程串话；
   - Part 05 `useComposerMultiline` 击键时将 `text` 作为 Effect 依赖导致每 150ms 反复拆装监听器与强制同步重排；
   - Part 06 `useSessionListWindow` 将 `scrollParentRef` 误绑至 `flex: none` 的无滚动条容器导致侧边栏 2000 会话虚拟化自毁；
   - Part 07 `useDiffHighlightMap` 滚动 1 行导致现有 49 行彩色高亮被重置为 `escapeHtml` 纯文本引发视口全量剧烈闪烁；
   - Part 08 `Tooltip.tsx` 在可见期启动 60~120fps `requestAnimationFrame` 死循环并在每帧读取 `getBoundingClientRect()`；
   - Part 08 `SafeAimEngine` 构造即注入全屏 SVG 并常驻 1000Hz `mousemove` 监听器；
   - Part 09 `taskEventHandlers.ts` 中 `onTimerFired` 误用 `activeTimerIds.add(e.timerId)` 导致已触发定时器永久泄漏；
   - Part 09 `MessageSnapshots.ts` 真实账本失真，快照强引用全量消息数组导致 20MB 物理内存驻留；
   - Part 10 `manualChunks` 将 `/src/api/chat-bridge/` 粗暴大包聚合引发 Rollup 依赖吸收黑洞与静态环；
   - Part 10 `entry-core.tsx` 中 `createRoot` 前置阻塞 `await preloadHydrationSnapshot()` 造成冷启动首屏白屏瀑布。  
     上述发现**100% 具备确凿的代码现场证据，分析极其深刻准确**。

2. **落地可行性与代码现场吻合度：存在局部断层与高风险区域（Caution Required）**  
   文档在从“架构构想”转化为“工程实施”的过程中，存在**三大系统性偏差**：
   - **偏差 A（重构爆炸半径过大）**：Part 01 提议将 `useSessionStore` 彻底物理拆解为 `metaById` + `messagesBySessionId` 并废除 `sessionsById`，但代码现场有 **80 多个文件、30 多个关键单测** 强依赖 `sessionsById` 与 `sessions` 结构。若一次性硬切，将引发全仓编译大面积红屏与逻辑断裂；
   - **偏差 B（文件路径漂移与扩展名假设不匹配）**：文档中存在至少 **12 处真实源码路径与文档引用路径的偏移**（如组件被放置在不存在的子目录中，或 `.tsx` 误写为 `.ts`），若开发者机械按照文档找文件或新建文件，将导致模块重复或找不到目标；
   - **偏差 C（跨文档参数与契约微小撕裂）**：持久化防抖在 Part 01 宣称为 300ms，在 Part 02 为 350ms，在 Part 09 为 250ms；子 Agent 实时事件在 Part 02 宣称 0 写入 `sessionStore`，但在 Part 01 状态树中又列出了 `agentsBySessionId`，状态收敛时序缺乏细化。

# 二、文档体系内在矛盾、参数冲突与契约漏洞审计

在全面交叉阅读全部 10 份详案与 `00` 总纲后，审查官定位出以下 5 处跨文档内在不一致与契约盲区：

### 2.1 状态树拓扑定义的断层：彻底物理拆解 vs 既有代码大面积引用的冲突

- **矛盾现场**：
  - `01-状态管理与重渲染优化实施详案.md` §2.1 与 §1.2 裁决：将 `SessionStoreState` 物理拆分为 `metaById`（只读元数据）与 `messagesBySessionId`（高频内容），并宣称“彻底切除 `sessionsById` 与 `sessions` 数组”。
  - 但在 `02-对话流式引擎.md`（P2-F08~F10）、`06-多窗格分屏.md`（PERF-06-15）、`07-重型工具视图.md`（D-01）、`09-内存生命周期.md`（F-09-02）中，大量代码示范与现有逻辑仍直接调用 `s.sessionsById[id]`、`s.sessions`，甚至依赖 `sessions.findIndex`。
- **漏洞危害**：若执行波次 W2-1 直接删除 `sessionsById` 与 `sessions` 字段，全仓其余 9 个模块的既有代码将瞬间遭遇类型断裂与运行时 `TypeError: Cannot read properties of undefined`。
- **裁决建议**：必须在 `01` 中确立**双轨兼容适配层（Compatibility Adapter Layer）**规范：内部数据源物理拆分为 `metaById` 与 `messagesBySessionId`，但对外通过只读 Getter 或 Proxy 保持 `sessionsById[id]` 的形状兼容，禁止一步到位强制全仓 80+ 文件同批修改。

---

### 2.2 持久化防抖参数的跨文档漂移：250ms vs 300ms vs 350ms 未归一

- **矛盾现场**：
  - `00-前端性能全景优化总方案.md` §1.1：定义“持久化 300ms 防抖”；
  - `01-状态管理详案.md` §2.5 / ISSUE-14：定义 `DebouncedStateStorage` 为 `300ms` trailing debounce；
  - `02-流式引擎详案.md` §1.3 / P2-F14：定义 SQLite 持久化防抖为 `350ms`（历史基线）；
  - `09-内存生命周期详案.md` §1.1 / F-09-20：定义 `withPersist` 存储防抖为 `250ms`。
- **漏洞危害**：同一客户端对于本地存储和磁盘持久化存在三种不同毫秒数的防抖定时器，导致在多窗口分屏或连续输入时，不同 Store 的落盘时序不可预测，甚至造成持久化快照相互覆盖。
- **裁决建议**：在 `00` 与各详案中统一锁定单一契约常量：**`STORAGE_PERSIST_DEBOUNCE_MS = 300`**，全仓所有 Storage 中间件统一遵循 300ms 尾随防抖。

---

### 2.3 子 Agent 高频流式事件的状态归属与时序语义模糊

- **矛盾现场**：
  - `02-流式引擎详案.md` §1.2 裁决：子 Agent 400~600Hz 高频事件**绝对禁止写入 `sessionStore`**，流式期间 100% 收敛在裸 Zustand `useStreamingStore`，流终态（`subagent-done`）才单次同步写入主库。
  - `01-状态管理详案.md` §2.1.2 状态树拓扑图：在 Tier 2B（领域主数据树）中显式定义了 `agentsBySessionId: Record<string, SubAgentState[]>`，并未清晰阐明该字段在流式运行期间是否实时派发。
- **漏洞危害**：如果前端 UI（如 `AgentCard.tsx` 或 `InlineAgentPanel.tsx`）直接订阅了 `useSessionStore(s => s.agentsBySessionId[pid])`，在流式期间将完全感知不到子 Agent 的实时状态变化；而若它去写入 `useSessionStore`，又击穿了 Part 02 的 0 写入红线。
- **裁决建议**：明确在 `01` 和 `02` 中建立**子 Agent 统一 ViewModel 订阅协议**：
  - 流式运行态：`useStreamingStore` 维护 `streamingAgentsByKey: Record<string, SubAgentState>`；
  - 视图层：统一使用派生 Hook `useSessionAgents(sessionId)`，在内存中浅合并持久态 `agentsBySessionId` 与流动态 `streamingAgentsByKey`，兼顾 0 污染主库与 UI 实时响应。

---

### 2.4 终端门闩 512KB 有界环形缓冲的高并发吞吐边界盲区

- **矛盾现场**：
  - `07-重型工具详案.md` §1.4 与 `09-内存生命周期详案.md` §2.4：设定后台隐藏终端使用 `BoundedRingWriteGate`（512KB 字符上限），超出时淘汰最老数据。
  - 但在方案中未详细定义：当后端突发超大并发吞吐（如 `cargo test` 瞬间输出 10MB 日志）且前端在后台长时间运行时，丢弃最老分片后是否向用户呈现截断提示？切回前台时，xterm.js 的滚动条（Scrollback）是否会与后端真实日志行号产生断层？
- **裁决建议**：在 `07` 中补充边界防御断言：当环形队列触发滑动淘汰时，必须在当前缓冲头部插入显式的 ANSI 警示标记 `\r\n\x1b[33m[crish: terminal background output truncated to 512KB to preserve memory]\x1b[0m\r\n`，确保开发者切回时知晓历史日志已被截断。

---

### 2.5 构建拆包预算双层门禁与实际产物现状的过渡断层

- **矛盾现场**：
  - `10-冷启动详案.md` §3 / PERF-DIM10-003：硬性要求首屏静态依赖图预算由 1800 KiB 压缩至 **≤980 KiB**，入口主包预算由 350 KiB 压缩至 **≤280 KiB**。
  - 但在当前源码库中，`scripts/check-startup-budget.mjs` 中的既有配置和真实构建输出显示，`vendor-pretext`（122.7KB）、`vendor-dompurify`（121.8KB）尚未完全与首屏解耦，若在 Wave 1 就直接以 980 KiB 作为 CI 阻断线，会导致当前流水线无法提交。
- **裁决建议**：在 `10` 与 `00` 规划中明确**渐进式门禁演进阶段**：
  - 第一阶段（Wave 1 基线）：维持 1800 KiB 软警报门禁；
  - 第二阶段（Wave 4 拆包断边落地后）：严格启用 ≤980 KiB 与 ≤280 KiB 硬阻断门禁。

# 四、关键路径重构波及面（Blast Radius）与落地风险评估

针对 10 大详案提出的激进重构设计，审查官从实际工程落地、改动扩散面与质量门禁风险出发，评估出以下 4 大核心风险：

## 4.1 核心风险一：全局 Store 拓扑断裂导致类型系统与单测全量雪崩

- **现状基线**：全仓经过 `rg` 严密排查，共有 **84 个业务/测试文件** 显式引用了 `sessionsById` 或 `sessions` 结构：
  - 包括核心 Action 文件：`sessionCrudActions.ts`, `sessionActions.ts`, `sessionIndex.ts`, `sessionOrderingActions.ts`, `sessionStateActions.ts` 等；
  - 包括核心组件与 Hook：`useSidebarSessionList.tsx`, `useSidebarHandlers.ts`, `UnitChromeActions.tsx`, `useChatMessageState.ts`, `useRuntimePanelData.ts` 等；
  - 包括 30 余个自动化回归单测：`sessionActions.test.ts`, `sessionIndex.test.ts`, `sessionRustDbWriteModel.test.ts` 等。
- **风险等级**：**严重（Critical）**
- **风险后果**：若在 Wave 2 第一拍就硬性从 `SessionStoreState` 中彻底删除 `sessions` 数组或 `sessionsById` 字典，将直接引发全仓上千处 TypeScript 类型报错，导致整个流水线瘫痪，且极易引入难以察觉的隐性逻辑回归。

---

## 4.2 核心风险二：Markdown 投机闭合与富文本输入器双向契约漂移

- **现状基线**：Part 04 裁决采纳基于元数据的投机闭合补齐器（`fastSpeculativeClose`），下游 `MarkdownBlockItem.tsx` 将真实消费 `virtualClosedText` 呈现流式代码块容器与高亮外壳；而 Part 05 对 Tiptap 的 Markdown 序列化规则进行了细化。
- **风险等级**：**高（High）**
- **风险后果**：若增量 Markdown 解析器在补齐代码围栏（` ``` `）或 LaTeX 公式块（`$$`）时，与 Tiptap 的反序列化规则（`markdownDeserializer`）在空格、换行符处理上存在微小差异，将导致用户在代码块附近进行协同输入时出现光标跳动或 AST 解析不一致。

---

## 4.3 核心风险三：Vite 构建拆包断边与动态导入缺失导致的运行时白屏

- **现状基线**：Part 10 要求将 `App.tsx`、`ChatCard.tsx`、`ChatMessageList.tsx` 等进行深层动静拆包，并对 `manualChunks` 施加严格的纯逻辑封闭红线。
- **风险等级**：**高（High）**
- **风险后果**：Rollup 的分包逻辑对隐式动态导入和跨 chunk 循环非常敏感。一旦某个被懒加载的组件（如 `ChatMessageList`）内部不小心静态引入了主 Chunk 依赖的上下文单例，Rollup 会默默生成不可控的双向依赖环，导致在生产环境打包后浏览器加载报错 `Cannot access '__WEBPACK_DEFAULT_EXPORT__' before initialization` 或直接白屏。

---

## 4.4 核心风险四：分屏 Resizer 拖拽期全局观察器冻结状态机失步

- **现状基线**：Part 06 要求三大 Resizer 必须成对调用 `beginLayoutInteraction` / `endLayoutInteraction`，并在拖拽期间 100% 挂起 `ResizeObserverManager`。
- **风险等级**：**中等（Medium）**
- **风险后果**：若用户在拖拽分屏线时鼠标移出窗口、触发浏览器失焦（`blur`）或触发快捷键切换应用，导致 `pointerup` / `pointercancel` 未被正常捕获，可能使 `ResizeObserverManager` 永久处于“冻结挂起”状态，后续全窗口将再也无法响应尺寸变化。

# 五、更优、更契合代码现状的实施改进方案（Alternative Solutions）

针对上述四大风险与代码现场实际，审查官提出以下 4 项修改面更小、风险更低、效果更稳固的工程落地替代方案：

## 5.1 方案 A：状态层渐进重构（兼容代理层 + 物理双轨分水岭）

为了化解“84 个文件强依赖 `sessionsById`”与“物理分层消除重绘级联”之间的尖锐矛盾，提出**渐进式兼容适配落地路径**：

```ts
// apps/crish-desktop/src/store/types.ts 演进设计
export interface SessionStoreState {
  // 1. 新增物理隔离的高频单会话实体树 (Tier 2B)
  messagesBySessionId: Record<string, SessionMessage[]>;
  agentsBySessionId: Record<string, SubAgentState[]>;

  // 2. 新增全局低频元数据实体树 (Tier 2A)
  metaById: Record<string, SessionMeta>;
  sessionIds: string[];

  // 3. 严格保留 sessions 与 sessionsById 的兼容层（只读投影）
  // 允许老代码以 s.sessionsById[id] 访问，但底层消息与高频流式更新时：
  // 仅更新 messagesBySessionId[id]，不克隆顶层 sessions 数组与 sessionsById 字典！
  sessions: SessionState[];
  sessionsById: Record<string, SessionState>;

  activeSessionId: string;
  // ... 其他字段
}
```

### 实施步骤：

1. **第一阶段（读取解耦）**：
   - 组件层与 Selector 全量迁移为标量选择器（如 `s.metaById[id]?.title`），高频消息读取接入专属选择器 `useSessionMessages(sessionId)`（直接命中 `s.messagesBySessionId[id]`）；
   - 维持 `sessionsById` 兼容字段存在，既有单测与未改造的 60 个低频文件无需同步修改，全仓 0 编译红屏；
2. **第二阶段（写入解耦）**：
   - 在 `sessionMessageActionsCore.ts` 与流式收尾处，消息变更仅向 `state.messagesBySessionId[sessionId]` 写入；
   - 彻底解除 Immer 对顶层 `sessionsById` 的克隆；
3. **第三阶段（水到渠成退役）**：
   - 待所有关键视图改造完毕后，将 `sessionsById` 降级为只读废弃标记（`@deprecated`），分批收敛。
