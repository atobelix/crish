# 第二轮战役 · 调度、需求锁定与假设清单

> 工作区：`docs/mobile-full-audit/`。本文件是第二轮战役的纪律文档：锁定用户需求、登记假设、固定席位与产出路径、规定后续波次。
> 所有席位的**共同约束**见 `prompts/00-共同约束前言.md`；各席位任务书见 `prompts/`。

## 一、需求锁定

用户硬性要求 U1–U10（极致启动速度、彻底重构、抽象合理、符合 token、非必要不兼容、彻底解决、集中测试、禁止描边类视觉、丝滑过渡、图标克制统一）逐条见前言第二节，**不得降级**。

## 二、假设与待用户裁决

主控对用户原话做了如下理解，席位在方案里必须**显式沿用并标注**，用户可随时推翻：

| 编号 | 用户原话 | 主控理解 | 状态 |
| :-- | :-- | :-- | :-- |
| A1 | “截图的这种带有一种立体的感觉……主界面在上面，侧边栏在主界面下面” | 用户**想要**这种层叠效果（截图来自另一款 App，作参考）；主界面像圆角卡片叠在抽屉之上并右移 | 待确认 |
| A2 | “下面放置头像和名字，然后再是设置再是新建对话的那个按钮” | 抽屉底部栏包含：头像+昵称、设置、新建对话；顺序/行数有歧义，由 N03 给出推荐与备选 | 待裁决 |
| A3 | 新版未提到通知铃铛 | 铃铛的去向未定，由 N03 给方案 | 待裁决 |
| A4 | “任何描边动效我看见就烦，也不允许伪描边” | 全应用清退一切随状态变化的描边/聚焦环/阴影描边；静态分隔线是否保留由 N02 逐处论证 | 已锁定（范围由 N02 登记） |
| A5 | “立体感” 与 项目“默认不要重阴影”规范 | 立体感优先靠圆角+色阶差+位移；是否允许轻阴影由 N03 论证后交用户裁决 | 待裁决 |
| A6 | “打开软件一秒甚至不到一秒” | 验收口径为 **Release 包、华为 P50 冷启动到可交互主界面 ≤1s**；Debug 仅作“尽量快” | 已锁定 |

## 四、设备使用约定

仅 N01 可在 `com.crish.mobile` 范围内使用 adb（只读测量）。其余席位纯静态分析。Metro（8081）常驻，任何席位不得终止。

## 五、后续波次（逻辑依赖，不含工期）

1. **整理波**（依赖：R01–R07 全部完成）
   - 把复核结论整理成「**已确认问题登记册**」：每条含编号、位置（路径:行号）、现象/直接原因/根因三层、置信度、来源席位；单列「降级条目」「作废条目」「待实机验证条目」。
   - 把 N01–N05 的方案**对齐**：合并 token 变更（避免互相冲突）、合并删除清单、裁定跨席位接口（启动→转场→抽屉→图标）。
2. **方案评审波**（依赖：整理波）：对合并后的统一方案做对抗评审——是否考虑全面、是否与代码对得上、是否违反 U2–U9、是否留有隐患。
3. **实现波**（依赖：评审通过）：按分维详案由子 Agent 实现，**全部改完再集中测试**（真机 + Release 实测 + 门禁），不逐步测试。

## 六、纪律

- 子 Agent 不得提交、不得回撤；改动留在工作区，由主控统一验证后提交。
- 复核结论与方案报告一律以“证据 + 置信度”表达，禁止绝对化措辞无前提。
- 第一轮大盘（`00-…汇总与综合修复大盘.md`）在 R07 复核完成前视为**未经复核**，不得引用其中数字。
