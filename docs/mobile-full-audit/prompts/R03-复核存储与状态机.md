## 核查重点

1. **DEF-STO-01「DB 初始化竞态 → Outbox 永久降级内存，离线决策 100% 丢失」**
   - 逐步追：`app/_layout.tsx` 里 `ensurePairingWiringForApp()`、`ensureDatabaseForApp()`、`ensureApprovalWiring()` 的**实际调用顺序与异步边界**；`getSqlDriver()` 在被调用瞬间的返回值；Outbox 单例何时创建、之后是否有替换/升级路径（全局 grep `MemoryOutboxAdapter`、`upgrade`、`setPersist`）。
   - 给出触发该竞态所需的**时序前提**（冷启动 / 热启动 / 已配对 / 未配对分别如何）。“100% 丢失”是否对所有启动路径成立？
2. **DEF-STO-02「`hydrateAccount()` 未捕获 SecureStore 异常 → 永久白屏」**
   - **完整读** `src/adapters/account/accountService.ts` 中 `hydrateAccount` 的整个函数体，标出 `loadAccountSession` 调用点相对于 `try` / `catch` / `finally` 的**精确位置**。`setHydrated(true)` 在哪些分支会执行？（提示：请特别留意 `finally` 块与 `loadAccountSession` 是否在 `try` 之内；不要采信报告所引行号，自己数。）
   - 再读 `loadAccountSession` 与 `expoSecureStoreDriver`：底层异常是在它内部被吞掉、还是向上抛出？“未设锁屏密码的 Android 机型会抛异常”这一前提是否有证据？若报告此条不成立，必须明确写出 🚫 并附完整证据。
3. **DEF-STO-03「序列空洞自愈倒挂，补洞事件被当重复帧丢弃」**：读 `feedBridge.ts` 与 `packages/shared-utils/src/event-ring-window.ts`，构造报告所述序列（游标 100，收到 105，再补 101–104）手工推演每一步 `lastSeq`/`appendFeed` 的结果；核实“立即同步写入 105”是否属实、补洞数据走的是哪条写入路径（是否绕过 `appendFeed` 的重复判定）。
4. **DEF-STO-04「observationWiring 漏传 projections」**：与 R02 同一事实，请独立核实并在报告里互相印证。
5. **DEF-STO-05「5/8 幽灵表零读写」**：对 8 张表逐表 grep 读写点，列出表→读写位置，核实是否真的“仅建表”。同时判断：这些表是“已规划未接线”还是“应删除的死代码”（给出依据：设计文档 `docs/mobile-app-rebuild/02-运行时与连接方案.md` 的规划）。
