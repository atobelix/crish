## 核查重点

1. **「asyncRoutes 缺失是 2378 模块的最大根因，贡献 400~600 模块」**
   - 核实 `app.json` / expo-router 插件配置里是否真无 `asyncRoutes`；到 `node_modules/expo-router` 与 `@expo/metro-config` 中核实 `asyncRoutes` 的**真实语义、适用平台与前提**（是否仅 web？是否要求特定 SDK/配置？Android 原生是否生效？），给出源码或类型定义出处。
   - “400~600 模块”这个区间的来源是什么？是测算还是估计？你能否用只读方式复算（例如统计 `app/**` 路由文件各自的静态依赖闭包大小，或读 Metro 输出）？不能复算就判 ❌ 或 ❓。
2. **「UI 桶文件让任何组件引入都连带 react-native-svg / 58 个 Hugeicons / Reanimated」**：读 `src/presentation/ui/index.ts` 与相关组件的 import 图；核实“Metro 默认不 tree-shake”的准确度（RN 0.86 + Expo 57 下 `inlineRequires` 的实际状态，读 `metro.config.js` 与 `@expo/metro-config` 默认值）——inline requires 会不会使“桶文件连带加载”的影响大幅减弱？
3. **「@noble 引入 126 个纯 JS 模块、2.1MB；应切到 Hermes 原生 `crypto.subtle`」**：核实模块数与体积的统计方法；**核实 RN 0.86 / Hermes 是否真有 `crypto.subtle`**（读 RN 源码/官方文档，找不到出处则判 🚫 或 ❓，并写明）。
4. **APK 体积（277MB）解构**：用只读方式打开 `apps/crish-mobile/android/app/build/outputs/apk/debug/app-debug.apk`（`[System.IO.Compression.ZipFile]::OpenRead`）统计 `lib/*`、`classes*.dex`、`assets` 的**未压缩/压缩大小**，复算“lib 231.44MB 占 83.5%”“24 个 dex”；核实 `expo.useLegacyPackaging`、ABI 列表（`reactNativeArchitectures`）在 `android/gradle.properties`、`app.json`、`build.gradle` 中的真实取值。
5. **「R8 与资源裁剪被全局关闭」**：核实 `android/app/build.gradle:69,116-118` 与 `gradle.properties` 的真实内容；`enableMinifyInReleaseBuilds` 缺省值在当前 RN Gradle 插件版本里是多少（读 `node_modules/@react-native/gradle-plugin` 或模板），“即使 assembleRelease 仍关闭”是否属实？
6. **「生产 APK 可降至 30~38MB」**：这个区间的计算依据是什么？按真实 lib 构成（arm64 单架构 so 大小）能否复算？不能复算则降级为“数量级估计，待 Release 实测”。
7. **渲染性能结论**（`DrawerSessionGroups` 裸 ScrollView、`openSession` 未 `useCallback`、`FileBrowser` 缺 `getItemLayout`、`TimelineView` 每项 `<FadeIn>` 且未 memo、`useApprovalListVm` 1Hz 重建）：逐条读代码确认；**务必考虑 app 已启用 React Compiler**（`app.json` / babel 配置），自动 memo 会使“未加 useCallback/memo”类结论部分失效——对每一条判断 Compiler 是否已覆盖，并给出依据。
8. 用户新增的核心目标是**冷启动 ≤1 秒**：报告是否分析了“启动链路里同步阻塞首屏的真实瓶颈”（例如启动闸门等待账号水合）？如果没有，把这个缺口写进遗漏项（N01 席位会做方案，你只需指出遗漏即可）。
