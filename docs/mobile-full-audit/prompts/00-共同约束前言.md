## 二、用户硬性要求（效果锁，不得降级、不得自行改目标）

| 编号 | 要求 |
| :-- | :-- |
| U1 | **极致启动速度**：打开软件 ≤1 秒（理想 <1 秒）进入可交互的软件界面；不允许长时间停留在开屏标题界面或等待界面。软件本身是轻量的，慢必有具体原因，必须找到并根除。 |
| U2 | **彻底改进代码**：保持简洁、架构清晰；**该删就删，该重构就重构**；减少重复。 |
| U3 | **适应未来发展**：抽象必须合理——要有当前至少两处复用或明确的未来需求依据；不得过度设计（遵守根目录 `ANTI_OVERENGINEERING_GUARDRAILS.md`）。 |
| U4 | **符合项目规范**：样式一律走 theme token，禁止散落硬编码数字/颜色；新增或修改 token 必须在方案里写明名称、值、用途；中文注释、UTF-8 无 BOM。 |
| U5 | **非必要不兼容**：兼容越少越好；反对补丁式改进和兼容式改进（不留旧接口、不留适配层、不留 `// 临时`、不做 `setTimeout` 之类魔法延迟补偿）。深链/路由是否需要兼容旧值，必须逐项论证“谁在依赖”，无人依赖就直接删。 |
| U6 | **发现即彻底解决**：不允许留下任何隐患；方案里每个问题都要有对应的根治动作与验收断言。 |
| U7 | **测试节奏**：不要“改一点测一点”。方案里的验证项写成**一份集中验收清单**（待一大批代码改完之后统一执行），不要把测试拆进每个改动步骤。 |
| U8 | **绝对禁止描边类视觉**：任何描边动效、聚焦环、外发光、阴影充当描边、下划线扫过、渐变边框、脉冲/呼吸光圈、跑马灯边框，以及一切“伪描边”效果。方案不得引入；现有代码中已有的此类效果，要**列出并给出删除方案**。 |
| U9 | **丝滑过渡**：界面切换要连续、跟手，不要生硬转场、不要突变、不要布局跳变；动画走原生线程（Reanimated worklet / 原生栈动画），禁止在 JS 线程逐帧 `setState` 驱动。 |
| U10 | **图标克制且统一**：非必要不显示图标；确需显示的必须来源统一、风格统一。主界面（新对话空态）的品牌大图标没有必要。 |

## 三、证据纪律（严格审计）

1. **亲自读过才算数**：每条结论必须带 `相对仓库根的路径:行号`，并引用不超过 10 行的关键代码。行号以**当前工作区**为准（用 `read_file` 或 `Select-String -Path ... -Pattern ... | Select LineNumber,Line` 现查）。
2. **顺着调用链追到底**：不能只看函数名/注释就下结论；“A 导致 B”必须能指出 A 到 B 的实际调用/数据路径。
3. **每条结论标置信度**：`已验证`（读了代码且追了链路）/ `部分验证`（说明缺什么）/ `推断`（说明推理依据）/ `未验证`。**禁止编造**；没证据就写没证据。
4. **外部知识断言必须有出处**：涉及 React Native / Expo / Android / HarmonyOS 行为的断言，要么指向 `node_modules` 内的源码/类型定义行号，要么指向官方文档并标注“文档，未在本仓库验证”；两者都没有的，降级为“待实机验证”，不得当事实写。
5. **措辞克制**：“100% 瘫痪”“永久丢失”“从未生效”这类绝对化措辞，必须附复现路径与前置条件；做不到就改成准确的条件描述。
6. **区分层次**：现象（用户看到什么）/ 直接原因（哪行代码）/ 根因（为什么会写成这样、架构上缺什么）。三层都要写。

## 四、方案纪律（仅方案席适用，复核席只需遵守第三节）

1. **纯逻辑规划**：只谈逻辑依赖、任务单元、文件域、验收断言；**不谈工期、人天、人员安排**。
2. **问题同权**：严重度（高/中/低）只用于描述风险，**不得用来裁剪方案范围**；所有问题都要解决。
3. **删除优先**：必须给出「可删除的文件/代码/依赖」清单与「重复实现合并」清单，精确到文件与符号。
4. **目标架构**：给出文件级的目标结构（新增/重构/删除），说明每个抽象的存在理由与复用点；不得为了“未来可能”造空壳。
5. **token 变更清单**：列出新增/修改的 token（名称、值、用途、替换哪些硬编码）；不得绕过 theme 直接写字面量。
6. **不降级目标**：用户要求与现实冲突（例如某目标当前做不到），写入「未决问题」并给出**设计验证实验**，不得悄悄把目标改小。
7. **跨席位接口**：与其他席位有依赖的点，只写“我需要对方提供什么 / 我向对方承诺什么”，不重复分析对方领域。
8. **多方案要完整**：用户明确“不怕方案多，就怕方案不全面”。存在真实取舍时，列出 2–3 个完整方案并给出推荐与理由；推荐必须基于代码证据，不基于流行度。

## 六、写文档的方法（前几轮子 Agent 在这里反复踩坑，请照做）

1. 若你有 `write_file` 工具，优先使用它。
2. 否则用 PowerShell 分块追加（每块 ≤150 行），**必须使用单引号 here-string**，避免反引号与 `$` 被解释：

```powershell
$p = 'C:\Software\conex\docs\mobile-full-audit\<目录>\<文件名>.md'
$t = @'
……这里是 Markdown 正文，可以放 ``` 代码围栏……
'@
[System.IO.File]::AppendAllText($p, $t + "`n", [System.Text.UTF8Encoding]::new($false))
```

   终止符 `'@` 必须独占一行且顶格。第一块用 `WriteAllText` 覆盖，其余用 `AppendAllText`。
3. 写完后必须自检：行数、末尾是否完整、中文是否乱码、代码围栏是否成对。
4. 文档为 UTF-8 无 BOM、中文撰写。

## 八、复核席通用规则（R01–R07）

对被复核报告里**每一条**缺陷/断言，逐条给出判定：

| 判定 | 含义 |
| :-- | :-- |
| ✅ 成立 | 引用位置存在且吻合，调用链追得通，表述准确 |
| ⚠️ 部分成立 | 现象存在但表述过强/前提缺失/范围偏大（写明准确表述） |
| ❌ 夸大 | 问题存在但严重度、影响面或量化数字缺乏依据（写明应有的准确程度） |
| 🚫 不成立 | 代码里不是这样（写明实际情况与证据） |
| ❓ 无法验证 | 需要实机/外部条件（写明验证实验） |

每条判定必须包含：被引用位置是否存在、行号是否漂移、调用链复核结果、**修订后的准确表述**、建议修复方案是否合理（是否违反“反补丁/非必要不兼容”）。

此外必须做**遗漏扫描**：列出该维度全部相关文件，逐一说明被复核报告覆盖与否；报告没覆盖到、但你读代码时发现的真实问题，单列「遗漏项」并给出同等质量的证据。

最后输出一张**汇总表**：被复核报告共 N 条，✅ a / ⚠️ b / ❌ c / 🚫 d / ❓ e；并给出“该报告可信度”的一句话评语。
