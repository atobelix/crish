## 用户原话（效果锁）

> 现在打开软件容易有很长时间的等待，我都以为是不能正常进入软件呢。我们的软件应该挺轻量的吧，为什么会有这种长时间停留在开屏标题界面，以及长时间在等待界面呢，这种的都是要避免的呢。一定要有那种快速的感觉才行。**必须在打开软件一秒甚至不到一秒就能进入软件界面才行呢。**

> 我这里还能看到 opendebugger 的提示呢，这个正式版应该没有的吧，如果调试的时候有那还是能接受的。

## 目标

冷启动（点击图标 → 看到**可交互**的主界面）**≤1 秒，Release 包，华为 P50**。不得以“Debug 慢是正常的”搪塞；Debug 另有“尽量快”的目标但不作为验收口径。

## 任务

### A. 还原冷启动时间线（核心）

把启动拆成逐段并给出每段的**证据**：

1. 原生启动：`app.json` 的 `expo-splash-screen` 配置（背景色/图片）、`MainActivity` 启动与 JS 引擎初始化（Hermes）。
2. JS 包加载与求值：expo-router 的 `require.context` 路由表是否一次性求值全部页面；模块总数（第一轮实测 Debug 为 2378 个）；`metro.config.js` 的 `inlineRequires` 状态；Hermes 字节码。
3. `RootShell`（`app/_layout.tsx`）挂载后的**启动闸门**：`if (!hydrated || !accountHydrated)` 显示 `BrandMark + Spinner`（约 `_layout.tsx:88-100`）。逐一追踪闸门依赖的两个状态：
   - `authStore.hydrated`：由 `ensurePairingWiringForApp()` → `authStore.hydrate()` 决定，里面做了什么（SecureStore？文件？网络？）；
   - `accountStore.hydrated`：由 `hydrateAccount()` 决定（`src/adapters/account/accountService.ts` 约 160–212 行），**其中是否包含网络请求**（刷新 token、`fetchAccountMe`、`fetchAccountProfile`、`loadDevices`……）？这些请求是否发生在 `setHydrated(true)` **之前**？网络慢/不可达时闸门会卡多久（读 `REQUEST_TIMEOUT_MS`，`accountApi.ts:19`）？
   - 其余并行的启动任务：`ensureDatabaseForApp()`、`startAppRuntime()`、`ensureNotificationsForApp()`：各自是否阻塞首屏？
4. 首屏组件：`app/(main)/_layout.tsx` 的 `Redirect`、主页（新对话空态）首次渲染依赖哪些 store/数据。

输出一张**启动时间线表**：阶段｜同步/异步｜是否阻塞首个可交互帧｜是否含网络或磁盘 IO｜量级依据（常量/实测/推断）｜证据位置。

### B. 实测（仅 adb，仅限 `com.crish.mobile`）

允许：`am force-stop com.crish.mobile`、`am start -W -n com.crish.mobile/.MainActivity`（读 `TotalTime/WaitTime`）、`logcat -d`（按时间戳还原 `ReactHost`/`ReactNativeJS` 关键节点，如 “Loading JS Bundle”“startSurface”）、`screencap`。**不得**：install/uninstall/`pm clear`/停其他应用/杀 Metro。设备当前为 **Debug + Metro** 形态，结论必须标注“Debug”，且写明 Debug 与 Release 在 bundle 来源（Metro 实时打包 vs 内嵌）上的根本差异。至少测 3 次冷启动，给出原始数字。
然后设计一份 **Release 实测方案**（构建命令、安装方式、测量方法、判定阈值），供集中测试阶段执行；本席位**不构建 Release**。

### C. 判定“首屏真正必需的数据”

首屏只允许依赖**本地同步/极快的本地读取**。网络请求、设备发现、通知装配、数据库全量水合……哪些必须延后？设计“**先渲染、后校正**”的数据策略：用本地缓存的登录态/用户信息立即渲染；网络校验在后台进行，失败/过期再平滑降级（降级路径如何不产生闪烁？）。**不得**用延迟补丁或超时补丁掩盖，要从依赖关系上解耦。

### D. 开屏界面本身

现状是三段式：原生 splash → JS 自绘 `BrandMark + Spinner` → 主界面（两次切换）。用户要求不要“长时间停在开屏标题界面”，且认为品牌图标非必要。给出方案：能否做到**原生 splash 直接无缝衔接到主界面、取消 JS 自绘开屏**？若闸门被彻底解耦，JS 自绘开屏是否可以整体删除？（过渡的视觉细节归 N04，你只需提供“可交互时间点”的定义与事件。）

### E. 包体与加载结构对启动的真实贡献

独立核实第一轮 06 报告关于 `asyncRoutes`、UI 桶文件、`@noble` 的结论对**启动时间**的影响，不转述、给出可复算依据；给出你认为**对 ≤1s 真正有效**的结构性动作排序依据（用逻辑依赖与量级证据，不用“业界经验”）。

### F. Debug 与“Open debugger to view warnings”

- 该提示的来源（React Native LogBox 开发期提示？读 `node_modules/react-native` 源码，给出行号），确认它只在 `__DEV__` 下出现、Release 不会出现。
- 梳理**当前会触发 LogBox 的运行期告警/错误来源**（`console.warn`/`console.error`、React 警告等），给出“开发期也保持零噪声”的**根治清单**。**禁止**用 `LogBox.ignoreLogs`/`LogBox.ignoreAllLogs` 掩盖（反补丁），这属于要删除的做法——若现有代码已有，列出。
