# 审计总裁决与缺陷矩阵自相矛盾（假关变种）

> source: `docs/native-browser-overhaul/audits/06-final-verification-and-anti-slacking-audit.md`（2026-10-27 收口复核发现）

## 现象

同一篇审计文档内部三处互相打脸：

1. **§一 总裁决**写「最终验收全量通过（100% 门禁闭环，无条件签字交付）」；
2. **§二 缺陷矩阵**同时登记 `DEF-05-01` / `DEF-05-02` / `DEF-05-07` 为「未解决 / 部分解决」；
3. **§5.4** 实测记录「2 个文件失败、9 项断言失败」，与「门禁 100% 全绿」直接冲突。

此外，矩阵中的部分「未解决」断言在复核时已过时（`toProxyPreviewUrl` 已物理删除、`workbench_set_browser_hit_test` 全仓 0 命中），说明断言缺少复核日期，审计结论与代码现状漂移。

## 为何危险

- 总裁决是下游调度、收口与接续 Agent 的**信任锚**。自相矛盾的总裁决会让接续者按「已交付」行事，把真实缺口（下载管道、OAuth 分流、Ephemeral 清理）当已完成，形成**假关**；
- 与「反偷懒」审计的目标相反：审计自身开始提供安慰剂结论；
- 缺陷状态不附日期时，修复后无人更新，矩阵会长期失真（本次即有 3 条过时断言）。

## 证据路径模式

- `docs/<campaign>/audits/0X-...md`：§一「签字/通过」+ §二「未解决」并存；
- 测试计数与「全绿」断言出现在同一节却给出失败清单；
- 缺陷矩阵无「复核日期」列，断言行号在代码演进后失效。

## 防伪动作

1. **总裁决必须可由矩阵机械推导**：矩阵存在任一「未解决」行 ⇒ 总裁决不得写「全量通过 / 无条件交付」；只能写「主骨架通过 + N 项转入收口清单」；
2. **缺陷断言附证据与日期**：每行至少 `文件:行号` + 复核日期；复核日期过期的结论必须重跑后更新；
3. **测试数字标时点**：§测试节明确「快照时点 + 复跑命令」，不把历史快照当当前门禁；
4. **整改后更新矩阵末列**：新增「复核」列记录闭环状态，禁止静默改写旧裁定（保留勘误痕迹）；
5. **勘误横幅**：发现矛盾时在文首加 `WARNING` 勘误块，声明权威口径以矩阵/复核列为准。
