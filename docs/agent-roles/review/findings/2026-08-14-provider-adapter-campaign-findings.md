## 毒点 1 · 并行 in-flight 编译波动：多 Agent 同 crate 并行改造时整包编译/测试被中间态周期性阻塞

- **现象**：多 Agent 同 crate 并行改造时，整包编译/测试周期性被其他 Agent 的中间态阻塞（本战役多次发生，均自愈、无跨域代修）。证据：
  - R1：`catalog_tests.rs` 由 T1.1/T1.5 并行写入（最终合并共存全绿）；运行期多次出现其他 Agent in-flight 编译阻塞。
  - R2 小结「三·4 并行波动」：R2 运行期多次出现其他 Agent in-flight 编译/用例波动（自愈）；各 Agent 文件域在绿窗口内独立验证，最终全量 631 绿。
  - R3 小结「三·4 并行战役中间态」：其他 Agent 移除 `BlockId::parse`（conex-note-runtime 编译失败）、in-flight 改 `budget_compaction.rs`——观察自愈，未干预。
  - R4 小结「三·3 并行波动」：A1 in-flight 期间多 Agent 编译波动（自愈）。
  - R5 小结「三·3 / 五」：全量 `cargo test --workspace` 在**收敛窗口绿**（并行战役 in-flight 波动排除）才判过。
- **处置先例**：派单时同文件域**合并或串行**——R1 的 `config.rs` 三单例（T1.2-4）由主控合并为 1 Agent 一体改造（零并发冲突）；R3 `engine_provider.rs` 三写（T3.2/T3.3/T3.5）一体改造 + 拆子模块（848→400 行）。验证用**绿窗口策略**：文件域独立验证 + 等并行收敛后做全量核验。
- **建议（未来战役）**：派单前识别同文件域，能合并/串行就不并行；Agent 自身验证在**自己文件域的绿窗口**内独立跑，全量整包核验（`cargo test --workspace` / `cargo check --workspace`）放到**并行收敛后的稳定窗口**，把其他 Agent 的 in-flight 波动当作预期噪声记录而非干预。

## 毒点 2 · hook 全局 `diff --check` 阻塞：并行战役的 EOF 空行/trailing whitespace 持续阻塞提交

- **现象**：`.husky/pre-commit` 的 `git diff --check` 检查**整个工作区**（含并行 Agent 未提交文件），他人文件的 EOF 空行/trailing whitespace 会阻塞所有 Agent 的提交（AGENTS.md §3.5；本战役 R1-R5 多轮提交门槛沿用此纪律）。
- **处置先例**：发现时对该行做**最小 whitespace 修复**解除阻塞（不碰内容），或上报主控协调；禁止 `--no-verify` 绕过（AGENTS.md §7 明确禁止）。
- **建议（未来战役）**：提交前先批量做最小修复——EOF 空行去尾、行尾空白剔除，**循环修复直到 `git diff --check` 干净立即提交**；不要把 whitespace 修复与内容改动混在一个 commit 里；钩子阻塞优先最小修复而非等主控。

## 毒点 3 · 契约登记与跨轮消费：C1-C25 先登记后消费机制有效

- **现象**：R1-R5 的 C1-C25 契约登记机制有效——跨轮数据结构变更（数据载体/类型/语义）**先登记 JSON 形状 + 兼容规则，后消费**，只追加不删改语义。证据：
  - R1 契约 C1-C5（档位载体/多提供方配置/模型替换/协议路由/compat 纯函数）→ R2/R3/R5 消费。
  - R2 契约 C6-C10（三协议 builder/序列化 wire/描述面/usage 缺口）→ R3/R4 消费。
  - R4 契约 C17-C20 + A6 mode 数据补录 → R5 消费；R5 契约 C21-C25 → R6 收尾消费。
- **处置先例**：每轮小结 §二 契约登记（含 JSON 形状、兼容解析规则、`#[serde(default)]` 兜底）；`00-总方案.md` §六「契约漂移」：派单前核对上一轮契约登记与实际代码，漂移→回退重派，演进→走变更顺序纪律。
- **建议（未来战役）**：任何跨轮数据结构变更都必须登记 JSON 形状与兼容规则（缺省/兜底/旧形状兼容）；**消费轮派单前核对契约登记与实际代码**，把「先登记后消费」作为跨轮派单的固定输入门槛。

## 毒点 4 · 行为变更随行为变更：行为变更时须同步更新断言（禁删测试）

- **现象**：行为变更（usage 归一、mode 数据补录）引发既有断言更新，属预期而非失败。证据：
  - R3 C14 usage 归一化（anthropic reasoning + gemini cache-write + cache_breakdown 派生）→ 两端 e2e usage 断言更新。
  - R4 小结「四」净变化含「部分既有断言随行为变更更新——行为变更随行为变更，禁删测试纪律保持」。
  - R5 断链 B-2：wire_integration stale 断言红（A6 mode 补录引发）→ 同步更新断言（claude→Anthropic / gemini→Gemini），13/13 绿。
- **处置先例**：行为变更时同步更新受影响断言并**禁删测试**；在轮次小结 §一完成项 + §四基线变化登记断言变更。
- **建议（未来战役）**：当数据/行为契约变化导致断言红时，先判断是行为变更还是回归——行为变更就**更新断言而非删测试**，并在小结登记「断言随行为变更更新」，避免下轮误判为回归失败。

## 毒点 5 · 吞并处理：并行定时 git Agent 可能扫走未提交改动

- **现象**：仓库内有自动化定时 git Agent 会扫描并提交未提交代码；可能把子 Agent 的工作区改动「吞并」进他人提交。
- **处置先例**：R5 小结「四·2 T5.2a 吞并」——其 3 个测试被并行 git 定时 Agent 扫入 `3819df61`，**已核对工作区与 HEAD 一致（`git show HEAD:<path>` 对比）**，内容完整则**不管归属、不回退重做**（AGENTS.md §3.4）。
- **建议（未来战役）**：提交前先 `git status` 核对目标文件未被并行 Agent 正在修改（AGENTS.md §3.1）；发现被吞并时**只验证内容完整性**（`git show HEAD:<path>` 对比），完整则接受、缺失则用 `git commit --only` 追加；**禁止回撤**（无 `reset --hard` / `checkout .` / `restore`）。

## 毒点 6 · 主控裁量合并派单：同文件多单元合并为单 Agent 一体改造（优于并行冲突与串行等待）

- **现象**：多轮出现同文件被多个任务单元共写，若并行会冲突、若纯串行会拉长轮次。
- **处置先例**：由主控裁量合并为单 Agent 一体改造，本战役 4 次实证成功：
  - R1 T1.2-4 三单例（config.rs）合并（小结「三·2」：零并发冲突）。
  - R3 T3.2/T3.3/T3.5 同写 engine_provider.rs，一体改造 + 拆 6 子模块（848→400 行）。
  - R4 A1：vendor 一体改造（T4.1 拒绝 + T4.2 改名 + T4.4 头 + T4.5 方言，vendor.rs 397 行拆 reject.rs/dialect.rs）。
  - R2 messages.rs 由 T2.2/T2.3 双写（标注同 Agent 顺序或串行）；R3 方案 M7 / R4 方案 M7 均以「拆函数面或同 Agent 顺序」处理共写文件。
- **建议（未来战役）**：方案评审时识别同文件共写风险（评审 M7 类），主控派单优先合并为单 Agent 一体改造；确实需要并行的，按函数面拆分并**标注串行顺序**，避免并行写冲突与纯串行等待拉长轮次。
