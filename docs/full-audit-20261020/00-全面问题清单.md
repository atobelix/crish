### SEC-03 全仓依赖审计 74 漏洞（生产依赖 43），CI 只审计 6 个桌面工作区

- **严重度**：中-高
- **证据**：
  - `npm audit`（含 dev）：**74**（18 moderate / 54 high / 2 critical）。
  - `npm audit --omit=dev`：**43**（16 moderate / 27 high / 0 critical），集中在移动端 `expo` / `@expo/*` / `metro` / `react-native` / `node-forge` / `micromatch` / `braces` 等。

### SEC-04 CI 依赖安装使用 `npm ci || npm install` 回退

- **严重度**：低-中
- **证据**：`ci.yml`、`ci-mid.yml`、`ci-slow.yml`、`release.yml` 的所有安装步骤均为 `npm install -g npm@11.6.2 && (npm ci || npm install)`。
- **影响**：lockfile 与 package.json 不一致时，CI 会静默改成 `npm install` 并可能改写依赖树，导致「本地/CI/发布」三者不一致，破坏可复现性。
- **修复**：CI 一律 `npm ci`；若失败就让 job 红，暴露 lock 漂移；只在本地开发脚本保留回退。

### SEC-05 GitHub Actions 引用未钉 SHA

- **严重度**：低
- **证据**：workflow 使用 `actions/checkout@v4`、`actions/setup-node@v4`、`actions-rust-lang/setup-rust-toolchain@v1`、`tauri-apps/tauri-action@v0` 等可变 tag。
- **影响**：上游 tag 被移动/仓库被攻破时，CI 会执行非预期代码；供应链风险。
- **修复**：对第三方 action 使用 commit SHA 固定；Dependabot/Renovate 定期升级。

### SEC-06 发布 workflow 手动触发时硬编码 `v0.1.0`

- **严重度**：中（发布流程错误）
- **证据**：`.github/workflows/release.yml` 中：
  ```yaml
  tagName: ${{ startsWith(github.ref, 'refs/tags/') && github.ref_name || 'v0.1.0' }}
  releaseName: "Crish ${{ startsWith(github.ref, 'refs/tags/') && github.ref_name || 'v0.1.0' }}"
  ```
  手动 `workflow_dispatch` 时没有 tag，会固定创建/覆盖 `v0.1.0` 的 draft release。
- **影响**：手动补发/重跑可能把新产物挂到旧版本号，或与已有 `v0.1.0` 冲突；版本追溯失真。
- **修复**：手动触发必须要求输入 `version`/`tag`，并校验 `tauri.conf.json` 的 version 与 tag 一致；禁止默认回退到固定版本。

### SEC-07 release 产物校验和覆盖范围靠目录猜测

- **严重度**：低
- **证据**：`.github/workflows/release.yml` 的 checksum 步骤遍历三个可能的 bundle 目录（`target/release/bundle`、`apps/agent-workbench/src-tauri/target/release/bundle`、`apps/agent-workbench/target/release/bundle`），找不到就静默跳过。
- **影响**：如果 Tauri 输出路径变化，checksum 步骤不会报错，只是少传文件；用户可能拿到没有校验和的产物。
- **修复**：从 `tauri-action` 的输出/固定路径读取实际产物；找不到任何产物时让 job 失败。
