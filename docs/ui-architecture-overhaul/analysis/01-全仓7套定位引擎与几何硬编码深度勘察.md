## 一、勘察背景与核心危害总结

在 `apps/crish-desktop` 中，浮层组件（包括普通菜单、级联子菜单、下拉选择器、组合输入框、智能面板、会话右键菜单、排序下拉、气泡提示等）历经多次局部修补与版本迭代，逐渐分化出了 **7 套各自为政、互不相通的坐标解算与几何布局逻辑**。

这些手写引擎在实现上存在以下四大系统性结构缺陷：

1. **魔术数字与粗暴预估满天飞**：在真实 DOM 尚未挂载或布局未稳定时，大量采用 `offsetWidth || 240`、`offsetHeight || 200`、`itemCount * 28 + 20`、`maxLen * 13 + 24` 等基于猜测的硬编码常量，不仅破坏了高 DPI 和多语言排版，更直接引发了首帧误判；
2. **强制同步回流（Forced Synchronous Layout / Layout Thrashing）**：部分引擎为了探测所谓的“自然高度”，竟在计算过程中直接修改 DOM 内联样式（如 `listEl.style.maxHeight = 'none'` 并读取 `scrollHeight` 后再恢复），在滚动或指针移动时引发灾难级的性能卡顿；
3. **坐标翻折与尺寸约束缺乏联动（缺少 `--available-height`）**：在视口高度不足或贴近屏幕边缘时，所有引擎仅机械地在翻折与钳位间做二值抉择，没有任何一套引擎会向宿主样式注入动态的 `--available-height`，导致菜单虽然翻折成功，但下边缘仍然被直接截断或冲出视口；
4. **两阶段渲染与状态机振荡**：多套 Hook 将解算出的坐标存储在 React State 中（如 `setPosition({ x, y })` 或 `setFlipLeft(true)`），导致元素必须先在屏幕上按默认方向“闪烁”一帧，再触发 `useLayoutEffect` 进行二次修正，造成肉眼可见的残影跳跃（Flicker）与二次翻转（Double Flip）。

### 2.1 引擎一：`apps/crish-desktop/src/components/ui/Menu/position.ts`

#### 2.1.1 核心职责与使用场景
该文件定位为“菜单/浮层坐标计算单源纯函数引擎”，主要服务于：
- `ui/Menu` 的基础浮层坐标钳位；
- `components/settings-models/ModelsCascadeSelect.tsx` 的二级模型级联子菜单（`calculateSubmenuPosition`）；
- `components/sidebar/SidebarContextMenus.tsx` 的旧版会话操作菜单坐标计算。

#### 2.1.2 行号级代码硬编码与魔术值清单

| 代码行号 | 源码片段 / 表达式 | 违规性质与具体隐患 |
| :--- | :--- | :--- |
| **Line 12** | `export const MENU_EDGE_PAD = 8;` | 视口边界硬编码留白 8px，缺乏与容器 Boundary 的动态适配。 |
| **Line 14-15** | `export const MENU_EST_WIDTH = 160; export const MENU_EST_HEIGHT = 280;` | 严重硬编码！脱水环境或首帧渲染前盲猜菜单尺寸为 160×280px。若实际菜单超过 300px，必然引发首帧误判。 |
| **Line 96-97, 109-110, 117, 122** | `rawW > 0 ? rawW : 1280; rawH > 0 ? rawH : 800;` | 视口回退硬编码为 1280×800，在小窗口或无头测试环境下造成虚假坐标。 |
| **Line 126-132** | `width: Math.max(320, rawW - 16), height: Math.max(200, rawH - 16), offsetLeft: 8, offsetTop: 8;` | 针对 Win32 最大化窗口手写的“8px 补丁补偿”。硬编码扣除 16px，导致非 Windows 平台或特定缩放比例下坐标偏移。 |
| **Line 310-316** | `const width = measuredWidth > 0 ? measuredWidth : MENU_EST_WIDTH; const height = measuredHeight > 0 ? measuredHeight : MENU_EST_HEIGHT;` | `measureAndCalculateMenuPosition` 测量失败时直接回退到 160×280px。 |
| **Line 381-385** | `submenuWidth = 190, submenuHeight = 280, sideOffset = 4, edgePadding = 8` | `calculateSubmenuPosition` 级联子菜单硬编码默认宽高 190×280px。 |
| **Line 423** | `const targetY = rowRect.top - 4;` | 触发行与子菜单的对齐通过魔术数字 `-4px` 进行人工补偿。 |

#### 2.1.3 几何算法与致命设计缺陷
1. **下溢出截断无动态高度**：在 `calculateMenuPosition`（Lines 179-225）中，当空间不足以容纳 `menuHeight` 且顶部空间比底部大时翻折到上方。但若当前视口的总高度本身就小于 `menuHeight`（如小屏或菜单条目很多时），垂直钳位 `clampedY`（Line 219）虽然将顶部强行钳制在 `offsetTop + edgePadding`，但由于没有动态计算并设置 `--available-height`，菜单底部直接冲出视口，最后几项操作不可见且无法滚动。
2. **瞬态形变测量漏洞**：虽然注释宣称“采用 offsetWidth/offsetHeight 测量真实尺寸，免疫 CSS scale(0.96) 形变”，但在 Line 311 中写道：
   ```ts
   const measuredWidth = el.offsetWidth > 0 ? el.offsetWidth : el.getBoundingClientRect().width;
   ```
   当浮层尚未完成物理绘制（如从 `display: none` 刚切出或在微任务阶段）时，`offsetWidth` 为 0，依然回退到了受 scale 影响的 `getBoundingClientRect()`，使预估几何完全失真。

| `positionGeometry.ts:60-61` | `triggerRect.top + triggerRect.height / 2 - selectedItemOffsetY : triggerRect.top - 4` | 原位对齐失败时魔术补偿 `-4px`。 |
| `useFloatingPosition.ts:72-80` | `useState<FloatingPositionResult>({ x: 0, y: 0, ... isPositioned: false })` | React 状态解法，首帧必然为 (0,0) 并导致二次渲染跳跃。 |

#### 2.2.3 几何算法与致命设计缺陷
1. **ResizeObserver 单向监听断裂**：
   在 `useFloatingPosition.ts` 的 Lines 201-206 中：
   ```ts
   const triggerEl = triggerRef.current;
   if (triggerEl) {
     roManager.observe(triggerEl, handleRo);
   }
   ```
   **该引擎只观察了 `triggerEl` 的尺寸变化，完全没有观察 `contentEl`！** 当 `Combobox` 键入关键词进行实时过滤时，下拉菜单的项数急剧减少或异步加载出新选项，`contentEl` 的物理高度发生了巨大变化，但定位引擎完全感知不到，依然维持初次打开时的坐标和翻折决策，导致悬空或溢出。
2. **遮盖触发器的粗暴 Clamp**：
   在 `positionGeometry.ts` 的 Lines 83-96 中，若 `side === 'bottom'` 且底部放不下，只有当 `spaceAbove > spaceBelow` 时才翻转到 `top`。若当前触发器处于屏幕偏下方（例如 45% 高度处），且菜单内容非常长（例如 60% 高度），则 `spaceBelow` 略大于 `spaceAbove`，算法强制判定留在 `bottom`；随后 Lines 111-112 的 Clamp 逻辑：
   ```ts
   const maxY = Math.max(minY, offsetTop + vp.height - popupHeight - edgePadding);
   const clampedY = Math.min(Math.max(minY, targetY), maxY);
   ```
   将 `clampedY` 向上拉回以贴紧视口底部，导致**整个下拉浮层直接覆盖在刚点击的触发器按钮正上方**，阻挡了用户的视线与再次点击！

#### 2.3.3 几何算法与致命设计缺陷
1. **尺寸预测与实际渲染的巨大鸿沟（Double Flip 的重灾区）**：
   当 `itemCount > 2` 时（例如 10 个操作项的右键菜单），初次渲染 `panelEl.offsetHeight` 为 0，代码估算高度为 `200px`。而 10 项菜单加分隔线的实际高度约为 `360px`。当用户在屏幕底部上方 260px 处右键点击时，引擎计算 `spaceBelow = 260px > 200px`，从而自信地选择向下弹出；下一帧挂载完成真实高度变为 360px，溢出视口，引擎又被迫翻转到上方，产生典型的二次翻转。
2. **双向迟滞（Hysteresis）导致的截断死锁**：
   Lines 120-125 试图通过 `hysteresisY = 32` 来抑制方向抖动：
   ```ts
   if (currentDirYRef.current && currentDirYRef.current !== idealDirY) {
     const currentSpace = currentDirYRef.current === 'down' ? spaceBelow : spaceAbove;
     const idealSpace = idealDirY === 'down' ? spaceBelow : spaceAbove;
     preferredDirY = idealSpace - currentSpace > hysteresisY ? idealDirY : currentDirYRef.current;
   }
   ```
   这一打补丁式的迟滞逻辑引入了严重的逻辑死锁：如果真实渲染后需要向上翻转，但 `idealSpace - currentSpace` 恰好小于等于 32px，**迟滞逻辑将强行拒绝翻转**，维持向下的错误方向，导致菜单底部被视口边缘生生斩断，关键操作项无法点击。
3. **JS 与 CSS 样式循环依赖（振荡隐患）**：
   引擎计算出 `allowedListHeight` 并传递给组件内联样式 `maxHeight`。这改变了 `panelEl` 的物理高度，导致下一次布局循环中 `panelEl.offsetHeight` 变小；而变小后的高度反过来影响了下一次 `useLayoutEffect` 中对 `availableSpace` 的判定，形成了 **“高度变小 → 认为放得下 → 高度变大 → 空间不足 → 高度变小”** 的死循环。

#### 2.4.3 几何算法与致命设计缺陷
1. **毁灭性能的强制布局抖动（Layout Thrashing）**：
   在 `measureNaturalHeight`（Lines 57-66）中：
   ```ts
   const prevMaxHeight = listEl.style.maxHeight;
   const prevOverflow = listEl.style.overflow;
   listEl.style.maxHeight = 'none';
   listEl.style.overflow = 'visible';
   const listScrollHeight = listEl.scrollHeight;
   listEl.style.maxHeight = prevMaxHeight;
   listEl.style.overflow = prevOverflow;
   ```
   为了计算未限制高度时的列表物理尺寸，在一次调用中进行了 **两次 DOM 写操作（Write）和一次 DOM 读操作（Read）**。这直接破坏了浏览器的异步渲染批处理队列，引发强制重排。如果在鼠标移动或高频滚动时触发定位计算，页面会发生剧烈掉帧。
2. **级联子菜单的粗暴估算与错位**：
   `placeCascadeSubmenu`（Lines 321-368）采用预估字长算宽（`maxLen * 13`）与预估项高算高（`divider ? 9 : 36`），由于真实渲染字体受系统抗锯齿、字体族、DPI 缩放影响，实际渲染后的尺寸必定与估算值存在 10~50px 偏差，导致子菜单在弹出时紧贴边缘或出现非预期的白边和向内穿模。

## 三、四大经典真实 Bug 的几何数学根因深度剖析

### 3.1 Double Flip（二次翻转）的几何数学机理与时序阶跃

“二次翻转”是浮层定位中最恶劣的交互体验问题。其本质原因在于：**决策前置于测量，且初次决策使用了严重失真的静态估计值。**

```
时间轴时序分解：
t0 [触发点击]  ──> 捕获坐标 (x, y) ──> 挂载浮层组件（DOM 未就绪，offsetHeight = 0）
t1 [首轮计算]  ──> 读取真实高度失败 ──> 触发回退估算 (H_est = 200px)
t2 [方向决策]  ──> 计算下方空间 (S_below = 250px) ──> 判断 S_below >= H_est (250 >= 200 为真)
                  ──> 决策：向下展开 (direction = 'down', top = y)
t3 [物理排版]  ──> 浏览器完成 11 个菜单项排版，实际高度确立 (H_real = 384px)
                  ──> 屏幕底部被击穿，超出视口 134px！
t4 [二次修正]  ──> useLayoutEffect 捕获 H_real = 384px ──> 重新判定 S_below < H_real (250 < 384)
                  ──> 且上方空间 S_above = 550px > S_below
                  ──> 决策颠覆：向上翻转 (direction = 'up', top = y - 384)
                  ──> 页面产生剧烈的视觉跳跃（Double Flip 完成）
```

#### 数学不等式断层分析：
设触发点坐标为 $Y_{click}$，视口有效高度为 $H_{vp}$，边缘安全留白为 $P_{edge}$。
下方可用空间为：
$$S_{below} = H_{vp} - Y_{click} - P_{edge}$$

当且仅当满足下列区间条件时，必然稳定复现 Double Flip：
$$H_{est} \le S_{below} < H_{real}$$

在项目中，$H_{est} = 200\text{px}$，而 $H_{real} \approx 384\text{px}$。这意味着在屏幕底部 **$200\text{px} \sim 384\text{px}$ 的整整 184 像素危险区间内**，任何点击都会百分之百触发二次翻转！

---

### 3.2 小屏/贴边视口溢出（Viewport Overflow）与 `--available-height` 缺失

无论在 `Menu/position.ts` 还是 `useFloatingPosition.ts` 中，现有的边界约束均采用简单的双向钳位（Clamp）：
$$Y_{clamped} = \max(Y_{min}, \min(Y_{target}, Y_{max}))$$
其中：
$$Y_{max} = H_{vp} - H_{menu} - P_{edge}$$

#### 致命数学破缺：
如果 $H_{menu} > (H_{vp} - 2 \cdot P_{edge})$（即菜单本身的高度已经超过了整个可用视口高度，常见于笔记本小屏幕、分屏工作区或拥有数十个选项的下拉框），则：
$$Y_{max} < Y_{min}$$
此时 $\min(Y_{target}, Y_{max})$ 会计算出一个小于 $Y_{min}$ 的值，随后的 $\max(Y_{min}, \dots)$ 强制将坐标锁死在 $Y_{min}$（即屏幕顶部）。

此时的屏幕底部坐标为：
$$Y_{bottom} = Y_{min} + H_{menu} = P_{edge} + H_{menu} > H_{vp} - P_{edge}$$
**多出的内容直接越过屏幕底边！**

#### 根因：
现有引擎全部**缺少“几何尺寸自适应裁剪（Size Constraint Middleware）”**。在工业级方案中，Positioner 绝不仅是计算 `left/top`，而是必须同时解算出当前方向的理论最大可用空间：
$$\text{AvailableHeight} = \begin{cases} 
H_{vp} - Y_{trigger.bottom} - P_{edge} - \text{sideOffset}, & \text{side} = \text{'bottom'} \\ 
Y_{trigger.top} - P_{edge} - \text{sideOffset}, & \text{side} = \text{'top'} 
\end{cases}$$
并将此值以 CSS 变量 `--available-height` 注入容器，配合容器的 `max-height: var(--available-height); overflow-y: auto;` 实现原生滚动。全仓 7 套引擎均未闭环这一链路。

---

### 3.3 弹出菜单抖动与高度回环震荡（Flip-Flop Oscillation）

在 `SmartPanel` 的 `usePanelPosition.ts`（Line 152）中，开发者为了解决小屏溢出，编写了如下逻辑：
```ts
if (estimatedHeight > availableSpace) {
  allowedListHeight = Math.max(80, availableSpace - 40);
}
```
并在 `SmartPanel.tsx`（Line 218）中将 `allowedListHeight` 赋予列表的 `maxHeight`。

#### 震荡回环数学模型：
1. **状态 A（未受限）**：
   - 列表未设置限高，面板物理高度 $H_1 = 400\text{px}$；
   - 空间 $S = 300\text{px}$，判定 $H_1 > S$，触发限制；
   - 计算限高 $H_{allow} = 300 - 40 = 260\text{px}$，通过 React State 触发更新。
2. **状态 B（被限高）**：
   - 列表应用 `maxHeight: 260px`，面板整体高度缩水至 $H_2 = 300\text{px}$；
   - 下一轮渲染测量到 $H_2 = 300\text{px}$，判定 $H_2 \le S$（不再大于可用空间）；
   - 代码执行 `allowedListHeight = null`，取消限高，通过 React State 触发更新。
3. **状态循环**：
   - 取消限高后，面板高度瞬间弹回 $H_1 = 400\text{px}$，再次触发状态 A。
   - 系统在状态 A 与状态 B 之间以每个渲染帧 60Hz~120Hz 的频率疯狂振荡，造成视觉上的高频猛烈抽搐（Shaking/Jitter）。

---

### 3.4 CSS 进场动画（Scale/Translate）对 DOMRect 测量的污染与基准错位

现代 UI 规范普遍要求浮层进场具有微弱的缩放动效（如 `transform: scale(0.96) → scale(1)`）或透明度过渡。

#### 测量污染几何机理：
浏览器的 `Element.getBoundingClientRect()` 返回的是经过当前渲染树上**所有 CSS 矩阵变换（Matrix Transform）计算后的物理视口矩形**。
若浮层初始挂载时处于动画第一帧（`transform: scale(0.96)`）：
$$W_{measured} = W_{real} \times 0.96$$
$$H_{measured} = H_{real} \times 0.96$$

若浮层真实宽度为 300px，则测量读数为 288px。
如果定位引擎根据 288px 进行边界贴靠计算：
$$X_{target} = \text{ViewportWidth} - 288\text{px} - 8\text{px}$$
在第 150ms 进场动画执行完毕后，`scale` 恢复到 1.0，浮层宽度向右扩展回 300px：
$$X_{right\_edge} = X_{target} + 300\text{px} = \text{ViewportWidth} - 288 - 8 + 300 = \text{ViewportWidth} + 4\text{px}$$
**浮层右侧边缘直接穿透视口右边界 4px，破坏视口边界不变式！**

## 四、工业级标杆设计对比分析（Radix UI vs Base UI / Appica UI）

### 4.1 Radix UI（`@radix-ui/react-popper`）中间件流水线与解耦机制

Radix UI 的核心理念是：**将几何运算抽象为完全纯粹的无状态流水线，将动画层与坐标层物理隔离。**

```
Radix 架构分层：
┌────────────────────────────────────────────────────────┐
│ <Popper.Root>                                          │
│   ├── <Popper.Anchor> (支持物理 DOM 或虚拟点 VirtualPoint) │
│   └── <Popper.Content>                                 │
│         ├── [Positioner Wrapper] (设置 absolute, left, top)│
│         │     └── 注入 CSS 变量:                        │
│         │           --radix-popper-transform-origin    │
│         │           --radix-popper-available-width     │
│         │           --radix-popper-available-height    │
│         └── [Visual Popup] (承载 Scale/Opacity 进场动画) │
└────────────────────────────────────────────────────────┘
```

#### Radix 核心中间件管线（Ordered Middleware Pipeline）：
1. **`offset`**：在初始方位轴上施加 `sideOffset` 与 `alignOffset`；
2. **`flip`**：按照优先级列表依次检验候选方位，以“完全不产生遮挡”为判定标准；
3. **`shift`**：沿交叉轴执行弹性滑动（Sliding），保证浮层完全约束在视口安全边距内；
4. **`size`**：解算最终剩余空间，写入 CSS 自定义变量，直接交由 CSS 处理滚动；
5. **`arrow`**：独立解算小三角的相对对齐偏移量，绝不反向干扰主容器坐标。

### 4.2 Base UI / Appica UI 的 `Portal → Positioner → Popup` 三元架构

     ```css

     overflow-y: auto;
     ```
   - **坐标归坐标，动画归动画，两者在 DOM 树上分为外层与内层，测量时只测未形变的外层骨架，彻底杜绝 scale 污染！**

## 五、统一轻量自研 Positioner 几何数学模型与技术规范

为收敛全仓 7 套引擎，建立全新的统一定位体系，提炼如下完整的几何数学模型规范。

### 5.1 统一输入模型（Input Schema）

```typescript
/** 物理锚点支持类型：真实 DOM 节点、Ref 引用、虚拟点或矩形 */
export type AnchorElement =
  | HTMLElement
  | React.RefObject<HTMLElement | null>
  | { x: number; y: number } // 虚拟光标点
  | DOMRect; // 自定义物理包围盒

export type FloatingSide = 'top' | 'bottom' | 'left' | 'right';
export type FloatingAlign = 'start' | 'center' | 'end';

export interface PositionerOptions {
  anchor: AnchorElement;
  side?: FloatingSide;               // 默认 'bottom'
  sideOffset?: number;               // 默认 6px
  align?: FloatingAlign;             // 默认 'start'
  alignOffset?: number;              // 默认 0px
  avoidCollisions?: boolean;         // 默认 true
  collisionBoundary?: HTMLElement | 'viewport'; // 默认 'viewport'
  collisionPadding?: number;         // 默认 8px
  sticky?: 'partial' | 'always';     // 默认 'partial'
  arrowPadding?: number;             // 默认 12px
}
```

### 5.2 六阶段几何解算流水线（Six-Stage Geometry Pipeline）

整个定位解算过程必须严格遵循纯函数管道，**禁止产生任何 DOM 写副作用**：

```
[ Stage 1: 视口与边界提取 ]
        │
        ▼
[ Stage 2: 锚点与浮层尺寸提取 (Bounding Resolution) ]
        │
        ▼
[ Stage 3: 主轴放置决策与碰撞翻转 (Flip Checking) ]
        │
        ▼
[ Stage 4: 交叉轴对齐与视口滑动钳位 (Shift & Clamp) ]
        │
        ▼
[ Stage 5: 动态最大可用空间提取 (Available Size Calculation) ]
        │
        ▼
[ Stage 6: 变换原点与箭头偏移动态标定 (Origin & Arrow Calibration) ]
```

#### 阶段 1：视口与安全边界提取（Viewport & Boundary Extraction）
- 支持提取 Windows 平台最大化窗口下的 8px 溢出安全补偿：
  $$\text{Bounds} = \begin{cases}
  [8, 8, W_{vp} - 8, H_{vp} - 8], & \text{Win32 Maximized} \\
  [P_{pad}, P_{pad}, W_{vp} - P_{pad}, H_{vp} - P_{pad}], & \text{Normal}
  \end{cases}$$

#### 阶段 2：锚点规范化矩形转换（Anchor Rect Normalization）
- 虚拟点 `{ x, y }` 转为长宽为 0 的退化矩形：`DOMRect(x, y, 0, 0)`；
- 真实 DOM 节点通过 `getBoundingClientRect()` 提取，过滤脱水或非法矩形。

#### 阶段 3：主轴翻折算法（Collision Flip Invariant）
以 `side = 'bottom'` 为例：
1. 评估下方空间：$S_{below} = \text{Bounds.bottom} - \text{Anchor.bottom} - \text{sideOffset}$；
2. 评估上方空间：$S_{above} = \text{Anchor.top} - \text{Bounds.top} - \text{sideOffset}$；
3. 翻转判定律：
   $$\text{FinalSide} = \begin{cases}
   \text{'top'}, & S_{below} < H_{floating} \land S_{above} > S_{below} \\
   \text{'bottom'}, & \text{otherwise}
   \end{cases}$$
4. **彻底杜绝 Double Flip**：此时 $H_{floating}$ 必须来自浮层挂载时由 `Positioner` 捕获的真实物理尺寸，若初次不可测，则保持浮层为 invisible，**绝不使用 200px 等魔术值提前向错误方向渲染**。

#### 阶段 4：交叉轴对齐与滑动（Shift & Clamp）
以垂直方向布局为例，计算水平 X 轴位置：
1. 初试对齐位置：
   $$X_{target} = \begin{cases}
   \text{Anchor.left} + \text{alignOffset}, & \text{align} = \text{'start'} \\
   \text{Anchor.left} + (\text{Anchor.width} - W_{floating}) / 2 + \text{alignOffset}, & \text{align} = \text{'center'} \\
   \text{Anchor.right} - W_{floating} - \text{alignOffset}, & \text{align} = \text{'end'}
   \end{cases}$$
2. 滑动钳位（Shift）：
   $$X_{final} = \max(\text{Bounds.left}, \min(X_{target}, \text{Bounds.right} - W_{floating}))$$

#### 阶段 5：动态可用尺寸提取（Available Size Injection）
根据最终裁定的 `FinalSide`，计算绝对精确的最大可用高度：
$$H_{available} = \begin{cases}
\text{Bounds.bottom} - (\text{Anchor.bottom} + \text{sideOffset}), & \text{FinalSide} = \text{'bottom'} \\
\text{Anchor.top} - \text{sideOffset} - \text{Bounds.top}, & \text{FinalSide} = \text{'top'}
\end{cases}$$
同理可计算 $W_{available}$。

#### 阶段 6：变换原点与小三角偏移动态标定
1. **Transform Origin**：
   $$\text{originY} = \begin{cases} \text{'top'}, & \text{FinalSide} = \text{'bottom'} \\ \text{'bottom'}, & \text{FinalSide} = \text{'top'} \end{cases}$$
   $$\text{originX} = \begin{cases} \text{'left'}, & \text{FinalAlign} = \text{'start'} \\ \text{'center'}, & \text{FinalAlign} = \text{'center'} \\ \text{'right'}, & \text{FinalAlign} = \text{'end'} \end{cases}$$
2. **Arrow Offset**：
   $$\text{ArrowX} = \text{Anchor.left} + \text{Anchor.width} / 2 - X_{final}$$
   通过约束区间 $[\text{arrowPadding}, W_{floating} - \text{arrowPadding}]$ 进行保护。

### 5.3 CSS 变量注入契约（CSS Variable Contract）

统一 Positioner 将运算结果直接转化为内联 CSS 自定义属性注入定位外壳，Popup 及子元素完全通过原生 CSS 消费：

```css
/* Positioner 注入给宿主 DOM 的 CSS 变量标准清单 */
--positioner-x: 240px;
--positioner-y: 180px;
--transform-origin: top left;
--available-height: 420px;
--available-width: 320px;
--anchor-width: 140px;
--anchor-height: 36px;
--arrow-offset: 70px;
```

#### 消费规范：
- **定位骨架层（Positioner）**：
  ```css
  position: fixed;
  top: 0;
  left: 0;
  transform: translate3d(var(--positioner-x), var(--positioner-y), 0);
  will-change: transform;
  ```
- **视觉气泡层（Popup）**：
  ```css
  max-height: var(--available-height);
  overflow-y: auto;
  transform-origin: var(--transform-origin);
  /* 动效只在此层施加，绝对不影响 Positioner 的位移测量 */
  transition: opacity 150ms ease, transform 150ms ease;
  ```

### 5.4 零闪烁与单帧收敛生命周期（Zero-Flash Reactivity）

为了实现肉眼零跳变、零二次翻转，Positioner 遵循如下挂载守卫生命周期：

```
Mount
  │
  ├── 1. 首次挂载：注入 style="visibility: hidden; pointer-events: none;"
  ├── 2. useLayoutEffect 同步读取容器尺寸（无 scale 干扰）
  ├── 3. 纯数学解算 FinalSide, X, Y 与 AvailableHeight
  ├── 4. 直接将变量同步写入 DOM style（不触发 React 二次 rerender）
  └── 5. 移出 visibility: hidden，完成单帧瞬时呈现（Zero-Flash）
```

- **持续追踪**：通过 `ResizeObserver` 同时双向监听 `Anchor` 和 `Floating` 元素；
- **滚动捕获**：以 `capture: true, passive: true` 监听祖先滚动容器；
- **批处理**：所有的几何重新解算均收敛至 `requestAnimationFrame` 单一通道，杜绝高频重排。

## 六、迁移收敛与架构演进路线建议

全仓 7 套引擎收敛是一项涉及数十个业务界面的系统工程，必须分步平稳推进：

```
[ 第一阶段：建设核心设施 ]
  └─ 研发 packages/ui/Positioner (或 components/ui/Positioner) 纯几何引擎与 React 组件
  └─ 完善单元测试：覆盖 Double Flip 边界、超长菜单截断、小屏贴边与 Win32 补偿

[ 第二阶段：收敛高发 Bug 点 ]
  └─ 改造 SidebarContextMenus & ContextMenuFlyout（拔除内联手写，消灭二次翻转）
  └─ 改造 SmartPanel & SmartSubmenu（移除手写 Hysteresis 与 itemCount*28 估算）

[ 第三阶段：收敛下拉与选择组件 ]
  └─ 改造 Select / Combobox（替换 useFloatingPosition，建立 contentEl 双向监听）
  └─ 改造 Menu / ModelsCascadeSelect（淘汰 ui/Menu/position.ts 的旧版估算）

[ 第四阶段：收敛 Tooltip 与全局清理 ]
  └─ 改造 Tooltip（剥离反向 translate 逆推，接入统一 Arrow 定位）
  └─ 全面清理存量魔术常量与冗余文件
```

通过这一重构方案，conex 将彻底告别手写估算时代，建立起与 Radix UI / Base UI 齐平的高性能、无闪烁、无回流的现代化桌面端浮层几何中枢。
