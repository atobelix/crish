## 一、勘察背景与核心缺陷总括

### 1.1 勘察范围与核心指标概览

在现代桌面 GUI 体系中，**卡片（Card）**承载着信息模块的物理边界，**行条目（Row）**规范着列表项的节律与可读性，**抽屉（Drawer / Sheet）**管理着深层配置与附属信息流的空间折叠，而**表面色阶（Surface Elevation）**与**同心圆角（Concentric Radius）**则是构建人眼空间立体层次感与工业级精致度的数学底座。

本次勘察对 `apps/crish-desktop` 仓库内所有容器组件、业务卡片、弹出抽屉、样式 Token 及几何数学关系进行了全量深度审计：

| 勘察维度 | 勘察目标与覆盖模块 | 源码物理文件数 | 核心断言 / 规则基线 |
| :--- | :--- | :--- | :--- |
| **原子基元** | `components/ui/Card/`、`Row/`、`PreviewCard/`、`DisclosureAffordance/` | 14 个文件 | P4 容器基元契约、0 描边铁律、4 档行高标尺 |
| **业务卡片** | `agent-card/`、`chat-card/`、`chat-attachment/`、`settings/`、`settings-*/` | 42 个文件 | 消除碎片化手写、统一采用设计系统 Token |
| **侧拉抽屉** | `FileViewerHistoryDrawer`、`leafDockDrawer`、`PreviewHistoryPanel`、`ModelConfigDialog`、`SkillEditorModal` | 18 个文件 | 抽屉基座统一、A11y 无障碍、非破坏性展开 |
| **表面色阶** | `tokens-surface.css`、全仓 `.module.css` 中的 `background` 属性声明 | 110+ 个 CSS 模块 | $e_0 \sim e_5$ 六级表面阶梯单调性、暗黑模式无倒挂 |
| **几何圆角** | `tokens-radius.css`、全仓 864 处 `border-radius` 声明 | 全仓样式表 | 同心圆角欧几里得定理：$R_{inner} = \max(0, R_{outer} - P)$ |

## 二、基础原子容器基元（Card / Row / PreviewCard / DisclosureAffordance）现状深度剖析

### 2.1 ui/Card：零业务消费的“僵尸基元”与能力断层

#### 2.1.1 现状与代码证据
在 `apps/crish-desktop/src/components/ui/Card/Card.tsx` 中，官方定义了现代化卡片原子基元：
- 严格遵循展示型容器 0 描边铁律（`border: none`）；
- 靠表面明度差 `--surface-card` 建立层级；
- 圆角锁定角色圆角 `--radius-card` (12px)；
- 提供 `padding: 'none' | 'sm' | 'md' | 'lg'` 四档标准留白与可选 `rim` 弱轮廓光。

然而，通过对全仓 `apps/crish-desktop/src` 展开全局搜索：
```bash
Get-ChildItem -Path apps/crish-desktop/src -Recurse -Filter '*.tsx' | Select-String -Pattern '<Card\b'
```
**检索结果证明**：在整个项目中，除了其自身的单元测试文件 `Card.test.tsx` 之外，**全仓没有任何一个业务组件使用 `<Card>`！**

#### 2.1.2 架构设计与能力断层
1. **只管外壳，不管内嵌几何（缺少 Concentric Context）**：
   `Card.tsx` 仅在宿主 `<div>` 上设置了 `padding` 和 `border-radius: var(--radius-card)`，但**没有向其子树注入任何 CSS 变量（如 `--card-inner-radius`、`--card-padding-x`）或 React Context**。当开发者在卡片内部放置图片、顶部横幅、操作按钮栏或底栏时，子元素根本无法感知父级当前是 `sm(8px)`、`md(12px)` 还是 `lg(16px)` 的 padding，只能盲目猜测并硬编码自身的 `border-radius`，从根源上导致了同心圆角的必然破裂。
2. **缺乏复合子组件结构（Compound Components）**：
   现代高质量卡片设计系统（如 Radix Themes、Shadcn UI、Base UI）均提供 `<Card.Header>`、`<Card.Title>`、`<Card.Description>`、`<Card.Content>`、`<Card.Footer>` 等结构性子组件，以规范标题字号、文本色阶和底部分割线。由于 `ui/Card` 只是一个简陋的纯 `<div>` 包装，业务开发者在遇到稍复杂的卡片布局时，发现其完全无法满足需求，只得在业务模块中另起炉灶重新手写。

### 2.2 ui/Row：标准化 4 档标尺架空与全仓手写 Row 泛滥

#### 2.2.1 现状与代码证据
`apps/crish-desktop/src/components/ui/Row/Row.tsx` 旨在作为侧栏会话项、工具调用行、思考行与列表项的单行条目基元：
- 4 档高度标尺：`dense(24px)`、`list(28px)`、`control(32px)`、`chrome(36px)`；
- 0 描边铁律，圆角固化为 `--radius-row` (6px)；
- 提供 `leading`、`children`、`trailing` 三段式语义槽位。

与 `Card` 的命运如出一辙，全局检索 `<Row\b` 显示：**除了 `Row.test.tsx`，全仓业务层没有任何一处调用！**

#### 2.2.2 业务层各自为政的混乱现状
在缺乏统一规范执行的情况下，各业务模块各自手写了数十种名称各异、高度各异、padding 各异的 Row 样式：
- `components/settings/SettingsUI.module.css:90`：`.settingsUiRow`（手写 padding 10px 14px，自定义 border-bottom 描边，自定义 flex 布局）；
- `components/agent-card/AgentCard.module.css:40`：`.agentCardTitleRow`（手写高度 32px，gap 5px）；
- `components/agent-card/InlineAgentPanel.module.css:177`：`.inlineAgentHeadRow`；
- `components/chat-card/ProjectPickerMenu.module.css:25`：`.projectRow`；
- `components/chat-card/SubagentHeaderPanel.module.css:102`：`.agentItemRow`；
- `components/chat-composer/ComposerDirTree.module.css:59`：`.row`（高度 26px，非标！）；
- `components/chat-message-row/ChatMessageRow.module.css`：`.row`、`.rowUser`、`.rowAssistant`、`.rowCarrier`、`.planApproveRow`。

这种割裂导致列表项在不同面板之间的行高跳变（24px、26px、28px、32px、36px 混杂），视觉垂直律动极度混乱。

### 2.3 ui/DisclosureAffordance：100% 闲置的展开指示基元

#### 2.3.1 现状与代码证据
`apps/crish-desktop/src/components/ui/DisclosureAffordance/DisclosureAffordance.tsx` 专门用于收敛工具调用折叠、思考块折叠、侧栏分组等处的常驻 chevron 尖角：
- 20px 固定槽位，SVG 图标，静止态低噪（`opacity: 0`）；
- 在父级被 Hover/Focus 或展开时平滑淡入；
- 展开时顺时针旋转 90 度（`transform: rotate(90deg)`）。

检索全仓：**仅在 `DisclosureAffordance.test.tsx` 中被引入！全仓业务组件使用率为 0%！**

#### 2.3.2 业务层重复造轮子与体验参差
业务模块中存在大量需要折叠展开的场景，但全部都在手动拼装 SVG 和旋转逻辑：
1. `components/chat-message-row/InlineAgentThinkingFold.tsx`：手动写 `<svg className={styles.chevron} ...>` 并手写 CSS `transform: rotate(180deg)`（逆时针或上下翻转，与设计系统的顺时针 90° 旋转规范冲突！）；
2. `components/chat-message-row/ToolCallBlock.tsx`：手动写折叠指示图标与 transition；
3. `components/settings-skills/SkillsSettingsTab.module.css:184`：使用原生 HTML `<details>` 与 `<summary>`，并通过 `::-webkit-details-marker { display: none; }` 隐藏原生三角，再由开发者手写内联文字字符；
4. `components/sidebar/SidebarGroupItem.tsx`：手写独立的小箭头状态。

规范化的原子组件被彻底束之高阁，业务层不仅代码量膨胀，更使得用户在不同界面的展开手势与视觉预期完全不一致。

### 2.4 ui/PreviewCard：独立定位引擎、scale 动画污染与孤岛现状

#### 2.4.1 几何定位引擎硬编码（全仓第 8 套隐藏引擎！）
在勘察报告《01-全仓 7 套浮层定位引擎与几何硬编码深度勘察》中盘点了 7 套定位逻辑，而深入勘察 `apps/crish-desktop/src/components/ui/PreviewCard/PreviewCard.tsx`（Lines 44–120）发现：**这里赫然潜伏着全仓第 8 套手写定位引擎！**

```typescript
// PreviewCard.tsx:53-61
export function computePreviewCardPosition(...) {
  const vw = typeof window !== 'undefined'
    ? window.visualViewport?.width || window.innerWidth || 1280
    : 1280;
  const vh = typeof window !== 'undefined'
    ? window.visualViewport?.height || window.innerHeight || 800
    : 800;
  // 硬编码 1280x800 fallback
  // 手写空间计算 spaceTop, spaceBottom, spaceLeft, spaceRight
  // 手写二次翻折逻辑与贝塞尔三角偏移 arrowOffset
}
```

该算法同样存在 1280×800 虚假视口回退、忽略视口 `--available-height` 动态约束、以及与即将建设的统一 Positioner 浮层中枢脱节的问题。

#### 2.4.2 进场动画对 DOM 测量的几何污染
在 `PreviewCard.module.css`（Lines 42–51）中：
```css
@keyframes previewCardEnter {
  from {
    opacity: 0;
    transform: translateY(4px) scale(0.97);
  }
  to {
    opacity: 1;
    transform: translateY(0) scale(1);
  }
}
```
当 `PreviewCard` 挂载时，`scale(0.97)` 会在首帧污染 `getBoundingClientRect()` 的测量值，导致内部文本换行计算偏差约 3%，若在动画未完成前触发边界检测，会引发二次抖动。

#### 2.4.3 业务命名同名冲突
更严重的是，全仓存在两个同名的 `PreviewCard`：
1. `components/ui/PreviewCard/`：通用浮层 RichTooltip 预览卡片原子组件；
2. `components/workspace/PreviewCard.tsx`：内置 Web 浏览器预览窗口业务组件！
在 `builtinViewFactories.tsx:44` 与 `dockToolsIsolation.test.tsx:38` 中，引入的全部是后者（浏览器业务卡片）。原子级 `ui/PreviewCard` 同样陷入了无人消费的孤岛窘境。

## 三、全仓业务卡片容器体系碎片化与实现硬伤勘察

### 3.1 协同体卡片：AgentCard、ApprovalAskCard 与 InlineAgentPanel

#### 3.1.1 AgentCard（`components/agent-card/AgentCard.module.css`）
`AgentCard` 是副 Agent 对话侧栏面板的核心容器。其样式实现暴露出以下问题：
- **废弃 Token 与旧设计混用**：第 6 行声明 `background: var(--bg-card);`，第 35 行头部再次重复声明 `background: var(--bg-card);`；但内部按钮与 Chip 大量依赖已声明废弃的旧圆角 Token：
  - Line 59, 97: `border-radius: var(--radius-sm);` (6px)；
  - Line 164: 外层容器 `border-radius: var(--radius-lg);` (8px)；
  - Line 211, 257: 内嵌元素 `border-radius: var(--radius-md);` (8px)；

## 四、表面色阶梯（Surface Elevation $e_0 \sim e_5$）统一性与暗黑模式倒挂深度审计

### 4.1 六级表面阶梯设计理念 vs 代码落地实测

在现代暗黑模式色彩科学中，空间距离与材质明度遵循**逆平方环境反射定律**：离视点更近、层级更高的悬浮物体，接受的环境反射光照更多，因而**明度应当更高（Lighter）**；而处于深槽、凹陷处的物体，由于遮挡效应，**明度应当更低（Darker）**。

在 `apps/crish-desktop/src/styles/tokens-surface.css` 中，系统设计了严谨的六级表面阶梯：

```
       Elevation
         ▲
$e_5$    │  --surface-overlay  (弹层/模态/菜单/Toast) ── 最顶层 (最亮)
$e_4$    │  --surface-raised   (输入坞/交互中心)
$e_3$    │  --surface-card     (内容卡片/对话流视口)
$e_2$    │  --surface-shell    (外壳/侧边栏/Mica 底板)
$e_1$    │  --surface-canvas   (画布底板/基准地平面)
$e_0$    │  --surface-sunken   (下潜凹槽/嵌入式代码块) ── 最底层 (最暗)
         └────────────────────────────────────────────────────────► Lightness
```

在浅色模式下，该梯队运作良好：从底部的微灰（`--surface-canvas: #fcfcfb`）逐级向纯白（`--surface-overlay: #ffffff`）提升，明度单调递增。

## 五、同心圆角（Concentric Radius）几何数学审查与全仓断层测绘

### 5.1 同心圆角欧几里得几何数学模型与公理推导

#### 5.1.1 欧几里得几何共心圆定义
在二维笛卡尔坐标系中，设外层矩形圆角的曲率圆心为 $C_o = (x_o, y_o)$，其外圆角半径为 $R_{outer}$。  
若内层元素相对外层元素具有均匀的内边距 $P$（Padding），则内层矩形角点的正交向内偏移量在 $X$ 轴与 $Y$ 轴上均为 $P$。

为使内层角部弧线与外层角部弧线在整个象限（$0 \le \theta \le \frac{\pi}{2}$）内保持**严格的法向等距（Equidistant Along Normals）**，内层圆弧的曲率圆心 $C_i$ 必须与外层圆心 $C_o$ **严格重合（$C_i \equiv C_o$）**。

由此可推导出同心圆角的**第一公理公式**：

$$R_{inner} = \max(0, R_{outer} - P)$$

反之，若从内层核心交互元件向外包裹容器，则容器外圆角公式为：

$$R_{outer} = R_{inner} + P$$

```
   Outer Corner (R_outer)
   ╭────────────────────────────
   │ ╲
   │   ╲  Padding P (Uniform)
   │     ╭──────────────────────
   │     │  Inner Corner (R_inner = R_outer - P)
   │     │
   │  C  │  ◄── Common Center of Curvature (Co ≡ Ci)
   │     │
```

---

### 5.2 违反对称性导致的视觉夹角与对角线挤压畸变数学证明

#### 5.2.1 常见错误一：外圆内同角（$R_{inner} = R_{outer}$）的对角线挤压定理
当开发者偷懒对容器和内部元素赋予相同的圆角时（例如卡片 8px，卡片内按钮也是 8px，Padding 为 $P = 8px$）：

在正交轴线方向（$\theta = 0$ 与 $\theta = \frac{\pi}{2}$），间距为 $P$。  
而在角平分线方向（$\theta = \frac{\pi}{4} = 45^\circ$），外圆弧到原点（外顶点）的距离为：
$$D_o = R_{outer} \cdot (\sqrt{2} - 1)$$
内圆弧由于半径同样为 $R_{outer}$，其圆心被向内平移了 $(P, P)$，内圆弧在 $45^\circ$ 方向的距离为：
$$D_i = P\sqrt{2} - R_{outer}(\sqrt{2} - 1)$$

两圆弧在 $45^\circ$ 对角线处的实际可见净间距 $d_{diag}$ 为：
$$d_{diag} = P\sqrt{2} - 2R_{outer}(\sqrt{2} - 1) \approx 1.414 P - 0.828 R_{outer}$$

当 $P = R_{outer} = 8px$ 时：
- 正交轴间距：$P = 8.00\text{px}$；
- **$45^\circ$ 对角线间距**：$d_{diag} \approx 1.414 \times 8 - 0.828 \times 8 \approx \mathbf{4.68\text{px}}$！

**几何畸变率**：
$$\text{Distortion} = \frac{P - d_{diag}}{P} = \frac{8 - 4.68}{8} = \mathbf{41.5\%}$$

**视觉危害**：在对角线处，间距被骤然挤压了 **41.5%**！内层元素的角落肉眼可见地向外凸出，仿佛要刺破外层卡片的边缘，形成极其廉价粗糙的“视觉压迫角”。

#### 5.2.2 常见错误二：外圆内方（$R_{inner} = 0$ 且 $R_{outer} > P$）
若外层圆角很大（如 16px），而内边距较小（如 8px），且内层元素未设圆角（$R_{inner} = 0$）：
正交间距为 8px，而角平分线处内层元素的尖锐直角会直接顶入外层圆角的弧线内部，产生严重的视线阻断与刺眼夹角。

### 5.3 全仓 864 处 border-radius 仅 8 处遵循同心圆角的“几何失序”现状

**极其悬殊的数据对比**：

- 仅有 **0.93%**（8 处，主要分布在 `SelectContent.module.css` 与 `ToastStackModern.module.css`）意识到了同心圆角的存在！
- 绝大多数业务卡片内部的按钮、输入框、头像、Chip 全部以 `var(--radius-md)`（8px）或 `var(--radius-sm)`（6px）一刀切，全仓陷入了严重的“几何失序”。

### 5.4 典型业务场景同心圆角违规图解与度量审计

#### 场景 1：`ApprovalAskCard`（审批危险卡片）
- 外层卡片：$R_{outer} = \text{var}(--radius-lg) = 8px$；
- 内边距：$P = 12px$；
- 内层 Payload 代码块：$R_{inner} = \text{var}(--radius-md) = 8px$。
- **理论同心要求**：因为 $P (12px) > R_{outer} (8px)$，根据第一公理，$R_{inner} = \max(0, 8 - 12) = \mathbf{0px}$！即内层代码块在此内边距下，**其外边缘应当为直角或微圆角（$\le 2px$）**，才能与外部弧线视觉协调。
- **现状缺陷**：内层代码块硬生生设置了 8px 圆角，导致其弧度比外框还要明显，外框成了扁平包裹。

#### 场景 2：`SettingsCard` 与设置列表行
- 外层卡片：$R_{outer} = \text{var}(--radius-xl) = 16px$；
- 内边距：横向 14px，纵向 10px；
- 内部控件：`Button`、`Switch` 均使用 $R = 8px$。
- **理论同心要求**：首行与末行在 Hover 态展开背景时，其朝外的两个角必须满足：
  $R_{row-top} = \max(0, 16px - 1px) = 15px$（若紧贴内沿），而不是依赖父级 `overflow: hidden` 来截断！被截断的 8px 按钮焦点环则因空间不足而直接破损。

#### 场景 3：`AttachmentCard` 52px 图片微卡
- 卡片尺寸：$52px \times 52px$；
- 卡片圆角：$R = 16px$；
- **畸变分析**：圆角直径 $2R = 32px$，占据边长 61.5%。卡片四边几乎没有平直线段，严重变形为非标准的 Squircle。

### 6.2 模态 Dialog 被滥用于垂直长表单的交互挤压灾难

在 `components/settings-models/ModelConfigDialog.tsx` 与 `components/settings-skills/SkillEditorModal.tsx` 中，存在极其别扭的交互设计：
- 模型配置（`ModelConfigPanel`）包含：展示名称、上下文窗口、最大输出 Token、Thinking 档位、模态能力（文本/图像/音频）、价格倍率等数十项垂直表单项；
- 技能编辑包含：发现候选列表、批量导入选项、手填新建技能、高级 YAML 配置；

目前，这两个业务全部强行使用了 `<Dialog size="lg">`。
**带来的严重弊端**：
1. **屏幕垂直空间严重被压榨**：在笔记本或矮屏幕上，居中模态对话框的最大高度受限于 `calc(100vh - 64px)`，表单不得不产生一个局促难用的内部双重滚动条；
2. **主界面上下文完全丢失**：用户在配置某一个模型的参数时，通常需要比对着左侧的模型列表、基线状态或其他同类模型。居中 Dialog 以巨大的身躯占据屏幕正中央，将背景全部遮挡，用户无法进行对照参考；
3. **工业界公认方案**：VS Code、IntelliJ、Linear、Chrome DevTools 均将此类深层配置放在**右侧滑出的 Sheet / Drawer** 中——抽屉全高贯通视口（`height: 100vh`），垂直滚动自然流畅，且左侧仍可透出 60%~70% 的主上下文。

### 6.3 破坏性布局挤压 vs 现代浮层抽屉体验对标

| 交互特性 | 当前全仓手搓现状（FileViewer / Settings） | 工业级标准 `<Drawer>` / `<Sheet>` |
| :--- | :--- | :--- |
| **挂载范式** | 内联在业务 DOM 树中，破坏性挤压兄弟元素 | 通过 `Portal` 独立挂载至顶层，可选 Overlay 或 Push 模式 |
| **进出场动效** | 0 动效，DOM 瞬间撑开，引发全局强制重排（Reflow） | 硬件加速 `transform: translateX(100% -> 0)` 弹簧微动效 |

| **表面色阶** | 混用 `--bg-card`，暗黑模式下变暗 | 锁定 $e_5$ `--surface-overlay`，与顶层物理层级严格对齐 |

## 七、自研标准 Drawer / Sheet 原子复合组件体系完整技术规范与蓝图

为了根治全仓手搓抽屉的乱象，并在架构上对齐 Radix UI / Base UI 的顶级工业设计，我们正式确立**自研 `<Drawer>`（又名 `<Sheet>`）原子复合组件体系**技术规范。

### 7.1 复合组件范式（Compound Component Pattern）架构设计

组件严格遵循复合组件模式（Compound Components），由状态机上下文驱动，严禁单体大 Props：

```tsx
// 业务层标准消费范式
<Drawer.Root open={open} onOpenChange={setOpen} side="right" size="lg">
  <Drawer.Trigger asChild>
    <Button>配置模型</Button>
  </Drawer.Trigger>
  
  <Drawer.Portal>
    <Drawer.Backdrop />
    <Drawer.Content>
      <Drawer.Header>
        <Drawer.Title>模型高级配置</Drawer.Title>
        <Drawer.Description>微调上下文窗口与 Thinking 档位</Drawer.Description>
        <Drawer.Close />
      </Drawer.Header>
      
      <Drawer.Body>
        {/* 表单内容，自带 ScrollArea 接入 */}
        <ModelConfigEditor />
      </Drawer.Body>
      
      <Drawer.Footer>
        <Button variant="secondary" onClick={() => setOpen(false)}>取消</Button>
        <Button variant="primary" onClick={handleSave}>保存配置</Button>
      </Drawer.Footer>
    </Drawer.Content>
  </Drawer.Portal>
</Drawer.Root>
```

#### 子组件职责切分
1. **`Drawer.Root`**：状态机核心，管理 `open`、`onOpenChange`、`side`（`right | left | bottom | top`）、`size`（`sm | md | lg | xl | full`）、`modal`（是否阻断外部交互）；
2. **`Drawer.Trigger`**：触发器，通过 `asChild` 注入 `onClick` 与 `aria-expanded`，免除样板代码；
3. **`Drawer.Portal`**：通过 `createPortal` 挂载至 `document.body` 或局部容器；
4. **`Drawer.Backdrop`**：半透明环境遮罩（`--modal-scrim`），绑定点击关闭逻辑与淡入淡出动画；
5. **`Drawer.Content`**：抽屉主体滑动面板，集成滑动手势、键盘监听与尺寸计算；
6. **`Drawer.Header` / `Title` / `Description`**：A11y 语义标配，自动生成 `aria-labelledby` 与 `aria-describedby`；
7. **`Drawer.Body`**：滚动内容区，注入 `--drawer-inner-radius` 供内部卡片实现同心圆角；
8. **`Drawer.Footer`**：底部操作区，吸底布局与安全边距；
9. **`Drawer.Close`**：关闭按钮，预置同心圆角与 24×24 舒适点击热区。

---

### 7.2 状态机与行为契约（A11y、FocusTrap、LayerStack 联动）

标准 Drawer 必须深度装配现有的基础设施三件套，严禁漏装：

```
                ┌─────────────────────────────────────┐
                │          Drawer.Root State          │
                └──────────────────┬──────────────────┘
                                   │
         ┌─────────────────────────┼─────────────────────────┐
         ▼                         ▼                         ▼
┌──────────────────┐      ┌──────────────────┐      ┌──────────────────┐
│ LayerStackManager│      │    FocusTrap     │      │ useRestoreFocus  │
├──────────────────┤      ├──────────────────┤      ├──────────────────┤
│ 注册至浮层中枢   │      │ 聚焦首个交互项   │      │ 关闭后焦点平滑   │
│ Esc 触发单层退栈 │      │ Tab 键漫游循环圈 │      │ 归还至 Trigger   │
│ 点击 Backdrop 退 │      │ 阻止焦点外溢视口 │      │ 杜绝焦点失踪丢失 │
└──────────────────┘      └──────────────────┘      └──────────────────┘
```

1. **A11y 契约**：
   - 宿主 `Content` 自动注入 `role="dialog"` 与 `aria-modal={modal ? "true" : "false"}`；
   - 自动生成 `id` 关联 `Drawer.Title`（`aria-labelledby`）与 `Drawer.Description`（`aria-describedby`）；
2. **Esc 键优先级**：
   当多层抽屉或抽屉内打开下拉菜单时，由 `LayerStackManager` 保证**后入先出（LIFO）**：按第一次 Esc 关闭下拉菜单，按第二次 Esc 退出抽屉，严禁一键关穿。

### 7.3 现代硬件加速动效规范（CSS @starting-style 与 3D Transform）

彻底废除会导致首帧测算失真的 `scale` 缩放，抽屉动画**全量采用纯正交平移（Translate3D）**：

```css
/* 自研 Drawer 核心动画契约 (无需 JS 介入，单帧极速响应) */
.drawerContent {
  position: fixed;
  z-index: var(--z-modal);
  background: var(--surface-overlay);
  box-shadow: var(--shadow-2xl);
  display: flex;
  flex-direction: column;
  transition: transform var(--transition-popover-enter), opacity var(--transition-popover-enter);
  will-change: transform;
}

/* 右侧滑出规范 */
.drawerContent[data-side='right'] {
  top: 0;
  right: 0;
  bottom: 0;
  height: 100vh;
  border-left: 1px solid var(--border-subtle);
}

/* 现代 CSS @starting-style 入场状态 (Chrome 117+ 原生支持) */
@starting-style {
  .drawerContent[data-side='right'][data-state='open'] {
    transform: translate3d(100%, 0, 0);
  }
  .drawerBackdrop[data-state='open'] {
    opacity: 0;
  }
}

.drawerContent[data-side='right'][data-state='open'] {
  transform: translate3d(0, 0, 0);
}

.drawerContent[data-side='right'][data-state='closed'] {
  transform: translate3d(100%, 0, 0);
  transition-timing-function: var(--ease-accelerate);
}

/* 减弱动态适配 (prefers-reduced-motion) */
@media (prefers-reduced-motion: reduce) {
  .drawerContent {
    transition: opacity var(--duration-fast) linear !important;
    transform: none !important;
  }
}
```

### 7.4 表面色阶与同心圆角严格绑定契约

#### 7.4.1 表面层级绑定
- `Drawer.Content` **刚性锁定 $e_5$ `--surface-overlay`**（在暗黑模式下为 17% 白度提升的炭黑 `#2a2a2e`），彻底杜绝与 $e_3$ 纯黑混用导致的黑洞现象；
- 内部如有子卡片（如抽屉内的参数分组卡），子卡片使用 `--surface-card`，并在此 $e_5$ 背景上自然下潜或浮起，色阶秩序完全恢复正向单调。

#### 7.4.2 同心圆角动态变量注入
`Drawer.Content` 在运行时根据其内边距与外角，向子树注入 `--drawer-inner-radius`：
```css
.drawerContent {
  --drawer-padding-inline: 24px;
  --drawer-padding-block: 20px;
  /* 侧边抽屉顶部/底部内角根据外角与内边距动态解算 */
  --drawer-inner-radius: max(0px, var(--radius-modal) - var(--drawer-padding-inline));
}
```
内部任何卡片或容器直接消费 `var(--drawer-inner-radius)`，在 CSS 引擎层刚性保证 $R_{inner} = \max(0, R_{outer} - P)$ 的绝对成立。

### 7.5 双模式支持：模态遮罩（Modal Overlay）与非破坏性侧推（Non-modal Push）

为了完美兼顾全仓不同业务场景，`<Drawer>` 原生支持两种交互模式：

1. **模态遮罩模式（Modal Overlay，`modal={true}`，默认）**：
   - 带有半透明 Backdrop；
   - 阻断背景点击；
   - 启用全局 FocusTrap；
   - **适用场景**：`ModelConfigDialog`、`SkillEditorModal`、`ScanResultsModal`、`YamlConfigEditorModal` 等深度配置任务。
2. **非破坏性侧推/停靠模式（Non-modal Push / Dock，`modal={false}`）**：
   - 不渲染全屏 Backdrop；
   - 点击抽屉外部的主工作区不会阻断事件，主界面可正常输入或滚动；
   - 支持向外分发 `--drawer-width`，使主工作区平滑增加 `padding-right`（侧推），而不是像目前 `FileViewer` 那样生硬重排挤压；
   - **适用场景**：`FileViewerHistoryDrawer`（文件历史比对）、`PreviewHistoryPanel`（网页历史）、辅助审查工具栏。
