## 一、勘察总览与严重性矩阵

在对 `apps/crish-desktop` 整体组件树进行无死角检索后，我们发现：全仓目前散落了 **至少 10 处独立编写的键盘方向键监听与焦点跳转逻辑**。几乎每一个带有下拉、列表、标签或选项卡特征的组件，都各自重新造了一遍 `ArrowDown / ArrowUp / Home / End / Enter / Space / Escape` 轮子。

这种“各立门户”的实现方式直接导致了三大核心问题：
1. **高重复度与维护分叉**：不同组件在修复 IME 拼音输入法冲突或边界条件时各自打补丁，有的组件拥有 160ms 缓冲，有的组件完全裸奔；代码重复量高达 800+ 行；
2. **交互品质严重缺失**：由于缺乏统一机制，诸如工业级菜单不可或缺的 **Typeahead 即时字符跳转**、**级联子菜单焦点栈**、**视口安全滚屏**、**焦点自动还原** 等高级能力在大部分组件中完全缺位；
3. **WAI-ARIA 规范断层**：读屏器需要的语义属性（`role="menu"`, `aria-activedescendant`, `aria-controls`, `aria-expanded`）东拼西凑、层级错乱，甚至出现“用 Dialog 嵌套 Menu”的非法 DOM 语义结构。

### 严重性等级矩阵

| 组件 / 文件 | 模式 | 重复程度 | A11y 完整度 | 交互缺失点 | 严重等级 |
| :--- | :--- | :--- | :--- | :--- | :--- |

| `SmartPanel/useKeyboardNav.ts` | 数据驱动列表 | 与 SmartExpandablePanel 95% 镜像 | **低**（缺少 controls 关联） | 缺 Typeahead、搜索输入框焦点强行耦合在通用 Hook 内部 | **High (P1)** |
| `SmartExpandablePanel/useSmartKeyboardNav.ts` | 数据驱动列表 | 几乎 1:1 Fork 自 SmartPanel | **低** | 纯拷贝分叉代码、缺 Typeahead、缺焦点还原 | **High (P1)** |

## 二、全仓键盘漫游重复造轮子逐一深度解剖

### 2.1 Menu 体系的双模式与下标脱节

文件定位：[`apps/crish-desktop/src/components/ui/Menu/menuKeyNavigation.ts`](file:///c:/Software/conex/apps/crish-desktop/src/components/ui/Menu/menuKeyNavigation.ts#L7-L199)

#### 代码剖析与重复点
该文件在单一函数 `handleMenuKeyDown` 中，硬性切分成了两套毫无继承关系的判定路径：
1. **L63-L127：`options.length > 0` 模式**：
   ```typescript
   if (e.key === 'ArrowDown') {
     e.preventDefault();
     setFocusedIndex((prev) => {
       let next = prev + 1;
       while (next < options.length && options[next]?.disabled) {
         next++;
       }
       return next >= options.length ? 0 : next;
     });
   }
   ```
2. **L129-L199：`children` 模式（DOM 轮询）**：
   ```typescript
   const elements = Array.from(
     contentRef.current?.querySelectorAll<HTMLElement>(
       '[role="menuitem"]:not([disabled]):not([aria-disabled="true"]), [role="option"]:not([disabled]):not([aria-disabled="true"]), .sep-item:not(.sep-disabled), .sep-selectable-item:not(.sep-disabled)'
     ) ?? []
   );
   // 过滤隐藏项...
   const curIdx = items.indexOf(active);
   if (e.key === 'ArrowDown') {
     e.preventDefault();
     const next = (curIdx + 1) % items.length;
     setFocusedIndex(next);
     items[next]?.focus({ preventScroll: true });
     items[next]?.scrollIntoView?.({ block: 'nearest', behavior: 'smooth' });
   }
   ```

#### 致命缺陷与架构断层
1. **数据下标与 DOM 下标错位**：
   在 `options` 模式下，状态管理在 `Menu.tsx`（L203-L213）：
   ```typescript
   useEffect(() => {
     if (focusedIndex >= 0 && contentRef.current) {
       const items = contentRef.current.querySelectorAll<HTMLButtonElement>(
         '[role="menuitem"], [role="option"]'
       );
       const target = items[focusedIndex];
       target?.focus();
     }
   }, [focusedIndex]);
   ```
   **断层触发场景**：如果 `options` 包含分隔符、分组头、或者自定义渲染组件未附加 `role="menuitem"`，`options` 的下标 `focusedIndex` 与 `querySelectorAll` 搜到的 `items` 节点位置就会产生**绝对偏差**！例如 `options[2]` 是常规项，但由于前面插入了未标角色的分组标题，`items[2]` 实际上对应的是 `options[3]`，用户按键高亮的是 B，键盘回车执行的却是 A！
2. **children 模式下的焦点初始死锁**：
   在 L147-L154：
   ```typescript
   const active = document.activeElement;
   if (
     !(active instanceof HTMLElement) ||
     !items.includes(active) ||
     !contentRef.current?.contains(active)
   ) {
     return; // 焦点不在 items 内时直接退出！
   }
   ```
   当菜单刚展开时，焦点通常停留在 `Popover.Content` 容器本身或触发按钮上。此时 `active` 根本不在 `items` 内部，该函数直接 `return`！导致用户第一次按下 `ArrowDown` 时毫无反应，必须先用鼠标点一下或者按 Tab 才能唤醒方向键漫游。

### 2.2 SmartPanel 与 SmartExpandablePanel 惊人同质化代码分叉

- [`apps/crish-desktop/src/components/ui/SmartExpandablePanel/useSmartKeyboardNav.ts`](file:///c:/Software/conex/apps/crish-desktop/src/components/ui/SmartExpandablePanel/useSmartKeyboardNav.ts#L50-L137)

#### 对比证据
两个文件无论是接口设计、状态初始化、DOM 聚焦同步，还是 keydown 循环，重合度高达 95%：

```typescript
// useKeyboardNav.ts (L71-L75) 与 useSmartKeyboardNav.ts (L61-L67) 完全一致
const validIndices = items
  .map((item, idx) =>
    item.type !== 'divider' && item.type !== 'group' && !item.disabled ? idx : -1

  .filter((idx) => idx !== -1);
```

```typescript
// useKeyboardNav.ts (L50-L59) 与 useSmartKeyboardNav.ts (L38-L48) 完全一致
useEffect(() => {
  if (focusedIndex >= 0 && contentRef.current) {
    const itemElements = contentRef.current.querySelectorAll<HTMLElement>(
      '[role="menuitem"], [role="option"]'
    );
    const target = itemElements[focusedIndex];
    target?.focus();
    target?.scrollIntoView?.({ block: 'nearest' });
  }
}, [focusedIndex, contentRef]);
```

#### 架构隐患
1. **冗余垃圾代码**：历史上有两个平行的展开面板实现（`SmartPanel` 与 `SmartExpandablePanel`），两边各自维护了一套完全相同的键盘漫游 hook，甚至在其 adapters（`MenuAdapter.tsx`, `SelectAdapter.tsx`）中再次层层转接。
2. **每次按键的 O(N) 垃圾对象分配**：在每次 `handleKeyDown` 中，都对整个 `items` 数组进行 `map` 和 `filter` 构造全新 `validIndices` 数组。当长菜单有 100+ 项并连续快速按键时，造成不必要的 JS 垃圾回收抖动。
3. **输入框业务污染**：`useKeyboardNav.ts`（L96-L98）把 `searchInputRef` 强行耦合在按键逻辑中（按 ArrowUp 到头后聚焦搜素框）。如果一个列表不需要搜索框，或者搜索框在底部，这个 hook 就无法复用。

### 2.3 SelectContent 与 SelectTrigger 的镜像重复与滚屏丢失

文件定位：
- [`apps/crish-desktop/src/components/ui/Select/SelectContent.tsx`](file:///c:/Software/conex/apps/crish-desktop/src/components/ui/Select/SelectContent.tsx#L45-L92)
- [`apps/crish-desktop/src/components/ui/Select/SelectTrigger.tsx`](file:///c:/Software/conex/apps/crish-desktop/src/components/ui/Select/SelectTrigger.tsx#L41-L106)

#### 惊人的双端镜像代码
`SelectTrigger` 和 `SelectContent` 分别定义了一模一样的 50 行键盘事件处理：

```typescript
// SelectContent.tsx (L47-L76) 与 SelectTrigger.tsx (L57-L88) 几乎一字不差
const enabledIndices = ctx.items
  .map((item, idx) => (!item.disabled ? idx : -1))
  .filter((idx) => idx !== -1);

if (e.key === 'ArrowDown') {
  e.preventDefault();
  if (enabledIndices.length > 0) {
    const currentPos = enabledIndices.indexOf(ctx.highlightedIndex);
    const nextPos = currentPos < 0 ? 0 : (currentPos + 1) % enabledIndices.length;
    ctx.setHighlightedIndex(enabledIndices[nextPos]!);
  }
} else if (e.key === 'ArrowUp') {
  e.preventDefault();
  if (enabledIndices.length > 0) {
    const currentPos = enabledIndices.indexOf(ctx.highlightedIndex);
    const prevPos = currentPos <= 0 ? enabledIndices.length - 1 : currentPos - 1;
    ctx.setHighlightedIndex(enabledIndices[prevPos]!);
  }
} else if (e.key === 'Home') {
  // ...
} else if (e.key === 'End') {
  // ...
}
```

#### 致命交互缺陷：无视口滚动跟随（Scroll Into View 丢失）
仔细检查 `SelectContent.tsx`：
- 在用户按下 `ArrowDown / ArrowUp` 时，仅仅调用了 `ctx.setHighlightedIndex(...)`；
- 在 `SelectContent.tsx` 和 `SelectRoot.tsx` 全文中，**没有任何一条 `scrollIntoView` 调用**！
- **真实重度 Bug 现象**：当 Select 下拉选项超过 10 项（例如有 40 个国家或分支选项），下拉菜单出现垂直滚动条。用户用键盘按下第 11、12、13 次 `ArrowDown` 时，界面视口完全不向下滚动！被高亮的项隐藏在滚动条下方看不见，用户必须用鼠标手动拖动滚动条才能确认当前光标在哪里。这在工业级 UI 库中属于**不可接受的交互断层**。
- **IME 组合态无任何防御**：两个文件均未对 `isComposing` 或 `keyCode === 229` 进行检测，输入法选词时会直接误吞方向键。

### 2.4 ContextMenuFlyout 内联双层状态机与硬编码死结

文件定位：[`apps/crish-desktop/src/components/sidebar/ContextMenuFlyout.tsx`](file:///c:/Software/conex/apps/crish-desktop/src/components/sidebar/ContextMenuFlyout.tsx#L248-L307)

#### 代码剖析
该组件是侧边栏排序/分组菜单的专用实现，它没有使用通用的 Menu/Submenu 原语，而是内联手写了两套 `onKeyDown`：
1. **父级行监听 (`handleRowKeyDown`)**：
   ```typescript
   const handleRowKeyDown = useCallback(
     (type: NonNullable<FlyKey>, e: React.KeyboardEvent) => {
       if (e.key === 'ArrowRight' || e.key === 'Enter' || e.key === ' ') {
         e.preventDefault();
         e.stopPropagation();
         clearFlyTimers();
         setFly(type);
         requestAnimationFrame(() => {
           const first = flyoutRefs.current[type]?.querySelector<HTMLElement>(
             '[role="menuitemradio"]'
           );
           first?.focus();
         });
         return;
       }
       if (e.key === 'ArrowDown' || e.key === 'ArrowUp') {
         // 硬编码轮询 FLY_ORDER = ['sort', 'group', 'filter']
         const idx = FLY_ORDER.indexOf(type);
         const nextIdx = (idx + (e.key === 'ArrowDown' ? 1 : -1) + FLY_ORDER.length) % FLY_ORDER.length;
         rowRefs.current[FLY_ORDER[nextIdx]!]?.focus();
       }
     },
     [clearFlyTimers]
   );
   ```
2. **飞层选项监听 (`handleFlyoutKeyDown`)**：
   ```typescript
   if (e.key === 'ArrowLeft' || e.key === 'Escape') {
     e.preventDefault();
     e.stopPropagation();
     clearFlyTimers();
     setFly(null);
     rowRefs.current[type]?.focus(); // 回退到父级行
     return;
   }
   if (e.key === 'ArrowDown' || e.key === 'ArrowUp') {
     // querySelectorAll 搜寻 [role="menuitemradio"] 并手动聚焦
   }
   ```

#### 架构缺陷
- **硬编码写死**：绑定了静态数组 `FLY_ORDER`，无法用于任何其他级联菜单；
- **异步竞争脆弱**：依靠 `requestAnimationFrame` 猜测 DOM 挂载时间，若组件因性能卡顿一帧未完成渲染，`first?.focus()` 就会落空，焦点彻底留在父级或 body；
- **焦点还原机制半途而废**：L313 记录了 `sortDropdownRestoreRef.current = document.activeElement`，但在关闭整个下拉时，根本没有调用 `sortDropdownRestoreRef.current?.focus()`，记录了等于白记录。

### 2.5 Tablist 四套并存的割裂格局

| [`TabStrip.tsx`](file:///c:/Software/conex/apps/crish-desktop/src/components/ui/TabStrip/TabStrip.tsx#L202-L248) | 通用 UI 组件 `TabStrip` | 自动/手动双模 | 绑定在每个单个 tab 项的 `onKeyDown` 上，额外支持 `Delete / Backspace` 关闭标签，不支持动态 orientation |

#### 危害总结
每个 Tablist 的按键体验均有细微不同（例如有的支持纵向 `ArrowDown/Up`，有的仅支持横向 `ArrowLeft/Right`；有的带 `scrollIntoView`，有的不带；有的关闭键是 `Delete`，有的无快捷键）。一旦需要统一遵循 WAI-ARIA APG 标准规范（例如按键仅漫游焦点、Space/Enter 才激活的手动模式 Manual Activation），必须改动 4 个不同文件。

## 三、工业级交互能力普遍缺失剖析

对照 W3C WAI-ARIA Authoring Practices Guide (APG) 与成熟桌面级软件标准，当前全仓键盘体系普遍存在以下四大核心能力断层：

### 3.1 Typeahead 字符即时检索跳转彻底空白

#### 什么是工业级 Typeahead？
在 macOS / Windows 原生菜单或成熟 Web 规范中，当用户打开一个包含几十个项目的下拉或菜单（如字体、颜色、会话列表、文件列表）：
1. 用户连续键入字母 `r` -> `e` -> `a`，光标应当**以毫秒级响应（通常 500~800ms 重置窗口）**瞬间跳到匹配前缀为 `rea...` 的项目（如 `React`）；
2. 用户连续多次按下同一个单字母 `d`，光标应当在所有以 `D` 开头的项（如 `Debug` -> `Desktop` -> `Device`）之间循环轮转跳转；
3. 如果项处于禁用态，Typeahead 应当自动寻找下一个可用的匹配项。

#### 当前项目现状
**全仓 100% 缺失 Typeahead 能力**。无论在 `Menu`、`Select`、`SmartPanel` 还是 `ContextMenuFlyout` 中，键入任何英文字符均被无视（或直接触发全局快捷键造成误操作）。键盘无障碍用户若想选择列表末尾的项目，唯一的办法就是死按 50 次 `ArrowDown`，体验极其原始。

---

### 3.2 级联子菜单缺乏通用焦点栈与意图保护

#### 缺陷现状
1. **无层级栈（Focus Stack）**：
   当前只有 `ContextMenuFlyout` 和 `menuKeyNavigation.ts` 勉强支持一级子菜单展开。展开时通常采用粗暴的直接修改状态或 DOM `.click()`，没有在架构上建立 `[ParentMenu, SubMenuLevel1, SubMenuLevel2]` 焦点堆栈。
2. **ArrowLeft 焦点丢失**：
   按 `ArrowLeft` 折叠子菜单时，由于缺乏对父触发项（Submenu Trigger）DOM 节点的严格引用锁定，经常发生子菜单消失、焦点被还给 `<body>` 的失焦 Bug；
3. **缺少光标斜向滑动意图保护（Safe Aim / Triangle Pointer Tracking）**：
   虽然 `SmartPanel` 曾尝试引入 `useSafeAim.ts`，但它与键盘漫游状态机完全脱节。键盘刚把焦点移入子菜单，鼠标轻微晃动立刻触发父菜单悬停，强行夺走焦点，导致键盘漫游被意外打断。

---

### 3.3 Disabled 禁用项跳过算法缺陷与边界崩溃

当前项目中跳过禁用项的逻辑散落在各处，且大多存在死循环或越界隐患：
1. **全部禁用时的死循环风险**：
   在 `menuKeyNavigation.ts`（L68-L70）：
   ```typescript
   let next = prev + 1;
   while (next < options.length && options[next]?.disabled) {
     next++;
   }
   return next >= options.length ? 0 : next;
   ```
   如果整个列表的所有选项（或循环回绕后的首项）全是 `disabled: true`，`next` 越界后归 0，而下标 0 仍然是 disabled，光标停留在禁用项上；甚至在某些变体实现中，由于 `while` 循环未设步进上限，当全部禁用时导致主线程完全冻结！
2. **DOM 属性与数据模型的不一致**：
   有的组件通过数据项 `item.disabled` 判定，有的组件通过 DOM 选择器 `:not([disabled]):not([aria-disabled="true"])` 判定。如果业务方动态通过 CSS 类名 `.is-disabled` 或不可见隐藏样式禁用，键盘漫游依旧会选中它。

---

### 3.4 菜单销毁时的焦点还原（Focus Restoration）极其脆弱

#### 什么是焦点还原？
当通过键盘（如按快捷键、在按钮上按 Enter/Space）唤起菜单或下拉时，**唤起前的活动元素（Trigger）必须被精确入栈记录**。当菜单以任何方式关闭（按 `Escape`、在外部点击、回车选择某项、或组件由于条件渲染被销毁）时，焦点必须**无缝且可靠地还给触发元素**。

#### 当前全仓现状
1. `SelectContent.tsx` 仅在用户明确按下 `Escape` 时手动写了 `ctx.triggerRef.current?.focus()`；如果在外部点击关闭，或者选择某项后关闭，焦点还原由各个业务自行决定，极不稳定；
2. `Menu.tsx` 依赖 Radix 的 `Popover.Content onCloseAutoFocus`。但若 Menu 是通过右键上下文菜单（ContextMenu）或自定义无 Trigger 的虚拟坐标唤起，Radix 的 autoFocus 会把焦点盲目重置到页首，破坏视障用户的上下文阅读流；
3. `ContextMenuFlyout.tsx` 在打开时执行了 `sortDropdownRestoreRef.current = document.activeElement`，但在所有退出路径（`onCloseSortDropdown`）中，**完全没有恢复焦点的执行代码**，导致焦点沦陷在被销毁的飞层内部。

## 四、全仓 WAI-ARIA 语义缺陷与无障碍断层深度审查

### 4.1 角色错乱：Dialog 冒充 Menu 导致读屏器误报

#### 根因剖析
在 [`apps/crish-desktop/src/components/ui/Menu/Menu.tsx`](file:///c:/Software/conex/apps/crish-desktop/src/components/ui/Menu/Menu.tsx#L299-L380) 中：
- 组件外层使用的是 `@radix-ui/react-popover` 的 `Popover.Root`, `Popover.Trigger`, `Popover.Content`；
- Radix Popover 遵循的是 **W3C Dialog Pattern**。因此 `Popover.Trigger` 会自动注入 `aria-haspopup="dialog"`，`Popover.Content` 会自动具有 `role="dialog"` 并绑定 `aria-modal`；
- 开发者在 `Popover.Content` 内部手工硬塞了一个 `<div role="menu" className={styles.menuList}>`。

#### 导致的 A11y 灾难
1. **语义层级非法**：在 W3C ARIA 规范中，`role="dialog"` 内部直接嵌套 `role="menu"` 是严重的反模式（Anti-Pattern）。辅助技术（如 Windows NVDA / Narrator）会向视障用户大声朗读：“进入对话框”，而不是“弹出菜单，包含 N 个项目”；
2. **快捷键提示失效**：操作系统读屏软件会针对 `menu` 自动开启按键直通模式（Menu Navigation Mode），但面对 `dialog` 容器时，它会保持通用虚拟光标模式，导致上下左右方向键被读屏软件拦截用于逐行念字，组件内部的 `onKeyDown` 根本收不到事件！
3. **children 模式完全丢失 role**：在 `Menu.tsx` L377：
   ```typescript
   {children != null ? (
     children
   ) : (
     <div role="menu" className={styles.menuList}>...</div>
   )}
   ```
   如果外部使用了自定义 `children` 渲染，`<div role="menu">` 直接不复存在！整个弹出层没有任何 ARIA 菜单角色。

---

### 4.2 物理焦点与 aria-activedescendant 混乱混用

在 WAI-ARIA 体系中，复合组件的焦点控制严格分为两种哲学，**二者不可混为一谈**：

| 模式 | 核心原理 | 适用场景 | 关键属性 |
| :--- | :--- | :--- | :--- |
| **模式 A：Roving TabIndex** | 物理焦点在子项间转移，当前项 `tabIndex={0}`，其余项 `tabIndex={-1}`。每次漫游调用目标 DOM 的 `.focus()`。 | Menu, Tabs, RadioGroup, Toolbar | 容器 `role="menu"`, 项 `role="menuitem"` + `tabIndex={0/-1}` |
| **模式 B：Active Descendant** | 物理焦点始终锁定在唯一的输入宿主（如 Input/Combobox），仅通过属性指定虚拟活动项 ID。 | Combobox, Searchbox, Autocomplete | 宿主 `aria-activedescendant="itemId"`, 列表 `role="listbox"`, 项 `role="option"` |

#### 当前代码的严重冲突
在 `SelectTrigger.tsx` 与 `SelectItem.tsx` 中：
- `SelectTrigger` 声明了 `role="combobox"` 并附加了 `aria-activedescendant={ctx.activeDescendantId}`（模式 B）；
- 但在 `SelectItem.tsx`（L78-L86）中，每个 Item 渲染为 `<button type="button" role="option" tabIndex={-1}>`；
- 同时在 `SelectContent.tsx` 中，容器又赋予了 `tabIndex={-1}`，但当按键切换时，却既没有在容器上声明 `aria-activedescendant`，也没有物理聚焦到按钮上；
- **读屏器彻底失明**：屏幕阅读器由于焦点在 Trigger 上，而 Content 已经被传送到了 `document.body` 的 Portal 中，两者在 DOM 树中毫无父子关系。读屏器根本无法捕获到 `activeDescendantId` 对应的元素变动，视障用户完全听不到任何选项朗读。

### 4.3 aria-controls 孤岛与销毁后悬空 ID

在 [`apps/crish-desktop/src/components/ui/Select/SelectTrigger.tsx`](file:///c:/Software/conex/apps/crish-desktop/src/components/ui/Select/SelectTrigger.tsx#L141)：

而在 [`apps/crish-desktop/src/components/ui/Select/SelectContent.tsx`](file:///c:/Software/conex/apps/crish-desktop/src/components/ui/Select/SelectContent.tsx#L98)：

- 当下拉菜单关闭时，`SelectContent` 节点被直接从 DOM 中卸载销毁（Unmount）；
- 此时 `SelectTrigger` 依然常驻在 DOM 中，并保留 `aria-controls="select-listbox-xxx"`；
- 这意味着页面上存在一个指向**虚无 DOM 节点**的 `aria-controls` 属性。根据 WCAG 2.1 审查标准，此类未解析的 ID 引用会被自动化无障碍测试工具（axe-core / Lighthouse）直接判定为高危违规。

### 4.4 级联状态与分组语义不匹配

在 `ContextMenuFlyout.tsx` 中：
1. 父级行 `FlyoutRow` 声明了 `role="menuitem"`；
2. 展开的子飞层容器却使用了 `<div role="group" aria-label={label}>`；
3. 子飞层内部的每一项却是 `role="menuitemradio"`。
- **规范冲突**：`menuitemradio` 必须归属于 `role="menu"` 或 `role="menubar"`。直接放在 `role="group"` 下，会导致辅助设备将其降级解释为无关联的单选组，丢失了菜单上下文。

### 4.5 aria-disabled 与原生 disabled 导致的屏幕阅读器跳过

在 `Menu.tsx`（L398）与 `SelectItem.tsx`（L85）：
```typescript
<button disabled={opt.disabled} ...>
```
直接使用原生 HTML `disabled` 属性会导致该元素在 DOM 中彻底不可聚焦（Focus Ineligible），许多屏幕阅读器在以导航模式遍历时会**完全跳过该元素**。
- **无障碍体验断层**：视障用户根本不知道系统里存在这个选项。例如某个功能由于权限不足被禁用，视障用户会认为该功能在软件里压根不存在，无法获取“需要管理员权限解锁”等辅助提示。
- **规范实践**：应当保留子项可聚焦，使用 `aria-disabled="true"` 并在键盘漫游时跳过其激活逻辑，允许屏幕阅读器驻留并读取禁用说明文本。

## 五、对比外部成熟工业级实现

为了确立收敛重构的技术标杆，我们深入审查了仓库 `reference/` 目录下的两大参考架构：

### 5.1 reference/appica-ui（Base UI 原语架构）

`reference/appica-ui` 基于现代 `@base-ui/react` 封装：
1. **状态机与外观彻底解耦**：
   - 所有的漫游、按键、定位逻辑均封装在无 DOM 绑定的 Primitive 内部；
   - 具有统一的 `Composite` 与 `RovingFocus` 原语，统一管理键盘循环规则；
2. **内置工业级 Typeahead**：
   - 原生支持按键字符聚合缓冲（500ms 重置）；
   - 在长列表和下拉菜单中，键入首字符即可精准跳转，无需组件层编写任何一行额外代码；
3. **浮动与多级树形拓扑（FloatingTree）**：
   - 级联子菜单天然接入 `FloatingTree`，父子菜单通过 Context 注册自身节点，子菜单展开时自动压栈，折叠时严格逆序还焦，从根本上根除竞争条件。

### 5.2 reference/ui（Radix UI Roving Focus 架构）

`reference/ui` 采用经典的 Radix UI 漫游设计：
1. **`RovingFocusGroup` 单根总线**：
   - 提供 `<RovingFocusGroup.Root>` 与 `<RovingFocusGroup.Item>`；
   - 统一管理所有子项的 `tabIndex` 分发（当前聚焦项为 0，其余为 -1）；
   - 事件全部在 Root 容器进行委托监听（Event Delegation），子项无需各自绑定昂贵的 `onKeyDown` 闭包；
2. **纯粹的手动与自动激活解耦**：
   - 通过 `activationMode="automatic" | "manual"` 彻底区分 Tablist 场景与 Menu 场景；
   - 严格遵循 W3C 规范，杜绝越界与死锁。

## 六、架构收敛方案：零依赖 useRovingFocus 状态机规范

为了彻底消除上述 10 处重复造轮子与 A11y 缺陷，同时坚决遵守仓库 **`ANTI_OVERENGINEERING_GUARDRAILS.md`（严禁引入臃肿外部第三方依赖）**，我们设计一套纯原生、强类型、零外部依赖的 **`useRovingFocus`** 状态机规范。

### 6.1 设计目标与反过度设计约束

1. **零外部依赖**：仅使用标准 React Hooks（`useRef`, `useState`, `useCallback`, `useEffect`, `useId`），包体积 0 负担；
2. **全场景统一收敛**：一套状态机必须无缝覆盖并彻底替换：
   - 菜单漫游（`Menu`, `ContextMenuFlyout`）
   - 下拉与组合框（`Select`, `ComboboxInput`）
   - 选项卡与分段控制（`Tabs`, `TabStrip`, `SegmentedControl`, `useSettingsNav`）
   - 命令弹窗与面板（`SmartPanel`, `SmartExpandablePanel`, `NewTabLauncherPopover`）
3. **原生集成四大工业级能力**：
   - 毫秒级防抖的 **Typeahead 字符即时检索**；
   - 严密的 **Disabled 自动跳过防死锁算法**；
   - 全链路 **Focus Restoration 焦点入栈还原机制**；
   - 零误触的 **CJK IME 组合态与 Windows 229 防御**。

---

### 6.2 统一状态机数据流与契约定义

#### TypeScript 规范接口契约

```typescript
export type RovingOrientation = 'horizontal' | 'vertical' | 'both';
export type RovingMode = 'roving-tabindex' | 'active-descendant';
export type RovingActivation = 'automatic' | 'manual';

export interface RovingItemData {
  id: string;
  disabled?: boolean;
  textValue?: string; // 用于 Typeahead 搜索匹配
  element?: HTMLElement | null;
}

export interface UseRovingFocusOptions<TItem extends RovingItemData = RovingItemData> {
  /** 漫游模式：roving-tabindex 物理移动焦点；active-descendant 仅更新指针 */
  mode?: RovingMode;
  /** 方向限制：水平、垂直或全向 */
  orientation?: RovingOrientation;
  /** 是否首尾循环 */
  loop?: boolean;
  /** 是否启用 Typeahead 字符按键跳转 */
  enableTypeahead?: boolean;
  /** 激活模式：automatic 焦点移动即激活（常用于 Tab）；manual 需按 Enter/Space 激活 */
  activationMode?: RovingActivation;
  /** 菜单/弹层展开状态（用于焦点还原与初始化） */
  isOpen?: boolean;
  /** 触发器引用（用于销毁后还原焦点） */
  triggerRef?: React.RefObject<HTMLElement | null>;
  /** 容器引用 */
  containerRef: React.RefObject<HTMLElement | null>;
  /** 项列表数据（或通过 DOM 注册提取） */
  items: TItem[];
  /** 当前激活/选中的 ID */
```

#### 1. 工业级 Typeahead 缓冲算法
```typescript
const typeaheadBufferRef = useRef('');
const typeaheadTimerRef = useRef<number | null>(null);

const handleTypeahead = useCallback((key: string, items: RovingItemData[]) => {
  if (key.length !== 1 || e.ctrlKey || e.metaKey || e.altKey) return false;

  if (typeaheadTimerRef.current) {
    window.clearTimeout(typeaheadTimerRef.current);
  }
  typeaheadBufferRef.current += key.toLowerCase();
  typeaheadTimerRef.current = window.setTimeout(() => {
    typeaheadBufferRef.current = '';
  }, 600); // 600ms 黄金重置窗口

  const query = typeaheadBufferRef.current;
  const startIndex = (highlightedIndex >= 0 ? highlightedIndex : 0) + 1;

  // 从当前光标之后优先查找，支持单字母快速循环轮转
  let matchIndex = -1;
  const n = items.length;
  for (let i = 0; i < n; i++) {
    const checkIdx = (startIndex + i) % n;
    const item = items[checkIdx];
    if (item && !item.disabled) {
      const text = (item.textValue || '').toLowerCase();
      if (text.startsWith(query)) {
        matchIndex = checkIdx;
        break;
      }
    }
  }

  if (matchIndex >= 0) {
    focusIndex(matchIndex);
    return true;
  }
  return false;
}, [highlightedIndex]);
```

#### 2. 防死锁的安全跳跃循环寻址
```typescript
function findNextNavigableIndex(
  items: RovingItemData[],
  currentIndex: number,
  delta: 1 | -1,
  loop: boolean
): number {
  const n = items.length;
  if (n === 0) return -1;
  let next = currentIndex;
  
  // 最多遍历 n 次，彻底杜绝所有项全为 disabled 时的死循环崩溃！
  for (let count = 0; count < n; count++) {
    next += delta;
    if (next >= n) {
      if (!loop) return currentIndex;
      next = 0;
    } else if (next < 0) {
      if (!loop) return currentIndex;
      next = n - 1;
    }
    if (!items[next]?.disabled) {
      return next;
    }
  }
  return -1; // 全被禁用，安全返回无可用项
}
```

```typescript
const restoreFocusRef = useRef<HTMLElement | null>(null);

useEffect(() => {
```

## 七、勘察结论与验收基线

1. **核心病灶查清**：全仓键盘漫游并非由于缺乏能力，而是由于各模块自发维护、缺乏统一底层抽象导致。10 处手写轮子造成了 800+ 行重复代码、多处禁用项死锁 Bug、滚屏丢失 Bug 以及严重的 ARIA 语义扭曲；
