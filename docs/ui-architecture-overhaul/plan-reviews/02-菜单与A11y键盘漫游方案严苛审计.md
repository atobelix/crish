## 二、致命级架构缺陷与阻断性风险（Level-1 P0 Blockers）

### 缺陷 2.1：FocusTrap 模态沙盒白名单缺失，导致弹窗内右键菜单变为 inert 死节点

#### 1. 现场代码实况验证
在 `apps/crish-desktop/src/components/ui/Dialog/focusTrap.tsx` 中，存在全局单例的 `FocusTrapIsolationManager`：
```typescript
// apps/crish-desktop/src/components/ui/Dialog/focusTrap.tsx:63-87
private isWhitelisted(node: Element): boolean {
  if (
    node.hasAttribute('data-radix-popper-content-wrapper') ||
    node.getAttribute('data-tooltip-portal') === 'true' ||
    node.getAttribute('data-toast-container') === 'true' ||
    node.classList.contains('radix-popper-content-wrapper') ||
    node.classList.contains('toaster') ||
    node.id === 'toast-root' ||
    node.id === 'tooltip-portal' ||
    node.getAttribute('data-slot') === 'select-content' ||
    node.getAttribute('data-slot') === 'combobox-content' ||
    node.getAttribute('role') === 'listbox' ||
    node.hasAttribute('data-floating-layer') ||
    node.querySelector?.(
      '[data-slot="select-content"], [data-slot="combobox-content"], [role="listbox"], [data-floating-layer]'
    ) != null
  ) {
    return true;
  }
  return false;
}
```
当任何模态弹窗（如 `Dialog`、`ConfirmDialog`、设置面板 `SettingsPanel`、规则编辑器 `RulesEditorDialog`）处于激活状态时：
1. `FocusTrapIsolationManager.applyIsolation()` 会遍历 `document.body` 下的所有兄弟节点；
2. 凡是不在 `isWhitelisted` 白名单内的节点，全部被强制写入：
   ```typescript
   target.setAttribute('aria-hidden', 'true');
   target.setAttribute('inert', '');
   ```

#### 2. 方案缺陷机理分析
- 《02-分维》§2.2 规范中，`ContextMenuContent` 的默认挂载目标为 `container?: HTMLElement | null; // 默认 document.body`；
- 但《02-分维》生成的浮层容器仅声明了 `role="menu"` 与 `class`，**完全未挂载 `data-floating-layer` 属性，亦未在 `focusTrap.tsx` 白名单中注册 `[role="menu"]` 或 `[data-slot="menu-content"]`**！
- **灾难后果**：
  1. 用户在模态弹窗（如查看会话详情、编辑规则弹窗）内触发任何上下文右键菜单时，菜单通过 Portal 挂到 `document.body`；
  2. `FocusTrap` 的隔离管理器立即对该菜单容器施加 `inert` 属性；
  3. 浏览器原生 `inert` 机制会全面阻断所有指针点击、悬停和键盘焦点，**整个右键菜单彻底瘫痪，点击无任何响应**；
  4. 一旦用户在右键菜单内按下 `Tab` 键，`focusTrap.tsx` 的全局监听器因判定 `!containerRef.current.contains(activeEl)` 且不属于白名单浮层，会强制调用 `e.preventDefault(); first.focus();`，**直接将焦点强行抢回弹窗内部，菜单焦点瞬间失控**。

### 缺陷 2.2：《02-分维》复合组件范式与《03-分维》数据驱动 Hook 的严重架构撕裂

#### 1. 冲突真相剖析
- **《02-分维》的实现愿景**是彻底消灭硬编码数据配置数组（`MenuItem[]`），走向声明式 JSX 语法树（§6.2）：
  ```tsx
  <ContextMenuContent>
    <ContextMenuItem onSelect={() => onSessionAction('open-current')}>在此处打开</ContextMenuItem>
    <ContextMenuItem onSelect={() => onSessionAction('open-split')}>拆分视图</ContextMenuItem>
    <ContextMenuSeparator />
    ...
  </ContextMenuContent>
  ```
- **《03-分维》的核心 A11y 漫游 Hook 却设计为纯数据驱动**（§5.3）：
  ```typescript
  export interface UseMenuKeyNavOptions<T extends MenuNavigationItem> {
    isOpen: boolean;
    items: readonly T[]; // 必须传入 items 数组！
    containerRef: React.RefObject<HTMLElement | null>;
    ...
  }
  export interface UseMenuKeyNavReturn<T> {
    getItemProps: (item: T, index: number) => { ... };
  }
  ```
- **严重架构断层**：
  在《02-分维》中，`<ContextMenuContent>` 内部直接包裹的是 JSX 子节点（`props.children`），**在组件渲染时根本拿不到一个扁平的 `items: readonly T[]` 数组**！
  若按《03-分维》的 API 设计：
  - `<ContextMenuContent>` 无法将 `items` 传入 `useMenuKeyNav`；
  - `useMenuKeyNav` 无法知晓当前有几个菜单项、哪一项被禁用了、哪一项的文本是什么；
  - 《03-分维》的 Typeahead 字符即时检索因为没有 `items` 文本提取源而彻底无法工作！

### 缺陷 2.3：SafeAim 几何算法背离当前代码实况，重新引入已废弃毒点

#### 1. 源码红线对抗
在当前仓库实际运行的 `apps/crish-desktop/src/components/ui/internal/SafeAimEngine.ts` L317-L318 中，明确记录了早期测试填坑的重要结论：
```typescript
// apps/crish-desktop/src/components/ui/internal/SafeAimEngine.ts:317-318
// 2. 运动趋势判定：只有当光标明显向反方向撤退回缩时，才提前释放安全区
// 严禁将目标当成单一几何中心点作内积判断，避免斜向划入目标下半部分时被误杀
```

#### 2. 《02-分维》方案的严重倒退
然而，《02-分维》在 §3.2 第 4 点中赫然写道：
> *“维护 4 帧光标历史队列，计算当前速度矢量 $\vec{v} = P_t - P_{t-1}$；计算朝向子菜单中心的目标矢量 $\vec{d} = C_{sub} - P_t$；若 $\vec{v} \cdot \vec{d} \le 0$，无需等待 300ms 宽限超时，立即释放保护区。”*

**严苛指责**：
- 方案作者在编制文档时未深入研读底层 `SafeAimEngine.ts` 的既有实现，擅自臆造数学模型；
- **几何反例证明**：当子菜单高度较长（如超过 300px），光标从上方触发器以 $45^\circ$ 斜向下快速移动至子菜单最下方的菜单项时，速度矢量 $\vec{v}$ 向右下，而朝向子菜单几何中心点 $C_{sub}$ 的目标矢量 $\vec{d}$ 却指向右上偏中。此时二者的点积 $\vec{v} \cdot \vec{d}$ 极易小于等于 0！这会导致用户在正常划向长子菜单底部选项时，安全区瞬间被误熔断，相邻菜单项立即夺取悬停，子菜单瞬间闪退！

## 三、严重级功能缺陷与边界漏洞（Level-2 P1 Major）

### 缺陷 3.1：Typeahead 缺乏可编辑元素（Input/Tiptap/xterm）事件守卫，将暴风式吞噬打字

#### 1. 现象描述
在《03-分维》§4.1 与 §5.2 的 `useTypeahead` 算法中，仅对修饰键（`Ctrl/Alt/Meta`）和 CJK 输入法合成态（`isComposing / 229`）做了过滤，**完全未检查击键事件的目标源节点（`event.target`）是否属于可编辑区域**。

#### 2. 现场击穿场景
1. **带搜索过滤的组合式下拉菜单（Select / Combobox / CommandPalette）**：
   当用户在菜单头部的 `<input type="text" placeholder="搜索选项...">` 中输入字符时，由于按键冒泡至外层 Roving 容器，`useTypeahead` 捕获到单个字符，会强行根据字符检索子菜单项并调用聚焦跳转，同时极易触发 `e.preventDefault()` 吞掉用户的输入！
2. **嵌入 Monaco / Tiptap 富文本 / xterm 终端的复合面板**：
   在桌面端复杂的交互面板中，键盘焦点处于富文本内时，若外部键盘漫游状态机未做靶向过滤，用户键入的普通英文字符将被当成漫游按键，直接破坏文字编辑。

#### 3. 补丁契约
在 `useTypeahead` 与 `useRovingFocus` 内部必须增加严格的 `isEditableElement(e.target)` 守卫：
```typescript
export function isEditableElement(target: EventTarget | null): boolean {
  if (!target || !(target instanceof HTMLElement)) return false;
  const tagName = target.tagName.toLowerCase();
  return (
    tagName === 'input' ||
    tagName === 'textarea' ||
    tagName === 'select' ||
    target.isContentEditable ||
    target.getAttribute('role') === 'textbox' ||
    target.closest('.xterm, [data-slate-editor], .tiptap, .monaco-editor') != null
  );
}
```

### 缺陷 3.3：SafeAim 向量叉积在 `flipLeft` 视口左翻时的几何反射缺失

#### 1. 数学缺陷
《02-分维》§3.2 第 1 点给出的 Safe Triangle 顶点生成公式为：
$$V_{top} = (X_{sub}, \text{SubBounds.top}), \quad V_{bottom} = (X_{sub}, \text{SubBounds.bottom})$$
并硬编码 $X_{sub} = \text{SubBounds.left}$。

#### 2. 边界翻转失效
当二级菜单在屏幕右边缘因视口不足触发 `flipLeft` 翻折展开在左侧时：
- 子菜单矩形位于光标左侧；
- 此时用户光标是从右侧向左下方/左上方移动；
- 安全保护区的三角形底边必须是子菜单的**右边界（`SubBounds.right`）**，而非左边界！
- 速度矢量的回缩判定必须同步对称反转：向右展开时光标速度 $v_x < -2$ 算回缩；而向左展开时，光标速度 $v_x > 2$ 才算回缩。
- 方案未将 `flipLeft` 的翻转状态（`actualSide === 'left'`）回传给 SafeAim，会导致向左展开的子菜单在斜向划入时保护区完全错位，形同虚设。

### 缺陷 3.4：单一 React Context 引发全量重渲染与多层嵌套状态串扰

#### 1. 性能劣化风险
《02-分维》仅设计了一个顶层 Context。当用户在一个包含 20 项以上的复杂菜单中漫游时：
- 键盘每移动一次，`focusedIndex` 变化；
- 鼠标每滑动一次，`pointerPosition` 或 `hoveredItem` 变化；
- 由于所有子项都消费统一个 Context，**整棵菜单树的所有子项（包括纯展示的图标、文字、分割线）全部触发 re-render**。
- 在桌面端快速连击方向键时，这会产生明显的渲染掉帧（16ms 预算被击穿）。

#### 2. 状态隔离缺失
当 `ContextMenuSub`（二级子菜单）展开时：
- 如果子菜单沿用根 Context，子菜单内部的 `focusedIndex` 将与父级菜单的 `focusedIndex` 产生变量竞争与互相覆盖；
- 若要在子菜单关闭时准确归还焦点给父级 `SubTrigger`，必须明确划分 `MenuRootContext`（全局唯一控制句柄）与 `MenuLevelContext`（每层级联立私有的上下文）。

   - 在 `ShortcutRegistry.ts` 中**根本没有登记**！
   - 在 `AppShortcuts.ts` 中**零处理逻辑**！
   - 在侧栏会话列表 `ProjectsSection.tsx`、`GeneralSection.tsx` 中**没有任何 `onKeyDown` 监听 `F2` 或 `Delete` 键**！

#### 2. 批判结论
**当前的 `F2` 与 `Del` 纯粹是欺骗用户的“假快捷键”（Fake Shortcuts）**！用户在侧栏高亮会话时按下 `F2` 无法重命名，按下 `Del` 无法删除。
《02-分维》引入了 `<ContextMenuShortcut>F2</ContextMenuShortcut>`，却完全没有指出这一事实，将旧代码的技术负债继续封装在新组件中。《03-分维》既然是全仓 A11y 与键盘交互的总纲，必须给出快捷键展示与真正快捷键调度的统一契约，消除这种视觉欺骗！

### 5.2 Typeahead 对 Space 空格键的双重歧义冲突

在《03-分维》§4.1 中，判断字符检索的条件是 `key.length === 1`。
- 空格键 `' '` 的字符长度刚好也是 1；
- 但在标准 WAI-ARIA 菜单规范中，空格键 `Space` 与回车键 `Enter` 承担着**激活当前项（Action Activation）**的职责；
- **冲突出现**：用户按下空格键，状态机究竟应该激活菜单项，还是把空格累加到检索缓冲区去搜索带空格的词条（如 "New Session"）？
- **裁决补丁**：
  必须执行**前置上下文消歧**：
  1. 当 Typeahead 缓冲区为空（`buffer === ''`）时，按下 `Space` 必须**一律视为激活操作（Activate/Select）**；
  2. 仅当用户在过去的 500ms 内已经键入了非空格字符（`buffer !== ''`）时，后续的 `Space` 才允许作为文本串接，写入缓冲区并执行匹配。

### 补丁 2：复合组件 Collection 自动收集器（桥接 02 与 03 范式断层）

为了让《02-分维》的纯 JSX 复合组件与《03-分维》的漫游状态机无缝协同，基于 React Context 构建轻量注册制收集器（无需用户手动传 `items` 数组）：

```typescript
// apps/crish-desktop/src/components/ui/internal/menu-base/MenuCollectionContext.tsx
import React, { createContext, useContext, useRef, useCallback } from 'react';

export interface MenuItemRecord {
  id: string;
  ref: React.RefObject<HTMLElement | null>;
  textValue: string;
  disabled: boolean;
  hasSubmenu?: boolean;
}

interface MenuCollectionContextValue {
  registerItem: (item: MenuItemRecord) => () => void;
  getItems: () => MenuItemRecord[];
}

const MenuCollectionContext = createContext<MenuCollectionContextValue | null>(null);

export const MenuCollectionProvider: React.FC<{ children: React.ReactNode }> = ({ children }) => {
  const itemsRef = useRef<Map<string, MenuItemRecord>>(new Map());

  const registerItem = useCallback((item: MenuItemRecord) => {
    itemsRef.current.set(item.id, item);
    return () => {
      itemsRef.current.delete(item.id);
    };
  }, []);

  const getItems = useCallback(() => {
    // 保证按照 DOM 树实际物理顺序排序
    return Array.from(itemsRef.current.values()).sort((a, b) => {
      const elA = a.ref.current;
      const elB = b.ref.current;
      if (!elA || !elB) return 0;
      return elA.compareDocumentPosition(elB) & Node.DOCUMENT_POSITION_FOLLOWING ? -1 : 1;
    });
  }, []);

  return (
    <MenuCollectionContext.Provider value={{ registerItem, getItems }}>
      {children}
    </MenuCollectionContext.Provider>
  );
};
```
在 `<ContextMenuItem>` 挂载时自动注册自己的文本与 Ref，`useMenuKeyNav` 即可在运行时 O(1) 获取当前菜单项列表，**完美弥合 02 与 03 的设计撕裂**。

### 补丁 3：SafeAim 几何推导与速度方向自适应修正（对齐真实源码）

在《02-分维》§3.2 中，替换错误的“中心点内积算法”，恢复与强化 `SafeAimEngine.ts` 的原生算法：

```typescript
// apps/crish-desktop/src/components/ui/internal/SafeTriangle.ts 修正
export function calculateSafeAimState(
  cursor: Point2D,
  prevCursor: Point2D,
  subRect: RectBounds,
  placement: 'left' | 'right'
): boolean {
  // 1. 速度回缩判定：只判定是否背离目标方向，严禁取中心点点积
  const vx = cursor.x - prevCursor.x;
  if (placement === 'right' && vx < -2) return false; // 向右展开时，明显向左退回
  if (placement === 'left' && vx > 2) return false;  // 向左展开时，明显向右退回

  // 2. 自适应构建目标边界顶点
  let pTop: Point2D;
  let pBottom: Point2D;
  const pad = 4;

  if (placement === 'left') {
    // flipLeft 场景：目标为子菜单右边界！
    pTop = { x: subRect.right, y: subRect.top - pad };
    pBottom = { x: subRect.right, y: subRect.bottom + pad };
  } else {
    // 正常场景：目标为子菜单左边界
    pTop = { x: subRect.left, y: subRect.top - pad };
    pBottom = { x: subRect.left, y: subRect.bottom + pad };
  }

  // 3. 2D 向量叉积同号判定
  return isPointInTriangle(cursor, prevCursor, pTop, pBottom);
}
```
