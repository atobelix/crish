## 二、真实宿主环境兼容性对抗审查

### 2.1 `DialogOverlayContext` 与 Containing Block（包含块）失效断层 (DEF-01)

#### 现场代码与方案矛盾：
在 `apps/crish-desktop/src/components/ui/Dialog/Dialog.tsx` 中：
```tsx
// 行 163-169
<div
  ref={setOverlayEl}
  className={overlayClasses}
  data-dialog-overlay=""
  data-dialog-state={state === 'exiting' ? 'exiting' : 'open'}
>
  <DialogOverlayContext.Provider value={overlayEl}>
    ...
```
当 `SelectContent` 或 `Menu` 在 `Dialog` 内部展开时，三级解析策略将它们 portal 到 `overlayEl` 中。  
在 `Dialog.module.css` 中：
```css
.dialogEnter {
  animation: dialog-enter var(--transition-modal-enter) forwards;
  transform-origin: center center;
}
@keyframes dialog-enter {
  from { opacity: 0; transform: scale(0.985); }
  to { opacity: 1; transform: none; }
}
```
并且，如果某些子面板使用了包含 `transform`、`perspective`、`filter`、`will-change` 或 `container-type` 的包装容器：

#### 物理机理断层：
CSS 规范明确规定：**当元素的任意祖先节点具有 `transform != none` 时，`position: fixed` 的 Containing Block 不再是视口（Viewport），而是该祖先元素！**  
方案 01 在 `usePositioner.ts` 第 523-526 行直接粗暴写入：
```ts
el.style.position = 'fixed';
el.style.left = '0px';
el.style.top = '0px';
el.style.transform = `translate3d(${res.x}px, ${res.y}px, 0)`;
```
这里的 `res.x` 与 `res.y` 完全是基于视口左上角 `(0, 0)` 的物理坐标（源于 `anchor.getBoundingClientRect()`）。  
如果 `portalContainer` 不是 `document.body`，而是带有局部偏移或处于动画变换态的容器（例如其自身 `getBoundingClientRect()` 的 `left = 120, top = 80`）：  
**最终视觉坐标将叠加该容器偏移，导致浮层向右下角严重漂移（漂移量恰好等于容器的 `(left, top)`），直接飞出可视区！**

> **严苛改进断言**：  
> `usePositioner` 必须读取挂载容器的 Containing Block 偏移：
> $$X_{final} = X_{viewport} - CB_{left} + CB_{scrollLeft}$$
> $$Y_{final} = Y_{viewport} - CB_{top} + CB_{scrollTop}$$
> 当挂载于非 `document.body` 时，自动扣除容器的相对基准坐标，保证纯粹相对坐标系的统一。

### 2.2 多显示器高 DPI 动态跨屏与子像素抖动

#### 现状分析：
方案在 `computePosition` 第 364 行执行：
```ts
x: Math.round(clampedX),
y: Math.round(clampedY),
```
在 Windows 下，多屏环境普遍存在主屏 100%（96 DPI）与副屏 125% / 150%（144 DPI）混用。
1. **125% DPI 缩放下**：1 CSS 像素等于 1.25 物理设备像素。强制 `Math.round(clampedX)` 会抹去 0.25/0.75 的浮点对齐，导致菜单边框（1px 发丝）在物理光栅化时与触发器产生 1px 的物理裂缝或字体模糊；
2. **跨屏拖拽窗口时**：`window.devicePixelRatio` 发生瞬时跳变。`usePositioner` 的 `useEffect` 仅监听了 `window.resize` 与 `scroll`，而跨屏拖拽若未改变窗口 CSS 宽高，不会触发 `resize` 事件，导致残留上一屏幕的 DPI 坐标。

> **严苛改进断言**：  
> 必须监听 `window.matchMedia('(resolution: ' + window.devicePixelRatio + 'dppx)')`，在 DPI 跨屏切换时主动触发 `update()`。

### 2.3 Win32 无边框窗口最大化补偿与未解绑陷阱

#### 现状分析：
方案在 `getEffectiveViewport`（行 163-186）中保留了：
```ts
const isMaximized =
  typeof document !== 'undefined' &&
  document.documentElement?.getAttribute('data-window-maximized') === 'true';
const isWindows =
  typeof navigator !== 'undefined' && /Win/i.test(navigator.userAgent);
if (isWindows && isMaximized) {
  return {
    width: Math.max(320, rawW - 16),
    height: Math.max(200, rawH - 16),
    offsetLeft: 8,
    offsetTop: 8,
  };
}
```
**对抗勘察发现**：
经全仓检索，当前系统在 Tauri 窗口最大化时，通过 Rust 或 `TitleBar.tsx` 维护状态，**但从未在 `document.documentElement` 上写入过 `data-window-maximized="true"`**！  
这意味着此段代码在现实中是 100% 的死逻辑。  
更严重的是：若某天前端补上了这个属性，`offsetLeft: 8` 会导致贴靠在屏幕左边缘（如侧边栏收起按钮 `left: 4px`）的图标弹出的菜单被强行钳位到 `8 + 8 = 16px`，**引发 12px 的无故横向跳变**！

> **严苛改进断言**：  
> Win32 最大化边缘补偿不能以硬编码假定全局 `offsetLeft: 8`，而应判断锚点是否处于屏幕不可见安全区，或直接由外层窗口容器统一样式内衬（Window Inset）处理，避免在定位算法层注入局部魔术数字。

## 三、LayerStackManager 深度互斥与状态机协同审查

### 3.1 渲染管线生命周期时序错位 (DEF-05)

#### 渲染序列时间线对抗还原：
```
[React Render] ──> [useLayoutEffect] (绘制前) ──> [Paint / 光栅化] ──> [useEffect] (绘制后)
                          │                                           │
                    usePositioner                               useLayerRegistration
                 (visibility: visible)                       (登记进入 LayerStackManager)
                          │                                           │
                     浮层已上屏呈现在屏幕上                       中枢才拿到 layerId！
```
1. 在 `useLayoutEffect` 执行完毕到浏览器将第一帧像素画上屏幕的极短窗口内，浮层已经是 `visibility: visible`；
2. 但由于 `useLayerRegistration` 使用的是普通的 `useEffect`，**在中枢真正完成登记之前，屏幕上已经存在可见浮层了**；
3. **破坏性场景**：
   - 此时 `layerStackManager.hasActiveFloatingLayers()` 返回 `false`；
   - `data-floating-active` 尚未被设置到 `document.body`；
   - 若用户在此毫秒级间隙内移动鼠标碰到了另一个按钮，系统的 Tooltip **不会被静默**，而是会瞬间弹起并盖在刚展开的菜单上，破坏互斥铁律！

> **严苛改进断言**：  
> `useLayerRegistration` 的核心注册必须提升至 `useLayoutEffect` 执行，或者在 `useFloatingLayer` 内部保证与 `usePositioner` 同帧完成中枢登记，绝不允许存在“已视觉呈现却未入栈”的幽灵状态。

### 3.2 `LAYER_TYPE_PRIORITY` 权重倒挂与退栈误杀 (DEF-06)

#### 深入分析 LayerStackManager 调度机理：
在 `apps/crish-desktop/src/components/ui/internal/layer-stack/layerStackTypes.ts` 中：
```ts
export const LAYER_TYPE_PRIORITY: Record<LayerType, number> = {
  'modal-dialog': 10,
  'confirm-dialog': 15,
  drawer: 20,
  popover: 30,          // <--- 权重 30
  'dropdown-menu': 40,  // <--- 权重 40
  'context-menu': 40,   // <--- 权重 40
  'cascade-submenu': 50,
  tooltip: 60,
  toast: 70,
  'virtual-interceptor': 100,
};
```
在 `LayerStackManager.ts` 第 210-215 行：
```ts
this.layers.sort((a, b) => {
  const pA = LAYER_TYPE_PRIORITY[a.type] ?? 0;
  const pB = LAYER_TYPE_PRIORITY[b.type] ?? 0;
  if (pA !== pB) return pA - pB;
  return a.mountedAt - b.mountedAt;
});
```
在 `handleGlobalKeyDown`（Esc 按键）中，中枢自顶向下（从数组最后一个元素倒序扫描）：
- 数组末端（权重数字最大）最先响应 Esc。

#### 破坏性场景还原：
1. 方案 01 的 `useFloatingLayer.ts` 默认：`layerType = 'popover'`（权重 30）；
2. 假设用户从一个 `dropdown-menu`（如顶部菜单，权重 40）内部点击触发了一个子气泡或操作弹层（未显式声明类型，缺省为 `popover`，权重 30）；
3. 经过 `layers.sort()`，子层 `popover`（30）被排在了父层 `dropdown-menu`（40）**的前面（底部）**；
4. 用户按下 Esc 时，中枢从后往前扫，**首先命中了父层 `dropdown-menu`（40）**！
5. 父层被退栈，触发级联关闭，把子层一起关掉！**无法实现单步退栈**！

> **严苛改进断言**：  
> `useFloatingLayer` 不能偷懒默认 `layerType = 'popover'`；必须根据上下文（如是否处于 `MenuContext` 下）自动继承或设为合法层级，且必须确保任何子层的有效层级权重 $\ge$ 父层。

## 五、极端边界与反过度设计挑刺

### 5.1 虚拟点 `VirtualPoint` 引发的 React 185 死循环 (DEF-02 致命毒点)

#### 毒点代码还原：
在方案 01 `usePositioner.ts` 第 476-536 行：
```ts
export function usePositioner(options: UsePositionerOptions) {
  const { anchor, ... } = options;
  
  const update = useCallback(() => {
    ...
    const anchorRect = normalizeAnchorToRect(anchor);
    ...
    setResult(res);
    setIsPositioned(true);
  }, [open, enabled, anchor, contentRef, ...]); // <--- 依赖了 anchor 对象引用

  useLayoutEffect(() => {
    if (!open || !enabled) return;
    update();
  }, [open, enabled, update]); // <--- update 改变触发执行
```
#### 致命逻辑闭环：
在右键菜单场景（如 `ContextMenu` 或 `FileAnnotationPopover`）：
```tsx
// 业务组件日常写法：
<ContextMenu anchor={{ x: e.clientX, y: e.clientY }} />
```
1. 每次父组件渲染时，`{ x, y }` 是一个全新的内存对象引用；
2. `usePositioner` 监听到 `anchor` 引用变更，重新生成 `update` 函数；
3. `useLayoutEffect` 检测到 `update` 变更，立刻同步执行 `update()`；
4. `update()` 内部调用 `setResult(res)` 和 `setIsPositioned(true)` 触发组件重新渲染；
5. 组件重新渲染，父组件再次传入新的 `{ x, y }` 对象字面量；
6. **循环往复，React 瞬间抛出 `Maximum update depth exceeded` 崩溃白屏！**

> **严苛改进断言**：  
> `anchor` 必须在 Hook 内部进行深度值比对（Value Equality），或者由专属 Ref 稳定化：
> ```ts
> const isSamePoint = prevPoint && typeof anchor === 'object' && 'x' in anchor &&
>   prevPoint.x === anchor.x && prevPoint.y === anchor.y;
> ```
> 绝不允许直接将外部传入的未 memoized 对象字面量作为 `useCallback` 的依赖！

### 5.2 内联 `transform` 暴力抢占覆写 `@starting-style` 动效 (DEF-03)

方案 00 大力推崇现代 CSS `@starting-style` 0-JS 弹性动效：
```css
/* 预期的优雅 CSS 动效 */
@starting-style {
  opacity: 0;
  scale: 0.975;
}
.menuContent {
  opacity: 1;
  scale: 1;
  transition: opacity 260ms var(--ease-spring), scale 260ms var(--ease-spring);
}
```
但方案 01 的 `usePositioner` 第 526 行却采用传统旧写法：
```ts
el.style.transform = `translate3d(${res.x}px, ${res.y}px, 0)`;
```
**严重冲突**：
1. 任何元素上的 `style.transform` 属性是单值容器。一旦 JS 写入了 `translate3d`，CSS 中的 `transform: scale(0.975)` 将被直接覆盖；
2. 即使在 CSS 中使用单独的 `scale` 属性，如果动效库使用的是 `transform: matrix(...)` 或复合动画，两者将彻底打架；
3. 方案 00 第 113 行宣称的“动效隔离架构（Positioner 定位，Popup 动效）”在方案 01 的代码落地中**荡然无存**，方案 01 依然把坐标直接怼在业务内容 DOM 节点上。

> **严苛改进断言**：  
> 必须全面拥抱现代 Chromium / WebView2 原生支持的 **独立 CSS 变换属性（Individual Transform Properties）**：
> ```ts
> el.style.translate = `${res.x}px ${res.y}px`; // 纯位移，完全不污染 CSS scale 动效！
> ```
> 彻底解耦 `translate` 与 `scale` / `rotate`，让 CSS `@starting-style` 免受任何 JS 干扰！

### 5.3 视口极小（< 300px）时的几何倒错与触发器遮挡 (DEF-07)

在小屏或分屏窄窗口（高度 250px）下：
假设触发器位于中间 `top: 110px, bottom: 138px`，浮层天然高度为 `200px`。
方案 01 计算：
- `spaceBelow = 242 - 144 = 98px`
- `spaceAbove = 104 - 8 = 96px`
- 因为两者皆放不下，但下侧略大，保持 `actualSide = 'bottom'`；
- 目标 Y 坐标：`targetY = anchor.bottom + sideOffset = 144px`；
- 进入 Clamp 阶段（行 336）：
  `clampedY = Math.min(Math.max(8, 144), Math.max(8, 242 - 200))`  
  `clampedY = Math.min(144, 42) = 42px`！

**视觉灾难发生**：  
浮层的 Y 坐标被强制推到了 `42px`，直接压在 `110px ~ 138px` 的触发器上方，将触发器严严实实盖住！  
同时，方案计算出的 `--available-height` 却是 `98px`。  
**结论**：当空间不足时，定位引擎必须**刚性锚定在触发器边缘**（Y 保持 144px），依靠 `--available-height: 98px` + `overflow-y: auto` 让浮层就地下拉滚动，**绝不能擅自向上平移遮挡触发源**！

### 5.4 动态内容导致 Flip Hysteresis（翻转震荡）与 ResizeObserver 闭环

1. **Flip Hysteresis（翻转迟滞）缺失**：  
   用户在搜索框内输入字符时，菜单项从 20 项过滤为 2 项，高度从 300px 骤缩到 60px。如果之前因空间不足翻转到上方展开，此时由于 60px 在下方能够容纳，引擎会立刻翻转到下方。用户再删掉字符，又猛然弹回上方！**输入过程中菜单上下翻飞，造成极度恶劣的视觉跳跃**。  
2. **ResizeObserver 闭环**：  
   `usePositioner` 监听了 `contentRef.current` 的 ResizeObserver。当引擎向 `el.style` 写入 `--available-height` 时，若组件设置了 `max-height: var(--available-height)`，可能触发高度微变，再次激活 ResizeObserver，形成微任务死循环。

### 补丁 1：解耦 `translate` 独立属性与 Containing Block 偏移矫正 (修复 DEF-01 / DEF-03)

```ts
/**
 * 纠正挂载容器非 Viewport 时的局部坐标偏移，并使用现代 CSS translate 独立属性
 */
export function applyPositionStyles(
  el: HTMLElement,
  res: PositionResult,
  portalContainer: HTMLElement | null
): void {
  let offsetX = 0;
  let offsetY = 0;

  // 1. 若挂载在局部 Containing Block (如 Dialog overlay / transform 容器) 中，扣除容器物理起点
  if (portalContainer && portalContainer !== document.body) {
    const containerRect = portalContainer.getBoundingClientRect();
    offsetX = containerRect.left - portalContainer.scrollLeft;
    offsetY = containerRect.top - portalContainer.scrollTop;
  }

  const finalX = Math.round(res.x - offsetX);
  const finalY = Math.round(res.y - offsetY);

  // 2. 拥抱现代 CSS 独立变换属性，彻底不碰 style.transform，免污染 @starting-style scale
  el.style.position = 'fixed';
  el.style.left = '0px';
  el.style.top = '0px';
  el.style.translate = `${finalX}px ${finalY}px`;
  
  el.style.setProperty('--transform-origin', res.transformOrigin);
  el.style.setProperty('--available-width', `${res.availableWidth}px`);
  el.style.setProperty('--available-height', `${res.availableHeight}px`);
  el.style.visibility = 'visible';
  el.style.pointerEvents = 'auto';
}
```

### 补丁 2：VirtualPoint 值语义稳定化与 Ref 防死循环 (修复 DEF-02)

```ts
/**
 * 稳定化 Anchor 引用，阻断对象字面量在 useLayoutEffect 中的无限触发
 */
export function useStableAnchor(anchor: PositionerAnchor): PositionerAnchor {
  const stableRef = useRef(anchor);

  const isSame = (prev: PositionerAnchor, next: PositionerAnchor): boolean => {
    if (prev === next) return true;
    if (
      prev &&
      next &&
      typeof prev === 'object' &&
      typeof next === 'object' &&
      'x' in prev &&
      'x' in next &&
      'y' in prev &&
      'y' in next
    ) {
      return (
        prev.x === (next as VirtualPoint).x &&
        prev.y === (next as VirtualPoint).y &&
        prev.width === (next as VirtualPoint).width &&
        prev.height === (next as VirtualPoint).height
      );
    }
    return false;
  };

  if (!isSame(stableRef.current, anchor)) {
    stableRef.current = anchor;
  }

  return stableRef.current;
}
```
