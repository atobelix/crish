## 三、阻断级设计缺陷（实现前必须返工）

> 下列任一条未关闭，对应 TU 不得开工。

### 3.1 【Critical·安全】CSP 回退到 `unsafe-inline`

- 现网：`tauri.conf.json:26` `script-src 'self'`（安全基线正确）。
- Stage 1 详案完整配置样例将 `script-src` 改为含 `'unsafe-inline'`。
- 总方案 ACT-202 提「动态 CSP Hash」，与详案样例互相矛盾。

**裁决**：**禁止 `unsafe-inline`**。内联 loader 必须走 cspPlugin 既有 hash 路径（`vite.config.ts:84-95`），或 `generateBundle` 注入 SHA-256；双 CSP（meta + tauri.conf）交集语义须单独一节写清。

### 3.2 【Critical·架构倒退】ReaderPool 整池重写

Stage 1 详案 `acquire_slot` 在持有 `slots` 全局锁期间执行查询闭包 → **串行化全部只读**；同时丢弃现池 `try_acquire` 自适应探测、`stats`、RAII `PooledReader`、超时退避与 `tests_concurrency.rs`。

**裁决**：**保留现有 `ReaderPool` API**，只做：
1. 业务读方法（`messages`/`agents`/`sessions`/`preferences`）从 `self.conn.lock()` 切到 `lib.rs:224` 既有 `read()` 助手；
2. 两阶段预热（`initial_readers:1` → 稳态 8）通过 `ReaderPoolConfig` 参数完成；
3. 禁止另造 `reader.prepare` 私有 API。

### 3.3 【Critical·编译级】`entry-core.ts` 含 JSX

详案 §4.8 写 `root.render(<App />)` 却扩展名 `.ts` → 无法编译。必须 `.tsx`。

### 3.4 【Critical·自相矛盾】首屏体积预算 vs 静态聚合 App

- `vite.config.ts:689-691` 记载 App 残留约 **455KB**；现网门禁 `CHUNK_SIZE_GATE_KB=600`，注释中 chat-bridge 约 **479KB 且低于阈值**。
- 详案同时要求：`entry-core` 静态 `import App` + `entry-core ≤ 180KB` + `chat-bridge ≤ 250KB`。

**裁决**：三者不可同时成立。实现顺序必须是：
1. 先跑一次真实 `npm run build`，以 manifest 产物为准冻结基线；
2. 再拆 App 静态闭包 / compositionRoot / chat-bridge；
3. 预算数字以基线报告修订，**禁止拍脑袋 180/250 写死进 CI**（先 warning 后 hard）。

另：「chat-bridge 674.4KB 且 CI 0% 通过」**与仓库注释矛盾，不可复现**；ACT-304 优先级须以实测重排。

### 3.5 【Critical·功能回退】WorkerPool 全量替换

- Stage 6 详案把类型收成 `'render'|'parser'`，与现网 `types.ts` 的 `'render'|'compute'|'io'|'network'` 冲突。
- 丢失 `pendingTasks` / `dedupCache` / `AbortController` / `taskTimeoutMs` / `getMetrics`。
- Stage 3 另造近整库 `JitWorkerPool`（~350 行）→ 双池漂移。

**裁决**：**只增量改**既有 `WorkerPool`：冷启不 `initMinimalPool` 或仅 1 个 render；首个 Markdown 到达再扩；15s 闲置 terminate 作为策略开关。禁止新写平行池。

### 3.6 【Critical·分层违规】`packages` 反向依赖 `apps`

Stage 6 详案让 `memory-manager.ts`（packages）import `apps/crish-desktop/src/services/idle/...`，违反仓库「底层不得反向上层」铁律。

**裁决**：阈值熔断通过回调 / 事件由 apps 注入；packages 只发 `MemoryPressureLevel`。

### 3.7 【Critical·时序】`applyAtomicCommit` 注水顺序错误

详案先 `hydrateWorkspaceShell()`（读 `layout.getAppSettings()` 判断 restore）再 `setState` 新快照 → restore 开关可能读到旧设置。

**裁决**：先原子写入全部 Store，再触发 shell hydrate；单测锁定顺序。

### 3.8 【Critical·不可达验收】若干「严格 = 1 / = 0 / = 2」断言

| 断言 | 问题 | 建议改写 |
| --- | --- | --- |
| 根调和「严格 1 次」 | fallback 分支自身 ≥2 拍；`showFirstRun` 等 useState 初值合法更新；StrictMode dev 双跑 | 常规路径 ≤2；兜底路径单独断言；E2E 在 production 构建跑 |
| 冷启 Worker「恒为 0」 | 详案又允许「积压≥2 破障」；与 E2E 绝对断言冲突 | FCP 前 = 0；交互后允许 JIT；禁止「恒为 0」措辞 |
| 水合 IPC「恒定 2 次」 | 样例仍 `listSessions + getSessionMeta×2 + body + agents` ≥4 | 改为「与会话数 N 无关的常数上界 K」并写清 K 的组成 |
| 待机协程「0 Hz」 | Push 桶 flush 需要到期驱动；详案未给 `PushDecisionEngine.next_expiry` 设计 | 无到期任务时 0；有到期时事件驱动，禁止固定 sleep |
| CLS≤0.05 / FID&lt;16 / setup≤20ms | 无本机基准方法学 | 先建 benchmark 脚本与机器指纹，再定阈值 |

### 3.9 【High·模型破坏】`LazyModelCatalog` OnceCell vs 现网可变刷新

现网 `Arc<RwLock<ModelCatalog>>` 支撑 `catalog_refresh` / `upsert_from_scan`（`catalog_commands.rs`）。OnceCell 只读惰性与覆盖合并冲突；且详案类型名 `Catalog`、`SharedDb::inner()` 均与现契约不符（实为 `local_db()`）。

**裁决**：惰性首次加载可保留，但刷新路径必须仍走 RwLock；或 `OnceCell<RwLock<…>>`。

### 3.10 【High·幻影设计】原生侧主题嗅探

详案读 `app_dir/.theme_cache`——仓库中**不存在**该文件；主题真源在 WebView `localStorage['crish_theme']` / SQLite preferences。

**裁决**：删嗅探；主题防闪走「骨架内联默认 + loader 读镜像 + Commit Ack」。
