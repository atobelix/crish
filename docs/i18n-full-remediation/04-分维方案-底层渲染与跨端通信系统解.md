## 一、方案摘要与目标矩阵

### 1.1 方案定位与演进使命

在客户端国际化（i18n）治理中，顶层 UI 组件的静态文案替换往往只是“水面上的冰山”。真正的技术暗礁深藏在**底层渲染引擎（Rust/Markdown）**、**核心会话循环与意图推进（SessionLoop/Prompt）**、以及**跨进程/跨设备通信（IPC/Push）**之中。

前期全景深度勘察（见问题勘察报告 04）抓获了多起严重的底层硬编码与架构断层事实：

1. **渲染层直接拼接硬编码中文**：Rust 渲染引擎 `conex-markdown` 在代码块中写死 `<button ... title="复制" aria-label="复制代码">复制</button>`；表格外壳写死 `aria-label="表格"`；
2. **前端 DOM 调和器的致命反向耦合**：前端流式渲染单元调和器 `unitReconciler.ts:45` 竟然硬依赖 `[role="region"][aria-label="表格"]` 选择器施加 `contain: layout` 排版隔离。若草率将 Rust 中的 `表格` 修改为英文 `Table`，将直接破坏前端表格的排版隔离，引发严重的流式重排抖动；
3. **意图自愈强行单向注入中文 Steering**：`session-loop` 的 Tool-Promise 自愈机制无论上下文语言，强行向对话流注入“【系统自动推进】：你刚刚在回复中表达了执行动作的意图...”，直接污染英文模型的上下文，引发严重的语言漂移（Language Contamination）；
4. **移动端/跨端推送通知全量硬编码中文**：17 种场景（S1~S12）文案写死在 Rust 字符串中，且移动端设备注册模型 `VendorDevice` 完全不感知设备 Locale，导致海外设备接收全中文通知；
5. **IPC 错误双向“假本地化”错觉**：前端自以为 Rust 会本地化错误文案，Rust 却直接抛出硬编码中文拼接错误，导致所有 Toast 与横幅在英文环境下失控展示中文。

**本方案的终极使命**：严格遵守反过度设计红线与单一真理源（SSOT）原则，**彻底消除跨层体验撕裂与大模型语言漂移**。确立**“底层输出 100% 语言中立语义 DOM / 结构化 Token + 前端客户端水合 / 事件委托接管文案”**的渲染架构；重构前端 DOM 调和器解除反向耦合；为会话意图推进建立**会话语言环境感知（Session Language Context）**；对跨端通知与 IPC 错误全面实施**结构化 Payload + 移动设备语言感知**改造。

## 二、Rust Markdown 渲染引擎 100% 语言中立化改造规范

### 2.1 架构设计抉择：彻底确立“方案 B：语言中立语义 DOM 结构”

在勘察阶段，团队深度对比了“方案 A：Rust 内核感知前端 Locale”与“方案 B：语言中立语义 DOM + 前端表现层解耦挂载”。

**裁决重申**：坚决摒弃方案 A，全面落地 **方案 B**。

- **原因 1：内存与缓存命中率保护**。`crates/conex-markdown/src/cache.rs` 维护全局渲染 LRU 缓存。若引入 `locale` 维度，缓存分裂为多份，内存翻倍；用户切换语言时数千条缓存全量失效。
- **原因 2：历史消息零重绘**。SQLite 数据库中持久化了历史消息的 HTML 渲染产物。采用方案 B，历史消息的 DOM 结构天然中立，切换语言时无需遍历历史重新渲染，由前端样式与事件中心瞬间适配，0 毫秒卡顿。
- **原因 3：单一真理源（SSOT）**。所有多语言字典 100% 收敛于前端 `apps/crish-desktop/src/i18n/`，Rust 无需引入笨重的本地化依赖。

## 三、前端 DOM 调和器（Unit Reconciler）紧急解耦重构方案

### 3.1 致命隐患根因与排版隔离（Layout Containment）机制

#### 3.1.1 根因剖析

在 [`apps/crish-desktop/src/api/markdown/unitReconciler.ts:44-48`](file:///c:/Software/conex/apps/crish-desktop/src/api/markdown/unitReconciler.ts#L44-L48)：

```ts
function applyLayoutIsolation(element: Element): void {
  if (element.matches('.md-table-wrap, [role="region"][aria-label="表格"]')) {
    (element as HTMLElement).style.contain = 'layout';
  }
}
```

以及行 68-74：

```ts
for (const nested of Array.from(
  element.querySelectorAll('.md-table-wrap, [role="region"][aria-label="表格"]')
)) {
  applyLayoutIsolation(nested);
}
```

**隐患分析**：

- 前端调和器通过 CSS `contain: layout` 对流式 Markdown 输出中的表格执行排版隔离。如果不进行隔离，当流式输出持续向表格 `<tbody>` 追加新行时，浏览器每次都会触发整个对话流气泡乃至整个视口的重排（Reflow），引发极严重的掉帧与性能雪崩。
- 代码中竟然硬编码了中文属性选择器 `[aria-label="表格"]`。一旦 Rust 侧升级将 `aria-label` 替换为英文，如果未同步修改调和器，任何依赖属性匹配的场景将导致排版隔离**静默失效**。

### 3.2 调和器重构方案与向下兼容策略

#### 3.2.1 标准选择器定义与常量收敛

在 `apps/crish-desktop/src/api/markdown/unitReconciler.ts` 顶部定义严格中立的排版隔离选择器常量：

```ts
/**
 * 表格布局隔离选择器（Layout Containment Selector）
 * 核心真理源：中立类名 `.md-table-wrap` 与语义属性 `[data-md-table]`
 * 兼容层：对历史持久化消息中的已渲染 HTML 保留向下兼容支持
 */
export const TABLE_LAYOUT_ISOLATION_SELECTOR = [
  '.md-table-wrap',
  '[data-md-table]',
  '[role="region"][data-role="table"]',
  // 历史存量消息向下兼容容错（只读兼容，严禁新代码产出）
  '[role="region"][aria-label="表格"]',
  '[role="region"][aria-label="Data table"]',
  '[role="region"][aria-label="Table"]',
].join(', ');
```

#### 3.2.2 函数重构落地

彻底重写 `applyLayoutIsolation` 与 `createUnitNode`：

```ts
function applyLayoutIsolation(element: Element): void {
  if (element.matches(TABLE_LAYOUT_ISOLATION_SELECTOR)) {
    (element as HTMLElement).style.contain = 'layout';
  }
}

function createUnitNode(unit: MarkdownUnit): Node {
  const clone = unit.sourceNode.cloneNode(true);
  if (clone.nodeType === Node.ELEMENT_NODE) {
    const element = clone as Element;
    applyLayoutIsolation(element);
    for (const nested of Array.from(
      element.querySelectorAll(TABLE_LAYOUT_ISOLATION_SELECTOR)
    )) {
      applyLayoutIsolation(nested);
    }
  }
  return clone;
}
```

**收益**：

1. **彻底解除中文字符强绑定**：主路径 100% 依赖 `.md-table-wrap` 与 `data-md-table`，Rust 渲染器输出任何语言的 `aria-label` 均绝对不影响排版隔离生效；
2. **零风险向下兼容**：即使历史数据库中存有几千条包含 `aria-label="表格"` 的旧消息，依然能在重绘或增量调和时无缝获得 `contain: layout`。

```
└──────────────────────────┬─────────────────────────────┘

┌──────────────────────────▼─────────────────────────────┐

└────────────────────────────────────────────────────────┘
```

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum SessionLocale {
    ZhCn,
    EnUs,
}

impl SessionLocale {
    pub fn from_str_loose(s: &str) -> Self {
        if s.starts_with("en") || s.eq_ignore_ascii_case("english") {
            SessionLocale::EnUs
        } else {
            SessionLocale::ZhCn
        }
    }
}

pub struct SessionLanguageDetector;

impl SessionLanguageDetector {
    /// 综合推导当前推进轮次应当使用的语言环境
    pub fn resolve_locale(
        explicit_locale: Option<&str>,
        matched_snippet: &str,
        assistant_text: &str,
    ) -> SessionLocale {
        // L1: 显式设置优先
        if let Some(locale) = explicit_locale {
            if !locale.trim().is_empty() {
                return SessionLocale::from_str_loose(locale);
            }
        }

        // L2: 根据命中的行动承诺片段特征快速判断
        if Self::looks_like_english(matched_snippet) {
            return SessionLocale::EnUs;
        }

        // L3: 统计 Assistant 消息尾部的 CJK 字符占比
        let cjk_count = assistant_text
            .chars()
            .filter(|c| is_cjk_char(*c))
            .count();
        let total_count = assistant_text.chars().count();

        if total_count > 0 && (cjk_count as f64 / total_count as f64) < 0.10 {
            // CJK 字符少于 10%，判定为英文会话
            SessionLocale::EnUs
        } else {
            SessionLocale::ZhCn
        }
    }

    fn looks_like_english(s: &str) -> bool {
        let ascii_count = s.chars().filter(|c| c.is_ascii_alphabetic()).count();
        let cjk_count = s.chars().filter(|c| is_cjk_char(*c)).count();
        ascii_count > cjk_count && cjk_count == 0
    }
}

#[inline]
fn is_cjk_char(c: char) -> bool {
    matches!(c,
        '\u{4E00}'..='\u{9FFF}' | // CJK Unified Ideographs
        '\u{3400}'..='\u{4DBF}' | // CJK Extension A
        '\u{F900}'..='\u{FAFF}'   // CJK Compatibility Ideographs
    )
}
```

```rust
pub fn reply_looks_goal_done(text: &str) -> bool {
    let trimmed = text.trim();
    if trimmed.is_empty() {
        return false;
    }
    // 中文完成标记
    if trimmed.contains("目标已完成") {
        return true;
    }

    let lower = trimmed.to_lowercase();

    // 英文常规完成语句匹配
    if lower.contains("goal completed")
        || lower.contains("goal is completed")
        || lower.contains("goal achieved")
        || lower.contains("all tasks completed")
        || lower.contains("all tasks are complete")
    {
        return true;
    }

    // 单词边界判定 \bDONE\b
    let bytes = lower.as_bytes();
    for (index, window) in bytes.windows(4).enumerate() {
        if window == b"done" {
            let prev_ok = index == 0 || !bytes[index - 1].is_ascii_alphanumeric();
            let next_ok = index + 4 >= bytes.len() || !bytes[index + 4].is_ascii_alphanumeric();
            if prev_ok && next_ok {
                return true;
            }
        }
    }
    false
}
```

## 五、Push 通知中立化与多端设备语言感知方案

### 5.1 架构分层：结构化 Payload vs 厂商通道服务端渲染

对于跨设备推送，通信链路分为两类：

1. **WebSocket / 在线端直连推送（In-App Direct Push）**：
   - 彻底废除预渲染中文字符串；
   - 发送**纯结构化通知 Payload**（事件枚举 `SceneId` + 参数键值对 `params`）；
   - 手机端或桌面端 Web 接收到后，直接调用本端的 i18n 字典进行本地化格式化展示。
2. **离线厂商通道（APNs / HMS）推送**：
   - 苹果 APNs 与华为 HMS 在应用后台或未启动时，必须由推送服务端直接向厂商服务器递交最终展示的 `title` 和 `body`；
   - 因此，Rust 推送服务必须根据**接收设备的偏好语言（`preferred_language`）**进行服务端精准双语渲染。

### 5.4 夜间静默折叠摘要多语言化（`quiet.rs`）

在 `apps/agent-workbench/src-tauri/src/push/quiet.rs:195-209` 中重构 `NightSummary` 构建逻辑：

```rust
pub fn build_night_summary(
    date: String,
    groups: Vec<NightSummaryGroup>,
    first_at_ms: i64,
    last_at_ms: i64,
    locale: Option<&str>,
) -> NightSummary {
    let is_en = matches!(locale, Some(l) if l.starts_with("en"));
    let total: u32 = groups.iter().map(|g| g.count).sum();
    let clauses: Vec<String> = groups.iter().map(|g| summary_group_clause(g, is_en)).collect();

    let mut body = if is_en {
        if total <= 1 {
            format!("{total} item completed during quiet hours")
        } else {
            format!("{total} items completed during quiet hours")
        }
    } else {
        format!("夜间完成 {total} 项")
    };

    if !clauses.is_empty() {
        if is_en {
            body.push_str(": ");
            body.push_str(&clauses.join(", "));
        } else {
            body.push('：');
            body.push_str(&clauses.join("、"));
        }
    }

    NightSummary {
        date,
        total,
        first_at_ms,
        last_at_ms,
        groups,
        body,
    }
}
```

### 6.1 终结“双向假本地化错觉”：结构化参数错误协议

勘察揭示：前端 `error-translation.ts:30` 注明“直接使用 `payload.message`，假定 Rust 端已本地化”，而 Rust 却直接使用中文拼接抛错。

**系统性根治策略**：

1. **Rust 永远只生产机器可读错误码（Machine-Readable Code）与结构化参数字典（Named Parameters）**；
2. **`payload.message` 仅作为英文开发者技术回退（Lingua Franca for Developers）**；
3. **用户可见文案 100% 收敛至前端字典 `apps/crish-desktop/src/i18n/locales/*/error.ts`**，通过参数插值动态生成。

### 6.3 前端 `error-translation.ts` 翻译器重构

重构 `apps/crish-desktop/src/utils/error-translation.ts`：

```ts
import { t } from '@/i18n';
import type { CrishErrorPayload } from '@shared-types/errors';

export interface LocalizedErrorDisplay {
  title: string;
  message: string;
  actionText?: string;
}

export function translateErrorPayload(
  payload: CrishErrorPayload
): LocalizedErrorDisplay {
  // 1. 标题翻译：优先从字典中查 error.<code}>.title，缺省回退
  const titleKey = `error.${payload.code}.title`;
  const title = t(titleKey as any, payload.params ?? {}, payload.code);

  // 2. 正文消息翻译：优先从字典查 error.<code}>.message 进行参数插值
  const messageKey = `error.${payload.code}.message`;
  // 若未配置特定 message，则使用通用文案，最后兜底到英文 payload.message
  const message = t(messageKey as any, payload.params ?? {}, payload.message);

  // 3. 行动建议翻译
  let actionText: string | undefined;
  if (payload.action) {
    actionText = t(payload.action as any, payload.params ?? {});
  }

  return { title, message, actionText };
}
```
