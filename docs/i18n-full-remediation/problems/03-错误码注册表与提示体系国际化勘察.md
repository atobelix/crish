## 摘要与核心结论

本报告对 Conex / Crish 客户端全仓的错误码体系、元信息注册表、异常跨端序列化契约、前端翻译分派层以及 UI 错误提示消费链路进行了深度穿透勘察。

### 核心勘察结论

1. **注册表结构缺陷阻断国际化**：
   - 在 [`packages/shared-types/src/errors/info.ts:25-916`](file:///c:/Software/conex/packages/shared-types/src/errors/info.ts#L25-L916) 与 Rust 镜像 [`crates/conex-types/src/error.rs:218-562`](file:///c:/Software/conex/crates/conex-types/src/error.rs#L218-L562) 中，全仓权威定义的 **105 个错误码全部将 `title` 写死为中文硬编码字符串**（覆盖率 100% 为中文）。元信息注册表缺乏语言解耦抽象，底层直接封死了多语言支持。
   - 跨进程序列化负载 [`CrishErrorPayload`](file:///c:/Software/conex/packages/shared-types/src/errors/serialize.ts#L9-L23) 契约中**完全丢失了 `title` 字段**，导致前端与跨端消费方无法在数据流中传递标准化标题。

2. **建议行动键与字典事实脱轨（缺失率高达 96.2%）**：
   - 105 个错误码在注册表中声明了 96 个不同的 `action`。然而在前端字典 [`apps/crish-desktop/src/i18n/locales/zh-CN.ts:114-120`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/locales/zh-CN.ts#L114-L120) 与 [`en-US.ts:114-120`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/locales/en-US.ts#L114-L120) 中，**`action` 命名空间下仅有区区 4 个键**（`common.report_bug`, `provider.check_network`, `provider.check_key`, `provider.retry`）。
   - 其余 **101 个错误码（占比 96.2%）的动作建议在字典中完全缺失**！
   - 存在 **3 处严重的契约污染**：`tool.aborted_before_dispatch`、`tool.cancelled`、`tool.outcome_unknown` 在注册表中的 `action` 并非命名空间键，而是直接写入了**中文自然语言长句**（如 `'请求已被用户或控制总线中止，无需重试'`），破坏了枚举键设计契约。

3. **前端翻译层处于半脱钩与英文倒灌状态**：
   - 前端 [`apps/crish-desktop/src/utils/error-translation.ts`](file:///c:/Software/conex/apps/crish-desktop/src/utils/error-translation.ts) 仅内置了 **33 个错误码的英文硬编码回退**（`BUILTIN_ERROR_DISPLAY:60-203`），剩余 72 个错误码全部回退为千篇一律的英文通用文案：`title: 'Error'`, `action: 'Please try again or contact support.'`。
   - 当中文用户遇到这 72 个错误码或 101 个缺失 action 时，由于字典未命中且回退仅有英文，**中文界面会直接倒灌英文建议**，用户体验严重割裂。

4. **UI 消费层空中楼阁（真实调用完全绕行）**：
   - 穿透检查发现：**整个 `apps/crish-desktop` 生产代码中，没有任何业务组件实际调用 `toUserVisibleError` 或 `translateError`！**
   - 业务组件（如 `WorkflowConfirmCard.tsx`、`useAgentToolApproval.ts`）全部直接向全局通知传递中文硬编码字符串（如 `toast.error('创建失败，请检查引擎是否就绪')`、`showToast('批准失败，请重试')`）。
   - 通知容器 [`ToastCard.tsx`](file:///c:/Software/conex/apps/crish-desktop/src/components/overlay/ToastCard.tsx) 与 [`ToastViewport.tsx`](file:///c:/Software/conex/apps/crish-desktop/src/components/overlay/ToastViewport.tsx) 自身包含多处中文硬编码（如 `撤销`、`aria-label="关闭通知"`、`aria-label="通知中心"`）。

## 一、现有错误注册表结构缺陷分析

### 1.1 Title 字段直接绑定中文导致多语言阻断

#### 源码证据

在共享类型包 [`packages/shared-types/src/errors/info.ts:16-23`](file:///c:/Software/conex/packages/shared-types/src/errors/info.ts#L16-L23)：

```typescript
export interface CrishErrorInfo {
  readonly code: CrishErrorCode;
  readonly title: string; // ← 缺陷点：直接定义为本地化后的字符串，而非国际化键
  readonly category: CrishErrorCategory;
  readonly retryable: boolean;
  readonly public: boolean;
  readonly action: string;
}
```

在同文件 [`CRISH_ERROR_REGISTRY`](file:///c:/Software/conex/packages/shared-types/src/errors/info.ts#L25-L916) 中，105 个错误码的所有条目全部填入中文硬编码字面量，例如：

```typescript
  'config.invalid': {
    code: 'config.invalid',
    title: '配置项非法', // ← 硬编码中文
    category: 'permanent',
    retryable: false,
    public: true,
    action: 'action.config.check_field',
  },
  'session.not_found': {
    code: 'session.not_found',
    title: '会话未找到', // ← 硬编码中文
    category: 'permanent',
    retryable: false,
    public: true,
    action: 'action.session.select_existing',
  },
```

在 Rust 核心层 [`crates/conex-types/src/error.rs:39-46`](file:///c:/Software/conex/crates/conex-types/src/error.rs#L39-L46) 与 [`CRISH_ERROR_REGISTRY:218-562`](file:///c:/Software/conex/crates/conex-types/src/error.rs#L218-L562) 中，结构完全同构，同样是 100% 中文字面量：

```rust
pub struct CrishErrorInfo {
    pub code: &'static str,
    pub title: &'static str, // ← &'static str 写死中文
    pub category: CrishErrorCategory,
    pub retryable: bool,
    pub is_public: bool,
    pub action: &'static str,
}
```

#### 架构危害分析

1. **单语言真理源（SSOT）绑定**：`CRISH_ERROR_REGISTRY` 被定义为全仓错误码元信息的“权威注册表”（见 `info.ts:2` 及 `codes-drift.test.ts:2`）。然而其 `title` 却固定为中文，导致任何非中文环境（如国际化英文版、海外部署环境、自动化日志分析工具）调用 `getErrorInfo(code).title` 时，强制只能拿到中文。
2. **序列化通道断层**：在跨端 IPC 传输层 [`CrishErrorPayload`](file:///c:/Software/conex/packages/shared-types/src/errors/serialize.ts#L9-L23) 中：
   ```typescript
   export interface CrishErrorPayload {
     readonly code: CrishErrorCode;
     readonly message: string;
     readonly category: CrishErrorCategory;
     readonly retryable: boolean;
     readonly public: boolean;
     readonly action: string;
     readonly metadata?: JsonObject | undefined;
     readonly cause?: CrishErrorPayload | undefined;
     readonly stack?: string | undefined;
     readonly timestamp: number;
   }
   ```
   **`CrishErrorPayload` 中压根没有 `title` 字段**！Rust 端发射错误至前端时，前端无法通过 payload 直接获知标题，导致前端必须在本地通过 `error.<code>.title` 或 `BUILTIN_ERROR_DISPLAY` 进行脆弱的“二次推断猜解”。

### 1.2 Action 键设计脱轨与契约污染现状

#### 键名命名空间规范与实际现状

`action` 字段设计的本意是为前端 UI（如 Toast 操作按钮、错误横幅建议、排障引导）提供可定位的可执行建议（Actionable Guidance）i18n key。

在 105 个错误码中，绝大部分（102 个）使用了 `action.<domain>.<action_name>` 的点分结构，例如：
- `action.config.check_field`
- `action.session.select_existing`
- `action.provider.check_api_key`
- `action.tool.fix_input`

#### 缺陷 1：前端字典缺失 96.2%（严重脱钩）

对比前端实际语言字典 [`apps/crish-desktop/src/i18n/locales/zh-CN.ts:114-120`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/locales/zh-CN.ts#L114-L120) 与 [`en-US.ts:114-120`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/locales/en-US.ts#L114-L120)：

```typescript
// 现有字典中 action 命名空间的全部内容：
action: {
  'common.report_bug': '请尝试重试或上报该问题。',
  'provider.check_network': '服务暂时不可用，请稍后重试。',
  'provider.check_key': '请在“设置”中检查 API 密钥。',
  'provider.retry': '请重试。',
},
```

注册表中涉及的 96 种不同 action 中，仅有以上 **4 个** 在字典中存在对应条目。
**整整 101 个错误码（96.2%）的 action 在查表时必然命中 undefined**！

#### 缺陷 2：自然语言长句侵入契约（3 处异类）

在 [`packages/shared-types/src/errors/info.ts:393-421`](file:///c:/Software/conex/packages/shared-types/src/errors/info.ts#L393-L421) 与 [`crates/conex-types/src/error.rs:721-747`](file:///c:/Software/conex/crates/conex-types/src/error.rs#L721-L747) 中，存在由 `session-integrity-repair` 遗留的历史包袱：

```typescript
  // session-integrity-repair 02 §4.1 F01：中断/取消/未知三码。
  // 注意：这三条的 action 在 Rust 侧是描述性文案而非 action.* i18n 键
  // （Rust 原样保留），本表按「逐字一致」不变量照录——后续若归一为
  // action.* 键需 Rust/TS 同步改，不可单侧漂移。
  'tool.aborted_before_dispatch': {
    code: 'tool.aborted_before_dispatch',
    title: '工具分发前已中止',
    category: 'permanent',
    retryable: false,
    public: true,
    action: '请求已被用户或控制总线中止，无需重试', // ← 异类：硬编码中文长句
  },
  'tool.cancelled': {
    code: 'tool.cancelled',
    title: '工具已被取消',
    category: 'permanent',
    retryable: false,
    public: true,
    action: '兄弟工具执行失败或批处理取消，跳过执行', // ← 异类：硬编码中文长句
  },
  'tool.outcome_unknown': {
    code: 'tool.outcome_unknown',
    title: '工具结果未知（崩溃自愈）',
    category: 'permanent',
    retryable: false,
    public: true,
    action: '系统冷启动恢复自动合成未闭合调用，继续会话', // ← 异类：硬编码中文长句
  },
```

**危害**：
1. 破坏了 `action` 字段“必须是 i18n key”的类型契约假定；
2. 在英文环境下，由于不是点分 key，前端解析函数 `resolveDictionaryKey` 将其当作未知 key 处理，最终因未命中直接被丢弃或回退为通用英文 `'Please try again or contact support.'`；
3. 注释明确指出“需 Rust/TS 同步改，不可单侧漂移”，说明该问题早已被发现，但长期搁置未作彻底治理。

#### 2. BUILTIN_ERROR_DISPLAY 的设计逻辑与致命瓶颈

在 `error-translation.ts:60-203` 中，声明了一个包含 33 个错误码的静态映射表：

```typescript
const BUILTIN_ERROR_DISPLAY: Readonly<
  Record<string, { readonly title: string; readonly action: string }>
> = { ... 33 条英文映射 ... };

const DEFAULT_DISPLAY: Readonly<{
  readonly title: string;
  readonly action: string;
}> = {
  title: 'Error',
  action: 'Please try again or contact support.',
};
```

**该设计的四大演进瓶颈**：

1. **瓶颈 1：双源维护与代码冗余（Double Sourcing）**：
   - 开发者在 `i18n/locales/en-US.ts` 中写了一遍这 33 条英文，又在 `error-translation.ts` 中一字不差地手写了一遍这 33 条英文；
   - 两个地方内容完全重复，一旦文案修改，极易发生单侧漂移。
2. **瓶颈 2：容量人为停滞（Frozen at 33）**：
   - 文件头部注释自述：“*不手写 77 个码的 switch/case，仅覆盖用户可见的高频码（>= 20 条）*”。
   - 这一妥协导致该文件在错误码从 77 扩展到 102、再扩展到 105 时，**完全停滞更新**！新纳入的 browser 9 码、computer 8 码、goal 3 码、write_path_conflict 等高频前台报错，在此表中全部缺失。
3. **瓶颈 3：非对称单向回退导致“英文倒灌”**：
   - [`toUserVisibleError:288-296`](file:///c:/Software/conex/apps/crish-desktop/src/utils/error-translation.ts#L288-L296) 的解析机制为：
     ```typescript
     const display = resolveDisplay(payload.code);
     const title = effectiveTranslate
       ? effectiveTranslate(`error.${payload.code}.title`, display.title)
       : display.title;
     const action = effectiveTranslate
       ? effectiveTranslate(payload.action, display.action)
       : display.action;
     ```
   - 当用户使用**中文**（`zh-CN`）时：

```typescript
export function toUserVisibleError(
  payload: CrishErrorPayload,
  translate?: TranslateFn,
  currentLanguage?: SupportedLanguage
): UserVisibleError {
  const effectiveTranslate = translate ?? activeTranslateFn ?? undefined;
  const lang = currentLanguage ?? getGlobalActiveLanguage();
  const info = getErrorInfo(payload.code);

  // 1. 尝试使用 i18n 查表解析 Title
  let title = effectiveTranslate?.(`error.${payload.code}.title`);
  if (!title) {
    // 2. 未命中时，根据当前语言执行智能兜底
    title = lang === 'en-US' 
      ? (FALLBACK_TITLES_EN[payload.code] ?? 'Error')
      : info.title; // 中文环境下直接使用注册表的标准中文标题！
  }

  // 3. 尝试解析 Action
  let action = effectiveTranslate?.(payload.action);
  if (!action) {
    action = lang === 'en-US'
      ? (FALLBACK_ACTIONS_EN[payload.action] ?? 'Please try again or contact support.')
      : (FALLBACK_ACTIONS_ZH[payload.action] ?? '请尝试重试或联系技术支持。');
  }

  return {
    visible: payload.public,
    title,
    message: payload.message,
    action,
    retryable: payload.retryable,
    code: payload.code,
    severity: mapSeverity(payload),
  };
}
```
