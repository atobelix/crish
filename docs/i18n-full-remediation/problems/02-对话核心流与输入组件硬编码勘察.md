## 摘要与勘察概览

对话主界面是 Conex / Crish 客户端的核心使用场景。经地毯式代码扫描与 AST 遍历勘察，发现**对话主视图绝大部分仍处于完全写死的硬编码中文状态**：
- `ChatEmptyState.tsx` 虽然引入了 `useI18n()`，但实际上仅读取了 `chat.welcome`（欢迎）与 `chat.placeholder`（输入消息...）两个词条，且仅仅绑定到只读的 `data-greeting` 和 `data-placeholder` DOM 属性上，界面可见的标题、副标题、行动按钮（CTA）、无障碍读屏（`aria-label`）均来自 `apps/crish-desktop/src/api/chatEmptyState.ts` 中写死的中文常量。
- `ChatComposer`、`TiptapComposerField`、`ComposerNoticeBar`、`ComposerPermissionBar`、`PermissionModeMenu`、`DraftUndoToast` 等输入全家桶中，所有占位符、Tooltip、按钮文本、快捷命令、权限切换说明均硬编码中文。
- 消息气泡与交互行（`chat-message-row`）中，思维链耗时（`已思考 12s`）、缓存命中指标（`缓存命中 85% · 读 12,450`）、固定颜色选择器、用户消息撤回/重试、系统上下文注入标记全部硬编码。
- 工具调用卡片（`chat-tool-call`）与附件体系（`chat-attachment`）中，工具批量审批、差异平铺行折叠、命令输入输出截断提示、缺失附件警告等均大量使用裸字符串及中文模板字符串拼接。
- 汇总统计：在 4 个核心目录 + 1 个纯逻辑文件 + 2 个扩展目录中，共发现 **75 个文件** 存在硬编码中文字符串，涉及 **666+ 处代码行**，需提取与规范化的词条规模达 **280~320 个**。

   > = {
     'create-session': '新建对话',
     'clear-filter': '清除过滤',
   };
   ```
2. **`resolveChatEmptyCopy` 提前求值为纯中文文本**：
   函数在无任何 i18n 上下文的情况下，直接将静态中文硬编码拼入返回的 `ChatEmptyCopy` 对象：
   - `sub: firstRunOpen ? '完成引导后即可新建对话' : '新建一条开始对话'`
   - `sub: preview ? \`没有匹配「${preview}」的内容\` : '没有匹配的消息'`
   - `sub: '引擎未就绪，可先选项目或打草稿'` 等等。
3. **UI 组件层无法挂载翻译**：
   在 `ChatEmptyState.tsx` 中，组件虽然调用了 `const { t } = useI18n()`，但由于 `copy` 对象内部的 `title`、`sub`、`actionLabel` 均已是在纯逻辑层算好的裸中文，组件只能直接渲染 `{copy.title}` 与 `{copy.sub}`，国际化通道被物理切断。
4. **单测过度绑定中文字符串**：
   现有的 `useChatEmptyKind.test.ts` 以及相关空态单测，大量通过断言 `copy.title === '暂无会话'` 或 `copy.actionLabel === '新建对话'` 来判断行为，导致若直接粗暴改写函数签名，将破坏脱水单测。

### 2. 双层解耦方案（契约保持 + 键名/参数结构化）

为遵循 [`AGENTS.md`](../../AGENTS.md) §1.7「架构优雅、杜绝补丁」与立体验证纪律，推荐采取**双层契约解耦模型**：

```

## 四、词条规模评估与 `chat.*` 命名空间细分规划

### 1. 规模评估

- **当前现状**：`apps/crish-desktop/src/i18n/locales/zh-CN.ts` 中 `chat` 命名空间仅定义了 **14 个扁平词条**，仅占实际使用文本的不到 5%。
- **勘察汇总**：
  - `chat-composer` 域：约 70~80 个独立词条（含斜杠指令说明与权限模式说明）；
  - `chat-card` 与 `chatEmptyState` 域：约 85~95 个独立词条（含空态、筛选、头部控制、项目切换等）；
  - `chat-message-row` 域：约 45~55 个独立词条（含思维链、缓存指标、固定管理、撤回重试等）；
  - `chat-tool-call` 与 `chat-attachment` 域：约 60~70 个独立词条（含批量审批、差异平铺、输出截断保护、附件卡片等）；
  - 全链路扩展域（`chat-message-list`、定时任务卡片等）：约 30~40 个独立词条。
- **总词条规模**：预计需要新增并规范化 **280 ~ 320 个词条**。

### 3. 与 `common.*` 及 `error.*` 的正交复用规范

为避免词条膨胀与冗余翻译，必须明确与已有命名空间的协作边界：
1. **通用操作词收口至 `common.*`**：
   - 确定 (`common.ok`)、取消 (`common.cancel`)、保存 (`common.save`)、删除 (`common.delete`)；
   - 复制 (`common.copy`)、已复制 (`common.copied`)、重试 (`common.retry`)、加载中 (`common.loading`)、搜索 (`common.search`)；
   - 关闭 (`common.close`)、刷新 (`common.refresh`)、返回 (`common.back`)。
   - 组件层禁止在 `chat.*` 中重复声明 `chat.composer.copy` 等同质词条。
2. **底层错误码对接 `error.*`**：
   - 工具执行底层报错、模型服务连接超时、配额超限等，统一使用 `error.<domain>.<code_id>.title` 机制（配合 `utils/error-translation.ts`），不在 `chat.*` 中硬编码后端错误映射。

- **诚实**：
  - 本报告如实列出了 4 大指定核心范围的 666+ 处中文硬编码，包括具体文件名与行号。
  - 诚实指出“当前 `ChatEmptyState.tsx` 宣称的 i18n 支持实际仅读取了 2 个未渲染到页面的属性词条”，指出其虚胖与断层。
  - 诚实补充了 `chat-message`、`chat-message-list` 等与对话流强绑定的关联组件勘察，未隐瞒遗漏。
- **必做与禁做**：
  - 坚持“反退避”原则，不以“词条过多”、“工具调用输出过于底层”为由擅自砍减勘察范围。
  - 未动用 `--no-verify`，无任何破坏性代码操作，纯勘察产物落盘。
- **负责**：
  - 交付物边界清晰、可直接复查，包含详尽的行号证据。
  - 为下一阶段的方案设计提供了具体可落地的“双层契约解耦模型”与“命名空间树状设计”。

### 2. 对后续 Phase 2（方案期）与 Phase 7（实现期）的建议

1. **解耦先行**：在开始大规模替换 UI 文本前，必须首先在 Phase 2 完成 `api/chatEmptyState.ts` 的结构重构，确立类型契约与脱水单测；
2. **防回归门禁研发**：在 Phase 7 落地时，必须基于本勘察梳理出的文件列表，编写针对 `apps/crish-desktop/src/components/chat-*` 的 AST/正则扫描门禁脚本（`scripts/check-i18n-hardcoded.mjs`），硬性阻断新引入的中文裸字符串；
3. **英文排版弹性防爆**：英文文本长度普遍比中文长 30%~50%（如“新建会话”→“New Conversation”，“全部批准”→“Approve All”）。输入框底部融合胶囊（`ComposerFusedTrigger`）、状态浮条（`ChatStatusRibbons`）与微卡片（`AttachmentCard`）在 Phase 7 必须重点校验弹性布局，严禁出现布局折行错位或硬性截断省略号。
