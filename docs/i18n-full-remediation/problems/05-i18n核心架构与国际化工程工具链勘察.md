## 摘要与核心结论

本报告对 Conex / Crish 客户端当前前端国际化子系统（`apps/crish-desktop/src/i18n/`）的架构设计、扩展性瓶颈、类型安全体系、格式化工具链以及工程化支撑能力进行了全面深度的代码级穿透勘察。

**核心结论**：
1. **现状定性**：当前 i18n 子系统是一个**自研的轻量级样板实现（约 400 行代码，覆盖仅约 66 个强类型键与 33 个错误码）**。在初始阶段完成了基础的 Context 挂载、localStorage 持久化、单测防护与错误码桥接。
2. **承载极限断言**：**现有架构绝对无法直接承受全仓数千词条的规模化落地**。若不进行工程化改造，强行塞入上千词条将直接导致：
   - **Git 冲突风暴**：单一大文件（`zh-CN.ts` / `en-US.ts`）导致多 Agent / 开发者并行编辑必然高频锁死冲突；
   - **类型维护成本指数级爆炸**：现行“手写 Interface + 手写 zh-CN + 手写 en-US”的三处人工对齐机制彻底失效；
   - **高级语法表达残缺**：复数化（Pluralization）、本地化日期时间、数字货币、富文本（React 节点嵌入）完全缺失，导致业务层出现大量语法畸形的字符串拼接与假国际化；
   - **首屏 Bundle 脏膨胀**：所有语言包被静态打包入首屏 chunk，拖慢启动性能。
3. **改造定位**：必须在**保持零外部大依赖（拒绝引入庞大笨重的 i18next / formatjs 全家桶）**的前提下，升级为**模块化命名空间组织 + 基于单一真理源（SSOT）的 Paths 自动类型推导 + 基于原生 ECMAScript Intl API 的全功能格式化工具链**。

### 1.3 致命短板与架构瓶颈（深度证据穿透）

虽然在样板阶段表现良好，但当面对全仓 695 个 TSX 组件、上千个词条的全面多语言化时，暴露出以下 6 项致命短板：

#### 短板 1：单一大文件与多 Agent 协同冲突（扩展性死穴）
- **现象证据**：当前全部词典直接平铺在两个单体文件中：[`zh-CN.ts:1-120`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/locales/zh-CN.ts#L1-L120) 与 [`en-US.ts:1-122`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/locales/en-US.ts#L1-L122)。目前每个文件仅约 120 行、百余条目。
- **致命后果**：
  - 全仓拥有 15 个设置 Tab、完整的 ChatComposer、ChatMessageRow、各种 Tool 卡片、状态栏等。词条总量将达 **1,500 ~ 3,000 条**；
  - 单个文件将迅速膨胀至 3,000 ~ 5,000 行，极易触发仓库行数超标警报（`scripts/check-line-counts.mjs`）；
  - **严重违背多 Agent 协作纪律**：当 T01（设置体系）、T02（对话流）、T03（错误系统）、T04（底层渲染）等多个 Agent 并行开展修复时，所有人都在修改同一个 `zh-CN.ts` 和 `en-US.ts`，造成无法自动解决的 Git 合并冲突，彻底破坏并行生产力。

#### 短板 2：三处手工对齐维护，类型安全形同虚设
- **现象证据**：
  - 维护一处词条，需要开发者/Agent 同时修改三处：
    1. [`types.ts:19-98`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/types.ts#L19-L98)：手写 TypeScript 接口（如 `CommonTranslations`, `NavTranslations` 等）；
    2. [`zh-CN.ts:4-78`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/locales/zh-CN.ts#L4-L78)：填充中文文案；
    3. [`en-US.ts:4-78`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/locales/en-US.ts#L4-L78)：填充英文文案。
  - [`types.ts:120-131`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/types.ts#L120-L131)：
    ```ts
    export type KnownTranslationKey =
      | `common.${keyof CommonTranslations}`
      | `nav.${keyof NavTranslations}`
      | `chat.${keyof ChatTranslations}`
      | `settings.${keyof SettingsTranslations}`
      | `about.${keyof AboutTranslations}`
      | `workspace.${keyof WorkspaceTranslations}`;
    export type TranslationKey = KnownTranslationKey | (string & {});
    ```
- **致命后果**：
  - **动态键零类型保护**：`error.*` 与 `action.*` 命名空间在 `I18nDictionary` 中仅声明为 `Record<string, string> | undefined`（[`types.ts:107-108`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/types.ts#L107-L108)），完全被排除在 `KnownTranslationKey` 之外！IDE 在调用 `t('error.provider.network.title')` 时没有任何拼写检查与自动提示；
  - **插值参数无类型校验**：[`types.ts:133-139`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/types.ts#L133-L139) 的 `TranslateFunction` 将参数声明为通用 `Record<string, string | number>`。如果词条模板是 `"欢迎, {name}!"`，调用 `t('chat.welcome')` 漏传 `{ name }` 或传错成 `{ user }`，TypeScript 编译器完全静默，无法在编译期拦截运行时缺参漏洞；
  - **层级受限**：`KnownTranslationKey` 仅支持两层 `namespace.key` 模板字符串。当拆分到三层（如 `settings.appearance.theme.dark`）时，现有联合类型彻底失效。

#### 短板 3：键解析规则充满补丁式试错逻辑
- **现象证据**：[`I18nContext.tsx:40-92`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/I18nContext.tsx#L40-L92) 的 `resolveDictionaryKey` 函数：
  ```ts
  // 1. 尝试直接以整 key 读取
  const direct = dict[key];
  // 2. 尝试首段作为 namespace，剩余作为子 key（如 error 域：error["provider.network.title"]）
  const firstDot = key.indexOf('.');
  // 3. 尝试多层点号逐级遍历
  const parts = key.split('.');
  ```
- **架构根因**：
  之所以会有第 2 种“首段截断 + 剩余子 key”的奇怪分支，是因为现有字典结构设计**自相矛盾**：`common` / `chat` 采用嵌套对象，而 `error` / `action` 却在子对象中保留了点号扁平键（如 `dict.error['common.unknown.title']`，见 [`zh-CN.ts:80-84`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/locales/zh-CN.ts#L80-L84)）。
  这是一种典型的“用运行时试错遍历来掩盖数据结构不一致”的补丁式妥协（违反 `AGENTS.md` §1.7“严禁打补丁、绕过与作弊”）。在数千词条的频繁查找下，这种多轮分支尝试带来无谓的性能开销。

#### 短板 4：高级格式化能力完全真空（复数、日期、数字、富文本）
- **现象证据**：
  1. **复数化（Pluralization）缺失**：
     现有插值 [`I18nContext.tsx:24-35`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/I18nContext.tsx#L24-L35) 仅用简单正则表达式 `replace(/\{([a-zA-Z0-9_]+)\}/g)` 做粗暴字符串替换。系统完全不知道什么是单复数。
     - 导致业务代码中出现大量的中文单位硬编码：如 [`AgentBrowsePad.tsx:66`](file:///c:/Software/conex/apps/crish-desktop/src/components/agent-card/AgentBrowsePad.tsx#L66) `<Tooltip content={'共 ${agents.length} 个'}>`、[`ApprovalPayloadSection.tsx:109`](file:///c:/Software/conex/apps/crish-desktop/src/components/agent-card/ApprovalPayloadSection.tsx#L109) `…等共 {deleteImpact.targets.length} 个目标`；
     - 英文中当数量为 1 时是 `1 target`，数量 > 1 时是 `5 targets`。缺少复数化机制导致无法用标准方式表达英文语法。
  2. **日期时间（DateTime）格式化无序与环境脱节**：
     - [`chatMessageRowUtils.ts:49`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-message-row/chatMessageRowUtils.ts#L49)：
       `date.toLocaleTimeString([], { hour: '2-digit', minute: '2-digit', hour12: false })`
       传空数组 `[]` 导致直接读取宿主操作系统语言，而非客户端内用户选择的 `language`！如果中文系统用户在 Crish 设置中选择了 English，时间格式仍然被渲染为中文 OS 习惯；
     - [`toolOutputParser.ts:71-86`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-tool-call/toolOutputParser.ts#L71-L86)：
       `formatTimestamp` 手写 `pad(d.getMonth() + 1)` 拼装 `YYYY-MM-DD HH:mm:ss`，完全硬编码。
  3. **数字、货币与字节（Bytes）硬编码中文**：
     - [`toolOutputParser.ts:57-66`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-tool-call/toolOutputParser.ts#L57-L66)：
       ```ts
       export function formatBytes(bytes: number): string {
         if (!Number.isFinite(bytes) || bytes < 0) return '0 字节';
         if (bytes < 1024) return `${bytes} 字节`;
         ...
         return `${mb} MB (${bytes.toLocaleString()} 字节)`;
       }
       ```
       直接在工具库中硬编码了 `'0 字节'`、`'${bytes} 字节'`，语言切换为英文后依然展示中文“字节”！
  4. **富文本插值（Rich Text / JSX）完全不可用**：
     - `t()` 返回值类型为严格 `string`。如果文案中包含链接或强调文字（例如：“查看[开源协议]或前往[设置]”），业务组件无法在翻译句子内部嵌套 `<a href="...">` 或 `<button>`，导致开发者只能采用违规的“拆散为 3 段字符串再拼接组件”的下策，破坏国际化语序一致性。

#### 短板 5：函数签名重载模糊易错
- **现象证据**：[`types.ts:135-139`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/types.ts#L135-L139)：
  ```ts
  export type TranslateFunction = (
    key: TranslationKey,
    fallbackOrParams?: string | TranslationParams,
    params?: TranslationParams
  ) => string;
  ```
- **隐患**：通过 `typeof fallbackOrParams === 'object'` 动态猜测第二个参数是 fallback 还是 params。
  如果开发者传错参数顺序，或者传了一个既非 string 也非简单纯对象的特殊值，将产生难以察觉的静默回退 bug。

#### 短板 6：全局状态同步冗余与打包无代码分割
- **现象证据**：
  1. [`I18nContext.tsx:203-212`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/I18nContext.tsx#L203-L212)：
     ```ts

       setLanguageState(lang);
       persistLanguage(lang);
     ```

  2. [`locales/index.ts:7-10`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/locales/index.ts#L7-L10)：

     直接在模块加载时将 `zhCN` 与 `enUS` 全部打包在主入口 chunk 中。目前只有几 KB 无关痛痒，但在上千词条且未来规划支持多国语言时，全量静态打入首屏将浪费客户端初始解析性能与内存。

### 2.2 命名空间划分职责矩阵与 Agent 隔离

通过文件物理隔离，彻底切断并行修改同一文件的冲突隐患：

| 命名空间 | 归属文件 | 包含范畴与对应功能域 | 对应勘察/实现角色 |
| :--- | :--- | :--- | :--- |
| `common` | `locales/{lang}/common.ts` | 确定、取消、保存、删除、搜索、刷新、复制、成功/失败提示等基础词条 | 基础公共层 |

### 3.2 深度受控的 Paths<T> 类型推导器（防编译死锁）

在大型项目中，无限制的递归类型会导致 TypeScript 语言服务严重变慢甚至崩溃。针对 Crish 词典深度不超过 4 层的特征，设计**深度严格受限（Depth-Guarded）的紧凑 Paths 提取器**：

```ts
type PrevDepth = [never, 0, 1, 2, 3];

type JoinPath<K, P> = K extends string | number
  ? P extends string | number
    ? `${K}${'' extends P ? '' : '.'}${P}`
    : never
  : never;

export type Paths<T, Depth extends number = 3> = [Depth] extends [never]
  ? never
  : T extends Record<string, unknown>
  ? {
      [K in keyof T]-?: K extends string
        ? T[K] extends Record<string, unknown>
          ? JoinPath<K, Paths<T[K], PrevDepth[Depth]>>
          : K
        : never;
    }[keyof T]
  : '';

/** 自动提取的强类型 KnownTranslationKey，享受完整的 IDE 智能提示与拼写守卫 */
export type KnownTranslationKey = Paths<AppLocaleDictionary>;

/** 既提供强类型提示，又支持动态后端错误码或插件扩展键 */
export type TranslationKey = KnownTranslationKey | (string & {});
```

### 3.3 模板插值参数编译期强约束

通过 TypeScript 模板字面量推导能力，从文案中自动提取 `{param}` 占位符，实现“有占位符则必传参数，无占位符则禁止多传”的极致安全：

```ts
type ExtractParams<T extends string> =
  T extends `${string}{${infer Param}}${infer Rest}`
    ? { [K in Param | keyof ExtractParams<Rest>]: string | number }
    : undefined;

// 改进后的 t 函数重载定义
export interface TypedTranslateFunction {
  <K extends KnownTranslationKey>(
    key: K,
    ...args: ExtractParams<PathValue<AppLocaleDictionary, K>> extends undefined
      ? [fallbackOrParams?: string | Record<string, string | number>]
      : [params: ExtractParams<PathValue<AppLocaleDictionary, K>>, fallback?: string]
  ): string;

  // 动态字符串兜底签名
  (key: string & {}, fallbackOrParams?: string | Record<string, string | number>, params?: Record<string, string | number>): string;
}
```

### 4.1 复数化引擎（`Intl.PluralRules`）

#### 机制设计
根据不同语言的语法规则（如英文 1 个为 `one`，其余为 `other`；俄语分为 `one` / `few` / `many` / `other`；中文全为 `other`），自动匹配词典分支：

```ts
// apps/crish-desktop/src/i18n/formatters/plural.ts
export interface PluralOptions {
  count: number;
  params?: Record<string, string | number>;
}

export type PluralDictionaryEntry = {
  zero?: string;
  one?: string;
  two?: string;
  few?: string;
  many?: string;
  other: string;
};

const pluralRulesCache = new Map<string, Intl.PluralRules>();

function getPluralRules(locale: string): Intl.PluralRules {
  let rules = pluralRulesCache.get(locale);
  if (!rules) {
    rules = new Intl.PluralRules(locale);
    pluralRulesCache.set(locale, rules);
  }
  return rules;
}

export function formatPlural(
  locale: string,
  entry: PluralDictionaryEntry | string,
  options: PluralOptions
): string {
  if (typeof entry === 'string') {
    // 语言不支持复数变化或简易配置时，直接按普通插值回退
    return interpolate(entry, { count: options.count, ...options.params });
  }

  const rules = getPluralRules(locale);
  const category = rules.select(options.count);
  const template = entry[category] ?? entry.other;
  return interpolate(template, { count: options.count, ...options.params });
}
```

#### 词典定义示例
```ts
// locales/en-US/units.ts
export default {
  items: {
    one: '{count} item',
    other: '{count} items',
  },
  filesScanned: {
    one: '{count} file scanned',
    other: '{count} files scanned',
  },
};

// locales/zh-CN/units.ts
export default {
  items: '共 {count} 项',
  filesScanned: '已扫描 {count} 个文件',
};
```
在业务中使用 `tPlural('units.items', { count: total })`，中英文即可得到完美的语法输出，彻底根除 `item(s)` 这种粗劣的拼凑写法。

### 4.2 日期与时间本地化（`Intl.DateTimeFormat` & `RelativeTimeFormat`）

彻底废除 `date.toLocaleTimeString([])` 传空数组导致读取操作系统语言的缺陷。

```ts
// apps/crish-desktop/src/i18n/formatters/datetime.ts
export type DatePreset = 'time-short' | 'date-short' | 'datetime-medium' | 'datetime-full';

const PRESET_OPTIONS: Record<DatePreset, Intl.DateTimeFormatOptions> = {
  'time-short': { hour: '2-digit', minute: '2-digit', hour12: false },
  'date-short': { year: 'numeric', month: '2-digit', day: '2-digit' },
  'datetime-medium': {
    year: 'numeric',
    month: '2-digit',
    day: '2-digit',
    hour: '2-digit',
    minute: '2-digit',
    second: '2-digit',
    hour12: false,
  },
  'datetime-full': {
    year: 'numeric',
    month: 'long',
    day: 'numeric',
    weekday: 'long',
    hour: '2-digit',
    minute: '2-digit',
  },
};

export function formatDate(
  locale: string,
  date: Date | number,
  presetOrOptions: DatePreset | Intl.DateTimeFormatOptions = 'datetime-medium'
): string {
  const d = typeof date === 'number' ? new Date(date) : date;
  if (isNaN(d.getTime())) return '-';

  const options =
    typeof presetOrOptions === 'string'
      ? PRESET_OPTIONS[presetOrOptions]
      : presetOrOptions;

  return new Intl.DateTimeFormat(locale, options).format(d);
}

export function formatRelativeTime(
  locale: string,
  value: number,
  unit: Intl.RelativeTimeFormatUnit
): string {
  const rtf = new Intl.RelativeTimeFormat(locale, { numeric: 'auto' });
  return rtf.format(value, unit);
}
```

改造后，`chatMessageRowUtils.ts` 中的 `formatMsgTime` 直接接入：
```ts

  if (!ts) return '';
  return formatDate(lang, ts, 'time-short');
}
```
确保始终与应用内设定的语言环境步调一致。

### 4.4 字节尺寸格式化重构（清退硬编码中文）

针对 [`toolOutputParser.ts:57-66`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-tool-call/toolOutputParser.ts#L57-L66) 的 `'0 字节'` 硬编码，设计专门的国际化 `formatBytes`：

```ts
// apps/crish-desktop/src/i18n/formatters/bytes.ts
export function formatBytesLocalized(
  locale: string,
  bytes: number,
  t: (key: string, params?: Record<string, string | number>) => string
): string {
  if (!Number.isFinite(bytes) || bytes < 0) {
    return t('units.bytesZero', { defaultValue: '0 B' });
  }

  const numFormatted = new Intl.NumberFormat(locale).format(bytes);
  if (bytes < 1024) {
    return t('units.bytesExact', { count: bytes, formatted: numFormatted, defaultValue: `${numFormatted} B` });
  }

  const k = 1024;
  const sizes = ['B', 'KB', 'MB', 'GB', 'TB'];
  const i = Math.floor(Math.log(bytes) / Math.log(k));
  const val = (bytes / Math.pow(k, i)).toFixed(i === 1 ? 1 : 2);

  return `${val} ${sizes[i]} (${numFormatted} B)`;
}
```

### 4.5 轻量富文本组件（`<Trans />`）

为了在翻译文案中安全嵌入 React 组件（如将 `请查看 <link>开源声明</link> 以了解详情` 渲染为点击跳转），编写一个不依赖外部第三方的轻量 `<Trans />` 组件：

```tsx
// apps/crish-desktop/src/i18n/components/Trans.tsx
import React from 'react';
import { useI18n } from '../useI18n';
import type { KnownTranslationKey } from '../types';

export interface TransProps {
  i18nKey: KnownTranslationKey | (string & {});
  components?: Record<string, React.ReactElement>;
  values?: Record<string, string | number>;
  fallback?: string;
}

export const Trans: React.FC<TransProps> = ({ i18nKey, components = {}, values = {}, fallback }) => {
  const { t } = useI18n();
  const rawText = t(i18nKey, fallback ?? i18nKey, values);

  // 匹配形如 <link>文本</link> 或 <bold>文本</bold> 的标签
  const tagRegex = /<([a-zA-Z0-9_]+)>(.*?)<\/\1>/g;
  const parts: React.ReactNode[] = [];
  let lastIndex = 0;
  let match: RegExpExecArray | null;

  while ((match = tagRegex.exec(rawText)) !== null) {
    // 放入匹配项前面的纯文本
    if (match.index > lastIndex) {
      parts.push(rawText.substring(lastIndex, match.index));
    }

    const tagName = match[1];
    const innerContent = match[2];
    const targetComponent = components[tagName];

    if (targetComponent) {
      // 克隆注入组件并替换子节点
      parts.push(React.cloneElement(targetComponent, { key: `trans-${match.index}` }, innerContent));
    } else {
      parts.push(innerContent);
    }
    lastIndex = tagRegex.lastIndex;
  }

  if (lastIndex < rawText.length) {
    parts.push(rawText.substring(lastIndex));
  }

  return <>{parts}</>;
};
```
该组件实现仅约 40 行，通过原生正则解析与 `React.cloneElement` 完美解决了富文本嵌入的国际化难题，同时避免拆词拼接。

## 五、性能、热更新与加载架构评估

### 5.1 语言切换时的 Context 渲染范围优化

1. **现状评估**：
   在 [`I18nContext.tsx:222-229`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/I18nContext.tsx#L222-L229) 中：
   ```ts
   const value = useMemo<I18nContextValue>(() => {
     return { language, setLanguage, t, dictionary };
   }, [language, setLanguage, t, dictionary]);
   ```
   - 上下文中直接透传了 `dictionary` 整个庞大对象。
   - 尽管语言切换本来就需要触发 UI 文本刷新，但很多纯逻辑或工具组件（如只调用 `setLanguage` 进行设置切换的选项卡）并不需要读取全部字典。
2. **优化建议**：
   - 建议将 Context 拆分为两个轻量级通道：
     - `I18nStateContext`：提供 `{ language, t, formatDate, formatNumber, tPlural }`（只包含文本消费方法，不包含庞大字典数据）；
     - `I18nDispatchContext`：提供 `{ setLanguage }`（引用永久稳定，设置语言的组件不会因为语言切换而重渲染）。
   - 将 `dictionary` 降为内部实现细节，不再暴露给普通业务 Hook，节约内存引用传递。

### 5.2 打包体积（Bundle Size）与内存占用核算

- **数千词条容量测算**：
  - 预计全仓总词条量：约 1,500 ~ 2,500 条。
  - 中文包体大小：约 120 KB（纯文本）。
  - 英文包体大小：约 180 KB（英文单词字符较长）。
  - 双语静态合并入 bundle：总增量约 300 KB，Vite 构建后 Gzip 压缩量仅约 **45 KB**。
- **打包策略裁决**：
  - **当前阶段（zh-CN + en-US 双语）**：**保持同步静态打包最为明智**。无需引入异步 `import()` 加载瀑布，消除网络或磁盘延迟带来的首屏文案闪烁（FOUC, Flash of Unstyled Content）。
  - **未来演进（10+ 语种扩展时）**：在 `locales/index.ts` 中抽象出 `loadLocale(lang: SupportedLanguage): Promise<I18nDictionary>` 动态加载接口，使小众语言按需动态 import。
