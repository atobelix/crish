## 二、深度专项技术分析（穿透表象，根因深挖）

### 2.1 专项 1：SettingsAboutTab 拥有字典却完全未接入的技术根因与架构教训

在现有代码库中，[`apps/crish-desktop/src/i18n/types.ts`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/types.ts#L89-L98) 中明确定义了 `AboutTranslations` 接口，且 [`locales/zh-CN.ts`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/locales/zh-CN.ts#L69-L78) 与 [`locales/en-US.ts`](file:///c:/Software/conex/apps/crish-desktop/src/i18n/locales/en-US.ts#L69-L78) 均提供了该字典的具体实现：
```ts
// src/i18n/types.ts
export interface AboutTranslations {
  appVersion: string;
  kernelVersion: string;
  openSourceLicense: string;
  viewLicense: string;
  viewThirdParty: string;
  noticeTitle: string;
  copySysInfo: string;
  sysInfoCopied: string;
}
```

然而，查阅 [`apps/crish-desktop/src/components/settings/SettingsAboutTab.tsx`](file:///c:/Software/conex/apps/crish-desktop/src/components/settings/SettingsAboutTab.tsx#L1-L30) 发现，该文件**完全没有引入 `useI18n` 或任何国际化 hook**，所有文本均直接以中文硬编码。

#### 深度原因穿透：
1. **架构孤岛与流水线脱节**：
   通过 `git log` 溯源可见，`SettingsAboutTab.tsx` 是在一次性合规整治任务（P1-LIC-02，开源合规披露）中由专门负责协议合规的开发者编写并提交的。当时的关注点主要集中在法律文本准确性（MPL-2.0 第 3.1/3.2 条声明、SIL OFL-1.1 字体授权、各大 LLM 商标合理使用 Fair Use 声明等），导致该模块与处于样板阶段的 `i18n` 子系统产生了认知孤岛，未能形成跨组件的强制接入规范。
2. **字典粒度严重错位（粗粒度 vs 细粒度长篇实体）**：
   预留的 `AboutTranslations` 仅有 8 个粗粒度键值（如 `appVersion`, `viewThirdParty`），而实际组件渲染了庞大的合规数据结构：
   - 依赖项列表数组 `MPL_DEPENDENCIES` 及其中的字段 `description`（例如 L113：*'固定容量的高效位图数据结构'*、L119：*'符合 CSS Syntax Level 3 规范的解析器'*）；
   - 随附字体数组 `BUNDLED_FONTS`；
   - 包含多段法律免责声明的长文本（L284-288 的商业模型商标合理使用声明、L396-398 的 MIT 许可证中文解释）；
   - 模态弹窗与手风琴交互的复合状态按钮（L422：`isExpanded ? '收起第三方许可证' : '查看第三方许可证'`、L433：`弹窗查看完整协议`）。
   因为现有字典架构根本承载不了这些结构化长文本，开发者在实现时面临“要接入就必须重构整个 i18n 类型契约”的阻力，最终选择退避，直接硬编码。
3. **缺少自动化门禁阻断（Lint Gate Missing）**：
   仓库现有的 CI 检查（`npm run typecheck` / `npm test`）对 TSX 文件中的裸中文字符串零感知。静态检查全绿掩盖了严重的国际化欠债，使得未接入 i18n 的代码能够长驱直入主干。

### 2.2 专项 2：UserProfileCard 的 aria-label 拼接中文硬伤分析

在 [`apps/crish-desktop/src/components/sidebar/UserProfileCard.tsx`](file:///c:/Software/conex/apps/crish-desktop/src/components/sidebar/UserProfileCard.tsx#L31-L52) 中，存在一段极具代表性的“伪国际化”中英混杂代码：
```tsx
const roleLabel = t('workspace.guestUser', '访客用户');
const tooltip = t('workspace.settingsNav', '设置导航');

const activeUser =
  (isLoggedIn && user?.email
    ? user.name || user.email.split('@')[0]
    : username) || roleLabel;

return (
  <SettingsQuickMenu
    renderTrigger={({ open, triggerProps }) => (
      <Tooltip content={tooltip} disabled={open}>
        <Button
          bare
          type="button"
          className={`${styles.userProfileCard}${open ? ` ${styles.isOpen}` : ''}`}
          data-testid="user-profile-card"
          data-role={roleLabel}
          data-tooltip={tooltip}
          aria-label={`用户卡片：${activeUser} (${roleLabel})，点击打开${tooltip}`}
          {...triggerProps}
        >
```

#### 深度硬伤分析：
1. **中英混杂的“科学怪人”式字符串（Chinglish Frankenstein String）**：
   当用户在设置中将语言切换为英文（`en-US`）时：
   - `roleLabel` 被正确翻译为 `"Guest User"`；
   - `tooltip` 被正确翻译为 `"Settings Navigation"`；
   - 但外层的模板字符串直接硬编码了中文前缀与连接符：`用户卡片：... (...)，点击打开...`！
   最终生成的 `aria-label` 为：
   ```
   "用户卡片：Developer (Guest User)，点击打开Settings Navigation"
   ```
2. **屏幕阅读器发音灾难（Accessibility Disaster）**：
   视障用户在使用英文操作系统和屏幕阅读器（如 Windows Narrator、NVDA、macOS VoiceOver）时，合成语音引擎会将语言设定为 English。当读到该节点时，英文 TTS 引擎会遭遇未标记语言属性的汉字，导致发音严重畸变、机械读音或直接静音跳过，使得无障碍辅助完全失效。
3. **语序与标点符号硬编码违背跨语言语法**：
   中文使用全角冒号 `：`、全角括号 `（）` 和逗号 `，`；英文语法习惯使用半角冒号与空格 `: `、半角括号 `()` 与逗号空格 `, `。此外，英文动词往往前置（例如 `Click to open {target}`）。在代码中直接写死模板拼接彻底剥夺了翻译器重组句子语序的能力。
4. **规范解决方案**：
   必须在字典中定义完整的参数化词条，彻底消灭代码中的裸字符串拼接：
   ```ts
   // 命名空间：sidebar.userCard.ariaLabel
   // zh-CN: '用户卡片：{user} ({role})，点击打开{target}'
   // en-US: 'User card: {user} ({role}), click to open {target}'
   aria-label={t('sidebar.userCard.ariaLabel', {
     user: activeUser,
     role: roleLabel,
     target: tooltip
   })}
   ```

### 2.4 专项 4：动态模板与字符串插值硬编码隐患

在侧栏和设置项中，广泛存在动态逻辑运算与字符串拼接的隐患，必须由主方案统一收敛：

1. **定时任务绑定文案（SessionRow.tsx:96）**：

   const tooltipText = `已绑定 ${activeCount} 个运行中定时任务：${activeList.map((w) => w.name).join('、')}`;

   - 语法硬编码：英文连接词应使用逗号加空格 `, `，而非中文顿号 `、`；

2. **分支会话标题正则替换（SessionRow.tsx:270, 299）**：

   const displayText = baseTitle.replace(/ - 分支$/, '');

   ? `分支会话：${displayText}`

3. **快捷菜单状态与底栏更新提示（SidebarFooter.tsx:23-24）**：

## 三、英文膨胀（English Expansion）与 UI 排版风险评估

在完成多语言化后，英文字符串相较于紧凑的中文表意文字，**平均字符长度与物理排版宽度将膨胀 30% 至 70%**。本节对关键容器的排版风险进行地毯式几何测算。

### 3.1 弹窗侧栏导航（SettingsSidebar）物理宽度瓶颈

在 [`apps/crish-desktop/src/styles/tokens.css:590`](file:///c:/Software/conex/apps/crish-desktop/src/styles/tokens.css#L590) 与 [`SettingsPanel.module.css:68`](file:///c:/Software/conex/apps/crish-desktop/src/components/settings/SettingsPanel.module.css#L68) 中：
```css
--settings-nav-width: 220px; /* 设置弹窗左侧导航固定宽 */
```
#### 空间测算：
- 容器总宽：`220px`
- 导航内边距：左右合计 `var(--space-2) + var(--space-2_5) = 8px + 10px = 18px`
- Tab 按钮内边距：左右合计 `var(--space-2) * 2 = 16px`
- 图标容器宽度及间距：`20px + var(--space-2)(8px) = 28px`
- **文本可用物理净宽**：`220 - 18 - 16 - 28 = 158px`。

#### 膨胀风险对照表：
| Tab 标识 | 中文原案 (约 14px) | 预计宽度 | 英文标准术语 | 英文预计宽度 (14px Sans) | 超限与排版隐患 |
| :--- | :--- | :---: | :--- | :---: | :--- |
| `diagnostics` | 状态诊断 | 56px | **Status Diagnostics** | **145px** | 临界，极易因不同系统字体溢出 |
| `devices` | 多端互通 | 56px | **Connected Devices** | **142px** | 接近 158px 上限 |
| `personalize` | 通用设置 | 56px | **General Preferences** | **162px** | **严重超限 (溢出 4px)** |
| `schedule` | 定时任务 | 56px | **Scheduled Tasks** | **132px** | 正常 |
| `shortcuts` | 快捷键 | 42px | **Keyboard Shortcuts** | **158px** | **临界触顶** |
| `security` | 安全 | 28px | **Security & Access** | **138px** | 正常 |

#### 代码缺陷与后果：
在 [`SettingsPanel.module.css:328-353`](file:///c:/Software/conex/apps/crish-desktop/src/components/settings/SettingsPanel.module.css#L328-L353) 中，`.sidebarTab` 设置了固定高度 `height: var(--control-height);`，但**完全没有声明 `white-space: nowrap`、`overflow: hidden` 或 `text-overflow: ellipsis`**！
一旦英文字符串超出 158px，文字将发生折行，导致双行文字与单行 32px 高度容器发生严重的垂直溢出与图标对齐变形！

## 四、词条命名空间规范与架构契约设计

### 4.1 命名空间划分总则

- `sidebar.*`：桌面主侧边栏、用户卡片、会话列表、项目分组、右键上下文菜单。

## 六、治理与系统性解耦重构建议

为了让后续 `Phase 2（方案）` 与 `Phase 7（实现）` 能够高效率、零返工平稳落地，针对本勘察发现的核心架构问题，提出以下 4 项系统性解耦与重构建议：

### 6.1 SchemaRenderer 国际化协议升级（解决 Tab 02 与动态表单）
- **问题现状**：`SettingsSchemaRenderer` 及 `useAppearanceSchema` 接收的 `SchemaSection` 结构中，`title` / `desc` / `options[].label` 全部被声明为静态 `string`。
- **解耦方案**：
  1. 扩展 `SchemaProperty` 支持 `i18nKey?: string` 与 `title?: React.ReactNode` 双模式；
  2. `useAppearanceSchema` 内部注入 `t: TranslateFunction`，所有 Label 统一使用 `t('settings.appearance.xxx')` 赋值；
  3. 彻底清退 `SettingsAppearanceTab.tsx` 中 `language === 'zh-CN' ? ... : ...` 的内联三元表达式，建立统一的 Schema 国际化标准范式。

### 6.2 扩展 settingsTabsMeta 为响应式/注入式 Provider（解决 Tab 元数据与搜索）
- **问题现状**：`TAB_META` 是模块顶层的静态只读常量数组，中文标签与拼音搜索词写死。
- **解耦方案**：
  1. 将 `TAB_META` 抽象为纯静态结构定义（仅包含 `id`、`icon`、`groupKey`、`i18nKey`）；
  2. 新增 `useSettingsTabs()` hook，在运行时结合当前语言动态计算带有本地化 `label` 与多语言搜索关键字的 `LocalizedTabMeta[]`；
  3. 确保搜索算法 `tabMatchesQuery` 同时支持英文匹配、中文拼音匹配与多语言别名检索。

### 6.3 构建“零裸硬编码中文”AST 自动化门禁（防回归测试矩阵）
- **问题现状**：缺乏门禁是 `SettingsAboutTab` 拥有字典却完全未接入的核心诱因。
- **治理方案**：
  1. 在 `scripts/` 下实现基于 Babel AST / TypeScript Compiler API 的源码检查脚本 `check-i18n-hardcoded.mjs`；
  2. 针对 `apps/crish-desktop/src/components/settings/` 与 `apps/crish-desktop/src/components/sidebar/` 目录设立刚性门禁：**任何新入库或修改的 TSX 文件若包含未包裹在注释/豁免名单中的中文字符，直接阻断 CI**；
  3. 建立 Missing Keys 双向核对门禁，确保 `zh-CN.ts` 与 `en-US.ts` 键集合 100% 对齐。

### 6.4 CSS 弹性排版与容错改造（抵御英文膨胀）
- **问题现状**：侧栏 Tab `.sidebarTab` 与主侧栏 `.navItem` 缺失文字截断保护，高度固定导致英文换行崩塌。
- **改造方案**：
  1. 为 `.sidebarTab` 与 `.navItem` 内的文字 `span` 强制注入：
     ```css
     white-space: nowrap;
     overflow: hidden;
     text-overflow: ellipsis;
     min-width: 0;
     flex: 1 1 auto;
     ```
  2. 对由于截断可能看不全的文本，外层统一挂载 `<Tooltip content={tab.label}>`，实现“长文本截断但悬停完整可读”的用户体验；
  3. 针对 `--settings-nav-width`，建议自适应放宽至 `clamp(220px, 25vw, 260px)`，以原生容纳更长的国际化术语。
