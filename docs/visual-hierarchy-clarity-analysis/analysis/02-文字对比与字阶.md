## 结论摘要（先行）

1. **正文人工降暗与过程行强制同构，直接造成主次层级全面塌平**  
   在暗色模式下，Crish 源码 [`tokens.css:1142`](file:///c:/Software/conex/apps/crish-desktop/src/styles/tokens.css#L1142) 通过 `color-mix(in srgb, var(--user-text-primary) 80%, black)` 将最亮主正文强行掺入 20% 纯黑，实测前景值从未压缩的 `#f5f5f5`（对比度 16.9:1）骤降为 `#c4c4c4`（对比度 10.56:1），使主阅读内容缺乏清晰高光；更关键的是，2026-09-11 的历史裁决（见 [`ChatToolCallBlock.module.css:2-9`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-tool-call/ChatToolCallBlock.module.css#L2-L9) 与 [`ReasoningRow.module.css:160-167`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-message-row/ReasoningRow.module.css#L160-L167)）强制要求过程区（思考行、工具调用行）字号一律放大至 14px、字重 400，导致正文与过程信息在字号（同为 14px）、字重（同为 400）上完全同构，人眼扫视时无法在 50ms 内依据轮廓切分主次。

2. **弱阶文字全面跌破 WCAG 2.1 AA 最低可读性门槛（3.02:1 < 4.5:1）**  
   暗色主题下 `--text-tertiary`（掺黑 60%，实测 `#626262`）在主聊天区 `#141414` 上的 WCAG 对比度仅为 **3.02:1**（中位数甚至低至 2.15:1~2.39:1），在侧栏 `#1e1e1e` 底色上更是跌至 **2.73:1**，严重违反 WCAG 2.1 AA 针对正常字号文本要求的 4.5:1 底线；导致思考耗时、工具执行详情、侧栏会话日期（如 `9/18`）严重发虚，强光或普通显示器下几不可辨。

3. **字阶步长过于细碎（1px 级差），且字面量与半像素严重违规绕过 Token**  
   设计系统在常用区间（xxs~base）步长仅为 1px（11px → 12px → 13px → 14px），人眼在正常视距下根本无法建立层级感知；更严重的是代码库存在大量硬编码绕过 token：统计发现代码中散落了 56 处 `11px`、32 处 `14px`、30 处 `12px`、16 处 `13px`、13 处 `10px`，甚至存在 `10.5px`（4 处）、`11.5px`（4 处）、`12.5px`（4 处）等难以渲染整齐的半像素字面量。

4. **Windows 环境下 CJK 字体物理字形缺失，导致 400 vs 500 的微弱字重阶梯彻底失效**  
   代码中高频使用 `font-weight: 500`（达 270+ 处）试图在不改字号的情况下区分标签、激活态与标题。但在 Windows 系统中，系统回退中文字体微软雅黑（`Microsoft YaHei`）仅包含 Regular (400) 和 Bold (700) 两个物理字形，不存在 Medium (500) 或 SemiBold (600)。WebView2 渲染中文字符时将 500 直接回退为 400（或劣质算法伪加粗），致使依靠字重建立的微妙层级在 Windows 桌面端全面塌缩。

5. **参考界面（Codex）执行「17.5:1 纯白正文 + 12px/6.9:1 过程行 + 严密 3:1 阶梯跨度」**  
   Codex 正文采用高对比白 `#FDFDFD`（实测 WCAG 17.5:1），过程单行采用低对比灰色 `#A2A2A2`（实测 WCAG 6.96:1，字号 12px）；右侧子任务卡片形成「标题 17.6:1（14px 加粗）/ 描述 8.0:1（12px 常规）/ 时间戳 5.0:1（11px 极弱）」的严格三层单调衰减阶梯，整屏视觉节奏清脆利落。

## 参考界面做对了什么（具体）

参考截图中 Codex 界面展现出高度清晰、呼吸感良好的视觉层级，其核心技术做对了以下四点：

### 1. 纯白高光正文与极端克制的过程信息（2.5倍对比度跨度）
- **正文高光突显**：在 [`ref-codex.png`](file:///c:/Software/conex/docs/visual-hierarchy-clarity-analysis/evidence/ref-codex.png) 中，Assistant 的回答正文（如 `全量 npm run test 已通过: 1046 个测试文件通过...`、`前端静态门禁发现 1 个行数违规...`）采用接近纯白的颜色（实测像素核心为 `#FDFDFD` / `#FEFEFE`），在 `#181818` 的深色背景上获得了高达 **17.46:1 ~ 17.61:1** 的极致对比度。文字锐利清脆，第一眼便能抓住视线。
- **过程行退居背景**：单行过程提示（如 `Import failure state已完成`、`运行了命令`、`编辑了文件运行了命令`）的前景颜色压低至 `#A2A2A2`（实测 WCAG 为 **6.96:1**，满足 AA 但明显弱于正文），实测字高仅 12px，且使用紧凑的单行容器。
- **2.5 倍对比度落差形成天然视觉漏斗**：正文亮度与过程行亮度比例达到 2.5:1。读者在扫视时无需逐字阅读，大脑能自动过滤灰色的过程信息，直接跳读至高亮正文。

### 2. 子任务面板（Right Panel）的三级严格单调视觉阶梯
在 Codex 右侧子智能体面板中，每一个任务项都遵循严格的「大小 + 字重 + 明度」三维一体阶梯，没有任何两个层级发生混淆：
1. **Tier 1 任务标题**（如 `Startup graph analysis`、`Asset scope sync fix`）：
   - 字号：~14px，字重：Medium/SemiBold（500/600），前景色：`#FFFEFE`（**17.64:1**）。
2. **Tier 2 执行动作描述**（如 `checking modelVendor chunk size`、`checking library exports`）：
   - 字号：~12px，字重：Regular（400），前景色：`#AEAEAE`（**8.00:1**）。
3. **Tier 3 状态与时间戳 / 分组标题**（如 `1m 8s`、`2分钟前`、`已开启 · 2`、`完成 · 20`）：
   - 字号：~11px，字重：Regular（400），前景色：`#888889`（**5.01:1**）。
这三个层级在亮度上严格递减（17.6:1 → 8.0:1 → 5.0:1），字号严格递减（14px → 12px → 11px），形成干净干练的排版结构。

### 3. 微状态色彩（Accent Indicators）与低饱和胶囊
- Codex 过程行仅在左侧使用了微小的彩度状态指示符（橙色菱形、绿色三角、黄色齿轮、蓝色方块），用色彩表明类型，文字保持中性。
- 变更统计胶囊（`3 个文件已更改 +14 -10`）底色为柔和的 `#2D2D2D`，增删代码数字分别采用软绿（`+14`）和软红（`-10`），不使用高饱和刺眼色彩，既清晰又不破坏全局灰度平衡。

### 4. 极端克制的输入框占位符
- 底部输入框占位符 `和 Codex 一起工作` 处于 `#363636` 的输入容器内，实测文字为 `#686868`，对比度仅 **2.17:1**。当用户未聚焦输入时，占位符几乎隐没于背景之中，将全部视觉重量留给主阅读区。

## 我们的现状与根因（带证据）

在 [`ours-crish.png`](file:///c:/Software/conex/docs/visual-hierarchy-clarity-analysis/evidence/ours-crish.png) 中，用户最强烈的感受是「界面蒙着一层灰、正文和过程行混成一片、标题像正文、侧栏字看不清」。通过源码交叉审查，定位到以下六大根本原因：

### 根因 1：暗色主题 `--text-primary` 人为混入 20% 纯黑，抹杀高光
- **源码证据**：[`apps/crish-desktop/src/styles/tokens.css:1134-1146`](file:///c:/Software/conex/apps/crish-desktop/src/styles/tokens.css#L1134-L1146)
  ```css
  /* 深色文字灰度（2026-10-21）：最亮正文 20%，次级 40%，三级 60%，极弱 70%。
     向黑混合皮肤完整前景，色相跟着当前主题走。
     --user-text-primary 保持未压灰，元素提亮和运行时注入读它。 */
  --user-text-primary: #f5f5f5;
  --user-text-secondary: #cccccc;
  --user-text-tertiary: #8c8c8c;
  --user-text-faint: #666666;
  --text-primary: color-mix(in srgb, var(--user-text-primary) 80%, black);
  --text-secondary: color-mix(in srgb, var(--user-text-primary) 60%, black);
  --text-tertiary: color-mix(in srgb, var(--user-text-primary) 40%, black);
  --text-muted: var(--text-tertiary);
  --text-faint: color-mix(in srgb, var(--user-text-primary) 30%, black);
  ```
- **机制与现象**：
  `--user-text-primary` 本是 `#f5f5f5`（在 `#141414` 底色上本应有 16.9:1 的极佳对比度），但源码通过 `color-mix` 强行掺入了 20% 纯黑，实际输出值为 `#c4c4c4`（RGB: 196, 196, 196）。截图像素采样证实，正文文本核心像素点实测仅为 `#c3c3c3`（对比度 **10.45:1**）。  
  虽然 10.45:1 理论上高于 WCAG AA（4.5:1），但在深黑底色（#141414）上，由于人类视觉对明度差的对数感知特性（Weber-Fechner 定律），`#c4c4c4` 呈现出强烈的「发灰、发闷、脏感」，缺少 Codex 的通透感与精神感。

### 根因 2：2026-09-11 历史裁决强制过程区「字号 14px、字重 400」同构化
- **源码证据**：
  1. [`apps/crish-desktop/src/components/chat-tool-call/ChatToolCallBlock.module.css:2-22, 109-110`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-tool-call/ChatToolCallBlock.module.css#L2-L22)

     ```css
      *    上下零外边距——消除两侧「边距不一样」的观感差异；
      * ② 除正文外一律默认浅色（--text-tertiary），字重统一 400，
      *    字号统一 14px（原 11px/12px/13px 混排且偏小）；
      * ③ 语义色（错误 / 差异增删）保留，不计入「统一浅色」范畴。
      */
     .toolStack {
       font-size: 14px;
     }
     .toolRowHead {
       font-size: 14px;
     ```

  2. [`apps/crish-desktop/src/components/chat-message-row/ReasoningRow.module.css:160-175`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-message-row/ReasoningRow.module.css#L160-L175)
     ```css
     /*
      * 【统一排版纪律 · 2026-09-11 用户裁决】
      * 过程区（思考行 / 工具行 / 折叠控制栏）必须同构：
      *   字号 14px、字重 400、颜色继承行级状态机（默认 --text-tertiary）。
     ```

  - 工具汇总行（`已读取 1 个文件 · 已运行 1 条命令`）：**14px，400 字重**；

  所有行的高度、字符宽度、笔画粗细在宏观排版上毫无区别。原本为了解决「字体偏小视觉割裂」而制定的同构化策略，矫枉过正地消除了原本应当存在的「主干 vs 旁支」几何差异。

### 根因 3：`--text-tertiary` 跌破 WCAG 2.1 AA 底线（实测 2.93:1 ~ 3.02:1）
- **源码证据**：[`apps/crish-desktop/src/styles/tokens.css:1144`](file:///c:/Software/conex/apps/crish-desktop/src/styles/tokens.css#L1144)
  ```css
  --text-tertiary: color-mix(in srgb, var(--user-text-primary) 40%, black);
  ```
- **机制与现象**：
  40% 的墨量混合 60% 黑色，计算 RGB 值为 `[98, 98, 98]`（`#626262`）。
  在主聊天背景 `#141414`（RGB `[20, 20, 20]`）上，pwsh 精确计算的 WCAG 对比度仅为 **3.02:1**；截图像素实测采样：
  - 思考行文本核心像素 `#606060`，对比度 **2.93:1**；
  - 工具行文本核心像素 `#626262`，对比度 **3.02:1**；
  - 工具汇总行文本核心像素 `#626262`，对比度 **3.02:1**。  
  WCAG 2.1 规范明确要求：对于低于 18pt（24px）或低于 14pt（约 18.6px）粗体的普通文本，对比度**不得低于 4.5:1**。Crish 当前的过程信息完全不达标，在低照度或稍有反光的显示器上几乎变成不可见的暗纹，严重影响可用性。

  ```css
  --font-size-md: calc(16px + var(--font-size-adjust, 0px));
  --font-size-lg: calc(18px + var(--font-size-adjust, 0px));
  --font-size-xl: calc(22px + var(--font-size-adjust, 0px));

  --font-size-nano: var(--font-size-xxs); /* 10px -> 11px */
  ```

- **机制与现象**：
  设计系统为了兼容各种碎片化的历史字号，设立了 `11px`、`12px`、`13px`、`14px` 这种 1px 步长的微细字阶。在 100% 缩放的 1080p 或 2K 屏幕上，11px 与 12px、13px 与 14px 在肉眼上几乎无法区分，无法形成认知梯次。
  同时，扫描 `apps/crish-desktop/src` 全量代码发现，组件普遍绕过 token 直接写死字面量：
  - `11px`：硬编码 56 处（如 [`ChatMessageRow.module.css:1486`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-message-row/ChatMessageRow.module.css#L1486)）；
  - `14px`：硬编码 32 处（如 [`ReasoningRow.module.css:111`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-message-row/ReasoningRow.module.css#L111)）；
  - `12px`：硬编码 30 处；
  - `13px`：硬编码 16 处；
  - `10px`：硬编码 13 处（如 [`ChatComposer.module.css:794`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-composer/ChatComposer.module.css#L794)）；
  - 甚至出现小数半像素：`10.5px`（4 处）、`11.5px`（4 处）、`12.5px`（4 处，如 [`NewTabLauncherPopover.module.css:170`](file:///c:/Software/conex/apps/crish-desktop/src/components/binary-tree/NewTabLauncherPopover.module.css#L170)）。  
  字号缺乏统一收敛，随意修补导致整个系统丧失了严格的视觉节奏法则。

### 根因 6：Windows 环境下 CJK 字体缺失 Medium (500) 字形造成字重塌陷
- **源码与系统证据**：
  [`tokens.css:1486-1495`](file:///c:/Software/conex/apps/crish-desktop/src/styles/tokens.css#L1486-L1495) 定义的字体栈：
  ```css
  --md-font-family: var(
    --font-sans,
    -apple-system, BlinkMacSystemFont, 'Segoe UI',
    'PingFang SC', 'Hiragino Sans GB', 'Microsoft YaHei', sans-serif
  );
  ```
- **机制与现象**：
  在 Windows 系统（本运行环境）中，`-apple-system`、`PingFang SC` 并不存在。`Segoe UI` 仅支持西文字符，所有中文统一回退到 `Microsoft YaHei`（微软雅黑）。  
  实测 Windows 字体目录 `C:\Windows\Fonts\`，微软雅黑物理文件仅有：
  - `msyhl.ttc`（Light 300）
  - `msyh.ttc`（Regular 400）
  - `msyhbd.ttc`（Bold 700）  
  **根本不存在 500（Medium）或 600（SemiBold）的物理字形文件**！  
  当前端 CSS 大量声明 `font-weight: 500`（代码库中多达 270+ 处）或 `font-weight: var(--font-weight-medium)` 时，Chromium / WebView2 在渲染中文字符时直接将其降级为 400（Regular）。这意味着：在 Windows 桌面端，开发者自以为通过 500 与 400 建立了精巧的层级，实际上在用户屏幕上**中文完全是一模一样的 400 字重**！

## 与其他维度的耦合点

1. **与维度 01（背景底色与层次 / Surface Tiers）的耦合**  
   文字的前景色是相对底色计算出来的。Crish 目前采用的三档底色（`#1e1e1e` 外层、`#141414` 主层、`#232323` 输入框）在亮度上跨度极小（20 到 35 之间）。因为底色层次拉不开，文字如果再人工压暗（#c4c4c4），整个界面的明度动态范围（Dynamic Range）被死死卡在 20~196 的窄带区间内。相比之下，Codex 底色虽然同样为黑，但文字动态范围直接拉满到 24~255，瞬间产生高对比通透感。

2. **与维度 03（容器与边框 hairline / Borders & Hairlines）的耦合**  
   为什么 Codex 页面几乎看不到生硬的边框线？因为它的文字层级足够强大，读者仅凭「14px 纯白正文」与「12px 弱灰过程行」的排版形态，就能在心理上完成信息分块。而 Crish 由于正文和过程行长相完全一致，设计者被迫引入大量的卡片框线、微弱分割线和容器包裹来人为“兜住”信息，最终导致页面被碎片化框线分割得支离破碎。

3. **与维度 04（信息密度与行高节奏 / Spacing & Leading）的耦合**  
   `ReasoningRow` 和 `ChatToolCallBlock` 被强制赋予 24px 高度和 14px 字号，导致每一个折叠的工具行都像是一条普通段落。一旦模型连续调用 5 个工具，页面就会被 5 条大号灰色字填满，直接破坏了正文的阅读心流。而在 Codex 中，过程信息极度紧凑（12px 单行），一屏可以容纳更多上下文。

4. **与维度 05（图标与辅助语义 / Icons & Status）的耦合**  
   Codex 的过程行依靠彩色的微型状态图标（绿色勾、黄色齿轮、蓝色菱形）提供快速辨识度，其文字可以心安理得地保持低对比；而 Crish 的过程行缺少这类明快的彩色微视觉锚点，单调的灰色文字不得不兼顾可读性与低调性，最终两头不讨好。

## 架构级修复方向

> **严禁魔术数字打补丁**：方案必须建立在 Token 系统重构、排版契约升级与字体栈治理的架构层面，严禁在个别组件中修改 `font-size: 13px !important` 这类局部修补。

### 1. 暗色文字 Token 阶梯架构重构（回归高光与 WCAG AA 基线）
- **废除 `tokens.css` 中的人工压黑逻辑**：
  在 [`tokens.css`](file:///c:/Software/conex/apps/crish-desktop/src/styles/tokens.css) 中，废止对 `--text-primary` 掺入 20% 黑色的处理，直接让其继承高质量白，并重置四级明度契约：
  ```css
  /* 架构级暗色墨量新规范：满足 WCAG 2.1 AA (≥4.5:1)，拉开 3 档分明阶梯 */
  html[data-theme='dark'] {
    --text-primary: #ededed;    /* 核心正文：对比度 15.6:1 (AAA)，通透高亮不刺眼 */
    --text-secondary: #a8a8a8;  /* 次级文本/面板副标题：对比度 7.7:1 (AA)，清晰辅助 */
    --text-tertiary: #828282;   /* 过程行/时间戳/元信息：对比度 4.8:1 (AA 达标)，严禁低于 4.5:1 */
    --text-faint: #545454;      /* 仅用于非文字元素（装饰点/极弱发丝边框）：对比度 2.6:1 */
  }
  ```

### 2. 废除 2026-09-11 历史裁决，恢复过程区与正文的「大小-字阶差」
- **打破 14px 同构假象**：
  在架构上确立：**AI 思考过程与工具调用属于「第二视线级别（Secondary Stream）」**。
  - 正文排版基准：保持 `14px`（`--font-size-base`），行高 `1.65`，颜色 `--text-primary`（`#ededed`）；
  - 过程区排版基准：恢复为 `12px`（`--font-size-xs`），高度保持 `22px~24px`，颜色 `--text-secondary`（`#a8a8a8`）或达标的 `--text-tertiary`（`#828282`），字重保持 400；
  - 这样，正文与过程行在字号（14px vs 12px）、色彩对比度（15.6:1 vs 4.8:1）上产生明确的层级跃迁，无需框线即可自然分开。

### 3. 字阶体系偶数化与清退 1px 细碎级差
- **重构 Type Scale 阶梯**：
  将当前 `10/11/12/13/14/16/18/22` 的 1px 细碎步长收敛为经典偶数级阶体系：
  - `Caption (辅助标签)`: `11px` (`--font-size-xxs`)
  - `Secondary (过程/代码/元数据)`: `12px` (`--font-size-xs`)
  - `Body (正文基准)`: `14px` (`--font-size-base`)
  - `Subhead (卡片标题/H3)`: `16px` (`--font-size-md`)
  - `Heading (H2)`: `18px` (`--font-size-lg`)
  - `Title (大标题/H1)`: `22px` (`--font-size-xl`)
- **硬编码清零与 Stylelint 门禁**：
  通过 ESLint / Stylelint 规则，彻底禁止 CSS 模块中出现裸 `px` 字号声明，强制使用 `var(--font-size-*)`；全面清理代码库中残存的 56 处 `11px`、32 处 `14px` 以及所有 `.5px` 半像素。

### 4. Windows 环境 CJK 字体栈与字重策略治理
- **引入现代字体栈**：
  在 `--md-font-family` 字体栈中前置支持现代可变字体（Variable Fonts）或包含原生 Medium/SemiBold 字重的优质 CJK 字体，如：
  `'Segoe UI Variable Text', -apple-system, 'PingFang SC', 'Source Han Sans SC', 'Noto Sans SC', 'Microsoft YaHei', sans-serif`。
- **降级断层保护**：
  在设计规范中明确：**在 Windows 传统环境下，严禁单纯依赖 400 vs 500 来承担主次区分职责**。必须遵循「字号变化（14px vs 12px）+ 色彩变化（Primary vs Tertiary）」作为第一道刚性分级防线；字重（Bold 700 vs Regular 400）只作为辅助增强手段。

### 5. 强化 Markdown 报告大标题的结构统治力
- **标题色彩高光独立**：
  将 `--md-heading-color` 显式解耦为独立的高光纯白 token（如 `--text-heading: #ffffff`），不再与正文共用被压暗的 `--text-primary`；
- **Chat 模式大标题差异化增强**：
  对于助手输出的大型 Markdown 报告，恢复 H1/H2 底部 1px 的极细发丝分割线（`--hairline`），恢复其 1.75em~1.85em 的庄重尺寸，使结构性报告与随口回答形成一眼可辨的层级区分。

## 未确认项

1. **亮色与高对比度皮肤表现**：本报告结论完全基于暗色模式（`data-theme='dark'`）与指定截图证据。亮色主题下是否存在类似的正文人工压灰或 WCAG 违规，需要后续在亮色截图中独立取样确认。
2. **Windows 125%/150% DPI 缩放下的 ClearType 亚像素抗锯齿影响**：高分屏缩放会影响字体的感知粗细度（亚像素边缘模糊会让 11px/12px 的实际可读性进一步降低），需在真实高分屏 Windows 机器上做动态验证。
3. **2026-09-11 裁决的历史业务背景**：当年制定「除正文外一律 14px 统一浅色」时，是否有未记录的特定硬件或视力辅助诉求，重构前需与主控 Agent 及架构师做最终对齐。
