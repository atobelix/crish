# 维度 08 分析报告：设计系统体量与一致性——Token 膨胀、别名坍塌与字面量绕过

> **分析维度**：【08 设计系统体量与一致性（Design-system coherence）】  
> **对比物证**：
> - 参考界面：`docs/visual-hierarchy-clarity-analysis/evidence/ref-codex.png`（Codex 暗色界面）
> - 本仓界面：`docs/visual-hierarchy-clarity-analysis/evidence/ours-crish.png`（Crish 暗色界面）  
> **核心命题**：为什么 Codex 的界面在视觉上通透、整洁、层级分明，而 Crish 显得灰蒙、拥挤且缺乏一致层级？从设计系统（Token 架构、别名链、圆角刻度与组件复用）的深层断裂给出全景证据。

---

## 结论摘要（先行）

1. **Token 虚胖与别名坍塌（Alias Collapse）**：`tokens.css` 拥有多达 1,235 处变量声明与 652 个独立变量名，但在暗色模式下，多达 9 个表面色变量（`--bg-primary`、`--bg-card`、`--bg-elevated`、`--surface-card`、`--surface-elevated` 等）全部通过 4-5 层别名链坍塌到单一字面量 `#141414`；10 个侧栏/外壳变量全部坍塌到 `#1e1e1e`。名为“Elevated（抬升）”的层级在物理色彩上与底层完全同色，导致组件层不得不滥用边框、阴影或透明度混合（`elevate-*`）补救，引发视觉混乱。
2. **空间与度量系统严重失控（5,098 处 px 裸写绕过）**：虽然历史战役（`design-token-ssot`）实现了 99.8% 的颜色 Token 化，但空间尺寸（Padding、Margin、Width、Height、Gap）完全未建立有效 SSOT。全仓 170 个 CSS 模块中散落 **5,098 处字面量 px**，顶级组件如 `ChatComposer`（323 处）、`ChatMessageRow`（206 处）、`ModernToolCall`（167 处）全凭手写微调，导致行高、对齐网格处处错位。
3. **圆角刻度膨胀且缺乏场景语义（10 档圆角混杂）**：系统内同时存活 4px、6px、7px、8px、10px、12px、14px、16px、20px、24px 共 10 档圆角，外加历史遗留别名（`--radius-s` 与 `--radius-sm` 异值、`--radius-lg` 与 `--radius-l` 异值）。缺少“哪类控件绑哪档”的语义层级规范，导致同一屏内 20px 大圆角输入框与 7px 独立按钮、10px 会话项、6px 状态徽标发生剧烈视觉冲突。
4. **同类基元各立门户、严重重复造轮子**：行（Row）、卡片（Card）、徽标（Badge）、图标按钮（IconButton）缺乏统一步调。`SidebarSessionList`、`ChatToolCallBlock`、`ModernToolCall`、`AgentCard`、`InlineAgentPanel` 分别手写了 6 套行高（20px、24px、26px、28px、32px、36px）、4 套 Badge 内边距与各自独立的 Hover 动画过渡（100ms、120ms、150ms、`--transition-press`）。
5. **暗色文字对比度与三级语义断层**：在暗色模式下，`--text-tertiary`（三级文字）对主背景 `#141414` 的实测 WCAG 对比度仅 **3.02:1**，对侧栏背景 `#1e1e1e` 仅 **2.73:1**，严重违反 WCAG AA（4.5:1）基准；侧栏选中态通过 `--elevate-3` 强行提亮至 `#464646`，形成突兀色块，而其内部辅助文字对比度仅 **3.07:1**。

## 参考界面做对了什么（具体）

观察 `docs/visual-hierarchy-clarity-analysis/evidence/ref-codex.png`：

1. **极度克制的三层物理背景体系（Ground / Surface / Float）**：
   - Codex 全界面在暗色下只有三个清晰的表面阶梯：底板（纯黑/极深底 `#000000` 或 `#0d0d0d`）、工作区面板卡片（轻微提亮沉稳暗灰）、浮动浮层/Composer 容器（具有细微半透明质感的悬浮卡片）。
   - 没有使用任何大面积高反差的实心灰块（如 Crish 中亮度高达 `#464646` 的侧栏选中项）。
2. **单一且严格对齐的度量步进（Unified Row Metric & Grid）**：
   - 右侧“子智能体”面板（Sub-agent Panel）与左侧会话列表的所有条目均采用一致的行高（约 36px）、固定的图标槽位（约 20×20px）、一致的左右 Padding（约 8px-12px）。
   - 状态说明（如“已开启 · 2”、“完成 · 20”、“再显示 10 个”）字号严格锁定在 12px/13px，辅以精准的垂直对齐，整屏没有任何文字与图标基线晃动。
3. **圆角收敛为 3 档经典梯次**：
   - 宏观外壳/输入框卡片：大微圆（约 12-16px）；
   - 列表项与行：紧凑小圆角（约 6-8px）；
   - 状态胶囊与计数器：全圆角胶囊（Pill / 9999px，如 `3 个文件已更改 +14 -10`）。
   - 绝不存在 7px、10px、14px 等半生不熟的碎刻度，整体视觉柔和、干净。
4. **非侵入式的信息层级（Subtle Indicators）**：
   - 状态指示（绿色小三角、黄色齿轮、蓝色方块）均直接在行内文字前作为微图标呈现，颜色仅作为语义提示点缀，而非将整行染亮或包围生硬边框。

## 我们的现状与根因（带证据）

### 1. Token 体系膨胀与别名链坍塌

在 [`apps/crish-desktop/src/styles/tokens.css`](file:///c:/Software/conex/apps/crish-desktop/src/styles/tokens.css) 中，全量 Token 声明达到 1,235 条，独立 Token 名称 652 个。但深入暗色主题 `html[data-theme='dark']`（1044-1170 行）发现：

#### 证据 1：表面色别名链深度与“多名同值”坍塌
```css
/* apps/crish-desktop/src/styles/tokens.css:1049-1068 */
--user-surface-outer: #1e1e1e;
--user-surface-main: #141414;
--user-surface-input: #232323;

--surface-paper: var(--surface-main);     /* -> #141414 */
--surface-card: var(--surface-main);      /* -> #141414 */
--surface-elevated: var(--surface-main);  /* -> #141414 */
--bg-primary: var(--surface-paper);       /* -> #141414 */
--bg-card: var(--surface-card);           /* -> #141414 */
--bg-elevated: var(--surface-elevated);   /* -> #141414 */
--bg-page: var(--surface-paper);          /* -> #141414 */
--bg-canvas: var(--surface-paper);        /* -> #141414 */
--leaf-card-bg: var(--bg-card);           /* -> #141414 (链长 5 层!) */
```
- **病灶**：在概念上，开发者以为使用了 `--bg-elevated` 就能让卡片在 `--bg-primary` 上“浮起”，以为 `--surface-card` 能够呈现卡片底色。但在 CSS 解析后，**`--bg-primary`、`--bg-card`、`--bg-elevated` 全等于 `#141414`**！
- **后果**：卡片在暗色主背景上完全无法通过背景色与画布分离，组件开发者为了区分卡片，只得盲目为所有卡片叠加 `border: 1px solid var(--border-subtle)`（如 `ChatToolCallBlock.module.css:57`、`AgentCard.module.css:18`、`approvalCard`），导致全屏都是细碎线框，界面显得非常脏。
- **空间语义反向倒挂**：
  - `--surface-sunken`（下沉） -> `--surface-outer` -> `#1e1e1e`（更亮！）
  - `--surface-elevated`（抬升） -> `--surface-main` -> `#141414`（更暗！）
  - 物理亮度上，下沉比抬升亮了 10 个 RGB 阶度，物理空间认知完全错乱。

#### 证据 2：历史兼容层与冗余别名
- **圆角别名冲突**：
  - [`tokens.css:490-494`](file:///c:/Software/conex/apps/crish-desktop/src/styles/tokens.css#L490-L494)：`--radius-xs: 4px;`、`--radius-sm: 6px;`、`--radius-md: 8px;`、`--radius-lg: 10px;`、`--radius-l: 12px;`
  - [`tokens.css:502-503`](file:///c:/Software/conex/apps/crish-desktop/src/styles/tokens.css#L502-L503)：`--radius-s: 4px;`、`--radius-m: 8px;`
  - **严重歧义**：`--radius-sm` 是 6px，但 `--radius-s` 是 4px；`--radius-lg` 是 10px，但 `--radius-l` 是 12px！两套命名在全仓混用（`--radius-sm` 用了 180 处，`--radius-s` 用了 9 处；`--radius-lg` 用了 72 处，`--radius-l` 用了 14 处）。
- **字号别名坍塌**：
  - [`tokens.css:673-676`](file:///c:/Software/conex/apps/crish-desktop/src/styles/tokens.css#L673-L676)：
    ```css
    --font-size-nano: var(--font-size-xxs);    /* 11px */
    --font-size-micro: var(--font-size-xxs);   /* 11px */
    --font-size-xs-plus: var(--font-size-xs);  /* 12px */
    --font-size-sm-plus: var(--font-size-sm);  /* 13px */
    --font-size-2xl: var(--font-size-xl);      /* 22px */
    ```
    nano、micro 两个意图不同的刻度全部坍塌至 xxs；xs-plus 与 sm-plus 坍塌至普通档，2xl 坍塌至 xl。徒增维护成本与概念负担。

### 2. 圆角体系：10 档碎刻度与“场景无约束”

在 `tokens.css` 与全仓组件中，圆角刻度严重过载，且未建立场景规范：

| Token 名称 | 解析值 | CSS 中使用次数 | 典型消费场景 | 存在的问题 |
|---|---|---|---|---|
| `--radius-xs` | 4px | 56 | 复选框、进度条、徽标、微型角标 | 与 `--radius-s` 重复 |
| `--radius-sm` | 6px | 180 | 菜单项、操作按钮、列表项、Tag | 容易与 7px、8px 混淆 |
| `--radius-btn` | 7px | 25 | 独立文字按钮（`--button-radius`） | 历史“用户锁 U1”打下的孤岛刻度，无法融入同心方程 |
| `--radius-md` | 8px | 183 | 标准控件、输入框、下拉项、工具行 | 最拥挤的刻度，既做控件又做卡片 |
| `--radius-lg` | 10px | 72 | 侧栏会话项（`SidebarSessionList`）、代码块 | 与 `--radius-l` (12px) 冲突，导致侧栏与浮层圆角不一致 |
| `--radius-l` | 12px | 14 | 附件卡片、浮动权限条 | 历史遗留，与 `--radius-lg` 并存 |
| `--sep-radius-outer` | 14px | 33 | 快捷菜单面板外壳、模型卡片 | 组件专属 Token 逃逸到全局 |
| `--radius-xl` | 16px | 49 | 审批卡片（`approvalCard`）、GitDiff 卡片 | 作为卡片外壳，内部嵌套 8px/6px 元素 |
| `--radius-2xl` / `--radius-input` | 20px | 16 | 底部 `ChatComposer`、用户气泡、弹窗 | 底部输入框极其圆润，与上方 7px/8px 控件形成视觉断层 |
| `--radius-3xl` | 24px | 8 | 极少数模态容器 | 极低频使用 |

**截图观察（`ours-crish.png`）**：
- 观察左下与右下：底部 `ChatComposer` 外框圆角是 20px（非常圆），但其上方的“首次使用请先配置服务端密钥与模型”卡片内“去配置”按钮是 7px（微圆偏方），卡片本身是 12px；左侧会话选中项是 10px。
- 一屏之内，同时并存 7px、8px、10px、12px、20px 五种弧度，完全缺乏视线流动的主次韵律。

### 5. 既有战役审计复盘：解决了什么？遗留了什么？

| 战役名称 | 核心初衷与解决项 | 未解决 / 留下的盲区 |
|---|---|---|
| **`design-token-ssot`** | **解决了**：<br>1. 统一偏好至 SQLite `app_preferences` 表与单一 `TokenRuntimeController`；<br>2. 清理了 CSS 中的硬编码颜色，达成 99.8% Token 化。 | **未解决**：<br>1. **语义层级 Token 完全缺位**：没有建立 Layer 0 (Base)、Layer 1 (Surface)、Layer 2 (Elevated) 的显式层级规范；<br>2. **表面色坍塌**：Token 虽多，但在暗色下全部指向同一 hex 值（`#141414`），造成“有 Token 无层级”；<br>3. **度量完全放任**：未将 Spacing/Size 纳入 SSOT 治理。 |

## 与其他维度的耦合点

1. **耦合【维度 01：空间密度与外边距系统】**：
   `tokens.css` 中只定义了 13 个间距 Token，却被 5,098 处硬编码 px 绕过。空间密度的错乱直接根植于设计系统缺乏刚性的 Layout Grid 与 Spacing Scale SSOT。
2. **耦合【维度 02：色彩与表面层级（Surface hierarchy）】**：
   表面 Token 的“多名同值坍塌”（`--bg-primary`、`--bg-card`、`--bg-elevated` 全等于 `#141414`）是表面层级丧失的直接罪魁祸首。表面层级无法自发表达，倒逼各个卡片加描边。
3. **耦合【维度 04：组件形态与微交互一致性】**：
   同类行（Row）、Badge、Button 在 5 个模块中独立手写，直接导致交互微动效（Transitions 100ms vs 120ms vs 150ms）与焦点态各有千秋，无法形成统一质感。
4. **耦合【维度 06：信息密度与扫描路径】**：
   由于 `--text-tertiary` 暗色实测对比度仅 2.73:1 ~ 3.02:1，用户在快速扫视消息流中的工具调用（如 `src/loop/loop_exec.rs:22`）时视觉阻力极大。

## 架构级修复方向

> 遵循 AGENTS.md 纪律：严禁魔术数字补丁，追求架构级收敛与单一真理源（SSOT）。

### 1. 建立显式三级语义表面（Semantic Surface Tier）
彻底打破全坍塌到 `#141414` 的扁平现状，建立基于物理光照规律的三层暗色基座：
- **Layer 0 (Canvas / Base)**：`#0f0f10`（极深纯净底板，用于主消息流底层）；
- **Layer 1 (Card / Section Surface)**：`#18181a`（卡片与侧边栏底色，ΔL ≈ +5%，无需硬描边即可温和浮出）；
- **Layer 2 (Elevated / Float Surface)**：`#222225`（浮动菜单、模态框、Composer 输入卡片，配合深色柔和弥散阴影）。
- **废除虚假别名**：彻底清理 `--surface-paper`、`--bg-canvas`、`--leaf-card-bg` 等多层中转，统一收敛为 `--surface-layer-0`、`--surface-layer-1`、`--surface-layer-2`。

### 2. 圆角体系收归“3+1 语义阶梯”并与组件类型强绑定
废除 10 档碎片圆角，规范场景映射契约：
- **Micro（4px）**：行内元素（复选框、Inline Code、极小角标）；
- **Control（8px）**：所有原子控件（标准按钮、列表行、下拉项、输入框控件）；
- **Container（14px）**：所有容器（业务卡片、代码块面板、下拉菜单外壳、侧栏卡片）；
- **Overlay（20px）**：顶级悬浮浮层（全局 Dialog、设置中心、大模态）；
- **Pill（9999px）**：状态胶囊、搜索栏丸形 Pill。
- **清除历史孤岛**：废除 7px（`--radius-btn`）、10px（`--radius-lg`）、12px（`--radius-l`），归并 `--radius-s`/`--radius-sm` 冲突。

### 3. 构建原子级 UI Primitives 并强制复用
严禁各业务组件私自手写行、徽标与卡片：
- **`<ActionRow>`**：统一承接会话列表项、工具调用头、Agent 卡片条目。统一行高（紧凑 28px / 标准 32px）、统一内边距、统一 Hover 背景增量（`--tint-hover`）；
- **`<Badge>`**：统一收拢状态徽标，锁死内边距（`2px 6px`）、字号（`11px / 12px`）与圆角（Micro / Control）；
- **`<IconButton>`**：统一收拢所有 24px/26px 图标按钮，内置 `<Tooltip>`，清除组件内重复手写的 CSS。

### 4. Spacing Token 刚性门禁化
- 严禁在业务 CSS 模块中书写裸字面量 `px`（除 1px 细线外）；
- 引入 ESLint / Stylelint 门禁规则（如 `stylelint-declaration-strict-value`），刚性拦截对 `padding`、`margin`、`gap`、`border-radius` 的裸写，强制走 `--space-*` 与 `--radius-*`。

### 5. 暗色灰阶 WCAG AA 达标校正
- 将暗色模式下的 `--text-tertiary` 亮度从当前 40% 墨（`#626262`）上调至 52% 墨（约 `#828282`），使对 `#141414` 的对比度从 3.02:1 提升至 **4.65:1**，满足 WCAG AA 4.5:1 法定基线。
