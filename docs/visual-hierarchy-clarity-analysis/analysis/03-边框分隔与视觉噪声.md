# 视觉层级清晰度分析 · 维度 03：边框、分隔线与视觉噪声

> **分析对象**：参考界面（Codex，截图 `ref-codex.png`） vs 我们的界面（Crish，截图 `ours-crish.png`）  
> **核心议题**：为什么参考界面看上去纯净平滑、信息一目了然，而我们的界面充斥着“线噪”、网格切割感与视觉毛刺？  
> **分析员身份**：UI 视觉分析员（只读分析，不改源码，基于截图观察、源码路径与实测数据）

---

## 结论摘要

1. **『既弱又多』的双重异化根因**：
   暗色主题下，界面的关键描边变量 `--border-subtle`（`#2e2e2e`）对主内容底板 `--surface-main`（`#141414`）的实测 WCAG 对比度仅为 **1.36:1**（对输入框底板仅 **1.16:1**），远低于 WCAG 2.1 AA 非文本边界要求的 **3.0:1** 最低分界线；但在源码中，活跃 `border` 属性却多达 **1578 处**，其中硬编码 `1px` 发丝线高达 **329 处**。它在光学上**无法有效建立结构性闭合与容器分界**，在物理排布上却**遍布全屏割裂连续性**，直接沦为发乌、模糊的“灰色毛刺与线噪”。
2. **工具流与思考行的 Chevron 视觉污染**：
   参考界面（Codex）在处理单轮对话的 5 步工具调用时，采用极其纯净的**单行平铺排版（0 边框、0 背景、0 个 chevron 箭头）**；而 Crish 在 `ToolCallHeader.tsx:199`、`FoldableProcessSection.tsx:310`、`FoldableToolGroup.tsx:237` 中，为思考行与每条工具调用**全量硬编码悬挂单角引号 `&#8250;`（chevron）**。一轮简单的 5 步调用即在视线右缘密集悬挂多达 5-9 个无语义几何折叠角，造成强烈的眼动震荡与认知负荷。
3. **视口底部双重胶囊堆叠的几何冲突**：
   底部 Composer 输入区域在纵向不足 120px 的狭小区域内，上下生硬堆叠了 `ComposerNoticeBar` 提示胶囊（`border: 1px solid var(--border-subtle)`）与 `composerCard` 输入卡片（同带完整 1px 闭合描边），形成两道平行闭合圆角线圈，彻底打破了视口落地的沉静感。
4. **结构思维断层：以线代面 vs 靠场控势**：
   Codex 遵循现代操作系统的 Surface 阶梯哲学，靠 **2%~5% 微弱明度差与呼吸感留白（Spacing）** 完成视觉分区，零线条即可建立立体秩序；Crish 长期缺乏表面分层体系，将 1px border 作为区分容器的唯一低成本手段，导致 UI 陷入严重的“过度容器化（Over-containerization）”与界面破碎化。

## 参考界面做对了什么（具体）

参考 Codex 界面（`docs/visual-hierarchy-clarity-analysis/evidence/ref-codex.png`），其视觉整洁与层级分明的本质，在于**彻底废黜了物理边框的支配地位，转向由底色明度场（Surface Field）与负空间（Spacing）主导的现代排版规范**：

### 1. 顶栏无界化（Zero-Border Titlebar）
- **截图证据**：顶栏直接透通至工作区背景，左侧导航键（`← →`）、窗口菜单（文件、编辑、视图、帮助）、中心任务标题（`分析 Conex 当前问题`）到右侧三联键，**没有任何横贯屏幕的 1px border-bottom 分隔线**。
- **排版智慧**：依靠顶栏固定高度（约 36px）以及轻微的文字灰度，自然与主工作区划定边界，消除了头部横切画面的硬横线。

### 2. 左侧导航极简 Dock（Border-Free Navigation）
- **截图证据**：最左侧为固定宽度（约 48px）的纯图标导航条（Home、Branch、History、Docs、@、...、Settings）。
- **排版智慧**：导航栏与主聊天区交界处**没有 1px 实体竖线**，仅靠微小的底色色阶差异（或自然列缝隙）过渡。图标以居中大留白排布，没有任何分割线和卡片包裹，整洁如一。

### 3. 聊天流与工具调用：纯单行流式平铺（Flattened Minimal Rows）
- **截图证据**：在连续 5 步任务推进中（`Import failure state已完成`、`运行了命令`、`Asset scope sync fix开始工作`、`Recovery state review已完成`、`编辑了文件运行了命令`）：
  - **无边框（0 Border）**：每条工具调用没有任何 1px 边框或轮廓线。
  - **无背景（0 Background Card）**：不给工具行套独立背景色块，直接在主层画布上平铺。
  - **无 Chevron（0 Chevron）**：**整列右侧没有任何折叠小箭头（`>` 或 `›`）！**
  - **极简语义**：每行仅由“单色/轻量彩色状态图标（14px） + 紧凑动作结果文字”构成。
  - **弱化胶囊**：“3 个文件已更改 +14 -10”采用极弱底色无边框药丸；折叠更多使用微小的 `...` 圆圈，完全不使用带尖锐箭头的控制组件。
- **排版智慧**：视线可以像阅读普通文本行一样顺畅向下扫描，眼动完全平滑，信息密度极高但视觉噪声为零。

### 4. 右侧辅助面板（子智能体）：纯排版分组
- **截图证据**：右侧子智能体面板内部容纳了 12 个 Agent 状态项，但画面毫无拥挤感：
  - 分组标题（`已开启 · 2`，`完成 · 20`）是纯文本标签，**完全没有横贯边框**。
  - 列表项没有卡片包裹，没有项间分割线，依靠 `图标 + 标题/状态 + 右侧时间` 的网格对齐自成秩序。
  - 底部 `再显示 10 个` 仅为弱化文本交互，不带按钮描边。

### 5. 一体化沉着输入底座（Single Unified Composer）
- **截图证据**：底部输入区为一个连续的大圆角深灰胶囊。
- **排版智慧**：输入框内部没有任何水平或垂直分割线，占位文字与下方操作组（`+`、`完全访问`、`6 Luna Max`、语音、停止按钮）共享同一容器底衬，依靠自然留白组织，无任何第二层嵌套边框，更无顶部悬浮提示的平行双边框。

## 我们的现状与根因（带证据）

观察 Crish 当前截图（`docs/visual-hierarchy-clarity-analysis/evidence/ours-crish.png`），界面存在大量被线条和几何图元切碎的“网格化燥点”，通过穿透源码，根因如下：

### 1. 聊天流与工具调用：Chevron 泛滥与容器过度包装
- **截图观察（聊天区中段）**：
  - 思考折叠行：`已思考 45.3s 全部 5 个步骤都完成并验证了。现在输出最终报告。 ›`，右侧悬挂一个单角引号 `›`。
  - 4 行可见工具调用（`列出目录 crates...`、`搜索「pub async fn run」...`、`写入 inventory.json...`、`已读取 1 个文件...`），**每一行的右缘都僵硬地悬挂着一个 `›` 折叠箭头**。
  - 报告卡片元数据栏（`自检代理: Ornith 1.5 9B ...`）右侧，还额外放置了一个带有圆形描边的大号向下展开箭头 `( v )`。
- **源码确证**：
  1. [`apps/crish-desktop/src/components/chat-tool-call/ToolCallHeader.tsx:194-201`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-tool-call/ToolCallHeader.tsx#L194-L201)：

  2. [`apps/crish-desktop/src/components/chat-message/FoldableProcessSection.tsx:305-312`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-message/FoldableProcessSection.tsx#L305-L312)：

- **根因剖析**：
  设计与实现将“是否具备展开能力”生硬地等同于“必须常驻显示 Chevron 图标”。在多步 Agent 循环中，一轮对话执行 10-20 次工具，右侧就会如栅栏般竖起 10-20 个毫无信息增量的 `›` 符号，不仅割裂了正文阅读节奏，更在右侧形成了一条刺眼的“虚假视觉轴”。

### 2. 底部输入区：NoticeBar 与 Composer 的双重闭合线圈冲突
- **截图观察（视口底部）**：
  - 视口底部上方悬浮着提示条：“首次使用请先配置服务商密钥与模型 去配置”。
  - 紧贴着下方是主输入框：“+ 输入消息，或键入 / 打开命令... (可粘贴截图) 完全访问”。
  - 两者均呈现为宽胶囊形态，垂直间距仅数像素，形成了上下平行的两道完整 1px 灰色闭合矩形。
- **源码确证**：
  1. [`apps/crish-desktop/src/components/chat-composer/ComposerNoticeBar.module.css:20-22`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-composer/ComposerNoticeBar.module.css#L20-L22)：
     ```css
     border-radius: var(--composer-radius-single, 20px);
     border: 1px solid var(--border-subtle);
     background-color: var(--bg-elevated);
     ```
  2. [`apps/crish-desktop/src/components/chat-composer/ChatComposer.module.css:1281-1284`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-composer/ChatComposer.module.css#L1281-L1284)：
     ```css
     border: 1px solid var(--border-subtle);
     border-radius: var(--composer-radius-single, 20px);
     background: var(--composer-bg, var(--surface-input));
     ```
- **根因剖析**：
  组件架构在演进时采用了“堆叠容器模式”（Strap-on Containers），没有将临时通知条内嵌或做进同一宿主容器，而是让每个功能块都具备一套自闭合的 `border + border-radius + box-shadow`，导致页面底部出现几何视觉重影（Visual Doubling）。

### 3. 左侧栏与标题栏：多余的物理切线与折叠指示
- **截图观察（左侧与顶部）**：
  - 左侧边栏宽度达 260px，与主界面之间使用了一条自顶贯底的 1px 实体竖线（`border-right`）硬性切割。
  - 侧栏内部，“搜索会话与消息...”外包了完整的 1px 轮廓边框。
  - 分组标题“置顶 v”、“项目 v”、“对话 v”每个都配有折叠小箭头。
  - 顶部存在完整的 Chrome 风格 Tab 胶囊，叠加下方主区面包屑导航，顶部水平区域被多条横向切线阻断。
- **源码确证**：
  - [`apps/crish-desktop/src/styles/tokens.css:1056`](file:///c:/Software/conex/apps/crish-desktop/src/styles/tokens.css#L1056)：定义了 `--content-frame-border: #222121`，专门用于在侧栏与内容矩形 `.leafBody` 之间强制画出“发丝细线”。
  - [`apps/crish-desktop/src/styles/tokens.css:240-248`](file:///c:/Software/conex/apps/crish-desktop/src/styles/tokens.css#L240-L248)：制定了线宽契约（Line Width SSOT），硬性规定所有常规分隔线、边框、卡片描边必须统一使用 `var(--hairline-width) (1px)`，并由 `check-line-width-ssot` 门禁强制推行。
- **根因剖析**：
  过去的工程治理虽然规范了“线宽必须是 1px”（消除了 2px/3px 等魔术数字），但从反向强化了“每一个组件都应该有 1px hairline”的错误假设。开发者在无意识中大量铺设 1px 细线，把原本属于排版留白的职责全部委托给了实体线。

## 与其他维度的耦合点

边框与视觉噪声并不是孤立的样式问题，它与其它视觉维度紧密交织：

1. **与维度 01（色盘与灰阶阶梯）的耦合**：
   - 依赖 1px 描边的直接原因，是暗色模式下**缺乏明确可辨的 Surface 明度台阶**。
   - 当前 `--surface-outer`（`#1e1e1e`）与 `--surface-main`（`#141414`）明度差仅约 2%，界面无法靠纯底色差异建立天然的立面感，迫使工程师引入 `--content-frame-border` 和各种 1px 细线去“画界限”。
2. **与维度 02（字阶、字重与排版节奏）的耦合**：
   - 当文字的字号、字重与垂直外边距（Vertical Spacing）缺乏严格节奏时，信息块之间就会粘连，开发者就会本能地使用 `border-bottom`、`hr` 或 `<div className="divider" />` 来做物理分割。
   - 工具调用行的参数与动作说明发生文本重复（`toolHumanLabel` 与 `actionText` 拼接冗余），使单行文字过长，进一步加剧了右侧 Chevron 的紧迫感。
3. **与维度 04（信息密度与有效负空间）的耦合**：
   - 每一个 1px 边框都伴随着内衬（Padding）与外衬（Margin），导致卡片内的实际内容区域被层层压缩。
   - 例如 NoticeBar 占用 48px 高度，加上外边距和自身描边，使得原本用于展现 AI 回复核心结论的纵向空间被无情挤占。
4. **与维度 05（组件规范与几何同心契约）的耦合**：
   - NoticeBar 和 Composer 各自定义了圆角（`--composer-radius-single, 20px`）和 1px 描边，但两者上下垂直排列时缺少几何呼应，形成了视觉上的“双筒望远镜”效应。

## 架构级修复方向

严禁使用魔术数字（如在局部 CSS 里补 `margin: -1px`、`border: none !important`）修补！必须从 Design Tokens、组件原子结构以及渲染流水线上推行系统性重构：

### 1. 建立 Surface Elevation SSOT 体系，废除以线代面的描边模式
- **架构方案**：
  构建纯净的暗色四级表面阶梯（Surface Elevation Ladder），取消依赖 `--border-subtle` 的容器切割：
  - `Surface-0 (Canvas 底板)`：`#101010`（窗口通底基座，最深层）
  - `Surface-1 (Main 工作区)`：`#161616`（主聊天区与侧边栏底色，依靠微弱明度差与列间距自然区分，**移除侧栏 1px border-right**）
  - `Surface-2 (Card / Row 卡片与展开块)`：`#1c1c1c`（展开后的代码块、工具详情卡片，**零 1px 描边**，靠底色明度差自然浮起）
  - `Surface-3 (Float / Composer 悬浮交互层)`：`#232323`（输入框、浮动通知，辅以 `0 4px 24px rgba(0,0,0,0.3)` 柔和漫反射环境光阴影，**剥离 1px 外围描边**）

### 2. 聊天流工具调用行：剥离常驻 Chevron，推行纯单行原子化排版
- **架构方案**：
  - 重构 `ToolCallHeader.tsx` 与 `FoldableProcessSection.tsx`：
    - **彻底移除常驻的 `&#8250;` DOM 节点**。工具行在折叠状态下仅呈现 `[状态图标] + [简明动作与核心参数]`，末尾不留任何折叠小尖头。
    - **交互心智由“点箭头展开”转为“整行隐式可点击（Row Affordance）”**：鼠标 Hover 时整行触发微弱背景提亮（`var(--tint-hover)`），鼠标指针变为 `pointer`，仅在 Hover 或已展开时，右端才平滑淡入弱化的展开指示，或仅靠行展开动画与内容自然呈现。
    - 修复动作文本与意图文本的去重算法，消除类似 `列出目录 crates 列出目录 crates` 的文本叠词噪波。

### 3. 底部 Composer 与 NoticeBar 的结构收敛与内联融合
- **架构方案**：
  - 终结“胶囊堆叠”模式，将 `ComposerNoticeZone` 架构收纳为 `ComposerCard` 的可选顶部嵌入槽（Embedded Header Slot）：
    - 当有服务商密钥未配置、权限警告或计划进度条时，**不生成独立的外部浮动胶囊**，而是作为 Composer 容器内部的顶栏（Top Bar），与输入框共享同一个外轮廓与底色。
    - 去除所有内外嵌套描边，整个输入区回归为如 Codex 般纯粹的一体化浮动底座（Unified Dock）。

### 4. 设立代码与设计门禁：Border-Zero 渐进收敛策略
- **架构方案**：
  - 在 `scripts/` 中新增静态检查脚本 `check-border-noise.mjs`，接入 `check:desktop` 流水线：
    - 对主聊天流相关组件（`chat-message-row`, `chat-tool-call`, `chat-composer`）建立 1px border 减量上限白名单。
    - 禁止在非表单控件的展示型组件中裸写 `1px solid var(--border-*)`。
    - 将存量 329 处 1px border 纳入技术债务收敛跟踪，强制新组件必须优先使用 `Surface` 色阶与 `gap` 留白。

## 未确认项

1. **Win11 Mica 材质与透明度折射动态比**：
   当应用运行在支持 Windows 11 Mica / Acrylic 的宿主环境下（`tokens.css:2283-2302`，`--outer-layer-bg: color-mix(... 68% transparent)`），侧栏与背景会透出系统桌面壁纸的色调。如果直接完全去除分栏线，在壁纸极端复杂（如高对比黑白壁纸）时，纯靠透明底色是否能保证足够的侧栏可读性，需要后续在真实 Mica 开启的真机环境下进一步验证。
2. **高 DPI 屏幕下的半像素发丝线渲染表现**：
   在 125% / 150% Windows 缩放比例下，部分现存的 1px border 会被 Chromium/WebView2 栅格化为模糊的 1.25px 或 1.5px 杂色带，进一步放大了“脏污感”。这属于底层渲染管线耦合，需结合高分屏截图作专项抽样。
