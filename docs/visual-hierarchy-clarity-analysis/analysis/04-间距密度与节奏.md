# 视觉层级清晰度分析 · 维度 04：间距、密度与垂直节奏（Spacing / density / rhythm）

> **分析对象**：参考界面（Codex，截图 `docs/visual-hierarchy-clarity-analysis/evidence/ref-codex.png`） vs 我们的界面（Crish，截图 `docs/visual-hierarchy-clarity-analysis/evidence/ours-crish.png`）  
> **核心议题**：为什么 Codex 的垂直节奏呼吸自如、信息单元聚类分明，而 Crish 呈现出“行距均匀平铺、接近性原则失效、水平内衬双重叠缩、信息密度稀释”的视线泥淖？  
> **分析员身份**：UI 视觉分析员（只读分析，不改源码；基于截图像素扫描、源码路径与实测统计数字）

---

## 结论摘要

1. **等间距平铺陷阱：格式塔『接近性原则』在垂直维度彻底瓦解**：
   实测行扫描表明，Crish 聊天流内部无论是思考行、工具调用行、正文段落、还是状态提示行，其行间垂直 gap 均在 **13px ~ 19px 之间均质徘徊**（平均 15.6px）。正文行距（`line-height: 1.68` 产生字间距约 9.5px）与工具调用固定高度（`height: 24px`）、段间距（`margin-bottom: 0.65em ≈ 9.1px`）相互抵消，消除了任何“组内紧密收拢（4-8px）”与“组间分界拉开（20-28px）”的梯次反差，导致用户眼球面对的是一整屏机械等距的碎片行，大脑无法自动将“思考-执行-结论”聚类为连贯认知单元。
2. **参考界面（Codex）的微密度聚类与块级呼吸韵律**：
   Codex 将执行流步骤在组内以 **5px ~ 8px 极紧密间距**聚合成连贯任务簇，而在任务簇与正文段落之间、段落与后续任务之间，均留出严格的 **20px ~ 21px 呼吸槽**；在右侧子智能体面板中，卡片内部主副标题仅相隔 **5px ~ 6px**，同级卡片间相隔 **18px ~ 20px**，大分组标题跨度达到 **32px**（`5px << 20px << 32px`）。垂直节奏呈现极具音乐感的 3 级梯次跳跃，信息密度虽高（每屏 35+ 单元 vs Crish 12 单元）却丝毫不显局促。
3. **侧边栏结构性近距离违规（Proximity Inversion）**：
   Crish 侧边栏列表项 `.sessionItem` 高度死锁为 `28px`，组内相邻项垂直紧贴（gap: 0），但文字基线距离为 28px；然而大业务分组 `.section` 的下外边距却被锁在 `margin-bottom: var(--space-2)`（**仅 8px**）！导致组内两行文字间隙（~14px 视觉空白）竟然大于组与组标题之间的距离（8px），严重违反格式塔接近性原则，置顶、项目、对话三大板块混成一团。
4. **水平内衬双重堆叠（Double Padding Stacking）与留白异化**：
   在 1024px 视口下，Crish 主对话区宽 828px，容器 `.listInner` 与 `.chatCol` 声明 `max-width: min(var(--chat-col-max, 760px), 100%)` 导致左右 margin 各留 34px，随后 `.listInner` 施加 `padding: 0 var(--chat-stream-pad-x)`（20px），接着虚拟切片容器 `data-chat-slice-container` 又在 inline style 中硬编码写入 `left: 20px; right: 20px`（`CHAT_SCROLL_PAD_X`）。双重内衬叠加使得实际内容区左边缘被迫内缩至 X=296（距侧栏多达 **100px 空洞**），阅读有效宽度被严重挤压至 619px；而顶部面包屑左起 X=314，工具行展开箭头却突破至 X=1010，导致左右留白既浪费空间又边缘犬牙交错。
5. **Token 体系的“名义治理”与硬编码字面 px 泛滥**：
   代码库虽定义了 `--space-0_5` ~ `--space-10` 梯级，但实际 CSS 中：**padding 硬编码 px 高达 510 处（占 55.0%）**、margin 硬编码 px 145 处（占 47.2%）、gap 硬编码 px 318 处（占 30.7%）、**line-height 字面裸写高达 283 处（占 67.5%）**。大量 `3px`, `5px`, `7px` 等奇数魔术数字与混杂单位直接破坏了 4px/8px 空间栅格；排版未建立行高网格（Baseline Grid），垂直节奏完全退化为各组件局部的随机构造。

## 参考界面做对了什么（具体）

参考 Codex 界面（`docs/visual-hierarchy-clarity-analysis/evidence/ref-codex.png`，视口尺寸 1024 × 778），其视觉秩序、清晰度与空间呼吸感的本质，在于**严格恪守格式塔接近性原则（Law of Proximity），通过强弱分明的微密度聚类（Step Chunking）与块级基线节奏（Vertical Rhythm Grid），实现高效的信息组织**：

### 1. 执行步骤的微密度聚类（Micro-density Step Chunking）
- **截图观察（聊天区 Y=122..234）**：
  连续 4 个执行步骤（`Import failure state已完成`、`运行了命令`、`Asset scope sync fix开始工作`、`Recovery state review已完成`）：
  - 步骤内部高度紧凑，行间垂直空白（Gap）实测仅为 **6px ~ 8px**；
  - 状态图标（14px）与极简文本紧密咬合，没有给单行套用独立厚重卡片；
  - 这种紧致的排布把 4 行分散操作收敛为一个认知簇（Chunk）——用户在潜意识中一眼就能看出“这是一组正在进行的自动化流水线”，而不是 4 段散落的内容。

### 2. 严谨一致的块级呼吸槽（Block-Level 21px Baseline Rhythm）
- **截图观察（聊天区段落与步骤间隙）**：
  通过精确像素行扫描，Codex 在主对话流中呈现出惊人的一致性基线：
  - 步骤簇末尾（Y=234）到正文段落第一行（Y=242）：正文内部两行（Y=242..253 与 Y=262..274）段内行距严格为 **7px ~ 8px**；
  - 正文末尾（Y=274）到后续执行动作（Y=296）：垂直间隔为 **21px**；
  - 执行动作（Y=307）到下一段正文（Y=329）：垂直间隔为 **21px**；
  - 正文末尾（Y=361）到后续命令（Y=383）：垂直间隔为 **21px**；
  - 命令（Y=395）到下一段正文（Y=416）：垂直间隔为 **20px**；
  - 正文末尾（Y=524）到后续步骤（Y=546）：垂直间隔为 **21px**。
- **设计智慧**：
  段落内部行距（7-8px）与块级（Block-to-Block）间距（20-21px）形成严格的 **1 : 2.6** 反差对比。用户阅读时，视线自然在段内流畅滑行，在遇到 21px 空白时自然停顿，形成极其舒适的生理呼吸节拍。

### 3. 右侧任务协同面板：教科书级的三级梯次接近性
- **截图观察（右侧子智能体面板 X=631..1023，Y=60..700）**：
  Codex 右侧面板在垂直方向承载了 2 个运行中任务卡片、2 个大分组标题、10 个完成项与折叠控制，信息密度极高，却给人以井井有条的安定感。其实测垂直几何具有严密的数学比例：
  - **第 1 级（卡片内亲密关系）**：任务标题（如 `Startup graph analysis`，H=18px）到副标题（`checking modelVendor chunk size`，H=12px），垂直间隙仅 **5px ~ 6px**；
  - **第 2 级（同类卡片并列关系）**：卡片 1 到卡片 2（`Recovery state review`）之间的垂直间距为 **18px ~ 20px**；
  - **第 3 级（不同大板块关系）**：进行中卡片组末尾（Y=227）到下一个大业务分组标题 `完成 · 20`（Y=260）之间，拉出了长达 **32px** 的大留白缓冲槽！
  - **比例规律**：`5px : 20px : 32px ≈ 1 : 3.6 : 5.8`。正是这种“组内极紧密、同级适度疏朗、跨组大幅拉开”的几何反差，彻底省去了多余的物理横线，单靠空间留白就立起了坚不可摧的视觉层级。

### 4. 空间利用率与凝聚阅读列（Spatial Efficiency & Cohesive Column）
- **截图观察（水平布局）**：
  - 窗口全宽 1024px，左侧采用 **46px** 极窄 Icon Dock，省出大量水平空间；
  - 主聊天区占宽 **584px**，Composer 占宽 **558px**（宽度利用率达 95.5%，左右各留 13px padding）；
  - 右侧为任务协同留出了 **394px** 的完整第二工作区；
  - 主阅读列宽度稳定在约 520px ~ 550px，完全符合人眼最佳阅读字符行宽（50-75 字符），左贴导航、右抵面板，没有任何一处超过 25px 的无效荒漠留白，整个界面既紧凑又沉稳。

### 5. 一体化沉着输入底座（Integrated Composer Docking）
- **截图观察（底部 Composer Y=675..763）**：
  Composer 高度达 **88px**，内部占位文字与底部功能按键（`+`、`完全访问`、模型选择、语音、终止）同处在同一卡片内部，上下内边距各约 **10px ~ 12px**。卡片底边缘距离窗口下边框仅 **15px**，上方与消息流留出 **25px** 安全距离，作为一个整体沉稳地锚定在窗口底部，消除了任何飘浮感。

## 与其他维度的耦合点

间距、密度与节奏不是孤立的视觉参数，它与整个界面的光学、结构和信息架构深度互锁：

1. **与维度 01（对比度与灰度阶）的恶性互锁**：
   当 Crish 的垂直间距彻底等距平铺（13~19px）时，信息在空间上失去了聚类边界；此时如果文字灰度阶（Text Hierarchy）又缺乏拉伸（正文、次级、三级灰度反差微弱），整个消息区就会迅速沦为一团没有视觉着力点的“灰色迷雾”。相反，Codex 即使在弱对比度下，依然能凭借 5px 与 21px 的强烈空间聚类引导用户视线。
2. **与维度 03（边框、分隔线与视觉噪声）的代偿因果**：
   这是整个 UI 架构退化的最核心链条：**因为没有在排版层建立起健康的留白呼吸槽（Spacing Rhythm），页面各模块之间无法依靠负空间（Negative Space）自动分界，前端开发者便被迫大量使用物理边框（`border: 1px solid var(--border-subtle)`）来强行划定区域！** 仓库中多达 1578 处 border 和 510 处硬编码 padding，正是空间间距体系失灵后的“病理性代偿产物”。
3. **与维度 05（对话流信息架构）的结构耦合**：
   Crish 目前将“单步执行工具调用”平铺在主对话流中，与正文 Markdown 处于同一 DOM 列同级排布；而 Codex 将其包裹为收敛的流水线过程簇（Step Chunking）。如果信息架构不提供“过程簇容器”的原生概念，CSS 层面就无法施加“组内 6px、组间 20px”的节奏规则。
4. **与维度 07（输入区与状态条）的布局堆叠冲突**：
   ComposerNoticeBar 目前作为单独的网格行硬塞在 Composer 顶部，由于缺乏统一的底座空间调度，NoticeBar 的 6px 外边距与 Composer 的 6px 内边距发生物理相撞，破坏了视口落地的整体性。
