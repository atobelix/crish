# 维度 07：输入区 Composer 与状态条（Composer & Status Strips）视觉层级分析

## 结论摘要

1. **容器架构从「单一内聚卡片」退化为「多级离散浮岛」**：参考界面（Codex）将输入框与底部工具栏严格封装在**单个圆角矩形卡片**内（1 个视觉容器、1 个背景底色、0-1 条低对比度边缘描线）；而 Crish 在主输入卡片上方额外堆叠了一个高度 48px 的独立自适应药丸横幅（`ComposerNoticeBar`），形成了两个外形相同（均为 20px 圆角胶囊）、宽度脱靶（360px 居中胶囊骑在 720px 全宽胶囊上）、层级平权的竞争容器，切断了用户的输入视线。
2. **状态元数据「完全反客为主」，警示色语义严重越权**：Codex 中的「完全访问」权限以次级中性暖灰弱字（与底板对比度仅约 1.6:1）收敛于左侧辅助工具组；而 Crish 在单行状态下将其挪至右侧端点，并硬编码混入了暗色主题下的 `--accent-orange`（`oklch(0.8 0.17 75)`），实测像素呈现高饱和刺眼琥珀金黄（RGB: `222, 160, 23`），WCAG 对比度高达 **9.38 : 1**。本属后台静默配置的权限状态，被赋予了甚至压倒主正文（9.56:1）和发送操作的最高警戒级视觉权重。
3. **关键操作端点缺失与动态隐藏导致「视觉重心蒸发」**：Codex 无论输入与否，右侧始终常驻高对比度蓝色实心圆发送/停止按钮（RGB: `44, 103, 197`）与清晰的模型选择器，形成稳定的视觉定盘星；而 Crish 因首次未配密钥触发 `showModelPicker = false` 将模型选择器彻底卸载，且发送按钮在无文字时被 CSS 归零（`width: 0; opacity: 0`），导致整个输入框右半部被完全挖空，仅孤零零暴露出亮黄色的「完全访问」，主次层级彻底倒置。
4. **CSS 架构过度膨胀与历史选择器污染**：`ChatComposer.module.css` 单文件体积达到 **45.3 KB（1,971 行）**，在单一文件中塞入了浮动审批条、目标进度条、选区批注、附件卡片、主输入网格等四层垂直堆叠样式；同时混杂了 `.container`、`.containerDense`、`.composerCard` 多代重构的选择器竞争，且聚焦态（`:focus-within`）的描边色依然维持原样 `var(--border-subtle)`，违背了微感知焦点反馈规范。
5. **栅格系统断裂与宽度脱靶**：主消息流与输入卡片严格遵循 760px 栅格（有效内宽 720px），但上方的通知条采用 `width: fit-content; margin: 0 auto;`，以居中悬浮的方式脱离了主视线垂线，破坏了自上而下的视觉流动连续性。

## 参考界面做对了什么（具体）

参考 Codex（`ref-codex.png`，尺寸 1024×778）在底部 Composer 区域的处理展现了极高的工业级界面克制与视觉聚焦力：

```
Codex 底部卡片结构示意：
┌─────────────────────────────────────────────────────────────────┐
│ 和 Codex 一起工作                                               │ <- 单行/多行输入区，弱灰占位符
│                                                                 │
│  ＋   ⓘ 完全访问 ⑂                           6 Luna Max ▾  🎙  ■ │ <- 底部轻量控件栏（一体化）
└─────────────────────────────────────────────────────────────────┘
```

1. **绝对的一体化容器（Single-Card Enclosure）**：
   - Codex 底部区域仅有 **1 个**圆角卡片容器（背景色 `#363636`，与主背景 `#181818` 形成温和的 2.05:1 层级抬升，无突兀硬边框）。
   - 卡片内部自上而下分为「输入编辑区」与「底部控制栏」，两者处于同一个背景域内，没有多余的卡片分割线或浮动胶囊，视觉整体感极强。
2. **极度克制的信息权重分配（Strict Information Hierarchy）**：
   - **Level 1（主操作端点）**：右下角的正圆发送/停止按钮，使用清爽高对比度蓝色（实测 RGB: `44, 103, 197`，#2C67C5，对比度 3.52:1），是整个暗色底板上**唯一的鲜艳强调色**，视觉流向的明确归宿。
   - **Level 2（核心参数选择）**：模型选择器（`6 Luna Max ▾`），字号小（约 12px），中性灰弱色，提供就地切换能力而不喧宾夺主。
   - **Level 3（功能扩展）**：左侧 `+`（附件）与右侧麦克风（语音），纯透明底（Ghost），悬停才微亮。
   - **Level 4（后台状态监控）**：左侧「完全访问」权限指示，实测文字为微弱暖灰（平均 RGB: `83, 55, 41`，对比度仅约 1.62:1），与加号、分支图标并列在左下角，完全作为一个不打扰用户的次要元数据存在。
3. **零干扰的任务通道（Uninterrupted Task Channel）**：
   - 输入框上方没有任何外部悬浮横幅或骑跨药丸；如果需要引导或错误提示，绝不通过在输入框头顶追加独立浮岛打断用户输入。
   - 输入卡片与上方消息内容保持绝对一致的左右边距，形成一条自上而下的刚性视觉边线（Alignment Spine）。

## 我们的现状与根因（带证据）

### 1. 双重独立胶囊容器堆叠，打断主任务焦点

- **截图证据（`ours-crish.png`）**：
  底部赫然出现上下两层平行并列的药丸容器。上方是钥匙图标 +「首次使用请先配置服务商密钥与模型」+ 灰底「去配置」按钮；下方是主输入框。两个容器高度几乎相同（48px vs 40px），圆角完全相同（均为 20px），带有独立的 1px 细描边。
- **源码根因**：
  - `ChatComposer.tsx:239-253`：
    在主输入卡片外，独立渲染了 `composerNoticeZone`：
    ```tsx
    {effectiveNotice ? (
      <div className={styles.composerNoticeZone} ...>
        <div className={styles.composerNoticeZoneInner}>
          <ComposerNoticeBar
            notice={effectiveNotice}
            ...
          />
        </div>
      </div>
    ) : null}
    ```
  - `ComposerNoticeBar.module.css:7-22`：
    ```css
    .noticeBar {
      display: flex;
      align-items: center;
      justify-content: space-between;
      gap: 10px;
      height: 48px;
      min-height: 48px;
      max-height: 48px;
      width: fit-content;
      max-width: min(760px, calc(100% - 24px));
      margin: 0 auto;
      padding: 0 10px 0 14px;
      border-radius: var(--composer-radius-single, 20px);
      border: 1px solid var(--border-subtle);
      background-color: var(--bg-elevated);
      ...
    }
    ```
  - `ChatComposer.module.css:1268-1282`：
    ```css
    .composerCard {
      --composer-radius-outer: var(--composer-radius-single, 20px);
      border: 1px solid var(--border-subtle);
      border-radius: var(--composer-radius-single, 20px);
      background: var(--composer-bg, var(--surface-input));
      ...
    }
    ```
- **视觉冲突**：
  通知条高度（48px）甚至超过了未激活的单行输入卡片（40px）。本应作为轻量通知的辅助信息，通过 `margin: 0 auto` 居中且使用与输入框完全相同的圆角与描边，变成了一个平权的实体卡片。用户的首要任务是输入，但视线从消息区向下移动时，首先撞上的是这个沉重的通知横幅，直接阻断了操作流。

### 2. 「完全访问」权限徽标色彩与位置严重越权

- **截图证据（`ours-crish.png`）**：
  主输入卡片右侧最显眼的位置，赫然悬挂着金黄色的「完全访问」文字。全卡片在没有文字输入时没有任何其他颜色，这个金黄色文字成为了全屏唯一的色度高光点。
- **源码根因与 Token 链分析**：
  - 组件逻辑 `PermissionModeMenu.module.css:89-91`：
    ```css
    .permPill[data-perm-mode='full'] {
      color: color-mix(in srgb, var(--accent-orange) 85%, var(--text-primary));
    }
    ```
  - 主题 Token 链（暗色模式 `tokens.css:1325, 1364`）：
    ```css
    --accent-orange: oklch(0.8 0.17 75);
    --color-warning: var(--accent-orange);
    ```
  - 将 `oklch(0.8 0.17 75)` 转换至 sRGB 空间为 `rgb(252, 171, 0)`（#FCAB00），按 85% 与暗色模式的主文本色 `--user-text-primary: #f5f5f5` 混合后，实际文字颜色为 `rgb(251, 182, 37)`（#FBB625）；在截图实际渲染采样中（`ours-crish.png:878, 660`），测得像素为 `rgb(222, 160, 23)`（#DEA017）。
  - **实测 WCAG 对比度**：
    在输入卡片背景色 `#141414`（或 `#1e1e1e`）上，该金黄色文字的对比度高达 **9.38 : 1**！
    而同界面的次级文本（`text-secondary`）对比度仅为 **5.43 : 1**，弱文本（`text-tertiary`）仅为 **2.73 : 1**。
  - **位置倒错**：
    `ChatComposer.tsx:369-387`：在单行状态下（`!isMultiline`），权限菜单被强行塞入右侧动作区 `ComposerFusedTrigger` 的 `prefix`：
    ```tsx
    <div className={styles.actionRight} data-composer-grid="right">
      <ComposerFusedTrigger
        prefix={
          !isMultiline ? (
            <PermissionModeMenu
              mode={permissionMode}
              hideChevron
              variant="fused"
              ...
            />
          ) : undefined
        }
      >
        {rightActions}
      </ComposerFusedTrigger>
      ...
    </div>
    ```
    本应作为输入框辅助状态的权限元数据，在单行时脱离了左侧辅助区，跳跃到了卡片右端，直接占据了发送按钮通常所在的黄金操作位。

### 3. 操作端点动态隐藏，视觉重心崩溃蒸发

- **截图证据（`ours-crish.png`）**：
  右侧没有任何发送按钮、没有任何模型选择器、没有任何语音按钮，只剩下一个黄色的「完全访问」。整个输入框右半部像发生截断一样空空如也。
- **源码根因**：
  1. **模型选择器被完全卸载**：
     `ChatCard.tsx:159-166`：
     ```tsx
     const mainModelBadgeNode = state.showModelPicker ? (
       <ModelBadgePicker ... />
     ) : null;
     ```
     在 `apps/crish-desktop/src/api/providerProfiles.test.ts:367-370` 验证的逻辑中：首次启动或未配置有效 Provider Key 时，`state.showModelPicker` 强行置为 `false`！导致 `rightActions` 直接为 `null`，模型切换器彻底从 DOM 中消失。
  2. **发送按钮在无内容时归零折叠**：
     `ChatComposer.module.css:1541-1550`：
     ```css
     .sendBtnCircle,
     .sendCircle {
       display: flex;
       align-items: center;
       justify-content: center;
       height: 28px;
       width: 0;           /* 宽度强制为 0 */
       min-width: 0;
       padding: 0;
       margin-left: 0;
       opacity: 0;          /* 完全透明 */
       transform: scale(0.92);
     }
     ```
     只有在输入框有内容（`active`）或者全页空态（`session-empty`）时才通过补丁恢复宽度。在已存在历史对话但当前未输入时，发送按钮直接「蒸发」。
  3. **连锁反应**：
     模型选择器消失 + 发送按钮归零 + 麦克风折叠，导致原本只作为前缀修饰的「完全访问」权限药丸独占了整个右侧容器！把一个不重要的状态指标推到了最刺眼的风口浪尖。

### 4. 几何对齐失序：自适应短胶囊骑在撑满长胶囊上

- **截图证据（`ours-crish.png`）**：
  上方的通知条宽度仅约 360px，孤立居中悬浮；而下方的输入框宽度约 720px，撑满内容列。垂直投影两端各露出约 180px 的空当，形成怪异的倒凸字形。
- **源码根因**：
  - `ChatCard.module.css:214-220`：内容列 `.chatCol` 宽度为 `max-width: min(var(--chat-col-max, 760px), 100%)`，内衬左右 20px，输入卡片 `width: 100%` 撑满。
  - `ComposerNoticeBar.module.css:16-18`：
    ```css
    width: fit-content;
    max-width: min(760px, calc(100% - 24px));
    margin: 0 auto;
    ```
    它没有遵守主栅格约束，而是按内容宽度 `fit-content` 自适应并 `margin: 0 auto` 居中。上面的长篇测试报告卡片是左对齐的，输入框是撑满的，唯独通知条居中且短小，彻底打破了界面的轴线一致性（Alignment Spine）。

### 5. CSS 架构体量失控与焦点态退化

- **源码证据**：
  - `ChatComposer.module.css` 拥有 **45,324 字节、1,971 行代码**，远超单组件样式规范（通常 <500 行）。
  - 在这个单文件内，塞入了 4 个 Layer 的全部样式：
    - Layer 1: 浮动权限审批条（行 68-348，共 280 行）
    - Layer 2: 目标/计划模式进度条（行 350-649，共 300 行）
    - Layer 3: 上下文与文件引用卡片区（行 651-1028，共 378 行）
    - Layer 4: 主输入区与正圆发送按钮（行 1264-1971，共 708 行）
  - **聚焦态伪类失效与规范冲突**：
    `ChatComposer.module.css:1305-1311`：
    ```css
    .composerCard:focus-within,
    .composerCard:active {
      border-color: var(--border-subtle);
      box-shadow:
        0 1px 3px color-mix(in srgb, var(--shadow-color) 1.5%, transparent),
        0 3px 8px -1px color-mix(in srgb, var(--shadow-color) 2%, transparent);
      outline: none;
    }
    ```
    由于未激活时 `.composerCard` 默认就是 `border: 1px solid var(--border-subtle)`，导致获得焦点时边框完全不发生任何变化；但同时在行 1690 又存在废弃的 `.container:focus-within { border-color: var(--border-color); }` 选择器残留。组件缺乏清晰的单一真理源（SSOT）。

## 与其他维度的耦合点

1. **与【维度 04：卡片、容器与边框体系】的耦合**：
   - 输入卡片与通知条的描边使用了 `var(--border-subtle)`，但两个容器叠加导致出现了「双层边框并立」现象。与信息卡片的边框冗余问题同源：过度依赖独立实体卡片承载单一信息，缺乏一体化收敛体系。
2. **与【维度 05：色彩、语义色与对比度】的耦合**：
   - `--accent-orange`（`oklch(0.8 0.17 75)`）被滥用于普通运行态「完全访问」权限。这是典型的「语义色污染」（Semantic Color Pollution）——将警告色系（Warning/Orange）误用为状态标签，导致系统真正出现危险/警告时失去色彩分化能力。
3. **与【维度 06：信息密度、留白与呼吸感】的耦合**：
   - 底部输入区纵向占用了 `48px（通知条）+ 6px（间隙）+ 40px（输入框）+ 20px（外边距） = 114px` 的空间。通知条侵占了本该留给历史消息浏览的竖向呼吸空间。
4. **与【维度 02：主次结构与视觉流线】的耦合**：
   - 发送按钮的宽度弹性坍塌（0px 隐藏）破坏了视线的稳定「终点锚定」（Anchor Point），让用户视线在输入区迷失，无法建立固定的交互肌肉记忆。

## 架构级修复方向

### 1. 容器架构一体化：消除外挂浮岛，收归卡片内嵌

- **方案**：废除输入框上方独立的 `ComposerNoticeBar` 浮动胶囊容器。将系统配置提示、权限状态、模型切换收归到**单个 Composer 卡片**的内部结构中：
  - **模式 A（内嵌顶部提示横幅）**：若确有服务商未配置提示，将其作为卡片内部的顶层内嵌条（嵌入同一张卡片内，无外圈多余描边，无独立圆角胶囊），与输入区共享同一背景底板。
  - **模式 B（落地空态/设置浮层引导）**：对未配置密钥的状态，直接在会话空态页面（Empty State）通过中心化导流卡片引导配置，而在活跃会话界面仅在模型选择器处展示微弱的 `(!)` 状态点，不再常驻大横幅横亘在输入框顶。

### 2. 权限指示降级为次级元数据，回归中性灰度

- **方案**：彻底剥离 `PermissionModeMenu` 对 `--accent-orange` 的硬编码绑定。
  - 将「完全访问」、「计划模式」等常规运行状态统一收拢至 `--text-secondary` 或 `--text-tertiary`（暗色模式下对比度控制在 **2.5:1 ~ 4.5:1** 之间，柔和不刺眼）。
  - 只有当权限处于「危险提权拦截」或「审批中」（Approval Required）时，才允许条件注入柔和的警示色。
  - 位置固定回归到输入框底部控制栏的**左侧辅助区**（与 `+` 加号并列），严禁单行态跳跃至右侧动作端点。

### 3. 操作端点常驻机制：保留常态定位锚点

- **方案**：发送/停止按钮与模型选择器必须建立**稳定的物理占位**，严禁宽度彻底归零（`width: 0`）。
  - 发送按钮在无内容时，应以 `disabled` 态（低透明度中性灰，如 `opacity: 0.35`，尺寸固定 28×28px）常驻右下角，使用户明确知晓操作终点。
  - 模型选择器在未配置密钥时，显示为占位文本（如「请选择模型 ▾」），点击直接呼出配置弹窗，而不是将整个节点从 DOM 中注销，避免造成右侧布局严重坍塌。

### 4. 拆解 45KB 上帝 CSS，按分层实体解耦

- **方案**：将 `ChatComposer.module.css`（1,971 行）按照职责硬性解耦为独立模块：
  - `ComposerCard.module.css`：专注于卡片外框、栅格、padding 与聚焦态（<250 行）。
  - `ComposerSendControls.module.css`：专注于发送/停止圆按钮与排队态（<150 行）。
  - `ComposerFloatingLayers.module.css`：专注于浮动审批与进度条（<200 行）。
  - 清理历史残留选择器（彻底清退 `.container`、`.containerDense` 等废弃类名），实现 CSS 资产单一真源（SSOT）。
