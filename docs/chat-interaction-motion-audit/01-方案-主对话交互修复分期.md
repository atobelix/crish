## 2. 任务 D：修复对话流丢内容（根因，最高优先）

### 2.1 实证结论

**数据层完整，渲染层不更新。** 真实宿主取证（tauri-mcp `execute_js`，会话 `sess-1789805341699`，消息 `assistant-msg-mu83zw9d-d5fea8e4-0003`）：

| 观测面 | 结果 |
|---|---|
| session store 的 `blocks` | `4` 个，类型序 `thought,text,tool_call,text` |
| session store 的 `toolCalls` | `1` 个（`project_tree:success`，output 9702 字符） |
| session store 的 `thinking` | 90 字符 |
| **React fiber props（`ChatAssistantMessageRowInner`）** | `blocksLen: 4`、`blockTypes: "thought,text,tool_call,text"`、`toolCalls: 1` —— **数据完整到达组件** |
| **实际 DOM** | `[data-section="tool-calls"]` = **0**；`[data-testid="reasoning-row"]` = **0**；`_assistantTimelineStream` 内**只有一个** `_contentText[data-kind="text"]` |

### 2.2 根因

**`apps/crish-desktop/src/api/sessionEventProjection.ts` 对 store 内消息对象做原地 mutate**，违反 React 不可变契约：

| 行号 | mutate 操作 |
|---|---|
| `:258` | `a.status = 'completed'` |
| `:262` | `a.thinking = thought` |
| `:267` | `a.thinkingTurns[ttIdx]!.content = thought` |
| `:269` | `a.thinkingTurns.push(...)` |
| `:275 / :305 / :328 / :346 / :369` | `if (!a.blocks) a.blocks = []` |
| `:280` | `a.blocks[blkIdx]!.content = thought` |
| `:282` | `a.blocks.push({ type: 'thought', ... })` |
| `:307` | `last.content = text` |
| `:308` | `a.blocks.push({ type: 'text', ... })` |
| `:297 / :301` | `a.text = text` |
| `:309` | `a.streamTextOffset = text.length` |

**失效链路**：

```
sessionEventProjection 原地 push thought / tool_call 块
  → msg 对象引用不变、msg.blocks 数组引用不变
  → assistantRowPropsEqual 比较 prev.msg.blocks === next.msg.blocks（chatMessageRowUtils.ts:272）
  → 返回 true → React.memo bailout
  → MessageContent 不重渲染
  → DOM 停留在「只有 text」的旧渲染结果
```

这解释了 fiber props 是**新数据**、DOM 是**旧结果**的悖论，也解释了用户观察到的「好像会丢」——它取决于该轮是否恰有其他字段变化触发重渲染，是**时序竞态**。

`blocks` 一旦被丢弃，`buildAssistantTimeline`（`apps/crish-desktop/src/api/tool-presentation/timelineNormalizer.ts:97`）自然产不出 `thought` / `tools` 项，`partitionTimelineSegments`（`apps/crish-desktop/src/api/tool-presentation/timelineSegmenter.ts:70`）也就不会产出过程段 —— 后续链路本身是正确的，问题全在数据入口。

### 2.3 改动面

- **主改**：`apps/crish-desktop/src/api/sessionEventProjection.ts` —— 全部 mutate 改为不可变更新（返回新消息对象 / 新数组），保持 `id` 稳定。
- **同类排查**：`apps/crish-desktop/src/api/subagentTimeline.ts:92-199`（同样 `a.blocks.push` 模式）。
- **契约守护**：为投影层补一条「不可变输出」断言测试（投影前后旧对象引用内容不得变化）。

### 2.4 验收断言

1. 投影后 `prevMsg !== nextMsg` 且 `prevMsg.blocks !== nextMsg.blocks`。
2. 构造 `thought → text → tool_call → text` 事件序列，投影结果 `blocks` 类型序为 `thought,text,tool_call,text`。
3. 真实宿主：该轮结束后 `[data-section="tool-calls"]` 与思考行**均存在**（当前为 0）。
4. 反复 reload / 多轮追加后，历史轮的思考与工具调用**不消失**。

## 5. 任务 C：块级结构流式渲染（表格 + 列表等），**不闪为前提**

### 5.1 现状与根因（两层，缺一不可）

**第一层 —— 块切分层：列表/表格在流式期间永远是「未封口草稿」。**

`apps/crish-desktop/src/api/markdown/IncrementalBlockSplitter.ts:321-354` 把「普通段落 / 列表 / 表格」归为同一类处理，注释原文：

> 7. 普通段落 / 列表 / 表格：持续累积直到遇到空行或新的独立块起始标志

其边界扫描只在遇到**空行**（`:328`）或**新的独立块起始**（标题 / 代码围栏 / 分割线，`:336-340`）时才封口；否则 `break`（`:354`）继续等待后续 chunk。非 flush 态还额外排除末行（`:193`、`:325`）。**⇒ 整个列表 / 表格在流式全程都是 draft。**

**第二层 —— 渲染层：draft 一律画源码。**

| 位置 | 事实 |
|---|---|
| `apps/crish-desktop/src/components/chat-message-row/MarkdownBlockItem.tsx:83-85` | `const renderTarget = isSealed ? text : ''` —— **只有封口块才向 Rust 发起编译** |
| 同文件 `:122-124` | 活跃尾块走 `el.textContent = activeContent` ⇒ **直接画 Markdown 源码** |
| 同文件 `:89` | `activeContent = virtualClosedText \|\| text` |
| `apps/crish-desktop/src/api/markdown/SpeculativeVirtualCloser.ts:118-132` | 表格补全**只补末行尾部 `\|`**，**不补分隔行** |
| `apps/crish-desktop/src/api/markdown/tableProbe.ts` | `hasTableBlock` 仅返回布尔，用途是抑制打字光标（`MarkdownBlockItem.tsx:163-166`），**不做渲染** |
| `apps/crish-desktop/src/components/chat-message-row/StreamingTableContainer.tsx` | 局部滚动容器（吸底 / 渲染隔离 / 吸顶表头），**生产零消费方**；其组件注释自称「单一真相源」且带 `isStreaming` prop ⇒ **属「待接线资产」而非废弃死代码**（前置条件由本任务提供，见 §5.4 第 6–7 条） |

两层叠加 ⇒ **列表与表格在流式期间全程显示源码，收口瞬间才变成渲染结果** —— 正是用户描述的「割裂 / 闪屏」。

### 5.2 「闪」的两个来源（必须分别消除）

1. **空白间隙**：`MarkdownBlockItem.tsx:135-138` 在封口且 LRU 缓存未命中时执行 `el.textContent = ''` —— **先把容器清空**，等 Rust/worker 就绪再填。这段空白即一次闪烁。
2. **形态剧变**：源码 → 渲染结果之间，列表标记（`- x` → `• x`）、缩进、行高、字重、块间距全部改变，视觉上是一次「跳变」。即使无空白间隙，仍感知为割裂。

⇒ **不闪 = 同时消除这两者**：既不能有空白窗口，也不能让「源码形态」先出现在用户眼前。

### 5.3 目标形态（按 R5 / R9）

块级结构**成立即渲染**：列表首项出现即渲染为真实 `<ul>/<ol>` 并逐项追加；表格分隔行完整出现即渲染为真实 `<table>` 并逐行追加。全程**不出现源码形态**，**不出现空白窗口**。

### 5.4 技术要点

1. **触发判据（结构成立的最小充分条件）**
   - 表格：**完整的 GFM 分隔行**（可复用 `tableProbe.ts:5` 的 `GFM_TABLE_DELIMITER_ROW_RE`）。仅表头行**不足**以构成表格。
   - 列表：**首个列表项标记**（`- ` / `* ` / `+ ` / `1. `）出现在行首。
2. **虚拟补全扩展**：`speculativeCloseBlock` 需在结构成立后补全**使其可被解析**的最小语法 —— 表格补缺失的分隔行；列表无需补全（GFM 列表天然可解析不闭合项）。补全仅存在于内存，**绝不污染原始文本流**（沿用现有 Virtual-Only 不变量，`SpeculativeVirtualCloser.ts:10`）。
3. **活跃尾块渲染路径改造**：`MarkdownBlockItem` 的 `isActiveTail` 分支需允许**未封口即发起编译**。既有「原地替换 + requestToken 校验」契约可复用（`MarkdownBlockItem.tsx:144-160`），但须调整两点：
   - 编译输入从 `isSealed ? text : ''` 改为「结构成立时取 `virtualClosedText`，否则不编译」；
   - **禁止清空**：编译期间保留上一版 HTML（当前 `:136` 的 `el.textContent = ''` 必须消除）。
4. **节流**：活跃尾块每帧变化，须对编译发起做节流/去抖（避免每帧触发 Rust 编译）。既有 `AdaptiveAnimateTimeline`（`api/markdown/AdaptiveAnimateTimeline.ts`）与 `SlidingWindowRateEstimator` 已提供速率自适应调度，优先复用而非新造。
5. **增量填充粒度（按 R5 / R9 / R10）**：**一律真增量** —— 已存在的结构单元其 DOM 节点必须复用，只允许「追加新单元」与「原地更新末尾活跃单元」两种操作，**禁止任何粒度的整块重建**（覆盖表格、列表、引用块、嵌套结构）。设计详见 `02-详案-块级结构真增量流式渲染.md`。
6. **待接线资产优先复用**（本次实测确认全部零消费方）：
   - `apps/crish-desktop/src/api/markdownCache.ts` 的 `markdownStreamingCacheKey` / `isMarkdownStreamingCacheKey` / `parseMarkdownStreamingCacheKey` / `invalidateMarkdownStreamCache` —— **流式专用缓存机制已设计但从未接线**；
   - `StreamingTableContainer.tsx` 的吸底与滚动隔离能力。

   > **定性修正（2026-09-19 评估）**：`StreamingTableContainer` 此前被多处表述为「死代码」，语气暗示其为未完成的遗留物。**该定性不准确** —— 其组件注释自称「流式表格局部滚动容器（**单一真相源**）」，设计完备（固定布局 + `contain` 隔离 + 8px 容差双向吸底 + 吸顶表头），且**专门带 `isStreaming` prop**。它未被接线的原因是**前置条件缺失**：它需要一个**已渲染好的 `<table>` 作 children**，而该前提正是任务 C 要建立的。
   > ⇒ 正确表述为**「待接线资产（前置条件由任务 C 提供）」**。这不改变「应复用而非新造」的结论，但改变风险提示 —— 见下条。

7. **三方高度观测的协同时序（接线 `StreamingTableContainer` 时的新风险）**：接线后，同一条消息行上的高度观测将由两方变为**三方**：
   - ① `MessageVirtualizer.tsx:196-208` 的行级 `ResizeObserver`；
   - ② `StreamingTableContainer` 内部的局部滚动视口（`contain: layout paint` + `content-visibility: auto`）；
   - ③ `03-详案` §4.2 的动画期冻结门禁。
   **要求**：接线时必须验证「局部滚动容器的吸底行为」不被 ② 的 `contain` 与 ③ 的冻结窗口互相干扰（吸底是局部 `scrollTop` 行为，冻结是行级高度写入，二者不得共用同一锁）；且 `content-visibility: auto` 可能使行高度在**离屏时失真**，需确认它不会向 ① 上报错误高度。**该验证列为任务 C 的 C6 阶段必做项**（不得以「复用既有资产」为由跳过）。

8. **反过度设计边界**：不得引入第三方 Markdown/表格渲染库；不得为表格或列表单独造一套解析器（必须复用 Rust 编译通道）；不得用「先渲染后隐藏」之类投机手段绕过。

### 5.5 验收断言

1. 构造「表头行 + 分隔行」中间态：DOM 中 `table` **已存在**（当前只有源码文本）。
2. 构造「首个列表项」中间态：DOM 中 `ul`/`ol` **已存在**（当前只有源码文本）。
3. 后续行/项到达时，`tbody tr`（或 `li`）数量**单调递增**，且 `thead` / 已有 `li` **不被重建**（以 DOM 节点引用恒定为断言）。
4. **全程无源码闪现**：流式期间 `_contentText` 内不得出现以 `\|`、`- `、`1. ` 开头的源码行。
5. **全程无空白窗口**：活跃尾块容器的 `innerHTML` 在任意两帧之间不得出现由非空变空的中间态。
6. 收口后与一次性完整渲染结果**逐单元格 / 逐项一致**。
7. `prefers-reduced-motion` 下不引入动画回归。
