## 0. 要解决的问题

当前主对话的 Markdown 渲染是**两态切换**：

- **活跃尾块（draft）**：`el.textContent = 源码`；
- **封口块**：Rust 编译后的 `innerHTML`。

因为列表 / 表格在流式全程都处于 draft（`IncrementalBlockSplitter.ts:321-354`），用户看到的是「**先出源码，收口瞬间跳变成渲染结果**」。用户判定这是**闪屏 / 割裂**，要求全部改为**真增量**。

---

## 1. 术语：「真增量」的判定标准（机器可判定）

本详案对「真增量」给出**可断言**的定义，避免「看起来不闪」这类主观验收。

### 1.1 三项硬指标

| 指标 | 判定方法 | 通过条件 |
|---|---|---|
| **节点复用** | 记录追加操作前后的 DOM 节点引用数组 | 已存在的结构单元节点**引用完全不变**（`before[i] === after[i]`） |
| **无空白窗口** | 逐帧采样活跃容器 | 任意相邻两帧之间，容器 `childNodes.length` 不得由 >0 变为 0 |
| **无源码形态** | 逐帧采样活跃容器的 `textContent` | 不得出现以 `\|`、`- `、`* `、`1. `、`> `、```` ``` ```` 开头的行 |

### 1.2 「真增量」的操作白名单

活跃容器上**只允许**三种 DOM 操作：

1. **追加（append）**：在末尾新增结构单元节点；
2. **原地更新（patch-in-place）**：更新**末尾活跃单元**的内容；
3. **删除（remove）**：仅在内容回退（retract / 重写）时发生。

**禁止**：`container.innerHTML = ...` 整块替换（这是当前实现，也是闪的根源之一）。

### 1.3 指标 2 的盲区修正（可见性维度）

> **修正记录（2026-09-19 评估）**：初稿指标 2 只查 `childNodes.length`，**存在盲区** —— 若实现为「清空 DOM + 把容器设为不可见」，则 `childNodes.length` 恒 ≥1（残留文本节点或占位节点），指标永远通过，但用户实际看不到任何内容。该盲区已在 `MarkdownBlockItem.tsx:136-137`（`el.textContent = ''` + `el.style.visibility` 组合）的真实链路中被证实存在。

**指标 2 扩展为双条件**：

| 子条件 | 判定方法 | 通过条件 |
|---|---|---|
| 2a 无空帧 | 逐帧采样 `childNodes.length` | 不得由 >0 变 0 |
| 2b **无不可见帧** | 逐帧采样容器的 `style.visibility` / `style.display` / `opacity` 与 `getBoundingClientRect().height` | 不得出现「DOM 非空但视觉不可见」的中间帧（`visibility === 'hidden'` 或 `display === 'none'` 或 `height === 0` 且预期应可见） |

⇒ **两条同时成立**方视为通过。仅 2a 通过不构成验收。

## 3. 目标形态

对**任意块级结构**（段落 / 标题 / 列表 / 表格 / 引用块 / 代码块 / 分割线 / 嵌套组合），在**结构成立的那一刻**即以真实元素渲染，后续内容以**追加**与**末尾原地更新**两种操作推进，全程不出现源码形态、不出现空白窗口。

**「结构成立」的最小充分条件**：

| 结构 | 成立判据 |
|---|---|
| 表格 | **完整的 GFM 分隔行**（复用 `api/markdown/tableProbe.ts:5` 的 `GFM_TABLE_DELIMITER_ROW_RE`）。仅表头行**不足**。 |
| 列表 | **首个列表项标记**（`- ` / `* ` / `+ ` / `1. `）出现在行首 |
| 引用块 | **首个 `>` 行** |
| 代码块 | **起始围栏行**（```` ``` ```` / `~~~`） |
| 标题 / 分割线 | 行首标记本身（已是完整单元） |
| 段落 | 首个非空行（无更具体结构时） |

## 4. 架构设计

### 4.1 数据流总览

```
流式 chunk
  └─ IncrementalBlockSplitter（既有，不改语义）
       ├─ 已封口块 → 既有路径：Rust 编译 → 整块 innerHTML（不变）
       └─ 活跃尾块（draft）
            ├─[新增] 结构探针 hasRenderableStructure(draft)
            │        ├─ 未成立 → 保持既有纯文本行为（唯一允许的源码态，且此时无结构可渲染）
            │        └─ 成立   → 进入真增量路径
            └─[新增] 真增量路径
                 ├─ 虚拟补全：speculativeCloseBlock 扩展（补表格分隔行等）
                 ├─ 节流编译：Rust md_render → HTML 字符串
                 ├─ 单元切分：splitHtmlIntoUnits(html) → Unit[]
                 └─ 单元协调：reconcileUnits(container, units)
                      ├─ 前缀复用（已存在单元节点不动）
                      ├─ 追加新单元
                      └─ 末尾单元原地更新
```

**关键取舍**：单元切分放在 **HTML 层**而非 Markdown 层。理由：
- HTML 是最终形态，单元边界（`table`/`ul`/`li`/`tr`/`p`）天然清晰，嵌套由浏览器解析器处理，无需前端理解 Markdown 嵌套语义；
- 可直接复用既有 Rust 编译结果与 LRU 缓存，不必另造 Markdown 解析器（符合反过度设计红线）。

### 4.2 结构单元模型

```ts
/** 块级结构单元类型（覆盖 R10 要求的一切块级结构） */
export type UnitKind =
  | 'paragraph' | 'heading' | 'table' | 'list' | 'blockquote'
  | 'code' | 'hr' | 'html' | 'other';

/** 容器型单元：其内部还需递归协调 */
export const CONTAINER_UNITS: ReadonlySet<UnitKind> = new Set([
  'table', 'list', 'blockquote',
]);

export interface MarkdownUnit {
  /** 稳定身份键：kind + 结构路径 + 内容指纹 */
  key: string;
  kind: UnitKind;
  /** 单元的 outerHTML（用于身份比对与叶子替换） */
  html: string;
  /** 是否容器型（需递归协调） */
  isContainer: boolean;
}
```

**身份键（`key`）设计**：`kind` + `结构路径`（如 `table>tbody>tr#3`）+ `内容指纹`。

- 已稳定单元：内容指纹不变 ⇒ key 不变 ⇒ 可复用；
- 末尾活跃单元：内容指纹每帧变 ⇒ key 变 ⇒ 走「原地更新」而非「重建」。

> **注意**：不能只靠 `key` 做 React 式列表 diff（末尾单元 key 每帧变会导致重建）。协调器必须**按位置前缀 + 类型匹配**决策，`key` 仅作辅助判等。

### 4.3 单元切分（UnitSplitter）

```ts
/** 将编译后的 HTML 字符串切分为顶层结构单元序列 */
export function splitHtmlIntoUnits(html: string): MarkdownUnit[];
```

实现要点：

1. 使用 `document.createElement('template')` + `tpl.innerHTML = html` 解析 —— 这是浏览器内**最快**的 HTML 解析路径（不触发资源加载、不执行脚本），且不引入第三方库。
2. 顶层单元 = `tpl.content.children`。
3. `tagName → UnitKind` 映射（`UL`/`OL` → `list`；`TABLE` → `table`；`BLOCKQUOTE` → `blockquote`；`PRE` → `code`；`HR` → `hr`；`P` → `paragraph`；`H1`-`H6` → `heading`；其余 → `other`/`html`）。
4. 不递归展开为扁平序列 —— **保持树形**，由协调器按需递归。这避免了「扁平化后无法还原嵌套」的常见陷阱。

### 4.4 单元级 DOM 协调（UnitReconciler）

```ts
/** 以真增量方式将 units 协调进 container（禁止整块重建） */
export function reconcileUnits(container: Element, units: MarkdownUnit[]): void;
```

算法（**受限子集 diff**，非通用 DOM diff）：

```
reconcile(container, units):
  old = Array.from(container.children)
  k = 0
  while k < old.length && k < units.length && unitsCompatible(old[k], units[k]):
      patchInPlace(old[k], units[k])        // 类型相同 → 原地更新（递归或叶子）
      k += 1
  // k 之后：追加 / 删除
  for i in [k, units.length):  container.appendChild(materialize(units[i]))
  for i in [units.length, old.length):  old[i].remove()

unitsCompatible(node, unit):
  return tagOf(node) === expectedTag(unit.kind)

patchInPlace(node, unit):
  if unit.isContainer:
      reconcile(node, splitHtmlIntoUnits(unit.html 的 children))   // 递归
  else:
      if node.innerHTML !== innerOf(unit.html): node.innerHTML = innerOf(unit.html)
```

**为什么这是「受限子集」而非通用 diff**：流式文本单调增长 ⇒ 结构序列单调 ⇒ 实际只发生「末尾单元更新 + 追加」。中间插入/删除仅出现在 retract / 重写场景，用上面的 `k` 分支即可正确处理，无需 LCS 算法。

**递归深度**：容器型单元递归一层（`table → thead/tbody → tr`、`list → li`）。`li` 内部不再递归（叶子处理），因为列表项内部的行内变化用 `innerHTML` 更新已足够且无跳变。

### 4.5 末尾活跃单元的原地更新

末尾单元（正在增长的那个）每帧内容都变，协调器会走 `patchInPlace`：

- **叶子单元**（`p` / `li` / `h*`）：替换 `innerHTML`。因为单元**位置不变、外层尺寸约束不变**，视觉上是文字连续增长，无跳变。
- **容器单元**（`table` / `ul` / `ol` / `blockquote`）：**递归协调**，即容器本身不动，只处理其子单元序列（追加行 / 更新末行）。

**表格列宽稳定性**（这是 `table` 独有的风险）：

- `thead` 复用 ⇒ 列宽基准稳定；
- 但 `table-layout: auto` 下，新追加的行若内容更宽，浏览器会**重新分配列宽**，导致已有行横向跳动。

> **修正记录（2026-09-19 评估）**：本节初稿曾给出「首帧实测各列宽度 → `colgroup` + `table-layout: fixed` 锁定」的对策，**该对策在真增量场景下自伤，已废弃**。理由：
> 1. 首次渲染（分隔行成立）时表格**通常只有表头 + 0～1 行数据**，实测宽度是「内容不足时的宽度」，不是最终宽度；
> 2. 一旦 `table-layout: fixed` 锁死，后续追加的**更宽内容会被压缩或溢出** —— 这等于把「列宽重分配」换成了「内容裁切」，比原问题更严重；
> 3. **「列集合确定」≠「列宽确定」**：列集合在分隔行成立时即确定，列宽却要等**全部行到齐**才稳定；而真增量下「全部行到齐」等于流结束，此时锁定已无意义。
>
> 初稿把上述两个「确定」混为一谈，是逻辑错误。

**修正后的对策（按优先级，明确二选一）**：

1. **若 Rust 输出含 `<colgroup>`**：保持其复用（协调器不得重建 `colgroup`），且**保留其中的列数声明与百分比/`auto` 宽度，不注入像素值**。
2. **若不含量化列宽**：采用 **`contain: layout` 隔离 + 接受 auto 布局重分配**——
   - 在 `table` 外层容器加 `contain: layout`，使列宽重分配的布局失效**不扩散到容器外**（不牵动外层消息行高度抖动，也就不会与 §4.7 的 VSM 观测打架）；
   - **不写死 `table-layout: fixed`**，让浏览器在已有行之间自然平衡列宽；
   - 重分配带来的既有行横向位移**属可接受代价**：它发生在表格**内部**，且位移量随行数增加而单调收敛。
3. **禁止**：在流式期间注入实测像素宽度、或声明 `table-layout: fixed`。若确有锁定需求，只能作为**流结束后的收口后处理**（此时列宽已稳定，锁定不影响可读性）。该后处理**不在本次范围**（本次 C 阶段不含列宽锁定），如未来立项须单独评估其收益是否值得。

**验收口径随修正调整**：§8.2-3 的「列宽位移为 0」断言**不再作为硬指标**（它与「不引入内容裁切」不可兼得）。改为断言：**表格容器外框尺寸与位置在追加行前后不变**（即重分配被 `contain: layout` 限制在容器内），此断言可机器判定且不牺牲内容完整性。

### 4.6 编译调度与节流

活跃尾块每帧变化 ⇒ 若每帧都发起 Rust 编译，IPC 与 CPU 均不可承受。

**调度设计**：

1. **节流窗口**：对活跃尾块的编译发起做时间节流（建议与既有 `frameBudgetMs = 6`（`StreamRenderBuffer.ts:60`）同一量级，具体值由 `AdaptiveAnimateTimeline` 的速率快照决定）。
2. **复用既有调度器**：`api/markdown/AdaptiveAnimateTimeline.ts`（GPU 挂钟时间轴）与 `api/markdown/SlidingWindowRateEstimator.ts`（速率分档 TURBO/NORMAL）已在 `StreamingMarkdownView.tsx:49-76` 装配，**优先复用**而非新造节流器。
3. **编译期间保留旧 DOM**：`pending` 状态下**绝不清空容器**（消除 §2.1 的闪源 2；封口晋升路径的具体改法见 §5.4，含其「活跃尾块须先渲染真元素」的先决条件）。
4. **过期结果丢弃**：沿用既有 `requestTokenRef` 递增校验模式（`MarkdownBlockItem.tsx:77`、`:105`），token 不匹配的编译结果直接丢弃。
5. **缓存接线**：接上既有的 `markdownStreamingCacheKey` / `invalidateMarkdownStreamCache`（`api/markdownCache.ts`，当前零消费方），使「同一草稿前缀」的编译结果可复用，并支持流结束时批量失效。

### 4.7 与虚拟滚动高度自愈的协同

既有机制：`MessageToolCallsSection.tsx:119-131` 与 `MessageVirtualizer.tsx:196-208` 通过 `ResizeObserver` 观测容器高度，回调 `virtualScrollManager.invalidateActual(msgId)`。

真增量下的新约束：

- **高度变化是单调递增的**（只追加不重建）⇒ VSM 可平滑跟随，不会出现「整块重建导致的先塌陷后撑开」。
- **禁止在协调过程中出现中间空态**（§1.1 指标 2，含 §1.3 的可见性子条件 2b）—— 否则 VSM 会观测到一次高度塌陷并触发错误的滚动锚定。

**协调与测高的时序（与 `03-详案` §4.2 统一口径）**：

> **修正记录（2026-09-19 评估）**：初稿此处写「协调完成后由 `ResizeObserver` **自然触发**一次 `invalidateActual`，**不得手动**在协调中间调用」，与 `03-详案` §4.2「`transitionend` 后**调用一次** `invalidateActual(msgId)`」**直接冲突**。两者在真实场景中会同时生效（用户点击折叠的同一帧流式仍在追加），必须统一。

统一后的规则（**两条并存，按场景分工**）：

1. **纯流式追加场景（无折叠动画）**：由 `ResizeObserver` **自然触发** `setActual`。协调过程本身**不主动调用** VSM 写入。
2. **折叠动画进行中（`03-详案` §4.2 的冻结窗口）**：RO 回调被 **animating 门禁拦截**，不写入；动画结束后由冻结机制**主动调用一次** `invalidateActual(msgId)`，再经 RO 写入终值。
3. **交叉场景（动画中仍有流式追加）**：**用户操作优先** —— 冻结窗口内忽略自动高度变化，窗口结束后**一次性**写入合并后的终值。**不允许**在冻结窗口内为流式追加单独写 VSM。

⇒ 措辞统一为：**「不主动写入」是流式追加路径的规则；「动画结束后主动写入一次」是冻结机制的规则；二者由 animating 门禁互斥，不存在同时写 VSM 的窗口。**

### 4.8 降级与容错

| 场景 | 降级行为 |
|---|---|
| Rust `md_render` 返回 null（命令缺失 / 失败） | 回退既有 worker pool 路径（`markdownRenderAsync.ts:44-51`） |

### 5.4 封口晋升路径的关键修正（防新闪屏）

> **修正记录（2026-09-19 评估）**：初稿把 `MarkdownBlockItem.tsx:135-138` 的 `el.textContent = ''` 笼统称为「闪源，必须消除」，并与活跃尾块路径混为一谈。**该理解有偏差，照此实现会引入新的闪屏。** 本节给出正确机制与改法。

**真实机制**（已逐行复核）：

活跃尾块与封口块是**两个不同的 JSX 分支，共用同一个 `containerRef`**（`MarkdownBlockItem.tsx:171-182` 为活跃分支，`:191-204` 为封口分支），React 复用同一 DOM 节点。因此**封口瞬间，容器里残留着上一帧活跃尾块写入的 Markdown 源码**。

由此，`:135-138` 的清空**不是**「凭空制造空白」，而是**擦掉残留源码**——其配对机制是紧跟其后的 `el.style.visibility = ''`（`:137`）以及异步替换路径 `:145-160`（`el.innerHTML = html` 后同样重置 visibility）。代码注释「绝不显示源码」说明这是**刻意设计**，且 `MarkdownBlockItem.test.tsx:68`、`StreamingMarkdownView.test.tsx:151` 均有对应断言守护。

> 补充事实：本文件中 `visibility` **只被重置为 `''`，从未被设为 `'hidden'`**（全文件 grep 确认）；`data-has-html` 也**没有配套 CSS 规则**。可见「隐藏」是残留状态而非主动置位——这恰恰说明**初稿认为的「清空即闪」与实际的「残留源码暴露」是两件事**。

**改动要求（三条同时满足，缺一即产生新闪）**：

1. **保留上一版 DOM**：封口且 LRU 未命中时，**不得**执行 `el.textContent = ''`；容器保持上一帧内容不动，等待异步 `html` 到达后由 `:145-160` 的 `el.innerHTML = html` 原子替换。
2. **不得残留源码**：由于活跃尾块已改真增量渲染（§4.1），封口时容器内**已经是真元素的 HTML，而非源码**，故第 1 条不会暴露源码。**这是「真增量」带来的新前提** —— 初稿正是在未区分此前提的情况下把清空当成纯缺陷。
3. **移除可见性切换**：随第 1 条一并移除 `:136-137` 的 `el.textContent = ''` + `el.style.visibility = ''` 组合；`:134`、`:150`、`:158` 的 `el.style.visibility = ''` 属无害重置，可保留（但不得新增 `'hidden'` 置位）。若实现中确需在等待期隐藏，必须改为**保留 DOM + `visibility` 切换**而非清空 DOM，且该分支需被 §8.1-5 的可见性断言覆盖。

**指标盲区修正**：§1.1 的「无空白窗口」指标（`childNodes.length` 不得由 >0 变 0）**测不出本问题**——若实现为「清空 + `visibility: hidden`」，`childNodes.length` 仍为 1（文本节点），指标恒过，但用户看不到内容。故 **§1.1 指标 2 增加可见性维度**（见 §1.3）。

### 5.3 不变量（必须由测试守护）

1. **节点复用不变量**：协调前后，索引 < k 的单元节点引用完全相等。
2. **单调性不变量**：流式期间单元数量单调不减。
3. **无空帧不变量**：容器 `childNodes.length` 在流式期间不得归零。
4. **无源码不变量**：活跃容器 `textContent` 不得匹配源码行首模式。
5. **Virtual-Only 不变量**：补全文本绝不回写原始 Markdown 流。

## 8. 验收断言（机器可判定）

### 8.1 单元 / 组件层（vitest + jsdom）

1. **节点复用**：构造 `ul` 追加一项的前后快照，断言 `before[i] === after[i]` 对全部已有项成立。
2. **表格结构**：`thead` 节点引用在追加 3 行后保持恒定；`tbody` 已有 `tr` 引用恒定。
3. **递归容器**：`blockquote` 内嵌套 `ul` 追加项时，`blockquote` 节点与已有 `li` 引用恒定。
4. **单调性**：模拟 50 帧草稿增长，单元数量单调不减。
5. **无空帧 / 无不可见帧**：每帧后断言 `container.childNodes.length > 0`（子条件 2a），**且**断言容器未处于视觉不可见态（子条件 2b：`style.visibility !== 'hidden'`、`style.display !== 'none'`、`offsetHeight > 0`）。
6. **无源码**：每帧后断言 `container.textContent` 不匹配 `/^\s*(\||- |\* |\d+\. |> |```)/m`。
7. **补全正确性**：仅「表头行 + 部分分隔行」输入 → 补全后 `table` 可被解析（DOM 中 `table` 存在且 `thead th` 数量与表头列数一致）。
8. **回退**：Rust 与 worker 均失败时，走既有 `failed` 纯文本回退，不产生新分支。

### 8.2 真实宿主（tauri-mcp `execute_js`）

1. **真增量指纹**：在一次真实流式回复中，用 `MutationObserver` 记录活跃容器的 childList 变更，断言**只出现 `addedNodes`，不出现「先清空后填充」**（`removedNodes` 不得包含全部既有子节点）。
2. **源码不出现**：全程轮询活跃容器 `textContent`，不得命中源码行首模式。
3. **列宽稳定（已按 §4.5 修正调整）**：表格追加行前后，断言**表格外层容器的 `getBoundingClientRect()` 的 `left` / `width` 位移为 0**（重分配被 `contain: layout` 限制在容器内）。
   - **不再断言**表格内部既有 `<tr>` 的 `left`/`width` 位移为 0 —— 该断言与「不引入内容裁切」不可兼得（见 §4.5 修正记录）。
   - 附加断言：追加 3 行更宽内容后，**已渲染单元格文本未被裁切**（`scrollWidth <= clientWidth + 1` 对每个 `td` 成立）。
4. **收口一致**：流结束后，与同一 Markdown 一次性完整渲染的结果**逐单元格 / 逐项一致**。

### 8.3 防回归门禁

- 上述 8.1 各项落为常驻单测；
- 新增一条**源码态禁令**门禁：活跃尾块路径中不得出现 `textContent = ` 直接写入源码的分支（可用源文本探针 + 行为断言双重守护）。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| `template.innerHTML` 每帧解析带来开销 | 单元切分只在**编译结果就绪时**执行（受 §4.6 节流约束），不是每帧；且 template 解析不触发资源加载 |
| 表格 `auto` 布局下列宽抖动 | §4.5 修正后方案：`contain: layout` 隔离容器外框 + **接受容器内重分配**（不锁 `fixed`，避免内容裁切）；C6 阶段真实宿主验证容器外框稳定与内容未被裁切 |
| 末尾单元 `innerHTML` 更新导致光标/选区丢失 | 流式期间用户通常不在活跃单元内选中；如出现，退化为「仅文本节点更新」（记录为后续增强，不在本次范围） |
| 结构探针误判导致过早编译 | 探针只决定「是否编译」，渲染形态由 Rust 结果决定；误判仅浪费一次编译，不产生错误渲染 |
| 与 VSM 高度自愈的时序冲突 | 禁止在协调中间手动 `invalidateActual`；依赖 `ResizeObserver` 自然回调（§4.7） |
| 既有测试对「活跃尾块画源码」有断言 | 需同步更新这些断言（属**行为变更**而非回归），并在提交信息中显式说明 |
