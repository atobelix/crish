## 一、失败现象与根因（逐条实测，不靠推测）

### 1. `StreamingGfmTable` ×2：一个挂起片段冻结整段正文

失败用例：

- `streams trailing units and discards a pending tail after parser reset`
- `discards a pending cell render when a split escape changes the cell source`

引擎层探针（`IncrementalMarkdownSession.advance`）实测确认：输入
`After **OLD_PENDING_TRAILING**` 一次推进会产生 23 个片段，最后一个才是
整 token `**OLD_PENDING_TRAILING**`，其前 22 个逐字符预览片段在 token 闭合时
被 **同步取消**（`cancelled = true`）。也就是说，引擎侧数据完全正确。

真正的缺陷在消费侧 `useStreamingMarkdownHtml`：

```ts
void Promise.all(partPromises).then((results) => { /* 统一提交 */ });
```

**`Promise.all` 把整批片段绑成一次提交**——只要有**任意一个**片段在途
（未闭合 token 的整 token 渲染、慢 IPC、被外部 deferred 挂起的单元格渲染），
**该批已经 resolve 的所有片段都无法进入 DOM**。实测后果：

- 尾块 `[data-streaming-table-trailing]` 的 `textContent` 恒为 `''`，`After` 永远不出现；
- 单元格 `td` 恒为空壳 `<div class="md-streaming-table-cell-content"></div>`，
  已渲染好的 `'v'` 也进不去；
- 重跑（retry）时 `pendingRenders` 里残留上一轮未决 Promise，
  同 key 直接命中在途 Promise，连 `renderMarkdown` 都不会被调用（表现为第二条断言失败）。

这是**队头阻塞（head-of-line blocking）**，不是测试时序问题。

### 2. `MarkdownBlockItem` ×1：两条战役契约直接冲突

- VS-03（`docs/message-disappearance-audit/execution/06-...`）：封口块编译失败要
  **有可读内容**，绝不退化成空白气泡（历史消息消失灾难）。
- 流式战役 `b08063b1a`：`useStreamingMarkdownHtml` 契约写明
  **“渲染失败保持空白，不回退显示原文”**。

VS-03 的实现（在 `MarkdownBlockItem.test.tsx` 中被钉死）把**原始 Markdown 源码**
`## Source text that failed to compile` 原样渲染；而
`StreamingMarkdownView.test.tsx` 要求封口失败块 `textContent === ''`。
两条断言在数学上不可能同时成立：

- 保留源码 → 违反“绝不回退源码”；
- 改为空白 → 违反 VS-03“零空白 DOM”，历史消息会重新变成空气泡。

### 3. `workflowScheduler.test.ts`：解绑 cwd 校验后的契约回潮

上一批修复依据 `WorkflowForm.tsx:135-146`（首项固定提供
`id: ''` / `label: '全局工作区'` / `hint: '默认沙箱'`）确认
**空 cwd 代表全局工作区沙箱，属合法绑定**，因此移除了
`validateWorkflowDraft` 中的“必须选择项目路径”校验；但
`workflowScheduler.test.ts` 仍钉着旧的 `'请选择所属工作区项目'`，成为残留尾巴。

## 二、修复方案

### 1. 逐片段提交（根治队头阻塞）

`apps/crish-desktop/src/api/markdownRenderAsync.ts`：把 `Promise.all` 整批提交
改为**每个片段独立 resolve 即提交**：

```ts
for (const part of advance.textParts) {
  void parseMarkdownFragmentToHtmlAsync(part.source, priority, part.kind, { signal: currentSignal, ... })
    .catch(() => '')
    .then((fragment) => {
      if (!mountedRef.current) return;
      if (sessionEpochRef.current !== sessionEpoch) return;
      if (!session.resolveTextPart(part.id, fragment)) return;
      if (unitsRef) {
        unitsRef.current = session.getUnitSnapshots();
        setRenderVersion((version) => version + 1);
      } else {
        setHtml(session.toHtml());
      }
    });
}
```

关键点：

- **已就绪片段不再被在途片段拖住**，`After`、`v` 这类先到的正文立即进入 DOM；
- 被取消的预览片段走 `resolveTextPart` 时返回 `false`（`!part.cancelled` 校验），
  **被取消的中间态不会被写回 DOM**，“绝不暴露源码 / 中间态”契约原样保留；
- 会话代次 `sessionEpochRef` 与 `mountedRef` 守卫不变，输入回退 / 卸载时
  旧结果依旧被丢弃；
- React 18 自动批处理会把同一微任务窗口内的多次 `setRenderVersion` 合并，
  不会引入额外渲染风暴。

### 2. 无源码安全纯文本兜底（同时满足两条硬约束）

新增 `apps/crish-desktop/src/api/markdown/markdownPlainTextFallback.ts`，
把 Markdown 投影为**去掉控制符的纯语义文本**：

- 剥离 ATX 标题标记、引用标记、列表标记、表格管道、强调/删除线/行内代码标记、
  围栏开关行、水平线与 setext 下划线、表格分隔行；
- 链接/图片只保留可见语义（`[label](url)` → `label`、`![alt](url)` → `alt`）；
- 代码围栏只丢开关行，**代码正文原样保留**；
- 残留的不配对控制符（`**`、`` ` ``、`~~` 连排与行首行尾孤立标记）一并清除；
- 结果仍是**语义正文完整**的文本，组件以 React 文本子节点渲染，天然转义，零 XSS 面。

`MarkdownBlockItem` 的失败分支改为渲染
`toMarkdownPlainTextFallback(text)`：

- `## Source **must never appear**` → `Source must never appear`
  （无 `##`、无 `**`，且**不是空白**，VS-03 与流式契约同时成立）。

冲突的两条断言统一升级为**更强的双重断言**（不是放宽，而是同时钉住两条契约）：

- `StreamingMarkdownView.test.tsx`：`not.toContain('##')` + `not.toContain('**')`
  + 正文内容断言 + `pre.md-text-fallback` 为 null；
- `MarkdownBlockItem.test.tsx`：正文语义文本断言 + `not.toContain('##')` + 无 `h2` 注入。

### 3. cwd 契约回潮收口

`workflowScheduler.test.ts` 改为验证真实契约：空 cwd（全局工作区）**合法**，
绑定项目同样合法，且**名称与提示词仍然必填**（补了两条必填断言，
比原来的单条断言更强）。
