## 一、战役背景与核心目标

现有的侧边栏与系统定时任务（Workflow / Scheduled Tasks）存在多项严重阻碍日常使用的架构性与实现性缺陷：

1. **无法编辑与控制当前任务**：用户在界面点击暂停/停止无实际效果（刷新后被旧状态反向冲刷），前端草稿回填存在键名不一致（`minutes` vs `intervalMinutes`）导致配置被抹除，修改 Prompt 无法同步至运行中调度器。
2. **运行中任务实际上从未执行**：应用在启动阶段因为缺少 tokio runtime 上下文导致 `restore()` 被直接跳过，应用重启后内存调度协程全失；到期触发时仅向内存队列推送了一条 steering 消息并虚假记录 `completed`，缺少专职的任务执行器与会话唤醒闭环。
3. **对话内创建定时任务的会话绑定缺失**：在具体对话中通过 `/schedule` 或 Agent 工具创建任务时，无法将定时触发绑定回该对话，任务触发无法在该对话内追加消息流并展现 Agent 思考与产出。
4. **缺少对标准 Cron 表达式的直接编辑支持**：前端只支持 daily / intervalMinutes，一旦编辑由 Agent 或高级配置生成的 cron 表达式任务，直接被降级回退为 manual。

**核心目标**：彻底打通从前端交互、Tauri 命令面、数据持久化到 Rust 底层调度与真实 Agent 执行的全链路，实现真正的单任务启停控制、对话归属绑定、开机自动恢复以及真实 Agent 任务执行。

## 四、文档规范与下一阶段规划

1. **独立方案产出格式要求**：
   - 包含：具体问题背景与根因断点、目标与验收断言、核心架构设计与数据流时序、具体文件与代码级改动清单、测试覆盖与向后兼容考量。
   - 统一使用中文，UTF-8 无 BOM，代码引用使用 `文件路径:行号`。
2. **下一轮综合融合流程**：
   - 当 5 位子 Agent 的方案全部落盘后，主 Agent 组织汇总分析，对比同一阶段两份独立方案的异同与优劣；
   - 结合现有代码基线，吸收两方长处，收敛产出 `docs/scheduled-tasks-revamp/plans/` 下的各阶段最终计划（Final Plan）及战役总计划。
