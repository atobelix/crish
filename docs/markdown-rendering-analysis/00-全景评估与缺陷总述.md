## 一、核心结论与业界段位定级

我们软件当前的 Markdown 渲染能力属于：**「实验室原型指标亮眼，但真实生产交付处于第三梯队（中下游）」**。

如果仅看 `reference/markdown-editor` 这个孤立的独立原型工程，它拥有 KaTeX 离线 Worker 渲染、基于 TanStack Virtual 的块虚拟化、以及较为前沿的「表格岛（Table Island）」拖拽与选区模型，纸面实力可达 **3.5 ~ 3.8 分**；  
然而，**用户在日常使用的真实桌面端（`apps/crish-desktop`）中，该原型代码的导入量为 0 行**。主端实际交付的 Markdown 系统得分仅为 **2.2 / 5.0 分**，不仅远远落后于全球最顶尖梯队（Typora 4.8、Obsidian 4.9、Notion 4.4、Bear 4.5、Cursor 4.3），甚至落后于常规开源的 ChatGPT / Claude 网页及桌面套壳客户端。

用户提出的要求非常明确：**“如果是缺点比较多，就着重说缺点”**。通过对全仓各层代码的穿透式审计，本软件在 Markdown 领域的**缺点和架构隐患占据了压倒性的主导地位**。

## 三、我们软件的优势（客观呈现）

尽管缺点繁多，但在针对**大语言模型（LLM）对话流式输出**的特定场景下，软件仍有一些针对性的架构尝试：

1. **流式分块与封口隔离思想**：
   - 相比于原生 `react-markdown` 每次接收新 Token 都会从头到尾全量重新解析整个 DOM 树的低劣做法，`StreamingMarkdownView` 与 `MarkdownBlockItem` 建立了「已封口历史块（Sealed）」与「活跃尾块（Active Tail）」的双轨分离机制；
   - 封口块通过 `React.memo` 锁住渲染结果，理论上大幅减轻了长对话流式打字时的协调压力。
2. **流式表格逐行投影（StreamingGfmTable）**：
   - 针对 GFM 表格在流式未闭合时经常导致全表闪烁或无法解析的问题，前端手写了 `StreamingGfmTableParser`，能够在模型仅吐出表头和前几行时，即时以表格结构逐行追加，避免了必须等待表格完整闭合才能渲染的糟糕体验。
3. **Rust 原生 IPC 渲染与代码高亮加速**：
   - 完成态的静态 Markdown 交付给 Rust 后端（`pulldown-cmark` + `syntect`），渲染性能和内存占用优于纯 JS 解释器；并且具备前端 Web Worker 异步降级通道。
4. **大文件安全熔断意识**：
   - 当检测到内容超出阈值（256KB）时，有意识地切断重型富文本渲染，防止前端主线程因数万个 DOM 节点而直接卡死崩溃（虽然其实现方式非常粗暴）。
5. **实验室原型（reference）具备较高天花板**：
   - 独立原型已跑通 KaTeX 公式 Web Worker 离线渲染、基于 TanStack Virtual 的视口虚拟化以及「表格岛」的独立选区与列宽模型，说明团队具备研发高级编辑器的技术储备。

## 四、核心缺点与硬伤清单（着重分析，直击痛点）

### 1. 【致命缺陷】核心能力完全缺失：数学公式与 Mermaid 图表均为 0 分
- **LaTeX 数学公式完全失明**：
  在学术研究、科学计算、算法推导及日常编码交流中，LaTeX 是不可或缺的核心语法。然而，生产客户端 `apps/crish-desktop` 的 `package.json` **完全没有引入 `katex` 或 `mathjax`**；Rust 后端 `conex-markdown` 也未启用 `pulldown-cmark` 的 `ENABLE_MATH` 扩展。
  模型输出的 `$E=mc^2$` 或 `$$\int f(x)dx$$` 在主界面中直接显示为毫无排版的丑陋纯文本字符串。
- **Mermaid 可视化图表完全交白卷**：
  全仓生产环境不存在任何 Mermaid 依赖。模型输出的 ````mermaid` 流程图、时序图，全被无差别路由至普通代码块显示，完全无法渲染为交互式矢量图。

### 2. 【架构断层】四套 Markdown 体系多头割裂，各自为战
软件内部不同模块为了解决各自局部问题，各自手写/引入了一套 Markdown 体系，彼此形同陌路：
1. **聊天流式渲染**：Rust `pulldown-cmark` + Web Worker `marked` + 自研正则切块；
2. **输入框 Composer**：基于 `@tiptap/react`（ProseMirror），其反序列化器在 `markdownDeserializer.ts` 中**主动自我阉割**，把用户粘贴的标题、列表、引用等所有块级结构强行降维为带 `#`、`-`、`>` 的普通段落；
3. **独立原型编辑器**：在 `reference/markdown-editor` 中用 2391 行手写了解析器，拥有 KaTeX 和 TableIsland，但主工程对其导入量为 **0**，完全是一座与世隔绝的孤岛；
4. **CRDT AST 协作层**：在 `crates/conex-md-ast` 中采用了第三种解析库 `markdown-rs`，且其 `BlockKind` 结构体居然缺失 `Table` 和 `TaskItem` 枚举，导致表格被永久有损降维为普通文本段落。

### 3. 【形式主义】流式防抖与投机机制大量沦为“死代码”
代码库中设计了大量看起来极其高级的流式调度概念，但在实际集成中严重脱节：
- **投机闭合完全悬空**：`SpeculativeVirtualCloser.ts` 计算出的 `virtualClosedText`，在 `MarkdownBlockItem.tsx:91` 中直接被重命名为 `_virtualClosedText` 并彻底闲置，末尾未闭合块依然带着残缺文本直接编译；
- **时间轴调度空转**：`AdaptiveAnimateTimeline` 在 `StreamingMarkdownView` 中每帧调用 `beginPass/commitPass`，传给子组件后同样被重命名为 `_timeline` 闲置，核心方法 `take()` 在全仓生产代码中的调用率为 0%；
- **封口块缓存协调破防**：`markdownBlockItemPropsEqual` 的比较逻辑中包含了 `prev.isStreaming === next.isStreaming`，导致模型流式输出完毕的那一刻，**整屏所有已经封口的历史块全量重新触发协调与重绘**。

### 4. 【排版灾难】过度防卫与“HTML 标签大屠杀”
- **原生常用 HTML 标签全军覆没**：
  Rust 渲染器在 `renderer.rs` 中，除了对顶级 `<img>` 透传清洗外，对其他所有原生 HTML 标签实施了暴力的一刀切转义（`escape`）。
  这一极端的历史包袱导致 Markdown 中极其常用的 `<details><summary>`（折叠面板）、`<kbd>`（快捷键标签）、`<mark>`（高亮）、`<sub>`/`<sup>`（上下标）、`<u>`（下划线）在渲染后全部变成带有 `&lt;details&gt;` 的裸露乱码；
- **CJK 粗暴切词反模式**：
  为了防止中文字符串在窄屏气泡中撑破容器，前端 `markdownSanitizer.ts` 顽固保留了**“每隔 10 个中文字符强行插入一个 `<wbr>`”**的原始正则，完全不考虑中文词法与分词，生硬切断成词，并彻底破坏了中文排版的标点避头尾禁则。

### 5. 【代码体验粗糙】专业代码块交互全交白卷，TypeScript 高亮竟是“假象”
- **Sublime Text 默认语法包遗漏现代语言**：
  Rust 后端基于 `syntect` 加载默认语法包，而 Sublime 3 官方默认包中**根本不包含 TypeScript、Swift、Kotlin、Dart**！后端高亮遇到 `typescript` 恒定返回 `None` 并降级为纯文本，单测通过弱断言掩盖了这一事实；
- **专业交互能力全部缺失**：
  代码块不支持行号（Line Numbers）、不支持特定行高亮（Line Highlighting）、不支持代码折叠、不支持软折行切换；
- **无法添加行号的架构死结**：
  长文档与聊天组件的代码复制逻辑，均盲目采用 `pre.textContent` 读取代码文本。由于源码与展示层未解耦，一旦在 DOM 中插入行号元素，用户点击复制就会把行号一股脑全复制进剪贴板。

### 6. 【性能极限低下】面对 256KB 以上文档直接“举白旗投降”
- `MarkdownDocumentView` 由于缺乏针对富文本 Markdown DOM 树的视口虚拟化能力，硬编码了 `DEFAULT_LARGE_FILE_THRESHOLD_BYTES = 256KB` 的熔断红线；
- 只要文档稍微包含较多的日志、规范文档或代码片段（超过 256KB），**软件就直接放弃富文本渲染，强制切入纯文本单色代码查看器 `VirtualPlainCodeViewer`**。对比 Typora、Obsidian、VS Code 等轻松流畅编辑预览数十万字长篇 Markdown 的能力，本软件在长文档处理上完全不具备工业级可用性。

## 五、整改战略建议（四归一收敛路线）

要打破当前第三梯队的落后局面，赶超一流竞品，必须彻底摒弃“打补丁”和“重复造轮子”的思维，坚定推进**「四归一」底层收敛**：

1. **统一核心解析底座**：
   - 彻底废除手写的 2391 行 `parser.ts` 以及各处拼凑的脆弱正则状态机；
   - 生产端引入工业级 AST 引擎（如基于 Rust 的统一 Markdown AST 或者是成熟的 CodeMirror 6 / Unified 生态），统一后端渲染与前端协作。
2. **打通公式与图表血脉**：
   - 将 `reference` 中已经验证可行的 KaTeX Web Worker 离线渲染管线正式收口并合入主工程 `apps/crish-desktop`；
   - 引入 Mermaid 渲染流水线，实现代码块的可视化拦截与渲染。
3. **修复 HTML 清洗管道，拯救排版富文本**：
   - 废除 `renderer.rs` 中的全局原始 HTML 暴力 escape，恢复基于 AST 的精确标签白名单（放行 details, summary, kbd, mark, sub, sup 等安全排版标签）。
4. **重构代码块架构，解耦展示与源码**：
   - 在 pre/code 容器上注入 `data-raw-code` 单一真理源，彻底解开行号注入与文本复制之间的死结，补齐行号、行高亮与折叠能力。
