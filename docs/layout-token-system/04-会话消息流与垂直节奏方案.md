## 一、方案背景与架构演进目标

### 1.1 现状核心病灶透视

根据 `docs/layout-token-system/survey/04-chat-flow-and-message-layout-survey.md` 的第一阶段现场调研事实，桌面端会话消息流在经历卡片流（DIM-01）、纯净画纸流（DIM-02）以及虚拟滚动盒模型（DEF-13/14）多次重构后，虽然奠定了高性能虚拟滚动的基础，但仍遗留了多处严重的几何断层与视觉补丁：

1. **几何单一真源（SSOT）断裂导致门禁红灯**：
   虚拟滚动切片容器 `[data-chat-slice-container]` 在 TypeScript 层面通过 `chatScrollGeometry.ts` 维护顶部内边距（`CHAT_SCROLL_PAD_TOP = 48`），并通过绝对定位 `top: 48px` 承载；然而 CSS 文件 `ChatMessageList.module.css:36` 的 `.listInner` 仍硬编码写死 `padding: 48px 20px 16px;`。这种 CSS 与 TS 的双轨定义不仅违背了单一真理原则，更直接导致现存门禁 `VirtualScrollGeometryContract.test.ts` 持续报红失败。
2. **DEF-13 内部盒模型充斥裸写数值**：
   为了根除外部 margin 造成的 1600px 累积高度蒸发黑洞，消息行内部普遍采用了 `padding-bottom` 承载垂直节奏。但目前 `.row` 写死 `16px`、`.rowCarrier` 写死 `4px`、`scroll-margin-top` 写死 `56px`，缺乏与系统 Token 的语义绑定。
3. **搜索高亮负 Margin 与 4px 突增高度颠簸**：
   `.row.searchHit` 采用了 `margin-left: -6px; margin-right: -6px; width: calc(100% + 12px);` 的负 margin 外扩补丁，突破父容器栅格；同时通过 `padding-top: 4px` 使得高亮消息物理高度突增 4px（$\Delta H = +4\text{px}$），引发虚拟滚动树状数组在搜索高频交互下密集失效与视口抖动。
4. **回底浮钮负 Margin 抽离与 2px 偏轴**：
   贴底卡槽 `ChatScrollFloorSlot` 中的回底按钮采用 `margin-top: -46px` 破坏性负 margin 向上反向提拉，且右侧边距使用了 `padding-right: 18px`，与消息流的 `20px` 栅格边距产生 2px 错位；同时在宽屏（$\ge 1200\text{px}$）下缺乏响应式断点，出现 40px 的严重偏轴。
5. **设计契约欺骗性假象与死代码残留**：
   `.userBubble` 中声明 `border-radius: var(--radius-xl, 16px)`，但 `:root` 的 `--radius-xl` 实质为 `12px`，导致 fallback 16px 永久无法生效；助手消息操作栏 `min-height: 22px` 与内部 28px 按钮撕裂，Hover 激活时产生 6px 纵向跳跃；`ChatMessageList.module.css` 中残留 116 行完全未消费的 `.pinnedBar` 僵尸样式。

### 1.2 架构重塑与纯净化四项铁律

为了彻底根除上述历史技术债务，本方案确立以下四项不可动摇的工程铁律：

- **铁律一：几何单一真理（SSOT）绝对统一**。
  绝对定位的虚拟切片容器不吃普通文档流内边距。所有的纵向偏移（顶部 48px、底部 16px）有且仅能由 TypeScript 几何常量与切片容器绝对定位单轨接管，CSS `.listInner` 纵向 padding 必须归零，消灭双重计算模型。
- **铁律二：DEF-13 物理高度恒等与防黑洞不变量**。
  消息行根节点外部 `margin` 恒为 0，所有垂直节奏由内部盒模型承载。任何状态切换（如常规态 $\leftrightarrow$ 搜索高亮态 $\leftrightarrow$ 悬浮态）必须严格保证物理盒模型高度恒等（$\Delta H \equiv 0$），严禁产生任何引致虚拟滚动失效的高度突变。
- **铁律三：零负 Margin 与全 GPU 合成位移**。
  严禁在文档流中使用负 margin 进行位置侵入或高度抽离。所有悬浮按钮与浮动层的位置偏移，一律收敛为 `transform: translateY(...)` 的 GPU 合成物理位移，确保对普通文档流布局与 `scrollHeight` 的影响严格为 0。
- **铁律四：架构净收敛与契约去欺骗**。
  清退所有未消费的死代码；彻底消除 CSS 变量写着 16px 但实际跑着 12px 的契约欺骗假象，让设计 Token 的预期与屏幕物理像素 100% 吻合。

## 三、几何单一真理（SSOT）统一与门禁红灯根治方案

### 3.1 核心病灶：双重内边距与门禁持续红灯根因

#### 1. 源码取证与矛盾重现
在 `apps/crish-desktop/src/components/chat-message-list/ChatMessageList.module.css:36` 中：
```css
.listInner {
  width: 100%;
  max-width: min(var(--chat-col-max, 760px), 100%);
  margin-left: auto;
  margin-right: auto;
  padding: 48px 20px 16px; /* 顶部 48px，左右 20px，底部 16px */
  box-sizing: border-box;
  min-width: 0;
  overflow-anchor: none;
}
```

而在虚拟滚动核心几何文件 `apps/crish-desktop/src/components/chat-message-list/chatScrollGeometry.ts:5-8` 中：
```typescript
export const CHAT_SCROLL_PAD_TOP = 48;
export const CHAT_SCROLL_PAD_BOTTOM = 16;
export const CHAT_SCROLL_PAD_X = 20;

export function chatSpacerHeight(contentHeight: number): number {
  const h = Number.isFinite(contentHeight) && contentHeight > 0 ? contentHeight : 0;
  return CHAT_SCROLL_PAD_TOP + h + CHAT_SCROLL_PAD_BOTTOM;
}
```

并在 `MessageVirtualizer.tsx:410-432` 中装配：
```tsx
<div
  className={styles.listInner}
  data-chat-list-inner=""
  data-vsm-spacer=""
  style={{
    height: `${totalHeight}px`, // totalHeight = CHAT_SCROLL_PAD_TOP + contentHeight + CHAT_SCROLL_PAD_BOTTOM
    position: 'relative',
    overflow: 'hidden',
  }}
>
  <div
    data-chat-slice-container=""
    style={{
      position: 'absolute',
      top: CHAT_SCROLL_PAD_TOP, // 48px
      left: CHAT_SCROLL_PAD_X,  // 20px
      right: CHAT_SCROLL_PAD_X, // 20px
      transform: `translateY(${startOffset}px)`,
    }}
  >
    {/* 消息行切片渲染 */}
  </div>
</div>
```

#### 2. 门禁测试失败的物理本质
执行单元测试 `npx vitest run apps/crish-desktop/src/components/chat-message-list/__tests__/VirtualScrollGeometryContract.test.ts`，持续输出以下红灯阻断：
```
FAIL apps/crish-desktop/src/components/chat-message-list/__tests__/VirtualScrollGeometryContract.test.ts
  × 1. ChatMessageList.module.css 契约：消除相邻兄弟外边距黑洞 (DEF-13) > .listInner 禁止纵向 padding（几何 SSOT 归 chatScrollGeometry）
    → expected listCss not to match /\.listInner\s*\{[^}]*padding:\s*48px/
```

**机理穿透**：
- 在 CSS 标准规范中，当一个容器设置了 `box-sizing: border-box` 与固定 `height`，且拥有 `padding: 48px 20px 16px` 时，其内部普通文档流区域的可用高度为 `height - 48px - 16px`；
- 但是，消息切片容器 `[data-chat-slice-container]` 是 `position: absolute` 定位的。绝对定位子元素相对于 `position: relative` 的父容器内边距外边缘（Padding Edge，即包含块的左上角 `(0, 0)`）进行偏移；
- 当切片容器声明了 `top: 48px` 时，它已经自顶向下空出了 48px；
- 如果父级 `.listInner` 在 CSS 中再次声明纵向 `padding-top: 48px; padding-bottom: 16px;`，两套内边距系统产生了**双轨重叠与概念混乱**。一旦后续前端维护者误以为垂直内边距是由 CSS 控制而在样式表中修改 `padding-top: 32px`，绝对切片依然死锁在 `top: 48px`，导致样式与运行时几何彻底脱节脱轨。

### 3.2 坐标系重塑与几何单一源收敛模型

为了确立绝对权威的单一真理源，本方案制定以下收敛模型：

1. **`.listInner` 纵向 padding 刚性归零**：

## 四、DEF-13 内部盒模型 Token 化与垂直节拍规范

### 4.1 历史缺陷复盘：1600px 累积高度蒸发黑洞机理

在早期的消息列表实现中，消息之间的间隔采用了传统的相邻兄弟选择器：
```css
/* 历史废弃反模式 */
[data-chat-list-inner] > :not([hidden]) + :not([hidden]) {
  margin-top: 16px;
}
```

#### 黑洞爆发的数学必然性
1. **浏览器几何测量 API 的天然局限**：
   - `Element.offsetHeight`：仅包含 `content + padding + border`，严格排除外部 `margin`；
   - `ResizeObserverEntry.contentRect`：仅度量内容盒 `content`，严格排除外部 `margin`；
2. **累积蒸发灾难**：
   假定当前会话有 $N = 100$ 条历史消息，屏幕可见区域仅渲染第 90~100 条。
   前 89 条已被滚出视口的元素在 DOM 中被卸载，并由虚拟滚动管理器（VSM）计算出一个顶部占位 Spacer。
   - 在旧模型下，DOM 物理上由外部 `margin-top: 16px` 撑开的高度为：
     $$\text{Visual Height} = \sum_{i=1}^{89} (\text{offsetHeight}_i + 16\text{px}) = \sum \text{offsetHeight}_i + 89 \times 16\text{px} = \sum \text{offsetHeight}_i + 1424\text{px}$$
   - 但 VSM 在测量阶段仅记录了 `offsetHeight`，导致生成的 Spacer 高度为：
     $$\text{Spacer Height} = \sum_{i=1}^{89} \text{offsetHeight}_i$$
   - **高度瞬间蒸发量**：
     $$\Delta \text{Height} = 89 \times 16\text{px} = 1424\text{px}$$
   - 滚轮每滚动一下，卸载与装载的交界处便会凭空蒸发上千像素，导致整个滚动条疯狂颤抖，视口内容剧烈闪烁甚至永远无法稳定吸底。

### 4.2 DEF-13 几何数学不变量恒等推导

为了彻底终结这一顽疾，DEF-13 架构提出了**内部盒模型自闭环原则**：
**严禁消息行存在任何外部 `margin-top` 或 `margin-bottom`，所有行与行之间的呼吸间隔，必须作为内边距（`padding-bottom`）收敛在行自身容器内。**

```
┌────────────────────────────────────────────────────────┐
│ .row (消息行主容器)                                     │
│ ┌────────────────────────────────────────────────────┐ │
│ │ 消息内容实体 (文字、气泡、Markdown、工具卡片)         │ │
│ │ 高度: H_content                                    │ │
│ └────────────────────────────────────────────────────┘ │
│ ▼ 内部 padding-bottom: var(--chat-row-gap, 16px)      │ │
└────────────────────────────────────────────────────────┘
```

#### 数学等式推导
对于任意消息行 $i$：
$$\text{Margin}_{\text{external}} \equiv 0\text{px}$$
$$\text{Physical Height}_i = \text{Height}_{\text{content}, i} + \text{Padding}_{\text{bottom}, i}$$
$$\text{Measured Height}_i (\text{el.offsetHeight}) \equiv \text{Physical Height}_i$$
$$\Delta \text{Height (Virtual Error)} = \text{Physical Height}_i - \text{Measured Height}_i \equiv 0\text{px}$$

在 $N$ 条消息的全生命周期中：
$$\sum_{i=1}^N \text{DOM Height}_i \equiv \sum_{i=1}^N \text{VSM Measured Height}_i$$
累积高度误差在数学上严格为 0，彻底根除了 1600px 黑洞。

### 4.3 消息行内部盒模型语义 Token 化方案

## 五、搜索高亮行 `.row.searchHit` 负 Margin 与高度突变根除

### 5.1 负 Margin 补丁与 4px 突变危害深度诊断

#### 1. 现状代码事实
在 `apps/crish-desktop/src/components/chat-message-row/ChatMessageRow.module.css:25-37` 中：
```css
.row.searchHit {
  background: color-mix(in srgb, var(--accent-color) 8%, transparent);
  border-radius: var(--radius-xl);
  padding-top: 4px;
  padding-bottom: 16px;
  padding-left: 6px;
  padding-right: 6px;
  margin-left: -6px;
  margin-right: -6px;
  width: calc(100% + 12px);
  max-width: calc(min(var(--chat-col-max, 760px), 100%) + 12px);
  box-sizing: border-box;
}
```

#### 2. 深度架构危害
1. **破坏栅格包含块与横向溢出**：
   为了让高亮背景比消息正文左右各外扩 6px，开发者使用了 `margin-left: -6px; margin-right: -6px; width: calc(100% + 12px);`。这不仅直接违反了 AGENTS.md §7「严禁打补丁」的铁律，在视口宽度较小（如小窗口或分屏）时，这额外的 12px 会直接冲出包含块，触发父容器的不良横向滚动或被裁切；
2. **破坏物理高度恒定性（$\Delta H = +4\text{px}$）**：
   对比常规 `.row` 与 `.row.searchHit` 的纵向内边距：
   - 常规 `.row`：`padding-top: 0; padding-bottom: 16px;` $\rightarrow$ 垂直衬垫总和为 **16px**；
   - 高亮 `.row.searchHit`：`padding-top: 4px; padding-bottom: 16px;` $\rightarrow$ 垂直衬垫总和为 **20px**！

   **严重后果**：
   当用户在搜索框输入一个常见字符时，数十条消息同时获得 `.searchHit` 类名。每一行的 `offsetHeight` 瞬间被拉伸 4px。
   - `ResizeObserver` 捕获到这几十个 DOM 节点的高度变化，向 `VirtualScrollManager` 疯狂派发重测事件；
   - 树状数组发生密集写入，引发前缀和全面失效；
   - 滚动容器发生剧烈的视觉跳动与触底抖动。搜索高亮明明是一个纯视觉表现，却反客为主重度污染了物理几何层！

### 5.2 物理高度恒等定理（$\Delta H \equiv 0$）与抗颠簸架构

为了保证虚拟滚动的绝对平稳，必须刚性确立**物理高度恒等定理**：
$$\text{Height}_{\text{searchHit}} - \text{Height}_{\text{regular}} \equiv 0\text{px}$$
$$\Delta H \equiv 0$$
$$\Delta W \equiv 0$$

任何高亮状态的进入与退出，**绝不允许改变元素的 `offsetHeight` 与 `offsetWidth`**。

### 5.3 现代 Box-Shadow 扩散与安全内衬双轨方案

为了在不改变盒模型物理尺寸的前提下，实现高亮背景向外舒展 6px 的视觉要求，设计以下两种高品质解决方案：

#### 方案 A：现代纯 Box-Shadow 扩散热区方案（首推，0 DOM 改动）

通过 CSS 的 `box-shadow` 扩散半径（Spread Radius），将高亮色向四周扩展 6px。由于 `box-shadow` 在渲染管线中属于合成/绘制（Paint）阶段，**完全不参与盒模型几何排版，对 `offsetHeight` 与 `offsetWidth` 的贡献严格为 0**！

```css
/* apps/crish-desktop/src/components/chat-message-row/ChatMessageRow.module.css */
.row.searchHit {
  /* 基础背景色 */
  background: color-mix(in srgb, var(--accent-color) 8%, transparent);
  border-radius: var(--radius-lg, 8px);

  /* 核心几何守门：与常规 .row 严格保持完全一致，严禁增加 padding-top */
  padding-top: 0;
  padding-bottom: var(--chat-row-gap, var(--space-4, 16px));
  padding-left: 0;
  padding-right: 0;

  /* 彻底拔除负 margin 补丁与宽度篡改 */
  margin-left: auto;
  margin-right: auto;
  width: 100%;
  max-width: min(var(--chat-col-max, 760px), 100%);
  box-sizing: border-box;

  /* 使用 6px spread-radius 实现向四周无损外扩，ΔH ≡ 0，ΔW ≡ 0 */
  box-shadow: 0 0 0 var(--chat-search-hit-inset, var(--space-1_5, 6px))
    color-mix(in srgb, var(--accent-color) 8%, transparent);
}
```

> **边界注意事项（Containment 适配）**：
> `.row` 原本声明了 `contain: layout paint`。根据 CSS 标准，`contain: paint` 会裁切掉超出边界的阴影。
> 由于父级 `[data-chat-slice-container]` 在左右预留了 `CHAT_SCROLL_PAD_X = 20px` 的空间，为了允许 6px 阴影完美外溢，将 `.row` 的隔离属性调整为 `contain: layout style;`（或保留 paint 并使用内衬方案 B）。在当前 Chrome 120+ 架构中，`contain: layout style` 既提供了完美的排版重排隔离，又消除了阴影被硬截断的问题。

#### 方案 B：安全内衬（Safe Gutter）预留方案（备选）

若必须保持 `contain: layout paint` 绝对防穿透，则将 6px 外扩空间下沉为 `.row` 内部的常态水平内衬：
- 常规 `.row` 统一预留 `padding-left: 6px; padding-right: 6px;`；
- 常规态背景为 transparent，高亮态背景为高亮色；
- 此时常规态与高亮态盒模型 100% 相同，背景自然填充到这 6px 衬垫内，完全无需负 margin 与阴影扩散。

**裁决推荐**：采用 **方案 A**，以最干净的现代 CSS 规范实现视觉效果与几何稳定性的绝对双赢。
