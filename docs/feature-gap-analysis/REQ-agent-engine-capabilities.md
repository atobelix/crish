## 一、概述与设计原则

### 1.1 文档目的

本文档将用户在功能反馈中提出的所有需求点进行系统化梳理与规范化描述，形成可直接用于开发排期与子 Agent 任务拆解的需求规格。每条需求均包含：

- **需求编号**（全局唯一，格式 `REQ-<模块字母><序号>`）
- **优先级**（P0 = 必做基础 / P1 = 核心体验 / P2 = 进阶增强）
- **需求描述**（用户视角的功能期望）
- **详细规格**（技术层面的行为定义与边界约束）
- **验收标准**（可客观判定的完成条件）

### 1.2 核心设计原则

在所有需求的设计与实现中，必须始终遵守以下原则：

1. **反过度设计**：严格遵守 `ANTI_OVERENGINEERING_GUARDRAILS.md`，不引入过度抽象的中间件管道、复杂断路器或动态路由器。所有实现追求简单、直观、高可读性。
2. **以事实为依据**：AI 对进程健康状态的判断必须基于日志输出、资源占用等可观测事实，严禁凭空臆断。
3. **不误杀正常进程**：系统不得强制 AI 为命令设置硬编码超时。只要进程在正常稳定运行（有日志输出、资源占用合理），就不应被 AI 过度或频繁终止。
4. **保留文档与注释**：所有代码编辑操作必须默认完整保留既有注释、Rustdoc / JSDoc 和上下文文档，除非用户明确要求清理。
5. **减少人工干预**：Agent 应具备全自动化处理交互式命令（如安装确认 `[Y/n]`）的能力，减少用户手动介入的频率。
6. **非放弃既有功能（Additive & Non-Degradation）**：本文档所列出的需求用于补充和扩展系统的能力体系，绝非随意裁撤现有已验证的核心能力。但**功能保留不等于妥协架构**，原有功能的底层实现若妨碍新架构的最佳设计，必须同步重构。
7. **架构纯洁性至上（Architecture Purity First）**：**坚决不允许引入后向兼容（Backward Compatibility）的包袱代码**！严禁编写丑陋的适配器层（Shims/Adapters）、废弃 API 兼容路径或双重逻辑分支。只要新设计在架构上更优、更纯粹、更内聚，凡是不符合新设计的旧接口、旧数据结构与旧 IPC 管道，**一律直接重构、一次到位**。

### 1.3 架构重构与最佳方案落地机制

为了确保工程代码库在功能扩展的同时保持绝对的纯洁性与架构领先性，在落地实施过程中必须遵循以下重构与演进机制：

1. **架构前瞻性与领先性至上（Future-Proof & State-of-the-Art Architecture First）**：
   鉴于项目处于快速迭代的全新阶段，**绝对不能因为现有代码实现或暂时的架构落后而限制软件未来的长期潜力**。在拆解与实施具体需求时，凡是发现现有代码架构或设计模式落后于业内顶尖标准（如现代超快 Agent 引擎架构），**必须果断推翻旧实现，直接采用最前瞻、最先进的领先架构方案进行重构与替换**。
2. **零兼容包袱设计（Zero-Compat-Baggage Design）**：
   新增加的能力（如 DAG 依赖图调度、全局事件总线、多块代码原子替换 `multi_replace` 等）必须采用当前场景下的**最佳架构方案**直接设计。如果既有的 API 契约或底层数据结构无法自然契合最佳方案，**严禁为了兼容旧接口而弯曲新设计**，必须直接升级 API 契约与数据结构，同步更新所有上游与下游调用点。
3. **根源性干净重构（Clean-Root Refactoring）**：
   遇到需要调整的基础模块（如 Session 循环、子 Agent 派发管道、命令执行引擎），应当秉持“根源性重构”原则：在 Rust 内核层修改底层 Trait/Struct，在 `ipc-transport` 升级传输协议，在 React 前端同步更新 Zustand Store，一次性清除所有旧时代的冗余实现。
4. **架构整洁与统一内聚（Architectural Integrity）**：
   所有新增功能与重构代码均须严格融入现有的分层解耦体系（`crates/` 引擎层 ➔ `ipc-transport` 协议映射 ➔ 前端 `StoreAccess` ➔ React UI 视图），确保整个代码库随功能迭代而更加纯炼、清晰、零技术负债。

## 二、模块 A — 命令执行与进程生命周期管理

本模块定义 Agent 在本地操作系统中执行 Shell 命令时的核心行为模型，包括同步/异步切换、守护进程、资源监控与防误杀机制。

---

### REQ-A01：命令执行的三种模式

**优先级**：P0（基础能力）

**需求描述**：  
Agent 执行的每一条命令，应支持以下三种执行模式，由 Agent 根据命令性质自行选择或由用户指定：

**详细规格**：

#### 模式 1：同步等待完成（Sync Wait）

- Agent 发出命令后阻塞等待，直到命令执行完毕（退出码返回），再继续后续逻辑。
- 适用于短命令（如 `git status`、`cargo check`、`ls`）。
- AI 应能设置一个"**预期等待时长**"（如 5000ms），在此时间内命令若完成则直接返回结果。

#### 模式 2：超时自动转后台异步（Auto-Background on Timeout）

- Agent 发出命令并设置一个"**等待窗口**"（如 `WaitMsBeforeAsync = 3000`）。
- 若命令在等待窗口内完成 → 行为等同模式 1，直接返回结果。
- 若命令在等待窗口内**未完成** → 系统自动将该命令升级为**后台异步任务**，分配唯一 Task ID，释放 AI 的执行线程，使 AI 能够继续进行其他判断或工作。
- 这是 Agent 最常用的"弹性"模式：短命令不浪费后台开销，长命令不阻塞 AI 思维链。

#### 模式 3：守护进程模式（Daemon Mode）

- 命令被标记为 `IsDaemon = true`，系统将其作为**持续运行的后台服务**对待。
- 适用于开发服务器（`npm run dev`）、文件监视器（`cargo watch`）、隧道代理等需要一直运行的进程。
- 守护进程不会被系统超时回收，仅在 Agent 显式调用 `kill` 或用户手动终止时才会停止。
- 守护进程的 stdout/stderr 持续写入日志文件，Agent 可随时按需读取最新日志片段。

**验收标准**：
- [ ] Agent 可通过参数在三种模式间切换。
- [ ] 模式 2 中，命令超时后 AI 的执行线程被正确释放，AI 可继续其他操作。
- [ ] 模式 3 中，守护进程在 AI 对话结束后仍然持续运行，日志持续累积。

---

### REQ-A02：工作目录显式指定（禁止 `cd`）

**优先级**：P0（基础能力）

**需求描述**：  
为防止路径状态混乱，Agent 执行命令时严禁使用 `cd` 改变工作目录。

**详细规格**：
- 每条命令通过 `Cwd` 参数显式指定在哪个绝对路径下执行。
- 若 Agent 尝试发出以 `cd` 开头的命令，系统应拒绝执行并返回提示："请使用 `Cwd` 参数指定工作目录，而非 `cd` 命令。"
- `Cwd` 必须为合法的已存在目录的绝对路径。

**验收标准**：
- [ ] 系统拦截并拒绝所有 `cd` 命令。
- [ ] 所有命令在指定的 `Cwd` 路径下正确执行。

---

### REQ-A03：命令输出防溢出控制

**优先级**：P1（核心体验）

**需求描述**：  
防止大量命令输出（如 `git log`、`cargo test` 的完整日志）冲垮 AI 的上下文窗口。

**详细规格**：
- 系统默认设置环境变量 `PAGER=cat`，禁止命令进入交互式分页器。
- 对于已知的高输出命令（如 `git log`），系统建议或自动附加输出限制参数（如 `-n 50`）。
- 命令输出超过设定阈值（如 50KB 或 500 行）时，系统应自动截断并告知 AI："输出已截断，完整日志保存在 `<日志路径>`，可通过文件读取工具查看完整内容。"
- 截断时必须保留**尾部输出**（因为错误信息和摘要通常在末尾），而非只保留头部。

**验收标准**：
- [ ] 超大输出被正确截断，日志文件保留完整内容。
- [ ] 截断策略优先保留尾部信息。

---

### REQ-A04：基于资源监控的进程健康判定（防误杀机制）

**优先级**：P1（核心体验）

**需求描述**：  
系统不得强制 AI 为命令设置硬编码超时来杀死进程。核心原则是：**只要进程在正常稳定运行（有日志产出、资源占用合理），就不应被终止**。需要提供基于事实的进程健康判定能力，而非依赖 AI 的时间猜测。

**详细规格**：

#### 4.1 资源统计采集参数

- Agent 在启动命令时，可选择携带一个 `ResourceMonitor` 参数（布尔型，默认 `false`）。
- 当 `ResourceMonitor = true` 时，系统在命令运行期间**周期性采集并记录**以下指标：
  - **CPU 占用率**：该进程及其子进程树的 CPU 使用百分比。
  - **内存占用**：RSS（常驻集大小）或工作集内存。
  - **最近一次 stdout/stderr 输出时间**：用于判断进程是否"静默卡死"。
  - **磁盘 I/O 活动**（可选）：判断进程是否在进行大量文件读写。
- 采集数据写入结构化日志，AI 在被唤醒时可直接读取最新的资源快照摘要，**无需重新运行命令**。

#### 4.2 进程健康判定逻辑

- **正常运行**：CPU 或 I/O 活跃，或最近 N 秒内有日志输出 → 进程健康，不触发告警。
- **疑似卡死**：CPU 近零、无 I/O、且超过 M 秒无任何 stdout/stderr 输出 → 系统向 AI 发送"疑似卡死"通知，由 AI 决定是否终止。
- **异常退出**：进程自行退出并返回非零退出码 → 系统立即通知 AI，附带最后 N 行日志。

#### 4.3 禁止的行为

- ❌ 系统不得强制要求 AI 在启动命令时必须设置 `timeout`。
- ❌ 系统不得在未经 AI 确认的情况下自动杀死仍在正常运行的进程。
- ❌ AI 不得仅凭"运行时间过长"就终止进程——必须结合资源监控数据做出判断。

**验收标准**：
- [ ] 携带 `ResourceMonitor` 参数的命令，系统可输出结构化资源快照。
- [ ] 进程卡死时 AI 收到通知；进程正常运行时不产生误报。
- [ ] 进程异常退出时 AI 立即收到退出码与尾部日志。

### REQ-A05：命令日志持久化与按需读取

**优先级**：P1（核心体验）

**需求描述**：  
所有后台运行的命令（模式 2 和模式 3），其完整的 stdout/stderr 必须被持久化到日志文件中，AI 可随时按需读取。

**详细规格**：
- 每个后台任务的日志文件路径应在任务创建时返回给 AI。
- 日志文件以追加（append）模式写入，支持 AI 通过文件读取工具指定行号范围读取（如"读取最后 100 行"）。
- 当 AI 被唤醒检查任务时，系统应附带一个摘要信息："任务 `<ID>` 已运行 `<耗时>`，日志已累积 `<行数>` 行，最近输出时间 `<timestamp>`。"
- 日志文件在任务终止后仍保留，不自动删除，便于事后审查。

**验收标准**：
- [ ] 后台任务日志文件在任务创建时路径可查。
- [ ] AI 可通过行号范围读取日志片段。
- [ ] 任务完成后日志文件保留。

## 三、模块 B — 后台任务管理与交互式控制

本模块定义 AI 对后台运行的命令进行管理与交互的完整能力。

---

### REQ-B01：后台任务列表查询

**优先级**：P0（基础能力）

**需求描述**：  
AI 可随时查询当前所有正在后台运行的任务列表。

**详细规格**：
- 返回字段包括：Task ID、命令内容摘要、启动时间、运行时长、当前状态（`running` / `completed` / `failed` / `killed`）、日志文件路径。
- 已完成和已终止的任务保留在列表中一段时间（如 30 分钟），之后自动归档。

**验收标准**：
- [ ] AI 调用 `list` 能获取所有活跃和近期完成的任务。

---

### REQ-B02：任务状态与日志检查

**优先级**：P0（基础能力）

**需求描述**：  
AI 可针对特定 Task ID 查询其详细运行状态。

**详细规格**：
- 返回：任务当前状态、退出码（若已完成）、日志文件位置、运行时长、资源快照摘要（若启用了 `ResourceMonitor`）。
- 若任务仍在运行，附带最近 N 行（如 20 行）的 stdout 尾部输出，便于 AI 快速判断进展。

**验收标准**：
- [ ] AI 可查询任意任务的详细状态与尾部日志。

---

### REQ-B03：交互式标准输入注入（`send_input`）

**优先级**：P1（核心体验）

**需求描述**：  
当后台命令等待用户输入时（如安装依赖的 `[Y/n]` 确认、交互式 CLI 的选项选择），AI 可向该任务的标准输入（stdin）管道发送数据，实现全自动化处理，减少人工干预。

**详细规格**：
- AI 调用 `send_input(task_id, input_text)` 向指定任务的 stdin 写入文本。
- `input_text` 末尾应自动追加换行符（`\n`），除非 AI 显式指定不追加。
- 系统应在检测到后台进程的 stdout 中出现常见的交互提示模式（如 `[Y/n]`、`[y/N]`、`Press Enter to continue`、`(yes/no)`）时，主动通知 AI："任务 `<ID>` 正在等待用户输入，检测到提示：`<提示内容>`。"
- AI 收到通知后可自主决定发送什么输入，或者上报用户手动处理。

**验收标准**：
- [ ] AI 能成功向后台任务的 stdin 发送文本。
- [ ] 系统能自动检测常见的交互提示并通知 AI。
- [ ] 发送输入后命令继续执行，不阻塞。

---

### REQ-B04：任务终止（`kill`）

**优先级**：P0（基础能力）

**需求描述**：  
AI 可优雅终止指定的后台任务。

**详细规格**：
- 发送终止信号时，优先使用优雅终止（如 `SIGTERM` / `CtrlBreak`），等待一定时间（如 5 秒）后若进程未退出再强制终止（`SIGKILL` / `TerminateProcess`）。
- 终止后，日志文件保留，不删除。
- 返回终止结果：成功终止 / 进程已不存在 / 终止失败（附原因）。

**验收标准**：
- [ ] AI 可终止正在运行的后台任务。
- [ ] 优雅终止 → 强制终止的两阶段策略生效。

## 四、模块 C — 定时调度与反应式唤醒引擎

本模块定义 Agent 的时间管理与事件驱动唤醒机制，使 AI 在"无事可做但需等待"的场景下高效运作。

---

### REQ-C01：单次定时器（One-shot Timer）

**优先级**：P1（核心体验）

**需求描述**：  
AI 可设置一个倒计时定时器，到期后系统向 AI 发送唤醒通知。

**详细规格**：
- 参数：`DurationSeconds`（等待秒数）、`Prompt`（到期时发送给 AI 的提示内容）。
- 定时器在后台静默运行，不阻塞 AI 的当前执行。
- 用途示例：AI 启动了一个长编译任务，设置 5 分钟后提醒自己检查编译状态。

**验收标准**：
- [ ] 定时器到期后 AI 收到包含 `Prompt` 内容的唤醒通知。
- [ ] 定时器运行期间不阻塞 AI 的其他操作。

---

### REQ-C02：智能早退条件（TimerCondition）

**优先级**：P1（核心体验）

**需求描述**：  
定时器可配置"早退条件"，当特定事件在定时器到期前发生时，自动取消定时器，避免不必要的唤醒。

**详细规格**：
- `TimerCondition` 参数取值：
  - `"never"`（默认）：无条件等待到期，除非被显式取消。
  - `"any"`：收到**任何来源**的消息时，自动取消定时器。适用于多个后台任务并行、等待任一更新的场景。
  - `"<task-id>"` 或 `"<agent-id>"`：仅当收到**指定发送者**的消息时才取消。适用于等待特定任务完成的场景。
- 约束：不允许同时存在多个会被同一个 sender 触发早退的定时器（防止语义冲突）。

**验收标准**：
- [ ] `TimerCondition="any"` 时，收到任意消息后定时器被取消。
- [ ] `TimerCondition="<task-id>"` 时，仅指定任务的消息能触发早退。
- [ ] 重复设置冲突条件时系统拒绝并返回错误提示。

---

### REQ-C03：周期性 Cron 调度（Recurring Cron）

**优先级**：P1（核心体验）

**需求描述**：  
AI 可设置基于 Cron 表达式的周期性调度任务，每次触发时向 AI 发送通知。

**详细规格**：
- 参数：`CronExpression`（标准 5 段式 Cron 表达式）、`Prompt`（每次触发的通知内容）、`MaxIterations`（可选，最大触发次数）、`IsDaemon`（可选，是否为独立常驻任务）。
- `IsDaemon = false`（默认）：Cron 是当前任务推进的一部分（如轮询部署状态），当前任务在 Cron 结束前保持活跃。
- `IsDaemon = true`：Cron 是独立的常驻任务（如每日报告），设置后 AI 当前任务可正常结束，Cron 继续在后台运行。
- 用途示例：每 5 分钟检查一次构建状态、每小时运行一次健康检查。

**验收标准**：
- [ ] Cron 表达式正确解析并按时触发。
- [ ] `MaxIterations` 到达后 Cron 自动停止。
- [ ] `IsDaemon = true` 的 Cron 在 AI 当前任务结束后仍继续运行。

---

### REQ-C04：反应式唤醒机制（Reactive Wakeup）

**优先级**：P0（基础能力）

**需求描述**：  
AI 的执行模型应为**事件驱动**，而非轮询驱动。当 AI 没有需要立即处理的工作时，应交出执行线程进入休眠，在以下事件发生时被系统自动唤醒：

**详细规格**：
- 触发唤醒的事件类型：
  1. **后台命令完成**：命令正常退出或异常退出。
  2. **子 Agent 发送消息**：子 Agent 完成任务或请求指导。
  3. **定时器到期**：REQ-C01/C02 中的定时器触发。
  4. **Cron 调度触发**：REQ-C03 中的 Cron 到时。
  5. **用户发送新消息**：用户在对话中追加了新的指令。
  6. **进程异常检测**：REQ-A04 中的"疑似卡死"或"异常退出"通知。
- AI 被唤醒时，系统应在上下文中注入事件来源与摘要信息（如"任务 `build-42` 已完成，退出码 0"），AI 无需手动调用查询即可了解发生了什么。
- **严禁**在系统或工具层面实现"定时轮询"来替代反应式唤醒。

**验收标准**：
- [ ] AI 在无事可做时不消耗计算资源。
- [ ] 上述 6 种事件均能正确唤醒 AI。
- [ ] 唤醒时上下文中包含事件摘要信息。

---

### REQ-C05：AI 等待策略自动选择

**优先级**：P2（进阶增强）

**需求描述**：  
当 AI 启动了一个长命令后，系统应辅助 AI 选择最优的等待策略，避免"空转"或"过度沉睡"。

**详细规格**：
- 如果 AI 启动了一个后台命令，且后续**有其他独立任务**可以并行处理 → AI 应继续处理其他任务，通过 REQ-C04 的反应式唤醒等待命令完成。
- 如果 AI 启动了一个后台命令，且**没有其他事可做**、必须等待该命令完成才能继续 → AI 应设置一个定时器（REQ-C01），定时器的 `TimerCondition` 指向该任务 ID，实现"任务完成即唤醒，超时则兜底检查"的双保险策略。
- 系统层面的**兜底防护**：如果 AI 启动了后台命令，既没有设置定时器、也没有继续其他工作，且超过 N 分钟（可配置，如 10 分钟）没有被任何事件唤醒 → 系统自动发送一次兜底唤醒通知："您有一个运行中的后台任务 `<ID>`，已运行 `<时长>`，请检查状态。"

**验收标准**：
- [ ] AI 在"无事可做 + 等待命令"场景下正确设置定时器。
- [ ] 系统兜底防护在超时后正确触发唤醒通知。

## 五、模块 D — 多 Agent 协同调度框架

本模块定义 Agent 引擎中多子 Agent 并行/流水线协作的完整能力，包括派发、隔离、通信与调度。

### REQ-D01：动态 Prompt 子 Agent 派发

**优先级**：P0（基础能力）

**需求描述**：  
主控 Agent 可在运行时动态创建并派发子 Agent，每个子 Agent 接收独立的 Prompt 指令与角色定义。

**详细规格**：
- 派发参数：
  - `Prompt`：分配给子 Agent 的具体任务描述。
  - `Role`：2-5 字的角色标签（如"Rust 内核分析师"、"前端重构者"），用于人类可读的标识。
  - `TypeName`：Agent 类型名（可从预定义类型中选择，如 `research`、`self`，或自定义 Agent 类型名）。
- 每个被派发的子 Agent 获得一个全局唯一的 `ConversationId`，用于后续通信与追踪。
- 支持单次调用中批量派发多个子 Agent（一个调用创建 N 个并行子 Agent）。
- 单轮调度上限遵守项目约定（当前为 12 个）。

**验收标准**：
- [ ] 主控 Agent 可在一次调用中派发 1-12 个子 Agent。
- [ ] 每个子 Agent 获得唯一 ConversationId。
- [ ] 子 Agent 接收到正确的 Prompt 和 Role。

---

### REQ-D02：子 Agent 工作区隔离策略

**优先级**：P0（基础能力）

**需求描述**：  
子 Agent 的文件系统工作区可配置为不同的隔离级别，防止并行修改同一文件时产生冲突。

**详细规格**：
- 三种隔离模式：
  - `inherit`（默认）：子 Agent 与主控 Agent 共享同一工作区。适用于顺序协作或只读任务。
  - `share`：类似 Git Worktree，子 Agent 获得独立的分支上下文但共享底层仓库存储。适用于不同文件的并行修改。
  - `branch`：完全隔离的 Git 分支空间，子 Agent 的所有修改在独立分支上进行。适用于破坏性尝试或实验性重构，成功后可合并回主分支。
- 子 Agent 被终止时：`branch` 模式的分支工作区自动清理（除非有未合并的有价值产出），`inherit` 和 `share` 模式无需清理。

**验收标准**：
- [ ] 三种隔离模式均可正确创建。
- [ ] `branch` 模式下子 Agent 的修改不影响主工作区。
- [ ] 子 Agent 终止后，`branch` 工作区正确清理。

---

### REQ-D03：子 Agent 默认使用当前模型

**优先级**：P0（基础能力）

**需求描述**：  
子 Agent 默认继承并使用当前主控 Agent 正在使用的模型，不需要每次派发时手动指定模型。多模型并行是高级功能，需要用户在设置界面显式启用。

**详细规格**：
- **默认行为**：子 Agent 自动使用与主控 Agent 相同的模型。这是最保险、最一致的策略。
- **多模型模式（高级）**：
  - 需要用户在**设置界面**中显式开启"多模型并行"选项。
  - 开启后，主控 Agent 或用户可在派发子 Agent 时指定不同的模型。
  - 也可由 AI 根据用户需求的描述，自动完成模型配置（如用户说"用轻量模型做搜索"，AI 自行为搜索 Agent 配置轻量模型）。
- 未开启多模型模式时，所有派发参数中的 `Model` 字段无效或被忽略，一律使用当前模型。

**验收标准**：
- [ ] 默认情况下所有子 Agent 使用与主控 Agent 相同的模型。
- [ ] 多模型模式关闭时，`Model` 参数被忽略。
- [ ] 多模型模式开启后，可为不同子 Agent 指定不同模型。

### REQ-D04：自定义 Agent 类型定义（高级角色配置）

**优先级**：P1（核心体验）

**需求描述**：  
主控 Agent 可临时定义新的 Agent 类型，具备比简单 `Prompt + Role` 更丰富的可配置项，用于精细化控制子 Agent 的行为边界。

**详细规格**：

#### 4.1 可配置参数

| 参数 | 类型 | 说明 |
| :--- | :--- | :--- |
| `name` | string | Agent 类型名，在当前会话中唯一（如 `"rust-refactor-agent"`）。定义后可多次实例化。 |
| `description` | string | 人类可读的 Agent 职责描述。 |
| `system_prompt` | string | 该类型 Agent 的完整系统指令（System Prompt）。 |
| `task_type` | enum | 任务类型标签，取值：`analysis`（分析/调研，只读）、`design`（方案设计，只读 + 文档输出）、`review`（评审，只读 + 文档输出）、`implementation`（实现，可写代码 + 测试）、`organization`（整理，可在指定区域内生成/编辑文档）、`commit`（提交，仅 Git 操作）。 |
| `enable_write_tools` | bool | 是否赋予文件创建与编辑权限。对于 `analysis` / `review` 类型，默认 `false`；对于 `implementation` / `organization` 类型，默认 `true`。 |
| `allowed_write_paths` | string[] | **可选**。白名单路径列表，限定该 Agent 只能在这些目录或文件中进行创建/编辑操作。若为空则不做路径限制（仅受 `enable_write_tools` 控制）。例如 `["docs/feature-gap-analysis/", "src/components/sidebar/"]`。 |
| `allowed_read_paths` | string[] | **可选**。白名单路径列表，限定该 Agent 只能读取这些目录或文件。若为空则允许读取全部工作区。 |
| `enable_command_tools` | bool | 是否赋予终端命令执行权限。 |
| `enable_mcp_tools` | bool | 是否赋予 MCP 工具调用权限。 |

#### 4.2 任务类型与权限的默认映射

| 任务类型 (`task_type`) | 默认写权限 | 默认命令权限 | 典型用途 |
| :--- | :--- | :--- | :--- |
| `analysis` | ❌ | ❌ | 代码调研、架构分析、依赖审查 |
| `design` | ✅（仅方案文档目录） | ❌ | 设计方案文档输出 |
| `review` | ✅（仅评审报告目录） | ❌ | 代码评审、安全审查 |
| `implementation` | ✅ | ✅ | 编码实现 + 运行测试 |
| `organization` | ✅（仅指定文档目录） | ❌ | 文档整理、报告生成 |
| `commit` | ❌ | ✅（仅 `git` 命令） | Git 提交与标签 |

- 以上为默认值，主控 Agent 可在定义时覆盖任何默认设置。
- `allowed_write_paths` 为 Rust 侧的硬性沙箱拦截，即使 Agent 的 Prompt 中未约束写入范围，系统也会在文件写入时进行路径校验并拒绝越界操作。

**验收标准**：
- [ ] 可定义包含上述所有参数的自定义 Agent 类型。
- [ ] `task_type` 的默认权限映射正确生效。
- [ ] `allowed_write_paths` 的硬性拦截在 Rust 侧正确实现。
- [ ] 自定义 Agent 定义后可多次实例化。

### REQ-D05：DAG 依赖图自动调度引擎

**优先级**：P1（核心体验）  
**重要性标记**：🔑 **重点需求**

**需求描述**：  
从目前的"主控 Agent 手动拆分并平铺式分发"升级为"根据任务间的依赖关系自动生成拓扑 DAG 图并进行最优调度"。

**详细规格**：

#### 5.1 任务依赖声明

- 主控 Agent 在派发任务时，可声明每个任务的依赖关系：
  ```
  Task A: 无依赖（可立即执行）
  Task B: 依赖 Task A 的产出
  Task C: 无依赖（可立即执行）
  Task D: 依赖 Task B 和 Task C 均完成
  ```
- 系统自动构建 DAG（有向无环图），验证无循环依赖。

#### 5.2 自动并行调度

- DAG 引擎识别所有"入度为零"的任务节点，立即并行派发。
- 某个任务完成后，引擎自动检查其下游任务的依赖是否全部满足，满足则立即派发。
- 所有叶子节点完成后，整个 DAG 调度完成，通知主控 Agent。

#### 5.3 失败处理

- 若某个任务失败，其所有下游任务自动标记为 `blocked`（被阻塞），不再执行。
- 系统通知主控 Agent 失败的任务 ID、错误信息，以及被阻塞的下游任务列表，由主控 Agent 决定是否重试或放弃。

#### 5.4 可视化（可选增强）

- 在前端提供 DAG 拓扑可视化（可使用 React Flow 或 Mermaid），展示各任务的状态（等待 / 运行中 / 完成 / 失败 / 阻塞）。

**验收标准**：
- [ ] 支持声明任务间依赖关系。
- [ ] DAG 引擎正确识别并行可执行的任务并同时派发。
- [ ] 任务完成后下游任务自动触发。
- [ ] 任务失败时下游任务正确标记为 blocked。

### REQ-D06：Agent 间全局事件总线（Global Event Bus）

**优先级**：P1（核心体验）  
**重要性标记**：🔑 **重点需求**

**需求描述**：  
允许并行运行的子 Agent 之间直接进行事件通信（Pub/Sub），而无需所有消息都必须经过主控 Agent 中转。

**详细规格**：

#### 6.1 事件发布与订阅

- 每个 Agent（主控和子 Agent 均可）可向事件总线发布带有 `topic` 标签的事件。
- Agent 可订阅感兴趣的 `topic`，当该 topic 有新事件时被唤醒。
- 预定义的系统 topic 示例：
  - `agent.started`：某个 Agent 启动。
  - `agent.completed`：某个 Agent 完成任务。
  - `agent.failed`：某个 Agent 失败。
  - `task.output`：某个后台命令产出了关键输出。
  - 自定义 topic：Agent 可自由定义业务 topic（如 `rust-build.done`、`frontend-test.passed`）。

#### 6.2 事件内容

- 每个事件包含：`topic`（主题标签）、`sender`（发送者 ID）、`timestamp`、`payload`（自由格式的内容，如 JSON 字符串或纯文本摘要）。

#### 6.3 与 DAG 调度的集成

- DAG 引擎（REQ-D05）内部使用事件总线监听 `agent.completed` 和 `agent.failed` 事件来驱动下游任务的触发。
- 这使得事件总线成为整个多 Agent 系统的统一通信基础设施。

#### 6.4 安全约束

- 子 Agent 只能发布事件，不能直接"命令"其他子 Agent 执行操作（指挥权保留在主控 Agent）。
- 事件按**背压分级持久化（分层持久化）**：**Critical 事件必达落库（重启后可重放，是崩溃恢复、审计底账与 DAG 补投的校验锚点）**；Soft 事件尽力投递（通知留痕，可落库、不阻塞）；Delta 事件内存级可丢（不落库）。自定义业务 topic 若为纯诊断类按 Delta 处理。如需进一步审计，可由主控 Agent 订阅记录。

#### 6.5 Critical 事件落库面清单（附证据，供评审核查）

| 事件域 | 具体事件 | 背压级 | 证据 |
| :--- | :--- | :--- | :--- |
| 子代理生命周期 | `SubagentStarted`（`conex-types/events.rs:567`）/ `SubagentEnded`（`conex-types/events.rs:599`） | Critical | `orchestrator/src/subagent_events.rs:15-19` |
| 子代理消息 | `SubagentEventKind::Message`（`conex-types/events.rs:129`） | Soft | `orchestrator/src/subagent_events.rs:15-19`；`conex-types/events.rs:797-798` |
| 子代理进度 | progress 类（`SubagentEventKind::Progress`） | Delta | `orchestrator/src/subagent_events.rs:15-19` |
| 恢复域 | recovery-* 五类事件（`orchestrator/src/recovery.rs:96-104`） | Critical | 恢复阶梯事件留痕 events 表（`orchestrator/src/recovery.rs:46,592`） |
| 审计面 | security-audit 审计事件（写操作处置留痕） | Critical | `agent-tools/src/audit.rs:23-26`（SecurityAuditSink） |

说明：Delta 不落库由 `orchestrator/src/events.rs` 事件类别分流实现（`event_class`，`orchestrator/src/events.rs:44-47`：progress 类不落库不阻塞 drive loop）；本条为**文档对齐现状**，不改代码。

**验收标准**：
- [ ] Agent 可发布和订阅自定义 topic 事件。
- [ ] 事件到达时订阅方 Agent 被正确唤醒。
- [ ] DAG 调度引擎通过事件总线驱动任务流转。
- [ ] Critical 事件必达落库，重启后可重放；Soft 事件尽力投递（通知留痕）；Delta 事件不落库可丢。

### REQ-D07：事件驱动无轮询唤醒（子 Agent 层面）

**优先级**：P0（基础能力）

**需求描述**：  
子 Agent 完成任务或遇到需要主控介入的问题时，系统自动将消息推送给主控 Agent 并唤醒之，主控 Agent 不需要轮询子 Agent 状态。

- 子 Agent 在执行中遇到任务书未覆盖的问题时，可主动向主控 Agent 发送"上报"消息，请求裁决。
- 主控 Agent 被唤醒后，上下文中自动注入所有待处理的子 Agent 消息（批量推送，不是逐条唤醒）。

**验收标准**：
- [ ] 子 Agent 完成后主控 Agent 被自动唤醒。
- [ ] 多个子 Agent 同时完成时，消息被批量推送。
- [ ] 子 Agent 的上报消息能正确送达主控 Agent。

### REQ-D08：子 Agent 生命周期管理

**优先级**：P0（基础能力）

**需求描述**：  
主控 Agent 可查看、管理和终止所有活跃的子 Agent。

**详细规格**：
- `list`：列出所有活跃子 Agent 及其 ConversationId、Role、当前状态、启动时间。
- `kill`：终止指定子 Agent。被终止的子 Agent 的日志和产出保留，`branch` 工作区被清理。

**嵌套禁止裁决（用户裁决，落为规格正文）**：
- `run_subagent` 仅主 Agent（深度 0）可调用；子 Agent 内调用一律拒绝（结构化错误：`subagent.nesting_denied`，错误文案「你没有创建子 Agent 的能力；所有子 Agent 由主 Agent 分配。请通过消息/上报向主 Agent 请求派发。」）。
- 工具面：子代理 run 装配工具注册表时剔除 `run_subagent`（防浪费，非安全边界）；守卫层兜底拒绝（`maxDepth=1` + `NestingDenied`）。
- 子 Agent 深度恒为 1，无派发能力；等待原语 `wait_subagents` 保留（等待语义与嵌套无关）。
- `kill_all`：终止所有子 Agent 及其后代。
- `resume`：用于恢复被杀死的（或者因为网络问题）子agent，携带其id、名称、prompt激活子agent

**验收标准**：
- [ ] 主控 Agent 可列出、终止单个或全部子 Agent。
- [ ] 被终止子 Agent 的产出文件和日志保留。

## 六、模块 E — 代码编辑与文件操作工具增强

本模块定义 Agent 在进行代码修改时所需的精准编辑能力。

### REQ-E01：多块非连续代码原子替换（`multi_replace`）

**优先级**：P0（基础能力）  
**备注**：此功能曾存在于项目中，在 AI 重构时遗失，需恢复。

**需求描述**：  
Agent 在修改一个大文件时（如在头部添加 `import`、中部修改结构体字段、尾部调整导出函数），应能通过**单次原子操作**完成所有修改，而非多次单点写入。

**详细规格**：

#### 1.1 接口定义

- 工具名：`multi_replace_file_content`（或等效命名）。
- 输入参数：
  - `target_file`：目标文件的绝对路径。
  - `replacement_chunks`：一个数组，每个元素为一个替换块（Chunk），包含：
    - `start_line`：搜索范围起始行号（1-indexed）。
    - `end_line`：搜索范围结束行号（1-indexed）。
    - `target_content`：要被替换的**精确原文**（必须与文件中的内容严格匹配，包括缩进空白）。
    - `replacement_content`：替换后的新内容。
    - `allow_multiple`：布尔值，是否允许在范围内匹配并替换多个实例（默认 `false`，发现多个匹配时报错）。

#### 1.2 原子性保证

- 所有 Chunks 的替换在内存中完成后，**一次性写入磁盘**。
- 若任意一个 Chunk 匹配失败（找不到 `target_content`），**整个操作回滚**，文件不做任何修改，返回错误信息指明哪个 Chunk 匹配失败。

#### 1.3 与单块替换的关系

- 当只有一个修改点时，仍使用 `replace_file_content`（单块替换工具）。
- 当有多个非连续修改点时，**必须**使用 `multi_replace_file_content`，禁止对同一文件并行发起多个单块替换调用（防止竞争条件）。

**验收标准**：
- [ ] 单次调用可完成 N 个非连续代码块的替换。
- [ ] 任一 Chunk 匹配失败时整个操作回滚，文件不变。
- [ ] 替换结果与逐个手工修改的效果一致。

### REQ-E02：文件创建工具

**优先级**：P0（基础能力）

**需求描述**：  
Agent 可创建新文件，父目录不存在时自动创建。

**详细规格**：
- 目标路径必须为绝对路径。
- 默认情况下，若文件已存在则报错（防止意外覆盖）。需要覆盖时必须显式设置 `Overwrite = true`。
- 创建成功后返回文件路径确认。

**验收标准**：
- [ ] 文件及父目录正确创建。
- [ ] 未设置 Overwrite 时已有文件拒绝覆盖。

### REQ-E03：保留文档与注释（编辑规范约束）

**优先级**：P0（基础能力）

**需求描述**：  
所有代码编辑工具在执行替换时，必须保证：**与当前修改无关的注释、文档字符串（Rustdoc / JSDoc / 行内注释）不被删除、修改或移位**。

**详细规格**：
- 这是一项工具级的行为约束，不依赖 AI 的 Prompt 遵守——工具本身的替换机制基于精确内容匹配，天然不会修改未被指定的内容。
- 但在系统 Prompt 与 Agent 指令中，仍需明确强调此原则，防止 AI 在生成 `replacement_content` 时遗漏原文中的注释。

**验收标准**：
- [ ] 替换操作后，未被 `target_content` 覆盖的注释行完整保留。

## 七、模块 F — 搜索、读取与防截断工具体系

本模块定义 Agent 在探查代码库时所需的搜索与文件读取能力，重点解决"AI 读到一半被截断导致误判"的问题。

---

### REQ-F01：全局符号与引用检索（Grep Search）

**优先级**：P0（基础能力）

**需求描述**：  
Agent 可在整个工作区或指定目录/文件中，使用精确文本或正则表达式进行全局搜索，获取所有匹配的文件名、行号与行内容。

**详细规格**：
- 支持两种模式：
  - **文件级匹配 (`MatchPerLine = false`)**：仅返回包含匹配的文件名列表（类似 `grep -l`）。
  - **行级匹配 (`MatchPerLine = true`)**：返回每个匹配的文件名 + 行号 + 行内容（类似 `grep -nI`）。
- 支持大小写不敏感搜索 (`CaseInsensitive`)。
- 支持 Glob 过滤 (`Includes`)，如 `*.rs` 只搜索 Rust 文件、`!**/node_modules/*` 排除依赖目录。
- 结果上限（如 50 条），超出时提示 AI 缩小搜索范围。

**验收标准**：
- [ ] 精确文本和正则两种模式均正常工作。
- [ ] Glob 过滤正确生效。
- [ ] 结果上限后的提示清晰。

---

### REQ-F02：完整文件读取与防截断机制

**优先级**：P1（核心体验）  
**重要性标记**：🔑 **重点需求**

**需求描述**：  
AI 在通过行号范围读取文件时，必须能够获取到**完整的代码 + 注释**内容，不应因为单次传输的字节限制而导致关键上下文丢失。系统应提供明确的续读机制。

**详细规格**：

#### 2.1 行号范围读取

- AI 可指定 `StartLine` 和 `EndLine` 读取文件的精确行范围（1-indexed，闭区间）。
- 单次最大读取行数设上限（如 800 行），超出时只返回范围内的前 800 行。
- 若省略 `StartLine` 和 `EndLine`，默认读取文件开头的 800 行或全部内容（取较小者）。

#### 2.2 字节级防截断续读

- 单次返回的内容有字节上限（如 46080 bytes）。
- 如果指定行范围内的内容超过字节上限，系统**必须**：
  1. 返回已传输的内容。
  2. 在返回结果中明确标注：`"content_truncated": true`，并提供 `ContentOffset` 值。
  3. AI 可通过传入 `ContentOffset` 参数进行续读，从截断点继续获取剩余内容。
- **关键要求**：截断点不应切断在行中间，应在最近的完整行边界处截断，确保 AI 拿到的每一行都是完整的（包含该行的完整注释）。

#### 2.3 二进制文件支持

- 对于图片、视频等二进制文件，不使用行号参数，直接返回完整文件内容（base64 编码或文件引用）。

**验收标准**：
- [ ] 行号范围读取正确返回指定行。
- [ ] 字节截断时标注 `content_truncated` 并提供续读偏移量。
- [ ] 截断点在完整行边界，不会切断某一行的中间内容。
- [ ] AI 通过 `ContentOffset` 续读后能获取完整剩余内容。

---

### REQ-F03：目录结构列举

**优先级**：P0（基础能力）

**需求描述**：  
Agent 可列出指定目录的子文件和子目录，用于快速了解项目结构。

**详细规格**：
- 输入：目录的绝对路径。
- 输出：每个子项的相对路径、类型（文件/目录）、文件大小（若为文件）、子项数量（若为目录）。
- 仅列出直接子项（深度 1），不递归。AI 如需深入某子目录，再次调用即可。

**验收标准**：
- [ ] 正确列出文件与目录并区分类型。
- [ ] 不递归展开子目录。

## 八、模块 G — 文档工作区与多 Agent 协作产出

本模块定义 Agent 生成规划文档、分析报告等长文产出时的工作区管理机制。

---

### REQ-G01：对话级默认工作目录自动生成

**优先级**：P1（核心体验）

**需求描述**：  
当 AI 需要输出文档（如规划方案、分析报告），而用户未指定落位文件夹时，系统应在工作空间中自动生成一个与当前对话绑定的默认工作目录。

**详细规格**：
- **用户指定文件夹时**：直接使用用户指定的路径作为文档产出目录。
- **用户未指定文件夹时**：
  - 系统在工作空间根目录下创建一个默认工作目录，格式建议：`<workspace_root>/.agent-outputs/<conversation-id>/` 或 `<workspace_root>/.agent-outputs/<日期>-<简短标题>/`。
  - 该目录在对话首次需要输出文档时自动创建（惰性创建，不在对话开始时就创建空目录）。
- 工作目录路径在创建后通知 AI，AI 后续的所有文档产出默认写入该目录。

**验收标准**：
- [ ] 用户指定路径时使用指定路径。
- [ ] 用户未指定路径时自动创建默认工作目录。
- [ ] 目录为惰性创建（首次写入时创建）。

---

### REQ-G02：多 Agent 协作文档产出

**优先级**：P1（核心体验）

**需求描述**：  
大型规划文档可能长达数千行，且需要拆分为多个子文档。多个子 Agent 应能并行向同一个文档目录产出各自负责的子文档，最终由主控 Agent 或用户汇总。

**详细规格**：
- 主控 Agent 在派发子 Agent 时，应在 Prompt 中明确指定：
  - **产出目录**：所有子 Agent 共享同一个文档产出目录。
  - **产出文件名**：每个子 Agent 写入不同的文件（如 `01-kernel-analysis.md`、`02-frontend-analysis.md`），避免文件写入冲突。
- 子 Agent 写入完成后，通过事件总线或消息通知主控 Agent，附带文件路径与内容摘要。
- 主控 Agent 可选择：
  - 直接将各子文档作为最终产出呈现给用户。
  - 生成一个汇总索引文档（如 `README.md` 或 `00-summary.md`），链接到各子文档。
- 文档格式遵循项目的 Markdown 规范（UTF-8 无 BOM、中文注释）。

**验收标准**：
- [ ] 多个子 Agent 可并行向同一目录写入不同文件。
- [ ] 不出现文件写入冲突。
- [ ] 主控 Agent 能汇总各子 Agent 的文档产出路径。

---

### REQ-G03：文档工作区与代码工作区的路径隔离

**优先级**：P2（进阶增强）

**需求描述**：  
文档产出目录（规划方案、分析报告等）应与源代码目录有清晰的路径隔离，避免大量 AI 产出的文档散落在源码目录中。

**详细规格**：
- 建议的目录约定：
  - 用户显式指定的文档路径（如 `docs/feature-gap-analysis/`）：直接使用，不做限制。
  - 系统默认的自动工作目录（REQ-G01）：统一放在 `.agent-outputs/` 或 `docs/.agent-outputs/` 下，便于 `.gitignore` 管理。
- 系统可提供配置项，让用户自定义默认文档产出的根目录。

**验收标准**：
- [ ] 默认工作目录不污染源码目录。
- [ ] 用户可自定义默认文档产出根目录。

## 附录 A — 术语表

| 术语 | 定义 |
| :--- | :--- |
| **主控 Agent（Orchestrator）** | 直接与用户交互、负责任务拆解与子 Agent 派发的顶层 Agent。 |
| **子 Agent（Subagent）** | 由主控 Agent 创建的、执行特定子任务的独立 Agent 实例。 |
| **DAG（有向无环图）** | Directed Acyclic Graph，用于描述任务间依赖关系的图结构。 |
| **事件总线（Event Bus）** | 基于 Pub/Sub 模型的内存级消息通信基础设施。 |
| **反应式唤醒（Reactive Wakeup）** | Agent 在无事可做时进入休眠，由外部事件驱动自动恢复执行的机制。 |
| **守护进程（Daemon）** | 标记为长期运行的后台进程，不会被超时回收。 |
| **原子替换** | 多个代码修改在内存中完成后一次性写入磁盘，任一失败则全部回滚。 |
| **防截断（Anti-truncation）** | 文件读取时确保内容在完整行边界截断，并提供续读偏移量。 |
| **资源监控（Resource Monitor）** | 采集进程的 CPU、内存、I/O 和输出时间等指标，用于判断进程健康状态。 |
| **TimerCondition（早退条件）** | 定时器可配置的提前取消条件，避免不必要的唤醒。 |
| **Cron 表达式** | 标准的 5 段式定时调度表达式（分 时 日 月 周）。 |
| **工作区隔离** | 子 Agent 文件系统的三种隔离级别：`inherit`（共享）、`share`（共享仓库独立分支）、`branch`（完全隔离分支）。 |
