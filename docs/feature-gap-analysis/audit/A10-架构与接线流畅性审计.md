# A10 审计：架构纯洁性/先进性 + 接线流畅性

> 日期：2026-08-05
> 方法：全链路追踪（主链路 / 子代理 / 后台任务 / 逃逸监视 / 定时-Cron 五条链路逐段验证数据形状、错误传播、事件消费）+ 架构评估（依赖方向 / 分层 / 耦合 / 扩展点 / 单例）+ 灵魂评估（有接口无行为 / 有事件无消费 / 有工具无装配）+ 技术栈评估（tokio / 错误处理 / 类型设计）

> 结论先行：**接线流畅性总体良好（主链路/子代理/逃逸监视三链绿色），但存在 1 条红色断头链路（后台任务事件面）与 2 个系统性幽灵面（任务域事件发射、定时器/Cron 事件面缓冲无 drain），以及若干"有接口无装配"的准扩展点**。架构分层干净、依赖方向单向、trait 注入模式一致；最大架构债集中在**壳层巨型状态对象 CoreRunState 与"待接线 = allow(dead_code)"的登记纪律**上。

## 三、架构评估

### 3.1 依赖方向（crate 层级）：🟢 干净

```
conex-types（契约）
  ├── conex-fs / conex-diff / conex-sandbox / conex-search / conex-markdown / conex-telemetry / conex-compaction（服务层，均只依赖 conex-types）
  ├── agent-tools（工具层：fs/diff/sandbox/search/types）
  ├── session-loop（引擎层：agent-tools / fs / compaction / telemetry / types）
  ├── orchestrator（编排层：session-loop / agent-tools / conex-db / types）
  └── conex-db（数据层：agent-tools* / types）
src-tauri（壳层：全部收敛）
crish-desktop（前端：IPC + 事件通道）
```

- 依赖图**单向无环**（Cargo.toml 实证，session-loop 不依赖 orchestrator/conex-db，orchestrator 不依赖 fs/compaction 生产面——compaction 仅 dev）；
- **唯一倒置**：conex-db 生产依赖 agent-tools（ExploreDocsQuotaStore 契约，conex-db/Cargo.toml:12-18）——数据层依赖工具层；已注释 dev-cycle allowed（agent-tools 侧为 dev 边，生产无环），属可容忍但需登记的结构性折衷；
- 壳层 src-tauri 作为唯一汇聚点承担全部装配（符合"外壳装配"职责），但这也意味着壳层体积失控（见 3.4）。

### 3.2 分层：🟢 清晰

契约层（conex-types：事件枚举 + 信封 + 状态机转移表）→ 服务层（叶子 crate 纯功能）→ 工具层（agent-tools：工具注册表 + 安全面）→ 引擎层（session-loop 状态机主循环 / orchestrator 编排恢复）→ 壳层（装配 + IPC + 适配器）→ 前端（纯消费）。分层职责边界基本一致；`agent-tools` 的 audit/middleware/registry 面被 session-loop 直接消费（引擎层依赖工具层）符合"工具即服务"设计。

### 3.3 扩展点设计（trait 注入）：🟢 模式一致，🟡 纪律问题

- 注入模式高度一致：`Arc<dyn Trait>` + Option 缺省（ProviderCall / ApprovalGate / DeltaSink / Summarizer / TimerChannel / SubagentWaitChannel / DaemonRunLauncher / SubagentSpawner / EscapeWatchInjector / UndeclaredWriteDetector / OutputDirResolver / AuditSink / BackgroundTaskManager / Store / Emitter，约 15 个）——便于测试替身与壳层装配；
- **纪律问题**：`#[allow(dead_code)]` 被当作"待接线"标记使用（EventBridgeSink / set_event_bridge / with_deadlock_detector 等 6+ 处）——编译器静音掩盖了"接口已建、装配未做"的事实，与 D-04（clippy 豁免面蔓延）同属"豁免面代替登记面"的机制缺陷；D-29（装配降级 None 不告警）使生产静默缺功能成为常态路径。

### 3.4 单例 / 可达性：🟡 CoreRunState 巨型状态对象 + D-02 可达性缺口

- `CoreRunState`（`core_run_commands.rs:1100-1200` 域）持有 store / engine / bridge / active_runs / pending_queue / background / subagent_spawner / diagnostics / session_history / resume 判定器等 ~30 个字段，是事实上的服务定位器（service locator）——壳层一切命令经它取全局对象；功能轮次每轮都在它上面加字段（T-D-13 加 subagent_spawner、T-CF-11 加 resume 判定器、T-40 加缓存态）；
- D-02 已登记的三处可达性缺口（nudge 通道无访问入口、EventQueue 无单一实例、活动 run 注册表跨模块不可达）仍在：ControlBusResolver=Noop 即注册表不可达的直接后果，WaitChannel 的 inject 面因此永久降级；
- `SessionLoopOptions` 22 字段（D-01）随轮次膨胀，`..Default::default()` 收尾三处（B-31）依赖默认值补缺——装配遗漏静默 None。

### 3.5 状态机 / 数据面：🟢 结构良好

- 状态机转移表逐行穷举（conex-types apply_transition + AgentSessionMachine）而非散落 if 分支；未定义转移显式失败——这是全仓最"有灵魂"的骨架；
- 事件体系：registry_drift 全事件循环断言（E-27 自检机制）+ events_schema_version 基线 + event_hook_mapping 分区计数（B-40 手工同步）——契约面护栏扎实，与"事件有消费者"是两回事（护栏保证形状，不保证装配）。

## 四、灵魂评估

**整体评级：B+（骨架与肉都全，约七成模块有灵魂）**

判定依据：主链路/子代理/逃逸监视三链是端到端真实闭环（数据形状、错误传播、事件消费三面齐备，且各有集成测试锚定）；但后台任务域与定时器事件面两个"事件消费者已备、发射者未接线"的幽灵面，以及 task_events.rs 这种"纯逻辑堆砌 + 零装配"的模块，说明**装配完成度低于契约完成度**——代码的"意图"与"生效"之间存在系统性落差，落差来源不是设计而是**装配登记纪律**（dead_code 静音 + None 降级 + 无健康检查）。

### 最有灵魂模块：逃逸监视链路（session-loop/escape_watch.rs + 壳层接线）

唯一一条从"外部物理事件"（notify 文件变更）到"AI 感知"（主 agent 注入 + 审计面板 + 高风险着色逻辑）四段全通的链路：watcher → 判定器（与工具互斥共享同一注册表实例，F7 闭环）→ 聚合限流（同路径去重 + 双限流）→ 双通道发射；每段都有集成测试锚定（真实 watcher + 消费循环 + 断言审计载荷形状）。设计意图（"监视是追踪面，不阻断"的诚实边界）贯穿实现。

### 最无灵魂模块：orchestrator/task_events.rs（838 行）

四类唤醒摘要模板、批量注入合并、审计留痕聚合、C7 steering 去重——全套逻辑 + 全套测试（30+ 用例），生产**零调用方**。它是"需求完成度 100%、接线完成度 0"的标本：测试验证的是它自己的逻辑，而不是它在系统中的位置。次之：EventBridgeSink（半成品两臂 + dead_code）。
