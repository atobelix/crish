## T2 H02：suspicious UI 生产接线（高）

### 现状证据（已核实）

- Rust 侧 `task-suspicious` 事件确有发射逻辑（background.rs:1964/2122），但生产链路 `TaskNotifier::unwired()`（background.rs:738）+ `set_event_bridge` 全仓零调用（A10 N-01）+ `EventBridgeSink::emit` 仅两臂（A10 N-03）——事件面生产零发射，**事件路径整链断在 Rust 装配**。

1. **Rust 侧小改**（background.rs）：`BackgroundTaskInfo` wire 结构体增补 `suspicious: bool`（serde camelCase 自动落 `suspicious`）；序列化时从 registry 内部任务状态带出（registry 已有 suspicious 判定与防抖：background.rs:2122 notify_suspicious、:4120 debounce 逻辑；list 快照构造点取该状态）。契约测试补字段断言。

   - 前缀越界：根 `c:/work` + `c:/workspace/x.txt` → 拒；根 `c:/work` + `c:/workspace` → 拒；

## T7 A-04：task/timer/cron 真实消费路径 + 全局事件面（中）

### 现状证据（已核实）

- 10 个 handler 显式空实现（taskEventHandlers.ts:27-77，dispatch.ts:120-133 注册）；A6-M02 补充结构性约束：任务事件经 per-run EventRouter 到达（ConnectionLifecycle.ts:526-544），run 结束 router 卸载后跨 run 存活任务的后续事件无消费者。
- Rust 侧任务事件发射时 runId 为 None（background.rs:2010-2011 `AgentEventEnvelope::new(event, None, None)`）→ `messageBelongsToRun`（eventUtils.ts:30-39）对无 runId 事件放行——per-run router 在 run 期间也会收到数据面事件，双面并存。
- transport 提供全局广播订阅 `onMessage`（tauriTransport.ts:204-211，懒订阅 `workbench-run-event` fanout）——**现成的全局事件面载体，无需新监听通道**。
- Rust 发射面（set_event_bridge + EventBridgeSink 七臂 + timer/cron 缓冲 sink drain）为 A10 红链（N-01/N-03/N-05），归 D1。

### 设计：全局数据面路由（前端）

1. **新建全局数据面路由**（建议 `chat-bridge/dataPlaneRouter.ts` 或并入 transport 消费面）：
   - 模块级单例订阅 `transport.onMessage`，解析事件信封（复用 `resolveEventType`/`parseBridgeEvent`）；
   - 只处理数据面类型集合 `DATA_PLANE_EVENT_TYPES = task-* 7 + timer-* 2 + cron-fired`（+ security-audit 可选并入——现安全审计走 per-run 面，迁移到全局面可顺带解决 run 结束后审计事件丢失，列为可选增强）；
   - 不带 runId 过滤（数据面事件 runId 为 None），承载跨 run 存活任务事件；
   - 生命周期：模块级单例 + refcount（对齐 useEngineState 模式），transport 重连后 fanout 自动恢复（懒订阅机制现成）。
2. **per-run EventRouter 隔离**：在 EventRouter 的 `handleAgentEvent` 入口对数据面类型直接 return（类型集合常量共享），避免双面重复 dispatch——数据面事件不进 run 流，run 流专注 run 内事件。改动点：EventRouter.ts 一处 + dispatch.test.ts 保持 41 键穷举不变。
3. **真实消费语义**（taskEventHandlers.ts 重写 10 个 handler）：
   - 新建 `backgroundTasksStore`（zustand，模式对齐 securityAuditStore.ts：id 为键的任务状态映射 + suspicious 标记 + 最近事件水位）。**或者**更小改动：事件驱动「刷新信号」——handler 触发一次列表拉取（节流：同任务同类型事件 1s 内合并一次），刷新结果回灌 useEngineState/useBackgroundTaskPolling 的下一轮轮询。方案选择建议：**先做「刷新信号」最小版（T7a），store 全量版（T7b）作为增强**——刷新信号复用现有轮询管道，改动量最小、风险最低，且天然与轮询 wire（T2a）一致性。
   - task-started/completed/failed/killed → 刷新信号（立即拉一次列表；节流防风暴）；
   - task-suspicious → 刷新信号 + 本地置标提示（T2b 使用）；
   - task-output/heartbeat → 仅日志水位提示（可选，默认只计数不渲染，防高频噪声）；
   - timer-fired/timer-cancelled/cron-fired → 刷新信号（workflow 运行历史随之更新；cron-fired 可驱动 workflowRuns 刷新）。
   - 显式降级登记：若本轮不接线 timer/cron 展示面，handler 保留「记录最近一次事件到轻量 store + 日志」的**可观测空实现**，并标注待接线面（对齐 A6 建议：接线前登记为「待接线」而非「已实现」）。
4. **测试**：
   - 数据面路由单测：注入模拟 transport 事件 → 断言数据面类型被消费、run 内类型不被数据面路由拦截、per-run EventRouter 对数据面类型 return（双面隔离）；
   - handler 单测：各类型事件 → 断言刷新信号触发（mock 拉取函数）与节流生效；
   - dispatch.test.ts：41 键穷举不回归。
