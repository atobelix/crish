## 结论速览

- **7 张任务卡（P1~P7）**，覆盖用户任务书 6 项（第 2 项按发射面 / 消费面拆两张卡）。

## 二、任务卡 P1：run 控制面接线（最高优先，A4 H2）

### 现状证据（已核对）

- 内核自建总线/信号：`LoopState` 构造时 `control_bus: Arc<Mutex<ControlBus>>` + `abort_signal: AbortSignal`（`loop/handlers/mod.rs:142-143`；字段 :68-70）。
- `AgentSessionLoop` 装配面（`loop/mod.rs:383-525`）只有 with_options / with_tool_options / with_approval / with_delta_sink / with_initial_conversation（+arc）；`abort_signal()`（:507-510）与 `control_bus()`（:512-515）仅是内部实例 getter，**全仓生产零调用**。
- 壳层另建孤儿总线：`core_run_commands.rs:2596` 新建 `control_bus`（逃逸注入器共用 :2605、:446-455）；`ActiveRun` 存入该 bus + **新建** `abort_signal`（:2840-2841）。
- 全部控制意图写入孤儿侧：`run_control_impl` L1（:2930-2939）/ L2（:2942-2952）/ L3（:2954-2978）；`ForceCancelSink` kill_all L3（:1751-1755）；逃逸 `ControlBusInjector`（:446-455）。
- 消费点在 loop 侧：`check_control`（`loop/handlers/mod.rs:515-550`；`safe_point.rs:126-130` 信号优先读）——**永不消费壳层总线**。
- `spawn(drive_run_loop)` 未保存 JoinHandle（:2855）。
- 附带：AbortSignal 无 reset（A4 M3；测试续接路径跨 run 失效，生产每 run 重建 loop 不受影响）。

### 改动点

1. **session-loop 内核补装配面**（`loop/mod.rs`，与既有 with_* 风格一致）：
   - `AgentSessionLoop::with_control_bus(Arc<Mutex<ControlBus>>)`：替换 `state.control_bus`（字段 pub(crate)，同 crate 可达）。
   - `AgentSessionLoop::with_abort_signal(AbortSignal)`：替换 `state.abort_signal`。
   - 顺序契约：必须在 `run()` 之前调用（与 with_options 同契约，`loop/mod.rs:381-382` 已注明）；check_control 读字段引用，替换即生效，run 内不可变。
   - 顺带（M3 低优）：`AbortSignal` 补 `reset()` 或文档化「每 run 重建 loop + 新信号」契约——生产路径天然满足（每次 run_task_impl 新建信号），测试复用路径补 reset。
2. **壳层装配**（`core_run_commands.rs` run_task_impl）：
   - 保留现有 `control_bus`（逃逸注入器继续用）；`ActiveRun.abort_signal` 在 produce 前经 `SessionLoopProducer` 新字段注入 loop（同一实例 clone；AbortSignal 内部共享状态，`safe_point.rs:369` 测试已证明克隆共享语义）。
   - `SessionLoopProducer`（`engine.rs:2380` 构造、`core_run_commands.rs:2799` 使用）增 `with_control_bus` / `with_abort_signal` 透传字段，在 `produce()` 内 loop 构造后、`run()` 前应用——与 P5 的「装配后注入」共用同一注入点，建议合并实现（一次改动双卡受益）。
3. **JoinHandle 管理**：`ActiveRun` 增 `driver: tokio::task::JoinHandle<()>`；`:2855` 保存；`drive_run_loop` / `finalize_failed` 收口 remove active_runs 时 detach（不 await，防挂起）。L3 强停后 run 经安全点快速收场，句柄用于可观测与未来 join 语义。
4. **端到端测试**（核心验收）：
   - 「TestProvider 栅栏 + L3 强停 → run 立即 aborted」：provider 阻塞挂起 turn → `run_control_impl` L3 → loop 下一安全点消费 abort → `RunOutcome.reason == Aborted`。
   - L1 soft_inject / follow_up → 会话实际收到注入消息（conversation 增长 / steer 环消费，不再只是 side effect 置位）。
   - L2 cooperative_stop → reason == Stopped。
   - kill_all（ForceCancelSink）→ 目标 run aborted。
   - 逃逸注入（run 进行中）→ 主 agent followUp 真实到达（总线被 check_control 消费）。

### 风险

- 注入时序：with_* 在 run() 前是编译期不可见的顺序契约——在 run() 内加 debug 断言（装配未注入告警）。
- 同实例共享：ActiveRun.abort_signal 与 loop 内信号必须同一实例 clone；避免「壳层置位、loop 不可见」复发——端到端测试锚定。
- JoinHandle detach 语义：收口路径不 await，防 panic 挂起（与 tokio 惯例一致）。

### 验收标准

1. `control_bus()` / `abort_signal()` getter 有生产消费方（或移除）。
2. L1/L2/L3 三条路径均有「loop 实际反应」端到端断言（不再只是 side effect 断言，响应 A4 E-07 盲区）。
3. 运行中 run 有真实外部终止路径：L3 强停 ≤ 下一安全点收场。

### 测试锚点

- 新增：`core_run_commands.rs` 测试区（ActiveRun 构造先例 :4430-4431、force_cancel 语义测试 :5042-5057 可扩展为真 loop 断言）。
- 回归：`safe_point.rs:369` abort_signal_preempts_bus、`loop/mod.rs` safe_point 既有测试保持绿。

## 三、任务卡 P5：逃逸判定器时序修复（A4 H1，C-36 假闭环更正）

### 现状证据（已核对）

- 壳层在 run 装配**之前** spawn：`core_run_commands.rs:2597-2606`（:2599-2605 只 with_injector，无 with_detector）。
- `consume_loop` spawn 时把 config 整体 move（`escape_watch.rs:356-366`），detector 读取恒为捕获值（:385-391 `unwrap_or(false)`）。
- `with_detector` 注入在 loop 的 with_options（`loop/mod.rs:409-413`），只作用于 `SessionLoopOptions.escape_watch` 副本；唯一读取方 `escape_watch_config()`（:523-525）**生产零调用**（仅 :1199 测试）。
- 后果：生产 `RegistryBackedDetector` 永不生效——工具声明覆盖的写路径全部按「未声明」上报（审计噪音 + 主 agent 注入刷屏）。

### 改动点（推荐方案 B：壳层同源构造 + 注入两端；审计 A4 建议同款）

1. `run_task_impl`（`core_run_commands.rs:2596-2627`）重构：
   - 按 with_options 同源解析链（workspace_root → cwd → 当前目录，`loop/mod.rs:388-395`）创建 `WritePathRegistry::new(session_id, root)`（壳层已用此类：subagent 沙箱 :2660）。
   - spawn 前 `config.with_detector(RegistryBackedDetector::new(registry.clone()))`（类型 pub：`undeclared_detector.rs:32-39`；EscapeWatchConfig::with_detector pub：`escape_watch.rs:108`）。
   - 同一 registry 注入 `SessionLoopOptions.write_claims`（producer 装配处 :2799）——with_options 解析链 `options.write_claims.clone()` 优先（`loop/mod.rs:399-402`），保证与工具执行面**同一实例**。
2. 备选方案 A（若 B 的实现受阻）：`RunProducer` trait（`core_run_commands.rs:130`）增 `escape_watch_config()`，`SessionLoopProducer` 转发 `loop.escape_watch_config()`；`drive_run_loop`（:2035 produce 后）取装配后 config 再 spawn、存 `active.escape_watch`。缺点：trait 面扩展 + spawn 移入 drive_run_loop 与 finalize_failed shutdown 路径（:2074-2081）交织。**推荐 B**。
3. 文档更正：`审计准备-已知缺点与技术债汇总.md` C-36「已闭环」登记不实（A4 已指出），任务卡产出时同步更正为「闭环中 / 见本方案 P5」。
4. 顺带项（不阻塞）：escape_watch_config() 消费方转正或保留观测用途；M2（时间窗非定时器）与 L3（shutdown 无超时）不属本卡，登记邻接。

### 风险

- **注册表根解析双处漂移**：run_task_impl 与 with_options 各有一份 root 解析链，若 cwd 缺省场景下 current_dir 解析时序不一致 → 判定器与工具执行不同源 → 假闭环复发。对策：提取共用解析 helper（壳层 subagent 块已有类似 :2645-2651），并在端到端测试覆盖「无 cwd 场景」。
- 双端注入遗漏：options.write_claims 注入与 detector 构造必须成对——代码评审清单项。

### 验收标准

1. 端到端：工具执行声明写路径 → 监视该路径写入 → **不**产生 undeclared-write 审计（声明覆盖静默）；未声明路径写入 → 产生审计。两种路径均断言。
2. 生产 run 的审计噪音消失（registry 非空时全量写不再误报）。
3. C-36 登记更正落地。

### 测试锚点

- 新增：`core_run_commands.rs` 端到端（真实 watcher + 真实 registry + 声明/未声明双路径，沿用 A1 轮真实 watcher 测试先例）。
- 回归：E-A3 冒烟（`loop/mod.rs:1105`，options 副本注入）保持绿——本卡在其之上补「生产链路生效」断言。

## 四、任务卡 P2：task 七事件生产发射（A10 N-01/N-03）

### 现状证据（已核对）

- 生产构造 `TaskNotifier::unwired()`（`background.rs:738`；`resource.rs:335` 双通道 None → LogEventSink 留痕）。
- `BackgroundTaskRegistry::set_event_bridge`（`background.rs:832-840`）带 `#[allow(dead_code)]`，main.rs 在 `:360` 构造 registry 后**零调用**。
- `EventBridgeSink::emit` 仅 task-suspicious / task-failed 两臂（`background.rs:1963-2008`），其余落入 `other => warn 丢弃`（:2000-2007）。
- 更上游缺口：`TaskNotifier` 只有 notify_suspicious / notify_failed 两个投递方法（`resource.rs:369-415`），**task-started / task-output / task-heartbeat / task-completed / task-killed 五个事件连发射点都没有**（background.rs 全部发射点仅 :1918 notify_failed、:2122 notify_suspicious）——审计 N-03 的「五事件无映射」根因在投递方法层。

### 改动点

1. **resource.rs `TaskNotifier` 补五个投递方法**（payload 按 conex-types events.rs 对应变体字段组装，camelCase 由 serde rename_all 处理）：
   - `notify_started(task_id, owner_run_id, pid, started_at_ms)` → task-started；
   - `notify_output(task_id, bytes, line_count, at_ms)` → task-output（**节流**：100ms 窗口合并聚合，防止高频输出刷屏；与心跳合并策略二选一）；
   - `notify_heartbeat(task_id, at_ms)` → task-heartbeat（若 task-output 已覆盖活跃证明可免发，登记为契约取舍，默认按七事件齐全实现）；
   - `notify_completed(task_id, exit_code, duration_ms)` → task-completed；
   - `notify_killed(task_id, reason, at_ms)` → task-killed。
2. **background.rs 挂接发射点**：adopt 登记（:1133 附近）发 notify_started；`forward_streams` 输出转发段发 notify_output（节流）/ heartbeat；`finish_task`（:1918 notify_failed 处补成功分支 notify_completed）；kill 两阶段路径（:1428-1544）发 notify_killed。
3. **EventBridgeSink::emit 全臂映射**：补五个 match arm（:2000-2007 前），`other =>` 保留 warn 兜底；或改类型化映射表（A10 建议）。
4. **main.rs 装配**：`:360` 构造后调 `background_tasks.set_event_bridge(bridge.clone(), session_id)`——session_id 语义沿用审计注释（注册表无会话概念，注入当前会话 / 空串占位，归属经信封 runId 与 payload ownerRunId 表达；`background.rs:1938-1941`）。
5. **移除 dead_code**：background.rs:831（set_event_bridge）、:1943（EventBridgeSink）、resource.rs:359（set_event_sink 生产路径）。

### 风险

- **输出事件高频**：节流设计不足会刷爆 workbench-run-event 通道（event_backpressure 分级兜底存在，但发射面自身应先限流）。
- 会话归属漂移：注入的 session_id 与真实会话可能不一致——文档化 + ownerRunId 归组（task_owner_run_id，见 P3）。
- 前端 A-04 七 handler 仍显式空实现（taskEventHandlers.ts）——本卡激活发射面但 UI 仍走轮询；前端消费为**邻接战役**（A-04 登记），不在本方案范围，验收不受阻。

### 验收标准

1. 真实任务全生命周期：adopt → 输出 → 完成/失败/被 kill，七事件全部经 `workbench-run-event` 通道发射（测试用内存 EventBridge 替身收集）。
2. EventBridgeSink 全臂无 `other` 丢弃路径（测试断言枚举覆盖）。
3. 三处 allow(dead_code) 移除（编译期验证接线完成）。

### 测试锚点

- 新增：EventBridgeSink 全臂发射形状测试（内存 bridge）；TaskNotifier 五新方法载荷断言（对齐 resource.rs:532 MemSink 先例）；adopt→terminate 事件序测试（started → output → completed/killed）。
- 回归：background.rs 既有 notifier 注入测试（:3884 with_nudge_queue）、resource.rs 判定矩阵保持绿。

## 五、任务卡 P3：task_events.rs 消费面接入（A10 N-02 / A-48）

### 现状证据（已核对）

- `orchestrator/task_events.rs` 838 行 + 全套测试（TaskWakeBatch / TaskAuditAccumulator / steer_for_task_failed / build_wake_steering_entry / task_owner_run_id / filter_tasks_by_owner），**src-tauri 零调用**（rg 实证 NO_MATCHES）。
- nudge 通道（PendingNudgeChannel）在 orchestrator PendingMessageQueue 内部，壳层无访问入口（D-02 / resource.rs:318-319 注释自认）——唤醒只能走 steering 队列。

### 改动点（接线点设计）

1. **新消费组件**（建议 `background.rs` 内或独立 `task_event_consumer.rs`）：持 `HashMap<Option<String /*owner_run_id*/>, TaskWakeBatch>`，任务终态事件到达时（P2 发射点同一位置）：
   - `TaskWakeBatch::push(&event)`（按 owner_run_id 分组批次，同 run 多任务合并为一条注入，REQ-D07 语义）；
   - `TaskAuditAccumulator::push(&event)` → 聚合 `security-audit`（operation=command-exec）经 EventBridge 发射（对齐 shell.rs 红线拦截先例；审计基线 31-security-baseline.md B4）；
   - task-failed 且「AI 显式等待」时 `steer_for_task_failed(...)` → 经引擎共享 `pending_queue` 入队（group_id=`task-<id>` 原位替换去重，is_steering 受保护位）。
2. **注入时机决策（需主 Agent 裁决，两案）**：
   - 案 A（推荐 v1）：终态即 drain_merged → `build_wake_steering_entry` → pending_queue。简单可靠，run 运行中条目在下次收口送达（不打断，对齐 REQ-D07）；多任务并发去重由 `replace_or_enqueue` 兜底；「同 run 合并一条」语义降级为「同任务原位替换」（批次按 owner 聚合的完整语义留 v2）。
   - 案 B：批次按 owner_run_id 累积，run 收口时经 CoreRunState 回调 drain——语义完整但跨模块回调节点复杂。
3. **访问链**：CoreRunState 增 `pub(crate) fn steering_queue(&self) -> Arc<Mutex<PendingMessageQueue>>`（透传 :1174 字段，对齐 :1452 模式）；审计事件经 CoreRunState 既有 bridge（或 EventBridge 注入消费组件）。
4. **无归属任务**（owner_run_id=None，如 daemon）：跳过唤醒只留审计留痕（登记为决策）。

### 风险

- 注入时机两案是体验决策（即时唤醒 vs 聚合注入），必须主 Agent 裁决后才实现。
- security-audit 走实时轨（sequence=None 广播）与 A-05 落库未接并存——不阻塞本卡，邻接登记。
- 与 timer/cron steering 共用队列：条目形状一致（SteeringInputEntry），无冲突。

### 验收标准

1. 端到端：任务完成 → 主 agent 收到「任务 <id> 已完成，退出码 N」注入（adopt → 完成 → 断言 pending_queue 条目 / 下个 run 注入消息）。
2. security-audit 事件流出现 command-exec 记录（任务启停/终止/归档留痕）。
3. task_events.rs 全部 pub 入口至少一个生产调用点（838 行死代码转正，响应 A10「最无灵魂模块」）。

### 测试锚点
