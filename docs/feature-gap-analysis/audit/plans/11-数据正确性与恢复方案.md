## T1（N04）runs 未知状态映射：显式 Unknown 透传，消除静默破坏

### 问题定位（证据）

- `crates/conex-db/src/runs.rs:362-375`：`map_run_row` 注释自称「按 Unknown 兜底」，实现为 `RunStatus::from_str(&status_str).unwrap_or(RunStatus::Failed)`——任何未知状态字面量被静默改写为 failed。
- 破坏链：`query_all_runs`（runs.rs:276-295）与 `get_run`（runs.rs:165-178）共用该映射 → 恢复域全量扫描（restore.rs:536 `store.query_runs()`）把未知状态 run 误判为终态 failed，既不打断也不收口 → `run-interrupted` 审计缺失、前端显示失真。
- 双路径语义分裂：快照路径 `SnapshotRun::to_stored_run`（restore.rs:212-225）对未知字面量是 **fail-closed**（`from_str` 返回 `SnapshotError`，快照读取被拒绝）；DB 行路径却是 **fail-open 且破坏性**（改写 failed）。同一状态字面量两条读路径处置相反。
- 写边界反而是严格的：recovery.rs:652-660 只接受 failed/completed/cancelled 三个终态字面量，其余返回 InvalidState。

### 方案决策（推荐）

`RunStatus` 增加显式变体 `Unknown(String)`（携带原始字面量），`as_str()` 对 Unknown 透传原字面量（roundtrip 保真，快照/事件/前端均不丢信息）：

- `map_run_row` 对未知字面量返回 `Ok(RunStatus::Unknown(s))`，不再 `unwrap_or(Failed)`；
- `is_inflight(Unknown) = false`：恢复时**保真保留、不打断**。理由：未知字面量无法区分「新版本的中间态」与「新版本的终态」，打断=改写为 failed 对可能已完成的 run 是破坏性操作，保真 + 显式上报是唯一不破坏数据的选择；
- 恢复输出显式上报：`RestoreOutcome` 增加未知状态 run 清单/计数（或至少 `tracing::warn` + 返回字段），供操作者介入；不静默。

**备选（A3 另一建议，fail-closed）**：`map_run_row` 返回错误 → `query_all_runs`/restore 整体失败、应用启动受阻。代价是恢复流程不可用，仅适合「宁可不可用也不放过坏数据」的运维场景，列为备选并在文档登记理由。

**放弃 Copy 的取舍**：`Unknown(String)` 使枚举失去 `Copy`（现枚举 9 态带 `Copy`）。全仓按值传递点（restore.rs:544 `let previous_status = run.status`、run.rs 状态机 `state` 字段与 transition 返回值、persist/events 的 `insert_run/update_run_status` 实参、各测试断言）需机械补 `.clone()`——编译器逐点指引，无手工遗漏风险。若评审反对放弃 Copy，退化为 fail-closed 备选。

### 涉及文件与改动点

1. `crates/conex-db/src/runs.rs`：枚举加 `Unknown(String)`；`as_str` 透传；`map_run_row` 显式映射（runs.rs:363-375）。
2. `crates/orchestrator/src/restore.rs`：`is_inflight`（:668-677）显式列出 Unknown=false；恢复循环（:540-549）对 Unknown 分支不做打断、追加上报（RestoreOutcome 新字段或 warn）；`SnapshotRun::to_stored_run`（:212-225）放宽为 Unknown 透传（与 DB 行路径一致）——若评审保留严格，则文档化双路径差异。
3. `crates/orchestrator/src/run.rs`：状态机（:139-161 transition 表）为 Unknown 增加显式臂（拒绝迁移，返回 TransitionError 或视为死态），`is_terminal`（:132）明确排除 Unknown。
4. `crates/orchestrator/src/recovery.rs`：:652-660 写边界保持严格（不动，登记为「写严格/读透传」对称语义）；`to_run_status` 类映射核对点。
5. `crates/orchestrator/src/session.rs`、`persist.rs`：`SessionRecord.status` / Store 签名透传，核对编译即可。
6. `apps/agent-workbench`（Rust 壳）与前端：`packages/shared-types/src/orchestration.ts:5` 的 `RunStatus` 联合类型已是窄化版（连 completing 都没有），建议放宽为 `RunStatus | (string & {})` 或保持窄化并在消费面「未知字面量原样显示」。

### 风险

- 枚举改动波及全仓穷举匹配点（编译器保障，但每个匹配的语义分支需人工核对——重点：is_inflight、restore 映射、状态机转移表）。
- Unknown 非 in-flight 语义意味着未知态 run 会以原字面量滞留（类 Completing 的滞留问题）——以显式上报对冲，比静默改写更安全，属「诚实滞留」取舍。
- 快照路径放宽后，旧快照里的未知字面量不再拒绝加载——语义从 fail-closed 变 fail-open（保真），需在文档中冻结该决策。

### 验收标准

1. 未知字面量不再被改写为 failed（行内 status 字节不变）；
2. 恢复后未知态 run 保真保留、不产生 `run-interrupted` 审计事件，且恢复输出含显式上报；
3. 快照含未知字面量时往返一致（存→读→写不丢信息）；
4. 全仓 `RunStatus` 穷举点编译通过并逐点核对语义。

### 测试锚点

- conex-db 新增：raw SQL 插入未知字面量行 → `query_all_runs`/`get_run` 返回 `Unknown(原字面量)`，`as_str()` 往返保真；
- restore.rs 测试域新增：未知态 run 恢复保真 + 上报计数（对照 `restore_marks_in_flight_runs_interrupted_with_previous_status`，restore.rs:780-880 五态列表不变）；
- 快照测试：`snapshot_full_roundtrip_and_incremental_restore`（restore.rs:968-1019）扩展未知字面量快照往返；
- 全量回归：`cargo test --workspace`（RunStatus 变体改动跨 crate 编译面验证）。

## T2（N01）迁移备份时序：checkpoint + 版本事务前备份

### 问题定位（证据）

- `crates/conex-db/src/migrate.rs:112-145`：备份 `backup_before_drop` 在 `tx.commit()`（:133）**之后**执行（:140-144），且全程未做 WAL checkpoint。
- WAL 模式下已提交未 checkpoint 的数据在主文件之外（`-wal` 文件），`std::fs::copy(path)`（migrate.rs:35）拷贝的主文件**不含**未 checkpoint 数据 → 备份内容取决于 autocheckpoint 偶然时机，可能是迁移前也可能是迁移后数据。
- 现有测试之所以绿：`upgrade_e2e_backup_contains_pre_migration_data`（upgrade_e2e.rs:450-472）与 `backup_file_contains_pre_migration_data`（migrations.rs:640-660）断言 `.bak-v4` 的 user_version=3——恰好因为 v4 提交后的变更还在 WAL 未落主文件，拷贝的主文件碰巧仍是迁移前形态。该断言是「运气锁定」，一旦 SQLite 版本/事务大小改变 autocheckpoint 行为，备份语义即翻转，升级中途失败将无回退保障。

### 方案决策（推荐）

每版本迁移**事务开始前**完成备份，顺序确定化为：

```
for version in (start+1)..=LATEST:
    if version != 5 && version != 6:      # v5/v6 纯 ADD COLUMN 无 DROP，维持跳过
        PRAGMA wal_checkpoint(TRUNCATE)   # 主文件 = 完整旧库态（TRUNCATE 后 WAL 清空）
        backup_before_drop(path, version) # 拷贝主文件（无需再拷 -wal）
    tx = conn.transaction()
    migrate_vX(&tx) -> commit -> PRAGMA user_version = version
```

- checkpoint 在**本版本事务前**执行：此时库内是「上一版本提交后的完整旧库」，`.bak-vN` 确定性 = vN-1 形态（user_version = N-1）；
- checkpoint 失败处理：与 N02（备份失败静默降级，migrate.rs:35-37 仅 eprintln）同点联动，建议一并改为「checkpoint 或备份失败 → 中止迁移（或至少写入 session_meta 可观测键）」。任务边界声明：本任务只保证时序与 WAL 一致性；N02 的失败传播若一并修（同函数同批次），改动面仍是 migrate.rs 单文件。
- 全新库路径（无 sessions 表建 v1，migrate.rs:98-103）与「current==0 但已有旧表按 v1 起点」路径不受影响（从 v2 步骤起走新时序）。

### 涉及文件与改动点

- `crates/conex-db/src/migrate.rs`：
  1. `migrate()` 循环重排（:112-145）：把备份块（:140-144）移到版本事务（:113）创建之前；
  2. 循环内新增 `PRAGMA wal_checkpoint(TRUNCATE)`（失败按备份失败处理，联动 N02）；
  3. `backup_before_drop`（:26-58）保持拷贝主文件逻辑，签名可携带 checkpoint/备份失败传播语义；
  4. 模块头注释（:1-4、:62-64）同步更新「commit 后备份」→「事务前 checkpoint+备份」语义。

### 风险

- 备份内容语义变化：`.bak-v2/.bak-v3` 现在确定性包含「该版本迁移前」数据（当前实现因 WAL 偶然也是该形态，行为不变，但语义从偶然变确定）——需黄金对比测试锁定，防止未来误改；
- checkpoint 时若存在第二连接（备份/迁移工具或测试开第二个连接），可能返回 busy——单连接互斥持有 conn 锁的现状下风险低，登记为已知边界；
- 磁盘占用与拷贝耗时仍在事务外（与现状一致），无锁窗口变化；Windows 下 SQLite 打开态主文件可被 copy（共享读），无文件占用问题。

### 验收标准

1. 任意 `.bak-vN` 的 `user_version` 恒等于 N-1（确定性，与 autocheckpoint 无关）；
2. 备份文件与「迁移前显式 checkpoint 后」的主文件**字节一致**（黄金对比）；
3. 备份先于本版本事务 commit（时序断言）；
4. 迁移中途失败时备份可用（回滚语义成立：用 `.bak-v4` 重开仍为 v3 形态可继续升级）。

### 测试锚点

- 既有测试回归（断言不变、改为确定性通过）：`upgrade_e2e_backup_contains_pre_migration_data`（upgrade_e2e.rs:450）、`backup_file_contains_pre_migration_data`（migrations.rs:640）、`upgrade_e2e_second_open_idempotent_no_backup_stacking`（upgrade_e2e.rs:424）、`second_open_idempotent_no_extra_backups`（migrations.rs:615）、`fresh_db_full_chain_reaches_v4`（migrations.rs:663）；
- 新增黄金对比：迁移前另开连接执行 checkpoint 后读取主文件字节 → 迁移完成 → `.bak-v4` 字节一致；
- 新增统一断言：`backup_files` 中每个 `.bak-vN` 打开后 `PRAGMA user_version == N-1`；
- 回归门禁：`cargo test -p conex-db`（migrate 域全部用例）。

## T3（N05/N24）session_agents 全量覆写竞态：单行定点 API

### 问题定位（证据）

三处「load → 全量 save（DELETE+INSERT）」快照覆写面，无版本号/期望值校验（TOCTOU）：

| 面 | 位置 | 场景 |
| :--- | :--- | :--- |
| kill_all | `crates/orchestrator/src/lifecycle.rs:209-218`（load_session_agents → 改 status/ended_at → save_session_agents） | kill 期间引擎并发 spawn 的新行被整批删除 |
| set_subagent_path | `crates/orchestrator/src/recovery.rs:674-696` | fork 后回写路径期间并发 spawn 行丢失 |
| spawn 落库 | `apps/agent-workbench/src-tauri/src/subagent_spawner.rs:302-307`（load → push → save_session_agents） | 与 kill_all/recovery 的 load 相互覆盖 |

根因在 `crates/conex-db/src/agents.rs:154-238`：`save_session_agents` 事务内 `DELETE WHERE session_id=?` 后全量重插（FK 级联连带清空 session_agent_messages），无并发保护；消息 seq 还按 Vec 下标重编号（agents.rs:205-206，N11 同面，顺带缓解）。两个 kill_all/recovery 调用点与 spawn 调用点互相构成「后写者覆盖先写者新增行」的竞态。

### 方案决策（推荐：结构性单行写面）

conex-db `agents.rs` 新增三个单行 API：

1. `update_session_agent_status(&self, session_id, subagent_run_id, status: &str, ended_at: Option<i64>)`——`UPDATE session_agents SET status, ended_at WHERE session_id=? AND subagent_run_id=?`，只动目标行（kill_all 用；不动 messages/其它行，天然满足「只改 status/ended_at，产出保留」语义）；
2. `update_session_agent_path(&self, session_id, subagent_run_id, path_json: &str)`——set_subagent_path 用；
3. `upsert_session_agent(&self, row: &SessionAgent)`——spawn 落库用（单行 INSERT OR REPLACE，含 v6 三列，不动其它行/messages）。

三个调用点迁移：

- `lifecycle.rs:209-218`：kill_all 改为逐目标 run_id 调 `update_session_agent_status`（不再 load 全量）；
- `recovery.rs:674-696`：`set_subagent_path` 改为单行 `update_session_agent_path`；
- `subagent_spawner.rs:302-307`：spawn 改为 `upsert_session_agent`（不再 load+push+save）。

`save_session_agents` 全量保存**保留**给前端快照写入面（`session_commands.rs:238-247`，`save_session_agents` 命令）与测试面——文档化「全量快照语义：仅用于 UI 显式保存/导入，引擎侧并发写一律走单行 API」。

**备选**：`updated_at` 乐观锁（全量保存带期望值，不匹配即失败/重试）——改动面覆盖所有调用点语义，成本高，列为可选演进（与前端保存面残余竞态一并收口时再评估）。

### 涉及文件与改动点

1. `crates/conex-db/src/agents.rs`：新增三个单行 API（复用 `map_agent_row` 字段集；`upsert_session_agent` 需完整 17 列 INSERT OR REPLACE）；模块头注释更新「全量保存仅快照面」；
2. `crates/orchestrator/src/lifecycle.rs:166-223`（kill_all 写面替换，查询面 `load_session_agents_by_parent_status` 不变）；
3. `crates/orchestrator/src/recovery.rs:674-696`；
4. `apps/agent-workbench/src-tauri/src/subagent_spawner.rs:292-307`（含 :380-395 失败兜底写面核对）；
5. `crates/conex-db/src/lib.rs` 公开导出（若新 API 需跨 crate 可见——已 pub 面扩展）。

### 风险

- `upsert_session_agent` 与 `save_session_agents` 的字段集合必须一致（v6 三列 task_type/display_label/allowed_write_paths_json 随行，row_for 已生成，需保持）；
- 残余竞态面：前端 `save_session_agents` 命令（用户操作触发的全量保存）与引擎 spawn 并发时仍可能覆盖新行——登记为文档化残余 + 后续乐观锁候选（不建议本轮扩展范围）；
- kill_all 的「非目标行」语义变化：单行 UPDATE 下非目标行（含其 messages）天然不动，比全量重写更符合「只改目标」的意图，但需确认无调用方依赖「全量重写顺带修正其他脏行」的隐含行为；
- 并发方向安全性：单行 API 两两交错不会互相覆盖（不同行不同 key），竞态从「互相覆盖」收敛为「同属性最后写赢」——可接受。

### 验收标准

1. kill_all 只更新目标行的 status/ended_at，非目标行及其 messages 字节原样；
2. spawn 落库为单行 upsert，不触碰既有行（含 v6 三列）；
3. 交错场景不丢行：kill_all 与 spawn 并发（串行化模拟：先 kill 后 spawn、先 spawn 后 kill、kill 中 spawn）后行数 = 两方行数之和；
4. set_subagent_path 只更新路径列；
5. 既有 kill_all 测试面全部回归。

## T4（N19）restore Completing 漏判：补入 in-flight 打断语义

### 问题定位（证据）

- `crates/orchestrator/src/restore.rs:668-677`：`is_inflight` 只含 Queued/Initializing/Running/AwaitingApproval/Cancelling 五态，**不含 Completing**（收口中、finalize 前）；
- 恢复循环（restore.rs:540-549）对 completing 的 run 既不打断（非 in-flight）也不收口（无 run 实例可继续 finalize）→ 重启后该 run 永久卡 completing；
- `crates/orchestrator/tests/crash_consistency.rs:122-194` 覆盖五态 in-flight + 终态保真，**无 completing 用例**。

### 方案决策（推荐）

`is_inflight` 增加 `RunStatus::Completing` → 恢复时打断为 failed（`INTERRUPTED_ERROR`，`previousStatus="completing"` 审计字段落库）。

理由：Completing 语义是「收口中、finalize 前」（AgentStop/MaxTurns/GoalComplete 已触发），其 run 实例已随进程死亡，与 queued/running 同属「本可继续推进的中间态」，打断语义与五态一致（05 §2.8 orchestrator.test.ts:404）；「重放 finalize 完成收口」不可行——finalize 依赖内存 run 实例与事件驱动，重启后无实例可重放，且打断为 failed 与「running 的自然结局也可能是 completed 但仍打断」的既有契约自洽。恢复旁路 `SnapshotRun::to_stored_run` 对 "completing" 字面量解析已支持（restore.rs:213-215 走 from_str），无需改快照面。

**备选（已否决，登记理由）**：恢复时对 completing 完成收口（重放 finalize）——无 run 实例可重放、finalize 语义依赖内存态，不成立。

### 涉及文件与改动点

- `crates/orchestrator/src/restore.rs`：`is_inflight`（:668-677）增加 Completing；恢复循环映射（:545-549）不变（Completing 走 `_ =>` 默认臂 → failed + INTERRUPTED_ERROR）；
- 模块头文档（:5-16）「in-flight run（queued / initializing / running / awaiting-approval / cancelling）」列表补 completing。

### 风险

- 语义分歧点：Completing 的「自然结局」是 completed，打断为 failed 是否「冤枉」该 run——与 running 打断同理（running 自然结局也可能 completed），契约一致，风险可控；若未来实现「崩溃续跑」（ADR 持久化方案已登记演进选项），本打断语义需随续跑机制重审——文档登记该联动；
- 前端/审计消费方若对 previousStatus="completing" 有特判，需核对（审计 payload 为 JSON 字符串字段，无枚举约束，风险低）。

### 验收标准

1. completing run 恢复后 status=failed、end_reason=daemon-restarted、审计事件 previousStatus="completing"；
2. 不再产生「永久卡 completing」状态；
3. 既有五态 + 终态保真用例不回归。

### 测试锚点

- `restore.rs:780-880 restore_marks_in_flight_runs_interrupted_with_previous_status`：六态列表加入 completing（prev 列表补 "completing"，审计计数 5→6，interrupted.len 断言同步）；
- `crash_consistency.rs:122-194 crash_restore_interrupts_in_flight_runs_with_status_mapping`：崩溃时刻六态（加 r_completing），prev 与审计断言同步；
- 快照路径：`snapshot_full_roundtrip` 系测试回归（快照含 completing 字面量解析无需改）；
- 回归门禁：`cargo test -p orchestrator`（restore + crash_consistency）。

## T5（N12）flow parallel 字段：实现同级串行约束（或冻结契约）

### 问题定位（证据）

- `FlowNode.parallel`（`crates/orchestrator/src/flow_graph.rs:102-104`）声明语义「false = 与同级串行，声明序为串行顺序」；
- `is_ready`（flow_graph.rs:1459-1471）只按 `depends_on` 判定，`advance` 就绪集合（:951-956）也只过滤依赖 → parallel=false 与 parallel=true 行为无差别；
- 全仓引用仅在测试（flow_graph.rs:1702 序列化往返）与文档；N30/A-02 已确认生产零调用点（declare_flow/load/reset_flow/on_subagent_terminal 均未接线），风险面当前只在测试域，随接线战役（A-02）开启才兑现。

### 方案决策（推荐：实现串行约束）

**语义定义（须主 Agent/评审确认后冻结）**：同级 = `depends_on` 集合相同的节点（同一波次同时就绪）；`parallel=false` 的节点须等待「同 depends_on 集合、声明序在前、且同样 parallel=false」的节点全部进入终态（Completed；前置失败放宽按该节点生效策略 Skip/Report 视为满足）后才就绪。parallel=true 节点不受此约束（显式声明并发）。

**实现位置**：

- `is_ready`（flow_graph.rs:1459-1471）增加同级串行检查：遍历 `graph.nodes()`（声明序），对同 depends_on 集合、声明序在前、parallel=false 的前置同级节点，其状态非终态（按生效策略放宽）即返回 false；
- `advance`（:930-1122）无需结构性改动：就绪集合每轮重算 + 终态事件驱动重推进（`on_subagent_terminal` → advance），满足「前一同级完成后第二节点才启动」的事件驱动语义，不轮询、不死锁（预算不足只延迟，终态事件必再评估）；
- 声明序来源：`graph.nodes()` 即声明序（declare_flow 自 declaration.tasks 构建）；
- FlowNode 文档注释（:101-104）补充「同级 = 同 depends_on 集合」的精确语义。

**备选（契约冻结）**：删除 parallel 字段或文档冻结「parallel 恒并行」——若评审认为串行消费方不存在。推荐实现：契约字段已对前端暴露（session_commands flow 读取面 + 前端声明 UI），静默失效是契约缺陷，删字段会让前端声明能力倒退。

### 涉及文件与改动点

- `crates/orchestrator/src/flow_graph.rs`：
  1. `is_ready`（:1459-1471）加同级串行检查（新增私有 helper，如 `serial_predecessor_pending(node)`）；
  2. `FlowNode.parallel` 文档注释（:101-104）语义精确化；
  3. 模块头（:49）「after / parallel 声明」行为描述与实现对齐；
- 测试：`crates/orchestrator/tests/flow_scheduler.rs`（RecordingSpawner 断言 spawn 时序）+ flow_graph.rs 测试域。

### 风险

- 「同级」定义歧义是主要风险：同 depends_on 集合（同波次）vs 同层（最长路径深度）——本方案冻结为前者（更贴近「与同级串行」的字面语义且实现简单）；若产品语义期望按层串行，改动点收敛在 is_ready 的同类判定，方案预留说明；
- 与 Block 传播交叠：前置 Blocked 节点被传播为 Blocked（终态），不再参与就绪判定，不影响串行检查（串行检查只等「同波次并行声明」节点，不含依赖关系）；
- 排期联动：生产无调用点（N30）时修复成本最低，建议接线战役（A-02）前完成实现与测试锚定；接线时按 N12-N18 逐条核对（A3 §6）；
- 复杂度：同波次判定 O(同波次数²) 量级，任务数 >20 才建独立表（Q3 裁决），当前规模无性能风险。

### 验收标准

1. 同波次两个 parallel=false 节点按声明序串行启动：前一个 Completed（终态事件到达）后，第二个才从 Pending → Running；
2. parallel=true 的同级节点并发不受影响（同一波次可同时 Running）；
3. 不同波次（depends_on 不同）节点不受 parallel 字段影响；
4. 声明序列化往返（wire 格式）不回归；
5. 预算不足时串行约束不引入死锁（事件驱动语义保持）。

### 测试锚点

- `crates/orchestrator/tests/flow_scheduler.rs` 新增：声明两个同波次 parallel=false 节点 → 断言第一个 spawn 后第二个仍未 spawn（Pending）→ 注入第一个 Completed 终态事件 → 断言第二个 Running（RecordingSpawner 记录时序）；
- flow_graph.rs 测试域新增 is_ready 单测（同波次/异波次/parallel=true 三种形态）；

- 回归门禁：`cargo test -p orchestrator flow`（flow_scheduler / multi_agent / crash_consistency 涉及 flow 面用例）。

## T6（M5）幂等 record 失败：内存键与 store 一致性

### 问题定位（证据）

- `crates/agent-tools/src/idempotency.rs:219-238`：`record` 先写内存键（:227-233）再 `store.append_key`（:234-236），store 失败返回 Err → `execute_with_output_policy`（`executor.rs:117-122`）整调用 Err——**但工具已实际执行成功**；
- 后果链：用户重试 → `check` 命中内存键 → 返回 deduplicated「已执行跳过」（假成功），而 store 永无记录；进程重启后键丢失 → 写类工具重新执行（重复副作用）。内存态与持久化态分叉且无提示。
- 注释契约（idempotency.rs:215-218「追加失败返回错误（内存键已写入，上层可决定是否视为不可恢复）」）把「内存已写」当作既定行为——正是缺陷本身。
- 现状边界：生产接线 `ToolIdempotencyGuard::new()` 纯内存（session-loop/loop/mod.rs:446-447），store 钩子仅测试面（idempotency.rs:584-619 FakeStore、executor.rs:579-606 FakeStore）——缺陷当前不触发，属于「接入持久化 store 即兑现」的潜伏面。

### 方案决策（推荐：store 先写 + 失败不写内存）

1. `record` 顺序改为：先 `store.append_key`（幂等契约已声明，重复写不报错，idempotency.rs:35-36），**成功后**再写内存键；store 失败 → 不写内存、直接返回 Err——内存与 store 保持一致（均无该键）→ 重试走执行路径重新执行，不再假去重；
2. 错误文案区分：record 失败返回的 ToolError 携带「工具已执行，但幂等记录持久化失败」语义（可含 key/domain），上层可见并决策（执行器当前直接上抛，与工具失败同路径）；
3. 内存写失败（锁中毒恢复路径，idempotency.rs:117-120）→ 返回 Err，但 store 已落盘 → 下次 check 懒加载（ensure_loaded，:260-291）收敛，无分叉；
4. 无 store（`ToolIdempotencyGuard::new()` 内存版）行为不变（顺序与现状等价）；
5. 可选增强（本轮不引入，登记）：per-key persisted 标记使 check 对「未确认持久化」的键穿透——store 先写后该需求自然消失，无需引入。

### 涉及文件与改动点

1. `crates/agent-tools/src/idempotency.rs`：`record`（:219-238）顺序调整 + 失败路径清理；模块注释与 trait 文档（:10-12、:25-37）更新「先写 store 后写内存」契约；
2. `crates/agent-tools/src/executor.rs`：`execute_with_output_policy`（:117-122）错误传播不变，错误文案/注释对齐「已执行但持久化失败」语义。

### 风险

- store 先写后、内存写前崩溃 → store 有键、内存无 → 重启懒加载恢复 → 去重生效（正确方向：不产生重复副作用）；
- `append_key` 幂等契约是方案前提：若未来接入的 store 实现不幂等（重复写报错），record 需容忍「已存在」——登记为接入面约束（trait 文档已声明幂等，接入时核对）；
- 行为变化：store 失败场景从「假成功」变「报错 + 重试重执行」——更诚实，但调用方需感知错误（与工具失败同路径上抛，可接受）；
- 本轮收益窗口有限（生产未接 store）——如实登记：修复是「为跨进程/持久化接线铺路」的正确性预备，防止接入时把缺陷带进生产。

### 验收标准

1. store 失败时内存键不残留：同进程重试重新执行（返回执行结果，非 deduplicated）；
2. store 成功后内存与 store 一致：新守卫（模拟重启）懒加载后同参去重；
3. record 失败的错误文案含「已执行但持久化失败」信息；
4. 无 store 内存版行为不变（既有去重/清除测试全绿）。

### 测试锚点

- idempotency.rs 新增：FakeStore 故障注入（append_key 返回 Err）→ record 返回 Err → 同参 check 返回 Execute（键未残留）；恢复后 record 成功 → 新守卫去重生效；
- executor.rs:608-636 `execution_result_persisted_via_store` 扩展故障注入分支（首次 append 失败 → 重试执行而非去重）；
- 既有回归：`failed_execution_returns_error_and_is_not_recorded`（executor.rs:432-448）、`record_persists_via_store_and_reloads_in_new_guard`（idempotency.rs:622-637）；
- 回归门禁：`cargo test -p agent-tools`。
