# 子代理权限传递层调研

> 定位：`docs/feature-gap-analysis/` 下的专项调研文档，为「子代理权限设计」这一用户决策提供现状证据与方案落地。
>
> **用户决策**：子代理的只读/权限相关设定**不要太细**——主 agent 逐项配置反而搞不清楚、考虑不全面子代理就挂了；改为「系统默认权限集（安全、够用、由系统给）+ 权限申请传递层（子代理实在有需要 → 向主 agent 申请 → 主 agent 审批后放行）」。
>
> **结论摘要**：
> 1. 现状审批链完整但**裁决者只有用户**：`PermissionVerdict::NeedsApproval` → `ApprovalGateImpl.request_approval`（广播 approval-requested + oneshot 等待）→ `core_approve_tool / core_deny_tool`（UI 命令）→ `approval-resolved`。子代理 run 与主 agent run 共用同一套机制，`permission.rs:133-134` 明确「审批人 = 用户，主 Agent 仅转呈」。
> 2. 建议新增**裁决者路由层**：approval-requested 携带 `requester`（子代理 run id + 理由）→ 引擎按「来源」把请求默认路由给**主 agent 裁决**（而不是 UI 用户）→ 主 agent 放行/拒绝/转用户 → 裁决经 approval-resolved 回到子代理执行器。机制完全复用现有 gate，只改「谁裁决」。
> 3. REQ-D04 的 9 项参数收敛为 5 项：保留 `task_type`（六枚举，默认权限映射由系统给）、`allowed_write_paths`（硬沙箱有价值）；去掉 `enable_write_tools / enable_command_tools / enable_mcp_tools / allowed_read_paths`（由 task_type 派生或默认继承），需要的更高权限走申请通道。
> 4. 权限申请的先例已存在：`explore_quota.rs` 的「配额凭证 + 拒绝时回报主 agent」正是「子代理无权自我授予、由主 agent 分配」的同一模式。

---

## 1. 现状机制调查

### 1.1 权限判定三态引擎（agent-tools）

`crates/agent-tools/src/permission.rs` 是权限判定的唯一纯函数出口：

| 要素 | 位置 | 说明 |
| :--- | :--- | :--- |
| `PermissionMode` 三态 | `permission.rs:19-27` | `Ask`（需确认）/ `FullAccess`（全放行）/ `Plan`（只读拒绝写类） |
| `PermissionVerdict` 三态 | `permission.rs:57-64` | `Allow` / `Deny` / `NeedsApproval` |
| `decide` 判定矩阵 | `permission.rs:78-87` | dangerous/requires_approval 按模式三态判定 |
| 红线先行 | `permission.rs:96-122` | `decide_with_redline` / `decide_command`：红线在任何模式（含 full-access）一律 `Deny`，不经矩阵 |
| C3 回退护栏 | `permission.rs:135-151` | `decide_command_with_revert`：大面积 git 回退 → `NeedsApproval`，full-access 不豁免 |

关键既有语义（本方案必须保持）：**红线不可豁免**（`permission.rs:94`）、**plan 模式写类直接拒绝不弹窗**（`permission.rs:83`）。

**「审批人 = 用户」的现状声明**（本调研要改动的点）：

```rust
// permission.rs:133-134
//! 审批人 = 用户：NeedsApproval 走既有 ApprovalGate 链路等待用户裁决，主
//! Agent 仅转呈，无任何单方面批准路径（ref-analysis 01 B3 防线配套）。
```

### 1.2 审批链：从工具触发到裁决返回

完整的调用链（工具内部触发 → 执行器 → 事件流 → 裁决）：

**（1）工具侧通道**：`crates/agent-tools/src/context.rs:56-75`

```rust
pub trait AskChannel: Send + Sync + std::fmt::Debug {
    async fn ask(&self, tool_name: &str, args: &serde_json::Value)
        -> Result<AskDecision, ToolError>;
}
```

`ToolContext.ask`（`context.rs:106`）是审批回调槽位；`AskCallback`（`context.rs:96`）为 trait 对象引用。`context.rs:100-118` 还承载 `write_claims`（写路径互斥）、`write_claim_holder`（子代理 run id）、`explore_docs_quota`（配额上下文）——**子代理身份已经部分注入 ToolContext**。

**（2）执行器装配**：`crates/session-loop/src/tool_exec.rs:657-669`

```rust
let ask: Option<AskCallback> = match options.permission_mode {
    Some(PermissionMode::FullAccess) => Some(Arc::new(NoopAskChannel)),
    _ => approval.as_ref().map(|gate| { /* ApprovalChannel 装配 */ }),
};
```

判定挂载点：`tool_exec.rs:533-575`（顺序路径）与 `tool_exec.rs:291-322`（并行组）——`call_verdict` 返回 `NeedsApproval` 即发起审批。

**（3）通道实现**：`crates/session-loop/src/approval.rs:97-141`（`ApprovalChannel::ask`）——先记录 `ApprovalRequested` 事件（先发后等防死锁），再 `gate.request_approval` 挂起等待，支持 abort 取消。

**（4）审批门抽象**：`crates/session-loop/src/tool_events.rs:69-77`

```rust
pub trait ApprovalGate: Send + Sync {
    async fn request_approval(&self, call_id: &str, tool_name: &str, args: &Value)
        -> ApprovalDecision;
}
```

裁决枚举：`tool_events.rs:58-65`——`Approved / Denied { reason } / Expired`。

**（5）门的具体实现（workbench 域）**：`apps/agent-workbench/src-tauri/src/core_run_commands.rs:124-148`（`ApprovalGateImpl`）+ `:207-262`（`request_approval`）：

```
1. 构造 PermissionRequest（:216-226）→ 广播 approval-requested（实时预览，sequence=None）
2. 状态机联动 running → awaiting-approval 落库（:234-244）
3. 注册 oneshot 等待通道（:247-255）
4. tokio::time::timeout(APPROVAL_TIMEOUT=120s) 等待裁决（:258-261，超时 → Expired）
```

常量 `APPROVAL_TIMEOUT = 120s`（`core_run_commands.rs:64`）。

**（6）裁决入口（当前只有用户）**：`core_run_commands.rs:1726-1775`

- `core_approve_tool`（`:1726-1749`）：仅接受 `decision == "approved"`；校验 `tool_call_id` 在待审批集合（I-02/PE-12 T12.3：杜绝伪造）→ `resolve` → 落地 `approval-resolved`。
- `core_deny_tool`（`:1753-1775`）：拒绝带 reason。
- `ApprovalGateImpl::resolve`（`:175-203`）：从 pending 集合移除 → oneshot send → 状态机恢复 `awaiting-approval → running`。

**裁决返回链路**：`resolve` → oneshot → `ApprovalChannel.ask` 返回 `AskDecision::Allowed/Denied`（`approval.rs:131-137`）→ 工具执行或拒绝结果（`tool_exec.rs:554-574`：Approved 重试执行 / Denied → `UserDenied` 错误）。

### 1.3 裁决者现状：只有用户，主 agent 不参与

- **事件翻译层**：`crates/session-loop/src/loop/handlers/executing_tools.rs:237-255` 把 `ToolEvent::ApprovalRequested` 翻译为 `AgentEvent::ApprovalRequested`，注释明确「真实 PermissionRequest 由 B4/B6 审批层补齐」。
- **载荷结构**：`crates/conex-types/src/events.rs:184-201` `PermissionRequest`（id / session_id / cwd / tool_call_id / tool_name / parameters / summary / tool_metadata / metadata）。**当前没有「请求方是谁（子代理 run id）」字段**。
- **裁决面**：`core_approve_tool / core_deny_tool` 是 Tauri 命令（`core_run_commands.rs:1725-1753`），即前端 UI 按钮调用。审批卡片的交互对象是**人**。
- **每 run 一个门**：`core_run_commands.rs:1446-1469` 每个 run（含子代理 run）各自装配 `ApprovalGateImpl`；full-access 模式不启用审批（`:1464`）。

**当前流向（调研问题 2 的明确回答）**：

```
子代理工具触发 → 判定 NeedsApproval → ApprovalGateImpl.request_approval
  → broadcast approval-requested → 【裁决者 = UI 用户】← 无其他分支
  → core_approve_tool / core_deny_tool（前端按钮）
  → approval-resolved → oneshot 回子代理执行器
```

- **谁裁决？** 只有 UI 用户。裁决入口是 Tauri 命令（`core_run_commands.rs:1725-1753`），前端审批卡片是唯一消费面；`permission.rs:133-134` 明示「主 Agent 仅转呈，无任何单方面批准路径」。
- **能否转给主 agent？** 现状不能。原因有三：① 请求载荷没有「请求方 = 子代理 run」字段（`events.rs:184-201`）；② 广播目标固定是前端事件桥（`core_run_commands.rs:216-231`），没有「转呈给另一 run」的路由；③ 主 agent run 的对话里没有任何「审批待办」的注入形态（steering/inject 通道 `wait_subagents.rs:388` 只用于任务调整，不承载审批）。
- **注意现状中的"无单方面批准路径"是一条安全基线**：`permission.rs:134` 与 `ref-analysis 01 B3` 的「审批人=用户」防线。本方案**不是**给主 agent 单方面批准权，而是把「用户裁决」扩展为「主 agent 裁决，可转用户」——主 agent 批准子代理申请本身仍是一次显式裁决动作，且可被用户兜底，不破坏该防线。

**结论**：子代理 run 的审批请求与主 agent run 走完全相同的通道，直接广播到 UI。**当前没有「把子代理的审批转呈给主 agent 裁决」的路径**——这正是权限传递层要补的洞。

### 1.4 子代理侧已有先例：配额凭证模式（explore_quota）

`crates/agent-tools/src/explore_quota.rs` 是「子代理权限受控 + 向主 agent 申请」的现成范式，本方案直接对齐它的四件套：

1. **凭证只能由主 agent 在 spawn 时给出**：`explore_quota.rs:9-10`「配额凭证只能由主 agent 在 spawn 时给出（[SubagentSpawnRequest] 的 allow_explore_docs 字段），子代理无权自我授予」——即「子代理不自己决策权限」的既有实现。
2. **拒绝时回报主 agent 指引**：`explore_quota.rs:162-176`——`NotGranted` / `Exhausted` 错误文案都含「请把发现以消息形式回报主 agent」「不要再尝试创建文档」。**这是"申请→被拒→回报"文案的现成模板**。
3. **纯函数判定 + 存储契约分离**：`check_explore_docs_write`（`:192-207`，凭证+配额上限双重判定）与 `ExploreDocsQuotaStore` trait（`:96-106`，agent-tools 只定义契约，引擎侧以 session_meta 实现）。
4. **提示词凭证注入段**：`explore_docs_credential_section`（`:213-221`）——子代理系统提示词里声明自己持有的配额与边界，固定结构可快照断言。

接线模式：`quota_context_for_spawn`（`:232-255`）在 spawn 时装配 `ExploreDocsQuotaContext`，`guard_explore_docs_write`（`:262-276`）在写文档工具执行前拦截。**权限传递层应复用同样的「spawn 时装配 + 工具执行前拦截 + 拒绝文案带回报指引 + 提示词凭证段」四件套结构**。

### 1.5 只读裁剪与提示词注入（现状的"粗"粒度权限）

### 1.7 参考模式（调研问题 4：codex / opencode 的权限演进做法）

| 参考模式 | 做法 | 对本方案的借鉴 |
| :--- | :--- | :--- |
| codex `execpolicy amend` | 审批通过后把规则**追加进策略文件**（amend 既有规则），后续同类调用直接按新规则放行，不再逐次问询 | 主 agent 裁决后可选择「追加规则」（见开放问题 6.3）；**第一版只做本次放行**，追加规则留会话级临时规则，不写全局策略文件 |
| opencode permission `saved` | 权限决策有持久化面：允许/拒绝的选择可保存，重启后仍生效，用户可事后修改 | 启示：**裁决本身是审计数据**（approval-requested/resolved 已落库，`events.rs:457-465`），但「申请→主 agent 裁决」若跨 run 生命周期，需要 6.1 的持久化待办设计 |
| codex 的「子代理/工具权限继承父」语义 | 子代理继承父会话权限设定，父的宽松不会自动传导给子代理 | 支撑 2.1 原则：「子代理的边界不由父会话的 permissionMode 宽容度决定」，full-access 会话里的子代理仍受默认集约束 |
| 通用「最小权限 + 申请」模式 | 默认最小、按需申请、申请带理由、审批留痕 | 本方案整体遵循：默认集 fail-closed（配少不配错）、申请必带理由（2.4）、裁决全留痕（审批事件原样落库） |

**核心取舍**：codex/opencode 的「审批后追加规则」解决的是「高频同类操作烦人」问题；本方案第一版**不追加规则**（安全优先、实现最简），若实测子代理申请频率过高，再按 6.3 引入会话级临时规则。

## 2. 权限申请传递层设计（核心）

### 2.1 设计目标与分层架构

目标三句话：

1. **主 agent 不配也能派**：spawn 子代理时只给 `task_type`（甚至不给），权限由系统默认集自动装配；
2. **子代理不自我授权**：默认集之外的操作一律拦截，走「申请 → 主 agent 裁决」；
3. **复用现有审批机制**：不动 `ApprovalGate` / `ApprovalChannel` / 事件流，只改「裁决者路由」。

分层模型（自上而下）：

```
┌─ 第 3 层：运行中权限申请（PermissionRequest → 主 agent 裁决 → 放行/拒绝）┐
│   子代理实在需要的更高权限（越界写、命令、MCP），带理由申请，不自我决策     │
├─ 第 2 层：主 agent 显式配置（可选覆盖，不是必填）───────────────────────┤
│   定义级覆盖：allowed_write_paths / 工具开关覆盖；默认全 None 不配置        │
├─ 第 1 层：系统默认权限集（task_type 六枚举默认映射，自动给）───────────────┤
│   spawn 时由引擎从 task_type 派生：工具集裁剪 + 写路径沙箱 + 命令策略        │
└─ 第 0 层：安全基线（对一切生效，不可被上层豁免）─────────────────────────┘
   红线命令 Deny（permission.rs:96-107）、C3 大面积回退审批（permission.rs:135-151）
```

**裁决优先级**：安全基线（不可豁免）> 系统默认集 > 主 agent 显式覆盖 > 运行时申请（仅本次调用放行，或由主 agent 明确追加规则）。

**与现状权限模式的关系**：会话级 `permissionMode`（ask/full-access/plan，`permission.rs:19-27`）继续作为**子代理 run 的会话底色**；默认集在 `permissionMode` 之上叠加（例如会话是 full-access 时，子代理默认集仍然生效——**子代理的边界不由父会话的宽容度决定**，这是权限传递层的独立价值）。

### 2.2 默认权限集（6 种 task_type 各一套"够用"默认）

在 REQ-D04 §4.2 默认映射表（`REQ-agent-engine-capabilities.md:480-491`）基础上收敛。**默认值由系统硬编码，主 agent 不用配、也不必知道细节**；文档只向主 agent 说明每个 task_type 一句话边界：

| task_type | 一句话边界（给主 agent 看） | 系统默认实现（子代理 run 装配） |
| :--- | :--- | :--- |
| `analysis` | 只读调研，不产生任何改动 | 工具集 = 只读白名单（复用 `readonly.rs:27-34`）；无命令；无写 |
| `design` | 只读 + 可在方案文档目录产出一份设计文档 | 只读白名单 + 仅 `write_file`（配额凭证式，对齐 `explore_quota.rs` 模式，默认 granted=true quota=1）；无命令 |
| `review` | 只读 + 可在评审报告目录产出一份报告 | 同 design（报告目录 = 会话配置的 review 目录，缺省不限制 + 配额 1） |
| `implementation` | 可读写工作区 + 常用构建/测试命令 | 全工具集 + 写路径沙箱 = 工作区根（`workspace_root` 即天然白名单）+ 命令白名单（构建/测试类，不含提权/网络发布类） |
| `organization` | 只读 + 可在指定文档目录整理/编辑文档 | 只读白名单 + 写路径沙箱 = 主 agent 显式给的目录（不配 = 退化为 read-only） |
| `commit` | 仅 git 操作，不碰其他 | 工具集仅 `shell_command` + 命令前缀过滤 git（对齐 T-D-08 的 commit 细化，`03-D方案.md:587`）+ 无写文件工具 |

**设计原则**：
- **粗粒度够用**：implementation 的"命令白名单"不必列命令细节，由系统按内置分类（构建/测试）过滤；写路径沙箱默认就是工作区根，不配置不放开；
- **配少不配错**：organization 不配目录就退化为只读（fail-closed），宁让子代理申请，不默认放开；
- **一次申请一次放行**：运行时申请默认只放行本次调用（不落规则），主 agent 若想追加规则走显式配置面（开放问题 6.3 讨论持久化）。

**默认集装配步骤（spawn 时，引擎侧执行）**：

```
1. 解析 task_type（缺省 = analysis，最安全）→ 查默认集映射表（上表）；
2. 工具集装配：按默认集裁剪注册表（复用 readonly.rs 白名单机制推广出的
   filter_registry，03-D方案.md:584）：
   - analysis/design/review/organization → 只读白名单（readonly.rs:27-34）；
   - implementation → 全工具集 + 写路径策略 = 工作区根（T-D-08 的
     WritePathPolicy::Allowed([workspace_root])）；
   - commit → 仅 shell_command（前缀过滤 git，03-D方案.md:587）；
3. 命令策略：implementation → 语义层命令分类过滤（复用 permission.rs:119-121
   semantics::analyze 的 CommandClass），仅放行构建/测试类；
4. 审批模式：子代理 run 的 permission_mode 独立于父会话设定——
   子代理默认按 ask 语义走申请通道（2.3），父会话 full-access 不传导；
5. 装配申请上下文：PermissionRequestor/ApprovalRequester 注入子代理 run
   的执行上下文（对齐 quota_context_for_spawn，explore_quota.rs:232-255）；
6. 提示词注入：权限边界段 + 申请声明段挂载（4.3）。
```

**"默认值由系统给"的落点**：主 agent 在 spawn 参数里只声明 `task_type`（可选）；上表与装配步骤全部是引擎侧代码（T-D-07 的 `default_permissions` 扩展），**主 agent 不可见也不需要可见**——只在文档/UI 里用一句话边界说明（表格第二列）。

### 2.3 权限申请流程（时序）

子代理工具触发审批 → 默认路由给主 agent → 主 agent 裁决 → 裁决回子代理执行：

```
子代理 run（agent-tools/session-loop）          引擎（workbench 域）                主 agent run
───────────────────────────                  ──────────────────                  ───────────
1. 工具执行，判定 NeedsApproval
   （tool_exec.rs:533-544 / 291-322）
2. ApprovalChannel.ask
   （approval.rs:97-141）
     │
     ▼
3. ApprovalGateImpl.request_approval
   （core_run_commands.rs:207-262）
   PermissionRequest + requester=子代理run id + reason
     │  broadcast approval-requested
     │  （载荷含 requester / reason 字段，新增）
     ▼
4. 裁决者路由（新增层，替换"直发 UI"）
   ┌─ 来源 = 子代理 run → 默认路由给主 agent
   │   → 主 agent 侧收到「权限申请」消息（带工具名+参数摘要+理由）
   │   → 主 agent 裁决：放行 / 拒绝 / 转用户
   └─ 来源 = 主 agent run → 保持现状直发 UI 用户
     │
     ▼
5. 裁决落地：resolve(tool_call_id, Approved/Denied)
   （core_run_commands.rs:175-203 原样复用）
   + approval-resolved 事件（:1777-1811 原样复用）
     │
     ▼
6. ApprovalChannel.ask 返回 Allowed/Denied
   （approval.rs:131-137）
   → Approved：重试执行工具（tool_exec.rs:554-561）
   → Denied：UserDenied 结果 + 结构化文案（含"如需更高权限，向主 agent 申请"指引）
```

**关键点：第 4 步是唯一的改动面**。第 3、5、6 步全部复用既有机制；`ApprovalGateImpl` 的 oneshot 等待天然支持「审批者换成主 agent」（主 agent 裁决动作 = 调用同一 `resolve`）。

**裁决者路由实现建议**：

```rust
/// 审批请求来源（挂在 PermissionRequest.metadata，或扩展 PermissionRequest 字段）
pub enum ApprovalSource {
    /// 主 agent run（保持现状：裁决者 = UI 用户）
    MainAgent,
    /// 子代理 run（新：裁决者默认 = 主 agent；主 agent 可转用户）
    Subagent { run_id: String, task_type: Option<String> },
}

/// 裁决者路由（引擎侧新增纯函数，替换 ApprovalGateImpl.request_approval 内
/// 「无条件广播给 UI」的分支）
pub fn route_approval(source: &ApprovalSource) -> Arbiter {
    match source {
        ApprovalSource::MainAgent => Arbiter::User,                       // 现状不变
        ApprovalSource::Subagent { .. } => Arbiter::MainAgent,            // 新默认
    }
}
```

## 3. "不要太细"的简化方案（REQ-D04 参数收敛）

### 3.1 问题定位

REQ-D04 的 9 项参数（`REQ-agent-engine-capabilities.md:466-478`）中，**逐项开关类参数是"细"的根源**：

- `enable_write_tools` / `enable_command_tools` / `enable_mcp_tools` 三个 bool 彼此独立，主 agent 要分别想三遍「这个子代理要不要写、要不要命令、要不要 MCP」；
- 但 6 种 task_type（`REQ-agent-engine-capabilities.md:473`）的默认映射（`:480-491`）已经把这组决策固化了——**bool 开关是 task_type 的冗余展开**；
- `allowed_read_paths`（`:476`）：只读限制基本没有安全价值（读不改状态），且子代理只读调研通常需要全工作区（`REQ-D-现状分析.md:291` 现状即无读路径限制）。

### 3.2 参数收敛表

| REQ-D04 参数 | 收敛后 | 理由 / 归属 |
| :--- | :--- | :--- |
| `name` | 保留 | 定义唯一标识（`REQ-agent-engine-capabilities.md:470`） |
| `description` | 保留 | 人读职责描述（`:471`） |
| `system_prompt` | 保留 | 完整系统指令（`:472`） |
| `task_type` | **保留（核心）** | 六枚举；默认权限映射由系统给（T-D-07 的 `default_permissions` 资产直接继承） |
| `enable_write_tools` | **删除** | 由 task_type 派生（implementation/organization/design/review 默认可写，analysis/commit 默认不可写——即 REQ-D04 §4.2 表）；不再单独配置 |
| `enable_command_tools` | **删除** | 由 task_type 派生（仅 implementation/commit 默认开命令）；命令范围由系统白名单定 |
| `enable_mcp_tools` | **删除** | 默认继承父代理 MCP 面；需要单独收紧/放开走权限申请 |
| `allowed_write_paths` | **保留（可选）** | **硬沙箱有价值**：越权拒绝是执行层拦截（`REQ-agent-engine-capabilities.md:492` 验收关键），保留为第 2 层显式覆盖；不配 = 默认集路径（implementation=工作区根） |
| `allowed_read_paths` | **删除** | 无安全增益；默认全工作区可读；确有需要走权限申请 |

**收敛结果：9 项 → 5 项（2 项元数据 + 1 项指令 + 1 项类型 + 1 项路径沙箱）**。显式配置从 8 项权限面减到 1 项（`allowed_write_paths`），主 agent 配置负担从「逐项决策」降到「（可选的）一处路径」。

### 3.3 与既有 T-D-07 / T-D-08 计划的关系

- **保留资产 1（T-D-07）**：`TaskType` 枚举 + `default_permissions` 纯函数（`03-D方案.md:496-506`）——直接继承，并扩展为本调研 2.2 节的六套默认集（增加命令白名单、写路径默认值）；
- **保留资产 2（T-D-08）**：`WritePathPolicy` + `check_write_allowance`（`03-D方案.md:562-574`）——保留，作为第 2 层显式配置面与 implementation 默认工作区沙箱；
- **裁剪部分（T-D-08 第 3 节）**：`enable_command_tools / enable_mcp_tools` 的逐项开关（`03-D方案.md:582-587`）不再作为定义字段落地——命令过滤下沉为 task_type 默认策略（implementation=构建/测试白名单、commit=仅 git），MCP 默认继承父；
- **新增强制项**：本调研新增的「子代理审批路由给主 agent」（2.3-2.5）不在原 T-D-07/08 范围内，需新增任务卡（估计 0.5 任务卡：载荷扩展 + 路由函数 + 广播目标分支 + 测试）。

### 3.4 保留的硬沙箱（第 0 层安全基线不受收敛影响）

收敛只动「配置面」，不动「执行面」：

- 红线命令不可豁免（`permission.rs:96-107`）——全模式 Deny；
- C3 大面积回退审批（`permission.rs:135-151`）——full-access 不豁免；
- 只读裁剪白名单 fail-closed（`readonly.rs:40-48`）——`analysis` 默认集直接复用；
- `allowed_write_paths` 越权拒绝（T-D-08 落地后）——先越权拒绝、再互斥拒绝（`REQ-D-现状分析.md:324`）。

## 4. 与现有 ApprovalGate / 事件流 / 提示词注入的接线点

### 4.1 ApprovalGate 接线（改动最小化）

**方案 A（推荐）：扩展现有 trait 参数，不加新 trait**。

```rust
// tool_events.rs:69-77 扩展（参数全部 Option，向后兼容现有实现）
pub trait ApprovalGate: Send + Sync {
    async fn request_approval(
        &self,
        call_id: &str,
        tool_name: &str,
        args: &Value,
        requester: Option<&ApprovalRequester>,   // 新增：None = 主 agent
    ) -> ApprovalDecision;
}

pub struct ApprovalRequester {
    pub run_id: String,        // 子代理 run id
    pub task_type: Option<String>,
    pub reason: Option<String>,
}
```

理由：
- `ApprovalGateImpl`（`core_run_commands.rs:207-262`）是唯一生产实现（另有 MockGate 测试实现，`approval.rs:151-167`），扩展签名波及面小；
- 请求方身份在 `ToolExecCtx`（`tool_exec.rs:66-77`，已有 `run_id`）可拿；子代理 run 的 `run_id` 即 `subagent_run_id`（`subagent.rs:341`），**父 run 关系**引擎侧已有（`subagent_events.rs:41-48` 的 `SubagentEmitContext.parent_run_id`），可直接复用判定"本 run 是谁 spawn 的"；
- 子代理理由由提示词协议保证（4.3 注入段），执行器原样透传，不做语义解析。

**方案 B：新增 `PermissionRequestor` trait 装进 ToolContext**（2.4 的完整形态）。适合未来需要「申请 ≠ 审批」独立语义（如批量申请、预授权）时再升级，**本轮不采纳**（避免重复机制）。

### 4.2 事件流接线

- **出站**：`ApprovalGateImpl::request_approval` 构造 `PermissionRequest`（`core_run_commands.rs:216-226`）时填充新字段：`requester_run_id = ApprovalRequester.run_id`、`reason = ...`；广播目标按 2.3 路由分支——子代理来源转呈主 agent 裁决面（事件仍照发，前端可观测）；
- **入站**：主 agent 裁决动作复用 `core_approve_tool / core_deny_tool`（`core_run_commands.rs:1726-1775`），**新增第 3 个决策 `escalate`（转用户）**；`emit_approval_resolved`（`:1777-1811`）不变；
- **持久化**：approval-requested 已落库（`events.rs` 注册表 Critical 级，`subagent_events.rs:15-19` 同类先例）；新字段随载荷落库，无 schema 变更（jsonb 载荷）；
- **背压**：审批事件 Critical 必达（`events.rs:168-169`），子代理审批转呈不改变此级别。

### 4.3 提示词注入接线

- **权限申请声明段**：仿 `subagent_inject.rs:151-168`（`subagent_session_injections` 返回段列表，挂载方逐项 `ContextInjector::push`），新增一段 `permission_relay_section(task_type, 边界一句话)`，在引擎 spawn 子代理 run 时经 `CONTEXT_INJECTION_ORDER`（`engine.rs:1097-1101`）挂载；
- **默认权限边界告知**：段内声明「你的默认权限按任务类型自动配置（<task_type 一句话边界>）」，让子代理知道哪些操作会触发申请；
- **凭证段复用先例**：`explore_docs_credential_section`（`explore_quota.rs:213-221`）已是「提示词里声明权限边界」的规范样板，本段对齐其固定结构、可快照断言；
- **steering 补充**：子代理被拒后的"回报主 agent"走 `SubagentEventEmitter::emit_event`（`subagent_events.rs:196-205`，Message 类）+ 主 agent 侧 `wait_subagents.inject`（`wait_subagents.rs:388`）回传调整意见。

### 4.4 子代理 run 的工具上下文装配（M2 执行上下文）

- `ToolContext` 已有子代理身份字段：`write_claim_holder`（子代理 run id，`context.rs:113-114`）、`explore_docs_quota`（`context.rs:117-138`）——**装配点先例完整**，新增 `permission_request`（如选方案 B）或 run 级 `ApprovalRequester` 注入方式与 `quota_context_for_spawn`（`explore_quota.rs:232-255`）对齐；

## 5. 测试锚点

| 锚点 | 场景 | 断言 |
| :--- | :--- | :--- |
| 路由纯函数 | `route_approval` 分类 | MainAgent→User；Subagent→MainAgent；子代理 run 无父 run 时兜底 User（数据异常不静默） |

| 主 agent 链路不回归 | 主 agent run 内工具审批 | requester=None → 路由 User → 既有 UI 审批流程全绿（兼容性回归） |
| 转用户链路 | 主 agent 裁决 EscalateToUser | 请求转 UI，用户裁决后按既有 resolve 路径返回 |
| 超时 | 主 agent 不裁决 | Expired → 子代理 run 不中断、工具返回 approval_expired（`approval.rs:253-264` 先例） |
| 默认权限集 | 六 task_type 各装配断言 | analysis 无写工具无命令；implementation 全工具集 + 工作区沙箱；commit 仅 git 命令；design/review 写配额=1（对齐 `explore_quota.rs` 测试面） |
| 参数收敛 | T-D-07 验收扩展（`03-D方案.md:537-539`） | `default_permissions` 六映射 + 定义字段覆盖合并语义；enable_* 字段不存在于定义契约 |

测试域：`crates/agent-tools`（纯函数、默认集、文案）+ `crates/session-loop`（链路，MockGate）+ workbench（路由与命令，Mock 主 agent 裁决器注入 `core_run_commands` 命令面）。

## 6. 开放问题

### 6.1 权限申请的持久化

- 现状：审批请求/裁决均落库（approval-requested / approval-resolved，`events.rs:457-465`；`core_run_commands.rs:1777-1811`），但**待审批集合在内存**（`ApprovalGateImpl.pending`，`core_run_commands.rs:141`），重启后 oneshot 丢失 → Expired。
- 问题：主 agent 裁决链路由到「另一个 run」，若主 agent run 恰好结束/重启，子代理的申请会悬挂到 120s 超时。是否需要把「子代理→主 agent 的申请」做成持久化待办（session_meta 或 events 表），主 agent 恢复后仍可裁决？
- 倾向：第一版不做持久化（超时兜底 + 子代理回报机制已可闭环），记 P2；但路由层要预留「裁决方不在线 → 转用户兜底」的分支。

### 6.2 审批超时

- 现状单一常量 `APPROVAL_TIMEOUT = 120s`（`core_run_commands.rs:64`）。
- 问题：子代理链路主 agent 需要思考时间，120s 可能不够；主 agent 也可能挂起（等子代理回报时形成环）。建议子代理链路超时可配（spawn 参数或 task_type 默认），并明确**超时后子代理收到 Expired + 指引**（可回报主 agent 说明超时）。

### 6.3 放行是否追加规则（对齐 codex execpolicy amend / opencode permission saved）

- 参考模式：codex 的 `execpolicy amend` 允许审批通过后把该规则**持久化进策略**（下次同类调用不再问）；opencode 的 permission 有 saved 持久化面。
- 问题：主 agent 放行后，是「仅本次」还是「追加为默认集内的临时规则」？建议：**默认仅本次**（安全），主 agent 可在裁决时显式勾选「同类调用本次会话不再问」（会话级，不落全局）；全局规则留给显式配置面。这一决策影响 `ApprovalGate` 是否需要「规则注册」返回通道。

### 6.4 循环依赖与死锁风险

- 主 agent 裁决子代理申请时，主 agent run 本身可能在等待子代理终态（`wait_subagents`，`wait_subagents.rs`）；子代理申请挂起 → 主 agent 无法推进 → 死锁（直到 120s 超时）。
- 缓解：① 超时兜底（6.2）；② 路由层检测「子代理申请的裁决者 run 正在 wait 该子代理」时直接转用户或自动拒绝+提示；③ 提示词指引子代理「大额申请先回报沟通，不要边做边申请」。
- 需在实现前做一次时序评审（对齐 `tool_exec.rs:29-33` 的「审批优先于中间件」决策记录风格）。

### 6.5 默认权限集的命令白名单口径

- implementation 的「构建/测试类命令」如何判定？语义层已有命令分类（`permission.rs:119-121` 的 `semantics::analyze`，`CommandClass`），建议复用其分类而非维护命令前缀表；commit 的「仅 git」用前缀过滤（`03-D方案.md:587` 既有约定）。两类口径不统一，需评审统一。

### 6.6 与 flow 调度（DAG）的交互

- DAG 调度的子代理（`flow_graph.rs` 综合节点/流程节点）同样走本链路；主 agent 是 planner_run（`flow_graph.rs:347-348` 的 planner_run_id）。申请路由的「主 agent」需明确 = 该子代理的父 run（`SubagentEmitContext.parent_run_id`，`subagent_events.rs:41-48`），而非会话内任意 run。
