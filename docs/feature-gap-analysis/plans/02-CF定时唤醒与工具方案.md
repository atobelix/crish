### 1.2 核心冲突（本方案要拆解的四个结构性矛盾）

**冲突一：事件驱动底座就绪、时间驱动为零。**

31 种域事件、背压三级、L0-L3 控制总线、DAG 合成唤醒、恢复阶梯通知全部在库（`crates/conex-types/src/events.rs:285-604`、`crates/session-loop/src/control.rs:32-59`、`crates/orchestrator/src/flow_graph.rs:918-1090`），但"时间"这一维度的唤醒源在 Rust 内核零实现：`rg "cron|Cron|timer|Timer" crates/` 全部命中集中在 wait_subagents.rs 的等待模式（`REQ-CF-现状分析.md` 附录 A.2）。修复方向不是重造事件系统，而是在既有事件面上生长两个新事件源（定时器到期、Cron 触发），复用现成的注入通道。

**冲突二：wait_subagents 三模式契约齐备、通道零接线。**

`SubagentWaitChannel` trait 四方法（persist_declaration / snapshot / wait_for_terminal / inject）已冻结（`crates/agent-tools/src/tools/wait_subagents.rs:366-389`），但 `BuiltinToolConfig.subagent_wait_channel` 默认 None（`crates/agent-tools/src/tools/mod.rs:54-57`、:68），生产装配 `EngineHandle::new` 用默认配置注册（`apps/agent-workbench/src-tauri/src/engine.rs:617`），三模式等待在生产环境整体返回 `common.unsupported`（wait_subagents.rs:533-538）。修复方向是引擎侧实现通道并注入，契约不动。

**冲突三：前端定时任务面板是连不到引擎的死 UI。**

`ScheduledTasksPanel` 面板完整（`apps/crish-desktop/src/components/settings/ScheduledTasksPanel.tsx:31-206`），cron 校验器完整存在但显式拒绝下发（`apps/crish-desktop/src/api/workflow-api/workflowScheduler.ts:301-312`"引擎暂不支持 cron 调度"），`workflowRunner.ts` 模块文档明确声明 Tauri 下 workflow 命令全部为幽灵命令（`apps/crish-desktop/src/api/workflow-api/workflowRunner.ts:4-7`、:27-87 恒 `ok:false`）。修复方向是 Rust 侧实装调度能力 + Tauri 命令面补齐 + 前端桥真实 IPC，前端面板与校验器原样保留。

**冲突四：read_file 截断在字符边界，可能切断行中间——防截断核心机制整体缺失。**

现状 `clamp_text` 按字符数截断（`crates/agent-tools/src/tools/mod.rs:384-390` 的 `text.chars().take(limit)`），无行号范围、无行边界保证、无续读偏移、二进制直接报错拒绝（`crates/agent-tools/src/tools/fs.rs:86-91`）。这正是 REQ-F02（🔑 重点需求）要解决的"AI 读到一半被截断导致误判"痛点。修复方向是"行优先"重写 `ReadFileTool::execute`（fs.rs:59-128），字符预算机制保留但截断点回退到完整行边界。

## 二、方案总纲

### 2.1 设计原则（本方案的六条硬约束）

1. **架构纯洁性优先**（REQ 1.3）：定时器/Cron 直接长在既有事件流与控制总线上，不引入独立守护线程、不新建第三套消息机制；凡既有契约能承载的（wait_subagents、PendingMessageQueue、L1 环）一律复用。
2. **不删除有用功能**（用户决策 2）：31 事件、背压三级、L0-L3、DAG 合成唤醒全部保留；`wait_subagents` 三模式与 `dispatch_*` 持久化原样保留，本轮只补引擎侧接线。
3. **分层持久化不变**（用户决策 3）：`timer-fired` / `cron-fired` 定级 Critical（必达落库，唤醒通知不可丢）；`timer-cancelled` 定级 Soft（尽力投递，丢失无害）；不引入第四级。
4. **契约先行**：agent-tools 定义 `TimerChannel` trait（仿 `SubagentWaitChannel` 注入模式）；壳层实现并注入；跨轮接口在 §四冻结，轮内按冻结形状并行实现。
5. **文件域互斥**：同一轮内同一文件只有一个 Agent 写；`fs.rs`、`search.rs`、`engine.rs`、`core_run_commands.rs` 等热点文件在任务分解时明确唯一所有者；同文件任务串行执行。
6. **诚实边界**：`contentOffset` 以行为粒度（非字节）是设计决策而非缺陷，必须在工具描述与文档中显式标注；二进制读取采用"文件引用"形态（非 base64）同样显式标注；IsDaemon=true 的会话归属与模块 B 联动裁决，本方案只做最小实现。

### 2.2 闭环模型与文档衔接（沿用 `docs/multi-agent-repair/00-方案总览.md` 框架）

本方案遵循同一闭环迭代模型：**问题识别 → 任务分解 → Agent 分配 → 并行修复 → 结果汇总 → 验证门禁 →（输出成为下一轮输入）**。

- 每轮输出轮次报告，格式沿用 `00-方案总览.md` §5 模板（轮次元信息 / 一已完成 / 二未完成 / 三新发现 / 四遗留问题 / 五验证结果 / 六输出到下一轮的问题清单）。
- 分配纪律沿用 `00-方案总览.md` §3：每轮最多 12 个 Agent；同轮文件域互斥；共享元文件（根 `package.json`、根 `Cargo.toml`、各 crate 的 `Cargo.toml`）每轮唯一所有者；安全红线沿用 `05-协同操作约束与安全.md`。
- 本方案与 `01-AB命令执行与后台任务方案.md` 的关系：AB 方案落地后台任务系统（task 域），本方案落地定时器/Cron/wait 接线（time 域）与工具防截断（F 域）。两方案共享事件注册表与背压分级基础设施（`conex-types`），新增任务域/时间域事件时统一在 `crates/conex-types/contracts/engine-events.json` 与 `engine_event_type_names!` 宏登记（`crates/conex-types/src/events.rs:611-664`），登记入口文档为 `docs/rust-rewrite/33-event-schema-changelog.md`。

### 2.3 总依赖图（只讲逻辑顺序，不排优先级）

```
G1/G2/G3 工具域（F 模块）── 独立链，无引擎依赖，先开工
        │
G4 wait 通道接线（C05 公共底座）
  ├── G10 兜底 watchdog（C05 验收 2）
  └── G7 会话级 idle 待命（C04 验收 1/2）
        │
G5 set_timer + TimerRegistry（C01）
  └── G6 TimerCondition 早退 + 冲突检测（C02）
        ├── timer-fired 事件（Critical）→ 事件注册表
        └── 到期注入（steering 条目 → idle 续 run）
              │
G8 唤醒摘要标准化（C04 验收 3）
G9 Cron 引擎（C03）── 解析器（conex-types）→ SchedulerRegistry → cron-fired 事件 + IsDaemon 拉起独立 run
```

依赖逻辑：

- G1/G2/G3 是纯工具改造（agent-tools 内部），无引擎依赖，逻辑上最先；
- G4 是 C01/C05 的公共底座（wait 通道接线），G10 依赖 G4（watchdog 消费 dispatch_* 声明）；
- G5 依赖 G4 的注入通道先例（steering 条目模式）与 §四冻结的 TimerChannel 契约；
- G6 依赖 G5 的 TimerRegistry（早退查表挂在注册表上）；
- G7 依赖 G5/G6（idle 待命要查"活跃定时器表"）与 G9（Cron 任务表）的非空判定；
- G8 依赖 G7（摘要随 idle 续 run 注入）；
- G9 独立成链，但 cron-fired 的注入复用 G7 的续 run 通道；IsDaemon=true 复用 RunProducer；
- 全部轮次不依赖 AB 方案的产物（后台任务系统），但"后台任务完成唤醒"在 AB 方案落地后经同一 steering 面并入（两方案在 steering_queue 上汇合）。

**IsDaemon 语义（冻结，最小实现）**：

- `is_daemon = false`：Cron 是当前任务推进的一部分——触发经 PendingMessageQueue steering 条目注入当前会话，随 idle 续 run 送达（与定时器同路径）；

### 8.4 开放问题与裁决点（承接 `REQ-CF-现状分析.md` §6.4）

1. **contentOffset 粒度**：已按用户决策定稿——**行粒度**（= 已返回完整行数），非字节；工具描述与 schema 显式标注，前端/需求侧记录偏差；
2. **二进制读取形态**：已定稿——**文件引用**（`binary: true` + path/size/encoding），非 base64（不冲击上下文窗口）；需求侧确认后本方案不再变；
3. **IsDaemon=true 会话归属**：本方案先落"新会话"最小形态（经 RunProducer 拉起独立 run），最终归属与模块 B 守护进程语义联动裁决——遗留至 R-CF3 轮次报告，由主调度 Agent 与 AB 方案统一裁决；
4. **idle 续 run 与 run 收场边界**：以"PendingMessageQueue 空 + 定时器表空 + Cron 表空"为硬条件 + 连续 3 次无产出停止续 run 护栏（T-CF-11），实现后由轮次验证回归确认；
5. **daily/intervalMinutes 转 cron 的语义边界**：intervalMinutes 转 `*/N * * * *` 是近似语义（N 不整除 60 时漂移），任务书（T-CF-14）写明该边界，必要时保留 daily/intervalMinutes 为独立调度类型（Rust 侧按原语义调度，不强制转 cron）。
