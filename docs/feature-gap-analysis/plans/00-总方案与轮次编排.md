## 一、方案定位

### 1.1 阶段定位：功能补齐阶段

`docs/multi-agent-repair/00-方案总览.md` 的 R0~R7 轮次（即 I1~I8 改进阶段）完成了"修复收敛"：可构建、可测试、可治理、可调度的地基，R7 产出多 Agent 调度能力本体（`00-方案总览.md:74`）。本方案是**修复收敛之后的新阶段**——"功能补齐阶段"：

| 阶段 | 职责 | 文档 |
| :--- | :--- | :--- |
| 改进阶段（I1~I8 / R0~R7） | 迁移收尾、契约层、引擎内核、治理固化、Agent 调度能力本体 | `docs/multi-agent-repair/` |
| **功能补齐阶段（本方案，F1~F12）** | 把 `REQ-agent-engine-capabilities.md` 的模块 A~G 需求与脚本逃逸防护全部落地为可验收能力 | `docs/feature-gap-analysis/plans/`（本系列） |

两个阶段的关系是"收敛地基 → 能力扩展"：改进阶段修好房子，本阶段往房子里安装功能。本方案覆盖：

1. **四模块方案**（各三轮，任务编号与分案完全一致）：
   - 模块 A+B：命令执行与后台任务（R-AB1/2/3，T-AB-01~20）；
   - 模块 C+F：定时唤醒与搜索读取工具（R-CF1/2/3，T-CF-01~14）；
   - 模块 D：多 Agent 协同调度（R-D1/2/3，T-D-01~13，其中 T-D-10/11/12 待定夺不排入）；
   - 模块 E+G：编辑工具与文档工作区（R-EG1/2/3，T-EG-01~13）。
2. **脚本逃逸防护**（`REQ-逃逸追踪分析.md`）：notify 实时监视 + write_paths 声明比对 + UndeclaredWrite 审计事件，拆为 T-ESC-01~05 五个任务卡，按其文件域并入早期轮次（T-ESC-05 为二期指纹复核，待用户定夺，不排入轮次）。

### 1.2 编排思路：统一的 F1~F12 轮次

各分案各自有三轮（R-AB1~3、R-CF1~3、R-D1~3、R-EG1~3），共 12 个分案轮次；加上逃逸防护的五个任务卡。本方案把它们**统一编排为 F1~F12 共 12 个执行轮**：

- 分案轮次保持原子性（每轮的轮内冻结接口与验证门禁不拆散），F 轮次是"分案轮次的排程容器"；
- 文件域互斥的多个分案轮次可并入同一个 F 轮并行执行（轮内多 Agent 并行）；
- 文件域冲突的轮次必须分处不同 F 轮（跨轮顺序由依赖与文件所有权共同决定）；
- F12 为终验门禁轮，不做新功能，全量核验完成态（对应 `00-方案总览.md:73` 的 R6 模式）。

## 二、闭环迭代模型与执行纪律

### 2.1 闭环模型（沿用 `00-方案总览.md` §2）

每一轮遵循同一条完整逻辑链路，轮与轮之间首尾相接：

```
问题识别 → 任务分解 → Agent 分配 → 并行修复 → 结果汇总 → 验证门禁 →（输出成为下一轮输入）
```

（`00-方案总览.md:26-46`）各环节职责：

| 环节 | 职责 | 产物 |
| :--- | :--- | :--- |
| 问题识别 | 依据上一轮轮次报告（已完成/未完成/新发现/遗留）与冻结契约，识别本轮问题范围 | 本轮问题清单 |
| 任务分解 | 把问题拆成可并行、文件域互斥的任务包 | 任务包集合（含独占文件域声明） |
| Agent 分配 | 按 §2.2 分配规则把任务包分配给本轮 Agent | 本轮 Agent 名单与文件域清单 |
| 并行修复 | 各 Agent 在独占文件域内独立修复，轮内不互等、不跨 Agent 沟通 | 各任务包修复结果（改动清单 + 自验证记录） |
| 结果汇总 | 汇总为轮次报告（格式见 §六） | 轮次报告 |
| 验证门禁 | 运行本轮触达的门禁（cargo test / typecheck / vitest / rg 抽查） | 验证结果（通过/未通过、失败明细） |
| 输出成为下一轮输入 | 轮次报告"二、未完成 / 三、新发现 / 四、遗留问题"合并编号进下一轮问题清单 | 下一轮问题清单（增量） |

闭环要点（沿用 `00-方案总览.md:44-46`）：轮内各 Agent 不互等，阻塞降级为"未完成"写入轮次报告由后续轮承接；轮次报告是下一轮的唯一输入。

### 2.2 Agent 分配纪律（沿用 `00-方案总览.md` §3）

1. **每轮最多 12 个 Agent**（`00-方案总览.md:52`）。上限是资源约束不是目标；本方案各轮 2~7 个，按需分配。
2. **同轮文件域互斥**（`00-方案总览.md:53`）：任务分解时先划文件域再拆任务包；同一文件轮内只允许一个 Agent 写。
3. **文件所有权纪律**（`00-方案总览.md:54-59`）：共享元文件（根 `package.json`、根 `Cargo.toml`、各 crate 的 `Cargo.toml`、前端各包 `package.json`）每轮唯一所有者；新增依赖需求写入轮次报告由下一轮唯一所有者承接；轮间文件转移所有权按 §3.17 表执行，不允许两轮残留未完成编辑。
4. **安全红线**：`docs/multi-agent-repair/05-协同操作约束与安全.md` 全文适用（checkpoint 恢复、git 操作安全、删除铁律、故障恢复阶梯 C7）。

### 2.3 "不排优先级"的纪律（本方案的防偏航机制）

需求文档第九章自带 P0/P1/P2 优先级表（`REQ-agent-engine-capabilities.md:858-920`），各现状分析也留有 gap 清单——**本方案一律不作为排程依据**。为防止 AI 在派单与执行中陷入"局部补丁思维"（挑容易的、挑影响面小的、先做"加分项"），固化以下纪律：

1. **排序只看依赖**：F 轮的先后只由 §1.3 的四条依赖与 §1.4 的文件冲突决定，不因"简单/难"或"收益高/低"调整顺序；任何任务书不得标注优先级字样。
2. **全量进入轮次**：各分案的 gap 清单（AB 的 G1~G8 `01-AB方案.md:71-80`、CF 的 G1~G10 `02-CF方案.md:69-90`、D 的 17 项缺口 `03-D方案.md:62-79`、EG 的 E1~E7/G1~G3 `04-EG方案.md:200-241`、逃逸形态 E1~E14 `REQ-逃逸追踪分析.md:259-285`）全部映射到任务卡，无取舍、无"可做可不做"。
3. **任务包全量交付**：每个任务包按任务卡四要素（文件域/内容/验收命令/验收断言）全量完成；禁止"先交付核心、边缘留白"式的部分实现——未完成即如实写"二、未完成"。
4. **每次改动全量回归**：任何改动必须过本轮验证门禁（含 `cargo test --workspace` 与前端回归），禁止以"只影响我这一处"为由跳过全量验证；回归失败的调用面（如 EG 的 write_file 覆盖语义变更）在轮次报告登记并由该轮唯一所有者承接修复，不推给下轮。
5. **待定夺项不是低优先级**：T-D-10/11/12 等体验增强项是"未决策"而非"不重要"——决策前不排入任何轮次，决策后按 §五的插入路径安排，不得自行脑补排期。
6. **有机结合而非堆叠**：新能力必须接入既有机制（事件注册表、控制总线 L0-L3、审计流、回收站、session_meta），凡发现"绕过既有机制另起炉灶"的实现，评审即判不合格（§四 4.1 的"保留/整合/新增"三列自检是评审抓手）。

### 2.4 子 Agent 不嵌套的派单纪律

- 嵌套裁决（`REQ-agent-engine-capabilities.md:616`）由 F4（R-D1）落地为三层工程：守卫默认值 maxDepth=1、工具面剔除 run_subagent、提示词结构化声明（T-D-01/02/03）。
- **F1~F3 期间**裁决尚未落地，但派单纪律立即生效：所有子 Agent 由主调度 Agent（主 Agent）派发，子 Agent 任务书首部必须含结构化声明——"你没有创建子 Agent 的能力；所有子 Agent 由主 Agent 分配。如需并行子任务、拆解或汇报，请通过消息/上报通道向主 Agent 提出，由主 Agent 统一派发。"（与 T-D-03 冻结文案一致，`03-D方案.md:252-253`）。
- F4 落地后，该声明由引擎自动注入子代理 run 的 System 段（`03-D方案.md:258-266`），派单纪律与引擎机制双轨并行。

## 三、轮次编排（核心）

### 3.1 编排原则

1. **分案轮次原子**：R-AB1~3、R-CF1~3、R-D1~3、R-EG1~3 作为不可拆分的排程单元，其轮内冻结接口与验证门禁原样执行；F 轮次只做"并包"与"排序"。
2. **并包条件 = 文件域互斥**：多个分案轮次并入同一 F 轮的唯一依据是写集两两不相交（src-tauri 与前端按文件粒度核对，不做目录级一刀切）；不满足即分轮。
3. **排序依据 = 依赖 + 所有权**：先满足 §1.3 依赖，再按 §3.17 所有权表把同一热点文件的写者排到不同 F 轮。
4. **轮内并行、轮间串行**：F 轮是执行顺序的最小单位，F{n} 全部收口（轮次报告 + 门禁通过）后才进入 F{n+1}；F5~F8 中无相互依赖的轮在保证文件所有权前提下允许调整次序（见 §3.2 依赖逻辑说明）。

### 4.1 "保留 / 整合 / 新增"三列自检（有机结合原则的评审抓手）

| :--- | :--- | :--- |
| 保留 | 本轮涉及面上已存在且继续有用的功能（含接口、机制、前端解析层） | 是否逐项列出？是否有改动其行为？ |

| intervalMinutes 转 cron | `*/N * * * *` 是近似语义（N 不整除 60 时漂移） | `02-CF方案.md:905` |
| 幂等键与 overwrite | 同一参数对"已存在/不存在"文件结果不同，参数 hash 键视为同一键——遗留细化项 | `04-EG方案.md:882` |
