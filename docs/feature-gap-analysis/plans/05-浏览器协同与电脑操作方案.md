# 05-浏览器协同与电脑操作方案（全局选型）

> 定位：为「软件内 AI 协同浏览器」与「电脑操作（Computer Use）」两条能力线做全局到细节的选型。
> 参考资料（已拉取至 `reference/`）：browser-use / playwright-mcp / chrome-devtools-mcp / agent-browser / anthropic-quickstarts（computer-use-demo）/ skyvern。
> 日期：2026-08-08。

---

## 0. 结论先行

1. **内嵌协同浏览器（推荐先做，P0-P3）**：唯一正解是「单渲染实例 + 双控制面」——右侧面板从 iframe 换成 **Tauri 子 WebView（Windows 下 WebView2）**，用户直接在里面操作，AI 经 **CDP 通道**操作同一个实例。这是"所见即所得 + 用户/AI 共同操作"的唯一架构形态（iframe 跨域隔离是铁律，不可绕过）。
2. **电脑操作（二期）**：能做到，但**比内嵌浏览器难一个量级**——没有结构化感知（全靠截图+视觉模型）、坐标不稳定（需缩放/对齐机制）、安全面大（全局输入注入）。两者**可以一起做但不共享核心层**：工具执行框架（注册面/审批/审计/事件）可复用，渲染/感知/执行三层完全独立。
3. **现成方案都不解决"协同"**：browser-use / playwright-mcp 是独立进程 + AI 独占；chrome-devtools-mcp 能 attach 用户浏览器但非软件内；agent-browser（eve）是沙箱内 headless + Rust CDP daemon。**「软件内 + 用户 AI 同屏操作」是全行业空白，是我们的差异化点**。
4. 最大技术风险（必须 P0 PoC 验证）：**WebView2 的 CDP 是受限子集**，`Input` 域（真实输入事件）可用性需实测；不可用则用注入脚本合成事件兜底（isTrusted=false，覆盖度足够）。
5. Cookie/用户数据导入的正确答案：**整目录复制 Chrome/Edge profile 到独立目录**（browser-use 已实现，`browser/profile.py:838-893`），比 DPAPI 解密简单可靠且覆盖全（cookie/书签/历史/扩展/登录态）。

## 1. 目标与约束

- 用户需求：AI 的操作用户可见；用户和 AI 共同操作同一浏览器；软件内完成；支持导入其他浏览器数据。
- 已确认事实（代码证据）：
  - 右侧面板现为 iframe 预览（`apps/crish-desktop/src/components/workspace/PreviewCard.tsx:190-202`），`sandbox="allow-scripts allow-same-origin"`，AI 无法操作第三方页面。
  - 引擎为 Rust + Tauri 2（`apps/agent-workbench/src-tauri/Cargo.toml:22`），Windows 渲染内核 WebView2。
  - agent-tools 工具注册面 / 权限审批 / 审计 / 幂等体系已就绪（`crates/agent-tools/src/lib.rs`），MCP 桥可即插即用（`register_plugin_server`，`engine.rs:1136`）。
  - agent-provider 已支持 vision 能力位与 image_url 多模态（`messages.rs:71-76`），截图喂模型管道已通；cache 白名单只缓存 text 块（`request/cache.rs:758`），vision 会涨成本。
  - conex-db 封装 rusqlite，可读浏览器 SQLite 数据（书签/历史/cookie 库）。
- 平台现实：开发环境 win32；跨平台需降级策略。

## 2. 全局选型：三条路线

| 路线 | 形态 | 用户可见 | 用户可操作 | AI 可操作 | 软件内 | 难度 |
|---|---|---|---|---|---|---|
| A 内嵌协同浏览器 | 右侧面板 = Tauri 子 WebView（WebView2），AI 经 CDP 驱动同一实例 | ✅ 同屏 | ✅ 原生 | ✅ CDP | ✅ | 中 |
| B 独立浏览器 + MCP（现成方案） | 接 chrome-devtools-mcp / playwright-mcp，独立 Chrome 窗口 | ⚠️ 另一窗口 | ⚠️ 但不同实例 | ✅ | ❌ | 低 |
| C 电脑操作（Computer Use） | 全屏截图 + 全局鼠标键盘注入 | ✅ | ✅ | ✅ 截图驱动 | ✅ | 高 |

**选型结论**：A 是最终形态（满足全部需求）；B 作为 A 未就绪时的过渡（1-2 天可通，MCP 桥已具备）；C 是独立产品线（二期）。

## 3. 内嵌协同浏览器（路线 A）—— 分项选型

### 3.1 渲染实例：Tauri 子 WebView（WebView2） ✅ 唯一现实选择

| 候选 | 结论 | 理由 |
|---|---|---|
| iframe（现状） | ❌ 死刑 | 跨域隔离铁律，无法注入/读取第三方页面 |
| Tauri 子 WebView2 | ✅ 首选 | Tauri 2 支持同窗口多 webview；WebView2 = Edge Chromium，真实渲染、自带 CDP、独立 userDataFolder（profile 持久化） |
| 独立 Chromium 进程 + 窗口嵌入 | ⚠️ 备选 | 控制力最强（完整 CDP），但窗口嵌入/聚焦/层级处理复杂，跨平台成本高 |
| CEF / Ultralight | ❌ | 体积/复杂度不可接受 |

- 落地：`tauri::webview::WebviewBuilder` 挂主窗口右侧区域（保留 PreviewCard 工具栏/历史/书签 UI 壳，替换内容区）；独立 `userDataFolder`（登录态持久化）。
- **P0 PoC 必测项**：WebView2 开启 `--remote-debugging-port=<随机端口>`（经 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` 或创建参数）后，`Input.dispatchMouseEvent` / `Input.dispatchKeyEvent` 是否可用（WebView2 CDP 为受限子集，微软不保证全协议）。Page/Runtime/Network 域基本可用。

### 3.2 AI 控制通道：CDP 首选 + 注入脚本桥兜底

| 候选 | 结论 | 理由 |
|---|---|---|
| CDP（WebSocket） | ✅ 首选 | 真实输入事件（isTrusted=true，反爬友好）、快照/截图原生支持、`chrome-devtools-mcp --browserUrl` 可直接 attach（MCP 兼容自动达成） |
| 注入脚本 + postMessage | ⚠️ 兜底 | CDP Input 域不可用时合成事件（isTrusted=false，部分站点可检测）；跨平台 macOS/Linux 的 WKWebView/WebKitGTK 无 CDP，只能走此路 |
| 双轨 | ✅ 最终 | Windows 主 CDP、辅注入；其他平台注入桥 |

- Rust CDP 客户端：`chromiumoxide`（成熟，异步 WS）或自写最小客户端。agent-browser 用 Rust 自写 CDP 客户端 + daemon（`reference/agent-browser` AGENTS.md：`cli/src/native/`），可作为实现参考。
- **长连接**：保持单一 WS 常驻（browser-use 自己都在 TODO 里承认"每步重连"是短板，`dom/service.py:51`）。

### 3.3 感知快照：借鉴 browser-use 的 serializer 算法

给模型喂的"眼睛"是快照文本，方案（全部参考 `reference/browser-use/browser_use/dom/`）：

1. `Accessibility.getFullAXTree`（CDP 原生 AX 树）+ DOM + computed styles（`REQUIRED_COMPUTED_STYLES`）
2. **可点击元素检测**（`serializer/clickable_elements.py:6-120`）：JS 事件监听器（CDP 探测，不 DOM 突变）/ label 包 input / search 类名 / AX focusable-editable / disabled/hidden 过滤
3. **绘制顺序过滤**（`serializer/paint_order.py`）：剔除被遮挡元素
4. bbox 过滤（99% 包含阈值）+ 树优化（去冗余父节点）
5. 序列化 + **索引定位**：每个可交互元素发 `[index=N]`，工具用 index 操作；缓存上一轮 selector_map 做增量匹配（`serializer.py:71-79`）
6. iframe 支持：CDP 可进跨域 frame（browser-use 默认关、配置开——我们默认开同源 iframe，跨域 iframe 按需）

- 不做视觉感知（当前 deepseek-v4 无视觉能力）：截图仅作调试/用户回显，快照文本为主。模型升级到视觉模型后，截图作为补充（vision 成本注意：cache 只缓存 text）。

### 3.4 元素定位与操作执行

- 定位链：快照 index → CDP `DOM.getNodeForLocation`（坐标）或保存的 backendNodeId → 操作。
- 操作原语（全部经 CDP）：click（真实输入或 `Runtime.evaluate` 合成，按 3.2 双轨）、type（按 chunk 输入，参考 computer-use `TYPING_GROUP_SIZE=50`）、scroll、hover、drag、key、wait_for（元素/网络空闲，参考 chrome-devtools-mcp `WaitForHelper`）。
- **失败重试**：页面变化导致坐标失效 → 重新快照再操作（agent-browser snapshot 有 CDP 竞态重试先例，`snapshot.ts:11-26`）。

### 3.5 协同模型（用户 ↔ AI）

- **双向事件**：AI 操作（导航/点击/输入）→ Rust → 前端工具栏地址栏/指示条更新；用户操作 → 本就在同一实例，AI 下次快照自然看到。
- **控制权指示**：AI 操作时面板顶部显示"AI 正在操作浏览器"条（可暂停/接管，接管后 AI 收到快照变化提示）。
- **冲突处理**：AI 的 index/坐标操作失败（页面被用户改了）→ 自动重快照重试，不硬刚。
- **历史/书签**：沿用现有 `previewBrowserStore`（`crish-preview-url` 事件机制），扩展到 webview 真实导航事件。

### 3.6 数据导入（Cookie/书签/历史/登录态）

| 数据 | 方案 | 来源参考 |
|---|---|---|
| Cookie + 登录态 + 扩展（主路径） | **整目录复制** Chrome/Edge `user_data_dir/<profile>` 到独立目录（跳过 `Singleton*`/`*.lock`/`*-journal` 锁文件，带 `Local State`），启动时 `--user-data-dir` 指向 | browser-use `profile.py:838-893` |
| Cookie（轻量路径） | `storage_state` JSON 导入/导出（Playwright 标准格式，CDP `Network.getAllCookies` 读取） | browser-use `session.py:1427-1470` |
| 书签 | Chrome `Bookmarks` JSON 直读导入 | — |
| 历史 | Chrome `History` SQLite（conex-db 可复用） | — |
| 密码 | **不做**（安全风险，浏览器本身也不建议存） | — |
| 长期登录态 | webview 自带 userDataFolder 持久化：用户登录一次，永久保留 | — |

- 复制冲突处理：Chrome 运行中锁文件 → 提示关闭 Chrome 或引导走 storage_state（browser-use 同策略，`profile.py:876-881`）。
- profile 复制完成后"增量同步"（定期或手动重拷）作为 P3 增强。

### 3.7 工具集设计（agent-tools 注册面）

新增 `browser_*` 工具族（Rust，挂 ToolRegistry，自动获得审批/审计/幂等）：

| 工具 | 说明 | dangerous |
|---|---|---|
| browser_navigate / back / forward / reload | 导航 | false |
| browser_snapshot | 快照（3.3 算法）| false |
| browser_click / type / scroll / hover / drag / key | 交互 | true（审批）|
| browser_screenshot | 截图（base64，供回显/调试）| false |
| browser_new_tab / close_tab / switch_tab / list_tabs | 多标签 | false |
| browser_wait_for | 元素/网络等待 | false |
| browser_console / browser_network | 控制台/网络（调试）| false |
| browser_evaluate | JS 执行（受限白名单场景）| true（审批）|
| browser_upload_file | 文件上传 | true（审批）|

- 命名对齐社区（chrome-devtools-mcp 用 `chrome-*` 前缀但工具本质相同；browser-use 用 navigate/click/input）。
- MCP 兼容后：`chrome-devtools-mcp --browserUrl http://127.0.0.1:<port>` 直接 attach 内嵌 webview，官方全套工具可用，与本工具族并存（用户配置选择）。

### 3.8 安全设计

- 调试端口：仅 loopback + 每次启动随机端口 + 面板激活才开启（对齐 `31-security-baseline.md` 网络监听基线；dev_mcp.rs 已有 loopback+env 先例）。
- 域名约束：`allowed_domains` / `prohibited_domains`（browser-use 已实现，`profile.py` 语义；agent-browser 扩展同样有 allowlist）。
- 危险操作审批 + 审计事件（复用 agent-tools permission/audit）。
- 下载文件落入工作区受限目录；剪贴板读取需授权。

### 3.9 跨平台策略

| 平台 | 渲染 | 控制通道 |
|---|---|---|
| Windows | WebView2（Tauri 默认）| CDP 优先 + 注入兜底 |
| macOS | WKWebView | 注入脚本桥（无 CDP）|
| Linux | WebKitGTK | 注入脚本桥 |

- 注入桥实现：wry 支持 `with_initialization_script` + `postMessage` 双向通道（对应 WebView2 `AddScriptToExecuteOnDocumentCreated`）。
- 先做 Windows 完整版（CDP），其他平台降级版（注入桥）后续；接口层（3.7 工具面）保持一致。

### 3.10 技术栈与 crate 划分


## 4. 电脑操作（Computer Use，路线 C）—— 对比与方案

### 4.1 难度对比（直接回答"哪个难"）

| 维度 | 内嵌协同浏览器 | 电脑操作 |
|---|---|---|
| 感知 | AX/DOM 快照（结构化，文本模型可用）| 截图（需视觉模型或 OCR）+ 偶尔无障碍 API |
| 操作 | CDP 输入事件（页面内，可信）| 全局鼠标键盘注入（SendInput/xdotool），影响整个系统 |
| 状态 | 页面加载可等待、事件可监听 | 无等待原语，靠轮询截图对比 |
| 坐标 | 视口内坐标，稳定 | 全屏坐标 + **多显示器/DPI/缩放**，需缩放对齐机制（Anthropic 的 `scale_coordinates`，`computer.py:268-291`）|
| 安全 | webview 沙箱 + 审批 | 注入发生在 OS 层，误操作风险大，必须审批+审计+可急停 |
| 复杂度 | 中 | 高（难 1.5-2 倍）|

**结论：电脑操作更难**，且强依赖视觉模型（当前 deepseek-v4 无视觉，体验打折）。内嵌浏览器不依赖视觉（快照文本），是更优的第一步。

### 4.2 若做，Windows 参考实现

- 动作空间（对齐 Anthropic 官方定义）：key / type / mouse_move / left_click / left_click_drag / right_click / scroll / hold_key / screenshot / cursor_position（`computer.py:21-46`）。
- 截图：`xcap`（Rust）或 `Windows.Graphics.Capture`；输入注入：`enigo`（Rust）或 winapi `SendInput`。
- 坐标缩放：截图缩放到模型友好分辨率（XGA 1024×768 等），API 坐标双向换算（`computer.py:58-62,268-291`）。
- 输入节奏：type 分 chunk（50 字符）+ 12ms 延迟（`computer.py:18-19`），避免漏字。
- 权限：dangeous=true + 审批 + 审计 + 全局急停（Esc）；白名单窗口/域名可作后续增强。
- 依赖：视觉模型（截图闭环）或 Windows UI Automation 降级（结构化但覆盖率低）。

## 5. 两条线的共享层与独立层

```
共享层（先建，一次投入两线受益）：
  工具执行框架（ToolRegistry/审批/审计/幂等/流式）
  ToolContext 扩展（browser 会话句柄）
  前端面板壳（工具栏/指示条/事件桥）
  事件与日志链路（tool_events / audit）

独立层（各自实现）：
  渲染：webview（A）vs 无（C，直接 OS 输入）
  感知：AX/DOM 快照（A）vs 截图+视觉（C）
  执行：CDP（A）vs SendInput/截屏（C）
```

**结论：不合并实现，共用框架。先 A（浏览器）后 C（电脑），C 的感知层可与 A 的截图工具共用 CDP 截图代码（浏览器内 computer use 是 C 的降级演练场）。**

## 8. 开放问题（需决策/验证）

1. WebView2 CDP `Input` 域可用性（P0 PoC 第一验证项）——决定控制通道主副配置。
2. Tauri 2 子 webview 嵌入主窗口的成熟度（版本确认，必要时退回"独立无边框窗口贴附"方案）。
