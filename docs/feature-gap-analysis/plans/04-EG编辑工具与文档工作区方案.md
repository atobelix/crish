## 0. 方案速览（结论先行）

### 0.1 一句话定位

模块 E 的三个需求**全部属于全新实现或小改造**（multi_replace 是全新设计而非"恢复"——现状调查已证伪"重构遗失"说法）；模块 G 的底层契约（写路径互斥、快照备份、探索配额、session_meta、wait_subagents）**多数已实现但主执行器未接线**，缺的是"默认工作目录"这一核心机制与引擎侧装配。本方案以三个轮次（R-EG1 / R-EG2 / R-EG3）按逻辑依赖顺序推进：先做最大的新工具（multi_replace），再做行为变更与引擎总接线，最后做文档工作区机制与协作产出流程。

## 1. 设计约束与整合原则

### 1.1 逻辑执行顺序原则

三个轮次的顺序由三条逻辑依赖决定，与任何优先级无关：

1. **新工具先于行为变更**：R-EG1 落地 multi_replace 工具本体（不依赖任何接线即可单元测试闭环，单进程内原子性天然成立）；R-EG2 再把它的引擎强制面（互斥/备份）接线——现状分析明确"E01 的原子性验收在单进程内即可满足，写路径互斥/中间件装配可作为同批或次批接线"（REQ-EG-现状分析.md:746）。
2. **行为变更先于协作接线**：write_file 默认拒绝覆盖是唯一影响既有调用面的改动（REQ-EG-现状分析.md:877），先行落地并全量回归，避免与接线改动混在一起难定位。
3. **工作区机制最后**：G01 的输出目录是 G02/G03 的共同前置；而 G01 的"引擎侧装配"复用了 R-EG2 已接好的 ToolContext 装配面（tool_exec.rs:670-687 附近一处接线服务多个需求，REQ-EG-现状分析.md:750）。

### 1.2 功能保留清单（明确不动的部分）

以下设施在本方案落地中**只增不改语义**，任何任务都不得删改其行为：

| 设施 | 位置 | 本方案的对待方式 |
| --- | --- | --- |
| write_file（写文件工具） | crates/agent-tools/src/tools/fs.rs:132-219 | 保留全部现有能力（父目录自动创建 fs.rs:197、编码续写、快照标记返回）；仅在 R-EG2 增加 overwrite 语义 |
| read_file / grep_search / fuzzy_find / list_dir / file_stat / diff_text / shell_command 等其余工具 | crates/agent-tools/src/tools/ | 不触碰 |
| 幂等守卫（executor.rs:72-131 / idempotency.rs:291-300） | crates/agent-tools/ | 零改动，multi_replace 自动受益（同参重试去重） |
| 写路径互斥（WritePathRegistry） | crates/agent-tools/src/write_paths.rs:135-281 | 保留机制本体，R-EG2 完成装配 |
| 快照备份中间件（BackupMiddleware） | crates/agent-tools/src/backup.rs:51-153 | 保留机制本体，扩展名单 + 装配 |

| wait_subagents（三模式等待） | crates/agent-tools/src/tools/wait_subagents.rs | 保留，R-EG3 只扩展产出字段（outputFiles），dispatch_* 持久化做旧数据兼容 |

### 1.3 统一编辑面模型（multi_replace 与既有设施的关系）

multi_replace 不是"又一个写工具"，而是与 write_file 并列、共享同一套编辑契约的**统一编辑面**的一部分。所有写类工具（write_file / multi_replace / delete_file）走同一链路：

```
工具执行器 executor.rs
   │  ┌────────────────────────────────────────────────────┐
   │  │ 中间件链（loop/mod.rs:219 装配，R-EG2 接线）          │
   │  │   BackupMiddleware：写前快照 → .crish-trash          │
   │  │   （backup.rs:134-151；失败即 Block）                 │
   │  └────────────────────────────────────────────────────┘
   ▼
execute 内（各工具内部，统一顺序）：
   1. resolve_workspace_path 路径安全校验（tools/mod.rs:171-226）
   2. claim_write_guard 写路径互斥声明（write_paths.rs:303-318）
   3. guard_explore_docs_write 探索配额检查（explore_quota.rs:262-276）
   4. 读入 → 解码（BOM/二进制判定，tools/mod.rs:295-334）
   5. 内容级操作（multi_replace：逐块匹配 + 内存整体应用；write_file：直接编码）
   6. 原子落盘（同目录临时文件 + rename 交换）
   7. consume_explore_docs_quota 配额消耗（explore_quota.rs:280-287）
   8. 返回 snapshot_tag（tools/mod.rs:277-281）
```

各设施的职责边界：

| 设施 | 在统一编辑面中的职责 | 与 multi_replace 的结合点 |
| --- | --- | --- |
| WritePathRegistry（write_paths.rs:135-281） | 会话级并发互斥（TTL 60s 防悬挂 write_paths.rs:40；多路径原子声明 write_paths.rs:172-223） | 执行第 2 步声明 target_file；冲突返回 `tool.write_path_conflict`（write_paths.rs:92-101），与 write_file 行为一致（fs.rs:187） |
| BackupMiddleware（backup.rs:51-153） | 任何破坏性写前自动快照（backup.rs:3-8 铁律） | 默认名单扩展加入 `multi_replace_file_content`（backup.rs:42-44）；快照进回收站域，restore_force 覆盖恢复（backup.rs:379-401） |
| 幂等守卫（idempotency.rs:291-300） | 同参重试去重（执行键 = 工具名 + 参数规范 hash） | 零改动；同 chunk 集合重试返回 Deduplicated（executor.rs:277-299 语义） |
| conex-fs::trash（trash.rs） | 删除与快照的存储面（snapshot / restore_force） | backup 中间件的存储后端；E01 自身不删文件，但写坏恢复走 trash |
| 探索配额（explore_quota.rs） | 探索类子代理的文档产出上限 | 第 3/7 步接线（与 write_file 同款，fs.rs:189/203），防借 multi_replace 绕过配额 |

### 1.4 注释保留双保险机制（REQ-E03）

- **保险一（工具级）**：multi_replace 的替换机制基于 `target_content` 精确匹配，未被指定的内容天然不动——这是机制性保证（REQ-agent-engine-capabilities.md:697）。工具 schema 的 description 必须明示："target_content 必须精确匹配原文（含缩进与注释行）；replacement_content 需完整承载目标区间内的注释行"；REQ-E03 验收并入 E01 测试（替换中部字段 + 断言头部注释/尾部 doc 注释原样保留）。
- **保险二（提示词层）**：新增固定注入段 `comment_preservation_section()`（对齐 subagent_inject.rs 的 `started_at_section` / `git_revert_caution_section` 先例，lib.rs:91-99 导出；同型先例还有探索配额凭证段 explore_quota.rs:213-221），挂载主 agent 系统提示词与子代理注入面，约束 AI 生成 replacement_content 时不得删除/改写与本次修改无关的注释与文档字符串。

### 1.5 现状分析采用结论清单

本方案直接采用 REQ-EG-现状分析.md 的全部调查结论，其中对任务书编写影响最大的六条：

1. **multi_replace 从未实现过**：legacy 时代只有 e2e 测试占位（967e7846^:packages/agent-daemon/src/__tests__/agent-real-workflow-e2e.test.ts:121-160，实际 writeFile 模拟），`replacement_chunks` / `replace_file_content` 全历史零命中（REQ-EG-现状分析.md:46-87）——任务书表述必须用"全新设计"，不得写"恢复/找回"；
2. **Rust 版 12 工具注册表无任何 replace 类工具**（tools/mod.rs:86-113 注册、461-490 断言）；
3. **写路径互斥 / 备份中间件 / 探索配额全部实现完毕但未接线**：主执行器 ToolContext 构造处 `write_claims: None`、`write_claim_holder: None`、`explore_docs_quota: None`（tool_exec.rs:683-686），中间件链空 Vec（loop/mod.rs:219），壳层零装配（REQ-EG-现状分析.md:134-141）——这是 R-EG2 的"总接线点"；
4. **前端 applyFileDiff.ts 的 search_replace 六态判定与 EOL 归一化是唯一成熟的精确替换参考实现**（applyFileDiff.ts:316-376 六态、287-297 EOL），E01 移植其判定语义；
5. **docs/multi-agent-repair/ 是 REQ-G02 的现实目标形态**：`00-方案总览.md` + `NN-编号子文档` + README 汇总索引（README.md:7-14），文件名 `NN-<简短标题>.md` 惯例与需求示例一致（REQ-EG-现状分析.md:540-567）；
6. **session_meta 全局 KV 可承载 G01 持久化**（conex-db schema.rs:87 表；sessions.rs:140-171 接口；explore_quota.rs:43-49 键编码先例），G01 不引入新表。

## 2. 问题识别

### 2.1 模块 E（约 40%）

#### 2.1.1 E-1：工具面没有任何 replace 类工具（核心问题）

12 个工具的注册断言清单（tools/mod.rs:461-490）：

```
["delete_dir", "delete_file", "diff_text", "file_stat", "fuzzy_find",
 "grep_search", "list_dir", "read_file", "run_subagent", "shell_command",
 "wait_subagents", "write_file"]
```

- **现象**：修改既有文件只能"read_file 全文 → write_file 全量重写"，没有"定位 + 精确替换"能力；无法做到"单次调用完成 N 个非连续块修改 + 任一失败整体回滚"；
- **历史纠偏**：需求备注"此功能曾存在、AI 重构时遗失"不准确——git 全历史检索证明只有 e2e 测试占位（流程 mock，实际 writeFile），从未有工具定义/schema/执行逻辑（REQ-EG-现状分析.md:46-87）。实施路径是**全新设计**，可复用当时规划过的语义（工具名、块替换思想、审批联动）；
- **影响**：REQ-E01 的验收（单次调用 N 块替换 / 任一失败回滚 / 与手工修改等价）全部落空；REQ-E03 的机制面（精确匹配天然保留注释）也随之悬空。

**legacy e2e 占位的证据细节（供任务书引用，避免写错历史）**：

```
967e7846^:packages/agent-daemon/src/__tests__/agent-real-workflow-e2e.test.ts:121
    it("路径 1.3: multi_replace_file_content 块替换与结构断言 ...", async () => {
    const approvalQueue.waitForApproval("call_multi_replace", "run_multi_replace", {
      toolName: "multi_replace_file_content",
      input: { path: targetFilePath, replacementsCount: 2 },   // 无 replacement_chunks
      ...
    });
    const replacedCode = [...].join("\n");
    await writeFile(targetFilePath, replacedCode, "utf-8");     // 测试直接 writeFile 模拟
```

三个关键事实（REQ-EG-现状分析.md:81-87）：

1. 入参只有 `{ path, replacementsCount }`，**没有 replacement_chunks**——测试只验证"审批 → 执行 → 落盘"的流程占位；
2. 实际替换是测试代码直接 writeFile 模拟的，**从未经过任何 multi_replace 工具实现**；
3. 因此"规划过但从未实现"（工具名、块替换思想、审批联动可复用），而非"实现过被删掉"——T-EG-01 任务书必须基于此表述设计，不能去 git 历史找"旧实现"。

#### 2.1.2 E-2：write_file 无条件覆盖，无 Overwrite 保护

- **现象**：write_file 直接 `std::fs::write` 覆盖写入（fs.rs:199），schema 无 overwrite 字段（fs.rs:145-158），工具描述明言"覆盖写入"（fs.rs:144）；
- **已具备的一半**：父目录自动创建（fs.rs:197，ensure_parent_dir 实现 conex-fs/src/lib.rs:84-95）、绝对路径校验、返回路径确认（fs.rs:210-217）；
- **影响**：AI 或前端误操作可无提示覆盖既有文件，与"防意外覆盖"语义相反；REQ-E02"默认拒绝覆盖、显式 Overwrite=true 才覆盖"完全不满足；
- **兼容面**：这是全模块唯一改变既有调用行为的需求（REQ-EG-现状分析.md:872-873 风险 1）——既有测试多处直接覆盖写入（如 fs.rs:584-598 的编码续写用例），需显式补 overwrite: true。

#### 2.1.3 E-3：单块 replace 工具缺失（决策点）

- **现象**：REQ-E01 1.3 规定"单点修改仍用 replace_file_content（单块）"，但该工具与 multi_replace 一样从未存在（全历史零命中）；
- **决策：不先建独立单块工具**。理由：
  1. multi_replace 的 `replacement_chunks` 长度为 1 时语义与单块替换完全等价，一个工具覆盖两种用法（现状分析 1.6.4 推荐，REQ-EG-现状分析.md:215）；
  2. 独立单块工具会导致注册表膨胀与"何时用哪个"的提示词负担；
  3. 不存在"恢复单块工具"的历史义务（从未实现过）；
- **落地方式**：schema 文档说明 chunks=1 用法；补一条"chunks=1 行为与单块替换一致"的测试（REQ-E01 1.3 验收映射）；REQ-E01 1.3 后半句"禁止对同一文件并行发起多个单块替换调用（防竞争）"由 R-EG2 的写路径互斥接线强制（并发同路径调用返回 `tool.write_path_conflict`）。

#### 2.1.4 E-4：EOL 归一化缺失（Windows 专属细节）

- **现象**：Windows 上 CRLF/LF 混用会使 `target_content` 精确匹配失效；Rust 侧无任何 EOL 归一化工具函数；
- **参考实现**：前端 applyFileDiff.ts:287-297 已有 normalizeEol / preferEolStyle（统一换行后比较、按原文件偏好还原 CRLF）；六态判定（applyFileDiff.ts:316-376）的"唯一匹配才替换"语义是 E01 匹配阶段的对标；
- **落地**：本方案采用现状分析建议的简化形态——目标文件为 UTF-8 无 BOM 项目惯例（REQ-EG-现状分析.md:188），匹配时 CRLF→LF 归一化，写回时恢复原文件换行风格。

#### 2.1.5 E-5：周边设施已实现但未接线（E01 的引擎强制面缺失）

### 4.3 write_file overwrite 参数

```json
{
  "overwrite": {
    "type": "boolean",
    "default": false,
    "description": "文件已存在时是否允许覆盖，默认 false（已存在则报错，需显式 true 才覆盖）"
  }
}
```

- 存在性检查位置：`claim_write_guard` 之后、写盘之前（fs.rs:187 之后）；
- 错误码：沿用 `tool.execution_failed` 或新增 `tool.file_exists` 域码（对齐 write_paths 的域码先例 write_paths.rs:37，任务书定稿）；
- 兼容矩阵见现状分析 2.5（REQ-EG-现状分析.md:385-399）：前端 applyFileDiff 走 Tauri `write_file_content` 命令不受工具改动影响，但壳层命令建议同步 overwrite 语义防口径分裂（T-EG-05）；
- 幂等注意：同一参数（path+content+overwrite=false）对"已存在/不存在"文件结果不同，参数 hash 键（idempotency.rs:291-300）会视为同一键——接线期细化项（现状分析 2.4 第 6 条）。

错误形状（默认拒绝覆盖时返回，供 T-EG-04 参考）：

```
ToolError { code: "tool.file_exists"（或 tool.execution_failed，任务书定稿），
            message: "write_file: 目标文件已存在（<path>）。如需覆盖请显式设置 overwrite=true；
                      该操作默认拒绝覆盖已有文件" }
```

### 4.4 AgentOutputDir 与 OutputDirResolver（G01 数据结构草案）

```rust
/// 会话级文档产出目录（REQ-G01）
pub struct AgentOutputDir {
    /// 会话标识（路径子目录名，经净化：剥离 \/:*?"<>| 与控制字符）

    pub user_specified: bool,
}

/// 产出目录解析服务（注入 ToolContext，None = 未接线，返回结构化错误）
pub trait OutputDirResolver: Send + Sync {

    /// 惰性：只记录路径不创建目录，首次 write_file 时由 ensure_parent_dir 自动创建

    /// 目录尚未创建，首次写入时自动创建（避免 AI 误判目录不存在）

}
```
