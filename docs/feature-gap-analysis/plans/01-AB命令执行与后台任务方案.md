### 1.2 四大核心冲突

**冲突一：超时即树杀与「不误杀正常进程」原则直接矛盾。**

现状超时分支唯一动作是「树杀 + 返回 timedOut=true」（`shell.rs:687-705`），正是需求文档明令禁止的「强制硬超时杀进程」。长编译、长测试被 AI 设置 timeoutMs 后，无论是否健康运行都会被一刀切杀。修复方向不是取消超时，而是把超时语义从「杀死」改为「转后台托管」（REQ-A01 模式 2），`timeoutMs` 保留为 AI 显式设置的绝对长跑防护，与「等待窗口」两个维度并存。

**冲突二：同步收口式读取与后台化改造互斥。**

`wait_with_output` 一次性收口（`shell.rs:660-661`）意味着：管道无法中途移交、无法记录「最近输出时间」、无法持续累积日志。G2（流式化）是所有后台化改造（G4/G5/G6/G7）的共同前置，必须先改。

**冲突三：资源监控零存在，但「不误杀」必须基于事实。**

AI 目前只能靠「运行时长」猜测进程健康与否——这正是需求禁止的行为（REQ-A04 4.3）。要落地「只要进程在正常稳定运行就不应被终止」，必须有可观测事实：CPU/内存/最近输出时间（REQ-A04 4.1 四指标）与三态健康判定（正常运行/疑似卡死/异常退出）。

**冲突四：前端后台任务 UI 是「调用已删除命令的死代码」，静默失效。**

`backgroundTasksApi.ts:511-557` 调用三个已删除的 Tauri 命令（`workbench_list_background_tasks` 等），`invokeCmd` 宽松语义（`tauriInvoke.ts:185-192`）导致 UI 静默显示空列表。修复方向不是删前端，而是 Rust 侧重建后台任务系统并恢复这三条命令——前端解析层（`backgroundTasksApi.ts:231-276`）原样复用。

## 二、方案总纲

### 2.1 设计原则（本方案的六条硬约束）

1. **架构纯洁性优先**（REQ 1.3）：不复活 sidecar WS 协议，不引入 PTY 到任务系统（终端面板与任务系统保持解耦）；所有新能力以 Rust 内核 + 壳层 + 前端分层直连，无兼容包袱。
2. **不误杀正常进程**（REQ 1.2-3 / A04 4.3）：转后台替代超时即杀；资源监控只通知不自动杀；AI 不得仅凭运行时长终止进程。
3. **契约先行**：agent-tools 定义 `BackgroundTaskManager` trait（仿 `subagent_spawner` 模式），壳层实现并注入；跨轮接口在任务书中冻结，轮内按冻结形状并行实现。
4. **文件域互斥**：同一轮内同一文件只有一个 Agent 写；`shell.rs` / `background.rs`（壳层）/ `mod.rs` 等热点文件在任务分解时明确唯一所有者。
5. **落盘为 best-effort**：日志目录不可写时命令执行不得失败，仅降级为「无 logPath」（对齐 `perf/jsonl.rs:49-72` 错误风格）。
6. **诚实边界**：Unix 资源采样口径（进程树近似）、Windows 优雅终止可用性、stdout/stderr 交错顺序在实现文档中显式标注。

### 2.2 闭环模型与文档衔接（沿用 `docs/multi-agent-repair/00-方案总览.md` 框架）

本方案遵循同一闭环迭代模型：**问题识别 → 任务分解 → Agent 分配 → 并行修复 → 结果汇总 → 验证门禁 →（输出成为下一轮输入）**。

- 每轮输出轮次报告，格式沿用 `00-方案总览.md` §5 模板（轮次元信息 / 一已完成 / 二未完成 / 三新发现 / 四遗留问题 / 五验证结果 / 六输出到下一轮的问题清单）。
- 分配纪律沿用 `00-方案总览.md` §3：每轮最多 12 个 Agent；同轮文件域互斥；共享元文件（根 `package.json`、根 `Cargo.toml`、各 crate 的 `Cargo.toml`）每轮唯一所有者；安全红线沿用 `05-协同操作约束与安全.md`（checkpoint 恢复、git 回退安全、故障恢复阶梯 C7）。
- 本方案与 improvement 系列（`docs/multi-agent-repair/improvement/`）的关系：本方案是 feature-gap-analysis 的实施层文档，落地「引擎基础能力」（命令执行与后台任务）；improvement 的 I 系列是「多 Agent 调度能力」。两者共享事件注册表与背压分级基础设施（`conex-types`），本方案新增任务域事件时需与事件注册表维护方协调（`docs/rust-rewrite/33-event-schema-changelog.md` 为登记入口）。

### 2.3 总依赖图（只讲逻辑顺序，不排优先级）

### 4.1 `BackgroundTaskManager` trait（agent-tools 契约层，仿 `subagent_spawner` 注入模式）

```rust
/// 后台任务管理器契约（AI 侧工具与壳层实现的解耦边界）
/// 注：与 `BuiltinToolConfig.subagent_spawner`（mod.rs:53-57）同一注入范式；
/// 壳层实现，agent-tools 只持 trait 引用；None = 未接线，保持现状（超时即杀）。
#[async_trait]
pub trait BackgroundTaskManager: Send + Sync + std::fmt::Debug {
    /// 把已 spawn 的 child 转交后台托管（模式 2 / 3 共用入口）
    async fn adopt(&self, req: BackgroundAdoptRequest) -> Result<BackgroundTaskRef, ToolError>;
    /// 查询任务列表（REQ-B01；include_finished=false 只返回活跃）
    async fn list(&self, include_finished: bool) -> Result<Vec<BackgroundTaskInfo>, ToolError>;
    /// 查询单任务状态与尾部日志（REQ-B02）
    async fn status(&self, task_id: &str) -> Result<BackgroundTaskStatus, ToolError>;
    /// 按行范围读取日志（REQ-A05；start_line=None 读尾部 max_lines 行）
    async fn read_log(&self, task_id: &str, start_line: Option<u64>, max_lines: u64)
        -> Result<LogSlice, ToolError>;
    /// 向任务 stdin 写入（REQ-B03；末尾自动追加 \n，除非 append_newline=false）
    async fn send_input(&self, task_id: &str, text: &str, append_newline: bool)
        -> Result<(), ToolError>;
    /// 两阶段终止（REQ-B04：优雅 → 5s → 强制）
    async fn kill(&self, task_id: &str) -> Result<KillResult, ToolError>;
}

/// adopt 请求（模式 2 / 3 共用；所有权转移，kill_on_drop 已关闭）
pub struct BackgroundAdoptRequest {
    pub child: tokio::process::Child,   // kill_on_drop=false，stdout/stderr 管道仍在

    pub cwd: PathBuf,
    pub is_daemon: bool,                // 模式 3：run 结束不回收
    pub resource_monitor: bool,         // REQ-A04
    pub owner_run_id: Option<String>,   // run 关联（审计与过滤用，不级联杀）
}

/// adopt 结果

    pub task_id: String,   // task-<seq>，命名风格对齐 pty id（pty/mod.rs:104-111），命名空间独立

}
```

### 4.6 日志目录约定（REQ-A05，`REQ-AB-现状分析.md` §7.4 直接采用）

```
<app_dir>/logs/tasks/<task_id>.log          # 后台任务完整输出（append，UTF-8，decode_console_bytes 口径）
<app_dir>/logs/tasks/<task_id>.meta.json    # 元数据（status/startedAt/lineCount/lastOutputAt/exitCode/prompt/行数 checkpoint）
<app_dir>/logs/tasks/<task_id>.samples.jsonl # 资源采样（A04，可选）
<app_dir>/logs/sessions/<session_id>/<ts>-<seq>.log  # 同步命令截断落盘（A03，与任务日志共用 read_log 语义）
```

- **行数索引**：转发器每写 512 行在 `.meta.json` 记一次 offset checkpoint；`read_log` 尾部读取走 `file_info` 拿 size → `read_chunk` 从尾回退 64KB → 完整行边界（复用 `take_suffix_bytes` 的字符边界语义，`tool_output.rs:144-157`）；精确行号走 checkpoint 二分定位；checkpoint 只做快速定位不做精确断言（进程崩溃时索引滞后，读到索引末尾回退文件实际末尾）。
- **保留语义**：任务终止（killed/completed/failed）不删 `.log`；30 分钟归档只清内存条目与 `.meta.json`。
- **日志轮转**：单文件上限 100MB，超限截断头部（保尾，与 A03 保尾语义一致）——首版护栏，长期运行守护进程必做。
- **摘要模板**（REQ-A05 4 点）：`任务 <id> 已运行 <duration>，日志已累积 <line_count> 行，最近输出时间 <timestamp>`。

#### T-AB-16 健康判定三态 + 通知（A04 4.2/4.3）

- **文件域（对接现有模块）**：`apps/agent-workbench/src-tauri/src/background.rs`（判定逻辑 + 通知投递）；只读复用：`crates/session-loop/src/steering/nudge.rs:172-238`（`PendingNudgeChannel`）、§4.5 事件形状（冻结接口 #4）。
- **内容**：
  1. **三态判定**（仅对启用 `resourceMonitor` 的任务，在采样 loop 内）：`Healthy`——CPU 活跃或最近 N 秒内有输出（N 默认 60s）；`Suspicious`——CPU 近零 + 超过 M 秒无输出（M 默认 60s，可配）；`Crashed`——非零退出码（由转发器终态触发，非采样判定）；
  2. **Suspicious 通知**：转 Suspicious 时投递「任务 <id> 疑似卡死（<M> 秒无输出），请确认是否终止」——通道一：nudge 排队（`PendingNudgeChannel::enqueue`）；通道二：发射 `task-suspicious` 事件（Soft 分级）；同任务防抖（同一任务只在状态保持期间通知一次，恢复 Healthy 后重置）；
  3. **Crashed 通知**：非零退出 → 投递「任务 <id> 异常退出（exit code N），附最后 20 行日志」——尾部日志直接复用 `read_log(None, 20)`（T-AB-09 已实现）；发射 `task-failed` 事件（Critical）；
  4. **严格不做**：不自动杀、不自动降级超时（对齐 REQ 4.3 禁止清单）；「立即唤醒」消费在 T-AB-18，本任务只保证检测与投递；
  5. **误报面控制**：编译类命令（cargo build 长时间无输出属正常）会被误报——通知文案注明「由 AI 裁决，系统不自动终止」，AI 看到通知后自行判断。
- **验收命令**：`cargo test -p crish-agent-workbench`
- **验收断言**：新增测试 `health_suspicious_detected`——注入短 silence 阈值（如 2s）的静默任务 → 采样周期内转 Suspicious，nudge 队列收到通知且同任务不重复通知；`health_healthy_no_false_positive`——持续输出或高 CPU 任务不产生 Suspicious 通知；`health_crashed_notified`——非零退出任务收到 Crashed 通知且附最后 20 行；`health_no_autokill`——Suspicious 判定后进程仍存活（显式断言不自动杀）。

### 8.3 诚实边界（实现文档必须标注，不得隐藏）

1. **Unix 资源采集口径**：`/proc` 进程树聚合退化为「主进程 + RUSAGE_CHILDREN」近似，与 Windows Job 聚合存在数值口径差异（跨平台不承诺等价）；
2. **Windows 优雅终止**：`taskkill /T`（无 /F）发送关闭请求，纯控制台进程可能直接忽略——测试以「两阶段路径可执行」而非「优雅一定成功」为准；
3. **stdout/stderr 交错顺序**：两流独立管道，日志顺序为「到达序」近似，行前缀 `[out]` / `[err]` 区分来源；
4. **I/O 采集**：`io_read_bytes/io_write_bytes` 首版恒 0（Windows 进程树聚合繁琐，列为可选）；
5. **行数索引**：进程崩溃时 checkpoint 滞后，索引只做快速定位不做精确断言。
