# 06 · 日志层与崩溃恢复 —— 可追溯性与原子化观测审计

> 战役：agent 循环过程的全链路可追溯性与原子化观测（2026-08-14）
> 维度：日志层与崩溃恢复（tracing 上下文 / 日志-事件时间对齐 / panic 与 crash 留痕 /
> 崩溃恢复链连续性 / redact 影响）
> 审计方式：只读代码检查，不参考任何外部软件。产出本文档，不修改代码、不提交 git。
> 审计范围：`crates/conex-telemetry/`（全模块）、`crates/session-loop/`（run 循环与 handlers 日志点）、
> `crates/orchestrator/`（restore / recovery 域 + events 落库）、`crates/agent-tools/`（审计日志点）、
> `apps/agent-workbench/src-tauri/`（main.rs 接线 / core_run_commands / engine_build）、
> `crates/conex-db/`（events 表 schema）、`crates/conex-types/`（AgentEventEnvelope）、

## 一、结论摘要

**现状总貌**：项目存在两条平行的记录通道——

1. **事件通道（权威链）**：SQLite `events` 表（session_id + 会话内自增 sequence + event_type +
   payload），payload 内每事件携带 session_id + ISO8601 毫秒时间戳；发射时经
   `AgentEventEnvelope` 注入 runId + sequence（conex-types/src/events.rs:1109-1120）。恢复域、
   steering、工具调用、恢复阶梯的**全部关键动作**都以事件落库。
2. **日志通道（tracing）**：`conex-telemetry::init_default` 安装 compact 格式双通道
   （stderr + 按日文件层，subscriber.rs:47-96）。全仓仅 **2 处手动 span**
   （`run`@drive_run_loop core_run_commands.rs:5316、`session_loop.run`@loop_exec.rs:23），
   **0 处 `#[instrument]`**；其余 ~200 处日志点中带显式上下文字段的比例低。

**「日志-事件双通道能否统一追溯」判定：当前不能，只能人工近似对齐。**

- 两侧**没有共享 trace id**（全仓 grep `traceId/trace_id/spanId` 零命中）；事件侧有会话内
  sequence 可排序，日志侧无任何序列。
- 关联键只有 (session_id, run_id) + 时间窗：日志毫秒级/微秒级时间戳与事件毫秒级 payload
  时间戳同源（都是 SystemTime UTC），可对齐到 ±ms；但 events 表行级 `created_at` 是
  SQLite `datetime('now')` **秒级**精度（schema.rs:23），不能用于精确对齐。
- 日志侧的 run 上下文（span 字段）依赖**线程本地 `span.enter()`**：tauri 异步运行时为
  tokio 多线程，future 在线程间迁移后 span 上下文即丢失；且 spawned 任务
  （approval.rs:427/451、summary_dispatch.rs:487、summary_coordinator.rs:175、
  escape_watch.rs:363、safe_point.rs:475、spawn_blocking summary_dispatch.rs:595）
  **从不继承 span**。后果：同一 run 的日志行「有时带 session_id/run_id、有时不带」，
  丢失是不确定、不可复现的——这正是可追溯性的大忌。
- 按 session_id 过滤日志做「单个 run 的完整日志」**不可行**；需要事件表 + 日志 + 时间窗
  三方人工拼图。

**崩溃恢复链（事件侧）是完整的**：进程重启 → restore（in-flight → interrupted，`run-interrupted`
审计事件携带 previousStatus 落库、序列续接无空洞、cursor=sequence-1）→ steering 恢复条目
（主 run「上次被重启打断，请继续」自动续跑；子代理「重派/接管/放弃」）→ watcher 拉起。
用户**能从事件流看出「这个 run 曾经崩溃过」**（run-interrupted 事件 + 对话内 steering 文案 +
日志「重启恢复完成」），但**没有**「恢复续跑的 run Y ← 被打断的 run X」的结构化关联字段——
链是人工可拼的，不是机器可查的。恢复域（recovery.rs 阶梯 1-4）在日志侧**零日志**，只在事件侧。

**意外发现（新增缺口）**：`cleanup_logs`（7 天 / 50MB / 3 个 crash 文件保留策略）在
**运行期无任何调用点**——main.rs 未接线，仅 lib.rs 重导出 + 自测调用。策略是死代码，
日志目录与 crash 文件会无限累积。

**crash 留痕**：panic hook 写独立 crash 文件（timestamp/thread/location/message），
文件名带秒级时间戳，与当日日志文件可时间对齐；但无 backtrace、无「最后 N 条日志」、
无活跃 run/session 上下文。`catch_unwind` 产物 `stack: None`（crash.rs:82）。

### 2.4 结构性缺失

- **turn_index 在日志侧零出现**：turn-start/turn-end 只在事件侧（prepare_turn.rs:70、

- **tool_call_id 在日志侧零出现**：工具执行只落事件（tool-start/end + envelope runId），
  日志侧（含 security.audit）无 tool_call_id。
- **orchestrator 主流程几乎无日志**：全 crate 仅 8 处 tracing（restore_manager 3 /
  events 3 / flow_graph 2）；run 分派、steering 队列、goal 评估、**恢复阶梯（recovery.rs 0 处）**
  全部只走事件通道。排查「某个 run 为什么这样走」时，日志侧对编排层是**空白的**。

## 三、崩溃留痕与恢复链现状

### 3.1 crash 文件内容（panic_hook.rs:93-116）

```
Crash report (conex-telemetry)
timestamp: YYYYMMDD-HHMMSS（UTC 秒级）
thread: <线程名>
location: file:line:col
panic_message: <载荷文本>
---
<载荷原文>
```

- 文件名 `crash-YYYYMMDD-HHMMSS-<thread>.log`，时间戳唯一防覆盖，**不轮转**；
  保留最近 3 个由 `cleanup_logs` 负责——**但该函数未接线（见 §6.6），实际不清理**。
- 与当日日志 `workbench.YYYYMMDD.log` 可时间对齐（文件层每条日志 open/append/close，
  进程崩溃不丢已写行），能还原「崩溃前发生了什么」**到日志粒度**。
- **缺失**：① 无 backtrace（`catch_unwind` 的 `stack: None`，crash.rs:82）；② 无活跃
  run/session 上下文（崩溃时正在跑的 run_id 不落盘）；③ 无最后 N 条日志快照；
  ④ 若 panic 发生在 spawned 任务（approval/summary），线程名是唯一线索。
- panic hook 同时发射 `tracing::error!(target: "panic", panic_message/panic_location/panic_thread)`
  （panic_hook.rs:68-74）——**这条日志在当日日志文件里有**，与 crash 文件互为冗余/交叉验证。

### 3.2 恢复链全流程（事件侧完整）

```
进程崩溃
  ↓ 重启（main.rs 初始化 tracing + panic hook）
run_restore（core_run_commands.rs:3716）
  ├─ RestoreManager::restore（restore_manager.rs:42）
  │   ├─ 快照加载（损坏回退 .prev，restore_snapshot.rs:296-310）
  │   ├─ runs 扫描 → in-flight（queued/initializing/running/awaiting-approval/
  │   │   cancelling/completing）→ interrupted
  │   │   ├─ update_run_status（failed/cancelled + reason=daemon-restarted）
  │   │   └─ append_event `run-interrupted`，payload 含 previousStatus/status/reason/
  │   │      error/timestamp（restore_manager.rs:84-115；序列续接 max+1 无空洞，
  │   │      cursor=sequence-1，T12.2/T12.3）
  │   ├─ session_agents running 行归一 failed + ended_at（restore_manager.rs:125-159，
  │   │   PERSIST-02 P1-3）
  │   ├─ 增量事件重放（逐会话锚点 session_last_sequence，P1-1）+ 叶子移动/压缩护栏
  │   └─ pending 输入 FIFO 恢复
  ├─ seed 序列预热（core_run_commands.rs:3694-3707）
  ├─ 恢复成功立即保存快照（:3734）
  ├─ 阶梯 2 通知重排入队（:3779「恢复阶梯 2 通知重排完成」）
  ├─ enqueue_restore_entries（:2871）：主 run → steering 条目
  │   「上次被重启打断，请继续」（RESTORE_MAIN_INJECT_TEXT，自动续跑）；
  │   子代理 run → 「子代理 run X 在重启时被中断，请决策：重派 / 接管 / 放弃」；
  │   父归属查不到 → 仅 warn 日志（:2904）
  └─ watcher spawn（:3803-3807）
```

**「用户能否从事件流看出曾经崩溃」：能。** 三处信号：① `run-interrupted` 审计事件
（previousStatus 可追溯）；② 对话内 steering 恢复条目文案；③ 日志「重启恢复完成」
（mode/interrupted 计数）。**但**：被打断的 run 与续跑的 run **无结构化关联字段**
（无 `resumed-by` / `resumes-from`），链靠 steering 文本与时间人工拼接；子代理 run 的
归属解析失败时只留日志，事件侧无对应。

### 3.3 测试覆盖（crash_consistency.rs）

T12.1-T12.8 + 扩展全部在**事件侧**断言：杀进程恢复状态映射、审计序列连续无空洞、
cursor 口径、半写快照回退、取号单调、终态唯一、写失败不假装可回放、pending FIFO、
flow 预算/恢复 Episode 跨重启、kill_all 一致性、running 归一、spawn 后崩溃不双跑。
**日志侧零断言**（observability.rs 只断消息文本「run 启动/收场」，不验证 span 字段是否
真的出现在输出行里——见 §5.7）。

## 四、脱敏影响

**接线点（call-site 打码，非 subscriber 级过滤）**：

- `core_backend.rs:329`：remote source 命令经 `redact_text` 打码后入事件与日志（红线 7）；
- `ws.rs:568`：WebSocket 连接 token 经 `redact_token`（sha256 前缀 12 hex）；
- 配置面 K-05：provider key 末 4 字符（`redact_provider_key`）。

**对可追溯性的影响（正面为主）**：

1. **确定性打码不破坏关联**：`sha256_prefix_12` 同输入恒同输出——同一令牌在日志/事件/
   审计中的掩码形态一致，**可按掩码前缀跨记录 join**；last4 同理。追溯能力保留。
2. `redact_text` 的形态判定（≥43 字符 [A-Za-z0-9_-] 运行 / CXN- 配对码 / sk- 前缀）
   有「过度脱敏安全优先」设计——**非敏感**的长 base64/长 hex/长标识符也会被整段吞掉
   （redact.rs:97-99），排查时若日志中出现 `<redacted>` 会丢失内容细节（概率低，因日志
   一般不打印长内容）。
3. **覆盖面风险（主要问题）**：redact 只在 2 个接线点生效。若其它路径把敏感物带进日志
   （如 provider 错误文案回显 URL query、工具输入回显、认证失败信息），**无兜底过滤**
   ——`redact_log_scan.rs` 是测试级逐行扫描（tests/redact_log_scan.rs），不是运行期
   日志管线的一部分。安全基线 D5 §6.3 的「日志/审计面只允许摘要形态」目前依赖各发射点自律。
4. 对排查的负面影响有限：**过度打码 < 漏打码**。排查所需的 session_id/run_id/sequence/
   error_code 等结构字段不在脱敏形态内，不受影响。

## 五、日志-事件对齐缺口（逐项）

1. **无统一 trace id**：事件 envelope 有 runId/sequence（wire 层），日志 span 有
   session_id/run_id（字段层），两者**无公共标识**；跨通道关联只能靠 (session_id, run_id)
   近似 + 时间窗。全仓无 traceId/spanId 概念（唯一命中是前端 ToolMetadata.traceId，
   非链路追踪）。
2. **时间精度不对齐**：日志 µs（tracing-subscriber datetime.rs:234 `.{:06}Z`）；事件 payload
   ms（now_iso_utc）；events 表行 `created_at` **秒级**（schema.rs:23）。对齐粒度被事件侧
   限制为 ms 级；行级 created_at 无法参与对齐。
3. **事件 sequence 与日志无对应**：日志行没有「对应事件 sequence」回写；把日志行钉到
   事件链上的某一步，只能靠时间窗猜测。
4. **turn_index / tool_call_id 只在事件侧**：日志行归不到轮次与工具调用（§2.4）。
5. **span 上下文不确定性丢失**（最严重）：`span.enter()` 线程本地 + 多线程运行时线程迁移
   - spawned 任务无 instrument → 同一 run 的日志行上下文时有时无，**按 run_id grep 日志
     的结果不可复现**。这是「从任意节点回溯整条链」的直接阻碍。
6. **编排层日志空白**：orchestrator/recovery 域 8 处日志覆盖，恢复阶梯零日志——
   日志侧无法单独讲述「恢复怎么走的」，必须查 events 表。
7. **无日志侧回归测试**：observability.rs 只断言消息文本；span 字段渲染/上下文传递无任何
   自动化保障，未来重构（如换 formatter、加 layer）不会触发红测。
8. **日志保留策略未接线**：cleanup_logs 无运行期调用点（全仓 grep 仅 lib.rs 重导出与
   file.rs 自测）——7 天/50MB 轮转清理与 crash 保留 3 个的语义在生产失效，长期运行
   磁盘增长不可控；清理策略本身（crash 保留 3 个）反而可能先于排查删掉旧崩溃现场。

## 六、建议方向（只给方向，不做方案选型）

1. **统一关联键**：让日志侧可携带事件侧锚点（sequence / run_id / turn_index / tool_call_id），
   或建立 run 级 trace id 在两侧同源注入；目标是「一条日志行可钉到事件链的唯一步」。
2. **span 传递加固**：以 `#[instrument]` / `.instrument()` 取代 async fn 内的 `span.enter()`
   （线程迁移安全）；spawned 任务（approval/summary/escape_watch 等）显式 instrument；
   落实 26-frontend-observability-audit.md P2 已定稿的字段名约定。
3. **补关键日志点**：restore 逐条 interrupted 留痕（当前只落 DB 事件）、recovery 阶梯 1-4
   每次升级、tool 执行带 tool_call_id、turn 边界带 turn_index。
4. **时间对齐标准化**：日志与事件共用同一时间戳格式/精度来源；events 表 created_at
   升到毫秒级，使行级时间可参与对齐。
5. **crash 留痕增强**：crash 文件补 backtrace、活跃 run/session 上下文、最后 N 条日志快照；
   `catch_unwind` 的 `stack: None` 补栈信息。
6. **清理接线**：`cleanup_logs` 挂到启动路径（main.rs 已设 log_dir），让保留策略真正生效。
7. **脱敏覆盖审计**：梳理全部日志发射点，评估 subscriber 级过滤层或逐点补齐；
   维持确定性掩码（不破坏关联）。
8. **可观测性测试资产化**：把「日志行携带 session_id/run_id」写成 LogCapture 断言进 CI，
   防 span 上下文回归；崩溃一致性测试补日志侧断言。
