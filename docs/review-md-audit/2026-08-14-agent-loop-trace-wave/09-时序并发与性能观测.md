## 一、结论摘要

**「时序还原与性能观测能力」判定：部分具备，存在结构性缺口。** 具体拆解：

| 能力                  | 判定        | 一句话说明                                                                                                                                                      |
| --------------------- | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 会话内事件全局总序    | ✅ 具备     | sequence 会话级原子计数器（session_sequence 表 + UNIQUE 约束），全局单调连续、跨 run 不重置（Q23 并发取号测试证明无冲突）                                       |
| 单 run 有序时间线还原 | ⚠️ 部分具备 | 实时路径（信封 runId）完整；**持久化路径缺 run 归属**——events 表无 run_id 列、payload 为裸事件（仅 run-terminal 事件体带 runId），并发交错时无法直接按 run 过滤 |
| 耗时统计              | ✅ 大体具备 | 工具/turn/run/子代理/审批/压缩均有 start/end 时间戳配对；**message-start/end 与 provider 请求发出点无时间戳**，首字节与请求排队时长不可精确测                   |
| token/成本观测        | ⚠️ 部分具备 | run 级完备（runs v5 列 + cache-stats-updated 事件）；**turn 级明细缺失、消息级 usage_json 写侧是前端、runs 表无模型列**                                         |
| 背压丢弃可补全性      | ⚠️ 大体安全 | message-delta 有 message-end 全文兜底（无「只丢增量、无终态」）；**task-heartbeat 无任何兜底**；任务域 7 事件整体不落库                                         |
| 用户输入可追溯性      | ❌ 缺失     | 输入队列覆盖最旧**静默无留痕**；pending_inputs 表在**生产路径无任何写入者**，恢复机制无数据源                                                                   |

最核心的三个缺口（影响战役目标本身）：

1. **持久化事件流无 run 归属列**（`events` 表）——「从任意节点回溯整条链」在并发场景（主 run + 多个子代理 run 共会话交错）下断链。
2. **事件体时间戳与落库 created_at 双源异质**——事件体是 ISO8601 毫秒（发射时取），events.created_at 是 SQLite `datetime('now')` 秒精度（落库时取），格式不同（空格分隔、无毫秒无 Z）。
3. **用户输入（含被覆盖输入）完全无留痕**——RingBuffer 覆盖静默、pending_inputs 无生产写者。

### 2.2 同源性判定

- **同源（一个时钟）**：全部 ISO 字符串与 epoch 毫秒均出自 `std::time::SystemTime::now()`（session-loop 与 orchestrator 各有一份 `now_iso_utc` 实现，算法相同、精度同为毫秒）。跨来源对齐在**毫秒级**可行（ISO 毫秒 ↔ epoch 毫秒一一可换算）。
- **异源（异常）**：仅 `events.created_at` 例外——SQLite 内置 `datetime('now')`，**秒精度**且格式与 ISO 不同（空格分隔、无毫秒、无时区后缀）。这是全系统唯一精度低于毫秒的时间戳来源，且是事件落库行的默认列。
- **时间语义差**：事件体 timestamp 在「发射时」取，events.created_at 在「落库时」取，两者差距 = 序列化 + SQL 写库耗时（毫秒级，慢 store 下可放大，见 `events.rs` 测试 `queue_persistent_events_wait_for_store` 的 40ms/条场景）。

### 2.3 结论

- 跨来源对齐**可行**（同一系统时钟），但 `events.created_at` 会让对齐精度降级到秒；对需要毫秒级排序的复盘（如同一秒内多个工具事件）必须依赖事件体 timestamp 而非 created_at。
- `session_messages.timestamp` 依赖前端写入时机与前端时钟语义，不能作为引擎权威时间线（引擎权威消息时间线在事件流 message-start/message-end 与内存 cache）。

## 三、并发交错还原能力评估

### 3.1 事实基础

- **序列分配**：会话级原子计数器（`session_sequence` 表，`conex-db/events.rs:72-99` reserve_sequence；`persist.rs:239` SessionSequencer）。会话内全局单调连续，跨 run 不重置（`events.rs` 测试 `sequences_continue_across_runs_in_session`：R2 首事件 seq=4 续接）。
- **并发真实存在**：子代理 run 与主 run **同会话**运行——`subagent_spawner.rs:457` 的 run 创建用 `session_id: req.parent_session_id.clone()`；flow_graph 的 `parent_session_id` 同父会话。Q23 测试 `concurrent_runs_reserve_unique_sequences` 明确验证同会话双 run 并发取号唯一。
- **事件归属的信息分布**：
  - 实时（内存）路径：信封 `runId` 在 emit 时注入——主 run 事件 runId=主 run（`core_run_commands.rs:5447-5451`）；子代理事件 runId=子代理 run（`core_run_commands.rs:3602-3606`）；任务域事件 runId=None（`bg_events.rs:259`）。前端按 runId 过滤（`core_query_commands.rs:599` 退役命令 `core_read_run_events`）。
  - 持久化路径：`events.rs:189` `serde_json::to_string(&event)` 存**裸事件**——只有 `run-terminal` 事件体自带 runId，其余 48 种事件 payload 无 run 归属；信封的 runId/sequence 不落库（`conex-types/events.rs:10-12` 明确「顶层 runId/sequence 不在事件体内，由 emit 层注入」）。

### 3.2 单 run 时间线还原

| 场景                                 | 还原方式                                                                                                   | 可行性                                                                                                             |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 串行 run（同会话依次执行）           | runs 表按 created_at 升序，每个 run 的 cursor 与上一 run cursor 形成连续序列区间 `[prev_cursor+1, cursor]` | ✅ 成立（events 测试证明区间连续）                                                                                 |
| 并发 run（主 run + 子代理 run 交错） | 区间启发式失效：交错区间无法归因到具体 run                                                                 | ❌ **不可还原**——events 表无 runId 列、payload 无 runId，且 message/turn/tool 事件体无 run 或 subagent_run_id 字段 |
| 子代理边界锚点                       | subagent-started/ended 事件体带 `subagent_run_id`                                                          | ✅ 可锚定子代理生命周期起止，但中间的 turn/message/tool 事件无法归属                                               |
| 实时复盘（run 存活期内）             | 信封 runId + sequence                                                                                      | ✅ 完整；但 sequence 混合多 run（全局交错），按 runId 过滤后**每个 run 内部不再连续**                              |

### 3.3 还原复杂度评估

- 排序键 = sequence（会话内全局单调）→ **全局总序天然存在**，这是现有设计最强的一点。
- 但「给定 run_id 重建该 run 的有序时间线」需要：① 实时期才有 runId；② 持久化后只有 run-terminal 带 runId；③ 消息级落库（session_messages）无 run_id 列。
- **结论**：从 events 表出发的**事后**单 run 还原，在存在子代理/并发 run 的会话中**不可行**（或只能给出「该 run 序列区间内的全部事件超集」）。要补齐需在持久化面引入 run 归属（列或 payload 注入），并让子代理事件与父 run 建立显式关联（subagent-run 会话树已在 session_agents 表，但 events 表未引用）。

## 五、背压丢弃影响面

### 5.1 三层分类体系（存在三套口径）

| 层                 | 机制                                              | 分级                                                                                                                                           | 代码                         |
| ------------------ | ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| 持久化分流         | `EventClass`（events.rs:48-58）                   | NonPersistent = message-delta + subagent-event(progress)；**其余全部 Persistent**（含 task-output/heartbeat——但它们实际不进 EventQueue，见下） | `orchestrator/events.rs:48`  |
| 事件缓冲（实时桥） | `DropClass`（buffer.rs:36-42）                    | Soft = **仅 message-delta**；其余 Critical 永不丢                                                                                              | `buffer.rs`                  |
| 背压注册表         | `BackpressureLevel`（conex-types/events.rs:1043） | Delta = message-delta、subagent progress、task-output/heartbeat；Soft = subagent message/tool、task-suspicious、timer-cancelled；其余 Critical | `conex-types/events.rs:1043` |

**不一致点**：subagent progress 在注册表标 Delta，但缓冲层只认 message-delta 为 Soft（progress 在缓冲层实际不可丢）；任务域 Delta（task-output/heartbeat）在持久化分流层被归 Persistent——但**任务域事件实际不走 EventQueue**（`bg_events.rs:259` 信封 runId/sequence 全 None、仅 bridge 直发 + 唤醒消费，`task_event_consumer.rs:89` 无 append_event），因此任务域 7 事件**事实上全部不落库**，与注册表「task-started/completed/failed/killed = Critical 必达落库」的表述不符。

### 5.2 丢弃影响面清单

| 事件                                                                | 落库？                       | 丢帧面                         | 事后补全                                                                        | 「只丢增量、无终态」？                                   |
| ------------------------------------------------------------------- | ---------------------------- | ------------------------------ | ------------------------------------------------------------------------------- | -------------------------------------------------------- |
| message-delta                                                       | ❌ 不落库                    | 缓冲层可丢（仅此一类）         | ✅ message-end 全文兜底（Critical 必达）                                        | 否（终态兜底完整）                                       |
| subagent-event(progress)                                            | ❌ 不落库                    | 缓冲层不丢（但注册表标 Delta） | ⚠️ subagent-ended.summary（概要非全文）；progress 载荷只实时可见                | 否（started/ended Critical 必达；progress 内容本身丢失） |
| subagent-event(message/tool)                                        | ✅ 落库（Soft 尽力）         | 缓冲层不丢                     | ✅ 终态补全                                                                     | 否                                                       |
| task-output                                                         | ❌ 不落库（绕开 EventQueue） | 无缓冲丢帧                     | ⚠️ task-completed.line_count / task-failed.tail（最后 20 行）——**中间内容丢失** | 否（终态存在，增量内容丢）                               |
| task-heartbeat                                                      | ❌ 不落库                    | 无缓冲丢帧                     | ❌ **无任何兜底**（资源采样只有实时事件）                                       | ✅ **是**——唯一真「只丢增量、无终态」                    |
| task-suspicious                                                     | ❌ 不落库（Soft 尽力投递）   | 无缓冲丢帧                     | ⚠️ 留痕语义未落地                                                               | 否（有 task-failed/killed 终态）                         |
| task-started/completed/failed/killed                                | ❌ 不落库（绕开 EventQueue） | 无缓冲丢帧                     | ❌ 终态本身无落库（唤醒摘要走 steering 面）                                     | 否（事件本身必达实时，但**无持久化痕迹**）               |
| 其余 Critical（agent/turn/tool/message-end/审批/审计/恢复/goal 等） | ✅ 落库                      | Critical 永不丢                | ✅                                                                              | 否                                                       |

### 5.3 结论

- message 域增量丢弃**安全**（message-end 全文兜底，测试锁定）；子代理 progress 内容丢失但生命周期锚点（started/ended）必达。
- 任务域是重灾区：7 事件全部无持久化，其中 **task-heartbeat 是真「只丢增量、无终态」**（无任何事后补全手段）；task-output 中间行不可复原。
- 实时桥丢帧（Soft 水位）只影响 UI 实时流，不影响落库回放——两个 drop 面语义不同，复盘时需区分「从未落库」与「实时被丢」。

## 六、建议方向（只给方向，不做方案选型）

1. **持久化事件补 run 归属**：events 表加 run_id 列（或在 payload 统一注入信封 runId）——这是单 run 时间线还原的前提；顺带修复 `core_read_run_events` 类按 runId 过滤失效的问题。
2. **事件时间戳统一收口**：评估把 events.created_at 改为显式毫秒 ISO（或 epoch ms）写入，消除与事件体 timestamp 的格式/精度双轨；message-start/message-end 补 timestamp 字段（需走事件 schema 变更登记）。
3. **补 provider 请求级锚点事件**（请求发出 → 首字节），或把 turn-start 前移为「请求构造起点」，让 provider 等待时长可测——对「排查循环过程中的改进部分」直接相关。
4. **turn 级 usage 落库**：TurnEnd 或独立事件携带本 turn usage（prompt/completion/cache），支撑逐 turn token 分析；runs 表补 model 列（成本分析必需维度）。
5. **输入可追溯性**：RingBuffer 覆盖时留痕（计数/日志/事件三选一）；确认 pending_inputs 的生产写入者或废弃该恢复面——当前恢复机制是空转。
6. **任务域事件落库决策**：task 终态（completed/failed/killed）是否应进 events 表（与注册表 Critical 口径对齐）；task-heartbeat 至少落一条会话级资源采样摘要，消除「只丢增量、无终态」盲区。
7. **两套分级口径收敛**：缓冲层 DropClass 与 backpressure 注册表对齐（或明确「注册表只管持久化、缓冲层只管实时」并在文档注明）。
8. **性能观测统计面**：把缓冲丢帧计数、输入覆盖计数等观测计数做持久化汇总（当前仅 tracing 日志），供事后复盘。
