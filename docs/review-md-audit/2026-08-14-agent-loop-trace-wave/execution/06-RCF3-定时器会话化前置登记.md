## 二、现状（2026-08-14 实测）

1. **事件体 sessionId 恒为空串**：timer/cron 发射点构造事件时 `session_id: String::new()`（timers.rs:198-209 区域，注释自述「注册表每引擎一个、无会话归属；会话归属语义在 R-CF3 定时器会话化时定稿」）；cron 域同构。
2. **FK 硬约束**：events 表 `(session_id, sequence)` 主键 + `FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE`——空串 sessionId 无对应 sessions 行，`EventQueue::push` 落库必然失败。
3. **无 run 可标 failed**：EventQueue 的失败收口语义（`fail_event_store` → `failed(event-store-write-failed)` 终态链）天然绑定 run 状态机；timer/cron 无 run 上下文，失败后无终态可标，强行落库会把 FK 错误拖入不存在的失败收口链。
4. **无可用持久化通道**：timer/cron 事件目前仅入 `AgentEventSink` / `SchedEventSink` 缓冲（timers.rs / sched.rs），经 `forward_drained_events`（engine_channels.rs:492-506）信封直发实时桥；不经任何 `EventQueue::push`。task 域落库通道（PC-02 走 D-01 规范化落库点，run_id=NULL + type 标签）为「无 run 持久化通道」的现成参照形态，R-CF3 翻转时可复用（不新建 reserve_sequence 直写通道）。

## 三、为什么本战役不落库（论证，引用 04 方案 PC-01）

04 独立方案 PC-01「落库的阻塞论证」（`independent-plans/04-独立方案-落库覆盖视角.md:43-47`）三条，本登记原样引用：

1. **FK 硬阻塞**：空串 sessionId 强行落库 FK 必失败 → `PersistError` → 拖入 run 失败收口链；而 timer/cron 没有 run 上下文（无 run 可标 `failed(event-store-write-failed)`），EventQueue 失败收口语义天然绑定 run 状态机，定时器域**不存在可用的持久化通道**。
2. **前置决议缺失**：落库需要「挂哪个会话」的答案。事件体 `session_id` 空串是注册表级设计（每引擎一个），会话化决议属于 **R-CF3 定时器会话化**（timers.rs 注释自认「未定稿」）——跨域契约变更，超出本战役落库视角单一决策范围。
3. **「不假装」原则一致性**：挂着 Critical 分级却不落库，比「显式声明不落库」更不诚实；与 PC-06「不假装可回放」同一哲学（R-27）。

**本战役定案（R-22）**：timer/cron **明确不落库**，但完成三类契约面收口——① 伪 runId 契约对齐（wire 缺键漂移消灭）；② 「仅实时轨」分级标注（分级语义保留 = 实时桥必达，持久化决策正交独立声明）；③ 本登记（前置依赖移交，不砍项）。

**读取面声明（PC-01 完成定义④）**：timer/cron 触发痕迹的持久事实源 = session_meta `timer_<id> fired=true`（timers.rs 落库键）+ steering 条目（group_id=`timer-<id>` / `cron-<id>`，续 run 链）+ 续 run 的事件链；事件面不承诺历史触发。
