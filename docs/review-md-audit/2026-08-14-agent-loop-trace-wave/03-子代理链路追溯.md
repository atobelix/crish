# 03 · 子代理链路追溯（内部审计）

> 战役：agent 循环过程的全链路可追溯性与原子化观测
> 维度：子代理链路追溯——run_subagent 工具调用 → SubagentStarted → 子代理内部循环 → SubagentEnded 的完整链；parent 链一致性；多层嵌套
> 日期：2026-08-14
> 模式：**只针对内部代码审计**（不参考外部软件），只读检查 + 本文档

---

## 一、结论摘要

**判定：子代理「全链路」存在，但「全链路可追溯」不成立——链条在结构上断裂于两处关键键缺失，且观测面存在「两套事件世界」的分裂。**

- **链路是真实存在的**：run_subagent 工具调用（父 run 的 tool-start/tool-end）→ spawner 落库 + 发射 SubagentStarted → 子代理独立 run（走 `run_task_impl` 同通道的完整 session-loop，独立 run id + 独立会话）→ 收口发射 SubagentEnded。每一段都有代码路径与落库。
- **但没有任何一个「动作」拥有完整、连贯、单一的链条记录**：
  1. **parent_tool_call_id 全线恒 None**（工具直调 `subagent/tool.rs:430-431`、flow 调度 `flow_graph.rs:1033`、recovery fork `recovery.rs:516-517` 三个构造点全部硬编码 None）。`SubagentStarted.parent_tool_call_id` 与 `session_agents.parent_tool_call_id` 列因此恒空——**从 SubagentStarted / SubagentEnded 无法反查触发它的父工具调用**，子代理与父 turn 之间的唯一结构化桥缺失。
  2. **持久化事件无 runId**：`events` 表只有 `(session_id, sequence, event_type, payload)`，payload 是纯事件体（`orchestrator/src/events.rs:189`）。runId 只存在于 wire 广播面信封。回放时信封 runId 恒 None → 无法按 run 切片、`read_run_events_impl`（C04 run-events 端点）的 runId 过滤实际只会命中 run-terminal（事件体自带 runId），其余事件恒被过滤掉。
  3. **子代理内部动作在父会话侧不可观测**：父会话只有 started/event/ended 三事件；`subagent-event` 的 message/tool 类（Soft 级落库语义）**没有任何发射方**，唯一发射点是收口时一次性补发的 kind=progress（截断文本 + 工具名列表，无 tool_call_id、无参数、无结果，Delta 级不落库）。
  4. **subagent-started / subagent-ended 只落库不广播**：SubagentEventEmitter 直接 push 进 store（`subagent_events.rs:183-217`），不经任何 run 的事件桥；前端只能靠 cursor 拉取事件表获得，实时性依赖拉取。
- 子代理内部循环是**独立 run**（`sub-run-{depth}-{n}`）落在**独立会话**（`sub-sess-{depth}-{n}`），内部工具调用有完整 tool-start/tool-end 且归属子 run——这半段是完整的；但子会话 id 与 run id 之间**没有显式映射存储**（仅靠同序号命名推导），且从父会话回放视角无法按 run 过滤子会话事件。

诚实边界：本维度检查了事件契约（`conex-types/src/events.rs`）、三个 spawn 构造点、生产 spawner（`apps/agent-workbench/src-tauri/src/subagent_spawner.rs`）、收口链（`core_run_commands.rs` drive_run_loop / on_subagent_run_terminal）、lifecycle（kill_all / kill_subagent / resume）、recovery fork、FlowScheduler、wait 通道、conex-db session_agents/events 读写、事件读侧（core_read_session_events / read_run_events_impl）。**未检查**：前端 subagentHandlers.ts 消费细节（仅凭注释与注册表推断面）、`send_message` 注入后的子代理侧消费路径（E3 属于消息注入域）、push/移动端场景。

## 二、子代理生命线事件序列图

```
父会话（父 run）事件表                    子代理会话（sub-sess-N）事件表
─────────────────────────────            ─────────────────────────────
tool-start  {runId=父run, call.id=C1}
   │  run_subagent 工具 execute
   │  └→ SubagentSpawnerImpl::spawn（subagent_spawner.rs:739）
   │      1. 守卫快照（depth=父depth+1 / siblings / concurrent）
   │      2. session_agents 行落库（parent_run_id 补齐；parent_tool_call_id=None；
   │         subagent_path_json=None；depth=N；status=running）
   │      3. launcher.launch → run_task_impl（同通道）→ 注册 run/sub-run-N、
   │         set_current_run(sub-sess-N)
   │      4. subagent-started（SubagentEventEmitter 落库，runId=父run，
   │         parentToolCallId=None；【不广播】）
   │      5. 工具返回 {subagentId, subagentRunId, sessionId, status} 信封
tool-end   {runId=父run, result=C1}
                                    │
                                    ▼
                              agent-start {runId=sub-run-N}
                              turn-start {runId=sub-run-N}
                              message-start/delta/end
                              tool-start / tool-end（read_file 等内部工具，
                                完整 tool_call_id / 参数 / 结果，归属子 run）
                              …（完整 session-loop，多轮）
                              agent-end / run-terminal {runId=sub-run-N}
                                    │
                                    ▼  收口 drive_run_loop
父会话（父 run）事件表
  subagent-event × N（kind=progress：截断文本+工具名列表；
```

## 三、子代理内部循环可追溯性现状

### 3.1 内部循环：存在且完整，但是独立 run

- 子代理 run 经 `CoreRunStateLauncher::launch` → `run_task_impl`（`core_run_commands.rs:6012-6657`）**同通道完整装配**：SessionLoopProducer、事件队列、审批门、工具注册表（按 task_type 裁剪）、写路径沙箱、配额、上下文注入。产出的 `agent-start / turn-start / message-start/delta/end / tool-start / tool-end / run-terminal` 全套事件落在**子代理自己的会话**（`sub-sess-{depth}-{n}`）事件表，广播信封 runId = 子 run id（`core_run_commands.rs:5447-5452`）。
- 子代理内部工具调用（read_file 等）**有完整 tool-start/tool-end**，含 tool_call_id / 参数 / 结果，归属子 run——**内部这一段的可追溯性是完整的**，前提是知道子会话 id。
- **两套事件世界的分裂**：父会话看到的是「三事件视图」（started / event / ended），子代理真实动作在「子会话视图」。两者之间的桥接键：
  - 正向：`run_subagent` 工具返回信封含 `subagentId / subagentRunId / sessionId`（tool.rs:450-457）→ tool-end output 里有子会话 id，可正向跳转。
  - 反向：`SubagentStarted / SubagentEnded` 事件体只有 `subagent_run_id`，**没有 session_id 字段**；`session_agents` 行（挂在父会话下）也**没有子会话 id 列**。子会话 id 只能靠「同序号命名推导」（sub-run-{d}-{n} → sub-sess-{d}-{n}）或遍历 session index 匹配 `engine_last_run_id=sub-run-N`（spawn 时写入，subagent_spawner.rs:319）——**无专用反查 API**。

### 3.2 观测面：父会话侧只有「收口后补发」的摘要

- `emit_subagent_progress`（core_run_commands.rs:3552-3621）在 **run 收口时**一次性遍历 `outcome.messages` 补发 progress 事件：每条 assistant 消息截断文本（`SUBAGENT_PROGRESS_TRUNCATE_CHARS`）+ 该消息的工具**名列表**（`tool_calls: Vec<&str>`，**无 tool_call_id / 参数 / 结果**）。
- 运行中**没有任何实时事件**；progress 为 Delta 背压**不落库**（`events.rs:180-187`），前端刷新后即丢失。
- `subagent-event` 契约的 `kind=Message / Tool`（Soft 级「尽力落库」）**没有任何生产发射方**——grep 全仓 `emit_event` 唯一生产调用点即 E3-2 的 progress 发射。注册表里声明的 message/tool 落库语义是空转的。
- 推论：从父会话事件表回放，子代理「内部发生了什么」只有截断文本 + 工具名列表；完整证据（参数/结果/增量）在子会话事件表，但子会话事件表回放时**无 runId**（见 §四），只能时间窗粗筛。

### 3.3 子代理消息的持久化双轨

- 子代理会话对话：由子 run 正常收口落子会话消息表（完整，可查）。
- `session_agents.messages / session_agent_messages`（父会话侧快照）：**生产代码无任何写入方**（spawn 落库时 `messages: Vec::new()`；on_subagent_terminal 只改 status/ended_at/summary；唯一写方是前端显式保存命令 `session_commands.rs:246`）。这直接影响 resume_subagent 的任务推断（见 §五）。

## 四、parent 链一致性审计

| 字段                                  | 来源                                                                                                                           | 是否一致                                          |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------- |
| `session_agents.parent_run_id`        | spawner 落库：`req.parent_run_id` 优先，否则 `resolve_parent_run`（按 current_runs 会话定位补齐，subagent_spawner.rs:253-262） | ✅ 与事件信封 runId（父 run）同源                 |
| SubagentStarted 信封 runId            | `SubagentEmitContext.parent_run_id` = resolve_parent_run 结果                                                                  | ✅ 与行 parent_run_id 同源                        |
| `session_agents.parent_tool_call_id`  | `req.parent_tool_call_id`（三个构造点恒 None）                                                                                 | ❌ 恒 NULL（生产路径）                            |
| `SubagentStarted.parent_tool_call_id` | `started_info_from_spawn` 透传 request 值（subagent_events.rs:242）                                                            | ❌ 恒 None（生产路径）                            |
| `session_agents.depth`                | 守卫深度（父 run 内存 depth+1；主 run=0）                                                                                      | ✅ 与守卫判定同源（仅内存态，崩溃恢复后靠行重建） |
| `session_agents.subagent_path_json`   | **唯一写方** = recovery fork（recovery.rs:545）；spawner 落库恒 None（subagent_spawner.rs:703）                                | ❌ 非 fork 路径恒 NULL                            |

**核心结论：parent_run_id 链一致且可用；parent_tool_call_id 链全线断裂（设计上预留了字段与事件位，但三个 spawn 构造点都未接线）。**

从 SubagentStarted 反查触发它的 tool-call 与 tool-end 结果（成功/失败）：

- 结构化路径：**不存在**。`parent_tool_call_id=None`，tool-end 的 result（含 `isError`、output）与 subagent 之间没有键。
- 非结构化路径：父 run 的 tool-end（run_subagent 的 output 含 subagentId/subagentRunId 信封）做文本匹配可以正向/反向桥接，但这是「文本 grep」，且回放时受 runId 缺失影响（§四.2）难以定位到具体父 run。
- 顺带发现：工具直调路径连「工具调用上下文」都没有传给 spawner——ToolContext 中本可携带当前 tool_call_id（工具执行器知道），但 `SubagentSpawnRequest` 无此输入，`flow_node_id` 字段注释也自认「工具直调路径为 None」。

### 4.1 持久化事件无 runId（全局性断裂，影响本维度全部回溯）

- `EventQueue::push` 落库 payload = `serde_json::to_string(&event)`（**纯事件体**，`orchestrator/src/events.rs:189-195`）；`events` 表无 run_id 列（conex-db `schema.rs:39-46`）。
- 读侧 `parse_envelopes`（core_query_commands.rs:500-508）直接反序列化 → 信封 runId 恒 None（run-terminal 例外：事件体自带 runId 字段，反序列化后信封可见）。
- 后果：
  - `core_read_session_events`（前端唯一事件读取面）返回的信封 runId 大多缺失 → 前端「多 run 并发过滤」失效（events.rs:1093-1097 自述的兜底语义）。
  - `read_run_events_impl` / `core_read_run_events`（C04 `GET /v1/runs/{id}/events`）按 `envelope.run_id == run_id` 过滤 → **除 run-terminal 外恒空**，run 事件分页端点实际失效（该命令已退役，前端改走会话事件面，但 remote 面仍引用）。
  - 事件重放 / 审计落底时无法按 run 切片，也无法「给定 SubagentEnded 回溯其父 run 的完整事件流」。

## 五、嵌套 / 终止 / 失败路径的缺口

1. **嵌套（depth 2+）不存在——守卫硬禁止**：`DEFAULT_RECURSION_GUARD.max_depth=1`（guard.rs:27-31），子代理发起 spawn → `NestingDenied`（`subagent.nesting_denied`）。所以「孙代理事件链」问题在工具面被消灭；`subagent_path_json` 的「工作流路径」语义（SessionTree 根→叶）与深度守卫**不是同一机制**，且：
   - 初始 spawn 恒 None（含 flow 调度路径）；仅 recovery fork 写入 → **字段语义与写入时机不配套**。
   - `resume_subagent`（lifecycle.rs:382-388）`leaf_from_path(subagent_path_json)` 对**任何未经 fork 的子代理恒返回 None → InvalidState「缺少工作流路径」→ resume_subagent 对普通 spawn 的子代理恒失败**（显式命令面实际不可用）。
   - `derive_task`（lifecycle.rs:479-487）依赖 `row.messages`（生产恒空，见 §3.3）→ 即使 path 补上，无显式 prompt 时任务推断也失败。
2. **timeoutMs 是死参数**：run_subagent 解析 `timeoutMs` → `SubagentSpawnRequest.timeout_ms`（tool.rs:384,430）→ **引擎侧无任何消费方**（SubagentRunConfig / RunTaskOptions / spawner 均无此字段）。「超时」概念不存在，子代理只能靠 kill 面（L3 强停）终止。
3. **kill 路径的事件时差与状态归并**：
   - kill_all / kill_subagent（lifecycle.rs）只做「行归一 failed + L3 投递」，**不发射任何事件**；run 收口时由 drive_run_loop 统一发 run-terminal（子会话，Cancelled）与 subagent-ended（父会话）。
   - `on_subagent_run_terminal`（core_run_commands.rs:2525-2539）把非 Completed 全部映射为 Failed：**`SubagentEndStatus::Cancelled` 在生产路径不可达**（事件契约里声明了 cancelled 语义，实际只会出现 completed/failed）。
   - kill 后行状态先 failed、收口时 on_subagent_terminal 再写一次 failed——两次写面最终一致，但期间存在窗口。
4. **spawn 启动失败路径事件缺失**：`spawn_unchecked` 中 launch 失败 → 行归一 failed + 工具返回错误；**无 subagent-started、无 subagent-ended**（emit_started 在 launch 成功之后）。行存在但事件链为空。
5. **flow 路径双发射防护**：flow 调度 spawn 时 spawner 不发射 started（`flow_node_id.is_some()` 跳过），由 FlowScheduler 发射（flow_graph.rs:1068-1097）；收口同理（spawner 不双发 ended，flow_graph.rs:1194-1231）。M14「唯一发射方」约束在 flow 与非 flow 两路各自成立——**但如果 flow 调度器实例未装配 subagent_events（Option），该子代理将完全没有 started/ended 事件**（flow_graph.rs:1068 的 `if let Some(emitter)` 静默跳过）。
6. **subagent-started / ended 不广播**：两事件只落库（`SubagentEventEmitter` 直推 store），不经 run 事件桥；前端实时性依赖 cursor 拉取。与子代理 run 内部事件（广播 runId=sub-run-N）和 tool 事件（广播 runId=父 run）的投递路径不同——同一链条三段三种投递形态。

## 六、建议方向（只给方向，不做方案选型）

1. **补齐 parent_tool_call_id 接线**：在工具执行器把当前 tool_call_id 注入工具上下文（三个 spawn 构造点统一补齐），使 `SubagentStarted.parent_tool_call_id` / `session_agents.parent_tool_call_id` 成为真键；并考虑在 SubagentEnded 上回填/携带触发 tool-call 的结果（成功/失败）语义位。
2. **持久化事件带 runId**：给 events 表加 run_id 列（或 payload 存完整信封），统一读侧合成信封，恢复「按 run 切片回放」能力；这同时修复 C04 run-events 端点与前端并发过滤。
3. **打通子会话映射**：在 session_agents 行上显式落子会话 id（或提供 sub-run → sub-sess 反查 API），消除命名推导；事件契约（SubagentStarted/Ended）考虑携带 session_id。
4. **子代理内部动作的实时/落库观测**：为 message/tool 类 subagent-event 接上真实发射方（运行中增量，而非收口补发）；或明确定义「子代理内部细节以子会话事件流为准」并补齐跨会话导航能力——二选一，避免当前「两边都看不到」。
5. **终止/失败路径的事件一致性**：统一「行状态写」与「事件发射」的顺序与归并规则（kill 直发 ended？spawn 失败补发 ended？cancelled 是否作为真值出现），消除行存在但事件链空、以及 cancelled 语义空转的问题。
6. **死参数与死路径收口**：timeoutMs 或实现或移除；resume_subagent 对 subagent_path_json 恒 None 的依赖需要重新设计（要么初始 spawn 就写路径，要么 resume 的 fork 源叶子推导改道）；`subagent-event` 的 Soft 落库语义若长期无发射方，应在注册表/契约层标注「未启用」而非装作可用。
