## 一、结论摘要

前端事件消费面**结构清晰、双面（per-run + 全局）隔离设计完备**，但「用户视角全链路可观测程度」为**中低（部分可观测）**：

- **用户能看到的**：对话正文/思考流、工具调用卡片（含状态与 diff）、审批卡、run 级失败横幅、子代理面板（状态/摘要/消息/工具进度）、后台任务/定时器/Cron/缓存统计/安全审计（RuntimePanel）、用量与编排 DAG（默认关）。
- **用户看不到的**：**run 级完整时间线不存在**——turn-start/end（轮次结构）、agent-start、工具批（batch）、tool-update、tool-input-repaired、上下文压缩、检查点、runtime-steering（steering 提示）、runtime-intervention-required（干预提示）、recovery-_（恢复阶梯）、goal-_（goal 轮次）全部无 UI 展示；其中 recovery-_/goal-_ 共 8 类事件**连解析层都进不来**（生成绑定缺 8 类 → parseErr → 丢弃登记）。
- **事后排查能力弱**：UI 无「本次 run 完整记录视图」；排查只能靠 console `[crish-stream]` 日志 + `window.__crishStreamDiag()`（40 条环形缓冲，不持久化）。
- **实测发现 CI 红灯**：`eventParser.normalizer-drift.test.ts` 3 项失败（recovery-escalated 样本不可解析）——生成事件绑定（41 类）与 Rust 注册表（49 类）**未同步**，`continuityHandlers.ts`（goal 投影 / 熔断横幅 / 子代理失败卡）为**死代码**（仅测试引用，未接分派表）。

判定：**引擎侧有完整、带 sequence 的事件留痕（可回溯性好），但前端观测面只消费了「消息 + 工具 + 审批 + 终态」主路径**，agent 循环内部动作（轮次、压缩、检查点、steering、恢复、goal）在 UI 上近乎不可见，且依赖前端本地快照的子代理/观测数据不抗崩溃重开。

## 二、事件消费架构（接收 → 分发 → 消费/丢弃）

### 2.1 接收面（唯一通道）

- `TauriTransport.onMessage`（`src/api/transport/tauriTransport.ts:204-210`）：懒订阅 `listen('workbench-run-event')`（`:30`、`:314`），payload 为 Rust emit 的**顶层平铺 JSON** `{ type, runId, sessionId, sequence, ... }`（`:13-17`），`JSON.parse` 后 fanout 给所有 listener（`:325-331`）。无 WS、无重连（进程内核心）。
- 消费方共三类（同一 fanout 上的不同订阅）：
  1. **per-run EventRouter**（每次 `streamViaEngine` 一个实例，`ConnectionLifecycle.ts:702-711`）；
  2. **数据面全局路由** `ensureDataPlaneRouter`（`dataPlaneRouter.ts:154-166`，装配于 `useEngineState.ts:176`）；
  3. **子代理面全局路由** `ensureSubagentPlaneRouter`（`dataPlaneRouter.ts:276-288`，装配于 `useEngineState.ts:181`）。

### 2.2 分发链

```
transport.onMessage fanout
├─ per-run EventRouter.onMsg（EventRouter.ts:92-132）
│   ① runId 归属过滤（:98，messageBelongsToRun）
│   ② parseBridgeEvent 单一解析（eventParser.ts:937-977）
│      = 生成解析器 parseEngineEvent（严格）→ ENGINE_NORMALIZERS（宽容）→ legacy 信封（subagent-*/error）
│   ③ 消费侧幂等去重（:125-131，consumedEvents Set）
│   ④ dispatchEvent（dispatch.ts:146-158）→ engineDispatchTable 41 键 / legacyDispatchTable 4 键
│   ⑤ 数据面类型 return 防双写（EventRouter.ts:85-88）
├─ dataPlaneRouter.handleDataPlaneMessage（dataPlaneRouter.ts:121-148）：只处理 10 类数据面事件，无 runId 过滤
└─ subagentPlaneRouter.handleSubagentPlaneMessage（dataPlaneRouter.ts:217-268）：
    观测 agent-start/agent-end/run-terminal 维护 _liveParentRuns（:211-235）；
    父 run 活跃 → 跳过（per-run 优先）；父 run 已收口 → 全局兜底消费
```

### 2.4 关键缺陷：recovery-_/goal-_ 8 类事件断链（实测确认）

- Rust 注册表 `crates/conex-types/contracts/engine-events.json` 已登记 **49 类**事件（id 42-49 = recovery-* ×5 + goal-* ×3，含字段形状与 backpressure）；`crates/conex-types/src/events.rs:810-940` 有对应变体；`src/device/events.rs:62-117` 已定义三种脱敏策略（Transparent/Redacted/Tuple）并说明「D8 登记面」。
- 生成 TS 绑定 `packages/shared-types/src/generated/engine/events.ts` 仅 **41 类**（`ENGINE_EVENT_TYPES`），**未包含**这 8 类 → `parseEngineEvent` 拒绝 → `ENGINE_NORMALIZERS`（eventParser.ts:470-930）无对应键 → 实时到达即 `parseErr` → `registerUnknownEvent` 丢弃。
- `continuityHandlers.ts` 实现了真实消费逻辑（goal-* 投影 session.goalMode、recovery-escalated → 熔断横幅/子代理失败卡 errorKind/retries），**但未出现在 dispatch.ts 的 import 与分派表中**（dispatch.ts:15-71 无引用），生产路径不可达 = 死代码；仅被测试直接调用。
- **实测**：`node node_modules/vitest/vitest.mjs run apps/crish-desktop/src/api/chat-bridge/handlers/eventParser.normalizer-drift.test.ts` → **3 failed / 8 passed**，首个失败样本即 `recovery-escalated`（其余 7 个连续性样本同因）。
- 影响判定：goal-* 按 D8 设计走 BufferedRunEventBridge **实时发射**（continuityHandlers.ts:6-8 注释），若引擎已发射则前端实时丢弃；recovery-* 按 D8 为 append_event 直写（实时 emit 不发射），检索面（core_read_session_events）**当前无任何前端消费者读取恢复域事件** → 恢复阶梯过程对用户完全不可见。

## 三、runId / sequence 机制现状

### 3.1 runId

- **生成**：前端自管（`ConnectionLifecycle.ts:677`：`run-${Date.now().toString(36)}-${random}`），经 `core_run_task` 下发，Rust 以请求携带的 runId 回发事件信封。
- **回填**：`onRunMeta` → `setEngineLastRunId`（sessionMessageActions.ts:337-344），用途：审批 scope（sessionMessageActions.ts:405-408）、RuntimePanel activeRuns 归属（useRuntimePanelData.ts:80）、子代理 runId 回填（types.ts:475-481）。
- **过滤**：`messageBelongsToRun`（eventUtils.ts:30-39）：**runId 缺失/空白 → 放行（广播语义）**；匹配 → 消费；foreign → 丢弃。过滤点在 `EventRouter.onMsg:98`。
- **多 run 并发语义**：每个 run 一个 router，只消费自己 runId + 无 runId 广播事件。广播事件（数据面 10 类）靠 per-run 路由对数据面类型的 `return` 防双消费（EventRouter.ts:85-88）；**但 per-run 路由不做 sessionId 过滤**，且**未列入数据面白名单的未来无 runId 广播事件会被每个存活 router 各消费一次**（潜在双写面）。
- 单 run 视图切换：无显式 run 选择器；「当前 run」即最近一次发送。

### 3.2 sequence

- **live 路径：前端不校验 sequence**（EventRouter.ts:100-104 注释：F5-12 已删除游标死代码；顺序契约由引擎单通道——Tauri IPC 串行 + Rust 背压缓冲——保证；**无乱序缓冲、无缺口检测、无重放**）。
- **消费侧幂等去重**：`consumedEvents` Set（每 router 实例），键 = `buildEventDedupeKey`（EventRouter.ts:166-189）：`type:messageId:sequence`（收口轨）→ 缺 sequence 退化 `type:messageId`（实时轨，**存在多轮 turn 同 messageId 误伤面**，代码自注）→ 无 id 无 sequence 的事件不参与去重（legacy 透传）。重复事件静默跳过 + `recordStreamDiag` 计数。
- **重放/水合（引擎侧游标）**：`hydrateSessionMessagesFromEngine`（sessionEventHydrate.ts:450-508）经 `core_read_session_events`（`fetchSessionEvents`，afterSequence 游标，800 事件/页 × 50 页上限 = 4 万事件；hasMore 停滞防御 + truncated 截断态）。`engineCursor` 持久化到会话索引（sessionCrudActions.ts:216-219），仅会话激活且 `needsEngineMessageHydrate` 时触发一次全量分页拉取（sessionCrudActions.ts:194-236）；**无基于 engineCursor 的增量同步循环**（H3 注释所述「增量同步」未实现）。
- `projectEventsToMessages`（sessionEventHydrate.ts:155-405）只投影 message-end/delta、tool-start/end 四类（白名单见 `agentEventFromOrchestrator` :39-52）——**subagent-\*、approval、compression、steering、run 级事件均不投影**。
- **诊断侧**：`streamDiag` 环形缓冲 40 条（streamDiag.ts:22-67），console `[crish-stream]` warn + `window.__crishStreamDiag()`；不持久化。

## 五、子代理与历史会话观测缺口

### 5.1 子代理展示链路（完整）

```
subagent-started/event/ended（信封 runId=父 run）
├─ per-run 面：subagentHandlers.ts:28-73 → useStreamCallbacks 回调 →
│   applySubagentStarted/Event/Ended（streamCallbacksEvents.ts:53-117）→
│   upsertSessionAgent / applySubagentEventToAgent / patchSessionAgentToolStatus（sessionAgentActions.ts:30-185）
└─ 全局面（父 run 收口后兜底）：subagentHandlers.ts:92-164 → 同一组 store action（防双写：同 id 已存在则跳过）
```

- **字段链路**：subagent-started 消费 `subagentId / subagentRunId / runId(父) / parentToolCallId / description / mode`（subagentHandlers.ts:28-43）；subagent-event 消费 `subagentId / subagentRunId / event`（:45-59），event 经 `applySubagentEventToMessages`（subagentTimeline.ts:106-238）投影到 agent 消息时间线——**只认 message-delta/message-end/tool-start/tool-end 4 类子事件**，其余（progress 类）忽略；subagent-ended 消费 `status（cancel/stop/abort→stopped；fail/error→failed；其余 completed）/ summary`（:61-73）。
- **展示**：AgentTeamBoard（侧栏切换：状态圆点/摘要/工具进度/时长，AgentTeamBoard.tsx:74-215）、AgentCard / InlineAgentPanel（消息列表含 thinking/text/toolCalls、失败摘要行、恢复按钮位——但恢复按钮数据源 recovery-escalated 不可达，属死代码链）、父工具卡「协作进行中…」（applySubagentStarted :78-88）。
- **幽灵命令**：`sendToSubagent` / `getSubagentStatus` 显式不可用（subagentApi.ts:16-33，Rust 无实现）→ `useAgentStream.ts:448-499` 的 daemon 状态轮询恒 null，**子代理终态完全依赖 subagent-ended 事件 + 全局面路由**；全局面路由依赖 useEngineState 单例 refcount——若没有任何组件挂载 RuntimePanel/OverviewCard（refcount=0），全局路由退订，父 run 收口后的子代理事件即断流。
- **内存上限**：store 内 `upsertSessionAgent` 硬截断 40 个 agent（sessionAgentActions.ts:51）；agent 消息 `MAX_MESSAGES_PER_AGENT` 截断；LS 镜像截断 40（sessionLocalStorage.ts:174-183）+ 截断标志留痕（sessionAgentsTruncation.ts）；SQLite 主路径全量保存、超 40 写 `agents_over_cap` meta（sessionRustDbSql.ts:303-308）。

### 5.2 历史会话水合

- **路径**：boot `hydrateSessionsFromRust`（sessionRustDbHydrate.ts:116-171，index + bodies + agents 并行加载，SQLite 优先、LS 回退）→ 激活会话时 `needsEngineMessageHydrate` 触发 `hydrateSessionMessagesFromEngine`（引擎事件回放，游标分页）→ 消息按 id 合并（mergeMessagesById，sessionEventHydrate.ts:118-149）。
- **agents 水合**：`load_session_agents` → `parseSessionAgent`（sessionHydration.ts:314-355，缺 id/subagentRunId/parentSessionId/parentRunId 即丢弃）→ `hydrateSessionAgents`（:450-464，running→stopped + sanitize + 「上次会话中断」摘要）。

### 5.3 缺口清单

1. **子代理历史不可重放**：引擎事件回放白名单只含 message*/tool*（sessionEventHydrate.ts:39-52）；subagent-*（含其消息/工具/进度）**不投影**。子代理记录恢复依赖前端本地 `save_session_agents` 快照——崩溃前未落盘的子代理活动、跨会话存活的子代理在重开后**永久丢失**（引擎事件表有留痕但无前端读取面）。
2. **审批历史不水合**：approval-requested/resolved 不进投影；重开后工具卡只保留 approvalMeta/决策落点，审批 AskCard 不恢复。
3. **压缩/检查点/steering 历史不可见**：事件留痕存在，但无任何前端消费者读取（recovery-* 检索面无消费方）。
4. **run 历史不展示**：run-terminal 不进投影，UI 无历史 run 列表/时间线；runId 仅存 engineLastRunId（最近一次）。
5. **运行期观测 store 全内存**：securityAuditStore、cacheEventsStore、timer/cron 摘要、streamDiag 环形缓冲均不持久化——重开即丢。
6. **engineCursor 无增量同步**：只有「激活时全量分页拉取」一次；长会话增量补事件机制未实现（H3 注释所述未落地）。
7. **截断面**：agent 40 上限（store 硬截断 + LS 截断）会导致超限旧子代理在 UI 上消失（SQLite 全量保存但 store 层已截断，重开会话恢复不回）；LS 截断有标志留痕但 UI 无提示。
8. **幽灵命令依赖**：子代理续聊失败后 `sendToSubagent` 恒失败（显式不可用），自动降级 startFollowUp（独立 run）；状态轮询恒 null 使「daemon 同步」形同虚设。

## 六、建议方向（只给方向，不做方案选型）

1. **同步生成绑定 + 接线连续性域**：把 recovery-_/goal-_ 8 类补进生成 TS 联合（重新跑 generate-engine-bindings）、补宽容归一器、注册 dispatch 表、接线 continuityHandlers（goalMode 投影 / 熔断横幅 / 子代理失败卡）；修复 drift 测试红灯（当前 3 failed）。这是**可验证的 CI 缺陷**，优先级最高。
2. **run 级时间线/日志面板**：消费 turn/agent/压缩/检查点/steering/审批事件，提供「本次 run 完整记录」视图（用户与开发者两个视角）；作为事后排查的 UI 落点，替代仅 console 的现状。
3. **sequence 真游标与增量补事件**：live 路径若引入乱序通道需补真游标（代码自注）；基于 engineCursor 实现增量同步循环（H3 语义落地），避免「激活时全量分页」的延迟与开销。
4. **子代理历史重放**：引擎事件回放白名单扩展 subagent-*（或新增子代理会话检索面），让崩溃/重开后子代理记录可恢复；同时把 40 硬截断改为可配置/可检索。
5. **运行期观测 store 持久化**：securityAudit / cacheStats / timer-cron 摘要 / streamDiag 落盘（或接入会话级事件检索），保证事后排查数据不因重开丢失。
6. **广播事件归属加固**：per-run 路由补 sessionId 过滤或类型白名单，防未来无 runId 广播事件在多 run 并发时被每个 router 重复消费。
7. **熔断/干预提示激活**：为 runtime-intervention-required / recovery-escalated 提供真实 UI 落点（当前用户无法感知「需要介入」与「熔断」），使恢复过程可观测。
