## 一、结论摘要

**判定：持久化链路能支撑「会话级、按 sequence 回溯」的追溯，但不能支撑「按 run 回溯」与「从库还原完整信封」。** 全链路可追溯性在三个面上断链：

1. **按 run 断链（最严重）**：events 表无 run_id 列，且落库 payload 是**裸事件体**（不含信封 runId/sequence/schemaVersion）。读取侧（`core_read_run_events` / `read_run_events_impl`）按 `envelope.run_id` 过滤，结果只有 `run-terminal`（事件体自带 runId）与 `run-interrupted`（payload 恰好有 runId 字段）能命中——**一个 run 的完整事件链经现有 API 只能取回终态事件那一行**。
2. **事件域断链**：timer-fired / cron-fired / task-output / task-heartbeat / task-suspicious 等事件**从不落库**（发射路径止于 EventBridge 广播；定时器事件 sessionId 为空串，连 FK 都过不了）。定时器/cron 在 run 结束后触发、后台任务输出——这些「动作」在 events 表无任何痕迹。
3. **读取面断链**：run-interrupted（restore 写）与 recovery-* 五类事件（recovery_store 写）**落库了但读取 API 解析不出**——payload 无顶层 `type` 标签，`parse_envelopes` 直接丢弃。审计事件躺在库里但对任何事件读取接口不可见。

**已闭合的（值得肯定的）**：会话级 sequence 原子取号 + UNIQUE 双保险、delta 不阻塞 drive loop、落库失败 → `failed(event-store-write-failed)` 不假装可回放、终态复用失败序列不留空洞（Q25）、崩溃恢复（T12.1–T12.8）全部有测试锚定、孤儿清理护栏齐全。这些单点机制是坚实的，断链集中在「事件归属建模」与「读取契约」两层。

## 二、按 run 查询路径现状与能力评估

### 2.1 现状（证据链）

**Schema 层**（`schema.rs:141-149`）：events 表只有 `(session_id, sequence)` 组合主键 + `event_type` + `payload` + `created_at`，**无 run_id 列**。runs 表有 `cursor`（终态序列），但没有「起始序列」。

**写入层**（`orchestrator/src/events.rs:189-193`）：`EventQueue::push` 落库 payload = `serde_json::to_string(&event)`——**裸事件体**。信封（runId/sequence/schemaVersion）只在**线面**构造（`events.rs:7479-7483` 的 `AgentEventEnvelope::new(event, Some(run_id), Some(sequence))` 只用于 bridge 广播）。注释声称「run 归属内嵌在 payload 的 runId 字段」与实际不符：**49 种事件里只有 run-terminal 的事件体带 runId 字段**，其余（agent-start/end、message-_、tool-_、turn-_、approval-_、subagent-*、security-audit 等）事件体均无 runId（`conex-types/src/events.rs` 各变体字段定义可证）。

**读取层**（`core_run_commands.rs:7540-7590` 与 `core_query_commands.rs:568-610`）：

```
query_events(session, after)   // 全量加载：Store trait 不下推 limit（persist.rs:697-713 传 None）
  → parse_envelopes            // serde 逐条解析为 AgentEventEnvelope（失败丢弃）
  → 按 envelope.run_id == Some(run_id) 过滤   // ← 断链点
  → paginate（内存 take）      // 分页在过滤之后，先全量后切片
```

结果：agent-start / message-start / message-end / tool-start / tool-end / turn-* / approval-requested 等全部被过滤掉；**readRunEvents 实际返回 ≈ 每条 run 一行 run-terminal**。

### 2.2 数据量大时的能力

- 10 万+ 事件的会话：每次 `readRunEvents` / `readSessionEvents` 都要**全量读出 + 全量 serde 解析**全部事件后才切片——O(n) 全表扫描 + O(n) JSON 解析，与 `maxEvents` 分页参数无关（limit 只在内存里生效）。
- `conex-db::query_events` 有 `limit` 参数（`events.rs:33-38`），但 `Store` trait 面未下推（`persist.rs:697-713` 恒传 `None`）——该参数只被 conex-db 层测试用到。
- 没有任何索引支持 JSON 内 runId 过滤；唯一可用索引是 `(session_id, sequence)` 主键前缀（会话 + 序列区间查询可用，但按 run 的序列区间未知）。

### 2.3 「导出某个 run 的完整事件链」现有 API 是否够用

**不够用**。可行的替代路径与代价：

- **runs.cursor 区间推导**：runs 表只存终态 cursor，不存起始序列；需按 `created_at` 排序取前一 run 的 cursor+1 做起点，且 run 之间可能插入 run-interrupted / recovery-* / 未来事件，区间归属不精确；仍需自己全量 parse payload 并在内存过滤——与现有 API 等价的工作量，且游标区间语义无文档锚定。
- **直接查库 + 自研过滤**：可行（payload 里 agent-start/run-terminal 等有 runId 的事件可作锚点分段），但完全绕开现有 API，且事件体无 runId 的多数事件只能靠「上一锚点后的序列区间」猜测归属。

结论：**「按 run 导出完整事件链」这一战役目标，当前代码路径上不可达成**，需要先补「事件归属」的数据建模。

## 三、持久化覆盖矩阵（事件类 → 是否落库 → 丢失影响）

| 事件类                                                                                                                                                                                                                      | event_class             | 背压级        | 是否落库               | 落库/发射路径                               | 丢失/降级影响                                                                      |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------- | ------------- | ---------------------- | ------------------------------------------- | ---------------------------------------------------------------------------------- |
| message-delta / thought-delta                                                                                                                                                                                               | NonPersistent           | Delta         | **否**                 | 桥广播（T09.1 实时轨，sequence=None）       | 流式过程不可复现；message-end 全文可补全（hydrate 依赖）                           |
| subagent-event · progress                                                                                                                                                                                                   | NonPersistent           | Delta         | **否**                 | 桥广播                                      | 子代理进度过程丢失；started/ended 仍在                                             |
| task-output / task-heartbeat                                                                                                                                                                                                | Persistent*（**误判**） | Delta         | **否**（实际）         | 壳层节流 → EventBridge                      | 后台任务输出事件面无痕；任务日志文件是唯一来源                                     |
| task-suspicious                                                                                                                                                                                                             | Persistent*             | Soft          | **否**（实际）         | 壳层 → EventBridge                          | 卡死告警无事件面留痕                                                               |
| timer-fired / cron-fired / timer-cancelled                                                                                                                                                                                  | Persistent*             | Critical/Soft | **否（从不）**         | 缓冲 → 桥广播；sessionId 为空串             | 定时器/cron 触发无事件面持久化；唯一痕迹 = session_meta `timer_<id>` 的 fired=true |
| run-interrupted（restore 写）                                                                                                                                                                                               | —（直写）               | —             | **是，但读取面不可见** | restore_manager 直写 payload=InterruptedRun | 库里可见、任何事件 API 读不出（无 type 标签）                                      |
| recovery-* ×5（recovery_store 写）                                                                                                                                                                                          | —（直写）               | Critical      | **是，但读取面不可见** | reserve_sequence 自取号直写 payload=裸 JSON | 同上                                                                               |
| run-terminal / agent-start/end / turn-* / message-start/end / tool-* / compression-* / approval-* / checkpoint-* / security-audit / subagent-started/ended / task-started/completed/failed/killed / goal-* / cache-* / 其余 | Persistent              | Critical      | **是**                 | EventQueue::push 同步等待落库               | 无                                                                                 |

_标注「Persistent_」= `event_class()` 判 Persistent，但事件实际不经过 EventQueue（发射路径在壳层直连桥），故未落库——**两套分类系统（event_class vs event_backpressure）集合不一致**（见 3.1），当前靠「不经过队列」侥幸一致，属隐患而非错误。

### 3.1 双重分类漂移（隐患）

`event_class`（orchestrator/src/events.rs:48-58）与 `event_backpressure`（conex-types/src/events.rs:1043-1079）是两套独立分类：

- 背压 Delta 集合 = {message-delta, subagent progress, **task-output, task-heartbeat**}；
- 持久化 NonPersistent 集合 = {message-delta, subagent progress}。

task-output / task-heartbeat / task-suspicious / timer-cancelled 在 `event_class` 里都判 **Persistent**。若未来任何接线把它们引入 EventQueue（例如「任务事件统一走队列」），会瞬间把**每行任务输出全部落库**并大量消耗会话序列号。建议方向见第六节 3。

### 3.2 delta 不落库的影响评估（核心问题 b）

- **message-delta**：对「事后复现」的影响 = 丢失流式过程（分块节奏、中途内容），**最终态由 message-end 全文补全**——桌面 hydrate（sessionEventHydrate.ts）只消费 message*/tool*，message-end 是恢复依据，**补全是成立的**。
- **例外缺口：崩溃中途的半条消息**。message-start 已落库、message-end 未发出（run 中途崩溃）→ 该消息在事件面不可复原（无全文）；session_messages 是前端 350ms 持久化窗口写的，也不保证。这是「复现完整链路」的一个真实空洞。
- **subagent progress**：过程不可复现；子代理最终产出经 subagent-ended summary（父会话事件）与子会话的 message-end（子会话事件）补全，**补全成立**。
- **task-output**：无任何事件面补全（任务日志文件是唯一事实源，事件面设计上就放弃了）。

### 3.3 payload 完整性（核心问题 f）

- payload = 完整事件体（全部字段 camelCase 原样），**body 层不裁剪**；message-end 含全文 AgentMessage。
- **信封层裁剪**：runId / sequence / schemaVersion **不在 payload**。从库行读事件：
  - sequence → 在行级 `sequence` 列（可还原）；
  - schemaVersion → 恒 1（可推导）；
  - **runId → 仅 run-terminal（事件体自带）/ run-interrupted（payload 含）可还原，其余全部丢失**。
- 更糟的是读取面输出：`parse_envelopes` 解析出的信封 `sequence=None`（payload 无该字段）→ `envelope_to_value` 序列化时**不注入 sequence** → **EventPage 输出的 wire 事件普遍缺 sequence 与 runId 两个信封字段**（03 §5.1-2/3 宣称的「重放去重与游标的唯一依据」在 DB 读路径上不存在）。游标可用服务端返回的 `next_after_sequence` 续页，但客户端无法按事件内 sequence 对齐实时流与回放流。
- 结论：**从数据库直接读事件不能还原完整信封**。

## 四、迟到 / 失败 / 并发写入的边界情况

### 4.1 迟到事件（核心问题 c）

| 场景                              | 实际行为                                                                                                                                      | 序列/时序一致性                                                            |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 子代理晚完成                      | 子代理事件进**子会话**（sub-sess-* 自己的 events），父会话只有 subagent-started/ended 摘要事件；跨会话追溯靠 subagent_run_id 手工关联，无索引 | 各自会话内 sequence 独立                                                   |
| 定时器/cron 在 run 结束后触发     | steering 条目 → 续 run；**事件面无任何落库**（3 覆盖矩阵）                                                                                    | 无事件，无序列                                                             |
| 审批迟到（run 终态后）            | approval-requested/resolved 都在 run 活跃期经 active run 的 queue 落库；终态后无 active run（服务层行为未追到底，见诚实声明）                 | —                                                                          |
| 恢复域 recovery-*                 | 可在父 run terminal **之后**按 reserve_sequence 续号落库——「run-terminal 之后还有事件」是会话内合法形态                                       | sequence 连续；payload 用 epoch ms（createdAtMs/elapsedMs），无 ISO 时间戳 |
| 崩溃后 restore 的 run-interrupted | 在会话事件流尾部追加（max+1 取号，**不经 session_sequence 计数器**）                                                                          | 见 4.3 并发节                                                              |

**时序一致性（时钟三轨并存）**：events 行 `created_at` = SQLite `datetime('now')`（**UTC 秒粒度、无时区标记**）；payload `timestamp` = ISO8601 毫秒（引擎 `now_iso_utc` 产生）；恢复/任务域 payload = epoch 毫秒。三类时钟并存，**排序必须以 sequence 为准**；created_at 秒粒度无法细排，且与 payload timestamp 可差 ±1s。

### 4.2 落库失败（核心问题 d）

- **链路**：`queue.push` append 失败 → `PersistError{sequence, event_type, error}` → drive_outcome 中断事件流 → `run.fail_event_store`（状态机收口 failed 或已终态翻转）→ 终态事件以**失败序列号** best-effort 重发（Q25 不留空洞）→ `end_reason=event-store-write-failed`。测试锚定：`mid_failure_terminal_reuses_failed_sequence_no_hole`。
- **失败瞬间事件是否丢失**：是——失败的这条事件永久丢失（无重试、无影子副本）；**无任何自动重试机制**（CrishError 的 retryable 标记只用于日志/上报，drive_outcome 不消费）。已落库的中间事件保留（半链），run 以 failed 收口，语义是「不假装可回放」。
- **半链不可回放**：restore 对 failed 终态 run 原样保留，不重放其事件——半链事件仍可从库读出（作为诊断材料），但没有「补全」机制。
- **终态矛盾窗口**：run-terminal 事件落库成功、随后 `finalize` 的 `update_run_status` 失败 → 库里 events 有 `run-terminal(completed)` 而 runs 表仍 running → 重启时 restore 把它打断为 failed(interrupted) → **事件说 completed、记录说 failed**，无对账逻辑（见第五节缺口 1）。

### 4.3 并发写入

- 同会话并发 run 取号：`session_sequence` 原子计数器 + `UNIQUE(session_id, sequence)` 双保险（T08.12 Q23 测试：100 号并发唯一连续）——**闭合**。
- 全部 DB 写经单连接 Mutex 串行化；LocalDbStore 经 spawn_blocking 不占 tokio worker——**闭合**。
- restore 的 run-interrupted 用 `max+1` 取号（restore_manager.rs:280-288，不经计数器）：若计数器已超前（如失败取号后未落库），恢复事件序列可能落在「已取号未落库」的空区间内；不破坏唯一性，但「序列连续无空洞」的 T12.2 语义只在无取号丢弃时成立（T12.5 测试自己承认 7/8 手动取号无事件）。
- 压缩块行：事件落库成功后才写块行（INSERT OR IGNORE 幂等）；**事件与块行之间崩溃 → 块行缺失，且 restore 不重建**（blocks.rs 注释声明「V2 backfill 可重建」——当前无 backfill）。

## 五、跨表一致性审计（核心问题 e）

| 一致性关系                                  | 约束/机制                                                                                       | 状态                                                                                                      |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |

| pending_inputs ↔ runs                       | 可绑定 run_id 也可不绑定（after-current-run）；FIFO 恢复（created_at + id 决胜）                | ✅ 测试锚定                                                                                               |
| 孤儿清理护栏                                | 宽限期 + 引擎子会话豁免 + 活动 run 豁免 + 未决 pending 豁免                                     | ✅ 三道护栏齐全                                                                                           |
| compression_blocks ↔ events                 | 同源同序（sequence = 事件序列）；写失败仅告警；restore 不重建                                   | ⚠️ 崩溃窗口块行缺失无自愈（4.3）                                                                          |
| 事件域 ↔ runs                               | **无 run_id 跨表约束/索引**                                                                     | ❌ 本战役核心断链（第二节）                                                                               |

**crash_consistency 测试覆盖**（crates/orchestrator/tests/crash_consistency.rs，全部通过）：T12.1 in-flight 打断映射、T12.2 审计序列连续、T12.3 cursor=审计-1、T12.4 半写快照回退 + 增量重放、T12.5 恢复后取号单调、T12.6 终态唯一不重发、T12.7 写失败不假装可回放、T12.8 pending FIFO；另有 SQLite 真实重启全周期、flow 预算/recovery Episode 跨重启、kill_all 行终态跨重启、running 行归一、spawn 后崩溃不双跑（T3.4）等扩展。

**缺口清单**（测试未覆盖 / 逻辑无对账）：

1. run-terminal 事件与 runs.status 的对账——restore 不校验「事件终态 vs 记录终态」矛盾（4.2 场景）。
2. compression_blocks 缺失重建（backfill）——restore 明确不重建块行。
3. run 归属建模缺失——无 run_id 列，无按 run 的序列区间（起始序列不落库）。
4. sessions.engine_cursor / engine_last_run_id 无引擎写面、无一致性校验。
5. 读侧对非 AgentEvent 载荷（run-interrupted / recovery-* / legacy 旧格式）无规范化，读取 API 静默丢行（不可见而非报错）。

## 六、建议方向（只给方向，不做方案选型）

1. **事件归属建模**：让「run 归属」成为 events 表第一类数据——方向 A：加 `run_id` 列 + 索引（写面注入，含子代理/无主事件的语义定义）；方向 B：落库 payload 存**完整信封 JSON**（含 runId/sequence/schemaVersion），使 DB 成为可还原信封的单一事实源。二者择一或并用（A 解决查询、B 解决还原）。
2. **按 run 查询修复**：新增/修复按 run 的事件查询（含起始序列落库或 run_id 索引直达），同步修正 `readRunEvents` 契约文档与 mock-daemon（现有「按 runId 过滤会话事件子集」的陈述与实际行为不符）。
3. **统一事件分类**：单一分类函数同时产出「背压级 + 是否落库 + 桥优先级」三个决策，消除 event_class 与 event_backpressure 的集合漂移（task-output/timer-cancelled 等当前靠「不走队列」侥幸不落库）。
4. **定时器/cron 事件落库决策**：二选一并文档化——要么明确「事件面不持久化，痕迹仅 session_meta fired 标记」并让读取面声明；要么补会话归属（去空串 sessionId）后入 events 表。
5. **读取面防御**：对非 AgentEvent 载荷（run-interrupted / recovery-* / legacy 行）做规范化（补 type 标签）或读取 API 显式透出原始行，消灭「落库了但读不出」的静默丢弃。
6. **恢复期对账**：restore 增加 run-terminal 事件与 runs.status 的一致性校验（矛盾时显式上报）；补 compression_blocks 缺失重建（backfill）。
7. **查询性能**：Store trait 下推 limit（避免 10 万+ 事件全量解析）；保持 (session, sequence) 索引；若加 run_id 列则按其建索引。
8. **信封字段回填**：读取面输出补注入 sequence（行级列 → 信封），使 EventPage wire 事件与实时流（03 §5.1-2/3 契约）一致。
9. **时钟统一**：行级 created_at 与 payload 时间戳的粒度/时区不一致——明确「排序唯一依据 = sequence」并在读取面保证，或统一时间格式。
