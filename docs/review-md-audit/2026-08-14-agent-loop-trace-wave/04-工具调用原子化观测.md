# 04 · 工具调用原子化观测审计

> 战役：2026-08-14 agent-loop-trace-wave（agent 循环全链路可追溯性与原子化观测）
> 维度：工具批/单工具的 start/end 配对完整性；耗时、结果、错误、重试可观测性；审批与工具调用关联；入参修复、逃逸监视留痕

## 一、结论摘要

**判定：工具级原子观测「基础达标，实时与细节不达标」。**

**达标部分**：

1. **start/end 配对完整性良好**——遍历执行器全部路径（成功/失败/超时/abort/审批拒绝/过期/取消兄弟项/防御兜底），每一条代码路径都保证 `tool-start` 后必有 `tool-end`，且 `tool-batch-start`/`tool-batch-end` 恒配对（`execute_batch` 单点收尾，`exec_batch.rs:425`）。
2. **单工具四要素可查**：调用参数（`tool-start.call.input` 完整 JSON）、结果（`tool-end.result.output`，text/json/artifacts 三选一）、错误（`is_error` + `error_code` + `error_message`）、状态（`isError` 布尔 + 错误码域）。
3. **batch_id 全局唯一**：进程级静态 AtomicU64 单调递增（`input.rs:22-26`，格式 `batch-<N>`），跨 turn / 跨 run 不重置，事件内可区分批次。
4. **审批-工具调用三环闭合**：`approval-requested(request.toolCallId)` → `approval-resolved(tool_call_id + decision)` → `tool-end(同 call_id)`，被拒/过期工具均有 tool-end。
5. **逃逸监视与工具侧审计有独立实时轨**：`security-audit` 经 `BridgeAuditSink` 实时广播（sequence=None 预览）+ L4 独立落库轨（`core_run_commands.rs:1006-1087`），双轨并存。

**重大缺口（按影响排序）**：

- **G1 失败路径 duration_ms 恒为 0**：`ClassifiedToolResult::error()` 构造器硬编码 `duration_ms: 0`（`tool_events.rs:227-236`），超时 59 秒的工具也记 0——「执行了多久才失败」完全不可观测。
- **G2 事件时间戳是翻译时刻而非执行时刻**：`emit_tool_events` 在 `execute_batch` await 完成后一次性遍历翻译（`executing_tools.rs:204-350`），批内所有 `tool-start`/`tool-end`/`tool-update` 的 timestamp 几乎同毫秒；并行组内 tool-end 按组序（非完成序）排列——**从事件时间戳无法计算执行耗时，也无法重建并行完成的真实顺序**。耗时唯一来源是 `duration_ms`，而它又被 G1 破坏。
- **G3 工具域事件无实时轨**：session-loop 仅 message-delta（DeltaSink）与审批（壳层 gate 广播）、审计（BridgeAuditSink）实时；`tool-start`/`tool-end`/`tool-batch-*` 全部随 run 收口经 `drive_outcome` 一次性落库+广播（`drive_run_loop` 注释「produce 单次覆盖整个 run」，`core_run_commands.rs:5320`）——**run 执行期间前端无法实时观测工具执行**。
- **G4 `tool-input-repaired` 是死事件**：事件变体存在（`events.rs:431-438`）但 Rust 全仓库**无任何生产发射点**（仅测试与白名单引用）；session-loop 也无入参修复逻辑（中间件 `before_execute` 可改入参但不产事件）。
- **G5 requires_approval 重试首次失败 attempt 无留痕**：`execute_single_with_retry`（`exec_single.rs:651-750`）第一次执行返回 ApprovalRequired 时**不产生任何事件**，审批通过后重试只推一次 tool-end——「失败→审批→重试」全过程在事件面只剩 approval-requested 一条，首次 attempt 的失败证据丢失。
- **G6 安全审计事件无法关联工具调用**：`ToolContext` 无 `tool_call_id` 字段（`context.rs:100-144`，只有 session_id/abort_token/ask/…），工具侧 `security-audit`（delete.rs:229、shell_redirect.rs:41）`tool_call_id` 恒 None；逃逸 `undeclared-write` 也恒 None（工具外语义）且 `write_claims` 声明以 run_id 为 holder（`exec_single.rs:253`）——**审计事件只能回溯到 run 级，不能回溯到触发它的工具调用**。
- **G7 重试/去重/中间件改写无结构化留痕**：`deduplicated`、attempt 序号、`before_execute` 改写后的实际执行入参均不进 `tool-end` 事件（幂等命中只能从输出文本里解析）。
- **G8 批清单字段空壳**：`tool-batch-start.calls` 与 `tool-batch-end.calls` 翻译层恒填空 Vec（`executing_tools.rs:219,342`），事件契约字段存在但信息缺失（可经逐个 tool-start 重建，但失去汇总语义）。

## 二、工具生命线事件序列 + 配对完整性审计表

### 2.1 生命线契约（tool_events.rs 头注 + 翻译层实测）

```
tool-batch-start
  → (tool-start
      → (approval-requested → approval-resolved?)*    审批类工具
      → (tool-update)*                                 流式进度，零或多条
      → tool-end)*
tool-batch-end
```

- 契约文档标注的序列为 `tool-batch-start → (tool-start → approval-requested → approval-resolved? → tool-update* → tool-end)* → tool-batch-end`。
- **实测偏差（G2）**：`tool-update*` 虽位于 tool-start 与 tool-end 之间（进度缓冲在 `exec_single.rs:385-397` 收集、执行结束并入事件链），但其真实发生时刻丢失——`ToolProgressUpdate` 结构无时间戳字段，`ToolUpdate` 事件 timestamp 也是翻译时刻。

### 2.2 配对完整性审计表（逐路径）

| 执行路径                     | tool-start                        | tool-end                        | error_code / 备注                                                                         |
| ---------------------------- | --------------------------------- | ------------------------------- | ----------------------------------------------------------------------------------------- |
| 正常成功（顺序路径）         | ✓（exec_single.rs:29）            | ✓（exec_single.rs:162）         | 无；duration_ms 真实                                                                      |
| 正常成功（并行组）           | ✓（exec_batch.rs:193 全组先发）   | ✓（exec_batch.rs:400 按组序收） | 无；真实完成序丢失                                                                        |

**批边界**：`tool-batch-start`/`tool-batch-end` 恒配对——BatchEnd 在循环外单点 push（exec_batch.rs:425），`break 'outer`（fatal+cancel-siblings）不影响其发射。

**反向单发**（有 end 无 start）：正常路径不存在；仅「批尾防御兜底」在理论上可能产生空 id 的 tool-end（无对应 start），属不可达防御分支。

**结论**：配对完整性 ✓（代码路径层面全部闭合）；但「配对」不携带时序与耗时信息（G1/G2）。

## 三、原子观测要素缺口（参数/耗时/结果/错误/状态）

| 观测要素     | 状态   | 证据与缺口                                                                                                                                               |
| ------------ | ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 调用参数     | ✓ 完整 | `tool-start.call.input`（模型原样入参 JSON）、`toolName`、`summary`、`category`、`concurrency`                                                           |
| 实际执行参数 | ✗      | `before_execute` 中间件改写后（exec_single.rs:288-332 `current_input`）与 tool-start 展示的原始 input 不一致时，事件面**无改写后入参**                   |
| 结果         | ✓      | `tool-end.result.output`（ToolOutput：text/json/artifacts）                                                                                              |
| 错误         | ✓      | `is_error` + `error_code`（tool.* 域）+ `error_message`（text）+ json.code 双承载                                                                        |
| 退出状态     | △      | 无统一 exit status 字段；仅工具输出内嵌（如 shell 的 exit_code 在输出 json）                                                                             |
| **耗时**     | **✗**  | ①失败路径 duration_ms 恒 0（G1，tool_events.rs:234）；②事件 timestamp 为翻译时刻，差值无意义（G2）；③幂等命中 duration_ms=0 且无结构化 deduplicated 标志 |
| 进度增量     | △      | tool-update 有 tool_call_id/batch_id 可归属；但无时间戳、无序号（G2 同源）                                                                               |
| 重试/attempt | ✗      | 事件面无 attempt 序号；requires_approval 重试首次 attempt 无事件（G5）                                                                                   |
| 去重         | △      | 幂等命中输出文本含 "skipped re-execution" + json.deduplicated，需解析文本而非结构化字段                                                                  |
| 批汇总       | ✗      | batch-start/end 的 calls 恒空（G8）；batch-start 仅 summary="N 个工具调用"                                                                               |

**从事件重建单次调用完整记录**：可行但受限——用 `tool_call_id` 关联 tool-start/tool-update/tool-end/approval-* 四类事件可拼出完整执行记录；受限点是耗时不可信（G1）、真实时间轴不可得（G2）、重试过程缺失（G5）。

## 四、审批链路闭合性

### 4.1 链路与关联键

```
tool-start(call.id)
  → approval-requested(request.toolCallId = call.id, request.id = "approval-<call.id>",
                        parameters, summary, requesterRunId?, reason?, metadata.arbiter?)
  → [壳层裁决] approval-resolved(tool_call_id = call.id, decision = approved|denied|expired)
  → tool-end(result.id = call.id, is_error, error_code = tool.user_denied|tool.approval_expired|tool.cancelled)
```

- **闭合性 ✓**：三环以 `tool_call_id` 关联，裁决后工具必有 tool-end；`request_id` 字段在 approval-resolved 中**恒 None**（翻译层 executing_tools.rs:283 与壳层 emit_approval_resolved core_run_commands.rs:7472 均不填）——关联唯一键是 tool_call_id，`request.id` 是死字段。
- **挂起期间工具状态**：事件面无「tool-pending」表达（tool-start 因 G3 也不可见）；可观测面 = run 状态机 `awaiting-approval` 中间态（orchestrator run.rs:146-156，落库可查）+ 壳层 gate `pending` 集合（list_pending_approvals 实时查询面）。
- **双发语义**：approval-requested 有两条来源——壳层 gate 实时广播（sequence=None 预览，core_run_commands.rs:847-851）与收口流持久化副本（executing_tools.rs:252）；前端按 `approval-requested:{toolCallId}` dedupe（push/dedupe.rs:24）。实时与持久化双轨是**有意的**，但依赖前端去重，属「协议脆弱点」。
- **超时 Expired 权威语义（G-9）**：引擎侧执行器收到 Expired 决策后补推 `ApprovalResolved(Expired)` 事件（exec_single.rs:124-127），随收口流落库；approve/deny 由壳层命令路径落事件。**双超时并存**：壳层 gate 120s（APPROVAL_TIMEOUT）+ 执行器批级 approval_timeout 120s（F1-02），一致收敛。
- **子代理审批留痕 ✓**：requester_run_id + reason + metadata.arbiter（main-agent/user）随 approval-requested 落库（executing_tools.rs:266-267、core_run_commands.rs:841-845）；拒绝文案带「主 agent 拒绝/回报主 agent」指引。

### 4.2 边角风险（非阻断）

- 壳层 gate 超时（Expired）**不清理** pending map 条目：超时后用户再裁决，`resolve()` 仍能找到 sender（send 到已 drop 的 oneshot，静默失败），随后无条件 `resolve_approval` 恢复状态机（core_run_commands.rs:750-760）——可能对已继续的 run 造成状态机误恢复。属可观测性审计顺带发现，未验证触发路径。

## 五、失败/重试/修复/逃逸留痕缺口

### 5.1 失败留痕

| 层                       | 留痕                                                                                   | 缺口                                                                                 |
| ------------------------ | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 工具失败                 | is_error + error_code + error_message ✓                                                | duration_ms=0（G1）；失败工具的实际执行入参（中间件改写后）缺失                      |
| 致命失败（fatalOnError） | tool-end 错误 + `runtime-error` 事件 + run failed 收口 ✓（executing_tools.rs:107-127） | 「本失败导致批中止」无事件标记（fail_strategy 不进事件）                             |
| 批级失败策略             | cancel-siblings 项有 cancelled 事件 ✓                                                  | 无「cancelled due to sibling X」的因果引用（error_message 仅文案 "sibling failure"） |

### 5.2 重试留痕

- **requires_approval 重试（G5）**：`execute_single_with_retry`（exec_single.rs:651-750）首 attempt 返回 `tool.requires_approval` 时事件流无记录；批准后重试，最终只推一条 tool-end。**「首次失败 → 审批 → 重试」在事件面塌缩为「approval-requested → tool-end」，失败证据丢失。** 二次 ApprovalRequired 直接透传（防循环），无 attempt 计数。
- provider 级重试有完整观测先例：`provider-diagnostic` phase=Retry + attempt/maxAttempts/elapsedMs（tool.rs:208-213）——工具域无对应物。

### 5.3 入参修复留痕

- **G4：`tool-input-repaired` 零发射**。全仓库 grep 仅命中 conex-types 测试（events_roundtrip.rs:315、972）、schema 版本 fixture、normalize.rs 白名单、device/events.rs 白名单——无任何生产 emit。session-loop 亦无入参修复机制（中间件 `before_execute` 的 `modified_input` 是唯一「改入参」点，不产事件）。**该事件是「定义了但从未活着」的死契约。**

### 5.4 逃逸监视留痕

| 面                        | 状态                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 实时性                    | ✓ 双轨：BridgeAuditSink 实时广播（sequence=None）+ L4 落库 worker 按发射序 reserve+append（core_run_commands.rs:1006-1087）；审计底账与收口流并存                                                                                                                                                                                                                         |
| 载荷                      | ✓ targets（绝对路径）、impact（file_count/cross_directory/flagged）、decision=denied、operation=undeclared-write（escape_watch.rs:421-437）                                                                                                                                                                                                                               |
| **工具关联**              | **✗ G6**：`tool_call_id` 恒 None（工具外写入语义）；判定基准 `WritePathRegistry.active_claims` 以 run_id 为 holder（exec_single.rs:253 `write_claim_holder: Some(ctx.run_id)`）——声明只记路径不记工具调用，**无法从一次未声明写入回溯到触发它的工具调用**，只能到 run 级。文档诚实边界亦声明「不承诺命令级归因（notify 事件无进程来源）」（undeclared_detector.rs:13-15） |
| 聚合限流                  | △ 同 run 同路径去重（只留首条+末时刻，escape_watch.rs:213-240）+ 批阈值 10 / 时间窗 5s——**重复写入次数丢失**（聚合报告只表达路径存在性与时间窗）                                                                                                                                                                                                                          |
| 工具侧审计（delete/拦截） | **✗ 同源 G6**：delete.rs:229、shell_redirect.rs:41 的 security-audit `tool_call_id` 恒 None（ToolContext 无该字段，executor 组装的 ToolContext 见 exec_single.rs:235-274）——删除接管/红线拦截审计无法关联到具体工具调用                                                                                                                                                   |

## 六、建议方向（只给方向，不做方案选型）

1. **修复失败路径 duration_ms**：`ClassifiedToolResult::error()` 改为接收真实耗时（exec_single 各失败分支已有 `start`/`duration_ms` 可用），或错误构造时从上下文取 elapsed。
2. **执行时刻打点**：在 ToolEvent 产出点（exec 层）携带 `occurred_at_ms` 或让翻译层使用执行器记录的时刻，而非翻译时刻；并行组 tool-end 携带真实完成序/完成时刻。
3. **工具域实时轨**：评估 tool-batch-start/tool-start 的实时发射通道（对齐 DeltaSink/BridgeAuditSink 先例），使 run 期间工具执行可观测；或至少在审批挂起期间补可见的 tool-pending 状态表达。
4. **结构化留痕字段**：ToolBatchResult 增加 `attempt`、`deduplicated`；tool-end 增加实际执行入参（中间件改写后）；batch-start/end 填 calls 清单（G8）。
5. **审计-工具关联**：ToolContext 注入 `tool_call_id`（或等价接线），使工具侧 security-audit 填真实 id；write_claims 声明带工具调用归属（声明持有者从 run_id 细化为 call_id）。
6. **重试过程事件化**：requires_approval 首 attempt 失败补事件（复用 tool-update 或新增 attempt 事件），使「失败→修复→重试→终态」链条完整。
7. **死事件治理**：`tool-input-repaired` 要么接线（中间件改写/入参修复时发射），要么从契约与注册表移除，避免「契约承诺存在、运行永不发生」的观测假象。
8. **tool-update 时序**：进度增量携带序号或相对时间戳，支持从事件流重建执行内时间轴。
