# 10 · 安全审计与红线

> 战役：agent 循环过程的全链路可追溯性与原子化观测
> 维度：安全审计与红线——高危操作（删除/回收站恢复/彻底清除/git 回退/命令执行/未声明写入/远程来源）的 security-audit 事件覆盖；审批链路（ask 模式）的可追溯；tool_call_id 关联；审计面板数据来源。
> 审计方式：内部审计，只针对本项目代码，不参考外部软件。只读检查，未修改任何代码、未提交 git。
> 日期：2026-08-14

## 一、结论摘要

**判定：「高危操作全链路可追责」总体成立，但存在系统性断链点，结论为「有条件成立」。**

- **成立的部分**：删除类（工具删除 + shell 删除形态重定向）在拦截/重定向/恢复/清除全路径均有 security-audit 发射；红线命令拦截、逃逸未声明写入（T-ESC-02）、远程白名单拒绝（remote-source-attempt）均有事件留痕；审批链路（approval-requested → approval-resolved → tool-end）闭合，等待期状态可观测；run 内工具/逃逸审计经 L4 持久化 worker 落 events 表（best-effort），有底账可查。
- **断链的部分**（详见各节）：
  1. **tool_call_id 关联形同虚设**：所有工具侧发射的 security-audit 恒为 `tool_call_id=None`（`ToolContext` 无该字段，事件契约 events.rs:592 的「工具侧发射时填充」未实现）；唯一填充的生产路径（任务审计）也硬编码空串。审计 → 工具调用 → turn 只能按时间序推测，无结构性链接。
  2. **「已批准执行」无审计**：审批放行（approved）后的命令执行、full-access 模式下的高危命令、git-revert 放行、browser 工具执行——均无 security-audit。审计面只覆盖「拦截/重定向/事后检测」，不覆盖「放行后执行」。
  3. **git-revert 操作类零发射点**：`SecurityAuditOperation::GitRevert` 枚举与前端标签齐备，但全仓无任何发射点（回退护栏只走审批流）。
  4. **非 run 上下文审计不落库**：任务域审计、trash restore/purge、remote-* 审计只走事件桥实时广播（runId=None），不写 events 表——重启即失，事后追责不可查。
  5. **多目标删除部分失败路径「执行了但无审计」**：shell 删除重定向循环中后置目标失败 → 直接返回错误，审计不发射，已移入回收站的前置目标无记录。
  6. **decision 语义错位三处**：undeclared-write 用 denied 但写入已发生（检测非阻止）；remote-mode-downgrade 用 blocked 但降级已生效；任务审计 decision 为展示位映射（Killed→blocked 前端显示「已拦截」，实际是启动后被强杀）。
  7. **审计面板无历史回填**：前端 store 为内存态（最多 20 条、展示 ≤8），只由实时事件流喂入，会话重载后审计区段为空；历史可经通用 events 查询，但无专用查询面。
  8. **remote-source-attempt 的 session_id 恒空串**，完全无法按会话/run 归属。

### 2.2 绕过审计的操作路径（重点核查结论）

1. **「审批放行后执行」与「full-access 直接执行」是最大盲区**：`shell.rs:257-259` 审批 `AskDecision::Allowed` 后直接进入执行，无任何 security-audit；`exec_verdict.rs:99-117` 的 permission_mode=full-access 对 dangerous 工具直接放行，同样无审计。`delete_file/delete_dir` 在任意权限模式下都发射（redirected），但**shell 命令、git 命令等其余高危工具在放行后零留痕**（只能靠 tool-start/tool-end 的入参推断）。
2. **多目标删除部分失败路径**：`shell_redirect.rs:166-183` 循环内对每个目标执行 `trash_file`；若第 N 个目标失败 → 直接 `return Err`，第 6 步（:190-197）的审计**不执行**——此前已移入回收站的 N-1 个目标「执行了但无审计」。且第 5 步的 `claim_write_guard` 全量声明（:137-143）虽防止并行冲突，但不产生审计。
3. **git-revert 全程无审计**：`git reset --hard` 不属于红线清单（semantics.rs:85-99 REDLINE_COMMANDS 之外），命中 `GitRevertShape` → `RevertPolicy.gate_verdict`（revert.rs:334-352）→ NeedsApproval（大面积）→ 审批流；审批放行后**执行亦无 audit**；小面积回退按 dangerous 工具矩阵走 ask，同样无 audit。`SecurityAuditOperation::GitRevert` 是「预留」状态。
4. **browser 域**：browser eval / 页面动作执行仅 tracing 日志，无 security-audit（M-4 留接线面）。
5. **后台任务启动本身**：任务域审计有发射（task_event_consumer.rs），但只广播不落库（见第五节）。

### 2.3 审计发射的统一形态与接线链

- 发射构造统一走 `crates/agent-tools/src/audit.rs:109-127`（`security_audit_event`，permission_mode 恒 None）。
- 接线链（run 内）：工具 `BuiltinToolConfig.audit_sink` → `RoutingAuditSink`（engine_audit.rs:50，按 session 路由，run 启动注册 / 收口注销）→ `BridgeAuditSink`（core_run_commands.rs:1013-1055：实时广播 + persist 通道）→ `spawn_audit_persistence`（:1065-1087，best-effort 落 events 表）。
- 域隔离：任务域审计不经 RoutingAuditSink（engine_audit.rs:42-45、core_run_commands.rs:6330-6333），直发 EventBridge；逃逸监视与工具审计共用同一 BridgeAuditSink 实例（core_run_commands.rs:6289-6291）。

## 三、审计-工具-审批链路闭合审计

### 3.1 审批链路（ask 模式）闭合性：✅ 闭合，reason 保留在 tool-end 文本

完整链（含行号证据）：

1. **approval-requested**：`ApprovalChannel::ask`（session-loop/src/approval.rs:105-122）先记录 `ToolEvent::ApprovalRequested`（进批事件流持久化，保序 tool-start → approval-requested → tool-end），再经 `ApprovalGateImpl::request_approval`（core_run_commands.rs:802-851）实时广播（sequence=None 预览，payload 含 `PermissionRequest`：toolCallId/toolName/parameters/summary + T-D-14 的 requesterRunId/reason/metadata.arbiter）。等待期间 RunHandle 状态机 `running → awaiting-approval` 落库（:853-864），并有 `list_pending_approvals`（pending_meta，C13）可查询。
2. **用户裁决**：`core_approve_tool` / `core_deny_tool`（core_run_commands.rs:7122/7161）→ `ApprovalGateImpl::resolve`（:728-762，先校验 tool_call_id 在待审批集合——I-02，杜绝伪造裁决）→ oneshot 送决策 + 状态机恢复。
3. **approval-resolved**：`emit_approval_resolved`（core_run_commands.rs:7463-7497）**落库 + 实时广播**（queue.push 带 sequence）；denied 的 reason 随 `ApprovalDecision::Denied { reason }` 传给 gate。
4. **工具侧收场**：`shell.rs:260-265` 拒绝 → `TOOL_USER_DENIED` 错误，文案 `user denied: {reason}` → 执行器分类 `ToolErrorKind::UserDenied`（exec_verdict.rs:145-157）→ **tool-end 必发**（is_error=true，error_code=tool.user_denied，error_message 含 reason）。✅
5. **超时收口**：120s 超时 → `ApprovalDecision::Expired` → 通道侧补记 `approval-resolved(expired)`（approval.rs:154-170；exec_single.rs:124、exec_batch.rs:334 同构）→ 翻译层映射 `AgentEvent::ApprovalResolved`（session-loop/src/loop/handlers/executing_tools.rs:272-280），非致命。

**缺口 1（reason 非结构化）**：`ApprovalResolved` 事件体（events.rs:506-513）无 reason 字段——拒绝理由只存在于 tool-end 的 errorMessage 文本中，无结构化消费/检索面（approval-resolved 历史补拉 C14 只能看到 decision）。

**缺口 2（approval-requested 双发）**：同一条请求存在「gate 实时广播（sequence=None）」与「批事件流持久化（带 sequence）」两份事件，桌面端/push 层靠 dedupe（push/dedupe.rs:24 `approval-requested:{toolCallId}`）收敛——若某侧漏接，可出现重复或单份。

**缺口 3（权限模式拒绝与 ask 拒绝均无 security-audit）**：`denied_result`（exec_verdict.rs:159-170，plan 模式拒绝写类工具）与 ask 拒绝（shell.rs:260-265）都只产生 approval-resolved/tool-end，**不发射 security-audit(denied)**——审批拒绝的高危操作在审计面板上不可见（需靠 tool-end 错误码推断）。

### 3.2 tool_call_id 关联：❌ 结构性断链

- **工具侧发射恒 None**：delete.rs:229、shell.rs:243、shell_redirect.rs:196、escape_watch.rs:436 全部 `tool_call_id: None`。根因：`ToolContext`（agent-tools/src/context.rs:100-145）**无 tool_call_id 字段**，工具在发射时拿不到调用 id。events.rs:592 注释「工具调用 id（工具侧发射时填充）」与实际实现不符。
- **任务域唯一填充但为假值**：`TaskAuditOperator::AiTool` 在 workbench 壳层硬编码 `tool_call_id: String::new()`（task_event_consumer.rs:124-128，自注「文档化」）——空串不构成关联键。
- **回溯能力现状**：
  - security-audit → run：✅ 信封 runId（BridgeAuditSink 注入，core_run_commands.rs:1051）——run 内审计可回溯到 run。
  - security-audit → tool-start：⚠️ 只能按「同 runId + 时间窗 + targets 与 tool-start 入参/输出人工比对」推断；无 tool_call_id 结构性关联。
  - tool-start → turn：⚠️ tool-start 携带 batch_id，turn-start/turn-end 携带 turn_index，两者之间无直接键，需按 sequence 顺序推断批的 turn 归属。
  - 非 run 上下文（task/trash/remote）：runId=None，无法关联。

### 3.3 审计-工具-审批三者时序（可观测性）

- 审批等待期间可观测：✅ approval-requested 已广播（请求含完整入参）、RunHandle awaiting-approval 状态落库、C13 待审批清单可查——「工具在等待」可观测。
- 但**等待中的工具没有 tool-update 或专门的 pending 标记**，前端需靠 approval-requested 卡片推断。

## 五、审计消费 / 查询 / 保留现状

### 5.1 数据源（前端）

- 链路：security-audit（事件桥）→ dispatch.ts:112 → securityAuditHandlers.ts → `useSecurityAuditStore`（securityAuditStore.ts:58）→ `RuntimePanel.tsx:61` → `SecurityAuditSection.tsx`（展示 ≤8 条，store 上限 **20** 条丢弃最旧，securityAuditStore.ts:48）。
- **纯内存态，无历史回填**：store 只由实时事件流喂入；会话重载/应用重启后审计区段为空，不查询 events 表补历史。历史审计只能经通用事件查询（`core_read_session_events` / `read_run_events_impl`，core_run_commands.rs:7504-7579）由消费方自行过滤。
- 逃逸扩展：impact.hasDestructive 前端可显示（SecurityAuditSection.tsx:54-60），与 T-ESC-04 接线一致。

### 5.2 持久化与保留

- **run 内工具/逃逸审计**：经 `spawn_audit_persistence`（core_run_commands.rs:1065-1087）→ `EventQueue.push_terminal_best_effort` 落 events 表——**best-effort 语义**（落库失败仅告警，不阻断 run、不重试）；随 run 收口排空。✅ 有底账。
- **非 run 上下文审计（任务域 / trash restore-purge / remote-\*）**：只经 EventBridge 实时广播（runId=None），**不落 events 表**——重启即失。trash 侧已自注「事件落库属 run 上下文数据面，本命令面无会话序列上下文，登记为 I3 遗留」（core_run_commands.rs:8078-8080）。
- **移动端**：security-audit 在同步面白名单（conex-types/src/device/events.rs:131，20 类之一），跨端策略 Redacted（:82）；events.resume 可补拉（限已落库行——故非 run 审计在移动端同样不可补）。
- **保留策略**：无审计专用保留/清理策略（随 events 表整体生命周期）。

### 5.3 查询能力

- 无专用「按 operation/decision/tool_call_id 查审计」的查询面；仅有通用 events 分页（按 session / 按 runId 过滤，core_run_commands.rs:7504-7579）。G10 denied 计数经 `DeniedStats`（agent-tools/src/audit.rs:80-105 CountingAuditSink 语义，engine_audit.rs 注记）供月度报告，但只计数不溯源。

## 六、建议方向（只给方向，不做方案选型）

1. **tool_call_id 贯通**：给 ToolContext 增加调用 id 字段（或等效的审计上下文注入面），工具发射审计时携带真实 call_id；同时修正事件契约注释与前端展示。任务域审计的空串 tool_call_id 一并落地为真值（壳层任务注册表已有 tool_call_id 记忆能力）。
2. **「放行后执行」审计面**：补齐 approved 语义——审批放行的高危命令、full-access 直接执行的 dangerous 工具发射 security-audit(approved/command-exec)（或引入等效的 execution-audit 事件），让「已批准执行」进入审计面板；git-revert 枚举落地真实发射点。
3. **非 run 审计落库**：把任务域 / trash restore-purge / remote-* 审计从「仅广播」升级为「广播 + 落库」（事件行 session_id/runId 归属修正，remote-source-attempt 的 session_id 空串问题一并解决），消除 I3 遗留与「重启即失」。
4. **多目标删除部分失败审计**：重定向循环改为「逐目标成功后即发审计」或「失败路径补发已执行部分审计」，保证无执行无记录、有执行必有记录。
5. **decision 语义归位**：undeclared-write / remote-mode-downgrade / 任务域 Killed 的 decision 与展示标签对齐真实语义（或引入 detection 类决策枚举，避免「已拒绝/已拦截」误导）；前端按语义区分「拦截未执行」与「事后检测/已生效记录」。
6. **审计面板历史化**：为审计区段增加 events 表回填（重启后可见历史），并考虑专用审计查询面（按操作类/决策/时间过滤）。
7. **browser 域审计接线**：将 M-4 留接线面（exec.rs:13-14）落地为 security-audit 发射（browser eval/动作执行），补齐最后一块高危执行盲区。
8. **决策-结果一致性验证面**：建立审计事件与 tool-end/文件系统状态的对照断言（回归测试锚点），使「审计说 X、实际做 Y」的漂移可被机器检出而非人工比对。
