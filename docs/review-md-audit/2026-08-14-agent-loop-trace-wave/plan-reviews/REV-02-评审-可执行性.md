## 一、结论摘要

**总体判定：6 份方案整体达到「可派单就绪」水平的 80%——五要素基本齐备、验收命令化程度较上个战役显著进步（REV-02 上个战役点名「人工核对/二选一」三类弱断言，本战役大部分已硬化），反过度设计自守良好（01 R3 / 02 LK-04/LK-06 / 03 EV-15 / 04 PC-01/PC-06 / 05 TR-02/TR-04/TR-07 / 06 零新表零新 IPC 均正确守线）。**

**主要障碍（按严重度排序）**：

1. **契约变更窗口未收敛**（阻塞级）：`conex-types/src/events.rs` 被 5 份方案认领（02 LK-04 契约字段、03 EV-03/EV-16/EV-18、04 PC-01/02/05/07、05 TR-01、06 SA-04），`AgentEventEnvelope` 信封字段（trace_id）与事件体字段（subagent_session_id/reason/turn_index/calls 改造）交织——必须集中为**一个契约变更窗口** + 窗口末统一 regen（06 OV-01 已提出该建议，正确），否则多次 regen 互相撞 diff。
2. **迁移版本号冲突**（事实错误级）：02 方案 LK-04 写「session_agents 增 sub_session_id 列（conex-db **v7 迁移**）」——实测 v7 已被 compression_blocks 占用、v8 已被浏览器导入表占用（migrate.rs:536/566，LATEST_VERSION=8），下一空位是 **v9**；且 02 衔接表说「与 run_id 列同一迁移版本（v7 一次迁移）」——**方向正确但版本号错误**，须修正为「并入 01 方案的 v9」。
3. **core_run_commands.rs 巨石多单元竞争**（风险级）：01（ActiveRun/read_run_events_impl/空闲态）、03（EV-02/EV-10/EV-18）、04（PC-04/PC-06/PC-07）、06（SA-02/SA-04/SA-05）四方案 8+ 单元触及（当前 8152 行，上战役曾 17828 已拆但仍是最大文件）——需冻结窗口 + 同文件串行矩阵，且 13 号教训 #6 已明示「派单前开工动作三件套 + 冻结确认」。
4. **EventRouter.ts 路径错一层**（事实错误级）：04 PC-04 与 06 OV-08 均引用 `handlers/EventRouter.ts`，实测真实路径为 `apps/crish-desktop/src/api/chat-bridge/EventRouter.ts`（不在 handlers/ 下）。
5. **03 方案 21 个 EV 单元偏多**（工作量均衡级）：需主控合单（EV-04~11 新事件组可并 2-3 个 Agent；EV-13/14/17 同文件域可并），且 03 自述「EV-09/E-10 建议由 08 视角承接、本方案只留联动约束」——存在**唯一派单悬空**，需主控拍板。
6. **伪断言残留 8 处**（见第三节），集中在 02 LK-05/LK-07、03 EV-05、04 PC-03、05 TR-08、06 SA-02 等「二选一」「或」「人工核验」表述。
