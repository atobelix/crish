## 二、方案详述

> 任务单元模板五要素：**ID / 目标边界（文件域锁）/ 完成定义 / 验收断言 / 禁止项**；附串行注记。

### 2.1 前端契约对齐（OV-01 → OV-02 → OV-03，逻辑递进：先有绑定、再有归一器、最后接分派）

#### OV-01 · 生成绑定重同步 41→49 + TS 侧漂移护栏

**现状（实测）**：`crates/conex-types/contracts/engine-events.json` 头部声明 49 类（id 42-46 = recovery-* ×5，47-49 = goal-* ×3，均含字段形状与 backpressure）；`packages/shared-types/src/generated/engine/events.ts` 的 `ENGINE_EVENT_TYPES` 仅 41 类（尾部可见最后键为 `cron-fired`，无 recovery/goal）。Rust 侧已有 `crates/conex-types/tests/registry_drift.rs` 锁 events.rs ↔ 注册表双向一致（实测文件存在）；**但注册表 ↔ TS 生成产物之间无机器护栏**——生成器 `scripts/generate-engine-bindings.mjs` 已支持 `--registry <path>` / `--only <contract>` / `--out <dir>` 单表再生（实测 CLI 注释），说明漂移测设计时预留了单侧再生成，却未挂「再生成后必须与已提交产物一致」的断言。

**目标边界（文件域锁）**：

- 白名单：`scripts/generate-engine-bindings.mjs`（仅加 `--check` 模式）、`packages/shared-types/src/generated/engine/events.ts`、`types.ts`、`parser.ts`（仅由生成器重跑产出，禁手改）、新增 `apps/crish-desktop/src/api/chat-bridge/handlers/eventParser.registry-drift.test.ts`（或等价 vitest 钉测）。
- 不碰：`crates/conex-types/src/events.rs`、`engine-events.json`（契约真源，本轮零改动——契约字段变更集中在 SA-04 与 05 维度的契约变更窗口）。

**完成定义**：

1. 重跑 `node scripts/generate-engine-bindings.mjs`，生成产物包含 49 类事件类型 + 对应 payload 结构 + backpressure 表。
2. 生成器加 `--check` 模式：再生成后逐字节比对产物，若有 diff 则 exit 非零（幂等性机器断言）。
3. 新增 TS 侧 drift 钉测：读 `engine-events.json` 的 events.type 集合，断言 `ENGINE_EVENT_TYPES` 与之完全一致（补丁模式：Rust 注册表新增事件类型而生成产物未同步 → 红）。
4. 事件契约保真清单（CT-05 形态，12 号梳理 §3.4 复用）：清单头句记录「真源 events.rs → 注册表 → TS 产物 → 归一器 → 分派表」五级同步链，注册表两侧钉测 + 生成器 --check 接线（建议挂 `check:desktop` 或独立 npm script，由主控定稿裁决具体门禁位）。

**验收断言**（命令化）：

- `node scripts/generate-engine-bindings.mjs --check` → exit 0（重跑两次产物字节一致，`git diff --stat` 对生成目录为空）；
- `npx vitest run apps/crish-desktop/src/api/chat-bridge/handlers/eventParser.registry-drift.test.ts` → 全绿（新钉测）；
- `cargo test -p conex-types` → registry_drift 保绿（Rust 侧不受影响，确认不误伤）；
- `rg "recovery-escalated" packages/shared-types/src/generated/engine/events.ts` → ≥1 命中（49 类落位）。
- 未真跑项：以上为执行轮真跑断言，本方案仅声明形状。

**禁止项**：禁止手改生成产物（含临时删 diff）；禁止改 `events.rs`/注册表；禁止给生成器加配置面/缓存；`Cargo.lock` 零 diff。

**串行注记**：生成产物文件被 SA-04（reason 字段再生成）与 05 维度（信封 runId 若入契约）共用——**建议主控把全部契约字段变更集中在同一窗口，窗口末统一重跑生成器 + drift 全链**，避免多次 regen 撞 diff。

#### OV-03 · dispatch 注册 8 键 + continuityHandlers 接线（或核销裁定）

**现状（实测 + 转引）**：`continuityHandlers.ts`（172 行）实现了真实消费逻辑——goal-* ×3 → `applyGoalRoundEventToGoalMode` 投影 `session.goalMode`（:44-99）、recovery-escalated → 熔断横幅（`raiseCircuitBanner`，:108-127）/ 子代理失败卡（:128+），且文件注释明确四类 recovery 事件「实时面显式空实现，检索面消费 `core_read_session_events`」（:143-171）；`dispatch.ts` 无任何 continuity import（死代码，仅测试引用）。审计 10 §2.2 同族：GitRevert 枚举无发射点、审批拒绝无审计——均属「契约在、接线断」。

**接线决策：接线而非核销**。理由：① 逻辑是 D8 设计意图消费方（goalMode 投影/熔断横幅），实现完整且有测试引用；② 核销会连带丢失 goalMode 投影能力，与战役目标「恢复/goal 过程可观测」冲突；③ 接线成本 = dispatch 表 3-8 键 + import。但须诚实：recovery-* 走 append_event 直写、实时不发射（文件注释自证），**接线只保证「若未来发射即消费」；真正数据源 = 检索面（05/08 维度的读侧修复）**——OV-03 验收不得宣称熔断横幅已被实时事件激活。

**目标边界（文件域锁）**：

- 白名单：`apps/crish-desktop/src/api/chat-bridge/handlers/dispatch.ts`（注册 8 键：goal-round-started/completed/continuation-decided → continuityHandlers；recovery-escalated → onRecoveryEscalated；recovery-steering/fork/report/budget-denied → 挂 OV-04 时间线入口函数或最小日志消费）、`continuityHandlers.ts`（仅必要小修：确认 HandlerEnv 签名匹配、导出一个供时间线/检索面复用的纯函数入口）。

1. dispatch 表 49 键全量注册，无 `parseErr` 后静默丢弃路径（8 类全部有消费去向；`registerUnknownEvent` 仅剩「真未知形态」兜底）。

### 2.2 run 级时间线最小形态（OV-04）

**设计原则**：最小可用（MVP）= 「当前 run 全事件条目流 + 历史补拉」，不加 run 历史列表全量形态、不加跨会话聚合、不进对话消息流（熔断/重连等观测面信息不进对话，09 约束沿用）。数据源：**live = per-run EventRouter 既有信封（type/runId/sequence），历史 = `core_read_run_events`（run_id 过滤面已存在，core_run_commands.rs:7540 实测）**——依赖 05 维度「落库行含 runId」修复后该查询才有效（当前 payload 无 runId，只能命中 run-terminal 一条，转引 05 §2）。UI 组件为新文件，遵守前端行数门禁（UI ≤500 硬阻断 650）与反过度设计红线。

**目标边界（文件域锁）**：

- 白名单：新增 `apps/crish-desktop/src/components/workspace/RunTimelinePanel.tsx`（或 runtime 面板内嵌 Section，UI ≤500 行）、新增 `apps/crish-desktop/src/api/chat-bridge/handlers/projectRunTimeline.ts`（事件类型 → 时间线条目投影映射表，业务 ≤400 行）、`RuntimePanel.tsx`（加入口点：active run 行「时间线」按钮 + 收口 run 摘要链接）、`sessionEventHydrate.ts`（历史补拉入口，runId 参数接线，小改）。
- 不碰：消息投影路径 `projectEventsToMessages`（OV-06 才动）；chat 消息 store；transport。

**完成定义**：

1. 时间线条目 = `{ runId, sequence, type, kind(分组: turn/agent/tool/审批/压缩/检查点/steering/恢复/goal/审计/终态), label, timestamp, 摘要字段, raw? }`；投影映射表覆盖 49 类（可分组共用 label 模板，如恢复类 5 键共 1 模板），缺映射键 = 编译期/测试期红（防再漂移）。
2. live 面：per-run 路由回调（新增轻量订阅或复用 streamCallbacks 面）把每个到达事件追加到会话级时间线 store（环形上限，如 500 条，超限丢最旧并留痕计数——对齐现有 store 上限模式，禁无限增长）。
3. 历史面：面板挂载 / run 切换时经 `core_read_run_events(runId, sessionId, afterSequence)` 分页补拉（复用水合分页模式 800/页 × 50 页上限 + hasMore 停滞防御），与 live 条目按 sequence 合并去重（复用 `consumedEvents` 同构键语义）。

5. 行数门禁：新组件与映射表 ≤ 门禁阈值；存量文件改动增量可控（`npm run check:line-counts` 归零）。

**验收断言**：`npx vitest run`（新增投影单测：49 类 fixture 各产 1 条目、未知 type 红测、sequence 排序、合并去重用例）+ 组件 jsdom 测试（空态/满态/分页加载态）；`npm run typecheck` 绿；`npm run check:line-counts` 无新超限。
