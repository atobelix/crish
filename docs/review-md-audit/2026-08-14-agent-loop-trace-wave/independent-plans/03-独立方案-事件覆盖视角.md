## 一、总览

**一句话方案**：以「事件契约保真清单」为基座（CT-05 形态），分六组收敛事件面——①死契约逐件裁决（接线/核销/登记三态）②无声动作按「决策类值得事件、细节类日志即观测」分级补点 ③孤儿 turn-start 以单点补发机制闭合 ④工具原子要素（耗时/时刻/attempt/批清单）字段化真实化 ⑤用户输入覆盖留痕 + pending_inputs 生产接线 ⑥新事件演进纪律（注册表/契约/前端/测试四同步）。

> 反过度设计总约束：**加字段不加系统、新事件一律 Delta/Soft 级可丢、禁 OTel/新通道/新服务/新表/新指标系统**（对齐 12-梳理 §四.8 与 `ANTI_OVERENGINEERING_GUARDRAILS.md`）。「每个动作都有事件」≠「每个动作都要事件」——本文给每个无声动作一个显式归宿（事件 / 日志 / 计数），不许悬空。

### 2.3 孤儿 turn-start 成对性修复

**问题**（01 §四）：turn-start 在 prepare_turn 必发；`streaming_aborted`（streaming.rs:252-284）、streaming 起始 check_control（streaming.rs:46-48）、executing-tools 批后 check_control（executing_tools.rs:130-132）、apply_recovery Abort（loop_exec.rs:261-273）四条收敛路径不经 turn_complete handler → turn-end 缺失。

**方案：发射点上移，单点补发**（结构干净、O(1)、防未来新收敛路径再漏——符合「穿透表象找架构断层」纪律）：

1. `LoopState` 增 `current_turn_index: Option<usize>`：turn-start 发射时置 Some(turn_index)；turn-end 发射后清 None。
2. 新增 `emit_missing_turn_end(state)` 辅助（`loop/handlers/mod.rs`）：若 `current_turn_index` 非 None → 补发 turn-end（reason=aborted/interrupted，携带该轮 tool_call_count——计数在 turn 状态内累计，不依赖 turn_complete handler 私有数据）。
3. 挂接点（全部收敛入口）：上述四条路径 + `loop_exec.rs:289-329` converge 前兜底（防未来新增路径漏挂）。**converge 前兜底 = 最终保证**，各路径补挂 = 载荷精确化。
4. 成对性不变量测试（`tests/run_loop.rs`）：新增「streaming 中途 abort → 事件流 turn-start/turn-end 恒成对」用例 + 通用断言辅助（扫事件序列：每个 turn-start 必被同 turn_index 的 turn-end 闭合，否则 panic）。

**验收**：run_loop abort 系列测试绿；`rg "turn-end"` 生产发射点 ≥2（turn_complete + 补发辅助）。

### 2.5 用户输入零留痕

**现状核实**（实测）：`input.rs:19` 容量 1000；`input.rs:67-68` 满则 `pop_front()` 静默覆盖最旧；`save_pending_input` 实现存在（`conex-db/src/runs.rs:310`、`orchestrator/persist.rs:175` trait、`persist.rs:720` 落库实现）但**生产零调用**（session-loop grep 零命中；壳层 `core_run_commands.rs:3901` 仅快照读侧 load）；崩溃恢复 FIFO 语义已有测试锁定（orchestrator/tests/crash_consistency.rs:471 `crash_restore_recovers_pending_inputs_in_fifo_order`）——**恢复机制是空转的**。

**方案（两件事）**：

1. **EV-19 覆盖留痕**：RingBuffer push 覆盖分支（input.rs:67-68）→ 模块级计数 `INPUT_OVERWRITES.fetch_add(1)` + `tracing::warn!`（含被覆盖消息 id 与截断文本前 120 字符）；暴露 `input_overwrite_count()`。事件化裁决：**不新增事件**（容量保护正常工况不触发；计数 + 日志满足「被丢弃输入可查」；若主控要求用户可见级留痕，再按 E-3 control-intent 同族扩展）。计数持久化汇总入 09 领衔的「观测计数持久化」清单。
2. **EV-20 save_pending_input 生产接线**：语义 = 「用户输入入队即持久化，消费即删除」（恢复面已有 loader，缺写者）：
   - 写点：三环队列 enqueue 入口（`loop_runner.rs:320` enqueue_input 单点）→ `save_pending_input(id=消息 id, session_id, run_id, payload=消息 JSON)`（INSERT OR REPLACE 幂等）；
   - 删点：消息出队被消费成为 message-start 时 → `delete_pending_input`；
   - 恢复消费端：崩溃恢复路径 load_pending_inputs → 重新入队（复用 crash_consistency 测试基建断言 FIFO 顺序）；
   - 预期影响：每条用户消息 1 INSERT + 1 DELETE（文本量小，写放大可接受；这正是该表存在与恢复设计的前提）。
3. 入队/消费事件：普通用户消息不经新事件（message-start/end 已可见）；软注入类入队由 E-3 control-intent 覆盖。

**验收**：input.rs 单元测试断言覆盖计数 +1 与 warn 日志（B1 三要素）；persist 集成测试断言「enqueue→pending_inputs 有行→消费→行删除」；crash_restore 既有测试在真实写者下继续绿。
