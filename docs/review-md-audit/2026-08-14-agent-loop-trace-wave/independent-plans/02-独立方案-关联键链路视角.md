## 一、总览（整体修复路径 · 一句话）

**把「横向链路」从三处断开修成两条可反查的链：一条以 `tool_call_id` 为键（工具调用 → 审计 / 子代理），一条以 `subagent_run_id + session_id` 为键（父会话三事件视图 ↔ 子会话完整视图）——工具执行器在唯一构造点注入调用 id，三个 spawn 构造点统一喂键，子会话映射落显式存储并进事件契约，投递形态统一「落库 + 广播」双轨，死路径按 CT-03 分类法收口，所有新字段按 S5 范式钉契约测。**

修复主线（逻辑依赖序）：`LK-01 工具调用 id 注入 → LK-02 三 spawn 构造点统一喂键 → LK-03 工具侧审计发射点补齐 → LK-04 子会话映射显式化 → LK-05 投递形态统一 → LK-06 子代理内部观测定案 → LK-07 死路径收口 → LK-08 契约测钉与演进纪律`。同权推进、无砍项；序只代表依赖（先有键、再喂键、再消费键）。

## 二、方案详述（每类断链的接法）

### LK-01 · 工具调用 id 注入 ToolContext（一切横向关联的键源）

**现状**：`ToolContext`（`agent-tools/src/context.rs:100-145`）无 `tool_call_id` 字段；但同一执行点已有 `ExecutorContext.tool_call_id: Option<String>`（`executor_types.rs:14`），且在 `exec_single.rs:209` 已填入 `Some(call.id.clone())`——**数据在手，缺的只是把它装进 ToolContext**。

**接法**：

1. `ToolContext` 增 `pub tool_call_id: Option<String>`（注释对齐 events.rs:592 语义：「工具侧发射时填充；None = 非工具上下文」）。
2. 唯一生产构造点 `session-loop/src/exec_single.rs:235`（`execute_one` 内；顺序与并行批路径均经此单点）填 `tool_call_id: Some(call.id.clone())`——与 :209 同源，O(1) 原生取值，无魔法数字、无猜测循环（§7 纪律）。
3. 其余构造点为测试/mock（`middleware.rs:266` 在 `#[cfg(test)]`、`create_mock_tool_context`、各工具 `mock_ctx`），默认 None 即可，编译器强制补字段后自然收敛。

**关键文件域**：`agent-tools/src/context.rs`、`session-loop/src/exec_single.rs`。

**验收断言**：`rg "tool_call_id: Some\(call.id" crates/session-loop` ≥1 命中；`ToolContext` 结构体含该字段（`rg "pub tool_call_id" crates/agent-tools/src/context.rs` ≥1）；契约测（见 LK-08）断言执行路径 `ToolContext.tool_call_id == call.id`；`cargo test -p agent-tools -p session-loop` 真跑绿。

**禁止项**：不加新依赖；不改 `ExecutorContext` 形状；不在多个构造点重复装配（单点 chokepoint 纪律）；不改工具执行语义。

### LK-02 · 三个 spawn 构造点统一接 parent_tool_call_id（按语义逐个接线）

**总原则**：`SubagentSpawnRequest.parent_tool_call_id`（`contract.rs:78`）→ spawner 落库（`subagent_spawner.rs:681`）→ `SubagentStarted` 事件（`subagent_events.rs:242`）**三层都是透传**——修好构造点，行与事件自动真值。逐点判定：

| 构造点          | 位置                                                                                      | 判定                                                                                                                                      | 接法                                                                                                                                                                                                                                            |
| --------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ① 工具直调      | `agent-tools/src/tools/subagent/tool.rs:431`（execute_many 内，`ctx: &ToolContext` 在手） | **真键**：run_subagent 就是一次工具调用，调用 id 即链条起点                                                                               | `parent_tool_call_id: ctx.tool_call_id.clone()`（依赖 LK-01）；顺带把 :198（`parent_session_id`/`parent_run_id` 段的 None 注释语义复核，:432 注释更新）                                                                                         |
| ② flow 调度     | `orchestrator/src/flow_graph.rs:1033`                                                     | **语义上无工具调用**：flow 节点由调度器事件驱动 spawn，不存在父工具调用                                                                   | **保持 None，但显式定案**：链路键改为 `flow_node_id`（已在请求中、已落库 `session_agents.description` 载体 + flow_state 映射）；注释改为「flow 路径链路键 = flow_node_id，parent_tool_call_id 恒 None（语义正确非欠接线）」，禁止用虚构 id 填充 |
| ③ recovery fork | `orchestrator/src/recovery.rs:517`                                                        | **可反查**：fork 承接的是原子代理 run（`ForkRecord` 含原 `subagent_run_id`），原 run 的 `session_agents.parent_tool_call_id` 即父工具调用 | fork 前经 store 查询原行 `parent_tool_call_id`（fork 场景同文件已有 store 查询先例，recovery.rs:544 set_subagent_path 同源），填入请求；查不到保持 None（fork 不因缺键失败——键是观测增强非前置条件）                                            |

**关键文件域**：`agent-tools/src/tools/subagent/tool.rs`、`orchestrator/src/flow_graph.rs`、`orchestrator/src/recovery.rs`（+ 相应测试 `subagent_tests.rs` / `flow_scheduler.rs` / `recovery_tests*.rs` 的断言更新）。

**验收断言**：`rg "parent_tool_call_id: None" crates` 仅剩 flow 构造点（②的定案声明处）与测试；工具直调路径测试断言请求 `parent_tool_call_id == 构造传入 call id`；`cargo test -p agent-tools -p orchestrator` 真跑绿。**测钉样式 = S5 范式**（见 LK-08）。

**禁止项**：不为 flow 路径编造调用 id；不让 fork 因查不到键而失败；不动 `resolve_parent_run` 语义（parent_run_id 链已一致，03 §四结论）。

### LK-03 · security-audit 带 tool_call_id（工具侧发射点补齐）

**现状**：`security_audit_event`（`audit.rs:109-127`）**已收** `tool_call_id: Option<String>` 参数，发射点传 None：delete.rs:223-230、shell_redirect.rs:35-43 / 190-197、shell.rs:237-243（红线拦截）。

**接法**（依赖 LK-01 后为纯接线）：

1. 各发射点 `None` → `ctx.tool_call_id.clone()`（`ctx: &ToolContext` 均在手）。覆盖：delete 接管、shell 删除重定向（拦截 + 重定向）、红线命令拦截。
2. 任务域唯一「假值」收口：`task_event_consumer.rs:124-128` 硬编码空串 → 由任务注册表既有 `tool_call_id` 记忆能力填真值（10 §六.1 方向，任务启动源自工具调用的场景）。
3. **归因粒度裁定**：`escape_watch`（undeclared-write）工具外语义（工具外写入检测），`tool_call_id` 保持 None 是语义正确的；`write_claims` holder 从 run_id 细化到 call_id 属**可选增强**（04 §五.4 建议），本方案列为后置项——先解决「审计 → 工具调用 → turn」结构性链接，holder 细化不阻塞主链闭合。

**关键文件域**：`agent-tools/src/tools/delete.rs`、`shell_redirect.rs`、`shell.rs`、`apps/agent-workbench/src-tauri/src/task_event_consumer.rs`。

**验收断言**：`rg "security_audit_event" crates/agent-tools/src/tools -A8 | rg "tool_call_id"` 中工具侧发射点均传 `ctx.tool_call_id`（grep 可核）；delete.rs:494 既有「恒 None」断言（`assert!(tool_call_id.is_none())`）翻转为「等于注入 id」；`cargo test -p agent-tools` 真跑绿。

**禁止项**：不改 `SecurityAudit` 事件契约形状（字段已在，只填值）；不改 decision 语义（decision 归位归 10 视角其它方案）。

### LK-04 · 子会话映射显式化（三选一裁决：落列 + 事件字段双轨，反查 API 不建）

**现状**（03 §三.1）：正向（父 → 子）靠 run_subagent tool-end output 信封（含 sessionId）；反向（子 → 父）无结构化键——SubagentStarted/Ended 事件体无 session_id 字段，session_agents 行无子会话列，只能「同序号命名推导」或遍历 session index 匹配 `engine_last_run_id`。

**三个候选方案与裁决**：

| 方案                                         | 优点                                                   | 缺点                                                                                    | 裁决                                 |
| -------------------------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------------------- | ------------------------------------ |
| A. session_agents 落子会话 id 列             | 持久层单一真相；崩溃恢复后仍可反查；与现有行同生命周期 | schema 变更（v7 迁移）；spawn 时需已知子会话 id                                         | **采用**（持久化主轨）               |
| B. sub-run → sub-sess 反查 API               | 无 schema 变更                                         | 依赖运行时 session index（引擎内存态），重启/恢复后不可靠；「API 查不到」就是另一条断链 | **不采用**（观测面不可依赖运行时态） |
| C. SubagentStarted/Ended 事件体加 session_id | 消费端（前端/审计）直接可用，零查询                    | 与 A 冗余？——不，A 管持久层反查、C 管事件流消费，双层互补                               | **采用**（事件轨）                   |

**接法**：

1. **schema**：`session_agents` 增 `sub_session_id TEXT` 列（conex-db v7 迁移，schema.rs 同族列模式；兼容旧库 NULL）。
2. **写入**：`subagent_spawner.rs` spawn 装配时子会话 id 已确定（`sub-sess-{depth}-{n}` 命名 + set_current_run 注册，03 §二）——row_for 落库补该列。
3. **事件契约**：`SubagentStarted`/`SubagentEnded` 事件体增 `subagent_session_id: Option<String>`（serde default + skip_serializing_if，向后兼容，S2 的「schema_version 不升 + 旧帧缺省读」纪律，12-梳理 §3.1）。发射点 `subagent_events.rs` started_info/ended_info 增字段透传。
4. **反查能力成形**：给定 SubagentEnded（subagent_run_id）→ session_agents 行（子会话列 + parent_run_id + parent_tool_call_id）→ 子会话事件流按会话查询——「子代理内部完整证据」一条链闭合；给定 tool-end（run_subagent 的 call id）→ session_agents.parent_tool_call_id 反查子代理 → 子会话事件流——「父工具调用 → 子代理全程」一条链闭合。

**关键文件域**：`conex-db`（schema/迁移/agents.rs 读写）、`subagent_spawner.rs`（row_for + launch 装配）、`orchestrator/src/subagent_events.rs`、`conex-types/src/events.rs`（契约 + 3 处同步：struct + 自定义 Serialize + Deserialize，对齐 S2 模板）。

**验收断言**：迁移后 `session_agents` 含 `sub_session_id` 且非 NULL（spawn 后查询断言）；`SubagentStarted`/`Ended` 事件体 `subagent_session_id == 子会话 id`（契约测钉，LK-08）；`cargo test -p conex-db -p orchestrator -p conex-types` 真跑绿。

**禁止项**：不新建反查 API/命令（运行时态依赖，反过度设计）；不改 `subagent-run-{d}-{n}` 命名生成逻辑（命名保留作人读冗余）；事件字段不做必填（向后兼容优先）。

### LK-05 · subagent-started/ended 投递形态统一（落库 + 广播双轨）

**现状**（03 §五.6）：同一链条三段三种投递形态——tool-start/end 广播（父 run）、子代理内部事件广播（子 run）、subagent-started/ended **只落库不广播**（前端实时性依赖 cursor 拉取）。

**接法**：`SubagentEventEmitter` 发射点（`subagent_spawner.rs:446-484` emit_started / `:489-660` on_subagent_terminal、flow 路径 `flow_graph.rs:1068-1097 / 1194-1231`）在**落库之外挂事件桥广播**（对齐 approval-requested「gate 实时广播 + 收口流持久化」双轨先例，10 §3.1 缺口 2；与 tool 事件广播通道同源）。发射器装配面补 `Option<事件桥>`（flow 路径 `if let Some(emitter)` 静默跳过的缺口一并处置：**未装配即记日志告警**，不静默，03 §五.5）。

**关键文件域**：`orchestrator/src/subagent_events.rs`（发射器构造）、`apps/agent-workbench/src-tauri/src/subagent_spawner.rs`（发射调用点）、`orchestrator/src/flow_graph.rs`（flow 发射点）。

**验收断言**：spawn 后事件桥收到 `subagent-started`（实时轨）；events 表同序列存在（落库轨）；前端无需 cursor 拉取即可在实时流收到 started/ended；`rg "if let Some(emitter)"` 后无静默跳过（或已带告警）。

**禁止项**：不为 started/ended 开新的专用通道（复用既有事件桥）；不改变 Critical 落库语义（必达性不降级）。

### LK-06 · 子代理内部动作观测定案（二选一裁决：以子会话事件流为准 + 跨会话导航）

**问题**（03 §三.2）：父会话侧对子代理内部动作只有「收口后补发 progress」摘要；`subagent-event` 契约的 message/tool 类（Soft 落库语义）**无生产发射方**——「两边都看不到」：父会话侧无实时内部动作，子会话完整证据又无法按 run 定位。

**两个候选与裁决**：

| 方案                                                                 | 成本                                                                                                            | 收益                                                   | 风险                                                                                |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| A. 为 message/tool 类接真实发射方（子 run 内增量 hook → 跨会话广播） | 高：子 run 的 drive_run_loop 需在 message/tool 产出点挂跨会话桥（会话边界穿越、软落库语义要新实现）             | 父会话侧实时可见内部动作                               | 第二套事件流复制子会话证据；与「完整证据在子会话」重叠；Soft 落库语义落地成本不可控 |
| B. 明确定义「子代理内部细节以子会话事件流为准」，补齐跨会话导航      | 低：LK-04 已建导航键（session_id 进事件体 + 子会话列）；只需在前端补「从 SubagentStarted/Ended 跳转子会话视图」 | 单一事件流、无复制；完整证据（参数/结果/增量）天然可达 | 父会话侧无实时内部动作——**用 progress 增量补发（已存在）补实时性缺口**              |

**裁决：B**。依据（路径合法排序键：效果完整度 → 正确性/不变量 → 可验证性 → 契约一致 → 结构干净）：

- 效果完整度：B + 既有 progress 补发 = 父会话侧可实时看到「进展」（文本 + 工具名），完整证据一跳可达；A 与 B 在「用户能否观测子代理内部动作」上无实质差异，但 A 多一套复制流。
- 正确性/不变量：单一事件流（子会话）保持「每个动作一条记录」不变量；A 引入同一动作两条记录（子会话 + 父会话 subagent-event），与「单一全链条记录」战役目标冲突。
- 可验证性：B 的验收可命令化（导航键非空 + 跳转可达）；A 的增量 hook 验收依赖时序竞态。
- 契约一致：B 不新增契约；A 要启用 Soft 落库语义（03 §六.4 指出其长期无发射方——按 CT-03 分类法，**未启用即显式标注**而非装作可用）。
- 反过度设计：B 零新设施；A 跨会话广播是新的投递面。

**接法**：

1. 契约层：`subagent-event` 的 message/tool 类在注册表/契约注释标注「未启用（设计裁决 LK-06-B：子代理内部细节以子会话事件流为准）」——CT-03 分类法处置（真契约 + 显式标注，禁删禁装）。
2. 导航面：前端从 `SubagentStarted.subagent_session_id` / `SubagentEnded.subagent_session_id` 跳转子会话事件流（消费 LK-04 契约字段）；无事件历史时经 session_agents 子会话列反查。
3. 实时性兜底：保留并标准化既有 progress 补发（03 §三.2 已存在）；progress 是否从 Delta 升级为落库属**后置决策**（03 §六方向），本方案不扩范围——诚实边界：补发制不升级。

**关键文件域**：`conex-types/src/events.rs`（注释标注）、前端 subagentHandlers / 会话导航（消费端，与 07 视角衔接）、`core_run_commands.rs` emit_subagent_progress（仅复核不动）。

**验收断言**：`subagent-event` message/tool 发射方 grep 零命中但契约注释含「未启用」标注（分类法落地）；前端跳转链路在测试中可达（导航键非空 → 子会话事件查询返回记录）。

**禁止项**：不为 message/tool 类新增发射方（裁决 B）；不删除 Soft 契约变体（分类标注而非删契约，CT-03 纪律）；不把 progress 升级夹带本任务。

## 四、未覆盖问题（诚实声明）

1. **持久化事件无 runId**（00 共性缺口 1：events 表无 run_id 列、payload 纯事件体）——本方案只修横向键（tool_call_id / session_id），**不修纵向 run 归属**；SubagentStarted/Ended 的父 run 归属与子会话事件流的 run 切片仍受其影响，由 02/05 视角方案解决。本方案依赖其落地才能完成「父工具调用 → 子代理全程」完整回放（LK-04 反查链的最后一环）。
2. **读侧解析静默丢弃**（00 共性缺口 2）——recovery-* 等 body-only 落库的 parse_envelopes 修复归 05/08 视角；LK-04 新增字段若落库 payload 无 type 标签同类受影响。
3. **前端消费面**（07 视角：normalizer-drift、运行期观测 store 内存态）——本方案只产出事件契约字段与标注，前端消费/导航 UI 实现归 07；「从 SubagentStarted 跳转子会话」的导航 UI 未在本方案展开实现细节。
4. **放行后执行审计 / GitRevert 发射点 / 非 run 审计落库 / decision 语义归位**（10 视角 §六.2/3/5）——安全审计的覆盖完整性补全归 10 视角其它方案；本方案只解决「审计能关联到工具调用」这一键。
5. **requires_approval 重试留痕 / 失败 duration_ms / 执行时刻时间戳 / 批清单 calls 填充**（04 视角 G1/G2/G5/G8）——工具原子观测的时序与重试细节归 04 视角。
6. **timeoutMs 的「实现超时机制」**——本方案裁决为删除死参数，不实现真超时；若战役范围要求真超时（L3 kill 之外的自动超时），需另行立项，不在本方案。
7. **subagent-event message/tool 的「实时增量观测」**——裁决 B 以子会话事件流为准，未做父会话侧实时内部动作流；若用户后续要求父会话侧实时内部动作（不满足「跳转查看」），需重新评估方案 A。
8. **本方案未真跑任何测试**（只读方案轮）；全部行号锚点为派单时实测，执行轮派单前必须开工动作三件套重定位（上一战役锚点漂移教训，13-梳理 §3.1）。
9. **不构成任何 EL 关账**：链路键接通 ≠ 全链路可追溯；测钉绿 ≠ 消费面完整；不抬任何 EL 状态。
