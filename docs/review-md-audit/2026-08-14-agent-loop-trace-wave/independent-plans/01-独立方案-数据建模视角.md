## 一、总览

### 1.1 一句话方案

**events 表加 `run_id` 列（解决按 run 查询）+ 落库 payload 改为存完整事件信封 JSON（解决从库还原完整信封），二者并用、各司其职；写面在 `EventQueue` 构造时绑定 run_id 单点注入（顺带把「名义统一注入点」normalize_envelope 真正接线），读面按 run 查询走 SQL 过滤 + limit 下推，无主/子代理/终态后三类特殊归属语义定案，迁移走 v9 纯 ADD COLUMN 幂等链。**

一句话展开：**「广播有归属、落库无归属」的根因是信封只在广播时构造、落库永远写裸事件体——修复 = 让「落库」也走信封，并把 runId 同时落成查询列。** 列与信封是同一注入点的两个输出，不是两套机制，不会漂移。

## 二、方案详述

### 2.0 三个核心裁决（先给结论，再论证）

| 裁决 | 结论                                                                                       | 一句话论证                                                                                                                    |
| ---- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| R1   | **run_id 列 + payload 存完整信封，二者并用**（05 建议方向 1 的「A+B 并用」落定为两职分工） | 列解决「查询」（索引直达、limit 下推），信封解决「还原」（读侧反序列化即完整 wire），两败俱伤的反面是各自 O(1)                |
| R2   | **写面注入 = EventQueue 构造时绑定 run_id（`Option<String>`），非 push 逐次传参**          | EventQueue 是全部持久化事件的唯一落库点（recovery/restore 直写除外），构造期绑定一次、push 内部自动携带，13+ 广播构造点零改动 |
| R3   | **不引入 start_sequence 列、不引入 run-closed 边界机制**                                   | run_id 列 + 复合索引已根治「按 run 直达」；start_sequence 是区间推导的兜底冗余；尾事件经「run-terminal 事件为界」天然切分     |

### 2.1 R1 论证：为什么「加列」与「存信封」必须并用，而不是择一

**只加 run_id 列（方案 A 单用）**：

- 解决查询 ✅，但还原仍有缺口：读侧 `parse_envelopes`（core_query_commands.rs:500-508）现按 serde 解析 payload 为信封，payload 无 runId/sequence 时信封字段为 None——若只加列，需把读侧改造成「解析事件体 + 从行级列合成信封」（runId 取列、sequence 取列、schemaVersion 恒 1），改造成本不小；
- 更关键：**未来任何新信封字段（如 trace_id，D-05 S2 蓝图已定稿未落地）要入库，每加一个字段就要加一列**——列与信封字段 1:1 演进，schema 漂移面大；
- 非 AgentEvent 载荷（run-interrupted / recovery-* 无 type 标签）在「合成信封」模式下仍然解析失败（合成需要先解析事件体）。

**只存完整信封 payload（方案 B 单用）**：

- 解决还原 ✅（反序列化即完整 wire），但查询无性能护栏：按 run 过滤只能全量读出 + 内存过滤（现状 `read_run_events_impl` 即此形态），10 万+ 事件会话 O(n) 全表扫描 + O(n) serde——05 §二.2 已明证 limit 只在内存生效；
- SQLite JSON 内过滤无索引可用，与「查询面」的战役目标（任意节点回溯整条链）不匹配。

**并用（本方案）**：

- **列 = 查询权威**：`(session_id, run_id, sequence)` 复合索引，按 run 过滤在 SQL 层完成，O(log n)；
- **payload 信封 = 还原权威**：写面序列化完整信封（含 runId/sequence/schemaVersion），读面 `parse_envelopes` 反序列化即得到与实时广播同构的 wire 事件——**前端消费面零改动**，且 trace_id 等未来信封字段天然入库、零新列；
- 冗余与一致性：payload 中的 runId/sequence 与行级列同源（同一注入点生成），列为主键级权威，payload 为 wire 镜像；由写面测试锚定「列值 == 信封值」不漂移（见 §2.7）；
- 存量兼容：旧行 payload 是裸事件体，serde 解析 `AgentEventEnvelope` 仍成功（run_id 缺省 None、sequence 缺省 None、schema_version 缺省 1，conex-types/events.rs:1153-1179 的缺省语义保证），读侧回退行为与现状一致，无破坏。

### 2.2 R2 论证：为什么绑 EventQueue 而非 push 逐次传参

现状（实测）：

- `EventQueue::push(&mut self, session_id, event)`（orchestrator/events.rs:161-207）——**不接收 run_id**；
- 落库 payload = `serde_json::to_string(&event)`（events.rs:189）——**裸事件体**；
- 生产路径 EventQueue 构造点：`ActiveRun.queue`（run 启动处，有 run_id 上下文）；`SubagentEventEmitter`（subagent_events.rs:188/201/213 每发射点 `EventQueue::new(store, 1)`）；`task_events.rs:444`；测试内 20+ 处 `EventQueue::new(store, run.cursor + 1)`。

方案：`EventQueue::new(store, base_sequence, run_id: Option<String>)`——**构造时绑定**，`push` / `push_terminal_best_effort` / `push_at_best_effort` 三个落库路径内部自动携带：

```
push(session_id, event):
  sequence = reserve(session_id)
  envelope = normalize_envelope(                       // ← 名义统一注入点真正接线
      AgentEventEnvelope::new(event, self.run_id.clone(), Some(sequence)),
      self.run_id.as_deref(), session_id)
  payload  = serde_json::to_string(&envelope)          // ← 完整信封落库
  append_event(session_id, sequence, event_type, &payload, self.run_id.as_deref())
```

- **13+ 广播构造点零改动**（它们构造的广播信封与落库信封同源同参，广播 runId 与列 runId 天然一致）；
- `normalize_envelope`（normalize.rs:99-131）从「仅测试调用的名义注入点」变为实际注入点——顺手修复 02 §三.3 的「名义统一注入点而非实际」问题；
- 唯一落库点收敛：此后除 recovery/restore 直写（§2.5）外，不存在「绕过注入写 events 表」的路径。

**签名连锁改动**：`Store::append_event` 加 `run_id: Option<&str>` 参数（persist.rs:159-165），波及 `LocalDbStore`（persist.rs:674-695）、`InMemoryStore`（persist.rs:446 区）、`conex-db::LocalDb::append_event`（conex-db/events.rs:8-27，INSERT 加 run_id 列）、`PersistedEvent` 加 `run_id: Option<String>`（persist.rs:112-121，读面携带）。连接层测试的 40+ 处 append_event 调用同步适配（机械改动）。

### 2.3 读面：parse_envelopes 还原完整信封（含旧行兼容）

现状：`parse_envelopes`（core_query_commands.rs:500-508）解析 payload 为信封，信封字段来自 payload（现在缺 runId/sequence）→ wire 缺字段（05 §三.3）。

改造后：payload 已是完整信封 → 反序列化直接得到 runId/sequence/schemaVersion 齐全的信封。唯一增强：**以行级列 run_id 为权威覆盖**（列 `Some` 时覆盖 payload 解析值；列 `None` 时保留 payload 值——旧行 run-terminal 自带 runId 仍可还原）：

```
fn parse_envelopes(events) -> Vec<(u64, AgentEventEnvelope)>:
  每行:
    envelope = serde_json::from_str(payload)?      // 失败跳过（现状语义保留）
    if row.run_id.is_some() { envelope.run_id = row.run_id }   // 列优先
    Some((row.sequence, envelope))
```

- wire 输出（`envelope_to_value`，core_query_commands.rs:511-513）自动带 `runId`/`sequence`/`schemaVersion`——与实时广播同构（03 §3.1 契约），前端消费面零改动；
- 旧行（裸事件体 payload）：解析成功、runId=None、sequence=None，wire 与现状一致（诚实兼容，不回填）。

### 2.4 查询面：按 run SQL 下推 + limit 护栏

**新增 `query_events_by_run`**（conex-db events.rs + Store trait 双面）：

```
SELECT session_id, sequence, event_type, payload, run_id, created_at
FROM events
WHERE session_id = ?1 AND run_id = ?2 AND sequence > ?3
ORDER BY sequence ASC LIMIT ?4
```

- **索引**：`CREATE INDEX idx_events_run ON events(session_id, run_id, sequence)`（复合；前导 session_id 与既有 `(session_id, sequence)` 主键查询不冲突、不冗余）；
- **`read_run_events_impl`**（core_run_commands.rs:7540-7590）改为调用 by_run 查询：SQL 层过滤替代「全量读 + 内存过滤」；`next_after_sequence` 取**页末全局 sequence**（修复 02 §四.3「过滤后取页末游标会跳事件」的语义问题——SQL 层过滤后页末序列即本 run 事件流中的位置，续页语义正确）；
- **limit 下推**：`Store::query_events` 加 `limit: Option<u64>`（persist.rs:168 现状无参，LocalDbStore 恒传 `None`，persist.rs:697-713——这就是 05 §二.2 的 O(n) 根因）；`core_read_session_events` / `read_session_events_impl` 把 clamp 后的 page_size 下推（SQL `LIMIT n+1` 判 has_more）；
- **`core_read_run_events`**（core_query_commands.rs:568-610，T-F 06 退役）：服务端语义修通后是否恢复 IPC 注册由主控裁决（涉及 07 前端消费面）；本方案保证 `read_run_events_impl` 及其远端 C04 通道（server/core_backend.rs:480）语义正确，注册面不作为本维度验收前提。

**明确不做（R3）**：runs 表不加 `start_sequence` 列——run_id 列 + 索引已 O(log n) 直达；「起始序列落库」仅在无 runId 的区间推导场景有价值，属冗余建模（02 建议方向 2 列为可选项，本方案按反过度设计红线判不选，登记为可选增强）。

### 2.6 归属语义定案（三类特殊场景）

**① 无主事件（run_id = NULL）**：

| 事件族                                                             | 现状 runId                     | 落库 run_id 列                          |
| ------------------------------------------------------------------ | ------------------------------ | --------------------------------------- |
| timer-fired / timer-cancelled / cron-fired                         | None（engine_channels.rs:493） | NULL（若落库实施归 05；本维度定义语义） |
| task-*（bg_events.rs:259 / task_event_consumer.rs:145）            | None                           | NULL                                    |
| 空闲态事件（push_emit_idle_event，core_run_commands.rs:7035）      | None                           | NULL（已走 EventQueue，绑 None 即可）   |
| 远端/回收站审计（core_backend.rs:252 / core_run_commands.rs:8116） | None                           | 不落库（保持广播；落库决策归 10）       |

**语义定案：`run_id` 列 NULL = 「会话级 / 无 run 上下文事件」**，不属于任何 run：按 run 查询（`query_events_by_run` WHERE run_id=?）不返回，按会话查询返回。与现有信封 `runId=None` 的前端语义（放行不过滤，conex-types/events.rs:1095-1097）一致，不新增状态。

_*② 子代理事件归属：父会话内 subagent-* 归父 run_id_*：

- 子代理生命周期事件（subagent-started / subagent-event / subagent-ended）落在**父会话**（session_id = parent_session_id，subagent_spawner.rs:457 / flow_graph 同构）——`SubagentEmitContext` 已携带 `parent_run_id`（subagent_spawner.rs:456-459），`SubagentEventEmitter` 构造 EventQueue 时绑 `Some(parent_run_id)`（空则 None）；
- 语义：子代理是父 run 驱动周期内发起的动作，父 run 的时间线应包含「发起了谁、何时收尾」的完整锚点；
- 子代理 run **自身**的事件在**子会话**（sub-sess-*）内走完整 session-loop，其 ActiveRun 的 EventQueue 绑子代理 run_id → 子代理 run 的完整链在子会话内可回溯；
- 跨会话关联：父会话 subagent-started 事件体带 `subagent_run_id`（反查子会话）；`parent_tool_call_id` 断链（03/10 维度）本维度不碰；
- 现有 progress 广播 runId = subagent_run_id（core_run_commands.rs:3602）——progress 是 Delta 不落库（event_class NonPersistent，events.rs:48-58），无落库归属冲突，广播语义保留。

**③ 终态后迟到事件：按事件发生时的 run 上下文归属，不因 run 终态改归属**：

| 尾事件                                                                    | 发生时机            | 归属                                                             |
| ------------------------------------------------------------------------- | ------------------- | ---------------------------------------------------------------- |
| security-audit 排空（audit_worker.await，core_run_commands.rs:5493-5500） | run-terminal 落库后 | 原 run（BridgeAuditSink 携带 run_id，core_run_commands.rs:1051） |
| subagent-ended 收尾（:5543）                                              | terminal 后         | 父 run（R2 绑定 + §2.6-②）                                       |
| goal-round-completed / goal-continuation-decided（:5610/:3199/:4688）     | terminal 后         | 原 run（emit_envelope_event 带 run_id，:5780-5797）              |
| 空闲态事件                                                                | 任意时点            | NULL（无主）                                                     |

- **不引入 run-closed / 终态边界新机制**：按 run 查询返回该 run 的**全链**（含 terminal 之后的 tail 事件）；消费方以 run-terminal 事件为界区分主链/尾链——run-terminal 唯一（terminal_sent 守卫，02 §五.5 已锚定），作为边界稳定可靠；
- 由此「run 事件链 ≠ 到 terminal 为止」成为**文档化语义**而非隐藏行为；02 §五.5 的「尾事件归 run 还是会话？」问题得到明确回答：**归 run（有 run 上下文者），空闲态归会话**。

### 2.7 迁移路径（schema v9）

**迁移设计（沿用 col-check 幂等先例）**：

- `migrate_v8_to_v9`（migrate.rs:148-184 的 match 加一臂），纯 ADD COLUMN + 建索引，无 DROP 无重建：
  - `table_columns(tx, "events")` 检查 → `ALTER TABLE events ADD COLUMN run_id TEXT`（幂等，对齐 migrate_v5_to_v6 的 col-check 模式，migrate.rs:500-523）；
  - `CREATE INDEX IF NOT EXISTS idx_events_run ON events(session_id, run_id, sequence)`；
- `LATEST_VERSION` 8→9（conex-db/lib.rs:65）、`SCHEMA_VERSION_STRING` "8"→"9"（lib.rs:67）；
- 备份区间：migrate.rs:157 的 `(5..=8).contains(&version)` 跳过备份 → 扩为 `(5..=9)`（v9 纯 ADD COLUMN，沿用「纯 ADD 跳过备份」裁定）；
- `create_v5_schema` 目标 DDL 的 events 定义同步加 `run_id TEXT` 列（schema.rs:141-149）——新库 ensure 路径直接建出含列结构；v9 迁移的 col-check 对已含列的新库自然跳过，幂等闭环；
- 崩溃重跑：每版本独立事务 + col-check，重跑自愈（对齐既有约定）。

**存量数据策略**：

- 存量行 run_id 列 = NULL（未知归属）——读侧信封 runId=None，与现状 wire 一致，**不破坏任何既有消费**；
- **默认不回填**：回填需启发式（agent-start 锚点到 terminal 之间分段），并发/交错会话下不可靠（09 §三.3 已证），且破坏「未知即诚实 NULL」语义；可选 backfill 登记为后续增强（主控裁决）。
