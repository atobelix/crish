## 一、总览

**一句话方案**：以「run 级 trace_id 作为日志-事件双通道共享关联键」+「span 上下文原生传播修复（instrument 取代 enter，spawn 显式继承）」为主线，把日志侧改造成「每一行可归属到 run/会话、可钉到事件链、崩溃现场可还原」的观测通道，与事件侧（权威链）以 `(trace_id, run_id, sequence)` 三元组对齐，双通道从「人工拼图」升级为「机器可查」。

### 1.2 与 S2 的承接关系

**原样承接（不改动 S2 已定稿点）**：run 级 trace_id（每 run 一枚，run 启动生成）；挂**既有** `info_span!("run", session_id, run_id, trace_id)`，不加新 span 层级；`AgentEventEnvelope` 增可选 `trace_id` 字段（wire 键 `traceId`），`schema_version` 保持 1、旧帧向后兼容；事件桥 emit 注入；前端 invoke 载荷透传（**禁按 HTTP 头**，Tauri IPC 无此语义）；字段长度钳制；禁 OTel / 新 crate / 新 span 层级 / Cargo.lock 零 diff。

**本方案扩展三处（S2 的空白）**：

1. **span 上下文传播机制设计**（TR-02）：S2 只定了「run 启动处挂一个 span」，未设计跨线程传播。本方案补：instrument 骨架函数取代 `span.enter()`、spawn 点显式 `.instrument()` 继承、turn_index/tool_call_id 走显式事件字段（不做 span）。
2. **trace_id 与落库面的关系裁定**（TR-01 落库注记）：S2 未触 schema。本方案裁定：**trace_id 不单独建列**（run 级 1:1，查询键 run_id 已足；详见第三节与 01 视角衔接），落库面追随 01 视角的最终决策，双方不得各自建 schema。
3. **日志侧关联**（TR-03/05/06）：S2 验收只覆盖 IPC/事件面；本方案补日志侧字段、时间对齐规则、日志侧回归测试。

## 二、方案详述

> 任务编号启用本战役新前缀 **TR-**_（trace/日志观测域），禁与 G-_/SR-_/B_/S*/CT-_/CONN-_/SD-* 互引（11 文档编号空间裁决）。五要素：ID / 目标边界（文件域锁）/ 完成定义 / 验收断言 / 禁止项。

### TR-01 · trace_id 信封字段（承接 S2 并扩展）——【信封面】

**目标边界（文件域锁）**：

- `crates/conex-types/src/events.rs`（`AgentEventEnvelope` struct:1109-1120 + 自定义 Serialize:1128-1151 + Deserialize:1153-1179 + `new` 构造:1183+，共 4 处同步）
- run 启动生成点（`apps/agent-workbench/src-tauri/src/core_run_commands.rs` spawn 前 / ActiveRun 结构，锚点须派单时重定位）
- 事件桥 emit 注入点（engine 事件桥 / `core_event_bridge.rs`）
- `docs/rust-rewrite/33-event-schema-changelog.md` 登记
- **不碰**：conex-db schema（归 01）、前端 transport（归 07/S2 承接方）

**设计决策**：

1. **字段名与形态**：Rust `trace_id: Option<String>`；wire 键 `traceId`（camelCase，与 runId/sequence/schemaVersion 对齐）。可选字段，缺省 None。
2. **缺失语义**：无 run 归属事件（timer/cron 域，run_id 为空串/伪 id）→ `trace_id = None`；run 归属事件 → `Some`（非空）。旧帧无 traceId 键 → 解析为 None，向后兼容。
3. **生成与生命周期**：run 启动点生成一枚（短随机 id，如 16 位 hex / nanoid 风格），随 run 状态持有，收口释放；长度钳制 ≤ `ID_MAX_LEN`（参照 core_query_commands.rs:459-468）。
4. **schema_version 纪律（铁律）**：**新增可选字段一律不升 schemaVersion**（保持 1）——旧帧缺省读（Deserialize 增 `map.get("traceId").and_then(Value::as_str)` → None，与 run_id 同模式）；按 33-event-schema-changelog.md 的 minor 规则登记；只有破坏性变更（字段必填/类型变更/语义变更）才走 major。S2 已裁定不升，本方案固化登记纪律。
5. **信封同步 4 处**：struct 增字段；Serialize 增 `if let Some(t) = &self.trace_id { map.insert("traceId", json!(t)) }`；Deserialize 增读取；`new` 建议保持 3 参 + `with_trace_id` 链式（减少调用点噪声），或 4 参带默认——以契约测为准，执行 Agent 二选一。
6. **事件桥注入**：emit 点注入当前 run 的 trace_id——**与 02 视角的 runId 注入同一构造点，同文件串行**（总案定唯一执行方，另一视角降为验收视角）。
7. **落库面（衔接注记）**：不单独建 trace_id 列（理由见第三节）。若 01 视角最终选「完整信封 JSON 落库」（05 文档方向 B），trace_id 随信封自然入 payload，本方案不重复设计。

**验收断言**：

- 契约测：信封 round-trip（含 traceId 序列化/反序列化）；**旧帧解析测**（无 traceId 的 JSON 帧解析成功且 trace_id=None）；wire payload 断言（传输面含 traceId）。
- `rg "trace_id" crates/` 生产代码 ≥ N 命中（S2 验收口径：≥1）。
- `cargo test -p conex-types` / 相关契约测试全绿。
- 33-event-schema-changelog.md 登记行存在。

**禁止项**：禁新 crate / 禁升 schema_version / 禁 OTel / 禁新 span 层级 / trace_id 不进用户可见 UI 文案 / 禁动 conex-db schema（归 01）/ Cargo.lock 零 diff。

### TR-02 · span 上下文原生传播（instrument 取代 enter，spawn 显式继承）——【日志面基础设施】

**目标边界（文件域锁）**：

- `crates/session-loop/src/loop/loop_exec.rs`（`:23-28` 现有 span 改造）
- `apps/agent-workbench/src-tauri/src/core_run_commands.rs`（`:5314-5317` 现有 span 改造 + ActiveRun 注入）
- 7 个已知 spawn 点：`approval.rs:427/451`、`summary_dispatch.rs:487/595`、`summary_coordinator.rs:175`、`escape_watch.rs:363`、`safe_point.rs:475`（文件在 `crates/session-loop/` 下，锚点派单时重定位）
- 26-frontend-observability-audit.md P2 字段名约定核对
- **不碰**：conex-telemetry subscriber（TR-07 才碰）；前端

**机制选择（三选一，结论：原生 instrument + 骨架函数，不建自定义 Layer）**：

| 机制                              | 线程迁移                                              | spawn 继承                     | 判定                                                                        |
| --------------------------------- | ----------------------------------------------------- | ------------------------------ | --------------------------------------------------------------------------- |
| `span.enter()`（现状）            | TLS 线程本地，迁移即丢                                | 不继承                         | **弃用**（根因：audit §五.5）                                               |
| `#[instrument]` / `.instrument()` | span 由 future 持有，每次 poll 重新进入，**迁移安全** | `.instrument(span)` 包裹可继承 | **采用（主机制）**                                                          |
| 自定义 Layer 做上下文传播         | 可兜底                                                | 可兜底                         | **不建**：属再造 tracing 原生机制（原生 span 继承已覆盖），撞反过度设计红线 |

**设计决策**：

1. **骨架函数纪律**：只对 ~8 个骨架 async 函数做 `.instrument()`（run 级：`drive_run_loop` / `run_task_impl` / `session_loop.run`；turn 级：`prepare_turn` / `turn_complete` 边界；工具级：工具执行入口），**子函数一律不 instrument**——compact 格式渲染在场 span 栈全部字段，逐函数 instrument 会字段重复输出 + span 栈膨胀。~200 处日志点靠 span 字段继承自然带上下文。
2. **run span 字段**：`session_id` / `run_id` / `trace_id` 三字段（trace_id 由 TR-01 引入后并入）。
3. **turn_index / tool_call_id 不做 span**（遵守 S2「禁新 span 层级」）：作为**关键日志点的显式事件字段**（`tracing::info!(turn_index = n, tool_call_id = %id, "...")`）。
4. **spawn 继承**：7 个已知 spawn 点用 `.instrument(span.clone())` 包裹 future（或任务入口重进 span）。验收钉：spawn 任务内日志行带 run span 三字段。
5. **并发 run 隔离**：多 run 并发各自 span 树，字段不串（tracing 原生隔离）；TR-06 测试钉死。

**验收断言**：

- 观测测试（TR-06 承接）：run span 在场 + spawn 任务内发射 → 捕获行含 `session_id=` / `run_id=` / `trace_id=` 三字段（LogCapture 断言）。
- `rg "\.enter\(\)"` 相关文件域零命中（全部转 instrument）。
- `rg "#\[instrument\]|\.instrument\(" crates/session-loop apps/agent-workbench/src-tauri/src` 骨架函数命中（数量级 ≈8）。
- 既有 `observability.rs` / `run_loop.rs` 测试全绿。

**禁止项**：禁新 span 层级；禁逐函数 instrument（只骨架函数）；禁自定义 Layer 做上下文传播；禁改日志点正文语义（本轮只补上下文，正文不动）。

### TR-04 · 崩溃留痕增强（crash 文件补 backtrace / 活跃 run 上下文 / 最后 N 条日志）——【崩溃面】

**目标边界（文件域锁）**：

- `crates/conex-telemetry/src/panic_hook.rs`（:68-74 既有 panic 日志 + :93-116 crash 文件写）
- `crates/conex-telemetry/src/crash.rs`（:82 `stack: None` 修复）
- `crates/conex-telemetry/src/subscriber.rs`（新增环形缓冲 layer 或并入 file layer）
- `crates/conex-telemetry/src/lib.rs`（新组件导出）
- 活跃上下文注册表（conex-telemetry 内定义；写入点在 drive_run_loop 入口/收口——与 TR-02 交接）
- **不碰**：事件面；前端

**设计决策**：

1. **backtrace**：两路径补 `std::backtrace::Backtrace::force_capture()`——① panic hook 写 crash 文件时捕获（hook 内可捕获，需注意 Windows 符号解析限制，force_capture 尽力而为，失败时保留 `backtrace: <unavailable>` 占位）；② `crash.rs:82` catch_unwind 的 `stack: None` 改为闭包内捕获（捕获的是 catch_unwind 调用点栈，够用）。
2. **活跃 run 上下文**：单槽全局 `static ACTIVE_RUN: Mutex<Option<ActiveRunCtx { session_id, run_id, trace_id, started_at }>>`（conex-telemetry 内），drive_run_loop 入口写、收口清；panic hook 读入 crash 文件。**单槽覆盖**（并发 run 时留最近一次写入者），不做并发全景（反过度设计：崩溃现场只需「正在跑什么」，不追求并发快照）。
3. **最后 N 条日志**：环形缓冲（容量 N=512，存格式化行）挂在 subscriber 内与既有 layer 并列；panic hook 把尾部 dump 进 crash 文件。**同步写，禁异步冲洗**（hook 路径无 runtime）。
4. **crash 文件新结构**：`header（timestamp/thread/location/panic_message）→ backtrace 段 → active_run 段 → recent_logs 段（最近 512 行尾部）`；既有字段顺序保持，向后兼容旧解析。
5. 与既有「panic_hook 同时发 `tracing::error!(target: "panic")`」的冗余关系保留（互为交叉验证，audit §三.1）。

**验收断言**：

- panic 注入测试（telemetry 单元测或 crash_consistency.rs 扩展）：crash 文件含 `backtrace:` 段、`active_run:` 段（含 run_id 值）、`recent_logs:` 段。
- `rg "force_capture" crates/conex-telemetry/src` 命中 ≥2。
- 既有 file.rs 自测与 crash_consistency.rs T12 系列全绿。
- 环形缓冲容量固定（512），crash 文件大小有界。

**禁止项**：禁异步冲洗（hook 内直接同步写文件）；禁新日志目录；禁无限增长（N 固定）；禁引入第三方 backtrace crate（std 够用）。

### TR-05 · 时间对齐（created_at 毫秒化 + 对齐规则声明）——【时间面】

**目标边界（文件域锁）**：

- `crates/conex-db/src/migrate.rs`（新增迁移：events.created_at 毫秒化）
- `crates/conex-db/src/events.rs` / `schema.rs`（写入面改 `strftime('%Y-%m-%d %H:%M:%f','now')`）
- 文档化：对齐规则声明（本方案 §TR-05 验收 + 05 文档口径）
- **不碰**：事件 payload timestamp 语义（执行时刻 vs 翻译时刻，归 09 视角）；recovery-* epoch ms 字段（08 视角契约，可换算不阻塞）

**设计决策**：

1. **最小改动**：events 表行级 `created_at` 由 `datetime('now')`（秒）改毫秒精度（`strftime('%Y-%m-%d %H:%M:%f','now')`）；存量秒级行兼容（读取不依赖该列排序）。
2. **对齐规则（总案裁决点，本方案提出）**：**排序唯一依据 = sequence**（05 文档已确认：时钟三轨并存，排序必须以 sequence 为准）——读取面保证按 sequence 排序，时间只作对齐辅助。对齐粒度：日志 µs（**保留**，精度更高，对齐时截断）与事件 payload ms（保留）**同源 SystemTime UTC**，日志-事件对齐用「(trace_id, run_id) + ±ms 时间窗」。
3. **精度梯度**：日志 µs ≥ 事件 ms ≥ created_at ms（毫秒化后）；消灭「created_at 秒级无法参与对齐」这一最粗轨；不强制统一到同一精度（无意义——排序有 sequence 兜底）。

**验收断言**：

- 迁移测试：新写入 created_at 含毫秒（`%f` 非零段）；存量秒级行读取正常。
- `rg "datetime\('now'\)" crates/conex-db/src` 事件写入面零命中（或已替换为 strftime 毫秒变体）。
- `cargo test -p conex-db` / crash_consistency 相关测试全绿（created_at 不参与任何排序断言，无语义破坏）。

**禁止项**：禁改 payload timestamp 语义（归 09）；禁新时钟系统/新时间库；禁把 created_at 引入排序键；migrate.rs 与 09 视角**单写锁**（总案定唯一迁移执行方）。

## 三、与其它视角的衔接（重点：数据建模视角的落库面扩展）

1. **01 数据建模视角（持久化丢 runId）——最大衔接面**：
   - **裁定建议：trace_id 不单独落库列**。依据：trace_id 与 run_id 为 **run 级 1:1**，「按 trace 过滤」≡「按 run 过滤」——库内按 run 追溯用 run_id 列（01 视角），trace_id 只服务「日志-事件对齐 + wire 面」，不服务库内查询。建独立列 = 重复建设。
   - **追随决策**：若 01 视角选「完整信封 JSON 落库」（05 文档方向 B，payload 存含 runId/sequence/schemaVersion 的完整信封），trace_id 随信封**自然入 payload**，本方案零额外设计；若 01 选「run_id 列」（方向 A），trace_id 保持 wire + 日志面。**总案裁决点：trace_id 落库面追随 01 的最终决策，双方不得各自建 schema。** 01 视角验收「库中事件含 run_id」与本方案验收「wire 信封含 traceId」互为补充，不重叠。
2. **08 恢复重试视角**：`resumed-by` / `resumes-from` 是事件面结构字段（08/02 视角）；本方案 TR-03 的恢复链日志是**过程描述**（怎么走的），与事件字段（谁续谁）互补不重复。recovery.rs / restore_manager.rs 同文件串行。
3. **10 安全审计视角**：TR-03 工具日志补 `tool_call_id` 的前提 = 10 视角给 ToolContext 加 call_id 字段——**执行序依赖：先 10，后 TR-03 工具子项**；日志点补字段不替 10 视角做审计事件发射。
4. **02 事件归属视角**：信封 trace_id 注入点与 runId 注入点同一构造点（事件桥 emit）——同文件串行，总案定唯一执行方；02 的「终态后落库 / approval 双发」等异常模式的**条件告警日志**（复用 `EmitReport.dropped → tracing::warn` 样板）属 02 视角任务，本方案只知会不接管。
5. **09 时序并发视角**：created_at 毫秒化归 TR-05（日志对齐的直接需求）；payload 时间戳**语义**（执行时刻 vs 翻译时刻、单一时源）归 09——双方在总案确认「不改同一文件同一字段」，migrate.rs 单写锁；09 若实现「执行时刻打点」，TR-05 对齐规则可顺势引用，本方案不先行。
6. **07 前端消费视角**：S2 的 transport 透传（traceId 经既有封装层、core_get_status 响应带 trace_id）归 07/S2 承接方；本方案日志侧在 Rust 侧独立闭环，**不依赖前端透传结果**。
7. **03 子代理视角**：子代理 run 各自独立 trace_id（每 run 一枚，符合 S2「每 run 一枚」口径）；父-子关联仍靠 `subagent_run_id` / `parent_tool_call_id`（03 视角）。**本方案不为子代理建跨 run trace 树**——反过度设计：不做 OTel 式分布式 trace 树，trace_id 是 run 级关联键不是端到端 trace。
8. **04 工具原子观测视角**：tool-start/end 事件已发射；TR-03 补工具日志字段与 04 视角的事件面互补；工具执行入口文件（tool_exec 域）同文件串行。

## 四、未覆盖问题（诚实声明）

1. **「线程迁移丢 span」未实机复现**：基于代码路径（tokio 多线程 + spawn + `enter()` TLS）与 tracing 语义推断为可能发生（audit §五.5 同样声明）；TR-02 是防御性修复，TR-06 测试用 spawn 断言**钉死正确语义**而非复现原 bug——若未来实机验证迁移场景实际未丢，本方案改造仍成立（instrument 是正确形式）。
2. **事件侧时间戳语义不在本方案**：payload 时间戳「翻译时刻 vs 执行时刻」归 09 视角；本方案只做精度对齐，不改变打点时刻。
3. **日志体积治理不在本方案**：按日轮转已存在；cleanup_logs 只接线保留策略，不重设计轮转粒度/压缩策略。
4. **crash 文件消费端不在本方案**：前端日志面板/运维工具读取 crash 新段的适配归 07 视角或后续战役，本方案只管 Rust 侧产写（新增段向后兼容，旧解析不坏）。
5. **前端 traceId 透传不派单**：invoke 载荷透传、`core_get_status` 响应带 trace_id 按 S2 蓝图归 07/S2 承接方；本方案仅复述验收口径。
6. **全仓 ~200 处日志点未逐点核对**：外围 crate（agent-provider / conex-browser / conex-computer / conex-fs）只统计未逐读（与 audit 口径一致）；TR-03 只覆盖审计点名的编排/恢复/工具域，外围 crate 日志字段补齐不在本轮。
7. **恢复域「父归属查不到只留 warn」不扩事件**：restore_manager 归属解析失败的事件侧留痕归 08 视角；本方案保留既有 warn，不新增事件。
8. **锚点行号以派单时实测为准**：本方案所有锚点（events.rs / restore_manager.rs / 7 个 spawn 点 / 骨架函数）受上战役拆分影响已漂移（实测 core_run_commands.rs:5316 → 5314-5317），派单前必须执行开工动作三件套（快照 + git status + 行号重定位）。
9. **不构成任何 EL 关账**：本方案是建议面，验收全部以执行轮真跑记录为准；「日志可归属」≠「全链路可追溯」整体达成，其余缺口（持久化/读侧/前端）归其它视角。
