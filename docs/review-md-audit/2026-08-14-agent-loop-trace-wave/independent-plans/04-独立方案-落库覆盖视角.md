## 二、方案详述

### PC-01 · timer/cron 事件落库决策：明确「事件面不持久化」+ 读取面声明（本战役闭合项）；补落库登记为 R-CF3 前置依赖

**现状（代码验证）**：

- `timers.rs:198-209`：`TimerFired` 事件体 `session_id: String::new()`（注释自述「注册表每引擎一个、无会话归属；会话归属语义在 R-CF3 定时器会话化时定稿」）；事件仅入 `AgentEventSink` 缓冲。
- `engine_channels.rs:475-504`：`forward_drained_events` 以 `AgentEventEnvelope::new(event, None, None)` 直发桥——**runId 键完全缺席**，与契约文档（`conex-types/events.rs:1112-1115`「置空串或 `timer-<id>` / `cron-<id>` 伪 runId」）**不符**。
- 从不经 `EventQueue::push`（`orchestrator/events.rs:160-207`）落库。
- 注册表（`conex-types/events.rs:1062-1066`）却标 `TimerFired/CronFired = Critical`（「必达落库」），域文档（02-CF §4.7）承诺「数据面：落库 + 前端可观测」——**文档-实现三重矛盾**（分级、文档、实现）。

**落库的阻塞论证（为什么本战役内不能简单「补落库」）**：

1. **FK 硬阻塞**：events 表 `(session_id, sequence)` 主键 + `FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE`（`schema.rs:141-149`）。TimerFired 事件体 sessionId 为空串——若强行 `EventQueue::push("", ...)`，FK 必失败 → `PersistError` → 拖入 run 失败收口链。而 timer/cron **没有 run 上下文**（无 run 可标 `failed(event-store-write-failed)`），EventQueue 的失败收口语义天然绑定 run 状态机，定时器域**不存在可用的持久化通道**。
2. **前置决议缺失**：落库需要一个「挂哪个会话」的答案。事件体 `session_id` 空串是注册表级设计（每引擎一个），会话化决议属于 **R-CF3 定时器会话化**（timers.rs:206 注释自认「未定稿」）——跨域契约变更，超出本战役落库视角单一决策范围。
3. **「不假装」原则一致性**：挂着 Critical 分级却不落库，比「显式声明不落库」更不诚实；且与 PC-06 的「不假装可回放」同一哲学。

**方案定案**：

- **决策 A（本战役执行）**：明确「timer/cron 事件面不持久化」，且让**每个面都声明一致**：
  - 分类函数（PC-05）中 `TimerFired/CronFired = Critical + persist=false`、`TimerCancelled = Soft + persist=false`——Critical 分级保留语义 =「实时桥必达」，持久化决策独立显式声明（两个维度正交，见 PC-05）。
  - 注册表 JSON 条目与域文档同步标注「仅实时轨，不落库」；读取面声明（readme/契约文档）：timer/cron 触发痕迹的持久事实源 = `session_meta timer_<id> fired=true` + steering 条目（续 run 链）+ 续 run 的事件链，事件面不承诺历史触发。
  - **伪 runId 契约对齐（文档-实现漂移修复）**：`forward_drained_events`（engine_channels.rs:490-504）在信封构造处按 `TimerFired{timer_id}` / `CronFired{cron_id}` 注入 `timer-<id>` / `cron-<id>` 伪 runId（匹配 02-CF §4.7 定稿），消除「缺键 vs 空串」契约漂移。前端 `messageBelongsToRun`（`eventUtils.ts:30-39`）对缺键与空串判定一致，行为零变化（②转引 02 §三-2 + ①代码验证）。
- **决策 B（登记移交，不砍项）**：把「补会话归属落库」（timer/cron 入 events 表 + 按会话索引）登记为 **R-CF3 会话化的前置依赖项**——会话归属决议落定后，本决策 A 中的「persist=false」翻转条件已文档化（翻转点 = 事件体 sessionId 非空 + 无 run 持久化通道就绪，后者见 PC-02 的通道方案）。

### PC-02 · 任务域事件落库决策：task 终态 4 事件补落库；增量保持 Delta

**现状（代码验证）**：

- `bg_events.rs:254-260`：任务事件信封 `AgentEventEnvelope::new(event, None, None)` 直发桥；有 `consumer.on_task_event` 挂点但注释「消费器为 None（未注入）时仅发射事件」；`task_event_consumer.rs:89` 无 `append_event`。
- 7 事件（started/completed/failed/killed/output/heartbeat/suspicious）**全部不落库**；注册表却标 4 终态 = Critical「必达落库」（`conex-types/events.rs:1056-1059`）——**宣称与实现矛盾**。
- 任务域事件有真实会话归属（前端按会话消费、事件体带 sessionId 形态与 run 域同构）——**FK 可行，与 PC-01 的 timer/cron 阻塞本质不同**。
- 兜底现状（②转引 09 §5.2 + ①代码验证）：task-output 中间行由 `task-completed.line_count` / `task-failed.tail`（最后 20 行）+ 任务日志文件兜底；task-heartbeat 有 `.samples.jsonl` best-effort 落盘（`bg_events.rs:273-274`）。

**方案定案**：

- **task 终态 4 事件（started/completed/failed/killed）补落库**——与注册表 Critical 语义对齐，「后台任务生命周期」是会话级重要动作，「任何动作都有全链条记录」战役目标下终态无痕迹是明显缺口：
  - **通道复用 recovery 先例**：recovery-* 五事件已用「`reserve_sequence` 自取号 + 直写 `append_event`」在无 run 上下文下落库（`recovery_store.rs`）——任务域落库照搬该模式（**不新建通道、不扩 EventQueue 失败收口语义**，反过度设计：有先例不发明）。
  - **落库即声明**：任务事件是标准 `AgentEvent` 变体，payload 天然带顶层 type 键——落库后读侧 `parse_envelopes` 可解析，**不会重蹈 recovery-\*「落库但读不出」覆辙**（05 §三：recovery 直写 payload 无 type 标签）。
  - 失败语义：无 run 可标 failed → 落库失败 = `tracing::error!` + 失败计数（PC-06 的观测原语），**不阻塞任务执行、不假装可回放**（与 recovery 直写先例一致）。
- **task-output / task-heartbeat / task-suspicious 保持不落库，并显式声明**（消灭「靠不走队列侥幸」）：
  - output/heartbeat = Delta + persist=false：高频增量（逐行输出、采样周期），落库会烧会话序列号且无复现价值——中间内容事实源 = 任务日志文件 / `.samples.jsonl`（与 message-delta「message-end 全文兜底」同构的「文件兜底」）；task-heartbeat 的「真只丢增量无终态」盲区由 `.samples.jsonl` + 终态事件（补落库后）闭合。
  - suspicious = Soft + persist=false：留痕语义声明 = notifier 通知 + `.samples.jsonl` + 后续 task-failed/killed 终态落库（卡死告警的**结局**有事件面痕迹，触发瞬间仅实时）。
- 读侧可见性验收：补落库后经 `core_read_session_events` 必须可读（带 type 标签 + sequence 列回填，05 建议 8 的信封字段回填是本项前置）。

### PC-03 · subagent-started/ended 广播对称性：补壳层广播（先落库后广播）

**现状（代码验证）**：

- `orchestrator/subagent_events.rs:172-218`：`SubagentEventEmitter` 仅经 `EventQueue::push`（落库 + 取号），**无桥广播**；发射点在 `flow_graph.rs:1068/1194` 与壳层 `subagent_spawner.rs:446-484/574-612` 接线。
- 对比：subagent progress 有广播（`core_run_commands.rs:3602`，信封 runId=子 run）——**同一域：progress 只有实时、started/ended 只有落库，双轨不对称**（02 §三-4）。
- 架构约束：orchestrator crate 不应依赖壳层 EventBridge；广播必须经壳层桥（progress 能广播说明壳层持桥）。

**方案定案**：

- **补广播（壳层接线，主推）**：在壳层 `subagent_spawner.rs`（与 FlowScheduler 接线点同文件域）的 emit_started/emit_ended **之后**补信封广播——**先落库成功、再广播**（顺序保证与 `emit_approval_resolved` 先例一致，core_run_commands.rs:7479），信封 runId = 父 run（`SubagentEmitContext.parent_run_id` 已有），`parentToolCallId` 已随载荷在场。
  - 前端幂等：started/ended 以 subagentId/subagentRunId 键控（`subagentHandlers.ts` 消费形态，②转引 02 §三-4），广播与 wait 通道 feed 若并存，前端去重键现成。
  - 为什么补而不是「明确 cursor 拉取」：子代理生命周期是用户在等待时的**实时反馈面**（与 progress 同体验轨），只靠落库则要等会话重放/增量拉取才可见；且补广播是对称闭合（同域同轨），成本低（壳层有桥、载荷齐全）。
- **退化定案（若主控核前端后确认 wait 通道已覆盖实时反馈——诚实声明未核前端依赖）**：不改代码，改文档定案「subagent 生命周期以落库为权威、前端经会话重放获取；wait 通道提供实时」——**二者必居其一，禁止维持现状双轨不对称不声明**。
- 验收锚定「补广播」后：前端实时收到 started/ended（无需重放）；若走退化路径，验收改为文档声明 + `rg` 检查无「只落库不广播」类注释残留。

### PC-04 · approval-requested 双发修复：保留实时轨 + 收口 emit skip

**现状（代码验证，前端去重已核）**：

- 双发路径：审批门实时广播（`core_run_commands.rs:6168`，sequence=None）→ session-loop 入流（`executing_tools.rs:244-252` 推入 state.events）→ drive_outcome 落库 → 收口 emit 再广播（`:5447`，sequence=N）。同一事件两种 wire 形态。
- **前端去重现状（本会话实测，补 02 报告「未核前端」缺口）**：
  - `EventRouter.ts:166-189` `buildEventDedupeKey`：approval-requested 无 messageId → 实时轨（sequence=None）返回 **null 透传不参与去重**；收口轨（sequence=N）键 = `approval-requested:N`。
  - `ApprovalFlowMachine.ts:178-187` `approval_pending`：同一 toolId 重复 pending → **noop（already_pending）**——pending 期间双发被 Set 幂等兜住，**不双渲染** ✅。
  - **真实风险分支**：实时轨 requested → 用户批准 → resolved（`approval_resolved` applied，resolved.add + pending.delete）→ 收口轨 requested（sequence=N）后到 → `approval_pending` 执行 `resolved.delete + pending.add` → **已放行的工具重新挂起，需二次批准**。这是「先发后等」设计下收口重发的确定性竞态，非理论。

**方案定案**：

- **服务侧（主修复）**：收口 emit 对 `approval-requested` 复用 T09.1 message-delta 的 skip 机制（`:5440` 显式 skip 先例）——**落库照常（drive_outcome 持久化面不动），广播面只发一次（实时轨）**。定案语义：approval-requested 的 wire 形态唯一 = sequence=None（实时轨），与 message-delta 完全同构。

### PC-05 · 统一事件分类：单一分类函数同时产出「背压级 + 是否落库 + 桥优先级」

**现状（代码验证，三套口径逐一定位）**：

| 层         | 机制                                       | 位置                                   | 口径                                                                                                                                                                                                         |
| ---------- | ------------------------------------------ | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 持久化分流 | `EventClass`                               | `orchestrator/events.rs:35-58`         | NonPersistent = {message-delta, subagent progress}；**其余全部 Persistent**（含 task-output/heartbeat、timer-cancelled——实际不进 EventQueue，靠「不走队列」侥幸不落库）                                      |
| 背压注册表 | `BackpressureLevel` + `event_backpressure` | `conex-types/events.rs:197, 1043-1080` | Delta = {message-delta, subagent progress, task-output, task-heartbeat}；Soft = {subagent message/tool, task-suspicious, timer-cancelled}；其余 Critical（含 task 终态、timer-fired/cron-fired「必达落库」） |
| 缓冲丢帧   | `DropClass`                                | `buffer.rs:36-42`                      | Soft = 仅 message-delta；其余 Critical 永不丢                                                                                                                                                                |

三套集合两两不一致（05 §3.1 / 09 §5.1）；且注册表已有 `registry_drift` 护栏（`crates/conex-types/tests/registry_drift.rs`，锁定「enum ↔ 注册表 JSON ↔ 生成产物」）——**护栏在但只锁了背压单字段，没锁持久化决策**。

**方案定案**：

- **单一决策函数（语义正交化）**：在 `conex-types`（注册表/契约层）新建：

  ```
  pub struct EventPolicy {
      pub backpressure: BackpressureLevel,  // 实时桥投递保证（注册表语义）
      pub persist: PersistenceDecision,     // 是否落库（事件面持久化）
      pub bridge_priority: DropClass,       // 缓冲层丢帧分级
  }
  pub fn event_policy(event: &AgentEvent) -> EventPolicy   // 单一 match 派生三值
  ```

  三个决策由**同一 match 表达式**产出——任何事件的三决策在同一处定义，新增事件只改一处，集合漂移从结构上不可能。关键澄清：「统一」不是把三值合并成一个枚举（三决策确实不同构：如 task-output = Delta + 不落库 + Critical，message-delta = Delta + 不落库 + Soft——丢帧语义不同），而是**单一事实源 + 正交声明**。

- **消费方迁移**：`EventQueue::push` 的 `is_non_persistent`（`orchestrator/events.rs:61-63`）改调 `event_policy(...).persist == NoPersist`；`buffer.rs` 的 `drop_class_of` 改调 `event_policy(...).bridge_priority`；`event_backpressure` 函数保留为 `event_policy(...).backpressure` 的薄壳（或直接收敛——保留薄壳减少波及面，由主控裁决）。`orchestrator` 的 `EventClass` 枚举退役或降为 `PersistenceDecision` 别名。
- **注册表联动**：事件注册表条目扩展 `backpressure / persist / bridgePriority` 三字段；`registry_drift` 护栏从「背压单字段锁定」升级为「**三字段双向锁定**」——分类函数 ↔ 注册表 JSON ↔ 生成产物（TS 绑定镜像三字段同步，normalizer-drift 修复联动，07 视角）。
- **漂移清零后的显式结论**（各事件域定案汇总到单一函数，配合 PC-01/02）：

  | 事件                                                                                           | backpressure             | persist                            | bridge_priority      |
  | ---------------------------------------------------------------------------------------------- | ------------------------ | ---------------------------------- | -------------------- |
  | message-delta                                                                                  | Delta                    | 否                                 | Soft（可丢）         |
  | subagent progress                                                                              | Delta                    | 否                                 | Critical（缓冲不丢） |
  | task-output / task-heartbeat                                                                   | Delta                    | 否（PC-02 定案）                   | Critical             |
  | task-suspicious                                                                                | Soft                     | 否（PC-02 定案）                   | Critical             |
  | timer-fired / cron-fired                                                                       | Critical（实时必达语义） | 否（PC-01 定案，R-CF3 翻转点注释） | Critical             |
  | timer-cancelled                                                                                | Soft                     | 否（PC-01 定案）                   | Critical             |
  | task 终态 4 事件                                                                               | Critical                 | 是（PC-02 定案）                   | Critical             |
  | 其余 Critical 族（agent/turn/tool/message-end/审批/审计/subagent started-ended/goal/recovery） | Critical                 | 是                                 | Critical             |

### PC-06 · 落库失败路径：维持「不假装可回放」，不做自动重试

**现状（②转引 02 §五-8 / 05 §4.2 + ①代码验证）**：

- 链路自洽且测试锚定（`mid_failure_terminal_reuses_failed_sequence_no_hole`）：push 失败 → PersistError → run failed(event-store-write-failed) → 终态复用失败序列 best-effort → cursor=失败序列。**无自动重试，语义 =「不假装可回放」**。
- 小缺口 a：`finalize_failed`（core_run_commands.rs:5823）runtime-error 用 `queue.push`（非 best-effort），store 已坏时 push 失败仅 `let _` 吞掉 → run 记录可能停留非终态。
- 小缺口 b：`fail_event_store` 依赖 update_run_status 成功，store 彻底损坏时循环风险极低（每次仅日志）。

**方案定案**：

- **主决策：不做自动重试**。论证：
  1. 语义自洽且被测试锚定——「一个库里只有一半事件的 run」重试落库无法保证因果完整，「不假装可回放」本身就是正确语义（半链保留为诊断材料，05 §4.2）。
  2. 自动重试引入「部分成功」歧义（重试成功的事件算已落库？序列连续性？Q25 无空洞语义被破坏？）——复杂度爆炸、收益低。
  3. 先例一致：上战役 CT-01 已定案「不自动重试」（12 报告 §3.4「持久层错误码透传链…不自动重试语义」），本战役同族机制沿用。
  4. 重试前提（瞬时失败占比）未实测：SQLite 本地库失败主场景是损坏（写入 latch）而非瞬时（未核 busy_timeout 配置），为假设场景建设重试机制属过度设计。
- **两个小修（不改变主语义）**：
  - 小修 a：`finalize_failed` 的 runtime-error 改走 `push_terminal_best_effort`（既有路径，`orchestrator/events.rs:210-235`）——消除「非终态停留」窗口，失败时返回 SequencedEvent 而非吞错。
  - 小修 b：落库失败观测 = `tracing::error!` + 模块级失败计数（B1 毒化测三要素形态：error! 成对 + `AtomicU64` + 计数 getter，12 报告 §3.6 模板）——失败可观测、可断言，不新增设施（复用既有原语，反过度设计零新基建）。
- **边界白名单（若主控在总案裁决坚持重试的保留面）**：仅对瞬时类错误码（如 SQLite busy/locked，需先核 busy_timeout 现状）做 ≤2 次有限重试 + 短退避；损坏类错误码直接走现有失败链。**本方案默认不采纳**，列此只为裁决留档。
- 终态矛盾窗口（run-terminal 落库成功但 update_run_status 失败 → 事件说 completed、记录说 failed）：restore 对账归恢复视角（05 建议 6 / 08 视角），本方案登记衔接、不重复设计。

| ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |

### PC-07 · 迟到事件（run-terminal 之后）时序与归属规则定案

**现状（②转引 02 §五-5 + 05 §4.1）**：

- run-terminal 之后确实有事件落库：审计排空（audit_worker.await 在 terminal 发射后，core_run_commands.rs:5493-5500）、子代理收尾（subagent-ended/progress，:5538/:5543）、goal 续轮（goal-round-completed / goal-continuation-decided，:5610/:3199/:4688）、空闲态（push_emit_idle_event，:7027）。
- 「run-terminal 是流尾」不成立；尾事件归属语义未定义 → 按 run 切分时间线会少收尾事件或误收相邻 run 事件。

**方案定案**：

- **不重排收口线**：审计排空与 goal 评估在 terminal 之后是语义必需（先宣告终态、再等待审计队列排空、再评估续轮）——重排（先发尾事件再发 terminal）会扭曲 goal-round-completed 的语义（它评估的是收口后的状态）。顺序保证维持现状。
- **归属语义定案（边界定义写进 read_run_events 契约）**：
  1. **run 收尾区**：run-terminal 之后、同一 runId 的事件（审计排空 / subagent-ended 收尾）归属该 run——按 run 查询返回区间 = [run 首个事件, 收尾区最后一个事件]，收尾区事件以同 runId 续排。依赖 02/05 视角「持久化 run_id」落地（本方案的归属判定键 = 落库 run_id 列）。
  2. **goal 轮次域**：goal-* 事件跨 run 边界（round-started 在 agent-start 之前、round-completed 在 terminal 之后），按 goal round 键控，**不属于任何单 run**——按 run 查询的边界明示「goal 事件不归 run，归轮次」，避免误收。
  3. **空闲态**：runId=None（如手动压缩）归会话域。
  4. **打断场景**：run-interrupted（restore 写）归属被打断 run 的收尾区（02 §五-1 缺口 A 的读侧可见性修复归 05 视角，本方案定案其归属语义）。
- **时序语义**：sequence 全局单调不变；「run-terminal 是流尾」修正为「run-terminal 是该 run 主体流的流尾，收尾区以同 runId 续排」——写入 `read_run_events` 契约文档与前端水合文档（07 视角的 UI 时间线消费按此定义）。
- 验收锚定：契约测「按 run 查询返回区间包含收尾区事件、不含 goal 事件」；前端 run 时间线渲染以收尾区为 run 终点（若 07 视角实现 UI）。
