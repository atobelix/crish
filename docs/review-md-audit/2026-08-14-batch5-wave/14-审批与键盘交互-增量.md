## ② 逐发现项

### A-01【黄】R-06 未修复：finalizeAgentMessages 仍按会话粒度清流，同会话多 agent 并行仍误伤

- **证据**：`apps/crish-desktop/src/store/sessionAgentActions.ts:200-203`：`queueMicrotask(() => { clearSessionStreams(sessionId); })`；`streamingStore.ts:345-347` `clearSessionStreams` → `clearSession(sessionId)` 整会话清空 byKey。
- **缺陷机制**：新增的残余流提取（:180-188）只把**正在 finalize 的那个 agent** 的 liveText/liveThinking 合入持久化消息，随后仍然按会话清空全部流。同会话另一 agent 仍在流式时，其流被先清空，等它 finalize 时 `getStreamText` 已空 → 尾部文本/思考丢失、视觉断流。上轮 R-06 指出的按 messageId（或 agent 维度）精确清理从未落地。
- **修复建议**：`clearSessionStreams(sessionId)` 改为按 messageId 集合清理（finalize 的 agent 的消息 id 列表），或 `clearSessionStreams(sessionId, agentId)` 过滤。

### A-02【黄】倒计时全链路半连通：remainingMs/onTimeout 生产零接线

- **证据**：全仓 `rg "remainingMs"`：生产消费点仅 `ApprovalAskCard.tsx:220-224`（透传给 useApprovalCountdown）与 `ApprovalCountdown.tsx`；**渲染方 `CompactToolRow.tsx:83-99` 未传 `remainingMs`/`onTimeout`**；唯一传值处在 `api/ApprovalAskCard.test.tsx`（测试）。`rg "onTimeout"` 生产侧同样零调用方。
- **缺陷机制**：进度条（`{remainingMs != null ? <ApprovalCountdown/> : null}`，ApprovalAskCard.tsx:382-384）在产品中永不渲染、`onTimeout` 永不触发——超时自动派发功能「实现了但没接线」（§15.2 半连通）。倒计时 hook 本身修好了（见 A-03），但接不了线等于白修。
- **修复建议**：在 AgentCard / ChatCard 侧注入 deadline（如 `tc.approvalMeta` 或后端超时字段）并接线 `remainingMs` + `onTimeout`（自动拒绝或提醒），或在收尾清单显式标注「延期」，禁止以 hook 测试绿冒充交付。

### A-03【黄】R-08 部分修复：动态倒计时已修（闭包初值冻结解除），但 100ms 硬编码心跳保留且未提取常量

- **证据**：对比 f1a2a604 版 `useApprovalCountdown.ts`（`setInterval` 内用闭包捕获的初始 `remainingMs` 算 pct，进度永远 100% 冻结）与 ed3434e9 版 `useApprovalCountdown.ts:55-74`（`endTime = Date.now() + remainingMs` + `(endTime - Date.now())/total` 动态差值）——动态化真实生效，且超时派发从「仅初始 ≤0」变为「实时到期触发 + busy 解除补发」（:78-85）。
- **残留**：`useApprovalCountdown.ts:74` 仍 `setInterval(..., 100)` 硬编码，未提取 `TICK_MS` 常量；每卡 10 次/秒心跳重渲染整卡（`timeoutPercent` 状态 → ApprovalAskCard 整卡重渲），remainingMs 大时（分钟级）无效心跳上千次。R-08 建议的「提取常量 / 按 deadline 单次 setTimeout」只做了一半。
- **修复建议**：提取 `TICK_MS`；心跳只更新 `ApprovalCountdown` 子组件（状态下沉）或改为「首帧 100% + deadline 前一次性刷新」。

### A-04【黄】useApprovalKeyboard Esc 处理器全局劫持：无 root 包含性校验

- **证据**：`apps/crish-desktop/src/components/agent-card/useApprovalKeyboard.ts:47-58`：`confirmArmed` 时挂 `window.addEventListener('keydown', onKey, true)`，对**任意焦点位置**的 Escape 执行 `preventDefault() + stopPropagation()`。对比同一文件的 Enter 处理器（:92-115）有 `rootRef.current.contains(target)` 校验与 textarea/contentEditable 排除。
- **缺陷机制**：armed 期间全应用 Esc 被捕获层吞掉——对话框无法 Esc 关闭、弹出层无法 Esc 收起、编辑器无法 Esc 取消；违反 AGENTS §8 / CODE_MODIFICATION「全局按键事件劫持必须校验焦点在容器内部」铁律（Enter 做对了、Esc 没做，同一 hook 内不自洽）。Esc 测试（useApprovalKeyboard.test.ts:153-182）只 `window.dispatchEvent` 直发，未覆盖「焦点在卡片外按 Esc 不应拦截」分支。
- **修复建议**：Esc 分支补 `rootRef.current?.contains(e.target)` 校验（或改为 `root.addEventListener` 非捕获）；测试补「外部焦点 Esc 不拦截」用例。

### A-05【黄】'completed' 类型逃逸死分支（REMEDIATION-06 自称「typeguard」反向引入逃逸）

- **证据**：`useChatApprovalHandlers.ts:147/:197/:294/:383` 与 `useAgentToolApproval.ts:114/:171` 共 6 处 `(currentTc?.status as string) === 'completed'`；而 `store/types.ts:245-246` 定义 `MessageToolCallStatus = 'running' | 'success' | 'error' | 'pending_approval'`——'completed' 不在联合中，全仓生产代码无任何位置写入 toolCall status='completed'（仅 agent/session/message status 用 'completed'）。
- **缺陷机制**：`as string` 属「类型逃逸」（§7 / CODE_MODIFICATION 类型逃逸红线），且守卫目标是类型系统中不可能的值 → 死分支；若真担心引擎事件注入非法 status（helpers.ts:119-122 确有 `as MessageToolCall['status']` 无校验强转），应在边界校验或扩展联合类型，而不是在 catch 里比对幻影值。
- **修复建议**：删除 6 处 'completed' 分支；如要防御非法 status，在 `commitToolPatchToSession` 边界做白名单校验（非 'pending_approval'/'running'/'success'/'error' 一律拒收或归一）。

### A-06【黄轻】R-04 timeline 签名修复留洞：blocks>0 且尾 text 块为空时 msg.text 未入签名 + 签名逻辑零测试覆盖

- **证据**：`timelineNormalizer.ts:315-320` 仅当 `blocks.length === 0` 时把 `hasText: Boolean((msg.text||'').trim())` 纳入签名；而 `buildAssistantTimeline` 的 `text-full` 回退分支（:248-250）在「有 blocks 但无 text 项被推入」时消费 `msg.text`——此时签名（最后 text 块的 `e` 标记 + blocksProj）不含 msg.text 内容，`msg.text` 从 '' 变非空（或继续增长）时签名不变 → 缓存命中返回缺正文的陈旧 timeline。`timelineSignature` / `buildAssistantTimelineCached` 在 `timelineNormalizer.test.ts`（113 行，仅 7 用例）中**零用例**（rg 无命中）。
- **缺陷机制**：签名覆盖面与 timeline 输出输入面不一致（签名注释自称「覆盖面 = buildAssistantTimeline 的全部输入依赖」，但 text-full 分支的 msg.text 是反例）；空→非空转换修复只覆盖了 blocks.length===0 路径。
- **修复建议**：在 blocks.length>0 分支同样投影 `hasText`（或把 text-full 场景并入「最后 text 项 = 流式区」约定并让调用方按流式区处理）；补签名缓存回归测试（空→非空首帧、纯流式帧引用稳定、工具事件失效三态）。

### A-08【黄】useChatApprovalHandlers 有效行数触 400 业务上限 + 13 返回值上帝 hook 形状

- **证据**：自测（block-comment-aware 计数）有效行 **400/400**（任务书口径 404）；返回 13 个状态/回调（useChatApprovalHandlers.ts:429-443）；`scripts/check-line-counts.mjs` 目标路径仅 `apps\crish-desktop\src\components\chat-composer`——**该文件不在任何门禁扫描范围内**，超标无 CI 拦截。
- **缺陷机制**：§5 业务逻辑 ≤400 上限触顶；单一 hook 同时承载挂起扫描、汇总派生、单批批准/拒绝、回滚守卫、批量配对——职责已偏重（批量与单条逻辑高度同构，可抽 `resolveBatchPairs`/`rollbackGuard` 纯函数）。

### A-09【黄轻】审批锁为实例级：同一 toolId 双 hook 实例可绕过防重入

- **缺陷机制**：同一 toolId 若在侧栏 AgentCard 与主时间线内嵌面板同时渲染，两侧各自通过锁检查 → 同工具双发 `engineApproveTool(tid)`；单实例内防重入真实有效（测试 :340-367 覆盖），但跨实例无共享锁。引擎侧若无幂等去重则重复执行。
- **修复建议**：锁提升为模块级 `Map<string, Promise<unknown>>`（或 store 级 in-flight 注册表），hook 实例间共享；至少注释声明「实例级锁」边界。

### A-010【黄轻】catch 防倒退守卫对「已 error 态」无保护：覆写真实错误输出
