## ② 逐发现项

### R-01【黄·接近红·未修复】SessionCoordinator 提交版仍零生产调用；删除会话不清理 streamingStore

- **证据**：`store/SessionCoordinator.ts:23-40` 定义 `deleteSessionCascade`（清 session + streaming `clearSession` + snapshots + terminal）。**生产调用方仍为零**——仅 `sessionStore.ts:185`、`storeAccess.ts:170-171` 逐层再导出，消费方只有 `SessionCoordinator.test.ts:58/90/91`。
- **缺陷机制**：真实删除路径 `sessionCrudActions.ts:409-445`（`deleteSession`）仍只 `dropTerminalForSession`(:421) + `clearMessageSnapshots(id)`(:442)，**无 `clearSessionStreams(id)`** → 删除会话后 `streamingStore.byKey` 条目残留（内存泄漏 + 幽灵流）。
- **修复建议**：在 `sessionCrudActions.deleteSession` 的 `if (removed)` 块补 `clearSessionStreams(id)`（最小修复）；或把 `useSidebarContextMenu` 的删除调用点改走 `deleteSessionCascade`。二选一，禁止以测试绿冒充交付。

### R-02【黄·未修复】快照 undo 面仍只存不撤（save 已接、恢复未接）

- **证据**：`MessageVirtualizer.tsx:88` `useUndoWithScrollAnchor(containerRef, manager)` 仍**不使用返回值**；`useUndoWithScrollAnchor.ts:23-70` 的 `performUndoWithAnchor` 生产零消费；`api/MessageSnapshots.ts:105` `applyDelta` 生产零消费；`undo()`(:278) 生产零消费。
- **缺陷机制**：快照系统「只存不撤」——本轮虽把 heightMap 灌进 delta（恢复数据已就绪），但恢复闭环（`snaps.undo()` + `applyDelta` + `hydrateHeightMap` + `performUndoWithAnchor`）仍只在测试。
- **正向注**：VSM 高度捕获链**已真实接线**（`MessageVirtualizer.tsx:81-86` register/unregister + `messageSnapshotsBridge.ts:62` getActiveVsm + `:97-112` saveMessageSnapshot 自动 capture）→ 撤销恢复的输入数据已备好，只差产品入口。
- **修复建议**：撤回二次确认加「恢复」入口（undo + 锚定）；或显式在收尾清单标注延期。

### R-03【黄·未修复+加剧】store→components 反向依赖保留；applyStream 测试双份

- **测试双份**：`streamingStore.test.ts:128-254`（applyStreamText 6 例 + applyStreamTools 4 例）与 `streamMessageViewModel.test.ts:7-125`（同 10 例**完全重复**）——同一批函数测试跑了 2 遍，共 20 例冗余执行。

### R-04【黄·部分修复】single dispatch 已修复；「引用变化不重建」测试/注释矛盾未解；sessionsIdKey 仍死导出

- **正向**：`autoIndexMiddleware.ts:69-135` 重写为**单次原子派发**——对象 partial 在同一个 `rawSet` 内合并 `sessionsById`（`:115-129`），消除上轮的「set 后 get() 再二次 set」双派发；新增测试 `autoIndexMiddleware.test.ts:135-152` 断言 `callCount === 1` 且每帧 sessions 与 sessionsById 同步。**R-04 主痛点已修**。
- **未解**：测试 `autoIndexMiddleware.test.ts:103-110`「does not rebuild when sessions array ref changes but id set is unchanged」仍断言 `toStrictEqual(mapBefore)`——实现 `:98/:117` 在 `partial.sessions !== prevSessions` 时**确实重建**，断言只比内容相等（重建后内容相同照样绿）；文件头注释 `:8`「只要 sessions 数组引用发生变化，就重建 map」与测试名**自相矛盾**。改 `toBe` 会红 → 该断言仍是注水（且矛盾）。
- **死导出**：`sessionsIdKey` 仍 `export`（`:152`），生产零消费（仅测试 :6/:62-64）。
- **修复建议**：测试名/意图改为「数组引用变化 → 原子重建且内容相等（toBe 引用不同）」，或删除该误导用例；删除 `sessionsIdKey` 死导出。

### R-05【黄·未修复】estimateBytes 不计 messages 全量副本，5MB LRU 失真

- **证据**：`api/MessageSnapshots.ts:251` `snapshot = { ...entry, id, delta, byteSize }` 保留**完整 `entry.messages` 副本**，但 `:244-250` `estimateBytes` 只计 `delta.inserted` + heightMap + diffFilePaths（`:174-191`）→ 全量副本内存**未计入** byteSize。
- **缺陷机制**：撤回快照的 `messages` 是**整个消息列表**，内存成本显著但被低估 → 全局 5MB 淘汰阈值失真，实际占用可能超限。
- **修复建议**：byteSize 计入 `messages` 序列化长度，或快照改引用 + 写时复制；按真实成本校准 LRU。

### R-06【黄·未修复】finalizeAgentMessages 整会话清流，同会话多 agent 并发误伤

- **证据**：`store/sessionAgentActions.ts:200-203`：`queueMicrotask(() => clearSessionStreams(sessionId))`——按会话清空 `byKey` 全部条目。
- **缺陷机制**：同会话多 agent 并行流式时，先 finalize 的 agent 会清掉同会话其它 agent **仍在流中**的条目 → 视觉断流/状态丢失。
- **正向注**：本轮新增 `:180-188` 将残余 `liveText`/`liveThinking` 从 streamingStore 合入持久消息（防数据丢失，好），但清流仍按整会话粒度。
- **修复建议**：按 messageId（或 agent 维度）精确清理已 finalize 的消息流，而非整会话 `clearSessionStreams`。

### R-09【黄轻·新增】saveSessionSnapshot 零生产调用（死导出）

- **证据**：`messageSnapshotsBridge.ts:113-135` `saveSessionSnapshot` 仅测试使用（`messageSnapshotsBridge.test.ts:192-212`「辅助函数正常工作」）；生产 `grep` 仅命中定义与桥内转发。

### R-10【黄轻·新增】estimateDeltaBytes 死导出

- **证据**：`api/MessageSnapshots.ts:153` `estimateDeltaBytes` 生产零消费（仅定义；save 走 `estimateBytes`）。
- **修复建议**：删除或并入 estimateBytes（若未来 undo 成本统计需要再导出）。

### R-11【黄·基线登记】「上帝 Store」：sessions 寄生于 layoutStore

- **证据**：`sessionStore.ts:27` `export const useSessionStore = useLayoutStore;`；`layoutStore.ts:191-247` 单 store 混 layout chrome（workspaces/uiSize/tabMode）、session 域（sessions/sessionsById/agents）、DnD 瞬态（draggedTab/dropPreview）、composer drafts、settings overlay。`withAutoIndex` 因此包住**整个 layout store**（`layoutStore.ts:195`）。
- **定性**：属**基线既有**（`sessionStore.ts:5-16` OPT-C1 ownership note 已自述「god-object … intentional residual」，非本轮引入）。审计按 review.md §4 登记为需排期的 SD 债，不判为新缺陷；但 `withAutoIndex` 覆盖全 store 使 sessions 索引中间件与布局瞬态耦合，值得留意。
- **修复建议**：排期拆分 session 域出 layoutStore（独立 `sessionStore` 实例 + 桥接），纳入 34-收尾清单。
