### R3 红 · 低（条件可达）· registerChannelsAsync 绕过安全包装 → 启动期未处理拒绝

- **证据**：
  - apps/crish-mobile/src/notifications/channels.ts:111-126——`Promise.all` 内直接调 `api.setNotificationChannelAsync(...)`（裸调用），无 try/catch；
  - apps/crish-mobile/src/notifications/expoNotificationsFacade.ts:159-171——`setNotificationChannelAsyncSafe` 已提供但**未被任何生产调用方使用**（"8 个安全包装"实际接线 7 个，漏的恰是启动路径）；
  - apps/crish-mobile/src/notifications/index.ts:64 `await registerChannelsAsync();` 无兜底；
  - apps/crish-mobile/src/notifications/permissions.ts:85 request() 内同路径。
- **缺陷机制**：P0-1 自身契约是「系统通知面不可用**或调用失败** → 空值/空操作，绝不向调用方抛错」（expoNotificationsFacade.ts:134 注释）。若原生 setNotificationChannelAsync 在真实设备 reject（渠道注册失败在 OEM 设备上可达），Promise.all 整体 reject → initNotificationLayer 抛未处理拒绝 → **启动即崩**——正是本批次要修的病症。degraded.test.ts 只覆盖「api=null」分支，未覆盖「api 存在但注册失败」分支。
- **修复建议**：channels.ts 改用 `setNotificationChannelAsyncSafe`（返回 boolean，失败跳过该渠道）；或 registerChannelsAsync 内逐渠道 try/catch 收敛。补一条「api 存在但注册 reject → 返回 0 不抛」的单测。

### Y1 黄 · 观察性 · 8 个安全包装静默吞错（能力缺失 vs 调用失败不可区分）

- **证据**：apps/crish-mobile/src/notifications/expoNotificationsFacade.ts:137-239——每个 wrapper 的 `catch { return null; }` 均无日志；loadApi 失败有 console.warn（101-103），但**模块加载成功后的运行期 API 调用失败无任何痕迹**。
- **缺陷机制**：「平台能力缺失→降级」（正确语义）与「运行期调用失败→应可观测」被同一空值折叠。e.g. getPermissionsAsync 运行期抛错 → 静默返回 null → UI 表现为 undetermined，与 Expo Go 降级无法区分，排障无入口。违反 §10 观察性纪律（对应 CODE_MODIFICATION「静默吞错与兜底掩盖」——本处降级是设计语义，但应保留可观测边界）。
- **修复建议**：catch 内补 console.warn（标识 wrapper 名与错误），与 loadApi 的 warn 同风格；不改变返回语义。

### Y2 黄 · 低 · 降级模式下去重登记不撤（「未呈现」记为「已呈现」）

- **证据**：apps/crish-mobile/src/notifications/pushConsumer.ts:335-343——`mark` 先于呈现，失败撤消依赖 presentSystemFn **reject**；但 Expo Go 降级下 `presentSystemPushAsync` 返回空串（pushConsumer.ts:156-168 映射 null → `''`，**resolve 而非 reject**）→ 去重条目保留 → 同 dedupeKey 后续后台到达被 deduped 跳过。
- **缺陷机制**：语义死角。实际影响近零（应用内 ingest 恒保留且幂等覆盖；进程内系统通知面不会恢复），且文件注释诚实标注（154「去重登记不撤，与无呈现语义一致」）。但若未来系统面改为进程内可恢复，会漏呈现。
- **修复建议**：presentSystemPushAsync 返回空串时撤登记（与 reject 同路径），或保留现状并升级注释为已知权衡。

### Y3 黄 · 低 · checkHostFingerprint 的 stored 参数语义误用

- **证据**：apps/crish-mobile/src/adapters/wiring/pairingWiring.ts:724-738——双信道冲突检查调用 `checkHostFingerprint(this.pendingHostFingerprint, okFingerprint)`，把 **pair.challenge 下发值**当作「stored（secure-store 历史存储位）」参数传入；函数文档语义是存储位（pairProtocol.ts:188-210）。
- **缺陷机制**：逻辑结果正确（两值齐备时做相等比较，冲突即拒），defense 标签（verified/no-stored/no-delivered）在此处语义失真，仅 `.ok` 布尔有意义。可读性/文档债务，非功能缺陷。
- **修复建议**：抽出独立相等判断（如 `fingerprintsAgree(a, b)`）供双信道检查使用，checkHostFingerprint 保持存储位语义。
