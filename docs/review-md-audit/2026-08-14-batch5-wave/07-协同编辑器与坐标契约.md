## ② 逐发现项

### H1（黄·一致性 §11）结构级 undo() 整树快照覆盖，吞并发远端变更

- **证据**：`crates/conex-doc-collab/src/session_undo.rs:103-105`（`self.tree = entry.pre.tree.clone(); self.text_engine.restore(entry.pre.text.clone())`）；`session_tests_undo.rs:110-111` 注释自认「undo 恢复的是 Agent apply 前快照 → 快照时刻 remote/sys 尚不存在，故一并消失——符合『整批 pre 快照』语义」。
- **缺陷机制**：`undo()` 恢复的是**该批 apply 之前**的整树+整文本引擎快照，而非该批的局部逆元。若该批期间有并发 `Origin::Remote`/`System` 写入（多端协同），undo 会把这些远端插入的块、远端文本编辑**一并抹掉**。测试 `a_col_04_undo_origin_filter`（:58-71 插入 remote/sys 后 undo Agent 批）证实该行为未被断言拦截（只注释承认）。与 `CODE_MODIFICATION_SYSTEMIC_DISCIPLINE.md` 铁律「撤销时用 CRDT 局部因果逆元（InverseOp）按 Origin 精确回退，禁止全量快照覆盖」冲突。
- **本波区分**：新交付的 `text_undo`（session_undo.rs:143）才是局部因果逆元（仅回退本地 Client 变更，远端 100% 保留，`session_crdt_concurrent_text_undo_preserves_remote_edits` 实证）。问题在于**产品侧 undo 入口选哪一个**——若走 `undo()`，并发安全不成立。
- **修复建议**：产品 undo 键路径优先接 `text_undo`（文本）+ 结构级 undo 改造为「该批结构 ops 的逆元重放」而非 pre 快照；短期至少把「undo() 吞并发远端」写为显式契约边界（单端会话才允许），并补一条 pin 该行为的回归断言（当前测试只注释承认、无断言）。

### H5（黄·坐标契约 §11/§13）代理项内部偏移：forward/reverse 非互逆 + 与 align 语义三分歧

- **证据**：`packages/block-paper-contract/src/coordinates.ts:133-157` `utf16OffsetToUnicodeScalar('A🎉B', 2) = 2`（循环把高位代理项计入 → **ceil 语义**）；`:163-184` `unicodeScalarToUtf16Offset('A🎉B', 2) = 3`；`:100-109` `alignToSurrogateBoundaryFloor('A🎉B', 2) = 1`（**floor 语义**）。
- **缺陷机制**：对同一「代理项内部偏移」（指向低位代理项起点）输入，三个函数给出 1 / 2 / 3 三种结果。`asUtf16Offset` 接受任意非负整数（不拒绝内部偏移），因此调用方误传内部偏移时：forward→2、reverse(2)→3，**round-trip ≠ 原值**，「双向单射」声称在未定义输入域上不成立。现有测试只覆盖代理项边界对齐后的合法位置（coordinates.test.ts:98-107 等），未 pin 内部偏移分支。
- **修复建议**：二选一：① `utf16OffsetToUnicodeScalar` 对 `isInsideSurrogatePair(text, offset)` 输入抛错（fail-fast，与 align 语义不打架）；② 文档化 floor 语义并在函数内先 `alignToSurrogateBoundaryFloor` 再转换（保证 forward/reverse 互逆）。补内部偏移的显式断言测试。

### H6（黄·结构 §5/§13）坐标转换 3 份实现 + DiffReplaceResult 字段语义相反

- **证据**：
  - `packages/editor-kit/src/diff/diffToReplace.ts:14-122` 内联 `isHighSurrogate/isLowSurrogate/utf16OffsetToUnicodeScalar/unicodeScalarToUtf16Offset/countUnicodeScalars`（独立第 1 份）；
  - `packages/block-paper-contract/src/coordinates.ts`（第 2 份，带品牌类型）；
  - `packages/block-paper/src/leaves/pm/diffToReplace.ts:12-22` 从 contract 导入（正确复用，第 3 份只是 diff 算法）。
  - **字段语义相反**：editor-kit `DiffReplaceResult.start = UTF-16 偏移`（diffToReplace.ts:127-131 `start: number /** UTF-16 替换起始偏移量 */`），block-paper 版 `start: startScalar as number`（pm/diffToReplace.ts:112-113 注释「兼容传统接口访问（标量值）」）。ASCII 文本下两值相等，混用不报错但静默漂移。
- **缺陷机制**：同一算法两套实现，修 bug 需改两处；调用方混淆 `start` 字段坐标系时产生 Off-by-N。对 ASCII 无感、对 Emoji 静默错。
- **修复建议**：SD 包：editor-kit 的 `diffToReplace` 改为复用 `@crish/block-paper-contract` 转换函数（消除内联重复），并统一 `DiffReplaceResult` 字段契约（`startU16/endU16/startScalar/endScalar` 全显式，`start/end` 兼容字段仅保留一处且注明坐标系）。

### H7（黄·可维护 §13）buildCodeTextEditIntent 默认 baseContent='' → 易错 API

- **证据**：`packages/block-paper/src/leaves/code/CodeLeafModel.types.ts:95` `const text = baseContent ?? '';`——未传 baseContent 时，非零 startU16 在空文本上 `utf16OffsetToUnicodeScalar('', n)` 恒为 0（coordinates.ts:138-141 limit=0），range 静默变 `[0,0]`。
- **现状**：两个调用点（CodeLeafModel.ts:301,374）均传了 `oldContent/pre`，安全；但函数签名把危险默认值暴露给未来调用者，且无测试覆盖「未传 baseContent」的失败分支。
- **修复建议**：签名改为必传 `baseContent: string`（或内部读 `this.content`），删除 `?? ''` 默认；补一条未传/误传的回归断言。

### H8（黄·安全基线 §13）unsafe impl Send/Sync for DocSession 无安全论证

- **证据**：`session.rs:222-223` `unsafe impl Send for DocSession {} / unsafe impl Sync for DocSession {}`，**无任何注释**；对比 `text_engine.rs:35-37` 的 TextHost unsafe impl 有明确论证（「yrs 内部在无 sync feature 时未对 closure 标记 Send/Sync，但仅在单线程或持锁访问」）。
- **缺陷机制**：DocSession 被 `conex-note-runtime/src/store_backend.rs:146` 放 `Arc<Mutex<DocSession>>`，跨线程需要 Send/Sync；yrs undo 在无 sync feature 时内部含 Rc 类结构，unsafe 声明合法的前提是**所有 &mut 访问均持锁**。当前无注释论证该前提，后续若有人 clone/移出 session 逃逸锁会形成 UB 面。
- **修复建议**：在 unsafe impl 上方补安全论证注释（访问约束：仅经 Mutex 持锁；无 &DocSession 逃逸），或将 `TextEngine` 内 Yrs 句柄改为 `Mutex<TextHost>` 消除 unsafe（更彻底，SD 债）。

### H9（黄·一致性 §6/§11）text_undo 忽略 UndoManager 返回值，无操作仍推进 rev

- **证据**：`text_engine.rs:346`（`let _ = host.undo_mgr.undo_blocking();`）与 :390（redo 同）；`session_undo.rs:150-158` 不校验 can_undo，无操作也 `rev + 1` 并 emit_commit（update 字节与撤销前相同）。
- **缺陷机制**：调用方误在无可撤项时调用 → 产生无实际变更的提交，rev 空洞推进；远端会收到空语义 update。
- **修复建议**：`undo_text` 返回 `Result<Option<String>, _>`（None=无可撤），或先 `can_text_undo` 短路返回 `Err(UndoError::Empty)` 语义错误，禁止无操作提交。

### H10（黄·性能 §3）每步 apply 全量快照文本引擎 → undo 栈 O(N) 内存

- **证据**：`session.rs:344-352` `capture_memory_snapshot` 全量 clone 树 + `text_engine.checkpoint()`；`text_engine.rs:480-502` checkpoint 现**为每个热块全量编码 `encode_state_as_update_v1`** 存入 `cold_updates`（本波新增），加上全部 plain text。每次 `apply`（含单字符击键）都全量编码所有热块 + clone。
- **缺陷机制**：大文档（512 热块 × 大文本）下 undo 栈每步几十~几百 KB 快照，长编辑会话内存线性膨胀，apply 延迟随文档增大（O(N) 每键）。
- **修复建议**：SD 债：undo 栈条目改为「该批结构逆元 + 该批触达块的增量 update」惰性快照；或 undo 步数上限 + 栈条目压缩。本波至少登记基线。

### H11（黄·可维护 §13）双构造器 API 行为不一致

- **证据**：`coordinates.ts:32-48` `asUtf16Offset/asUnicodeScalarOffset`（`Math.floor` + RangeError）；`:51-64` `createUtf16Offset/createUnicodeOffset`（整数校验 + TypeError）。`asUtf16Offset(1.2) = 1`，`createUtf16Offset(1.2)` 抛错——同一语义两套规则，两套都从 index.ts 导出。
- **修复建议**：收敛为一个构造器（推荐整数严格版），或明确 as=容错版/ create=严格版并只导出其一（§13 命名一致性）。

### 绿项（无发现）
