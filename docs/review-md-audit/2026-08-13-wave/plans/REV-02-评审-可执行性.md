### 4. 门禁收敛可行性

**结论：G-01 根因分析经代码验证为真且语义设计正确；G-03「HARD 只能拆」代码验证为真；但 G-01 迁移实现存在「误用 --update 全量登记 88 项」的执行隐患，G-02 的 88 项逐文件决策粒度偏大。**

- **G-01 语义硬化可行性**：✅ 脚本根因属实（parseBaseline 只存路径 check-crate-size.mjs:173-183；`--update` 只写路径 :203-220；判定只查「超限且未登记」:234-244——已登记文件涨到天零信号）。**迁移风险**：若迁移用现有 `--update` 路径实现，会把当前全部超限文件（含 88 个未登记的）一次性写回——正是 G-02 禁止项「无差别 --update 全量登记」；迁移必须走**独立代码路径**（仅读既有 66 条标记区 → 实测行数 → 回写 path+count），且「迁移时点实测行数」会把 core_run_commands 17495 合法化为上限——必须与 G-02 时限注记同轮联动，避免第二次「登记即豁免」。
- **既有 66 个登记的影响**：✅ 标记区实测 66 条（表头写 65，标记区 66，正文表与标记区本就存在 1 条口径差）；G-01 迁移 = 全部 66 条带行数重写，无破坏性；G-06 的「正文表与标记区一致」要求需明确由 G-01 一并更新正文表（或 G-06 追补，二选一，避免悬空）。
- **line-counts 3 HARD 只能拆**：✅ **代码验证**：computeStatus（check-line-counts.mjs:160-168）`hardBlock = max(650, limit)`，先于 baselined 判定——登记救不了 HARD。但注意**语义细节**：useStreamCallbacks 基线 915 → hardBlock=915，即拆到 ≤915 就退为 baselined 通过（方案 G-03 写「≤650 且 ≤类别上限」是更严口径，验收时二选一写明，避免执行 Agent 困惑）。
- **3 HARD 拆分粒度现实性**：✅ 现实。noteApi 704（业务类 ≤400）拆出 ~300 行纯逻辑子模块；BrowserImportSection 751（UI ≤500）拆 2 个子组件；useStreamCallbacks 950→拆 2–3 个 hook 子文件。均为机械切分、可单 Agent 完成；建议拆为 **3 个独立子任务**（不同文件天然可并行），合成任务只对 useStreamCallbacks 的 B6 常量处理部分。
- **G-02 88 项收敛**：⚠️ 按域 7 批 × ~12 个「逐文件决策」粒度偏大（每决策 = 读文件 + 判断 + 写注记或拆分）；建议每批 ≤5–8 个，或按「纯登记（并行域）」「顺带拆分（安全域）」分流两类派单。
