## 一、总览（整体修复路径 · 一句话）

**先把「错误能看见」（吞错收口、降级可感知、占位接线），再让「过程能关联」（最小面 Trace ID 加字段不加系统），最后让「热点能量化」（三热点耗时计数复用 EmitReport 样板）——可观测面不改任何运行语义，只改「能否看见」；六维共享同一批文件域时串行，同权推进，覆盖问题池全部 25 项。**

可观测/错误维度主线：`S4 吞错收口 → S5 session_id 占位接线 → S1 批写降级可感知化 → S2 分布式追踪最小面 → S3 性能热点埋点`。其中 S1/S4/S5 是「已具备代码形状、缺接线/缺感知/缺测钉」的收口类；S2/S3 是「从零到最小面」的新增类，受反过度设计红线约束最重。

## 五、本方案看到但审计报告未覆盖的问题（代码验证）

1. **`traceId?: string` 死字段（shared-types/tool.ts:55）**：审计 05 §10-8「traceId 全仓零命中」对 Rust 成立，但对 TS **不精确**——`ToolExecutionContext.traceId` 声明存在、全仓零读写。死字段会持续误导未来 grep 与排障（看起来像有追踪）。S2 完成定义 ④ 已把「接线或删除」二选一列为强制终态。
2. **`logInternalError` 不进 telemetry 链（userFacingErrors.ts:265-271）**：仅 `console.warn`。审计 05 §7 称「上报链 errorStore→telemetry 存在」，但 `persist-degraded-ls`/`hydrate-degraded-repair` 等专名事件**全程只到 console**——「有日志」≠「可检索」。「降级可感知」的最低标准应包含 telemetry 落库，审计 S1 建议包未点明此缺口。
3. **`ErrorStore.setPersistenceStatus` 槽位已在、零调用方（ErrorStore.ts:200）**：审计 S1 验收把「persistenceStatus 联动」描述为新机制；实测槽位（含 `PersistenceStatus` 三态类型 :34）已存在，缺的只是接线、展示与测钉——S1 工作量因此显著小于「新建机制」想象，且禁止重造第二个槽位。
4. **回灌闭环代码在、无闭环测钉**：`loadSessionBodyWithDegradedRecovery`（:1118-1149）完整实现「打戳 → LS 真源 → 回写 SQLite → 清戳」，但测试只有降级戳写入（:880-907），**无「分叉消除」闭环测**——审计 S1 验收「回灌测试存在」当前不满足；这是「代码在、测缺」的典型，执行轮须补测而非补实现。
5. **审计 S2 验收「X-Trace-Id 头」与 Tauri IPC 形态错位**：Tauri 命令走 IPC invoke，**无 HTTP 请求头语义**；按头实现是架构错位（且会诱导出新的传输面）。最小面正确形态 = payload 参数透传 + 事件/响应字段，本方案 S2 已按此定义完成定义与验收。
6. **S5 审计口径：「事件 session_id」实为 `ProviderRequest` 字段**：审计 S5 验收写「该消息路径**事件** session_id 非 None」；实测该字段在**引擎→provider 请求结构**（`build_request`），事件面早已带 session_id span（`loop/mod.rs:775`）。接线对象与验收断言应以请求字段为准（本方案已按代码形状修正）；另：接线后 provider 缓存键是否应含会话维度，审计未提，属语义影响面（S5 完成定义 ② 已处置）。
