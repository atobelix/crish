## 一、总览

**整体修复路径（一句话）**：先让门禁与结构面把执行域稳定下来（门禁实红清零、巨石拆分形成稳定文件域），再在稳定文件域上实施并发/性能拆解——**恢复可观测 → 阻塞出运行时 → 锁按文档分片 → 并行工具组有界 → 前端流式线性化**——同步以可观测、一致性、连通三面收口验证；六维互为输入输出，同波并行推进、同文件串行，覆盖问题池全部 25 项。

**并发/性能维度主线（本方案核心）**：`毒丸恢复观测化（B1）→ 计数面（B5）→ note 命令链阻塞出 async（B2）→ store 锁粒度细分（B3）→ 并行工具组并发上限（B4）→ 前端裸延迟与 O(N²) 形状（B6）`。不改变任何恢复语义与运行语义，只改"能否看见"与"在哪条线程上发生"。

**与本轮关系判定说明**：04 审计报告 B1 曾标注「不要求本轮改，仅建议」；但问题池 item 10（毒丸恢复 34+ 处静默无观测）为**同权问题项**，方案轮必须全量覆盖，故 B1 纳入本方案，不存在"可不做"选项。

### 3.2 单元间逻辑依赖与执行注记

- **B5 依赖 B1 落地**（计数面是 B1 的横切形态）；B1 内部按文件域可分片派单（store 家族 / summary_coordinator / note_memory 家族 / explore_quota / engine / telemetry 六个域互不重叠，可并行）。
- **B2 与 B3 同文件域**（store_backend 家族）——同文件串行；逻辑上 B2 先（阻塞出线程）后 B3（细锁），但二者可同一 Agent 顺序完成，不拆波。
- **B4 独立**：文件域仅 `session-loop/src/tool_exec.rs` + 装配面，与其它单元无文件重叠。
- **B6 依赖结构轮拆分时序**：`useStreamCallbacks.ts` 同时在 line-counts HARD BLOCK 名单（基线 915，将被拆分）——400ms 常量与 O(1) 索引随拆分一并迁移，或与拆分串行执行，禁止两轮同时写该文件。
- **全单元共同约束**：改动后必过 `node scripts/check-line-counts.mjs --all`（不新增 HARD/VIOL）、`cargo test --workspace`、前端 typecheck 与相关 vitest；不触达安全面（31 基线 §1 判定表：锁改动触达 B8，须附毒化测试；无新依赖、无新命令、无渲染面改动）。

## 五、本方案看到但审计报告未覆盖的问题

2. **telemetry file.rs:147 并非完全静默**：代码验证显示该处已有 `error_reported` 首次 `eprintln!` 去重 + `FileSink::Null` 降级（file.rs 降级分支）。04 报告列入"静默"不精确——B1 对它的动作是"统一到 tracing 面并计数"，不是"从零加观测"；`error_reported` 去重语义应保留（防刷屏），计数累计不受影响。
3. **engine.rs 毒化面远大于报告点名 1 处**：当前树 engine.rs 有约 30 处 `into_inner`（814-854 事件批、1156-1231 控制总线装配、1636-1704 provider 装配、2081-2090 事件桥、3286/3312/3706/3737/4031/4052 等）——04 报告仅点名 2083-2088。B1 的 engine 域应以**当前树全量 into_inner 清单**为观测化对象（低频装配路径同样计入，因毒化一旦发生审计无从发现）。
