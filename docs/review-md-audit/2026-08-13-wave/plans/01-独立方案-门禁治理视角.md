## 一、总览（整体修复路径 · 一句话）

**先把门禁的「裁判规则」修对（登记即限速：登记带行数、增长即拦、HARD 不可豁免），再把三扇红门（crate-size 88 未登记 / line-counts 3 HARD+7 VIOL / depcruise 3 违规）按域收敛到绿，CSP 在首屏内联外链化之后落地——门禁轮只做语义修正与收敛决策，真拆分交结构轮，并行域文件只登记不触碰。**

拆解为四条主脉：

1. **语义修正（根因）**：crate-size 基线从「只存路径」改为「存路径+登记行数」，对齐本仓前端基线已有的 per-file 冻结语义（登记值即上限、增长必 fail、下降放行）。这是 `core_run_commands` 2524→15101 六倍回涨盲区的唯一根因闭合点——审计报告报了现象（6 倍回涨），未指出脚本层标记区只存路径这一根因（本方案 G-01 覆盖）。
2. **红门收敛（存量）**：88 个 crate-size 未登记 + 10 个前端超限 + 3 处 depcruise 违规，按域分批逐文件决策（拆分 / 新语义登记），文件域锁与并行域错开。
3. **CSP 落地（配置）**：先外链化首屏内联 `<style>`/`<script>`，再声明 CSP（index.html meta 或 tauri.conf.json `security.csp`），dev/prod 双态验收。
4. **治理纪律固化（防再犯）**：基线注记三要素（实测行数/理由/时限触发条件）、门禁实红期间禁称「门禁绿」、责任域登记表。

## 三、门禁治理维度详案

### 3.1 可复用任务单元模板（本轮用完下轮可继续套）

每个任务单元固定五要素：

| 要素                     | 定义                                                               |
| ------------------------ | ------------------------------------------------------------------ |
| **ID**                   | 阶段前缀-序号（本轮 G-*）；下轮新任务从新前缀续号，不改旧 ID       |
| **目标边界（文件域锁）** | 允许触碰的文件/目录白名单 + 明确「不碰」清单（并行域、其他视角域） |
| **完成定义**             | 可测的终点状态（不依赖主观判断）                                   |
| **验收断言**             | 执行什么命令 / 看什么输出即判定完成（含 exit code）                |
| **禁止项**               | 该任务明确不得做的事（防越界、防替其他视角代劳、防作弊）           |

配套可复用机制：

- **责任域登记表**（G-00 产出）：`git status` 逐文件归类（并行域 / 门禁域 / 结构域 / 契约域），所有任务的「不碰」清单由此生成。

## 六、本视角看到但审计报告未覆盖的问题

1. **crate-size「登记即永久豁免」的脚本根因未被点名**：审计报告（02 §4.1、00 总判）报了「6 倍豁免盲区回涨」现象，但未指出根因是标记区只存路径、不存登记行数（本会话读 `check-crate-size.mjs:172-183`、`:203-220`、`:234-244` 验证）。「登记时记录行数、超登记值即报错」是唯一能拦住第二例 `core_run_commands` 的机制——已化为 G-01。
2. **line-counts 的 HARD BLOCK 在脚本语义下「登记不可豁免」未被点明**：>650 硬阻断与基线无关，`--update` 救不了 HARD 文件——3 个 HARD 只能拆分。审计报告只列了数字；若执行轮不明此语义，会出现无效的 `--update` 尝试（G-03 背景中已论证）。
3. **双门禁行数口径不一致（物理行 vs 有效行）**：crate-size 数物理行（含注释/内嵌测试，`check-crate-size.mjs:66-74`）、line-counts 数有效行（剔注释空行，`check-line-counts.mjs:60-73`）——07 §10 已现「主控初扫数字与脚本不符」的口径打架先例。建议总方案固化「以脚本输出为权威口径」，报告引用时标注口径，消除跨报告数字冲突。
4. **入口类 vs mod 类限额的登记强度未区分**：`conex-browser/lib.rs` 1224 是入口类（≤800）超限，比 mod 类（≤600）语义更严重（crate 门面）；现行基线文件对两类登记一视同仁。建议登记注记区分入口类（理由须说明门面为何超限），见 G-02 入口类特例。
5. **并行域 line-counts 增量缺责任归属登记机制**：eventParser/goalModeController/sessionSharedHelpers 的超标靠 `git status M` 人工归类（02 §6.2 如此处理），无落盘登记——一旦并行域收口合并，责任会漂移。G-00 责任域登记表将其固化。
6. **updater 死配置未进问题池**：`tauri.conf.json:32-38` `updater.active:true + pubkey:""` 而 Rust 侧零注册（06 建议包 D，未收进 25 项）——「配置声称启用、实际不校验签名」的表面积。建议并入契约视角或本维度的治理条款（二选一：注册插件+填 pubkey / `active:false`）。
7. **hook 全工作区 diff --check 阻塞面**：`.husky/pre-commit` 检查整个工作区（AGENTS.md §3.5 已有纪律），并行域 trailing whitespace 会阻塞门禁轮全部提交——提交流程需在总方案注明「被阻塞时最小 whitespace 修复或上报主控协调」，避免门禁轮误以为自己的改动有 whitespace 问题。
