## 一、登记三要素注记规范（全波引用模板）

### 1.1 规范定义

**任何新增登记条目必须同时具备三要素**，缺一即视为无效登记（下轮审计可 grep 校验）：

| 要素         | 必含内容                                                   | 形式要求                                                   |
| ------------ | ---------------------------------------------------------- | ---------------------------------------------------------- |
| **ID**       | 拆分/修复任务标识（`SR-0x 批①` / `CT-0x` / `B2` 等）       | 必须是真实存在的任务卡 ID，禁止自造编号                    |
| **触发事实** | 登记何时失效的**可机器判定事实**（如「该文件 ≤ 600 行」）  | 用「触发事实 = …」明示，不得用形容词                       |
| **时限**     | 完成该任务的边界条件（如「SR-06 批② 拆分完成后移除登记」） | 二元结构「任务完成后移除登记；触发事实 = 该文件 ≤ 600 行」 |

### 1.2 二元结构模板（复制即用）

```
**SR-06 批②（browser 域拆分）完成后移除登记；触发事实 = 该文件 ≤ 600 行（入口类 ≤ 800）**
```

## 二、updater 死配置裁决建议（tauri.conf.json）

### 2.1 现状（本会话实测）

`apps/agent-workbench/src-tauri/tauri.conf.json:32-38`：

```json
"updater": {
  "active": true,
  "endpoints": ["https://releases.crish.me/updates/{{target}}-{{arch}}/{{current_version}}"],
  "dialog": true,
  "pubkey": ""
}
```

- `active:true` 但 `pubkey:""` —— 空公钥 + 端点域名无实际注册；Rust 侧插件**零注册**（转引 REV-02 §一.8-7）。
- 后果：产物携带「宣称可更新但实际不可用」的死配置；`tauri build` 若走 updater 校验路径存在隐患。

### 2.2 二选一方案

| 方案                  | 改动                        | 适用前提                       | 成本                       |
| --------------------- | --------------------------- | ------------------------------ | -------------------------- |
| **A：`active:false`** | 仅改 1 行，保留端点配置     | 发布渠道未就绪                 | 最小面，零风险             |
| **B：登记 pubkey**    | 填入签名公钥 + 确认端点可用 | 发布渠道已就绪、签名密钥已生成 | 需密钥管理，当前无证据就绪 |

### 2.3 裁决倾向：**A（`active:false`）**

理由（按路径合法排序键：效果完整度 → 正确性/不变量 → 可验证性 → 契约一致 → 结构干净）：

1. **可验证性**：`pubkey:""` 下无法验证任何更新签名，`active:true` 是一份无法兑现的声明；改为
   `false` 后配置与运行时行为一致（诚实配置）。
2. **最小面**：方案 A 单行改动、无密钥依赖；方案 B 需要签名密钥与发布端点，超出本战役范围。
3. **不变量**：改动不触碰任何业务逻辑，不引入依赖。
4. **反过度设计**：在发布渠道就绪前先建签名/发布基建属于新工程面，本战役禁止开新面。

> 落盘权限：属主控裁决后落盘（D-01 §六-10）；本任务只出建议。若主控后续启用更新，再改回
> `active:true` + 登记 pubkey（方案 B），同时确认端点可达。

## 四、「门禁红禁称绿」条款（治理纪律建议 · 供主控追加）

1. **门禁实红期间禁止宣称门禁绿**：任何单元在 `check-crate-size` / `check-line-counts` /
   depcruise 任一输出 FAIL 时，禁止以「已登记」「已拆分」「轮次完成」等表述宣称门禁通过。
   宣称门禁绿**必须以当次真跑 exit 0 输出为证**（G-00 快照「状态列 = {FAIL, PASS} 且与 exit code
   一一对应」；00 执行方案定稿 §一.2）。
2. **登记 ≠ 拆分完成**：`--update` / edit 基线登记只是**限速豁免**（冻结上限、增长即 FAIL），
   不是结构债务的清偿。登记文件仍在「待拆分」队列，拆分完成的标准是**该文件实测 ≤ 限额且登记移除**，
   不是登记动作本身。
3. **新登记条目必须带时限触发条件**（见 §一），无时限注记的登记视为无效并验收 FAIL。
4. **存量条目冻结**：2026-08-04 建线的历史条目统一标注「历史遗留，冻结」，禁止删除（G-06 禁删纪律），
   由结构轮 SR-06 各批拆完后按 §一 规范收紧/移除。

## 五、BOM 检测最小面门禁建议（G-06 修订接收项 · 防再犯）

### 5.1 背景

轮 1 CT-02 已字节级清理 3 个 BOM 文件（`ttfb_measure.rs` / `multi_agent.rs` / `strategy.rs`），
本会话实测确认清理完成。防再犯需一个最小面检测，**禁止新服务/新表/新指标体系**。

### 5.2 建议方案（二选一，均复用既有面）

**方案 A（推荐）：pwsh7 单行字节头扫描**（复用 CT-02 断言模板）：

```powershell
# 扫描全部 Rust/TS 源码文件，头 3 字节 ≠ EF BB BF
$bad = Get-ChildItem -Recurse -Include *.rs,*.ts,*.tsx,*.mjs,*.mts -Path crates,apps,packages,scripts |
  Where-Object { !$_.FullName.Contains('node_modules') -and !$_.FullName.Contains('\dist\') } |
  Where-Object { $b = [System.IO.File]::ReadAllBytes($_.FullName); $b.Length -ge 3 -and $b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF }
if ($bad) { $bad.FullName; exit 1 } else { 'BOM check OK'; exit 0 }
```

**方案 B：rg 字节模式扫描**（与 `check:css-encoding` 同族接线）：

```bash
rg -l -U "^\xEF\xBB\xBF" --glob '!node_modules' --glob '!dist' -g '*.{rs,ts,tsx,mjs,mts}' crates apps packages scripts
```

### 5.3 接线建议

- 方案 A 落为 `scripts/check-no-bom.ps1`（或 .mjs 等价），注册 `package.json` script
  `check:no-bom`，并入 `check:desktop` 或 CI lint job（与 `check:css-encoding` 并列，
  `scripts/check-css-encoding.mjs --whitelist-dirty-check` 已有先例）。
- 或最小化：仅接入 CI lint job 一步，不新增 package.json script。
- **禁**：新数据库表 / 新指标体系 / 常驻服务 / 监控面板——超出即视为违规开面（D-01 G-06 禁止项）。
