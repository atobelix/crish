## 二、260 首帧跳：写入者实测坐实（D §8.2 遗留项，本批关闭）

施工前用 MCP rAF 采样 + 根变量轨迹定位（记忆宽 248.80001831054688px）：

- **收起**：wrapper 首帧即 0（141 帧无中间值）；内层 248.8 → 0 约 182ms（被 0 宽 wrapper 裁掉、不可见）；根 `--sidebar-width` 全程保持记忆值不变——证实折叠路径上同步效应不跑（hook 随手柄卸载）。
- **展开**：wrapper 取值仅 {260, 248.8}。t=56ms 时根变量已被写成 **`"260px"`**（整数形），t=83ms 才落回 `248.80001831054688px`；内层随后在已到位的 wrapper 内自行动画 0 → 248.8 约 166ms。
- **写入者**：手柄重挂载时 useSidebarResize 的挂载同步效应——旧初值恒为默认 260，效应先把 260 写上根变量；而本机 config 无有效值、restore 走 preferences 异步兜底，记忆宽迟一步才落。修复即改动 3（同步真源初值 + 布局期落值），从源头消灭 260 中间态，而非在呈现层遮盖。

## 三、实机量测（改后，直播应用 MCP rAF 逐帧）

环境注记：直播窗口视口退化为 146×20（断点解析为 overlay），与 D 批同一限制；wrapper ↔ 工作区左缘的 flex 联动与 inline 模式共用同一代码路径，结论不依赖视口（D §2.3 同口径）。真实宽窗复测仍待（登记项）。

计算样式先行确认：wrapper `transition: width 0.2s cubic-bezier(0.2, 0, 0, 1)`；内层 aside `transition-duration: 0s`（过渡已收敛）。

- **收起**（133 帧）：wrapper 宽 18 个不同值 248.8 → 147.76 → 90.46 → 71.97 → 57.09 → … → 0，运动段约 185ms（decelerate 曲线）；工作区左缘与 wrapper 宽**逐帧相等（0 帧不匹配）**；内层宽全程恒 248.8（钉住、被裁切）；根变量恒记忆值。
- **展开**（132 帧）：wrapper 宽 17 个不同值 0 → 134.46 → 176.82 → 191.45 → … → 248.8，运动段约 186ms；**全程单调不减，超过 248.81 的帧数 = 0**（260 跳变消失）；根变量全程恒 `248.80001831054688px`、从未出现 `"260px"`；左缘逐帧相等；内层恒 248.8。
- **拖拽关停级联**（真实 WebView，手动挂/摘 body 类读 computed 值）：0.2s →（is-resizing）0s →（sidebar-resizing）0s → 摘类后恢复 0.2s，类已清干净。

时长决定：**保持 `--duration-normal` 200ms，未升 240ms**。依据：200ms 即原内层过渡对同一行程区间（160–480px）的既定口径，本批是把既有手感搬到正确挂点、无新造手感；无「480px 行程明显赶」的实测证据，按简报门槛不升档。

## 四、layoutAnimationStore 处置决定：删死类型（不接线）

全仓检索证：`'sidebar-transition'` 与 `isSidebarTransitioning` 仅出现在 store 本体与其测试，**零生产调用、零消费方**。侧栏动画是纯 CSS 过渡，不需要 JS 门控；给它接 start/end 而无人读标记 = 假接线，简报明禁。故按二选一删：类型联合成员 + 派生标记（接口/deriveFlags/初态）+ 测试 reset 一行。store 其余机制（窗格门控、catchup、看门狗）未动。

`--sidebar-visible-width` 动画期镜像策略（D §4.7 开放项）本批定为：**保持已提交记忆值、不逐帧镜像呈现宽**。理由：该变量的既定语义就是「折叠态也保持的记忆宽」（提交值），其唯一消费方 SettingsQuickMenu 锚定读的是提交语义；拖拽期逐帧镜像是因为拖拽呈现值本身即待提交值，与开关动画的瞬态不同。
