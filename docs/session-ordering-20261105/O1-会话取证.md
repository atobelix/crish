## 五、乱序首现层结论

**结论：乱在「前端把引擎事件收口装配成 SessionMessage」这一层——落盘数据（blocks_json）已经是乱的，呈现层只是照单渲染；引擎层（events 真值）完好无损。**

证据链（按强度）：

1. **引擎层无罪**：events 表 sequence 单调序里，五段 message-end 的 blocks 就是交错原样（thought/正文/工具调用同段共存），message-start 与 message-end 内容一致，流式期间无重组。
2. **落盘层已乱**：blocks_json 的字节形态即上表——类别重组、正文合并置尾、思考只剩末段。这不是渲染问题：换任何客户端读这份数据都是这个顺序。
3. **呈现层无二次重组**：前端回读路径 `sessionRustDbWire.ts` 的 `fromRustSessionMessage` 把 blocksJson 原样 parse 成 blocks（第 292–293 行），完成态 UI 渲染的就是落盘序。流式时 UI 走事件/分段路径（有序），完成后切到收口后的消息形态——与用户「流式时正常、完成之后才乱」的观察严丝合缝。
4. **乱序形态是「收口时按分组字段重建 blocks」**，四处指纹互证：
- text 块的 `startTime`=1793884409222（08:13:29.222），**晚于**末段 message-end（08:13:28.221）、约等于 agent-end 时刻，`durationMs`=0——这块正文是完成瞬间才被物化出来的，不是流式期逐段建的；
- tool_call 块只剩 {type,id,turnIndex,startTime,durationMs}，时间值与 `tool_calls_json` 里的执行记录（startedAt/durationMs）对齐——是从「工具列表」字段反建的，不是流式期推入的原始块（原始块带 intent/group、无时间戳）；
- thought 块是单块 `id="thought-turn-0"`，startTime 在运行早期、durationMs=70136 贯穿全程，内容却只有最后一段——单块被逐段**覆盖**的形态，与 `sessionEventProjection.ts` message-end 处理里「按 turnIndex 找既有 thought 块并 `content = thought` 覆盖、`a.thinking = thought` 覆盖」的语义逐字对上；
- 5 个引擎 turn 的块落盘后 `turnIndex` 全部塌成 0，段边界信息（原 message id 后缀 -4…-8）在投影里不留痕。
5. ****落盘前规范化函数 `normalizeAssistantTimeline`（`timelineReconciler.ts`，persist 路径经 `sessionRustDbWire.ts:347` 调用）本身**造不出**这个形态：它的合并契约明文「严格按插入顺序输出、禁止 type/turn 重排」，喂给它有序 blocks 出来仍有序。所以分组形态在消息对象到达落盘规范化**之前**就已经形成了——即活在前端 store 的完成态消息本身就是分组的，落盘只是把它如实存下。

一句话定位：**引擎组装无罪、持久化序列化无罪（照单存储）、呈现投影无罪（照单渲染）；罪在前端事件→消息的收口装配——消息模型用 text/thinking/toolCalls 三个分组字段承载一轮输出，完成时 blocks 由分组字段按「思考→工具→正文」类别重建，段间交错在字段模型里根本不存在、无从保留。**

## 六、证据缺口与补证方法

- **未钉死的最后一环**：磁盘证据能证明分组形态在「到达落盘规范化之前」已存在，但无法单独指认是 store 的哪个完成动作（finalize 回调 / PublicationScheduler 一类的发布步骤 / 投影合并）按下最后一下——活内存里的 store 状态没有落盘副本可比（orchestrator-snapshot.json 是引擎侧状态，不含前端消息块）。补证方法：在落盘入口（persistAllSessions / toRustSessionMessage 调用点）对一个复现会话打点记录 `msg.blocks` 的类型序列，与完成瞬间 store 内同一消息对比，即可分开「活 store 已乱」与「落盘瞬间才乱」。本取证按只读纪律未做运行时打点。
- 本报告只取了 run 3（问题轮）与 run 2（同型复核）的事件；run 1 是无工具的短问答，不涉及交错。
