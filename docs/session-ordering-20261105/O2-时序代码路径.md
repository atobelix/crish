## 1. 链路顺序图（一轮 run 在桌面端的完整路径）

```
provider 流
│ (session-loop: stream/aggregate.rs 按桶聚合: text 一条 String / thought / tool_calls 一组 Vec)
▼
Rust 事件双轨
├─ 实时轨: message-delta 按真实到达序发射（前端流式显示的依据）
└─ 收口轨: 每轮 stream 结束 → build_assistant_message 按组装定稿消息
[thought 块… → 本轮全文一块 → tool-call 块…] → message-start/deltas/end
│ (conex-db events 表按 sequence 落盘, 读回恒 ORDER BY sequence ASC)
▼
桌面 chat-bridge handlers (messageHandlers.ts)
├─ onMessageDelta: 按 turnIndex 记双账本 (turnStreamedTexts / turnAuthoritativeTexts)
└─ onMessageEnd: 本轮权威 text/thought 覆写账本; 全轮正文以 '\n\n' 拼成一条扁平 msg.text
→ updateMessageText 落盘 (不碰 blocks 的交错结构本身, 见下)
▼
桌面 store (SessionMessage: text + blocks + toolCalls + thinkingTurns 四件套并存)
├─ 正文块维护: updateMessageText 以单一 streamTextOffset + 「最后界标后 segment」模型增量维护 blocks
├─ 工具块: addMessageToolCall 推进 offset、弹掉尾部空 text 块、追加 tool_call 块
└─ 思考块: updateMessageThinking 按 thought-turn-N 维护 (带 id + turnIndex)
▼
streamRunCompletion 三步:
1. commitRunCompletion: committedText = 既有 msg.text 与流缓冲中
2. finalizeAssistantMessageText: updateMessageTimeline → normalizeAssistantTimeline(全文最终态)
3. finalizeRunCompletionStatuses: 状态置 completed
▼
渲染: selector (session-selectors.ts:45) 对每条 assistant 消息再跑一次 normalizeAssistantTimeline
→ buildAssistantTimeline (blocks 单遍保序) → timelineSegmenter (单遍分段, 末尾正文=最终答复)
▼
持久化: sessionRustDbWire (写前再 normalize) → DB; 重开时 hydrate (parseTimelineBlocks 逐块保序)
或事件重放 sessionEventProjection (按事件序重建 blocks, 末尾再 normalize)
```

**一句话总览**：整条链路上，**唯一被设计成保序的只有事件序与 blocks 数组序**；正文的权威形态在 Rust 侧与 handler 侧都是「扁平全文 + 按轮账本」，交错结构只存在于前端 store 的 blocks 里，由一套 offset 记账增量维护——而完成时的 `normalizeAssistantTimeline` 持有两个「把内容追加到末尾」的补偿口子。这是全部嫌疑的土壤。

## 3. 完成时动作清单（乱序发生的确切时刻）

run 收口由 `hooks/chat-stream/streamRunCompletion.ts` 三步执行：

1. **`commitRunCompletion`**（:72-131）：`preferredText` 取「既有 msg.text 与流缓冲文本中较长的一条」作为 committedText，经 `commitStreamToSession` 落盘。注意：blocks 此前是按**另一版本**的文本切片维护的，最终全文与切片版本可以长度/内容不一致（流式原文 vs handler 权威的 trim 后 `\n\n` 拼接版是两个生产者）。
2. **`finalizeAssistantMessageText`**（:137-165）：清理思考占位后，在:157-160 **无条件**调用 `updateMessageTimeline(sid, assistantMsgId)`。
3. `updateMessageTimeline`（`store/sessionMessageActionsTools.ts:236-245`）：`normalizeAssistantTimeline({...msg})` 后**整表替换** `msg.blocks` 与 `msg.toolCalls`——归一的输出即成为消息的权威时间线，且随后被持久化（wire 写前还会再 normalize 一次，`sessionRustDbWire.ts:347`）。

与流式期的关键差异（解释「流式正常、完成才乱」的时间差）：

- 流式期渲染有 streamingStore 的实时文本兜底，blocks 的缺陷被掩盖；完成时状态翻转、实时层撤除，渲染**纯由 blocks 驱动**（selector → buildAssistantTimeline → segmenter）。
- 流式期 normalize 虽也被 selector 反复调用，但其危险变换需要「最终全文 + 终态 blocks」的组合条件；完成步是第一次拿最终全文对终态 blocks 整表归一并**写回 store 落盘**，变换一旦发生即被固化（后续 normalize 看到已追加的块只会保留）。

## 4. 双路径分叉点（同一产品内并存的几套时间线生产方式）

1. **主流聊天路径**（chat-stream + handlers）：text 块由 updateMessageText 的 offset 机器增量维护——有交错，但记账脆弱（见嫌疑 S3）。
2. **子代理/面板路径**（`hooks/agentStreamCallbacks.ts` + useAgentStream）：`onChunk` **只写 `m.text`、从不建 text 块**；blocks 里只有 thought 与 tool_call 块。此路径的消息到完成时**必然**满足「有正文、无 text 块」——补偿 ① 是确定性触发，不是概率事件。
3. **事件重放路径**（sessionEventProjection）：自建 blocks，text 块 turnIndex 两套写法并存（:341 带 /:388 不带），与主流路径「text 块恒无 turnIndex」又不一致——reconcile 的槽位键对 text 块靠 `(turnIndex, type, 序号)`，跨路径口径不一致时中间正文会被认成 orphan（见嫌疑 S2）。
4. **存储合成路径**：前端 `addMessage` 对无 blocks 的消息合成 `[全文一块, 工具块…]`（`sessionMessageActionsCore.ts:52-58`）；Rust hydrate 无 blocks_json 时合成 `[Text, Thought, ToolCall…]`。两处合成都是按类型归拢，与交错无关。

## 5. 嫌疑排序

### S1（头号）完成时归一补偿 ①：无 text 块 → 全文一块追加到 blocks 末尾

- **位置**：`api/tool-presentation/timelineReconciler.ts` normalizeAssistantTimeline 的「有正文但无 text 块时补偿」（`alignedBlocks.push({ type: 'text', content: msg.text, turnIndex: 0})`，约:262-268）；触发入口 `hooks/chat-stream/streamRunCompletion.ts:157-160` → `store/sessionMessageActionsTools.ts:236` updateMessageTimeline。
- **机制**：消息在完成时若 blocks 里有工具/思考块、却没有任何 text 块，整条 msg.text（多轮正文以 `\n\n` 拼接的全量）被作为**单个** text 块追加到 blocks **末尾**。随后 segmenter 扫描：所有工具在其之前、这块全文成为唯一的「最终答复」——即用户看到的「夹在工具之间的正文全被放进最后的总结」。
- **为何流式正常、完成才乱**：流式期正文由实时层呈现、到达序天然正确；完成步首次以最终全文整表归一并写回，补偿一旦命中即固化并落盘，重开会话仍是乱的。
- **触发条件与证据强度**：机制为代码实证（强）。触发分路径：子代理/面板路径**确定性触发**（该路径从不建 text 块，§4.2）；主流聊天路径为**条件触发**——需 blocks 处于「有工具块、无 text 块」状态，可达路径见 S3 的记账失效（offset 超越最终全文长度时 segment 恒空、尾段 text 块永不创建；addMessageToolCall 弹掉尾部空 text 块等）。本事故会话走哪条路径、当时 blocks 的确切形态，无数据侧证据（本调查未读会话数据），但症状形态（**全部**正文整块沉底）与 ① 的产物逐字吻合，其余嫌疑都只能解释单段迁移，解释不了全量沉底。
- **修复方向**：① 不应把全文当作一个块塞到末尾——应按轮次 segment（handler 侧已有 `messageEndTurnSegments` / 权威分轮账本）把各轮正文插回各自轮次的位置；或在 ① 命中时以 streamTextOffset + 工具块 startedAt 为界标重建分段。更根本的是让所有路径的 text 块在创建时就带稳定 id 与 turnIndex（见 S2），使归一不再需要这种全文兜底。
- **影响面**：全部经 updateMessageTimeline / selector / hydrate / wire 四处 normalize 的消息；子代理面板为必现。

### S2（同归一内）thought 重水合末尾 push + reconcile orphan 末尾追加

- **位置**：同文件——thinkingTurns 中某轮 thought 块缺失时，turnIndex>0 的思考块被 `blocks.push` 到末尾（约:195-199）；`reconcileAssistantMessageBlocks` 槽位未命中的既有块（orphan）一律追加输出末尾（:191-194）；槽位键 `getReconciliationSlotKey`（:126-138）对无 id 的 text 块用 `(turnIndex, type, 出现序号)`。
- **机制**：(a) 思考块被推到最终正文之后时，segmenter 的最终答复判定失效（正文后有过程项 → 降为中间叙述），视觉上像「总结被吞/正文错位」；(b) text 块无 id、turnIndex 各路径口径不一（主流恒无、重放:341 有 /:388 无），一旦 existing 与 incoming 的 turnIndex 口径不一致，同序号对齐失败，中间正文成 orphan 被追加到末尾——与 S1 同形的沉底，但只沉「错位的那几段」。
- **与症状的对应**：部分对应（单段或思考错位）；可与 S1 叠加。
- **证据强度**：机制代码实证（强）；在 updateMessageTimeline 的同源调用（existing 与 incoming 同出 msg.blocks）里 orphan 分叉空间有限，主要风险在跨路径合并/重放后再归一的组合（中）。
- **修复方向**：thought 重水合按 turnIndex 插回轮次位置而非 push 末尾；orphan 按 startTime 就近插回（alignToolCallBlocks 对工具已有此先例）而非一律末尾；text 块创建即带 id（主流路径 updateMessageText 建块时补上），槽位键脱离序号对齐。

### S3（主流路径）updateMessageText 的单 offset 记账被「最终全文」击穿

- **位置**：`store/sessionMessageActionsCore.ts` updateMessageText（单一 `streamTextOffset` + 「最后界标后 segment」模型）；`messageHandlers.ts` onMessageEnd 的权威覆写；`streamRunCompletion.ts` commitRunCompletion 的 preferredText（较长者胜出）；工具提交的批量 flush（`hooks/chat-stream/helpers.ts` pendingToolCommits）。
- **机制**：正文有两个生产者（流缓冲原文 / handler 权威 trim 拼接版），blocks 却只有一本 offset 账。完成时提交的最终全文与切片所依据的版本长度不一致时：`text.length < offset` → segment 恒空（尾段正文永不入块，为 S1 备好触发条件）；或尾块内容被错位切片覆写。另，工具块经批量 flush 落盘时若其前置正文段尚未 commit，该段的 text 块会被插到工具块**之后**（按界标插入逻辑），造成单段正文越过紧随其后的工具。
- **与症状的对应**：解释「某段正文挪到后面」与 S1 的前置条件；单独不足以解释全量沉底。
- **证据强度**：记账结构与失效分支代码实证（中强）；事故当时的具体失步序列未复现（无数据侧证据）。
- **修复方向**：offset 账本按界标/轮次分段而非单一标量；完成时 committedText 选定后应以同一版本重切片校验 blocks；工具 flush 前强制先快照待提交正文（已有 snapshotStreamTextToSession，审计其调用点覆盖）。

### S4（Rust 侧）定稿消息按类型归拢——轮内交错在源头不可表示

- **位置**：`crates/session-loop/src/stream/aggregate.rs`（分桶聚合）；`crates/session-loop/src/loop/handlers/streaming.rs:688` build_assistant_message（thought → 全文 → tool-call 的组装序，注释明文为规格）；收口轨 deltas 亦按此序从定稿消息逐块派生（emit_message_deltas）。
- **机制**：单个 provider 回复（一轮）内的 text↔tool 交替在聚合层即被压平；定稿消息与落盘的收口事件序都是归拢后的顺序。桌面前端主流路径靠自己的账本重建交错、不直接消费定稿 blocks，故它不是桌面实时乱序的直接原因；但**事件重放、历史回看、以及任何直接消费定稿消息 blocks 的投影（含移动端对已完成会话的呈现）只能拿到归拢序**。本事故若是「重开/回看时才发现乱」，此环与 S5 的组合解释力上升。
- **证据强度**：代码实证（强，含规格注释）；对本事故的归因取决于乱序是完成瞬间发生还是回看时发现（用户描述为「输出完成后」，两读都成立，未做数据侧区分）。
- **修复方向**：若要轮内保真，aggregate 需保留有序 parts 序列（改动面大，属引擎层决策）；否则应明文规定定稿 blocks 不是交错真相源，并审计所有投影不得以其为准重建交错（重放投影目前部分依赖事件序，需逐项核对）。

### S5（兜底路径）无 blocks 时按类型归拢重构 + 单 offset 切分

- **位置**：`api/tool-presentation/timelineNormalizer.ts` buildAssistantTimeline 的 blocks 缺失分支（约:275-360）：注入 → 思考 → 工具前文本 → 工具 → 工具后文本；offset 无效（0/缺失）时默认**全文置于所有工具之后**；offset 只够切一刀，多段交错不可表示。
- **与症状的对应**：产物形态与事故一致，但仅在 blocks 缺失/为空时触发；本事故会话为实时流式会话（blocks 机器在运行），概率低于 S1/S3。历史/旧格式会话回看时风险实在。
- **证据强度**：机制代码实证（强）；本事故适配度低-中。
- **修复方向**：兜底切分改用分轮 segment 数据（thinkingTurns 已带 turnIndex、正文分轮账本在 handler 侧存在），无分轮数据时寧可整段置于工具前也不默认沉底——或至少让默认分支与 offset 的来源一起落一条可观测日志。

### S6（移动端）无完成态重组，乱序只会继承、不会原创

- **位置**：`apps/crish-mobile/src/presentation/timeline/buildTimeline.ts`（在途修改状态）：无 normalize/reconcile/segmenter 对应物；fold 按帧序追加，message-end 就地覆写既有正文块。
- **机制与边界**：移动端呈现的交错 = 宿主 feed 帧序；完成时仅当 delta 从未建出正文草稿块时，message-end 才把正文块追加到当时末尾（工具帧已先到时正文会落其后）——属边缘追加，非系统性归拢。该会话若在移动端观看，乱序应与桌面/存储侧一致（继承 S1/S4 的产物），移动端本身不是源头。
- **证据强度**：代码实证（中强；文件在途，结论以当前工作树为准）。
- **修复方向**：无需独立修复；随宿主侧 S1/S4 的处置自然收敛。message-end 追加位置可按 messageId 的轮次邻接关系就近插入，作为健壮性改进。

## 6. 前任结论复核表

| 前任结论 | 复核结果 | 本文出处 |

## 7. 结论

乱序不在渲染层（segmenter 无辜），也不在存储层（事件序、Vec 序、hydrate 解析均保序）。**根子在「交错结构只有一份、且由脆弱记账维护，却在完成时被一个带末尾追加补偿的归一整表重写」**：头号嫌疑 S1 的产物与事故症状逐字吻合，且在子代理路径上是必现、在主流路径上由 S3 的记账失效备齐触发条件；Rust 侧 S4 的按类型归拢则决定了回看/重放时同样保不住轮内交错。修复的优先序建议：S1（补偿改按轮回插）→ S2/S3（text 块 id 化 + offset 分段记账）→ S4/S5（定稿与兜底的口径明文与审计）。
