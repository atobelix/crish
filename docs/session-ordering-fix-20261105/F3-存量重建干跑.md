## 1. 重建工具说明

一次性脚本（不进产品代码），核心 `rebuild_core.js`，两个驱动：`dryrun_target.js`（目标会话）、`scan_one.js`（全库逐会话扫描）。

- **只读纪律**：源库一律以 `node:sqlite` 的 `{ readOnly: true }` 打开；全程未对源库执行任何写语句，未跑 vacuum/analyze；扫描按 `session_id` 索引逐会话查询。产物只写独立 JSON 文件。
- **重放规则**（形态对齐现行 `blocks_json` schema，不发明新字段）：
  - 每个 run 的 assistant `message-end` 事件按 sequence 序构成段（segment），段内按引擎 blocks 原序出块；
  - 段内多个 thought 项合并为一个 thought 块（内容以 `'\n'` 连接，id `thought-turn-<轮序>`）——与前端「一轮一思考块」的现行模型一致；
  - 每个 text 项独立成块；tool-call 项优先复用落盘同 id 的 tool_call 块（其 startTime/durationMs 来自执行记录、已核验正确），仅重排位置并把 turnIndex 恢复为真实轮序；事件里有而落盘缺失的工具块由 tool-start/tool-end 合成并计数标记（本次全库未出现需合成的情形，见 §3 工具对齐校验）；
  - thought/text 块 startTime 取段 message 的 createdAt（epoch ms），durationMs 置 0（与本库健康样本口径一致；原直播时间戳不可恢复，见 §5 开放点 iv）；
  - 轮序 ordinal = 引擎 turnIndex − 1（引擎 1 基，用户消息为 0）。
- **run ↔ 消息配对**：目标会话用顺序配对（3 run ↔ 3 条 assistant 消息，经内容校验成立）。全库扫描发现多数历史会话 runs 表条数远多于落盘消息（自动化测试会话动辄数百 run），顺序配对不成立，改用**内容配对**：先整 run 配对（工具 id 集合全等，或无工具时全文相等），未中再单段配对（子会话的落盘模型是「一个 run 的每个 message-end 各落一条消息」）。配对可信度由工具 id 对齐校验背书（§3）。
- **schema 差异注记**：F1 新语义给 text 块加 id；现行落盘 schema 的 text 块**无 id**。本次干跑按现行 schema 未补 id；真写阶段若 F1 已落地，应按 F1 格式补齐（见 §5 开放点 iii）。

## 7. 「兜底可删」证据小结

- 归拢兜底是**写路径**行为（O2 已定位机制），删除它只影响未来写入，不触碰已落盘数据本身；
- 存量侧凡能与事件配对的消息（182 条，工具 id 100% 对齐背书）：落盘正文与事件逐字全等或差额精确可计（真实类 50/52 全等、2 条字差单列；思考丢失 2,871 字精确可计且只能从事件恢复）——**兜底没有为任何一条消息保存下事件之外的独有内容**；
- 配不上/空行/无消息的部分（§4）不依赖兜底，删除无影响；
- 结论：**删除旧归拢兜底不丢任何数据**；存量损伤用本工具按 §6 预案从事件重放修复即可，与删兜底互不阻塞。
