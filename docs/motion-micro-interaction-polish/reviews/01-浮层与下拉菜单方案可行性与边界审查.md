## 2. 核心任务 1：Radix UI 浮层与下拉菜单生命周期深度审查

### 2.1 Primitive 溯源与真实组件拓扑图谱

经查阅 `apps/crish-desktop/package.json:34`：

```json
"dependencies": {
  "@radix-ui/react-popover": "^1.1.23",
  ...
}
```

**关键事实发现**：

1. 项目**并未引入** `@radix-ui/react-dropdown-menu`，也**并未引入** `@radix-ui/react-select`；
2. 全应用下拉体系呈现两种截然不同的架构形态：
   - **形态 A（基于 Radix Popover 封装）**：`ui/Menu`（通用菜单基座）与 `SmartExpandablePanel`（智能展开面板）均基于 `@radix-ui/react-popover` 的 `Root`、`Trigger`、`Portal`、`Content`；
   - **形态 B（自研手写浮动层）**：`ui/Select`（包含 `SelectRoot`、`SelectContent` 等）是纯自研组件，基于 React 19 `createPortal` + 自定义数学钩子 `useFloatingPosition.ts` 计算坐标，**完全不依赖 Radix Primitive**！

### 2.2 Radix Presence 退出动画机制 vs React 物理卸载的冲突审计

#### 1. Radix Presence 原理

`@radix-ui/react-popover` 内部集成了 `@radix-ui/react-presence`。当 `open` 切换为 `false` 时：

- Radix 并不会立即把 DOM 从树上移除；
- 它将 DOM 属性置为 `data-state="closed"`，并挂载监听 `animationstart` 与 `animationend`；
- 若元素有 CSS 动画在运行，它会等待动画完全播放完毕后再执行 unmount。

#### 2. 代码现场：全仓普遍存在的“React 强制物理斩断”

审查员穿透了所有业务浮层消费端代码，发现了惊人的一致性事实——**绝大多数上层业务组件在 `open=false` 时，直接执行了短路渲染或 `return null`，将整个 Popover 连根拔起**：

- **证据 1：`ModelBadgePickerMenu.tsx:168`**
  ```tsx
  if (!open) return null; // 👈 open 刚变 false 的首帧，整个组件直接蒸发！
  return (
    <Menu openState={{ open, ... }} panel={{ contentClassName: styles.mbMenu }}>
  ```
- **证据 2：`ComposePlusMenu.tsx:263`**
  ```tsx
  if (!open) return null; // 👈 瞬间销毁 SmartExpandablePanel
  return <SmartExpandablePanel open={open} ... />
  ```
- **证据 3：`PermissionModeMenu.tsx:125`**
  ```tsx
  {open ? ( // 👈 条件渲染：关闭时瞬间 unmount
    <Menu openState={{ open, ... }} panel={{ contentClassName: styles.permMenu }} />
  ) : null}
  ```
- **证据 4：`SelectContent.tsx:100`（自研 Select）**
  ```tsx
  if (!ctx.open) return null; // 👈 关闭时直接销毁 Portal 节点
  ```
- **证据 5：`Menu.tsx:284-286`（核心基座内部逻辑）**
  ```tsx
  if (anchor && !isOpen) {
    return null; // 👈 只要传了 anchor，Menu 自己在 !isOpen 时也直接 return null！
  }
  ```

#### 3. 冲突定性与架构结论

在上述所有组件中，一旦用户点击外部或选中选项，React 在当帧直接卸载了节点。`data-state="closed"` 的生命周期在 DOM 中存活时间恒为 **0 毫秒**。
若详案执迷于“让所有下拉菜单播放 100ms 退出动画”，就必须：

1. 把这数十个业务组件的 `if (!open) return null` 全部删除；
2. 为所有组件引入 `isExiting` 状态机或重构状态提升；
3. 将 `Menu.tsx:284` 的 `anchor` 模式全部改写为全时挂载。

这不仅会产生严重的内存常驻与幽灵层风险，而且严重违反了根目录 `ANTI_OVERENGINEERING_GUARDRAILS.md`（反过度设计红线）与 `AGENTS.md` §1 铁律。

### 2.3 `Menu.module.css:41-44` `display: none` 的处理裁决

#### 现状分析

在 `apps/crish-desktop/src/components/ui/Menu/Menu.module.css:41-44`：

```css
.menuContent[data-state='closed'] {
  animation: none;
  display: none;
}
```

作者初衷是为了在纯 `trigger` 模式（非 anchor、无 `if (!open) return null` 阻断）下，当 Radix 未完全卸载时，防止残留不可见的图层阻挡页面点击。但写了 `display: none`，会导致即便 Radix 处于 presence 阶段，元素也会由于盒模型直接消失而看不到任何过渡。

#### 审查裁决

1. **移除 `display: none` 与 `animation: none`**：
   将其升级为干净的加速离场过渡：
   ```css
   .menuContent[data-state='closed'] {
     animation: crish-popover-exit 100ms cubic-bezier(0.4, 0, 1, 1) forwards;
     pointer-events: none;
   }
   ```
   使用 `pointer-events: none` 既完美解决离场期间误挡鼠标交互的问题，又为原生支持 Presence 的通道保留平滑退场能力。
2. **战略优先级明确**：
   **核心发力点 100% 聚焦于入场动效（140ms 微位移 + scale(0.97) + 贝塞尔平滑减速）**。
   人机工程学事实：下拉菜单是工具型临时界面，用户关掉它时心理预期是“即刻执行操作或专注文档”，0ms 物理卸载属于自然的利落行为；而弹出时必须有 140ms 柔和滑入，彻底消灭生硬闪现。

## 3. 核心任务 2：Chevron 小箭头的 DOM 命中与旋转方案审查

### 3.1 `ComposerProjectPicker.tsx` 脆弱选择器 `svg:last-child` 风险排查

详案 01 §2.4 提出的方案为：

```css
.projectPill svg:last-child {
  transition: transform 150ms var(--ease-emphasized);
  flex-shrink: 0;
}
.projectPill[aria-expanded='true'] svg:last-child {
  transform: rotate(180deg);
}
```

#### 源码穿透排查

审查 `apps/crish-desktop/src/components/chat-card/ComposerProjectPicker.tsx:200-213`：

```tsx
<Button
  bare
  type="button"
  className={styles.projectPill}
  data-composer-project-picker=""
  aria-expanded={open}
  aria-haspopup="menu"
  aria-label={ariaLabel}
>
  <AppIcon name="folder" size={12} aria-hidden />
  <span className={styles.projectName}>{displayName}</span>
  <AppIcon name="chevron-down" size={12} aria-hidden />
</Button>
```

再审查 `AppIcon.tsx:80-92`：
`<AppIcon name="folder" />` 会直接渲染一个 `<svg data-icon="folder" ...>`。
`<AppIcon name="chevron-down" />` 会直接渲染一个 `<svg data-icon="chevron-down" ...>`。

#### 致命缺陷分析

1. **结构脆弱性（Fragile Structural Dependency）**：
   CSS 选择器 `svg:last-child` 依赖的前提是：**该元素必须是父级节点的绝对最后一个子节点，且类型必须是 svg**。
   - 若业务在右侧添加了清除按钮、锁定徽章、提示信息、快捷键角标或小红点（例如 `<span className={styles.badge} />`），`svg:last-child` 将立即**静默失效**（因为最后一个子节点是 `span`，不符合 `svg:last-child`）；
   - 若某模式下不渲染 Chevron，而只渲染了文件夹图标，若其恰好排在最后，`svg:last-child` 将导致**文件夹图标被旋转 180°（倒立）**！
2. **违背架构底线**：
   详案作者企图通过不修改 JSX 的“纯 CSS 补丁”，这是典型的“避重就轻打补丁”，违背了 `AGENTS.md` §7 铁律。

### 3.2 最精准稳健的选择器与类名绑定方案

修改 `ComposerProjectPicker.tsx` 的 JSX，向 Chevron 图标显式注入独立的 CSS Modules 类名 `styles.chevron`：

```tsx
// ComposerProjectPicker.tsx:211
<AppIcon name="chevron-down" size={12} className={styles.chevron} aria-hidden />
```

在 `ComposerProjectPicker.module.css` 中定义精准样式：

```css
/* ComposerProjectPicker.module.css */
.chevron {
  flex-shrink: 0;
  color: var(--text-tertiary);
  transition:
    transform 150ms var(--ease-emphasized),
    color var(--transition-micro);
  will-change: transform;
}

.projectPill:hover .chevron {
  color: var(--text-secondary);
}

.projectPill[aria-expanded='true'] .chevron {
  transform: rotate(180deg);
  color: var(--text-primary);
}
```

**收益**：

- $O(1)$ 单类名命中，零遍历、零子节点顺序依赖；
- 与全仓 `SelectTrigger.module.css` 的 `.chevron`、`PermissionModeMenu.module.css` 的 `.permPillChev` 保持设计语言与代码结构 100% 统一。

### 3.3 `SelectTrigger.module.css`：上下双箭头（`ChevronUpDown`）旋转几何异样审查

#### 源码穿透排查

审查 `apps/crish-desktop/src/components/ui/Select/SelectTrigger.tsx:159-161`：

```tsx
<span className={styles.chevron} aria-hidden="true">
  <ChevronUpDownIcon size={ctx.size === 'lg' ? 16 : 14} />
</span>
```

再审查 `SelectIcons.tsx:16-35` 中 `ChevronUpDownIcon` 的 SVG 路径：

```tsx
<path d="M5 6.5L8 3.5L11 6.5" />  {/* 向上小三角 ^ */}
<path d="M5 9.5L8 12.5L11 9.5" /> {/* 向下小三角 v */}
```

#### 视觉认知与几何学冲突

`ChevronUpDownIcon` 是**中心对称图形**（上下各有一个箭头，形状为 `/\ \/`）。
如果直接对其应用 `transform: rotate(180deg)`：

- 旋转前：上面指着上，下面指着下；
- 旋转后：上面依然指着上，下面依然指着下！
- **几何终态与初始态完全一致**！
- 用户在展开时，只会看到图标在原地莫名其妙自转了半圈，展开定格后没有任何“当前已处于展开态”的视觉提示（不像单向箭头从 `v` 变成 `^`），反造成视觉困惑。

#### 审查裁决方案

- **推荐方案（视觉精准）**：
  若保持 `ChevronUpDownIcon` 图标语义（代表系统级 Picker），在展开态下：
  ```css
  /* SelectTrigger.module.css */
  .chevron {
    display: inline-flex;
    align-items: center;
    justify-content: center;
    flex-shrink: 0;
    color: var(--text-tertiary);
    margin-left: auto;
    transition:
      color var(--transition-micro),
      transform 150ms var(--ease-emphasized);
    will-change: transform;
  }

  .trigger.open .chevron,
  .trigger[data-state='open'] .chevron {
    color: var(--text-primary);
    transform: translateY(-1px); /* 轻微浮动上跃，指示活跃态 */
  }
  ```
- **备选方案（标准单向下拉）**：
  若产品与设计规范要求下拉菜单必须具备 180° 指示性旋转，应将 `SelectTrigger.tsx` 的图标替换为单向 `<AppIcon name="chevron-down" />`。但在未统一提单改动图标组件前，严禁盲目套用 `rotate(180deg)`。

### 3.4 `PermissionModeMenu.tsx`：状态联动与曲线参数修正

#### 现状分析

审查 `PermissionModeMenu.module.css:55-63`：

```css
.permPillChev {
  opacity: 0.55;
  transition: transform var(--transition-micro, 100ms ease);
  flex-shrink: 0;
}
.permPill.isOpen .permPillChev {
  transform: rotate(180deg);
}
```

**现存不足**：

1. 缓动曲线采用 `100ms ease`，节奏仓促生硬，与浮层入场的 `140ms var(--ease-emphasized)` 脱节；
2. 选择器仅绑定了 `.permPill.isOpen`，遗漏了 `[aria-expanded='true']`，在部分无障碍和测试断言中状态不完整。

#### 修正方案

```css
.permPillChev {
  opacity: 0.55;
  transition:
    transform 150ms var(--ease-emphasized),
    opacity var(--transition-micro);
  flex-shrink: 0;
  will-change: transform;
}

.permPill.isOpen .permPillChev,
.permPill[aria-expanded='true'] .permPillChev {
  transform: rotate(180deg);
  opacity: 0.9;
}
```

## 4. 核心任务 3：CSS 特异性（Specificity）层叠冲突审查与彻底解决方案

### 4.1 特异性反向碾压的数学证据（`0-2-0` vs `0-1-0`）

#### 现场代码证据

1. **基座层定义**（`apps/crish-desktop/src/components/ui/Menu/Menu.module.css:37-39`）：
   ```css
   .menuContent[data-state='open'] {
     animation: cds-popover-enter var(--transition-popover-enter) forwards;
   }
   ```
2. **消费端面板定义**（`apps/crish-desktop/src/components/provider/ModelBadgePickerMenu.module.css:1-13`）：
   ```css
   .mbMenu {
     ...
     animation: crish-popover-enter var(--transition-popover-enter) forwards;
   }
   ```
3. **DOM 渲染形态**（`Menu.tsx:275, 294`）：
   ```tsx
   const contentClasses = [styles.menuContent, contentClassName]
     .filter(Boolean)
     .join(' ');
   // 渲染结果: <div class="menuContent mbMenu" data-state="open">
   ```

#### 浏览器特异性裁判过程

依据 W3C CSS Cascading and Inheritance 规范：

- 选择器 A：`.menuContent[data-state='open']`
  - 1 个 Class (`.menuContent`) + 1 个 Attribute (`[data-state='open']`) $\to$ **特异性 = `(0, 2, 0)`**
- 选择器 B：`.mbMenu`
  - 1 个 Class (`.mbMenu`) $\to$ **特异性 = `(0, 1, 0)`**

$$\text{Specificity}(A) = (0, 2, 0) > \text{Specificity}(B) = (0, 1, 0)$$

**致命后果**：
选择器 A 拥有更高的特异性，因此浏览器强制采用选择器 A 的属性！原本在 `ModelBadgePickerMenu.module.css` 中声明正确的 `crish-popover-enter`，被基座层失效的 `cds-popover-enter` **无情覆盖并处死**！这也是为什么此前即使个别组件写对了动画名称，在界面上依然毫无动效闪现的深层根因。

同理，若在 `SmartExpandablePanel.module.css` 中仅声明：

```css
.panel {
  animation: crish-popover-enter 140ms var(--ease-emphasized) forwards;
}
```

由于 `SmartExpandablePanel.tsx:340` 同样混入了 `menuStyles.menuContent`，特异性 `(0, 1, 0)` 同样会被基座的 `(0, 2, 0)` 碾碎。

### 4.2 杜绝 `!important` 补丁：SSOT 基座内敛化方案设计

严禁使用 `!important` 污染层叠上下文。彻底解决该问题的工业级解法是——**将双向动画感知与动态锚点全量收敛至基座层（Single Source of Truth），子组件无需重复声明动画**！

#### 基座层改造（`Menu.module.css` & `SmartExpandablePanel.module.css`）

在基座层直接支持 Radix 动态锚点与 `[data-side]` 双向感知：

```css
/* apps/crish-desktop/src/components/ui/Menu/Menu.module.css */
.menuContent {
  /* 优先消费 Radix 计算的几何锚点，兜底为 top center */
  transform-origin: var(--radix-popover-content-transform-origin, top center);
  will-change: transform, opacity;
}

/* 默认向下弹出 (data-side='bottom') */
.menuContent[data-state='open'] {
  animation: crish-popover-enter 140ms var(--ease-emphasized) forwards;
}

/* 向上弹出自适应 (data-side='top') */
.menuContent[data-state='open'][data-side='top'] {
  animation-name: crish-popover-enter-top;
}

/* 优雅离场过渡 */
.menuContent[data-state='closed'] {
  animation: crish-popover-exit 100ms cubic-bezier(0.4, 0, 1, 1) forwards;
  pointer-events: none;
}

.menuContent[data-state='closed'][data-side='top'] {
  animation-name: crish-popover-exit-top;
}
```

#### 子组件净收敛

在 `ModelBadgePickerMenu.module.css`、`PermissionModeMenu.module.css`、`SmartExpandablePanel.module.css` 中：

- **彻底删去**多余的 `animation: ...` 声明；
- 继承基座天然赋予的 140ms 入场、`data-side='top'` 向上微升、`data-side='bottom'` 向下滑入能力；
- 架构实现真正的零冲突与代码净收敛。

### 4.3 消费端定制的合法提权规则

若未来有极特殊面板（如某种全屏展开浮层）确实需要覆盖基座动效，必须遵守**特异性对齐契约**，使用状态属性选择器维持 `(0, 2, 0)` 特异性：

```css
/* 合法提权写法：Class + Attribute = (0, 2, 0) */
.customPanel[data-state='open'] {
  animation: custom-popover-enter 200ms var(--ease-emphasized) forwards;
}
```

## 5. 时序与渲染边界补充审查（Custom Floating vs Radix Popover）

### 5.1 `SelectContent.tsx` 首帧定位竞态（FOUPC 闪烁）治理

#### 现状隐患排查

审查 `apps/crish-desktop/src/components/ui/Select/SelectContent.tsx:125-131`：

```tsx
style={{
  left: `${position.x}px`,
  top: `${position.y}px`,
  transformOrigin: position.transformOrigin,
  visibility: position.isPositioned ? 'visible' : 'hidden',
  pointerEvents: position.isPositioned ? 'auto' : 'none',
}}
```

与 `SelectContent.module.css:23`：

```css
animation: selectPopEnter 140ms cubic-bezier(0.16, 1, 0.3, 1) forwards;
```

**时序断层剖析**：

- 节点刚被 Portal 挂载时，`position.isPositioned` 为 `false`，内联样式为 `visibility: hidden`；
- 但 CSS 中只要元素挂载到 DOM，140ms 的入场动画立刻开始空转计时；
- 经过 1 帧或 2 帧，`useFloatingPosition` 算完坐标并触发组件重新渲染，`isPositioned` 变为 `true`，`visibility` 变为 `visible`；
- 此时用户看到的往往是**已经播放了 30ms~50ms 的残缺动画**，甚至由于第一帧坐标跳变引起微小闪烁（Flash of Unpositioned Content）。

#### 修正方案

在 `SelectContent.tsx` 中为容器元素打上 `data-positioned={position.isPositioned}` 标识：

```tsx
// SelectContent.tsx:138
data-positioned={position.isPositioned ? 'true' : 'false'}
```

在 `SelectContent.module.css` 中改造动画激活时机：

```css
.content {
  will-change: transform, opacity;
  animation: none; /* 未就绪前静止 */
}

/* 仅当坐标测量完毕且可见后，才激发 140ms 入场动画 */
.content[data-state='open'][data-positioned='true'] {
  animation: crish-popover-enter 140ms var(--ease-emphasized) forwards;
}

.content[data-state='open'][data-positioned='true'][data-side='top'] {
  animation-name: crish-popover-enter-top;
}
```

### 5.2 `transform-origin` 动态变量消费规范

在 `ModelBadgePickerMenu.module.css:14` 与 `SidebarContextMenus.module.css:19` 中，均发现了硬编码的 `transform-origin: top left;`。
当菜单在界面下方（如在 ChatComposer 底部）向上弹出时，Radix 会自动在内联样式中注入 `--radix-popover-content-transform-origin: bottom right`。
硬编码 `top left` 导致缩放动画的锚点完全脱离点击源头，视觉上呈现从左上角撕扯展开的异形感。

**统一规范**：
全仓浮层一律使用：

```css
transform-origin: var(--radix-popover-content-transform-origin, top center);
```

向上弹出的菜单兜底为 `bottom center`，杜绝任何硬编码坐标。
