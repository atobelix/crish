## 1. 执行摘要与审查裁决

分维详案二（`02-输入框提示与快捷菜单动效详案.md`）确立了“响应及时（160ms）、空间微距浮现（6px）、杜绝 54px 剧烈跳跃、零果冻弹跳”的正确设计方向，但在与当前前端工程实际代码的对接上存在**三大关键断层与实施风险**：

1. **NoticeBar 折叠方案脱离 React 条件渲染机制**：
   详案直接建议在 `.composerNoticeZone` 上加 CSS Grid `grid-template-rows: 0fr` 与 `:empty` 规则，但实际代码 `ChatComposer.tsx:322` 采用 `{effectiveNotice ? <div className={...}>...</div> : null}`。一旦 Notice 被关闭或清空，整个容器在 React Commit 阶段瞬间被完全卸载（0ms 物理从 DOM 蒸发），CSS 动画根本没有挂载载体，**54px 的瞬间跳跃依旧会 100% 发生**！
2. **Tiptap 斜杠菜单动画缺失方向自适应与潜在位移冲突**：
   详案仅声明了单一正向 `translateY(6px)`，忽视了光标靠近窗口下沿时菜单会由 Floating UI 向上或向下翻转（`data-side="top"` vs `data-side="bottom"`）；若在视口受限向下反转时依然执行向上 6px 动画，会导致菜单逆向撞击输入光标；且关键帧动画必须与 Floating UI 的 `translate3d` 定位层级彻底隔离。
3. **`ComposerErrorBar` 存在死引用风险**：
   详案中为 `.errorBar` 声明 `animation: noticeIn 150ms`，但在 `ComposerErrorBar.module.css` 甚至全局均未定义该作用域下的 `@keyframes noticeIn`，将直接导致动画静默失效。

**审查裁决**：分维详案二总体设计原则合理，但**技术实现层面必须推翻重拟**。本报告提出无需引入任何重型动画库、仅通过 React 本地状态与纯 CSS Grid/Compositor 协同的轻量无过度设计方案，彻底打通落地的最后一公里。

## 3. 核心议题一：NoticeBar 54px 剧烈跳移折叠方案可行性深度穿透

### 3.1 现有详案的致命漏洞与脱节分析

#### 现状断层回顾

`ComposerNoticeBar` 是一条高度为 48px 的灵动配重胶囊，外部外边距为 `margin-bottom: 6px`，总高度占用为 **54px**。当前代码在关闭提示时：

- [ChatComposer.tsx:322-330](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-composer/ChatComposer.tsx#L322-L330):
  ```tsx
  {
    effectiveNotice ? (
      <div className={styles.composerNoticeZone} data-composer-notice-zone="">
        <ComposerNoticeBar
          notice={effectiveNotice}
          onDismiss={handleDismissNotice}
          onFeedback={onNoticeFeedback}
        />
      </div>
    ) : null;
  }
  ```
- [ComposerNoticeBar.tsx:80-82](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-composer/ComposerNoticeBar.tsx#L80-L82):
  ```tsx
  if (!notice) {
    return null;
  }
  ```

#### 详案二（02）的方案：

```css
.composerNoticeZone {
  display: grid;
  grid-template-rows: 1fr;
  transition: grid-template-rows 120ms var(--ease-emphasized);
}
.composerNoticeZone:empty,
.composerNoticeZone[data-collapsed='true'] {
  grid-template-rows: 0fr;
}
.composerNoticeInner {
  overflow: hidden;
}
```

#### 深度审查致命漏洞剖析：

1. **React 条件渲染瞬间卸载（Unmount Bypass）**：
   当用户点击关闭按钮时，调用 `handleDismissNotice`，父组件状态更新将 `notice` 设为 `null`。在接下来的 React 渲染周期中，`effectiveNotice` 变为 `null`。
   `{effectiveNotice ? <div ...> : null}` 直接使得 `<div className={styles.composerNoticeZone}>` 节点**从 DOM 树中被彻底拔除**！
   浏览器不会对一个已经不存在于 DOM 树中的节点执行任何 CSS transition；`:empty` 也永远不会被命中。结果就是：**0ms 瞬间塌陷，54px 跳动依旧**！
2. **实际 DOM 结构缺少 Grid 项包装层**：
   CSS Grid 的 `grid-template-rows: 0fr -> 1fr` 能够平滑过渡的**底层物理法则**是：
   Grid 容器内部必须有一个直接子元素（Grid Item），并且该 Grid Item 必须具备 `overflow: hidden; min-height: 0;`。
   然而在当前 `ChatComposer.tsx` 中，`.composerNoticeZone` 的直接子元素就是 `<ComposerNoticeBar>`，且没有任何 `.composerNoticeInner`。而 `ComposerNoticeBar.module.css:12-14` 明确声明了：
   `height: 48px; min-height: 48px;`！
   在 CSS Grid 规范中，Grid 项的默认最小尺寸是 `min-height: auto`，固定高度的内容会撑开 `0fr`，导致 `0fr` 根本无法将容器收拢到 0px！
3. **外部状态清空的不确定性**：
   如果仅在 `ComposerNoticeBar` 内部监听自身关闭按钮，那么一旦遇到会话切换、报错超时自动清除或由外部主动触发的 Notice 置空，组件将瞬间 unmount，依然无法实现平滑合拢。

### 3.2 轻量化无过度设计最优解：两阶段平滑退场机制（Graceful Exit Phase）

根据反过度设计红线（严禁引入类似 Framer Motion 等 100KB+ 的外部动效库，坚守纯原生 React + CSS 方案），我们对比了两种技术路线：

| 维度           | 方案 A：NoticeBar 内部维护 `isDismissing` | 方案 B（推荐最优解）：`useComposerNotice` 两阶段退场状态机             |
| :------------- | :---------------------------------------- | :--------------------------------------------------------------------- |
| **控制范围**   | 仅能截获内部“关闭”按钮点击                | **全覆盖**：用户手动关闭、外部超时自动清除、父组件状态置空均能优雅退场 |
| **DOM 保持**   | 内部组件无法控制外部外边距与外层容器      | 外部容器与内部组件联动，**高度与下边距 6px 同步匀速合拢**              |
| **性能开销**   | 局部 `setTimeout`                         | 单个 120ms 延时定时器，退场后真正卸载 DOM，零无用节点常驻              |
| **架构整洁度** | 逻辑分散在子组件，父级高度过渡不知情      | 职责清晰收敛在 `useComposerNotice` 与 `ChatComposer`                   |

#### 最优解设计精要：

在 `useComposerNotice.ts` 中引入一个轻量两阶段退场控制器：

1. **状态保持**：维护 `displayNotice`（当前呈现在 DOM 中的 Notice 对象）与 `isClosing`（是否正处于 120ms 折叠退场阶段）。
2. **入场与常态**：当外部 `noticeProp` 存在且与当前不同时，立即同步 `displayNotice = noticeProp`，`isClosing = false`。
3. **退场触发**：当外部 `noticeProp` 变为 `null` 或用户调用 `handleDismissNotice` 时：
   - 不立即将 `displayNotice` 清空；
   - 将 `isClosing` 置为 `true`；
   - 触发 CSS Grid `grid-template-rows: 1fr -> 0fr` 与 `margin-bottom: 6px -> 0px`（120ms）；
   - 同时胶囊自身播放加速淡出动画 `100ms cubic-bezier(0.4, 0, 1, 1)`；
   - 启动 120ms 计时器，时间到达后，正式将 `displayNotice = null`，并触发父级 `onDismissNotice?.()`。
4. **中断防御（防竞态）**：如果在 120ms 退场过程中突然来了新的 `noticeProp`，立即清理定时器，重置 `isClosing = false`，恢复展示新 Notice，无任何闪烁。

#### 1. `apps/crish-desktop/src/components/chat-composer/useComposerNotice.ts` 升级

```typescript
import { useState, useEffect, useRef, useCallback } from 'react';
import type { ChatAttachment } from '../../hooks/useChatStream';
import type { ComposerNotice } from './ComposerNoticeBar';

export interface UseComposerNoticeOptions {
  attachments: ChatAttachment[];
  noticeProp?: ComposerNotice | null;
  onDismissNotice?: () => void;
}

export interface UseComposerNoticeResult {
  /** 当前正在 DOM 中渲染的 Notice（退场期间仍保留用于高度过渡） */
  displayNotice: ComposerNotice | null;
  /** 是否正在执行 120ms 折叠退场动画 */
  isClosing: boolean;
  /** 关闭处理函数（触发退场流程） */
  handleDismissNotice: () => void;
}

export function useComposerNotice({
  noticeProp,
  onDismissNotice,
}: UseComposerNoticeOptions): UseComposerNoticeResult {
  const [displayNotice, setDisplayNotice] = useState<ComposerNotice | null>(
    noticeProp ?? null
  );
  const [isClosing, setIsClosing] = useState<boolean>(false);
  const closeTimerRef = useRef<ReturnType<typeof setTimeout> | null>(null);

  // 同步外部 noticeProp 变化
  useEffect(() => {
    if (noticeProp) {
      if (closeTimerRef.current) {
        clearTimeout(closeTimerRef.current);
        closeTimerRef.current = null;
      }
      setDisplayNotice(noticeProp);
      setIsClosing(false);
    } else if (displayNotice && !isClosing) {
      // 外部主动清空 noticeProp，进入平滑退场
      setIsClosing(true);
      closeTimerRef.current = setTimeout(() => {
        setDisplayNotice(null);
        setIsClosing(false);
        closeTimerRef.current = null;
      }, 120);
    }
  }, [noticeProp]);

  // 组件卸载时清理定时器
  useEffect(() => {
    return () => {
      if (closeTimerRef.current) {
        clearTimeout(closeTimerRef.current);
      }
    };
  }, []);

  const handleDismissNotice = useCallback(() => {
    if (isClosing) return;
    setIsClosing(true);
    closeTimerRef.current = setTimeout(() => {
      setDisplayNotice(null);
      setIsClosing(false);
      closeTimerRef.current = null;
      onDismissNotice?.();
    }, 120);
  }, [isClosing, onDismissNotice]);

  return {
    displayNotice,
    isClosing,
    handleDismissNotice,
  };
}
```

## 4. 核心议题二：Tiptap SlashMenu 与 Floating UI 定位交互与防冲突审查

### 4.1 Radix Popover / Floating UI 底层定位机制剖析

在 `apps/crish-desktop/src/components/chat-composer/TiptapSlashMenu.tsx` 与 `SlashExtension.ts` 中：

1. `SlashExtension` 在光标输入 `/` 或 `@` 时，通过 `safeCursorAnchor.ts` 的 `measureCursorLineBox` 获取到光标在当前视口的绝对像素位置（`SafeAnchorRect`）。
2. `TiptapSlashMenu` 使用了 `@radix-ui/react-popover`。在挂载时，它在光标处生成一个不可见的固定定位锚点（`Popover.Anchor`），并挂载 `Popover.Portal`：
   ```tsx

     <Popover.Anchor asChild>
       <div style={triggerStyle} />
     </Popover.Anchor>
     <Popover.Portal>
       <Popover.Content
         className={styles.popoverContent}
         side={side}
         ...
   ```
3. **Radix Popover 的底层渲染结构**：
   `Popover.Portal` 在 `document.body` 中动态插入一个定位包装层：
   ```html
   <div
     data-radix-popper-content-wrapper=""
     style="position: fixed; left: 0px; top: 0px; transform: translate3d(240px, 680px, 0px); min-width: max-content; --radix-popper-transform-origin: 0% 100%; will-change: transform;"
   >
     <div
       class="popoverContent"
       data-side="top"
       data-align="start"
       data-state="open"
     >
       <div class="menuList" ...></div>
     </div>
   </div>
   ```

### 4.2 CSS transform 覆盖位移的潜在风险与 Containing Block 陷阱

#### 风险陷阱 1：关键帧 transform 覆盖包装层 inline-style

- Floating UI / Radix 的核心坐标是计算出光标相对视口的像素值，并通过内联样式：
  `style="transform: translate3d(240px, 680px, 0px);"` 施加在 `[data-radix-popper-content-wrapper]` 上。
- **高危禁忌**：如果开发人员误把动画挂载到包装层上，例如：
  ```css
  :global([data-radix-popper-content-wrapper]) {
    animation: slashMenuEnter 160ms;
  }
  ```
  在 `@keyframes slashMenuEnter` 执行期间，关键帧里的 `transform: translateY(6px)` 具有极高优先级，会**瞬间强制覆盖**包装层的内联 `translate3d(240px, 680px, 0px)`！
  其直接物理灾难就是：菜单瞬间从光标位置被扯回屏幕左上角 `(0px, 6px)` 处狂闪！

#### 风险陷阱 2：祖先级 Containing Block 污染

- 根据 W3C CSS Transforms 规范，**任何设置了非 none 的 `transform`、`filter`、`perspective` 或 `backdrop-filter` 的元素，都会为其所有后代元素强制创建新的包含块（Containing Block）**。
- 如果浮层不是渲染在 `Popover.Portal`（`document.body` 下），而是被放置在一个包含 `transform` 的组件内部，`position: fixed` 将退化为相对于该祖先元素的定位，导致 Floating UI 算出的视口坐标完全错位漂移。
- **审查结论**：`TiptapSlashMenu.tsx` 正确使用了 `<Popover.Portal>`，将包装层直接置于 `body`，成功避开了 Containing Block 污染。这一设计必须严格保持，绝不可将 Portal 移除。

#### 风险陷阱 3：单向位移动画的逆向“撞车”

- 详案二中仅声明了一个 `@keyframes slashMenuEnter`：
  ```css
  from {
    opacity: 0;
    transform: translateY(6px) scale(0.985);
  }
  ```
- 这是假设菜单永远是在光标**上方**展开（`side="top"`，向上浮出 6px）。
- 但是，当输入框在页面偏上方，或者当多行输入框高度撑满、光标在视口靠上位置时，Radix Floating UI 会触发 `avoidCollisions` 碰撞检测，自动将 `data-side` 翻转为 `"bottom"`（菜单向下方弹出）！
- 如果菜单是在光标下方弹出，却依然执行 `translateY(6px)` 向上滑入，菜单将从光标下方逆行向上冲向光标，造成明显的“逆向撞车”视觉错觉！正确的物理空间轨迹必须根据 `[data-side]` 进行动态区分。

### 4.3 安全复合变换最佳实践与双向方向感知（data-side）落地

为杜绝任何形式的坐标覆盖风险，并提供最丝滑的方向感知物理微动效，确立以下双重防御规范：

#### 防御策略 1：安全内容隔离（Safe Content Isolation）

动画加在 `.popoverContent` 自身（作为 wrapper 的子元素）上是安全的，因为它的坐标系是相对于 wrapper 的局部坐标系。但更为稳健的方式是利用独立变换属性（CSS Independent Transform Properties）或将 `translateY` 明确收敛于局部内容层。

#### 防御策略 2：利用 Radix `data-side` 与 `data-state` 驱动双向微距入场

- 当 `data-side="top"`（向上弹出）：从光标处微向上浮起（`translateY(6px) scale(0.985)` $\to$ `translateY(0) scale(1)`）；
- 当 `data-side="bottom"`（向下弹出）：从光标处微向下沉入（`translateY(-6px) scale(0.985)` $\to$ `translateY(0) scale(1)`）；
- 统一配置 `transform-origin` 对齐 Radix 的 `--radix-popover-content-transform-origin`。

#### 修改代码落地：`apps/crish-desktop/src/components/chat-composer/TiptapSlashMenu.module.css`


### 5.2 DynamicChipBar 4% 果冻晃动与脉冲绿点次像素发虚根除

#### 现状代码排查

在 `apps/crish-desktop/src/components/chat-card/ChatStatusRibbons.module.css`:

```css
.dynamicChip {
  ...
  animation: chipFadeIn var(--transition-popover-enter);
}

@keyframes chipFadeIn {
  0% {
    opacity: 0;
    transform: translateY(4px) scale(0.96);
  }
  100% {
    opacity: 1;
    transform: translateY(0) scale(1);
  }
}

@keyframes pulseDot {
  0%, 100% {
    transform: scale(1);
    opacity: 0.9;
  }
  50% {
    transform: scale(1.4);
    opacity: 0.45;
  }
}
```

#### 审查发现与物理体验分析：

1. **4% 剧烈果冻缩放（`scale(0.96)`）**：
   `DynamicChip` 是高度仅 26px 的精致药丸。当它以 `0.96` 缩放时，相当于宽度瞬间被压缩了十几个像素，文字在 Chromium 栅格化重采样时产生明显的形变跳跃，完全违背了用户“不要弄的和果冻一样上下跳”的核心诉求。
   **纠正方案**：将初始缩放比纠正为 `scale(0.985)`（1.5% 微缩放），消除橡胶感，保持实体质感。
2. **Token 顺序语法隐患**：
   `tokens.css:533` 中的 `--transition-popover-enter` 值为 `var(--ease-emphasized) 180ms`（缓动函数在前，时间在后）。在部分浏览器严格解析 `animation: <name> <duration> <timing-function>` 时存在异常风险。
   **纠正方案**：统一采用标准写法 `animation: chipFadeIn 160ms var(--ease-emphasized) forwards;`。
3. **脉冲绿点（`pulseDot`）次像素模糊**：
   绿点原本尺寸仅 6px。`scale(1.4)` 放大到 8.4px 时，因落在非物理像素点上，抗锯齿算法使得绿点边缘模糊发虚。
   **纠正方案**：改用微缩放 `scale(1.15)`，并配合 `box-shadow` 阴影外圈扩张动画，既营造出空灵的呼吸感，又保护核心绿点的锐利度。

#### 修复代码规范（`ChatStatusRibbons.module.css`）：

```css
/* apps/crish-desktop/src/components/chat-card/ChatStatusRibbons.module.css 第 30 行与第 58-79 行 */

.dynamicChip {
  ...
  /* 标准语法顺序，160ms 快速响应 */
  animation: chipFadeIn 160ms var(--ease-emphasized) forwards;
  will-change: transform, opacity;
}

@keyframes chipFadeIn {
  0% {
    opacity: 0;
    transform: translateY(4px) scale(0.985);
  }
  100% {
    opacity: 1;
    transform: translateY(0) scale(1);
  }
}

/* 绿点微呼吸：保护 6px 核心清晰度，利用柔和光晕扩散 */
@keyframes pulseDot {
  0%,
  100% {
    transform: scale(1);
    box-shadow: 0 0 0 0 color-mix(in srgb, var(--accent-green) 50%, transparent);
    opacity: 0.95;
  }
  50% {
    transform: scale(1.15);
    box-shadow: 0 0 0 3px color-mix(in srgb, var(--accent-green) 0%, transparent);
    opacity: 0.6;
  }
}
```
