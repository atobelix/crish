# Conex 多 Agent 协同开发：不可逾越的红线规则 (Red Line Rules)

这份文档是对现有的 `AGENTS.md` 和防过度设计指南的强力补充，由之前的协同审计流程中提炼而出。所有在此项目中工作的 Agent 都必须**绝对遵守**以下硬性规则，绝不允许任何形式的讨价还价或自行其是。

## 1. 严禁骗取门禁通过 (Zero Tolerance for Fake CI Passing)
- **绝对禁止降级规则**：当面对 CI 流水线（如 ESLint、Clippy 或 TypeScript `typecheck`）的大量报错时，**严禁**通过修改配置文件（如 `eslint.config.js`）将报错（error）降级为警告（warning）来“糊弄”和骗取 `Exit code 0`。
- **直面 Hard Error**：所有的报错（即使是数百个 `no-unused-vars` 或 `no-explicit-any`）必须通过代码层面的重构、清理或是精确到特定行的 `eslint-disable-next-line` 来硬碰硬地修掉。
- **不得隐藏问题**：不得滥用 `@ts-expect-error` 或 `@ts-ignore` 掩盖真实存在的类型冲突。

## 2. 绝对防御底线与系统稳定性 (Absolute Defense Lines & OOM Prevention)
- **安全网永远优于极限性能**：在进行底层优化（例如针对极其高频渲染的 `requestAnimationFrame` 虚拟队列优化）时，绝不允许为了追求“原汁原味的无边界体验”而撤销系统的硬性防护网。
- **内存防爆机制 (OOM Protection)**：所有接收外部输入的流式接口、文本框和 DOM 渲染器，必须保留严格的阈值截断（例如 `100000` 字符硬截断），防止因模型失控或恶意注入导致虚拟 DOM 爆炸。
- **如果确实需要突破上限**：只能使用带有严格视口控制的 Virtualization（虚拟滚动）等成熟方案，**绝对不能**通过直接解绑长度限制来解决。

## 3. 拒绝“偷懒式”优化 (No Lazy Optimizations)
- **优化在先，截断在后**：遇到性能瓶颈或高并发需求，第一优先级是重构代码架构（如剥离序列化线程、引入防抖/节流、剥离主线程开销），而不是直接采取“截断功能”、“降级体验”这种偷懒的捷径。
- **能力逼近极限时的妥协**：只有当代码的算法优化已经达到 V8 或 DOM 的物理引擎极限，且仍然无法满足要求时，才能经过用户确认后采用功能截断。

## 4. 交叉审计的“冷血”原则 (Cold-Blooded Auditing)
- 当你被要求审计其他 Agent 的方案或代码时，你的唯一角色就是**安全与质量的吹哨人**。
- 审计报告应聚焦于**致命缺陷、潜在边界问题、作弊行为以及性能隐患**，不需要花费篇幅去表扬代码现有的优点。
- 一旦在合并前的审计流程中发现 `Exit code 1` 或是破坏性漏洞，应立即锁死合并流程并回退重写。
