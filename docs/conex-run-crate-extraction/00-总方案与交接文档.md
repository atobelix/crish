## 一、任务背景与目标

### 1.1 为什么做

2026-10 后端审计结论（最高优先级问题）：run/workflow 编排域约 1.6 万行业务逻辑塞在 Tauri 壳层（`apps/agent-workbench/src-tauri/src`）里，包括 `run/` 九模块、`workflow_commands.rs`（3671 行）、`sched/`、`subagent_spawner/`、`timers/`、`engine_*` 族、`core_*` 族。壳层是全仓改动最热、测试最薄的区域，业务逻辑与 Tauri 类型（AppHandle / State / async_runtime）纠缠。

### 1.2 目标架构

新建 workspace crate `crates/conex-run`，承载运行编排域全部业务逻辑：

```
壳层（src-tauri，bin + lib）
  ├─ 只保留：#[tauri::command] 薄壳、Tauri 宿主装配、浏览器/电脑/窗口等壳域
  └─ 依赖 ↓
conex-run（零 tauri 依赖）
  ├─ run/            run 状态机 9 模 + 11338 行测试
  ├─ workflow.rs     WorkflowBackend / 调度触发执行链
  ├─ sched/ timers/ subagent_spawner/ wait_channel/
  ├─ engine_handle.rs engine_provider(.rs+/) engine_channels.rs run_producer.rs
  ├─ core_error / core_event_bridge / core_query / buffer / audit / pricing
  ├─ status_diagnostics / task_event_consumer / wake_watcher / wakeup_summary
  ├─ run_policy / context_injection
  └─ engine_assembly.rs  ← crate ⇄ 壳层装配边界（注入契约集中地）
依赖 ↓
conex-types / conex-db / orchestrator / session-loop / agent-provider / agent-tools / conex-fs / conex-shared / conex-telemetry
```

依赖方向严格单向：壳层 → conex-run → 底层 crate，零环、零反向依赖（cargo tree 可验证 crate 不依赖 tauri/crish-agent-workbench）。

### 1.3 解耦总原则

crate **零 tauri 依赖**。所有原 tauri 触点一律改为 trait 注入或全局槽注入（见第三节）。这不是权宜——每个注入点都有明确语义（谁注入、何时注入、未注入时的行为）。

## 三、六个注入契约（crate ⇄ 壳层边界）——**续作者必读**

全部集中在 `engine_assembly.rs`（与 engine_provider.rs 的配置源）。**每个契约的注入时序都有语义**，不要随意改动顺序：

### 3.1 CommittedConfigSource（配置快照源）
- 位置：`engine_provider.rs`；trait 方法 `committed_snapshot()` / `resolve_active_model()`。
- 注入：壳层 `EngineHost::new` 里 `set_committed_config_source(Arc::new(ShellConfigSource))`（engine_build.rs，实现经壳层 `config::models_store()` 单例）。
- 存储：**RwLock<Option<...>>，可覆盖**（不是 OnceLock）——crate 内测试按用例注入 TestConfigSource 替身。
- 消费：`load_provider_endpoint()` 与 `protocol::live_catalog()` 的唯一配置读面。

### 3.2 EngineHostHooks（壳域工具注册 + workflow 通道）
- `register_host_tools(&mut ToolRegistry)`：browser 工具族后置注册（27 §3 纪律：不进 register_builtin_tools，注册数断言不可扰动）；computer 工具族生产路径原本就未注册（仅测试面 `#[cfg(test)] register_tools`，维持现状）。
- `workflow_creation_channel() -> Option<Arc<dyn WorkflowCreationChannel>>`：create_workflow 工具延迟绑定面；返回的是壳层 `WorkflowCreationChannelBinding`（其 `bind(backend, app)` 在 main.rs setup ⑧c 生产转正）。
- 注入时点：`set_engine_host_hooks` 在 EngineHost::new；消费时点 = `conex_run::engine_handle::assemble_engine_core` 内置工具注册完成后调用（未注入 = 测试面跳过，工具缺失降级）。

### 3.3 RunLaunchHooks（run 装配后置接线）
- `on_run_assembled(session_id, subagent_run, abort_signal)`：主 run → browser estop 复位 + watcher；所有 run → computer 停止 watcher。estop 仅主 run 装配的语义（31 评审 F2）在钩子实现里保持。
- 注入：EngineHost::new；消费：`run/run_launch.rs` 的 run_task_impl 装配区（abort_signal 创建后）。

### 3.4 WorkflowEventSink（workflow 域事件广播）
- `emit(&self, event, payload)`：替代原 `emit_workflow_event(&AppHandle,...)`。Tauri 实现 = 壳层 `TauriWorkflowEventSink`。
- 注入点两处（main.rs）：`WorkflowBackend::set_app_context(dir, Some(sink))` 与 `ProductionScheduledLauncher::new(sink, core_state, backend, dir)`。
- 注意 crate 侧 `workflow.rs` 的 `set_app_context` 第二参已从 `Option<tauri::AppHandle>` 改为 `Option<Arc<dyn WorkflowEventSink>>`。

### 3.5 runtime 句柄槽（替代 tauri::async_runtime）
- `set_runtime_handle(Handle)` + `spawn_here(future)` / `block_on_here(future)`（engine_assembly.rs）。
- 注入：EngineHost::new（经 `tauri::async_runtime::block_on(async { Handle::current() })` 取句柄——这是壳层唯一一次触碰 async_runtime 来喂 crate）。
- 消费：run_snapshot 周期快照 / 退出阻塞落盘 / drive 任务 spawn / 缓冲桥 trailing flush。`spawn_here` 未注入时回落 `Handle::current()`（测试上下文）；`block_on_here` 未注入 panic（装配契约违约）。
- **语义注意**：原 tauri JoinHandle 有 `.inner()`；crate 全部改原生 `tokio::task::JoinHandle`（run_core 的 driver/audit_persist 字段、tests 的 finished_driver 等）。

### 3.6 app_data_dir 槽 + note_backend 工厂
- `set_app_data_dir(PathBuf)`：run 域后台任务日志根（log_root）消费；未注入回落系统 temp_dir。
- `set_note_backend_factory(Arc<dyn Fn() -> Option<Arc<dyn NoteBackend>>>)`：壳层注入 `|| crate::note_runtime::try_backend()`；crate 侧 run_producer 每次产 run 时惰性调用（None = 工具 note_backend_unwired）。NoteBackend trait 真源在 agent-tools（`agent_tools::note_backend::NoteBackendHandle`）。

**另有一个宿主实现**：`tauri_emitter.rs` 的 `TauriEmitter`（Emitter trait 实现），main.rs 事件桥 / PushAwareEmitter 内层 / browser 槽事件 / computer 槽事件统一用它。PushAwareEmitter（lib push 模块）现在**直接实现** `conex_run::core_event_bridge::Emitter`（push/pusher.rs），不再需要 lib/bin 双向桥。

- push_wiring.rs 的 `lib_push_aware_emitter_usable_as_bin_emitter` 测试 + LibRecordingEmitter/RecordingLibChannel 等 helper：被测物（lib/bin 双 Emitter trait 桥）随双副本合一**物理消失**。PushAwareEmitter 的转发+直推语义仍在 lib push 模块自身测试覆盖。**§9 测试资产保护铁律的适用性判断**：被测架构不存在则测试随之退役，属结构收敛而非删资产；如不认同，等价覆盖应在 push 模块内补，而非复活桥接。
