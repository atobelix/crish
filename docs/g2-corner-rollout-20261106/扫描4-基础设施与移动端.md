### 1.2 引用普查：值层面已高度 token 化，但引用锚在废弃别名层

- 全 app（`apps/crish-desktop` 已跟踪文件）：**180 个文件、949 处** `border-radius`；其中 CSS 162 文件、TS 11 文件、TSX 7 文件。长写分角属性（`border-top-left-radius` 等）仅 6 处 / 2 文件，可忽略。
- `src/` 内声明行 **861 条**，按值分类：

| 类别 | 条数 | 占比 |
|---|---|---|
| `var(--…)` token 引用 | 687 | 79.8% |
| 字面量/其他 | 167 | 19.4% |
| `calc()` 派生 | 7 | 0.8% |

- 167 条字面量里大头是**非卡片语义**：`50%` ≈67 条（正圆：头像、状态点、圆钮）、`0` ≈55 条（直角复位）、`inherit` 10 条。真正的**裸 px 卡片级半径**只有约 30–40 条（如 `14px` ×9、`1px` ×5、`4px` ×5、`10px` ×4、`18px/20px/12px/8px/6px` 各 1，及 `14px 0 0 14px` 类分角速记 ×4）。TS/TSX 内联样式同理，多数走 `var(--radius-*)` 字符串，裸值仅个别（如 `ApprovalCountdownBar.tsx` 的 `borderRadius: 2` ×2、`ModelBadgePickerMenu.tsx` 的 `'14px'`）。
- **但 token 引用的构成是倒置的**：引用量最大的全是废弃别名——`--radius-sm` 158、`--radius-md` 148、`--radius-lg` 58、`--radius-xs` 50、`--radius-xl` 41、`--radius-m` 18、`--radius-2xl` 15、`--radius-l` 14、`--radius-s` 12、`--radius-3xl` 7、`--radius-full` 3，合计约 **524 条（占 var 引用的 76%）**；而语义角色层用量很低：`--radius-control` 21、`--radius-menu-inner` 11、`--radius-menu-outer` 7、`--radius-card` 仅 6、`--radius-option` 5、`--radius-row` 5、`--radius-dock` 不进前列（经 `--composer-radius-outer` 间接使用）。即：**值没散，名字的权威层散了**——现行代码事实上以废弃别名层为日常口径。

### 1.5 共享 UI 原语（`components/ui/`，共 35 个目录）

原语层同样逐个在自己的 module CSS 里写 border-radius，无统一的圆角注入点：统计到的原语内声明以 `50%` ×10（Spinner/圆钮类）、`var(--radius-md)` ×9、`var(--radius-xs)` ×8、`var(--radius-lg)` ×8、`var(--radius-sm)` ×7、`inherit` ×6 为主，仍以别名层为主锚。几个关键原语：

- **Button**：`--btn-radius: var(--button-radius)`，变体覆写为 `--radius-control` / `--radius-lg`；权威值 `--radius-btn: 10px` 由 layout-contract 钉死。
- **Card / Dialog / Popover / Menu / Tooltip / ConfirmDialog**：各自 CSS（或 TSX 内联，如 ConfirmDialog 用内联 `borderRadius: 'var(--radius-md, 8px)'`）取半径，无共享基类。
- **SegmentedControl / Tabs**：自带 outer/inner 私有变量做同心推导（§1.3）。
- **ScrollArea**：`--scrollbar-thumb-radius` 私有变量。

结论：原语层是「每个原语自带一份圆角声明」，G² 集中管理若只做 token 层，原语层仍需逐个接入。

### 1.6 既有 G² / corner-shape / SVG 路径尝试

- **产品代码内：零。** `corner-shape`、`squircle`、`superellipse` 在 `apps/crish-desktop/src` 内无任何实现命中（仅 `Sidebar.module.css:407` 一条注释把 10px 圆角口语称为「squircle」）；`clip-path` 仅 3 处且全是 `inset(50%)` 类裁切（AnimatedCounter、ColorPicker），与角轮廓无关；无 SVG 背景层作角的先例。

### 1.8 散落度量化结论

| 维度 | 结论 |
|---|---|
| 半径**值** | 集中。裸 px 卡片半径仅约 30–40 处；值由 tokens-radius.css 一文件定义。 |
| 半径**引用名** | 分散且倒置。约 76% 的 var 引用挂在自称待清除的 WAVE2 别名层；语义角色层近乎闲置。 |
| 半径**推导** | 分散。≥15 个模块私有半径变量各写一份同心推导；1 处 token 被模块局部改值（SettingsRulesTab `--radius-xl: 14px`）。 |
| 圆角**形状** | 至今只有普通圆弧一种（border-radius），形状层无任何集中点——G² 化等于**新建一层**，不是改一层。 |
| 文件面 | 180 文件 / 949 处，长尾分布，无单点组件可代改。 |

一句话：桌面端「半径数值」已集中、「圆角形状」从未集中；G² 推广的真实工作量在形状层的建立与逐面接入，而非数值收敛（数值侧只剩别名层倒置这一笔历史账，是否同批处理见 §3.6 问题 7）。

### 2.4 既有 SVG 表面先例：SoftShadow 体系（G² 化的现成地基）

移动端**已经有**一套 SVG 表面渲染基建：`SoftShadow.tsx` / `SoftShadowSurface.tsx` 用 `react-native-svg`（15.15.4，已在 dependencies）以实测尺寸 W×H 现场生成 SVG 层承载阴影轮廓（第二校准的 feComposite 挖空 + userSpaceOnUse 全画布即出自此体系），宿主把 borderRadius 作为数值 prop 传入、SVG 侧据此画轮廓。也就是说：**「按实测尺寸生成轮廓路径」这条路移动端已经在生产里跑通了**（阴影用途），G² 化在移动端是把同一生成点从「阴影轮廓」扩到「表面轮廓本身」，不是从零建基建。

### 2.5 RN 实现 G² 的可行路线（初判）

RN 原生 `borderRadius` 只有普通圆弧（Android/iOS 皆然），且本项目验收平台为 **Android 12（P40 Pro，Kirin 990）**、iOS 不追求——以下按 Android 为准：

| 路线 | 做法 | 代价/风险初判 |
|---|---|---|
| (a) SVG 轮廓层（扩 SoftShadow 先例） | 表面填充改由 react-native-svg 的 Path（超椭圆角，自生成）承载，内容层叠其上；阴影可与轮廓同层生成（与 SoftShadow 现有职责天然合并） | 与现有基建同构，风险最低的一条；但每个表面多一个 SVG 层：长列表行复用/滚动时的重绘成本需实测（Kirin 990 为 CPU 渲染敏感机型）；动态尺寸需 onLayout 驱动重生成（SoftShadow 已有此模式） |
| (b) clipPath / mask 裁切 | 容器保持普通 View，用 SVG clipPath 按超椭圆轮廓裁内容 | RN 的 clipPath 支持面窄（需经 react-native-svg 的 ClipPath + Svg 容器，普通 View 不能直接吃）；且裁切不解决填充与阴影，只适合「内容溢出裁切」子场景 |
| (c) `borderCurve: 'continuous'` | iOS 专有属性，Android 无效 | **验收平台是 Android，直接出局**；仅记录以免后续有人提 |
| (d) 普通圆弧保底（现状） | 不动 | 与 G² 标准差距同桌面路线 (c)：名义半径同值时轮廓系统性偏「瘦」，用户已在桌面侧明确表达能看出差别；移动端是否同标准是口径问题（§3.6 问题 5），不在此代答 |

另两条移动端特有硬约束，先于路线选型存在：① **elevation/阴影与轮廓同节点问题**（roundButton 审计定案）——任何把轮廓改到 SVG 层的方案必须复核阴影承载方式，不能把 elevation 挂回带 9999 的节点；② **性能预算未测**——SoftShadow 目前只用于少量大表面（按钮/composer 级别，全屏同时在场的数量是个位数到两位数），若扩到列表行级别（会话列表、设置行），在场 SVG 层数量上两个数量级，须先做在场数量与帧率的实测再定推广面。

## 三、系统性改造方案：G² 圆角的集中管理与全产品推广（方案输入）

设计原则先行（均为本方案的论证，不是已定口径）：**名义半径的真相源已经存在（tokens-radius.css / theme.ts），本方案不新建数值体系；要新建的是「形状层」——轮廓形状必须像数值一样只有一个来源：一个参数、一份生成代码、一组接入面。** 任何表面不得再自带轮廓推导（对应用户原话「专门管理，不要放在哪里都是了」）。

### 3.1 真相源设计

#### 3.1.1 参数层：形状参数进 token，与半径档位表绑定

桌面在 `tokens-radius.css` 增设形状区（与现有半径定义同文件同作用域，深浅共用），草案：

```css
/* 形状层（G² 连续曲率）—— 全产品唯一形状来源 */
--corner-exponent: 2.42;          /* 超椭圆指数 n，全产品单值 */
--corner-kappa-peak: 1.337;       /* κ_peak = 1.337 / R，校验用常量，随 n 由公式锁定 */
```

- **单值而非逐档**：n 是「曲率语言」本身，设计稿全稿（R24/20/16/10）用同一 n；若逐档可调，等于允许每个表面自选形状，集中管理即告失效。R 只决定 κ 的大小（κ_peak = 1.337/R），n 决定曲线的族。
- **档位表**（半径 token → 形状待遇的映射，写进 tokens 文件注释 + 守卫断言，施工前须经 §3.6 问题 1/2 定档）：

| 半径档 | 桌面 token（值） | 移动 token（值） | 形状待遇（草案） |
|---|---|---|---|
| 枢纽/坞 | `--radius-dock` 20 | `sheet` 28 / `composer` 26 | G² 全表面（第一波） |
| 模态 | `--radius-modal` 24 | `dialog` 36 / `overlay` 30 | G² 全表面（第一波） |
| 浮层外框 | `--radius-menu-outer` 18 / `--sep-radius-outer` | `menu` 18 / `sheetApproval` 24 | G² 全表面（第一波） |
| 卡片 | `--radius-card` 12 / `--radius-option` 12 / `--radius-menu-inner` 12 | `card` 20 | G² 全表面（第二波） |
| 控件/按钮 | `--radius-control` 8 / `--radius-btn` 10 | `control` 12 | 待定档（问题 1） |
| 行 | `--radius-row` 6（别名层 sm 6 / xs 4 用量最大） | `xs` 6 / `sm` 10 | 待定档（问题 1） |
| 胶囊 | `--radius-pill` 9999 | `pill` 9999 | 几何半圆本身即连续——设计稿既定不改（推广沿用与否见问题 2） |
| 正圆 | `--radius-circle` 50% | 直径/2 实值 | 豁免（圆是常曲率，无 G² 课题） |
| 非对称角 | 气泡 `14px 0 0 14px` 类速记 | `bubble` 18 + `bubbleTail` 4 | 生成器须支持逐角 R（§3.1.2），待遇随所属表面档 |

#### 3.1.2 生成层：一份生成代码，两个宿主端形态

**核心生成函数（单一实现，两端各一份同构转写 + 同一数值测试向量互相校验）**：

```ts
// 输入：实测宽高、四角名义半径、指数 n；输出：闭合轮廓路径
// 每角取超椭圆 (R−x)^n + (R−y)^n = R^n 的四分之一段采样（设计稿用 24 点/角，偏差 <0.02px）
cornerPath(w: number, h: number, r: {tl,tr,br,bl}, n = CORNER_EXPONENT): PathString
kappaPeak(R: number, n = CORNER_EXPONENT): number  // = ((n−1)/2)·2^(1/2+1/n) / R
```

- 桌面形态：一个 React 组件 + 一个 hook（草案 API 见 §3.1.3），内部把路径写为行内 SVG 背景层（填充取表面底色变量），带阴影的面走 `filter: drop-shadow`（与设计稿呈现法一致）；`<input>` 类 void 元素走同路径 `clip-path`。
- 移动形态：并入既有 SoftShadow 体系——`SoftShadowSurface` 已按实测尺寸生成 SVG 轮廓，把其圆弧轮廓换成 `cornerPath` 输出即完成形状升级，宿主 API（传数值半径）不变。这是移动端成本最低的接入点，也是「先在阴影层验证生成函数」的天然试点。
- **同心链在生成层收口**：内层表面的轮廓由生成器以 `R − padding` 直接生成（角占位 = 名义 R 的性质保证同心算术与现行 `concentric-radius.contract.test.ts` 的公理完全兼容，契约的数值断言不需要改，只需在形状层另加断言）。禁止各模块再手写 `calc(var(--x-radius) - var(--pad))` 式推导——现存 ≥15 个私有半径变量（§1.3）随迁移逐个退役，退役进度由守卫的棘轮清单跟踪（§3.4）。

#### 3.1.3 接入层：表面只声明「半径档 + 形状待遇」，不碰几何

桌面草案（二选一由施工批定，均在 design-system.css / ui 原语层落点，不进模块 CSS）：

```tsx
// 形态 A：组件（适合本就是组件的表面：Dialog / Card / Popover / Toast …）
<G2Surface radius="dock" shadow="composer" className={...}>…</G2Surface>
// 形态 B：全局工具类 + 数据属性（适合 module CSS 宿主；与 S4 退场层选全局类的理由相同——
// 全局类定义在 design-system.css 内，不存在 module CSS 按名引用悬空的失效模式）
<div class="crish-g2" data-g2-radius="20" data-g2-shadow="composer">
```

- 半径以**档位名**传入（`dock`/`modal`/`menu-outer`/`card`…），组件/hook 内部查 tokens 表得数值——表面代码里不出现半径数字，更不出现路径数据。
- 尺寸由宿主实测（ResizeObserver），重生成节拍：仅在尺寸**落定**时重算（拖拽/动画进行中冻结为起始尺寸轮廓，理由见 §3.5 风险 2）；静态尺寸表面（按钮、chip、菜单项）在挂载时算一次。
- **禁止清单**（写入守卫，§3.4 逐条对应检查）：① 模块 CSS/TSX 中手写 SVG 角路径或 `corner-shape` 声明；② 新增私有半径变量（`--*-radius` 局部定义）；③ 新增裸 px `border-radius`（豁免清单除外）；④ 以 `corner-shape` 作为唯一实现（可作渐进增强叠加，但不得替代生成层）；⑤ 生成函数被复制到第二个文件（两端同构转写是唯一例外，且须共用测试向量）。

### 3.3 迁移次序论证

**第 0 波 · 真相源与守卫先行（零视觉变化）**
落 §3.1 的参数 token、生成函数（含数值测试）、组件/工具类空壳（接入后视觉应与普通圆弧**可区分但同尺寸**）、§3.4 的全部守卫与棘轮基线。理由：keyframes 悬空事故的教训是「先有引用、后无校验」；本立项面广（桌面 180 文件），没有守卫先行，迁移中途的口径漂移无法收口。此波还包含移动端 SoftShadow 试点：把生成函数先在阴影轮廓上换装验证（视觉变化最小、已有真机校准基线），为移动端路线 (a) 取得实测数据。

**第一波 · 用户点名五类 + 枢纽面对（槽 A–E + dock/modal/menu-outer 档）**
先大表面、高可见、低数量：请求面板/composer 对（产品里已有设计稿规格的对应面）、Dialog/Modal、菜单浮层。此波与 S5b/S6 的衔接是硬约束：
- **与 S5b**：S5b 在跑 popover 退场收敛 + SEP 集成 + Menu 入场死选择器。G² 第一波的槽 B（SEP）、槽 D（斜杠/popover 族）**必须等 S5b 落地后在其终态上施工**；槽 A/C/E 与 S5b 文件面不重叠，可并行。次序理由：popover 族现在是多轨副本状态，先 G² 化等于把形状层复制进每份副本，之后 S5b 收敛还要再拆一遍——先收敛、后加形状，只付一次钱。
- **与 S6**：S6 在跑会话列表/文件树动效，文件面（SidebarSessionList 12 处半径、FilesCard 18 处）与 G² 第二波的长尾面重叠。会话列表**行**属 6px 小半径档（待遇待定档，问题 1），大概率不在前两波；FilesCard 的卡片外框属 card 档第二波——两批在 FilesCard 上如相遇，以 S6 先行（动效是行为层，形状是呈现层，呈现层后叠加成本低）。

**第二波 · 卡片族整族迁移**
settings 余部、Models/Skills、DiffCard、PreviewCard、FilesCard、AgentCard、NotePaperPanel 等头部散落文件（§1.4）按「文件族」整批接入（一个文件内所有卡片面同批换装，避免同文件新旧形状混杂）。

**第三波 · 原语层与长尾**
`components/ui/*` 35 个原语逐个接入（原语接入后，其消费方自动受益，是长尾收敛的杠杆点）；其余 1–3 处的长尾模块 CSS 随棘轮清单逐项核销；控件/行小半径档按问题 1 的定档结果在本波处理。

**第四波 · 移动端（独立波，取决于问题 5 的口径）**
以 SoftShadow 试点数据为据：若路线 (a) 成立，按 §2.3 清单自 Sheet 基座与 composer 起整族推进（移动端表面数量少、token 已集中，是四波里机械成本最低的）；验收必须含 P40 Pro 真机帧率与阴影复核（roundButton 守卫回归）。

**次序总原则**：形状层永远**叠加在已收敛的配方之上**（S5b 收敛 popover、S4 已收敛退场、高度族已收敛时钟），绝不走在任何正在收敛的面之前；每波结束以守卫棘轮 + 截图验收双关收口，不绿不进下一波。

### 3.4 守卫设计：验产物，不只验意图

keyframes 悬空事故的定案（审计 B 之 T8）是：守卫只断言「定义已收敛到一处」，对「引用侧是否真的生效」不设防，于是 42 处悬空引用在全绿的收口里活了下来。G² 守卫按三层设计，每层都对着一个具体的失效模式：

**第一层 · 源码契约（意图层，快、进日常 CI）**
沿 `concentric-radius.contract.test.ts` 的先例扩写（新文件 `g2-corner.contract.test.ts`，不改旧契约）：
1. 参数唯一性：全仓只有 tokens-radius.css 定义 `--corner-exponent`，且值 = 2.42；生成函数只有一处实现（按文件路径白名单断言）。
2. 禁止清单扫描（对应 §3.1.3）：全仓 CSS/TSX 正则扫 `corner-shape`、手写 `path(` 角路径特征、私有 `--*-radius:` 局部定义、裸 px `border-radius`——命中即红，豁免只能登记在契约内的豁免表（带理由与表面名，不许整文件豁免）。
3. **棘轮（ratchet）**：现存违规（裸 px ≈30–40、私有半径变量 ≥15、别名层引用 ≈524 若纳入）逐项列成基线清单文件，断言「实际违规集合 ⊆ 基线集合」——新违规进不来，旧违规只能随迁移变短；基线文件只能由迁移批在同提交里删行，守卫比对基线行数只减不增。此法是审计 B 为 keyframes 准备的路线无关守卫（kf-audit 原型）的同构应用。

**第二层 · 产物验证（渲染层，专防悬空）**
1. **served-CSS/CSSOM 探针**：构建后（或 dev server 所 serve 的）CSS 里断言 G² 接入面的最终样式**真的携带生成几何**（SVG 背景层存在且路径非空），而不是只断言源码写了类名——这是 keyframes 事故里缺失的那一环（当时的 served CSS 里 `animation: _crish-spin_…` 无定义、守卫全绿）。
2. **生成函数数值测试**：采样点对解析超椭圆方程的偏差 < 0.02px（设计稿口径）；`kappaPeak(20) ≈ 1/14.96`；角占位 = R（路径包围盒角区恰为 R×R）；`R − padding` 同心生成与旧同心契约的数值断言并行不悖。两端（桌面 TS / 移动 TS）共用同一组测试向量数值，防同构转写漂移。
3. **live 探针（每波收口，非日常 CI）**：MCP 在真实 WebView 里对已迁移表面取 `getAnimations`/computed 样式与轮廓截图——jsdom 验不了渲染，这条是 S 波历次收口的既有做法，沿用。

**第三层 · 视觉验收（每波收口）**
按设计稿 QA 的既定做法：Chrome 无头全页截图 + 角部 5× 放大裁切存档，与胶囊端弧并置核对 κ 一致感；移动端加 P40 Pro 真机截图与帧率观察。视觉验收不进 CI，但每波报告必须附裁切图——G² 是视觉标准，最终裁判是像素，不是断言。

**守卫自身的防腐**：棘轮基线与豁免表都是「只减不增/逐项带理由」，且守卫文件列入 §1.4 那种被测面时要排除自身（concentric 契约本身含 29 处 border-radius 字样的先例——新契约需同样自排除并注明）。

### 3.5 风险与回滚面

| # | 风险 | 具体形态 | 缓解（方案内建） |
|---|---|---|---|
| 1 | **阴影不跟随轮廓** | `box-shadow` 按 border-radius 画，SVG 背景层/clip-path 的轮廓它不认识；改走 `filter: drop-shadow` 后阴影参数与现行 `--composer-shadow` 只是近似（设计稿已如实登记此差距），且 filter 比 box-shadow 贵、会建立包含块影响 fixed 子元素 | 带阴影表面逐个列入迁移槽并单独验收阴影参数；drop-shadow 参数进 token（不散落）；含 fixed/弹层子元素的表面优先评估「SVG 层只作填充、阴影仍由同 R 的隐形 border-radius 兄弟层承载」等替代形态后再定 |
| 2 | **尺寸动画中的轮廓重生成** | 高度族动画（折叠展开、composer 高度 glide、坞抽屉宽度动画）期间表面尺寸逐帧变；逐帧重生成 SVG 路径 = 每帧 layout/paint 压力，且与 S 波刚调顺的动效时钟打架 | 生成层节拍定为「尺寸落定才重算，动画中冻结起始轮廓」（§3.1.3）；槽 E（工具调用展开区）作为首个实测场验证冻结策略的观感（展开中角形不变、落定后一帧切换到终态轮廓——R 不变时差异极小，预计不可感知，但须实测确认） |
| 3 | **焦点环被裁** | `clip-path` 会连同 `box-shadow`/`outline` 视觉一并裁切；产品的 `--focus-ring` 键盘焦点态若走外扩阴影，clip 宿主会吃掉它 | 接入面清单逐项标注焦点环承载方式；void 元素（input）的 clip-path 用法在设计稿已验（焦点走亮度台阶、无外扩环），非输入表面默认不用 clip-path 而用 SVG 背景层（不裁子元素） |
| 4 | **内容溢出裁切语义变化** | 现有卡片靠 `overflow: hidden + border-radius` 裁子元素边角；SVG 背景层只画填充、不裁内容 | 需要裁切的表面保留 overflow 语义的等价实现（内层同轮廓 clip），在接入清单里逐项登记「裁切需求：有/无」，不得默认 |
| 5 | **在场层数与重绘成本（桌面）** | 聊天流是长列表 + 虚拟滚动，一屏可有数十个卡片面；每面一个 SVG 背景层，滚动重绘成本叠加；虚拟窗口重挂载时批量生成路径 | 小半径/行级表面默认不在前两波（问题 1 定档前不扩面）；生成结果按（w,h,R）缓存，相同尺寸不重算；虚拟化列表面接入前先做滚动帧率 A/B |
| 6 | **移动端性能与 elevation 冲突** | Kirin 990 CPU 渲染敏感；SVG 层扩到列表行级时在场数量涨两个数量级；elevation 与轮廓同节点的八角缺陷有前科 | 第 0 波 SoftShadow 试点先测在场数量-帧率曲线再定第四波面；roundButton / styleTokens 守卫全程回归；阴影继续由 SoftShadow 体系承载，不回 elevation |
| 7 | **他线并行污染** | 树里多条线在飞（provider/remote、工具流、approval 重构等），半径密集文件（ChatMessageRow、SEP、Menu）正是纠缠高发区 | 沿用 09:01 裁决：纠缠文件不抢改，迁移槽按文件纠缠状态动态排序（§3.3 已把槽 B/D 排在 S5b 之后）；每槽动工前 git 保存点（stash create 锚 ref）+ 延迟哈希复核，均为既有纪律 |
| 8 | **口径中途变更** | §3.6 的问题（小半径定档、胶囊沿用、移动同标准与否）任一改答，已迁移波次的待遇表要回改 | 待遇表是**数据**（tokens 注释 + 契约断言 + 生成器查表），不是写死在各表面的代码——改档只改表与个别接入面声明，不动生成层；这也是把档位名（而非数值/路径）作为接入 API 的理由 |

**回滚面**：形状层是**叠加层**——迁移不删除原 `border-radius` 声明（它退居为无生成层时的兜底，与设计稿的降级口径一致），名义半径数值全程不动。因此：单表面回滚 = 摘掉该表面的 G² 接入（一处声明），立即回到当前普通圆弧外观，零数据迁移；整波回滚 = 按槽提交逐笔 revert，守卫棘轮基线随之回加（棘轮允许在回滚提交中增行，但须在提交信息中声明回滚）。不存在不可逆步骤；移动端 SoftShadow 试点同理（换回圆弧轮廓生成一行代码）。

### 3.6 口径问题清单（只列问题，不代答）

1. **小半径定档**：控件 8/按钮 10/行 6（及别名层 4px）这些小半径表面是否纳入 G²？此量级下超椭圆与圆弧的像素差极小，但接入成本与大表面相同——全纳入、分档纳入、还是豁免？
2. **胶囊沿用**：设计稿口径「胶囊几何半圆本就连续、不改」是否全产品沿用？产品里介于卡片与胶囊之间的「大圆角近胶囊」表面（如 composer 展开态、移动 composer 的 R26@98px）按哪边归类？
3. **豁免清单边界**：正圆（头像/状态点/圆钮）与 `border-radius: 0` 之外，还有哪些表面明示豁免——滚动条 thumb、代码块/行内 code、markdown 渲染内嵌元素、拖拽幽灵行、虚拟列表行、第三方/WebView 内容？

6. **移动 composer 的胶囊态**：单行 52px 高时 R26 是严格半圆（同桌面胶囊口径），展开 98px 时 R26 保持——展开态按 G² 生成还是按胶囊族豁免？
