# G² 圆角推广立项 · 扫描 1：桌面端聊天与输入区

- 日期：2026-11-06。性质：**只读扫描**，未改任何代码。
- 规格口径：设计说明第十一节（PC `reference\muse-approval-card-design-20261106\设计说明.md`）——超椭圆角族 n=2.42、κ_peak=1.337/R、角占位=名义半径 R；生产落地须按同一轮廓参数复现（SVG 背景层 / clip-path / 原生路径任选），不得以 corner-shape 为唯一实现。
- 方法：全量普查 `border-radius` / radius 变量（CSS 声明 + TSX 内联），逐声明定位所属选择器；点名表面逐文件读源码核链路。代码基线：PC `C:\Software\conex`，`apps/crish-desktop/src`。

## 0. 总判定（先说结论）

1. **本范围内 G² = 0 处。** `corner-shape` 出现 0 次、`clip-path` 出现 0 次；全部圆角均为普通圆弧（border-radius）或有意直角。改造面 = 全部非圆/非胶囊的圆弧面。
2. **量级**：范围内 CSS `border-radius` 声明约 **322 处**（含 styles 全局文件），外加 TSX 内联 8 处有效声明（已剔除测试断言）。其中圆点/圆形（50%）与胶囊（pill/9999px）按设计稿口径「几何半圆，本就连续」**不进改造面**；`border-radius: 0` 多为有意直角（清单中标注），亦不进改造面。真正的 G² 改造面约 **190 处声明 / 约 110 个表面**。
3. **值的来源总体健康、挂接点总体存在**：绝大多数半径经 CSS 变量解析，名义 R 集中在少数 token 上（见 §1）。但存在三类系统性问题，直接决定施工切分：
   - **别名层仍是实际消费主力**：聊天域大量消费 WAVE2 废弃别名（`--radius-xl/lg/md/sm/xs/s/m`），角色 token（card/control/row）反而用得少；且 **16px（--radius-xl）在角色系里没有对应档**（card 12 与 dock 20 之间是空的），而 16 是聊天域用量最大的外框档之一（图片、附件卡回退、Diff 预览卡、ribbons 抽屉、ApprovalDock、GoalRibbon、草稿 toast 等）。G² 参数表必须为 R16 单独立档（设计稿参数表里 R16 本就存在：舞台/状态格小卡）。
   - **组件本地同心链有 6 条**（composer / ann / slash / soft-hint / toast / sep），各自在本文件内用 calc 重建「外角=内角+padding」，值同源但定义分散——这正是用户说的「不要放在哪里都是了」的现状形态。
   - **同名同面多轨**有 9 组（§8），其中图片圆角三轨、附件卡半径三值、菜单面四实现最要紧，须在逐面施工前先收敛，否则 G² 化后四家立刻分家。
4. **机制层三条全局风险**（任何路线都绕不开，须在立项方案里先定）：
   - **box-shadow 不跟随 clip-path / SVG 背景层**：走 clip-path 路线时阴影会被一并裁掉，带阴影的面（composer 卡、SEP 家族、菜单、toast 等）必须改走 `filter: drop-shadow`（设计稿稿内即如此）；走 SVG 背景层路线时原 box-shadow 仍按旧 border-radius 弧投射，角部与 G² 轮廓偏差随 R 增大（R20 时对角方向偏差约 1–2px 量级），大 R 带阴影面同样建议 drop-shadow。
   - **1px 边框沿旧弧走**：带边框的面（composer 卡、SEP、toolResultBody、菜单等）若只换背景层，边框仍画普通圆弧，与 G² 轮廓在角部错位。要么边框改由同一生成路径描边，要么该面去边框（与产品无描边方向一致，但属设计变更，需裁决）。这是全域最普遍的耦合，几乎每个外框面都有。
   - **原生替换元素（img）与尺寸不固定面**：img 的 border-radius 是直接裁切，改 G² 需 clip-path 且路径依赖实测尺寸（工具结果图 max 420×280、md 图片宽度随列宽变），要么 JS 测量生成，要么结构改造（外层容器裁切 + img 直角）。见 §9 难点 3。

### 3.1 深挖一：工具调用详细展开区域

**圆角定义全链路（实际生效路径）**：
`tokens-radius.css --radius-lg(10，别名层)` → `ChatToolCallBlock.module.css:589 .toolResultBody { border-radius: var(--radius-lg); border: 1px solid var(--border-subtle); background: var(--surface-raised); overflow: hidden }` → 组件 `ChatToolCallBlock.tsx` 渲染于 `.toolBody > .toolBodyInner` 之内。展开体内部段（`.toolSection`）一律 radius 0，靠外框 overflow hidden 统一收角——**同心链是「外框 10 + 内段直角贴合」式**，不是逐层递减式。段内容另有封顶滚动（`.toolSectionContent` max-height 180px / 单卡模式走 --expand-max-h-content，内部滚动 + 渐隐），与外框圆角不在同一层，无耦合。

**展开/收起动效与圆角的相互影响**：
- 折叠机制 = `.toolBody` 的 `grid-template-rows: 0fr→1fr` + `--accordion-duration` 同钟过渡（AN1 契约），`.toolBodyInner { overflow: hidden }` 作剪裁窗。关键点：**动画中被拉伸的是剪裁窗，不是 .toolResultBody 本体**——详情容器始终以自然高度渲染、被逐步解剪，因此挂在其上的 G² 背景层/clip 路径不发生纵向畸变，挂接安全。这与「容器本体被 height 动画拉伸」的面（如 accordion 本体带圆角者）有本质区别，本面属于低风险型。
- 但 `.toolResultBody` 的 **1px 边框沿 border-radius 旧弧绘制**：若 G² 只换背景层，边框弧与轮廓在四角错位（R10 偏差小但存在）；施工时须二选一——边框改同路径描边，或该面按无描边口径处理（需裁决，因边框是现行设计）。
- 组级同理：FoldableToolGroup `.groupBody`（grid-rows 折叠）与 FoldableProcessSection `.sectionBody` 本体均无圆角，G² 面只在被揭示的 .toolResultBody 等内容卡上（见 §6）。

**DiffCard 展开详情面（同属本深挖）**：
- 全链路：`components/diff/DiffCard.module.css .panel` 根面**根本无 border-radius 声明**（无边框卡面，靠底色分面）；文件列表族更进一步——`DiffCardFileList.test.tsx` 以测试钉死「全链路嵌套容器为纯直角 (border-radius: 0)」，CSS 中 .flatFileList/.fileNode/.fileRow/.diffPane/.scrollParent/.linesContainer/.collapseBar/.commitTriggerBar/.expandLineBtn 共 10 处显式 `border-radius: 0`；嵌入工具详情时再由 `.embeddedDiffCard` 强制 0 + 去边框。
- 即：**DiffCard 的直角是被契约测试锁定的有意设计，不是遗漏**。G² 推广到此面 = 先改裁决与契约测试，再谈技术。且 DiffCard 独立形态服务于 dock 文件面板（跨扫描域），嵌入形态在本扫描域——施工切分时此面必须单独成项、两域对齐。

### 5.1 深挖二：展开面板（SmartExpandablePanel 家族 + ComposePlusMenu 一带）

**圆角定义全链路（SEP 本体）**：
`tokens-radius.css --radius-menu-outer(18) / --radius-menu-inner(12)` → `ui/SmartExpandablePanel/SmartExpandablePanel.module.css:12 .panel { border-radius: var(--radius-menu-outer, 18px); padding: 6px; border: 1px solid var(--border-panel); box-shadow: var(--shadow-popover) }`、`:175 .item { var(--radius-menu-inner, 12px) }`、`:349 .cascadeSubmenu { 同 .panel 规格，position: fixed }`、`:455 .cascadeSubmenu .item { 同 inner }`。同心链：**18 − 6(padding) = 12**，文件头自称 “Concentric Radii”——这是全仓最规整的一条链。组件层：`SmartExpandablePanel.tsx` 用 `useClosingValue`（S4）保活级联子菜单播退场，级联定位由 TSX 内联 style 注入（position: fixed + max-content 宽）。

**同规格的四套实现（本深挖核心发现）**——「展开面板」在聊天输入区实际有四个独立 CSS 实现，名义值全同（18/12、padding 6）：

| 实现 | 文件 | 外框 | 条目 | 差异点 |
|---|---|---|---|---|
| SEP 本体 | ui/SmartExpandablePanel/SmartExpandablePanel.module.css | .panel / .cascadeSubmenu | .item | 基准实现 |
| ＋菜单 | chat-composer/ComposePlusMenu.module.css | .plusMenu | .item | 文件头自称 “SEP Design System Specification”；.icon 用 control 8（其文件头注释却写 4px，注释与代码已漂移）；SEP 作为其子菜单宿主被内嵌渲染 |
| 权限菜单 | chat-composer/PermissionModeMenu.module.css | .permMenu | .permMenuItem | 另有 .permPill 14px 字面量触发胶囊 |
| 项目选择菜单 | chat-card/ProjectPickerMenu.module.css | .pickerPanel（经 --sep-radius-outer）+ **自有 .cascadeSubmenu（:102，第二份级联实现）** | .item（经 --sep-item-radius） | 唯一走 tokens-components sep 变量的一家；级联与 SEP 的 .cascadeSubmenu 同名同值双定义 |

**展开/退场动效与圆角的相互影响**：
- 入场/退场走全局 keyframes `crish-popover-enter/exit`（design-system.css 定义，transform: scale 0.96~0.97 + translateY + opacity；S4 后退场由宿主保活驱动）。transform 为**整体等比缩放**：若 G² 层是元素自身的背景层/clip，随元素一同缩放，轮廓形状不变（等效 R 随 scale 在 ±4% 内浮动，视觉无感）——此族动效与 G² 兼容性好。注意 transform-origin 随 data-side 在 top left/right 间切换，独立子层方案须同 origin 同步（同元素背景层天然同步）。
- 级联子菜单宽度为 max-content（内容定宽）、打开后还可能因异步内容改宽：**JS 测尺寸生成路径的路线在此族最脆弱**（每次宽度变化都要重生成）；`background-size: 100% 100%` 的可拉伸 SVG 背景层对此最宽容，应为此族首选挂接方式。
- .panel/.cascadeSubmenu 均带 1px 边框 + box-shadow：§0-4 两条全局风险在此族全中——clip 路线丢阴影、背景层路线边框错位，四套实现要同批同法处理。

**改造点与风险**：
1. 先收敛、后 G²：四实现先统一到一个挂接点（共享 G² 类/机制按名义 R 参数化），再逐面验；只改 SEP 本体一家，其余三家立刻与其分家。
2. ProjectPickerMenu 的 .cascadeSubmenu 与 SEP 的同名同值——收敛时二选一，勿留双份。
3. SEP 的滚动区在内层（.listContainer / .cascadeListBody，overflow-y auto），外框 overflow 可见——内层滚动条会贴近角部，G² 轮廓内缩量大于旧弧时，滚动条/首尾条目与角的间隙关系需复验（现状已有 6px padding 保护，预计低风险，但须在验收清单里列明）。

## 9. 最难的三处

1. **ComposerFusedTrigger 分角拼接胶囊**（chat-composer/ComposerFusedTrigger.module.css，9 处 14px 字面量声明）。难因：它不是一个元素的圆角，而是模型钮/思考钮等**多个独立按钮按四种状态组合拼成一个胶囊**，每段只持有整胶囊轮廓的一部分角（`14px 0 0 14px` / `0 14px 14px 0` / 全 14 / 全 0 共四种组合 × 多个选择器）。普通圆弧下「每段画自己的角」恰好拼得上；G² 轮廓是整角曲线，「每段各画一条完整 G² 角」会在拼接缝处曲率过量，必须按**整胶囊轮廓的切片**逐段生成——生成机制要支持「轮廓分段」这一特殊模式，全仓唯一。注：用户 2026-11-06 最新口径对此面是「大圆角、不是胶囊形式看着还行」，可排最低优先级或维持登记，但结构难度不变。FilesCard 的 filesOpenCapsule 分角对（:686/709）是同型小规模版，可作试切点。
2. **DiffCard 直角契约**（components/diff/DiffCard.module.css + DiffCardFileList.test.tsx）。难因不在技术在裁决：直角被测试钉死为有意设计（10 处显式 0 + 契约断言禁止 var(--radius 混入），嵌入工具详情时再强制归零。此面 G² 化必须先有用户裁决推翻/修订契约，且它同时服务 dock 独立面板（跨扫描域），两边须同批。
3. **消息内图片面（三轨 + 原生 img）**（§8-1 的四点）。难因叠加：值先分歧（8 vs 16 未定）；img 是原生替换元素，border-radius 直接裁切，改 G² 只能 clip-path，而图片显示尺寸随列宽/原图比变化（工具图 max 420×280、md 图宽随列），路径须随实测尺寸生成或改结构（外层定形容器裁切）。且此面与 A 批刚动过的行内代码台阶相邻，台阶类改造宜同批对齐避免两轮动同一渲染层。

次难点（未进前三但施工须知）：composerCard（边框 + 阴影 + border-radius 过渡三耦合，全产品锚点面，须与设计稿 R20 落地同批）；pinPickerPopover 双态半径（10→20 跳变，G² 双轮廓切换）。
