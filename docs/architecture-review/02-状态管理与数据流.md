# 诊断方向 02：状态管理与数据流

## 检查目标
评估前端状态管理架构、前后端状态同步机制、数据流向的合理性，以及状态一致性问题。

## 检查清单

### 2.1 前端状态架构
- [ ] Zustand store 的划分粒度——是否多个关注点混入同一 store（如 layoutStore 管理 workspace + session + settings）
- [ ] store 之间的同步机制是否可控（bootstrapStores 中的双向同步是否存在循环更新风险）
- [ ] Zustand selector 的精度——是否存在因 selector 过粗导致的不必要重渲染
- [ ] immer 中间件的使用是否过度——简单赋值操作是否也走了 proxy 开销
- [ ] store 的 persist 策略——哪些状态应该持久化、哪些可以重建

### 2.2 前后端状态同步
- [ ] UI session state 与 daemon event store 之间的数据一致性如何保证
- [ ] 会话元数据（session list）在 UI 和 daemon 两端是否都有独立副本
- [ ] 同步冲突时谁优先（UI 变更覆盖 daemon，还是 daemon 覆盖 UI）
- [ ] 离线 / 重连后的状态恢复逻辑是否健壮

### 2.3 事件驱动数据流
- [ ] EventBus 是全局单例还是可隔离的实例
- [ ] 事件订阅是否具有完善的取消订阅机制（防止内存泄漏）
- [ ] 事件冒泡 / 过滤 / 转换是否有统一机制
- [ ] 跨标签页通信（CrossTabCoordinator）的事件冲突处理

### 2.4 数据一致性保障
- [ ] 前端 optimistic update 失败后的回滚机制
- [ ] 操作序列号 / 版本号机制避免陈旧覆盖
- [ ] 写冲突检测（尤其在 tool approval 等并发场景）
- [ ] 数据校验是在边界层统一做还是分散在各个消费者中

## 检查方法
- 追踪一次用户操作（如发送聊天消息）的完整数据流，标记每个中间状态
- 列出所有 store 之间的 import 依赖，绘制依赖图
- 评估 session metadata 在 UI/daemon/event store 三个副本间的一致性保障
- 检查事件订阅方是否都有对应的取消订阅调用
