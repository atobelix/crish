# 诊断方向 07：可观测性与运维

## 检查目标
评估系统的日志体系、监控指标、健康检查、可调试性和生产运维能力。

## 检查清单

### 7.1 日志体系
- [ ] 是否有结构化日志（JSON format、log levels）而非纯 console.log
- [ ] 各组件的日志输出是否统一格式、统一路由
- [ ] 日志级别（debug/info/warn/error/fatal）是否被正确使用
- [ ] 是否有敏感信息过滤机制（密钥、token 在日志中脱敏）
- [ ] daemon 写 stdout 的日志是否与 WebSocket 数据流混合
- [ ] 前端日志是否有循环缓冲区用于事后排查

### 7.2 指标监控
- [ ] 关键性能指标是否暴露（请求延迟、token 消耗、错误率、并发数）
- [ ] 是否有 Prometheus 端点或 OpenTelemetry 导出
- [ ] 运行时指标（RuntimeMetricsCollector）的 snapshot 是否周期性 flush
- [ ] 是否有自定义业务指标（tool 调用频率、会话持续时间、provider 错误率）
- [ ] 指标数据是否有可视化仪表盘

### 7.3 健康检查
- [ ] daemon 是否有 HTTP/WebSocket 健康检查端点
- [ ] 健康检查是否正确反映了各组件的健康状态（provider 连通性、event store 可用性）
- [ ] 前端是否有 daemon 不可用时的降级 UI 提示
- [ ] Tauri shell 是否有对 daemon sidecar 的健康轮询

### 7.4 追踪与调试
- [ ] 请求链路是否有唯一 Trace ID 贯穿整个系统
- [ ] 分布式追踪（WebSocket 消息 → orchestrator → runtime → provider 调用）是否可追溯
- [ ] 错误报告中是否包含足够的上下文（sessionId、runId、事件序列号）
- [ ] 事件存储（JSONL）是否可作为审计日志和调试依据

### 7.5 部署与运维
- [ ] daemon 是否有进程管理（systemd、PM2 或内置进程守护）
- [ ] 是否有 Dockerfile / docker-compose 用于容器化部署
- [ ] 日志文件是否有轮转和大小限制
- [ ] 配置变更是否支持热重载（无需重启进程）
- [ ] 是否有数据备份机制（事件存储、配置文件）

## 检查方法
- 审查所有 console.log/warn/error/info 的调用点，统计使用模式
- 检查 RuntimeMetricsCollector 的数据流向和导出路径
- 审查 daemon 启动后的端⼝暴露情况
- 检查是否有 `.env.example`、配置模板等运维文档
- 搜索 Trace ID / Correlation ID 的生成和传递
