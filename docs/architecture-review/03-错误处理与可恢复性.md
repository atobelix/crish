# 诊断方向 03：错误处理与可恢复性

## 检查目标
评估系统各层的错误处理策略、异常传播路径、故障恢复机制和容错设计。

## 检查清单

### 3.1 空 catch 块审计
- [ ] 全局搜索 `catch { }`、`catch { /* */ }`、`catch () { }` 模式
- [ ] 所有 `.catch(() => {})` Promise 链末端
- [ ] 空 catch 是否有业务合理性的注释说明
- [ ] 是否存在本应记录错误日志却 silent 吞掉的场景

### 3.2 错误传播机制
- [ ] WebSocket 连接错误的传播路径——从 daemon 到 UI 是否清晰
- [ ] 运行时错误（LLM 调用失败、tool 执行异常）是否影响会话整体可用性
- [ ] 组件渲染错误是否有 Error Boundary 兜底且可恢复
- [ ] 是否有一致的错误类型层次结构（如 `AppError extends Error`）而非到处 throw 原始对象

### 3.3 故障恢复
- [ ] WebSocket 断线重连后的 session 状态恢复
- [ ] daemon 崩溃后 sidecar 自动重启及状态重建
- [ ] 前端 localStorage 损坏后的降级行为
- [ ] 事件存储（JSONL）损坏 / 缺失的处理
- [ ] 会话 checkpoint/rollback 机制的可靠性

### 3.4 超时处理
- [ ] LLM 请求超时后的重试策略（退避、最大次数）
- [ ] WebSocket 心跳超时检测与断线判定
- [ ] 工具执行超时后的取消链路
- [ ] 用户操作超时（如 tool approval 等待）的反馈

### 3.5 全局异常兜底
- [ ] `window.onerror` / `window.onunhandledrejection` 处理器
- [ ] daemon 进程的 `process.on('uncaughtException')` / `process.on('unhandledRejection')`
- [ ] Tauri Rust 端的 panic 恢复
- [ ] 以上兜底处理是否仅记录日志而不影响进程存活

## 检查方法
- grep 搜索 `catch\s*{`、`catch\s*\(\)\s*{`、`\.catch\(\s*\(\s*\)\s*=>` 等模式
- 模拟 WebSocket 断线、daemon 重启、localStorage 清空等场景测试恢复逻辑
- 审查 Error Boundary 的层级覆盖——哪些组件没有自己的 Error Boundary
- 审查 JSONL 事件存储的 read/write/rollback 代码路径
