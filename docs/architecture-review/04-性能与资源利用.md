# 诊断方向 04：性能与资源利用

## 检查目标
评估系统在各个维度的性能表现，包括运行时性能、内存管理、I/O 效率、渲染性能、资源浪费等。

## 检查清单

### 4.1 运行时性能
- [ ] 数据查找时间复杂度——session 查找、tool 查找等是否使用了 O(1) 数据结构
- [ ] 数组操作是否在热路径上重复创建中间数组（filter/map 链式调用）
- [ ] 对象 clone/deep clone 是否在每次请求中都做（如 provider-gateway 的 route 克隆）
- [ ] 上下文压缩（context-compression）的全量序列化是否过于频繁
- [ ] Token 估算的缓存命中率

### 4.2 渲染性能
- [ ] Zustand store 的 selector 粒度是否导致组件频繁重渲染
- [ ] 虚拟列表（虚拟滚动）是否在长列表场景中正确使用
- [ ] React.lazy 的拆分粒度——是整页拆分还是每个 icon 单独拆
- [ ] CSS 模块数量与 bundle 大小
- [ ] 图片 / 字体资源的懒加载与预加载策略

### 4.3 内存管理
- [ ] 是否有无界增长的数据结构（Set、Map、数组）在运行时持续增长
- [ ] 事件监听器的注册与取消是否配对
- [ ] Web Worker 的生命周期管理（创建、复用、销毁）
- [ ] pending request map 在断连时是否彻底清理
- [ ] WeakMap/WeakRef 的使用是否足够覆盖缓存场景

### 4.4 I/O 效率
- [ ] localStorage 操作是否在同步上下文中阻塞主线程
- [ ] JSONL 事件存储的写入是否有批量/缓冲机制
- [ ] 文件读取是否使用流式接口处理大文件
- [ ] 网络请求（LLM API）的并发控制与连接复用

### 4.5 缓存策略
- [ ] LLM API 响应的缓存（相同 prompt 是否可以 cache hit）
- [ ] 上下文压缩结果的跨会话缓存
- [ ] 前端 API 调用是否有 SWR/stale-while-revalidate 策略
- [ ] 数据获取是否有去重（deduplication）机制防止并行重复请求

## 检查方法
- 使用 Chrome DevTools Performance 录制典型操作（发送消息、切换会话、打开大型会话）
- 在 daemon 中插入性能埋点统计 hot path 耗时
- 使用 `--inspect` 堆快照分析内存泄漏
- 分析 bundle visualizer 输出检查重复代码与大型依赖
- 统计各数据查找操作的数据结构类型与调用频率
