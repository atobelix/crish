# 诊断方向 01：架构解耦与模块边界

## 检查目标
评估系统各模块之间的耦合程度、依赖关系的合理性、接口抽象程度，以及模块边界的清晰度。

## 检查清单

### 1.1 包间依赖关系
- [ ] agent-daemon 对 agent-runtime / agent-orchestrator 的内部 API 依赖是否过多
- [ ] 包之间的 `file:` / `workspace:` 引用是否形成了正确的单向依赖方向
- [ ] 是否存在循环依赖（包级别/模块级别/文件级别）
- [ ] shared-types 是否承担了过多共享类型导致变更传播面过宽
- [ ] 各 package 的 `exports` 字段是否合理限制了外部可见性
- [ ] agent-daemon `index.ts` 是否暴露了过多实现细节（应仅暴露 `startDaemon` 等公共 API）
- [ ] 包间依赖统计：每个包被多少其他包 import、每个包 import 了多少其他包

### 1.2 接口抽象程度
- [ ] 关键服务（DaemonClient、EventBus、ProviderGateway、AgentRuntime、SessionStore）是否有正式接口定义
- [ ] 是否存在依赖具象类而非接口的模式——搜索 `implements` 关键字的频率
- [ ] 测试中 mock/stub 的难度——是否因为缺少接口导致测试困难
- [ ] plugin-sdk 是否有完整的 SPI 定义，还是仅有类型骨架（当前仅有 `definePlugin()` + 5 个可选 hook）
- [ ] SPI 注册机制、生命周期管理、版本兼容性协议是否存在

### 1.3 模块内聚性
- [ ] 是否有 God Class / God Module 承载了过多职责：
  - `App.tsx` (~946 行) —— 14 个 useEffect、键盘处理、初始化逻辑、布局渲染
  - `server.ts` (~930 行) —— 25+ 方法、20+ 依赖
  - `layoutStore.ts` (~967 行) —— workspace + session + settings + diffs 混在一起
  - `sessionActions.ts` (~1065 行) —— 单一函数返回 30+ 方法
  - `clientApi.ts` (~770 行) —— settings + providers + cron + MCP + telemetry 混在一起
- [ ] handler 模块划分是否符合单一职责——`handlers/` 下 14 个 handler 的职责边界
- [ ] 是否有个别文件过于庞大：
  - `types.ts` (1756 行) —— 100+ 类型定义 + 协议消息 + 配置 + 工具函数
  - `daemonChatBridge.ts` (959 行) —— 事件解析 + 审批流 + diff 处理
  - `sessionPersistence.ts` (931 行)
  - `provider-openai-compatible.ts` (2666 行)

### 1.4 前后端边界
- [ ] 前端 Zustand store 是否直接操作了后端应有的逻辑
- [ ] 前端与服务端之间是否存在状态双写（既存 localStorage 又存 daemon event store）
- [ ] WebSocket 消息协议是否已形成正式契约且版本化管理
- [ ] 是否有前后端逻辑重复（如权限在前端和后端各做一遍但规则不统一）
- [ ] 会话 metadata 在 UI/daemon/event store 三个副本间的一致性保障

### 1.5 进程边界
- [ ] Tauri shell 与 daemon 之间的进程通信职责是否清晰
- [ ] sidecar 进程的生命周期管理是否定义在正确的边界内
- [ ] Rust HTTP provider 与 Node.js daemon 的边界是否干净
- [ ] `process.platform` 被 Vite 构建硬编码 (`'win32'`) 的风险

### 1.6 事件与消息架构
- [ ] 消息类型的联合类型规模——`DaemonInboundMessage` + `DaemonOutboundMessage` 合计 ~120+ 变体
- [ ] 协议类型与内部类型是否应分离（types.ts 合并了协议 + 内部 + 生命周期类型）
- [ ] 前端 EventBus 的 `EventHandler` 使用 `(payload: any, source?: string)` 完全无类型约束
- [ ] 事件类型映射表（EventMap）是否存在

## 检查方法
- 绘制完整依赖图，标记所有循环依赖和跨层引用
- 对每个包分析其 public exports 与 internal imports 的比例
- 核心模块冲击分析：如果拆分 server.ts，需要修改多少调用方
- `rg "from '.*'" packages/ --include="*.ts" | sort | uniq -c` 统计导入模式
