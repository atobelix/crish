# 诊断方向 01：架构解耦与模块边界

## 检查目标
评估系统各模块之间的耦合程度、依赖关系的合理性、接口抽象程度，以及模块边界的清晰度。

## 检查清单

### 1.1 包间依赖关系
- [ ] agent-daemon 对 agent-runtime / agent-orchestrator 的内部 API 是否存在过多直接依赖
- [ ] 包之间的 `file:` 引用是否形成了正确的单向依赖方向
- [ ] 是否存在循环依赖（包级别 / 模块级别 / 文件级别）
- [ ] shared-types 是否承担了过多共享类型导致变更传播面过宽
- [ ] 各 package 的 exports 字段是否合理限制了外部可见性

### 1.2 接口抽象程度
- [ ] 关键服务（DaemonClient、EventBus、ProviderGateway、SessionStore）是否有正式接口定义
- [ ] 是否存在依赖具象类而非接口的模式
- [ ] 测试中 mock/stub 的难度——是否因为缺少接口导致测试困难
- [ ] 插件 SDK 是否有完整的 SPI 定义，还是仅有类型骨架

### 1.3 模块内聚性
- [ ] 是否有 God Class / God Module 承载了过多职责（如 App.tsx、server.ts、layoutStore.ts）
- [ ] handler 模块的划分是否符合单一职责原则
- [ ] 是否有个别文件过于庞大（如 agent-daemon/types.ts ~1756 行）
- [ ] api/ 层的各个文件是否职责清晰互不重叠

### 1.4 前后端边界
- [ ] 前端 Zustand store 是否直接操作了后端应有的逻辑
- [ ] 前端与服务端之间是否存在状态双写（既存 localStorage 又存 daemon event store）
- [ ] WebSocket 消息协议是否已经形成正式契约且版本化管理
- [ ] 是否有前后端逻辑重复（如权限判断在前端和后端各做一遍但规则不统一）

### 1.5 进程边界
- [ ] Tauri shell 与 daemon 之间的进程通信职责是否清晰
- [ ] sidecar 进程的生命周期管理是否定义在正确的边界内
- [ ] Rust HTTP provider 与 Node.js daemon 的边界是否干净

## 检查方法
- 绘制完整依赖图，标记所有循环依赖
- 对每个包分析其 public exports 与 internal imports 的比例
- 对核心模块（server、orchestrator、runtime）进行"如果拆分这个模块，需要修改多少调用方"的冲击分析
- 检查 import 语句中是否存在跨层引用（如 UI 层直接 import daemon 内部模块）
