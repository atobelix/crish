# 诊断方向 10：依赖管理与升级策略

## 检查目标
评估第三方依赖的健康状况、版本管理策略、升级路径及依赖中的潜在风险。

## 检查清单

### 10.1 依赖健康状况
- [ ] 所有依赖的当前版本与 latest 版本的差距
- [ ] 是否存在不再维护或社区活跃度低的依赖
- [ ] 直接依赖的数量是否可控——是否需要合并/替代某些依赖
- [ ] Dev dependencies 是否误放在 dependencies 中（如 @types/*）

### 10.2 大型依赖审查
- [ ] highlight.js 是否可以替换为更轻量的语法高亮方案（Shiki、Prism 子集）
- [ ] 四个字体包（inter、jetbrains-mono、ibm-plex-sans、ibm-plex-mono）是否全部必要
- [ ] lucide-react 的导入方式是否支持 tree-shaking
- [ ] immer 的开销是否值得——是否可以部分替换为原生 immutable 操作

### 10.3 版本策略
- [ ] 是否使用锁文件（package-lock.json）确保可复现构建
- [ ] 依赖版本范围是否过于宽松（^x.y.z 可能引入 breaking change）
- [ ] Cargo.lock 是否正确管理 Rust 依赖版本
- [ ] 是否有过时的依赖版本被锁定无法升级

### 10.4 安全漏洞
- [ ] 是否有配置自动化的依赖漏洞扫描（Dependabot、Renovate、Snyk）
- [ ] 已知漏洞的依赖是否已经修复或存在缓解措施
- [ ] 间接依赖中是否存在已知的高危漏洞
- [ ] ws 库、Tauri 依赖、zod 等关键依赖的版本是否为最新稳定版

### 10.5 升级路径
- [ ] TypeScript 7 升级是否已有计划和兼容性测试
- [ ] ESLint 10 升级是否已评估 breaking changes
- [ ] React 19 新特性是否已充分利用（如 use()、Actions）
- [ ] Vite 7 升级后是否已适配所有 breaking changes

### 10.6 内部依赖管理
- [ ] 内部 package 的版本号是否保持一致
- [ ] `file:` 引用的包在 publish 后是否需要改为 `workspace:` 或 `npm:` 协议
- [ ] 内部包的代码是否在多个消费者间合理共享
- [ ] 共享类型变更时是否影响到了不相关的消费者

## 检查方法
- 运行 `npm outdated` / `npm audit` 在根目录和各 package
- 审查每个依赖在源码中的使用点统计 import 频率
- 计算依赖的已安装大小（`du -sh node_modules/xxx`）
- 审查 package.json 的 dependencies vs devDependencies 分类
- 检查 Renovate / Dependabot 配置是否存在
