# 诊断方向 08：类型系统与代码质量

## 检查目标
评估 TypeScript 类型系统的使用深度、代码规范一致性、潜在类型安全隐患及整体代码可维护性。

## 检查清单

### 8.1 类型安全
- [ ] `as any` / `as unknown as T` 类型断言的使用数量与合理性
- [ ] 是否存在可以但不使用类型参数的泛型函数（`<T = unknown>` 不传 T）
- [ ] 函数返回类型是否有显式注解（而非依赖推断）
- [ ] 是否有安全导出 internal 类型（类型泄漏到公共 API）
- [ ] strict mode 的额外选项是否开启（noUncheckedIndexedAccess、exactOptionalPropertyTypes）

### 8.2 类型组织
- [ ] 超大类型文件（agent-daemon/types.ts 1756 行）是否应拆分
- [ ] 跨包共享的类型是否集中在 shared-types 还是散布在各包
- [ ] 消息类型的联合类型是否过于庞大（~50+ 变体）需要分层组织
- [ ] 平台相关类型与核心类型的分离

### 8.3 代码可维护性
- [ ] 函数/模块的圈复杂度——是否存在过长的 switch/if-else 链
- [ ] 魔术数字/字符串是否提取为具名常量
- [ ] 硬编码的本地语言（中文）是否影响国际化
- [ ] 死代码 / deprecated 代码是否已清理（如 clientApi 中的 `isDemoMode()` 分支）
- [ ] 控制台日志（console.log）是否应保留在生产代码中

### 8.4 命名与风格一致
- [ ] 文件名风格是否统一（kebab-case vs PascalCase）
- [ ] 导入路径格式是否一致（`.js` vs 无扩展名）
- [ ] 函数命名是否遵循统一约定（`get*` vs `fetch*` vs `query*` vs `load*`）
- [ ] 组件 Props 类型的命名规范（`XxxProps` vs `IXxxProps` vs inline）

### 8.5 代码异味
- [ ] 参数过多函数（超过 4 个参数是否需要 Options 对象）
- [ ] 使用布尔参数控制不同路径（flag 参数是否需要拆分为独立函数）
- [ ] 长链条 `.a.b.c.d` 是否存在潜在的 null/undefined 风险
- [ ] 复杂的条件表达式是否提取为具名函数

## 检查方法
- 使用 `rg " as any" | wc -l` 统计 as any 数量
- 审查 tsconfig.json 中 strict 系列选项的配置
- 使用 TypeScript compiler API 分析类型复杂度
- 手动审查超大文件（types.ts、server.ts）的类型定义质量
- 搜索 `console\.log` 和 `@deprecated` 标签
