# 诊断方向 05：测试覆盖与质量保障

## 检查目标
评估测试架构的完整性、测试策略的有效性、测试质量与测试基础设施的健全度。

## 检查清单

### 5.1 测试覆盖边界
- [ ] 核心模块覆盖审计（逐文件）：
  - `runtime.ts` → `runtime.test.ts` ✓（已覆盖）
  - `agent-session-loop.ts` → 无测试 ✗（1300+ 行核心逻辑）
  - `server.ts` → `server.test.ts` ✓（3629 行详尽的集成测试）
  - `orchestrator.ts` → `orchestrator.test.ts` ✓
  - `server-handlers.ts` → 无测试 ✗
  - `provider-gateway.ts` → 无测试 ✗
  - `daemon-provider-gateway.ts` → 无测试 ✗
  - `runtime-components/*.ts` → 无测试 ✗
- [ ] CI 配置中 vitest include 是否覆盖了所有测试类型
- [ ] `apps/crish-desktop/tests/` 下的 integration/recovery/fuzz 是否被默认运行

### 5.2 测试质量
- [ ] 是否存在只测 happy path 不测 error path 的测试
- [ ] 是否依赖实现细节的脆弱测试（断言内部状态而非公共行为）
- [ ] mock 模式：mock 接口还是 mock 具体实现（`createScriptedProvider()` 基于接口是良好实践）
- [ ] `vi.useFakeTimers` 的 cleanup 是否正确——故障时是否泄漏计时器状态
- [ ] 测试间是否共享可变状态（module-level caches、WeakMap、全局单例）
- [ ] 没有 `@ts-expect-error` 非必要绕过类型检查

### 5.3 测试基础设施
- [ ] CI 是否运行 unit + integration + fuzz + recovery 测试
- [ ] 覆盖度阈值是否设置（目前未设置——0% 也能通过 CI）
- [ ] CI 中是否包含 stress/startup/benchmark 回退检测
- [ ] 端到端测试：Playwright visual test 仅 1 个 spec，缺乏完整用户流程
- [ ] 是否有 mock 工厂/测试助手共享（`createMockProvider()`、`createMockDaemon()` 等）
- [ ] 测试文件命名与源文件结构是否对应

### 5.4 特殊测试类型
- [ ] Fuzz 测试：目前仅覆盖 markdown parser——工具参数、WebSocket 消息、config 等输入面缺少 fuzz
- [ ] 压力测试：daemon 高并发 WebSocket 消息场景
- [ ] 恢复测试：daemon crash 后恢复 run 状态、WebSocket 断连后恢复、JSONL 损坏场景
- [ ] 竞态测试：并发 store 修改、并行 WebSocket 消息、并发 file I/O
- [ ] 安全测试：XSS 注入、路径遍历、API key 泄露

### 5.5 特殊关注
- [ ] agent-session-loop.ts 无测试是最大风险——需确认是否在 runtime.test.ts 中隐式覆盖
- [ ] agent-orchestrator/orchestrator.ts (1725 行) 虽然有 test，但覆盖率是否足够
- [ ] 集成测试（server.test.ts 3629 行）是真实 WebSocket 连接还是 mock

## 检查方法
- `npx vitest run --coverage` 获取覆盖率报告，人工审查未覆盖的关键代码区域
- 各 package 列出源代码文件 vs 测试文件对应关系表
- 审查 mock 模式——是否依赖无接口的具体类
- 检查 `vitest.config.ts` 及其它 vitest 配置的 include patterns
- 搜索 `@ts-expect-error` 在测试中的使用，评估其必要性
