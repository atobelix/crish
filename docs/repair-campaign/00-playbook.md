# 多 Agent 协同修复战役 · 玩法手册（Playbook）

> 效力：任何「整改 / 修复 / 重构 / 技术选型」类任务域的多 Agent 调度框架。
> 性质：**仅逻辑执行顺序**——不涉及时间安排、人员分配、优先级排序；清单内问题同权。
> 约束：每轮最多部署 12 个 Agent；数量按该轮实际需求灵活决定，无需强制占满。
> 闭环：每轮输出 = 下一轮输入；迭代直至目标态达成（销号报告为轮次出口）。

---

## 0. 一句话

**问题识别 → 任务分解 → Agent 分配 → 并行修复 → 结果汇总与验证**，全链路以逻辑依赖排序；选型由多模型独立出方案、评审收敛、主控敲定；方案文档先于执行，执行忠于方案。

---

## 1. 完整逻辑链路（一轮的骨架）

| # | 环节 | 动作 | 产出 |
|---|---|---|---|
| 1 | 问题识别 | 多 Agent 按维度独立分析代码 + 档案 + 业界参考 | N 份独立方案文档 |
| 2 | 任务分解 | 主控整合独立方案 → 维度划分 + 规则文档 | 总文档 + 方案敲定文档 |
| 3 | Agent 分配 | 按维度派发详设 Agent（维度数量 = 详设 Agent 数） | 每维度一份详细文档 |
| 4 | 并行修复 | 按详细文档派执行 Agent，批次独立提交 | 代码 + 测试 + 提交 |
| 5 | 结果汇总与验证 | 主控逐批实读验证 + 全量门禁 + 销号报告 | 轮次销号报告 v2 |

每环节间有评审闸门（见 §2），防止错误放大。

---

## 2. 选型与方案阶段（本框架的核心差异点）

### 2.1 阶段 A：多模型独立分析（问题识别）

- 派 **N 个 general Agent**（N 通常 4-8，按问题域维度划分；每个 Agent 持一个维度视角）。
- 每个 Agent 任务书必含：
  - 必读档案清单（精确路径）；
  - 实读代码范围（文件域）；
  - 维度侧重（3-5 个核心问题点）；
  - **业界参考方向 + 选型对比要求**（对比候选方案间的详细差别，禁止含糊带过）；
  - 产出文件路径与章节结构；
  - 验收断言。
- 每个 Agent 输出**独立总方案**：问题清单（实读验证）+ 选型对比表 + 改进方案分步 + 维度划分建议 + 验收断言。
- **选型纪律**：
  - 每个选型点必须给出 ≥2 个候选 + 差别分析 + 推荐理由；
  - 复杂度控制：候选若比常规做法复杂 3 倍起步 → 放弃；1-2 倍 → 可考虑；
  - 最终效果优先（不计调试时间、不计成本）；
  - 参考软件（开源/商业）允许引用——**仅限方案文档生成前**。

### 2.2 阶段 B：方案评审（2-3 Agent）

- 评审前面的 N 份方案：选型差别是否讲清、冲突点、遗漏面、不可验证项。
- 每个评审 Agent 输出：问题清单 + **自己认为的最佳方案**（综合裁决）。

### 2.3 阶段 C：主控整合（主 Agent 本人，不可外包）

- 读全部独立方案 + 评审 → 写两份文档：
  - **总文档**：维度划分（依据 = 前面各 Agent 的不同维度看法）+ 每维度设计要点 + 阶段间规则；
  - **方案敲定文档**：每个选型点的最终裁决（含被否候选与理由）。

### 2.4 阶段 D：总方案评审（2 Agent）

- 评审对象 = 总文档 + 敲定文档。
- 评审重点：**任务分配合理性、维度划分完整性、方案间逻辑关系（依赖/冲突/共享文件）、需调整部分审计**。
- 评审输出问题清单；主控逐条定夺（吸收/驳回/修改），驳回需给理由。

### 2.5 阶段 E：修订

- 主控定夺后，派 Agent（或主控自改）修订总文档/敲定文档至闭环。

### 2.6 阶段 F：维度详设（维度数量 Agent）

- 每个 Agent **只写一个维度**的详细文档：
  - 依据 = 敲定文档（强制）+ 参考软件/业界方案（可引用）+ 前面各 Agent 的方案（供取舍）；
  - 产出 = 该维度的任务单元、文件域、分步、验收断言、风险与回退；
  - 与其他维度的共享文件/依赖边必须显式登记（供阶段 G 审计）。

### 2.7 阶段 G：维度评审（3 Agent）

- 评审全部维度文档：维度间逻辑关系、共享文件冲突、验收可验证性、目标缩水。
- 输出问题清单 → 主控定夺 → 派 Agent 修订（阶段 H）。

### 2.8 阶段 I：执行

- 按详细文档派执行 Agent；批次独立提交（BATCH-<轮次>-<批> 命名）。
- 每批 = 代码 + 测试 + 提交 + 该域门禁验证；主控逐批实读复核。
- 最终 = 全量门禁 + 两段式销号报告（修复销号 + 登记/保留销号）。

## 3. 参考软件引用规则（阶段切换的语义分界）

| 阶段 | 引用规则 |
|---|---|
| A-F（方案生成前/中） | 允许引用参考软件/开源实现，用于选型对比与差别分析 |
| F 详设文档起、I 执行 | **禁止再提参考软件**——正式方案 = 被内化、融合升级后的最佳业界解决方案，且为适合本软件（Crish/Conex）的自研实现细节 |
| 执行代码 | 代码即方案落地，注释/文档不出现「参考 XX 软件」措辞 |

## 4. 调度纪律（对所有轮次强制）

1. **问题同权**：用户未要求排序时，清单内问题同等重要；排序仅可按数据/类型/依赖。
2. **效果锁**：用户给定的效果与范围不得自行降级；冲突标出并请示，Agent 无权改目标。
3. **反退避**：禁止以时间/重要性/成熟度/生态流行度/「做不到」否决路径；不确定 → 设计验证。
4. **共享文件串行**：同文件多 Agent 触碰必须显式登记（F-登记表）并串行；引擎写路径互斥兜底。
5. **勤 git**：工作区存在并行域（其他 Agent/线程），每批/每阶段产物立即精确 `git add` 提交；禁止 `git add -A`。
6. **门禁零容忍**：红必修复；禁止 `--no-verify`；禁止删测试（测试资产铁律，删前 `git ls-files` 确认）。
7. **子 Agent 空返回**：返回空不代表没干活——先查 git status/文件存在性再判断；仍空则主控直接做或换派。
8. **Agent 类型**：一律 `general-purpose`（用户裁定）。

## 5. 提示词规范（主控派单时）

- **不瘦身**：任务书完整写入背景、档案、文件域、产出、验收、注意事项。
- **实时化补充**：任务书除引用文档外，必须补充「文档未提及、需动态决策」的内容：
  - 行号漂移处理（以实读为准并注明）；
  - 档案与代码冲突的处理（以实读为准、冲突登记）；
  - 发现档案未登记的新问题 → 登记进产出，不阻塞主线；
  - 并行域 M 状态文件先读最新再改。
- **子 Agent 注意事项**随任务书下发：只读/可写范围、产出文件配额、编码（UTF-8 无 BOM 中文）、禁止改动面、反退避短块。

---

## 6. 验证与闭环

- 每阶段验收断言必须在任务书中写明（可测/可看/可复核）。
- 执行批次验证 = 该域门禁；轮次出口验证 = 全量门禁 + 销号报告。
- 销号报告两段式：① 修复销号（逐项对应批次）；② 登记/保留/移交销号（含挂账与条件触发项）。
- 发现回归 → 回到对应环节修复 → 重跑门禁（允许多轮迭代）。

## 7. 自检清单（主控每轮派单前）

- [ ] 轮内 Agent 数 ≤ 12？
- [ ] 维度划分是否有依据（前面各 Agent 的看法）？
- [ ] 每个任务书：档案/文件域/产出路径/验收断言/注意事项齐全？
- [ ] 共享文件是否登记并串行？
- [ ] 选型点是否都有 ≥2 候选 + 差别 + 推荐？
- [ ] 参考软件引用是否被限定在方案生成前？
- [ ] 本阶段产出是否已 git 提交？
