# KWS 语音引擎合并门禁（波 7b · 正式门禁）

- 立规时间：2026-11-05（《系统性解决方案》待裁决 ② 经用户授权执行，自本文落盘起生效）
- 适用对象：对方语音功能线（sherpa-onnx KWS 唤醒引擎，`com.crish.voice.speaker.KwsEngine` 及其 JS/TS 桥接面）**合并主线之前**，必须逐条自证并通过核查；任一条不过，整线不合并。
- 背景（事故实证，D 文档摘栈）：该引擎曾在对方 278MB 包中于原生模块线程抛出未捕获 `ClassCastException`（桥接 Map 在 JNA 回调重入时被误读为 Array）直接杀进程——JS 层 try/catch 拦不住 Java 层异常，语音功能故障带走了整个 App。本门禁的五条规范即针对这条崩溃链的五个断点。
- 现状注记：截至 2026-11-05 核查时点，KWS 引擎代码**不在主线树内**（全仓检索 `KwsEngine` / `voice.speaker` 零命中），五规范无从核查。本门禁只立规矩，不声称引擎已合规。

---

## 五条规范（逐条自证 + 逐条核查）

### 规范 1 · 桥接参数进入 Kotlin 后第一时间深拷贝为纯原生数据

- **要求**：桥接方法收到的 `ReadableNativeMap` / `ReadableNativeArray` 等桥接容器，必须在进入任何可重入段（JNA 回调、引擎回调、跨线程投递）之前，第一时间拷贝为纯 Kotlin/Java 原生数据结构（基本类型、String、普通集合）；不得把桥接容器原件带进 JNA 可重入段或异步回调里延迟读取。
- **自证要求**：给出每个桥接入口的参数拷贝位点（文件:行），并说明拷贝发生在任何回调注册/线程投递之前。
- **核查方法**：静态通读桥接层全部入口，逐个确认「先拷贝、后使用」；重点复查引擎回调闭包捕获的对象是否为拷贝后的原生数据。

### 规范 2 · 识别器创建不在 `mqt_v_native` 线程执行

- **要求**：KWS 识别器（含 sherpa-onnx 引擎对象）的创建/初始化必须由模块自有的 executor（单线程或专用线程池）承接；桥接方法本身只做投递 + 回 promise，绝不在 RN 原生模块线程（`mqt_v_native`）上同步执行引擎创建。
- **自证要求**：给出 executor 的定义位点与初始化调用链，说明桥接线程与引擎线程的边界；附一次初始化时线程名的日志证据（如有）。
- **核查方法**：静态核查初始化调用链无同步穿透；真机冷启时观察初始化期间主线程/桥接线程无长阻塞。

### 规范 3 · 初始化全程 `try/catch (Throwable)`，失败转 promise reject

- **要求**：初始化路径（及一切可能抛 Java 异常的桥接入口）全程被 `try/catch (Throwable)` 包裹——注意是 `Throwable` 而非仅 `Exception`（`Error` 类同样不得穿透）；捕获后一律转 promise reject 并带可诊断信息，绝不让未捕获异常越过桥接层杀进程。
- **自证要求**：给出每个桥接入口的兜底位点；说明 reject 的错误结构（code/message 口径）。
- **核查方法**：静态核查桥接层全部 `AsyncFunction` / `@ReactMethod` 入口无裸奔；构造一次必失败初始化（如模型缺失），真机确认 App 存活且 JS 侧收到 reject。

### 规范 4 · 初始化状态机串行化 + 失败冷却

- **要求**：初始化必须走串行化状态机（`idle → starting → ready / failed`）：并发或重复的 init 调用在 `starting` 期间不得重入创建；`failed` 后进入冷却期，冷却内拒绝立即重试，防止失败风暴反复冲击原生层。
- **自证要求**：给出状态机的定义与迁移位点、冷却时长口径；说明重复 init 的返回语义（共享同一 promise / 明确拒绝，二选一写清）。
- **核查方法**：静态核查状态字段的并发保护（锁/单线程 executor/原子量）；真机快速连点触发多次 init，确认只创建一次、无崩溃、无重复引擎实例。

### 规范 5 · JS 侧熔断：语音失败只降级语音功能

- **要求**：JS/TS 侧必须有熔断：init 失败达到阈值（或单次致命失败）后，语音入口降级为不可用态（明确提示 + 不再自动重试），**会话、输入、发送等主流程完全不受影响**；不得出现「语音初始化失败拖垮对话页」或「失败后每次交互都重试一遍原生初始化」的形态。
- **自证要求**：给出熔断状态的存放与判定逻辑、阈值/退避口径、降级态的用户可见形态（截图或组件位点）。
- **核查方法**：静态核查语音入口的失败分支终点是降级而非抛出/重试环；真机在引擎必失败条件下走一遍完整对话流程，确认主流程可用且语音呈降级态。

## 合并流程

1. 对方工作线提交**自证清单**：逐条对应上表，给出代码位点与证据（测试/日志/截图），缺一不可。
2. 我方按「核查方法」逐条核查（含真机场景：冷启、重复 init、必失败 init、熔断后主流程走查）。
3. 五条全过 → 准予合并；任一条不过 → 整线退回，修复后重新自证。
4. 合并后首个装机包必须补抓一份 dropbox/logcat，确认无 KWS 签名崩溃，归档备查。

## 与既有规范的关系

- 本门禁只管 KWS 线的原生边界，不替代 worklet 安全守卫、TextPath 枚举守卫等既有静态门。
- 主线既有原生模块 `crish-asr`（离线 ASR，已验证路径）不在本门禁适用范围内，其已验证行为不因本门禁重开。
