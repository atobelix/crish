## 一、逐项对账

### 1. inset 变化落点纠正 —— ✅ 已做
`useTimelineAutoScroll` 新增 inset 纠正 effect：`effectiveBottomInset` 变化且跟随态（且锚点已落定、有内容、非手势/惯性中）时按新 inset 重算目标——
- 流式中：更新 chase 目标并确保 chase 续跑一帧纠正；
- 滑行在飞：只刷新目标，终止帧精确落到新真底（不另起第二落点）；
- 非流式：一次同步精确落位。
覆盖停止胶囊（±40）、错误条（+48）、附件条（+68）三类条件层扰动——即 E-R2 的主场景（流式结束胶囊消失、内容高不变、旧实现无任何纠正运行）。非跟随态明确不动作。键盘高度变化不经此路（键盘打开时落点归 linkage，方案波 5 要点 2）。
钉测：hook 场景 8（152→112 同步纠正到 512；非跟随态再变不动作）。

### 2. settle 同步化 —— ✅ 已做
- `useTimelineAutoScroll` 新增 settle effect：busy true→false 跃迁时做一次**同步**贴底纠正（`snapToBottom`），仅守跟随态 + 锚点已落定两道门（另加手势优先/有内容的安全门）。
- `scheduleScrollToEnd` **整体退役删除**：其 rAF 延迟一帧 + 回调重查互斥锁、锁占用时静默丢弃的形态不复存在。snap 路径直接接管落点并释放锁，不存在「被锁吞」。
- 锁的语义保留且纠正不丢：滑行在飞时内容撑高的纠正折入在飞滑行目标（`handleContentSizeChange` 的锁分支只刷新 `targetOffsetRef` 后返回），滑行终止帧精确落到新目标——比「锁释放点补发」更强（纠正与在飞落点合并为同一次落位）。钉测：hook 场景 7（锁被人为占用时 settle 仍同步落到 552 且锁被接管释放）、场景 9（滑行途中内容撑高，终止帧落到新目标 552 而非旧目标 352）。

### 3. chase 记账隔离 —— ✅ 已做

- **`scrollYRef` 在 `useTimelineAutoScroll.ts` 内已零写入**（grep 实证）；其唯一写方回到 TimelineView 的 `handleScroll`（onScroll）。

### 4. inset 双推导收敛 —— ✅ 已做

### 5. 落点机制收敛为单入口 —— ✅ 已做
- `useTimelineAutoScroll` 对外只剩一个落点函数 `scrollToTrueBottom(animated)`：animated=true → 阻尼平滑滑行（回底按钮门面 `scrollTimelineToBottom` 即其别名）；animated=false → 同步精确落位。settle、inset 纠正、非流式贴底、流式 chase、宿主 `[follow, blocks.length]` 效应全部经此单入口或其内部原语（snap/chase），公式仍单源 `computeBottomTarget`（未动）。

- TimelineView 的 `[follow, blocks.length]` 效应改走 `scrollToTrueBottom(false)` 同步落位（原经 scheduleScrollToEnd 的 rAF）。

### 6. N-3 —— ✅ 已定位并按根因修复（代码层证据；真机复核归波 8）
**根因（代码实证链）**：长会话按恢复锚点打开时，若锚点行尚未布局（长会话必然如此：`initialNumToRender=16`、锚点在深部），`attemptAnchorRestore` 走 `scrollToIndex` 估算落位；RN 在应用提供了 `onScrollToIndexFailed` 时把失败处理完全委托给应用，而旧 `handleScrollToIndexFailed` 的精定位只靠**单次 rAF 重试**——行按批挂载（maxToRenderPerBatch=16）时，该帧几乎必然早于锚点行 onLayout 到达而空转；与此同时恢复阶段已被置 `done`，后续 `contentSizeChange`/`rows` 触发的 `attemptAnchorRestore` 全部空转，**估算落位被永久化**。估算 = 平均行高 × 序号，对 Markdown 异高行误差可达数百 dp，落点停在任意行中间、首行被切；而落点恰在视口顶部——半透明标题栏 + 顶部 EdgeFade 所在的 `headerClearance` 区（真机约 290 设备像素 ≈ 100dp）——切行文本在该区即呈「不可读乱码带」。短会话锚点行在首批渲染内、走布局精定位路径，故无此症。与方案推测（初始滚动偏移/顶部 inset 与标题栏安全区未对齐）方向一致，但落点在锚点恢复链而非标题栏组件：顶部避让本身仍是单一推导（headerClearance 同时供 paddingTop 与指示器），无需也不应给恢复落点再叠一层避让（那会改变阅读位置复现语义）。
**修法**：
- 估算落位时登记「待精修锚点」（`anchorRefineRef`）；锚点行 `onLayout` 到达（`handleRowLayout`）即按布局图精确重落位一次（差 ≤1dp 视为已准、只解除）；删除旧的单次 rAF 重试。
- 解除条件：精修完成 / 用户手势介入（scrollBeginDrag）/ 回跟随锚点作废 / anchorKey 变更——精修不与用户争抢、不跨会话残留。
- 钉测：batchB 新增两例（估算后布局到达 → 精确落到 layout.y + offsetPx；手势介入后布局到达 → 不重落位）。

### 附带项：linkage 触底原点归正（V4 #7 / S3，波 5 要点 1 的另一半）—— ✅ 已做
