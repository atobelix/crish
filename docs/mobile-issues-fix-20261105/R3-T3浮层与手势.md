## 1. 抽屉 onFinalize 兜底收口（题 8 主根因）— ✅ 完成

文件：`src/presentation/components/drawer/CrishDrawerLayout.tsx`

- Pan 链新增 `.onFinalize(...)`，与 `onEnd` 共用 worklet 助手 `settleProgress(target, velocityX)`：关侧先 `runOnJS(handleDrawerClose)`（导航重置/焦点归还/状态机 close），减动效直落数值，否则 `withSpring` + 落定回调同步 `isOpen`/`phase`。onEnd/onFinalize 抽共用助手是为杜绝两条收口路径行为漂移（单轨纪律）。
- 防双重收口：新增 SharedValue `endHandled`——onEnd 置真后执行收口；onFinalize 见其为真只清标跳过。落指/抬手/取消（onTouchesUp/onTouchesDown 单指分支）统一清零四枚新 SharedValue。
- onFinalize 的落位口径：progress 恰为 0/1 直接跳过；否则以 `drawerReleaseTarget({startProgress, progress, velocityX: 0})` 就近落位。**速度刻意置 0**：onFinalize 不是用户主动甩动（多为系统 fail/取消中断），斜向滚动的速度分量若带入提交判定会误开抽屉；只取最近侧落定。
- 冻结链闭合验证（新增测试）：复刻 G 证明的链——在飞落指 `cancelAnimation` → 纵向采样判 fail → 手势 finalize → 断言 `withSpring(1)` 被调用（收口启动）且 close 逻辑不重复执行。另有双重收口防护、onEnd 正常落位时 onFinalize 不起弹簧、progress 恰 0/1 跳过，共 5 个新用例。

**N-1（主页约 8px 露边）同源结论**：静止残值只能来自未收口的中间 progress——程序化弹簧（open()/close()）落点精确为 0/1，不存在静止残值路径；手势路径此前唯一能留下中间 progress 的就是无收口的中断链，onFinalize 已断掉该产生路径。故 N-1 不再单列施工，随本项闭合。真机复现验收仍待装机环节（见遗留风险）。

## 5. DeviceSheet pendingAction 死代码 — ✅ 整段删除（处置与理由）

文件：`src/presentation/components/chat/DeviceSheet.tsx`

- **现状细读结论**：设备行 onPress 的时序是 登记 pendingAction → `onClose()` → **同步执行 action()** → 清空 ref。`handleCloseComplete` 里的待执行分支因此永不触发（纯死代码）；且若 action 抛错，清 ref 不执行，关闭完成时还会二次执行（双重执行风险为真）。
- **处置：整段删死机制**。理由：现行可观察行为就是「点选同步执行」（`DeviceSheet.test.tsx` L92/140/155-156 钉的正是同步契约），且源码注释已述退场动画与数据面切换经 Sheet 的 `runOnJS(handleExitFinished)()` 根治后安全共存——延迟机制既无真实需求、又从未生效，按「非必要不兼容」不修成真机制，直接删除。
- **删除内容**：`pendingActionRef`、`handleCloseComplete` 包装、登记/清空两行；`onCloseComplete` 改为直通 Sheet（与 DeviceSheet 的姊妹 Sheet 同构）。设备行保留删除前的逐点顺序（先 `onClose()` 再切换/重连），行为零变化；误导性注释改写为真实契约并注明删除缘由。DeviceSheet 套件全过（同步契约测试未动一字）。
