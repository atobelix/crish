## 2. 路径重叠与冲突（审计重点 1）

### 2.1 P1 · 引擎配置读写：两方案各保一条「单轨候选」，直接对撞

- **01 §3-P1 / §7 待确认 2**：收敛到「统一树 / `settings_*` / 明确退役封装」三选一，且删除面含「**及任何 REST 孪生，查清即删**」。
- **05 §2.1 生产收敛列**：明确把「**② 改经引擎 REST `GET/PUT /v1/settings`**」列为与删死调用、并树**并列**的合法路线 R1-04。
- **02 §3-P1**：收敛到「统一配置树读写面（或明确退役后的唯一合法封装）」，未列 REST 为候选；待确认 1 只问「孪生是否存在」。
- **代码证据**：`command-contract-drift.test.ts:286-287` 已记载 REST 孪生**存在于后端**（`server/backend.rs:205` / `PUT :217`），但前端未经 HTTP 消费；`engineConfigIO.ts:181` / `:208` 仍是唯一前端调用点，恒走 Tauri invoke。

**冲突判定**：01 要「删 REST 孪生」，05 要「可选采用 REST」——若两案条款同时合入执行，同一概念（配置读写单轨）出现**互斥目标**；若实现者各取一半，则树投影 + REST 并存 = 第二条路径，直接踩不可变条件 6（不新建并行路径）与 D1「→ 1 条」。  
另外 02 待确认 1 把「REST 孪生是否存在」当未知项，而 drift 测试证据已存在——**01/02 的待确认可凭 `command-contract-drift.test.ts:286-299` 升级为已核事实**（孪生在后端、前端未消费），缩小裁决面。

### 2.2 P2 · hasKey 路线 A：05 给「删回写」开了镜像后门，与 01/04 对撞

- **01 §3-P2**、**04 §2.1**（`profileKeySecret.ts:63` `saveProfiles(list)`）：删除面明确 = **删 `p.hasKey` 回写**，LS 字段不再被采信；04 §0.2 论证拒绝路线 B。

## 3. 删除面可执行性与假删除（审计重点 2）

### 3.1 可执行、且以物理删除为 DoD（好样板）

- **04 §2.1**：16+3 逐行、函数级（`saveProfiles` 整函数、`setProfileKey:63` 调用、`oauthTokenManager:109`）——与 D8 实扫逻辑（`check-provider-single-track.mjs:701` 符号表、`:740-753` WARN 计数）对得上，且 §8.1 自认 16 行需重跑取权威全量（诚实）。
- **02 §5 / §6**：每期删除面 + 双路径过渡表带**收敛触发条件**（「某期合入」而非「视情况」）——满足不可变条件 6 对 fallback 的约束方式，是六案中过渡纪律最清晰的。
- **05 §5.1 R1–R8**：棘轮条目删除全部挂「生产收敛后」前置条件，§4 明文「禁止先删棘轮再改生产」——防假删除的顺序锁是对的。

### 3.2 假删除 / 留壳风险点

1. **05 §2.2② 镜像回写**（§2.2 已述）：验收允许保留 `p.hasKey` 写——**最重的假删除缝**。
2. **01 §5 风险表**「LS / AppSettings 陈旧键残留：键可暂缓物理清除……键清理列入删除面尾项」：尾项**无日期**，与不可变条件 6「不留无删除日期的 fallback」擦边；若读面已断，风险降为脏数据，但完成定义 §6 只说「零活引用」，键永久留存也判过——建议给键清除挂战役收口条件。
3. **04 §1.1 行 2 与 §2.1 对 `setActiveModelId` 措辞摇摆**：行 2 写「**豁免（键空间）+ 收敛（符号）**」，§2.1 又写「删写口（或整文件降为迁移读侧）」；§4.4 给「只读 hydrate 后清除」选项。三档处置并存且未定序，执行者可选最松的「豁免」——需在合并稿锁成「读面迁完 → 写口删 → 键清」单一序。
4. **02 §3-P3②**「appSettings.defaultModel：字段若保留仅只读投影且写路径关闭，**或**直接删字段——二选一」：保留字段 + 关写 = 半死字段，后续没人删；不可变条件 3 已禁其参与决议，删字段才是净收敛。二选一应锁死到删。
5. **04 §1.6 / §4.3 新键 `crish_oauth_tokens_v1`**：把 OAuth token 从档案整表拆到**新 LS 键**——若 `saveProfiles` 调用如约删除（§2.1），这是搬移不是并行，可接受；但新键写口必须进 `D8_SETITEM_FILES` 白名单（脚本 `:756-807` 只增查不自动知），04 未显式写「登记新键」一步，执行漏掉则门禁红或漏管。
6. **03**：无删除面正文——README 规则 5 对「确无可删须写验证依据」的豁免路径也没走（P6 类型是新增物证，02 §3-P6 写了豁免依据，03 连豁免依据都没写）。**规则 5 不合格**。

### 3.3 读面假删除（删了写、留了真值读）

- 01/02 断言「业务分支只读 credentialStates」，但 01 的正逆向未点名 `profileKeySecret.ts:81-84` 这类「函数内回读 LS hasKey 判成败」——04 §1.2 有列。合并时 P2 删除面**以 04 §1.2/§1.4 表为权威全集**，01/02 的 16+3 口径是计数锚不是读面全集。
- 04 §1.5 `getProviderSetupStatus`（`profileStoreActivation.ts:213` 仍 `anyProfileHasKey()`）列为反例——正确；01/02 均未单列该读点，若按 01/02 执行会漏改。

## 6. 逻辑依赖顺序与断环（审计重点 5）

### 6.1 种子拓扑 vs 各案期序

种子（`00-总方案.md` §2）：`B 删除面定稿 → {C config, D hasKey} → E 选择 → {C,E} → F 预估 → G 注释 → H 验收`。

| 方案 | 期序主张 | 与种子关系 | 判定 |
|---|---|---|---|
| 01 §4 | 契约 → P2 → P1 → P3 → P4 → P5 → P6 | 串行化 C∥D（更保守）；F 在 C、E 后 | **一致**（串行不违草案） |
| 02 §0.4 | **P4 可先行**，P1∥P2，P2→P3，P5 后置，P6 末位 | **P4 先行 = 违背种子 C→F、E→F**；且 §0.4 自称「依赖拓扑与总方案 §2 一致」 | **内部自相矛盾 + 与种子冲突** |
| 04 §3 | 摸底 → 密钥入口 → 岛外 → 活动 → 档案 → OAuth → 门禁 → 验证 | D 域内部序，挂 E 前 | **一致**；但活动写口删除的读面依赖未环入 P3（§6.3） |

**断环/顺序风险**：

1. **02「P4 先行」与种子及 01/05 直接矛盾**——三案对同一依赖给出两种答案；合稿必须二选一（改种子拓扑或改 02），不能两说并存。
2. **写口删除先于读面迁移**（01/02/04 均 P2 在 P3 前 + P3 读面清单不全）：`setActiveModelId` 写删后，§2.3 列举的十余个 `getActiveModelId` 读方继续消费冻结的 LS 值——**顺序在图上无环，在数据流上是「先拆电源线再换灯泡」**。正确序应为：读面迁树（P3 扩清单）→ 写口删（P2/D8）→ 键清理，或至少同交付原子换。04 §3 步骤 4 只迁了 resolve 系读面，未覆盖外部读方。
3. **05「先门禁后生产」** 是唯一显式防「先删棘轮」的总序——应作为合稿骨架，02 的窄域 commit 粒度叠在其上。
4. **06 的 D 类文档修订**挂「P1–P4 收口或 P6 归档前」——与 01「交主控」、02/06「直改」的文件归属冲突（§2.5）未解，顺序本身无环。
