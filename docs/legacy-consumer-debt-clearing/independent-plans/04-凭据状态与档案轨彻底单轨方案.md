## 0. 视角定位与路线裁决

### 0.1 问题池对本视角的表述

问题池 P2 标题为「D8 旧 LS 档案真相源（`hasKey` 双轨）」：

- 岛内白名单：`api/provider-profiles/*`、`api/providerProfiles.ts`、`api/oauthTokenManager.ts`（16 处写口）；
- 岛外 3 处：`useModelProfilesState.ts:299` / `:343`、`useFirstRunWizard.ts:224`；
- 证据：`check-provider-single-track.mjs` D8 两条 WARN；`profileKeySecret.ts` 已 `configSecretSet` 但仍 `saveProfiles` 回写 `p.hasKey`；
- 候选：路线 A（彻底单轨：`hasKey` 全面改读树 + 删 `saveProfiles` 回写）；路线 B（仅消岛外 3 处判据）——**本池倾向 A**。

### 0.2 本方案裁决：**坚持路线 A（彻底单轨）**，理由经论证后不修正为 B

| 对比维度 | 路线 A（彻底单轨） | 路线 B（消判据不消根因） |
|---|---|---|
| 是否解决真相源双轨 | **是**：`hasKey` 唯一真源 = 统一树 `credentialStates` | **否**：LS 仍为真相源之一，树/LS 可分叉 |
| D8 岛内 16 处写口 | 随写口清退一并归零，`D8_ISLAND` 表可整体删除 | 保留 16 处登记债务，WARN 永存 |
| 岛外 3 处 | 迁到统一单轨密钥写入（`configSecretSet` → 树回执） | 仅改调用封装，判据可能仍命中（`saveProfileKey` 是岛内导出的公共 API） |
| 与 P3 Picker 衔接 | Picker 名单/凭据态同时收敛到树 | Picker 仍读 `loadProfiles()`，活动选择多源残留不消 |
| 与总方案不可变条件 §2 | **完全一致** | 违背「LS 档案不得再作真相源」 |
| 改动面与风险 | 大，但消费面已在本方案摸清到文件行级 | 小，但留下双轨分叉与后续二次战役成本 |

**裁决**：采纳路线 A。问题池「倾向 A」在穷尽生产消费面后**成立**，无需修正为 B。路线 B 仅在「无法列出全部读面、迁移动作不可验证」时才可作为临时妥协——本方案 §1–§4 已给出全部读写面与删除面，B 的前提不成立。

### 0.3 目标态（完成定义）

1. `hasKey` / `credentialStates` 唯一真源 = 统一树回执（`modelsCatalogStore.credentialStates`）；LS `crish_provider_profiles_v1` 中的 `hasKey` 字段**不再被任何生产读路径采信**，字段本身从序列化形状中移除（或恒不写）。
2. 密钥写入唯一合法口 = DPAPI（`config_secret_set`）→ 树回执刷新 `credentialStates`；禁止任何 `saveProfiles(list)` 旁路回写 `hasKey`。
3. 活动选择（`crish_active_profile_id` / `crish_active_model_id`）在本战役内的**逻辑位**：与 P3 身份二元组决议对齐（详见 §6），本方案负责「与树 `activeModel` 的一致性断言」，不单独扩权到 P3 全量清退。
4. OAuth token 合法写口保留且**仅限** `oauthTokenManager` 刷新成功回写 `oauthToken` + 触发树凭据态刷新（不再经 `saveProfiles` 写 LS 档案整表）。
5. 岛内 `D8_ISLAND` 三域写调用归零 → 门禁 D8 岛内 WARN 消失；岛外 `D8_KNOWN_DEBT` 两文件三处归零 → `D8_KNOWN_DEBT` 表删除。

### 1.6 `oauthTokenManager` 合法写口

- **现状**：`refreshOAuthToken` 成功 → `profile.oauthToken = …; profile.hasKey = true; saveProfiles(profiles)`（`:106-109`）；`initOAuthTokenScheduler` 由 `bootstrap-full.ts:54-57` 生产拉起（**非死岛**，`D8_ISLAND` 注释 2026-09-15 已更正）。
- **合法边界**：
  1. OAuth access/refresh token **可以且仅可以**由 `oauthTokenManager` 在刷新成功后写入持久介质（豁免域）；
  2. **禁止**经 `saveProfiles` 整表写 LS 档案（消除 D8 `saveProfiles` 命中）；
  3. **禁止**写 `profile.hasKey` 当作真相——`hasKey` 由树 `credentialStates` 表达；OAuth 供应商若「有 token ⇒ 已配置」，应在树凭据态回执或独立 `authType=oauth2` 判定中表达（诚实待确认：Rust 侧 `credentialStates` 是否已覆盖 oauth 凭据存在位，见 §8）。
- **处置**：拆出 `oauthTokenPersistence` 最小写口（单 profile 的 `oauthToken` 字段，键空间若仍属 `crish_provider_profiles_v1` 则**整键迁移**到独立键，如 `crish_oauth_tokens_v1`——避免与档案列表键纠缠）；写完后调用统一树 `credentialStates` 刷新（或触发 `reload`）。从 `D8_ISLAND` 保留「oauthTokenManager 为唯一 OAuth 写口」豁免注释，但 `saveProfiles` 调用行必须删除。

## 4. 迁移设计要点（实现向，仍不改码）

### 4.1 密钥写入（岛外 3 处依赖的内核）

- 入口签名保持 `saveProfileKey(profileId, apiKey, opts?)` 可降低 UI  diff，但实现体：
  1. `configSecretSet` / `configSecretClear`；
  2. 触发 `modelsCatalogStore` 读刷新（现网已有 `reload_live_catalog`/`publish_change` 链，以实际读回执为准——**诚实待确认**：密钥写后树回执是否自动推送，若否则入口内显式 `reload`）；
  3. 读 `credentialStates[profileId].hasKey` 决定 `ok`；
  4. 激活同步仅在需要时走 `configProfileApply`（已内部统一树）。
- `setProfileKey` 不再 `loadProfiles`/`saveProfiles`；profile 不存在时：树无该 provider → 调用方应先 `ensureProviderShell`（首启/设置页已有该步）。

### 4.2 档案列表 `saveProfiles` 消费点

- 创建：`createCustomProfile` → 仅 `ensureProviderShell`（树），返回视图可由 `listLiveProviders` 投影。
- 增删改模型/启用/改名：全部改为对 `modelsCatalogStore` 的事务调用（已有 `addModel`/`ensureProviderShell` 等——实现时盘点缺口，缺则补薄封装，**不新建并行路径**）。
- `loadProfiles` 空库 `saveProfiles([])`：删除；空状态由树空快照表达。

### 4.3 OAuth

- 独立键 `crish_oauth_tokens_v1: Record<profileId, OAuthTokenData>`（或同等最小形状）；`oauthConfig` 若仍在 LS 档案对象，则迁移为读侧导入（`modelsLsImport` 同级显式边界）或迁树旁路元数据——**边界日期**：随本战役收口删除写回。
- 刷新成功：写 token 键 + 触发树刷新；不写 `hasKey`。

### 4.4 活动选择

- 写：仅树 `activeModel`（`applySelectionToTree` 已支持 `activeModel` 字段）。
- `crish_active_*` LS 键：迁移期**只读**用于冷启动回放（一次性 `hydrate` 后清除写口），或直接废弃并以树为唯一源（若冷启动顺序保证树先就绪）。  
  **诚实待确认**：启动时序中树快照晚于首帧 UI 的竞态是否要求 LS 旁路（§8）。
- `sanitizeGhostActiveModel` / `clearActiveModelId`：迁为对树 activeModel 的幽灵清洗或删除。

### 4.5 `getProviderSetupStatus` 等 LS 读残留

- `anyProfileHasKey` → 树上 `Object.values(credentialStates).some(s => s.hasKey)`。
- `anyProfileHasModel` → 树上任意 provider 有 models。
- `profileHasConfiguredKey` → `providerHasKey`（P3 对话选择器「可用」判定同源）。
