# 本仓对话流现状审计（apps/crish-desktop）

> 审计人：主控，2026-09-06。范围：`apps/crish-desktop/src` 的 chat-* 组件与 chat-bridge 数据链路。
> 总评：**底子不差（虚拟化、timeline blocks、token 体系、slot 服务都在），但对话流被三代 UI 叠加 + 多头状态账本拖垮**：流式真相有三套账、渲染层 prop drilling 28 项、工具卡三代并存、滚动所有权分散在 4 个 hook、单个 CSS 文件 1163 行。这就是「界面基本没法看」的结构性根因——不是缺样式，是缺统一渲染契约。

## 2. 数据层：流式真相有三套账（核心病灶）

1. **Store 内 mutable `SessionMessage`**（store/types.ts:496-）：`text / thinking / thinkingTurns / toolCalls / blocks / streamTextOffset / precomputedHtml` 并存于同一对象，随事件命令式 patch。
2. **streamState 命令式账本**（api/chat-bridge/handlers/streamState.ts:3-45）：`turnStreamedTexts` / `turnAuthoritativeTexts` / `messageEndTurnSegments` / `endTimer` / `activeTurnIndex` 多账本对账，注释自述「严禁向实时增量队列二次注入」——靠纪律而不是靠结构保证单一路径。
3. **视图层 merge**（chat-message/streamMessageViewModel.ts）：`applyStreamTextToMessage` 处理 committed/stream 分叉（divergence 分支）把流文本再合一次进 view model。

对照 dsh：事件 → per-kind 状态机折叠 → 不可变 order + per-key source，**只有一条折叠路径**；落定/中断/重试都是同一 State 的不同终态。本仓三层各自为政导致：每加一种事件都要改 handler+viewmodel+store 三处；divergence 是常态防御而非异常。

## 3. 渲染层：prop drilling 与行级白名单 memo

- `ChatMessageList → MessageVirtualizer` 手工透传 **28 个 props**（ChatMessageList.tsx:203-236），另配 `messageVirtualizerPropsEqual` 白名单浅比较（MessageVirtualizer.tsx:329-332）。
- 每行无统一 Seat/锚点契约：行容器只有 `data-vindex={msg.id}`（MessageVirtualizer.tsx:244,265）；没有 `data-chat-turn` 之类语义锚点，滚动/导航/测试无法 O(1) 命中语义单元。
- 节点渲染分发散在 if/else（sender === 'user' 分叉 + ChatUserMessageRow / StreamingAssistantRow 二选一），新增节点类型（注入、压缩、审批、错误、重试）各自找位置插——chat-injection、PlanApprovalRow、EphemeralStatusSlot 就是这么长出来的。

## 4. 工具卡三代并存

`MessageToolCallsSection → ChatToolCallBlock → CompactToolRow → ModernToolCall → Modern{Terminal,Json,Approval,CodeBlock}`（chat-tool-call/ 内部调用链），CSS 三份：ChatToolCallBlock.module.css 968 行、ModernToolCall.module.css 548 行、TimelineThoughtSection.module.css 213 行，视觉规格互不一致。dsh 对应物是**一个** ToolRow（24px 单行 + 类型化展开卡 + data-variant/data-tool/data-state）。

## 5. 滚动：所有权分散

- `useVirtualScroll`（VSM 管理器）+ `useScrollAnchor` + `useUndoWithScrollAnchor` + `useChatScroll`（ChatCard 侧）四处共同决定滚动行为；`registerActiveVsm` 全局注册活跃管理器（MessageVirtualizer.tsx:74-79）。
- 回底按钮藏在 ChatStatusRibbons（ChatCard.tsx:136-137），与 dsh 的零高度 sticky 槽不同。
- 无跨会话滚动位置恢复（仅高度缓存 clearHeights）；无 prepend 锚点补偿（load-older 场景直接置顶）。
- 流式跟随没有 reader/programmatic 判别与 followSig，回底逻辑靠 showScrollToBottom 状态翻转，惯性滚动场景易被 snap 打断（dsh ChatView.tsx:533-536 专门防这个）。

## 6. 样式现状

- token 体系存在（`--chat-col-max: 760px`、`--space-*`、`--radius-xl`、`--accent-color`），但行级实现与 dsh 差异大：行距靠 `.row { margin-bottom: 22px }` + `.rowUser/.rowAssistant { margin-bottom: var(--space-5) }` 链（ChatMessageRow.module.css:6, 53-51），搜索高亮用负 margin hack（22-31 行）。
- 用户气泡 `border-radius: 14px 14px 4px 14px` + 5.5% 灰度底（62-82 行）——与 dsh 的 22px 全圆角胶囊是两种语言；无内容宽轴百分比（78% 上限 + 560px）。
- Markdown 类型阶梯（.md-h1..h6、行内代码 3.5% 灰度底）已自成体系，保留即可，只需对齐节奏变量。

## 7. 会话壳 chrome 堆积

ChatCard 周边有 ChatStatusRibbons(394 行)、UnitChromeActions(369)、DynamicChipBar(226)、ChatMsgFilterBar、SubagentHeaderPanel、ApprovalDock、ChatQueuePanel、SetupHintBanner、PlanGoalRibbons——全部平铺在 composer 上方/流区域内，无统一 dock 分层（对照 dsh：composer dock slot `conversation.composer.dock` 按 order 组装，回底/菜单 z 序有明确栈：composer 7 / 回底 8 / 菜单 9）。

## 8. 可保留的资产（重构不应推翻）

1. **VSM 虚拟化**（自研、有 perf 测试）——dsh 没有的能力，长会话必需。
2. **Worker markdown 渲染 + precomputedHtml 预热**（api/markdown-render、markdownBatchPrewarm）。
3. **Tiptap composer 全家桶**（近期刚按 §19/§20 铁律重构，四态体系已达标）。
4. **services/view-registry + SlotOutlet**、`workspace.chat.stream` slot——node 注册表可挂载其上。
5. timeline blocks 模型（thought/text/tool_call 交错）与工具展示归一（tool-presentation/timelineNormalizer）。
6. 丰富的行级测试（streamMessageViewModel、MarkdownBlockItem、TimelineThoughtSection 等测试资产，按 §9 铁律保留改造）。
