# 通知与异常展示单轨收敛总方案

> 状态：已落地（2026-09-20），本文与代码同版
> 日期：2026-09-19 立项 / 2026-09-20 收口
> 范围：`apps/crish-desktop` 前端展示层（对话流 / 输入框上方区域 / 全局浮层）
> 关联：docs/chat-flow-resilience、docs/linear-chat-stream-convergence

---

## 0. 背景与问题陈述

收敛前，一次「用户发消息 → AI 运行 → 出错/重试」的生命周期里，同一异常状态最多同时出现在 **5 个位置**：

1. 右下角 Toast 堆叠浮层（`overlay/ToastViewport.tsx`，`position='bottom-right'`）；
2. 输入框上方 `RunNoticeBar` 横幅；
3. 对话流内气泡错误卡（`msg.errorDetail` → `TurnErrorNode`，`MessageContent` 三个分支各挂一份）；
4. 对话流内瞬态重试行（`ephemeralChatStore` → `ModelRetryNode`）；
5. 输入框上方重试横幅（`continuityUiStore.retryNotices` → `RetrySlotNotice`）。

根因不是组件多，而是**写入侧有多个互不感知的状态出口**：`handleRunError` 同时写 runNotice / toast / 气泡 errorDetail / ephemeral，`onProviderDiagnostic` 同时写 continuityUiStore 与 ephemeral。旧裁决器 `resolveRunErrorSurface` 只管前两者，其余通道对任何 surface 都无条件写入，"展示唯一性"名存实亡。

另有三处契约缺口在收敛前就已存在：

- 重试成功后没有任何路径清理重试行：`onChunk` 与 complete 都不清 `retryNotices` / `retryState`，「重连中 n/m」在成功后一直挂着；
- 重试倒计时是假的：前端读 `diag.delayMs`，而引擎 `ProviderDiagnostic` 根本没有该字段（只有 `elapsed_ms` / `retry_after_ms`），秒表恒从 3 秒起跳；
- 首 token 之前出错重试时（最常见场景）`MessageContent` 走分支 α，只渲染 `WorkingStatusIndicator`，根本没有挂重试行。

用户裁决（2026-09-19）：

- **通知 = 全局浮层**（顶部居中 Toast，移除右下角堆叠）；
- **重试进行中 = 对话流内临时显示**，闪光流动文字 + 重试进度；**重试成功即消失，不留痕**；
- **重试失败/错误 = 输入框上方错误组件**（非胶囊），带引导重试按钮；存续到「问题解决 / 切换会话 / 用户主动关闭」；
- 目标只是"让用户在对话流里能看到异常状态"，**单轨、不重排、不重复**。

## 1. 目标态：单轨展示模型

### 1.1 没有"裁决器"，只有状态机

初稿设想过一个 `resolveNoticeSurface(kind, phase, hasText)` 纯函数。实施时删除了这一层：它的输入 `phase` 已一对一决定输出，`kind` 与 `hasText` 根本不参与裁决，保留它等于给未来留下第二个决策点——恰恰是本次要消灭的东西。**事件源本身就是相位**：

| 事件源 | 相位 | 唯一承载体 |
|--------|------|-----------|
| `provider-diagnostic phase=retry`（引擎自动重试中） | `retrying` | 对话流内 `InFlowStatusLine` |
| `onRunError`（引擎重试耗尽 / 额度 / 鉴权 / 服务端 / 网络终态） | `failed` | 输入框上方 `ComposerErrorBar` |
| 新 Token / run complete / 新一轮发送 / 切换会话 / 用户关闭 | `idle`（缺键） | 无 |
| 与会话运行无关的全局事件（设置保存、模型目录刷新、停止生成、空回复） | 不进状态机 | 顶部居中 Toast |

引擎侧这两个事件天然可区分：重试走 `stream_error_retry.rs` 的 `emit_retry_diagnostic`（`phase=Retry`），耗尽后走 `fatal_provider_error` → `run-terminal failed` → `onRunError`。

### 1.2 三条通道的物理边界

```
┌────────────────────────── 全局层 ──────────────────────────┐
│  ToastViewport（顶部居中，上限 3，TTL 5s，同文案 dedupe）   │  ← 全局事件
├────────────────────────── 会话层 ──────────────────────────┤
│  对话流 ChatMessageList                                    │
│    └─ 活跃 assistant 行尾 InFlowStatusLine（瞬态，成功即销毁）│  ← retrying
│    └─ 失败轮次正文尾「回复中断」一行灰字（事实标记，无操作）  │  ← msg.status==='error'
│  ───────────────────────────────────────────────          │
│  ComposerErrorBar（输入框上方，全宽非胶囊：文案+详情+重试+关闭）│  ← failed
│  ChatComposer                                              │
└────────────────────────────────────────────────────────────┘
```

不变量：

- **I1 唯一性**：任一事件只命中一个相位，只有一个 DOM 承载体；`retrying` 与 `failed` 是同一字段的两个值，物理上不可能同屏双显。
- **I2 对话流纯洁性**：对话流只承载「真实 AI 输出 + 进行中的瞬态行 + 持久化的事实标记」。瞬态行绝不持久化；事实标记来自 `msg.status==='error'` 这一已持久化字段，不带文案、不带按钮，不与 ComposerErrorBar 重复信息（它记录"发生过"，错误条负责"现在怎么办"）。
- **I3 不重排**：瞬态行挂在当前活跃 assistant 消息末尾，不参与排序，不产生新消息节点；「重试」复用原 user 消息位，严禁新建用户消息。
- **I4 错误持久可见**：`failed` 相位无 TTL，消解条件只有：①新一轮发送/重试成功 ②切换会话 ③用户点关闭 ④`network` 类在 transport 恢复时**跨全部会话**自动清空。

## 2. 详细设计（与代码同版）

### 2.0 SessionRuntimeStatusStore：单一状态机 + 唯一写入口

`store/sessionRuntimeStatusStore.ts`：

```ts
type SessionRuntimeStatus =
  | { phase: 'retrying'; sessionId; retry: { attempt; maxAttempts?; errorKind? }; timestamp }
  | { phase: 'failed';   sessionId; kind: RuntimeErrorKind; message; technicalDetail?;
      turn: { userMsgId; assistantMsgId }; timestamp };

reportRuntimeStatus(event)          // 全库唯一写入口（retrying | failed，单例覆盖）
clearRuntimeStatus(sessionId)       // 自愈清空
clearNetworkFailedRuntimeStatuses() // transport 恢复：全会话 network 类 failed 清空
```

硬保证：

- **写入唯一**：`scripts/check-runtime-status-ssot.mjs` 挂在 `check:desktop` 首位，禁止直接 `setState` / `.report(`、禁止旧通道标识符回流（`ephemeralChatStore` / `retryNotices` / `pushRunNotice` / `RunNoticeBar` 等）。
- **不缓存提问文本**：`failed.turn` 只带 `userMsgId / assistantMsgId`。重试按 id 现查文本，用户编辑过消息也不会重发旧内容。
- **不臆造数据**：`retry` 不含倒计时（引擎不下发）；`maxAttempts` 缺省时 UI 显示「第 n 次」而不是伪造分母 3。

### 2.1 通道 A：全局浮层

- `ToastViewport` / `ToastContainer` / `ToastProvider` 默认 `top-center`；顶部锚定阴影向下。
- `TOAST_MAX_QUEUE = 3`（不取 1：单例会让「设置已保存」与「模型目录已刷新」同帧互相覆盖，也会瞬间吞掉带撤销按钮的分支/删除 toast）；保留同文案 dedupe。
- 会话运行类事件**不再有任何 toast 调用点**（`handleRunError` 的 `toast.show` 已删）。「已停止本轮生成」「这一轮没有文字回复」属操作反馈，走 toast。

### 2.2 通道 B：InFlowStatusLine（重试进行中）

`chat-message-row/InFlowStatusLine.tsx`：图标 + shimmer 单行文字（复用「正在思考」的 `background-clip:text` 视觉语言）。文案由纯函数 `formatRetryStatusText` 产出：有上限 `正在重试 2/5`，无上限 `正在重试 · 第 2 次`。无按钮、无详情、无倒计时。

挂载：`MessageContent` 三个渲染分支（α 零内容 / β 降级正文 / γ 分段时间线）各在末尾挂同一节点，条件 `isLiveTurn && status.phase==='retrying'`。分支 α 也挂，修复了"首 token 前重试看不到"的缺口。

生命周期（六处清空，全部落地）：

| 触发 | 位置 |
|------|------|
| run 启动 | `useRunStreamingAssistant` 启动即 `clearRuntimeStatus` |
| 新 Token 首帧 | `onChunk` 首帧 |
| run complete | `commitRunCompletion` |
| 新一轮发送 | `useSlashSend` |
| 切换/删除会话 | `SessionCoordinator.deleteSessionCascade`；ComposerErrorBar 按 activeSessionId 订阅，切走即不显示 |
| 重试点击 | `regenerateTurn` |

### 2.3 通道 C：ComposerErrorBar（终态错误）

`chat-card/ComposerErrorBar.tsx`，挂在 `ChatStatusRibbons` 原 `RunNoticeBar` 位置：

- 全宽非胶囊；错误文案**可换行不截断**（曾用 `nowrap + ellipsis`，长 message 又无 technicalDetail 时后半段不可见，已改）；
- 「详情」仅在有 `technicalDetail` 时出现；「重试」恒有；「×」关闭；
- 「重试」派发 `retry-failed-turn` UI 事件，由 `useChatHandlers.regenerateTurn` 处理：按 `turn.userMsgId` 现查提问文本 → 撤回失败的 assistant 节点 → 复用同一 user 消息位（置 `processing`，`clientMessageId = userMsgId`）重跑。行动作栏的「重新生成」与它共用同一函数。

`handleRunError`（`streamCallbacksEvents.ts`）的消息收口，**错误即本轮终态，不依赖随后是否还有 onComplete**：

```
onRunError(message, kind, detail)
  → user 消息 processing → completed        // 否则 isProcessing 恒真，发送按钮被 Stop 常驻
  → assistant 零正文 → withdrawMessage       // 不留幽灵占位
  → assistant 有正文 → status = 'error'      // 正文保留；流内一行「回复中断」事实标记
  → reportRuntimeStatus({ type:'failed', kind, message, technicalDetail, turn })
  → 不写 toast / 横幅 / errorDetail
```

`msg.errorDetail` 字段保留类型定义供历史数据反序列化，**零写入点、零渲染点**。

### 2.4 排队与运行态提示

- 排队语义只有一种：follow-up 进对话流时间线（`status:'queued'`，气泡内「排队中」）。composer 侧队列轨 A（`useChatQueue` / `ChatQueuePanel` / `SessionRuntimeRegistry.queuedMessages` / 设置项 `queueMode` 的类型、归一化与 UI）**整体删除**，不保留兼容读取。
- 「这一轮没有文字回复」「已停止本轮生成」走全局 toast。

## 3. 明确不在本方案内的事项

以下曾列入初稿 §3「时间线防重排专项」，实施中确认它们与通知收敛**无因果关系**且风险独立，已从本方案剔除、代码已还原到收敛前状态，另立任务跟进：

1. **engineSequence 透传**：引擎信封顶层已有 `sequence`（`eventDedupe.ts` 在用），只是没透传到消息对象。这是一个便宜的独立小任务，不应与展示层改动捆绑。
2. **显示层排序降级为断言**：在 engineSequence 真正落地之前，`useChatMessages` 的 `sortMessagesByOrder` 是唯一兜底。先拆兜底再修源头等于把乱序直接给用户看。**保留**。
3. **孤儿 injection 置顶**：`timelineNormalizer` 的 `unshift` 行为**保留**，与上一条一起归入排序专项。
4. **assistant 占位时间戳继承 user 消息**：同上归入排序专项。

本方案对"不重排"的贡献只有一条、且已落地：重试复用原消息位，不新建用户消息。

## 5. 风险

- **R1 历史消息 errorDetail 不再渲染**：老会话的错误轮次显示已产出正文 + 「回复中断」（status 为 error 的旧消息同样命中该标记）。可接受。
- **R2 ComposerErrorBar 与引擎崩溃条同屏**：崩溃条是 transport 级、错误条是会话级，二者语义正交；崩溃期间 `network` 类错误条会在恢复时自动消失，不需要额外互斥。
- **R3 `queueMode` 设置字段删除**：存量本地配置里的该键在归一化时被丢弃，无迁移成本。
