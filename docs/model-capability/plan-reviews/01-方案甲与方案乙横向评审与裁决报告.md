## 一、评审总览与并行方案对决

本次并行方案设计中，主控 Agent（方案甲）与独立子 Agent 乙（方案乙）分别独立面对用户的五大核心诉求：
1. **思考等级全面英文呈现**（Default, Off, Minimal, Low, Medium, High, X-High, Max）；
2. **思考等级通用化与外部配置**（摆脱 AI 幻觉与静态写死，支持各协议参数）；
3. **模型配置的外部热更新管线（Hot Reloading）**；
4. **超长模型名称智能自适应缩写（防判别度丢失）**；
5. **过时模型淘汰与动态演进机制**。

两套方案均展现了极高的工程严谨性与深度。以下针对两套方案在五大核心维度的技术实现展开客观、尖锐、代码级的横向对比评审。

## 二、五大核心维度横向对比评审

### 2.1 维度一：外部配置文件与热重载内核（Hot-Reloading Core）

| 评审指标 | 方案甲（Plan Architect A） | 方案乙（Plan Architect B） | 评审结论与高下判定 |
| :--- | :--- | :--- | :--- |
| **并发读取性能** | 使用 `Arc<RwLock<ModelCatalog>>`，热重载时持有写锁。 | 采用 **RCU（Read-Copy-Update）架构与 `arc_swap::ArcSwap`**，读操作 **Wait-Free（零等待、零锁开销）**。 | **方案乙完胜**。在 10+ 子 Agent 并发推理请求时，方案甲的写锁会导致网络请求流水线被瞬时阻塞挂起；方案乙读零锁，指针原子 CAS 替换，推理零丢帧。 |
| **文件监听可靠性** | 单文件 Watcher 直接监听 `~/.conex/models.json`。 | **目录级防换 Inode 监听器（Parent-Directory Watcher）** 配合路径规范化过滤。 | **方案乙完胜**。现代编辑器（VS Code, JetBrains）保存文件时采用 Atomic Rename（写入临时文件后覆盖重命名），方案甲单文件监听会导致 Windows 下 Inode 替换后掉监听；方案乙监听父目录彻底免疫此问题。 |
| **文件锁与截断容灾** | 50ms..400ms 指数退避重试，侦测 `ERROR_SHARING_VIOLATION`。 | 40ms..300ms 动态退避，侦测 0 字节截断窗口与 Windows 共享违规。 | **两方案平手**。均具备优秀的 Windows 独占锁和 Truncate 0 字节自愈能力。 |
| **坏配置隔离与自愈** | 锁外校验，失败则保持现有 Catalog，Tauri 广播 `catalog:error`。 | **LKG 影子副本两阶段提交**，不仅广播 `catalog:config-error`（带行号列号），在修复保存后还下发 `catalog:config-recovered` 自动消警，且首次启动自动生成带详尽注释的标准模板。 | **方案乙略优**。闭环体验更完整，首次启动引导极大降低用户上手成本。 |

### 2.2 维度二：通用思考能力契约与协议 Wire 映射

| 评审指标 | 方案甲（Plan Architect A） | 方案乙（Plan Architect B） | 评审结论与高下判定 |
| :--- | :--- | :--- | :--- |
| **配置灵活性** | 模型需逐条在 `models.json` 中完整声明 `thinkingFormat` 与 `thinkingTiers`。 | **正交三层能力解析模型**：显式覆盖 ➔ 通配符规则（Wildcard Rules，如 `"*-r1*"`） ➔ 协议预设模板（如 `anthropic_budget`, `openai_reasoning`）。 | **方案乙完胜**。方案甲要求用户给每个新模型手写冗长 JSON；方案乙允许一条通配符规则或绑定模板解决整类中转模型，大幅降低用户维护负担。 |

### 2.3 维度三：模型名称智能自适应缩写算法（SADA）

| 评审指标 | 方案甲（Plan Architect A） | 方案乙（Plan Architect B） | 评审结论与高下判定 |
| :--- | :--- | :--- | :--- |
| **分词与判别模型** | 静态分词，手工维护硬编码缩写词表（`contributor -> ctrb`, `sensenova -> snova`）。 | **SADA-v2 语义锚点模型**：拆解为 $\text{Brand} \oplus \text{EntropyKey} \oplus \text{Specifier}$。以信息熵识别核心版本号，通用规则压紧。 | **方案乙完胜**。方案甲手工字典遇到未知词汇（如用户自定义的奇怪后缀）即刻失效；方案乙基于信息熵和通用形态压缩，适应性极强。 |

### 2.5 维度五：工程实施与反过度设计约束

- **反过度设计红线检查（`ANTI_OVERENGINEERING_GUARDRAILS.md`）**：
  - 两套方案均**未引入**复杂进程池、外部数据库、内核沙箱或滥用中间件；
  - 方案甲改动量较小，实现直接；
  - 方案乙引入的 `arc_swap` 是 Rust 高性能无锁并发的成熟标准轻量库（零依赖、单文件级实现），在零锁开销与并发安全上带来了质的飞跃，完全符合轻量化准则。

## 四、最终裁决结论与实施指导

### 4.1 裁决结论
经过全面横向比对，**方案乙（Plan Architect B）以 96.35 的综合得分大幅胜出，被正式裁定为本次战役的最终实施总方案**！

方案乙在以下三个关键痛点上的突破尤其令人惊艳：
1. **彻底攻克 Windows 换 Inode 掉监听问题**（采用目录级监听取代单文件监听）；
2. **彻底消除高并发读写锁争用**（采用 RCU `arc_swap` 保证 10+ 子 Agent 推理并发零等待）；
3. **彻底根治模型缩写双省略号破碎与手工字典局限**（采用 SADA-v2 语义锚点与 CSS 容器查询）。

### 4.2 最终执行融合意见
虽然方案乙在架构上全面胜出，但在具体落地实施时，主控决定吸收方案甲的一项轻量化优点：
- 在外部配置初次落地阶段，先以简洁明了的 `~/.conex/models.json` 格式落地，逐步展开通配符匹配规则，确保迁移与改动节奏稳健有序，分阶段平稳交付。
