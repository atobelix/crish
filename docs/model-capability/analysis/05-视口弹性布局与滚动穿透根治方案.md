# 视口弹性布局与鼠标滚动穿透根治方案

> **文件标识**：`docs/model-capability/analysis/05-视口弹性布局与滚动穿透根治方案.md`
> **状态**：方案已锁定（只读分析与落地规范）
> **适用范围**：设置中心模型管理页（`ModelsSettingsTab`）、外层全屏设置壳（`SettingsPanel`）、模型列表视口（`ModelList` / `ModelConfigEditor`）
> **核心原则**：纯逻辑规划、反退避（`.agents/LOGIC_PLAN_NO_RETREAT.md`）、严禁魔术数字补丁、SSOT 架构净收敛

---

## 一、背景与问题全景

### 1.1 现场症状复现
用户在日常配置模型与服务商过程中，反馈并截图标注了严重影响交互体验的异常行为：
> **“鼠标滚动滑动，整个界面跟着滑动，很奇怪。”**

经过对用户交互路径与现场组件渲染行为的精准复现，复现场景如下：
1. 用户进入设置中心（`SettingsPanel`），切换到左侧导航的 **“模型”** 选项卡（`ModelsSettingsTab`）。
2. 页面顶部展示“模型”大标题与“添加服务商”下拉按钮，紧接着是“默认模型”配置卡片（`SettingsSection`，包含全局默认模型级联选择器）；下方是服务商列表与模型详情的左右分割双栏工作区（`modelsSplit`）。
3. 当用户将鼠标悬停在右侧模型条目列表（`ModelList`）区域并上下滚动鼠标滚轮时：
   - **预期行为**：仅右侧模型列表内部产生纵向滚动，顶部的页面标题与“默认模型”卡片牢牢固定在视口顶端，服务商分割面板整体尺寸稳定。
   - **实际异动**：**外层整个设置页连同“默认模型”卡片被整体向上卷走推移出屏幕**；随着滚轮向下滚动，用户必须再次费力向上滚动才能重新看到“全局默认模型”下拉框。
   - **空态/少模型异动**：即便选中的服务商只有 1~2 个模型，其列表高度未超出右侧容器，只要用户在右侧空白区域滚动滚轮，整个页面依然发生上下滑动，产生不可预期的界面漂移。
   - **滚动狂飙**：在触控板轻扫或无极滚轮滑动时，页面出现跳跃式剧烈抖动，滚轮加速度异常。

## 二、根因穿透分析（Architecture Disconnect & Root Causes）

通过对 `SettingsPanel.module.css`、`SettingsPanel.tsx`、`ModelsSettingsTab.module.css`、`ModelConfigEditor.tsx` 以及 `ModelList.tsx` 进行跨层审查，确认该缺陷是由 **伪弹性魔术数字、高度传递链断裂、双层嵌套滚动链式穿透、全局事件盲目劫持、缺乏独立视口容器** 五大断层叠加共振导致的必然产物。

### 2.1 根因一：伪弹性布局的魔术数字补丁（`calc(100vh - 220px)`）
在 `apps/crish-desktop/src/components/settings-models/ModelsSettingsTab.module.css` 第 1-12 行：
```css
.modelsSplit {
  display: flex;
  gap: 0;
  flex: 1;
  height: max(480px, calc(100vh - 220px)); /* 严重架构硬编码 */
  min-height: 420px;
  border: var(--hairline-width, 1px) solid var(--hairline, var(--border-subtle));
  border-radius: 0;
  overflow: hidden;
  background: transparent;
  box-shadow: none;
}
```

#### 理论计算 vs 物理现实的致命偏差
前人由于未能打通自顶向下的 Flexbox 高度继承链，试图用 `calc(100vh - 220px)` 猜测视口剩余空间，但**220px 是一个凭空猜测的严重偏小的魔术数字**。

我们计算在 `models` 标签页下，渲染在 `modelsSplit` 之上的所有垂直物理占用：

| 结构层级 / DOM 元素 | 对应 CSS / 属性 | 实际垂直高度占用 |
| :--- | :--- | :--- |
| 顶栏窗口操作区 | `.coverHeader` | **36px** |
| 内容容器上下内边距 | `.coverContent` (`padding: 24px 32px 32px`) | 24 + 32 = **56px** |
| 设置页根容器底部边距 | `.settingsUiPage` (`padding-bottom: 24px`) | **24px** |
| 页面主标题与操作区 | `.settingsUiPageHead` + 行高与内边距 | 约 **36px** |
| 页面主标题与卡片间距 | `.settingsUiPage` (`gap: var(--space-4, 16px)`) | **16px** |
| “默认模型”卡片小标题 | `.settingsUiSectionTitle` (`font-size: 12px`, padding) | 约 **22px** |
| “默认模型”卡片本体 | `.settingsUiCard` + `.settingsUiRow` (`padding: 10px 14px`) | 约 **62px** |
| 卡片与下方工作区外间距 | `.settingsUiPageBody` (`gap: var(--space-5, 20px)`) | **20px** |
| **上方物理占位总计** | **Σ (Top Elements & Paddings)** | **至少 272px** |

#### 溢出数学证明
- 页面实际可用高度：`100vh - 36px`（排除顶栏）。
- 内容实际占用总高：`272px + height(modelsSplit)`。
- 代入前人的公式：`272px + max(480px, 100vh - 220px)`：
  1. 在大屏/高分辨率（如 `100vh = 1080px`）：
     `modelsSplit` 高度为 `1080 - 220 = 860px`。
     总内容高度为 `272 + 860 = 1132px`。
     外层容器高度为 `1080 - 36 = 1044px`。
     **恒定溢出：`1132 - 1044 = 88px`！**
  2. 在中小屏（如 `100vh = 768px`）：
     `100vh - 220 = 548px`。
     总内容高度为 `272 + 548 = 820px`。
     外层容器高度为 `768 - 36 = 732px`。
     **恒定溢出：`820 - 732 = 88px`！**
  3. 在极限小屏（如 `100vh = 600px`）：
     `max(480px, 600 - 220) = 480px`（被 480px 钳制）。
     总内容高度为 `272 + 480 = 752px`。
     外层容器高度为 `600 - 36 = 564px`。
     **严重溢出：`752 - 564 = 188px`！**

**物理结论**：由于魔术数字少估了至少 52px（加上 padding 和 gap 达 88px~188px），**外层 `.coverContent` 无论在什么屏幕分辨率下，都恒定处于溢出状态，其垂直滚动条恒定生效，且具备 88px 以上的滚动行程**！

### 2.2 根因二：Flex 高度继承链断裂（Broken Flexbox Height Chain）
为什么前人会写下 `calc(100vh - 220px)`？这是因为在布局树中存在断层：
1. `.coverContent` 设置了 `display: flex; flex-direction: column;`。
2. 但是在其内部，挂载了通用组件 `<SettingsPage>`（定义于 `SettingsUI.tsx`）：
   ```css
   /* SettingsUI.module.css */
   .settingsUiPage {
     display: flex;
     flex-direction: column;
     gap: var(--space-4, 16px);
     width: 100%;
     max-width: var(--settings-content-max, 820px);
     margin-left: auto;
     margin-right: auto;
     padding-bottom: 24px;
     box-sizing: border-box;
     /* 致命缺失：未设置 height: 100% 或 flex: 1 1 0; min-height: 0; */
   }
   .settingsUiPageBody {
     display: flex;
     flex-direction: column;
     gap: var(--space-5, 20px);
     /* 致命缺失：未设置 flex: 1 1 0; min-height: 0; */
   }
   ```
3. `<SettingsPage>` 最初是为“个人资料”、“外观”、“快捷键”等常规文档流（Document Flow）设计的——内容自然向下延伸，依靠外层滚动。
4. 但模型管理页面属于 **IDE 工作区面板模型（Workbench Viewport Model）**，它需要 100% 填满父容器剩余高度，并在内部各自独立滚动。
5. 前人试图在 `.modelsSplit` 上写 `flex: 1`，但因为父级 `.settingsUiPageBody` 和祖父级 `.settingsUiPage` 都没有确定高度（其高度由子元素内容撑开），导致 `flex: 1` 无法计算出高度基准（Flex Basis 为 auto 并塌陷）。前人未能通过架构方式打通弹性链，转而退避使用了 `calc(100vh - 220px)`。

### 2.3 根因三：双层嵌套滚动与浏览器原生滚动链式传递（Scroll Chaining）
在当前的 CSS 设定中，形成了双层嵌套滚动容器：
- **外层滚动容器**：`SettingsPanel.module.css` 中的 `.coverContent`，声明了：
  ```css
  .coverContent {
    ...
    overflow-y: auto;
    overflow-x: hidden;
    overscroll-behavior: auto; /* 关键：允许滚动链向上级传递 */
    ...
  }
  ```
- **内层滚动容器**：`ModelsSettingsTab.module.css` 中的 `.modelsDetail`（以及左侧 `.mrlList`）：
  ```css
  .modelsDetail {
    ...
    overflow-y: auto;
    overscroll-behavior: auto; /* 关键：允许滚动链向上级传递 */
    ...
  }
  ```

#### 滚动穿透物理机制
在现代 Web 渲染引擎（Chromium / WebView2）中：
1. **Scroll Boundary & Chaining**：当内层滚动容器（`.modelsDetail`）滚动到边界（例如已经处于最顶端，用户依然向上滑；或滚到最底端，用户依然向下滑）时，引擎默认触发 **Scroll Chaining（链式滚动）**。
2. 引擎会寻找 DOM 树中最近的可滚动祖先容器（即外层 `.coverContent`）。
3. 由于根因一证实了 `.coverContent` 永远存在 88px+ 的溢出空间，祖先容器接盘了后续的滚轮事件，执行纵向滚动！
4. **结果**：用户的滚轮动量直接推动 `.coverContent.scrollTop` 变大，页面整体向上移动，“默认模型”卡片被瞬间顶出可视区！
5. **少模型陷阱（Zero-Scroll Trap）**：如果当前服务商只有 1~2 个模型，`.modelsDetail` 的内容高度小于容器高度（`scrollHeight <= clientHeight`），`.modelsDetail` 自身**根本无法滚动**。此时用户在右侧区域滚动滚轮，Chromium 判定当前元素不具备滚动能力，**直接把 100% 的滚轮事件全部派发给外层 `.coverContent`**！导致用户在没有任何长列表的面板里轻滑鼠标，整个页面就像滑梯一样上下乱晃。

### 2.4 根因四：`SettingsPanel.tsx` 中 `handleRootWheel` 的逻辑缺陷与盲目劫持
在 `apps/crish-desktop/src/components/settings/SettingsPanel.tsx` 第 215-231 行，存在一个全局 Wheel 监听器：

```tsx
// SettingsPanel.tsx (源码现状)
const handleRootWheel = (e: React.WheelEvent) => {
  if (contentAreaRef.current) {
    const target = e.target as HTMLElement;
    if (
      target.closest('textarea') ||
      target.closest('pre') ||
      target.closest('select')
    )
      return;
    if (
      contentAreaRef.current.contains(target) &&
      target !== contentAreaRef.current
    )
      return;
    contentAreaRef.current.scrollTop += e.deltaY;
  }
};
```

并且绑定在根节点上（第 270 行）：
```tsx
<div
  ref={rootRef}
  className={`${styles.settingsPanel} ${styles.settingsDialogBody}`}
  data-testid="settings-panel"
  data-density="compact"
  onWheel={handleRootWheel}
>
```

#### 致命逻辑缺陷审查
1. **空白边缘导致 2x 狂飙滚动（Padding Click Failure）**：
   注意第 224-227 行的判定：
   `if (contentAreaRef.current.contains(target) && target !== contentAreaRef.current) return;`
   如果用户鼠标落在 `.coverContent` 自身的内边距（Top 24px, Left/Right 32px）或组件间的 gap 空白上，此时事件的 `target` 就是 `contentAreaRef.current` 自身！
   判定条件中 `target !== contentAreaRef.current` 为 **`false`**！
   因此条件不成立，函数**不会 return**，而是执行了：
   `contentAreaRef.current.scrollTop += e.deltaY;`
   **此时，浏览器原生在执行滚动，JS 又额外手动叠加了一次 `e.deltaY`，导致双倍速滚动与严重的视觉跳跃（Double Scroll Acceleration）！**
2. **无视页面类型（Tab Blindness）**：
   `handleRootWheel` 盲目假定设置页只有一个纵向大页面，没有任何关于当前 Tab 是不是工作区视口型（如 `models`）的逻辑。
3. **绕过 CSS `overflow: hidden` 的锁定红线**：
   在 DOM 规范中，**即使一个元素在 CSS 中被设置为 `overflow: hidden`，在 JavaScript 中修改其 `element.scrollTop += deltaY` 依然会生效！**
   这意味着，即使我们在 CSS 中给 `.coverContent` 设置了 `overflow: hidden`，只要 `handleRootWheel` 还在执行，鼠标在侧边、顶栏或空白处滑动滚轮，JS 依然会强行把 `.coverContent` 滚上去，彻底击穿 CSS 防线！

### 2.5 根因五：`ModelList.tsx` 缺乏独立的滚动容器与视觉骨架
审查 `ModelConfigEditor.tsx` 与 `ModelList.tsx`：
```tsx
// ModelConfigEditor.tsx (源码现状)
<section className={`${styles.modelsDetail} models-detail`}>
  <div className={`${styles.mrdBody} mrd-body`}>
    {/* 1. 服务商头 */}
    <ProfileHeader ... />
    {/* 2. 凭证输入（custom 时） */}
    <ProviderProfileForm ... />
    {/* 3. 模型列表头（搜索过滤 + 扫描 + 新增按钮） */}
    <ModelListHeader ... />
    {/* 4. 手动添加抽屉 */}
    {mc.manualOpen && <ManualAddForm ... />}
    {/* 5. 模型条目列表 */}
    <ModelList ... />
  </div>
</section>
```
而在 `ModelsSettingsTab.module.css` 中：
- `styles.mrdBody` **根本没有定义任何 CSS 类**（未声明规则），退化为无样式的标准 block。
- `styles.mrdModelList` 只是一个平铺的 `display: flex; flex-direction: column;`。
- 整个右栏唯一的滚动容器就是最外层的 `.modelsDetail`。

#### 导致的交互体验崩塌
1. **工具栏随列表滚走（Header Loss）**：当服务商有数十个模型（如 OpenAI 或本地 Ollama 扫描出 30+ 模型）时，用户往下一滚，顶部的 `ModelListHeader`（包含搜索框、扫描模型、添加模型按钮）被直接滚出了视野。用户想要搜索过滤时，必须先费力向上滚回顶部。
2. **列表缺乏独立边界**：模型列表没有独立的 `overflow-y: auto` 和 `overscroll-behavior: contain` 保护，滚轮事件直接冲撞外层。
3. **合成层隔离缺失**：列表项频繁重绘（例如单项展开配置面板 `ModelConfigPanel`）时，导致整个 `modelsDetail` 甚至外层页面触发重排重绘。

## 三、架构解耦与弹性重构总纲（Non-Retreat Architectural Solution）

基于反退避与架构净收敛原则，我们拒绝任何“在 wheel 事件里用 setTimeout 防抖”、“监听坐标做偏移量补偿”等打补丁作弊行为，从根本上建立 **“四层立体隔离防线”**：

```
┌───────────────────────────────────────────────────────────────────────────────────────┐
│ 立体防御体系架构图                                                                    │
│                                                                                       │
│  [防线 1：外层视口刚性锚定]                                                           │
│  .coverContent[data-settings-tab="models"]                                            │
│   ├── overflow: hidden; (从渲染树中物理抹除外层 scrollport，杜绝任何外层滑动可能)    │
│   └── display: flex; flex-direction: column;                                          │
│                                                                                       │
│  [防线 2：Flex 弹性链 100% 贯通 (SSOT)]                                                │
│  SettingsPage.fillHeight ──> SettingsPageBody ──> modelsSplit                         │
│   ├── 标题与默认模型区: flex-shrink: 0; (牢固钉在顶部)                                │
│   └── modelsSplit: flex: 1 1 0; min-height: 0; height: auto; (零魔术数字，精准吃满空间)│
│                                                                                       │
│  [防线 3：内层三段式独立视口]                                                         │
│  modelsDetail (右侧面板)                                                              │
│   ├── Header Area (ProfileHeader / KeyForm / SearchHeader): flex-shrink: 0; (固定)    │
│   └── mrdModelListScroll (全新独立模型滚动视口):                                      │
│        ├── flex: 1 1 0; min-height: 0; overflow-y: auto;                              │
│        ├── overscroll-behavior: contain; (硬件合成层阻断链式传递)                     │
│        └── scrollbar-gutter: stable;                                                  │
│                                                                                       │
│  [防线 4：事件流向物理阻断守卫]                                                       │
│   ├── DOM/React 层: ModelList.onWheel -> e.stopPropagation() (阻止合成事件冒泡)       │
│   └── Root 层: handleRootWheel 审计清理，增加 Tab 白名单守卫，封杀 JS 篡改 scrollTop   │
└───────────────────────────────────────────────────────────────────────────────────────┘
```

## 四、精确重构代码方案（Implementation Specifications）

### 4.1 `SettingsPanel.module.css`：外层视口锁定
针对 `models` 标签页，彻底消除外层 `.coverContent` 的滚动能力，使其退化为纯净的弹性承载容器：

```css
/* apps/crish-desktop/src/components/settings/SettingsPanel.module.css */

/* 既有规则保持不变 */
.coverContent {
  flex: 1;
  min-width: 0;
  min-height: 0;
  height: 100%;
  margin: 0;
  border-radius: 0;
  border: none;
  box-shadow: none;
  padding: 24px 32px 32px;
  display: flex;
  flex-direction: column;
  gap: var(--space-3_5, 14px);
  position: relative;
  background: var(--bg-elevated, var(--bg-card, hsl(0 0% 100%)));
  overflow-y: auto;
  overflow-x: hidden;
  overscroll-behavior: auto;
  contain: strict;
  align-items: stretch;
}

/* ─────────────────────────────────────────────────────────────
 * 【新增】工作区视口型 Tab 强约束（模型管理页）：
 * 1. overflow: hidden 抹除外层 scrollport，从底层阻止“默认模型”被滚上去
 * 2. padding-bottom 调整为 24px，收口底部多余空白
 * ───────────────────────────────────────────────────────────── */
.coverContent[data-settings-tab="models"] {
  overflow: hidden;
  overscroll-behavior: none;
  padding: 20px 32px 24px;
}
```

---

### 4.2 `SettingsPanel.tsx`：`handleRootWheel` 逻辑审计与安全加固
修复 `handleRootWheel` 的逻辑缺陷，增加 Tab 白名单豁免与内边距判定修复：

```tsx
// apps/crish-desktop/src/components/settings/SettingsPanel.tsx

  const handleRootWheel = (e: React.WheelEvent) => {
    // 【关键阻断 1】：当激活 tab 为 models 等全屏固定视口时，严禁以任何形式干预滚动
    if (safeActiveTab === 'models') {
      return;
    }

    if (contentAreaRef.current) {
      const target = e.target as HTMLElement;

      // 文本输入框与代码块由其自身滚动，不冒泡干预
      if (
        target.closest('textarea') ||
        target.closest('pre') ||
        target.closest('select')
      ) {
        return;
      }

      // 【关键阻断 2】：修复 target === contentAreaRef.current 导致双倍速滚动的缺陷
      // 只要 target 属于 contentAreaRef.current（包括自身及其任意子元素），
      // 就由浏览器原生滚动机制接管，JS 不得重复累加 scrollTop！
      if (contentAreaRef.current.contains(target)) {
        return;
      }

      // 仅当用户在侧栏空白处、顶栏拖拽空白处滚动时，才辅助滚动内容区
      contentAreaRef.current.scrollTop += e.deltaY;
    }
  };
```

> **架构净收敛审查**：经评估，`handleRootWheel` 的存在主要是为了让用户在顶部 36px 的拖拽栏空白处偶尔能滚动物料区。在 `models` 标签页下，该行为必须硬性阻断，确保零副作用。

## 五、响应式与极端边界防护（Edge Cases & Degradation Resilience）

在桌面客户端中，用户的窗口尺寸可能被随意缩放。本方案对各种极端几何场景进行了严密闭环：

### 5.1 极限小高度视口退化（窗口高度 < 500px）
- **现象**：当用户把设置窗口拉到极扁（例如高仅 450px）时，标题（36px）+ 默认模型卡片（84px）+ 搜索栏（36px）已占用了约 200px。
- **自适应行为**：
  - 由于我们删除了硬编码的 `min-height: 420px` 和 `calc(100vh - 220px)`，`modelsSplit` 与 `mrdModelListScroll` 均配置了 `min-height: 0`。
  - 模型列表视口会自动弹性压缩至约 150px~200px。
  - 内部 `mrdModelListScroll` 会即时激活滚动条，用户依然可以在有限的小视口内平滑浏览每一个模型，**外层结构依然岿然不动**，卡片绝不上移。

### 5.2 列表条目极少（0~1 个模型）
- **现象**：新添加的服务商只有 1 个模型，或搜索过滤后仅留 1 项。
- **自适应行为**：
  - `mrdModelListScroll` 内部无滚动条。
  - 用户在右侧区域任意滚动滚轮：
    - `overscroll-behavior: contain` 阻断了浏览器原生滚动链；
    - `.coverContent[data-settings-tab="models"]` 的 `overflow: hidden` 抹除了外层滚动能力；
    - `onWheel={e => e.stopPropagation()}` 阻断了 JS 事件冒泡。
  - **三重保险确保：界面 100% 纹丝不动，彻底消灭“无模型时页面乱滑”的怪异感！**

### 5.3 列表条目海量（100+ 模型）与无阻尼滑轮冲击
- **现象**：用户使用罗技 MX Master 开启无阻尼模式快速甩动滚轮，或在 MacBook 触控板上双指剧烈甩动。
- **自适应行为**：
  - 滚轮产生的巨大惯性动量在抵达 `mrdModelListScroll` 底部边界时，直接被 Compositor 线程的 `overscroll-behavior: contain` 吸收消费，不会泄露给任何父级 DOM。
  - 搜索工具栏、默认模型卡片、左侧服务商列表全部零位移。

## 七、反过度设计与架构净收敛审查（Anti-Overengineering Audit）

根据仓库根目录 `ANTI_OVERENGINEERING_GUARDRAILS.md`，对本方案进行严格红线核验：

1. **严禁引入复杂滚轮物理模拟器（No Smooth-Scroll Physics Engine）**：
   - 坚决不用任何第三方 JS 滚轮平滑库（如 smooth-scrollbar、lenis 等）。
   - 100% 采用浏览器原生 `overflow-y: auto` + `overscroll-behavior: contain`，由浏览器硬件加速（GPU Compositor）原生处理。
2. **严禁使用 ResizeObserver 进行 JS 动态高度测算补偿**：
   - 坚决不写 `window.addEventListener('resize', ...)` 监听计算高度。
   - 100% 依赖标准 CSS Flexbox `flex: 1 1 0; min-height: 0;` 弹性流，计算复杂度为 $O(1)$。
3. **严禁修改其他非相关 Tab 的基础契约**：
   - 通过 `[data-settings-tab="models"]` 精准限定视口模式，对其他常规设置 Tab 零侵入、零污染。
4. **净收敛收益**：
   - 删除了混乱的 `calc(100vh - 220px)` 与 `max(480px, ...)` 脏代码。
   - 修复了 `handleRootWheel` 中潜藏的 2x 双倍速狂飙 bug。
   - 使模型列表 Header 在长列表浏览时常驻可见，大幅提升产品级交互品质。
