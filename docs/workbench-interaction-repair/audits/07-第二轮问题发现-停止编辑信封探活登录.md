## 二、逐问题根因穿透

### P1 停止生成（发送后停止失灵）

**表象**：点击发送后，停止按钮行为"好像有问题"。

**根因链（代码实证）**：

1. 前端按钮面：`ComposerSendControls.tsx:14-19` 默认停止 = L2 协作停止（Tooltip「停止生成（协作停止）」），Shift+点击 / 长按 550ms 才升级 L3 强制取消（带确认弹窗）。`isProcessing` 时渲染「排队」+ 方形停止按钮（`ComposerSendControls.tsx:159-175`）。
2. 前端停止链：`useStreamCallbacks.ts:218-354` `finalizeStopGeneration` —— **本地立即收口**（删流句柄、消息标 completed、清 runtime status、`settleStaleSessionProcessingMessages` 清扫 queued/processing），随后 `dispatchStreamStopCancel`（`streamStop.ts:71-96`）→ `createStreamCancel`（`streamFinishControl.ts:69-98`）→ L2 `runControl` 派发。
3. 引擎侧 L2 语义：`run_launch.rs:1717-1728` —— `cooperative_stop` 仅向 ControlBus 投递意图 + 置会话级 `user_stopped`，**"等安全点收场"**。
4. **关键断层**：安全点检查只存在于 streaming handler 起始（`session-loop/src/loop/handlers/streaming.rs:52-56`）与"stream 结束且消息已落盘"之后（同文件头注释步骤 6）。**流式消费循环内部没有任何 L2 检查点** → 长文本生成中点停止，引擎会把当前流完整读完、提交全文、落库，才在下一个安全点结束。
5. 后果三连：
   - 前端已"停止"，引擎仍在烧 token 直至 turn 结束；
   - 前端订阅已 cleanup，引擎后到的 `message-end`（全文）不再投影到当前界面；
   - **持久层已落全文** → 重新进入会话 / 重新水合后，"已停止"的消息以全文复活（待真机复测确认水合路径，代码层面成立）。
6. 对照组：L3 `force_cancel` 走 `abort_signal`，流中 abort 是支持的且"内容保留"（`streaming.rs` 头注释：「流中 abort（信号已置位）→ 安全点 ABORT 收场（aborted，内容保留）」）。

**系统性修复方向**：

- 在流消费循环加 **O(1) 协作停止检查点**：ControlBus 的 L2 意图镜像为 `AtomicBool`（`request_cooperative_stop` 时同步置位），逐 chunk 检查；触发即 break → 提交已收到的部分文本 → 以 `stopped` 收场。禁止逐 chunk 抢 Mutex。L2 语义不变（优雅、保内容、不触发自动续轮），停止延迟从「整个 turn」降到「一个 chunk」。
- 停止后收口对账：引擎安全点终态事件与前端"已停止"投影合并策略单一化（保留已展示部分文本为真值，丢弃后到增量），杜绝复活。
- 默认停止仍为 L2（语义正确），修复后即时生效；L3 保持 Shift/长按 + 确认，不动。

**验收断言**：流式生成 2 秒后点停止，≤1 个 chunk 延迟后 UI 停止；引擎侧请求在 ≤500ms 内终止（服务器日志可证）；已展示部分文本入库；重进会话无全文复活；token 无持续消耗。

### P2 编辑消息重发（「已清空…并重新排队」观感）

**根因链**：

1. 编辑预填：`ChatCard.tsx:75-101` `handleStartEditMessage` 用 `targetMsg.text` 预填——该字段是**含信封的全文**（见 P3），编辑框先天污染（截图 2 实证）。
2. 提交链：`ChatCard.tsx:109-118` → `useChatHandlers.ts:239-283` `handleEditMessageAndResend`：
   - 先 `handleStopGeneration()`（**借用停止链**）→ 有 processing/queued 时弹停止 fallback toast **「已停止任务并清空排队。」**（`useStreamCallbacks.ts:263`）——这是用户看到的「已清空…」前半句唯一来源（全库唯一含"清空"的 toast）；
   - `core_session_retract`（`retraction_commands.rs:80-152`）：L3 force_cancel + 会话冻结 + `timeline-truncate` + 写类工具文件回滚（S10b）+ SQLite `truncate_session_messages_after`——**从目标消息起整段截断**（fork 语义）；
   - `withdrawMessage` + `handleSendChat` 重发。
3. 视觉放大器：`useUserBubbleEntrance.ts:34-49` —— 重放重建的行拥有新 id/新 timestamp，全部命中入场动画窗口 → 时间线大面积"删光重播"观感。

**系统性修复方向**：

- 编辑重发成为**一等交互**：不再借用停止的用户可见语义——专用轻提示（或仅发丝线），严禁弹「已停止任务并清空排队。」。
- 时间线投影身份保留：truncate 重放只对被摘除后缀做精确卸载，**前缀行不得重播入场动画**（保留 DOM/消息 id 身份；动画只授予真正新增的行）。
- 语义对齐（建议，需产品拍板）：删除消息已明确「仅精确摘除目标节点及其派生节点，后续排队追问完整保留」（`sessionMessageActionsCore.ts:112`），而编辑是"整段截断"——两个相近交互语义分裂。统一为：编辑 = fork 截断重发（保持现语义）+ 被截断的后续 queued 用户消息可见地重新排队，消除"删除保后续、编辑清后续"的矛盾。
- 保留现有文件回滚能力（S10b 已覆盖）。

**验收断言**：编辑中间消息后，前缀消息无任何视觉抖动/动画；无停止类 toast；被截断后缀精确消失；新消息以正常流式进入；DB 与事件流无孤儿残留。

### P3 模型切换通知混入用户消息（信封 SSOT 违规）

**根因链**：

1. **信封在存储层落盘**——三处合并点双写：
   - 前端 A：`useSlashSend.ts:228`；
   - 前端 B：`slashSendQueueHelper.ts:164`；
   - 后端 C：`run_launch.rs:1491-1498`（`contains` 幂等保护）。
   合并结果 `[用户输入]\n…\n\n[系统环境上下文]\n…` **就是持久化的消息正文**（message-start 事件 / DB / 时间线）。
2. 气泡第二条呈现路径：`ChatUserMessageRow.tsx:45-75` `parseStructuredUserText` 反解析信封，`:488-506` 渲染 cpu 图标信封附段（截图 1 实证）——**违反 §21**：系统状态切换的唯一合法呈现 = `ContextStateNotice` 发丝线（组件已存在：`chat-message/ContextStateNotice.tsx`，经 `ProcessItemRenderer.tsx:182` 挂载，数据源 `MessageContextInjection`）。
3. 编辑污染：`ChatCard.tsx:78` 预填 `targetMsg.text`（= 信封全文）。
4. 附带违规：`ChatUserMessageRow.tsx:467` `<span aria-hidden="true">⏰</span>`——触发源徽标使用 Emoji，直接违反 §21「全系统杜绝 Emoji」。

**系统性修复方向（单一真理路径）**：

- **存储层**：消息正文只存用户原始输入；`context_state` 结构化旁挂（metadata 字段或独立事件），不进 text。
- **合并点唯一化**：删除前端两处拼装；保留 Rust `run_launch` 在**请求组装期**合并（仅 LLM 可见，不入库、不投影）。需核实并确保 `run_launch.rs:1491` 合并对象是请求正文而非落库正文。
- **呈现唯一化**：删除 `ChatUserMessageRow` 信封附段渲染；状态切换只走 ContextStateNotice 发丝线。
- **存量数据**：二选一——(a) 一次性数据迁移（正文拆成 text + contextState，删除解析器，符合「非必要不兼容」）；(b) 保留 `parseStructuredUserText` 作只读视图兼容（渲染剥离、编辑提交洗白）。**推荐 (a)**。
- ⏰ → Lucide 图标（`AppIcon`）。

**验收断言**：新消息正文不含信封标记；气泡无信封附段；编辑框只见用户文本；切换模型后发丝线出现且不堆叠；历史会话渲染不回归；`check:input-guard` 与 §21 守护单测全绿。

### P4 供应商探活失败（已实测定位）

**实测记录（2026-10-29 16:19–16:26）**：

| 步骤 | 结果 |
|------|------|
| `config_secret_has(custom-mv5z0jdf)`（真机 IPC） | `hasKey: true`，尾号 `91a4` —— DPAPI blob 在 `%APPDATA%\Roaming\Crish\AgentWorkbench\secrets\75e1ba27-….dpapi` |
| `provider_probe_ping`（真机 IPC，真实探活） | `{"ok":false,"error":"服务端错误（HTTP Some(503)）"}`，1.3s 失败 |
| `curl POST https://api.flowbit.me/v1/chat/completions`（真实密钥，`gpt-5.6-luna`） | **HTTP 200**，正常回复 "OK" |
| 同上，`gpt-6-luna` | **HTTP 503** `{"error":{"message":"Service temporarily unavailable"}}` |
| `GET /v1/models`（真实密钥） | HTTP 200，列出 5 个模型（gpt-5.6-luna/sol/terra、gpt-6-astra、gpt-6-luna） |
| 服务器 SSH（aliyun-korea-api 100.77.75.39） | nginx:443 → docker（sub2api / zo2api-proxy / flowbit-auth + pg/redis/sing-box） |
| sub2api 日志实锤 | `account_select_failed error="no available OpenAI accounts supporting model: gpt-6-luna (pool=9, filtered: channel_upstream_restricted=3 model_not_supported=6)"` → 503 |

**结论**：应用侧配置、DPAPI 密钥、网络链路**全部正常**；失败根因是**中转站 `gpt-6-luna` 模型当前无可用上游账号**（3 个通道上游受限 + 6 个账号不支持该模型）。`gpt-5.6-luna` 实测可用（虽经 429 换号 failover 但成功）。用户侧解法：在服务器 sub2api 管理面修复 `gpt-6-luna` 通道，或先用 `gpt-5.6-luna`。

**客户端仍值得收口的三个架构隐患**（非本次失败直接原因）：

1. **URL 归一化缺通用 `/v1` 规则**：`wire_protocol.rs:188-198` 对 OpenAiChat 只特判 `sensenova.cn` / `openai.com`，通用中转站（如本例 `https://api.flowbit.me/`）被拼成 `/chat/completions`（少 `/v1`）。本站恰好兼容无版本路径，多数站会 404。改为「未含版本段即补 `/v1`」的通用归一，删除域名特判。
2. **探活硬编码 `.no_proxy()`**：`probe.rs:137、189-196` 探活客户端显式绕过系统代理，与引擎主链路（`engine_provider/connection.rs:59-78`，默认跟随环境代理）行为分裂。本机依赖 TUN/代理出网时探活与实连行为可能不一致。统一策略：默认跟随系统代理解析，`provider.proxy_url` 显式配置优先，行为写入探活诊断。
3. **探活错误透传不足**：引擎只报「服务端错误（HTTP Some(503)）」，响应体（含中转站具体原因）被吞。应解析 body 摘要透出（如"该模型无可用上游通道"），错误分类区分 401（密钥）/ 404（路径）/ 503（上游）。

**并行会话对齐提醒**：工作区未提交 diffs（`model_store.rs` 的 `unwrap_or_default` + `headers.rs` 空 key 跳过 Authorization）正被并行会话以更精确的 `is_loopback_or_private_base_url`（loopback/内网才放行免密）方案取代——收口时二选一，禁止双重语义并存。

### P5 账户登录入口

**根因链**：

1. 主界面头像点击 → `openAccount()` = `setAccountView('overview') + openSettings('profile')`（`UserProfileCard.tsx:60-63`）——固定跳设置，未登录也不弹登录。
2. 登录弹窗 `AccountCenterDialog` 由 `accountUiStore.loginOpen` 驱动（`accountUiStore.ts:20-23`），但**只挂载在设置账户分区** `AccountAuthCard.tsx:67` 内——主界面 `openLogin()` 无挂载点，弹不出来。
3. 登录按钮：`AccountAuthCard.tsx:55-62` 用 `Button variant="unstyled"` + 私有 class `controls.primary`（`accountControls.module.css:88-101`，走 `--account-action` 独立体系、纯黑底）——绕开全局原子组件与设计 token，观感"硬编码"。

**系统性修复方向**：

- 未登录时主界面头像点击 = `openLogin()` 直接弹登录弹窗；已登录保持跳账户概览。名字点击快捷菜单不动。
- `AccountCenterDialog` 提升到应用根（或 Sidebar 层）**单实例挂载**，设置分区与主界面共用，消灭双挂载点。
- 登录按钮收敛到全局原子 `Button`（primary variant + 设计 token）；account 模块私有按钮体系中与全局重复的定义清退。遵守 §12/§13/§19/§20（无原生 title、克制焦点 3%–10%、四态、圆角 5 档）。
- 设置里保留登录按钮（用户裁决：设置里可以有）。

**验收断言**：未登录点主界面头像直接弹登录弹窗（真机验收）；登录成功后头像/名字/设置三处状态同步；按钮视觉走全局 token；设置分区登录入口保留。

## 三、跨问题架构观察

1. **配置路径双根**：`models.yaml` 在 `~/.conex/`，DPAPI secrets 在 `%APPDATA%\Roaming\Crish\AgentWorkbench\secrets\`（`config/persistence.rs:10-27` 两套解析逻辑）。排查时极易误判"密钥丢失"（本次排查即先入坑）。建议统一单一 config root + 一次性迁移。

3. **测试缺口**：停止链路缺「流中 L2 即时性」与「复活防护」测试；编辑重发缺「前缀无动画/后缀精确卸载」测试；信封迁移需数据迁移测试；探活缺「错误体透传」测试。
