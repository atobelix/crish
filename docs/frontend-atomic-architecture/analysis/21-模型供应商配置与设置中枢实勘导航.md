## 一、执行摘要与实勘全景概览

### 1.1 战役定位与勘察使命

在 Conex / Crish 桌面客户端（Rust 内核 + Tauri IPC + WebView2 React 18 前端架构）中，**设置中枢（Settings Hub）**与**模型供应商配置中枢（Model Provider Center）**是整个桌面客户端控制面与能力面的核心总枢纽：
1. **控制面核心**：设置中枢承担了账户认证、外观皮肤、通用交互偏好、快捷键热键映射、多端设备配对、工作流与定时任务调度、系统权限与安全白名单、状态诊断等全站绝大多数全局配置的加载、呈现与持久化；
2. **能力面源泉**：模型配置中枢则是 AI 生产力运转的发动机。无论是会话上下文装配、Agent 思维链流式生成、代码补全、工具调用还是多模态视觉理解，全部依赖于模型配置中枢所维护的服务商凭证（Base URL、API Key）、可用模型列表、能力矩阵（Tools / Image / Video / Reasoning）、调用协议（OpenAI Chat / OpenAI Responses / Anthropic Messages）以及 Token 定价数据。

作为前端原子化组件库战役的任务书 21，本实勘的核心使命是对 `apps/crish-desktop/src/components/settings/` 与 `apps/crish-desktop/src/components/settings-models/` 下的**全量 113 个文件（包含源码、样式表、测试用例与辅助库）展开代码级、逐行深度的透视实勘**。以客观事实为基石，深入揭示模型 CRUD 状态机、API Key 安全管道、延迟测速机制、计费展示模型、深浅模式表单失控、7px 奇数圆角、野生 Checkbox 以及温度/上下文滑块断层，为后续构建全站统一的原子化表单与设置架构奠定无可辩驳的证据链。

### 1.4 现状核心断层与架构痛点总评

经过对全部 113 个文件的深度实勘，设置中枢与模型配置体系展现出高度完备的业务功能（如同厂商自愈降级、YAML 双层高亮、安全三角多级级联、Token 双币种计费等），但在**前端原子化规范、样式一致性与无障碍交互**上，暴露出了八大显著的结构性断层：

1. **深浅表单严重混乱（硬编码纯白背景）**：在 `ManualAddForm.tsx`、`PriceConfigModal.module.css`、`ScanResultsModal.module.css` 等多处，表单输入框的 `background` 被硬编码为 `#ffffff`。当用户切换至深色模式（Dark Theme）时，这些输入框呈现出刺眼的白底，与深色容器严重脱节，且文字与边框出现严重对比度失常；
2. **深色模式手工补丁与光学下沉**：由于缺乏统一的卡片与面板背景 Token，`ModelsSettingsTab.module.css` 中充斥着 `:global(html[data-theme='dark']) .modelConfigPanel`、`:global(html[data-theme='dark']) .modelsRail` 等手工通过 `color-mix` 补偿的 CSS 规则，维护成本极高且极易漏配；
3. **奇数圆角（7px）历史残留广泛**：在 `SettingsUI.module.css`（L148, L202, L226）、`ModelsSettingsTab.module.css`（L198, L410, L530, L560）中，多处输入框、色块选择器、状态按钮仍在使用 `var(--button-radius, 7px)`，严重违反了全仓规范的 8px/12px 系统圆角网格契约；
4. **野生 Checkbox（复选框）重复造轮子**：全站通用组件库 `ui/` 缺失标准 `Checkbox` 原语，导致 `ScanResultsModal.tsx`（L224-229）不得不使用裸 `div` 配合 `styles.customCheckbox` 与 `Lucide.Check` 图标手绘复选框，不仅无原生 `:focus-visible` 键盘聚焦环，在深色模式下更因硬编码 `background: #ffffff` 导致未选中态呈现为白底方块；
5. **模型参数控制维度断层（滑块缺失与文本退化）**：在通用设置 `SettingsSchemaRenderer` 中已经存在基于 `ui/Slider` 的 `type: 'range'` 驱动机制，但在 `ModelConfigPanel.tsx` 中，“上下文长度 (contextLength)”却退化为没有任何范围约束的裸文本 `<Input placeholder="如 128000" />`；而像“温度 (temperature, 0.0~2.0)”、“核采样 (top_p, 0.0~1.0)”等大模型核心生成参数，在整个模型管理 UI 中完全没有暴露，用户无法进行直观的滑动微调；

### 3.2 本地变更标记与外部失效广播防御：runAsLocalMutation 与 localMutationRef

当 Conex 桌面应用运行于多窗口或受到后台 Rust 守护进程同步时，经常会触发全仓 UI 事件 `'profiles-changed'`。

#### 1. 冲突问题
若当前用户正在设置页面中手填 API Key 或编辑模型参数（尚未点击保存），此时若外部触发 `'profiles-changed'` 事件直接粗暴调用 `refresh()` 重新拉取磁盘配置，用户刚刚输入的内容将被无情冲掉（静默覆盖灾难）。

#### 2. 解决方案架构
在 `useModelProfilesState.ts`（L86-166）中，实现了精密的**本地变更保护机制与外部失效广播防御**：
```typescript
// useModelProfilesState.ts:91-123
const localMutationRef = useRef(false);
const externalChangeStateRef = useRef({
  profileId: '',
  configOpenId: null as string | null,
  hasUnsaved: false,
});

useEffect(() => {
  externalChangeStateRef.current = {
    profileId: selectedId,
    configOpenId,
    hasUnsaved:
      cfgDraft != null ||
      keyDraft.trim() !== '' ||
      editingName ||
      nameDraft.trim() !== '',
  };
}, [selectedId, configOpenId, cfgDraft, keyDraft, editingName, nameDraft]);

/** 本地写入包装器：标记执行区间，屏蔽自己触发的 profiles-changed 事件 */
const runAsLocalMutation = useCallback(
  async <T>(fn: () => Promise<T> | T): Promise<T> => {
    localMutationRef.current = true;
    try {
      return await fn();
    } finally {
      localMutationRef.current = false;
    }
  },
  []
);
```
在事件监听器中：
```typescript
// useModelProfilesState.ts:148-166
useEffect(() => {
  return onUiEvent('profiles-changed', () => {
    // 1. 如果是自己引发的本地写入落盘，直接忽略
    if (localMutationRef.current) return;

    const st = externalChangeStateRef.current;

    if (st.hasUnsaved) {

      if (st.configOpenId && st.profileId) {

          settingsObjectId(st.profileId, st.configOpenId),
          'external'
        );
      }
      return;
    }
    // 3. 无未保存草稿：安全重载最新配置
    refresh();
  });
}, [refresh, notify]);
```

### 3.7 审计 1 铁律落地：resolveActiveModelAfterMetaChange 同厂商自愈降级与置空引导

在模型中枢的设计中，全仓强制执行**“审计 1（Audit 1）：严禁跨厂商隐式静默切模”**铁律。

在 [`ModelsSettingsTab.tsx`](file:///c:/Software/conex/apps/crish-desktop/src/components/settings-models/ModelsSettingsTab.tsx)（L59-89）中，`resolveActiveModelAfterMetaChange` 严格落实了该状态机规则：
```typescript
// ModelsSettingsTab.tsx:59-89
export function resolveActiveModelAfterMetaChange(
  currentActive: { profileId: string; model: string } | null,
  profiles: readonly ProviderProfile[],
  isModelEnabled: (profileId: string, model: string) => boolean
): { nextActive: { profileId: string; model: string } | null; selfHealed: boolean } {
  if (!currentActive || !currentActive.profileId || !currentActive.model) {
    return { nextActive: currentActive, selfHealed: false };
  }

  // 1. 若当前活动模型仍处于启用态，无需自愈
  if (isModelEnabled(currentActive.profileId, currentActive.model)) {
    return { nextActive: currentActive, selfHealed: false };
  }

  // 2. 当前活动模型已被停用！仅在【同服务商】内部寻找下一个已启用的模型
  const currentProfile = profiles.find((p) => p.id === currentActive.profileId);
  const sameProviderNext = currentProfile?.models.find((m) => {
    if (m === currentActive.model) return false;
    return isModelEnabled(currentActive.profileId, m);
  });

  if (sameProviderNext) {
    return {
      nextActive: { profileId: currentActive.profileId, model: sameProviderNext },
      selfHealed: true,
    };
  }

  // 3. 该服务商已无任何可用模型 -> 严禁跨厂商切换！直接置空以引导手动选择
  return { nextActive: null, selfHealed: true };
}
```
**铁律执行价值**：如果用户正在使用 OpenAI 的 `gpt-4o`，当用户在模型列表中把 `gpt-4o` 关闭（停用）时，系统绝不允许悄悄把当前模型切换到 DeepSeek 或 Anthropic；系统只允许自愈降级到同厂商下一个可用模型（如 `gpt-4o-mini`）；如果 OpenAI 下所有模型全被用户停用，系统宁可将活动模型显式置空并弹窗警告，也绝对不执行任何越权跨服务商跳变！

### 4.2 API Key 安全输入原子：variant="password" 与脱敏占位符规范

在安全输入与回显设计上，表单遵循了工业级安全规范：
1. **暗文保护（`variant="password"`）**：输入框采用密码样式掩盖，输入时光标处即时掩蔽为圆点，防止肩窥（Shoulder Surfing）；
2. **已配置状态脱敏（Masked Placeholder）**：当检测到当前服务商本地钥匙串中已经保存过 Key（`hasKeySelected === true`）时，输入框的 `placeholder` 强制显示为 20 位固定圆点脱敏串：`••••••••••••••••••••`；
3. **真实密钥零回显**：前端界面**绝对不把已保存的 API Key 明文从后端读回填入 `value`**。`value` 仅绑定用户当前输入的未保存暂存草稿 `keyDraft`。只要用户未开始重新输入，输入框始终处于空白状态（展示脱敏占位符），杜绝任何通过 DOM 检查、控制台 `input.value` 抓取明文密钥的安全漏洞。

---

### 4.3 零明文外泄与内存生命周期控制

在 `useModelProfilesState.ts` 中，API Key 草稿的生命周期被严格控制在最小化窗口：
- 切换不同服务商时：立即触发 `setKeyDraft('')` 清空内存；
- 保存操作完成后：立即触发 `setKeyDraft('')` 清空内存；
- 窗口最小化或卸载时：草稿不写入任何持久化存储（如 localStorage 或 sessionStorage），完全驻留在易失性组件状态中。

当用户触发 `saveKey` 时，数据流向如下：

[React Frontend: Input]

## 十、未来设置中心与模型中枢原子化重构方案建议

基于本次实勘发现的全部断层、样式异味与交互缺陷，前端原子化架构战役必须对设置中枢与模型管理体系实施针对性的**无损重构与收敛升级**：

### 10.1 统一表单原语族设计规范（Form / Field / Control / Message）

当前设置中心普遍通过散乱的 `label` 嵌套 `span` 与 `Input`，且大量通过 `style={{ ... }}` 覆盖样式。
必须在 `components/ui/` 中建立统一的**原子化表单原语族（Form Primitives）**：
```
<FormRoot>
  <FormField name="contextLength">
    <FormLabel>上下文长度</FormLabel>
    <FormControl>
      <DualSliderInput min={4000} max={2000000} step={1000} unit="Tokens" />
    </FormControl>
    <FormDescription>模型单次对话允许容纳的最大上下文窗口容量</FormDescription>
    <FormMessage />
  </FormField>
</FormRoot>
```
1. **语义解耦**：彻底剥离组件层散落的手写 `label` 与 `span`，由 `FormField` 自动注入 `id`、`aria-labelledby`、`aria-describedby` 与 `aria-invalid`；
2. **布局规整**：统一控制 Label 处于左侧对齐还是顶部垂直堆叠，消除各 Tab 页面边距与间距的 Ad-hoc 差异。

---

### 10.2 全量迁移至标准原子组件：Checkbox、Slider、Select、Switch、IconButton

1. **废黜野生 Checkbox**：
   - 立即在 `components/ui/Checkbox/` 建立符合 WAI-ARIA 规范的标准 `Checkbox` 原语；
   - 全量替换 `ScanResultsModal.tsx` 中的 `customCheckbox` 手绘结构，支持纯正 `:focus-visible` 软性焦点环、键盘空格切换、indeterminate 半选态与 Design Tokens 勾选色；
2. **推进 Slider 连续滑块重构**：
   - 将 `ModelConfigPanel.tsx` 中的“上下文长度”与后续新增的“温度”、“Top-P”全面升级为联动滑块；
   - 刻度吸附采用对数尺度（Logarithmic Scale），便于在 4K 到 2M 的超大跨度区间内进行平滑无级拖拽；
3. **彻底替换行内按钮为 IconButton**：
   - 将 `ModelListHeader.tsx`、`ModelList.tsx`、`ProfileHeader.tsx` 中大量手写 `style={{ height: '28px', width: '28px', padding: 0 }}` 的 `<Button>` 全面替换为标准 `<IconButton size="sm" variant="ghost">`，确保 40px 安全点击热区（`::after`）与软焦点环全仓一致。

### 10.3 模型参数配置面板 Schema 化与通用抽屉解耦（ModelConfigSchema）

借鉴 `SettingsSchemaRenderer` 的成功经验，模型行展开配置抽屉应全面过渡至声明式 Schema：
```typescript
export interface ModelConfigSchema {
  displayName: { type: 'string'; title: '展示名称' };
  contextLength: { type: 'dual-range'; title: '上下文长度'; min: 4096; max: 2048000; scale: 'log' };

  capabilities: { type: 'cap-matrix'; title: '能力矩阵' };
}
```
通过驱动引擎一次性渲染抽屉面板，彻底消除手写 Grid、手写 Label 与手写行内样式的混乱状态。
