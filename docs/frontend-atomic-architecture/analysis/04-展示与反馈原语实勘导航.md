## 一、实勘概述与战役目标全景

### 1.1 战役背景与实勘使命

在前端现代化与原子化设计系统（Atomic Design System）演进中，**展示类（Display Primitives）** 与 **状态反馈类（Feedback Primitives）** 原语构成了 UI 界面中最为高频、微观且关键的基础层级：
- **展示原语**：Badge（徽标）、Tag（标签）、Pill（胶囊药丸）、Avatar（头像）、Separator / Divider（分割线）；
- **反馈原语**：Toast（全局通知）、Skeleton（骨架屏占位）、Spinner / Loading（旋转加载器）。

然而在当前 `crish-desktop` 仓库的长期演进迭代中，展示与状态反馈原语陷入了**严重的碎片化割裂与“造轮子”孤岛现象**：
1. **组件库内冷清空置，业务层内私造泛滥**：公共组件库目录 `src/components/ui/` 中只提供了简陋的 `Badge`、孤立的 `SmartModelBadge` 以及与 Select 强绑定的伪 Separator；而业务组件（如 `agent-card`、`chat-card`、`chat-composer`、`settings-models`、`overview` 等）中却散落着大量自主手写的私有 badge、pill、divider、spinner、skeleton 与 avatar。
2. **先进机制被束之高阁（被遗忘的明珠）**：精心设计的 `SmartModelBadge` 尝试了纯 CSS 原生容器查询（`@container`）与无损缩写算法，却因自身布局几何缺陷及业务组件职责杂糅，在整个前端业务树中**零接线**，成为完全悬空的死代码。
3. **严重缺陷与空壳组件隐蔽潜伏**：如 `SelectContent.module.css` 中的 Separator 样式遗漏了 `border-top`，导致组件物理不可见；全局加载占位组件 `SkeletonFallback` 引用的 `.skel-shimmer` 样式在全局 CSS 中根本不存在，导致首屏 Suspense 骨架屏退化为完全透明的空 DOM。
4. **双轨架构与历史包袱滞留**：Toast 体系存在两套互不通气的实现（一套极简旧版 `ToastStack`，一套现代 3D 层叠 `ToastViewport`），导致旧代码长期作为无引用孤岛留在仓库中；行内还额外私造了 `DraftUndoToast`。
5. **中性黑白灰断层与杂色彩边散落**：违背 `AGENTS.md` §13（克制焦点与激活边框）与 §14（HSLA 色彩空间），硬编码十六进制色值（如 `#059669`, `#dc2626`, `#c2410c`, `#10b981`, `#555555` 等）、高对比度彩边与不一致的 9999px 药丸圆角在多个模块中随意使用。

### 1.3 核心失范总览（孤岛化、平替野蛮生长、死代码滞留、规范脱节）

从架构演进的角度审视，当前仓库在展示与反馈原语层面呈现出以下深层次病灶：
1. **“写完即被遗弃”的研发断层**：许多优秀的设计规范（如 4px 微圆角矩形 Badge、原生容器查询 SmartModelBadge、现代 3D Toast）在完成基础开发后，并未建立强制性的架构门禁与替换流水线，导致业务开发团队出于惯性或局部快速交付压力，继续在页面级 CSS 中就地写出大量的内联类名。
2. **缺乏原子与复合组件的边界分层**：
   - 试图在 Badge 中容纳 Chip 的删除交互（`onRemove`）；
   - 试图在 SmartModelBadge 中硬编码自封闭的 Tooltip 与胶囊外观，导致其无法嵌入 Dropdown Button 内部；
   - 将通用 Separator 限制为 Select 的私有切片，导致其他地方要用时“借用无门”。
3. **“看不见”的线上静默劣化**：
   - `SelectContent.module.css` 遗漏 `border-top`：肉眼极难在下拉菜单浅背景上迅速察觉，造成功能实际缺失；
   - `SkeletonFallback` 缺少样式：开发者误以为 Suspense 正在优雅过渡，实际上用户面对的是无反馈的白屏等待；
   - ToastStack 成为孤岛代码：测试还在继续运行，但生产环境早已换轨，形成虚假安全感。

  modelId,
  displayName,
  showDot = false,
  className = '',
  forceTier,
}) => {
  // Line 34-36: 模型缩写纯逻辑计算，返回包含 standard, compact, micro 三个纯文本字段的对象

    return abbreviateModel(modelId, { displayName });

  // Line 38-47: 构造悬停提示内容，遵循中性黑白灰与等宽字体排版

    return (
      <div style={{ display: 'flex', flexDirection: 'column', gap: 2 }}>

        </div>
      </div>
    );
  }, [abbr.standard, modelId]);

  // Line 49-71: 渲染外层容器查询宿主与胶囊药丸结构
  return (
    <div className={`${styles.badgeContainer} ${className}`.trim()}>
      <Tooltip content={tooltipContent} side="top" delayShow={200}>

### 2.3 原生容器查询（@container）机制深度解构与几何陷阱

#### 技术设想的先进性：
传统的前端自适应文本方案通常采用以下两类手段：
1. **JavaScript 轮询或 ResizeObserver 测距**：通过 `offsetWidth` 获取宽度，根据像素值动态 `setState` 切换缩写。该方案会触发强制同步布局（Layout Thrashing），引发严重的卡顿。
2. **纯 CSS `text-overflow: ellipsis`**：直接在末尾截断打点。但模型名通常关键特征在末尾（例如 `claude-3-5-sonnet-20241022` 如果截断为 `claude-3...`，用户完全分不清是 Sonnet 还是 Haiku）。

`SmartModelBadge` 提出的方案是：**利用辅音骨架抽脂算法（Consonant Skeleton）计算出 standard/compact/micro 三档纯文本，在 DOM 中同时挂载三个 span，再利用原生 CSS 容器查询（`@container`）在渲染引擎内部完成 O(1) 瞬时切换**。

#### 规范级几何计算陷阱（Containment Loop Hole）：
但在实测与深入 CSS 规范审计中，该组件暴露出一个极其严重的**盒模型几何死锁问题**：
1. **尺寸隔离原则（CSS Containment Level 3）**：
   当对 `.badgeContainer` 赋予 `container-type: inline-size` 时，规范强制要求该元素**建立内联轴尺寸隔离（Size Containment on Inline Axis）**。
   即：**容器在计算自身宽度时，必须完全无视其子元素（Descendants）的内容宽度！** 它的宽度必须且只能由外部环境推导出来。
2. **内联弹性盒的自相矛盾**：
   `.badgeContainer` 同时声明了 `display: inline-flex`。
   在正常的 CSS 布局流中，一个 `inline-flex` 元素的宽度是**由内容撑开的（Shrink-to-fit）**。
   但一旦加入了 `container-type: inline-size`，内容宽度被隔离屏蔽，而外部父容器又没有给这个内联元素显式指定宽度（如 `width: 100%` 或固定像素），那么根据规范，该元素在 inline 轴上的可用宽度**直接坍塌为 0px**（或其 min-content 默认值）！
3. **断点永久失效**：
   既然 `.badgeContainer` 的宽度坍塌为 0px，那么无论是 `min-width: 130px` 还是 `min-width: 220px`，都**永远不可能被触发**！
   结果就是：组件会一直死锁在默认的 `.microSpan`（显示为极简缩写，如 `DS4P`），无法随着空间变大而展开为 `DeepSeek V4 Pro`。
4. **强行定宽的破坏性**：
   如果使用者试图在外层给 `.badgeContainer` 加上 `width: 100%`，那么它就不再是一个紧贴文字的胶囊 Badge，而是会撑满整个父级块，导致父级 Flex 行内的其他按钮被挤压出屏幕或换行。

2. **复合交互容器冲突**：

3. **交付验收链路缺失**：
   - `SmartModelBadge` 作为一个实验性组件入库后，开发人员没有将其作为必须替换既有内联代码的刚性门禁，导致业务代码库形成了“两套相同的缩写算法逻辑、各自独立的 CSS 类名”的双重技术债务。

### 2.5 修复与归位方案建议

1. **分层解耦（Pure Display vs Dropdown Trigger）**：
   - 将 `SmartModelBadge` 改造为无副作用的自适应展示原语，支持通过 Props 接收外部容器名 `containerName`（默认为 `chatContainer` 或 `surfaceContainer`）；
   - 移除写死的内部 `<Tooltip>`，改为可选插槽或外部包裹；
   - 将 `ChatHeaderControls.tsx` 的内联三段式 span 清退，接入标准化的 `SmartModelBadge`。

### 3.6 语义混淆与概念界定：Badge、Tag、Chip、Pill 的职责边界梳理

在排查这 10 大平替的过程中，我们发现团队开发者对展示性标签的术语理解存在严重的认知混淆：
1. **Badge（徽标）**：**纯只读、信息提示**。通常只有极简的短文本（如 `PROD`、`v1.2`、`已装`）或小圆点，严格禁止内嵌按钮或点击移除行为。圆角采用微圆角矩形（4px）。
2. **Pill（胶囊药丸）**：**纯展示、物理胶囊形态（9999px 全圆角）**。通常用于强调状态（如在线/离线）或数值统计（如 `12`、`$0.15`），视觉上比 Badge 更柔和、更具封闭感。
3. **Chip / Tag（标签/滤芯芯片）**：**具备交互行为（可选、可删除、可点击）**。例如输入框中的 Mention 芯片、MCP 启停滤芯、思考档位选择器。通常包含右侧的 `×` 关闭图标或左侧图标盒。
目前由于组件库中只有 `Badge`，并强行塞入了 `onRemove`，导致大家想用药丸时写 CSS，想用滤芯时写 Button，造成彻底失控。

#### 核心算法与高难度机制解剖：

   ```typescript
   const getOffsetY = useCallback(
     (index: number, gap: number = 12): number => {
       let acc = 0;
       for (let i = 0; i < index; i++) {
         const item = toasts[i];
         const h = item
           ? heights[item.id] ?? heightsRef.current[item.id] ?? 56
           : 56;
         acc += h + gap;
       }
       return acc;
     },
     [toasts, heights]
   );
   ```
   在展开态下，卡片不再是简单的 `i * 56px`，而是**前 `i` 张卡片的实测高度总和累加 `i * gap`**！这保证了不论某张卡片是单行简讯还是包含代码块与三行描述的复杂通知，都能丝滑平铺、绝不重叠。
2. **Hover Bridge 防闪烁桥接（ToastStackModern.module.css:157-171）**：
   ```css
   .toastCard::after {
     content: '';
     position: absolute;
     top: 100%;
     left: 0;
     right: 0;
     height: calc(var(--gap, 12px) + 2px);
     pointer-events: auto;
   }
   ```

**缺陷指认**：
- 该偏移量与 26px 宿主紧密强耦合。一旦宿主头像尺寸发生改变（例如改为 32px 或 20px），或者在不同的缩放 DPI 渲染下，圆点将产生 1px 锯齿裁切或悬空漂移。
- 状态圆点使用了 `border: 1.5px solid var(--bg-elevated)` 进行物理割裂，但在深色或复杂半透背景下，`--bg-elevated` 与外层容器底色不匹配，会产生明显的“发白环形毛边”。

### 8.4 统一 ui/Avatar 原语方案设计

在 `src/components/ui/Avatar/` 新增统一头像组件：
- **形状支持**：`shape="circle" | "square"`（用户用 circle，Bot 用 square）；
- **尺寸档位**：`xs`(20px), `sm`(26px), `md`(32px), `lg`(40px)；
- **状态徽标插槽**：内置无损 Status Badge（支持 `status="online" | "busy" | "offline"`），通过数学百分比定位，绝不发生像素级偏离；
- **容灾机制**：支持真实 Image URL，加载失败或无图片时自动渲染首字母（Initials）或兜底 Icon。

在深入审查全库样式文件的过程中，我们梳理出了导致界面没有统一中性黑白灰的三大历史阶段：

3. **阶段三（AGENTS.md 规范立项期）**：确立了 §13（焦点对比度上限 10%，克制激活边框）与 §14（HSLA 色彩空间、感知均匀渐变、中性黑白灰为主），但已有业务代码存量巨大，未能进行地毯式清洗。

   通过 ESLint / Stylelint 插件，禁止在任何 `*.tsx` 的 `style` 属性或 `*.module.css` 中直接书写 `#...` 十六进制色值，任何颜色必须经由 `var(--...)` 派生。
2. **No Orphan Export 规则（防孤岛组件）**：
   对 `src/components/ui/index.ts` 导出的组件进行静态使用率扫描，如果在整个业务目录中引用次数为 0（如历史上的 SmartModelBadge），在 CI lint 阶段发出严重阻断告警。
3. **Separator Completeness 断言**：
   在自动化测试中加入盒模型尺寸断言，任何声明了 `role="separator"` 的元素，其实测高度或宽度不得为 0 且背景/边框不得为全透明，防止 `SelectContent.module.css` 式的隐形暗病再次发生。

---

## 十一、总结与汇报决议

本篇实勘历经代码逐行深度核查，彻底查清了 `crish-desktop` 视觉展示与状态反馈原语的现状基底：
- **SmartModelBadge**：概念领先但陷入了 `inline-flex` 与 `container-type: inline-size` 的规范级尺寸计算矛盾，且与业务下拉交互需求脱节，导致在业务中遭遇 100% 冷落；
- **展示原语**：`Badge` 规范严格却仅被 1 个业务引用，业务层野生生长出 10 大私有 Badge / Pill 平替，药丸圆角泛滥成灾；
- **分割原语**：通用原语完全缺位，现有 Select Separator 存在致命的 `border-top` 丢失隐形缺陷，全库至少 9 处手写私有分割线且 Token 打架；
- **反馈原语**：Toast 体系存在新旧双轨，旧轨为无用死代码，新轨残留硬编码高彩十六进制；骨架屏 `SkeletonFallback` 的 `.skel-shimmer` 样式全库失踪沦为空壳透明 div；加载 Spinner 存在六路割裂。

本篇导航文档为后续原子化重构奠定了详实、客观、确凿的现场事实证据，所有改动路径清晰明确，建议主控立即以此为依据发起实现波次调度。
