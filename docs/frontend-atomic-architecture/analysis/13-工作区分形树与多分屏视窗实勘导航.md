## 1. 执行摘要与系统全景（Executive Summary & Architecture Panorama）

### 1.1 系统定位与核心使命：分形树容器 vs 多视窗业务承载

在 Conex / Crish 桌面客户端的架构体系中，**工作区分形树（Binary Tree Workspace）** 与 **多分屏视窗系统（Multi-Pane Workspace System）** 构成了用户进行高强度智能辅助开发、多会话并发对话、以及多维工具观测（终端、浏览器、运行时监控）的核心舞台。

整个多视窗系统的职责边界在历史演进中形成了两级分层架构：
1. **分形树容器层（`components/binary-tree/`）**：负责纯二维空间几何的划分、分形嵌套树的扁平化投影、多窗格之间的 Sash 拖拽手柄控制、跨窗格的会话/标签拖拽（Tab Drag & Drop）、以及各窗格专属的外置标题栏（`PaneHeader`）与叶内抽屉工具栏（`LeafToolTabStrip`）。
2. **多视窗业务承载层（`components/workspace/`）**：负责在每个由分形树派生出来的几何叶子（`LayoutLeaf`）或叶内抽屉（`LeafDockDrawer`）内部，按需挂载具体的业务实体視窗。这包括工作区空态落地页（`WorkspaceEmptyState`）、原生内置透明代理浏览器（`PreviewCard`）、多终端会话与 PTY 交互系统（`TerminalCard`）、运行时状态与运维监控总控台（`RuntimePanel`）、以及工作流 DAG 编排可视化（`FlowDagView`）。

### 1.2 架构三层拓扑解构（算法数据层 → 空间容器层 → 视窗宿主层）

从数据流向、状态派生到物理 DOM 的渲染，整个多视窗系统展现出高度清晰但深层耦合的“三层拓扑结构”：

│    - 拖拽检测引擎: detectDropZone(pointer, leafRect) => DropZone        │
└──────────────────────────────────┬─────────────────────────────────────┘

                                   ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 2. 空间分形容器层 (src/components/binary-tree/)                        │
│    - 调度中枢: BinaryTreeWorkspace (双稳定化缓存: stabilizeLeaf/Branch) │
│    - 叶子微内核: TreeLeafPanel (绝对定位百分比盒，包含主对话列与右侧工具坞)  │

└──────────────────────────────────┬─────────────────────────────────────┘
                                   │ 声明式插槽挂载 (SlotOutlet: workspace.leaf.panel)
                                   ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 3. 视窗业务宿主层 (src/components/workspace/)                           │

### 1.3 核心技术指标与硬伤直击

通过本次深入全量源码的实勘，工作区系统虽然在多窗格拖拽、分形几何计算和 PTY 会话绑定上展现了极高的工程复杂度，但在样式管理、DOM 嵌套开销、组件封装度上暴露出亟待解决的深层次技术债务：
1. **资产体量庞大**：所辖的 `binary-tree`（22 个文件，5,907 行）与 `workspace`（83 个文件，17,905 行）共计 105 个文件、23,812 行代码，属于整个桌面前端最具业务密度的核心地带；
2. **DOM 树层级极度膨胀**：从 Desktop 顶层外壳到终端字符渲染节点或浏览器内联 Inspect 节点，DOM 树垂直嵌套深度高达 **18 ~ 24 层**（平均 21 层）。每一层容器均包裹独立的弹性盒子、溢出控制和相对定位，造成了不必要的复合图层开销与样式重排压力；
3. **样式穿透与 `!important` 滥用灾难**：在 `PreviewCard.module.css`、`BinaryTreeWorkspace.module.css` 中大量使用 `!important` 强制压制底层基础组件的样式（例如 URL 输入框的 7 处 `!important`、叶内抽屉最大化全屏的 4 连击 `!important`）。在 `BinaryTreeWorkspace.module.css:442` 更是使用了 `.leafChatColumn > *:not(:global(header)):not(:global(footer)) > *` 这类危险脆弱的子代穿透选择器来对抗 Flexbox 均分拉伸；
4. **分屏逻辑的双重割裂与特化**：整个桌面已经具备完整通用、可任意嵌套的二叉树分屏系统，但 `TerminalCard` 为了实现终端的上下/左右分屏，竟然在卡片内部又手写了一套硬编码的 `splitContainer`、`splitMode`、`activePaneIndex` 和 `termHandleRef1/termHandleRef2`。外层分屏与内层分屏概念重叠，严重违背了“单一真理路径（SSOT）”原则；
5. **焦点同步与事件拦截的过度防御**：在 `TreeLeafPanel:handleActivate` 中，为了防止用户点击窗格内的控件时误触发窗格焦点切换，维护了一个包含 20 余种选择器的庞大字符串黑名单（`closest('button, input, textarea, select, a, summary, [role="button"], [role="menuitem"], ...')`），脆弱易漏，缺乏标准的 Focus Scope 状态机。

### 1.4 反退避与反过度设计守则执行纲领

本次实勘严格遵循仓库全局协作铁律 `AGENTS.md`、反退避全文 `.agents/LOGIC_PLAN_NO_RETREAT.md` 以及反过度设计红线 `ANTI_OVERENGINEERING_GUARDRAILS.md`：
- **反退避底线**：不因“既有二叉树逻辑极度复杂、牵一发动全身”而妥协保留丑陋补丁。不搞降级版，必须穿透到底层算法与 DOM 结构，提出完全闭环的原子化多窗格微内核重塑方案；
- **反过度设计红线**：严禁引入笨重且不透明的第三方重型 Docking 框架（如 Dockview / GoldenLayout / FlexLayout 等巨石库）；保持当前二叉树轻量纯逻辑算子的优势，仅将 UI 外壳解耦为纯粹、高内聚、低耦合的原子化原语组件（Atomic Primitives），并全面转向现代 CSS Grid / Container Queries 原生排版能力。

#### 2.2.1 `BinaryTreeWorkspace.tsx`
- **绝对路径**：`c:/Software/conex/apps/crish-desktop/src/components/binary-tree/BinaryTreeWorkspace.tsx`
- **真实代码行数**：234 行
- **组件职责**：二叉树分屏工作区的总装调度器，负责订阅树形状态、展平为二维绝对定位矩形、稳定化缓存以保护 React.memo、并渲染所有的叶子面板与分屏手柄。
- **Props 契约与核心状态**：
  ```typescript
  export interface BinaryTreeWorkspaceProps {
    className?: string;
  }
  // 内部维护两个稳定化缓存 Ref：
  const leafEntryCacheRef = useRef<Map<string, StableLeafEntry>>(new Map());
  const branchCacheRef = useRef<Map<string, FlatBranch>>(new Map());
  ```
- **关键机制解构**：
  1. `flattenTree` 算子在每次 store 更新时都会返回全新的对象字面量（包含新的 `rect` 与 `tabs` 引用）。为防止下层子组件全部重绘，实现了 `stabilizeLeafEntries` 与 `stabilizeBranches`；

  3. 挂载了两个全局性副作用 Hook：`useTreePanelEvents()`（监听快捷键分屏/聚焦事件）与 `useChatPanelSync()`（同步主对话列的会话状态）。

## 3. 二叉分形树拓扑与分裂/合并算法深度剖析（Fractal Binary Tree & Split/Merge Algorithms）

### 3.1 树数据结构模型：`LayoutNode = LayoutLeaf | LayoutBranch` 纯数据定义与不变式

Conex 的多分屏布局内核建立在一个经典的纯函数式二叉树模型之上（定义于 `src/store/layout-tree/types.ts`）。
模型摒弃了传统网格式（CSS Grid）的行列固定划分，采用分形递归二叉树：每个视口区域要么是一个不可再分的叶子节点（`LayoutLeaf`），要么是由一条水平或垂直分割线切开的分支节点（`LayoutBranch`）。

```typescript
export interface LayoutLeaf {
  type: 'leaf';
  id: string;
  panelId: 'chat';
  tabs: SessionTab[];
  activeTabId: string;
  dock?: RightToolDockState;
}

export interface LayoutBranch {
  type: 'branch';
  id: string;
  direction: 'horizontal' | 'vertical';
  children: [LayoutNode, LayoutNode]; // 严格二叉元组
  splitRatio: number;                 // 0.12 <= splitRatio <= 0.88
}

export type LayoutNode = LayoutLeaf | LayoutBranch;

export interface LayoutTree {
  root: LayoutNode;
  version: 3;
}
```

#### 三大底层不变式（Mathematical Invariants）：
1. **严格二叉完备性（Binary Completeness）**：分支节点的 `children` 数组长度恒等于 2。整棵树没有空指针子节点；
2. **拓扑非退化性（Non-Degenerate Topology）**：任何分支节点必须至少拥有两个子节点。当其中一个子节点被移除时，该分支节点必须立即解构塌陷，由其幸存兄弟节点无损顶替；
3. **比例有界性（Bounded Split Ratio）**：`splitRatio` 严格受限于常量区间 `[0.12, 0.88]`。这保证了在任何方向的分屏中，最小的窗格至少占据母空间的 12%，从根本上杜绝了除以零或窗格完全不可见（0 像素）的渲染异常。

### 3.2 树展平与几何投影算法：`flattenTree` 递归遍历与归一化百分比 Rect 坐标系

直接递归渲染 React 组件树会导致 DOM 层级深陷、手柄定位极度繁琐。系统在 `src/store/layout-tree/layoutTreeFlatten.ts` 中实现了一套极其高效的**空间展平与归一化投影算法**。

#### 算法数学模型：
给定根节点分配的初始空间：
$$	ext{Rect}_{	ext{root}} = { x: 0, y: 0, w: 1, h: 1 }$$
对于任意分支节点 $N_{	ext{branch}} = (	ext{direction}, 	ext{ratio}, C_1, C_2)$ 与分配空间 $	ext{Rect} = (x, y, w, h)$：

- **水平分割（`direction === 'horizontal'`）**：
  $$	ext{Rect}_{C_1} = { x, y, w 	imes 	ext{ratio}, h }$$
  $$	ext{Rect}_{C_2} = { x + w 	imes 	ext{ratio}, y, w 	imes (1 - 	ext{ratio}), h }$$
- **垂直分割（`direction === 'vertical'`）**：
  $$	ext{Rect}_{C_1} = { x, y, w, h 	imes 	ext{ratio} }$$
  $$	ext{Rect}_{C_2} = { x, y + h 	imes 	ext{ratio}, w, h 	imes (1 - 	ext{ratio}) }$$

#### 展平算法源码剖析：
```typescript
export function flattenTree(root: LayoutNode, options?: { collapsedDomain?: CollapsedDomain }) {
  const leaves: FlatPanel[] = [];
  const branches: FlatBranch[] = [];
  flattenRecursive(root, { x: 0, y: 0, width: 1, height: 1 }, leaves, branches, options?.collapsedDomain);
  return { leaves, branches };
}

function flattenRecursive(
  node: LayoutNode,
  rect: Rect,
  leavesOut: FlatPanel[],
  branchesOut: FlatBranch[],
  collapsedDomain?: CollapsedDomain
): void {
  if (isLeaf(node)) {
    leavesOut.push({
      leafId: node.id,
      panelId: 'chat',
      tabs: node.tabs,
      activeTabId: node.activeTabId,
      dock: createDefaultDock(node.dock),
      sessionId: node.tabs.find((t) => t.tabId === node.activeTabId)?.sessionId ?? '',
      rect: leafMatchesCollapsedDomain(node, collapsedDomain)
        ? { x: rect.x, y: rect.y, width: 0, height: 0 }
        : rect,
    });
    return;
  }

  const { direction, splitRatio, children } = node;
  // 记录 branch 绝对几何占比，用于 Sash 物理定位
  branchesOut.push({ branchId: node.id, direction, splitRatio, rect });

  if (direction === 'horizontal') {
    const firstWidth = rect.width * splitRatio;
    flattenRecursive(children[0], { x: rect.x, y: rect.y, width: firstWidth, height: rect.height }, leavesOut, branchesOut, collapsedDomain);
    flattenRecursive(children[1], { x: rect.x + firstWidth, y: rect.y, width: rect.width - firstWidth, height: rect.height }, leavesOut, branchesOut, collapsedDomain);
  } else {
    const firstHeight = rect.height * splitRatio;
    flattenRecursive(children[0], { x: rect.x, y: rect.y, width: rect.width, height: firstHeight }, leavesOut, branchesOut, collapsedDomain);
    flattenRecursive(children[1], { x: rect.x, y: rect.y + firstHeight, width: rect.width, height: rect.height - firstHeight }, leavesOut, branchesOut, collapsedDomain);
  }
}
```

**特性保证**：
- 单次 $O(N)$ 递归遍历；
- 输出所有叶子的绝对百分比坐标与所有分支的分割手柄矩形；
- 无论树结构如何深层嵌套，渲染层全部平铺展开，彻底消除了 DOM 的层级嵌套！

### 3.3 窗格分裂算法：`splitLeaf` / `splitTab` / `splitSessionFromSidebar`

窗格分裂是多分屏系统的核心交互，支持“拖拽标签到边缘分屏”与“从侧栏拖入会话直接分屏”。

#### 算子执行流程拓扑图：
```
[发起分屏: splitTab(tree, srcLeafId, tabId, dstLeafId, region, splitRatio)]
                 │
                 ▼
        目标区域 region === 'center' ?
       ┌─────────┴─────────┐
       ▼ YES               ▼ NO
  moveTab 合并为标签     确定分屏方向 direction:
                        - left / right => 'horizontal'
                        - top / bottom => 'vertical'
                           │
                           ▼
                    从源叶剥离该 Tab:
                    src.tabs.filter(t => t.tabId !== tabId)
                           │
                           ▼
                    构造全新目标 Leaf:
                    fresh = createLeaf({ tabs: [tab], activeTabId: tab.tabId })
                           │
                           ▼
                    构造二叉 Branch:
                    first, second = (region 为 right/bottom) ? [dst, fresh] : [fresh, dst]
                    branch = createBranch(direction, first, second, splitRatio)
                           │
                           ▼
                    替换目标节点 replaceNode(root, dstLeafId, branch)
                           │
                           ▼
                    级联修剪源叶 pruneEmptyLeaves(tree)
```

在 `src/store/layout-tree/layoutTreeInsert.ts:199-281` 中：
- 当源叶与目标叶相同时（在同一个窗格内向右切分）：原叶作为左子节点，新建叶作为右子节点，直接由父 Branch 原地替换；
- 当源叶与目标叶不同时：在目标位置创建 Branch 插入，并将源叶中对应的 Tab 移除。若源叶此时变空，调用 `pruneEmptyLeaves` 自动折叠消除源窗格。

### 3.4 窗格合并与折叠消除算法：`removeNodeFromTree` 兄弟节点提升与 `pruneEmptyLeaves` 级联修剪

#### 1. 兄弟节点提升（Tree Collapse）：
在 `src/store/layout-tree/layoutTreeMoveRemove.ts` 中：
当删除某个节点 `nodeId` 时，找到其父节点 `parent`。因为父节点只有两个子节点，被删除节点的兄弟节点将直接提升，取代父节点的位置：

```typescript
export function removeNodeFromTree(tree: LayoutTree, nodeId: string): LayoutTree | null {
  const { root } = tree;
  if (root.id === nodeId) return null; // 根节点不可删

  const parentInfo = findParent(root, nodeId);
  if (!parentInfo) return null;

  const { parent, index } = parentInfo;
  // 幸存兄弟节点：index 为 0 保留 1，为 1 保留 0
  const keepIndex: 0 | 1 = index === 0 ? 1 : 0;
  const newRoot = removeBranch(root, parent.id, keepIndex);
  return { ...tree, root: newRoot };
}
```

#### 2. 空叶级联修剪循环（`pruneEmptyLeaves`）：
当多个 Tab 被连续关闭或移走时，树中可能产生无内容的空叶。
```typescript
export function pruneEmptyLeaves(tree: LayoutTree): LayoutTree {
  let current = tree;
  let changed = false;
  // 设定最大防御上限 32 轮，防止环形结构死循环
  for (let guard = 0; guard < 32; guard++) {
    const leaves = collectLeaves(current.root);
    const empty = leaves.filter((l) => l.tabs.length === 0);
    if (empty.length === 0) return changed ? current : tree;

    // 唯一空叶保护铁律：如果全树只剩一个叶子且为空，绝不删除它！
    // 而是保留其作为“新对话草稿态（Draft Composer）”，防止整个桌面视口坍塌成空白！
    if (leaves.length === 1) {
      const only = leaves[0]!;
      if (only.activeTabId !== '') {
        return { ...current, root: replaceNode(current.root, only.id, { ...only, activeTabId: '' }) };
      }
      return changed ? current : tree;
    }

    // 移除第一个空叶，触发兄弟提升
    const next = removeLeafFromTree(current, empty[0]!.id);
    if (!next) return changed ? current : tree;
    current = next;
    changed = true;
  }
  return current;
}
```

### 3.5 跨窗格会话标签迁移算法：`moveTab` / `moveNode` 深度剪枝与挂载

- 算法保证：会话标签跨窗格迁移是原子的；

## 4. 分屏拖拽调节器（Resize Splitter）与高性能手势控制（Splitter & Gesture Control Engine）

### 4.1 全局树手柄：`TreeResizeSash` 架构与水平/垂直绝对定位投影

在多分屏二叉树中，分隔手柄（Sash）是用户调整窗格比例的关键桥梁。
在 `src/components/binary-tree/TreeResizeSash.tsx` 中，手柄不是由 Flexbox 自动排版，而是依托 `flattenTree` 输出的 `branch.rect` 执行精准的**绝对几何投影**：

- **水平分割线（Horizontal Sash · 左右调节）**：
  ```typescript
  el.style.left = `${(rect.x + rect.width * ratio) * 100}%`;
  el.style.top = `${rect.y * 100}%`;
  el.style.height = `${rect.height * 100}%`;
  ```
  光标呈现为 `cursor: col-resize`，手柄宽度 6px，通过 `transform: translateX(-3px)` 居中对齐；
- **垂直分割线（Vertical Sash · 上下调节）**：
  ```typescript
  el.style.top = `${(rect.y + rect.height * ratio) * 100}%`;
  el.style.left = `${rect.x * 100}%`;
  el.style.width = `${rect.width * 100}%`;
  ```
  光标呈现为 `cursor: row-resize`，手柄高度 6px，通过 `transform: translateY(-3px)` 居中对齐；
- **视觉常态绝缘与激活高亮**：
  - 常态下 `.sash::after` 背景为完全透明（`background: transparent`），因为相邻窗格各自自带 1px 的发丝边框，如果手柄常态也画线，会导致两窗格交界处出现 3 条黑线的视觉灾难；
  - 仅在用户鼠标悬停（`:hover`）或按下拖拽（`[data-active='true']`）时，伪元素亮出 2px 的翡翠品牌绿（`var(--accent-green, #10b981)`）。

### 4.2 零 React 重新渲染的高性能手势管线

桌面客户端分屏拖拽的核心挑战是：在用户以 60Hz/120Hz 甚至 240Hz 极速拖动鼠标时，如何保证不丢帧、零卡顿、无撕裂？

#### 传统状态流的灾难：
若在 `pointermove` 事件中直接调用 `store.resizeBranch(ratio)`：
- Zustand 派生状态改变 → 触发 `flattenTree` → 触发 `BinaryTreeWorkspace` 重新渲染 → 重新构造并比对所有 Leaf 与 Sash 虚拟节点；
- 造成每秒触发上百次全量 React Reconciliation，导致渲染管线严重拥堵，表现为鼠标跟手严重滞后。

#### `useTreeResize` 的零重绘直写架构：
`src/hooks/useTreeResize.ts` 彻底切断了手势期间的 React 渲染环路，设计了纯 DOM 驱动的“旁路直写引擎”：

```
[ 1. 拖拽开始 pointerdown ]
  │
  ├── body.classList.add('tree-resizing')
  │   └── 触发 CSS: .tree-resizing .leaf { transition: none !important; will-change: ... }
  ├── 一次性扫描建立缓存: collectLiveResizeDomMap()
  │   └── Map<leafId, HTMLElement>, Map<branchId, HTMLElement>
  └── 计算当前像素基准尺寸:
      pixelRect = canvas.getBoundingClientRect() * branch.rect
  │
[ 2. 拖拽进行 pointermove (极速触发) ]
  │
  ├── 纯数学计算: newRatio = (e.clientX - pixelRect.left) / pixelRect.width
  ├── 数学校验: clampSplitRatioForParent(newRatio, parentPx)
  └── requestAnimationFrame(() => {
        // A. 纯算法产生下一帧虚拟树 (耗时 < 0.1ms)
        const nextTree = resizeBranchTree(tree.root, branchId, newRatio);
        const { leaves, branches } = flattenTree(nextTree.root);
        // B. 绕过 React，直接刷物理 DOM inline style
        for (const leaf of leaves) {
          const el = domMap.leaves.get(leaf.leafId);
          el.style.left = `${leaf.rect.x * 100}%`;
          el.style.width = `${leaf.rect.width * 100}%`;
        }
        for (const branch of branches) {
          const el = domMap.branches.get(branch.branchId);
          el.style.left = `${(branch.rect.x + branch.rect.width * branch.splitRatio) * 100}%`;
        }
      });
  │   (注意: 此阶段 React 组件完全不感知，渲染帧率稳锁 120 FPS!)
  │
[ 3. 拖拽松开 pointerup / pointercancel ]
  │
  ├── body.classList.remove('tree-resizing')
  ├── 清空并释放 DOM 缓存: clearLiveResizeDomCache()
  ├── 若发生实质位移 (didMove === true):
  │   ├── pushHistory() 记录撤销重做状态
  │   └── store.resizeBranch(branchId, finalRatio) 一次性写入单一真理源
  └── 恢复 React 受控状态
```

### 4.3 瞬态防抖与尺寸钳制安全防线

在拖拽过程中，若用户将分割条直接拉到视口边缘，会导致被挤压窗格的宽度变为 0 甚至负数。
在 `src/hooks/treeResizeClamp.ts` 中定义了严格的防坍塌保护算法：

```typescript
export const MIN_CHILD_PX = 120; // 单个分屏视窗物理最小像素宽度/高度

export function splitRatioBounds(parentPx: number): { min: number; max: number } {
  if (parentPx <= 0) return { min: 0.12, max: 0.88 };
  // 计算在当前容器物理像素下，120px 占据的比例
  const minRatioByPx = MIN_CHILD_PX / parentPx;
  const maxRatioByPx = 1 - minRatioByPx;

  // 综合业务比例界限 [0.12, 0.88] 与像素界限，双重收紧
  const min = Math.max(0.12, minRatioByPx);
  const max = Math.min(0.88, maxRatioByPx);

  return min <= max ? { min, max } : { min: 0.5, max: 0.5 };
}
```
即使在 800px 宽的小屏窗口中，左右双分屏的最小宽度也被死死锁定在 120px 以上，绝不发生布局坍塌！

### 4.4 叶内坞调节手柄：`LeafDockResizer` 0px 跨越与负外边距对称热区

除了二叉树节点之间的 Sash，每个叶子内部的“主对话列”与“右侧工具抽屉”之间同样需要可调节手柄（`LeafDockResizer.tsx`）。
这里的架构设计极其精妙：

### 4.5 拖拽全链路“防粘手与防事件丢失”四重防线

在跨 iframe 复杂的桌面应用场景中，普通事件监听极易出现严重 Bug。本系统构筑了**四重立体防线**：

| 防线层级 | 实现方式 | 防范的致命 Bug |
| :--- | :--- | :--- |
| **第一道：硬件级捕获** | `handleEl.setPointerCapture(e.pointerId)` | 用户鼠标快速划过视窗边缘甚至移出整个桌面窗口时，事件丢失 |
| **第二道：iframe 黑洞屏蔽** | `disableIframePointerEvents()` | 鼠标划过 PreviewCard 或外部嵌入页面时，指针事件被 iframe 吞噬（事件黑洞） |
| **第三道：全局 Body 标记** | `document.body.classList.add('is-resizing')` | 拖拽过程中意外选中文本、高亮代码，引发全屏文本选区闪烁 |
| **第四道：系统手势收敛** | 同时监听 `pointercancel` 与 `blur` | 用户按下 Alt+Tab、Win 键或触发系统多任务手势时，拖拽状态未释放导致鼠标粘手 |

## 5. 多视窗聚焦状态同步与生命周期调度（Multi-Pane Focus Sync & Lifecycle Management）

### 5.1 双层焦点解耦模型：树级 `activeLeafId` 与叶内 `activeTabId` / `activePanelId`

在单视窗应用中，当前激活项由一个全局的会话 ID 决定；但在多分屏分形树架构中，如果依然沿用单层全局 ID，将导致多分屏状态彻底混乱（例如用户点击左边，右边的工具栏被迫跟随联动）。

系统通过**双层焦点解耦模型**成功实现了窗格自治与全局协同：

```
┌────────────────────────────────────────────────────────────────────────┐
│ 全局焦点层: useLayoutTreeStore((s) => s.activeLeafId)                  │
│ - 标识当前哪一个分屏叶子处于物理输入和键盘快捷键的受控态                    │
│ - 仅负责：加深活动卡片的发丝边框色 (border-color: var(--border-color))   │
│ - 绝不干涉各叶子内部的显示内容                                        │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │ 派发到物理窗格
                                   ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 窗格自治层: TreeLeafPanel (leaf.id === activeLeafId)                   │
│ ├── 1. 主对话列焦点: readActiveTabId(leaf)                              │
│ │   - 决定主对话区渲染哪一个会话（SessionTab）                          │
│ │   - 若为空字符串 ""，则进入独立的草稿态（Draft Composer）            │
│ └── 2. 右侧工具坞焦点: leaf.dock.activePanelId                         │
│     - 决定当前叶内抽屉展示的是 'preview'、'terminal' 还是 'runtime'   │
│     - 决定抽屉是展开还是折叠 (dock.collapsed)                         │
└────────────────────────────────────────────────────────────────────────┘
```

#### 架构收益：
- **多任务真并发**：左窗格可以停留在一个长文本阅读会话，右窗格可以停留在终端跑编译命令，两个窗格互不干扰各自的活动状态；
- **焦点切换零重绘**：切换全局 `activeLeafId` 仅仅改变两个 `<div>` 的边框颜色属性，不会触发任何会话内容的卸载或重建。

### 5.2 跨窗格事件委托与交互穿透拦截

在 `TreeLeafPanel.tsx:195-218` 中，为了实现“点击卡片任何非交互区域即可切换激活该窗格”，外层容器监听了 `onPointerDown={handleActivate}`。
然而，如果用户正在卡片内部点击输入框打字、点击按钮提交、或者在终端选中文本，这一事件冒泡如果被粗暴捕获，就会瞬间抢夺原生控件的焦点。

为此，系统构建了一道极为严格的**交互穿透拦截白名单防线**：

```typescript
const handleActivate = useCallback(
  (e?: React.PointerEvent) => {
    if (e && e.target && 'closest' in (e.target as HTMLElement)) {
      const target = e.target as HTMLElement;
      // 拦截 20 余种表单元素、富文本、无障碍角色与专用终端画布
      if (
        target.closest(
          'button, input, textarea, select, a, summary, [role="button"], ' +
          '[role="menuitem"], [role="menu"], [role="combobox"], [role="listbox"], ' +
          '[role="option"], [role="tab"], [role="switch"], [role="dialog"], ' +
          '[role="toolbar"], [contenteditable="true"], [data-interactive], ' +
          '[data-radix-popper-content-wrapper], [data-interactive="true"], ' +
          '[data-pty-host], [class*="xtermHost"], .xterm, canvas, .xterm-screen'
        )
      ) {
        return; // 处于交互控件内部，终止聚焦拦截，放行原生行为
      }
    }
    if (chatMainSurface !== 'chat') return;

    const tabId = readActiveTabId(leaf);
    if (tabId) {
      sessionShell().activateTab(leaf.id, tabId);
    } else {
      getCompositionRoot().shell.focusLeaf(leaf.id);
    }
  },
  [leaf, chatMainSurface]
);
```

#### 评价与隐患：
虽然该白名单成功解决了绝大多数表单和 xterm 终端的点击穿透问题，但使用长达数百字符的选择器字符串 `closest(...)` 进行 DOM 树向上递归回溯，在性能上存在开销；且未来若引入新的富文本原语，若未登记在此字符串中，将再次引发焦点抢夺 Bug。

### 5.3 会话身份漫游与草稿哨兵机制

在多分屏系统中，用户经常点击“新建对话（+）”。
传统架构往往会立即在底层数据库创建一条空的会话记录，并生成标签页。这会导致数据库产生大量无用的“幽灵空会话”，且标签栏被空白标签占满。

#### Conex 的草稿哨兵机制（Draft Sentinel）：
1. **未提交新对话绝对不占标签栏**：点击新建对话时，`leaf.activeTabId` 被重置为空字符串 `""`；
2. **草稿哨兵隔离**：通过 `mintDraftSessionId(leaf.id)`（如 `draft-leaf-123`）为当前窗格分配专属的临时内存 ID；
3. **真实会话物化**：用户在 Composer 中输入第一条指令并敲击回车成功发送后，系统才调用后端 IPC 正式创建会话 UUID，随后将该真会话物化为 `SessionTab`，并以优雅动画插入当前叶子的 `tabs` 数组中。

### 5.4 视窗内容卸载与保活权衡

在右侧工具坞抽屉（`leafDockDrawer`）中，用户常常需要频繁在“浏览器预览”和“终端”之间来回切换。
如果每次切换都卸载（Unmount）旧组件：
- 浏览器 iframe 将重新加载页面，丢失滚动条位置和用户填写的表单；
- xterm.js 终端将重置，断开与 PTY 的数据流，丢失清屏历史。

在 `TreeLeafPanel.tsx:502-536` 中，系统通过 `tabModeEnabled` 策略实现了**基于 CSS `display` 的 DOM 级完全保活**：
```tsx
{dock.openPanelIds.map((pid) => {
  const isActive = pid === toolPanelId;
  return (
    <div
      key={pid}
      className={styles.dockPanelPane}
      style={{
        display: isActive ? 'flex' : 'none',
        flex: '1 1 auto',
        width: '100%',
        height: '100%',
      }}
      data-panel-id={pid}
      data-active-panel={isActive ? 'true' : 'false'}
      aria-hidden={!isActive}
    >
      {renderToolOutlet(pid)}
    </div>
  );
})}
```
- **收益**：所有已打开的工具保持完整的内存和 DOM 状态，切回时即时展现（0 延迟）；
- **代价**：后台未激活的视窗依然驻留在 DOM 中，若同时打开数十个终端和重型浏览器页面，内存占用会线性上升。

## 6. DOM 树嵌套开销与渲染性能瓶颈分析（DOM Tree Nesting Overhead & Performance Bottlenecks）

### 6.1 DOM 层级膨胀解剖：从桌面根到叶内视窗的 21 层嵌套拓扑与逐层盒模型分析表

在现代高性能桌面应用中，过深的 DOM 嵌套不仅导致 HTML 结构晦涩，更会对浏览器的样式计算（Recalculate Style）、布局排版（Layout / Reflow）和图层合成（Compositing）带来沉重负担。

通过深入审查实勘代码中的物理挂载链，我们对多视窗桌面在挂载“终端卡片（TerminalCard）”时的完整 DOM 链路进行了逐层度量：

| 层级 | HTML 标签与关键 Class / 属性 | 所属组件 / 物理职责 | CSS Display & 盒模型特征 | 布局开销评估 |
| :---: | :--- | :--- | :--- | :--- |
| **L1** | `<html>` | 浏览器视口根容器 | 块级 (Block) | 顶层根 |
| **L2** | `<body>` | 页面主体容器 | 块级，监听全局手势类名 | 挂载 `.tree-resizing` |
| **L3** | `<div id="root">` | React 应用注入根节点 | `display: flex; height: 100vh` | 全局弹性盒 |
| **L4** | `<div class="appRoot">` | 应用顶层主题注入容器 | `display: flex; flex-direction: column` | 样式变量宿主 |
| **L5** | `<div class="workbenchLayout">` | 桌面工作台整体布局壳 | `display: flex; flex-direction: row` | 左右分栏划分 |

### 6.2 分形树扁平化渲染（Flatten）与绝对定位架构的得与失

Conex 架构将树结构通过 `flattenTree` 展平成平铺在画布（`canvas`）下的 Leaf 集合，是一次重大的架构进步，但同时也引入了物理层面的权衡代价：

#### 架构收益（Gains）：
- **组件层级平铺化**：避免了树形递归组件树的反复拆装，所有 Leaf 在 React 虚拟 DOM 中处于兄弟并列层级；
- **重绘隔离（Reflow Boundary）**：所有 Leaf 采用 `position: absolute`，单个窗格尺寸的变化被限制在其自身的绝对定位盒内，不会引起标准文档流其他兄弟节点的全局 Reflow。

#### 潜在隐患与代价（Costs）：
- **合成图层（Compositing Layers）膨胀**：每个绝对定位的 Leaf 均声明了 `isolation: isolate`，且在拖拽时声明了 `will-change: left, width, top, height`。这迫使 Chromium（WebView2）为每一个分屏窗格创建独立的 GPU 渲染合成图层。在 4~6 分屏并同时打开多个 Canvas/WebGL 终端与 iframe 时，GPU 显存占用明显偏高；
- **文档流脱离引发的代码复杂度**：因为脱离了标准文档流，工具栏（`AppTopBar`）、状态栏以及侧边栏无法感知卡片的自然高度，所有卡片之间的边缘对齐与避让只能依赖 JavaScript 运行时的数学计算（`paneEdgeGeometry.ts`）。

### 6.3 内存泄漏与 ResizeObserver 管理

在实勘中发现，多视窗系统中对 `ResizeObserver` 的监听存在明显的**管理割裂**：

1. 在 `LeafToolTabStrip.tsx:263` 中，开发者意识到了内存问题，使用了单例管理器：
   ```typescript
   const ro = ResizeObserverManager.getInstance();
   ro.observe(el, checkOverflow);
   return () => { ro.unobserve(el, checkOverflow); };
   ```
2. 然而在 `PaneHeader.tsx:149` 中，却直接裸写了原生实例：
   ```typescript
   let ro: ResizeObserver | null = null;
   if (typeof ResizeObserver !== 'undefined') {
     ro = new ResizeObserver(checkOverflow);
     ro.observe(el);
   }
   return () => { ro?.disconnect(); };
   ```
- **风险分析**：在用户高频切分、合并窗格的过程中，原生 `new ResizeObserver` 的重复创建与销毁会增加垃圾回收（GC）开销；若某个窗格发生异态卸载导致 cleanup 未能触发，极易产生长期未释放的游离 DOM 节点引用。

### 6.4 React 引用抖动与缓存击穿排查

在 `BinaryTreeWorkspace.tsx:112-156` 中，存在一段为了保护 `React.memo` 不被击穿而不得不编写的极其繁琐的深度比对代码：

```typescript
function stabilizeLeafEntries(
  panels: FlatPanelItem[],
  prev: Map<string, StableLeafEntry>
): Map<string, StableLeafEntry> {
  const next = new Map<string, StableLeafEntry>();
  for (const panel of panels) {
    const cached = prev.get(panel.leafId);
    let leaf: LayoutLeaf;
    if (
      cached &&
      cachedActive === activeTabId &&
      tabsIdentityEqual(cached.leaf.tabs, panel.tabs) &&
      dockIdentityEqual(cached.leaf.dock, panel.dock)
    ) {
      leaf = cached.leaf; // 强制复用旧引用
    } else {
      leaf = toLayoutLeaf(panel);
    }
    const rect = cached && rectEqual(cached.rect, panel.rect) ? cached.rect : panel.rect;
    next.set(panel.leafId, { leaf, rect });
  }
  return next;
}
```

#### 架构穿透洞察：
这种在每次组件渲染时，使用 `tabsIdentityEqual` 和 `dockIdentityEqual` 对深层数组和对象进行逐字段巡检的模式，**实质上是在组件渲染层为“上游数据产生器缺乏引用不可变性保证”而买单**。
正确的长效治理方案是在 Store 派生层（Selector）使用基于不可变数据结构的 Memoized Selector（如通过 Immer 或类似方案），在数据派生端直接稳定引用，从而彻底砍掉组件层的这种高成本运行时巡检！

### 7.1 滥用 `!important` 强制覆写排查

在现代原子化 CSS 架构中，`!important` 是最高级别的视觉反模式（Anti-Pattern），它彻底摧毁了 CSS 的自然层叠规则（Cascading Rules），通常是组件封装过度、缺少样式插槽、以及强行打补丁的直接产物。

在本次实勘中，发现了多处极其恶劣的 `!important` 扎堆滥用：

#### 违规点 1：`PreviewCard.module.css:52-82`（连续 7 处 `!important`）
```css

  height: 24px !important;
  min-height: 24px !important;
  font-size: var(--font-size-xs, 12px) !important;
  background: transparent !important;
  border: 1px solid transparent !important;
  border-radius: var(--radius-md, 6px) !important;
  box-shadow: none !important;
}

.urlInput::placeholder {
  color: var(--text-tertiary) !important;

.urlForm:hover .urlInput:not(:disabled),

  background: var(--sidebar-hover, ...) !important;
  border: 1px solid transparent !important;

```
- **致命根因**：业务层引入了底层的通用 `<Input>` 组件，由于通用组件内部写死了较高的特异性（Specificity）并带有默认的灰色边框与聚焦蓝色光环，`PreviewCard` 的地址栏为了伪装成极简无框文本框，只能通过连续 7 次连击 `!important` 暴力覆盖！

#### 违规点 2：`BinaryTreeWorkspace.module.css:412-416`（连续 4 处 `!important`）

## 8. 未来原子化多窗格系统重塑详案（Future Atomic Multi-Pane System Architecture）

### 8.1 架构设计哲学：从“臃肿复合组件”走向“Headless 视窗微内核 + 原子化原语”

基于前述实勘中发现的全部架构断层与物理样式缺陷，未来的工作区分屏系统必须推进**彻底的原子化重塑**。

#### 核心设计哲学：
1. **彻底解耦“空间拓扑”与“业务渲染”**：
   - 二叉树只管“切蛋糕”（二维矩形切分、手势捕获、比例维护）；
   - 视窗只管“自身业务”（浏览器导航、终端字节流、DAG 图排版）；
   - 彻底废除视窗内部私自实现分屏（如终端内嵌分屏）的违规做法。
2. **Headless 核心驱动（`usePaneTree`）**：
   - 将二叉树的展平计算、Sash 定位、Live Resize 直写手势管线完整下沉为一个 Headless 纯逻辑微内核 Hook；
   - 输出纯粹的数据模型、CSS 变量、以及无状态的事件绑定函数，支持任意 UI 壳层消费。
3. **原子组件原语化（Atomic Primitives）**：
   - 将庞大的 `BinaryTreeWorkspace`、`TreeLeafPanel`、`PaneHeader` 拆解为细粒度的 Compound Components（复合组件群），通过声明式 JSX 进行任意插槽组装。

   - 而是直接向全局 `layoutTreeStore` 派发原生的分裂指令：
     ```typescript
     splitLeaf(tree, currentLeafId, 'horizontal', 'after', 0.5);
     ```
   - 全局二叉树自动为用户创建一个新的分屏窗格，并在新窗格中直接挂载第二个终端！
2. **重构收益**：
   - 立即删除 `TerminalCard.tsx` 中 40% 的分屏样板代码；
   - 立即删除 `TerminalToolbar.tsx` 中复杂的 `splitMode` 状态管理；
   - 终端分屏瞬间获得外层原生 Sash 的所有高级能力（像素级防坍塌、无障碍键盘微调、双击恢复 0.5 均分、拖拽吸附高亮）。

### 8.4 CSS 现代化重构规范（CSS Subgrid / Container Queries 替代深层穿透）

1. **全面清剿所有 `!important`**：
   - 改造基础组件库 `<Input>`，提供无边框/透明底的语义变体（`variant="ghost"`），让 `PreviewCard` 地址栏通过属性原生渲染，彻底淘汰 7 个 `!important`；
   - 工具坞抽屉的最大化改造为标准的类名切换，在 CSS 规则中通过特异性对齐，彻底淘汰 4 连击 `!important`。
2. **彻底废除通配符 `> *:not(...) > *`**：
   - 将 `.leafChatColumn` 与视窗内容容器改造为标准的 CSS Grid 或 Flex 容器；
   - 直接给子元素显式标注原子样式类 `.paneFillRoot { flex: 1 1 0%; width: 100%; height: 100%; min-height: 0; }`；
   - 结构清晰可见，绝不在父容器上写任何穿透式猜测选择器。
3. **桌面端环境变量自适应避让**：
   - 彻底废除 `padding-left: 52px / 106px` 与 `padding-right: 112px` 的硬编码；
   - 改为通过 CSS 变量由最外层桌面环境统一注入：
     ```css
     .paneHeader {
       padding-left: var(--titlebar-left-reserved, 4px);
       padding-right: var(--titlebar-right-reserved, 4px);
       height: var(--pane-header-height, 36px);
     }
     ```
   - 顶层窗口在 macOS 下自动派生 `--titlebar-left-reserved: 80px`，Windows 下自动派生 `--titlebar-right-reserved: 120px`，叶子组件无需感知操作系统类型。

### 8.5 统一焦点管理状态机（Focus Scope Provider）

- 淘汰 `closest('button, input, ...')` 长达 20 项的选择器硬编码；
- 引入类似现代无障碍标准的 **Focus Scope** 机制：
  ```tsx
  <PaneFocusScope paneId={pane.id} onFocus={() => setGlobalActivePane(pane.id)}>
    {/* 窗格所有内容 */}
  </PaneFocusScope>
  ```
- 在容器上监听原生的 `onFocusCapture` 与 `onBlurCapture` 事件，通过 DOM 原生的事件流驱动焦点切换，精确、轻量且具备 100% 的组件普适性。

## 10. 结论与主控汇报纲要（Conclusion & Handoff Summary）

### 10.1 核心实勘结论汇总

经过对 `binary-tree`（22 个文件，5,907 行）与 `workspace`（83 个文件，17,905 行）全量 105 个文件、23,812 行源码与样式的深度逐行阅读与系统性解剖，得出以下核心结论：

1. **资产基石稳固，算法底座极其优秀**：
   - 现有的二叉分形树数据模型（`LayoutNode = LayoutLeaf | LayoutBranch`）、空间展平算法（`flattenTree`）、以及零 React 重绘直写手势管线（`useTreeResize`）展现了极高的工业级工程设计水平；
   - 这一套算法经过了数十个针对性测试用例（如 `TreeResizeSash.memo.test.tsx`、`TreeLeafPanel.routing.test.tsx`）的严格锤炼，具备极高的稳定性和极致的手势性能，应当作为宝贵的核心资产，在重构中 100% 提炼传承为 Headless 微内核。
2. **物理层与样式层债务严重，亟待原子化重构**：
   - DOM 树垂直嵌套达 21 层，弹性盒子计算与合成图层开销偏高；
   - 存在 11 处严重的 `!important` 强制覆盖与不可维护的深层子代通配符选择器（`.leafChatColumn > *:not(...) > *`）；
   - 终端卡片私造内嵌分屏，导致全桌面存在两套互相割裂的分屏体系；
   - 窗格头（36px）与工具栏（38px）存在 2px 视觉撕裂，且散落大量物理像素魔术数字（52px, 106px, 112px）。
