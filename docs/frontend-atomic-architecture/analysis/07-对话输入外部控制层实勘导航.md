## 一、实勘总览与架构拓扑定位

### 1.1 外部控制层在对话中枢中的核心使命

在 Conex / Crish 桌面工作台中，对话输入区（Chat Composer）承担着整个人机交互界面的咽喉要道职责。它并非单纯的单行或多行文本输入框，而是一个承担了**模型交互控制、系统安全权限守卫、长程执行规划反馈、上下文多模态附件投喂以及高并发队列管理**的复合型交互中枢。

整个输入中枢在物理和逻辑维度被解耦为两大子系统：
1. **内部编辑内核 (Internal Input Kernel)**：由 Layer 4 内部的富文本 Tiptap 引擎（`TiptapComposerField`）以及装配失败时的自动兜底 Textarea（`ComposerField`）组成，负责富文本渲染、Markdown 提取、斜杠菜单提示（Slash Menu）、@提及候选人以及文本级别的撤销重做。
2. **外部控制层 (External Control Layer)**：由包裹并穿插在编辑内核外围的 Layer 0、Layer 1、Layer 2、Layer 3 以及 Layer 4 外围控制控件组成。

外部控制层的核心使命包括：
- **执行主权守卫 (Layer 1 Permission Guard)**：在 Agent 发起危险系统命令（如 `rm -rf`, `cargo install` 等）或写文件操作时，以高对比度双行排版与 60s 倒计时槽位拦截执行，将审批权交还用户；
- **长程目标透视 (Layer 2 Goal/Plan Scrubber)**：在 Plan 或 Goal 模式下，实时展现宏观步骤进度计数（如 `2/5`）、任务滚动条（`planRoller`）、运行耗时，并提供可向上展开的步骤抽屉列表；
- **上下文实体注入 (Layer 3 Context/Attachment Chips)**：将外部拖拽放入、剪贴板粘贴或文件选择器导入的文件、图片、代码片段转化为 24px 微型芯片卡片，提供分类图标、即时缩略图、快速移除与右侧工作区叶级联动预览；
- **扩展中枢与模式切换 (Layer 4 Perimeter Controls)**：
  - 左侧：提供包含文件、技能、插件、MCP、扩展与定时任务的加号抽屉面板 (`ComposePlusMenu`)；
  - 权限位：提供 4 档权限矩阵（`ask` / `deep` / `plan` / `full`）极简盾形/药丸切换器 (`PermissionModeMenu`)；
  - 右侧：提供融合模型与思考档位的弱分割双槽胶囊 (`ComposerFusedTrigger`)、语音/统计扩展按钮以及具备 200ms Spring 展开动力学的墨绿色实体正圆发送控制组 (`ComposerSendControls`)；
- **并发排队管理 (Layer 0 Queue Panel)**：在模型流式回复尚未结束期间，支持用户持续输入并进入就地排队，提供序号徽标、文本摘要、直接插队发送、就地二次编辑与危险移除能力。

### 2.5 单多行跃迁中枢：`useComposerMultiline` 算法深度剖析

`apps/crish-desktop/src/components/chat-composer/useComposerMultiline.ts` 是整个输入中枢形态跃迁的“大脑”。为了解决传统实现中因反复挂载 DOM 测量导致的界面高频卡顿与死循环翻转问题，该 Hook 实现了 5 大核心设计：

#### 1. 单例 Canvas 2D 离屏度量
彻底废弃在 DOM 树中临时创建并销毁不可见 `<span>` 元素的方式，改用全局单例 Canvas 2D 进行亚像素级纯数学文本测距：
```ts
// File: apps/crish-desktop/src/components/chat-composer/useComposerMultiline.ts (L18-33)
let sharedCanvas: HTMLCanvasElement | null = null;
let sharedCtx: CanvasRenderingContext2D | null = null;

export function measureTextWidthCanvas(text: string, font: string): number {
  if (typeof window === 'undefined' && typeof document === 'undefined') return 0;
  if (!sharedCanvas && typeof document !== 'undefined') {
    sharedCanvas = document.createElement('canvas');
    sharedCtx = sharedCanvas.getContext('2d');
  }
  if (!sharedCtx && sharedCanvas) {
    sharedCtx = sharedCanvas.getContext('2d');
  }
  if (!sharedCtx) return text.length * 8;
  sharedCtx.font = font;
  return sharedCtx.measureText(text).width;
}
```

#### 2. 解耦单行容量基准计算 (Decoupled Baseline)
如果直接在多行模式下测量文本框当前的宽度，由于多行模式下文本框横跨整行，其测量宽度会远大于单行时的可用空间，从而导致状态回落判定永远无法成立。
因此算法采用了**解耦容量基准**：
$$\text{capacity} = \max(\text{MIN\_CAPACITY\_PX}, \text{layoutW} - (\text{leftW} + \text{permW} + \text{rightW} + \text{GRID\_GUTTER\_PX}))$$
无论当前处于单行还是多行模式，基准容量始终以“如果在单行模式下文本能分到的最大宽度”为基准进行虚拟衡量（`MIN_CAPACITY_PX = 200px`，`GRID_GUTTER_PX = 18px`）。

#### 3. 24px 双门限施密特迟滞区间 (Schmitt Trigger Deadband)
为防止用户在临界宽度输入特定字符时，输入框在单行与多行之间来回交替抖动，算法引入了电子工程中的施密特触发器死区（Deadband）机制：
- **突破上门限展开**：当当前为单行态时，只有当 $\text{textWidth} \ge \text{capacity}$ 时，才触发展开为多行态；
- **跌破下门限收起**：当当前为多行态时，只有当 $\text{textWidth} < (\text{capacity} - 24\text{px})$ 时，才允许收起为单行态；
- **死区区间锁定**：在 $[\text{capacity} - 24\text{px}, \text{capacity}]$ 这 24 像素的区间内，无论文本宽度如何微变，**严格保持上一帧的状态不变**。

#### 4. 120ms 振荡自愈熔断器 (Flip Circuit Breaker)
针对极端边界（如窗口缩放与快速粘贴并发），设置了高频翻转熔断保护：
- 在 `120ms`（`FLIP_WINDOW_MS`）滑动时间窗口内，若状态翻转次数累计达到 `3 次`（`FLIP_THRESHOLD`）；
- 立即强制触发 `400ms`（`LOCKOUT_DURATION_MS`）的冷却锁定期；
- 冷却期内强制锁定在多行模式，彻底阻断高频布局重排导致的浏览器掉帧。

#### 5. ResizeObserver 与 RAF 批处理协调
通过 `ResizeObserver` 监听外层网格容器宽度，在窗口发生拖拽缩放时，通过 `requestAnimationFrame` 防抖触发重测，杜绝了每帧重复度量。

#### 3.1.3 内部状态机与 60s 倒计时器逻辑
组件内部维护了一个由 `setInterval` 驱动的秒级倒计时器：
```ts
// File: apps/crish-desktop/src/components/chat-composer/ComposerPermissionBar.tsx (L46-58)
const [timeLeft, setTimeLeft] = useState(countdownSeconds);

useEffect(() => {
  setTimeLeft(countdownSeconds);
}, [countdownSeconds]);

useEffect(() => {
  if (resolved || timeLeft <= 0) return;
  const timer = setInterval(() => {
    setTimeLeft((prev) => Math.max(0, prev - 1));
  }, 1000);
  return () => clearInterval(timer);
}, [resolved, timeLeft]);
```

export function attachKind(a: ChatAttachment): AttachKind {
  if (
    a.dataUrl ||
    (a.mime && a.mime.startsWith('image/')) ||
    /\.(png|jpe?g|gif|webp|bmp|svg)$/i.test(a.name)
  ) {
    return 'image';
  }
  if (/\.(csv|tsv|xlsx?)$/i.test(a.name)) {
    return 'table';
  }
  if (/\.(ts|tsx|js|jsx|py|rs|go|java|c|cpp|h|css|json)$/i.test(a.name)) {
    return 'code';
  }
  if (a.text || /\.(md|markdown|txt|log|ya?ml|toml)$/i.test(a.name)) {
    return 'text';

  return 'file';
}

## 六、现有架构缺陷、视觉短板与冗余债务分析 (7 大缺陷深入剖析)

### 6.1 缺陷 1：四层垂直堆叠的空间挤压与最大高度溢出风险
- **现象**：当 Layer 0 排队面板（~140px）、Layer 1 审批条（~58px）、Layer 2 展开抽屉（~160px）、Layer 3 附件条（~32px）以及 Layer 4 多行输入框（~220px）同时显现时，总高度突破 `600px`；
- **隐患**：在小分辨率桌面或笔记本上，对话流历史被完全压缩至不可见状态，输入区严重失衡；
- **根因**：缺乏跨图层的复合高度预算管理器（Composite Max-Height Budget）。

---

### 6.2 缺陷 2：双源分裂的审批条与计划条 (内置层 vs 扩展 SlotOutlet)
- **现象**：输入框内部有一套 `ComposerPermissionBar` 与 `ComposerPlanProgressBar`，而外壳 `ChatComposerWrapper` 又有一套基于 `SlotOutlet` 的 `extensions/conversation-flow/PermissionBar` 和 `PlanGoalRibbons`；
- **隐患**：维护路径割裂，事件与数据模型存在重复传递与属性钻取（Props Drilling）。

---

### 6.3 缺陷 3：加号菜单选项的“功能空悬”与配置路径同质化
- **现象**：加号菜单中的“插件”、“MCP 工具”和“扩展中心”三个选项，最终全部执行了 `openSettings('plugins')`；
- **隐患**：未闭环的占位功能给用户造成困惑，属于不完整的界面半成品。

---

### 6.4 缺陷 4：发送按钮宽度弹性展开带来的网格瞬态抖动与回流
- **现象**：正圆发送按钮宽度从 `0px` 过渡到 `32px` 时，动态挤压左侧模型胶囊产生横向位移；
- **隐患**：在用户高速键入或连续删除字符时，右侧控件产生轻微横向抖动。

---

### 6.5 缺陷 5：附件条横向滚动的交互阻滞与缺乏批量操作能力
- **现象**：附件条横向滚动条被彻底隐藏，Windows/Linux 鼠标滚轮无法原生横移；且当附件数量极多时缺乏“一键清空”或“紧凑折叠”。

---

### 6.6 缺陷 6：排队面板固定高度在小屏上的断层与滚动遮挡
- **现象**：排队面板硬编码 `max-height: 140px`，产生卡片内滚动条，易与外层聊天滚动产生滚轮事件捕获冲突。

---

### 6.7 缺陷 7：单多行切换依赖离屏 Canvas 2D 的运行时上下文开销与测量偏差
- **现象**：Canvas 2D 的纯文本排版与 ProseMirror 富文本 DOM 的实际排版存在细微差异，特定字形或字体未完成加载时存在测量延迟与偏差。

---

## 七、面向前端原子化架构的重塑蓝图与演进方案

### 7.1 原子化组件库体系解耦重组规划 (Atoms / Molecules / Organisms)

按照原子化设计思想，建议将 `chat-composer` 外部控制层拆解为三层架构：

```
packages/ui-atomic/composer/
│
├── atoms/ (基础原子)
│   ├── ComposerRoundButton/     ── 统一 32x32px 正圆幽灵/实体按钮原子 (加号、语音、停止)
│   ├── SpringSendButton/        ── 独立墨绿正圆发送按钮原子，内置 200ms 弹性展开动力学
│   ├── RiskBadge/               ── 权限风险等级徽章原子
│   ├── SlotCountdown/           ── 统一倒计时槽位原子，内置色阶与脉冲动画
│   ├── PlanStepDot/             ── 计划步骤状态圆点原子 (完成、呼吸绿点、等待)
│   └── AttachTypeIcon/          ── 文件类型启发式图标原子
│
├── molecules/ (复合分子)
│   ├── AttachmentChip/          ── 24px 附件芯片分子 (缩略图、微型移除、中键删除、叶联动)
│   ├── FusedTriggerCapsule/     ── 弱分割透明物理融合胶囊分子
│   ├── PlanStepItemRow/         ── 单条计划步骤展示分子 (含单步批准动作)
│   └── QueuedMessageItem/       ── 单条排队消息分子 (含等宽序号与三态操作)
│
└── organisms/ (业务有机体)
    ├── ComposerPermissionDock/  ── Layer 1 权限审批条有机体
    ├── ComposerPlanDrawer/      ── Layer 2 计划进度条与向上展开抽屉有机体
    ├── ComposerAttachmentStrip/ ── Layer 3 附件横滑轨道有机体
    └── ComposerQueueManager/    ── Layer 0 并发消息排队管理器有机体
```

### 7.2 外部控制状态机抽象 (`InputHubStateMachine`)

将散落在各个组件内部的 `isMultiline`, `isExpanded`, `open`, `timeLeft` 等状态统一收口为独立无副作用的纯状态机：

```ts
export interface InputHubState {
  // 空间层级可见性
  layers: {
    queueVisible: boolean;
    permissionVisible: boolean;
    planVisible: boolean;
    attachmentVisible: boolean;
  };
  // 布局几何形态
  layoutMode: 'single-line-capsule' | 'multi-line-grid';
  // 运行执行态
  executionState: 'idle' | 'processing' | 'awaiting-approval';
  // 互斥菜单独占所有权
  activeMenu: 'none' | 'plus' | 'permission' | 'thinking';
}
```

### 7.3 统一外部浮动挂载槽位规范 (`Unified FloatingLayerOutlet`)
- 彻底废除 `ChatComposerWrapper` 与 `ChatComposer` 两套平行的条带渲染体系；
- 将 `composerFloatZone` 确立为整个应用唯一的浮动条出口，外部插件或会话流必须通过规范的 Provider 接口向该出口注册条带，由宿主实行统一的高度预算与优先级排序。

---

### 7.4 无头交互逻辑 (Headless Core) 与样式呈现层分离方案
将核心交互算法提取为无头 Hooks：
- `useSchmittMultiline()`：封装 Canvas 2D 离屏度量与 24px 双门限算法；
- `useSpringSendAnimation()`：基于 CSS 变量或绝对占位封装发送按钮的展开动力学，杜绝推挤周围网格；
- `useForceStopGate()`：封装单击软停、Shift+单击与 550ms 长按高危拦截确认。

---

### 7.5 渐进式重构路线图与防回归测试守护策略
1. **第一阶段 (资产清理与契约固化)**：清退加号菜单中的重复设置路由，固化现存 10 个测试套件基线；
2. **第二阶段 (原子提取与 Token 接入)**：将按钮、芯片、倒计时槽位抽取为 `packages/ui-atomic` 中的通用原子；
3. **第三阶段 (双源审批与计划条归一)**：将 `extensions/conversation-flow` 与 `chat-composer` 审批组件彻底合流；
4. **第四阶段 (空间预算与状态机落地)**：接入 `InputHubStateMachine` 与自适应高度预算，完成全量端到端回归验收。

## 八、总结与向主控汇报要点

本篇实勘导航文档对对话流输入中枢 Layer 1~3 外部控制层进行了全方位、地毯式的代码审查与交互动力学解构。

### 核心结论与现状定性：
1. **四层垂直空间堆叠架构已成熟运转**：从 Layer 1（权限）、Layer 2（计划）、Layer 3（附件）到 Layer 4（主网格），物理层次与视觉对齐度极高，无硬编码色，严格遵守 5%/6% 极柔和聚焦边框规范；
2. **核心交互细节打磨完备**：墨绿色正圆发送按钮的 200ms Spring 展开、24px 附件芯片的文件分类与中键删除、双门限 24px 施密特单多行切换防抖，均展现了优秀的交互工程水准；
3. **架构隐患集中在“双源分裂”与“垂直空间过度堆叠”**：内置图层与外部 SlotOutlet 插槽的两套体系亟待在原子化战役中做深度净收敛；部分菜单项的假性占位亦需在本次战役中标准化重塑。

本报告已全部落盘至指定交付路径，可直接作为后续原子化方案设计与代码重构的高精度导航指南。
