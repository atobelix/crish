## Executive Summary（方案核心要点总览）

本详案针对 Conex / Crish 桌面端长链路推理中“思考、工具调用与多段正文复杂交错”时**折叠逻辑一刀切、中间过程无损分段断裂、底层数据结构覆盖吞并**等核心痛点，提出一套完整的**生产级时间线分段状态机与数据流治理方案**：

1. **以正文（Text）为天然物理界标（Milestone）的分段契约系统**：
   - 彻底废除全轮次单一布尔值暴力过滤（`isProcessExpanded` 导致的 `return null`），建立 `TimelineSegment` 强类型判别联合体：`ProcessTimelineSegment`（过程段）与 `TextTimelineSegment`（正文段）；
   - 过程段内聚封装 `thought`、`tools`、`context_injection` 等过程子项，提供开箱即用的分类统计度量（`ProcessSegmentMetrics`），并对齐图五的动作分类（搜索/读取/编辑/命令/思考等）。
2. **纯函数分段算法 `partitionTimelineSegments` 与四大核心铁律推导**：
   - **铁律一（后继正文折叠断言）**：当前过程段后继只要存在 AI 正文（`hasNextText === true`），该过程段必须裁决为**可折叠（`foldable=true`）且默认折叠（`defaultExpanded=false`）**；
   - **铁律二（尾部活跃展开断言）**：当且仅当处于流式生成中且无后继正文时（`isTurnLive === true && !hasNextText`），尾部过程段维持**直出展开态（`defaultExpanded=true`）**；
   - **铁律三（纯工具终态收敛断言）**：全轮次无正文的纯工具调用终态，在 `toolCount >= 2` 时自动触发**自收敛折叠（`foldable=true && defaultExpanded=false`）**；
   - **铁律四（子代理常驻外露断言，2026-09-11 用户裁决，最高优先）**：段内只要发生过子代理调度（`subagentCount >= 1`），**无条件 `defaultExpanded=true`**，优先级高于铁律一/三；子代理是多 Agent 协同的认知主干，用户明确要求「不要被折叠，因为子代理的重要性还是比较高的」。
3. **底层数据模型 5 大断层根治与净收敛**：
   - **修复断层 1（无工具正文切分失效）**：在 `updateMessageThinking` 中校准 `streamTextOffset` 并在 `updateMessageText` 中引入双界标（`thought` + `tool_call`）隔离，杜绝跨思考正文被合并；
   - **修复断层 2（三元槽位吞并多段正文）**：在 `reconcileAssistantMessageBlocks` 中为 `text` 块建立物理块 ID 与独立槽位映射，彻底根除 `"0:text:"` Key 碰撞覆写灾难；
   - **修复断层 3（`alignToolCallBlocks` 盲目插位）**：重构工具块对齐算法，结合 `startedAt` 时间戳进行因果就近插位，根除无脑置于最后正文前的时序颠倒；
   - **修复断层 4（历史无 blocks 消息降级重组）**：通过时间戳排序与交错重水合，替代原有生硬的 `thought -> tools -> text` 扁平死板组装；
   - **修复断层 5（UI 视图层分段渲染接入）**：全面接入 HTML5 `hidden="until-found"` 原生穿透，彻底根除 `return null` 导致的 DOM 销毁、重新挂载性能震荡及 Ctrl+F 搜索失效。
4. **用户中途插入节点（Interruption / Follow-up）神圣隔离**：
   - 严格维护“用户消息为顶层独立实体”铁律，以用户消息为物理栅栏，将前序流式助手消息优雅收口折叠，后序助手消息独立开启，严禁将用户输入包入助手折叠块中。

## 一、方案背景与架构演进目标

### 1.1 从“全轮次暴力单体”演进到“正文界标分段状态机”

在当前的 Conex / Crish 桌面端实现中，AI 助手的交互面临严重体验断层：
- **现实场景**：Agent 解决复杂问题时往往经历多轮推理：
  $$\text{思考 1} \to \text{搜索工具} \to \text{阶段性解释正文 1} \to \text{后续思考 2} \to \text{修改代码工具} \to \text{最终总结正文 2}$$
- **现状缺陷**：
  1. `MessageContent.tsx:352-354` 仅维护全局布尔值 `isProcessExpanded`，折叠时粗暴执行：
     ```tsx
     if (!isProcessExpanded && (item.kind === 'tools' || item.kind === 'thought')) return null;
     ```
     这不仅导致中间正文与最终正文无法跟各自的前序过程关联，而且直接将 DOM 树销毁，彻底破坏了 HTML5 原生搜索穿透（Ctrl+F）和虚拟滚动（VSM）的高度稳定性；
  2. `turnProcessState.ts:161` 将非最终答案的中间正文判定为 `processMember`，导致中间过渡文本在折叠时一同被吞没；
  3. 底层数据流中缺乏对多段正文的唯一标识与槽位隔离，导致流式推送与时间线重水合时多段正文频繁被覆盖丢失。

```
【现有架构：全局单体打平过滤】
SessionMessage ──► timelineReconciler (三元槽位 Key 碰撞丢失正文)
                         │
                         ▼
             buildAssistantTimeline (一维打平 items)
                         │
                         ▼
             MessageContent.tsx (顶层单体 Header + 全局 return null) ──► 灾难：DOM 销毁、搜索穿透失效、中间文本丢失

【本方案目标架构：正文物理界标分段状态机】
SessionMessage ──► 加固版 Reconciler & Store (游标校准 + 物理块 ID 槽位保全)
                         │
                         ▼
             AssistantTimelineItem[] (线性时间线一等公民)
                         │
                         ▼
         partitionTimelineSegments (纯函数分段状态机 · 三大铁律推导)
                         │
                         ▼
                 TimelineSegment[]
           ├── ProcessTimelineSegment (0) ──► FoldableProcessSection (图五折叠态 · until-found)
           ├── TextTimelineSegment (0)    ──► ProcessItemRenderer (Markdown 阶段正文常驻平铺)
           ├── ProcessTimelineSegment (1) ──► FoldableProcessSection (图五折叠态 · until-found)
           └── TextTimelineSegment (1)    ──► ProcessItemRenderer (Markdown 总结正文常驻平铺)
```

### 1.2 核心架构原则与设计红线

根据根目录 `AGENTS.md`、`ANTI_OVERENGINEERING_GUARDRAILS.md` 与反退避准则，本方案恪守以下五大红线：
1. **单一真理源（SSOT）**：`AssistantTimelineItem[]` 仍然作为底层物理时序的纯粹表达；`TimelineSegment[]` 为纯函数衍生视图（Derived View），绝不反向污染数据库/Store 中的原始事件；
2. **正文神圣不可折叠性**：正文是人类与 AI 对话的高价值信息资产，**正文段（Text Segment）永远不可被折叠隐藏**；所有折叠只作用于正文之前的过程段（Process Segment）；
3. **彻底根除 `return null` 销毁 DOM**：过程段折叠态必须挂载真实 DOM 节点并施加 HTML5 `hidden="until-found"`，确保原生 `beforematch` 搜索唤醒与 VSM 尺寸自愈；
4. **零魔法补偿（No Hack / No Workaround）**：穿透解决数据层 5 大断层，严禁使用延迟 `setTimeout` 补偿游标或盲目追加正文；
5. **用户节点神圣独立性**：用户中途插入的消息在数据层和视图层永远作为一等公民兄弟节点，严禁嵌套折叠。

> 2. **纯逻辑实现唯一宿主**：`apps/crish-desktop/src/api/tool-presentation/timelineSegmenter.ts`（与 `timelineReconciler.ts` / `timelineNormalizer.ts` 同域，禁止落到 `components/chat-message/`——详见 `07-方案收敛审计与SSOT裁决.md` §2）。
> 3. **度量与聚合唯一宿主**：`apps/crish-desktop/src/api/tool-presentation/processMetricsEngine.ts`。`ProcessSegmentMetrics` 与 `partitionTimelineSegments` **在本战役中只允许存在一份实现**，任何并行详案（04）不得复制第二份。

### 2.1 判别联合体设计：`ProcessTimelineSegment` vs `TextTimelineSegment`

```typescript
/**
 * 过程段子项联合契约：思维链思考、工具调用集合、系统上下文注入
 */
export type ProcessSegmentItem =
  | TimelineThoughtItem
  | TimelineToolsItem
  | TimelineInjectionItem;

/**
 * 动作主导分类（对齐图五折叠栏主导图标与细颗粒度文案）
 *
 * 图标映射（SSOT：AppIcon/iconMap，底层 @hugeicons/core-free-icons；
 * 严禁裸 emoji、严禁绕过 AppIcon 直连图标库）：
 *   search   → 'search'
 *   read     → 'file-text'
 *   edit     → 'file-edit'
 *   command  → 'terminal'
 *   subagent → 'brain-circuit'
 *   thought  → 'brain-circuit'
 *   mixed    → 'code'
 */
export type ProcessLeadAction =
  | 'search'      // 搜索主导（如 search_web, grep_search, find_by_name）
  | 'read'        // 读取主导（如 read_file, view_file, read_url_content）
  | 'edit'        // 编辑修改主导（如 write_to_file, replace_file_content）
  | 'command'     // 命令执行主导（如 run_command）
  | 'subagent'    // 子代理调度主导（如 invoke_subagent）
  | 'thought'     // 深度思考主导
  | 'mixed';      // 多种混合动作

/**
 * 过程段聚合度量指标（0 计算成本直出图五统计）
 *
 * 【SSOT 裁决】本契约是全场唯一权威定义；02/04 详案中的同名接口一律删除，
 * 字段命名以本处为准（工具按「次」记 searchCount/readCount/commandCount/subagentCount，
 * 文件按「个」去重的只有 editFilesCount/readFilesCount 两个计数集合）。
 */
export interface ProcessSegmentMetrics {
  /** 思维链思考块数量 */
  thoughtCount: number;
  /** 思考总耗时（毫秒） */
  thoughtDurationMs: number;
  /** 工具调用总次数（含 subagent 调用，作为折叠门槛判定基数） */
  toolCount: number;
  /** 子 Agent 调度次数（toolCount 的子集，单独暴露用于「协作」维度与不可折叠特权） */
  subagentCount: number;
  /** 搜索类工具调用次数（按次累加，不去重） */
  searchCount: number;
  /** 命令执行类工具调用次数（按次累加，不去重） */
  commandCount: number;
  /** 读取类工具调用涉及的文件/URL 去重集合大小（按「个」计） */
  readFilesCount: number;
  /** 编辑/写入类工具调用涉及的文件去重集合大小（按「个」计） */
  editFilesCount: number;
  /** 读取类工具涉及的路径集合（供 02 详案去重与调试，禁止跨层序列化） */
  readPaths: readonly string[];
  /** 编辑类工具涉及的路径集合（同上） */
  editPaths: readonly string[];
  /** 系统上下文注入卡片数 */
  injectionCount: number;
  /** 过程段总耗时（毫秒） */
  totalDurationMs: number;
  /** 是否存在正在执行中的工具/子代理 */
  hasRunning: boolean;
  /** 是否存在执行失败/报错的工具 */
  hasError: boolean;
  /** 是否处于思考流式打字中 */
  isStreaming: boolean;
  /** 主导动作类别（用于折叠栏左侧首个高亮图标渲染） */
  leadAction: ProcessLeadAction;
}

/**
 * 过程分段实体（Process Timeline Segment）
 * 承载某段正文之前的思考、工具与上下文注入
 */
export interface ProcessTimelineSegment {
  readonly kind: 'process';
  /** 稳定分段唯一标识（如 `${msgId}-seg-proc-0`） */
  readonly key: string;
  /** 分段序号（在全段落列表中的全局连续索引，0-based） */
  readonly segmentIndex: number;
  /** 过程段局部索引（第几个过程段，0-based） */
  readonly processIndex: number;
  /** 关联的消息/轮次编号 */
  readonly turnIndex: number;
  /** 过程子项数组（严格保持物理发生时序） */
  readonly items: readonly ProcessSegmentItem[];
  /** 预聚合统计指标（供图五发丝控制栏直出渲染） */
  readonly metrics: ProcessSegmentMetrics;
  /**
   * 折叠资格判定（折叠状态机推导真值）：
   * 是否具备可折叠资格。纯文本无工具不具备折叠资格，纯工具 >= 2 或存在后继正文具备折叠资格
   */
  readonly foldable: boolean;
  /**
   * 默认展开状态（折叠状态机推导真值）：
   * true: 直出展开态（图一至图四）；false: 默认折叠态（图五发丝控制栏）
   */
  readonly defaultExpanded: boolean;
  /**
   * 是否处于实时生成中：
   * 仅当处于活跃轮次且无后继正文时为 true
   */
  readonly isLive: boolean;
  /**
   * 是否存在后继 AI 正文：
   * 核心判定铁律的依据
   */
  readonly hasNextText: boolean;
  /**
   * 段内是否存在子代理协作（铁律四派生标记）：
   * true 时该段常驻外露，FoldableProcessSection 必须跳过 hidden="until-found" 挂载
   */
  readonly forceExpanded: boolean;
  /**
   * 图五折叠栏摘要文案（唯一由 processMetricsEngine.formatSegmentSummary 派生，
   * 禁止在视图层二次拼接，确保摘要格式 SSOT 唯一）
   */
  readonly summaryText: string;
}

/**
 * 正文分段实体（Text Timeline Segment）
 * 对话时间线上的天然物理界标（Milestone）
 */
export interface TextTimelineSegment {
  readonly kind: 'text';
  /** 稳定分段唯一标识（如 `${msgId}-seg-text-0`） */
  readonly key: string;
  /** 分段序号（在全段落列表中的全局连续索引，0-based） */
  readonly segmentIndex: number;
  /** 正文段局部索引（第几个正文段，0-based） */
  readonly textIndex: number;
  /** 关联的消息/轮次编号 */
  readonly turnIndex: number;
  /** 对应的原始时间线正文项引用 */
  readonly item: TimelineTextItem;
  /** 正文 Markdown 文本内容 */
  readonly content: string;
  /** 是否为全轮次最终收口正文（Final Answer） */
  readonly isFinal: boolean;
  /** 是否正处于流式打字机输出中 */
  readonly isStreaming: boolean;
  /** 开始时间戳（毫秒）与累计耗时 */
  readonly startTime?: number;
  readonly durationMs?: number;
}

/**
 * 统一时间线分段契约联合体
 */
export type TimelineSegment = ProcessTimelineSegment | TextTimelineSegment;
```

### 2.2 工具动作语义分类器（对齐图五视觉规范）

为了向图五折叠栏（`已搜索 X 次 · 已读取 Y 个文件`）提供精确的度量统计，系统需要一个确定性的工具动作分类器。

> **【收敛修订 · 反裸子串匹配铁律】**
> 初版草案使用 `name.includes('list')` / `name.includes('read')` 这类裸子串匹配，
> 存在**系统性误判**：`list_dir` 会被错分到 read（实际是探查搜索）、`read_thread` /
> `spreadsheet_read` 会被错分、`delete_file` 既不含 write 也不含 replace 而漏分类。
> 收敛方案：改为**「精确名注册表 + 有序后缀/前缀规则」两段式**，并把分类表列入可测契约。
>
> 本分类器**唯一宿主**为 `apps/crish-desktop/src/api/tool-presentation/toolActionClassifier.ts`；
> 01 与 02 详案共用此一份，**禁止各自实现第二套**。

```typescript
// apps/crish-desktop/src/api/tool-presentation/toolActionClassifier.ts

import type { ProcessLeadAction } from './toolPresentationTypes';

/**
 * 第一段：精确名注册表（覆盖全部已知工具，1:1 对齐主注册表）。
 * 新增工具必须在此登记，未登记工具走第二段规则 + DEV 告警。
 */
const EXACT_ACTION_TABLE: Readonly<Record<string, ProcessLeadAction>> = {
  // ── 搜索/探查 ──
  grep_search: 'search',
  search_web: 'search',
  find_by_name: 'search',
  list_dir: 'search',
  glob: 'search',
  codebase_search: 'search',
  // ── 读取 ──
  read_file: 'read',
  view_file: 'read',
  read_url_content: 'read',
  read_notebook: 'read',
  // ── 编辑/写入（含删除与重命名，语义上同属「变更」域）──
  write_to_file: 'edit',
  replace_file_content: 'edit',
  edit_file: 'edit',
  delete_file: 'edit',
  move_file: 'edit',
  create_file: 'edit',
  apply_patch: 'edit',
  // ── 命令 ──
  run_command: 'command',
  bash: 'command',
  pwsh: 'command',
  run_terminal_cmd: 'command',
  // ── 协作（子代理，最高特权，见 §3.4）──
  invoke_subagent: 'subagent',
  run_subagent: 'subagent',
  wait_subagents: 'subagent',
  send_message: 'subagent',
  // ── 思考 ──
  sequential_thinking: 'thought',
};

/**
 * 第二段：有序规则兜底（仅对未登记名生效；按数组顺序短路，顺序即优先级）。
 * 前缀/后缀语义化匹配，杜绝 includes 裸子串。
 */
const FALLBACK_RULES: ReadonlyArray<readonly [RegExp, ProcessLeadAction]> = [
  [/^sub_?agent|_subagent$|^invoke_agent$/, 'subagent'],
  [/_(search|grep|find|glob|scan)$|^search_/, 'search'],
  [/^(read|view|inspect)_|_read$/, 'read'],
  [/^(write|edit|replace|patch|modify|create|delete|move|rename)_/, 'edit'],
  [/_(exec|command|cmd|shell|terminal)$|^(bash|pwsh|sh)$/, 'command'],
];

/**
 * 根据工具名称分类动作语义（O(1) 查表 + O(k) 规则匹配，k 为规则常数）
 */
export function classifyToolAction(toolName: string): ProcessLeadAction {
  const name = (toolName || '').trim().toLowerCase();
  if (!name) return 'mixed';

  const exact = EXACT_ACTION_TABLE[name];
  if (exact) return exact;

  for (const [re, action] of FALLBACK_RULES) {
    if (re.test(name)) return action;
  }

  if (import.meta.env?.DEV) {
    console.warn(`[classifyToolAction] 未登记工具名，退化为 mixed: ${toolName}`);
  }
  return 'mixed';
}
```

| 工具名 | 期望分类 | 说明 |
| :--- | :--- | :--- |
| `list_dir` | `search` | 探查类，非 read（纠正初版裸子串误判） |
| `delete_file` | `edit` | 变更类（纠正初版漏分类） |
| `invoke_subagent` | `subagent` | 协作特权域 |
| `run_command` | `command` | 精确登记 |

## 三、纯函数分段状态机（`partitionTimelineSegments`）核心设计与数学推导

### 3.1 核心铁律推导系统与数学不变量

时间线切分不是简单的数组分组，而是一套**具有因果时序与生命周期守卫的确定性状态机**。

设输入为线性时间线数组 $I = [i_0, i_1, \dots, i_{n-1}]$，整轮活跃标记为 $\text{isTurnLive} \in \{\text{true}, \text{false}\}$。  
我们将 $I$ 投影为段落序列 $S = [s_0, s_1, \dots, s_{m-1}]$，其中每个过程段 $P \in S$ 必须满足以下数学推导约束：

```
                    【分段折叠判定核心推导状态机】
                               │
                               ▼
               当前过程段 P 处于时间线位置 k
                               │
            ┌──────────────────┴──────────────────┐
            │ 是否存在后继 AI 正文 (hasNextText)？ │
            └──────────────────┬──────────────────┘
                      是       │       否
        ┌──────────────────────┘       └──────────────────────┐
        ▼                                                     ▼
【铁律一：中间过程必折叠】                               当前过程段位于时间线末尾
foldable = true                                               │
defaultExpanded = false                                       │
isLive = false                          ┌─────────────────────┴─────────────────────┐
                                        │ 整轮是否处于活跃流式中 (isTurnLive)？      │
                                        └─────────────────────┬─────────────────────┘
                                                      是      │      否 (已达终态)
                                        ┌─────────────────────┘      └─────────────────────┐
                                        ▼                                                  ▼
                         【铁律二：尾部流式直出展开】                         【铁律三：纯工具终态收敛】
                         foldable = true                                  toolCount >= 2 ?
                         defaultExpanded = true                           ├── 是: foldable=true, defaultExpanded=false
                         isLive = true                                    └── 否: foldable=false, defaultExpanded=true
```

#### 铁律一：中间过程必须可折叠且默认收拢（Intermediate Process Convergence）
$$\forall P \in S, \text{ if } \text{hasNextText}(P) = \text{true} \implies \begin{cases} P.\text{foldable} = \text{true} \\ P.\text{defaultExpanded} = \text{false} \\ P.\text{isLive} = \text{false} \end{cases}$$
- **推导Rationale**：用户看 AI 回复的本质是获取正文结论。既然 AI 已经在该过程之后输出了人类可读的正文（无论阶段性解释还是终结论），那么服务于该正文的前置过程在认知层面上就已经**履职完毕（Mission Accomplished）**。因此必须收敛收起，让用户的视觉焦点直接落在正文上。

#### 铁律二：尾部活跃过程直出展开（Tail Live Process Streaming）
$$\forall P \in S, \text{ if } \neg \text{hasNextText}(P) \land \text{isTurnLive} = \text{true} \implies \begin{cases} P.\text{foldable} = \text{true} \\ P.\text{defaultExpanded} = \text{true} \\ P.\text{isLive} = \text{true} \end{cases}$$
- **推导Rationale**：AI 正在思考或正在执行工具，且尚未产出正文。此时展开过程向用户展示实时的进度、调用参数、终端输出与思考文本，能够极大缓解用户的等待焦虑，建立对 Agent 自主操作的安全感与掌控感（参考图一至图四细颗粒度呈现）。

#### 铁律三：纯工具终态轮次自收敛（Pure-Tool Terminal Self-Convergence）
$$\forall P \in S, \text{ if } \neg \text{hasNextText}(P) \land \text{isTurnLive} = \text{false} \implies \begin{cases} \text{if } P.\text{metrics.toolCount} \ge 2: & P.\text{foldable} = \text{true} \land P.\text{defaultExpanded} = \text{false} \\ \text{if } P.\text{metrics.toolCount} < 2: & P.\text{foldable} = \text{false} \land P.\text{defaultExpanded} = \text{true} \end{cases}$$
- **推导Rationale**：当 AI 任务不需要文本回答（例如静默执行批处理任务、自纠错任务），终态时没有正文。若工具调用次数 $\ge 2$，说明是批量过程，应当自收敛折叠，避免冗长的工具栈刷屏；若工具调用仅 1 次，直接铺开展出最清晰。

#### 铁律四：子代理协作段常驻外露（Subagent Visibility Privilege · 2026-09-11 用户裁决 · 最高优先）

$$\forall P \in S, \text{ if } P.\text{metrics.subagentCount} \ge 1 \implies \begin{cases} P.\text{foldable} = \text{true} \\ P.\text{defaultExpanded} = \text{true} \end{cases}$$

该断言**优先级高于铁律一与铁律三**：即 $\text{subagentCount} \ge 1$ 时，即便 `hasNextText === true`（本应折叠）或 `toolCount >= 2`（本应自收敛），仍裁决 `defaultExpanded = true`。

- **推导 Rationale（用户裁决原文）**：
  > 「开启子代理的时候，最好也保留一下，不要被折叠，因为子代理的重要性还是比较高的。」
- **为什么这是架构级不变量而非 UI 偏好**：子代理调度是多 Agent 协同的**认知主干**。它向用户暴露「系统正在并行分工、当前哪一路在执行、哪一路等待」，是用户在长链路任务中建立信任、定位异常的**唯一可见窗口**。把子代理折叠进 33px 发丝栏，等于剥夺用户对并发拓扑的知情权，与战役「缓解等待焦虑、建立掌控感」的效果锁正面冲突。
- **落地形态（跨三处契约）**：
  1. **分段状态机（本文件）**：`partitionTimelineSegments` 在铁律裁决时**先判 subagent**，
     命中即短路返回 `defaultExpanded = true`（代码见 §3.2 `flushProcessSegment`）；
  2. **度量与摘要（02 详案）**：`subagentCount > 0` 时「协作」维度**强制参与语序拼接**，
     永不被"非零维度过滤"裁掉；主导图标仲裁优先级提升到与 `edit` 同级；
  3. **折叠容器（04/06 详案）**：`FoldableProcessSection` 接收 `forceExpanded` 提示位，
     子代理段在 DOM 上不挂载 `hidden="until-found"`，DOM 常驻可见。
- **与用户手动操作的边界**：铁律四约束的是**默认态**（`defaultExpanded`）。用户显式点击收起后，
  `userExpandedMap[key] = false` 覆盖 default，允许手动折叠——不赋予组件"拒绝用户操作"的权限。
- **否定断言（强制）**：`N-ASSERT-11`：含 `invoke_subagent` 的过程段在终态
  **不得**满足 `defaultExpanded === false`；且该段 DOM 不得携带 `hidden="until-found"`。

```typescript
// apps/crish-desktop/src/api/tool-presentation/timelineSegmenter.ts

import type {
  AssistantTimelineItem,
  TimelineSegment,
  ProcessTimelineSegment,
  TextTimelineSegment,
  ProcessSegmentItem,
} from './toolPresentationTypes';
import { aggregateProcessMetrics } from './processMetricsEngine';

/**
 * 纯函数：将线性时间线列表物理分段为正文界标分段序列
 *
 * @param linearItems 底层排好序的时间线项
 * @param isTurnLive 当前消息所属的整轮是否仍处于流式生成/执行中
 * @param msgId 当前消息唯一标识（用于生成稳定全局 key）
 */
export function partitionTimelineSegments(
  linearItems: readonly AssistantTimelineItem[],
  isTurnLive: boolean,
  msgId: string = 'msg'
): TimelineSegment[] {
  const segments: TimelineSegment[] = [];
  let currentProcessBuf: ProcessSegmentItem[] = [];
  let globalSegmentIndex = 0;
  let processSeq = 0;
  let textSeq = 0;

  // 1. 预先提取所有正文项在 linearItems 中的索引，供 O(1) 前瞻判定后继正文
  const textItemIndices: number[] = [];
  for (let i = 0; i < linearItems.length; i++) {
    if (linearItems[i]!.kind === 'text') {
      textItemIndices.push(i);
    }
  }

  /**
   * 闭包：将缓冲的过程项收口为一个 ProcessTimelineSegment
   * @param atItemIndex 触发收口时的 linearItems 索引（扫描结束时传入 linearItems.length）
   */
  const flushProcessSegment = (atItemIndex: number) => {
    if (currentProcessBuf.length === 0) return;

    // 前瞻断言：在当前项索引 atItemIndex 之后，是否仍存在正文项？
    const hasNextText = textItemIndices.some((idx) => idx >= atItemIndex);
    const metrics = aggregateProcessMetrics(currentProcessBuf);

    // 折叠状态机四大铁律裁决
    let foldable = false;
    let defaultExpanded = false;
    let isSegmentLive = false;

    if (metrics.subagentCount >= 1) {
      // ★ 铁律四（最高优先）：存在子代理协作 → 常驻外露，禁止默认折叠。
      //   即便 hasNextText 为真也在此短路，绝不落入铁律一的折叠分支。
      foldable = true;
      defaultExpanded = true;
      isSegmentLive = isTurnLive && !hasNextText;
    } else if (hasNextText) {
      // 铁律一：后继有正文，必须收敛折叠，绝非活跃态
      foldable = true;
      defaultExpanded = false;
      isSegmentLive = false;
    } else if (isTurnLive) {
      // 铁律二：流式进行中，保持展开直出与活跃态
      foldable = true;
      defaultExpanded = true;
      isSegmentLive = true;
    } else {
      // 铁律三：终态无正文，依据工具数量收敛
      if (metrics.toolCount >= 2) {
        foldable = true;
        defaultExpanded = false;
      } else {
        foldable = false;
        defaultExpanded = true;
      }
      isSegmentLive = false;
    }

    const firstItem = currentProcessBuf[0]!;
    const segment: ProcessTimelineSegment = {
      kind: 'process',
      key: `${msgId}-seg-proc-${processSeq}`,
      segmentIndex: globalSegmentIndex++,
      processIndex: processSeq++,
      turnIndex: firstItem.turnIndex ?? 0,
      items: [...currentProcessBuf],
      metrics,
      foldable,
      defaultExpanded,
      isLive: isSegmentLive,
      hasNextText,
      // 铁律四派生标记：供 FoldableProcessSection 决定是否跳过 hidden="until-found" 挂载
      forceExpanded: metrics.subagentCount >= 1,
      summaryText: '', // 由 processMetricsEngine.formatSegmentSummary 派生（见 02 详案 §4）
    };
    segments.push(segment);

    currentProcessBuf = [];
  };

  // 2. 单趟扫描线性 items
  for (let i = 0; i < linearItems.length; i++) {
    const item = linearItems[i]!;

    if (item.kind === 'text') {
      // 遇到正文界标：先收口前置过程段
      flushProcessSegment(i);

      const isLastText = textItemIndices[textItemIndices.length - 1] === i;
      const isFinal = isLastText && !isTurnLive;

      // 推入正文段（常驻一等公民）
      segments.push({
        kind: 'text',
        key: `${msgId}-seg-text-${textSeq}`,
        segmentIndex: globalSegmentIndex++,
        textIndex: textSeq++,
        turnIndex: item.turnIndex ?? 0,
        item,
        content: item.content,
        isFinal,
        isStreaming: Boolean(!isFinal && isTurnLive && isLastText),
        startTime: item.startTime,
        durationMs: item.durationMs,
      } as TextTimelineSegment);
    } else {
      // 思考、工具、上下文注入均归入过程缓冲
      currentProcessBuf.push(item);
    }
  }

  // 3. 收口末尾残余过程段（如正在流式调用的工具，或无正文的纯工具终态）
  flushProcessSegment(linearItems.length);

  return segments;
}
```

### 4.1 断层 1 修复：无工具思考+正文交错时的游标校准

#### 根因回顾（`sessionMessageActionsCore.ts:223-232` 与 `sessionMessageActionsTools.ts:91`）
- `msg.streamTextOffset` 仅在 `addMessageToolCall` 发生时才被更新为 `msg.text.length`；
- 在 `updateMessageThinking` 时，没有推进 `streamTextOffset`；
- 导致在无工具调用但有多轮思考（$\text{正文 1} \to \text{思考 2} \to \text{正文 2}$）时，`updateMessageText` 从 blocks 倒序查找 `text` 块，直接命中了思考 2 之前的正文 1 块，把正文 2 的内容追加合并进了正文 1，将原本插入在中间的 `thought` 挤到了正文末尾或完全错乱！

#### 生产级修复实现
在 `sessionMessageActionsCore.ts` 中执行两项刚性加固：
1. **在 `updateMessageThinking` 中刷新游标**：一旦开启新轮次思考，记录当前累计正文长度；
2. **在 `updateMessageText` 中引入双重物理界标隔离**：定位最新文本承接块时，必须确保该正文块位于**最后一个工具块 AND 最后一个思考块之后**！

### 4.2 断层 2 修复：三元槽位合并算法吞并多段正文根治

#### 根因回顾（`timelineReconciler.ts:96-107`）
- 合并槽位 Key 使用了 `${cleanTurn}:${type}:${id}`；
- 但此前所有的 `text` 块既没有 `id`，`turnIndex` 也为 `undefined`（被清洗为 `0`）；
- 导致整条消息中所有的正文块的槽位 Key 全部退化为 `"0:text:"`！
- 在 `existingMap.set(key, b)` 时，后面的正文块直接把前面的正文块覆盖抹杀。

#### 生产级修复实现
在 `timelineReconciler.ts` 中建立**正文块一等物理槽位契约**：
1. 若块本身携带显式 `id`，则 Key 为 `${cleanTurn}:${type}:${id}`；
2. 若块为 `text` 且缺失 `id`，在建立 Map 时分配基于顺序的槽位 Key（`${cleanTurn}:text:idx_${seq}`），禁止同轮多正文在 Map 中发生 Key 碰撞覆盖；
3. 为历史孤儿块（orphan blocks）保留无损追加策略。

```typescript
// 修复文件：apps/crish-desktop/src/api/tool-presentation/timelineReconciler.ts

/**
 * 为时间线块生成抗碰撞的稳定槽位 Key
 */
function getReconciliationSlotKey(
  b: MessageTimelineBlock,
  cleanTurn: number,
  typeSeqMap: Map<string, number>
): string {
  if (b.id && b.id.trim()) {
    return `${cleanTurn}:${b.type}:${b.id.trim()}`;
  }
  // 无 id 块（尤其是历史 text 块）：分配按类型递增的序列槽位，禁止同名覆写
  const typeKey = `${cleanTurn}:${b.type}`;
  const seq = typeSeqMap.get(typeKey) ?? 0;
  typeSeqMap.set(typeKey, seq + 1);
  return `${cleanTurn}:${b.type}:#seq_${seq}`;
}

export function reconcileAssistantMessageBlocks(
  existingBlocks: MessageTimelineBlock[] | undefined,
  incomingBlocks: MessageTimelineBlock[]
): MessageTimelineBlock[] {
  const result: MessageTimelineBlock[] = [];
  const existingMap = new Map<string, MessageTimelineBlock>();
  const existingSeqMap = new Map<string, number>();

  // 1. 注册既有持久块（重点保护 thought、tool_call 与多段 text）
  if (existingBlocks && existingBlocks.length > 0) {
    for (const b of existingBlocks) {
      const cleanTurn = sanitizeTimelineTurnIndex(b.turnIndex);
      const key = getReconciliationSlotKey(b, cleanTurn, existingSeqMap);
      existingMap.set(key, { ...b, turnIndex: cleanTurn });
    }
  }

  // 2. 融合 incoming blocks
  const incomingSeqMap = new Map<string, number>();
  if (incomingBlocks && incomingBlocks.length > 0) {
    for (const b of incomingBlocks) {
      const cleanTurn = sanitizeTimelineTurnIndex(b.turnIndex);
      const key = getReconciliationSlotKey(b, cleanTurn, incomingSeqMap);
      if (existingMap.has(key)) {
        result.push({ ...existingMap.get(key)!, ...b, turnIndex: cleanTurn });
        existingMap.delete(key);
      } else {
        result.push({ ...b, turnIndex: cleanTurn });
      }
    }
  }

  // 3. 追加未被覆盖的历史孤儿块（100% 永久保全历史思考、工具与独立正文段）
  for (const [, orphan] of existingMap) {
    result.push(orphan);
  }

  // 严格按流式到达的物理因果顺序返回，禁止强制重排序
  return result;
}
```

### 4.3 断层 3 修复：`alignToolCallBlocks` 盲目插位根治

#### 根因回顾（`timelineReconciler.ts:45-56`）
- 当 blocks 中缺失某个 `toolCall` 需要补齐时，旧算法寻找最后一个 `text` 块，并将缺失工具统统插到其之前：
  ```typescript
  for (let i = next.length - 1; i >= 0; i--) {
    if (next[i]?.type === 'text') { insertAt = i; break; }
  }
  ```
- 如果消息包含多段正文（正文 1 $\to$ 工具 2 $\to$ 正文 2），若工具 1 缺失，它会被错误插在正文 2 之前（即正文 1 的后面、工具 2 的后面），导致时序彻底倒流颠倒！

#### 生产级修复实现
引入**因果时间戳就近定位插位算法（Temporal Proximity Insertion）**：
- 优先根据工具调用的开始时间戳 `startedAt`（或 `startTime`），在 blocks 序列中通过时间戳二分/线性对比，将其精准插回历史真实发生的时段之间；
- 兜底规则：若时间戳未知，则插入到**首个正文块之前**或**所属轮次思考块之后**，绝不盲目跨越到尾部正文之前。

```typescript
// 修复文件：apps/crish-desktop/src/api/tool-presentation/timelineReconciler.ts

export function alignToolCallBlocks(
  blocks: MessageTimelineBlock[] | undefined,
  tools: MessageToolCall[]
): MessageTimelineBlock[] {
  const toolMap = new Map(tools.map((t) => [t.id, t]));
  const next = (blocks || []).filter(
    (b) => b.type !== 'tool_call' || (b.id != null && toolMap.has(b.id))
  );
  const inBlocks = new Set(
    next.filter((b) => b.type === 'tool_call' && b.id).map((b) => b.id as string)
  );
  const missing = tools.filter((t) => !inBlocks.has(t.id));
  if (missing.length === 0) return next;

  // 对每一个缺失的工具块，执行精准因果插位
  for (const t of missing) {
    const tTime = t.startedAt || 0;
    let targetIndex = -1;

    if (tTime > 0) {
      // 策略 A：按时间戳寻找首个时间戳晚于该工具的块，插在其前
      for (let i = 0; i < next.length; i++) {
        const bTime = next[i]!.startTime || 0;
        if (bTime > tTime) {
          targetIndex = i;
          break;
        }
      }
    }

    if (targetIndex === -1) {
      // 策略 B：若未找到更晚的块，插在末尾正文块之前（若无正文则插在末尾）
      for (let i = next.length - 1; i >= 0; i--) {
        if (next[i]?.type === 'text') {
          targetIndex = i;
          break;
        }
      }
    }

    const newBlock: MessageTimelineBlock = {
      type: 'tool_call',
      id: t.id,
      startTime: t.startedAt,
      durationMs: t.durationMs,
    };

    if (targetIndex >= 0) {
      next.splice(targetIndex, 0, newBlock);
    } else {
      next.push(newBlock);
    }
  }

  return next;
}
```

### 4.4 断层 4 修复：历史无 blocks 消息降级重组的时序自愈

对于老版本会话或外部导入的未包含 `blocks` 数组的 `SessionMessage`，旧版 `timelineNormalizer.ts:224-238` 采用完全死板的拼接：
$$\text{injections} \to \text{pushFallbackTurns (thoughts)} \to \text{tools} \to \text{text}$$
这彻底抹杀了历史思考与工具的交替关系。

**自愈方案**：
在 `normalizeAssistantTimeline` 中，当 `msg.blocks` 为空时，不再静态拼装，而是利用 `msg.thinkingTurns` 的时间戳与 `msg.toolCalls` 的 `startedAt` 时间戳进行一次**时序归并排序（Temporal Merge Sort）**，动态生成出具备真实交错顺序的 `msg.blocks`，再进入分段状态机。

### 5.2 用户中途插入节点（User Steering / Interruption）时序隔离与收口契约

针对战役核心效果锁：
> “若 AI 在工作过程中用户发送消息，必须根据用户插入节点将 AI 输出内容分开折叠组织，严禁将用户消息折叠进 AI 的过程块中。”

#### 架构实现机制
1. **数据模型物理隔离**：
   - 用户发送消息时，由 `enqueueFollowUpMessage`（`slashSendQueueHelper.ts:123`）在会话根列表 `session.messages` 中以独立实体（`sender: 'user', status: 'queued'`）追加，绝不混入当前 Assistant 消息的 `blocks`；
2. **前序助手消息自动优雅收口**：
   - 引擎接收到 Follow-Up 事件后，当前正在运行的 Assistant 消息立即执行 `executeStreamCompletion`，状态转为 `completed` 或 `stopped`；
   - 随着该消息进入终态（`isTurnLive: false`），其内部的 `partitionTimelineSegments` 依据铁律自动将所有的前置过程段执行收敛折叠（`defaultExpanded = false`）；
3. **视觉多段隔离效果**：
   - 虚拟滚动列表中呈现为：
     $$\text{Assistant 1 (过程折叠 + 已产出内容)} \to \text{User Interruption 气泡 (平铺外露)} \to \text{Assistant 2 (新流展开)}$$
   - 结构上实现物理级的神圣隔离，绝对不可能发生“用户消息被包裹在助手折叠栏内部”的严重退化。

      expect(proc.metrics.subagentCount).toBe(1);
      // 若无子代理，toolCount>=2 会折叠；有子代理则强制展开
      expect(proc.defaultExpanded).toBe(true);
      expect(proc.forceExpanded).toBe(true);
    }
  });
});
