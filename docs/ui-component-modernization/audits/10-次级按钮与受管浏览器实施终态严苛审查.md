## 一、原子按钮（Button / IconButton）严苛缺陷审查

### 1. [严重级别: 严重] 深色模式下 Secondary 按钮 `:disabled` 状态 CSS 变量与选择器特异性割裂
- **文件路径**：`apps/crish-desktop/src/components/ui/Button/Button.module.css:152-169`
- **缺陷剖析**：
  在 `Button.module.css` 中，深色模式 Secondary 选择器通过 `:global(html[data-theme='dark']) .buttonSecondary` 重设了 CSS 变量：
  ```css
  :global(html[data-theme='dark']) .buttonSecondary,
  :global(html[data-theme='dark']) .button[data-variant='secondary'] {
    --btn-bg: color-mix(in srgb, var(--text-primary) 6.5%, var(--bg-card));
    --btn-border: color-mix(in srgb, var(--border-color) 80%, var(--text-primary) 20%);
    ...
  }
  ```
  而在后续的禁用态规则中：
  ```css
  .buttonSecondary:disabled,
  .button[data-variant='secondary']:disabled {
    opacity: var(--opacity-disabled, 0.45);
    box-shadow: none;
    border-color: var(--border-subtle);
    background-color: transparent;
  }
  ```
  选择器特异性计算：`:global(html[data-theme='dark']) .buttonSecondary` 特异性为 `(0, 2, 0)`（1 个属性选择器 + 1 个类选择器），`.buttonSecondary:disabled` 特异性同样为 `(0, 2, 0)`（1 个类选择器 + 1 个伪类）。
  当处于深色模式时，行 156 的 `--btn-border` 依然是明度抬升的高亮发丝色，虽然行 167 强行指定了 `border-color: var(--border-subtle)`，但基础 Token 变量 `--btn-border` 与 `--btn-bg` 未同步退化。任何依赖 `--btn-border` 的派生伪元素或复合组件（如组合键帽、外框）将依然读到高亮边框值，导致视觉状态割裂。
- **极致修复方案**：
  在 CSS 变量体系内完成 disabled 状态的退化收敛，统一重写深浅色禁用态变量：
  ```css
  .buttonSecondary:disabled,
  .button[data-variant='secondary']:disabled {
    --btn-bg: transparent;
    --btn-border: var(--border-subtle);
    --btn-shadow: none;
    opacity: var(--opacity-disabled, 0.45);
    cursor: not-allowed;
  }

  :global(html[data-theme='dark']) .buttonSecondary:disabled,
  :global(html[data-theme='dark']) .button[data-variant='secondary']:disabled {
    --btn-bg: transparent;
    --btn-border: color-mix(in srgb, var(--border-color) 50%, transparent);
    --btn-shadow: none;
  }
  ```

### 2. [严重级别: 严重] `IconButton` 处于 `disabled` 状态时 `Tooltip` 彻底失效且丢失键盘可访问性
- **文件路径**：`apps/crish-desktop/src/components/ui/Button/IconButton.tsx:32-48`
- **缺陷剖析**：
  在 `IconButton.tsx` 中：
  ```tsx
  const buttonNode = (
    <Button
      ref={ref}
      icon={icon}
      variant={variant}
      aria-label={ariaLabel}
      className={classNames}
      {...props}
    />
  );

  if (tooltip != null) {
    return <Tooltip content={tooltip}>{buttonNode}</Tooltip>;
  }
  ```
  当 `<IconButton disabled={true} tooltip="当前不可用：需管理员权限" ... />` 时，渲染出的原生 `<button disabled>` 会被浏览器的渲染引擎彻底禁用所有的指针事件（`pointer-events: none` 的原生底层行为）与焦点捕获。
  其后果包括：
  1. 用户将鼠标悬停在被禁用的按钮上时，无法触发 `mouseenter` / `pointerenter`，`Tooltip` 浮层永远无法弹出，用户无法得知该按钮被禁用的业务原因；
  2. 键盘 Tab 导航跳过该按钮，视障用户完全无法聚焦该节点获取无障碍辅助说明。
- **极致修复方案**：
  当处于 `disabled` 且包含 `tooltip` 时，使用内联 `span` 包装层捕获指针事件，或者使用 `aria-disabled="true"` 结合无障碍焦点代理，确保在禁用态下 Tooltip 依然可以正常激活：
  ```tsx
  if (tooltip != null) {
    if (props.disabled) {
      return (
        <Tooltip content={tooltip}>
          <span className={styles.disabledTooltipTrigger} tabIndex={0} role="button" aria-disabled="true">
            {buttonNode}
          </span>
        </Tooltip>
      );
    }
    return <Tooltip content={tooltip}>{buttonNode}</Tooltip>;
  }
  ```

### 3. [严重级别: 一般] `Button.module.css` 缺少 `background-color` 与微位移过渡，Active 态缺少物理阻尼微动反馈
- **文件路径**：`apps/crish-desktop/src/components/ui/Button/Button.module.css:43-46`
- **缺陷剖析**：
  行 43-46 的过渡属性声明为：
  ```css
  transition:
    border-color var(--transition-micro, 100ms) ease-out,
    box-shadow var(--transition-micro, 100ms) ease-out;
  ```
  整个基座仅对 `border-color` 和 `box-shadow` 配置了 transition。当按钮由普通态切至 `.buttonActive`（如受控 `active={true}` 切换）时，`background-color` 是瞬间硬切的，没有任何平滑渐变；且用户在鼠标按下 `:active` 时，缺乏 Appica 标准的微阻尼按压反馈（`transform: scale(0.985)`）。
- **极致修复方案**：
  补全基座 transition 属性，并添加轻量物理微动按压反馈：
  ```css
  .button {
    ...
    transition:
      background-color var(--transition-micro, 100ms) ease-out,
      border-color var(--transition-micro, 100ms) ease-out,
      box-shadow var(--transition-micro, 100ms) ease-out,
      transform var(--transition-micro, 100ms) cubic-bezier(0.16, 1, 0.3, 1);
  }

  .button:active:not(:disabled) {
    transform: scale(0.985);
  }
  ```

## 二、快捷键键帽（Kbd）与诊断面板严苛缺陷审查

### 4. [严重级别: 致命] 快捷键录制未处理中文输入法（IME Composition），导致按键被永久固化为 `'Process'`
- **文件路径**：`apps/crish-desktop/src/components/settings/SettingsShortcutsTab.tsx:122-165`
- **缺陷剖析**：
  在 `SettingsShortcutsTab.tsx` 的全局 `keydown` 监听器中：
  ```tsx
  const handleKeyDown = (e: KeyboardEvent) => {
    if (e.key === 'Tab') return;
    e.preventDefault();
    e.stopPropagation();

    if (e.key === 'Escape' && !e.ctrlKey && !e.shiftKey && !e.altKey && !e.metaKey) {
      setRecordingShortcutId(null);
      return;
    }
    ...
    if (!['Control', 'Shift', 'Alt', 'Meta'].includes(e.key)) {
      let keyName = e.key;
      if (keyName === ' ') keyName = 'Space';
      keys.push(keyName.length === 1 ? keyName.toUpperCase() : keyName);
    }
  ```
  在 Windows 环境中，当用户使用中文拼音输入法（如微软拼音输入法）时，按下任意字母键（例如按 `K` 录制 `Ctrl+K`），浏览器派发的 `KeyboardEvent.key` 值为 `'Process'`，且 `e.isComposing` 为 `true`！
  当前代码未对 `e.isComposing` 与 `e.key === 'Process'` 做任何拦截，直接将其当作有效按键字符格式化为 `'Process'`，最终将快捷键错误固化为 `Ctrl + Process` 或 `Process` 并持久化写入配置文件！用户不仅改键失败，且由于 `Process` 无法匹配任何键盘物理按键，导致该快捷键彻底失效。
- **极致修复方案**：
  拦截 IME 输入法合成态，优先采用 `e.code` 解析物理按键名称（如 `KeyK` -> `K`），彻底免疫输入法状态影响：
  ```tsx
  const handleKeyDown = (e: KeyboardEvent) => {
    if (e.key === 'Tab') return;
    e.preventDefault();
    e.stopPropagation();

    if (e.key === 'Escape' && !e.ctrlKey && !e.shiftKey && !e.altKey && !e.metaKey) {
      setRecordingShortcutId(null);
      return;
    }

    // 过滤输入法组合过程（Composition）
    if (e.isComposing || e.keyCode === 229) {
      return;
    }

    const keys: string[] = [];
    if (e.ctrlKey) keys.push('Ctrl');
    if (e.shiftKey) keys.push('Shift');
    if (e.altKey) keys.push('Alt');
    if (e.metaKey) keys.push('Meta');

    if (!['Control', 'Shift', 'Alt', 'Meta', 'Process'].includes(e.key)) {
      let keyName = e.key;
      if (keyName === ' ') keyName = 'Space';
      // 物理按键兜底解析（避免输入法下 key 异常）
      if (keyName === 'Process' && e.code) {
        keyName = e.code.replace(/^Key|^Digit/, '');
      }
      keys.push(keyName.length === 1 ? keyName.toUpperCase() : keyName);
    }
  ```

### 5. [严重级别: 严重] `SettingsShortcutsTab.tsx` 中 `aria-labelledby` 指向幽灵 DOM ID 破坏无障碍可访问性
- **文件路径**：`apps/crish-desktop/src/components/settings/SettingsShortcutsTab.tsx:316`
- **缺陷剖析**：
  在第 316 行中：
  ```tsx

  ```
  在整个组件渲染树中，没有任何一个元素的 ID 为 `${listId}-title`。
  当屏幕阅读器访问到快捷键列表容器时，解析到一个悬空的 `aria-labelledby` 引用，无障碍树（Accessibility Tree）判定其关联失败，抛出 A11y 警告并丢失列表语义描述。

  ```tsx
    aria-label="快捷键配置列表"

  >
  ```

### 6. [严重级别: 严重] 快捷键搜索过滤时 `btnRefs.current` 未清空造成幽灵节点引用与内存残留
- **文件路径**：`apps/crish-desktop/src/components/settings/SettingsShortcutsTab.tsx:43, 194, 214, 220, 363`
- **缺陷剖析**：
  第 43 行：`const btnRefs = useRef<Array<HTMLButtonElement | null>>([]);`
  在第 363 行的渲染闭包中：
  ```tsx
  ref={(el) => {
    btnRefs.current[rowIndex] = el;
  }}
  ```
  当用户在输入框键入关键词进行搜索筛选时，`filtered` 数组从 30 项过滤为 2 项，`flatIdx` 仅走到 1。但是 `btnRefs.current` 是一个持久化数组引用，索引 2 到 29 依然持有上一次渲染中已从 DOM 树卸载的 `<button>` 真实 DOM 元素！
  这导致两个严重问题：
  1. **内存泄漏**：已卸载的 DOM 节点被 `useRef` 强引用长期锁死在内存中，垃圾回收器无法回收；
  2. **键盘遍历越界与幽灵焦点**：在极端边界（如快速清空搜索并按 `End` 键），`btnRefs.current[last]?.focus()` 可能会聚焦到悬空的游离节点上，破坏焦点流。
- **极致修复方案**：
  在依赖 `flatIds` 的 `useEffect` 中，或在每次列表扁平索引重新生成时，重置并修剪 `btnRefs.current` 的长度：
  ```tsx
  useEffect(() => {
    btnRefs.current = btnRefs.current.slice(0, flatIds.length);
    setFocusIndex((i) => {
      if (flatIds.length === 0) return 0;
      return Math.min(Math.max(0, i), flatIds.length - 1);
    });
  }, [flatIds]);
  ```

### 8. [严重级别: 一般] 诊断页 `copyTextBestEffort` 在 `execCommand` 异常时存在 DOM 孤儿节点残留泄漏
- **文件路径**：`apps/crish-desktop/src/components/settings/StatusDiagnosticsPanel.tsx:45-58`
- **缺陷剖析**：
  在 `copyTextBestEffort` 的降级实现中：
  ```ts
  try {
    if (typeof document === 'undefined') return false;
    const ta = document.createElement('textarea');
    ta.value = text;
    ta.setAttribute('readonly', '');
    ta.style.position = 'fixed';
    ta.style.left = '-9999px';
    document.body.appendChild(ta);
    ta.select();
    const ok = document.execCommand('copy');
    document.body.removeChild(ta);
    return ok;
  } catch {
    return false;
  }
  ```
  若在 `ta.select()` 或 `document.execCommand('copy')` 阶段触发了环境安全异常（如跨域 iframe 限制或无权限拒绝），代码直接跳转进入 `catch` 分支返回 `false`。
  此时 `document.body.removeChild(ta)` 被跳过未执行，创建的 `textarea` 临时节点将永久残留在宿主 `document.body` 中，造成 DOM 孤儿节点泄漏。
- **极致修复方案**：
  使用 `try...finally` 块确保 DOM 节点 100% 必定被清理移除：
  ```ts
  if (typeof document === 'undefined') return false;
  const ta = document.createElement('textarea');
  ta.value = text;
  ta.setAttribute('readonly', '');
  ta.style.position = 'fixed';
  ta.style.left = '-9999px';
  document.body.appendChild(ta);
  try {
    ta.select();
    return document.execCommand('copy');
  } catch {
    return false;
  } finally {
    if (ta.parentNode) {
      ta.parentNode.removeChild(ta);
    }
  }
  ```

## 三、受管浏览器与导入（BrowserImport / List）严苛缺陷审查

### 11. [严重级别: 严重] 列表切换采用独立 Toggle 按钮且共享同一容器 ID，未接入现代 `SegmentedControl` 组件
- **文件路径**：`apps/crish-desktop/src/components/workspace/browser-panel/ImportedListBlock.tsx:44-69`
- **缺陷剖析**：
  在 `ImportedListBlock.tsx` 中：
  ```tsx
  <Button

    variant={list.listTab === 'bookmarks' ? 'primary' : 'secondary'}
    size="sm"
    disabled={busy === 'list'}
    aria-expanded={list.listTab === 'bookmarks'}

      void list.toggleList('bookmarks');

  >
    书签列表{list.listTab === 'bookmarks' ? '（收起）' : ''}
  </Button>
  <Button
    type="button"
    variant={list.listTab === 'history' ? 'primary' : 'secondary'}
    size="sm"
    disabled={busy === 'list'}
    aria-expanded={list.listTab === 'history'}
    aria-controls={panelId}
    onClick={() => {
      void list.toggleList('history');
    }}
  >
    历史列表{list.listTab === 'history' ? '（收起）' : ''}
  ```

  缺陷分析：
  1. **违背设计规范**：重构目标明确要求“列表切换接入现代 `SegmentedControl`”，而当前仍采用两个并排的独立 Button 拼凑，缺少分段滑块平滑物理过渡动画；

### 12. [严重级别: 严重] DropZone 拖拽计数器在窗口外部松开或按 Esc 取消时产生僵尸高亮态泄漏
- **文件路径**：`apps/crish-desktop/src/components/workspace/browser-panel/BrowserImportSection.tsx:61-76`
- **缺陷剖析**：
  在 `BrowserImportSection.tsx` 中：
  ```tsx
  const onDragEnter = (e: React.DragEvent<HTMLDivElement>) => {
    e.preventDefault();
    dragDepthRef.current += 1;
    if (dragDepthRef.current === 1) {
      setIsDragging(true);
    }
  };

  const onDragLeave = (e: React.DragEvent<HTMLDivElement>) => {
    e.preventDefault();
    dragDepthRef.current -= 1;
    if (dragDepthRef.current <= 0) {
      dragDepthRef.current = 0;
      setIsDragging(false);
    }
  };
  ```
  当用户把文件拖入窗口上方触发 `onDragEnter` 使 `dragDepthRef.current` 递增为 1（`isDragging = true`）后：
  如果用户在窗口外部松开鼠标（Cancel Drop），或者在拖拽过程中按下了键盘 `Esc` 键取消拖拽，浏览器**不会向该元素派发 `dragleave` 或 `drop` 事件**！
  此时 `dragDepthRef.current` 永久保持在 `1`，`isDragging` 将永远卡在 `true`，拖拽放置区域持续呈现高亮发光、翡翠绿虚线与背景变色的“僵尸拖拽中”状态，直至用户再次进行另一次拖拽并正常移出！
- **极致修复方案**：
  在 `window` 全局挂载 `dragend`、`dragleave` 与 `drop` 兜底清理监听：
  ```tsx
  useEffect(() => {
    const handleGlobalDragEnd = () => {
      dragDepthRef.current = 0;
      setIsDragging(false);
    };
    window.addEventListener('dragend', handleGlobalDragEnd);
    window.addEventListener('drop', handleGlobalDragEnd);
    return () => {
      window.removeEventListener('dragend', handleGlobalDragEnd);
      window.removeEventListener('drop', handleGlobalDragEnd);
    };
  }, []);
  ```
