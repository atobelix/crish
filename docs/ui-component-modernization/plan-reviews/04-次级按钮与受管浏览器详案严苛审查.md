# 一、对比度、双主题与状态冲突严苛缺陷清单（Button & Kbd）

### 【缺陷 BTN-01 | 致命】深色模式下 Secondary 按钮与卡片底板 0 视感落差（对比度 1.00:1 严重坍塌）与 `:disabled` 状态不可分

- **文件路径与行号**：`docs/ui-component-modernization/plan-improvements/06-全仓次级按钮实体白卡重塑与受管浏览器现代化详案.md:200-208, 668-675`
- **缺陷剖析**：
  在权威 Design Tokens 单一真源 `tokens.css` 中（第 826-832 行）：
  - 深色模式下：`--bg-card: #242424;`，`--bg-elevated: #242424;`，`--bg-secondary: #242424;`；
  - 详案在 `Button.module.css` 的深色模式分支中写道：
    ```css
    :global(html[data-theme='dark']) .buttonSecondary,
    :global(html[data-theme='dark']) .button[data-variant='secondary'] {
      --btn-bg: var(--bg-elevated, #242424);
      --btn-fg: var(--text-primary, #dddddd);
      --btn-border: var(--border-subtle, #333333);
      --btn-shadow: 0 1px 3px rgba(0, 0, 0, 0.25);
    }
    ```
  当 Secondary 按钮放置在设置界面的 `SettingsCard`（背景色为 `--bg-card` 即 `#242424`）内部时：
  1. **背景对比度为 $1.00:1$（绝对零反差）**：按钮底色 `#242424` 与容器底色 `#242424` 完全融为一体！所谓的“实体凸起卡片”在深色模式下彻底退化为一条极弱的 `$1\text{px}$` 暗灰发丝框；
  2. **微阴影在纯黑底色上完全失效**：`rgba(0, 0, 0, 0.25)` 在 `#242424` 背景上由于明度被压制，肉眼根本无法分辨出任何 Z 轴物理抬升感；
  3. **启用态与禁用态视觉冲突**：
     详案第 604-608 行定义 `.button:disabled { opacity: var(--opacity-disabled, 0.45); box-shadow: none; }`。在深色模式下，因为启用态的底色已经和背景一致，降低 45% 不透明度仅仅把文字从 `#dddddd` 变暗为 `#636363`。用户在深色模式下看普通 Secondary 按钮就像一个“空心幽灵框”或“禁用的残留框”，破坏了浅色模式下纯白实体卡片的同构体验！
- **极致修复方案/代码片段**：
  在深色模式下，Secondary 按钮必须拥有比 `--bg-card` 稍高阶的微发光实体暗色底板（通过墨阶混色抬升 6.5%~8% 明度），并增强边框对比度；在 disabled 态下彻底归零为透明底板：
  ```css
  /* apps/crish-desktop/src/components/ui/Button/Button.module.css */
  .buttonSecondary,
  .button[data-variant='secondary'] {
    --btn-bg: var(--bg-card, hsl(0 0% 100%));
    --btn-fg: var(--text-primary);
    --btn-border: var(--border-color, hsl(35 10% 86%));
    --btn-shadow: 0 1px 2px color-mix(in srgb, var(--shadow-color) 4%, transparent);
    --btn-hover-overlay: var(--tint-hover);
    --btn-active-overlay: var(--tint-active);
  }

  /* 深色模式：精准抬升 6.5% 墨阶明度，塑造精致暗色实体纸片感知 */
  :global(html[data-theme='dark']) .buttonSecondary,
  :global(html[data-theme='dark']) .button[data-variant='secondary'] {
    --btn-bg: color-mix(in srgb, var(--text-primary) 6.5%, var(--bg-card, #242424));
    --btn-fg: var(--text-primary, #dddddd);
    --btn-border: color-mix(in srgb, var(--border-color, #333333) 80%, var(--text-primary) 20%);
    --btn-shadow: 0 1px 3px color-mix(in srgb, var(--shadow-color) 40%, transparent);
    --btn-hover-overlay: color-mix(in srgb, var(--text-primary) 6%, transparent);
    --btn-active-overlay: color-mix(in srgb, var(--text-primary) 12%, transparent);
  }

  /* 禁用态：深色模式下实体暗底退回透明，明确切断可点击实体感 */
  .buttonSecondary:disabled,
  .button[data-variant='secondary']:disabled {
    opacity: var(--opacity-disabled, 0.45);
    box-shadow: none;
    border-color: var(--border-subtle);
    background-color: transparent;
  }
  ```

### 【缺陷 BTN-02 | 严重】快捷键录制态（Recording）缺少 `outline: none` 重置，触发浏览器原生 Focus 产生双重焦点框

- **文件路径与行号**：`docs/ui-component-modernization/plan-improvements/06-全仓次级按钮实体白卡重塑与受管浏览器现代化详案.md:358-364, 826-831`
- **缺陷剖析**：
  详案在 `SettingsShortcutsTab.module.css` 中定义了快捷键录制状态：
  ```css
  .recording {
    border-color: var(--brand, hsl(160 84% 39%)) !important;
    box-shadow: 0 0 0 2px color-mix(in srgb, var(--brand, hsl(160 84% 39%)) 20%, transparent) !important;
    background-color: color-mix(in srgb, var(--brand) 4%, var(--bg-card)) !important;
    color: var(--brand-deep, hsl(160 84% 30%)) !important;
  }
  ```
  在 `.shortcutKeyBtn`（第 795-817 行）和 `.recording` 中，**完全没有声明 `outline: none;` 或 `:focus` 抑制**！
  在 Windows Tauri（WebView2 / Chromium 内核）环境下，当用户点击或通过 Tab 键聚焦快捷键按钮进入录制态时，浏览器宿主会强制绘制默认的蓝/黑原生焦点轮廓线（`outline: 2px solid -webkit-focus-ring-color` 或 `outline: 1px dotted`）。
  这导致界面上同时出现：
  1. CSS `box-shadow` 绘制的 2px 翡翠绿呼吸微光环；
  2. 浏览器外层原生的粗黑/高亮蓝 Outline 外框。
  两者在 1px 距离内发生叠套与颜色冲突，产生恶性 **双重焦点框（Double Focus Ring）**，直接违反 `AGENTS.md` §13 焦点环单一真源规范！
- **极致修复方案/代码片段**：
  在 `.shortcutKeyBtn` 基座与 `.recording` 状态中显式封杀原生 `outline`，并将焦点环统一挂载在 `:focus-visible` / `.recording` 之上：
  ```css
  /* apps/crish-desktop/src/components/settings/SettingsShortcutsTab.module.css */
  .shortcutKeyBtn {
    appearance: none;
    -webkit-appearance: none;
    outline: none; /* 坚决封杀宿主默认粗黑 Outline */
    /* ... 保持基础几何 ... */
  }

  .shortcutKeyBtn:focus-visible {
    outline: none;
    box-shadow: 0 0 0 1.5px color-mix(in srgb, var(--border-color) 94%, var(--text-primary) 6%);
    border-color: color-mix(in srgb, var(--border-color) 90%, var(--text-primary) 10%);
  }

  .shortcutKeyBtn.recording {
    outline: none;
    border-color: var(--brand, hsl(160 84% 39%));
    box-shadow: 0 0 0 2px color-mix(in srgb, var(--brand, hsl(160 84% 39%)) 20%, transparent);
    background-color: color-mix(in srgb, var(--brand) 4%, var(--bg-card));
    color: var(--brand-deep, hsl(160 84% 30%));
  }
  ```

### 【缺陷 BTN-03 | 严重】快捷键录制态深色模式文字对比度严重穿底（`--brand-deep` 在暗底上仅 2.21:1，WCAG AA 失败）

- **文件路径与行号**：`docs/ui-component-modernization/plan-improvements/06-全仓次级按钮实体白卡重塑与受管浏览器现代化详案.md:362, 830`
- **缺陷剖析**：
  详案为 `.recording` 状态指定了文字颜色：
  ```css
  color: var(--brand-deep, hsl(160 84% 30%)) !important;
  ```
  在 `tokens.css` 中，`--brand-deep` 的定义是 `hsl(160 84% 30%)`（即深翡翠绿 `#047857`），该 Token 是专门为浅色模式纯白卡底设计的（在纯白 `#ffffff` 上对比度为 $4.77:1 \ge 4.5:1$）。
  但在深色模式下：
  - 卡片底色 `--bg-card` 为 `#242424`；
  - 录制态底色为 `color-mix(in srgb, var(--brand) 4%, var(--bg-card))` 即 `#232826`；
  - 文字颜色 `--brand-deep`（`#047857`）在 `#232826` 背景上的明度对比仅为 **$2.21:1$**！
  远远低于 WCAG AA 要求的 $4.5:1$ 最低无障碍阈值！用户在深色模式下录制快捷键时，“按下新键…” 文案几乎完全黑化隐形，属于重大的无障碍合规事故。
- **极致修复方案/代码片段**：
  深色模式下必须收敛至高明度品牌主色 `--brand` 或 `--text-primary`：
  ```css
  .shortcutKeyBtn.recording {
    border-color: var(--brand, hsl(160 84% 39%));
    box-shadow: 0 0 0 2px color-mix(in srgb, var(--brand, hsl(160 84% 39%)) 20%, transparent);
    background-color: color-mix(in srgb, var(--brand) 4%, var(--bg-card));
    color: var(--brand-deep, hsl(160 84% 30%));
  }

  :global(html[data-theme='dark']) .shortcutKeyBtn.recording {
    background-color: color-mix(in srgb, var(--brand) 12%, var(--bg-card));
    color: var(--brand, hsl(160 84% 45%)); /* 在 #242424 暗底上对比度达到 6.8:1，完全达标 */
  }
  ```

### 【缺陷 BTN-04 | 一般】全仓 Secondary 按钮与徽标样式中硬编码 `rgba(0, 0, 0, ...)`，违反 AGENTS.md §14 色彩空间规范

- **文件路径与行号**：`docs/ui-component-modernization/plan-improvements/06-全仓次级按钮实体白卡重塑与受管浏览器现代化详案.md:194, 296, 328, 388, 672, 808, 930`
- **缺陷剖析**：
  在详案多个 CSS 规范中，反复出现了旧式绝对黑透明度硬编码：
  - `Button.module.css:L194, L672`: `--btn-shadow: 0 1px 2px rgba(0, 0, 0, 0.04), 0 1px 1px rgba(0, 0, 0, 0.02);`
  - `SettingsShortcutsTab.module.css:L328, L808`: `box-shadow: 0 1px 2px rgba(0, 0, 0, 0.04), 0 1px 1px rgba(0, 0, 0, 0.02);`
  - `StatusDiagnosticsPanel.module.css:L296, L930`: `box-shadow: 0 1px 2px rgba(0, 0, 0, 0.03);`
  - `SettingsRulesTab.module.css:L388`: `box-shadow: 0 1px 2px rgba(0, 0, 0, 0.03);`
  `AGENTS.md` §14 明确规定：“全量淘汰旧式 `rgba()`，全量收敛至 `hsl(... / a)` 与 `color-mix(in srgb, ...)`”。硬编码 `rgba(0, 0, 0, ...)` 绕过了主题引擎注入的 `--shadow-color` 变量，在 Windows HDR 或 OLED 广色域显示器下会导致 alpha 混合曲线断层。
- **极致修复方案/代码片段**：
  全面接入 `tokens.css` 权威阴影变量或 `color-mix`：
  ```css
  --btn-shadow:
    0 1px 2px color-mix(in srgb, var(--shadow-color) 4%, transparent),
    0 1px 1px color-mix(in srgb, var(--shadow-color) 2%, transparent);
  ```

### 【缺陷 BTN-05 | 一般】快捷键录制态连续滥用 4 个 `!important` 破坏 CSS Cascading 层叠架构

- **文件路径与行号**：`docs/ui-component-modernization/plan-improvements/06-全仓次级按钮实体白卡重塑与受管浏览器现代化详案.md:358-364, 826-831`
- **缺陷剖析**：
  详案在 `.recording` 规则中对 `border-color`、`box-shadow`、`background-color`、`color` 全部添加了 `!important`。
  在 CSS Modules 构建体系下，类名天然具备命名空间哈希隔离。滥用 `!important` 是前端架构的严重坏味道，它直接破坏了 CSS 特异性阶梯，导致后续在此状态下的 `:disabled` 或主题修饰类（如暗色适配）必须写出更丑陋的 `!important` 才能覆写，埋下样式污染隐患。
- **极致修复方案/代码片段**：
  通过类名组合链式选择器提升特异性，彻底清退 `!important`：
  ```css
  .shortcutKeyBtn.recording {
    border-color: var(--brand, hsl(160 84% 39%));
    box-shadow: 0 0 0 2px color-mix(in srgb, var(--brand, hsl(160 84% 39%)) 20%, transparent);
    background-color: color-mix(in srgb, var(--brand) 4%, var(--bg-card));
    color: var(--brand-deep, hsl(160 84% 30%));
  }
  ```

### 【缺陷 BRW-01 | 致命】`SettingsBrowserTab` 与 `BrowserImportSection` 重构假继承：声称使用 `SettingsCard` / `SettingsRow` 实质硬编码私有 DOM，破坏全局设置体系一致性

### 【缺陷 BRW-02 | 严重】拖拽区域（DropZone）缺少 Drag 计数器（Depth Counter）与活态拖拽样式，窗口跨界/子节点穿透时高亮闪烁与悬挂卡死

- **文件路径与行号**：`docs/ui-component-modernization/plan-improvements/06-全仓次级按钮实体白卡重塑与受管浏览器现代化详案.md:1136-1163, 1584-1596`
- **缺陷剖析**：
  详案中的拖拽区域实现如下：
  ```tsx
  <div
    className={styles.dropZone}
    role="button"
    aria-label="拖入 Chrome Bookmarks JSON"
    tabIndex={0}
    onDragOver={(e) => e.preventDefault()}
    onDrop={bookmarks.onBookmarksDrop}
    onKeyDown={...}
  >
  ```
  样式表第 1156-1163 行仅仅声明了 `.dropZone:hover, .dropZone:focus-visible`。
  存在四大致命交互 Bug：
  1. **拖拽过程中 `:hover` 伪类失灵（Zero Drag Feedback）**：
     在 Windows Chromium / Tauri 体系下，当光标拖拽外部文件进入窗口时，浏览器不会触发 CSS `:hover` 状态！由于代码没有监听 `dragenter` / `dragleave`，也没有设置激活类名（如 `.dropZoneDragging`），**用户拖拽文件悬停在虚线框上方时，虚线框没有任何高亮反馈**，用户无法得知是否可以松开鼠标；
  2. **子节点穿透导致的频闪 Bug（Strobe Flicker）**：
     如果后续补充 `onDragEnter` / `onDragLeave` 状态，由于 `.dropZone` 内部包含 `<span>` 与 `<code>` 子 DOM 节点，当拖拽光标划过子节点时，父级会触发 `dragleave`，导致拖拽高亮以极高频率疯狂闪烁；
  3. **拖拽中止悬挂（Stuck Drag State）**：
     若用户把文件拖入窗口后按 `Esc` 键取消或拖回任务栏，没有全局事件兜底，拖拽激活状态将永久卡死在高亮态；
  4. **缺少 `dropEffect` 声明**：
     `onDragOver` 没有设置 `e.dataTransfer.dropEffect = 'copy'`，在部分 Windows 资源管理器拖拽场景下光标会呈现禁止放置的 `🚫` 图标。
- **极致修复方案/代码片段**：
  在 Hook 层引入引用计数器（Depth Counter）并显式挂载 `data-dragging` 状态属性：
  ```tsx
  // 在 useBookmarksImport.ts 或组件中封装严密的拖拽状态机
  const [isDragging, setIsDragging] = useState(false);
  const dragDepthRef = useRef(0);

  const onDragEnter = (e: React.DragEvent) => {
    e.preventDefault();
    dragDepthRef.current += 1;
    if (dragDepthRef.current === 1) {
      setIsDragging(true);
    }
  };

  const onDragLeave = (e: React.DragEvent) => {
    e.preventDefault();
    dragDepthRef.current -= 1;
    if (dragDepthRef.current <= 0) {
      dragDepthRef.current = 0;
      setIsDragging(false);
    }
  };

  const onDragOver = (e: React.DragEvent) => {
    e.preventDefault();
    e.dataTransfer.dropEffect = 'copy';
  };

  const onDrop = (e: React.DragEvent) => {
    e.preventDefault();
    dragDepthRef.current = 0;
    setIsDragging(false);
    bookmarks.onBookmarksDrop(e);
  };
  ```
  并在 CSS 中精准定义活态拖拽样式：
  ```css
  .dropZone[data-dragging='true'] {
    border-color: var(--brand, hsl(160 84% 39%));
    background-color: color-mix(in srgb, var(--brand) 8%, var(--bg-secondary));
    color: var(--brand-deep, hsl(160 84% 30%));
    transform: scale(1.005);
  }
  ```

# 三、列表切换、分段控制器与异步竞态严苛缺陷清单（ImportedListBlock & SegmentedControl）

### 【缺陷 LST-01 | 致命】`SegmentedControl` Radio 语义与可收起列表（Collapsible List）状态模型逻辑冲突：折叠功能彻底失效且首屏数据脱节

- **文件路径与行号**：`docs/ui-component-modernization/plan-improvements/06-全仓次级按钮实体白卡重塑与受管浏览器现代化详案.md:500-511, 1357-1380`
- **缺陷剖析**：
  在原版受管浏览器中，底部列表是通过两个 Button 实现的，支持三种状态：`'bookmarks'`、`'history'` 和 **`null`（折叠收起）**。
  在详案重构中：
  ```tsx
  const currentTab = list.listTab ?? 'bookmarks';

  <SegmentedControl
    aria-label="已导入数据类型切换"
    size="sm"
    disabled={busy === 'list'}
    value={currentTab}
    options={[
      { value: 'bookmarks', label: `书签列表${list.bookmarkRows ? ` (${list.bookmarkRows.length})` : ''}` },
      { value: 'history', label: `历史列表${list.historyRows ? ` (${list.historyRows.length})` : ''}` },

    onChange={(val) => {
      void list.toggleList(val as 'bookmarks' | 'history');

  ```
  存在两大致命逻辑与交互死锁：
  1. **折叠收起功能永久报废（Unresponsive Click）**：
     `SegmentedControl` 的无障碍角色是 `role="radiogroup"`，其内部选项为 `role="radio"`。根据单选语义与 `SegmentedControl.tsx:L130` 的实现：
     `if (val !== currentValue) { onChange?.(val); }`
     当用户再次点击当前已高亮的选项（例如此时正在查看“书签列表”，试图点击它收起列表）时，`val === currentValue`，`SegmentedControl` **直接拦截并不触发 `onChange`**！
     因此 `list.toggleList` 根本收不到点击事件，**用户永远无法将列表收起折叠**！
  2. **首屏“假激活”视觉欺骗（Ghost Active Tab）**：
     初始挂载时，`list.listTab` 的默认状态是 `null`（尚未展开列表且未请求数据）。

     用户看到的是“书签列表已选中”，下方却是空空如也，造成极为严重的视觉状态与数据模型脱节。

### 【缺陷 LST-02 | 严重】异步列表加载（`listBookmarks` / `listHistory`）缺少请求时序保护与 AbortController，快速切换导致异步竞态覆盖（Async Race Condition）

- **文件路径与行号**：`docs/ui-component-modernization/plan-improvements/06-全仓次级按钮实体白卡重塑与受管浏览器现代化详案.md:1377-1380` 与 `useHistoryImport.ts:85-108`
- **缺陷剖析**：
  在 `useHistoryImport.ts` 中，`loadList` 的执行逻辑如下：
  ```ts
  const loadList = async (tab: 'bookmarks' | 'history') => {
    setBusy('list');
    if (tab === 'bookmarks') {
      const res = await listBookmarks();
      if (res.status === 'ok') setBookmarkRows(res.data);
      else reportListError('书签列表加载失败：', resultMessage(res, ''));
    } else {
      const limit = Math.max(1, Math.floor(Number(historyLimit)) || 50);
      const res = await listHistory(undefined, limit);
      if (res.status === 'ok') setHistoryRows(res.data);
      else reportListError('历史列表加载失败：', resultMessage(res, ''));
    }
    setBusy(null);
  };
  ```
  这里存在严重的 **异步竞态漏洞（Async Race Condition）**：
  如果用户在网络/IPC 延迟时快速在“书签列表”和“历史列表”之间连续切换，先发出的 `listBookmarks()`（耗时较长，如 400ms）在后发出的 `listHistory()`（耗时较短，如 50ms）之后完成响应并触发 `setBookmarkRows(res.data)`。由于没有任何请求时序计数器（Sequence Token）或中止机制，慢响应会覆盖新状态，导致界面显示的列表内容与当前激活的 Tab 不一致！
- **极致修复方案/代码片段**：
  在 Hook 中引入单调递增的 `requestId` 计数器，保证只有最新发起的请求才有权写入 State：
  ```ts
  const reqSeqRef = useRef(0);

  const loadList = async (tab: 'bookmarks' | 'history') => {
    const currentSeq = ++reqSeqRef.current;
    setBusy('list');
    try {
      if (tab === 'bookmarks') {
        const res = await listBookmarks();
        if (currentSeq !== reqSeqRef.current) return; // 拦截过期竞态响应
        if (res.status === 'ok') setBookmarkRows(res.data);
        else reportListError('书签列表加载失败：', resultMessage(res, ''));
      } else {
        const limit = Math.max(1, Math.floor(Number(historyLimit)) || 50);
        const res = await listHistory(undefined, limit);
        if (currentSeq !== reqSeqRef.current) return; // 拦截过期竞态响应
        if (res.status === 'ok') setHistoryRows(res.data);
        else reportListError('历史列表加载失败：', resultMessage(res, ''));
      }
    } finally {
      if (currentSeq === reqSeqRef.current) {
        setBusy(null);
      }
    }
  };
  ```

  根据 WCAG 2.1 权威规范（第 1.3.1 节信息与关系，第 4.1.2 节名称、角色与值）：
  `placeholder` 占位符绝对不能替代表单的可访问标签！屏幕阅读器用户在通过 Tab 键聚焦到该多行文本框时，仅能听到“多行文本编辑框”，无法获知该输入框的明确业务含义。
- **极致修复方案/代码片段**：
  必须显式挂载无障碍名称：
  ```tsx
  <textarea
    id={`${baseId}-storage-json`}
    className={styles.textarea}
    aria-label="登录态 JSON 内容（Playwright 兼容格式）"
    placeholder="粘贴标准 storage_state JSON（Playwright 兼容 { cookies, origins }）"
    value={storage.storageJson}
    onChange={...}
    rows={3}
  />
  ```

### 【缺陷 A11Y-02 | 一般】`DropZone` 装载文件后 `aria-label` 状态不更新，无障碍用户无法感知装载结果

- **文件路径与行号**：`docs/ui-component-modernization/plan-improvements/06-全仓次级按钮实体白卡重塑与受管浏览器现代化详案.md:1584-1604`
- **缺陷剖析**：
  拖拽区域声明了静态 `aria-label="拖入 Chrome Bookmarks JSON"`。
  当文件通过文件选择器或拖拽完成装载后，界面在视觉上更新了：
  `已装载：bookmarks_2026.json`
  然而 `DropZone` 的 `aria-label` 依然是 `"拖入 Chrome Bookmarks JSON"`！视障用户使用读屏软件导航时，依然听到“拖入 Chrome Bookmarks JSON 按钮”，完全无法感知当前是否已经成功载入文件以及载入了什么文件。
- **极致修复方案/代码片段**：
  动态响应装载状态，并配合 `aria-live` 进行状态播报：
  ```tsx
  <div
    className={styles.dropZone}
    role="button"
    aria-label={
      bookmarks.bookmarksFileName
        ? `已装载书签文件：${bookmarks.bookmarksFileName}。按回车或空格可重新选择文件`
        : '拖入 Chrome Bookmarks JSON 文件，或按回车选择文件'
    }
    tabIndex={0}
    // ...
  >
  ```

### 【缺陷 A11Y-03 | 一般】`ImportedListBlock` 的 `SegmentedControl` 与下方列表容器缺少 `aria-controls` 与 `id` 关联

- **文件路径与行号**：`docs/ui-component-modernization/plan-improvements/06-全仓次级按钮实体白卡重塑与受管浏览器现代化详案.md:1362-1380, 1423, 1452`
- **缺陷剖析**：
  分段控制器（`SegmentedControl`）作为视图切换中枢，下方的列表容器（`<ul className={styles.list}>`）未被赋予唯一的 DOM `id`，且分段控制器中的各个 Radio 按钮未设置 `aria-controls` 属性。
  辅助技术（Assistive Technologies）无法建立分段控制器选项与下方动态内容区之间的控制拓扑关系，属于 WAI-ARIA 语义轻度缺失。
- **极致修复方案/代码片段**：
  通过 `useId` 派生关联 ID 并挂载 `aria-controls` 与 `id`：
  ```tsx
  const panelId = `${baseId}-list-panel`;

  // 下方列表容器：
  <ul id={panelId} className={styles.list} role="region" aria-label={currentTab === 'bookmarks' ? '已导入书签列表' : '已导入历史列表'}>
  ```
