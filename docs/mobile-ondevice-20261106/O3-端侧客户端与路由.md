## 二、端侧客户端（onDeviceChatClient.ts）

实现 `LocalChatClient` 全接口，与 HTTP 版同签名、同错误分类（出口统一 `withErrorMessage`）：

- **接口形状核对**：llama.rn 0.12.9 的 JS API 以包内类型定义实查为准（`lib/typescript/index.d.ts` / `types.d.ts`）并与 O1 冒烟页互证：`initLlama({model, n_ctx, n_gpu_layers, use_mlock})`、`context.completion(params, onToken)`（TokenData `{token, content?, reasoning_content?}`；结果 NativeCompletionResult `{content, reasoning_content, truncated, stopped_eos, stopped_limit, …}`）、`stopCompletion()`、`release()`。客户端只依赖自定义的窄桥接口（结构子集），生产桥惰性 `require('llama.rn')`（仓内 expo-notifications 门面同款纪律：接线层静态引用本模块时，导入期不触碰原生模块，jest 安全）。
- **streamChatCompletion**：按 `input.model` 经 O2 管理器 `check()` 取就绪文件（ready = 文件在位 + 尺寸精确 + verified.json 标记在案）→ 惰性 initLlama 单例（n_ctx 取目录 `inference.contextSize`，缺省 4096、3B 为 2048；`n_gpu_layers: 0` 恒定——Kirin 无 GPU 路径是设计基线；`use_mlock: true`；切换模型先 release 旧 context，并发 init 去重）→ wire 消息直映射（user 多模态 parts 只取 text 段；assistant 只取正文；tool 角色跳过）→ completion 逐 token 回调：`content` 为正文增量（权威，缺失回退原始 token），`reasoning_content` 独立走 `onReasoningDelta` → 结束 `onComplete({content, finishReason, toolCallCount: 0})`（truncated/stopped_limit → `'length'`，其余 `'stop'`，与 HTTP 路径 finish_reason 口径一致）。`abort()` 先标记完成再 `stopCompletion()`，迟到回调一律忽略（与 HTTP 客户端 abort 纪律同款）。
- **纯对话口径（第二道闸）**：completion 参数组装函数根本没有 tools 字段——无论 input 带什么都不下发，`onComplete` 永不带 toolCalls。Qwen3 按目录 spec 关闭思考：`enable_thinking: false` + `chat_template_kwargs: {enable_thinking: false}` 双路下发（模板变体兼容）；停止词按目录 spec（Qwen 系 `<|im_end|>`、Llama `<|eot_id|>`）。
- **completeChatCompletion**：同 context 非流式收集（缺省 maxTokens 32 / temperature 0.3，与 HTTP 实现同缺省），供 AI 标题，零新通道。
- **模型面（零网络）**：`fetchProviderModels` 只列 check 为 ready 的 id；`fetchProviderModelsRobust` 返回就绪模型的最小诚实规格（id/displayName/enabled，其权威全规格由 O4 内置供应商条目承载）；`checkConnectivity` 以指定模型「文件在位且校验标记在案」为真值；`pingProviderEndpoint` 以「至少一个模型就绪」为真值、无就绪模型时如实 notConfigured。两者的 `latencyMs` 填**本地核对的真实耗时**（非网络往返，不伪造数字，代码注释已标明语义）。
- **错误映射**（进既有 LocalChatError 分类，不新造）：未知 id / 磁盘零占用 → `notConfigured` + detail；文件在盘但未过就绪校验 → `unknown` + detail 引导「删除后重新下载」；原生 init/生成失败 → `unknown` + detail 带原始错误信息。

目录侧的小增量：`OnDeviceModelSpec` 加可选组 `inference?: { contextSize?, enableThinking?, stop? }`（工程口径值，与 HF 实查的下载身份字段分开标注）——3B 填 contextSize 2048，Qwen3 填 enableThinking false，其余填各自 eos 停止词。O2 的目录单测逐条钉死 size/sha256/urls/license，本增量不触碰这些字段，O2 套件复跑全绿。

## 三、路由（localChatWiring.ts）

- `streamChatCompletion` / `completeChatCompletion` 按 `input.providerId` 查 `localChatStore` 当前配置的 `provider.protocol`——`'ondevice/gguf'` 走端侧（惰性组装、只组装一次），其余（含 providerId 缺失、配置查不到）一律走既有 HTTP 客户端，存量行为不变。`setLocalChatClientForTest(deps)` 签名与语义保留（HTTP 面走假传输），另加 `setOnDeviceClientForTest` 供引擎级测试注入假端侧客户端。

## 六、未做与裁决登记

1. **`LocalVendorKey` 未加 `'ondevice'`（与 §5.3 字面有一处出入，理由如下）**：实测一加即撑破 6 个 UI 消费点——`useLocalProvidersVm` 的 `Record<LocalVendorKey, string>` 字面量缺键、且域类型被用来索引 `providerPresets` 的 `Record`（预置侧另有一份**独立声明**的同名 LocalVendorKey，未含 ondevice，互赋即报错），另有 useProviderDetailVm / useProviderWizardVm / ProviderDetailView / ProvidersListView 四处同类。根源是 vendor 字段驱动预置字典与图标映射，而端侧供应商无端点、无密钥、无预置——强行扩展还要给 PROVIDER_PRESETS 造一条空端点预置，会作为可选厂商漏进供应商向导（假入口）。本批处理：`LocalProviderSpec.vendor` 本就是可选字段，O3 的路由/客户端零依赖 vendor，端侧条目不挂 vendor 即可成立；**枚举扩展连同预置字典与 UI 映射的处理归 O4**（内置供应商条目落地时一并裁决，含两份 LocalVendorKey 声明的存量双轨问题）。本批引擎集成测试的端侧条目即按无 vendor 形态验证通过。
2. **AI 标题调用点未填 providerId**：按简报「引擎改动只许两处、providerId 一处调用点」的口径，`maybeGenerateAiTitle` 的 `completeChatCompletion` 本批未动——后果如实登记：端侧线程的 AI 标题调用会按 HTTP 路径走（baseUrl 为空必然失败），引擎既有设计对此静默回退 derived 截断标题，不报错、不假装。后续只需在该组装点补填 `providerId: sel.providerId` 一行即通（建议随 O4 或收口批处理）。
3. **单例上下文的并发限制**：原生 context 全局单例（§5.3 既定），两个线程同时生成且模型不同时会互相 release 对方上下文，被中断的一轮以 unknown 错误收尾（诚实报错，不静默）。同模型并发在 llama.rn 单 context 上亦为串行语义。此为 1–2GiB 权重的内存必然，v1 接受。
4. **checkConnectivity 的 model 参数**：接口要求带 model，本客户端按该模型单查；UI 若要「整供应商」口径请用 ping（至少一个模型就绪）。
