## 三、管理器（onDeviceModelManager.ts）

把 ASR `AsrModelManager` 的状态机/校验/多源回退按其形状泛化为多模型目录版：构造入参 specs[]（默认目录清单）；存储 `documentDirectory + 'crish-llm-models/<modelId>/'`，每模型目录自带 `verified.json`（{fileName: sha256}）。

- **状态机**（逐模型，与 ASR 同构 + modelId）：missing / downloading / verifying / ready（带原生路径）/ error（message + canRetry）。进度类型与 `AsrModelProgress` 同构：fileName/fileIndex/totalFiles/receivedBytes/totalBytes/overallFraction/progressText，另按采样（≥400ms 窗口）给出 speedBytesPerSec。`check()` 快速路径（尺寸+标记，零哈希零下载）、存量文件哈希自愈补标记、`checkAll()`、逐模型 inflight 去重，均与 ASR 口径对齐；非破坏性策略保留（校验失败不删既有正式文件，损坏件只留 .part）。
- **断点续传（对 ASR 版的明确增量，已做实）**：生产实现包 expo-file-system legacy 的 `createDownloadResumable(url, fileUri, {}, cb, resumeData)`；下载进度回调中节流（≥1.5s 或 ≥4MiB）把 `savable()` 的 {url, fileUri, resumeData} 写 SQLite kv（键 `ondevice.resume.<modelId>`，kv 面即 SqlSettingsDao 的 get/set/delete 子集，由 wiring 注入）；失败退出前再尽力存一次；App 重启后 `ensureReady` 读记录、以 resumeData 调 `resumeAsync()` 续传；**服务端不接受续传（抛错/尺寸不符）时自动清 kv 记录、删 .part、同源整文件重下**；成功后删记录。单测三条覆盖：失败落记录→新管理器实例（模拟重启）以在案 resumeData 续传成功；续传被拒→整文件回退；大文件（5MiB 假件）在 4MiB 节流阈值后断网→记录中 resumeData ≥4MiB（下载中途已持久化，非仅失败点）。
- **空间管理**：下载前预检 `freeDiskSpace() ≥ ceil(size × 1.1)`，不足置 error（文案含需要/可用数字，canRetry=true）且零网络调用；取不到可用空间（null）时不虚假拦截。`usageBytes(modelId)`（正式文件 + .part）与 `totalUsageBytes()` 可查。
- **删除幂等**：`remove(modelId)` 清正式文件、.part、verified.json、模型子目录与 kv 续传记录；对已删/未下载/未知 id 重复调用不抛错；删除后可重新下载。
- **诚实口径**：无首启自动下载（只有显式 `ensureReady` 触发）；未知模型 id 返回 canRetry=false 的 error；HTTP 非 200 判失败（同 ASR）；`localPath()` 给 O3 的路径已剥 file:// scheme（复用 ASR 的 `toNativeFilePath`）。

## 四、双轨裁决（共享基类抽取）

**结论：本批不抽共享基类，按同一接口形状平行实现；收口时二选一复核。**理由已写进管理器文件头：

1. ASR 管理器已在真机生产运行，公开面（扁平单目录 + 三件固定文件 + `AsrModelPaths` 专用路径组）与本管理器（多模型、每模型独立子目录/标记）不同构，抽基类必须改动 ASR 公开行为面，风险与本批收益不成比例；
2. 本管理器对 ASR 版有三处增量（续传持久化、空间预检、逐模型状态/占用），基类会被增量反向污染；
3. 真正可共享的纯函数 `toNativeFilePath` / `formatBytes` 已直接从 ASR 模块导入复用，没有复制第二份；原生文件 SHA-256 亦复用 crish-asr 原生模块的通用 `fileSha256`（与 ASR 同口径）。

留给收口的二选一：届时把两者共同的「下载→尺寸校验→哈希校验→原子落正→标记」内核抽成基类（前提 ASR 回归全绿），或维持平行实现并在两处文件头互相标注。本批已在本文件头标注，未无声留轨。
