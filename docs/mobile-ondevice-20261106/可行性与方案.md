# 手机端自机部署（端侧）模型：可行性与方案

调查时间：2026-11-06。范围：crish-mobile 端侧（on-device）LLM 推理——模型跑在手机本身上、客户端直连公开源拉取、不经我方服务器。方法：PC 仓库实读（文件+行号）+ 官方仓库/HF API 实查（文件字节数与 sha256 取自 HF tree API 的 LFS oid，非估算）。

## 一、结论先行

**能实现，推荐路线一句话：以 llama.rn（llama.cpp 的 RN 绑定，MIT）为推理运行时，新增一个与现有 HTTP 客户端同接口的端侧 `LocalChatClient` 实现，模型以 GGUF 格式经「hf-mirror → HF 原站」双源直拉、固定 sha256 校验、断点续传落盘，全部复用现有本地会话栈（引擎/线程/SQLite 持久化/模型选择器零新体系）。**

三个决定性事实：

1. **接入缝现成**：本地对话的引擎只依赖 `LocalChatClient` 接口（`src/adapters/localChat/localChatClient.ts:439-472`），客户端经单例接线层装配（`localChatWiring.ts:15-18`），依赖注入面本就存在（`LocalChatClientDeps`，同文件 381-388 行）。端侧引擎做成该接口的第二个实现即可，引擎的工具循环、流式批处理、线程持久化全部原样复用。
2. **拉取机制本仓已有生产先例**：ASR 离线模型管理器（`src/adapters/asr/modelManager.ts`）已在真机跑通「hf-mirror.com 优先 + huggingface.co 回退 + 固定 sha256 + 尺寸校验 + .part 原子落盘 + 诚实状态机（缺失/下载中/校验中/就绪/失败可重试）」，SenseVoice 228MiB 模型就是这么分发的。LLM 模型管理器是它的泛化，不是新发明。
3. **目标机只有 CPU 路径**：llama.rn 的 Android GPU 后端是 OpenCL（官方文档注明支持与测试对象为 Adreno 700+）与 Hexagon NPU（高通 SM8450+，实验）；README 全文无 Vulkan。P40 Pro（Kirin 990，Mali-G76）两条都不沾——**按纯 CPU 设计**，预期生成速度 1.5B 级约 9–15 tok/s、3B 级约 5–8 tok/s（估算依据见第四节），可接受但别拿旗舰机数字对标。

**必须如实说的降级**：v1 端侧模型**只做纯对话，不启用工具调用**。理由不是运行时不行（llama.rn 有通用 tool call 解析），而是 1–3B 模型在多轮 agent 循环（现有引擎最多 6 轮、每轮重发全量历史+工具 schema）下可靠性不够、且 A76 的 prefill 速度撑不起每轮数千 token 的工具提示词。详见第六节。

## 二、现有本地链路证据（PC 实读）

### 2.1 Provider 抽象与接口形状

- 配置模型与桌面同构：`LocalModelsConfig { version: 2, providers: Record<providerId, LocalProviderSpec>, activeModel: {providerId, modelId} | null }`（`src/domain/types/localChat.ts:197-201`）。`LocalProviderSpec` 含 baseUrl / apiKeyRef（固定形态 `secure:<providerId>`，密钥材料只进 SecureStore）/ protocol / models: LocalModelSpec[]（同文件 145-176 行）。协议枚举目前只有 `'openai/chat'`（19 行 `LocalProtocolKind`）。
- 配置落盘：非密配置单体 JSON 存 SQLite kv（键 `localchat.config`），密钥只进 SecureStore（`src/domain/store/localChatStore.ts:3-9` 文件头注释；`readApiKey(providerId)` 在 63 行）。
- 客户端接口（**端侧接入点**）`LocalChatClient`（`localChatClient.ts:439-472`）：
  - `streamChatCompletion(input: StreamChatInput, callbacks: StreamChatCallbacks): StreamHandle`（440-443 行；`StreamHandle = { abort(): void }`，63-65 行）；
  - `completeChatCompletion(input): Promise<string>`（449 行，AI 标题等小调用用）；
  - `fetchProviderModels / checkConnectivity / pingProviderEndpoint / fetchProviderModelsRobust`（模型列表与连通性面）。
- 流式回调签名 `StreamChatCallbacks`（418-437 行）：`onTextDelta(delta: string)`、`onReasoningDelta?`、`onActivity?`、`onToolCallsDetected?(toolCalls)`、`onComplete({content, finishReason, toolCallCount, toolCalls?, reasoning?})`、`onError(error: LocalChatError)`。输入 `StreamChatInput`（402-417 行）= `{ baseUrl, apiKey: string | null, model, messages: readonly LocalWireMessage[], tools?, toolChoice?, thinkingFormat?, thinkingTier?, maxTokens?, temperature? }`——注意**不带 providerId/protocol**，路由设计需补一笔（见 5.3）。
- 现有实现是 OpenAI 兼容 HTTP/SSE：XHR onprogress 增量读（84 行 `xhrStreamTransport`），端点归一与 wire 组装在 `src/domain/pure/localChatProtocol.ts`。

### 2.2 本地会话引擎在哪一层消费

- 会话层 hook `useLocalConversationEngine.tsx:48-50` 调 `localChatEngine.sendLocalChatMessage`。
- 引擎 `src/adapters/localChat/localChatEngine.ts`：`sendLocalChatMessage`（323 行）解析线程模型选择（`resolveThreadSelection`，303 行）→ `localChatStore.readApiKey(providerId)`（456-460 行）→ **agent 循环** `executeRound`（最多 `MAX_AGENT_ROUNDS = 6` 轮，74 行）：每轮经 `mobileToolRegistry.toOpenAiFunctionSchemas({threadId})` 取工具声明（486-497 行，工具实现在 `src/adapters/tools/`：webSearchTool / webFetchTool / runJsSandboxTool），调 `client.streamChatCompletion({... , tools, toolChoice: 'auto'}, callbacks)`（518-527 行）；`onComplete` 带 toolCalls 则经 `mobileToolRegistry.executeToolCall` 执行（221 行）并回填历史续轮，无 toolCalls 则收尾、落盘、生成 AI 标题（532 行起）。
- 流式呈现经引擎内 `StreamBatchScheduler`（96 行，默认 33ms 批窗）平滑后写 `localChatSessionStore`——端侧 token 回调天然对接，不需要新呈现通道。
- 线程为一等公民：多线程 + SQLite 持久化（`src/db/dao/localThreadsDao.ts`；`LocalThreadMeta.modelRef` 每线程模型选择，localChat.ts:293-306）。**端侧会话复用这套栈，线程/消息表不新开。**
- 模型选择器：`LocalModelSheet.tsx` 直接遍历 `config.providers → models` 渲染，选中调 `setActiveModel(providerId, modelId)`（62-112 行）。**只要端侧供应商以普通 provider 条目进同一份 config，现有选择器零改造就能列它**——前提是「列出的即可用」，故 config 里只同步已下载完成的模型（见 5.4）。
- 供应商管理 UI 路由已成套：`app/settings-local-providers.tsx` / `-detail` / `-edit` / `-wizard` / `settings-local-model-spec.tsx`。
- providerPresets 已有「本地/局域网」先例（Ollama 预置，`providerPresets.ts:210-214`）。

### 2.3 原生层现状

- **Expo SDK 57 / RN 0.86.3 / expo-router**（package.json），`android/` 为 prebuild 产物形态，settings.gradle 为标准 Expo autolinking（本地模块自动装配）。RN 0.86 已是新架构单轨——llama.rn v0.10+ 的硬性要求（新架构）自动满足。
- **自研原生模块先例齐全**：`modules/` 下有 crish-asr（Kotlin Expo 模块，含原生 sha256 加速 `fileSha256` 与流式语音）、crish-js-sandbox（C++/JNI QuickJS）、crish-haptics。团队有写/维护原生模块的完整经验与构建通道；release APK 已能正常打包（arm64 单 ABI，约 101MB）。
- 已装可复用设施：expo-file-system 57（含 `createDownloadResumable`）、expo-sqlite、expo-secure-store、@noble/hashes（纯 JS sha256 兜底）。
- ASR 踩过的坑直接适用：原生引擎只认真实文件系统路径，`file://` URI 喂给原生侧会被判「不存在」（`modelManager.ts:70-87` 文件头实证，2026-11-03 真机 logcat 定根因）——给 llama.rn 的 model 路径必须经同款 `toNativeFilePath` 剥 scheme。

### 2.4 ASR 模型分发先例（拉取机制的真源）

`src/adapters/asr/modelManager.ts`（490 行，含测试）：
- 源序：`https://hf-mirror.com/<repo>/resolve/main/<file>` 第一，`https://huggingface.co/...` 第二，逐源回退（28-31 行）；另有 GitHub Releases 源（VAD 模型，51-54 行）。
- 每文件固定 `size + sha256`（34-56 行），下载到 `.part` → 尺寸校验 → sha256 校验（原生加速优先、纯 JS 分块兜底，225-254 行）→ 原子 move 落正（372-378 行）；`verified.json` 标记增量持久化，断电不丢已校验文件。
- 状态机对 UI 诚实：missing / downloading（带 overallFraction + 速率）/ verifying / ready / error(canRetry)（133-143 行）；`removeAll()` 供设置页删除（205-212 行）；存储在 `documentDirectory + 'crish-asr-models/'`（427 行）；并发下载去重（inflight 共享）。
- **缺口（LLM 场景必须补）**：其 `downloadToFile` 每轮新建 DownloadResumable 从零下载（463-481 行），不持久化断点——228MiB 可忍，0.8–2.1GB 不可忍。expo-file-system 的 DownloadResumable 本身支持 `savable()` 导出 resumeData 并跨进程恢复，设计上把 resumeData 存进 SQLite kv 即可补齐（见 5.2）。

## 五、集成设计（分层到文件，不另造平行体系）

### 5.1 运行时层（新依赖，仅一处）

- `apps/crish-mobile` 引入 `llama.rn`（引入时锁当时最新稳定版 + 过真机回归），app.json 加其 Expo plugin（`enableOpenCL` 保持开但运行时以 `initLlama` 返回的 `reasonNoGPU` 为准，Kirin 上实际走 CPU，不向用户宣称 GPU 加速）。
- 新架构、arm64 与本项目现状吻合；x86_64 模拟器（emulator-5554）是否含对应 jniLibs 本轮未核——验收一律以 P40 Pro 真机为准（与既有移动验收纪律一致），模拟器仅做 UI 冒烟。

### 5.2 模型管理层（泛化 ASR 先例）

- 新建 `src/adapters/onDevice/onDeviceModelManager.ts`：把 `AsrModelManager` 的状态机/校验/多源回退**按其形状泛化**为多模型目录版（构造入参 = 目录清单 specs[]，每条含 id/文件名/size/sha256/urls），存储目录 `documentDirectory + 'crish-llm-models/<modelId>/`，每目录自带 `verified.json`。
  - 实现纪律：优先评估把 ASR 的类抽成共享基类供两边用；若抽取风险大，则照其接口形状平行实现并注明（整改宪章忌双轨——收口时二选一，不能长期两份近似实现并存）。
- 目录清单 `src/adapters/onDevice/onDeviceModelCatalog.ts`：第四节五条（3B 视裁决），urls 按 ASR 同序生成（hf-mirror 第一、huggingface.co 第二）。
- **断点续传补齐**（对 ASR 版的明确增量）：下载任务的 `DownloadResumable.savable()` 状态（url/fileUri/resumeData）随进度节流写入 SQLite kv；App 重启后以 resumeData 重建任务续传；服务端不接受续传时自动回退整文件重下并如实置状态。下载进度经既有 `onState` 形态回调进 RN（与 ASR 的 AsrModelProgress 同构，含 overallFraction/速率/文案）。
- 空间管理：管理面显示每模型占用与总占用；下载前预检可用空间（文件大小 ×1.1 不足则拒绝并提示）；删除走 `removeAll` 同款幂等清理（含 .part 与 resumeData 记录）。

### 5.3 推理客户端层（核心接入，改动最小化）

- 新建 `src/adapters/onDevice/onDeviceChatClient.ts`，实现 `LocalChatClient` 接口（与 HTTP 版同签名）：
  - `streamChatCompletion`：按 input.model 找已下载文件 → 惰性 `initLlama({ model: toNativeFilePath(path), n_ctx: 4096（3B 为 2048）, n_gpu_layers: 0, use_mlock: true })` 建/复用单例 LlamaContext（切换模型时 release 旧 context）→ 把 `LocalWireMessage[]` 直映射为 llama.rn 的 messages（role/content 同构；tool 角色消息在纯对话口径下不会出现）→ `context.completion({ messages, n_predict: input.maxTokens, temperature, stop: [...按模型 eos] }, ({token}) => callbacks.onTextDelta(token))`；结束回 `onComplete({content, finishReason, toolCallCount: 0})`；`StreamHandle.abort()` 转 `context.stopCompletion()`。
  - **tools 字段一律不下发**（纯对话口径）：无论 input 带什么工具声明，端侧客户端都不传给 llama.rn，`onComplete` 永不带 toolCalls——引擎的收敛路径（无 toolCalls 即收尾）天然接住。Qwen3 的思考：经 `chat_template_kwargs` 关思考（或按模型 spec 的 thinking 配置映射），`onReasoningDelta` 仅在原生返回独立 reasoning 时接。
  - `completeChatCompletion`：同 context 非流式收集全文（AI 标题复用，零新通道）。
  - `fetchProviderModels` 返回本机已下载模型 id 列表（**纯本地、零网络**——绕开模型选择器历史上的网络超时病灶）；`checkConnectivity` 以「模型文件在位且校验标记在案」为真值返回；`pingProviderEndpoint` 返回文件在位状态（不伪造延迟数字，未下载即如实 notConfigured 类错误）。
  - 错误映射到既有 `LocalChatError` 分类：未下载→`notConfigured`；文件损坏/校验失效→`unknown` + detail 注明并引导重下；原生 init 失败→`unknown` 带原始信息。不新造错误体系。
- 路由一小步（唯一接口增量）：`StreamChatInput` / `CompleteChatInput` 各加可选 `providerId?: string`，引擎在组装 input 时填 `currentSel.providerId`（`localChatEngine.ts:518` 调用点一处）。`localChatWiring.ts` 的单例改为**分发客户端**：按 providerId 查 `localChatStore` 配置的 `provider.protocol`——`'ondevice/gguf'` 走端侧客户端，其余走现有 HTTP 客户端。类型侧 `LocalProtocolKind` 增加 `'ondevice/gguf'`，`LocalVendorKey` 增加 `'ondevice'`。
- 引擎工具闸（唯一引擎改动）：`sendLocalChatMessage` 解析 selection 后，若 `provider.protocol === 'ondevice/gguf'`，本轮不取工具声明、系统提示词走无工具版（避免模型被提示词诱导输出伪工具文本）——一个条件分支，不动循环骨架。

### 5.4 配置与 UI 接线（全挂现有层）

- 内置供应商条目：providerId 固定 `ondevice`，`displayName: '本机模型'`，protocol `'ondevice/gguf'`，无 baseUrl、无 apiKeyRef（引擎 `readApiKey` 返回 null，HTTP 客户端本就允许 `apiKey: null`）。其 `models[]` **只同步已下载且校验在案的模型**（管理器在下载完成/删除时回写 config，经 localChatStore 既有持久化落 SQLite）——保证 LocalModelSheet「列出的即可用」，选择器与每线程 modelRef 全部零改造生效。
- 管理面：`app/settings-local-providers.tsx` 列表里「本机模型」置顶为特殊行 → 进新视图 `app/settings-local-ondevice.tsx`（或复用 provider-detail 路由形态）：目录五条逐条呈现 状态（未下载/下载中 x%/校验中/已就绪/失败重试）、大小、许可证标注（3B 条目带研究许可警示）、下载/删除按钮、总占用。视觉与交互沿用 ASR 下载门与本地供应商页的既有形态，不另起设计语言。
- 会话侧零新 UI：本地模式下选中本机模型即走端侧客户端；线程列表仍在本机分区（既有口径：本地是本地）。

## 六、风险与降级（如实）

- **工具调用**：运行时（llama.rn）有通用解析、Qwen 系模板原生带 tools 段——「能解析」不等于「小模型可靠执行」。1–3B 在本引擎的 6 轮循环、全量工具 schema（web 搜索/抓取/JS 沙箱，光 schema 就数千 token）下，格式漂移与参数错误率不可控，且每轮 prefill 按 A76 速度要数十秒。**v1 口径：端侧纯对话，工具面关闭**（5.3 的客户端吞 tools + 引擎不下发双保险）。后续若要开，先立真机成功率验收门（单工具单轮 ≥ 某阈值）再谈，不预先承诺。
- **发热/功耗**：纯 CPU 满核解码是持续高负载，P40 Pro 被动散热下数分钟量级即可能温控降频、速度衰减（本轮未实测，O5 必测并如实记录）；电量消耗显著，属此类功能的固有成本，UI 不做「省电」类虚假承诺。
- **后台限制**：推理只在前台会话内进行；切后台/锁屏时 Android 可能冻结进程——生成中断按既有 `stopped` 形态收尾，不假装续跑。下载同理靠 resumeData 断点而非后台常驻（EMUI 对后台网络与进程的回收更积极，已有 ASR 下载在该机跑通的先例，但 2GB 级时长更久，O2/O5 须实测杀进程续传）。
- **流量与体积**：单模型 0.75–1.96 GiB，首次下载是用户真金白银的流量——只许用户显式点击下载，不做首启自动拉取；管理面逐条标体积；Wi-Fi 提示文案如实标注大小。
- **GPU/NPU 兜底口径**：Kirin 无可用加速路径就是设计基线本身（CPU NEON + Q4_K_M），不存在「加速失败再降级」的二次落差；`n_gpu_layers` 恒 0，OpenCL 在非 Adreno 上不启用、不试探。
- **上下文与长会话**：n_ctx 封顶使超长历史在 llama.cpp 侧截断/移位，长线程的早期内容会被挤出上下文——与云端模型的表现差异要在端侧会话里如实存在（引擎按 wire 历史全量发送，截断发生在原生侧；必要时在 O3 加「按 contextWindow 裁剪历史」的既有口径对齐，本轮未核引擎是否已按 contextWindow 裁剪，不虚报）。
- **iOS**：不在验收范围；llama.rn 本身支持 iOS（Metal），设计未堵死（客户端/管理层皆平台无关，仅运行时后端不同），本期不投入。
