## 一、方案概述与核心诉求穿透

### 1.1 用户原声反馈与真实体验断层分析

在近期完成方案 16（消息列表满页联动键盘上平移架构方案）的初期落地后，用户在 Android 真机环境进行了实际体验，并给出了直击交互本质的精准反馈：

> **用户原声反馈**：  
> “在这个最新位置点击输入框确实消息都往上移动了，**当然还是有空白区域**。第三，在二的基础上点击非输入区域的时候，**消息不是平移往下的，而是会再往上一段距离**。以及现在这个过程的平滑效果也没有，**整个动画都很生硬，就像是生拉硬拽一样... 以及任何地方都要加上平滑效果**。”

用户指出的三个核心问题，精准刻画出了当前系统在动态插值、状态时序与原生布局协同上的深层矛盾：
1. **空白区域问题**：当键盘升起后，消息列表底部与悬浮输入框之间留存了显著的无意义空白，视觉上未贴合，内容未能紧密落在输入框上缘；
2. **反向跳动问题（收起跳升）**：在键盘弹出的状态下，用户点击列表空白区域收起键盘时，消息不仅没有顺滑跟随键盘向下回落，反而**突兀地再次向上跃升一段距离**，随后生硬地卡住；
3. **生硬、生拉硬拽感（缺乏满帧平滑度）**：整个键盘弹起与回落的过程充满锯齿感与卡顿，输入框在向上飞，而消息列表的平移像是在掉帧追赶，呈现出严重的“撕裂”与“生拉硬拽”，缺乏主流高品质即时通讯产品（如 Telegram、WeChat、iOS Messages）所具备的丝滑阻尼感。

### 1.2 丝滑键盘联动的物理直觉与核心工程准则

顶级移动端体验的核心在于**遵循物理世界的确定性与惯性**：
1. **同帧同速同位移（Zero Frame Phase Delay）**：悬浮输入框（Composer）与处于跟随态的消息流（TimelineView），在键盘运动的每一帧（无论 60Hz 还是 120Hz 刷新率），两者的相对距离必须**精确保持恒定**（即设定的 20dp 呼吸间隙），相对位移导数恒为 0；
2. **零 JS 线程插手动效（Pure UI Thread Pipeline）**：键盘运动全程持续约 200~300ms。在此微秒级时间窗口内，严禁任何依赖 React JS 线程 `setState`、`useEffect` 或 Yoga 树重新计算的逻辑介入，所有坐标与内边距必须在底层 UI 线程（Reanimated Worklet）内直接驱动；
3. **收起对称性与无级回滚（Symmetric Reversible Trajectory）**：键盘收起的物理轨迹必须是升起轨迹的精确数学逆过程。在收起的任意时刻（无论正常完成、半途中断、快速二次点按），列表位移均应平滑插值回到静止基线，绝不允许出现突变阶跃（Step Function）或符号反向（Sign Reversal）。

## 二、现状底层动画机制排查与三大生硬跳变根因剖析

### 2.1 底层驱动拓扑：`react-native-keyboard-controller` 在 Android 上的驱动管线

在 Android 11+（API 30+）平台，`react-native-keyboard-controller` 基于 Android 原生 `WindowInsetsAnimationCallback`（向下兼容至低版本的 `ViewCompat.setWindowInsetsAnimationCallback`）构建事件管道：

```
[Android 系统软键盘 (IME)]
        │ 
        ▼ 逐帧触发原生 VSYNC 回调 (60Hz / 120Hz)
[WindowInsetsAnimationCallback.onProgress(insets, runningAnimations)]
        │
        ▼ JNI / C++ Native 层封装
[KeyboardAnimationCallback (Kotlin)]
        │
        ├──► 驱动 Worklet: useKeyboardHandler.onMove(e: { height, progress, duration })
        └──► 更新 UI 线程共享值: useReanimatedKeyboardAnimation({ height, progress })
```

在我们的会话屏（`SessionDetailScreen`）中，当前参与键盘联动的三大核心组件呈现如下拓扑关系：
1. **悬浮输入框（Composer）**：被包裹在 `KeyboardStickyView` 中，直接消费 `useReanimatedKeyboardAnimation()`，通过 `transform: [{ translateY: height.value }]` 在 UI 线程以 GPU 硬件加速方式移动；
2. **消息列表（TimelineView）**：外层通过 `FlatList` 的 `renderScrollComponent` 注入 `KeyboardChatScrollView`，尝试在底层调用 `scrollTo(scrollViewRef, 0, target, false)`，并设置原生 `contentInsetBottom`；
3. **底部羽化遮罩（EdgeFade）**：作为绝对定位的静态 SVG 覆膜，高度由 React 状态 `floatingHeight = overlayHeight + keyboardHeight` 决定。

这一拓扑在理论设计上看似完备，但在实际运行时，由于四处致命的机制冲突，导致了灾难性的交互表现。

### 2.2 病灶一：双重内边距叠加缺陷（Padding Doubling 产生巨大空白断层）

#### 代码级证据穿透
审查 `apps/crish-mobile/src/presentation/timeline/TimelineView.tsx` 第 163-174 行与第 728-732 行：

```tsx
// TimelineView.tsx:163
const effectiveBottomInset =
  floatingOverlayHeight !== undefined
    ? floatingOverlayHeight + (bottomGap ?? theme.space.xl)
    : bottomInset !== undefined && bottomInset > 0
      ? bottomInset
      : theme.space.xxl;

// 底部额外内衬共享值（驱动 KeyboardChatScrollView 的 extraContentPadding）
const extraPaddingSV = useSharedValue(effectiveBottomInset);
useEffect(() => {
  extraPaddingSV.value = effectiveBottomInset;
}, [effectiveBottomInset, extraPaddingSV]);

// ... 第 668 行：注入 KeyboardChatScrollView
renderScrollComponent={(props) => (
  <KeyboardChatScrollView
    {...props}
    keyboardLiftBehavior="whenAtEnd"
    extraContentPadding={extraPaddingSV}
  />
)}

// ... 第 728 行：FlatList 的 contentContainerStyle
contentContainerStyle={{
  paddingHorizontal: 18,
  paddingTop: headerClearance ?? theme.space.lg,
  paddingBottom: effectiveBottomInset, // 致命：FlatList 内部内容已经垫高了 effectiveBottomInset！
  gap: theme.space.lg,
}}
```

#### 原生底层代码还原
再深入查看 `react-native-keyboard-controller` 的底层组件：  
`node_modules/react-native-keyboard-controller/src/components/KeyboardChatScrollView/index.tsx` 第 91 行：
```tsx
const totalPadding = useDerivedValue(() =>
  Math.max(blankSpace.value, padding.value + extraContentPadding.value),
);
```
该 `totalPadding` 被作为 `bottomPadding` 传入 `ScrollViewWithBottomPadding`，进而在 Android 原生层 `ClippingScrollViewDecoratorView.kt` 中生效：
```kotlin
// ClippingScrollViewDecoratorView.kt:53
scrollView.setPadding(
  scrollView.paddingLeft,
  scrollView.paddingTop,
  scrollView.paddingRight,
  (insetBottom + insetTop).toFloat().px.toInt(), // insetBottom 包含了 totalPadding！
)
```

#### 数值推演与空白成因
假设静止常态下：`overlayHeight = 118dp`, `bottomGap = 20dp`，则 `effectiveBottomInset = 138dp`：
1. **FlatList 自身内部**：`contentContainerStyle.paddingBottom` 设置了 **138dp** 的内容垫高；
2. **原生 ScrollView**：`KeyboardChatScrollView` 接收 `extraContentPadding={138dp}`，通过 `setPadding` 为 Android 原生 `ScrollView` 再次追加了 **138dp** 的底部 Padding！
3. **静止时总内衬**：
   $$\text{Total Inset}_{\text{closed}} = 138\text{dp (Yoga Padding)} + 138\text{dp (Native ScrollView Padding)} = 276\text{dp}!$$
   而悬浮输入框实际只需要 138dp 即可避让，此时底部已经多出了整整 $138\text{dp}$ 的无意义空白空间！
4. **键盘弹起时（假设 $K = 300\text{dp}$）**：
   - `padding.value` 跃升为 300dp；
   - 原生 `ScrollView` 的 Padding 变为 $300 + 138 = 438\text{dp}$；
   - 叠加 FlatList 内部的 138dp，列表总底部留白高达：
     $$\text{Total Inset}_{\text{open}} = 138\text{dp} + 438\text{dp} = 576\text{dp}!$$
   - 此时输入框升起后的实际总高度为 $300 + 118 = 418\text{dp}$；
   - 列表最后一条消息距离屏幕底部的总空隙与输入框顶缘之间，形成了高达 $576 - 418 = 158\text{dp}$ 的巨大荒芜空白区域！

这就是用户反馈：“在这个最新位置点击输入框确实消息都往上移动了，**当然还是有空白区域**”的根本物理病因。

### 2.3 病灶二：JS 线程重排竞争与收起反向冲顶根因（`scheduleScrollToEnd(false)` 恶性踩踏）

用户反馈中最反直觉的一点是：“**点击非输入区域的时候，消息不是平移往下的，而是会再往上一段距离**”。

#### 代码病灶溯源
审视 `TimelineView.tsx` 第 525-543 行：

```tsx
useEffect(() => {
  if (
    !follow ||
    isDraggingRef.current ||
    isMomentumRef.current ||
    isProgrammaticScrollingRef.current ||
    blocks.length === 0
  )
    return;
  scheduleScrollToEnd(false); // 致命：传入 animated = false
  // bottomInset 入 deps：浮层增厚（错误条/停止胶囊出现、键盘弹起）
  // 时跟随态须重新贴底，否则尾部会被新浮层压住一截
}, [
  follow,
  blocks.length,
  scheduleScrollToEnd,
  bottomInset,           // 致命监听源！
  effectiveBottomInset,
]);
```

#### 逆向跳跃踩踏时序全息还原

```
[用户点击时间线非输入区域]
        │
        ├──► 1. 触发 TimelineView 的 onTouchStart ──► Keyboard.dismiss()
        │
        ├──► 2. 原生 Android 开启 WindowInsetsAnimation 收起动画 (全程约 250ms)
        │
        ├──► 3. KeyboardChatScrollView 原生工作线程启动:
        │         closing.value = true;
        │         offsetBeforeScroll.value = scroll.value - actualOpenShift.value;
        │         准备在随后的 250ms 内逐帧向下回调 scrollTo 回退位置...
        │
        ├──► 4. 【致命断裂】：与此同时，JS 线程接收到键盘状态变化 (useKeyboardHeight)
        │         keyboardHeight 从 300 变更为 0 (或开始递减)
        │         SessionDetailScreen 重新渲染，重算 timelineBottomInset
        │         TimelineView 的 props.bottomInset 发生变更！
        │
        ├──► 5. 【踩踏爆发】：TimelineView.tsx:525 的 useEffect 被触发执行！
        │         此时用户并未拖拽 (isDraggingRef = false)，处于 follow 态
        │         useEffect 立即调度 scheduleScrollToEnd(false)！
        │         通过 requestAnimationFrame 调用：targetRef.current?.scrollToEnd({ animated: false })
        │
        └──► 6. 【冲顶现象产生】：
                  此时 Android 原生 ScrollView 内部的 insetBottom 尚未完全完成收起 (仍有残余 padding)，
                  scrollToEnd({ animated: false }) 瞬间按照当前的 maxScroll 执行硬跳转！
                  contentOffset.y 被猛烈强推至最大值，内容被“啪”地一下强行往上拽了一大截！
                  几毫秒后原生动画结束清空 padding，视口再次剧烈抖动抽搐！
```

**结论**：收起键盘时发生反向向上跳动，正是由于 **JS 线程基于 React Hook（`useKeyboardHeight`）的异步响应，在动画中途强行执行了 `scrollToEnd(false)`**，粗暴斩断了原本应该平滑向下的原生回滚过程，硬生生把列表打回最大底部偏移！

### 2.4 病灶三：Android 主线程 `requestLayout()` 布局重排雪崩与“生拉硬拽”卡顿机理

用户反馈：“**整个动画都很生硬，就像是生拉硬拽一样... 以及任何地方都要加上平滑效果**”。

#### 为什么 `KeyboardChatScrollView` 在 Android 上会产生“生拉硬拽”感？

1. **`setPadding` 引发的 Android UI 线程重排雪崩**：  
   `KeyboardChatScrollView` 依赖底层 `ClippingScrollViewDecoratorView.kt`。如前文源码所示，当键盘高度变化时，它调用了 `scrollView.setPadding(...)`。  
   在 Android View 体系中，`View.setPadding()` 会标记 `PFLAG_FORCE_LAYOUT` 并向上调用 `parent.requestLayout()`。这意味着在键盘升起的 250ms 期间，Android 的 UI 线程必须执行昂贵的 View 树测高与排版计算，而不是纯粹的 GPU 变换！
2. **CPU `scrollTo` 与 GPU `translateY` 的渲染管线脱节**：  
   - `KeyboardStickyView` 中的输入框是通过 RenderNode 的 `transform: [{ translateY }]` 位移的，该操作完全在 Android 的 RenderThread（渲染线程）上进行硬件矩阵变换，达到稳固的 120fps；  
   - 而 `KeyboardChatScrollView` 试图通过在每一帧向 `ScrollView` 发送 `scrollTo()` 指令来推动消息列表。在 Android 上，连续的 `scrollTo()` 会导致 `mScrollY` 变化、Canvas 重新裁剪、分发 `onScrollChanged` 并向 React Native 桥接队列派发事件；  
   - 一个走 GPU 硬件变换（快且无布局开销），一个走 CPU 滚动计算与重排（慢且容易阻塞丢帧）。**两者在时间线上存在严重的相位差（Phase Jitter）**，导致输入框已经在高速上升，而消息流却在断断续续地抽动，给用户留下了极其强烈的“生拉硬拽”、“生硬撕扯”的恶劣观感。

### 2.5 病灶四：底部 `EdgeFade` 静态 React State 滞后突变与泛白闪烁

审查 `sessionDetailScreen.tsx` 第 108 行：
```tsx
<EdgeFade side="bottom" height={Math.max(0, floatingHeight)} />
```
与 `useTimelineBottomInset.ts` 第 129 行：
```ts
const floatingHeight = effectiveOverlayHeight + keyboardHeight;
```

#### 视觉突变机制
1. `keyboardHeight` 来自 `useKeyboardHeight()`（React 状态 Hook）；
2. 当软键盘升起时，在底层 120fps 动画播放的 250ms 内，React JS 线程的 `keyboardHeight` 状态完全处于滞后状态（通常在动画完成后或中途才触发重渲染）；
3. 底部 `EdgeFade` 是一个普通的 React 函数组件，没有接任何 Reanimated 共享值动画；
4. 现象：输入框已经飞起，底部羽化遮罩却停在原地；当键盘终于到位后，React 状态更新，`EdgeFade` 的高度瞬间从 138dp 暴增到 438dp，一整块半透明渐变覆膜突然“砸”在屏幕底部，遮挡了消息内容；
5. 收起时同理，键盘已降下，底部白色的羽化覆膜依然悬在半空，几百毫秒后突然“啪”地消失。这使得用户在视觉感知上觉得全屏幕都在生硬闪烁。

## 三、满帧平滑升降动画方案（Reanimated Worklet 协同物理管线）

### 3.1 视口几何单一真理源（SSOT）重构与全生命周期去 JS 调度

必须刚性确立两条架构铁律：
1. **静态 Yoga 布局原则（Static Yoga Inset）**：
   `TimelineView` 的 FlatList `contentContainerStyle.paddingBottom` **恒定只等于「悬浮输入框静止高度 + 呼吸空隙（20dp）」**，在整个应用生命周期中，**绝不跟随键盘高度动态增减**！
   $$\text{StaticPaddingBottom} = \text{effectiveOverlayHeight} + \text{gap}$$
   从根源上彻底斩断键盘动作引发的 Yoga 树全量重排和 Android `requestLayout()` 性能雪崩！
2. **JS 线程滚动力学完全解耦**：
   从 `TimelineView.tsx` 的跟随监听中，**彻底移除 `bottomInset` 与 `effectiveBottomInset` 依赖**！键盘的弹起与收起，**绝对不允许在 JS 线程触发任何 `scrollToEnd`**。

### 3.2 方案选型深度对照：自研 UI 线程连续 Worklet 联动 vs 深度矫正 `KeyboardChatScrollView`

| :--- | :--- | :--- |
| **底层实现机制** | 修改 `extraContentPadding` 配置并去除 FlatList 重复 padding | 基于 `useKeyboardHandler` 的 `onMove` 驱动 Reanimated Worklet，直接计算位移 |

| **收起反向跳动防御** | 易受库内部 `useChatKeyboard` 对 `actualOpenShift` 判定的边界偶发缺陷影响 | **100% 自主可控**：显式追踪开闭过程与起始锚点，物理公式严格对称，杜绝任何逆向阶跃 |

### 3.3 架构决策：原生 UI 线程 120fps 连续协同插值引擎

我们利用 `react-native-keyboard-controller` 提供的原生级 `useKeyboardHandler`，在 UI 线程构建毫秒级响应的闭环控制器：

```ts
// 核心动力学控制器接口示意
export function useSmoothKeyboardTimelineLinkage(
  scrollViewRef: AnimatedRef<FlatList<any> | Animated.ScrollView>,
  options: {
    follow: boolean;
    overlayHeight: number;
    gap: number;
    onFollowChange: (follow: boolean) => void;
  }
) {
  // UI 线程共享值：记录键盘动作触发瞬间的初始滚动状态与内容状态
  const initialScrollY = useSharedValue(0);
  const isEligibleForLift = useSharedValue(false);
  const maxDisplacement = useSharedValue(0);
  const currentLiftProgress = useSharedValue(0);

  useKeyboardHandler({
    onStart: (e) => {
      'worklet';
      // 1. 键盘开始运动：捕获当前的滚动坐标与视口几何
      if (e.height > 0) {
        // 键盘弹起：判定当前是否处于满页且触底状态
        initialScrollY.value = currentScrollY.value;
        const isAtBottom = checkIsAtBottom(currentScrollY.value, viewportHeight.value, contentHeight.value);
        isEligibleForLift.value = options.follow && isAtBottom;
        
        // 计算最大需要平移的距离（至多为键盘高度与内容可滚动空间的协调值）
        maxDisplacement.value = e.height;
      } else {
        // 键盘收起：严格锁定收起轨迹的起始位移
        // 杜绝任何重新采样或突变，以当前已推升的高度为基准顺滑向下递减！
      }
    },
    onMove: (e) => {
      'worklet';
      // 2. 逐帧连续插值 (60Hz / 120Hz VSYNC 同步)
      if (!isEligibleForLift.value) return;

      currentLiftProgress.value = e.progress;
      const targetDisplacement = maxDisplacement.value * e.progress;
      
      // 直接在 UI 线程逐帧调用平滑滚动，无任何 requestLayout 开销
      const targetScrollY = initialScrollY.value + targetDisplacement;
      scrollTo(scrollViewRef, 0, targetScrollY, false);
    },
    onEnd: (e) => {
      'worklet';
      // 3. 动画平稳落定：同步最终坐标，清除瞬态标记
      if (e.height === 0) {
        isEligibleForLift.value = false;
      }
    },
  });
}
```

### 3.4 满页触底、短对话与历史翻阅的三态连续物理方程

#### 状态 A：满页且吸底（`follow === true` 且处于内容末尾）
- **物理现象**：最新一条消息底部原本停在距屏幕底端 $H_{\text{bottom}} = \text{overlayHeight} + \text{gap}$ 处；
- **动力学方程**：  
  设当前时刻键盘高度为 $k(t)$，归一化进度为 $p(t) \in [0, 1]$：
  $$S(t) = S_0 + k(t)$$
- **效果**：消息流以与键盘完全相等的瞬时加速度和速度同步向上移动，最后一条消息与升起的输入框顶缘的间距全程严格保持为 $\text{gap} = 20\text{dp}$，不多一分空白，不少一分遮挡！

#### 状态 B：短对话（未满一屏，内容高度较小）
- **物理现象**：只有 1~2 条消息，内容底端原本就悬在屏幕中央或上半区；
- **防越界方程**：  
  设消息内容总高为 $H_{\text{content}}$，视口高度为 $H_{\text{viewport}}$，头栏避让区为 $H_{\text{header}}$：
  $$\text{FreeSpace} = H_{\text{viewport}} - H_{\text{content}} - H_{\text{header}} - \text{overlayHeight}$$
  若 $\text{FreeSpace} \ge k(t)$，则键盘完全处于空白区内，**位移推升量恒为 0**（$S(t) = S_0$）；  
  若 $\text{FreeSpace} < k(t)$，则仅推升溢出的差额：
  $$\Delta S(t) = k(t) - \text{FreeSpace}$$
- **效果**：短消息不会被无脑顶进顶部头栏背后，永远保持优雅沉底或就近停留！

#### 状态 C：历史翻阅态（`follow === false`）
- **物理现象**：用户正在回看前面的第 5 条消息；
- **保护方程**：  
  $$S(t) \equiv S_{\text{userReading}}$$
- **效果**：无论输入框如何升降，用户当前阅读的消息行在屏幕坐标系中**绝对静止不动**，视口零抖动，输入框仅作为悬浮层静默覆盖下部区域。

### 3.5 底部 `EdgeFade` 120fps 动效改造（SharedValue 逐帧贴合）

将原本基于 React Props 静态传值的 `EdgeFade`，升级为支持 Reanimated 动效的现代架构：

```tsx
// 改造后的 EdgeFade 消费 UI 线程动态高度
export function AnimatedEdgeFade({
  side,
  baseHeight,
  animatedAdditionalHeight,
}: {
  side: 'bottom';
  baseHeight: number;
  animatedAdditionalHeight: SharedValue<number>;
}) {
  const animatedStyle = useAnimatedStyle(() => {
    'worklet';
    // 实时计算总高：baseHeight (overlayHeight) + 动态键盘高度

    return {
      height: Math.max(0, totalHeight),
    };
  });

  return (
    <Animated.View style={[{ position: 'absolute', bottom: 0, left: 0, right: 0 }, animatedStyle]}>
      {/* 渐变遮罩渲染 */}
    </Animated.View>
  );
}
```
通过该改造，底部羽化遮罩将伴随输入框以微秒级同步拉伸与回缩，彻底根除“白块滞后闪现”的视觉灾难。

## 四、全链路交互与边界状态治理

### 4.1 点击空白区域收起键盘（Dismiss Keyboard）安全状态机

#### 现状缺陷排查
在当前 `TimelineView.tsx` 中：
```tsx
onTouchStart={dismissKeyboardForTimelineTap}
```
直接在根容器的 `onTouchStart` 上无条件调用 `Keyboard.dismiss()`，存在两大严重隐患：
1. **轻微滑动误判**：用户手指按下准备开始上下滑动浏览时，在滑动的最初几个像素点就会被立即触发 `Keyboard.dismiss()`，导致键盘误收；
2. **滚动中途误触**：列表惯性滑动（Momentum）过程中，手指点击屏幕叫停（Cancel Scroll）时，也会强杀键盘，引发视觉跳跃。

#### 治理方案：手势意图识别与安全收起状态机
1. **利用 FlatList 标准 `keyboardDismissMode="on-drag"`**：作为拖拽收起的权威通道；
2. **静止点按的确定性收起**：通过包装时间线背景点击（非消息气泡内部的空白区域），在触摸释放（`onPress` 或 `touchEnd`）且未发生滚动位移时，才触发失焦收起；
3. **收起期间的动效互斥锁**：当由点击空白触发收起时，设置 UI 线程互斥标志 `isDismissingByTap.value = true`，在此期间，列表绝对禁止响应任何来自 JS 线程的滚动校准，确保原生收起回滚动画完整、对称地执行完毕。

---

### 4.2 打字中与多行动态生长（Multiline Composer expansion）的平滑吸收机制

当用户在输入框中输入长文本导致输入框从 1 行换行膨胀到 3 行（高度由 52dp 增加到 98dp）时：
1. `KeyboardStickyView` 的 `onLayout` 测量出新的 `overlayHeight`；
2. 由于我们坚持 **Yoga 静态 Padding 模式**，输入框高度增加的 $\Delta H$ 通过 Reanimated 的 `extraContentPadding` 机制平滑推送；
3. 列表内容在 UI 线程向上微调 $\Delta H$,使得尾部消息与增高的输入框顶缘依然丝毫不差地维持 20dp 呼吸区，不会产生任何挤压变形。

---

### 4.3 快速切换焦点与键盘抖动防御（Keyboard Jitter / Fast Toggle Hysteresis）

在极端操作场景下（如用户在 200ms 内快速连续点击输入框、点空白收起、再快速点击输入框）：
1. **中途反转平滑插值（Mid-flight Direction Reversal）**：  
   `useKeyboardHandler` 的 `onMove` 能够自动跟随 Android 原生动画的实际瞬时高度。当动画在半途被反向逆转时，动力学方程直接以当前瞬态进度 $p_{\text{current}}$ 作为新的起点进行无缝过渡，绝不出现回到 0 重新开始的重置闪烁；
2. **迟滞带状态机保护**：  
   在键盘收起未完全 settle（到达基线）前，`follow` 状态锁死为收起前的状态，防止状态机在临界点疯狂跳变。

---

### 4.4 回到底部按钮（`ScrollToBottomButton`）物理坐标与平滑淡出协同

回到底部按钮必须严格遵守 **方案 14 与方案 16 的键盘解耦与淡出规范**：
1. **基准物理锚点**：纯静态定位于 `overlayHeight + 8dp`，严禁在 JS 线程累加任何键盘高度；
2. **UI 线程渐隐 Worklet**：  
   在键盘弹起的最初 **40dp** 内，按钮在原位以 `withTiming` 快速平滑淡出（Opacity 从 1 降为 0），并设置 `pointerEvents="none"`；
3. **退场静默**：键盘完全弹起打字期间，按钮在原位隐身，绝对不飞窜到屏幕中央或遮挡输入内容；
4. **键盘收起复原**：当键盘收回至距底端 40dp 以内时，按钮若仍满足 `!follow` 条件，则在原位以 150ms 平滑淡入，浑然天成。

### 5.3 `useTimelineBottomInset.ts` / `timelineBottomInset.ts` 纯粹化

**改动要点**：
- `deriveTimelineBottomInset` 中去除 `keyboardHeight` 的累加，纯粹推导静态避让高度；
- `useTimelineBottomInset` 仅产出 `staticBottomInset` 与 `overlayHeight`，消除一切双源污染。

```ts
// apps/crish-mobile/src/domain/pure/timelineBottomInset.ts

export interface TimelineBottomInsetInput {
  overlayHeight: number;
  gap: number;
  minOverlayHeight?: number;
}

/**
 * 推导时间线 FlatList 静态真实的 contentContainerStyle.paddingBottom。
 * 键盘高度已完全移交 UI 线程 Worklet 实时驱动，严禁在此静态叠加！
 */
export function deriveTimelineBottomInset(
  input: TimelineBottomInsetInput
): number {
  const minOverlay = sane(input.minOverlayHeight);
  const measuredOverlay = sane(input.overlayHeight);
  const effectiveOverlay = Math.max(minOverlay, measuredOverlay);
  const gap = sane(input.gap);

  return effectiveOverlay + gap; // 纯净的静态物理高度，彻底杜绝空白与冲突
}
```

## 七、单元测试与验证矩阵

方案配套全套自动化单元测试，对齐本仓门禁铁律：

### 7.1 纯数学与几何推导单元测试
- **`timelineBottomInset.test.ts`**：
  - 验证 `deriveTimelineBottomInset` 彻底剥离 `keyboardHeight` 后的纯净输出；
  - 验证实测值、保底值、gap 的精确加和，绝无重复倍增；
  - 验证负数与 NaN 边界守卫。

### 7.2 UI 线程动力学状态机测试（Mock Reanimated / Keyboard Controller）
- **`useSmoothKeyboardTimelineLinkage.test.ts`**：
  - 模拟 `onStart` -> `onMove` (progress 0 -> 0.5 -> 1.0) -> `onEnd` 序列，断言 `scrollTo` 调用的单调性与线性平滑度；
  - 模拟收起流程，断言位移严格递减，断言 `scrollTo` 目标值永不大基于前一帧（彻底杜绝反向向上跳）；
  - 模拟 `follow === false` 场景，断言 `scrollTo` 零调用。

### 7.3 组件交互集成测试
- **`sessionDetailScreen.motion.test.tsx`**：
  - 验证软键盘弹起时 `EdgeFade` 动态样式的 `height` 连续性；
  - 验证 `ScrollToBottomButton` 在 40dp 阈值内的淡出与属性锁定；
  - 验证点击空白处收起键盘时，无意外的 `scrollToEnd(false)` 调用。
