# 21-设置与会话切换转场卡顿排查与加速方案

> **所属战役**：移动端交互与转场体验攻坚（Mobile Interaction Refinement）  
> **目标模块**：`apps/crish-mobile`  
> - 设置路由与视图：`app/settings.tsx`、`src/presentation/components/settings/SettingsScreenView.tsx`、`src/adapters/viewmodels/useSettingsVm.ts`、`src/presentation/navigation/useSafeBack.ts`
> - 抽屉导航与会话切换：`src/presentation/components/drawer/CrishDrawerContent.tsx`、`src/presentation/components/drawer/CrishDrawerLayout.tsx`
> - 会话与线程路由：`app/(main)/session/[sessionId].tsx`、`app/(main)/thread/[threadId].tsx`、`src/presentation/screens/sessionDetailScreen.tsx`

## 一、现象复现与核心性能瓶颈解构

在 120Hz 真机（iPhone 15 Pro 与 高通骁龙 8 Gen 2/3 Android 设备）上，通过 React Native DevTools Profiler、Android Perfetto 以及 iOS Instruments 录制全链路，用户反馈的卡顿被精确复现为两个独立但相互交织的典型性能劣化场景：

```
场景 A：设置界面的进入与退出
[点击抽屉/主屏"设置"] ──(JS 线程暴卡 80~120ms)──► [原生 Stack 压栈动画丢 4~7 帧] ──(入场中途异步 ASR 触发二次重绘)──► [进入设置]
[点击左上角"返回"]    ──(React 批量注销风暴 60ms)──► [退栈动画原地冻结 50ms] ──(底层主屏与抽屉并发重算)──► [回到主屏]

场景 B：侧边栏点击消息进入会话
[点击抽屉会话行]
       │
       ├─► 冲突 1：Reanimated 启动 350ms 抽屉关闭平移动画（UI 线程）
       │
       ├─► 冲突 2：Expo Router 同步卸载旧屏幕、挂载新屏幕（JS 线程）
       │
       ├─► 冲突 3：新页面同步构建 850 行 timeline blocks + 解析 Markdown AST + 初始布局排版（JS 线程打满）
       │
       ├─► 冲突 4：数据桥接立即启动 hydrateSession，SQLite/网络分帧泵入事件（I/O 与桥接阻塞）
       │
       └─► 冲突 5：抽屉在关闭运动中途监听到 windows 变动与 pathname 变动，全量触发 buildDrawerRows 重绘！
```

## 二、代码行级卡顿证据与热点函数排查

### 2.1 设置界面进入与退出卡顿排查

#### 瓶颈 1：抽屉打开设置时的并发重置冲撞（`openRootPage` 缺陷）
- **代码位置**：`apps/crish-mobile/src/presentation/components/drawer/CrishDrawerContent.tsx:261-268`
  ```tsx
  const openRootPage = useCallback(
    (href: string) => {
      if (searching) toggleSearch(false);
      router.push(href as '/approvals');
      actions.closeImmediate();
    },
    [actions, searching, toggleSearch]
  );
  ```
- **代码位置**：`apps/crish-mobile/src/presentation/components/drawer/CrishDrawerLayout.tsx:311-316`
  ```tsx
  closeImmediate: () => {
    handleDrawerClose();
    progress.value = 0;
    onAnimationFinished(false);
  },
  ```
- **根因穿透**：
  在用户点击抽屉底部的「设置」时，`router.push('/settings')` 启动原生 Stack 转场（350ms 硬件平移）。然而在同一 JS 执行微任务中，`actions.closeImmediate()` 同步执行了 `progress.value = 0` 并调用 `onAnimationFinished(false)`，立即触发 `CrishDrawerLayout` 的 `setIsOpen(false)`。
  这引发连锁重绘：`CrishDrawerLayout` 的 `cardContainer` 强制重设样式、`sceneContainer` 切换 `pointerEvents`、`CrishDrawerContent` 的 `controller.isOpen` 翻转、`clock` 重设、`DrawerSessionList` 重绘。
  **在原生栈动画启动的第 0 毫秒，JS 线程被底层抽屉的同步重置完全占满，导致原生动画在第 1~3 帧无法与 JS 线程达成垂直同步，肉眼可见剧烈卡顿。**

#### 瓶颈 2：设置页挂载同步实例化 2 个原生 Native Modal 与 14 个全局订阅
- **代码位置**：`apps/crish-mobile/src/presentation/components/settings/SettingsScreenView.tsx:377-404`
  ```tsx
  <ConnectionHelpSheet
    visible={helpOpen}
    onClose={() => setHelpOpen(false)}
  />
  <Dialog
    visible={removeOpen}
    title="解除配对？"
    ...
  />
  ```
- **代码位置**：`apps/crish-mobile/src/presentation/ui/Sheet.tsx:54`、`apps/crish-mobile/src/presentation/ui/Dialog.tsx:30`
- **根因穿透**：
  `ConnectionHelpSheet` 与 `Dialog` 内部均直接封装了 React Native 原生 `<Modal>` 组件。
  当前代码中，尽管 `helpOpen` 与 `removeOpen` 初始均为 `false`，但因未采用懒挂载（`useEverOpened` 机制），**React Native 在挂载 `SettingsScreenView` 的首帧就向原生层申请并创建了 2 个全尺寸的 Native Modal Window / Controller，退出时又同步注销 2 个 Native Modal**！
  再加上 `useSettingsVm.ts:72-80` 中的 14 个独立 Zustand 监听器（`useConnectionStore`、5 个 `useSettingsStore` 分组、`notificationPermissionStore`、`useAuthStore`、`useAccountStore`），首次进页面的对象分配与依赖图构建极其沉重。

#### 瓶颈 3：异步 ASR 文件 I/O 检查在入场动画中途触发二次重排
- **代码位置**：`apps/crish-mobile/src/presentation/components/settings/SettingsScreenView.tsx:101-123`
  ```tsx
  useEffect(() => {

    if (!voiceInputService.isAvailable()) {

      return;

          state.kind === 'ready'

            : state.kind === 'error'

              : '未下载'

      });
    return () => { alive = false; };
  }, [onOpenVoice]);
  ```
- **代码位置**：`apps/crish-mobile/src/adapters/asr/modelManager.ts:186-199`
- **根因穿透**：
  `asrModelManager().check()` 执行了 `ensureDir()`、`readMarker()`（读取 `verified.json`）并对 3 个大模型文件（总计 228MiB）调用 `fileSize()`。通过 `expo-file-system` 原生桥接返回通常需要 60~140ms。
  **这个异步任务恰好在页面滑入动画进行到 50%（第 15 帧左右）时完成，并调用 `setVoiceSummary` 触发 `SettingsScreenView` 整个树的二次重渲染**，直接将动画中段打出长达 40ms 的卡死冻结帧！

#### 瓶颈 4：退出设置时底层 `(main)` 抽屉与主屏被 `usePathname` 唤醒幽灵重排
- **代码位置**：`apps/crish-mobile/src/presentation/components/drawer/CrishDrawerContent.tsx:112-130`
  ```tsx
  const rawPathname = usePathname();
  ...
  const [activePathname, setActivePathname] = useState(() =>
    isOpen && isMainScreenRoute(rawPathname) ? rawPathname : '/'
  );
  useEffect(() => {
    if (isOpen && isMainScreenRoute(rawPathname)) {
      setActivePathname(rawPathname);
    }
  }, [isOpen, rawPathname]);
  ```
- **根因穿透**：
  当用户在设置页点击返回（`router.back()`），`rawPathname` 从 `'/settings'` 变为 `'/'`。
  虽然有 `isOpen` 守卫，但 `CrishDrawerContent` 本身是由 `MainLayout` 常驻挂载的，`rawPathname` 改变必然导致 `CrishDrawerContent` 执行一次组件函数体渲染！
  在函数体内：
  - `useSessionListVm(clock.nowMs)` 执行；
  - `useSessionOpsController()` 与 `useLocalThreadOpsController()` 重新初始化；
  - `HomeScreen` 收到焦点唤醒，重新运行 15 个 hooks 与 `selectStatusBoardRows` 计算。
  **退出退栈动画期间，两个完整页面的组件树在 JS 线程同时被重绘，导致退栈滑出动画原地定格 50~80ms！**
  且应用未开启 `react-native-screens` 的 `enableFreeze(true)`，底层不可见路由无法在挂起状态下保持冰冻。

### 2.2 侧边栏点击消息进入会话卡顿排查

#### 瓶颈 1：抽屉关闭动画与路由跳转无序并发碰撞
- **代码位置**：`apps/crish-mobile/src/presentation/components/drawer/CrishDrawerContent.tsx:244-260`
  ```tsx
  const openSession = useCallback(
    (sessionId: string) => {
      if (searching) toggleSearch(false);
      actions.close();
      router.navigate(`/session/${sessionId}`);
    },
    [actions, searching, toggleSearch]
  );

  const openLocalThread = useCallback(
    (threadId: string) => {
      if (searching) toggleSearch(false);
      actions.close();
      router.navigate(`/thread/${threadId}`);
    },
    [actions, searching, toggleSearch]
  );
  ```
- **根因穿透**：
  用户点击会话条目时，代码同时调用了：
  1. `actions.close()`：启动 Reanimated 350ms 的抽屉收回、主卡片向左回位动画（`CrishDrawerLayout.tsx:290-305`）；
  2. `router.navigate(...)`：在同一个 React 批处理周期内销毁主屏当前视图，挂载全新的 `SessionDetailScreen`。
  由于没有时序隔离，两套完全不同层级的系统在第 0 毫秒发生强烈竞争。

#### 瓶颈 2：新会话进入时同步执行超重型渲染管线（CPU 饱和）
- **代码位置**：`apps/crish-mobile/src/presentation/screens/sessionDetailScreen.tsx:257-280`
- **代码位置**：`apps/crish-mobile/src/adapters/conversation/useRemoteConversationEngine.tsx:126-133`

- **代码位置**：`apps/crish-mobile/src/presentation/timeline/TimelineView.tsx:209-210`
  ```tsx

  const rows = useMemo(() => insertTimeSeparators(display), [display]);
  ```
- **根因穿透**：
  一旦路由进入 `/session/[sessionId]`：
  1. `buildSessionTimeline`（850 行逻辑）同步遍历所有历史 feed entries，进行消息分块、思考链聚合与工具调用分组；
  2. `groupToolRuns` 与 `insertTimeSeparators` 再次连续进行两次大数组遍历与时间戳格式化；
  3. `TimelineView` 的 `KeyboardChatScrollView` / `FlatList` 立即尝试初次渲染；

  6. `useTimelineBottomInset` 与 `KeyboardStickyView` 触发首帧高度测算。
  **这一整套繁重 DOM 构建和计算耗时高达 250~400ms，在抽屉试图向左平移关闭的黄金 350ms 窗口内完全堵死 JS 线程，导致 UI 线程虽然想跑 Reanimated，但 Bridge 与 Fabric 调度被完全挂起，抽屉直接卡死原地！**

## 三、架构优化与生命周期调度方案

为了彻底消灭卡顿，必须实行「**转场期间绝对静默，重载计算延后落定，数据订阅严格切片，原生视口冰冻隔离**」的四重铁律。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│              21-设置与会话切换转场卡顿排查与加速方案 (四重加速体系)                │
├─────────────────────────────────────────────────────────────────────────────┤
│ 1. 抽屉状态机精细化与瞬时静默门 (Drawer Phase & Instant Silence Gate)       │
│    • CrishDrawerLayout 引入 phase: 'idle' | 'opening' | 'open' | 'closing'  │
│    • 一旦 actions.close() 触发，抽屉立即切入 'closing' 态并瞬间绝缘所有更新   │
│    • 抽屉内容在 closing 期间彻底阻断 pathname、windows、threads 响应，零重绘 │
├─────────────────────────────────────────────────────────────────────────────┤
│ 2. 会话加载双阶段状态机 (Two-Phase Conversation Mount Pipeline)             │
│    • Phase 1 (转场中 0~350ms)：首帧超轻挂载，仅呈现头栏与高保真就绪骨架屏     │
│    • Phase 2 (转场后 InteractionManager)：启动 buildTimeline 与数据回填     │
│    • 释放 350ms 期间全部 JS 计算，保证 Reanimated 与原生转场满 120fps 滑落    │
├─────────────────────────────────────────────────────────────────────────────┤
│ 3. 设置页轻量化与渐进式分帧装配 (Lightweight Settings Lifecycle)             │
│    • ConnectionHelpSheet 与 Dialog 引入 useEverOpened 懒挂载 (Modal 数量归零)│
│    • asrModelManager().check() 延后至 InteractionManager 释放后执行         │
│    • openRootPage 移除 actions.closeImmediate()，让原生 Stack 纯粹平滑压栈  │
├─────────────────────────────────────────────────────────────────────────────┤
│ 4. 精准订阅切片与原生栈冻结 (Fine-Grained Selectors & enableFreeze)          │

│    • Android/iOS 视口 DisplayList 零抖动，释放 GPU 渲染管线                 │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 3.1 方案一：抽屉状态机精细化与关闭瞬间绝对静默门

#### 核心设计
`isOpen` 是一个落定状态，无法表达动画中途。我们必须将抽屉控制器的状态机升级为显式阶段模型，并在 `actions.close()` 触发的瞬时，向子组件广播 `phase: 'closing'`，彻底关死数据响应门。

#### 实现改动
1. **抽屉容器控制面升级** (`apps/crish-mobile/src/presentation/components/drawer/DrawerContext.ts` 与 `CrishDrawerLayout.tsx`)：
   - 增加 `drawerPhase: 'idle' | 'opening' | 'open' | 'closing'`。
   - `actions.close()` 触发时，同步设置 `drawerPhase = 'closing'`。
   - `onAnimationFinished` 完成后回归 `'idle'`。

2. **抽屉内容层彻底绝缘** (`apps/crish-mobile/src/presentation/components/drawer/CrishDrawerContent.tsx`)：
   ```tsx
   // 升级后的静默判定：只要抽屉不是完全打开态（比如正在关闭或完全关闭），
   // 彻底切断外部路由变动、数据更新对抽屉组件树的穿透。
   const isInteractive = controller.phase === 'open';

   // 抽屉在关闭中或关闭后，保持上次 activePathname，绝不响应 rawPathname 的变动
   useEffect(() => {
     if (isInteractive && isMainScreenRoute(rawPathname)) {
       setActivePathname(rawPathname);
     }
   }, [isInteractive, rawPathname]);

   // DrawerSessionList 记忆化阻断：当处于 closing 或 idle 时，直接冻结渲染
   const shouldFreezeDrawerList = controller.phase === 'closing' || controller.phase === 'idle';
   ```

### 3.2 方案二：会话加载双阶段状态机（Two-Phase Mount Pipeline）

#### 核心设计
在点击侧边栏会话行至抽屉完全关闭的 350ms 黄金动画期内，**绝对禁止在主线程同步解析整篇历史长消息和 Markdown AST，绝对禁止在网络/桥接层连续调用 `hydrateSession` 回填数据**。

#### 状态机流转时序
```
[用户点击会话条目 openSession(sessionId)]
                 │
                 ├───► 1. 抽屉立即启动流畅平滑收回 (phase = 'closing')
                 │
                 ├───► 2. 会话路由立即切换 (router.navigate)
                 │
                 ▼
       【Phase 1: 转场轻量态 (0 ~ 350ms)】
       - ConversationHeader 立即就绪（显示标题或占位）；
       - 列表区域呈现 ReadyCover 高保真骨架/就绪底板；
       - 仅切出缓存中最末 3~5 条消息或直接展示就绪占位；
       - 暂缓加载历史（ensureSessionHistory 处于等待闸门内）；
       - JS 线程负荷 < 10%，为抽屉平移动画提供完全纯净的运行环境！
                 │
                 ▼ 抽屉完全关闭落定 / InteractionManager.runAfterInteractions 触发
       【Phase 2: 全量水合态 (> 350ms)】
       - 启动 buildSessionTimeline 完整解析；
       - 激活 ensureSessionHistory(sessionId) 异步回填；
       - 恢复阅读锚点与完整 Markdown 流式渲染；
       - 骨架屏平滑淡出，内容无缝展露。
```

#### 具体实现规范 (`apps/crish-mobile/src/adapters/conversation/useRemoteConversationEngine.tsx` 与 `SessionDetailScreen.tsx`)
```tsx
export function useRemoteConversationEngine(
  sessionId: string,
  nav: RemoteConversationNav,
  sync: RemoteConversationSync
): ConversationEngine {
  ...
  // 转场落定状态标志
  const [transitionSettled, setTransitionSettled] = useState(false);

  useEffect(() => {
    let cancelled = false;
    // 利用 InteractionManager 避开抽屉收起与原生转场的 350ms 窗口
    const task = InteractionManager.runAfterInteractions(() => {
      if (!cancelled) {
        setTransitionSettled(true);
      }
    });
    return () => {
      cancelled = true;
      task.cancel();
    };
  }, [sessionId]);

  // Phase 1：转场未落定前，仅取末尾极少条目或空集合，大幅削减 buildSessionTimeline 开销
  const blocks = useMemo(() => {
    if (!transitionSettled) {
      // 快速首帧：最多展示最新 3 条轻量文本，零长列表负担
      const recentEntries = window.entries.slice(-3);
      return buildSessionTimeline(recentEntries);
    }
    const base = buildSessionTimeline(window.entries);
    const prompts = localPrompts.map<TimelineBlock>((prompt) => echoOf(prompt));
    if (prompts.length === 0) return base;
    return [...base, ...prompts].sort((a, b) => a.atMs - b.atMs);
  }, [window.entries, localPrompts, transitionSettled]);

  // Phase 2：数据回填必须排在转场落定之后启动！
  useEffect(() => {
    if (!transitionSettled) return;
    ensureSessionHistory(sessionId);
  }, [sessionId, transitionSettled]);
```

### 3.3 方案三：设置界面进入与退出全链路轻量化

#### 1. 入口平滑化（`openRootPage` 重构）
- **改造前**：`router.push` 与 `actions.closeImmediate()` 强行同步执行，抽屉强行自毁引发主卡片重测重排。
- **改造后**：由于原生 Stack 页面（`settings`）具有完全不透明的硬件绘制全屏层，其压栈过程天然覆盖底层。
  在从抽屉点击设置时：
  ```tsx
  const openRootPage = useCallback(
    (href: string) => {
      if (searching) toggleSearch(false);
      // 先平滑压入原生栈
      router.push(href as '/settings');
      // 延后一帧在后台将抽屉静默重置，不在 push 动画启动的第 0 毫秒抢占主线程
      requestAnimationFrame(() => {
        actions.closeImmediate();
      });
    },
    [actions, searching, toggleSearch]
  );
  ```

#### 2. 原生 Modal 懒挂载（`useEverOpened` 机制）
- **代码位置**：`apps/crish-mobile/src/presentation/components/settings/SettingsScreenView.tsx`
- **改造方案**：引入 `useEverOpened` 钩子，只有当 `helpOpen` 或 `removeOpen` 首次为 `true` 时，才将 `<ConnectionHelpSheet>` 和 `<Dialog>` 挂入 JSX 树中。
  ```tsx
  const helpEverOpened = useEverOpened(helpOpen);
  const removeEverOpened = useEverOpened(removeOpen);

  return (
    <Screen ...>
      ...
      {helpEverOpened ? (
        <ConnectionHelpSheet
          visible={helpOpen}
          onClose={() => setHelpOpen(false)}
        />
      ) : null}
      {removeEverOpened ? (
        <Dialog
          visible={removeOpen}
          ...
        />
      ) : null}
    </Screen>
  );
  ```
  **收益**：日常进入和退出设置页时，原生 Native Modal 实例化开销**直接由 2 变为 0**！

#### 3. ASR 模型检查移出转场关键路径
- **改造前**：`useEffect` 中无保护调用 `asrModelManager().check()`。
- **改造后**：
  ```tsx
  useEffect(() => {
    if (!onOpenVoice) return;
    if (!voiceInputService.isAvailable()) {
      setVoiceSummary('不支持');
      return;
    }
    let alive = true;
    // 强制延后至转场完全结束后再进行文件 I/O
    const task = InteractionManager.runAfterInteractions(() => {
      void asrModelManager()
        .check()
        .then((state) => {
          if (!alive) return;
          setVoiceSummary(
            state.kind === 'ready'
              ? '已就绪'
              : state.kind === 'error'
                ? '下载失败'
                : '未下载'
          );
        });
    });
    return () => {
      alive = false;
      task.cancel();
    };
  }, [onOpenVoice]);
  ```

#### 4. 分帧挂载次级分组（Progressive Settings Groups）
设置页的“关于”、“退出当前账号”、“解除配对”等位于屏幕下方、首屏不可见区域的内容，通过 `InteractionManager` 稍后渲染，首帧仅渲染顶部账号卡与基础偏好设置，让入场转场零压力。

### 3.4 方案四：精准数据订阅与原生栈冻结（`enableFreeze`）

#### 1. 废除 `useSessionsVm` 的全量 `windows` 字典订阅
- **代码位置**：`apps/crish-mobile/src/adapters/viewmodels/useSessionsVm.ts`
- **痛点**：任何单会话的数据回填都会生成新的 `windows` 引用，击穿所有订阅者的 memo。
- **优化方案**：
  抽屉会话列表只需要最后一条预览文本，不需要全量事件流！
  在 `useSessionListVm` 中，将 `previewOf` 转换为按需读取（读取 `eventStore.getState().windows[id]` 快照），或者在 `sessionStore` 的 `SessionSummary` 中内联维持 `lastPreview` 纯字符串字段。
  彻底切断 `useEventStore((s) => s.windows)` 对 `useSessionsVm` 的全量连带反应！

#### 2. 全局启用 `react-native-screens` 原生冻结
- **代码位置**：`apps/crish-mobile/app/_layout.tsx`
- **优化方案**：
  ```tsx
  import { enableScreens, enableFreeze } from 'react-native-screens';

  enableScreens(true);
  enableFreeze(true);
  ```
  在 React 19 / RN 0.86 下开启 `enableFreeze(true)` 后：
  当用户进入 `/settings`，底层的 `(main)` 路由（包含 `HomeScreen`、`CrishDrawerLayout`、`CrishDrawerContent`）会自动进入 React Suspense Freeze 状态。此时无论后台接收到任何 WebSocket 事件或全局 store 变更，底层被覆盖的视图树**一律停止执行任何 React 渲染**，直到设置页退栈返回后才恢复。这从根本上终结了退栈时的幽灵计算争抢！

4. **会话切换两阶段加载断言**：
   - 切换到新 `sessionId` 时，前 350ms 内 `ensureSessionHistory` 未被触发；
   - `transitionSettled` 触发后，`ensureSessionHistory` 正好调用一次。
