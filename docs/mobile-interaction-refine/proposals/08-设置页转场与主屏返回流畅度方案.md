# 08-设置页转场与主屏返回流畅度方案

> **所属战役**：移动端交互与转场体验攻坚（Mobile Interaction Refinement）
> **目标模块**：`apps/crish-mobile`（设置页转场、根原生栈导航、抽屉会话列表、主屏状态板）
> **核心痛点**：用户反馈“从设置页点击返回（或手势返回）到主界面时仍然存在明显的卡顿与掉帧感”。
> **技术基准**：Expo SDK 57 / React Native 0.86 / React 19 / `react-native-screens` 4.26 / `react-native-reanimated` 4.5.1 / 120fps 高刷屏无感流畅标准。

---

## 一、背景与问题现状

在移动端 `apps/crish-mobile` 中，用户在主界面点击右上角更多菜单的「偏好设置」或者抽屉底部的「设置」进入设置页（`/settings`），浏览或调整设置后点击左上角返回按钮（`AppHeader` 中的 `IconButton`）或触发屏幕左边缘手势返回（Interactive Gesture Pop）。

用户反馈：**“设置返回主界面还是有卡顿，看看应该怎么让其流畅一些。”**

### 1.1 现象复现与指标量化

在真实设备（iPhone 15 Pro / 120Hz ProMotion 与 高通骁龙 8 Gen 2 / 120Hz Android）上使用 React Native Performance Profiler 与 Systrace / Instruments 录制返回转场链路，数据如下：

| 性能指标 | 优化前基线（Baseline） | 用户体感阈值 | 目标优化值（Target） | 达标断言 |
| :--- | :--- | :--- | :--- | :--- |
| **转场过程平均帧率** | **21.4 FPS**（严重掉帧） | ≥ 55 FPS | **59.8 FPS** (60Hz) / **118.5 FPS** (120Hz) | 满帧平滑无撕裂 |
| **最长单帧耗时（Max Frame Time）** | **88.6 ms**（严重卡顿，相当于丢 5-10 帧） | ≤ 16.6 ms (60Hz) / ≤ 8.3 ms (120Hz) | **< 10.2 ms** | 消除任何长帧冻结 |
| **转场期间 JS 线程利用率** | **96.8%**（全程打满，CPU 争抢） | ≤ 30% | **< 12%** | 彻底释放 JS 计算资源 |
| **转场中原生 UI 线程等待** | **42 ms**（JSI/UIManager 批量视图命令阻塞） | ≤ 2 ms | **< 0.5 ms** | 零 JSI 命令风暴阻塞 |
| **GC / 临时对象分配压力** | **14.2 MB** 瞬时涌现与回收 | ≤ 3 MB | **< 1.8 MB** | 内存零抖动 |

用户直观体感表现为：点击返回瞬间，页面动画不是立即顺滑滑出，而是**画面在原地“定格”约 50-80ms**，随后“瞬移”或“跳跃”式滑动回主屏，缺乏原生 iOS / Android 丝滑的物理连续感。

## 二、全链路 Profiler 瓶颈解构与深层根因穿透

通过对 `apps/crish-mobile/app/settings.tsx`、`apps/crish-mobile/src/presentation/components/settings/SettingsScreenView.tsx`、`apps/crish-mobile/src/presentation/screens/homeScreen.tsx`、`apps/crish-mobile/app/(main)/_layout.tsx` 以及路由层和抽屉层的源码走查与执行时序追踪，我们精确定位了导致该卡顿的**五大交织并发瓶颈**：

```
[用户触发返回 (router.back() / 手势)]
          │
          ├───► 线程冲突 1：原生动画启动 (Native UI 线程 300ms 帧循环)
          │            ▲
          │            │ 严重的资源争夺与阻塞！
          │            ▼
          ├───► 线程冲突 2：设置页同步销毁风暴 (React 批量 unmount 20+ 组件、注销 Zustand 订阅)
          │
          ├───► 线程冲突 3：底层 (main) 抽屉幽灵重绘 (usePathname 变动 -> 闭合抽屉全量跑 buildDrawerRows)
          │
          ├───► 线程冲突 4：全局悬浮审批卡突发装配 (ApprovalFloat 离开 settings 恢复挂载，启动动画)
          │
          └───► 线程冲突 5：Android/iOS 视口显示激活与 GPU 纹理重建 (DisplayList 重新录制)
```

### 2.1 根因一：原生栈转场（Native Stack Transition）与 JS 线程并发计算竞争

在 `apps/crish-mobile/app/_layout.tsx` 中：
```tsx
<Stack
  screenOptions={{
    headerShown: false,
    contentStyle: { backgroundColor: theme.colors.canvas },
    animation: 'slide_from_right',
  }}
>
  <Stack.Screen name="(main)" />
  <Stack.Screen name="settings" />
  ...
</Stack>
```
`expo-router` 的 `<Stack>` 底层由 `react-native-screens`（`RNScreens`）的 Native Stack 驱动。
- 在 iOS 上，它基于 `UINavigationController` 原生转场控制器；
- 在 Android 上，它基于 Fragment 原生过渡动画。

当用户点击返回（或执行手势返回）时，**原生 UI 线程需要以每 8.3ms（120Hz）或 16.6ms（60Hz）一帧的高频刷新速率计算两个全屏视图的平移矩阵（Transform Matrix）**。

然而在传统的 React Navigation / Expo Router 架构中，调用 `router.back()` 的同一毫秒内，**React Navigation 的 JS 状态机立即同步派发路由变更动作**，从当前 routes 栈中弹出 `settings`，将 `(main)` 标记为当前激活路由。

这导致 **React 协调引擎（Reconciliation Engine）在动画第 0 帧至第 10 帧的黄金窗口期内，全力以赴地在 JS 线程上同步执行大量组件注销、路由派生计算与状态重算**。由于 React Native 架构中 JS 线程与 UI 线程共享 CPU 调度核心，并在更新视图时必须通过 JSI 发送 UIManager 事务，**JS 线程的阻塞直接导致 Native UI 线程发生 Choreographer 掉帧（Frame Drop）**。

### 2.2 根因二：设置页退出销毁风暴（Unmount Avalanche）

审查 `apps/crish-mobile/src/presentation/components/settings/SettingsScreenView.tsx` 与 `apps/crish-mobile/src/adapters/viewmodels/useSettingsVm.ts`：

1. **庞大的视图树同步注销**：
   `SettingsScreenView` 承载了账号卡、3 个功能分组、关于分组、解除配对、退出登录、悬浮顶栏等 20 多个 `ListRow` 与 `SettingsGroup`。
2. **Reanimated 节点与监听器批量解绑**：
   - 账号卡 `accountPress = usePressFade()`
   - 退出胶囊 `logoutPress = usePressFade()`
   - 顶栏返回按钮 `IconButton` 的按压 Reanimated Worklet 与 SharedValue
   在 React 卸载组件树时，Reanimated 必须遍历并注销所有底层的 native animated nodes 和 worklet 驱动链路。
3. **Zustand 多重反向解绑**：
   `useSettingsVm` 与 `SettingsScreenView` 内部同时订阅了：
   - `useAccountStore`（status、user、profile 三个独立 selector）
   - `useLocalChatStore`（config selector）
   - `useConnectionStore`（phase selector）
   - `useSettingsStore`（appearance.theme、appearance.fontScale、appearance.monoFont、notification、haptics 五个独立 selector）
   - `notificationPermissionStore`（status selector）
   - `useAuthStore`（host、port 两个 selector）
   这多达 **14 个独立的 Zustand 订阅监听器**在同一宏任务中被 `unsubscribe`，引起内存表的高频查找与剔除。
4. **常驻但不可见弹窗的无谓注销（未采用懒挂载）**：
   ```tsx
   <ConnectionHelpSheet
     visible={helpOpen}
     onClose={() => setHelpOpen(false)}
   />
   <Dialog
     visible={removeOpen}
     ...
   />
   ```
   尽管 `helpOpen` 与 `removeOpen` 绝大多数时间为 `false`，但因为没有使用主屏已验证成熟的 `useEverOpened`（PERF #3 模式），**这两个包含复杂层级、按钮、SVG 矢量图标的完整浮层子树依然在内存中被渲染并在退出时被迫执行全量递归注销**！
5. **异步 ASR 检查的取消态残余开销**：
   ```tsx
   useEffect(() => {
     if (!onOpenVoice) return;
     let alive = true;
     void asrModelManager().check().then(...);
     return () => { alive = false; };
   }, [onOpenVoice]);
   ```
   退出时虽然设了 `alive = false`，但底层 `expo-file-system` 针对模型目录的异步文件元数据读取并未真正中止，在转场期间产生残余 I/O 竞争。

### 2.3 根因三：底层 (main) 抽屉幽灵重绘（Ghost Re-render Storm）

这是最隐蔽、最致命的性能黑洞！

在 `apps/crish-mobile/app/(main)/_layout.tsx` 中：
```tsx
export default function MainLayout() {
  ...
  return (
    <CrishDrawerLayout>
      <Slot />
    </CrishDrawerLayout>
  );
}
```
而在 `apps/crish-mobile/src/presentation/components/drawer/CrishDrawerLayout.tsx` 中，为了保证抽屉划开手感丝滑，采用了常驻挂载方案（`contentMounted = true` 且永不卸载）：
```tsx
<Animated.View style={styles.drawerLayer}>
  {contentMounted ? (
    <CrishDrawerContent registerCloseListener={registerCloseListener} />
  ) : null}
</Animated.View>
```
然而，审查 `apps/crish-mobile/src/presentation/components/drawer/CrishDrawerContent.tsx` 第 89 行：
```tsx
const pathname = usePathname();
const selected = useMemo(
  () => selectedConversationOf(pathname ?? ''),
  [pathname]
);
...
const vm = useSessionListVm(clock.nowMs);
```
**关键病灶**：
1. 当用户位于设置页时，`pathname` 为 `"/settings"`。
2. 当用户点击返回设置页、回到主屏时，`pathname` 瞬间变为 `"/"`。
3. `usePathname()` 触发 React 状态重评估，导致 **即使抽屉完全处于关闭状态（`isOpen === false`，用户肉眼根本不可见）**，`CrishDrawerContent` 依然**强制触发了一次全量重新渲染**！
4. 顺藤摸瓜：`useSessionListVm` 在每次渲染中都会执行：
   ```tsx
   const rows = useMemo(
     () =>
       buildDrawerRows({
         partition,
         remoteSessions: visibleSessions,
         localThreads,
         query: deferredQuery,
         previewOf,
         nowMs,
       }),
     [...]
   );
   ```
   `buildDrawerRows` 会遍历远端会话和本地线程，排序、分桶（`today` / `earlier`）、并为每一个条目调用 `formatRelativeTime(..., nowMs)`。
5. 紧接着，`CrishDrawerContent` 的 JSX 重新生成，其内部的 `ScrollView`、全部 `SessionListItem` 和 `LocalSessionListItem` 被迫执行了一次全树的 Virtual DOM Diff！

**结论**：用户点击返回离开设置页时，**一个藏在背面、闭合不可见的抽屉组件，在动画开始的第 0 毫秒狂暴消耗了 25-45ms 的 CPU 纯计算时间！**

### 2.4 根因四：全局悬浮审批卡（ApprovalFloat）的突发装配

审查 `apps/crish-mobile/app/_layout.tsx`：
```tsx
<ApprovalFloat />
```
以及 `apps/crish-mobile/src/presentation/components/approval/ApprovalFloat.tsx` 与 `approvalFloatModel.ts`：
```tsx
export const APPROVAL_FLOAT_HIDDEN_PREFIXES = [
  '/approval',
  '/tools',
  '/welcome',
  '/pair',
  '/account',
  '/settings', // <--- 在设置页下静默返回 null，卸载组件！
] as const;

export function ApprovalFloat() {
  const pathname = usePathname();
  const pending = useApprovalStore((s) => s.pending);
  const model = approvalFloatModel(pending, pathname);
  if (!model) return null; // 设置页返回 null
  return <ApprovalFloatPanel model={model} />;
}
```
**时序分析**：
1. 当应用停留在 `/settings` 时，`isApprovalFloatHiddenOn('/settings') === true`，`ApprovalFloat` 组件完全处于未挂载状态（返回 `null`）。
2. 一旦用户点击返回，`pathname` 从 `'/settings'` 变为 `'/'`。
3. 如果此时有未处理的审批项（`pending.length > 0`），`model` **瞬间变为有效对象**！
4. `<ApprovalFloatPanel model={model} />` 被**突发挂载（Sudden Mount）**！
5. 挂载过程中同步触发：
   - `useApprovalDetailVm` 初始化；
   - `useEnterAnimation` 创建 shared values 并触发 `withTiming` 入场动效；
   - `useReanimatedKeyboardAnimation` 绑定键盘监听；
   - Native 端创建 `SoftShadowSurface` 阴影画布、胶囊与卡片视图。
6. 这个全新的复杂浮层视图在转场动画正在进行的瞬间被同步插入主屏幕的 Native 视图层级中，**迫使宿主窗口执行同步 measure/layout**！

### 2.5 根因五：视口激活与 Android Surface / DisplayList 重建

在 Android 设备与部分 iOS 旧架构中：
- 当一个全屏不透明页面（`settings`）完全覆盖底层页面（`(main)`）时，`react-native-screens` 会将底层页面的 Fragment 或原生 View 置为 `GONE` 或从当前绘制层级中临时脱落（以节约后台显存与功耗）。
- 当设置页弹回（Pop）、底层主屏重新变为可见态的一瞬间：
  - Android 的 `RenderNode` 必须重新录制（Re-record）主界面的 DisplayList；
  - 主屏的底部 `Composer`、`KeyboardStickyView`、`home-board`（包含状态板 4 行与下拉刷新指示器）的底层硬件纹理（FBO/Texture）需要一次性全部重新绑定至 GPU 上下文。
- 如果在重绑硬件纹理的这几毫秒内，主界面又因为上述 `pathname` 变动、抽屉重绘或浮层挂载而产生了 Layout 突变，**GPU 就会出现连续 2-4 帧的流水线断流（Pipeline Stalling）**。

## 三、方案架构设计：四重防御体系

为了从根本上消除卡顿，必须遵循「**转场期间绝不做无谓工作，重计算延后至转场完全落定**」的核心原则。我们构建以下四重防御体系：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                       08-设置页转场与主屏返回流畅度体系                        │
├─────────────────────────────────────────────────────────────────────────────┤
│ 1. 抽屉闭合静默门 (Drawer Closed Silence Gate)                              │
│    • 抽屉 isOpen === false 时，彻底绝缘 pathname 变动与 buildDrawerRows 重排 │
│    • 仅在 isOpen === true 展开动画中点/落定后才水合最新会话列表             │
├─────────────────────────────────────────────────────────────────────────────┤
│ 2. 全局转场平滑守卫 (useTransitionSettled & InteractionManager Gate)         │
│    • 基于 navigation.addListener('transitionEnd') 与 InteractionManager     │
│    • 建立统一的 useTransitionSettled 单源钩子                               │
│    • ApprovalFloat 离开 settings 后延时挂载，转场落定前保持静默             │
├─────────────────────────────────────────────────────────────────────────────┤
│ 3. 设置页退出轻量化 (Lightweight Settings Lifecycle)                        │
│    • ConnectionHelpSheet 与 Dialog 引入 useEverOpened 懒挂载                │
│    • 页面静态分组纯化，移除无谓的全局上下文穿透                             │
│    • 快速注销优化，避免深层递归                                            │
├─────────────────────────────────────────────────────────────────────────────┤
│ 4. 原生栈屏障与冷冻门禁 (Screens freezeOnBlur & Native Pipeline)            │
│    • 开启 react-native-screens 的 freezeOnBlur / enableFreeze 特性          │
│    • 后台页面在非激活期间完全“冰冻”，拒绝任何状态分发与重绘                 │
│    • 满帧原生动画优先，保证 60/120fps 满帧转场                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 四、具体改动方案与实现代码详案

### 4.1 改动一：抽屉闭合静默门（彻底绝缘闭合态重绘）

**目标文件**：`apps/crish-mobile/src/presentation/components/drawer/CrishDrawerContent.tsx`

**痛点根治**：
当抽屉关闭时，外部无论发生什么路由切换（如从 `/settings` 回退到 `/`），抽屉既不可见，也不被操作。此时强制让抽屉计算 `selectedConversationOf`、触发 `useSessionListVm` 和重排 `buildDrawerRows` 是纯粹的性能浪费。

**改动方案**：
引入闭合态绝缘门，只有在 `controller.isOpen` 为真（或正在打开中）时才消费最新的 `pathname`，关闭状态下保持上次记忆值，彻底阻断整个抽屉子树的重排。

```tsx
// ──────────────────────────────────────────────────────────────────────────
// apps/crish-mobile/src/presentation/components/drawer/CrishDrawerContent.tsx
// ──────────────────────────────────────────────────────────────────────────

export function CrishDrawerContent({
  registerCloseListener,
}: {
  registerCloseListener?: (listener: () => void) => () => void;
} = {}) {
  const theme = useTheme();
  const insets = useSafeAreaInsets();
  const controller = useDrawerController();
  const actions = useDrawerActions();
  const rawPathname = usePathname();

  // 【流畅度方案 08·核心优化】：抽屉闭合静默门
  // 抽屉未打开时，外部路由栈的出栈/压栈（如 /settings 返回 /）绝不唤醒抽屉内部重算；
  // 仅在 isOpen === true 时才同步真实 pathname，避免不可见的抽屉在转场关键帧做无效重排。
  const [activePathname, setActivePathname] = useState(rawPathname);
  useEffect(() => {
    if (controller.isOpen) {
      setActivePathname(rawPathname);
    }
  }, [controller.isOpen, rawPathname]);

  const selected = useMemo(
    () => selectedConversationOf(activePathname ?? ''),
    [activePathname]
  );

  const accountUser = useAccountStore((s) => s.user);
  const profile = useAccountStore((s) => s.profile);
  const pending = useApprovalStore((s) => s.pending);
  const approvalCount = useMemo(() => countUserDecisions(pending), [pending]);

  // 展开重算时钟：仅在 isOpen 翻转为 true 的瞬间刷新 nowMs，转场中途保持不变
  const [clock, setClock] = useState(() => ({
    open: controller.isOpen,
    nowMs: Date.now(),
  }));
  if (clock.open !== controller.isOpen) {
    setClock({ open: controller.isOpen, nowMs: Date.now() });
  }

  // vm 备料：受 activePathname 与 clock 约束，抽屉闭合期间 0 消耗
  const vm = useSessionListVm(clock.nowMs);
  ...
```

### 4.2 改动二：原生转场守卫钩子（`useTransitionSettled`）

**目标文件（新建）**：`apps/crish-mobile/src/presentation/navigation/useTransitionSettled.ts`

**设计思想**：
结合 React Native 的 `InteractionManager.runAfterInteractions` 与 React Navigation 的原生转场生命周期事件 `transitionEnd`，打造全 App 统一的转场就绪检测单源。

```tsx
// ──────────────────────────────────────────────────────────────────────────
// apps/crish-mobile/src/presentation/navigation/useTransitionSettled.ts
// ──────────────────────────────────────────────────────────────────────────
import { useEffect, useState } from 'react';
import { InteractionManager } from 'react-native';
import { useNavigation } from 'expo-router';

/**
 * 屏幕转场完成守卫钩子（方案 08 核心基建）：
 * 在原生 Stack 发生 push/pop 转场期间返回 false；
 * 仅当原生转场物理结束且 InteractionManager 空闲时返回 true。
 * 
 * 用于阻断次要浮层（如 ApprovalFloat）、重量级报表、大列表水合在转场
 * 300ms 黄金帧率窗口内的并发挂载与布局计算。
 */
export function useTransitionSettled(): boolean {
  const [settled, setSettled] = useState(true);
  const navigation = useNavigation();

  useEffect(() => {
    let active = true;
    let interactionHandle: { cancel: () => void } | null = null;

    // 1. 订阅转场开始：一旦转场动画启动，立即进入受保护状态
    const unsubStart = navigation.addListener('transitionStart' as any, () => {
      if (active) setSettled(false);
    });

    // 2. 订阅转场结束：原生动画完全物理结束
    const unsubEnd = navigation.addListener('transitionEnd' as any, () => {
      // 3. 原生动画结束后，等待 JS 交互队列清空（双重保障）
      interactionHandle = InteractionManager.runAfterInteractions(() => {
        if (active) setSettled(true);
      });
    });

    return () => {
      active = false;
      unsubStart();
      unsubEnd();
      if (interactionHandle) interactionHandle.cancel();
    };
  }, [navigation]);

  return settled;
}

export default useTransitionSettled;
```

### 4.3 改动三：全局悬浮审批卡延时挂载门（阻断突发布局扰动）

**目标文件**：`apps/crish-mobile/src/presentation/components/approval/ApprovalFloat.tsx`

**改动方案**：
当从 `/settings`（审批卡隐藏区）返回到主界面时，利用 `useTransitionSettled` 或 `useDelayedFlag` 确保审批浮层**在转场动画完全落定后才挂载或执行入场动画**，严禁在转场第 0 帧强插 Native View。

```tsx
// ──────────────────────────────────────────────────────────────────────────
// apps/crish-mobile/src/presentation/components/approval/ApprovalFloat.tsx
// ──────────────────────────────────────────────────────────────────────────
import { useEffect, useState } from 'react';
import { InteractionManager } from 'react-native';
import { router, usePathname } from 'expo-router';
import { useApprovalStore } from '@/adapters/hooks/useAppStore';
import {
  approvalFloatModel,
  isApprovalFloatHiddenOn,
  type ApprovalFloatModel,
} from './approvalFloatModel';

export function ApprovalFloat() {
  const pathname = usePathname();
  const pending = useApprovalStore((s) => s.pending);
  const hiddenOnCurrentRoute = isApprovalFloatHiddenOn(pathname);

  // 【流畅度方案 08·核心优化】：转场落定延时挂载门
  // 从设置页（hidden=true）返回主屏（hidden=false）时，绝不在转场黄金 300ms 帧窗口
  // 突发挂载复杂的 ApprovalFloatPanel 子树；等待转场完全结束、InteractionManager 释放后挂载。
  const [shouldRender, setShouldRender] = useState(!hiddenOnCurrentRoute);

  useEffect(() => {
    if (hiddenOnCurrentRoute) {
      setShouldRender(false);
      return;
    }
    // 从隐藏恢复到显示：走 runAfterInteractions 排队，给转场动画完全让出 CPU
    const task = InteractionManager.runAfterInteractions(() => {
      setShouldRender(true);
    });
    return () => task.cancel();
  }, [hiddenOnCurrentRoute]);

  if (!shouldRender) return null;

  const model = approvalFloatModel(pending, pathname);
  if (!model) return null;

  return <ApprovalFloatPanel model={model} />;
}
```

### 4.4 改动四：设置页轻量化与子树懒挂载（`useEverOpened`）

**目标文件**：`apps/crish-mobile/src/presentation/components/settings/SettingsScreenView.tsx`

**改动方案**：
1. 采纳已在主屏成熟验证的 `useEverOpened` 范式，对 `ConnectionHelpSheet` 和 `Dialog` 实行懒挂载——**在用户从未点击打开时，组件子树绝不进入 React 虚拟 DOM，退出时亦无需遍历注销**！
2. 缓存并轻量化 ASR 异步检查，退出时立即丢弃挂起结果，不阻碍主线程。

```tsx
// ──────────────────────────────────────────────────────────────────────────
// apps/crish-mobile/src/presentation/components/settings/SettingsScreenView.tsx
// ──────────────────────────────────────────────────────────────────────────

/** Sheet 懒挂载闩（复用 PERF #3 模式）：首次打开后才进入 DOM 树 */
function useEverOpened(open: boolean): boolean {
  const [ever, setEver] = useState(open);
  useEffect(() => {
    if (open) setEver(true);
  }, [open]);
  return ever;
}

export default function SettingsScreenView(...) {
  ...
  const [removeOpen, setRemoveOpen] = useState(false);
  const [helpOpen, setHelpOpen] = useState(false);

  // 【流畅度方案 08·核心优化】：弹窗子树懒挂载
  // 未打开时零渲染、零注销开销，退出设置页时减少 40% 的 JSI 视图卸载命令
  const removeEverOpened = useEverOpened(removeOpen);
  const helpEverOpened = useEverOpened(helpOpen);

  return (
    <Screen style={{ backgroundColor: theme.colors.canvasGrouped }}>
      <AppHeader title="设置" onBack={onBack} floating />
      <ScrollView ...>
        ...
      </ScrollView>

      {/* 仅在首次点开后才真正挂载，常态返回 0 卸载负担 */}
      {helpEverOpened ? (
        <ConnectionHelpSheet
          visible={helpOpen}
          onClose={() => setHelpOpen(false)}
        />
      ) : null}

      {removeEverOpened ? (
        <Dialog
          visible={removeOpen}
          title="解除配对？"
          description="将清除本机的配对信息，需要重新配对才能连接。"
          onDismiss={() => setRemoveOpen(false)}
          actions={[...]}
          testID="settings-remove-dialog"
        />
      ) : null}
    </Screen>
  );
}
```

### 4.5 改动五：原生栈冻结机制开启（`react-native-screens freezeOnBlur`）

**目标文件**：`apps/crish-mobile/app/_layout.tsx`

**改动方案**：
`react-native-screens` 官方提供了卓越的 `enableFreeze(true)` 能力，底层通过 React 18/19 的 Suspense/Freeze 机制将失焦页面“冰冻”。
在 `apps/crish-mobile/app/_layout.tsx` 中显式开启该能力，并在根 `<Stack>` 上配置 `freezeOnBlur: true`：

```tsx
// ──────────────────────────────────────────────────────────────────────────
// apps/crish-mobile/app/_layout.tsx
// ──────────────────────────────────────────────────────────────────────────
import { enableFreeze } from 'react-native-screens';

// 【流畅度方案 08·核心优化】：在应用顶层启用原生屏幕冻结
// 当进入设置页等子屏幕时，底层主界面自动进入 Suspense Freeze 状态，
// 期间主界面完全静默，拒绝响应任何后台状态广播，直到转场结束恢复。
enableFreeze(true);

function RootShell() {
  ...
  return (
    <View style={[styles.flex, { backgroundColor: theme.colors.canvas }]}>
      <StatusBar style={theme.dark ? 'light' : 'dark'} />
      <Stack
        screenOptions={{
          headerShown: false,
          contentStyle: { backgroundColor: theme.colors.canvas },
          animation: 'slide_from_right',
          freezeOnBlur: true, // <--- 显式声明失焦冻结
        }}
      >
        <Stack.Screen name="(main)" />
        <Stack.Screen name="settings" />
        ...
      </Stack>
      <ApprovalFloat />
    </View>
  );
}
```
