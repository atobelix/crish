# 内置工具权限与沙箱

> 日期：2026-10-13
> 范围：`agent-tools` 内置工具、权限、执行器、中间件、备份、幂等、写路径、回滚守卫，以及 `conex-sandbox`。
> 安全基线（`docs/rust-rewrite/31-security-baseline.md` B1/B2/B4）只作线索；结论以当前代码为准。
> 不评 MCP、笔记存储、后台任务管理器、session-loop 批调度本身。批调用只在「它让下面的互斥失效」时引用一处。

## 能力结论

文件类工具（读/写/替换/删除）会把路径 canonicalize 后按工作区成分边界卡住，单文件删除的校验和失败发生在移走之前。命令红线若被语义层标成 `Redline`，任何权限模式（含 full-access）都拒绝。生产 run 会把写路径注册表和路由审计 sink 注入工具上下文。

这些没有守住工具自己宣称的事：PowerShell 编码命令的常用缩写、解释器 `-c`/`-e` 的非 shell 载荷、以及 `Push-Location` 一类 cd，都不会被标成红线或 cd，门禁因此放行；放行后的 shell 子进程不受工作区根约束。写路径注册表按 run 各建一份，且同一 run 的并行调用共用一个持有者，并行写同一文件不会冲突。commit 任务类型的 git 命令白名单没有接到执行链。full-access 下 shell 删除形态不进回收站。幂等守卫默认关闭，打开也只活在进程内存里。

## 问题清单

### BC10-1 编码命令缩写不解码，红线载荷被放行

- 现象：`powershell -ec <base64>`、`pwsh -en <base64>`（以及 `/ec`、`-ec:payload` 这类）不会被当成 EncodedCommand。内层命令不解码。整段按普通命令放行后，外壳仍会执行这段真正的编码命令。full-access 不审批；ask 只把整段当危险工具问一次，审批人看到的是看不懂的 base64，不是红线原文。plan 仍拒绝全部 shell，不受本条影响。
- 证据：`crates/conex-sandbox/src/semantics.rs:567-583`（`is_ps_encoded_command_flag`）；同文件 `643-650`、`989-997`（仅当该函数为真才升 Redline）；`1137-1145`（抽不出内层则空分析、分类 Normal）；`1205-1223`（内层没有段就不当 Indirect，继续往下掉到 Normal）；`2085-2103`（测试钉住 `-e`/`-enc`/`-enco`，没有 `-ec`/`-en`）。门禁对 Normal 返回 Allowed：`crates/conex-sandbox/src/lib.rs:122-143`。工具层把 `dangerous` 写死为 false，只在门禁结果是 `RequiresApproval` 时才问：`crates/agent-tools/src/tools/shell.rs:303-311`。
- 机制：函数先要求旗标是 `"encodedcommand"` 的前缀，再额外要求旗标等于 `"e"` 或以 `"enc"` 开头。`"ec"`、`"en"` 是 `"encodedcommand"` 的前缀，但两段附加条件都不成立，函数返回 false。Windows PowerShell 参数绑定里 `-ec` 是 `-EncodedCommand` 的文档短名（`-ex` 才是 `-ExecutionPolicy`），`-en` 同样唯一指向编码命令。抽不出 `-c`/`-Command` 内层后，`powershell` 虽在间接命令表里，分类落到 Normal，静态红线正则也不扫 base64。判定之后外壳才用自己的 `-EncodedCommand` 包装用户原文（`crates/agent-tools/src/tools/shell_invoke.rs:12-29`、`64-78`），包装发生在门禁之后，补不回这次漏判。
- 影响：full-access 下红线不可豁免这条不成立。编码载荷里的 `rm -rf /`、删盘、再起一个 shell，都以普通命令执行。ask 下审批看不到明文，拦红线的作用失效。

### BC10-2 解释器 `-c` / `-e` 的非 shell 载荷被放行

- 现象：`python -c "import os; os.system('rm -rf /')"`、`node -e "..."` 一类不会升成红线。python 的 `-c` 被抽出来再当 shell 语句分析，Python 源码对不上 `rm`，外层只标 Indirect，门禁仍 Allowed。`node -e`（node 真正执行代码的开关）根本不抽取。
- 证据：间接命令表含 `python`/`python3`/`node`/`cmd`/`bash`：`crates/conex-sandbox/src/semantics.rs:61-83`。抽取只认 `-c`/`-Command`/`/c`，注释写明 `-e` 已移出：同文件 `989-1024`。内层不是红线/危险/删除、但有段时，外层固定 Indirect：`1205-1221`。门禁只在「整体是 Indirect 且 `delete_targets` 非空」时才升级审批：`crates/conex-sandbox/src/lib.rs:122-131`。shell 再次把 `dangerous` 传 false：`crates/agent-tools/src/tools/shell.rs:305-311`。
- 机制：设计是把解释器 `-c` 的内层递归当 shell 看。内层语言不是 shell 时，递归既看不到删除目标，也不会因为「这是任意代码」而升 Dangerous。`node -e`、以及不在间接表里的 `ruby -e`/`perl -e`/`php -r`，连递归都没有，直接 Normal。Indirect 且没有删除目标在门禁里与 Normal 一样是 Allowed。
- 影响：与 BC10-1 相同的豁免洞，只是载荷是源码而不是 base64。full-access 直接跑；ask 的审批依据是看不懂或未展开的内层，红线拒绝不会自动发生。工作区外的写、删、再起进程都从这条缝出去。

### BC10-3 cd 家族拦不住，初始工作目录可以被改掉

- 现象：纯 `cd` / `Set-Location` / `sl` / `pushd` / `popd` 会拦。`Push-Location`、`Pop-Location` 不拦。包在 `cmd /c`、`powershell -Command` 里的 `cd` 也不拦。`git -C <工作区外>`、`powershell -WorkingDirectory <工作区外>` 不拦。
- 证据：名单只有五个名字：`crates/conex-sandbox/src/semantics.rs:88-92`。命中条件是段首命令名恰好在名单里：`1231-1236`。注释写了 Push-Location / Pop-Location 是别名，名单里却没有这两个命令名。内层即使是 CdShape，外层只在红线/危险/删除时升级，其余非空内层一律 Indirect：`1205-1221`。拦截器只看最外层重建段的整体分类是否仍为 CdShape：`crates/agent-tools/src/tools/shell_redirect.rs:367-386`。调用点在删除重定向之后：`crates/agent-tools/src/tools/shell.rs:294-297`。
- 机制：实际执行宿主是 PowerShell（`shell_invoke.rs:15-29`），用户脚本经 `[scriptblock]::Create` 跑在同一个 powershell 进程里。`Push-Location` 是这个宿主的正式 cmdlet，不在名单里，分类 Normal，门禁 Allowed，然后改变本进程后续命令的当前目录。`cmd /c "cd /d D:\ & ..."` 的外层命令名是 `cmd`，内层 cd 不会把外层改成 CdShape，`intercept_cd_shape` 直接返回。语义层自己写明 `git -C` 不算 cd（`semantics.rs:1234`）。
- 影响：禁 cd 的目的是强迫使用工具的 `cwd` 参数（该参数走工作区包含性校验）。漏网形态让同一次命令的后半段在工作区外的相对路径上读、写、删。见 BC10-4。

### BC10-4 放行后的 shell 可以读写工作区外的绝对路径

- 现象：`read_file` / `write_file` / `delete_*` 的路径参数出不了工作区。`shell_command` 只校验参数 `cwd` 必须在工作区内。命令正文里的绝对路径不经这套校验。
- 证据：文件工具入口 `resolve_workspace_path`：`crates/agent-tools/src/tools/mod.rs:341-404`（拒 `..`、canonicalize、`is_subpath`、再查 symlink 链）。shell 子进程只设 `current_dir(cwd)`：`crates/agent-tools/src/tools/shell_exec.rs:52-55`。门禁的工作区比较也只看 cwd，且仅把「cwd 已在界外且其余 Allowed」升级为审批：`crates/conex-sandbox/src/lib.rs:186-193`。删除重定向的「工作区外一律拒绝」只覆盖被认成删除形态的目标：`crates/agent-tools/src/tools/shell_redirect.rs:113-127`。
- 机制：没有进程级文件系统沙箱（基线也不要求 Seatbelt/Seccomp）。工作区约束全靠命令分类加 cwd 校验。BC10-1 到 BC10-3 放行的命令，以及本来就 Allowed 的 `Get-Content C:\...\id_rsa`、`Set-Content` 绝对路径，都在子进程里按操作系统权限执行。另外，文件工具的 symlink 复查在 `strip_prefix` 失败时返回 false（当成没逃逸）：`crates/agent-tools/src/tools/mod.rs:416-418`。调用方先用大小写不敏感的 `is_subpath` 放过之后才进这个函数。推断：规范化大小写不一致时，symlink/junction 复查被跳过；两条路径都被 canonicalize 时通常一致，这是失败开的分支，不是已经复现的样本。
- 影响：模型用 shell 读或写工作区外文件，不需要先逃出 `resolve_workspace_path`。cd 漏网时相对路径同样出界。

### BC10-5 写路径互斥挡不住并行写同一文件

- 现象：生产会注入 `WritePathRegistry`，不是完全没接线。但同一工作区上同时进行的写入仍然互斥不住：不同 run（主 run 与子代理 run、两个子代理）各持一份注册表；同一个 run 里并行的写/删共用一个持有者，同持有者不算冲突，先结束的调用还会把这个持有者的全部声明清掉。
- 证据：同持有者跳过冲突：`crates/agent-tools/src/write_paths_state.rs:200-203`。守卫 Drop 按持有者整表删除：同文件 `111-114`。未注入才不强制：`293-300`（生产主路径不是这条）。生产每个 run `WritePathRegistry::new`：`apps/agent-workbench/src-tauri/src/run/run_launch.rs:737`。子代理在有白名单或 `implementation` 时再 `new` 一份，不接父表：同文件 `791-809`。装配进循环的是这份 per-run 表：`917-919`。执行上下文的持有者是整个 run id，不是单次工具调用：`crates/session-loop/src/exec_single.rs:419`。回合里助手消息的工具调用被标成 Parallel：`crates/session-loop/src/loop/handlers/executing_tools.rs:90`（批调度细节不在本路展开）。默认声明 TTL 60 秒且执行中不续期：`crates/agent-tools/src/write_paths_state.rs:27-28`、`193-195`。
- 机制：互斥键是「注册表实例 + 持有者」。生产实例按 run 隔离，持有者按 run 合并。并行的两次 `write_file`/`multi_replace`/`delete_*` 看到的是同一个 holder，第二笔声明被当成续期。先返回的守卫 `release_holder` 会把还在写的那笔声明一起删掉，第三笔可以插进来。子代理与父 run 根本看不到对方的声明。主 run 的表也没有装 `WritePathPolicy`（`run_launch.rs:737` 对比 `803-805`），越权白名单对主 run 不生效：`write_paths_state.rs:316-326`。
- 影响：同一回合并行写同一文件会交错覆盖。父代理与 implementation 子代理可以同时改同一路径。60 秒以上的写在共享同一张表时还会被 TTL 提前放行；当前跨 run 不共享表，TTL 是次要缝。

### BC10-6 任务类型命令白名单没有接到执行

- 现象：`commit` 子代理的工具面只有 `shell_command`，文档要求命令首词必须是 `git`。`implementation` 文档要求命令必须是门禁 Allowed 的普通命令。这两条在执行时都不跑。只读任务类型（`analysis` / `organization` / 未知）靠工具白名单，没有 shell，不受本条影响。
- 证据：函数自述不参与每条命令的放行，唯一判定链是 `decide_command_with_revert`：`crates/agent-tools/src/readonly.rs:149-165`。git 前缀与 implementation 的 `CommandClass::Normal` 只写在这个函数里：`165-188`。全仓调用点只有本文件测试（`readonly.rs` 测试模块）。子代理装配只裁工具名：`apps/agent-workbench/src-tauri/src/run/run_launch.rs:591-607`。shell `prepare` 不读 task_type。
- 机制：工具集裁剪是真的（commit 拿不到 `write_file`）。命令策略是另一层，没有挂进 `prepare` 或执行器的 `call_verdict`。commit 代理因此可以跑任何被 BC10-1/2/3 放行的命令，包括写文件、解释器、`Push-Location`。`design`/`review` 按名单本来就有 `write_file`（`readonly.rs:137-139`），那是声明过的写权限，不算本条。
- 影响：commit 不是「只能 git」。它用 shell 写工作区或工作区外，任务类型边界失效。implementation 的「非普通命令默认拒绝」同样只存在于未被调用的函数。

### BC10-7 full-access 的 shell 删除不进回收站

- 现象：`delete_file` / `delete_dir` 无论权限模式都进回收站。`shell_command` 在 full-access 下遇到删除形态不再重定向，交给外壳真删。没有快照、没有 entryId。
- 证据：跳过条件：`crates/agent-tools/src/tools/shell.rs:275-292`（`permission_mode != FullAccess` 才重定向）。非 full-access 的重定向调用 `trash_file(..., true)`：`crates/agent-tools/src/tools/shell_redirect.rs:167`。删除工具始终 `trash_file`：`crates/agent-tools/src/tools/delete.rs:225-228`。full-access 的审批通道是直接放行的 `NoopAskChannel`：`crates/session-loop/src/exec_single.rs:394-395`。
- 机制：工具头注释写删除形态改走回收站（`shell.rs:6-9`），实现把 full-access 排除在外。full-access 的 `decide` 对非红线危险操作本来就 Allow（`permission.rs:84-91`），再叠加 Noop 询问，删除命令不会停在审批，也不会停在 trash。`Remove-Item` / `del` / `rm` 若被标成 DeleteShape，在这条模式下是物理删除。
- 影响：同一产品里「删除可恢复」只对删除工具和非 full-access 的 shell 成立。full-access 是壳层显式模式（`run_launch.rs:673-674` 关闭审批），该模式下 shell 删除没有备份可恢复。这不是「备份函数返回错误后仍继续」——单目标校验和失败会在移动前返回，见下文闭合项。

### BC10-8 幂等记录不跨进程，重启后同样的写和命令会再做一遍

- 现象：幂等守卫能在同一进程、同一守卫实例里按参数去重。生产默认不打开。打开时用的也是无持久化存储的内存守卫，进程退出或新循环构造后键就没了。已成功的写、删、shell 在重试或新 run 里会再执行。
- 证据：模块写明默认内存、跨进程应接 store：`crates/agent-tools/src/idempotency.rs:10-12`、`128-142`（`new` 的 `store: None`，`with_store` 无人在生产调用）。默认开关关闭：`crates/session-loop/src/loop/loop_options.rs:107`。唯一生产构造是 `ToolIdempotencyGuard::new()`：`crates/session-loop/src/loop/loop_runner.rs:199-201`。执行器只在开关与守卫都在时去重：`crates/agent-tools/src/executor_run.rs:41-42`。全仓 `idempotency_enabled = true` 只出现在 session-loop 测试。
- 机制：`with_options` 在开关为真时新建一份内存守卫，不读 `conex-db`，也不跨 run 共享。守卫随循环实例消亡。失败路径会 `forget` 以便重试，这是对的；成功路径的键无法在进程重启后被下一次 `check_and_record` 看见。
- 影响：崩溃、重启、新 run 之后，相同参数的 `write_file`、删除、shell 再执行一次。去重只在「同一次进程里打开了开关并且复用了同一个守卫」时成立，生产两条都不满足。

## 已核对闭合或不是问题

- 语义层标成 `Redline` 的命令，`decide_with_redline` / `decide_analysis_with_revert` 在 ask、plan、full-access 都 Deny（`crates/agent-tools/src/permission.rs:102-110`、`161-164`）。门禁对段或整体 Redline 返回 Blocked（`crates/conex-sandbox/src/lib.rs:104-111`）。shell 在 Blocked 时直接 `tool.command_blocked`（`shell.rs:249-263`）。经典「正则没看见 `rm -rf -- /`」这条，若当前语义层仍把它标成 Redline，不会从权限模式漏出去。本路没有重跑 sandbox 测试，不把测试全绿写成事实。
- 文件路径：`resolve_workspace_path` 拒空串、控制字符、任何 `..` 成分、canonicalize 失败，并用 `is_subpath` 做成分边界（不是裸 `starts_with`）。父级 symlink 指向区外时，canonicalize 会落到区外再被包含性检查拒绝（`conex-fs` 的 `safe_canonicalize` 与 `mod.rs:381-402`）。这不覆盖 shell 正文，见 BC10-4。
- 单目标删除的备份失败不会先删后报错。`trash_file` 在 `backup=true` 时先算校验和，`?` 失败发生在 `atomic_move` 之前（`crates/conex-fs/src/trash.rs:212-232`）。写前 `BackupMiddleware` 快照失败返回 Block，不放行修改（`crates/agent-tools/src/backup.rs:164-180`）。多目标 shell 重定向是另一行为：前面的目标已经进回收站，后面的目标失败就返回，不回滚已成功的条目（`shell_redirect.rs:151-180`）。失败的那一个不会被继续删掉。
- plan 模式：执行器按工具 `dangerous` 拒绝写和 shell；shell `prepare` 再次拒绝全部命令（`shell.rs:266-272`）。`write_file` 自身不读 `permission_mode`，生产路径靠执行器判权。只读任务类型的工具白名单不含 `write_file` / `shell_command` / 笔记写工具（`readonly.rs:52-66`）。
- `decompress_context` 虽在只读白名单且 `dangerous=false`，落文件条件是 `write_claim_holder == None`（`decompress_context.rs:116-118`）。生产执行上下文把持有者设成 `Some(run_id)`（`exec_single.rs:419`），主代理和子代理都不会走落文件。这是落文件能力没接上，不是只读模式偷偷写盘。
- 权限 Noop 不是 ask 的默认放行。`NoopAskChannel` 只在显式 full-access 注入（`exec_single.rs:394-395`）。shell 在需要审批且 `ctx.ask` 为 None 时返回 `tool.requires_approval`，不执行（`shell.rs:319-335`）。`context.rs:126`「None 按放行兜底」与 shell 实现不一致，生产 ask 走的是审批门，不是这条注释。
- 审计：工作台构造时把 `RoutingAuditSink` 注入 `BuiltinToolConfig`（`apps/agent-workbench/src-tauri/src/engine_build.rs:301-345`）。run 启动注册桥并起落库 worker（`run_launch.rs:727-768`）。`NoopAuditSink` 只在配置没注入时使用（`crates/agent-tools/src/tools/mod.rs:184-186`）。无路由时 `RoutingAuditSink` 只打 `tracing::debug` 并丢掉事件（`engine_audit.rs:160-169`），正常 run 在工具执行前已经注册，门禁不依赖 sink 才拒绝。因此不把「默认丢弃」记成现存的追责或门禁失效。未注册窗口上的事件仍然不可回放，那是收口时序，不是工具门禁被关掉。

## 给主控的摘要

1. 编码命令：`-ec`/`-en` 不在 `is_ps_encoded_command_flag` 里，不解码，full-access 当普通命令执行，红线豁免失效（BC10-1）。
2. 解释器：`python -c` 的非 shell 内层只标 Indirect，门禁仍 Allowed；`node -e` 不抽取（BC10-2）。
3. cd：`Push-Location`/`Pop-Location` 和包在 `cmd /c` 里的 cd 拦不住，同进程后续相对路径出工作区（BC10-3）。
4. shell 只约束 cwd，命令里的绝对路径可读写工作区外；文件工具的路径校验管不到（BC10-4）。
5. 写互斥已注入，但是每 run 一张表、持有者是 run id、同持有者不冲突，并行写同一文件不拒绝（BC10-5）。
6. `command_allowed_for_task_type` 没有接到执行；commit 子代理只有 shell，却能跑非 git 命令（BC10-6）。
7. full-access 的 shell 删除形态不进回收站，直接物理删除（BC10-7）。
8. 幂等默认关，打开也是内存 `new()`，重启后写/删/shell 会再执行（BC10-8）。
9. 已闭合：Redline 不可被模式豁免；单目标校验和失败在移动前返回；plan 与只读工具白名单；Noop 不是 ask 默认；生产审计 sink 有落库，不单列丢弃。
10. 未跑测试。symlink 复查在 `strip_prefix` 失败时失败开，只记为推断。
