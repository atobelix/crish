# 供应商解析重试与目录

> 日期：2026-10-13
> 范围：`crates/agent-provider/src/parse/` 全部，以及 `error.rs`、`error_classify.rs`、`retry.rs`、`retry_decision.rs`、`retry_stream.rs`、`models/`、`model_store.rs`、`model_store_import.rs`、`credentials.rs`、`pricing.rs`、`migration.rs`。当前代码为准。
> 请求体怎么拼、SSE 怎么切帧，归 08。会话层怎么消费 Stop、怎么跑阶梯，归 02。下文引用这两侧，只说明本范围的分类和解析会被哪条生产路径接住。

## 能力结论

四家解析器都能把「标准位置上的工具调用」收成 `ToolCall`：Chat 的 `tool_calls` / `function_call`、Anthropic 的 `tool_use` + `input_json_delta`、Gemini 的单独 `functionCall` part、Responses 的 `function_call` 按 `call_id` 去重。思考标签只剥 `<think>` / `<thought>` / `<thinking>`。凭证解析是失败关闭的：密钥缺失或读失败不会组装出可发送的配置。目录查找是精确身份，版本后缀和 `*` 厂商默认窗口已经去掉。迁移对同一字段冲突会拒绝，不在请求期猜厂商。

闭环上仍有几处会让「选中的模型」叫错，或让一次工具意图变成正文、空参数调用、截断参数调用。供应商自己的 `provider_stream` 重试循环不在生产路径上，也明确不重放鉴权、配额和上下文超限。会把请求再发出去的是会话层：它只相信 `classify_provider_error` 给出的 kind。kind 判宽，同一份输入就会被加码重发，然后进入压缩。

## 问题清单

### BC09-1 「too long」先于 5xx 和超时命中，非超限失败被送进长度阶梯

- 现象：HTTP 失败体里只要出现连续的 `too long`，分类就是 `ContextLengthExceeded`。504「took too long」、500「response too long」、400「parameter too long」和真正的「prompt is too long」「maximum context length」走同一条恢复。会话层先把 `max_tokens` 翻倍再发同一份输入，最多两次，然后才压缩。
- 证据：`crates/agent-provider/src/error_classify.rs:14-18`，`too long` 与 `maximum context`、`context_length_exceeded`、按序的 `context`+`length`+`exceed` 并列。`crates/agent-provider/src/error.rs:233-236` 在 400/422 上直接采用这个检测。`error.rs:276-277` 在无早期状态分支时再次采用，位置在鉴权（279）、限流（285）和 `is_server_status`（301-302）之前。超时字样在 `error_classify.rs:278-282`，排在服务端状态之后。生产非 2xx 把状态码和正文一起送进这个函数：`apps/agent-workbench/src-tauri/src/engine_provider.rs:524-539`。
- 机制：早期状态分支只覆盖 413、质询、401/403、402、404/405/415、400/422、429。500/502/503/504 要等消息模式走完才落到 `Server`。`too long` 因此抢走本应是 `Server` 或 `Timeout` 或 `InvalidRequest` 的失败。`ProviderError::is_retryable`（`error.rs:168-170`）对 `ContextLengthExceeded` 为真，因为 `conex-types` `error.rs:1641-1648` 把这类放进默认可重试矩阵。本模块的 `should_retry` 并不重放它（`retry_decision.rs:110-119`、`194-200`）。接住 kind 的是会话层 `stream_error.rs:70-80`：`ContextLengthExceeded` 进 `length_ladder`。`stream_error_recover.rs:40-76` 在压缩前执行 `max_tokens` 饱和翻倍并 `NoProgressContinue`。同文件 77-79 行的注释写明，放大输出预算解决不了输入超限。
- 影响：真超限会先把同一份超限输入再打出去两次，然后才压缩历史。假超限（网关耗时、字段过长）不走瞬态退避，反而改输出预算并可能改写对话。流已经进入解析器、且没有任何正文的错误 Stop，kind 会被消费层改写成 `Unknown` 并不再进这条阶梯（`crates/session-loop/src/stream.rs:427-432`、`606-611`）。放大发生在流前 HTTP 失败，不发生在那条被折叠的流内错误上。

### BC09-2 鉴权正文对不上四条短语时，5xx 被当成可重试的服务端错误

- 现象：状态码已经是 401 或 403 时，分类固定为 `Auth`，不会重试。状态码是 5xx，正文却是鉴权失败时，只要没撞上四条短语，分类就是 `Server`，会话层按瞬态错误重放整次请求。
- 证据：短语表在 `crates/agent-provider/src/error_classify.rs:34-42`，只有 `unauthorized`、`forbidden`、`invalid api key`、`invalid authentication`。`error.rs:221-223` 让 401/403 在消息模式之前返回。`error.rs:279-280` 的鉴权消息检测在 `error.rs:301-302` 的 5xx 判定之前；短语没命中就落到 `Server`。`is_transient_kind` 包含 `ServerError`（`retry_decision.rs:112-119`）。会话层对这个 kind 调用 `transient_retry`（`crates/session-loop/src/loop/handlers/stream_error.rs:73-76`）。
- 机制：OpenAI 常见文案 `Incorrect API key provided` 小写后是 `incorrect api key`，不含 `invalid api key`。下划线形式 `invalid_api_key` 也不含带空格的 `invalid api key`。Anthropic 错误帧拼出来的 `authentication_error: invalid x-api-key`（`parse/anthropic_map.rs:105-109`）不含 `invalid authentication`，也不含 `invalid api key`。这些字符串在状态码 500–599 上穿过鉴权检测，被 `is_server_status` 收成可重试。状态码缺失时它们会落到 `Unknown`（不可重试）；流内空内容错误还会再被消费层收成 `Unknown`。429 在 `error.rs:244-253` 于消息模式之前返回 `RateLimit`，正文里的鉴权短语同样不会被看到。
- 影响：网关把鉴权失败包成 5xx 时，同一请求带着同一把无效密钥按退避重发，直到重试次数或 60 秒预算用尽。这不是密钥读失败后的空密钥请求；空密钥在目录层就被拒绝，见文末已核对。重放本身不执行工具，因为失败发生在流前、还没有工具事件。

### BC09-3 Anthropic 增量只要带字符串 text，工具参数就不再追加

- 现象：`content_block_delta` 的 `delta.text` 只要是字符串，就先产出 `TextDelta`，不再进入 `input_json_delta`。工具参数片段出现在正文里；`content_block_stop` 仍可能按已注册的名字发出一次工具调用，参数是此前攒下的前缀，前缀为空则是 `{}`。
- 证据：`crates/agent-provider/src/parse/anthropic_core.rs:169-176` 的条件是 `delta_type == "text_delta"` 或 `delta.text` 为字符串，两者满足其一就返回，后面的 `input_json_delta` 分支在 197-205 行。注册块只认 `type == "tool_use"`（148 行）。有名字就在 211-218 行发出 `ToolCall`，参数来自 `parse_arguments`。
- 机制：官方 `input_json_delta` 只带 `partial_json`，不带 `text`，不会踩中这个或条件。或条件不看 `type`。代理或兼容实现若在同一 delta 上同时给出 `type: input_json_delta` 和字符串 `text`，`partial_json` 被跳过，`text` 进入助手正文。空参数经 `parse/tool_call.rs:187-189` 变成空对象，仍然是一次工具调用。
- 影响：用户看到本应属于工具参数的文本。若名字已经在 `content_block_start` 注册，工具照样执行一次，入参是截断或空对象。这不是重试打出的第二遍。

### BC09-4 Gemini 同一 part 有非空正文就丢掉 functionCall

- 现象：一个 part 同时有非空 `text` 和 `functionCall` / `function_call` 时，只产出正文，函数调用被 `continue` 跳过。工具不会执行，调用内容留在助手文本里。
- 证据：`crates/agent-provider/src/parse/gemini_core.rs:167-172` 对非空 `text` 提取后 `continue`。`functionCall` 的读取在 174-203 行，排在这次 `continue` 之后。缺名字的调用在 181-182 行丢弃。
- 机制：官方 Part 是互斥字段，正常分片不会同时带正文和函数调用。解析器没有「同一 part 两种都要」的分支，也没有跨帧按 id 去重。兼容层若把文本和 `functionCall` 合并进同一个 part，函数调用整段消失。`MALFORMED_FUNCTION_CALL` 作为 finishReason 会收成错误终态（`gemini_map.rs:44-56`），那是另一条路：没有 part 里的函数调用时，回合失败，不会把畸形调用补成工具或正文。
- 影响：本应执行的工具变成一段助手正文，回合按普通文本结束。多个 candidate 里各自出现的函数调用会各发一次 `ToolCall`（141-142 行起遍历全部 candidates），官方默认单 candidate，本文不把「候选被重放」写成已发生的双调用。

### BC09-5 Chat 工具增量缺 index 时拆成另一槽，截断参数仍会发出

- 现象：带 `index` 的后续参数片段会拼回同一调用。不带 `index` 的片段用当前槽位数当新下标。同一调用的后半段进新槽：新槽没有名字就只留诊断，已命名的前半段带着截断 JSON 发出；后半段若再次带上名字，就会变成第二次同名工具调用。
- 证据：`crates/agent-provider/src/parse/tool_call.rs:93-98`，`index` 缺失时 `unwrap_or_else(|| self.pending.len())`。参数追加在 120-122 行。`finish` 在 147-159 行对有名字的槽发出 `ToolCall`。解析失败的入参是 `{__rawArguments, __parseError}`（`tool_call.rs:187-197`），仍然随调用发出。`missing_index_falls_back_to_pending_len`（272-279 行）只锁定两条各自带 id 和名字、没有参数分片的调用。
- 机制：第一条无 index 增量占用下标 0 并写下名字和参数前缀。下一条仍无 index 时 `pending.len()` 已是 1，写入新槽。官方流式工具调用每片都带 `index`，这条路径对得上。兼容实现若只在首片给 index，或全程不给 index 却把参数切开，槽就裂开。
- 影响：工具执行器拿到截断参数或 `__rawArguments`，按这个入参执行一次。后半段再带名字时，同名工具再执行一次，两次都不是重试循环打出来的。

### BC09-6 同一个 Chat 工具对象上的两套 arguments 会拼成一份非法 JSON

- 现象：`function.arguments` 和对象顶层的 `arguments` 都会追加。同一对象两字段都是非空字符串时，参数文本变成两段 JSON 首尾相接，解析失败后仍发出工具调用。
- 证据：`crates/agent-provider/src/parse/tool_call.rs:120-122` 追加 `function.arguments`，134-136 行无条件再追加顶层 `arguments`。失败形态在 194-197 行。平铺变体测试把两字段分在不同增量里（291-300 行），没有锁定「同一对象两字段同时存在」。
- 机制：顶层字段是为缺少 `function` 包装的兼容增量准备的。合并函数不判断这两处是不是同一段文本。
- 影响：工具以 `__rawArguments` 执行一次，模型给出的结构化参数到不了工具实现。

### BC09-7 Chat 正文只认字符串，数组 content 整段丢掉

- 现象：`delta.content` 或无 delta 时的 `message.content` 不是非空字符串时，不产生 `TextDelta`，也不扫描数组里的文本片段或工具片段。标准字段 `tool_calls` 仍会收集。
- 证据：`crates/agent-provider/src/parse/chat_mapping.rs:118-122` 的 `non_empty_string` 只接受 `as_str`。消费点在 `chat_core.rs:121-124` 和 166-168 行。思考字段对对象有 `text` / `content` / `delta` 兜底（`chat_core.rs:251-265`），正文没有对应兜底。
- 机制：只含 `content: [{type, text}]` 的分片被当成没有正文。思考标签提取器收不到这段文本，因此也不会从中拆工具标记。`think_tags.rs:16-28` 本来也只认思考标签。
- 影响：这一帧的可见回复丢失。若整次流的正文都是数组，回合在消费层看起来没有正文；工具只在同时存在 `tool_calls` 时才会执行。字符串正文里的 `<tool_call>` 不会被收成工具调用，会留在助手文本里。本文没有把某家目录模型的线格式断言成 XML。

### BC09-8 Chat 把顶层字符串 message 或 code 当成错误帧，choices 不再解析

- 现象：一帧只要有字符串形式的顶层 `message`、`error_description` 或 `code`，解析立即终止为错误 Stop，同帧的 `choices` 不再读取。
- 证据：`crates/agent-provider/src/parse/chat_mapping.rs:81-91` 的优先级在对象 `error.message` 和字符串 `error` 之后包含 `message`、`error_description`、`code`。`chat_core.rs:76-86` 在读取 choices 之前返回。`chat_tests.rs:481-488` 把 `{"message":"m3"}` 和 `{"code":"m5"}` 锁成错误 Stop。
- 机制：这是为「整帧就是错误」准备的。判定不要求缺少 `choices`。终止文案再经 `stream_error_kind`（`events.rs:291-292`）做无状态分类，所以文案里的 `too long` 会在 Stop 上标成 `ContextLengthExceeded`。无正文时消费层仍把 kind 收成 `Unknown`；有此前正文时，这帧的剩余内容丢失，回合按已有正文结束。
- 影响：成功分片若带状态字符串，本帧正文和工具增量都不会进入回合。单独一帧时，用户得到一次失败结束，而不是模型已经生成的 choices。

### BC09-9 旧 profile 没写 endpoint 时，导入把协议写成 openai/chat

- 现象：尚无 `models.yaml`、只有旧 `profile-config.json` 时，缺省 `endpoint` 和字面量 `chat-completions` 都变成 `openai/chat`。模型 id 按原字符串保留，窗口和工具能力不写入。认不出的 endpoint 字面量会拒绝导入并保留原文件。
- 证据：`crates/agent-provider/src/model_store.rs:190-193` 在文件不存在且尚未打过导入标记时调用 `missing_source`。`model_store_import.rs:296-305`：`None | Some("chat-completions")` 写 `openai/chat`，`responses` 写 `openai/responses`，其余返回 `MIGRATION_REQUIRES_REVIEW`。327 行只保存 `{"id": id}`。`catalog_types.rs:60-61` 与 `105-108` 行让省略的供应商协议再默认成 `openai/chat`；`ModelSpec::effective_protocol`（306-308 行）用模型协议，否则用供应商协议。
- 机制：严格迁移（`models/config_legacy.rs:58-61`）对扁平模型缺少显式协议会拒绝，不猜厂商。旧 profile 这条入口在交给该迁移函数之前已经把协议填上。没写 endpoint 和写了未知 endpoint 因此不是同一条失败关闭。
- 影响：旧配置若用 Anthropic 或 Gemini 的地址、却没有 endpoint 字段，选中的模型 id 还在，发出去的协议是 Chat Completions。对方按 Messages 或 GenerateContent 解析就会失败，或把工具调用回成另一套 SSE，再落到 BC09-3 至 BC09-7 的解析缺口。这是导入时写死的协议，不是目录查找的多级兜底。

### BC09-10 Anthropic 只登记 tool_use，pause_turn 等未知停止原因收成正常 Stop

- 现象：`server_tool_use` 以及其他非 `tool_use` 的内容块不进入待发工具表。`pause_turn` 以及表外的停止原因映射成普通 `Stop`，不是错误，也不是工具调用。回合按正常结束提交，不会为了服务端暂停再请求一次。
- 证据：`crates/agent-provider/src/parse/anthropic_core.rs:146-161` 只在 `type == "tool_use"` 时登记。`parse/anthropic_map.rs:23-29`：`tool_use`、`max_tokens`、`end_turn`、`stop_sequence`、空、`refusal` 各有分支，其余 `Some(_)` 一律 `StopReason::Stop`。
- 机制：映射表把「其他」定义成正常停止。`pause_turn` 落在这个分支。没有登记过的块在 `content_block_stop` 不会发出 `ToolCall`。
- 影响：需要客户端继续的暂停回合被当成助手已经说完。服务端工具没有对应的本地工具执行，也没有下一次续传请求。用户看到的是一条普通结束，而不是工具结果或明确失败。

## 已核对闭合或不是问题

- 供应商重试循环只重放 `RateLimit` / `ServerError` / `Timeout` / `Network`（`retry_decision.rs:112-119`、`194-200`）。鉴权、配额、上下文超限、未知错误在这个循环里返回不再重试。`RetryPolicy` 默认 `max_retries` 为 0（`retry_decision.rs:33-35`）。`provider_stream` 的生产调用点没有找到，只有 `crates/agent-provider/tests/retry.rs` 与 `retry_stream.rs` 的测试。失败尝试的帧在 `retry_stream.rs:155-158` 丢弃，成功才返回；调用方若在返回前已经执行工具，且仍报 `produced_content: false`，这个循环会再跑一次闭包。现网会话路径不经过它。
- 已经解析出工具调用、正文或思考的流，消费层收成 Message 而不是 StreamError（`crates/session-loop/src/stream.rs:413-451`），随后工具只派发一次（`streaming.rs:319-329`）。所以「重试把同一次工具调用再执行一遍」在这条生产路上没有对上。截断参数执行一次，记在 BC09-5，不是重试双发。
- 401/403 在任何正文之前定为 `Auth`（`error.rs:221-223`）。无状态且对不上鉴权短语的文案定为 `Unknown`，会话层当致命，不会重试。流内空内容错误 Stop 的 kind 被消费层改写，见 02 的记录；本范围仍会在 Stop 上写入 `stream_error_kind` 的结果。
- 目录 `lookup` 只做 trim 后的精确键（`models/catalog.rs:430-433`）。`context_window_for` 缺失即 `None`（436-438 行）。去版本后缀和 `*` 厂商默认窗口的测试断言它们不再发生。文件头 8-9 行仍写着多级兜底，与函数不符，不改变运行结果。`upsert_from_scan` 会用任意正数窗口覆盖已有窗口（`catalog_override.rs:96-99`），仓库内调用点只有测试，生产请求不经它改窗口。`prompt_cache_min_tokens_for` 对未收录模型回退 1024（`catalog.rs:449-452`），仓库内同样只有测试调用。
- yaml 投影把协议写进 `entry.protocol`，故意不写 `mode`（`catalog.rs:753-755`）。`supports_function_calling` 只有 `supports_tools == Some(true)` 才为真（791 行）。本仓库没有生产请求构造读取这个投影位来决定是否发送工具。省略协议时的唯一默认是 `openai/chat`（`catalog_types.rs:105-108`），模型级协议覆盖供应商级。这是单点默认，不是多级窗口或协议猜测。旧 profile 缺 endpoint 被写成 chat 的那条，记在 BC09-9。
- `resolve_in` 要求供应商启用、模型启用、非空 base URL，且 `key_for` 必须读到非空密钥，否则 `CREDENTIAL_MISSING` 或 `CREDENTIAL_READ`（`model_store.rs:410-422`、`444-462`）。密钥文件不存在时读接口返回 `Ok(None)`（`credentials.rs:90-93`），解析侧把 `None` 收成缺失，不发出请求。非 Windows 读系统槽返回 `Unsupported`（104-107 行），写入也不落明文（122-125 行）。清除凭据时，若活动模型指向该供应商，活动模型被清空（`model_store.rs:545-551`），不改成另一家模型。配置解析失败的快照 `tree` 为 `None`（`model_store.rs:233-243`），`committed` 在 `state.error` 存在时返回错误（335-338 行），新请求不会用上一份坏树。
- 活动模型指向已停用或不存在的条目时被清空，不替换成别的 id（`models/config_validation.rs:60-63`）。扁平迁移把 `model` 改名为 `id`、`contextLength` 改名为 `contextWindow`（`config_legacy.rs:166-174`）；同一规范字段两边值不同则拒绝（103-111 行）。缺显式协议或字面量 `apiKey` 拒绝改写（58-61 行、132-135 行）。`ensure_migrated` 算出的树不直接写盘，`commit_through_store` 再调用 `ModelsStore::read`（`migration.rs:96-111`），读路径再次调用同一个 `migrate_legacy_value`（`model_store_import.rs:153-154`）。这是同一转换跑两次，不是把算好的 id 丢掉。
- Responses 的 `arguments: ""` 会整段替换已累积参数（`responses_tool_call.rs:61-63`）。测试 `function_call_item_done_emits_when_arguments_ready` 把「added 时参数为空、done 时带完整参数」锁成一次发出（`responses_tests.rs:164-178`）。`arguments.done` 与终态重送按 `call_id` 去重（`responses_tool_call.rs:145-148`，测试 199-215 行）。无终态收成 `Unknown`（`responses_core.rs:193-203`），本重试循环不重放。
- 计费缺 `prompt_tokens` 或 `completion_tokens` 时返回 `None`（`pricing.rs:232-241`）。缓存读或缓存写大于 prompt 时也返回 `None`（128-131 行），不填 0。费率十进制解析失败返回 `u64::MAX`（269-271 行）。本范围内没有找到用这个金额去换模型、放行工具或结束回合的门闩。浪费提示和查询展示不在本文件的行为闭环里。展示精度不记。

## 给主控的摘要

解析、分类、重试、目录、凭据、迁移、计费都按当前代码看过；请求体拼装不在本份。
供应商重试循环不重放鉴权、配额和上下文超限，默认零次重试，生产也没有调用 `provider_stream`。
上下文超限会被加码重发，是因为分类 kind 被会话层长度阶梯接住：先翻倍 `max_tokens` 再压缩。
`too long` 比 5xx 和超时更早命中，耗时或字段过长的 HTTP 失败会进这条阶梯。
401/403 不会当可重试；5xx 且正文对不上四条鉴权短语时会当 `Server` 重放。
Anthropic 带字符串 `text` 的工具增量、Gemini 同一 part 的正文，会把工具调用收成正文或空参数调用。
Chat 缺 index 的参数分片会拆槽，截断参数仍执行；两套 `arguments` 会拼坏 JSON；数组 `content` 整段丢掉。
旧 profile 没写 endpoint 会导入成 `openai/chat`，模型 id 还在，协议已经换掉。
目录查找已去掉后缀和星号兜底；凭据读不到不会发请求；迁移冲突会拒绝，不改写坏 id。
已经解析出的工具调用不会再进流错误重试，现网这条路对不上「重试导致双工具调用」。
