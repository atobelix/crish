# 供应商请求与流传输

> 日期：2026-10-13
> 范围：`crates/agent-provider` 的 `request/`、`transport/`、`sse/`、`events.rs`、`consume/`、`config.rs`。`lib.rs` 只作模块地图。生产发送面以 `apps/agent-workbench/src-tauri/src/engine_provider.rs` 的 `HttpProviderCall::stream` 为准：剖面 → 请求体 → URL → `stream_frames` → `http_stream_next`。
> 不深挖 `parse/` 的增量拼接、`retry`、`model_store`、`credentials`（归 09）。解析器只在「流交不到消费层」的交界引用。

## 能力结论

Chat、Responses、Anthropic 的生产请求按目录剖面选协议，正文、URL、解析器同一把钥匙。Chat 在 `stream` 不是 `false` 时带 `stream_options.include_usage`。合法的 `\n\n` / `\r\n\r\n` 半帧和半个 UTF-8 字符会留在缓冲里，凑齐再切。干净的 `[DONE]` 或 EOF 会走 `parser.finish()`，工具调用和 usage 在这一步才冲刷成事件。消费层把完整 `ToolCall` 收成消息；abort 且已有正文时保留部分内容。

这条链有几处会让用户看到错结果。Gemini 的 URL 是一次性的 `:generateContent`，读端却只认 SSE 的 `data:` 行，模型正文进不了消费层。流已经开始之后，idle 超时、abort、坏帧都以读错误结束，不调用 `parser.finish()`，未冲刷的工具增量与 usage 丢失，已开始的成功流被判失败。思考回放缺协议要求的字段。Responses 没有工具配对闸门。无正文的 stop 把 usage 从结算元数据里拿掉。目录未命中或 base 没带 `/v1` 时，端点会静默拼错。

## 问题清单

### BC08-1 Gemini 请求打到一次性 generateContent，回答被 SSE 分帧丢掉

- 现象：Gemini 回合的 HTTP 目标是 `{base}/v1beta/models/{model}:generateContent`。请求体没有 `stream` 字段，请求头只有 `x-goog-api-key` 和 `content-type: application/json`。2xx 之后一律按 SSE 增量读。整段 JSON 没有 `data:` 行时分帧结果为空，解析器收尾变成「没有内容事件」的错误 stop。用户看到失败空回合，看不到模型正文。
- 证据：`apps/agent-workbench/src-tauri/src/engine_provider/protocol.rs:432-436`；`apps/agent-workbench/src-tauri/src/engine_provider.rs:567`（成功响应进入 `stream_frames`）；`crates/agent-provider/src/request/build_gemini.rs:75-136`（body 无 `stream`）、`305-311`（头）；`apps/agent-workbench/src-tauri/src/engine_provider/headers.rs:60`；`crates/agent-provider/src/sse/frame.rs:261-262`（无 `data:` 行则不产出帧）、`109-125`（EOF 残留仍走同一解析）；`crates/agent-provider/src/parse/gemini_core.rs:247-256`。测试把这条 URL 钉死：`apps/agent-workbench/src-tauri/src/engine_provider_tests.rs:214-218`。
- 机制：`build_endpoint_url` 对 Gemini 只补到 `/v1beta`（`crates/agent-provider/src/request/wire_protocol.rs:201-207`），调用方再拼模型方法，方法名固定 `generateContent`。SSE 解析器只把带 `data:` 的对象当帧。一次性 JSON 文档没有这个前缀，`finish` 得到 `Ok(None)`，不报损坏帧，内容被静默丢掉。正文超过 4MB 且中间没有帧分隔时，更早变成 `FrameTooLarge`（`frame.rs:59`、`93-97`）。推断：官方 `generateContent` 返回的就是这种整段 JSON，所以生产路径稳定复现空失败。
- 影响：Gemini 模型的回答、工具调用和 usage 都到不了消费层。后续回合没有可回放的助手消息。

### BC08-2 流已经开始后，超时、abort 和坏帧不收尾，成功流被判失败

- 现象：首字节默认 30 秒、块间空闲默认 60 秒。正文已经流出之后，只要 60 秒没有下一块，或者用户 abort，或者分帧/解析报错，流以 `Err` 结束。解析器的 `finish()` 不会跑。还没冲刷的 `tool_call` 参数增量组不回完整调用，本应挂在最终 stop 上的 usage 也不会变成事件。
- 证据：超时默认值 `apps/agent-workbench/src-tauri/src/engine_provider.rs:61-63`，读选项 `557-559`。abort 与超时的竞速 `crates/agent-provider/src/sse/reader.rs:229-240`；错误把流标成结束 `360-363`。`apps/agent-workbench/src-tauri/src/engine_provider/stream.rs:129-133` 在读错误上直接 `finished = true` 并返回 `Err`，不调用 `parser.finish()`。解析错误同样跳过收尾：同文件 `119-121`。工具调用与 usage 只在 `finish` 里冲刷：`crates/agent-provider/src/parse/chat_core.rs:192-210`、`236-241`。干净 EOF 才会收尾：`stream.rs:104-108`。
- 机制：生产走 `stream_frames` → `read_sse_stream`。已经切好、还排在 reader 或 `http_stream_next` 队列里的帧会先交出去，然后才是 `Err`。`select` 是 abort 优先：abort 已置位时，就绪但还没读的下一块不会再读（`reader.rs:230-232`）。丢失的是解析器内部尚未 `finish` 的工具拼接和 usage，以及「本该正常 stop」的终态。idle 把「模型已经写完、结束帧还没到」和「流真的断了」收成同一种失败。
- 影响：用户看到半截回答加一次失败。依赖这次工具调用的下一回合没有工具请求。结算缺少这次调用的 usage。会话层如何对待已经发出的正文增量归 02；这一层自己不会把未冲刷状态补成 stop。

### BC08-3 SSE 分帧在错误分隔和同帧多段 JSON 上丢掉已切出的增量

- 现象：帧边界只认 `\n\n` 和 `\r\n\r\n`。`\n\r\n` 和 `\r\r` 一直留在缓冲里，直到 EOF 被当成一整段去解析。同一事件里多行 `data:` 用换行拼成一个字符串；两段 JSON 因此粘在一起，解析失败，整条流报 `MalformedSseFrame`。同一次 `push` 里已经切出的更早帧，在这次错误上也不会交给上游。
- 证据：分隔扫描 `crates/agent-provider/src/sse/frame.rs:202-219`。`data:` 拼接与非对象 JSON 直接跳过 `247-264`、`273-284`。`split_frames` 在 `175` 用 `?` 传播解析错误，已消费前缀的 `drain` 在 `189-191`，只在循环正常结束时执行。
- 机制：`?` 在 `drain` 之前返回，函数的局部 `frames` 被丢掉，`pending` 也不前移。下一次读取仍从坏帧之前的字节重新切，坏帧还在，流已经因 `Err` 结束（见 BC08-2），这些增量没有第二次机会。合法 JSON 数组被 `Ok(_) => Ok(None)` 静默跳过，不报错也没有内容。半个合法 `\n\n` / `\r\n\r\n` 和半个 UTF-8 字符会留下，那是另一条路径，见文末闭合项。`\r\n\n` 能切，因为其中含有 `\n\n`（`frame.rs:226-230`）。
- 影响：供应商或代理若用 `\n\r\n` 分帧，或在缺少空行时把多条 `data:` JSON 放进同一块，用户丢掉这一块里已经完整的正文和工具增量，回合以坏帧失败。

### BC08-4 思考回放缺协议要的字段，下一回合的推理上下文是错的

- 现象：领域思考块只有 `text` 和可选 `redacted`。Anthropic 回放只发 `{type:thinking, thinking:text}`，没有 signature，`redacted` 被 `..` 丢掉。Gemini 历史里的 `Thought` 在 `contents` 组装时直接跳过，`functionCall` 也不带回放 id。Responses 默认不回传思考；即便模式被改成回传，发出去的也是 `{type:reasoning, content:纯文本}`。Chat 在推理模式为 Omit 时，把已经填上的 `reasoning_content` 再清掉。
- 证据：领域类型 `crates/conex-types/src/message.rs:142-146`。Anthropic `crates/agent-provider/src/request/build_anthropic.rs:643-645`。Gemini `crates/agent-provider/src/request/build_gemini.rs:388`（`_ => {}` 吃掉思考）。Responses 形状与「空思考不发」`crates/agent-provider/src/request/messages.rs:503-537`；默认 Omit `crates/agent-provider/src/request/build_responses.rs:53-56`。Chat 清洗 `crates/agent-provider/src/request/build_chat.rs:156-162`。生产模式：`thinking_format == DeepSeek` 才是 Require，其余 Omit（`apps/agent-workbench/src-tauri/src/engine_provider/protocol.rs:246-249`）。
- 机制：出站没有地方保存或转发 signature、`thoughtSignature`、`encrypted_content`、reasoning item id。`agent-provider` 源码里没有这些字段的写入。DeepSeek 且目录把 `thinking_format` 标成 DeepSeek 时，Require 让 Chat 的 Omit 清洗不生效，工具轮次仍带 `reasoning_content`。目录没把该模型标成 DeepSeek 时，清洗会把键抹掉。显式思考档位在字典未命中时，发送前就拒绝，不会静默省掉档位（闭合项）。
- 影响：带思考的多回合里，Anthropic 收到的 thinking 块不是上一回原样；Gemini 的历史思考整段缺失；Responses 的推理项不是带 id 的原项。推断：这些协议在下一回合要求原样回放时，请求会 400，或者模型丢掉上一段推理后改口。DeepSeek 工具轮次在格式标记缺失时同样缺键，推断为 400。

### BC08-5 Anthropic 丢掉消息里的 system 角色，运行时转向进不了请求

- 现象：转向消息的角色是 `System`。Anthropic 组消息时对 `System` 直接跳过，只把 `context.system_prompt` 放进顶层 `system`。会话中途插入的转向正文不会出现在发给模型的 `messages` 里。
- 证据：转向消息 `crates/session-loop/src/steering/nudge.rs:98-114`。跳过 `crates/agent-provider/src/request/build_anthropic.rs:507-509`。Gemini 把同角色并进 `systemInstruction`：`crates/agent-provider/src/request/build_gemini.rs:318-333`。Chat 会把 system 角色写进消息数组（`messages.rs` 的角色映射；生产 Chat 体走 `build_chat.rs:117-123`）。
- 机制：注释写明 Anthropic 没有独立的 system 角色消息，于是消息域里的 system 被整条丢弃，而不是并进顶层 `system`。顶层字段只来自请求的 `system_prompt`，不扫描消息列表。
- 影响：用户在 Anthropic 会话里触发的运行时转向，模型看不到。同一条转向在 Chat 里会进消息，在 Gemini 里会进 `systemInstruction`。三条协议上的可控性不一致，Anthropic 这一侧是丢内容。

### BC08-6 Gemini 把「指定某一个工具」改成任意工具，调用也不带 id

- 现象：`tool_choice` 为某个函数名时，请求里的 `functionCallingConfig.mode` 是 `ANY`，没有 `allowedFunctionNames`。历史 `functionCall` 只有 `name` 和 `args`，没有 id。非对象参数被包成 `{value: 原值}`。
- 证据：`crates/agent-provider/src/request/build_gemini.rs:526-536`（`Function { .. }` 与 `Required` 都落 `ANY`）；`373-386`（无 id，非对象包 `value`）。
- 机制：注释写明指定函数不再用白名单。模型收到的约束是「必须调用某个函数」，不是「必须调用这一个」。回放没有调用 id，配对只能按函数名加出现顺序数（同文件 `139-143` 的检测说明）。同名多次调用的结果对错位时，这一层分不出来。
- 影响：用户或上层指定了工具名，模型可以改调另一个已声明工具。下一回合按名字配对，同名调用的结果可能接到另一次调用上。

### BC08-7 Responses 出站没有工具配对闸门，孤儿调用会直接发出去

- 现象：Anthropic、Gemini、Chat 在组体之前校验工具配对，失败则 `InvalidRequest`，请求不发。Responses 分支没有这步校验，直接 `build_responses_request_body`。`request/` 里也没有 Responses 的配对校验函数。
- 证据：三轨拒绝 `apps/agent-workbench/src-tauri/src/engine_provider.rs:265-339`。Responses 直接构建 `343-346`。`build_responses.rs` 无 orphan / validate 匹配。
- 机制：Chat / Anthropic / Gemini 的 builder 内部还有一道过滤，会丢掉孤儿调用并在空助手消息上塞 `WIRE_CONTINUATION_NOTE`。生产路径在进 builder 之前已经返回错误，这道改写轮不到。Responses 两道都没有，未配对的 `function_call` 原样进 `input`。
- 影响：Responses 会话里工具结果没接上时，请求仍然发出。推断：上游以 400 拒绝，而另外三轨在本地就停。用户看到的是供应商错误，不是本地的配对失败。

### BC08-8 没有正文的 stop 不带 usage；错误帧的 stop 丢掉已经解析的 usage

- 现象：消费层只从 `Stop` 拷贝 usage。聚合结果没有文字、工具调用和思考时，`Empty` 和 `StreamError` 的 `metadata` 是 `Null`，stop 上即使带着 usage 也不进结算。Chat 解析器遇到错误对象时，立刻发 `usage: None` 的 error stop 并终止，之前帧上已经记下的 usage 不会出现在这一个 stop 里。
- 证据：只认 stop 上的 usage `crates/agent-provider/src/consume/mod.rs:176-191`。无正文丢掉元数据 `273-294`，abort 且无正文同样 `323-338`。有正文时 `build_message_metadata` 会写入 usage（`380-383`）。错误帧 `crates/agent-provider/src/parse/chat_core.rs:76-86`；正常 `finish` 才会把 `self.usage` 挂上 stop（`236-241`）。
- 机制：Chat 在 `stream` 不是 `false` 时请求 `include_usage`（`build_chat.rs:219-225`），供应商把用量放在后面的帧上。那一帧若是错误对象，构造 stop 时不读 `self.usage`，并且 `terminated` 之后 `finish` 直接返回空。无正文的 length / error / abort 在消费层再丢一次。有正文的 stop 会保留 usage，不限 stop 原因。
- 影响：内容过滤、空回复、未产出正文就被 abort 的回合没有可结算的 token。错误帧若发生在用量帧之后，已经数过的用量也到不了消费层。

### BC08-9 目录未命中或 base 没带 `/v1` 时，静默走错协议和路径

- 现象：`provider_id` 或模型 id 在已提交目录里对不上时，剖面固定为 Chat、思考格式空、推理模式 Omit、不支持图像。生产用这个剖面同时决定请求体和 URL，不读 `config.endpoint`。Chat 的 URL：base 已经以 `/v1` 结尾才拼 `/chat/completions`；只有 `openai.com` 结尾或主机名含 `sensenova.cn` 才会自动补 `/v1`。其余主机直接拼 `/chat/completions`。
- 证据：未命中即 `fail_closed` `apps/agent-workbench/src-tauri/src/engine_provider/protocol.rs:161-174`、`193-213`。剖面不读 endpoint，协议只来自目录 `216-217`。发送 `engine_provider.rs:455-474`。crate 侧 `resolve_endpoint` 把缺省和 Auto 收成 chat-completions：`crates/agent-provider/src/request/build.rs:139-144`；`config.rs:11-16` 写明 Auto 恒退化为 chat-completions。路径规则 `crates/agent-provider/src/request/wire_protocol.rs:189-199`。
- 机制：未知模型不会改写用户给出的 model 字符串，但协议和路径改成 Chat。用户把 endpoint 配成 responses 也改变不了这次未命中。兼容网关的 base 若是 `https://host/openai` 这种不带 `/v1`、又不是那两个主机特例，路径落在 `/chat/completions` 而不是 `/v1/chat/completions`。`https://api.deepseek.com` → `/chat/completions` 被测试钉死（`wire_protocol_tests.rs:601-606`），与这条特例分开，不记为问题。
- 影响：模型 id 写错或目录还没有这条模型时，Anthropic / Gemini / Responses 的基址会收到 Chat 形状的请求，用户看到 404 或协议错误，界面仍显示他选的那个模型名。base 漏写 `/v1` 的兼容网关同样打到错误路径。

### BC08-10 工具参数 schema 在规范化时改了语义

- 现象：布尔 schema 变成 `{type:string}`。字符串、数字、数组、null 这些非对象 schema 变成空对象 `{type:object, properties:{}}`。`const` 改写成只含该值的 `enum`，并且覆盖原来的 `enum`。四条协议的工具参数都走这一套。
- 证据：`crates/agent-provider/src/request/schema.rs:39-46`、`96-100`。Gemini 声明 `build_gemini.rs:517-523`；Chat / Responses 经 `to_openai_tool` / `to_responses_tool` 使用同一函数（`crates/agent-provider/src/request/tools.rs:55-57` 说明 Responses 与 Chat 同款规范化）。
- 机制：规则把「任意值」的布尔 `true` 和「禁止一切」的布尔 `false` 都收成 string。`const` 与已有 `enum` 并存时，发出去的只剩 const 那一个值。`$ref` 当叶子保留，不在这里展开。
- 影响：工具若用布尔 schema 或 `const` 约束参数，模型看到的是另一种类型。它会按 string 或被收窄的 enum 填参，工具执行拿到的值和作者声明的不一致。

### BC08-11 Anthropic 在调用方没给 max_tokens 时自己写一个上限

- 现象：Chat、Responses、Gemini 在对应字段为 `None` 时不写输出上限。Anthropic 始终写入 `max_tokens`：调用方没给时用 `budget + 4096`，没有思考预算时用 2048，再与 64000 取较小值。
- 证据：`crates/agent-provider/src/request/build_anthropic.rs:88`、`147-159`。Gemini 仅在 `Some` 时写入 `build_gemini.rs:99-101`。Responses 同样只在有值时写 `max_output_tokens`（`build_responses.rs:81` 一带的字段写入）。
- 机制：抬升是为了给 thinking 预算留出正文空间。没配 `max_tokens` 的普通 Anthropic 请求也会带上 2048。思考预算很大时，上限被 64000 封顶，方言侧也用这个常数当物理上限（同文件 `430`）。
- 影响：用户没设输出长度时，Anthropic 回答在 2048 token 处被截断，另外三轨仍由供应商默认长度决定。长思考加长回答会被 64000 再截一刀。

## 已核对闭合或不是问题

- 半个 UTF-8 字符和未凑齐的 `\n\n` / `\r\n\r\n` 留到下一块（`frame.rs:137-151`、`169-170`）。`\r\n\n` 按 2 字节分隔，不吞掉下一帧（`226-230`）。`[DONE]` 丢掉其后字节是分帧的既定终止（`176-188`）。干净 EOF 会 `parser.finish()`（`stream.rs:104-108`）。
- abort 不会继续读新的上游字节。`select` 里 abort 优先于已就绪的下一块（`reader.rs:230-232`）。已经切好的帧会在错误之前交出，那是缓冲，不是 abort 之后又去读。
- 显式思考档位不在 `thinking_map` 里，或模型没有思考字典时，HTTP 之前就 `InvalidRequest`（`apps/agent-workbench/src-tauri/src/engine_provider/thinking.rs:71-83`）。方言函数在 map 未命中时返回空键（`dialect.rs:233-236`），生产发送路径走不到「静默省掉用户档位」。档位省略、Off、Auto 不注入思考键，是发送前的显式分支（`thinking.rs:57-67`）。
- 生产 DeepSeek：`thinking_format == DeepSeek` 时推理模式是 Require（`protocol.rs:246-249`），`build_chat` 的 Omit 清洗不会抹掉 `reasoning_content`。格式没标成 DeepSeek 时的清洗见 BC08-4。
- Anthropic / Gemini / Chat 的孤儿工具调用在生产出站前被拒绝，不伪造工具结果（`engine_provider.rs:265-339`）。builder 里的占位句只在绕过这道闸门、直接调 build 时才会写进请求体。
- 连续 assistant 会插入一条 `WIRE_CONTINUATION_NOTE` 用户占位（`messages.rs:520-530`，Anthropic 侧 `build_anthropic.rs:536`）。这是为了满足角色交替而改写模型可见的上下文，占位句不是用户原话。本路把它记为有意投影，不单列成丢字段。
- Chat 空工具 id 会落成 `call_{工具名}`（`messages.rs:308-310`）。`stream != false` 的 Chat 请求带 `include_usage`。Responses 体不写 `stream_options`，用量放在终态事件上，这是该协议的构造选择（`build_responses.rs:28` 附近的说明与测试断言）。
- `https://api.deepseek.com` 拼成 `/chat/completions` 而不是 `/v1/chat/completions`，由 `wire_protocol_tests.rs:601-606` 钉死。不记进 BC08-9。
- 消费层在 abort 且已有正文或思考时保留部分消息，`stopReason=aborted`（`consume/mod.rs:321-346`）。无正文的 abort 才是 `StreamError`，usage 缺口见 BC08-8。

## 覆盖与未覆盖

覆盖了 `request/` 的四套请求体、消息角色、工具 schema、端点 URL 与 `config.rs` 的端点枚举；`sse/` 的分帧和 `read_sse_stream`；`transport/stream_frames`；`consume/` 如何把事件收成 `ProviderOutput`。生产接线只引用 `engine_provider` 的 `stream`、剖面、URL 和 `http_stream_next`，用来确认这些函数是否真的被发出去、流是否交到消费层。

未深挖：`parse/` 里按 index 拼接 `tool_call` 参数的细节（归 09）。本路只确认完整 `ToolCall` 事件能被 `consume` 收下，以及 `finish` 没被调用时拼接结果出不来。`retry_stream` 在已有内容后再出错会丢掉已收集帧，且观察者的 usage 恒为 `None`；那不是 `HttpProviderCall::stream` 的活路径，归 09。会话层收到中途 `Err` 之后是否保留已发出的正文，归 02。`model_store` 与凭据归 09；目录未命中的行为只通过 `catalog_request_profile` 的 `fail_closed` 记录。摘要专用的 `chat_provider_url`（`protocol.rs:411-412`）是另一条字符串拼接，本路没有把它当主对话路径。没有改代码，没有跑测试。Gemini「官方返回整段 JSON」和「缺 signature / 缺 reasoning 项会 400」是推断，已在对应条目标明。

## 给主控的摘要

1. Gemini 生产 URL 是 `:generateContent`，读端只认 SSE `data:` 行，整段 JSON 被丢掉，回合变成没有内容的错误 stop（BC08-1）。
2. 正文开始后的 idle（默认 60 秒）、abort、坏帧都不调用 `parser.finish()`，未冲刷的工具增量和 usage 到不了消费层，已开始的流被判失败（BC08-2）。
3. SSE 不认 `\n\r\n` 和 `\r\r`；多行 `data:` 粘成非法 JSON 时，同一次 push 里已经切出的帧也被 `?` 丢掉（BC08-3）。
4. 思考回放缺 signature / thought / reasoning item id；Anthropic 的 system 角色（含转向）整条不进请求（BC08-4、BC08-5）。
5. Gemini 把指定工具收成 `ANY`，`functionCall` 不带 id（BC08-6）。Responses 没有工具配对闸门（BC08-7）。
6. 无正文的 stop 在消费层丢掉 usage；Chat 错误帧的 stop 把已解析 usage 写成 `None`（BC08-8）。
7. 目录未命中静默改走 Chat，且不看 endpoint；base 非 `/v1`、又不是 openai.com / sensenova 时拼 `/chat/completions`（BC08-9）。DeepSeek 主机这条是测试钉死的，不记。
8. 工具 schema：布尔收成 string，非对象收成空 object，`const` 覆盖 `enum`（BC08-10）。Anthropic 未给 `max_tokens` 时写成 2048 或 budget+4096，封顶 64000（BC08-11）。
9. 已闭合：半帧与半个 UTF-8 会缓冲；abort 不读下一块；思考档位未命中在 HTTP 前拒绝；三轨孤儿工具本地拒绝；Chat 的 `include_usage` 有接上。
10. 未跑测试。`parse/` 拼接细节、`retry_stream`、目录装载归 09；中途 `Err` 之后会话是否留正文归 02。
