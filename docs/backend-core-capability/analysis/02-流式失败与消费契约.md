# 流式失败与消费契约

> 日期：2026-10-13
> 范围：`crates/session-loop` 的 `stream.rs`、`provider.rs`、`loop/handlers/streaming.rs`、`stream_error.rs` 及其 fatal / recover / retry。当前代码为准。
> 生产适配把解析结果原样收成 `ProviderStreamEvent` 再交给本层（`apps/agent-workbench/src-tauri/src/engine_provider/stream.rs` 的 `to_loop_event`）。请求体与解析器内部不在本文展开。

## 能力结论

session-loop 自己聚合 provider 流，不走 agent-provider 的 consume。流前 `Err`，以及「一个事件都还没有」的流中 `Err`，会保住 `ClassifiedStreamError`，按 kind 进入瞬态重试、length 阶梯或溢出压缩。这条路径不落助手消息，退避睡眠期间 abort 优先。

另一条才是线上常见形状：解析器把失败收成 `Ok(Stop { reason: Error, error_kind })`（过载、限流、上下文超限、空流保护、`content_filter` / `refusal`）。无正文时本层丢掉 kind 和文案分类，一律 `Unknown` 且不可重试，该进阶梯的直接 fatal。已经吐过正文、思考或工具调用后再失败，则被收成正常 `stop` 或 `tool-call`：回合当成功结束，工具照执行，实时 delta 也不撤回。length 重试发生在这条已提交的正文之后，下一轮再追加一条助手消息。

## 问题清单

### BC02-1 无正文的错误 Stop 被折叠成 Unknown，该重试的直接停

- 现象：流里只有错误 Stop、没有正文时，429、5xx、超时、上下文超限、payload 过大都变成不可重试的 `Unknown`，直接 fatal。`retry_after_ms` 和 Stop 上的 usage 同时丢掉。Auth 一类本来也该停，但恢复面看到的 kind 不再是 Auth，而是笼统 unknown。
- 证据：`crates/session-loop/src/stream.rs:427-432` 无内容且有 error 时只调用 `classify_stream_error`，不读已经放进聚合的 `error_kind`；`stream.rs:606-612` 该函数固定 `ProviderErrorKind::Unknown`、`retryable: false`、`retry_after_ms: None`，metadata 写成 `Value::Null`。分派在 `stream_error.rs:70-85`：只有 RateLimit / ServerError / Timeout / Network / ContextLengthExceeded / PayloadTooLarge 进阶梯，其余进 `fatal_provider_error`（`stream_error_fatal.rs:59-64`）。
- 机制：线上错误帧是 Ok 事件，不是流条目 `Err`。适配层原样转发 `error_kind`（`engine_provider/stream.rs:192-206`）。例如 Anthropic / chat / Gemini / Responses 的错误帧在终止 Stop 上带 `stream_error_kind(...)`（`crates/agent-provider/src/parse/anthropic_core.rs:113-126`，chat 同形于 `chat_core.rs:75-86`）。`consume_stream` 把这条 Stop 当普通事件推进构建器（`streaming.rs:159-183`），不走「空构建器则保留 ClassifiedStreamError」的分支。`finish` 再把分类抹掉。`pure_error_stop_yields_stream_error`（`stream.rs:678-686`）只锁定「Stop 上没有 error_kind → Unknown」，没有锁定「带了 Timeout / RateLimit 也必须保住」。
- 影响：该重试的停了，length / 压缩阶梯不会启动。该按 Auth、Quota、GatewayChallenge 交给恢复面的，kind 和 Retry-After 都丢了。这一轮如果 Stop 上已经有 usage（错误帧会带上 `self.usage`），也进不了 `turn_usage`。

### BC02-2 已有增量后再失败，被收成正常结束，工具照执行

- 现象：正文、思考或工具调用已经发给上游之后，流以 error 结束（含超时、过载、`content_filter`、`refusal`）。回合不进重试，也不以 error 收场。没有工具调用时走正常 `stop`；有工具调用时照常派发执行。实时 delta 已经推到前端，收口消息再提交一次，失败看起来像成功。
- 证据：`stream.rs:435-444` 有内容时，`StopReason::Error` 落进 `_ => ConsumeStopReason::Stop`；只要 `tool_calls` 非空就强制 `ToolCall`，Length 和 Error 都被盖掉。`ConsumeStopReason` 没有 Error 变体（`stream.rs:207-216`）。`streaming.rs:259-329` 先 `commit_message_with_deltas`，再按这个 stop reason 调用 `no_tool_calls` 或 `HasToolCalls`。abort 才会就地合成中断的工具结果（`streaming.rs:286-300`）；provider error 不会。`text_then_error_stop_yields_message`（`stream.rs:622-640`）和 `thought_with_error_stop_yields_message`（`stream.rs:1112-1131`）把「有字或有思考 + error → stopReason=stop」锁成当前行为。
- 机制：有内容的流中 `Err` 被合成一条 `usage: None` 的 error Stop（`streaming.rs:185-198`），然后走同一条 `finish`。chat 的 `content_filter` 等未知 finish_reason 映射成 `StopReason::Error`，但收口 Stop 的 `error` 和 `error_kind` 都是 None（`chat_mapping.rs:18-24`，`chat_core.rs:237-241`）。Anthropic `refusal` 同样只把 stop reason 标成 Error，finish 不带 error 文案（`anthropic_map.rs:28`，`anthropic_core.rs:300-304`）。聚合层见到 `reason == Error` 就填上笼统的「provider 流异常终止」（`stream.rs:327-328`）。`has_content` 用 `!text.is_empty()`，一个空白增量也算有内容（`stream.rs:413-416`）。下游 `no_tool_calls` 只看 `ConsumeStopReason`，看不到 `providerFinishReason`。
- 影响：该停的没停。拒绝和内容过滤在已经吐过字或思考时，run 以 stop 成功结束。截断的工具调用（length 或 error 收尾）会进入执行，而不是留在失败收场。可重试错误一旦有了增量就不再重试。这不是重试打出的第二份工具调用：阶梯根本不会再跑。

### BC02-3 非正文事件把仍可重试的流中 Err 赶出重试入口

- 现象：连接已经有首字节诊断、但模型还没吐正文时，随后的 Timeout / Network `Err` 不再按原分类重试。Retry-After、`retryable` 和 usage 在合成 Stop 时被丢掉，最后同样掉进 BC02-1 的 Unknown fatal。
- 证据：`ConsumeBuilder::is_empty` 看的是推入次数，不是有没有可抢救正文（`stream.rs:397-399`）。`streaming.rs:185-199` 只有 `is_empty()` 才把 `ClassifiedStreamError` 原样放进 `stream_error`；否则合成 Stop，且 `usage: None`。诊断来自适配层：`engine_provider.rs:560-566` 打开了 diagnostics，SSE 首块先发 `SseFirstByte` 再发帧（`crates/agent-provider/src/sse/reader.rs:392-404`）。
- 机制：首字节诊断让 `pushed > 0`。真正的分类错误不再走 `handle` 开头那条「空则重试」捷径（`streaming.rs:94-98`）。合成 Stop 的类型里没有 `retry_after_ms`，`finish` 又不读 `error_kind`。
- 影响：最常见的「连上了但正文前超时 / 断流」被当成不可恢复失败。阶梯测试只覆盖已经拿到 `ClassifiedStreamError` 的 `handle`，覆盖不到这条被诊断垫过的入口。

### BC02-4 length 重试不撤回已提交正文，下一轮再追加一条

- 现象：`stopReason=length` 的截断回复先作为一条完整助手消息落进对话，实时 delta 也已经按这个 message id 推走。阶梯然后提高 `max_tokens` 再请求一次。第二次流用新的助手 id，再追加一条助手正文。两段都留在会话里。
- 证据：`streaming.rs:84` 每次 streaming 预生成一个新 id；`streaming.rs:279` 在调用 `no_tool_calls` 之前就 `commit_message_with_deltas`。`no_tool_calls.rs:36-65` 在 length 升级时只翻倍 `max_tokens` 并 `NoProgressContinue`，不删除、不替换刚提交的那条。阶梯用尽后的 continue nudge 同样是再 `NoProgressContinue`（`no_tool_calls.rs:67-72`）。本层 stream_error 的 length 阶梯（`stream_error_recover.rs:56-76`）只处理「还没有消息」的 `ContextLengthExceeded`，不会回头撤掉 streaming 已经提交的截断消息。
- 机制：length 被定义成 Message 而不是 StreamError（`stream.rs:441`），所以重试发生在提交之后。重试不是重放同一条流，而是带着截断助手消息再叫一次模型。实时轨和收口轨都已经把第一段交给上游。
- 影响：用户看到两段助手正文。模型若复读截断前缀，就是双份；若接着写，会话里仍是两条助手消息对一轮用户消息。工具调用不会因此执行两遍：一旦有 tool call，stop reason 被改成 `tool-call`（BC02-2），length 阶梯不跑。

### BC02-5 溢出压缩重试不与 abort 竞速，取消可能被 fatal 盖掉

- 现象：上下文超限或 payload 过大走到压缩重试时，摘要等待（缺省墙钟 60s）不观察 abort。等待结束后无论用户是否已经取消，都不会走 `streaming_aborted`。摘要失败则直接 fatal；摘要成功则改写对话并排下一次 provider 调用。状态机在整个等待期间停在 Streaming。
- 证据：`stream_error_recover.rs:119-122` 只在入口查一次 abort。摘要调用的是 `summarize_via_blocking`（`stream_error_recover.rs:168-170`），其实现把 abort 传成 `None`（`summary_dispatch.rs:864-870`）。同文件已有 `summarize_via_blocking_with_abort`（`summary_dispatch.rs:877-900`）会 `select` abort，溢出路径没有用。返回后 `stream_error_recover.rs:185-194` 在 `llm_unavailable` 时 `fatal_provider_error`，`245-253` 在成功时 `apply_compaction` 并 `NoProgressContinue`，两处都不再读 abort。缺省 `compact_require_llm = true`（`loop_options.rs:64`），摘要 `Err` 会让压缩计划 `llm_unavailable`（`conex-compaction` `engine.rs:413-414`），于是 fatal。墙钟缺省 `LOOP_SUMMARY_MAX_WALL_MS = 60_000`（`summary_dispatch.rs:67`）。
- 机制：fatal 是 `HandlerOutcome::end`，主循环立刻 `converge`，到不了下一轮 `prepare_turn` 开头的 `check_control`。成功压缩的那条还能在下一轮入口被 abort 拦住，但对话已经被溢出压缩改写。瞬态退避的 `select`（`stream_error_retry.rs:152-160`）没有套到这条等待上。
- 影响：abort 和这次重试准备抢的是同一回合的下一次请求。用户取消可以被收成 provider error，而不是 aborted。压缩副作用在取消之后仍然落地。

### BC02-6 收到 Stop 之后不结束消费，状态机停在 Streaming

- 现象：模型侧的 Stop 已经进了构建器，handler 仍阻塞在 `stream.next()`。连接若不关，回合停在非终态 Streaming，直到 EOF 或空闲超时。空闲超时缺省 60s（`engine_provider.rs:63`）。超时再以流中 `Err` 到来时，会按 BC02-3 再合成一条 Stop，盖掉原来的 `error_kind` 和 usage。
- 证据：`streaming.rs:142-202` 的循环只在 abort、流结束或流中 `Err` 时跳出，没有「见到 Stop 就收口」。`provider.rs:19` 把「Stop 后流立即结束」写成实现方义务，消费方不执行。`http_stream_next` 在交出 Stop 后继续读帧，直到帧流 EOF（`engine_provider/stream.rs:96-114`）。解析器在错误帧后虽然 `terminated`，不再产出第二份正文，但 TCP 流本身不会因此结束。
- 机制：逻辑流结束和传输流结束被当成同一件事。Stop 之后若再有事件，本层仍会追加正文和工具调用，不按 call id 去重（`stream.rs:311-315` 只在合成空 id 时避让已有 id）。当前 HTTP 解析器在 terminated 后返回空事件，所以这条不会在正常适配上打出第二份工具调用；消费契约本身没有这道闸。
- 影响：错误帧之后用户要空等，状态机不是 TurnComplete / Done。随后的空闲超时把一个本可分类的失败改写成另一条错误，再掉进 BC02-1 或 BC02-2。

### BC02-7 失败和 abort 收口丢掉 usage，缓存拆分口径恒为 Included

- 现象：无正文错误的 usage 不进入回合；有正文的流中 `Err` 把 usage 写成空；abort 和 fatal 的 turn-end 再把 usage 写成 None。缓存拆分永远按「prompt 已含缓存」计算，Anthropic / Gemini 的 miss 和 input_total 是错的。stop reason 在有正文时被改写成 stop，见 BC02-2。
- 证据：无正文错误 `metadata: Value::Null`（`stream.rs:429-432`），`turn_usage_from_metadata` 读不到 usage（`streaming.rs:554-564`）。流中 `Err` 合成 Stop 时 `usage: None`（`streaming.rs:193-198`）。正常 turn-end 用的是 `state.budget_state.turn_usage.take()`（`turn_complete.rs:50`）。abort / fatal / converge 兜底走 `emit_missing_turn_end`，TurnEnd.usage 写死 None（`handlers/mod.rs:467-476`）；`streaming_aborted` 在 `streaming.rs:375` 调用它，`loop_exec.rs:309` 再兜一次。`consume_classify` 即使已经把 usage 放进 `budget_state.turn_usage`（`streaming.rs:256`），这条补发也不读。生产构建器是 `ConsumeBuilder::new()`（`streaming.rs:126`），从不调用 `usage_accounting`。缺省 `CacheAccounting::Included`（`stream.rs:73-76`、`104-115`）。`cache_accounting_kind` 用 `inputTotal == prompt` 判断 Excluded（`streaming.rs:604-619`），而 Included 公式下 `input_total` 永远等于 prompt，Excluded 分支对这条生产路径不可达。
- 机制：usage 只挂在 Stop 上。失败收口要么不建 metadata，要么合成一条没有 usage 的 Stop，要么 turn-end 不读已经解析出的槽位。口径 setter 只在 `stream.rs` 单测里用过，streaming 没有按协议族传入。
- 影响：失败回合和取消回合的账单 / 压缩估算缺少这轮真实 usage。Excluded 协议族的 cache miss 会被减成 0 或算小，浪费审计和下一轮预算钳制跟着偏。

## 已核对闭合或不是问题

- 流前 `Err`，以及构建器里还没有任何事件的流中 `Err`，原样进入 `stream_error::handle`，分类不被 `classify_stream_error` 改写（`streaming.rs:94-98`、`185-187`、`205`）。
- 阶梯按 kind 分派，不是看一个笼统字符串：瞬态重试、length 再压缩、payload 直接压缩、其余 fatal（`stream_error.rs:70-85`）。这些测试锁的是「分类已经在手里」之后的行为，例如 `abort_during_backoff_sleep_closes_aborted_without_consuming_retry`、`backoff_sleep_keeps_conversation_prefix_untouched`。无正文重试不 commit 助手消息，不会因此打出双份正文或双份工具调用。
- 退避睡眠与 abort 竞速，abort 优先且不占重试次数（`stream_error_retry.rs:90-92`、`148-160`）。length / 压缩阶梯入口也先查 abort（`stream_error_recover.rs:47-49`、`119-122`）。缺省 `retry_backoff = None` 时等待为 0、不睡，下一轮 `prepare_turn` / `streaming` 入口的 `check_control` 仍会先看到 abort。
- fatal 派发 `ProviderError`，Streaming → TurnComplete 且 `end_reason=Error`，handler 返回 `EndDecision::error`，主循环收敛，不会停在 Streaming（`stream_error_fatal.rs:59-64`，`conex-types` `transition.rs:144`）。
- 流消费的 `select` 把 abort 放在 `stream.next()` 前面；abort 与「零事件错误」同时出现时走 `streaming_aborted`，不进重试（`streaming.rs:143-158`、`94-97`）。有正文的 abort 保留部分消息并标 `stopReason=aborted`，不重试。
- 没有任何事件、也没有 error 的流收成 Empty，再 `SteeringNeeded`；steering 关闭时是 stop 加诊断，不是把分类错误收成空成功（`stream.rs:417-423`，`streaming.rs:332-350`）。chat 空 body 该不该先标成 error Stop，属于解析器，不在本层另判。
- 重试不会把同一条 HTTP 流再读一遍。`consume_stream` 返回后流被 drop，下一次是新的 `provider.stream()`。工具调用不会因为这条重试执行第二遍；失败流上执行一次的问题记在 BC02-2，不是双份。

## 给主控的摘要

线上失败多半是带 `error_kind` 的 Ok Stop，不是流条目 Err。
无正文时 session-loop 丢掉 kind、文案分类、Retry-After 和 usage，一律 Unknown fatal，429、5xx、超时和上下文超限都不会进阶梯。
首字节诊断会让「还没有正文的流中 Err」掉进同一条致命路径。
已经吐过字、思考或工具调用后再失败，会被收成正常 stop 或 tool-call：回合当成功，工具照执行，content_filter 和 refusal 也一样。
length 重试不撤回已提交的截断正文和已发出的 delta，下一轮用新 message id 再追加一条助手消息。
重试阶梯本身不会把同一条流上的工具调用打两遍。
溢出压缩的 60s 摘要等待不跟 abort 竞速；摘要失败会 fatal，盖掉用户取消，成功则会先改写对话。
收到 Stop 后消费循环不结束，状态机停在 Streaming，直到 EOF 或 60s 空闲超时，超时还可能盖掉原来的分类。
abort 和 fatal 的 turn-end 把 usage 写成 None；缓存拆分在生产路径上永远按 Included 算。
流前 Err、零事件的流中 Err、退避睡眠里的 abort、以及 fatal 的 ProviderError 收口是闭合的。
