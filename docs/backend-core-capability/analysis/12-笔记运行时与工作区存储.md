# 笔记运行时与工作区存储

> 日期：2026-10-13
> 范围：`conex-note-runtime`、`conex-workspace-store`（snapshot / updates / blocks / FTS / mirror / persist / commit）、`conex-doc-collab` 的 apply / hydrate / persist 边界、壳层 `note_*` 与 `StoreNoteBackend` 注入点。
> 只列现存问题。不记风格、行数、命名。问题同权。

## 能力结论

权威落盘是真的：`DocSession::apply` 把整树 CDCS（含 `text_snapshot`）写进 `workspace.db` 的 snapshot/updates，失败时内存树回滚。生产注入在库打开成功时是 `StoreNoteBackend`，不是 `MemoryNoteBackend`。UI 的 `note_apply_ops` 和工具的 `apply_md_fragment` / `apply_block_ops` 进同一张进程内会话表，不是两棵 Rust `DocSession` 互相整树覆盖。MD mirror 没有被做成 `get_md` 或第二写入口。

没接上的是「下一步能把这一步当真」：纸面按自己的文本基准发 `text_edit`，引擎按当前树钳制后提交整树快照；冷 `document_get_md` 对已落盘文档返回成功空串；删除不摘会话，缓存树能把已删文档写回去；`intent_id` 幂等表不过重启，collab 写路径根本不查；blocks/FTS 与权威不是一笔事务，文本撤销不更新投影；打开投影最多 200 块。库注释里的「≠ 存储完成」和这几条对得上，不是口号。

## 问题清单

### BC12-1 纸面文本基准与 DocSession 不是同一棵树，text_edit 打在已前进的权威上

- 现象：工具改过的块，用户下一次落盘仍按纸面「上次确认文本」算偏移。引擎不按纸面基准重放，而是把这对偏移用在当前权威文本上，越界的 `end` 被钳短而不是拒绝。结果写成新的整树快照。反向一样：工具 `get_md` 看不到纸面还没刷出的缓冲，按旧文再写，随后纸面差量打回来。
- 证据：`apps/crish-desktop/src/components/note-paper/useNoteTextPersistence.ts:245`（`oldText = lastPersistedText`）；`apps/crish-desktop/src/components/note-paper/noteTextEditOp.ts:34`；`crates/conex-doc-collab/src/text_engine.rs:784`（`e_idx = end.min(char_len)`）；`crates/conex-doc-collab/src/session.rs:468`（每次提交整树 CDCS）；`apps/crish-desktop/src/api/noteApplyOpsIpc.adapt.ts:39`（只有前端 apply 成功才 `notifyNoteDocWritten`）。Rust 写路径无对应通知：`crates/conex-note-runtime` 内没有该总线。
- 机制：同进程只有一棵 `DocSession`（`store_hydrate.rs:35` 的 `session_handle`，`note_apply_ops` 与 `apply_md_fragment` 都走它）。分叉的是纸面投影 + `lastPersistedText`。工具写只动 Rust 树和 SQLite，不刷新纸面基准。`computeTextEditOp` 的 `[start,end)` 相对旧字符串；`simulate_char_edit` / `char_range_to_bytes` 把 `end` 钳到当前长度后照样 splice。`emit_commit` 把 splice 之后的整棵树写成结构帧，下一次 hydrate 认这棵树。
- 影响：同一块上，工具插入的前缀会被用户的后缀编辑切碎（例如权威已是 `Xhello`，纸面仍按 `hello` 在偏移 5 插入，得到 `Xhell!o`）。纸面未刷出的键击对工具不可见，工具的整段替换再被后到的差量盖掉。不是两棵 Rust 会话抢 CAS，CAS 挡不住这条路径。

### BC12-2 冷 document_get_md 对已落盘文档返回成功空串

- 现象：进程内还没打开过该 doc 的会话时，`document_get_md` 返回 `ok: true, md: ""`。库里已有 snapshot 也不读。大纲在无会话时会退到投影表，全文不会。
- 证据：`crates/conex-note-runtime/src/store_backend_query.rs:49`（map 未命中直接 `Ok("")`，不 `session_handle`）；同文件 `:62`（空根也是空串）；`crates/agent-tools/src/tools/note_document_get_md.rs:79`（`Ok(md)` 即 `ok: true`）；对照 `crates/conex-note-runtime/src/store_backend.rs:311`（大纲无会话走 `build_outline_from_store`）。
- 机制：会话表只在写、hydrate、import 提案时填充。读全文被写成「无热会话 = 空文档」，与「无会话就从 snapshot hydrate」不是一条路径。工具契约写的是即时 S(树)，调用方分不清「真的空」和「还没把权威载入」。
- 影响：重启后、或 UI 还没 hydrate 过该 doc 时，代理以为笔记是空的，接着 `apply_md_fragment`。写路径会 `session_handle` 载入真树再插入（`store_apply_md.rs:111`），旧块还在，新的「全文」叠在后面。用户看到双份，不是替换，也不是报错。

### BC12-3 删除不摘会话，缓存树把已删文档写回

- 现象：`note_document_delete` 清掉 snapshot、updates、blocks、FTS 之后，进程里的 `DocSession` 还在。下一次工具或 UI 再写同一 `doc_id`，用的是删除前的内存树，并把这棵树作为新权威提交。
- 证据：`apps/agent-workbench/src-tauri/src/note_commands_document.rs:135`（只 `delete_document`，不 `remove_session_for_cold`）；`crates/conex-note-runtime/src/store_hydrate.rs:39`（map 命中直接返回，不重新 `load_doc`）；`crates/conex-workspace-store/src/persist_plugin.rs:90`（`expect_rev = Some` 时，行不存在走 INSERT，`WHERE rev = ?` 只约束 UPDATE）；`crates/conex-doc-collab/src/session_apply.rs:251`（`full_rebuild: false`，diff 只有本批 upsert/remove）。
- 机制：CAS 只在 `doc_meta` 行还在且 rev 不符时冲突。删除把行删掉后，INSERT 分支恒成功，期望版本被跳过。提交的结构帧是缓存树的整树，不是空文档加这一笔。投影只应用本批 diff，缓存里那些没出现在本批 upsert 里的旧块回到 snapshot，不回到 `blocks` / `blocks_fts`。
- 影响：用户删掉的笔记会在下一次代理写入或纸面落盘时复活。搜索和 `query_blocks` 看不到复活块，hydrate 看得到。权威和投影从此分叉。

### BC12-4 intent 幂等表不过重启，并发下同进程也会双插；collab 写路径不查这张表

- 现象：`send_to_note` / `apply_md_fragment` 的同 `intent_id` 第二次调用，只在本进程、且第一次已经写入缓存之后才返回 `idempotent`。重启后再送同一 intent 会再插一块。`note_apply_ops` 收 `intent_id` 只回显，不参与去重。同一 doc 上两个并发的相同 intent 也会都写进去。
- 证据：`crates/conex-note-runtime/src/store_backend.rs:138`（`intents: HashMap`，注释写明不随 `workspace.db` 复活）；`crates/conex-note-runtime/src/store_apply_md.rs:95`（查表后锁释放）与 `:236`（`commit_ops` 成功后才插入）；查表键只有 `intent_id`，不含 `doc_id`；`crates/conex-note-runtime/src/store_backend_apply.rs:47`（`apply_collab_ops_json` 无幂等参数）；`apps/agent-workbench/src-tauri/src/note_commands_apply.rs:200`（`intent_id` 只塞进响应 JSON）。
- 机制：幂等检查在 per-doc 锁之外。两个调用可以同时看到缓存未命中，再在 doc 锁上排队，各自 `commit_ops`。MD 解析每次分配新块 id，第二次不是 IdConflict，是再插一段。collab wire 的重试连这张内存表都不看；文本 op 的块 id 不变时，重放会在同一区间再 splice 一次（`end` 仍落在加长后的文本里）。
- 影响：超时重试、进程重启后的 send_to_note、UI apply 重放，都会多出一块或把同一段文字再写一遍。调用方看到的 `idempotent: true` 不能当成跨进程保证。库自己写了「杀进程可双插」，生产路径仍把这张表当幂等实现。

### BC12-5 权威提交与 blocks/FTS 不是一笔事务，文本撤销不更新投影

- 现象：`commit_ops` 先在 `DocSession::apply` 里提交 snapshot/updates，再另开事务写 blocks、FTS、refs、mirror lag。后一步失败或进程死在两笔之间，权威已前进，索引没有这批块。`note_undo_text` / `note_redo_text` 只 `emit_commit`，投影一行都不改。
- 证据：`crates/conex-workspace-store/src/projection.rs:209`（`session.apply` 成功后才 `index_after_apply`）；`crates/conex-workspace-store/src/persist_plugin.rs:155`（`on_committed_expect` 自己 `tx.commit`）；`crates/conex-doc-collab/src/session_undo.rs:175`（`text_undo` 的 `emit_commit`）；`crates/conex-note-runtime/src/store_backend_apply.rs:187`（`undo_text_inner` 成功后直接返回，无 `apply_projection_diff`）。同事务里的 FTS 与 blocks 行是一起写的（`fts_index.rs:25` 与 `:50`），脱节的是这对表相对权威，不是这两张表彼此。
- 机制：投影 diff 是增量且 `full_rebuild: false`。缺了的 upsert 不会在下次成功提交时补上，除非那次 diff 又碰到同一块。撤销改的是 `text_snapshot` 并写入 CDCS，`blocks.plain_text` 和 `blocks_fts` 仍是撤销前的文本。打开时没有按 snapshot 重建投影的步骤。
- 影响：崩溃或索引失败后，hydrate 看得到新块，`query_blocks` / 英文 FTS 看不到。撤销之后搜索仍命中旧句子，代理按搜索结果改的是已经不在权威里的文本。重试失败的 apply 会再插一批新 id（BC12-4 的缓存还没写入），第一批块留在树里但永远不进索引。

### BC12-6 打开投影最多 200 块，且能在父节点中间切断；query 对照轨不是这棵树

- 现象：`note_document_hydrate` 默认走 DocSession，但条数夹到 1..=200，没有续页。DFS 数满就停，父块可以出现、后半子树不出现。`prefer_query=true` 时块文本是检索摘要，`rev` 被写成 0 或 1，不是会话 rev。`note_query_blocks` 把后端错误一律改成 `note.execution_unknown`。
- 证据：`apps/agent-workbench/src-tauri/src/note_commands_hydrate.rs:93`（`clamp(1, 200)`）；`crates/conex-note-runtime/src/store_hydrate.rs:178`；`crates/conex-note-runtime/src/hydrate_projection.rs:109`（`out.len() >= limit` 即停，不再走剩余兄弟）；同文件 `:106`（`index` 是扁平 DFS 计数，不是父内序号）；`note_commands_hydrate.rs:194`（query 路径 `rev = 空?0:1`，文本用 `hit.snippet`）；同文件 `:50`（`map_err` 成 `ExecutionUnknown`）。
- 机制：权威树在热会话里是全的，IPC 投影不是。`truncated` 有字段，命令没有 offset。纸面按返回的块列表当打开结果（Strict 列表是这块数组的扁平序）。query 路径的 snippet 在 FTS 上是 32 字窗口（`query_blocks_sql.rs:40`），当块正文用会丢字。`execution_unknown` 的契约是「写执行结果未知、不要自动重试」；用在只读查询上，非法参数和索引错误变成同一种终态。
- 影响：超过 200 块的笔记打开后，纸面和后续按可见块算出的编辑都看不见被截掉的子树。那些块仍在权威里（和 BC12-1 叠在一起时，用户在可见块上的编辑打到完整树上，被截掉的块还在，但用户不知道）。对照轨若被打开，修订号和正文都是假的。查询失败会被当成写状态不明。

### BC12-7 apply_md 在进权威树之前丢掉表格和部分嵌套

- 现象：工具把 GFM 表、脚注定义、frontmatter、引用里的嵌套块写进笔记时，权威树上没有对应结构。表变成一段纯文本段落，脚注和 frontmatter 不建块。`lossy` 会出现在工具结果里，但树里已经没有可 hydrate 回来的结构。
- 证据：`crates/conex-note-runtime/src/store_apply_md.rs:179`（`apply_md_fragment` → `conex_md_ast::apply_md_fragment`）；`crates/conex-md-ast/src/parse_mdast.rs:268`（引用内嵌套「暂不二次展开」）；同文件 `:274`（表按 Paragraph 降级，`BlockKind::Table` 未入 IR）；同文件 `:295`（definition/footnote 不建块）；`crates/conex-doc-collab/src/ir.rs:14`（`BlockKind` 无表）。lossy 映射在 `store_apply_md.rs:39`，不恢复结构。
- 机制：collab IR 的 kind 集合小于 Markdown。运行时把降级后的 ops 交给 `commit_ops`，CDCS 存的是降级树。hydrate 按 CDCS 可逆，逆不回降级前的节点。
- 影响：代理写入的表、脚注、引用内的列表，重新打开或 `get_md` 不再是原来的结构。调用方若只看 `inserted > 0` 会当成写成功；lossy 有报告，但没有第二条路径把结构补进权威。

### BC12-8 snapshot 合并保留全部历史全树帧，打开要读完整个 blob

- 现象：每次提交都追加一帧完整 CDCS，不是增量 op。pending 达到 100 或调用 `flush_doc` 时，旧 snapshot 整段再包进新 snapshot，历史帧不丢掉。hydrate 只采用最后一帧结构，但必须先把整个 blob 读进内存再跳过前面的帧。
- 证据：`crates/conex-doc-collab/src/session.rs:468`（每笔都 `encode_structure_payload` 整树）；`crates/conex-workspace-store/src/lib.rs:128`（阈值 100）；`crates/conex-workspace-store/src/persist_plugin.rs:248`（`append_chunk` 旧 snapshot，再追加每条 update，然后删 updates）；`crates/conex-doc-collab/src/structure_codec.rs:111`（非 CDCS 帧跳过，最后一帧结构胜出）；`persist_plugin.rs:34`（`load_doc` 读出整段 `blob`）。
- 机制：压缩不是「折叠成最新树」，是 length-prefix 拼接。第二次压缩把第一次的整包当作一个外层帧。外层帧不是 CDCS，解码时跳过，所以最新树还在，字节数却是历代全树之和。`snapshot_tick` 在 `emit_commit` 里恒为 false（`session.rs:482`），自动压缩只靠条数阈值，不会把 blob 换成单帧最新树。
- 影响：长寿命笔记的 `doc_snapshots.blob` 随编辑次数线性涨（每笔都是当时的整树 JSON）。打开该 doc 的内存和 IO 跟历史编辑量走，不跟当前树大小走。涨到 SQLite 读不进或 hydrate 分配失败时，文档打不开；在那之前读写都变慢。这不是「最新结构不可逆」，是打开成本没有上界。

### BC12-9 workspace.db 打开失败时笔记链保持 None，应用照常就绪

- 现象：笔记库打不开不阻断启动。之后每次 run 把 `note_backend` 设成 `None`，`note_*` 命令返回 `note.unwired`。命令本身已注册，不是漏注册。
- 证据：`apps/agent-workbench/src-tauri/src/db_setup.rs:86`（失败记日志并返回 `None`）；`apps/agent-workbench/src-tauri/src/main.rs:770`（`None` 分支为空，随后 `:777` `mark_db_ready`）；`apps/agent-workbench/src-tauri/src/run/run_launch.rs:925`（`try_backend()`，失败即 `None`）；`crates/session-loop/src/loop/loop_runner.rs:163`（原样放进 `tool_ctx`）；`apps/agent-workbench/src-tauri/src/main.rs:461`（`note_document_apply_md` 等已进 `command_registry!`）。子代理走同一个 `run_task_impl`（`run_core.rs:1114`），不会另注入一套后端。
- 机制：设计是打开失败就 unwired，而不是换成内存后端。就绪握手不区分「会话库好了、笔记库没有」。工具返回 `note_backend_unwired`，不是假成功。
- 影响：磁盘满、路径不可写、迁移失败时，对话主链仍跑，笔记工具和纸面命令整段不可用，直到重启并且打开成功。没有把笔记库失败升成 run 失败。

## 已核对闭合或不是问题

- 同进程 UI 写与工具写共用 `StoreNoteBackend.sessions`。第二棵从空 blob hydrate 的 `DocSession` 在行还在时会被 CAS 拒绝（`persist_plugin.rs:115`，`document_ops_tests.rs:457` 锁的是这条）。BC12-1 / BC12-3 是这条保护盖不住的路径，不是「两棵 Rust 会话 LWW」。
- `DocSession::apply` 在 `on_committed` 失败时回滚内存树、文本和 rev（`session_apply.rs:105`，`emit_commit` 用 `expect_rev = rev - 1`）。单笔权威提交不是半树。不原子的是后面的投影（BC12-5）。
- hydrate 对已写入的 CDCS 可逆：最后一帧结构含 `text_snapshot`，冷文本经 `init_block_with_text` 登记，下次编辑会从快照重新灌进 YText（`session_hydrate.rs:56`，`text_engine.rs:185`）。yrs 二进制 pending 故意不回放；跨进程 undo 栈清空。这是文本内容可恢复，不是协作史可恢复。
- MD mirror 不是读路径，也不是第二写入口。`document_to_md` 不读文件；`import_mirror_proposal` 只产 op 或冲突，不 `apply`（`mirror_import.rs:151`）。生产 `commit_ops` 不调用 `commit_ops_with_mirror`，所以写成功不会自动刷新 mirror 文件，lag 会涨。这是导出没接上，不是把 mirror 当权威读。OS watcher 没有产品装配，和库注释一致。
- 命令已注册：`main.rs:461` 与 `command_manifest.rs` 的 `note_document_*` / `note_apply_ops` / `note_undo_text` / `note_redo_text` / detect / import。打开成功时 `run_launch.rs:925` 和 `engine_build.rs:1553` 注入的是 `Arc<StoreNoteBackend>`。`blocks` 与 `blocks_fts` 在同一次 `reindex_block_conn` 里更新，不是这两张表各写各的。
- 新建文档初始 rev 0，首笔 `expect_rev = 0` 可以提交（`note_documents.rs:152`）。这是已修的 CAS 首写冲突，不是现存问题。

## 覆盖与未覆盖

- 已读：`conex-note-runtime/src` 全部分模；`workspace-store` 的 `lib` / `persist_plugin` / `projection` / `fts` / `fts_index` / `query_blocks` / `mirror_import` / `mirror_export` / `note_documents`；`doc-collab` 的 `session_apply` / `session_hydrate` / `session_undo`（文本撤销）/ `structure_codec` / `persistence` / `text_engine` 的编辑与钳制；壳层 `note_runtime`、`note_commands*`、`db_setup`、`run_launch` 注入点、`engine_build` 补注入、`loop_runner` 透传。纸面只追了「谁产生打到这棵树上的 op、谁不收到工具写通知」。
- 未覆盖：`conex-md-ast` 除 apply 降级以外的往返；FTS CJK `instr` 的召回质量；CAS blob 附件与 GC；mirror 三路 diff 的块匹配是否漏块；协作双 peer（`harness`）不是这条单进程写路径。agent-tools 默认拒写表按纪律不审。

## 给主控的摘要

1. 真后端在库打开成功时已注入；`note_*` 已注册。打开失败则整段 `None`，应用仍就绪（BC12-9）。
2. UI IPC 与工具共用一棵 Rust `DocSession`；第二棵陈旧 Rust 会话在行还在时会被 CAS 拒绝。
3. 纸面另有文本基准，工具写不通知它；`text_edit` 按旧偏移打在新树上，`end` 被钳制，整树快照把盖写结果变成权威（BC12-1）。
4. 冷 `document_get_md` 对已落盘文档返回成功空串，随后写入会把「新全文」叠进真树（BC12-2）。
5. 删除不摘会话；缓存树用无条件 INSERT 复活文档，投影只有本批 diff（BC12-3）。
