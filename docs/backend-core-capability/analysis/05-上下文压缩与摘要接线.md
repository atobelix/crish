# 上下文压缩与摘要接线

> 日期：2026-10-13
> 范围：`crates/conex-compaction/src/` 全库；`session-loop` 的 `compaction_dispatch`、`summary_coordinator`、`summary_dispatch`、`stage_summary`（只追与摘要调度的关系）、`cache_tracker`、`attachment_budget`、`attachment_truncation`。摘要离开调度器之后的写库回调、压缩块、下一回合读回，证据落在调度侧与壳层装配侧。`conex-db` 表实现不在本文重审。

## 能力结论

同一次 run 内，同步摘要成功会把 markdown 放进内存对话，本 run 后续回合看得到这段摘要。默认配置要求 LLM 摘要：摘要失败或没有摘要器时不替换对话、不计入本 run 压缩次数。

摘要结果离开调度器之后有两个落点。本 run 内存对话被 `plan.messages` 替换。壳层给会话级协调器装了默认回调，后台成功时调用 `update_compression_block_summary`，写入块表的 `summary_json` / 状态 / 尝试次数。调度侧每次触发仍把单次回调传成 `None`，`rendered_markdown` 没有交给这个回调，链上那条摘要消息也不再改写。`last_outcome` 只留在协调器里，没有生产读者把它塞回对话。注释里的「未接线回调时只落日志」对当前壳层已经过时；「后台成功自动替换 stub」没有实现。

下一轮由桌面发起的 run 以前端从会话正文装出的 history 为准。压缩不写 `MessageEnd`，会话正文仍是压缩前的消息，模型再次看到全文。手动压缩只替换 `SessionHistoryCache`，桌面下一条用户消息仍走同一条正文优先的读路径。空闲续 run 才回退缓存，并且不带 `context_window`。

附件预算函数停在模块内。回合准备不调用它，入站结构也没有 `attachments` 字段。触发线是 `window - reserve`，85% / 95% 水位不驱动压缩。主会话没有 `context_window` 时预检直接返回。一旦真正压缩，保留量是约 2 万 token 的尾部，函数没有「已在预算内则原样返回」。

## 问题清单

### BC05-1 压缩进了本 run 内存和块表索引，下一轮桌面 run 读回全文

- 现象：同步摘要成功后，本 run 内模型看到的是摘要 markdown 加保留尾部。后台摘要完成后，块表索引更新了，链上消息仍是压缩当时的正文（同步成功是 markdown，stub 路径是占位句）。下一条桌面用户消息重新装入会话正文里的原始消息，压缩结果不在其中。空闲续 run 读缓存，缓存里若是 stub，续 run 继续把 stub 当历史，并且不再预检压缩。
- 证据：`crates/session-loop/src/loop/compaction_dispatch.rs:487` 用 `plan.messages` 替换 `state.conversation`，同函数 `:535-539` 用 `summary_is_llm` 区分 committed / awaiting，`:558-622` 只在非 LLM 摘要时登记后台任务，且 `try_trigger` / `try_spawn` 的回调参数是 `None`。同文件没有 `record_message`。`crates/session-loop/src/loop/handlers/mod.rs:248-277` 的 `record_message` 才发 `MessageEnd`。`apps/agent-workbench/src-tauri/src/run/run_core.rs:465-479` 的默认回调只调用 `update_compression_block_summary`，参数是 `summary_json` 与 attempts，没有 `rendered_markdown`。`crates/session-loop/src/loop/summary_coordinator.rs:122-123`、`:213-223` 把结果写入 `last_outcome` 再交给默认回调；生产代码没有第二处读取 `last_outcome` 来替换对话消息。`crates/session-loop/src/loop/compaction_dispatch.rs:404-411` 只有块 id 从对话消失才清除 `pending_summary_retry`。`crates/session-loop/src/loop/handlers/stream_error_recover.rs:109` 写明 stub 会在后台成功后自动替换。`apps/agent-workbench/src-tauri/src/run/run_history.rs:416-422` 在前端 history 非空时选用 Frontend。`apps/crish-desktop/src/api/chat-bridge/streamSession.ts:172-177`、`:224` 从会话正文 `loadSessionBody` 装 history 并下发。`apps/agent-workbench/src-tauri/src/run/run_launch.rs:1389-1395` 手动压缩只 `session_history.store`。`apps/agent-workbench/src-tauri/src/run/run_idle.rs:1239-1240` 空闲续 run 的 history 与 context_window 都是 `None`；同文件 `:1349` 在 run 收口把当时的 outcome 消息写入缓存。`crates/orchestrator/src/events.rs:472-476` 在压缩结束事件之后写的是压缩块行。
- 机制：调度器把「本 run 对话替换」和「块表索引更新」当成两段。块表回调不回写内存消息，也不产生一条新的会话消息。桌面下一 run 的 history 来自会话正文，正文来自消息事件，压缩事件不改这条正文。`resolve_history_source` 在正文 history 非空时不读缓存，所以缓存里的压缩序列到不了这条桌面路径。空闲续 run 不带 history，才会读到缓存；它同时不带窗口，`resolve_context_budget` 对非子代理返回 `None`（`run_history.rs:447-453`），预检在 `compaction_dispatch.rs:195-197` 直接返回。stub 的块 id 一直留在对话里，待重试快照不会因为后台写库成功而清除；默认 `LlmRequired` 不走这条 stub 登记（见已核对闭合），豁免落下 stub 时才会每到用户消息边界再触发。
- 影响：跨桌面 run 的压缩对模型不可见，超窗对话会按全文再次进入下一 run，并可能再次压缩。块表里的 `summary_json` 与模型实际读到的文本分叉。注释中的自动替换不发生，stub 若落下就一直留在本 run 与缓存续 run 的上下文里。目标恢复若另读块表 `nextSteps`，那是另一条读路径，不改变模型提示词。

### BC05-2 会话级协调器不经过窗口尝试护栏

- 现象：低功耗窗口护栏只装在 run 级 `SummaryDispatch` 上。生产 run 始终注入会话级协调器，`try_trigger` 不查这道护栏。默认 `compact_require_llm=true` 且 `compact_allow_stub_fallback=false` 时，摘要失败不落 stub，本条不会在默认失败路径上发出后台摘要。豁免放开、对话里留下 stub 之后，每个 episode 结束仍可在下一条用户消息边界再次打摘要，窗口内 8 次 / 30 分钟的累计上限不作用在这条路径上。
- 证据：`crates/session-loop/src/loop/loop_options.rs:64-65` 默认要求 LLM 且不允许 stub 回退。`apps/agent-workbench/src-tauri/src/run/run_launch.rs:924` 始终 `summary_coordinator = Some(...)`。`crates/session-loop/src/loop/loop_runner.rs:183-192` 只对 `summary_dispatch.set_retry_guard`，注释写明协调器侧护栏由后续壳层批次装配。`crates/session-loop/src/loop/summary_coordinator.rs:159-197` 的 `try_trigger` 只做单飞和全局并发上限，没有 `SummaryRetryGate`。`crates/session-loop/src/loop/summary_dispatch.rs:12-14` 写明跨 episode 成本由该护栏约束，并点名 `coordinator.try_trigger`。全局并发上限在 `summary_coordinator.rs:187-196`，达到上限时本次触发被忽略，后续 run 会再触发。
- 机制：两套触发面。run 级 `try_spawn` 先问护栏；生产走协调器，单次回调是 `None`，于是落到协调器自带的默认写库回调，护栏不参与。单飞只挡住「任务还活着」的重复触发。任务结束后，只要 stub 消息还在（BC05-1），`maybe_retry_pending_summary` 会再组一份任务。单 episode 内部仍有 `MAX_SUMMARY_ATTEMPTS`（含同步那一次），episode 之间不再受窗口累计约束。
- 影响：豁免路径上，同一批被丢弃消息可以在用户消息边界反复送去摘要。默认失败路径不落 stub，不会因此连打；护栏与生产触发面已经分叉，注释里的约束没有落在实际调用上。

### BC05-3 压缩代数固定为 1，会话元数据代数与缓存代数各算各的

- 现象：每次 AgentMessage 压缩计划的 `generation` 都是 1。块 id 形如 `compacted-summary-1-{fold}`。会话元数据在每条压缩结束事件上把 `last_compaction_generation` 加一，引擎不读这个值。应用压缩时缓存跟踪先自增，再被 `apply_external_generation(1)` 拨回 1。桌面下一 run 若重新装入不含摘要链的正文，链长归零，块 id 再次成为 `compacted-summary-1-1`。
- 证据：`crates/conex-compaction/src/engine.rs:361-371` 注释写明本轮以 1 占位、应由 `SessionContextMeta.last_compaction_generation` 注入，代码是 `let generation: u32 = 1`。`crates/session-loop/src/loop/compaction_dispatch.rs:505-507`、`:515-516` 用 `plan.generation` 校准跟踪器并拼块 id。`crates/orchestrator/src/session.rs:209-226` 把 `last_compaction_generation` 写成会话级代数，按压缩事件加一。`crates/orchestrator/src/events.rs:472-473` 与 `crates/orchestrator/src/blocks.rs:1-5` 对同一 `(session_id, block_id)` 使用 `INSERT OR IGNORE`（表语句本身不在本文展开）。`apps/agent-workbench/src-tauri/src/run/run_launch.rs:1424` 手动压缩使用同一 id 格式。
- 机制：代数有三处来源。引擎写死 1；会话元数据按事件累加；块行兜底还可以按事件条数计数（`blocks.rs:11-13` 的说明）。应用压缩时的「外部代数校准」把缓存跟踪对齐到引擎的 1，元数据上的累加值没有回到引擎。桌面读路径不保留链消息时（BC05-1），下一次成功压缩的 fold 又从 1 开始，块 id 与已有行冲突。`INSERT OR IGNORE` 保持首行，后一次的丢弃集合与摘要状态不会靠这次插入更新该行。同一次 run 内若链消息还在内存里，fold 会递增，id 不撞；跨桌面 run 的重置才会撞。
- 影响：第二次及以后的跨 run 压缩在块表上可能仍指向第一次的丢弃集合与摘要。缓存跟踪的压缩代数停在 1，与会话元数据的累计代数不一致，压缩后的前缀签名按这个被拨回的代数解释。

### BC05-4 附件预算函数没有进入回合准备，桌面附件到不了这道钳制

- 现象：`clamp_attachments_to_budget` 与首尾截断函数只在自身模块和测试里。回合准备的步骤是控制、压缩、追加、转向、预检，没有附件钳制。桌面发送会带 `attachments`，运行入站结构没有这个字段。
- 证据：`crates/session-loop/src/lib.rs:39-42` 写明消费接线留到后续轮次。`crates/session-loop/src/attachment_budget.rs:31` 定义 `clamp_attachments_to_budget`，仓库内调用点只在该文件测试。`crates/session-loop/src/attachment_truncation.rs` 的首尾截断只被附件预算模块使用。`apps/crish-desktop/src/api/chat-bridge/streamSession.ts:216-217` 在有附件时把 `attachments` 放进启动参数。`apps/agent-workbench/src-tauri/src/run/run_launch.rs:380-431` 的 `RunTaskOptions` 有 history、context_window、content、has_images，没有 attachments。`RunTaskOptions` 未拒绝未知字段，多出来的键在反序列化时被丢掉。壳层里出现的 `attachments: Vec::new()` 是转向队列条目，不是这套上下文附件预算的消费。
- 机制：预算函数是纯函数，没有任何生产调用把它接到 `prepare_turn`。即便回合准备补上调用，当前 IPC 结构也接不住桌面已经发出的附件数组，函数的输入在边界上就是空的。
- 影响：附件体积不会按上下文预算被截断或丢弃并告警。桌面附上的上下文附件不会进入这道护栏，也不会进入回合对话。

### BC05-5 估算与真实窗口脱节，该压不压，或一压就收到约 2 万 token

- 现象：主会话没有入站 `context_window` 时不做预检、不做输出钳制。有窗口时，触发线是 `window - reserve`（默认 reserve 16384），85% / 95% 分类不参与。真正调用压缩函数时，不判断「当前已经低于目标预算」，切割按保留最近约 20000 token 与最少 2 个完整回合执行。窗口远大于 2 万时，刚超过触发线就会把历史收到约 2 万。窗口小于 reserve 时，触发预算被减成 0，任意非负估算都算超限；紧急收紧要求预算不少于保留量，因此被跳过，计划仍按约 2 万的尾部应用。紧急路径即使跑起来，也只截保留段里的工具结果文本，普通文本块保持原样，截完仍超预算的 token 数会写进成功计划。输出钳制在可用额度低于 256 时返回调用方原来的 `max_tokens`。
- 证据：`apps/agent-workbench/src-tauri/src/run/run_history.rs:442-453` 两者皆缺时预算为 `None`。`crates/conex-types/src/context.rs:29-35` 默认窗口 64000、reserve 16384、safety 4096；`assemble_context_budget`（`run_history.rs:428-432`）只覆盖窗口，reserve 仍是 16384。`crates/session-loop/src/loop/compaction_dispatch.rs:210-213`、`:256-258` 用 `should_compact`，条件是 `estimate >= budget_tokens`（`engine.rs:741-742`）。`apps/agent-workbench/src-tauri/src/run/run_core.rs:764-767` 写明 85% / 95% 键本策略面不消费。`crates/conex-compaction/src/thresholds.rs:23-28` 写明 Critical 不驱动独立压缩。`crates/conex-compaction/src/tool_output.rs:316` 的 `classify_after_truncation` 仅被该文件测试调用。`crates/conex-compaction/src/engine.rs:233-234` 文档写预算内原样返回；`compact_agent_messages_with_stub_policy` 从 `:305` 起直接找切割点，没有这道比较。`crates/conex-compaction/src/cut_point.rs:11` 默认保留 20000。`engine.rs:472-481` 仅当 `budget_tokens >= keep_recent_tokens` 且压缩后仍超预算才进紧急预检。`engine.rs:534-546` 紧急收紧把最少回合放到 1 再放到 0。`engine.rs:575-637` 只改 `ToolResult` 的 text，然后返回当前 token 数，没有「仍超预算则放弃」。`compaction_dispatch.rs:63-77` 可用额度小于 256 时返回 requested。`apps/crish-desktop/src/api/chat-bridge/historyMessages.ts:21`、`:103-112` 另用 200000 的历史预算做锚点加尾部截断，与模型窗口无关。`crates/conex-compaction/src/tokens.rs:13-41` 把每个 ASCII 分隔符算 1 token，每个非 ASCII 字符算 1 token。同文件 `:8` 的图片常量注明当前无图片块，`:62-76` 的消息计数只加块，不加 `content` 与 metadata。`crates/session-loop/src/hydrate.rs:81-87` 水合把 metadata 清掉，usage 不进入下一 run 的消息。`thresholds.rs:149-155` 在 usage 时间戳早于压缩边界时整段 usage 作废。`run_idle.rs:1065-1075` 阶段里程碑只用消息块启发式合计，不加算系统提示与工具前缀，窗口缺失时用默认 64000。`run_launch.rs:1312-1332` 手动压缩有「目标低于 reserve + keep_recent 则拒绝」的下限；自动预检没有这道下限，也没有先调用 `should_compact` 的手动路径对照——手动路径在 `:1368` 直接压缩，不先问是否已经低于预算。
- 机制：预检闸门和压缩函数的预算语义不一致。闸门回答「要不要压」，函数回答「从哪一刀切到保留尾部」。文档中的预算内早退没有进入函数体，短对话测例能通过是因为切不到 20000 token 的保留段，切割点为空。小窗口把 `window - 16384` 减成 0 之后，闸门常开，紧急预检因 0 小于 20000 关闭，成功计划的 `tokens_after` 仍可以大于模型窗口。估算偏大（分隔符、工具 JSON、思考块）会提早压缩；估算偏小（CJK 按一字一 token、图片不计入、水合丢掉 usage 后下一 run 只剩启发式）会晚压或不压。前端 20 万截断与引擎触发线是两套数。
- 影响：目录没有给出窗口的主会话会把截断后的历史原样送进模型。大窗口会话在刚超触发线时丢掉远多于「刚挤进窗口」的历史。小窗口会话可以在仍然超窗的情况下被记成压缩成功，本 run 自动压缩默认只有 1 次（`loop_options.rs:61`），预检不会再补一刀。紧急收紧到 0 个最近回合时，靠近切点的用户回合会进入丢弃段。输出侧在已经没有余量时保持原 `max_tokens`，超窗请求的生成额度不被缩小。

### BC05-6 提示词要求 criticalContext 为数组，进模型的 markdown 只认字符串

- 现象：摘要提示词要求 `criticalContext` 是数组，并要求路径、符号、命令、错误串逐字保留。校验只要求该键存在，不要求类型。渲染用 `as_str`，数组得到空串。同步校验通过后，这段空的 Critical Context 被当成 LLM 摘要写入链消息，原文按成功压缩丢弃。
- 证据：`crates/conex-compaction/src/ai_summary.rs:100`。`crates/conex-compaction/src/summary_document.rs:71-92` 只把 `droppedIds` 检查为数组。同文件 `:95-97` 的 `string_field` 取不到字符串就是空串，`:241-242` 用它渲染 Critical Context。`engine.rs:395-405` 在校验通过时 `summary_is_llm=true`，摘要文本是 `summary_to_markdown` 的结果。`summary_document.rs:112` 一带的 decisions 对对象和字符串都有渲染，criticalContext 没有对应分支。
- 机制：提示词、校验、渲染三套契约不一致。模型若按提示词输出数组，文档仍是合法 Schema V1，markdown 投影把这一节印成空标题。链上消息放的是投影，不是原始 JSON。块表若随后写入 `summary_json`，模型读不到那份 JSON（BC05-1）。思考块在构造摘要提示时被跳过（`ai_summary.rs:33-38`），估算却把思考块算进 token（`tokens.rs:68`），这一节与 BC05-5 的估算偏差叠在同一条摘要链上。
- 影响：按提示词诚实输出的关键上下文，在模型下一回合读到的摘要里是空的，被折叠的原文已经不在保留段中。这是同步成功路径上的静默丢字段，默认 `LlmRequired` 会把这种「校验通过但关键节为空」当成已压缩。

## 已核对闭合或不是问题

- 默认摘要失败不当成已压缩。`compaction_dispatch.rs:349-368` 在 `llm_unavailable` 时不调用 `apply_compaction`、不增加计数，并发出 runtime-intervention。溢出阶梯默认同样不落 stub，直接 fatal（`stream_error_recover.rs:104-106`）。壳层没有改写 `compact_require_llm` / `compact_allow_stub_fallback`。豁免打开后的 stub 替换是另一条路径，见 BC05-2。
- 同步 LLM 成功时，本 run 的 `plan.messages` 含 markdown 链消息（`engine.rs:399-458`），`apply_compaction` 替换对话后，同 run 后续回合读的是这份对话。

## 给主控的摘要

1. 同 run 同步摘要成功会进入内存对话；默认失败不替换、不计数，不当成已压缩。
2. 后台成功只更新块表 `summary_json`。调度侧回调参数是 `None`，壳层默认回调不接收 `rendered_markdown`，也不改链上消息。
3. 「只打日志」对当前壳层已过时；「后台成功自动替换 stub」没有实现，`last_outcome` 无生产读者。
4. 下一轮桌面 run 用会话正文 history，压缩不写 `MessageEnd`，模型再次看到全文。手动压缩只换缓存，同一读路径。
5. 空闲续 run 读缓存且 `context_window` 为 `None`，缓存若是 stub 就继续用 stub，并且不再预检。
6. 窗口尝试护栏只挂在 run 级调度器。生产走协调器。默认不落 stub，所以默认失败不会连打；豁免落下 stub 后，块 id 还在，待重试不会清除。
7. 引擎代数恒为 1，应用时把缓存代数拨回 1。会话元数据另按事件加一。跨桌面 run 块 id 会再撞 `compacted-summary-1-1`，插入忽略旧行。
8. 附件预算函数未进 `prepare_turn`。`RunTaskOptions` 没有 `attachments`，桌面附件在入站被丢掉。
9. 触发线是 `window - reserve`，不是 85%。无窗口则主会话不预检。函数没有预算内早退；一压保留约 2 万 token。小窗口可把预算减成 0，紧急截断跳过，普通文本不截，仍可超窗并当成功。`criticalContext` 提示词要数组，markdown 只渲染字符串，该节会空，原文仍被丢掉。
10. 旧 Message 压缩仍挂在 `core_compact_messages`，回合与 `/compact` 不走它。工具配对在两侧都在列表里时有闭包保护。压缩后签名已在 `apply_compaction` 捕获。阶段总结会进下次系统提示，不回放压缩链。
