# 控制停止与转向

> 日期：2026-10-13
> 性质：只读审查。问题同权，不按优先级砍项。
> 范围：`crates/session-loop/src/control.rs`、`safe_point.rs`、`steering/`、`freeze.rs`、`retraction.rs`、`checkpoint.rs`。判定停止、冻结、恢复是否生效时，沿调用链核对了壳层 `run_control` / `run_idle` / `retraction_commands`、编排器事件队列与子代理强停、以及 shell 工具对中止令牌的消费。系统地图只作线索。

## 能力结论

协作停止（L2）不掐断 provider，这一点与「等安全点、endReason=stopped」一致，桌面 Stop 也不再成对发送 `core_cancel_run`。强停（L3）的生产分叉在工具侧：界面路径会置位 run 级 `AbortSignal`，执行器据此丢掉工具 future，但工具看到的 `AbortToken` 是另一只从未 `abort()` 的令牌；shell 又把 `kill_on_drop` 关掉，只在令牌已中止时杀进程。只入队、不打信号的强停（子代理 kill）要等整批工具跑完才进安全点。信号已置位时安全点直接返回 `reason: None` 且不排空总线，用户原因到不了收场诊断。

冻结注册表已经挂到 run 事件队列和撤回协议上。写侧不用序号比较，白名单把 `RunTerminal` / `AgentEnd` 放行，两条尽力落库路径完全不看冻结。撤回超时发生在冻结之前，已发出的停止不回滚，且只等会话里被 HashMap 迭代到的第一个 run。成功路径对外的 `boundary_seq` 是冻结时的日志尾，不是目标消息的起始序号；现场截断按消息 id 切内存，消息库不改。

检查点提示词协议没有生产调用点。收口会把模型标记写上当前叶子，紧接着阶段总结用另一份载荷覆盖同一叶子；没有标记或标记损坏时不清除旧叶子。续 run 把待注入队列的正文和检查点摘要粘成一段 prompt，不重接输入环，也不移动叶子。

恢复转向策略已经装配进生产 loop。空响应与工具批后都有 `evaluate` 调用点，「没有生产调用点」这条线索已闭合。现存分叉是预算：协调器默认还能注入 3 次，策略对同一计数在 1 次时就要求人工干预；成功工具批在下一轮评估之前把计数清零，成功重复调用环攒不到这 1 次。

## 问题清单

### BC03-1 L3 强停停不掉正在跑的工具进程

- 现象：界面强停把本轮工具调用标成取消，shell 子进程仍继续跑。子代理 kill 连 `AbortSignal` 都不打，工具批要整批结束才看到强停。
- 证据：`apps/agent-workbench/src-tauri/src/run/run_launch.rs:1209`（L3 先 `abort_signal.abort()` 再入队）；`crates/session-loop/src/exec_single.rs:283`（`_abort_token` 丢弃）、`:391`（每次执行 `AbortToken::new()`，与信号无关联）、`:319`（信号已置位时，即便执行已有结果也改写成取消）、`:572`（`race_execution` 在 `AbortSignal` 上 `select` 后丢掉 execute future，不调用 `abort_token.abort()`）。`crates/agent-tools/src/tools/shell_exec.rs:241`（流式路径 `kill_on_drop(false)`）、`:367`（只有 `abort_token.is_aborted()` 才 `kill_child`）。同步路径同样 `kill_on_drop(false)`（`shell_exec.rs:59`），等待循环不读中止令牌，只在自身超时分支树杀（`:196`）。子代理入口 `apps/agent-workbench/src-tauri/src/run/run_core.rs:1125` 与 `crates/orchestrator/src/lifecycle.rs:221` 只调 `request_force_cancel` / `request_subagent_force_cancel`（`crates/session-loop/src/control.rs:328` 仅入队）。
- 机制：run 级信号和工具级令牌是两套对象。执行器用信号丢掉 future，令牌保持未中止，shell 的显式杀进程条件不成立；`kill_on_drop(false)` 使 drop `Child` 也不杀。子代理强停不置位信号，批中的竞速不会触发。生产代码里对工具令牌的 `abort()` 不在这条执行路径上。
- 影响：用户看到的强停收场与操作系统里仍在跑的命令脱节。被标成取消的写操作、长命令、后台化进程可以在 run 终态之后继续改工作区。子代理「已终止」只是行状态写成 failed，工具侧要等本批自然结束。

### BC03-2 安全点把只入队的强停推迟到工具批结束，并丢掉已置位信号的原因

- 现象：控制总线里的 `force_cancel` 不能打断正在执行的工具批。界面强停虽然打了信号，安全点却不排空总线，收场原因变成空。
- 证据：`crates/session-loop/src/control.rs:370`（`request_force_cancel` 只入队）。`crates/session-loop/src/loop/handlers/executing_tools.rs:49`（批前 `check_control`）、`:102`（整批 `execute_batch`，批中只把 `AbortSignal` 交给执行器）、`:148`（批后才再查安全点）。`crates/session-loop/src/safe_point.rs:124`（信号已 `is_aborted()` 时直接 `ForceCancel { reason: None }`，不 `drain`）。`crates/session-loop/src/loop/handlers/mod.rs:500`（abort 抢占不 `take_trace`）、`:542`（用这个 `reason` 做 aborted 诊断）。界面入队的默认原因是 `ui-force-cancel`（`run_launch.rs:1212`），顺序是先 abort 再入队（`:1209`）。`crates/session-loop/src/loop/loop_exec.rs:34` 写明 `AbortSignal` 不能复位。
- 机制：安全点的优先级把「信号已置位」放在总线 drain 之前。生产 L3 先打信号，下一次安全点永远走短路，队里的 reason、intent 轨迹留在总线上不消费。只入队的调用方没有信号，批中竞速不触发，要等 `execute_batch` 返回。
- 影响：强停诊断丢失用户原因。中途不能再靠同一条总线表达新的停止原因。子代理和任何「只 request、不 abort」的调用方，强停语义退化成「等当前工具批跑完」。信号一旦置位，本 run 剩余阶段都按已强停处理。

### BC03-3 冻结之后仍能把事件写过冻结序号

- 现象：会话冻结之后，终态事件和尽力落库路径仍能追加 `sequence > frozen_seq` 的记录。撤回注释声称冻结到截断之间没有 await，实现在中间等了回滚计划。
- 证据：共享注册表已接上，不是未挂载：`apps/agent-workbench/src-tauri/src/retraction_commands.rs:90`、`run_launch.rs:633`。判定在 `crates/orchestrator/src/events.rs:240`（`NoPersist` 在冻结检查前直接成功返回）、`:253`（冻结中且非撤离才拒绝）。撤离判定 `crates/session-loop/src/freeze.rs:172` 放行 `TimelineTruncate`、`RunTerminal`、`AgentEnd`。`events.rs:309` 的 `push_terminal_best_effort` 与 `:356` 的 `push_at_best_effort` 不读注册表。`freeze.rs:142` 的 `check_write` 全仓只有本文件测试调用。测试 `events.rs:2469` 在冻结后仍把 `RunTerminal` 落库，事件条数从 2 增到 3。审计 worker 走尽力落库（`run_core.rs:201`）。`run_idle.rs:1387` 在 `drive_outcome` 里终态化，`:1451` 才移出活动表，`:1465` 才 await 审计 worker。撤回侧 `retraction.rs:179` 声称冻结与 truncate 之间无 await，`:222` 实际 `await prepare_rollback_plan`。`events.rs:254` 与 `freeze.rs:128` 对 `is_frozen` 和 `frozen_seq` 各拿一次锁，中间释放会让「已冻结但读不到序号」的写入漏过去。
- 机制：护栏是「冻结中且不在白名单」，不是「序号不得超过冻结点」。收口把 `is_terminal` 提前到审计排空之前，撤回的收敛等待看到终态就返回并随后冻结，审计 worker 仍可用尽力路径写入。白名单把本应落在冻结点之前的终态事件继续放进冻结窗。
- 影响：冻结点不是事件流的稳定上界。截断之后仍可能出现新的终态或审计事件。`TimelineTruncate` 不一定占 `frozen_seq + 1`。投影若按冻结序号重放，会把冻结后写入的收口事件算进「边界之内」。

### BC03-4 撤回超时后停止副作用留下，且只等一个 run

- 现象：收敛超时发生在冻结之前。协议返回失败时，run 已经被强停，信号不能复位。同会话其它 run 不在等待窗口里。
- 证据：`crates/session-loop/src/retraction.rs:147`（`CONVERGE_TIMEOUT_MS = 15_000`）、`:200`（先看是否已冻结）、`:204`（然后 `stop_run`）、`:207`（再 `wait_converged`）、`:216`（超时路径到不了 `freeze`）。壳层 `retraction_commands.rs:234` 对每个活动 run 入队 `force_cancel` 并 `abort_signal.abort()`，`:241` 只记下迭代到的第一个 `run_id`。`:252` 只等这一个 id；无 id 直接成功。`:279` 超时返回 `ConvergeTimeout`。活动表是 `HashMap`（`:221` 起按 `values()` 收集），「第一个」不是稳定的主 run。`:200` 到 `:216` 之间有整段收敛等待，第二个撤回可以在冻结登记前也走进 `stop_run`。
- 机制：停止是副作用，超时只是还没登记冻结。`AbortSignal` 不能复位（见 BC03-2）。工具进程又停不掉（见 BC03-1），15 秒后协议报失败，命令可能仍在写，信号保持已中止。其它 run 已被 abort，却不参与收敛判定。
- 影响：一次失败的撤回留下「协议未冻结、run 已强停、工具可能仍在跑」的分叉。多 run 会话上，被漏等的 run 可以在调用方认为超时之后继续写事件。并发第二次撤回会再打一遍停止，随后在 `freeze` 上得到 Busy，停止已经发生。

### BC03-5 撤回成功时的边界序号是日志尾，不是目标消息

- 现象：定位到的目标消息起始序号只用于停止原因和回滚窗口。对外的 `boundary_seq` 以及截断事件里的边界，写的是冻结时的最大序号。现场界面对同一事件按消息 id 切内存。协议不改会话消息行。
- 证据：`retraction.rs:192` 得到目标 `boundary`，`:234` 把 `frozen_seq` 传给 `push_timeline_truncate`，`:248` 把 `RetractionOutcome.boundary_seq` 设为 `frozen_seq`。文件头 `:19` 与注释 `:183` 把这个冻结序号同时叫做「投影重放上界」。`retraction_commands.rs:103` 成功后只做文件回滚，不改 `session_messages`。现场 `apps/crish-desktop/src/store/sessionMessageActionsCore.ts:143` 的 `applyTimelineTruncate` 接收 `boundarySeq`，`:151` 起按 `targetMessageId` 下标截内存，序号不参与切片。`apps/crish-desktop/src/store/sessionActivateHydrate.ts:188` 只有本地消息为空才走引擎事件重放；非空时 Phase 1 用水合消息返回（`:180` 之前的本地加载路径）。
- 机制：协议内部有两个边界。目标消息序号决定「想撤哪条」，冻结 MAX 决定「事件流停在哪」。注释要求投影重放到 `boundary_seq`。按冻结 MAX 重放等于保留到当前日志尾，撤不掉目标之后的消息。现场改按消息 id 切，于是内存时间线与事件流边界不是同一刀。消息库不在这条命令上更新。
- 影响：同一次撤回，事件、文件回滚窗口、内存列表三套边界。推断：进程重启后 Phase 1 从 SQLite 取回未裁剪的消息，内存截断不在；事件流里的 `timeline-truncate` 也不会把目标之后的历史消息删掉。文件回滚用的是目标序号窗口，可能和留下的消息不一致。

### BC03-6 检查点恢复时叶子载荷与待注入输入对不上

- 现象：续 run 读到的检查点常常不是本次收口从对话标记采集的那一份，待注入队列也被收成一段用户 prompt。叶子不随恢复移动。
- 证据：`crates/session-loop/src/checkpoint.rs:16` 的 `checkpoint_prompt_section()` 全仓只有定义和本文件测试，生产零调用。该段 `:18` 要求模型输出 `CHECKPOINT:` 行，`:20` 又写模型不写、引擎在安全点采集。生产采集在收口 `apps/agent-workbench/src-tauri/src/run/run_idle.rs:1357` 的 `collect_checkpoint_on_close`，不是回合中的安全点。`:717` 的 `Ok(None)` 与 `:718` 的 `Err` 不写也不清除旧叶子。紧接着 `:1373` 的 `evaluate_stage_milestones` 调用 `:1177` 的 `stage_summary_to_checkpoint_payload` 再 `set_leaf_checkpoint`。转换函数 `crates/session-loop/src/loop/stage_summary.rs:272` 把 `files` 留空。恢复读当前叶子：`run_idle.rs:741` 调用 `read_leaf_checkpoint(None)`，实现在 `crates/orchestrator/src/session.rs:570`。续 run `run_idle.rs:1212` 把注入消息的 `text()` 拼成一段字符串，`:1222` 再把检查点摘要粘到同一段，`:1232` 作为单个 `prompt` 拉起；不重接 `AgentInputQueue` 的 steer / follow_up 环，也不改 `current_leaf`。
- 机制：同一叶子有两个写者，后写的阶段总结覆盖先写的标记载荷；`checkpoint-created` 若已发出，载荷仍是标记那一份，叶子上后来是另一份。没有新标记的 run 继续注入更早的叶子。提示词协议没进系统提示，模型不被要求输出标记，采集经常走 `Ok(None)`，旧叶子就留下来。续 run 读的是调用当时的当前叶子；用户若已把叶子 fork 走，读到的不是收口时写下的那一枚。队列在进入本函数前已按会话合并成消息，本函数再抹成一段正文，检查点摘要与唤醒文本变成同一条用户输入。
- 影响：恢复文本可以描述上一段进度、另一枚叶子，或一份没有文件清单的阶段总结，而当前对话已经往前走。输入环的分时语义（本轮 steer 与 idle follow-up）在这次拉起里不存在。推断：模型按这段粘合 prompt 继续，会重做检查点里已完成的步骤，或跳过队列里被省略的旧唤醒（合并上限在 `run_idle.rs:557`，超出只留一句省略说明）。

### BC03-7 steering 预算有第二道阈值，成功工具环在评估前被清零

- 现象：协调器默认预算是 3，恢复策略在计数达到 1 时就要求人工干预。成功的工具批会在下一轮「工具批后」评估之前把计数归零，这条环的 1 次上限攒不到。同一次空响应事件里，「评估后计数」和「剩余预算」不是同一个数算出来的。
- 证据：协调器 `crates/session-loop/src/steering/mod.rs:43`（`DEFAULT_MAX_STEERING_BUDGET = 3`），唯一增量在 `apply`（`:372`）。策略 `crates/session-loop/src/steering/strategy.rs:37`（`DEFAULT_MAX_STEERING_MESSAGES = 1`），`:105` 与 `:121` 在 `context.steering_count >= max_steering_messages` 时返回 `InterventionRequired`。评估轨迹把 `steering_count_after` 定义为含本次预占的潜在计数（`steering/mod.rs:285`、`:330`、`:341`）。`budget_remaining`（`:421`）是 `max - 当前实际计数`，发生在 `apply` 之前。空响应 handler `crates/session-loop/src/loop/handlers/steering_evaluation.rs:45` 先 `evaluate_traced`，`:49` 注释写剩余预算是「max − 潜在计数」，`:51` 实际传入的是 `budget_remaining()`，此时 `apply` 还在 `:73`。成功工具批 `executing_tools.rs:120` 调用 `emit_steering_reset_event(..., "after-tools")`，`handlers/mod.rs:417` 先读后 `reset`。下一轮 `prepare_turn.rs:96` 才对 `AfterTools` 做 `evaluate` + `apply`。错误环不走这个 reset。机器上下文字段 `crates/session-loop/src/state.rs:94` 只在 `reset_all_counters` 时把 `steering_count` 置 0；类型注释 `crates/conex-types/src/session.rs:125` 写「此处仅镜像/归零」，生产评估读的是协调器（`handlers/mod.rs:405`），收场计数也来自协调器（`crates/session-loop/src/loop/end.rs:70`）。
- 机制：同一整数上叠了两道门。策略门默认更早，协调器的 3 次上限在默认恢复策略下到不了。潜在计数在评估时加一，实际计数要等 `apply`。空响应事件把两者放在一起，观察者会以为还剩的次数已经扣过这次注入。成功路径把「工具批全部成功就归零」放在「下一轮按这个计数决定是否干预」之前，计数永远从 0 开始评估。错误路径不归零，第二次才干预。机器上下文里那份计数不跟随协调器增加，不能当第二观察口。
- 影响：默认配置下「最多纠偏 3 次」不是运行门槛，空响应第二次就停。反过来，工具成功但模型反复做同一类调用时，恢复注入可以每轮重来，直到回合上限，而不是策略写的 1 次。同一条 `steering-evaluated` 上的 after 与 remaining 不能互相复核。

## 已核对闭合或不是问题

- L2 不掐 provider。`run_launch.rs:1189` 的 `cooperative_stop` 只 `request_cooperative_stop` 并 `set_user_stopped`，不 `abort`。流消费只与 `AbortSignal` 竞速（`crates/session-loop/src/loop/handlers/streaming.rs:143`）。`streaming_aborted` 在协作停止分支走 stopped、不发 Abort（`:392`）。会话级 Abort 注册表的写入只在测试配置里（`apps/agent-workbench/src-tauri/src/engine_provider/stream.rs:36`），生产 `get_session_abort_signal` 读到的表没有生产写入。前端本地把流标成结束，不等于后端掐流。
- 桌面 Stop 不再成对发送 cancel-run。`apps/crish-desktop/src/api/runControlClient.ts:8` 写明过渡双线已删除，停止与强停只走 `core_run_control`。`cancelRunCommand`（`apps/crish-desktop/src/api/daemonClient.ts:119`）在桌面产品调用点上只剩定义和它自己的测试。系统地图里「L2/L3 成对附 cancel-run」对这条 UI 出站已过时。命令面还在：`run_launch.rs:1551` 的 `cancel_run_impl` 只有 `mode == "cooperative"` 走 L2，其余缺省 Force（`:1558`），Force 会打到 `ActiveRunEngine::abort`（`run_core.rs:124`）。这是残留命令，不是当前 Stop 按钮的双发。
- nudge 独立通道已删除，不是现存空洞。`crates/session-loop/src/steering/nudge.rs:1` 说明未接线通道已删；当前 run 的纠偏文本由 `build_steering_message` 生成，经 `SteeringCoordinator::apply` 写入对话（`steering/mod.rs:370`）。跨 run 队列属于另一路审查。
- 该注入的恢复转向有生产调用点。装配在 `apps/agent-workbench/src-tauri/src/engine_build.rs:1588`（`RecoverySteeringStrategy::default()`）。空响应在 `steering_evaluation.rs:45`。工具批后在 `prepare_turn.rs:96`（`steering_enabled && !has_runnable_pending` 时评估 `AfterTools` 与 `BeforeTurn`）。`BeforeTurn` 没有策略处理它（`strategy.rs:93` 只声明 AfterTools 与 EmptyResponse），评估得到空动作后继续，这不是「恢复策略没接上」。`no_tool_calls` 里的工具承诺自愈走输入队列，不是这条 `InjectMessage`。`SelfTerminationDiagnostic::should_emit`（`steering/diagnostics.rs:54`）因计数字段恒 0 而恒为 false，生产注释要求不要新依赖它；它不是恢复注入的入口。
