# 会话状态机与回合主路径

> 日期：2026-10-13
> 范围：`session-loop` 的状态机、输入环、历史水合，以及回合主循环与指定 handler。流式错误阶梯、压缩引擎、控制总线策略、工具执行器本体只在断裂处点名，整段留给邻域。
> 问题同权。旧文档只作线索，下列条目以当前代码为准。

## 能力结论

状态机表本身拒绝未定义转移，失败不改状态。一次 `run` 的收口事件却对不齐：重进准备回合会盖掉上一轮 `turn-start` 且不补 `turn-end`；安全点只要抽到控制动作，就会先发一条 `usage` 为空的 `turn-end`，软注入随后还能再发一条真的。无工具回合若带着 follow-up 或可运行输入续跑，`turn_index` 被整表归零，同一 `run` 里两轮助手消息共用 `turnIndex = 1`，桌面按这个下标覆盖上一轮正文。

桌面多轮请求的历史走前端载荷而不是缓存保真水合。水合把序列截到最后一个用户消息，调用方又已经排除了本条新用户消息，于是上一轮助手回复在进模型前被删掉。工具结果生产上写在 `toolCalls[].output`，水合只保留 `id` / `name` / `arguments`，再补一条 `outcome-unknown` 的假结果，调用和真实结果被拆开。历史图片和时间线块没有对应的块类型，解析失败后只剩正文。

协作停止在准备回合和转向评估两相不推状态机，却立刻以 stopped 收场，并从控制总线抽走的附带消息只进本轮队列。待处理输入的落库与删除是两次无序 spawn，后完成的 `INSERT OR REPLACE` 可以把已消费的用户消息写回，恢复时再注入。

准备回合里的压缩在真正发生时会发压缩事件；默认保留最近两个用户回合，本路没有证明「新用户消息被静默裁掉」。静默截断发生在进循环之前和进循环的水合出口，见 BC01-4、BC01-9。

## 问题清单

### BC01-1 重进准备回合时上一轮 turn-start 没有 turn-end，本轮 usage 被清掉

- 现象
  同一次 `run` 里，长度升级、空响应继续、工具批后的可运行输入、转向评估完成，都会回到准备回合再发一条新的 `turn-start`。前一条 `turn-start` 的 `turn-end` 不再出现。中间那次供应商调用记下来的 usage 在下一次准备时被写成空。
- 证据
  - `crates/session-loop/src/loop/handlers/prepare_turn.rs:66-80`：用 `turn_index.saturating_add(1)` 发 `TurnStart`，把 `current_turn_index` 直接换成新值，并把 `budget_state.turn_usage` 置 `None`。这里没有调用 `emit_missing_turn_end`。
  - `crates/session-loop/src/loop/handlers/prepare_turn.rs:134`：随后 `TurnPrepared` 才把机器上的 `turn_index` 加一。
  - 重进且不经过 `turn_complete` 的分派：`no_tool_calls.rs:64`、`no_tool_calls.rs:71`、`no_tool_calls.rs:119`（`NoProgressContinue`）；`executing_tools.rs:155-159`（`InputAvailable`）；`steering_evaluation.rs:39-41` 与 `steering_evaluation.rs:90`（`SteeringComplete`）。
  - 邻域同一洞：`stream_error_retry.rs:179`、`stream_error_recover.rs:75`、`stream_error_recover.rs:253` 也派 `NoProgressContinue`。阶梯本身交给 02，准备回合这个洞在本路。
  - 转移表：`crates/conex-types/src/transition.rs:140`、`transition.rs:151`、`transition.rs:163` 都是普通转移回 `PreparingTurn`，不补终态、不递增轮次。
- 机制
  `current_turn_index` 只记「当前已发出的那一条 turn-start」。正常收口在 `turn_complete.rs:41-55` 发 `TurnEnd` 后把它清成 `None`。重进路径跳过这个 handler，准备回合又先覆盖槽位再发新的 `TurnStart`。`emit_missing_turn_end`（`handlers/mod.rs:467-477`）只在收敛和 `check_control` 里调用，补不回已经被覆盖的上一轮。长度阶梯走两次时，事件是 `TurnStart(1)`、`TurnStart(2)`、`TurnStart(3)`，收口只剩 `TurnEnd(3)`。第一次和第二次写入的 usage 在 `prepare_turn.rs:70` 丢掉。工具批后若队列里已有 force/steer，`executing_tools.rs:155-156` 直接 `InputAvailable`，工具回合同样没有 `TurnEnd`。
- 影响
  一次 `run` 的轮次终态缺失。按 `turn-start`/`turn-end` 成对记账的用量、轮次耗时和「这一轮是否结束」都会把多次供应商调用并成一轮，中间轮的 token 用量消失。工具批后插队续写时，工具调用落在一个从未关闭的轮次里。

### BC01-2 安全点先补一条 usage 为空的 turn-end，软注入路径随后再发一条

- 现象
  流结束、工具批开始、工具批结束、回合收口，只要安全点抽到任何控制动作，都会先发 `TurnEnd` 且 `usage` 固定为 `None`。软注入并不结束本次 handler，后面的正常收口再发一条带真实 usage 的 `TurnEnd`。强停打在工具批入口时，这条空 usage 的 `TurnEnd` 先发出，合成的工具结果落在它后面。
- 证据
  - `crates/session-loop/src/loop/handlers/mod.rs:537-540`：`check_control` 在区分动作之前无条件调用 `emit_missing_turn_end`。
  - `handlers/mod.rs:467-477`：补发的 `TurnEnd.usage` 写死 `None`，不读取 `budget_state.turn_usage`。
  - `handlers/mod.rs:558-569`：`SoftInject` 把消息放进环后返回 `Ok(None)`，handler 继续。
  - `turn_complete.rs:35-55`：开头的 `check_control` 若只是软注入，函数继续，再发一条 `TurnEnd`，usage 用 `take()`。
  - `streaming.rs:256` 已把本轮 usage 写入槽位；`streaming.rs:304` 的 `check_control` 仍先补空 usage 的 `TurnEnd`。
  - `executing_tools.rs:49-62`：入口 `check_control` 先补发闭合，返回结束决策之后才 `synthesize_and_record_interrupted_calls`。
- 机制
  注释把 `check_control` 里的补发当成「本路径不会再走进 `turn_complete`」。软注入返回的是继续，不是收口。于是同一 `current_turn_index` 先被 `take()` 发出一条空 usage 的 `TurnEnd`，槽位清空；后续 `turn_complete` 用机器上的 `turn_index` 再发一条，usage 才是供应商刚写入的值。强停和协作停止会立刻返回结束决策，不会双发；但工具批入口的强停已经把轮次关掉，中断合成的 `Tool` 消息（`tool_pairing.rs:117-121`）排在这条 `TurnEnd` 之后。
- 影响
  一次 `run` 出现同一个轮次的两条 `TurnEnd`：第一条用量为空，第二条才是真值。按第一条截断轮次的消费者丢掉用量，按两条都入账的消费者把一轮记成两轮。强停时工具结果出现在轮次已经结束后，调用与结果的事件边界被拆开。控制总线何时入队软注入交给 03；双终态发生在回合 handler。

### BC01-3 无工具回合的后续输入把 turn_index 归零，同一 run 两轮助手共用 turnIndex 1

- 现象
  纯文本回合结束时，若 follow-up 被提升，或队列里已有可运行输入，机器把 `turn_index`、工具计数、转向计数全部归零，然后回到等待输入。下一轮准备再发 `TurnStart`，下标仍是 1。桌面只对助手 `message-end` 按 `turnIndex` 分段，同一下标覆盖上一轮正文。
- 证据
  - `turn_complete.rs:187-199`：`tool_call_count > 0` 时走 `NextTurn` 并返回，不提升 follow-up。计数为 0 时 `promote_follow_up`，然后 `InputAvailable`。
  - `crates/conex-types/src/transition.rs:172-177` 与 `crates/session-loop/src/state.rs:91-95`：`TurnComplete + InputAvailable` 的效果是 `reset_all_counters`，`turn_index = 0`。
  - `prepare_turn.rs:66`：下一轮 `TurnStart` 的下标是 `0 + 1 = 1`。
  - `handlers/mod.rs:277-283`：`message-end.turn_index` 取机器当前值。同段注释写明助手收口在递增之后，前端只按 `turnIndex` 给助手分段。
  - `apps/crish-desktop/src/api/chat-bridge/handlers/messageHandlers.ts:146-193`：助手消息把 `turnAuthoritativeTexts` 和 `segs[turnIndex]` 写成覆盖，不是追加。
  - `eventDedupe.ts:123-152`：带 `sequence` 的键含序号；`sequence` 为空时轮次键退化为 `turn-start:m:turn-N`。实时轨注释写明 `sequence=None`（`loop_runner.rs:247-250`）。
- 机制
  有工具的续轮走 `NextTurn`，计数保持递增，`turn_complete` 会先发 `TurnEnd`。无工具续轮走另一条 `InputAvailable`：先归零再等下一条用户消息。`awaiting_input.rs:20-24` 在下一次 `TurnPrepared` 之前就 `record_message`，这条用户消息的 `turn_index` 仍是 0，前端忽略非助手。随后助手再次以 1 收口。工具批中途的 `InputAvailable`（`transition.rs:163`）不归零，但也不收口，那是 BC01-1。两条 `InputAvailable` 的轮次语义不一致。
- 影响
  同一次 `run` 里先有一轮助手、再跟一条 follow-up 或安全点插话时，第二轮助手正文替换第一轮分段，聚合结果丢掉前一轮文字。若中间还有工具轮，新回复落在下标 1，排到更早的分段位置，后出现的正文显示在更前的轮次上。推断（未跑界面）：持久轨因序号不同不会单靠 `turnIndex` 丢掉事件；实时轨序号为空时，第二次 `turn-start`/`turn-end` 的去重键与第一次相同，会被当成重复丢掉。事件日志里则实实在在有两个 `turn_index = 1` 的轮次对。

### BC01-4 桌面多轮水合删掉上一轮助手回复

- 现象
  从第二条桌面消息起，送进模型的历史在最后一个用户消息处截断。本条新用户消息已被调用方排除，截掉的是上一轮助手回复。该助手若带工具调用，调用连同结果一起消失，轮不到孤儿修补。
- 证据
  - `apps/crish-desktop/src/api/chat-bridge/streamSession.ts:177`：`buildHistoryMessages(body, { excludeId: userClientMessageId })`。
  - `historyMessages.ts:121`：命中 `excludeId` 的消息不进入载荷。
  - `apps/agent-workbench/src-tauri/src/run/run_history.rs:416-422`：前端 `history` 非空就用前端源，缓存只在前端为空时启用。
  - `run_launch.rs:980-987`：前端源调用 `hydrate_history`，缓存源才走 `cached_history_to_conversation`。
  - `crates/session-loop/src/hydrate.rs:323-330`：截到最后一个 `User`，其后消息全部丢掉；序列里没有用户消息则整表清空。
  - `hydrate.rs:424-426` 写：截断只约束「纯历史」形态，因为 `run` 还会追加新用户消息。这与 `excludeId` 对不上。新用户消息不在这份历史里，尾部被删的是上一轮助手。
- 机制
  常见桌面历史是 `[user1, assistant1, …, userN, assistantN]`，当前正在发送的 `userN+1` 被排除。水合后最后一个用户是 `userN`，`assistantN` 被 `truncate`。`run` 再把新用户消息追加到尾部。首条消息历史为空，不受影响；会话里已经有一轮完整问答之后，每条新消息都会丢掉紧挨着的上一条助手回复。缓存水合不按这个规则截尾，但桌面只要带了非空前端历史就不会走缓存。`with_initial_conversation` 的首尾断言只要求首条是用户、含水合链时以用户收尾（`loop_runner.rs:262-264`），截完再追加新用户后断言仍然通过。
- 影响
  多轮上下文缺少模型刚刚给出的回答。上一轮若调用了工具，这些调用不会进入 BC01-5 的修补，模型既看不到调用也看不到结果。推断依据是调用链阅读，不是一次实机请求抓包。

### BC01-5 工具真实输出停在 toolCalls.output，水合改成 outcome-unknown

- 现象
  下一轮上下文里，助手消息上的工具调用还在，对应结果变成错误码 `TOOL_OUTCOME_UNKNOWN` 的合成 `Tool` 消息。生产路径把真实输出写在 `toolCalls[].output`，水合结构不读这个字段。
- 证据
  - `apps/crish-desktop/src/hooks/agentStreamCallbacks.ts:175-192`：`onToolSuccess` 写 `tc.status` 与 `tc.output`，不写 `toolCallResults`。
  - `apps/crish-desktop/src/store/types.ts:314-320`：`MessageToolCall.output` 是工具调用对象上的字段。
  - `historyMessages.ts:147-150`：整个 `toolCalls` 数组进 `tool_calls_json`；`tool_call_results_json` 只在 `toolCallResults` 非空时才有。
  - `hydrate.rs:194-202`：`LegacyToolCall` 只有 `id`、`name`、`arguments`。同文件 `170-177` 用这份子集组 `ToolCall`。
  - `hydrate.rs:346-404`：没有配上 `ToolResult` 的调用，在助手消息后插入 `role = Tool`、`is_error = true`、正文含 `TOOL_OUTCOME_UNKNOWN` 的消息。
  - 第二处潜伏：`hydrate.rs:131-133` 在 `blocks_json` 能解析成非空 `AgentMessageBlock` 时直接返回，不再读 `tool_call_results_json`。当前桌面构造器不填 `blocks_json`，活路径是 `output` 被丢掉这一条；缓存写入若只留 `blocks_json` 且块里没有结果，会走上这条提前返回。
- 机制
  合成兜底按「结果在 `tool_call_results_json`」设计。桌面把结果放在调用对象的 `output` 上，解析时该字段被 serde 忽略，于是每条调用都看起来没有结果。修补插入的角色是 `Tool`，角色本身没有配错，正文是假的。水合修补插在调用后一位（`hydrate.rs:402-403`）。回合内 Tier-2 用 `record_message` 追加到对话尾部（`tool_pairing.rs:117-121`、`tool_pairing.rs:224-231`），历史中部的孤儿不会紧挨调用。Tier-2 修的是本轮未派发调用，补不回水合丢掉的真实输出。
- 影响
  下一轮模型读到的工具结局是「水合后结果不可知」且标记为错误，真实输出不在上下文里。模型会重试已经成功的工具，或按错误结局继续推理。`arguments` 在桌面是字符串，这条路径上参数还在。

### BC01-6 历史图片和时间线块进不了模型上下文

- 现象
  上一轮消息里的图片、时间线块，到了水合出口只剩纯文本或被整段丢掉。本条新用户消息的图片仍可经 `metadata.contentParts` 进入本次请求。
- 证据
  - `crates/conex-types/src/message.rs:136-157`：`AgentMessageBlock` 只有 `text` / `thought` / `tool-call` / `tool-result`，没有 image。
  - `hydrate.rs:124-143`：`blocks_json` 按该枚举解析；失败则警告并回退到 text/thinking/工具 JSON。测试 `unparseable_timeline_blocks_json_falls_back_to_text` 在 `hydrate.rs:645` 一带覆盖时间线形状回退成正文。
  - `hydrate.rs:81-87`：metadata 只在失败回合保留 `failed-turn`，其余运行期字段不进上下文。
  - `historyMessages.ts:138-152`：载荷只有 id、sender、timestamp、text、thinking、两列工具 JSON、status，不拷贝 blocks、附件或 content parts。
  - `run_launch.rs:498-499` 与 `run_launch.rs:966-969`：本次消息在 `has_images` 时把 content parts 写进新用户消息，不经过历史水合。
- 机制
  时间线 `blocks_json` 的 `type` 是 `text` / `tool_call` / `image`，对不上 `tool-call` 这类 tagged enum，整段 JSON 被拒绝，只留 `text` 字段能表达的正文。图片没有块可以落。即便某条历史消息的 metadata 里曾有 `contentParts`，水合也会摘掉 metadata。工具调用上的 `images`（`types.ts:340-341`）同样不在 `LegacyToolCall` 里。
- 影响
  多轮之后模型看不到此前轮次的图片和按时间线交错的结构，只看到退化为正文的文本。推断依据是类型与构造器阅读：当前这条用户图片仍走 `content_parts`，不受本条影响。前端组包细节交给 14/15；丢字段的位置在 `hydrate`。

### BC01-7 准备回合与转向评估上的协作停止立刻收场，附带消息只进本轮队列

- 现象
  协作停止打在 `PreparingTurn` 或 `SteeringEvaluation` 时，状态机停在原相位，函数仍返回 stopped。随停止一起抽走的消息被放进本轮 steer 环。壳层每个 `run` 新建循环对象，这些消息随对象丢掉。
- 证据
  - `handlers/mod.rs:436-451`：`drive_machine_to_stop` 对 `PreparingTurn | SteeringEvaluation` 是空分支。注释写「停止在下一安全点生效」。
  - `handlers/mod.rs:548-556`：空转之后仍然 `enqueue_steer`，并返回 `EndDecision::stopped`。
  - `prepare_turn.rs:39-40` 在发 `TurnStart` 之前就调用 `check_control`，所以准备阶段的停止不会等到流结束。
  - `loop_runner.rs:256-259`：真实接线每个 `run` 重建 `AgentSessionLoop`，对话由 store 水合，不靠循环对象跨 `run` 保留队列。
- 机制
  控制动作已经从总线取走（`check_control` 在返回前完成 drain）。协作停止语义是把机器推到 done 并保留附带消息到下一安全点。这两相既不推转移，又立刻结束本次 `run`。附带消息只存在于即将被换掉的 `input_queue`。等待输入、流式、执行工具、回合收口四相会真正派发停止转移，不在本条。
- 影响
  用户在准备或转向评估窗口发出的停止会结束本轮，同时附在停止上的待注入消息从总线消失，下一轮 `run` 看不到它们。推断：队列丢失依赖「每 run 重建循环」这条注释，未做一次停机复现。控制优先级与转向策略交给 03。

### BC01-8 已消费用户消息的落库与删除无序，后写的替换可能把行写回

- 现象
  用户消息入队时 spawn 一次保存，被 `record_message` 消费时再 spawn 一次删除。两次都不等待，也没有代数。保存是按消息 id 的 `INSERT OR REPLACE`。删除先完成、保存后完成时，已消费行会重新出现在 `pending_inputs`。
- 证据
  - `loop_runner.rs:335-367`：`spawn_pending_input_save` 在 tokio 上 spawn，失败只警告。`loop_exec.rs:112-113` 对本次用户消息同样调用。
  - `input.rs:52-57`：保存语义是 `INSERT OR REPLACE`，id 等于消息 id。
  - `handlers/mod.rs:248-267`：仅 `User` 角色 spawn `delete_pending_input`，失败只警告，不与保存排队。
  - `crates/orchestrator/src/restore_manager.rs:357-367`：恢复按会话把 `load_pending_inputs` 的剩余行放进 `RestoreOutcome.pending_inputs`。
- 机制
  两个任务抢同一行，没有 generation，也没有「先保存成功再允许删除」的顺序。SQLite 单写者下后提交的语句生效。消费已经完成、删除已经执行之后，迟到的替换把 payload 写回去。崩溃恢复按表里剩下的行注入。空 payload（`serde_json::to_string` 失败时 `unwrap_or_default`，`loop_runner.rs:354`）会写成空串行，本条不单列。
- 影响
  用户已经看到本轮开始处理的消息，在进程重启后可能被再注入一次，形成重复用户消息。推断：竞态结构来自两次无序 spawn 与替换语义，本路没有跑并发测试。恢复之后如何注入会话交给 07；无序写发生在循环入队和 `record_message`。

### BC01-9 送进循环之前的历史预算截断没有压缩事件

- 现象
  桌面在调用水合之前按约 20 万 token 的预算从中间丢掉消息，只保留第一条用户消息锚点和预算内的尾部。循环收到的已经是截短数组，准备回合不会为此发出压缩事件。
- 证据
  - `historyMessages.ts:21`：`HISTORY_TOKEN_BUDGET = 200_000`。
  - `historyMessages.ts:82-100`：总量超预算时保留到第一条用户消息为止的头部，再从尾部向前丢，直到头部加尾部放进预算。
  - `run_launch.rs:980-987`：这个数组直接进入 `hydrate_history` 或在前端为空时才改走缓存。循环侧没有对应的「调用方已截断」事件。
- 机制
  这是进 `session-loop` 之前的裁剪。准备回合里的 `maybe_compact_*` 只对自己即将压缩的对话发事件，看不到桌面已经丢掉的中段。超预算时长对话会在锚点与尾部之间开一个洞，模型上下文与会话库正文不一致。未超预算时函数原样返回，本条不触发。
- 影响
  长会话的中间回合从模型上下文消失，循环、压缩计数和上下文压缩事件都不会留下这次截断。交给邻域 14（运行面历史装配）和 15（载荷契约）。估算器本身不在本路重审。

## 已核对闭合或不是问题

- 未定义转移不会被吞掉。`state.rs:64-67`：`apply_transition` 失败则状态与上下文都不变。`handlers/mod.rs:224-236` 把 `TransitionError` 映射成 `RUNTIME_TRANSITION_FAILED`，调用方用 `?` 传出。状态机测试覆盖已定义转移对。
- 恢复缺省是 `Fatal`，不再把内部错误派成 `NoToolCalls` 静默收场。`loop/mod.rs:128` 与 `loop_exec.rs:289-293`（F1-01）。
- `turn_index` 饱和加，到 `u32::MAX` 不再回绕。`state.rs:78-82`，事件侧 `prepare_turn.rs:63-66`。
- 有定义转移的协作停止使用 `Stop`/`Stopped` 收场，不记成 `Aborted`。`end.rs:11-12`。空转的两相是 BC01-7，不是非法事件被吞。
- 干预与转向预算耗尽以 stop 加诊断收场，这是 `end.rs:6-9` 与 handler 注释里的既有裁决。`prepare_turn.rs:109-115`、`steering_evaluation.rs:58-86` 在派发后立刻返回，不会再走进 `turn_complete.rs:65-73` 把机器上的 `Error` 收成 `RunOutcome` 错误。流式 handler 本身不派 `InterventionRequired`。
- 输入环容量 1000（`input.rs:33-34`）。满则覆盖最旧并增加 `INPUT_OVERWRITES`、打出 id 与 120 字预览（`input.rs:170-188`），与环自己的契约一致。`dequeue` 先 force 再 steer，不取出 follow-up（`input.rs:241-249`）。`promote_follow_up` 只在无工具收口调用（`turn_complete.rs:193-199`）。编排侧队列容量 100，转入时先被那边裁过，正常转入不会打满 1000。`into_user_message` 只保留文本、丢掉附件（`steering_queue.rs:97-113`），交给 07，不在本路展开。
- 待处理输入只对 `User` 删除（`handlers/mod.rs:252-267`）是按角色设计的：工具结果和助手消息不是 pending 行。无序竞态是 BC01-8。
- 主用户消息在 `awaiting_input.rs:20-24` 先入对话，随后 `prepare_turn` 的 hold 区通常是空的。hold 只对仍在队列里的消息生效；单测直接往 `PreparingTurn` 入队，不经过等待输入。压缩真正发生时事件在压缩分发内部发出。引擎默认保留最近 2 个用户回合（`crates/conex-compaction/src/cut_point.rs:13`）。推断：生产顺序绕过了「用户消息绝不进 dropped_ids」那条 hold 注释，但默认下限会留下尾部用户消息，本路没有证明新用户消息被静默裁掉。切割正确性交给 05。`maybe_compact_*` 的布尔返回值被忽略，这本身不构成静默丢消息。
- `clamp_max_tokens`（`compaction_dispatch.rs:63-78`）钳的是输出 token 上限。可用预算低于 256 时保持请求值并打日志；够用时取较小值。这不是对话消息被丢掉。请求构造交给 02/05。
- 工具输出 G8 截断写入 `metadata.g8ToolOutputTruncation`（`executing_tools.rs:165-174`），循环能看见截断记录。
- Tier-2 `reconcile_orphan_tool_calls`（`tool_pairing.rs:188-232`）按 `tool_call_id` 幂等，补的是未派发调用，用 `TOOL_ABORTED_BEFORE_DISPATCH`。它不负责找回 BC01-5 丢掉的真实输出。`NextTurn` 之前 `turn_complete` 已经发过 `TurnEnd`。
- `max_turns == 0` 在 `AgentStart` 之前收成 `MaxTurns`（`loop_exec.rs:50-68`，`AgentStart` 在 `loop_exec.rs:119`）。测试锁定的是没有 `TurnStart`、没有供应商调用。生产默认是 64。这是一条「有 `AgentEnd`、没有 `AgentStart`」的边界，不列入现存问题主项。
- 空响应且转向关闭时，`streaming.rs:332-339` 直接 stop 加诊断，不派转移。`converge`（`loop_exec.rs:309`）仍会补 `turn-end`。机器停在 `Streaming` 直到下一次 `run` 换新机器，事件与 outcome 已经收口，不单列。
- `executing_tools.rs:66-71` 在缺少助手工具调用时直接错误收场、不派转移。入口本应来自 `HasToolCalls`，属于防御分支。
- 桌面 `isHistoryEligible` 只放行无状态或 `completed`（`historyMessages.ts:68-70`），`error` 状态进不了载荷。水合本身会把 `status=error` 收成带 `failed-turn` 的消息（`hydrate.rs:84-86`、`hydrate.rs:114-118`）。当前桌面路径没有把失败回合送进来，不记成水合丢失败回合。
- `sender` 不是 `user`/`assistant` 的历史行被跳过（`hydrate.rs:71-75`）。系统提示来自选项，不靠历史行里的 system。连续用户消息保持原样；本路没有证据表明当前供应商会因此拒请求。
- `stage_summary` 只构造里程碑文档，回合分派不调用它。`loop_options` 是配置。`invariants.rs` 是压缩前缀测试。三者没有单独的能力断裂。

## 给主控的摘要

1. 状态机拒绝未定义转移；断裂在回合重进、终态补发和轮次号归零。
2. BC01-1：长度升级、空响应继续、工具批后插队、转向完成重进准备回合时，上一轮没有 `turn-end`，usage 被清掉。`NoProgressContinue` 的错误阶梯交给 02。
3. BC01-2：安全点先发 `usage=None` 的 `turn-end`；软注入还会再来一条真 `turn-end`。强停时合成工具结果落在闭合之后。
4. BC01-3：无工具后续输入把 `turn_index` 归零，同一 `run` 两轮助手共用下标 1，桌面按该下标覆盖正文。
5. BC01-4：桌面排除当前用户消息后再截到最后一个用户，上一轮助手回复进不了模型。
6. BC01-5：真实工具输出在 `toolCalls.output`，水合改成 `outcome-unknown`。BC01-6：历史图片和时间线块没有落点。
7. BC01-7：准备/转向两相的协作停止立刻收场，附带消息只进本轮队列（交给 03）。BC01-8：pending 保存与删除无序，已消费行可能被写回（交给 07）。
8. BC01-9：桌面 20 万 token 预算截断中段历史，循环没有压缩事件（交给 14/15）。
9. 准备回合压缩在发生时有事件；默认保留最近两个用户回合，没有证明新用户消息被静默裁掉（切割交给 05）。
10. 已闭合：未定义转移显式失败、缺省 Fatal、轮次饱和、环满覆盖有日志、G8 留痕、干预以 stop 加诊断收场。
