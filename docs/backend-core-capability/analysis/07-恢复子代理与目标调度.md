# 恢复子代理与目标调度

> 日期：2026-10-13
> 范围：`recovery*`、`restore*`、`lifecycle`、`subagent_events`、`task_events`、`goal_state`、`steering_queue`、`flow_graph*`。生产调用点追到壳层 `run_snapshot` / `run_idle` / `run_resume` / `run_core` / `subagent_spawner` / `task_event_consumer`，不重审 `run.rs` 日常状态机。
> 只记现存问题。旧方案只作线索，以当前代码为准。

## 能力结论

进程重启后，没有 `run-terminal` 的在途 run 会被写成 `failed`（取消中则 `cancelled`），原因 `daemon-restarted`，并留下 `run-interrupted`。主 run 不自动拉起，这是启动路径上写明的约束。子代理中断会尽量通知父会话。恢复阶梯的判定、fork 和通知重排都有生产入口。

接上之后有八处对不齐。坏的终态载荷会把在途 run 改成无法解析的状态字面量，本轮既不打断也不续跑。快照退化和叶子 id 对不上时，内存里的会话树变成空树，启动继续。阶梯 2 和任务唤醒放进 steering 队列的条目会话 id 是空串，按会话取不出来，确认函数没有生产调用。fork 记录上的上下文模式不进入新 run，父 run 关联落到「当前活动 run」或空串。强停没投进活动 run 时，行和结束事件已经写成终止。无清单时，否定句里的完成字样会把目标判完成。依赖图的环检测和失败策略只在调度器内部，生产没有构造调度器的地方。文档里的输入队列适配只有测试在用；崩溃前写入的 `pending_inputs` 被装进恢复结果后没有生产读取。

## 问题清单

### BC07-1 终态载荷缺 `terminal` 时，在途 run 被改成字面量 `run-terminal`

- 现象：库里已经有一条 `run-terminal`，但载荷解析不出 `terminal` 字段时，这次恢复把该 run 的状态改成字面量 `run-terminal`，然后跳过打断。它不会变成 `daemon-restarted`，也不会进入重启后续跑条目。
- 证据：`crates/orchestrator/src/restore_manager.rs:79-86` 解析失败或缺少 `terminal` 时回退字符串 `"run-terminal"`。`88-93` 用 `RunStatus::from_str`，失败则 `Unknown(该字符串)`。`crates/conex-db/src/runs.rs:59-73` 的合法字面量不含 `run-terminal`。`restore_manager.rs:119-120` 该分支直接 `continue`，不写 `run-interrupted`。`388-398` 规定 `Unknown` 本身也不算 in-flight。
- 机制：终态事件优先于 runs 表。完好载荷能读到顶层 `terminal`，这条回退走不到。载荷不是对象、字段缺失、或字段不是字符串时，回退字面量无法解析，恢复把它当成「已有权威终态、只是不认识」。原先的 `running` / `completing` 被覆盖掉，后续重启看见的是未知终态，不再补打断。
- 影响：一次写坏或写半的终态事件，会让崩溃时仍在跑的 run 永久停在不可识别状态。界面和续跑都不会把它当成「被重启打断」。

### BC07-2 快照退化和叶子对不上时，会话树变成空树，启动继续

- 现象：主快照和备份都不可用时，恢复不读会话表，只按 run 行造会话，分支列表为空。另一条路径上，叶子移动只改当前叶子 id；这个 id 不在分支里时，树还原失败，壳换成一棵空树并继续启动。
- 证据：`crates/orchestrator/src/restore_snapshot.rs:250-264`、`312-322`：损坏或缺失走备份，备份也不可用则 `None` 加说明，恢复模式为全量重放（`restore_manager.rs:55-58`）。`restore_manager.rs:259-274` 无快照时会话只从 run 的 `session_id` 派生，`branches` 为空、`current_leaf_id` 为 `None`。`crates/orchestrator/src/session.rs:176-190` 重放 `session-leaf-moved` 只写 `current_leaf_id`，并写明事件可以指向分支列表里没有的叶子。`session.rs:480-488` 与 `701`：`from_session_record` 经 `restore_leaf`，叶子不在条目里返回 `NotFound`。`apps/agent-workbench/src-tauri/src/run/run_snapshot.rs:201-209` 捕获该错误后 `SessionTree::new`。`restore_manager.rs:341-343` 叶子载荷解析失败被丢掉，恢复不中断。
- 机制：快照文件本身不会被反序列化成一份空 JSON 会话；不可用时是整段跳过。全量重放留下的是「有 run 才有会话、且没有分支」。增量路径则把「允许悬空叶子」的事件重放，交回「叶子必须存在」的树构造。构造失败被定义成可继续：阶梯 1/2 照常，fork 会在空树上结构化拒绝。损坏的叶子事件连当前叶子都不更新。
- 影响：快照主备都坏时，只存在于快照里的会话不会回到内存注册表；有 run 的会话丢掉分支历史。叶子 id 对不上时，原本有分支的会话也被换成空树，分叉和 resume 找不到源叶子。进程仍报恢复完成。

### BC07-3 阶梯 2 与任务唤醒的队列条目会话 id 为空，确认函数没有生产调用

- 现象：子代理失败升到阶梯 2、以及任务终态唤醒，都会往共享 steering 队列放条目。条目的 `session_id` 是空串。按真实会话取出的路径匹配不到。阶梯 2 的 `acknowledge` 没有生产调用，通知一直 `pending`，每次重启把同一条空会话条目再放进去。
- 证据：`crates/orchestrator/src/recovery_notify.rs:85-97` `build_steering_entry` 固定 `session_id: String::new()`。`crates/orchestrator/src/recovery.rs:458` 入队用的就是这个构造。`recovery.rs:718-743` `acknowledge` 会把 `pending` 翻成 false。全仓生产代码没有 `acknowledge(` 调用，只有 `crates/orchestrator/tests/recovery_ladder.rs:662`、`crates/orchestrator/src/recovery_tests_coordinator.rs:98`、`crates/orchestrator/tests/multi_agent.rs:741`。`recovery.rs:749-760` 对所有 `pending` 再入队。`apps/agent-workbench/src-tauri/src/run/run_snapshot.rs:217-220` 每次恢复成功都会调用它。取出是 `crates/orchestrator/src/steering_queue.rs:201-202` 的相等比较，消费点 `apps/agent-workbench/src-tauri/src/run/run_idle.rs:543-547` 传入活动 run 的真实 `session_id`。任务唤醒同一形状：`crates/orchestrator/src/task_events.rs:174-182`，`apps/agent-workbench/src-tauri/src/task_event_consumer.rs:208-212` 原样入队。`task_events.rs:199-217` 的 `build_task_failed_steering_entry` 会带上事件里的 `session_id`，但 `task_event_consumer.rs:18-19` 写明 `steer_for_task_failed` 在 v1 不启用，生产无调用。
- 机制：队列后来按会话隔离。阶梯 2 和任务唤醒的构造仍写空会话，分组却是全局的 `recovery-<run>` / `task-wake`。`replace_or_enqueue` 用会话加分组对齐，于是所有任务终态挤在同一条空会话记录上，后一条盖掉前一条。`clear_for(真实会话)` 也清不掉。`acknowledge` 是唯一把 `pending` 清掉的函数，生产不调用，所以重启重排不会停止。对照：子代理正常收口的 steering 带父会话 id（`apps/agent-workbench/src-tauri/src/subagent_spawner.rs:1113-1123`），那条取得到。
- 影响：阶梯 2 的「请主代理决策」到不了该会话的下一轮。任务完成、失败、被杀也不会把摘要注入所属会话。库里的通知和审计事件还在，主代理看不到队列提醒。与 14 路 BC14-7 是同一条任务唤醒事实，这里补上阶梯 2 和 `acknowledge` 不闭合。

### BC07-4 fork 与 resume 不把上下文交给新 run，父 run 关联落到当前活动 run 或空串

- 现象：阶梯 3 和 `resume_subagent` 会 fork 一个新 run 承接同一段任务文本。上下文模式只写在 fork 记录和树节点载荷上。新 run 的启动历史恒为空。请求里的 `parent_run_id` 先被写成 `None`，再被解析成父会话此刻的活动 run；没有活动 run 时落成空串。空串使开始/结束事件的 run 列为空，对不上原来的父 run。
- 证据：`crates/orchestrator/src/recovery.rs:550-563` 计算 `context_mode` 后只放进 `ForkRecord`。`recovery_notify.rs:124-135`：注入字节为 0 就是 `New`，其余参数被丢掉，窗口和时长不参与。`recovery.rs:606-626` 的 `SubagentSpawnRequest` 没有历史字段，`parent_run_id: None`。`apps/agent-workbench/src-tauri/src/subagent_spawner.rs:531-539` 缺省时取 `current_runs[parent_session_id]`。`752` 启动选项 `history: None`。`1150-1153` 再 `unwrap_or_default()`，空变成 `""`。`crates/orchestrator/src/subagent_events.rs:249-254` 与 `287-292`：父 run id 为空时事件 run 列为 `None`。`crates/orchestrator/src/lifecycle.rs:415-416` resume 的 `inject_bytes` 来自 `current.messages`。同文件 `559-561` 写明 spawn 落库行的 `messages` 列恒空。`609-623` `subagent_history` 的注释写「待 history 字段落地后一行接入」；`recovery.rs:188-210` 的 `RunFailureContext` 没有 `history` 字段。全仓只有 `crates/orchestrator/tests/kill_all.rs:1377` 调用 `subagent_history`。`lifecycle.rs:402-411`：没有 `subagent_path_json` 的普通 spawn 直接拒绝 resume。
- 机制：`decide_fork_context` 的 `Verbatim` 表示「有注入字节」。字节数统计的是行上那份恒空消息，子会话里已经落库的对话不算进去，所以模式通常是 `New`。即便某次被算成 `Verbatim`，spawn 请求也不接收历史，启动选项再写死 `None`。父 run 不从原行复制，而从「这个父会话现在正在跑谁」推断。fork 发生时若父会话已经换了 run，新子代理的开始/结束事件挂到新 run 上；父会话闲着则挂到空 run id。
- 影响：重派后的子代理只看到任务文本，看不到被打断前的对话和工具结果。事件按 run 查询时，对不上发起它的那次父 run。普通 spawn 本来就不能 resume，这是函数自己写明的限制；能 resume 的恢复 fork 同样继承不到上下文。

### BC07-5 强停没投进活动 run 时，行和结束事件已经写成终止

- 现象：`kill_all` / `kill_subagent` 先问引擎要不要强停。引擎找不到该 run 时返回 false。两条命令仍把 `session_agents` 行写成 `failed`，并直接发 `subagent-ended`，状态是 `cancelled`。`kill_subagent` 的返回值仍是 `killed`。找到活动 run 时，只往该 run 的控制总线投 L3，不打这份 run 的 `abort_signal`。
- 证据：`crates/orchestrator/src/lifecycle.rs:225-239` 未投递的目标放进 `non_terminal`。`245-262` 随后对全部目标写 `failed` 并发结束事件，不看投递结果。`313-325` 单目标在 `delivered == false` 时仍 `mark_row_failed`、`emit_killed_ended`，`outcome` 为 `"killed"`。`apps/agent-workbench/src-tauri/src/run/run_core.rs:1125-1135`：`active_runs` 没有这个 id 就返回 false；有则 `request_subagent_force_cancel`。`crates/session-loop/src/control.rs:328-336` 该调用只入 L3 队列。用户强停会另打 `abort_signal`（`apps/agent-workbench/src-tauri/src/run/run_launch.rs:1209`），这条子代理路径没有对应的一句。
- 机制：行状态和结束事件在命令返回前写完。控制意图要等循环下一个安全点才被看。run 已不在 `active_runs`（重启后没再跑起来、或 id 对不上）时，没有任何循环会读到这次 L3，行却已经是失败、事件已经是取消。run 还在活动表里时，流读取仍看自己的 abort 信号，当前请求不会因为这次 kill 被选中取消。
- 影响：调用方和父代理看到「已杀掉」。子 run 可能仍在读流和写工具结果，也可能根本没被信号碰到、只是账本先死了。与 14 路 BC14-6 是同一事实，这里从 lifecycle 的返回值和未投递分支记。

### BC07-6 没有清单时，否定句里的完成字样会把目标判完成

- 现象：助手正文里出现独立的 ASCII 单词 `done`（大小写不敏感），或任意位置出现子串「目标已完成」，在没有 checklist 时，本轮评估结果是 `Completed`。`not done`、`不是目标已完成` 都会命中。
- 证据：`crates/orchestrator/src/goal_state.rs:515-532`：先 `contains("目标已完成")`；再对小写字节做长度为 4 的窗口，前后只要不是 ASCII 字母数字就算边界。`354-362`：`looks_done && !has_tasks` 返回 `GoalDecision::Completed`。生产消费看的是这个 `decision`：`apps/agent-workbench/src-tauri/src/run/run_resume.rs:367-372` 调用 `assess_round`，`400-405` 把 `Completed` 收成 `action=complete`。续跑门闩是 `goal_pending`（`run_idle.rs:150-153`），完成后 `is_active()` 为假，不再续。
- 机制：L0 是子串和单词边界，没有否定词。checklist 为空时 L0 单独就能收口。有未完成清单时，同一句完成字样不会收口（`354` 要求 `!has_tasks`），这条只打在「全文没有任务行」的回合上。
- 影响：模型说还没做完、或引用「不是目标已完成」，目标账本会被写成完成，idle 不再为这个目标续轮。

### BC07-7 依赖图的环检测和失败策略没有生产调度器驱动

- 现象：`FlowGraph::validate` 会查重、查悬空依赖、查环。`advance` 会按 Skip / Report / Block 处理失败节点，并带 `parent_run_id` 去 spawn。生产代码没有 `FlowScheduler::new`、`load`、`declare_flow` 的调用。真实子代理走 `run_subagent` / spawner。查询接口只读 meta，不启动 run，也不在子代理终态时推进图。
- 证据：`crates/orchestrator/src/flow_graph_model.rs:259-266` `from_declaration` 调用 `validate`。`304-306` 环检测失败即 `FlowGraphError::Cycle`。`355` `detect_cycle` 本体。`crates/orchestrator/src/flow_graph_scheduler.rs:488-489` `declare_flow` 用这份校验后再推进。`crates/orchestrator/src/flow_graph_advance.rs:141-157` 只有 `advance` 会按节点构造 spawn，`parent_run_id` 取 `planner_run_id`。`341-367` 在节点失败时应用三种策略并再次 `advance`。`FlowScheduler::new` / `load` 的引用都在测试里：`apps/agent-workbench/src-tauri/src/subagent_spawner.rs:2579` 起是 `#[cfg(test)]` 模块，以及 `crates/orchestrator/tests/flow_scheduler.rs`、`crash_consistency.rs`、`multi_agent.rs`、`kill_all.rs`。生产终态处理 `subagent_spawner.rs:1084-1132` 更新行、发 `subagent-ended`、喂给 wait、向父会话入队，没有 `FlowScheduler::on_subagent_terminal`。`apps/agent-workbench/src-tauri/src/run/run_commands.rs:446-482` `get_flow_snapshot_impl` 只读 `flow_declaration` / `flow_state` 和子代理行。`crates/orchestrator/src/flow_graph.rs:15-17` 本文件是门面，逻辑在上述三个子模块。
- 机制：环检测和失败策略的代码路径是 `declare_flow` → `validate` → `advance`，以及终态回调里的策略分支。没有任何生产装配创建调度器，所以声明不会落库，终态也不会回来推下一节点。`session_agents.description` 里预留的 `flow_node_id` 载体（`subagent_spawner.rs:1155-1168`）没有调度器去读。另外声明键写在 `session_meta`，读取 SQL 只有 `key`、没有 `session_id`（`crates/conex-db/src/sessions.rs:194-197`，键名 `flow_graph_scheduler.rs:258`，写入适配 `296-304`）。当前没有生产写入方，这条存储形状要等调度器真接上才会让两个会话共用一份声明。
- 影响：带环的依赖图不会在真正启动 run 之前被拒绝，因为根本没有这条启动。节点失败后的跳过、阻塞、上报也不会发生。调用方从快照接口看到的是空声明或历史残留 meta，不是一张正在跑的图。

### BC07-8 steering 队列与 session-loop 输入队列是两条消费路径，崩溃前的 pending 输入没有被放回

- 现象：队列文档把 `transfer_follow_up` 写成进入 session-loop follow-up 环的适配。生产续跑不调用它。生产把该会话的队列条目拼成一条用户消息，强制 `kind=steering`，丢掉附件，只保留最新 16 条，然后新开一轮。恢复管理器会把 `pending_inputs` 表装进 `RestoreOutcome`，壳层恢复不读这个字段，启动处再把返回值丢掉。
- 证据：`crates/orchestrator/src/steering_queue.rs:220-239` `transfer_into_input_queue` / `transfer_follow_up`。调用点只有测试和注释（`crates/orchestrator/tests/steering_queue.rs:120`、`crates/orchestrator/tests/recovery_ladder.rs:654`、`crates/session-loop/src/input.rs:21`）。生产消费是 `apps/agent-workbench/src-tauri/src/run/run_idle.rs:543-611`：`dequeue_all_for` 之后只拼接 `text`，构造的 `AgentMessage` 没有附件，元数据固定 steering。`crates/orchestrator/src/restore_manager.rs:357-367` 从库加载 `pending_inputs` 放进结果。`run_snapshot.rs:163-269` 的成功路径使用了会话、打断列表、序列号和通知重排，没有读取 `outcome.pending_inputs`。`apps/agent-workbench/src-tauri/src/main.rs:943` `let _ = restore_state.run_restore().await`。`crates/session-loop/src/loop/loop_runner.rs:335-342` 写明崩溃恢复允许这些输入丢失。全仓 `.pending_inputs` 的生产读取只有测试断言（`crates/orchestrator/tests/crash_consistency.rs:587`）。
- 机制：同一条用户后续输入有三条落点。忙时注入进 `PendingMessageQueue`（内存，按会话）。文档化的交接是原样排进 `AgentInputQueue` 的 follow-up 环，等当前 run 到 idle 边界再提升。实际交接是抽干、合并、改写，由 idle 判定再 `start` 一轮。第三条是 `pending_inputs` 表：循环入队时尽力写库，恢复时读回内存结构，然后没有任何一步把这些行重新放进上述两个队列，也没有在恢复成功后删掉它们。快照保存会再读一遍表写进快照文件（`run_snapshot.rs:365-370`），加载快照时恢复逻辑仍只信表、不信快照里的那份，读出之后同样不回放。
- 影响：follow-up 环上的「本轮内不注入、idle 再提升」在生产不发生。多条带附件的转向会被收成一条纯文本，最旧的超过 16 条在文本里被省略。崩溃前已写入 `pending_inputs`、尚未被本轮消费的用户消息，重启后不回到输入队列。

## 已核对闭合或不是问题

- 没有 `run-terminal` 的在途 run（`queued` / `initializing` / `running` / `awaiting-approval` / `cancelling` / `completing`）会写成 `failed`，取消中写成 `cancelled`，原因 `daemon-restarted`（`restore.rs:63-65`，`restore_manager.rs:126-186`）。主 run 不自动续跑是 `run_snapshot.rs:46-70` 里的启动约束：避免把全部历史会话拉起来。函数头 `6-12` 和调用点注释 `242-243` 仍写「主 run 自动续跑」，与函数体相反，这是注释漂移，不单列成能力问题。子代理中断会通知能解析到的父会话。
- 完好的 `run-terminal` 信封把 `terminal` 放在载荷顶层，恢复走权威终态分支，不会落到 BC07-1 的回退字面量。未知状态字面量保真、不打断，是 `restore_manager.rs:206-214` 与 `388-398` 的显式规则。无事件背书的 `completed` 会被改成 `failed`（`187-205`）。
- `RecoveryCoordinator::new` 在 `run_core.rs:965-969`。阶梯失败入口在 `run_resume.rs` 的 `on_subagent_run_failure`，由 idle 收口调用。`fork_and_reassign` 被 lifecycle resume 使用。`restore_steering_notifications` 在 `run_snapshot.rs:220`。整条阶梯不是空实现。缺口是 BC07-3 的空会话 id 和无人 `acknowledge`，以及 BC07-4 的上下文。
- `session_agents` 里残留的 `running` 行会在恢复时归一成 `failed`（`restore_manager.rs:218-256`）。这只改行，不负责把对应 run 重新跑起来。
- goal 的非 `Stop` 收场（`Error` / `MaxTurns` / `Aborted` / `Stopped`）在 `goal_state.rs:330-343` 返回 `Blocked`。`goal_pending`（`187-191`）要求进行中、未达轮数上限、且 `allows_auto_continue`（`normalize.rs:205-207` 仅 `Stop`）。坏 JSON 或缺键经 `from_json`（`199-204`）变成无 goal，idle 不因此续跑。`should_continue` 只在本文件测试里出现，`assess_goal_round` 不读它。所以不存在「运行失败被当成继续」。BC07-6 是无清单时的完成字样被当成完成。
- `detect_cycle` 和三种 `FailStrategy` 在调度器内部有实现和测试。问题是 BC07-7 的生产驱动缺失，不是算法缺席。
- 子代理 run 仍在 `active_runs` 时，强停会进入该 run 的 L3 队列，`ForceCancelSink` 不是空函数。`Pending` 与 `Running` 落库都是 `running`，kill 的行过滤能命中仍在跑的行。BC07-5 只覆盖「未投递仍标死」和「投递了也不打 abort」。
- `started_info_from_spawn`（`subagent_events.rs:304` 起）会填 `subagent_session_id`。`from_subagent_state` 注释里的「未接线」只指旧帧把 `subagent_session_id` 留空，不是所有子代理事件都缺关联 id。关联对不上的生产路径是 BC07-4 的 `parent_run_id: None`。
- 恢复域事件的 `append_event` 不带 run id（`recovery_store.rs:16-32`），这是这个 trait 写明的形状，不另记。
- `derive_task`（`lifecycle.rs:571-580`）已经改读子会话消息，resume 缺省任务不再只看空的 `messages` 列。字节数统计没跟着改，所以上下文模式仍落在 BC07-4。
- 预算 JSON 坏掉时 `RecoveryBudget::from_json` 回到空计数，这是计数器的 fail-open，不表示阶梯没接上。

## 给主控的摘要

1. 本路 8 条，同权，BC07-1 到 BC07-8。
2. 无终态事件的在途 run 会标成 `daemon-restarted`；主 run 按启动约束不自动续跑。两头落空的是坏 `run-terminal`：状态被改成字面量 `run-terminal`。
3. 快照主备都不可用时只按 run 派生空分支会话。叶子 id 不在分支里时，树还原失败被换成空树，启动继续。
4. 阶梯 1/3 和通知重排有生产调用。阶梯 2 与任务唤醒的条目 `session_id` 为空，按会话取不到；`acknowledge` 只有测试调用，pending 每次重启重入队。任务唤醒与 BC14-7 同一事实。
5. fork 的 `context_mode` 只写在记录上。新 run 的 `history` 恒为 `None`，`parent_run_id` 绑到父会话当前 run 或空串。resume 的注入字节来自恒空的 `messages` 列。
6. 强停未投递时，行和 `subagent-ended(cancelled)` 仍写成已终止，`kill_subagent` 仍返回 `killed`。命中活动 run 时只入 L3，不打 `abort_signal`。与 BC14-6 同一事实。
7. goal 的失败收场是 `Blocked`，不会当继续。无清单时 `not done` 和「不是目标已完成」会被 L0 判完成。
8. 环检测和 Skip/Block/Report 只活在 `FlowScheduler` 里。生产没有构造点，终态处理不推进图，查询只读 meta。
9. `transfer_follow_up` 只有测试。生产把队列拼成一条 steering 新消息。`pending_inputs` 装进恢复结果后没有生产读取，启动处丢掉返回值。
10. 未重审 `run.rs` 日常状态机。`recovery_store` 的无 run id 是 trait 写明的形状。孤儿工具自愈写回未单列。
