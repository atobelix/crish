# 会话库持久化

> 日期：2026-10-13
> 范围：`crates/conex-db/src/` 生产代码，以及 orchestrator / 壳层对这套 API 的调用。不重审压缩算法和 run 状态机本身。
> 问题同权。只记当前代码里仍会造成丢数据、写成功但没写上、或两套真相分叉的行为。

## 能力结论

SQLite 库能够存下会话索引、消息正文、事件、run、pending、压缩块和用量。运行期域写入走组提交 Actor 的 `BEGIN IMMEDIATE`。`query_events` / `query_events_by_run` / `query_events_by_type` 已把 `limit` 下推到 SQL；`None` 被实现成 `i64::MAX`，等于不限。消息没有「只追加尾部」的 API，增量契约是整段数组按 `seq` upsert，再删掉超出新长度的尾部。

这套库还不能单独保证「重启后事件序号不撞车、正文和事件是同一份对话、run 行和终态事件一起落盘、坏导入不会改掉已有正文」。打开失败时，壳层会换成空临时库继续跑，旧文件里的会话对这次进程不可见。

## 问题清单

### BC13-1 显式插入的事件不推进序号，同一次恢复里下一次取号会撞上刚写入的 sequence

- 现象：`append_event` 只插入事件行。`session_sequence` 只在 `reserve_sequence` / `seed_sequence` 里变化。计数器行已经存在时，取号不再读 `MAX(events.sequence)`，直接把现有计数加一。恢复打断用 `max(sequence)+1` 直接 `append_event`，不取号、也不 seed。同一次 `restore` 随后的孤儿工具自愈再 `reserve_sequence`，会交出刚被打断事件占用的序号。
- 证据：`crates/conex-db/src/events.rs:301-310`（插入不碰计数器）、`crates/conex-db/src/events.rs:313-335`（`INSERT OR IGNORE` 只在缺行时用 `MAX+1`）、`crates/orchestrator/src/restore_manager.rs:159-180`（先 `update_run_status`，再用 `next_sequence` 的号追加 `run-interrupted`）、`crates/orchestrator/src/restore_manager.rs:404-410`（`max_sequence + 1`）、`crates/orchestrator/src/restore_manager.rs:283` 与 `:766`、`:799`（自愈 `reserve_sequence` 后再 `append_event`）。内存 store 每次取号都会把计数抬到已落库最大序号（`crates/orchestrator/src/persist.rs:550-563`），SQLite 热路径不会。
- 机制：正常跑过的会话已经有 `session_sequence` 行，且 `next_sequence` 等于 `MAX(events)+1`。打断把这个号写进行，计数器仍停在原值。自愈的 `UPDATE … RETURNING` 再把同一个号发出去，主键 `(session_id, sequence)` 拒绝第二行。v4 迁移只原样拷贝旧 `next_seq`（`crates/conex-db/src/migrate_steps.rs:214-216`），不会按 `MAX(events)` 重新对齐。另一条路径：壳层预热用全量 `query_events`，失败时 `unwrap_or(0)` 再 `seed(1)`（`apps/agent-workbench/src-tauri/src/run/run_core.rs:1072-1078`）。`seed_sequence` 是 `MAX(next_sequence, 目标)`，只会抬高，`seed(1)` 抬不动已经落后的计数器。`RecoveryStore::append_event` 把取号和插入分成两次已提交的写（`crates/orchestrator/src/recovery_store.rs:93-100`），中间崩溃留下空洞，不会靠这次拆开制造重复号。
- 影响：同一次恢复里，打断事件已经落库之后，该会话的工具自愈事件插入失败，恢复以错误结束。run 行却已经在前一次提交里改成 failed 或 cancelled。下次启动这条 run 不再是在途，也没有 `run-terminal`，恢复不会再补审计事件。之后的用户事件若再取到这个号，同样插入失败。

### BC13-2 消息正文和事件流是两套真相，空保存会返回成功

- 现象：引擎把回合写进 `events`。用户看得见的对话在 `session_messages`，只由 `save_session_body*` 和恢复自愈回写。两边没有共同事务。无 `batch_version` 的空数组在库里已有消息或已有 `message-start` / `message-end` 时直接 `Ok(())`，不删除、不改 `message_count`。同一条非 CAS 路径只要真的写入，就会把 `sessions.body_version` 归零。
- 证据：`crates/conex-db/src/messages.rs:141-169`（空数组守卫返回成功）、`:147-163`（计数或事件查询失败时 `unwrap_or(0)` / `unwrap_or(false)`，守卫不生效，接着执行尾部删除）、`:246-259`（非 CAS 把 `body_version` 写成 0）、`crates/orchestrator/src/restore_manager.rs:906-912`（自愈用无版本 `save_session_body`，失败只告警）、`apps/agent-workbench/src-tauri/src/session_commands.rs:147-161`（前端保存走同一函数，`batch_version` 可以缺省）。
- 机制：`seq` 是数组下标，不是事件序号。前端整段快照和引擎自愈整段快照谁后提交谁赢。归零之后，进程内 `Some(v)` 只要大于 0 就能通过 `batch_version > body_version`，把自愈刚写上的工具结果覆盖成自愈前的快照。守卫查询若失败，会被当成「没有旧数据」，空数组继续 `DELETE ... seq >= 0`。
- 影响：崩溃发生在事件已落库、前端尚未保存正文时，重开看到的是旧正文，事件里已经有这一回合。调用方收到成功时，正文可能还在，也可能在守卫查询失败时被清空。自愈写上的结果可以被随后一次合法 CAS 整段换掉。

### BC13-3 run 行和终态事件不是一次提交，缺行更新也返回成功

- 现象：`run-terminal` 先插入 `events`，`runs.status` 再由另一次 `update_run_status` 写入。更新语句不看影响行数，目标 run 不存在也是 `Ok(())`。`save_run_usage` 同样是缺行跳过仍成功。恢复只在「事件里已经有终态」时改 run 行。没有终态事件、状态又已经是 `failed` / `cancelled` 时不动，也不补终态事件。没有终态事件的 `completed` 会被改成 failed，这次改写仍不写终态事件。
- 证据：`crates/conex-db/src/runs.rs:149-174`（更新不检查 `changes()`）、`:197-239`（用量缺行仍 `Ok`）、`crates/orchestrator/src/events.rs:571-585`（先 `push` 终态事件，再 `finalize`）、`crates/orchestrator/src/run.rs:480-488`（终态行是第二次写）、`crates/orchestrator/src/restore_manager.rs:75-114` 与 `:187-215`。内存 store 对缺行返回错误（`crates/orchestrator/src/persist.rs:529`）。
- 机制：两次 `write_blocking` 各自 `COMMIT`。进程停在中间时，事件已经是终态而 run 行仍是在途，或 run 行已是终态而事件里没有 `run-terminal`。正常终态载荷是带顶层 `type` 的信封，恢复用 `payload.get("terminal")` 能读到 `completed` / `cancelled` / `failed`。缺的是「行和事件必须同一事务」，以及「没有终态事件时补一条」。
- 影响：只信 run 表的恢复和只信事件的回放会得出不同终态。没插上的 run 行会被后续状态更新悄悄丢掉。没有终态事件的 failed 行重启后一直没有可回放的收口事件。

### BC13-4 导入把解析失败写成成功，并删掉已有正文或子代理

- 现象：localStorage 正文先按 JSON 数组解析，失败再按行解析；坏行跳过。数组整体失败、或行都解析不出消息时，得到空列表。导入仍对该会话执行 `DELETE ... seq >= 0`，然后把该会话计入成功。子代理 JSON 整体解析失败变成空 `Vec`（注释写「坏元素跳过」，实现是整份失败就空），空列表会 `DELETE` 该会话全部 `session_agents`。用量旧快照没有可写入的天，或天数都非法时，仍然写下 `legacy_usage_migrated_v10`。消息导入的列清单里没有 `usage_json`。
- 证据：`crates/conex-db/src/messages.rs:271-295`、`crates/conex-db/src/import.rs:98-152`（空解析结果仍尾删）、`crates/conex-db/src/import.rs:104-120`（插入列不含 `usage_json`；对照 `messages.rs:176-179`）、`crates/conex-db/src/agents.rs:371-376` 与 `:335-343`、`crates/conex-db/src/import.rs:169-175`、`crates/conex-db/src/usage_analytics.rs:263-278` 与 `:334-344`。导入的会话列清单也不含 `body_version`（`import.rs:58-74`）。
- 机制：消息导入没有走 `save_session_body_conn` 的空数组守卫。一条损坏的 JSON 数组不会退化成逐条对象，行解析也救不回，于是「有 body 键」被当成「正文是空的」。`ON CONFLICT` 更新同样不写 `usage_json`：新序号的用量是空，旧序号的用量停在导入前的值。统计里的 `sessions` 照加。用量标记和「有没有写入有效天」在同一次事务末尾无条件执行。
- 影响：一次坏导入可以删光该会话已经在库里的消息或子代理，命令仍成功。消息用量在导入后丢失或停在旧值。用量快照若第一次是空的或坏的，以后好的快照也不会再进 `usage_records`。重新导入后 `body_version` 保持原值，前端若用更小的批次号保存，会 `CasConflict`，新正文写不进去。

### BC13-5 限量读取已经有了，多条生产路径仍把 limit 传成 None，部分失败当成没有事件

- 现象：库 API 支持 `LIMIT`。会话事件 IPC 和 run 事件 IPC 传了 `page_size + 1`。恢复拉终态、工具自愈、快照锚点、审批历史、撤回定位、服务端 `latestSequence`、序列预热仍传 `None`，把整段事件读进内存再过滤或取最大序号。`latestSequence` 和序列预热在查询失败时变成「没有事件 / 下一号是 1」。撤回这三处查询失败会把错误交回去，不会当成空历史。
- 证据：`crates/conex-db/src/events.rs:99-106`（`None` → `i64::MAX`）、`crates/orchestrator/src/restore_manager.rs:427-430`、`:595-596`、`:742`、`apps/agent-workbench/src-tauri/src/run/run_snapshot.rs:357-362`、`apps/agent-workbench/src-tauri/src/run/run_approval.rs:614-654`（先无界读，再内存过滤 `approval-resolved` 并 `take(limit)`）、`apps/agent-workbench/src-tauri/src/retraction_commands.rs:165-170`、`:203-210`、`:343-346`、`apps/agent-workbench/src-tauri/src/server/core_backend.rs:435-441`（`.ok()` 吞掉错误）、`apps/agent-workbench/src-tauri/src/run/run_core.rs:1053-1058` 与 `:1072-1078`（`unwrap_or(0)`）。同库已有 `max_sequence`（`events.rs:190-199`）。有界的 IPC 是 `apps/agent-workbench/src-tauri/src/core_query_commands.rs:763` 和 `run/run_commands.rs:320`。
- 机制：`None` 是不限制，不是库给的安全上限。审批历史的分页发生在全表物化之后。快照用全量事件只为了算每个会话的 max，查询失败会中止这次快照保存。读连接池超时本身会回退到主连接（见已核对），但预热和 `latestSequence` 把任意 `Err` 收成 0 或空。`retraction_commands.rs:210` 的 `unwrap_or(0)` 只覆盖「查询成功且没有行」。
- 影响：长会话上的恢复、快照、审批历史和撤回会按事件总量占用内存。读失败时序列缓存从 1 开始，`latestSequence` 变成空，客户端无法区分「真的没有事件」和「这次没读出来」。与 BC13-1 叠在一起时，失败的 seed 不会把计数器抬过已插入的恢复事件。

### BC13-6 压缩块写入有调用点，但没写上也会返回成功

- 现象：`insert_block` / `update_block_state` 有生产调用。`drive_outcome` 在压缩事件落库后调用 `persist_compression_block`，空闲压缩路径同样调用，摘要回调调用 `update_compression_block_state`。缺表时插入和更新都 `Ok(())`，读取返回空。同键 `INSERT OR IGNORE` 不更新已有行。`UPDATE` 影响 0 行也返回成功。`dropped_message_ids` 坏 JSON 读成空 `Vec`，行仍返回。
- 证据：`crates/conex-db/src/blocks.rs:144-160`、`:222-241`、`:367-371`、`crates/orchestrator/src/events.rs:475-489`（只在 `Err` 时告警）、`crates/orchestrator/src/blocks.rs:36-63` 与 `:92-99`（`get_block` 失败时高度用 1，更新错误才上传）、`apps/agent-workbench/src-tauri/src/run/run_launch.rs:1466`。
- 机制：缺表探测结果按进程缓存。探测为假之后，后续块写入都不会再碰 SQL。两阶段协议的第二阶段无法知道第一阶段没有行。调用方只把 `Err` 当失败，`Ok` 被当成块已落库。
- 影响：块表是事件之外的第二份压缩索引。没写上时事件还在，但按块表恢复的摘要、丢弃消息列表和状态是空的或停在旧行。坏 JSON 会让「哪些消息被折进摘要」变成空清单。

### BC13-7 旧库打不开时，这次进程改用空临时库

- 现象：`LocalDb::open` 迁移失败即返回错误。壳层捕获后 `open_in_memory()`，把诊断记成未就绪，进程继续。内存模式实际是临时 WAL 文件，不是原来的 `sessions.db`。v2→v3 无条件 `ALTER TABLE session_agent_messages`，缺这张表的旧库会在这里迁移失败并掉进这条路径。v3/v4 的删表重建在备份失败时仍继续；备份失败只打到 stderr 和 `session_meta`。版本 5 到 12 不做这次备份。
- 证据：`apps/agent-workbench/src-tauri/src/db_setup.rs:110-133`、`crates/conex-db/src/lib.rs:145-196`（写 Actor 在 `migrate` 之前启动，`open` 返回前迁移仍用主连接）、`crates/conex-db/src/migrate.rs:191-198`（步骤失败返回 `Migration`）、`crates/conex-db/src/migrate_steps.rs:41-43`、`crates/conex-db/src/migrate.rs:75-90` 与 `:159-172`。
- 机制：用户看到的是一个空会话库。新产生的会话写进临时文件。原文件保持打开失败时的样子，这次进程不会再写它。v4 重建会丢掉不属于现存 `sessions` 的事件、run 和 pending（`migrate_steps.rs:146-148`），这是有计数的过滤；备份没做成时，这次过滤没有库外副本。
- 影响：迁移或文件锁一旦失败，旧对话在界面上消失，随后的新对话不在原库里。修复原文件之后，临时库里新写的内容不会自动回去。

## 已核对闭合或不是问题

- `query_events` 无 limit、只能内存分页：API 已闭合。`events.rs:111-112` 有 `LIMIT`。`core_read_session_events` / `read_run_events_impl` 传 `Some(page_size + 1)`（`core_query_commands.rs:763`、`run/run_commands.rs:320`）。未闭合的是 BC13-5 的那些 `None` 调用。
- `append_session_messages`：库里没有这个函数，也没有「只提交新增尾部」的追加。增量是 `save_session_body_conn` 的整段 upsert + `seq >= len` 收缩（`messages.rs:172-237`）。命令有没有接到 IPC 归 15。
- 压缩块写入无人调用：生产路径在 `orchestrator/src/events.rs:476` 和 `run/run_launch.rs:1466`。未闭合的是 BC13-6 的假成功。
- 读连接池超时被库本身当成空结果：`LocalDb::read` 在 `acquire` 失败时回退主连接（`lib.rs:289-299`）。`read_async` 超时返回 `Lock` 错误。池打开失败会换成 0 槽并走主连接（`lib.rs:177-183`）。`try_read` 在池满时返回 `Ok(None)`（`reader_pool.rs:500-507`），生产代码没有调用点。空结果来自 BC13-5 的调用方和 BC13-6 的缺表分支。
- 运行期域写入绕过单写 Actor：会话、消息、事件、run、pending、导入、用量、租约、CAS 的写都进 `write_blocking`。启动迁移使用主连接，发生在 `open` 返回之前，见 BC13-7。
- 正常 v1→v12 链不会丢掉消息正文列。v5 以后的列是 `ADD COLUMN` 或新表，并有列存在检查。`events.run_id` 在后续版本 `ADD COLUMN`（`migrate_steps.rs:414-415`），v4 重建时这列还不存在。`metadata` 在 v4 删除是旧表废弃。v4 丢掉无会话归属的事件/run/pending 有 `migration_v4_dropped_orphans` 计数。
- `insert_run` 冲突更新不覆盖 `created_at`（`runs.rs:124-129`）。组提交在 `COMMIT` 成功之后才把 `Ok` 送回调用方；外层提交失败会把本批结果改成错误（`group_commit.rs:425-441`）。
- `PRAGMA synchronous = NORMAL`（`lib.rs:156-173`）是显式选择。掉电可能丢掉最后一批已返回成功的事务。这不是某条路径把错误收成成功。
- 带 `batch_version` 的过期保存会返回 `CasConflict`（`messages.rs:133-139`）。问题在无版本归零和导入不碰 `body_version`，见 BC13-2、BC13-4。

## 给主控的摘要

1. 库能存会话、消息、事件、run 和压缩块；运行期这些域的写都进单写 Actor。
2. `append_event` 不推进 `session_sequence`；计数器行已在时，取号不再向 `MAX(events)` 对齐。
3. 恢复用 `max+1` 直接插入打断事件，同一次恢复里工具自愈再取号，会撞上刚写入的主键。
4. 打断的 run 行已经先提交；插入失败后这条 run 停在 failed/cancelled，且没有终态事件。
5. 正文在 `session_messages`，回合在 `events`；无版本空保存返回成功，守卫查询失败才会真的删掉正文。
6. 非 CAS 保存把 `body_version` 归零，之后更大的批次号可以覆盖引擎刚写的自愈正文。
7. run 行和 `run-terminal` 分两次提交；更新 0 行也返回成功；没有终态事件的 failed 行恢复不补事件。
8. localStorage 坏 JSON 会被当成空正文，删掉已有消息或全部子代理，导入仍成功，并且不写 `usage_json`。
9. 用量旧快照没有有效天也会写下已迁移标记；`query_events(None)` 仍用于恢复、快照、审批、撤回和 `latestSequence`。
10. 压缩块写入有调用点；缺表、同键忽略、更新 0 行都返回 `Ok`。打开或迁移失败时壳层改挂空临时库。
