# 文件查看器与选区批注链路缺陷审计报告

## 一、选区批注坐标定位与多级滚动容器几何漂移断层

### 【缺陷分类与编号】：选区定位几何越界与顶部悬挂 · DEFECT-FA-01
- **【代码文件与精确行号】**：
  - `apps/crish-desktop/src/components/files/FileAnnotationPopover.tsx:78-87`
  - `apps/crish-desktop/src/components/files/FileViewerCard.tsx:502-505`
- **【断层事实】**：
  在 `FileAnnotationPopover.tsx` 中，浮层垂直坐标直接基于选区边界框相对于宿主容器的相对位置进行计算：
  ```ts
  // apps/crish-desktop/src/components/files/FileAnnotationPopover.tsx:78-87
  let top = rect.bottom - containerRect.top + 6;
  // 若下方越界，自适应向上翻转至选区上方
  if (top + popoverHeight > containerRect.height - 10) {
    const topAbove = rect.top - containerRect.top - popoverHeight - 6;
    if (topAbove >= 6) {
      top = topAbove;
    } else {
      top = Math.max(6, containerRect.height - popoverHeight - 10);
    }
  }
  ```
  在 `FileViewerCard.tsx` 中，传入的 `containerRef` 为最外层的 `cardRef`（`style={{ position: 'relative' }}`），而实际触发滚动的容器是深嵌在 `contentPane` 内的 `VirtualPlainCodeViewer`（`.plainScrollParent`）。
  当用户在代码区选中文本后向下滚动代码内容时，选区元素被向上卷出视口，`rect.bottom < containerRect.top`，导致 `top` 计算值为负数（例如 `-60px`）。此时 `top + popoverHeight > containerRect.height - 10` 判定为假，代码没有任何下限边界防御，`top` 保持负值直接输出给浮层样式。
  反之，当用户向上滚动代码使得选区被卷出容器底部时，`topAbove` 同样超出容器高度，`topAbove >= 6` 判定依然为真，`top` 被赋值为超出视口下方的超大值；若 `topAbove < 6`，则执行回落逻辑 `top = Math.max(6, containerRect.height - popoverHeight - 10)`，将浮层强制吸附在容器最底部。
- **【危害后果 / 真实运行期隐患】**：
  当用户滚动代码使选区滑出视口顶部时，批注浮层不会隐藏，而是以负坐标漂移并悬挂在查看器顶部工具栏、Tab 标签页甚至窗口之外，遮挡核心操作按钮且无法点击；当选区滑出视口底部时，浮层被刚性锁死在视口底端边缘，形成脱离选区上下文的“幽灵悬浮框”。

### 【缺陷分类与编号】：虚拟化节点卸载导致 0x0 坐标孤儿冻结 · DEFECT-FA-02
- **【代码文件与精确行号】**：
  - `apps/crish-desktop/src/components/files/FileAnnotationPopover.tsx:67-70`
  - `apps/crish-desktop/src/components/diff/VirtualPlainCodeViewer.tsx:143-170`
- **【断层事实】**：
  在 `FileAnnotationPopover.tsx` 的选区更新逻辑中：
  ```ts
  // apps/crish-desktop/src/components/files/FileAnnotationPopover.tsx:67-70
  const rect = range.getBoundingClientRect();
  if (rect.width === 0 && rect.height === 0) {
    return;
  }
  ```
  `VirtualPlainCodeViewer` 采用严格虚拟化渲染，随着用户滚动容器，离开视口过切缓冲区的行会被 React 从 DOM 树中彻底卸载。在 Blink/WebView2 引擎中，当处于选区范围内的 DOM 文本节点从文档树脱落时，`range.getBoundingClientRect()` 将直接返回 `width === 0 && height === 0` 的退化矩形。
  此时代码仅执行了 `return;`，既没有清除 `selAnchor` 状态，也没有触发 `handleClose()`。
- **【危害后果 / 真实运行期隐患】**：
  只要选区所在的代码行被虚拟滚动卸载，浮层位置更新事件立刻被短路吞没。浮层永久保留在最后一次有效计算的屏幕物理坐标上，悬空冻结在编辑器中央。用户即使滚动到文件的几千行之外，批注框依然恒定显示在原有位置，指向完全无关的代码。

### 【缺陷分类与编号】：草稿态批注在首发 mint 真会话后彻底孤儿化丢弃 · DEFECT-FA-06
- **【代码文件与精确行号】**：

- **【断层事实】**：
  在 `fileAnnotations.ts` 中，当活跃会话处于草稿态（`activeSessionId` 为空或为 `PENDING_DRAFT`）时，`resolveSessionId` 解析会话键为 `__composer_draft_session__`（或 `PENDING_DRAFT` 常量）：
  ```ts
  // apps/crish-desktop/src/api/fileAnnotations.ts:46-56
  function resolveSessionId(explicit?: string | null): string {
    if (explicit === '') return '';
    if (typeof explicit === 'string' && explicit.trim()) return explicit.trim();
    try {
      const active = useSessionStore.getState().activeSessionId;
      return active && active.trim() ? active.trim() : DRAFT_SESSION_KEY;

      return DRAFT_SESSION_KEY;
    }
  }
  ```
  批注数据随后被存入 `pendingBySession.get('__composer_draft_session__')`。

  ```ts

  ```
  此时传入的 `sessionId` 是新铸造的 `session-1725696000000`，而 `pendingBySession` 中保存的键名依然是 `__composer_draft_session__`。系统没有任何会话状态迁移（promote/transfer）逻辑。
- **【危害后果 / 真实运行期隐患】**：
  `takePendingFileAnnotations` 传入新会话 ID 返回空数组 `[]`，用户在草稿态添加的代码批注在第一次发送时被完全丢弃，不会被组装进任何模型的 Prompt 中；该批注被永久滞留在内存 `pendingBySession` 的草稿键中，沦为不可清除的孤儿数据，甚至在后续开启下一个新草稿时被串扰污染。
