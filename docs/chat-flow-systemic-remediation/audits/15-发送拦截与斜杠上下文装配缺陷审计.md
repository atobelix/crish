# 发送拦截与斜杠上下文装配缺陷审计报告

## 一、发送拦截、前置预检与会话路由缺陷

### 【DEF-SEND-01】引擎实时就绪性检查弱断言放行未就绪状态
- **【代码文件与精确行号】**：`apps/crish-desktop/src/hooks/chat-stream/slashSendPreflight.ts:116-120`
- **【断层事实】**
  ```typescript
  const readiness = await checkEngineReadyRealtime();
  if (!readiness.ok && readiness.domain) {
    setPickerInlineError(domainUserMessage(readiness.domain));
    return { status: 'abort' };
  }
  ```
  `checkEngineReadyRealtime` 返回的就绪状态对象为 `{ ok: boolean; domain?: string }`。当引擎核心通道异常、未连通或连接建立超时，若底层仅标明 `ok: false` 但因未知网络故障未填充 `domain` 字段（`readiness.domain` 为 `undefined` 或空），`!readiness.ok && readiness.domain` 判定直接为假。
- **【危害后果 / 真实运行期隐患】**
  预检逻辑对引擎未就绪状态静默穿透放行，后续消息被强行推进至数据库持久化与底层 IPC 调用，导致消息在未连接的通道中发送失败，产生静默丢失或产生不可恢复的悬挂状态。

## 二、并发控制与 Follow-up 队列管理缺陷

### 【DEF-QUEUE-01】`handleSendChat` 缺少发送中防重互斥锁（In-flight Lock）
- **【代码文件与精确行号】**：`apps/crish-desktop/src/hooks/chat-stream/useSlashSend.ts:68-98, 155-253`
- **【断层事实】**
  ```typescript
  const handleSendChat = async (
    isInsert: boolean = false,
    textOverride?: string,
    attachmentsOverride?: ChatAttachment[]
  ) => {
    // ...
    const preflight = await runPreflightChecks({ ... });
    if (preflight.status === 'abort' || preflight.status === 'handled') {
      return;
    }
    // ...
    const isAiBusy = checkSessionAiBusy(
      streamManagerRef.current?.hasStream(sessionId) ?? false,
      sessionId
    );
    // ...
    addMessage(wsId, sessionId, { id: userMsgId, ... status: 'processing' });
    runStreamingAssistant(input, userMsgId, sessionId, streamOptionsWithClientMsg);
  ```
  `handleSendChat` 为 `async` 函数，在执行 `await runPreflightChecks` 期间存在多次异步 I/O（`checkEngineReadyRealtime`、`import`、配置读取）。在此微任务挂起窗口期内，若用户双击发送按钮或通过快捷键连续快速敲击回车，没有任何同步互斥标识（如 `isSubmittingRef` 或 `isSending`）阻断二次进入。
- **【危害后果 / 真实运行期隐患】**
  两次调用均在首次消息入库前读取到会话为闲置态（`isAiBusy === false`），各自生成新的 `userMsgId`，并发调用 `addMessage(status: 'processing')`，并双双触发 `runStreamingAssistant`。底层引擎瞬间收到两条同会话流式任务，触发底层串行守卫（`SESSION_BUSY` 报错），并在时间线上留下相互践踏的双重用户消息与失控流。

### 【DEF-QUEUE-02】`checkSessionAiBusy` 状态机漏斗导致排队消息乱序插队
- **【代码文件与精确行号】**：`apps/crish-desktop/src/hooks/chat-stream/helpers.ts:312-322`
- **【断层事实】**
  ```typescript
  export function isSessionAiBusy(opts: {
    hasLiveStream: boolean;
    messages?: Array<{ sender?: string; status?: string }> | null;
  }): boolean {
    if (opts.hasLiveStream) return true;
    const msgs = opts.messages;
    if (!Array.isArray(msgs) || msgs.length === 0) return false;
    return msgs.some(
      (m) => m.sender === 'assistant' && m.status === 'processing'
    );
  }
  ```
  忙碌状态判断仅检查了 `hasLiveStream` 以及 `m.sender === 'assistant' && m.status === 'processing'`。
  断层如下：
  1. 用户发送消息后，先入库 `sender: 'user', status: 'processing'`。在助理消息建立之前的几十毫秒间隙内，`messages` 中尚无 `assistant processing`，`isSessionAiBusy` 会误判为闲置；
  2. 当上一轮流式结束、但队列中尚有 `sender: 'user', status: 'queued'` 待调度处理的消息时，`hasLiveStream` 为假且无 `assistant processing`，`isSessionAiBusy` 同样返回 `false`。
- **【危害后果 / 真实运行期隐患】**
  当队列中存在积压消息时，新发送的消息会被直接判为空闲并发起新流式（`status: 'start'`），直接抢先于队列中正在排队的历史消息执行，导致多轮对话次序颠倒，破坏 FIFO 队列保证。

## 三、多模态附件解析与 Payload 构建缺陷

- **【断层事实】**

### 【DEF-HIST-01】前端与 Rust 引擎字段命名风格（snake_case vs camelCase）断裂（特大断层）
- **【代码文件与精确行号】**：`apps/crish-desktop/src/api/chat-bridge/historyMessages.ts:14-19, 140-143` 与 `crates/conex-types/src/history.rs:16, 33, 36`
- **【断层事实】**
  前端 `historyMessages.ts` 构造的 wire 对象字段为下划线风格：
  ```typescript

    tool_calls_json?: string;
    tool_call_results_json?: string;
  }
  // ...

  if (toolCallsJson) entry.tool_calls_json = toolCallsJson;
  ```

  ```rust
  #[serde(rename_all = "camelCase")]

      pub tool_calls_json: Option<String>,        // serde 实际映射键名: "toolCallsJson"
  ```

- **【危害后果 / 真实运行期隐患】**
