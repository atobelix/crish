### 【DEF-TERM-02】`ptyRegistry.ts` 与 `ptySessionApi.ts` 中 `ptyHistoryMap` 导致 Tauri IPC 事件监听器永久不解绑与内存泄漏
- **【代码文件与精确行号】**：`apps/crish-desktop/src/api/ptySessionApi.ts:61-70, 149-160`，`apps/crish-desktop/src/api/ptyRegistry.ts:246-256`
- **【断层事实】**
  在 `ptySessionApi.ts` 中定义了事件清理守卫：
  ```typescript
  // ptySessionApi.ts:61-70

    if (entry.handlers.size === 0 && entry.unlisten && ptyHistoryMap.size === 0) {
      try {
        entry.unlisten();
      } catch {
        /* ignore */
      }
      entry.unlisten = null;
    }
  }
  ```
  解绑底层 Tauri 事件监听器强制要求 `ptyHistoryMap.size === 0`。而在创建 PTY 时：
  ```typescript
  // ptySessionApi.ts:258-260
  if (!ptyHistoryMap.has(ptyId)) {
    ptyHistoryMap.set(ptyId, { chunks: [], totalBytes: 0 });
  }
  ```


  即使所有终端面板均已关闭、所有前端事件回调 `handlers.size` 已清空，底层 Tauri IPC 事件监听器 `EVENT_PTY_OUTPUT`、`EVENT_PTY_EXIT`、`EVENT_PTY_GC_KILLED` 永远无法解绑，形成永久性 IPC 监听器泄漏；且 `ptyHistoryMap` 中残留的历史输出字符串数组无法被垃圾回收，导致前端内存持续泄漏。

### 【DEF-TERM-03】`ptySessionApi.ts` `ptyDetach`、`ptyAttach` 与 `ptyPing` 虚假声明且零调用，导致后端 GC 活性失联

### 【DEF-TERM-04】`ptySessionApi.ts` 中 `subscribePtyOutput` 引发的 Exit / GC 事件全局监听空转与常驻泄漏

- **【断层事实】**

  ```typescript
    handler: (p: PtyOutputPayload) => void

    void ensureTauriListen(EVENT_PTY_GC_KILLED, gcKilledFanout, parseExitPayload);
  ```

## 二、Xterm 渲染、高频数据流与主线程性能阻塞缺陷

### 【DEF-XTERM-01】`ptyLifecycle.ts` 中高频输出无批处理、无节流的密集同步 `term.write` 导致主线程假死冻结
- **【代码文件与精确行号】**：`apps/crish-desktop/src/components/workspace/ptyLifecycle.ts:311-318`
- **【断层事实】**
  ```typescript
  // ptyLifecycle.ts:311-318
  const unsubOut = subscribePtyOutput((p) => {
    if (cancellation.isCancelled() || p.ptyId !== activePtyId) return;
    try {
      term.write(p.data);
    } catch {
      /* swallow-ok: 终端已销毁时输出帧丢弃，不阻断会话 */
    }
  });
  ```
  在接收到底层 PTY 输出时，代码直接无节制地同步调用 `term.write(p.data)`。没有任何写入队列、无 chunk 合并批处理（Batching Buffer）、无 microtask / requestAnimationFrame / 节流调度。
  在执行如 `cargo build -vv`、`npm run build`、`cat large_file.log` 或 `git log` 等产生密集日志的高频命令时，Tauri 后端每秒可产生数千次 IPC output 事件。每一个事件都在浏览器主线程同步驱动 xterm.js 进行 VT/ANSI 转义序列解析与字符状态机运算。
- **【危害后果 / 真实运行期隐患】**
  由于大量碎小 chunk 密集轰炸主线程，JavaScript 事件循环被完全占满，帧率骤降至 0 FPS。不仅终端自身出现严重打字延迟与滚动卡死，整个 Crish 桌面客户端（包括编辑器、对话卡片、工具栏）均陷入完全无响应的假死状态，用户无法进行任何操作。

### 【DEF-XTERM-02】`ptySessionApi.ts` 中 `recordPtyOutputHistory` 密集调用 `shift()` 与重复 `TextEncoder` 导致 O(N^2) 内存颠簸与 GC 停顿
- **【代码文件与精确行号】**：`apps/crish-desktop/src/api/ptySessionApi.ts:86-117, 75-80`
- **【断层事实】**
  ```typescript
  // ptySessionApi.ts:75-80
  function getChunkBytes(chunk: string): number {
    if (textEncoder) {
      return textEncoder.encode(chunk).length;
    }
    return chunk.length;
  }

  // ptySessionApi.ts:96-112
  const chunkBytes = getChunkBytes(data);
  entry.chunks.push(data);
  entry.totalBytes += chunkBytes;

  while (entry.totalBytes > PTY_HISTORY_MAX_BYTES && entry.chunks.length > 0) {
    // ...
    const oldest = entry.chunks.shift();
    if (oldest) {
      entry.totalBytes -= getChunkBytes(oldest);
    }
  }
  ```
  1. 每当有终端日志 chunk 产生时，`getChunkBytes` 内部调用 `new TextEncoder().encode(chunk)`，强制分配一个临时的 `Uint8Array` 实例来读取字节长度；
  2. 当环形缓冲达到 256KB 上限后，每进入一个新 chunk，`while` 循环就会执行 `entry.chunks.shift()`。JS 数组在头部执行 `shift()` 必须将数组内所有后续引用向前移动重排，时间复杂度为 O(N)；
  3. 移出后为了更新 `totalBytes`，又再次对 `oldest` 字符串重复调用一次 `getChunkBytes(oldest)`，又分配一次 `Uint8Array`。
- **【危害后果 / 真实运行期隐患】**
  在高吞吐量日志场景下，持续执行 O(N^2) 的数组元素搬移操作，同时高频分配数万个瞬时 `Uint8Array` 垃圾对象，诱发极其严重的 V8 Major GC 停顿（GC Pause），导致桌面主进程 CPU 占用率飙升并持续掉帧卡顿。

## 三、端口探测器（`activePortDetector.ts`）并发竞争与时序缺陷

### 【DEF-PORT-01】`fetchActiveDevPorts` 并发探测请求无去重与响应乱序覆盖（Race Condition）
- **【代码文件与精确行号】**：`apps/crish-desktop/src/components/workspace/activePortDetector.ts:58-114`
- **【断层事实】**
  ```typescript
  // activePortDetector.ts:58-67
  export async function fetchActiveDevPorts(
    options?: FetchActiveDevPortsOptions
  ): Promise<number[]> {
    const timeoutMs = options?.timeoutMs ?? DEFAULT_TIMEOUT_MS;
    const skipCache = options?.skipCache ?? false;
    const now = Date.now();

    if (!skipCache && cachedPorts !== null && now - lastFetchTime < CACHE_TTL_MS) {
      return [...cachedPorts];
    }
  ```
  1. 函数缺乏任何 Inflight Promise 合并去重机制。当多个组件挂载或多次调用传入 `skipCache: true` 时，瞬间并行发起多个 `fetch('/__crish_active_ports')`；
  2. 请求之间没有单调自增序号（Sequence ID）或时序保护。若较早发起的请求 A 遭遇网络或服务器延迟（耗时 700ms 返回），而较晚发起的请求 B 极快返回（耗时 30ms 返回，发现新端口如 5174），请求 B 先写入 `cachedPorts`；随后请求 A 返回，再次执行：
     ```typescript
     // activePortDetector.ts:105-106
     cachedPorts = ports;
     lastFetchTime = Date.now();
     ```
     请求 A 的旧数据将覆盖请求 B 的最新数据。
- **【危害后果 / 真实运行期隐患】**
  本地端口状态出现幽灵回退，已经启动的开发服务被检测为离线，导致预览面板空态展示错乱或反复抖动。

  ```javascript
  function computeXPath(el) {
    if (!el || el.nodeType !== 1) return '';
    var parts = [];
    var node = el;
    while (node && node.nodeType === 1 && node !== document.documentElement) {
      var index = 1;
      var sib = node.previousElementSibling;
      while (sib) {
        if (sib.tagName === node.tagName) index++;

    }
  ```
