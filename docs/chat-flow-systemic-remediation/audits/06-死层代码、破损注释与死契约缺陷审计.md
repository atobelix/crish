## 二、真实缺陷逐项剖析

### 【缺陷 DEF-01】
- **缺陷分类**：假实现 / 界面荒谬呈现 / 测试打桩死契约
- **代码文件与精确行号**：
  - `apps/crish-desktop/src/components/chat-card/RetrySlotNotice.tsx:9-26`
  - `apps/crish-desktop/src/components/chat-card/ChatStatusRibbons.tsx:363-370`
- **断层事实**：
  ```tsx
  // apps/crish-desktop/src/components/chat-card/RetrySlotNotice.tsx
  export const RetrySlotNotice: React.FC<RetrySlotNoticeProps> = ({
    attempt,
    maxAttempts,
  }) => {
    const max = maxAttempts ?? 0;
    return (
      <div
        className={styles.retrySlotNotice}
        data-testid="retry-slot-notice"
        role="status"
        aria-live="polite"
      >
        <span>
          重连中 {attempt}/{max}
        </span>
        <span data-attempt={String(attempt)} style={{ display: 'none' }} />
      </div>
    );
  };
  ```
  1. `maxAttempts` 为可选字段，在未由后端下发时被强行回退为 `0`，界面直接呈现极其荒谬反常的“重连中 1/0”、“重连中 2/0”。
  2. 历史方案及上层注释（`ChatStatusRibbons.tsx:363`）明示“临时通知老虎机滚动（D8 §3.7.4）”，但底层完全没有任何 slot machine 轮播滚轮动画，仅是一个静态文本 `div`。
  3. 第 24 行包含为应付旧测试而硬塞的无用隐形节点 `<span data-attempt={String(attempt)} style={{ display: 'none' }} />`，且该组件的原生测试文件已被物理删除，沦为残留垃圾。
  4. 该组件没有任何交互回调（无手动重连、无取消重连）。当重试次数耗尽失败后，上层直接将其从 DOM 中卸载移除，导致重试过程在用户眼前静默蒸发。
- **危害后果 / 真实运行期隐患**：
  分母显示为 0 造成严重的用户界面认知障碍与品质感崩塌；无交互手段使重试失败后的网络故障成为不可恢复的黑洞；隐藏标签增加无谓 DOM 开销。

### 【缺陷 DEF-02】
- **缺陷分类**：死成员变量 / NaN 级联算术崩溃 / 二分查找越界截断
- **代码文件与精确行号**：
  - `apps/crish-desktop/src/components/diff/VirtualCodeEngine.ts:24, 41, 77, 83, 139-154`
- **断层事实**：
  ```ts
  // apps/crish-desktop/src/components/diff/VirtualCodeEngine.ts
  export class VirtualCodeEngine {
    private buffer: LineBuffer;
    private wordWrap: boolean; // <-- 死成员变量
    ...
    constructor(...) {
      this.wordWrap = wordWrap;
      this.charsPerLine = Math.max(8, Math.floor(availableWidth / (charWidth || 7.2)));
      ...
    }
  ```
  1. `private wordWrap: boolean;` 在构造器中赋值后，在后续的 `buildSparsePrefixSums`、`isExpanded`、`computeViewport`、`findLineIndex` 等任何方法中**完全没有被读取**，为纯死属性。
  2. 当 `availableWidth` 为 `NaN`（如容器在初始化挂载未完成布局计算或隐藏态触发计算时），在 JavaScript 标准中 `Math.max(8, NaN)` 结果恒为 `NaN`。导致 `charsPerLine` 成为 `NaN`。
  3. 在第 77 行和 83 行：
     ```ts
     accum += Math.max(1, Math.ceil(dw / cpl));
     ```
     `dw / NaN` 为 `NaN`，整个 `prefix` 数组和 `totalVisualLines` 全部被计算为 `NaN`（TypedArray 存入 0 或异常），导致 `computeViewport` 中的 `totalHeight` 计算结果为 `NaN`，视口切片彻底雪崩。
  4. 二分查找边界缺陷（第 139-154 行）：
     ```ts
     private findLineIndex(prefix: Uint32Array, target: number, total: number): number {
       if (total <= 0 || target <= 0) return 0;
       let low = 0;
       let high = total - 1; // <-- prefix 长度为 total + 1，前缀和有效上限是 total
       let ans = 0;
       while (low <= high) { ... }
       return ans;
     }
     ```
     `high` 被强行截断至 `total - 1`，导致二分查找永远无法探查下标 `total`，视口滚动至文件底部时引发末行计算偏移。
- **危害后果 / 真实运行期隐患**：
  容器尺寸抖动或未就绪时，虚拟排版引擎整体被 `NaN` 击穿，整个大文件代码查看器白屏、滚动条高度塌陷；滚动触底时长行排版切片计算失真。

### 【缺陷 DEF-03】
- **缺陷分类**：死导出函数 / 大文件主线程全量扫描卡死 / 虚假格式化契约与解析崩溃
- **代码文件与精确行号**：

- **断层事实**：
  ```ts
  // apps/crish-desktop/src/components/files/jsonFormatUtils.ts
  const JSON_EXT_RE = /\.(json|jsonc|jsonl|ndjson|geojson|topojson|har|map)$/i;

  export function isJsonFileOrContent(filePath?: string | null, content?: string): boolean {
    ...
    if (content && typeof content === 'string') {
      const trimmed = content.trim(); // <-- 数兆大字符串全量复制扫描
      if (
        (trimmed.startsWith('{') && trimmed.endsWith('}')) ||
        (trimmed.startsWith('[') && trimmed.endsWith(']'))
      ) {
        return true; // <-- 粗暴假识别
      }
    }
    return false;
  }

  export function isCompactOrSingleLineJson(content: string): boolean { ... } // <-- 全仓零业务引用死函数

  export function formatJsonSafe(raw: string, indent = 2): FormatJsonResult {
    ...
    try {
      const parsed = JSON.parse(raw); // <-- 对 jsonc / jsonl / ndjson 必抛 SyntaxError 崩溃
      return { success: true, formatted: JSON.stringify(parsed, null, indent) };
    } catch (err) { ... }
  }
  ```
  1. `isCompactOrSingleLineJson` 虽被 `export`，但在整个应用代码库中没有任何业务代码或 Hook 调用，仅在自身单测中空转，属于死代码。
  2. `isJsonFileOrContent` 对 `content` 调用全量 `content.trim()`。在 `FileViewerCard.tsx` 打开数十兆日志或大文本时，主线程强行分配和修剪巨大字符串，引发界面秒级冻结。
  3. 判定算法极度草率：任意首尾包含 `{}` 或 `[]` 的 C 语言、Rust 代码块或 Markdown 文本均被误判为 JSON 文件。
  4. 契约虚假承诺：正则声称支持 `.jsonc`（含注释 JSON）与 `.jsonl` / `.ndjson`（换行分隔的多个 JSON），但在执行 `formatJsonSafe` 时直接调用原生 `JSON.parse(raw)`。原生 `JSON.parse` 无法解析带有注释或多行拼接对象的文本，格式化 100% 报错失败。
- **危害后果 / 真实运行期隐患**：
  非 JSON 源码被误识别为 JSON 导致界面乱弹格式化按钮；点击格式化后必遭解析异常；大文件打开时主线程卡死掉帧。

## 三、结论与危险警示

全仓落地代码中广泛存在**以单元测试脆弱 Mock 掩盖功能未实现**、**以静态脱水文本冒充交互控件**、**声明回调但直接用 `void` 丢弃**、以及**前端布尔值自嗨冒充后端业务闭环**的恶劣架构断层。

这些代码不仅违背了单一真理源与反过度设计的铁律，更在运行期埋下了静默吞没错误、会话死锁、主线程全量扫描卡死与跨会话状态污染的巨大风险隐患。必须对上述缺陷逐项实施穿透根因的架构净化，严禁任何形式的假实现与表面门禁蒙混过关。
