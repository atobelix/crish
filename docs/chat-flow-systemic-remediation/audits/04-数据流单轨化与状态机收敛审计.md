## 缺陷 01：【跨会话覆盖与状态机残留】`localStorage` 全局单键暂存导致多会话并发切换时状态被静默覆盖破坏

- **代码文件与精确行号**：
  - `apps/crish-desktop/src/api/provider-profiles/contextStatePending.ts:26, 126-154, 182-189, 200-212`
- **断层事实**：
  在 `contextStatePending.ts` 中定义了全局单键存储：
  ```ts
  export const PENDING_CONTEXT_STATE_KEY = 'crish_pending_context_state_v1';
  // ...
  function writeStash(stash: ContextStatePayload): void {
    try {
      localStorage.setItem(PENDING_CONTEXT_STATE_KEY, JSON.stringify(stash));
    } catch { /* swallow-ok */ }
  }
  ```
  当用户在会话 A 中切换模型时，`recordPendingContextState` 将 `{ sessionId: 'sess-A', text: '...', ... }` 写入全局单键。如果用户随后在侧边栏切换至会话 B 并触发了配置变更（或新建会话修改配置），会话 B 的快照会无条件覆写该键。当用户切回会话 A 发送消息时，消费逻辑如下：
  ```ts
  export function takePendingContextState(
    currentSessionId?: string | null
  ): ContextStatePayload | undefined {
    const stash = readStash();
    if (!stash) return undefined;
    if (stash.sessionId && stash.sessionId !== (currentSessionId || '')) {
      // 绑定他会话：本次不消费，保留快照供目标会话消费
      return undefined;
    }
    clearStash();
    return stash;
  }
  ```
- **危害后果**：
  在真实多会话切换场景中，会话 A 产生的上下文状态切换快照被会话 B 的暂存无条件覆盖并永久蒸发。当用户在会话 A 中正式发送消息时，由于读取到的暂存属于会话 B，`takePendingContextState('sess-A')` 判定为“绑定其他会话”返回 `undefined`。结果会话 A 的模型/权限切换信息完全丢失，引擎未接收到任何切换指令；而残留的会话 B 暂存因为得不到清理，可能在未来会话 B 的某次调用中被延迟注入，造成严重的时序错乱。

## 缺陷 02：【模块全局变量伪去重】`lastRecordedSignature` 缺乏会话维度导致同模型切换被全局误杀

- **代码文件与精确行号**：
  - `apps/crish-desktop/src/api/provider-profiles/contextStatePending.ts:29, 176-177, 209-211`
- **断层事实**：
  `contextStatePending.ts` 使用了模块顶层单一变量记录去重签名：
  ```ts
  /** 上一次记录的快照签名（模块级去重：状态未变化不重新写入） */
  let lastRecordedSignature: string | undefined;
  // ...
  export function recordPendingContextState(): void {
    const snapshot = buildContextStateSnapshot();
    if (!snapshot) return;
    const text = snapshot.text;
    if (text === lastRecordedSignature) return; // 模块级全局命中
    lastRecordedSignature = text;
    // ...
  }
  ```
  在 `takePendingContextState` 消费暂存时，调用了 `clearStash()` 清空了 localStorage，但**根本没有重置 `lastRecordedSignature`**。
- **危害后果**：
  若用户在会话 A 中将模型切为 `gpt-4o` 并发送了消息（暂存被清空，但 `lastRecordedSignature` 仍为 `gpt-4o` 的文本签名），随后用户切换到会话 B 并同样选择 `gpt-4o`，第 176 行判定 `text === lastRecordedSignature` 成立，直接提前退出！会话 B 无法写入任何暂存。当用户在会话 B 发送首条消息时，由于没有暂存可用，该会话彻底丢失上下文状态切换通知。

## 缺陷 03：【草稿态晋升 ID 断层】草稿态虚拟 ID `'__pending_draft__'` 与晋升真会话 ID 不匹配导致首条消息状态丢弃且孤儿暂存永驻

- **代码文件与精确行号**：
  - `apps/crish-desktop/src/api/provider-profiles/contextStatePending.ts:179-189, 203-208`
  - `apps/crish-desktop/src/hooks/chat-stream/useSlashSend.ts:100`
  - `apps/crish-desktop/src/api/chat-bridge/streamSession.ts:163-165`
- **断层事实**：
  用户在点击“新建会话”处于草稿态时，`activeSessionId` 为虚拟常量 `'__pending_draft__'`; 此时如果用户在顶部切换模型或权限模式，`recordPendingContextState` 记录的内容为：
  ```ts
  const sid = useSessionStore.getState().activeSessionId || ''; // sid === '__pending_draft__'
  writeStash({ sessionId: sid, ... });
  ```
  当用户在输入框键入文字点击发送时，`useSlashSend.ts:100` 调用 `resolveTargetSessionId` 将草稿提交并生成真实会话 ID（例如 `sess-1712345678`），并以该新 ID 启动流式请求：
  ```ts
  const contextState = takePendingContextState(safeSessionId); // safeSessionId === 'sess-1712345678'
  ```
  在 `takePendingContextState` 中：
  ```ts
  if (stash.sessionId && stash.sessionId !== (currentSessionId || '')) {
    return undefined;
  }
  ```
  `stash.sessionId`（`'__pending_draft__'`）与 `currentSessionId`（`'sess-1712345678'`）严格不相等！
- **危害后果**：
  任何在新建对话欢迎页中进行的模型切换、服务商选择或思考档位调整，在用户发送首条消息时 **100% 丢失**！首条消息向后端发起的 `startRunTask` 完全不携带任何 `contextState`。同时，该记录以 `sessionId: '__pending_draft__'` 的形式永久残留在 localStorage 中，既无法被消费也无法被正常清理。

## 缺陷 04：【事件监听器泄漏与内存泄露】`createStreamSession` 异步断层期间任务取消导致 `transport.onMessage` 监听器永久泄漏

- **代码文件与精确行号**：
  - `apps/crish-desktop/src/api/chat-bridge/streamSession.ts:74, 77-158`
  - `apps/crish-desktop/src/api/chat-bridge/streamFinishControl.ts:80-84`
- **断层事实**：
  在 `streamSession.ts` 中：
  ```ts
  state.unsub = transport.onMessage(onMessage); // 第 74 行：注册 IPC 监听
  callbacks.onThought('正在处理…');

  const { getWorkspacePath } = await import('../projectStore');
  // ... 多次 await 跨进程与跨模块异步加载 ...
  const body = await loadSessionBody(safeSessionId);
  // ...
  if (isRunDead(state)) return; // 第 158 行：检测已死亡
  ```
  如果用户在第 77 行至第 156 行的异步加载期间点击了取消或关闭了标签页，`createStreamCancel` 会被执行：
  ```ts
  state.cancelled = true;
  cleanup(); // 调用 cleanupStreamState(state) -> state.unsub?.()
  ```
  但在异步加载完成恢复执行时，第 158 行 `if (isRunDead(state)) return;` 仅仅是执行了 `return;`，**并未再次调用 `cleanupStreamState(state)` 或 `state.unsub?.()`**。
  更严重的是：若在第 59 行到第 74 行之间发生了 cancel，第 74 行依然会强行执行并创建全新的 `state.unsub`，随后在第 158 行被 `isRunDead(state)` 捕获直接 `return;`。
- **危害后果**：
  `transport.onMessage(onMessage)` 的事件监听器被永久泄漏在全局通信总线上。该死去的 run 所持有的 `router`、`callbacks` 以及闭包环境无法被垃圾回收，长此以往引发内存泄漏；当下游 Rust 进程广播事件时，这些僵尸监听器仍会被唤醒并抛出非预期的状态错误。

## 缺陷 06：【草稿态时序倒置与卡片静默吞噬】斜杠命令在草稿态未提交前派发可见卡片导致被底层校验直接丢弃

## 缺陷 07：【异常路径孤儿卡片残留】发送前置校验通过后若底层发送失败，已写入 store 的注入卡片缺乏回滚机制

## 缺陷 11：【会话切换状态撕裂与闪烁】`useChatEmptyKind` 采用 `useEffect` 重置超时状态导致首帧读取过期值引发 UI 抖动

     ```ts
       cacheRef.current = { sid, session, value: selector(session) }; // 渲染阶段直接原地篡改 Ref
     }
     return cacheRef.current!.value;
     ```
     在并发模式、挂起或 StrictMode 双重调用下，渲染阶段修改 Ref 会破坏状态可回溯性，产生非预期视图撕裂。
  2. **缺少返回值比较引发 5 重重渲染风暴**：
     在 `useScopedSessionField.ts:56-57` 中：
     ```ts
     cacheRef.current = { sid, session, value: selectorRef.current(session) };
     forceUpdate();
     ```
     只要当前会话对象的引用发生变化（例如流式输出新增一条 chunk），所有订阅该 session 的 hook 均被触发。在 `useChatMessages.ts` 中连续挂载了 5 个 `useScopedSessionField`（`messages`、`agents`、`hydratedFromEngine`、`engineCursor`、`engineLastRunId`）。后 4 个字段的值根本没有变，但因为没有对 `cached.value` 与新提取的值做 `Object.is` 比较，5 个 Hook 全部无条件调用 `forceUpdate()`！
- **危害后果**：
  每接收到一小段文本流式更新，React 内部就会排队调度 5 次独立的 `forceUpdate()`，引发组件重渲染级联风暴，严重拖垮前端渲染帧率，造成严重的 CPU 开销与输入卡顿。
