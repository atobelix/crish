# 交互伪实现清理与真实控制闭环详案

> **权威路径**：`docs/chat-flow-systemic-remediation/plans/08-交互伪实现清理与真实控制闭环详案.md`  
> **规划属性**：纯逻辑架构详案（无工期、无人天、无优先级、问题同权）  
> **针对缺陷**：DIM-05、DIM-06、DIM-11、DIM-12、DIM-14（audits/05、audits/06、audits/11、audits/12、audits/14）

## 一、断层事实与根因

1. **虚假暂停（ComposerPlanProgressBar 假暂停）**：
   - 现状：前端维护了一个毫无下发通信的本地布尔状态 `isPlanPaused`，点击暂停仅停止前端计时器，后台 LLM 生成和工具执行继续狂奔扣费。
   - 根因：协议层（session-loop）当前仅有 `stop`（终止）协议，未实现 `pause_stream` 协作式打断协议；前端凭空捏造了暂停按钮。
2. **同名附件级联误删（ComposerAttachmentBar 误伤）**：
   - 现状：删除附件时使用 `attachments.filter(x => x.name !== name)`，当用户上传了不同路径下的同名文件（如 `a/index.ts` 和 `b/index.ts`）时，点击删除一个会导致两个同名文件被全部抹除。
   - 根因：未采用唯一 ID 或索引比对，而是使用文件名作为删除的唯一标尺。
3. **存量文件保存必败（useFilePreview 写入被拒）**：
   - 现状：用户在内置文件编辑器中修改已有文件后点击保存，Rust 后端报“文件已存在”拒绝写入。
   - 根因：`useFilePreview.ts` 调用 `writeTextFile(selected, editBuf)` 时，漏传了第三个参数 `overwrite: true`，默认值为 `false`。
4. **重试通知 1/0 荒谬呈现与假滚动（RetrySlotNotice 伪实现）**：
   - 现状：`maxRetries` 缺省为 0 时计算出 `1/0`，且老虎机滚动数字为无动态 DOM 动画的测试桩。
   - 根因：非防御性数值计算，缺乏有效状态保护。
5. **重试链路全线断空（onRetryTool / onRetryInjection 悬空）**：
   - 现状：卡片层声明了重试 props，但最外层 `ChatCard` 与 `useChatMessageState` 的 `toolStackProps` 从未下发 `onRetryTool`。

## 二、架构设计与真实控制闭环

```
┌─────────────────────────────────────────────────────────────┐
│ 1. 真实控制通道 (True Stream Control Contract)               │
│    • 移除伪暂停：仅保留 onStop（终止）与 onEditGoal         │
│    • 若未来接入真实 pause，必须经 IPC 发送 pause_stream 帧   │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. 附件唯一实体控制 (Attachment Unique Entity SSOT)          │
│    • 每个 ChatAttachment 必带稳定 id: string                │
│    • handleRemoveAttachment: findIndex 唯一索引删除          │
│    • 杜绝同名文件级联误删，支持纯附件无文本回车发送          │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. 宿主文件持久化契约 (Host File Persistence Contract)       │
│    • useFilePreview.saveFile 显式传入 overwrite: true       │
│    • 写入前触发外部修改检测（若 content != baseline 提示覆盖）│
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 4. 重试动作与状态机闭环 (True Retry Pipeline)                │
│    • RunNoticeBar 提供真实「重试连接 / 重新发送」闭环动作    │
│    • 失败工具行提供真实 onRetryTool 闭环（重新派发该工具）    │
└─────────────────────────────────────────────────────────────┘
```

## 三、纯逻辑落地执行次序

### 阶段 1：去除假暂停与空状态清理
1. 在 `ChatComposerWrapper.tsx` 中彻底切除本地 `isPlanPaused` 状态与 `onTogglePause` 回调；
2. 在 `ComposerPlanProgressBar.tsx` 中将暂停按钮约束为：仅当显式传入有效 `onTogglePause` 且支持真实流式挂起协议时才渲染，缺省不渲染假按钮；
3. 清理已废弃的 `RetrySlotNotice.tsx` 假老虎机无意义 DOM，防止出现 1/0 荒唐呈现。

### 阶段 2：附件唯一实体索引与发送闭环
1. 在 `ChatAttachment` 中统一保障 `id` 属性；
2. 重构 `ChatComposer.tsx` 的 `handleRemoveAttachment`：
   ```ts
   const targetIndex = prev.findIndex(
     (x) => (x.id && x.id === identifier) || x.name === identifier
   );
   if (targetIndex === -1) return prev;
   return prev.filter((_, idx) => idx !== targetIndex);
   ```
3. 在 `ComposerAttachmentBar.tsx` 中以 `itemKey` 渲染并传递唯一 `removeId`；
4. 修复键盘发送拦截：允许 `attachments.length > 0 && text === ''` 时的回车发送。

### 阶段 3：存量文件保存与外部冲突守护
1. 在 `useFilePreview.ts` 中调用 `writeTextFile(selected, editBuf, true)`；
2. 完善外部冲突检测：`readTextFile` 读取最新内容与 `openedContentRef.current` 比对，若外部已被修改，弹出 ConfirmDialog 提示确认覆盖。

### 阶段 4：真实重试动作链通
1. 在 `RunNoticeBar.tsx` 中提供针对可恢复错误（如网络中断、认证失败、服务超时）的一键重试按钮，点击触发当前会话重试；
2. 在 `ChatCard.tsx` 的 `toolStackProps.actions` 中注入真实 `onRetryTool`。

## 四、验收断言

1. **假暂停消除断言**：在任何会话中进行模型生成，计划进度条中绝对不出现假暂停按钮；
2. **附件独立删除断言**：向输入框同时添加 `dirA/data.csv` 与 `dirB/data.csv`，点击其中一个的删除叉号，另一个同名附件依然完整保留；
3. **文件保存断言**：在文件浏览器中打开存量已有文件，修改内容后点击保存，内容成功写入磁盘且无 `file_exists` 报错；
4. **单元测试**：`ComposerAttachmentBar.test.tsx` 与 `FilePreview.test.tsx` 100% PASS。
