## 一、跨平台原生构建依赖与 CI 流水线审计

### 1.1 Linux (Ubuntu) 构建依赖缺失根因与修复

- **现场问题**：
  在 GitHub Actions `ubuntu-latest` 运行环境中，Rust 内核编译（`cargo check --workspace`）与 Release 打包先后报错：
  1. `error: failed to run custom build command for glib-sys v0.18.1`
  2. `The system library libpipewire-0.3 required by crate libspa-sys was not found. The file libpipewire-0.3.pc needs to be installed.`
- **根因分析**：
  `apps/agent-workbench/src-tauri` 作为 Tauri 1.x / 2.x 桌面壳，依赖系统级 WebKitGTK、GIO/GLib、AppIndicator、PipeWire 及 SPA（用于屏幕录制与多媒体处理）。GitHub Actions 官方 `ubuntu-latest` 镜像仅提供极简开发工具，缺失上述原生系统开发包。
- **物理修复方案**：
  在 [.github/workflows/ci.yml](file:///c:/Software/conex/.github/workflows/ci.yml#L223-L227) 及 [.github/workflows/release.yml](file:///c:/Software/conex/.github/workflows/release.yml#L28-L32) 的 `ubuntu-latest` 作业前，统一部署系统依赖安装步骤：
  ```bash
  sudo apt-get update
  sudo apt-get install -y libwebkit2gtk-4.1-dev build-essential curl wget file libxdo-dev libssl-dev libayatana-appindicator3-dev librsvg2-dev libpipewire-0.3-dev libspa-0.2-dev
  ```
- **验证结果**：
  三端一致性审查确认：CI `rust-check` 矩阵及 Release 流水线中，Linux 依赖包列表 100% 镜像一致，无版本漂移。

## 二、测试资产保护与契约夹具放行

### 2.1 Gitignore 规则吞噬测试夹具事故根因与修复

- **现场问题**：
  CI `rust-unit-fast` 作业中，`conex-types` 的设备协议校验测试报 Panic：
  `thread 'invalid_samples_are_rejected_both_sides' panicked at crates/conex-types/tests/device_parity.rs: 读取样例目录 tests/fixtures/device-protocol/invalid 失败: No such file or directory`
- **根因分析**：
  [.gitignore](file:///c:/Software/conex/.gitignore#L445) 中历史配置了全局忽略规则 `/tests/**/*.json`。该规则粗暴拦截了所有 JSON 文件，导致 `tests/fixtures/device-protocol/` 下用于设备通信契约双向校验的 22 个真实 JSON 夹具文件（6 个 invalid 异常用例、16 个 valid 合法用例）被 Git 忽略，无法检入仓库。
- **物理修复方案**：
  严格遵循 `AGENTS.md §9`「测试资产保护铁律」，在 [.gitignore](file:///c:/Software/conex/.gitignore#L446) 紧随 `/tests/**/*.json` 下方追加白名单反向放行规则：
  ```gitignore
  !/tests/fixtures/**
  ```
- **实测验证**：
  `git check-ignore -v tests/fixtures/device-protocol/invalid/01-missing-auth-sig.json` 确认已不再被忽略。本地执行 `cargo test -p conex-types --test device_parity`：3/3 测试 targets 100% 通过（Exit Code 0）。

## 四、前端 Chunk 循环依赖与架构解耦治理

### 4.1 Vite ManualChunks 依赖环根因分析

- **现场问题**：
  生产构建静态分析门禁 `npm run check:chunk-cycles` 报错：
  ```
  check-chunk-cycles: 发现 3 个 chunk 依赖环：
    chat-provider-catalog-*.js → chat-bridge-transport-*.js → chat-provider-catalog-*.js
    chat-provider-catalog-*.js → chat-bridge-transport-*.js → chat-stream-core-*.js → chat-provider-catalog-*.js
    chat-bridge-transport-*.js → chat-stream-core-*.js → chat-bridge-transport-*.js
  ```
- **穿透根因**：
  1. `apps/crish-desktop/src/api/chat-bridge/` 内部模块高度内聚（`dataPlaneRouter`、`EventRouter`、`streamSession` 互联）。此前人为将其中 4 个文件拆分为 `chat-stream-core`，导致两者产生强依赖环。
  2. `chat-provider-catalog` 匹配规则涵盖 `providerProfiles`。而 `providerProfiles` 间接引用的状态与会话持久化层导入了跨层叶子工具：
     - `computeCacheMetricsFromUsage`（原位于 `chat-bridge/handlers/cacheMetricsCompute.ts`）
     - `eventUtils`（原位于 `chat-bridge/handlers/eventUtils.ts`）
     - `invalidateEditObjects`（原位于 `chat-bridge/editSessionConsumer.ts`）
  3. 上述叶子工具被默认收归 `chat-runtime-core`，而 `chat-runtime-core` 的 `readiness.ts` 又需要导入 `providerProfiles` 获取当前活跃模型，从而形成跨 Chunk 闭环。
- **物理修复方案**：
  在 [apps/crish-desktop/vite.config.ts](file:///c:/Software/conex/apps/crish-desktop/vite.config.ts#L781-L820) 中实现单向有向无环图（DAG）解构：
  1. 将跨层的纯工具函数与底座叶子模块抽离，由 `chat-bridge-common` 优先捕获：
     ```ts
     if (
       n.includes('/src/api/chat-bridge/handlers/cacheMetricsCompute') ||
       n.includes('/src/api/chat-bridge/handlers/eventUtils') ||
       n.includes('/src/api/chat-bridge/editSessionConsumer')
     ) {
       return 'chat-bridge-common';
     }
     ```
  2. 将传输协议与流式恢复核心统一整合为 `chat-runtime-core`。
  3. 最终形成严格单向的静态依赖拓扑：
     `chat-runtime-core` → `chat-provider-catalog` → `chat-bridge-common` → `vendor-shared-utils`。
- **门禁验证**：
  - `npm run check:chunk-cycles`：**107 个 chunk 零依赖环（0 cycles）通过**。
  - `node scripts/check-dist.mjs --max-app-kb 500 --csp-enforce`：主入口 322 KB < 500 KB，CSP 严格合规。
  - `node scripts/check-startup-budget.mjs --strict`：入口 314.5 KiB / 520 KiB，静态图 1500.2 KiB / 1800 KiB 全部在预算内。
