## 一、核心测试套件健康度评估

### 1.1 Rust 内核测试（`cargo test --workspace`）

#### 现状数据与健康度

- **用例与套件规模**：全仓包含 161 个测试套件，合计 6322+ 个测试用例，覆盖 27 个 Workspace 成员 crate。
- **通过性表现**：在单线程编译模式下，`cargo test --workspace -j 1` 全量测试处于全绿状态（参考 `FULL_CHECK_COMMANDS.md:61` 实测基线）。
- **CI 分层布局**：
  - 快层（`ci.yml:229`）：仅运行核心子集 `cargo test -p conex-types -p session-loop --locked`（约 15-30s 内完成）。
  - 中层（`ci-mid.yml:46`）：运行 `cargo test --workspace --locked`，作为 PR 合并前兜底。
  - 慢层（`ci-slow.yml:38`）：以 Release 模式运行全量压测场景 `cargo test --workspace --release --locked -- --ignored`。

#### 核心差距与隐患分析

1. **Windows 本地内存瓶颈与编译损坏假象（硬性环境陷阱）**：
   - **确凿证据**：`FULL_CHECK_COMMANDS.md:28` 明确标注 `cargo test --workspace -j 1（-j 1 必带：Windows 页面文件余量有限，默认并行编译曾 OOM 中断并留下「产物损坏」假象 E0463）`；`scripts/check-provider-single-track.mjs:142`（D2 防线）甚至写入门禁强制断言全量命令必须带 `-j 1`。
   - **外部影响**：外部开源贡献者在 Windows 机器上若直接按开源常规认知运行 `cargo test --workspace`，极易因并发编译 OOM 导致 rustc 崩溃并报错 `E0463: can't find crate for ...`，导致开发者误以为代码库被破坏。
2. **重度依赖 Faux/Mock，真实系统调用与网络穿透不足**：
   - **确凿证据**：`ci-mid.yml:44` 注释坦陈 `全量测试：L1 单测 + L2 集成 + L3 契约 + L4 e2e faux`。如 `crates/orchestrator/tests/approval.rs:30-60` 使用内存 fake store 与内存事件队列；`crates/session-loop` 测试使用 `MockProvider`。
   - **差距级别**：**P1 关键级**。真实 OS 进程 spawn、真实 TCP/HTTP 异常穿透测试在 Rust 侧近乎空白。

### 1.3 前端测试（Vitest 单元/集成套件）

#### 现状数据与健康度

- **测试规模**：`packages/` 下 87 个测试文件（900 个用例全绿，耗时 ~12s）；`apps/crish-desktop/src/` 下 785 个测试文件。
- **项目结构（`vitest.config.ts:57-134`）**：
  - `unit`：覆盖 `packages/*` 与 `apps/crish-desktop`、`apps/agent-workbench` 绝大部分单测；
  - `integration`：覆盖 `tests/stress` 与 `apps/crish-desktop/tests/{integration,race,recovery,fuzz}`（共 12 文件）；
  - `native-smoke`：独立项目，承载 `tests/e2e/tauri-native-smoke.spec.ts`。

#### 核心差距与隐患分析

1. **覆盖率门禁的全局覆盖陷阱与误导性报错**：
   - **确凿证据**：`vitest.config.ts:3-14` 指出，Vitest 3.2.7 的根 `test.coverage` 块会强制覆盖项目级阈值（`thresholds: { statements: 45, branches: 70, functions: 65, lines: 45 }`）。
   - **实测影响**：`vitest.config.ts:47-49` 注明，`integration` 项目实测覆盖率仅 `3.75% / 61.16% / 33.5% / 3.75%`。当外部开发者习惯性执行 `npm run test:coverage`（全量运行）时，会因为 `integration` 项目覆盖率未达到 45/70/65/45 而**直接导致测试套件失败**。必须手动传入专项参数 `npm run test:coverage -- --project=unit` 才能通过。
2. **测试运行环境的双重人格（Node 伪装与 jsdom 偶发冲突）**：
   - **确凿证据**：`vitest.config.ts:61` 将 `unit` 项目的默认环境设为 `environment: 'node'`，但在 `vitest.setup.ts:40-60` 中通过全局对象挂载大量的浏览器垫片（`localStorageMock`, `sessionStorageMock`, `globalThis.window = globalThis`, 自定义 `CustomEvent` 模拟器）。
   - **脆性隐患**：部分 UI 组件测试文件在头部声明 `// @vitest-environment jsdom`（如 `vitest.setup.ts:34-39` 所述）。这导致在同一套配置下，部分测试运行在 Node+垫片中，部分运行在真实 JSDOM 中；历史事故记录显示，如果全局补齐不当，会导致 `localStorage instanceof Storage` 判定为 false，原型链 spy 拦截静默失效。
3. **官方文档与基线记录的历史残留漂移**：
   - **确凿证据**：`FULL_CHECK_COMMANDS.md:62` 仍记载 `chat-bridge / approval / conversation-flow / workspace / store / styles 等 33 文件 ⏳ 存量失败`。
   - **实际情况**：本次实测运行 `apps/crish-desktop/src/store`（56 文件/660 测试）、`approval`（10 文件/173 测试）、`styles`（11 文件/159 测试）均已全绿。文档中记载的“33 个存量失败文件”属于旧战役遗留的陈旧账目，未及时同步，严重干扰外部开发者对项目健康度的客观认知。
   - **差距级别**：**P1 关键级**。

## 三、自定义门禁脚本体系（`scripts/check-*.mjs`）全量盘点

### 3.1 门禁脚本全景统计

全仓 `scripts/` 目录下累计存在多达 **60 个**以 `check-*.mjs` 命名的静态与架构守卫脚本，形成了极度庞大的自定义守卫网。

  在 package.json 脚本中注册             : 44 个 (73.3%)

### 3.4 脚本跨平台运行环境脆弱性分析

1. **强依赖外部 Git CLI 与全局仓库元数据**：
   - 如 `check-repo-integrity.mjs:34`、`check-conflict-markers.mjs`、`check-source-assets-tracked.mjs` 等大量脚本通过 `execFileSync('git', ...)` 与本机 Git 深度绑定。外部开发者若通过 zip 下载源码解压开发，或处于 linked worktree、shallow clone、submodule 环境中，脚本会直接因找不到 Git 指针或特定 ref 而 crash。
2. **路径分隔符与正斜杠/反斜杠兼容性风险**：
   - 部分脚本内部未统一使用 `path.normalize()` 或将 Windows 反斜杠 `\` 归一化为 `/`，在按文件路径做正则排除（如 `node_modules` 判定、路径深度切分）时，跨平台容易出现假阴性或假阳性。
3. **换行符（CRLF / LF）误报敏感性**：
   - `check-css-encoding.mjs` 与代码行数扫描脚本在 Windows 下若受 `core.autocrlf=true` 影响引入 `\r\n`，常因字节序与换行符计数产生偏移，误触发行数或编码门禁。

## 四、Git Hooks（Husky）与提交门禁摩擦力评估

### 4.1 `.husky/pre-commit` 门禁强度与副作用审查

#### 现状实现（`.husky/pre-commit:1-16`）

```bash
git diff --check
node scripts/check-conflict-markers.mjs
node scripts/check-runtime-status-ssot.mjs
node scripts/check-repo-integrity.mjs
node scripts/check-guard-system.mjs
node scripts/check-token-fallback-drift.mjs
node scripts/check-inline-style-hardcode.mjs
node scripts/check-session-message-upsert.mjs
node scripts/check-tool-pairing-invariants.mjs
node scripts/check-db-write-bypass.mjs
node scripts/check-frontend-convergence.mjs
```

#### 致命摩擦力证据

1. **`git diff --check` 扫描全工作区（严重反常识）**：
   - **确凿证据**：第 1 行是裸 `git diff --check`，未带 `--cached`！
   - **后果**：如果外部开发者修改了 `A.ts` 并 `git add A.ts` 准备提交，但其工作区内有未暂存的笔记、临时 scratch 文件，或者被某些编辑器自动补齐了行尾空格，`git diff --check` 将扫描整个工作区并**拦截当前的独立提交**！`AGENTS.md:43` 甚至专门为此立下一条规则（“他人文件的 trailing whitespace 会阻塞所有提交……”），这在开源协作中属于极其不可接受的体验。
2. **完全旁路 `lint-staged`**：
   - `package.json:138-149` 费心配置了 `lint-staged`（支持 eslint --fix 与 prettier 自动格式化暂存区），但在 `.husky/pre-commit` 中根本没有调用 `npx lint-staged`！取而代之的是无差别串行执行 10 个 Node 脚本。
3. **本地提交耗时过长**：
   - 实测仅这 10 个 Node 脚本的顺序执行就需要 **6.1 秒**。外部开发者每次执行小步提交（`git commit`）都要经历 6 秒以上的机械等待。

### 4.2 `.husky/pre-push` 门禁强度与体验灾难

#### 现状实现（`.husky/pre-push:1`）

```bash
npm run typecheck && npm test
```

#### 致命摩擦力证据

1. **推送前全量运行数千测试（严重过度防御）**：
   - 每次 `git push` 时，Hook 会完整执行 `npm run typecheck`（5 个项目）和 `npm test`（运行 870+ 测试文件、4400+ 个用例）；
   - 在标准开发者机器上，完整执行耗时通常在 **1.5 至 3 分钟以上**；
   - 只要有任意一个脆弱用例（flaky test）出现微小超时，或者开发者仅修改了 README/文档，整个 `git push` 即被硬性中止；
   - **次生灾害**：极高的摩擦力会导致外部贡献者普遍采用 `git push --no-verify`，最终彻底架空了本地保护体系。

- **差距级别**：**P0 阻断级（开源体验灾难）**。

## 五、覆盖率与测试缺口（未测关键链路）

### 5.1 模型 Provider 真实网络栈与 HTTP 行为零覆盖

- **现状**：`crates/agent-provider/src/` 包含了对 Anthropic、OpenAI、Gemini、DeepSeek、Azure 等多家厂商协议的完整解析与构建逻辑。

### 5.2 工具执行审批（Approval）端到端真实闭环缺口

- **现状**：

  - **缺乏跨进程真实交互链路测试**：没有自动化用例测试“高危命令触发 -> Rust 内核拦截并下发 `approval-requested` -> 前端渲染审批卡片 -> 用户点击同意/拒绝/记忆权限 -> 前端发送 IPC `approval_resolve` -> Rust 内核唤醒对应线程在沙箱执行/拒绝”的完整端到端链路；
  - Playwright E2E 中，审批完全由前端本地模拟的假事件直接驱动，脱离真实状态机。

### 5.3 跨窗口与并发文档协作（Cross-Window / Collab）测试缺口

- **现状**：
