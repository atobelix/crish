## 摘要与就绪度综合评定

本审计报告针对 Conex / Crish 仓库正式在公网（GitHub）开源分发的法律合规性进行了全面穿透式审查。审查覆盖根目录许可证、法定归属文件、全量依赖图谱（872 个 Cargo crate + 1576 个 npm package）、静态资源与字体版权、SPDX 源码标头覆盖率以及 CI/CD 自动化门禁等 6 大核心领域。

**当前法律与合规就绪度状态：基本面健康，但存在 3 处高风险阻断点与多项法定归属缺失，未达到直接公开发布标准。**

  1. **高风险**：Git 外部依赖 `tauri-plugin-mcp`（`apps/agent-workbench/src-tauri/Cargo.toml:36`）在 Cargo 层面处于**无许可证状态**（`license: null`，上游仓根目录无 LICENSE 文件），属于严重法律盲区；

## 维度一：根目录 LICENSE 完整性与法律效力审查

### 1. 现状事实与确切证据

根目录 `LICENSE`（[`LICENSE:1-22`](file:///C:/Software/conex/LICENSE#L1-L22)）全文如下：

```text
1: MIT License
2:
3: Copyright (c) 2026 Conex Community
4:
5: Permission is hereby granted, free of charge, to any person obtaining a copy
...
21: SOFTWARE.
```

- **协议类型**：标准 MIT 许可证（SPDX: `MIT`）；
- **版权声明所有者**：`Conex Community`；
- **声明年份**：`2026`；
- **配置一致性**：
  - 根目录 `Cargo.toml:34-35` 声明：`license = "MIT"`，`authors = ["Conex Community"]`；
  - 根目录 `package.json:6` 声明：`"license": "MIT"`。

### 2. 法律合规深层缺陷分析

1. **主体资格模糊性（Legal Entity Ambiguity）**（风险等级：**低**）：
   - 版权主体标明为 `"Conex Community"`。在普通法系与大陆法系中，“Community” 本身若未登记为法律实体（如 501(c)(3) 非营利基金会、合伙或有限责任公司），其作为民事主体的主张在著作权诉讼或维权场景中可能存在主体认定瑕疵。
   - **建议**：在 `README.md` 或 `NOTICE` 中明确指出：`"Conex Community refers to the collective contributors of the Conex / Crish open source project."`。
2. **缺乏显式专利授权（Patent Grant Retaliation）**（风险等级：**中**）：
   - MIT 协议仅赋予“使用、复制、修改、合并、发布、分发、再许可和/或销售软件副本”的版权许可，**不包含类似 Apache-2.0 第 3 条的显式专利授权（Patent License）与专利报复终止条款（Patent Retaliation Clause）**。
   - 如果未来有第三方将包含专利的技术贡献进代码库，随后向使用者索赔专利费，MIT 许可证无法提供刚性防御。
3. **商标权边界缺失（Trademark Disclaimer）**（风险等级：**中**）：
   - 标准 MIT 文本不包含商标保留条款。第三方在 Fork 或商业二次分发时，可能滥用 "Conex" 或 "Crish" 的名称与标识，引发品牌混淆。

## 维度二：缺失的法定文件与合规归属资产审查

### 1. 现状事实与确切证据

经对根目录及关键目录的严格排查，发现以下法律及归属文件**全量缺失**：

1. **`NOTICE` 文件**：缺失（根目录无此文件）；
2. **`THIRD-PARTY-LICENSES.md`（或 `ATTRIBUTION.md` / `LICENSES/`）**：缺失；
3. **`PATENTS` 专利政策文件**：缺失；
4. **贡献者协议（DCO / CLA 政策声明）**：缺失（`CONTRIBUTING.md` 中未定义任何贡献者许可条款）；
5. **商标政策（Trademark Policy）与免责声明**：缺失。

### 2. 法律风险穿透分析

#### 2.1 缺少 NOTICE 与第三方归属文件（违约风险：高）

- **许可证法律义务**：
  - **MIT 许可证第 12-13 行**明确要求：`"The above copyright notice and this permission notice shall be included in all copies or substantial portions of the Software."`；
  - **Apache-2.0 许可证第 4(d) 条**要求：若被分发产品包含第三方代码，必须在分发包中保留原有的版权声明与 NOTICE 说明；
  - **SIL Open Font License (OFL-1.1) 第 2 条**强制要求：内嵌字体分发时必须附带版权所有人声明与许可证全文。
- **现状危害**：
  - 当前打包产物（Tauri 桌面应用二进制分发版）直接静态编译了数百个 Rust crates 和 npm 依赖包，**但未在软件安装包、设置界面或发布包中附带任何第三方许可证归属清单**，直接构成了对上游开源协议中“保留版权声明”条款的形式违约！

#### 2.2 缺少贡献者授权协议 CLA / DCO（所有权污染风险：高）

- 当项目在 GitHub 公开接收 Pull Request 时，若未要求贡献者签署 CLA（Contributor License Agreement）或签署 DCO（Developer Certificate of Origin，即 `git commit -s` 签名），外部提交者的代码所有权归属将产生法律不确定性。一旦产生法律纠纷，个别贡献者可能主张撤回授权或声称侵权，阻碍开源项目的长久发展。

#### 2.3 缺少商标政策与声明（品牌维权风险：中）

- 项目命名包括 "Conex" 与 "Crish"，在缺乏明确的 Trademark Guidelines 情况下，社区分发版容易被恶意打包或被冒名发布含有恶意载荷的二开版本。

#### 2.2 商标侵权与合理使用（Fair Use）法律边界

- **法律性质判定**：
  商业公司 Logo（如 OpenAI 花朵标、Anthropic 辐射标、Google Gemini 四芒星、Apple 苹果标）属于**受严格保护的注册商标（Registered Trademarks）**，其权利独立于开源著作权法之外。即使上游图标库（如 `@lobehub/icons`）本身采用 MIT 协议开源，该 MIT 协议**仅涵盖图标代码实现的著作权，完全不代表商标所有权人的商标授权**！
- **合理使用（Nominal Fair Use）前提条件**：
  在开源客户端软件中展示这些 Logo，仅可用于“表明系统支持与该特定模型厂商服务对接”的名义合理使用。为免受侵权指控，**必须在法律层面做到三点**：
  1. **明确商标归属声明**：在 `NOTICE` 或 `LEGAL.md` 中声明各商标归其各自所有者所有；
  2. **声明无背书关系（Non-affiliation Disclaimer）**：明确说明使用其 Logo 并不意味着获得这些厂商的赞助、背书或商业合作；
  3. **注明上游代码署名**：为 `@lobehub/icons` 保留必要的 MIT 署名声明。

### 2. 规范性与合规风险分析（风险等级：中）

- **开源标准规范要求**：
  - 遵循 Linux 基金会推荐的 **REUSE 规范**（Software Package Data Exchange, SPDX）与 **OpenChain ISO/IEC 5230** 标准，开源项目应在每个具有独创性的源代码文件头部嵌入标准许可证标识符，例如：
    ```rust
    // Copyright (c) 2026 Conex Community
    // SPDX-License-Identifier: MIT
    ```
- **实际影响**：
  - 虽然 MIT 许可证本身并没有“必须逐文件打标”的刚性要求（根目录 LICENSE + package 配置已具备基础法律效力），但在以下场景中无标头会带来严重阻碍：
    1. **Linux 官方源打包审核**：Debian / Fedora / Alpine 维护者在引入软件包时，通常使用机器扫描（如 `licensecheck`、`scan-copyrights`），0 覆盖率会导致打包审核被驳回或要求繁琐的例外说明；
    2. **企业级合规扫描工具**：FOSSA、Black Duck、Snyk、Mend 等商业合规扫描仪在扫描子目录代码时，会将其误报为 "Unlicensed Code"，增加企业采纳门槛；
    3. **独立模块解耦发布**：当某个 crate（如 `conex-db` 或 `conex-types`）未来独立发布至 crates.io 时，单文件溯源清晰度严重不足。
