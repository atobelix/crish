## 摘要与综合就绪度评估

经过对 Conex / Crish 项目全仓库代码、构建流水线、依赖配置、开发脚本及文档资产的立体化审查，**当前项目距离正式在 GitHub 等公网社区开源，在开发者上手体验（Developer Experience, DX）与环境准备度方面存在显著的断层与摩擦力**。

当前综合 DX 就绪度评级为：**C（高摩擦 / 需深度整改）**。

### 核心阻断痛点提要

1. **Clone-to-Run 第一步指令断裂**：`README.md:34` 与 `CONTRIBUTING.md:38` 中引导的快速开始步骤存在致命路径不一致——使用 `git clone .../crish.git` 拉取后，指引命令执行 `cd conex`，在纯净机器上直接抛出路径不存在错误；同时缺少 `.nvmrc`、`.node-version` 与 `rust-toolchain.toml`，Node 与 Rust 版本无法自动对齐。
2. **三大平台系统依赖文档化严重欠缺**：Linux 构建 Tauri 2 所需的 9 项关键系统库（如 `libwebkit2gtk-4.1-dev`、`libayatana-appindicator3-dev` 等）在文档中仅以一句模糊外链带过；Windows 平台未声明构建原生 C 依赖（`rusqlite(bundled)`、`syntect` 等）所需的 Visual Studio C++ Build Tools，新手极易遭遇 `link.exe not found` 致命阻塞。
3. **零配置启动与离线体验完全缺失**：全仓库根目录及客户端工程缺失 `.env.example`；多服务商预置配置为空列表（`DEFAULT_PROFILES = []`），Demo/Mock 模式被硬编码禁用（`isDemoMode() { return false; }`）。新开发者克隆代码并成功启动后，若无商业大模型 API Key 或未在本地搭建 Ollama，将面对完全无法交互与测试的死核工作台。
4. **IDE 与容器辅助资产为 0**：仓库完全缺少 `.vscode/` 目录（无推荐插件、无 clippy/prettier 统一 settings、无 Tauri/Rust 调试 launch 脚本）与 `.devcontainer` 支持，不同环境协作极易被行尾换行符（CRLF vs LF）触发 Git Hook 拦截。
5. **故障排查手册缺失且存量指南严重腐化**：缺少针对构建环境报错的 FAQ；而存量的 `docs/opensource/provider-dx/` 系列文档充斥着对早已删除的旧 TS 包（`packages/agent-runtime`）与虚构 crate（`conex-stream`）的失效命令指导，极具误导性。

## 一、开箱即用路径（Clone-to-Run）阻断痛点与摩擦力分析

模拟一名使用纯净操作系统（Linux/macOS/Windows）的开源开发者，首次通过官方文档运行本项目的完整链路：

### 1. 仓库克隆与目录进入（阻断级别：P0 - 硬阻塞）

- **代码证据**：
  - `README.md:33-34`：
    ```bash
    git clone https://github.com/conex-community/crish.git
    cd conex
    ```
  - `CONTRIBUTING.md:37-38`：
    ```bash
    git clone https://github.com/conex-community/crish.git
    cd conex
    ```
- **实际发生**：
  Git 默认根据 URL 的 basename 创建目录，克隆完成后的实际文件夹名称为 `crish`。当开发者复制文档命令并在终端执行 `cd conex` 时：
  - Bash/Zsh（Linux/macOS）：`cd: no such file or directory: conex`
  - PowerShell（Windows）：`Set-Location: 找不到路径 "conex"，因为该路径不存在。`
- **影响评估**：新开发者在接触项目的第一分钟即遭遇命令报错，体验极差，损害项目专业度。

### 2. 依赖安装与运行时版本缺失（阻断级别：P1 - 高摩擦）

- **代码证据**：
  - `package.json:1-15`：
    ```json
    "name": "crish",
    "version": "0.1.0",
    "private": true,
    "packageManager": "npm@11.6.2",
    ```
  - 根目录文件检测：经查证，根目录**不存在** `.nvmrc`、`.node-version`、`rust-toolchain.toml` 或 `rust-toolchain`。
  - `Cargo.toml:31-38`：仅声明 `edition = "2021"`，未声明 `rust-version`（MSRV，最低受支持 Rust 版本）。
- **实际发生**：
  1. **Node 工具链无法感知**：现代前端主流版本管理器（`nvm`、`fnm`、`asdf`、`mise`、`volta`）全部依赖 `.nvmrc` 或 `.node-version` 进行目录级环境自动切换。开发者如果本地全局是 Node 18 或 Node 24，`package.json` 中缺失 `"engines": { "node": ">=20", "npm": ">=10" }` 约束，安装阶段不会给予任何提示，后续构建中可能隐式触发未知兼容问题。
  2. **多工程 Node 版本分裂**：`apps/crish-mobile`（Expo SDK 57）要求 Node ≥ 22.13（见 `ci.yml:161`），而桌面端主推 Node 20，多端版本冲突未在根目录做任何工程化引导。
  3. **Rust 工具链无约束**：缺乏 `rust-toolchain.toml`，无法确保开发者安装了与 CI 相同版本的 Rust 编译器（如 1.83+）及必要组件（`clippy`、`rustfmt`）。若开发者机器缺少 `clippy`，后续 pre-commit 或 CI 将直接崩溃。
  4. **包管理器绑死与脚本硬编码**：`package.json:26-30, 45, 50` 中大量 npm 专用参数硬编码（如 `npm --workspace @crish/crish-desktop run dev`），若开发者使用 `pnpm install` 或 `yarn`，在执行相关命令时会产生严重紊乱。

### 3. Git Hooks 强拦截与小白开发者挫败感（阻断级别：P1 - 高摩擦）

- **代码证据**：
  - `package.json:25`：`"prepare": "husky"` 在 `npm install` 自动触发安装；
  - `.husky/pre-commit:1-16`：
    ```bash
    git diff --check
    node scripts/check-conflict-markers.mjs
    node scripts/check-runtime-status-ssot.mjs
    node scripts/check-repo-integrity.mjs
    node scripts/check-guard-system.mjs
    node scripts/check-token-fallback-drift.mjs
    node scripts/check-inline-style-hardcode.mjs
    node scripts/check-session-message-upsert.mjs
    node scripts/check-tool-pairing-invariants.mjs
    node scripts/check-db-write-bypass.mjs
    node scripts/check-frontend-convergence.mjs
    ```
  - `.husky/pre-push:1`：`npm run typecheck && npm test`
- **实际发生**：
  1. **工作区级全量空白检查拦截**：第 1 行 `git diff --check` 会对**工作区内所有未暂存与已暂存改动**进行空白符（trailing whitespace / conflict marker）扫描。新开发者在 Windows 上若未配置 `core.autocrlf=input`，或在探索过程中随手修改了测试文件，即使提交范围只限定在某一个文档，整个 `git commit` 也会被当场击坠。
  2. **10 道内部架构守护脚本全量执行**：这些脚本包含极其严格的架构收敛守卫（如 `check-token-fallback-drift.mjs`、`check-guard-system.mjs` 等）。缺乏清晰的错误提示与背景说明，新开发者一旦触发阻断无法理解其意图。
  3. **pre-push 耗时过长与偶发单测失败阻断**：`npm test` 包含庞大的 vitest 套件，每次推送前耗时可能达 2~4 分钟；在轻微修改场景下挫败感极强。

### 4. 首次启动执行（`npm run dev:workbench`）摩擦点（阻断级别：P1 - 高摩擦）

- **代码证据**：
  - `package.json:27`：`"dev:workbench": "node scripts/ensure-dev-ports.mjs && npm --workspace @crish/agent-workbench run tauri -- dev"`
  - `apps/agent-workbench/package.json:9, 11`：`"dev": "npm --prefix ../crish-desktop run dev"`，`"tauri": "node ../../node_modules/@tauri-apps/cli/tauri.js"`
  - `apps/agent-workbench/src-tauri/tauri.conf.json:8-10`：
    ```json
    "devUrl": "http://localhost:5174",
    "beforeDevCommand": "npm run dev",
    "beforeBuildCommand": "npm run build"
    ```
  - `scripts/ensure-dev-ports.mjs:13, 85-96, 108-118`：
    ```javascript
    const TARGET_PORTS = [5174, 4000];
    const SAFE_PROCESS_NAMES = [
      'node',
      'node.exe',
      'crish-agent-workbench',
      'crish-agent-workbench.exe',
      'vite',
    ];
    // ...
    const procName = isWin ? getProcessNameWindows(pid) : '';
    const isKillable =
      !procName ||
      SAFE_PROCESS_NAMES.some((name) => procName.includes(name.toLowerCase()));
    ```
  - `apps/agent-workbench/src-tauri/Cargo.toml:36`：
    ```toml
    tauri-plugin-mcp = { git = "https://github.com/P3GLEG/tauri-plugin-mcp" }
    ```
- **实际发生**：
  1. **Unix 平台无差别 SIGKILL 越权隐患**：在 Linux 与 macOS 平台上，`isWin` 为 `false`，导致 `procName` 为空字符串。逻辑 `!procName` 恒为真，`isKillable` 恒真！这意味着在 Unix 系统上，任何监听在 5174 或 4000 端口的进程，都会被脚本以 `process.kill(pid, 'SIGKILL')` 强行击杀！如果开发者机器上运行着其他项目的本地服务（4000 是 Apollo GraphQL、Jekyll、Phoenix 等常见端口），会惨遭误杀。
  2. **双重多进程并行构建输出混乱**：`tauri dev` 在启动 Rust 编译的同时，通过 `beforeDevCommand` 启动了 Vite 前端服务器。首次 Rust 编译需要编译包括 `tokio`、`tauri`、`windows-sys`、`rusqlite`、`syntect` 在内的数百个 crate，耗时极长。在此期间 Vite 终端不断输出 HMR 提示，而桌面窗口迟迟不出。如果 Rust 编译因底层链接错误退出，其报错容易被前端日志冲刷淹没。
  3. **Git 依赖网络阻断**：`tauri-plugin-mcp` 直接指向 GitHub git 仓库而非 crates.io。在部分网络受限或公司内网环境中，Cargo 无法直连 GitHub，会直接在 `Updating git repository` 环节超时报错，且全工程未提供离线 vendor 或镜像源说明。

### 2. 离线 Mock / 演示模式断裂与默认服务商空置（阻断级别：P0 - 硬阻塞）

- **代码证据 2**：`apps/crish-desktop/src/api/appMode.ts:62-64`：
  ```typescript
  export function isDemoMode(): boolean {
    return false;
  }
  ```
- **代码证据 3**：`crates/agent-provider/src/`：
  除 `*_tests.rs` 内部包含单元测试用的 mock frame 外，**Rust 引擎内核没有任何运行时 MockProvider / EchoProvider 实现**。
- **阻断痛点还原**：
  1. 开发者首次运行 `npm run dev:workbench`，打开应用后没有任何可用模型，聊天界面处于空态；
  2. 开发者若想体验发送一条消息、观察 UI 流式渲染、验证命令批准机制或测试 Markdown 组件，**必须自行注册并付费购买大模型 API Key（或下载并配置数 GB 显存的 Ollama）**；
  3. 如果开发者没有准备大模型 Key，`isDemoMode()` 又被硬编码封死，整套桌面应用蜕变为一个不可运行业务的「植物人」界面，开发者根本无法进行任何功能交互或本地界面二次开发；
  4. 对比业界标杆开源项目（如 LibreChat 提供 dummy mock、OpenDevin / Cursor 类似项目提供 Echo Mock Agent），本项目对无 Key 开发者的上手摩擦力高达 100%。

### 3. 本地开发端口与 CSP 静态硬编码冲突（阻断级别：P1 - 高摩擦）

- **代码证据**：
  - `apps/crish-desktop/vite.config.ts:729-732`：
    ```typescript
    server: {
      port: 5174,
      strictPort: true,
    },
    ```
  - `apps/crish-desktop/vite.config.ts:34` 与 `apps/agent-workbench/src-tauri/tauri.conf.json:29`：
    ```text
    connect-src 'self' ipc: http://ipc.localhost http://localhost:8765 http://127.0.0.1:8765 ws://localhost:8765 ws://127.0.0.1:8765 ...
    ```
  - `apps/agent-workbench/src-tauri/src/server/mod.rs:3-4, 170-171`：
    桌面 Hub 服务默认绑定 `8765`，当 `8765` 被占用时，自动顺序探测 `8766..8775`。
- **实际发生**：
  若开发者机器上 8765 端口已被占用，Rust 引擎会优雅降级并绑定到 8766 端口。**但是前端的 CSP 规则在 `vite.config.ts` 与 `tauri.conf.json` 中写死了 `ws://localhost:8765`**！前端向 `ws://localhost:8766` 发起连接时，会被浏览器的 Content Security Policy 当场扼杀，抛出 CSP 拦截错误，多端互通与设备配对功能静默失效。

- **缺少 `.vscode/extensions.json`**：
  - 未向开发者推荐 `rust-lang.rust-analyzer`（Rust 官方语言服务器）；
  - 未向开发者推荐 `tauri-apps.tauri-vscode`（Tauri 官方插件）；
  - 未向开发者推荐 `dbaeumer.vscode-eslint`、`esbenp.prettier-vscode`、`stylelint.vscode-stylelint`、`tamasfe.even-better-toml`。
  - 新手打开 VS Code 无法获得代码补全与格式化支持。
- **缺少 `.vscode/settings.json`**：
  - **Rust-Analyzer 关键配置缺失**：Monorepo 多 crate 场景下，缺少：
    ```json
    "rust-analyzer.check.command": "clippy",
    "rust-analyzer.cargo.buildScripts.enable": true
    ```
    会导致 VS Code 在后台使用 `cargo check` 而非与仓库纪律一致的 `clippy`，且无法正确索引 `tauri-build` 生成的代码。
  - **统一格式化与换行符防护缺失**：
    未配置 `"files.eol": "\n"`。在 Windows 环境下，Git 检出的换行符可能变成 CRLF，这会直接引爆 `.husky/pre-commit` 里的 `git diff --check`（见 `AGENTS.md` §3.5 专门强调的惨痛历史）。
- **缺少 `.vscode/launch.json` 与 `tasks.json`**：
  - 缺乏针对 Tauri 2 应用的调试配置（混合调试 Rust 端 LLDB 与 WebView 端 Chrome Debugger）；
  - 缺乏针对单个 Vitest 文件或 Rust 单元测试的断点调试配置。

### 2. DevContainer 支持（缺失级别：P2 - 优化项）

- **代码证据**：根目录**不存在 `.devcontainer/`**。
- **现状分析**：
  由于 Tauri 2 在 Linux 平台依赖繁琐的 GTK/WebKitGTK 系统库，缺乏 DevContainer（Docker 容器化开发环境）导致想要在 Linux 干净容器中进行开发、或 Windows/macOS 用户希望通过 Docker 进行纯净测试的开发者无法实现「一键开箱」。

## 五、开发者故障排查指南与存量文档老化审计

### 1. 常见构建报错 FAQ 完全缺失（阻断级别：P1 - 高摩擦）

经检索 `docs/` 目录，全库**不存在任何面向新环境初始化的故障排查指南**。对于以下极其普遍的构建报错，缺少现成的排查与自救手册：

1. **Windows 链接器缺失**：`error: linker 'link.exe' not found`（未安装 VS C++ 工具箱）；
2. **Linux 缺失 WebKitGTK**：`Package webkit2gtk-4.1 was not found`（未安装 `libwebkit2gtk-4.1-dev`）；
3. **WebView2 未安装/无法加载**：Windows 旧版系统或沙盒环境中 Tauri 启动白屏或报错；
4. **端口 5174/4000/8765 冲突**：开发进程残留如何排查与释放；
5. **Node.js 版本不符或 esbuild 报错**：Node 18/22 差异处理；
6. **Git CRLF 换行符导致的 pre-commit 钩子拦截**：如何通过 `git config core.autocrlf input` 修复。

### 2. 存量文档严重腐化与失真（阻断级别：P0 - 硬阻塞）

在 `docs/opensource/provider-dx/` 目录下的多份指导文档，严重滞后于内核 Rust 重写架构，遗留了大量早已物理删除的文件和不存在的命令，会对开源贡献者产生致命的误导：

- **证据 1**：`docs/opensource/provider-dx/DEV-ENVIRONMENT.md:15-22`：
  ```bash
  # All provider tests
  npx vitest run packages/agent-runtime/src/provider/__tests__/
  ```
  **事实**：`packages/agent-runtime` 早已被物理删除（见 `README.md:12` 与 `CONTRIBUTING.md:20` 明示）；新开发者复制此命令必报路径不存在。
- **证据 2**：`docs/opensource/provider-dx/DEV-ENVIRONMENT.md:28-30`：
  ```bash
  npx tsx packages/agent-runtime/src/provider/cli/provider-validate.ts packages/agent-runtime/src/provider/builtin/providers/
  ```
  **事实**：脚本路径完全不存在。
- **证据 3**：`docs/opensource/provider-dx/DEV-ENVIRONMENT.md:60-61`：
  ```bash
  cargo test -p conex-stream
  cargo bench -p conex-stream
  ```
  **事实**：全库根本不存在 `conex-stream` 这个 crate（已被 `crates/agent-provider/src/sse` 吸收）。
- **证据 4**：`docs/opensource/provider-dx/TROUBLESHOOTING.md:26, 119`：
  再次引用 `packages/agent-runtime/src/provider/cli/provider-test.ts` 与不存在的 `conex-stream` crate。

开源发布前若保留这些虚假/坏死文档，将严重消耗社区开发者的信任与精力。

## 六、开源准备度差距级别（Gap Matrix）对照表

根据开源就绪度评估标准，将发现的缺陷分为：

- **P0（硬阻断 / Blocker）**：导致无法构建、无法运行、命令直接报错或严重误导；
- **P1（高摩擦 / High Friction）**：造成重大体验阻碍、频繁误拦截或上手门槛过高；
- **P2（中低摩擦 / Polish）**：缺乏现代工程规范利器，存在优化空间。

| 编号       | 审计领域     | 核心缺陷与差距                                                                                                       | 影响平台    | 级别   |
| :--------- | :----------- | :------------------------------------------------------------------------------------------------------------------- | :---------- | :----- |
| **GAP-01** | 开箱即用路径 | `README.md` 与 `CONTRIBUTING.md` 中 `cd conex` 路径与克隆目录 `crish` 不符，第一步即报错                             | 全平台      | **P0** |

## 七、生产级整改行动清单（Remediation Action Plan）

为达到一流开源软件的开发者体验标准，提出以下具体落地整改路线：

### 阶段一：紧急阻断修复（P0 - 消除硬阻塞）

1. **修正文档快速开始命令**：
   - 修改 `README.md:33-34` 与 `CONTRIBUTING.md:37-38`：
     ```bash
     git clone https://github.com/conex-community/crish.git
     cd crish    # 修正：克隆目录名为 crish，或明确 git clone ... crish && cd crish
     ```
2. **补齐三平台系统依赖指南**：
   - 在 `CONTRIBUTING.md` 中为 Linux 提供显式的一键安装命令块：
     - Ubuntu/Debian：`sudo apt update && sudo apt install -y build-essential curl wget file libwebkit2gtk-4.1-dev libssl-dev libayatana-appindicator3-dev librsvg2-dev libxdo-dev`
     - Fedora：`sudo dnf install -y webkit2gtk4.1-devel openssl-devel libappindicator-gtk3-devel librsvg2-devel libxdo-devel`
     - Arch：`sudo pacman -S --needed webkit2gtk-4.1 base-devel openssl libappindicator-gtk3 librsvg xdotool`
   - 为 Windows 明确指引安装 **Visual Studio 2022 生成工具**（勾选“使用 C++ 的桌面开发”工作负载）及 Windows 10/11 SDK。
3. **清洗与归档腐化的 `provider-dx` 文档**：
   - 彻底重写或删除 `docs/opensource/provider-dx/DEV-ENVIRONMENT.md` 与 `TROUBLESHOOTING.md` 中对 `packages/agent-runtime` 和 `conex-stream` 的全部历史虚构引用，与现有的 Rust 引擎架构（`crates/agent-provider`）真实测试命令（`cargo test -p agent-provider`）对齐。
4. **落地开箱即用离线/Mock 演示体验**：
   - 在前端 `apps/crish-desktop/src/api/provider-profiles/profileCatalog.ts` 中提供开箱即用的「本地模拟演示服务商（Local Mock / Echo Model）」预置配置；
   - 恢复或完善 `appMode.ts` 中的本地 Demo 模式支持，使得新开发者在无需任何 API Key 与本地大模型的情况下，即可输入消息、触发流式打字效果、测试 Tool 审批卡片与 Markdown 渲染。

### 阶段二：配置与脚本鲁棒性治理（P1 - 消除高摩擦）

1. **补充根目录与客户端 `.env.example`**：
   - 在仓库根目录创建 `.env.example`，列出并注释常用调试开关：
     ```bash
     # 日志级别 (trace | debug | info | warn | error)
     CRISH_LOG_LEVEL=info
     # 覆盖本地数据与配置目录（默认遵循 OS 标准应用数据目录）
     # CRISH_WORKBENCH_CONFIG_DIR=
     # 开发端口（默认 5174）
     # VITE_PORT=5174
     # 模型测试可选环境变量（运行 scripts/test-real-provider-api.mjs 时使用）
     # OPENAI_API_KEY=
     # DEEPSEEK_API_KEY=
     ```
2. **规范版本约束文件**：
   - 在根目录添加 `.nvmrc` 与 `.node-version`（内容写入 `20`）；
   - 在 `package.json` 中声明 `"engines": { "node": ">=20.0.0", "npm": ">=10.0.0" }`；
   - 在根目录添加 `rust-toolchain.toml`：
     ```toml
     [toolchain]
     channel = "stable"
     components = ["rustfmt", "clippy"]
     profile = "minimal"
     ```
   - 在根目录 `Cargo.toml` 中增加 `rust-version = "1.80"`（或经实测确定的最低版本）。
3. **加固 `scripts/ensure-dev-ports.mjs`**：
   - 修复 Unix 平台下的进程识别逻辑：非 Windows 平台改用 `ps -p ${pid} -o comm=` 准确提取进程名，严格仅对 `SAFE_PROCESS_NAMES`（node, vite, crish）执行杀进程，严禁盲目 `SIGKILL` 杀死未知外部进程；
   - 支持环境变量开关 `CRISH_SKIP_PORT_CLEANUP=1`，允许开发者手动管理端口。
4. **动态协调 Hub 服务端口与前端 CSP**：
   - 当 Rust Hub 端口因占用回退到 8766~8775 时，通过 IPC 动态握手或向前端通知端口变更，并确保 CSP 策略中支持动态端口或在开发模式下允许 `ws://localhost:*` 连接，避免连接被浏览器阻断。
5. **创建 `.vscode/` 开发者辅助套装**：
   - `.vscode/extensions.json`：推荐 `rust-analyzer`、`tauri-vscode`、`eslint`、`prettier`、`stylelint`、`even-better-toml`；
   - `.vscode/settings.json`：配置 `files.eol: "\n"`、保存自动 Prettier/Rustfmt、`rust-analyzer.check.command: "clippy"`；
   - `.vscode/launch.json`：配置 Tauri 桌面调试组合（Launch Desktop & Debug）。
6. **编写通用开发者排错手册**：
   - 创建 `docs/guides/TROUBLESHOOTING.md`（或 `docs/opensource/TROUBLESHOOTING.md`），覆盖编译依赖缺失、WebView2 诊断、换行符 Hook 拦截、端口占用等 7 大常见场景的标准解决方案。

### 阶段三：长效工程优化（P2 - 持续精细化）

1. **添加 DevContainer 支持**：
   - 创建 `.devcontainer/devcontainer.json` 与 `Dockerfile`，基于 Debian/Ubuntu 预装 Node 20、Rust stable 及 WebKitGTK 4.1 开发包，支持 VS Code DevContainer 与 GitHub Codespaces 开箱即用。
2. **重构跨平台维护脚本**：
   - 将 `clean-cargo-cache.ps1` 与 `clean-test-artifacts.ps1` 包装为跨平台的 Node 脚本（`.mjs`），解绑仅适用于 Windows 的 `pwsh` 调用，确保 Linux/macOS 开发者运行 `npm run clean:cargo-cache` 正常工作。
3. **优化 pre-commit 钩子体验**：
   - 将 `git diff --check` 收敛为仅检查当前提交的暂存区改动（`git diff --cached --check`），避免工作区未暂存的草稿空格直接导致无辜提交失败。

## 结论

开发者上手体验（DX）是开源项目能否吸引社区贡献者、构建繁荣生态的生命线。当前 Conex / Crish 项目在 Rust 内核性能与前端组件架构上具备扎实的技术积累，但在**面向外部新开发者的环境准备度、零配置开箱体验以及依赖文档化**方面仍停留在私有项目或内部协同的初级阶段。

按照上述行动清单系统性落实 P0 阻断修复与 P1 体验加固后，项目将具备一流的 Clone-to-Run 流畅度与开源就绪标准。
