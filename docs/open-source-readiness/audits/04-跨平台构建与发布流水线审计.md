## 一、执行摘要与准备度评级

### 1.1 总体就绪结论

本报告对 Conex / Crish 项目距离正式公网开源在 **持续集成（CI）**、**跨平台兼容性**、**客户端打包与签名**、**自动更新机制** 以及 **GitHub Releases 发布自动化** 层面进行了穷举式证据链审计。

**审计结论**：当前项目在前端代码质量、静态类型检查、Linux 环境下的基础门禁方面建立了极其完备的本地与单平台自动化拦截（如 `check:desktop` 与 19 项门禁守卫）；**但在跨平台发布流水线层面，当前项目处于“严重未就绪（Not Ready / Blocked）”状态**。

### 1.2 五大核心差距速览

1. **CI 矩阵单一平台孤岛（Blocker）**：全仓 4 个 GitHub Actions 工作流（共计 27 个 Job 节点）**100% 硬编码运行于 `ubuntu-latest`**，完全缺失 Windows (`windows-latest`) 与 macOS (`macos-latest`) 真实构建与运行测试矩阵。由于全仓包含海量 `#[cfg(windows)]` 原生代码，所有 Windows 专有逻辑在云端处于“零编译、零测试、零验证”的失控状态。
2. **客户端打包流水线完全空白（Blocker）**：仓库内**没有任何自动化打包工作流**，未接入 `tauri-apps/tauri-action`，无法在 GitHub 上为用户产出 Windows `.exe`/`.msi`、macOS `.dmg`/`.app` 或 Linux `.deb`/`.AppImage` 安装包。
3. **自动更新器配置虚设与严重违规（Blocker）**：`tauri.conf.json` 中配置了 `"active": true`，但公钥 `"pubkey": ""` 为**空字符串**，且更新端点指向无后端服务的独立域名 `releases.crish.me`。同时 Rust 端未引入 `tauri-plugin-updater` 依赖，未在 `main.rs` 注册，前端亦无任何更新界面，属于完全不可运行的“幽灵配置”。
4. **代码签名与安全公证为零（High）**：Windows Authenticode 与 Apple Developer 证书签名配置全部为 `null`，且未配置 macOS `entitlements.plist`。在此状态下分发客户端，Windows 必遭 SmartScreen 拦截，macOS 必被 Gatekeeper 拦截并弹窗报错“文件已损坏”。
5. **脚本与平台实现断层（High）**：根 `package.json` 硬编码绑定 `pwsh`，清理脚本硬编码开发者本地路径 `C:\Software\conex`；macOS/Linux 下凭据存储降级为明文，系统电源管理与开始菜单应用发现大面积缺失。

### 2.2 影响分析与风险断层

1. **Windows 原生代码处于“幽灵验证”盲区**：
   - 项目在 [`apps/agent-workbench/src-tauri/Cargo.toml:121-135`](file:///c:/Software/conex/apps/agent-workbench/src-tauri/Cargo.toml#L121-L135) 中声明了大量 `windows-sys`（14 个 Win32 feature，包括 GDI、JobObjects、Power、Security、WinSock、IpHelper 等）与 `windows` 0.62 依赖。
   - 在 [`apps/agent-workbench/src-tauri/src/window_snap_overlay.rs`](file:///c:/Software/conex/apps/agent-workbench/src-tauri/src/window_snap_overlay.rs)（贴靠布局热区 HWND）、[`multi_device_network.rs`](file:///c:/Software/conex/apps/agent-workbench/src-tauri/src/multi_device_network.rs)（NLM COM/注册表检测）、[`auth/credential_store.rs`](file:///c:/Software/conex/apps/agent-workbench/src-tauri/src/auth/credential_store.rs)（DPAPI）、[`system_power.rs`](file:///c:/Software/conex/apps/agent-workbench/src-tauri/src/system_power.rs)（电源事件挂钩）以及 [`conex-computer`](file:///c:/Software/conex/crates/conex-computer/src/lib.rs)（UIA 自动化与屏幕捕获）中存在上万行 `#[cfg(windows)]` 代码。
   - **因为云端 CI 从不在 `windows-latest` 运行，任何对 Windows 依赖、Win32 FFI、注册表逻辑、类型转换的破坏性代码，在 CI 中都能 100% 畅通无阻地“绿灯”合并！**
2. **macOS 架构与生态零守护**：
   - macOS 存在 Apple Silicon (aarch64) 与 Intel (x86_64) 双架构；
   - macOS 对于动态库链接、文件路径大小写规则、以及 Unix Socket 权限与 Linux 存在细微差别；
   - 完全没有 `macos-latest` 的编译守护，无法保证 macOS 开发者 `git clone` 后的首发编译可用性。
3. **缺少 Matrix 构建矩阵机制**：
   - 生产级开源项目标准的 GitHub Actions 实践是对编译检查（`cargo check`）和核心测试（`cargo test`）采用：
     ```yaml
     strategy:
       fail-fast: false
       matrix:
         os: [ubuntu-latest, windows-latest, macos-latest]
     ```
     当前全仓无一处使用 `strategy.matrix`。

## 三、维度二：跨平台代码与脚本兼容性断层审查

### 3.1 脚本过度绑定 Windows 与硬编码路径

#### 证据 1：`package.json` 中的硬编码 `pwsh`

- [根目录 `package.json:24`](file:///c:/Software/conex/package.json#L24):
  ```json
  "clean:cargo-cache": "pwsh -ExecutionPolicy Bypass -File scripts/clean-cargo-cache.ps1",
  ```
  - **严重性**：Linux / macOS 用户在检出仓库后运行 `npm run clean:cargo-cache`，会直接由于缺少 PowerShell 7+ 而抛出 `pwsh: command not found`。
  - **规范冲突**：开源跨平台项目的根脚本必须具备平台自适应能力，应采用 Node.js（`.mjs`）编写清理逻辑或做多平台分流。

#### 证据 2：清理脚本硬编码本地开发者绝对路径

- [`scripts/clean-cargo-cache.ps1:10`](file:///c:/Software/conex/scripts/clean-cargo-cache.ps1#L10):

- [`scripts/clean-test-artifacts.ps1:10`](file:///c:/Software/conex/scripts/clean-test-artifacts.ps1#L10):
  ```powershell
  [string]$TargetRoot = "C:\Software\conex\target\debug\deps",
  ```

## 四、维度三：Tauri 客户端跨平台打包与签名准备度审查

### 4.1 审查发现与证据链

#### 确凿证据 1：自动化打包工作流完全不存在

- 在 `.github/workflows/` 下搜索 `tauri` 或 `tauri-action`，**匹配结果为 0**；
- 没有任何配置能够触发桌面客户端二进制（`.exe`, `.msi`, `.dmg`, `.deb`, `.AppImage`）的编译、组装与打包。

#### 确凿证据 2：`tauri.conf.json` 代码签名配置全为 `null`

查看 [`apps/agent-workbench/src-tauri/tauri.conf.json:54-63`](file:///c:/Software/conex/apps/agent-workbench/src-tauri/tauri.conf.json#L54-L63)：

```json

      "certificateThumbprint": null,
      "digestAlgorithm": "sha256",
      "timestampUrl": null
    },
    "macOS": {
      "signingIdentity": null,
      "providerShortName": null
    }
```

- **Windows Authenticode 签名**：
  - `certificateThumbprint: null`，`timestampUrl: null`；
  - 缺乏用于签名安装包的证书与时间戳服务器配置。

### 4.2 影响分析：开源用户体验与安全拦截灾难

如果以当前配置发布打包产物：

1. **Windows 平台**：
   - 用户从 GitHub 下载安装包或 `.exe` 运行时，Windows Defender SmartScreen 将直接弹窗全屏警告：“Windows 已保护你的电脑 — 未知发布者”；

2. **macOS 平台（致命阻断）**：

   - 必须通过终端运行 `xattr -cr /Applications/Crish.app` 才能解除隔离，极大增加上手摩擦力。

## 五、维度四：Tauri 自动更新（Updater）协议与基础设施审查

### 5.1 审查发现与证据链

#### 确凿证据 1：公钥为空字符串（致命漏洞/构建阻断）

查看 [`apps/agent-workbench/src-tauri/tauri.conf.json:36-43`](file:///c:/Software/conex/apps/agent-workbench/src-tauri/tauri.conf.json#L36-L43)：

```json
  "plugins": {
    "updater": {
      "active": true,
      "endpoints": ["https://releases.crish.me/updates/{{target}}-{{arch}}/{{current_version}}"],
      "dialog": true,
      "pubkey": ""
    }
  },
```

- **配置矛盾**：`"active": true` 打开了自动更新机制，但 `"pubkey": ""` 是**空字符串**。
- **协议阻断**：在 Tauri v2 的安全模型中，自动更新必须使用 Minisign (ed25519) 密钥对对升级包进行签名。客户端在下载新版本后必须使用 `pubkey` 校验签名以防止中间人攻击（MITM）。公钥为空会导致 Tauri 构建时警告/失败，或者在运行时直接报签名验证错误，更新机制完全不可用。

#### 确凿证据 2：更新端点不可行与私有化绑定

- `endpoints: ["https://releases.crish.me/updates/{{target}}-{{arch}}/{{current_version}}"]`
- **问题分析**：
  1. `releases.crish.me` 是一个未在代码库中有任何运维基础设施支持的私有域名；
  2. 采用动态 URL 格式（带 target、arch、current_version 路径参数），需要架设并维护一个后端 Web 服务（动态解析请求并返回对应平台的 JSON）；
  3. 对于开放源代码社区而言，维护私有升级服务器存在单点故障风险（服务器宕机或域名过期将导致全网已发布客户端更新中断），且消耗不必要的服务器运维成本。

#### 确凿证据 3：Rust 内核与前端插件未接线（“幽灵配置”）

- 在 [`apps/agent-workbench/src-tauri/Cargo.toml`](file:///c:/Software/conex/apps/agent-workbench/src-tauri/Cargo.toml) 的依赖列表中：
  - 只有 `tauri-plugin-dialog`, `tauri-plugin-fs`, `tauri-plugin-persisted-scope`, `tauri-plugin-single-instance`, `tauri-plugin-mcp`；
  - **根本没有声明 `tauri-plugin-updater = "2"`**！
- 在 [`apps/agent-workbench/src-tauri/src/main.rs:715-718`](file:///c:/Software/conex/apps/agent-workbench/src-tauri/src/main.rs#L715-L718) 的插件初始化链条中：
  - 仅有 single_instance, fs, dialog, persisted_scope；
  - **根本没有调用 `.plugin(tauri_plugin_updater::Builder::new().build())`**！
- 在 [`apps/crish-desktop/package.json`](file:///c:/Software/conex/apps/crish-desktop/package.json) 中：
  - 未安装 `@tauri-apps/plugin-updater` 前端包；
  - 前端 UI 中没有任何更新检查按钮、更新进度条或版本比对逻辑。

### 5.2 规范方案推荐

开源项目在 GitHub 上最稳定、零成本的自动更新实践是 **GitHub Releases 静态 JSON 模式**：

- 更新端点配置为：
  `https://github.com/conex-community/crish/releases/latest/download/latest.json`
- 由 GitHub Actions 在每次发布新 Release 时自动由 `tauri-action` 生成 `latest.json` 并作为 Release Asset 上传；
- 格式原生兼容各平台架构（`windows-x86_64`, `darwin-aarch64`, `darwin-x86_64`, `linux-x86_64`），全球 GitHub CDN 分发，免除任何后端运维成本。
