## 0. 结论先行（给主控的裁决摘要）

1. **全景判断**：恢复所需的**全部算法资产已实现且测试充分**（C7 recovery.rs 四级阶梯 + Episode 预算 + fork 三态 + 持久化；agent-provider retry.rs 退避/Retry-After/预算；session-loop 内核 3 次重试 + length/压缩阶梯；T-CF-11 idle 续 run 拉起器）。**缺口 100% 是接线**，不是新写。产出 = 一张接线清单（§3，W1-W8）+ 三个选型裁决（§2）。
2. **选型裁决 A（退避重试）**：**推荐方案 B**——在 session-loop `transient_retry` 内加退避 + Retry-After + 预算（stream_error.rs:81-95），不接方案 A 的 `provider_stream_with_observer` 外包。决定性理由：`HttpProviderCall::stream` 返回流式 unfold（engine.rs:514-517），而 `provider_stream_with_observer` 是「收集全部帧后返回」的形状（retry.rs:370-463），直接外包与流式契约冲突，且会造成「流前重试 + 流中重试」两套计数。retry.rs 资产保留为「分类/退避公式的语义真源」，stream_error 镜像其常量（recovery.rs 已开镜像先例）。
3. **选型裁决 B（C7 阶梯接线）**：**推荐完整装配**（每会话 RecoveryCoordinator + SessionTree 重建 + spawn_blocking），不做「仅阶梯 1+2」的最小接线。增量成本 ~200 行（SessionTree 重建 ~50 行、spawn_blocking 包裹 ~40 行、装配 ~110 行），换来阶梯 3 fork 与 resume 命令面零二次接线、预算/通知/forks 跨重启自动恢复——几千行以内直接选效果好的（用户裁定原则）。
4. **选型裁决 C（fork 三态）**：**Summarized 摘要实装本轮不做**。代码事实修正：现有 `fork_and_reassign` 三态只判定与记录（ForkRecord.context_mode），**实际注入恒为任务文本**（recovery.rs:1117 `prompt: ctx.task`），不存在「字节级继承」实装；降级路径（context_normalized 记录位）语义诚实、够用。比摘要更便宜且更基础的是「history 注入」（把原 run 消息作为新 run history），本轮可不做、列 P1。
5. **选型裁决 D（主 run 预算）**：**复用 C7 Episode 预算池**（同 `recover_episodes` 键），主 run 指纹用独立 subagent_id 标记（`"main"`）。单一预算池、同款持久化（重启不重放）、同款 denied 统计，不同任务指纹天然隔离。
6. **选型裁决 E（会话级熔断）**：`provider_fail_streak` 键（10 分钟窗口 ≥6 次 → 熔断 5 分钟），**只闸自动恢复、不闸手动与 run 内 3 次重试**；与 C7 Episode 预算构成两级闸门（熔断 = 会话级一级闸，Episode = 指纹级二级闸）。
7. **风险首位**：阶梯 1 自动重试的**接线时序**——`drive_run_loop` 每 run 必须收口（终态不可悬置），「重试不计入 run 失败」的 C7 注释语义在生产落地为「**预算内自动重派（新 run）**」，原 run 置 failed（reason=`recovery-retry`），重试不消费 Episode 预算、不产生 steering 通知（事实修正，§2-B 与 §6-D1 详述）。

## 2. 关键技术选型（深挖对比 + 代码量评估）

### A. 退避重试接线：方案 A（engine 外包）vs 方案 B（session-loop 内加退避）

#### A.1 两个方案的接线点与机制

**方案 A：`HttpProviderCall::stream` 外包给 `provider_stream_with_observer`**
- 接线点：engine.rs:456-489（`send` + 非 2xx 分类段）改为 retry.rs 的 attempt 闭包；`RetryPolicy { max_retries: 3, ..Default }` 实例化注入；`RetryState` 生命周期 per stream call。
- 机制：流前错误（传输失败/非 2xx）在 engine 层循环重试，Retry-After 合并、60s 预算、abort 竞速（TokioSleeper）全部现成（retry.rs:370-463）。

**方案 B：`transient_retry` 内加退避 + Retry-After + 预算**
- 接线点：stream_error.rs:81-95，计数后、派发 `NO_PROGRESS_CONTINUE` 前插入异步 sleep；`LoopState` 增重试预算计时字段。
- 机制：退避 = `max(指数退避, retry_after_ms)` 钳到单次上限与剩余预算，常量镜像 retry.rs（750/8000/60000，recovery.rs:115-120 已开镜像先例）；`ClassifiedStreamError.retry_after_ms` 已被 consume 层解析（agent-provider/src/consume/mod.rs:370），直接消费，零新解析代码。

#### A.2 关键差异（决定性）

| 维度 | 方案 A（外包） | 方案 B（内核加退避） |
|---|---|---|
| **流式契约** | **冲突**：`HttpProviderCall::stream` 返回 `ProviderEventStream`（流式 unfold，engine.rs:514-517）；`provider_stream_with_observer` 返回 `Vec<SseFrame>`（收集全部帧后返回，retry.rs:370-463）。外包必须把整个流收进 attempt 闭包，破坏流式消费，或给 provider_stream 做「流式重试变体」——结构性改造 agent-provider 共享 crate，测试锁定面大 | 无冲突：退避发生在内核错误处理处，流式消费路径不动 |
| **重试计数语义** | 两套重试并存：流前错误在 engine 层（RetryState），流中读取错误仍在 session-loop（transient_retry）——「重试几次」无法单一观测，预算/诊断割裂 | 单一真源：所有瞬态错误（流前 Err 与流中 Err 条目同路径进 stream_error::handle）统一计数、统一退避、统一 provider-diagnostic 事件 |
| **Retry-After 覆盖** | 仅流前错误（非 2xx 头）；流中错误（读取类）无 Retry-After 概念 | 全部瞬态错误统一消费 `retry_after_ms`（已有字段） |
| **改动面** | engine.rs ~60-80 行 + 可能动 agent-provider（流式变体，若要做干净）；诊断桥（ModelRequestObserver）需新装配 | stream_error.rs ~40 行 + LoopState 2 字段 + SessionLoopOptions 3 字段 + 测试 ~100 行 |
| **测试策略** | 复用 tests/retry.rs（mock 429/5xx 语义已锁定），但需 mock server 层（已有 serve_sse 模式） | session-loop 单测 + tokio 时钟注入（pause/advance），镜像 retry.rs 同期望值（recovery.rs 先例：测试锁定 750/1500/3000/6000/8000 序列） |
| **对 RunOutcome/诊断影响** | engine 层吞掉错误，内核只看到最终结果——重试诊断（provider-diagnostic phase=retry）由 engine 发还是内核发？语义漂移风险 | 诊断事件天然一致（emit_retry_diagnostic 已有，stream_error.rs:214-234），RunOutcome 无需感知退避 |

#### A.3 推荐：**方案 B（内核加退避），方案 A 资产保留**

理由（按路径合法排序键）：
1. **正确性/不变量**：方案 A 的「两套重试」破坏单一真源，重试计数与预算语义割裂，与已锁定的「错误处理在 session-loop 阶梯」契约（stream_error.rs 模块头 01 §2.5）冲突。
2. **结构干净**：方案 B 与 length/压缩阶梯同域（stream_error.rs 已是恢复阶梯单域），退避是阶梯的自然组成部分；方案 A 需动 agent-provider 共享 crate。
3. **改动量与可验证性**：方案 B ~40 行 + 注入时钟测试（确定性）；方案 A 若只做「流前错误外包」是半截方案（流中错误仍无退避），若做全则需流式变体大改。
4. **Retry-After 覆盖完整性**：方案 B 全错误统一消费（这是 04 P0-2 的核心诉求）。

`provider_stream_with_observer` 的资产保留用途：未来「多端点 failover」（04 P3-1）才是 provider 层换端点的正确载体——那时该函数或其流式变体才有接线意义，本轮不接。

**配套改动（不可省）**：`SessionLoopOptions` 增 `retry_backoff: Option<RetryBackoffConfig { base_ms, max_ms, total_budget_ms }>`（None = 现状无退避，向后兼容），壳层经 session_meta 键 `provider_retry_backoff_ms` 可配（仿 META_KEY_SUMMARY_BACKOFF_MS 模式，01 P1-1）。退避上限钳到 max_ms（默认 8s，镜像 retry.rs），总预算 60s——防止「3 次重试 + 退避」把单 run 拖到分钟级（护栏见 §4.1）。

### B. C7 阶梯接线形态：完整装配 vs 最小接线

#### B.1 两形态对比

| 维度 | 形态 1：每会话 RecoveryCoordinator 完整装配 | 形态 2：最小接线（仅阶梯 1+2） |
|---|---|---|

| SessionTree | 必须：restore 后从 `RestoreOutcome.sessions`（SessionRecord，restore.rs:100）经 `from_session_record`（session.rs:589）重建 | 「传空树」占位——fork 路径以结构化错误拒绝（recovery.rs:1066-1070） |
| spawner | 复用已装配的 SubagentSpawnerImpl（CoreRunState 持有） | 「拒绝型占位」spawner 或同上复用 |
| fork/resume | 阶梯 3 + lifecycle.rs resume 命令面直接可调（coordinator 权威实例） | 阶段 B 再补装配（二次接线） |
| 预算/通知/forks 重启恢复 | `new()` 自动从 session_meta 恢复（recovery.rs:854-876） | 同左（new 是必经构造） |
| F2-27（同步 SQLite） | 收口路径经 spawn_blocking 包裹（每次 coordinator 调用） | 同样需要（避免不了） |
| 代码量 | 装配 ~110 行 + SessionTree 重建 ~50 行 + spawn_blocking helper ~40 行 + 测试 ~200 行 | 装配 ~110 行（coordinator 构造绕不开）+ 测试 ~150 行；**省的是树重建与 fork 面** |
| 风险 | 装配面略大（树重建需与 restore 衔接） | 二次接线风险：阶段 B 补 fork 时要再动一遍收口；「占位树」是假接线，违反禁补丁纪律 |
| 可演进性 | 阶梯 3 / resume / 重启重排全部免费获得 | 每级阶梯单独补接线，恢复语义半吊子 |

#### B.2 推荐：**形态 1（完整装配）**

- 代码量差 ~200 行（几千行以内），按用户裁定原则直接选效果好的。
- 决定性理由：① `RecoveryCoordinator::new` 的五件套构造无法回避（形态 2 也必须构造权威实例，否则预算制与持久化恢复全部落空）；② 传空树/拒绝型 spawner 是假接线——fork 路径被结构化拒绝但预算/通知仍在，语义半吊子；③ resume 命令面（lifecycle.rs:243）明确要求调用方持有 coordinator 权威实例，「不另建实例防双写分裂」（lifecycle.rs:129-130 注释）；④ SessionTree 重建成本低（restore 已产出 SessionRecord 全部数据，session.rs:589 `from_session_record` 现成）。
- SessionTree 装配点：`run_restore` 成功路径（core_run_commands.rs:2195-2227）之后、`seed_sequences` 同批——与 restore 天然绑定（会话树数据在快照里，不在 session_meta）。
- spawn_blocking 包裹（F2-27）：RecoveryStore 是同步 trait（recovery.rs:594-620），收口路径（async 上下文）每次 coordinator 持久化调用经 `tokio::task::spawn_blocking` 包裹——封装一个 `blocking_store_call` helper 即可（core_run_commands.rs:2958 `save_run_usage` 已有同模式先例）。

#### B.3 关键时序事实修正（阶梯 1 接线形态）

C7 注释「重试不计入 run 失败」（recovery.rs:13-14）隐含「重试发生在 run 收口置 failed 之前」。但生产 `drive_run_loop` 的收口链是刚性的（produce → drive_outcome 置终态 → 事件 → 移出注册表 → 子代理收口，core_run_commands.rs:2701-2852），每 run 必须收口、终态不可悬置。在 `produce` 之后、`drive_outcome` 之前插入重试判定意味着当前 run 永不终态——不可行（run 状态机 9 态无「重试中」态，run.rs:113-188；加中间态是大改）。

**采纳接线形态（方案 Y）**：收口后重派——
- 原 run 照常 failed（reason 记 `recovery-retry`）；
- `AutoRetry` 动作 = 退避 sleep 后经 `SubagentSpawnerImpl.spawn` 重新派发同一任务（同 prompt、`mode=recovery-retry` 可观测），**不消费 Episode 预算**（区别于 fork）、**不产生 steering 通知**（区别于阶梯 2）；
- 语义对齐：用户可见效果 = 「预算内自动重派一次」，与「自动重试」一致；重试 run 走 spawn 守卫（12/5/1 记账，旧 run 已释放）。

### C. fork 上下文继承：Summarized 摘要本轮是否必须？

**事实修正（以代码为准）**：现有 `fork_and_reassign` 的三态只做**判定与记录**——`decide_fork_context` 产出 `ForkContextMode`（recovery.rs:425-442）落 `ForkRecord.context_mode`（recovery.rs:1079-1087），但实际 spawn 请求的 prompt 恒为 `ctx.task`（任务文本，recovery.rs:1117），**没有任何「字节级继承」或「摘要注入」发生**。03 文档「Verbatim = 字节级继承」的表述是设计意图，不是实现现状。

**决策：Summarized 摘要实装本轮不做；降级路径（context_normalized 记录位）够用。**
- 理由：① 三态对本轮 fork 行为的实际影响 = 0（恒 task-only 注入），摘要实装不会改善本轮恢复效果；② M10 摘要实装依赖 Summarizer 生产装配（C9 断链，DEEPCHECK-11）；③ ForkRecord.context_mode + `recovery-fork` 事件已诚实记录「本应摘要未摘要」，语义无欺骗；④ fork 预算耗尽即阶梯 4，摘要只会影响上下文质量，不影响恢复可达性。
- **更便宜的 P1 增强（推荐先做，比摘要基础）**：Verbatim 场景把原 run 消息作为新 run 的 `history` 注入——spawn 请求的 `history: None` 是既有缺口（subagent_spawner.rs:364-365 恒 None，DEEPCHECK-06 §1 P0），与「子代理预算覆盖」共享同一个装配点。本轮 fork 接线时 history 仍 None（最小可用 = task-only 上下文 + 消息水合兜底），列 P1。

### D. 主 run 半自动续跑：复用 C7 Episode 预算 vs 独立计数

**推荐：复用 C7 Episode 预算池**（同一 `recover_episodes` 键 + 同一 `RecoveryBudget`）。
- 预算语义：C7 指纹 = `fingerprint(subagent_id, task)`（FNV-1a，recovery.rs:251-262）；主 run 以 `subagent_id = "main"` + 任务文本（run 首条 user 消息文本，lifecycle.rs:353-361 `derive_task` 同款提取）参与同池计数，**指纹天然隔离**（不同任务不同指纹；主/子代理互不消耗——subagent_id 不同）。
- 会话级熔断共用：见 E。
- 默认上限：与 00 总览「连续 error ≤ 3」一致，主 run 指纹上限 3（同一 `recover_max_episodes` 键，默认 3；如需更严可配 `recover_max_episodes=1` 单会话全局收紧）。
- 替代方案（独立计数键 `main_recover_episodes`）不选的理由：双池语义分裂、denied 统计（G10 月度）只挂 recovery 池、重启恢复要写两套。
- 续跑机制（接线）：`decide_idle_resume` 放行 `reason==Error && provider_error.retryable && 预算内 && !熔断` → `PendingMessageQueue` 入队系统条目（注入「上一轮 provider 中断（<kind>），继续任务」）→ `spawn_idle_resume_run` 拉起（core_run_commands.rs:2637-2671 现成拉起器）→ 新 run 模式标 `recovery-retry`。护栏：连续 error 续跑 ≤3（预算）+ 退避（复用 resume_empty_streak 计数模式，core_run_commands.rs:2561-2582）+ user_touched/abort 不续（已有硬条件）+ 非 retryable 不续（Auth/Quota 等）。

### E. 会话级熔断（04 G9）：provider_fail_streak 阈值设计

- **键与形态**：session_meta `provider_fail_streak` = JSON `{"count": n, "window_start_ms": t, "tripped_until_ms": t2}`（宽容解析，fail-open）。
- **阈值**：窗口 10 分钟（对齐 retry.rs 预算时长量级）内瞬态失败 ≥6 次（= 2 个 run 的 3 次重试耗尽，即「两次完整的 run 内重试撞墙」）→ 熔断 5 分钟。可配键 `provider_fail_threshold` / `provider_fail_cooldown_ms`。
- **成功清零**：run 正常收场（非 error）时 `count` 归零并清 `tripped_until_ms`。
- **与 C7 Episode 预算的关系**（两级闸门）：
  - 熔断（会话级、按原始失败计数）是**一级闸**：熔断期内**所有自动恢复**关闭——run 内重试照旧（3 次预算有限、不放大单次成本）？不——设计为：熔断期内跳过「跨 run 自动恢复」（阶梯 1 重派、主 run 半自动续跑），run 内 3 次重试保留（避免复杂度），同时新增阶梯 4 上报（`recover_needs_user` 标记，UI 可观察）；
  - Episode 预算（指纹级、按恢复动作计数）是**二级闸**：防同任务无限重派；
  - 关系：熔断是时间窗级的「会话健康闸」，Episode 是任务级的「动作闸」，互相独立、叠加生效。熔断超阈值时不消费 Episode 预算（动作未发生）。
- **接线点**：壳层（session_meta 读写只能在壳层）：W4（子代理收口）+ W5（主 run 续跑判定）前检查；成功路径清零挂 run 收口（drive_run_loop 正常终态分支）。
- **为什么不放内核**：session-loop 无 session_meta 面（引擎层职责边界），熔断数据必须在壳层维护；run 内重试保持现状（每 run 仅 3 次，成本有界）。

## 4. 风险与护栏

### 4.1 自动重试风暴（五层护栏，防「火焰重试」）

| 层 | 机制 | 位置 |
|---|---|---|
| 1 | 单次退避上限（8s 封顶）+ 总预算（60s） | W2（stream_error.rs） |
| 2 | 重试次数上限（run 内 3 + 跨 run 阶梯 1 预算 2） | 内核 + W3 策略 |
| 3 | Episode 预算（每指纹 ≤3，超限直接阶梯 4 不重试不通知） | recovery.rs:266-336（已实现） |
| 4 | 会话级熔断（10 分钟 ≥6 次 → 停 5 分钟） | W6 |
| 5 | 空转护栏（连续 3 轮无产出停止续 run） | core_run_commands.rs:2561-2582（已实现） |

### 4.2 重复副作用（重试会不会重复执行工具/写文件？）

- **run 内/跨 run 重试**：**不会重复工具副作用**。重试 = 基于完整对话（含已提交的工具调用与结果）的**新 provider 请求**，工具不重新执行（工具执行与 provider 流互斥，turn 顺序保证）。三层 produced_content 镜像（retry.rs:412-428 / streaming.rs:116-129 / recovery.rs:205-217）保证已产出内容绝不重试。
- **fork 重派**：新 run 重新执行任务，写文件副作用**可能重复**。护栏：写路径互斥注册表（write_claims）是会话级共享（fork 沿用同一 parent_session，W4/W8 不建新会话），并发写冲突被引擎拒绝（write_paths.rs 互斥）；工具幂等闸（ToolIdempotencyGuard，idempotency_enabled）建议在重试 run 装配时开启（默认关，改造面小、防同域同参工具去重）。
- **用户显式停止永不自动续**：Aborted/Stopped 不进入任何恢复路径（decide_idle_resume 硬条件 + W5 分支均保留）。

### 4.3 配额冲突（fork 与 12/5/1、explore_quota）

- **RecursionGuard 12/5/1**：阶梯 1 重派与阶梯 3 fork 的新 run 全部走 `SubagentSpawnerImpl.spawn` 全流程（守卫快照采集 + 记账，subagent_spawner.rs:743-764），**不绕过**；旧 run 在收口时已释放记账（on_subagent_terminal 五步第一步，subagent_spawner.rs:506-526）——时序上 spawn 时并发数已减，无假占位。
- **嵌套禁令**：恢复路径的 spawn 来自引擎守卫层/主 agent 命令面，子代理工具注册表依旧剔除 run_subagent（subagent.rs:653-659），无任何自派发能力。
- **explore_quota（C5）**：按会话计数（explore_quota.rs:8-9），fork/重派沿用同一 session_id（parent_session 不变）→ 配额语义自动延续，无需改配额模块。

### 4.4 事件背压与队列

- recovery-* 事件量小（每 run 失败 ≤2 条），EventQueue Critical 必达落库（subagent_events.rs:336-366 同机制）无丢失风险。
- steering 条目 `replace_or_enqueue` 同 run 分组原位替换（recovery.rs:982-1021），不会重复堆积；与 subagent-terminal 条目 group_id 不同（recovery-<run_id> vs subagent-terminal-<run_id>），批量拼接成一条 user 消息注入主 agent（drain_pending_to_inject_messages，core_run_commands.rs:2603-2626），消费语义见 §6-D1。

### 4.5 观测缺口（阶段 C 顺带）

- `recover_needs_user` 无 UI 消费（G8）：core_get_status 未暴露——建议 core_query_commands 增字段 + 前端失败态卡片（recovery 摘要 + resume 按钮），列阶段 C。

## 5. 维度边界建议（供主控整合）

**判断标准**：共享「RunOutcome.provider_error 数据面」或「RecoveryCoordinator 装配」的改动必须同一轮；只共享「idle_resume 拉起器 / PendingMessageQueue 注入通道」的可以拆。

| 维度 | 内容（接线点） | 耦合性 | 建议 |
|---|---|---|---|
| 1. 断网继续主干 | W1（数据面）+ W2（退避）+ W3（装配）+ W4（子代理阶梯 1+2）+ W5（主 run 半自动续跑）+ W6（熔断）+ W7（重启重排） | **高耦合**：W1 是 W4/W5 的输入；W3 是 W4/W7/W8 的前提；W6 闸 W4/W5 | **必须同一轮**（本方案核心） |
| 2. 显式恢复命令面 | W8（resume/kill_all）+ 阶梯 3 fork 完整消费 | 依赖维度 1 的 coordinator 装配；自身独立可测 | 同一轮的第二阶段，或独立紧随一轮 |
| 3. 重启续跑 | restore 打断 run 生成恢复条目（restore-<run_id>）+ 独立唤醒 watcher（队列非空且无活动 run → 拉起） | 只复用 spawn_idle_resume_run 拉起器与队列 | **可拆**（与 07 文档 P0-2/P1-3 合并成独立维度） |
| 4. goal / checkpoint | 引擎化 goal 判定 + checkpoint 机制面注入 | 只共享 PendingMessageQueue 注入通道 | **可拆**（独立维度，依赖 07 的 watcher 更顺） |
| 5. 定时器/Cron 持久化 | MemoryTimerStore/SchedStore 换 session_meta 真适配 | 无耦合（链头） | **可拆**（07 P0-1） |

**不建议**本轮纳入：provider 主备链 failover（P3-1，需要流式重试封装新件，独立评估）、stationarity 检测、TodoGate、CompletionRequirement（08 文档 P1/P2 项，与恢复机制正交）。
