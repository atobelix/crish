## 2. 关键技术选型（深挖对比 + 代码量评估）

### 2.A 事件登记：恢复域/Goal 域事件如何进注册表

**候选 A1：并入主注册表（AgentEvent enum + engine-events.json + 生成产物）——推荐**
**候选 A2：独立恢复域事件注册表（orchestrator 侧自持）——不推荐**

**现状事实（事实修正）**：
- 05 文档称「Rust 事件注册表（27+ 事件，normalize.rs:22-73）」**已过时**——代码真源是
  `crates/conex-types/src/events.rs` 的 `AgentEvent` enum（41 变体）+ `contracts/engine-events.json`
  （eventCount: 41）+ `engine_event_type_names!` 宏（events.rs:810-852），三者一致性由
  `tests/registry_drift.rs` 锁定；normalize.rs 只是终态/续轮判定（allows_auto_continue，normalize.rs:177），
  不含注册表。33-event-schema-changelog.md:9-14 已写明 24→41 的演进史。
- recovery.rs:99-111 自述「M7 事件注册表外，M14 事件源补齐时登记」——即**设计上就预留了并入主注册表**。
- 现有先例全部是主注册表 minor 兼容新增：1.1 cache 域 3 事件、1.2 security-audit、1.3 subagent 域 3 事件、
  1.4 任务域 7 事件、1.5 timer 域 2 事件、1.6 cron-fired（33-changelog:108-113）——**每次登记的改动面是固定的 6 处**：

  ③ `V1_EVENT_TYPES` 清单 + 断言改名（events_schema_version.rs）；④ v1 同形 fixture 追加；
  ⑤ `event_backpressure` 静态判定函数分支；⑥ changelog 登记行。外加生成链路
  `scripts/generate-engine-bindings.mjs` 重跑产出 TS 类型。

**A2 否决理由**：事件信封（AgentEventEnvelope）只有一个序列化面（events.rs:922-993），emit 层
（core_event_bridge.rs）按 AgentEvent 分发；独立注册表意味着第二套序列化、第二套前端解析、绕过

与 subagent-ended（已登记）是同一叙事链，割裂只会让检索更难。

**代码量评估**：A1 约 400-600 行（含 fixture 与测试断言改名）；A2 约 900-1400 行（新注册表 +
双序列化 + 前端第二解析器）且收益为负。**选 A1，差距 <1000 行且效果更完整，直接定案。**

载荷形状建议：recovery 五事件 payload 直接序列化既有 struct（RecoveryNotification / ForkRecord /
UserReport，recovery.rs:341-358、445-464、518-531——serde 形状已就绪，零新设计）；

action/reason/prompt/progressSignature/detail），其中 progressSignature 与 goal_state 的
progress_signature 同源（见 2.B）。

### 2.B session_meta 键设计：goal_state / provider_fail_streak 的 JSON 形状与并发

**命名空间纪律（既有，强制延续）**：recovery.rs:80-81 明言「各能力独占自己声明的键命名空间」。
现状已占用：`recover_*`（恢复域）、`timer_*` / `sched_*`（软调度域，timers.rs:51-52、sched.rs:10-34）、
`dispatch_*` / `dispatch_outputs`（wait 域，wait_channel.rs:70-86）、`compact_*`（压缩域）、
`flow_*`（flow_graph）、`{session_id}:output_*`（G03 产出根，outputs_config.rs:41）。
**本轮新增键必须独占前缀**：`goal_state`（goal 域单键）、`provider_fail_streak`（provider 域单键）——
不复用 `recover_*` 前缀（恢复预算与熔断语义不同：预算按指纹、熔断按会话时间窗）。

**goal_state JSON 形状（冻结）**：

```json
{
  "schemaVersion": 1,
  "goal": "修复构建",
  "maxRounds": 12,
  "maxStalledRounds": 2,
  "currentRound": 3,
  "completedRounds": 2,
  "stalledRounds": 0,
  "progressSignature": "sha256:abc...",
  "stoppedReason": "stop",
  "updatedAtMs": 1789000000000
}
```

设计要点（对齐 05 文档 P0-2 的 GoalState 字段清单，补充本方案决策）：
- **宽容解析**：缺键 → 无 goal（普通会话）；坏 JSON → 视为无 goal（fail-open，对齐
  `parse_json_list`（recovery.rs:1286-1292）与 `RecoveryBudget::from_json`（recovery.rs:327-335）先例）。
  字段级容忍：新字段缺省（`#[serde(default)]` 语义的手工等价——手工序列化时以 `serde_json::Value`
  增减或全字段 Option 结构处理，不引入版本列，对齐 33-changelog「持久化 payload 不引入版本列」决策）。
- **progressSignature 定义**：对话尾部消息 id 链哈希（FNV-1a，复用 recovery.rs:251-262 的指纹函数模式）
  或工具批指纹——stalled 检测输入（连续相同 ≥ maxStalledRounds → goal-stalled）。**必须与
  goal-continuation-decided 事件的 progressSignature 字段同源同函数**，防双写不一致。
- **并发写（原子性）**：session_meta 的 set 是整键覆盖（LocalDb::set_session_meta）。goal_state 的
  写路径只有一条——run 收口的 RoundAssessment 评估处（驱动线程串行），**会话内串行守卫已保证
  同会话单活动 run（core_run_commands.rs:3209-3215），不存在并发写**。若未来有第二写方（如前端
  直写），必须走「读-改-写」+ 会话级 mutex（与 RecoveryCoordinator 的 `Arc<Mutex<...>>` 装配同模式），
  禁止裸 set 覆盖。这与 recover_* 五键现状一致（全部由 coordinator 单实例持有写权，recovery.rs:832-839）。
- **写触发点**：仅 round 边界（run 收口）写，run 内不写——对齐「run 收口写 SessionHistoryCache」
  的既有写入时机纪律（core_run_commands.rs:2714-2718）。

**provider_fail_streak JSON 形状（冻结）**：

```json
{
  "count": 3,
  "firstFailAtMs": 1789000000000,
  "lastFailAtMs": 1789000060000,
  "windowMs": 3600000
}
```

设计要点（对齐 04 文档 P2-2：「连续瞬态失败计数 + 时间窗，达阈值（3 turn 内 ≥6 次）暂停自动重试」）：
- 写触发点：`stream_error.rs` 瞬态重试耗尽收场处（fatal_provider_error 路径）——主 run 与子代理 run
  共用同一循环，**熔断按会话计**（键是会话级，不是 run 级，修 04 G9「重试计数跨 run 重置」）。
- 时间窗语义：`firstFailAtMs` + `windowMs` 判定窗口过期 → 计数清零（惰性：读时判定，不写时清零）。
- 与 C7 Episode 预算的关系：**两套独立机制**——Episode 按「操作指纹」限 fork 次数（recovery.rs:247-262），
  熔断按「会话」限自动重试频率；熔断命中时本会话暂停自动重试（含内核 3 次），直接上抛给
  recovery 阶梯 2/4。写面互不干扰（不同键）。
- 并发：同 goal_state，单写方（stream_error 收口线程串行）。

### 2.C 命令面形态：Tauri 命令 vs 主 agent 工具

**候选 C1：注册为 Tauri 命令（command_manifest 机制）——推荐，作为唯一正式入口**
**候选 C2：注册为主 agent 工具（run_subagent 同面）——不推荐本轮做，保留为 P2 增强**

  `lifecycle_service()` 访问器 + ForceCancelSink 由 CoreRunState 实现，:2402-2408），`resume`（:243-321）

  ② command_manifest.rs `COMMAND_MANIFEST` 条目（registered=true）；
  ③ 前端 commandManifest.ts `BUILTIN_COMMAND_MANIFEST` 镜像条目；

  剔除先例 core_run_commands.rs:3236-3241）+ 权限模型。**收益面窄**：主 agent 已有 run_subagent

工具面供主 agent 编排，共用 lifecycle.rs 实现体。**本轮只做 C1，不做 C2**（C2 增加 agent-tools
注册与权限面约 300-500 行，收益延迟可见）。

**代码量评估**：C1 三条命令 ≈ 250-400 行（命令函数 + manifest 双端条目 + 测试），其中
resume/kill_all 是「翻注册 + 薄包装」，core_resume_run 是唯一真新增（复用 spawn_idle_resume_run
的装配路径 core_run_commands.rs:2637-2671 + 注入「上次被重启打断」文本）。

### 2.D 水合双路径统一：引擎缓存保真 vs 前端过滤 error 态

**问题**：hydrate.rs:87-93 的 `is_completed` 只放行 completed/无 status，error 态消息被跳过；
而引擎侧 SessionHistoryCache 全角色保真（core_run_commands.rs:907-915、916-941）——重启后若前端
store 为主源（T-29 混合路线：前端 history 优先，core_run_commands.rs:3615-3622），网络中断轮的
对话内容从上下文中消失，模型「失忆」（01 G6）。

**候选 D1：保留 error 态 + metadata 标记（`{kind:"failed-turn"}`）——推荐**
**候选 D2：前端路径与缓存同语义（error 态全放行，无标记）——不推荐**

- D1：`hydrate_one` 放行 error 态但注入 metadata（AgentMessage.metadata 已支持自由 JSON，
  events.rs 注册表 AgentMessage 类型 fields 有 metadata 可选字段），模型可自行参考失败回合；
  兼容「失败回合会污染判断」的原始顾虑（hydrate.rs:85-86 注释）——污染与否交模型判断，不再由
  引擎替模型做决定。
- D2 的问题：error 态与正常内容无区分，模型无法识别「这是失败的一轮」，且旧数据无 status 与
  error 态无法区分——信息量反而降低。

**D1 改动面**：hydrate.rs `is_completed`/`hydrate_one` 约 15-30 行（error 态放行 + 标记注入 +
单测补充）。**无事件/schema 改动**（metadata 是 AgentMessage 既有字段，不进注册表）。
**验收**：error 收场轮的对话内容在重启后仍在水合序列中，且带 failed-turn 标记
（01 文档 P3-1 验收原文）。

### 2.F 持久化实现：conex-db session_meta 真适配（Memory store 替换）

**现状**：三个内存 store 装配在生产（engine.rs:1112 MemoryTimerStore、engine.rs:1606
MemorySchedStore、wait_channel MemoryWaitStore），键形状全部冻结：
`timer_<id>`（timers.rs:51-52、248-250）、`sched_<cron_id>`（sched.rs:10-34）、`dispatch_*` /
`dispatch_outputs`（wait_channel.rs:70-86）。**可复制先例**：workflow_commands.rs:400-478 已用
`LocalDb::get/set_session_meta` + 自持 `sched_index` 索引键实现真适配（注释明言「conex-db 当前仅
有 get/set_session_meta（无键扫描/删除 API），自持索引保证可枚举」）。

**候选 F1：各 store 独立真适配（timer/sched/wait 各自写 impl，同 workflow 先例）——推荐**
**候选 F2：统一 Store 抽象（把 TimerStore/SchedStore/WaitStore 收敛为一个 trait）——不推荐**

- F1：三个 trait 的 shape 完全不同（TimerStore: load_all/save；SchedStore: 类似；WaitStore:
  load_all/save/save_outputs/load_outputs），收敛为统一抽象需要「泛型键 + 泛型值 + 索引」三层
  泛化，收益只是省 ~100 行重复代码，代价是 trait 可读性下降与**三个域的语义差异被抹平**
  （timer 的 fired 位、wait 的 dispatch 时刻幂等、outputs 整表覆盖——各自的特殊语义在统一抽象里
  需要 if/else 分支）。
- F1 的重复成本其实很低：每个真适配 ≈ 80-120 行（LocalDb 句柄 + load_all 枚举索引 + save upsert +
  宽容解析），三个共 300-400 行；且**索引键的维护模式与 workflow_commands.rs:400-478 完全一致**，
  是照抄不是创新。
- 附加约束（F2-27 同源）：LocalDb 的 session_meta 读写是同步 SQLite，真适配的调用面在
  async 上下文必须走 `spawn_blocking`（recovery.rs:60-62 已指明此方向；outputs_config.rs:234
  有 spawn_blocking 先例）。

**F1 三个真适配的验收锚点**：复用既有测试语义——timers.rs `timer_registry_persists_and_recovers`
（内存版断言：注册 → 模拟重启 → restore 重建 → 到期注入恰好一次）；sched.rs
`scheduler_registry_persists_and_recovers`（sched.rs:1203-1244）；wait_channel 的声明/产出
往返断言。**换真 store 后同断言不改**（07 文档 P0-1 验收原文）。

**代码量评估**：F1 ≈ 350-500 行（三 impl + 装配面替换 + 测试改 store 注入）；
F2 ≈ 250-350 行但语义层退化 + 回归面扩大。差距 <1000 行，**按用户裁定标准选效果更好的 F1**。

## 4. 兼容与迁移

1. **旧 session_meta 无键 → fail-open**：`recover_*` 五键、`goal_state`、`provider_fail_streak`、
   `timer_*`/`sched_*`/`dispatch_*` 全部「缺键 = 默认态」——旧会话（重启升级场景）零迁移成本：
   - recover 域：预算空表 → 默认 3 上限；通知/forks/needs_user 空数组（recovery.rs:327-335、1286-1292 已保证）；
   - timer/sched：旧内存 store 的声明自然丢失（现状即如此），真适配后**新注册的声明才持久化**——
   这是语义增强不是迁移，不需要数据搬运；
   - goal：旧会话无 goal_state = 非 goal 会话，行为与现状一致（前端 goalMode 是内存态，本就不持久）。
2. **事件旧帧解析**：新增事件类型对旧解析器静默忽略（33-changelog:26-29 的既有保证）；
   旧帧（41 事件基线）对新解析器照常解析（信封 schemaVersion 缺省 1）。**无破坏变更**——本轮
   不删不改既有事件字段，全部 minor 兼容新增。
3. **前端旧路径过渡**：
   - goal：前端 decideGoalContinuation（goalModeController.ts:202-273）是现行权威，保留为过渡兼容；
     引擎 goal_state + 事件登记后，前端逐步投影化（05 文档 P2-10）——**过渡期内双写，以引擎为准**
     （详情见 §6 D2 双写一致性裁定）；
   - hydrate：error 态从「过滤」变为「保留+标记」是行为变更，但只影响「重启后水合内容变多」——
     模型侧无 schema 契约；前端 store 路径（sessionRustDb.ts 写入面）不受影响。
4. **schemaVersion 演进**：信封恒 1（events.rs:939）；持久化 payload 不引入版本列
   （33-changelog:22）；goal_state JSON 内嵌 schemaVersion 字段仅为结构自描述，解析时缺省视为 1，
   不参与迁移判定。
5. **命令面退役对称**：登记新命令走 33-changelog 1.8 命令面登记的逆向流程（main.rs 注册 +
   manifest 双端 + commandMap 白名单 + 条数测试）；`resume_subagent`/`kill_all` 实现体已带

## 5. 维度边界建议（数据面哪些随机制维度走，哪些必须集中）

**必须集中（单一真源，禁分叉）**：

| 集中面 | 真源位置 | 理由 |
|---|---|---|

| 事件 changelog | 33-event-schema-changelog.md | minor/major 规则 + fixture 四件套勾稽（33-changelog:41-46） |
| UI 组件（失败态卡片/恢复状态行） | crish-desktop 单一组件族 | 跨维度复用（子代理失败 / 主 run 打断 / goal stalled 共用卡片形态），分散即三处改版 |
| session_meta 键命名空间纪律 | recovery.rs:80-81 注记 + 本文档 2.B 表 | 防键碰撞与语义污染（如熔断键误入 recover_* 前缀） |

**随机制维度走（各自建键/事件，不集中）**：

| 维度 | 数据面 | 独立理由 |
|---|---|---|
| C7 恢复 | recover_* 五键 + recovery-* 五事件 | 预算/通知/fork 生命周期自成闭环（RecoveryCoordinator 单写方） |
| goal 模式 | goal_state 单键 + goal-* 事件 | 轮次语义与恢复语义正交（goal 是目标跟踪，recovery 是错误恢复） |
| provider 熔断 | provider_fail_streak 单键 | 会话级频率控制，独立于指纹预算 |
| 软调度（timer/sched/wait） | timer_*/sched_*/dispatch_* | 声明生命周期各自管理（fired 位/时刻幂等/整表覆盖），trait 形状不同（2.F F1 理由） |
| 重启恢复 | restore 域（restore.rs）+ interrupted 列表 | 现状已独立（RestoreStatus），本轮只加「恢复条目入队」消费端，不改其形状 |

**边界裁定**：机制维度的**行为**随各模块走（各自的键、各自的事件 payload struct），
但**入口与出口集中**——入口 = 事件注册表/命令清单（一个文件改）、出口 = core_get_status +
前端组件族（一个查询命令 + 一个组件族）。这正是「数据面集中、机制面分散」的既有架构
（timer 域事件 1.5 先例：发射点在 timers.rs，登记在 conex-types，消费在 steering 面）。
