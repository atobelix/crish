## 0. 结论速览（选型裁决摘要）

1. **退避重试接线位置：推荐方案 B（会话层 `transient_retry` 内加退避 + Retry-After + 预算）**，不推荐 04 文档 P0-1 的「方案 A：直接外包给 `provider_stream_with_observer`」——该函数是**收集式 API（返回 `Vec<SseFrame>`）**，与生产**增量流**（T09.1 实时 delta）矛盾，不可直接落地（§2.1 事实修正 1）。方案 B 是唯一同时覆盖流前（pre-stream）与流中（mid-stream）两类瞬态错误的决策点，改动面最小，且与 C7 阶梯 1 的 `RecoveryRetryPolicy` 常量（750/8000/60000）天然镜像。
2. **Retry-After 消费：429 必须等（可突破 8s 封顶，钳到 5 分钟与剩余预算）；5xx/Timeout/Network 纯退避即可**（分类器只在 429 解析 Retry-After 头，error.rs:248-251）。（§2.2）
3. **连接配置：生产客户端从裸 `Client::new()` 改为显式 `Client::builder()`**（connect_timeout 10s / tcp_keepalive 30s / http2 keepalive ping 30s+5s / 不设总超时），全部为 reqwest/hyper 既有能力，约 30 行 + 可配面。（§2.3）
4. **多端点 failover：P3 独立项，不与本次接线捆绑**。代码量 500-800 行 vs 熔断 80-120 行，量级差一个数量级，收益仅对配置了多端点的用户存在；与缓存亲和头（engine.rs:426-430）冲突需专门处理。（§2.4）
5. **会话级熔断：必做**，与退避接线同批落地（防火焰重试），数据面与 C7 Episode 预算共用 session_meta + 「禁止自动恢复」出口（recovery.rs:956-975）。（§2.5）
6. **流中断部分保留：metadata.providerError 增强为结构化标注（含 kind）**，约 40-60 行，成本低、水合后模型/用户可感知中断原因；前端展示渲染列入 P2 观测项。（§2.6）
7. **维度边界：`RunOutcome.provider_error` 字段必须与恢复阶梯维度一起做**（C7 阶梯 1 的 `RunFailureContext` 输入，03 文档 A2 同点）；其余改动（退避/连接配置/超时可配/熔断）可独立先行。

## 1. 传输韧性目标架构：从「字节流读取」到「run 收场」的分层

错误处理链路共 5 层。现状全链已闭环（错误不会静默吞掉），但**重试决策层缺少退避/预算/Retry-After 三个要素**（G1/G2，04 文档），是本维度唯一的实质性缺口；连接层配置薄弱（G3）。

```
┌──────────────────────────────────────────────────────────────────────┐
│ L5 收场层（run 生命周期 + 跨 run 调度）                                 │
│   session-loop turn_complete/end（EndDecision::error）                 │
│   + 壳层 drive_run_loop 收口 / decide_idle_resume（core_run_commands.rs:2505-2515）│
│   现状：error 收场不自动续 run（reason != Stop 硬排除，:2511-2515）        │
│   本维度输入：RunOutcome.provider_error（fatal 填充，03 A2 同点）        │
├──────────────────────────────────────────────────────────────────────┤
│ L4 恢复阶梯层（run 内恢复决策）                                          │

│   决策输入：ClassifiedStreamError{kind, retryable, retry_after_ms}       │
│   （retry_after_ms 已透传至本层但从不消费——consume/mod.rs:370 解析，       │

├──────────────────────────────────────────────────────────────────────┤
```

分层职责与关键不变量：

| 层 | 职责 | 现状实现位置 | 本维度缺口 |
|---|---|---|---|
| L1 读取层 | 字节读取、超时探测、abort 中断、TCP/h2 保活 | reader.rs:158-248（双段超时 + biased abort 竞速）；transport/mod.rs:73-79；engine.rs:1093 | 无连接配置（G3：半开连接只能等 idle 60s） |
| L2 分类层 | 错误归一为 13 类 + retryable + retry_after_ms | error.rs:203-314；engine.rs:456-488、603-609、615-622 | 无（分类完备，04 §2.1 逐行有测试） |
| L3 重试决策层 | 是否重试、等待多久、预算约束、abort 复查 | stream_error.rs:81-95（立即重试，无 sleep） | **退避 / Retry-After / 预算全缺（G1/G2）** |
| L4 恢复阶梯层 | 瞬态→length→压缩→fatal 的分流 | stream_error.rs:47-77 | 无（L3 补上后本层即完整）；C7 接线属恢复维度 |
| L5 收场层 | error 收场、消息保留、跨 run 调度 | turn_complete.rs:56-65；core_run_commands.rs:2844-2872、2505-2515 | error 不自动续 run（01 G2，恢复维度）；fatal 的分类信息不上行（03 G7，`RunOutcome.provider_error`） |

分层不变量（本维度改动不得破坏）：

1. **超时/abort 一律以错误上抛，绝不静默结束**（reader.rs:7「02 §六.2」）。
2. **已产出内容绝不重试**：三层镜像语义 `retry.rs produced_content`（retry.rs:412-428）→ `streaming.rs builder.is_empty()`（streaming.rs:116-129）→ `recovery.rs ladder1_decision ContentProduced`（recovery.rs:212-217）。退避只影响「未产出」路径的等待，不触碰本不变量。
3. **abort 优先级**：L1 读取竞速（reader.rs:230-232 biased）、L2 分类直传、L3 每级决策前复查（Q40，stream_error.rs:52-55、82-85）——退避 sleep 必须可被 abort 中断（§4.3）。

## 2. 关键技术选型（深挖对比，含代码量评估）

### 2.1 选型 A：退避重试接线位置（方案 A / B / C）

**前置事实修正 1（04 文档 P0-1 与代码矛盾，以代码为准）**：04 文档 §5 P0-1 建议「把 `HttpProviderCall::stream` 的发送+分类逻辑外包给 `provider_stream_with_observer`」。**该方案在代码层面不可直接落地**：

- `provider_stream_with_observer` 的 attempt 闭包返回 `StreamAttempt { frames: Vec<SseFrame>, error, produced_content }`（retry.rs:327-336、370-463）——即**尝试必须读完整条流、收齐所有帧后才返回**，是「收集式」API；
- 而生产 `HttpProviderCall::stream` 返回的是**增量事件流**（`ProviderEventStream`，engine.rs:514-517 unfold 状态机），每帧到达即产出 `message-delta` 实时轨（T09.1，engine.rs:104-114、`delta_sink.push`）。T09.1 是已落地的核心体验（前端实时渲染），不能为接退避而回退成「收完再返回」。

**修正后的方案 A 有三个子形态**（代码量评估见对比表）：

- **A1（轻量）**：`HttpProviderCall::stream` 的发送段（engine.rs:452-489）改为内部循环：`send → 非 2xx 分类 → should_retry 决策 → TokioSleeper 退避 → 重发`。只覆盖流前（HTTP 层）错误；流中错误（Network/Timeout/StreamInterrupted）仍走会话层 3 次立即重试。约 60-80 行 + mock server 测试 ~100 行。
- **A'（完整）**：在 agent-provider 新增「增量流 + 重试」封装（Stream transformer：空闲→发送→流式→失败未产出→退避→重发），`HttpProviderCall::stream` 改用它。覆盖全错误路径，但需改造 engine 返回逻辑、`streaming.rs:116-129` 的 `builder.is_empty()` 分支将退化（错误被 provider 层吞掉）、Q21 abort 竞速（streaming.rs:86-101）与 delta 时序需重新验证。约 250-400 行 + 测试，**回归风险集中在 T09.1 增量轨这条敏感路径**。
- **A2（不接线，仅复用决策函数）**：不动 engine，仅把 agent-provider 的 `should_retry`/`choose_retry_delay_ms`/`TokioSleeper` 作为会话层实现的参照（B 方案直接镜像其语义）。

**方案 B（会话层接线）**：`stream_error.rs` 的 `transient_retry`（81-95）内、`NO_PROGRESS_CONTINUE` 派发前插入退避等待：

- 决策输入齐全：`classified.retry_after_ms` 已在 `ClassifiedStreamError` 上（conex-types/response.rs，consume 层已透传，engine.rs:620 填充）；abort 复查点已有（Q40）；
- 需要把 `transient_retry` 从同步 fn 改为 async fn（调用链 `streaming.rs:147 handle(...).await` 已是 async，改造成本一行）；
- 需要新增：退避函数、预算起点字段、abort 竞速 sleep、`SessionLoopOptions` 可配字段。约 100-150 行 + 单测 80-120 行。

**方案 C（A+B 双层）**：provider 层短退避（秒级吸收抖动）+ 会话层长预算（跨 provider 预算耗尽再尝试）。改动 = A + B 之和（A1+B 约 350 行，A'+B 约 600-700 行）。

**对比表**：

| 维度 | A1（provider 层，轻量） | A'（provider 层，完整） | **B（会话层，推荐）** | C（双层） |
|---|---|---|---|---|
| 覆盖错误路径 | 仅流前（429/5xx） | 流前+流中全覆盖 | **流前+流中全覆盖**（streaming.rs:133 与 :117 两路都汇到 `stream_error::handle`） | 全覆盖 |
| 代码量（含测试） | ~160-200 行 | ~400-500 行 | **~180-270 行** | 350-700 行 |
| 触碰敏感路径 | engine 发送段（低风险） | T09.1 增量流、Q21 abort 竞速、`builder.is_empty()` 分支退化（高风险） | **仅 stream_error.rs + LoopState 字段 + options 字段（零触碰）** | A1+B 触碰发送段；A'+B 触碰增量轨 |
| 退避预算语义 | 依赖 RetryPolicy 默认 750/8000/60000 | 同左 | **镜像 recovery.rs 常量（750/8000/60000），未来 C7 接线预算口径天然一致** | 双层预算需定义分层（provider 短/会话长） |
| 诊断事件 | 可接 M14 observer（生产当前零发射） | 同左 | 复用现有 `emit_retry_diagnostic`（provider-diagnostic phase=retry），扩展 delay/retry_after 字段即可 | 双层诊断叠加 |
| 测试成本 | 需 mock HTTP server（429+Retry-After 头） | 需 mock server + 增量流回归套件 | **纯单测（注入时钟 `start_paused` + advance），无需网络**；端到端 mock 可作集成测试补充 | 叠加 |
| 对 Retry-After 语义 | 受 `max_delay=8s` 钳制（retry.rs:128），429 等 30s 会被钳成 8s | 同左（需配 max_delay 放宽） | **会话层可对 429 放宽钳制（§2.2），语义精确** | 需对齐两层钳制口径 |

**推荐：方案 B**。理由：

1. **唯一覆盖全部瞬态错误的单一决策点**：流前错误（engine.rs:456-488 → `Err(classified)` → streaming.rs:133）与流中无内容错误（streaming.rs:117-119）在 `stream_error::handle` 汇合（stream_error.rs:47-77），在此加退避一次解决两个入口；方案 A 任何形态都只覆盖流前，A' 需新建整条重试封装才能覆盖流中。
2. **改动面最小且零回归风险**：不触碰 T09.1 增量轨、Q21 竞速、delta 时序（这些是 04 文档与 03 文档共同确认的生产核心体验）。
3. **与 C7 阶梯 1 预算镜像一致**：`RecoveryRetryPolicy`（recovery.rs:115-120，750/8000/60000）是 retry.rs 的镜像，本方案在会话层再镜像同组常量并加测试锁定（防漂移），未来 C7 接线（恢复维度）时「run 内退避 → 跨 run 阶梯」预算口径连续，无单位换算断层。
4. **Retry-After 数据已在手**：`classified.retry_after_ms` 是 `ClassifiedStreamError` 字段（非 agent-provider 依赖），session-loop 无需新增依赖即可消费（保持「session-loop 不直接依赖 agent-provider」的分层约束，B3.4 第 5 点，engine.rs:634-635 注释）。

**方案 A 的定位**：A1 作为 P1 增强候选（当会话层状态机往返成本（NO_PROGRESS_CONTINUE → preparing → streaming 重建，stream_error.rs:91 + prepare_turn TURN_PREPARED）被实测证明不可接受时）；A'（增量流重试封装）**明确不做**——回归风险大于边际收益（B 已吸收 90% 场景，A' 的增量价值仅为状态机往返与 M14 观测事件）。

**事实修正 2（01 文档 P1-1 与代码矛盾）**：01 文档 P1-1 建议「缺省指数退避 600ms × attempt，镜像 recovery.rs 750/8000/60000 常量」——600ms 与 750ms 自相矛盾，且规范出处 01-session-loop-semantics.md:138 的 600ms 是旧值。以代码为准：**基数为 750ms**（retry.rs:48 `base_delay_ms: 750`；recovery.rs:116 `RECOVERY_BASE_DELAY_MS = 750`；退避序列测试锁定 750→1500→3000→6000→8000，retry.rs:503-514）。退避序列 3 次重试累计等待 5.25s（750+1500+3000）。

### 2.2 选型 B：Retry-After 消费规则

分类器只在 HTTP 429 时解析 Retry-After 头（error.rs:248-251）；`retry_after_ms` 经 `to_classified` 透传（engine.rs:620）。消费规则按错误类分档：

| 错误类 | 是否必须等 Retry-After | 规则 | 上限钳制 | 证据 |
|---|---|---|---|---|
| RateLimit（429） | **必须**（服务端权威指令） | `wait = max(退避, retry_after)` | **突破 8s 封顶**，钳到 `min(MAX_RETRY_AFTER_MS=5min, 剩余预算)` | retry.rs:29、116-133；错误头只有 429 解析（error.rs:248-251） |
| ServerError（5xx） | 否（客户端猜测） | 纯指数退避 750/1500/3000…8s 封顶 | `min(8s, 剩余预算)` | 分类器不解析 5xx 的 Retry-After 头，无需消费 |
| Timeout / Network | 否 | 纯指数退避（断流/连接失败恢复快，退避足够） | `min(8s, 剩余预算)` | 同左 |

关键设计决策（见 §6-D1）：**429 的 Retry-After 必须突破 `max_delay=8s` 钳制**。理由：agent-provider retry.rs 的语义是 `choose_retry_delay_ms` 先取 `max(backoff, retry_after)` 再钳 `max_delay`（retry.rs:128）——默认策略下 `Retry-After=30s` 被钳成 8s（测试 `retry_after_respected_and_clamped` 锁定，retry.rs:650-668），等于「消费了但没消费」：provider 说 30s 后重试，客户端 8s 就打回去，必再 429，浪费一次配额。会话层实现独立于 retry.rs，可对 429 放行到 5 分钟上限；同时保留预算钳制（60s 预算下 429+30s 只能等一次，第二次重试被预算拦截——这正是预算存在的意义，见 §4.1）。

一致性要求：若未来补 A1（provider 层也接），其 `RetryPolicy.max_delay_ms` 必须配为 60000 且语义与会话层对齐，否则双层口径漂移。

### 2.3 选型 C：连接配置（reqwest client 显式配置清单）

生产客户端现状：`reqwest::Client::new()`（engine.rs:1093），零显式配置。逐项清单与效果/风险：

| 配置 | 值 | 效果 | 风险 | 可配性 |
|---|---|---|---|---|
| `connect_timeout` | 10s（reqwest 默认 30s） | 建连失败探测 30s→10s，DNS/建连/TLS 失败更快进入 Network 分类 → 更早重试（G3 缓解） | 极慢网络下偶发误判（10s 建连对绝大多数网络充裕，TCP+握手通常 1-2s） | 可配（session_meta 键或配置文件） |
| `tcp_keepalive` | 30s | TCP 层探活：半开连接（网络波动中 TCP 静默挂起）在 2-3 探针周期内被 RST → 挂死探测从「idle 60s 才超时」显著提前（G3 直接缓解） | 低（每连接少量探针包） | 可配 |
| `http2_keep_alive_interval` | 30s | h2 PING 对抗静默挂起（provider 支持 h2 时） | 低；**不支持 h2 的 provider 自动协商到 HTTP/1.1，本设置无效但不报错**（reqwest/hyper 按 ALPN 协商，无需显式降级逻辑，见 §6-D3） | 可配 |
| `http2_keep_alive_timeout` | 5s（须 interval>0 才生效） | PING 无响应判定超时 | 低 | 跟随 interval |
| 总 `.timeout()` | **不设** | 流式长输出（分块慢流）不被总超时误杀；请求级超时继续由双段超时（first-byte 30s / idle 60s，engine.rs:93-95）承担 | 无总超时 → 挂死流只能靠 idle+keepalive 兜底（60s 内可接受） | 不提供 |
| `pool_idle_timeout` | 保持默认 90s，显式注明 | 连接池闲置回收 | 无 | 不提供（注明即可） |

总代码量约 30 行（`reqwest::Client::builder()` 链）+ 可配接线 ~40 行。验收：`cargo test -p agent-workbench` 编译绿；本地 TCP 挂起流在 keepalive 窗口内以错误收场（复用 transport/mod.rs:124-140 `serve_sse_headers_only` 模式，transport/mod.rs 测试域已有本地 TCP server 基建，见 :92-119 `serve_sse`）。

实现注意：engine.rs 中 `Client::new()` 出现 10 处（1093 为生产装配点；2625/2721/2727/3100/3202/3541/3698/3730/3749/3784 为测试装配）——封装 `fn build_http_client() -> reqwest::Client` 单点，测试装配可传参覆盖（短超时/关 keepalive）。

### 2.4 选型 D：多端点 failover vs 单端点 + 熔断

| 维度 | 主备链 failover（TS fallback-chain 迁 Rust） | 单端点 + 会话级熔断（选型 E） |
|---|---|---|
| 代码量 | **500-800 行**（agent-provider 新模块：链状态/失败转移/不重试已试端点/耗尽上抛 ~300-400 行 + 配置面（base_url 列表解析）~100 行 + 测试 ~300 行） | **80-120 行**（session_meta 键 + 装配 + 判定） |
| 收益场景 | 主 provider 长时故障（如 DeepSeek 网关持续 5xx）时换端点继续；**仅对配置了多端点的用户生效**（自建网关+官方双备） | 所有用户生效（防跨 run 反复撞墙，04 G9） |
| 与缓存亲和头冲突 | **必须处理**：切换端点后 `x-grok-conv-id` 等亲和头（engine.rs:426-430 `request_headers`，affinity_http_headers 追加）跨端点失效 → 应放弃亲和头 + 缓存策略降级（`build_cache_policy` engine.rs:358-364 按 session_id 判定）→ 接受缓存 miss | 无 |
| 与重试预算关系 | 挂在重试预算耗尽后的出口（04 P3-1：首次失败主端点重试，≥2 次切备端点） | 独立护栏，与退避同文件 |
| 幂等性 | 重试请求体不变（engine.rs:443-456 每次重进 streaming 重建请求但内容相同），安全 | — |

裁决：**两者不是二选一，而是不同层次**——熔断是默认路径的护栏（必做，§2.5），failover 是「配置了才存在」的能力（P3 独立项）。代码量量级差一个数量级，且 08 文档同样将 failover 列为 P1 资产迁移项（08 §3「provider 主备链 failover 迁入 Rust」）。本次接线清单**不捆绑 failover**，仅给出接入点设计（挂在 §3-1 重试耗尽后的出口 + 亲和头放弃规则），作为恢复维度的后续排期输入。若用户裁定优先补 failover（「几千行以内选效果更好的」），其实现顺序建议为：配置面 → 链状态机 → 亲和头降级 → 测试，排在方案 B 之后。

### 2.5 选型 E：会话级熔断（provider_fail_streak）

**问题**（04 G9）：`transient_retries` 是 LoopState 字段（每 run 重建，handlers/mod.rs:91、loop/mod.rs:672 归零），跨 run 的持续故障每 turn 都有 3 次配额 → 长会话反复撞墙。

**设计**：

- **计数语义**：session_meta 键 `provider_fail_streak`（u32）。任何一次**瞬态类 fatal**（stream_error.rs:237-269 fatal_provider_error 路径，kind ∈ RateLimit/ServerError/Timeout/Network）streak+1；任何一次**成功调用**（消息正常 commit）streak 归零。纯连续计数、无时间窗（成功即复位已天然防累积误伤，§6-D4）。
- **阈值**：6 次连续瞬态 fatal（04 文档 P2-2 建议「3 个 turn 内 ≥6 次」的简化：连续 6 次等价于 3 个 turn 各耗尽 3 次配额后再撞一次；且无窗口更简单可测）。
- **触发后行为**：`transient_retry` 入口检查（options 注入当前 streak）→ 超过阈值跳过 run 内重试直接 fatal → 发 `runtime-intervention-required` 事件（复用 steering_evaluation.rs:68-75 模式）→ 用户可见、用户手动重试不受限（resume 语义保留）。
- **与 C7 Episode 预算共用数据面**：C7 预算（recovery.rs:245-336，`fingerprint(subagent_id, task)` + `recover_episodes` 上限 3）按「操作指纹」计数，熔断按「会话」计数，语义不同但**共用三样东西**：① session_meta 存储面（`recover_*` 键 namespace，recovery.rs:80-97）；② 「超预算 → 禁止自动恢复」的判定出口（`can_recover`，recovery.rs:956-975）；③ 重启宽容解析（fail-open，recovery.rs 从 JSON 容错读取不重放授权）。熔断触发后自动重试禁用的判定即挂在 can_recover 同侧（streak ≥ 阈值视同超预算），C7 接线（恢复维度）时零额外工作。
- **数据流时序**：run 内 fatal → 壳层 drive_run_loop 收口消费 runtime-error 事件（core_run_commands.rs:2772-2774 已捕获，含 retryable 标志）→ 写 session_meta streak → 下一 run 装配 SessionLoopOptions 时读入。熔断语义天然跨 run（正是 G9 的目标），run 内不加状态。
- **代码量**：session_meta 读写 ~30 行 + options 字段 ~8 行 + transient_retry 入口检查 ~10 行 + 壳层收口更新 ~20 行 + 测试 ~40 行。

### 2.6 选型 F：流中断部分保留的错误标注增强

**现状**（G8）：已产出内容的断流 → `streaming.rs:119-127` 注入 `Stop{reason: Error}` → consume 侧 Message + `metadata.providerError` 标注（agent-provider consume/mod.rs:340-342；session-loop stream.rs:474-476 镜像）。标注是**裸错误文案字符串**，无分类信息：用户看到半截回答，前端无法渲染「中断原因（Network/Timeout/429）」；且水合后模型也只知道「有错误」不知道「什么错误」。

**决策：增强为结构化标注，不做用户级强提示**：

- 改动：`providerError` 保持字符串（向后兼容，既有消费方不破坏）**之外**，新增 `metadata.providerErrorKind`（kebab-case 13 类）与 `metadata.providerErrorRetryable`（bool）两个字段。改动点：agent-provider consume/mod.rs `build_message_metadata`（:308-347）+ session-loop stream.rs `build_message_metadata`（:439-481）两处镜像（各 ~15-20 行）。但 session-loop 侧拿不到 kind——`streaming.rs:122-126` 注入 Stop 时只有 `classified.message`，需要同时透传 `classified.kind`：`Stop{reason: Error}` 事件扩展 error_kind 字段（session-loop stream.rs 的 Stop 变体 + engine.rs to_loop_event 映射，~15 行）。
- 为什么不做用户级强提示（弹窗/横幅）：① 部分保留消息的 stopReason 是正常值（Message，01 D6「error 不一票否决」），系统语义是「内容可用」，强提示与语义冲突；② 中断后的恢复决策权在主 agent/用户（C7 阶梯 2/4，恢复维度），传输层只负责「标注到位」，渲染/提示是观测维度（P2）的事。
- 收益验证点：hydrate.rs:87-93 会过滤 error 终态消息，但部分保留消息是正常 Message（含 providerError 标注），不会被过滤 → 标注在水合链路可见。
- 代码量：~40-60 行 + 测试。

## 4. 风险与护栏

### 4.1 火焰重试

三道护栏叠加：① 指数退避（750→8s，重试窗口内击打频率指数下降）；② 60s 总预算（`elapsed >= total_budget` 停止，对齐 retry.rs withinRetryBudget 严格小于，retry.rs:163-166）；③ 会话级熔断（连续 6 次瞬态 fatal → 自动重试全禁，§2.5）。预算对 429 长 Retry-After 的真实约束场景：429+30s → 第一次等 30s（累计 30s），第二次重试时 `elapsed=30s`，等待被钳到剩余 30s，第三次重试前 `elapsed=60s` 预算耗尽 → 直接 fatal——**这正是预算的价值**：不无限尊重服务端的「再来一次」。

### 4.2 预算耗尽后的行为

预算/次数耗尽 → `fatal_provider_error`（stream_error.rs:237-269）→ `PROVIDER_ERROR` + endReason=error → run 以 error 收场（现状语义不变）。跨 run 的自动恢复 = 恢复维度（01 P1-2 自动续 run：retryable 放行 + 连续 error ≤3 + user_touched 取消；C7 阶梯 1 接线）。本维度承诺：**退避接线不改变收场路径与收场原因**，只改变收场前的等待与次数分布（3 次立即 → 3 次退避），熔断额外提供「跳过无效重试」的提前终止——均不引入新的收场状态。

### 4.3 abort 竞速

三层已就绪：L1 读取竞速（reader.rs:230-232 biased abort 优先）、Q40 每级决策前复查（stream_error.rs:52-55、82-85）、退避 sleep 竞速（§3-1 ④，select! biased）。语义对齐 retry.rs `TokioSleeper`（retry.rs:316-323：sleep 期间 abort 立即中断并返回 Aborted）。用户 force_cancel（L3）在退避 sleep 期间立即响应；cooperative_stop（L2）延迟到 sleep 后的下一个安全点处理（L2 本就是安全点协作语义，01 文档 2.5，非回归）。

### 4.4 重试与 token 成本

未产出内容的重试 = 全量新请求（对话 + tools + max_tokens 重发，engine.rs:443-456 每次重进 streaming 重建请求体）；已产出内容绝不重试（三层镜像不变量）。退避不改变单次成本，但：① 减少无效击打（429 尊重 Retry-After 后不再白费请求）；② 预算耗尽终止防无限成本；③ 熔断防跨 run 反复烧钱（04 G9 的直接收益）。**重试不计入 usage/token 统计**（§6-D5）：失败尝试的 usage 不落库，仅成功消息的 metadata.usage 记账（consume build_message_metadata），防重复记账。

### 4.5 断流不重复输出的既有保证

三条不变量在接线后原样保持：① `builder.is_empty()` 判定（streaming.rs:116-129）决定「重试 or 保留」，退避只挂在重试分支内；② 已产出内容 → Stop{Error} → Message + 标注（§2.6 增强只加字段不改语义）；③ 会话层 commit 基于完整对话（部分消息已 commit 后，重试若发生也是新请求基于完整对话——语义层重复不可能，04 §3.3）。回归护栏：现有测试 `text_then_error_stop_yields_message` / `abort_with_content_keeps_partial_message`（consume/mod.rs:425-434、539-544）与 streaming.rs 单测原样保留，新增退避测试不得触碰这些断言。

### 4.6 测试资产与门禁

退避改动直接落在 `crates/session-loop` 现有单测面（stream_error.rs 测试域），无新测试框架；agent-provider 既有 retry.rs 测试（决策表/退避序列/Retry-After 钳制/预算）作为语义参照不删改。reference/markdown-editor 门禁（npm test）与本改动无关，不触碰。`cargo test --workspace` 为回归面（73 套件基线）。

## 5. 维度边界建议

### 5.1 必须与恢复阶梯维度一起做的（本维度提供数据面）

1. **`RunOutcome.provider_error` 字段**（§3-6）：C7 阶梯 1 接线（03 文档阶段 A 的 A2）的直接输入——`RunFailureContext` 需要 error_kind/retries/produced_content，目前收口只收到 Completed/Failed 二态（03 G7）。本维度的 fatal 路径（stream_error.rs:237-269）是唯一能填充该字段的点。**两个维度必须在同一批次改动 stream_error.rs**（3-1 改 transient_retry、3-6 改 fatal_provider_error，同文件同批最安全）。
2. **retryable 标志语义**：runtime-error 事件已带（stream_error.rs:261），01 P1-2 自动续 run 直接消费；本维度不重复造。
3. **熔断与 C7 预算的「禁止自动恢复」出口**（§2.5）：数据面共用 session_meta，判定出口同侧（can_recover），C7 接线时零额外工作——若熔断先行，需在恢复维度接线时保留该出口契约（streak ≥ 6 视同超预算）。

### 5.2 可独立先行的（本维度内部闭环）

1. 退避 + Retry-After + 预算（§3-1）：session-loop 内部闭环，不依赖任何其他维度。
2. 连接配置（§3-2）与超时可配（§3-3）：engine 侧独立。
3. 流中断标注增强（§3-5）：consume/stream 层独立，不影响收场语义。
4. 会话级熔断数据面（§3-4）：可后接 C7（见 5.1-3 契约）。

### 5.3 依赖关系与建议顺序

```
§3-1 退避（核心） → §3-4 熔断（同文件同批） → §3-2/3-3 连接配置（独立并行）
→ §3-5 标注增强（独立） → §3-6 RunOutcome.provider_error（与恢复维度 A2 同批）
```
failover（§2.4）为 P3 独立项，接入点设计已给出，排期归恢复维度/配置面。

## 6. 动态决策记录

| # | 问题 | 决策 | 理由 | 影响面 |
|---|---|---|---|---|
| D1 | 429 的 Retry-After（如 30s）在默认 `max_delay=8s` 下被钳到 8s，是否仍算「消费」？ | **不算**。会话层退避对 RateLimit 放行 Retry-After 到 5 分钟上限（预算仍钳）；5xx/Timeout/Network 维持 8s 封顶 | 服务端 429 头是权威指令，钳掉等于没消费（8s 后打回必再 429，浪费配额）；5xx 退避是客户端猜测，8s 足够；与 agent-provider retry.rs 的钳制语义差异在会话层独立实现，不影响既有测试 | 会话层退避函数分错误类处理；未来 A1 接线需配 max_delay_ms=60000 对齐 |
| D2 | 退避基数 600ms（01 文档/规范 01 §2.5）还是 750ms（retry.rs/recovery.rs）？ | **750ms**（事实修正 2，§2.1） | 代码真值：retry.rs:48、recovery.rs:116；退避序列测试锁定 750→1500→3000（retry.rs:503-514）；600ms 是旧 TS 规范残留 | 会话层常量与 recovery.rs 镜像一致 |
| D3 | HTTP/2 ping 对不支持 h2 的 provider 是否会报错/需要降级？ | **不需要显式降级**。reqwest/hyper 按 ALPN 自动协商，h1.1 连接上 h2 keepalive 设置无效但不报错 | hyper 的 h2 设置只在协商到 h2 时生效（标准行为），无配置错误面 | 连接配置清单按默认值即可 |
| D4 | 熔断计数要不要时间窗（04 建议「3 turn 内 ≥6 次」）？ | **纯连续计数、无时间窗**（连续 6 次瞬态 fatal 即熔断） | 成功即归零已天然防「长会话累积误伤」；无窗口实现与测试都更简单；连续 6 次 fatal 已充分证明 provider 不可用 | 熔断判定为单键单值 |
| D5 | 重试是否计入 usage/token 统计？ | **不计入**。失败尝试的 usage 不落库，仅成功消息的 metadata.usage 记账 | 防重复记账（部分保留消息已计成功尝试 usage）；失败尝试的 usage（若有）对成本归因无意义；现状即如此，不改变 | 无代码改动，仅记录 |
| D6 | 读超时的心跳语义：idle 60s 是否需 per-chunk 心跳？ | **保持现状**。慢速但持续有数据的流永不超时（reader.rs:214-248 每次新块重置计时）是特性非缺陷；挂死探测由 keepalive（§3-2）兜底 | 「数据缓慢不停」是合法流，不该被心跳误杀；真正挂死由 TCP keepalive + idle 60s 双保险 | 无 per-chunk 心跳改动；分块大小保持 reqwest 默认 |
| D7 | 熔断触发后用户手动重试是否受限？ | **不受限**。熔断只禁「自动重试」（run 内 + 自动续 run 侧），用户显式发消息/手动 resume 照常 | 用户意志永远优先（与「用户显式停止永不自动续」红线对称）；熔断是护栏不是闸门 | 熔断判定只挂在自动路径 |
| D8 | 会话层退避 sleep 期间 L2 cooperative_stop 是否延迟？ | **接受延迟**。L3 force_cancel 经 select! 立即中断；L2 协作停止在 sleep 后安全点处理 | L2 本就是安全点协作语义（01 文档 2.5），延迟到下一个安全点是设计内行为，非回归 | 退避 sleep 竞速只绑 abort_signal（L3） |
