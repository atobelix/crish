## 1. 结论速览

1. **现状一句话**：「任务连续性」的全部关键资产（C7 四级恢复阶梯、退避重试、checkpoint 三件套、idle 续 run 拉起器、12/5/1 守卫）**已实现且测试充分，缺的是生产接线与三条链的闭合**——(a) 子代理失败 → C7 阶梯 1/2 无触发点（recovery.rs:57-62 自述 F2-08）；(b) AI 休眠后唤醒事件无消费方（缺独立 watcher，07 G2）；(c) 主 run 错误收场被 `decide_idle_resume` 硬性排除（core_run_commands.rs:2513）。
2. **架构主线**：把「继续工作」收敛为**单一一套「run 边界决策 + 唤醒源汇聚 + 拉起器复用」机制**，不新造循环。所有自动续 run（goal 未完成 / error 可重试 / 定时器到期 / 子代理失败 / 重启恢复）共用 `PendingMessageQueue + decide_idle_resume/spawn_idle_resume_run` 通道（core_run_commands.rs:2505-2671），差异只在唤醒源与注入文本。
3. **选型裁决（详见 §4）**：重试退避放 **provider 层**（外包 `provider_stream_with_observer`，复用 retry.rs 现成实现）；C7 接线取**完整生命周期装配**（分阶段：先阶梯 1+2，fork 后置）；goal 引擎化取**收口 RoundAssessment**（前端降级投影）；唤醒**四源扩展与独立 watcher 是互补关系，两者都做**；checkpoint 走**机制面注入**；熔断与预算**模式复用、键分立**。
4. **维度划分**：8 个互斥维度（D1-D8），覆盖用户四诉求 × 全部缺口，维度间仅依赖关系无重叠（详见 §3）。
5. **红线不变**：12/5/1 守卫与嵌套禁令只增不减；用户显式停止永不自动续；探索类文档配额不绕过；测试资产门禁不受影响。

## 2. 目标架构总图：端到端「agent 任务连续性」分层架构

### 2.2 层间接口（契约面）

| 接口 | 方向 | 契约载荷 | 现状 |
|---|---|---|---|
| 流错误上行 | L0 → L1 | `ClassifiedStreamError{kind, retryable, retry_after_ms}`（conex-types/src/response.rs:24；engine.rs:615-632 分类） | ✅ 已通 |
| 重试阶梯回执 | L1 内部 | `transient_retry`（上限 3）/ length / 压缩 → `NO_PROGRESS_CONTINUE` 或 `fatal_provider_error` | ✅ 已通（无退避） |
| 收场数据面 | L1 → L2 | `RunOutcome`（reason=error/stop/max-turns）+ `runtime-error` 事件（retryable 透传，stream_error.rs:252-262） | ⚠️ 收口只消费二态（Completed/Failed），错误分类信息丢弃（03 G7） |
| 恢复决策 | L2 内部 | `RecoveryCoordinator::on_subagent_run_failure(RunFailureContext)` → AutoRetry/SteeringQueued/NeedsUser | ❌ 无生产调用方（recovery.rs:57-62） |
| 唤醒汇聚 | L2 内部 | `PendingMessageQueue`（跨 run steering 条目）+ 定时器/Cron 判定器 → `decide_idle_resume` → `spawn_idle_resume_run` | ✅ 三源已通；四源与 watcher 缺失 |
| 持久化 | L2 ↔ L3 | session_meta 键（`recover_*` / `goal_state` / `timer_<id>` / `dispatch_*`）+ events 表 | ⚠️ recover_*/goal_state 无写入方；timer_*/dispatch_* 仅内存实现 |
| 观测 | L2/L1 → L4 | `recovery-*` / `goal-round-*` 事件 + `core_get_status` 恢复摘要 | ❌ 事件未登记、UI 无消费（03 G4/G8） |

### 2.3 三条主数据流（端到端）

**流 ①：provider 网络中断（主 run / 子代理共用）**

```
L0 分类（13 类）→ 退避重试（750ms→8s 封顶，Retry-After 合并，60s 预算）
  → 未产出重试 / 已产出保留（produced_content 防重复）
  → 耗尽 → L1 fatal_provider_error（endReason=error，retryable 透传）
  → L2 收口：主 run → retryable && 预算内 → 恢复条目入队 → 续 run 拉起（D2）
            子代理 → on_subagent_run_failure → C7 阶梯 1 重试 → 阶梯 2 steering+落库 → 阶梯 4 上报（D3）
```

**流 ②：goal 未完成自动继续**

```
前端 /goal 下发 visibleGoal/maxRounds → L2 RunTaskOptions 收字段 → session_meta goal_state
  → run 收口 RoundAssessment（endReason×产出 → needs-continuation/no-progress/completed/blocked）
  → 四源判定命中 goal_pending → spawn_idle_resume_run 注入 nextSteps（摘要 JSON 消费）→ 新 run（D5）
```

**流 ③：无人值守唤醒与重启恢复**

```
定时器到期/Cron 触发/恢复条目入队 → 独立 watcher（队列非空且无活动 run → 拉起 idle-resume run）
  → 注入文本 + checkpoint 载荷（read_leaf_checkpoint）→ 新 run 水合 SessionHistoryCache（D6/D7）
  重启：restore 打断 in-flight → 恢复条目入队（restore-<run_id>）→ 同链消费
```

## 3. 维度划分建议（8 个互斥维度）

划分原则：**用户四诉求 × 事实缺口 → 按「闭环链段」切分**——每维度对应一条可独立交付、可独立验收的链段；维度间只通过数据面（session_meta 键 / 事件 / RunOutcome 字段）和命令面耦合，无功能重叠。

| 维度 | 名称 | 对应诉求 | 主要缺口依据 |
|---|---|---|---|
| D1 | 传输层退避与连接硬化 | 诉求 1（断网继续） | 04 G1/G2/G3；01 G1 |
| D2 | 主 run 错误收场自动续 run | 诉求 1 + 诉求 4 | 01 G2；03 G9；08 §3 J |
| D3 | C7 恢复阶梯生产接线 | 诉求 3（子代理恢复） | 03 G1-G3/G5/G7；02 缺口 1 |
| D4 | 子代理显式恢复命令面 | 诉求 3 | 03 G6；02 缺口 2/4 |
| D5 | goal 引擎化与完成契约 | 诉求 4（一直工作） | 05 缺口 1-7；01 G3 |
| D6 | 无人值守唤醒链路 | 诉求 4 | 07 G1/G2/G3 |
| D7 | checkpoint 机制面闭环 | 诉求 4（恢复质量） | 01 G4/G5；07 G4；06 C1 |
| D8 | 观测、UI 与口径对齐 | 横切 | 03 G4/G8；02 缺口 5；00 汇总 |

### D1 传输层退避与连接硬化

- **做什么**：① 把生产 provider 出口 `HttpProviderCall::stream` 外包给 `provider_stream_with_observer`（engine.rs:435-518 → agent-provider/src/retry.rs:327-463），实例化 `RetryPolicy{max_retries: 3, ..Default}`，接入退避 + Retry-After + 60s 预算；② `reqwest::Client::new()`（engine.rs:1093）改显式 `Client::builder()`（connect_timeout 10s / tcp_keepalive 30s / http2 keepalive）；③ 会话级熔断：session_meta 键 `provider_fail_streak`（时间窗内连续瞬态失败计数，达阈值暂停自动重试转上报）。
- **不做什么**：不动 session-loop 的三阶梯结构（length/压缩阶梯保留）；不做多端点 failover（P3 单独评估）；不引入协议级断点续传（04 P3-2 明确不做）。
- **依赖现有模块**：`crates/agent-provider/src/retry.rs:107-180`（退避公式/Retry-After/预算，现成）、`apps/agent-workbench/src-tauri/src/engine.rs:435-518,1093`（外包点）、`crates/session-loop/src/loop/handlers/stream_error.rs:81-95`（内层兜底，见 §4-A）、`crates/conex-types/src/error.rs:899-908`（default_retryable 矩阵）。
- **与相邻维度接口**：→ D2：`RunOutcome` 增加 `provider_error: Option<ClassifiedStreamError>`（fatal_provider_error 填充，stream_error.rs:237-269 处接线），D2 据此判定 retryable；→ D8：熔断事件 `provider-circuit-opened` 登记。
- **验收断言**：mock 429 + Retry-After=30s → 下一次请求 ≥30s 后发出（复用 retry.rs:650-668 语义）；连续 5xx → 退避序列 750/1500/3000（retry.rs:503-514 测试锁定）；熔断达阈值后自动重试被禁且事件留痕。

### D2 主 run 错误收场自动续 run

- **做什么**：① `EndDecision`/`RunOutcome` 增 `retryable` 标志（error 收场时取 runtime-error 的 retryable，stream_error.rs:261 已有）；② `decide_idle_resume`（core_run_commands.rs:2505-2593）放行 `reason==Error && retryable && 预算内`——在 :2513 硬条件处新增分支；③ 恢复条目经 `PendingMessageQueue` 入队（复用 C7 写入侧，orchestrator/task_events.rs）→ `spawn_idle_resume_run`（:2637-2671）拉起，注入「上一轮 provider 中断（<错误>），继续任务」；④ 主 run 恢复预算：复用「指纹+Episode 上限」模式（recovery.rs:251-336），指纹前缀 `main-`，键沿用 `recover_episodes`（见 §4-F）。
- **不做什么**：不自动续 max-turns 收场（保守语义保持，core_run_commands.rs:2493-2494 注释）；不续非 retryable error（Auth/Quota/InvalidRequest）；不做主 run 的 fork/阶梯 3（只做「重发起一次」级别）。
- **依赖现有模块**：`core_run_commands.rs:2505-2593,2637-2671`（判定器+拉起器现成）、`stream_error.rs:237-269`（retryable 数据面）、`crates/orchestrator/src/recovery.rs:251-336`（预算模式复用）。
- **与相邻维度接口**：← D1（provider_error 字段）；→ D6：恢复条目与其它唤醒源共用队列，watcher 消费；→ D8：`recovery-resume-main` 事件。
- **验收断言**：模拟 3 次重试耗尽 → 系统自动拉起新 run 且上下文完整（history 经 SessionHistoryCache 续接）；第 4 次连续 error 后停止自动续；非 retryable error 不续；用户消息到达即取消（user_touched 已覆盖，:2517-2519）。

### D3 C7 恢复阶梯生产接线（子代理路径）

- **做什么**：① 每会话 `RecoveryCoordinator` 生命周期：`CoreRunState::new`（core_run_commands.rs:1474-1600 一线）新增 `HashMap<session_id, Mutex<Option<RecoveryCoordinator>>>` 惰性构造，注入 store=LocalDb（RecoveryStore impl 已有，recovery.rs:594-702）/ queue=engine.timer_steering_queue()（engine.rs:1413）/ spawner=SubagentSpawnerImpl / tree（恢复时以 RestoreOutcome.sessions 的 SessionRecord 分支重建，restore.rs:678-694）；持久化调用走 `spawn_blocking`（F2-27，recovery.rs:620 注释指明方向）；② 触发点：`drive_run_loop` 子代理收口（core_run_commands.rs:2844-2852）在 `on_subagent_run_terminal` 前，当终态为 Failed 时还原 `RunFailureContext` 调 `on_subagent_run_failure`（recovery.rs:914）——AutoRetry → 复用拉起器重试（不消费 Episode 预算，recovery.rs:13-14）；SteeringQueued → 通知已在队列；NeedsUser → 暴露给 UI；③ 重启接线：`run_restore` 成功路径（core_run_commands.rs:2210-2227）后调 `restore_steering_notifications()`（recovery.rs:1231-1248）重排 pending 通知。
- **不做什么**：阶段内不做阶梯 3 fork（会话树装配后置，见 §4-B）；不改变 `on_subagent_terminal` 五步收口（subagent_spawner.rs:506-651 保持）。
- **依赖现有模块**：`crates/orchestrator/src/recovery.rs`（全部四阶梯+预算+RecoveryStore，2233 行现成）、`apps/agent-workbench/src-tauri/src/subagent_spawner.rs:486-660`（终态收口）、`core_run_commands.rs:2087-2101,2844-2852`（收口点）。
- **与相邻维度接口**：→ D4：`RecoveryCoordinator` 实例经 `lifecycle_service()`（core_run_commands.rs:2107-2120）暴露给 resume 命令；→ D8：`recover_needs_user`（recovery.rs:30-31）经 `core_get_status` 暴露；← D2：预算制同模式（指纹不同前缀）。
- **验收断言**：recovery.rs 既有 40+ 单测 + `tests/recovery_ladder.rs` 等 4 个集成测试在生产装配下全绿（接线回归面）；注入 2 次瞬态错误 → 阶梯 1 自动重试恢复；预算耗尽 → steering 条目 `recovery-<run_id>` 入队且落库；重启后 pending 通知重排。

### D4 子代理显式恢复命令面与 wait 持久化

- **做什么**：① `SubagentLifecycleService`（lifecycle.rs:131-349）注册 `#[tauri::command]`：`resume_subagent`（走 fork_and_reassign，recovery.rs:1031-1173，幂等 :1037-1048）+ `kill_all`（lifecycle.rs:149-224），命令清单登记 command_manifest.rs；② `MemoryWaitStore`（wait_channel.rs:104-115）换 session_meta 真适配（键形状已冻结：`dispatch_*`/`dispatch_outputs`，wait_subagents.rs:89-99,277-353）；③ 前端失败态卡片 + resume/放弃按钮（与 D8 共享 UI 面，此处只做命令接线）。
- **不做什么**：不自动 fork（编排权留主 agent，对齐「所有子 Agent 由主 Agent 分配」）；不新增 run_subagent 变体工具（守卫层不变）。
- **依赖现有模块**：`crates/orchestrator/src/lifecycle.rs:131-349`（服务本体现成）、`apps/agent-workbench/src-tauri/src/wait_channel.rs:104-115`（换后端）、`core_run_commands.rs:2107-2120`（装配点现成）。
- **与相邻维度接口**：← D3（coordinator 生命周期是 resume 的前置）；→ D8（命令清单 + UI 按钮）；resume 的 fork 新 run 走 spawn 全流程 → 自然受 12/5/1 守卫（subagent_spawner.rs:743-773）。
- **验收断言**：kill 后 resume → fork 新 run、三态上下文判定（Verbatim/Summarized/New）、Episode 预算记账、同指纹不重复 fork；重启后 wait 声明与产出清单可恢复（watchdog 判定跨重启一致）。

### D5 goal 引擎化与完成契约

- **做什么**：① `RunTaskOptions`（core_run_commands.rs:3123-3143）补齐 `visible_goal`/`max_rounds`/`max_stalled_rounds` 三字段（serde camelCase 对齐前端 ConnectionLifecycle.ts:628-631，激活已被静默丢弃的字段）；② 会话级载体 `goal_state`（JSON：goal/max_rounds/max_stalled_rounds/current_round/completed_rounds/stalled_rounds/progress_signature/stopped_reason），存 session_meta（对齐 recover_* 键先例，零新表）；③ 收口 `RoundAssessment`（纯函数，对齐 TS GoalRoundAssessmentState orchestration.ts:62-89）：输入 endReason × 本轮产出（tool_call_count/messages/runtime-error）→ needs-continuation/no-progress/completed/blocked；`allows_auto_continue`（normalize.rs:170-179）成为首个生产调用方；④ 四源判定：decide_idle_resume（:2555）三源→四源，新增 goal_pending（GoalState.active 且 current_round<max_rounds 且 reason 允许）；⑤ 续轮注入：spawn_idle_resume_run 注入「继续推进目标」前缀 + 从 compression_blocks.summary_json 提取 nextSteps/goal（blocks.rs:66-87 落库面已有，补读取面）；⑥ 事件登记 `goal-round-started/completed`、`goal-continuation-decided`（对齐 05 建议 P0）；⑦ 完成契约增强（轻量 CompletionRequirement，08 §3 P1）：任务声明必备工具，stop 收场时必备工具未调用 → 注入恢复提示词重试（独立预算，挂 RoundAssessment 同评估点，不进 goal 状态机）。
- **不做什么**：不引入 grok 全链 goal classifier（08 §4 排除项 3）；不新建 run 循环（复用 idle 续 run 拉起器）；前端 decideGoalContinuation 保留为过渡兼容，降级为投影。
- **依赖现有模块**：`core_run_commands.rs:3123-3143,2505-2593,2637-2671`、`crates/session-loop/src/loop/summary_dispatch.rs:403-408`（goal/nextSteps 字段）、`crates/orchestrator/src/blocks.rs:66-87`、`crates/orchestrator/src/normalize.rs:170-179`、`crates/session-loop/src/steering/mod.rs:48-57`（GoalAudit 占位保持不动）。

## 5. 红线与护栏清单（接线与实现全程强制）

1. **12/5/1 守卫只增不减**：maxDepth=1 / maxSiblings=5 / maxConcurrent=12（subagent.rs:497-501）；恢复路径 fork 的新 run **必须显式走 spawn 守卫**（不允许绕过 check_recursion_guard 直接启动），先释放旧 run 记账再 fork（02 缺口 7）。
2. **嵌套禁令**：恢复机制的所有触发面只在「主 agent 命令面 / 引擎守卫层」；子代理工具注册表依旧剔除 run_subagent（subagent.rs:653-659）；C7 阶梯 2 通知不携带任何自动 spawn 能力；恢复决策永远由主 agent / 系统守卫作出（02 §5.1）。
3. **用户显式停止永不自动续**：Stopped / Aborted / abort_signal / user_touched 一律不续（core_run_commands.rs:2513,2517-2519 语义保持并扩展至所有新唤醒源）；自动恢复只针对引擎判定可恢复的瞬态失败与任务未完成。
4. **连续失败上限 + 退避**：error 续 run 连续 ≤3 次（复用 resume_empty_streak 计数器模式，core_run_commands.rs:2561-2582）；每次自动重发起带退避；非 retryable error（Auth/Quota/InvalidRequest）永不续。
5. **空转护栏**：连续 N 次续 run 无 AI 产出 → 停止续 run（IDLE_RESUME_MAX_EMPTY_ROUNDS=3，core_run_commands.rs:2458,2571-2580）；watcher 拉起同样复用该计数（空注入轮不计入 streak，见 §7 决策 7）。
6. **配额红线**：探索类文档配额每会话 1 份（explore_quota.rs:8-9）不绕过——fork 沿用同一 session_id 时配额语义自动延续，新会话需在 spawn 时透传配额快照。
7. **goal 护栏**：max_rounds / max_stalled_rounds 计数持久化于 goal_state；错误收场不续（沿用 :2513 硬条件）；stalled 签名连续相同 ≥ 上限 → blocked 转人工。
8. **恢复预算制**：指纹 + Episode 上限（默认 3，可配 recover_max_episodes）；超预算禁止自动恢复（含阶梯 2 通知）直接阶梯 4（recovery.rs:956-975）；重启不重放授权。
9. **测试资产门禁**：recovery.rs 40+ 单测 + 4 集成测试文件（tests/recovery_ladder.rs 等）直接作为接线回归面；reference/markdown-editor 门禁（npm test）与主仓库 tests/e2e 5 个 markdown-editor 专项 spec 不受影响、禁止删除。
10. **性能红线**：F2-27——RecoveryStore 同步 SQLite 调用必须走 spawn_blocking（recovery.rs:620 注释指明方向），禁止在 async 内直调阻塞 tokio worker。

## 6. 分阶段实施依赖序（逻辑 DAG，不含工期）

```
D1 传输层 ──────────────┐
                        ├──→ D2 主 run error 续 run ──┐
                        │                             │
D3 C7 接线 ──→ D4 命令面/wait 持久化                    │
                        │                             │
D5 goal 引擎化 ─────────┼──→ D6 唤醒链路（四源并入收口判定）─→ D7 checkpoint 注入
                        │                             │
                        └─────────────────────────────┘
D8 观测/UI/口径：并行依赖 D3/D5 的事件面，任意阶段可局部先行（事件登记 + 口径修正）
```

- **关键路径**：D1 → D2 → D6 → D7（断网继续 → 唤醒链路 → 恢复质量）；D5 独立于 D1 可并行（仅依赖 RunTaskOptions 字段面），但 D5 的四源判定需在 D6 的 watcher 之前并入收口（否则 goal 续 run 只能靠收口命中）。
- **并行集**：{D1, D3, D5} 互相独立（不同 crate/模块域）；D4 依赖 D3；D2 依赖 D1（provider_error 字段）；D6 依赖 D5（四源）但不依赖 D2（watcher 消费的恢复条目由 D2 产生，watcher 本体可先接定时器源）。
- **D8 横切**：事件登记（recovery-*/goal-round-*）建议随 D3/D5 同步登记，不单独排期；UI 卡片与 resume 按钮依赖 D3/D4。
- **禁止反向依赖**：任何维度不得依赖尚未落地的维度（如 D3 不得依赖 D4 的命令面；D6 watcher 不得依赖 D7 的 checkpoint 注入）。
