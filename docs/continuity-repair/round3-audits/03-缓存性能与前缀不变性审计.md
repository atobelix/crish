## 2. 逐项审计(证据)

### 2.1 重试请求前缀零改动 — ✅ 符合

**约束对应**:D1 §3.1.7 R7(前缀零改动)/ R9(sleep 零改动);final/00 §9.2「重试/续写请求不改变已 commit 消息;system prompt 字节级稳定」。

**证据**:

1. 瞬态重试路径不产生新 commit:`transient_retry`(crates/session-loop/src/loop/handlers/stream_error.rs:164-234)在退避 sleep 期间只做三件事——计数 `state.transient_retries += 1`(:225,run 内瞬态字段)、发诊断事件 `emit_retry_diagnostic`(:229)、派发 `E::NoProgressContinue`(:230,重进 provider 循环)。**无消息产出、无 commit、无对话改动**。sleep 本身是 `tokio::select!` abort 竞速(:215-219),不触碰 conversation。
2. 诊断只走事件面:`emit_retry_diagnostic`(:397-422)仅 `state.events.push(AgentEvent::ProviderDiagnostic { .. })`,不进对话、不写 steering 队列、不进请求前缀(D1 §3.1.5 临时通知通道,约束 A/C)。
3. 重试 = 全新 HTTP 请求但同前缀:NoProgressContinue 重进 provider 循环,`build_request` 复用同一 `state.conversation` 快照,无重建路径(D1 §2.6 G10 修复面)。
4. system prompt 字节级稳定:`build_system_prompt`(crates/agent-provider/src/request/build.rs:123-128)是单点规范化(trim + 空值归一),同一配置字节确定;装配点 core_run_commands.rs:5241 只调用一次,全链透传原始。
5. 测试证据(Arc 身份断言,重试后消息指针不变 → 前缀字节不变):
   - `stream_error.rs:1171-1205` D1 A9(R7/R9):退避 sleep 期间与重试后对话零改动,「重试路径消息 Arc 身份不得变化(零 commit,前缀字节级一致 R7)」;
   - `tests/prefix_stability.rs:180-257` `system_prompt_stable_across_runs_same_settings`:同设置跨 run system prompt 稳定;
   - `tests/prefix_stability.rs:116-178` `two_turn_tool_loop_keeps_request_prefix_byte_stable`:工具循环请求前缀字节稳定。
6. 特例核对:length 阶梯(core_run_commands 同源,stream_error.rs:239-260)只改 `state.max_tokens`(请求体非消息面字段),对话零改动,不违反 R7。

### 2.2 续写 run(从断点继续)— ✅ 符合

**约束对应**:E1 §3.2.1 四条纪律;final/00 §9.2。

**证据**:

1. **history = 原对话 + 已 commit 部分,零改动**:
   - 收口全角色保真:`to_history_messages`(core_run_commands.rs:1293-1318)序列化全部消息(含部分保留 assistant 消息及其文本块,blocks_json 完整),run 收口处原子替换 `state.session_history.store(&session_id, to_history_messages(&outcome))`(:4293,core_run_commands.rs:4289-4293);
   - 历史源判定:`resolve_history_source`(core_run_commands.rs:1465-1473)前端 history 优先、Cache 回退;续写 run 的 `RunTaskOptions.history` 恒 None(E1 设计锁定)→ Cache 分支;
   - 缓存保真水合:`cached_history_to_conversation`(core_run_commands.rs:1423-1452)——**无尾部 user 截断**(与 hydrate.rs 的 Frontend 路径不同),全角色(含 assistant 收尾)原样映射,部分文本天然成为续写请求的 assistant 前缀。
2. **「从断点继续」追加在对话末尾(user 消息),不破坏已缓存前缀**:
   - `content_resume_decision`(core_run_commands.rs:3991-4067)构造锁定模板「上一轮生成中断({kind}),请从断点继续完成,不要重复已输出的内容」(:4045-4048)为 `SteeringInputEntry`(is_steering=true,:4055)入 pending_queue → `drain_pending_to_inject_messages`(:4062)→ 新 run 的 produce 把注入作为新 user 消息**追加在 initial_conversation 之后**(对话末尾),正是「命中前缀 + 尾部 miss」目标形态;
   - 装配链:core_run_commands.rs:5309-5316 `resolve_history_source` → Cache 分支保真水合 → `SessionLoopProducer::new(.. initial_conversation ..)`(:5325-5337)预置,注入消息追加其后。
3. **已产出内容不重复注入**:部分文本已 commit 为 assistant 消息在 history 内,模板不含已产出文本;触发判定 `last_assistant_provider_signal`(core_run_commands.rs:352-363)读消息 metadata(D7 标注,streaming.rs:116-129 部分保留断流语义:builder 非空 → error-stop 收尾,内容保留),不重复注入请求体。
4. **前缀不变性注记**:缓存分支 metadata 全裁剪 `metadata: None`(:1446)——providerErrorKind 标注是引擎判定信号,不进 wire(to_chat_messages 不读 metadata),新 run 对话无标注字段反而保证两次 run 的 wire 消息面字节一致。

### 2.6 阶段总结注入位置 — 🟡 部分(设计权衡已定,实现未落地)

**约束对应**:E2 §6.3 注入位置权衡 + §6.5 ⑤;final/00 §9.2。

**证据**:

1. **设计层已权衡(合理)**:E2 §6.3 注记「对话开头 user 消息」与「system 段」两候选都会破坏前缀缓存——但触发时(里程碑达标/恢复拉起)上下文本已超窗、缓存重建不可避免,故位置自由、无缓存差别;代价仅在于触发后新前缀是否稳定 → 阶段总结文本须稳定序列化(§6.5 ① 同纪律,避免缓存碎片)。D7 §3.2 同样权衡:checkpoint 注入仅发生在中断恢复/新 run 拉起场景(缓存必然失效),接受,正常续 run(Absent 分支)前缀零改动。
2. **实现状态:未接线(非违规,计划内)**:
   - `compact_stage_ratios` / `stage_summary` / `stage-1` / `StageSummary` 在 crates/ 与 apps/ 全库**零命中**——E2 F5 分阶段总结注入(E2 §6.3 系统提示词段拼接)尚未实现;

3. 结论:触发时缓存已失效的权衡设计合理且已文档化;实现侧待 E2 F5 接线。**接线时约束**:阶段总结文本稳定化 + 注入位置(建议 system 段)不越界。

## 4. 改进建议(缓存命中的可提升点)

1. **E2 F5 阶段总结接线时的稳定化纪律(最高优先,防未来缓存碎片)**:
   - 实现阶段总结注入前,先落地「文本稳定化」:同一阶段内容重复注入逐字节一致(与 §6.5 ① 同纪律)——建议复用 ContextInjector 静态段通道 + static_fingerprint 比对(engine.rs:2311-2325),注入段若含 range/tier 等动态字段须带 @dynamic 标记;
   - 注入位置选 system_prompt 段(E2 §6.3 主选),零对话污染;每阶梯生命周期只触发一次(次数天然 ≤ 阶梯数),避免触发后新前缀再被改写;
   - 阶段总结文本落 checkpoint 载荷(E2 §6.4)时,载荷面复用 Schema V1 冻结骨架,不另造序列化路径。

2. **C1 checkpoint 接线约束**:注入点 = system 段(非对话首条),`checkpoint_prompt_section` 已是静态 &'static str 直接可用;恢复场景注入(缓存必然失效,零代价),正常续 run 不注入(维持 Absent 分支前缀零改动,D7 §3.2)。

3. **wire 级前缀字节一致端到端断言(防回归增强)**:现有测试以「消息面 Arc 身份」(I1/I2/I3、stream_error.rs:1171-1205)与请求体纯函数(prefix_stability.rs)为主;建议在 mock provider 侧记录完整序列化请求体(含 system_prompt + messages wire 投影),补一条端到端断言:注入 Network 错误 + 长退避 → 重试请求体与首请求体逐字节一致(D1 §5.3 T19 已在验收计划中,落地时以字节比对为准)。

4. **亲和头集合编译一次(低优先)**:在 HttpProviderCall 构造时把 `affinity_http_headers(policy)` 结果缓存为成员(会话内恒等),request_headers 直接追加——消除每请求重算,并将「亲和头集合装配面固化」落到实处(D1 R8 字面)。

5. **跨 run system prompt 漂移检测(观测面增强)**:在 cache_tracker / cache_session(T-40 既有面)增加 system prompt 指纹记录,跨 run 检测 system prompt 漂移(检测不改请求)——为未来注入段接线(问题 #1/#2/#3)提供漂移告警,接线失误可被早期发现。

6. **保持现状即可的确认项**:熔断键/续写预算计数(provider_fail_streak、recover_episodes)全部走 session_meta 会话面,不落对话、不进请求前缀——审计确认无违规路径,无需改动。
