### 2.3 子 agent 失败通知 steering 🟡

- 实际文本（recovery.rs:366-375）：`"子代理 {subagent_id}（run {subagent_run_id}）停摆：网络类错误重试预算已耗尽（已重试 {retries} 次，状态 {remaining_status}）。请注入激活指令处理：继续等待 / 降低要求 / 取消。"`
- `RecoveryNotification` 字段（recovery.rs:343-358）：subagent_id / subagent_run_id / retries / remaining_status / pending —— **无 kind 字段**。
- 设计 §9.3 要求「含 kind/retries」：retries ✅（retries + remaining_status 足够 AI 判断重试强度）；kind ❌——文本只有笼统「网络类错误」字样，无法区分 rate-limit/server-error/timeout/network；具体 kind 仅经终态事件面（recovery-escalated 载荷含 kind/retries，registry_drift.rs:1058）传递，AI 对话内不可见。
- 三决策提示「继续等待 / 降低要求 / 取消」与设计三决策路径（接管 / resume_subagent 重派 / kill_subagent+重派）**不对齐**：文案是行为建议而非决策选项，且「取消」≠「关闭重来」语义。

## 3. 体验问题

### 3.1 重要级

| #   | 问题                                                                                                                                 | 影响                                                          |
| --- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------- |
| W1  | 子 agent steering 文本无具体 kind：只能看到「网络类错误」+ retries，无法区分 rate-limit（可降速等）/server-error（可重试）等决策因子 | AI 三决策（接管/重派/关闭重来）缺关键输入，只能盲猜或重复重派 |
| W2  | steering 文案「继续等待 / 降低要求 / 取消」与设计三决策路径不对齐，且是行为建议非决策指令                                            | 通知指导性弱化；AI 可能选择「等待」而非「重派」，任务滞留     |
| W3  | /compact slash 入口缺失（02 审计 F4，本审计复核确认未修）                                                                            | 用户无法手动触发压缩；core_compact_now 仍 registered=false    |

### 3.2 建议级

| #   | 问题                                                                                   | 影响                                                                                                                     |
| --- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| S1  | 「继续任务」注入无任何任务标识——若同一会话多次 error 续 run，AI 只知「继续」不知续什么 | 依赖 AI 从对话上下文自恢复；设计约束（最小化+前缀不变）下可接受，但可考虑在 steering 队列侧附加 task_text 指纹信息       |
| S2  | RetrySlotNotice maxAttempts 未下发时分母显示 0（RetrySlotNotice.tsx:16-17、41）        | 小 UI 边界：分母 0 观感突兀，建议缺省显示「重连中」                                                                      |
| S3  | 恢复条目「上次被重启打断，请继续」无任务摘要——重启后 AI 需自行从历史水合恢复任务状态   | checkpoint 摘要（≤500 字符）承载进度，恢复条目只负责唤醒，职责分离正确；但重启场景 AI 首轮产出质量依赖 checkpoint 覆盖度 |

## 4. 改进建议（具体到文案）

1. **steering 文本补 kind（W1）**：`RecoveryNotification` 增 `provider_error_kind` 字段（复用终态面 D1 数据源），文案改：
   `"子代理 {id}（run {run_id}）停摆：{kind} 错误重试预算已耗尽（已重试 {retries} 次，状态 {remaining_status}）。请决策：接管继续 / 重派（resume_subagent）/ 关闭重来（kill_subagent 后重派）。"`
2. **三决策对齐（W2）**：删除「继续等待 / 降低要求 / 取消」行为建议，替换为与设计三决策路径同名的指令式选项（接管 / 重派 / 关闭重来），并附命令面提示（resume_subagent / kill_subagent），AI 可直接执行。
3. **/compact 落地（W3，引用 02 审计 §4.1-3）**：resolveSlashCommand 登记 `/compact`（别名 /压缩 / /compress）+ useSlashSend 分支 + core_compact_now 实现体（registered=true）——按 02 审计建议方案实施，本审计不重复展开。
4. **goal 前缀微调（S1 关联）**：保持「继续任务」锁定串不变（前缀不变性硬约束），但在 error 续 run 的 steering 条目 attachment 中附任务指纹摘要（不进请求体、不破坏前缀），供前端临时通知区展示「正在继续任务：<摘要>」，解决用户侧「不知道在续什么」。
5. **RetrySlotNotice 分母缺省（S2）**：maxAttempts 为 undefined 时显示「重连中」文本替代「重试 N/0」，或不下发分母时省略分母只显示数字。
