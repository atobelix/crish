## 1. 结论先行

**设计完整度:高。生产接线完整度:子代理路径几乎为零,主 run 路径内核级已生效。**

分两句话说:

- **设计端(C7)**:四级阶梯机制完整、边界清晰、测试充分。`recovery.rs` 实现了阶梯 1 自动重试(ladder1_decision,镜像 agent-provider retry.rs 语义)、阶梯 2 主 agent 激活(steering 软注入 + 通知落库)、阶梯 3 fork 重分配(会话树 fork + 三态上下文继承 + spawner)、阶梯 4 上报用户(尝试明细聚合 + 需介入标记);恢复预算制(操作指纹 + Episode 预算默认 3);全链路持久化(`recover_*` 5 键 + events 表 `recovery-*` 事件 + steering 队列条目);重启恢复(`restore_steering_notifications` 重排 pending 通知)。测试覆盖:recovery.rs 内 40+ 单测(决策表/退避/预算/fork 三态/幂等/重启) + 4 个集成测试文件(`tests/recovery_ladder.rs`、`multi_agent.rs`、`kill_all.rs`、`crash_consistency.rs`)。
- **生产端(接线)**:F2-08 属实——`RecoveryCoordinator` 在 `apps/agent-workbench/src-tauri`(生产壳层)与 `crates/session-loop`(循环内核)**零构造、零调用**;`on_subagent_run_failure` 无任何生产调用方;`fork_and_reassign` 仅测试与 lifecycle resume 命令面消费,而 resume 命令面没有 Tauri/IPC 注册、前端无入口。引擎侧连 `SessionTree`(阶梯 3 依赖)都未装配。**当前生产二进制里,子代理网络中断不会触发 C7 的任何一级**。

**那么用户关心的「agent 任务连续性」现在靠什么?** 三块已生产的机制在兜底,但都不是 C7:

1. **session-loop 内核恢复阶梯(主 run + 子代理 run 共用,已生效)**:`stream_error.rs` 对瞬态 provider 错误重试上限 3(默认)+ length 阶梯 + 溢出压缩阶梯,用尽才 fatal 收场——这是"阶梯 1 的进程内版本",但**无预算、无留痕、无跨重启**。
2. **主 agent idle 续 run / steering 唤醒(T-CF-11,已生效)**:主 agent run 正常收场后,若跨 run steering 队列/定时器/Cron 有唤醒源,自动拉起新一轮 run(`decide_idle_resume` / `spawn_idle_resume_run`,core_run_commands.rs:2505-2671)。子代理终态通知(subagent-ended)也经此通道送达主 agent——这是当前"系统调度让 agent 继续"的主干。
3. **重启一致性恢复(restore.rs,已生效)**:冷启动把 in-flight run 打断为 interrupted(failed/cancelled)、会话树/事件流/pending 输入快照重建。语义是**状态一致性,不是续跑**。

### 2.1 各阶梯机制细节与预算

- **阶梯 1**(recovery.rs:113-243):`RecoveryRetryPolicy` 默认 `max_retries=0`(显式开启才重试,与 retry.rs 同语义)、base 750ms、max 8s、总预算 60s。`is_transient_kind` 镜像 retry.rs 可重试集:RateLimit/ServerError/Timeout/Network;Auth/Quota/ContextLengthExceeded 等不上行到本阶梯。`ladder1_decision` 顺序:已产出内容 → Escalate(ContentProduced)→ 非瞬态 → Escalate(NonTransient)→ 次数超限 → Escalate(RetriesExhausted)→ 预算耗尽 → Escalate(BudgetExhausted)→ 否则 Retry(attempt/delay/剩余预算)。重试不计入 run 失败、不留痕(测试断言 recovery.rs:1801-1803)。
- **阶梯 2**(recovery.rs:338-387, 982-1021):`escalate` 构造 `RecoveryNotification`(pending=true)→ `queue.replace_or_enqueue`(同 run 分组原位替换,不重复堆积)→ 通知落库 `recover_notifications`(JSON 数组,幂等替换同 run 旧记录)→ 事件留痕 `recovery-escalated` + `recovery-steering`。主 agent 经 L1 steer 环消费:条目转用户消息(`transfer_follow_up`,带 `{kind:"steering"}` 元数据,steering_queue.rs:89-106),在 run idle/下一条用户消息边界注入——该消费通道生产已通(T-CF-11 是现成消费者)。
- **阶梯 3**(recovery.rs:389-475, 1031-1173):`fork_and_reassign` 幂等(同指纹同源已 fork → 返回既有记录不重复 spawn);预算检查;`SessionTree::fork(from_leaf, new_leaf, payload)` 派生新叶子;`decide_fork_context` 三态:注入 0 字节 → New;≤24h 窗口且 ≤ 窗口 80% → Verbatim(字节级继承);超窗/超占比 → Summarized(C9 摘要位,摘要实装归 M10 之前以 context_normalized 记录);`spawner.spawn` 新 run(SubagentSpawnRequest 全扩展位显式 None,recovery.rs:1115-1135);新 run 行落 `subagent_path_json`;原 run `update_run_status(failed, "recovery-fork")`;`budget.record_fork` + 落 `recover_forks` + `recover_episodes`;事件 `recovery-fork`。spawn 失败结构化上抛且**不消费预算**(recovery.rs:2225-2231)。
- **阶梯 4**(recovery.rs:477-585, 1180-1209):`report_to_user` 从持久化的阶梯 2 通知与阶梯 3 fork 记录聚合同指纹尝试明细(AttemptRecord 含阶梯/时间/详情),附固定建议文案;run id 记入 `recover_needs_user`(JSON 数组,UI 可观察位);事件 `recovery-report`;预算耗尽拒绝另有 `recovery-budget-denied` 事件 + G10 全局 denied 月度统计(conex_types::denied_stats,recovery.rs:972-973)。
- **恢复预算制**(recovery.rs:245-336):`fingerprint(subagent_id, task)` = FNV-1a 64 十六进制;`RecoveryBudget` 上限默认 3,可配 session_meta 键 `recover_max_episodes`;计数落 `recover_episodes`;`can_recover` 为超预算时**禁止自动恢复(含阶梯 2 通知),直接阶梯 4**(recovery.rs:956-975);重启 `from_json` 宽容解析(fail-open),**不重放授权**。
- **持久化键总表**(recovery.rs:80-97):`recover_max_episodes` / `recover_episodes` / `recover_notifications` / `recover_forks` / `recover_needs_user`,独占 `recover_*` 键命名空间。`RecoveryStore`(recovery.rs:594-702)为 conex-db 只读抽象,`impl RecoveryStore for LocalDb` 全经既有接口(get/set_session_meta、reserve_sequence + append_event、update_run_status、update_session_agent_path),零新增表结构。

### 2.2 生产接线逐项核实(关键)

**① 引擎侧有没有调用 on_subagent_run_failure?→ 没有。**
在整个 `apps/agent-workbench/src-tauri/src`(生产壳层)搜索 `on_subagent_run_failure` / `RecoveryCoordinator` / `RecoveryStore` / `recover_` / `fork_and_reassign` / `restore_steering_notifications`:**0 处**。`RecoveryCoordinator` 仅存在于 `crates/orchestrator` 自身(实现 + 4 个集成测试文件)。recovery.rs:57-62 模块注释自述:「上述引擎侧接线点当前无调用方——子代理 run 失败时生产二进制不触发阶梯 1/2(仅 tests 与 lifecycle resume 命令面消费)…属 I6 遗留 L1–L3 大件,另行排期,不硬接」。F2 审计独立确认:docs/organization/audit/F2-orchestrator-db-audit.md:39(F2-08)。

**② 主 agent 处理阶梯 2 通知的路径通不通?→ 通道通,但没有生产者。**

## 4. 缺口与风险

**4.1 子代理网络中断的实际现状(无 C7 时)**

一次子代理 provider 网络中断的完整现行路径:session-loop 内核瞬态重试 ×3(进程内,无预算/无留痕)→ fatal → run failed → `on_subagent_run_terminal`(core_run_commands.rs:2087-2101)→ subagent-ended 广播 + steering 通知入队(subagent_spawner.rs:571-599)→ 主 agent 下一轮被 idle 续 run 拉起,读到「子代理已结束(失败)」→ 主 agent 决策:手动重新 spawn_subagent。**相当于裸的「阶梯 4 前身」**:有通知、有主 agent 人肉决策,无自动重试(阶梯 1 只有内核 3 次,无预算制)、无软注入主动唤醒(靠终态通知)、无 fork 语义(重派是全新 run,无上下文继承/无预算共用)、无恢复轨迹(recover_* 不存在)。

**4.2 重启场景**:**in-flight run 一律打断为 failed**(含 completing,11-T4),blocked/终态保真,Unknown 透传(restore.rs:575-633,780-794);session_agents 残留 running 归一 failed(restore.rs:642-676,防 FlowScheduler 永久卡死)。重启后主 agent 的旧 run 不会自动续跑——用户消息仍在,但「继续」只能用户发起;子代理 run 同理。这是与「用户关心的任务连续性」最直接的落差:**崩溃/重启本身会把一切进行中的代理工作清零为 failed,系统只保证状态一致,不保证任务继续**。

**4.3 主 run(主 agent)中断现状**:内核有瞬态重试(默认 3,`transient_retry_limit` 可配)与 length/压缩阶梯;用尽即 fatal(stream_error.rs:237-269)。idle 续 run 硬条件排除错误收场(decide_idle_resume:2513 `reason != AgentEndReason::Stop` → 不续),所以 fatal 后无自动拉扯;用户 L1 重新发消息才重启。无 steering 侧主动通知「主 run 因网络停摆」(没有一个「主 run 的 recovery 通知」概念),也无 fork/上报。

**4.4 风险排序**:

1. **子代理任务无痕中断**(G1+G7):网络波动时子代理白跑/重复劳动,主 agent 按其经验重新派发可能重复执行副作用(写文件/审批),无预算护栏。
2. **重启清零**(G10):daemon 重启(升级/崩溃/手动)打断长任务,无续跑。对「无人值守派发了一批子代理后关灯走人」场景是体验断点。
3. **恢复动作不幂等/无观测**(G3+G4):即使接线,若预算/通知不跨重启恢复,会出现重复 fork(依赖 G3 装配正确)。
4. **F2-27 阻塞风险**:直接接线而不 spawn_blocking,SQLite 同步调用阻塞 tokio worker,反噬 run 循环本身。
5. **resume/fork 无入口**(G5+G6):即使引擎侧接好,主 agent 也没有命令面发起 fork;UI 无按钮。

## 5. 建议:把 C7 接上生产(按落地顺序)

### 阶段 A:最小接线(让阶梯 1+2 生产生效)——核心改动 3 处

1. **A1:每会话 RecoveryCoordinator 生命周期**(G3)。装配点:`CoreRunState::new`(core_run_commands.rs:1474-1600 一线,与 `finalize_subagent_spawner` :1605 同批)新增 `HashMap<session_id, Mutex<Option<RecoveryCoordinator>>>` + 会话首次出现时惰性构造(`RecoveryCoordinator::new`);依赖注入:`store = LocalDb`(RecoveryStore impl 已有)、`queue = engine.timer_steering_queue()`(engine.rs:1413 已接)、`spawner = SubagentSpawnerImpl`(已装配)、`tree` 需补(见 A3)。**F2-27 起点**:coordinator 的持久化调用在收口路径经 `tokio::task::spawn_blocking` 包裹(RecoveryStore 保持同步 trait,recovery.rs:620 注释已指明此方向)。
2. **A2:阶梯 1+2 触发点**(G1+G7)。最自然插槽 = `drive_run_loop` 子代理收口(core_run_commands.rs:2844-2852):在 `on_subagent_run_terminal` 之前,当 `active.subagent` 为 Some 且终态为 Failed 时,从 RunOutcome/run 终态错误(runtime-error 事件文案含 `ProviderErrorKind`,stream_error.rs:252-262;RunOutcome.reason=Error)还原 `RunFailureContext`(error_kind/retries=内核 transient_retries 计数需从 LoopState 透出——建议在 RunOutcome 增加 `provider_error: Option<ClassifiedStreamError>` 字段,由 fatal_provider_error 填充,这是本阶段唯一需要动 session-loop 的点),调 `on_subagent_run_failure`:
   - `AutoRetry` → 用 `spawn_idle_resume_run` 同款拉起器复用 run 装配拉起重试 run(注意不消费 Episode 预算、不计入 run 失败——recovery.rs:14);
   - `SteeringQueued` → 无需额外动作(条目已在队列,主 agent 下轮收到);
   - `NeedsUser` → 暴露给 UI(阶段 C)。
3. **A3:重启接线**。`CoreRunState::run_restore` 成功路径(core_run_commands.rs:2210-2227)之后、`seed_sequences` 同批:对每个已知会话构造/重建 coordinator 并调 `restore_steering_notifications()`(recovery.rs:1231-1248),pending 通知重排入队;预算/forks/needs_user 随 `new()` 自动从 session_meta 恢复。**SessionTree 装配(G5 前半)**:恢复时以 `RestoreOutcome.sessions` 的 SessionRecord 分支重建会话树(restore.rs:678-694 已组装 SessionRecord,含 branches/current_leaf_id),挂到 coordinator 的 `tree`。fork 的 from_leaf_id 在阶段 B 前可退化为「无叶子则拒绝 fork」的受控路径(recovery.rs:1066-1070 已有结构化拒绝)。

### 阶段 B:resume 命令面 + 阶梯 3(fork)手动入口(G5 后半 + G6)

### 主 run 恢复能力增强建议(与 C7 并列,优先级 P1)

7. **主 run「重启续跑」**(G10,价值最高、改动最小):restore 的 `interrupted` 列表(restore.rs:600-632 已有 run_id + previous_status)在 `run_restore` 成功后,对**主会话**的 interrupted run 经 idle 续 run 拉起器(spawn_idle_resume_run,core_run_commands.rs:2637-2671)注入一条「上次 run 被重启打断(daemon-restarted),请继续未完成的工作」用户消息——pending_inputs 恢复(FIFO,restore.rs:747-751)本就在队列,续 run 自然消费。恢复预算面:主 run 可复用 C7 的 session_meta `recover_episodes` 做同款 Budget 护栏(半自动重发起,防风暴)。
8. **主 run provider 中断的半自动续跑**(G9):`decide_idle_resume` 的硬条件扩展——reason=Error 且 `runtime-error` 为瞬态类(ProviderErrorKind ∈ 可重试集)且预算内时,允许经「恢复注入」(区别于正常 idle 续 run)自动重发起一次(上限 1 次,N 分钟内),并留 `recovery-*` 事件;超限则交用户。这等价于把 C7 阶梯 1 的对象从「子代理」推广到「主 run」,预算键同 namespace 不同指纹前缀。
9. **主 run 阶梯 2**(选做):「主 run 停摆通知」可经现成 steering 通道写回自身会话的 followUp(recovery 通知语义复用 `recover_notifications`),下次用户消息边界主 agent 自述「我上次因网络中断,建议继续/降级」——这是把 C7 的「主 agent 激活」搬给用户侧的最小实现。优先级低于 7/8。
