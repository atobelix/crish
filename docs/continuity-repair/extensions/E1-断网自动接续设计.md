## 0. 结论速览

1. **三级自动接续定义**:① 传输级重连(同请求重发,未产出时,现状 + D1 硬化后已完整覆盖);② **内容级续接**(已产出部分文本后断流 → 自动发起「续写 run」,以历史中的部分文本为上下文,追加「从断点继续」指令,请求模型完成剩余部分)——**本次新增的核心**;③ 会话级续接(D2 error 续 run 现有通道,降级路径)。
2. **关键事实基础**:部分保留断流(已产出内容 + 流错误)的收场是 **reason=Stop 的正常收场**(streaming.rs:149 → Message → no_tool_calls → EndDecision::stop),**RunOutcome 无 provider_error**——D2 error 续 run 通道对该场景**不可达**;今日行为 = 半截回答保留、无人自动接续(04 G6)。这恰是本次补充需求的落点。
3. **触发信号**:D7 流中断结构化标注落地的 `metadata.providerErrorKind ∈ 瞬态四类`(与 D1 熔断 S2 计数**同一数据源**,core_run_commands.rs:2718 前可读)。
4. **续写请求构造**:部分文本已在会话历史中(收口 SessionHistoryCache 保真存储 + resolve_history_source Cache 分支水合),**无需把已产出文本重复注入请求体**;续写 run 经拉起器注入「从断点继续」指令即可。通用构造(完整对话 + assistant 前缀 + 续写指令)对 chat/responses 双轨全厂商可用,零协议级依赖(04 P3-2 已证协议级续传不存在)。
5. **与「已产出不重试」纪律的关系**:**叠加**非替代——内核三层语义(streaming.rs:117 / retry.rs:412-428 / recovery.rs:205-217)零触碰;续接在 run 粒度、壳层执行。
6. **护栏**:续写次数上限默认 2(指纹域独立,激活 D2 W8 前瞻)、熔断闸、abort 竞速、预算封顶、用户意志优先、失败自然降级 ③。

## 1. 「自动接续」的定义与分级

### 1.1 三级定义

| 级 | 名称 | 机制 | 触发 | 现状 | 属主 |
|---|---|---|---|---|---|
| ① | 传输级重连 | 同请求重发(流未产出任何事件) | 流前/流中未产出错误 | **已覆盖**(transient_retry 立即重试 ×3);D1 硬化后 = 退避 750→8s / 60s 预算 / Retry-After / 熔断闸 | D1(已设计) |
| ② | **内容级续接(自动续写)** | 发起新一轮「续写 run」:部分文本在历史中(assistant 消息),注入「从断点继续」指令,模型完成剩余部分 | 已产出部分文本后断流(部分保留收场) | **缺口**(04 G6 无续传;收场 Stop 后无自动动作) | **本扩展(E1)** |
| ③ | 会话级续接 | error 续 run:注入「上一轮 provider 中断(<kind>),继续任务」→ 新 run 继续任务 | run 以 Error 收场(provider_error retryable) | 已设计(D2),未实现 | D2 |

**分级语义(用户诉求对齐)**:「断网自动接续」= ①+② 组合——① 吸收秒级瞬时抖动(未产出),② 吸收「产出到一半断网」(已产出)。② 失败或不可用 → 自然降级 ③(「走正常的接续流程」)。三级构成完整断网不丢任务链:run 内(①)→ run 间(②/③)→ 会话级(③ 预算耗尽后停止自动动作,半截保留,交用户)。

### 1.2 现状事实与缺口(证据)

### 1.3 与 04 P3-2「不建议续写」的冲突标注

04 §4.5 与 P3-2 曾表述:「不建议把已产出文本注入重试请求(语义污染 + token 浪费)」。本设计**不冲突**:

- 04 P3-2 反对的是「协议级断点续传 / 把已产出文本塞回**同一请求**」(重试语义),其正确性顾虑已被「已产出不重试」三层纪律吸收;
- ② 是「**新 run 新请求**」,部分文本经历史水合自然携带,不重复注入请求体(见 §3.2 构造),token 成本 = 一轮普通请求,受次数上限封顶;
- 04 自身的 P2-1「部分中断后的恢复决策面」正是「主 agent 经阶梯 2/4 决策补发」的方向,② 是它的自动化形态(系统代主 agent 决策「续写」),而非推翻。

### 1.4 「自动接续」可行性结论(任务书问题逐条回答)

| 问题 | 结论 | 依据 |
|---|---|---|
| 续写请求的构造:已产出文本如何注入 | **历史即载体,不重复注入**:部分文本已作为 assistant 消息 commit 进会话,收口经 SessionHistoryCache 保真存储(:2718),续写 run 经 resolve_history_source Cache 分支(:1088-1096)水合后对话天然包含该文本;拉起器注入文本只需「从断点继续 + 不要重复」指令 | §3.2 |

| 哪些 provider 支持 | **通用构造,全厂商可用**:chat-completions 与 responses 双轨(engine.rs:381-391)均支持任意 user/assistant 交错消息;续写请求与普通请求形状完全相同,零厂商专用接口 | engine.rs:381-391;04 P3-2 |

| 重复输出风险与防重复 | 三层:① 注入指令显式「不要重复已输出内容」;② 状态层零重复(消息只 append 不覆盖,部分文本在会话中恰好一份);③ 验收断言锁定前缀重叠检测 | §3.4、§4 A3 |

| 配置开关 | **默认开启**(与用户诉求「断网自动接续最好」一致),可关;`content_resume_enabled` session_meta 键 | §3.4 |

## 2. 触发条件

### 2.1 判定矩阵(收口判定顺序)

```
run 收口(drive_run_loop 收口区,core_run_commands.rs:2701-2733)
├─ reason == Error(provider_error 存在)
│   └─ retryable && !熔断 && 预算内 → ③ 会话级续接(D2 既有,本扩展不触碰)
├─ reason == Stop 且最后一条 assistant 消息为纯文本(无 tool_calls)
│   └─ metadata.providerErrorKind ∈ {rate-limit, server-error, timeout, network}
│       (瞬态四类,即 D7 流中断标注)且 providerErrorRetryable != false
│       → ② 内容级续接(本扩展新分支)
└─ 其余(正常 Stop / 非瞬态标注 / 用户停止 / abort)
    → 现有三源判定路径(00 §3.1),零改动
```

### 2.2 ② 的触发条件(全部满足)

| # | 条件 | 证据/来源 |
|---|---|---|
| T1 | 收场 `reason == Stop`(部分保留断流收场形态) | streaming.rs:149、:199;no_tool_calls.rs:62-63 |
| T2 | 最后一条 assistant 消息 metadata 含 `providerErrorKind` 且为瞬态四类、`providerErrorRetryable != false`(D7 标注,与 D1 熔断 S2 计数同源判定) | D7 §3.7;D1 §3.2.2 落点 2 |
| T3 | 该消息为**纯文本消息**(无 tool_calls)——工具调用已完整解析并提交,断流发生在工具调用之后时 run 已进工具执行分支,无需续写 | streaming.rs:197-208;consume/mod.rs:254-255 |
| T4 | `!user_touched && !abort_signal.is_aborted()`(decide_idle_resume 既有硬条件) | core_run_commands.rs:2511-2519 |
| T5 | 熔断未触发(`circuit_breaker_is_tripped == false`,D1 提供) | D1 §3.2.4 |
| T6 | 续写预算内(指纹域 `content-resume` 计数 < 上限,默认 2) | §3.4 |
| T7 | `content_resume_enabled == true`(默认) | §3.4 |
| T8 | 部分文本非空(消息 text 长度 ≥ 1 字符)——理论上已由「有内容才保留」保证 | consume/mod.rs:233 |

### 2.3 ② 不触发(保持现状)的情形

| 情形 | 处理 | 依据 |
|---|---|---|
| 非瞬态 kind(Auth/Quota/InvalidRequest/ContextLengthExceeded/PayloadTooLarge/Unknown/Aborted 等) | 半截保留 + 无自动动作,交用户 | 验收基线 2「非瞬态错误不自动续」(00 §1.2) |
| `ConsumeStopReason::Length`(length 截断) | 不续写——length 阶梯语义在流内已处理(no_tool_calls.rs:27-51),length 截断是正常收场,不视为中断 | no_tool_calls.rs:5-11、:52 |
| 消息含 tool_calls(工具调用部分保留) | 不续写——工具调用已提交,断流发生在收尾;run 内工具执行路径正常继续 | §2.2 T3 |

## 3. 接线设计

### 3.1 位置裁决:壳层 decide_idle_resume,不触碰内核

| 候选位置 | 结论 | 理由 |
|---|---|---|
| 内核 stream_error.rs / streaming.rs(续写分支) | **否** | ① 内核无 session_meta 面(预算/配置不可达,02 §2-E「为什么不放内核」同款);② 续写 = 新 run,内核无拉起能力;③ 内核「已产出不重试」语义冻结,续写若放流内会破坏「每流恰好一个 Stop / 内容保留」不变量(streaming.rs:116-129) |
| 内核 consume 层 | **否** | consume 是纯聚合函数(finish),无 run 生命周期概念;部分保留判定在 streaming.rs 已二分完毕 |
| **壳层 decide_idle_resume(Stop 分支新增子分支)** | **是** | ① 信号(收口 metadata)在壳层可见(core_run_commands.rs:2718 前);② 预算/熔断/退避/拉起器全部在壳层(D2 同区);③ 与 D2 error 分支同函数,硬条件(abort/user_touched)免费复用;④ 不触碰内核冻结语义 |
| 壳层收口直发(spawn 不经 decide_idle_resume) | 否 | 会绕过 abort/user_touched/熔断/预算判定链,与 D2 「判定顺序」结构不一致,且失去拉起器单点语义(00 §3.1 单一机制) |

### 3.2 续写请求构造(核心设计)

**不需要重复注入已产出文本**。数据流:

```
部分保留断流 run 1(内核,零改动)
  → 消息 commit(部分文本 + providerError/ providerErrorKind 标注)
  → 收口:session_history.store(:2718,全角色保真,含部分消息)
  → 收口判定:最后消息 metadata.providerErrorKind 瞬态四类(S2 同源)
  → decide_idle_resume Stop 分支续写子分支:
      预算消费 → 退避 → 构造续写条目(steering 条目,注入文本) → 入队 → drain
  → spawn_idle_resume_run(mode="content-resume",subagent_config=None,:2660-2661)
  → 新 run 装配:resolve_history_source(:1088-1096)回退 SessionHistoryCache
      → 对话水合含 run 1 部分文本(assistant 消息)+ 注入文本(user 消息)
  → 续写请求 = 完整对话 + 「从断点继续」指令(与普通请求形状相同,零厂商差异)
```

**注入文本(锁定模板,C8 风格,测试断言绑定)**:

```
format!("上一轮生成中断({kind}),请从断点继续完成,不要重复已输出的内容")
// kind 人读化映射复用 stream_error.rs:305-321 kind_str
```

**为什么「历史即载体」成立(三证据)**:

1. 收口缓存全角色保真:to_history_messages 序列化全部消息(含部分保留消息与其文本块),`session_history.store`(core_run_commands.rs:2718);
2. 续写 run 的 history 装配回退缓存:RunTaskOptions.history 恒 None(spawn_idle_resume_run 构造,core_run_commands.rs:2657)→ resolve_history_source Cache 分支(core_run_commands.rs:1088-1096)→ cached_history_to_conversation 水合(含文本块,hydrate.rs:36 起);
3. 部分文本作为 assistant 消息存在于对话中 → 续写请求里它天然是「assistant 前缀」——与任务书设想的「完整对话 + assistant 前缀 + 请求续写」形态**逐字等价**,只是前缀来自历史而非显式注入。

**P2 可后置项(本轮不做)**:协议级续写(Anthropic `continue_final_message` 类「在同一 assistant 消息上追加」)——需厂商专用字段,非通用构造,与「零协议依赖」目标冲突;本轮续写产出为**新 assistant 消息**(两段式),展示层合并归前端后续项。

### 3.3 与 RunOutcome.provider_error 的关系

| 面 | ② 内容级续接 | ③ 会话级续接 |
|---|---|---|
| 收场形态 | reason=Stop,provider_error=None | reason=Error,provider_error=Some(retryable) |
| 触发数据 | 最后消息 metadata.providerErrorKind(消息面) | RunOutcome.provider_error(收场数据面,D1) |
| 两数据源 | 互斥(部分保留断流不 fatal、fatal 无内容) | 同上 |
| 熔断消费 | is_tripped 判定(同 ③) | is_tripped 判定(既有) |
| 预算域 | `content-resume`(新) | `error-retry`(既有) |

**收口提取点**:`drive_run_loop` 在 outcome 移动消费前(:2710-2712 同批,对齐 D1 §3.4 提取点)增加「最后一条 assistant 消息 + metadata」判定——判定所需信息在 to_history_messages 前已在手(outcome.messages,core_run_commands.rs:2718 同点,与 D1 S2 落点 2 判定并列)。

### 3.4 预算、max_tokens 与护栏

**预算(指纹域独立,激活 D2 W8 前瞻设计)**:

- 域:`fingerprint_with_source("main", 任务文本, "content-resume")`(D2 §3.3 三参指纹;任务文本取法 = D2 的 main_task_text,会话首条非 steering user 消息);
- 载体:`recover_episodes` 键(recovery.rs:86)同键同形状,与 `error-retry` / 子代理两参指纹域互斥,读-改-写安全由会话串行守卫保证(core_run_commands.rs:3208-3216);
- 上限:`content_resume_max` session_meta 键,u32,**默认 2**(比 error-retry 的 3 更紧——续写是「质量增强」而非「任务救急」,且每次续写都是完整请求);
- 消费语义:每次续写 run 拉起前消费一次(对齐 D2 D2-3 决策:判定时消费,拉起失败不重复消费,条目滞留由 watcher 兜底);
- 超限 → 不续写 + `recovery-budget-denied` 事件留痕(W6 双发射方语义,主 run 侧 subagentRunId=None)。

**max_tokens 预算**:

- 续写 run 是全新 run,`state.max_tokens` = 常规默认(DEFAULT_MAX_TOKENS,loop/mod.rs 常量,8192)——剩余回答可能很长,不主动缩小;

### 3.5 降级链(② → ③ → 用户)

```
断流(部分产出) → ② 续写 run 1
  ├─ 续写成功(正常 Stop) → 完成,链路闭合
  ├─ 续写 run 自身 Error 收场(provider_error retryable)
  │     → ③ 会话级续接(该 run 的收口自然落入 D2 error 分支)
  │     └─ ③ 预算耗尽 → 停止自动动作,半截保留,上报(现状语义)
  └─ 续写 run 自身再次部分断流(metadata 瞬态标注)
        → ② 再次触发(预算内)→ 预算耗尽 → 停止自动动作,半截保留
```

**关键语义**:

- **降级是天然发生的,无需显式跳转**:续写 run 是新 run,它自己的收口走同一 decide_idle_resume 判定链;Error 收场 → ③;部分断流 → ②(预算内);
- **② 预算耗尽后不再自动续**:与 ③ 预算耗尽同语义(半截保留、交用户),不额外打开「error-retry 域」救场——两个域职责独立,互不挪用(与 D2 指纹隔离语义一致);
- **用户手动路径不受限**:用户看到半截回答后可手动重发/继续(手动路径不查熔断、不查预算,D1 规则 C4 语义保持)。
