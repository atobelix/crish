# 07 后台任务与自动续跑能力(软调度域 · 定时器 / 注入 / 会话恢复审计)

> 域:后台任务 / 定时器 / 注入调度 / 事件总线 / 会话恢复。分析日期:2026-08-10。
> 方法:全量读 `crates/agent-tools/src/tools/background_task.rs`、`background.rs`、`streaming.rs`、`tools/set_timer.rs`、`subagent_inject.rs`、`context.rs`;`crates/session-loop/src/control.rs`、`input.rs`、`safe_point.rs`、`hooks.rs`、`hydrate.rs`、`checkpoint.rs`;`crates/orchestrator/src/session.rs`、`steering_queue.rs`、`restore.rs`;`apps/agent-workbench/src-tauri/src` 的 `core_run_commands.rs`(T-CF-11 idle 续 run)、`timers.rs`、`sched.rs`、`watchdog.rs`、`wakeup_summary.rs`、`engine.rs` 装配面、`main.rs` 命令注册面;前端 crish-desktop / agent-workbench 的继续/停止/恢复用户侧语义(简查)。

## 1. 结论先行

**「agent 没被停就能一直工作」的软调度主干已存在且生产已接线:T-CF-11 idle 待命续 run 是唯一完整的「系统自动让 agent 继续」链路;定时器/Cron/watchdog/子代理完成/后台任务终态五类唤醒源汇聚到同一个跨 run steering 队列,由 run 收口消费并自动拉起新一轮。但这条链有三个真实断点:**

1. **定时器持久化未接线**:`TimerRegistry` 生产装配用 `MemoryTimerStore`(engine.rs:1112),重启即丢——「无人值守」跨重启断链(对比:Cron 同为内存 store,同病)。
2. **「AI 已休眠 + 唤醒事件后到」断链**:`decide_idle_resume` 只在 run 收口处判定(core_run_commands.rs:2872)。若收口时三源全空(AI 休眠),之后定时器/Cron 到期只入队**没有消费方**——没有「队列非空 → 主动拉起 run」的独立 watcher(watchdog 只管子代理 dispatch 声明,watchdog.rs:240-242)。理想链路「定时器唤醒→消息入队→run 重启」的最后一跳缺失。
3. **重启恢复只保一致性不保续跑**:restore 把 in-flight run 一律打断为 interrupted 终态(restore.rs:51-55),无自动恢复消费端;`resume_subagent` 命令面无 IPC 注册(doc 03 G6 已登记);主 run 无任何 resume 命令——用户重开软件后只能手动重发。

**其余关键事实**:
- 后台任务机制是**进程级托管**(shell_command 转后台的 OS 进程),**不是 agent run 的挂后台续跑**;run 是 drive_run_loop 一次性 produce 的进程内循环,收口即终态(core_run_commands.rs:2701-2703)。run 终态**不清理、不级联杀**后台任务(T-AB-19,core_run_commands.rs:2830-2838),任务与子代理完成后经 steering 条目唤醒主 agent——这才是「run 结束后还能继续工作」的既有形态。
- 三环输入(force/steer/followUp)是 **run 运行期**输入通道;「run 结束后再启动」不走三环,走跨 run steering 队列 + 收口续 run。
- checkpoint(C1)已有采集/落库/读取三件套(safe_point.rs:255-278、session.rs:514-574),但**恢复消费是提示词协议层**(AI 自己读历史),机制面无「检查点自动注入续 run」。

## 2. 各机制现状(文件:行号证据)

### 2.1 后台任务机制:进程托管,不是 agent 续跑

| 面 | 现状 | 证据 |
|---|---|---|
| 工具面 | `background_task` 五 action(list/status/read_log/send_input/kill),经 `ToolContext.background` 访问 manager;未接线返回 common.unsupported 结构化错误 | `tools/background_task.rs:41-139`、`:121-126` |
| 契约面 | `BackgroundTaskManager` trait(adopt/list/status/read_log/send_input/kill);`is_daemon=true` = 模式 3「run 结束不回收」;`owner_run_id` 审计关联**不级联杀** | `background.rs:29-52`、`:61-67` |
| 注入面 | 会话级装配 `ToolContext.background`(None = 未接线);子代理执行上下文同一注入模式 | `context.rs:118-121` |
| 生命周期 | run 终态只清 `owner_run_id` 注入槽,注册表不清理、任务不级联杀;守护任务与普通任务 run 后均持续运行 | `core_run_commands.rs:2830-2838` |
| 唤醒面 | 后台任务终态 → `TaskEventConsumer` → steering 条目(group_id=`task-wake`,is_steering 受保护)→ 共享队列 → 主 agent 收口续 run | `task_event_consumer.rs:86-198`、`background.rs:5054` |

**回答 Q1**:agent 的 run 结束后**不能**「挂后台继续」——run 是进程内一次性驱动循环;能跨 run 存活的是:① 后台 OS 进程(background_task 托管),② 跨 run steering 队列条目,③ 会话历史缓存(SessionHistoryCache,core_run_commands.rs:2714-2718 收口写入)。「继续」的现有形态 = 任务/子代理完成事件入队 → 主 agent 收口自动续 run。子 agent 上 background_task 与主 agent 完全同构(同一会话级 manager),子 agent run 结束后其托管的 shell 进程继续运行,终态经 task-wake 条目唤醒主 agent。

### 2.2 定时器:能注入消息,但只在「有 run 收口」时生效

触发链(timers.rs):
```
set_timer(durationSeconds, prompt, timerCondition)          tools/set_timer.rs:216-253
  → TimerRegistry::register(校验1~86400 → 冲突表 → 落库 timer_<id> → early_exit 登记 → spawn fire 任务)
                                                           timers.rs:339-409
  → spawn_fire_task:10ms 粒度轮询 now() >= expires_at_ms 即 fire   timers.rs:626-654
  → fire_timer:发射 TimerFired(Critical) + steering 条目入队
    (group_id=timer-<id>, text="<prompt>(定时器 <id> 已到期)") + 标 fired 落库   timers.rs:663-713
  → PendingMessageQueue(timers.rs:152-166 QueuePendingSink)
  → 消费方:T-CF-11 idle 续 run(见 2.4)
```
早退条件(TimerCondition):never / any / <task-id>,`on_event` 旁路判定(timers.rs:526-572)。重启恢复 `restore()` 扫描已持久化声明重建 sleep、补发已到期未注入(timers.rs:458-518)——**但生产 store 是 `MemoryTimerStore::shared()`(engine.rs:1112),重启即空,restore 实际无事可做**;conex-db session_meta 真适配登记 R-CF3 未接线(timers.rs:26-28、engine.rs:1095-1098)。

**回答 Q2**:set_timer **能**在未来时刻把消息注入给主 agent——但「注入」的落点是 steering 队列,**真正唤醒(拉起新 run)依赖某次 run 收口判定**。触发后的执行链见上;若 AI 已休眠(最后一次收口三源全空),到期条目在队列滞留,**没有独立触发器拉起 run**(断点 2)。「无人值守自动继续」因此只在「收口发生在定时器活跃期内」成立——`timer_has_active` 判定器会因活跃定时器存在而持续续 run 保持待命(core_run_commands.rs:2534-2541),这是当前唯一的待命保活机制,但受空转护栏(连续 3 轮无产出停,core_run_commands.rs:2561-2582)与用户交互/手动停止硬条件约束。

### 2.3 输入注入通道:三环是运行期,跨 run 是 steering 队列

| 环 | 语义 | 消费点 | 证据 |
|---|---|---|---|
| force | mid-stream 可打断(legacy) | streaming 中途 `has_force_pending` | `input.rs:36-45`、`:419-429` |
| steer | 下一安全点注入(provider 结束/tool 批后) | 安全点 drain 后 dequeue | `input.rs:137-139`、`safe_point.rs:121-154` |
| followUp | 仅 run 即将 idle 时 promote 消费 | `promote_follow_up` | `input.rs:181-188` |
| 跨 run steering 队列 | run 收口后由 `decide_idle_resume` 批量转出为注入消息(单条 user 消息,`{kind:"steering"}` 元数据) | `drain_pending_to_inject_messages` core_run_commands.rs:2603-2626 | `steering_queue.rs:109-114`、`:199-215` |

控制总线(L0-L3):continue 不入队 / L1 steer·followUp / L2 cooperative_stop / L3 force_cancel;drain 优先级 force_cancel > cooperative_stop > soft_inject(control.rs:382-439)。安全点映射:safe_point.rs:121-154。子代理运行中注入走 L1 steer 环 `request_subagent_inject`(control.rs:275-286);子代理强停走 L3(control.rs:296-305)。

**回答 Q3**:三环中**没有**一环能让系统在 run 结束后再启动 agent——三环的生命周期是「run 运行中」。run 结束后系统再启动 agent 的唯一通道是 T-CF-11:idle 续 run(收口判定 + 拉起新 run,core_run_commands.rs:2505-2671)。steering 队列条目在收口时被 `drain_pending_to_inject_messages` 转成**新 run 的初始 prompt**,而非塞回三环。

### 2.4 无人值守触发器:五源汇聚 + 收口续 run(T-CF-11,已生产接线)

唤醒源判定(core_run_commands.rs:2485-2558):
1. `PendingMessageQueue` 非空(定时器到期 / Cron 触发 / 子代理完成 subagent_spawner.rs:624-646 / 后台任务终态 task-wake / watchdog 兜底);
2. `TimerRegistry` 活跃定时器非空(timer_has_active 判定器,core_run_commands.rs:1642-1646);
3. enabled Cron 非空(cron_has_enabled,core_run_commands.rs:1652-1660)。

不续硬条件(core_run_commands.rs:2513-2519):abort_signal 触发 / `reason != Stop`(Error/MaxTurns/Aborted/Stopped 不续)/ 本 run 经 L1 收到用户消息(user_touched)。空转护栏:连续 3 轮无 AI 产出停止续 run(core_run_commands.rs:2458、:2561-2582)。续 run 拉起:`spawn_idle_resume_run` → `run_task_impl`(mode=`idle-resume`,history 经 SessionHistoryCache 自动续接,core_run_commands.rs:2637-2671)。子代理 run 不参与续 run(防自续循环,core_run_commands.rs:2867-2871)。

watchdog(G10/T-CF-13):每会话周期任务(60s),存在 dispatch 声明(子代理等待中)且自最近分发/唤醒起超 N 分钟(默认 10)无事件 → 注入兜底 steering 条目「您有一个运行中的后台任务 <ID>…请检查状态」(watchdog.rs:233-302);活跃定时器非空时抑制(watchdog.rs:236-238)。**watchdog 只针对「子代理等待」场景,不覆盖「AI 休眠后定时器到期」**。

### 2.5 会话恢复:一致性恢复 + 手动重发,无自动续跑

- 重启恢复:`RestoreManager.restore`(full-replay / snapshot-incremental)把 in-flight run 打断为 interrupted 终态(restore.rs:51-55、:549-611),重建会话树/事件流/序列号,门禁 `restore_ready` 放行新 run(core_run_commands.rs:2195-2239、:3197-3199)。
- 会话续接:run 收口把对话写 SessionHistoryCache(core_run_commands.rs:2714-2718),下次 run 的 history 参数回退源;冷启动回退前端 history,经 `hydrate_history` 水合(session-loop/hydrate.rs:36-46、:306-320 `with_initial_conversation_arc`)。
- 命令面:`main.rs:147-161` 仅注册 core_run_task / core_run_control / core_cancel_run 等,**无 resume 命令**;dev CLI 有 `status/continue/background-demo/run/run-json/goal-run/goal-json` 白名单(cli_bridge.rs:83-96,workbench 调试面);`resume_subagent`(子代理恢复阶梯)有实现无 IPC(orchestrator lifecycle.rs:226-320;doc 03 G6)。
- checkpoint(C1):采集(safe_point.rs:255-278 倒序扫描对话/工具输出)→ 落库叶子 payload(session.rs:545-574)→ 读取判定(session.rs:514-538)→ rewind 计划(会话树回退,session.rs:887-979)。提示词协议声明「存在 checkpoint 时优先恢复」(checkpoint.rs:16-21)——**由 AI 自行阅读历史执行,机制面不注入检查点载荷**。

**回答 Q4**:重启后停掉的 run **不能从检查点续跑**——被打断为 interrupted 终态且无自动/手动恢复入口;用户需重发消息(core_run_task + history 水合)开启新 run。命令行面无产品级 resume(仅 dev CLI 调试命令)。

### 2.6 goal 模式(无人值守场景目标形态)

- 判据已存在:`allows_auto_continue` 仅 Stop reason 允许自动续轮(orchestrator normalize.rs:177-179);goal-blocked / goal-max-rounds / goal-stalled 终态 reason 已定义(restore.rs:807-815)。
- **驱动未实现**:drive_run_loop 注释明言「未来 goal 多轮模式在本循环续轮」(core_run_commands.rs:141、:2702);rust 侧无 startGoalRun/driveGoalRun(grep 全仓 0 命中)。
- 前端 goalModeController(maxRounds=12,goalModeController.ts:12-50)构造 `/goal` 续写提示词,但「自动续轮」实际靠用户手动再发 + 系统 idle 续 run 兜底,无 goal 专属轮次驱动。

**回答 Q5**:现有组件里「自动重新唤醒 agent」的触发器 = T-CF-11 三源(队列/定时器/Cron)+ watchdog(仅子代理等待场景)。goal 模式无独立自动唤醒器——它复用 idle 续 run 通道,但缺少 goal 语义的轮次评估与 max_rounds 停机。

### 2.7 「自动继续链路」图(现有 vs 理想)

```
[现有] 唤醒源汇聚 → 收口消费 → 新 run(循环,但两头断)
                                        ┌──────────── 循环 ────────────┐
                                        ▼                              │
 set_timer 到期 ──┐                                             ┌──────┴──────┐
 Cron 触发 ───────┤→ PendingMessageQueue ─→ run 收口 decide_idle_resume ─→ spawn_idle_resume_run
 子代理完成 ──────┤   (steering 条目)        (队列/timer/cron 三源)        (mode=idle-resume,
 后台任务终态 ────┤                                              history 续接)
 watchdog 兜底 ───┘                                                      │
                                                                         └── 新 run 收口再判定
 断点 A:AI 已休眠后到期条目入队 → 无收口点消费(缺独立唤醒 watcher)
 断点 B:定时器/Cron store 是内存版 → 重启丢声明 → 跨重启无人值守断链
 断点 C:restore 打断的 run(interrupted)无自动恢复消费端;checkpoint 只在提示词层

[理想] 定时器唤醒 → 消息入队 → run 重启 → checkpoint 恢复(全链闭环)
 set_timer(持久化 store) 到期
   → 入队 steering 条目 + 独立唤醒 watcher(队列非空且无活动 run → 直接拉起 idle-resume run)
   → run_task_impl(mode=idle-resume, history 续接)
   → 注入消息附带叶子 checkpoint 载荷(read_leaf_checkpoint)
   → 收口再判定(循环);重启后:TimerStore/CronStore 恢复声明 → restore 打断的 run 生成恢复条目入队 → 同链消费
```

## 5. 建议:补齐「无人值守继续」链路(定时器唤醒 → 消息入队 → run 重启 → checkpoint 恢复)

链路缺口定位:G1(持久化)在链头,G2(唤醒 watcher)在链中,G3/G4(恢复消费)在链尾。建议按优先级落地:

**P0-1 定时器/Cron store 真适配接线(补 G1)**
- 实现 `TimerStore`/`SchedStore` 的 conex-db session_meta 真适配(键形状已冻结:`timer_<id>` / `sched_<id>`,配套 `timer_ids`/`sched_ids` 索引键),替换 engine.rs:1112/1176 的内存 store;同步把 `MemoryTimerStore::shared()` 的共享实例语义迁移到真适配(注册表与恢复共用同一数据源)。现有 `restore()`(timers.rs:458-518、sched.rs:474-517)与幂等落库(fire 后标 fired/cancelled/enabled=false)已按持久化设计,接线即可闭环。
- 验收:注册定时器 → 模拟重启 → restore 重建 sleep → 到期注入恰好一次;fired 声明不重复注入(已有测试 `timer_registry_persists_and_recovers` 的共享内存版,换真 store 后同断言)。

**P0-2 独立唤醒 watcher(补 G2,链路最关键一跳)**
- 新增 tokio 周期任务(可复用 watchdog 的每会话 spawn 模式,watchdog.rs:307-319):判定「PendingMessageQueue 非空 且 该会话无活动 run」→ 直接调用 `spawn_idle_resume_run`(复用 T-CF-11 现有拉起器,core_run_commands.rs:2637-2671)。判定条件与 `decide_idle_resume` 对齐(不续条件:abort/user_touched 语义按会话级状态),空转护栏复用 `resume_empty_streak`。
- 更小改法:在 `fire_timer`/`fire_cron` 落队列后,若检测无活动 run 则同步触发拉起(把「入队」与「唤醒」合并)。优先独立 watcher(解耦、可测、覆盖非定时器源的队列条目)。
- 验收:AI 休眠(收口三源全空)→ 定时器到期 → watcher 拉起 idle-resume run → 注入文本含到期提示。

**P1-3 restore 打断 run 的恢复消费端(补 G3)**
- `run_restore`(core_run_commands.rs:2195-2239)对 `RestoreOutcome.interrupted` 逐条生成恢复 steering 条目(「上次任务 <run_id> 在重启时被中断,请依据会话历史继续」,group_id=`restore-<run_id>`),入共享队列,由 P0-2 watcher / 下次收口消费——把「重启恢复」接入自动继续链。
- 验收:重启后无用户操作,interrupted run 自动被续跑(history 经 SessionHistoryCache/前端 history 水合)。

**P1-4 checkpoint 机制面注入(补 G4)**
- `spawn_idle_resume_run` 注入消息时,经 `read_leaf_checkpoint`(session.rs:514-538)读取当前叶子 checkpoint 载荷,拼入注入文本(「上次检查点:target/summary/next」)——把提示词协议(C1)升级为机制面保证;AI 仍在历史中可见完整载荷,但续跑不再依赖 AI 主动回溯。
- 验收:叶子含 checkpoint 的会话续 run,注入文本含检查点摘要;无 checkpoint 行为不变。

**P2-5 goal 模式轮次驱动(补 G6)**
- 基于 `allows_auto_continue`(normalize.rs:177-179)与 run_task_impl 的 mode 字段,在 drive_run_loop 收口对 mode=goal 的 run 增加 goal 续轮评估(max_rounds/max_stalled_rounds,前端 goalModeController 已下发):Stop 且未 DONE 且未达上限 → 按 idle 续 run 同通道续轮;达上限 → goal-max-rounds 终态。与 T-CF-11 共用拉起器与护栏。
- 验收:`/goal` 会话自动续轮至 DONE 或上限,停机 reason 正确。

**P2-6 resume 命令面(补 G7)**
- `core_resume_run`(run_id/session_id):打断的 run 复用其 run_id 语义(或新 run_id + 注释),装配 = core_run_task + history 水合 + P1-4 checkpoint 注入;前端「继续上次任务」按钮接入。

**顺序与依赖**:P0-1 → P0-2(独立于 P0-1,可先行)→ P1-3(依赖 P0-2 消费端)→ P1-4 → P2。P0-2 落地后,「定时器唤醒 → 消息入队 → run 重启 → checkpoint 恢复」四段链全部有机制面支撑;P0-1 补链头持久化;P1-3/P1-4 补链尾恢复语义。
