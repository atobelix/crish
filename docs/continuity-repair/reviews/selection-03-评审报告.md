## 1. 覆盖度矩阵（用户四诉求 × 5 份方案）

### 1.1 诉求定义（基线取自 00-总览与建议汇总.md:6）

- **诉求 1**：provider 网络问题中断输出后，能否经系统调度继续任务。
- **诉求 2**：子 agent 分配上限（确认型诉求——上限已存在，缺的是口径统一）。
- **诉求 3**：子 agent 网络中断后，主 agent / 系统能否恢复。
- **诉求 4**（核心原则）：只要 agent 未主动停止、用户未手动停止，agent（主/子）应能一直工作；goal 模式下未完成任务但 agent 主动结束，系统也应能继续。

### 1.3 覆盖度结论

1. **诉求 1/3/4 的机制面由 01+02+03 三角完整覆盖，04 提供层内韧性，05 提供数据面**；没有任何一个单一方案覆盖全部四诉求——01 是最接近的（8 维度全诉求映射，proposals/01:100-109），但 01 在若干细节（stalled 签名形态、429 Retry-After 钳制、熔断语义、收口时序）上不如 02/03/04 精细。
2. **诉求 2 是确认型诉求，方案层被 03/04/05 完全缺席**。这不构成功能缺口（上限已存在且 01 已做口径修正），但整合方案应显式标注「诉求 2 = 现状成立 + 口径修正（01 D8-④）」，避免评审矩阵盲格被误读为缺失。

### 2.2 只闭环一半的典型形态

1. **04（传输层）**：会退避、会重试、会熔断，但「续 run」完全不在本域（proposals/04:264 明言「退避接线不改变收场路径」）——它是唯一「改动即生效」的层，但单独交付时用户看到的效果只是「错误等待变长」，**不会让任务继续**。整合时必须与 D2/D3 同批。
2. **02（恢复机制）**：goal 场景「会恢复但不续目标」——02 的 W5 只对 error 收场续 run，goal 未完成场景显式排除（proposals/02:329）。单独落地 02 后，goal 用户仍靠前端文本环。
3. **03（Goal与调度）**：断点 3「会恢复但不持久」——只对主会话 run 生成恢复条目，子代理 in-flight 重启后仍停留在 failed（restore.rs:593-629），靠主 agent 手动重派。
4. **05（数据面）**：一切就绪但无机制——「会持久但不会动」。05 自认是支撑层（proposals/05:3-7 原则），依赖其他方案注入行为。

### 2.3 贯彻度总体判定

- **「未停就该一直工作」的机制主干 = 01（架构）+ 02（恢复时序细节）+ 03（goal/无人值守细节）三者的并集**；04/05 分别是 L0 与数据面支撑。五份方案无方向冲突（全部复用 idle 续 run 拉起器与 PendingMessageQueue，无新循环），冲突只出现在具体选型参数（见 §4 与 §6）。
- **贯彻度最弱的一环是 S1**（子代理 in-flight 重启恢复）：02 恢复预算/树重建完备但无「子代理 interrupted 续跑」消费语义；03 显式只做主 run。这直接冲击诉求 4 的「无人值守派发一批子代理后关灯走人」场景（领域 03-恢复阶梯:83 已点出）。

### 3.2 护栏遗漏场景（评审补充）

除 §1.4 的 S2/S3/S4/S5 外，进一步补漏：

1. **恢复条目的消费上限**（S3 衍生）：01 D6-③ 对 interrupted「逐条生成恢复条目」，未定义单次唤醒的条目数上限。极端场景（重启 + 30 个 in-flight run）→ 一次续 run 注入 30 条恢复文本，注入消息超长。补充护栏：恢复条目按会话合并、单条注入合并为一条摘要文本（drain_pending_to_inject_messages 已拼接，core_run_commands.rs:2603-2626，但需上限）。
2. **子代理恢复路径的自动 fork 禁令**（S1 衍生）：子代理 interrupted 恢复若走「自动续跑」，等于绕过「所有子 Agent 由主 Agent 分配」的嵌套裁决（AGENTS.md）。补充护栏：子代理恢复条目一律走通知主 agent 决策（阶梯 2 语义），**禁止**自动 fork/自动重派——主 run 才允许自动续跑。
3. **goal 续轮的「连续无产出但非 stalled」场景**：03 的空转计数区分「有工具调用无进展（计 stalled）」与「完全空转（计空转护栏）」（proposals/03:245），但「有工具调用且有产出、但产出与目标无关」的绕圈场景（工具批指纹变化 → 不 stalled，轮数消耗 → 不空转）无护栏。补充护栏：可配「每轮产出与 progress_signature 的相关性」暂不实现，至少把 max_rounds 设为硬上限（已有）并暴露轮数消耗观测（05 RecoveryStatus.goalState 已含 currentRound，proposals/05:241-261）。
4. **watcher 启动抖动**：03 断点 2 的 watcher 未定义启动延迟。重启后恢复条目 + 定时器补发 + 通知重排可能同刻到达 → watcher 立即拉 run，与用户刚发消息的 run 竞争（串行守卫会拒绝，core_run_commands.rs:3208-3216，但产生告警噪音）。补充护栏：watcher 首次轮询延迟（如 5s）与最小拉 run 间隔。
5. **预算键的跨会话语义**：02 W5 主 run 预算指纹 = fingerprint("main", 任务文本)（proposals/02:248），任务文本取「run 首条 user 消息」——定时器/Cron 唤醒的 idle-resume run 首条消息是系统注入文本，同一注入模板 = 同一指纹 → 不同定时器到期共享预算。补充护栏：指纹需混入唤醒源类型（timer-<id>/cron/restore/goal），否则「2 个定时器各续 3 次」被误算为「同任务续 6 次」。

### 3.3 护栏完整性总体判定

- **护栏存量充足且互相补位**：01 的红线面 + 02 的风暴五层 + 03 的 goal 面 + 04 的 abort/token + 05 的数据面纪律，合并后覆盖了递归、嵌套、用户意志、重试风暴、空转、预算、配额、并发写、迁移九类风险。
- **缺口集中在三处**：① 熔断对「部分保留断流」的计数盲区（S2，无方案覆盖）；② 恢复风暴的队列挤占与注入合并上限（S3/S3 衍生）；③ 子代理 interrupted 的消费语义与自动 fork 禁令（S1）。这三处均属「接线期会真实撞上」的缺口，建议主控在实现任务书中显式补护栏。
