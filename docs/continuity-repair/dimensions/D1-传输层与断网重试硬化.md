## 0. 结论速览

1. **退避接线**：`transient_retry`（stream_error.rs:81-95）改 async，sleep = `max(指数退避 750ms×2^(n-1), retry_after_ms)`，429 钳到 `min(5min, 剩余预算)`，5xx/Timeout/Network 钳 8s，再钳 60s 总预算；`tokio::select!{ biased; abort → 收场; sleep → 重试 }` 竞速。常量镜像 recovery.rs:115-120（750/8000/60000）加测试锁定防漂移。
2. **熔断**：session_meta 键 `provider_fail_streak`（JSON：count/first_fail_at_ms/last_fail_at_ms/window_ms，05 形状冻结），连续 6 次、成功归零、无窗口（裁决 #6 采纳 04 语义 + 05 键形状 + S2 补丁）；闸面 = `transient_retry` 入口检查（streak ≥ 6 直接 fatal 转上报）；**部分保留断流（瞬态类）计入计数，成功清零仅在 run 以非瞬态错误收场或正常完成时执行**（S2 补丁）；手动路径不受限。
3. **连接配置**：`Client::new()`（engine.rs:1093）改为 `fn build_http_client()` 单点封装 `Client::builder()`：connect_timeout 10s / tcp_keepalive 30s / h2 ping 30s+5s / 不设总超时；测试装配传参覆盖。
4. **provider_error 数据面**：`RunOutcome.provider_error: Option<ProviderErrorSummary{kind, retryable, retry_after_ms, retries}>`（loop/end.rs:99-125 增字段），fatal_provider_error（stream_error.rs:237-269）填充，drive_run_loop 在移动消费前（core_run_commands.rs:2710-2712 同批）提前提取。
5. **流中断结构化标注**：`providerErrorKind`/`providerErrorRetryable` 进消息 metadata（session-loop stream.rs build_message_metadata :439-481 + agent-provider consume/mod.rs :308-347 两处镜像）；`Stop` 事件扩展 error_kind 透传（streaming.rs:122-126 注入点、engine.rs:655-660 映射）。
6. **明确不做**：failover 主备链（裁决 #18，P3 独立项）；A' 增量流重试封装（selection-01 分歧 1 / 04 §2.1）；超时可配（P1-2，04 §3-3，归入连接配置小节但标 P1 可后置）。

### 3.1 退避接线（核心，stream_error.rs + handlers/mod.rs + loop/mod.rs）

#### 3.1.1 新增常量（stream_error.rs 模块头，镜像 recovery.rs:115-120 + retry.rs:29）

```rust
/// 首次退避基数（镜像 retry.rs:48 / recovery.rs:116，测试锁定防漂移）
pub(crate) const RETRY_BACKOFF_BASE_MS: u64 = 750;
/// 单次等待上限（5xx/Timeout/Network 类，镜像 retry.rs:49 / recovery.rs:118）
pub(crate) const RETRY_MAX_DELAY_MS: u64 = 8_000;
/// 429 Retry-After 放行上限（= MAX_RETRY_AFTER_MS，retry.rs:29：5 分钟）
pub(crate) const RETRY_RATE_LIMIT_MAX_DELAY_MS: u64 = 5 * 60_000;
/// 总重试预算（镜像 retry.rs:50 / recovery.rs:120）
pub(crate) const RETRY_TOTAL_BUDGET_MS: u64 = 60_000;
```

#### 3.1.2 退避决策函数（纯函数，可单测）

```rust
/// 计算本次重试等待（规则：429 放行到 5min，其余 8s 封顶，再钳剩余预算）
/// 返回 None = 预算耗尽，不再等待（直接 fatal）
fn retry_delay_ms(
    kind: ProviderErrorKind,
    attempt: u32,                    // 1 起
    retry_after_ms: Option<u64>,
    elapsed_ms: u64,                 // 预算起点以来墙钟
) -> Option<Duration> {
    // 预算闸：elapsed < 60s 才继续（对齐 withinRetryBudget 严格小于，retry.rs:163-166）
    let remaining = RETRY_TOTAL_BUDGET_MS.checked_sub(elapsed_ms)?;
    // 指数退避（镜像 retry.rs:107-112：min(max_delay, base * 2^(attempt-1))，指数上限 62）
    let exponent = (attempt.max(1) - 1).min(62);
    let backoff = RETRY_BACKOFF_BASE_MS.saturating_mul(1u64 << exponent);
    let cap = match kind {
        ProviderErrorKind::RateLimit => RETRY_RATE_LIMIT_MAX_DELAY_MS,
        _ => RETRY_MAX_DELAY_MS,
    };
    let wait = match retry_after_ms {
        Some(after) => backoff.max(after),   // Retry-After 与退避取大（镜像 retry.rs:124-127）
        None => backoff,
    };
    Some(Duration::from_millis(wait.min(cap).min(remaining)))
}
```

**分错误类规则表**（裁决 #3 + 04 §2.2）：

| 错误类 | 是否消费 Retry-After | 等待公式 | 上限 | 证据 |
|---|---|---|---|---|
| RateLimit(429) | **必须** | `max(退避, retry_after)` | `min(5min, 剩余预算)`——**突破 8s 封顶** | 裁决 #3；retry.rs:29 |
| ServerError(5xx) | 否 | 纯退避 | `min(8s, 剩余预算)` | 裁决 #3；分类器不解析 5xx 头（error.rs:248-251 只 429） |
| Timeout / Network | 否 | 纯退避 | `min(8s, 剩余预算)` | 同左 |

#### 3.1.3 transient_retry 改 async + abort 竞速

```rust
async fn transient_retry(
    state: &mut LoopState,
    classified: &ClassifiedStreamError,
) -> Result<HandlerOutcome, LoopError> {
    // Q40：每级决策前查 abort（既有，stream_error.rs:83-85 保持）
    if state.abort_signal.is_aborted() {
        return streaming_aborted(state);
    }
    // ── 熔断闸（§3.2 规则 C1）：streak ≥ 阈值 → 跳过 run 内重试直接 fatal ──
    if state.options.provider_fail_streak.is_some_and(|s| s >= PROVIDER_FAIL_THRESHOLD) {
        return fatal_provider_error(state, classified);
    }
    let limit = state.options.transient_retry_limit;
    if state.transient_retries < limit {
        // 预算起点惰性初始化（首次瞬态错误时；随 run 重建归零，loop/mod.rs:672 同批）
        let started_at = *state.transient_retry_started_at.get_or_insert_with(tokio::time::Instant::now);
        let elapsed_ms = started_at.elapsed().as_millis() as u64;
        // 熔断计数转发（瞬时错误已发生，无论是否重试都计熔断——S2 语义的 run 内面）
        // 注：实际计数落键在壳层收口（§3.2 规则 C2/C3），本层只透出状态
        if let Some(delay) = retry_delay_ms(classified.kind, state.transient_retries + 1, classified.retry_after_ms, elapsed_ms) {
            // abort 竞速 sleep（规则 R5：abort 优先，biased）
            tokio::select! {
                biased;
                _ = state.abort_signal.wait_aborted() => return streaming_aborted(state),
                _ = tokio::time::sleep(delay) => {}
            }
            // sleep 后复查 abort（竞速窗口收口）
            if state.abort_signal.is_aborted() {
                return streaming_aborted(state);
            }
            state.transient_retries += 1;
            emit_retry_diagnostic(state, classified, state.transient_retries, limit);  // 扩展：附 delay_ms/retry_after_ms（§3.1.4）
            dispatch(state, E::NoProgressContinue)?;
            return Ok(HandlerOutcome::continue_run());
        }
        // 预算耗尽：不进重试直接 fatal（不消耗次数）
    }
    fatal_provider_error(state, classified)
}
```

**规则汇总**（R1-R5，均对应测试断言）：

| # | 规则 | 语义 |
|---|---|---|
| R1 | 预算起点 | `LoopState.transient_retry_started_at: Option<tokio::time::Instant>`（handlers/mod.rs 新增字段，01 敲定 §2.3）；首次瞬态错误时 `get_or_insert`；fresh run 归零（loop/mod.rs:672 同批 `self.state.transient_retry_started_at = None`） |
| R2 | Retry-After | 429 必须等：`wait = max(退避, retry_after)`，钳到 min(5min, 剩余预算)；**不钳 8s**（裁决 #3） |
| R3 | 预算钳制 | 等待再钳 `min(wait, remaining_budget)`；`elapsed >= 60s` → `retry_delay_ms` 返回 None → 不消耗次数直接 fatal（对齐 retry.rs:163-166 严格小于） |
| R4 | 预算语义 | 429+30s 场景：第一次等 30s（累计 30s）→ 第二次钳到剩余 30s → 第三次前预算耗尽直接 fatal——**不无限尊重服务端「再来一次」**（04 §4.1） |
| R5 | abort 竞速 | `tokio::select!{ biased; abort → streaming_aborted; sleep → {} }` + sleep 后复查；语义对齐 retry.rs TokioSleeper（retry.rs:316-323）；abort 不消耗计数、不发诊断（扩展现有 Q40 测试） |
| R6 | 配置缺省 | `SessionLoopOptions.retry_backoff: Option<RetryBackoffConfig>`（None = 现状立即重试，向后兼容）；`Some` 时本规则生效。**常量默认值即 750/8000/60000**，配置位主要用于关闭/自定义（02 W2 / 04 3-1） |

### 3.2 会话级熔断（circuit breaker）

#### 3.2.1 键与形状（01 敲定 §2.1 冻结：05 形状）

session_meta 键 `provider_fail_streak`（独立前缀，不复用 recover_*，裁决 #7）：

```json
{
  "count": 3,
  "first_fail_at_ms": 1789000000000,
  "last_fail_at_ms": 1789000060000,
  "window_ms": 0
}
```

- **count**：当前连续失败计数（瞬态类）。
- **first_fail_at_ms / last_fail_at_ms**：首次/最近一次失败时刻（epoch ms）。
- **window_ms**：窗口配置（**默认 0 = 无窗口**，裁决 #6「无窗口」；字段保留 = 惰性过期支持，若未来配置 >0，读时判定 `now - first_fail_at_ms >= window_ms` → 惰性清零——05 设计要点 :171）。**window_ms 不参与默认语义判定**（连续计数、成功归零是唯一语义）。
- 宽容解析 fail-open：坏 JSON / 缺字段 → 视为 count=0（对齐 recovery.rs:327-335 fail-open 先例；05 §2.B :359）。

#### 3.2.2 计数触发与清零规则（裁决 #6 + S2 补丁）

| # | 规则 | 语义 | 触发位置 |
|---|---|---|---|
| C1 | **闸面**：`transient_retry` 入口检查 `options.provider_fail_streak >= 阈值(6)` → 跳过 run 内重试直接 fatal | 熔断期不烧 run 内配额（selection-01 分歧 9 裁决采纳 04 闸面） | stream_error.rs transient_retry（§3.1.3 伪码已含） |
| C2 | **计数（run 内面）**：任何瞬态类错误（RateLimit/ServerError/Timeout/Network）**发生即计**，无论是否部分产出 | 部分保留断流也计入（S2 补丁）——「产出一点再断流」无法无限绕开熔断 | 壳层收口按「瞬态类收场」统一计数（见 C3 落点） |
| C3 | **清零（成功面）**：成功清零仅在 **run 以非瞬态错误收场（fatal 非瞬态类）或正常完成** 时执行 | 部分保留断流（stop 收场但瞬态类）**不清零**；「run 内重试中成功」**不清零**（那是瞬态波动，不是会话健康信号——连续计数语义下只有收场级判定） | 壳层 drive_run_loop 收口 |
| C4 | **手动路径不受限**：用户显式发消息 / 手动 resume 不查熔断 | 用户意志永远优先（04 §6 D7；与「用户显式停止永不自动续」红线对称） | 闸只挂在自动重试入口 |
| C5 | **熔断触发事件**：streak 达阈值 → 发 `runtime-intervention-required` 事件 + 留痕 | 复用 steering_evaluation.rs:68-75 模式（selection-02 §1.4 统一裁决：熔断触发发 runtime-intervention-required + recovery-escalated 留痕——recovery-escalated 属 D3 事件登记批，本维度只发 runtime-intervention-required，D3 登记时补 recovery 域留痕） | 壳层收口计数落键处 |

**S2 计数落点设计**（关键：计数不在内核，在壳层收口——session-loop 无 session_meta 面，02 §2-E「为什么不放内核」）：

```
drive_run_loop 收口（core_run_commands.rs）
├─ 从 RunOutcome 读取 provider_error（§3.4 提取点）
│
├─ 有 provider_error（fatal 收场）：
│   ├─ kind 瞬态四类 → streak +1（count++、last_fail_at=now、first_fail_at 首次填充）
│   └─ kind 非瞬态 → streak 清零（规则 C3 非瞬态错误收场分支）
│
├─ 无 provider_error 且 reason==Stop/正常完成 → streak 清零（规则 C3 正常完成分支）
│   └─ 注：部分保留断流（reason=Error 但无 fatal？）——
│       部分保留断流走「Message + providerError 标注」收场，reason 为正常值
│       （streaming.rs:119-127 → Stop{Error} 注入 → consume Message），
│       **RunOutcome 无 provider_error 且收场是正常 Message**——
│       此时必须按「流中断标注判定」计数：metadata 含 providerErrorKind 且为瞬态类
│       → streak +1（不清零）【S2 补丁的落点】；否则清零
│
└─ 计数落键：spawn_blocking 写 session_meta（F2-27，01 敲定 §3-5：熔断键读写全走
    spawn_blocking，先例 session_commands.rs:269-288）
```

**S2 落点的精确化**：部分保留断流在 RunOutcome 上没有 provider_error（不是 fatal），但有「metadata.providerErrorKind 标注 + 瞬态类」信号（§3.5 标注增强正是 S2 计数的数据源）。收口判定顺序：

1. `RunOutcome.provider_error` 存在 → 按 C3 分支（瞬态 +1 / 非瞬态清零）；
2. 无 provider_error 但 run 内最后一条消息 metadata 含 `providerErrorKind` 且为瞬态四类（RateLimit/ServerError/Timeout/Network）→ streak +1（**部分保留计入**，不清零）；
3. 其余（正常完成 / 无任何 provider 错误信号）→ streak 清零。

判定所需的「最后一条消息 + metadata」信息在收口时已在手（outcome.messages 含部分保留消息，T09.1 消息带 metadata，core_run_commands.rs:2718 to_history_messages 前可读）。

#### 3.2.3 装配时序（数据流）

```
run 内 fatal / 部分保留断流（内核）
  → RunOutcome（provider_error / 消息 metadata 标注）
  → 壳层 drive_run_loop 收口：按 C3 判定 → spawn_blocking 写 provider_fail_streak
  → 下一 run 装配 SessionLoopOptions（run_task_impl / SessionLoopProducer 装配面）：
     读 provider_fail_streak 键 → options.provider_fail_streak = Some(count)
  → transient_retry 入口闸（C1）生效
```

熔断语义天然跨 run（04 G9 目标）；run 内不加状态（LoopState 只读 options 注入值）。

**与 recovery.rs 的镜像关系**：熔断**不镜像** RecoveryRetryPolicy 常量（那是退避；§3.1 已镜像）；与 C7 的共用面是「禁止自动恢复」判定出口——recovery.rs:956-975 `can_recover` 同侧，熔断触发后 D2 续 run 判定查 `provider_fail_streak >= 阈值` 视同超预算（02 §2-E「共用三样东西」③）。D1 只负责键读写与闸面，D2 消费时零额外工作。

/// connect_timeout 10s / tcp_keepalive 30s / h2 ping 30s+5s；不设总超时

fn build_http_client(options: Option<ClientConnectionConfig>) -> reqwest::Client {

        .tcp_keepalive(Duration::from_secs(30))

|---|---|---|---|---|
| connect_timeout | 10s（reqwest 默认 30s） | 建连失败探测 30s→10s，更快进 Network 分类重试 | 极慢网络偶发误判（可接受） | 可配（session_meta 或配置层，04 §3-2） |

## 6. 风险与护栏

### 6.1 火焰重试三道护栏（04 §4.1 + 02 §4.1 五层中的前三层）

| 层 | 机制 | 本维度实现 |
|---|---|---|
| 1 | 指数退避 750→8s | §3.1.2（429 分支放宽到 5min，由预算闸兜底） |
| 2 | 60s 总预算（elapsed >= budget 停止，严格小于） | retry_delay_ms 预算钳制 + 耗尽直接 fatal（规则 R3） |
| 3 | 会话级熔断（连续 6 次 → 自动重试全禁） | §3.2（闸 run 内重试入口；跨 run 闸由 D2 消费） |

### 6.2 token 成本（04 §4.4 / §6-D5）

失败尝试不记账：失败尝试的 usage 不落库，仅成功消息的 metadata.usage 记账（现状即如此，本维度不改变，仅记录纪律）。退避/预算/熔断三护栏间接限制总消耗（429 尊重 Retry-After 后不再白费请求、预算耗尽终止防无限成本、熔断防跨 run 反复烧钱）。

### 6.3 断流不重复输出不变量保持（04 §4.5）

三条不变量接线后原样保持：① `builder.is_empty()` 判定（streaming.rs:116-129）决定「重试 or 保留」，退避只挂在重试分支内（stream_error.rs，未产出路径）；② 已产出内容 → Stop{Error} → Message + 标注（§3.5 只加字段不改语义）；③ 会话层 commit 基于完整对话（部分消息已 commit 后重试是新请求基于完整对话——语义层重复不可能）。回归护栏：既有测试原样保留（§5.4）。

### 6.4 熔断相关护栏（selection-03 S2 补丁 + 裁决 #6）

- **部分保留断流计入**：瞬态类错误不论是否部分产出均计熔断；成功清零仅在「run 以非瞬态错误收场或正常完成」时执行（S2 补丁核心，防「产出一点再断流」无限绕开熔断）。
- **手动路径不受限**：熔断只禁自动重试（run 内 + D2 自动续 run 侧），用户显式发消息/手动 resume 照常（04 §6 D7）。
- **run 内不加状态**：熔断数据只在壳层 session_meta 维护（02 §2-E），LoopState 只读注入值。

### 6.5 与既有护栏的衔接

- 用户显式停止永不自动续：本维度不触碰 decide_idle_resume（D2 接线时保证 Stopped/Aborted 不误放行，00 总纲 §6 契约冲突注）。
- F2-27 spawn_blocking：熔断键读写（01 敲定 §3-5）走 spawn_blocking（先例 session_commands.rs:269-288）。
- 测试资产门禁：recovery.rs 40+ 单测 + 4 集成测试作回归面；禁止 --no-verify。
