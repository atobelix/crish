## 1. 维度目标与验收断言

### 1.1 目标（引用 00 总纲 §3 D3 最低线，逐条细化）

00-总纲-维度设计.md:77 定义 D3 最低线：

> ① 每会话 RecoveryCoordinator 完整装配（五件套：store/queue/tree/spawner/policy）+ SessionTree 重建（restore 后 from_session_record）+ spawn_blocking helper 扩展覆盖全部持久化点；② 子代理收口触发：RunFailureContext 还原 → on_subagent_run_failure；阶梯 1 = **收口后重派**（原 run failed reason=recovery-retry，预算内重派新 run，不消费 Episode、无 steering）；阶梯 2 steering+落库；③ 重启 restore_steering_notifications 重排。

> 验收断言（最低线）：注入 2 次瞬态错误 → 阶梯 1 自动恢复；预算耗尽 → 阶梯 2 steering 条目 + recover_notifications 落库；重启后 pending 通知重排入队（recovery.rs 既有 40+ 测试作回归面）。

## 3. 改动设计

### 3.1 装配：CoreRunState 两字段 + coordinator_for 惰性构造

**新增字段**（CoreRunState，core_run_commands.rs:1480-1587 结构体增）：

```rust
/// D3：每会话恢复协调器（C7 权威实例；五件套装配，惰性构造）
recovery_coordinators: Mutex<HashMap<String, Arc<Mutex<RecoveryCoordinator>>>>,
/// D3：每会话会话树（restore 后 from_session_record 重建；fork 源叶子载体）
session_trees: Mutex<HashMap<String, Arc<Mutex<SessionTree>>>>,
```

**coordinator_for（惰性构造，幂等）**：

```rust
fn coordinator_for(self: &Arc<Self>, session_id: &str) -> Option<Arc<Mutex<RecoveryCoordinator>>> {
    // 1. 已构造 → 返回既有（幂等，同会话同实例）
    // 2. local_db() 为 None（测试替身 store）→ None 降级（协调器不可用，行为与接线前一致）
    // 3. 五件套：
    //    store   = Arc::new(db) as Arc<dyn RecoveryStore>   // LocalDb impl 现成（recovery.rs:622）
    //    queue   = Arc::clone(&self.pending_queue)          // 与引擎共享队列同一实例（core_run_commands.rs:1633、2025-2028）
    //    tree    = session_trees 查 / 无则 SessionTree::new(session_id)（session.rs:334）
    //    spawner = Arc::clone(&self.subagent_spawner) as Arc<dyn SubagentSpawner>
    //    policy  = RecoveryRetryPolicy { max_retries: 2, ..Default }  // V3：跨 run 2 次，与内核 3 次叠加
    // 4. RecoveryCoordinator::new 经 spawn_blocking（new 同步读 4-5 键，F2-27）
    // 5. double-check：锁内重查（并发双构造时丢弃后到者）
}
```

要点：
- **五件套必传**是裁决 #4（完整装配一次到位，禁占位树）：RecoveryCoordinator::new 签名即五件套（recovery.rs:846-853），不存在「轻量构造」。
- **policy.max_retries = 2**（敲定 §5 V3：「建议壳层装配 2，与内核 3 次叠加共 5 次瞬态尝试/任务，实施时确认」）。可配键沿用 02 W3 建议：session_meta `recover_ladder1_max_retries`（装配时读，缺省 2；不新增冻结键，属 D3 自决键，见 §4.1）。
- **队列同一实例**：engine.timer_steering_queue()（engine.rs:1414-1415）与 CoreRunState.pending_queue 同一 Arc（core_run_commands.rs:1633；测试锁定 :6754-6761），直接 Arc::clone(self.pending_queue) 即满足「引擎侧持有的共享队列」。
- **spawner 同一实例**：SubagentSpawnerImpl（core_run_commands.rs:1575）→ Arc 宽化为 `Arc<dyn SubagentSpawner>`（与 fork_and_reassign 的调用契约一致，recovery.rs:829、1136-1142）。
- **降级语义**：local_db() 为 None 时 coordinator_for 返回 None——测试替身 store 下恢复路径不触发（与 save_run_usage 的 None 跳过先例一致，core_run_commands.rs:2954-2956）。生产恒为 LocalDb 恒 Some。

#### 3.2.2 收口块改写（:2844-2852，触发点伪代码）

```rust
// ── D3：C7 恢复触发（决策先行于既有收口；重派动作后置于记账释放）──
let mut recovery_plan: Option<RecoveryPlan> = None;
if let Some(cfg) = active.subagent.clone() {
    let terminal_status = { /* 锁内读 run.status（既有） */ };
    if terminal_status == RunStatus::Failed {
        if let (Some(coord), Some(pe)) = (state.coordinator_for(&session_id), resume_provider_error.as_ref()) {
            let ctx = build_run_failure_context(&cfg, pe, &first_user_text, has_assistant_output, &state).await;
            let outcome = blocking_coordinator_call(coord, |c| c.on_subagent_run_failure(&ctx)).await;
            recovery_plan = match outcome {
                Ok(RecoveryOutcome { action: RecoveryAction::AutoRetry { delay, .. }, .. }) => Some(RecoveryPlan::AutoRetry { delay, ctx }),
                _ => None,   // SteeringQueued / NeedsUser：通知已入队/已标记，无需额外动作
            };
        }
    }
    // 既有收口五步（记账释放 → 行更新 → subagent-ended → wait feed → steering 通知）
    state.on_subagent_run_terminal(&cfg, terminal_status).await;
    // ── 阶梯 1 收口后重派（裁决 #5；旧 run 记账已释放 → spawn 守卫计数正确）──
    if let Some(RecoveryPlan::AutoRetry { delay, ctx }) = recovery_plan {
        tokio::time::sleep(delay).await;                 // 退避（async sleep 不阻塞 worker）
        // 原 run end_reason 覆写（RecoveryStore::update_run_status，同步 → spawn_blocking）
        blocking_store_call(|| store.update_run_status(&ctx.subagent_run_id, "failed", "recovery-retry"));
        // 预算内重派新 run（mode=recovery-retry；不消费 Episode、无 steering）
        match state.subagent_spawner.spawn(&retry_spawn_request(&cfg, &ctx)).await {
            Ok(_) => { state.ladder1_retry_count(session_id, &ctx).increment(); /* 观测日志 */ }
            Err(e) => {
                // spawn 失败（含 12/5/1 守卫拒绝）：计数推满 → 重入 escalate（阶梯 2 通知，不静默）
                state.ladder1_retry_count(session_id, &ctx).set_max();
                let _ = blocking_coordinator_call(coord, |c| c.on_subagent_run_failure(&ctx)).await;
            }
        }
    }
}
```

### 3.3 重启：run_restore 成功路径后树重建 + 通知重排

run_restore（core_run_commands.rs:2195-2254）成功分支，在 :2227 状态回写之后、:2236 `Some(outcome)` 返回之前插入：

```rust
// D3：逐会话重建会话树 + 构造协调器 + 重排 pending 通知
for record in &outcome.sessions {
    // 1. 树重建（from_session_record 含结构校验；失败降级空树，fork 结构化拒绝）
    let tree = SessionTree::from_session_record(record.clone())
        .map_err(|e| tracing::warn!(...))
        .unwrap_or_else(|_| SessionTree::new(&record.session_id));
    self.session_trees.lock().insert(record.session_id.clone(), Arc::new(Mutex::new(tree)));
    // 2. coordinator 惰性构造（触发 new：恢复预算/forks/通知/needs_user）
    if let Some(coord) = self.coordinator_for(&record.session_id) {
        // 3. pending 通知重排入队（同步 → spawn_blocking）
        let n = blocking_coordinator_call(coord, |c| c.restore_steering_notifications()).await;
        tracing::info!(session_id, "恢复阶梯 2 通知重排 {n} 条");
    }
}
```

要点：
- **树重建数据现成**：`RestoreOutcome.sessions: Vec<SessionRecord>`（restore.rs:100），快照会话 ∪ run 派生会话已在 restore.rs:679-694 组装（含 branches/current_leaf_id）。树重建成本 ~50 行（裁决 #4 依据）。
- **降级空树不是假接线**：from_session_record 失败 = 快照数据异常（重复 id / 父先于子 / abandoned 未出现，session.rs:599-626 校验），降级空树后阶梯 1/2/4 照常（不依赖树），阶梯 3 fork 被 recovery.rs:1066-1070 结构化拒绝——fail-open 语义，与「禁占位树」不冲突（占位树指「故意传空树当装配完成」，降级指「异常数据兜底」）。§8 决策 5。

### 3.4 spawn_blocking helper 与覆盖全表（F2-27）

#### 3.4.1 helper 形态（仿 save_run_usage 先例，core_run_commands.rs:2958）

```rust
/// F2-27：RecoveryStore 同步 SQLite 全走 spawn_blocking。
/// coordinator 变体：持锁在 blocking 线程执行同步方法；on_subagent_run_failure 为
/// 「无 await 的 async 方法」（函数体全同步，recovery.rs:914-978 无 .await），经
/// block_on 在 blocking 线程执行（futures_util::executor::block_on，workspace 依赖
/// futures-util，Cargo.toml:73 / agent-workbench Cargo.toml:31）。
async fn blocking_coordinator_call<R: Send + 'static>(
    coord: Arc<Mutex<RecoveryCoordinator>>,
    f: impl FnOnce(&mut RecoveryCoordinator) -> Result<R, RecoveryError> + Send + 'static,
) -> Result<R, RecoveryError> {
    tokio::task::spawn_blocking(move || {
        let mut c = coord.lock().unwrap_or_else(|e| e.into_inner());
        f(&mut c)
    })
    .await
    .map_err(|join| RecoveryError::PersistFailed { message: join.to_string() })?
}
```

- 纯同步方法（new / restore_steering_notifications / acknowledge / report_to_user / persist_*）：闭包直调。
- on_subagent_run_failure（声明 async、函数体无 await，recovery.rs:914-978）：闭包内 `block_on(c.on_subagent_run_failure(&ctx))`（无 await future 立即完成，无阻塞）。

### 3.5 跨 run 阶梯 1 重试计数（壳层状态）

`ctx.retries` 的语义 = **该任务（指纹）的跨 run 阶梯 1 已重试次数**，与 run 内 `transient_retries`（provider_error.retries）是两套独立计数（02 D5 的「内核 3 + 跨 run 2 叠加」语义要求）。recovery.rs 无此计数键（阶梯 1 不留痕是既有语义，测试断言 recovery.rs:1801-1803），故由壳层维护进程内记账：

```rust
/// 会话级：指纹 → 跨 run 阶梯 1 重试次数（进程内；重启清零是既有语义——
/// 阶梯 1 不持久化，重启后直接重头判定，Escalate 兜底不会无限重试）
ladder1_retries: Mutex<HashMap<(String, String), u32>>,   // (session_id, fingerprint) → count
```

- 初始 0；AutoRetry 重派成功 → +1；spawn 失败 → 置 max_retries（重入必 Escalate）；Escalate（含重入）后该任务计数不再变化（已上阶梯 2，后续失败走通知）。
- 该计数不需要持久化：重启后归零 + 重派 run 自身失败会再走一遍阶梯 1（预算 2 次内）或直接阶梯 2——不产生无限重试（每 run 至多 2 次跨 run 重派，且 Episode 预算与熔断（D1）兜底）。
