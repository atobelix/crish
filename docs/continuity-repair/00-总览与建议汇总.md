# 00 — Agent 任务连续性综合分析与建议汇总

> 目录：docs/agent-resilience-analysis/（本轮分析产出）
> 日期：2026-08-10
> 方法：8 个并行分析子代理各出一份领域文档（01-08），本总览做交叉对比、一致性核验与推荐方案裁决。
> 用户诉求：① provider 网络问题中断输出后能否经系统调度继续任务；② 子 agent 分配上限；③ 子 agent 网络中断后主 agent/系统能否恢复；④ 核心原则——只要 agent 未主动停止、用户未手动停止，agent（主/子）应能一直工作；goal 模式下未完成任务但 agent 主动结束，系统也应能继续。

---

## 一、用户四诉求的直接回答

### 诉求 1：provider 网络中断后能继续吗？

**部分能，但自动恢复只到「单 run 内 3 次立即重试」，之后任务悬挂。**

- 引擎内核（主/子 agent 共用）：瞬态错误（RateLimit/ServerError/Timeout/Network）自动重试 **3 次/run**（`crates/session-loop/src/loop/handlers/stream_error.rs:81-95`），**无退避、无 Retry-After 消费**；另有 length 升级（2 次）与溢出压缩（1 次）阶梯。
- 流已产出内容的中断：**部分保留、不重试**（防重复输出，`streaming.rs:116-129`），错误降级为 metadata 标注。
- 耗尽后：`PROVIDER_ERROR` → endReason=error → run 结束，**系统不自动恢复**（`decide_idle_resume` 硬性排除 `reason != Stop`，`core_run_commands.rs:2511-2515`）。
- 跨 run 恢复：C7 四级恢复阶梯（orchestrator/recovery.rs，2233 行，含预算制、fork 三态继承、重启重排）**设计+实现完整，但生产零接线**（F2-08，`recovery.rs:57-62` 自述）。用户可手动再发消息续接（消息级水合成立）。

### 诉求 2：子 agent 分配上限？

**「一轮最多 12 个」的文档口径与代码语义不同。** 代码真值为 `DEFAULT_RECURSION_GUARD`：**maxDepth=1（仅主 Agent 可派发）/ maxSiblings=5（同父并发）/ maxConcurrent=12（全会话未终态并发）**（`crates/agent-tools/src/tools/subagent.rs:497-501`）。即**同时运行**的子 agent ≤ 12（同父 ≤ 5），不是「每轮累计派发 ≤ 12」——前序完成后可继续派发，累计可超 12。建议统一表述。

### 诉求 3：子 agent 网络中断，主 agent / 系统能否恢复？

**系统不自动恢复，主 agent 可被通知后手动重派。**

- 中断路径：run 内 3 次重试 → failed → 记账释放 → `subagent-ended`（Critical 必达落库）→ wait 通道 feed → **steering 通知唤醒主 agent**（`subagent_spawner.rs:486-660`）→ 主 agent 下一轮读到「子代理失败」，手动重新 `run_subagent`。
- C7 阶梯 1/2/3/4（自动重试 / 主 agent 激活 / fork 重派 / 上报用户）**全部未接线**；`resume_subagent`/`kill_all` 命令面**未接 IPC**（仅测试消费）；无 checkpoint。
- 重启后：in-flight run 一律打断为 failed（`restore.rs`），**不续跑**。

### 诉求 4（核心原则）：只要 agent 未主动停止、未用户停止，应能一直工作？

**当前不满足「强语义」，只满足「单 run 内多轮 + 系统事件驱动续 run」。**

- 已成立的自动续 run 主干：**T-CF-11 idle 续 run**——run 以 stop 收场后，若跨 run steering 队列/定时器/Cron 任一非空，自动拉起新 run（`core_run_commands.rs:2505-2671`），三源已接线（子代理完成、后台任务终态、watchdog 兜底）。
- 三个断点：① 定时器/Cron store 是内存版，重启丢声明；② AI 休眠后到期事件只入队、无独立 watcher 拉起 run；③ 重启恢复只保一致性不保续跑。
- goal 模式：**前端是唯一活跃的自动续写权威**（`/goal` → `decideGoalContinuation` → 自动发起下一轮，有 12 轮上限）；引擎侧全是占位（GoalAuditStrategy 占位、`visibleGoal/maxRounds` 字段被 serde 丢弃、`allows_auto_continue` 零生产调用、`GoalComplete` 事件无发射点）。

**共识度最高（6 份文档 P0 重合或互补）**：
1. **C7 阶梯接线**（03/06/08 直指，01/02/04 佐证）——把已写好的四级恢复阶梯接上生产，是「断网继续」的第一响应。
2. **重试退避/Retry-After 接入生产**（01/04 直指，03/08 佐证）——改 3 次连发为有退避的重试。
3. **idle 续 run 通道扩展为四源（goal_pending）**（01/05/07 直指）——goal 未完成作为自动继续的唤醒源。
4. **resume 命令面 + 定时器持久化**（02/03/06/07 指向）。

### 2.3 交叉补充（不同视角的独有建议）

- **05 号独有发现**：前端 `/goal` 已传 `visibleGoal/maxRounds/maxStalledRounds` 但 RunTaskOptions 字段缺失被 serde 静默丢弃——引擎补字段即可激活前端已发出的目标信息。
- **08 号独有建议**：CompletionRequirement（grok 式显式完成契约）、provider 主备链 failover（TS fallback-chain 资产未迁 Rust，属资产遗失风险）、TodoGate 轻量版。
- **07 号独有断点**：AI 休眠后定时器到期事件「只入队无消费方」——缺独立唤醒 watcher（这是「无人值守自动继续」最关键的一跳）。
- **01 号独有细化**：error 收场自动续 run 的具体护栏设计（连续 error 上限 3 次 + 退避 + user_touched 取消 + 非 retryable 不续）。

## 三、综合推荐方案（主 Agent 裁决）

### 原则

1. **复用现成资产**：C7 recovery.rs（2233 行 + 40+ 测试）、checkpoint 三件套、retry.rs、T-CF-11 拉起器、PendingMessageQueue——全部已实现，缺的是接线，不是新写。
2. **红线不变**：12/5/1 递归守卫与嵌套禁令只增不减（恢复路径 fork 必须显式走 spawn 守卫）；探索类文档配额不绕过；测试资产门禁不受影响（recovery.rs 既有测试直接作接线回归面）。
3. **用户显式停止永不自动续**（Stopped/Aborted 不续 run），自动恢复只针对引擎判定可恢复的瞬态失败与任务未完成。
4. **护栏齐备**：所有自动续 run 都带连续失败上限、退避、空转护栏、user_touched 取消。

### 推荐落地路线（按依赖排序，同权不砍项）

**阶段一（P0）：断网继续的主干接线**
1. **C7 阶梯 1+2 生产接线**（03/06/08 共识）：每会话 RecoveryCoordinator 生命周期（CoreRunState 装配 + F2-27 spawn_blocking）+ `drive_run_loop` 子代理收口挂 `on_subagent_run_failure` + RunOutcome 增加 `provider_error` 字段（fatal_provider_error 填充）+ 重启 `restore_steering_notifications` 重排。
2. **瞬态重试加退避 + 消费 Retry-After**（01/04 共识）：stream_error.rs 插入退避（优先 retry_after_ms，缺省指数 600ms×attempt，镜像 recovery.rs 750/8000/60000 常量），SessionLoopOptions 加可配置项。备选方案 A：直接把 HttpProviderCall 外包给 provider_stream_with_observer（改动更集中）。
3. **主 run error 收场后自动续 run**（01/03/08 共识）：EndDecision/RunOutcome 加 `retryable` 标志 → decide_idle_resume 放行 `reason==Error && retryable && 预算内` → PendingMessageQueue 入队系统条目 → spawn_idle_resume_run 拉起；护栏：连续 error ≤3 + 退避 + 非 retryable 不续 + user_touched 取消。

**阶段二（P1）：goal 继续工作 + 子 agent 显式恢复**
4. **goal 引擎化**（05 主线，01/07 佐证）：RunTaskOptions 补齐 goal 三字段（激活前端已发信息）→ session_meta `goal_state` 载体 → 收口 RoundAssessment（未完成检测 + stalled 签名）→ decide_idle_resume 三源扩四源（goal_pending）→ 续轮注入 nextSteps（摘要 JSON 消费）→ goal-round-* 事件登记。护栏：max_rounds/max_stalled/空转复用。
5. **resume_subagent/kill_all 命令面 + 定时器/Cron store 真适配**（02/03/06/07 共识）：lifecycle_service 注册 Tauri 命令 + 前端入口；TimerStore/SchedStore 换 session_meta 真适配（键形状已冻结）。
6. **独立唤醒 watcher**（07 独有但影响面大）：队列非空且无活动 run 时直接拉起 idle-resume run——补「AI 休眠后定时器到期」断链。

**阶段三（P2）：恢复语义增强**
7. **checkpoint 机制面注入**（01/06/07）：收口采集（collect_checkpoint_from_messages）→ 叶子落库 → 续 run 注入「上次检查点」载荷，从提示词协议升级为机制保证。
8. **restore 打断 run 生成恢复条目**（03/07）：重启后 interrupted 列表入队，自动续跑（注入「上次被重启打断，请继续」）。
9. **子代理 checkpoint/断点续跑**（02/08）：fork 携带产出清单 + 断点位置（write_claims → SubagentOutput 已存在）注入新 run。
10. **CompletionRequirement + TodoGate 轻量版**（08）：显式任务完成契约（grok 验证过的机制），治「AI 半途而废」。
11. **provider 主备链 failover**（08）：TS fallback-chain 资产迁 Rust。
12. **观测/UI**（03/05）：recovery-* 事件登记、core_get_status 暴露 recover_needs_user、前端失败态卡片 + resume 按钮、goal 前端投影化。

### 不建议做（08 号有理由的排除项）

- grok 三层 actor 模型、doom-loop 私有信号、goal 全链 classifier（过度设计）、cline 全量 shadow-git 快照（成本高）、opencode 全量事件溯源改造（现有事件版本化已领先）、grok leader-follower 多客户端（单宿主无需求）。
