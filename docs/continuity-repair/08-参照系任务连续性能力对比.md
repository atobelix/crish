## 0. 结论速览

1. 四个参照系解决「任务连续性」的路径完全不同：
   - **grok-build** 靠「按错误类型分级预算的三层恢复（sampler → turn → session actor）+ 目标系统（goal classifier→planner→orchestrator→stop_detector→tracker）+ 可续执行 workflow journal + fork/rewind/checkpoint」——恢复纵深最完整，也是本项目 C7 恢复阶梯的直接参照；
   - **pi** 靠「双层 while 循环（内层工具环 + 外层 follow-up 环）+ 宿主回调决策 + 会话级 checkpoint/resume」——续轮语义最简单，把「是否继续」的决策权完全交给宿主；
   - **opencode** 靠「事件溯源 + prompt 受理/提升两阶段 + `SessionExecution.resume(sessionID)` + revert/snapshot 回滚」，但其 **post-crash continuation recovery 明确 deferred 未实现**（specs/v2/session.md:104,153,165）；
   - **cline** 靠「task 即会话 + Git shadow 仓库 checkpoint（每次文件修改/命令执行存快照）+ 跨会话中断恢复」——任务连续性主要由文件系统快照而非执行引擎保证。
2. **本项目已把参照系最核心的机制写进设计**：错误分类 + 预算内重试（D5/D6/D7 裁决，对齐 grok/pi）、length 恢复阶梯、nudge 注入下一条用户消息（对齐 grok recovery 注入 user 消息）、安全点 + 三环输入队列（对齐 pi 分环）、C7 四级恢复阶梯（fork 三态 Verbatim/Summarized/New + Episode 预算 + 幂等 + 重启重排）。**最大缺口不是设计而是接线**：C7 恢复阶梯生产零接线（F2-08，recovery.rs:57-62 自述），`resume_subagent`/`kill_all` 命令面未接 IPC——子代理网络中断后系统没有任何一级自动恢复，只能靠主 agent 人肉重派。
3. 值得借鉴但本项目缺失：显式任务完成契约 **CompletionRequirement**（grok）、**provider 主备链 failover**（TS `fallback-chain` 资产未迁 Rust）、**TodoGate 轻量版**、**step 级 stationarity 检测**、**跨进程工具遗留 fail 语义**（opencode `failInterruptedTools`）、**子代理 checkpoint/断点续跑**、**workflow journal 可续执行**。
4. 不建议引入：grok 三层 actor 模型、doom-loop 服务端信号（xAI 私有协议）、goal 全链 classifier（与现有 goal 模式重叠）、pi 的「不自动续轮」与「无内置重试」、cline 全量 shadow-git 快照、opencode 全量事件溯源改造、grok leader-follower 多客户端架构、恢复 fork 的 worktree 快照。

## 1. 对比总表

### 1.1 总表（参照系 × 三个问题）

### 1.2 grok-build：恢复纵深最完整（本项目 C7 的直接参照）

**① provider 网络中断**：错误恢复按类型分级、各层独立预算，是 grok 的核心纪律（`xai-grok-sampler/src/retry.rs:144-251` 纯函数 `classify_error`；`actor/request_task.rs:81-312` 执行层）：
- 传输层预算 15 次（`DEFAULT_MAX_RETRIES`），429 独立阈值 2（retry.rs:43）；`RetryWithImageStrip`（413 剥图）、`RetryWithClientRebuild`（5xx 重建 HTTP/1.1 client 逃离连接池中毒）、`EmitToSession`（auth/加密内容上抛）；
- **`retry_only_before_output`**（request_task.rs:158-163）：一旦观察到输出 token，传输重试预算归零——系统性解决「流式重试导致内容重复」；
- doom-loop（服务端 `response.doom_loop_check` SSE 信号 + 客户端独立预算 + mid-stream abort + budget 耗尽 `disarm_abort` 接受当前响应）；
- turn 层 `CompactAndResubmit`（上下文压缩后 `continue` 重提交，turn.rs:2195-2198）、`RefreshAuthAndResubmit`（401 刷新 token 退避重试，sampler_turn.rs:916-956）。
**② 子任务失败恢复**：子代理跑独立 worktree，崩溃后按快照回收文件（`test_subagent_orphan_reconcile`，C2 调研 §7.3-16）；workspace 层 checkpoint（workspace/session/checkpoint + file_state）支撑 `/rewind` `/undo`（对话 + 文件双恢复）；`ProcessScope::enroll` 强制子进程登记（clippy `disallowed-methods` ban 裸 `Command::spawn`）；leader-follower IPC 重连指数退避（TUI 无限 / headless 5 次）+ 僵尸 leader 30s 驱逐 + 按版本收敛。
**③ 自动继续/goal**：三层防线治「AI 说做完其实没做完」——**TodoGate**（回合末仍有 pending todo 强制再轮，默认关 + fire 上限 2 防成本爆炸，turn.rs:2398-2451）、**stop_gate**（外部 hook 可 `KeepWorking` 注入合成 user message 强制继续，上限 8，stop_gate.rs:251-335）、**CompletionRequirement + auto-recovery**（agent 定义声明必备工具，未调用则按指数退避注入 `auto_recovery` prompt 重试，独立预算，turn.rs:1509-1647）；另有 goal 系统（goal_classifier 285KB 级）与带 journal 的可续执行 workflow 引擎（xai-workflow/journal.rs：JSONL、replay、resume_from、断尾修剪 `prune_trailing_host_error`）。

### 1.3 pi：续轮语义最简（「循环内 continue」范式的代表）

- 双层 while（`packages/agent/src/agent-loop.ts:170-272`）：内层 `hasMoreToolCalls = !terminate`——工具结果非 `terminate` 即继续，**不需要续轮决策**；外层 `getFollowUpMessages` 在 agent 本应停止时注入续轮消息。仅 `stopReason === "error" | "aborted"` 才退出循环（agent-loop.ts:196-200）——empty-response、工具错误都不终止。
- **续轮决策权完全交宿主**：pi 明确「AI 返回纯文本无工具调用时不自动续轮」（agent-loop.ts:263-268），续轮 = 外层回调返回 follow-up 消息。
- **恢复即快照**：compaction 产出结构化 checkpoint summary（`harness/compaction/compaction.ts:450`「another LLM will use to continue the work」）；git-checkpoint 扩展每 turn 存 stash 供 `/fork` 恢复（examples/extensions/git-checkpoint.ts）；会话 `/resume` `--session` 恢复（interactive-mode.ts:2815,4830；main.ts:369）。
- **length 截断恢复**：`failToolCallsFromTruncatedMessage`（agent-loop.ts:381-406）把截断的工具调用全部标记 error 并继续内层循环，让模型重新发起——不丢轮次。
- 局限：无子代理概念；provider 瞬时重试完全外包（`getApiKey` 动态解析是唯一凭证恢复手段，agent-loop.ts:305-306）。

### 1.4 opencode：事件溯源 + 显式 resume 语义（V2 的 post-crash recovery 明确未做）

- **resume 是显式语义而非自动恢复**：V2 `SessionExecution.resume(sessionID)` 只凭 Session ID 路由（specs/v2/session.md:42）；`prompt({ ..., resume? })` 三态——`resume=false` 仅受理入 durable `session_input` 队列不执行、省略/true 受理后排程执行（:13-26）。**prompt 受理与提升是两阶段事务**（`PromptAdmitted` → `Prompted`），事件溯源保证跨进程可续。
- **跨进程工具遗留处理**：本地工具先持久化记录再执行，运行中的工具跨进程遗留（`running` 状态）在下一轮开始前以 `Tool execution interrupted` 失败（session.md:50；runner/llm.ts:119-131）——**绝不静默重放副作用**。
- **V2 明确 deferred 的恢复面**（重要参照，说明成熟产品也未全做）：post-crash continuation recovery（session.md:104,165）、provider timeout/retry/watchdog 策略（:153）、durable failure reporting（specs/v2/todo.md:56-70）——要求 future slice 建模「explicit retry/abandon 决策 + bounded auto retry + retry budget/backoff + visible recovery status」，**不得假定存在包围的 durable execution identity**。
- **回滚面**：revert staging（session.revert.stage/clear/commit + snapshot 文件快照，revert.ts、config.ts:67）+ V1 retry/revert/status/summary/todo 模块（C1 调研 §2.1）。
- **任务跟踪**：todo 持久化事务（todo.ts）+ todowrite 工具；plan 模式（`.opencode/plans` 文件，plan→build 切换自动注入计划提示，reminders.ts:37-84）。

### 1.5 cline：任务连续性的「文件系统快照」路线

- **checkpoints 是核心**（core-workflows/checkpoints.mdx）：shadow git 仓库，每次文件修改/命令执行存完整文件状态快照；`Restore Files`（只回滚代码）与 `Restore Files & Task`（文件 + 对话一起回滚）两级；消息编辑后可「Restore All」到该点 checkpoint 再重发。
- **task 跨会话恢复**（task-management.mdx:149-159）：任务自动落盘 → 从历史打开 → 加载完整对话 → checkpoint 校验文件状态 → 感知中断继续。产品层面承诺「关掉编辑器几天后回来还能接上」。
- 无 provider 级重试文档、无子代理；plan-and-act 模式是人工流程而非引擎自动 gate。

## 3. 建议引入的机制（附理由与优先级）

> 优先级口径：P0 = 直接影响「网络中断后任务能否继续」的接线/恢复主干；P1 = 任务未完成自动继续的正确性机制；P2 = 防循环/可观测性增强。同权问题，仅按依赖顺序列号，不构成砍项依据。

## 4. 不建议引入的机制与理由

| # | 机制 | 来源 | 不适合理由 |
|---|---|---|---|
| 1 | **grok 三层 actor 模型**（ChatStateActor / SamplerActor / SessionActor + mpsc 命令） | grok | 该模型是 Rust 所有权下避免数据竞争的编译期需求；conex 会话循环是同步状态机 + SessionSequencer 序列号（C3：状态机可验证性领先），actor 化是重架构，收益（并发宽度）当前无场景；`03-恢复阶梯机制与接线现状.md` 已确认 conex 属单机单宿主 |
| 2 | **doom-loop 服务端信号**（`response.doom_loop_check` SSE） | grok（xAI 私有协议） | 多 provider 通用 agent 无法依赖私有信号；客户端的 stationarity 检测（§3 P2）已覆盖同症状 |
| 3 | **goal 全链 classifier**（goal_classifier 285KB / goal_planner / goal_strategist / goal_summarizer） | grok | 与 conex 已有 goal 模式（goal::rounds / assess::goal / stalled / max-rounds，orchestrator 裁决式）功能重叠；全链 classifier 是 grok 商业产品纵深（模型驱动生命周期），对 conex 的「任务/子代理」编排模型属过度设计。建议只补 CompletionRequirement + TodoGate（§3），不引入模型驱动的 goal 生命周期 |
| 4 | **pi 的「无内置瞬时重试」**（外包 streamFn）与「AI 停止不自动续轮」 | pi | conex 已有更优的分类重试（D5/D6/D7 + B2.7）；「不自动续轮」与用户对「goal 未完成自动继续」的诉求直接冲突——pi 是宿主驱动（每次调用方决定），conex 是常驻 daemon + 调度（必须自持续轮能力） |
| 5 | **cline 全量 shadow-git checkpoint**（每次文件修改/命令执行全仓快照） | cline | 桌面仓库规模下每工具快照成本高（cline 官方文档自述大仓性能问题，checkpoints.mdx:37）；conex 已有事件溯源 + 写模型 + 会话树回滚，checkpoint 的增量版（§3 P1 产出清单断点）足够；全量快照与「先落库再执行」纪律冲突 |
| 6 | **opencode 全量事件溯源改造**（V2 durable event + 投影器） | opencode | conex 已有 28 事件 + 信封 schemaVersion + changelog 门禁 + golden fixtures（C3 §2.2：事件版本化与兼容门禁显著领先 opencode）；全量溯源是「重写不推翻」的大迁移，当前收益不抵风险。可借鉴其单点：prompt 受理/提升两阶段 → 对应 conex 已有 input queue + 序列号语义 |
| 7 | **grok leader-follower 多客户端架构**（Unix socket IPC + 僵尸驱逐 + 版本收敛） | grok | conex 是 Tauri 进程内单宿主（Rust 引擎 + React 前端同进程），无「多形态共享一个 agent 状态」的需求；引入 leader 进程是纯开销 |
| 8 | **恢复 fork 的 worktree 快照隔离** | grok（子代理独立 worktree） | `REQ-D-现状分析.md:202` 已评估登记：单用户桌面场景收益有限，现有「写路径互斥 + 只读裁剪 + allowed_write_paths」已覆盖主要冲突；worktree 管理器 + 脏仓库检查 + 清理交互的工作量约 2 任务卡，P2 缓办 |

## 5. 结论

1. **参照系分工明确**：grok 提供「恢复纵深」（分级预算、CompletionRequirement、TodoGate、stationarity、journal、fork/checkpoint）；pi 提供「续轮语义」（循环内 continue、宿主回调、快照式恢复）；opencode 提供「resume 语义与副作用纪律」（显式 resume、先落库再执行、遗留工具显式 fail、revert/snapshot）；cline 提供「产品级任务连续性」（跨会话恢复 + 文件快照）。
2. **conex 的差距结构 = 设计已齐、接线未做 + 三个正确性机制缺失**：C7 四级阶梯（含 fork 三态继承、Episode 预算、幂等、重启重排）是本项目相对 grok 的最完整借鉴，但生产零接线使一切悬空（F2-08）；run 内 3 次重试是唯一生效的自动恢复。建议顺序：P0 接线（阶梯 1+2、主 run 半自动续跑、resume 命令面）→ P1 正确性（CompletionRequirement、provider 主备链、TodoGate、checkpoint 断点）→ P2 防循环与纪律（stationarity、遗留工具 fail、journal、watchdog 装配）。
3. **红线约束**（接线时必须保持）：12/5/1 RecursionGuard 与嵌套禁令只增不减（恢复路径 fork 必须显式走 spawn 守卫）；探索类文档配额每会话 1 份不绕过（fork 沿用同一 session_id 时配额语义自动延续）；测试资产门禁不受影响（recovery.rs 40+ 单测 + 4 集成测试文件直接作为接线回归面）。
