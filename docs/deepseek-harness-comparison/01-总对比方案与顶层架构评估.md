# Conex vs DeepSeek Harness 架构与工程实现总对比评估

> **战役工作区**：`docs/deepseek-harness-comparison/`  
> **对比双方**：
> - **Conex (Crish)**：Rust 原生引擎 + Tauri 2 桌面壳 + React 19 UI（`crates/*`, `apps/agent-workbench/src-tauri/`, `apps/crish-desktop/`）
> - **DeepSeek Harness (dsh)**：DeepSeek 开源智能体框架，TypeScript + Cordis 微内核插件系统 + Electron/Web/CLI 多宿主（`reference/deepseek-harness/packages/*`, `apps/*`）

---

## 一、综合结论：谁做得好？（直面裁判，不含糊）

如果用一句话定调：
> **“在插件微内核设计、事件溯源日志契约、协议标准化与通用框架生态抽象上，DeepSeek Harness 做得更好；而在端到端运行时性能、内存安全与开销、桌面端极致架构、细粒度状态机控制与安全工程落地深度上，Conex 做得更好。”**

两者代表了当前 AI Agent 框架/应用设计演进中的两个不同极值方向：

| 评估维度 | DeepSeek Harness (`dsh`) | Conex (`Crish`) | 胜出方与核心裁决 |
| :--- | :--- | :--- | :--- |
| **1. 架构可扩展性与解耦** | **Cordis 微内核（一切皆插件）**：时空可组合性，全组件无特权内核，支持运行时级联 patch | **Rust 静态模块 + Trait 解耦**：编译期强类型，硬边界 Crate，扩展需改 Rust 代码或经 Plugin-SDK 桥接 | 🏆 **DeepSeek Harness 胜出**（扩展抽象与生态解耦极其优雅） |
| **2. 运行时性能与资源开销** | **Node.js 运行时 + GC + 跨进程分帧 IPC**：进程内存占用较大（数百 MB），V8 存在垃圾回收与热点损耗 | **Rust 原生编译 + 零 GC + 零运行时开销**：单进程内存控制在数十 MB，CPU 瞬时峰值极低，无卡顿 | 🏆 **Conex 绝对统治**（代差级性能优势） |
| **3. Agent Loop 与状态机控制** | **基于 Promise/异步 Generator + 瀑布事件**：turn/step 结构清晰，但状态流转依赖事件级联，取消机制依靠 AbortSignal | **形式化穷举有限状态机 + L0-L3 控制总线**：`apply_transition` 状态全表穷举，严格安全点调度，无死锁设计 | 🏆 **Conex 胜出**（工程鲁棒性、可验证性与竞态免疫性极高） |
| **4. 会话持久化与事件模型** | **严格事件溯源（Event Sourcing）+ JSONL vN 迁移链**：模型所见即记录，Zstd 帧压缩，跨版本无损迁移 | **SQLite WAL + 全量快照 + 增量事件流**：原子事务强，读写池分离，崩溃恢复机制成熟 | ⚖️ **各有千秋**（dsh 在事件纯粹性与历史回放上更胜一筹；Conex 在结构化查询与 ACID 事务上更扎实） |
| **5. 工具管线与沙箱安全** | **OS 级三端内核沙箱（bwrap/Landlock/Seatbelt/Windows ACL）+ PTC 代码模式** | **三层 AST 语法树切分 + 动态审批门禁 + 防过度设计红线** | ⚖️ **各有千秋**（dsh 沙箱深度高，Conex 应用层拦截更轻量可控；dsh 独创 PTC 模式值得 Conex 深度借鉴） |
| **6. 桌面端宿主整合** | **Electron + 内置独立 Node 二进制 + 内置 pnpm 包管理**：多进程复杂管道通信，包体积与启动成本沉重 | **Tauri 2 壳 + 进程内引擎（In-Process）**：Rust 引擎与桌面壳同进程，直接原生 FFI/IPC，启动极快 | 🏆 **Conex 绝对统治**（桌面级架构与打包体验完全碾压） |
| **7. 协议开放与生态互通** | **原生支持 ACP (Agent Client Protocol) + 丰富 SDK (TS/Py) + LSP** | **私有 Tauri IPC + 专用 JSON 契约**：以桌面工作台为唯一核心目标 | 🏆 **DeepSeek Harness 胜出**（协议前瞻性与标准化显著领先） |

## 二、六大核心维度的深入代码级剖析

### 维度一：微内核与插件架构（Cordis vs Rust Crate）

- **DeepSeek Harness (`reference/deepseek-harness/packages/`)**：
  - 核心基座是 `Cordis` 框架（`packages/core/agent-loop/src/index.ts:8`）。
  - **核心设计**：任何组件（LLM 驱动器、Tools 注册表、Session 日志、Agent 循环本身）全都是挂在 `ctx` 上的 Service 插件（如 `ctx.tools`、`ctx.sessions`、`ctx.agents`）。
  - **优势**：
    1. 动态可替换性：不需要特权内核，随时可以在 `cordis.patch.yml` 中替换任何服务的实现；
    2. 副作用自动撤销：插件 unload 时，其注册的所有事件、工具、RPC 自动按时序回滚撤销。
  - **缺陷**：依赖 TypeScript 运行时的动态 Monkey-patch / Context 注入，在大型工程中缺乏编译期绝对的静态依赖检查，类型推断需要大量的 `declare module '@deepseek-ai/cordis'` 声明合并。

- **Conex (`crates/`)**：
  - 采用 **Cargo Workspace 多 Crate 强边界** 模式（24 个 crates）。
  - **核心设计**：`session-loop` 仅依赖 `conex-types`，通过 Trait（如 `ProviderCall`、`ApprovalGate`、`DeltaSink`）做显式注入（`crates/session-loop/src/loop/loop_runner.rs:28-47`）。
  - **优势**：
    1. 编译期零成本抽象，无动态查找开销；
    2. 依赖方向绝对单向，杜绝循环依赖（CI 硬门禁校验）。
  - **缺陷**：动态扩展能力弱。外部用户无法在不重新编译 Rust 二进制的前提下注入新的核心中间件（虽然有 TS 插件 SDK，但核心回路位于 Rust 内部）。

### 维度二：Agent 循环与控制流（ReactLoopAgent vs session-loop）

- **DeepSeek Harness (`packages/core/agent-loop/src/agent.ts`)**：
  - 采用 `ReactLoopAgent`（`agent.ts:72-120`）：
    - `phase`: `idle` | `maintenance` | `running`。
    - 瀑布事件流水线：`agent/pre-step` -> `step/start` -> `agent/request` -> `prepareCall` -> `agent/assistant-stream` -> `tools/execute` -> `step/end`。
    - 输入处理：`inbox.ts` 区分立即唤醒与惰性上下文注入。
  - **亮点**：设计了**不可变请求冻结**（`frozenMessages: WeakSet<Message>`，`agent.ts:94`），保证抵达模型历史的消息具有身份不可变性。
  - **局限**：状态控制相对粗粒度（只有 running/idle/maintenance），对并发控制、抢占取消主要依赖 `AbortController` 广播。

- **Conex (`crates/session-loop/`)**：
  - 采用极其硬核的**全状态转移表 + 安全点控制总线**：
    1. **显式穷举状态机**：`AgentSessionMachine`（`crates/session-loop/src/state.rs:1-98`），状态转移表（`apply_transition`）全表逐行穷举，未定义转移直接报 `TransitionError`，杜绝任何未定义行为；
    2. **四级控制总线（ControlBus）**：`crates/session-loop/src/control.rs:6-16`，L0 continue / L1 soft_inject / L2 cooperative_stop / L3 force_cancel，严格按优先级 `force_cancel > cooperative_stop > soft_inject` 汇聚；
    3. **安全点仲裁（SafePoint）**：`crates/session-loop/src/safe_point.rs:77-94`，协作停止不打断当前步骤执行，流式响应完成后平滑收敛，彻底杜绝强行 Abort 导致的脏状态；
    4. **附件与上下文防爆截断**：`attachment_budget.rs` 与 `attachment_truncation.rs`，在进入 Provider 之前进行精确到 Token 级的 Head-Tail 首尾截断钳制。
  - **裁决**：**Conex 在控制流的状态机严密性、并发安全性与异常防御上明显强于 DSH**。

### 维度三：持久化与事件溯源（SessionEvent/vN JSONL vs SQLite/Snapshot）

- **DeepSeek Harness (`packages/session/session-persistence-jsonl/`)**：
  - **核心设计**：纯粹的 **Event Sourcing（事件溯源）**。
  - **实现深度**：
    1. 磁盘上每个 Session 是独立的世代文件：`session.vN.jsonl.zstd`（`format.ts`, `zstd.ts`）；
    2. 采用 Checksummed Zstandard 帧，首帧严格限定为 Header，后续每一行都是不可变事件；
    3. 具有无损的单步跨版本迁移链：`v0 -> v1 -> v2`，未提交版本不覆盖，Worker 线程校验（`migration-verifier.ts`）；
    4. **模型可见即记录**（What is visible is logged）：模型所见的一切输入都能从事件流中 100% 确定性回放。
  - **优势**：架构纯粹度极高，无数据库锁，单文件归档与分享极其方便。

- **Conex (`crates/conex-db/`, `crates/orchestrator/src/restore.rs`)**：
  - **核心设计**：**SQLite WAL 关系数据库 + 全量快照 + 增量重放**。
  - **实现深度**：
    1. `conex-db` 实现组提交（`group_commit.rs`）、CAS GC（`cas_gc.rs`）、连接池分离；
    2. `restore.rs:1-35`：冷启动时扫描 in-flight 任务自动标记 `interrupted`（`run-interrupted` 审计事件），保证崩溃一致性；
    3. 双快照文件轮转（`StateSnapshot`，主文件 + `.prev` 备份），损坏时自动回退。
  - **裁决**：**DSH 在设计哲学上更优雅，事件溯源和 Zstd 压缩日志极其干净；Conex 在工程查询效率、并发 ACID 事务与崩溃一致性恢复上更成熟**。

### 维度四：工具执行、沙箱与安全体系（Tools/PTC/Sandboxing）

- **DeepSeek Harness**：
  - **两大杀手级特性**：
    1. **PTC (Program-The-Call / Code-mode tools)**（`packages/core/tools/src/ptc.ts:1-100`）：模型不再通过低效的单轮 JSON-RPC 频繁交互，而是直接输出一段 TypeScript 或 Python 异步代码（`run_code`），在宿主内一次性并行调用多工具（`await tools.read(...)`）并就地处理过滤，仅将清洗后的精炼输出回填上下文！这极大地节省了 Token 与多轮往返耗时；
    2. **真实 OS 级内核沙箱**（`packages/sandbox/sandbox-local/src/index.ts:1-100`）：Linux 下 `bwrap` + `Landlock`，macOS 下 `Seatbelt`，Windows 下基于 ACL 的受限令牌（Restricted Token）与随机独立 Temp 目录。
  - **局限**：系统级沙箱维护成本极高（macOS Seatbelt 易被 Apple 废弃，Windows 令牌受限于 NTFS 继承规则与 hardlinks 别名）。

- **Conex**：
  - **自研 AST 命令语法门禁**（`crates/conex-sandbox/src/lib.rs:25-95`）：
    1. 纯语义 AST 分析 + 正则红线清单 + 敏感操作审批（`CommandGatekeeper`）；
    2. 遵循反过度设计红线：明确放弃维护难度极大的操作系统级内核沙箱（Seatbelt/Seccomp），转向聚焦于开发者命令行为拦截、路径遍历防御与精确审批路由（`approval_router.rs`）。
  - **裁决**：**DSH 的 PTC 代码模式极其惊艳，是当前业界最前沿的工具交互范式，Conex 应立即学习借鉴；在沙箱方面，DSH 偏学术/防御纵深，Conex 偏工程实用与可维护性**。

### 维度五：多 Agent 协同与协议生态（Subagent / Teams / ACP）

- **DeepSeek Harness**：
  - 原生支持 **ACP (Agent Client Protocol)**（`packages/acp/acp/src/index.ts:1-80`），可通过标准 stdio JSON-RPC 与任何第三方 Agent 客户端互通；
  - 原生支持 **LSP 客户端工具**（`packages/lsp/tool-lsp/src/index.ts:1-60`），直接向模型提供精准代码跳转、引用查找与悬停签名；
  - 实验性 **Agent Teams**（`packages/experimental/agent-team/`）：包含成员花名册、看板（Taskboard）与邮箱（Mailbox）。
- **Conex**：
  - 针对子 Agent 实现了完善的**权限传递层与死锁防护**（`crates/session-loop/src/approval_router.rs:1-50`）：子代理权限向主 Agent 申请，主 Agent 被 wait 阻塞时智能转用户裁决，彻底杜绝死锁；
  - 遵循严格的单层嵌套纪律（`AGENTS.md` §2，禁止无限套娃），单会话管理稳定。
- **裁决**：**DSH 在协议通用性（ACP）与专业代码能力（LSP）上领先；Conex 在工程死锁规避与多 Agent 资源互斥（`WritePathRegistry`）上更扎实**。

---

### 维度六：桌面端宿主整合与性能（Tauri 2 vs Electron+Node）

- **DeepSeek Harness (`apps/desktop/`)**：
  - 采用 **Electron + 独立 Node.js 二进制 + 内置 pnpm 包管理器**（`main.ts:49-65`, `host-process.ts:1-40`）。
  - 架构极重：Electron 启动后先 fork 一个内嵌的 `node.exe`，该进程使用内置 `pnpm` 安装/加载插件，再通过文件描述符管道（`DESKTOP_REQUEST_PIPE_FD` / `RESPONSE_PIPE_FD`）建立自研分帧协议，最后映射为自定义 URL Scheme `dsh-app://` 给渲染进程。
  - **重大痛点**：安装包体积庞大（携带整套 Node + pnpm + Electron 运行环境），内存占用巨大，冷启动延迟高，跨进程序列化开销大。

- **Conex (`apps/agent-workbench/src-tauri/`)**：
  - 采用 **Tauri 2 壳 + 进程内 Rust 引擎（In-Process）+ React 19 UI**（`main.rs:1-35`）。
  - **核心优势**：
    1. 引擎与窗口宿主完全在同一个操作系统进程内运行；
    2. 无任何独立的 Node/daemon 进程，无需网络端口或复杂管道协议，直接通过 Tauri IPC 与内部事件流（`workbench-run-event`）通信；
    3. 打包体积小、启动毫秒级、内存占用极低（数十兆级别）；
    4. 针对流式渲染自研了 `conex-markdown`（pulldown-cmark + syntect + moka 缓存），彻底避免大模型高频输出下的 JS 主线程卡顿。
  - **裁决**：**在桌面端架构、启动体验、资源消耗与端到端性能上，Conex 拥有代差级的绝对优势，做得远比 DSH 更好**。

## 三、Conex 应当吸收借鉴的四大核心技术点

1. **PTC (Program-The-Call) 代码调用模式**：
   - 将现有零散的单工具调用模式升级，支持模型输出 Python/TS 脚本进行多工具链式聚合执行，显著压缩上下文轮次。
2. **结构化事件溯源日志与紧凑压缩**：
   - 借鉴 DSH 的 `AssistantStreamRecord`（带 Delta-time 时间戳的增量块记录）与 Zstd 帧压缩存储，实现极其精简的高保真历史回放。
3. **内置 LSP 精准代码感知**：
   - 借鉴 DSH 的 `tool-lsp`，为编程 Agent 提供基于语言服务器的定义跳转、引用分析工具，补充纯文本搜索的局限。
4. **ACP (Agent Client Protocol) 协议兼容**：
   - 评估支持 ACP 标准接口，让 Conex 的高能 Rust 内核可作为标准化 Agent 后端被外部生态调度。
