# 大文件打开卡死问题分析与性能瓶颈定义

## 一、问题背景与现场现象

在工作台（Crish Desktop / Agent Workbench）中，当用户打开几百 KB（例如 800 多 KB，包含常规源码、配置、未格式化 JSON、压缩代码或 Markdown）的文件时，界面会发生严重卡死甚至直接弹出浏览器“页面无响应（Page Unresponsive）”报错。

经过对系统底层与前端链路的排查，明确以下事实：
1. **不仅是 Markdown 文件卡死，所有格式（.ts, .js, .json, .rs, .txt, .sql, .log 等）均会卡死**：因为桌面端所有代码与文本查看入口最终全部收敛至同一个核心虚拟代码组件 `VirtualPlainCodeViewer.tsx`。
2. **卡死完全发生在前端（WebView2 / Chromium 的 JavaScript 主线程与渲染排版层），而不是 Rust 后端**：
   - Rust 后端（`apps/agent-workbench/src-tauri/src/fs_commands/read.rs`）使用流式缓冲，从磁盘读取 800KB 文件并完成 UTF-8 校验与行控制实测仅需 1～2 毫秒；
   - 真正耗尽 CPU、霸占事件循环的是前端主线程接管这 800KB（上万行、80 万字符）字符串后的同步计算。
3. **系统虽然使用了“虚拟化技术”，但这是一个“半吊子/伪虚拟化”**：
   - 它虽然只渲染了视口内的约 30 行 DOM，但在渲染前，主线程却把全量 80 万个字符同步执行了全量逐字符循环和前缀和计算，彻底抵消了虚拟滚动的性能优势。

## 二、关键链路与调用拓扑

用户打开文件的路径有以下几条：
1. **文件树 / 附件 / @提及点击代码文件**：
   `openFileViewerInSession` (`openTool.ts`) -> `FileViewerCard.tsx` -> `VirtualPlainCodeViewer.tsx`。
2. **文件树右侧面板代码预览**：
   `FilesCard.tsx` -> `FilePreview.tsx` -> `VirtualPlainCodeViewer.tsx`。

   `DiffCard.tsx` -> `changeFileCompareMode` (`useDiffData.ts`) -> `DiffCodeViewer.tsx` -> `VirtualPlainCodeViewer.tsx`。
4. **Markdown 文件打开**：
   `FilePreview.tsx` -> `useAsyncMarkdownHtml` -> `dangerouslySetInnerHTML`（若切到源码模式依然进入 `VirtualPlainCodeViewer.tsx`）。

涉及的关键源文件：

- `apps/agent-workbench/src-tauri/src/fs_commands/types.rs`（Rust 端 `ReadPolicy`）

## 三、五大致命性能瓶颈与根因剖析

### 1. `VirtualPlainCodeViewer.tsx` 全量逐字符同步循环与折行测算（CPU 100% 死锁）
- **代码位置**：`apps/crish-desktop/src/components/diff/VirtualPlainCodeViewer.tsx:136-145`
- **机理**：在计算折行行高的 `useMemo` 中，组件对全量所有行调用 `calcDisplayWidth(text)`。而 `calcDisplayWidth` 内部对每一个字符跑 `for` 循环和 `charCodeAt(i) > 255 ? 2 : 1`。
- **恶化**：800KB 文件包含约 800,000 个字符，主线程同步循环 80 万次。
- **雪崩**：`useMemo` 依赖 `[lines, totalLines, wordWrap, rowHeight, containerWidth, gutterWidth, charWidth]`。在组件挂载瞬间，`useLayoutEffect` 行高实测、探针测宽、`ResizeObserver` 宽度更新会连续触发 3～4 次重算。打开文件瞬间连续执行 3~4 轮 80 万次循环，JS 主线程完全卡死。

### 2. 默认强制全局自动换行（wordWrap = true）使 O(1) 虚拟滚动彻底失效
- **现状**：工业级编辑器（Monaco / VS Code）处理大文件时，行高为常数 $H$（如 22px），滚动起始行计算直接用除法 `Math.floor(scrollTop / H)`，计算耗时为 0.001ms（O(1)），无需扫描任何字符。
- **断层**：当前组件在 `FileViewerCard` 和 `FilePreview` 中默认全量开启 `wordWrap={true}`，导致所有大文件直接跌入 $O(N \times L)$ 的全量测算深渊。

### 3. 超长单行击穿虚拟滚动与 `highlight.js` 正则灾难性回溯
- **机理**：许多几百 KB 的文件是未格式化 JSON、压缩 JS（.min.js）、单行长 SQL 或包含巨大 path 的 SVG。行数可能只有 1～10 行。
- **断层**：虚拟滚动按行切片，认为“总共 1 行，在视口内，全量渲染”。
- **灾难**：视口内直接调用 `highlightCode(l.content, codeLang)`，将数十万甚至 80 万字符的单行丢进 `hljs.highlight(...)`。highlight.js 的正则状态机在超长未换行文本上发生严重回溯，单行解析耗时可达数秒，且生成带有几十万字符的单个 DOM 节点引发浏览器排版死锁。

### 4. 数据预备阶段的数组与对象爆炸触发 V8 GC 暂停
- **代码位置**：`VirtualPlainCodeViewer.tsx:55-60`
- **机理**：`content.split('\n').map((line, idx) => ({ num: idx + 1, content: line }))` 瞬间在 JS 堆中分配数万个独立包装对象。触发 V8 频繁 Full GC 暂停（Stop-the-world），造成严重界面定格。

### 5. 大 Markdown 文件的非虚拟化富文本 DOM 膨胀
- **代码位置**：`FilePreview.tsx:90-96`
- **机理**：800KB 的 Markdown 若以 render 模式打开，直接一次性转换为数万个 HTML 标签并插入 DOM，样式重排与图层合成（Recalculate Style & Layout）直接将浏览器渲染进程压垮。

## 四、方案设计任务要求与约束

请子 Agent 基于上述问题分析，**直接阅读上述相关源码**，给出最系统、最彻底的解决方案。

1. **禁止兼容、多轨或双轨设计**：必须是统一、清晰的单一真理源（SSOT）架构，严禁新老两套逻辑并存。

3. **禁止作弊与偷懒**：必须真正解决 800KB 乃至数 MB 文件在工作台中的秒开与丝滑滚动。

   - `DiffCard.perf.test.tsx` 性能门禁必须通过；
   - 前端类型检查 `npm run typecheck` 必须零报错。
5. **回归代码本身**：直接针对仓库既有代码给出具体重构设计，包含清晰的类/函数/接口修改方案。
