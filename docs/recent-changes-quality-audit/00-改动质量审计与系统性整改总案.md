## 二、P0 级缺陷（必须阻断）

### P0-1 · 移动端审批 Outbox 静默丢数据

- **位置**：`apps/crish-mobile/src/adapters/persistence/outboxPersist.ts:45-51`
- **机理**：整个离线审批队列以**单个 JSON 字符串**存入 Keychain：

  ```ts
  async save(items: readonly OutboxItem[]): Promise<void> {
    try {
      await this.driver.setItem(this.key, JSON.stringify(items));
    } catch (err) {
      console.warn('[OutboxPersist] save failed:', err);   // 吞掉
    }
  }
  ```

  队列容量上限为 `OUTBOX_MAX_ITEMS = 200`（`domain/data/outbox.ts:9`），单项含 `id`/`toolCallId`/`msgId`/`lastError` 等字段，满载约数十 KB。而 **iOS Keychain 单值上限约 2KB**（expo-secure-store 文档明确限制），`setItem` 必然抛错，被 `catch` 吞成一条 `console.warn`。
- **后果**：离线累积若干条审批决策后，**持久化静默失效**；应用重启则离线决策全部丢失，用户以为已提交的批准/拒绝再也不会送达。
- **为何测试没发现**：所有测试注入 `InMemorySecureStore`（`db/secureStore.ts:121`），无 2KB 限制，**永远不会复现**。这是典型的"脱水 Mock 自欺"。
- **整改方向**：Outbox 属"泄漏仅损失隐私"的数据，按项目自身分层原则（`db/secureStore.ts:3-4` 注释）**不应进 Keychain**。迁移至 SQLite `approval_queue` 表，一次性导入旧 Keychain 值后清除。

### P0-2 · 全部二级路由 `router.back()` 无栈退避，深链冷启动即困死

- **位置**：10 个路由文件，代表性三处——
  - `apps/crish-mobile/app/session/[sessionId].tsx:11`
  - `apps/crish-mobile/app/approval/[toolCallId].tsx:11`
  - `apps/crish-mobile/app/run/[runId].tsx:12`
- **机理**：全部直接 `onBack={() => router.back()}`，无任何 `canGoBack()` 判断。
- **后果**：推送通知或深链**冷启动**直达二级页时，导航栈深度为 1，`router.back()` 无操作。用户点返回按钮**界面毫无反应**，只能强杀应用。审批详情页是高危场景——收到审批推送点进来，处理完想返回却发现卡死。
- **整改方向**：统一封装 `useSafeBack()`：`canGoBack()` 为真则 `back()`，否则 `router.replace('/(tabs)')`。全仓 10 处替换为该 hook，杜绝散落重复实现。

### P0-3 · TLS accept 循环无握手超时（Slowloris DoS）

- **位置**：`apps/agent-workbench/src-tauri/src/server/tls_listener.rs:44`
- **机理**：

  ```rust
  let acceptor = self.acceptor.clone();
  match acceptor.accept(stream).await {   // 无 timeout
  ```

  单任务 accept 循环中直接 await TLS 握手，局域网内任意客户端建立 TCP 连接后不发送握手数据，即可**永久挂死**该循环。
- **后果**：桌面端多设备服务彻底失去响应——正常手机配对、事件推送全部连不进来。零成本拒绝服务。
- **整改方向**：`tokio::time::timeout(Duration::from_secs(5), acceptor.accept(stream))`，超时记 debug 日志并 continue（语义与现有"握手失败继续"分支一致）。

### P0-4 · `blob:` 协议逃逸 + Windows UNC 泄露 NetNTLMv2

- **位置**：`crates/conex-markdown/src/url_safety.rs:317-354`（`is_local_path_ref`）、`:270-309`（`file_url_to_path`）
- **机理 1（blob 逃逸）**：`is_local_path_ref("blob:payload.rs")` 的判定链为——非 http/mailto、非 `javascript|vbscript|data`（`JS_VBSCRIPT_DATA_RE` 未含 `blob`）、无 `://`、命中 `CODE_EXT_RE` 的 `.rs` 后缀 → **返回 true**，被当作合法本地文件渲染成特权 `<button class="md-path-link">`。攻击者用 `[点我](blob:payload.rs)` 即可让不可信 Markdown 生成可交互的本地路径链接。
- **机理 2（UNC 哈希泄露）**：`file_url_to_path` 对 `file://server/share` 在 Windows 下拼成 `\\server\share`（`:298-300`）。用户点击该链接，Windows 会向攻击者的 SMB 服务器发起 445 连接并**自动发送当前用户的 NetNTLMv2 哈希**——无需任何交互确认，即可离线破解或中继。
- **整改方向**：
  1. `JS_VBSCRIPT_DATA_RE` 增加 `blob:`；
  2. `file_url_to_path` 在 Windows 下遇 authority 形式（非盘符）**直接返回 `None`**，彻底拒绝 UNC；Unix 下同理拒绝 `//host` 形式。
  3. 补两个回归测试（现有 `:417-430` 测试只覆盖盘符与本地路径，恰好漏掉这两类）。

## 四、治理体系与重构脱节（本次最系统性的问题）

模块拆分完成，但**门禁脚本、测试、注释仍指向旧位置**，导致治理真空。这类问题不会让代码运行出错，但会让所有质量防线对拆分后的现实失明。

### G-1 · 命令注册门禁指向已搬迁的 `main.rs`（假红）

- **位置**：`scripts/check-provider-single-track.mjs:923-934`
- **事实**：脚本硬编码在 `apps/agent-workbench/src-tauri/src/main.rs` 里找 `command_registry![`，但该宏已迁至 `command_registry.rs:42`。脚本于是读出空集合，报"manifest 声明 170+ 条命令**全部未实装**"。
- **真相**：`main.rs:881` 的 `registration_surface_matches_manifest` 单测是**真正有效**的一致性守护（比对 `COMMAND_REGISTRY_NAMES` 与 manifest `registered=true` 集合），且随 `cargo test` 运行。门禁脚本只是过期。
- **性质**：**假红**。但危害真实——团队会习惯性忽略这条红，真出问题时也看不见。
- **附带真问题**：同脚本第二条断言报 `tauri-command-registry.ts` **缺 `multi_device_export_ca`**，这一条经核对**是真漂移**（详见 G-3）。
- **整改**：脚本改为读取 `command_registry.rs`；或者更彻底——**删除该脚本的重复扫描逻辑**，直接调用 Rust 单测作为唯一真源（符合"减少重复"）。

### G-2 · 吞错与 unwrap 基线新增未登记

- `check-swallowed-errors.mjs`：`conex-relay` 新增 **13 处** `let _ =`、`conex-run` **+1**。
- `check-unwrap-baseline.mjs`：`conex-md-ast` **+1 expect**、`conex-relay` **+1 expect**。
- **核对结论**：`conex-md-ast` 与 `conex-relay` 的新增 `expect` **全部位于 `#[cfg(test)]` 测试代码内**（如 `server.rs:748`、`hub.rs:182-204`），是基线统计口径把测试算进生产的问题，**不是真实缺陷**。`conex-relay` 的 13 处 `let _ =` 需逐一甄别（`handle_client_text` 里的 `tx.try_send` 失败即丢弃帧，这类是合理的背压语义）。
- **整改**：修正基线脚本的测试代码识别逻辑（这是根因）；对确属有意的 `let _ =` 显式登记并加注释说明为何可忽略。

### G-3 · 前端命令注册表真实缺失一条

- **位置**：`apps/agent-workbench/src/core/tauri-command-registry.ts`
- **事实**：manifest 与 Rust 注册面都有 `multi_device_export_ca`，前端注册表缺失。这是本次账号/多端改动新增命令后**第四处登记漏了一处**（项目铁律要求"四处同步"）。
- **整改**：补齐该条；并考虑把"四处同步"从纪律变成生成物（由 Rust manifest 生成前端注册表），从根上消除漏登记可能。

### G-4 · crate 体积基线回涨

- `main.rs` 898→904、`pty/session.rs` 880→896。
- **性质**：登记值即冻结上限，增长即失败。说明拆分过程中有代码被追加回已登记的入口文件。
- **整改**：继续把新增逻辑推向子模块，使入口文件回落到登记值以内（不建议上调基线，那等于放弃约束）。

### G-5 · 测试头注释与事实相反

- **位置**：`apps/crish-desktop/src/api/transport/command-contract-drift.test.ts:8-13`
- **事实**：注释大写"断言一当前状态：**红**，且不得修绿……已知断链 `catalog_get`/`catalog_refresh`"。实测该测试 **7/7 全绿**，且全仓已无 `invoke('catalog_get')` 真实调用（只剩注释与历史说明）。断链早已修复，注释未同步。
