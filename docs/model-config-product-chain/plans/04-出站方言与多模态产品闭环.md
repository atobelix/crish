## 0. 本维效果锁与诚实边界

### 0.1 效果锁（缺一不可）

用户在设置里为某模型写下：

```yaml
thinking:
  Low: "low"
  High: "ultra_wire_param"
  Max: "max"
compat:
  thinkingFormat: openai   # 或 deepseek / qwen / zai / anthropic / gemini
modalities:
  input: [text]            # 或 [text, image]
```

因果链在本维必须闭合到 **可检查的请求体**：

1. 主界面选 `High` → 出站 JSON 含 **`"ultra_wire_param"`**（不是 `"high"`，不是前缀表猜的）。
2. 选 `Max` → 出站含 yaml 值 `"max"`（禁止 `High|X-High|Max → "high"` 折叠）。
3. `thinkingFormat: deepseek` 且 base_url 是自建反代（URL **不含** `deepseek`）→ 出站是 `thinking: { type: "enabled" }`，不是 `reasoning_effort`。
4. URL **含** `deepseek` 但 yaml 声明 `protocol: openai/chat` + `thinkingFormat: openai` → 出站走 OpenAI 方言，不因 URL 绑架。
5. `modalities.input` 不含 `image` 的模型，若请求消息仍带 `image_url` / `ImageUrl` → **HTTP 发出之前** `InvalidRequest`，上游零字节。
6. 视觉模型带图 → 图进入对应协议的 wire（Chat `image_url` / Responses `input_image` / Anthropic `image` / Gemini `inline_data`），不得只发 `[图片附件]` 文本备注。

模块内「`assemble_thinking_dialect` 被 Chat builder 调用」「手工构造 `thinking_map: Some` 的单测绿」**不等于**本维完成。审计 12/13/21 已证伪这条叙事。

## 1. `request_options` 如何从 `live_catalog` 按 `(vendor, model)` 填字段

### 1.1 查找键（禁止跨厂商标识串线）

```
lookup_key = (EngineProviderConfig.provider_id, EngineProviderConfig.model)
entry      = live_catalog().lookup(provider_id, model)
```

- `provider_id` = yaml 树 `providers.<id>` 的键（S1 写入 `EngineProviderConfig`；**不是** `infer_reasoning_vendor(base_url, model)` 猜出来的 `"openai"`）。
- `model` = yaml `models[].id`（与 UI 当前模型同一字符串）。
- **禁止** `lookup_by_model_id` 跨供应商首个匹配（问题全集 15；审计 21 开放项 12）。
- `provider_id` 为空或 lookup 未命中 → **fail-closed 剖面**（§2.3），禁止再拿 URL / 模型前缀补一层。

S1 必须让 `EngineProviderConfig` 带上身份字段。本维消费，不另起配置源：

```text
EngineProviderConfig {
  provider_id: String,   // yaml providers 键 · S1 必填
  model: String,
  base_url, api_key, endpoint, stream, extra,  // 现状
  // 可选缓存：S1 也可直接灌 protocol / thinking_* ；
  // 本维仍以 live_catalog 现场 lookup 为单一热路径，避免配置对象与 yaml 快照分叉
}
```

`load_provider_endpoint`（`engine_provider.rs:81-98`）现状只读 `effective_api_base_url` / `effective_api_key` / `effective_model`，`extra` 恒空。S1 负责改加载源为 yaml 当前供应商；本维若发现 `provider_id` 仍空，**不得**用 URL 猜，按 §2.3 fail-closed。

### 1.2 单一 lookup 剖面（禁止四条出站各查一次各猜一次）

新增（建议放 `engine_provider/protocol.rs` 或 `engine_provider.rs` 私有函数，名字任选但全仓只准一个）：

```text
CatalogRequestProfile {
  provider_id: String,
  protocol: WireProtocol,                          // Model.protocol ≻ Provider.protocol ≻ openai/chat
  thinking_map: Option<IndexMap<String, String>>,  // TitleCase → wire；隐藏档（None）丢弃
  thinking_format: Option<ThinkingFormat>,         // yaml compat.thinkingFormat
  supports_image: bool,                            // modalities.input 含 "image"
  supports_reasoning: bool,                        // thinking_map 非空
  max_tokens_field: MaxTokensField,                // 仅 CompatSpec.max_tokens_field，否则协议默认
  supports_developer_role: bool,                   // 仅 CompatSpec，缺省 false
  reasoning_content: ReasoningContentMode,         // deepseek format 或显式声明 → Require，否则 Omit
}
```

填充算法（纯函数，无 IO 以外的 `live_catalog()` 读）：

1. `cat = live_catalog()`。本维热路径 **零调用** `bundled_catalog()`。
2. `entry = cat.lookup(provider_id, model)`。
3. **protocol**：`WireProtocol::from_raw_str(entry.mode)`（必须认全称 `openai/chat` / `openai/responses` / `anthropic/messages` / `google/generate-content`，与 `wire_protocol.rs:67-79` 已有解析对齐）≻ provider 级 protocol ≻ `WireProtocol::Chat`。禁止 `p.contains("responses")`（`catalog.rs:836`）。`google/interactions` 只作为 serde alias 在 S1 类型层单向归一，运行时枚举只有 `google/generate-content`。
4. **thinking_map**：`entry.thinking_tiers` → `IndexMap<String,String>`。键保持 yaml TitleCase（`High` 就是 `High`）。值 `Some(wire)` 收录，`None`（隐藏档）丢弃。空 map 与缺失同义 → `None`。
5. **thinking_format**：`entry.thinking_format` 按 yaml 词汇解析为 `catalog_types::ThinkingFormat`（`openai|deepseek|qwen|zai|anthropic|gemini`）。catalog.json 旧词 `reasoning_effort` / `thinking_budget` / `thinking_level` **不是**本维运行时词汇；S1 投影必须写成 yaml 枚举。解析失败 → `None`（进入 §2.3，不猜）。
6. **supports_image**：`entry.input_modalities` 含 `"image"`，或 S1 若已投影 `ModelSpec.modalities.input`。**禁止** `capabilities.image` 与 `modalities` 双读。lookup 未命中 → `false`。
7. **max_tokens_field**：仅 `CompatSpec.max_tokens_field`。缺省：Chat → `max_tokens`；Responses 体字段本就 `max_output_tokens`（builder 写死，不走 chat 字段名）；Anthropic → `max_tokens`；Gemini → `maxOutputTokens`。**禁止** `is_openai_o_series` / `url.contains("openai.com")`。
8. **supports_developer_role**：仅 `CompatSpec.supports_developer_role`，缺省 `false`。**禁止** `url.contains("openrouter")`。
9. **reasoning_content**：`thinking_format == DeepSeek` **或** yaml 显式 `compat` 声明 DeepSeek 工具循环强制键 → `Require`；否则 `Omit`。**禁止** `infer_reasoning_vendor(base_url, model)`（`engine_provider.rs:243-247` 现状）。

yaml → 目录投影（`catalog.rs:810-870`）若仍丢掉 `compat` / 把 `modalities` 读成 `{image:bool}` / 把 `mode` 写成无法 `from_raw_str` 的值，则 lookup 得到的剖面是空的，本维只能 fail-closed。这是 **S1 输出契约**；本维实现时若 S1 尚未把这些字段投影进 `live_catalog` 条目，允许在 `parse_yaml_to_catalog` 做 **补投影**（不新增第二解析器、不读 `catalog.json`）。补投影范围仅：`compat.thinkingFormat` / `max_tokens_field` / `supports_developer_role`、`modalities.input/output`、`protocol` 全称、`thinking` TitleCase 字典。禁止顺手改定价字段（S5）。

### 1.3 `request_options` 赋值合同

`HttpProviderCall::request_options`（`engine_provider.rs:141-163`）改为：

```text
let profile = catalog_request_profile(&self.config);
ChatCompletionsRequestOptions {
  model: Some(self.config.model.clone()),
  stream: Some(self.config.stream),
  max_tokens: request.max_tokens.map(u64::from),
  max_tokens_field: Some(profile.max_tokens_field),
  reasoning_effort: request.reasoning_effort.map(thinking::to_provider_effort),
  reasoning_content: Some(profile.reasoning_content),
  thinking_map: profile.thinking_map,
  thinking_format: profile.thinking_format,
  cache: build_cache_policy_from_profile(...),  // 见 §2.4；禁止再传 bundled_catalog + base_url 猜
  // 其余温度/top_p/tool_choice 维持缺省
}
```

**禁止**再写一组显式字段后靠 `..Default::default()` 把字典清掉。Rust 结构更新语法里，未写出的字段才会吃 Default——漏写 `thinking_map` 就是当前断点。

`request_body_for` 的 Anthropic / Gemini 枝（`engine_provider.rs:192-210`）必须走 **同一** `catalog_request_profile`，把 `thinking_map` / `thinking_format` / `reasoning_effort` 填进 `AnthropicRequestOptions` / `GeminiRequestOptions`（这两结构现状没有字典字段，本维补上）。禁止各枝再 `..Default`。

缓存：`build_cache_policy(Some(bundled_catalog()), Some(base_url), Some(model), ...)`（`engine_provider.rs:147-148`）改为读 profile 的显式 vendor/protocol/compat。无缓存声明 → `cache = None`（请求体不出现 cache 键），**禁止** `infer_cache_capability` URL 表。

### 1.4 思考档位校验改读同一剖面

`thinking.rs:70-102` `validate_reasoning_effort`：

- 数据源从 `describe_model(bundled_catalog(), catalog_vendor(config), ...)` 改为 `catalog_request_profile`。
- 白名单 = `thinking_map` 的 TitleCase 键，经 `ReasoningEffort::from_title_case` 归一后比较。**禁止** `e == provider_effort.as_str()` 拿小写 `"high"` 去撞 yaml `"High"`（当前会把合法档位在 HTTP 前误杀）。
- 无 `thinking` 字段 + 显式档位（非 off/auto）→ `InvalidRequest`（模型声明不支持思考）。省略 / off / auto → 放行且出站不带思考键。
- 显式档位不在字典 → `InvalidRequest`，不降级、不改写成 medium。

`catalog_vendor`（`protocol.rs:78-89`）生产路径删除。lookup 键是 `provider_id` 字符串，不是 `ReasoningVendor` 枚举。

## 2. 拆除生产 URL / 前缀启发式：显式 `protocol` + `compat.thinkingFormat`

### 2.1 决议公式（生产唯一）

```
EffectiveProtocol     = Model.protocol ≻ Provider.protocol ≻ openai/chat
ThinkingDialectFormat = yaml compat.thinkingFormat 映射表（§3.2）
                        ≻ （仅当协议已是 openai/chat 或 openai/responses 时的协议缺省）
                        ≻ 否则不注入思考键
thinking wire 值      = thinking_map[TitleCase(用户档位)]
                        缺失则不发送（validate 已拒或不下发）
```

任何模块严禁用下列信号改写上述结果：

- `url.contains("anthropic"|"deepseek"|"gemini"|"openai"|"openrouter"|…)`
- `model.starts_with("claude"|"gpt"|"o1"|"o3"|"gemini"|…)`
- `is_openai_o_series`
- `MODEL_SERIES_CAPABILITIES` / `infer_thinking_capability`
- `infer_reasoning_vendor` / `infer_vendor` / `infer_cache_capability`

### 2.2 映射表：`ThinkingFormat` → `ThinkingDialectFormat`

现状 `dialect.rs:172-182` 把 `Gemini => OpenAiEffort`、`Zai => DeepSeekNative`。本维修订：

| yaml `compat.thinkingFormat` | `ThinkingDialectFormat` | 出站形状（值来自 thinking_map） |
| --- | --- | --- |
| `openai` | Chat：`OpenAiEffort`；Responses：`OpenAiResponsesNested` | `reasoning_effort: "<wire>"` 或 `reasoning: { effort: "<wire>" }` |
| `deepseek` | `DeepSeekNative` | `thinking: { type: "enabled"|"disabled" }`；map 值若是 `enabled`/`disabled` 用字面，否则非 Off → enabled |
| `qwen` | `QwenBailianBoolean` | `enable_thinking: true|false`；map 值 `"true"`/`"false"`/`"1"`/`"0"` 解析，否则非 Off → true |
| `zai` | 独立变体或 DeepSeek 形（`type: "enable"` 按智谱字面） | 值来自 map，禁止再偷偷改成 OpenAI effort |
| `anthropic` | `AnthropicBudget` | `thinking: { type: "enabled", budget_tokens: N }`；map 值能 `parse::<u64>` 则用该数字（≥1024）；值为 `adaptive` → `{ type: "adaptive" }`；禁止 `effort_to_budget_tokens` / `to_anthropic_budget` 两套魔法刻度 |
| `gemini` | **新增** `GeminiThinkingConfig` | 并入 `generationConfig.thinkingConfig.thinkingLevel`（类型注释 SSOT：`catalog_types.rs:168`）。map 值原样（允许 `"HIGH"` / `"high"` / 用户自定义）。数值字符串则走 `thinkingBudget`。禁止 `thinking_to_gemini_thinking_level` 把 Max 折 `high` |

协议与 format 冲突（例如 `protocol: anthropic/messages` 但 `thinkingFormat: openai`）：**fail-closed**，不注入思考键，不按 URL 修好。产品 yaml 由 S2 编辑器约束一致；本维不提供「兼容修好」。

### 2.3 无字段时的仅有合法缺省

| 缺什么 | 合法行为 | 非法行为 |
| --- | --- | --- |
| `protocol` 模型级与供应商级都缺 | `openai/chat` | 按 URL 猜 anthropic/gemini/responses |
| `thinkingFormat` 缺，且协议是 `openai/chat` | `OpenAiEffort` | 前缀表、Max→high |
| `thinkingFormat` 缺，且协议是 `openai/responses` | `OpenAiResponsesNested` | 把 Anthropic/Gemini 折进 nested |
| `thinkingFormat` 缺，且协议是 anthropic / gemini | **不注入思考键**（fail-closed） | 猜 budget 表 / thinking_level 表 |
| `thinking` 字典缺 | 不注入思考键；显式档位在 validate 拒绝 | `to_openai_str` 折叠发送 |
| 字典有、当前 TitleCase 键缺 | validate 拒绝或本请求不带思考键 | 用 `to_openai_str` 当 map 的 fallback 键（`dialect.rs:224-228` 必须删这条 `or_else`） |
| lookup 未命中整个模型 | 协议 `openai/chat`；无思考键；`supports_image=false` | `lookup_by_model_id`、bundled 回落、URL 猜 |

`assemble_thinking_dialect` 在 `thinking_map` 为 `Some` 时：**只准**用 map 命中值；禁止 `.or_else(|| opts.effort.to_openai_str())`。map 为 `None` 时函数应返回 `(None, None)`（除 DeepSeek/Qwen 的显式 Off→disabled/false，且仅当 format 已显式声明）。

### 3.1 总调用序（`HttpProviderCall::stream`）

## 4. `ensure_content_modalities` 唯一挂载点

### 4.1 挂哪里

唯一调用点：`HttpProviderCall::stream`，位于 `validate_reasoning_effort` 之后、`request_body_for` / `client.post` 之前（`engine_provider.rs:282-296` 附近）。

审计 13 链路 C：前端 `streamSession.ts:226-227` 已下发 `content` / `hasImages`，但 `RunTaskOptions`（`run_launch.rs:209-258`）无这两字段，serde 丢弃；`user_message`（`timestamp.rs:53-64`）`metadata: None`。守卫若只看 `AgentMessage`，生产永远看不到 `ImageUrl`，纯文本+图「硬拒」测会被假绿（没有图可拒）。

| 文件 | 允许改动 |
| --- | --- |
| `run_launch.rs` `RunTaskOptions` | 增加 `content: Option<Value>`、`has_images: Option<bool>`（camelCase）。其它字段不动 |
| `timestamp.rs` `user_message` | 增加可选 `content_parts`，写入 `metadata.contentParts` |

## 5. 与 S3 的接口：档位与 modalities 从哪来

S4 **不改** Composer / Picker / `slashSendPreflight`（S3 文件域）。本维只声明消费合同。S3 未闭合时，本维实现可以先用 IPC 夹具灌 `reasoning_effort` + `content` 做出站测，但不得宣称用户侧增量完成。

### 5.1 思考档位

| 方向 | 契约 |
| --- | --- |
| S3 → 用户 | 胶囊选项 = 当前模型 yaml `thinking` 的 TitleCase 键；无 `thinking` 字段 → DOM 物理卸载，**不下发** `reasoningEffort` |
| S3 → 引擎 | `streamSession` / `core_run_task.reasoningEffort` = 规范小写 `minimal\|low\|medium\|high\|xhigh\|max`（现状 `streamSession.ts:106-112`）。本维 `to_provider_effort` 后再 `to_title_case` 查 map |
| 本维 → 出站 | `thinking_map[TitleCase]` 的 **值** 写入 JSON。用户选 High 且 yaml `High: "ultra_wire_param"` → 体里就是该字符串 |
| 禁止 | S3 用 `catalog.json` + 正则保底画出 low/medium/high；本维用 bundled 白名单把 yaml 自定义模型杀掉；本维读 LS `defaultThinkingLevel` |

yaml 额外自定义键（如 `CustomUltra: "ultra"`）超出 `ReasoningEffort` 枚举时：S3 负责把该 TitleCase 键渲染进胶囊；本维可在 `ProviderRequest` 增加可选 `reasoning_effort_key: Option<String>` **仅当 S3 已下发**。本战役用户增量以标准 TitleCase 键 + 自定义 **wire 值** 为完成线；自定义键是同一查找算法的自然延伸，不得用「枚举不够」把自定义 **值** 砍掉。

### 5.2 模态

| 方向 | 契约 |
| --- | --- |
| S3 → 用户 | `modalities.input` 不含 `image` → 加号/拖放/粘贴图不可用（L8 前半） |
| S3 → 引擎 | 视觉模型：`content` 为 OpenAI 形 parts（`type: image_url`）；`hasImages: true` |
| 本维 | `supports_image` 只来自 live yaml `modalities.input`；纯文本+图硬拒；视觉+图进四协议 wire |
| 禁止 | 本维或 S3 在 store 已有 `modalities` 时回落到 `isModelVisionSupported` 正则（审计 13：关了 image 的 `gpt-4o` 仍被正则放行） |

### 5.3 模型身份

S3 保证当前会话的 `(providerId, modelId)` 与 yaml 树一致（问题 15）。本维 lookup 用 `EngineProviderConfig.provider_id`（S1 从同一棵树灌入），不从消息里再猜。

### 5.4 与 S1 / S5 的接口（只规定，不实现对方）

- **S1**：`live_catalog()` 可调用、yaml 热更新后 `reload_live_catalog()` 被下一次 `stream` 看见；类型 `ThinkingFormat` / `ProtocolKind` / `ModalitiesSpec` 同构。本维是第一个热路径读者。
- **S5**：本维把 SSE usage 原样交给既有解析器；**不**调用 `PricingEngine`，不改费用 UI。cache 单价字段即使出现在 catalog 条目里，本维只用来决定 **是否发 cache 控制键**，不算钱。

## 13. 诚实（三原则）

**做了什么**：对照调度 L5–L8、问题全集、审计 12/13/21 与当前出站源码，写出本维可执行合同（lookup、去启发式、四轨调用序、唯一 modalities 挂载、S3 接口、验收体断言、兜底删除、问题映射）。

**没做**：未改产品源码；未跑测试；未 MCP 抓包；未写 S1/S2/S3/S5 实现。`catalog.rs` 投影缺口标为 S1 契约 + 本维可补，避免双解析器。

**额外发现（上报主控，不擅自扩面）**：

1. `thinking_tiers` 键 TitleCase vs `validate_reasoning_effort` 小写比较——即使灌上 live 也会误杀，本维 §1.4 已纳入。
2. Anthropic/Gemini builder 本身不投影图像块；只挂守卫不够，视觉出站仍断。已纳入 TU-5。
3. `engine_build.rs` 仍用 `bundled_catalog` + `infer_vendor` 做 TTL（S5 文件域）。本维提供 live lookup helper，不改结算。
4. `load_user_catalog_or_default` 失败回空目录（`catalog.rs:393-397`）。误接 live 后 yaml 损坏会让全部模型 fail-closed——这比继续用 bundled 更诚实，但 S1 应保证保存校验，避免空目录被当成「无思考、无图像」。

**对派单的建议**：S4 与 S5 可并行，但 `engine_provider.rs` 同文件不得两名 Agent 同时改；S5 不要动 `request_options`。S1 未交出 `provider_id` 时本维 fail-closed，不要临时 URL 猜「先打通」。
