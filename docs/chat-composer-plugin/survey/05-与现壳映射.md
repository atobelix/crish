# 05 · 与现壳映射（对话流像笔记扩展，不另造轨）

| 元数据 | 值 |
| --- | --- |
| **战役** | `docs/chat-composer-plugin/` |
| **定位** | 把参考仓能力钉到**现产品壳**：`App → BinaryTreeWorkspace → TreeLeafPanel → SlotOutlet + viewRegistry` |
| **效果锁** | 叙事可插拔；未挂插件 = 用户消息 ↔ 助手正文的线性对话；不复活已删插件轨 |

## 2. 推荐映射：主方案 A

用户口径：「正常就是直来直去」。调研边界：未挂叙事插件 = 线性用户↔助手正文。因此 **默认 renderer 已在 chat 叶**；插件只替换/装饰同一叶的流，不换 view id。

### 2.1 三案对照

| | A. chat 叶 renderer 插件（主推） | B. 新 tool view（像 note） | C. 拆多个 view |
| --- | --- | --- | --- |
| view id | **仍是 `chat`** | 新增 `conversation-flow`（或 `narrative`） | `thinking` / `purpose` / `artifacts` / `plan`… |
| 几何 | 留在 primary 叶；`isPrimary` 不变 | `category:'tool'` → **右坞**，用户要「打开叙事」 | 对话被撕成多叶 |
| 未激活 | `ChatMessageList` 线性直出 | chat 叶仍线性，但叙事躲在坞里，等于第二套对话 | 更碎 |
| 激活 | `activateConversationFlow` 换流内 renderer | `registerView` + UnitChrome 新按钮 | 一堆打开命令 |
| 像笔记吗 | **像激活/注销外形**；不像「再占一槽」（笔记必须占槽） | 外形最像 note，语义错：叙事不是旁路工具 | 最不像 |
| 与 `flow-dag` | 不抢名、不抢槽 | 易与已有「编排图」tool 混淆 | 更混 |

### 2.2 为何不是 B

1. **primary 几何锁死对话位置。** `isPrimary('chat')` 为真才走 UnitChrome / conversation unit；tool 走右坞（`TreeLeafPanel.tsx:151,191-198`；`adapterShapeStoreOps.ts:356-358`）。把叙事做成 note 那样的 tool，用户默认看见的仍是旧线性 `ChatCard`，叙事变成「再开一栏」——违反「直来直去」。
2. **打开面会被逼出来。** note 需要 `UnitChrome` 按钮，是因为纸面不是 chat。叙事若也要按钮，产品就多了一条「打开对话流」手势。用户要的是同一条对话变好看，不是新码头。
3. **`setChatMainSurface('flow')` 不是合法逃逸。** 类型只有 `chat | scheduled`（`layoutStore.ts:109`）。B 若走表面切换，等于复活已禁的 `setChatMainSurface('note')` 写法。
4. **11 内置名单不能涨。** 即便 B 用 `registerView` 当扩展（不写进 `registerBuiltInViews`），仍会污染 `getToolViews()` / 工具条，和 `flow-dag`（拓扑图）抢「flow」心智。

B 唯一合理的残片：若将来做「只读会话回放」独立窗，可以再谈 auxiliary view。那不是本战役默认产品句。

### 2.3 为何不是 C

- 思考 / 目的 / 工具 / 产物 / 权限是 **同一条助手回合的叙事层级**（`CONVERSATION_FLOW_SPEC.md:38-45`），不是可分屏的独立工具。
- C 会强迫 `openToolInSession` 几何、多叶虚拟化、跨叶滚动同步，把「扫读一条流」做成 IDE。规格非目标写明「不在对话流里做完整 IDE 侧栏」（同文档 `:58-62`）。
- 权限条规格就在 **composer 上方**，本来就不是 view。
- 产物点开文件应复用已有 `file-viewer` / `note`，不必为每种 chip 长一个 view。

### 2.4 A 怎么挂（像笔记，但不新增 view id）

外形对齐 `activateNotePaper`：

```
main.tsx startup
  registerBuiltInViews(...)          // 11 内核，chat factory = ChatCard
  activateNotePaper()?               // 可选；tool 槽
  activateConversationFlow()?        // 可选；不 register 新 id
```

**默认（未调用 / deactivate 后）**：`ChatCard.chatDocFlow` 仍渲染 `ChatMessageList`（用户 ↔ 助手正文 + 现有折叠工具栈）。Purpose 树、计划时间线、参考仓轨 **不是**必选项。

**激活**：`apps/crish-desktop/src/extensions/conversation-flow/activate.ts`（尚不存在，只定形）：

1. **禁止** `registerView({ id: 'conversation-flow' | 'narrative' | 'thinking' … })`
2. **禁止**改 `registerBuiltInViews` / `builtinViewFactories` 名单
3. **允许**用现有 `slotCore.registerSingle` / `registerChain`（`SlotCore.ts:19-36,78+`）往 **chat 叶内部**登记 stream renderer；`SlotTypes.ts:3-6` 已写明可用 declaration merging 扩槽
4. 建议槽名（实现轮再落，本调研只锁语义）：`workspace.chat.stream`（single）。`ChatCard` 在现 `ChatMessageList` 位置改挂 `SlotOutlet`，`fallback={ChatMessageList}`。未登记则线性；登记则叙事组件吃同一份 `sessionId` + 消息投影
5. 对称 `deactivateConversationFlow()` 卸槽 → 线性立刻回来
6. **官方捆绑默认关**（与 note 相反）。note 默认开，否则用户摸不到纸面；叙事默认开会把 Purpose 树变成必选项，违反调研边界条 2。测 / 设置用 `setOfficialConversationFlowActivateForTesting` 对称 note

次选（更糙，不推荐作主路径）：`viewRegistry.registerView({ id: 'chat', category: 'primary', component: DecoratedChatCard })` 覆盖同 id。`registerView` 同 id 会先卸旧 keyed 槽再挂新（`ViewRegistry.ts:55-70`），`isPrimary` 因硬前缀仍为真。问题：`registerBuiltInViews` 有一次性旗标（`:58-60`）；覆盖整颗 `ChatCard` 会把 composer / 空态 / scheduled 绑进叙事包，边界脏。只在「SlotOutlet 端口还没开」的临时桥使用，终态仍应是叶内 stream 槽。

**A 不是新插件运行时。** 只用已有 `registerView` 家族之外的 **已有** `slotCore.register*` 注销函数，或叶内一个 `currentDeactivate`（与 `activate.ts:9-10,49-57` 同构）。禁止为此再写 `PluginRegistry`。

## 5. 包边界建议（对照笔记三包，不叠床架屋）

笔记需要三包是因为 **纸面是编辑器**：契约（Flavour/Diff/Intent）→ kit（Viewport/IME/Selection）→ paper（chrome/叶子/PaperList），桌面只宿主。对话叙事是 **投影 + 呈现**，没有 DocSession、没有 IME 状态机、没有行高图。抄三层 = 叠床架屋。

推荐 **1 个实现包 + 1 个桌面激活模块**（需要时再拆契约，现在不要）：

```
packages/conversation-flow          @crish/conversation-flow
  projector/     纯函数：消息/工具事件 → 叙事树（对齐 reference flow-projector）
  components/    Purpose / Thinking / Action / Subagent / Artifact 呈现（无 zustand / 无 Tauri）
```
