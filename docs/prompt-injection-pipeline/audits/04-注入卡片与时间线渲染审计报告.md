### 2. VirtualScrollManager 的高度估算与 Virtualizer 120Hz 滚动性能

#### 2.1 性能与算法优秀实践
- **Fenwick Tree（树状数组）原语**：[`VirtualScrollManager.ts:404-418`](file:///c:/Software/conex/apps/crish-desktop/src/api/VirtualScrollManager.ts#L404-L418) 采用 `Float64Array` 实现前缀和计算与增量更新，单点 DOM 测量回写 `setActual` 复杂度为硬性 $O(\log N)$，区间求和与二分查找行定位为 $O(\log^2 N)$，无任何全量前缀遍历。
- **rAF 批量合并与防抖**：[`useVirtualScroll.ts:150-170`](file:///c:/Software/conex/apps/crish-desktop/src/hooks/useVirtualScroll.ts#L150-L170) 通过 `pendingActualRef` 收集微任务内的多次 ResizeObserver 回调，经由单帧 `requestAnimationFrame` 集中冲刷；并在冲刷前做同值跳过（`cur === height`）和微小差值判定（`Math.abs(delta) > 0.0001`），只有真实尺寸变动才触发 `setActualTick`，极大降低了 120Hz 高刷新率屏幕下的 GC 压力与重渲染。
- **防视口塌陷过渡保护**：[`VirtualScrollManager.invalidateActual`](file:///c:/Software/conex/apps/crish-desktop/src/api/VirtualScrollManager.ts#L258-L267) 作废高度时，将 `estimated` 锚定在上一次测量值而非无条件倒退至 `120px` 兜底，避免了重新测量期间的大幅抖动。

#### 2.2 发现缺陷与隐患（Defects & Gaps）

##### 🚨 [MAJOR] 缺陷 2.1：`MessageVirtualizer.tsx` 的 `ResizeObserver` 缺少滚动依赖，且存在已卸载 DOM 强引用泄漏
- **代码位置**：[`apps/crish-desktop/src/components/chat-message-list/MessageVirtualizer.tsx:85-120`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-message-list/MessageVirtualizer.tsx#L85-L120)
- **证据**：
  ```tsx
  useEffect(() => {
    const container = containerRef.current;
    if (!container) return;
    if (!roRef.current) {
      roRef.current = new ResizeObserver((entries) => { ... });
    }
    const ro = roRef.current;
    const observed = observedRowsRef.current;
    const current = new Set<Element>(
      Array.from(container.querySelectorAll('[data-vindex]'))
    );
    for (const row of current) {
      if (!observed.has(row)) {
        ro.observe(row);
        observed.add(row);
      }
    }
    for (const row of observed) {
      if (!current.has(row)) {
        ro.unobserve(row);
        observed.delete(row);
      }
    }
  }, [msgIds, containerRef, setActual]); // ❌ 依赖项仅为 msgIds
  ```
- **影响分析**：
  1. **滚动进入视口的新行不会被监听**：当用户在长列表中滚动时，`msgIds` 序列不变，`useEffect` **根本不会重新触发**！因此，随视口滑入并初次挂载到 DOM 的元素节点，永远不会执行 `ro.observe(row)`。这些消息行的高度将永远滞留在 `fallbackHeight: 120px`，直到消息总列表发生变动。这是造成长列表滚动错位、跳闪和白屏的直接根因。
  2. **内存强引用脱水节点**：`observedRowsRef` 保持对已滚出视口并被 React unmount 的历史 DOM 元素的强引用。由于 effect 未随渲染更新，`observed.delete(row)` 未被执行，导致脱水 DOM 树无法被 V8 垃圾回收，构成内存泄漏。

##### ⚠️ [MINOR] 缺陷 2.2：注入卡片高度估算模型未接线，且未感知展开态
- **代码位置**：[`apps/crish-desktop/src/api/VirtualScrollManager.ts:39-41, 223-225`](file:///c:/Software/conex/apps/crish-desktop/src/api/VirtualScrollManager.ts#L39-L41)
- **证据**：
  1. `VirtualScrollManager.ts:40` 中对注入卡片估算为紧凑单行 `h += 40`。但若卡片 `content.length <= 160`（默认展开）或包含 Diff 跳转、错误信息时，展开高度实际在 `120px ~ 420px` 之间，40px 与真实 DOM 存在高达 300px 的测量阶跃。
  2. 经全仓检索，`estimateTimelineMessageHeight` 仅在 `VirtualScrollManager.ts` 内部被 `manager.estimateHeight(msg)` 封装，在 `MessageVirtualizer.tsx` 与 `useVirtualScroll.ts` 中**从未被实际调用注入 Fenwick 树**！所有新消息在渲染前均统一采用静态 `fallbackHeight = 120`，高度细化估算模型在运行时处于闲置状态。

### 4. 刷新重载时内联注入载荷还原的鲁棒性

#### 4.1 C1 持久化方案与还原机制核验
- **架构考量**：依据 00-总方案 §三.5 裁决，为避免在 Rust 引擎层对 SQLite `session_messages` 表引入高风险 DDL 改动（新增 `injections_json` 列），设计了 C1 方案：在前端写入时将完整 `MessageContextInjection` 载荷直接内联到 `blocks` 的 `context_injection` 块中（[`sessionInjectionMount.ts:74-79`](file:///c:/Software/conex/apps/crish-desktop/src/store/sessionInjectionMount.ts#L74-L79)）。
- **重载回退链条**：[`timelineNormalizer.ts:122-123`](file:///c:/Software/conex/apps/crish-desktop/src/api/tool-presentation/timelineNormalizer.ts#L122-L123) 通过 `const inj = (b.id ? injectionsById.get(b.id) : undefined) || b.injection;` 实现防御性回退。经单测与代码追踪验证，在页面刷新后从 SQLite 重新反序列化出 `blocks` 时，内联载荷能够准确还原为 `TimelineInjectionItem`，有效防御了历史消息卡片空转丢失。

- **代码位置**：[`apps/crish-desktop/src/api/tool-presentation/timelineCache.ts:28-63`](file:///c:/Software/conex/apps/crish-desktop/src/api/tool-presentation/timelineCache.ts#L28-L63)

  该路径提取的 `cwd` 字符串未经任何安全过滤或项目根路径校验，便直接经 `registerWorkflowFromGrillMe` -> `createWorkflow` 作为 IPC 参数提交给 Rust 后台。若模型受提示词注入攻击（Prompt Injection）输出包含敏感路径（例如 `C:\Windows\System32`、`C:\Users\...\Desktop` 或跨目录 `../../`）的配置，用户点击确认卡片后，该定时工作流将获得越权目录的执行权限。必须在此处强制增加 `pathWithinWorkspace(cwd, activeProjectFolder)` 防护，或在缺失安全域时清空 `cwd` 强制使用引擎会话隔离目录。

##### 🚨 [MAJOR] 缺陷 5.2：卡片确认状态仅存储于组件本地状态，虚拟滚动回收后可被二次点击重复创建
- **代码位置**：[`apps/crish-desktop/src/components/chat-injection/WorkflowConfirmCard.tsx:45-72`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-injection/WorkflowConfirmCard.tsx#L45-L72)
- **现象描述**：
  确认成功状态 `result: 'ok'` 仅由 `useState<'idle' | 'ok' | 'error'>('idle')` 维持在组件内存中。
  1. 一旦用户在长对话中上下滚动，虚拟滚动组件（`MessageVirtualizer`）将该卡片卸载（unmount）；
  2. 当用户滚回该消息时，组件重新挂载，`result` 被重新初始化为 `'idle'`；
  3. 确认按钮重新恢复为高亮可点击的「确认创建并激活」；
  4. 用户再次点击将重复向引擎注册同名或同内容的重复定时任务，或引发引擎重名报错。应将已确认状态持久化在消息 block 或与任务状态池绑定联动。

##### ⚠️ [MINOR] 缺陷 5.3：流式输出过程中的围栏闪烁问题
- **代码位置**：[`apps/crish-desktop/src/components/chat-message/MessageContent.tsx:361-368`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-message/MessageContent.tsx#L361-L368)
- **现象描述**：
  流式生成期间，助手消息直接由 `StreamingMarkdownView` 渲染未完成的原始 `streamText`。在模型开始吐出 ````json:workflow-payload```` 到完全闭合围栏之间，用户会看到一段原始的 JSON 代码块在屏幕上逐字打印；当最后三个反引号输出完成且消息转入 stable 时，JSON 代码块瞬间消失并被 `WorkflowConfirmCard` 取代，视觉上存在明显的「内容突跳（Flash/Jank）」。

## 三、架构全景与反过度设计审查（对齐 §8 铁律）

1. **依赖纯度**：`chat-injection` 组件群仅依赖 `react`、`lucide-react` 及本仓 `ui` 组件库，无外引第三方重型模态或状态机库，代码结构紧凑。
2. **零反向依赖验证**：组件群通过 props 与组合根通信，未反向 import 业务上层 store 或命令处理器，保持单向数据流与高内聚。
3. **性能基座稳固**：核心虚拟滚动基于 Fenwick Tree（树状数组），拒绝了全局遍历与重排补丁；单帧更新经 rAF 严格限频，满足 120Hz 丝滑滚动标准。
4. **无冗余数据抽象**：未新建冗余的注入卡片中间表，严格遵循 C1 决策复用既有 `blocks` 内联存储，对底层 SQLite 保持零破坏升级。
