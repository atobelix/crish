## 一、目标与领域概念定义

### 1.1 核心使命与架构范式重塑

在 Conex / Crish 既有架构中，用户选取的代码、Git 差异、终端报错、长文本文件以及多模态图片的处理长期存在**「通道割裂、暴力拼接、全局单键竞争、内存失控与 Token 盲盒」**五大结构性断层：
1. **通道分裂与暗流拼接**：文本附件通过 `[附件] \n\n --- file ---` 裸拼注入用户输入尾部，图片通过 `ChatContentPart` 下发，批注通过全局数组注入，缺乏统一的元数据管理与结构化隔离；
2. **全局共享状态污染**：`fileAnnotations.ts` 的全局内存变量 `pendingAnnotations` 与 `contextStatePending.ts` 的全局单键 `crish_pending_context_state_v1` 导致跨会话严重串扰与消费丢失；
3. **缺乏防爆保护与截断机制**：长日志与大文本采用粗暴的末尾截断（Tail Truncation），丢失最关键的底部报错/Panic 摘要；巨型 Base64 塞入 IPC 载荷导致 UI 渲染卡顿；
4. **Token 盲盒与预算超限**：缺乏发送前的轻量精确 Token 估算，极易击穿模型上下文窗口引发下游 API `400/413` 报错。

**本详案核心使命**：基于用户最新核心裁决（“不用隐式通道，直接在对话流显示为类似工具调用效果的可见注入卡片，无需 AI 主动调用，由系统在动作触发时直接注入”），构建涵盖 **代码选区、Diff 快照、终端日志、结构化文件与多模态图片** 5 大维度的统一上下文引用标准化体系，实现全链路单一真相源（SSOT）、四级防爆保护、精准 Token 调度、XML CDATA 防注入隔离与高质感可见卡片渲染。

### 1.2 五大标准化领域概念模型

系统将所有注入到对话上下文中的引用实体划分为 **5 大标准维度**，每个维度具备强类型元数据定义、专属截断规则与视觉呈现规范：

#### 1. 代码选区引用 (`CodeSnippet`)
- **场景**：用户在编辑器中选中局部代码点击「引用到对话」、快捷键导入，或外部工具检索出的关键代码段。
- **核心元数据**：
  - `filePath`: 工作区相对路径（规范化斜杠）；
  - `startLine` / `endLine`: 1-indexed 起止行号；
  - `commitSha`: 捕获时刻工作区 HEAD Commit SHA（用于外部文件变动时的行号重映射）；
  - `languageId`: 代码语言标识（如 `rust`、`typescript`、`python`）；
  - `symbolScope`: 选区所属函数/结构体名（如 `handlePrepareTurn`）；
  - `surroundingContext`: 选区上下各扩展 2 行的上下文窥探（用于消除歧义）。

#### 2. Diff 对比快照 (`DiffSnapshot`)
- **场景**：用户评审代码变更、Git 暂存区比对，或工具执行修改前后的差异确认。
- **核心元数据**：
  - `diffKind`: 差异类型枚举（`workingTree` | `staged` | `commit` | `threeWayConflict`）；
  - `filePath`: 受影响的文件路径；
  - `additions` / `deletions`: 新增与删除行数统计；
  - `hunks`: Unified Diff 块列表（包含 `@@ -a,b +c,d @@` 范围与差异行）；
  - `baseRef` / `targetRef`: 对比的基准与目标引用。

#### 3. 终端报错与运行日志 (`TerminalLog`)
- **场景**：用户在内置终端执行命令失败后一键发送分析，或后台测试工具（如 `cargo test`）输出的诊断流。
- **核心元数据**：
  - `command`: 触发的完整命令行指令（如 `cargo test -p session-loop`）；
  - `cwd`: 执行命令所在的工作目录；
  - `exitCode`: 进程退出状态码（如 `101`、`1`、`0` 或信号终止）；
  - `durationMs`: 执行耗时（毫秒）；
  - `streamKind`: 日志流类型（`stdout` | `stderr` | `mixed`）；
  - `stackTraces`: 解析出的结构化错误堆栈列表（文件名、报错行、错误简述）；
  - `ansiPreserved`: 是否包含 ANSI 颜色代码（下发 LLM 时强制清洗，UI 渲染时可选 ANSI 高亮）。

#### 4. 结构化文件与虚拟文档 (`FileDocument`)
- **场景**：用户拖拽、文件选择器或 `@file` 提及挂载源码、Markdown、JSON、配置文件或内存虚拟文档。
- **核心元数据**：
  - `filePath`: 文件绝对路径或虚拟工作区 URI；
  - `fileName`: 文件展示名称；
  - `fileSizeBytes`: 原始字节大小；
  - `mimeType`: MIME 类型；
  - `isVirtual`: 是否为内存未落盘虚拟文档；
  - `contentEncoding`: 编码格式（`utf-8` 或 `external-ref`）。

#### 5. 多模态图像与视觉资产 (`MultimodalImage`)
- **场景**：用户粘贴系统截图、拖拽设计稿（PNG/JPG/WebP）、UI 报错截图或架构白板图。
- **核心元数据**：
  - `imageFormat`: 图片格式（`png` | `jpeg` | `webp` | `gif` | `svg`）；
  - `dimensions`: 像素尺寸 `{ width: number, height: number }`；
  - `detailLevel`: 视觉解析精度（`auto` | `low` | `high`）；
  - `storageRef`: 存储分流引用（`< 256KB` 采用 `inlineDataUrl`；`≥ 256KB` 采用 `localBlobPath`）；
  - `ocrText`: 预处理 OCR 提取文本（可选，供降级模型使用）。

### 1.3 对话流可见卡片与工具调用同构设计（WYSIWYG & Tool-Call Analogy）

依据用户最新裁决，系统上下文注入彻底告别隐式黑盒，确立**「被动直接注入（Passive Direct Injection）+ 工具调用卡片同构」**模型：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ 📎 代码选区: prepare_turn.rs (L45-L60)                          [Rust] [⎘ 复制] │
├─────────────────────────────────────────────────────────────────────────────┤
│ 45 │ let held: Vec<AgentMessage> = {                                        │
│ 46 │     let mut messages = Vec::new();                                     │
│ 47 │     while let Some(message) = state.input_queue.dequeue() {            │
│ 48 │         messages.push(message);                                        │
│ 49 │     }                                                                  │
│    │ ... (已折叠其余 11 行，点击展开)                                       │
├─────────────────────────────────────────────────────────────────────────────┤
│ 📍 commit: 3f8a91b • 约 184 Tokens • [↗ 在编辑器中定位]                     │
└─────────────────────────────────────────────────────────────────────────────┘
```

- **同构表现**：注入卡片在前端采用与 `ToolCard` (`CompactToolRow`) 统一的视觉设计规范（圆角容器、柔和 HSLA 边框、分类图标槽位、状态胶囊、Token 统计指示器与默认折叠面板）；
- **被动直接注入机制**：
  - **常规工具调用**：LLM 发起 `tool_call` $\rightarrow$ 宿主执行 $\rightarrow$ 宿主返回 `tool_result`；
  - **被动上下文注入**：用户动作或系统事件触发 $\rightarrow$ 宿主直接构造 `ContextAttachmentCard` 插入时间线 $\rightarrow$ LLM 在下一轮推理中作为标准上下文自然读取（无需模型浪费轮次发起工具请求）。

### 1.4 单一真相源（SSOT）与双向投影架构（Dual-Projection）

```mermaid
flowchart TB
    subgraph InputCapture [上下文捕获层 (UI / System Event)]
        A1[代码选区 Editor Selection] --> AT[统一上下文实体 ContextAttachment]
        A2[Git Diff 比较快照] --> AT
        A3[终端报错与运行日志] --> AT
        A4[多模态图片与截图] --> AT
        A5[文件与虚拟文档] --> AT
    end

    subgraph CoreEngine [引擎中枢：契约、防爆截断与 Token 预算]
        AT --> IPC[Tauri IPC: core_run_task / run_launch]
        IPC --> MT[L1~L3 守卫: Head-Tail 截断 & 大文件分流]
        MT --> TE[加权特征 Token 预估 & ContextBudget 钳制]
        TE --> SSOT[(单一真相源 ContextAttachmentPayload)]
    end

    subgraph DualProjection [双向无损投影]
        SSOT -->|UI 渲染投影| UIP[前端富交互卡片系统<br/>- Shiki/Prism 语法高亮<br/>- Unified Diff 差异视图<br/>- 终端日志控制台<br/>- 缩略图与 Lightbox 全屏预览]
        SSOT -->|Wire 消费投影| LLMP[LLM 提示词无损注入<br/>- XML CDATA 沙箱化隔离标签<br/>- 结构化 Multimodal Parts<br/>- 显式元数据属性注入<br/>- Anthropic Ephemeral 缓存断点]
    end
```

- **单一真相源（SSOT）**：所有附件与引用实体均由统一的 `ContextAttachmentPayload` 描述，消除多套数据模型并行维护的冗余；
- **UI 渲染投影（UI Projection）**：面向用户，提供高可读性、可折叠、语法高亮与一键跳转编辑器的交互卡片；
- **Wire 消费投影（Wire Projection）**：面向 LLM，生成具备严格 XML CDATA 隔离、显式元数据属性与结构化 Multimodal Parts 的标准载荷。

```rust
    pub end_line: u32,
```

### 2.2 核心算法一：Head-Tail 40/60 智能首尾保留截断算法

#### 1. 算法背景与设计机理
传统简单的尾部截断（Tail Truncation）在处理日志与代码时具有毁灭性：
- 终端报错与编译日志中，**最关键的报错概要与 Panic 调用栈通常出现在最底部**，若直接截断尾部，模型将完全看不到错误原因；
- 代码与 Diff 中，头部包含函数签名与关键导包，尾部包含核心返回与边界处理。

因此，算法采用 **头部保留 40% 配额 + 尾部保留 60% 配额**，中间注入清晰可解释的结构化省略标记。

#### 2. Rust 实现 (`crates/session-loop/src/attachment_truncation.rs` - 新增)

```rust
//! crates/session-loop/src/attachment_truncation.rs
//! 智能首尾保留截断算法实现

use conex_types::attachment::TruncationInfo;

/// 首尾智能保留截断
/// - raw_text: 原始文本
/// - max_chars: 最大允许字符数
/// - kind_label: 实体类型名称（用于警告展示）
pub fn truncate_text_head_tail(
    raw_text: &str,
    max_chars: usize,
    kind_label: &str,
) -> (String, TruncationInfo) {
    let total_chars = raw_text.chars().count();
    let total_lines = raw_text.lines().count();

    if total_chars <= max_chars {
        return (
            raw_text.to_string(),
            TruncationInfo {
                is_truncated: false,
                original_size_bytes: raw_text.len(),
                injected_size_bytes: raw_text.len(),
                original_lines: total_lines,
                injected_lines: total_lines,
                truncation_strategy: "none".to_string(),
            },
        );
    }

    // 头部保留 40%，尾部保留 60%
    let head_limit = (max_chars as f64 * 0.40) as usize;
    let tail_limit = max_chars - head_limit;

    let head_str: String = raw_text.chars().take(head_limit).collect();
    let tail_str: String = raw_text.chars().skip(total_chars - tail_limit).collect();

    let omitted_chars = total_chars - head_limit - tail_limit;
    let omitted_lines = total_lines.saturating_sub(
        head_str.lines().count() + tail_str.lines().count()
    );

    let separator = format!(
        "\n\n... [! 警告：{}内容过长已触发安全截断：已省略中间 {} 行 / {} 字符] ...\n\n",
        kind_label, omitted_lines, omitted_chars
    );

    let mut result = String::with_capacity(head_str.len() + separator.len() + tail_str.len());
    result.push_str(&head_str);
    result.push_str(&separator);
    result.push_str(&tail_str);

    let injected_lines = result.lines().count();
    let injected_bytes = result.len();

    (
        result,
        TruncationInfo {
            is_truncated: true,
            original_size_bytes: raw_text.len(),
            injected_size_bytes: injected_bytes,
            original_lines: total_lines,
            injected_lines,
            truncation_strategy: "head-tail".to_string(),
        },
    )
}
```

#### 3. TypeScript 同构实现 (`apps/crish-desktop/src/utils/attachmentTruncation.ts` - 新增)

```typescript
/**
 * apps/crish-desktop/src/utils/attachmentTruncation.ts
 * 前端首尾保留截断算法（与 Rust 端 100% 对齐）
 */
import type { TruncationInfo } from '../types/attachmentContracts';

export function truncateTextHeadTail(
  rawText: string,
  maxChars: number,
  kindLabel: string
): { text: string; truncation: TruncationInfo } {
  const totalChars = Array.from(rawText).length;
  const totalLines = rawText.split('\n').length;

  if (totalChars <= maxChars) {
    return {
      text: rawText,
      truncation: {
        isTruncated: false,
        originalSizeBytes: new TextEncoder().encode(rawText).length,
        injectedSizeBytes: new TextEncoder().encode(rawText).length,
        originalLines: totalLines,
        injectedLines: totalLines,
        truncationStrategy: 'none',
      },
    };
  }

  const headLimit = Math.floor(maxChars * 0.4);
  const tailLimit = maxChars - headLimit;

  const chars = Array.from(rawText);
  const headStr = chars.slice(0, headLimit).join('');
  const tailStr = chars.slice(totalChars - tailLimit).join('');

  const omittedChars = totalChars - headLimit - tailLimit;
  const headLines = headStr.split('\n').length;
  const tailLines = tailStr.split('\n').length;
  const omittedLines = Math.max(0, totalLines - headLines - tailLines);

  const separator = `\n\n... [! 警告：${kindLabel}内容过长已触发安全截断：已省略中间 ${omittedLines} 行 / ${omittedChars} 字符] ...\n\n`;
  const resultText = `${headStr}${separator}${tailStr}`;

  return {
    text: resultText,
    truncation: {
      isTruncated: true,
      originalSizeBytes: new TextEncoder().encode(rawText).length,
      injectedSizeBytes: new TextEncoder().encode(resultText).length,
      originalLines: totalLines,
      injectedLines: resultText.split('\n').length,
      truncationStrategy: 'head-tail',
    },
  };
}
```

### 2.3 核心算法二：加权特征 Token 估算器与多模态 Vision Token 标准化计算

#### 1. 文本与代码加权特征启发式估算器
为了在前端与 Rust 引擎中以低于 0.1ms 的极低延迟完成 Token 预估，完全避免引入 50MB+ 的 WASM 词表库，采用**加权特征分析算法**：

$$\text{Estimated Tokens} = \lceil N_{\text{ascii}} \times 0.28 + N_{\text{cjk}} \times 0.70 + N_{\text{symbols}} \times 0.45 + N_{\text{lines}} \times 0.1 \rceil$$

```typescript
// apps/crish-desktop/src/utils/tokenEstimator.ts

export function estimateTextTokens(text: string): number {
  if (!text) return 0;
  let asciiCount = 0;
  let cjkCount = 0;
  let symbolCount = 0;
  let lineCount = 0;

  for (let i = 0; i < text.length; i++) {
    const code = text.charCodeAt(i);
    if (code === 10) {
      lineCount++;
    } else if ((code >= 65 && code <= 90) || (code >= 97 && code <= 122) || (code >= 48 && code <= 57) || code === 32) {
      asciiCount++;
    } else if (code >= 0x4e00 && code <= 0x9fff) {
      cjkCount++;
    } else {
      symbolCount++;
    }
  }

  const tokens = Math.ceil(
    asciiCount * 0.28 + cjkCount * 0.70 + symbolCount * 0.45 + lineCount * 0.1
  );
  return Math.max(1, tokens);
}
```

#### 2. 多模态 Vision Token 标准化计算引擎
统一建模主流模型（OpenAI GPT-4o、Anthropic Claude 3.5、Google Gemini 1.5）的官方图片 Token 计算公式：

```typescript
// apps/crish-desktop/src/utils/visionTokenEstimator.ts

export type VisionProvider = 'openai' | 'anthropic' | 'gemini';

export function estimateVisionTokens(
  width: number,
  height: number,
  detail: 'auto' | 'low' | 'high' = 'auto',
  provider: VisionProvider = 'anthropic'
): number {
  if (width <= 0 || height <= 0) return 0;

  if (provider === 'openai') {
    if (detail === 'low') return 85;
    // OpenAI High Detail 模式计算
    let w = width;
    let h = height;
    if (w > 2048 || h > 2048) {
      const scale = 2048 / Math.max(w, h);
      w = Math.round(w * scale);
      h = Math.round(h * scale);
    }
    const minSide = Math.min(w, h);
    if (minSide > 768) {
      const scale = 768 / minSide;
      w = Math.round(w * scale);
      h = Math.round(h * scale);
    }
    const tilesX = Math.ceil(w / 512);
    const tilesY = Math.ceil(h / 512);
    return tilesX * tilesY * 170 + 85;
  }

  if (provider === 'anthropic') {
    // Claude 3.5 Sonnet / Opus 面积公式
    let w = width;
    let h = height;
    if (w > 1568 || h > 1568 || w * h > 1_600_000) {
      const scale = Math.min(1568 / Math.max(w, h), Math.sqrt(1_600_000 / (w * h)));
      w = Math.round(w * scale);
      h = Math.round(h * scale);
    }
    return Math.ceil((w * h) / 750);
  }

  // Gemini 1.5 瓦片公式
  const tilesX = Math.ceil(width / 384);
  const tilesY = Math.ceil(height / 384);
  return tilesX * tilesY * 258;
}
```

### 2.5 动态上下文预算调度（`ContextBudget` 联动与二次裁剪）

在 `crates/session-loop/src/loop/handlers/prepare_turn.rs` 中，附件注入深度联动 `ContextBudget`，严格计算最大可用附件配额：

$$\text{Max Attachments Budget} = \text{ContextWindow} - \text{ReserveTokens} - \text{SafetyTokens} - \text{HistoryTokens} - \text{PromptTokens}$$

```rust
// crates/session-loop/src/attachment_budget.rs

use conex_types::attachment::ContextAttachmentPayload;
use crate::attachment_truncation::truncate_text_head_tail;

pub fn clamp_attachments_to_budget(
    mut attachments: Vec<ContextAttachmentPayload>,
    available_tokens: u32,
) -> (Vec<ContextAttachmentPayload>, Vec<String>) {
    let mut total_tokens = 0u32;
    let mut accepted = Vec::new();
    let mut warnings = Vec::new();

    for mut att in attachments {
        if total_tokens + att.estimated_tokens <= available_tokens {
            total_tokens += att.estimated_tokens;
            accepted.push(att);
        } else {
            // 尝试进行二次深度截断
            if let Some(text) = &att.text_content {
                let remaining_budget = available_tokens.saturating_sub(total_tokens);
                if remaining_budget >= 300 {
                    let max_chars = (remaining_budget as f64 * 3.2) as usize;
                    let (truncated_text, trunc_info) = truncate_text_head_tail(
                        text,
                        max_chars,
                        &att.title,
                    );
                    att.text_content = Some(truncated_text);
                    att.estimated_tokens = remaining_budget;
                    att.truncation = trunc_info;
                    total_tokens += remaining_budget;
                    accepted.push(att);
                    continue;
                }
            }
            warnings.push(format!(
                "附件「{}」因超出剩余上下文预算（{} Tokens）被安全移除",
                att.title, available_tokens
            ));
        }
    }

    (accepted, warnings)
}
```

### 2.6 IPC 大载荷分流机制与本地附件缓存生命周期

#### 1. 阈值分流设计

## 六、验收标准（功能验收 + 负产出验收断言）

依据 `AGENTS.md` §7.1「立体验证纪律」，本方案落地必须严格满足以下功能验收与负产出刚性断言：

### 6.1 核心功能验收标准

1. **五维附件无损捕获与呈现**：
   - 选区引用：在编辑器选中代码后点击引用，时间线生成 `<CodeSnippetCard />`，正确展示起止行号与高亮，点击「在编辑器中定位」可精确定位；
   - Diff 快照：工作区改动生成 `<DiffSnapshotCard />`，Unified Diff 红绿双栏/单栏折叠展示清晰；
   - 终端日志：终端报错生成 `<TerminalLogCard />`，正确呈现命令、退出码与 Panic 堆栈高亮；
   - 多模态图片：粘贴图片生成 `<MultimodalImageCard />`，展示尺寸与 Detail 档位，点击可 Lightbox 全屏放大。
2. **Head-Tail 智能截断正确性**：
   - 模拟 10,000 行超长终端日志，截断后严格保留头部 40% 与尾部 60% 字符配额，中间包含显式省略标记；
   - 尾部致命错误（Panic）100% 完整保留，不发生丢失。
3. **Token 估算高精度与预算钳制**：
   - 文本与代码启发式估算误差在 $\pm 5\%$ 以内；
   - 模拟附件总 Token 超过 `ContextBudget` 阈值，预算裁剪器能安全进行二次截断或优雅告警移除，绝不引发下游 API `400/413` 报错。
4. **XML CDATA 沙箱与防注入**：
   - 构造包含 `</context_attachment>`、`]]>` 与 ANSI 转义字符的恶意文本，Wire 输出经清洗与安全包裹后不发生标签逃逸。
5. **Prompt Caching 命中验证**：
   - 当附件总 Token $> 1024$ 时，下发请求自动在尾部 Part 挂载 `cache_control: { type: "ephemeral" }`，连续轮次首字延迟与计费显著降低。

### 6.2 负产出刚性验收断言（Invariant Assertions）

```
========================================================================================
                                 负产出刚性验收断言
========================================================================================
 [INV-1] 零隐式字符串拼接断言 (Zero Ad-hoc Splicing Invariant)
         - 检索全仓代码，禁止出现 promptAttachBlock = `\n\n[附件]...` 或 annBlock 暴力拼接入
           modelText 的行为；所有上下文必须通过 ContextAttachmentPayload 强类型下发。

 [INV-2] 零全局单键残留断言 (Zero Global Key Invariant)
         - 全局搜索 crish_pending_context_state_v1 与 pendingAnnotations 变量，匹配项
           必须为 0；所有状态感知与批注必须严格绑定 targetSessionId。

 [INV-3] 零 IPC 内存爆破断言 (Zero IPC Memory Bloat Invariant)
         - 单个体积 >= 256KB 的大文件或图片绝对禁止以 Base64 内联塞入 IPC 载荷；必须
           强制走 .conex/attachments/ 本地缓存绝对路径分流。

 [INV-4] 零重型 WASM 词表依赖断言 (Zero Heavy Tokenizer Invariant)
         - 严禁在前端或 session-loop 中引入任何 WASM BPE / Tiktoken 巨型二进制包。

 [INV-5] 零 --no-verify 作弊断言 (Zero Gate Bypass Invariant)
         - 严禁使用 --no-verify 绕过 Git Hook 门禁；所有 Lint 与测试必须刚性通过。
========================================================================================
```
