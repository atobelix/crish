## 一、执行摘要与评审结论

### 1.1 评审背景与核心定性

在 `docs/prompt-injection-pipeline/independent-plans/` 下，6 份独立方案针对系统提示词（01）、统一注入通道（02）、前端交互（03）、Rust 底层协议（04）、多维附件（05）以及定时任务模式（06）展开了详尽设计。

然而，在方案编制过程中，方案 01、02、03、04、06 普遍沿袭了**「隐式系统提示词通道（Implicit System Prompt Channel）」**与**「隐式用户前缀（Invisible User Prefix）」**的历史惯性思维：
- 将定时任务编排助手（Workflow Grill-Me）、目标模式迭代状态（Goal Mode）、方案对齐（Grill-Me）、技能指引（Skills）、运行时纠偏（Steering Nudges）等动态上下文，均设计为通过后台隐式拼接到 System Prompt 或静默插入请求前缀中；
- 为了管理这些隐式注入段，方案 02 与 03 设计了极其复杂的 8 级槽位分配、单次消费状态机（`Ephemeral` 状态转移、SQLite 临时表管理、GC 垃圾回收）以及四层 XML 语义嵌套合并；
- **核心断层**：用户在前端对话界面中**完全看不到**当前注入了哪些指令、模型为何会突然进入某种行为模式，产生“黑盒感”与“盲盒体验”；同时，前端与后端维护了两套割裂的状态管理管道，增加了严重的认知负荷与过度设计复杂度。

### 1.2 评审总体裁决：范式彻底重构

针对这一深层架构断层，用户作出了明确裁决：

> **“不用隐式通道了，这种注入应该是在上下文里面的，所以正常在对话流里面显示为对应的注入显示即可，当做工具调用的效果一样就行，只是这个不用ai主动调用，是直接注入的。”**

**总体评审结论**：
1. **彻底废除隐式系统提示词通道**：除了系统不变的核心基座（L0 身份定义、OS 运行环境契约、基础工具协议）保留在静态 System Prompt 中外，**所有动态模式助手、运行期指令纠偏、技能指引、上下文附件与编排引导，一律停止隐式拼接**。
2. **确立「对话流上下文可见注入卡片（Visible Context Injection Card）」为单一真理模型**：
   - **所见即所得（WYSIWYG）**：所有注入项作为一等公民消息（`ContextInjectionMessage`）进入对话时间线，在 UI 上渲染为清晰直观的可见卡片；
   - **工具调用同构（Tool-Call Analogy）**：视觉与语义表现与「工具调用结果卡片（Tool Result Card）」完全一致，具备图标、状态标签、参数展示与折叠视窗；
   - **被动直接注入（Passive Direct Injection）**：无需模型发起 `tool_call`，由前端/系统在特定事件触发时（如点击助手模式、粘贴代码选区、触发定时任务）直接作为上下文消息注入时间线；
   - **Agent 无损读取**：在下发给 LLM 时，注入卡片按时间戳自然排布在 `messages` 消息流中，模型按时间线先后因果关系直接读取，既具备完整的上下文注意力，又极大简化了 Rust 引擎的装配逻辑与缓存机制。

## 二、用户最新核心裁决深度解构与架构范式转移

### 2.1 从「隐式通道黑盒」到「对话流可见注入（WYSIWYG）」

通过对照表清晰展示架构范式的本质跃迁：

```
【旧架构：隐式多层通道 (Implicit Blackbox)】
用户操作 ──> 隐式注入通道 (Slot 0..7) ──> 后台拼接 XML/字符串 ──> 注入底层 System Prompt
                                                                      │
UI 对话流：用户完全看不见 ◄─────────────────────────────────────────────┴─── 仅模型可见 (黑盒漂移)

──────────────────────────────────────────────────────────────────────────────────────────

【新架构：对话流可见注入 (WYSIWYG Visible Context Injection)】
用户操作 / 系统事件
       │
       ▼
【对话流上下文可见注入卡片 (Visible Context Injection Card)】
       ├─► [UI 渲染投影]：时间线内渲染为精美卡片 (类似工具结果卡，支持折叠、高亮、状态徽章)
       └─► [LLM 消费投影]：作为消息时间线中的标准消息实体进入 messages 数组 (所见即所知)
```

| 架构维度 | 历史隐式通道方案（旧设计） | 对话流上下文可见注入卡片（新设计） | 架构收益 |
| :--- | :--- | :--- | :--- |
| **用户可见性** | 完全不可见（隐式黑盒）或散落在输入框草稿中 | 对话流时间线中清晰可见，具备独立卡片、状态与折叠面板 | 用户知情权与确定性 100% 提升 |
| **注入位置** | 汇入顶层 `system_prompt` 或用户文本 ad-hoc 头部 | 作为标准消息实体（`role: "system"` 或专用 context part）按时间戳嵌入 `messages` 历史流 | 符合真实时间因果序，注意力更集中 |
| **生命周期管理** | 复杂的 `Persistent` / `Ephemeral` / `Reactive` 状态机与 GC 机制 | 天然随会话时间线持久化，消费即留痕，历史回放完全保真 | 消除 300+ 行临时状态转移逻辑 |
| **Prompt Caching** | 动态注入频繁修改 System Prompt 前缀，导致 KV 缓存失效 | System Prompt 保持绝对静态（高缓存命中率），注入卡片在 messages 流中享受增量前缀缓存 | 提升缓存命中率，降低 API 成本 |
| **调试与审计** | 难以排查某轮请求时生效的具体 Prompt（需查日志） | 直观查看聊天记录即可完全复原注入内容与时序 | 审计与可解释性极大提升 |

### 2.2 核心类比机制：类似工具调用效果，直接被动注入（Passive Direct Injection）

用户明确指出：**“当做工具调用的效果一样就行，只是这个不用ai主动调用，是直接注入的。”**

#### 1. 与常规工具调用（Active Tool Call）的同构与差异

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                    常规工具调用 (Active Tool Invocation)                      │
│  1. LLM 发出 tool_call 请求 ──> 2. 宿主执行工具 ──> 3. 宿主返回 tool_result 卡片 │
└──────────────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────────────┐
│             可见上下文直接注入 (Passive Direct Context Injection)             │
│  1. 用户触发 / 系统事件发生 ──> 2. 宿主直接构造注入卡片 ──> 3. 立即呈现在时间线    │
│  4. LLM 在下一轮推理中直接感知该卡片内容 (无需先请求再返回)                     │
└──────────────────────────────────────────────────────────────────────────────┘
```

- **视觉呈现同构**：注入卡片在前端采用与 `ToolCard` 一致的设计语言（圆角边框、柔和背景色、图标标识、折叠展开抽屉、复制与操作按钮）；
- **执行机制差异**：
  - **常规工具**：LLM $\rightarrow$ `tool_use` $\rightarrow$ Host Execute $\rightarrow$ `tool_result`；
  - **被动注入**：Trigger (User/Event) $\rightarrow$ Host Generate $\rightarrow$ Timeline Insert $\rightarrow$ LLM Read。

---

### 2.3 对话流时间线（Timeline）与消息模型重塑

在统一消息时间线中，注入卡片作为一种特化消息类型（`ContextInjectionMessage`）存在，与普通的用户消息、助手消息并列：

```
[Session Messages Timeline]
 ├── Turn 1: UserMessage ("请帮我审查代码")
 ├── Turn 1: AssistantMessage ("好的，我开始检查...")
 ├── Turn 2: ContextInjectionCard [⚡ 模式注入: 定时任务编排助手 (Workflow Grill-Me)]
 │             ├─ 目标: 每日代码健康巡检
 │             ├─ 约束: 严格四要素对齐，不盲目写代码
 │             └─ 状态: 激活中
 ├── Turn 2: AssistantMessage (Grill-Me 追问: "请问您希望每天几点执行？")
 ├── Turn 3: UserMessage ("每天早上 9:00")
 └── Turn 3: ContextInjectionCard [📎 上下文引用: prepare_turn.rs (L45-L60)]
```

## 三、6 份独立方案逐份深度审查与重构指导

### 3.1 方案 01（系统提示词组织与维护方案）审查与重构

- **原方案定位**：`01-系统提示词组织与维护方案.md`
- **核心问题诊断**：
  1. **层级膨胀与过度拼接**：原方案设计了 L0~L5 六层装配体系（`base` $\rightarrow$ `environment` $\rightarrow$ `mode` $\rightarrow$ `rules` $\rightarrow$ `skills` $\rightarrow$ `dynamic`），试图把所有动态模式（`/goal`、`/grill-me`、定时任务编排助手、阶段总结）全部通过 `PromptAssemblyPipeline.build()` 拼接到唯一的 `System Prompt` 字符串中（第 523~578 行）。
  2. **违反可见性原则**：把本该让用户感知的模式指引（如 Grill-Me 对齐规则、Goal Mode 任务清单要求）深埋在 System Prompt 底层，导致用户在 UI 界面上无法感知当前 AI 的行为约束。
- **重构与精简方案**：
  - **静态 System Prompt 大幅瘦身（仅保留 L0~L1）**：
    - 仅保留 `core/systemCore.ts`（AI 身份定义、中文注释、安全红线）与 `environment/hostEnvironment.ts`（OS、Shell 类型、工作区根目录）；
    - System Prompt 在整个会话生命周期中保持**绝对不可变（Immutable）**，最大化利用大模型 KV 缓存。
  - **L2 模式助手与 L5 动态状态下放为「可见注入卡片」**：
    - `modes/workflowAssistant.ts` $\rightarrow$ 改造成 `WorkflowAssistantCard`；
    - `modes/goalMode.ts` $\rightarrow$ 改造成 `GoalModeStatusCard`；
    - `modes/grillMe.ts` $\rightarrow$ 改造成 `GrillMeAlignmentCard`；
    - 触发时直接向会话时间线 `addMessage` 插入可见卡片，模型从历史消息中读取，彻底剔除 `PromptAssemblyPipeline` 中繁冗的动态多层拼装逻辑。

### 3.2 方案 02（统一注入通道设计方案）审查与重构

- **原方案定位**：`02-统一注入通道设计方案.md`
- **核心问题诊断**：
  1. **8 级物理槽位阶梯（Slot 0~7）过度设计**：原方案设计了 8 级槽位矩阵与 32 位复合优先级键（第 185~220 行），为隐式 System Prompt 拼装提供了极其复杂的排序与加权计算。
  2. **复杂的生命周期状态机与 SQLite 表**：为管理单次注入项，设计了 `session_prompt_injections` 表、`Persistent/Ephemeral/Reactive` 三种模式转换、`mark_consumed` IPC 调用与后台 GC 清理（第 395~455 行）。
- **重构与精简方案**：
  - **废弃 8 级隐式槽位与复合优先级矩阵**：不再需要将注入项物理映射到 Slot 0~7。
  - **重塑 `PromptInjectionChannel` 为「可见注入派发器（ContextInjectionDispatcher）」**：
    - 当任何模块需要注入上下文时（规则加载、技能激活、附件引用、模式切换），直接调用 `contextInjectionDispatcher.inject(sessionId, payload)`；
    - 派发器直接生成标准 `ContextInjectionMessage` 写入 `useSessionStore` 的消息时间线；
    - **无需单独的 SQLite 注入表**：由于注入卡片就是一条消息，天然随现有的 `session_messages` 表持久化与重放；
    - **无需复杂的 Ephemeral 消费清理逻辑**：在对话流中，历史轮次的注入卡片随时间线推进自然成为历史上下文，模型与用户均能清晰看到完整的因果流转。

### 3.3 方案 03（前端会话流转与交互注入方案）审查与重构

- **原方案定位**：`03-前端会话流转与交互注入方案.md`
- **核心问题诊断**：
  1. **四层 XML System Prompt 隐式合并**：原方案第 292~412 行设计了 `assembleStructuredSystemPrompt`，将全局提示词、会话专属提示词与运行时环境拼装成一个大型 `<system_context>` XML 块，并在 Header 处设计了隐式的 Token 估算器与预览弹窗。
- **优点保留**：
  - 原方案提出的 **三级草稿保护架构**（Viewport Tiptap AST $\rightarrow$ SessionDraftManager $\rightarrow$ SessionStore）与基于 `targetSessionId` 的草稿隔离机制极其优秀，彻底解决了多会话切换串扰与 350ms 防抖竞态问题，应完整保留。
- **重构方案**：
  - 废弃 `assembleStructuredSystemPrompt` 中的 XML 隐式嵌套拼装；
  - 会话级专属提示词、外部模板引入、代码引用通过 `PromptInjectionRouter` 转化为消息流中的可见卡片直接插入；
  - 输入框（Composer）保持极致轻量、纯粹与无干扰，专注于用户当前的键入与草稿保护。

### 3.4 方案 04（Rust 引擎与底层协议对接方案）审查与重构

- **原方案定位**：`04-Rust引擎与底层协议对接方案.md`
- **核心问题诊断**：
  1. **排斥消息流包含注入内容**：原方案第 362 行写道：“对话消息列表 messages 中严禁混入 role: 'system'，所有注入段均通过 ContextInjector 汇入 system_prompt”，与用户最新裁决直接冲突。
  2. **`ContextInjector` 过于重型**：在 Rust 侧设计了排序、体积截断与静态指纹校验等多重冗余关卡。
- **重构方案**：
  - **接纳可见注入消息进入 messages 流**：
    - Rust 内核在 `crates/session-loop` 中将 `ContextInjectionMessage` 视为合法消息实体；
    - 针对不同 LLM Provider 协议（Anthropic / OpenAI / Gemini）：
      - **OpenAI 系**：映射为带 `role: "system"` 或 `role: "user"`（带 `[Context Injection]` 标签）的消息节点；
      - **Anthropic 系**：映射为标准 `user` 角色中的结构化文本 Block，带有显式的 `[Context Injection]` 元数据标头；
  - **Prompt Caching 极致简化**：
    - 静态 System Prompt 保持恒定不变 $\rightarrow$ 稳定命中第一级系统缓存断点；
    - 可见注入卡片随 messages 时间线推进 $\rightarrow$ 自然参与消息前缀树缓存，完全无需 Rust 内核进行复杂的动态断点重排。

### 3.5 方案 05（上下文引用与多模态附件注入方案）审查与重构

- **原方案定位**：`05-上下文引用与多模态附件注入方案.md`
- **方案亮点评估**：
  - 方案 05 本身的设计理念与用户的最新裁决高度契合！其设计的 `<CodeSnippetCard />`、`<DiffSnapshotCard />`、`<TerminalLogCard />`、`<MultimodalImageCard />`（第 707~744 行）正是可见卡片的典范。
  - 其提出的**四级防爆保护**与**首尾保留智能截断（Head-Tail Truncation）**算法非常扎实，具有极高工程价值。
- **重构与收敛点**：
  - 将附件卡片（Attachment Cards）与通用可见注入卡片（Visible Context Injection Cards）的底层契约进行**同构合并**；
  - 无论是代码选区、Diff 快照、终端日志，还是模式助手指令，统一使用通用的 `ContextInjectionCardPayload` 容器承载，消除多套卡片组件的重复定义。

### 3.6 方案 06（定时任务与助手模式落地实践方案）审查与重构

- **原方案定位**：`06-定时任务与助手模式落地实践方案.md`
- **核心问题诊断（直接冲突点）**：
  - 原方案第 149~200 行明确定义了 **「通道一：System Prompt 隐式定向注入 (Invisible Steering Channel)」**，将 `WORKFLOW_ASSISTANT_SYSTEM_PROMPT` 隐式挂载在系统提示词后台；
  - 与用户的最新裁决“不用隐式通道了，正常在对话流里面显示为对应的注入显示即可”产生直接正面冲突，必须彻底重构！
- **重构方案**：
  - **彻底废除「通道一（隐式 System Prompt 注入）」**；
  - 当用户在定时任务面板点击「在对话中创建」、在设置页点击「用对话创建」或输入 `/schedule` 时：
    1. 前端向当前对话流插入一张 **「⚡ 定时任务编排助手模式注入卡片（Visible Workflow Assistant Card）」**；
    2. 卡片内清晰展示：编排目标、四大核心要素清单（名称/周期/指令/项目）、Grill-Me 交互规范；
    3. LLM 在收到该可见卡片后，立即自然进入编排助手状态，主动对齐缺项；用户同时能清晰看到 AI 为什么会这样提问；
    4. 对齐完成后，输出标准确认卡片，调用工具落盘。全流程 100% 透明、无缝且可见。

### 4.1 数据模型与强类型契约（TypeScript & Rust）

#### 4.1.1 前端 TypeScript 契约定义 (`apps/crish-desktop/src/types/injectionCard.ts`)

> **主控复核定案（2026-09-02，取代本节落点）**：契约统一收敛到 `apps/crish-desktop/src/store/types.ts` 的 **`MessageContextInjection`**（详案 02 定义版，9 类 snake_case kind + 5 态 status + `summary` / `tokenEstimate` 字段名）——卡片本就是消息时间线模型的一部分，与 `SessionMessage` / `MessageTimelineBlock` 同域定义。本节下方的 `types/injectionCard.ts` / `ContextInjectionCardPayload` 作为评审历史记录保留，**不作为实施依据**；详案 05 的 `mode-assistant` 场景映射为 `kind: 'schedule_trigger'`。见 00-总方案 §三。

export interface ContextInjectionCardPayload {

### 4.3 LLM Wire 协议无损映射规范（Wire Projection）

在向下游 LLM 提供商构建请求时，可见注入卡片以结构化消息格式无损投影到 `messages` 时间线中，绝不丢失关键元数据：

```json
// LLM Provider Request messages 数组中的标准映射
{
  "role": "user",
  "content": [
    {
      "type": "text",
      "text": "[系统上下文注入 · 定时任务编排助手模式]\n\n# 角色与定位\n你现在是系统专属的「定时任务调度编排架构师」。你的职责是通过结构化对齐（Grill-Me）流程协助用户设计并创建定时任务。\n\n# 核心约束\n1. 严禁直接执行业务代码；\n2. 确保四要素（名称、周期、指令、项目）完整合法；\n3. 要素齐备后输出确认表格并调用 create_workflow 工具。\n\n[元数据: mode=workflow-creation, workspace=C:/Software/conex]"
    }
  ]
}
```

- **语义隔离**：通过清晰的 `[系统上下文注入 · <Title>]` 与 `[元数据: ...]` 标记，使大模型明确理解这是系统注入的背景上下文或工作模式约束；
- **自然因果序**：卡片排布在用户输入之前或作为独立 Turn，模型按照天然从上到下的注意力顺序阅读，无需任何复杂的注意力位置调控黑魔法。

### 4.4 消息持久化、会话回放与上下文压缩（Compaction）兼容机制

1. **持久化零成本（Zero-Cost Persistence）**：
   - 注入卡片直接作为 `SessionMessage` 的一种特化形态持久化存储在现有 SQLite 数据库（`session_messages` 表）中；
   - 无需新建独立的注入数据表，会话加载、导出 Markdown、跨设备同步完全保持一致。
2. **上下文压缩与历史归档保护（Compaction Invariance）**：
   - 当会话达到长上下文阈值触发 `conex-compaction` 时：
     - **最新活跃卡片**：完整保留在活跃上下文窗口内；
     - **历史轮次卡片**：压缩引擎自动将其提炼为轻量摘要锚点（如 `[历史注入: 定时任务编排助手 (已完成注册)]`、`[历史引用: prepare_turn.rs (L45-L60)]`），既释放了 95% 的上下文 Token，又保留了完整的历史回溯能力。
