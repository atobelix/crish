## 一、执行摘要与评审结论

### 1.1 评审背景与定性

在 Conex / Crish 系统演进中，提示词（Prompt）、草稿种子（Composer Seed）、上下文批注（Annotations）、状态感知（Context State）、技能（Skills）以及多模态附件（Attachments）的注入链路经历了野蛮生长，形成了多处 ad-hoc 字符串拼接、全局单键竞争以及隐式黑盒通道。

为了解决上述问题，`docs/prompt-injection-pipeline/independent-plans/` 产出了 6 份独立方案。然而审查发现：
1. **旧路径尚未彻底摸清**：部分方案未能完全识别现存代码库中由 `sessionStorage` 单键、全局内存数组、拦截吞掉的斜杠命令所构成的隐式暗流；
2. **缺乏明确的「删除面（Deletion Surface）」**：部分方案只顾“新建模块”，未列出详尽的旧代码清退清单，容易演变为在旧系统上层加挂“新壳”，导致多条并行路径并存；
3. **引入了新的过度设计**：方案 01 的 6 层装配堆栈、方案 02 的 8 级槽位与 32 位复合键及 SQLite 临时表、方案 03 的 4 层 XML `<system_context>` 嵌套、方案 06 的隐式 System Prompt 通道，严重违背了“轻量、确定、可见、低复杂度”的工程原则，更与用户最新关于**“告别隐式通道、采用对话流可见注入（WYSIWYG）”**的权威裁决相抵触。

### 1.2 评审核心裁决与收敛目标

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                               评审核心裁决：六大概念单一真理路径 (SSOT)                     │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ 1. System Prompt (系统提示词)  ──► 仅保留静态 L0 基座 + L1 环境，整个会话生命周期绝对不可变      │
│ 2. Dynamic Injections (动态注入) ──► 统一收敛为「对话流上下文可见卡片」，所见即所得，被动直接注入   │
│ 3. Composer Seed (草稿与种子)  ──► 彻底废除 sessionStorage 单键，统一走三级会话隔离草稿缓冲池 │
│ 4. Slash Commands (斜杠命令)   ──► 消除拦截吞掉逻辑，/schedule 等命令统一进入可见助手模式卡片  │
│ 5. Context / State (上下文感知) ──► 消除全局 pending 数组/键，严格按 targetSessionId 即时绑定  │
│ 6. Wire Mapping (底层协议映射) ──► 消除 8 级槽位与动态断点重排，静态 System + 动态 Messages    │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

### 2.2 全局单键草稿种子（Composer Seed）竞态与穿孔路径

在设置页与面板中点击「AI 辅助创建 / 在对话中创建」时，通过全局单键中转草稿：

- **源码位置**：[`apps/crish-desktop/src/api/composerSeed.ts:6-36`](file:///c:/Software/conex/apps/crish-desktop/src/api/composerSeed.ts#L6-L36)
  ```typescript
  const KEY = 'crish_composer_seed_v1';
  export function setComposerSeed(text: string): void {
    sessionStorage.setItem(KEY, t);
    window.dispatchEvent(new CustomEvent(COMPOSER_SEED_EVENT, { detail: { text: t } }));
  }
  export function takeComposerSeed(): string | null {
    const t = sessionStorage.getItem(KEY);
    if (!t) return null;
    sessionStorage.removeItem(KEY);
    return t.trim() || null;
  }
  ```
- **消费位置**：[`apps/crish-desktop/src/components/chat-card/useChatInput.ts:25-35`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-card/useChatInput.ts#L25-L35)
- **核心破坏性**：
  1. **跨会话草稿污染**：用户在设置页为「会话 A」点击生成种子，随后点击切换至「会话 B」，`useChatInput` 在 `useEffect([activeSessionId])` 中执行 `takeComposerSeed()`，导致会话 A 的种子被错误注入并强行覆盖会话 B 的输入框！
  2. **React StrictMode 破坏（破坏性读取）**：`takeComposerSeed` 采用 `getItem` + `removeItem` 模式，在 StrictMode 下双挂载会导致第二次读取为 `null`，引发草稿闪烁或丢失。
  3. **350ms 防抖时序竞态**：`scheduleComposerDraft` 存在 350ms 延迟，在快速切换会话时，旧会话的未保存草稿会覆盖新会话的草稿。

### 2.3 跨会话污染的全局暂存态

系统中存在多个模块级全局变量或单一 LocalStorage 键用于“下一条消息注入”：

#### 1. 文件选区批注（File Annotations）
- **源码位置**：[`apps/crish-desktop/src/api/fileAnnotations.ts:17-54`](file:///c:/Software/conex/apps/crish-desktop/src/api/fileAnnotations.ts#L17-L54)
  ```typescript
  let pendingAnnotations: PendingFileAnnotation[] = [];
  export function takePendingFileAnnotations(): PendingFileAnnotation[] {
    const list = pendingAnnotations;
    pendingAnnotations = []; // 全局清空
    return list;
  }
  ```
- **破坏性**：用户在项目面板为某个文件添加批注，本意是在会话 A 中询问。若用户此时在会话 B 发送了一条问候语，批注被会话 B `takePendingFileAnnotations()` 取走并发送，会话 A 再次发送时批注已永久丢失！

#### 2. 状态切换感知（Context State）
- **源码位置**：[`apps/crish-desktop/src/api/provider-profiles/contextStatePending.ts:25-118`](file:///c:/Software/conex/apps/crish-desktop/src/api/provider-profiles/contextStatePending.ts#L25-L118)
  ```typescript
  export const PENDING_CONTEXT_STATE_KEY = 'crish_pending_context_state_v1';
  export function takePendingContextState(): string | undefined {
    const text = localStorage.getItem(PENDING_CONTEXT_STATE_KEY) || undefined;
    if (text) localStorage.removeItem(PENDING_CONTEXT_STATE_KEY);
    return text;
  }
  ```
- **破坏性**：全局共享一个 LocalStorage 键，模型切换通知被随机触发的第一个会话取走，其他活跃会话完全无法感知模型切换。

### 2.5 附件与多模态二元分裂路径

用户在发送附件时，系统在 [`slashSendPreflight.ts:311-349`](file:///c:/Software/conex/apps/crish-desktop/src/hooks/chat-stream/slashSendPreflight.ts#L311-L349) 中执行分裂处理：

```typescript
const { promptAttachBlock, streamOptions } = buildMultimodalFromAttachments(modelText, attachments);
const fileAnns = takePendingFileAnnotations();
const annBlock = formatAnnotationsForModel(fileAnns);
const input = (annBlock ? `${annBlock}\n\n` : '') + modelText + promptAttachBlock;
```

- **破坏性**：
  - 文本附件被硬编码拼装为 `\n\n[附件] ...` 塞入文本末尾；
  - 批注被格式化为 `<file_annotations>` 塞入文本头部；
  - 图片附件被剥离为 `ChatContentPart` 塞入 options；
  - 三者缺乏统一的元数据标准、缺乏结构化隔离，且在 UI 上用户只能看到简陋的文本追加，无法折叠或定位。

### 2.6 Rust 内核与前端协议断层与双头组装

- 前端在 `streamSession.ts` 中根据设置组装出 `systemPrompt`；
- Rust 壳层在 `run_idle.rs:assemble_system_prompt_with_stages` 中再次从数据库拉取阶段总结拼入；
- Rust 内核在 `engine_build.rs:ContextInjector` 中再次按 `[System, Skills, Mcp, AgentDefinition]` 顺序进行第三次重排和拼接；
- **破坏性**：前后端组装职责严重重叠，缺乏单一真相源，任何一方修改分隔符或段落格式都会导致提示词缓存失效或断层。

### 3.1 方案 01（系统提示词组织与维护方案）审查

- **审查结论**：**设计方向需大幅纠偏，删除面严重缺失**。
- **具体问题**：
  1. **层级膨胀与职责倒挂**：方案 01 划分了 L0~L5 六层体系，试图将模式助手（Workflow Assistant、Goal Mode、Grill-Me）全部编译进 System Prompt。这导致 System Prompt 变成一个高频变动的“大杂烩”，不仅用户完全看不见当前模式，而且彻底摧毁了大模型前缀缓存（Prompt Caching）。
  2. **删除面缺失**：方案中只有“Phase 2 迁移”，没有明确列出要物理删除哪些散落硬编码文件（如 `slash-prefixes.ts`、`goalModeContinuation.ts` 中的前缀函数）。
- **收敛与删除建议**：
  - **砍掉 L2~L5 动态拼装**：`PromptAssemblyPipeline` 仅保留 L0 基础基座 + L1 宿主环境，输出绝对静态的 System Prompt；
  - **模式助手全部下放**：Workflow、Goal、Grill-Me 彻底移出 System Prompt，转为对话流中的可见注入卡片；
  - **彻底物理删除**：删除 `slash-prefixes.ts`，清退 `workflowAssistantPrompt.ts` 乱码文件。

### 3.2 方案 02（统一注入通道设计方案）审查

- **审查结论**：**典型的重型过度设计，删除面流于表面，必须彻底归零重构**。
- **具体问题**：
  1. **8 级物理槽位与 32 位复合键过度设计**：方案 02 提出了 `CompositePriority = (SlotIndex << 16) + (65535 - LocalPriority)`，并设计了 5 个专用 Coordinator。为了在隐式通道中排队，凭空制造了巨大的算法复杂度。
  2. **冗余的 SQLite 临时表与生命周期状态机**：为了管理单次消耗项（`Ephemeral`），设计了 `session_prompt_injections` 数据库表、`mark_consumed` IPC 命令与 GC 机制。这完全是脱离业务场景的自我复杂化——在对话流中，一条可见卡片消息随着时间线推进自然沉淀为历史，天然具备持久化与生命周期，根本不需要数据库状态机！
- **收敛与删除建议**：
  - **彻底废除 8 级槽位与 32 位优先级键**；
  - **彻底废除 `session_prompt_injections` SQLite 临时表与 `mark_consumed` IPC**；
  - **收敛为轻量派发器**：`PromptInjectionChannel` 简化为 `ContextInjectionDispatcher`，直接向 `useSessionStore` 写入标准可见卡片消息。

### 3.3 方案 03（前端会话流转与交互注入方案）审查

- **审查结论**：**草稿保护架构极佳，但 System Prompt 拼装部分需剔除**。
- **具体问题**：
  1. **亮点肯定**：方案 03 提出的「三级因果缓存架构（Level 1 视口 AST $\rightarrow$ Level 2 会话草稿池 $\rightarrow$ Level 3 全局 Store）」精准击中了 `sessionStorage` 单键污染与 350ms 防抖竞态的根因，逻辑严密，应作为全系统草稿 SSOT 刚性采纳。
  2. **冗余设计**：第 292~412 行的 `assembleStructuredSystemPrompt` 设计了复杂的 XML `<system_context>` 嵌套，试图在前端拼装所有层级，并在 Header 增加预览弹窗，与可见注入卡片范式重叠。
- **收敛与删除建议**：
  - **完整保留草稿三级保护与 `targetSessionId` 路由机制**；
  - **删除 `assembleStructuredSystemPrompt` XML 隐式拼装逻辑**；
  - **彻底删除 `src/api/composerSeed.ts`**，统一收敛至 `SessionDraftManager`。

### 3.4 方案 04（Rust 引擎与底层协议对接方案）审查

- **审查结论**：**底层缓存设计优秀，但对可见注入卡片存在协议排斥硬伤**。
- **具体问题**：
  1. **协议断层**：方案 04 第 362 行断言“对话消息列表 messages 中严禁混入注入内容”，这与用户裁决“在对话流中显示为注入显示，作为 messages 传输”完全背道而驰。
  2. **`ContextInjector` 冗余**：Rust 侧维护了复杂的动态段排序与体积截断逻辑，而实际上动态段下放为 messages 卡片后，Rust 内核仅需组装静态 System Prompt。
- **收敛与删除建议**：
  - **放行 messages 中的可见注入卡片**：`session-loop` 将注入卡片按标准 user/system message 解析；
  - **精简 `ContextInjector`**：仅保留静态 System Prompt 的基座注入与指纹校验，动态内容由前端消息流自然传递。

### 3.5 方案 05（上下文引用与多模态附件注入方案）审查

- **审查结论**：**工程质量最高，需与通用注入卡片进行契约同构收敛**。
- **具体问题**：
  1. **契约未完全统一**：方案 05 单独定义了 `ContextAttachmentPayload`，而方案 02/03 定义了 `PromptInjectionItem`，形成了附件与注入项两套并行的卡片系统。
- **收敛与删除建议**：
  - **同构合并**：将附件载荷全面并入统一的 `ContextInjectionCardPayload`，作为 `kind: 'code-snippet' | 'diff-snapshot' | 'terminal-log' | 'file-document'` 等子类型；
  - **完整保留**：采纳其四级防爆截断（Head-Tail 40/60 截断）与加权特征 Token 启发式估算算法。

### 3.6 方案 06（定时任务与助手模式落地实践方案）审查

- **审查结论**：**必须彻底推翻隐式通道设计，全面重构为可见卡片交互**。
- **具体问题**：
  1. **与用户裁决直接冲突**：方案 06 将 `WORKFLOW_ASSISTANT_SYSTEM_PROMPT` 作为“通道一：隐式 System Prompt 注入”，用户在界面上完全看不到助手模式的激活状态。
  2. **未提供删除面**：未指出如何改造 `slashSendPreflight.ts` 中拦截吞掉 `/schedule` 的旧代码。
- **收敛与删除建议**：
  - **彻底废除隐式 System Prompt 注入通道**；
  - **改造为可见助手卡片**：用户触发时，向当前对话流插入 `<WorkflowAssistantCard />`，展示四要素检查清单与交互规范；
  - **解除 `/schedule` 拦截**：在 `resolveSlashCommand.ts` 中将 `/schedule` 从 `navigation` 移出，改为派发可见助手卡片。

### 5.1 概念一：System Prompt 收敛为「单一静态基座」
- **唯一真理源**：`apps/crish-desktop/src/prompts/core/` 下的基础核心指令与环境指引。
- **不变性契约**：在整个会话生命周期内，System Prompt **绝不包含任何动态轮次状态、单次模式或附件**，保持逐字节绝对稳定，确保 100% 命中 Anthropic / OpenAI 的 Prompt Caching。

### 5.2 概念二：动态注入与附件收敛为「单一时间线可见卡片」
- **唯一真理源**：`apps/crish-desktop/src/types/injectionCard.ts` 中的 `ContextInjectionCardPayload`。
- **机制**：无论是模式切换（`/goal`, `/grill-me`, 定时任务助手）、代码引用、Diff 对比还是终端报错，全部通过 `ContextInjectionDispatcher` 生成可见注入卡片插入消息流，**所见即所知，无任何隐式后台暗流**。

### 5.3 概念三：草稿与种子收敛为「单一会话隔离三级缓冲」
- **唯一真理源**：`SessionDraftManager`（基于 `targetSessionId`）。
- **机制**：彻底废除 `sessionStorage` 单键，外部填词或模板载入必须显式指定 `targetSessionId`，切换会话时通过微任务原子 Barrier 同步 Flush，确保零草稿丢失与跨会话串扰。

### 5.4 概念四：斜杠命令收敛为「统一透传与可见卡片派发」
- **唯一真理源**：`apps/crish-desktop/src/api/resolveSlashCommand.ts`。
- **机制**：废除 Preflight 阶段对 `/schedule` 的拦截吞掉逻辑；用户键入 `/schedule` 时，直接在当前会话生成并插入 `WorkflowAssistantCard` 可见卡片，无缝开启对齐流程。

### 5.5 概念五：状态与批注感知收敛为「会话绑定即时注入」
- **唯一真理源**：移除模块级全局变量 `pendingAnnotations` 与 `crish_pending_context_state_v1`，批注与状态切换在触发瞬间直接绑定当前 `activeSessionId` 并转为可见卡片入库。

### 5.6 概念六：底层 Wire 映射收敛为「静态 System + 动态 Messages」
- **唯一真理源**：`crates/agent-provider/src/request/`。
- **机制**：静态基座直接映射为 API 的 `system` 字段；所有可见卡片随 `messages` 数组无损透传，彻底消除 Rust 引擎内部复杂的 8 槽位排序与断点重排。
