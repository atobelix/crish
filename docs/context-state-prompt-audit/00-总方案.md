## 一、用户现场反馈与问题全景定义

### 1.1 用户现场原声与异常现象

用户在多模型切换与日常对话操作中明确提出反馈：

> **用户原话**：  
> “当前已切换到模型 ornith:latest（服务商 ollama）。权限模式：full。思考档位：Max。 这个不是系统提示吗，是随到用户发送的消息后面，不是一个单独用户输入内容的。 你看看这是什么情况吧”

现场表现为极其反直觉的“幽灵双轮交互”现象：

1. **用户操作**：在配置栏切换了模型/服务商/权限/思考档位，然后在输入框输入了正常的提示词（例如：“帮我分析这个报错”），点击发送。
2. **第一轮执行**：系统启动 `run-1`，模型针对用户的“帮我分析这个报错”进行了正常思考与回复。
3. **异常爆发**：在 `run-1` 刚收口、会话理应回到 idle 状态的瞬间，聊天界面**突然凭空多出了一条由“用户”发送的独立消息气泡**：
   > “当前已切换到模型 ornith:latest（服务商 ollama）。权限模式：full。思考档位：Max。”
4. **连锁异常**：紧接着，大模型立刻被该伪用户消息**再次唤醒（触发了第二轮全新的 `idle-resume` run）**，模型针对这句提示词给出了答复（例如：“好的，我已经了解已切换到模型 ornith:latest，请问有什么可以帮助您的？”）。
5. **用户困惑**：明明是一次性操作，却产生了两次 Run、两条气泡，且系统状态提示被李代桃僵伪装成了用户的输入内容。

### 1.2 预期行为与实际劣化行为对照表

| 维度                     | 预期正确行为（Expected Behavior）                                                        | 实际劣化行为（Actual Buggy Behavior）                                                           | 破坏等级                  |
| :----------------------- | :--------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------- | :------------------------ |
| **消息归属（Role）**     | 系统级环境上下文提示（System Meta Prompt），不属于用户发言。                             | 被包装为 `AgentMessageRole::User`，前端渲染为带用户头像的独立用户消息气泡。                     | 🔴 严重违背业务逻辑       |

| **UI 呈现（Visual）**    | 作为会话中的轻量微提示（居中浅灰药丸/随附微标签）展示，或者内联于当次消息。              | 渲染为全尺寸 User Bubble，后跟一个无意义的 Assistant Bubble。                                   | 🔴 视觉视觉噪音           |

## 二、缺陷全景图与深度根因剖析（Root Cause Analysis）

通过穿透 Rust 后端内核、事件驱动循环、前端状态与渲染管线，精确定位到三大结构性断层：

### 2.1 后端病灶：`run_launch.rs` 错位入队与 `run_idle.rs` 误导唤醒

#### 1. 错位入队病灶

在 `apps/agent-workbench/src-tauri/src/run/run_launch.rs:801-819`：

```rust
// ── I1-α②（扩展点 A）：context-state 感知注入 ─────────────────
if let Some(text) = context_state.filter(|t| !t.trim().is_empty()) {
    let now = now_ms_internal();
    let entry = orchestrator::steering_queue::SteeringInputEntry::context_state(
        format!("context-state-{run_id}-{now}"),
        text,
        now,
    )
    .with_session(&session_id);
    state
        .pending_queue
        .lock()
        .unwrap_or_else(|e| e.into_inner())
        .replace_or_enqueue(entry);
    tracing::info!(
        target: "run",
        session_id = %session_id,
        "context-state 感知注入已排入跨 run 队列（下一次用户提交边界注入时间线）"
    );
}
```

**根因分析**：  
代码原作者意图将状态变更暂存给“下一次用户提交”，却错误地调用了 `state.pending_queue.replace_or_enqueue(entry)`。  
然而，`state.pending_queue` 在 Conex 架构中是**用于异步唤醒空闲 Agent 的 Steering 消息队列**（例如定时器触发 `timer-*`、子 Agent 完成 `subagent-complete`、外部拦截打断等）。将 `context-state` 放入此队列是致命的设计错位。

#### 2. 空闲判定被欺骗

在 `apps/agent-workbench/src-tauri/src/run/run_idle.rs:114-120`：

```rust
let queue_pending = {
    let queue = state
        .pending_queue
        .lock()
        .unwrap_or_else(|e| e.into_inner());
    queue.has_pending_for(&active.session_id)
};
```

当用户的当次 Run（`run-1`）完成并收到 `AgentEndReason::Stop` 时，调度器检查四项唤醒源：
`if !(queue_pending || timer_active || cron_enabled || goal_pending) { return None; }`  
因为刚刚在 `run_launch.rs` 中被塞入的 `context_state` 条目赫然躺在 `pending_queue` 中，导致 `queue_pending == true`！调度器误以为“用户有新的 Steering 消息等待执行”。

#### 3. 角色伪造与二轮唤醒

在 `apps/agent-workbench/src-tauri/src/run/run_idle.rs:619-633`：

```rust
// 全为 context-state 条目：逐条注入（各带 kind=context-state）
context_states
    .into_iter()
    .map(|entry| AgentMessage {
        id: entry.id,
        role: AgentMessageRole::User, // 💥 致命错误：将系统状态直接标记为 User 角色！
        created_at: crate::engine::now_iso_utc(),
        blocks: vec![AgentMessageBlock::Text { text: entry.text }],
        metadata: Some(serde_json::json!({
            "kind": AgentMessageMetadataKind::ContextState
        })),
        client_message_id: None,
        content: None,
    })
    .collect()
```

`drain_pending_to_inject_messages` 取出该条目后，直接赋予其 `role: AgentMessageRole::User`，正文就是那句“当前已切换到模型 ornith:latest...”。  
随后在 `run_idle.rs:1250-1281`：

```rust

    run_id: crate::engine::new_message_id("idle-resume"),
    session_id: session_id.clone(),
    prompt: Some(text), // 💥 此处的 text 就是伪造的用户消息！
    mode: Some(mode.to_string()),
    ...
};

```

系统启动了一次全新的 `idle-resume` Run，大模型将这段环境提示视作用户的输入，并给出了第二轮多余的答复！

### 2.2 提示词断层：当次 Run 毫无感知，时序倒置

在 `apps/agent-workbench/src-tauri/src/run/run_launch.rs:736-737`：

```rust
o.assembly.system_prompt =
    assemble_system_prompt_with_stages(&state, &session_id, system_prompt);
```

当次由用户发起的真正 Run 在装配系统提示词时：

- 传入的参数只有 `&state`、`&session_id`、`system_prompt`；
- 来自 `options.context_state` 的入参被彻底丢弃，**完全没有合入 `o.assembly.system_prompt`**！
- 结果：**大模型在回答用户真实问题时，完全不知道当前切换了新模型或调整了权限档位**；而当回答结束后，系统却用一条伪用户消息告诉模型环境变了——形成滑稽的时序倒置与逻辑断层。

### 2.3 前端 UI 与事件反向污染断层

#### 1. 前端发送契约失控

在 `apps/crish-desktop/src/api/sessionEventProjection.ts:193-199` 与 `220-226`：

#### 3. 渲染层无法识别

因为 `msg.sender === 'user'`，消息被交给 `ChatUserMessageRow` 渲染，从而不可避免地被画成全尺寸的用户头像加背景气泡。

## 三、端到端系统级改造总体架构设计

### 3.1 核心设计哲学（Four Iron Principles）

1. **铁律 1：元数据归位（Zero Fake User Message）**  
   `context_state` 是运行环境的**系统级上下文事实（System Environmental Fact）**，在协议层、内核层、呈现层严禁出现任何 `role: User` 或 `sender: user` 的伪造定义！
2. **铁律 2：零额外 Turn（Zero Extra Turn）**  
   状态感知必须合入当次执行的 System Prompt，**当次生效、零延迟、零额外轮次、零 Token 浪费**，彻底切断与 `idle-resume` 状态机的任何关联！
3. **铁律 3：队列物理绝缘（Physical Queue Isolation）**  
   `state.pending_queue` 是异步打断/唤醒队列。`context_state` 严禁生成 `SteeringInputEntry`，严禁进入 `pending_queue`，在编译期与逻辑层刚性绝缘！
4. **铁律 4：展现与存储单一真理源（SSOT & Self-Healing）**  
   前端仅通过微提示胶囊呈现当次环境切换；遇到历史留存的脏数据，在投影与水合层执行无感自愈清洗，确保旧会话不再显现幽灵气泡。

### 3.2 改造后全链路数据流对比图

```
【改造前（异常链路）】：
用户点击发送 ──> run_launch ──> 塞入 pending_queue ──> 运行 run-1 (无状态感知)
                                                             │
                                                   run-1 结束进入 idle
                                                             │
                                                             ▼
UI 渲染出用户气泡 <── 回发 fake User 消息 <── 重新唤醒启动 run-2 (idle-resume)

-----------------------------------------------------------------------------

【改造后（标准收敛链路）】：
用户点击发送
     │
     ├─ 前端本地: 创建轻量居中微提示 (workspace_env / mode: 'context-state')
     │
     └─ IPC 传递 options.context_state
              │
              ▼
    [Rust: run_launch.rs]
              │
              ├─ 1. 物理移除 pending_queue 写入 (绝不入队，绝不触发 idle 唤醒！)
              │

                    assemble_system_prompt_with_stages(...)

                          │
                          ▼
              [Run 结束收口] ──> pending_queue 为空 ──> 会话优雅静默休眠 (Idle)
```

### 4.2 维度二（Rust 提示词正确注入通道）

#### 1. 系统提示词装配契约升级

- **目标文件**：`apps/agent-workbench/src-tauri/src/run/run_idle.rs`（或装配模块）与 `run_launch.rs`
- **函数签名改造**：
  扩展 `assemble_system_prompt_with_stages` 或增加明确的上下文状态追加器：
  ```rust
  /// 统一环境上下文状态系统提示词段格式化
  pub(crate) fn format_context_state_section(context_state: &str) -> String {
      format!("[系统环境提示：{}]", context_state.trim())
  }

  /// 组装包含阶段总结与上下文状态的最终系统提示词
  pub(crate) fn assemble_system_prompt_with_stages(
      state: &CoreRunState,
      session_id: &str,
      system_prompt: Option<String>,
      context_state: Option<&str>,
  ) -> Option<String> {
      let mut base = build_system_prompt(system_prompt);

      // 1. 若存在阶段总结，注入阶段总结段
      let stages = stored_stage_summaries(state, session_id);
      if !stages.is_empty() {
          let mut section = format!("阶段总结：{} 条", stages.len());
          for (_, markdown) in &stages {
              section.push_str("\n\n");
              section.push_str(markdown);
          }
          base = match base {
              Some(b) => Some(format!("{b}\n\n{section}")),
              None => Some(section),
          };
      }

      // 2. 注入当前环境上下文状态（单轨无污染注入）
      if let Some(cs) = context_state.filter(|s| !s.trim().is_empty()) {
          let env_section = format_context_state_section(cs);
          base = match base {

          };
      }

  }
  ```

### 4.4 维度四（历史脏数据清洗与自愈）

针对用户当前已经受到污染的现有会话数据库与本地 Store，必须提供全自动、无感知的自愈策略，消除数据库中已存的幽灵气泡。

#### 1. 脏数据指纹定义（Bogus Fingerprint）

满足以下条件的为脏消息对象：

- **指纹 A（用户端幽灵消息）**：
  `sender === 'user'` 且 `text` 满足正则：  
  `/^(?:\[系统环境提示：\]?)?(?:当前)?已切换到模型\s*[^\s。]+.*权限模式.*思考档位/`
- **指纹 B（伴生大模型废话答复，可选连带清理）**：
  紧跟在指纹 A 之后的 `sender === 'assistant'` 消息，且其 `text` 为短确认文本（如 `/^(?:好的[，,])?(?:我已了解|收到|明白).*已切换到模型/` 且长度 `< 150` 字符）。

#### 2. 水合层自愈拦截（Hydration Self-Healing）

- **目标文件**：`apps/crish-desktop/src/store/sessionSharedHelpers.messageMerge.ts` 与 `sessionHydrationMessages.ts`
- **自愈时机**：在从 SQLite 或 IndexedDB/LocalStorage 加载消息数组，以及进行增量 Merge 时。
- **自愈动作**：
  遍历消息列表，执行过滤净化：
  ```typescript
  export function purgeStaleContextStateBubbles(
    messages: SessionMessage[]
  ): SessionMessage[] {
    if (!messages.length) return messages;
    const cleaned: SessionMessage[] = [];
    for (let i = 0; i < messages.length; i++) {
      const current = messages[i]!;
      if (isStaleContextStateUserMessage(current)) {
        // 发现脏用户气泡：跳过不加入展示列表！
        // 检查其紧随的下一条 assistant 消息是否为伴生废话
        const next = messages[i + 1];
        if (
          next &&
          next.sender === 'assistant' &&
          isStaleAssistantFollowup(next)
        ) {
          i++; // 跳过伴生的无意义答复
        }
        continue;
      }
      cleaned.push(current);
    }
    return cleaned;
  }
  ```

#### 3. 存储层持久化自愈（SQLite Database Purge）

- **目标文件**：`crates/conex-db/src/messages.rs`
- **改造动作**：
  在 `conex-db` 增加安全的清理事务 `clean_stale_context_state_bubbles(session_id)`：
  ```sql
  -- 清理历史遗留的伪用户状态消息
  DELETE FROM session_messages
  WHERE session_id = ?1
    AND sender = 'user'
    AND (
      text LIKE '当前已切换到模型%权限模式%思考档位%' OR
      text LIKE '[系统环境提示：当前已切换到模型%'
    );
  ```
  并在执行后依照 `conex-db` 铁律对 `seq` 进行平滑连续重编（Rebase Seq）或通过 versioned save 保证 `message_count` 绝对一致。
