## 一、审计背景与问题定性

### 1.1 现场复现与用户核心质疑

用户在使用桌面客户端切换模型/配置后与模型交互时，发现并提出了以下核心问题：

> **用户原话**：  
> _“当前已切换到模型 ornith:latest（服务商 ollama）。权限模式：full。思考档位：Max。 这个不是系统提示吗，是随到用户发送的消息后面，不是一个单独用户输入内容的。 你看看这是什么情况吧”_

从用户的实际交互表现来看：

1. 用户在前端切换了模型（例如切换到 Ollama 的 `ornith:latest`）、权限模式或思考档位；
2. 用户随后在聊天框中发送了一句常规的业务指令（如：“帮我分析这个函数的性能”）；
3. 运行结束后，客户端不是安静地在一次交互中完成指令，而是**凭空产生了一条独立的用户气泡**，内容为：`当前已切换到模型 ornith:latest（服务商 ollama）。权限模式：full。思考档位：Max。`；
4. 随后，模型被**再次强制唤醒（Idle-Resume Run）**，以助手身份回复了一句空洞而冗余的确认语（例如：“收到，我已切换到模型 ornith:latest，权限为 full，思考档位为 Max。请问有什么可以帮助您的？”）；
5. 这一过程消耗了多余的 LLM 请求次数、耗费了额外的 API Token/本地算力、增加了请求延迟，更严重的是让用户感觉 Agent “在自言自语，行为极其异常”。

### 1.2 问题的核心定性

经审查，本问题的根因在于**严重的「语义模型错位」与「异步调度队列滥用」**：

- **语义本质错位**：环境状态通知（`context_state`）本质上是关于当次会话运行环境的**系统约束元数据（System Constraints / Metadata Envelope）**，本应随同当次运行生效。
- **调度通道误杀**：历史开发中错误地将 `context_state` 塞进了用于**后台异步长任务唤醒**的 `PendingMessageQueue`（该队列原本专供定时器到期、Cron 触发、子 Agent 终态汇报等场景）。
- **角色伪造与二次触发**：当次用户请求运行完毕并进入 Idle 状态后，`run_idle.rs` 发现 `PendingMessageQueue` 中有遗留项，误以为是“外部异步唤醒通知”，将其提取并**伪造为一条 `role: AgentMessageRole::User` 的独立消息**，通过 `spawn_idle_resume_run` 拉起全新的第二次 LLM Run。
- **线网层完全失真**：由于该消息角色被标为 `User`，底层 Provider 在组包出站时，直接将其作为普通的用户发言序列化（`{"role": "user", "content": "当前已切换到模型..."}`），导致大模型完全无法区分这究竟是系统通知还是用户的真实诉问，被迫当成普通对话进行回复。

## 三、主流大模型线网协议标准与语义对比

大模型对于“系统设定、环境状态、用户输入”的处理在各大标准协议中有严格明确的界定：

| 维度 / 协议                           | OpenAI Chat Completions / Ollama `/api/chat`                               | Anthropic Messages API (`/v1/messages`)                                                              | 标准模型语义期望                                                                                     |
| :------------------------------------ | :------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------- |
| **System Role**                       | `messages: [{"role": "system" (或 "developer"), "content": "..."}]`        | 顶层 `system: "..."` 字段（或带断点的块数组），严禁在 `messages` 中出现 system role（否则 400 报错） | 设定全局角色、不可违背规则、基础执行环境；模型不会对该段落生成显式应答。                             |
| **User Role**                         | `messages: [{"role": "user", "content": "..."}]`                           | `messages: [{"role": "user", "content": [...]}]`，要求 user 与 assistant 必须严格交替                | 用户的对话、提问、业务诉求；**模型必须对其生成回复**。                                               |
| **动态上下文注记 (Context Envelope)** | 在该轮 `user` 消息前/后缀包裹上下文信息：`[系统上下文：...] \n\n 用户提问` | 在该轮 `user` content 的首个 text block 中注入上下文信封，或使用中性系统说明标记                     | 提供当次操作的临时环境感知；模型将其视作用户提问的背景前置，**只回答用户的问题，不单独回答上下文**。 |

### 关键结论：

将状态说明赋予 `role: User`，并且作为一个**独立的对话回合（Turn）**提交给模型，直接打破了大模型的交互假定。大模型在收到纯粹的 `role: User` 输入后，必然会触发生成逻辑，产生无意义的对话废话。

## 四、目标协议方案设计与 Prompt Cache 友好性深度评估

针对用户的核心诉求：“这个状态说明本质上是系统提示，应该随到用户发送的消息后面，不是一个单独用户输入内容”，存在两种主流的协议实现架构：

### 4.1 方案 A：系统提示词动态追加（Dynamic System Prompt Append）

- **工作机制**：
  在 `run_launch.rs` 启动当次 Run 时，直接消费 `options.context_state`，通过 `assemble_system_prompt_with_stages` 或 `ContextInjector` 将其作为独立小节渲染进当次 Run 的 `system_prompt`：
  ```markdown
  <Base System Prompt>

  ## 当前环境状态

  当前已切换到模型 ornith:latest（服务商 ollama）。权限模式：full。思考档位：Max。
  ```
- **线网输出**：
  - OpenAI / Ollama：随首条 `role: "system"` 发出；
  - Anthropic：随顶层 `system` 字段发出。
- **优点**：
  - 纯粹的系统角色，语义最标准；
  - 绝不产生独立对话回合，零多余 LLM 调用。
- **Prompt Cache（KV 缓存）致命缺陷分析**：
  1. **切换模型场景**：
     - 如果用户从 Claude 切换到 Ollama `ornith:latest`，由于底层模型已改变，KV Cache 本来就不可能跨模型复用，因此在切换模型时修改 system prompt **不会造成额外的缓存损失**。
  2. **同模型切换权限 / 思考档位场景（高频致命伤）**：
     - 如果用户在同一个模型下，将权限模式从 `ask` 切换到 `full`，或将思考档位从 `Low` 调整为 `Max`；
     - 大模型的 Prompt Cache（无论是 Anthropic 的块级缓存、DeepSeek 的自动前缀缓存，还是 Ollama/llama.cpp 的 KV Cache）**均依赖从 Token 0 开始的严格逐字节一致性**；
     - `system_prompt` 位于所有 Token 的最前端（Token 0..N）。一旦修改 `system_prompt` 中的权限或思考模式文本，**整条会话积累的所有几十轮历史对话（几万 Token）的前缀缓存将全部失效（Cache Busting）**！
     - 导致该轮请求必须全量重新预填充（Prefill），引发严重的首字延迟飙升与 Token 成本浪费。

---

### 4.2 方案 B：当次用户输入上下文信封（User Turn Context Envelope）——【推荐首选】

- **工作机制**：
  在 `run_launch.rs` 构造当次 Run 的用户消息时，如果检测到当次存在 `context_state`，**直接将环境状态作为上下文信封（Context Envelope）与当次用户的业务 Prompt 融合为单条 User 消息**：
  ```markdown
  [系统环境上下文：当前已切换到模型 ornith:latest（服务商 ollama）。权限模式：full。思考档位：Max。]

  用户真实发送的消息正文（例如：帮我重构一下这个函数）
  ```
- **线网输出**：
  随同当次用户消息一次性发出，在线网协议中依然保持单一的 `role: "user"`。
- **优点与全面契合性**：
  1. **100% 契合用户直觉与诉求**：
     正如用户所言：“_是随到用户发送的消息后面，不是一个单独用户输入内容的_”。它紧密依附于用户当次请求，作为背景提示。
  2. **Prompt Cache 极致友好（零缓存失效）**：
     - 会话的历史对话部分（Turn 1 到 Turn N-1）以及前面的 System Prompt **保持 100% 逐字节不变**！
     - 历史前缀缓存 100% 命中；
     - 包含 `[系统环境上下文：...]` 的变动仅仅发生在对话的最尾部（Tail），尾部增量输入天然不会破坏前面的缓存前缀。
  3. **零多余 LLM 调用与零空转唤醒**：
     - 当次 Run 一并处理，模型在阅读问题的同时理解了当前的环境状态；
     - 彻底免除 `PendingMessageQueue` 的二次唤醒，不再触发孤立的 `idle-resume`。
  4. **模型理解意图极佳**：
     - 模型很自然地知道：“从本条指令开始，我拥有 full 权限且处于 Max 思考模式”，并在当次回答中立即生效。

## 五、缺陷根因总结与整改行动指南

### 5.1 根因总结（Root Causes）

1. **队列职责越界**：
   `PendingMessageQueue` 在架构设计中本是处理**跨 Run 异步后台事件（Timer/Cron/Watchdog/Subagent Complete）**的接线通道。将其挪作“前端 UI 配置变更”的传递通道，是典型的职责错配。
2. **状态感知时机倒错**：
   状态切换通知在用户点击发送的瞬间便已经确定，它本就属于**当次 Run 的执行上下文**。代码却将其入队推迟到当次 Run 结束后的 Idle 阶段才消费，人为制造了状态与行动的时间差。
3. **线网协议角色伪造**：
   内核盲目使用 `AgentMessageRole::User` 包装系统状态通知，在线网转换层又没有过滤其 `metadata.kind`，最终把机器生成的系统通知以用户身份提交给 LLM，导致 LLM 被迫做出对话响应。
