# 修复执行 —— 防作弊总则（Execution Code of Conduct）

> 适用：所有参与审计修复（PS-01 ~ PS-06）的实现 Agent。
> 目的：防止执行过程中的偷懒、作弊、方式不当、方案劣化——确保每个修复真实、可验证、根因级。
> 关联：各任务书（PS-0x）内的"防作弊条款"为本总则在具体任务上的实例化；两者冲突时以本总则为准。

---

## 1. 红绿纪律（核心）

1. **先红后绿**：每个缺陷修复必须先写红测试（复现原缺陷的失败断言）→ 运行确认失败（红）→ 改实现 → 运行确认通过（绿）。禁止"先改实现再补测试"。
2. **红测试必须真实复现缺陷**：禁止写"必然失败"的占位断言（如 `expect(1).toBe(2)` 再删）；红测试的断言内容必须与缺陷行为直接相关（如"8/8 绕过形态应 Blocked"）。
3. **两段提交**（任务书要求时）：红测试可单独一次提交（含测试文件），修复另一次提交——验收者可通过 git log 核对红→绿证据链。

## 2. 禁止清单（触碰即视为作弊）

| #   | 禁止项                                              | 说明                                                                                                     |
| --- | --------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| B1  | `--no-verify` / `--no-commit` 之类绕过              | 提交必须走 husky/lint 钩子；钩子失败要修复原因而非绕过                                                   |
| B2  | `it.skip` / `test.skip` / `#[ignore]`（无书面理由） | 新测试不得跳过；既有跳过项需在报告中说明理由并经调度者同意                                               |
| B3  | 删除/弱化既有断言                                   | 既有测试断言是契约；确需变更（如错误契约 T3.2）必须经任务书明确授权                                      |
| B4  | mock 掉被验证行为                                   | 例：验证"provider 重载"不得 mock 成恒通过；验证"写竞态"不得 mock 掉写路径                                |
| B5  | 用固定 sleep/时序掩盖竞态                           | 并发验证用真实并发（join/barrier/Channel）；禁止 `sleep(1000)` 假装稳定                                  |
| B6  | 伪造/美化测试输出                                   | 报告必须贴真实命令输出（EXIT code + `test result:` 行 + 关键断言）；禁止 `                               |     | true`、禁止只贴成功片段 |
| B7  | 声明完成而未实跑                                    | 报告的每个验证项必须对应实际执行过的命令；未执行必须明说"未跑"                                           |
| B8  | 恒真断言                                            | 新断言不得是 `expect(1).toBe(1)` 或 `assert!(true)`                                                      |
| B9  | 擅自扩大改动面                                      | 只改任务书分配的文件/模块；发现的新问题记录上报，不顺手改（防范围蔓延掩盖质量）                          |
| B10 | 绕近路修复                                          | 必须根因修复：禁止用 `unwrap_or_default()` 吞错、`allow(dead_code)` 遮掩、注释掉报错行、把错误降级为静默 |

## 3. 实跑报告义务

每个任务报告必须包含：

1. **验证命令与输出**：如 `cargo test -p conex-sandbox` → 贴 `test result: ok. N passed` 行；`npx vitest run <file>` → 贴 EXIT 与通过数。
2. **红→绿证据**：红测试阶段输出（失败断言行）+ 修复后输出（通过断言行）。
3. **回归范围**：任务书指定的回归命令（如 `cargo test --workspace`）全量结果；未跑全量的必须列出跳过理由。
4. **代码位置**：新增/修改的函数与文件清单（文件:行号）。
5. **诚实边界**：不确定的、未覆盖的、依赖外部条件的，明说"未验证/风险"——宁可承认不完整，不可虚报。

## 4. 范围与规范纪律

1. 只改任务书分配的文件；同文件冲突按调度者排定的串行顺序执行。
2. 新增代码遵循项目规范：中文注释（UTF-8 无 BOM）、不引入新 unwrap（生产路径）、类型安全（TS strict / Rust 无 `any`）、错误类型化。
3. 修复必须带"为什么这样修"的注释（根因 vs 绕近路一目了然）。
4. 发现任务书未覆盖的真实问题 → 记录到 `docs/organization/audit/plan/99-EXECUTION-FINDINGS.md`（编号 + 位置 + 描述 + 建议），不上报不擅自修。

## 5. 验收流程

1. **自验**：实现者按第 3 节完成实跑报告。
2. **独立验收**：调度者派独立验收 Agent——**不读修复报告**，自行运行任务书验收命令，核对：红绿断言是否真实、输出是否与报告一致、是否有禁止项痕迹（git log 查 `--no-verify`、查 skip/ignore 新增）。
3. **抽样复核**：对每个域至少 1 项做"攻击性复核"（尝试绕过修复看是否防住）。
4. 验收不通过 → 打回修复者补正，不直接代改。

## 6. 执行节奏

1. 每域一批（安全/CI/数据/会话/前端），批内任务按任务书依赖并行/串行。
2. 每批完成 → 全量回归（cargo test --workspace + tsc + 相关 vitest + 门禁脚本）→ 调度者确认 → 提交。
3. P0 批优先且独立验收；P1 按域批；P2 批次最后。
