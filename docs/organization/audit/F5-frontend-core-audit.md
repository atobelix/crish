# F5 前端核心层严格代码审计报告

- 审计日期：2026-08-07
- 审计范围：`apps/crish-desktop/src/api/`（transport/、chat-bridge/、session-persistence/、StreamRenderBuffer.ts、streamTextBatcher.ts、tauriInvoke.ts、engineConfig.ts、engineStatus.ts、chatApi.ts、clientApi.ts、streamStop.ts、streamDiag.ts、migrateFromLocalStorage.ts）+ `src/services/ConnectionManager.ts`
- 方式：只读，逐文件逐行核读 + Rust 侧契约交叉验证（session-loop streaming.rs、conex-types events.rs、agent-workbench core_event_bridge.rs / engine.rs）+ 既有测试断言核对
- 严重度定义：P0=可致数据丢失/权限越界/崩溃；P1=明确缺陷，正常或常见路径可触发；P2=边界缺陷，特定场景触发或行为不一致；P3=文档/冗余/低风险边界

## 一、总体结论

前端核心层整体工程质量高：命令清单双源校验（manifest + commandMap 幽灵门禁）、事件解析双路径（生成解析器 + 宽容归一器收敛单入口）、三态 invoke 结构化错误、审批 fail-closed 兜底（`approval-resolved` 未知决策归 denied）、refcount 数据面路由、Web Locks 设置锁等设计均扎实。**未发现 P0 级问题**。

但存在 **4 个 P1**，集中在两类：① **持久化写模型无批次戳/无串行队列**——并发批次「最后写者胜」被测试显式固化（旧数据覆盖新数据为已接受契约），在 debounce 未覆盖的 IPC 飞行期可造成已提交消息回滚消失；② **取消与启动竞态**——流启动未就绪期间点停止，run 仍会启动。另有 P2 × 11（超时无 abort、错误重试对写命令非幂等、超大流块拆帧死代码、run-terminal 未知值 fail-open、LS quota 静默截断等）与 P3 × 8。

## 三、类型安全与 wire 契约（维度 6）专项结论

- **严格面**：T6 生成解析器 `parseEngineEvent`（packages/shared-types/generated/engine）优先，失败才进宽容归一——主路径有 schema 校验；wire 契约字段名（camelCase）与 Rust serde 对齐，抽查 `message-delta`（block.text 为**增量**语义，session-loop streaming.rs:485-506 确认，前端 `assistantText += t` 正确）、`run-terminal`（枚举三值封闭）、数据面事件（runId=None，前端双面隔离）均一致。
- **宽容面**：所有 `as` cast 均发生在「生成解析器失败后」的兜底路径，行为可控；`approval-resolved` 未知决策 → denied（fail-closed，方向正确）；`security-audit` 未知 operation/decision → command-exec/denied（fail-closed）。
- **反例**：F5-09 run-terminal fail-open（唯一方向错误的兜底）；F5-21 无验证透传 cast。

## 四、测试盲区（维度 8）

1. **StreamRenderBuffer 无「单块超限拆帧」用例**——F5-05 死代码未被 64KB/超大 delta 用例捕获（现有测试大概率只覆盖多块场景）。
2. **持久化写竞态测试固化错误契约**——`sessionRustDbWriteModel.test.ts:278-308` 断言「旧批次覆盖新批次」为预期行为，无「防止回滚」用例；建议改写为断言「最终 = 更新批次」。
3. **无 cancel 与启动竞态用例**（F5-04）：mock transport 让 `waitUntilConnected` 挂起 → cancel → 断言 `core_run_task` 未被调用。
4. **无「invoke error 降级」后 SQLite/LS 分叉恢复用例**（F5-01）：模拟一次 error 后 hydrate，断言展示一致性与修复路径。
5. **无超时后底层 invoke 仍执行副作用的断言**（F5-07）——至少断言超时路径记日志。
