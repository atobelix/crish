## 一、战役总原则与反退避铁律

### 1.1 纯逻辑规划与问题同权

- **纯逻辑执行顺序**：所有方案仅包含逻辑依赖、任务单元、文件域与验收断言，**绝对不涉及**工期、人天、人员分配或优先级排序（禁止使用 P0/P1 业务优先级砍项）；
- **所有问题一律同权**：用户未要求排序时，所有列出的缺陷与重构目标优先级完全相同，任何人不得替用户决定“哪个更重要”而忽略其他问题；
- **效果锁不容妥协**：审计报告与用户反馈的问题范围即为修复目标，任何 Agent 无权擅自降级、裁撤功能或用“简化版/MVP 砍功能”敷衍；遇到真正冲突只能在文档中客观标出并请示主控。

### 1.2 禁止退避裁判与复杂度控制

- **禁止退避裁判**：严禁以“太难了”、“方案不成熟”、“业界都用 X”为由否决可行的修复路径或劝退自研。不确定的地方必须通过真实单元测试、集成测试或 CDP 机器真值验证，**严禁把不确定写成不可能**；
- **复杂度控制原则**：
  - 比正常选型多 3 倍复杂度的放弃；
  - 1～2 倍复杂度的可以考虑；
  - **代码量衡量标准**：只要代码量差距在 **3500 行左右以内**的，必须选择架构更优雅、体验更好的方案；
- **严禁打补丁**：严禁盲目遍历循环、基于坐标测距的魔术数字补偿、或临时性兼容代码。必须穿透现象找到架构断层，以原生、精确、高内聚、单向数据流的优雅方案解决；
- **内化融合而非生硬拼凑**：最终方案必须是适合本项目的专属最佳方案，自然内化在软件里。正式最终方案中禁止出现“参考某某软件”字样，必须是经过我们深度内化融合升级后的成果。

## 二、多 Agent 生命周期与协同调度纪律

### 2.1 嵌套禁止与总控架构

- **嵌套绝对禁止**：仅主控 Agent 有权派发子 Agent；子 Agent 深度固定为 1，**工具注册表剔除一切派发子 Agent 工具**；所有子 Agent 由主控统一调度；
- **每轮数量控制**：存活子 Agent 上限不超过 **16** 个；方案调研阶段一般 5~~12 个，方案评审阶段 2~~3 个，收尾决策由主控完成。

### 2.2 接续模式与空返回无限重派

- **接续模式优先**：子 Agent 若任务未完成被迫中断，优先使用接续模式让其继续原任务；
- **空返回处理（网络瞬时故障）**：子 Agent 汇报为空返回或无产出时，**默认是供应商网络瞬时问题而非任务失败**：
  1. 先核查目标文件是否已实际落盘（空返回时常已写完）；
  2. 未落盘则**按原提示词（保持完整长度，绝对不缩短）原样重新派发**；
  3. **不设重试上限**，前 3 次接续重试，4～6 次可拆细重派，累计 6 次以上仍失败才由主控接管；禁止因空返回擅自砍任务范围。

### 2.3 运行环境与命令等待铁律

- **执行环境**：统一使用 **pwsh7（PowerShell 7+）**，禁止使用 Windows PowerShell 5.1 避免 GBK 编码与插值缺陷；
- **定时器最小阈值**：如果设置定时器，最短必须为 **100 秒**；
- **命令等待机制**：命令执行耗时较长时，**最佳方式是等待系统推送通知（Reactive Wakeup）**，严禁高频轮询命令状态。

### 2.4 子 Agent 自主性与品德

- **自主边界**：主控给出任务方向、约束边界和验收标准，子 Agent 在任务边界内拥有充分的技术判断空间；
- **三条通用品德**：诚实报告做了什么和没做什么、绝对禁止偷懒作弊、为自己的产出和项目整体负责；
- **输出长度自适应**：根据任务复杂度自然输出，不刻意压缩有用信息，该长则长，该短则短。

## 三、Git 提交与工作区隔离铁律

### 3.1 提交权与工作区隔离

- **主控独占 Git 提交权**：在战役分析、方案与多轮执行全过程中，**所有子 Agent 绝对严禁执行 `git commit`、`git push` 或任何 Git 操作**；子 Agent 完成任务后把改动保存在工作区，由主控统一审计并提交；
- **严禁任何回撤**：任何 Agent **严禁执行 `git reset --hard`、`git checkout .`、`git restore` 或破坏性 rebase** 覆盖他人已提交或未提交的代码；改错文件必须用精确的 edit 工具修复，不用全局回撤；
- **精准提交限定**：主控提交时必须使用 **`git commit --only <paths...>`** 精确限定本次涉及的文件路径，避免误提交其他并行任务的工作区文件；
- **被吞并处理（不回撤、不重做）**：若工作区改动已被外部定时 Git 流程提交，仅通过 `git show HEAD:<path>` 校验内容完整性——完整则直接通过，缺失则精准追加，禁止回退重做；
- **绝对禁止绕过门禁**：严禁使用 `--no-verify` 绕过 Husky / pre-commit 校验。遇到他人文件的 whitespace 阻塞时，做最小 whitespace 修复解除阻塞。

## 四、反过度设计硬性红线与插件化架构

### 4.1 拔除过度设计与伪沙箱死锁

- **严禁过度设计**：严格遵守反过度设计红线，杜绝内核级黑盒沙箱、无意义的循环熔断器、复杂的深层工具中间件与内存伪缓冲；
- **权限体系极简集中化**：
  - **只读模式（Read-Only / Plan）**：仅允许只读搜索、文件查阅，写操作静默拦截，零弹窗打扰；
  - **标准模式（Standard Workspace）**：工作区内自由读写、常规编译测试自动放行，仅跨目录危险操作提示确认；
  - **完全访问模式（Full Access）**：用户授权后的完全信任执行，**彻底拔除**脱离上下文的 PowerShell 复合删除拦截与私设卡点，允许执行测试、构建与临时文件清理。

### 4.2 官方标准 TypeScript 插件架构

- 系统扩展能力一律收拢为 **TypeScript 插件体系（`@crish/plugin-*`）**，严禁在主界面中生硬内嵌丑陋脚手架：
  1. **MarkdownEditor 插件**（`@crish/plugin-markdown-editor`）：独立文档/笔记富文本编辑器打包为纯 TS 插件，仅在打开文档 Tab 时按需加载；
  2. **Browser 自动化插件**（`@crish/plugin-browser`）：受管浏览器自动化能力插件化，书签/历史导入移入系统设置中心；
  3. **Computer Use 插件**（`@crish/plugin-computer-use`）：系统级键鼠与屏幕感知能力插件化；
  4. **Follow-up 行动建议插件**（`@crish/plugin-follow-up`）：行动建议插件化，子 Agent 上下文与 UI **100% 严格隔离屏蔽**。

### 4.3 原生双轨终端与命令监视器

- **轨道一：原生系统纯终端（Native ConPTY Terminal）**：Rust 基于 `portable-pty` 直连 Windows 原生 **ConPTY**（`pwsh.exe`/`cmd.exe`）+ 前端标准 `@xterm/xterm`，双向字节流直通，支持键盘输入、Tab 补全、上下键历史、ANSI 颜色与 Vim 交互，零多余业务定制；
- **轨道二：AI 命令输出只读面板（Command Output Inspector）**：AI 跑脚本时的无头只读监视器，全要素呈现命令、参数、退出码、耗时与 stdout/stderr 实时日志流，彻底废除伪终端数据混杂。

## 五、设计系统与 UI 交互契约

### 5.1 输入框（ChatComposer）纯净性契约

- **彻底剥离博客排版**：聊天输入框严禁混入 `Heading 1/2/3`, `Bullet List`, `Task List` 等富文本排版扩展；
- **专注 AI 系统指令**：输入 `/` 仅触发 AI 元指令（如 `/clear`, `/settings`, `/compact`, `/help`, `/goal`）与 Skill 指令；
- **弹层坐标绝对锁定**：采用几何探测器确保弹层绝对锁定在输入框光标正上方 8px，全零坐标下严禁挂载 Portal，彻底消除 `(0, 0)` 左上角漂移。

### 5.3 交互细节与色彩规范

- **Tooltip 规范**：始终使用项目自定义 `<Tooltip>` 组件，严禁使用原生 HTML `title` 气泡；
- **输入框与焦点态**：默认不加厚重 `box-shadow`；激活态/焦点态禁止深黑实线边框，灰色混入文本色上限约为 **10%**（常规保持在 3%~6%），温润克制；
- **色彩空间**：UI 与 Token 优先采用 `hsl(h s l / a)` 或 `hsla(...)` 斜杠透明度语法；
- **真实 CDP 验收**：所有 UI 调试与截图必须直接针对 Tauri WebView2 的 `http://127.0.0.1:9222`，严禁在独立浏览器或 mock 数据上冒充验收。

## 六、测试资产保护与门禁修正规范

### 6.1 测试资产神圣不可侵犯

- **测试是资产不是杂物**：`reference/markdown-editor/` 等目录下的全部源码与单元测试**必须 100% 入库保护**，任何会话绝对禁止删除或清理该目录下的测试资产；
- **主仓库 E2E 专项测试保留**：主仓库 `tests/e2e` 下的 markdown-editor 专项 spec 是用户针对性测试，回归时必须全部保留。

### 6.2 门禁分析与修正准则

- **门禁正确性审查**：如果现有某些门禁/测试用例本身具有反作用或逻辑错误，允许对其进行分析与修复；
- **修改透明度**：所有被修改的测试用例与门禁逻辑，**必须在最终的汇总报告中清晰列出改动原因、改动前后对比与逻辑依据**；
- **强制履行验证责任**：修复完成后必须全量运行 `npm run typecheck`、`cargo test --workspace` 与相关单元测试，在确凿的测试绿灯日志下才能宣称完成。

## 七、文档产出与规范动态迭代机制

### 7.1 文档产出规范

- **专用目录**：所有战役产出均放置在 `docs/system-audit-and-redesign/` 对应子目录下；
- **唯一文件名**：主控派发时分配唯一文件名（`NN-*.md`），禁止并发写冲突；
- **探索类配额**：探索类子 Agent 最多写一份文档，中文 UTF-8 无 BOM 编码；
- **汇总索引生成**：每轮收齐全部产出后，主控负责在目录根下生成汇总索引文件（如 `00-summary.md`）。

### 7.2 规范文档动态迭代（追加 ➔ 整理 ➔ 遵守）

- **子 Agent 自由追加**：子 Agent 在执行中发现的新踩坑点、架构缺陷或工程经验，可随时在 `docs/system-audit-and-redesign/rules/` 共享规则文档末尾追加（**只加不删**）；
- **主控定期收敛整理**：每轮跑完后，主控负责将散落的经验去重整理并沉淀进本文档，成为后续轮次必须遵守的正式标准；
- **循环闭环**：每轮派发前提示词直接指向最新规范，形成“执行 ➔ 发现 ➔ 追加 ➔ 整理 ➔ 遵守”的高质量自进化闭环。
