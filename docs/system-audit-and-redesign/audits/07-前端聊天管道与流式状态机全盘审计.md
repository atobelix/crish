## 二、`EventRouter.ts` 去重矩阵与因果缓冲专项审计

### 2.1 归一器默认 `turnIndex: 0` 导致多轮 `message-end` / `turn-start` 假去重误杀

#### 代码事实与位置

- `apps/crish-desktop/src/api/chat-bridge/handlers/eventParser.ts:118-164`
- `apps/crish-desktop/src/api/chat-bridge/EventRouter.ts:312-346`

#### 缺陷还原与时序分析

在 `eventParser.ts` 的 `CORE_NORMALIZERS` 中，若后端事件未提供 `turnIndex`，归一器默认将其赋值为 `0`：

```ts
// eventParser.ts:118-164
'turn-start': (raw) => ({
  type: 'turn-start',
  sessionId: str(raw.sessionId),
  turnIndex: num(raw.turnIndex) ?? 0, // 👈 缺省时恒为 0
  timestamp: str(raw.timestamp),
}),
'message-end': (raw) => ({
  type: 'message-end',
  sessionId: str(raw.sessionId),
  turnIndex: num(raw.turnIndex) ?? 0, // 👈 缺省时恒为 0
  message: raw.message as unknown as AgentMessage,
}),
```

而在 `EventRouter.ts` 的 `buildEventDedupeKey` 中：

```ts
// EventRouter.ts:312-346
if (
  event.type === 'turn-start' ||
  event.type === 'turn-end' ||
  event.type === 'message-end'
) {
  const turnIdx =
    'turnIndex' in event &&
    typeof (event as { turnIndex?: unknown }).turnIndex === 'number'
      ? (event as { turnIndex: number }).turnIndex
      : typeof raw.turnIndex === 'number'
        ? raw.turnIndex
        : null;

  const turnTag = turnIdx !== null ? `turn-${turnIdx}` : 't0';

  if (sequence !== null) {
    return `${event.type}:${messageId || 'm'}:${turnTag}:${sequence}`;
  }
  if (turnIdx !== null) {
    return `${event.type}:${messageId || 'm'}:${turnTag}`;
  }
  // ...
}
```

#### 破坏性后果

1. **实时轨（sequence 为 null 时）**：
   - 因为归一器确保了 `event.turnIndex` 必定为 `0`（数字类型），所以 `turnIdx !== null` 恒为 `true`，`turnTag` 恒为 `'turn-0'`。
   - `turn-start` 产生的去重键恒为 `turn-start:m:turn-0`。
   - 在多轮自主运行循环（Autonomous Multi-turn Loop / Goal Mode）中，若后端在第 2 轮未注入显式 `sequence` 或新 `turnIndex`，第 2 轮的 `turn-start` 将算出与第 1 轮完全相同的键 `turn-start:m:turn-0`。
   - `EventRouter.onMsg` 判定 `this.consumedEvents.has(dedupeKey)` 为真，**直接作为重复事件静默丢弃（`recordSkippedDuplicate`）**！
   - 同理，第 2 轮的 `message-end`（当 `messageId` 为空或跨轮复用占位 id 时）计算出 `message-end:m:turn-0`，导致整段终态合并逻辑被跳过！

### 2.2 因果时序乱序到达缓冲（`pendingToolEnds` 与 `knownStartedTools`）缺陷

#### 代码事实与位置

- `apps/crish-desktop/src/api/chat-bridge/EventRouter.ts:47-49, 89-124`

```ts
// EventRouter.ts:47-49
private readonly pendingToolEnds = new Map<string, BridgeEventEnvelope>();
private readonly knownStartedTools = new Set<string>();
```

#### 缺陷 1：跨轮次同名/相同 ID 工具调用导致因果缓冲击穿

- `knownStartedTools` 是纯 `Set<string>`，仅存储 `toolId`，**完全无视轮次 `turnIndex`**。
- 若 Agent 在 Turn 0 执行工具 `read_file`（toolId: `call-1`），`knownStartedTools.add('call-1')`。
- 在后续 Turn 1 中，若引擎再次复用或生成了相同 ID 的工具调用 `call-1`，且由于 IPC 调度抖动导致 `tool-end` 先于 `tool-start` 到达：
- `EventRouter.handleAgentEvent` 执行检查：
  ```ts
  if (envelope.type === 'tool-end') {
    const toolId = extractToolIdFromEnvelope(envelope);
    if (toolId && !this.knownStartedTools.has(toolId)) {
      // 👈 命中 Turn 0 遗留的 'call-1'，返回 true！
      this.pendingToolEnds.set(toolId, envelope);
      return;
    }
    dispatchEvent(this.env, envelope); // 💥 绕过缓冲，直接分派 tool-end！
    return;
  }
  ```
- **后果**：Turn 1 的 `tool-end` 被错误地判定为「已启动」，直接触发 `onToolSuccess`/`onToolError`，破坏 UI 工具卡状态机，导致前端渲染出尚未启动即已结束的幽灵工具卡。

#### 缺陷 2：流异常终止/取消时 `pendingToolEnds` 悬挂残留与静默丢失

- 当流由于网络错误、用户主动停止（L2/L3 Cancel）或引擎抛出 `run-terminal: failed` 而收口时，`finish()` 会被直接调用。
- `EventRouter` 内部的 `pendingToolEnds` **未做任何清空、上报或排空检查**。
- 若在流结束前有工具因引擎崩溃只发出了 `tool-end` 而缺失 `tool-start`，该事件将永久被死锁在 `pendingToolEnds` 中，既不向诊断系统报告 `causality-lost`，也不向 UI 发出失败补丁。

#### 缺陷 3：`tool-update` 完全脱离因果缓冲轨道

- `tool-start` 和 `tool-end` 建立了因果缓冲，但 `tool-update`（工具执行进度分片）完全直通分派（`dispatchEvent`）。
- 若 `tool-update` 先于迟到的 `tool-start` 到达，由于此时 UI 尚未通过 `onToolStart` 建立工具卡槽位，`tool-update` 将在无宿主状态下被丢弃或产生未定义副作用。

### 2.3 `extractToolIdFromEnvelope` 与 Handler 字段抽取的解析分叉与二义性

#### 代码事实与位置

- `apps/crish-desktop/src/api/chat-bridge/EventRouter.ts:196-254`（`extractToolIdFromEnvelope`）
- `apps/crish-desktop/src/api/chat-bridge/handlers/toolUtils.ts:14-44`（`toolCallFieldsFromEvent` & `toolResultFields`）
- `apps/crish-desktop/src/api/chat-bridge/handlers/toolHandlers.ts:17, 37`

#### 架构断层与双面分叉

`EventRouter` 先通过 `extractToolIdFromEnvelope` 判定工具 ID 并决定是否放入因果缓冲：

```ts
// EventRouter.ts:200-226 (检查 envelope.event)
if (envelope.kind === 'engine') {
  const { event } = envelope;
  if (
    'call' in event &&
    event.call &&
    typeof event.call === 'object' &&
    'id' in event.call
  ) {
    const id = String((event.call as { id?: unknown }).id ?? '').trim();
    if (id) return id;
  }
  // ...
}
```

然而，进入 `toolHandlers.ts` 分派执行时：

```ts
// toolHandlers.ts:17, 37
export function onToolStart(
  env: HandlerEnv,
  envelope: EngineEnvelope<'tool-start'>
): void {
  const { id, name, args, explanation } = toolCallFieldsFromEvent(envelope.raw); // 👈 弃用 envelope.event，重新读 envelope.raw！
  // ...
}
export function onToolEnd(
  env: HandlerEnv,
  envelope: EngineEnvelope<'tool-end'>
): void {
  const resultPayload = envelope.raw.result ?? envelope.raw; // 👈 弃用 envelope.event，重新读 envelope.raw！
  const { id, text, isError, diffs } = toolResultFields(resultPayload);
  // ...
}
```

- **问题根因**：`eventParser.ts` 已经执行了严格解析与宽容归一（将 `tool_call_id`、`callId` 等收敛进 `envelope.event`）。`EventRouter` 基于归一后的 `envelope.event` 进行因果缓冲与去重，而下游 Handler 却**绕过归一后的结构，使用独立的 `toolUtils.ts` 去重新解析 `envelope.raw`**。
- **风险**：一旦 `eventParser.ts` 与 `toolUtils.ts` 的字段优先级回退逻辑产生微小漂移（例如 `callId` vs `toolCallId` 的次序），将导致因果缓冲锁定的 `toolId` 与 Handler 实际派发给 UI 的 `toolId` 不一致，因果队列永远无法被正确唤醒！

### 2.4 FIFO 淘汰边界（`MAX_CONSUMED_EVENTS = 2000`）长会话风险

#### 代码事实与位置

- `apps/crish-desktop/src/api/chat-bridge/EventRouter.ts:43-44, 160-168`

```ts
private readonly consumedEvents = new Set<string>();
private readonly MAX_CONSUMED_EVENTS = 2000;

private recordConsumedEvent(key: string): void {
  if (this.consumedEvents.size >= this.MAX_CONSUMED_EVENTS) {
    const oldest = this.consumedEvents.values().next().value;
    if (oldest !== undefined) {
      this.consumedEvents.delete(oldest);
    }
  }
  this.consumedEvents.add(key);
}
```

#### 审计结论

1. **未分级淘汰**：`consumedEvents` 将所有事件的去重键混合在同一队列中。高频事件（如带 sequence 的 `tool-update`、高频 `turn` 心跳）会迅速填满 2000 槽位，过早将初期的关键事件（如 `approval-resolved`、`message-end`）的去重键淘汰出队列。
2. **重连重放风暴下的状态踩踏**：在超长自主任务（Goal Mode 运行数小时、数百轮工具调用）中，若遇到网络闪断后后端全量重发会话历史，已被淘汰出 2000 队列的早期事件将被视作新事件再次分派，导致已完成的工具和消息被重复重放。

#### 破坏性隐患

- **状态不一致**：路径 1 完整执行了工具终态补丁 `buildTerminalToolPatches('complete')`，而路径 3（错误中断）中若有正在运行的工具，未调用 `buildTerminalToolPatches('error')`，导致助手消息状态变为 `error`，但其内部的部分工具调用卡片依然停留在 `running`（转圈）状态！
- **用量统计漂移**：路径 2（Stop）完全绕过了真实 Usage 快照同步（`applyRunUsageSnapshot`），直接采用前端粗略估算的 `applyStopUsageApprox`，导致已消耗 Token 数与引擎真实统计存在不可逆差额。

### 3.2 高并发/快速切换会话下的 `generationMapRef` 清理竞态漏洞

#### 代码事实与位置

- `apps/crish-desktop/src/hooks/chat-stream/useRunStreamingAssistant.ts:156-175`
- `apps/crish-desktop/src/hooks/chat-stream/streamCallbacksInternals.ts:307-328`
- `apps/crish-desktop/src/hooks/chat-stream/streamExecutionHelper.ts:195`

#### 竞态场景还原

1. **Run 1 触发收口**：
   - 引擎返回 `onComplete`，`createCompleteHandler` 执行：
   - `state.draining = true;`
   - `streamManagerRef.current?.delete(sid);`（提前释放 session stream 句柄以允许新输入）。
   - `buffer.flushFinal()` 开始按 rAF 节奏异步排空残余文本（大残余分帧输出）。
2. **用户在排空期间立刻发送 Run 2**：
   - 因为 `streamManagerRef` 已无当前 session，`handleStreamConflict` 放行。
   - Run 2 启动，递增当前会话代次：
     ```ts
     // useRunStreamingAssistant.ts:156-157
     const myGen = (generationMapRef.current.get(sid) ?? 0) + 1; // 假设由 1 变为 2
     generationMapRef.current.set(sid, myGen);
     ```
3. **Run 1 的异步排空结束**：
   - Run 1 的最后一帧 `isFinal` 到达，触发 `finishComplete()` -> `executeStreamCompletion()`。
   - `streamExecutionHelper.ts:195` 执行：
     ```ts
     generationMapRef.current.delete(sid); // 💥 严重竞态：直接把 Run 2 刚写入的 myGen=2 删除了！
     ```
4. **Run 2 的后续帧被全部丢弃**：
   - Run 2 收到模型流式文本分片，`buffer.onFrame` 执行安全检查：
     ```ts
     if (myGen !== generationMapRef.current.get(sid)) return;
     ```
   - 此时 `myGen` 为 2，而 `generationMapRef.current.get(sid)` 已是 `undefined`！
   - **后果**：Run 2 的所有实时流式文本被视为「过期代次」全部静默吞掉，用户界面表现为卡死无字，直到 Run 2 完全结束落盘时才突然跳出全文！

#### 代码事实与位置

- `apps/crish-desktop/src/hooks/chat-stream/helpers.ts:226-234`

#### 审计分析

- `commitStreamToSession` 在持久化写入 `layoutStore`（Immer）后，通过 `queueMicrotask` 清理 `streamingStore`。

```ts
if (state.endTimer) clearTimeout(state.endTimer);
state.endTimer = setTimeout(() => {
  if (!state.cancelled && !state.finished) finish(false);
}, 8000);
```

#### 审计分析

- `state.endTimer` 被两个完全不同语义的超时机制共享：
  1. `createFinishController` 中的审批等待超时（默认 120s）；
  2. `onAgentEnd` 中的终端事件到达兜底超时（8s）。
- 当有审批挂起且引擎先行发出了 `agent-end` 时，`onAgentEnd` 的 8s 超时会**直接覆盖并销毁 120s 的审批等待定时器**！
- 8 秒后，流被强制调用 `finish(false)` 关闭，而此时用户可能仍停留在审批弹窗界面，导致审批完成后后端已无法再将结果同步给已销毁的前端流会话。

### 6.1 `EventRouter` 去重与因果缓冲体系重构建议

1. **修正去重键与归一器默认值耦合**：
   - 区分「信封归一」与「去重判据」：在计算去重键时，若 `raw.turnIndex` 确实不存在且 `raw.sequence` 为空，应判定为实时轨无序列号事件，**放行不作强行去重**，或以唯一的 `runId:messageId:turnCounter` 作为键，防止多轮自主循环中的合法事件被判定为重复。
2. **升级因果缓冲为轮次感知复合键**：
   - 将 `pendingToolEnds` 与 `knownStartedTools` 的键升级为 `${turnIndex}:${toolId}`。
   - 在流终态（`onRunTerminal` / `finish`）时，增加 `flushPendingToolEnds()` 逻辑，若仍有未匹配的 `tool-end`，输出明确的 `causality-unresolved` 诊断日志并作为错误工具补丁通知 UI。
3. **统一字段解析真源**：
   - 下游 Handler（`toolHandlers.ts` 等）统一消费经过 `eventParser.ts` 归一化后的 `envelope.event`，彻底废除绕过信封重读 `envelope.raw` 的重复解析逻辑。

---

### 6.2 收拢流式生命周期为单一控制器（Single Lifecycle Controller）

1. **统一收口管线**：
   - 将 `executeStreamCompletion`、`finalizeStopGeneration` 和 `handleRunError` 中的公共逻辑收敛为统一的 `finalizeStreamRun(reason: 'complete' | 'stop' | 'error', ctx)` 控制器。
   - 保证无论何种原因终态，工具终态补丁、Usage 快照同步、Session 状态流转均按确定性的严格顺序执行。
2. **修复代次清理竞态**：
   - 代次清理不能仅按 `sid` 无脑 `generationMapRef.current.delete(sid)`；
   - 必须改为基于代次或 `assistantMsgId` 的守卫删除：仅当当前会话在 `generationMap` 中的代次与即将关闭的 run 代次一致时才执行删除，若发现已被新 run 占用则安全跳过。

### 6.3 清理死代码、无用选择器并消除逆向分层依赖

1. **拔除 `onTerminalLine`**：从 `StreamCallbacks` 接口与 `useRunStreamingAssistant` 中彻底删除该废弃回调。
2. **移除 `streamingStore.ts` 的未用图片与实体方法**：
   - 移除 `setStreamImages`、`updateStreamImage`、`getStreamImages`、`getStreamEntry`、`clearSessionStreams`；
   - 将 `streamingStore.ts` 精简为仅关注 `text`、`thinking`、`tools` 的高性能流缓冲器。
3. **消除逆向分层依赖**：
   - 移除 `streamingStore.ts` 中对 `components/chat-message/streamMessageViewModel` 的 re-export；
