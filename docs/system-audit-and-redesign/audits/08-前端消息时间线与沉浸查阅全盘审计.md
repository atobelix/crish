## 二、维度一：交错多步骤时间线

### 2.1 `MessageContent.tsx` 渲染期 `setState` 违背 React 纯净契约

- **问题定位**：[`MessageContent.tsx:276-277, 294-301`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-message/MessageContent.tsx#L276-L301)
- **源码还原**：
  ```tsx
  if (streaming) {
    const frame = stripper.next(streamText!);
    streamDelta = frame.appended;
    streamSeq = ++streamSeqRef.current;
    if (frame.resynced) {
      streamImgScanRef.current = { tail: '', seen: new Set() };
      setStreamImgs([]);
      setStreamKey((k) => k + 1); // 🔴 在渲染函数体直接调用 setState
    }
    // ...
    if (fresh.length > 0) {
      setStreamImgs((prev) => { ... }); // 🔴 在渲染函数体直接调用 setState
    }
  }
  ```
- **根因分析**：
  在组件主渲染函数体内直接触发 `setState` 会触发立即重新渲染（Render-phase update）。虽然 React 在特定情况下允许该模式，但此处它依赖了外部可变类实例 `stripper.next(streamText)` 的内部游标状态。
  在 `React.StrictMode` 或并发渲染（Concurrent Mode）下：
  1. 第一次渲染 pass 调用 `stripper.next()` 发现 resynced 并推进了内部状态；
  2. 第二次渲染 pass 重复执行时，`stripper.next()` 不再返回 `resynced=true`；
  3. `streamSeqRef.current` 却在两次 pass 中被递增了两次（`streamSeq` 变成 N+1），导致与 DOM 挂载帧序号脱节，破坏了 `StreamingTextBlock` 的双执行拦截防线。
- **重构建议**：
  将 `streamKey` 与 `streamImgs` 的计算重构为派生状态或收敛至 `useLayoutEffect`，避免在 render body 中产生外部副作用与反向状态调度。

### 2.2 `ChatAssistantMessageRow` 中残留的空转 `useStreamingStore` 性能陷阱

- **问题定位**：[`ChatAssistantMessageRow.tsx:178-183`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-message-row/ChatAssistantMessageRow.tsx#L178-L183)
- **源码还原**：
  ```tsx
  // S4.4: row owns thinking only. Body text/tools live in MessageContent's
  // single shallow streamingStore sub so streamText is not dual-subscribed.
  const _streamThinking = useStreamingStore((s) => {
    if (!live || !sessionId) return undefined;
    return s.byKey[streamStoreKey(sessionId, msg.id)]?.thinking;
  });
  void _streamThinking; // 🔴 订阅了但立即 void 丢弃
  ```

- **根因分析**：
  在早期的架构演进中，思维链置顶在 `ChatAssistantMessageRow`，因此行容器订阅了 `thinking`。在彻底将思维链下放至 `MessageContent` 交错管线后，行容器已经不再消费 `_streamThinking`。
  但该 Hook 依然存在，且在流式输出时每来一个思考 Token，Zustand selector 都会计算出新的字符串并触发 `ChatAssistantMessageRow` 全量重渲染。
- **危害**：

- **重构建议**：
  彻底删除该 `useStreamingStore` 订阅，保持行容器的纯净无流式订阅状态。

### 2.3 `TimelineThoughtSection` 行内 8k~12k 预算在超长流式思考中的首段死锁

- **问题定位**：
  - [`TimelineThoughtSection.tsx:44-46, 163-167`](file:///c:/Software/conex/apps/crish-desktop/src/components/chat-message-row/TimelineThoughtSection.tsx#L44-L46)
  - [`messageWindowDomBudget.ts:24-42`](file:///c:/Software/conex/apps/crish-desktop/src/api/messageWindowDomBudget.ts#L24-L42)
- **源码还原**：
  ```ts
  export function budgetThinkingText(
    text: string,
    cap: number = THINKING_INLINE_CHAR_CAP // 10000 字符
  ): ThinkingBudgetResult {
    const totalChars = text?.length ?? 0;
    if (!Number.isFinite(cap) || cap < 0 || !text || totalChars <= cap) {
      return { displayText: text || '', isTruncated: false, totalChars };
    }
    const safeCap = Math.floor(cap);
    return {
      displayText: text.slice(0, safeCap), // 🔴 永远截取 [0, 10000]
      isTruncated: true,
      totalChars,
    };
  }
  ```
- **现象与断层**：
  当大模型生成长达 20k~50k 的万字思考链时：
  1. 字符数达到 10,000 字后，`displayText` 锁定为前 10,000 个字符；
  2. 随着第 10001~50000 个 Token 持续涌入，行内渲染的文本 **完全静止不更新**；
  3. `useLayoutEffect` 虽然触发追尾滚动 `el.scrollTop = el.scrollHeight`，但由于 DOM 文本没有新节点产生，视口停留在第 10,000 字处；
  4. 用户在主界面看到脉冲动画在闪烁，但文本内容处于假死状态，必须手动打开沉浸式查阅器才能看到正在输出的最新思考内容。
- **重构建议**：
  在 `isLive === true` 阶段：
  - 方案 A（尾窗滑动）：当超长流式输出时，采用滑动尾窗（显示最新的 10,000 字符，并提示「已省略前 N 字」）；
  - 方案 B（实时流式放宽）：流式期间不阻断纯文本增长（纯文本 DOM 成本远低于 Markdown HTML），等流式完成后（`isLive === false`）再应用 10,000 字符截断预算并渲染「查看完整思考链」底栏。

### 3.3 TOC 标题 ID 生成对非 ASCII / 扩展 Unicode 的破坏性清洗

- **问题定位**：[`thoughtWorker.ts:51`](file:///c:/Software/conex/apps/crish-desktop/src/workers/thoughtWorker.ts#L51)
