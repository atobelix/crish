## 三、防 Raw JSON 逃逸与 13 类工具中文语义提取矩阵审计

### 3.1 严重逻辑缺陷：高危分类拦截短路（Tool Priority Collision）

在 `toolHumanDescriptions.ts:72-326` 的 `toolLabelFromArgs` 函数中，按顺序排列了 14 个 `if` 条件分支。存在严重的条件包含与判定劫持：

#### 缺陷 1：`read_url_content` / `read_resource` / `read_browser_page` 被第 3 类 `read_file` 错误拦截

- **代码位置**：`toolHumanDescriptions.ts:108-128` 与 `290-308`
- **现场还原**：
  ```ts
  // 第 3 类：文件读取 / 查阅 (line 108-114)
  if (
    name === 'read_file' ||
    name === 'view_file' ||
    name === 'open_file' ||
    name.includes('read') ||   // 💥 致命短路：所有包含 read 的工具在此被劫持
    name.includes('view')
  ) {
    const path = String(p.absolutepath || p.path || p.filepath || p.file_path || p.targetfile || p.file || '');
    // ...
    return path ? `查看 ${basename(path)}${lineTag}` : '查看文件';
  }

  // 第 14 类：网络访问 (line 290-295)
  if (
    name.includes('fetch') ||
    name.includes('web') ||
    name.includes('browser') ||
    name.includes('read_url')  // 💥 永远无法执行到此处！
  ) { ... }
  ```
- **实际影响**：
  当调用 Antigravity/Browser 插件工具 `read_url_content`（参数为 `Url: "https://github.com"`）或 MCP 工具 `read_resource`、`read_text` 时，由于包含 `'read'`，在第 3 类直接命中。
  但因为网络工具传入的是 `Url` 而非 `path`，最终提取出的标题恒为 **「查看文件」**，网络 URL 语义 100% 丢失！

#### 缺陷 2：`define_subagent` 与 `manage_subagents` 被第 10 类错误提取为「启动子代理」

- **代码位置**：`toolHumanDescriptions.ts:235-246`
- **现场还原**：
  ```ts
  if (
    name.includes('subagent') ||
    name === 'invoke_subagent' ||
    name === 'run_subagent'
  ) {
    const role = String(
      p.role || p.typename || p.description || p.prompt || ''
    ).trim();
    return role && !role.startsWith('{')
      ? `启动子代理：${role.length > 28 ? `${role.slice(0, 27)}…` : role}`
      : '启动协作子任务';
  }
  ```
- **实际影响**：
  - 工具 `define_subagent`（用于注册/定义子 Agent 类型，参数为 `name`, `system_prompt`）被错误展示为 **「启动子代理：[未定义]」** 或 **「启动协作子任务」**；
  - 工具 `manage_subagents`（用于查询列表或终止子代理，参数为 `Action: "kill"`, `ConversationIds`）被错误展示为 **「启动协作子任务」**。

### 3.2 `unwrapPowerShellCommand` 无法解包带值参数的 PowerShell 指令

- **代码位置**：`toolCommandExtractor.ts:11-13`
- **现场还原**：
  ```ts
  const m = s.match(
    /^(?:powershell|pwsh)(?:\.exe)?\b(?:\s+-[A-Za-z]+)*=?(?:\s+"([^"]*)"|\s+'([^']*)'|\s+(.+))?$/i
  );
  ```
- **缺陷分析**：
  正则中的参数部分 `(?:\s+-[A-Za-z]+)*` 仅能匹配无参数值的开关标志（如 `-NoProfile -NonInteractive`）。
  当遇到带有值的选项时（例如 `powershell -ExecutionPolicy Bypass -Command "cargo test"`），`-ExecutionPolicy` 后面的 `Bypass` 没有前导短横线 `-`，正则直接匹配失败。
  后方的捕获组 `m[1]` 错误地将 `Bypass -Command "cargo test"` 识别为内层命令，导致后续人话翻译失败，最终只能回退为生硬的 `'运行 Bypass -Command "cargo test"'`。

### 3.3 `sanitizeHumanLabel` 的粗暴剥离与防护漏洞

1. **合法标点误杀**：
   - `toolLabelSanitizer.ts:37`：`clean.replace(/[{}[\]"]/g, '')`。
   - 当用户或工具执行合法带有双引号的搜索（如搜索 `grep_search(query: '"Authorization"')`）时，双引号被粗暴全部剥离，导致展示变为 `搜索「Authorization」`，丢失了精确匹配语义。
2. **防穿透正则白名单遗漏**：
   - `toolLabelSanitizer.ts:17-19`：
     `^(\{|\[|"(action|taskId|task_id|path|command|CommandLine|Query|TargetFile)":)/i`
   - 仅硬编码了 8 个特定字段名。如果遇到大模型偶发的子字段（如 `"tool_args":`、`"server_name":`、`"parameters":`）且未被首字符拦截时，存在穿透到 UI 的安全隐患。

### 3.4 英文自然语言意图说明（LLM Explanation）被误判为命令并丢弃

- **代码位置**：`toolHumanDescriptions.ts:29-30`
- **现场还原**：
  ```ts
  if (/^[\w./\\:-]+\s+[\w./\\:-]+/.test(t) && !/[\u4e00-\u9fff]/.test(t))
    return false;
  ```
- **缺陷分析**：
  此正则表达式原意是拦截 `git commit -m ...` 这类两个英文单词开头的命令行字符串。
  但对于全英文大模型给出的自然语言 Explanation（例如 `"Running test suite"`, `"Checking build status"`, `"Installing project dependencies"`），由于满足「两个非中文单词开头」且「无中文字符」，被判定为非人话直接返回 `false` 丢弃！
  这导致英文上下文中的优质意图说明被全部抹杀，只能回退到底层硬编码的中文模板。

## 四、两段式分栏容器（InputPane & OutputPane）与大输出保护审计

### 4.1 严重业务逻辑缺陷：大输出「下载日志」下载的居然是已截断残卷！

- **代码位置**：`ToolCallOutput.tsx:51-87` 与 `ToolCallOutputPane.tsx:58-68`
- **现场还原**：
  1. 在 `ToolCallOutput.tsx` 中，当输出超过 2000 行 / 256KB 门限时，计算截断：
     ```ts
     // ToolCallOutput.tsx:82
     return {
       displayOutput: `${sliced}\n… [输出过长，已截断显示前 ${TOOL_OUTPUT_LINE_CAP} 行 / 256 KB]`,
       isTruncated: true,
       totalLines: lines.length,
       totalBytes: bytes,
     };
     ```
  2. 随后将截断后的 `displayOutput` 传给了 `ToolCallOutputPane`：
     ```tsx
     // ToolCallOutput.tsx:108-111
     <ToolCallOutputPane
       toolId={tc.id}
       output={displayOutput}  // 💥 传入的是已截断的残卷字符串！
       isTruncated={isTruncated}
       ...
     />
     ```
  3. 用户在 UI 上看到「⚠️ 输出已超过 2000 行 / 256KB 保护门限」，点击右上方出现的「下载完整日志文件 (.log)」按钮：
     ```ts
     // ToolCallOutputPane.tsx:58-68
     const handleDownloadLog = (e: React.MouseEvent) => {
       e.stopPropagation();
       if (!output) return;
       const blob = new Blob([output], { type: 'text/plain;charset=utf-8' }); // 💥 下载的就是传进来的 output！
       const url = URL.createObjectURL(blob);
       // ... 执行下载
     };
     ```
- **实际后果**：
  用户点击「下载完整日志」本是为了获取被截断的剩余 50,000 行完整构建/测试日志，但实际下载到的 `.log` 文件**竟然依然只有前 2000 行和末尾的省略号**！原始完整输出在容器层被直接丢弃，构成了严重的功能欺骗与体验假象。

### 4.2 输入区 `ToolCallInputPane` 缺乏防护，存在巨量入参导致的 DOM 爆炸崩溃隐患

- **代码位置**：`ToolCallInputPane.tsx:113-158`
- **缺陷分析**：
  - `ToolCallOutputPane` 设计了完善的 2000 行 / 256KB 门限保护，但 `ToolCallInputPane` **完全没有任何大小与行数保护**。
  - 当大模型执行 `write_to_file` 或 `multi_replace_file_content` 写入一个 5MB（50,000 行）的大型源码文件时，`argumentsStr` 或 `parsedArgs.rawObject` 的 `CodeContent` 字段直接通过 `<pre className={styles.toolValPre}>{valStr}</pre>` 完整塞入 DOM 树。
  - 虽然 CSS 设置了 `max-height: 160px; overflow-y: auto`，但 50,000 个文本节点的排版与内存分配会瞬间卡死浏览器主线程（UI Freeze），造成严重的性能与稳定性隐患。

### 4.3 字符长度与字节截断混淆及不必要的 Blob 实例分配

- **代码位置**：`ToolCallOutput.tsx:60-78`
- **缺陷分析**：
  1. `const bytes = typeof Blob !== 'undefined' ? new Blob([full]).size : full.length;`
     在 React 组件的 `useMemo` 计算中，每次文本变动都实例化一个新的 `Blob` 对象来测定大小，产生不必要的垃圾回收（GC）压力；应使用轻量的 `new TextEncoder().encode(full).length`。
  2. 第 77 行：`if (sliced.length > TOOL_OUTPUT_BYTE_CAP) { sliced = sliced.slice(0, TOOL_OUTPUT_BYTE_CAP); }`
     `sliced.length` 是 JavaScript UTF-16 字符串长度（字符数），而 `TOOL_OUTPUT_BYTE_CAP` 是 262,144 字节。对于 UTF-8 中文字符（每个汉字 3 字节），262,144 个字符实际上对应约 786 KB 内存，造成字节限制失准。

### 4.4 剪贴板未捕获异常与 URL 内存释放竞态

1. `ToolCallInputPane.tsx:38` 与 `ToolCallOutputPane.tsx:52`：
   `void navigator.clipboard.writeText(textToCopy);`
   在非安全上下文（如未获焦点的 WebView2 或某些 Linux/远程环境）下，`writeText` Promise 会 reject。由于使用 `void` 忽略且未提供 `.catch()`，会触发未捕获的全局 Promise Rejection 错误。
2. `ToolCallOutputPane.tsx:67`：
   `a.click(); URL.revokeObjectURL(url);` 同步执行。在部分 WebKit/Chromium 引擎内核中，主线程立即销毁 ObjectURL 会导致尚未完成拉取的下载任务被中断。标准做法应为 `setTimeout(() => URL.revokeObjectURL(url), 100)`。

### 详细实施建议清单：

1. **重构 `toolHumanDescriptions.ts` 消除单体大函数**：
   - 提取工具分类策略映射表（Strategy Map / Rule Table），每个工具类别一个独立判定器（如 `resolveShellDescription`, `resolveFsDescription`, `resolveSubagentDescription`, `resolveNetDescription`）；
   - 将宽泛的 `includes('read')` 限制为精确的 `name.startsWith('read_file') || name.startsWith('view_file')`，将 `read_url_content` / `read_resource` 的判定提升到文件读取之前。
2. **重构 `ToolCallOutput.tsx` 修复「下载截断日志」致命缺陷**：
   - `ToolCallOutputPaneProps` 增加 `fullOutput?: string` 属性；
   - `ToolCallOutput` 计算截断时，将 `full` 赋值给 `fullOutput`，`displayOutput` 仅用于渲染；
   - `ToolCallOutputPane` 中的 `handleDownloadLog` 使用 `fullOutput || output` 构造 Blob，确保下载的文件 100% 完整。
3. **给 `ToolCallInputPane.tsx` 增加大入参防御视口**：
   - 定义 `TOOL_INPUT_LINE_CAP = 1000` 与 `TOOL_INPUT_BYTE_CAP = 128 * 1024`；
   - 当 `argumentsStr` 超标时，提供轻量预览并显示「输入参数过长已折叠」提示，彻底杜绝 50,000 行源码塞爆 DOM 节点。
4. **收敛路径抽取工具至单一权威源**：
   - 彻底废除 `workspaceFsApi.ts` 与 `toolFeedback.ts` 中重复且简陋的私有路径抽取函数，统一使用 `toolArgsNormalizer.ts` 的 `parseToolArgsSafe`。
5. **升级单测套件断言深度**：
   - 在 `ToolCallOutput.test.tsx` 中使用 `URL.createObjectURL = vi.fn(...)` 拦截并验证 Blob 实际内容等于原始全量文本，将 9 个测试扩展至 20+ 个全覆盖测试；
   - 在 `toolCardPresenter.test.ts` 中加入所有边界/冲突工具名的魔鬼用例（涵盖 13 类全部变体）。
