## 二、分屏与布局树：拓扑、拖拽与水合一致性缺陷

### 2.1 根节点移除返回值 `null` 破坏防御性契约 (LT-01)

- **代码位置**：[`apps/crish-desktop/src/store/layout-tree/operations.ts:257-275`](file:///c:/Software/conex/apps/crish-desktop/src/store/layout-tree/operations.ts#L257-L275)
- **问题分析**：
  ```ts
  export function removeNodeFromTree(tree: LayoutTree, nodeId: string): LayoutTree | null {
    const { root } = tree;
    if (root.id === nodeId) return null; // 根节点直接返回 null
    const parentInfo = findParent(root, nodeId);
    if (!parentInfo) return null;
    ...
  }
  ```
  `removeLeafFromTree` 直接委托给 `removeNodeFromTree`。当树中仅剩一个 Leaf 节点且用户触发删除时，该纯函数返回 `null`。虽然部分上游调用点写了 `return result ?? tree`，但在复杂的拖拽流水线（如 `mergeTabIntoLeaf`、`applyDrop`）中，多步组合操作假设返回的总是 `LayoutTree` 对象。一旦返回 `null` 传入下一阶段 `findNodeById(tree.root)`，将直接抛出 `TypeError: Cannot read properties of null (reading 'root')`。
- **架构建议**：纯函数层必须返回确定性树。当删除最后一个节点时，应安全返回单 Leaf 干净初始树（`createDefaultTree('chat')`），杜绝运行时 `null` 传播。

### 2.2 拖拽拆分时 Tab 移除导致目标分支塌陷与静默吞并 (LT-02)

- **代码位置**：[`apps/crish-desktop/src/store/layout-tree/operations.ts:702-718`](file:///c:/Software/conex/apps/crish-desktop/src/store/layout-tree/operations.ts#L702-L718)
- **问题分析**：
  ```ts
  // tab 拖拽到 split：从源 leaf 移除 tab，在 target 旁边 split 出新 leaf
  const afterRemove = removeTabFromLeaf(tree, srcLeafId, srcTabId);
  const targetStillExists = findNodeById(afterRemove.root, targetLeafId);
  if (!targetStillExists) return afterRemove;
  ```
  当用户把某个 Leaf 中唯一的 Tab 拖出并试图 Split 到相邻 Target 时：
  1. `removeTabFromLeaf` 发现源 Leaf 为空，自动将其从父 Branch 中移除，并将兄弟节点提升（Flatten）；
  2. 如果 `targetLeafId` 恰好是源 Leaf 的祖先或与源 Leaf 共享需要重组的父分支，Target 节点的拓扑引用可能被改变或在极端情况下丢失；
  3. `if (!targetStillExists) return afterRemove;` 检测到目标失效后，**直接返回移除了 Tab 的破损树**，既没有完成 Split，又把用户的 Tab 给销毁了，出现静默丢 Tab 的恶性缺陷。
- **架构建议**：必须采用原子化操作：先计算目标插入点并挂载新 Leaf，再从源节点安全移除 Tab；或者在操作前使用不可变事务机制，确保如果 Split 失败则完整回滚到原树状态。

### 2.3 冷启动数据恢复校验全灭策略过于激进 (LT-03)

- **代码位置**：[`apps/crish-desktop/src/store/layout-tree/layoutTreeStore.ts:500-508`](file:///c:/Software/conex/apps/crish-desktop/src/store/layout-tree/layoutTreeStore.ts#L500-L508)
- **问题分析**：
  在 `onRehydrateStorage` 中：
  ```ts
  const verdict = restore
    ? validateRestorableLayoutTree(state.tree)
    : { ok: false as const };
  if (!restore || !verdict.ok) {
    applyCleanColdStartOnState(state);
    return;
  }
  ```
  `validateRestorableLayoutTree` 只要遇到任意一项不满足（例如 `orphan-tool-session`——因为异步会话加载延迟，Tool Leaf 绑定的 Session 尚未在当前瞬间注水），就会判定校验失败，将用户的多分屏工作区**无任何二次确认或错误日志地直接抹杀**，强行覆盖为单 Chat 初始态。
- **架构建议**：引入渐进式修复机制（Repair & Sanitize）——当检测到孤儿 Tool 叶时，仅清理该孤儿叶，保留其余完好的分屏拓扑；仅在 JSON 结构严重损坏无法解析时才回退默认单屏。

### 2.4 WorkspaceShell 与 LayoutTree 双向同步断层 (LT-04)

- **代码位置**：[`apps/crish-desktop/src/store/workspace-shell/adapterShape.ts:257-270`](file:///c:/Software/conex/apps/crish-desktop/src/store/workspace-shell/adapterShape.ts#L257-L270)
- **问题分析**：
  系统在 `WorkspaceShellStore`（管理 `openTabs` 和 `rightDock`）与 `LayoutTreeStore`（管理实际渲染树 `tree`）之间存在双重事实来源（Dual Source of Truth）：
  - 当用户在画布上直接通过 Sash 拖拽关闭某个 Tool Leaf（或通过 TabStrip 关闭最后一个 Tab）时，触发的是 `LayoutTreeStore.removeTabFromLeaf`；
  - 但 `WorkspaceShellStore` 中对应 Tab 的 `rightDock.collapsed` 与 `rightDock.activePanelId` 并没有收到反向同步通知，仍保持 `collapsed: false`；
  - 下次用户点击切换 Tab 时，`WorkspaceShellStore` 再次触发 `applyDockToTree`，又把刚刚被用户关闭的 Tool 面板强行弹出来，造成“关不掉的幽灵面板”。

### 2.5 遗留五文件旧工作区与二叉树新系统架构冗余 (LT-05)

- **代码位置**：
  - `src/components/workspace/Workspace.tsx`

  - `src/components/workspace/WorkspaceResizer.tsx`
  - `src/components/workspace/WorkspaceStrip.tsx`
  - `src/components/workspace/WorkspaceChromeBars.tsx`
- **问题分析**：
  在 `src/components/workspace/` 目录下保留了基于 `columns: ColumnState[]` / `groups: GroupState[]` 模型的完整一套画布渲染体系（`WorkspaceCanvas.tsx` 316 行、`Workspace.tsx` 191 行等）。而在 `src/components/binary-tree/` 下已经实现了全套现代二叉树工作区（`BinaryTreeWorkspace.tsx` 等）。
  虽然 `App.tsx` 中使用 `useTreeWorkspace` 旗标控制分支，但实际上二叉树已经是默认且唯一的生产形态，旧工作区代码长期处于维护断层状态，增加了类型冗余、样式污染和心智负担。

## 三、设计系统契约：曲率阶梯、Tooltip 与焦点态全面违背

### 3.1 视觉曲率 4 级阶梯违背（硬编码与魔术数字）

#### 规范基准（4 级阶梯）：

1. **Pills / 胶囊（触发器/徽标）**：`var(--radius-full)`（9999px）
2. **Buttons / 独立功能按钮**：`var(--radius-xl)`（10px）
3. **Containers / 卡片与浮层容器**：`var(--radius-2xl)`（12px）/ `var(--radius-lg)`（8px）
4. **Items / 菜单与列表内部项**：`var(--radius-md)`（6px）

#### 严重违规点：

1. **尺寸 Token 定义异常 (DS-01)**：
   - [`src/styles/tokens.css:777`](file:///c:/Software/conex/apps/crish-desktop/src/styles/tokens.css#L777)：`[data-ui-size='small']` 中将 `--radius-full` 写成 `998px`；
   - [`src/styles/tokens.css:853`](file:///c:/Software/conex/apps/crish-desktop/src/styles/tokens.css#L853)：`[data-ui-size='large']` 中将 `--radius-full` 写成 `1000px`；
   - **危害**：破坏胶囊端头两端半圆的数学不变量，在超宽按钮下可能产生椭圆或变形。全系统必须统一为 `9999px`。
2. **Fallback 值与 Token 实值冲突 (DS-02)**：
   - [`src/components/settings/SettingsUI.module.css:66`](file:///c:/Software/conex/apps/crish-desktop/src/components/settings/SettingsUI.module.css#L66)：`border-radius: var(--radius-xl, 12px);`

3. **全系统 60+ 处硬编码 `border-radius: 999px` (DS-03)**：

### 3.3 焦点态与边框加深规范违背 (DS-09, DS-10)

#### 规范基准：

- 输入框默认禁止重阴影；
- 激活态/焦点态禁止深黑实线边框（禁止 `0 0 0 1px` 黑环或 `#000`）；
- 相对基线，灰色加深混入文本色上限约为 **10%**（常规约 **3%–6%**）。

#### 违规点：

1. **全局 `:focus-visible` 强塞固定 5px 圆角 (DS-09)**：
   - [`src/styles/focus-visible.css:7-10`](file:///c:/Software/conex/apps/crish-desktop/src/styles/focus-visible.css#L7-L10)：
     ```css
     :focus-visible {
       outline: 2px solid var(--focus-ring-color);
       outline-offset: 1px;
       border-radius: var(--radius-sm); /* 5px 固定圆角！ */
     }
     ```
     导致所有获得焦点的 9999px 药丸按钮或 10px 独立按钮，在显示键盘焦点外框时，被强制截断成 5px 圆角矩形，视觉出现严重棱角穿透。
2. **快捷键暗色录制态 `!important` 实线覆写 (DS-10)**：
   - [`src/styles/settings/settings-advanced.css:135-139`](file:///c:/Software/conex/apps/crish-desktop/src/styles/settings/settings-advanced.css#L135-L139)：
