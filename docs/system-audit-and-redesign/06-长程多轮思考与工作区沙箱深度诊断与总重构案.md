## 二、问题一：对话模式下的工作区沙箱越界与 AI 脚本绕过机制

### 1. 现象与 AI 自述分析

**用户提供的 AI 回复现象**：

> _“【你指定的目录 c:/Software/conex/temp_ai_test_workspace 位于当前工具工作区（...\apps\agent-workbench\src-tauri）之外，工作区文件工具会因路径越界拒绝写入。因此我改用了一个可审计的 PowerShell 生成脚本（已执行完并清理）在该目录落盘文件，再以 npm --prefix 方式安装依赖并运行测试。】”_

### 2. 根因剖析（Root Cause）

1. **工作区根目录回退错位**：
   - 当用户在未打开具体项目的会话（纯对话/全局模式）中提问时，前端 `projectStore.getWorkspacePath()` 返回 `undefined`；
   - 随 `core_run_task` IPC 传递给后端的 `cwd` 为 `None`；
   - Rust 壳层与会话循环（`resolve_escape_watch_root(cwd.as_deref())`）执行以下回退：
     ```rust
     cwd.map(PathBuf::from)
        .unwrap_or_else(|| std::env::current_dir().unwrap_or_else(|_| PathBuf::from(".")))
     ```
   - 在开发调试与启动环境下，Tauri 进程的工作目录是 `C:\Software\conex\apps\agent-workbench\src-tauri`；
   - 这导致引擎把工作区沙箱硬性限制在 `src-tauri` 这一子目录下；
   - 当 AI 调用 `write_file` / `read_file` 访问 `c:/Software/conex/temp_ai_test_workspace` 时，`resolve_workspace_path` 中的包含性校验判定目标目录在 `src-tauri` 外部，直接抛出 `[tool.path_escape] Path escapes workspace`。
2. **AI 的自愈绕过逻辑**：
   - 模型的规划能力极强：在发现标准文件读写工具被沙箱阻断后，模型尝试使用未被路径沙箱严格限制的 `shell`（`run_command`）工具，动态生成一个 PowerShell 脚本将文件直接写入目标路径，然后再通过 `npm --prefix` 完成安装与测试。
3. **Windows 路径归一化盲区**：
   - `crates/agent-tools/src/tools/mod.rs` 的 `normalize_for_compare` 遗漏了 Windows `\\?\` UNC 前缀剥离；
   - `has_symlink_below_root` 对 Windows 目录联接（NTFS Junction）存在过度防御，直接将合法 Junction 视为符号链接逃逸拒绝。

### 3. 标准化架构设计与修复方案

1. **纯对话状态（无工作区）的显式建模**：
   - 明确「无工作区会话」与「绑定项目会话」的边界；
   - 纯对话模式下，如果任务需要操作文件系统，允许 AI 提议目标工作目录（如 `c:/Software/conex/temp_ai_test_workspace`），在获得用户授权后动态更新当前会话的 `activeWorkspace` / `cwd`。
2. **默认工作区回退策略治理**：
   - 当 `cwd` 为 `None` 时，禁止回退到未知的内部进程目录 `src-tauri`，而是回退到 Conex 应用根目录（通过 `host_paths::workspace_root()` 解析）或用户主目录，或者在 ToolContext 标记 `unrestricted_with_approval` 模式。
3. **Windows 路径比较健壮性加固**：
   - 在 `crates/agent-tools/src/tools/mod.rs` 中统一剥离 `\\?\`、`\\.\`、`\\?\UNC\` 前缀，统一盘符大小写与正反斜杠。

## 三、问题二：后台任务管理器（BackgroundTaskManager）未接线断点

### 1. 现象与报错

AI 在执行长时间命令（`npm install`）转入后台任务 `task-0` 后，尝试调用 `background_task` 工具查询状态，抛出：
`[common.unsupported] background_task 未接线：后台任务管理未装配（引擎侧注入 BackgroundTaskManager 后可用）`

### 2. 根因剖析

1. **壳层实现已就绪，但传递链中途断裂**：
   - `apps/agent-workbench/src-tauri` 中已经完整实现了 `BackgroundTaskRegistry` 与 `RunAwareBackgroundManager`，并在应用启动时初始化为单例；
   - 但在 `crates/session-loop/src/exec_single.rs:299` 组装单次工具调用的 `ToolContext` 时，字段被硬编码为：
     ```rust
     // exec_single.rs:299
     background: None,
     log_root: None,
     ```
2. **工具层的不对称表现**：
   - `ShellCommandTool` 在构造时持有了注册期的 fallback manager，因此命令转后台能够成功；
   - 但 `BackgroundTaskTool`（查询/停止任务）是纯无状态工具，只从执行期的 `ctx.background` 获取管理器；
   - 由于 `ctx.background` 恒为 `None`，导致 `BackgroundTaskTool` 每次调用都直接崩溃报错。

### 3. 修复方案

1. 在 `crates/session-loop/src/tool_exec.rs` 与 `loop_options.rs` 中增加 `background: Option<Arc<dyn BackgroundTaskManager>>` 与 `log_root: Option<PathBuf>` 字段；
2. 在 `AgentSessionLoop::with_options` 中将 options 赋值给 `tool_ctx`；
3. 在 `exec_single.rs` 中修改为 `background: ctx.background.clone()` 与 `log_root: ctx.log_root.clone()`；
4. 在 `apps/agent-workbench/src-tauri/src/run/run_launch.rs` 组装 `SessionLoopOptions` 时注入 `state.background` 与日志目录。

## 四、问题三：思考内容碎片化（"TheTheThe..."）与多轮展示延迟

### 1. "TheTheThe...All...package" 根因（已修复）

- **根因**：前端 `EventRouter.ts` 的 `buildEventDedupeKey` 将无 `sequence` 的流式增量 `message-delta` 统一映射为 `${type}:${messageId}`。导致同一个 assistant 消息流中只有第 1 个 Token（如 `"The"`）被放行，后续几千个 Token 全部被作为“重复事件”拦截丢弃。
- **修复**：对无 `sequence` 的 `message-delta` 显式返回 `null`（放行），全量 297 个测试 100% 通过。

### 2. Rust 双轨事件发射延迟

- **机制审查**：
  - **实时轨（Real-time Track）**：仅 `ThoughtDelta` 与 `TextDelta` 能够通过 `BridgeDeltaSink` 即时 push 到 IPC；
  - **收口批量轨（Terminal Track）**：`ToolStart`、`ToolEnd`、`TurnStart`、`TurnEnd`、`MessageEnd` 全部仅保存在内存 `state.events` 中，直到整个多轮循环全部结束才统一批量发射给前端；
- **优化方向**：
  - 前端流式管理器通过实时到达的 `ThoughtDelta` 保持思考流持续刷新；
  - Rust 侧后续可将 `ToolStart` / `ToolEnd` 接入轻量级实时通知轨，实现工具卡片的逐帧实时登场。

### 3. 前端思考窗 UI 交互优化

- **高度放宽**：将 `.thinkingFoldBody` 的 `max-height` 从仅 4 行（84px）放宽至 `260px`（live 态）与 `480px`（展开态）；
- **吸底追尾滚动（Sticky Auto-Scroll）**：在 `MessageThinkingSection.tsx` 中增加 `useLayoutEffect` 驱动的滚动同步，当用户未主动向上翻看时，随新 Token 生成自动平滑滚动至底部；
- **解除强制锁定**：移除 `aria-disabled` 与思考中禁止点击的限制，允许用户在模型思考期间自主展开或收起思考块。

## 五、问题四：工具卡片运行期黑盒与时间线割裂

### 1. 运行中不可展开限制（Lockout）

- **代码断裂点**：`toolCardPresenter.ts:348` 中 `if (tc.status === 'running') return false;` 硬编码禁止展开；
- **修复方案**：当 `status === 'running'` 时，只要工具包含输入参数（`tc.arguments`）或已有输出，即允许展开卡片，并在内部展示实时运行时间、参数 JSON 与执行进度。

### 2. 多轮思考交错时间线改造

- **现状**：目前所有轮次的思考被累加为 `msg.thinking` 单一字符串，置顶在气泡最上方；
- **重构方案**：
  1. 在 `toolPresentationTypes.ts` 中为 `AssistantTimelineItem` 增加 `{ kind: 'thought', content: string, key: string }`；
  2. 升级 `timelineNormalizer.ts`，将每个工具调用前后的 `thought` 块切片交错内嵌在时间线中；
  3. 实现如现代前沿 Agent 一致的清晰“阶段推理 ➔ 工具执行 ➔ 结果评估 ➔ 下一步决策”的因果视觉链条。
