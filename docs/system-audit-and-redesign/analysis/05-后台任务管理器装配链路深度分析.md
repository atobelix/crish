## 一、执行摘要与问题背景

### 1.1 致命结构化报错现场

在 Conex / Crish 桌面客户端运行期间，当 AI 智能体执行耗时较长的后台任务命令（如使用 `shell_command` 指定 `mode: "auto-background"` 或 `mode: "daemon"`）后，智能体收到命令已转入后台托管的返回结果（携带生成的 `taskId: "task-0"`），紧接着尝试使用系统提供的 `background_task` 工具查询该任务的状态或读取其输出日志，系统却直接抛出致命结构化错误：

```json
{
  "code": "common.unsupported",
  "message": "background_task 未接线：后台任务管理未装配（引擎侧注入 BackgroundTaskManager 后可用）"
}
```

### 1.2 故障现象的严重危害

1. **AI 闭环控制断裂**：AI 发起后台构建、依赖安装或守护进程后，完全无法感知任务的存活、退出码或控制台输出，导致后续多轮对话进入盲等或误判崩溃；
2. **行为极其困惑（伪成功）**：AI 看到 `shell_command` 明确返回了后台任务 ID（表明后台机制“可用”），但一调用 `background_task` 工具却提示“未接线”（表明后台机制“不可用”），造成 AI 在多轮规划中陷入逻辑冲突；
3. **伴生静默降级**：伴随 `background` 未接线，`ToolContext.log_root` 同样未接线，导致同步命令执行输出超限时无法将完整日志溢出落盘（spill to disk），前端和模型均丢失 `logPath`。

## 二、核心机制与不对称性根因深度剖析

### 2.1 架构设计意图：构造期解耦与执行期会话注入

在 R3 T9 / T-AB-02 架构规范中，`agent-tools` 内置工具的设计原则为**构造期无状态化、执行期上下文动态注入**：

- **`ToolRegistry` 注册期**：工具实例全局共享，不绑定具体会话 ID、工作区路径或会话级服务；
- **`ToolContext` 执行期**：在工具被调用的时刻（`Tool::execute(&self, ctx: &ToolContext, args: Value)`），由上层执行器（`ToolExecutor`）组装包含 `session_id`、`workspace_root`、`abort_token`、`ask` 审批通道、`write_claims` 互斥表、`output_dir` 产出目录、`background` 后台管理器、`log_root` 日志根的执行上下文。

### 2.2 为什么 `shell_command` 转后台能够成功？（双通道回退机制）

审查 `crates/agent-tools/src/tools/shell.rs` 的实现逻辑：

1. **注册期持有**：

   ```rust
   // crates/agent-tools/src/tools/shell.rs:185-191
   pub(crate) fn with_background_manager(
       default_timeout_ms: u64,
       max_output_bytes: usize,
       trash_root: Option<PathBuf>,
       audit_sink: Arc<dyn SecurityAuditSink>,
       background_manager: Option<Arc<dyn BackgroundTaskManager>>,
   ) -> Self { ... }
   ```

   在 Tauri 壳层引擎初始化（`apps/agent-workbench/src-tauri/src/engine_build.rs:305-306`）时，`BuiltinToolConfig` 显式注入了 `background_manager: Some(Arc<RunAwareBackgroundManager>)`。因此，`ShellCommandTool` 实例的内部字段 `self.background_manager` 成功持有了后台任务管理器的引用。

2. **执行期双通道 Fallback**：
   ```rust
   // crates/agent-tools/src/tools/shell.rs:304-307
   let manager = ctx
       .background
       .clone()
       .or_else(|| self.background_manager.clone());
   ```
   当 `shell_command` 工具执行时，优先读取 `ctx.background`；当 `ctx.background` 为 `None` 时，**优雅回退至注册期的 `self.background_manager`**！
   因此，`shell_command` 能够顺利调用 `manager.adopt(req).await`，将子进程的所有权成功移交给 `BackgroundTaskRegistry`，并生成 `task-<seq>` 成功返回给 AI。

### 2.3 为什么 `background_task` 工具却直接报错 `[common.unsupported]`？（严格单通道无回退）

审查 `crates/agent-tools/src/tools/background_task.rs` 的实现逻辑：

1. **构造期零依赖**：

   ```rust
   // crates/agent-tools/src/tools/background_task.rs:47-49
   pub(crate) fn new() -> Self {
       Self { def: ToolDefinition { name: "background_task".to_string(), ... } }
   }
   ```

   `BackgroundTaskTool` 结构体本身**完全没有** `background_manager` 字段，其设计严格遵循了 R3 T9 的执行期动态注入契约。

2. **执行期硬拦截**：
   ```rust
   // crates/agent-tools/src/tools/background_task.rs:117-122
   let Some(manager) = &ctx.background else {
       return Err(ToolError::new(
           codes::COMMON_UNSUPPORTED,
           "background_task 未接线：后台任务管理未装配（引擎侧注入 BackgroundTaskManager 后可用）",
       ));
   };
   ```
   `BackgroundTaskTool` 在分发 `list` / `status` / `read_log` / `send_input` / `kill` 前，必须从 `ctx.background` 解包出管理器。若 `ctx.background` 为 `None`，则立即返回结构化错误。

### 2.4 根因对比总结表

| 维度           | `shell_command` 工具                | `background_task` 工具              | 差异后果                                 |
| :------------- | :---------------------------------- | :---------------------------------- | :--------------------------------------- |
| **结构体字段** | 持有 `self.background_manager` 选项 | 仅持有 `def: ToolDefinition`        | 构造期形态不同                           |
| **注册期注入** | 经 `BuiltinToolConfig` 注入成功     | 未在注册期注入（零字段）            | `shell` 有静态兜底，`background_task` 无 |
| **执行期解析** | `ctx.background.or_else(            |                                     | self.background_manager)`                | `let Some(manager) = &ctx.background` | `shell` 走通回退，`background_task` 硬拦截 |
| **运行时表现** | **转后台成功**，返回 `task-0`       | **直接抛错** `[common.unsupported]` | **全系统表现出严重的不对称与逻辑分裂**   |

## 四、Tauri 壳层后台任务管理器生命周期全景

为了实现无缝装配，必须完整理解 Tauri 壳层内部 `BackgroundTaskRegistry` 与 `RunAwareBackgroundManager` 的生命周期和职责边界：

```
[main.rs]
  ├── 1. 实例化: background_tasks = Arc::new(BackgroundTaskRegistry::new())
  │     ├── 日志根: host_paths::app_dir()/logs/tasks
  │     └── 保留期: 30 分钟 (finished_at + retention)
  ├── 2. 状态托管: app.manage(Arc::clone(&background_tasks))
  ├── 3. 构造状态机: CoreRunState::new(..., Some(Arc::clone(&background_tasks)))
  │     └── 包装为装饰器: background = Arc::new(RunAwareBackgroundManager::new(inner))
  ├── 4. 事件消费器装配:
  │     ├── background_tasks.set_task_event_consumer(core_state.task_events())
  │     └── background_tasks.set_event_bridge(bridge.clone(), String::new())
  └── 5. 引擎注册面注入:
        └── EngineHandle::new_with_spawner(Some(Arc::clone(&background) as Arc<dyn BackgroundTaskManager>), ...)
```

### 4.1 `BackgroundTaskRegistry`（原生注册表核心）

- **存储与索引**：使用 `Mutex<HashMap<String, Arc<TaskHandle>>>` 存储任务句柄，采用原子递增计数器 `task_seq` 分配 `task-0`, `task-1`...
- **日志与监控**：
  - 子进程 stdout/stderr 通过异步管道读取，分别标记 `[out]` / `[err]` 行前缀落盘至 `<task_id>.log`；
  - 内存中维护 `OutputPreview`（有界双端队列，保留最新 200 行/64KB 用于 `status` 的 `tail` 快速预览）；
  - 每 512 行生成 `.meta.json` checkpoint，支持行号范围二分快速索引。
- **容量淘汰与归档清理**：
  - 容量上限 `MAX_BACKGROUND_TASKS = 200`，超限时 FIFO 淘汰最旧条目（运行中任务先强杀收尾，保留磁盘 `.log`）；
  - 任务终止后保留 30 分钟，周期归档线程自动清理内存条目与 `.meta.json`，保留 `.log` 用于审计。

### 4.2 `RunAwareBackgroundManager`（运行感知装饰器）

- **`owner_run_id` 自动注入**：
  在 AI 工具执行 `shell_command` 时，由于底层的 `BackgroundAdoptRequest` 构造处无法直接知晓外层当前的 `run_id`，装饰器在 `adopt()` 调用进入时，自动检查 `req.owner_run_id`；若为空，则注入当前活跃的 `current_run_id`。
- **生命周期挂钩**：
  - **Run 启动**（`run_launch.rs:788`）：调用 `state.background.set_current_run(&run_id)`；
  - **Run 成功收口**（`run_launch.rs: drive_run_loop`）：调用 `state.background.clear_current_run(&run_id)`；
  - **Run 异常失败**（`run_launch.rs: finalize_failed`）：调用 `state.background.clear_current_run(&run_id)`。
- **会话级存活铁律**：
  Run 的结束**绝不清理注册表，也绝不级联杀死任务**。后台任务生命周期与宿主应用/会话绑定，即使发起该任务的单次 Run 已经结束，任务依然在后台持续运行并记录日志，后续 Run 仍可随时查询。

## 六、完整代码修复方案设计

### 6.1 修改 1：`crates/session-loop/src/tool_exec.rs`

在 `ToolExecCtx` 中增加 `background` 与 `log_root` 字段：

```rust

    pub run_id: String,

    pub cwd: Option<String>,
    pub parent_run_id: Option<String>,
    pub workspace_root: Option<PathBuf>,
    pub write_claims: Option<Arc<WritePathRegistry>>,
    pub explore_docs_quota: Option<ExploreDocsQuotaContext>,
    pub output_dir: Option<Arc<dyn agent_tools::tools::output_dir::OutputDirResolver>>,
    pub note_backend: Option<NoteBackendHandle>,
    /// 后台任务管理器（T-AB-02 / T-AB-13：None = 未接线，background_task 返回 common.unsupported；
    /// 引擎侧注入 RunAwareBackgroundManager 适配）
    pub background: Option<Arc<dyn BackgroundTaskManager>>,
```

## 八、总结与修改清单

通过本次深度审查，完全明晰了 AI 执行后台任务报错 `[common.unsupported]` 的根本原因：**`ShellCommandTool` 凭借注册期持有的 fallback 掩盖了执行期 `ctx.background == None` 的缺陷，而 `BackgroundTaskTool` 严格依赖 `ctx.background`，最终在 `exec_single.rs:299` 的硬编码占位处触发拦截**。
