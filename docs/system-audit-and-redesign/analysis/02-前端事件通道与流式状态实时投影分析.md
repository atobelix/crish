# 前端事件通道与流式状态实时投影深度分析报告

**分析师角色**：前端事件通道与流式状态实时投影分析师
**被分析模块**：`EventRouter.ts` → `ConnectionLifecycle.ts` → `useRunStreamingAssistant.ts` → `StreamRenderBuffer` / `streamTextBatcher` → `streamingStore.ts` → `ChatAssistantMessageRow.tsx` / `MessageContent.tsx` / `MessageThinkingSection.tsx`

---

## 一、核心结论速览

在长程多轮 Agent 任务中，中间工具调用与思考过程**未实时呈现**、用户感知为“全程无动静，直到最后总结突然弹出”的**第一核心致命根因**是：

> **`EventRouter.ts` 的事件幂等去重键（`buildEventDedupeKey`）在无 `sequence` 的实时 IPC 流中，对 `tool-start`、`tool-end`、`turn-start`、`turn-end`、`message-end` 等事件全部回退为 `${event.type}:${messageId}`。**
> **这导致第 1 个工具之后的所有中间工具调用（`tool-start` / `tool-end`）以及后续轮次的思考与文本收口事件，被 `EventRouter` 误判为重复事件并在入口处被【静默全部丢弃（Silently Dropped）】！**

配合以下次级隐患共同构成了“假死”体感：

1. **思考占位误清（Thinking Dropped on First Chunk）**：首个正文 Token 到达时，`handleThinkingResetOnChunk` 误将尚未 flush 的 `thinkingBatcher` 队列直接 `drop`。
2. **`isThinkingMsg` 语义泛化与旋转菊花遮蔽**：`isThinkingMsg` 在整个 run 生命周期（`processing`）常驻为 `true`，当无思考文本时持续展示“思考中 …”，掩盖了实际处于工具执行期的状态。

## 四、具体修复与重构方案

### 1. 修复 `EventRouter.ts` 的 `buildEventDedupeKey`（P0）

针对工具域事件，必须使用 `toolId` 区分；针对轮次域与 `message-end`，必须引入 `turnIndex` 或在缺少 `sequence` 时放行透传（返回 `null`），禁止按 `messageId` 粗暴拦截！

### 2. 修复 `handleThinkingResetOnChunk` 避免误清思考（P1）

在清理占位符前，检查 `streamingStore` 是否已接收到真实的思考流；若已有真实思考，严禁调用 `thinkingBatcher.drop()`。

### 3. 优化工具启动首帧响应（P2）

确保 `tool-start` 事件在到达前端后立即触发 `flushNow`，使得工具卡片 0 延迟上屏。
