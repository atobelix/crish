## 二、专题审查 1：交错步骤时间线边界、动态折叠与虚拟滚动视口跳动（Jank）

### 2.1 动态折叠高度反向震荡（Height Oscillation）击穿滚动吸底锁定

#### 【缺陷机理剖析】

方案 02 第 3.4 节与第 5.6 节规定：当进入新一轮步骤（`Turn k+1`）时，当前正在执行的步骤（`Turn k`）自动平滑折叠为胶囊行（高度 32px），新步骤自动展开。

在代码实现中（`MessageContent.tsx` 与 `TimelineThoughtSection.tsx`）：

1. `Turn k` 包含展开的思考内容（高度约 240px）与运行中工具卡片（高度约 120px），总高度约为 **360px**；
2. 当收到 `Turn k+1` 的 `turn-start` 事件瞬间，React 重新渲染：`Turn k` 的 `isOpen` 变为 `false`，瞬间收缩为 **32px**（高度瞬间减少 **-328px**）；
3. 此时 `Turn k+1` 刚刚初始化，仅包含占位 Spinner，高度仅为 **32px**；
4. 整条 `SessionMessage` 的 DOM 高度在 **1 个渲染帧内发生暴跌：$\Delta H = -296\text{px}$**；
5. 在现存滚动吸底逻辑中：
   ```typescript
   // ChatMessageList.tsx / MessageThinkingSection.tsx 常用吸底检测
   const isAtBottom = scrollHeight - scrollTop - clientHeight <= 40;
   userScrolledUpRef.current = !isAtBottom;
   ```
   当容器高度暴跌 296px 时，若外层视口尚未触发新的 `scrollToBottom`，`scrollTop` 相对位置瞬间超出底部判定阈值，系统误判定为“用户主动向上滚动”，将 `userScrolledUpRef.current` 置为 `true`，**导致长程任务在进入第 2 轮后自动滚动彻底停滞，用户必须手动拖动滚动条跟读！**

#### 【方案 02 漏洞定位】

- `02-流式管道与交错时间线独立总方案.md:397-400`（仅有文字动效描述，完全未给出高度突变补偿算法）；
- `02-流式管道与交错时间线独立总方案.md:1741-1753`（`TimelineThoughtSection` 的滚动监听仅作用于局部，未向上通知外层 `VirtualScrollManager` 与 `ChatMessageList`）。

#### 【强制修正方案】

1. 引入**全局流式吸附锁（`stickToBottomLock`）**：在 Run 处于 `processing` 状态且用户未发生主动物理 Wheel 事件期间，不论 DOM 高度产生何种正向膨胀或负向收缩，均在 `useLayoutEffect` 中强制锚定 `container.scrollTop = container.scrollHeight`；
2. **高度过渡动画抑制与几何补偿**：折叠历史步骤时，采用 CSS `transition: height 150ms ease-out` 渐变收缩，并配合 `ResizeObserver` 节流通知，严禁单帧瞬时坍塌 300px。

### 2.2 `VirtualScrollManager` 估高模型失真引发历史列表视口剧烈跳动

#### 【缺陷机理剖析】

现存 `VirtualScrollManager.ts`（`apps/crish-desktop/src/api/VirtualScrollManager.ts:30-120`）依赖纯文本预测量：
$$\text{EstimatedHeight} = \text{clamp}(\text{charCount} \times \text{lineFactor}, 120, 2000)$$
在引入交错多步骤时间线后：

- 一条包含 5 个执行步骤、3 个工具调用与万字思考的 `SessionMessage`，其纯文本交付物可能只有 200 字（文本估高约 120px）；
- 但其内部包含：5 个 `StepGroup` 容器（$5 \times 36\text{px} = 180\text{px}$）、2 个展开思考块（$2 \times 200\text{px} = 400\text{px}$）、3 个工具卡片（$3 \times 160\text{px} = 480\text{px}$），**真实渲染高度达到 1180px（误差近 10 倍！）**；
- 当用户向上滚动加载历史消息时，`VirtualScrollManager` 先使用 120px 作为占位高度计算 `offsetsCache`；当该节点真正挂载并被 `ResizeObserver` 捕获后，回写 `setActual(id, 1180)`；
- `VirtualScrollManager` 瞬间将偏移量增加 1060px，导致视口内的其他消息被暴力推挤出当前视口，产生极其严重的**白屏、内容反复闪烁与跳跃（Scroll Thrashing）**。

#### 【方案 02 漏洞定位】

- 方案 02 仅重构了组件层（`MessageContent.tsx`），对底层核心服务 `VirtualScrollManager.ts` 与 `messageWindowDomBudget.ts` **未做任何针对步骤块（Step Blocks）的结构化估高契约改造**。

#### 【强制修正方案】

重构 `VirtualScrollManager.estimateBlockHeight(msg: SessionMessage)`：

```typescript
export function estimateTimelineMessageHeight(msg: SessionMessage): number {
  let h = 48; // Base Header + Padding
  const blocks = msg.blocks || [];
  if (blocks.length > 0) {
    for (const b of blocks) {
      if (b.type === 'thought')
        h += 40; // 折叠思考胶囊预估
      else if (b.type === 'tool_call')
        h += 52; // 工具折叠条预估
      else if (b.type === 'text')
        h += Math.max(32, Math.ceil((b.content?.length || 0) / 40) * 20);
    }
  } else {
    h += Math.max(60, Math.ceil((msg.text?.length || 0) / 40) * 20);
  }
  return Math.min(Math.max(h, 120), 4000);
}
```

### 2.3 `StreamingTextBlock` 与 `AsyncMarkdownBlock` 交接时的 DOM 撕裂

#### 【缺陷机理剖析】

在 `MessageContent.tsx:1403-1430` 与 `1672-1693` 中：

- 流式正文输出时，末尾块使用 `StreamingTextBlock` 渲染，通过原生 DOM 的 `textContent += delta` 获得极致的 60FPS 追加性能；
- 当本轮流式结束、消息状态跃迁为 `completed` 时，`MessageContent.tsx` 卸载 `StreamingTextBlock`，切换回 `AsyncMarkdownBlock`；
- **致命断层**：`AsyncMarkdownBlock` 依赖 Web Worker 异步编译 Markdown。在 Worker 返回编译好的 HTML 前，组件处于挂起或 fallback 状态（纯文本无格式），耗时约 10~50ms；Worker 返回后再次执行 `dangerouslySetInnerHTML` 替换整个 DOM 结构；
- 这导致用户在流式结束的瞬间，肉眼可见地观察到内容从“富文本追加”瞬间退化为“纯文本”，几十毫秒后再突变为“最终高亮 Markdown”，造成**严重的界面跳闪（FOUC）与高度抖动**。

## 三、专题审查 2：`EventRouter` 去重矩阵在网络抖动与多轮自愈下的误杀隐患

### 3.1 工具去重键缺少 `turnIndex` 导致同名工具与自愈重试被静默吞噬

#### 【代码级缺陷审查】

审查 `02-流式管道与交错时间线独立总方案.md:730-760`：

```typescript
// 方案 02 提供的 buildEventDedupeKey 重构代码：
if (
  event.type === 'tool-start' ||
  event.type === 'tool-update' ||
  event.type === 'tool-end'
) {
  const toolId = ...;
  const seq = raw.sequence;
  const sequence = seq === null || seq === undefined || seq === '' ? null : String(seq);
  if (toolId && sequence !== null) {
    return `${event.type}:${toolId}:${sequence}`;
  }
  if (toolId) {
    if (event.type === 'tool-update') return null; // 进度更新无 seq 全放行
    return `${event.type}:${toolId}`; // 🔴 致命漏洞！缺少 turnIndex
  }
  ...
}
```

#### 【推导演练与灾难后果】

1. **场景 1：长程多轮使用自增 Tool ID 编号**
   - 某 Provider 或自研状态机在 Turn 0 发起 `view_file`，生成的 `toolId` 为 `"call_0"`；
   - 实时轨（`sequence=None`）发射 `tool-start`，`buildEventDedupeKey` 返回 `"tool-start:call_0"`，加入 `consumedEvents`；
   - 任务推进至 Turn 1，模型发起第 2 次 `view_file`，Provider 再次以 0 起始分配 `toolId = "call_0"`；
   - 实时轨发射 `tool-start`，`consumedEvents.has("tool-start:call_0")` 命中！**该工具调用被前端当作重复事件直接丢弃！** 用户在界面上完全看不到第 2 轮工具卡片。
2. **场景 2：方案 01 状态机自愈重试（Immediate Reflexion）**
   - 在方案 01 的自愈体系中，当 `tool-1` 执行报错，状态机发起同名同 ID 工具的即时重试执行；
   - 前端因记录了 `tool-start:tool-1`，重试的 `tool-start` 被直接抹杀，导致工具状态卡死在旧的报错状态，无法进入重试流。

#### 【强制修正代码】

```typescript
// 必须融合 turnIndex 与 runId
if (toolId) {
  if (event.type === 'tool-update') return null;
  const turn =
    typeof event.turnIndex === 'number' ? `turn-${event.turnIndex}` : 't0';
  return `${event.type}:${turn}:${toolId}`;
}
```

### 3.2 乱序网络到达（Out-of-order Delivery）引发工具状态永久卡死

#### 【缺陷机理剖析】

在 Tauri IPC / LiveSink 异步事件分发通道中，极端高负载下存在微秒级的事件交错：

1. `tool-end:tool-A` 事件由于网络瞬时并发先于 `tool-start:tool-A` 到达前端 `EventRouter`；
2. `EventRouter` 处理 `tool-end`：执行 `consumedEvents.add("tool-end:tool-A")` 并分派给 handler；但此时前端 Store 中尚无 `tool-A` 实体，handler 只能丢弃或生成孤儿结果；
3. 随后，延迟的 `tool-start:tool-A` 到达，在 Store 中创建了状态为 `running` 的工具卡片；
4. 由于 `tool-end:tool-A` 已经在此前被消费且不会再次发射，该工具卡片将**永久处于 `running`（持续转圈）状态**，直到整个 Run 终态强制推平。

#### 【强制修正要求】

在 `EventRouter` 或 `StreamState` 中建立**轻量因果时序缓存区（Causality Buffer）**：若收到 `tool-end` 时发现本地未曾注册该 `toolId` 的 `tool-start`，将其暂存至 `pendingEndMap`，等待 `tool-start` 到达后在同一微任务内立即触发状态收口。

#### 【性能瓶颈实测推导】

  - 每次比对后构建搜索匹配 DOM 高亮；
  - **主线程单次按键响应耗时 25~45ms，在 60Hz 屏幕下必然发生严重的掉帧与按键粘连假死（Keypress Latency）**。

#### 【强制修正方案】

1. `ThoughtSearchBar` 必须内置 **150ms Debounce 防抖**；
2. 50,000 字符的大纲提取与高亮搜索必须**移入 Web Worker 或 Rust 线程处理**，主线程仅接收结构化的 `{ id, index, matchRanges }` 轻量索引。

### 4.2 Web Worker Markdown 解析缺少流式背压控制（Backpressure）

#### 【缺陷机理剖析】

在 `FullThoughtModal` 开启状态下，若后台大模型仍在持续流式输出思考内容（如 Claude 3.7 Extended Thinking 持续吐出 32K Token）：

1. 前端流式管道每 48ms 发射一次更新的思考全文字符串（如 20,000 ➔ 20,100 ➔ 20,200 字符）；
2. `FullThoughtModal` 中的 `AsyncMarkdownBlock` 将这串文本作为新任务 `postMessage` 给 Web Worker；
3. Worker 编译 20,000 字符的 Markdown（含代码高亮与 LaTeX 公式）平均耗时 **60~120ms**；
4. **生成速率（48ms/次）> 消费速率（100ms/次）**，Worker 任务队列发生严重积压（Queue Explosion）；
5. 当流式结束时，Worker 队列中积压了十几个已经过期的旧解析任务，Worker 仍会逐一计算并连续向主线程 post 回传，导致主线程在流式结束后持续进行 1~2 秒的无效 DOM 重绘。

#### 【强制修正架构：最后帧覆写模式（Latest-Frame Drop Policy）】

```typescript
class BackpressureWorkerDispatcher {
  private inflight = false;
  private pendingPayload: string | null = null;

  public dispatch(text: string) {
    if (this.inflight) {
      // 正在计算中，仅暂存最新的一帧，丢弃所有中间过渡帧！
      this.pendingPayload = text;
      return;
    }
    this.execute(text);
  }

  private execute(text: string) {
    this.inflight = true;
    worker.postMessage({ type: 'RENDER_MARKDOWN', text }, (result) => {
      this.inflight = false;
      applyResultToDom(result);
      if (this.pendingPayload !== null) {
        const next = this.pendingPayload;
        this.pendingPayload = null;
        this.execute(next);
      }
    });
  }
}
```

### 5.1 10MB 超长 Stdout 引发 V8 Heap 内存爆炸与数组分配风险

#### 【代码级缺陷审查】

审查 `05-工具摘要与输入输出分栏独立总方案.md:1185-1215`：

```typescript

const raw = output || '';
const images = useMemo(() => extractImageRefs(raw), [raw]);
const full = useMemo(() => fullToolOutput(raw), [raw]); // 🔴 复制一次 10MB
const lineCount = useMemo(() => {

```

#### 【内存与垃圾回收灾难推导】

1. 运行 `cargo build` 或 `npm test` 输出 10MB 文本；
2. `raw` 占用 10MB 内存；
3. `fullToolOutput(raw)` 产生清洗副本，占用 10MB 内存；
4. `full.split('\n')` 将整块内存切碎为 200,000 个独立的 JS String 对象与 1 个大 Array，V8 内存分配瞬时飙升 **40MB ~ 80MB**；
5. `extractImageRefs(raw)` 执行全局正则表达式匹配，扫描 10MB 文本耗时超过 **100ms**；
6. 若一次会话中有 10 个类似工具输出，组件树常驻持有近 **1GB 内存**，直接诱发 WebView2 GC 频繁卡顿（GC Thrashing）甚至进程 OOM 崩溃。

#### 【强制修正代码：O(1) 字符流轻量统计】

```typescript
// 严禁使用 full.split('\n')！改为 O(N) 扫描、O(1) 内存计行：
export function fastCountLines(str: string): number {
  if (!str) return 0;
  let count = 1;
  for (let i = 0; i < str.length; i++) {
    if (str.charCodeAt(i) === 10) count++;
  }
  return count;
}
```
