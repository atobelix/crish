## 二、专题深挖一：权限体系完全访问放行后的安全底线漏洞

### 2.1 `FullAccess` 模式放行后操作系统级毁灭命令（`rmdir /s /q C:\Windows`）绝对拦截失效推导

#### 1. 漏洞定位与代码证据

在 `04-权限体系与沙箱重构独立总方案.md` §2.4 与 §2.5 中，方案提议：

- 在 `ToolContext` 中下沉 `permission_mode`；
- 在 `PermissionMode::FullAccess` 下，彻底绕过 `shell_redirect.rs` 的复合删除拦截与间接执行拦截；
- 仅依靠 `CommandGatekeeper::new().is_critical_system_redline(&command)` 与 `is_redline` 进行绝对拦截。

**代码审计真相**（核对 `crates/conex-sandbox/src/semantics.rs:893-912` 与 `crates/conex-sandbox/src/lib.rs:42-49`）：

```rust
// crates/conex-sandbox/src/semantics.rs:893-912
fn is_root_target(target: &str) -> bool {
    let normalized = target.trim();
    if normalized == "/" || normalized == "*" || normalized == "/*" {
        return true;
    }
    // Windows 盘符根：恰好 "C:\" / "C:/" / "C:"（后面不能再有路径成分）
    let lower = normalized.to_lowercase();
    if lower.len() >= 2 && lower.as_bytes()[0].is_ascii_alphabetic() && lower.as_bytes()[1] == b':'
    {
        if lower.len() == 2 {
            return true;
        }
        if lower.as_bytes()[2] == b'\\' || lower.as_bytes()[2] == b'/' {
            // 仅当盘符根后直接结束（C:\ 或 C:/），或仅跟通配根（C:\*）
            let rest = &lower[3..];
            return rest.is_empty() || rest == "*" || rest == "\\*" || rest == "/*";
        }
    }
    false
}
```

```rust
// crates/conex-sandbox/src/lib.rs:42-44
r"(?i)\bRemove-Item\b.*(-Recurse|-Force).*[A-Za-z]:(\\|\/)?(\*|\s*$)",
r"(?i)\bformat\s+[A-Za-z]:",
r"(?i)\b(del|erase|rd|rmdir)\b.*[A-Za-z]:(\\|\/)?(\*|\s*$)",
```

#### 2. 致命漏洞推导演算

1. 现有静态正则与语义分析中的 `is_root_target` 函数，**严格仅对裸盘符根（如 `C:\`、`C:`、`C:\*`）返回 `true`**；
2. 当命令为 `rmdir /s /q C:\Windows`、`rd /s /q C:\Windows\System32`、`del /f /s /q C:\Windows\*` 或 `pwsh -c "Remove-Item -Recurse -Force C:\Windows"` 时：
   - 目标路径解析为 `C:\Windows`，`rest` 为 `"windows"`；
   - `is_root_target("C:\\Windows")` 返回 **`false`**；
   - `classify_delete_command` 将其分类为 **`CommandClass::DeleteShape`**（而非 `CommandClass::Redline`！）；
   - `lib.rs` 的静态正则也因末尾存在 `Windows` 而**无法匹配** `[A-Za-z]:(\\|\/)?(\*|\s*$)`；
3. 在 Plan 04 设计的 `FullAccess` 模式下：
   - `PermissionDecisionEngine::evaluate` 接收到的 `is_redline` 为 `false`；
   - `FullAccess` 分支直接返回 **`PermissionVerdict::Allow`**；
   - `ShellCommandTool::prepare` 完全跳过 `redirect_or_intercept_delete`，直接将 `rmdir /s /q C:\Windows` 发送给操作系统进程执行！
4. **灾难后果**：系统核心操作系统目录在“完全访问模式”下被直接物理清空，导致操作系统崩溃假死，彻底违背了“仅放行工作区开发操作，绝对守住系统毁灭红线”的根本承诺！

### 2.2 磁盘与卷级破坏性指令集（`diskpart`、`Initialize-Disk`、`bcdedit` 等）红线防护真空

#### 1. 现有 Redline 清单的严重遗漏

审查 `crates/conex-sandbox/src/semantics.rs:112-126` 中的 `REDLINE_COMMANDS`：

```rust
const REDLINE_COMMANDS: &[&str] = &[
    "mkfs", "mkfs.ext2", "mkfs.ext3", "mkfs.ext4", "mkfs.xfs", "mkfs.btrfs",
    "format-volume", "clear-disk", "format", "dd", "stop-computer", "restart-computer",
];
```

#### 2. 漏洞分析

该清单仅覆盖了最基础的磁盘格式化命令，但在现代 Windows 系统运维与自动化中，存在大量足以造成物理级数据毁灭但未被纳入红线的原生工具：

1. **`diskpart` 脚本注入**：AI 执行 `diskpart /s script.txt`（脚本内容包含 `select disk 0; clean all`），可瞬间抹除整块硬盘的分区表与引导扇区；
2. **PowerShell 存储管理 Cmdlet 遗漏**：`Initialize-Disk`、`Remove-Partition`、`Reset-PhysicalDisk`、`Clear-Bcd`、`Disable-BitLocker` 等高级破坏命令完全未被识别；
3. **引导损坏命令**：`bcdedit /delete ...`、`bootrec /fixmbr` 变体可直接破坏 Windows BCD 启动项；
4. **卷影副本与备份清空**：`vssadmin delete shadows /all /quiet` 与 `wbadmin delete catalog`（典型的勒索病毒行为特征）在 `FullAccess` 下毫无阻拦；
5. **WMI / CIM 间接格式化**：`Get-CimInstance Win32_Volume | Invoke-CimMethod -MethodName Format`。

### 2.3 `PermissionDecisionEngine` 与叶子工具上下文断层的二次穿透

#### 1. 架构断层证据

在 Plan 04 §2.5 中，`PermissionDecisionEngine::evaluate` 仅接收 5 个布尔标志：

```rust
pub fn evaluate(
    mode: PermissionMode,
    is_dangerous: bool,
    is_redline: bool,
    requires_approval: bool,
    is_out_of_workspace: bool,
) -> PermissionVerdict
```

#### 2. 缺陷剖析

这种设计存在**上下文剥离（Context-Stripping）**的致命缺陷：

- 裁决引擎本身不感知具体的路径、不感知目标文件是否为操作系统关键保护对象（如 `%SystemRoot%`、`%ProgramFiles%`、`%USERPROFILE%` 根目录）；
- 它将“是否为红线”的判定完全推卸给外部调用者；
- 若各个叶子工具（`fs.rs`、`shell.rs`、`shell_redirect.rs`）在组装 `is_redline` 时标准不一致，就会产生“前门拦截了、后门通过了”的特权逃逸。

### 2.4 解决方案与加固要求（OS 核心路径防御网与红线矩阵扩展）

面向 Plan 04 架构师下达以下**硬性整改指令**：

1. **确立 Windows 系统核心保护目录（System Critical Invariant Paths）**：
   在 `crates/conex-sandbox/` 中建立不可逾越的系统根目录防护谓词 `is_system_critical_path(path: &Path) -> bool`，无论何种权限模式（包括 `FullAccess`），只要删除或修改目标命中以下路径及其父级/直属子系统，**硬性判定为 `CommandClass::Redline` 并 100% 阻断**：
   - Windows 目录：`C:\Windows`, `C:\Windows\System32`, `C:\Windows\SysWOW64` 及 `$env:SystemRoot`；
   - 程序安装目录：`C:\Program Files`, `C:\Program Files (x86)`, `C:\ProgramData`；
   - 系统引导与驱动：`C:\Recovery`, `C:\Boot`, `C:\bootmgr`, `C:\pagefile.sys`；
   - 用户根目录：`C:\Users`、`C:\Users\<username>`（除非是工作区内部的白名单子目录）。
2. **红线指令集必须全面补齐**：
   将 `diskpart`、`initialize-disk`、`remove-partition`、`reset-physicaldisk`、`bcdedit`、`vssadmin`、`wbadmin`、`mountvol` 统一纳入 `REDLINE_COMMANDS` 核心清单；
3. **重构 `is_root_target` 谓词**：
   将其升级为 `is_redline_target(target: &str) -> bool`，不仅检查 `C:\`，同时结合 `is_system_critical_path` 对路径成分进行全量规整化检测。

## 三、专题深挖二：Windows 路径归一与动态挂载边缘死锁与循环挂起

### 3.1 `ConexPathNormalizer` 在网络共享路径（UNC `\\server\share`）与 `ParentDir` 下的词法截断崩溃

#### 1. 代码缺陷证据

审查 Plan 04 §3.2 中 `ConexPathNormalizer::normalize` 的实现代码（第 458~507 行）：

```rust
Component::ParentDir => {
    // 安全弹出上一级（词法规范化）
    if !normalized_components.is_empty() && normalized_components.last().unwrap() != ".." {
        normalized_components.pop();
    } else {
        normalized_components.push("..".to_string());
    }
}
```

以及后续的路径组装：

```rust
for (i, comp) in normalized_components.iter().enumerate() {
    if i == 0 && comp.ends_with(':') {
        result.push(format!("{}\\", comp));
    } else {
        result.push(comp);
    }
}
```

#### 2. 边缘场景崩溃推导

1. **UNC 根被非法弹出**：
   - 对于输入路径 `\\server\share\sub\..\..`；
   - `normalized_components` 初始压入 `["\\\\server\\share", "sub"]`；
   - 遇到第一个 `ParentDir`，弹出 `"sub"`；
   - 遇到第二个 `ParentDir`，`normalized_components.last()` 为 `"\\\\server\\share"`（非 `".."`），代码直接执行 `normalized_components.pop()`，**将 UNC 服务器共享根直接弹空**！
   - 最终输出变成了 `".."`，彻底破坏了 UNC 根的物理语义！
2. **UNC 组装缺少反斜杠**：
   - 组装循环中只检查了 `comp.ends_with(':')`（盘符）；
   - 当 `i == 0` 且 `comp` 为 `"\\\\server\\share"` 时，执行 `result.push(comp)`；
   - 随后 `i == 1` 执行 `result.push("folder")`；在 Windows 下 `PathBuf::push` 拼接 UNC 根与第一个子目录时，若 UNC 根末尾没有显式分隔符，会导致拼接出的路径格式混乱（`\\server\sharefolder`）。

### 3.2 同步探测不可达网络路径（UNC）引发 Tokio 异步工作线程池饥饿与会话假死

#### 1. 机制缺陷分析

在 Plan 04 提出的动态挂载全链路（§3.4）中，当 AI 调用 `propose_workspace_mount(path)` 时，系统需要对路径进行有效性与元数据探测（`std::fs::metadata` 或 `canonicalize`）。

#### 2. 致命挂起链条

1. 当 AI 提议一个处于离线状态的内网共享路径（例如 `\\192.168.1.199\share\repo` 或 `\\offline-host\app`）时；
2. Windows SMB/NetBIOS 客户端驱动在同步系统调用层（Win32 `CreateFileW` / `GetFileAttributesW`）会发起 TCP 连接与 NetBIOS 广播探测，其默认内核超时为 **30 秒 ~ 60 秒**；
3. 如果 `propose_workspace_mount` 或 `resolve_workspace_path` 在 Tokio 的异步 Task 中**直接执行同步文件系统 I/O**（未包装进 `spawn_blocking`）：
   - 该 Tokio Worker 线程将被内核死死挂起 60 秒；
   - 若 AI 并发调用或重试探测多次，**Tokio 运行时默认的全部核心 Worker 线程将瞬间全部耗尽（Thread Starvation）**；
   - 整个桌面端后台 IPC、LiveEventSink 事件流与会话循环将发生**全系统假死（Global Event Loop Deadlock）**！

---

### 3.3 NTFS Junction / 符号链接递归循环路径（Cyclic Symlinks）下的无限遍历与栈溢出隐患

#### 1. 现状病灶

在 Windows 现代前端与 Rust 开发中，`pnpm` 依赖树与 `cargo` 构建缓存大量使用 NTFS Junction 与符号链接。开发者甚至可能创建自引用的循环联接点（例如 `dirA/link_to_dirA -> dirA`）。

#### 2. 缺陷推导

Plan 04 宣称“原生放行 NTFS Junction”，但在 `crates/conex-fs` 与 `agent-tools` 现有的 `has_symlink_below_root` 与文件遍历实现中：

- 仅移除了对符号链接的即时阻断，**未引入任何访问集追踪（Visited Inode/FileIndex Tracking）**；
- 当 `list_dir`、`grep_search`、`read_file` 或沙箱路径解析进入循环 Junction 时，递归函数将陷入死循环，直至耗尽栈空间触发 **`STATUS_STACK_OVERFLOW` (0xC00000FD) 崩溃退出**，或引发 CPU 100% 旋转死锁。

---

### 3.4 `propose_workspace_mount` 动态挂载并发竞态与系统根目录提议越权

#### 1. 缺陷定位

审查 Plan 04 §3.4 的状态机图（第 570~600 行）：

1. **系统根挂载越权**：方案未对 AI 申请挂载的路径施加安全禁区校验。AI 可提议 `propose_workspace_mount(path: "C:\\")` 或 `path: "C:\\Windows"`，一旦用户误触“授权并挂载”，工作区沙箱被重置为整个系统盘，所有文件工具的越界防护全面失效；
2. **多 Agent 并发修改竞态**：`ToolContext.workspace_root` 在会话循环内部是动态修改的。在多 Agent 协同（主 Agent + 16 个子 Agent）并发执行时，若子 Agent 调用了挂载提议并更新了会话级工作区根，会导致其他正在按旧工作区相对路径读写的子 Agent 路径解析错位。

### 3.5 解决方案与加固要求（UNC 异步探测超时、Inode/FileIndex 环路检测、挂载禁区守卫）

面向 Plan 04 架构师下达以下**硬性整改指令**：

1. **修正 `ConexPathNormalizer` 的 UNC 边界处理**：
   - 明确将 `Component::Prefix`（含 UNC 根 `\\server\share`）定义为**不可弹出的锚点（Immutable Root Anchor）**，`ParentDir` 到达 UNC 根时严禁继续 pop；
   - 路径组装阶段对 UNC 根强制补齐标准分隔符；
2. **网络路径探测必须隔离与超时熔断**：
   - 涉及任何可能触发网络 I/O 的路径（以 `\\` 或 UNC 前缀开头）探测，必须强制放入 `tokio::task::spawn_blocking` 中执行；
   - 施加严格的 **2000ms 硬超时熔断（Hard Timeout）**，超时立即向 AI 返回 `ToolError::new(TOOL_PATH_INVALID, "Network path unreachable or timeout")`，绝对禁止阻塞异步调度器；
3. **全系统文件遍历与符号链接解析必须建立环路检测机制**：
   - 基于 Windows 的 `BY_HANDLE_FILE_INFORMATION`（提取 `dwVolumeSerialNumber` 与 `nFileIndexHigh/Low`）或跨平台唯一标识建立 `HashSet<(u64, u64)>` 访问轨迹表；
   - 限制符号链接与 Junction 的最大跳转深度（如最大 8 层），发现环路立即剪枝跳过，彻底杜绝栈溢出；
4. **`propose_workspace_mount` 注入系统禁区拦截与会话隔离**：
   - 挂载提议必须经过 `is_system_critical_path` 校验，严禁提议挂载盘符根、Windows 目录及系统敏感路径；
   - 动态挂载仅对发起提议的当前 Context 隔离生效，严禁在多任务并发期无锁污染全局工作区。

## 四、专题深挖三：TypeScript 插件体系生命周期与资源泄漏

### 4.1 `PluginContext` 缺乏 `DisposableBag` 与反注册机制导致的事件与 View 泄漏

#### 1. 代码缺陷证据

审查 Plan 06 §4.2 `packages/plugin-sdk/src/index.ts`（第 779~808 行）：

```typescript
export interface PluginContext<TConfig = unknown> {
  pluginId: string;
  config: TConfig;
  invokeIpc<TResult = unknown>(
    channel: string,
    payload?: unknown
  ): Promise<TResult>;
  registerView(viewId: string, component: React.ComponentType<any>): void;
  registerSettingsCard(
    section: string,
    component: React.ComponentType<any>
  ): void;
  registerHudOverlay(hudId: string, component: React.ComponentType<any>): void;

```

#### 2. 架构缺陷分析

1. **单向注册、无法注销**：`PluginContext` 仅提供了 `register*` 方法，完全没有提供对应的 `unregisterView`、`unregisterSettingsCard` 或 `unregisterHudOverlay`；
2. **缺少 `Disposable` 契约**：在现代化扩展体系（如 VS Code 扩展模型）中，任何扩展点注册必须返回一个 `IDisposable` 句柄或接收一个 `SubscriptionBag`。当前方案中，一旦插件被激活（`activate`），其向 Host 注入的 React 组件、DOM 节点将永久滞留在全局注册表 `ViewRegistry` 中；
3. 当插件执行 `deactivate` 或发生热重载（HMR / Plugin Reload）时，旧的 React 组件闭包无法被垃圾回收，造成严重的闭包与 DOM 内存泄漏。

### 4.2 `@crish/plugin-browser` CDP WebSocket 连接、屏幕捕获帧与 DOM 监听器的常驻泄漏

### 4.3 `@crish/plugin-markdown-editor` 多 Tab 独立 Store、AST 树与撤销栈缺乏按 Tab 销毁契约

#### 1. 缺陷推导

审查 Plan 06 §4.3：

### 4.4 `@crish/plugin-computer-use` 系统级键鼠钩子与屏幕轮询定时器的僵尸存活风险

### 4.5 `invokeIpc` 缺乏基于 `permissions` 的能力级沙箱鉴权，存在特权逃逸漏洞

### 4.6 解决方案与加固要求（标准 Disposable 架构、Session/Tab 级生命周期钩子、Capability-based IPC Guard）

2. **建立 Tab 与 Session 细粒度生命周期契约**：

4. **`invokeIpc` 必须引入能力级权限阻断（Capability-based IPC Firewall）**：

## 五、专题深挖四：子 Agent 物理隔离机制在多窗口并发下的穿透风险

### 5.1 Follow-up 插件依赖全局单例 Store 与 CustomEvent 导致的跨窗口/跨分屏状态污染

#### 1. 缺陷定位与代码证据

审查 Plan 06 §8.2.1 `FollowUpSlot.tsx`（第 1148~1222 行）：


#### 2. 并发穿透风险分析

   - `window.dispatchEvent(new CustomEvent('crish:focus-composer'))` 广播至整个 DOM 树；
   - 若右侧子 Agent 监视器正好拥有焦点，该事件会强行将用户的输入焦点从子面板抢回主 Composer，破坏用户的分屏监视体验。

### 5.2 仅靠前端组件级 Props（`isSubagent`）防御的脆弱性与身份伪造/默认漏判风险

#### 1. 缺陷剖析

Plan 06 的隔离完全发生在前端渲染层（View Layer），而**后端引擎层（Rust / Provider 链路）根本没有阻断逻辑**：

## 六、专题深挖五：输入框几何防漂移在极小视口与缩放下的失效边缘

### 6.1 DPI 缩放（125%/150%）与亚像素抖动导致 `isPhysicallyVisibleNonZeroRect` 误判与漏判

#### 1. 代码缺陷证据

审查 Plan 06 §3.5 `safeCursorAnchor.ts`（第 619~639 行）：

```typescript
export function isPhysicallyVisibleNonZeroRect(rect: unknown): rect is DOMRect {
  if (!rect || typeof rect !== 'object') return false;
  const r = rect as DOMRect;
  // ...
  const hasDimensions = r.width > 0 || r.height > 0;
  const notAtOrigin = r.top !== 0 || r.left !== 0; // ❌ 致命判定漏洞！

  return hasDimensions && notAtOrigin;
}
```

#### 2. 数学与浏览器渲染逆向推导

1. **零坐标误杀真原点**：
   - 假设用户在窗口顶部贴边放置了一个全屏或分屏编辑器，其光标在第一行第一个字符处的物理坐标恰好为 `top: 0px, left: 0px, width: 1px, height: 18px`；
   - `notAtOrigin` 计算为 `0 !== 0 || 0 !== 0` $\to$ **`false`**！
   - `isPhysicallyVisibleNonZeroRect` 判定该合法光标为无效矩形，错误触发了降级逻辑！
2. **DPI 亚像素微小抖动判定穿透**：
   - 在 Windows 系统设置 125% 或 150% DPI 缩放下，浏览器在未排版完成时的零矩形可能返回浮点数微小噪点（如 `top: 0.000031px, left: 0.000015px, width: 0px, height: 0px`）；
   - 若某些浏览器版本为未就绪光标赋予默认 `height: 1px`；
   - `notAtOrigin` 计算为 `0.000031 !== 0` $\to$ **`true`**，`hasDimensions` 为 **`true`**；
   - 虚假的零坐标微小噪点成功绕过了 `isPhysicallyVisibleNonZeroRect` 校验，继续导致浮层被钉死在左上角！

---

### 6.2 极小视口/分屏容器双向溢出时 Radix Popover 翻转失败与 `(8px, 8px)` 幽灵漂移二次回潮

#### 1. 碰撞翻转失效推导

在 Plan 06 与 Plan 07 的设计中，斜杠菜单与 Tooltip 依赖 Radix UI Popover / Floating UI：

- 当用户在极小视口高度（如高度 $\le 350\text{px}$ 的紧凑分屏、或开启屏幕虚拟键盘时）：
  - 输入框位于视口中央偏下；
  - Popover 向上渲染（`side="top"`）时，高度（约 260px）超出视口顶部边界（Collision Top Overflow）；
  - Radix 触发碰撞翻转（Flip），尝试向下渲染（`side="bottom"`）；
  - 但由于输入框距离视口底部也不足 260px，向下渲染同样超出底部边界（Collision Bottom Overflow）；
  - **当上下双向同时发生碰撞溢出时，Radix 的兜底策略是将浮层强制贴合视口安全边距 `collisionPadding: 8px`**；
  - 最终结果：**浮层再次被生硬地拍死在屏幕左上角 `(8px, 8px)`！**

---

### 6.3 缺少 `available-height` 动态约束与 CSS 视口钳位引发的视口外截断

#### 1. 缺陷分析

Plan 06 仅关注了 Anchor 锚点的坐标计算，但**完全忽略了浮层容器自身的动态高度与滚动条约束**：

- 未通过 Floating UI 的 `size` 中间件或 CSS `max-height: var(--radix-popover-content-available-height)` 限制浮层最大高度；
- 在小屏幕或缩放场景下，斜杠菜单底部会被屏幕物理边缘硬性裁切，用户无法看到或点击底部的菜单项。

---

### 6.4 解决方案与加固要求（Floating UI 动态视口感知、双向防溢出降级策略、精准几何边界断言）

面向 Plan 06 与 Plan 07 架构师下达以下**硬性整改指令**：

1. **重写 `isPhysicallyVisibleNonZeroRect` 判定数学逻辑**：
   ```typescript
   export function isPhysicallyVisibleNonZeroRect(
     rect: unknown,
     epsilon = 0.5
   ): rect is DOMRect {
     if (!rect || typeof rect !== 'object') return false;
     const r = rect as DOMRect;
     // 必须是有效有限数字
     if (![r.top, r.left, r.width, r.height].every(Number.isFinite))
       return false;

     // 必须具有真实视觉可见宽高
     const hasVisualDimensions = r.width >= epsilon || r.height >= epsilon;
     // 杜绝绝对零点噪点（容差判定）
     const isNearZeroOrigin =
       Math.abs(r.top) < epsilon && Math.abs(r.left) < epsilon;

     return hasVisualDimensions && !isNearZeroOrigin;
   }
   ```
2. **引入视口双向溢出降级保护（Bidirectional Collision Fallback）**：
   - 接入 Floating UI `size` 中间件，动态计算当前方向可用空间：
     ```css
     max-height: min(
       280px,
       var(--radix-popover-content-available-height, 280px)
     );
     overflow-y: auto;
     ```
   - 当双向均无法完整容纳菜单时，优先保持在输入框正上方并启用内部滚动，**严禁回退至屏幕绝对坐标 `(8px, 8px)`**。

## 七、其余方案交叉缺陷与隐蔽断层排查

### 7.1 Plan 07 ConPTY 读线程在子进程管道继承时的挂起与僵尸线程泄漏

#### 1. 缺陷代码定位

审查 Plan 07 §3.2.2 `session.rs`（第 384~415 行）：

```rust
thread::Builder::new()
    .name(format!("pty-read-{pty_id}"))
    .spawn(move || {
        let mut buf = [0u8; 8192];
        loop {
            match reader.read(&mut buf) {
                Ok(0) => break, // EOF
                Ok(n) => { /* 发送事件 */ }
                Err(_) => break,
            }
        }
        let exit_code = child.wait().ok().map(|s| s.exit_code());
        // ...
    })?;
```

#### 2. Windows 底层机制缺陷

- 在 Windows ConPTY 架构中，若用户在终端中启动了一个后台守护进程（如 `npm run dev` 衍生出多个 node.exe 子进程并继承了标准句柄）；
- 当用户在前端点击“关闭终端 Tab”（执行 `workbench_pty_kill`）时，虽然主 Shell 被杀死，但继承了 Stdout 句柄的后台子进程仍未退出；
- `reader.read(&mut buf)` 将**永久阻塞在 Windows 内核管道读调用上**；
- 导致 `pty-read-{pty_id}` 线程无法退出，持有的 `session` Arc 引用计数无法归零，**造成 PTY 实例与 OS 线程的双重僵尸泄漏**！
- **加固要求**：必须在 `kill_pty` 时显式调用 Win32 API 关闭 Master 句柄，并利用 Windows Job Object 强制级联终止全部衍生进程。

---

### 7.2 Plan 07 交互式终端与 Plan 04 三档权限（Plan 只读模式）的概念脱节与权限穿透

#### 1. 架构冲突事实

- **Plan 04** 严格定义了“只读计划模式（Plan Mode）下静默拦截一切命令执行”；
- **Plan 07** 引入的原生 ConPTY 纯终端直通 Windows 系统底层 Shell（`pwsh.exe`），用户敲击键盘即直接发往 OS 执行。

#### 2. 裁决与明确边界

方案未对“AI 工具命令”与“人类交互终端”的权限边界做出清晰界定，导致概念混淆：

- **权威仲裁**：**权限模式（PermissionMode）仅且只约束 AI Agent 的自主工具调用（`ShellCommandTool` / `agent-tools`）**；
- 原生 ConPTY 终端是**人类开发者自主交互的主权领地**，用户在终端中的手动输入不受 Plan 只读模式限制；但严禁 AI 将自动化命令偷渡灌入原生 ConPTY 中执行！

---

### 7.3 Plan 05 / 06 工具卡片提取器（`formatToolTitleAntiEscape`）对 MCP 嵌套调用的解构缺失

#### 1. 缺陷代码定位

审查 Plan 06 §6.1 `toolCardPresenter.ts`（第 1005~1047 行）：

- 函数 `formatToolTitleAntiEscape` 仅硬编码了 `run_command`、`read_file`、`write_to_file` 等原生工具名；
- 当系统接入 MCP 协议（如 `call_mcp_tool` 或动态 MCP 服务工具 `mcp_server_*`）时，`switch (toolName)` 全部命中 `default`；
- 前端卡片将展示毫无可读性的 **`执行工具 call_mcp_tool`**，甚至再次将 `{ "ServerName": "...", "ToolName": "..." }` 原样暴露为 raw JSON！
- **加固要求**：提取器必须前置解构 `call_mcp_tool` 参数，递归提取内部真实 `ToolName` 与业务参数，杜绝二次逃逸。

---

### 7.4 Plan 03 思考强度与 PromptCache 状态在插件体系中的上下文透传断裂

#### 1. 缺陷分析

Plan 03 提出了全链路 Thinking 档位调节与 PromptCache 四态反馈，但 Plan 06 在设计四大 TS 插件架构时，**未将思考上下文与缓存指标纳入 `PluginContext`**：

- 当 `@crish/plugin-browser` 或其他自动化插件需要调用大模型进行视觉推理时，无法继承当前会话的思考强度与缓存策略；
- 造成插件内 LLM 调用与主会话 LLM 调用的配置撕裂。
