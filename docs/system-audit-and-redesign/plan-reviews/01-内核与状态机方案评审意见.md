## 一、评审总览与核心批判性裁决

在对 `independent-plans/01~07-*.md` 全部 7 份独立方案进行系统级穿透审查后，本评审指出：各方案在愿景层面均宣称解决了 19 轮黑盒滞留、权限死锁、自愈推进与终端解耦等问题，但在**底层状态机流转严密性、前后端双轨事件收敛一致性、操作系统级进程树生命周期管控、以及多方案跨模块接口协议的一致性**上，存在大量严重的设计断层、竞态漏洞与逻辑冲突。

若不进行严格的批判性纠偏与统一收口，直接合并执行必将引发以下重大事故：

1. **事件风暴与 UI 闪烁二次回放**：由于实时轨（`sequence=None`）与持久收口轨（`sequence=1..N`）去重 Key 构造逻辑完全脱节，收口事件到达前端时将作为全新事件被二次分发，导致多步骤时间线重复创建与状态颠簸；
2. **AI 自白探测器引发死循环与系统劫持**：方案 01 提出的 `PROMISE_REGEX` 正则表达式过于草率，将 AI 正常的代码教学、技术解释与向用户反问误判为“未兑现工具承诺”，强制中断正常答复并死循环注入 `promise-nudge` 推进提示；
3. **Windows 孤儿进程灾难**：后台任务（`BackgroundTaskManager`）完全没有设计 Windows Job Object 级联自杀机制，在应用关闭、奔溃或会话销毁时，所有后台启动的 `node.exe`、`python.exe` 进程全部泄漏在后台；
4. **跨方案接口与定义全面打架**：`PermissionMode` 枚举在方案 01（`ReadOnly/Standard/FullAccess`）与方案 04（`Plan/Ask/FullAccess`）中定义不同；路径规范化在方案 01（盘符强制大写 `C:`）与方案 04（盘符强制小写 `c:`）中截然相反，导致路径比对 100% 崩溃。

## 二、核心审查一：Rust 内核双轨事件冲突与前端重放竞态漏洞

### 2.1 `EventRouter` 实时轨与收口轨 Dedupe Key 脱节导致二次回放与 UI 闪烁

- **涉及方案与代码**：
  `01-内核事件与自愈状态机独立总方案.md` §8.3（第 1317–1350 行）及 `02-流式管道与交错时间线独立总方案.md` §4.1。
- **具体缺陷剖析**：
  方案 01 提出的 `buildEventDedupeKey` 实现如下：
  ```typescript
  export function buildEventDedupeKey(
    envelope: AgentEventEnvelope
  ): string | null {
    // 1. 收口持久轨事件：按 sequence 精确去重
    if (envelope.sequence != null) {
      return `seq:${envelope.sequence}`;
    }
    const { event } = envelope;
    if (event.type === 'message-delta') return null;
    if (event.type === 'tool-start') return `tool-start:${event.callId}`;
    if (event.type === 'tool-end') return `tool-end:${event.callId}`;
    if (event.type === 'turn-start') return `turn-start:${event.turnIndex}`;
    if (event.type === 'turn-end') return `turn-end:${event.turnIndex}`;
    return null;
  }
  ```
  **致命逻辑断层**：
  1. 在 19 轮执行期间，实时轨发射的 `ToolStart` 事件携带 `sequence: None`，其 DedupeKey 为 `tool-start:c1`，前端将其记录进已消费 Set 并创建了处于 `running` 状态的工具卡片；
  2. 当第 19 轮全部结束、Rust 内核 `drive_outcome` 批量倾泻带有 `sequence: 12` 的持久化 `ToolStart` 事件时，`envelope.sequence != null` 分支成立，生成的 DedupeKey 为 `seq:12`！
  3. `seq:12` 与 `tool-start:c1` **字面完全不同**，Dedupe 检查直接放行！
  4. 结果：**收口持久轨的全部事件被前端当作全新的陌生事件全量重新执行一遍**！这将导致 `streamingStore` / `sessionStore` 重复 append 节点、卡片状态机发生颠簸闪烁、甚至在交错时间线中生成重复的步骤节点！
- **必须执行的纠偏裁决**：
  去重逻辑必须基于**业务实体唯一标识（`callId` / `messageId` / `turnIndex` + `eventType`）**进行归一，**严禁**将 `seq:${sequence}` 作为与实时事件平行的去重维度！持久轨到达时，必须根据实体主键对实时状态进行状态落定（Reconciliation），而非生成异构 Key 绕过检查。

### 2.2 `BufferedRunEventBridge` 背压丢帧与 `flush()` 异步乱序竞态

- **涉及方案与代码**：
  `01-内核事件与自愈状态机独立总方案.md` §2.5（第 401–422 行）与 `apps/agent-workbench/src-tauri/src/engine_channels.rs:606-670`。
- **具体缺陷剖析**：
  1. 方案 01 中 `BridgeLiveSink::push_live` 的实现方式是每来一个事件立即调用 `self.bridge.emit(&envelope)` 并紧接着调用 `self.bridge.flush()`；
  2. 在多线程/异步场景下（如 Provider SSE 流在 Tokio 线程池产生 `MessageDelta`，而 `ToolExecutor` 批处理在另一个线程产生 `ToolStart`），多个线程并发竞争 `BufferedRunEventBridge.buffer` 的 `Mutex` 锁；
  3. 若某一线程执行 `emit()` 后尚未调用 `flush()`，另一个线程抢先执行了 `flush()`，会导致该事件被提前冲刷，而后续 `flush()` 冲刷空数组；
  4. 更严重的是：`EventBuffer` 内部存在 `drop_class_of` 背压丢帧机制。如果实时轨的事件量极大触发了 Soft 水位丢帧，`ToolStart` 或 `TurnStart` 若被错误归类为可丢帧（或在缓冲区溢出时被丢弃），前端将永远收不到 `ToolStart`，而随后收到 `ToolEnd`，导致前端状态机因缺失前置状态而抛出未捕获异常。
- **必须执行的纠偏裁决**：
  `LiveEventSink` 必须独立于用于批量收口的背压缓冲区，或者明确声明实时轨事件为 `Critical` 级别（永不丢帧）。对于高频 `MessageDelta`，必须在 Rust 侧采用无锁或专有通道传输，杜绝与大锁竞争引起的时序倒挂。

### 2.3 `MessageDelta` 与 `MessageEnd` 渲染冲突及光标重置抖动

- **涉及方案与代码**：
  `01-内核事件与自愈状态机独立总方案.md` §2.4（第 258–292 行）与 `02-流式管道与交错时间线独立总方案.md` §5.3。
- **具体缺陷剖析**：
  1. 在流式生成期间，前端通过逐个 `MessageDelta` 累加文本，驱动打字机追尾与 Markdown 渐进式渲染；
  2. 在 `streaming.rs` 中，当 Provider 结束时，`commit_message_with_deltas` 立即向实时轨推送 `MessageEnd`（携带完整 `AgentMessage` 对象）；
  3. 前端在接收到 `MessageEnd` 时，若直接用 `message.blocks` 全量替换当前正在流式打字的局部文本，由于两者在换行符截断、转义字符或 AST 树解析上的微小差异，会导致正在进行的文本渲染发生高度跳动（Height Thrashing）和光标重置闪烁；
  4. 方案 01 完全没有定义从“实时流式投影”到“最终消息落定”的平滑过渡状态（Commit Phase），仅假设前端能自动“幂等覆盖”。
- **必须执行的纠偏裁决**：
  必须在前端状态机中显式定义 `Streaming -> Finalizing -> Committed` 三态迁移模型，`MessageEnd` 到达时仅标记流结束并锁定当前 DOM 视口，待下一帧渲染周期再完成 AST 树的无缝置换。

### 2.4 `commit_message_with_deltas` 轮次信标滞后导致首帧无挂载容器

- **涉及方案与代码**：
  `01-内核事件与自愈状态机独立总方案.md` §2.4（第 230–292 行）。
- **具体缺陷剖析**：
  1. 方案 01 在 `prepare_turn.rs` 发射 `TurnStart`，然后在 `streaming.rs` 中一边流式传输 `MessageDelta`，一边在流结束后才通过 `commit_message_with_deltas` 发送 `MessageStart` 与 `MessageEnd`；
  2. **严重时序错误**：`MessageDelta` 在 `MessageStart` 之前就已经到达了前端！
  3. 当第一批 `MessageDelta` 到达前端 `EventRouter` 时，由于前端尚未收到 `MessageStart`（不知道该消息的 `id`、`role`、`created_at` 等元数据），前端无法将 Delta 正确归属到某个消息容器中，导致首批 Token 丢失或被挂载到虚拟节点上；
  4. 直到大模型全部输出完毕，`commit_message_with_deltas` 才把 `MessageStart` 推出来，此时流式过程早已结束！
- **必须执行的纠偏裁决**：
  `MessageStart` **必须在发起 LLM 请求并收到首个 Token 的瞬间（或者在准备进入 Streaming 状态时）立即发射**，严禁将 `MessageStart` 拖延到 `commit_message_with_deltas` 结束时才发射！

## 三、核心审查二：Tool-Promise 自愈状态机死锁、误判与边界漏洞

### 3.1 `PROMISE_REGEX` 粗暴正则超高误判率（误杀解释文本、代码讲解与反问句）

- **涉及方案与代码**：
  `01-内核事件与自愈状态机独立总方案.md` §4.2（第 732–760 行）。
- **具体缺陷剖析**：
  方案 01 定义的意图侦测逻辑为：
  ```rust
  static PROMISE_REGEX: LazyLock<Regex> = LazyLock::new(|| {
      Regex::new(r"(?m)(尝试|准备|调用|执行|正在使用|运行|单独调用|通过)[\s\S]{0,30}(命令|脚本|工具|PowerShell|Bash|终端|函数|pwsh|cmd)").unwrap()
  });
  ```
  **此设计极度业余且脆弱，存在不可接受的超高误判率**：
  1. **误杀代码讲解与方案答复**：
     若用户提问：“如何在 Windows 下查看端口？”，AI 正常回复：“你可以通过运行命令 `Get-NetTCPConnection` 来查看端口。”
     ——命中 `通过...运行命令`，系统判定 AI 承诺了但没调工具！
  2. **误杀反问与需求澄清**：
     AI 向用户反问：“请问你是否希望我尝试调用脚本来批量重命名文件？”
     ——命中 `尝试调用脚本`，系统判定 AI 口头自白违约！
  3. **误杀否定句与安全警告**：
     AI 回复：“请不要在当前目录下执行命令，因为可能导致数据丢失。”
     ——命中 `执行命令`，系统强行介入自愈！
  4. **误杀 Markdown 代码块**：
     AI 在代码块中输出了包含 `pwsh` 或 `function` 的示例脚本，尾部 300 字符恰好落在代码块内，直接被无差别捕获！
- **必须执行的纠偏裁决**：
  彻底废除基于全局模糊关键字的文本正则扫描！意图侦测必须引入多维约束：
  - **过滤 Markdown 代码块与行内代码**（`pre` / `code` 段不参与扫描）；
  - **排除疑问句式**（句尾含 `？` / `?` / `是否` / `请问` 严格放行）；
  - **排除否定句式**（含 `不要` / `无需` / `避免` / `不要执行` 严格放行）；
  - **结合模型前置状态**：仅当模型在前一轮发生工具报错（`ToolError`）且当前轮未发起新工具时才激活窄范围自白侦测。

### 3.2 意图侦测引发状态机劫持与系统级自愈死循环

- **涉及方案与代码**：
  `01-内核事件与自愈状态机独立总方案.md` §4.5（第 854–880 行）。
- **具体缺陷剖析**：
  1. 当上述误判发生时，`no_tool_calls.rs` 会拦截正常的文本答复，向 `state.input_queue` 注入一条 System 提示词：
     `【系统推进】你刚才表示要：“...”，请立即调用对应工具执行该操作，不要仅停留在口头自白。`
  2. 然后调用 `dispatch(state, E::NoProgressContinue)` 强制续轮；
  3. 大模型接收到这条莫名其妙的系统警告后，由于自身本意只是在向用户解释，再次回复：“抱歉，我的意思是建议您手动运行命令，我当前不需要调用工具。”
  4. 该回复的尾部再次包含“运行命令”，**再次触发正则命中**！
  5. 状态机在 `continue_nudge_limit`（默认 3 次）用尽前，将持续不断地打断 AI、持续向 LLM 发起无意义重试，白白消耗数千 Token 并导致界面长达十几秒无响应，最终在第 3 轮耗尽预算后突兀停机。
- **必须执行的纠偏裁决**：
  当触发 `promise-nudge` 一次后，若下一轮模型依然输出纯文本且明确未调用工具，状态机**必须判定模型拒绝执行工具调用并尊重其纯文本答复立即准出**，严禁连续多轮自循环打断！

### 3.3 `continue_nudges` 计数器在跨轮工具调用中被误清空导致重试失控

- **涉及方案与代码**：
  `01-内核事件与自愈状态机独立总方案.md` §4.5（第 883 行）。
- **具体缺陷剖析**：
  在 `no_tool_calls.rs:883` 中，方案 01 写入了 `emit_steering_reset_event(state, "no-tool-calls")`。
  在会话循环中，一旦模型在某轮成功调用了一个工具（哪怕只是调用了 `list_dir`），`state.continue_nudges` 就会被重置为 0。
  在长程 19 轮任务中，如果模型在第 2 轮自白、第 3 轮调工具、第 4 轮自白、第 5 轮调工具……这导致 `continue_nudges` 的单 Run 上限防护形同虚设，单次任务中累积触发的推进重试可能高达十几次，严重偏离了原本控制重试预算的初衷。
- **必须执行的纠偏裁决**：
  必须在 `LoopState` 中区分 **“单轮连续自愈计数（`streak`）”** 与 **“整会话总自愈预算上限（`budget_cap`）”**，防止计数器被反复清零导致无限重试逃逸。

### 3.4 `Format Self-Healing` 缺乏独立计数阈值导致无限解析重试死循环

- **涉及方案与代码**：
  `01-内核事件与自愈状态机独立总方案.md` §4.3（第 769–800 行）。
- **具体缺陷剖析**：
  方案 01 在 `streaming.rs` 中捕获 `InvalidToolCall`：
  ```rust
  if raw_stop == Some(ConsumeStopReason::ToolCall) || has_diagnostic_tool_error {
      state.input_queue.enqueue_steer(AgentMessage { ... "【系统自愈提示】...请重新发起..." });
      dispatch(state, E::NoToolCalls)?;
      return Ok(HandlerOutcome::continue_run());
  }
  ```
  **严重缺陷**：方案 01 在此处**完全没有检查任何计数器**！既没有 `format_heal_attempts`，也没有设置最大重试次数。
  如果某开源模型（或能力较弱的小模型）由于 Prompt 模板冲突，持续输出非法的 JSON 格式，该逻辑将在 `dispatch(E::NoToolCalls)` ➔ `NextTurn` ➔ `Streaming` ➔ `InvalidToolCall` 之间形成**死循环**，直到触发全局 `max_turns`（如 50 轮）或上下文爆仓崩溃！
- **必须执行的纠偏裁决**：
  必须为 `Format Self-Healing` 设置严格的单故障类型重试阈值（硬限制 $\le 2$ 次）。超过 2 次格式解析失败，必须将原始输出降级为普通纯文本呈现，并标记 `ToolParseError` 退出循环，严禁无限自愈。

### 3.5 白名单准出契约无法识别纯文本且无终止意图的“僵尸轮次”

  `else if has_pending_inputs => InputAvailable`
  `else => ShouldStop`

## 四、核心审查三：`BackgroundTaskManager` 跨进程/跨会话泄漏与日志管理漏洞

### 4.1 Windows 下后台进程未绑定 Win32 Job Object 导致 App 退出时残留孤儿进程树

- **涉及方案与代码**：
  `01-内核事件与自愈状态机独立总方案.md` §3.4、`04-权限体系与沙箱重构独立总方案.md` §4.2、`07-原生ConPTY终端与质量门禁独立总方案.md` §3.2.5。
- **具体缺陷剖析**：
  1. 方案 07 在 PTY 交互终端中正确配置了 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`；
  2. **但在后台任务（`BackgroundTaskManager`）中，方案 01 与 04 完全遗漏了 Job Object 保护**！
  3. 当 AI 调用 `shell_command(mode: "auto-background", command: "npm run dev")` 时，Rust 底层通过 `tokio::process::Command` 启动了子进程；
  4. 在 Windows 操作系统中，`tokio::process::Child` 在父进程异常崩溃、被任务管理器杀死或 Tauri 窗口关闭时，**不会自动杀死子进程及其衍生的孙子进程**（如 `node.exe`、`vite.exe`、`esbuild.exe`）；
  5. 结果：用户关闭 Conex 客户端后，后台数十个开发服务器与编译器进程继续疯狂消耗 CPU/内存并占用 3000/5174/8080 等本地端口，用户重启客户端后因端口冲突报错无法再次运行。
- **必须执行的纠偏裁决**：
  `BackgroundTaskRegistry` 在 Windows 下创建任何后台进程时，必须通过 Win32 API 统一将其附加到带有 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 标志的全局作业对象（Job Object），确保应用无论以何种方式终止，操作系统内核 100% 连根拔除全部子进程树。

### 4.2 会话切换/删除与后台进程脱节（端口与句柄永久占用冲突）

### 4.3 `log_root` 同步溢出日志缺乏配额、轮转与生命周期清理机制

## 五、核心审查四：原生 ConPTY 终端与 AI 日志彻底解耦的边界漏洞

### 5.1 同工作区用户与 AI 并发操作导致 Git 索引与文件锁冲突

- **涉及方案与代码**：
  `07-原生ConPTY终端与质量门禁独立总方案.md` §3.2 与 `01-内核事件与自愈状态机独立总方案.md` §6.1。
- **具体缺陷剖析**：
  方案 07 将 ConPTY 终端直接对准工作区（`CWD = workspace_root`），并赋予用户 100% 原生交互权限；同时 AI 在后台通过 `ToolExecutor` 执行写文件、Git 提交等操作。
  **严重边界盲区**：方案 07 完全没有考虑**并发冲突防护**：
  1. 当 AI 正在使用 `write_to_file` 或 `git commit` 修改仓库时，用户在 ConPTY 终端里手动敲了 `git checkout` 或 `git merge`；
  2. Git 的 `.git/index.lock` 瞬间发生排他锁冲突，导致 AI 工具调用直接暴毙（`Git fatal: Unable to create index.lock`）；
  3. 在 Windows 环境下，若用户在 ConPTY 中用编辑器（如 `vim`、`notepad`）打开了某个源码文件，Windows 的共享锁定机制（Share Lock）会导致 AI 的 `write_to_file` 报 `PermissionDenied / SharingViolation` 错误。
- **必须执行的纠偏裁决**：
  虽然用户交互与 AI 是双轨解耦，但在文件系统与 Git 层面必须建立**优雅冲突自愈机制**：AI 遇到 `.git/index.lock` 或文件占用时，内核必须实现带退避的瞬态重试（3 次，间隔 200ms），并在自愈失败时给出明确的“外部进程锁冲突”诊断，而不是直接当成沙箱违规挂死。

### 5.2 AI `tokio::process::Command` 遇非交互式 `[y/N]` 提示导致无声挂死直至超时

  - `DEBIAN_FRONTEND=noninteractive`
  - `NPM_CONFIG_YES=true`
  - `PIP_NO_INPUT=1`
  - `GIT_TERMINAL_PROMPT=0`
    彻底从进程环境变量层面切断 CLI 的交互式等待。

### 5.3 PTY 2 小时宽限期 GC 造成多会话内存积压，16 实例硬顶缺乏 LRU 淘汰

  - 方案 01（line 1328）：`if (event.type === 'message-delta') return null;`（完全不参与 Dedupe，直接放行）；

  方案 01 的简单放行无法防止 Provider 异常时的重复推流；方案 02 的三级缓冲如果实现过于厚重，又违反了反过度设计红线。两者的 Dedupe 签名与返回值类型存在差异。
- **权威收敛裁决**：
