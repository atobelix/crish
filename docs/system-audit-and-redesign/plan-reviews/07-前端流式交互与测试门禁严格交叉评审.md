## 二、第一部分：前端跨模块数据流与时序撕裂审查

### 2.1 缺陷一：`EventRouter.ts` 动态 `turnIndex` 状态机与 `ToolCallOutput.tsx` 完整日志传递的时序竞态与内存滞留

#### 1. 跨轮工具调用的因果缓冲键漂移与死锁（Causal Key Turn Drift）

- **代码位置**：`docs/system-audit-and-redesign/detailed-plans/06-流式管道因果去重与交错时间线详案.md` §3.2 & §4.2。
- **根因分析**：
  在 `EventRouter.ts` 中，因果键生成逻辑为：
  ```ts
  private buildCausalKey(envelope: BridgeEventEnvelope): string {
    const toolId = extractToolIdFromEnvelope(envelope);
    const rawTurn = typeof envelope.raw.turnIndex === 'number' ? envelope.raw.turnIndex : null;
    const eventTurn = ('turnIndex' in envelope.event && typeof (envelope.event as { turnIndex?: unknown }).turnIndex === 'number')
      ? (envelope.event as { turnIndex: number }).turnIndex : null;
    const turn = eventTurn ?? rawTurn ?? this.currentTurnIndex; // 🚨 依赖易变单例 currentTurnIndex
    return `${turn}:${toolId}`;
  }
  ```
  在长程异步工具或子代理任务中，工具执行往往耗时数秒至数分钟。后端引擎可能在工具执行期间推进到了新的一轮（例如由系统诊断或用户打断发起新的 `turn-start`，将 `currentTurnIndex` 推进为 `1`）。
  如果原始工具在 Turn 0 发出 `tool-start`（由于无显式 `turnIndex`，存入 `knownStartedTools("0:tool-1")`），当其完成时的 `tool-end` 到达时，此时 `currentTurnIndex` 已经变为 `1`。`tool-end` 生成的因果键变为了 `"1:tool-1"`！
  此时：
  `this.knownStartedTools.has("1:tool-1")` 判定为 `false`！
  **灾难后果**：该 `tool-end` 事件被错误识别为“提前到达”，被永久挂入 `pendingToolEnds.set("1:tool-1", envelope)` 中！前端工具卡永远停留在 Running 旋转状态，因果状态机彻底死锁。
- **整改要求**：
  因果缓冲状态机**严禁**依赖可变的 `this.currentTurnIndex` 作为工具因果锁。必须在 `tool-start` 到达时，在内存表 `toolTurnBindings: Map<toolId, number>` 中记录该 `toolId` 的生命周期轮次；所有后续的 `tool-update` 与 `tool-end` 必须优先从 `toolTurnBindings` 查表对齐，彻底阻断跨轮漂移。

#### 2. `ToolCallOutput.tsx` 大日志 Props 透传引发 Fiber 闭包内存泄漏（OOM Crash）

- **代码位置**：`docs/system-audit-and-redesign/detailed-plans/07-工具分栏输入框纯化与插件体系详案.md` §4.1。
- **根因分析**：
  DIM-07 在修复下载截断问题时，方案为：
  ```tsx
  // ToolCallOutput.tsx
  const full = fullToolOutput(tc);
  <ToolCallOutputPane fullOutput={full} ... />
  ```
  当运行 `cargo build` 或全量 `grep` 输出 50MB 原始日志时，`full` 是一个 50MB 的连续大字符串。
  将其作为 React Component Props 透传：
  1. React Fiber Tree 的 `memoizedProps` 会深度持有该 50MB 字符串引用；
  2. 每当该工具卡发生一次细微的 re-render（例如耗时跳动、聚焦、折叠切换），新的 Fiber 节点都会持有该大字符串快照；
  3. 在多轮会话中连续执行数次大工具调用，前端渲染进程的 V8 堆内存将迅速飙升至 1.5GB 以上，引发页面崩溃白屏（Out of Memory）。
- **整改要求**：
  `ToolCallOutputPane` **严禁**在 Props 中同步直传未截断的 `fullOutput` 巨型字符串。UI 组件只接收截断后的 `output: string`（≤2000行 / 256KB）。
  下载按钮点击时，通过工具 `toolId` 触发按需异步获取：从底层 Store 或 Session Cache 中读取原始日志流并即时生成 Blob 下载，下载完成后立即释放，绝不让巨型日志驻留在 React Props 树中。

### 2.2 缺陷二：`TimelineThoughtSection.tsx` 尾窗切片破坏 Markdown 语法边界引发重排抖动（Layout Thrashing / Scroll Jank）与虚拟滚动崩溃

- **代码位置**：`docs/system-audit-and-redesign/detailed-plans/06-流式管道因果去重与交错时间线详案.md` §6.2。
- **根因分析**：
  DIM-06 §6.2 设计的 `budgetThinkingText` 在实时流阶段采用了纯字符尾部截断：
  ```ts
  if (mode === 'tail') {
    const omitted = totalChars - safeCap;
    return { displayText: text.slice(-safeCap), ... }; // 🚨 暴力截取最后 10,000 个字符
  }
  ```
  该算法存在三大致命语法破坏与渲染崩溃隐患：
  1. **Markdown 代码块（Code Fence）断裂震荡**：
     当思考内容中包含代码块时（如 `ts ... `），若截断点恰好落在代码块中间（丢失了开头的 ` ``` `），Markdown 解析器会将原本高亮、等宽、换行固定的代码块，突然解析为带有自动折行的普通自然语言段落；而在随着 Token 持续涌入推进到下一个字符时，又可能碰巧把某个 ` ``` ` 纳入视口，导致渲染器在 `<pre><code>` 与 `<p>` 之间以 60fps 剧烈颠簸！单个 DOM 节点高度在 100px 与 1000px 之间来回跳跃，引发可怕的 Layout Thrashing。
  2. **UTF-16 代理对截断导致乱码（Surrogate Pair Corruption）**：
     JavaScript 字符串基于 UTF-16 编码。若 `text.slice(-safeCap)` 刚好切在 4 字节字符（如 Emoji、高阶数学符号、特殊标点）的 High Surrogate 与 Low Surrogate 中间，切出的首字符将是一个非法的孤立代理字符（如 `\uD83D`），导致渲染出的首字出现 `` 乱码，并在某些特定 Markdown 解析插件中触发异常抛错。
  3. **虚拟滚动容器的高度重算崩溃（Virtual Scroll Jank）**：
     外层时间线采用虚拟化滚动列表管理。由于每当收到一个流式 Delta，`displayText` 的高度都因为 Markdown 语法的破碎重构而发生剧烈波动，导致虚拟滚动引擎（`VirtualScrollManager`）维护的行高缓存（Height Cache）完全失效，滚动条疯狂跳动，吸底状态机直接被冲垮。
- **整改要求**：
  `budgetThinkingText` 必须重构为**语法安全与换行对齐切片算法（Safe Markdown Slicer）**：
  - **行边界对齐（Line-boundary Aligned）**：截断点必须向前寻找最近的合法换行符 `\n`，保证切出的视口永远始于完整的一行；
  - **代码块语法闭合补偿（Fence Auto-Closure）**：扫描切片外部的前置文本，若截断发生时处于未闭合的代码块内部，自动在切片头部补充匹配的 ` ```lang\n `，并在切片尾部补充 `\n``` `，确保送入 Markdown 渲染器的永远是结构合法闭合的 AST！
  - **代理对安全检查**：严禁在代理对中间发生切割。

### 2.3 缺陷三：`SlashExtension.ts` 视口防碰撞翻折算法在极小视口、DPI 缩放与双向受限下的几何失效

- **代码位置**：`docs/system-audit-and-redesign/detailed-plans/07-工具分栏输入框纯化与插件体系详案.md` §5.1。
- **根因分析**：
  DIM-07 §5.1 在 `SlashExtension.ts` 中计算翻折方向时，仅使用了单一的顶部阈值判断（`top < 120px` 翻转为 `'bottom'`）：
  1. **小视口与分屏下的双向挤压失效**：
     在 Conex 的多工作区二叉树分屏模式下，一个聊天 Pane 的视口高度可能只有 350px。当输入框处于该 Pane 的中偏上位置（如 `top = 130px`）时：
     - 由于 `130px >= 120px`，算法依然决策 `suggestedSide: 'top'`；
     - 但 `TiptapSlashMenu` 的标准弹出高度为 280px，向上弹出需要 280px，而顶部仅剩 130px！
     - 此时菜单向上冲出容器边界被裁剪（Overflow Clip），用户根本看不到顶部菜单项；
     - 若盲目翻折到下方，下方空间也仅剩 `350 - 130 - 40 = 180px`，同样容纳不下 280px！算法缺少动态 `max-height` 适配与内部滚动条启用逻辑。
  2. **高 DPI 缩放下的临界点颠簸（Hysteresis Flapping）**：
     在 Windows 125% / 150% 缩放下，`DOMRect.top` 是亚像素浮点数（如 `119.9px` 与 `120.1px`）。当光标在 120px 附近换行输入时，由于缺少迟滞回差（Hysteresis Margin），菜单会在 `'top'` 与 `'bottom'` 之间产生极其恶劣的高频闪烁。
  3. **CSS 变换容器下的局部坐标错位**：
     `rawCursorRect` 获取的是相对于浏览器 Viewport 的绝对坐标。当聊天输入框处于具有 `transform: translate3d(...)` 或 `contain: paint` 的面板中时，Radix Popover 或绝对定位菜单若直接消费该 Viewport 坐标，会产生巨大的定位偏移。
- **整改要求**：
  1. 引入**双向空间权衡与动态高度限制算法（Bidirectional Clamping）**：不仅检查顶部空间，同时测量底部剩余空间 $S_{\text{bottom}} = H_{\text{viewport}} - \text{rect.bottom}$；选择空间更大的一侧，并将菜单的最大高度动态限制为 $\min(280px, S_{\text{available}} - 16px)$；
  2. 增加 **16px 迟滞回差（Hysteresis Margin）**，避免在边界处反复颠簸；
  3. 统一使用相对于 `composerContainer` 的相对偏移坐标系。

### 3.1 缺陷四：DIM-07 TS 插件体系对子 Agent `isSubagent` 的“假隔离”——仅前端视觉抑制，后台事件监听与 Token 依然泄漏

- **根因分析**：

export class EventRouter {
  /** 记录每个 toolId 首次启动时锁定的真实 turnIndex，阻断后续事件漂移 */
  private readonly toolTurnRegistry = new Map<string, number>();
  private readonly pendingToolEnds = new Map<string, BridgeEventEnvelope>();
  private readonly pendingToolUpdates = new Map<
    string,
    BridgeEventEnvelope[]
  >();
  private readonly knownStartedTools = new Set<string>();

  private resolveToolTurn(
    toolId: string,
    envelope: BridgeEventEnvelope
  ): number {
    // 1. 若该工具已有绑定轮次，严格返回绑定轮次
    if (this.toolTurnRegistry.has(toolId)) {
      return this.toolTurnRegistry.get(toolId)!;
    }
    // 2. 否则优先读取事件携带的 turnIndex
    const rawTurn =
      typeof envelope.raw.turnIndex === 'number'
        ? envelope.raw.turnIndex
        : null;
    const eventTurn =
      'turnIndex' in envelope.event &&
      typeof (envelope.event as { turnIndex?: unknown }).turnIndex === 'number'
        ? (envelope.event as { turnIndex: number }).turnIndex
        : null;
    const resolved = eventTurn ?? rawTurn ?? this.currentTurnIndex;

    // 若为 tool-start，锁定该 toolId 的轮次绑定
    if (envelope.type === 'tool-start') {
      this.toolTurnRegistry.set(toolId, resolved);
    }
    return resolved;
  }

  private buildCausalKey(envelope: BridgeEventEnvelope): string {
    const toolId = extractToolIdFromEnvelope(envelope) || 'unknown-tool';
    const turn = this.resolveToolTurn(toolId, envelope);
    return `${turn}:${toolId}`;
  }
}

### 5.2 修复方案 2：`messageWindowDomBudget.ts` 语法闭合安全切片算法（Safe Markdown Slicer）

在 `apps/crish-desktop/src/api/messageWindowDomBudget.ts` 中，实现抗代码块断裂与代理对安全的切片引擎：

````ts
export interface SafeSliceResult {
  displayText: string;
  isTruncated: boolean;
  totalChars: number;
  omittedHeadChars: number;
}

export function budgetThinkingText(
  text: string,
  options?: { cap?: number; mode?: 'head' | 'tail' }
): SafeSliceResult {
  const cap = options?.cap ?? 10000;
  const mode = options?.mode ?? 'head';
  const totalChars = text?.length ?? 0;

  if (!text || totalChars <= cap) {
    return {
      displayText: text || '',
      isTruncated: false,
      totalChars,
      omittedHeadChars: 0,
    };
  }

  if (mode === 'tail') {
    let rawCutIndex = totalChars - cap;

    // 1. 代理对安全保护：若切在 Low Surrogate 上，向前退 1 字符
    if (rawCutIndex > 0 && isLowSurrogate(text.charCodeAt(rawCutIndex))) {
      rawCutIndex -= 1;
    }

    // 2. 行边界对齐：向后寻找最近的换行符，确保从完整行开始
    const nextNewline = text.indexOf('\n', rawCutIndex);
    const safeCutIndex =
      nextNewline !== -1 && nextNewline < rawCutIndex + 200
        ? nextNewline + 1
        : rawCutIndex;

    const tailSlice = text.slice(safeCutIndex);
    const headPrefix = text.slice(0, safeCutIndex);

    // 3. Markdown 代码块 Fence 状态机闭合检测
    const openFenceMatch = detectUnclosedCodeFence(headPrefix);
    let normalizedDisplayText = tailSlice;
    if (openFenceMatch) {
      // 若截断发生时处于代码块内部，在头部自动补充开标签，保证渲染器不发生语法突变
      normalizedDisplayText = `${openFenceMatch.fence}${openFenceMatch.lang || ''}\n${tailSlice}`;
    }

    return {
      displayText: normalizedDisplayText,
      isTruncated: true,
      totalChars,
      omittedHeadChars: safeCutIndex,
    };
  }

  // mode === 'head' 逻辑
  return {
    displayText: text.slice(0, cap),
    isTruncated: true,
    totalChars,
    omittedHeadChars: 0,
  };
}

function isLowSurrogate(code: number): boolean {
  return code >= 0xdc00 && code <= 0xdfff;
}

function detectUnclosedCodeFence(
  prefixText: string
): { fence: string; lang?: string } | null {
  const lines = prefixText.split(/\r?\n/);
  let activeFence: { fence: string; lang?: string } | null = null;
  for (const line of lines) {
    const trimmed = line.trim();
    if (trimmed.startsWith('```') || trimmed.startsWith('~~~')) {
      const fenceType = trimmed.slice(0, 3);
      if (!activeFence) {
        const lang = trimmed.slice(3).trim();
        activeFence = { fence: fenceType, lang };
      } else if (trimmed.startsWith(activeFence.fence)) {
        activeFence = null;
      }
    }
  }
  return activeFence;
}
````

### 5.3 修复方案 3：`safeCursorAnchor.ts` 双向视口防碰撞与迟滞回差（Hysteresis）算法

在 `apps/crish-desktop/src/components/chat-composer/safeCursorAnchor.ts` 中重构计算契约：

```ts
export interface SafeAnchorRectOptions {
  rawCursorRect: DOMRect | null;
  editorViewDom: HTMLElement | null;
  composerContainer?: HTMLElement;
  menuHeight?: number; // 默认 280px
  previousSide?: 'top' | 'bottom'; // 用于迟滞回差计算
}

export interface SafeAnchorResult {
  left: number;
  top: number;
  width: number;
  height: number;
  suggestedSide: 'top' | 'bottom';
  availableHeight: number;
}

export function calculateSafeCursorAnchor(
  options: SafeAnchorRectOptions
): SafeAnchorResult | null {
  const { rawCursorRect, composerContainer, previousSide } = options;
  if (!rawCursorRect) return null;

  const menuHeight = options.menuHeight ?? 280;
  const viewportHeight = window.innerHeight;
  const topSpace = rawCursorRect.top;
  const bottomSpace = viewportHeight - rawCursorRect.bottom;

  // 1. 引入 24px 迟滞回差 (Hysteresis Margin)
  const hysteresis = previousSide === 'top' ? -24 : 24;
  let suggestedSide: 'top' | 'bottom' = 'top';

  if (topSpace < menuHeight + hysteresis) {
    // 顶部空间不足，且底部空间更大时翻折到底部
    if (bottomSpace > topSpace) {
      suggestedSide = 'bottom';
    } else {
      suggestedSide = 'top'; // 顶部更大依然放顶部
    }
  } else {
    suggestedSide = 'top';
  }

  // 2. 计算当前方向下可用的最大安全高度
  const availableHeight =
    suggestedSide === 'top'
      ? Math.max(120, topSpace - 16)
      : Math.max(120, bottomSpace - 16);

  return {
    left: rawCursorRect.left,
    top: rawCursorRect.top,
    width: rawCursorRect.width,
    height: rawCursorRect.height,
    suggestedSide,
    availableHeight: Math.min(menuHeight, availableHeight),
  };
}
```

### 5.4 修复方案 4：TS 插件体系会话作用域硬阻断与 IPC 精确通道映射表

```ts
/** 系统核心无害通道白名单（默认放行） */
const SYSTEM_SAFE_CHANNELS = new Set([
  'app:get_version',
  'app:get_info',
  'clipboard:write_text',
  'clipboard:read_text',
  'window:set_title',
  'window:minimize',
  'window:maximize',
  'window:is_maximized',
  'dialog:open',
  'dialog:save',
]);

/** 严格权限映射表 */
const CHANNEL_PERMISSION_MAP: Record<string, string> = {
  'fs:read_file': 'fs:read',
  'fs:list_dir': 'fs:read',
  'fs:write_file': 'fs:write',
  'fs:delete_file': 'fs:write',
  'shell:open_external': 'shell:external',
  'browser:navigate': 'browser:control',
  'assistant:get_suggestions': 'assistant:suggestions',
};

export class PluginContext {
  public async invokeIpc<TResult = unknown>(
    channel: string,
    payload?: unknown
  ): Promise<TResult> {
    // 1. 系统基础无害通道放行
    if (SYSTEM_SAFE_CHANNELS.has(channel)) {
      return (await this.hostIpc(channel, payload)) as TResult;
    }

    // 2. 精确权限判定
    const requiredPermission = CHANNEL_PERMISSION_MAP[channel];
    if (!requiredPermission) {
      throw new Error(
        `[PluginSecurityError] Channel '${channel}' is not mapped or forbidden in IPC whitelist (Default-Deny)`
      );
    }

    const declared = this.manifest.permissions ?? [];
    if (!declared.includes(requiredPermission)) {
      throw new Error(
        `[PluginSecurityError] Plugin '${this.manifest.id}' lacks required permission '${requiredPermission}' to call '${channel}'`
      );
    }

    return (await this.hostIpc(channel, payload)) as TResult;
  }
}

#### 2. 快层装配 AST 静态门禁（`scripts/check-test-invariants.mjs`）

在仓库根目录 `package.json` 的 `npm run check:all` 与 `ci.yml` 快层加入 AST 检验脚本：

```js
// scripts/check-test-invariants.mjs
import fs from 'node:fs';
import path from 'node:path';
import { globSync } from 'glob';

const testFiles = globSync('tests/e2e/**/*.spec.ts');
let hasError = false;

const FORBIDDEN_PATTERNS = [
  /if\s*\(\s*await\s+[^)]+\.isVisible\(\)\s*\)/,
  /if\s*\(\s*await\s+[^)]+\.count\(\)\s*>\s*0\s*\)/,
  /expect\(true\)\.toBe\(true\)/,
  /page\.waitForTimeout\(\d+\)/,
];

for (const file of testFiles) {
  const content = fs.readFileSync(file, 'utf-8');
  for (const pattern of FORBIDDEN_PATTERNS) {
    if (pattern.test(content)) {
      console.error(
        `❌ [Test Governance Block] 文件 ${file} 包含禁用的假阳性/盲等模式: ${pattern}`
      );
      hasError = true;
    }
  }
}

if (hasError) {
  console.error(
    '\n🚨 门禁阻断：严禁在 E2E 测试中使用 if(isVisible) 条件假绿或 waitForTimeout 盲等！'
  );
  process.exit(1);
} else {
  console.log('✅ E2E 测试强断言与零盲等 AST 门禁检查通过。');
}
```
