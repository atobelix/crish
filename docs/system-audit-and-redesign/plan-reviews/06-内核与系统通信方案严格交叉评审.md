## 二、跨方案 Rust 接口结构体与枚举契约冲突

### 2.1 DIM-01 `LiveEvent` 扩充与 Provider 协议事件、Tauri IPC 桥接的类型与序列化割裂

#### 【缺陷审查】

1. **事件字段与命名割裂**：
   - DIM-01 §3.1 中扩充了 `AgentEvent::SteeringEvaluated`、`AgentEvent::ProviderRequestAnchored`、`AgentEvent::ProviderRequestDiag`、`AgentEvent::ContextCompressionStart` 等内部内核事件；
   - 然而在 DIM-05 §8.1 与 Tauri 宿主契约中，IPC 仅对 `AgentEvent` 进行简单的 JSON 序列化转发（`app.emit("agent://event", ...)`）；
   - DIM-03 §7.6 产生的 `ProviderStreamEvent::ThoughtDelta { text, redacted }` 属于底层流式协议事件。DIM-01 并没有明确定义 `ProviderStreamEvent` 如何转换为 `AgentEvent::MessageDelta`，且 `MessageDelta` 目前缺少对 `redacted` 遮罩字段的承载契约；
2. **前端 TS 类型漂移**：
   - DIM-01 擅自新增的多个 `AgentEvent` 变体未同步提供前端 TypeScript 的 Discriminated Union 定义；前端在接收到未知的 `type: "SteeringEvaluated"` 时，由于 Reducer 缺少 `default` 安全分支或类型守卫，将导致状态机产生未捕获的运行时静默失效。

#### 【整改要求】

- 必须在 `crates/conex-types` 中统一定义权威 `AgentEvent` 枚举，并派生 `#[derive(Serialize, Deserialize, TS)]`；
- 严禁在 `crates/session-loop` 中私设未在 `conex-types` 登记的事件变体；
- 为 `AgentEvent::MessageDelta` 补齐 `thought: Option<ThoughtPayload>` 字段，对齐 DIM-03 的明文/遮罩思考契约。

---

### 2.2 DIM-02 `PermissionDecisionEngine`（`CommandDecision`）与 DIM-01 `ApprovalChannel` / `ToolContext` 契约断层

#### 【缺陷审查】

1. **决策结果与审批状态机脱节**：
   - DIM-02 §5.1 定义了裁决枚举 `CommandDecision::NeedsApproval { prompt }`；
   - 在 DIM-02 §5.3 `shell.rs` 中，当触发 `NeedsApproval` 时，代码调用 `ctx.ask.ask(&self.def.name, args).await`；
   - 但在 DIM-01 §4.4 中，`ApprovalChannel` 的超时语义被重构为 `ApprovalDecision::Expired`；
   - **严重断层**：DIM-02 的 `shell.rs` 仅 `match` 了 `Ok(AskDecision::Allowed)` 与 `Ok(AskDecision::Denied)`，对于 `Expired` 状态直接跌入未处理分支，导致前端审批超时后，底层的 `ToolError` 错误码退化为通用的 `InternalError`，而不是规范的 `TOOL_APPROVAL_EXPIRED`；
2. **双通道命名冲突**：
   - DIM-01 称为 `ApprovalChannel`（位于 `crates/session-loop/src/approval.rs`）；
   - DIM-02 称为 `AskChannel`（位于 `crates/agent-tools/src/tools/shell.rs`）；
   - 两者在不同 Crate 间存在概念二义性与 trait 割裂。

#### 【整改要求】

- 统一收拢为 `ApprovalChannel` 与 `ApprovalDecision`（包含 `Allowed`, `Denied { reason }`, `Expired`）；
- DIM-02 的 `PermissionDecisionEngine` 与 `shell.rs` 必须穷尽匹配 `ApprovalDecision::Expired` 并返回结构化错误 `ToolError::new(TOOL_APPROVAL_EXPIRED, ...)`。

---

### 2.3 DIM-03 思考预算下限（`Minimal=1024`）与 DIM-01 自愈 Steering Nudge 的延迟与 Token 惩罚

#### 【缺陷审查】

1. **自愈轮次思考预算过度浪费**：
   - DIM-03 §3.1 将 `ReasoningEffort::Minimal` 强制钳制为 `1024` tokens，且针对高档位（如 `High=4096`, `Max=16384`）默认上报大预算；
   - DIM-01 §2.5 中，当 `ToolPromiseDetector` 发现模型在回复中承诺了工具但未实际调用时，会注入 Steering Nudge 并发起下一轮转向推理（`S::PreparingTurn`）；
   - **灾难性后果**：Steering Nudge 的提示词是明确且极为简短的指令（`"请立即输出对应的工具调用以继续任务"`）。如果沿用当前会话设定的 `ThinkingIntensity::Max`（16,384 tokens），大模型将在自愈轮次再次进行长达数十秒的深度思考，消耗数万 Token 仅仅为了输出一个 `{"name": "shell_command"}`！
   - 自愈机制本应是轻量、低延迟的快速纠偏，但由于 DIM-03 未对系统转向轮次（Steering Turn）进行预算抑制，导致系统可用性与响应速度严重恶化。

#### 【整改要求】

- 在 `RequestBuildContext` 中增加 `is_steering_turn: bool` 标识；
- 当 `is_steering_turn == true` 时，强制将思考预算压低至 `Minimal`（1024 tokens）或直接关闭思考（`ReasoningEffort::Off`），实现毫秒级快速工具生成。

---

### 2.4 DIM-02 Windows 路径大写正斜杠（`C:/`）与 DIM-05 `resolve_cwd` 原始 PathBuf 的形态失配

#### 【缺陷审查】

1. **路径格式割裂与红线校验失效**：
   - DIM-02 制定了铁律 RUL-04：全系统路径必须经过 `ConexPathNormalizer::normalize`，盘符统一大写且使用正斜杠（如 `C:/Users/orange/workspace`）；
   - 然而 DIM-05 §4.2 实现的 `resolve_cwd` 直接返回 `PathBuf`，内部使用了 `dirs::home_dir()`、`std::env::current_dir()` 与 `std::path::PathBuf::from`，在 Windows 下输出为包含反斜杠的原生路径（如 `c:\Users\orange`）；
   - 当该未规范化的 `PathBuf` 传递给沙箱检查（`is_system_critical_path`）或进行 `is_subpath` 判定时，由于大小写与斜杠差异，将直接导致包含性比对失败，引发误判拦截或红线穿透。

#### 【整改要求】

- DIM-05 的 `resolve_cwd` 在返回前**必须**强制调用 `conex_fs::ConexPathNormalizer::normalize(&path)`，确保传递给 PTY 和沙箱的路径完全符合 RUL-04 规范。

## 三、并发、死锁与内存/句柄泄漏隐患

### 3.1 DIM-04 `LocalDb` 读连接池耗尽回退锁死主连接，及 `BlobLeaseGuard` 只读连接写库崩溃

#### 【缺陷审查】

1. **降级锁反转导致写饥饿**：
   - DIM-04 §3.3 的 `LocalDb::read` 实现如下：
     ```rust
     if let Ok(reader) = self.reader_pool.acquire() {
         return f(&reader)...;
     }
     // 降级：争用主写连接互斥锁
     let conn = self.conn.lock()...;
     f(&conn)...
     ```
   - 当系统处于高并发读场景（例如同时进行大文件分词、多会话列表渲染和知识库检索），`ReaderPool` 的 8 个连接全部处于借出状态。
   - 此时后续的所有只读查询全部回退到 `self.conn.lock()`，占用了主写连接！
   - 如果一个耗时较长的只读查询占用了 `self.conn`，会导致所有写事务（`LocalDb::write`）被长时间阻塞排队，彻底破坏了 SQLite WAL 模式读写互不阻塞的核心优势。
2. **只读连接写库 Panic 缺陷**：
   - DIM-04 §3.2 为只读连接配置了 `PRAGMA query_only = ON;`；
   - 但在 DIM-04 §4.2 中，`BlobLeaseGuard::acquire_lease_synced` 接收 `db_conn: &Connection` 并执行 `INSERT INTO active_blob_leases ...`；
   - 如果在上层 `LocalDb::read` 的闭包中试图读取 Blob 并刷新租约，传入的 `db_conn` 是只读连接，SQLite 将立即抛出致命错误 `attempt to write a readonly database`，引发业务崩溃。

#### 【整改要求】

- 读连接池耗尽时，`acquire()` 应当使用有界等待（如 `try_acquire_timeout(50ms)`），严禁无节制地回退占用主写连接；
- 明确分离读写职责：任何租约刷新与元数据修改操作必须显式路由至 `LocalDb::write`，严禁在只读连接上下文中混入写 SQL。

### 3.2 DIM-05 ConPTY `Utf8ChunkBuffer` 跨线程读写竞态与高频键盘输入导致 Tokio 阻塞线程池饥饿

#### 【缺陷审查】

1. **`Utf8ChunkBuffer` 跨线程安全隐患**：
   - DIM-05 §3.3 设计了 `Utf8ChunkBuffer`，包含 `carry: [u8; 4]` 与 `carry_len: usize`，该结构是非 `Sync` 的可变状态机；
   - 在 `PtySession` 中，读端运行于独立的 OS 线程，但如果前端触发 `ptyDetach` 或 `close`，主线程若尝试调用 `decoder.flush_lossy()` 排空残存字节，由于缺乏互斥锁同步，将与正在读取的后台线程产生直接的数据竞态（Data Race）；
2. **`spawn_blocking` 线程池风暴**：
   - DIM-05 §5.2 将 `workbench_pty_write` 改造为 `tokio::task::spawn_blocking`；
   - 用户在 xterm 终端快速打字、连续按住退格键或运行输出密集型交互程序时，前端每秒可能发送上百次 `workbench_pty_write` 调用；
   - 每一个 IPC 调用都向 Tokio 阻塞线程池投递一个闭包。Tokio 的 `blocking_threads` 默认上限为 512，频繁的线程创建与上下文切换将导致线程池颠簸，甚至挤占文件 I/O 任务的执行资源。

#### 【整改要求】

- `Utf8ChunkBuffer` 必须完全封闭在后台读线程的作用域内部，外部线程只通过 channel 接收其解码后的完整字符串，严禁跨线程共享解码器可变状态；
- 在 `PtySession` 内部引入专用的单协程写入 Channel（`tokio::sync::mpsc::Sender<Vec<u8>>`），所有 `workbench_pty_write` 仅执行零阻塞的 Channel 发送，由专职后台写入协程批量 Flush，消除频繁调用 `spawn_blocking` 的系统开销。

### 3.3 DIM-01 `BackgroundTaskManager` Win32 Job Object 与 `taskkill` PID 快速复用误杀系统进程灾难

#### 【缺陷审查】

1. **Windows PID 快速复用误杀风险**：
   - DIM-01 §5.2 实现的 `terminate_process_tree(pid: u32)` 直接调用外部命令：
     `taskkill /PID <pid> /T /F`
   - **高危机理**：Windows 操作系统的 PID 是由内核全局循环分配的，进程退出后其 PID 会迅速被新创建的系统进程或用户应用复用；
   - 如果一个后台编译子进程刚好自行结束，而 `BackgroundTaskManager` 超时回收协程在毫秒级的竞态窗口内执行了 `taskkill /PID <pid> /T /F`，此时该 PID 可能已被操作系统重新分配给其他核心进程（如 VS Code、Node.js 甚至系统服务）；
   - `taskkill /F /T` 将会把该 PID 及其所有子进程无差别强制全量杀死，造成灾难性的连带系统崩溃；
2. **外部命令同步阻塞**：
   - `std::process::Command::new("taskkill").output()` 是同步阻塞调用，在 16 个子 Agent 并发取消任务时，会瞬间派生 16 个 `taskkill.exe` 外部进程，产生严重的 Windows 句柄颠簸与 CPU 尖峰。

#### 【整改要求】

- 彻底废除基于裸 PID 的外部 `taskkill.exe` 树杀方案；
- 统一依托 Win32 原生 `Job Object`（配置 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 标志位），通过关闭 Job 句柄（`CloseHandle`）实现操作系统内核级别的 100% 安全、零 PID 误杀的原子级进程树销毁。

---

### 3.4 DIM-01 `IncrementalEventWriter` 阶段性 Checkpoint 与 SQLite WAL 并发事务冲突

#### 【缺陷审查】

1. **事务嵌套与死锁**：
   - DIM-01 §6.2 引入了 `IncrementalEventWriter`，要求在 `TurnEnd`、`ToolBatchEnd`、`ContextCompressionEnd` 关键阶段即时将内存事件 Flush 到 SQLite；
   - 如果此时外部 Orchestrator 正在持有外层的大事务（如更新会话元数据或 CAS 引用计数），内部阶段性 Flush 又尝试开启新的写入事务，将直接触发 SQLite 嵌套事务报错（`cannot start a transaction within a transaction`）或引发锁等待死锁。

#### 【整改要求】

- 增量事件写入必须统一采用基于 Sequence 的单条或微批次追加写入（`INSERT INTO events ...`），严禁在外层已开启的长事务内部启动平行排他事务。

## 四、反过度设计红线审查

对照仓库根目录 [`ANTI_OVERENGINEERING_GUARDRAILS.md`](file:///c:/Software/conex/ANTI_OVERENGINEERING_GUARDRAILS.md) 的 13 项硬性禁令，审查 5 份详案中的违规设计：

### 4.1 DIM-05 PTY 3 态状态机（Active/Detached/Dead）+ 60s 心跳 + 30s GC 轮询

#### 【红线违规判定】

- **审查事实**：DIM-05 §7 设计了一套包含 `Active`、`Detached`、`Dead` 3 态的保活状态机，并引入了前端 60 秒周期的 `ptyPing` 心跳定时器、后端 30 秒周期的 GC 轮询协程、以及 2 小时的后台宽限期；
- **过度设计批判**：
  1. Conex / Crish 是单机本地桌面应用，终端进程运行在用户本地机器上，绝非多租户云端远程容器集群（如 JupyterHub / Docker Daemon）；
  2. 桌面终端的生命周期极其简单：**前端卡片打开即存在，卡片关闭或会话销毁即终止**；
  3. 前端挂载 60 秒的 `setInterval` 心跳定时器，不仅破坏了 React 声明式渲染原则，而且会导致移动设备（笔记本电脑）的 WebView 无法进入深度低功耗休眠，无谓消耗电池电量；
  4. 30 秒常驻 GC 协程纯属将云端 Daemon 架构生搬硬套到单机客户端。

#### 【整改裁决】

- **彻底废除 60s 心跳定时器与 30s GC 协程**；
- 终端进程生命周期收敛为极简的原生模型：
  1. 窗口/卡片显式关闭 ➔ 触发 `pty_close` ➔ 关闭 Job Object 终止进程；
  2. 应用退出 ➔ Tauri 退出钩子触发 ➔ Job Object 级联清空子进程；
  3. 切换 Tab 时后台保持挂起运行，不设人工 2 小时死刑倒计时。

---

### 4.2 DIM-04 CAS 存储 7 天两阶段软删除隔离期与内存-数据库租约双向同步

#### 【红线违规判定】

- **审查事实**：DIM-04 §4.2 与 §4.3 规划了 `BlobLeaseGuard` 内存 `RwLock<HashMap>` 与 SQLite `active_blob_leases` 表的双向同步，并设置了 7 天的软删除隔离期（`marked_for_delete_at`）与垃圾回收扫描器（`cas_gc.rs`）；
- **违反禁令 3（单机桌面端严禁引入分布式复杂共识与重型 GC）**：
  1. 本地单机笔记与会话附件不存在复杂的分布式网络延迟，CAS 内容引用关系完全在本地 SQLite 关系表内（`block_attachments`、`message_attachments`）；
  2. 设计一套内存加锁、数据库写租约、GC 扫描、7 天反隔离自愈的复杂体系，不仅带来了 3.1 节所述的读写连接冲突，而且代码量高达 700 余行，极易产生边缘死锁与孤儿堆积。

#### 【整改裁决】

- 废弃内存与数据库双向租约同步的复杂状态机；
- 采用极简的 SQLite 声明式引用计数或单次批量 Mark-and-Sweep：仅在用户显式执行“清理存储空间”时，执行单次简单的 `DELETE FROM blob_cas WHERE hash NOT IN (SELECT hash FROM attachments)`。

---

### 4.3 DIM-04 `FuzzyMatcher` 引入 Rayon 全局多线程并行

#### 【红线违规判定】

- **审查事实**：DIM-04 §5.4 将文件模糊搜索重构为 `paths.par_iter().filter_map(...)`，拉入了 `rayon` 全局工作线程池；
- **过度设计批判**：
  1. 桌面工作区的文件列表通常在 1,000 ~ 30,000 条左右；
  2. 在 Rust 中，单线程对 30,000 个路径进行 `FuzzyMatcher` 评分耗时仅需 **1~3 毫秒**；
  3. 引入 Rayon 并行迭代器会将任务切碎分发给 8~16 个 OS 核心，产生的线程通信开销、内存缓存失效（Cache Thrashing）以及对 Tokio 运行时 CPU 的争抢，反而会导致端到端延迟恶化。

#### 【整改裁决】

- 移除 `rayon` 依赖，保留单线程高效向量化计算与 SmallVec 缓冲区复用，确保轻量低耗。

## 五、边界漏洞、算法死角与容错缺陷

### 5.1 DIM-01 `ToolPromiseDetector` 否定句/反语模式盲区与代码块围栏计数假阳性

#### 【缺陷审查】

1. **否定与反语过滤盲区**：
   - DIM-01 §2.6 的 `ToolPromiseDetector` 仅排除了历史复盘短语（如 `"在上一轮中"`、`"刚才尝试了"`）；
   - **反例现场**：若模型回复：`"为了系统安全，我不会执行 shell_command 来删除此文件。"`
   - 算法提取到正向模式 `"执行 shell_command"`，由于文本中不含历史短语，且未以问号结尾，算法将**错误判定为模型承诺执行工具**，随后向模型注入 Steering Nudge：`"检测到你承诺执行：'执行 shell_command'，请立即调用工具"`；
   - 模型被迫在下一轮执行了原本明确拒绝的危险命令，引发严重的安全违规与行为错乱！
2. **代码块围栏统计脆弱性**：
   - 算法采用 `text.matches("```").count() % 2 == 1` 判定是否在代码块内；
   - 若文本中包含内联 Markdown 转义（如在行内解释字符 `\`\`\` `），或使用了 4 个反引号围栏（` ```` `），计数将发生奇偶性倒错，导致代码块过滤彻底失效。

#### 【整改要求】

- 必须在第二层过滤中增加强烈的**否定式语义检查**（如 `"我不会"`, `"不建议"`, `"禁止"`, `"无需"`, `"i will not"`, `"cannot run"`, `"avoid executing"`）；
- 废除简单的子串计数，采用严格的行级 Markdown AST 扫描器（基于 `pulldown-cmark` 或紧凑状态机）判定光标是否处于代码围栏内部。

---

### 5.2 DIM-02 `split_segments` 缺少 Windows CMD 转义符（`^`）与 PowerShell 重音符（`` ` ``）支持

#### 【缺陷审查】

1. **Windows 原生转义穿透**：
   - DIM-02 §7.3 仅修补了 `\` 转义字符的判定；
   - 但在 Windows 平台上：
     - `cmd.exe` 使用脱字符 `^` 作为转义符（如 `dir ^& whoami` 中的 `&` 是字面量而非命令分隔符）；
     - `pwsh.exe` 使用重音反引号 `` ` `` 作为转义符（如 `Get-Process ```& echo 1`）；
   - DIM-02 的 `split_segments` 仍将 `^&` 或 `` `& `` 视作多命令连接符进行强制切分，导致命令被非预期斩断或沙箱误报解析失败。

#### 【整改要求】

- 分段器必须识别当前 Shell 类型（CMD 模式识别 `^`，PowerShell 模式识别 `` ` ``），在转义符后紧跟控制字符时正确保持整体 Token，杜绝分段畸变。

---

### 5.3 DIM-03 `build_anthropic_headers` 静态切片返回与 `reqwest::HeaderMap` 类型系统失配

#### 【缺陷审查】

1. **类型构造低效与签名失配**：
   - DIM-03 §4.3 中函数签名定义为：
     `pub fn build_anthropic_headers(...) -> Vec<(&'static str, String)>`
   - 上层 `agent-provider` 发起 HTTP 请求使用的是 `reqwest::Client`，其请求头需要 `reqwest::header::HeaderMap` 或 `HeaderName`；
   - 返回字符串元组列表导致外层每次请求都要进行二次遍历和 `HeaderValue::from_str` 转换，若 Header 字符串中意外混入非 ASCII 字符（如在动态 Model 字段中），转换时将直接抛出 `InvalidHeaderValue` 错误。

#### 【整改要求】

- 函数签名直接重构为返回 `reqwest::header::HeaderMap`，在内部完成 `HeaderName::from_static` 与校验，向调用方提供强类型保障。

---

### 5.4 DIM-04 `SummaryDocument` 宽容解析全空回填导致模型衰退静默掩盖

#### 【缺陷审查】

1. **全默认值掩盖模型严重劣化**：
   - DIM-04 §6.3 中，当大模型输出的 JSON 格式严重残缺或缺少核心字段时，解析器将 `goal`、`progress`、`decisions`、`next_steps` 全部回填为空字符串 `""` 并返回 `Ok(SummaryDocument)`；
   - 这虽然消除了连续 3 次重试风暴，但导致会话上下文压缩生成了毫无内容的“空摘要卡片”；
   - 随后的多轮对话将彻底丢失先前的历史决策与目标上下文，智能体发生严重的“记忆丧失”却没有任何告警日志。

#### 【整改要求】

- 宽容解析器必须设定**底线有效性断言**：`goal` 与 `progress` 至少有一项非空；若全部为空，则判定为解析失败，优雅回落至基于规则的确定性文本拼接摘要（Deterministic Fallback），而非生成空对象。
