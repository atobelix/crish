## 二、专题一：跨方案 Rust 与 TS 接口结构体/枚举不一致断层

### 2.1 【致命编译断层】DIM-01 `AgentEvent::ToolStart/ToolEnd` 变体私设字段与 `conex-types` 严重冲突

#### 缺陷事实与证据链：

在 `01-内核双轨事件与自愈状态机执行详案.md` §3.3（第 343-351 行）与 §6.8 中，作者给出了如下 Rust 代码蓝图：

```rust
// ❌ DIM-01 伪代码（直接导致 rustc 编译中断）
sink.push_live(AgentEvent::ToolStart {
    session_id: state.machine.context().session_id.clone(),
    timestamp: crate::steering::now_iso_utc(),
    call_id: call.id.clone(),      // 🔴 错误：AgentEvent::ToolStart 没有 call_id 字段！
    tool_name: call.tool_name.clone(), // 🔴 错误：AgentEvent::ToolStart 没有 tool_name 字段！
    input: call.input.clone(),          // 🔴 错误：AgentEvent::ToolStart 没有 input 字段！
    turn_index: Some(state.machine.context().turn_index),
});
```

而在真实权威底层契约 `crates/conex-types/src/events.rs:470-505` 中：

```rust
// ✅ crates/conex-types/src/events.rs 真实定义
#[serde(rename = "tool-start", rename_all = "camelCase")]
ToolStart {
    session_id: String,
    batch_id: String,                  // 必填字段
    call: ToolBatchCall,               // 包装了 id, tool_name, input 的结构体！
    timestamp: String,
    turn_index: Option<u32>,
},
#[serde(rename = "tool-end", rename_all = "camelCase")]
ToolEnd {
    session_id: String,
    batch_id: String,
    result: ToolBatchResult,           // 包装了 tool_call_id, output, is_error 的结构体！
    timestamp: String,
    attempt: Option<u32>,
    deduplicated: Option<bool>,
    executed_input: Option<serde_json::Value>,
    turn_index: Option<u32>,
},
```

#### 破坏性影响：

1. **代码完全无法编译**：若照搬 DIM-01 详案代码，`cargo check` 直接报 `error[E0560]: struct 'AgentEvent::ToolStart' has no field named 'call_id'` 与 `missing field: 'batch_id', 'call'`；
2. **事件序列化结构脱靶**：前端生成的 TS 解析器依赖 `event.call.id` 与 `event.result.toolCallId`。DIM-01 私设平铺字段破坏了全系统双端代码生成协议。

### 2.2 【致命运行时丢包】DIM-02 `EventRouter` 缺失字段寻址引发全量工具事件去重误杀（`tool-start:undefined`）

#### 缺陷事实与证据链：

在 `02-前端流式管道与交错多步骤时间线执行详案.md` §3.4（第 392-394 行）中：

```typescript
// ❌ DIM-02 致命去重计算代码
if (
  envelope.event.type === 'tool-start' ||
  envelope.event.type === 'tool-end'
) {
  return `${envelope.event.type}:${envelope.event.callId}`; // 🔴 严重 BUG：event 上根本没有 callId！
}
```

根据 `conex-types` 的 Serde 序列化产物：

- `tool-start` 事件体为：`{ type: "tool-start", batchId: "...", call: { id: "call_1", toolName: "shell_command", ... } }`
- `tool-end` 事件体为：`{ type: "tool-end", batchId: "...", result: { toolCallId: "call_1", isError: false, ... } }`

在 TS 运行时中，`envelope.event.callId` 恒为 `undefined`！

#### 破坏性影响：

第 1 个工具事件到达时计算 key 为 `"tool-start:undefined"`，加入 `consumedEvents`。后续执行的所有第 2、第 3、第 N 个工具的 `tool-start` 事件，计算 key 全部都是 `"tool-start:undefined"`，**全部被判定为重复事件而静默丢弃！**
这将导致长程任务中除第 1 个工具外，后续所有工具卡片完全无法在前端弹出，引发严重的黑盒假死！

### 2.3 【架构抵触】DIM-01 `ToolContext` 缺失 `permission_mode` 且私自回退 `current_dir()` 破坏 DIM-04 根基

#### 缺陷事实与证据链：

对比 DIM-01 与 DIM-04 在核心文件 `crates/session-loop/src/exec_single.rs` 的构造点：

```rust
// ❌ DIM-01 §4.3（第 509-528 行）代码蓝图：
let tool_ctx = ToolContext {
    session_id: ctx.session_id.clone(),
    abort_token,
    ask,
    workspace_root: ctx.workspace_root.clone()
        .or_else(|| ctx.cwd.clone().map(PathBuf::from))
        .unwrap_or_else(|| std::env::current_dir().unwrap_or_else(|_| PathBuf::from("."))), // 🔴 违背 DIM-04
    write_claims: ctx.write_claims.clone(),
    write_claim_holder: Some(ctx.run_id.clone()),
    explore_docs_quota: ctx.explore_docs_quota.clone(),
    output_dir: ctx.output_dir.clone(),
    background: ctx.background.clone(),
    log_root: ctx.log_root.clone(),
    compression_store: None,
    note_backend: ctx.note_backend.clone(),
    tool_call_id: Some(call.id.clone()),
    // 🔴 严重遗漏：完全没有 permission_mode 字段！
};
```

而在 DIM-04 §3.2（第 275-327 行）与 §4.1 中明确定义：

1. `ToolContext` 必须包含 `pub permission_mode: PermissionMode`；
2. 严禁无工作区时回退到 `std::env::current_dir()`（避免沙箱绑定到桌面壳所在目录 `src-tauri`），必须显式建模为 `Unbound`。

#### 破坏性影响：

DIM-01 的实现方案与 DIM-04 的权限集中化方案在同一文件 `exec_single.rs` 发生不可调和的代码冲突。DIM-01 会抹掉权限模式，导致所有叶子工具无法读取 `ctx.permission_mode`。

### 2.4 【类型降级与丢失】DIM-03 6 档 `ThinkingLevelMode` 无法下沉至 Rust `ReasoningEffort` 导致档位丢失

#### 缺陷事实与证据链：

1. **主控总纲 vs DIM-03 档位冲突**：`00-总方案` §3 DIM-03 明确规定支持底栏即时切换 `Minimal`/`Medium`/`Deep` 3 档；而 DIM-03 详案私自扩展为 6 档：`'off' | 'minimal' | 'low' | 'medium' | 'high' | 'max' | 'custom'`（DIM-03 第 1180 行）；
2. **Rust 内核类型不支持**：在 `crates/session-loop/src/loop/loop_options.rs` 中，`reasoning_effort` 字段类型为 `Option<crate::provider::ReasoningEffort>`。该 Rust 枚举只有 `Off`, `Low`, `Medium`, `High`, `Auto`。
3. 当前端下发 `thinking_level: "minimal"` 或 `"max"` 时，`run_launch.rs` 无法将其转换为 `ReasoningEffort`，直接丢失语义或引发匹配分支 Panic。

---

### 2.5 【反序列化隐患】DIM-04 极简三档 `PermissionMode` 与 TS `permissionModes.ts` 字符串字面量脱节

#### 缺陷事实与证据链：

1. 在 DIM-04 §3.1 中，Rust 枚举被命名为 `PermissionMode::Plan`, `PermissionMode::Ask` (在表格中又被称为 `Standard`), `PermissionMode::FullAccess`；
2. 在前端 `apps/crish-desktop/src/api/permissionModes.ts` 中，历史遗留的 `PermissionMode` 字符串为 `'ask' | 'deep' | 'full' | 'plan'`，引擎模式为 `'ask' | 'auto' | 'full-access' | 'plan'`；
3. DIM-04 未在 Rust `PermissionMode` 枚举上明确标注 `#[serde(rename_all = "kebab-case")]` 及别名 `#[serde(alias = "full")]`。
4. 前端通过 IPC 传入 `"full"` 或 `"standard"` 时，Rust serde 将无法正确反序列化，导致模式静默回落到默认的 `Ask`，完全访问模式名存实亡。

---

### 2.6 【状态机数据孤岛】DIM-02 `timelineNormalizer` 完全忽略 DIM-03 `thinkingTurns` 导致多轮思考蒸发

#### 缺陷事实与证据链：

1. DIM-03 §3.3 在 `SessionMessage` 中新增了结构化字段 `thinkingTurns?: Array<{ turnIndex: number; content: string; durationMs?: number }>`；
2. 然而，DIM-02 §5.3 的 `normalizeAssistantTimeline` 与 `buildAssistantTimeline` 核心算法中，仅处理了 `msg.blocks` 与旧版 `msg.thinking`，**完全未对 `msg.thinkingTurns` 进行任何迭代或转换为 `AssistantTimelineItem`**；
3. 当用户刷新界面或触发消息重整化时，DIM-03 记录的多轮思考数据将被 DIM-02 的规范化器直接丢弃，退化为仅渲染最后一段思考或无思考。

---

### 2.7 【元数据断裂】DIM-01 `shell_exec` 字符串拼接 `logPath` 导致 DIM-05/DIM-07 结构化面板读取落空

#### 缺陷事实与证据链：

1. DIM-01 §4.5（第 576-581 行）中，超限日志落盘后，将日志路径直接作为普通文本拼接到工具输出的末尾：
   `ToolOutput::success(format!("{}\n\n[⚠️ 输出已超过 256KB 阈值被截断。完整原始日志已落盘至: {}]", view, path))`；

### 3.1 【违反红线 11】DIM-06 私设前端多包微内核与 IPC 虚假权限校验代理层（`packages/plugin-sdk`）

#### 审查裁决：

**严重违背《反过度设计硬性红线》禁令 11（严禁同进程微服务套娃与虚假解耦 Facade）**：

1. Markdown 编辑器、受管浏览器与 Follow-up 本质上是当前桌面客户端内置的 4 个核心 UI 视图组件；
2. 客户端前端处于同一个浏览器 WebView 内存空间内，在前端 TS 层额外设立 4 个独立 npm package 并包裹一套仿 VSCode 的插件沙箱与 IPC 权限代理拦截层，属于典型的过度工程化；
3. **整改要求**：保留统一的组件生命周期与卸载清理逻辑，取消单独抽包（`packages/plugin-*`），直接在 `apps/crish-desktop/src/components/` 内按领域模块组织，消除虚假的中间代理层。

### 3.2 【引入冗余外置依赖】DIM-05 终端等宽排版引入 `@chenglou/pretext` 导致不必要包体积膨胀

#### 违规事实：

在 `05-工具摘要防逃逸与输入输出分栏执行详案.md` §5.2（第 41-42 行）中，作者引入了 `@chenglou/pretext` 库用于计算工具输出日志的虚拟行高与排版测距。

#### 审查裁决：

**过度设计且技术选型不合理**：
工具输入输出区（`ToolCallInputPane` / `ToolCallOutputPane`）的终端日志采用严格的等宽字体（Monospace，如 JetBrains Mono / Consolas），且 CSS 明确锁定了固定行高（`line-height: 20px`）。
在此场景下，行高测量是一个常数级数学计算（`y = lineIndex * 20`），根本不需要引入基于 Canvas 2D 的多语言动态折行测量库 `@chenglou/pretext`。应当彻底移除该外部依赖。

### 3.3 【状态机过度复杂】DIM-07 原生终端私设 3 态生命周期与“2 小时 Detach 宽限期 GC 机制”

#### 违规事实：

在 `07-原生ConPTY终端与质量门禁执行详案.md` §2.6（第 24 行）中，作者为本地 ConPTY 会话设计了 `Active` / `Detached` / `Dead` 三态转移，并引入了“2 小时无操作后台清理 GC 机制”。

#### 审查裁决：

**单机桌面端过度设计**：
Conex 是单机桌面应用，PTY 会话与前端 Tab 视图是 1:1 的直接绑定关系。当用户在 UI 关闭终端 Tab 时，应当直接通过 Job Object 发送终止信号销毁进程树并释放 PTY 资源；没有必要模仿远程 SSH 终端（如 tmux/screen）在后台挂起进程长达 2 小时并轮询 GC。

## 四、专题三：死锁、竞态、线程饥饿与状态机边界漏洞

### 4.1 【死锁/误判】DIM-01 `ToolPromiseDetector` 语言偏见与反向过滤误杀正常计划解释

#### 缺陷事实与代码盲区：

在 `01-内核双轨事件与自愈状态机执行详案.md` §5.3 中：

```rust
// ❌ DIM-01 ToolPromiseDetector 逻辑漏洞
let action_patterns = [
    "尝试单独调用", "正在调用", "现在开始执行", "接下来使用",
    "准备运行", "尝试通过", "我将执行", "使用 PowerShell",
    "使用 shell_command", "重新运行",
];
```

1. **纯中文硬编码，英文完全失效**：当模型以英文回复 `"I will now execute the build script via shell_command to fix this."` 时，正则完全脱靶，导致英文自白暴毙问题依然 100% 存在；
2. **反向过滤误杀**：如果模型在回复中给出规划说明：“我将执行重构计划，但在开始前需要向您说明以下背景情况。”（句末是句号，非问号），由于未命中 `？` 且未包含 `是否需要`，它将被判定为行动自白，状态机强行注入 Steering Nudge，打断正常对话！
3. **Nudge 历史堆积**：自愈注入的 `AgentMessage::user_nudge` 未标记为临时瞬态消息，会作为永久 User 消息存入 SQLite 与 Context，导致后续多轮对话的上下文被系统垃圾提示词污染。

---

### 4.2 【时序竞态】DIM-02 `handleThinkingResetOnChunk` 与 48ms `thinkingBatcherRef` 竞态导致首字抹除

#### 缺陷事实与竞态时序：

在 `02-前端流式管道与交错多步骤时间线执行详案.md` §4.2 中：

- `thinkingBatcherRef` 采用了 **48ms** 的 Leading/Debounce 批合并策略；
- 当 LLM 快速从思考流（`thought`）切换到正文流（`text`）时，第 1 个正文 chunk 在 10ms 内到达，触发 `handleThinkingResetOnChunk`；
- 此时，由于 48ms 定时器尚未触发，`streamingStore` 中的 `liveThinking` 依然为空；
- `handleThinkingResetOnChunk` 检查 `liveThinking` 为空，误判定为“没有思考”，直接调用 `thinkingBatcher.drop(key)`，将 48ms 缓冲区中排队的真实思考 Token 全部丢弃并抹除！

---

### 4.3 【内存泄漏】DIM-02 `pendingToolEnds` 因果缓存区在工具异常崩溃时永不释放

#### 缺陷事实：

在 `02-前端流式管道与交错多步骤时间线执行详案.md` §3.4 中：

```typescript
private readonly pendingToolEnds = new Map<string, BridgeEventEnvelope>();
```

若后端在发射 `tool-start` 之前发生 panic 或网络通道故障，只在收口阶段发射了带有 error 的 `tool-end`，该事件将进入 `pendingToolEnds` 并永远等待 `tool-start`。由于没有设置最大容量限制（Capacity Limit）和基于时间的淘汰策略（TTL），长时间运行的长程会话会导致该 Map 无界增长，造成内存泄漏。

---

### 4.4 【Tokio 线程饥饿】DIM-04 路径解析内部同步 `canonicalize` 阻塞 Tokio Worker 线程

#### 缺陷事实：

在 `04-三档权限集中化与Windows路径归一执行详案.md` §4.2 与 §6.1 中，`ConexPathNormalizer::normalize` 与 `safe_canonicalize` 直接调用了标准的阻塞式系统调用 `std::fs::canonicalize`。
在 Windows 平台上，若工作区位于 SMB/NFS 网络映射盘或慢速外部移动硬盘，`std::fs::canonicalize` 会触发耗时数十毫秒至数秒的阻塞式 I/O。在异步 Tokio 上下文中高频同步调用该函数，将迅速耗尽 Tokio 工作线程池，引发整个后端 IPC 响应停滞。

---

### 4.5 【交互死锁】DIM-02 `stickToBottomLock` 强力吸底与用户向上回滚查看输入区产生冲突

#### 缺陷事实：

在 `02-前端流式管道与交错多步骤时间线执行详案.md` §6.4 中，为了解决步骤折叠引起的视口跳动，引入了全局流式吸附锁 `stickToBottomLock`。
然而，在多步骤长程任务中，用户经常需要在第 3 步执行时向上滚动去查看第 1 步工具卡片中的输入参数（DIM-05 Input Pane）。如果 `stickToBottomLock` 在流式期间无条件保持 `true`，用户每一次向上滚轮操作都会在下一个 Token 到达时（16ms 内）被强制重置回页面最底部，造成用户无法审查历史步骤的“视口锁定死锁”。

### 5.2 统一前端 `EventRouter` Dedupe Key 提取算法（纠偏 DIM-02）

前端提取 Tool ID 必须穿透 `call` 与 `result` 嵌套层级：

```typescript
// ✅ 统一纠偏后的 EventRouter 去重键生成逻辑
export function buildEventDedupeKey(
  envelope: AgentEventEnvelope
): string | null {
  if (envelope.sequence != null) {
    return `seq:${envelope.sequence}`;
  }

  const { event } = envelope;
  if (event.type === 'message-delta') {
    return null; // 增量分片全量放行
  }

  if (event.type === 'tool-start') {
    const callId = event.call?.id || (event as any).callId;
    const turn = event.turnIndex ?? 0;
    return callId ? `tool-start:${turn}:${callId}` : null;
  }

  if (event.type === 'tool-end') {
    const callId =
      event.result?.toolCallId || event.result?.id || (event as any).callId;
    const turn = event.turnIndex ?? 0;
    return callId ? `tool-end:${turn}:${callId}` : null;
  }

  if (event.type === 'turn-start' || event.type === 'turn-end') {
    return `${event.type}:${event.sessionId}:${event.turnIndex}`;
  }

  return null;
}
```

## 六、评审总结与整改推进令

1. **总评结论**：7 份详案覆盖了重构的核心范围，但在跨模块协作接口处存在明显的**“各自为政、字段臆造、时序竞态与过度设计”**问题。若直接进入代码实施，必将导致编译全面阻断和多处运行时诡异 Bug。
2. **强制整改动作**：
   - DIM-01 与 DIM-02 必须按照 §5.1 与 §5.2 修正事件载荷与去重逻辑；
   - DIM-01 与 DIM-04 必须合并统一 `exec_single.rs` 的 `ToolContext` 构造点；
   - DIM-06 必须剥离 `packages/plugin-sdk` 虚假微内核，改为组件级高内聚解耦；
   - DIM-05 必须剔除 `@chenglou/pretext` 依赖，采用常数级等宽行高模型；
   - DIM-02 必须修复 `handleThinkingResetOnChunk` 竞态并为 `pendingToolEnds` 设置上限。
3. **整改产物归档**：本评审报告作为实施前的最终把关基准，所有整改必须在代码落地阶段严格执行，违者门禁一律阻断。
