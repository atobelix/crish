## 一、总体结论

1. **6 份方案的核心问题全部成立**，没有误报型方案。问题不是六个孤立缺陷，而是同一种架构病在六个面的表现：**同一概念存在多个真源、多个形态、多个入口，且缺少防回归门禁**。
2. 方案是快照，当前工作区已继续演进，部分数量发生漂移，但结论不变：
   - `#[path]`：方案快照 196 条，当前 **206 条**（按路径名近似分类：生产 117 / 测试 89），增加 10 条；
   - `unix_millis()`：方案称 33 处调用，当前 **31 处调用**（另有 1 处定义），其中 **28 处**仍是 `as u64` / `as i64`；
   - `UNIX_EPOCH`：当前 **110 个文件**、`SystemTime::now()` **146 处**、`duration_since(UNIX_EPOCH)` **54 处**；
   - 错误码：Rust 常量 **105**、Rust 注册表 **105**、TS 联合类型 **105**、TS 注册表 **105**，四份手工镜像当前数值相等，但真源方向仍不唯一；
   - `conex-types/src/lib.rs` 仍为 654 行、`events.rs` 1579 行、`device/` 5389 行；`conex-compaction/src/engine.rs` 仍为 869 行。
3. **当前工作区不满足多数阶段门控**：三个模块分支（`refactor/session-stream`、`refactor/provider-loop`、`refactor/sandbox-classifier`）均未合并进 `main`；工作区有 481 条未提交状态记录（284 条含暂存改动、216 条含未暂存改动，二者有重叠），其中 `crates/conex-run/src/run/**`、`crates/conex-db/**`、`apps/agent-workbench/src-tauri/**` 等正是方案的在写区。
4. 因此当前只能安全执行**稳定区 Wave A**（目标文件与在写区不相交），其余阶段必须等待在写改动提交、模块分支合并后再做。强行越过门控会把并行改动互相覆盖，违反仓库 Git 纪律。
5. 本次核实新增 **5 项方案未覆盖的连带问题**（见第三节），其中 `output_dir` 生产恒为内存实现属于真实功能缺口，需要单独决定是否纳入本轮。

TY 方案 D-TY-5 只讨论把模型默认值改为语言无关常量；若只改模型、不改 DB 默认与迁移，会形成“新写入 `default`、旧行 `常规会话`、DDL 默认 `常规会话`”的三态漂移。**该问题要么保持现状只提取常量，要么作为独立的数据迁移任务处理，不能只改一处。**

### N2 · `output_dir` 生产装配恒为内存实现（真实功能缺口）

`session-loop/src/loop/loop_runner.rs:154-159`：当 `options.assembly.output_dir` 为 `None` 时自动装配 `OutputWorkspace::new(..., InMemoryOutputDirStore)`。全生产链路没有任何一处设置 `output_dir: Some(...)`（`rg` 仅命中 `loop_runner` 的兜底分支；`run_launch.rs` 只读取 `config.output_dir` 做注入提示，不装配 store）。结果是：**生产运行时输出目录映射只存在于进程内存，重启即丢失**。

这不是测试替身问题（X-06 a.3 已把它转交缺失的 `agent-tools.md`），而是功能缺口。若本轮要“系统性、彻底”，建议单列一项：由壳层注入基于 `session_meta` 的持久化 `OutputDirStore`，并删除内存兜底作为生产默认。

### N3 · `#[path]` 数量在快照后继续增长

方案快照 196 条，当前 206 条，新增 10 条。仓库没有任何 `#[path]` 门禁，因此该数字只会在并行拆分中继续上涨。X-05 的 P4 门禁不是可选项，而是必须与 P1 同步落地的止损措施。

### N4 · `ToolErrorKind` 反向映射只覆盖 12 个变体中的 6 个

`exec_verdict.rs:293-305` 只把 `tool.not_found`、`tool.invalid_input`、`tool.requires_approval`、`tool.user_denied`、`tool.approval_expired`、`tool.cancelled` 映射回具体变体，其余全部落入 `ExecutionFailed`。这意味着 `Timeout`、`SoftDeny`、`PolicyBlocked`、`AbortedBeforeDispatch`、`OutcomeUnknown` 在“码 → kind”方向丢失语义。X-04 D-X04-3 已提出此问题，但方案把它列为“待决策”；按“彻底改进”原则应一次性补齐，并在补齐前确认审批/重试分支的行为变化。

### N5 · `ToolErrorKind::SoftDeny` 是无生产者的兼容变体

`SoftDeny` 仅出现在枚举定义、`is_never_fatal` 匹配、码映射和一条测试断言中；生产代码不再构造它（`tool_exec.rs` 注释已声明“不再折叠为 SoftDeny”）。这正是“非必要不兼容”的对象：若确认无外部 API 消费者，应删除该变体，而不是保留一个没有生产者的枚举值。该问题不在 6 份方案内，建议随 X-04 P4 一同裁决。

## 七、风险与注意事项

1. **在写区冲突**：Wave A 虽只碰干净文件，但提交后若当前在写改动也修改同一路径，合并时需人工解冲突；执行前必须再次核对 `git status` 目标文件。
2. **wire 回归**：错误码/事件/摘要/设备协议的字符串与字段形态不得变化。X-04 P1 与 TY P7 必须先做 fixture 对拍，再改代码。
3. **测试数量流失**：X-05 全部是移动，测试数量前后必须一致；用 `cargo test --workspace -- --list` 计数写入进度。
4. **chrono 引入**：只允许用于 cron 的本地时区/DST；时间工具仍保持纯 std，不得把 chrono 扩散到 `conex-shared::time`。
