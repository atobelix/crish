## 一、背景与空间挑战分析

### 1.1 右坞物理环境约束

在 Conex/Crish 桌面应用中，右侧工具坞（`leafDockDrawer`）是挂载在每个对话叶（`TreeLeafPanel`）内部右侧的工具区。
- **宽度范围**：受限于用户的屏幕尺寸以及主对话流与右坞的分隔比例（`widthRatio`，默认 0.5），右坞在常规 1080p~4K 屏幕下的实际物理宽度通常分布在 **320px ~ 900px** 之间。
- **全屏 vs 右坞差异**：
  - 此前顶层的二叉树分屏系统运行在整个窗口宽度（1280px ~ 2560px）上，水平空间极其充裕；
  - 迁移至右坞后，每个分屏窗格（Split Pane）面对的横向物理宽度可能被腰斩至 **160px ~ 450px**，纵向高度在 **400px ~ 1000px** 之间。

### 1.2 现有单窗格右坞的交互瓶颈

目前 `TreeLeafPanel.tsx` 中的右坞为单窗格结构：
```tsx
// 现行实现：无论打开多少个面板，右坞只通过单一 LeafToolTabStrip 在同一时刻展示一个 panel
{dock.openPanelIds.length > 0
  ? dock.openPanelIds.map((pid) => (
      <div key={pid} style={{ display: pid === toolPanelId ? 'flex' : 'none' }}>
        {renderToolOutlet(pid)}
      </div>
    ))
  : renderToolOutlet(toolPanelId)}
```
这种模式在多工具协同工作时存在显著瓶颈：
1. **多任务盲切**：用户无法同时观察代码变更（Diff）与测试终端（Terminal），必须频繁在顶部 TabStrip 来回点击切换；
2. **缺乏空间并行能力**：在 Web 预览时无法对照源码文件树；在执行持续构建时无法同步查看输出日志与正在编辑的草稿笔记；
3. **空间利用率两极分化**：当用户将右坞拉宽至 800px 时，单栏终端或单栏文件树出现大面积空白浪费；当右坞较窄时，缺乏垂直切分的自适应手段。

### 1.3 核心设计目标与体验愿景

将分屏能力下沉至右坞后，本方案必须达成以下体验原则：
1. **轻量极致（Zero Overhead）**：不能因为增加了分屏而让右坞充满沉重的边框、繁杂的工具栏或重叠的标题栏；每一像素都必须服务于有效工作内容；
2. **自适应感知（Adaptive & Resilient）**：窗格随右坞整体宽度以及 Sash 拖拽动态响应，通过 CSS 容器查询自动呈现最合适的内容密度与布局模式；
3. **直觉操作（Intuitive Splitting）**：在窗格右上角提供一目了然的“向右/向下分屏”、“最大化/还原”与“关闭”动作，并辅以一键预设与全键盘导航；
4. **视觉严守项目规范**：杜绝厚重黑边（`AGENTS.md` §13），禁止使用原生 `title`（§12），全面拥抱 HSL 柔和色系（§14）。

## 二、右坞微型头部交互条（Micro TabStrip）架构与交互设计

### 2.1 整体拓扑与层级关系（Dock Header vs Pane Header）

在分屏右坞体系中，存在两级头部概念：
1. **全局坞控制条（Dock Top Bar）**：
   - 当右坞处于**单窗格（Single Pane）状态**时：保持原有的 `LeafToolTabStrip` 形态，兼具全局坞关闭、坞最大化与单窗格 Tab 切换功能；
   - 当右坞处于**多分屏（Multi-Pane）状态**时：右坞顶部保留一个超紧凑的全局辅助条（Dock Header，高度 28px），提供“全局预设切换”、“新建窗格”、“全坞收起/全坞最大化”；各个子窗格则各自拥有专属的微型窗格头部（Micro Pane TabStrip）。
2. **微型窗格头部（Micro Pane TabStrip，子窗格头部）**：
   - 附着于每一个具体的分屏叶子窗格（Pane）顶部；
   - 高度统一固定为 **26px ~ 28px**（对齐 `TAB_HEIGHT_PX = 28` 几何常量）；
   - 负责承载该窗格内的多 Tab 切换、新建 Tab、向右/向下分屏动作及窗格最大化/关闭。

```text
┌────────────────────────────────────────────────────────┐
│ [📐 布局预设 ▾]                          [◰ 全坞最大化] [✕ 收起]│ ← Dock Top Bar (全局坞状态控制)
├──────────────────────────┬─────────────────────────────┤
│ [📄 Diff.tsx ✕] [+]      │ [🖥️ Terminal ✕] [+]        │ ← Micro Pane TabStrip
│                          │          [◫ 右分] [⬒ 下分] [⛶] [✕]│ ← 窗格动作集群
├──────────────────────────┼─────────────────────────────┤
│                          │                             │
│       Diff 比对内容       │       原生 ConPTY 终端       │
│                          │                             │
└──────────────────────────┴─────────────────────────────┘
```

### 2.2 窗格微型 TabStrip 视觉与几何规格

微型 TabStrip 继承并微调了 `tabStripGeometry.ts` 的规范，在保证触控与点击精度的前提下实现最大垂直空间节省：

| 属性 | 几何数值 / Token | 规范与说明 |
| :--- | :--- | :--- |
| **头部容器高度** | `28px` (`--pane-tab-height`) | 紧凑无下边框设计，底部分界由窗格细分边框提供 |
| **Tab 默认高度** | `24px` | 比主标签（28px）微小 4px，突出子层级关系 |
| **Tab 最大宽度** | `130px` (`--tool-tab-width-max`) | 内容自适应，超出文本以 `text-overflow: ellipsis` 截断 |
| **Tab 最小宽度** | `32px` | 极限挤压时保留图标展示，文本隐退 |
| **Tab 间距 (Gap)** | `3px` | 保持视觉轻盈 |
| **Tab 左右内边距** | `padding: 0 4px 0 6px` | 紧凑微型布局 |
| **Tab 圆角** | `var(--radius-md, 6px)` | 柔和圆角，呼应主界面 token |
| **字体大小与字重** | `11.5px / 400`（激活态 `500`） | 紧凑清晰，`var(--font-size-xs)` |
| **图标尺寸** | `12px × 12px` | 匹配微型标签比例 |
| **关闭按钮** | `14px × 14px`，hover 时浮现 | 默认透明度 0，聚焦或悬停时呈现柔和微底色 |

#### Tab 入场与离场动效
- **入场动效**：沿用 `@starting-style` 机制，首帧 `max-width: 0; opacity: 0;` 平滑向右撑开，时长 150ms（`var(--duration-fast)`）；
- **离场动效**：`[data-leaving="true"]` 先文字快速淡出（80ms），壳体紧随收缩（150ms），配合负 `margin-right` 消除布局跳变。

### 2.3 窗格右上角动作集群（Pane Action Cluster）

每个分屏窗格头部右侧常驻或悬停展现微型动作按钮组（高度 22px，宽度 22px），为用户提供即时的窗格操控能力：

```text
┌──────────────────────────────────────────────┐
│ [🖥️ Terminal ✕] [+]   [◫ 右分] [⬒ 下分] [⛶ 最大化] [✕ 关闭]│
└──────────────────────────────────────────────┘
```

1. **向右分屏按钮（Split Right）**：
   - **图标**：`split-horizontal`（或矩形左右均分图标，13px）；
   - **Tooltip**：`<Tooltip content="向右分屏 (Ctrl+Shift+\)">`；
   - **交互行为**：
     - 将当前窗格拆分为左右两个子窗格，当前窗格占 50%，右侧新建窗格占 50%；
     - 新窗格默认弹出轻量级面板选择器（Quick Launcher）或复制当前窗格的工具视图；
     - **宽度守卫**：若当前窗格宽度 `< 360px`，按钮呈现提示态并附带 Tooltip：“当前宽度过窄，推荐使用向下分屏”。
2. **向下分屏按钮（Split Down）**：
   - **图标**：`split-vertical`（或矩形上下均分图标，13px）；
   - **Tooltip**：`<Tooltip content="向下分屏 (Ctrl+Shift+-)">`；
   - **交互行为**：
     - 将当前窗格拆分为上下两个子窗格，各占 50% 高度；
     - 适合在紧凑宽度下扩展工作区，极具可用性。
3. **窗格最大化 / 还原按钮（Maximize / Restore Pane）**：
   - **图标**：最大化态 `maximize-2` / 还原态 `minimize-2`（13px）；
   - **Tooltip**：`<Tooltip content={isSolo ? "还原分屏 (Alt+M)" : "最大化此窗格 (Alt+M)"}>`；
   - **交互行为**：在多窗格状态下，临时让该窗格独占右坞 100% 空间，其余窗格 `display: none`（保持运行时与 DOM 存活，不销毁），再次点击恢复原多窗格拓扑。
4. **关闭窗格按钮（Close Pane）**：
   - **图标**：`x`（12px）；
   - **Tooltip**：`<Tooltip content="关闭窗格 (Alt+W)">`；
   - **交互行为**：优雅关闭该窗格及其包含的所有 Tab，剩余兄弟窗格平滑填充释放的空间。若右坞仅剩最后一个窗格，关闭该窗格等同于收起右坞。

### 2.4 单窗格最大化（Solo Focus）与分屏还原

在多窗格下，用户经常需要临时放大某个窗格（如临时需要大量终端输出审查，或看详细 Diff）：
- **状态记录**：右坞状态树维护 `soloPaneId: string | null`；
- **纯 CSS 级非破坏性缩放**：
  - 树结构不被展平，二叉树 ratio 保持不变；
  - 拥有 `data-solo-active="true"` 的窗格通过 CSS `position: absolute; inset: 0; z-index: 10;` 铺满右坞内容区；
  - 隐藏其他窗格与中间的 Sash 分割条，零重排损耗；
- **还原反馈**：头部微型条显式展示高亮蓝点或呼吸徽标，提示用户当前处于“聚焦放大模式”，快捷键 `Esc` 或再次点击图标即瞬间还原。

### 2.5 空态窗格与新建面板（Micro Launcher）

当用户通过快捷分屏新建了一个没有指定默认面板的空白窗格时，该窗格内部呈现 **Micro Launcher（微型启动磁贴）**：
- **快速唤起选项**：
  - 🖥️ **终端（Terminal）**：快速新建一个隔离的会话 PTY；
  - 📄 **代码比对（Diff）**：查看当前 Git 变更；
  - 📁 **文件树（Files）**：浏览工程文件；
  - 🌐 **Web 预览（Preview）**：打开内置浏览器；
  - 📝 **笔记（Notes）**：打开草稿备忘；
- **极简卡片流**：卡片采用单行小胶囊按钮（高度 32px，圆角 8px），悬停微反差背景，无繁琐说明，一键点击即就地挂载对应工具组件。

## 三、紧凑空间自适应排布与容器查询体系

### 3.1 宽度梯度分级与物理断点策略

右坞宽度（Dock Width, $W_d$）以及各窗格宽度（Pane Width, $W_p$）具有极强的动态性。我们确立四个标准物理断点档位：

```text
       320px              450px              680px              900px+
─────────┬──────────────────┬──────────────────┬──────────────────►
  极窄坞 (Compact)    窄坞 (Tight)       标准坞 (Normal)     宽坞 (Spacious)
  严禁左右分屏        左右分屏强退化       标准上下/左右分屏     自由网格/多栏
  强制纯单栏/紧凑     工具双栏转单栏       完整工具体验         宽松高密度
```

| 档位名称 | 坞宽度区间 ($W_d$) | 窗格分屏策略建议 | 核心适配手段 |
| :--- | :--- | :--- | :--- |
| **极窄坞 (Compact)** | `< 360px` | **禁止向右分屏**；仅允许**上下分屏**（最多 2 窗格） | 向右分屏按钮置灰；TabStrip 仅保留活动 Tab 图标与简短名；工具视图进入极简视图 |
| **窄坞 (Tight)** | `360px ~ 480px` | **优先推荐上下分屏**；若强行左右分屏，单窗格进入超紧凑态 | 左右分屏时弹出温和引导；文件树双栏折叠为单栏；Diff 强制 Unified 单列 |
| **标准坞 (Normal)** | `480px ~ 720px` | 左右分屏、上下分屏均完全支持（黄金区间） | 窗格平分宽度约 240px~360px，终端字号微调，Diff 保留主要行统计 |
| **宽坞 (Spacious)** | `> 720px` | 支持 3 窗格甚至 2x2 网格分屏 | 左右分屏体验极佳，文件树支持展开详情侧栏，Web 预览支持 PC 视口 |

### 3.2 左右分屏防挤压与退化引导

当用户在窄坞状态下（如 $W_d = 400px$）点击“向右分屏”时，若机械拆分，两个窗格各自宽度将只有 195px（扣除 10px Sash 与内边距），将导致绝大多数复杂视图崩溃。我们设计三道守卫：

1. **第一道防线：物理最小尺寸守卫（Min-width Clamp）**：
   - 设定单窗格的物理极限最小宽度为 `MIN_PANE_WIDTH = 180px`；
   - 当右坞总宽度 $< 360px$ 时：
     - 窗格头部的“向右分屏”按钮置为 `aria-disabled="true"`；
     - 鼠标悬停 Tooltip 呈现解释：“当前右坞空间过窄（<360px），向右分屏将严重压缩内容。建议使用【向下分屏】或拉宽右坞。”；
2. **第二道防线：智能方向推荐（Smart Direction Default）**：
   - 当用户使用通用分屏快捷键（如 `Ctrl + \`）而未指定方向时：
     - 若 $W_d < 500px$：自动采用**向下分屏（上下布局）**；
     - 若 $W_d \ge 500px$：自动采用**向右分屏（左右布局）**；
3. **第三道防线：自动溢出滚动条消除与边界裁切安全**：
   - 所有分屏窗格根节点配置 `overflow: hidden; min-width: 0; min-height: 0;`；
   - 彻底杜绝外层右坞因内部元素内容撑开而产生意外的横向全局滚动条。

### 3.3 `@container` 容器查询体系与规范修正

传统的 `@media` 媒体查询只能感知整个操作系统窗口宽度，完全无法感知右坞内部单个窗格的真实尺寸。必须采用现代标准的 **CSS 容器查询（Container Queries）**。

#### 1. 规范硬伤剖析与 `container-type: size` 修正

依据 **W3C CSS Containment Level 3 规范（§3.1）**：
> `container-type: inline-size` 仅在内联轴（Inline Axis，即宽度方向）建立尺寸查询上下文。在 `inline-size` 容器中评估任何块轴（Block Axis，即高度方向）的查询（如 `max-height`、`min-height`），**必须恒定求值为 unknown（在 CSS 条件语句中视为 false）**。

因此，若将窗格声明为 `container-type: inline-size`，文档中书写的 `@container dock-pane (max-height: 200px)` 将在 Chromium 与 WebKit 中 **100% 恒定失效**！

为彻底根治此问题，本方案确立**双重守卫方案**：

##### 修正方案 A（推荐，WebView 原生 2D 容器查询）：声明 `container-type: size`
```css
/* 窗格内容宿主容器（具有绝对确定的宽高，防止 size 包含引起高度塌陷） */
.dockPaneBody {
  flex: 1 1 0%;
  width: 100%;
  height: 100%;
  min-width: 0;
  min-height: 0;
  position: relative;
  overflow: hidden;
  
  /* 声明容器类型为 size：同时建立宽度和高度查询上下文 */
  container-type: size;
  container-name: dock-pane;
}

/* 此后可以同时合法查询宽度和高度 */
@container dock-pane (max-width: 340px) { ... }   /* 宽度查询：合法有效 */
@container dock-pane (max-height: 200px) { ... }  /* 高度查询：合法有效 */
```

> **高度塌陷免疫证明**：CSS 规范中 `container-type: size` 会强制应用 2D 尺寸包含（Size Containment），要求容器尺寸不得由子元素撑开。在我们的分屏架构中，`DockPaneHost` 是由二叉树展平算法 `flattenDockTree` 计算出的归一化百分比绝对定位（`left/top/width/height %`），且父链每级均声明了 `min-height: 0; flex: 1 1 0%;`，因此窗格几何尺寸完全由外层画布自顶向下刚性定死，**天然免疫高度坍塌为 0px 的风险**。

##### 修正方案 B（备选，针对 Vitest/jsdom 不支持 @container 的降级与测试断言桥梁）
由于前端单元测试环境（Vitest + jsdom）**至今完全不支持任何 CSS Container Queries**，为了让自适应逻辑在自动化测试中可验证，并为低版本 WebView 提供安全兜底，系统同时提供基于数据属性的响应桥梁：

```typescript
// 在 DockPaneHost / MicroPaneTabStrip 组件中
// 根据容器实际尺寸打上标准化数据属性
const height = containerRef.current?.clientHeight ?? Infinity;
const heightTier = height < 80 ? 'collapsed' : height < 200 ? 'compact' : 'normal';
containerRef.current?.setAttribute('data-height-tier', heightTier);

const width = containerRef.current?.clientWidth ?? Infinity;
const widthTier = width < 260 ? 'narrow' : width < 340 ? 'compact' : 'normal';
containerRef.current?.setAttribute('data-width-tier', widthTier);
```

CSS 侧提供双选择器支持：
```css
/* 方案 A: 现代 WebView 原生容器查询 */
@container dock-pane (max-height: 200px) {
  .terminalHeaderSummary {
    display: none !important;
  }
}

/* 方案 B: 数据属性双重守卫与 jsdom 自动化测试断言降级桥梁 */
[data-height-tier="compact"] .terminalHeaderSummary,
[data-height-tier="collapsed"] .terminalHeaderSummary {
  display: none !important;
}
```

#### 2. 窗格级标准容器断点规格

统一基于 `dock-pane` 容器名称编写断点规则：
```css

/* 窗格极窄宽度断点：< 260px */
```

## 四、一键分屏与高频场景预设（Presets）

### 4.1 核心工作流预设定义与几何配比

针对开发者日常最高频的四个协同工作场景，系统提供一键式预设排布（Presets）。无需用户从零反复手动拖拽分屏，点击即可瞬间获得最佳比例：

```text
1. 编程攻坚 (Code Review)     2. 全栈审查 (Fullstack)
┌─────────────────────────┐   ┌────────────┬────────────┐
│      📄 Diff 比对       │   │   📁 文件   │   🌐 预览   │
│         (60%)           │   │   (40%)    │   (60%)    │
├─────────────────────────┤   │            │            │
│      🖥️ 原生终端        │   │            │            │
│         (40%)           │   │            │            │
└─────────────────────────┘   └────────────┴────────────┘

3. 双终端监听 (Dual Shell)    4. 文档攻关 (Spec & Shell)
┌─────────────────────────┐   ┌─────────────────────────┐
│   🖥️ Dev Server (50%)   │   │   📝 规范/笔记 (50%)    │
├─────────────────────────┤   ├─────────────────────────┤
│   🖥️ Git / Shell (50%)  │   │   🖥️ 原生终端 (50%)     │
└─────────────────────────┘   └─────────────────────────┘
```

| 预设 ID | 预设名称 | 分割方向 | 窗格 1 (主) | 窗格 2 (副) | 推荐比例 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| `code-review` | **编程攻坚** | 垂直上下 (Vertical) | 变更比对 (`diff`) | 原生终端 (`terminal`) | **60% : 40%** | 一边查看 Agent 修改的代码 Diff，一边在终端运行测试或 Git 提交 |
| `fullstack` | **全栈审查** | 水平左右 (Horizontal) | 文件资源 (`files`) | 网页预览 (`preview`) | **40% : 60%** | 适用于前端/全栈开发，左侧定位工程结构，右侧即时查看渲染呈现 |
| `dual-shell` | **双终端协同** | 垂直上下 (Vertical) | 运行服务 (`terminal:dev`) | 交互命令行 (`terminal:cli`) | **50% : 50%** | 上窗格跑本地 Dev Server / Vite，下窗格运行即时脚本或数据库 CLI |
| `spec-shell` | **文档攻关** | 垂直上下 (Vertical) | 方案/笔记 (`note`) | 验证终端 (`terminal`) | **50% : 50%** | 对照需求设计文档或战役纪律进行命令验证 |

> **宽坞保护断点**：对于水平左右布局的预设（如 `fullstack`），当右坞当前物理宽度 $< 500px$ 时，系统自动无缝将方向修正为**垂直上下堆叠**，避免窗格过窄产生视觉崩坏。

### 4.2 预设触发展示与交互入口

预设排布在 UI 上提供两个极为便捷的交互触点：
1. **全局坞顶栏快捷下拉菜单（Layout Presets Menu）**：
   - 位于右坞最顶部操作栏左侧，呈现 `[📐 布局预设 ▾]` 微型按钮；
   - 点击展开轻量浮层菜单，带有图文并茂的 4 个场景排布胶囊，支持一键切换；
2. **微型启动页磁贴（Empty Slate Tiles）**：
   - 当右坞刚刚打开或用户关闭了所有工具窗格时，空态居中卡片展示 4 块磁贴，配有快捷键标记，实现 0 次鼠标多余寻路即可进入心仪布局。

### 4.3 预设切换时的 Tab 无损迁移算法

当用户在不同预设之间切换（或从单窗格切换至分屏预设）时，**绝不允许发生“已有终端 PTY 被杀掉”或“编辑中的笔记草稿丢失”的事故**！
- **迁移算法核心原则**：
  1. **实例存活不变（Instance Preservation）**：所有已打开的工具实例（尤其是具备后台运行时的 `terminal` 与 `preview`）在底层的生命周期完全保持，不触发 unmount；
  2. **智能归槽（Slot Matching）**：
     - 若预设窗格 1 声明需要 `diff`，且当前已存在打开的 `diff` 实例，则该实例直接绑定到窗格 1 的活跃 Tab；
     - 若当前已有多个终端实例（如 `term-1`、`term-2`），在应用 `dual-shell` 时自动将它们分别分配到上下两个窗格，而不是凭空新建；
  3. **非预设 Tab 归拢（Orphan Tab Consolidation）**：
     - 若用户此前打开了 5 个不同工具 Tab，而新预设只有 2 个窗格，其余未直接命中的 Tab 统一保留在主窗格的后台标签列表中，用户依然可以随时在 Micro TabStrip 中点击切出。

## 五、全键盘流转与无障碍（A11y）体系

### 5.1 空间感知键盘焦点导航

右坞分屏后，支持全键盘在不同窗格之间快速流转，极大提升高阶开发者的沉浸效率：

```text
                     [Alt + ArrowUp]
                            ▲
                            │
[Alt + ArrowLeft] ◄── [当前激活窗格] ──► [Alt + ArrowRight]
                            │
                            ▼
                    [Alt + ArrowDown]
```

1. **窗格间空间导航 (`Alt + 方向键`)**：
   - 系统依据各分屏窗格在二叉树与二维几何空间中的外接矩形（Rect：`x, y, width, height`）；
   - 按下 `Alt + ArrowRight` 时，计算所有窗格中心点向量，自动聚焦到正右方最接近的窗格；
   - 聚焦后，该窗格的 Micro TabStrip 和内容层获得焦点。
2. **跨区域穿梭 (`Ctrl + \`` 或 `Alt + D`)**：
   - 在**左侧会话主编辑区（Chat Composer / Message Stream）**与**右坞当前激活窗格**之间往返循环切换；
   - 彻底摆脱每次都要拿起鼠标寻找输入焦点的琐碎操作。

### 5.2 快捷分屏与窗格管理键位契约

键盘快捷键映射表设计严谨，避免与操作系统全局快捷键（如 Windows/macOS 系统键）及 VS Code/Chrome 核心键位冲突：

| 快捷键 (Windows/Linux) | 快捷键 (macOS) | 触发上下文 | 动作行为 |
| :--- | :--- | :--- | :--- |
| `Ctrl + Shift + \` | `Cmd + Shift + \` | 右坞内任意窗格聚焦时 | **向右水平分屏**当前窗格 |
| `Ctrl + Shift + -` | `Cmd + Shift + -` | 右坞内任意窗格聚焦时 | **向下垂直分屏**当前窗格 |
| `Alt + W` / `Ctrl + F4` | `Option + W` | 右坞窗格内聚焦时 | **关闭当前 Tab**（窗格清空时自动收合窗格） |
| `Alt + M` | `Option + M` | 右坞窗格内聚焦时 | **最大化/还原当前窗格**（Solo Focus 切换） |
| `Ctrl + PageUp` / `PageDown` | `Cmd + Shift + [` / `]` | 窗格 TabStrip 聚焦 | 在当前窗格内部**循环切换上一个/下一个 Tab** |
| `Alt + 1 ~ 4` | `Option + 1 ~ 4` | 全局右坞上下文 | **一键应用第 1~4 号工作流预设** |

### 5.3 焦点指示环设计（严守 §13 规范）

在右侧紧凑空间中，窗格获得焦点时必须给用户清晰的视觉反馈，但**绝对禁止使用粗黑边、高反差深色边框或生硬的过渡动画**（严守 `AGENTS.md` §13 铁律）。

- **规范要求**：
  - “任何情况下焦点/激活态不得使用硬实线”；
  - “相对基线，灰色加深混入文本色不超过约 **10%**；常规元素优先约 **3%–6%** 混入以保持柔软”；
- **具体实施 CSS 方案**：
  ```css
  /* 窗格基础发丝边框 */
  .dockPaneContainer {
    border: 1px solid var(--border-subtle);
    border-radius: var(--radius-md, 8px);
    transition: border-color var(--duration-fast) var(--ease-standard);
  }

  /* 窗格聚焦态：微混入 5% 文本主色，保持浅灰柔和 */
  .dockPaneContainer:focus-within,
  .dockPaneContainer[data-focused="true"] {
    border-color: color-mix(
      in srgb,
      var(--border-subtle) 95%,
      var(--text-primary) 5%
    );
    /* 极致克制的微弱柔和外发光，拒绝厚重重影 */
    box-shadow: 0 0 0 1px color-mix(
      in srgb,
      var(--border-subtle) 95%,
      var(--text-primary) 5%
    );
  }
  ```

### 5.4 ARIA 无障碍树与焦点兜底恢复

1. **ARIA 树层级定义**：
   - 右坞根节点：`role="region" aria-label="右侧分屏工具坞"`；
   - 每个窗格容器：`role="region" aria-label="分屏窗格: [当前活动工具名]"`，附带 `aria-current="true"` 标记激活窗格；
   - 窗格内部微型 Tab 栏：`role="tablist"`，Tab 项标明 `role="tab"` 与 `aria-selected`；
2. **焦点兜底恢复机制（Focus Restoration）**：
   - 当用户关闭某个窗格或窗格内最后一个 Tab 时：
     - 若焦点仍在被销毁的元素上，立即触发焦点重定向守卫；
     - 自动将焦点优雅转移至**最近的兄弟窗格（优先左侧/上方窗格）**的活动 Tab；
     - 若整个右坞所有窗格均已关闭，平滑将键盘焦点交还至左侧对话区的主输入框（Chat Composer），杜绝“焦点坠入虚空”的无障碍缺陷。

- **落地执行**：
  - 窗格头部右上角所有操作按钮（`向右分屏`、`向下分屏`、`最大化`、`关闭`、`添加 Tab`）一律包裹 `<Tooltip content="..." side="bottom">`；
  - 标签项超长省略时，由 Tooltip 承载完整标题展示；
  - 统一享受项目的圆角胶囊、柔和阴影与主题一致性，杜绝浏览器默认泛黄气泡。

### 6.2 焦点边框与无重阴影审计（§13）
- **红线规定**：默认无重阴影，禁止粗黑边（如 `0 0 0 1px #000`），焦点混合度上限 10%；
- **落地执行**：
  - 微型 TabStrip 内部与分屏窗格边界杜绝任何多层 `box-shadow` 嵌套；
  - 窗格聚焦态采用 `color-mix(in srgb, var(--border-subtle) 95%, var(--text-primary) 5%)`；
  - 分屏 Sash 悬停与激活态仅呈现微弱色阶提升（`var(--border-focus)`），避免视觉干扰。

### 6.3 现代色彩空间审计（§14）
- **红线规定**：优先使用现代 HSL / HSLA / OKLCH，斜杠透明度语法，杜绝散落旧式 `rgba(...)`；
- **落地执行**：
  - 所有微型 TabStrip、Sash、按钮悬停、激活背景统一采用 CSS custom properties（如 `hsl(var(--hue) var(--sat) var(--lit) / 0.08)`）；
  - 激活高亮色采用 `var(--tab-active-surface, var(--surface-raised))`，保持全域色彩同构。

### 6.4 反过度设计红线对照
对照 `ANTI_OVERENGINEERING_GUARDRAILS.md`：
- **拒绝**引入重量级第三方 Docking 框架（如 GoldenLayout、FlexLayout）；
- **拒绝**为每个窗格编写冗长复杂的事件订阅总线；
- **坚持**采用现存已验证的二叉树数学几何模型（`flattenTree`），以极简纯组件形式下沉至 `leafDockDrawer` 内部；
- **坚持**优先使用标准 CSS 原生能力（`container-type: size`、`@container`）配合属性降级桥梁解决自适应，不使用繁重的 JavaScript 频繁监听 resize 触发全量重渲染。

### 7.4 Phase 4 实施前置条件与容器查询降级规范

依据工程审计 E 裁决，**本文档（06）中描述的所有 `@container` 容器查询功能，统一在 Phase 4 实施**。在 Phase 4 正式编码前，必须严格完成以下两项前置核验：

1. **跨平台 WebView 环境兼容性验证**：

   - 在进入 Phase 4 之前，必须在 `DockPaneHost` 中准备好基于实际像素计算的 `data-height-tier`（`collapsed` | `compact` | `normal`）与 `data-width-tier`（`narrow` | `compact` | `normal`）注入管道；
   - 此管道不仅作为低版本 WebView 的终极安全兜底，更是 **Vitest + jsdom 自动化单测断言容器自适应行为的唯一可行手段**。所有关键组件的样式规则必须同时书写 `@container` 选择器与 `[data-height-tier]` 属性选择器，确保在无真实浏览器渲染引擎的 CI 环境下亦能履行严密的立体验证。

## 八、总结与结论

本方案针对右坞通常在 **320px ~ 900px** 的紧凑物理环境，提供了一套高度契合工程实际的分屏交互与自适应视觉系统：
1. **微型交互条（28px）**：通过精致的 TabStrip 与窗格右上角动作集群（向右/向下分屏、最大化、关闭），在不挤占内容空间的前提下提供直觉操作；
2. **容器查询（@container size）与属性降级**：穿透全屏媒体查询的局限，修正了 `inline-size` 无法查询 `max-height` 的 W3C 规范硬伤，辅以 `data-height-tier` 数据属性构建跨 WebView 兼容与 jsdom 自动化测试的坚固桥梁；
3. **高频预设（Presets）**：为“编程攻坚”、“全栈审查”等高频场景提供 0 门槛一键布局与 Tab 无损迁移；
4. **严格遵循设计纪律**：全键盘导航、微反差焦点指示环（§13）、自定义 Tooltip（§12）与现代色彩语法（§14），实现架构优雅与用户体验的极致统一。
