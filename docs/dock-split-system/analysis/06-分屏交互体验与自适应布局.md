## 一、背景与空间挑战分析

### 1.1 右坞物理环境约束

在 Conex/Crish 桌面应用中，右侧工具坞（`leafDockDrawer`）是挂载在每个对话叶（`TreeLeafPanel`）内部右侧的功能区：
- **宽度范围**：受限于用户的显示器分辨率以及主对话流与右坞的分隔比例（`widthRatio`，默认 0.5），右坞在常规 1080p~4K 屏幕下的实际物理宽度通常分布在 **320px ~ 900px** 之间；
- **全屏 vs 右坞物理差异**：
  - 顶层的二叉树分屏系统运行在整个窗口宽度（1280px ~ 2560px）上，水平空间充裕；
  - 沉浸至右坞内部后，若进行多窗格切分，每个分屏子窗格（Dock Leaf Pane）面对的横向物理宽度可能被压缩至 **160px ~ 450px**，纵向高度在 **400px ~ 1000px** 之间。

### 1.2 现有单窗格右坞瓶颈与 V1 过度设计反思

#### 1. 现行单窗格模式的交互瓶颈
目前 `TreeLeafPanel.tsx` 中的右坞为粗暴的单窗格结构：
```tsx
// 现行实现：无论打开多少个面板，右坞同一时刻只能 display 一个面板
{dock.openPanelIds.length > 0
  ? dock.openPanelIds.map((pid) => (
      <div key={pid} style={{ display: pid === toolPanelId ? 'flex' : 'none' }}>
        {renderToolOutlet(pid)}
      </div>
    ))
  : renderToolOutlet(toolPanelId)}
```
该模式导致用户在“查看 Diff”与“运行测试终端”之间来回盲切，无法空间并行，严重割裂了深度编码心流。

#### 2. V1 方案的过度设计病灶
在先前的 V1 方案草案中，为了解决分屏问题，设计了复杂的两级头部架构与一键预设系统：
- **双层头部堆叠**：单窗格用经典 `LeafToolTabStrip`，多窗格则在顶部额外塞入一个 28px 的“全局坞顶条（Dock Header）”，每个子窗格再塞入一个 28px 的“微型标签栏（MicroPaneTabStrip）”。这直接掠夺了 56px 的纵向宝贵高度，导致子窗格内容区严重逼仄；
- **组件割裂与双重维护**：维护 `LeafToolTabStrip` 与 `MicroPaneTabStrip` 两套几乎相同但属性各异的头部组件，伴随着高额的条件分叉与状态同步成本；
- **华而不实的 Presets 预设系统**：设计了所谓的“一键三窗格场景预设（Presets）”与极其晦涩的“Tab 无损迁移槽位匹配算法”。用户在实际桌面开发中更倾向于最直接、最符合直觉的原生操作：点击按钮分屏或直接拖拽标签。

### 1.3 V2 核心设计原则：单一抽象与极简自适应

依据用户对架构重构的最高指导意志（**“不允许打补丁，不允许硬编码，有合理的抽象，代码尽量简洁，具有优秀的可维护性。需要删除的代码就删除，需要系统性的重构”**），V2 交互体验确立四大核心准则：

1. **单一窗格头部抽象（Single Header Architecture）**：
   彻底废除“全局顶条 + 子窗格微条”的双层堆叠，无论右坞处于单窗格还是多窗格状态，每个 `DockLeaf` 窗格顶部统一且仅渲染同一个重构后的 `LeafToolTabStrip`，把纵向空间 100% 留给工具内容区；
2. **极简原生动作集群（Zero-Fat Action Cluster）**：
   砍掉华而不实的预设模板菜单与复杂的迁移算法。每个窗格头部右侧提供 4 个清爽的标准动作图标（向右分屏、向下分屏、最大化/还原、关闭窗格/收起），辅以直觉的 22% 边缘拖拽热区分屏；
3. **基于标准 CSS 的容器自适应（W3C Size Containment）**：
   依托 `container-type: size; container-name: dock-pane;` 规范建立自适应体系，辅以基于像素计算的 `data-*-tier` 属性，实现纯 CSS 驱动的密度降级与 Vitest/jsdom 自动化测试立体覆盖；
4. **严格遵循设计纪律**：
   严禁使用原生 `title`（§12：强制自定义 `<Tooltip>`），严禁粗黑边与深阴影（§13：激活态仅 5%~6% 极柔和混色），全面使用现代 HSL 斜杠透明度语法（§14）。

## 二、单一窗格头部（LeafToolTabStrip）与窗格动作交互设计

### 2.1 彻底废除“两级头部”，确立单一 `LeafToolTabStrip` 架构

在 V2 架构中，右坞不再维护“全局坞顶条”与“微型窗格顶条”两套组件，而是实现彻底的**单一组件统一化（Single TabStrip Paradigm）**：

```text
┌────────────────────────────────────────────────────────────────────────┐
│                              右侧工具坞抽屉                             │
├───────────────────────────────────┬────────────────────────────────────┤
│ [📄 Diff.tsx ✕] [+] [◫] [⬒] [⛶] [✕] │ [🖥️ Terminal ✕] [+] [◫] [⬒] [⛶] [✕] │ ← 统一的 LeafToolTabStrip (28px)
├───────────────────────────────────┼────────────────────────────────────┤
│                                   │                                    │
│        窗格 A：Diff 比对内容        │         窗格 B：ConPTY 原生终端      │
│                                   │                                    │
└───────────────────────────────────┴────────────────────────────────────┘
```

#### 统一设计优势
1. **纵向空间零浪费**：顶部不再强行堆叠全局控制条，所有分屏窗格自顶向下完全平铺，工具内容视口高度最大化；
2. **单窗格与多窗格无缝等价**：
   - 当右坞仅有 **1 个窗格**时，该窗格的 `LeafToolTabStrip` 即代表全局标签与全局动作（关闭按钮表现为“收起右坞”）；
   - 当右坞切分为 **N 个分屏**时，每个窗格的 `LeafToolTabStrip` 独立管理所属窗格的 `tabs` 与当前窗格动作（关闭按钮表现为“关闭当前分屏并释放 PTY”）；
3. **代码架构高内聚**：单一组件统一消费 `LeafToolTabStripProps`，消除了 V1 方案中两套组件来回切换与 CSS 样式漂移的历史包袱。

### 2.2 窗格头部视觉与几何规格

重构后的 `LeafToolTabStrip` 统一定位为微型高密度标签栏，严格对齐几何规范：

| 属性 | 几何数值 / CSS Token | 规范与设计说明 |
| :--- | :--- | :--- |
| **头部容器高度** | `28px` (`--tool-tab-strip-height`) | 紧凑无下边框设计，底部分界由窗格细分边框提供 |
| **Tab 默认高度** | `24px` | 留出上下各 2px 呼吸间距，视觉轻盈 |
| **Tab 最大宽度** | `130px` (`--tool-tab-width-max`) | 内容自适应，超出文本以 `text-overflow: ellipsis` 截断 |
| **Tab 最小宽度** | `32px` | 极限挤压时保留图标展示，文本平滑隐退 |
| **Tab 间距 (Gap)** | `3px` | 避免标签紧挨，维持清爽层次 |
| **Tab 圆角** | `var(--radius-md, 6px)` | 柔和圆角，匹配系统一致的控件风格 |
| **字体大小与字重** | `11.5px / 400`（激活态 `500`） | 紧凑清晰，消费 `var(--font-size-xs)` |
| **图标尺寸** | `12px × 12px` | 匹配微型标签比例 |
| **关闭按钮** | `14px × 14px` | 默认透明度 0，鼠标悬停或当前 Tab 激活时柔和显现 |

#### 标签入场与离场动效
- **入场动效**：采用现代 CSS `@starting-style` 机制，首帧 `max-width: 0; opacity: 0;` 平滑向右撑开，过渡时间 150ms（`var(--duration-fast)`）；
- **离场动效**：`[data-leaving="true"]` 先文字快速淡出（80ms），壳体紧随收缩（150ms），配合负 `margin-right` 消除兄弟标签跳变。

### 2.3 窗格右上角标准动作集群（Pane Action Cluster）

每个分屏窗格头部右侧常驻微型动作按钮组（高度 22px，宽度 22px，圆角 4px）。**全部按钮必须包裹项目自定义 `<Tooltip>` 组件，严禁使用原生 HTML `title` 属性（`AGENTS.md` §12 铁律）**：

```text
┌────────────────────────────────────────────────────────┐
│ [🖥️ Terminal 1 ✕] [+]      [◫ 右分] [⬒ 下分] [⛶ 最大] [✕ 关闭]│
└────────────────────────────────────────────────────────┘
```

#### 4 个标准图标按钮交互规范

1. **向右分屏按钮（Split Right）**：
   - **图标**：`split-horizontal`（或左右矩形均分图标，13px）；
   - **可用性守卫**：
     - 当当前窗格实际渲染宽度 `< 240px` 时，按钮自动置为禁用态（`disabled` 且 `opacity: 0.4`）；
     - 此时 Tooltip 呈现解释性文案：`<Tooltip content="窗格宽度过窄（<240px），无法继续向右分屏。建议拉宽右坞或向下分屏" side="bottom">`；
   - **正常触发行为**：
     - Tooltip 显示：`<Tooltip content="向右分屏 (Ctrl+Shift+\)" side="bottom">`；
     - 点击后在当前窗格右侧创建兄弟窗格，当前窗格与新窗格各占 50% 宽度；新窗格呈现 Micro Launcher 或挂载新工具。
2. **向下分屏按钮（Split Down）**：
   - **图标**：`split-vertical`（或上下矩形均分图标，13px）；
   - **可用性守卫**：
     - 当当前窗格实际渲染高度 `< 160px` 时，按钮自动置为禁用态（`disabled` 且 `opacity: 0.4`）；
     - 此时 Tooltip 呈现解释性文案：`<Tooltip content="窗格高度过矮（<160px），无法继续向下分屏。建议拉高窗口或向右分屏" side="bottom">`；
   - **正常触发行为**：
     - Tooltip 显示：`<Tooltip content="向下分屏 (Ctrl+Shift+-)" side="bottom">`；
     - 点击后在当前窗格下方创建兄弟窗格，各占 50% 高度。
3. **最大化 / 还原按钮（Maximize / Restore）**：
   - **图标**：最大化态 `maximize-2` / 还原态 `minimize-2`（13px）；
   - **自适应上下文行为**：
     - **当右坞处于多窗格状态时（`isOnlyPane = false`）**：
       - 点击触发当前窗格的 **Solo Focus（子窗格独占）**，使该窗格 100% 铺满右坞视口，其余兄弟窗格临时隐蔽；再次点击恢复多窗格拓扑；
       - Tooltip 动态呈现：`isSolo ? "还原分屏布局 (Alt+M)" : "最大化当前窗格 (Alt+M)"`；
     - **当右坞处于单窗格状态时（`isOnlyPane = true`）**：
       - 点击触发**右坞整体抽屉的最大化/还原**（将右坞 `widthRatio` 扩大至全屏或恢复默认）；
       - Tooltip 动态呈现：`isDrawerMaximized ? "还原右坞宽度 (Alt+M)" : "最大化右坞 (Alt+M)"`。
4. **关闭窗格 / 收起按钮（Close / Collapse）**：
   - **图标**：标准关闭图标 `x`（12px）；
   - **自适应上下文行为**：
     - **当右坞存在多个窗格时（`isOnlyPane = false`）**：
       - 表现为**关闭当前分屏窗格**；
       - 一键关闭该窗格及其所有 Tab，彻底回收窗格内部承载的 ConPTY 原生终端进程与运行时资源，释放的矩形空间由相邻兄弟窗格平滑填充；
       - Tooltip 显示：`<Tooltip content="关闭此分屏窗格 (Alt+W)" side="bottom">`；
     - **当右坞仅剩最后 1 个窗格时（`isOnlyPane = true`）**：
       - 表现为**收起右坞抽屉**（设置 `dock.collapsed = true`），保持窗格内部 Tab 存活；
       - Tooltip 显示：`<Tooltip content="收起右坞 (Alt+W)" side="bottom">`。

### 2.4 单窗格最大化（Solo Focus）与分屏还原机制

在多窗格协同中，开发者常需要临时全屏审查某个视图（例如终端执行大型构建、精细化审查复杂 Diff）：
- **状态维护**：右坞状态树维护纯逻辑字段 `soloPaneId: string | null`；
- **非破坏性 CSS 绝对定位**：
  - 底层二叉树几何拓扑保持绝对不变，不执行节点解构与销毁操作；
  - 拥有 `data-solo-active="true"` 的窗格通过 CSS `position: absolute; inset: 0; z-index: 10;` 覆盖铺满右坞工作区；
  - 其他兄弟窗格通过 `display: none` 隐蔽（**严格保持 React 实例与底层 ConPTY 终端会话存活，不触发 unmount**）；
  - 隐藏所有 Sash 分割条，零重排计算开销；
- **快捷键联动**：支持按下 `Esc` 或快捷键 `Alt + M` 瞬间无缝还原回原有多窗格分屏拓扑。

### 2.5 空态窗格与微型启动器（Micro Launcher）

当用户通过快捷按钮或快捷键切分出一个全新的空白窗格时，该窗格内部自动呈现极简的 **Micro Launcher（微型启动磁贴）**：

```text
┌────────────────────────────────────────────────────────┐
│ [新建窗格] [+]                      [◫] [⬒] [⛶] [✕]    │
├────────────────────────────────────────────────────────┤
│                                                        │
│                    点击快速加载工具                     │
│                                                        │
│   [🖥️ 原生终端]    [📄 代码比对]    [📁 文件资源]        │
│   [🌐 网页预览]    [📝 备忘笔记]                        │
│                                                        │
└────────────────────────────────────────────────────────┘
```

- **交互体验**：
  - 采用极轻量胶囊按钮（高度 30px，圆角 6px，背景 `hsl(var(--surface-color) / 0.6)`）；
  - 点击对应工具，立即在当前窗格追加对应 `ToolTab`，并切换至工具 Outlet；
  - 杜绝繁琐引导，0 延迟进入工作态。

### 2.6 原生拖拽分屏与中心合并交互

除了右上角动作按钮，右坞完全支持原生的直觉拖拽交互：
1. **22% 边缘分屏热区（Edge Splitting）**：
   - 拖拽任意 `ToolTab` 至目标窗格的边缘区域（上、下、左、右各占窗格几何尺寸的 **22%**）；
   - 目标窗格边缘浮现半透明淡蓝色分屏投影预览（采用 `hsl(var(--brand-hue) 80% 60% / 0.15)`，禁止粗黑线）；
   - 释放指针后，目标窗格自动以 50% 比例执行二叉切分，将拖拽的 `ToolTab` 迁入新窗格；
2. **中心区域合并（Center Merging）**：
   - 拖拽 `ToolTab` 至目标窗格中心区域（扣除 22% 边缘热区后的中央 56% 区域）；
   - 目标窗格整体呈现微弱柔和高亮底色；
   - 释放指针后，将该 `ToolTab` 追加合并至目标窗格的 `tabs` 列表中，并置为 `activeTabId`。

## 三、紧凑空间自适应排布与容器查询体系

### 3.1 宽度梯度分级与物理断点策略

右坞宽度（Dock Width, $W_d$）以及各窗格宽度（Pane Width, $W_p$）具有极强的弹性。本方案确立四个标准物理断点档位：

```text
       240px              360px              600px
─────────┼──────────────────┼──────────────────┼──────────────────►
    极窄窗格 (Narrow)    紧凑窗格 (Compact)   标准窗格 (Normal)   宽松高密度 (Spacious)
    严禁向右分屏         强推向下分屏         黄金分屏体验        多栏并排/自由网格
    工具单栏极简         工具双栏转单栏       完整工具体验        全量信息呈现
```

| 档位名称 | 窗格物理宽度 ($W_p$) | 分屏交互决策 | 核心工具自适应手段 |
| :--- | :--- | :--- | :--- |
| **极窄窗格 (Narrow)** | `< 240px` | **向右分屏按钮强制 Disabled**；仅允许向下分屏 | Tab 仅展示图标隐藏文字；Diff 强制内联单列并压缩行号；终端微缩字号 |
| **紧凑窗格 (Compact)** | `240px ~ 360px` | 允许向右分屏，但 Tooltip 提示“优先向下分屏” | 文件树双栏折叠为单栏浏览；终端隐藏次要辅助操作栏；Diff 隐藏长目录路径 |
| **标准窗格 (Normal)** | `360px ~ 600px` | 水平左右、垂直上下分屏黄金体验区间 | 完整工具操作栏展现；Diff 保留增删统计；文件树支持轻量详情 |
| **宽松窗格 (Spacious)** | `> 600px` | 支持高密度多栏网格切分 | Web 预览支持桌面视口渲染；Diff 支持 Side-by-side 双列对比 |

### 3.2 窗格防挤压与安全守卫

在右坞紧凑空间中，粗暴拆分可能导致内容视口完全崩溃。系统通过三道安全守卫进行刚性防御：

1. **第一道防线：物理最小尺寸硬钳制（Min Size Clamp）**：
   - 单窗格绝对最小宽度 `MIN_PANE_WIDTH = 180px`，最小高度 `MIN_PANE_HEIGHT = 120px`；
   - Sash 拖拽调比时，实时钳制计算结果，防止任何窗格被压缩至不可读状态；
2. **第二道防线：智能分屏方向默认决议（Smart Split Direction）**：
   - 当用户使用全局快捷键（如 `Ctrl + \`）而未显式指定方向时：
     - 若当前窗格 $W_p < 400px$：自动采用**向下垂直分屏**；
     - 若当前窗格 $W_p \ge 400px$：自动采用**向右水平分屏**；
3. **第三道防线：全局横向溢出硬隔离**：
   - 窗格根容器配置 `overflow: hidden; min-width: 0; min-height: 0;`；
   - 坚决杜绝因子组件宽度撑开而导致右坞出现全局水平滚动条。

### 3.3 W3C `@container size` 与 `data-*-tier` 双轨机制

传统的媒体查询 `@media` 仅能侦测浏览器顶层视口宽度，对右坞内部子窗格的微观尺寸毫无感知。必须采用现代标准的 **CSS 容器查询（Container Queries）**。

#### 1. W3C 规范硬伤与 `container-type: size` 修正

依据 **W3C CSS Containment Level 3 规范（§3.1）**：
> `container-type: inline-size` 仅在内联轴（Inline Axis，即宽度方向）建立尺寸查询上下文。若在 `inline-size` 容器中评估任何块轴（Block Axis，即高度方向）的查询（如 `max-height`、`min-height`），**必须恒定求值为 unknown（在 CSS 条件规则中恒为 false）**。

因此，若将窗格声明为常见的 `container-type: inline-size`，所有垂直上下分屏场景下的高度查询（如 `@container dock-pane (max-height: 200px)`）在 Chromium 与 WebKit 中 **100% 恒定失效**！

为彻底根除此规范硬伤，本方案落地**双轨守卫机制**：

##### 轨 A（现代 WebView 原生 2D 容器查询）：声明 `container-type: size`
```css
/* 窗格内容宿主容器（具有绝对确定的宽高，防止 size 包含引起高度塌陷） */
.dockPaneBody {
  flex: 1 1 0%;
  width: 100%;
  height: 100%;
  min-width: 0;
  min-height: 0;
  position: relative;
  overflow: hidden;
  
  /* 严格声明为 size：同时建立宽度和高度的双向查询上下文 */
  container-type: size;
  container-name: dock-pane;
}

/* 此时高度与宽度查询均合法且高效执行 */
@container dock-pane (max-width: 340px) { ... }
@container dock-pane (max-height: 200px) { ... }
```

> **高度塌陷免疫证明**：CSS 规范中 `container-type: size` 会强制应用 2D 尺寸包含，要求容器尺寸不得依赖子内容撑开。在我们的分屏架构中，`DockSplitPane` 是由几何展平算法 `flattenDockTree` 计算出的归一化绝对定位百分比（`left/top/width/height %`），且父容器各层均显式声明了 `min-height: 0; flex: 1 1 0%;`，因此窗格几何边界完全由外层画布自顶向下刚性锁定，**天然具备 0px 高度塌陷免疫力**。

##### 轨 B（针对 Vitest/jsdom 单元测试与低版本环境的数据属性降级桥梁）
由于前端单元测试环境（Vitest + jsdom）**至今完全不支持任何 CSS Container Queries**，为了保证自适应逻辑在自动化门禁中能够被 100% 验证，并为低版本 WebView 提供兜底，窗格宿主通过 `ResizeObserver` 动态计算并打上标准数据属性：

```typescript
// 在 DockSplitPane 挂载 ResizeObserver
const updateTiers = (width: number, height: number) => {
  const widthTier = width < 240 ? 'narrow' : width < 360 ? 'compact' : 'normal';
  const heightTier = height < 160 ? 'collapsed' : height < 240 ? 'compact' : 'normal';
  
  hostElement.setAttribute('data-width-tier', widthTier);
  hostElement.setAttribute('data-height-tier', heightTier);
};
```

CSS 侧统一采用双选择器并排书写：
```css
/* 轨 A: 现代 WebView 原生高效容器查询 */
@container dock-pane (max-height: 200px) {
  .terminalHeaderSummary {
    display: none !important;
  }
}

/* 轨 B: 数据属性双重守卫与 Vitest / jsdom 自动化测试断言桥梁 */
[data-height-tier="compact"] .terminalHeaderSummary,
[data-height-tier="collapsed"] .terminalHeaderSummary {
  display: none !important;
}
```

## 四、全键盘流转与无障碍（A11y）体系

### 4.1 空间感知键盘焦点导航（`Alt + 方向键`）

在多窗格环境下，纯键盘流转是沉浸式编码的关键基础设施：

```text
                     [Alt + ArrowUp]
                            ▲
                            │
[Alt + ArrowLeft] ◄── [当前激活窗格] ──► [Alt + ArrowRight]
                            │
                            ▼
                    [Alt + ArrowDown]
```

- **空间向量寻路算法**：
  1. 系统读取当前所有活动分屏窗格的几何包围盒（Rect：`x, y, width, height`）；
  2. 当按下 `Alt + ArrowRight` 时，以当前焦点窗格的中心点为原点，向正右方发出探测射线；
  3. 计算所有位于右侧的候选窗格中心点欧氏距离与夹角权重，自动转移焦点至最邻近的最佳窗格；
  4. 目标窗格获得焦点，其 `LeafToolTabStrip` 呈现柔和激活态。
- **跨主区往返穿梭（`Alt + D` 或 `Ctrl + \``）**：
  - 在**左侧会话主工作区（Chat Composer）**与**右坞当前激活分屏窗格**之间往返切换，手无需离开键盘。

### 4.2 快捷分屏与窗格管理键位契约

快捷键映射契约严守项目全局标准，杜绝系统键位冲突：

| 快捷键 (Windows/Linux) | 快捷键 (macOS) | 触发上下文 | 动作行为说明 |
| :--- | :--- | :--- | :--- |
| `Ctrl + Shift + \` | `Cmd + Shift + \` | 窗格聚焦时 | **向右水平分屏**当前窗格 |
| `Ctrl + Shift + -` | `Cmd + Shift + -` | 窗格聚焦时 | **向下垂直分屏**当前窗格 |
| `Alt + W` / `Ctrl + F4` | `Option + W` | 窗格聚焦时 | **关闭当前活动 Tab**（窗格无 Tab 时自动收合窗格并回收 PTY） |
| `Alt + M` | `Option + M` | 窗格聚焦时 | **最大化/还原当前窗格**（Solo Focus 状态切换） |
| `Ctrl + PageUp` / `PageDown` | `Cmd + Shift + [` / `]` | 标签栏聚焦时 | 在当前窗格内部**循环切换上一个 / 下一个 Tab** |

> **精简说明**：彻底移除 V1 方案中绑定的 `Alt + 1~4` 一键布局预设快捷键，消除不必要的按键占用。

### 4.3 焦点指示环设计（严守 §13 规范）

依据 `AGENTS.md` §13 铁律（**“默认不要重阴影，激活态禁止粗黑边，边框加深混入文本色不超过约 10%，常规优先 3%~6% 混入以保持柔软”**），窗格焦点边框严格按以下规范落地：

```css
/* 窗格基础发丝边框 */
.dockPaneContainer {
  border: 1px solid var(--border-subtle);
  border-radius: var(--radius-md, 8px);
  position: relative;
  transition: border-color var(--duration-fast) var(--ease-standard);
}

/* 窗格聚焦态：微混入 5% 文本主色，保持浅灰柔和，严禁粗黑环 */
.dockPaneContainer:focus-within,
.dockPaneContainer[data-focused="true"] {
  border-color: color-mix(
    in srgb,
    var(--border-subtle) 95%,
    var(--text-primary) 5%
  );
  /* 极致克制的微弱柔和外发光，杜绝厚重重影 */
  box-shadow: 0 0 0 1px color-mix(
    in srgb,
    var(--border-subtle) 95%,
    var(--text-primary) 5%
  );
}
```

### 4.4 ARIA 无障碍树与焦点兜底恢复

1. **ARIA 树层级标注**：
   - 右坞根节点：`role="region" aria-label="右侧分屏工具坞"`；
   - 每个窗格容器：`role="region" aria-label="分屏窗格: [活动工具名]"`，附带 `aria-current="true"` 标记激活窗格；
   - 窗格头部标签栏：`role="tablist"`，Tab 项标明 `role="tab"` 与 `aria-selected`；
2. **焦点生命周期兜底恢复**：
   - 当用户关闭某个分屏窗格或窗格内最后一个 Tab 时：
     - 若当前焦点仍停留在将被销毁的 DOM 节点上，立即触发焦点重定向守卫；
     - 自动将焦点优雅转移至**最近的兄弟窗格（优先左侧/上方窗格）**的活动 Tab；
     - 若整个右坞的所有分屏窗格均已关闭，平滑将键盘焦点交还至左侧对话区的主输入框（Chat Composer），杜绝“焦点坠入虚空”的无障碍缺陷。

## 五、项目设计语言落地与红线审计

### 5.1 Tooltip 规范审计（§12）
- **红线要求**：始终使用项目自定义 `<Tooltip>` 组件，**严禁使用原生 HTML `title` 作为主悬停提示**；
- **落地验证**：
  - 窗格头部右上角所有操作按钮（`向右分屏`、`向下分屏`、`最大化/还原`、`关闭窗格`、`添加 Tab`）一律包裹 `<Tooltip content="..." side="bottom">`；
  - 标签项超长文本省略时，由 Tooltip 承载完整标题；
  - 统一享受项目的圆角胶囊、柔和阴影与主题一致性，杜绝浏览器默认泛黄方框气泡。

### 5.2 焦点边框与无重阴影审计（§13）
- **红线要求**：默认无重阴影，激活态禁止粗、深、实心黑边（如 `0 0 0 1px #000`），混色上限约 10%；
- **落地验证**：
  - 单一 `LeafToolTabStrip` 与窗格容器杜绝任何厚重 `box-shadow`；
  - 窗格激活态仅使用 `color-mix(in srgb, var(--border-subtle) 95%, var(--text-primary) 5%)`；
  - Sash 分割条悬停态仅提升微弱反差（`var(--border-focus)`），避免视觉割裂。

### 5.3 现代色彩空间审计（§14）
- **红线要求**：优先使用现代 HSL / HSLA / OKLCH，斜杠透明度语法，杜绝散落旧式 `rgba(...)`；
- **落地验证**：
  - 窗格标签、Sash、按钮悬停、激活背景统一采用 CSS custom properties（如 `hsl(var(--hue) var(--sat) var(--lit) / 0.08)`）；
  - 激活高亮色采用 `var(--tab-active-surface, var(--surface-raised))`，保持全域色彩同构。

### 5.4 反过度设计红线对照
对照 `ANTI_OVERENGINEERING_GUARDRAILS.md` 与用户最新 V2 裁决：
- **拒绝引入多层 Header 冗余**：废除“全局顶条 + 窗格微条”双层结构，统一为单一 `LeafToolTabStrip`；
- **拒绝华而不实的预设菜单**：直接砍掉所谓的“Presets 预设菜单”与晦涩的“Tab 迁移矩阵算法”，保持方案极其纯粹；
- **拒绝重量级外部 Docking 库**：依托自研轻量二叉树纯逻辑（`flattenDockTree`），以极简纯组件形式下沉；
- **坚持原生标准能力**：采用标准 `container-type: size` 配合属性降级桥梁解决自适应，不使用繁重低效的全局 JS resize 监听器频繁触发全量组件重渲染。

## 七、总结与结论

本方案针对右侧工具坞通常处于 **320px ~ 900px** 的紧凑物理约束，确立了一套符合用户最新 V2 架构意志的分屏交互与自适应视觉系统：
1. **单一窗格头部（LeafToolTabStrip）**：彻底剔除双层头部堆叠与组件切换包袱，高度固定在 28px，实现代码高度内聚，将纵向空间 100% 留给工具内容区；
2. **直觉操作与极简动作集群**：摒弃复杂的预设菜单与 Tab 迁移算法，以 4 个标准图标按钮（向右分屏、向下分屏、最大化/还原、关闭/收起）与 22% 边缘拖拽热区满足用户全部高频分屏诉求；
3. **W3C `@container size` 与双轨自适应**：穿透全屏媒体查询局限，纠正了 `inline-size` 无法查询高度的 W3C 规范硬伤，辅以 `data-*-tier` 属性构建跨平台兼容与自动化单测断言的坚固桥梁；
4. **严守项目设计红线**：全键盘空间流转、5%~6% 极柔和焦点指示环（§13）、自定义 Tooltip（§12）与现代色彩空间（§14），实现架构优雅、性能卓越与体验极致的深度统一。
