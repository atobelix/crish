## 1. 审计综述与严重性等级分布

在对前端 538 个测试文件（7026 个用例）进行全量逆向分析后，确认当前测试套件在 Vitest + jsdom 环境下达到 **100% 绿灯（538/538 Passed）**，但在真实浏览器渲染树与 Tauri WebView2 宿主环境下，存在多处 **「测试全绿但真机异常」的重大隐患**。

| 严重等级          | 问题数量 | 核心类型                                                           | 影响范围                                        |

## 2. 核心发现一：正在「守卫错误行为」的测试用例

### 2.1 `ModelBadgePickerMenu.tsx` 顶部面板硬编码 `side="top"` 导致向上穿顶溢出，单测全面失焦守卫假象

- **相关源码**：`apps/crish-desktop/src/components/provider/ModelBadgePickerMenu.tsx:65`
- **实际挂载位置**：`apps/crish-desktop/src/components/chat-card/ChatHeaderControls.tsx:127`
- **相关测试**：`apps/crish-desktop/src/components/provider/ModelBadgePickerMenu.test.tsx:57-212`

#### 缺陷与危害分析

1. **物理几何违背**：`ChatHeaderControls` 位于 `ChatCardHeader` 顶部导航栏最上端。在 `ModelBadgePickerMenu.tsx:65` 中硬编码了 `side="top"`，这意味着 Radix Popover 默认尝试将菜单弹向按钮上方（即窗口标题栏甚至屏幕外部）。对比同一 Header 区域的 `ChatHeaderMore.tsx:75` 与 `ProjectPickerMenu.tsx:139` 均正确配置为 `side="bottom"`。
2. **测试假阳性与失焦**：`ModelBadgePickerMenu.test.tsx` 编写了 213 行测试（覆盖服务商展开、子菜单漫游、Esc 逐级关闭、Hover 定时器等），但所有测试均在 jsdom 下运行，完全未断言 `side` 属性，也没有测试碰撞避让或方向预期。测试在没有任何真实视口几何检验的情况下宣告「全部通过」，掩盖了顶部菜单朝向错误的缺陷。

### 2.2 `SkillsMoreMenu.tsx`：`options` 与 `children` 双重透传引发多通道事件与漫游错位

- **相关源码**：`apps/crish-desktop/src/components/settings-skills/SkillsMoreMenu.tsx:149-153`
- **基座逻辑**：`apps/crish-desktop/src/components/ui/Menu/Menu.tsx:151-188, 341-393`
- **相关测试**：`apps/crish-desktop/src/components/settings-skills/SkillsMoreMenu.test.tsx:1-90`

#### 缺陷与危害分析

1. **架构双重透传**：`SkillsMoreMenu` 向 `<Menu>` 同时传入了 `options={options}` 且包裹了自定义 `children={<div id={moreMenuId}>...}`。
2. **事件与漫游通道冲突**：
   - `Menu.tsx:341` 渲染分支判定：若 `children != null` 则直接渲染 `children`，传入的 `options` 不参与 UI 渲染；
   - 但 `Menu.tsx:151` 键盘漫游判定：若 `options.length > 0`，键盘 `ArrowDown`/`Enter` 强制走 `options` 模式处理，在 `Enter` 时执行 `options[focusedIndex].onClick?.()`；
   - 同时，如果子 DOM button 上原本绑定了原生 `onClick`，会产生双重执行或不同步的隐患。
3. **测试假阳性**：`SkillsMoreMenu.test.tsx` 仅测试了直接通过 Testing Library 点击渲染出来的菜单文字，从未通过键盘漫游触发 `Enter` 选中，未发现此架构冲突。

### 2.3 `CardPanelHeader` / `placeTabsAddMenu`：手写未保护的 DOMRect 计算

- **相关源码**：`apps/crish-desktop/src/components/card-panel/CardPanelHeader.tsx:28-47`
- **调用位置**：`apps/crish-desktop/src/components/card-panel/useCardPanelTabs.ts:141`

#### 缺陷与危害分析

1. **脱离统一收敛体系**：项目已确立 `ui/Menu/position.ts` 与 `Menu` 基座为所有浮层坐标单源（PE-05 T05.3.1），但 `CardPanelHeader.tsx` 仍遗留了手写的 `placeTabsAddMenu(anchor: DOMRect)`。
2. **零坐标归零缺陷**：在元素未渲染或测试环境中 `anchor` 为 `DOMRect(0,0,0,0)` 时，`placeTabsAddMenu` 计算出 `top = 0 + 4 = 4`, `left = max(8, 0) = 8`，将菜单钉在屏幕左上角 `(8, 4)`。
3. **零测试保护**：`placeTabsAddMenu` 完全没有任何独立的单测用例覆盖。

## 3. 核心发现二：不可信的 Mock、假数据与 DOM 猴子补丁

### 3.1 `ChatComposer.test.tsx` / `TiptapComposerField.test.tsx` / `TiptapEditorField.test.tsx` 中的全局全零 Range 补丁

- **相关文件及行号**：
  - `apps/crish-desktop/src/components/chat-composer/ChatComposer.test.tsx:13-36`
  - `apps/crish-desktop/src/components/chat-composer/TiptapComposerField.test.tsx:13-37`
  - `apps/crish-desktop/src/components/chat-composer/TiptapEditorField.test.tsx:23-48`

#### Mock 片段

```typescript
if (
  typeof Range !== 'undefined' &&
  typeof Range.prototype.getClientRects !== 'function'
) {
  Range.prototype.getClientRects = function getClientRects() {
    return [this.getBoundingClientRect()];
  };
}
if (
  typeof Range !== 'undefined' &&
  typeof Range.prototype.getBoundingClientRect !== 'function'
) {
  Range.prototype.getBoundingClientRect = function getBoundingClientRect() {
    return {
      top: 0,
      left: 0,
      right: 0,
      bottom: 0,
      width: 0,
      height: 0,
      x: 0,
      y: 0,
    } as DOMRect;
  };
}
if (
  typeof Element !== 'undefined' &&
  typeof Element.prototype.scrollIntoView !== 'function'
) {
  Element.prototype.scrollIntoView = function scrollIntoView() {};
}
```

#### 危害分析

1. **非物理假数据注入**：将 `Range.prototype.getBoundingClientRect` 固定 Mock 为全 0 数据。在真实的浏览器中，光标或选区无论在输入框第 1 行还是第 10 行，都会产生具有真实 `top`, `left`, `bottom` 坐标的矩形。全 0 数据完全脱离物理世界。
2. **ProseMirror 坐标定位失真**：ProseMirror 的 `coordsAtPos` 依赖于 `Range.prototype.getBoundingClientRect`。全 0 返回导致编辑器内部计算出的光标坐标永远是 `(0, 0)`。
3. **制造假阳性**：测试中斜杠菜单弹出的所有测试均顺利通过，但实际测试仅仅验证了 DOM 节点被插入，根本无法验证菜单是否贴合光标弹出，掩盖了真实机器上斜杠菜单错位或跳动的风险。
4. **测试用例间污染**：此补丁直接打在 `Range.prototype` 与 `Element.prototype` 上，未在 `afterEach` 中还原，持久污染当前 Vitest 工作进程。

## 4. 核心发现三：迎合假测试而写入业务代码的「防御性反模式」（毒代码追踪）

### 4.1 `TiptapSlashMenu.tsx` 中的虚假零点过滤逻辑

- **相关源码**：`apps/crish-desktop/src/components/chat-composer/TiptapSlashMenu.tsx:143-149`

#### 毒代码片段

```typescript
const editorDom = (props.editor as any)?.view?.dom as HTMLElement | undefined;
const fallbackRect =
  editorDom?.getBoundingClientRect?.() || new DOMRect(0, 0, 0, 0);
const rawRect = typeof clientRect === 'function' ? clientRect() : clientRect;
const rect =
  rawRect &&
  (rawRect.top !== 0 ||
    rawRect.left !== 0 ||
    rawRect.width !== 0 ||
    rawRect.height !== 0)
    ? rawRect
    : fallbackRect;
```

#### 因果逆向溯源与危害

1. **起源**：由于 `ChatComposer.test.tsx` 等单测 Mock 的 `Range.prototype.getBoundingClientRect` 恒定返回全 0（`{top:0, left:0, width:0, height:0}`），单测中 `clientRect()` 返回了全零矩形。为了让单测不抛出异常崩溃，业务代码被迫添加了 `(rawRect.top !== 0 || rawRect.left !== 0 || rawRect.width !== 0 || rawRect.height !== 0)` 的判断，在全 0 时回退到 `fallbackRect`。
2. **真机毒性反噬**：
   - 在 `SlashExtension.ts:277` 中，光标位置被构造为：`new DOMRect(coords.left, coords.bottom, 0, 0)`（光标为单点，宽高物理上即为 0）；
   - 若用户在输入框最左上角（`coords.left === 0 && coords.bottom === 0`）输入 `/`，或者由于某种原因 `rawRect` 的宽高为 0 且坐标为 0，该毒判断会将真实合法的 `rawRect` 当作非法数据抛弃，错误回退到 `fallbackRect`；
   - 若 `editorDom` 尚未完成首帧渲染，`fallbackRect` 又回退到 `new DOMRect(0, 0, 0, 0)`，最终导致浮层钉死在屏幕 `(0, 0)` 坐标！
