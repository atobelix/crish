## 一句话结论

**文件 I/O 与搜索域的安全边界（路径沙箱、symlink 防护、二进制探测、原子写状态机、索引沙箱根校验）明显优于平均水平，但存在两类结构性放大：① 壳 fs 三命令仍以同步 `fn` 跑在 Tauri 命令线程（03-I3 未修）；② agent-tools 的 `read_file` / `grep_search` / `fuzzy_find` 在 `async fn execute` 内直接调用 `std::fs` 全量读/全量重建索引，阻塞 tokio worker——叠加前端「代码预览默认 20000 行整包拉取」，大目录扫描、全文检索与大文件预览构成当前域内最高危的延迟与内存放大面。**

## 正面发现（禁止回潮）

### G1. `core_search_files`：读锁短持有 + Arc 零拷贝 + spawn_blocking

- **位置**：`apps/agent-workbench/src-tauri/src/core_commands.rs:144-160`
- **现场**：
  ```rust
  let files = state.files.read()...clone();   // Arc clone，零数据拷贝
  let hits = tokio::task::spawn_blocking(move || { ... }).await?;
  ```
- **评价**：读锁仅覆盖 Arc clone；匹配与排序在 blocking 线程池；`files.len() >= 1000` 才走并行（阈值 `SEARCH_PARALLEL_THRESHOLD`，`:35`）。与 F2-27 / 03-P3 纪律一致。
- **禁止回潮**：不得把 `search_files`/`search_files_parallel` 移回 async 路径直调。

### G2. `core_rebuild_search_index`：spawn_blocking + 工作区沙箱根

- **位置**：`core_commands.rs:174-241`
- **现场**：`resolve_index_root` 要求 canonicalize 后 ∈ WorkspaceRegistry；越界返回 `workspace_not_granted`；索引重建经 `spawn_blocking`；完成后原子交换 `Arc<Vec<String>>`。
- **评价**：防「任意目录建索引（全盘文件名枚举 + 长时间占线程）」——安全与性能双重正确。

### G3. 壳读文件策略完备：字节上限 + 行上限 + 二进制探测 + 分块

- **位置**：`fs_commands/types.rs:4-8`、`read.rs:41-132`
- **常量**：`MAX_TEXT_FILE_BYTES=4MB`、`DEFAULT_MAX_TEXT_FILE_LINES=2000`、`MAX_TEXT_FILE_LINES=20_000`、`BINARY_SCAN_BYTES=8KB`、`READ_CHUNK_BYTES=8KB`
- **评价**：分块读 + 行限截断 + 二进制 magic/NUL/控制字符启发式 + UTF-8 前缀校验，边界处理扎实（与 agent-tools 的「整文件读」形成鲜明对比）。

### FS01.【高】壳 fs 三命令同步 `fn`：同步文件 IO 跑在 Tauri 命令线程（03-I3 展开）

#### 位置

- `apps/agent-workbench/src-tauri/src/fs_commands/mod.rs:29-63`
  - `list_directory`（`fn`，非 async）
  - `read_file_content`（`fn`）
  - `write_file_content`（`fn`）
- 对照同文件 `select_folder`：`async fn` + `blocking_pick_folder`（`mod.rs:19-24`、`dialog.rs:18-33`）

#### 现场

```rust
#[tauri::command(rename = "workbench_list_directory")]
pub(crate) fn list_directory(...) -> Result<...> { directory::list_directory(&app, path) }
// read_file_content / write_file_content 同形态
```

内部：

- `directory.rs:29-66`：`std::fs::read_dir` + 每条目 `symlink_metadata`
- `read.rs:45-104`：分块 `File::read` 循环
- `write.rs:51-52`：`std::fs::write` 整串落盘

#### 调用链

```
前端 invokeResult('workbench_list_directory'|read|write)
  → Tauri 命令线程（非 async 命令）
  → 同步 std::fs
  → JSON 序列化回传
```

前端消费：`workspaceFsApi.ts:121-221`（listDirectory / readTextFile / writeTextFile）、`importFsHost.ts:117-142`、`ComposerDirTree.tsx`、`useFileNavigation.ts`。

#### 根因

PE-03 / F2-27 要求「tokio worker 不执行同步 IO」；全仓 65+ 处 `spawn_blocking` 覆盖下，fs 三命令保持同步 `fn`（Tauri 2 将非 async 命令放在专用命令线程池，不直接占 tokio worker，但仍占用命令派发面，且与纪律不一致）。03 报告 I3 已认定，本方向展开完整 IO 面。

#### 影响量化（静态）

| 场景 | 成本 |
| ---- | ---- |
| 大目录 list（数万条目） | 每条目一次 `symlink_metadata` + sort，命令线程长时间占用 |
| 读接近 4MB / 20k 行文件 | 分块循环 + `String::from_utf8` 二次拷贝 |
| 写数 MB 文本 | 整串 `fs::write`，非原子 |
| 与 03 事件通道并发 | 命令线程阻塞 → 其它 GUI 命令排队延迟 |

#### 修复方案

1. 三命令改 `async fn` + `tokio::task::spawn_blocking`（模式照抄 `session_commands.rs` / `core_commands.rs`）。
2. `list_directory` 增加分页/条目上限（见 FS03）。
3. 写路径评估接 `atomic_write`（小文件）或保持直写但明确非原子契约。

#### 回归锚点

- `fs_commands/mod.rs` 现有单测保持绿（`read_file_content_*` / `write_file_content_*`）。
- 新增：命令签名 `async` 的编译期断言；`spawn_blocking` 调用点静态检查（可选 clippy/grep 门禁）。

### FS02.【高】`read_file_content`：行限截断后仍可能读到字节上限 / 二次分配

#### 位置

- `fs_commands/read.rs:55-104`（主循环）
- `read.rs:119-125`（`String::from_utf8(output)` + `content.lines().count()`）

#### 现场

```rust
loop {
    if reached_line_limit && truncated && scan_prefix.len() >= policy.binary_scan_bytes {
        break;  // 有提前退出条件
    }
    ...
    output.extend_from_slice(...);
}
let content = String::from_utf8(output)...;
let line_count = content.lines().count();  // 再扫一遍
```

#### 分析

- **正面**：行限达到且已截断、二进制前缀扫满时会提前 `break`（`:56-58`）——并非总读满 4MB。
- **缺口 1**：当 `truncated=false`（文件在行限内）仍读完整文件（正确），但前端常传 `maxLines=20000`（FE01），大文件会把接近 4MB 全部拉进 IPC。
- **缺口 2**：`output` 先 `Vec<u8>` 再 `from_utf8` 再 `lines().count()`——内容已按字节组装，行数再全文扫描一次；对 20k 行文件是额外一次 UTF-8 扫描。
- **缺口 3**：`max_lines==0` 时 `reached_line_limit=true` 初始为真，但仍可能因 `truncated` 逻辑继续读直到二进制前缀满足（`:56` 条件含 `truncated`）——边界路径略绕。

#### 修复方案

1. 行数改为组装过程中维护（已有 `line_breaks_kept`，可在 return 时直接使用）。
2. 对「仅预览」路径默认收紧 `DEFAULT_MAX_TEXT_FILE_LINES` 或强制分页（对齐 FE01 修复）。
3. 契约增加 `nextLineOffset` / 字节 offset，支持前端真正分段拉取（现在「继续加载」是整包重拉更大 maxLines）。

#### 回归锚点

- `mod.rs` 测试：`read_file_content_stops_output_at_line_limit`、`preserves_content_when_line_limit_matches_file`。
- 新增：`line_count` 与 `content.lines().count()` 一致性；分段续读契约测试。

### FS04.【中】`write_file_content`：整串同步写、非原子、无大小节流于 IPC 入口

#### 位置

- `fs_commands/write.rs:26-56`
- 入口参数：`mod.rs:56-62`（`content: String` 全文经 IPC 反序列化）

#### 现场

```rust
if content.len() > MAX_TEXT_FILE_BYTES { return Err(...); }
std::fs::write(&file_path, content.as_bytes())...
```

#### 分析

- 有 4MB 上限（`:45-49`）——正面。
- 非原子：崩溃窗口可能半写（对照 `conex_fs::atomic_write` 已存在但未用于此路径）。
- `content` 已在 IPC 反序列化为 `String`，再 `as_bytes` 写——与 atomic_write 的 `&[u8]` 兼容。

#### 修复方案

- 小文件走 `atomic_write`（配置/文档编辑场景）；大文件保持直写但文档化。
- 与 agent-tools `write_file` 对齐：工具侧也非原子（SR06）——可统一接 atomic_write。

#### 回归锚点

- `write_file_content_rejects_existing_by_default` 等 T-EG-05 测试；新增崩溃中断一致性可选集成测试。

### SR01.【高】agent-tools 全部 fs/search 工具：`async fn execute` 内同步 `std::fs`，阻塞 tokio worker

#### 位置

| 工具 | 关键 IO | 行号 |
| ---- | ------- | ---- |
| `read_file` | `std::fs::metadata` + `std::fs::read` 全文件 | `tools/fs.rs:75-106` |
| `write_file` | `exists` + `std::fs::write` | `fs.rs:322-346` |
| `list_dir` | `read_dir` + 每目录 `count_direct_children` | `fs.rs:507-563` |
| `file_stat` | `metadata` | `fs.rs:639` |
| `grep_search` | `walk_files` + 每文件 `metadata`+`read` | `search.rs:162-178` |
| `fuzzy_find` | **每次** `build_directory_index` | `search.rs:488` |

#### 调用链

```
session-loop tool_executor
  → agent-tools::execute_with_output_policy (executor_run.rs:67)
  → tool.execute(...).await   // async trait
  → std::fs::* 同步调用       // 占用 tokio worker
```

#### 根因

工具接口为 `async_trait`，实现方未包 `spawn_blocking`。与壳侧 core_commands / session_commands 的 F2-27 纪律不一致。

#### 影响量化（静态）

| 工具 | 最坏成本 |
| ---- | -------- |
| read_file | 单文件可达数 MB～数十 MB 全读（无文件大小硬上限在读前拒绝） |
| grep_search | ≤2000 文件 × ≤512KB 读 + 逐行扫描，单次工具调用可秒级阻塞 worker |
| fuzzy_find | 全树 walk（depth 16）每调用一次 |
| list_dir | 大目录 + 每子目录二次 read_dir |

#### 修复方案

1. **统一**：重 IO 工具（read/grep/fuzzy_find/list_dir/write）在 execute 内 `tokio::task::spawn_blocking` 包裹同步核心。
2. **read_file**：按需流式/分段读（见 SR02），大文件读前 `metadata.len()` 超 `maxBytes * k` 时只读窗口。
3. **fuzzy_find**：共享会话级目录索引（带 TTL / watch 失效），禁止每调用全量重建（SR03）。

#### 回归锚点

- `tools/fs.rs` / `tools/search.rs` 现有单测全绿。
- 新增：`spawn_blocking` 存在性静态检查；并发 worker 压测（runtime 验证）。

### SR02.【高】`read_file` 工具整文件读入再切行窗口

#### 位置

- `tools/fs.rs:105-149`

#### 现场

```rust
let bytes = std::fs::read(&file_path)?;          // 整文件
let decoded = decode_text(&bytes);
let lines: Vec<&str> = decoded.text.lines().collect();
let window_text = lines[window_start..window_end].join("\n");
```

#### 分析

即使 `maxLines=80` / `maxBytes=256_000`，仍：

1. 读完整文件字节；
2. 全文解码；
3. `lines()` 为整个文件建指针表；
4. 仅 join 窗口。

对「读第 1–80 行」请求，I/O 与内存与文件总大小成正比，与请求窗口无关。

#### 修复方案

1. 读前 `metadata.len()`：若 `len > maxBytes * 2`（或独立 `maxReadBytes`），只 `read` 前 `maxBytes * 2` 字节再切行（注意 UTF-8 边界）。
2. 或 mmap / 惰性行索引（对超大文件）。
3. 保留二进制引用分支（读前用前 8KB 探测，避免整文件读）。

#### 回归锚点

- `read_file_roundtrip`、`truncates_oversize_content`、`content_offset_resumes` 等（`fs.rs:698+`）。

### SR03.【高】`fuzzy_find` 每次调用全量 `build_directory_index`

#### 位置

- `tools/search.rs:487-490`

#### 现场

```rust
let indexed = conex_search::walker::build_directory_index(&root_str);
let hits = conex_search::search::search_files(&query, &indexed, limit, &matcher);
```

#### 调用链

模型循环内多次 `fuzzy_find` → 每次全树 walk（gitignore + max_depth 12 + 组件 SKIP 过滤 + sort）→ 再模糊打分。

#### 根因

未复用 `core_commands::SharedSearchState`（壳侧索引）；工具与命令两套索引生命周期，工具侧无缓存。

#### 影响量化（静态）

中型 monorepo（~5 万文件，忽略后数千～数万）：单次 walk 数十～数百 ms 量级 CPU+IO；模型一轮 3～5 次 fuzzy_find = 秒级累计。

#### 修复方案

1. 会话 `ToolContext` 挂 `Arc<RwLock<Arc<Vec<String>>>>` 目录索引，带 mtime/TTL；walk 仅 miss 时发生。
2. 与壳 `SharedSearchState` 通过装配层共享（若同进程）。
3. 或工具内 `spawn_blocking` 包 walk（SR01 的最小修复）。

#### 回归锚点

- `fuzzy_find_returns_ranked_candidates`；新增：连续两次调用 walk 计数（可用 mock/计数器）或 TTL 行为测试。

### SR04.【中】`grep_search`：先收集路径数组再逐文件全读；无流式早期退出的 IO 层优化

#### 位置

- `tools/search.rs:162-220`、`walk_files` `:360-404`

#### 现场

`walk_files` 先物化 `Vec<PathBuf>`（≤maxFiles），再循环 `metadata` + `read`。

#### 分析

- 行级模式在 `matches.len() >= max_matches` 时 `break`——文件级循环可提前停（`:192-200`），但**路径列表已全部物化**（walk 完成）。
- 每文件 `std::fs::read` 全文件进内存；`maxFileBytes=512KB` 上限为正面。
- 无并行文件读（单线程顺序）；对「全库宽 grep」延迟线性叠加。

#### 修复方案

1. 合并 walk 与搜索为单次迭代（命中即搜，避免二次遍历物化）。
2. 可选：文件级并行（rayon/spawn_blocking 池），注意输出顺序与上限。
3. 继承 SR01 的 spawn_blocking。

#### 回归锚点

- `grep_max_matches_truncates`、`grep_glob_filter_limits_to_rust_files` 等。
