## 1. 执行摘要

**一句话结论：架构骨架健康（三道防线真实有效），但主线程「每渲染帧派生计算」层系统性退化——4 个专门构建的增量组件中 3 个闲置或失效，长输出（100KB+）流式后期每帧派生计算合计可达毫秒级，是卡顿首要嫌疑；另有装配层 memo 契约被内联引用局部击穿。**

- **防线有效的部分**：48ms 定时批 + rAF 帧预算双层节流（每 token 0 次 store set）；streamingStore（热缓冲）与 sessionStore（immer 持久域）物理隔离；流式尾块纯文本直写 DOM，封口块才走 Rust markdown 编译一次（不存在"每 token 全文 parse/sanitize/highlight"灾难）；订阅面干净（全仓仅 3 处无 selector 整体订阅，均在低频 store）；自研 Fenwick 树虚拟化质量高（单点高度更新 O(log N)，窗口常驻 ~22-26 行）。
- **退化的部分**：增量块切分器被当一次性 API 每帧全文重建（H1）；封口块哈希每帧全文重算（H2）；增量 thought 剥离器无人使用、缓存被流式输入击穿（M3）；增量代码高亮器是死代码（L1）；timeline 签名每帧全量 stringify（M4）；装配层（ChatCard）引用稳定性失守导致下游 memo 集体失效（M6）。
- **发现计数**：4 高（H1–H4）/ 11 中（M1–M11）/ 7 低（L1–L7），另有 3 项交叉发现归入方向 02/03/05/08。
- **修复性价比最高**：H1+H2（`useStreamingBlocks` 真增量化）——改动局部、直击长输出流式后期主线程开销。

### 2.3 术语与约定

- 「每帧」= 每个 rAF 渲染帧，由 `StreamRenderBuffer` 限流（6ms 预算 / 1024 字符每帧上限），实测上限 60–120 fps、实际受预算压制更低。
- 「每次 flush」= 48ms 批合并窗口触发的一次状态落地（text/thinking/tools 三个 batcher，`intervalMs: 48`）。
- 「封口块」= markdown 块结束的文本段（空行分隔 / 围栏闭合），此后内容不可变；「活跃尾块」= 尚未封口的最后一段。
- 行号基准：2026-09-12 工作区快照；后续代码变动需按符号名重定位。

### 3.3 节流与批合并机制详解（现状基线）

**正文（rAF 层）**：`useRunStreamingAssistant.ts:293-306` onChunk 只做内存累计 + `renderBufferRef.current.push(chunk)`，不触碰 store。`StreamRenderBuffer.ts:214-219` 用 `requestAnimationFrame` 分帧：每帧上限 1024 字符 / 6ms 执行预算 / 超积压降级跳帧；`buffer.onFrame` 回调里才调 `setStreamText(sid, assistantMsgId, frame.full)`（`useRunStreamingAssistant.ts:165/173`）。

**thinking / tools（48ms 定时层）**：`useStreamBatchers.ts:43-107`，三个 batcher 均 `intervalMs: 48`（leading-edge 合并窗口）；text `maxBufferedChars: 8000`、thinking `4000`，超限 force flush。thinking 的 push 语义正确：`messageHandlers.ts:105-108` 传入的是累计全文 `prevThought + t`，与 batcher「全文覆盖」契约一致。

**工具终态例外（同步写）**：`isImmediateToolStatus`（success/error/pending_approval）跳过 batcher，立即 `commitToolPatchToSession` 写 sessionStore + `clearStreamTool`（`useStreamBatchers.ts:82-85`）——设计内行为，保证审批卡片零延迟。

**净效果**：token 事件每秒数十至数百次，store set 被压至 ≤ 每帧一次（正文）+ ≤ ~21 次/秒（thinking/tools）。**每 token 对 React 的更新次数为 0**。

## 4. 正面发现（已验证防线，禁止回潮）

### P1. 双层节流：48ms 定时批 + rAF 帧预算
- 证据：`src/hooks/chat-stream/useStreamBatchers.ts:43-107`；`src/api/StreamRenderBuffer.ts:60-66`（6ms 帧预算 / 1024 字符单帧上限，超限跳帧降级）。
- 价值：token 事件风暴被压到「每帧至多一次正文 set + ~21 次/秒 thinking/tools」，React 更新频率与 token 速率解耦。
- 回潮风险：任何「绕过 batcher 直写 store」的新代码都会破坏该防线；`check:store-writes` 门禁已强制裸 setState 零残留（README:193-204），本次 grep 与之吻合。

### P2. 热缓冲与持久域物理隔离
- 证据：`streamingStore.ts:138`（plain zustand）；`useStreamBatchers.ts:39-40` 注释明示设计意图：「Text/thinking flush into lightweight streamingStore (no immer) so token ticks do not rewrite session messages」。
- 价值：token 不经过 immer 的整树 produce，sessionStore 在流式期间写入被刻意排除。
- 附加验证：`sessionMessageActionsCore.ts:193-206`（updateMessageText 有同值短路）、`:39-88`（addMessage 经 sessions[] 写避免 immer fork 陷阱，有 `MAX_MESSAGES_PER_SESSION` 截断）——持久域 action 粒度已收窄到单会话/单消息。

### P3. 尾块纯文本直写 + 封口块一次编译
- 证据：`MarkdownBlockItem.tsx:84-85`（`const renderTarget = isSealed ? text : ''`）、`:113-124`（活跃尾块 TURBO 模式单 TextNode `textContent` 直写 / SPAN 模式）、`:145-160`（useEffect 中 `el.innerHTML = html`，LRU 命中跳过，双缓冲垫片）；`markdownRenderAsync.ts:29-43`（LRU 命中 → Rust `core_md_render`：pulldown-cmark + syntect + ammonia，spawn_blocking → 失败回退 render worker highlight.js）。
- 价值：**链路中不存在**「每次更新重建整个 HTML 字符串 + 全量 dangerouslySetInnerHTML 替换」的路径；每帧唯一 DOM 写入是尾块 `textContent`（无 parse、无 sanitize）。
- 附注：组件层无重复 sanitize——`rustCore.ts:202` 注释明确 DOMPurify 为冗余（Rust ammonia 已一次到位）。

### P4. 订阅面干净
- 证据：§3.4 统计表；`streamMessageViewModel.ts:116-123`（streamingStore 唯一组件级挂载点：`useShallow` + `EMPTY_STREAM_BODY` 稳定空切片 `:97-101`），非流式行零重渲染。

### P5. 自研 Fenwick 树虚拟化
- 证据：`VirtualScrollManager.ts:420-452`（computeVisibleRange：2 次 `findIndexAtOffset`，各 O(log²N)）；单点高度更新 `bitAdd` O(log N)；`useVirtualScroll.ts:120-209` Gesture Epoch（滚动中冻结测高回写，100ms 静默窗口后统一 commit）。
- 价值：动态高度不是「全量重测」而是「估算兜底 + 实测单点回写」；500 条消息滚动每帧计算 ≈ 2×(9²)≈160 次数组访问，可忽略。overscan = 8（`MessageVirtualizer.tsx:122`，hook 默认 6）。

### P6. 封口块 0 重渲染 + 测试锁定
- 证据：`useStreamingBlocks.ts:86-104`（sealedCacheRef 对象引用复用）；`__tests__/reRenderMonitoring.test.tsx:357`（「流式纯文本帧稳定历史块渲染 0 次」）、`:419`（「工具区渲染 = 工具事件数而非帧数」）——防回归机制完备。

### P7. Context 与动画无滥用
- 证据：19 处 `createContext` 均为低频或正确隔离设计（`narrativeRenderSlots.ts:41` 模块级稳定空值；`SessionRow.tsx:41-56` tick 消费隔离到 memo 叶子）；motion ^13 仅 4 处悬停图标且走 `LazyMotion(domMin)`；消息行无 layout 动画，流式动画走 CSS（`streaming-animation.css`）。

### P8. key 策略健康
- 证据：消息行 `key={msg.id}`（`MessageVirtualizer.tsx:447, 478`）；高度缓存键 `data-vindex={msg.id}`（`:196` 注释明确「不再用数字下标」）；markdown 块键 `${messageId}-blk-${i}-${hash16}`（`useStreamingBlocks.ts:85`）；`key={index}` 仅存在于渲染后不变的静态子列表（diff 行号、grep 行、代码行号）。

## 5. 问题清单

### 5.1 高严重度

---

#### H1. 每帧对全量文本做 O(n) 全文重切分——增量切分器被当一次性 API 用

- **严重度**：高 ｜ **类别**：算法退化（增量设计未接线） ｜ **置信度**：高（双路独立探查交叉确认）
- **位置**：
  - 调用点：`src/components/chat-message-row/useStreamingBlocks.ts:62-67`
  - 实现：`src/components/chat-message-row/IncrementalBlockSplitter.ts:129-136`（静态 `split()`）；`:235-243`（未闭合围栏等待逻辑）
- **现象**：流式期间每个渲染帧，整条消息全文被从头重新切块。
- **代码现场**：

```ts
// useStreamingBlocks.ts:62-67 —— Hook 主体
const blocksResult = useMemo<StreamingBlocksResult>(() => {
  ...
  const rawBlocks = IncrementalBlockSplitter.split(fullText);   // ← fullText 每帧都是新前缀
```

```ts
// IncrementalBlockSplitter.ts:129-136 —— 静态 split 的真实行为
static split(fullText: string): RawBlock[] {
  const s = new IncrementalBlockSplitter();   // ← 每帧新建实例
  s.appendChunk(fullText);                    // ← 全量喂入
  s.flush();
  return s.getBlocks();
}
```

- **调用链与触发时机**：`setStreamText`（每 rAF 帧）→ streamingStore 变更 → `useStreamMessageViewModel` 合并 → `MessageContent` → `useStreamingBlocks(fullText)` → useMemo 依赖 `fullText` 失效 → 全量重切。触发频率 = 渲染帧率（≤60fps），输入规模 = 当前消息全长。
- **根因**：切分器类本身具备完整增量能力（行前缀和 `lineOffsets` + `pendingStartLine` 增量扫描 + 历史封口块零重复），但 Hook 侧以「无状态纯函数」方式调用静态 `split()`，增量状态机每帧被丢弃重建。属典型「有增量设计、无增量使用」。
- **影响量化**：每帧 O(n) 行扫描 + O(n) `lines/lineOffsets` 数组重建 + 块对象全量重建。100KB 消息（约 3000 行）× 60fps ≈ 每秒 18 万行扫描 + 每帧约 3000 元素数组 ×2 分配。消息越长越慢，正是「长 agent 输出后期越打越卡」的形状。
- **修复方案**（建议形态）：

```ts
// Hook 内持有实例（ref），流式期只喂增量
const splitterRef = useRef<IncrementalBlockSplitter | null>(null);
useEffect(() => { splitterRef.current = new IncrementalBlockSplitter(); }, [messageId]);

useMemo(() => {
  if (streamDelta) {
    splitterRef.current!.appendChunk(streamDelta);       // 只喂 delta
    return splitterRef.current!.getBlocks();             // 历史块引用复用
  }
  // 编辑回放 / 会话切换：全量重建（可接受，非热路径）
}, [messageId, streamDelta]);
```

  - 改动文件：`useStreamingBlocks.ts`（主）、`IncrementalBlockSplitter.ts`（暴露 `getBlocks()`，若未导出）。
  - 关键约束：封口块对象引用必须跨帧稳定（现 sealedCacheRef 机制依赖引用比较，P6）；收口（message-end）时必须 `flush()` 一次。
- **回归风险与测试锚点**：`__tests__/reRenderMonitoring.test.tsx:357/456` 已锁定「历史块 0 渲染」与「工具区渲染 = 事件数」；补一组切分结果等价性测试（全量 split vs 增量 appendChunk 对同一文本流输出逐块相等）。
- **关联**：与 H2 同文件同函数，建议一并修复；与 M8（尾块探针）同主题。

#### H2. 每帧对所有已封口块全文重算 hash16

- **严重度**：高 ｜ **类别**：无效计算（缓存判定顺序错误） ｜ **置信度**：高
- **位置**：`src/components/chat-message-row/useStreamingBlocks.ts:83-92`；哈希实现 `hash16`（同文件或 utils，逐字符 FNV 双哈希循环）
- **现象**：封口块文本帧间不变（不可变语义），但其哈希每帧重算。
- **代码现场**：

```ts

  if (cached && cached.isSealed && cached.key === key && cached.text === blockText) {
    // 缓存命中判定在哈希之后 —— 顺序颠倒
```

- **调用链与触发时机**：同 H1——每渲染帧、每个封口块各一次。块数随消息增长线性增加（100KB 消息可达数十块）。
- **根因**：哈希本应作为「缓存键的稳定分量」一次算好随块缓存；当前实现在缓存命中判定**之前**计算，等于每帧对全文（所有块长度之和）做一遍 FNV 双哈希。与 H1 叠加后，每帧对全文 = 1 遍扫描（切分）+ 1 遍哈希 + 2 遍数组重建。
- **影响量化**：100KB 消息 × 60fps = 每秒约 6MB 字符的哈希循环（每字符 2 次乘加），纯主线程。
- **修复方案**：两选一（可叠加）：
  1. **哈希随块缓存**：块对象在切分时（封口瞬间）生成并携带 `hash` 字段（H1 增量化后封口只发生一次，天然挂点）；
  2. **引用短路前置**：封口块文本引用稳定（切分器输出同一字符串对象）时，先 `cached.text === blockText` 短路，命中则完全跳过哈希：

```ts

  return cached;                                   // 引用相等 → 零计算
}
const blockHash = hash16(blockText);               // 仅首见块计算一次
```

- **回归风险与测试锚点**：块键格式 `${messageId}-blk-${i}-${hash16}` 被下游用作 React key（P8），改动后需保证键仍稳定——方案 1 天然满足；方案 2 需确认引用稳定性（增量切分器对封口块返回同一实例）。
- **关联**：H1、P8。

#### M7. 每事件主线程同步 JSON.parse，Worker 闲置

- **严重度**：中 ｜ **类别**：主线程卸载缺失
- **位置**：`src/api/transport/tauriTransport.ts:341-354`；worker 现状 `src/workers/worker-pool-options.ts:34-41`（默认 2 个 render worker，compute/io/network=0）、`render-worker.ts:13-16`（仅一次性全文 parseMarkdownToHtmlUncached，作 Rust 缺失时的降级）
- **代码现场**：

```ts

  const parsed = typeof payload === 'string'
    ? safeParseEventPayload(payload) : ...        // ← 每事件主线程同步 parse
  for (const cb of this.messageListeners) {
    try { cb(parsed); } ...                        // ← 同步 fanout 全部 listener
```

- **根因**：事件解析与分发无合并不卸载。token 事件本身小（几十~几百字节），但 thought/tool 参数流事件可能含大 `raw.message.content` 前缀回显。compute-worker 的轻量任务通道（json.parse 等）存在但未用于事件 parse。
- **影响量化**：高 token 率（>200 事件/秒）时的固定线性开销；单事件 parse 0.01–0.1ms，200 事件/秒 ≈ 2–20ms/秒 主线程占用。真实风险在**大 payload 事件**（工具参数流）——单事件可达数十 KB，parse 1ms+ 且不可预测。
- **修复方案**：短期——大 payload 事件（按 `payload.length` 阈值）转 compute worker parse；长期——与方向 03（IPC）协同：Rust 侧事件聚合（48ms 微批 emit），从源头降低事件数。
- **回归风险**：事件顺序保证（worker parse 是异步的，需保序——同 run 事件按序号排队）；`safeParseEventPayload` 的错误兜底语义在 worker 环境等价。

## 6. 量化分析（核心问答）

### Q1. 流式状态下，每接收一个事件，CPU 做多少重复工作？

**按事件（token 级）**：主线程同步 `JSON.parse` + EventRouter 同步 fanout + 字符串拼接/slice（M7、L3）。事件本身不做任何 markdown parse / sanitize / highlight。无 store set（P1 双层节流保证）。

**按渲染帧（rAF 级）**——重复工作真正聚集处。**不做**的（P3 证明）：全文 markdown parse、全文 sanitize、全文 highlight、全文 HTML 字符串重建 + dangerouslySetInnerHTML 全量替换。

**但每帧都做**的 O(全文长度 n) 主线程重复计算：

| # | 计算 | 问题号 | 复杂度 |
| - | ---- | ------ | ------ |
| 1 | 全文重切分 + `lines/lineOffsets` 数组重建 ×2 | H1 | O(n) |
| 2 | 所有封口块全文 FNV 双哈希 | H2 | O(n) |
| 3 | `stripThoughtPlaceholders` 全文正则 ×~10 ×2 调用点 | M3 | O(10n) |
| 4 | `timelineSignature` 历史块全量 stringify | M4 | O(n + 工具输出) |
| 5 | 尾块投机补全 + 表格探针 | M8 | O(尾块) |
| 6 | `renderSegmentItem` 新引用 → 折叠树壳层全渲染 | M5 | O(段数) |

合计约 **O(14n)/帧**（n = 全文长度）。20KB 消息 ≈ 28 万字符操作/帧 ≈ 0.1–0.3ms（无感）；100KB 消息 ≈ 140 万字符操作/帧 ≈ 0.5–1.5ms + GC 压力（每帧 2–3 个兆级中间数组），叠加 JS 主线程预算 16.7ms 中的 React reconcile（窗口 ~25 行）与布局（M1 强制 reflow），**长输出流式后期逼近掉帧阈值**——与「越打越卡」的体感形状吻合。

### Q2. 500 条消息的会话里，DOM 常驻多少节点？布局计算范围多大？

- **常驻**：可见 6–8 行（900px 视口 ÷ 平均行高 120–200px）+ overscan 8×2 ≈ **22–26 行**；单行 80–200 节点（wrapper + MessageContent + 工具卡 30–60 节点/个 + markdown 封口块 innerHTML 10–80 节点 + 操作栏），估算 **2000–5000 节点**。对照：不虚拟化全量渲染为 5 万–10 万节点级。工具卡展开时其输出 DOM 全量存在（M11），单卡另加数百–上千节点。
- **每次 flush（48ms）的布局工作**：Fenwick 单点更新 O(log N)（只更新最后一条消息，**非全列表重测**，P5）→ 全组件重渲染一次：窗口 ~25 行 reconcile（封口块 0 重渲染，P6）→ layout 阶段：全窗口 `offsetHeight` 批读（M1，1 次强制布局）+ `scrollHeight` 读 + `scrollTop` 写（吸底）→ 合计 1–2 次强制 reflow，范围为整个滚动容器（内容高度变化无法局部化，属必然成本）。M1 修复后可省掉其中一次。
- **每次滚动帧**：窗口计算 O(log²N)（P5，健康）+ 若 FlowScrubber 可见则另有 O(N log N) 全量 tick 计算（M2，**唯一随消息总数线性增长的滚动开销**）。
