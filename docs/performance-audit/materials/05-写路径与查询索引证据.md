## 1. 事件写路径热力

```
reserve_sequence（3 条独立自动提交）
  → INSERT OR IGNORE session_sequence
  → SELECT next_sequence
  → UPDATE next_sequence+1
append_event（1 条自动提交）
  → INSERT INTO events (session_id, sequence, event_type, payload, run_id, created_at)
```

调用链：orchestrator persist.rs:880-925 → blocking_db_call → LocalDb::reserve_sequence / append_event。

NoPersist 事件同样走此链（03 报告 R3 已交叉引用，DB 侧证据：persist.rs:96-97 列出的 kind 含 reserve_sequence）。

## 2. save_session_body 全量重写细节

```50:102:crates/conex-db/src/messages.rs
pub fn save_session_body(...) {
    let tx = conn.transaction()?;
    tx.execute("DELETE FROM session_messages WHERE session_id = ?1", ...)?;
    for (seq, msg) in messages.iter().enumerate() {
        tx.execute("INSERT INTO session_messages (...14列) VALUES (...)", ...)?;
    }
    tx.commit()?;
}
```

配套触发器（schema.rs:262-272）每次 DELETE/INSERT 更新 sessions.message_count。

CAS 参数：03 报告 I1 指出 `batch_version` 在 Rust 签名中被丢弃——DB 层签名本身也不含 CAS 列（messages.rs:50-53 仅 session_id + messages）。

bench：`benches/db_write.rs` 明确标注「全量路径 O(n)（DELETE 全表 + 逐条 INSERT + 逐行触发器 UPDATE）」，覆盖 100/1000/5000。

## 4. 读路径细节

- `load_session_body`：SELECT 全列文本（text/thinking/tool_calls_json/blocks_json/tool_call_results_json/usage_json）按 session_id——无 LIMIT，会话全历史进内存。
- `load_session_agents`：先查 agents，再 **逐 agent** `load_agent_messages`（agents.rs:67-71）——N+1 查询。
- `list_blocks`：SELECT 含 summary + summary_json 全量 TEXT（blocks.rs:347-353）。
- `query_usage_dashboard`：SELECT 时间范围内 **全部行**，Rust HashMap 分桶聚合（usage_analytics.rs:405-491）。
- `query_all_runs`：全表读 runs（persist.rs:1004 → 03 报告 I4 交叉引用；DB 侧 `runs.rs:293`）。
- `max_sequence`：SQL MAX 下推（events.rs:129-146）——正面。

## 5. 迁移与 GC

### 迁移
- 版本链 v1→v11，每版本独立事务 + `PRAGMA user_version` 进事务（migrate.rs:199-206）。
- DROP 前 checkpoint(TRUNCATE)+整库拷贝；v5–v11 纯 ADD COLUMN/建表跳过备份。
- v3→v4 重建 events/runs/pending 时 INSERT ... SELECT WHERE session_id IN sessions——大库启动一次全表拷贝（迁移期成本，冷路径可接受但需记录）。
- ensure 路径（current==LATEST）只 `create_v5_schema()`——**不含** compression_blocks / imported_* / usage_records / app_preferences 表 DDL（它们只在 migrate 步骤中创建）。新库走全链没问题；若 LATEST 库被外部 DROP 这些表，ensure 不会重建（靠缺表降级）。

### CAS GC
- `run_cas_gc` 持主 Mutex 全程（cas_gc.rs:290-296）：COUNT×4 + 标记扫描 + 逐 hash UPDATE + 逐 hash DELETE。
- mark/purge SQL 用 4 个 `hash NOT IN (SELECT DISTINCT ...)` 子查询（cas_gc.rs:496-507,546-557）。
- 后台 `spawn_cas_gc_loop` 用 `tokio::time::interval`（cas_gc.rs:656-695），调用方决定间隔。

### Lease
- 内存 HashMap 快速探测（lease_guard.rs:49-119）——正面。
- 持久化租约写仍持主 Mutex。

## 6. 双开连接与 FK 不一致

- write_conn 从未 `PRAGMA foreign_keys=ON`——若未来把域写迁到 group_commit，会绕过 FK。
- ReaderPool 只读连接设 query_only=ON——正确。
- 主连接 FK 仅在 migrate() 打开时设置一次；open() 的第一次 PRAGMA 批未含 FK。

## 7. 其他

- `sessions` 为 WITHOUT ROWID 且 `ORDER BY updated_at DESC, id ASC`——无 (updated_at,id) 复合索引，list_sessions 全表扫+排序。
- `insert_run` 使用 INSERT OR REPLACE（runs.rs:126）——OR REPLACE = DELETE+INSERT 语义，会短暂触发 FK 检查；生产 insert_run 频率低。
- `import_legacy_usage_snapshot` 在单连接循环逐条 INSERT 无外层事务（usage_analytics.rs:307-328）——一次性路径，量通常为天级条目数（≤数百）。
