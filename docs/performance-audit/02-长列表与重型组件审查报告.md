## 1. 执行摘要

**一句话结论：四个重型域中，容器拖拽主链路与 tiptap 击键热路径是教科书级实现，但「隐藏面板全存活」「卡片链 memo 全线缺失」「编辑实例挂在虚拟窗口内」三个结构性问题在各自域内构成规模化悬崖。**

- **终端域（X）**：PTY 进程生命周期管理自洽（无孤儿、无泄漏、拖拽期 fit 三重冻结），但**隐藏终端标签完全存活**（display:none 继续解析 PTY 输出并持有 WebGL 上下文，Chromium 上下文上限 8–16 个，耗尽即永久降级 DOM renderer）+ **PTY 数据流零合批**（每 ≤8KB chunk 一次 IPC emit + 一次 term.write）构成大输出场景主瓶颈。
- **编辑器域（E）**：击键路径 0 次 setState（150ms 防抖）、ref 桥装配、回流短路——热路径近乎满分；两个高危都在边界：**编辑实例挂在虚拟化窗口内**（滚动/流式窗口位移 → 编辑器销毁重建、焦点/IME/undo 栈全丢）+ **水合路径无 IME 守卫**（中文合成期注入即打断输入）。
- **容器域（C）**：主 sash 拖拽链路 0 setState/帧 + rAF + DOM map 缓存，架构声明成立；缺口在 RO 侧通道（`useTreeResize` 未接 `beginLayoutInteraction`，拖拽期间每 leaf 每帧 setState）与**SessionRow memo 被内联对象 props 击穿**（tick/重命名/拖拽指示每次变化全量行重渲染）。
- **卡片域（T）**：工具卡片链是四域中防护最弱的——**8 个核心组件无 memo**、`expandedTools` 单对象击穿全列表、流式文本注入每张卡片（流式期间每帧全部卡片 reconcile）、卡内每渲染重复 JSON.parse/正则/diff 统计。run 期间点击一次卡片展开 = 全列表所有卡片整树重渲染。

**发现计数**：9 高（X1 X2 X3 E1 E2 C1 T1 T2 T3）/ 13 中（X4–X8 E3 E4 C2–C5 T4–T8）/ 12 低或信息项。

## 3. 各域链路现状

### 3.1 终端域链路

```text
Rust pty-read 线程（8192 字节/read，无合批）
  → emit 'workbench://pty-output'（每 read 一次 IPC）
  → ptySessionApi 全局单 listener fan-out（Set<handler> 逐个调用）
      ├─ recordPtyOutputHistory：256KB 环形缓冲（每 chunk 全量 UTF-8 编码计量）
      └─ ptyLifecycle 订阅 → 按 ptyId 过滤 → term.write(chunk)
  → xterm 解析 → WebGL renderer（onContextLoss 后永久 DOM renderer）
```

- PTY 生命周期策略 A：卸载/切 session **不** kill PTY（`ptyLifecycle.ts:380-386`），仅关标签/关分屏/restart 杀（`TreeLeafPanel.tsx:253-267`）——切 tab 零延迟的代价是 PTY + 256KB 历史 + xterm scrollback 常驻。
- xterm 实例随组件卸载销毁重建；折坞再开 = 实例重建 + 256KB 历史重放。

### 3.2 编辑器域链路

```text
ChatCard（每 chat 视图卡 1 个）
  ├─ mainComposerElement（常驻 ChatComposer → TiptapComposerFieldLazy → TiptapEditorField → useEditor）
  └─ editComposerElement（editingMessageId 时第二个 ChatComposer，原位挂到被编辑消息行内）
击键：PM transaction → onUpdate（仅重置 150ms 防抖计时器，0 setState）

受控回流：content prop → lastContentRef 等值短路（打字路径跳过）；不等值 → rAF → parseFromMarkdown → setContent（全量重解析）
```

#### X1.【高】隐藏终端标签完全存活：继续解析 PTY 输出并持有 WebGL 上下文

- **位置**：`src/components/binary-tree/TreeLeafPanel.tsx:490-514`（display:none 挂载）；`src/components/workspace/ptyLifecycle.ts:311-318`（订阅无可见性判断）
- **现象**：tabMode 下非活跃终端 tab 仅切 `display:none`，React 树、xterm 实例、PTY 订阅、WebGL 上下文全部存活；输出链路不做可见性判断。
- **代码现场**：

```tsx
// TreeLeafPanel.tsx:494-514
dock.openPanelIds.map((pid) => {
  const isActive = pid === toolPanelId;
  return (
    <div key={pid} className={styles.dockPanelPane}
      style={{ display: isActive ? 'flex' : 'none', ... }}
      aria-hidden={!isActive}>
      {renderToolOutlet(pid)}          {/* ← 隐藏面板全量挂载 */}
```

```ts
// ptyLifecycle.ts:311-318 —— 隐藏终端同样持续 write
const unsubOut = subscribePtyOutput((p) => {
  if (cancellation.isCancelled() || p.ptyId !== activePtyId) return;
  term.write(p.data);                // ← 无可见性检查
});
```

- **调用链与触发时机**：打开 K 个终端标签 → K 路订阅常驻；任一 PTY 输出 → 全部存活终端的 fan-out（见 X4）→ 活跃终端 write 之外，隐藏终端也各自 write（仅 ptyId 不匹配的才跳过——注意隐藏终端自己 ptyId 匹配时照常 write）。
- **根因**：面板保留策略「内存换切 tab 零延迟」未对**终端这种持续产出的重型组件**做差异化处理。
- **影响量化**：每个隐藏终端 = VT 解析 CPU + 5000 行 scrollback 增长 + 1 个 WebGL 上下文。Chromium 单页活动 WebGL 上下文上限 8–16 个，**超限强制丢最旧上下文 → `onContextLoss` → 永久降级 DOM renderer**（与 X3 叠加）。16 PTY 满载 + 各持 256KB 历史缓冲 ≈ 4MB 字符串 + xterm 内部缓冲双份。
- **修复方案**：对非活跃终端 tab：① 停止 `term.write`（改入 pending 队列，激活时一次性 flush——历史环形缓冲已保证数据不丢，重放路径现成，见 X8 的 `getPtyOutputHistory`）；② 评估 WebglAddon 的按需卸载/重载（激活时 `loadAddon`，隐藏时 dispose，代价是重挂 ~10ms 级）或至少把「隐藏终端不持有 WebGL」作为目标。
- **回归风险**：切回 tab 后输出完整性（历史重放 + 增量衔接）；并发输出场景的队列顺序。

#### X2.【高】PTY 数据流零合批：每 ≤8KB chunk 一次 IPC emit + 一次 term.write

- **位置**：后端 `apps/agent-workbench/src-tauri/src/pty/session.rs:461-507`（read 循环即 emit）；前端 `src/api/ptySessionApi.ts:337-366`（listener）→ `ptyLifecycle.ts:314`（write）
- **现象**：`cat` 大文件 / 高噪声构建日志时，ConPTY 吐出速率数十 MB/s，每秒数百到上千次「Rust read → 序列化 → Tauri emit → JS parse → fan-out → 历史记录（含编码）→ term.write」全链路，无任何时间窗合批。
- **代码现场**：

```rust
// session.rs:464-507 —— 每次 read 立即 emit
loop {
    match reader.read(&mut buf) {          // buf = [0u8; 8192]
        Ok(n) => {
            let data = decoder.push(&buf[..n]);
            if !data.is_empty() {
                let _ = app_reader.emit("workbench://pty-output",
                    PtyOutputEvent { pty_id, data });   // ← 无 2ms/64KB 累积窗口
```

```ts
// ptyLifecycle.ts:314 —— 每 chunk 直接 write，无 batch
term.write(p.data);
```

- **调用链与触发时机**：高频 IO 场景（构建、日志刷屏）持续触发；多终端同时输出时 fan-out 循环 ×N（X4 叠乘）。
- **根因**：读循环与 emit 一比一耦合，缺少「微批聚合」层（对照：聊天 token 流有 48ms batcher + rAF 帧预算，PTY 流什么都没有）。
- **影响量化**：每 chunk 一次宏任务调度 + 一次 Tauri IPC 序列化/反序列化 + 一次 UTF-8 编码计量（X5）。1000 chunk/s 时仅调度开销即 5–15ms/s 主线程占用，再加 term.write 队列膨胀；前端事件循环被高频小任务切碎，影响同页其他渲染。
- **修复方案**：后端聚合——read 循环内累积到 64KB 或 2ms 窗口再 emit（Rust 侧 10 行改动，收益最大）；或前端 `listen` 回调内 8–16ms 时间窗合批后一次 `term.write(joined)`。xterm write 队列本身会缓冲，合批只减少调度与 IPC 次数，无正确性风险。
- **回归风险**：输出顺序（合批保持 chunk 顺序即可）；退出事件与最后一批输出的先后（exit 前必须 flush）。

#### X3.【高】WebGL 上下文丢失永久降级 DOM renderer，静默无恢复无观测

- **位置**：`src/components/workspace/useXtermTerminal.ts:272-284`
- **代码现场**：

```ts
try {
  const webgl = new WebglAddon();
  webgl.onContextLoss(() => {
    try { webgl.dispose(); }            // ← 丢弃后没有重新 loadAddon / 上报
    catch { /* swallow-ok */ }
  });
  term.loadAddon(webgl);
} catch {
  // swallow-ok: WebGL 不可用时静默降级 canvas 2d   ← 无日志无遥测
}
```

- **调用链与触发时机**：构造失败（WebGL 不可用）或运行中 context loss（X1 的上下文耗尽是最常见诱因）→ 该终端实例余生固定 DOM renderer。
- **根因**：降级路径只有 dispose，没有恢复（重新 loadAddon）与观测（日志/遥测/用户提示）。
- **影响量化**：DOM renderer 全量重绘（如主题刷新 `term.refresh(0, rows-1)`，X7）成本约为 WebGL 的一个数量级；降级发生完全不可知，性能悬崖无诊断入口。
- **修复方案**：contextLoss 后延迟重试 `loadAddon(new WebglAddon())`（限重试次数）；降级时 `logger.warn` + telemetry 埋点（conex-telemetry 已有基建）；构建失败路径同样记日志。
- **回归风险**：低（恢复失败仍落到现有降级行为）。

#### X4.【中】每个输出事件广播给所有已订阅终端再按 ptyId 过滤

- **位置**：`src/api/ptySessionApi.ts:34-48, 354-365`（fan-out 结构）；`ptyLifecycle.ts:312`（过滤）
- **代码现场**：

```ts
for (const h of entry.handlers) {       // ← 单 listener，Set<handler> 全量调用
  try { h(payload); } catch (err) { logger.warn(...) }
}
// ptyLifecycle.ts:312
if (cancellation.isCancelled() || p.ptyId !== activePtyId) return;   // ← 各自比对丢弃
```

- **根因**：全局单 listener 是正确的（避免每终端一个 listen），但分发缺少 ptyId → handler 的索引。
- **影响量化**：单 chunk O(存活终端数)；16 终端满载 + X2 的高频 chunk 时是乘法项；`logger.warn` 在异常 handler 上可能放大。
- **修复方案**：`Map<ptyId, Set<handler>>` 索引分发，O(1) 命中；保留全量兜底（ptyId 未注册时）。
- **回归风险**：低（分发语义等价）。

## 6. 量化分析（核心问答）

### Q1. 一次「点击工具卡片展开」到底渲染多少东西？

点击 → `toggleTool` → `expandedToolsBySession` 新对象 → 全列表所有助手行比较失败 → 每条助手消息整树重渲染 → 每张卡片渲染体裸跑 T4 的 6 项派生计算（含 `JSON.parse(arguments)` + `toolDiffLineStats` 全文扫描）。50 消息 / 200 卡会话：**200 张卡 × 各自 O(arguments+output) 计算 + 200 次组件渲染**，单次点击 5–20ms 级主线程占用。修复 T1（per-message 粒度）后降为单卡。

### Q2. 流式 run 期间（正文 + 工具并发），每帧的卡片侧开销？

每 rAF 帧：`streamText` 变 → T3 的 `streamingTextContent` 注入全部卡片 → 全部卡片 reconcile（叠加 01 报告 H1/H2/M3/M4/M5 的全文计算）。若 run 期间用户点开过卡片，还叠加 T1 的全列表基线。**流式 + 卡片密集是当前最差场景**，预计每帧 3–8ms（长输出 + 多卡）——01 批次 A + T1/T3 修复后可降一个数量级。

### Q3. 隐藏终端的「真实存活成本」？

每隐藏终端：PTY 订阅活着（X1）+ 输出时 term.write VT 解析 + 5000 行 scrollback + 1 个 WebGL 上下文 + 256KB 历史。缓解面：`display:none` 无布局盒 → RO 不触发 → fit/测量被 CSS 冻结（C9）。最坏场景：16 终端 × 满历史 ≈ 4MB 字符串 + 16 WebGL 上下文（>上限，先开的前几个已被强制降级 DOM renderer 且无人知晓——X3）。

### Q4. 拖拽分栏时的每帧账单（修复前后）？

- 主 sash（现状）：0 setState/帧（P1）+ 2–8 次 PaneHeader setState/帧（C2，RO 侧通道）+ 全树 immutable 重算/DOM 写（C5 级别低危）+ 终端 fit 完全冻结（P4）。
- 侧栏/坞宽拖拽（现状）：每 pointermove 一次 layout（C3 无 rAF）+ 0 setState。
- 修复后（C2/C3）：全拖拽路径 0 setState/0 事件级 layout，RO 全挂起——与架构声明完全一致。
