## 一、结论摘要

启动链路的**架构骨架明显健康**：双 SQLite 并发装配（ACT-102）、restore 异步化、窗口握手看门狗、前端单拍入口（ACT-301）、水合软超时 + Late-Arrival（ACT-401/406）、会话正文懒水合 K=5（ACT-502，**已消解 03 报告 I2 的 2×N 风暴**）、xterm/tiptap code-split、FCP 前 Worker=0、PTY GC 惰性拉起——这些正面发现构成防回潮基线。

结构性问题集中在**两处击穿**：

1. **首屏静态依赖图被 catalog 击穿**：生产 dist 的 entry 静态 import 闭包合计 **≈1709 KiB**，其中 `chat-provider-catalog` **550.5 KiB 以静态边进入 entry**（ACT-304「模型目录惰性加载」意图被 `App.tsx → firstRunWizardLib / AppGlobalDialogs → providerProfiles` 与 `chat-bridge-transport ↔ catalog` 互 static 边击穿）。首屏 parse 必付，且现有 `check-startup-budget` 门禁只锚 entry 单文件（497.4 KiB），**不约束静态图总和**。
2. **壳 setup 串行链过长**：`db → workspace → pairing token → CoreRunState::new（含全量引擎装配）→ …` 大段同步在 setup 闭包；其中 `EngineHandle::build` 在窗口可见前完成全量工具注册 / BrowserSlot / ComputerSlot / Timer / WaitChannel 装配。restore 已异步，但 setup 返回前的同步段仍是首窗可用的关键路径上限。

**一句话**：启动架构（并发库、异步 restore、K=5 懒水合、软超时水合）是一流的；但首屏静态图 ≈1.7 MB（catalog 550 KB 静态边）与 setup 同步段过长，是当前两大真实启动税。

**发现计数**：共 **27** 项登记——**3 高 / 11 中 / 5 低 + 8 正面**（另 3 条交叉移交 03/02/11）。

## 三、问题发现（八要素）

### 域 A · 前端首屏 bundle 与静态依赖图

---

#### A1.【高】entry 静态 import 图 ≈1709 KiB：`chat-provider-catalog` 550 KiB 以静态边进入首屏

- **位置**：`apps/crish-desktop/src/App.tsx:20` · `apps/crish-desktop/src/components/firstRunWizardLib.ts:8-12` · `apps/crish-desktop/src/app/AppGlobalDialogs.tsx:6` · `apps/crish-desktop/vite.config.ts:754-815` · dist manifest entry `imports`
- **代码现场**：

```ts
// App.tsx:20 — 静态 import，无 lazy
import { shouldShowFirstRunWizard } from './components/firstRunWizardLib';

// firstRunWizardLib.ts:8-12
import {
  normalizeModelIds,
  anyProfileHasKey,
  type ProviderProfile,
} from '../api/providerProfiles';   // ← 被 manualChunks 归入 chat-provider-catalog

// AppGlobalDialogs.tsx:6 — 同样静态拉 providerProfiles
import { getActiveModelId, getActiveProfileId } from '../api/providerProfiles';
```

- **调用链**：`entry → App → firstRunWizardLib|AppGlobalDialogs → providerProfiles → (catalog chunk) → chat-bridge-transport / vendor-react / workers / zustand`；manifest 实证 entry 静态 import catalog + transport。
- **根因**：ACT-304 把 `providerProfiles`/`modelCatalog*` 切成 `chat-provider-catalog` chunk 并宣称「惰性加载」，但 **App 静态边**与 **transport ↔ catalog 互 static import**（manifest：catalog imports transport；transport imports catalog）使 chunk 虽独立文件名，仍在首屏静态 parse 闭包内。`manualChunks` 只改打包分组，**不切断静态依赖**。
- **影响量化**：冷启动 WebView 必须下载+parse ≈1.7 MB JS（未 gzip）；catalog 550 KiB 单块即超软预算本身。低端机首帧 parse 与 IPC 探测争主线程，TTI 显著劣化。对比：xterm/tiptap 430/409 KiB 因真 lazy 未进静态图——证明分包策略有效，问题在静态边。
- **修复方案**：
  1. **断静态边**：`firstRunWizardLib` 对 `anyProfileHasKey`/`normalizeModelIds` 改动态 import 或抽「轻量 key 探测」到不进 catalog 的小模块；`AppGlobalDialogs` 内 `getActiveModelId` 仅在向导/对话框打开时调用，改为组件内 `await import`。
  2. **断 transport ↔ catalog 互边**：catalog 侧 types/常量下沉 `modelCatalogTypes`（已在拆分清单）；transport 依赖的 `getActiveModelId` 改注入或轻量旁路模块，禁止 transport 静态 import catalog chunk 成员。
  3. **门禁补强**：`check-startup-budget` 增加「静态图总和」软/硬阈值（建议软 900 KiB / 硬 1200 KiB，待基线冻结），与 entry 单文件 520 KiB 双轨。
- **回归锚点**：`scripts/check-startup-budget.mjs` 静态图合计断言；`noWaterfallOrchestrator.test` 扩展为「entry manifest imports 不得包含 chat-provider-catalog」。
- **严重度判定**：高——首屏 parse 体积翻倍以上，且门禁现无法拦截。

#### A2.【高】启动体积门禁只锚 entry 单文件，静态图 1709 KiB 信息展示不 fail

- **位置**：`scripts/check-startup-budget.mjs:221-224,260-266`
- **代码现场**：

```js
// 主预算锚定：isEntry 产物文件本身；静态图合计仅信息展示
const entryFileBytes = rows.filter((r) => r.isEntry && r.bytes != null)
  .reduce((s, r) => s + r.bytes, 0);
// …
if (entryFileBytes > budgetBytes) { /* warning */ }
// 静态图 totalBytes 从未进入 warnings/errors
```

- **影响量化**：entry 497.4 KiB ≤ 520 KiB → OK；但用户实际首屏成本 ≈ entry + 8 个静态 vendor/business chunk = 1709 KiB。门禁绿灯与真实首屏税脱节约 **3.4×**。
- **修复方案**：`totalBytes`（静态闭包）进入软预算（env `STATIC_GRAPH_BUDGET_KB`，缺省建议 900）；`--strict` 下超限 exit 1。与 A1 修复联动：断边后合计应显著下降再冻结基线。
- **回归锚点**：同脚本输出「静态 import 图合计」行 + CI job。
- **严重度判定**：高——门禁失灵使 A1 类回归可无声合入。

#### A3.【中】`vendor-highlight` 108.6 KiB + `vendor-hugeicons` 117.3 KiB 随静态图首屏加载，首帧无消费路径

- **位置**：`apps/crish-desktop/src/api/codeHighlight.ts:13-34`（17 语言全量注册）；`components/ui/icons/iconMap.ts:10,154`（`@hugeicons/core-free-icons` 大表）；manifest：二者均在 entry 静态 imports。
- **调用链**：highlight 经 `markdownCodeFence` / Diff / File 等**打开卡片后**才需要；hugeicons 经 AppIcon/Sidebar 首屏有图标需求但 free-icons 全量包可拆。静态图反向依赖显示 `platformDetect`/`lightweightMode`/`skillsApi` 等 idle 模块也静态引用 highlight chunk（构建图层面把它们并进静态闭包贡献者集合）。
- **根因**：`optimizeDeps.include` 强制预打包 `highlight.js`（vite.config.ts:717）+ 无按语言动态注册；hugeicons 无 per-icon 分包策略。
- **影响量化**：两 chunk 合计 226 KiB 纯 parse/下载税；highlight 首帧渲染（空会话/无代码块）零收益。
- **修复方案**：`codeHighlight.ts` 改动态 `import('highlight.js/lib/languages/…')` 按首块语言懒注册；hugeicons 收敛 iconMap 到首屏必需子集，其余视图 chunk 内局部 import。
- **回归锚点**：静态图中不得出现 `vendor-highlight`（打开 Diff 前）；图标 bundle 按视图拆分后的体积断言。
- **严重度判定**：中——可延后到 A1 断边后一并处理。

#### A4.【中】`preloadHydrationSnapshot` 在 createRoot 前阻塞，软超时 400ms 成为 TTI 下限的一部分

- **位置**：`apps/crish-desktop/src/entry-core.tsx:141-152` · `UnifiedAppHydrationCoordinator.ts:143-147,284-302`
- **代码现场**：

```ts
const snapshot = await coordinator.preloadHydrationSnapshot(); // 等 IPC 或 400ms
markStartupPhase('preloadSnapshotDone');
coordinator.applyAtomicCommit(snapshot);
const root = createRoot(rootElement);
```

- **调用链**：`getSettings` + `getAllPreferences` 两次 IPC + `waitLayoutTreeHydration`（zustand rehydrate）进 `Promise.allSettled`；任一慢则整包等满 400ms（双核 800ms）才 fallback 挂载。
- **根因**：ACT-401「单拍原子 Commit」把 settings/layout 注入锁在 createRoot 前，换取零闪变；代价是 **TTI ≥ min(IPC 延迟, 软超时)**。设计取舍明确（有 Late-Arrival），但软超时无用户可感知进度（loader 已内联，体感仍是等）。
- **影响量化**：常规机 IPC <50ms 时几乎无感；冷盘/杀软扫描下 settings IPC >400ms 时，**每次启动固定 +400ms** 才出 React 树。静态分析，待运行时 crishStartupReport 回填 preloadSpan 分布。
- **修复方案**（不降级效果锁，只提供选项）：
  1. 保持 400ms，但把 `getSettings`/`getAllPreferences` 合并为单命令或 Rust 侧 startup snapshot 一次往返（契约评审，归 03 批次 M 邻域）。
  2. 探索「骨架屏立即 createRoot + 主题从 loader DOM 镜像直接读」路径：`bootstrapTheme` 已继承 loader 属性；仅 sidebar/tabMode 等次要字段走 Late-Arrival——需产品确认无闪变风险。
- **回归锚点**：`crishStartupReport` 的 `preloadSpan` / `ttiFromEntry` P50/P95。
- **严重度判定**：中——设计内代价，但值得量化与合并 IPC。

### 域 B · Tauri 壳初始化串行链

---

#### B1.【高】`CoreRunState::new` 在 setup 同步路径完成全量引擎装配（工具注册 / Browser / Computer / Timer / Wait）

- **位置**：`main.rs:902-917` · `run/run_core.rs:376-410` · `engine_build.rs:202-379+`
- **代码现场**：

```rust
// main.rs:902 — setup 闭包内同步构造
let core_state = Arc::new(core_run_commands::CoreRunState::new(...));
// run_core.rs:395 — EngineHandle::new_with_spawner → build()
// engine_build.rs:317-379 — ToolRegistry::new + register_builtin_tools_with_config
//                            + BrowserSlot::new + browser tools 注册 + ComputerSlot …
```

- **调用链**：setup 线程 → CoreRunState::new → EngineHandle::build → 内置工具全量注册、BrowserSlot、ComputerSlot、TimerRegistry（含 `Handle::try_current` 下 spawn restore）、WaitChannel、SchedulerRegistry、audit sink、HTTP client 构造。完成后才 `manage` 并 spawn restore。
- **根因**：装配完整性优先（工具/槽位在首 run 前必须存在）；但「存在」≠「完成重 I/O/大 HashMap 构造」。BrowserSlot 注释写「惰性启动」（engine_build.rs:357-359），与 ToolRegistry 全量同步注册并存。
- **影响量化**：静态分析：注册数十工具 + 构造 reqwest client + 槽位单例，估算 setup 同步段数十至数百 ms（磁盘冷缓存更高）。该段直接推迟 setup 返回 → 推迟窗口可交互依赖的 state 就绪面（虽 db_ready 已提前置位，命令面仍要 manage 完成）。待运行时 tracing `elapsed_ms` 回填。
- **修复方案**：
  1. **分级装配**：`EngineHandle::build` 拆「轻核（HTTP client + 空 ToolRegistry + 事件通道）」与「重注册（builtin tools + browser/computer）」——轻核同步 manage，重注册 `spawn` 到 runtime，首 run 前 `ensure_tools_ready().await` 门闩（run 路径已有 restore_ready 先例可复用模式）。
  2. BrowserSlot / ComputerSlot 构造若仅占位，改为 `OnceLock` 首次访问初始化。
  3. 保持 restore 异步与 mark_initialized 语义不变（效果锁：工具面行为不减）。
- **回归锚点**：壳测「轻核 manage 后 50ms 内可 invoke core_get_status」；工具注册数断言不变；首 run 工具可用性 e2e。
- **严重度判定**：高——setup 同步段是窗口后首命令可用的硬上限之一。

#### B2.【中】WorkspaceRegistry / TokenStore / Auth 串行在双 DB 之后，可与 DB open 并行

- **位置**：`main.rs:745-776`（DB）→ `:779-792`（workspace）→ `:832-847`（pairing token）→ `:855-857`（auth）
- **根因**：历史顺序「先有 app_dir 再逐项 init」；workspace/pairing/auth 与 sessions.db 打开无数据依赖（均只依赖 app_dir 路径）。

- **回归锚点**：db_setup 测试扩展为四路 join 成功；诊断环形缓冲字段不变。
- **严重度判定**：中。

### 域 C · 引擎 boot 与事件桥

---

#### C1.【正面】restore 异步 spawn + 失败不阻塞启动

- **位置**：`main.rs:919-927` · `run/run_snapshot.rs:131-249`
- **证据**：`tauri::async_runtime::spawn` 执行 `run_restore`；失败仅 diagnostics + 懒 `base_sequence_for` 兜底。
- **禁止回潮**：setup 不得同步 `block_on(run_restore)`。

---

#### C2.【中】restore 成功路径逐会话重建 SessionTree + coordinator + 通知重排，串行 for 循环

- **位置**：`run_snapshot.rs:179-220`
- **代码现场**：

```rust
for record in &outcome.sessions {
    let tree = SessionTree::from_session_record(record.clone())...;
    self.session_trees.lock()...insert(...);
    if let Some(coord) = self.coordinator_for(&record.session_id) {
        let mut c = coord.lock().await;
        c.restore_steering_notifications()
    }
}
```

- **影响量化**：N 个恢复会话 = N 次锁 + N 次 await 通知重排；大会话树 clone（`from_session_record(record.clone())`）放大 CPU/内存。异步任务内不阻塞 UI，但拉长「引擎真正可续跑」窗口。
- **修复**：树构建纯 CPU 段 `spawn_blocking` 批处理；通知重排对多会话 `JoinSet` 并行（注意 pending 队列锁粒度）。
- **回归锚点**：restore 集成测（中断 N 会话）耗时基线；行为：阶梯 1/2/4 照常、fork 结构化拒绝不变。
- **严重度判定**：中。

## 十、运行时验证操作细则（回填模板）

> 下列步骤在**生产包**（`npm run build` 后 Tauri debug/release）上执行；**禁止**用 `http://localhost:5174` 浏览器会话代替（AGENTS §15.3）。调试通道唯一合法 = **4000 Tauri MCP**。

### V1 · 静态图下载与 parse

1. 干净冷启动生产包（可先清 WebView 缓存目录做「冷」样本）。
2. 经 Tauri MCP 取 Performance / Network：记录 entry + 8 个静态 chunk 的下载完成时刻与 ScriptEvaluation 结束时刻。
3. 记录字段：`bytes_static`、`parse_ms`、`compile_ms`、`first_paint`、`dom_contentloaded`。
4. **通过判据**（断边后）：静态图合计 <900 KiB；catalog 不出现在首屏 Network 直到 idle / 打开模型选择。

### V2 · crishStartupReport 采样

1. 应用内 WebView 控制台（MCP evaluate）：`crishStartupReport({ history: true })`。
2. 连续冷启动 ≥10 次，取 `preloadSpan / ttiFromEntry / coreReady / bootstrapFullDone / shellReady` 的 P50/P95。
3. 记录 `preload-timeout-fallback` 是否出现（软超时是否打满）。
4. **通过判据**：常规机 TTI P50 <800ms（待基线冻结后收紧）；fallback 率 <10%。

### V3 · setup 同步段

1. Rust 侧对 `db_setup` / `WorkspaceRegistry::init` / `CoreRunState::new` / `EngineHandle::build` 包 `Instant::now()` tracing（若尚未有则临时加，合入前按仓库纪律）。
2. 记录 setup 返回前各段 `elapsed_ms` 与窗口 `show` 时刻差。
3. **通过判据**：引擎重注册移出同步路径后，`CoreRunState::new` 轻核段 <20ms（NVMe 常规机）。

### V4 · 启动 IPC 计数

1. 在 `invokeResult` / `tauriInvoke` 包装层打计数（或 MCP 侧消息计数）。
2. 冷启动至 `paneQueueIdle`：断言 `load_session_body` ≤1、`read_session_events` ≤1（每 active session）、`list_sessions` ≤1、`getSettings` ≤1、`getAllPreferences` ≤1。
3. **通过判据**：无双拉；D3 修复后计数不变差。

### V5 · restore 耗时

1. 构造含 ≥20 interrupted 会话的 snapshot（或真实大会话用户）。
2. tracing `target=restore`：mode、interrupted 数、总耗时。
3. **通过判据**：异步 restore 不推迟窗口 show；树重建并行化后耗时下降可测。
