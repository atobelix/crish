#### B1.【高】catalog 550.5 KiB 静态边未断，且 modulepreload 把它写进首屏预取清单

- **位置**：`apps/crish-desktop/dist/.vite/manifest.json`（entry imports / modulepreload）· `apps/crish-desktop/dist/index.html`（构建产物）· 源头（07 已定位，未修）：`apps/crish-desktop/src/App.tsx:20` · `src/components/firstRunWizardLib.ts:8-12` · `src/app/AppGlobalDialogs.tsx:6` · `src/api/chat-bridge/readiness.ts:12` · `vite.config.ts:754-815`
- **代码现场**：

```ts
// firstRunWizardLib.ts:8-12（07-A1 原现场，仍然静态）
import { normalizeModelIds, anyProfileHasKey, type ProviderProfile }
  from '../api/providerProfiles';   // → manualChunks 归入 chat-provider-catalog

// readiness.ts:12 — transport 侧静态反向边
import { getActiveModelId, getActiveProfileId } from '../providerProfiles';
```

```html
<!-- dist/index.html 构建产物（modulepreload 片段） -->
<link rel="modulepreload" href="/assets/chat-provider-catalog-DQHM7wt8.js">
<link rel="modulepreload" href="/assets/vendor-highlight-F2iis0FW.js">
<!-- …共 8 条，见素材 §3 -->
```

- **调用链**（两条同时成立）：
  1. 网络层：`index.html → modulepreload → catalog.js（550.5 KiB 下载）`；
  2. 解析层：`entry index.js → 静态 import catalog → parse/eval 必付`；且 `catalog ↔ transport` 互 static 边仍在（manifest 双向 imports 实证）。
- **根因**：ACT-304 的 manualChunks 只改「打包分组」，不切断静态依赖（07-A1 根因复述）；本方向补充：Vite 对静态 import 的 chunk 自动发 `modulepreload`，使「静态边」获得网络层杠杆——断边不彻底时 preload 会把惰性意图再次击穿。`AppGlobalDialogs`/`firstRunWizardLib`/`readiness` 三处静态 import `providerProfiles` 是 preload 条目存在的直接上游。
- **影响量化**：冷启动首屏 JS 静态闭包 1709.3 KiB 中 catalog 占 **32.2%**；modulepreload 保证这 550.5 KiB 与 entry 497.4 KiB 并行下载但**串行 parse 预算内**。低端机（参考 07 V1 判据）首帧后主线程 parse ≈1.7 MB 未压缩 JS。修复后（07 批次 S 目标）静态图 <900 KiB，catalog 仅在 idle/打开模型选择时出现。
- **修复方案**（与 07-A1 同向，本方向补充三点）：
  1. 落地 07 批次 S 断边：`firstRunWizardLib` 轻量 key 探测下沉；`AppGlobalDialogs.getActiveModelId` 改打开时 `await import`；`readiness` 依赖注入或轻量旁路模块（断 transport↔catalog 互边）。
  2. 断边后用 `vite build` 复查 manifest：entry `imports` 与 `index.html` modulepreload **均不得**再出现 `chat-provider-catalog`。
  3. preload 白名单门禁（并入 B2 修复）：check-dist 断言 modulepreload 集合 ⊆ 静态图允许清单（可配置）。
- **回归锚点**：`check-startup-budget` 静态图合计断言（B2）；`entry manifest imports 不含 chat-provider-catalog` 单测（07 已建议，仍未见落地）；modulepreload 列表快照测试。
- **严重度判定**：高——首屏 32% 体积税 + 网络预取双重钉死；07 已高危登记，一个审查周期后仍未修，保持高。

- **调用链**：CI/本地跑 `check-startup-budget` → 只对 entry 文件比较 520 KiB → 打印 OK；`check-dist` 对 index 497.4 < 500 → OK；`chunkSizeGatePlugin` 对 catalog 550.5 < 600 → 构建放行。三条绿灯叠加下，**1709.3 KiB 静态图、750.6 KiB CSS、5.12 MiB dist 总量全部无守卫**。
- **根因**：门禁体系按「单文件最大 chunk」时代设计；三元解构后真实首屏成本=静态图总和，门禁语义没有跟随升级。check-dist 的 500 KiB 目标是「App 拆分达成线」，被复用为唯一硬断言后形成假安全感。

- **修复方案**：
  1. check-startup-budget：`totalBytes`（静态图 JS）进入软预算 `STATIC_GRAPH_BUDGET_KB`（缺省 900，断边完成前可先 1800 软 warning），`--strict` 下超限 exit 1；输出保持现有信息行格式。
  2. check-dist 增三类断言：① modulepreload ⊆ 允许清单；② entry css ≤ `MAX_ENTRY_CSS_KB`（建议 280 起步）；③ `dist` JS 总量 ≤ `MAX_DIST_JS_KB`（基线冻结后定）。
  3. entry 500 KiB 断言保留但与静态图双轨；断边完成后评估把 entry 目标降至 450 并冻结基线。
  4. 与 07 批次 S 验收合并：断边 PR 必须同 PR 更新静态图基线数字。
- **回归锚点**：上述 env 阈值 + CI job 输出行；`chunkSizeGatePlugin` 保持 600 单 chunk 硬线不变（防巨型 chunk 回潮）。
- **严重度判定**：高——门禁失灵使 B1/B3 类回归可无声合入；且 entry 余量已薄到「修复性 CI 爆炸」边缘。

### 9.5 术语表

| 术语 | 含义 |
| ---- | ---- |
| 静态图（static graph） | entry 经静态 `import` 可达的 chunk 闭包（不含 dynamicImports）；首屏 download+parse 必付面 |
| modulepreload | Vite/Rollup 对静态 import chunk 生成的 `<link rel="modulepreload">`，HTML 解析期触发预取 |
| 杂物抽屉 chunk | chunk 名与实际内容域不符：manualChunks 路径分组 + 共享模块归置导致多域代码焊入同一文件 |
| 指纹级归因 | 用 minified 产物中稳定字符串判断模块域归属，精度到「域」不到「单模块字节」 |
| 会话首开税 | 首次打开/新建会话时，相对静态图额外加载的 JS/CSS（本报告 B4） |
| 双轨门禁 | entry 单文件预算与静态图总和预算并行；防止单锚点失真 |
