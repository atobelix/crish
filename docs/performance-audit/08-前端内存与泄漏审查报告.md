## 一、结论速览

| 维度 | 判定 |
| ---- | ---- |
| 事件监听 / Observer / rAF 对称性 | **健康**（系统性泄漏未发现） |
| zustand 会话域内存 | **结构性风险高**：双持久化全量序列化 + 非活跃消息不驱逐 |
| streaming 残留 | **健康**（收口 microtask clear + 删会话级联） |
| 重型实例（xterm/tiptap/markdown） | 生命周期基本对称；隐藏终端存活归 02 X1，本方向补内存账 |
| 工具输出 | store 全文驻留 + 展示层再拷贝，无 store 侧字节上限 |
| Worker | 默认池收缩到位；taskQueue 无上限；生产路径少用 transferable |
| 内存压力响应 | 仅清 idle queue + LRU shrink，未覆盖会话消息/PTY/streaming |

**发现计数**：6 高（H1–H6）/ 10 中（M1–M10）/ 8 低（L1–L8）+ 8 正面（P1–P8）。

**一句话结论**：监听器与流式清理纪律健康，但会话域「双持久化全量 JSON 序列化 + 已水合消息永不驱逐 + 工具输出无界驻留」构成长会话场景下的系统性内存增长主因。

**TOP3 高危**：
1. **H1** sessionStore zustand persist 与 SQLite 双写：任意 set 触发全量 sessions（含消息正文）JSON.stringify 进 localStorage  
2. **H2** 非活跃会话已水合 messages 永不驱逐：多会话切换后全文并存内存  
3. **H3** 工具输出 store 侧无字节上限：长 shell/FS 输出全文进 MessageToolCall.output，展示层再 ×2–3 份

### 2.3 M4 · 多 Agent 状态轮询 interval 并存

- **位置**：`hooks/useAgentStream.ts:361-366`
- **现场**：
  ```ts
  void poll();
  const intervalId = setInterval(() => void poll(), 4000);
  return () => { cancelled = true; clearInterval(intervalId); };
  ```
- **调用链**：每个 InlineAgentPanel 挂 useAgentStream → 每 running agent 一条 4s interval → 触发 `getSubagentRunId` / patchSessionAgent（读 sessionStore）。
- **根因**：子代理状态同步走轮询而非仅事件驱动；并发 agent 数上升时 interval 数线性增长。
- **影响量化**：N 个 agent ≈ N/4 次·s⁻¹ 读 store；内存占用小（每闭包 KB 级），CPU 归 01/12。
- **修复方案**：合并为单例轮询器（按 agent 列表扇出）；或 subagent-plane 事件已覆盖时降频/停轮询。
- **回归锚点**：单测 mock setInterval 计数；多 agent 并发 active interval ≤1。

### 2.4 L1 · PTY fanout unlisten 与 history 生命周期耦合

- **位置**：`api/ptySessionApi.ts:61-70,150-158`
- **现场**：`checkCleanupUnlisten` 要求 `handlers.size===0 && ptyHistoryMap.size===0`。
- **根因**：history 需持续 `recordPtyOutputHistory`，故 listeners 在 history 存活期间保持。
- **影响**：kill/exit 会 `clearPtyOutputHistory`（:316,:351），正常路径可回收；若 kill 失败则 history+listener 双悬挂。
- **修复**：kill 失败路径加超时强制 clear；或 history 独立于 listener 生命周期（listener 可关，history 静态保留）。
- **回归锚点**：kill 失败注入后 ptyHistoryMap.size===0。

### 2.5 L2 · WorkerPool taskQueue 无上限

- **位置**：`workers/worker-pool.ts:16,237-243`
- **现场**：`taskQueue.push` 后按 priority 排序，无 maxQueue。
- **根因**：默认仅 2 个 render worker；FCP 门闩期任务只入队。
- **影响量化**：极端积压时每个 Task 持有 payload 引用（markdown 源串等）→ 队列 MB 级驻留。
- **修复**：taskQueue 长度上限 + 溢出 reject；或对 render 任务 dedupKey 强制。
- **回归锚点**：压测 10k schedule 后 queue length 有界。

### 2.6 A 域扫描方法附录

- **命令面**：`rg -n "addEventListener|removeEventListener" apps/crish-desktop/src --type ts -g '!*.test.*'`  
- **Observer 面**：`rg -n "ResizeObserver|MutationObserver|IntersectionObserver"`  
- **定时器面**：`rg -n "setInterval|requestAnimationFrame|setTimeout"` 于 `hooks/` 与 `services/`  
- **对照标准**：每个 `useEffect` / `useLayoutEffect` 返回的 cleanup 是否覆盖该 effect 内注册的全部句柄；单例服务（ShortcutService、EngineState、WorkerPool）是否有显式 dispose 与 refcount。

## 三、域 B：zustand store 大对象驻留

### 3.0 B 域状态拓扑（导读）

```
useSessionStore (zustand + immer + withPersist)
├── sessions[] ────────────── 全量 SessionState（含 messages/agents）
├── sessionsById Record ───── 与 sessions 同引用的 O(1) 索引
├── composerDrafts ────────── sessionId → 草稿串
└── 两条持久化出口：
    ① withPersist → localStorage['crish_session_store']（同步 stringify）
    ② initStorePersistence → persistAllSessions → SQLite（350ms debounce）

useStreamingStore (plain zustand)
└── byKey[sessionId::messageId] → 热缓冲（收口后 clear）

MessageSnapshots（模块单例）
└── stacks[sessionId] → SnapshotEntry[]（messages 全量 + delta）
```

该拓扑是 H1/H2/H5 的共同结构基础：**正文一旦进入 sessions[]，在删除会话前没有「预算驱逐」出口，且被 persist 两条路径反复序列化**。

### 3.1 会话消息全量驻留模型

- **位置**：`store/sessionStore.ts:26-35,51-59`；`store/types.ts` SessionMessage
- **结构**：`sessions[]` + `sessionsById` 双索引；每会话 `messages[]` 内嵌 `toolCalls[].output` 全文、`agents[].messages[]`。
- **上限常量**：`packages/shared-utils/src/bounds.ts:1-7`
  - MAX_MESSAGES_PER_SESSION=500  
  - MAX_MESSAGES_PER_AGENT=2000  
  - MAX_AGENTS_PER_SESSION=40  
  - MAX_SESSIONS=200  

- **正面（P2）**：冷启动懒水合 —— `sessionRustDbHydrate.ts:142-239` 仅活跃会话拉 body+agents，历史 `messages: []` + `messagesHydrated: false`。

### 3.2 H1 · 双持久化：zustand persist 全量 JSON + SQLite 并行

#### 位置

- `store/sessionStore.ts:49-70`（withPersist partialize 含 sessions）
- `store/layout-helpers/store-persistence.ts:124-322`（initStorePersistence 订阅 + 350ms debounce）
- `store/middleware/withPersist.ts:19-36`（默认 zustand persist，无自定义 storage/debounce）
- `api/session-persistence/sessionRustDbHydrate.ts:292-339`（persistAllSessionsRust 探测 + 全量写）

#### 代码现场

```ts
// store/sessionStore.ts:46-71
export const useSessionStore = create<SessionStore>()(
  withDevtools(
    withLogger(
      withPersist(
        immer<SessionStore>((set, get) => ({
          sessions: [],
          sessionsById: {},
          // ...
        })),
        {
          name: 'crish_session_store',
          partialize: (s) => ({
            sessions: s.sessions,          // ← 全量 SessionState[]
            folderOrder: s.folderOrder,
            activeSessionId: s.activeSessionId,
            composerDrafts: s.composerDrafts,
          }),
        }
      )
    ),
    'SessionStore'
  )
);
```

```ts
// store/layout-helpers/store-persistence.ts:139-166（第二条出口）
const unsub = store.subscribe((state) => {
  const domain = pickSessionDomain(state);
  if (!sessionDomainChanged(lastDomain, domain)) return;
  lastDomain = domain;
  if (persistTimer) clearTimeout(persistTimer);
  persistTimer = setTimeout(() => {
    const cur = store.getState();
    void persistAllSessions(cur.sessions, cur.activeSessionId, cur.folderOrder);
  }, 350);
});
```

#### 调用链（一次消息 upsert 的完整内存路径）

```
addMessage / updateMessageToolCall
  → immer set(sessions[i].messages[…])
  → zustand persist 订阅
      → partialize 取全量 sessions
      → JSON.stringify(...)          // 临时字符串 ≈ 全部已水合正文
      → localStorage.setItem('crish_session_store', json)
  → initStorePersistence 订阅
      → 350ms 后 persistAllSessions
          → persistAllSessionsRust
              → 每会话 save_session_body IPC（再次序列化）
```

同一时刻并存：
1. 内存中的 sessions 对象图（可达数十 MB）
2. zustand persist 的 JSON 字符串（临时，GC 前峰值 ≈ 对象图序列化尺寸）
3. localStorage 内的持久 JSON（WebView 侧驻留）
4. IPC/SQLite 写路径上的再序列化缓冲

#### 根因

Stream D 将会话正文主存迁到 SQLite 后，`initStorePersistence` 成为设计内写路径；但 sessionStore 上的 `withPersist` **未收窄 partialize**，仍把 `sessions` 全量（含 messages）交给 zustand 默认 persist。两条出口并存且互不知情。

`withPersist` 仅合并 name/version（`withPersist.ts:31-36`），未注入 debounce storage，故 zustand 默认「每次 set 同步写」语义完整生效。

#### 影响量化（静态推算 · 待 V1 实测）

设活跃 + 已浏览共 M 个会话，每会话平均正文+工具输出 B 字节：

| 场景 | M | B | 估算 JSON | 说明 |
| ---- | - | - | -------- | ---- |
| 轻会话 | 5 | 50KB | ~250KB | 每次 set 一次 stringify |
| 典型长会话 | 3 | 2MB | ~6MB | 含大工具输出 |
| 浏览 10 历史 | 10 | 200KB | ~2MB | H2 使 M 增长 |

额外成本：`JSON.stringify` 主线程阻塞（6MB 字符串分配常见 10–50ms 级）+ GC 压力；与 03 IPC 序列化峰值**同源不同路径**——03 管 Rust→前端事件，本项管前端 store→LS/SQLite。

#### 修复方案

1. **首选（W1）**：`partialize` 收窄为 `{ activeSessionId, folderOrder, composerDrafts }`（或 `hydrationComplete` 标志）；正文唯一落盘路径 = initStorePersistence → SQLite。
2. 若需 LS 回退镜像：写入侧改为「仅会话索引壳（id/title/timestamp/messageCount/engineCursor）」，正文永不进 zustand persist。
3. 与 L3 注册表键名一并迁移；迁移需处理存量 `crish_session_store` 大键（启动时读入后 remove，避免 LS 配额长期占用）。

#### 回归锚点

- `localStorage.getItem('crish_session_store')` 解析后 **不得** 出现 `sessions[].messages` 非空数组；
- 构造 2MB 工具输出收口，Performance 面板无 >1MB 的 `JSON.stringify` 热点；
- boot 回灌集成测试（`sessionRustDbHydrate` / `store-persistence` 既有单测）全绿。

### 3.3 H2 · 非活跃会话已水合消息永不驱逐

#### 位置

#### 调用链

```

  → setActiveSessionId(B)
  → triggerSessionMessageHydrateIfNeeded(B)   // 若空则拉引擎
  → A 的 messages 仍完整保留在 sessionsById[A]
```

#### 根因

「切 tab 零延迟」策略（与 02 C9 / 面板全存活同哲学）在消息域没有配套的内存预算。懒水合（P2）只优化**冷启动**，不覆盖**热浏览**。

#### 影响量化

- 单会话：500 消息 ×（正文 2KB + 工具输出均值 4KB）≈ 3MB 量级（静态推算）；
- 浏览 10 个重会话 ≈ 30MB 常驻，直到删会话；
- 与 H1 叠加：每次任意 sessionStore.set 都要把这 30MB 再 stringify 一遍（若 H1 未修）。

#### 修复方案（W2）

1. `setActiveSessionId` 在 id 变更时对 **previousActive**（及可选 LRU 尾部）执行软驱逐：
   ```ts
   // 伪代码
   prev.messages = [];
   prev.messagesHydrated = false;
   // 保留 messageCount / engineCursor / pinnedMessageIds
   ```
2. 驱逐策略：仅保留 active + 最近 K-1 个已水合（K 建议 2–3）；或按估算字节预算。
3. 切回已驱逐会话 → 既有 `needsEngineMessageHydrate` / `triggerSessionMessageHydrateIfNeeded` 路径自动重拉。
4. 流式中的会话禁止驱逐（`streamingStore` 有活跃 key 时跳过）。

#### 回归锚点

- 单测：activate A→B→C 后 `sessions.filter(s => (s.messages?.length ?? 0) > 0).length ≤ K`；
- 切回 A 触发 hydrate 且消息完整；
- 流式中切走再切回不丢流（generationMap 守卫仍有效）。

### 3.4 H5（原 H6）· MessageSnapshots 全量 messages 副本 + 预算漏计

#### 位置

- `api/MessageSnapshots.ts:117-140` SnapshotEntry 结构
- `api/MessageSnapshots.ts:154-191` estimateDeltaBytes / estimateBytes
- `api/MessageSnapshots.ts:205-206` MAX_STACK_DEPTH=20 / MAX_MEMORY_BYTES=5MB
- `api/MessageSnapshots.ts:238-270` save 写入与淘汰
- 桥：`store/messageSnapshotsBridge.ts:99-110` saveMessageSnapshot

#### 代码现场

```ts
export interface SnapshotEntry {
  messages: SessionMessage[];   // ← 操作前完整副本
  delta: MessageDelta;          // ← 增量（inserted 为差异段）
  byteSize: number;             // ← 只按 estimateBytes(delta.inserted) 计
  // ...
}

export function estimateBytes(input: EstimateBytesInput): number {
  let bytes = 256;
  for (const m of input.inserted) {          // 只有 delta.inserted
    bytes += (m.text?.length ?? 0) * 2;
    // toolCalls.output / arguments …
  }
  return bytes;
}
```

#### 调用链

```
withdrawMessage / regenerate / archive / batch-pin / applyTimelineTruncate
  → saveSessionSnapshot / saveMessageSnapshot
  → MessageSnapshots.save
      → computeDiff(prev, after) → delta
      → estimateBytes(delta) → byteSize（偏小）
      → stack.push(snapshot)   // snapshot 含 messages 全量引用
      → 超 5MB 时 evictOldestUntilUnderLimit（按偏小 byteSize）
```

#### 根因

设计注释写明「附带完整副本以支持直接恢复」（:210），但容量控制只覆盖 delta 路径的字节估算，**未把 messages 全量副本计入 totalBytes**。双存储结构与单侧记账不对称。

#### 影响量化

- 真实驻留 ≈ byteSize 的 2×（messages + delta.inserted 有重叠引用时略低，但对象头/独立数组仍在）；
- 5MB 上限 → 实际可达 ~8–10MB；
- 大工具输出消息使单条 entry 的 messages 远大于 delta.inserted（truncate 丢弃旧消息时 delta 只含新插入段）。

#### 修复方案（X1）

1. estimateBytes 增加对 `entry.messages` 的独立估算并累加（或对 messages 全量与 delta 二选一记账）；
2. 评估取消 messages 全量副本、undo 仅走 delta 还原（需验证 `undo` 消费方是否依赖完整 messages）；
3. 按 V4 实测回调 MAX_MEMORY_BYTES。

#### 回归锚点

#### 4.1.1 MarkdownBlockItem 与 WeakMap 结论

- **位置**：`components/chat-message-row/MarkdownBlockItem.tsx:64-206`

2. streaming `setStreamTool` patch 同样 cap；
3. 超 CAP 时在 output 尾部标注截断标记，展开 UI 提示「完整输出见引擎/文件」；
4. 与 10-T4 口径对齐，避免双截断语义分叉。

#### 回归锚点

- 注入 2MB 工具输出：`tc.output.length ≤ CAP`；
- 单测覆盖 shell / read_file / grep 三类工具名。

### 4.4 M3 · 全局内存预算叠加无单一账本

## 十一、扫描范围与未覆盖说明

### 11.0 数组无界 push 专项补扫

任务书第 4 点要求覆盖「数组无限 push」。生产路径扫描结果：

| 结构 | 位置 | 上限 | 判定 |
| ---- | ---- | ---- | ---- |
| session.messages | addMessage + truncateMessagesForAppend | MAX_MESSAGES_PER_SESSION=500 | 有界（P） |
| agent.messages | appendSessionAgentMessage | MAX_MESSAGES_PER_AGENT=2000 | 有界但上限偏大 |
| sess.agents | upsertSessionAgent | >40 时 length=40 | 有界 |
| streaming byKey | clear on 收口/删会话 | 无硬上限，靠生命周期 | 设计内有界 |
| ptyHistoryMap.chunks | recordPtyOutputHistory | 256KB 字节感知 | 有界（P8） |
| MessageSnapshots stacks | save + evict | 深度 20 + 5MB 预算（口径有偏） | 有界（H5） |
| worker taskQueue | enqueueTask | **无上限** | L2 |
| LoggerService.buffer | pushOverwritingOldest | 环形覆盖 | 有界 |
| TelemetryService.buffer | buffer.push | 需确认 max（services/TelemetryService.ts:83） | 低危待核 |

**结论**：除 L2 taskQueue 与 Telemetry buffer 待核外，无「数组无限 push 直至 OOM」的裸奔路径；主要风险仍是**有界但上限过大 + 多会话叠加**（H2/H3）而非数学意义上的无界。
