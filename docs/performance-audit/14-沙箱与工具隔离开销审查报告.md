## 0. 阅读指南

- 编号规则：**SB**=沙箱门禁层、**SH**=shell 隔离与进程、**OP**=host openers/壳命令面、**BR**=浏览器隔离边界、**CP**=computer 隔离边界、**DC**=doc-collab。
- 严重度定义对齐 01/03/10：高=真实 run 中可系统性放大延迟/内存或阻塞 runtime；中=局部热点或边界放大；低=开销明确但量级小或防御性。
- 每条问题模板：**位置 → 现象 → 代码现场 → 调用链与触发时机 → 根因 → 影响量化 → 修复方案 → 回归风险**。
- 未标注处不臆测运行时数字；量化以代码结构与默认常量推导，标注「静态推导」。
- **命名澄清**：`conex-sandbox` 不是 OS 级沙箱（无 namespace/seccomp/cgroup/Windows Job Object）；它是**命令门禁 + 语义分析**逻辑层。本报告「隔离开销」= 门禁判定 + 子进程包装 + 边界序列化的总成本。

## 1. 执行摘要

**一句话结论：系统没有 OS 级隔离税（无 seccomp/命名空间/jail），真实「隔离开销」集中在三处可收敛浪费——① 每次 shell/opener 调用重编译双 RegexSet 并对同一命令行做 2–3 次完整语义分析；② 浏览器域名门禁在 async 路径同步 DNS 解析（默认策略每次导航主机名全量解析、无缓存，超时可拖垮 tokio worker）；③ computer 的 UIA 快照在 async 上下文同步执行而未走已验证的 spawn_blocking 路径——叠加 PowerShell 进程创建 + EncodedCommand 双 base64 后，短命令的「门禁+包装」固定成本在批量 shell 场景可系统性放大。**

- **门禁层（SB）**：`CommandGatekeeper::new()` 每次构造编译 blocked+approval 两个 `RegexSet`（约 14+8 条正则）；`SharedGatekeeper` 单例已在 Tauri State 注册并被 `core_check_command` 消费，但 **shell 工具、workbench_run_shell、host_openers、cli_bridge、readonly 子代理过滤均未复用**，各自 `new()`。语义分析 `analyze()` 在 shell `prepare` 内被调用 **3 次**（门禁内 1 + 显式 1 + `decide_command_with_revert` 内 1）。
- **shell 隔离（SH）**：隔离形态 = 门禁后 spawn PowerShell/bash 子进程；Windows 为 `-EncodedCommand`（用户命令 UTF-8→base64 嵌脚本，再 UTF-16LE→base64）。`resolve_system_powershell` 每次 PATH 扫描/`is_file` 探测。无 Job Object / 无独立用户 / 无文件系统虚拟化——子进程与主进程同权限域。
- **host openers（OP）**：每次打开重新 `opener_candidates` + PATH 分割 + `CommandGatekeeper::new()`；Windows 默认关联已改 ShellExecuteW 直调（正面），但门禁构造成本仍在。
- **浏览器（BR）**：`MvpDomainGate::check` 对默认策略（白名单空）主机名走 `ToSocketAddrs` **同步 DNS**；工具层 `check_navigation_url` 为同步函数，从 async 工具体直接调用——DNS 慢解析阻塞 tokio worker。无解析结果缓存；DNS rebinding 60s 窗口按设计未接线（gate.rs:20-21）。
- **computer（CP）**：dispatch/screenshot 已 `spawn_blocking`（正面）；**snapshot 的 UIA 树遍历未 spawn_blocking**。每次注入 `action.clone()` + UIA 前景窗口解析 + `WindowTargetGate`。截图默认全帧 PNG + base64 进 JSON。
- **doc-collab（DC）**：纯进程内库，无隔离进程/管道/临时目录生命周期；热集/冷藏是内存管理。无隔离开销发现（信息项）。

**发现计数**：4 高（SB1 SB2 BR1 CP1）/ 7 中（SH1 BR2 BR3 CP2 CP3 OP1 OP2）/ 6 低（BR4 BR5 CP4 OP3 SH2 DC1）+ 7 项正面防回潮。修复路线图批次 X–Z（§10），性价比最高为 **批次 X（共享 Gatekeeper + 语义分析结果复用）** 与 **批次 Y（门禁 DNS 异步化/缓存 + computer snapshot spawn_blocking）**。

## 3. 域 A：conex-sandbox 门禁层（SB）

### 3.1 架构定位（非负面澄清）

`conex-sandbox` 的模块文档与依赖仅含 `serde` + `regex`（`Cargo.toml:13-15`）。无 `windows` job API、无 `nix` namespace、无 seccomp 绑定。其职责是：

1. 静态红线 `RegexSet` + 审批 `RegexSet`；
2. `semantics::analyze` 七类命令分类（含间接递归、深度熔断、反混淆）；
3. `check_command` / `check_command_with_context`（工作区越界升级）。

因此「沙箱开销」= **策略判定 CPU + 其后子进程成本**，不存在「每次创建容器/Jail 的固定税」。正面：避免了 Linux namespaces/seccomp 在 Windows 桌面上的不可用与错误移植；负面：隔离强度=权限门禁+子进程，无独立资源/文件系统域（安全模型问题，非性能；本报告不展开安全审计）。

### 3.2 SB1（高）· 每次调用重编译 CommandGatekeeper RegexSet

#### 位置

- 构造：`crates/conex-sandbox/src/lib.rs:25-70`（`CommandGatekeeper::new` 内两次 `RegexSet::new`）
- 消费点（全部 `new()`，无共享）：
  - `crates/agent-tools/src/tools/shell.rs:235`
  - `apps/agent-workbench/src-tauri/src/process.rs:77`
  - `apps/agent-workbench/src-tauri/src/host_openers/execute.rs:97,180,304`
  - `apps/agent-workbench/src-tauri/src/cli_bridge.rs:101`
  - `crates/agent-tools/src/readonly.rs:182`
- 已有单例却未推广：`apps/agent-workbench/src-tauri/src/core_commands.rs:70-77`（`SharedGatekeeper`）、`main.rs:805` `app.manage`、`core_commands.rs:274-284`（仅 `core_check_command` 消费）

#### 现象

每次 shell 工具执行、终端 shell、host opener 打开、CLI bridge 校验，都从零编译两个 `RegexSet`（blocked ≈14 条含回溯风险的破坏性命令正则 + approval ≈8 条），然后做整行/逐参匹配。

#### 调用链与触发时机

- Agent 调 `shell_command` → `prepare` → SB1；每条命令一次。
- 并行工具批（10：默认 max_parallel=4）可同时 4 次 `new()`。
- UI 终端每敲一回车一次；host opener 每次打开一次。

#### 根因

门禁实例被当作纯函数对象在调用点「就地构造」，未提升为会话/进程级单例；尽管壳层已有 `SharedGatekeeper`，工具 crate 依赖方向不允许直接吃 Tauri State，也没有把 `Arc<CommandGatekeeper>` 注入 `BuiltinToolConfig` / shell 工具构造。

#### 影响量化（静态推导）

- `regex` crate 编译复杂 `(?i)` 交替正则通常为数十～数百微秒量级/模式；两套 RegexSet 合计进入 **亚毫秒～毫秒级**/次固定开销。
- 短命令（`git status` 实际执行 ~50–200ms，但纯判定路径若无子进程对比）中门禁编译可占不可忽略比例；批量 4–16 shell 并行时线性放大。
- 与「正则匹配本身」不同：匹配是 O(编译后自动机)，编译是 O(模式源码)，**重复编译是纯浪费**。

#### 修复方案

1. 将 `CommandGatekeeper` 改为 `Arc` 共享或 `once_cell`/`LazyLock` 静态单例（正则集编译期固定，无运行时配置依赖时最简）。
2. 壳/工具注入面：`BuiltinToolConfig` / 引擎装配传入 `Arc<CommandGatekeeper>`，shell/readonly/host openers/cli_bridge 全部消费同一实例。
3. `core_check_command` 已用的 `SharedGatekeeper` 与工具侧对齐（同进程内 State 与引擎 registry 可共 Arc）。
4. 回归锚点：`conex-sandbox` 全部 gatekeeper 测试 + `shell_tests` 红线/审批矩阵 + `process.rs` eleven red-line 测试——构造方式变更不得改变判定结果。

#### 回归风险

低。判定纯函数化无状态；`patterns()` 返回引用的 API 在共享生命周期下需 `Arc` 持有方提供 `'static` 或改返回拷贝/内部匹配方法。

### 3.3 SB2（高）· shell prepare 语义分析三连

#### 位置

- `crates/agent-tools/src/tools/shell.rs:235-308`
- 门禁内：`conex-sandbox/src/lib.rs:77-125`（`check_command` 第 85 行 `analyze`）
- 权限链：`crates/agent-tools/src/permission.rs:141-157`（`decide_command_with_revert` 再 `analyze`）
- `check_command_with_context`：`lib.rs:129-151` 委托 `check_command`

#### 现象

同一条 `command` 字符串在一次 `prepare` 中被 `semantics::analyze` **完整跑三遍**：

1. `gatekeeper.check_command_with_context` → `check_command` → `analyze(&full_line)`；
2. `let analysis = semantics::analyze(&command)`；
3. `decide_command_with_revert(&command, …)` → 内部再 `analyze(command_line)`。

门禁与权限链各自为政，不传递已算好的 `SemanticAnalysis`。

#### 调用链与触发时机

每条 `shell_command`（sync / stream / auto-background / daemon 的预检共用 `prepare`）必经；含删除形态重定向与审批分支在分析结果上分支，但分析值本身未上提复用。

#### 根因

`decide_command*` 系列 API 以「命令行字符串」为契约方便接线，未暴露「已有 SemanticAnalysis」的重载；`CommandGatekeeper::check_command` 同样字符串入口。属接口形态导致的重复计算，而非分类器逻辑错误。

#### 影响量化（静态推导）

- `analyze` 对复合链做拆段、引号状态机、包裹提取、间接递归（深度≤5/16）、token 扫描；对 **32KB 上限**（`shell.rs:38`）恶意/复杂命令单次可达毫秒～数十毫秒 CPU。
- 三连后门禁相关 CPU ≈ 3×，对「短命令 + 重门禁」尾延迟贡献显著；对正常短命令（数十字符）分析成本通常 ≪ PowerShell 启动，但在 **批量 shell + 长命令** 场景线性叠加。
- 另：`check_command` 对 `full_line` 做 `format!("{cmd} {}")` 再对 `cmd`/`full_line`/`args` 三路 RegexSet——args 空时仍双路匹配，属小额放大。

#### 修复方案

1. 增加 `check_command_with_analysis(&SemanticAnalysis, …)` 或让 `check_command` 接受可选已算分析。
2. `prepare` 内：**先** `analyze(&command)` 一次 → 传给门禁（红线/危险/删除/cd）→ 传给 `decide_command_with_revert`（或新增 `decide_analysis_with_revert`）。
3. `check_command_with_context` 工作区越界升级不依赖重复分析，仅消费已有 verdict。
4. 回归锚点：shell 全红线矩阵、删除重定向、cd 拦截、审批升级、readonly 过滤——判定结果字节级不变。

#### 回归风险

中低。需保证 `full_line` 与 `command` 在 args 拼接语义上一致（当前 shell 路径 args 恒空，`full_line==command` trim 后一致）；host openers 带 args 的路径若共享分析需保留「命令+args」拼入口径。

### 3.4 SB3（中）· 无 OS 级隔离原语（模型澄清）

见 §3.1。非缺陷，但影响性能与安全预算表述：

- **性能**：无容器/seccomp 附加开销（相对容器化方案为正面）。
- **边界**：子进程与主进程同用户、同文件系统可见面（Windows 上无 Job Object 限 CPU/内存/断开子进程树——树杀靠自实现 `terminate_process_tree`）。
- **文档**：crate 名含 sandbox 易误导运维/安全评审；建议在 ARCHITECTURE/注释标明「逻辑门禁沙箱」。

严重度：中（模型/文档）；若未来引入真隔离，需预留「进程复用池」设计，避免每命令重进命名空间。

## 4. 域 B：shell 隔离与进程创建（SH）

### 4.1 SH1（中）· PowerShell 包装固定成本

#### 位置

- `crates/agent-tools/src/tools/shell_invoke.rs:12-94`
- `apps/agent-workbench/src-tauri/src/process.rs:230-309`
- 执行：`shell_exec.rs:49-80` / `process.rs:120-148`

#### 现象

每条通过门禁的 shell 命令：

1. 解析系统 PowerShell（PATH 环境变量 `split_paths` + 逐目录 `is_file`，或 System32 固定路径）；
2. 构造包装脚本：用户命令 UTF-8 → base64 字面量嵌入 → 再整脚本 UTF-16LE → base64 作为 `-EncodedCommand`；
3. `tokio::process::Command::spawn` 子进程（CREATE_NO_WINDOW、管道、环境变量）。

Unix 侧为 `bash -lc`，无 EncodedCommand，但仍有 `bash -lc` 启动 + login profile 潜在成本。

#### 根因

Windows 下避免 cmd 二次解释与引号损坏的正确性选择（见文件头注释与 P1-S5 壳演进）；代价是每次完整 PowerShell 进程映像加载。`resolve_system_powershell` 未缓存「已解析路径」。

#### 影响量化（静态推导）

- Windows PowerShell 5.1 冷启动常在 **数百毫秒** 量级；pwsh 7+ 通常更快但仍远高于纯门禁判定。对 `echo`/`git status` 类微命令，**进程启动主导端到端延迟**（固定地板）。
- 双层 base64：对 32KB 命令，编码 CPU 可忽略，但 `-EncodedCommand` 命令行长度膨胀 ~2.67×（UTF-16→base64），受 Windows 命令行长度上限约束——当前 32KB 用户命令 + 包装头，接近但一般低于 32K 字符 CreateProcess 限制的宽松区间；超限场景应有失败路径（现依赖命令长度前置拒绝 32_000 字符，包装后更长——**静态风险登记**：`MAX_COMMAND_LEN=32_000` 是用户命令字符数，非最终 argv；需确认 encode 后是否可能触发 CreateProcess 失败）。
- PATH 探测：无 pwsh 环境下多次 `is_file`；中等偏短（毫秒级）。

#### 修复方案

1. **缓存 PowerShell 解析结果**（`OnceLock<PathBuf>`），进程生命周期内一次 PATH 扫描。
2. 对高频微命令评估 **常驻 helper 进程**（长连接 stdout 行协议）——与 10 MCP 桥模式类似；需评估与门禁「每命令判定」契约的一致性（判定仍在主进程，helper 仅执行已判定命令）。
3. 保持 `-EncodedCommand` 语义（安全/正确性优先）；不要为省 base64 改回拼接字符串（防注入回潮）。
4. 校验包装后 argv 长度并提前 InvalidInput。
5. 回归锚点：十一红线测试、EncodedCommand 存在性测试（`process.rs` 测试区）、PAGER=cat 注入测试。

#### 回归风险

常驻 helper 改变生命周期与崩溃隔离语义，需独立设计评审；缓存解析路径风险极低。

### 4.2 SH2（低）· resolve 探测顺序重复

`process.rs:261-309` 与 `shell_invoke.rs:41-59` 两套实现（壳优先 pwsh7，工具优先 System32 WinPS 5.x）——除一致性外，每次调用重复探测。合并解析函数 + OnceLock 即可。

## 6. 域 D：浏览器隔离边界（BR）

### 6.1 BR1（高）· 域门禁同步 DNS 在 async 路径

#### 位置

- 解析：`crates/conex-browser-tools/src/gate.rs:34-44`（`SystemResolver` → `ToSocketAddrs`）

#### 调用链与触发时机

- `browser_navigate` / `browser_new_tab` 发送前；
- `back`/`forward`/`reload` 当前 URL 预检；

#### 根因

`DomainGate` trait 设计为同步 `fn check`；SSRF 解析校验（评审 F10）为安全正确性要求，但实现选择了同步系统解析器且未缓存。浏览器工具本身异步，阻塞面未隔离。

#### 影响量化（静态推导）

- 系统 DNS 超时常见数秒；极端可达 15–30s。期间 **占满一个 tokio worker**，与 session-loop 事件处理、其他工具竞争。
- 每次导航 + 每次 H4 变 URL 复核 = 每导航至多 2× 解析；无 TTL 缓存 → 重复 `example.com` 导航全额重付。
- 公共 CDN 主机名正向解析通常 <100ms，但 CI/断网/慢 DNS 环境为尾延迟炸弹。
- 静态分析未连接「DNS 失败率」——标注待运行时验证。

#### 修复方案

1. `DomainGate` 增加 async 变体，或工具层 `spawn_blocking(|| gate.check(url))` 包一层（最小改动，立刻消除 worker 阻塞）。
2. `HostResolver` 实现短 TTL 缓存（如 30–60s 正/负缓存；与文档中「60s rebinding 窗口」对齐时需安全评审：缓存降低 rebinding 检出频率——**安全 vs 性能**需裁决；可选「每次导航强制新鲜解析 + 动作路径用缓存」）。
3. 可选：解析超时上限（`tokio::time::timeout` + 自定义 resolver）。
4. 回归锚点：`gate.rs` 全部测试（T-5/T-6/T-7、SSRF、fail-closed）；注入 resolver 测试不受影响。

#### 回归风险

中。spawn_blocking 不改变判定语义；缓存策略必须显式安全评审（负缓存 + fail-open 组合危险）。

### 6.2 BR2（中）· 默认策略每次导航全量解析无缓存

### 6.3 BR3（中）· 导航后 H4 复核轮询

#### 位置

`navigate_common.rs:20-23,104-119`：`REDIRECT_POLLS=5`，`REDIRECT_POLL_INTERVAL=100ms`；`new_tab` 路径 `poll=true`。

#### 现象

#### 根因

#### 影响量化

**升级为高？** 对每次 `browser_new_tab` 成功路径 +500ms 固定延迟——量级明确、路径明确。判 **高**（结构化固定延迟）更贴切；原中 → **调为高 BR3**。

修正计数后见 §1。

#### 修复方案

1. 条件改为「URL 尚未知/为空」或「与 requested 不同且已变化」才轮询；`Some(requested)` 稳定则立即 break。
2. 或基于 `Page.loadEventFired` / lifecycle 事件。
3. 回归锚点：navigate/new_tab 测试中重定向用例。

#### 回归风险

中低；事件驱动改动面大，先改轮询条件即可。

## 14. 结论

方向 14 的核心事实是：**当前系统并未支付传统「沙箱/容器」税，支付的是「策略与包装税」**。逻辑门禁（RegexSet + 语义分析）与「每命令一个 PowerShell 子进程」构成隔离开销主体；浏览器与电脑工具组在隔离边界上混入了同步 DNS 与同步 UIA，与仓内已建立的 spawn_blocking 纪律不一致。优先落地批次 X（共享门禁 + 单次分析）与批次 Y（DNS 异步 + new_tab 轮询修正 + snapshot spawn_blocking）即可消除全部高危静态项；常驻 helper 与非 base64 图像载体留产品与安全联合裁决。
