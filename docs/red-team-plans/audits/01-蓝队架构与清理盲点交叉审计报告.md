# 一、 审计执行摘要与红蓝两军架构全景研判 (Executive Summary)

## 1.1 总体评价与红蓝两军架构特征对比

本专项审计（`AUDIT-RED-BLUE-01`）聚焦于**架构契约撕裂、死代码遗漏与微观代码级清理**。在对红队资产（00 总案、00 框架、00 契约与 `detailed-plans/01~08`）与蓝队资产（00 必读契约、01 维度定案、02 总计划框架、`detailed-plans/01~05`、`independent-plans/01~06` 及 `reviews/01~03`）进行全景深入比对后，审计官得出以下总体研判：

1. **红队的架构优势（宏观构筑与理论完备性）**：
   - 红队在**微内核扩展架构（Microkernel ViewRegistry + SlotCore 4 拓扑）**、**同心几何设计系统（3 大数学定理与严格尺寸闭环）**、**长文档 0 重绘虚拟化管线**以及**拓扑分域的无环 DAG 依赖链**上展现了极其强大的系统级架构功底。
   - 红队具备极强的宏观视野与自研决心，全面拒绝打补丁，建立了完整的物理删除总账本（-12,668 行净削减）。

2. **蓝队的架构优势（微观代码穿透力与盲区捕获能力）**：
   - 蓝队在**真实代码细节穿透与隐性反模式排查**上表现出罕见的敏锐度。蓝队成功捕获了红队在宏观规划中忽略的一系列“微观暗礁”与“语义撕裂”。
   - 蓝队精确指出了 `crish_workspace` 存储键的双重语义冲突、`TerminalCard.xterm.tsx` 中私自挂载的 `body MutationObserver` 性能刺客、`file-viewer` 字符串拼接与全局 Mode Map 逃逸、`autoIndexMiddleware` 的隐式二次广播及 `TelemetryMonitor.ts` 僵尸服务的遗留。

3. **两军交叉合流的必要性**：
   - 红队的宏观架构框架需要吸收蓝队在微观代码层面的深刻洞察，将其补齐至相应的详细实施方案中；
   - 同时，红队必须坚决剔除蓝队在部分方案中暴露的致命缺陷（如蓝队 06 误将核心产品资产 `WorkspaceEmptyState` 判为旧列式死代码而整组删除的重大失误、蓝队 05 遗留的无日期 JS fallback 等）。

# 二、 专项审计 1：`crish_workspace` 双语义撕裂与持久化键清洗深度审查 (Dual-Semantic Tear in `crish_workspace`)

## 2.1 历史病理剖析：同一 LocalStorage 键的双重撕裂语义 (CWD vs 'columns')

在 Conex/Crish 前端架构演进过程中，`localStorage` 中的键名 `'crish_workspace'` 发生了严重的语义撕裂与重载：

1. **第一重语义：工作区布局架构模式开关（Legacy Workspace Mode Switch）**
   在二叉树工作区（`BinaryTreeWorkspace`）研发初期，为了允许开发人员或特定配置回退到旧的列式工作区（`CardPanelLayout`），系统在底层引入了读取 `localStorage.getItem('crish_workspace')` 是否等于 `'columns'` 的逻辑。
2. **第二重语义：当前工程项目工作目录路径（Project Root CWD）**
   在工程项目管理（`projectStore.ts`）与终端/底层引擎执行 API（`clientApi.ts`）中，`'crish_workspace'` 被作为存储用户当前打开的本地项目绝对路径（如 `C:/Software/conex` 或 `/Users/user/project`）的持久化键名。

**病理危害**：

- 若用户打开了一个名为 `columns` 的本地项目文件夹，或者项目路径末尾为 `columns`，系统启动时 `createSsrGlobals.ts` 会误判用户期望进入旧列式宿主，导致整个二叉树布局崩溃并强制降级至已废弃的旧列式组件；
- 更加严重的是，在进行死代码清剿时，若重构 Agent 盲目执行 `rg "crish_workspace"` 归零并执行全局删除，将会直接清空用户的当前项目路径（CWD），导致引擎执行 `run_command`、文件树扫描与终端初始化完全丢失工作目录！

# 五、 专项审计 4：`autoIndexMiddleware` 废除与会话索引维护职责拓扑转移 (Abolition of `autoIndexMiddleware`)

## 5.1 中间件反模式病理：全量数组扫描、$O(N)$ 重建 Map、双重广播与 Immer 引用颠簸

在 Zustand 状态管理架构中，`autoIndexMiddleware.ts` 是一种典型的**由于早期架构职责不清而引入的低效隐式副作用中间件**。

**反模式运作机制**：

- 在 [`apps/crish-desktop/src/store/autoIndexMiddleware.ts:23-37, 56-76`](file:///c:/Software/conex/apps/crish-desktop/src/store/autoIndexMiddleware.ts#L23-L37) 中，该中间件柯里化包裹了 Zustand 的 `set` 函数；

# 八、 蓝队内部逻辑缺陷与红队应规避的误区专项审查 (Flaws in Blue Team Plans & Risks to Avoid)

## 8.1 蓝队 06 误将 `WorkspaceEmptyState*` 关键资产列入删除名单的重大过失

- **重大过失事实**：蓝队独立方案 06（Line 21）将 `WorkspaceEmptyState*` 全组文件定性为“旧列式删除面”，并规划整组物理删除；

- **审计裁决**：红队方案对此识别精准，必须**坚决保护 `WorkspaceEmptyState*` 资产**，仅剥离其对旧 `layoutStore.workspaces` 的依赖，绝不允许整组误删！

## 8.2 蓝队 05 方案中无日期 `field-sizing` JS Fallback 违规问题

- **违规事实**：蓝队独立方案 05（Line 255）在 auto-grow 改造中，允许在不支持 CSS `field-sizing: content` 的环境中增加“单次 rAF 内读 scrollHeight 后写 height”的 JS fallback，且**未注明删除日期**；

---

## 8.3 蓝队早期方案中 Z-Index 标尺层级（6 级 vs 7 级）与封顶值（2000 vs 9000）的分歧

- **分歧事实**：蓝队 01 方案声称 6 级但列出 7 个 Token；蓝队 05 方案封顶 2000；蓝队 06 方案封顶 9000；
- **审计裁决**：统一裁决以**红队 7 级语义 Token（`--z-base:0` 至 `--z-tooltip:9000`）**为全仓唯一真理标准，全面废止 2000 封顶与 100000 历史脏 Token。

## 8.4 蓝队 02 方案误删 Web resize 导致非 Tauri/浏览器环境尺寸信号归零的风险

- **风险事实**：蓝队独立方案 02 粗暴主张删除所有 Web `resize` 监听，仅保留 Tauri `win.onResized`；这会导致在 Web 端开发（`npm run dev:workbench` Vite 调试）或测试环境下，全站完全丢失窗口尺寸信号；
- **审计裁决**：采纳红队 Plan 03 与蓝队详案 04 的宿主判定单分支模型（Tauri 环境下走 `onResized`，非 Tauri 环境下走单一 passive `window.resize`）。

---

## 8.5 蓝队 06 方案“三段式先建后切后删”带来的短暂双轨与假收敛风险

- **风险事实**：蓝队 06 方案规划第 1 阶段新建所有基础设施，第 2 阶段切流，第 3 阶段才删除旧代码。这种多阶段执行会在中间提交产生严重的“新旧两套代码并存”的假收敛窗口；
- **审计裁决**：红队必须坚持**“原子交割（Atomic Handover）”纪律**——每个领域的重构必须在同一个逻辑提交内同时完成“新入口接管 + 旧路径物理删除”，绝不给系统留下哪怕 1 个提交的双轨空窗！
