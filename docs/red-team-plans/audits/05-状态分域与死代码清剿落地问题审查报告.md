### 2. 会话 Diff 纯函数派生、脏数据渗透与总览文件树审查

#### 【问题编号】AUDIT-C-06

- **【涉及文件及精准行号】**：
  - `apps/crish-desktop/src/api/sessionDiffDerivation.ts:18-68`
- **【违反的详案契约条款】**：
  - `docs/red-team-plans/detailed-plans/07-状态拓扑分域与空态白板门闩维度详案.md` §1.3（会话 Diff 纯函数派生规范）、Plan 06 §1.1（Posix 路径归一化契约）。
- **【潜在风险/病理剖析】**：
  - 在 `selectSessionDiffFiles(messages)` 实现中，解析 `edit_file`、`write_to_file`、`multi_replace_file_content` 等工具调用的入参路径时，直接使用了原始入参字符串作为 `fileMap` 的 Key（如 `const filePath = String(args.target_file || args.TargetFile || ...)`），完全没有进行跨平台的斜杠标准化（如 `replace(/\\/g, '/')`）；
  - 在 Windows 环境下，不同工具或不同 Agent 模型可能输出 `c:\project\src\App.tsx` 或 `c:/project/src/App.tsx`，未标准化的路径会导致 `fileMap` 将同一物理文件识别为两个独立的修改文件，造成总览文件树与变更列表中出现重复条目，Diff 计数加倍。
- **【精确整改建议】**：
  - 提取路径后立即进行 Posix 格式归一化：
    ```ts
    const normalizedPath = rawPath.replace(/\\/g, '/');
    ```
  - 统一使用 `normalizedPath` 作为 `fileMap` 键值及结果的 `filePath`。

### 3. Diff 视图虚拟化渲染、Intraline 算法与色彩标尺审查

#### 【问题编号】AUDIT-C-08

- **【涉及文件及精准行号】**：
  - `apps/crish-desktop/src/components/diff/DiffCardSplitView.tsx:99, 167`
  - `apps/crish-desktop/src/components/diff/DiffCardUnifiedView.tsx:88, 139`
- **【违反的详案契约条款】**：
  - `docs/red-team-plans/detailed-plans/06-总览文件树与Diff审查维度详案.md` §1.5（虚拟滚动列表渲染契约与性能预算）。
- **【潜在风险/病理剖析】**：
  - 在分栏视图（SplitView）和合并视图（UnifiedView）的虚拟滚动渲染循环中，列表子项直接使用了数组下标 `idx` / `globalIdx` 作为 React 的 `key`（L167: `key={idx}`, L139: `key={globalIdx}`）；
  - 当虚拟滚动条快速滚动导致视口项重用时，使用数值下标作为 key 会破坏 React 的 DOM 复用启发式算法，导致高亮状态残留、选中区域错位以及不必要的 DOM 节点频繁销毁与重建；
  - 此外，在 `renderTokens` 降级路径中，代码在每帧 render 循环内无缓存地同步调用 `highlightCode(change.content, 'diff')`，在大文件（10,000+ 行）Diff 滚动时会造成严重的掉帧与 UI 卡死。
- **【精确整改建议】**：
  - 使用具备业务唯一性的稳定 Key：如 `key={`${f.filePath}-${item.oldLine ?? 'x'}-${item.newLine ?? 'y'}-${localIdx}`}`；
  - 为行级代码高亮接入 LRU 缓存或在 `useDiffData` 数据准备阶段完成批量高亮派生，严禁在虚拟滚动 render 热路径中进行同步语法解析。

- **【潜在风险/病理剖析】**：
  - `DiffCardUnifiedView.tsx` 中的 Intraline 差异计算逻辑仅进行了极其粗糙的单行前后探测（`prevItem` 与 `nextItem`）：
    ```ts
    // 检查前一项是否是 deletion
    const prevItem = globalIdx > 0 ? renderItems[globalIdx - 1] : null;
    if (
      prevItem &&
      !prevItem.isCollapsedPlaceholder &&
      prevItem.item.change.type === 'deletion'
    ) {
      const pairResult = computeIntralinePair(
        prevItem.item.change.content,
        change.content
      );
      tokens = pairResult.newTokens;
    }
    ```
  - 当出现多行连续删除紧随多行连续新增（例如连续删除 3 行，随后新增 2 行）时，只有第一行新增与最后一行删除能匹配，其余行均因相邻项类型不满足条件而丢失词法级高亮，甚至发生错位对齐比对，造成差异高亮展示支离破碎。
- **【精确整改建议】**：
  - 将 Intraline 对齐计算从组件渲染期前移至 `useDiffData` 预处理管道；
  - 采用标准的块级连续变更聚类算法（Continuous Hunk Chunking），在预处理阶段将相邻的 `Deletion[]` 与 `Addition[]` 列表进行 1:1 或 LCS 矩阵对齐后，再将结构化 tokens 注入渲染模型。

## 三、审查结论与收敛建议

本次对状态拓扑分域、Diff 审查与全仓死代码清剿落地的穿透式审查共捕获 **15 项违背详案契约的落地缺陷**（其中包含 **7 项 CRITICAL 级**、**6 项 MAJOR 级** 与 **2 项 MINOR 级** 缺陷）。

**核心病理总结**：

1. **伪分域现象严重**：虽然 `sessionStore` 完成了切分，但 `workspaceStore` 与 `settingsUiStore` 依然采用别名同体挂载在 `layoutStore` 上，且测试单测反向锁定了错误实现；
2. **白板门闩与会话隔离存在漏洞**：`sessionDiffDerivation.ts` 未标准化路径且未过滤报错工具调用，`useBackgroundTaskPolling.ts` 未传 `sessionId`，导致全局脏数据向会话白板渗透；
3. **全局服务架构未能闭环**：`ToastProvider` 根本未在应用入口挂载，导致 30+ 个组件依然在进行深层 `onShowToast` 属性透传；
4. **CSS 纯净化落地滞后**：`theme-dark.css`（249 行）与 `index.css` 中的 9 个全局样式表（>120KB）依然在全局污染样式空间；
5. **门禁引擎存在大面积盲区**：`check-frontend-convergence.mjs` 规则过于脆弱，未能起到防回潮的刚性门禁作用。

建议主控立即安排专项修复战役，严格对照上述 15 项整改建议逐一完成代码落地与物理歼灭。
