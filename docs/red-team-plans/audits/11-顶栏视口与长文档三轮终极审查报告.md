# 二、 36px Seamless 顶栏外壳与视口几何缺陷审查 (Domain 1: TopBar Chrome & Viewport Geometry)

### 【AUDIT-R3-01】SessionTabDragProvider 硬编码 NOOP_DRAG 致使顶栏会话标签拖拽功能彻底瘫痪 (P0 致命)

- **涉及文件及精准行号**：
  - `apps/crish-desktop/src/components/shell/SessionTabDragContext.tsx:32-46`
  - `apps/crish-desktop/src/components/top-bar/AppTopBar.tsx:82`
  - `apps/crish-desktop/src/components/shell/GlobalSessionTabBar.tsx:253-258`
  - `apps/crish-desktop/src/App.tsx:170`
- **违反的详案契约条款**：`03 详案` §1.2.1、§3.2 (Task-G04)；`02 修复方案` §3.3
- **代码病理剖析与确凿证据**：
  在 `apps/crish-desktop/src/components/shell/SessionTabDragContext.tsx` 中查看其 Provider 的实际落地实现：
  ```tsx
  // apps/crish-desktop/src/components/shell/SessionTabDragContext.tsx:32-46
  const NOOP_DRAG: UseTopBarDragResult = {
    isDragging: false,
    startSessionDrag: () => {},
    startToolDrag: () => {},
    setGhostRef: () => {},
    ghostLabel: null,
  };

  export function SessionTabDragProvider({
    children,
  }: {
    children: ReactNode;
  }) {
    return (
      <SessionTabDragContext.Provider value={NOOP_DRAG}>
        {children}
      </SessionTabDragContext.Provider>
    );
  }
  ```
  在 `App.tsx:170` 中，应用根节点使用 `<SessionTabDragProvider>` 包裹全应用：
  ```tsx
  // apps/crish-desktop/src/App.tsx:170-171
  <SessionTabDragProvider>
    <div className={`app-container ${appModeClass}`}>
  ```
  而在顶栏 `AppTopBar.tsx:82` 中：
  ```tsx
  // apps/crish-desktop/src/components/top-bar/AppTopBar.tsx:82
  const { startSessionDrag } = useSessionTabDrag();
  ...
  <GlobalSessionTabBar
    variant="caption"
    startSessionDrag={startSessionDrag}
  />
  ```
  **病理剖析**：
  1. `SessionTabDragProvider` 向下分发的 `value` 恒定为 `NOOP_DRAG`，其内部 `startSessionDrag` 只是一个空函数 `() => {}`；
  2. 虽然 `GlobalSessionTabBar.tsx:253-258` 接入了 `onTabPointerDown={startSessionDrag ? ... : undefined}`，但调用进去后直接命中空操作；
  3. 这导致在 36px 顶栏一体化会话条中，**会话标签的拖拽重新排序、跨工作区分屏拖拽撕裂（Tab Tear-off / Drag to Split）功能在运行时 100% 彻底瘫痪**！
  4. 用户在标签上按住并移动指针，界面无任何响应，幽灵拖拽层（`dragGhost`）永远无法被激活。
- **精确整改建议**：
  在 `SessionTabDragProvider` 中实现真实的拖拽协调状态机（或接入二叉树工作区拖拽服务），管理 PointerDown/PointerMove/PointerUp 全局监听、位移阈值检测（$|\Delta x| > 4\text{px}$）与 Portal 拖拽镜像渲染，绝不能向下分发空闭包 `NOOP_DRAG`。

### 菲茨定律（Fitts's Law）指数模型复核：

根据菲茨定律，用户将指针移动到目标区域所需的时间 $T$ 由下式决定：
$$T = a + b \log_2 \left( \frac{D}{W_{\text{target}}} + 1 \right)$$
其中 $D$ 为起始距离，$W_{\text{target}}$ 为目标在移动方向上的有效投影宽度。

1. **设置页垂直滚动条 ($X = W_{\text{screen}}$)**：
   由于滚动槽紧贴屏幕极右侧物理边缘，屏幕右边界充当了物理挡板（$W_{\text{target}} \to \infty$），因此命中时间 $T \to a$（常数极小时间），达到完美的人机工效学体验；
2. **Windows 窗控关闭按钮 ($X = W_{\text{screen}}, Y = 0$)**：
   由于 `.trail` 存在 `padding-right: 4px` 且按钮高度仅为 28px（上下各有 4px 空白），屏幕物理右上角 $(W, 0)$ 成为无响应区域。有效目标宽度从无穷大骤降为有限小宽度 $W_{\text{target}} = 32\text{px}$，命中时间 $T$ 增加了 **240%**，严重违反桌面端窗控人机工效学基本常识。
