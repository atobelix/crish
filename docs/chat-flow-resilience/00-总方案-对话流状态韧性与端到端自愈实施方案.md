## 一、方案背景与攻坚目标

### 1.1 现场四大核心病灶（Root Causes）
在 Conex 近期使用与用户反馈中，暴露了四个严重的架构断层与交互缺陷：
1. **缺陷 1（发送打回死锁）**：由于断网或异常中断，历史消息残留 `status: 'processing'`。在用户点击发送时，`isSessionAiBusy` 仅依据消息数组判定忙碌，强行将新消息转为 `isFollowUp` 并标记为 `queued`，输入框永久卡在“输入排队消息…”与“排队”按钮，用户无论如何手动点击发送都被系统直接打回。
2. **缺陷 2（系统排队提示污染思维链）**：在 `streamSession.ts` 中捕获 `SESSION_BUSY` 串行守卫时，错误调用 `callbacks.onThought('当前会话上一轮任务仍在收尾中，已自动为您排队…')`，导致界面出现带折叠箭头的“已思考 v”灰色大卡片，被用户红叉严厉警告。
3. **缺陷 3（125秒假思考与计时错乱）**：消息初始化与流启动阶段，代码盲目注入 `thinking: '正在处理…'`，将后台网络准备、首 Token 等待与工具耗时统统计入思维链，生成持续走字的 125s 假思考卡片。
4. **缺陷 4（流内重试与错误自愈黑盒）**：后台网络重试、重连与 429 退避未在对话流内结构化呈现，原本设计的 `ephemeralChatStore` 悬空脱节；终态错误时粗暴撤回整个助手卡片，造成信息丢失与黑屏感。

### 1.2 攻坚铁律与架构原则
1. **对话流单一事实源（SSOT）**：后台重试、重连、状态指示与终态错误是一等公民对话流节点，**坚决不放在底栏浮条或全局悬浮条**；
2. **绝对自愈契约（Absolute Self-Healing）**：只要用户手动触发发送，无实时流时立即清扫收口一切僵尸 `processing` / `queued` 状态，确保新消息畅通无阻，**绝对不能打回**；
3. **思维链绝对纯洁性（Reasoning Purity）**：`callbacks.onThought` 仅用于传递 LLM 原生 `<think>` 推理内容，禁止任何系统级排队、重试或占位文案混入；
4. **工作态与推理态严格解耦**：首 Token 到达前仅挂载轻量翡翠绿脉冲单行指示器（`WorkingStatusIndicator`），仅当真正解析出思维链增量时才挂载 `ReasoningRow`。

## 二、架构决策：吸收 DeepSeek Harness 核心精髓

借鉴 `reference/deepseek-harness`（`ConversationNode` 体系），我们在 Conex 中确立以下关键机制：

| DeepSeek Harness 设计精髓 | Conex 对话流落地映射 | 架构价值与解决的问题 |
| :--- | :--- | :--- |
| **`model-retry` 单行链式聚合** | `ModelRetryNode` 融入助手回复卡片 | 一整条退避重试链通过 `retryId` 聚合为单一视图，支持动态倒计时与扫光微交互，避免流长度爆炸。 |
| **`turn-error` 终态挂载** | `TurnErrorNode` 挂载于 Turn 末尾 | 终态错误（401/403/500/网络断开）结构化收口，保留历史上下文，提供一键原地重试与修改提问。 |
| **独立屏障白名单（Independent Kinds）** | 错误与警告不受推理/过程折叠影响 | 即使思维链被用户折叠，重试节点与错误节点仍 100% 显性穿透，绝不遮蔽故障信息。 |
| **微序号插桩（Micro-sequencing）** | 浮点逻辑偏移序（`Synthetic Seq Offsets`） | 保证错误节点、重试指示器与正文在虚拟时间线上单调严格排序，消除 React DOM 重排抖动。 |
| **生命周期闭合（Lifecycle Closure）** | 容器/连接关闭时自动结算悬挂重试 | 在流成功到达或显式取消时，自动将重试态结算为闭合，消除僵尸定时器。 |

## 三、四大模块端到端落地方案

### 3.1 模块一：发送入口绝对自愈与死锁根治

#### 3.1.1 `settleStaleSessionProcessingMessages` 纯逻辑实现
在 `apps/crish-desktop/src/hooks/chat-stream/helpers.ts` 导出绝对自愈契约：
```typescript
export function settleStaleSessionProcessingMessages(
  sessionId: string,
  hasLiveStream: boolean
): { healedCount: number; clearedQueueCount: number } {
  if (hasLiveStream) {
    // 存在物理活动流，遵循正常的并发保护
    return { healedCount: 0, clearedQueueCount: 0 };
  }

  const root = getCompositionRoot();
  const session = root.session.getState();
  const currentSession = session.sessionsById[sessionId];
  if (!currentSession || !Array.isArray(currentSession.messages)) {
    return { healedCount: 0, clearedQueueCount: 0 };
  }

  let healedCount = 0;
  let clearedQueueCount = 0;

  for (const msg of currentSession.messages) {
    if (msg.status === 'processing') {
      if (msg.sender === 'assistant') {
        const hasText = Boolean((msg.text || '').trim());
        session.setSessionMessageStatus(sessionId, msg.id, 'error', undefined, {
          errorDetail: {
            message: hasText ? '上一轮生成异常中断' : '未收到回复内容（连接已断开）',
            kind: 'stream_abort',
          },
        });
      } else {
        session.setSessionMessageStatus(sessionId, msg.id, 'completed');
      }
      healedCount++;
    } else if (msg.status === 'queued') {
      session.setSessionMessageStatus(sessionId, msg.id, 'completed');
      clearedQueueCount++;
    }
  }

  // 同步清理瞬态错误与重试 store
  useEphemeralChatStore.getState().clearEphemeralStatus(sessionId);
  useContinuityUiStore.getState().clearRetryNotice(sessionId);

  return { healedCount, clearedQueueCount };
}
```

#### 3.1.2 改造 `isSessionAiBusy`
```typescript
export function isSessionAiBusy({ hasLiveStream, messages }: SessionAiBusyCheckOptions): boolean {
  // 核心铁律：若无真实 live stream，无论历史消息如何，绝不单凭 processing 判定 busy！
  if (!hasLiveStream) {
    return false;
  }
  return (messages || []).some(m => m.sender === 'assistant' && m.status === 'processing');
}
```

#### 3.1.3 入口接线：`useSlashSend.ts`、`useChatMessages.ts`、`useChatComposerProps.ts`
- 在 `handleSendChat` 的第一行先调用 `settleStaleSessionProcessingMessages(sessionId, hasLiveStream)`；
- 重新计算 `isAiBusy`，确保其在无活跃流时为 `false`；
- 切断 `isFollowUp` 的虚假触发，新消息直接进入 `runStreamingAssistant`。

### 3.2 模块二：思维链纯洁性与工作态解耦

#### 3.2.1 彻底切除污染源
1. **`streamSession.ts:86`**：删除 `callbacks.onThought('正在处理…')`；
2. **`streamSession.ts:263-265`**：删除 `callbacks.onThought('当前会话上一轮任务仍在收尾中...')`，改为结构化 runNotice 或普通日志；
3. **`useRunStreamingAssistant.ts:114`**：删除消息初始化时设置的 `thinking: '正在处理…'`，改为 `thinking: undefined`。

#### 3.2.2 新建极简工作态指示器：`WorkingStatusIndicator.tsx`
- **定位**：首 Token（TTFT）到达前的轻量等宽脉冲组件；
- **视觉风格**：24px 极简行高，翡翠绿脉冲高亮点（`#10b981`），柔和扫光文字 `正在连接模型...`，等宽计时 `0.8s`；
- **生命周期**：首个 chunk / thought / tool 到达时，透明度淡出并卸载，绝不固化进历史消息！

#### 3.3.2 节点组件构建
1. **`ModelRetryNode.tsx`**：
   - 展现：🔄 正在自动重试 (1/3) · 下次重试倒计时 2.4s；
   - 交互：提供 `[立即重试]` 按钮（跳过等待）与 `[放弃重试]` 按钮；

#### 3.3.3 编排集成到 `MessageContent.tsx`
在消息卡片底部，按微序号有序渲染：
```tsx
{/* 1. 工作态等待指示器（首 Token 前） */}
{isWorking && <WorkingStatusIndicator startTime={workingStartTime} />}

{/* 2. 真实思维链（仅在收到真实 reasoning 时挂载） */}
{hasReasoning && <ReasoningRow content={message.thinking} ... />}

{/* 3. 正文流渲染 */}
{hasContent && <RichContent content={message.text} />}

{/* 4. 流内原生重试卡片 */}
{inFlowRetry && <ModelRetryNode retryState={inFlowRetry} ... />}

{/* 5. 流内原生终态错误卡片 */}
{turnError && <TurnErrorNode errorStatus={turnError} ... />}
```

## 六、立体验证方案

1. **单元测试门禁**：
   - 编写 `helpers.test.ts` 专项用例，断言 `hasLiveStream = false` 时调用自愈契约彻底清理僵尸消息；
   - 断言 `callbacks.onThought` 在准备期与排队期零调用；
   - 断言新消息初始状态 `thinking === undefined`。
2. **真实场景现场验收**：
   - **打回死锁自愈场景**：手动将消息标记为 `processing` 并关闭流，再次发送新消息，断言秒级自愈并成功发起新轮次；
   - **假思考切除场景**：延迟首 Token，断言仅显示翡翠绿脉冲单行指示器，绝不生成带折叠箭头的假思考卡片；
   - **429 退避场景**：模拟限流，断言流内展示 `ModelRetryNode` 倒计时与扫光动效；
   - **终态错误场景**：模拟连接中断，断言流内显示 `TurnErrorNode` 并可点击“重试此轮”。
