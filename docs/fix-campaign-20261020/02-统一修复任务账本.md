# 统一修复任务账本（2026-10-20）

> **用途**：本账本是本战役的唯一任务状态源。所有审计条目必须在账本中有行；状态、负责人、证据、复核都以本表为准。
> **输入**：`../full-audit-20261020/00-全面问题清单.md` 的全部条目。
> **规则**：条目只能追加、状态流转、补充证据，不得删除；确需废弃时改为 `cancelled` 并写明理由、批准人与证据。
> **完成定义**：只有满足 `01-反作弊与反偷懒执行铁律.md` §14 的 DoD，状态才可以是 `done`；否则只能是 `pending / in_progress / blocked / in_review`。

## 0. 状态与证据规则

| 状态 | 含义 | 进入条件 |
| :--- | :--- | :--- |
| `pending` | 已导入，未开始 | 审计条目已登记 |
| `in_progress` | 正在实现/测试 | 已有负责人、任务卡、基线证据 |
| `blocked` | 无法继续 | 有阻塞证据、已尝试路径、所需外部条件 |
| `in_review` | 待红队/主控复核 | 实现完成，证据包齐全，等待独立复跑 |
| `done` | 完成 | 满足 DoD；证据可复现；复核通过 |
| `cancelled` | 经批准废弃 | 有理由、批准人、替代方案或风险说明 |

- **证据列**必须包含：命令、退出码、原始日志路径、测试计数、修复前后对比、复核人。
- **无证据不得 `done`**；日志含 `FAILED` / `error` / `panic` 时不得 `done`。
- **不得用「基本完成」「后续优化」代替状态**；未完成就写 `blocked` 或 `in_progress`，并列出剩余项。
- **不得删除行**：审计条目与账本行必须保持可追溯的一一对应关系（允许一个审计条目拆成多行，但必须在「审计 ID」列标注同一 ID）。

## 3. 全量导入规则（阶段 A 必须完成）

1. 从 `../full-audit-20261020/00-全面问题清单.md` 逐节读取 BLK、RUN、SEC、GAP、DEBT、DOC 条目。
2. 每个条目至少一行；同一问题跨多个文件可拆行，但「审计 ID」必须一致。
3. 在「依赖」列标注阻塞关系（例如 BLK-09 → 全量 cargo test；RUN-05 → 发布验收）。
4. 在「验收断言」列引用审计条目的验收建议，不允许只写「修好」。
5. 导入完成后做一次核对：审计 ID 数量 = 账本中去重后的审计 ID 数量；缺项必须补齐并说明原因。
6. 不允许因为「看起来不重要 / 太难 / 时间不够」而不导入；问题同权。

## 4. 任务量守恒检查

- 每次阶段收口时统计：审计 ID 总数、账本行数、`done` 数、`blocked` 数、`cancelled` 数。
- `done + blocked + cancelled + pending + in_progress + in_review` 必须等于总行数；不得有「消失」的条目。
- `cancelled` 必须有用户/主控批准记录；不得用 `cancelled` 逃避修复。
- 子任务拆分后，父条目必须保留并链接子任务；父条目不得提前 `done`。
