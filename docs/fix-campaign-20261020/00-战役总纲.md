# 统一修复战役总纲（2026-10-20）

> **战役定位**：把 `docs/full-audit-20261020/00-全面问题清单.md` 中的全部问题，按同一验收标准修复、验证、收口；不允许以任何理由降低标准、缩小范围或伪造通过。
> **适用范围**：本文件与 `01-反作弊与反偷懒执行铁律.md`、`02-统一修复任务账本.md` 共同构成本战役的执行契约。
> **与仓库纪律的关系**：不修改、不替代 `AGENTS.md` / `.agents/AGENTS.md` / `.agents/LOGIC_PLAN_NO_RETREAT.md`；本战役规则只在战役内生效，并与仓库既有纪律叠加执行；冲突时按更严格的一方执行，并上报主控。

---

## 1. 战役目标

1. **阻断项清零**：让 CI / 门禁恢复到可判定、可阻断的真实状态，不靠改阈值、删测试、缩范围变绿。
2. **运行时与数据风险闭环**：更新、发布、日志、产出目录、会话删除、搜索预热、release 数据路径等生产链路必须真实可用或有明确不可用状态。
3. **未完成功能补齐**：真壳 E2E、Windows 原生 smoke、移动端构建、avatar-studio 定位、Tiptap 状态账本等按审计结论补齐，不把「文档写了」当完成。
4. **技术债与文档收口**：死代码、未用导出/依赖、TODO、忽略测试、豁免记录、方案与状态账本全部有处置结论。
5. **建立可复用的反作弊验收机制**：任务账本、证据包、红队复核、违规熔断在战役中真实运行，而不是只写在文档里。

## 2. 范围与不变量

### 2.1 范围

- 审计总账中的全部类别：BLK、RUN、SEC、GAP、DEBT、DOC。
- 与这些问题直接相关的代码、测试、CI、脚本、配置、文档与发布链路。
- 审计中明确标注「未验证」的项，必须在战役结束前转为「已验证」或「有证据的阻塞」。

### 2.2 不变量（任何 Agent 不得违反）

- **目标不缩水**：不得把「完整修复」改成「MVP / 简化版 / 先这样」；如确需改变目标，只能由用户裁决。
- **问题同权**：审计条目默认同权；阶段顺序只按依赖与可验证性排列，不按「看起来重要/容易」砍项。
- **标准只升不降**：不得降低覆盖率、性能 SLA、行数/体积基线，扩大 allowlist/ignore/exclude，删除或弱化测试，自动接受 snapshot。
- **禁止假绿/假成功**：不得隐藏退出码或失败日志、不得用 stub/假提示/TODO 冒充完成、不得只改文档不改行为。
- **同类全量修复**：审计列出的同类问题必须全量搜索并处理；只修一个点视为未完成。
- **证据先于结论**：没有命令、退出码、原始日志、测试计数与前后对比，不得标记完成。
- **主控唯一收口**：子 Agent 不提交、不回滚、不改他人文件；主控 100% 审 diff 并独立复跑关键命令。
- **测试资产保护**：按 `AGENTS.md` §9 执行；不得删除 `reference/markdown-editor` 或既有 E2E 资产。
- **用户并行工作不被覆盖**：工作区可能同时存在用户/其他 Agent 的未提交改动；禁止 `git reset --hard` / `checkout .` / `restore` 等全局回撤；提交必须按路径限定。

## 4. 战役阶段（按依赖关系，不按业务优先级）

> 阶段顺序是逻辑依赖：先让门禁可判定，才能可靠判断后续修复是否真正通过。阶段不等于「重要性排序」，任何阶段的问题都不得被放弃。

### 阶段 A：基线复核与账本建立

- 将审计总账的全部条目导入 `02-统一修复任务账本.md`，保证「审计 ID ↔ 账本行」一一对应。
- 逐项复核阻断项与关键运行时问题的当前状态；记录 HEAD、工作区状态、复现命令、退出码、原始日志。
- 识别用户并行改动与运行中进程（如 app 锁定 workbench 二进制），在账本中登记为环境约束。
- 产出：全量账本、基线证据包、阶段 A 验收记录。

### 阶段 B：阻断项清零

- 处理 BLK-01～BLK-09 及其它 CI 必红项。
- 修复顺序按依赖：先修会阻断全量测试/门禁的项，再修单项门禁；不得用基线/allowlist 绕过。
- 每项必须有 red→green 回归测试或等价的可验证证据；门禁修复必须证明能拦住原始缺陷。
- 产出：阻断项证据包、`cargo test` / ESLint / knip / 治理门禁结果、阶段 B 验收记录。

### 阶段 C：运行时、数据与发布闭环

- 处理 RUN、SEC 中涉及更新、签名/公证、日志保留、产出清理、会话删除、搜索预热、release 数据路径等条目。
- 数据路径必须验证旧数据升级、迁移、回滚；发布必须验证真实产物与安装链路；UI 必须真机/Tauri MCP 验收。
- 产出：迁移/回滚记录、发布配置与产物证据、阶段 C 验收记录。

### 阶段 D：未完成功能补齐

- 处理 GAP 类：真壳 E2E、Windows 原生 smoke、移动端构建、avatar-studio、Tiptap 状态账本、覆盖率接线等。
- 「方案存在」不等于「功能完成」；必须有可执行入口、验收断言与 CI 接线。
- 产出：功能验收记录、CI job 结果、阶段 D 验收记录。

### 阶段 E：技术债与文档收口

- 处理 DEBT、DOC 类：死代码、未用导出/依赖、TODO、ignored 测试、豁免记录、PROJECT 状态、FULL_CHECK 漂移等。
- 文档必须与代码/CI 同步；不得用文档修改掩盖代码未修。
- 产出：债务处置清单、文档同步记录、阶段 E 验收记录。

### 阶段 F：全量验收与发布前复核

- 按 `FULL_CHECK_COMMANDS.md` 与 CI 实际阻断面执行全量门禁；Rust/前端/移动端/桌面构建全部覆盖。
- 复核任务账本：所有条目为 `done` 或 `blocked`（有证据）；不得有「基本完成」「后续优化」。
- 建立 `04-发布前总验收.md`，记录签名、公证、更新、数据迁移、真壳 E2E、残余风险。
- 产出：发布前总验收报告、最终任务账本、事故/违规记录（如有）。

## 5. 单条目执行闭环

每个审计条目必须经过以下闭环，缺一步即不得标记完成：

1. **读条目**：完整阅读审计总账中的证据、影响、修复建议与相关代码位置。
2. **复现**：执行最小复现命令，保存原始日志与退出码。
3. **建卡**：在任务账本中登记任务卡（级别、文件域、依赖、验收断言、禁止捷径）。
4. **根因**：定位到 `文件:行号`，区分实现/测试/文档/CI/环境问题。
5. **修复**：最小正确改动；不做无关重构；不降低标准。
6. **测试**：先红后绿；覆盖边界、异常、回归；必要时真机/真实数据验证。
7. **门禁**：定向 + 全量相关门禁；保留日志。
8. **评审**：不同 Agent 红队复核；主控独立复跑关键命令。
9. **收口**：更新账本、证据、残余风险；未完成项显式标注。
10. **提交**：仅主控按路径提交；不跳过 hook。

## 6. 角色与指挥

| 角色 | 职责 | 禁止 |
| :--- | :--- | :--- |
| 主控 | 拆任务、派单、维护账本、集成、独立复验、提交、阶段验收 | 把验收外包给实现者；未复验就提交 |
| 实现 Agent | 在任务卡范围内实现与测试；提交证据包 | 提交、回滚、改他人文件、嵌套派单、缩范围 |
| 评审/红队 Agent | 只读复核、尝试证伪、检查作弊模式、独立跑命令 | 替实现者改代码；与实现者同一人 |
| 文档 Agent | 维护账本、阶段记录、索引 | 改代码、改门禁、掩盖未完成 |

派单必须使用 `01-反作弊与反偷懒执行铁律.md` §11.2 的任务卡字段；子 Agent 汇报必须使用 §11.5 模板。详细协议见该文件 §11。

## 7. 验收门槛

- 每个条目必须满足 `01` §14 的 DoD；缺一项只能是「待复核/阻塞」。
- 阶段验收必须包含：命令、退出码、原始日志、测试计数、修复前后对比、未验证项。
- 全量验收必须覆盖：前端 typecheck/ESLint/knip/单测/覆盖率、Rust 全量测试/clippy/治理基线、桌面构建产物门禁、移动端 typecheck/构建、E2E/真壳、依赖审计。
- 任何「环境失败」必须给出可复现证据与已尝试路径；不得直接归因于环境。
- 任何「flaky」必须提供 ≥3 次运行记录；不得用重跑绿了结案。
- 发布前总验收必须验证真实签名/公证/更新/安装链路；只改配置字段不算完成。

## 8. 变更与升级

- 本总纲、`01` 规范、`02` 账本的变更由主控提出，用户确认后生效。
- 任何 Agent 不得自行降低验收标准、扩大豁免、删除条目或改变阶段目标。
- 新增审计条目：追加到账本并标明来源（新发现/审计补充），不得挤掉既有条目。
- 条目废弃：状态改为 `cancelled`，写明理由、批准人与证据；不得直接删除行。
- 事故或 L3/L4 违规：建立 `05-事故与违规记录.md`，保留证据，按 `01` §13 处理。
