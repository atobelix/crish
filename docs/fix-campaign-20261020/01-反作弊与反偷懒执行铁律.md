# 统一修复战役 · Agent 反作弊与反偷懒执行铁律（2026-10-20）

> **效力**：仅在本战役工作区 `docs/fix-campaign-20261020/` 内强制；所有参与本战役的实现、评审、文档、调度 Agent 必须阅读并执行。本文件不挂载到 `AGENTS.md` / `.agents/AGENTS.md` 等 Agent 入口，也不替代仓库既有纪律。
> **依据**：`../full-audit-20261020/00-全面问题清单.md`、`AGENTS.md` §7 / §7.1、`.agents/LOGIC_PLAN_NO_RETREAT.md`、`FULL_CHECK_COMMANDS.md`。
> **核心原则**：诚实失败优于虚假通过；任务量守恒；标准只升不降；证据先于结论；全量门禁先于交付。
> **冲突处理**：当本文件与「快速交付」「先让 CI 变绿」「时间不够」「审查催得急」冲突时，以本文件为准。任何 Agent 不得自行降级标准，必须停止并上报。
> **配套文档**：战役总纲见 `00-战役总纲.md`；任务账本见 `02-统一修复任务账本.md`；问题总账见 `../full-audit-20261020/00-全面问题清单.md`；反退避契约见 `.agents/LOGIC_PLAN_NO_RETREAT.md`；提交纪律见 `AGENTS.md` §3。

## 0. 一句话铁律

**禁止用降低标准换取通过，禁止用缩小范围冒充完成，禁止用掩盖失败冒充修复，禁止以任务量大为由偷工减料。**

## 1. 适用范围与优先级

### 1.1 适用对象

- 所有在本仓库内工作的 Agent，包括主控、实现、分析、评审、文档、测试、发布与自动化维护 Agent。
- 所有任务类型：缺陷修复、重构、测试补齐、CI/门禁调整、数据迁移、发布配置、文档更新、审计收口。
- 所有交付形态：代码、测试、脚本、配置、文档、提交、发布产物。

### 1.2 强制优先级

1. 用户显式要求与验收标准。
2. `AGENTS.md`、本文件、`.agents/LOGIC_PLAN_NO_RETREAT.md`、`FULL_CHECK_COMMANDS.md`。
3. 本次任务书 / 审计问题条目 / 方案文档。
4. 效率、工期、实现便利性、生态惯例。

**效率与工期不是降低验收标准的理由。** 任务量大时，正确动作是增加分解、增加验证、增加证据，而不是减少验收项。**审查催促也不是降低标准的理由；审查越急，证据越要完整。**

### 1.3 禁止的自我降级

任何 Agent 不得单方面执行以下动作：

- 把「完整修复」改成「MVP / 简化版 / 先这样」。
- 把「全量门禁」改成「只跑相关测试」。
- 把「真壳验收」改成「单元测试通过」。
- 把「修复失败」改成「标记 flaky」。
- 把「未完成」改成「已完成，后续优化」。
- 把「门禁太严」改成「调整基线 / 放宽阈值」。
- 把「用户要求 A」改成「先做 A 的替代方案 A'」。

上述任何一项，若确有现实阻碍，必须提交「阻塞报告」，写明证据、影响、可选路径，由用户或主控裁决；不允许先做了再解释。

## 2. 行为分类与判定

| 类型 | 定义 | 典型表现 | 判定 |
| :--- | :--- | :--- | :--- |
| **A 类：硬作弊** | 伪造、隐瞒、篡改验证事实 | 编造测试结果；隐藏失败日志；删除/跳过测试；改基线让门禁变绿；`--no-verify`；伪造退出码 | 零容忍，任务驳回并回退 |
| **B 类：软作弊** | 不直接伪造，但通过降低标准或替换验证制造「通过」 | 降低覆盖率/性能阈值；扩大 allowlist；把集成测试降级为 mock；把 error 改成 warning；用 stub 假成功；只修表象 | 零容忍，任务驳回重做 |
| **C 类：偷懒** | 未穷举、未根因、未完成就交付 | 只修一个调用点；只测 happy path；不做回归；不读任务书；长任务缩范围；留下 TODO/stub | 任务驳回，补全后再验收 |
| **D 类：合法阻塞** | 有充分证据的未完成/不可完成 | 环境缺失、依赖未实现、产品决策未定；已给出复现证据与影响 | 允许，但必须显式标注「未完成」并列入未验证清单 |

**判定原则：**

- 「没做完」不是作弊；「没做完却声称做完」才是。
- 「测试失败」不是作弊；「把失败改成不失败」才是。
- 「环境阻塞」不是免责；必须给出可复现证据、已尝试路径与下一步。
- 任何 Agent 不得用「时间不够」解释未完成；只能说明未完成项与所需条件。

## 3. 零容忍红线（R-01～R-30）

### 3.1 证据与结果类

| 编号 | 红线 | 典型违规 |
| :--- | :--- | :--- |
| R-01 | 未运行命令却声称通过 | 「应该没问题」「本地已验证」但无命令、退出码、日志 |
| R-02 | 隐藏退出码或失败日志 | `cmd \| tee log \| tail`、`\|\| true`、`set +e`、`2>/dev/null`、只贴最后几行 |
| R-03 | 只报「通过」不报数量 | 不写测试文件数、用例数、失败数、忽略数、退出码 |
| R-04 | 截断/筛选日志掩盖失败 | 用 `grep -v FAILED`、只贴成功段、删除失败输出 |
| R-05 | 编造测试/覆盖率/性能数字 | 未跑覆盖率却写百分比；未跑 3 次却写 P99 |
| R-06 | 无证据归因 | 把代码失败说成环境问题，或把环境失败说成代码问题 |
| R-07 | 修改审计文档/任务状态掩盖未完成 | 把「未验证」改成「通过」，把「阻塞」改成「已完成」 |

### 3.2 标准与门禁类

| 编号 | 红线 | 典型违规 |
| :--- | :--- | :--- |
| R-08 | 降低阈值 | 覆盖率 45/70/65/45 下调；P99 SLA 放宽；行数上限上调 |
| R-09 | 扩大基线/豁免让门禁变绿 | 往 baseline 列表加文件；扩大 `UNWIRED_ALLOWLIST`；`ignore` 整个目录 |
| R-10 | 删除/跳过/弱化测试 | 删除失败用例；删断言；去掉负例/边界例；把 `expect` 改成 `expect(true)` |
| R-11 | 自动更新快照/黄金文件 | `--updateSnapshot` 后不审阅；直接覆盖预期输出 |
| R-12 | 绕过门禁 | `--no-verify`；禁用 hook；改 CI 只跑容易的子集；删除 job |
| R-13 | 把错误降级 | error 改 warning；改为 report-only；空 catch；静默降级 |
| R-14 | 缩小审计/门禁范围 | 从 CI 移除 package/job；只审计 6 个包却宣称全仓安全 |
| R-15 | 用 mock 替代真实验证 | 把 integration/E2E 改成 mock-only；真壳测试不存在却宣称端到端通过 |
| R-16 | 用忽略逃避失败 | `#[ignore]`、`it.skip`、`describe.skip`、`test.only`、`should_panic` 掩盖错误 |
| R-17 | 全局压制告警 | 文件级 `eslint-disable`、`@ts-ignore`、`#[allow(...)]`、`#![allow(...)]` |
| R-18 | 绕过类型系统 | `any`、双重断言、`unknown as`、`@ts-expect-error` 掩盖真实类型错误 |
| R-19 | 绕过设计 Token SSOT | `var(--token, hsl(...))` 假兜底；硬编码颜色；JS 直接注入 A 类 Token |
| R-20 | 隐藏运行时错误 | `unwrap_or_default`、空 `catch`、`let _ =`、默认成功返回值、静默 fallback |
| R-21 | 保留假成功/占位实现 | 后端 stub 恒返回成功；前端提示「已安装」；生产路径留 `TODO` 却宣称完成 |
| R-22 | 只修一个点 | 审计列出 10 处，只改 1 处；同类调用点不搜索、不修复 |
| R-23 | 只改文档不改行为 | 把「未接线」写成「已实现」；用注释替代代码修复 |
| R-24 | 只做 happy path | 无边界、无负例、无回归、无失败路径测试 |
| R-25 | 长任务缩范围 | 把大任务拆成若干块后只交付容易的块，难块静默丢弃 |
| R-26 | 不读任务书就改 | 未读审计条目、方案、相关源码与测试，凭猜测打补丁 |
| R-27 | 用重构逃避根因 | 大范围重写、过度抽象、引入新框架来绕开一个具体缺陷 |
| R-28 | 子 Agent 越权 | 子 Agent 提交、回滚、改他人文件、创建嵌套 Agent |
| R-29 | 破坏测试/资产/并发纪律 | 删除 `reference/markdown-editor` 测试；同文件多 Agent 并发写 |
| R-30 | 用「flaky」逃避根因 | 失败就重跑直到绿，不做 3 次以上证据与根因分析 |

**上述 30 条不因任务紧急、问题简单、改动很小而豁免。**

## 4. 任务分级与大型任务强制协议

### 4.1 分级

| 级别 | 判定 | 最低要求 |
| :--- | :--- | :--- |
| **S** | 单文件、单点、无跨层影响 | 根因说明 + 定向测试 + 相关门禁 |
| **M** | 2–5 个文件、单域 | 任务卡 + 影响面搜索 + 回归测试 + 相关门禁 |
| **L** | >5 个文件，或跨层、跨 crate、CI/门禁、数据迁移、发布配置 | 完整执行 §4.2；分阶段验收；独立评审 |
| **XL** | 多个 L、多个域、发布闭环或全仓治理 | 总账 + 阶段门禁 + 多 Agent 编排 + 每阶段独立验收 |

任务级别由影响面决定，不由「看起来难不难」决定。**把 L/XL 当 S 做，属于偷懒。**

### 4.2 大型任务强制协议（L/XL 必须逐项执行）

1. **读全输入**：审计条目、任务书、`AGENTS.md`、本文件、相关源码、测试、CI、历史修复记录。
2. **建任务账本**：列出全部子项、验收断言、涉及文件、依赖边、负责人、禁止捷径、证据路径。禁止只写一句「修复 X」。
3. **基线取证**：记录 HEAD、工作区状态、复现命令、退出码、失败日志、测试计数、门禁数字。未取证不得开工。
4. **全量影响面搜索**：用 `grep`/`rg` 搜索所有同类调用点、测试、文档、CI、脚本；列出「已确认要改 / 确认不改及理由」。
5. **根因分析**：定位到 `文件:行号` 与数据流/状态机；区分代码缺陷、测试基线错误、文档错误、CI 缺口。禁止先改再找原因。
6. **最小正确方案**：给出方案与被拒绝的捷径清单；禁止用降低标准、扩大豁免、假成功、mock 替代来「解决」。
7. **分解与排期（逻辑序）**：按依赖排序，不按「哪个容易先做」。拆分不得减少总验收项；每个子项必须有归属与收口标准。
8. **测试先行**：能复现的先写失败测试（红），再修到绿；无法写测试的必须说明原因并给出替代验证。
9. **全量验证**：按 §7 跑定向、回归、全量快层/中层/相关慢层；保留原始日志与退出码。
10. **对抗评审**：由不同 Agent 做红队复核；主控 100% 审 diff，并独立复跑关键命令。
11. **收口**：更新任务账本、审计文档、未验证清单、残余风险；文档与代码同步，不得只改一边。
12. **禁止半成品交付**：除非用户明确同意分批，否则不得以「先交一部分」结束 L/XL 任务。

### 4.3 「任务量大」的正确处理

- 任务量大 → 增加分解、增加验证、增加证据、增加评审；**不是**减少验收、减少测试、减少范围。
- 拆分子任务必须保持「任务量守恒」：所有原子项最终都要完成，不能拆着拆着消失。
- 不允许用「先做 P0」砍掉 P1/P2；用户未明确排序时，审计条目同权。
- 不允许用「时间不够」把未完成项标成「后续优化」；只能标「未完成/阻塞」并列入清单。
- 不允许把大任务交给一个 Agent 黑箱完成；必须有可见的任务账本与阶段产物。

## 5. 标准修复流程（八步法）

### 第一步：基线与复现

- 记录 `git rev-parse HEAD`、`git status --short`、当前分支、运行环境。
- 执行最小复现命令，记录**完整命令、退出码、原始日志路径**。
- 不用 `tail` 代替完整日志；至少同时检查 `FAILED`、`error`、`panic`、`FAIL`、`warning`。
- 失败基线未建立，不得开始改代码。

### 第二步：影响面盘点

- 搜索缺陷符号/模式的所有出现：生产代码、测试、脚本、文档、CI、配置。
- 列出所有需要同步修改的文件；不能只修报告里点名的那一处。
- 对「同类问题」给出全量清单；无法确认时标记「待确认」，不得默认为不存在。

### 第三步：根因定位

- 必须回答：错误发生在哪一层？触发条件是什么？为什么现有测试/门禁没有拦住？
- 区分：实现缺陷、测试基线错误、契约不一致、文档过期、CI 未接线、环境限制。
- 根因未定位前，禁止用「加重试」「加延时」「加 try/catch」「改断言」等方式让现象消失。

### 第四步：方案设计

- 选择最小正确改动；优先修根因，不修表象。
- 列出至少一个被拒绝的捷径，并说明为什么拒绝（例如「提高基线」会让同类回潮无法被发现）。
- 若涉及契约/数据/发布，先写迁移与回滚方案。
- 若任务书要求与现状冲突，停止并上报，不自行选择简单路径。

### 第五步：实现

- 只改与任务相关的文件；不做无关重构、不引入不必要抽象。
- 保持中文注释、UTF-8 无 BOM、仓库既有代码风格。
- 不新增未登记 TODO/stub/抑制；确需新增，必须带 issue ID、理由、负责人、到期条件。
- 测试先行：先让新测试在旧实现上失败，再修到通过。

### 第六步：验证

- 定向测试：新增/修改用例、相邻模块回归。
- 全量门禁：按 `FULL_CHECK_COMMANDS.md` 与 CI 实际阻断面执行。**若 `FULL_CHECK_COMMANDS.md` 缺少 CI 已有门禁，以 CI 为准并补文档；不得用文档缺项作为跳过理由。**
- 失败用例必须解释；不允许以「与本次无关」跳过，除非有依赖分析证明。
- 性能/稳定性问题至少 3 次运行，报告分布，不得只挑一次通过的结果。
- UI 必须真机/Tauri MCP 验证；数据必须验证升级/回滚；发布必须验证真实产物。

### 第七步：评审

- 自审 diff：逐行确认没有夹带、没有 suppression、没有删除测试、没有降低阈值。
- 交叉评审：由未参与实现的 Agent 复核；红队只读，不替实现者改代码。
- 主控独立复跑关键命令，不直接相信子 Agent 的「已通过」。

### 第八步：收口

- 更新任务账本与审计文档；记录已修复、未修复、未验证、残余风险。
- 证据包归档；原始日志保留路径。
- 未完成项必须显式标注，不允许用「基本完成」模糊表述。
- 只有主 Agent 可以提交；提交前确认工作区只包含预期文件。

## 6. 证据标准

### 6.1 每个任务必须提交的证据包

```text
任务 ID：
审计 ID：
HEAD：
工作区状态：
复现命令：
退出码：
原始日志路径：
修复前结果：
修复后结果：
新增/修改测试：
全量门禁结果：
未验证项：
残余风险：
变更文件：
```

### 6.2 证据硬性要求

- **命令与退出码**：必须写实际执行的命令和真实退出码；不能只写「通过」。
- **完整日志**：保留原始日志；总结不能替代原始输出。
- **测试计数**：文件数 / 用例数 / passed / failed / ignored；缺一不可。
- **前后对比**：修复前失败、修复后通过；性能/覆盖率给前后数字。
- **可复现**：另一 Agent 按记录能重新执行并得到相同结论。
- **UI 证据**：Tauri MCP 操作步骤、关键截图/状态；单元测试不能替代真机验收。
- **数据证据**：旧数据升级、迁移、回滚、异常中断场景。
- **发布证据**：真实构建产物、签名/公证状态、更新安装链路；不能只看配置字段。
- **性能证据**：至少 3 次运行的 P50/P95/P99 与环境说明；不允许只报最好的一次。

### 6.3 退出码纪律

- 管道命令必须保留真实退出码：使用 `set -o pipefail` 或 `${PIPESTATUS[0]}`；禁止 `cmd | tee log | tail` 后把 `tail` 的 0 当作通过。
- 禁止 `|| true`、`; true`、`set +e` 掩盖失败。
- 日志结尾若出现 `FAILED` / `error:` / `panicked`，即使退出码为 0 也必须解释；不能直接判通过。
- 任何「后台任务 exit 0」必须与日志内容交叉验证。

**无证据 = 未完成。日志有失败 = 未通过。**

## 7. 测试与验证完整性

### 7.1 测试层级不可互相替代

| 层级 | 作用 | 不可替代性 |
| :--- | :--- | :--- |
| 单元测试 | 纯逻辑、边界、状态机 | 不能证明真实集成/UI |
| 集成测试 | 跨模块、真实 DB/真实 IPC | 不能用 mock 单测替代 |
| 真壳 E2E | Tauri/Windows 真实运行 | 不能用 Vitest/Playwright mock 替代 |
| 性能/压力 | P99、并发、死锁 | 不能只跑一次功能测试 |
| 发布验证 | 安装、升级、签名、回滚 | 不能只看配置文件 |

### 7.2 缺陷修复的最低测试要求

- 每个代码缺陷必须有**回归测试**：在旧代码上失败，在新代码上通过。
- 修复边界条件时，必须覆盖：正常、边界、异常、空值、超限、并发（如适用）。
- 修复数据/路径问题时，必须覆盖旧数据升级与失败回滚。
- 修复 UI 问题时，必须有组件测试 + 真机验收。
- 修复 CI/门禁问题时，必须验证「门禁能拦住原始缺陷」，不能只验证门禁本身退出 0。
- 纯文档修改可以不做代码测试，但必须给出文档链接、影响范围与校验方式。

### 7.3 覆盖率纪律

- 不得降低仓库/包/文件的覆盖率阈值。
- 修改文件的行覆盖率不得低于修改前；新增分支必须有测试。
- 不得通过排除文件、排除目录、忽略未覆盖代码来「提高」覆盖率。
- 覆盖率报告必须包含真实统计口径；不得用「估算」代替。

### 7.4 抑制与豁免纪律

- 禁止文件级/目录级 blanket suppression。
- 行级 suppression 必须同时具备：`issue ID + 原因 + 负责人 + 到期/移除条件`。
- 新增 `eslint-disable`、`@ts-ignore`、`@ts-expect-error`、`#[allow(...)]`、`#[ignore]`、`it.skip`、`test.only`，必须在同一任务中说明为何不能用正确实现替代。
- 禁止在提交中遗留 `test.only`；CI 应硬阻断。
- 禁止删除、跳过、重命名测试来规避失败；测试资产受 `AGENTS.md` §9 保护。
- 禁止自动接受 snapshot 变化；必须人工审阅差异并说明为什么新输出是正确的。

### 7.5 Flaky 处理

- 任何「flaky」结论必须有至少 3 次独立运行的耗时/结果记录。
- 必须给出根因或明确「根因未定位」；不得用「重跑绿了」结案。
- 允许隔离（quarantine）的唯一条件：有 issue、有负责人、有到期时间、有独立 job 持续观测；隔离不得扩大。
- 功能测试的偶发失败优先按真实缺陷处理，不得默认归因于环境。
- 性能阈值抖动应报告分布（P50/P95/P99、失败次数），由用户/架构裁决是否调整；实现 Agent 无权自行放宽。

### 7.6 真实环境纪律

- 涉及 Tauri/WebView2/窗口/输入法/焦点/主题/拖拽的改动，必须通过 Tauri MCP（4000）验收；禁止 CDP 9222。
- 涉及数据库、文件路径、日志、产出目录的改动，必须在真实 app data dir / 真实临时目录验证。
- 涉及发布/更新/签名的改动，必须验证真实安装包与升级链路，不能只改 JSON。
- 涉及移动端的改动，必须在 Metro/Expo 构建链路验证，不能只跑 typecheck。

## 8. 代码修改红线

### 8.1 禁止的「修复」方式

| 禁止方式 | 为什么禁止 | 正确替代 |
| :--- | :--- | :--- |
| 加 `try/catch` 吞掉异常 | 错误被隐藏，用户看到假成功 | 记录上下文并向上传播/显式失败 |
| `unwrap_or_default()` 返回空结果 | 把失败伪装成正常空数据 | 返回错误/显式 fallback 状态并测试 |
| 后端 stub 恒返回成功 | 前端闭环演示变成欺骗 | 实现真实链路，或明确返回「不可用」 |
| 前端 toast「已安装更新」但后端未实现 | 用户被误导 | 未实现前移除入口或禁用并说明 |
| 用 mock 替代真实数据库/真实 IPC | 测试通过但生产失败 | 集成测试使用真实边界；mock 只用于外部服务 |
| 只修一个调用点 | 同类缺陷继续存在 | 全量搜索并修复所有调用点 |
| 加重试/延时让测试变绿 | 掩盖竞态或性能问题 | 定位竞态/超时根因，加确定性同步 |
| 改断言匹配错误输出 | 把 bug 固化为契约 | 先判断产品正确行为，再修实现或测试并留证据 |
| 改基线/阈值让门禁通过 | 标准侵蚀，问题回潮不可见 | 修实现；基线变更走 §9 审批 |
| 大范围重写/换框架 | 用重构逃避根因，引入新风险 | 最小正确修复；必要时先出方案与验收 |

### 8.2 具体实现红线

- **Store**：禁止生产代码直接 `useXStore.setState`；必须经 store action/facade。
- **React Hooks**：禁止条件调用 Hook、早退后调用 Hook、在循环/回调中调用 Hook。
- **更新/发布**：禁止假成功、假进度、假安装；未实现必须显式不可用。
- **错误处理**：禁止空 catch、`let _ =`、静默 fallback、默认成功；必须有日志上下文或用户可见错误。
- **Token/样式**：禁止假 Token 兜底、硬编码颜色、越界线宽、JS 注入 A 类 Token。
- **类型**：禁止 `any`、双重断言、`unknown as` 绕过真实类型问题；确需窄化必须有运行时校验。
- **安全**：禁止对不可信内容使用 `innerHTML`；禁止命令注入、路径穿越、明文密钥；新增 `unsafe` 必须独立安全评审。
- **数据路径**：release 数据必须放 app data dir；禁止把数据库/日志/工作区放 exe 目录。
- **资源清理**：删除会话必须级联清理 stream、snapshot、terminal、runtime、outputs、session_meta；不能只删 UI 记录。
- **死代码**：要么接线，要么删除；不得保留「已实现但永远不调用」的生产模块。
- **占位/TODO**：生产路径不得长期保留 stub/TODO；必须关联 issue、负责人、验收条件。

## 9. 基线、阈值与豁免变更的合法路径

### 9.1 唯一合法变更流程

1. **证明现有基线错误**：给出测量工具/口径错误的证据，而不是「数字太高不方便」。
2. **独立变更**：基线/阈值变更必须与功能修复分开提交，禁止混在一个「修复」里偷偷放水。
3. **前后对比**：记录旧值、新值、受影响文件/指标、为什么不会掩盖真实回退。
4. **风险与期限**：说明风险、补偿措施、负责人、到期复核条件。
5. **审批**：由用户或主控（经用户明确授权）批准；实现 Agent 无权自行决定。
6. **回归证明**：变更后必须证明原始缺陷仍能被其它门禁/测试拦住。
7. **零容忍项不可豁免**：安全、数据丢失、假成功、测试删除、门禁绕过不得进入豁免流程。

### 9.2 合法 vs 不合法示例

| 场景 | 合法做法 | 不合法做法 |
| :--- | :--- | :--- |
| 文件超行数 | 拆分文件；或登记基线并给出拆分计划与到期日 | 直接把文件加入 baseline，永久豁免 |
| 测试 fixture 假设错误 | 用生产 token 计数证明假设错误，修 fixture 并保留回归 | 改断言迁就现状，不确认产品行为 |
| 性能断言偶发失败 | 3 次以上数据 + 分布 + 架构裁决；移入 nightly 并保留报告 | 直接放宽 50ms 到 100ms，或重跑直到绿 |
| 覆盖率不足 | 补测试；对确实不可测的边界写理由并评审 | 排除文件/目录，或下调阈值 |
| 历史遗留告警 | 分阶段清零，冻结新增，登记到期 | 新增 blanket suppression，或把 error 改 warning |
| CI 某个 job 太慢 | 拆分 job、并行化、缓存，保留全部检查 | 删除 job / 只跑子集 / 加 `continue-on-error` |

**标准只升不降：允许把基线收紧，不允许为了让当前分支变绿而放宽。**

## 11. 多 Agent 指挥协议

> 后续修复战役由主 Agent 统一指挥。所有 Agent 必须按本节角色与边界工作。

### 11.1 角色

| 角色 | 职责 | 禁止 |
| :--- | :--- | :--- |
| **主控 / Orchestrator** | 拆任务、派单、维护账本、集成、独立复验、提交、最终验收 | 把验收外包给实现者；未复验就提交 |
| **实现 Agent** | 只执行分配的任务；改代码/测试；提交证据包 | 提交、回滚、改他人文件、嵌套派单、缩范围 |
| **评审 / 红队 Agent** | 只读复核；尝试证伪；检查作弊模式；独立跑关键命令 | 替实现者改代码；与实现者同一人 |
| **文档 / Scribe Agent** | 更新账本、审计文档、索引 | 改代码、改门禁、掩盖未完成 |

### 11.2 派单必须包含的字段

```text
任务 ID：
对应审计 ID：
任务级别：S / M / L / XL
目标与非目标：
允许修改的文件：
禁止修改的文件：
必须运行的命令：
验收断言（逐条）：
明确禁止的捷径：
证据包格式：
依赖与串行约束：
完成定义（DoD）：
```

- 禁止派发「把 X 修好」这类无验收、无文件域、无证据要求的任务。
- 同一文件同一时间只能有一个写 Agent；冲突任务必须串行。
- 每个子 Agent 只做一件事；任务过大必须拆分，但拆分后总量守恒。
- 子 Agent 必须深度 1，不得嵌套；不得提交（`AGENTS.md` §3）。
- 子 Agent 只能读最终计划/任务卡，不得自行扩大范围；发现未覆盖问题上报主控。

### 11.3 主控验收义务

1. **100% 审 diff**：逐文件确认变更范围、无夹带、无 suppression、无测试删除、无阈值下调。
2. **独立复跑**：至少复跑关键失败用例、全量门禁中的阻断项；不得只读子 Agent 报告。
3. **证据核验**：检查退出码、原始日志、测试计数、前后对比；发现日志含 FAILED 即驳回。
4. **红队复核**：对 L/XL 任务必须由不同 Agent 做对抗评审；主控不能既实现又唯一评审。
5. **提交纪律**：只有主控可提交；`git commit --only <paths>` 限定路径；禁止 `--no-verify`；禁止破坏性 git 操作。
6. **账本同步**：每个任务状态与证据写入任务账本；未完成项保留在清单，不得删除。
7. **不信任原则**：子 Agent 的「已完成」只作为待验证声明，不作为验收结论。

### 11.4 并行与冲突

- 遵循 `AGENTS.md` §2：每轮 5–12 个子 Agent，同时存活 ≤16，深度仅 1；收尾阶段可少于 5。
- 文件域互斥优先于并行度；同文件任务串行。
- 大型任务按阶段推进：基线 → 修复 → 测试 → 全量门禁 → 红队 → 收口；每阶段有独立验收，不得跳阶段。
- 子 Agent 空返回按 `AGENTS.md` §2 处理；空返回不等于完成，必须核查落盘与 `git status`。
- 可选：对独立大任务使用隔离 worktree；由主控合并，子 Agent 仍不得提交或回滚。

## 12. 审查与红队检查清单

### 12.1 Diff 审查

- [ ] 是否只改了任务允许的文件？
- [ ] 是否夹带无关重构/格式化/重命名？
- [ ] 是否删除/跳过/弱化任何测试？
- [ ] 是否新增 `eslint-disable`、`@ts-ignore`、`#[allow]`、`#[ignore]`、`test.only`？
- [ ] 是否修改基线/阈值/覆盖率/CI 范围？
- [ ] 是否把 error 改成 warning/report-only？
- [ ] 是否引入 stub/假成功/空 catch/静默 fallback？
- [ ] 是否只修一个调用点，遗漏同类？
- [ ] 是否新增未登记 TODO/FIXME？
- [ ] 是否修改生成的快照/黄金文件而未审阅？

### 12.2 测试审查

- [ ] 新测试在旧代码上是否真的失败？（红→绿证据）
- [ ] 是否覆盖边界、异常、空值、超限、并发？
- [ ] 是否只测 happy path？
- [ ] 是否用 mock 替代了被测对象？
- [ ] 测试断言是否真的验证行为，而不是验证 mock 调用？
- [ ] 是否存在 `expect(true)`、无断言、只跑不验？
- [ ] 测试是否依赖执行顺序/时间/随机数而未固定？
- [ ] 覆盖率是否下降？
- [ ] ignored/skip 是否有 issue、负责人、期限？

### 12.3 证据审查

- [ ] 命令是否真实执行？退出码是否为 0？
- [ ] 原始日志是否存在且完整？
- [ ] 日志中是否仍有 `FAILED` / `error` / `panic`？
- [ ] 测试计数是否完整（files/tests/passed/failed/ignored）？
- [ ] 修复前后对比是否可复现？
- [ ] 性能是否 ≥3 次并有分布？
- [ ] UI 是否真机验收？数据是否验证升级/回滚？
- [ ] 发布是否验证真实产物而非配置字段？

### 12.4 红队反问

1. 这个修复如果回退，测试会变红吗？
2. 这个测试如果换回旧实现，会失败吗？
3. 有没有更简单的「假绿」方式被使用？
4. 同类问题在全仓还有多少处？
5. 这个门禁真的能拦住原始缺陷，还是只拦住了表面现象？

8. 这个基线变更是否在掩盖回潮？
9. 这个 UI 结论是否只在 mock 中成立？
10. 这个数据路径是否在 release 形态下仍然正确？

### 12.5 自动化反作弊门禁（后续必须接线）

在统一修复战役开始前，主控应把以下检查接入 CI 或 pre-commit；未接线前由主控人工执行同等检查：

- **Diff 模式扫描**：新增 `eslint-disable`、`@ts-ignore`、`#[allow(`、`#[ignore]`、`it.skip`、`test.only`、`expect(true)`、`--no-verify`、`|| true`、`set +e`。
- **测试删除检测**：diff 中出现删除测试文件/删除 `it(`/`test(`/`#[test]`/断言时，必须人工审批并给出替代测试。
- **阈值/基线变更检测**：任何 baseline、coverage threshold、SLA、allowlist、CI job 范围变更，必须单独标记并阻断自动合并。
- **退出码与日志一致性**：CI 收集原始日志；日志出现 `FAILED`/`error`/`panic` 时不得标记绿色。
- **测试数量不下降**：同一包/模块的测试用例数不得因修复而减少；确需删除重复/错误测试，必须有证明与审批。
- **覆盖率不下降**：修改文件覆盖率与全仓阈值均不得下降。
- **任务账本校验**：每个审计 ID 必须有状态、证据路径、验收人；「完成」缺少证据时自动驳回。
- **提交路径校验**：只允许主控提交；PR/提交中出现测试资产、门禁文件、基线文件的可疑修改时强制人工复核。

> 自动化门禁的作用是降低审查成本，不是替代红队与主控复验；任何「门禁没报错」都不能代替真实运行与证据审查。

## 13. 违规处理与熔断

| 级别 | 行为 | 处理 |
| :--- | :--- | :--- |
| **L1** | 证据不完整、报告遗漏、未复跑 | 驳回补证；不计完成 |
| **L2** | 范围缩水、测试不足、同类未修、未登记 suppression | 任务驳回重做；主控不得提交 |
| **L3** | 伪造结果、隐藏失败、删除/跳过测试、降低阈值、绕过门禁 | 先保留证据并隔离该 Agent 的改动；主控仅对其文件做精确 edit 回退（禁止全局 reset/clean/checkout）；替换 Agent；记录事故；重新审计 |
| **L4** | 数据丢失、安全漏洞、发布假成功、破坏测试资产 | 立即停止相关任务；通知用户；保留证据；事故报告与全量复核 |

- **诚实阻塞不处罚**：D 类阻塞允许存在，但必须写入未验证清单。
- **重复违规**：同一 Agent 在战役中累计 2 次 L2 或 1 次 L3，移出该战役。
- **主控同样受约束**：主控不得以「收口压力」为由接受假绿；违反时由用户直接裁决。
- **不搞连坐**：只处理违规行为与责任人，不因一个 Agent 违规否定其他 Agent 的真实产物；但必须复核其经手的所有结论。

## 14. 完成定义（DoD）总清单

一个任务只有同时满足以下条件，才能标记「完成」：

- [ ] 对应审计 ID 的全部验收项已满足，未缩范围。
- [ ] 根因已定位到 `文件:行号`，不是只修表象。
- [ ] 同类问题已全量搜索并处理，或逐项说明不改理由。
- [ ] 有回归测试，且证明旧实现会失败、新实现通过。
- [ ] 边界、异常、空值、超限、并发（如适用）已覆盖。
- [ ] UI 改动已真机/Tauri MCP 验收。
- [ ] 数据/路径改动已验证升级、回滚、异常中断。
- [ ] 发布/更新改动已验证真实产物与安装链路。
- [ ] 全量门禁按 `FULL_CHECK_COMMANDS.md` 执行，退出码 0，日志无 FAILED/error/panic。
- [ ] 没有降低任何阈值、覆盖率、性能 SLA 或门禁范围。
- [ ] 没有删除/跳过/弱化测试，没有自动接受快照。
- [ ] 没有新增未登记的 suppression/TODO/stub/假成功。
- [ ] 没有绕过 `--no-verify` 或 hook。
- [ ] 文档、审计账本、CI 配置与代码同步。
- [ ] 证据包完整，原始日志可复现。
- [ ] 未完成项与残余风险已显式列出，没有被「基本完成」掩盖。
- [ ] 只有主控提交，且提交路径限定；工作区无意外文件。
- [ ] 红队评审通过；L/XL 任务有独立评审记录。

**任何一项不满足，状态只能是「未完成 / 阻塞 / 待复核」，不能是「完成」。**
