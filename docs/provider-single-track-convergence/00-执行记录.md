### 根因（跨层契约断裂）

1. 前端 `apps/crish-desktop/src/api/session-persistence/sessionRustDbWriteGuard.ts:41`：`let batchVersionCounter = 0;`；`:59-61`：`nextBatchVersion() { return ++batchVersionCounter; }` —— **模块级内存计数器，每次进程启动从 0 开始** ⇒ **首批恒为 1**。
2. 同文件 `:38-39` 注释明示：「Wave C 后内存侧不再做 CAS 比较/丢弃（writtenBodyBatchVersions 已删）；**版本仅作 IPC 观测**与未来 Rust 侧可选消费」。
3. 后端 `crates/conex-db/src/messages.rs:118-138` 却把它当 **CAS 令牌**：`if batch_version <= current { return CasConflict }`，其中 `current = SELECT body_version FROM sessions WHERE id = ?`。
4. 库中 `body_version` 是**上次运行**留下的值（`messages.rs:209-213`：`Some(v)` 写入时 `body_version = v`）。
5. ⇒ 重启后首批 `1 <= current(数十)` 恒成立 ⇒ **CasConflict** ⇒ 65 个会话正文全部写不进 SQLite。
6. 观测面缺口：前端 `sessionRustDbSql.ts:159` 只记 `{command, sessionId, batchVersion, status}`，**不含后端错误消息**，日志无法区分 CasConflict 与其他错误。

### 为什么「首批传 `null`」不足以修复

`None` 分支（`messages.rs:214-219`）**只更新 `message_count`、不推进 `body_version`**。首批 rebase 成功后，第二批传 `Some(2)` 仍会 `2 <= current(47)` 冲突。⇒ 正确修法是让**前端版本戳与库中 `body_version` 连续**，而非仅豁免首批。

### 修法方向（待独立一轮实施；**不得弱化 CAS 防线**）

- 后端：暴露 `body_version` 读面（`SessionIndexEntry` 增字段，或新增只读命令）；
- 前端：`nextBatchVersion` 改为「进程内首次调用以库中 `max(body_version)` 为基线，此后递增」，首批不再固定 1；
- 观测面：`persist-degraded-ls` 记录带后端错误消息（至少区分 `CasConflict`）；
- 测试：补「重启后首批保存成功、且 CAS 仍能拦截过期批次」的回归断言（正逆向对称）。

### 用户侧影响

会话正文写不进 SQLite ⇒ 持久化降级到 localStorage ⇒ **重启/换窗口可能丢最近消息**，且 UI 会提示持久化降级。
