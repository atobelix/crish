## 一、执行概述与核心战果

本次任务针对历史消息在水合、持久化转换、合并去重与引擎事件投影回放中的**乱序、字段丢失、因果倒置与连续消息塌缩**四大致命缺陷（RC-02 ~ RC-06）进行了深度穿透根治：

### 核心战果速览

1. **根治 RC-02（全会话因果自愈误判与乱序洗牌 Bug）**：
   - 彻底修复 `hasRoleIdInversion`：明确排除 UUID（`/^[0-9a-f]{8}-[0-9a-f]{4}-/i`）及 16 进制长哈希，仅当两个同角色 ID 均为**显式同前缀递增计数器**（如 `user-msg-1` / `user-msg-2`）时才比对 ID 逆序，杜绝了含数字随机 UUID 误判率高达 99%+ 的灾难。

## 二、四大核心缺陷逐项修复详解

### 1. 根治 RC-02：`healMessagesCausalOrder` 全会话乱序洗牌 Bug

#### 缺陷机制

原 `sessionHydrationMessages.ts` 中的 `healMessagesCausalOrder` 存在两个致命设计断层：

1. `hasRoleIdInversion` 使用 `/\d/.test(id)` 作为「ID 是否可做因果序列比对」的依据，而随机生成的 32 位十六进制 UUID（形如 `9b1deb4d-...`）包含数字的概率接近 100%。只要任意两个同角色 UUID 字典序倒置，即误判整段会话「因果损坏」。
2. 原代码第 307 行在完成了局部分组后，又对**跨越整场会话全部时间戳的全局数组 `healed`** 执行了一次 `if (isCausalGroupCorrupted(healed)) healed = healCausalGroup(healed);`。这导致整场多轮会话的所有 User 消息和 Assistant 消息被抽离出来、完全无视时间戳按 UUID 字典序机械交错，第 1 轮的问题配上第 5 轮的回答，并把时间戳强行夹逼改写！

#### 修复落地（`apps/crish-desktop/src/api/session-persistence/sessionHydrationMessages.ts`）

1. **显式排除 UUID 与十六进制哈希**：
   ```ts
   function isUuidOrHexHash(id: string): boolean {
     return (
       /^[0-9a-f]{8}-[0-9a-f]{4}-/i.test(id) || /^[0-9a-f]{16,}$/i.test(id)
     );
   }

   function extractExplicitCounter(
     id: string
   ): { prefix: string; seq: number } | null {
     if (!id || isUuidOrHexHash(id)) return null;
     const m = id.match(/^(.*?[^\d])(\d+)$/);
     if (m) {
       const num = Number.parseInt(m[2]!, 10);
       return Number.isFinite(num) ? { prefix: m[1]!, seq: num } : null;
     }
     if (/^\d+$/.test(id)) {
       const num = Number.parseInt(id, 10);
       return Number.isFinite(num) ? { prefix: '', seq: num } : null;
     }
     return null;
   }
   ```
2. **仅在同前缀计数器时检测角色倒置**：
   在 `isCausalGroupCorrupted` 中，`hasRoleIdInversion` 仅当两个相邻同角色消息的 `extractExplicitCounter` 均存在且 `prevCounter.prefix === currCounter.prefix` 时比对 `prevCounter.seq > currCounter.seq`。
3. **彻底删除跨时间戳全会话洗牌**：
   移除原 307 行对全量 `healed` 数组的 `healCausalGroup` 调用，因果修复仅在同毫秒时间戳桶 `run.length > 1` 时局部进行；原有合法递增时间戳与序列号严格保真。

### 2. 根治 RC-03：`parseSessionMessage` 字段丢弃与展示层过滤联动 Bug

#### 缺陷机制

原 `sessionHydrationMessages.ts:16` 中的 `MSG_STATUSES` 仅包含 `['queued', 'processing', 'completed']`，历史中的 `'error'` 状态被抹除；`parseTimelineBlocks` 漏掉 `'image' | 'step_start' | 'step_end'`；`parseSessionMessage` 漏掉顶层 `injections`、`attachments`、`images`、`errorDetail`、`metadata`。当一条助手消息是报错中断、纯图片回复或系统注入卡片时，由于文本为空且 blocks 被剥离，展示层 `isRenderableAssistantMessage` 返回 `false`，导致消息在 UI 上凭空蒸发。

#### 修复落地（`apps/crish-desktop/src/api/session-persistence/sessionHydrationMessages.ts`）

1. `MSG_STATUSES` 扩充：
   ```ts
   const MSG_STATUSES = new Set<NonNullable<SessionMessage['status']>>([
     'queued',
     'processing',
     'completed',
     'error',
   ]);
   ```
2. `parseTimelineBlocks` 支持完整块类型：
   ```ts

     msg.metadata = o.metadata;
   ```

### 3. 根治 RC-04：Wire 层与合并辅助漏透传 `engineSequence` Bug

#### 缺陷机制

从 SQLite 读取的 `RustSessionMessage` 接口未定义 `engineSequence`，导致从 Rust 还原出的消息 `engineSequence` 全为 undefined。此外，`mergeSessionMessageFields` 在内存合并时未拷贝 `incoming.engineSequence`。当内存已有消息（`seq = undefined`）与水合消息合并时，排序键退化为 `Number.MAX_SAFE_INTEGER`，在第一优先级按 seq 排序时直接被沉底到队列最末端。

#### 修复落地

1. **`apps/crish-desktop/src/api/session-persistence/sessionRustDbWire.ts`**：
   - 在 `RustSessionMessage` 中增加可选字段：`engineSequence?: number | null;`
   - 在 `toRustSessionMessage` 中序列化：`if (msg.engineSequence != null) out.engineSequence = msg.engineSequence;`
   - 在 `fromRustSessionMessage` 中反序列化：`...(rust.engineSequence != null ? { engineSequence: rust.engineSequence } : {}),` 并导出 `fromRustSessionMessage` 供测试复用。
2. **`apps/crish-desktop/src/store/sessionSharedHelpers.messageMerge.ts`**：
   - 在 `mergeSessionMessageFields` 中透传保留 `engineSequence`：
     ```ts
     if (
       typeof incoming.engineSequence === 'number' &&
       Number.isFinite(incoming.engineSequence)
     ) {
       existing.engineSequence = incoming.engineSequence;
     }
     if (incoming.injections !== undefined)
       existing.injections = incoming.injections;
     if (incoming.attachments !== undefined)
       existing.attachments = incoming.attachments;
     if (incoming.images !== undefined) existing.images = incoming.images;
     if (incoming.errorDetail !== undefined)
       existing.errorDetail = incoming.errorDetail;
     if (incoming.metadata !== undefined) existing.metadata = incoming.metadata;
     ```

### 4. 根治 RC-05 & RC-06：事件回放投影时间戳失真与跨 Turn 塌缩

#### 缺陷机制

1. **连续 Assistant 消息塌缩（RC-06）**：`projectEventsToMessages` 仅在 `pushUser` 时将 `currentAssistant` 重置为 `null`。遇到跨 Turn 的多轮连续 Assistant 回复（例如自主规划多步工具调用）或未触发 `pushUser` 时，后一条带有新稳定 ID 的 assistant 事件被持续拼接到前一条已完成的消息上，且 ID 重键被拒绝，导致多条消息被强行压扁为单条。
2. **无时间戳回放失真（RC-05）**：`extractMessageTimestamp` 对 `message-delta`/`tool-start` 回退当前时间 `Date.now()`，但对 `message-end` 回退 `0`。历史回放时 assistant 先在 delta 拿到 `Date.now()`，后续 end 的 0 无法覆盖正数；而 user 在 end 拿到 0，导致整场会话 user 排在 0，assistant 排在 `Date.now()`，顺序严重倒置。
3. **富媒体用户消息丢失**：`pushUser` 检查 `if (!text) return;`，导致纯图片或附件的用户消息直接被丢弃。

#### 修复落地

1. **`apps/crish-desktop/src/api/sessionEventTimestamp.ts`**：
   - 扩充 `isHistoricalTerminalEventType`，覆盖 `message-end`、`message-start`、`turn-start`、`turn-end`、`agent-start`、`run-terminal`；
   - 引入 `fallbackToZero` 参数选项，在历史事件回放时统一回退 `0`，避免伪造墙钟时间。
2. **`apps/crish-desktop/src/api/sessionEventProjection.ts`**：
   - 统一传入 `{ fallbackToZero: true }` 调用 `extractMessageTimestamp`；
   - 监听 `turn-start` 与 `run-terminal`，主动重置 `currentAssistant = null;`；
   - 在 `message-start` 与 `message-end` 遇到角色为 assistant 且携带不同稳定 ID 时，重置 `currentAssistant = null;`，防止跨消息合并；
   - 支持 `message-start` 事件投影；
   - 重构 `pushUser`：放行无文本但携带 `attachments` 或 `images` 的富媒体用户输入，返回布尔值便于高效短路；
   - 在 `tool-end` 中增加全量历史消息回溯兜底查找，即使 `currentAssistant` 发生切换也能精确完成对应工具调用状态更新。
