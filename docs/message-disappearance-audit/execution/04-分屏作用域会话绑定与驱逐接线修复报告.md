## 一、修复背景与断层根因回顾

在专项审计报告 `docs/message-disappearance-audit/audits/05-分屏作用域与会话绑定链路审计.md` 中，审计团队指出了多分屏（`multi-pane-isolation`）架构重构后引入的 5 项严重功能断层（F-01 ~ F-05）及 5 大架构根因（RC-01, RC-02, RC-05, RC-06, RC-07）：

1. **F-01 / RC-01（冷启动双源状态撕裂）**：  
   在默认冷启动（`restoreLastWorkspace = false`）时，SQLite 元数据已成功回水最近一条历史会话并设置为 `sessionStore.activeSessionId`；然而 `TreeLeafPanel` 因 `tabs: []` 强行通过 `mintDraftSessionId(leaf.id)` 注入 `__pending_draft__:<leafId>`，将 `ChatCard` 作用域完全锁死在草稿哨兵中，造成侧边栏高亮历史会话而主画布却展示空白草稿落地页的严重撕裂。
2. **F-02 / RC-02（异步回水时序倒挂与 `useChatMessages` 依赖缺失）**：  
   `hydrateWorkspaceShell()` 在冷启动时先于 SQLite 异步回水执行。首次挂载时，`useChatMessages` 执行 `triggerSessionMessageHydrateIfNeeded`，但因 `sessionsById` 为空直接静默返回；当后续 SQLite 异步回水填充会话数据时，由于 `useChatMessages` 仅依赖 `[activeSessionId]`，无法感知 `messagesHydrated` 从 `false` 到可水合状态的变化，导致非焦点分屏和后台标签的消息永远无法回水，消息列表永久显示为空。
3. **F-03 / RC-05（`tabsIdentityEqual` 漏判 `sessionId` 导致 `React.memo` 吞掉重渲染）**：  
   在草稿叶子中发送首条消息触发草稿转正（`promoteDraftTab`）时，原有 `tabId` 保持不变，仅将 `tab.sessionId` 替换为真实会话 ID。而 `BinaryTreeWorkspace.tsx` 中的 `tabsIdentityEqual` 仅比对 `tabId` 和 `dock`，漏判了 `sessionId` 和 `title`；导致 `stabilizeLeafEntries` 错误复用旧 `cached.leaf` 引用，`TreeLeafPanel` 的 `React.memo` 判定前后 props 相等而跳过重渲染，使得 `LeafScopeProvider` 依然持有旧的草稿哨兵，转正后的历史消息完全无法渲染。
4. **F-04 / RC-07（跨分屏切换与分屏坍塌防御缺失）**：  
   在跨分屏打开会话时，`openOrFocusSession` 默认调用 `treeOpenSession`，若目标会话已在另一个分屏存在，会误触发跨分屏移动（`moveTab`）并调用 `pruneEmptyLeaves` 导致原分屏意外坍塌；此外在 `TreeLeafPanel` 点击捕获时若无条件调用 `enterDraftMode()`，会误将全局活跃会话冲刷为草稿态。
5. **F-05 / RC-06（驱逐器无视可见分屏与分屏白屏回水阻断）**：  
   `sessionCrudActions.ts` 中的 `queueMicrotask` 软驱逐逻辑此前调用的旧驱逐器仅保护单一全局 `activeSessionId`，完全无视当前布局树中多窗口正在展示的可见分屏会话，导致非焦点分屏的已水合消息在切换焦点时被误驱逐为 `messages = []` 且 `messagesHydrated = false`；加之断层 F-02 的存在，被误驱逐的分屏不会重新触发回水，导致正在用户眼前展示的分屏瞬间变为空白。

## 二、核心修复方案与实现细节

### 1. `treeLeafPanelModel.ts`：收口分屏会话解析单一真理源

在 `treeLeafPanelModel.ts` 中新增并导出了 `resolveLeafSessionId` 与 `isDraftSessionId`（别名自 `isPendingDraftSessionId`）：

```ts
/**
 * 解析分屏叶子绑定的会话 ID（F-01 / RC-01 单一真理源）：
 * 1. 当叶子节点有显式 activeTab?.sessionId 时，返回 activeTab.sessionId。
 * 2. 当叶子节点 tabs.length === 0（无打开标签）时：
 *    如果当前叶子是焦点叶子（isFocused）且全局 globalActiveSessionId 是非草稿真实会话 ID
 *    （!isPendingDraftSessionId(globalActiveSessionId)），回退使用 globalActiveSessionId；
 *    只有当全局本身处于草稿态或该叶子是非焦点空分屏时，才使用 mintDraftSessionId(leaf.id)。
 */
export function resolveLeafSessionId(
  leaf: LayoutLeaf,
  options?: {
    isFocused?: boolean;
    globalActiveSessionId?: string | null;
  }
): string {
  const tabs = readLeafTabs(leaf);
  const activeTab = readActiveTab(leaf);
  if (activeTab?.sessionId) {
    return activeTab.sessionId;
  }
  if (tabs.length === 0) {
    const isFocused = options?.isFocused ?? false;
    const globalId = options?.globalActiveSessionId;
    if (isFocused && globalId && !isPendingDraftSessionId(globalId)) {
      return globalId;
    }
  }
  return mintDraftSessionId(leaf.id);
}
```

- **消除冷启动撕裂**：当空分屏作为当前焦点叶子挂载时，若全局已有真实历史会话，优先绑定该历史会话，杜绝强行锁定草稿哨兵；
- **纯逻辑无副作用**：解除了组件层对草稿状态的混乱推断，提供确定的单一真理源输出。

### 3. `BinaryTreeWorkspace.tsx`：补齐 `tabsIdentityEqual` 关键比对字段

在 `BinaryTreeWorkspace.tsx` 的 `tabsIdentityEqual` 比较循环中，补齐 `x.sessionId === y.sessionId` 与 `x.title === y.title`：

```tsx
function tabsIdentityEqual(a: unknown, b: unknown): boolean {
  if (a === b) return true;
  if (!Array.isArray(a) || !Array.isArray(b)) return false;
  if (a.length !== b.length) return false;
  for (let i = 0; i < a.length; i++) {
    const x = a[i] as
      | { tabId?: string; sessionId?: string; title?: string; dock?: unknown }
      | string;
    const y = b[i] as
      | { tabId?: string; sessionId?: string; title?: string; dock?: unknown }
      | string;
    if (x === y) continue;
    if (
      typeof x === 'object' &&
      typeof y === 'object' &&
      x &&
      y &&
      x.tabId === y.tabId &&
      x.sessionId === y.sessionId &&
      x.title === y.title &&
      dockIdentityEqual(x.dock, y.dock)
    ) {
      continue;
    }
    return false;
  }
  return true;
}
```

- **彻底根治 F-03**：草稿转正（`promoteDraftTab`）更新 `sessionId` 时，`tabsIdentityEqual` 能够立即检测出差异，生成新的 `leaf` 引用并触发 `TreeLeafPanel` 的 `React.memo` 重新渲染，`LeafScopeProvider` 顺畅绑定新会话。

### 5. `sessionStateActions.ts`：驱逐器活动会话与流式态保护，纯逻辑断环

```ts
function isSessionStreaming(sess: SessionState): boolean {
  const ext = sess as { isStreaming?: unknown; status?: unknown };
  if (
    ext.isStreaming === true ||
    ext.status === 'streaming' ||
    ext.status === 'processing' ||
    ext.status === 'running'
  ) {
    return true;
  }
  if (Array.isArray(sess.messages)) {
    for (let i = sess.messages.length - 1; i >= 0; i--) {
      const msg = sess.messages[i] as
        { status?: unknown; isStreaming?: unknown } | undefined;
      if (!msg) continue;
      if (
        msg.isStreaming === true ||
        msg.status === 'processing' ||
        msg.status === 'streaming'
      ) {
        return true;
      }
    }
  }
  return false;
}

/** 在 Immer 更新中按 evictSessionMessages 的同一契约清除正文。增加活动会话与流式态保护守卫。 */
export function evictSessionMessagesInState<T extends SessionStoreSlice>(
  state: T,
  sessionIds: readonly string[]
): void {
  const activeId = state.activeSessionId ? state.activeSessionId.trim() : '';
  for (const rawId of sessionIds) {
    const id = rawId ? rawId.trim() : '';
    if (!id) continue;
    if (activeId && id === activeId) continue;
    const sess = getSessionForWrite(state, id);
    if (!sess) continue;
    if (isSessionStreaming(sess)) continue;
    sess.messages = [];
    sess.messagesHydrated = false;
    delete sess.hydratedFromEngine;
  }
}
```

- **杜绝任何驱逐事故**：无论外部驱逐计算逻辑如何，绝对禁止清空全局当前活动会话（`activeSessionId`）以及正处于流式生成中的会话消息。

```ts
queueMicrotask(async () => {
  const state = get();
  const currentActiveId = (state.activeSessionId || nextId || '').trim();
  // 收集受保护的会话 ID：实时 activeSessionId 及所有分屏叶当前激活或打开的 Tab
  const protectedSessionIds = new Set<string>();
  if (currentActiveId && !isPendingDraft(currentActiveId)) {
    protectedSessionIds.add(currentActiveId);
  }
  try {
    const { useLayoutTreeStore, listChatLeaves } =
      await import('./layout-tree');
    const { ownedChatLeaves } =
      await import('./workspace-shell/treeSessionQuery');
    const treeRoot = useLayoutTreeStore.getState()?.tree?.root;
    if (treeRoot) {
      for (const owned of ownedChatLeaves(treeRoot)) {
        if (owned.tabs && Array.isArray(owned.tabs)) {
          for (const t of owned.tabs) {
            if (t.sessionId && !isPendingDraft(t.sessionId)) {
              protectedSessionIds.add(t.sessionId);
            }
          }
        }
      }
      for (const leaf of listChatLeaves(treeRoot)) {
        if (Array.isArray(leaf.tabs)) {
          for (const t of leaf.tabs) {
            const sid = (t as { sessionId?: string })?.sessionId;
            if (sid && !isPendingDraft(sid)) {
              protectedSessionIds.add(sid);
            }
          }
        }
      }
    }
  } catch {
    // 容错守卫
  }

  try {
    const { findInactiveHydratedSessionIdsToEvict } =
      await import('./sessionEviction');
    const evictedSessionIds = findInactiveHydratedSessionIdsToEvict(
      currentActiveId,
      new Set(),
      state.sessions || [],
      state.sessionsById || {},
      SESSION_HYDRATE_KEEP_K,
      {
        openTabs: protectedSessionIds,
        visibleSplitSessionIds: protectedSessionIds,
      }
    ).filter((id) => !protectedSessionIds.has(id));

    if (evictedSessionIds.length === 0) return;
    set((current) => {
      evictSessionMessagesInState(current, evictedSessionIds);
    });
  } catch {
    // 容错守卫
  }
});
```

- **异步安全加载**：采用 `await import()` 避免模块加载期的循环引用。

## 三、循环依赖陷阱与静态依赖解耦专项说明

在修复过程中，我们遭遇并彻底攻克了由多 Store 相互引用导致的 **Vite SSR / Vitest 模块求值循环依赖死锁**：

### 1. 陷阱复盘

- **循环依赖链条**：  
  `sessionStore.ts` ➡️ `sessionActions.ts` ➡️ `sessionCrudActions.ts` ➡️ `sessionEvictionProbes.ts` ➡️ `workspaceShellStore.ts` ➡️ `sessionStore.ts`。
- **运行期后果**：  
  如果在 `sessionCrudActions.ts` 顶层静态 `import` 了 `sessionEvictionProbes.ts` 或 `sessionEviction.ts`，由于其静态引入了 `workspaceShellStore`，会导致在模块初始化求值时刻 `createSessionCrudActions` 导出为 `undefined`，进而抛出：  
  `ReferenceError: Cannot access '__vite_ssr_import_0__' before initialization`，导致数十个涉及会话 Store 的单测套件全部崩溃。

### 2. 解耦与架构净收敛方案

- **纯逻辑就地下沉**：在 `sessionStateActions.ts` 中实现纯逻辑函数 `isSessionStreaming`，直接基于会话对象与消息状态做纯布尔判定，完全不依赖外部任何 Store 或 probe；
- **微任务动态加载断环**：软驱逐逻辑天然运行在微任务（`queueMicrotask`）中，此时所有 Store 模块早已完成初始化求值。在微任务体中使用 `await import('./sessionEviction')` 与 `await import('./layout-tree')` 动态读取布局树，**在编译与模块求值层面将静态循环依赖链彻底切断**。
