## 1. 任务列表状态切换行高突变（35.0px ↔ 31.6px）与行盒基线守恒

### 1.1 根因深度剖析

在当前编辑器实现中，任务列表（Task List）在非激活渲染态、悬停态与激活源码态之间切换时，存在极其严重的行高跳动现象（实测行高在 **35.0px** 与 **31.6px** 之间突变，高度差 $\Delta H = 3.4\text{px}$）。这种行高跳变直接破坏了虚拟化滚动容器 `HeightMap` 的测量缓存，引发下游所有文本行在视口内发生剧烈且恼人的上下抖动。

#### 1.1.1 CSS 行格式化上下文（IFC）与 `vertical-align: sub` 的几何破坏

查阅 [src/index.css](file:///c:/Software/conex/reference/markdown-editor/src/index.css#L457-L463) 与 [src/index.css](file:///c:/Software/conex/reference/markdown-editor/src/index.css#L540-L543)：

```css

  display: inline-block;
  padding: 0;

...

```

在 [src/components/InlineRenderer.tsx](file:///c:/Software/conex/reference/markdown-editor/src/components/InlineRenderer.tsx#L114-L116) 中，任务列表 Token 的最外层容器元素被赋予该样式类：


根据 W3C CSS 2.1 规范 §10.8（Line height calculations），行盒（Line Box）的高度由其内部所有行内级盒（Inline-level boxes）的最高顶缘（highest top）与最低底缘（lowest bottom）决定：

$$\text{LineBox Height} = \max_{i} (\text{Top}_i) - \min_{i} (\text{Bottom}_i)$$

1. **非激活渲染态（Visual Render Mode）**：
   - 包含了 `.task-checkbox-wrapper`（内部高度 16px 的 SVG 复选框）。
   - 外层 `.interactive-checkbox` 被声明为 `display: inline-block; vertical-align: sub;`。
   - `vertical-align: sub` 将此 `inline-block` 的基线强行下沉至父级基线之下（通常为父级字号的 $0.2 \sim 0.25\text{em}$，在 14px 字号下沉约 $3 \sim 4\text{px}$）。
   - 此时该行既包含正常基线对齐的文本行盒（Font Box），又包含被强行压低底缘的复选框盒，行盒的底缘被压至文字基线以下约 $10\text{px}$，而顶缘仍由正常文本的行内度量（Line-height: 28px）支撑。
   - 结果：父级包含块 `.line-block`（[src/index.css:170](file:///c:/Software/conex/reference/markdown-editor/src/index.css#L170) 声明 `min-height: var(--grid-size); line-height: var(--grid-size);`，基准为 28px）被内部被拉伸的行盒硬生生**撑破至 35.0px**！

2. **激活源码态（Active Source Mode）**：
   - 当光标移入或选中该 Token 时，[src/index.css:750-761](file:///c:/Software/conex/reference/markdown-editor/src/index.css#L750-L761) 生效：
     ```css

       display: inline !important;
       color: var(--text-muted);
     }
     .is-active-token.token-list-task .syntax-content {
       display: none !important;
     }
     ```
   - 视觉组件 `.task-checkbox-wrapper` 被完全隐藏（`display: none`），转而展示源码文本 `- [ ] `。
   - 虽然此时外层依旧挂载 `.interactive-checkbox`（`vertical-align: sub`），但由于其内部变成了单纯的文本流，不再有 16px 的刚性外物块，行盒高度退化回文本基线与下标偏移的合成高度（实测为 **31.6px**）。

3. **高度突变断层**：
   $$\Delta H = 35.0\text{px} - 31.6\text{px} = 3.4\text{px}$$
   无论是 35.0px 还是 31.6px，都严重偏离了编辑器核心网格基准 `var(--grid-size) = 28px`，并在光标每次划过任务复选框时触发下层文档几千像素的重排与跳动。

### 1.2 行高绝对恒等（$\Delta H \equiv 0$）重构方案

要实现行高在任何状态下绝对锁定为 28px，必须遵循 **CSS 格式化上下文盒模型几何守恒定律**：

1. **彻底清退 `vertical-align: sub`**：
   移除针对 `.interactive-checkbox` 的所有 `vertical-align: sub` 规则，切断行盒底缘异常下沉的物理根源。
2. **构建行内弹性对齐盒（Inline-Flex Alignment Box）**：
   将 `.token-list-task` 与 `.token-list-task .syntax-content` 的显示模型由混乱的 `inline-block` 规范为 `display: inline-flex;`，高度严格锚定为 `var(--grid-size)`（28px）。
3. **垂直中轴物理居中**：
   利用 Flexbox 的 `align-items: center`，在 28px 的固定高度空间内部实现复选框组件与文本基线的中轴无损对齐，无需借助任何引起行盒形变的纵向偏移机制。
4. **源码态与渲染态盒子高度锁死**：
   在源码态展示 `.syntax-hidden` 时，其行高同样继承 `line-height: var(--grid-size);`，盒高同样锁定 28px，使得：
   $$H_{\text{render}} = H_{\text{hover}} = H_{\text{active}} = H_{\text{edit}} \equiv 28\text{px} \implies \Delta H \equiv 0$$

```
【重构后守恒模型】
父容器 line-block (height / line-height: 28px 严格锁定)
┌──────────────────────────────────────────────────────────┐ ▲
│  token-list-task (display: inline-flex; height: 28px)    │ │
│  ┌───────────────────────┐                               │ │ 恒等于 28px
│  │ 垂直中轴对齐 (Y=14px) │ 正常文本 (Line-height: 28px)   │ │ (ΔH ≡ 0)
│  │   [✓] 16px 复选框     │ Task Text Here...             │ │
│  └───────────────────────┘                               │ │
└──────────────────────────────────────────────────────────┘ ▼
```

## 2. 任务复选框渲染占宽与源码字符宽度守恒（消除 14.5px 水平横移断层）

### 2.1 物理几何断层根因剖析

在编辑器的等宽字体渲染系统（`--font-mono: "JetBrains Mono", Consolas, monospace`）中，每一个字符单元具有精确恒定的水平步进 $1\text{ch}$。在标准 14px 字号下，实测 $1\text{ch} \approx 7.697\text{px}$（约 7.7px）。

#### 2.1.1 占宽失配的数学推导

我们审查 [src/index.css:707-735](file:///c:/Software/conex/reference/markdown-editor/src/index.css#L707-L735) 中视觉复选框的尺寸声明：

```css
/* src/index.css:707 */
.task-checkbox-wrapper {
  display: inline-flex;
  align-items: center;
  justify-content: center;
  width: 16px;
  height: 16px;
  margin-left: 2px;
  margin-right: 6px;
  cursor: pointer;
  user-select: none;
  vertical-align: middle;
  transform: translateY(-1px);
  box-sizing: border-box;
}

.task-space {
  display: inline-block;
  width: 1ch;
  user-select: none;
}
```

计算 `.syntax-content` 的总物理占据宽度 $W_{\text{render}}$：
$$W_{\text{render}} = \text{margin-left} + \text{width}_{\text{svg}} + \text{margin-right} + \text{width}_{\text{task-space}}$$
$$W_{\text{render}} = 2\text{px} + 16\text{px} + 6\text{px} + 1\text{ch} = 24\text{px} + 7.697\text{px} = 31.697\text{px}$$

再计算源码态 `.syntax-hidden` 的实际字符占据宽度 $W_{\text{source}}$：
标准 Markdown 任务列表语法为 `- [ ] ` 或 `* [ ] `，包含缩进后的标记字符序列共计 **6 个等宽字符**（短横线、空格、左方括号、空格、右方括号、尾部空格）：
$$W_{\text{source}} = 6\text{ch} \approx 6 \times 7.697\text{px} = 46.182\text{px}$$

两者之间的物理宽度断层（Horizontal Geometric Gap）计算如下：
$$\Delta W = W_{\text{source}} - W_{\text{render}} = 46.182\text{px} - 31.697\text{px} = 14.485\text{px} \approx 14.5\text{px}$$

```
【当前横移断层现象】
1. 非激活视觉渲染态:
   [✓] 任务正文从 X = 31.7px 处开始排版
   |<- 31.7px ->|任务正文...

2. 光标移入或处于激活源码态:
   - [ ]  任务正文被强行向右推开 14.5px，从 X = 46.2px 处开始排版！
   |<------ 46.2px ------>|任务正文...

   ▲ 导致用户每次点击或光标穿越时，正文发生 14.5px 的水平横向剧烈跳动！
```

### 2.2 盒模型严格配平方案（$\Delta W \equiv 0$）

为了彻底根除水平弹跳，**必须使渲染态 `.syntax-content` 的外部盒模型总占宽在像素级与源码字符占宽严格恒等**。

#### 2.2.1 动态占宽守恒公式

任务列表标记的长度可能是 `- [ ] `（6 字符）或有序任务列表 `1. [ ] `（7 字符）。设标记字符数为 $L_{\text{marker}}$：
$$\text{Target Width} = L_{\text{marker}} \times 1\text{ch}$$

将 `.syntax-content` 的外层盒容器宽度严格绑定为：
$$\text{width} = L_{\text{marker}}\text{ch}$$

在标准 `- [ ] `（$L_{\text{marker}} = 6$）下，容器总宽度恒定为 $6\text{ch}$。

#### 2.2.2 6ch 内部几何槽位精密划分

在 $6\text{ch}$（约 46.2px）的物理空间内，我们需要优雅地放置：
1. 复选框左侧留白（对齐无序列表符号的视觉中轴）；
2. 16px 复选框实体；
3. 复选框右侧留白（补偿配平空间）；
4. 尾部 $1\text{ch}$ 标称空格（与正文隔离）。

由于普通无序列表项 `- ` 占据 $2\text{ch}$，其 Bullet 圆点居中于第 1 个字符（中心点 $X = 0.5\text{ch}$）：
- 我们将 16px 复选框置于前 $5\text{ch}$ 区域内，并使其视觉中轴与常规列表对齐；
- 容器采用 Flexbox 布局：`display: inline-flex; width: 6ch; justify-content: flex-start; align-items: center;`；
- 通过 CSS 变量或 `calc()` 公式自动配平间距：
  $$\text{margin-left} = \text{calc}(0.5\text{ch} - 2\text{px})$$
  $$\text{margin-right} = \text{auto}$$
  $$\text{task-space width} = 1\text{ch}$$

无论在任何屏幕 DPI、缩放比例或字体微调下，$6\text{ch} - 6\text{ch} \equiv 0$，实现真正的**自适应动态零断层**！

## 3. 消除硬编码 `transform: translateY(-1px)` 机械位移

### 3.1 机械位移的技术弊端剖析

在当前 [src/index.css:718](file:///c:/Software/conex/reference/markdown-editor/src/index.css#L718) 中：
```css
.task-checkbox-wrapper {
  ...
  vertical-align: middle;
  transform: translateY(-1px);
  box-sizing: border-box;
}
```

这种使用 `transform: translateY(-1px)` 强行在视觉上将复选框向上推 1 像素的做法属于典型的“打补丁式排版”，具有三大不可接受的渲染缺陷：

1. **合成层隔离与亚像素抗锯齿恶化**：
   `transform` 会在 Blink/WebKit 渲染树中创建独立的渲染层（Paint Layer）甚至触发硬件合成加速，使该行内元素与周围文本从同一个文本光栅化上下文（Rasterization Context）中脱离。在 Windows ClearType 或 macOS 亚像素抗锯齿环境下，复选框与相邻文本将出现渲染阶梯感、文字边缘微糊或颜色透光不一致。
2. **高分屏非整数 DPI 下的模糊与抖动**：
   在常见非整数缩放比（125%、150%、175%）下，`-1px` 乘以缩放系数（如 $1.25$）会导致 $-1.25\text{dpx}$ 的物理像素偏移。SVG 边框将被迫在亚像素网格中插值重采样，导致原本 1.2px/1.5px 的锐利边框出现明显的发虚和锯齿。
3. **物理命中测试（HitTest）与 Range 盒模型脱节**：
   `getBoundingClientRect()` 测得的坐标包含了 Transform 变换矩阵，但行内流式排版的基线测算却不感知此变换，导致鼠标事件响应区（HitBox）与实际排版占位错位。

---

### 3.2 基于 Flexbox 内部对齐的原生 $O(1)$ 替代方案

在行高锁定为 28px 的前提下，排版几何本身就具备极其优美的对称性：
- 行盒总高：$H = 28\text{px}$；
- 复选框总高：$h = 16\text{px}$；
- 垂直居中数学中心点：$Y_{\text{center}} = \frac{28}{2} = 14\text{px}$；
- 复选框起始 Y 坐标：$Y_{\text{top}} = \frac{28 - 16}{2} = 6\text{px}$。

在 JetBrains Mono / Consolas 等宽字体中，14px 字号的大写字母（Cap-height）高度约为 10px，小写字母（X-height）高度约为 7.5px。在 28px 行高中，大写字母的垂直几何中心几乎精确落在 $Y = 14\text{px}$ 上！

因此，**只需将包含块设为 `display: inline-flex; align-items: center;`，16px 的复选框自然在数学中轴上与文字几何中心实现 $100\%$ 精确重合！**

若设计上需要对字母 X-Height 进行 $0.5\text{px}$ 级的视错觉微调，**绝不能动用 CSS Transform**，而应在 SVG 内部通过矢量路径坐标（`viewBox` 与 `<rect y="...">`）进行无损平移。由于 SVG 内部的坐标是矢量空间，GPU 会进行矢量栅格化，完全避免了 CSS 变换带来的图层提升与亚像素抖动。

### 4.2 零退化测量引擎：三级几何投影探测策略（Three-Tier Geometric Projection）

为了彻底杜绝 0x0 盲区与行首退化，我们重构测量引擎的定位与 Range 探测逻辑，确立如下策略：

```
                    ┌───────────────────────────────┐
                    │ 目标字符偏移量 offsetInToken   │
                    └──────────────┬────────────────┘
                                   │
                                   ▼
             ┌───────────────────────────────────────────┐
             │ Tier 1: 真实挂载可见文本 Range 探测        │
             │ (TextNode 存在且位于非 display: none 子树) │
             └─────────────┬───────────────┬─────────────┘
                  成功      │               │ 失败/0x0
                           ▼               ▼
                  ┌─────────────┐  ┌─────────────────────────────────────────┐
                  │ 采用物理    │  │ Tier 2: Token 内部可见内容几何投影      │
                  │ Range 坐标  │  │ (.syntax-content 物理盒内线性插值探测)   │
                  └─────────────┘  └───────────────┬─────────────────────────┘
                                           成功     │               │ 失败/内容空
                                                    ▼               ▼
                                           ┌─────────────┐  ┌─────────────────────────────────────────┐
                                           │ 采用插值    │  │ Tier 3: 邻近可见兄弟 Token 边界投影    │
                                           │ 几何物理坐标│  │ (紧邻的下一个或上一个可见 Token 物理边缘)│
                                           └─────────────┘  └───────────────┬─────────────────────────┘
                                                                    成功     │               │ 纯空行
                                                                             ▼               ▼
                                                                    ┌─────────────┐  ┌─────────────────────┐
                                                                    │ 采用边界物理│  │ Tier 4: 行内文本起始 │
                                                                    │ 吸附坐标    │  │ 槽位精确测量兜底    │
                                                                    └─────────────┘  └─────────────────────┘
```

#### 4.2.1 Tier 2：Token 内部可见内容几何投影（Within-Token Geometric Projection）
当 `.syntax-hidden` 隐藏时，渲染层必然挂载了替代组件 `.syntax-content`（如复选框）。
- 我们直接获取 `.syntax-content` 的物理矩形 `scRect = syntaxContentEl.getBoundingClientRect()`；
- 若光标偏移处于前缀内部（$0 \le \text{offset} \le \text{token.length}$），通过插值比率计算物理坐标：
  $$\text{ratio} = \frac{\text{offsetInToken}}{\text{token.length}}$$
  $$\text{targetLeft} = \text{scRect.left} + \text{scRect.width} \times \text{ratio}$$
- 这一机制确保光标在隐藏前缀内移动时，坐标平滑连续，零 0x0 错误，绝无跳动。

#### 4.2.2 Tier 3：邻近可见兄弟 Token 边界投影（Sibling Boundary Projection）
如果 Token 既无可见 TextNode，又无可见内容（典型如非激活态的 `token-heading-prefix`）：
- 沿 DOM 树向后寻找同属于该物理行的下一个可见 Token（如标题正文文本 Token `token-heading-text`）；
- 若存在下一个可见 Token，其物理 `left` 边界即为此隐藏前缀的物理终止点！直接取 `nextRect.left`；
- 若不存在下一个 Token，向前寻找上一个可见 Token 的 `right` 边界；
- 彻底废除直接取包含块 `line.el.left` 的野蛮回退！

### 4.3 核心代码重构实现

```typescript
// ==========================================================================
// 重构代码: src/core/measure.ts
// 消除 0x0 盲区与行首退化，实现三级几何投影探测
// ==========================================================================

function measureTokenExact(
  entry: TokenEntry,
  offsetInToken: number
): MeasuredRect | null {
  const located = locateTextNode(entry, offsetInToken);
  let rect: {
    left: number;
    top: number;
    width: number;
    height: number;
    bottom?: number;
  } | null = null;

  // ------------------------------------------------------------
  // Tier 1: 真实挂载可见文本 Range 探测
  // ------------------------------------------------------------
  if (located) {
    // 快速前置探查：如果所在父节点处于 display: none，不建立无意义 Range
    const parentEl = located.textNode.parentElement;
    const isHidden = parentEl?.closest('.syntax-hidden') &&
      (!parentEl.closest('.is-active-token') && !parentEl.closest('.is-active-line'));

    if (!isHidden) {
      const range = getSharedRange();
      try {
        range.setStart(located.textNode, located.localOffset);
        range.setEnd(located.textNode, located.localOffset);
        const r = range.getBoundingClientRect();
        // 确保不是 0x0 盲区
        if (r.height !== 0 || r.width !== 0) {
          rect = r;
        }
      } catch (e) {
        rect = null;
      }
    }
  }

  // ------------------------------------------------------------
  // Tier 2: Token 内部可见内容几何投影探测 (Within-Token Projection)
  // ------------------------------------------------------------
  if (!rect) {
    const syntaxContent = entry.el.querySelector('.syntax-content') as HTMLElement | null;
    if (syntaxContent) {
      const scRect = syntaxContent.getBoundingClientRect();
      if (scRect.height > 0) {
        const totalLen = Math.max(1, entry.length);
        const ratio = Math.max(0, Math.min(1, offsetInToken / totalLen));
        rect = {
          left: scRect.left + scRect.width * ratio,
          top: scRect.top,
          width: 0,
          height: scRect.height,
          bottom: scRect.bottom,
        };
      }
    }
  }

  // ------------------------------------------------------------
  // Tier 3: 邻近可见兄弟 Token 边界物理投影 (Sibling Projection)
  // ------------------------------------------------------------
  if (!rect) {
    const er = entry.el.getBoundingClientRect();
    if (er.height > 0 && er.width > 0) {
      const isStart = offsetInToken === 0;
      rect = {
        left: isStart ? er.left : er.right,
        top: er.top,
        width: 0,
        height: er.height,
        bottom: er.bottom,
      };
    } else {
      // 自身完全不可见（如隐藏的标题前缀 ## ），向后寻找同行的下一个可见兄弟 Token
      let sibling = entry.el.nextElementSibling as HTMLElement | null;
      while (sibling) {
        const sr = sibling.getBoundingClientRect();
        if (sr.height > 0 && sr.width > 0) {
          rect = {
            left: sr.left,
            top: sr.top,
            width: 0,
            height: sr.height,
            bottom: sr.bottom,
          };
          break;
        }
        sibling = sibling.nextElementSibling as HTMLElement | null;
      }

      // 若向后无可见兄弟，向前寻找上一个可见兄弟
      if (!rect) {
        let prevSibling = entry.el.previousElementSibling as HTMLElement | null;
        while (prevSibling) {
          const pr = prevSibling.getBoundingClientRect();
          if (pr.height > 0 && pr.width > 0) {
            rect = {
              left: pr.right,
              top: pr.top,
              width: 0,
              height: pr.height,
              bottom: pr.bottom,
            };
            break;
          }
          prevSibling = prevSibling.previousElementSibling as HTMLElement | null;
        }
      }
    }
  }

  if (!rect) return null;

  const fontSize = tokenFontSize(entry.el);
  const cursorHeight = fontSize * 1.15;
  return {
    top: rect.top + (rect.height - cursorHeight) / 2,
    left: rect.left,
    height: cursorHeight,
    bottom: rect.bottom ?? rect.top + rect.height,
  };
}
```

## 5. 坐标缓存（posCache / measCache）与动态渲染状态脱敏

### 5.1 缓存失效盲区的根因剖析

在当前 [src/core/measure.ts](file:///c:/Software/conex/reference/markdown-editor/src/core/measure.ts) 中，设计了双层坐标缓存体系以提升性能：
1. `idx.posCache`: 容器级同帧位置结果缓存；
2. `entry.measCache`: Token 级行内偏移坐标缓存。

然而，这两套缓存与 React 的装饰层渲染状态之间存在极其严重的**状态感知失明（State Desensitization）**：

#### 5.1.1 `posCache` 键缺乏版本约束
查看 [src/core/measure.ts:608](file:///c:/Software/conex/reference/markdown-editor/src/core/measure.ts#L608)：
```typescript
const cacheKey = index + ':' + container.scrollTop + ':' + container.scrollLeft;
```
缓存键仅由 `index`、`scrollTop`、`scrollLeft` 三者拼接而成。
当光标刚刚移动至某个任务列表项，或者鼠标悬停切换激活态时：
- 容器未发生滚动，`scrollTop` 与 `scrollLeft` 保持不变；
- 如果前一帧由于探测或光标位于附近，`posCache` 已经缓存了未激活状态下的坐标；
- 当 Token 被赋予 `.is-active-token` 展开源码态后，`getCoordinatesFromIndex` 再次被调用；
- 由于缓存键完全相同，**直接命中过期缓存**！返回旧的、甚至包含了上一节所述 0x0 行首退化的历史错误坐标，导致光标死锁在偏左或偏上的错误物理位置！

#### 5.1.2 `MutationObserver` 完全过滤掉了 `class` 变化
查看 [src/core/measure.ts:258-268](file:///c:/Software/conex/reference/markdown-editor/src/core/measure.ts#L258-L268)：
```typescript

  subtree: true,
  attributes: true,

    'data-token-start',
    'data-token-length',
    'data-line-start',
    'data-line-length',
  ],

```
`MutationObserver` 的 `attributeFilter` **只监听了定位相关的 `data-*` 属性，根本没有监听 `class`！**
这意味着：当 React 在 Commit 阶段为 Token 增删 `is-active-token`、`is-active-line`、`is-empty-token` 等样式类时，`MutationObserver` 根本不会被触发！`idx.dirty` 依然为 `false`！容器索引不会重建，Token 上的 `measCache` 和 `textTable` 得不到任何清理！

#### 5.1.3 React 生命周期时序错位

### 5.2 状态脱敏重构：全生命周期精确失效通道

为了彻底根除坐标过期问题，我们建立三位一体的精确失效通道：

### 5.3 核心代码重构实现

#### 5.3.1 `src/core/measure.ts` 数据结构与接口升级

```typescript
// ==========================================================================
// 重构代码: src/core/measure.ts
// 升级缓存数据结构与精确失效机制
// ==========================================================================

interface TokenEntry {
  start: number;
  length: number;
  el: HTMLElement;
  lineEl: HTMLElement | null;
  textTable: TokenTextNode[] | null;
  measCache: Map<number, MeasuredRect> | null;
  /** 记录上一次测量的活跃态，用于感知 is-active-token 突变并精确失效 */
  lastIsActive?: boolean;
}

interface ContainerIndex {
  container: HTMLElement;
  isLine: boolean;
  tokens: TokenEntry[];
  lines: LineEntry[];
  byEl: WeakMap<HTMLElement, TokenEntry>;
  dirty: boolean;
  posCache: Map<string, MeasuredRect>;
  observer: MutationObserver | null;
  /** 容器当前绑定的全局装饰版本号 */
  currentDecorationVersion?: number;
}

/**
 * 测量 Token 偏移坐标（具备活跃态感知自愈能力）
 */
function measureTokenOffset(
  idx: ContainerIndex,
  entry: TokenEntry,
  offsetInToken: number
): MeasuredRect | null {
  // 1. 动态感知 Token 的激活样式是否发生突变
  const currentIsActive = entry.el.classList.contains('is-active-token') ||
    Boolean(entry.el.closest('.is-active-line'));

  if (entry.lastIsActive !== undefined && entry.lastIsActive !== currentIsActive) {
    // 状态翻转！立即淘汰过期的 Token 级测量与文本表缓存
    entry.measCache = null;
    entry.textTable = null;
  }
  entry.lastIsActive = currentIsActive;

  if (!idx.isLine) {
    if (!entry.measCache) entry.measCache = new Map();
    const hit = entry.measCache.get(offsetInToken);
    if (hit) return contentToViewport(hit, idx.container);
  }

  const rect = measureTokenExact(entry, offsetInToken);
  if (!rect) return null;

  if (!idx.isLine) {
    const content = viewportToContent(rect, idx.container);
    (entry.measCache as Map<number, MeasuredRect>).set(offsetInToken, content);
  }
  return rect;
}

/**
 * 单次测量（接入 decorationVersion 代际脱敏缓存）
 */
function measureOnce(
  idx: ContainerIndex,
  index: number,
  decorationVersion: number = 0
): MeasuredRect | null {
  const container = idx.container;

  // 如果容器代际版本落后，立即清空 posCache
  if (idx.currentDecorationVersion !== decorationVersion) {
    idx.posCache.clear();
    idx.currentDecorationVersion = decorationVersion;
  }

  // 视口坐标缓存键显式绑定 decorationVersion，绝不返回过期的激活态几何
  const cacheKey = `${index}:${container.scrollTop}:${container.scrollLeft}:${decorationVersion}`;
  if (idx.posCache.size >= POS_CACHE_LIMIT) idx.posCache.clear();
  const hit = idx.posCache.get(cacheKey);
  if (hit) return hit;

  const entry = locateToken(idx, index);
  let rect: MeasuredRect | null = null;
  if (entry) {
    if (!validateEntry(entry)) {
      rebuildIndex(idx);
      return null;
    }
    rect = measureTokenOffset(idx, entry, index - entry.start);
  }
  if (!rect) rect = measureLineFallback(idx, index);
  if (rect) idx.posCache.set(cacheKey, rect);
  return rect;
}

/**
 * 对外统一接口：获取光标 index 处的物理坐标（视口坐标系）
 */
export function getCoordinatesFromIndex(
  index: number,
  container: HTMLElement | null,
  decorationVersion: number = 0
): MeasuredRect | null {
  if (!container) return null;
  const idx = getIndex(container);
  const rect = measureOnce(idx, index, decorationVersion);
  if (rect) return rect;

  const fresh = indexMap.get(container);
  if (fresh && fresh !== idx) return measureOnce(fresh, index, decorationVersion);
  return null;
}
```
