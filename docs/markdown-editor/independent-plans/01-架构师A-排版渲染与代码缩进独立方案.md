## 1. 架构愿景与设计哲学

在现代富文本/Markdown 双模混排引擎中，渲染排版的本质是**几何空间的绝对对齐**、**CSS 硬件加速层叠上下文的安全隔离**与**标准通用标记规范（CommonMark）的严格还原**。

本项目作为桌面端与高性能 Web 端融合的下一代 AI Markdown 引擎，在底层架构设计上必须恪守以下四条核心公理：

1. **绝对几何守恒（Geometric Invariance）**：
   行内任意可视组件（复选框、缩进线、前缀槽位）的尺寸与排版边界必须严格处于其容器物理盒模型之内。杜绝负坐标溢出与隐式边缘裁剪。
2. **GPU 合成层隔离与裁剪防御（Paint Containment Integrity）**：
   虚拟滚动行盒采用 `contain: paint` 提供了极高的滚动与直刷重绘隔离，但其物理副产物是对任何溢出像素的一刀切硬裁切。排版几何必须为 GPU 裁剪边界保留确定性的安全间距（Safe Gutters）。
3. **CommonMark §4.5 规范的像素级投影（Spec-Compliant Visual Projection）**：
   CommonMark 规范不仅是 AST 语法解析的准则，更是视口投影排版的绝对法定依据。在列表、引用与代码围栏嵌套时，开围栏的缩进剥离与代码卡片槽位对齐必须做到逻辑与视觉的双重一致。
4. **纯净色彩代币与现代色彩空间演化（Pure Modern Color Tokens）**：
   彻底弃绝遗留的 Raw Hex（十六进制）与旧式 `rgba(...)` 标量，全量迁入 CSS Color Module Level 4 的现代空格式 `hsl()` 与超广色域 `oklch()` 体系，以 0.4%M + 0.8%Y 的米纸基底构筑具人文温度的视觉底色，辅以 3% 纯黑混入的极简纯灰交互阶梯。

## 2. 问题 1：对号复选框裁剪根除与边缘判定剥离

### 2.1 缺陷现象剖析
用户在编辑 `- [ ] 顶层未完成任务` 时，顶层任务项的复选框方框左侧竖线及左侧倒角彻底消失，视觉上被平截为一个残缺的 `]` 形；而当任务项位于二级或更深层嵌套（如 `  - [ ] 嵌套任务`）时，复选框呈现完整的四边闭合圆角矩形。

此外，用户在点击复选框左侧或右侧边沿时，任务状态未发生切换，反而常常误触发光标置入与 Markdown 源码模式展开，造成严重的操作挫败感。

### 2.2 根因定位与几何动力学推导

#### 根因一：盒模型负溢出与 `contain: paint` 的冲突
定位代码：
- `reference/markdown-editor/src/index.css` L698-L712
- `reference/markdown-editor/src/index.css` L593-L595
- `reference/markdown-editor/src/components/InlineRenderer.tsx` L716-L755

```css
/* src/index.css */
.task-checkbox-wrapper {
  display: inline-flex;
  align-items: center;
  justify-content: center;
  width: 1ch;                 /* 在等宽字体下约 8.4px (Consolas/JetBrains Mono 14px) */
  cursor: pointer;
  user-select: none;
  vertical-align: middle;
  transform: translateY(-1px);
}

.virtual-row-gpu {
  contain: paint;             /* 关键：行级重绘隔离，开启硬件硬裁切 */
}
```

```tsx
/* src/components/InlineRenderer.tsx */
<span className="task-checkbox-wrapper" ...>
  <svg width="14" height="14" viewBox="0 0 16 16" className="task-checkbox-svg">
    ...
  </svg>
</span>
```

**物理几何推导**：
1. 等宽字符槽位宽度 `1ch` 在 14px 字号下被浏览器渲染引擎计量为 `8.4px`。
2. `.task-checkbox-wrapper` 设置了 `width: 1ch; justify-content: center;`。
3. 内部包含的 SVG 物理宽度为 `14px`。
4. 在 Flex 居中布局下，SVG 的左侧相对于父容器左侧的水平坐标为：
   $$X_{\text{offset}} = \frac{8.4\text{px} - 14\text{px}}{2} = -2.8\text{px}$$
5. **顶层任务项（Top-level List Item）**：
   `token.indent` 为空（`indentLen = 0`），行首不渲染任何 `.syntax-indent` 节点。
   `.task-checkbox-wrapper` 紧贴虚拟行 `.virtual-row` 的物理最左边缘（`left: 0`）。
   因此，SVG 左边缘的物理屏幕绝对坐标落于行盒边界的负向空间：$X = -2.8\text{px}$。
6. **`contain: paint` 的裁切判定**：
   `.virtual-row-gpu` 声明了 CSS 规范中的 `contain: paint`。根据 W3C Containment Level 2 §3.3，paint containment 将元素变成其后代元素的不溢出视口（Clipping Box）。任何坐标落在 $[-\infty, 0)$ 区间的像素均被 GPU 光栅化管线彻底丢弃！
   因此，SVG 方框左侧 $0$ 到 $2.8\text{px}$ 的绘制内容（包含左竖边框与左上/左下圆角）被物理截断，退化为 `]` 形。
7. **嵌套任务项为何正常**：
   嵌套任务项前置了 `span.syntax-indent`（例如 2 空格或 4 空格，宽度 $\ge 16.8\text{px}$）。SVG 即使向左溢出 $2.8\text{px}$，其绝对物理坐标依然 $\ge 14\text{px} > 0$，因此完全处于行盒可视区内，避开了 GPU 裁剪边界。

#### 根因二：`isEdgeClick` 伪逻辑破坏交互确定性
定位代码：
- `reference/markdown-editor/src/components/InlineRenderer.tsx` L638-L661

```tsx

**破坏性分析**：
- 复选框本身是仅 14px 的极小微控件，`edgeMargin = 2` 意味着在控件四周各划取 2px 作为“边缘区”。
- 如果容器尺寸仅 8.4px，左 2px + 右 2px 占据了横向宽度的近 $50\%$！用户点击很容易落在该区域。
- 试图通过点击边沿让用户“就地编辑源码”是一个严重违背心智模型的设计——用户点击复选框图标的唯一明确意图就是**切换完成状态**；若需编辑 Markdown 原文，用户自然会点击行尾文字后使用光标回退，或通过快捷键切入。将微控件的一半面积设为“静默拦截并不切换”是极具破坏性的。

### 2.3 精确修复方案

#### 步骤 1：CSS 盒模型修复（根除负坐标溢出）
将 `.task-checkbox-wrapper` 尺寸拓宽至完整的 `16px × 16px` 触摸盒，且配置 `margin-left: 3px; margin-right: 5px;`。
- 容器宽度大于 14px SVG，SVG 在内部居中时 $X_{\text{offset}} = \frac{16 - 14}{2} = +1\text{px} > 0$。
- 容器自带 `margin-left: 3px`，即使在顶层任务项中，复选框最左端距离 `.virtual-row-gpu` 的硬件裁剪边界也有 $3\text{px} + 1\text{px} = 4\text{px}$ 的充足安全余量，永不发生亚像素裁切。

#### 步骤 2：彻底移除 `isEdgeClick`
在 `InlineRenderer.tsx` 中移除全部边沿坐标测算、容差边界判定与降级逻辑。凡是点击发生在复选框 wrapper 内部，100% 触发状态切换 `[ ]` $\leftrightarrow$ `[x]`。

## 3. 问题 2：0.4%M 0.8%Y 暖米橙基底与 3% 纯灰交互色彩阶梯

### 3.1 暖米橙色纸张背景（`--parchment`）的科学推导
Conex 的设计核心理念为“数字羊皮纸（Digital Parchment）与人文墨香”。
传统印刷中的米色高质感纸张，采用四色减色法混墨：
- $C = 0\%$（无青色）
- $M = 0.4\%$（极微量品红，注入红润温润感，消除冰冷感）
- $Y = 0.8\%$（双倍于品红的暖黄，确立米黄主基底）
- $K = 0\%$（无碳黑）

**色彩空间转换**：
减色模型向加色模型（sRGB）映射：
$$R = 1 - C = 1.0 \implies 255$$
$$G = 1 - M = 1 - 0.004 = 0.996 \implies 253.98 \approx 254$$
$$B = 1 - Y = 1 - 0.008 = 0.992 \implies 252.96 \approx 253$$

转换至 HSL 色彩空间：
- $R=1.0, G=0.996, B=0.992$
- 最大值 $M = 1.0$，最小值 $m = 0.992$，差值 $\Delta = 0.008$
- 亮度 $L = \frac{1.0 + 0.992}{2} = 99.6\%$（基底明度）
- 饱和度色相：$\text{Hue} = 60^\circ \times \frac{G - B}{\Delta} = 60^\circ \times \frac{0.004}{0.008} = 30^\circ$（暖橙琥珀色相，Warm Orange Hue）
- 饱和度：在纸张漫反射呈现上，适配屏幕背光对比度，色调演进至 Conex 标志性的：
  $$\text{--parchment: } \text{hsl}(30\ 2.5\%\ 96.5\%)$$
  对应 OKLCH 色彩空间标定为：
  $$\text{--parchment-oklch: } \text{oklch}(0.978\ 0.005\ 65)$$

### 3.2 3% 纯灰交互阶梯（Neutral Gray Tier）
在浅色背景的人机交互界面中，色彩学研究表明：任何带有高色相饱和度的交互悬停底色（如浅蓝、浅橙）长时间阅读均会造成视网膜微疲劳，并干扰用户对代码语法高亮与文档主题色彩的感知。

因此，交互控件（按钮、下拉菜单、工具栏项、分段控制器）的默认态、悬停态（Hover）与按压态（Active）必须严格统一于**3% 纯灰阶演化**：
- **基底白色/卡片色**：`--white: var(--ivory);` 即 `hsl(0 0% 100%)`
- **3% 纯灰悬停阶梯**：
  采用 CSS Color Module Level 4 的 `color-mix` 原生插值：
  ```css
  --interactive-hover-bg: color-mix(in srgb, hsl(0 0% 0%) 3%, var(--white));
  ```
  该插值结果在 sRGB 下精确等价为亮度 $97\%$ 的无倾向纯中性浅灰：
  $$\text{hsl}(0\ 0\%\ 97\%)$$
- **5% 纯灰按压阶梯（Active/Pressed）**：
  ```css
  --interactive-active-bg: color-mix(in srgb, hsl(0 0% 0%) 5%, var(--white));
  ```
- **微弱边框融合（Border Subtle）**：
  ```css
  --interactive-border: hsl(30 2.5% 88%);
  --interactive-border-hover: hsl(30 2.5% 76%);
  ```

### 3.3 彻底清退 Raw Hex 与旧式 RGBA
全面审查 `src/` 下所有样式，执行格式化清洗：
- 严禁出现 `#ffffff`、`#333333`、`#eee` 等 Hex 格式。
- 严禁使用逗号分隔的传统 `rgba(0, 0, 0, 0.1)` 语法。
- 全部统一为现代空格语法：`hsl(H S L / A)` 与 `oklch(L C H / A)`。

## 4. 问题 3：纵向导线极细化与跨行零缝隙连贯拓扑

### 4.1 现象与几何断裂剖析
当前编辑器中存在两套纵向引导线机制：
1. 列表多级缩进引导线：`.syntax-indent-guide`，线宽 `1px`，颜色 `--list-guide-line`。
2. 块引用前缀导线：`.blockquote-bar`，线宽 `2.5px`，颜色 `--warm-sand`。

视觉问题表现在：
- **粗细割裂**：列表缩进线（1px）与引用导线（2.5px）在同一文档并存时，视觉比重失衡，引用线过于笨重粗暴，列表线过于模糊。
- **行间 10px 垂直断隙**：当连续多行同级缩进或多行连续引用时，导线在两行交界处出现明显的空白断裂断茬，无法形成一根贯穿整个段落的竖直流水线。

### 4.2 垂直断裂根因定位
定位代码：
- `reference/markdown-editor/src/index.css` L602-L661
- `reference/markdown-editor/src/components/InlineRenderer.tsx` L690-L695, L770-L789

```css
/* src/index.css 现状 */
.token-blockquote-prefix {
  display: inline-block;
  position: relative;
  white-space: pre;
  vertical-align: baseline;     /* 关键病因 1：基线对齐使行内盒子高度受限于字体字形 */
}

.token-blockquote-prefix .blockquote-bar {
  position: absolute;
  left: calc(0.5ch - 1px);
  top: 1px;                     /* 关键病因 2：上下硬编码留空 1px */
  bottom: 1px;
  width: 2.5px;
  background-color: var(--warm-sand, hsl(30 2.5% 86%));
  border-radius: 1.5px;         /* 关键病因 3：两端圆角使断茬变成胶囊孤岛 */
  pointer-events: none;
}

.syntax-indent {
  white-space: pre;
  position: relative;
  display: inline-block;
  vertical-align: baseline;     /* 关键病因 1 */
}

.syntax-indent-guide {
  position: absolute;
  top: 0;
  bottom: 0;
  width: 1px;
  background-color: var(--list-guide-line, hsl(30 2.5% 78%));
  pointer-events: none;
  user-select: none;
}
```

**几何物理机制分析**：
1. 虚拟列表行 `.virtual-row` 的行高网格基准为 `min-height: 28px`（`--grid-size: 28px`）。
2. `.syntax-indent` 与 `.token-blockquote-prefix` 被设置为 `display: inline-block; vertical-align: baseline;`。
3. 当一个 `inline-block` 元素采用 `vertical-align: baseline` 时，其物理渲染高度不再是整行行高 28px，而是仅等于字体渲染文本的字形边界（Bounding Box），即 14px 字号下的约 18px-19px。
4. 顶部和底部因此产生了未铺满的空隙：
   $$\Delta H_{\text{gap}} = 28\text{px} - 18.5\text{px} \approx 9.5\text{px} \approx 10\text{px}$$
5. 在上一行的行底（距离行边界约 5px）与下一行的行顶（距离行边界约 5px）之间，两根原本意图连接的引导线出现了整整 **10px 的垂直无色虚空断裂**！
6. `.blockquote-bar` 又人为附加了 `top: 1px; bottom: 1px; border-radius: 1.5px;`，进一步加剧了断裂，使得每一行引用线都沦为一个独立的“短圆棒”。

### 4.3 极细高精度连贯拓扑方案
1. **线宽与色彩系统收敛**：
   - 统一引导线宽为高精极细线：物理尺寸设定为 `0.5px`（在 Retina/高 DPI 屏上呈现锐利的单物理像素发丝线，普通屏退化为平滑抗锯齿半像素线）。
   - 颜色统一为微暖灰代币：`--guide-line: hsl(30 2.5% 82%)`。
2. **盒模型贯通重构**：
   - 将 `.syntax-indent`、`.syntax-indent-guide`、`.token-blockquote-prefix`、`.blockquote-bar` 全部改造为行级贯通拓扑。
   - 声明 `height: 100%; top: 0; bottom: 0; vertical-align: top;`。
   - `.token-blockquote-prefix .syntax-content` 与父容器同高（`height: 100%`）。
   - `.blockquote-bar` 与 `.syntax-indent-guide` 彻底移除 `top: 1px; bottom: 1px; border-radius: 1.5px`，设为直角平齐截面。
3. **连贯性保证**：
   上一行的导线底部物理坐标恰为 $Y_1 = 28\text{px}$，下一行的导线顶部物理坐标恰为 $Y_2 = 0\text{px}$。由于虚拟列表绝对定位 `top: index * 28px`，两行导线在几何平面上严丝合缝闭合，拼接误差恒为 $0\text{px}$！

## 5. 问题 4：文字选区品牌微绿微光光学呈现

### 5.1 光学体验失衡根因
定位代码：
- `reference/markdown-editor/src/index.css` L40-L41, L159-L161
- `reference/markdown-editor/src/components/SelectionHighlight.tsx` L345-L358

  background-color: var(--selection-bg);
}
```

```tsx
/* src/components/SelectionHighlight.tsx */
<div
  key={i}
  className="selection-rect"
  style={{
    position: 'absolute',
    top: rect.top,
    left: rect.left,
    width: rect.width,
    height: rect.height,
    backgroundColor: 'var(--blue-selection)',
    mixBlendMode: 'multiply',

**问题本质**：
- 现有的 `color-mix(in srgb, hsl(0 0% 0%) 4%, transparent)` 是极淡的 4% 灰度透明，在明亮的米纸背景上几乎不可见，用户拖动鼠标划选文字时，甚至无法明确察觉当前选区究竟覆盖到了哪个字符，误操作率极高。
- 原生浏览器的深蓝高反差选区又会完全遮盖行内语法高亮（粗体、标记、行内代码）。

### 5.2 品牌微绿微光系统方案

## 8. 问题 7：列表内嵌套代码块 CommonMark §4.5 规范严格对齐

### 8.1 规范定义与故障现象
#### 故障现象
用户在列表中嵌套代码块，例如：
```markdown
- 列表项
  ```python
  def calculate(x):
      return x * 2
  ```
```
或者多级有序列表中：
```markdown
1. 第一项
   ```python
   x = 1
   ```
```
渲染出的代码卡片内部，代码行并未顶格对齐到卡片的左侧内容区，而是每一行都出现了 **3 到 4 个空格的异常缩进**；更严重的是，当代码块第一行含有缩进的 Python 关键字时，光标点击与测量甚至出现错位。

#### CommonMark §4.5 权威规范
CommonMark 规范 §4.5 *Fenced code blocks* 明确指出：
> *"The opening code fence may be preceded by up to three spaces of indentation... If the opening code fence is indented, each line of code may have up to that amount of indentation removed, if present. (More indentation than that will not be removed.)"*

**规范要义**：
1. 开围栏行（Opening Fence）允许有 **0 至 3 个空格**的前导缩进（在列表项内嵌套时，该缩进是列表结构要求的对齐缩进）。
2. 一旦开围栏具有 $N$ 个空格的前导缩进（$1 \le N \le 3$），则代码块内部的**每一行代码（包括普通代码、空行与闭合围栏）**，在渲染与导出时，必须将行首**至多 $N$ 个空格剥除**。
3. 剥除后的代码第一列，必须顶格对齐在代码卡片的内容槽位左边缘（Gutter 之后的基线处），从而使代码块内部的真实代码缩进（如 Python 的 4 格缩进）在卡片内得到绝对真实还原。

### 8.2 现有代码三大致命缺陷诊断

#### 缺陷 1：`computeFenceContext` 与 `useFenceContext` 状态缺失

#### 缺陷 2：`stripCodeFenceIndent` 处理不全面与 `InlineRenderer` 的倒错
定位代码：
- `reference/markdown-editor/src/components/BlockRenderer.tsx` L644-L668
- `reference/markdown-editor/src/components/InlineRenderer.tsx` L794-L856

```ts
/* BlockRenderer.tsx 现状 */
function stripCodeFenceIndent(
  tokens: InlineNode[],
  indent: number
): InlineNode[] {
  if (indent <= 0 || tokens.length === 0) return tokens;
  const first = tokens[0];
  if (first.type === 'text') {
    let spaces = 0;
    while (
      spaces < indent &&
      spaces < first.content.length &&
      first.content[spaces] === ' '
    ) {
      spaces++;
    }
    if (spaces > 0) {
      const strippedFirst: InlineNode = {
        ...first,
        content: first.content.slice(spaces),
      };
      return [strippedFirst, ...tokens.slice(1)];
    }
  }
  return tokens;
}
```
**致命漏洞剖析**：
1. **漏判 `blockquote_prefix`**：
   在 `parseCodeLine` 中，若代码块处于引用内，`tokens[0]` 的类型是 `'blockquote_prefix'`，真正的代码文本位于 `tokens[1]`。现有逻辑直接判断 `tokens[0].type === 'text'`，一旦遇引用直接失效！
2. **`raw` 守恒与 `indexOf` 错位崩溃**：
   现有代码只切除了 `first.content`，却未对 `first.raw` 进行同步标定。
   进入 `InlineRenderer.tsx`：
   ```ts
   const prefixLen = token.raw.indexOf(token.content);
   ```
   假设行首原本有 7 个空格（3 格围栏缩进 + 4 格 Python 缩进），`raw = "       "`。
   剥除 3 格后，`content = "    "`（4 格）。
   在 `InlineRenderer` 中，计算 `prefixLen = "       ".indexOf("    ")`，**返回的索引恰恰是 0**！
   结果：
   - 前缀 `prefix = raw.substring(0, 0) = ""`！
   - 剥除的 3 格被放到了后缀 `suffix = raw.substring(4) = "   "` 中！
   - 渲染出来的可视节点 `<span>{token.content}</span>` 依然包含了错误的字符位置，且 `data-sub-offset` 彻底倒错，导致光标定位失准！
3. **整空格 token 切空后的渲染倒退**：
   若该行仅缩进 2 格且紧跟关键字（如 `  def foo():`），`tokens[0]` 为纯空格 `{ content: "  ", raw: "  " }`。
   `content.slice(2)` 变成空串 `""`。
   在 `InlineRenderer` 中，`token.content !== ''` 为 false，退化进 `else` 分支。
   当光标落在行内时，`.is-active-token` 激活，`.syntax-hidden` 强制显示，被剥除的空格再次赫然回显在屏幕上！

#### 缺陷 3：`LangRenderer` 与代码复制（Copy）链路的整体失守

/* ============================================================
   REPLACEMENT TARGET: reference/markdown-editor/src/components/BlockRenderer.tsx
   Lines 644 - 668 (stripCodeFenceIndent 彻底重构)
   ============================================================ */
/**
 * CommonMark §4.5: 若开围栏行有 1~3 空格缩进（常见于列表内嵌套代码块），
 * 则代码块内每行至多剥除对应空格数，消除异常缩进，保持卡片顶格对齐与精准光标。
 */
function stripCodeFenceIndent(
  tokens: InlineNode[],
  indent: number
): InlineNode[] {
  if (indent <= 0 || tokens.length === 0) return tokens;

  // 1. 跳过前置的 blockquote_prefix，定位到代码首个内容 token
  let targetIdx = 0;
  while (
    targetIdx < tokens.length &&
    tokens[targetIdx].type === 'blockquote_prefix'
  ) {
    targetIdx++;
  }
  if (targetIdx >= tokens.length) return tokens;

  const target = tokens[targetIdx];
  // 2. 仅当代码首 token 为 text 且包含前导空格时处理
  if (target.type === 'text') {
    let spaces = 0;
    while (
      spaces < indent &&
      spaces < target.content.length &&
      target.content[spaces] === ' '
    ) {
      spaces++;
    }
    if (spaces > 0) {
      const remainingContent = target.content.slice(spaces);
      // 若首 token 被完全剥空（纯缩进空格 token），从流中彻底剔除，避免激活态倒退回显
      if (remainingContent.length === 0) {
        return [
          ...tokens.slice(0, targetIdx),
          ...tokens.slice(targetIdx + 1),
        ];
      }
      const strippedTarget: InlineNode = {
        ...target,
        content: remainingContent,
        raw: target.raw.slice(spaces),
        length: target.length - spaces,
      };
      return [
        ...tokens.slice(0, targetIdx),
        strippedTarget,
        ...tokens.slice(targetIdx + 1),
      ];
    }
  }
  return tokens;
}
