## 3. ADR-01：C-1 认证方案三选一（A-1）——四类令牌分治

- **状态**：已裁决（R0 协议冻结评审会，2026-08-10 关闭）
- **决策人**：主调度者 + 审计轮（AU3 §5.1 C-1 / AU1 P1-5、P1-10）
- **关联项**：C-1 = A-1（AU3 §8.1）；Z0 §3.1 C-1 行、§3.6 A-1 行
- **影响范围**：桌面 server 模块 handler 面、移动端连接层（signer.ts）、中继握手、推送直推、协议包生成器——四端全部实现

### 3.1 背景

方案库存在三套认证与消息面并存（AU3 §5.1 C-1）：

| 方案 | 文档 | 形态 |
|------|------|------|
| A | D2 §7/§8 | 配对码 → 32 字节随机令牌 + Bearer 头 + REST + WS JSON Lines；每消息无签名 |
| B | D3 §4-5 / M6 / M7 / D5 | CXN-12 配对码 + X25519 ECDH + PAKE 混合 + 消息级 HMAC-SHA256 + DeviceEnvelope（103 kind schema 已细化） |
| C | D4 §12.5 / M5 §4.2 | WsEnvelope 第三套帧格式，与 B 不兼容 |

三套并存 = 三倍实现 + 三倍测试 + 必然漂移。同时令牌面存在第三套形态（D5 §3.3 的 256bit 随机令牌 vs D3 §4.4 派生形态 vs D2 的 Bearer 随机令牌），M7 已用四类令牌分治收敛（【裁决修正 10】M7 §4.2:721-724 明确"四类令牌分治为认证方案唯一真源"）。

### 3.2 决策

**选 B：以 D3/M6 为协议真源——DeviceEnvelope + 消息级 HMAC-SHA256，四类令牌分治（M7 §4）作为认证体系正式结构。** 推导如下：

1. **消息面统一 DeviceEnvelope**（D3 §5.1 / M6 §10）：每条消息带 `auth {deviceId, ts, nonce, sig}`，`sig = HMAC-SHA256(token_key, canon(header) ∥ bodyJson)`，nonce ±5min 防重放；103 kind 由 M6 注册表冻结。D2 的 axum 只承担"监听 + 信封编解码"，**Bearer 令牌面作废**（D2 已收敛：会话令牌语义 = D3 token_key 派生体系）；**D4 §12.5 的 WsEnvelope 作废**（M5 §0.2 已声明信封并入 D3 体系，两处文档均已完成收编标注）。
2. **认证面按四类令牌分治**（M7 §4.1-§4.2，各司其职、互不代替——M-04）：
   - **T1 配对令牌（token_key/refresh_key）：本地形态**。D3 §4.4 配对派生（X25519 ECDH + 配对码 PAKE → master → HKDF 三子钥），桌面落盘派生值、移动端 Keychain/Keystore；**不依赖云、不出桌面**——局域网断网仍可配对与控制（M7 §4.2"局域网直连"行）；端间消息鉴权唯一凭据。
   - **T2 账号 token（access 15min / refresh 30 天）：云端不共享**。账号中心签发验证（AC §4.3.1）；双端各自登录同一账号、各自持有各自会话（M-05：令牌共享反而扩大泄露面——一端泄露 = 两端同时失守）；两端经"同一 accountId 下设备注册表"互认（F6 §5.2），**不存在"两端同一份 token"设计**。
   - **T3 中继凭据 rc_<32B>：HMAC-only**。账号中心签发（明文只返回一次），服务端只存 HMAC，verify 走一次性 nonce（中继本地缓存 ≤5min），TTL 30 天可刷新（AC §6.4）；独立于 access token 生命周期——避免"长连接用 15min access token 频繁过期、用 refresh 轮换语义不符"（M7 §4.2"中继长连接"行）。
   - **T4 推送注册 push_tokens：寻址表**。厂商 SDK 生成 → 注册到账号中心（token_hash 幂等），与身份令牌解耦（M7 §4.2"推送寻址"行）；发送方 = 桌面 push-core 直连厂商。
3. **信任根唯一**（AU1 §2.3）：master 是唯一信任根——M3 P2P 链路密钥（k_link）、M2 中继 AEAD（enc_key）均从 master 展开，无第二套独立密钥体系。
4. **否决项**：否决 A（Bearer）——每消息无签名，重放/篡改防护弱（AU3 §5.1 C-1 优缺点表），且单令牌无法覆盖"局域网离线 / 云端身份 / 中继长连接 / 推送寻址"四个正交问题；否决 C（WsEnvelope）——第三套帧格式，与 B 不兼容，属 D4 在 D3 冻结前的早期草案。

### 3.3 后果

- **正面**：D5/M7 安全模型（M-TOKEN/M-VERIF/M-OUTBOX）与 M6 的 103 kind schema 全部直接成立；移动端 signer.ts 只实现一套签名逻辑；中继/推送无需第二套鉴权。
- **代价**：R0 一次性投入（DeviceEnvelope 编解码 + HMAC 实现 + 配对派生链），已计入 R0-02/R0-03 任务包；D2 §7 Bearer 面与 D4 §12.5 WsEnvelope 的文档作废标注已完成（裁决修正 2/5/10 已落各文档）。
- **验收锚点**：T-D3-01（配对全流程）、T-D3-02（令牌派生一致性 HKDF 已知向量）、T-D3-08（命令白名单拒绝）、对拍门禁绿（R0-05）。

## 4. ADR-02：C-2 TLS 范围（A-2）——wss 强制 + 自签 CA pinning

- **状态**：已裁决（R0 协议冻结评审会，2026-08-10 关闭）
- **决策人**：主调度者 + 审计轮（AU3 §5.1 C-2 / D5 §10.1 ADR 既有裁决）
- **关联项**：C-2 = A-2（AU3 §8.1）；Z0 §3.1 C-2 行、§3.6 A-2 行；D5 §10.1 ADR"传输协议"行
- **影响范围**：自签证书生成与生命周期（R1-06）、移动端证书固定（R2-03）、配对载荷携带 tlsFingerprint（D3 §4.6）、D1 P1 验收 ⑤、开发期 S1 联调矩阵

### 4.1 背景

局域网直连的安全基线冲突（AU3 §5.1 C-2）：

- D2 §3.2 非目标 5：「v1 不做 TLS，局域网可信模型假设」；
- D1 §8.2 P1 验收 ⑤：「抓包验证 TLS + 指纹校验生效」——验收无法两全；
- D3 §3.1：「TLS 首选（自签证书 + 配对期证书指纹交换），无 TLS 降级必须显式开启」；
- D5 §10.1 ADR：「wss 强制 + 自签 CA pinning」——安全母方案既定。

### 4.2 决策

**wss 强制 + 自签 CA pinning 直接进 R1，无"免 TLS v1"阶段**：

1. **传输层**：TLS 1.3/1.2 仅 AEAD 套件 + ECDHE（D5 第 2 层）；禁止 ws 明文降级（TH-04 缓解）；系统 CA 不参与信任链（TH-03 缓解——ARP+伪造 CA 中间人）。
2. **信任建立时机 = 配对期**：自签 CA 由桌面生成（R1-06 rustls 装配 + 证书生命周期），证书指纹 `tlsFingerprint` 经**配对码信道带外传递**（D3 §4.6/§4.8：`pair.challenge` 载荷携带）；移动端 TLS 钉扎只信该指纹——配对即建立信任，无需用户手动导入证书。
3. **废除项**：D2 §3.2"免 TLS v1"删除/标记为废弃（已由 D2 §11-G 裁决修正标注）；"中继路径加密前的过渡选项"表述一并取消——中继路径本身走 wss + 端到端 enc_key AEAD（M2 §5.6）。
4. **开发期例外**：S1 本机联调允许 dev 放宽指纹校验、production 强制（D4 §10.2 联调矩阵）；任何放宽不得进入 production 构建路径。

### 4.3 后果

- **正面**：D1 P1 验收 ⑤ 与 D5 红线 1-7 全部可执行；局域网窃听（TH-08）、帧注入（TH-04）、QR 钓鱼（TH-19）三类威胁闭环；移动端商店审核"传输加密"要求满足（AU3 §5.1 C-2 理由）。
- **代价**：R1-06 证书面工作量（自签生成/轮换/指纹钉扎，约 3-5 人日）；配对协议多一字段（tlsFingerprint，已设计进 D3 §4.6，无协议变更成本）。
- **验收锚点**：R1-06 的 TLS 检查清单 TLS-01~10（仅 AEAD 套件、禁 ws 降级、指纹校验）；D1 P1 验收 ⑤ 抓包验证；移动端 R2-03 证书固定真机验证。

## 5. ADR-03：C-3 移动端审批时机（A-3）——审批中心 P0（R2 首批）

- **状态**：已裁决（R0 协议冻结评审会关闭；R2 排期前做最终确认，责任转 R2 任务包 R2-04）
- **决策人**：主调度者 + 审计轮（AU3 §5.1 C-3）
- **关联项**：C-3 = A-3（AU3 §8.1）；Z0 §3.1 C-3 行、§3.6 A-3 行；Z0 §5.3 功能×阶段矩阵
- **影响范围**：R2 审批中心范围（F2 全量）、R3 推送联动（深链直达）、D4 M2 里程碑、移动端第一功能定位

### 5.1 背景

产品定位冲突（AU3 §5.1 C-3）：

- M8 §9.3 O2：「一期只收通知 + 查看，决策按钮需新增移动端 → 桌面命令通道」；
- D1 §8.2 P1：「手机……审批端到端 <2s」——远程审批是母方案 P1 验收红线；
- D4 §11.1 M2：审批中心里程碑（3 周：审批卡 UI + 状态机 + 决策发送 + outbox）；
- F2 全篇：审批中心域设计（L1/L2 决策、双因素、离线 outbox）——决策链路完整、无技术阻塞。

若采纳"一期只收通知"，R2 核心价值（远程审批）被砍，D4 M2 / F2 整域白做（AU3 §5.1 C-3 影响分析）。

### 5.2 决策

**移动端审批中心 P0，随 R2 首批开放决策发送（approve/deny）**：

1. **R2 审批中心包含完整决策链路**：审批卡 UI + 审批流状态机 + 决策发送（cmd.approve/cmd.deny）+ 离线 outbox + 双阶段确认（绝不乐观显示"已批准"，D6 §8.3）+ 120s 超时展示（F2 §8）；3 秒决策路径（推送→生物解锁→决策，点按 ≤3 次）。
2. **R3 推送只负责"通知 + 深链直达"**：推送域与审批域互补不重叠——R3 提供息屏/杀进程后的系统通知与 `approval/[toolCallId]` 深链，点击直达审批卡完成决策；与 R2 在审批中心的交互设计解耦。
3. **M8 O2 的保守默认仅作安全边界表述**：不作产品裁减（AU3 §5.1 C-3 建议原文）；"推送域独立于审批域时的安全边界"表述保留于 D7/M8，不影响 R2 审批决策开放。
4. **验收红线不降**：审批端到端 <2s（局域网）/ <3s（4G 异地）；离线决策入 outbox 送达 P95 达标。

### 5.3 后果

- **正面**：D1 P1 验收红线（审批 <2s）与 R2"能用了"定义成立（Z0 §8.10）；F2 整域价值落地；R3 深链直达有 R2 审批中心承接。
- **代价**：R2 排期含审批中心全量（R2-04 约 3 周，L 级）；移动端安全面提前引入（L1/L2 验证分层随 M7 落地）。
- **验收锚点**：R2-04（离线决策送达 P95 / 幂等测试 / 双阶段确认语义）；R2-16（F2 验收 1-7 + 真机审批闭环）；R3-04（三形态深链直达）。

## 6. ADR-04：A-4 统一阶段命名（P-5）——R0-R5

- **状态**：已裁决（R0 协议冻结评审会，2026-08-10 关闭；Z0 §3.6 A-4 行"本文档即载体"）
- **决策人**：主调度者 + 审计轮（AU3 §2.3）
- **关联项**：A-4 = P-5（AU3 §5.2）；Z0 §8.14 阶段迁移动作
- **影响范围**：全部任务书引用、11 份文档的 P/M/L/R 前缀、验收锚点挂靠

### 6.1 背景

P/M/L/R 四套前缀 + 数字编号在 11 份文档中混用且语义互撞（AU3 §2.1 全表）：D1 的 P1 ≠ M1 的 P1；D4 的 M2 ≠ D7 的 M2 ≠ D5 的 M2 ≠ AC 的 M2；D2 的 P0-P5 与 D1 的 P0-P3 直接冲突（D2 P0=文档评审 1 天 vs D1 P0=原型开发 1 周，引用歧义差一个数量级）。

### 6.2 决策

**统一为 R0-R5 六阶段**（R0 协议冻结 / R1 桌面服务端 / R2 移动端基础 / R3 推送 / R4 中继+P2P / R5 鸿蒙），替换全部 P/M/L/R 前缀：

1. R 前缀避开全部既有 P/M/L 撞名；语义与 D1 母方案对齐（R1≈D1 P1 桌面侧、R2≈D1 P1 移动侧、R3≈D1 P2 推送面、R4≈D1 P2 中继面、R5≈M1 P2 鸿蒙面）——母方案验收标准可直接挂靠（AU3 §2.3 理由）；
2. R0 单列"协议冻结"：与 D8 阶段 0/1 对齐，是全链唯一"一切之前"的前置，不给独立阶段号会被并排期压缩（AU3 §2.3 理由 3）；
3. 迁移动作（低成本，不重写 25 份文档）：各方案文档头加一行"本方案阶段 ↔ 统一阶段映射"（对照表见 Z0 §8.14）；任务书引用一律用统一阶段号；后续任务书（PE 系列）不得再出现 P/M/L 前缀（Z0 附录 A）。

### 6.3 后果

- **正面**：排期与验收引用歧义消除；D2/D1 的 P0 撞名陷阱关闭；M8 M1 与 M1 平台 P1 的排期合并语义明确。
- **代价**：11 份文档头映射行的一次性标注（已列入 AU3 §2.3 迁移动作，属 P-5 低成本项）。
- **验收锚点**：Z0 §8.14 迁移动作完成核对；R0 出口检查"任务书引用全部使用 R0-R5 编号"。

## 8. ADR-06：A-6 配对码参数（P-2）——D3 CXN-12 字符

- **状态**：已裁决（R0 协议冻结评审会，2026-08-10 关闭；Z0 §3.6 A-6 行）
- **决策人**：主调度者 + 审计轮（AU3 §5.2 P-2 / AU1 P0-1）
- **关联项**：A-6 = P-2（AU3 §5.2）= P0-1（AU1 §10.1）；Z0 §3.2 P-2 行、§3.3 P0-1 行
- **影响范围**：配对码生成/校验/锁定逻辑、二维码载荷、移动端输入 UI、审计打码断言（D5 §6.3 / M7 KB-2）、配对时长口径

### 8.1 背景

五套规格并存（AU1 P0-1 冲突方）：D2 §7.2（8 字符 40bit 120s）/ D3 §4.1（CXN-12 字符 60bit 10min）/ D5 §3.2（8 字符 base32 10min）/ D7 §4.5a（6 位 5min）/ F6 §6.1/§12.3（6 位 10min）。码长一变，D5 §6.3 / M7 KB-2 的安全测试断言全部失效。

### 8.2 决策

**以 D3 §4.1 的 CXN-XXXX-XXXX-XXXX 为唯一真源**：

1. 格式 `CXN-XXXX-XXXX-XXXX`（3 组 × 4 字符，去 0/O/1/I/L 的 base32 子集）；熵 60bit；人读回显 CXN- 前缀，输入忽略分隔符与大小写（`normalize_pair_code()` 标准化）；
2. 有效期 10 分钟（PAIR_CODE_TTL_MS=600_000）；单码失败上限 5 次；并发码 ≤3；一次性（成功后立即作废）；桌面只存 `SHA-256(code+salt)` 不存明文；
3. QR 内容 `conex-pair://<code>?v=1&s=<desktopId短号>`，扫码与手动输入走同一 `pair.verify` 消息；
4. 作废规格：D2 8 字符 120s、D5 8 字符 base32、D7 6 位 5min、F6 6 位——全部改引用 D3 §4.1（D7 §4.5a 推送 WS 因 P1-5 方案甲并入协议面自然统一）；
5. 全流程时长统一 <60s（P2-5，M3 §12.2 验收锚点；F6 §6.1 的 <2 分钟口径作废）。

### 8.3 后果

- **正面**：熵最高（60bit）、二维码与手动输入同构、带前缀可识别；安全测试断言（打码形态）随唯一规格成立；配对流程 <60s 可验收。
- **代价**：D2/D5/D7/F6 四处文档引用修正（P0-1 修改建议已列出归属）；移动端输入 UI 按 CXN 格式实现。
- **验收锚点**：T-D3-01（配对全流程）、T-D3-02（派生一致性）；暴力穷举缓解（TH-15：限 5 次 + 锁定）依赖本参数生效。

## 9. ADR-07：A-7 事件变体策略（P-3）——41 变体冻结 + 会话面消息

- **状态**：已裁决（R0 协议冻结评审会，2026-08-10 关闭；Z0 §3.6 A-7 行）
- **决策人**：主调度者 + 审计轮（AU3 §5.2 P-3 / AU1 P1-2 关联）
- **关联项**：A-7 = P-3（AU3 §5.2）；D1 O1 关闭（Z0 §10.2）；Z0 §3.2 P-3 行
- **影响范围**：41 变体注册表（events.rs:789-852）、D2 桥、移动端解析器、F5 会话列表增量刷新、registry_drift 护栏

### 9.1 背景

事件变体策略三选一：D1 O1 倾向新增 `session-index-changed` 变体（走登记三件套：注册表 + 生成物 + 对拍）vs D2 §7.4 41 变体冻结不新增 vs M6 §13 会话面消息 `events.session.updated` 替代（走 D3 信封，不动 41 变体注册表）。

### 9.2 决策

**41 变体冻结不新增；会话列表增量走 M6 会话面消息**：

1. 跨端事件基 = AgentEventEnvelope 扁平 JSON 原样透传，41 变体注册表冻结（T=13 透传 / R=18 摘要化 / U=10 元组，M6 §5.1）；
2. 会话索引增量刷新走 `events.session.updated` / `session.removed`（D3 信封内的会话面消息，M6 §13 T-M6-12 验收锚点）——避开登记三件套成本（AU3 §5.2 P-3 理由）；
3. D1 O1 的"新增 session-index-changed 变体"**关闭**，降级为远期（Z0 §10.2 C 组已登记"此项关闭"）；
4. 同步面白名单以 M6 §5.0 的 20 类为准（P1-2 已裁决：D6 §7.3 可选表收缩，删 message-start/tool-batch-*/tool-input-repaired/checkpoint-* 可选项）；run-interrupted 实现前复核 restore.rs，不存在则移出白名单（P2-8）。

### 9.3 后果

- **正面**：零新增变体 → 零注册表漂移风险；F5 会话列表增量刷新有现成消息承载；registry_drift 双护栏（engine-events + device-protocol）不增负担。
- **代价**：移动端解析器需处理会话面消息（session.updated/removed）而非新增事件变体；D1 O1 文档标注降级。
- **验收锚点**：T-D3-10（配对审计不进 41 变体）、T-M6-12（会话索引广播）、对拍门禁（P3 改动面为零）。
