## 1. 结论摘要（TL;DR）

### 1.1 三层拓扑裁决

| 层 | 名称 | 场景 | 技术形态 | 服务器带宽 |
|----|------|------|----------|-----------|
| L1 | 局域网直连 | 同一 WiFi / 网段 | mDNS 辅助 + 二维码（含局域网 IP）引导 + TLS WebSocket 直连 | 0 |
| L2 | 云中继 | 跨网默认路径 | 双端出站 WS/UDP 经中继转发（M2 落地） | 全量（数据经中继） |
| L3 | P2P 打洞 | 跨网优选路径 | 中继协助自研 UDP 打洞 + 轻量可靠 UDP + AEAD 加密 | 约 0（仅信令） |

**路径优先级**：同一局域网（可达性判定命中）→ L1；跨网 → 先尝试 L3，失败回落 L2；
L2 不可用 → 离线投影模式（沿用 D1 §3.4 离线矩阵）。

### 1.2 P2P 技术裁决（核心结论）

**推荐：中继信令协助的自研 UDP 打洞（uu 远程模式）+ 自研轻量可靠 UDP 传输 +
AES-256-GCM 应用层加密（密钥派生自配对 master，复用 D3 §4.4 已预留的 `enc_key`）**。

| 候选 | 裁决 | 一句话理由 |
|------|------|-----------|
| WebRTC（ICE/STUN/TURN） | **方案 B（备选）** | 成熟但依赖重：RN 需原生模块 + New Arch 兼容风险（D4 R2）；桌面 Rust 需 webrtc crate 或 WebView 桥；鸿蒙生态缺失；小 JSON 帧上 SCTP 头开销高；仅在自研打洞达标率低时启用 |
| 自研 UDP 打洞（uu 风格） | **方案 A（采用）** | 信令复用现成中继 WS（D3 DeviceEnvelope 加 `link.*` 消息族即可）；数据面零新增基础设施；任何有 UDP socket 的平台可用（含鸿蒙）；帧开销最小；桌面 tokio UDP 零新依赖 |
| QUIC（HTTP/3 传输） | **否决（主传输）/ 远期桌面-桌面** | 内建 TLS 1.3 与连接迁移很吸引人，但 RN 移动端无成熟 QUIC 桥（quinn 仅桌面可用）；打洞仍需自己做；列为远期第二桌面场景增强 |

### 1.3 切换逻辑一句话

**make-before-break + 质量评分 + 滞回**：连接管理器维护候选链路集
（LocalLink / RelayLink / P2PLink 三实现，统一 `Link` 接口），按「可达性 →
质量分（延迟/丢包/成本）→ 冷却期」三级判定切换；新链路协议层就绪
（hello + subscribe + 游标追平）后才切换流量，旧链路保活至切换确认，
会话连续性由 D3/D6 已设计的逐会话游标续传兜底——**链路切换对业务层透明**。

### 1.4 带宽结论一句话

- **L3 打洞成功时服务器带宽约等于 0**：中继仅承担信令——单会话建立 2~10 KB，
  保活约每小时几十 KB，业务事件/命令数据 0 字节过服务器（量化见 §8.2）；
- **L2 中继兜底时**：启用 zstd 文本压缩（JSON 事件流压缩率 5~10 倍）+
  Delta 帧裁剪 + 每端带宽配额限流（衔接 M2，契约见 §5.3、§8.4）。

### 1.5 阶段一句话

**L1（快，2 周）→ L2（中，随 M2 落地 3~4 周）→ L3（大，6~8 周分三个里程碑）**。
L3 与 D1 的「远期 P4+」规划衔接：本方案将 L3 拆为可独立验收的三个里程碑，
M3a（信令扩展 + NAT 探测）与 M3b（可靠 UDP 传输）不依赖打洞成功率，
风险最高的 M3c（端口预测与并发打洞）最后收口（详见 §12）。

## 2. 背景与任务边界

### 2.1 任务输入

用户要求（M3 任务书）：

1. 设计 crish 多端互通的**网络分层拓扑**（局域网直连 → 云中继 → P2P 打洞），
   尽量不占服务器带宽——参考 uu 远程的「UDP 中转 / 打洞」模式；
2. 局域网直连深化（发现 / 安全 / 自动切换）；
3. P2P 打洞方案深挖（WebRTC / 自研 UDP / QUIC 三候选裁决；打洞状态机；失败回落）；
4. 路径选择与切换（Link 抽象；切换判定；会话连续性衔接游标续传）；
5. 带宽与成本量化（P2P 成功时服务器带宽约等于 0 的量化；中继兜底压缩/限流）；
6. 与协议衔接（连接层与消息层分离；Link 层帧格式）；
7. 安全（P2P 直连加密不降级；打洞信令防滥用）；
8. 测试（NAT 场景矩阵、切换、回落）；
9. 工作量与阶段（L1 → L2 → L3）。

### 2.2 既有方案裁决与本方案的增量

| 移动端：Expo SDK 57 / RN 0.86（New Arch 默认）/ RN 内建 WebSocket / netinfo | D4 §3 | L3 需要新增原生 UDP socket（自研薄 TurboModule，§6.6）；RN 新架构风险 R2 直接适用 |
| 中继：只转发不解密、无业务状态、可选推送 | D1 §3.3 | 扩充中继为「转发 + 信令 + 探测辅助」三位一体（§5、§6.3），带宽目标不变 |
| 推送：桌面内嵌 WS 直推优先，云中继为演进 | D7 §1、§路线 C | 命名对齐说明见 §2.3 |

### 2.3 命名对齐说明（重要）

D7 文档中「M3 云中继」（`D7-push-notifications.md:15,1481,1507`）指的是**云中继服务**
这一演进项；本任务编号体系里**中继服务 = M2**，**本方案 = M3（网络拓扑与 P2P）**。
二者指向同一演进方向（自建云中继），后续文档统一以本任务编号为准：
`M2 = 云中继服务`，`M3 = 本方案`。D7 的「M3 云中继」在 L2 落地后即视为
「M2 中继 + L2 RelayLink」，无功能冲突。

### 2.4 网络层设计原则

1. **协议面与链路面严格分离**：D3 的 DeviceEnvelope 跑在任何链路上，链路层
   不感知业务消息语义；链路切换不改变协议面（§9）。
2. **服务器带宽最小化是硬目标**：P2P 成功时数据 0 过服务器；中继路径只在
   L3 不可用时启用，且启用时有压缩与限流（§8）。
3. **桌面绝不被动暴露除网关端口以外的面**：P2P 阶段桌面只出站 UDP，不做
   入站监听——入站打洞探测是「对已知对端地址的应答」，不是监听服务（§6.8）。
4. **安全不因直连降级**：P2P 直连加密强度与中继路径持平（AEAD + 防重放），
   密钥唯一来源是配对 master（§10）。
5. **一切切换对业务透明**：移动端 UI 只感知连接相位（沿用 D4 §6.2.5 相位投影），
   不感知底层链路（§7.5）。
6. **诚实边界**：P2P 是「尽力而为的带宽优化」，不是可用性承诺；中国网络环境
   运营商 CGNAT 普遍，打洞成功率预期 50%~80%，失败即回落 L2——这是产品行为
   不是缺陷（§6.7、§12.5 风险表）。

### 2.5 术语表（本方案新增）

| 术语 | 含义 |
|------|------|
| Link | 一条端到端传输通道的实现（L1/L2/L3 各一实现） |
| LinkFrame | 链路层帧格式（消息信封外层再包一层，§9.2） |
| LinkManager | 路径选择与切换管理器（每端一个） |
| 候选集 | LinkManager 维护的可选链路集合（LocalLink / RelayLink / P2PLink） |
| 打洞（punch） | 通过双向 UDP 探测穿透 NAT 建立直连的过程 |
| 反射地址（SRFLX） | NAT 分配给会话的公网 IP:port（server-reflexive 候选概念） |
| 端口预测 | 对称 NAT 下根据连续探测的端口增量预测下一次映射端口的技术 |
| punch-ticket | 中继签发的短时打洞许可（防信令滥用，§10.3） |
| make-before-break | 新链路协议层就绪后才切换、旧链路保活至切换确认的策略（§7.4） |
| 相位投影 | 把传输层状态映射为 UI 连接相位的纯函数（沿用 D4 §6.2.5） |

## 3. 三层拓扑总览

### 3.1 三层定义与职责

```
                         ┌─────────────────────────────────────────┐
                         │             桌面端（Hub）                 │
                         │                                         │
  L1 局域网直连           │  TLS WS 服务网关（0.0.0.0:8765 起）        │
  ───────────────►       │  ├─ LocalLink 服务端（入站，D2 产物）      │
  同网段手机 ─────────────►  ├─ RelayLink 客户端（出站，连中继）        │
                         │  ├─ P2P 客户端（出站 UDP，打洞）           │
                         │  └─ LinkManager（路径裁决，桌面侧决策面）    │
                         └──────────────┬──────────────────────────┘
                                        │
                         ┌──────────────▼──────────────┐
                         │     L2 云中继（M2 落地）       │
                         │  ┌────────┬────────┬────────┐ │
                         │  │ 转发面  │ 信令面  │ 探测面  │ │
                         │  │(数据)   │(link.*)│(NAT 探测)│ │
                         │  └────────┴────────┴────────┘ │
                         └──────────────┬──────────────┘
                                        │（L3 信令经中继，数据直连）
                         ┌──────────────▼──────────────┐
                         │     移动端（Companion）        │
                         │  ├─ LocalLink 客户端（L1）      │
                         │  ├─ RelayLink 客户端（L2）      │
                         │  ├─ P2P 客户端（L3，UDP）       │
                         │  └─ LinkManager（移动侧裁决面）  │
                         └─────────────────────────────┘

 L3 P2P 打洞：信令经中继交换，打洞成功后 UDP 数据流直连对端，中继只做信令。
```

### 3.2 每层的触发条件 / 切换逻辑 / 回退（总矩阵）

| 判定 | 当前层 | 条件 | 动作 |
|------|--------|------|------|
| 启动连接 | — | 候选集构造完成（§7.2） | 按优先级评估：L1 可达 → L1；否则并行发起 L3 与 L2 |
| 保持 L1 | L1 | 同网可达 + 质量合格 | 继续；L2/L3 候选保持休眠（不建连） |
| L1 失联 | L1 | L1 连续探测失败（桌面睡眠 / 换网 / AP 隔离） | 先尝试 L3（若上次成功过或策略允许），失败或超时（3s 探测窗口）切 L2 |
| 跨网启动 | L2 | 移动端在蜂窝网 / 异地网 | 优先发起 L3（历史成功率高时先 L3，否则并行）；L3 未就绪时流量走 L2 |
| L3 成功转正 | L3 | 打洞 + 验证 + 3 次 RTT 采样合格（§7.4） | 切换流量到 L3；L2 连接保活为热备 |
| L3 失效 | L3 | 连续 2 次丢包超阈 / 心跳超时 / NAT 映射失效 | 回落 L2（热备，秒级）；30s 冷却后允许重试打洞 |
| L2 → L3 | L2 | 网络恢复平稳 + 冷却期过 + L2 质量差（如高延迟） | 后台重试打洞；成功后 make-before-break 切 L3 |
| 全部不可达 | — | L1/L2/L3 均失败 | 离线投影模式（D1 §3.4）+ 网络监听触发重连 |

**回退铁律**：

1. **L2 是唯一「保证可达」的层**（前提：M2 中继服务在线）——L3 的任何失败
   都不允许导致移动端失联；
2. 切换动作永远由**新链路协议层就绪**驱动，不是由「旧链路断开」驱动
   （make-before-break，§7.4）；旧链路断开的唯一后果是提前触发候选评估；
3. 局域网内**不打洞**：L3 只在跨网时启用（同网 L1 延迟 1~10ms 已最优，
   打洞只会引入协商开销，D1 §3.1.3 已论证 WebRTC 在局域网无优势——自研打洞同理）。

### 3.3 桌面侧与移动侧的链路职责不对称

| 端 | 入站 | 出站 | 链路管理职责 |
|----|------|------|-------------|
| 桌面 | L1 WS 服务（0.0.0.0:8765） | L2 中继出站、L3 UDP 出站 | 维护 L2/L3 出站链路；L1 是服务端不主动建链 |
| 移动端 | 无入站 | L1/L2/L3 全出站 | 主导建链顺序与切换判定 |

**关键不对称**：切换的**发起方是移动端**（移动端网络环境变化频繁：WiFi 与
蜂窝切换、后台恢复）；桌面侧被动跟随——移动端切换后在新链路上发起 hello +
subscribe，桌面侧按连接族管理（§7.5.4）识别「同设备的新链路」，旧链路由
桌面侧主动关闭或短时共存。

### 3.4 与 D1 §3.7.2 决策表的演进关系

D1 决策表是两候选（LocalLink / RelayLink）；本方案升级为三候选，并补充
「L1 与 L3 的场景正交性」：L1 解决「同网」，L3 解决「跨网直连」，二者不构成
切换竞争（同网绝不打洞）。L2 是跨网兜底。因此路径优先序为：

```
同网判定命中 ──► L1
跨网判定命中 ──► L3（转正成功）──► 长期持有
             └─► L2（L3 失败 / 未就绪期间的兜底流量通道）
```

## 4. L1 局域网直连深化

### 4.1 发现三通道（主次分明）

| 通道 | 角色 | 方向 | 可靠性 | 说明 |
|------|------|------|--------|------|
| 二维码引导 | **主通道** | 桌面 → 移动端（扫码） | 高 | 内容直接携带局域网端点（IP:port + 指纹），零依赖 mDNS |
| mDNS/DNS-SD | 辅助通道 | 双向广播 | 中 | 桌面广播 `_crish-hub._tcp.local.`；移动端「附近桌面」列表刷新；Windows 需纯 Rust 实现 |
| 手动输入 | 兜底 | 用户手输 | 高 | 桌面设置页展示 `IP:port + 配对码`（D3 §4.1 的 CXN- 格式） |

裁决：**二维码是唯一必须成功的通道**，mDNS 只是体验增强（移动端不必等待
mDNS 才能连接——扫码即得端点）。理由：

1. iOS 上 mDNS 需要 `NSLocalNetworkUsageDescription` 权限弹窗（首次触发即
   吓退用户），且 iOS 16+ 本地网络权限收紧；二维码路径零权限问题；
2. Windows 系统不内置 mDNS 广播服务（需要 Bonjour 或自实现 DNS-SD，
   D1 §3.5 已注明不可靠）——二维码规避了桌面侧 mDNS 不可靠的问题；
3. 二维码同时完成「端点发现 + 配对码传递 + 桌面身份确认」三件事，
   与 D3 §4.1 的配对流程天然衔接。

### 4.2 mDNS 实现选型（桌面侧）

- **库**：`mdns-sd`（纯 Rust DNS-SD 实现，Windows/Linux/macOS 无系统依赖，
  无需 Bonjour 服务；MIT 协议）。与 D2 §6.4 的依赖纪律核对：D2 允许在
  `axum`/`tokio-tungstenite` 之外按需加依赖，mdns-sd 属同类（纯 tokio
  生态，无 C 依赖），登记进 D2 的 Cargo.toml 改动清单即可。
- **广播内容**：`_crish-hub._tcp.local.`，TXT 记录携带：
  - `v=1`（协议版本）
  - `id=<desktopId 前 8 位>`（人类可辨）
  - `fp=<证书指纹前 8 位>`（预核对，防扫到假桌面）
  - `tls=1`（是否启用 TLS，恒为 1）
  - SRV 记录 = `desktopId.local:8765`
- **广播生命周期**：网关启动时注册、关闭时注销；每 5s 重发（DNS-SD 标准
  刷新间隔取 1/4 TTL，TTL 取 30s）；
- **多网卡**：mdns-sd 按接口广播（IPv4 链路本地组播 224.0.0.251:5353），
  多个物理网卡各自广播，不需要手动枚举 IP；
- **移动端消费**：可选增强（见 §4.3 裁决）；若实现，用
  `react-native-local-network-permission`（iOS 权限）+ 自研轻量 DNS-SD 查询
  或依赖 `bonjour-service` 的 JS 移植——**列为 P2 后增强，P1 不做**。

### 4.3 二维码端点扩展（与 D3 §4.1 衔接）

D3 §4.1 的二维码格式为：

```
conex-pair://<code>?v=1&s=<desktopId短号>
```

本方案扩展为（向后兼容：新移动端能读旧码，旧移动端忽略新参数）：

```
conex-pair://CXN-7K4P-Q2MB-9XRT?v=1&s=a1b2&h=192.168.1.23:8765&h=192.168.1.24:8765&fp=3f4a2c
```

| 参数 | 含义 | 说明 |
|------|------|------|
| `code` | 配对码（D3 §4.1 格式不变） | 主鉴权材料 |
| `s` | desktopId 短号（D3 已有） | 配对目标确认 |
| `h` | 局域网端点候选，可多个（重复参数） | **本方案新增**；桌面枚举全部网卡 IP（§4.4），首选 IP 在前 |
| `fp` | 证书 SHA-256 指纹前 8 位 | 预核对；完整指纹仍走 D3 §4.6 的 pair.challenge 带外传递 |

**端点候选枚举规则（桌面侧）**：

1. 枚举本机所有非回环 IPv4 地址（用 `if-addrs` crate 或 Windows 平台 API——
   D2 §7.3 已有 windows-sys 先例，登记依赖时二选一）；
2. 排序而非硬过滤虚拟网卡（VirtualBox / WSL / tailscale 等虚拟适配器）：
   按「物理网卡优先、虚拟网卡标记次之」排序，移动端按序尝试（每个候选
   3s 超时跳到下一个）；`169.254.*`（链路本地）地址标记为末位；
3. 若启用了 tailscale（用户明确「tailscale 也可但带宽低」），tailscale 的
   `100.x.y.z` CGNAT 地址天然在枚举结果内——二维码同时携带 WiFi 局域网 IP
   与 tailscale IP 两类候选，移动端按序尝试，谁通用谁（tailscale 通 =
   跨网也通，天然成为「无需自建中继的跨网直连」通道，见 §4.6 备注）；
4. IPv6：同一 WiFi 若支持 IPv6（SLAAC），附带全局 IPv6 候选（带 `[...]`
   方括号，符合 RFC 3986）；无 IPv6 时不发空候选。

**移动端解析规则**：

1. 扫码 → 解析 `h` 列表 → 按序尝试 TLS WS 连接（每个 3s 超时）；
2. 全部失败 → 若为同一 WiFi 且 mDNS 可用，尝试 mDNS 反查（辅助）；
3. 仍失败 → 进入「跨网路径」（L2/L3，§7.2）。

### 4.4 多网卡与绑定面

- 网关绑定面沿用 D2 §5.1 决策：默认 `127.0.0.1`，配对模式开启时绑
  `0.0.0.0`（D2 §12.1 绑定面安全边界不变）；
- 二维码 `h` 列表在「配对模式开启」时生成（此时 0.0.0.0 生效）；
- 移动端连接时用 `h` 中的具体 IP，不依赖绑定面的主机名解析；
- 桌面端监听所有接口意味着网关同时暴露在多个网段（WiFi + 有线 + 虚拟网卡），
  令牌鉴权（D2 §7.2）是统一防线，绑定面本身不做网段白名单（保持简单）。

### 4.5 直连安全（与配对协议衔接）

| 威胁 | 防护 | 出处 |
|------|------|------|
| 局域网内冒名桌面（伪造二维码 / 伪造 mDNS） | 证书指纹固定：完整指纹经 pair.challenge 带外传递；移动端 TLS 钉扎 | D3 §4.6 |
| 配对被窃听（配对码在传输中泄露） | X25519 ECDH + 配对码 PSK 混合派生 master（60bit 熵 + 256bit 前向安全） | D3 §4.4 |
| 重放攻击 | 每条消息 HMAC 签名（token_key）+ nonce 窗口 | D3 §5.1 |
| 局域网内其它设备连入 | 令牌鉴权 + Origin 校验 | D2 §7.2、§12.3 |
| 二维码被转发给他人 | 配对码一次性 + 10min TTL + 桌面 UI 显式授权（配对模式开启才有码） | D3 §4.3 |

**本方案补充**：二维码 `h` 中的端点列表本身不携带敏感信息（配对码才是
秘密）；`fp` 前缀仅用于「扫到错码立刻提示」，不构成信任依据。

### 4.6 手机端局域网自动切换（L1 与 L2/L3 场景）

**需求**：手机在同一 WiFi 时用 L1；离开 WiFi（出门 / WiFi 断）时自动切
L2/L3；回到 WiFi 时自动切回 L1。

**方案：不依赖 SSID 匹配，用「候选可达性 + 质量评分」驱动**：

1. **候选集**（LinkManager 持有，§7.2）：
   - LocalLink 候选 = 历史成功过的局域网端点（上次配对 / 上次连接缓存，
     含二维码 `h` 列表与 mDNS 结果），按最近成功时间排序；
   - RelayLink 候选 = 中继地址（配好后固定）；
2. **触发时机**：`@react-native-community/netinfo` 网络状态变更事件
   （WiFi 与蜂窝切换、WiFi 失联、恢复联机）→ LinkManager 立即重评候选集
   （D4 §6.2 已要求 netinfo 触发即时重连）；
3. **判定**：
   - WiFi 上线且 LocalLink 候选存在 → 并行探测 L1（1 次 RTT 探测，300ms
     内通 → 切换，make-before-break）；
   - WiFi 失联 / 跨网 → L1 自然断（探测超时）→ 走 L3 → L2（§3.2 矩阵）；
   - 蜂窝网络下**不探测 L1**（蜂窝 IP 与局域网必然不同网段，探测纯浪费）；
4. **防乒乓**：切换后 60s 冷却（§7.4.4）；L1 短暂抖动（WiFi 漫游）由
   「连续 2 次失败才判定失联」吸收。

**tailscale 衔接备注**：移动端若装了 tailscale 客户端，二维码 `h` 中的
tailscale IP 直连路径天然成为「跨网直连」选项（不经中继、数据不绕云）。
本方案把它当作 **L3 之外的第三方直连通道**处理：它只是「另一个可达端点」，
走 L1 同款逻辑（TLS WS + 指纹），不进入打洞流程。用户感知「带宽低」的原因：
tailscale 默认走 DERP 中继（打洞不成功时），与我们的 L2 中继等价；打洞成功
时 tailscale 也是直连。**优先级排序**：L1 同网 > L3 打洞直连 > tailscale
直连 > L2 中继——tailscale 通道与自建中继、自研打洞共存无冲突，三层拓扑
不依赖 tailscale 存在。

## 5. L2 云中继（M2 接口预留）

> M2 方案未产出。本节定义的是 **M3 对中继服务的接口契约**（服务端 API +
> 客户端行为 + 带宽约束），M2 落地时必须满足；M2 的自由度：服务端语言 /
> 部署形态 / 账号体系（D1 §4.5 预留）/ 可观测实现。

### 5.1 中继角色定义（三位一体）

| 角色 | 功能 | 归属 | 带宽特征 |
|------|------|------|----------|
| 转发面 | 双端出站连接间的数据转发（L2 兜底数据通道） | M2 | 全量数据过服务器 |
| 信令面 | `link.*` 消息交换（打洞协商 / 切换通知 / 在线状态） | M2 + M3 契约 | 极小（KB 级） |
| 探测面 | NAT 探测辅助端点（STUN 风格行为测试，§6.3） | M3 契约（M2 实现） | 极小 |

**铁律（沿用 D1 §3.3）**：中继只转发、不解密（端到端设备级加密在 D3 §5.1
已定义）；中继不做业务状态（无事件存储、无会话快照）；中继可选的辅助职责：
在线状态发布、推送适配（D7 路线 C 衔接）。

### 5.2 连接模型（双出站）

```
桌面端 ──(出站 wss)──► 中继 ◄──(出站 wss)── 移动端
        └────────── 同一连接上的双向帧流 ──────────┘
```

- 桌面与移动端**都是出站客户端**（规避桌面无公网 IP / NAT 的问题，
  D1 §3.1.2）；
- 两端连上后各自 `relay.hello`（携带 deviceId + desktopId + HMAC 签名，
  复用 D3 §5.1 信封），中继据此建立「设备对」路由映射；
- 消息格式：【裁决修正 2】**帧格式唯一真源 = M6 DeviceEnvelope**（WS 帧与
  轻量可靠 UDP 帧统一由 M6 §10 定义）；中继只解析自身控制帧头（M2 RelayFrame
  to/from 路由），**不读 D3/M6 信封的 kind/body**（AU1 P0-2 按 M2 §6.1 帧级
  透传裁决；本条原「中继读信封头（deviceId/kind）做路由」表述作废）；
- 在线状态：中继维护 `deviceId → {connId, lastSeen}`；某端断线通知对端
  （`link.peer-offline`），供移动端快速切换（不等心跳超时）。【裁决修正 2】
  `relay.*`/`link.*` 消息族中的**中继控制面**（hello/hello-ack/bye/
  peer-offline/backpressure）并入 M2 RelayFrame 控制帧枚举；`link.*` 打洞
  信令保持为**业务层消息**（经 data.frame 透传，中继只转发不解析）。

### 5.3 M2 服务端 API 契约（预留接口面）

```
WS 端点：  wss://<relay-host>/v1/ws              # 双端通用出站连接（信令 + 转发共用）
UDP 端点： udp://<relay-host>:<probe-port>       # NAT 探测辅助（§6.3.3，M3 定义协议）
REST 端点（可选，管理面）：
  GET /v1/health                                 # 健康检查（供客户端选址）
  GET /v1/servers?region=...                     # 区域端点列表（客户端测速选优，P2 增强）
```

**中继必须满足的契约约束（M3 侧硬要求）**：

| 编号 | 约束 | 理由 |
|------|------|------|
| R-RELAY-1 | 信令面延迟 p95 < 100ms（同区域），丢包 < 1% | 打洞协商超时预算（§6.4） |
| R-RELAY-2 | 转发面吞吐不低于 10Mbps/连接，单连接带宽配额可配置 | L2 兜底文件浏览 / 事件流场景 |
| R-RELAY-3 | 转发面支持帧级压缩透传（zstd，两端协商） | §8.4 压缩策略 |
| R-RELAY-4 | 信令面与转发面可分离（同进程两端口即可） | 打洞成功后信令与数据解耦 |
| R-RELAY-5 | 打洞指令（link.punch）只能由「已配对的在线设备对」请求，且带 TTL | §10.3 防滥用 |
| R-RELAY-6 | 探测端点协议由 M3 定义（§6.3.3），M2 必须按契约实现 | NAT 类型探测是本方案依赖 |
| R-RELAY-7 | 中继不落盘任何业务载荷（内存转发，重启清空路由表） | 隐私铁律（D1 §3.3） |
| R-RELAY-8 | 每设备断线重连窗口内路由表保留不少于 60s | 移动端后台切换场景防丢路由 |

### 5.4 客户端 RelayLink 行为（本方案定义）

```
RelayLink（客户端实现，桌面与移动端同构）：
  connect():   wss 连接 + relay.hello + 等待 relay.hello-ack
  send(msg):   DeviceEnvelope 原样入转发面（信封头带路由字段）
  onMessage:  转发面帧分发到协议层（LinkManager 上层）
  qualify():  周期性信令 ping/pong 测 RTT 与丢包（5s 周期，供 LinkManager 评分）
  close():    relay.bye + 断连
```

- 与 D2 §10.3 的 WS 心跳（30s ping / 90s 断连）区分：RelayLink 的 5s 快速
  探测是**质量采样**（供 LinkManager 评分），不替代协议层会话心跳（那是
  会话保活，负责游标续传触发）；
- 桌面侧 RelayLink 是**常驻热备**（不因 L1/L3 就绪而断开——L2 是保底通道，
  保持「立即可用」状态，成本仅一个空闲出站连接）；
- 移动侧 RelayLink 在 L1 活跃时也可保持连接（省去切换时的建连耗时）；
  若为省电可配置「L1 活跃时断开中继」，切换时先建连再切（多花 1~2s，
  可接受）——**默认保持连接**，原因：热备切换延迟是审批场景的关键指标。

### 5.5 L2 带宽控制（衔接 M2 的转发面要求）

L2 转发面的带宽控制策略在 §8.4 详述，此处仅声明 M2 必须支持的机制面：

1. **压缩协商**：连接建立时（relay.hello 扩展字段）协商 zstd 压缩级别
   （0=关闭 / 1=低延迟 / 3=默认）；帧级压缩，压缩失败自动降级原帧；
2. **配额**：每设备对（device-pair）可配置带宽上限（默认值见 §8.4）；
3. **背压透传**：接收端缓冲满时向发送端回 `link.backpressure`（中继透传），
   发送端按 D3 §9.4 背压语义降速（丢 Delta 保 Critical，复用
   `drop_class_of` 哲学，`crates/conex-types/src/events.rs:867-903`）。

## 6. L3 P2P 打洞方案（重点）

### 6.1 目标与边界

- **目标**：跨网时建立移动端与桌面端的 UDP 直连，数据 0 字节过中继；
  中继只做信令（交换候选、发打洞指令、转达验证结果）。
- **边界**：
  - 不做多媒体（无音视频），只传业务消息（JSON 事件/命令，单帧最大 1MiB，
    D3 §5.5）；
  - 不做 ICE 全家桶（无 Trickle 协商、无 srflx 候选的渐进发现——本方案用
    「探测 + 预测」两步获取候选，见 §6.3）；
  - 不做 TURN 等价物：打洞失败 = 回 L2 中继（中继本身就是 TURN 的角色，
    不需要再部署 TURN 服务）。
- **成功率预期（诚实边界）**：家庭宽带路由器（锥型 NAT 为主）成功率较高；
  运营商 CGNAT / 企业网（对称 NAT / 禁 UDP）会失败——回 L2 是产品行为。

### 6.2 候选方案详评

#### 6.2.1 候选一：WebRTC（ICE/STUN/TURN）

**原理**：两端经信令交换 SDP/ICE 候选；STUN 探测反射地址；候选直接连通
即 P2P；失败走 TURN 中继兜底。`RTCDataChannel` 承载业务消息（SCTP over
DTLS over UDP）。

**优点**：
- ICE 算法成熟（libwebrtc 大规模生产验证），全锥/受限锥/对称 NAT 均有
  处理路径（含 peer-reflexive 候选与端口预测探测）；
- STUN/TURN 是标准协议，生态完善（coturn 等）；
- DTLS 内建加密，安全链路成熟；
- 移动端有现成库：`react-native-webrtc`（Android/iOS 数据通道可用，
  经 Expo config-plugin + expo-dev-client 接入；当前捆绑 libwebrtc M124，
  Unified Plan only）——webfetch 查证事实（2026-08-09 抓取 GitHub README）。

**缺点（对本项目致命）**：
- **移动端依赖重**：react-native-webrtc 是重型原生模块（iOS 框架约
  50~80MB 编译产物、Android 各 ABI 的 .so 均显著增包），且 Expo Go 不可用，
  必须走 dev-client + prebuild（CNG）——与 D4 §3.2「依赖面刻意收窄、
  官方包优先」纪律冲突；RN 0.86 New Arch 默认开启，react-native-webrtc
  的新架构兼容性需逐个版本验证（D4 R2 风险直接命中）；
- **桌面侧更痛**：Rust 侧要么引入 `webrtc` crate（libwebrtc 级编译，
  构建时间与 CI 压力巨大，与仓库「依赖克制」哲学冲突），要么经 WebView
  桥接（引入浏览器栈，违背「引擎零改动」）；两条路都重；
- **鸿蒙生态缺失**：HarmonyOS NEXT 无 react-native-webrtc 对应物；
- **小帧开销高**：SCTP 数据通道每消息固定开销大（SCTP 头 + DTLS 记录头 +
  UDP 头，小 JSON 帧上常超过 60B/消息，且 SCTP 有自身流控与心跳），
  与 crish 事件流「几百字节的小 JSON 帧」场景不匹配；
- **服务器带宽目标不直接满足**：WebRTC 不部署 TURN 时打洞失败=连不上
  （WebRTC 标准里 relay 候选只能来自 TURN），而我们的 L2 中继本来就在——
  引入 WebRTC 等于重复建设中继兜底。

**结论**：方案 B（备选）。仅在「自研打洞实测达标率低于阈值」（§12.5）时
启动，且届时按「移动端 react-native-webrtc + 桌面 WebView 桥 + coturn」三件套
重新评估成本。

#### 6.2.2 候选二：自研 UDP 打洞（uu 远程模式）

**原理**：两端经中继信令交换各自的「反射地址 + 预测地址」；中继指令双方
同时向对方候选地址发送 UDP 探测包（顺序或并发打洞）；任一方向收到对方
探测包即打通 NAT 映射；随后双方以该地址对建立加密 UDP 流。

**优点（对本项目全部命中）**：
- **信令零新增**：复用 L2 中继的 WS 连接 + D3 DeviceEnvelope（加一个
  `link.*` 消息族），信令基础设施与 L2 完全共享；
- **桌面零新依赖**：tokio `UdpSocket` 即全部需要；NAT 探测/可靠传输/加密
  均为自有代码（壳内新模块，`#[path]` 独立编译测试先例）；
- **移动端可控**：只需一个薄原生 UDP socket 模块（自研 TurboModule，
  iOS 用 GCDAsyncUdpSocket 语义、Android 用 DatagramSocket——约 300~500
  行原生代码，§6.6），无重型第三方依赖；New Arch 兼容面自己掌控；
- **鸿蒙可行**：HarmonyOS NEXT 提供标准 UDP socket 能力，自研协议在
  鸿蒙上只需移植薄层，无生态依赖；
- **帧开销最小**：约 30~60B/帧（头 + AEAD tag），对 JSON 小帧友好；
- **服务器带宽目标直接达成**：打洞成功后中继零数据流量，且中继不需要
  单独的 TURN 服务。

**缺点**：
- **NAT 穿越算法要自己写**：NAT 类型探测、对称 NAT 端口预测、并发打洞
  时序，都属于「容易踩坑但模式成熟」的领域（RFC 3489/4787/5128 + 大量
  开源先例可参考）；
- **成功率上限低于 ICE+TURN**：对称 NAT 之间预测失败即回落中继——但
  回落路径是现成的（L2），损失只是带宽成本而非可用性。

**结论**：方案 A（采用）。理由：与现有栈的衔接成本最低、带宽目标直接、
鸿蒙兼容、桌面依赖零新增；打洞失败回 L2 无损可用性。

#### 6.2.3 候选三：QUIC（HTTP/3 传输）

**原理**：UDP 之上的可靠传输 + 内建 TLS 1.3（0-RTT）+ 连接迁移
（Connection ID 使 NAT 重绑定后连接不断，RFC 9000 §9）。打洞仍需自行实现
（QUIC 不含 ICE）。

**优点**：
- 传输层完成度高：可靠、多路复用、TLS 内建、连接迁移天然适配 NAT 重绑定
  与 Wi-Fi/蜂窝切换；
- 桌面侧 Rust 生态好：`quinn` 是成熟生产级实现；
- 0-RTT 重连对「切换」场景很友好。

**缺点**：
- **移动端无成熟 QUIC 栈**：RN 生态没有可用的 QUIC 原生桥（quic-go 是
  Go；chromium quic 在浏览器内不可控；自研 TurboModule 桥接 quiche 成本
  远超 UDP socket 薄层）；
- 打洞本身仍要自研（NAT 探测 + 信令 + 预测），QUIC 只解决「打洞成功后的
  传输」，收益面窄；
- 鸿蒙原生 QUIC 支持不明确。

**结论**：否决为主传输；列为**远期桌面-桌面**场景增强（第二桌面连接主桌面，
两端都是 Rust/quinn，可用 QUIC 替换可靠 UDP 层，接口面已在 §7.1 预留——
P2PLink 的传输层是内部实现，替换不动上层）。

### 6.3 NAT 类型探测（打洞前奏）

#### 6.3.1 为什么要探测

打洞策略依赖 NAT 行为类型：

| NAT 类型 | 映射行为 | 过滤行为 | 打洞策略 |
|----------|----------|----------|----------|
| 全锥型（Full Cone） | 任意 | 任意 | 被动打洞即可通 |
| 受限锥（Restricted Cone） | 任意 | 只收来自「本会话已发往的 IP」的包 | 主动发包即可通 |
| 端口受限锥（Port Restricted） | 任意 | 只收来自「已发往 IP:port」的包 | 需要精确端口，双方同时打洞 |
| 对称型（Symmetric） | 每个目标端口独立映射 | 通常同时受限 | 需端口预测 + 并发打洞 |

（分类依据 RFC 3489 行为测试与 RFC 4787/5128 的映射/过滤行为模型；
实现时按「映射行为」与「过滤行为」两个正交维度探测，不做旧式四分类
简化。）

#### 6.3.2 探测协议（M3 定义，M2 实现）

复用 STUN 语义的精简 UDP 协议（不引入 STUN 库，自实现 5 条消息）：

```
探测请求（客户端 → 中继探测端点，<probe-port> 固定端口）：
  magic:  'CXP1'        # 4 字节魔数（crish nat probe v1）
  type:   u8            # 1=映射探测 2=过滤探测 3=预测探测
  seq:    u32           # 客户端侧递增（匹配应答）
  nonce:  [u8;8]        # 随机（防伪造应答）
探测应答（中继 → 客户端，从不同源 IP:port 发出）：
  magic:  'CXP1'
  type:   u8            # 回显
  seq:    u32           # 回显
  src:    IPv4/IPv6 地址  # 中继应答包的源地址（供客户端识别来源）
  mapped: IPv4/IPv6 地址  # 客户端本次会话的公网映射地址（SRFLX）
```

**映射行为探测**（判断锥型 vs 对称）：

1. 客户端从同一 UDP socket 向中继的**两个不同端口**（probe-port 与
   probe-port+1）连续发映射探测（间隔 100ms）；
2. 中继应答各自回显 mapped 地址；
3. 若两个 mapped 相同（同一 IP:port）→ 映射行为「地址无关」（锥型）；
   若不同 → 继续预测探测（§6.3.4）判断对称。

**过滤行为探测**（判断是否受限锥）：

1. 客户端先向中继端口 A 发映射探测（建立映射）；
2. 中继从**另一个端口 B** 向客户端的 mapped 地址发过滤探测包（该包不响应
   客户端的请求，是主动入包）；
3. 客户端收到 B 的包 → 过滤行为宽松（全锥/地址无关）；收不到（2s 超时）
   → 受限型。精确区分「IP 受限」与「IP:port 受限」需第三跳测试，实现时
   简化：只区分「宽松」与「受限」两级（受限时一律按端口受限锥处理，
   打洞策略取最保守——保证不误判）。

#### 6.3.3 探测端点要求（M2 契约 R-RELAY-6 细化）

- 中继暴露至少 1 个 UDP 探测端口（建议 2 个：probe-port 与 probe-port+1，
  同 IP 双端口即可满足映射行为探测）；若中继有多个公网 IP，多 IP 应答
  可提升过滤行为探测精度（可选增强）；
- 探测端点**无鉴权**（探测包无业务敏感性，防滥用靠频率限制：单源 IP
  每分钟 60 包）；应答只含 mapped 地址与回显字段，不泄露其他客户端信息；
- 探测端点与转发面隔离（转发面不受探测洪峰影响）。

#### 6.3.4 端口预测（对称 NAT 的关键技术）

对称 NAT 对每个目标地址分配独立映射端口，但许多商用设备（含部分运营商
CGNAT）的端口分配是**连续递增**的。预测流程：

1. 客户端连续向中继探测端点发 3 次映射探测（间隔 200ms），记录
   mapped 端口序列 `p1, p2, p3`；
2. 计算增量 `d1 = p2 - p1`、`d2 = p3 - p2`（取模 65536）；
3. 若 `d1 == d2` 且 `d1 > 0` → 线性分配，预测下一次端口
   `p_pred = p3 + d1`；
4. 若 `d1 != d2` → 随机分配，放弃预测（该 NAT 打洞仅靠并发探测碰运气，
   成功率低，直接判「预测不可用」）；
5. 预测结果作为「预测候选地址」随信令交换（§6.5）。

**预测的用途**：打洞时向「目标地址的预测端口」发探测包——目标 NAT 为
线性分配时，发出的包正好命中新映射端口，实现穿透。预测候选是**附加候选**
（与反射地址候选并行使用），命中失败不影响其他候选。

### 6.4 打洞信令（`link.*` 消息族）

在 D3 消息 kind 命名空间新增（D3 §5.3 kind 列表扩展；实现落位
`crates/conex-types/src/device/` 新模块，D3 §12.2 已规定新增类型放
conex-types 不建新 crate）：

| kind | 方向 | 载荷 | 说明 |
|------|------|------|------|
| `link.offer` | 移动 → 桌面（经中继） | deviceId, natType, 候选集（本地地址 / 反射地址 / 预测地址）, punchToken | 移动端发起打洞 |
| `link.answer` | 桌面 → 移动 | 桌面候选集, natType | 桌面侧同意打洞 |
| `link.punch` | 中继 → 双端 | 对端候选集, 指令（并发/顺序）, TTL | 中继命令双方同时开打 |
| `link.punch-ack` | 双端 → 中继 | 已开打, 打洞用源端口 | 中继转告对端「已开打」 |
| `link.probe` | 双端 → 中继 | 探测结果（可选信令通道重发探测） | 探测结果交换 |
| `link.verify` | 双端互相 | 挑战/应答（AEAD 密钥确认） | 打洞成功后的密钥验证（§10.1） |
| `link.connected` | 桌面 → 移动 | 确认直连建立 | 移动端切流量到 L3 |
| `link.fallback` | 任一 → 对端 | 原因（timeout / nat-impossible / firewall） | 打洞失败通知，回 L2 |
| `link.renegotiate` | 任一 → 对端 | 原因 | 链路劣化时请求重新打洞 |
| `link.peer-offline` | 中继 → 对端 | deviceId | 在线状态变化（§5.2） |

**时序预算**（信令面 R-RELAY-1 支撑）：

```
移动端发起 → offer（中继延迟 1×RTT）→ answer（2×RTT）→ punch（3×RTT）
→ 双方打洞（并发，1~2s 内完成）→ verify（4×RTT）→ connected（5×RTT）
典型耗时（RTT=50ms）：打洞协商约 0.5s，打洞本身 0.5~2s，总 2~3s 完成转正。
```

超时预算：整个打洞会话 TTL 10s（link.punch 的 TTL 60s 是安全上限，
实际打洞窗口 3s）；超时即 `link.fallback`。

### 6.5 打洞流程状态机

```
                    ┌──────────┐
                    │   Idle   │  （无 L3 需求）
                    └────┬─────┘
                         │ LinkManager 决策「跨网需 L3」
                         ▼
                 ┌──────────────┐   NAT 探测失败（中继不可达等）
                 │   Signaling  │ ──────────────────────────────► ┌──────────┐
                 │  offer/answer │                                 │ Fallback │──► 回 L2
                 └──────┬───────┘                                 └──────────┘
                        │ 双方候选集就绪
                        ▼
                 ┌──────────────┐  双端候选集为空（无反射/预测地址）
                 │   Punching   │ ───────────────────────────────►  Fallback
                 │  并发/顺序打洞│  打洞窗口 3s 无任何方向收到探测包
                 └──────┬───────┘                                   │
                        │ 收到对端探测包（至少一个方向）              │
                        ▼                                           │
                 ┌──────────────┐   verify 失败（密钥不匹配/身份不符） │
                 │  Verifying   │ ────────────────────────────────►  Fallback
                 │ AEAD 挑战应答 │
                 └──────┬───────┘
                        │ 双向密钥验证通过（双方各自持有 k_ab / k_ba）
                        ▼
                 ┌──────────────┐  链路质量差（RTT 采样不合格）──────►  Fallback
                 │  Connected   │  NAT 映射失效（保活超时 4×25s）────►  Reattempt
                 └──────┬───────┘  连续 2 次丢包超阈 ────────────────►  Fallback
                        │
                        │（长期持有；LinkManager 判定需要时）
                        ▼
                 ┌──────────────┐
                 │  Reattempt   │──► 冷却 30s 后回到 Signaling（保留上次 NAT 探测缓存）
                 └──────────────┘
```

**状态迁移细则**：

1. **Signaling**：移动端发起 `link.offer`（携带自己的 NAT 探测结果与候选
   集）；桌面回 `link.answer`；若桌面 NAT 探测缓存新鲜（5 分钟内）可跳过
   探测直接答（移动端通常已探测，桌面冷启动首连需探测一次并缓存）；
2. **Punching**：中继发 `link.punch` 给双方（TTL 60s）；双方同时向对方
   「反射地址 + 预测地址」全组合发 UDP 探测包（每个候选组合发 5 包，
   间隔 100ms，窗口 3s）；
   - **顺序打洞**：若一方 NAT 为「宽松过滤」（全锥/受限锥），先收包方
     应答即通——无需并发；
   - **并发打洞**：双方对称/端口受限时，同一 500ms 窗口内互相发包，
     增大「映射建立 + 过滤放行」同时成立的命中率；
3. **Verifying**：收到对端探测包后，双方各自建立 UDP 会话并立刻跑
   AEAD 挑战应答（§10.1）——确认「我在跟配对过的设备直连」，防
   打洞打歪到第三方（见 §10.3 放大器防护）；
4. **Connected**：verify 通过 → `link.connected` → 移动端把业务流量切到
   P2PLink（make-before-break 语义，§7.4）；桌面侧登记新链路到连接族；
5. **Reattempt**：回退冷却 30s（可配），避免打洞风暴；缓存 NAT 探测结果
   5 分钟，重试不重复探测。

### 6.6 可靠 UDP 传输层（P2PLink 内部实现）

#### 6.6.1 选型：自研轻量可靠传输（借鉴 KCP 语义，不引入 KCP 依赖）

- **为什么不自研类 TCP 全量重传**：crish 业务是「消息流」不是「字节流」
  （一帧一 JSON），需要的是「消息级可靠 + 有限乱序重排」，不需要字节流
  粘包处理；
- **为什么不用现成 KCP**：KCP 是协议规范，Rust/JS 各有一堆实现，维护活跃
  度参差；协议面与 D3 信封有对齐成本；自研约 400 行核心逻辑即可覆盖
  需求（重传 + 乱序窗口 + 保活），且能精确对接 AEAD 加密与帧格式
  （§9.2）——符合仓库「依赖克制 + 自研可控」纪律；
- **参数以「小 JSON 帧 + 低频事件流」为基准**，不做大吞吐优化（文件浏览
  等大载荷走 D3 §9 流协议分块，传输层不变）。

#### 6.6.2 帧格式（P2PLink 专用，与 §9.2 的 LinkFrame 分层）

```
偏移  长度  字段        说明
0     2    magic       0x4358 ('CX')
2     1    ver         0x01
3     1    flags       bit0=ACK, bit1=SYN, bit2=FIN, bit3=HEARTBEAT
4     4    seq         发送序号（单调递增）
8     4    ack         累计确认（收到 seq）
12    2    len         payload 长度（加密前明文长度）
14    N    payload     应用消息（DeviceEnvelope JSON 字节）
14+N  16   tag         AES-256-GCM 认证标签
```

- 每帧单独加密：`ciphertext = AES-256-GCM(key_xy, nonce=IV计数器, AAD=头 14 字节)`
  ——头字段不加密（路由需要），AAD 绑定头防止头部篡改；
- 无 ACK 累积回传（收到 seq 单调推进）；ACK 帧只含 ack 字段；
- **重传**：发送侧 128 窗口；RTO 初始 300ms，指数退避至 2.4s 封顶；
  快速重传（收到 3 次重复 ack 立即重发）；
- **乱序重排**：接收侧 256 槽窗口按 seq 重组，顺序交付上层（保证与
  WS 路径一致的「帧到达有序」语义——D2 §10.2 已规定事件帧按到达序）；
- **保活**：25s 心跳（NAT 映射典型超时 30~60s，取 25s 留裕量）；4 次
  心跳无响应判定链路失效（→ Fallback）；
- **分片**：payload > 1024 字节时分片（每片 1024B，独立加密），对端重组；
  与 D3 §9 流协议的分块语义对齐（大载荷本来就该走流协议，传输层分片
  只是兜底）。

#### 6.6.3 拥塞与背压（轻量版）

- 业务低频（事件流 + 命令，远低于 LAN 吞吐），不做复杂拥塞控制；
  仅做：发送队列长度阈值（默认 1024 帧）超限 → 丢弃 Delta 类帧（复用
  `drop_class_of` 语义，`crates/conex-types/src/events.rs:867-903`），
  Critical 必达——与 D2 §10.4 连接级缓冲哲学一致；
- 对端回 `link.backpressure`（经中继信令通道）时降速 50% 重试。

### 6.7 失败场景与回落（打洞失败矩阵）

| 场景 | 现象 | 判定 | 动作 |
|------|------|------|------|
| 对称 NAT - 对称 NAT 且预测失败 | 打洞窗口无双向命中 | Punching 3s 超时 | Fallback → L2 |
| 企业网防火墙禁 UDP | 探测包无应答（连中继探测端点都不通） | Signaling 阶段探测失败 | Fallback → L2（并标记「本网络禁 L3」，24h 内不重试） |
| 运营商 CGNAT 对称分配 | 预测端口命中失败 | Punching 超时 | Fallback → L2；30s 冷却后允许重试（CGNAT 可能因会话数变化改变行为） |
| 打洞成功但质量差 | Connected 后 RTT > 500ms 或丢包 > 10% | 3 次采样不合格 | Fallback → L2（L3 标记「低质」，2h 内优先走 L2） |
| 中途 NAT 映射失效 | 保活心跳 4 次无响应 | Connected 超时 | Fallback → L2（热备秒级恢复）；30s 后 Reattempt |
| IPv6 直连可用 | 双端有公网 IPv6 | （特殊：IPv6 无 NAT，直接连通） | 若双端均有全局 IPv6，跳过打洞直接建连（候选集含 IPv6 地址） |

**特殊通道：IPv6**——双端均有全局 IPv6 地址时，无需打洞（IPv6 设计上
无 NAT，运营商移动网络 IPv6 覆盖率近年显著提升）；P2PLink 候选集
包含 IPv6 地址，`link.offer` 时若双方都有全局 IPv6，直接进入 Verifying
（省去打洞窗口）。

### 6.8 桌面侧 P2P 的实现约束（安全与绑定）

- 桌面 P2P 出站 UDP socket：绑定 `0.0.0.0:0`（随机端口），**只向对端
  候选地址 sendto**，收到的包只处理「来源 = 已验证对端地址」的帧；
- 桌面 **不做入站 UDP 监听服务**：打洞探测包是「对端主动发来的包」，
  收到后应答同样发往该地址——没有新增监听面，防火墙/NAT 无需开端口
  （与 D2 §12.1「绑定面最小化」精神一致）；
- 打洞期间桌面不处理来自未知地址的任何包（先验地址 = 中继信令交换的
  候选，后验地址 = 打洞窗口内收到探测包的来源地址——后者仅在「该来源
  地址出现在对端候选集或对端 punch-ack 声明的端口」时才应答，防反射放大）。

### 6.9 移动端实现（自研薄 UDP 原生模块）

#### 6.9.1 选型：自研 TurboModule vs react-native-udp

| 维度 | 自研薄模块（推荐） | react-native-udp（现成库） |
|------|--------------------|---------------------------|
| 维护状态 | 自己掌控 | 社区库更新节奏慢，New Arch 适配需验证（D4 R2 纪律） |
| 依赖面 | 零新增（壳内原生代码） | 新增一个三方原生模块 |
| 能力需求 | 只需要 bind/sendTo/recv/close 四能力 | 库提供更多但本项目用不到 |
| 鸿蒙 | 同一 API 面可移植到 HarmonyOS | 鸿蒙无对应物 |
| 成本 | 约 300~500 行原生 + 100 行 TS 桥 | 集成 + 适配 + 风险排查，未必更省 |

**裁决：自研薄 TurboModule**（项目内 `crish-mobile/native-modules/udp-socket`），
能力面刻意最小化：

```
TS API（P2PLink 专用，不暴露给业务层）：
  createSocket(): Promise<SocketHandle>
  bind(handle, port: 0)                       // 随机本地端口
  sendTo(handle, data: ArrayBuffer, host, port)
  onMessage(handle, cb: (data, fromIp, fromPort) => void)
  close(handle)
```

- iOS 实现：GCDAsyncUdpSocket 语义（或直接 POSIX socket，轮询收包线程
  → 事件回调到 JS 线程）；
- Android 实现：java.net.DatagramSocket + 收包线程；
- New Arch：按 Expo SDK 57 / RN 0.86 的 TurboModule 规范实现（D4 R2
  「新增三方库需过新架构兼容检查」——自研模块走同样的 expo-doctor +
  真机冒烟门禁）。

#### 6.9.2 鸿蒙支持路径（远期）

- HarmonyOS NEXT 提供标准 UDP socket 能力（`@ohos.net.socket` 的
  UDPSocket）；
- 本方案的自研协议（探测 / 打洞 / 帧格式 / 密钥派生）全部是平台无关
  逻辑，鸿蒙侧只需实现 §6.9.1 的 4 能力薄层（或复用同类桥）；
- 若鸿蒙以「Web 组件内 WebView」形态接入，则 UDP 不可用——届时鸿蒙端
  只能走 L1/L2（直连/中继），L3 不作为鸿蒙承诺项；
- **裁决**：L3 协议设计保持平台无关（§6.2.2 方案 A 的鸿蒙优势即在此）；
  鸿蒙原生端落地前不承诺 L3 支持，但架构不堵死。

### 6.10 打洞效果与带宽（预告，量化见 §8）

- 打洞成功：事件/命令数据走 UDP 直连，中继仅剩信令心跳（每小时约几十 KB）；
- 打洞失败：回落 L2，中继全量转发（有压缩与配额，§8.4）；
- 目标：**P2P 成功率在家庭网络不低于 70%，移动网络不低于 50%**（§12 验收）。

## 7. 路径选择与切换（连接管理器）

### 7.1 Link 抽象（统一接口）

D1 §3.7 已声明 `Link` 抽象，本方案给出正式接口（Rust 侧壳内模块
`server/link/mod.rs`；移动端 TS 侧 `services/links/types.ts` 镜像）：

```rust
/// 链路抽象：三种实现 LocalLink / RelayLink / P2PLink
pub trait Link: Send + Sync {
    /// 链路类型（用于状态展示与统计）
    fn kind(&self) -> LinkKind;                 // Local | Relay | P2P
    /// 建立连接（异步；Local 为服务端 accept 语义的封装）
    async fn connect(&self) -> Result<(), LinkError>;
    /// 发送一条消息（DeviceEnvelope 序列化字节；链路层负责分帧/加密）
    async fn send(&self, bytes: Bytes) -> Result<(), LinkError>;
    /// 订阅收到的消息（mpsc 流）
    fn incoming(&self) -> mpsc::Receiver<Bytes>;
    /// 质量采样：RTT / 丢包率 / 可用性（供 LinkManager 评分）
    fn metrics(&self) -> LinkMetrics;
    /// 关闭（幂等）
    async fn close(&self) -> Result<(), LinkError>;
}

pub struct LinkMetrics {
    pub rtt_ms: Option<u32>,        // 最近一次采样（5s 周期）
    pub loss_pct: f32,              // 滑动窗口丢包率
    pub last_ok_at: Option<Instant>,// 最后一次成功收发
    pub cost_class: CostClass,      // Direct(0) / Tailscale(1) / Relay(2) / P2P(0)
}
```

**三实现要点**：

| 实现 | 形态 | 承载 | 加密 | 备注 |
|------|------|------|------|------|
| LocalLink | 客户端（移动）/ 服务端（桌面） | TLS WebSocket（D2 §10） | TLS + 指纹钉扎 | 桌面侧为 accept 封装 |
| RelayLink | 双端客户端 | wss 出站（§5.4） | TLS + 设备级 HMAC（D3 §5.1） | 常驻热备 |
| P2PLink | 双端客户端 | 自研可靠 UDP（§6.6） | AEAD（§10.1） | 仅跨网时启用 |

### 7.2 LinkManager 状态机（候选集 + 选路）

```
候选集构造（每端）：
  - LocalLink 候选：历史成功端点（二维码 h 列表 / mDNS 缓存 / 手动输入）
  - RelayLink 候选：中继地址（配置持久化）
  - P2PLink 候选：懒创建（仅在需要时发起打洞流程）

决策循环（每 5s 评估 + 事件驱动评估）：
  1. 可达性分层：同网判定（见下）→ L1 优先
  2. 质量评分：score = w1*rtt_norm + w2*loss_norm + w3*cost（权重表）
  3. 滞回判定：仅当 新分 - 旧分 > 阈值 且 冷却期已过 才切换
  4. 切换执行：make-before-break（§7.4）
```

**同网判定**（不依赖 SSID，纯网络事实）：

1. 手机当前 IP 与 LocalLink 候选 IP 同网段（掩码 255.255.0.0 起逐级放大
   匹配，最多试 /8）——保守策略：`/16` 内视为同网；
2. 同网 → 直接尝试 L1（TLS WS 连接 3s 超时）；
3. 不同网 / 失败 → 跨网路径（L3 → L2）。

**评分权重（初始值，实施期标定）**：

| 指标 | 权重 | 归一化 |
|------|------|--------|
| RTT（5s 采样中位数） | 0.4 | 0~500ms 线性映射 1.0~0.0 |
| 丢包率 | 0.3 | 0~10% 线性映射 1.0~0.0 |
| 成本等级 | 0.3 | Direct=1.0 / P2P=0.9 / Tailscale=0.7 / Relay=0.5 |

成本等级给「直连/打洞」溢价（带宽目标驱动），但**不超过**「连通性」——
链路不可达时分数直接为 0，任何可达链路都优先于不可达链路。

### 7.3 切换判定（触发条件全表）

| 触发源 | 条件 | 动作 |
|--------|------|------|
| 周期评估 | 分数差 > 0.15（滞回阈值） | 执行切换 |
| netinfo 事件（移动端） | 网络类型变化 / 失联 / 恢复 | 立即重评（不等 5s 周期） |
| 链路失效 | metrics.last_ok_at 超时（L1/L2 90s、L3 心跳 4×25s） | 立即降级候选（分数置 0）并重评 |
| 打洞转正 | P2PLink verify 通过 + 3 次 RTT 采样合格 | 直接提升（不等待周期评估） |
| 冷却期 | 切换后 60s | 期间禁反向切换（防乒乓）；正向切换（劣化方向）不受冷却限制 |
| 链路失败计数 | 同一链路连续 2 次失败 | 该链路降级 5 分钟（进「惩罚名单」），期间分数打 6 折 |

### 7.4 make-before-break 切换协议

```
移动端                                    桌面端
  │ 评估：切 L1 → L3                       │
  │ 1. 建立新链路（P2PLink Connected）     │
  │ 2. 新链路 hello + subscribe            │──► 桌面按连接族识别同设备（§7.5.4）
  │    （携带逐会话游标 resume）             │──► 重放补齐 + catchup
  │ 3. 新链路 catchup 完成（协议层就绪）     │
  │ 4. 切换流量出口到新链路                  │
  │ 5. 旧链路保持 5s（收尾帧转发）后关闭      │
  │    （若 5s 内新链路异常 → 回退旧链路）    │
```

- **切换点判定**：`catchup`（D2 §10.3）收到即「协议层就绪」——注意
  catchup 是「该会话重放完成锚点」，多会话订阅时取全部订阅会话 catchup；
- 切换失败回退：新链路就绪前旧链路故障 → 走「立即断连重连」路径
  （旧链路直接重连或换下一候选），不阻塞业务（游标续传兜底）；
- 桌面侧对「同设备新链路」的识别与连接族上限见 §7.5.4。

### 7.5 会话连续性（衔接 D3/D6 游标续传）

**核心结论：链路切换不需要传输层连续性——协议层的游标续传是唯一兜底。**

1. **事件流**：切换后移动端在新链路重新 `subscribe`，携带每个会话的
   `last_sequence` 游标（D2 §10.3 / D3 §7.5 / D6 §4 逐会话游标）；
   桌面按游标重放补齐（`query_events(after=last_sequence)`，
   `crates/conex-db/src/events.rs:33-68`）；Delta 类未落库事件由
   `message-end` 全文兜底（D2 §10.3 已有裁决）；
2. **命令**：切换窗口内的请求-响应靠 D3 §5.4 幂等重发兜底（msgId 不变
   重发，桌面按 reqMsgId 去重回显缓存结果）；移动端 outbox 队列（D6 §6.2）
   在重连后按序发送；
3. **审批**：approval-requested 事件若在切换窗口丢失，由重放补齐（审批
   事件落库，D3 §7.2 已确认）；approval-decision 是命令（幂等键），
   重发安全；
4. **顺序保证**：重放批次按 sequence 升序，实时帧按到达序（D2 §10.2），
   与链路无关——**上层观察不到切换**（除非重放耗时 > 1s，移动端 UI 显示
   「同步中…」角标，D6 §8.5 已定义该弱一致 UI 语义）。

#### 7.5.4 连接族（多链路共存与桌面侧上限）

- D2 §10.5 规定「每令牌最多 2 条并发连接；全局上限 8」——make-before-break
  窗口内同一设备需要短时共存 2 条链路，**连接上限语义升级为「连接族」**：
  同一 `deviceId` 的 N 条链路（不同 kind）属一族，族内上限 3 条（旧链 +
  新链 + 缓冲），族外（不同 deviceId）总数上限仍 8；【裁决修正 3】本段即
  **连接模型唯一真源**（每设备一主连接 + 会话级多流）：M2 §4.6 与 D2 §10.5
  已按此语义回写（同 kind 重复连接踢旧、不同 kind 同设备共存 ≤3）；
- 桌面侧按「hello 中的 deviceId + deviceLinkId（本方案新增的链路实例
  标识）」识别连接族；族内新链路就绪后，旧链路由移动端主动关闭（5s
  收尾），桌面侧惰性清理（30s 无帧回收）；
- 打洞场景的桌面侧 L3 会话与 L2 中继会话是**两个独立连接**（不同出口），
  都属于同一连接族。

### 7.6 切换场景演练（时序表）

| 场景 | 起始 | 动作序列 | 用户感知 |
|------|------|----------|----------|
| 回家进 WiFi | L2 | netinfo 触发 → 同网判定 → L1 建连 3s 内 → 切换 → L2 保活 | 无感知（审批延迟从 ~200ms 降到 ~5ms） |
| 出门断 WiFi | L1 | L1 探测超时（30s 内判定）→ L3 尝试（2~3s）失败/成功 → L2 兜底 | 若 L3 成功：无感知；失败：1~3s 内事件恢复（游标补齐） |
| 桌面睡眠唤醒 | L1→L2 | 移动端 L1 失联 → 中继热备立即接管（L2 一直在线） | 桌面唤醒后自动 Reattempt L1/L3 并切回 |
| 中继宕机 | L3 活跃 | L3 不受影响（数据直连）；信令通道断 → 打洞维持（保活独立）→ 中继恢复后信令重连 | 无感知（仅「云连接」状态短暂变灰） |
| 打洞失败首连 | L2 | 协商 10s 超时 → fallback → L2 建立 | 首次连接多 10s（可接受；后续有探测缓存） |

## 8. 带宽与成本量化

### 8.1 流量模型（三类流量）

| 流量类别 | 频率 | 单条典型字节 | 来源 |
|----------|------|--------------|------|
| 事件推送 | 高频（run 进行中秒级） | 0.2~5 KB/条（JSON 信封） | 引擎广播（D2 §10.4） |
| 命令/审批 | 低频（秒~分钟级） | 0.1~1 KB/条 | 移动端 → 桌面（D3 §8） |
| 信令/心跳 | 固定周期 | 50~200 B/条 | link.* / 心跳（本方案） |
| 文件浏览（P2） | 按需 | 10~100 KB/次 | stream.* 分块（D3 §9） |

### 8.2 P2P 成功时服务器带宽约等于 0 的量化

以「run 进行中 + 移动端在线审批」为典型负载（事件流 20 条/分钟 × 1KB、
命令 2 条/分钟 × 0.5KB、文件浏览 1 次/小时 × 50KB）：

| 路径 | 服务器月流量（8 小时/天活跃） | 占比 |
|------|------------------------------|------|
| L2 中继全量（无 L3） | 事件 20×60×8×30 ≈ 288MB + 命令 ≈ 14MB + 文件 ≈ 120MB ≈ **422MB/月/设备对** | 100% |
| L3 打洞成功（信令仅此） | 打洞协商 ≈ 10KB/会话 + 探测 ≈ 2KB/次 + 保活信令 ≈ 8KB/小时 ≈ **2MB/月/设备对** | **约 0.5%** |
| L1 局域网（中继仅热备） | 中继连接保活（心跳 2 条/分 × 100B × 8×60×30 ≈ 2.9MB）+ 断线重连信号 | 约 0.7% |

**结论**：L3 转正后，服务器带宽相对 L2 全量路径**下降 99.5%**；即「P2P 成功
时服务器带宽约等于 0」的量化口径 = 服务器只承担 KB 级信令，不承担业务
字节。1000 个活跃设备对（L3 成功率 60% 时）服务器月流量约
400×2MB + 600×422MB ≈ 255GB——其中 98.4% 来自打洞失败的 L2 兜底，
**提升 L3 成功率是成本优化的第一杠杆**（§12.5 风险表呼应）。

### 8.3 服务器成本模型（供 M2 立项参考）

| 规模 | 并发连接 | 中继带宽（峰值） | 机型参考 |
|------|----------|------------------|----------|
| 家庭/小团队（10 设备对） | ≤ 20 | L2 峰值约 2Mbps | 2C4G 轻量云 |
| 个人规模化（100 设备对） | ≤ 200 | 约 20Mbps | 4C8G + 按量带宽 |
| 商用（1000 设备对） | ≤ 2000 | 约 200Mbps | 多节点 + 区域化（R-RELAY-1 需同区域） |

- 带宽成本按「L2 兜底占比」线性增长 → §8.4 的压缩/限流是成本护栏；
- L3 信令面几乎免费（KB 级），**无需按流量计费的信令通道**——信令与
  转发共用一个连接即可（R-RELAY-4 允许分离，但不强制）。

### 8.4 L2 兜底时的压缩与限流（衔接 M2）

**压缩（zstd，帧级）**：

1. 协商：relay.hello 扩展字段 `compress: {algo: "zstd", level: 3}`；
2. 阈值：帧 JSON 长度 ≥ 512B 才尝试压缩（小帧压缩率差且浪费 CPU）；
3. 兜底：压缩后不小于原文 90% → 发原文（标记未压缩，防膨胀）；
4. 实测参考：事件信封 JSON（含 message 全文）zstd level 3 压缩率
   约 5~10 倍（JSON 重复字段多）；实施期在真机数据上校准。

**限流（设备对配额）**：

| 方向 | 默认配额 | 超出行为 |
|------|----------|----------|
| 桌面 → 移动（事件） | 256 KB/s（可配） | 丢 Delta 保 Critical（drop_class_of）；移动端标记「降级」 |
| 移动 → 桌面（命令） | 32 KB/s（可配） | 队列 + 背压（命令低频，通常用不满） |
| 文件浏览 | 512 KB/s（可配） | stream.* 流控（D3 §9.4） |

**裁剪（应用层，D6 已定）**：事件白名单（D6 §7.3）+ 敏感字段重写
（D6 §7.4）在链路层之上生效，与压缩叠加——**顺序：裁剪 → 序列化 →
压缩 → 分帧**。

## 9. 与协议层的衔接（连接层与消息层分离）

### 9.1 分层不变式

```
┌────────────────────────────────────────────────┐
│ L5 业务面（events/cmd/approval/...）            │  与链路无关（D3 原样）
├────────────────────────────────────────────────┤
│ L4 会话面（subscribe/resume/ack/heartbeat）      │  与链路无关（D2 §10 语义）
├────────────────────────────────────────────────┤
│ L3 信封 DeviceEnvelope（v/kind/msgId/ts/auth/   │  body 原样；auth 签名不变
│     body）                                      │  ← 跨链路同一信封
├────────────────────────────────────────────────┤
│ L2 链路层 LinkFrame（本方案新增）                │  ← 每个 Link 实现自己的分帧
│    LocalLink: WS 文本帧（信封 JSON 一帧一消息）    │  （D2 §10.2 现状）
│    RelayLink: WS 二进制帧（信封 JSON + 压缩标记）  │
│    P2PLink:  可靠 UDP 帧（§6.6.2，信封 JSON 加密） │
├────────────────────────────────────────────────┤
│ L1 传输（TLS WS / wss / UDP）                   │
└────────────────────────────────────────────────┘
```

**不变式一：信封字节不变**。任何链路上传输的都是同一个
`DeviceEnvelope` 的序列化字节（D3 §5.3 规范）；链路的差异只体现在
「外层的分帧/加密/压缩」。

**不变式二：auth 签名不因链路而变**。D3 §5.1 的 HMAC 签名覆盖
`canon(header) ∥ body`，与传输方式无关——同一信封在 L1/L2/L3 上签名
一致，接收端校验逻辑零改动。

**不变式三：消息顺序语义一致**。三条链路都向上层交付「有序帧流」
（WS 天然有序；P2PLink 靠乱序重排窗口保证）——上层不需要感知链路差异。

### 9.2 LinkFrame（链路层帧格式）

三实现共用头部语义（方便调试与统一背压逻辑），只是承载不同：

```
LinkFrame（统一逻辑帧）：
  magic    0x434C ('CL')
  version  u8 = 1
  flags    u8    bit0=compressed(zstd)  bit1=last-fragment
  kind     u8    0=信封JSON 1=流分块 2=链路控制(心跳/backpressure)
  len      u16   payload 长度（≤ 4095；超限走分块）
  payload  ...   （信封 JSON 字节 / 流块 / 控制消息）
  frameId  u32   （发送方递增，用于 P2PLink 可靠层；WS 上恒 0）
```

- LocalLink：不需要 frameId/压缩位（WS 自带帧边界），但**统一封装**便于
  三实现共享「帧 → 信封」解码器（解码器是纯函数，入快层单测）；
- RelayLink：启用 zstd 位 + 信封 JSON payload；
- P2PLink：加密在 LinkFrame 之下（§6.6.2 帧格式），LinkFrame 的 payload
  是密文的明文形态——**同一解码器对 P2PLink 先解密再解 LinkFrame**。

### 9.3 帧大小与分块（对齐 D3 §5.5）

- 单帧 ≤ 1 MiB（D3 §5.5 `MAX_FRAME_BYTES`）不变；
- LinkFrame 的 `len` 上限 4095 只是分帧粒度（LinkFrame 本身可多帧拼接
  成一条信封）——具体实现取「信封 JSON ≤ 4KB 单帧，超限按
  kind=流分块 拆分」，与 D3 §9 流协议的分块语义一致；
- 接收端超限拒绝 + 断链（`frame_too_large`，D3 §6.2）语义不变。

### 9.4 新消息族注册（协议变更登记）

- 新增 kind：`relay.*`（relay.hello / hello-ack / bye / peer-offline /
  backpressure）与 `link.*`（§6.4 全表）；
- 版本化：跟随 D3 §10 协议版本协商（hello 里 `protocolVersions` 声明
  支持 `link` 消息族的最小版本）；旧端收到未知 kind → `error.unknown_kind`
  （D3 §6.2 扩展，登记进错误码表）；
- 登记文档：按 D3 §13.3 建议，首次发布时登记进
  `docs/multi-device/plans/33-device-schema-changelog.md`。

## 10. 安全设计

### 10.1 P2P 直连加密（不因直连降级）

**密钥唯一来源：配对 master**（D3 §4.4 派生链）。链路密钥派生：

```
k_link = HKDF-SHA256(
    ikm   = master,
    salt  = "conex-link-v1" ∥ desktopId ∥ deviceId,
    info  = "conex-link", L = 96)
   ├─ k_ab  = k_link[0..32]   （A=桌面 → B=移动 方向密钥）
   ├─ k_ba  = k_link[32..64]  （B → A 方向密钥）
   └─ iv0   = k_link[64..80]  （双方各自 AAD 计数初始化的种子）
```

- **每方向独立密钥 + 独立计数器 nonce**（AES-256-GCM 计数模式），
  方向互不重放（反向密钥不同，重放的帧验签必败）；
- **防重放**：接收侧 seq 滑动窗口（§6.6.2），窗口外帧丢弃；
- **身份确认（Verifying 阶段）**：双方各发随机挑战，应答 =
  `HMAC(k_link, "verify" ∥ 挑战 ∥ 对端deviceId)`——确认「持同 master 的
  配对设备」；挑战应答失败立即丢弃会话并 Fallback；
- **加密范围**：整个业务载荷（信封 JSON 序列化字节）；帧头明文仅含
  路由/序号字段（§6.6.2 表格）——与中继路径「TLS + 设备级签名」相比，
  P2P 路径是「AEAD + 防重放」，**机密性强度持平、完整性更强**（AEAD 认证
  标签）——安全不降级目标达成；
- **无证书依赖**：不使用 DTLS（库生态不成熟，Windows schannel DTLS 与
  RN 侧均无成熟实现——§6.2.3 已论证），密钥来自配对信道，等价于
  「PSK 式 DTLS 的加密语义」由应用层实现。

### 10.2 打洞信令的防滥用

| 威胁 | 防护 |
|------|------|
| 未配对设备利用中继打洞 | `link.offer` 必须携带合法 HMAC 签名（token_key，D3 §5.1）；中继只对「签名校验通过且在线的设备对」转发打洞指令（R-RELAY-5） |
| 打洞风暴（恶意高频 offer） | punch-ticket：中继对每次打洞会话签发 60s TTL 令牌（`offer` 附带 ticket，`punch` 必须回显）；每设备对每 10 分钟最多 3 次打洞尝试（超限 → `link.rate-limited`） |
| 反射放大（向任意地址发探测包，利用对端应答攻击第三方） | 见 §10.3 放大器防护 |
| 候选地址泄露（SRFLX 被第三方获取） | 反射地址只在配对设备间的信令通道交换（中继读信封头路由，不公开地址表）；中继的探测端点应答只回显 mapped 地址给请求方，不广播 |
| 信令重放 | 信封 nonce 窗口（D3 §5.1）覆盖 link.* 消息——信令重放被协议层拒掉 |

### 10.3 打洞反射放大器防护（重点）

打洞的本质是「双向诱骗 NAT 放行」——若不设防，攻击者可让两端向受害
地址狂发探测包（放大反射）。防护：

1. **应答前验地址**：收到探测包后，仅当来源地址 ∈ {对端信令声明的候选集}
   ∪ {对端 punch-ack 声明的实际源端口} 才应答；未知来源一律丢弃（且
   不产生任何出站流量）；
2. **打洞包低频率**：每候选组合 5 包 / 500ms 窗口，总包数有上限
   （单会话 ≤ 40 包）；打洞窗口 3s 封顶——即使被诱导，放大倍数有限；
3. **punch-ack 双向绑定**：双方都必须先声明自己的打洞源端口（
   `link.punch-ack` 携带），中继转达后双方才互发——**先声明、后发包**，
   从协议上杜绝「向未声明地址盲发」；
4. **探测端点限速**：中继探测端点对单源 IP 每分钟 60 包（§6.3.3）——
   探测端点不做反射源。

### 10.4 审计与可观测

- 打洞会话事件记入桌面审计日志（本地文件，不进入 AgentEvent 41 变体
  注册表——D3 §13.4 已明确配对审计不进事件流，打洞审计同例）；
- 关键审计点：NAT 探测结果、打洞开始/成功/失败（含原因）、verify 失败
  （安全事件，记时间+来源地址）、rate-limit 触发；
- LinkManager 状态经 `StatusDiagnostics.record`（D2 §7.4 先例）暴露给
  桌面设置页（当前链路、候选集、质量指标、打洞历史）——移动端相位
  投影（D4 §6.2.5）消费同一信息面。

### 10.5 安全边界总结（一句话）

**P2P 直连的信任等价于中继路径**：密钥同源（配对 master）、身份同源
（token_key 签名）、防重放独立实现（AEAD 计数器 + 序号窗口）；新增面
（UDP 端口、打洞探测）被「先声明后发包 + 验地址应答 + 限速」三重约束。

### 11.2 NAT 场景矩阵（测试基建与用例）

**基建**：Docker 容器矩阵——Linux 容器 + iptables NAT 规则模拟各类 NAT
（对齐 RFC 5128 分类；CI 在 Linux job 上跑，本地用 Docker Desktop 跑）：

| 编号 | 场景 | 模拟方式 | 预期 |
|------|------|----------|------|
| N-01 | 无 NAT（公网直连 / 局域网） | 同网容器直连 | 跳过打洞，直接连通 |
| N-02 | 全锥型（映射宽松 + 过滤宽松） | iptables MASQUERADE + 全放行 | 顺序打洞成功 |
| N-03 | 受限锥（过滤按 IP） | 自定义 nftables 规则 | 主动发包后成功 |
| N-04 | 端口受限锥（过滤按 IP:port） | nftables 精确规则 | 并发打洞成功（端口匹配） |
| N-05 | 对称 NAT（线性端口分配） | iptables + 端口增量规则 | 端口预测成功 → 打洞成功 |
| N-06 | 对称 NAT（随机端口分配） | iptables 随机端口 | 预测不可用 → Fallback L2 |
| N-07 | CGNAT（对称 + 共享公网 IP） | 双层 NAT 叠加 | 预测成功则通，否则 Fallback |
| N-08 | 企业网禁 UDP | iptables DROP UDP 出站 | Signaling 探测失败 → 标记禁 L3 → L2 |
| N-09 | IPv6 双端全局地址 | IPv6 网络模拟 | 跳过打洞直接连通 |
| N-10 | IPv4/IPv6 双栈混合（一端无 v6） | 混合配置 | 降级 IPv4 打洞流程 |
| N-11 | 双端同 NAT 后（同一路由器两台设备） | 同 NAT 容器内双端 | 打洞应成功（回环路径） |
| N-12 | 移动网络模拟（高延迟 + 丢包） | tc netem（+50ms/2% 丢包） | 打洞窗口内重传策略生效 |

**矩阵断言**：成功率（预期成功场景 ≥ 90% 通过）、耗时（打洞协商 + 打洞
≤ 5s）、回落正确性（失败场景必须落 L2 且业务连续）、无泄漏（失败场景
无残留 UDP socket）。

### 12.1 阶段总览

合计：L3 全量约 6~8 周；L1 深化可与 D2 收尾并行。

### 12.2 L1 深化（快，2 周）交付物

1. 二维码生成扩展：网卡枚举 + `h`/`fp` 参数（桌面侧 `server/pairing/`
   扩展，接入 D2 §7.4 的配对命令面）；
2. mDNS 广播（mdns-sd 集成，桌面侧可选开关，默认开）；
3. 移动端端点解析（二维码 `h` 列表解析 + 按序尝试 + 3s 超时）；
4. 自动切换 v1：netinfo 触发 + 同网判定 + L1/L2 双候选（RelayLink 未落地
   前以「离线投影」为 L2 占位——切换逻辑先行，链路接入点后置）；
5. 连接族上限升级（D2 §10.5 语义 → §7.5.4）。

**验收**：扫码配对 < 60s（含端点尝试）；WiFi 进/出自动切换；桌面重启后
自动重连追平（D1 §8.2 P1 验收 1/2 复用）。

### 12.3 L2（中，随 M2 落地）交付物

1. RelayLink 客户端双端实现（§5.4）；
2. 压缩协商（zstd 帧级）与配额客户端侧（§8.4）；
3. 连接族多链路共存（L1 活跃时中继热备默认开启）；
4. 与 M2 服务端的契约对齐联调（R-RELAY-1~8 逐条验证）。

**验收**：4G 异地审批 < 3s（D1 §8.2 P2 验收 1）；中继宕机不影响局域网
路径（验收 2）；端到端加密验证（验收 3）。

### 12.4 L3（大，6~8 周）交付物

| 里程碑 | 内容 | 验收（§11.5） |
|--------|------|---------------|
| M3a（2 周） | `link.*` 消息族（conex-types 新模块 + 双端编解码）+ NAT 探测协议 + 中继探测端点契约（交 M2 实现） | 探测准确率 ≥ 95%；消息族互通 |
| M3b（2~3 周） | 可靠 UDP 层（Rust + TS 双端）+ 移动端 UDP 薄模块 + AEAD 加密 | 压测 0 丢帧；抓包无明文 |
| M3c（2~3 周） | 打洞状态机 + 端口预测 + 并发打洞 + LinkManager 三链路收口 + NAT 矩阵 | 矩阵全跑通；真机达标率 |

**排序理由**：M3a/M3b 不依赖打洞成功率（风险隔离）；M3c 是唯一「结果

信令面（link.* 扩展 ICE 候选交换）与 M3b 的桌面 UDP 基建可部分复用，
损失最小化。

### 12.5 风险表与回退决策

| 风险 | 概率 | 影响 | 对策 |
|------|------|------|------|
| P2P 达标率低于预期（家庭 < 50%） | 中 | 带宽优化落空 | 启动方案 B（WebRTC + coturn）；切换决策点：M3c 真机验收不达标且 NAT 矩阵 N-02~N-05 成功率 < 80% |
| 移动端自研 UDP 模块在 New Arch 有坑 | 中 | M3b 延期 | 降级评估 react-native-udp 兼容性；再降级：L3 仅桌面-桌面（第二桌面），移动端留 L1/L2 |
| 运营商 CGNAT 普及导致移动网络打洞率极低 | 高（中国环境） | 移动端 L3 收益小 | 产品口径收敛为「家庭网络优化」；移动端以 L2 为主，L3 按网络类型门控（检测到 CGNAT 不发起打洞） |
| 中继探测端点协议与 M2 实现偏差 | 中 | 联调延期 | 契约先行（R-RELAY-6 + §6.3.3 协议冻结为文档契约），M2 未完成期间用测试桩模拟 |
| mdns-sd 在 Windows 组播受限 | 低 | 二维码路径不受影响 | mDNS 降级为纯增强（默认静默失败） |
| 打洞包被误判为攻击（家庭路由器） | 低 | 打洞失败 | 打洞包刻意低频率（§10.3），与 P2P 游戏流量同型；失败即回落，无安全风险 |

### 12.6 与 D1 阶段规划的衔接

- D1 §8.2 的 P1（局域网）/ P2（云中继）验收全部保留，本方案不更改；
- D1「远期 P4+」的 WebRTC P2P：本方案将其**升级为 P3.5（L3）**——理由：
  自研方案的信令复用与零新增基础设施大幅降低复杂度，且服务器带宽目标
  是产品诉求（用户明确要求）；方案 B（WebRTC）仍留在远期；
- 非目标不变（D1 §8.3）：不做多 Hub 同步、不做影子执行、不做端间文件
  同步、不做 TURN 自建（L2 即兜底）。

## 13. 开放问题

1. **打洞达标率的真实数据**：本方案的成功率预期（家庭 ≥ 70% / 移动
   ≥ 50%）来自行业经验（uu 远程、ZeroTier、Tailscale 公开数据），需
   M3c 阶段用真实路由器矩阵校准；不达标触发方案 B 决策（§12.5）。
2. **移动端 UDP 模块的 New Arch 实现细节**：TurboModule 规范在
   RN 0.86 下的编解码器注册流程，实施期按 expo-doctor 门禁验证；
   若受阻，react-native-udp 兼容性评估作为备选。
3. **中继信令与转发的连接复用**：同一 WS 连接承载 link.* 与转发数据时，
   中继的路由优先级（信令帧优先，防打洞协商被数据流拥塞）——M2 实施期
   定夺（R-RELAY-4 已允许分离）。
4. **多桌面场景**（一台移动端连多台桌面，D3 §13.4 开放问题 3）：本方案
   的候选集/连接族按 `desktopId` 隔离已兼容；「打洞失败名单」需要按
   desktopId + 网络环境双键缓存，避免桌面 A 的失败污染桌面 B。
5. **鸿蒙接入时 L3 的承诺口径**：是「原生 UDP 薄层移植」还是「仅 L1/L2」，
   取决于鸿蒙端的产品形态（原生 vs WebView），预留决策点，不阻塞当前。
6. **IPv6 优先策略**：双端有 IPv6 时直连几乎必然成功——是否在候选集中
   IPv6 优先于 IPv4 打洞（当前裁决：优先，§6.7 特殊通道），但需观察
   运营商 IPv6 前缀稳定性（PD 切换导致地址变化）后定稿。
7. **zstd 压缩的 CPU 成本**：桌面事件洪峰（D2 §10.7 的 20 万条 delta）
   下帧级压缩的 CPU 预算，实施期压测后确定是否降级为「仅文件/大帧压缩」。

### 14.4 一句话总结

**P2P 技术裁决：自研 UDP 打洞（中继信令协助，uu 模式）+ 轻量可靠 UDP +
AEAD 加密（密钥派生自配对 master），WebRTC 留作方案 B、QUIC 只留桌面-桌面
远期；三层切换：同网 L1 直连、跨网先 L3 打洞后 L2 中继兜底，make-before-break
+ 质量评分 + 游标续传保证切换对业务透明；带宽结论：L3 转正后服务器带宽
降 99.5%（仅信令，约 2MB/月/设备对），L2 兜底用 zstd 压缩 + Delta 裁剪 +
配额限流。**
