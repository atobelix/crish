## 1. 审计结论（TL;DR）

### 1.1 总体判断：可落地，但开工前必须先完成「协议三选一」

全部 25 份方案的共同优点：**以仓库代码事实为锚**（每份方案均有 `文件:行号` 证据链），
事件信封 / sequence 游标 / 命令 manifest / Emitter trait 四大融合点的复用判断一致且可复核，
「桌面 Hub 主从 + 单一真相源 + 局域网直连优先」的总体架构在 D1/D2/D3/D6 四份文档中无实质分歧。
这部分工程地基是稳的。

但落地路径上存在 **3 组必须在实现前裁决的架构级冲突**（第 5 章详析）：

| # | 冲突 | 冲突方 | 影响面 | 建议裁决 |
|---|------|--------|--------|----------|
| C-1 | 认证与消息面：REST+Bearer 令牌 vs DeviceEnvelope+HMAC 消息签名 vs WsEnvelope 第三套帧 | D2（Bearer+axum REST）vs D3/M6/M7（DeviceEnvelope+HMAC）vs D4 §12.5 / M5（WsEnvelope） | 桌面 server 模块与移动端连接层的全部实现 | 以 D3 为协议真源（消息级 HMAC 更安全、M6 已细化 103 kind、D5/M7 均引用它）；D2 的 axum 只承担「监听 + 信封编解码」，弃用 Bearer token 面；D4/M5 的 WsEnvelope 作废，统一 DeviceEnvelope |
| C-2 | TLS 范围：D2 v1「不做 TLS」vs D1/D3/D5「wss 强制 + 自签 pinning」 | D2 §3.2 非目标 5 vs D1 §8.2 P1 / D3 §3.1 / D5 §10.1 ADR | 局域网直连的安全基线 | wss+pinning 直接进 R1。D1 P1 验收含「抓包验证 TLS」，移动端商店审核也要求传输加密；D2 的「v1 免 TLS」是早期简化，两者不可两全——以 D1/D5 为准 |
| C-3 | 移动端审批时机：M8 O2「一期只收通知」vs D1 P1「审批端到端 <2s」 | M8 §9.3 O2 vs D1 §8.2 P1 / D4 §11.1 M2 / F2 全篇 | 产品核心价值定位 | 移动端远程审批是母方案 D1 的 P1 验收红线，F2 已设计完整决策链路，无技术阻塞；明确「推送一期=通知+直达审批卡，审批决策随 R2 审批中心一并开放」 |

另有 **7 组参数不一致**（端口、配对码、事件变体策略、命令数、阶段命名、生命周期、聚合端点），
详见第 2/5 章；其中阶段命名冲突与命令数勘误（92 vs 95）影响排期与任务书引用，必须统一。

### 1.2 阶段命名总冲突（第 2 章详表）

当前 **P/M/L/R 四套前缀 + 数字编号 0-7** 在 11 份文档中混用且语义互撞：
D1 的 P1 ≠ M1 的 P1；D4 的 M2 ≠ D7 的 M2 ≠ D5 的 M2 ≠ AC 的 M2；D2 的 P0-P5 与 D1 的 P0-P3 直接冲突。
**建议：开工前统一为 R0-R5 六阶段**（理由与映射见第 2.3 节）。

### 1.3 依赖链要点（第 3 章详表）

- **协议类型落 conex-types 是全局第一前置**（D3 §12.2 / M6 §12：`device/` 模块族 + `device-protocol.json` + 生成器泛化），先于桌面服务端与移动端的一切实现；
- 桌面服务端（D2）与协议包（D8 阶段 1）可**并行**（互不依赖：D2 依赖「事件信封既有契约」，协议包依赖「设备域新类型」）；
- 移动端工程骨架（D8 阶段 0）只依赖根 workspaces 与 .gitignore 白名单修正，可与协议包并行；
- **账号中心模块（push_tokens / relay_credentials）是中继（M2）与云推送（M8 M3）的共同前置**，且属外部系统（flowbit），应尽早启动（与 R0 并行）；
- P2P（M3 L3）依赖中继信令（L2），而 L2 依赖账号中心；L3 排在整条链末端（R4）；
- 鸿蒙（M1 P2）依赖「双端共享层冻结」（协议/状态/UI 三层），最早只能在 R2 末启动预研。

### 1.4 工作量要点（第 4 章详表）

- 全链路单人估算约 **54-73 人周**（约 12-18 个月），其中 3 个超大包需要拆分：
  - M6 的 37 命令实现（含 103 kind 注册表 + 双端编解码 + 白名单）→ 按 F 系列域拆 6 批；
  - M8 M1 的 32-44 人日（推送 + 发布准备）→ 拆 5 包，其中「发布准备」3-5 人日与开发并行；
  - M8 M3 的 47-72 人日（鸿蒙 + 中继 + 账号）→ 依赖 O5 裁决是否立项，立项后按「账号→中继→鸿蒙」串行排；
- 无「单点独大拖垮整体」的包：最大单体包（D4 移动端工程 21 周）内部已有 M0-M7 里程碑闸门；真正的时间风险在**外部等待**（备案 1-3 周、厂商账号 1-5 个工作日、App Review、鸿蒙设备采购）。

### 1.5 缺口要点（第 5 章详表）

方案已覆盖：Windows 防火墙提示（D2 §12.1）、移动端 mock daemon（D4 §9.2 / M4 §10.4）、
账号中心部署环境（AC §3.7/§6.10：flowbit-auth 8787 + Cloudflare + Let's Encrypt）、
中继部署（M2 §13.3 env + Dockerfile）、版本升级协议（D3 §10 + M8 三轨）。

**未覆盖或需补强的落地缺口 8 项**：桌面睡眠/唤醒的服务恢复、桌面多实例端口竞争、
「桌面服务未就绪时移动端 UI 开发依赖的 mock 契约交付时机」（R1 就必须交付，各方案默认其晚于真实网关）、
Windows AP 隔离/公用网络防火墙配置的用户引导、桌面端开机自启与托盘常驻（推送域刚需，D2 未接）、
移动端商店更新与协议兼容窗口的联动 SOP、中继/账号中心的线上监控与容量水位、
旧桌面端（无网关版本）与新移动端的升级路径（当前仅「新桌面+旧移动」演练）。

### 1.6 验收要点（第 6 章详表）

D1 §8.2 的 P0-P3 验收标准（含量化指标）是全库最完整、最可执行的验收体系，建议作为总验收基线；
D2 §13.1 L4 清单 1-9、D3 T-D3-01~10、D4 §11.1、M6 T-M6-01~14、D5 §10.3 红线 1-7、M3 §11.5、M8 §8.1-8.3 与之对齐即可。
**缺口**：D1 的 P1 验收含「抓包验证 TLS + 指纹校验」，与 D2 的「v1 不做 TLS」冲突（C-2），验收无法两全，必须裁决；R1 阶段缺少「Windows 真实局域网（非虚拟网卡）」验收场景。

### 1.7 风险要点（第 7 章详表）

登记 **24 项风险**（技术 13 / 业务 6 / 时间 5）。最高关注：
- 技术：RNOH 生态（活跃但小、无推送类适配包）、Expo SDK 57 新架构边角、自研 UDP 打洞在运营商 CGNAT 下的成功率（预期 50-80%，移动网更低）；
- 业务：账号中心是 flowbit 商业系统（外部依赖 + 白名单扩展影响现有 chat_sync_desktop 用户）、App Review 远程控制类审查、桌面关机=推送断源（架构属性，只能中继代发缓解）；
- 时间：工信部 APP 备案（1-3 周，进关键路径）、厂商账号与商店审核、鸿蒙 ArkTS 技能零积累。

### 1.8 待裁决项统计

合并去重后共 **52 项待裁决**（8 份文档的开放问题 + AU3 新发现 3 组冲突与 7 组不一致），
其中「开工前必须裁决」7 项、「R1/R2 排期内裁决」12 项、「可延后」33 项。全部清单与建议见第 8 章。

### 2.2 阶段命名冲突的实质影响（不止是文档观感）

1. **排期引用歧义**：任务书写「进入 P1」时，读者无法区分是 D1 的局域网直连、M1 的双端上线、还是 F5 的只读骨架——会直接导致排期错配。
2. **验收引用歧义**：D5 的「M2 出口条件」与 D4 的「M2 审批中心」毫无关系，但共享 M2 代号；安全评审引用 D5 M2 时极易被排期错挂。
3. **D2 与 D1 的 P0 撞名最危险**：D2 P0=文档评审（1 天量级），D1 P0=原型开发（1 周量级）——若任务书引用「P0 完成」验收，双方理解可能差一个数量级。
4. **M8 的 M1 与 M1 平台的 P1 语义接近但不同**：M8 M1=推送+首发（内容含备案），M1 平台 P1=双端上线（含鸿蒙预研）——两者排期必须合并为同一时间窗，否则商店首发与推送能力脱节（M8 §0.1 明言「没有推送矩阵就没有上架资格」）。

### 2.3 统一阶段划分建议（R0-R5 总纲）

**建议以「能力进网顺序」为轴，替换全部 P/M/L/R 前缀。每阶段含独立验收（第 6 章）。**

| 统一阶段 | 名称 | 内容摘要 | 对应既有阶段 | 验收锚点 |
|----------|------|----------|--------------|----------|
| **R0** | 协议冻结 | 设备域类型落 conex-types + device-protocol.json 注册表 + 生成器泛化 + TS↔Rust 对拍闭环 + 协议三选一裁决（C-1/C-2/C-3 在此关闭） | D8 阶段 0-1、D3 §12、M6 §12 | T-D3-01~10、T-M6-01~14、对拍门禁绿 |

| **R2** | 移动端基础 | crish-mobile 重建 + 连接层 + 审批中心 + 观测面 | D4 M0-M4、M4 M0-M4、F1 M2、F2 全量、F5 P1 | D4 §11.1 M0-M4 出口 + F2 验收 1-7 |
| **R3** | 推送 | 在线 WS 直推 + APNs/HMS 离线 + 厂商全矩阵 + 商店首发 | D7 M0-M2、M8 M1-M2、D4 M5-M6、AC M0-M5、F1 M3 | M8 §8.1-8.2 验收、D7 §12 验收 |
| **R4** | 中继 + P2P | 账号中心 relay_credentials + Rust 中继 + L2/L3 链路 | D1 P2、M2 R1-R6、M3 L1-L3、AC M6 集成、M8 M3（中继部分） | D1 P2 验收 1-5、M2 §11.5 验收 1-6、M3 §11.5 |

**理由**：
- 与 D1 母方案语义对齐（R1≈D1 P1 桌面侧、R2≈D1 P1 移动侧、R3≈D1 P2 推送面、R4≈D1 P2 中继面、R5≈M1 P2 鸿蒙面），母方案验收标准可直接挂靠；

- R0 单列「协议冻结」与 D8 阶段 0/1 对齐——这是全链唯一「一切之前」的前置（第 3 章拓扑序），不给它独立阶段号会导致前置任务被并排期压缩。

**迁移动作（低成本）**：不必重写 25 份文档；在 D1 文档头加「阶段对照表」一张 + 各方案文档头加一行「本方案阶段 ↔ 统一阶段映射」，任务书引用一律用统一阶段号。

## 5. 缺口与遗漏审计

### 5.1 三大架构冲突（实现前必须裁决）

#### C-1 认证与消息面三选一（最高优先级）

| 方案 | 文档 | 形态 | 优缺点 |
|------|------|------|--------|
| A | D2 §7/§8 | 配对码(8 字符,120s,40bit) → 32 字节随机令牌(SHA-256 哈希落盘) + Bearer 头 + REST + WS JSON Lines | 简单、可 curl 验证；但每消息无签名（仅连接级鉴权），重放/篡改防护弱 |
| B | D3 §4-5 / M6 / M7 / D5 | 配对码(CXN-12 字符,10min,60bit) + X25519 ECDH + PAKE 混合 + HMAC-SHA256 每消息签名（nonce 防重放）+ DeviceEnvelope | 消息级安全、前向安全、多端权威方案一致；实现量大（但 M6 已细化到 103 kind schema） |
| C | D4 §12.5 / M5 §4.2 | WsEnvelope（v/type/seq/payload）+ hello/invoke/invoke-result 帧 + 令牌 | 介于两者间，但是第三套帧格式，与 B 不兼容 |

**影响**：桌面 server 模块的 handler 面、移动端 signer.ts、中继握手、推送代发全部取决于此。三套并存 = 三倍实现 + 三倍测试 + 必然漂移。
**建议**：选 B（D3/M6 体系）。理由：D5/M7 已在其上建立安全模型（M-TOKEN/M-VERIF/M-OUTBOX），M6 已交付完整 103 kind schema 与 T-M6 验收锚点，B 的额外成本集中在 R0 一次性投入；C 作废（D4 §12.5 的 WsEnvelope 是 D4 在 D3 冻结前的早期草案，M5 §4.2 已声明信封并入 D3 体系，说明 M5 已向 B 收敛）。

#### C-2 TLS 范围冲突（R1 排期内必须裁决）

- **D2 §3.2 非目标 5**：「不做 TLS 加密（v1 假设局域网可信模型）」——与 D2 §12.2 威胁表「局域网窃听（配对模式）→ 信任模型声明」配套；
- **D1 §8.2 P1 验收 5**：「安全：抓包验证 TLS + 指纹校验生效」；
- **D3 §3.1**：「TLS 首选（自签证书 + 配对期证书指纹交换）；无 TLS 的降级模式必须显式开启」；
- **D5 §10.1 ADR**：「传输协议 wss 强制 + 自签 CA pinning」。

**影响**：局域网直连是 R1-R2 的核心链路，TLS 与否决定自签证书生成、移动端证书固定、配对载荷是否携带 tlsFingerprint（D3 §4.6）三块工作量；「v1 免 TLS」只省证书面，但违背 D1 P1 验收与 D5 红线。
**建议**：以 D1/D3/D5 为准——R1 即做 wss + 自签证书 + 指纹固定（D3 §4.6 的 tlsFingerprint 已设计进配对协议，成本可控）；D2 的「免 TLS v1」降级为「中继路径加密前的过渡选项」，删除或标记为废弃。

#### C-3 移动端审批时机冲突（产品定位，R2 排期前裁决）

- **M8 §9.3 O2**：「审批能否在移动端直接批准/拒绝？——一期只收通知 + 查看；决策按钮需新增移动端 → 桌面命令通道」；
- **D1 §8.2 P1**：「手机……审批端到端 < 2s」——远程审批是 P1 核心场景；
- **D4 §11.1 M2**：「审批中心（3 周）：审批卡 UI + 审批流状态机 + 决策发送 + outbox 离线队列」；
- **F2 全篇**：审批中心域设计（含 L1/L2 决策、双因素、离线 outbox）。

### 9.2 里程碑闸门（每阶段出口判定）


### 9.3 里程碑判定规则（沿用 D1 §8.5 铁律）

- 每阶段验收全绿才进入下一阶段；
- 任一阶段发现「单写者假设被破坏」（移动端出现绕过桌面的写路径）即回退评审；
- R0 未完成前，任何端不得开始设备域协议相关实现（mock daemon 除外——它恰好是 R0 产物的测试载体）；
- 每阶段结束提交纪律：测试与调试脚本立即 `git add` 入库（AGENTS.md 铁律）。

### 9.4 建议立即启动的三件事（不等任何裁决）

1. P-0.1 备案 + P-0.2 开发者账号（纯外部等待，越早越好）；

3. P-0.4 鸿蒙 RNOH 技术预研（2-4 人周，Gate A/B 的输入，无论是否立项都不浪费）。
