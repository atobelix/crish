## 1. 审计结论（TL;DR）

### 1.1 一句话结论

**方案集总体自洽度中等偏上**：D3→M3→M7→M2 的密钥派生链、M6 的 103 kind 内部账目、
D6/M6 的 at-least-once 写命令语义、M7/F2/F6 的授权交互叠加逻辑四项**自洽**；
但存在 **4 项 P0 直接矛盾（配对协议三套规格 / 中继读帧与控制帧双轨 / 连接上限语义互斥 /
推送场景级别三处打架）** 与 **11 项 P1 不一致（命令数 92vs95 / 同步面白名单 20vs26 /
命令路由命名两套 / Tab 结构 3 套 / 推送 WS 中继游离于 D3 体系 / store 范式冲突等）**，
以及 **12 项 P2 轻微不一致**。
**最需裁决的一项：配对协议规格三套并存（D2 8 字符 120s / D3 CXN-12 字符 10min /
D5 8 字符 base32 10min / D7 6 位 5min），必须冻结为单一真源后才能开工实现配对。**

## 2. 重点 1：密钥与凭证链审计

### 2.1 审计范围

D3（X25519 ECDH + HKDF token_key）→ M3（AES-256-GCM 派生自配对 master）→
M7（四类令牌分治）→ M2（relay credential HMAC-only）——逐环核对派生输入、
存储形态、TTL、撤销语义。

### 2.2 派生链逐环核对（结论：同源自洽）

| 环节 | 文档位置 | 结论 |
|---|---|---|
| master 派生 | D3 §4.4：`master = HKDF(ikm=ecdh ∥ psk, salt=desktopId ∥ mobilePub ∥ "v1", info="conex-pair-master", L=32)` | 事实源 |
| token_key/enc_key/refresh_key 三子钥 | D3 §4.4 步骤 5（HKDF 一次展开，info 区分） | 事实源 |
| P2P 链路密钥 | M3 §10.1：`k_link = HKDF(master, "conex-link-v1" ∥ desktopId ∥ deviceId, "conex-link", L=96)` → k_ab/k_ba/iv0 | **与 D3 master 同源，自洽** |
| 中继链路 AEAD | M2 §5.6：端到端加密用 D3 §4.4 派生的 `enc_key`（AES-256-GCM），中继/账号中心均无密钥 | **同源，自洽**（但见 P2-1） |
| 消息级 HMAC | M7 §4.3 T-1 / D3 §5.1：token_key 派生值即为 HMAC 签名材料 | 自洽 |
| 中继凭据 | M2 §5.2 / M7 §4.5 / AC §6.4：`rc_<32B>`、TTL 30 天、服务端只存 HMAC、verify 一次性 nonce | **三处一致，自洽** |
| 推送注册 | M7 §4.6 / M2 §7.3 / AC §6.3：push_tokens 表 + token_hash 幂等 | **三处一致，自洽** |

### 2.3 自洽性结论

1. **master 是唯一信任根**：D3 配对期派生 → M3 P2P 链路密钥、M2 中继 AEAD 都从它展开，
   没有出现第二套独立密钥体系（D5 的 256bit 随机令牌形态除外，见 P1-10）；
2. **四类令牌职责边界清晰**（M7 §4.2 表）：配对令牌 ⊥ 账号 token 双信任根，
   中继凭据依赖账号 token 但生命周期独立，推送注册与身份令牌解耦——与 AC §4.3.5 分工一致；
3. **HMAC-only 存储纪律一致**：relay_credentials（AC §6.4 / M7 R-1）、push_tokens vendor_token
   （M7 P-1 加密存储）、桌面 token_key（D3 §4.5 落盘派生值不落 master）——无明文落库设计。

### 2.4 三处需协调项

1. **P1-10 令牌形态双轨**：D3 §4.4 派生形态 vs D5 §3.3「256bit 随机令牌形态」——
   M7 §4.3 已自我标注「两套协议文本的差异是 M7 遗留协调项，见 §10 开放问题 O-01」，
   M7 倾向以 D3 派生形态为准。**审计确认此倾向合理**（消息级 HMAC 已依赖派生值，
   D2 的 32 字节随机 Bearer 令牌是第三套形态，见 P0-1 关联）。
2. **P2-1 enc_key 状态过期**：D3 §4.4 步骤 5 将 enc_key 标注为「预留：载荷加密 AES-256-GCM，
   本期 TLS 承载，密钥预派生留位」；但 M2 §5.6 已把 enc_key 作为中继链路的正式 AEAD 密钥、
   M3 §10.1 已从 master 展开 P2P 链路密钥（k_ab/k_ba 即 enc_key 的角色）。D3 的「预留」表述
   与下游的「已启用」不一致——建议 D3 §4.4 更新为「enc_key 用于中继（M2 §5.6）与
   P2P 直连（M3 §10.1）的应用层加密，局域网 TLS 承载期仍预派生留位」。
3. **P2-2 令牌 TTL 出处缺失**：M7 §4.1 表 T-1 行「默认 30 天（D5 §3.3，可配 10~365 天）；
   会话密钥 8h（D5 §3.5）」——D3 全文没有 token_key 的 TTL 常量（D3 §13.2 常量表无此项），
   D3 §5.1 只说「token_key 不变，只换 nonce 基数」。30 天 TTL 与 8h 会话密钥的概念
   只存在于 D5/M7，建议在 D3 常量表补登记或明确由 D5 层管辖。

## 3. 重点 2：消息清单审计

### 3.1 M6 的 103 kind 内部账目（结论：自洽）

M6 §1.1 与 §3.1：`cmd.*` 37 + `result.*` 37 + `events.*` 11 + `stream.*` 4 + `pair.*` 4 +
`auth.*` 3 + `device.*` 4 + `heartbeat` 2 + `error` 1 = **103**。逐项核对：

- `events.*` 11 = subscribe / subscribeAll / subscribe.ok / push / ack / resume /
  resume.page / resume.done / session.updated / session.removed / session.updatedAll（M6 §1.1）——
  与 §10.5 schema 的 11 个 $defs 一致；
- 41 事件分类统计（M6 §5.1）：T=13（1,2,3,4,14,15,24,29,31,32,35,36,38）+
  R=18 + U=10 = **41**，同步面 20——内部账目自洽；
- 推送统计（M6 §5.3）：p0 6 + p1 4 + p2 3 = 13 场景，宣称与 D7 §3 场景清单一一对应。

**结论：M6 是消息清单的协议真源，其内部账目（103 / 37 / 41 / 13）全部自洽。**

### 3.3 与 M7 远程命令清单的关系（P1-3：37 vs 30 vs 13）

| 清单 | 数量 | 命名风格 | 出处 |
|---|---|---|---|
| M6 命令 kind | 37 | `cmd.getStatus` / `cmd.runControl`（camelCase） | M6 §4.1-4.6 |
| M7 网关路由 | 约 30 | `remote.get_status` / `remote.run_control`（snake_case） | M7 §2.8 汇总矩阵 |
| D3 早期映射 | 13 | `cmd.approve` / `cmd.runControl` | D3 §8.2 |

- 三份清单的**数量不同**（37/30/13）且**命名不同**（camelCase kind vs snake_case route）；
  M7 §2.8 表列出的 remote 路由（remote.write_file / remote.read_file /
  remote.request_approval_list / remote.pair_start 等）与 M6 的 cmd 命令
  （cmd.writeFile / cmd.readFile / cmd.listPendingApprovals / cmd.getPairState 等）
  **无显式映射表**。
- M7 §2.9 的 `RemoteCommandEntry.route`（remote.* 命名）将被登记进
  `remote_manifest.rs` 注册表，且 M7 §8.6 红线 1 要求「矩阵每一行都在注册表有对应条目」——
  若 route 名与协议 kind 名不一致，移动端网关需要一份「kind → route → risk_class」
  三层映射，目前没有任何文档给出这份映射。
- **结论**：协议命令面（M6/D3）与安全授权面（M7/D5 remote_manifest）命名体系未统一。
  **修改建议**：在 M7 §2.9 增加「remote.* 路由名 ↔ M6 cmd.* kind 名 ↔ manifest 命令名」
  三列映射表（生成器或测试锁定），或直接规定 remote.* 路由名 = cmd.* 后缀（同一命名）。

### 3.5 P1-2 同步面白名单 20 vs 26

- M6 §5.0：同步面参与 = 20（1,2,3,4,7,8,9,10,14,15,20,21,24,28,29,31,32,36,37,38），
  并明确「21 个不同步：message-delta / **message-start** / subagent-event / task-output /

  M6 的 20 类清单，并删除 message-start/tool-batch-*/tool-input-repaired/checkpoint-*
  的可选项；或反向（若评审认为 D6 更全），则 M6 §5.0/§5.1 需扩同步面到 26 类——
  二选一，需主控裁决。

### 4.3 两处标注性问题（P2）

1. **P2-9 危险度 1 允许的验证等级标注**：M7 §2.3 矩阵 F2-03「决策：允许（危险度 1）」

### 6.1 三层拓扑与路径选择（结论：自洽）

### 6.2 P0-2 中继读帧边界与控制帧双轨

| 面 | M2 的裁决 | M3 的表述 | 矛盾点 |
|---|---|---|---|
| 中继是否解析业务帧 | M2 §6.1：「中继**不认识 D3 的 kind/msgId/auth 字段**，payload 对中继是不透明字节」；M2 §6.2 `data.frame` 对中继是不透明字符串 | M3 §5.2：「消息格式：**复用 D3 DeviceEnvelope**（from/to 字段已有设备语义），中继**读信封头（deviceId / kind）做路由**，不读 body」 | 中继能否读 D3 信封的 `kind` 字段——M2 说不读、M3 说读 |
| 中继控制帧协议 | M2 §6.2 `RelayFrame`：`{t: hello/hello-ok/hello-err/data/broadcast/delivery/ping/pong/error/kicked/bye, v, credential, to, from, frame, ...}`（独立于 D3 信封的帧格式） | M3 §5.4 `RelayLink` 行为：`relay.hello` + 等待 `relay.hello-ack`；M3 §9.4 新增消息族 `relay.*`（relay.hello / hello-ack / bye / peer-offline / backpressure）与 `link.*`（§6.4 全表） | 中继控制面两套：M2 的 RelayFrame（t 字段枚举）vs M3 的 relay.*/link.* 消息族（D3 信封 kind 命名） |
| 在线状态通知 | M2 §4.3：在线判定由桌面做，中继搬运 appState | M3 §5.2：中继维护 deviceId → connId/lastSeen，断线通知对端 `link.peer-offline` | M2 未定义 peer-offline 推送（M2 §12.3 开放问题 1：「在线状态是否广播给端侧——不做主动广播，靠查询」）；M3 要求 `link.peer-offline` 主动通知 |

- 背景：M3 写作时 M2 尚未产出（M3 §5 标题「L2 云中继（M2 接口预留）」），M3 按
  「接口预留」定义契约；M2 落地后**未回头对齐 M3 的预留契约**（M2 §1.3 承接图声称
  「输出：D3 的 RelayLink 服务端」，但 M2 的帧协议与 M3 §5.2/§9.4 的契约不一致）。
- **结论**：中继的读帧边界（读不读 D3 kind）与控制面协议（RelayFrame vs relay.*/link.*
  消息族）双轨并存，直接决定双端 RelayLink 客户端与中继服务端的实现接口。
  **修改建议**：以 M2 §6.1/§6.2 的「帧级透传 + RelayFrame 控制帧」为基线（M2 是
  中继服务设计真源，其「不解析业务」原则与 D1 §3.3 铁律一致），M3 §5.2 改为
  「中继经 RelayFrame 头 to/from 路由，不读 D3 信封」；M3 §9.4 的 relay.*/link.* 消息族
  中的**中继控制面**（hello/hello-ack/bye/peer-offline）并入 M2 RelayFrame 枚举，
  link.* 打洞信令保持为**业务层消息**（经 data.frame 透传）——打洞信令是端间内容，
  中继只转发不解析，与 M2 §2.5 非目标 7「P2P 信令若未来经中继走，也是转发不是汇聚解析」一致。

### 6.3 P0-3 每设备连接上限语义互斥

### 7.2 P0-4 推送场景级别三处打架

### 7.3 P1-5 推送 WS 中继游离于 D3 协议体系

- D7 §4.5a 定义了独立的「WS 中继协议 v1」：`pair-request/pair-accept/ping/pong/push/ack/
  unpair/kick` 帧 + **6 位配对码（5min、3 次、锁 30min）** + 32 位 wsKey HMAC；
  端口为「随机高位端口」（D7 §4.1 路线 A）；
- M8 §0.2/§1.2.1 声称「直接承接 D7 §4.5a」；
- 而 D3/D6 体系的事件推送走 `events.push`（DeviceEnvelope 内），命令/事件走 D2 网关
  WS（`/v1/events`，8765 端口，Bearer token）；
- 于是移动端在线时存在**两条 WS**：协议 WS（D2/D3 面，事件/命令/审批）与推送 WS
  （D7 面，PushMessage/ack），两套帧协议、两套配对（6 位码 vs D3 配对码）、两套鉴权
  （wsKey vs token_key HMAC vs Bearer），且没有任何文档说明两通道的关系
  （同一连接复用 / 并行双连接 / 推送并入协议面）。
- D7 §4.3 决策 5 的辩护是「推送协议与事件协议解耦」；M6 §5.3 却又把「push（D7 组合消息）」
  列为跨端推送消息并纳入协议语境——**协议归属摇摆**。
- **结论**：P1-5——推送直推通道与 D3 协议面必须明确归属。**修改建议（两选一）**：
  方案甲（推荐）：在线直推改为协议面的 `events.push`（D3/M6 已具备），推送专用
  PushMessage 降级为「移动端从 events.push 裁剪出通知语义 + 厂商通道载荷」，
  D7 §4.5a 的独立 WS 中继作废（消两套帧/两套配对/两套鉴权）；方案乙：若保留独立
  推送 WS，则 D7 §4.5a 的配对必须复用 D3 配对协议（同码、同 TTL、同鉴权），
  且 D7 §4.5a 与 D2 网关端口合并（8765）——不允许「随机端口 + 6 位码」第三套体系存在。

### 7.4 P1-9 appState 枚举两套

- D7 §4.5a：`appState: active | background | inactive`；
- M2 §4.3-2：`appState: foreground | background | active`。
