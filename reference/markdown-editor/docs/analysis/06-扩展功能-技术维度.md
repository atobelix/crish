# 扩展功能分析 · 技术维度（06）

> 自研 Markdown 渲染引擎（reference/markdown-editor）的架构可扩展点与技术改造路线。
> 与 01（性能帧率）/ 02（解析器正确性）/ 03（测试门禁）/ 04（编辑深度）/ 05（扩展功能产品维度）互补。

## 1. 规则插件体系：INLINE_RULES 硬编码 vs markdown-it ruler

**现状**：`parser.ts` 的 `INLINE_RULES` 硬编码数组（顺序即优先级）+ `scanTokens` 单函数递归——加语法 = 改数组 + 改递归分支，规则间顺序耦合，核心文件膨胀（965 行）。

**可扩展性评估**：低。当前 20+ 规则已让 scanTokens 成为全引擎最复杂函数；每加一条规则，回归风险指数增长（已实证：未闭合 HTML 链触发 2^n 递归爆炸）。

**改造方案**：轻量 ruler（不照搬 markdown-it 全量）：
```
interface InlineRule {
  name: string;
  priority: number;
  match(text, pos): InlineMatch | null;  // 纯函数，无副作用
}
class InlineRuler {
  add(rule); remove(name); // 运行时增删
  scan(text, pos): InlineMatch | null;  // 按 priority 排序尝试
}
```
- scanTokens 主体改为"遍历 ruler 尝试 match + 失败规则位图记忆"（同时消灭 2^n 爆炸，见 02 分析）
- 优先级 = 显式数字而非数组顺序
- 接入点：`parseLine` 的 inline 分支；自定义语法（@mention/Purpose 块）注册为普通 rule

**兼容路径**：INLINE_RULES 数组直接转为 ruler 初始注册表（同名同序），行为零变化。

## 2. 装饰层：统一 activeState/选区/链接样式

**现状**：activeState 经 props 逐层传（MarkdownEngine→LineItem→BlockRenderer→InlineRenderer）、选区高亮独立组件（SelectionHighlight 矩形层）、链接样式 class 直改——三个机制三套实现。

**可扩展性评估**：中。功能上可用，但装饰与渲染内容耦合：加一种"高亮类型"（如搜索结果高亮）要动 props 链。

**改造方案**（借鉴 CM6 decoration 的 RangeSet 索引，但轻量）：
```
interface Decoration { from: number; to: number; kind: 'active'|'selection'|'search'|'link'|'custom'; }
class DecorationSet {
  query(from, to): Decoration[];  // 区间查询
  // 内部：按行索引的排序数组（每行一个 bucket，增量维护）
}
```
- LineItem 渲染时查 `decorationSet.query(行范围)` → 决定 class
- activeState/选区高亮/未来搜索高亮统一进 DecorationSet
- 光标/选区变化只更新 DecorationSet（O(受影响行)），不再重渲染整行

**兼容路径**：SelectionHighlight 和 activeState 逻辑迁入，外部行为不变。

## 3. 语法扩展点：自定义语法注册

**现状**：无。宿主（Conex）若需 @mention、代码引用块、对话流 Purpose 块，只能改 parser 核心。

**改造方案**：语法扩展双入口：
- **行级**：`registerBlockSyntax({ name, test(line, context), parse(line, context): LineNode })`——在现有块级判定（heading/hr/table/fence）之后尝试自定义
- **内联**：上述 InlineRuler.add()
- 扩展返回的节点类型需登记到 `LineType/InlineType` 联合类型（TS 侧用接口合并或扩展注册表 `customNodeTypes: Map<string, Renderer>`）

**渲染侧**：BlockRenderer/InlineRenderer 增加"未知类型查注册表"分支——自定义节点渲染器（React 组件）注册进表，核心渲染器不感知。

**接入点**：宿主 @mention 场景 = 行内 rule（`@` 前缀）+ 渲染注册；Purpose 块场景 = 块级语法 + 渲染注册。

## 4. 流式与协作的架构统一：事务日志 → CRDT 演进

**现状**：appendText（流式快速通道，不进 undo）+ insertText/deleteText（进 undo，EditorOperation 行级 splice）+ LineOffsetTree（可变 + clone 深拷贝）。三套写路径。

**可扩展性评估**：协作友好度中等——EditorOperation 是行级 splice（无 from/to/insert 位置级 diff），并发索引漂移无解。

**改造方案**：
- **近期**：统一 `applyChange(from, to, insert, meta)` 事务入口（表格操作全部收敛进它）；EditorOperation 扩展 `{ from, to, insert, removedText }` 位置级字段；append 经 applyChange（meta: 'stream'）走"流式合并为单 undo 步"规则
- **中期**：append-only 变更日志（每事务追加 `{ seq, op }`）+ 版本号——为同步/回放铺路
- **远期 CRDT**：双结构——CRDT 管正确性（并发合并），LineOffsetTree 退化为渲染索引（从 CRDT 状态重建，idle 分块）；分段树的分裂/合并操作与 CRDT 的 list 操作天然同构

**兼容路径**：applyChange 先作为内部新入口，旧操作签名保留为薄封装。

## 5. 渲染层抽象：自定义块渲染 + 主题 + 数学引擎替换

**现状**：BlockRenderer switch（12 种类型）+ InlineRenderer switch（20+ 类型）——加类型 = 改 switch。

**改造方案**：
- `BlockRendererRegistry: Map<LineType, React.ComponentType<{block, lineOffset, activeState}>>`——核心类型内置，自定义类型注册
- 主题：`renderTheme` 上下文（token 映射：颜色/字体/圆角）——现有 colorAdaptor 承担颜色计算，主题只是 token 选择层
- 数学引擎：`mathRenderer: (formula, display) => string` 注入点——KaTeX 默认，可换 MathJax/自研

**兼容路径**：默认注册表 = 现有 switch 分支提取，行为零变化。

## 6. 性能分层：Canvas 只读层 + Worker 增量解析预留

**现状**：全 DOM 渲染；worker 文件存在但未接线（且宿主 RL-05 #10 禁自定义 worker 池）。

**改造方案**：
- **Canvas 只读层**（超大文档阅读模式）：`readOnlyCanvas` 模式——文本块绘制到 canvas（字符纹理），DOM 只保留光标/选区覆盖层 + 交互热区；行高模型（01 分析）是它的前置——canvas 模式下行高纯预测，无测量回环
- **Worker 增量解析**：不新增 worker 池——复用宿主既有 worker 通道（若宿主提供）或保持主线程（行级解析已够快，0.035ms/用例）；fence 增量状态机在数据层维护（已做），不需要 worker
- 判定：Canvas 层只在"纯阅读 + 超长行密集"场景启用，编辑器模式不启用

**兼容路径**：`renderMode: 'dom' | 'canvas'` 开关，DOM 模式为默认且为唯一编辑模式。

## 7. 状态层可测试性：纯函数化边界

**现状**：EditorStore 是 zustand store（759 行），增量逻辑（updateLinesIncremental）在 store 内部——测试需 setState 初始化 + 走 store API（白箱耦合）。

**改造方案**：
- 把增量核心提取为纯函数模块 `core/editor-model.ts`：`applyChange(lines, offsets, codeState, fenceLines, from, to, insert): State`（无副作用，输入输出纯数据）
- store 变薄：只做"调纯函数 + set 结果 + 记录日志"
- 测试直接测纯函数（快、无 React/zustand 依赖），store 层测薄封装

**兼容路径**：函数签名与现有 updateLinesIncremental 对齐，store 内部一行替换。

## 8. 宿主集成接口：引擎独立包形态

**现状**：单实例全局 store（useEditorStore 单例）+ React 组件直接引用——无法多实例（文档工作区/多面板需要）。

**改造方案**：
```
// 引擎作为可实例化包（未来独立 npm 包 @crish/markdown-engine）
createEditorStore(): EditorStore        // 实例工厂（替换全局单例）
<MarkdownEngine store={store} />        // 受控组件
props: { readOnly?, streamMode?, theme?, onOpenPath?, onApprove? }
events: onCursorChange/onSelectionChange/onTextChange（debounced）
```
- 全局单例保留为默认实例（向后兼容），新工厂供宿主多实例
- readOnly 模式（05 分析的高频项）在此接口层落地

**兼容路径**：`useEditorStore` 导出改为"默认实例"；组件接受可选 store prop，缺省用默认实例。

## 架构演进路径总表

| 改造点 | 现状 | 目标形态 | 前置依赖 |
|---|---|---|---|
| 规则插件 | INLINE_RULES 数组 | InlineRuler 注册表 | 失败规则记忆（修 2^n） |
| 装饰层 | props 链 + 独立组件 | DecorationSet 区间查询 | 行级缓存稳定 |
| 语法扩展 | 改核心 | 块/行内双注册 | 规则插件 |
| 事务统一 | 三套写路径 | applyChange 单入口 | — |
| 渲染注册 | switch | 注册表 + 主题 + 注入点 | 渲染层测试网 |
| 性能分层 | 全 DOM | DOM/Canvas 双模式 | 行高模型（01） |
| 状态纯函数 | store 内 | editor-model 纯模块 | — |
| 包形态 | 全局单例 | 实例工厂 + 受控组件 | 事务统一 |

> 逻辑执行顺序（非优先级）：修 2^n（正确性地基）→ 规则插件（扩展地基）→ 事务统一（协作/测试地基）→ 渲染注册 + 装饰层（功能扩展面）→ 状态纯函数（测试深化）→ 包形态（宿主集成）→ Canvas 层（性能终局）。
