# 03 · Markdown 渲染引擎测试门禁体系设计

> 定位：自研渲染引擎（`reference/markdown-editor`）的分层严格门禁方案，纯设计文档。
> 现状基准：unit 25 文件 126 用例（全 core 层）；e2e 18 spec 约 29 用例；CommonMark spec 652 例未接入；
> 渲染层（7 组件）零测试；无属性测试；无 CSS 契约；无性能/内存门禁。

**架构事实（门禁设计的地基）**：

- 引擎是"AST 驱动的编辑渲染器"：`MarkdownParser.parse` → `LineNode[]`（`ast.ts:75-77`），组件按 `LineNode.type` 分派渲染（`BlockRenderer.tsx:61` switch）。
- AST 带完整位置信息：`InlineNode.localOffset/length`（`ast.ts:54-55`）→ 组件输出 `data-token-start/data-token-length/data-sub-offset/data-index/data-line-start/data-line-length`（`InlineRenderer.tsx:201-202`、`MarkdownEngine.tsx:71-73`），构成**DOM ↔ 源码 offset 的无损映射**，是渲染层断言的天然锚点。
- 两套 codeBlockState 计算并存：全量重扫 `computeLineOffsets`（`parser.ts:31-84`）与增量收敛 `updateLinesIncremental`（`EditorStore.ts:179-319`）——**交叉一致性即最强不变量**。
- 确定性：parser 静态无状态（除 LRU 缓存与 id 计数器），store 可整体重置（现有测试 `beforeEach` 模式，`codestate-convergence.test.ts:6-16`）。
- 黑箱入口：`getText()/verifyConsistency()`（`EditorStore.ts:842-855`）与 `window.__CRISH_METRICS__`（`main.tsx:26-30`）。

## 1. 分层架构总表

九类门禁，按"验证深度 × 执行成本"分层。断言强度分三级：

- **黑箱（B）**：只经公开 API/DOM/可观测指标断言，重构安全；
- **灰箱（G）**：经 `data-*` 映射属性/公开指标断言结构契约，允许结构演进但契约稳定；
- **白箱（W）**：断言内部字段/中间态，仅限不变量核心与安全类，需注释"为什么"。

| 门禁类 | 代码 | 内容 | 断言强度 | 执行时机 | 新增用例量级 |
|---|---|---|---|---|---|
| G1 core 不变量 unit | U1 | 现有 126 例加固 + 不变量工具集 | W/G | pre-commit + CI fast | 扩容至 ~200 |

## 3. G2 属性测试（U2）——不变量集设计

### 3.1 随机文档生成器 `DocGen`

确定性：seeded PRNG（mulberry32），`DocGen.generate(seed, options)` 可复现；CI 固定种子集，nightly 扩展种子集。

```
语法片段库（按权重采样）：
  块级：heading(#1..6)、hr(---/***/___)、blockquote(1..4 层前缀)、
        code_fence(``` lang / 无 lang / ````` 超长 fence)、math_fence($$)、
        table(1..6 列，含对齐分隔行 :--- :---: ---:、转义管道 \|、空单元格)、
        列表(bullet/number/task [x][ ]，缩进 0..8 级)、空行、普通段
  行内：bold/italic/bold_italic/strike/mark/kbd/sub/sup/spoiler/checklist/
        link(含嵌套)/image/code(反引号 1..3 重)/math($ / $$)/html 标签
        (b/strong/i/em/s/sub/sup/kbd/mark/s/del 含 style 属性)、
        footnote[^n]、转义 \\*、emoji/组合字符/ZWJ 序列、CJK、tab
  分布控制：
        行数 1..200；行长 1..10_000（其中 5% 概率超 MAX_PARSE_CHARS=10_000 触发截断路径）
        嵌套深度受 20 层 bailout 约束；fence 闭合概率 50%（留悬空 fence 场景）
        片段间随机插入 0..3 空行
```

生成器输出三种形态：`rawText`（可 setText）、`expect 结构`（供语义断言复用：每行 type 期望由"独立重扫"基准函数 `computeLineOffsets` + 朴素行型判定器给出——注意：**生成器不得依赖被测 parser 本身**，行型期望由生成器记录自己放了什么）。

### 3.2 随机操作序列 `OpGen`

```
操作库（权重）：
  insertText：单字符(30) / 多字符(20) / 含\n(15) / 粘贴块≥2行(10) / 含fence文本(5)
  deleteText backward(15) / forward(10)
  deleteSelection(10)   —— 选区由无偏随机 [0..textLength) 对
  setSelection(5)       —— 方向翻转、越界、跨行
  setCursorPos(5)
  undo(15) / redo(8)
  appendText(7)         —— 流式快速通道
序列长度：50..200 步；每步位置在 grapheme 边界对齐（snap）与原始随机之间随机选择，
以同时覆盖"用户合法输入"与"程序化越界输入"两类路径。
```

### 3.3 每步不变量清单（`invariants.ts`，每步全量断言）

| # | 不变量 | 断言实现 | 对应风险 |
|---|---|---|---|
| I1 | token 覆盖守恒 | 每行 inlineTokens 递增不重叠、覆盖 `[0,line.length)`、`raw` 拼接==lineText（table 递归） | offset 漂移、token 丢字 |
| I2 | offset 一致 | `verifyConsistency()`；`lineOffsets.getOffset(i)`==逐行累加；`findLineIndex(getOffset(i))==i`；`lineOffsets.toArray()` 与 lines 长度同步 | SegmentTree 增删分裂错位 |
| I3 | textLength 一致 | `textLength == lines.join('\n').length`；`cursor/selection ∈ [0,textLength]`；`lines` 至少 1 行 | 双轨 length 漂移 |
| I4 | fence 与独立重扫一致 | 每步后 `store.codeBlockState` == `MarkdownParser.computeLineOffsets(getText()).codeBlockState`（含 fenceLines 单调性） | 增量收敛提前终止 |
| I5 | undo 恒等 | 任一步后 `undo()` 得回上步文本与选区；`undo∘redo` 恒等；连续 undo 至空栈 == setText 前快照 | undo 栈记录错误 |
| I6 | 图素往返 | 对 `cursorPos`：`findNext(findPrev(p))`、`findPrev(findNext(p))` 幂等；`deleteText` 后文本 == 原文本移除一个图素（对 `s==e` 时） | 半代理字被删 |
| I7 | parse 确定性/不崩溃 | 任意文档 parse 不抛异常；同输入两次 parse 结构相等（忽略 id）；fence_start/end 成对出现 | 解析器爆炸 |
| I8 | 缓存语义透明 | 缓存命中分支（astCache 预热后）与冷缓存 parse 产出 token 序列等价 | LRU 返回脏 AST |
| I9 | 长行不变量 | 行长 >10_000 时：截断指示（`truncation-indicator` 出现）且截断点前后 raw 拼接 == 原文本 | 截断丢字符 |

**强度**：I1–I5 每步全量；I6–I9 每 10 步或事件触发时抽样。断言失败必须打印到步号+种子+最小化路径（记录操作前缀，bisect 到首败步）。

**用例形态**（`fuzz-editor-state.test.ts` 等）：每 `it` 一组 `(seed, 序列长度)`，CI 固定 10 组种子；nightly `Fuzz` 类 100 组。超时预算：单组 <30s（200 步 × 每步 O(lines) 不变量，文档 ≤200 行）。

## 4. G3 渲染层 RTL（R1）

**环境**：新增 devDependencies：`@testing-library/react`、`@testing-library/jest-dom`、`jsdom`。vitest `environment: 'jsdom'` 按文件头注释开启。

## 5. G4 行为契约（R2）

**目标**：把 store/parser 的"用户可感知行为"固化为黑箱契约，与实现解耦——重构可动、语义不动。

**`store-edit-contract.test.ts`**：插入/删除/选择覆盖的文本终态（黑箱断言 `getText()`）；`insertText` 覆写选区、`deleteText` 图素语义、`appendText` 光标仅在尾部时推进（`EditorStore.ts:586`）；跨行删除的合并行行为。

**`store-undo-contract.test.ts`**：undo/redo 恢复文本与选区（`devil.test.ts` 已示范的语义，扩为契约矩阵：单字符/多字符/换行/选区删除/连续输入合并/新编辑清空 redo——**只断言黑箱结果，不断言 `undoStack.length`**，`undo.test.ts:32` 为现存白箱反例，移入 `unit/` 白箱专档或改造为黑箱）。

## 6. G5 CommonMark 符合度（C1）

### 6.1 组织方式

- 离线编译 `spec.txt` → `tests/commonmark/spec.json`：`[{section, exampleNo, markdown, html, line}]`（652 例）。编译脚本 `scripts/compile-commonmark.mjs`（node 一次性产物，入库；`spec.txt` 由 `compare/markdown-it/test/fixtures/commonmark/spec.txt` 拷贝为 `tests/commonmark/spec.txt` 以自包含）。
- 用例生成：vitest `describe(section)` + `it('example N')` 惰性注册（与 markdown-it `generate` 同构，`test/cmspec/commonmark.test.mjs:31-39`）。

### 6.2 断言策略：AST 语义级

引擎输出是 AST 而非 HTML，直接比 HTML 将产生大量"渲染差异噪音"。设计三层判定：

1. **语义序列化器 `astToHtml.ts`**（测试工具，独立于引擎）：把 `MarkdownDocument` 按语义折叠为近似 HTML——线型→块标签、行内 token→span/语义标签、`raw` 拼接为文本节点；对 `content != raw` 的 token 只保留 content（语义等价折叠）。**自检**：对 652 例全部 example 的 `markdown` 输入 parse + 序列化不崩溃、无缺失段。
2. **判定三级**：
   - `PASS`：`astToHtml(parse(md))` == 期望 HTML（规范化空白后）；或引擎明确以"文本保真"定义的子集（见下）。
   - `KNOWN_FLAW`：语义可达但细节偏差（如 reference link 未解析、HTML block 原文直出）——记入 baseline，按 section 分类；
   - `FAIL`：不在以上两类。
3. **文本保真次级断言**（对所有 652 例无条件执行）：解析后 AST 的 raw 拼接 == 输入原文（token 覆盖守恒全局版），保证即使语义不支持也不丢字、不崩溃。

### 6.3 通过率门槛机制

- `baseline.json` 记录每例分类 + 引擎版本 + 日期；CI 流程：
  1. 全量跑 652 例 → 与 baseline 对比；
  2. **禁止回归**：PASS→KNOWN_FLAW/FAIL 一律报错（新缺陷必须修复或显式改 baseline 并附原因）；
  3. **门槛线**：`PASS 数 ≥ baseline.PASS` 且 `PASS/total ≥ 基线比例`；核心子集（标题/段落/强调/代码围栏/列表/块引用/转义 等 section）要求 PASS 100%（阈值 0.99，缺省计入 KNOWN_FLAW 需人工评审）；
  4. baseline 更新须附 diff 说明，走评审。
- **执行时机**：CI mid 跑全量 652（单例 <50ms，总计 <60s，可行）；nightly 增加"浏览器真实渲染比对"（G7 金样对核心子集抽样 40 例）。
- **门槛值**：首次接入基线（预计 40–55% 通过，因引擎未实现 reference link/autolink/HTML block 语义）；三个月内目标 ≥60%；核心子集 0.99 硬门槛。

## 9. G8 性能门禁（P1）

### 9.1 指标采集基建

- 现有 `__CRISH_METRICS__`（`main.tsx:26-30`）扩展（向后兼容）：增加 `frameStats`（rAF 采样：每帧耗时数组/滚动帧 p95/p99）、`longTasks` 计数、`parseDuration` 累计。

- **注意**：CI 虚拟化环境无 GPU、无真实刷新率，帧率门槛分档（见下）。

### 9.2 断言方法与门槛值

| spec | 场景 | 指标 | 门槛 |
|---|---|---|---|
| `frame-rate.spec.ts` | 1 万行文档：滚动 2000px、连续输入 100 字符、切换光标行 | rAF 帧间隔 p95/p99（采样 ≥300 帧） | 目标档位：60fps → p95 <16.7ms；120fps → p95 <8.3ms；140fps → p95 <7.1ms。**探测刷新率**（`matchMedia`/rAF 校准）取 min(标称, 实测) 档位；CI 无显示器时降一档执行（≥30fps 硬门槛 p95<33ms），本地/nightly 真机全档 |
| `long-task.spec.ts` | 上述场景并跑 | `PerformanceObserver('longtask')` 计数 | 单次滚动/输入过程 0 长任务（>50ms）为软门槛 warn；>2 个长任务 fail |
| `layout-thrash.spec.ts` | 全场景 | `__CRISH_METRICS__.layoutThrashCount` 采样；帧内 getBoundingClientRect 次数 | 光标移动一帧内 ≤8 次（对照 `main.tsx:35` 的 5 次哨兵语义上浮）；滚动连续 1s 内总调用 < 3000；且 console 无 `[CRISH METRICS] Layout Thrash Detected!` |
| `parse-budget.spec.ts` | 节点维 parse | `MarkdownParser.parse` 大文档耗时（对比 `parser-redos.test.ts` 的 500ms/800ms 上限） | 万行文档 parse <500ms；5 万字符单行 <150ms；输入 1 字符触发重parse 的增量耗时 <16ms（rAF 帧内完成） |
