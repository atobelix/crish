## 0. 结论摘要

**稳定性**：652 用例 0 崩溃、23ms 跑完——单行解析无栈溢出、无限循环（深度剪枝 + 2000 字符规则窗口 + 10000 字符行内截断三件套兜底）。

**严重度分级发现**：

| 级别 | 发现 | 位置 |
|---|---|---|
| **CRITICAL** | 未闭合 HTML 起止标记（`<b>x` 重复）触发 **2^n 指数爆炸**，88 字符行长耗时 11.4s，深度剪枝（parser.ts:720）结构性失效 | parser.ts:956-1008 |
| HIGH | 6 项 CommonMark 语法缺失：Setext、缩进代码块、引用链接定义、自动链接、HTML 块级、实体引用 | 见 §2 |
| HIGH | 额外语法缺口：**下划线强调（`_x_`/`__x__`）整族缺失**（INLINE_RULES 无任何 `_` 规则）；`foo\n---` 被误判为 hr（应为 Setext H2）；`~~~` 围栏不支持；围栏关闭行不校验长度/信息串 | §2.7、§7 |
| MEDIUM | 行内规则顺序耦合：链接 title 被吞进 URL、`[a](b c)` 非法目标放行、`<u>` 被解析成 sub | §4 |
| MEDIUM | 覆盖守恒两处违例：代码块内空行产生 `' '` token（length 1 > 行长度 0）、hr 行 token 不覆盖 raw | §6 |
| LOW | 缓存命中复制 cached 节点导致**行 id 重复**；`shiftInlineOffsets` 是死代码（offset 模型中途变更痕迹） | §5 |
| LOW | 长行 >10000 字符时行内语法整体截断（链接/强调在 10000 之后不解析） | §3.1、§6 |

**主结论**：引擎的"行级 + 内联递归扫描"架构在典型输入上性能与稳定性达标，但存在一个可被 200 字符文本触发的指数级 DoS 空洞；6 项语法缺口全部可在行级模型的既有接入点补齐，无需改写状态机；CommonMark 套件可通过"AST→HTML 忠实投影"方案接入且不降难度。

## 1. CommonMark 652 用例量化方案

### 1.1 spec.txt 用例格式

```text
```````````````````````````````` example
  →foo→baz→→bim        ← 输入 Markdown（→ 代表制表符）
.
<pre><code>foo→baz→→bim    ← 期望输出 HTML
</code></pre>
````````````````````````````````
```

- 用例容器：32 个反引号围栏 + 行尾 ` example`；正文用 `.` 单行分隔 markdown 输入与期望 HTML 输出；`→` 表示制表符（读取时替换为 `\t`）。
- 计数实证：`rg -n '^\`{5,} example$'` 命中 **652** 个用例容器。

### 1.2 提取器设计（阶段二实现，约 60 行）

1. 按 `^`+`{32} example$` 切块（用长度锚点而非精确 32，兼容未来版本）；
2. 块内按 `/^\.\s*$/m` 分割为 `md` 与 `html` 两段；
3. `md` 与 `html` 中 `→` → `\t`；
4. 输出 `{ section, number, markdown, expectedHtml }[]`（节名由前一个 `# Section` 标题注入）。

### 1.3 AST→HTML 投影渲染器（断言载体，约 150 行）

引擎产出的是 `MarkdownDocument`（行数组），不是 HTML。要跑 652 用例必须做一层投影。**投影只允许"一对一映射"，不允许任何语义修复**：

| LineNode 类型 | 投影规则 |
|---|---|
| `body` | 连续 `body` 行合并为一个 `<p>`，行间软换行 `\n` |
| `heading` | `<h{headingLevel}>` + 行内投影 |
| `hr` | `<hr />` |
| `code_fence_start/end`、`code` | 围栏首尾行剔除，中间行按行内 `text` 内容拼接为 `<pre><code>…</code></pre>`（`\n` 结尾，代码内容不再二次转义） |
| `math_*` | 投影为 `<pre><code>`（math 是扩展语法，CommonMark 无对应，套件不会覆盖） |
| `blockquote`（按 blockquoteLevel 分组） | 连续同层行包 `<blockquote><p>…</p></blockquote>`，层数嵌套 |
| `table_row/table_separator` | `<table><tr><td>…`（GFM 扩展，套件不覆盖，但管道行误判会在此暴露） |
| `list_bullet/list_number/list_task`（按 listIndent+listPrefix 分组） | `<ul>/<ol>/<li>`，嵌套按缩进——**这是投影里唯一需要启发式的部分**，因为引擎没有列表容器状态；启发式规则写死在投影器并记为已知偏差 |

| InlineNode 类型 | 投影规则 |
|---|---|
| `text` | HTML 转义（`& < >`，引用链接的 `&` 转义与实体解码冲突见 §2.6） |
| `bold` | `<strong>`，`italic` → `<em>`，`strike` → `<del>`，`mark` → `<mark>`，`code` → `<code>`，`sub/sup/kbd/spoiler` 按名 |
| `link` | `<a href="{url}">{content}</a>` |
| `image` | `<img src="{url}" alt="{alt}" />` |
| `html_tag` / `html_element` | **raw 原样透传**（不转义）——与 CommonMark "raw HTML 通过" 一致 |
| `table_pipe/table_cell/heading_prefix/list_*/blockquote_prefix` | 结构性 token：投影时跳过，不产出文本（与第 1.4 条归一化不冲突，见 §6 守恒定义） |

### 1.4 断言与归一化（防作弊条款）

- **允许的归一化**（仅限 HTML 字符串层、不涉及引擎输出）：块引用空 `<blockquote></blockquote>` 的 `\n` 折叠（markdown-it 的 specsplit 也做此归一化，spec 本身允许）；行尾空白剥离；`&quot;` 与 `"` 等价（spec 0.31.2 起）。
- **禁止的归一化**：任何作用于引擎产出物的修复——禁止在投影器里补 Setext/缩进代码/引用链接/自动链接/实体解码；禁止在比对前把引擎的 `<p>a</p><p>b</p>` 折叠成 `<p>a\nb</p>`；禁止忽略差异（无 diff 白名单）。
- **断言**：`expect(project(doc)).toBe(expectedHtml)`，逐用例；失败收集 `{section, number, diff}`。
- **计分**：按 spec 章节（Thematic breaks / ATX headings / Setext headings / Indented code / Fenced code / HTML blocks / Link reference definitions / Paragraphs / Block quotes / Lists / Code spans / Emphasis / Links / Images / Autolinks / Raw HTML / Hard breaks / Entity refs / Backslash escapes / Tabs）输出"节 × 通过数/总数"表，作为语义差距的量化基线。
- **难度保证**：与 markdown-it 官方 commonmark 模式跑同一 spec 得 652/652（它不做 GFM 扩展），因此引擎的通过率可公平对比；投影器若有语义修复嫌疑，可用"反向抽查"（对随机 20 例手写比对投影器输出的 HTML 与 spec 期望）审计。

### 1.5 预期结果分布（基于 §2 缺口推演）

- **大概率全过的节**：Tabs（制表符仅出现在缩进代码中，会因缩进代码缺失而挂——预计 Tabs 节全挂）、Backslash escapes（基本实现正确）。
- **预计接近全挂的节**：Tabs（缩进代码）、Indented code、Setext headings、Link reference definitions、Autolinks、Entity refs（13 例左右）、Hard breaks（行模型无跨行 `<br>`）。
- **预计部分通过的节**：Fenced code（`~~~` 与关闭行长度校验缺失）、HTML blocks（行级 raw 无状态）、Emphasis（`*` 族通过、`_` 族全挂）、Links（行内式通过、引用式全挂）、Lists（行内标记通过、容器/延续/松散列表挂）。
- 预估总通过率 **40%~55%**，运行后以实际数字更新基线。

## 2. 六项缺语法实现方案

### 2.1 Setext 标题（`===` / `---` 下划线）

**现状**：`foo\n===` 解析为两行 body（实证 SETEXT）；`foo\n---` 解析为 body + hr（实证 HRSETEXT，`---` 被 parser.ts:409 的 hr 正则 `^(\s*[-*+_]){3,}\s*$` 吞掉）。CommonMark 期望：`foo\n===` → `<h1>foo</h1>`，`foo\n---` → `<h2>foo</h2>`；`===`/`---` 仅在紧跟前一行段落时成为下划线，独立成行且前行为空时分别是正文/`<hr />`。

**接入点**：`parseNormalLine`（parser.ts:353）。当前行判定顺序为 hr（:408）→ ATX（:417）→ table_separator（:432）→ 列表（:449）。Setext 需要**前一行上下文**，而 `parseLine` 是行本地的——这正是"行级模型"的第一个结构性缺口，需要预扫描。

**实现方案**：
1. 在 `parse()`（parser.ts:19-29）增加一次性预扫描 `computeLineContexts()`（与 `computeLineOffsets` 并列），产出与行数组平行的上下文数组：`prevLineType`（上一行的 lineType 与 blockquoteLevel、listIndent）。
2. 在 hr 判定（:408）之后、ATX（:417）之前插入 Setext 判定：`/^(?:=+|-+)\s*$/` 且 `prevLine.type === 'body'` 且 `prevLine.blockquoteLevel === 当前行 blockquoteLevel` 且 `prevLine.listIndent === undefined`（列表项内不允许 Setext 下划线，CommonMark 列表项是独立容器）→ 行类型 `setext_underline`，并回写上一行为 `setext_heading_1/2`（LineType 扩展，AST 是纯函数数组，回写安全）。
3. `===` 与 `---` 的优先级：先 hr（前一行非 body）、再 Setext（前一行 body）、再 table_separator（GFM 表格，当前启发式：含 `|`）。
4. 块引用内 lazy continuation（`> foo` 后裸 `===`）暂不支持（CommonMark 允许），记为已知偏差，测试只覆盖同层。

**冲突点**：与 hr（:408-415）同正则前缀；与 table_separator（:432-447）同 `-+` 字符；块引用前缀剥离（:386-402）之后的行才能判定。注意 `---` 在 GFM 表格头下的语义（表格分隔行）由 table_separator 先判，不冲突（表格分隔行必含 `|`）。

**测试用例**：`foo\n===` → h1；`foo\n---` → h2；`\n===\n` → 正文 + 正文；`- foo\n===` → 列表 + 正文；`> foo\n> ===` → 块引用内 h1。

### 2.2 缩进代码块（4 空格）

**现状**：`    x` 解析为 body（实证 INDENT）。CommonMark 期望：块起始的 ≥4 空格（tab 停靠 4）行构成 `<pre><code>`，块不能打断段落，列表容器内 4 空格是延续内容不是代码。

**接入点**：`computeLineOffsets`（parser.ts:31-84）——缩进代码是**跨行状态**（连续缩进行合并成一个块），与 fence 同构，必须进状态机。`parseNormalLine` 的 `pos`（blockquote 前缀长度，:386-392）之后加缩进剥离。

**实现方案**：
1. `computeLineOffsets` 增加 `indentCode` 布尔状态：strip 掉块引用前缀后，若行以 ≥4 空格（含 tab 按停靠 4 展开）开头、不在 fence/math 状态、且"上一行不是 body/table_row/list 项"→ 置 `indentCode`，该行及后续连续缩进行标记 `code_indented`；空行保持状态（CommonMark：缩进代码块内允许空行）。
2. CodeState 增加 `'indent_code'`，`parseLine` 复用 `parseCodeLine`（:246）输出。
3. tab 处理：`computeLineOffsets` 目前无 tab 展开，需实现停靠 4 展开函数（spec §Tabs：`→` + 2 空格 = 2 个停靠位置 = 8 列 < 4? 反例：`  →foo` 是 2+4=6 列 ≥4 → 是代码）。

**冲突点**：
- 与列表：`- foo` 的延续行 `  bar`（2 空格）不是代码（缩进 <4 ✓ 天然排除）；但 `    - nested`（4 空格）CommonMark 是嵌套列表而非代码——行级模型无列表容器状态，**必须先判列表再判缩进代码**，而当前列表判定在 `parseNormalLine` 内联（:449-506），无法前置——因此缩进代码判定需要"前一行是列表项"的上下文（复用 2.1 的 `computeLineContexts` 预扫描）。
- 与块引用：`>     code` → 块引用内缩进代码（块引用前缀剥离后判定 ✓）。
- 与段落打断规则：`para\n    code` → CommonMark 中缩进代码**不能**打断段落，`    code` 是段落延续——预扫描的 prevLine 判定必须处理。
- 与表格行：`| a |` 缩进 4 的表格行（GFM 允许缩进表格）——优先表格。

**测试用例**：spec Tabs 节 5 例、Indented code 节全部约 24 例；`para\n    code` → 单段落；`- item\n    cont` → 列表延续。

### 2.3 引用链接定义 `[id]: url`

**现状**：`[foo]: /url` 解析为 body 文本，`[foo]` 不解析为链接（实证 REF）。CommonMark 期望：定义行**零输出**，后续 `[foo]`（引用式）、`[foo][]`（折叠式）、`[foo][bar]`（全引用式）解析为链接。

**接入点**：`parse()` 预扫描（与 2.1 同一预扫描通道）收集定义表；`INLINE_RULES`（:597-637）在 link 规则（:603-605）失败后增加引用解析规则。

**实现方案**：
1. 预扫描：逐行 strip 块引用前缀后匹配 `/^\[([^\]]+)\]:\s*(<[^<>]*>|\S+)(?:\s+("(?:[^"\\]|\\.)*"|'(?:[^'\\]|\\.)*'|\((?:[^)\\]|\\.)*\)))?\s*$/`；label 归一化（CommonMark 3.1.4：去首尾空白、内部空白折叠为单空格、ASCII 大写折叠小写、`&` 实体解码后归一）后入 `Map<normalizedLabel, {url, title}>`。
2. 定义行标记为新 LineType `reference_definition`（AST 新增行类型，投影器输出空串）——保持行级 AST 完整（渲染/统计可跳过）。
3. 行内解析：INLINE_RULES 中在 footnote 规则（:607）之后、code 规则（:608）之前插入 `reference` 规则：`^\[((?:[^\]\\]|\\.){0,2000})\]`，匹配后按三种形式查表——`[label]`（label 直接查）、`[label][]`（label 查）、`[label][ref]`（ref 查）；查到则产出 link token（url/title 来自定义表），查不到按原样文本。
4. 定义行内不允许行内语法（CommonMark：定义行是块结构）——LineType 早退，不进 parseNormalLine 内联。

**冲突点**：
- footnote `[^x]`（:607）必须先于引用规则（`[^x]` 的 label 归一化含 `^`，CommonMark 无 footnote，扩展优先）；checkbox `[x]`（:606）必须先于引用（`[x]` 的引用查表几乎不会命中，但顺序要显式保证）。
- 折叠式 `[foo][]` 会与 link 正则 `\]\(` 竞争：link 规则先试，失败后引用规则试。
- 引用式链接与图片 `![foo][id]`：image 规则（:599-601）需同步加引用分支。

**测试用例**：spec Link reference definitions 节约 30 例；`[foo]: /url "title"` 三引号形式；`[Foo]: /a` + `[foo]` 大小写折叠；`[foo][]`；`![alt][id]`；未定义 `[unknown]` 保持文本。

### 2.4 自动链接 `<url>` / `<email>`

**现状**：`<http://example.com>` 整个成为 text token（实证 AUTOLINK）——因为 HTML 分支（:847-905）把 `http` 当 tagName 找 `</http>` 失败后落入文本。CommonMark 期望：`<http://example.com>` → `<a href="http://example.com">http://example.com</a>`；`<foo@bar.example.com>` → 邮件链接。

**接入点**：`scanTokens` HTML 分支（:847）之前插入自动链接判定（比 htmlMatch 更早，且早于 INLINE_RULES 的 html_tag 规则 :635）。

**实现方案**：
1. 在 `sub.startsWith('<')` 分支内、htmlMatch 之前试两个正则：
   - URI：`^<([a-zA-Z][a-zA-Z0-9+.-]{1,31}:[^<>\x00-\x20]*)>`（scheme 2~32 字符，CommonMark 6.9）
   - 邮件：`^<([a-zA-Z0-9.!#$%&'*+/=?^_`{|}~-]+@[a-zA-Z0-9](?:[a-zA-Z0-9-]{0,61}[a-zA-Z0-9])?(?:\.[a-zA-Z0-9](?:[a-zA-Z0-9-]{0,61}[a-zA-Z0-9])?)*)>`
2. 命中 → 产出 link token（type `link`，url = 组 1，content = 组 1）；scanTokens 主循环推进。
3. 内容内不能有空格/`<`/`>`（正则已保证）；`\` 转义不适用于自动链接内部（CommonMark 不处理）。

**冲突点**：
- `<span>`、`<div>` 等真 HTML 标签不含 `:` scheme，自动链接正则不命中 → htmlMatch 路径不受影响。
- 邮件正则的 `+`/`-` 字符集与 `<b>` 等单字符标签名无交集。
- **关键边界**：`<http://x>` 目前被 htmlMatch 当作 tagName `http` 做 `text.toLowerCase().indexOf('</http>')` 全行扫描——即使不实现自动链接，也该修 htmlMatch 的 tagName 校验（§4.3），否则 `http://` 形态文本触发无谓的 O(n) 扫描。

**测试用例**：spec Autolinks 节约 20 例（URI 含 `?`/`#`/端口；邮件含 `-` 连字符；`<foo+bar@baz>` 通过、`<foo bar@baz>` 不通过、`<foo@baz.>` 不通过、含 `*` 的 `<>` 不通过）。

### 2.5 HTML 块级

**现状**：`<div>\ncontent\n</div>` 解析为三行 body（html_tag / text / html_tag，实证 HTMLBLOCK）。CommonMark 期望：7 类 HTML 块（type 1：`<pre>`/`<script>`/`<style>`/`<textarea>`；type 2：`<!--`；type 3：`<?`；type 4：`<!`；type 5：`<![CDATA[`；type 6：块级标签名单；type 7：完整开闭标签对），type 1-6 可打断段落，type 1-5 到匹配闭合或空行终止，type 6 到空行终止，type 7 单行。

**接入点**：`computeLineOffsets`（跨行状态，与 fence 同构）+ 新 CodeState `'html_block'`。

**实现方案**：
1. `computeLineOffsets` 增加 html 状态：行首（≤3 空格）匹配 7 类正则之一 → 进入 `html_block`；type 1-5 遇匹配闭合标签或空行退出，type 6 遇空行退出，type 7 行尾退出；块内行一律标记 `html_block`。
2. `parseLine` 对 `html_block` 早退：整行作为单个 `html` token（raw = 行原文），不做行内解析（HTML 块内 CommonMark 不做任何行内处理——与代码块一致）。
3. 投影器把连续 `html_block` 行按行拼接原样透传。

**冲突点**：
- 与 ATX 标题/Setext/缩进代码：HTML 块可打断段落，判定优先级高于"段落延续"逻辑（预扫描中 prevLine 是 body 时仍需允许 HTML 块开始——CommonMark 6.6：type 1-6 可打断段落，type 7 不行）。
- 与 fence：`<pre>` 块内出现 ```` ``` ```` 行——fence 状态与 html 状态互斥，需先 html 后 fence（或同一状态机内互斥分支）。
- 与块引用：`> <div>` → 块引用内 HTML 块（前缀剥离后判定）；块引用 lazy continuation（`> <div>` 后裸 `</div>`）暂不支持。
- 与行内 html_element（:876-901 递归）：`html_block` 状态行不走行内，天然避让；但块外单行 `<div>x</div>` 仍走行内分支（CommonMark 中这是 type 6 的块——单行开闭标签对 + 段落），属于行内/块级判定交叉点，需要"行首块级判定优先"的次序保证。

**测试用例**：spec HTML blocks 节约 20 例（7 类各至少 1 例；`<div>` 后普通段落行被并入块直到空行；type 7 只吞一行；`<pre>` 内空行不退出）。

### 2.6 实体引用 `&amp;` `&#35;` `&#x22;`

**现状**：`&amp; &#35; &#x22;` 全部保持字面文本（实证 ENTITY）；`\&amp;` 与 `&amp;` 无区别（实证 ESCENT）。CommonMark 期望：`&amp;` → `&`、`&#35;` → `#`、`&#x22;` → `"`、`&copy;` → `©`；未定义实体（`&ampx;`）保持字面；反斜杠转义阻止解码。

**接入点**：`scanTokens` 的文本累积路径（`currentRawText`/`currentContentText`，:729-741）。解码只发生在**content**，raw 保持原文（投影器用 content 渲染文本，raw 用于守恒校验）——这与现有 raw/content 双轨模型天然契合。

**实现方案**：
1. 新增 `decodeEntity(str): string`：先匹配 `&#x([0-9A-Fa-f]{1,6});` / `&#([0-9]{1,7});`（数值），再查命名表（HTML5 实体子集：spec 0.31.2 附录只要求约 30 个命名实体，`amp lt gt quot apos nbsp copy reg trade hellip mdash ndash ...`；全表 2231 个可从 micromark-util-decode-string 抽取，但套件只测子集）。
2. 文本 token 产出时（`flushText`，:729）对 content 解码，解码条件：该文本段的 raw 以 `&` 开头且不以 `\` 开头（转义阻止解码）。
3. 解码必须发生在**规则匹配之后**——`&` 不在任何规则起始符中，天然满足；解码字符不回流进扫描循环（token 已定型）。
4. 代码 span、数学、raw HTML 内**不**解码（CommonMark：code span 内实体保持字面）——`isCodeContext`/`isMathContext` 分支（:743-745, :830-836）内的文本段跳过解码；html_element 的 content 透传不解码。

**冲突点**：
- 与 §1.3 投影器的转义规则：投影器对 text 的 content 做 `& < >` 转义——若 content 已解码为 `&`，转义后变 `&amp;` ✓ 恰好与 spec 期望一致（spec 输出为转义后的 HTML）；若未解码保持 `&amp;`，再转义一次会变 `&amp;amp;` ✗。**因此投影器必须用 content 而非 raw 渲染文本**——这条已在 §1.3 约定，且要在守恒测试（§6）里用 `\&amp;` 反向用例防回归。
- 与链接 URL：CommonMark 要求链接目标内实体解码（`[a](url?x=1&amp;y=2)`）——link token 的 url 字段需同解码。
- 与 `&` 的 ESCAPABLE_PUNCTUATION（:753）：`\&` 转义已处理，仅需保证解码层不重复处理。

**测试用例**：spec Entity refs 节约 13 例（含 `&#35;` `&#x22;` 混合、`&ampx;` 未定义、`\&amp;` 转义、code span 内字面）。

### 2.7 补充：下划线强调整族缺失（第 7 个缺口）

**现状**：`_italic_ __bold__ foo_bar` 全部为 text（实证 UNDSCORE）——INLINE_RULES（:597-637）从第 609 行 `code` 到第 634 行 `spoiler` 之间**没有任何 `_` 起始规则**。CommonMark 期望：`_x_` → `<em>`、`__x__` → `<strong>`，且受围挡规则（Rule 9/10）约束：词内下划线不解析（`foo_bar_baz` 保持字面）、下划线两侧空白/标点围挡才有效。

**实现方案**：在 `bold_italic`/`bold`/`italic` 规则（:609-611）后追加 `_` 族三规则（`___`/`__`/`_`，close 同 start），并实现围挡校验（开边界：start 后不可直接跟空白；闭边界：close 前不可直接是空白；词内规则：两侧字符均为字母数字时禁用）。围挡校验同时修正现有 `*` 族的对应偏差（`* hello*` 目前会被列表吞掉——实证 STARSP 显示 `* hello*` 被 list_bullet 规则 :470 抢先，CommonMark 中它也是列表项所以偏差不在强调而在列表内容）。

**测试用例**：spec Emphasis and strong emphasis 节约 65 例的 `_` 部分；`foo_bar_baz`、`a__b__c` 词内不解析；`_foo_`、`__foo__`、`___foo___` 三层；`_foo bar_` 空格围挡。

## 3. 递归扫描最坏复杂度：scanTokens 的退化路径

### 3.1 实证数据（完整曲线见附录 A.4/A.5）

| 输入 | 长度 | 耗时 |
|---|---|---|
| `'*a'.repeat(20000)` | 40000 | 25ms（线性，`*` 成对闭合） |
| `'~~a'.repeat(16000)` | 48000 | 4ms（线性，成对闭合） |
| `'<div>'.repeat(160000)` | 800000 | 23ms（近线性，closeIdx 失败路径 O(n)/次但被 10000 截断窗口限定） |
| `'<b>x'.repeat(12)` | 48 | 21ms |
| `'<b>x'.repeat(16)` | 64 | 179ms |
| `'<b>x'.repeat(20)` | 80 | 2787ms |
| `'<b>x'.repeat(22)` | 88 | **11402ms** |
| `'<b>x'.repeat(8)` | 32 | scanTokens 调用数 = 256（=2^8） |
| `'<u>z'.repeat(12)` | 48 | 调用数 = 4096（=2^12） |
| `'<b>x'.repeat(2500)`（10000 字符） | 10000 | **超时挂死（>180s）** |

**结论：`<b>` 系未闭合 HTML 起止标记链触发 2^n 指数爆炸，且随 n 增长无上界**——`<b>x` × 22 共 88 字符即需 11.4s，约 200 字符（×50）即不可恢复挂死。

### 3.2 根因（代码级）

1. **规则递归无条件**：parser.ts:956-1008，`r.start && sub.startsWith(r.start)` → `scanTokens(text, i, localOffset, r, depth+1)`（:988）。`<b>`（:614）、`<strong>`、`<i>`、`<em>`、`<s>`、`<del>`、`<mark>`、`<u>`、`<ins>`、`<kbd>`、`<sub>`、`<sup>`（:614-625）共 **12 个起止式规则**均无关闭时走此路径。
2. **失败后整段重扫**：对 `<b>x` 链，位置 p 的 `<b>` 尝试在 p+3..EOF 找不到 `</b>`（:798-828 全文本线性扫描）返回 null，然后父级把 `<b>` 当 html_tag 消费；下一个 `<b>` 位置再开一次**同规则**的递归尝试——每次尝试的窗口是"当前位置到行尾"，窗口单调不缩短（无失败记忆），形成 2^n 分支树（每多一个 `<b>` 节点数翻倍，实证调用数恰好 2^n）。
3. **深度剪枝结构性失效**：parser.ts:720 `if (depth > 20) return null`——它只把第 21 层及以下的调用剪成 O(1) 空转，但 2^n 树的**节点数本身仍在深度 ≤20 层内爆炸**（n=22 时剪掉的只有 C(22,21)+C(22,22)=23 个节点，实测 11.4s 说明剪枝几乎没有效果）。注释"prevent O(N^2) / O(2^N) nesting bomb"声明的目标并未达成。
4. 其他防护的真实效果：
   - 2000 字符规则窗口（:841-844）：只限制正则扫描，**不限制** close 查找循环（:798 对全文本操作）——`*` 族的"成对闭合"让它线性，`<b>` 族不受此约束。
   - 10000 字符行内截断（:511-528）：把单行扫描上限钉在 10000 字符——`<b>x` × 2500 恰为 10000，挂死；这是**防护还是漏洞窗口**取决于视角：10000 字符的恶意行足以挂死单线程编辑器数分钟。
   - 失败字符 run 合并（:1012-1024）：仅对 `*~=_`` 生效，`<` 不在合并表——`<b>` 链每个标记单独触发递归。

### 3.3 修复方案（按优先级）

1. **失败规则记忆（首选，O(规则数×行长度)）**：向 `scanTokens` 传递 `failedRules: Set<rule>`；规则 X 在位置 p 尝试失败（返回 null）后，把 X 加入集合——其后的任何位置 q>p 对 X 的尝试窗口 (q,EOF) ⊂ (p,EOF)，闭包不可能出现，直接返回 null。`<b>` 链从此变为每规则一次全行扫描，2^n 分支树坍缩为 O(n)。改动约 15 行，可单元测试验证（调用数从 2^n 降为 O(n)）。
2. **预扫描 close 位置（备选）**：每行进入 scanTokens 前对 12 个起止式规则各做一次 `indexOf` 预扫描（HTML 分支已经做了 closeIdx 扫描，可复用其结果缓存），仅当 close 存在于 start 之后才允许递归——与方案 1 等价但侵入点不同。
3. **降低深度上限至 8（兜底）**：2^8=256 次调用×O(n) 扫描 = 可接受上界；同时保留方案 1/2 作为正确性修复（深度上限只是 DoS 闸门，不是语义修复）。
4. **回归测试**：`'<b>x'.repeat(30/60/100)` 断言耗时 <100ms 且调用计数线性；纳入 parser-redos.test.ts（:1-38 现有三例均未覆盖此形态）。

### 3.4 与 micromark 状态机的差距

- **micromark**（`packages/micromark-core-commonmark/dev/lib/`）：每个构造（code-fenced、attention、html-flow…）是 `start(code)` 状态函数链，`effects.consume` 每码元恰好消费一次，**无回溯**；lookahead 通过 `code` 窥视（O(1)）与工厂循环（factory-label/factory-destination 只遍历自己的输入）；状态切换由 `ok`/`nok` 回调显式推进。`attention.js` 用分隔符栈 + 后处理匹配（线性），不存在"失败后重扫"路径。
- **markdown-it**（`parser_block.ts:56-119`）：ruler 链每个规则带 `silent` 试判，行级推进 `state.line`，规则失败不回溯；`rules_inline/emphasis.ts` 用 `scanDelims` + `state.delimiters` 栈（线性）；`rules_inline/link.ts` 的 label 扫描有长度上限。它同样没有 2^n 路径。
- **本引擎的差距本质**：递归式"试错 + 重扫"范式与状态机/栈式范式的结构性差异——不是常数差距，是 2^n 与 O(n) 的差距。

### 3.5 是否值得改状态机：改造边界

- **不值得整体重写为 micromark 式状态机**：引擎的核心价值在"行级 AST + 偏移量"模型（编辑器增量渲染依赖），且 6 项语法缺口、缓存 id 问题、守恒违例都可在现状架构内修复；整体重写会把 652 用例的 23ms 与 50k 缓存架构全部推倒，风险收益比极差。
- **值得做的"状态机化"边界**（局部改造，见 §3.3）：
  1. 行内扫描的**失败记忆**（§3.3.1）——把"试错递归"降为"每规则一次扫描"，这是不改变架构的最小状态机化；
  2. **块级上下文预扫描**（§2.1 的 `computeLineContexts`）——Setext/缩进代码/引用定义/HTML 块都需要前一行或全文档上下文，把这部分从"行本地"提升为"文档级一次遍历"（与 `computeLineOffsets` 合并为单趟 O(n)），行内层保持现状；
  3. 若未来需要**流式增量解析**（按击键只重扫受影响行段），则 fence/缩进代码/HTML 块的跨行状态必须从"全量重算 computeLineOffsets"改为"状态增量传播"，那时才需要真正的块状态机——这是现阶段唯一值得预留的架构接口（把 CodeState 计算收敛为纯函数 `nextState(state, line)`，便于逐行增量）。

## 4. INLINE_RULES 硬编码顺序耦合的风险点

规则表（parser.ts:597-637）的 41 项全部按数组顺序线性匹配，无规则名、无优先级声明，以下耦合点均有实证：

### 4.1 image 先于 link（:599-605）

- `![alt](url "title")`：image 正则 `((?:[^)\\]|\\.){0,2000})` 把 `url "title"` 整体吞进 url（`"` 和空格都在 `[^)\\]` 内），**title 丢失**（实证 TITLE 的 link 版同样）。CommonMark 中 title 是独立概念，`<img src="url" alt="alt" title="title">`。修复：目标正则区分 `<>` 包裹与裸目标，title 单独捕获。
- `[a](b c)`：link 正则同样放行含空格的非法目标（实证 DESTSP），CommonMark 要求裸目标不含空格（除非 `<>` 包裹）。修复：目标段正则收紧。
- 空目标 `[a]()`：CommonMark 允许空目标（`<a href="">a</a>`）✓ 现状一致。

### 4.2 code 规则边界（:608）

- `/^(`+)(.*?)\1/` 非贪婪 + 子串窗口 2000：长内容 code span 在 2000 字符后无法闭合（与 spec "code span 长度无限制"偏差）；`.*?` 的灾难性回溯被窗口 + 逐位置尝试约束，实测无 ReDoS，但 `\1` 反引用对 `` `` `` `` 多反引号边界（2 反引号开、1 反引号闭）依赖惰性匹配的从左到右语义，spec 的 32 例中部分多反引号用例需逐例验证。
- **code 规则在 html_tag 之前**（:608 vs :635）：`` `<div>` `` 在 code span 内被 code 规则正确吞掉 ✓（顺序正确），但 `code` 在 `html_tag` 前意味着 `<b>` 开头的**裸文本**（非代码）会先被 html_tag 正则 :635 外的 HTML 分支（:847）与 `<b>` 起止规则（:614）截获——见 4.3。

### 4.3 HTML 扫描在规则循环外的分支（:847-905）

- **执行顺序**：每轮主循环先跑 HTML 分支（:847），**再**跑规则循环（:907）——即 `sub.startsWith('<')` 且 htmlMatch 命中时，`<b>` 起止规则（:614）被 HTML 分支抢先（先找 `</b>`），找到则 html_element、找不到则落回规则循环走 `<b>` 起止规则——**两条路径产出不同 token 类型**（html_element vs bold），语义不稳定：`<b>x</b>` → html_element（实证 EL），`<b>x</b>` 后无闭合 → bold 尝试失败 → 文本。同一文本形态在不同行尾上下文产出不同 AST。
- **closeIdx 全行扫描**（:862-865）：`text.toLowerCase().indexOf('</div>', ...)`——每次 HTML 开标签命中都做全行 lower + indexOf（实证 A.6：1000 个 `<div>` 触发 1000 次 closeIdx、500 万字符 lower 拷贝），是 2^n 之外的第二个退化路径（O(标记数×行长)，被 10000 截断窗口兜住但常数巨大）。
- **tagName 未校验**：`<http://example.com>` 被当作 tagName `http` 做闭合查找（实证 AUTOLINK）——浪费 + 语义错误。
- **`<u>`/`<ins>`/`<sub>`/`<sup>`/`<kbd>` 双重定义**（:621-625 的 `sub` 起止规则 vs :857-860 的 isSpecialTag 豁免）：isSpecialTag 让 HTML 分支跳过这些标签，随后规则循环把 `<u>x</u>` 解析为 **sub(x)**（下划线语义被映射成下标）——语义错位。

### 4.4 其他顺序依赖

- checkbox（:606）在 link 前：`[x]` 被 checkbox 吞（扩展语法，CommonMark 无此冲突，但 `[x](url)` 链接形式不受影响 ✓）。
- math（:626-631）在 sup/sub 前：`$x^2$` 的 `^` 在 math 内原子化 ✓。
- table_pipe（:636）**最后**：任何正文 `|` 都变 table_pipe token——与行级表格启发式（:439-446）联动，`a | b | c` 段落被误判为 table_row（实证 PIPE），这是 652 套件中段落含管道字符用例（如 spec §Tabs 前几例的 `→foo→baz` 无管道，但 §Emphasis 的管道字面用例）的失败来源。
- spoiler `||`（:634）与 table_pipe `|`（:636）竞争：`||text||` 会被 spoiler 先吞，但行级表格判定（:439-446）在 spoiler 解析**之前**就把行标为 table_row——表格投影器与 spoiler token 并存时渲染矛盾。

**修复方向（不改架构）**：把 41 项规则表改为**带优先级的分组链**（regex 组 / 起止组 / 原子组），组内保持现状顺序，组间语义显式声明；HTML 分支（:847）与 `<b>` 起止规则（:614-625）合并为同一"HTML 语义层"，消除双路径。

## 5. AST 缓存上下文漂移风险

### 5.1 缓存键与命中路径

- 键：`cacheKey = codeState + ':' + lineText`（parser.ts:117）——LRU 容量 50k（:86），静态类级缓存（跨文档共享）。
- 命中：`return { ...cached, localOffset }`（:121-124）——浅拷贝，只替换顶层行偏移。

### 5.2 实证确认的漂移（本任务核心确认项）

1. **行 id 重复（确认，LOW-MEDIUM）**：命中时 `id` 从缓存节点继承，同一 `lineText` 在文档不同位置全部复用同一 id（实证 IDS：`aaa\naaa` 两行 id 均为 `line_j`）。当前 src 中无 `.id` 消费方（grep 全仓库仅 parser.ts 自引用，React key 用 `type-index`，InlineRenderer.tsx:39），属**潜伏风险**——一旦渲染层改用 id 做锚点/选区定位即出现重复 key 冲突。
2. **`shiftInlineOffsets` 是死代码（确认）**：parser.ts:98-110 定义、仅在自身递归调用（:107），无任何外部调用点——它是"token 存绝对偏移"时代的遗留：若某次改动把 token 偏移从"行内相对"改回"文档绝对"（并忘掉这条死代码），缓存命中将返回**旧文档位置的绝对偏移**，渲染错位。

### 5.3 任务假设的修正：blockquote 前缀已在键内

任务书假设"cacheKey 不含 blockquote 前缀等上下文"，**实证反证**：`>` 前缀剥离发生在 `parseLine` 内部（:131-134），cacheKey 用的是含前缀的原始 `lineText`——`> foo` 与 `foo` 键不同，`> foo` 与 `> > foo` 键也不同。同理，fence/math 跨行状态已编码在 `codeState`（:54-77），列表/表格/hr 判定全部行本地。因此**当前架构下不存在"同键不同 AST"的上下文漂移**——漂移面仅剩 id 重复与死代码遗留，均属"缓存复制缓存节点"这一行为本身。

### 5.4 仍需关注的上下文敏感线型（风险登记）

| 线型 | 上下文依赖 | 是否进键 | 风险 |
|---|---|---|---|
| fence/math 行 | 跨行开关 | codeState ✓ | 无 |
| `code` 状态行（含 `true` 旧布尔形态） | 跨行开关 | codeState ✓（`true:` 与 `code:` 分键，功能相同、条目重复，无害） | 无 |
| `> ` 前缀 | 行内剥离 | lineText 含前缀 ✓ | 无 |
| Setext 下划线（待实现） | **前一行类型** | 不在键内 | **必须把 prevLineType 纳入上下文数组而非缓存键**（§2.1 的预扫描产物天然规避） |

| 引用定义（待实现） | 全文档定义表 | 定义表是文档级 | 解析期引用查询必须走"每文档一次的定义表快照"，不能走行缓存 |
| 表格行 | 无（行本地启发式） | ✓ | 无（错误是启发式本身的误判，非缓存） |

### 5.5 修复建议

1. 命中路径改为 `{ ...cached, id: generateId(), localOffset }`——id 每行唯一；
2. 删除死代码 `shiftInlineOffsets`（或补一条断言：token.localOffset 必须落在 [0, line.length] 内，防偏移模型回退）；
3. 缓存键加注释声明"键内已含 codeState 与完整行文本，token 偏移为行内相对值"；
4. 为 §5.3 的三条反证写回归测试（`> foo` 与 `foo` 的 AST 差异、fence 内外的同文本行）。

## 6. token 覆盖守恒（inlineTokens 拼接 == raw）验证方案

### 6.1 不变量定义

直接断言"叶子 raw 拼接 == 行 raw"不成立——容器 token（bold 的 `**b**`）的 raw 包含子 token raw，叶子拼接会丢失定界符。**正确的不变量**（递归式）：

```
reconstruct(node) = node.raw                              （叶子）
reconstruct(node) = node.raw − Σ reconstruct(children)    （容器，取差分）
线级：Σ reconstruct(token) == lineNode.raw                （含结构性 token：heading_prefix/list_bullet/table_pipe 等）
```

等价写法：`Σ 叶子 raw + Σ (容器 raw − 子 raw 拼接) + Σ 结构性 raw == 行 raw`。table_cell 的 raw 恒等于子拼接（差分 0，parser.ts:564），管道 token 是叶子。

### 6.2 实证发现的两处违例

1. **代码块内空行**：`parseCodeLine('')` 的兜底（parser.ts:333-341）产出 `{type:'text', raw:' ', length:1}`，而行 `length:0`（实证 BLANKCODE）——token 占位 [0,1) 超出行界 [0,0)，**validator.ts:92-103 的 token-bounds-integrity 会报 error**（每条空代码行一条）。修复：空行 code 行产出 length 0 的 text token（或直接空 token 数组）。
2. **hr 行**：hr 判定（parser.ts:408-415）推进 `pos` 但不产 token，剩余空串解析出 length 0 空 text——`***` 行叶子拼接为 `''` ≠ raw `'***'`（实证 CONSERV_FAIL hr）。修复：hr 行产出覆盖 raw 的结构性 token（如 `hr_marker`），或守恒断言按行类型豁免 hr/empty 并显式登记。

### 6.3 验证方案（测试设计）

1. **扁平化投影函数** `flatten(lineNode): {raw, offsets[]}`：DFS，容器按差分、叶子按 raw，同时校验 `localOffset` 链：首 token offset == 0、相邻 token 首尾相接、末 token 末位 == line.length、容器 token 的 offset/length 与子集合一致（groupTableCells 的 length 计算 :558-560 是现成的差分校验点）。
2. **语料**：652 套件全部用例输入 + 随机拼接 fuzz（现有 fuzz-document-typography 风格）+ 既有 corpus（附录 A.2 的 8 组）——对每行断言守恒 + 边界 + 单调性。
3. **与 validator 集成**：validator.ts:87-136 的 token 循环已有 bounds 检查，把守恒断言并入同一诊断通道（rule: `token-coverage-conservation`），空代码行违例修复后该通道应全绿。
4. **防作弊**：守恒断言**独立于投影器**（投影器用 content，守恒用 raw），两者同时成立才允许宣称"token 覆盖守恒"。

## 7. fence 嵌套边界

### 7.1 现状状态机（computeLineOffsets，parser.ts:43-81）

```
逐行：剥离 blockquote 前缀（:48-51）→ trim（:52）
  → startsWith('```')（:54）→ fence_start/fence_end 切换
  → 否则 trimmed === '$$'（:62）→ math_fence_start/fence_end 切换
  → 否则按 inCodeBlock/inMathBlock 标记 code/math_block/none
```

### 7.2 实证确认的边界缺陷

| 场景 | 现状（实证） | CommonMark 期望 |
|---|---|---|
| 4 反引号开 ```` ``` ````，内嵌 3 反引号行 | 3 反引号行被当作 fence_end 提前关闭（FENCE34：`[start, end, start]`） | 关闭围栏长度必须 ≥ 开围栏长度，3<4 不关闭 |
| 关闭行带信息串 ` ``` js` | 照常关闭（FENCEINFO） | 关闭行不允许信息串 |
| `~~~` 波浪围栏 | 三行 body（TILDE） | 支持 `~~~`（spec 约 7 例） |
| 开围栏信息串 ` ```js ` | `startsWith('```')` 命中 ✓ 开围栏（与 CommonMark 一致） | ✓ |
| `$$` 在 code fence 内 | 保持 code（:62 的 `!inCodeBlock` 守卫 ✓） | GFM 数学扩展无冲突 |
| ```` ``` ```` 在 math 块内 | 保持 math_block（:54 的 `!inMathBlock` 守卫 ✓） | ✓ |
| 未闭合 fence 至 EOF | 尾部全部标记 code，validator 报 unclosed-code-fence（validator.ts:140-148）✓ | 语义一致 |
| 围栏开行内 ```` ``` `` 后接内容 | ` ```code` 开围栏 ✓ | ✓ |
| 2 反引号行 `` `` `` 在 code 内 | 不关闭 ✓ | ✓ |

### 7.3 根因

围栏判定只看"3 个以上反引号"（:54 的 `startsWith('```')`），**不记录开围栏长度、不校验标记字符、不区分关闭行的信息串**。`computeLineOffsets` 需要从"布尔切换"升级为"带状态的结构化状态机"：

```
type FenceState = { kind: 'code'|'math'; marker: string; length: number } | null
关闭判定：marker 相同 && 长度 >= state.length && 行内除尾部空白无信息串
```

### 7.4 修复方案

1. `computeLineOffsets` 维护 `FenceState`（如上）：开围栏记录 marker+length；关闭行要求 `^ {0,3}(`+marker+`{length,})\s*$` 且 marker 匹配；`~~~` 与 ```` ``` ```` 双 marker 支持；math `$$` 保持精确匹配（现有 :62 语义）。
2. 开围栏长度正则：`^(`+`+)(\S*)$` 或 `^(~+)(\S*)$`——信息串捕获供未来渲染器使用（现行 fence_start 行把整行作为 code token，:137-155，信息串渲染留待投影器）。
3. 流式状态：未闭合 fence 的流式语义已被 validator（:140-148）覆盖；若编辑器增量路径（EditorStore）调用 computeLineOffsets 全量重算，未闭合大文档每次击键 O(n)——登记为性能项，改进为 §3.5 的增量状态传播后再议。
4. 测试：spec Fenced code blocks 节约 29 例 + 附录 A.3 的 FENCE34/FENCEINFO/TILDE 三例反证。
