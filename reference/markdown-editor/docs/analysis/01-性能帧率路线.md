# 百万行文档 + 500 token/s 流式 + 60/120/140fps 性能路线分析

- 分析对象：`reference/markdown-editor`（自研 Markdown 渲染引擎）
- 性能参考：`reference/compare/codemirror-view`（CM6 的 heightmap.ts / viewstate.ts / docview.ts）
- 目标：百万行文档、500 token/s 流式注入、60fps 保底（16.6ms）、120fps（8.3ms）与 140fps（7.1ms）目标帧率
- 文档定位：九项已知问题的根因定位（代码行级证据）、修复方案设计（可执行级伪码）、帧率预算分解、依赖关系、验证方法

## 零、结论先行

引擎当前架构是「**React 受控渲染 + 固定行高估计 + DOM 全扫测量**」：功能完整，但三条主链路上都存在与百万行/高帧率目标冲突的架构断层：

1. **行高与滚动定位**：`estimateSize` 粗粒度启发式（仅区分 5 种前缀）+ `measureElement` 事后校正，滚动条在内容稍复杂时必然失真；没有 O(log n) 的「位置 ↔ 像素」双向定位结构。
2. **测量与光标**：`getCoordinatesFromIndex` 每次全扫可见 DOM + 多次强制 layout（Range/`getBoundingClientRect`/`getComputedStyle`），且 CursorLayer 与 HiddenInput **双重重复测量**，被滚动导致的 `layoutDeps` 字符串变化高频触发。
3. **数据层**：`LineOffsetTree.clone()` 每次击键全量深拷贝 O(全文)；`updateLinesIncremental` 的 fence 前缀重放 O(编辑点前 fence 数)；`appendText` 无光标冲突语义。

九项问题按「严重度 × 修复成本」分级：

| 级别 | 问题 | 一句话定性 |
|---|---|---|
| P0 | 1 行高模型 | 滚动条失真的根源，滚动定位复杂度的根源 |
| P0 | 6 滚动管线 | 每次 scroll 事件全量 reconcile，140fps 不可达 |
| P0 | 3 LineOffsetTree.clone | 每次击键 O(全文)，百万行下是硬伤 |
| P1 | 2 坐标测量 | 每次击键/滚动重复全扫 + 强制 layout，120fps 不可达 |
| P1 | 4 fence 前缀重放 | 编辑点靠前时每击键 O(万级) 线性重放 |
| P1 | 5 appendText 冲突 | 流式与用户编辑语义冲突，正确性缺陷 |
| P1 | 8 表格行高 | 与固定行高模型冲突，测量回环风险 |
| P2 | 7 跨视口箭头 | 体验缺陷，视口外列位置丢失 |
| P2 | 9 帧率组合 | 上述各项的组合目标，见第四节预算表 |

修复路线（依赖序）：**先数据层（P3→P4→P5），再定位骨架（P1→P6→P2→P7），最后体验项（P8），全程以 P9 预算表为准绳**。逐帧预算见第四节：140fps 目标的本质是「滚动帧零 React 提交 + 命令式位置更新 + 单次 Range 测量」。

## 一、九项问题：根因定位与修复方案

### 问题 1：行高模型 —— 固定 28px 估计 + measureElement 事后校正

#### 1.1 根因定位

| 位置 | 代码 | 说明 |
|---|---|---|
| `src/components/MarkdownEngine.tsx:106-114` | `estimateSize` 硬编码 5 类前缀高度（`# `→46 / `## `→40 / `### `→36 / `#### `→32 / 表格分隔→0 / 其他→28） | 预测只看前缀，对超长行 wrap、表格行、math 块、代码块**完全不预测** |
| `MarkdownEngine.tsx:74,408` | `ref={measureElement}`（tanstack 的 ResizeObserver 校正） | 行渲染后才实测校正，**校正发生在「错误位置已滚动过去」之后** |
| `MarkdownEngine.tsx:81` | `minHeight: 28px` 固定 | 与实际内容高度脱钩 |
| `src/index.css:139-150` | `.line-block { min-height:28px; line-height:28px }` | 行高名义固定，但 `pre-wrap`（:144）意味着长行会 wrap 成多行 |
| `index.css:279-295` | `.token-table-cell` padding 6px 12px + `line-height:1.5` + `word-break:break-word` | **表格行实际高度 ≈ 33px+（21px 文字 + 12px padding），与 28px 估计冲突**（问题 8 的雏形） |

失真机制：tanstack 的 `totalSize` 是「已测量行之和 + 未测量行按 estimateSize 之和」。滚动到新区域时，未测量行全部按 28px（或 5 类前缀猜测）计，实测后逐行回填修正 —— 于是：
- 滚动条 thumb 比例与位置**永远滞后于真实内容**（新区域估计偏差大时尤其明显）；
- `measureElement` 每次触发 `resizeItem` → 行 offset 变化 → React 重渲染 → 与滚动叠加形成抖动；
- 百万行时 `getTotalSize` 依赖全量 cache，任何 estimateSize 变化都波及后续全部 offset。

对照 CM6 的正确模型（`heightmap.ts`）：
- `HeightOracle`（heightmap.ts:12-75）：`lineHeight/charWidth/textHeight/lineLength` 每次测量阶段刷新一次（`measureTextSize`，docview.ts:433-467），`heightForLine(length)`（heightmap.ts:29-33）按「长度 ÷ 每行字符数」预测 wrap 行数；
- `HeightMap` 树（heightmap.ts:146-583）：`HeightMapText`（单行：实测或预测）、`HeightMapGap`（未测量区间：按 `perLine/perChar` 插值，heightmap.ts:345-471）、`HeightMapBranch`（聚合 `height/length`，O(log n) 双向查询 `blockAt`/`lineAt`）；
- `MeasuredHeights`（heightmap.ts:80-84 + 433-462）：**只把可见行实测值回填树**，其余区域继续用 oracle 预测 —— 滚动条在任何位置都准确，因为 gap 的 perLine 均值本身就是「已测样本」校准过的；
- 稳定性护栏：`heightChangeFlag` + `Epsilon=1e-3`（heightmap.ts:144,167）——高度变化小于阈值不触发刷新，避免测量回环；
- 超大文档护栏：`BigScaler` + `VP.MaxDOMHeight=7e6`（viewstate.ts:58,695-738）——总高超过浏览器 DOM 上限时，视口外区域按比例压缩。

#### 1.2 修复方案：行级 HeightMap 树 + 行高 Oracle

**核心数据结构**（在现有 `LineOffsetTree` 旁新增，或直接扩展它）：

```
class HeightLeaf {            // 一棵叶子 = 一行（或一个块级元素）
  from: number;               // 全局字符偏移（doc 坐标）
  length: number;
  height: number;             // 实际像素高度（实测后回填）
  measured: boolean;          // 是否已实测
}
class HeightNode {            // 内部节点
  left, right: HeightNode;
  length: number;             // 子树覆盖字符数
  height: number;             // 子树总高（预测或实测之和）
  lineCount: number;          // 子树行数
  size: number;               // 平衡权重（AVL/替罪羊，2:1 再平衡同 CM6 balanced()）
}
```

不变式：叶子高度 = `measured ? 实测值 : oracle(行)`；节点高度 = 子树和。全部操作 O(log n)：

- `lineAt(pos) → {top, height}`：字符偏移 → 行几何（光标定位、行内坐标）
- `blockAt(scrollTop) → 行`：像素 → 行（滚动定位，视口首行计算）
- `update(编辑区间)`：只重建受影响叶子的路径（path copying，与问题 3 的 COW 同构）
- `measureBackfill(可见行实测数组)`：一次批量回填（对应 CM6 `MeasuredHeights`）

**行高 Oracle**（预测函数，替代 `estimateSize`）：

```
oracle(line, wrap, containerWidth):
  // 1. 块级固定倍率（与 .line-h1..h6 的 font-size/line-height 对齐）
  if 标题: height = 28 × 倍率(h1:1.65,h2:1.35,h3:1.15,h4:1.02,其余1.0)  // 上限对齐实测
  if table_separator: return 0
  if 表格行: height = 行内最大单元格 wrap 行数 × 21 + 12      // 见问题 8
  if math_block: height = 预测常数（首次实测后回填为样本）     // 唯一不可预测项，进样本表
  // 2. 文本行 wrap 预测（CM6 heightForLine 同款）：
  linePerRow = max(5, containerWidth / charWidth)
  rows = 1 + max(0, ceil((length - linePerRow) / (linePerRow - 5)))
  height = rows × 28
```

关键点：**预测函数从「5 类前缀猜测」升级为「长度 × wrap 模型 + 类型倍率」**，使未测量区域的偏差从「结构性错误」降为「±一行 28px 内」，滚动条误差随样本校准收敛。Oracle 的全局度量（`charWidth/lineHeight`）在每次测量阶段刷新一次（CM6 `measure()` 同款，viewstate.ts:267-386）。

**必须保留的测量回填**：仅 `math_block`、表格行、图片等不可预测行需要实测；普通文本行在 wrap 模型下几乎不需要实测（可作「抽样校验」而非全量 RO）。

**稳定性护栏**（防回环）：
- 实测高度与预测偏差 < 0.5px 时不回填（吸收浮点抖动）；
- `math_block` 高度进「样本表」（key=公式哈希，LRU），同公式直接命中，KaTeX 只在首测时渲染一次。

#### 1.3 收益量化

- 滚动条准确性：从「偏差随内容复杂度放大」→「偏差 ≤ 预测误差 ±28px 且收敛」；
- 滚动定位复杂度：O(可见行) 全扫 → O(log n)；
- 消除 `measureElement` 引发的测量-渲染抖动（每次滚动少 N 次 `resizeItem`）。

### 问题 2：getCoordinatesFromIndex —— 每次全扫可见 token + Range 测量

#### 2.1 根因定位

| 位置 | 代码 | 成本 |
|---|---|---|
| `src/core/measure.ts:14` | `container.querySelectorAll('[data-token-start]')` | 每次调用全扫可见行 token 元素（视口 ~40 行 + overscan 80 行 ≈ 数百个节点） |
| `measure.ts:18-41` | 循环内每个 token 一次 `getBoundingClientRect()` | 每个元素一次 layout 读取，无缓存 |
| `measure.ts:72` | `findNodeAndOffset` 递归遍历文本节点 | 每次调用重复整棵子树遍历 |
| `measure.ts:87-92` | `document.createRange().setStart/setEnd().getBoundingClientRect()` | 强制 layout，且每次调用新建 Range |
| `measure.ts:100` | `getComputedStyle(targetElement)` | 强制样式计算 |

调用频率（放大因素）：
- `CursorLayer.tsx:40-70` 与 `HiddenInput.tsx:43-86` **各自独立**对同一光标执行一遍完整测量（两处重复，同帧两次全扫 + 两次 Range）；
- `MarkdownEngine.tsx:417-420`：`layoutDeps = getVirtualItems().map(v => v.start).join(',')` —— 每次滚动都生成新的巨大字符串 → 触发 CursorLayer 的 `useLayoutEffect`（依赖 `layoutDeps`）→ **滚动期间每帧都执行全扫测量**（这就是滚动时卡顿的主贡献之一）；
- `measure.ts:274-383` `getArrowNavigationIndex` 的几何回退分支对目标行做二分 × 多次 `getCoordinatesFromIndex`（每次一个 Range）。

**关键认识**：这个函数在「每击键一次、每滚动帧一次」的热路径上，却做了「全扫 + 多 Range + 多 layout」的冷路径式工作；而且它本可以用纯数据层（行号 + 行内偏移）把搜索范围从「全视口」缩到「一行」。

#### 2.2 修复方案：行级 token 索引缓存 + 单次 Range 测量 + 单测量源

**A. 行级 token 索引缓存**（替代全扫）：

```
// 行挂载时构建一次（O(行内 token 数)），行卸载即弃
class LineMeasureIndex {
  readonly tokens: { start: number; length: number; el: HTMLElement; textNode: Text | null }[];
  // 每行追加一次 binary search（O(log token 数)），命中后 1 次 Range：
  locate(index): { textNode; localOffset } | null
}
```

- 构建时机：虚拟行挂载（`useLayoutEffect` 一次）；失效时机：行内容变化（parseLine key 变化）或行卸载。与问题 6 的「挂载/卸载生命周期钩子」共用一套。
- 查找：`LineOffsetTree.findLineIndex(pos)`（O(log n)）→ 行内 offset → 该行的 `locate()` 二分 → 目标 text node。**全扫 O(数百) → 二分 O(log k) + 1 次 Range**。

**B. 单次测量、单测量源**：
- CursorLayer 与 HiddenInput 合并测量：坐标计算结果写入共享 ref（`useRef<{top,left,height}>`），HiddenInput 通过订阅该 ref（或由 CursorLayer 的同一 layoutEffect 顺手更新 textarea 位置）消费，删除重复调用；
- `getComputedStyle` 的 fontSize 全局化：字体度量一次测量（CM6 `measureTextSize` 同款），不再每 token 查；
- Range 对象复用（模块级单例，`setStart/setEnd` 复用实例，避免每次 `createRange` 分配）。

**C. 消除 layoutDeps 陷阱**：`layoutDeps` 改为「窗口首行索引 + 窗口长度 + 一个单调版本号」的紧凑签名；若滚动帧走命令式路径（问题 6），光标测量不再依赖 layoutDeps。

#### 2.3 收益量化

- 单次坐标测量：当前 ≈ 300-800 次 DOM 读取 + 2-4 次 layout → 优化后 ≈ 1 次 Range + O(1) 读取；
- 每击键/每滚动帧省 2 次全扫（CursorLayer + HiddenInput 双重）；
- 滚动帧光标跟随时，测量成本从「不可忽略」降为「0.1-0.3ms 预算内」（见第四节）。

### 问题 3：LineOffsetTree.clone() 全量深拷贝

#### 3.1 根因定位

| 位置 | 代码 | 成本 |
|---|---|---|
| `src/core/SegmentTree.ts:209-213` | `clone()`：`blocks.map(b => b.clone())`，每块 `[...lineLengths]` 全量复制 | O(全文)。百万行 = 3907 块 × 256 元素深拷贝 |
| `src/core/EditorStore.ts:191` | `insertText/deleteText/undo/redo` 每次 `lineOffsets.clone()` | **每次击键 O(全文)** |
| `EditorStore.ts:533` | `appendText` 同样 `clone()` | 每次流式 chunk O(全文) |
| `SegmentTree.ts:84-125` | `getOffset/findLineIndex` 线性扫块 | O(#blocks)（百万行 3907 次迭代/次，常数小但随规模线性） |

量化：百万行数组复制 ≈ 100 万次数字写入 ≈ 1-3ms；若目标 120fps（8.3ms 预算），**仅 clone 一项就吃掉 1/3 预算**；千万行文档（1 亿字符级别）不可用。注释声称「O(N/BLOCK_SIZE) 使其对百万行极快」——定位是 O(N/BLOCK_SIZE)，但 clone 是 O(N)，两者被混为一谈。

#### 3.2 修复方案：块级 Copy-on-Write（与持久化共享）

**方案**（与现有分块结构天然契合）：

```
class SegmentBlock {
  lineLengths: number[];   // 共享数组（只读共享，写时复制）
  totalLength: number;
}
class LineOffsetTree {
  private blocks: SegmentBlock[];   // 数组本身也是共享引用数组
  clone(): LineOffsetTree {
    // 浅拷贝：blocks 数组复制指针（O(#blocks)≈4k 次引用拷贝，<0.1ms）
    const t = new LineOffsetTree([]);
    t.blocks = this.blocks.slice();   // 注意：块对象共享！
    return t;
  }
  updateLines(...) {
    // 写时复制：仅对「删除/插入触及的块」克隆后修改
    const touched = 定位受影响块（O(#blocks) 或块级前缀跳表 O(log n)）;
    for (const b of touched) this.blocks[b] = b.clone();  // 只克隆触及块
    ...原删除/插入逻辑（块内 splice O(BLOCK_SIZE)）...
  }
}
```

- 未触及的块完全共享（持久化结构）：**undo/redo 天然免费**——旧树保留着编辑前的块引用，内存增量 O(触及块)；
- 修改路径上新增的块是新对象，旧树不受影响（这就是 undo 需要的语义，当前实现靠全量 clone 保证）；
- `appendText`（EditorStore.ts:533）同样受益：只克隆末尾块，**每次流式 chunk O(256) 而非 O(全文)**——500 token/s 下这是流式帧预算的关键。

**可选第二层**：块级「前缀 offset」数组（每块的 `blockStartOffset`，COW 更新 O(#blocks)）→ `getOffset/findLineIndex` 二分 O(log #blocks)；百万行时第一层已够用（3907 次迭代 ≈ 0.05ms），作为文档超过千万行时的后续增强。

#### 3.3 收益量化

- 击键路径：O(全文) → O(256 + 触及块数)，百万行下 1-3ms → 0.05-0.1ms；
- 流式路径：每 chunk O(256)，500 token/s 完全无感；
- undo/redo：额外内存从 O(全文) → O(编辑块)。

### 问题 4：updateLinesIncremental 的 fence 前缀线性重放

#### 4.1 根因定位

| 位置 | 代码 | 成本 |
|---|---|---|
| `EditorStore.ts:207-218` | 二分定位 `splitIdx`（fence 数组中编辑点之前的最后一个） | O(log #fence)，OK |
| `EditorStore.ts:220-228` | **`for (i=0; i<splitIdx; i++)` 线性重放 splitIdx 个 fence 状态** 以恢复 `inCodeBlock/inMathBlock` 初始状态 | **O(编辑点前的 fence 数)**。文档头部有 1 万个 fence（如 5000 个代码块）时，编辑第 1 行 = 每击键重放 1 万个分支 |
| `EditorStore.ts:230-291` | 收敛扫描（编辑点 → 下一个 fence） | 通常 O(局部)，仅当 fence 状态翻转不一致时才继续 |

根因本质：`fenceLines` 是有序数组，但**没有前缀状态摘要**，恢复「编辑点前的块状态」必须从头重放。

#### 4.2 修复方案：fence 块级摘要（奇偶前缀）

关键洞察：fence 状态是 **toggle 奇偶性**——`inCodeBlock = (编辑点前 fence_start 数) 的奇偶性`（fence_start/fence_end 成对出现），math 同理。因此可以按块（复用 SegmentTree 的 BLOCK_SIZE=256 行粒度）维护摘要：

```
class FenceBlockSummary {        // 每 256 行一个
  fenceStartParity: { code: boolean; math: boolean };   // 该块内 fence_start 数的奇偶
  fenceEndParity:   { code: boolean; math: boolean };   // fence_end 数奇偶
  hasFence: boolean;
}
class FencePrefixIndex {         // 与 LineOffsetTree 并行维护
  summaries: FenceBlockSummary[];         // 每个块一条
  prefixParity: { code: boolean; math: boolean }[];     // 前缀奇偶（COW 更新）
}

// 编辑点 startLineIdx 前的初始状态：
blockIdx = startLineIdx >> 8;             // O(1)
init = prefixParity[blockIdx]             // O(1)：编辑点前所有块的 fence_start 奇偶和
      ⊕ 块内局部重放（编辑点在该块内前 256 行的 fence 逐行重放，O(256) 上限）
```

- 每次编辑后**增量重建**：只重算「受影响块」及其之后的前缀奇偶（O(#受影响块 + 其后块数) 的最坏仍 O(#blocks)，但触发面极小——常态击键只影响 1-2 个块，其后前缀奇偶在 COW 树中只需重建路径上的块，O(log n)）；
- 与问题 3 的 COW 共享失效/重建逻辑（同一处 update 流程）。
- 更简单的替代（若不想维护双结构）：把 `inCodeBlock/inMathBlock` 作为**每一行**的派生状态缓存进 `codeBlockState` 数组——该数组已存在（EditorStore.ts:194-202 已维护），**问题其实是：该数组在编辑点之前的行从未失效，重放完全多余**。只要在 `codeBlockState` 上附加一个「行级前缀状态位图」（每行 2 bit：inCode/inMath，COW 更新），初始状态查询 = O(1) 位图读取 + 编辑点所在块局部重放。

推荐实现：**行级前缀状态位图**（并入现有 `codeBlockState` 的维护循环，成本几乎为零）：

```
// EditorStore 新增（COW，与 lines 同生命周期）
blockStatePrefix: Uint8Array      // 每行 2 bit：bit0=inCode, bit1=inMath（编辑点之前的状态）
// 编辑时：
init = blockStatePrefix[startLineIdx]            // O(1)
// 重放循环从 startLineIdx 开始（现状已有），结束时回填受影响区间的 prefix：
blockStatePrefix.fill(..., startLineIdx, i)      // 一次性批量回填
```

#### 4.3 收益量化

- fence 初始状态恢复：O(编辑点前 fence 数) → **O(1)**；
- 头部密集代码块的文档中，击键路径从「每键 1 万次分支重放」→「位图读 + 局部重放 ≤256 行」。

### 问题 5：appendText 无光标冲突检测

#### 5.1 根因定位

| 位置 | 代码 | 问题 |
|---|---|---|
| `EditorStore.ts:521-598` | `appendText` 无条件把文本拼到 `lastLine` 末尾 | 追加位置是「全文末尾」，不感知光标 |
| `EditorStore.ts:586` | `wasAtEnd = cursorPos === textLength` 时推进光标 | 仅在光标**精确等于**全文长度时推进；光标在末尾行中间（`cursorPos < textLength` 且在最后一行）时不推进——追加内容出现在光标右侧，用户正在打字的行被流「塞字符」 |

冲突场景：流式注入期间用户在末尾行中间输入（最常见：用户在等 LLM 输出时往下滚、在最末行打字）：
1. 流把新文本拼到 `lastLine` 末尾 → 光标位置不变，但光标右侧凭空多了流内容；
2. 用户下一次 `insertText` 在旧光标处插入 → 字符被插入到流内容中间 → 文本语义错乱（用户的击键落入「已生成的流内容」中段）；
3. 选择（selection）跨追加点时同样不平移 → 选择范围语义漂移。

#### 5.2 修复方案：追加点策略 + 偏移平移（CM6 变更映射语义）

```
appendText(text):
  delta = text 长度（去除换行语义后的字符增量）
  追加点 anchor = 当前全文末尾（保持现状语义：流始终追尾）

  // 1) 平移语义：光标/选区位于追加点之后 → 平移 delta
  if cursorPos >= anchor:  cursorPos  += delta
  if selectionStart >= anchor:  selectionStart += delta
  if selectionEnd   >= anchor:  selectionEnd   += delta

  // 2) 冲突策略（用户正在末尾行编辑时）：
  lastLineIdx = lines.length - 1
  userEditingTail = (findLineIndex(cursorPos) == lastLineIdx)
                    && (cursorPos > 上一行末尾)          // 光标落在最后一行
                    && (now - 最近一次用户输入 < 1000ms)  // 用户有活跃输入
  if userEditingTail:
    // 策略 A（推荐）：追加点前移 —— 流内容插入到光标之前，用户打字区不被污染
    // 实现：在光标处拆行插入，光标不动，selection 平移规则同上
    insertAt(cursorPos, text)          // 走 insertText 的数据路径（COW 后成本一致）
  else:
    appendAtEnd(text)                  // 原路径 + 平移规则
```

补充规则：
- 表格/KaTeX 等块级状态在追加点前移时随 `updateLinesIncremental` 自然重算（现有收敛逻辑）；
- 光标恰好落在**追加点**（全文末尾）时维持现状（`wasAtEnd` 语义保留）；
- undo 栈：流式 chunk 不进 undo（现状已如此，EditorStore.ts:520 注释），冲突插入路径也应保持不进栈——因为它属于流，不属于用户操作。

#### 5.3 收益量化

- 消除流式期间的文本错乱（正确性修复，用状态机测试断言，见第五节）；
- 无性能影响（COW 后插入路径与追加路径同价）。

### 问题 6：滚动管线 —— 每次 scroll 事件同步 setState

#### 6.1 根因定位

| 位置 | 代码 | 问题 |
|---|---|---|
| `MarkdownEngine.tsx:103-116` | `useVirtualizer` 默认行为：scroll 事件 → `_willUpdate` → 通知 → React 渲染 | **每个 scroll 事件一次 React 提交**，无 rAF 合并；触摸板惯性滚动时每帧可达 1-3 次 |
| `MarkdownEngine.tsx:397-411` | `getVirtualItems().map(virtualRow => <LineItem virtualRow={virtualRow} …/>)` | `virtualRow` 每次通知都是**新对象字面量** → `LineItem` 的 React.memo 必然失效 → **每次滚动事件全量 reconcile 可见窗口内全部行**（含 overscan 40+40） |
| `MarkdownEngine.tsx:417-420` | `layoutDeps` = 全部虚拟项 start 的字符串 join | 每次滚动重建巨型字符串 → CursorLayer/HiddenInput 的 `useLayoutEffect` 全部重跑 → 问题 2 的全扫测量在滚动期间每帧执行 |
| `MarkdownEngine.tsx:81` | 行位置写 `style.top`（React 属性） | 位置更新必须走 React 提交，无法命令式更新 |

结构性矛盾：**「滚动位置变化」与「行内容变化」被绑定在同一个 React 渲染通道里**。滚动时内容不变，但位置全变 —— 正确的架构是「位置变化走命令式 DOM，内容变化才走 React」。

#### 6.2 修复方案：rAF 合并 + 命令式位置更新（滚动帧零 React 提交）

**A. 滚动事件合并**：

```
scroll（passive: true，绑定在容器上）
  → scrollTopRef.current = e.target.scrollTop
  → 若无挂起 rAF：requestAnimationFrame(onFrame)
onFrame():
  → 窗口计算：blockAt(scrollTopRef.current)（O(log n)，问题 1 的树）
    firstIdx/lastIdx 与当前窗口比较
  → 若窗口未变化：
      仅命令式更新已挂载行的 top（style.transform/translateY，或直接改 style.top）
      → 本轮零 React 提交
  → 若窗口变化：
      卸载滚出窗口的行，挂载新行（React，仅新行）
      已挂载行位置仍走命令式
```

**B. 行位置更新去 React 化**：

- 每行 ref 注册表：`rowRefs: Map<index, HTMLElement>`；
- rAF 帧内直接写 `el.style.top = (top + scrollDelta) + 'px'`（对窗口内所有行一次批量写，无 React 参与）；
- 视觉同步用「容器整体 `translateY` + 行绝对定位」或「每行绝对 top」二选一：推荐**每行 `translateY` 增量**（相对上次帧的 delta，避免大数精度问题）——`el.style.transform = translate3d(0, ${top}px, 0)`，position 绝对定位不变。

**C. LineItem 的 props 稳定化**（窗口内容变化帧也受益）：

- `virtualRow` 对象由 React 侧自行缓存（`useMemo` 化的行描述对象 `{index, top, key}`），只把 `index/top` 作为 props；
- 或更进一步：行内容（text/offset/isCode）与位置（top）拆成两个 props，位置变化不触发内容子树渲染（React.memo 按字段比对——`top` 变则必须渲染，所以滚动帧仍需命令式路径，A+B 才是根治）。

**D. 光标层的滚动跟随**：光标测量在滚动帧走「已测量坐标 + scrollTop 增量」的算术更新（无 DOM 读取），仅当窗口内容变化时才重新测量（问题 2 的缓存随之更新）。

#### 6.3 收益量化

- 滚动帧 React 提交数：每次 scroll 事件 1 次 → 每帧 ≤1 次（窗口变化时）或 0 次（纯位置滚动）；
- 窗口 reconcile 量：全量 80+ 行 → 仅挂载/卸载的新行；
- 这是 120/140fps 目标的**决定性优化**（滚动是最高频交互路径）。

### 问题 7：跨视口箭头导航退化为行首/行尾

#### 7.1 根因定位

| 位置 | 代码 | 问题 |
|---|---|---|
| `src/core/measure.ts:301-312` | `getArrowNavigationIndex`：`container.querySelector(\`[data-index="${targetIdx}"]\`)` 找目标行 DOM | 目标行在视口外 → 未挂载 → 返回 null |
| `measure.ts:305-311` | null 时回退：上箭头回行首、下箭头回行尾 | **列位置（X 坐标）丢失**，跨屏箭头导航体验断裂 |
| `measure.ts:321-332` | `caretRangeFromPoint` 分支 | 仅视口内有效，视口外目标行不可测量 |

#### 7.2 修复方案：数据层列保持 + 字符宽度预测 + 两帧校正

```
getArrowNavigationIndex(cursorPos, dir, container):
  // 1) 当前列 X 坐标（问题 2 的 O(1) 测量，仅 1 次 Range）
  currentX = measureX(cursorPos)
  // 2) 目标行：纯数据层（LineOffsetTree，O(log n)）
  targetIdx = 当前行 ± 1
  targetLine = lines[targetIdx]                       // 百万行数组 O(1) 取行文本
  // 3) 目标行在视口内 → 现状 DOM 测量路径（保持）
  if targetIdx 在窗口内: 现有 caretRangeFromPoint/二分路径
  // 4) 目标行在视口外 → 字符宽度预测 + 滚动跟随
  else:
    colHint = clamp(round((currentX - 行左缘) / charWidthOracle), 0, targetLine.length)
    newPos  = offsets.getOffset(targetIdx) + colHint   // O(log n)
    // 两帧校正：先滚动视口到目标行，下一帧（目标行已挂载）用真实测量校正列位置
    schedule(下一帧 → measureX 校正 newPos)
    return newPos
```

- `charWidthOracle`：全局单次测量（CM6 `measureTextSize` 同款，docview.ts:433-467）；本引擎为等宽字体族（`--font-mono`，index.css:35-38），列预测误差 ≤ 2px，进入视口后一帧校正即可；
- 不需要为每行缓存字符宽度表（代价过高）；等宽字体 + 两帧校正方案在准确性/成本上最优；
- 现有「邻域 ±2 检查」（measure.ts:368-380）保留，覆盖 kerning 等局部波动。

#### 7.3 收益量化

- 跨屏上下箭头：列位置保持率从 0% → ~100%（±1 字符内）；
- 每次箭头导航成本：O(log n) + 1 次 Range（视口内）或 O(log n)（视口外 + 一帧后 1 次 Range）。

### 问题 8：表格行高依赖单元格 wrap —— 与固定行高模型冲突

#### 8.1 根因定位

| 位置 | 代码 | 问题 |
|---|---|---|
| `src/index.css:235-244` | `.line-table-row { min-height: 28px; display:flex }` | 名义 28px |
| `index.css:279-295` | `.token-table-cell { padding: 6px 12px; line-height:1.5; word-break:break-word; overflow-wrap:break-word }` | 单行文字 21px + padding 12px = **33px > 28px**；内容换行 → 行高随内容变化 |
| `MarkdownEngine.tsx:112` | `estimateSize` 表格分隔 0、其他 28 | 与 33px+ 实际不符 |
| `MarkdownEngine.tsx:74,408` | `measureElement` 实测回填 | 表格行高度由**单元格内 wrap 文本**决定 → 高度是内容函数 → 与「预测-实测」模型耦合 |
| `src/core/TableStore.ts:16-50` | `setColumnWidth/setTableWidths`（当前无调用方，列宽暂为 flex 均分） | 列宽一旦可调，wrap 变化将**级联改变整表所有行高** → 测量回环放大 |

测量回环机制：RO 实测表格行高 33px → 回填 → 该行 offset 变化 → 同一表格相邻行与后续行重排 → 若相邻行也有 RO → 再次触发测量 → 抖动/回环。

#### 8.2 修复方案：表格行高 = 预测 + 整表失效标记 + 稳定点检测

**A. 行高 Oracle 的表格分支**（问题 1 的 oracle 扩展）：

```
oracleTableRow(line, colWidths, cellTexts):
  // 每列 wrap 行数 = ceil(该列文本宽 / (colWidth - 2×12px padding))
  maxRows = max(1, max over cols of ceil(textWidth(col) / (colWidth(col) - 24)))
  return maxRows × 21 + 12          // 21 = 14px × 1.5 line-height，12 = 上下 padding
```

**B. 打破回环**：
- **整表失效标记**：表内任一单元格内容/列宽变化 → 该表全部行的实测标记失效，下一测量阶段整表批量回填（一次 RO 回调完成，避免逐行回填抖动）；
- **稳定点检测**（CM6 `Epsilon` 同款）：实测与预测偏差 < 0.5px → 不回填；表内所有行都收敛时，行高不再写回树 → 回环终止；
- 表格分隔行高度 0（MarkdownEngine.tsx:81 + index.css:252-260 已有），维持。

**C. 可选简化**（若产品允许）：单元格 `white-space: pre`（不 wrap，横向滚动）→ 表格行高恒定为 33px，彻底移除 wrap 变量——但会改变现有表格阅读体验，作为备选方案记录，默认走 A+B。

#### 8.3 收益量化

- 表格行高预测准确率：首次预测误差 ≤ 1 行；回环触发次数 → 0（稳定点收敛）；
- 表格密集文档（如 1000 行表格）的滚动条失真消失。

## 二、关键数据结构汇总（合并到实现的蓝图）

| 结构 | 对应问题 | 说明 |
|---|---|---|
| `HeightMap`（平衡树：叶子=行，节点聚合 height/length/lineCount） | P1/P6/P7 | 双向定位：`lineAt(pos)` / `blockAt(top)` / `measureBackfill()`，path copying 更新 |
| `HeightOracle`（lineHeight/charWidth 全局度量 + 类型倍率 + wrap 预测） | P1/P7/P8 | 替代 `estimateSize`；不可预测行（math/表格）走实测样本表 |
| `LineMeasureIndex`（行级 token → textNode 二分索引） | P2 | 行挂载时构建，卸载即弃；与 P6 生命周期共用 |
| `LineOffsetTree` COW（块共享 + 触及块克隆） | P3/P4/P5 | 击键/流式/undo 全部 O(局部) |
| `blockStatePrefix`（每行 2bit 块状态前缀） | P4 | fence 初始状态 O(1) |
| `rowRefs + rAF 滚动帧调度器` | P6 | 命令式位置更新，滚动帧零 React 提交 |
| 表格整表失效标记 + 稳定点 | P8 | 防测量回环 |

## 三、优化项依赖关系（DAG）

```
P3 LineOffsetTree COW（数据层地基，击键/流式/undo 共用）
 └─→ P4 fence 前缀状态（块摘要挂靠 COW 的更新流程）
      └─→ P5 appendText 冲突检测（追加路径与插入路径同价后，冲突策略才有意义）

P1 行高模型 HeightMap（定位骨架，滚动/光标的公共地基）
 ├─→ P6 滚动管线（依赖 blockAt(top) O(log n) 窗口计算与测量回填）
 │    └─→ P2 坐标测量缓存（依赖 P6 的行挂载/卸载生命周期钩子与滚动帧通道）
 ├─→ P7 跨视口箭头导航（依赖 lineAt/charWidth oracle；视口内路径依赖 P2）
 └─→ P8 表格行高（oracle 的表格分支；稳定点依赖 P1 的回填护栏）

P9 帧率目标 = P3+P4+P5（击键路径）∩ P1+P6+P2（滚动/测量路径）∩ P8（表格）∩ P7（体验）
```

**必须先做的两项**：P3（数据层）与 P1（定位骨架）。理由：P3 是三个击键路径问题（P4/P5）的依赖，P1 是三个滚动/测量问题（P6/P2/P7）的依赖；两者互不依赖，可并行。P6 是 140fps 达标的最关键单项，但它需要 P1 提供 O(log n) 窗口计算，故排 P1 之后。

## 四、帧率预算分解

### 4.1 总预算与场景划分

三种典型帧场景，预算口径 = **JS 阶段 + 浏览器 layout/paint 阶段**（GPU 合成不计）：

| 场景 | 触发 | 频率假设 | 优化前 JS 成本（百万行估计） | 优化后目标 |
|---|---|---|---|---|
| 滚动帧 | 滚轮/触摸板 | 每秒 60-144 次 | 3-8ms（全量 reconcile + 双份测量） | ≤1.5ms |
| 击键帧 | 打字/箭头 | 每秒 10-30 次 | 2-6ms（clone + fence 重放 + 双份测量） | ≤1ms |
| 流式帧 | 500 token/s 注入 | 每秒 ≤60 次 burst | 每 chunk O(全文) clone + 全量渲染 | 每 chunk ≤1ms，且行渲染仅新增行 |

### 4.2 逐帧预算分配表（优化后，单位 ms）

| 阶段 | 内容 | 60fps（16.6ms） | 120fps（8.3ms） | 140fps（7.1ms） |
|---|---|---|---|---|
| 1. 事件处理 | scroll/input/keydown 事件分发（含 rAF 合并调度） | 0.1 | 0.1 | 0.1 |
| 2. 数据层更新 | insertText/appendText：COW（O(256)）+ fence 前缀 O(1) + 光标平移 | 0.15 | 0.15 | 0.15 |
| 3. 窗口计算 | `blockAt(top)` / `lineAt(pos)`（O(log n)）+ 挂载/卸载 diff | 0.05 | 0.05 | 0.05 |
| 4. 光标测量 | 1 次 Range + 行级索引二分（滚动帧：算术增量，0 DOM 读取） | 0.2 | 0.2 | 0.2 |
| 5. React 提交 | 仅窗口变化帧：新行挂载/旧行卸载（≤20 行，parseLine LRU 命中 + memo 稳定 props）；滚动纯位置帧：**0**（命令式 transform） | 0.5-1.0 | 0.5-1.0 | 0.5-1.0（仅变化帧；位置帧 0） |
| 6. 浏览器 layout+paint | 内容 DOM 增删的增量 layout + 文本 paint | 3-5 | 2-3.5 | 1.5-2.5 |
| 7. 预留 | GC、帧调度抖动、overscan 挂载突刺 | 1.5 | 1.0 | 0.8 |
| **合计** | | **5.5-8.0** | **4.0-6.0** | **3.3-4.8** |

达标解读：
- **60fps 保底**：仅需 P1+P2+P3+P4（消除结构性 O(全文)/O(全扫)）即可稳定压线；
- **120fps**：叠加 P6 的 rAF 合并（滚动帧从「每事件一次提交」→「每帧 ≤1 次」）与 P5/P8（消除流式冲突与测量回环的抖动源）；
- **140fps**：必须 P6 的**命令式位置更新**（滚动位置帧零 React 提交）+ P2 的滚动帧算术跟随（零 DOM 读取）。关键约束：滚动帧预算（1+3+4 阶段 ≈ 0.35ms JS）内不能出现任何 React 渲染、querySelectorAll、getBoundingClientRect 调用。

### 4.3 500 token/s 流式专项预算

- 流式 burst（LLM 单次吐 500 token ≈ 2500-3500 字符 ≈ 60-80 行/秒）：StreamBuffer 按 rAF 合并（`StreamBuffer.ts:16-28` 已实现），每帧注入 ≤1 个 chunk；
- 每 chunk 数据层：COW 追加 O(256)（P3）→ 0.05ms；渲染：仅新增行挂载（P6 的 diff 机制天然只挂新行）→ 每帧新增 1-2 行 ≈ 0.2-0.5ms；
- 光标冲突（P5）保证追加点语义稳定，不引入额外渲染；
- 结论：流式路径在优化后每帧额外成本 ≤0.6ms，60fps 下完全吸收；**不占用滚动预算**。

## 五、验证方法（每项收益的量化手段）

### 5.1 通用测量设施（先建）

- `perf` 探针：模块级 `performance.now()` 打点计数器（挂 `window.__CRISH_PERF__`），覆盖：数据层更新、窗口计算、光标测量、React 提交、rAF 帧间隔；
- 帧率统计：连续 rAF 打点 3 秒，输出均值/P95/P99 与 60/120/144Hz 分位；
- 强制刷新率测试：Chrome DevTools 的「Frame Rendering Stats」+ `--force-device-scale-factor` 无关；直接用 `requestVideoFrameCallback` 或 rAF 间隔统计。
- DevTools Performance 录制分离 JS / Layout / Paint 三段耗时。

### 5.2 分项验证

| 问题 | 量化指标 | 方法 |
|---|---|---|
| P1 行高 | ① 滚动条准确性：`scrollTop = 总高×50%` → 树预测的 `blockAt` 行号 vs 实际渲染首行行号，误差行数；② 测量回环次数（RO 回调计数）；③ `totalSize` 与实测总高偏差 | 专用测试页：百万行混合文档（长行/标题/表格/math 穿插），程序化滚动采样 20 个位置 |
| P2 坐标测量 | 单次 `getCoordinatesFromIndex` 耗时（万次平均）、每击键 DOM 读取次数（Performance 面板 Layout 事件数）、滚动期间光标测量调用次数（探针计数） | 击键/滚动录制 + 探针 |
| P3 clone | `clone()` 单次耗时随行数（100 万/500 万/1000 万）曲线；击键端到端延迟（keydown → 光标更新） | 探针 + 脚本化击键 |
| P4 fence | 编辑点前 fence 数 vs 单次击键耗时（构造头部 5000 代码块文档，编辑第 1 行） | 探针 |
| P5 冲突 | 状态机测试：流式注入中用户在末尾行中间打字 → 断言字符顺序、光标位置、选区平移正确 | vitest 单测（EditorStore 直接调用 appendText/insertText） |
| P6 滚动 | 滚动期间 rAF 帧间隔 P95、每帧 React 提交次数（`__CRISH_PERF__.commits`）、滚动 JS 总耗时 vs Layout 耗时 | 触摸板惯性滚动录制 + 探针 |
| P7 箭头 | 跨屏上下箭头 50 次：目标列偏差（字符数）、是否退化行首/行尾 | 自动化键盘事件 + 断言 cursorPos |
| P8 表格 | 表格行高预测误差（首次挂载）、RO 回环计数、表格密集文档滚动条误差 | 同 P1 方法，表格专项文档 |
| P9 综合 | 三场景（滚动/击键/流式）分别的帧间隔 P95/P99 与 60/120/144Hz 达标率 | 综合性能测试页 + 探针汇总 |

### 5.3 回归与门禁

- 现有门禁不动：`npm test`（tests/unit，grapheme/undo/parser-redos/chunk）必须全绿——P3/P4/P5 改动直接影响 EditorStore，需补：COW 不变式（clone 后旧树独立）、fence 前缀等价性（与线性重放结果逐位一致）、appendText 冲突状态机；
- 新增 perf 套件：`tests/perf/`（独立 vitest 项目，不进常规门禁，`npm run test:perf` 手动/CI 定时跑），断言预算：clone 耗时 < 0.5ms（百万行）、fence 初始状态 < 0.1ms、单次坐标测量 < 0.5ms、滚动帧 JS < 2ms；
- 主仓库 e2e 的 markdown-editor 专项 spec（ast-block-tables/format-checker/ime-composition/keyboard-navigation/wysiwyg-interaction）回归保留，重点盯 keyboard-navigation（P7 改动）与 wysiwyg-interaction（P2/P6 改动）。

## 六、附：与 CM6 基准实现的关键对照表

| 能力 | 现状（markdown-editor） | CM6（基准） | 本路线目标 |
|---|---|---|---|
| 行高预测 | `estimateSize` 5 类前缀（MarkdownEngine.tsx:106-114） | `HeightOracle.heightForLine`（heightmap.ts:29-33） | 类型倍率 + wrap 模型 + 样本校准 |
| 未测量区域 | 无（按估计值直算） | `HeightMapGap` perLine/perChar 插值（heightmap.ts:345-471） | 同构实现 |
| 滚动定位 | 虚拟器线性窗口 | `blockAt` O(log n)（heightmap.ts:483-487） | 同构实现 |
| 测量回填 | `measureElement` 全量 RO | `MeasuredHeights` 可见行批量回填（heightmap.ts:433-462） | 同构 + 稳定点护栏 |
| 文档超高防护 | 无 | `BigScaler`/7e6px（viewstate.ts:58,695） | 百万行文档（~2.8 万 px 高）暂不需要；千万行级启用 |
| 变更映射 | clone 全量 | HeightMap `replace` path copying（heightmap.ts:515-533） | COW 块级 path copying |
