# 04 编辑深度扩展分析：自研 Markdown 渲染引擎的编辑器能力路线

> 分析对象：`reference/markdown-editor`（React + Zustand + react-virtual 的 markdown 源码编辑器）
> 参考实现：`reference/compare/codemirror-view`（bidi.ts / input.ts / draw-selection.ts / domchange.ts / rectangular-selection.ts）与 `reference/compare/prosemirror-view`（domchange.ts 事务与 DOM 兜底）
> 定位：纯分析文档，产出编辑能力维度的扩展路线，供主 Agent 决策排期。
> 结论先行：**引擎当前的编辑内核是「隐藏 textarea + 逻辑索引状态机」，在单字节 LTR 纯文本输入上已闭环；所有深度能力（RTL、IME 深水区、选区方向性、事务抽象、剪贴板语义、无障碍、协作）的共同根因是同一个：编辑器状态缺少「事务/变更」抽象层与「方向性（anchor/head、assoc、bidiLevel）」字段。先补这两块地基，其余能力才能逐个挂载。**

## 0. 引擎现状速览（编辑链路全景）

编辑链路由四个文件构成：

| 文件 | 职责 | 关键行号 |
|---|---|---|
| `src/components/HiddenInput.tsx` | 键盘/IME/选区入口，隐藏 textarea 定位 | 全局 637 行 |
| `src/components/CursorLayer.tsx` | 光标绘制（逻辑索引 → 坐标） | 光标隐藏条件 74 |
| `src/components/SelectionHighlight.tsx` | 选区高亮（行级矩形拼接） | 全局 101 行 |
| `src/core/EditorStore.ts` | 文档/光标/选区/undo 状态机 | undo 758-840、merge 484-508 |
| `src/core/measure.ts` | 逻辑索引 ↔ DOM 坐标双向映射 | getCoordinatesFromIndex 1-117、getGlobalIndexFromDOMNode 193-256 |
| `src/core/SegmentTree.ts` | LineOffsetTree 行偏移分段树 | 块大小 256 行、clone 209-213 |

核心数据模型：

- **文本**：`lines: string[]` + `LineOffsetTree`（两级块、每行长度含换行符），逻辑索引 = 全局字符偏移。
- **光标/选区**：`cursorPos` + `selectionStart` + `selectionEnd` 三个数字，**选区无方向**（归一化为 min/max，cursor 恒等于 end）。
- **撤销**：`EditorOperation`（行级 splice 记录 + 光标前后状态 + timestamp），500ms 窗口内合并。
- **DOM 映射**：每个 token 渲染为带 `data-token-start` / `data-token-length` / `data-sub-offset` 的 span；坐标测量走 `Range.getBoundingClientRect()`；点击回写走 `caretRangeFromPoint` → `getGlobalIndexFromDOMNode`。
- **输入**：隐藏 textarea（1px、opacity 0）浮在光标处，onChange → `insertText`，composition 期间整体忽略。

已具备的基础能力（不重复论证）：grapheme 边界移动/删除（`Intl.Segmenter`，EditorStore.ts:11-131）、方向键跨行导航（坐标二分，measure.ts:274-383）、列表续写/缩进（HiddenInput.tsx:379-495）、表格 Excel 交互（TableStore + TableOperations）、流式追加快速通道（appendText）、十万行级虚拟化。

## 1. Bidi / RTL 混排

### 1.1 现状

**引擎对 bidi 零感知**：`grep direction|dir=|bidi|rtl` 在 `src/` 全部无命中。当前行为完全依赖浏览器原生 UAX#9：

- 渲染层：token span 按逻辑顺序排布，浏览器自动重排，**显示是正确的**（这一点与 CM6 相同——CM6 的 bidi 算法也不是为了排版，而是为了「光标移动/选区边界」的视觉语义）。
- 光标定位：`getCoordinatesFromIndex` 用 Range 测量（measure.ts:87-112），Range 反映重排后的视觉位置 → 光标视觉上贴住字符，**在 RTL 文本内光标显示正确**。
- **方向键是逻辑移动**：ArrowLeft/ArrowRight 直接调 `findPrevGraphemeBoundary` / `findNextGraphemeBoundary`（HiddenInput.tsx:347-372），**在 RTL 段落中方向与视觉相反**（按下 → 光标向左视觉跳动）。
- 选区高亮：SelectionHighlight 用「行矩形 + startCoord.left / endCoord.left 裁剪」（SelectionHighlight.tsx:41-76），在 RTL 行中 start/end 的 x 坐标互换，**高亮矩形错误**。
- IME 候选窗：textarea 定位在光标的视觉坐标上，候选窗锚定正确。

### 1.2 差距

| # | 差距 | 严重度 |
|---|---|---|
| B1 | ArrowLeft/Right 在 RTL/双向行中方向相反（视觉移动缺失） | 高（直接功能错误） |
| B2 | 选区无 assoc/bidiLevel，光标落在 LTR/RTL 边界时「左右两侧」不可区分 | 高（影响 B1 修复） |
| B3 | SelectionHighlight 行内裁剪在 RTL 行错误 | 中 |
| B4 | Ctrl+Arrow 词移动（当前无）若实现也需 bidi 感知 | 低（能力未建，一并设计） |
| B5 | 无 per-line bidi 缓存，大文件 RTL 行全量计算有性能风险 | 中（算法常数大） |

### 1.3 方案（移植 CM6 bidi.ts 的简化结构）

CM6 bidi.ts 的算法骨架（457 行，纯函数、无 DOM 依赖，可直接移植）：

1. **字符分类**（bidi.ts:60-67）：`charType(ch)` 查静态表（`LowTypes` 0x00-0xF7、`ArabicTypes` 0x600-0x6F9 两段查表）+ 区间判断（希伯来 0x590-0x5F4 → R，阿拉伯 0x600-0x8AC → AL/R，隔离符 0x2000-0x200C → NI）。引擎只需这两张表 + 区间，约 120 行。
2. **规则扫描**（bidi.ts:135-277）：`computeCharTypes`（W1/W2/W3/W5/W6/W7，NSM 继承前类型、数字前后向强类型归类）→ `processBracketPairs`（N0，括号配对方向）→ `processNeutrals`（N1/N2，中性字符取上下文）。每行线性一遍。
3. **span 生成**（bidi.ts:283-404）：`emitSpans` 按 level 正/反向扫描，产出 `BidiSpan[]{from, to, level}`（level 奇 = RTL）。`computeOrder` 提供快速路径：无 RTL 字符（`BidiRE` 不命中）直接返回单个 LTR span——**引擎绝大多数 markdown 行走此快速路径，性能无虞**。
4. **视觉移动**（bidi.ts:425-448）：`moveVisually(line, order, dir, range, forward)`——基于 span 序求「当前字符的视觉邻居」，返回新位置 + assoc + bidiLevel。这是方向键的替换实现。

引擎侧改造面：

- `SelectionRange` 概念升级：`cursorPos` 增加伴生字段 `assoc: -1|0|1`（光标偏左/居中/偏右）与 `bidiLevel`（光标当前所在 span 的 level）。参考 CM6 的 `SelectionRange{head, assoc, bidiLevel}`。
- 新模块 `src/core/bidi.ts`：移植 charType/扫描/BidiSpan/moveVisually，配 `computeLineOrder(line, dir)`，结果按行号缓存（复用现有 `LRUCache.ts`，以「行文本 hash + 方向」为 key；行文本变化即失效）。
- `measure.ts` 不动：坐标测量与 bidi 无关（Range 已正确）。
- `getArrowNavigationIndex` 不动：上下键是行间导航，与 bidi 无关。
- 选区高亮：SelectionHighlight 对 RTL 行改用 `order` 折算——先求 span 序列，行内裁剪按「视觉顺序」映射逻辑区间。

### 1.4 接入点

| 接入点 | 改动 |
|---|---|
| `HiddenInput.tsx:347-372` | ArrowLeft/Right 分支改调 `moveVisually`；shift 扩展语义同步升级（见 §3） |
| `EditorStore.ts` 状态 | 增加 `assoc`、`bidiLevel` 字段（可先默认 0） |
| 新文件 `src/core/bidi.ts` | 移植算法 + LRU 缓存 |
| `SelectionHighlight.tsx:41-76` | RTL 行按 span 裁剪 |

## 2. IME 深水区

### 2.1 现状

当前实现（HiddenInput.tsx:569-593）：

- `handleCompositionStart`：置 `isComposing`（组件局部 + store 双份）。
- `handleCompositionEnd`：**只插入 `e.data`**，然后清空 textarea。
- `handleInput`：`if (isComposing) return;`——composition 期间所有 onChange 被忽略。
- Enter 处理：`if (isComposing) return;`（HiddenInput.tsx:381），防合成确认键误触。
- 候选窗锚定：composition 期间 textarea 变 300px 宽、opacity 1（HiddenInput.tsx:613-615）。
- 光标隐藏：`CursorLayer.tsx:74` 在 composing 时不画光标。
- 撤销粒度：一次合成 = compositionend 的一次 `insertText` = 一个 undo 步（粒度正确）。

### 2.2 差距

| # | 差距 | 说明 |
|---|---|---|
| I1 | **compositionend 只信 `e.data`，丢字风险** | Android / 部分 IME（Safari dead-key、Chrome Android）compositionend 的 `data` 为空或不可靠，但 `textarea.value` 里已有提交文本。当前代码在 `e.data` 为空时什么都不插——**真实丢字路径**。CM6 的做法是 compositionend 后检查 pending DOM 变更（`compositionPendingChange`，input.ts:63）并 flush |
| I2 | **composition 中途变更无记录** | 引擎靠「忽略 onChange」回避问题；但浏览器可能在合成中途 flush 文本（候选替换、Android 预测、拼写纠错 `insertReplacementText`），这些变更被丢弃。CM6 用 `composing` 计数（-1 非合成 / ≥0 计数）+ `compositionFirstChange` 标记（input.ts:49-63）把整个合成期变更归入同一事务组 |
| I3 | **无 beforeinput 处理** | `insertCompositionText` / `insertReplacementText` / Android 的 Backspace/Enter（`deleteContentBackward` / `insertParagraph`）全部没接。CM6 用 beforeinput 在 Android 模拟按键（input.ts:854-907），iOS 处理 dead-key 合成收尾 |
| I4 | **合成被拆散时撤销粒度失控** | 若 IME 在一次合成中产生多次变更（候选替换等），每次 `insertText` 因 `inserted.length > 1` 不合并（EditorStore.ts:489 条件），产生多个 undo 步，与「一次合成 = 一步撤销」的期望不符 |
| I5 | **泰文/印度文组合** | grapheme 层已正确（Segmenter 处理 delete/移动）；缺口在 Enter 列表续写/输入过滤不感知 grapheme——属边缘，风险低，需补测试而非改逻辑 |

### 2.3 方案（对齐 CM6 合成状态机）

1. **状态机升级**：`isComposing: boolean` → `composing: -1 | number`（计数）+ `compositionGroupId`（每次 compositionstart 生成自增 id）。语义：composing ≥ 0 期间的所有文本变更都带 `compositionGroupId` 进入 `insertText`。
2. **提交语义**：compositionend 时**以 `textarea.value` 为准**而非 `e.data`（value 是浏览器最终承诺文本；e.data 仅作参考）。若 value 为空但 DOM/内部有 pending 变更（如 Android），用 setTimeout 50ms 兜底 flush（对齐 input.ts:843-847 的清理策略）。
3. **beforeinput 接线**（新）：`insertText` / `insertCompositionText` / `insertReplacementText` → 直接走引擎 `insertText`（带 compositionGroupId）；`deleteContentBackward` / `deleteContentForward` / `insertParagraph` → 复用现有 deleteText/Enter 逻辑（这是 Android 无可靠 keydown 的补丁通道）。
4. **撤销合并扩展**：`EditorStore.insertText` 的合并条件在「500ms + 同行 + 单字符」之外增加**「同 compositionGroupId」合并**（合成期间的多次变更合并为一个 undo 步），合并时不检查 `inserted.length === 1`。
5. **候选窗交互**：维持「composing 期间 textarea 放大可见」策略（已对）；补充 Safari 特判——Enter 确认合成后 100ms 内的 keydown 忽略（对齐 input.ts:179-182 的 Safari 乱序补丁）。
6. **测试**：新增 IME 专项（vitest + Playwright 合成事件模拟）：中文合成一次撤销、候选替换拆段合并、Android 空 data 丢字回归。

### 2.4 接入点

| 接入点 | 改动 |
|---|---|
| `HiddenInput.tsx:569-593` | composition 三件套重写（value 优先、pending flush、beforeinput 监听） |
| `EditorStore.ts:433-518` | insertText 增加 `compositionGroupId?` 参数与合并规则 |
| `EditorStore.ts:146-175` | 状态字段 `composing` / `compositionGroupId` 替换 `isComposing`（CursorLayer.tsx:18 同步消费） |

## 3. 选区模型

### 3.1 现状

- 状态：`selectionStart` / `selectionEnd` **归一化**（min/max），`cursorPos` 恒等于 end（EditorStore.ts:422-431）。**没有 anchor/head 方向**。
- Shift+方向键扩展：启发式 `selectionStart === cursorPos ? newPos : selectionStart`（HiddenInput.tsx:350-371）——只在「光标恰好停在选区一端」时正确。**反向扩展（Shift+Left 后 Shift+Right）第二次方向即错误**：光标已离开选区端，条件不再满足。
- 词级/行级：无 Ctrl+Arrow 词移动；Home/End 有行首尾（534-566）；PageUp/PageDown 无。
- 鼠标拖选：依赖原生 DOM 选区 + `selectionchange` → `getGlobalIndexFromDOMNode`（HiddenInput.tsx:88-137）。**虚拟化视口外（overscan 40 行）DOM 不存在 → 拖出视口选断裂**；跨行拖选依赖浏览器原生行为，引擎无法控制粒度。
- 双击/三击：无词/行选择语义（浏览器原生双击在 token 上工作，但引擎的 selectionchange 处理只认 `s !== e` 的拖选，双击选词结果被 store 吸收时方向/粒度由 DOM 决定）。
- 多选区 / 矩形选区：无。表格有独立 cell 选区（TableStore），与文本选区互斥。
- 选区渲染：SelectionHighlight 只覆盖**DOM 中存在的行**（`querySelectorAll('[data-line-start]')`，SelectionHighlight.tsx:38），虚拟化外的高亮天然缺失。

### 3.2 差距

| # | 差距 | 严重度 |
|---|---|---|
| S1 | **无 anchor/head：反向扩展语义错误** | 高（最常用交互） |
| S2 | 拖选出虚拟化视口断裂 | 高（大文档常见） |
| S3 | 无词级选择（Ctrl+Arrow / 双击）与行选择（三击） | 中 |
| S4 | 多选区、矩形选区（Alt+drag）缺失 | 低（能力面） |
| S5 | 选区高亮不覆盖视口外行 | 中（与 S2 同根） |

### 3.3 方案

1. **选区模型升级（第一步，地基）**：`{anchor, head, assoc}` 替代归一化三元组。`setSelection(start, end)` 保持兼容包装（anchor=start, head=end）。Shift+方向键语义改为「anchor 不动、head 移动」，方向由 anchor/head 相对位置判定，天然支持反向扩展与选区两端切换。cursorPos 恒 = head。
2. **词级移动/选择**：新增 `wordBoundary(text, pos, dir)`（基于 Unicode 分类：字母数字连串 / 空白 / 标点，或用 `Intl.Segmenter('en', {granularity:'word'})` 现成能力），接 Ctrl+Arrow（无 shift 移动 / 有 shift 扩展）；双击 → 取光标处 word 区间（与 click 的 detail 计数结合）。
3. **拖选状态机（替换原生依赖）**：参考 CM6 `MouseSelection`（input.ts:293-401）：mousedown 记录起点坐标 → mousemove 用 `caretRangeFromPoint`（已有，MarkdownEngine.tsx:182-194）→ `getGlobalIndexFromDOMNode` 转索引；**目标行不在 DOM（虚拟化外）时用坐标定位行 + 二分求列**（`getArrowNavigationIndex` 已沉淀该算法，measure.ts:334-382 可直接复用），彻底解决 S2。mouseup 结算。双击/三击用 `event.detail` 计数区分。
4. **矩形/多选区**：标为远期。矩形选区参考 rectangular-selection.ts:12-73（Alt+drag → 每行一个 range）；多选区需 selection 数组化，是独立大改造，本阶段只保证数据结构（anchor/head）不堵死未来。
5. **SelectionHighlight**：行级矩形方案保留；S2 修复后视口内高亮自然正确。跨行空行最小宽度逻辑（SelectionHighlight.tsx:64-67）保留。

### 3.4 接入点

| 接入点 | 改动 |
|---|---|
| `EditorStore.ts:146-175, 412-431` | 状态模型升级（anchor/head/assoc），所有 setSelection 调用点同步 |
| `HiddenInput.tsx:347-371, 496-566` | 方向键扩展语义重写；新增 Ctrl+Arrow / 双击词选择 |
| 新文件 `src/core/mouse-selection.ts` | 拖选状态机（mousedown/mousemove/mouseup 纯逻辑 + 事件接线） |
| `src/core/word.ts`（新） | wordBoundary 实现（或并入 bidi.ts 模块） |
| `SelectionHighlight.tsx` | 基本不动（行级方案兼容） |

## 4. 事务与撤销完善

### 4.1 现状

- `EditorOperation`（EditorStore.ts:133-144）：行级 splice 记录 `{startLineIdx, removedLines, insertedLineCount, 光标/选区前后, timestamp}`。
- 三个变更入口各自 push：`insertText`（433-518）、`deleteText`（600-695）、`deleteSelection`（697-756）。
- 合并规则：insertText 500ms 内同 `startLineIdx` + `inserted.length===1` + 非换行（484-508）；deleteText 500ms 内同 `startLineIdx` + `insertedLineCount===1`（660-685）。
- **`appendText` 完全不进 undo 栈**（注释明示「流式尾部追加快速通道」，520-598）——设计如此，但带来断层（见 U2）。
- **表格操作绕过 store**：HiddenInput.tsx:213/240/260/278/297/444 直接 `useEditorStore.setState({ lines: res.newText.split('\n') })`——**不进 undo、不更新 lineOffsets / codeBlockState / textLength**（updateLinesIncremental 是唯一正确入口，被绕过）。
- `undo`/`redo`（758-840）：逆操作重建 + 互推栈。

### 4.2 差距

| # | 差距 | 严重度 |
|---|---|---|
| U1 | **表格操作不落 undo、不走统一变更管道** | 高（撤销断层 + 状态一致性风险：直改 lines 会与 LineOffsetTree 漂移，`verifyConsistency` 会报错） |
| U2 | **流式追加（appendText）不可撤销**：流式期间无栈记录；流式后再手动编辑，undo 只能退手动编辑，「流式段」永远退不回去 | 中高 |
| U3 | **deleteText 合并规则缺陷**：打字后立即 Backspace，删除操作会并入打字 op（条件只查 `startLineIdx` 与 `insertedLineCount`，不区分 op 类型）——合并后的 op `removedLines` 仍是打字前的行，undo/redo 的逆 op 重建语义混乱 | 中 |
| U4 | **无 DOM 突变兜底**：任何绕过 store 的 DOM 变更（React 竞态、未来外部注入、表格直改）都不被感知。CM6（domchange.ts DOMChange + findDiff）与 PM（domchange.ts parseBetween + findDiff，383 行）都内置「DOM 与 doc diff → 生成补丁事务」的兜底链 | 中（风险兜底） |
| U5 | **无 change 抽象**：op 只够自身 undo/redo；CM6 的 `ChangeSet`（sections: lenA/lenB/text + mapPos）可做事务间位置映射、折叠/注解复用、OT 数据源——当前 op 结构无法承载 | 中（架构预留） |
| U6 | 合并窗口仅靠 500ms 时间戳，无「输入会话」概念（移动光标、点击后输入不应与之前合并——现状：500ms 内移动光标后同位置输入**仍会合并**，因为条件不含 cursor 移动检查） | 低中 |

### 4.3 方案

1. **统一变更入口（第一步，地基）**：新增内部事务函数 `applyChange(from, to, insert, meta)`：
   - 内部复用 `updateLinesIncremental` 的 splice 语义；
   - 自动生成 op + undo/redo 互推 + 光标/选区映射（对齐 PM `tr.replace + mapping` 的思路）；
   - **表格操作全部改走它**（TableOperations 返回纯 diff，由调用方提交事务），一举修复 U1。
2. **op 增加类型与元数据**：`{type: 'insert'|'delete'|'replace'|'append'|'table', userEvent: 'input.type'|'delete'|'paste'|'drop'|'table.*'}`（对齐 CM6 userEvent 注释体系，input.ts:389-391）。
3. **合并规则重构**：
   - 基于「连续输入会话」：500ms 窗口 + 相邻位置（`cursorAfter === from`）+ 类型相同 + **光标未跳变**（修复 U6）；
   - 修复 U3：delete 只与 delete 合并、insert 只与 insert 合并，类型不符不合并；
   - **appendText 生成可折叠 op**：连续 append 合并为单个 op（undo 一次退完流式段，修复 U2），期间手动编辑打断合并。
4. **DOM 兜底（渐进式，参考 PM domchange.ts）**：新模块 `src/core/dom-observer.ts`：
   - `MutationObserver` 监听 engine-container，仅在「非 composition、非程序化更新窗口、非表格拖拽」期间激活；
   - 变更时按 `data-line-start` / `data-token-start` 序列 diff DOM 文本与 store 文本（复用 getGlobalIndexFromDOMNode 的逆向能力），产出补丁 → 走 applyChange；
   - 首期只做「校验 + console 告警 + 尝试重同步」，不做自动回写（避免与 React 渲染循环打架）；稳定后再考虑完整回写。
5. **ChangeSet 预留（远期）**：op 增加 `from/to/insert` 位置级字段（现可行级字段可推导），为多选区映射与协作铺路（见 §7）。

### 4.4 接入点

| 接入点 | 改动 |
|---|---|
| `EditorStore.ts` | 新增 `applyChange` 事务函数；insertText/deleteText/deleteSelection/appendText 全部收敛为 applyChange 包装；op 结构扩展 |
| `HiddenInput.tsx:191-313, 435-495` | 表格交互/缩进分支改调事务 API（删除全部直改 `setState({lines})`） |
| 新文件 `src/core/dom-observer.ts` | MutationObserver 兜底 |

## 5. 复制粘贴富文本

### 5.1 现状

- 粘贴：**无 onPaste 处理**。粘贴行为 = 浏览器把剪贴板纯文本注入隐藏 textarea → `onChange` → `insertText`（HiddenInput.tsx:585-593）。多行粘贴天然正确（store 测试覆盖，clipboard.test.ts）。
- 复制/剪切：MarkdownEngine.tsx:351-381 的 onCopy/onCut 只写 `text/plain`（原始 markdown 源），cut 调 `deleteSelection`。
- 无 text/html 读写、无 linewise 复制（CM6 的「无选区复制整行」，input.ts:731-746）、无拖放（见 §8）。

### 5.2 差距

| # | 差距 | 说明 |
|---|---|---|
| C1 | **无 HTML 粘贴语义**：从网页/Word 粘贴表格、富文本结构信息丢失（textarea 只给纯文本） | markdown 源码编辑器「纯文本优先」合理，但结构增值可做 |
| C2 | **Excel/表格粘贴**：多行多列（\t 分隔）无法转 markdown 表格 | 高频场景，用户期望「粘贴即表格」 |
| C3 | 链接粘贴：纯 URL 无法包成 `[text](url)`（选区有文本时） | 小但高感知 |
| C4 | 复制无渲染语义：复制渲染文本 = 复制源码；对「所见即所得」预期不符（需产品决策：源码 vs 渲染后 markdown vs HTML） | 产品决策项 |
| C5 | 无 linewise 复制（无选区复制整行） | 中 |

### 5.3 方案

1. **onPaste 增强**（在 textarea 上监听 paste，读 `e.clipboardData.getData('text/plain'/'text/html')`）：
   - 结构检测：含 `\t` + `\n` → 用现有 `parseRowCells`（TableOperations.ts:52）反向生成 markdown 表格行 → 一次事务插入；
   - 单 URL + 选区有文本 → `[text](url)`；
   - HTML → markdown 简化转换器（h1-h6→`#`、strong/em/del→`**`/`*`/`~~`、ul/ol→列表、blockquote、pre/code→围栏、a→`[t](u)`、table→markdown 表格），实现为纯函数模块便于单测。
2. **onCopy 扩展**：按 token 结构把选区反转为 markdown（= 现状源码复制，保持）或渲染 HTML（`text/html` 写入 clipboardData，可选），由产品开关。
3. **linewise 复制**：无选区时复制整行（对齐 CM6 copiedRange，input.ts:725-746）。
4. 所有粘贴统一走 `applyChange`（§4）一次事务 = 一个 undo 步。

### 5.4 接入点

| 接入点 | 改动 |
|---|---|
| `HiddenInput.tsx` | 新增 onPaste（clipboardData 读取） |
| 新文件 `src/core/paste.ts` | html→markdown / 表格结构检测 / URL 包装（纯函数） |
| `MarkdownEngine.tsx:351-381` | onCopy/onCut 扩展（linewise + 可选 HTML） |

## 6. 可访问性（aria / 屏幕阅读器）

### 6.1 现状

- 唯一可聚焦元素是隐藏 textarea（1px、opacity 0、HiddenInput.tsx:598-635），**value 恒为 ''**（每次输入后清空，592）→ 屏幕阅读器**读不到任何文档内容**。
- 无 aria-label、无 role 声明；渲染层是大量 span token（InlineRenderer.tsx），无语义结构。
- 光标是自定义 div（CursorLayer.tsx:78-93），无 caret 语义；选区由 store 驱动的高亮 + 原生 DOM 选区双轨。
- 表格是 Excel 式键盘交互（F2/方向键/Tab），无 grid 语义。
- 已做对的事：全局 click 兜底聚焦（HiddenInput.tsx:140-148）、selectionchange 时不抢焦点（144-146）。

### 6.2 差距

| # | 差距 | 严重度 |
|---|---|---|
| A1 | SR 读不到文档（textarea value 不同步） | 高（结构性） |
| A2 | 无 aria-label / role / aria-live 反馈（撤销、粘贴等操作无声） | 高 |
| A3 | 表格无 grid 语义（role/aria-colindex 等） | 中 |
| A4 | 高对比/强制配色下光标与选区高亮依赖 CSS 变量（var(--blue-selection)），无强制配色兜底 | 低 |

### 6.3 方案

1. **短程（低成本高收益）**：
   - textarea 加 `aria-label="Markdown 编辑器"`，`role="textbox"` + `aria-multiline`；
   - **value 同步策略**：不做全文同步（大文档性能不可接受），改为同步「光标所在行文本」+ 用 `aria-live="polite"` 的静默节点播报光标位置/操作结果（对齐 VS Code 的屏幕阅读器播报思路）；
   - 容器加 `role="application"` + `aria-roledescription="Markdown 编辑器"`。
2. **中程**：提供「无障碍模式」——快捷键切换到全文普通 textarea 视图（双向同步，编辑后 diff 回 store），这是隐藏 textarea 方案的根治性兜底（CM6/PM 无此问题是因为其 contenteditable 原生可读，本引擎 DOM 是渲染态，SR 读渲染态会产生「所见非所编辑」的混乱，纯文本视图是最干净的方案）。
3. **表格**：单元格加 `role="gridcell"`、选中态 `aria-selected`（InlineRenderer.tsx table_cell 分支，229-361）。

### 6.4 接入点

| 接入点 | 改动 |
|---|---|
| `HiddenInput.tsx:598-635` | aria 属性 + value 同步策略 + 播报节点 |
| `MarkdownEngine.tsx:342-426` | 容器 role / aria-roledescription |
| `InlineRenderer.tsx:271-360` | 单元格 aria 语义 |

## 7. 协作 / CRDT 预留

### 7.1 现状（LineOffsetTree vs CM6 Text/ChangeSet 对比）

| 维度 | 本引擎 LineOffsetTree（SegmentTree.ts） | CM6 Text / ChangeSet |
|---|---|---|
| 结构 | 两级块数组（256 行/块），每行存长度（含换行） | 不可变 B-tree（`Text`），叶子是行 |
| 不可变性 | **可变 + `clone()` 深拷贝全树**（SegmentTree.ts:209-213，每次编辑全量拷贝块数组） | 天然不可变，**结构共享**（浅复制路径节点） |
| 位置语义 | 行索引 → 偏移（`getOffset`/`findLineIndex`） | 全局位置 + 行内偏移，`Text.lineAt` 等 |
| 变更表示 | `EditorOperation`：行级 splice（startLineIdx/removedLines/insertedLineCount） | `ChangeSet`：`ChangeDesc{sections: [lenA, lenB, text]} `，**位置级 diff + `mapPos` 映射** |
| 协作适配 | 行级 splice 无法表达并发字符级编辑；无块身份标识（谁的编辑、哪个片段） | 位置级 diff 可直接作 OT 载荷；`Text` 版本号支持增量同步 |

### 7.2 差距

| # | 差距 | 严重度 |
|---|---|---|
| O1 | **位置身份缺失**：全引擎以「逻辑索引」为唯一坐标，并发编辑下索引必然漂移；CRDT（yjs 相对位置 / YATA）或 OT 都需要稳定的位置身份 | 高（架构级） |
| O2 | **clone 深拷贝**：undo 已够用（栈顶即最新）；但若要做版本历史/协作快照，O(行数) 拷贝不可行——需要结构共享 | 中 |
| O3 | **op 不是位置级 diff**：行级 splice 无法精确表示「在 p 插入 n 字符」，`mapPos`（选区/注释/折叠映射）无从谈起 | 中 |
| O4 | 无 append-only 变更日志（undo 栈 pop 即弃，无法广播） | 中 |

### 7.3 方案

1. **近期（零依赖，只铺路）**：op 增加位置级字段 `{from, to, insert, removedText}`（从现有行级信息推导，成本低）；保留 append-only change log（环形缓冲，容量可配，undo/redo 之外复用）；`LineOffsetTree` 增加**版本号**（每次变更 +1，渲染层可据此判断重解析/重测量必要性）。
2. **中期（引入协作时）**：双结构策略——引入 CRDT（推荐 yjs）后，**CRDT 文本负责正确性，LineOffsetTree 退化为纯渲染索引**（CRDT 文本 → 行长度数组重建，重建成本 = 一次全量扫描，可放在 idle 回调，对齐 setText 的分块加载模式，EditorStore.ts:358-400）。ChangeSet 映射能力由 CRDT 库提供。
3. **远期**：若自研 OT/CRDT，以「行长度 + 块身份」为段身份（块在 split/merge 时继承身份），参考 CM6 Text 的结构共享做浅拷贝 clone。

### 7.4 接入点

| 接入点 | 改动 |
|---|---|
| `SegmentTree.ts` | 版本号字段 + （远期）浅共享 clone |
| `EditorStore.ts:133-144` | op 增加位置级字段 + change log |
| 渲染层（MarkdownEngine/LineItem） | 消费版本号做缓存失效 |

## 8. 其他编辑能力（拖放 / 自动补全 / 滚动 / 缩放）

### 8.1 拖放文件与文本

- 现状：无任何 drag/drop 处理。
- 方案：参考 CM6 input.ts:664-693——`drop` 事件：`dataTransfer.files` → `FileReader.readAsText`（二进制/大文件加控制字符过滤，`/[\x00-\x08\x0e-\x1f]{2}/` 模式判断）+ `insertText` 路径落盘事务；文本拖放 → 判定拖拽源是否来自本引擎（`draggedContent` 记录）→ 移动（删除原选区 + 插入落点，对齐 `dragMovesSelection` 语义）。
- 接入点：`MarkdownEngine.tsx` 容器 onDrop/onDragOver + `applyChange`。

### 8.2 自动补全

- 现状：无。且**无插件系统**（CM6 的 ViewPlugin/Extension 体系不存在），任何补全都要做「内建」。
- 方案（内建路线）：与 parser token 体系结合——补全触发基于「光标前 token 上下文」：`@`（提及）、`#`（标题/标签）、markdown 语法片段（`[` → 链接、`![` → 图片）、code fence 语言名；候选 UI 复用 ContextMenu.tsx 的悬浮层模式；键盘导航（上下 + Tab/Enter 接受）与现有 handleKeyDown 串行。标为中期能力（依赖选区模型升级后的光标语义）。
- 接入点：新文件 `src/core/completion.ts` + 新组件 CompletionPopup；HiddenInput.tsx 挂接。

### 8.3 滚动条与边缘拖选

- 现状：原生滚动条 + react-virtual（标准组合）；`__CRISH_IS_MOUSE_DOWN` 已解决「拖选与自动滚动打架」（HiddenInput.tsx:62-73）；**拖选到视口边缘无自动加速滚动**（依赖浏览器原生 drag-scroll，虚拟化行超出 overscan 即断选，见 §3 S2）。
- 方案：§3 拖选状态机内建边缘滚动（参考 CM6 `MouseSelection.move` 的 `dragScrollSpeed`，input.ts:285-383：距边缘 <6px 时以 50ms 间隔滚动 + 重新定位选区），一并解决虚拟化断选。

### 8.4 缩放（Ctrl+滚轮）

- 现状：无缩放实现，也无缩放冲突（字体大小测量是动态的，measure.ts:100-104 读 computedStyle）。
- 差距/风险：react-virtual 的 `estimateSize` 硬编码 28px（MarkdownEngine.tsx:102-116）——缩放后作为估算值会偏差，`measureElement` 会修正但**滚动条高度/位置会抖动**；另有 `line-height 28px` 的网格纸 CSS 对齐（MarkdownEngine.tsx:102 注释）。
- 方案：Ctrl+wheel 改为 CSS 变量 `--editor-font-size`（限制范围 0.7x-2x）；`estimateSize` 与网格对齐改读该变量；wheel 事件中 `e.ctrlKey` 拦截 preventDefault 并步进变量。低优先。

4. **远期（P3）**：§7 协作预留 → 多选区 → 自动补全插件化 → 无障碍模式。
