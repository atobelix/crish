## 0. 结论先行：扩展功能清单（高频 / 高体验价值排序视角）

### 0.1 一句话定位

引擎当前是「编辑器 + 渲染器」一体（行级 AST + LRU 行缓存 + 增量 offset 树 + 虚拟滚动），宿主把聊天历史渲染交给它（40 方案 SRS §1.2 铁律：聊天历史渲染禁止 tiptap，见 40-tiptap接线方案.md:203），但引擎尚未被接线为「只读渲染组件」——**所有高价值扩展都建立在「引擎从单文档编辑实例，升级为可实例化、可只读、可流式、可查询的渲染核心」这一底座上**。

### 0.2 扩展功能排序（频度 × 体验价值）

| 序 | 功能 | 关联场景 | 频度判断 | 引擎侧核心扩展点（摘要） |
|---|---|---|---|---|
| 1 | 流式软渲染（未闭合 fence/公式/表格渐进呈现） | 1 | 宿主高频（每条 AI 消息必经） | BlockRenderer 软渲染分支；行内未闭合已天然退化（parser.ts:1030-1033） |
| 2 | 流式增量追加 + 帧节流 | 1 | 宿主高频 | appendText 快通道（EditorStore.ts:521-598）+ StreamBuffer（rAF 帧批）已就绪，补 stop-flush 语义 |
| 3 | 只读渲染模式（消息历史） | 1/2 | 宿主高频 | readOnly 视图（隐藏光标层/隐藏输入、禁用编辑操作） |

### 1.3 引擎定位边界（本文的判断前提）

- **定位**：「渲染引擎 + 轻编辑」，聊天历史渲染禁止 tiptap（40 方案 SRS §1.2 铁律）→ 引擎即宿主聊天历史的渲染器，这是第一优先级场景（场景 1、2、3）的立论基础。
- 引擎当前是**独立 Vite 应用形态**（App.tsx 硬编码压力测试文档），宿主消费前需「组件库化」：导出 `<MarkdownViewer doc onAppend readOnly ... />` 一类受控组件契约，或源码包引入——这是场景 4/8 的 `createEditorStore` 实例化的前置。
- 备选独立软件形态（对标 Typora/Obsidian，超大文档 + AI 流式）与宿主形态共享同一批引擎扩展点，差异只在「宿主集成接口」列。

## 2. 九大场景逐项分析

### 2.1 场景一：AI 流式输出渲染

**场景描述**：模型以 500 token/s 级别增量输出 markdown 文本（宿主 SSE delta 流），消息渲染区逐帧呈现；流式中 fence 代码块、`$$` 公式块、表格可能未闭合（` ``` ` 已出现、闭合行未到）；流停止/消息结束后，切换到完成态权威渲染。每条 AI 消息是一个独立渲染单元，与用户消息、工具调用消息在时间线上并列。

**为什么高频**：**宿主每条 AI 消息都必经流式路径**，这是体感的第一触点。23 方案 §1.1 审计已定性当前 AsyncMarkdownBlock 流式态为「伪流式」（渲染短路，`renderTarget = isStreaming ? '' : text`，消息结束后才整篇渲染），并已立项 E2.1~E2.5（增量解析器接线、完成态权威渲染、帧节流、性能验证）。引擎作为自研渲染器，是 E2 方案的天然承接者。

**引擎侧需扩展什么**：

1. **软渲染模式**（未闭合块渐进呈现）：
   - fence 未闭合：`codeBlockState` 持续为 `code`/`fence_start`（appendText 已从尾行状态推断，EditorStore.ts:540-567），BlockRenderer 对 `fence_start` 后无 `fence_end` 的区间渲染为等宽原文块——**跳过启发式高亮与 lang pill**，避免「半块突然变色」的视觉跳变；
   - 行内未闭合：`scanTokens` 对找不到 close 的规则返回 null 整体退化纯文本（parser.ts:1030-1033），**已天然满足**，需补测试锁定；
   - 公式未闭合：`$$` 只出现起始行时，`math_fence_start` 后的 `math_block` 行原样渲染（不送 KaTeX，`renderMathToHtml` 失败兜底已有 throwOnError:false，但流式态应直接跳过渲染避免抖动）。
2. **流式节流**：StreamBuffer 已实现 rAF 帧批（StreamBuffer.ts:6-55），需接入「流结束 flush」语义（flush() 已有）与宿主 useStreamRenderThrottle 对齐；追加走 `appendText` 快通道（不进 undo 栈、不触发整篇重解析，EditorStore.ts:521-598）。
3. **完成态切换**：消息结束后软→硬渲染。两个选项（对齐 23 方案 E2.2 二选一）：(a) 引擎软渲染状态直接平滑为硬渲染（同一渲染器语义，差异最小化）；(b) 仍走 Rust `md_render` 权威整篇替换——需要引擎硬渲染与 md_render 输出视觉一致性验证（表格/列表/fence 边界）。
4. **只读视图模式**（见 2.2 第 1 点）：流式渲染的消息历史不可编辑，需 readOnly 模式隐藏 CursorLayer/HiddenInput 并禁用编辑操作。

**与宿主集成的接口点**：

- AsyncMarkdownBlock 流式态替换为引擎 readOnly 组件；`streamAssistantResponseApi` 的 delta 回调 → `appendText`（宿主发送管线不动，40 方案红线）；
- 完成态事件 → 软/硬切换信号；E2.3 的 useStreamRenderThrottle 接线；
- 与聊天消息边界：每消息独立引擎实例（或 store 分区），消息间不做跨块解析——fence 状态不得跨消息传播。

### 2.2 场景二：长文档 / 会话归档阅读

**场景描述**：百万 token 会话导出为 .md 归档后阅读；长会话内折叠历史（旧消息折叠为单行摘要）；大纲/目录导航（heading 索引 + 点击跳转 + 当前章节高亮）。

**为什么高频**：宿主核心目标就是百万上下文对话流——「回看」是长会话的必然动作：找之前某个结论、翻某次工具调用的参数、导出归档给同事/自己沉淀。折叠历史直接改变长会话的浏览效率；大纲是结构化回看的入口。当前宿主会话列表只有消息级滚动，无大纲、无折叠。

**引擎侧需扩展什么**：

1. **只读渲染模式**：引擎当前是编辑型（光标层 + HiddenInput + 点击定位），只读场景需要 `readOnly` 开关：隐藏输入/光标、保留滚动与 token 映射；同时保留选择复制能力（onCopy 已有，MarkdownEngine.tsx:351-364）。
2. **Heading 索引（大纲）**：headingLevel 已在 AST（parseLine:418-430），构建 O(n) 扫描或增量维护（挂 updateLinesIncremental 的 delta 回调）；数据结构 = 有序 heading 数组 `{level, text, lineIdx, offset}`，支持嵌套树与「当前视口章节」高亮；点击跳转 = 虚拟滚动 `scrollToIndex`（现有 virtualizer 直接可用）。
3. **折叠区间（历史折叠）**：新增折叠数据 `fold ranges: {startLine, endLine}`（可嵌套），渲染时折叠区间内行跳过、显示折叠占位行（摘要 + 展开按钮）；**虚拟滚动行高感知**是难点——折叠改变 estimateSize（MarkdownEngine.tsx:106-114 目前基于行首字符猜测高度），需折叠感知的 size 估计或折叠后固定行高；折叠状态存宿主侧（消息级折叠天然按消息边界切分，存 session_meta 或前端 store）。
4. **超大文档验证**：百万 token ≈ 25-40 万行。chunked 加载已就绪（EditorStore.ts:359-409）；需验证 30 万+行下虚拟滚动性能（measureElement 成本、overscan 40 是否足够），可提供「固定行高模式」（关闭动态测量，代价是折叠摘要行一致性）。

**与宿主集成的接口点**：

- 会话导出：host conex-db 导出 .md → 引擎 loadFile（setText 已有，需去 App.tsx 硬编码）；
- 大纲面板：引擎提供 `<OutlinePanel headingIndex onChangeLine />` 组件，宿主布局侧栏集成；
- 折叠状态：host 会话 store 持久化（消息边界折叠），引擎只消费 fold ranges。

### 2.3 场景三：Agent 工具产物渲染

**场景描述**：工具调用（读文件/搜索/写文件/子代理运行等）的输出在对话流中渲染：JSON 结构化数据、日志流、代码 diff、表格型结果。当前宿主对工具输出多为纯文本呈现，可读性差（超长 JSON 一行到底、diff 无红绿、日志无级别着色）。

**为什么高频**：**每次工具调用都产生结构化输出**，工具流（子代理/权限/后台任务）是宿主区别于普通聊天的核心交互；读工具结果（特别是 diff、JSON、日志）是用户高频动作。

**引擎侧需扩展什么**：

1. **fence lang 分发渲染器注册表**：AST 层不感知语言，渲染层按 `fence_start` 行的 lang（BlockRenderer.tsx:76 已有 lang 提取）分发：
   - `json` → 折叠 JSON 树（键值、数组长度、行内值、可折叠/展开、复制）；
   - `diff` → 行级 `+`/`-` 红绿着色（fence 内逐行，parseCodeLine 已逐行 token 化，加 diff 行前缀判定即可）；
   - `log`/`console` → 级别着色（ERROR/WARN/INFO）+ 时间戳弱化；
   - 其余 lang 走现有启发式代码渲染。
2. **行号与块边界**：fenceLines 有序数组（EditorStore.ts:151、570-581）O(log n) 定位代码块区间，是「复制整块」「行号显示」「diff 上下文」的基础。
3. **复制按钮**：结构化块 hover 复制（与场景 7 共用组件）。
4. 可选：```` ```table ```` 或表格型输出直接渲染为表格（引擎已有表格能力，TableOperations 现成）。

**与宿主集成的接口点**：

- 工具调用消息体（host chat-stream 消息类型含 tool call / tool output 结构化字段）→ 序列化为带 lang 的 fence 交给引擎，或引擎提供 `ToolOutputRenderer` 直接消费结构化数据；
- 与 workbench-run-event 事件通道关联（工具开始/结束/结果事件驱动消息块状态：运行中「…」→ 完成渲染）；
- 审批流（权限模式）中工具参数/结果的展示也复用同一渲染器。

### 2.4 场景四：文档工作区

**场景描述**：多文档并行（会话产出 .agent-outputs/、用户工作区文件）；文档间链接（`[[文件名]]`、`[[文件|别名]]` wiki 链接、相对路径链接）点击跳转；文件树侧栏；快速切换（Cmd+P 类）。

**为什么高频**：04-EG 方案已把「多 Agent 协作产出目录 + NN 编号文档 + 00-summary 索引」落地为引擎强制面（.agent-outputs/ 约定）——**多文档是产出形态的必然结果**，用户/主 Agent 需要消费这些文档；宿主产品定位「文档工作区」（04-EG 标题即「编辑工具与文档工作区方案」），文档间跳转是工作区形态的基本能力。

**引擎侧需扩展什么**：

1. **多文档 store 实例化**：当前 `useEditorStore` 是全局单例 zustand（EditorStore.ts:323）——工作区需要 `createEditorStore()` 工厂（每文档一实例），并把状态访问改成实例化 store（组件接收 store 实例 prop）。这是文档工作区/多标签的**结构性前置**。
2. **wiki 链接 token**：INLINE_RULES 新增 `[[...]]` 规则 → 新 InlineType `wiki_link`（ast.ts 枚举扩展），渲染为 chip 样式 + `onWikiLinkClick` 事件回调（host 负责解析路径并打开文档）；保留 raw 完整保真（raw 语义已有）。
3. **相对链接解析**：现有 `link` token 的 url 为相对路径时，渲染层不做拦截，由 host 提供 open 回调（链接点击目前无处理，需补 onClick 链路）。
4. 文件树/最近文件属 host 能力（fs 工具面），引擎只暴露「打开文档 API」：`openDoc(id, text)` + 文档标题索引。

**与宿主集成的接口点**：

- host workspaceFsApi（已有）+ .agent-outputs/ 目录约定（04-EG T-EG-08/09）；
- 引擎组件化契约：`<MarkdownEditor store={instance} onOpenDoc={...} />`；
- 快速切换面板由 host 实现，引擎提供活动文档状态与标题。

### 2.5 场景五：搜索 / 定位

**场景描述**：当前文档全文搜索 + 命中高亮 + 上/下一条导航；goto 行（输入行号或大纲点击跳转）；符号索引（heading/表格/链接/任务清单项）快速定位。

**为什么高频**：长文档（百万 token 会话、导出归档）的**定位刚需**——「找那个结论在哪」是回看的第一动作；工具产物文档（00-summary 索引）本身就是搜索入口的形态。当前引擎零搜索能力。

**引擎侧需扩展什么**：

1. **行级全文搜索**：数据模型是 lines 数组 + offset 树，行级扫描天然匹配；单文档搜索 O(总行数) 可在主线程分批（requestIdleCallback 先例 EditorStore.ts:388-399，**不走 worker**——RL-05 #10 禁令）；命中结果 `[{lineIdx, start, end}]`，跨行命中（fence 内）合并展示。
2. **高亮层**：命中区间渲染复用 data-token-start 映射（MarkdownEngine.tsx:244-253），做法：token 级 mark 包裹或覆盖层（SelectionHighlight.tsx 同构）；当前页命中优先、滚动定位（scrollToIndex + 目标行高亮，active-line 样式已有）。
3. **goto 行**：行号输入 → `offsets.getOffset(lineIdx)` + scrollToIndex + 光标定位（编辑态）/高亮（只读态）。
4. **符号索引**：与大纲（2.2）共用一份增量索引，扩展表格起始行/链接/task 项；可作为「符号面板」输出。
5. 编辑时命中失效策略：搜索快照 + 编辑后重扫（增量维护成本高，快照重扫对行级模型足够）。

**与宿主集成的接口点**：

- host 搜索框（消息级搜索已有雏形？无——需新建）→ 引擎 `search(term) → matches[]` + `gotoMatch(i)`；
- 跨文档搜索（.agent-outputs/ 工作区）走 host（conex-db 全文或 fs 层），引擎只做当前文档搜索与高亮；
- Ctrl+F 快捷键接入引擎容器（编辑态/只读态都要）。

### 2.6 场景六：协作场景

**场景描述**：共享文档（多人/多窗口同时编辑）、评论/标注（选区锚定评论、回复流）、多人光标与选区颜色区分。

**为什么高频**：对宿主（桌面单机 AI 工具）**低频**——但若走独立软件形态（对标 Notion/Google Docs 类），是差异化能力；本地多窗口协作（同一机器双窗口）是 Tauri 应用可实现的最低成本形态。

**引擎侧需扩展什么**：

1. **远端光标/选区模型**：EditorState 扩展远端 selection 列表（`userId → {start, end, color}`）；渲染层新增远端光标层（CursorLayer 同构实现，MarkdownEngine.tsx:415-421）；**关键优势**：offset 模型是逻辑位置，天然可映射 CRDT/OT，不依赖 DOM 锚。
2. **操作序列化**：EditorOperation（startLineIdx/removedLines/insertedLineCount，EditorStore.ts:133-144）已是行级 splice 语义——可序列化为同步 op 包（行级 OT 的现成形状），undo/redo 栈（:758-840）可复用为 op 源。
3. **评论/标注**：选区锚定 = `{start, end, snapshotText, docVersion}` 持久化；渲染层标注高亮（mark 样式）+ 评论浮层；选区随编辑漂移（offset 树可 O(log n) 漂移，LineOffsetTree 现成）。
4. 冲突面：并发写同文件已有宿主侧写路径互斥（04-EG 已接线），协作引擎层主要做 op 应用与冲突检测。

**与宿主集成的接口点**：

- 若做本地多窗口：BroadcastChannel/文件锁 + 引擎 ops 导入导出接口；
- 评论存储：conex-db 或 .agent-outputs/ 内 .comments 文件；
- 优先级判断：**可后置**（宿主低频）；独立形态时提升到「差异化卖点」档。

### 2.7 场景七：导出 / 分享

**场景描述**：导出 HTML（自包含、样式内联）与 PDF（打印友好）；代码块一键复制（保格式、复制原文）；公式复制（KaTeX 已渲染，复制 LaTeX 源或 PNG）；复制为纯文本（Markdown 原文）。

**为什么高频**：代码块/公式复制是**高频微操作**（工具产物查看后必然复制），成本最低、见效最快；导出是会话归档（场景二）的出口动作——沉淀的终点是带走。

**引擎侧需扩展什么**：

1. **复制按钮**（第一优先）：BlockRenderer 的 code 分支挂 hover 复制钮（fenceLines 定位块区间 → 拼接原文行）；math 分支挂「复制 LaTeX」（math token raw 已有，BlockRenderer.tsx:43-56 KaTeX 渲染处取 raw）；复制逻辑复用已有 clipboard 处理（MarkdownEngine.tsx:351-364 的 selection 复制先例）。
2. **renderToHTML 纯函数**：复用 BlockRenderer 渲染语义（含 KaTeX、表格、代码高亮）输出无交互层的打印友好 HTML（样式内联、隐藏光标层/交互元素）；AST → HTML 不走 DOM，纯函数可测。
3. **PDF**：宿主 WebView2 打印能力（宿主工作台已有打印路径则复用）；引擎只需提供分页友好的打印 CSS（page-break 规则：表格/代码块不跨页）。
4. Markdown 导出已是 `getText()`（EditorStore.ts:339）天然能力，零成本。

**与宿主集成的接口点**：

- host 导出菜单 → 引擎 exportHtml() → workbench fs 保存/打印；
- 复制按钮为引擎内组件，无需宿主接线（纯引擎扩展）；
- 消息级导出（导出当前消息）与文档级导出（导出整个会话 md）由 host 组合。

### 2.8 场景八：独立软件形态的扩展

**场景描述**：若引擎产品化为独立极简 Markdown 软件（对标 Typora/Obsidian，主打超大文档 + AI 流式）：打开即用（双击文件 / 文件关联启动）、最近文件、自动保存、深浅主题、多语言（见场景九）、多窗口/标签页。

**为什么高频**：这是「备选形态」的基本盘能力——**不做这些就不成为产品**；对宿主内嵌形态则大多不适用（宿主自己有会话/配置体系）。频度判断拆两档：宿主内嵌低相关、独立形态必需。

**引擎侧需扩展什么**：

1. **组件库化（结构性前置）**：引擎从 Vite 应用形态（App.tsx 硬编码）变成可导入的组件+API 面：`<MarkdownEditor doc onEdit readOnly theme locale ... />` 受控组件 + `createEditorStore()`（2.4 复用）；App.tsx 只是 demo 壳。
2. **打开即用**：Tauri 文件关联 + 启动参数解析是宿主能力面（workbench_*），引擎只提供 loadFile（路径 → setText + 文件名/标题状态）；**去硬编码**：App.tsx:12-22 当前写死压力测试文档。
3. **自动保存**：编辑事件防抖（对齐宿主 350ms 草稿惯例，40 方案 §2.2）→ `onSaveRequest(contents)` 回调 → host 落盘；引擎提供 dirty 状态 + 未保存提示。
4. **最近文件**：host 层（Tauri 存储或配置文件）+ 引擎 openRecent API。
5. **主题**：colorAdaptor 已有 HSL 解析与自适应（color-gate.test.ts 门禁），扩展为显式 light/dark/sepia + 跟随系统（CSS 变量体系已 token 化，改动面小）。
6. **多标签页**：createEditorStore 实例化 + host 标签栏。

**与宿主集成的接口点**：全部为「引擎纯 API + host 能力面」边界——引擎不假设宿主，宿主通过 props/IPC 注入（fs 保存、文件关联、打印、窗口）；这条边界同时服务宿主内嵌与独立形态两种消费方式。

### 2.9 场景九：无障碍 / 国际化

**场景描述**：RTL（阿拉伯语/希伯来语文档段落方向正确显示与光标移动）、i18n（UI 文案多语言：占位、按钮、右键菜单、空态）、键盘导航与 aria（大纲、搜索、折叠控制的可访问性）。

**为什么高频**：RTL 对中英产品低频，但**文档内容可能含 RTL 段落**（技术文档引用、多语言资料）；i18n 是独立软件形态出海的必需（宿主出海亦然）；无障碍是宿主已建立的纪律（40 方案 T10：aria combobox 链、焦点回迁），引擎作为新组件不能掉队。

**引擎侧需扩展什么**：

1. **RTL**：段落级方向检测（首字符 Unicode 方向 → `dir="auto"`）；**引擎 offset 模型是逻辑序**（非视觉序），光标左右键天然正确，只需显示层 bidi 化——成本低、正确性高（对比 DOM-based 编辑器的 bidi 痛点）；grapheme 处理（Intl.Segmenter）对 RTL 合成字符已正确。
2. **i18n**：文案抽取（当前硬编码中文：App.tsx:33「生成万行超大文档...」、BlockRenderer.tsx:922「🖼️ 图片」、context 菜单等）；文案资源表 + `locale` prop；宿主若有全局语言设置则透传。
3. **aria/键盘**：虚拟行 aria-label（行号+内容摘要）、大纲/搜索/折叠的键盘导航与 aria-expanded 链（对齐 40 方案 T10 标准）；聚焦管理（引擎接管键盘焦点时 Host 退出组合输入）。

**与宿主集成的接口点**：locale 由 host 设置面板注入；RTL 纯渲染层改动（不碰 parser/offset/测试基线）；aria 断言并入引擎门禁（对齐宿主「axe 无 critical」验收惯例）。

## 4. 阶段建议（依赖关系，非优先级）

按逻辑依赖分四批推进（与本文排序解耦，只表达先后关系）：

| 批次 | 内容 | 依赖 | 说明 |
|---|---|---|---|
| 第一批：宿主主线底座 | 只读模式 → 流式软渲染 → 完成态切换 → 大纲索引 | 无 | 场景 1/2 是 23 方案 E2 的直接承接；只读模式是所有其他宿主场景的前置 |
| 第二批：高频消费面 | 代码/公式复制 → 工具产物 lang 分发渲染 → 全文搜索+高亮+goto → 折叠区间 | 只读模式 | 复制最便宜先做；结构化渲染依赖 fence lang 提取（已具备） |
| 第三批：工作区与出口 | 导出 HTML/PDF → createEditorStore 实例化 → wiki 链接 → 文档工作区 | 引擎组件库化 | 组件库化是 2.4/2.8 的结构性前置，与导出（renderToHTML）可并行 |
| 第四批：延伸形态 | 主题显式切换 → i18n/RTL → 最近文件/自动保存 → 协作/评论 | 第三批 | 独立形态基本盘；协作与评论按形态决策后置 |

**跨批次共享红线**：引擎改动后必须跑通门禁 `npm test`（vitest run tests/unit，含 grapheme/undo/parser-redos/chunk）；新增功能（lang 分发、fold、search、wiki_link）各自带单测；不新增 worker 渲染路线（RL-05 #10）；新 UI 对齐宿主 token 体系与视觉红线（RL-01 对比度 mix、零阴影）。

## 5. 风险与边界

| 风险/边界 | 说明 | 对策 |
|---|---|---|
| 引擎组件库化成本 | 当前是 Vite 应用 + 全局单例 store，宿主消费需形态改造 | 第一批先做「只读组件化」最小改造（readOnly prop + 受控 text），完整 createEditorStore 放到第三批 |
| 软/硬渲染视觉跳变 | 流式软渲染与完成态渲染不一致（高亮、表格、数学） | E2.2 差异最小化 + 视觉对比测试（23 方案 E2.4 已有口径） |
