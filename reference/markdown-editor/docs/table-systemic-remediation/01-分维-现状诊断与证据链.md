## 2. 结论台账（结论 → 证据 → 复核命令）

### C1　AST 中不存在表格聚合节点

- **结论**：表格只有 `table_row` / `table_separator` 两种**行**类型，没有任何携带 `rows/cells/alignments/spans/行号范围` 的聚合节点。
- **证据**：`src/core/ast.ts:13-14`（`LineType` 含 `table_row`/`table_separator`）、`ast.ts:51-52`（`InlineType` 含 `table_pipe`/`table_cell`）、`ast.ts:78-97`（`LineNode` 字段仅 `type/raw/inlineTokens/localOffset/length`）。
- **复核**：`E1`；另 `grep -n "interface TableNode\|type TableNode" src/core/ast.ts` → 0 命中。
- **后果**：表头语义、列数、对齐、跨列合并全部在**渲染时**逐行重新推导 → 见 C5/C6。

### C2　组件层完全没有原生表格元素与表格布局

- **结论**：编辑器表格是 **div + flex 手工表格**；全仓 `src/` 无 `<table>` / `<thead>` / `<colgroup>` / `table-layout` 任何一处。
- **证据**：`E1` 唯一命中为 `src/core/parser.ts:1534` 的**注释**（讨论 HTML 块类型）。
- **后果**：无原生表格的列对齐/列宽语义 → 列宽必须自研 → 见 C7；导出无 `<table>` 包裹 → 见 C11。

### C3　每一行都是独立的横向滚动容器（D1）

- **结论**：N 行表格 = N 个 `overflow-x: auto` 容器；跨行滚动对齐靠 zustand 状态 + `useLayoutEffect` 手工回写；且「只在最后一行显示滚动条」是显式 hack。
- **证据**：
  - `src/index.css:379-391`（`.line-table{width:100%;max-width:100%;overflow-x:auto;overflow-y:hidden;scrollbar-width:none}` + `::-webkit-scrollbar{display:none}`）
  - `src/index.css:393-414`（`.line-table.table-last-row` 独有 `scrollbar-width:thin` + `::-webkit-scrollbar{display:block;height:6px}`）
  - `src/components/BlockRenderer.tsx:1504-1530`（分隔行块的 `scrollLeft` 回写）、`1595-1621`（表格行块的 `scrollLeft` 回写，带 rAF 守卫）
  - 状态源：`src/core/TableStore.ts:16,59-68`（`tableScrollLeft` + `setTableScrollLeft`）
- **后果**：症状 S1（多滚动条）、S2（重挂载行先以 `scrollLeft=0` 绘一帧 → 旧列闪现）。

### C4　表格身份由「首行行号」向上探测生成（D2）

- **结论**：`tableId = "table-" + firstTableIndex`，`firstTableIndex` 由**逐行向上探测**「上一行 `trim().startsWith('|')`」得到。该 `store(...)` 订阅在**每一行**上执行 → 一张 N 行表产生 O(N²) 次字符串探测。探测条件与 parser 的成表条件**不一致**。
- **证据**：
  - `src/components/MarkdownEngine.tsx:548-562`（身份推导）
  - parser 成表条件：`src/core/parser.ts:2380-2390`（`pipeCount>=2 && (以 | 开头/结尾 或 pipeCount>=3)`）
  - 分隔行判定：`src/core/parser.ts:2302-2312`（前导/尾随 `|` 可选）
- **后果**：
  - 身份随「表格上方任何编辑」漂移 → 视图状态落到错误目标 → 症状 S7（列顺序/列宽在不同时刻不一致）。
  - 合法但**不以 `|` 开头**的表格行（`pipeCount>=3`）会把一张表劈成两个 `tableId` → 表头高亮/列宽失配（对应 S5）。
  - 不变量 I10 的直接依据。

### C5　视图状态全部挂在漂移身份上（D3）

- **结论**：`tableWidths` / `tableAlignments` / `tableScrollLeft` 均以 `tableId` 为键；`selectedCell.tableId` 亦同。
- **证据**：`src/core/TableStore.ts:14-33`（状态定义）、`TableStore.ts:3-10`（`CellSelection` 含 `tableId` + 绝对 `startLine/endLine/startCol/endCol`）。
- **消费点**：`src/components/InlineRenderer.tsx:470`（`tableWidths?.[colIndex + c] ?? 100`）、`:473`（`tableWidths?.[colIndex] ?? 0`）、`:481`（`tableAlignments?.[colIndex] || 'left'`）、`:495`（`tableId === selectedCell.tableId`）。
- **后果**：身份漂移 → 列宽取不到 → 落到 C7 的兜底分支 → 症状 S7。

### C6　表头语义无单一真源

- **结论**：表头判定是 `isHeaderRow = tableId === 'table-' + index`（**首行即表头**）；分隔行到达前 `| a | b |` 已被判为 `table_row`；对齐从分隔行**即时解析**并缓存进 store，编辑分隔行后需失效（存在 stale 风险）。
- **证据**：
  - 表头判定：`src/components/BlockRenderer.tsx:1565`
  - 分隔行块：`BlockRenderer.tsx:1495-1556`
  - 对齐解析：`src/core/TableOperations.ts:657-667`（`parseTableAlignments`）
  - 对齐缓存：`src/components/BlockRenderer.tsx:1570-1586`（`useEffect` 现算 + 写 store）
- **补充**：`.line-table-separator{height:0!important;overflow:hidden}`（`index.css:441-451`）与 `.is-active-line.line-table-separator{height:28px!important}`（`index.css:453-460`）；后者要求 className 含 `is-active-line`，而 `BlockRenderer.tsx:1540` 的 className 只有 `line-table-separator` → **该规则疑似永不命中**（列入 §5 待验证）。
- **后果**：症状 S5（表头渲染成 `------`）。

### C7　列宽来源与兜底（D4 的一半）

- **结论**：有 `tableWidths` 时用 `flex: 0 0 Npx; minWidth: Npx`；**取不到时兜底 `minWidth:100px; flex:1 0 auto`**（弹性宽度）→ 列宽随容器与内容变化，无法稳定。
- **证据**：`src/components/InlineRenderer.tsx:466-478`（`cellWidth` 计算 + `cellStyle` 分支）。
- **行盒宽度兜底**：`.line-table-row{width:max-content;min-width:100%}`（`index.css:420-431`）→ `tableWidths` 之和小于容器宽时右侧留空条（症状 S2 的「多出空列」）。
- **后果**：症状 S7、S2。

### C8　列宽测量的循环依赖（D4）

- **结论**：列宽由「测量单元格 `scrollWidth`」得出（非流式走闭合定型取逐列 max；流式走 grow-only 锁宽），再写回 `flex:0 0 Npx` 反过来决定换行与行高 → **循环依赖**。
- **证据**：
  - 非流式闭合定型：`src/components/MarkdownEngine.tsx:2173-2195`
  - 流式锁宽：`MarkdownEngine.tsx:2090-2114`
  - 消费：`InlineRenderer.tsx:476-478`
  - 观测钩子：`src/core/tableSettle.ts:33-35`（`recordTableWidthSettle`，经 `window.__CRISH_TABLE_SETTLE__` 供 perf suite 读「定型次数」）
- **后果**：症状 S4、S7、S8。

### C9　高度预言机不知道真实列宽（D5）

- **结论**：`HeightOracle.predict` 的表格分支用 `cols = pipes-1` 与 `containerWidth` **估算**列宽（`colPerRow = (containerWidth - PAD*2*cols) / cols / charWidth`），**从不读 `tableWidths`**；且只有当前可见行才回填实测高度。
- **证据**：
  - `src/core/HeightMap.ts:232-269`（表格分支；`colPerRow` 见 `:254`）
  - 常量：`HeightMap.ts:51-53`（`TABLE_CELL_HEIGHT` / `TABLE_CELL_PAD_Y`，注释要求与 CSS 同步）
  - 分隔行恒 0：`HeightMap.ts:230`
  - 可见行回填：`src/components/MarkdownEngine.tsx:1913-1956`
- **常量漂移风险**：CSS `.token-table-cell{min-height:40px;padding:10px 16px}`（`index.css:470-486`）vs oracle `rows * TABLE_CELL_HEIGHT + TABLE_CELL_PAD_Y`；`.line-table-row{min-height:28px}`（`index.css:427`）vs oracle `lineHeight * 1.2`。
- **后果**：症状 S8（行位置与实际高度失配 → 行序视觉错乱 / 幽灵行，对应不变量 I8）。

### C10　测量时序错位（D6）

- **结论**：同一个批量测量 effect 内**先读 `offsetHeight` 测高**（`:1913-1956`）、**之后才读 `scrollWidth` 定型列宽**（`:2075-2195`）——高度是按旧列宽测的；且 effect 依赖数组**不含 `tableWidths`**，定型后不触发重测。
- **证据**：
  - 测高：`MarkdownEngine.tsx:1913-1956`（`:1925` 读 `offsetHeight`，`:1944` 校准，`:1949` `resizeItem`）
  - 定型：`MarkdownEngine.tsx:2075-2195`
  - 依赖：`MarkdownEngine.tsx:2201-2210` = `[mainLines, streamTail, mainCodeState, streamTailCodeState, lineCount, windowKey, flushStreamBuffer, decorationVersion]` → **无 `tableWidths`**
  - 测量纪律：`MarkdownEngine.tsx:1130-1151`（`useCachedMeasurements: true`，RO 只回缓存值，逐行测量由批量协议独占）
- **后果**：症状 S4、S8。

### C11　导出投影与编辑器渲染双源，且导出非法（D8）

- **结论**：`renderToHtml` 的表格分支输出**裸 `<tr><td>`**，无 `<table>` / `<thead>` / `<tbody>` 包裹；`table_separator` 直接跳过。与编辑器（div+flex+InlineRenderer+TableStore）是两套实现，无共享布局逻辑。
- **证据**：`src/core/renderToHtml.ts:509-524`（`renderTableRow`）、`:713-717`（`case 'table_row'` 调用、`case 'table_separator'` 跳过）。
- **后果**：症状 S11；不变量 I9 的直接依据。

### C12　选区实现范式错误（D7）

- **结论**：选区轮廓由**每个单元格各自的 `inset box-shadow`** 拼出（单格用 `0 0 0 1.5px`；多格按「是否在 min/max 行列」逐边 inset）。这在范式上无法保证「一个矩形」，且跨虚拟行窗口时上/下边会画在错误的行上。
- **证据**：`src/components/InlineRenderer.tsx:503-539`（`selectionShadow` 拼边 + `is-selection-bottom-right`）。
- **选区身份**：`TableStore.ts:3-10` 用**绝对行号**；`TableToolbar.tsx:121-163` 的增删行列**不回写选区**（仅 `handleMerge` 在 `:85-89` 回写）→ 增删后选区指向旧行号/旧列号。
- **选区层附带缺陷**：
  - `SelectionHighlight.tsx:372` effect 依赖 `[decorations, decorationVersion, containerRef]` → **无布局依赖**，列宽定型/行高回填/虚拟窗口变化均不重测 → 旧矩形残留。
  - `SelectionHighlight.tsx:240` `LINE_HEIGHT = 28` 硬编码（`:270-284` 用于切片高度），而表格单元格 ≥40px（`index.css:476`）。
- **后果**：症状 S3、S2（蓝框幽灵）。

### C13　裁剪与装饰失配（S4/S6 次因）

- **结论**：虚拟行启用 `contain: paint` 且行盒高度被预言机锁定；单元格换行后超出即被裁掉（视觉等同 ellipsis）。表格行**无** `text-overflow: ellipsis` / `-webkit-line-clamp`（全局仅在 `.fm-key/.fm-value`、`.doc-tab-title`、`.sidebar-item-title` 出现，均与表格无关）。
- **证据**：
  - `src/index.css:955-957`（`.virtual-row-gpu{contain:paint}`）、`src/components/MarkdownEngine.tsx:239`（默认启用）
  - `src/index.css:470-486`（`.token-table-cell{display:inline-flex;align-items:center;min-height:40px;padding:10px 16px;overflow-wrap:break-word}`）
  - 反证：`grep -rn "text-overflow\|line-clamp" src/` → 命中均在非表格选择器。
- **「漂浮 `-`」与「左缘竖条」候选来源**（**未定位，需动态调试**）：
  - `src/components/BlockTypeBadge.tsx:13-30,47-49` + `index.css:1868-1891`（`position:fixed;top:56px;right:26px`；表格行显示 `|`、分隔行显示 `—`）
  - `index.css:441-460`（分隔行激活时从 0 撑到 28px 并显示源码）
  - `index.css:462-468`（`.token-table-pipe{display:none}`，仅激活行显示）
  - 实测坐标与 `right:26px` 不符 → 列入 §5 待验证。

### C16　行判定双源：`isTableLine` 与 parser 成表条件不一致（**已知识别缺陷，登记不修**）

- **结论**：`TableOperations.isTableLine` 要求 `trim().startsWith('|')`，而 parser 的成表条件是 `pipeCount>=2 && (以 | 开头/结尾 或 pipeCount>=3)`。→ 对「不以 `|` 开头但 `pipeCount>=3`」的合法表格行，`findTableRange` 返回 `null`（找不到表格区间），而渲染层却按表格渲染。
- **证据**：`src/core/TableOperations.ts:76-81`（`isTableLine`）vs `src/core/parser.ts:2380-2391`（成表条件）。
- **裁决（`00-总方案` §13 R2）**：**以 parser 行类型为唯一真源**；`findTableRange` **保持现状**，本战役**不修**（修改会破坏 `table-operations.test.ts` 既有断言，违反「测试只增不减」）。**另立登记，待后续战役处理**。
- **后果**：本战役的 TableModel 必须以「**行类型**」而非「行文本前缀」作为成表依据，否则会把此缺陷固化进新模型。

### C17　`BlockIntervalTree` 在 `src/` 内零实例化

- **结论**：`BlockIntervalTree.buildFromLines` 只产 `code_block` / `callout` / `blockquote`，**不含 table 区间**；且该类在 `src/` 内**零实例化**（引擎实际用的是 `MarkdownEngine.tsx:37-66` 的另一套行/块索引）。
- **证据**：`src/core/BlockIntervalTree.ts:94-103,133-142,152-161`（区间类型）vs `BlockIntervalTree.ts:8`（文件头声称）；`new BlockIntervalTree(` 仅命中 `tests/unit/block-interval-tree.test.ts:11`；`src/components/MarkdownEngine.tsx:37-66`（实际索引）。
- **裁决（`00-总方案` §13 R1）**：TableModel 缓存改用 `src/core/tableModel.ts` **模块级缓存**；`BlockIntervalTree.ts` 为本战役**只读**。
- **后果**：`00-总方案` ADR-1 初稿的「由 `BlockIntervalTree` 承接」为**事实性偏差**，已在 ADR-1 代价项更正。
