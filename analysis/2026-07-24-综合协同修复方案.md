## 1. 总体架构：数据驱动的单轮六阶段闭环

方案的核心是一个**数据驱动的固定循环**。每一轮都执行相同的六个阶段，轮与轮之间只通过一份机器可读的《问题台账》（Issue Ledger）传递状态：

```
┌──────────────────────────────────────────────────────────────────────┐
│                          第 N 轮（Round N）                           │
│                                                                      │
│  阶段0        阶段1        阶段2        阶段3         阶段4     阶段5  │
│ 问题识别 ──► 任务分解 ──► Agent分配 ──► 并行修复 ──► 结果汇总 ──► 验证 │
│    ▲                                                              │   │
│    └──────────────────────── 台账更新 ◄───────────────────────────┘   │
│                          （阶段6，闭环点）                            │
└──────────────────────────────────────────────────────────────────────┘
        输入：第 N-1 轮台账           输出：第 N 轮台账（→ 第 N+1 轮输入）
```

**角色总量约定**：「每轮 ≤ 12 个 Agent」指每轮部署的**执行型子代理**（修复、集成、验证）。阶段 0/1/4/6 的编排、分解、台账读写由**主控编排器**（会话主线程）承担，不占用 12 个名额。若某轮执行型 Agent 需求 > 12，按第 3.3 节的分批规则拆轮。

**复用性来源**：阶段定义、台账格式、门禁规则、分配规则全部与具体问题无关；换新一批问题时，只需替换台账内容，循环结构不变。

## 2. 统一数据契约（轮次间的唯一接口）

### 2.1 问题台账（Issue Ledger）

落盘位置：`.workbuddy/repair/ledger.json`。每轮结束由主控原子重写（先写临时文件再 rename，防止半写状态）。

```json
{
  "version": 3,
  "round": 2,
  "baseline": {
    "commit": "<上轮合并后的 sha>",
    "build": "pass",
    "perf": { "stream_mainthread_ms_per_20kb_code": 0, "drag_fps_median": 0 }
  },
  "issues": [
    {
      "id": "P1",
      "title": "StreamRenderBuffer 每帧 hljs+markdown 产物被丢弃",
      "cluster": "streaming",
      "source": "audit-2026-07-24 + AG-05",
      "files_write": ["apps/crish-desktop/src/api/StreamRenderBuffer.ts"],
      "status": "open | in_progress | fixed | verified | regressed | blocked | new",
      "owner_round": "R3",
      "acceptance": ["流式期间 highlightCode 调用次数 == 0（插桩断言）"],
      "evidence": { "commit": "", "gates": { "G0": "", "G1": "", "G3": "", "G4": "" } },
      "failure_notes": "",
      "discovered_in": "audit-2026-07-24"
    }
  ]
}
```

状态机：`open → in_progress → fixed → verified`；验证失败回退 `fixed → regressed`（附 failure_notes）；修复中发现的新问题以 `new` 追加。**只有 `verified` 视为关闭**。

### 2.2 任务卡（Task Card）

阶段 1 的产物，每个执行型 Agent 领到一张。字段即契约：

| 字段 | 说明 |
|---|---|
| `task_id` | 如 `R3-T01` |
| `issue_ids` | 本卡覆盖的台账条目（可多选，但写集必须内聚） |
| `files_write` | **写集**：本轮内全局唯一，任何两张任务卡写集不得相交 |
| `files_read` | 只读引用集（允许与他卡写集相交，但禁止依赖其未合并行为） |
| `depends_on` | 上游任务卡 id（构成 DAG，决定 Wave 分层） |
| `contracts` | 跨任务卡接口约定，分解阶段冻结 |
| `acceptance` | 可机器验证的验收条件（断言/命令/阈值） |
| `verify_cmds` | 验收命令（build / vitest / playwright / 基准脚本） |
| `impl_guide` | **代码级实施指引**：具体文件路径、行号范围、修改伪代码/关键 API 签名 |
| `rollback` | 回滚方式（默认：集成分支 revert 该 Agent 的提交） |

### 2.3 分支模型

```
main ──► round-N-integration（轮次集成分支，每轮一条）
            ├── agent/R3-T01-xxx（每个修复 Agent 一条作业分支，从集成分支切出）
            ├── agent/R3-T02-xxx
            └── ...
```
集成分支合并全部作业分支并通过门禁后，fast-forward 回 main，该 commit 即下一轮 baseline。**同 Wave 内的并行 Agent 必须使用隔离工作区（`git worktree` 或 branched workspace）**。

## 3. 通用规则

### 3.1 单一写者原则
任一轮次内，每个文件有且仅有一个拥有写权限的 Agent。任务卡写集两两不相交是阶段 1 的硬性校验项（主控在分配前对全部 `files_write` 求交，非空即重划分）。

### 3.2 Wave 分层规则
Wave 编号 = 任务卡在 DAG 中的拓扑深度。同层并行，层间设合并屏障 + G0 门禁。

### 3.3 超容分批规则
当一轮所需执行型 Agent > 12 时：先按 DAG 深度切分；同层仍超容时，按模块内聚性聚类分批。分批不构成优先级判断。

### 3.4 跨模块契约规则
写集可分离但行为耦合的问题，禁止两个 Agent 各自暗改。必须在阶段 1 冻结契约（如 `C-STREAM-1`、`C-DRAG-1`），写入双方任务卡；集成时由 G5 评审核对。

### 3.5 验证独立原则
验证 Agent 不得是同一批任务的修复 Agent；性能基准 harness 与 e2e 场景一经建成即沉淀为仓库资产（`tests/` 下），后续轮次直接复用。

### 3.6 门禁序列 G0–G5

| 门禁 | 内容 | 执行者 |
|---|---|---|
| G0 编译 | `tsc --noEmit` + `vite build` + `cargo check` 通过 | 验证 Agent V1 |
| G1 静态检查 | `eslint --max-warnings 0` + `depcruise` + 冲突标记扫描归零 | V1 |
| G2 单元测试 | `vitest run` 全量通过（含新增测试） | V1 |
| G3 交互回归 | `playwright` 拖拽 e2e + 流式渲染 e2e | V2 |
| G4 性能回归 | 流式压测 harness + 拖拽基准；**不低于上轮 baseline** | V3 |
| G5 评审 | 高风险 diff 人工/评审 Agent 复核（热路径、协议解析、store 中间件、契约一致性） | V4 |

回退规则：任一门禁失败 → 集成 Agent revert 涉事任务卡提交 → 台账对应条目置 `regressed` → 不阻塞其他任务卡。

## 14. Round 10+：模板迭代轮（可复用模板）

当 Round 9 完成后，若台账中仍有 `open`/`regressed` 条目（新发现问题或回归），则启动模板迭代轮。

### 14.1 模板轮流程

```
1. 主控读取 ledger.json，筛选 status ∈ {open, regressed, new}
2. 按 cluster 分组 → 执行阶段 0（问题识别）
3. 阶段 1（任务分解）：按 §3.1-3.4 规则生成任务卡
4. 阶段 2（Agent 分配）：≤12 个 Agent，写集不相交
5. 阶段 3（并行修复）
6. 阶段 4（结果汇总）：台账更新
7. 阶段 5（验证）：G0-G5 门禁
8. 阶段 6（台账更新）：原子写回 ledger.json
9. 若仍有未关闭条目 → 回到步骤 1
```

### 14.2 终止条件

| 条件 | 判定方式 |
|---|---|
| 全量关闭 | `ledger.json` 中所有条目 `status === 'verified'` |
| 收敛失败 | 连续 2 轮同一条目在 `fixed` → `regressed` 间振荡 → 升级为人工介入 |
| 容量耗尽 | 剩余 `open` 条目总修改行数预估 < 单轮可承载量 → 合并进最终收尾轮 |
