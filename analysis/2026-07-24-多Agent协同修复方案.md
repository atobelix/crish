# 多 Agent 协同修复方案（可复用迭代框架）

> 版本：v1.0 · 2026-07-24
> 输入：`analysis/2026-07-24-前端性能与拖拽问题审查报告.md`（26 项问题：合并冲突组 B0、流式渲染 P1–P11、窗口与标签拖拽 D1–D15）
> 约束：仅规定逻辑执行顺序；不涉及时间安排、人员分配、优先级排序（所有问题优先级相同）；每轮部署的执行型 Agent ≤ 12 个，按需取用、不要求占满。

---

## 1. 总体架构：单轮六阶段闭环

方案的核心是一个**数据驱动的固定循环**。每一轮都执行相同的六个阶段，轮与轮之间只通过一份机器可读的《问题台账》（Issue Ledger）传递状态：

```
┌──────────────────────────────────────────────────────────────────────┐
│                          第 N 轮（Round N）                           │
│                                                                      │
│  阶段0        阶段1        阶段2        阶段3         阶段4     阶段5  │
│ 问题识别 ──► 任务分解 ──► Agent分配 ──► 并行修复 ──► 结果汇总 ──► 验证 │
│    ▲                                                              │   │
│    └──────────────────────── 台账更新 ◄───────────────────────────┘   │
│                          （阶段6，闭环点）                            │
└──────────────────────────────────────────────────────────────────────┘
        输入：第 N-1 轮台账           输出：第 N 轮台账（→ 第 N+1 轮输入）
```

**角色总量约定**：「每轮 ≤ 12 个 Agent」指每轮部署的**执行型子代理**（修复、集成、验证、基准）。阶段 0/1/4/6 的编排、分解、台账读写由**主控编排器**（会话主线程）承担，不占用 12 个名额。若某轮执行型 Agent 需求 > 12，按第 5.3 节的分批规则拆轮。

**复用性来源**：阶段定义、台账格式、门禁规则、分配规则全部与具体问题无关；换新一批问题时，只需替换台账内容，循环结构不变。

## 2. 统一数据契约（轮次间的唯一接口）

### 2.1 问题台账（Issue Ledger）

落盘位置：`.workbuddy/repair/ledger.json`。每轮结束由主控原子重写（先写临时文件再 rename，防止半写状态）。

```json
{
  "version": 3,
  "round": 2,
  "baseline": {
    "commit": "<上轮合并后的 sha>",
    "build": "pass",
    "perf": { "stream_mainthread_ms_per_20kb_code": 0, "drag_fps_median": 0 }
  },
  "issues": [
    {
      "id": "P1",
      "title": "StreamRenderBuffer 每帧 hljs+markdown 产物被丢弃",
      "cluster": "streaming",
      "files_write": ["apps/crish-desktop/src/api/StreamRenderBuffer.ts"],
      "status": "open | in_progress | fixed | verified | regressed | blocked | new",
      "owner_round": "R2",
      "acceptance": ["流式期间 highlightCode 调用次数 == 0（插桩断言）"],
      "evidence": { "commit": "", "gates": { "G0": "", "G1": "", "G3": "", "G4": "" } },
      "failure_notes": "",
      "discovered_in": "audit-2026-07-24"
    }
  ]
}
```

状态机：`open → in_progress → fixed → verified`；验证失败回退 `fixed → regressed`（附 failure_notes）；修复中发现的新问题以 `new` 追加。**只有 `verified` 视为关闭**。

### 2.2 任务卡（Task Card）

阶段 1 的产物，每个执行型 Agent 领到一张。字段即契约：

| 字段 | 说明 |
|---|---|
| `task_id` | 如 `R2-T01` |
| `issue_ids` | 本卡覆盖的台账条目（可多选，但写集必须内聚） |
| `files_write` | **写集**：本轮内全局唯一，任何两张任务卡写集不得相交 |
| `files_read` | 只读引用集（允许与他卡写集相交，但禁止依赖其未合并行为） |
| `depends_on` | 上游任务卡 id（构成 DAG，决定 Wave 分层） |
| `contracts` | 跨任务卡接口约定（见 5.4 节），分解阶段冻结 |
| `acceptance` | 可机器验证的验收条件（断言/命令/阈值） |
| `verify_cmds` | 验收命令（build / vitest / playwright / 基准脚本） |
| `rollback` | 回滚方式（默认：集成分支 revert 该 Agent 的提交） |

### 2.3 分支模型

```
main ──► round-N-integration（轮次集成分支，每轮一条）
            ├── agent/R2-T01-xxx（每个修复 Agent 一条作业分支，从集成分支切出）
            ├── agent/R2-T02-xxx
            └── ...
```
集成分支合并全部作业分支并通过门禁后，fast-forward 回 main，该 commit 即下一轮 baseline。

## 3. 阶段详解

### 阶段 0：问题识别与基线建立（主控 + 0~2 个侦察 Agent）

1. **台账装载**：读取上轮 `ledger.json`；首轮由审查报告初始化（26 条）。
2. **全量冲突/完整性扫描**：`grep -rn "^\(<<<<<<<\|=======\|>>>>>>>\)"` 确认编译阻塞面；检查台账中每条 `files_write` 是否仍存在（文件可能已被重命名/删除，条目需重定位）。
3. **基线采集**（首轮 + 每轮合并后刷新）：
   - 构建基线：`tsc --noEmit` / `vite build` / `eslint` / `vitest run` 的通过状态与耗时；
   - 性能基线：流式基准（见 G4）与拖拽基准的中位值，写入 `baseline.perf`。
4. 产出：本轮《工作清单》= 台账中所有 `open + regressed + new` 条目。

### 阶段 1：任务分解与依赖图构建（主控）

对每条问题执行四步归约：

1. **定位写集**：该问题修复需要修改的文件集合（审查报告已给出文件+行号，直接映射）。
2. **写集合并**：写集相交 ≥ 1 个文件的问题条目，**必须并入同一张任务卡**（单一写者原则，见 5.1）。例如 P1/P3/P10a/P11a 都触及 `useChatStream.ts` → 同卡。
3. **依赖标注**：满足以下任一条件即建立 `depends_on` 边：
   - D-1 编译依赖：不修它代码无法编译/测试（B0 → 全部）；
   - D-2 行为依赖：修复策略依赖另一问题的决策结果（D15 死代码清理依赖 D7 对 `useColumnResize.ts` 的启用决策）；
   - D-3 写集时序依赖：写集与多张任务卡相交、无法归属单一写者（D10 z-index 触及 5 个模块的文件）→ 排到其所有相关卡之后的后续 Wave。
4. **契约冻结**：跨模块问题（写集可分离但行为耦合）在分解阶段确定接口契约并写入双方任务卡（实例见 6.2、6.3）。

产出：任务卡集合 + DAG（按拓扑深度分层 = Wave）。

### 阶段 2：Agent 分配（主控）

按以下规则把任务卡映射为 Agent：

| 规则 | 内容 |
|---|---|
| A-1 一卡一 Agent | 一张任务卡由一个 Agent 独立完成，不共享写集 |
| A-2 角色绑定 | 修复卡→修复 Agent；集成卡→集成 Agent；门禁卡→验证 Agent（验证 Agent 必须独立于修复 Agent，不得自查自验） |
| A-3 容量 | 本轮执行型 Agent 总数 ≤ 12；超出时按 5.3 节拆轮 |
| A-4 上下文注入 | 每个 Agent 的 prompt 必须包含：任务卡全文、审查报告对应段落（文件+行号+代码片段）、写集禁令（"不得修改 files_write 之外的任何文件"）、验收命令、提交格式（`[R2-T01] ...`） |

### 阶段 3：并行修复（执行型 Agent，按 Wave 推进）

- 同一 Wave 内的 Agent **完全并行**（DAG 同层，写集互不相交）；
- Wave 之间有**合并屏障**：Wave k 的全部作业分支合并进集成分支且 G0（编译门禁）通过后，Wave k+1 的 Agent 才从最新的集成分支切出作业分支；
- 每个修复 Agent 的标准作业流：切分支 → 读任务卡写集内文件 → 实施修复 → 自检 `verify_cmds` → 提交并推送 → 回报（改了什么、自检结果、发现的新问题）。
- **新问题捕获**：修复中发现的台账外问题，Agent 不得顺手修复（防止写集膨胀），只能写入回报，由主控在阶段 6 以 `new` 状态入台账。

### 阶段 4：结果汇总（1 个集成 Agent）

1. 按 Wave 顺序合并全部作业分支到集成分支；
2. 解决合并冲突（理论上被单一写者原则杜绝；若发生，说明任务卡划分有漏，记录到台账 `failure_notes` 并复盘阶段 1）；
3. 生成《轮次变更摘要》：每张任务卡一段——改动文件清单、对应台账条目、自检证据。

### 阶段 5：验证（1~4 个独立验证 Agent，可并行）

门禁序列（G0→G5 逐级，任何一级失败即触发回退）：

| 门禁 | 内容 | 执行者 |
|---|---|---|
| G0 编译 | `tsc --noEmit` + `vite build` 通过 | 验证 Agent V1 |
| G1 静态检查 | `eslint` + 冲突标记扫描归零 | V1 |
| G2 单元测试 | `vitest run` 全量通过（含修复 Agent 新增的针对测试） | V1 |
| G3 交互回归 | `playwright` 拖拽 e2e 场景（边界松手、指针静止收敛、双系统拆除后单套提交） | V2 |
| G4 性能回归 | 流式压测 harness（以 100+ tok/s 回放录制帧，统计主线程帧耗时 P95、内存曲线斜率）与拖拽基准；**不低于上轮 baseline**，且命中台账条目的专项验收阈值 | V3 |
| G5 评审 | 高风险 diff 人工/评审 Agent 复核（热路径、协议解析、store 中间件） | V4 |

回退规则：任一门禁失败 → 集成 Agent 在集成分支 revert 涉事任务卡提交 → 台账对应条目置 `regressed` 并附门禁日志 → 不阻塞其他任务卡的验证结论。

### 阶段 6：台账更新与闭环（主控）

1. 全部 `verified` 条目归档；`regressed`/`blocked` 条目连同 failure_notes 进入下一轮工作清单；
2. 修复回报中的新问题以 `new` 入台账；
3. 刷新 `baseline`（commit + 门禁结果 + 性能数值）；
4. 判断终止条件（第 7 节）；未终止则开启下一轮，回到阶段 0。

## 5. 通用规则

### 5.1 单一写者原则
任一轮次内，每个文件有且仅有一个拥有写权限的 Agent。任务卡写集两两不相交是阶段 1 的硬性校验项（主控在分配前对全部 `files_write` 求交，非空即重划分）。

### 5.2 Wave 分层规则
Wave 编号 = 任务卡在 DAG 中的拓扑深度。同层并行，层间设合并屏障 + G0 门禁。

### 5.3 超容分批规则
当一轮所需执行型 Agent > 12 时：
1. 先按 DAG 深度切分（深层任务自然进入后续轮次）；
2. 同层仍超容时，按**模块内聚性**聚类分批（同一目录/同一子系统的问题优先同轮，减少跨轮接口漂移）；
3. 分批不构成优先级判断：被拆开的各批逻辑地位相同，先后次序任意。

### 5.4 跨模块契约规则
写集可分离但行为耦合的问题，禁止两个 Agent 各自暗改。必须在阶段 1 冻结契约（接口签名、触发时机、数据格式），写入双方任务卡；集成时由 G5 评审核对双方实现是否同时满足契约。

### 5.5 验证独立原则
验证 Agent 不得是同一批任务的修复 Agent；性能基准 harness 与 e2e 场景一经建成即沉淀为仓库资产（`tests/` 下），后续轮次直接复用——这是"每轮输出作为下轮输入"在验证层的体现。

## 6. 轮次实例化（基于 2026-07-24 审查报告）

> 说明：Round 2 与 Round 3 分别承载流式簇与拖拽簇，唯一原因是 5.3 的容量约束（两簇合并 + 验证将超过 12 个 Agent）；两簇逻辑独立，次序可互换。

### Round 1：解阻塞轮（2 个 Agent）

目标：恢复可编译、可测试的基线。这是其他一切修复的逻辑前置（D-1）。

| Wave | Agent | 任务卡 | 写集 | 验收 |

### Round 3：窗口与标签拖拽簇（8 个 Agent）

### Round 5+：模板迭代轮（Agent 数量 = f(台账剩余)）

从第 5 轮起，方案退化为纯模板循环，不再有预定义任务卡：

1. 阶段 0 装载台账：工作清单 = 全部 `regressed` + `new` + 验证中发现的 `open` 残留；
2. 若工作清单为空 → 进入第 7 节终止判定；
3. 否则按阶段 1~2 的规则现场生成任务卡与 DAG（写集求交 → 合并 → 分层），Agent 数量按清单规模伸缩（1 张卡 1 个 Agent + 1 集成 + 按域选配验证 Agent，总量 ≤ 12）；
4. 验证层直接复用既有 harness 与 e2e 场景库，仅对变更域补针对性用例；
5. 阶段 6 更新台账，回到 1。

## 7. 终止条件（全部满足方可收束）

1. 台账中不存在 `open / in_progress / regressed / new` 状态的条目（全部 `verified`）；
2. 连续两轮 G0–G5 全门禁绿（防止"修复引入修复"的振荡）；
3. G4 性能数值不低于 Round 1 基线，且两项核心指标达标：流式压测下主线程帧耗时 P95 无随文本长度增长的二次曲线特征；拖拽 e2e 无振荡场景失败；
4. 冲突标记扫描归零；死代码清单（D15）清零。
