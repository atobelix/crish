# 第一部分：流式渲染性能

## 1.1 链路总览

```
Rust daemon → WebSocket (daemonClient.ts) → JSON.parse/帧 → EventRouter (daemonChatBridge.ts)
→ onChunk(delta) → StreamRenderBuffer.push (rAF 分帧) → updateMessageText (zustand+immer)
→ ChatCard/ChatMessageList 重渲染 → 流式行渲染纯文本(pre-wrap) → 终态 Worker 跑 markdown
```

架构主干设计正确：不丢字、无内存泄漏、无每帧 setState 失控。但热路径上存在三处随文本长度增长的 O(n²) 浪费，长回复/代码密集场景会出现渐进式卡顿。

## 1.2 确认无问题的点

- **接入层不丢字**：`daemonClient.ts:402-410` 每帧 JSON.parse 后分发；监听器 Set + 返回解绑函数（144-147）；心跳/重连定时器有清理（517-529）。背压只发信号不丢 chunk（`useChatStream.ts:1080-1085`）。
- **rAF 分帧缓冲**：`StreamRenderBuffer.ts:158-255` 每帧 12ms 预算 + 8192 字符上限 + 换行边界切分。
- **48ms 三层批合并**：`streamTextBatcher.ts` 分桶 + 终态 `flushNow`（`useChatStream.ts:466-531`）。
- **流式期间不跑 markdown**：`MessageContent.tsx:176-184` 流式段渲染 `whiteSpace: pre-wrap` 纯文本；终态才经 Worker 异步渲染（`markdownRenderAsync.ts:8-27`，LRU + pending 去重 + 1MiB 上限）。
- **行级渲染隔离**：`ChatMessageRow.tsx:114-116` 自定义 props 比较 + `ChatMessageList.tsx:295-302` 按消息 id 订阅。
- **长列表有界**：默认尾部窗口 80 条（`messageWindow.ts:50`），>80 条启用虚拟滚动；BoundedMap 上限 2000。
- **持久化防抖**：350ms localStorage / 2.5s 磁盘镜像（`layoutStore.ts:454-467`）。
- **监听/定时器清理**：各自 effect 清理到位，未见明显泄漏。

## 1.3 问题清单

### 【高】P1. StreamRenderBuffer 每帧全量增量 markdown + highlight.js 高亮，产物被完全丢弃

- `apps/crish-desktop/src/api/StreamRenderBuffer.ts:238` — 每次 flush 都执行 `this.bridge.push(this.fullText)`（增量 markdown 解析 + hljs 高亮 + html 拼接）。
- `apps/crish-desktop/src/hooks/useChatStream.ts:742-748` — `onFrame` 只消费 `frame.full`，`frame.html`/`frame.chunkUpdates` 从未被使用（注释明确"不传 html"）。
- `apps/crish-desktop/src/api/IncrementalMarkdownParser.ts:69-87` — 尾部块每帧变化 → 缓存必 miss → 重渲染；`:365` 的 `renderCodeBlock` 调 `highlightCode`。
- `apps/crish-desktop/src/api/codeHighlight.ts:98-114` — 缓存键为 `${lang}:${raw}` 全文，流式中每帧必 miss → **每帧在主线程同步高亮整个已累积代码块**，且 LRU 每帧塞入更大的新条目；`getHtml()`（95-97）每帧 join 全部 chunk，O(全文)。

**影响**：流式输出代码块时，每帧（~60fps）对整个代码块做 hljs 高亮 + 尾部块 markdown 渲染 + 全文 html 拼接，总成本 O(n²)，而产物 100% 被丢弃。20KB 代码流式回复在主线程产生持续数毫秒→数十毫秒/帧的纯浪费。
**修复**：仅在消费者注册 html 回调时才调 `bridge.push`（当前主路径直接跳过），改动 <10 行，收益最大。

### 【高】P2. 自动滚动每帧对全文做 Pretext 文本布局

- `apps/crish-desktop/src/hooks/useChatAutoScroll.ts:36-84`：
  ```ts
  }, [messages, getFont, isProcessing]);   // messages 每帧新引用 → effect 每帧执行
  // :42  [...msgs].reverse().find(...)     每帧拷贝整个数组
  // :50  parseFloat(getComputedStyle(el).lineHeight)   每帧强制样式计算
  // :51-55  layout(prepare(currentText, font), ...)    O(全文)，且文本每帧变 → 内部缓存失效
  // :56,65  读 scrollHeight 后立即写 scrollTop          layout thrashing 模式
  ```

**影响**：成本随回复长度线性增长、全程 O(n²)。长回复（>30KB）时成为主线程主要开销之一。
**修复**：按 delta 增量推进 `scrollTop += deltaHeight`；或对 prepare 结果按 text ref 缓存 + 节流到 ~100ms。

### 【高】P3. 子 agent 流式通道完全绕过批合并

- `apps/crish-desktop/src/hooks/useChatStream.ts:942-956` — `onSubagentEvent` 每个 token 直接 `useLayoutStore.setState`。
- `apps/crish-desktop/src/api/subagentTimeline.ts:111,137` — 每 token 拷贝消息数组 `[...messages]` + 字符串拼接。

**影响**：主消息流有 rAF/48ms 批合并，subagent 路径无任何节流。immer setState → 全 store 广播 → 所有订阅 selector 重跑，多 agent 高频输出时 store 更新频率比主路径高 3-6 倍。
**修复**：子 agent 事件接入与主路径相同的 StreamTextBatcher。

### 【中】P4. withAutoIndex 每帧重建全量索引并二次广播

- `apps/crish-desktop/src/store/autoIndexMiddleware.ts:23-29` — 每个 token 帧 sessions 数组必变 → 每帧重建 `sessionsById` Map + **第二轮**全 store 通知（所有 selector 每帧跑两遍）。

### 【中】P5. 流式行每帧对每个文本段跑 10 条正则（含 7 次 `new RegExp`）

- `apps/crish-desktop/src/components/chat/MessageContent.tsx:173-175` — 每帧 `stripThoughtPlaceholders`（全文）+ `extractImageRefs`（全文正则）。
- `apps/crish-desktop/src/api/markdownRenderLite.ts:41-71` — 每次调用现场构造 7 个 RegExp + 全文 ~10 趟 replace。
- 叠加：`timeline` 数组每帧新建（`ChatMessageRow.tsx:140`）使 `MessageContent` 的 React.memo 永远 miss。

### 【中】P6. 事件解析热路径每帧 2 次 Zod 校验

- `apps/crish-desktop/src/api/daemonChatBridge.ts:236-254`（resolveEventType safeParse）+ `:839-844` 与 `:540-545` 对 type==='event' 再解析一次。100+ tok/s 时是持续 CPU 占用。
- **修复**：为 `message-delta/text-delta` 高频类型走绕过 zod 的快速路径。

### 【中】P7. 帧级重渲染沿组件树放大（多处 O(n) 扫描）

- `ChatCard.tsx:91` — `messages.some(...)` 每帧 O(n)；`useChatCardSelectors.ts:10` 每帧新 messages 引用 → ChatCard 整树每帧重渲染。
- `ChatMessageList.tsx:295-302` — `MessageRowById` **未包 React.memo**，父级每帧重渲染时全部可见行（≤80）重新 render + reconcile。
- `useMessageWindow.ts:28-42` — `collectMustIncludeIndices` / `resolveExpandedForKeepAlive` 每帧 O(n) 扫描。
- `ChatMessageList.tsx:124-133` — 有 pin 时每帧 `new Map(...)` O(n)。

### 【中】P8. 虚拟化开启时 usePretextHeights 每帧向 Worker 发全量文本批布局

- `apps/crish-desktop/src/components/chat/hooks/usePretextHeights.ts:33-64` — effect 依赖 `visibleMessages`（每帧新引用）；流式行每帧被 `invalidateActual` 重置高度 → 每帧调度 `pretext.batch-layout`（payload 含全文）；`cancelledRef` 每次 effect 重跑被重置（:36），旧任务无法真正取消（竞态 + 过期写）。

### 【中】P9. AsyncMarkdownBlock 双重解析

- `MessageContent.tsx:83-104` — Worker 产出 html 后，又在主线程动态 `import('incrementalMarkdownBridge')` 并 `bridge.push(text)`（含 hljs）重算一遍，仅为写 innerHTML。每条完成消息付出双倍解析 + 双倍高亮成本。

### 【低】P10. onChunk 热路径重复心跳与 O(n) 查找

- `useChatStream.ts:1076` 与 `daemonChatBridge.ts:1179-1184` — `updateHeartbeat` 每 chunk 调两次，各带新对象字面量（GC 碎屑）。
- `useChatStream.ts:1093-1101` — 每 chunk `messages.find(...)` O(n)，仅为检查占位文案（可用局部布尔锁存）。

### 【低】P11. 其他次要项

- `withLogger.ts:8-21`：dev 模式每次 set 持有 prev/next 整树引用 + console 序列化（生产无影响）。
- `useTextMeasure.ts:85-138`：流式期间每帧销毁/重建 ResizeObserver（计算已防抖）。
- `StreamRecovery.ts:68-81`：`markCompleted/markFailed` 不清理 streams Map 条目（有界，可忽略）。
- `useChatStream.ts:589-594`：unmount 时三个 batcher 未 `dispose()`（最多残留一次 48ms flush）。
- **正确性附带发现**：`directFetchBridge.ts:258-264` SSE 回退路径把 **delta** 传给 `onThought`，但上层 batcher 是全文覆盖语义（`useChatStream.ts:865-871`）→ 回退路径下思考文本只剩最后一帧增量（丢内容 bug，非性能）。

## 1.4 结论

| 场景 | 能否承受 100+ tok/s |
|---|---|
| 短-中回复（<10KB）纯文本 | ✅ 可以，rAF 分帧 + 批合并 + 行级 memo + 窗口化列表组合正确 |
| 长回复 / 代码块密集 | ❌ 会渐进式卡顿，P1 + P2 均 O(n²)，P1 为 100% 纯浪费 |
| 多子 agent 并行 | ⚠️ P3 + P4 使 store 更新放大 3-6 倍，掉帧风险显著 |
| 丢字 | ✅ 不会（背压只暂停信号，终态 flushNow 保底） |
| 内存泄漏 | ✅ 未发现；GC 压力来自每帧字符串/正则分配（P5/P10） |

## 2.3 实现良好的方面

1. **标签拖拽事件模型正确**：pointer 事件 + `setPointerCapture`（`index.ts:57-63`，带 try/catch 回退），move/up/cancel 绑 window 且结束时完整解绑（`drop-handlers.ts:3-20`），5px 拖拽阈值（`types.ts:52,78-88`）防误拖。
2. **抓握偏移正确**：`clickOffsetX/Y = clientX - rect.left/top`（`index.ts:81-92`），全套视口坐标系，未混用 pageX/screenX/offsetX；无容器 zoom/transform，不会跳变。
3. **store 写入 diff 节流**：`safeSetDropPreview` + `dropPreviewEquals`（`pointer-state.ts:107-118`、`types.ts:268-279`），预览真正变化才重渲染。
4. **碰撞解析模型设计成熟**：`collision.ts:186-300` "边缘感知五分区 + 中心 60% 安全区" + 冗余拆分抑制，纯函数可测（有 `useTabDrag.test.ts`）。
5. **落点提交校验**：`canCommitTabDrop`（`types.ts:281-308`）收口 cancelled/自合并。
6. **resize 提交模型正确**：拖动中只改 DOM、松手才写 store（`Workspace.tsx:397-408`）；`WindowResizeBridge.ts` 窗口 resize 期间冻结布局动画（含 5s watchdog）。
7. **标签重排插入算法**：`resolveTabInsertIndex`（`types.ts:107-119`）中点判定，不重排真实 DOM。

## 2.4 结论

骨架设计良好、执行有失。核心缺陷四点：

1. **边界检测形同虚设**（D1）：最近卡片兜底 + 坐标钳制 → 画布外松手也提交拆分/合并。
2. **抖动双重成因**（D2/D3）：静态快照命中测试 vs 实时变化的预览布局互相错位；侧栏每个 move 全量 splice 重排。
3. **性能优化做半截**（D5/D6/D7）：有 capture、有 diff，但 move 热路径无 rAF、每帧多次强制布局、overlay 用 left/top；最规范的 `useColumnResize.ts` 零引用，线上跑的是无 capture/无节流/无 iframe 屏蔽的内联版。
4. **稳定性隐患**（D4/D9）：双拖拽系统并存 + 直接改 React 管理的 DOM。
