### 【阻断-2】"消除渲染抖动"的提交把唯一的合帧机制删掉了

**对比三个连续提交的同一个函数 `apps/crish-desktop/src/hooks/useVirtualScroll.ts`：**

```ts
// ad3f4140 (03:59) 与 7693fe5d (12:12) —— 提交态，行 125-131
const onScroll = useCallback<React.UIEventHandler<HTMLDivElement>>((e) => {
  latestScrollTopRef.current = e.currentTarget.scrollTop;
  if (rafRef.current == null) {
    rafRef.current = requestAnimationFrame(() => {
      rafRef.current = null;
      setScrollTop(latestScrollTopRef.current);
    });
  }
}, []);

// e3fb232f (12:48) —— 提交信息 "stabilize virtual scroll geometry and
//                     eliminate render thrashing during scroll"
const onScroll = useCallback<React.UIEventHandler<HTMLDivElement>>((e) => {
  setScrollTop(e.currentTarget.scrollTop);   // 无 rAF、无等值守卫
}, []);
```

前两版已有 **rAF 合帧 + latest 值去抖**：一帧内多次 scroll 事件只触发 1 次 `setState`。e3fb232f 把它删掉，改为**每个 scroll 事件直接 setState**，且没有任何等值判断。这会**增加**每帧的渲染次数，与提交信息声称的方向完全相反。`behavior:'smooth'` 程序化滚动与触控板惯性滚动都会一帧产生多个 scroll 事件，属于高频命中路径。

**旁证**：工作区未提交版本已把该行改成 `setScrollTop((prev) => (prev === top ? prev : top))` 补回等值守卫 —— 说明有人事后察觉，但 **HEAD 上留着的仍是退化的版本**。

**建议**：恢复 rAF 合帧（或至少保留等值守卫），并修正 `e3fb232f` 的提交信息与 changelog；如有性能测试，应补一条"单帧多次 scroll 事件只触发一次渲染"的断言防回归。

### 【阻断-3】`reconcileAssistantMessageBlocks` 对正文块"非对称保全"→ 正文静默丢失

`timelineReconciler.ts:81-120` 的三元槽位设计存在两处结构性缺陷：

1. **正文块没有身份**：槽位 key 是 `${cleanTurn}:${type}:${id ?? ''}`（`:96`、`:105`），而 `apps/crish-desktop/src/store/sessionMessageActionsCore.ts:242-247` 创建的 text 块**既无 `id` 也无 `turnIndex`**。因此一条消息里**所有**正文块都塌缩成同一个 key `0:text:`。`existingMap.set()` 为覆盖语义，步骤 1 注册既有块时前一段正文就被后一段顶掉。
2. **步骤 3 的保全是非对称的**（`:115-120`）：只复活 `tool_call` / `thought`，**正文块的 orphan 直接丢弃**，且不产生任何日志或告警。

**运行时验证**：

```
twoText = [text(第一段正文), tool:t1, text(第二段正文)]

B1 首次规范化 : ["text(第一段正文)","tool:t1","text(第二段正文)"]   <- 幂等路径正常
B3 二次规范化 text 块数量 2 == 2                                    <- 正常路径无损失

C1 reconcile(两段, 只带一段 plainText) :
   ["text(只带一段)","tool:t1"]        <- 第二段正文被静默丢弃
```

**当前可达性**：主流水线 `normalizeAssistantTimeline` 的 incoming 由 `msg.blocks` 派生，通常是 existing 的超集，所以 B 路径（幂等）当前安全。真实风险在于：

- 该函数**被公开导出**（`store/sessionMessageActionsTools.ts:31` 再导出），任何后续调用方传入部分 incoming 就会**静默丢正文**；
- 「incoming ⊇ existing」这个关键不变量**在代码与注释中均未声明，也无断言保护**。

**建议**：给 text 块补稳定身份（id 或 `startTime` 参与 key），或让步骤 3 对 text 同样保全；无论哪种，都应在函数入口加一条不变量断言（`incoming` 缺失的 text 块数 > 0 时至少落日志），把"静默丢失"变成"显式报错"。

## 二、应修：设计缺陷与风险（逻辑成立，触发需条件）

### 【严重-4】fork 恢复：外部副作用先于幂等键持久化，重试会产生重复子 run

`crates/orchestrator/src/recovery.rs:616-641`

```
:616  let spawned = self.spawner.spawn(&request).await?;   <-- 外部副作用（起了一个新 run）
:633  self.store.set_subagent_path(...)?;                  <-- 以下任一步失败，函数带 Err 返回
:636  self.store.update_run_status(&ctx.subagent_run_id, "failed", ...)?;
:639  self.budget.record_fork(&record.fingerprint)?;
:640  self.forks.push(record.clone());                     <-- 幂等键直到这里才进内存
:641  self.persist_forks()?;                               <-- 直到这里才落库
```

幂等判定在 `:469-480` 依赖 `self.forks`，并发占位 `in_flight_forks` 在 `:505` 无条件移除。因此**若 spawn 成功但 `:633`–`:641` 任一环节失败（磁盘满、IO 错误等）**：本次返回 Err，`self.forks` 无记录、`in_flight_forks` 已清空 → 下次恢复流程重查 `:469` 查不到 → **再次 spawn，产生孤儿/重复 run**；且原 run 因 `:636` 未执行而**仍停留在非 failed 状态**。

**建议**：把"写 in-progress fork 记录（含预留 `new_run_id`）"提到 spawn 之前，spawn 成功后再补全并置 committed；或把记录写成可回滚的补偿事务。

### 【严重-5】fail-closed 改造可能把瞬时故障放大为"完全无法发消息"

`apps/crish-desktop/src/hooks/chat-stream/readiness.ts:151-159` 把 `core_get_status` 抛错从 `ok:true` 改为 `ok:false`；`slashSendPreflight.ts:122-126` 收到非 ok 直接 `return { status: 'abort' }`，**无重试、无降级路径**。若探测因 IPC 瞬时超时或引擎短暂抖动失败，将阻断**全部**发送。

这是"用可用性换安全性"的取向问题：安全侧确实更严，但代价是瞬时抖动即全量不可发。**建议**：对 `retryable_wait` 类失败给一次短 TTL 重试或降级提示，而不是硬 abort。（此项属设计取舍，需作者确认是否有意为之。）

### 【严重-6】`live_catalog` 失败快照缓存无失效条件

`apps/agent-workbench/src-tauri/src/engine_provider/protocol.rs:283-289`：parse/IO 失败时把失败态 `Arc` 装进 `LIVE_CATALOG` 槽位，`live_catalog()` 命中即返回、**不再读盘**（测试 `:682-700` 印证），且**无 TTL**，仅在显式 `reload_live_catalog` 成功时才覆盖。若首次读盘是**瞬时 IO 故障**（而非文件语法损坏），该失败态会一直缓存到下次显式 reload 或重启。**建议**：对 IO 类失败（区别于 `parse_error`）使用较短重读窗口。

### 【严重-7】时间线单测把"逆因果顺序"锁死为期望值

`apps/crish-desktop/src/store/__tests__/timelineBlocksReconcile.test.ts:124-144`：

```ts
// 插入顺序：incoming turn1 先到，orphan turn0 追加到末尾
expect(thoughtContents).toEqual(['第 2 轮思考：读取配置文件', '第 1 轮思考：扫描工作区']);
expect(merged.map((b) => `${b.turnIndex}:${b.type}`)).toEqual([
  '1:thought','1:tool_call','1:text','0:thought','0:tool_call',   // turn1 在 turn0 之前

```

测试**明确断言 turn 1 排在 turn 0 之前**，并将注释写为"插入顺序即为权威"。这与同一批提交信息反复宣称的「严格因果时序」直接冲突。即使该状态在当前调用点不可达，把逆序锁进期望值意味着**将来真出现乱序也无法靠测试发现**。

**建议**：断言改为按 `turnIndex` 递增的真值顺序；若"插入序优先"确为设计意图，则应显式在文档/注释中说明它与"因果时序"的优先级关系，避免两个目标继续互相污染。

### 【严重-8】「锁往返」并非真往返，字段保真无覆盖

`apps/agent-workbench/src-tauri/src/models_yaml.rs:593-622` 的 `save_roundtrip_and_atomic_rejects_invalid` 只做 `save(str)` 后断言磁盘文本 == 原串（原子写自证），**没有 `parse(serialize(parse(x))) == parse(x)` 的结构级相等**。`serialize_models_yaml_tree` 的字段保真度不受测试保护 —— 字段重命名/丢失不会被判红，而这恰是 SSOT 治理最需要防的事。

## 五、同源问题的演化史（最需要警惕的一点）

结果是**同时存在 4 套互相打架的排序规则**（`reconcile` 禁止排序 / `normalizeAssistantTimeline:154-185` turn0→unshift 否则 push / `enforceThoughtBeforeText` 强制搬迁 / `messageOrderKey.ts:24-29` 缺 seq 时退回 `Date.now` 近似）。

**根因**：块级顺序**没有任何基于真实事件序号（engineSequence）的权威排序**，全靠"thought 必在 text 前"这类启发式猜测。而消息级排序在缺 seq 时退回时间戳近似 —— 一旦同一毫秒内到达多个事件即失去确定性。

**另外**：`afe5c505` 声称"流式 thinking 单轨"，但 `apps/crish-desktop/src/api/.../agentStreamCallbacks.ts:117-145` 仍在做 `m.thinking = t` 的**双写**（blocks + thinking 双源），可能造成重复渲染 —— 单轨未真正落地。

**建议**：停止继续加启发式，改为**由引擎侧下发单调递增的事件序号**并作为唯一排序权威，其余排序规则全部删除。这是本次审查中我认为最值得优先处理的结构性问题。
