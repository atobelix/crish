- **审查时间**：2026-09-10 15:55–16:35 (EDT)
- **触发**：用户反馈「token 体系挺乱的，实际跑起来更多硬编码手写样式；体系没落地；而且现在也不满足需要了，要扩充和优化」

## 二、确定性缺陷（已逐条读码确认）

### 2.1 【阻断】16 个 token 被引用但从未定义，且无 fallback —— 静默失效

这是"体系没落地"最硬的证据。`var(--x)` 在未定义且无 fallback 时，声明的整个值变为 **invalid at computed-value time** → 该属性退回 `inherit`/`initial`，**没有任何报错**。

**修法**：这是一个纯机械、可完全自动化的检查（见 §六 门禁 G1）。

### 2.2 【严重】平行调色板：`themePresets.ts` 的 209 处硬编码颜色

```
$ grep -oE "#[0-9a-fA-F]{3,8}\b|hsla?\([^)]*\)|oklch\([^)]*\)" api/themePresets.ts | wc -l
209
```

这个文件是一份**与 `tokens.css` 平行的手工调色板**，运行时经 `themePersonalization` → `setProperty` 注入，**覆盖** tokens.css 里同名 token。所以：

- 改 `tokens.css` 不会影响走个性化的用户；
- 两套色值会各自漂移；
- 这是"改了 token 但界面没变"的根源之一。

**修法**：`themePresets.ts` 只允许产出 **primitive 层**（色阶原始值），语义层必须由 tokens.css 用 `var()` 派生；禁止个性化直接写 `--text-*` / `--bg-*` 这类语义名。

### 2.3 【严重】`oklchColorGuard` 用**字符串比较**推断明暗，并写死 4 个颜色

`api/oklchColorGuard.ts:114-127`

```ts
const textPrimary = getContrastGuardedText(bgPrimaryColor, isDark);   // ← 计算得出，正确
root.style.setProperty('--text-primary', textPrimary);

const isComputedDark = textPrimary === 'hsl(0, 0%, 94%)';            // ← 拿硬编码字符串反推
if (isComputedDark) {
  root.style.setProperty('--text-secondary', 'hsl(0, 0%, 72%)');      // ← 写死
  root.style.setProperty('--text-tertiary',  'hsl(0, 0%, 50%)');      // ← 写死
} else {
  root.style.setProperty('--text-secondary', 'hsl(35, 8%, 34%)');     // ← 写死
  root.style.setProperty('--text-tertiary',  'hsl(35, 6%, 52%)');     // ← 写死
}
```

两个问题：
1. **`isComputedDark` 是字符串相等判断**。`getContrastGuardedText` 的返回值只要格式化方式变一下（多一个空格、换个色彩空间写法、或调整阈值导致返回不同色），这个分支就会**静默翻转**，把深色主题的文字层级换成浅色的那组 → 对比度崩掉，且不报错。
2. **`--text-secondary` / `--text-tertiary` 的四个值只存在于这个文件里**，tokens.css 里没有对应定义。也就是说，开启主题个性化后，**文字层级的 SSOT 就不是 tokens.css 了**。

**修法**：`getContrastGuardedText` 直接返回 `{ value, isDark }` 而不是让调用方反推；secondary/tertiary 改为从 primary 用 `color-mix` 派生，或放进 tokens.css 作为带 `data-theme` 的语义对。

### 2.4 【严重】`--radius-2xl` 是 `--radius-xl` 的纯重复

tokens.css 三档全部相等：

```
:373  --radius-xl:  12px;      :1471  --radius-xl:  10px;    :1547  --radius-xl:  14px;
:374  --radius-2xl: 12px;      :1472  --radius-2xl: 10px;    :1548  --radius-2xl: 14px;
```

（顺带说明：`--radius-lg` 等在 tokens.css 里"出现三次"是 `[data-ui-size='small'|'large']` 的**有意覆盖**，不是 bug——这一点我一开始误判过，已排除。）

### 2.5 【严重】圆角刻度与实际用法严重脱节

- token 基准刻度：**2 / 4 / 6 / 8 / 12 / (12) / 9999**
- 组件实际写了 **14 个离群值**：`1, 3, 5, 7, 9, 10, 13, 14, 16, 18, 20, 22, 24, 999`
- **25.8%（118/458）的圆角不在刻度上**

并且 tokens.css 里已经留了注释（`:474`）：
> `/* 设置/按钮圆角锁：默认档 8px，禁止再别名到 --radius-md 的 6 */`

而未跟踪文档 `docs/desktop-ui-repair/survey/04-设置按钮圆角7px与曲率混乱.md` 也在讲同一件事。**说明 7px 这个值已经在 token 层被"锁"成 8px，但组件 CSS 里 `border-radius: 7px` 仍有 23 处** —— 锁在 tokens.css，破在组件里。

> 这正是用户说的"实际执行起来还有更多硬编码"的一个典型：**规则写在了 token 文件里，但没有执行机制**。

### 2.6 【一般】4 份 monospace 字体栈

| 来源 | 内容 |
|---|---|
| `tokens.css:467` `--font-mono` | Cascadia Mono / JetBrains Mono / SF Mono… |
| `tokens.css:224` `--sep-font-mono` | SFMono-Regular / Consolas / Menlo… |
| `tokens.css:547` `--md-font-mono` + `markdown-typography.css:15` | 各自兜底 `IBM Plex Mono` / `SFMono-Regular` |
| `utils/pretextFontBridge.ts:2` | `FONT_MONO_PRETEXT = 'Consolas'`（兜底用） |

兜底字体不同 → 字体未加载时各处回退不一致，**同一段代码在编辑器和聊天区可能显示成两种字体**。

（修正：`pretextFontBridge.ts:48-49` 实际上会读 `getComputedStyle(document.documentElement).getPropertyValue('--font-sans'/'--font-mono')` 并取栈中**第一个具名字体**做测量——所以它**会跟随用户字体设置**。真正的隐患是：它假设"第一个具名字体就是实际渲染字体"，在 Web 字体尚未加载完（`font-display: swap`）或首个字体缺失时，**测量用的字体与渲染字体不一致 → 高度估算全错**，而这些估算正是虚拟滚动几何的输入。）

### 2.7 【一般】`check-text-color-tokens` 的覆盖面比它宣称的窄得多

`scripts/check-text-color-tokens.mjs:61`

```js
const colorHard = /(?:^|[;{\s])color:\s*(#[0-9a-fA-F]{3,8}\b|hsla?\(|rgba?\()/g;
```

三个盲区：
1. **只匹配 `color:` 属性**。`:65` 还会主动跳过 `background|border|outline|shadow|fill|stroke` —— 也就是说**背景色、边框色、填充色完全不在管辖范围**。
2. **不包含 `oklch(`**。仓库正在推 OKLCH，而门禁不认它。
3. **对 `.tsx` 的 `style={{color:'#fff'}}` 漏检**（属性名与值之间有引号，正则不匹配）。

结果：**117 处硬编码颜色、352 处内联样式，全部门禁通过。**

### 2.8 【一般】8 个 check 脚本没有任何自动化引用

`scripts/` 下 34 个 `check-*.mjs`，其中 13 个未被 `package.json` 引用；把 CI workflow 也算上后，**仍有 8 个完全没有任何调用方**：

check-lr-t1-memory-prod-ban  check-sec7-gfm-emoji  check-tsc-threshold  check-ui-negative-churn
```

（其余 5 个如 `check-crate-size` / `check-unwrap-baseline` / `check-dist` 是接在 CI workflow 上的，不是孤儿。）

## 四、主题机制评估

**结论：部分可用，有明确的坏点清单。**

好消息（是真的做对了）：
- `themeStore` 是 `data-theme` 的**单一真源**；`visualThemeController` 管 `data-ui-size/--ui-scale/data-density`，职责不重叠。
- `tokens.css` 浅色 569 个 / 暗色覆盖 453 个，**成对 449**；语义色、语法色、图表色、终端色（`--xterm-*` 浅 `:345-361` / 暗 `:1124-1141`）**双套齐全**。
- 代码高亮（`--syntax-*`）、图表、FlowScrubber、Tiptap **都走 token**，切主题能跟随。
- 终端主题通过 `readCssVar('--xterm-*')` **真能取到 token**，不是永远走兜底。
- 18 处内联 `style={{color}}` 全部引用 `var(--…)`，能跟随主题。

坏点清单：
| 严重度 | 问题 | 位置 |
|---|---|---|
| 中 | **已开的终端不随主题重上色** —— 只在创建/restart 时 `getXtermTheme()`，全文无 `crish-theme-changed` 监听 | `useXtermTerminal.ts:219,230` |
| 中 | **不跟随系统深色** —— 全文 0 处 `prefers-color-scheme`，启动只读 `localStorage` | `themeStore.ts:38` |
| 中 | **"智能时光"每分钟轮询重绘未包过渡锁** → 带过渡闪烁 | `themeStore.ts:145` |
| 低 | 25 处 `rgba(0,0,0,α)` 阴影未 token 化，暗色下层级变平 | `ChatMessageRow.module.css:917,964,1000,1031,1042,1077` 等 |
| 低 | `#ffffff` 硬编码（展示页，非主流程） | `ComponentGallery.module.css:12,77,82,122,143,169,187,209` |

## 五、为什么"体系没落地"——根因归因

门禁体检结果（实跑）：

| 脚本 | 检查什么 | 实现 | 结果 | 盲区 |
|---|---|---|---|---|
| `check-text-color-tokens` | 文字硬编码色 | 正则，**仅 `color:`** | PASS | 漏 bg/border/fill、漏 oklch、漏 tsx 内联 |
| `check-color-ssot` | 业务硬编码色 | 正则，**仅 background/color** | PASS | 漏 border/fill/shadow；关键字只认 white/black |
| `check-markdown-style-compliance` | **单个文件** | 正则 | PASS | 只覆盖 `markdown-typography.css` |
| `check-frontend-convergence` | G-01~G-13 | AST+正则 | **FAIL**(G-11/12) | G-04 只查 `9999px` 不查任意圆角；G-05 只查 `z-index>=100`；**G-06 排除 `src/styles/`** → 91 处 `!important` 全漏 |
| `eslint local/*` | 只有 `deprecated-requires-reference` / `no-silent-catch` | AST | — | **没有任何样式类规则** |

**归因**：10 类样式问题里，**没有一类**被现有门禁覆盖，而且不存在"写好了没接线"的样式检查（34 个 check 脚本里没有样式/token 相关的孤儿）。所以：

> 不是"门禁写了但没跑"，而是**从来没人写过这些门禁**。token 体系是"文档 + 约定"，不是"约束"。
>
> 叠加第零轮的发现（`.husky/pre-commit` 只跑空白检查、仓库无 git remote），结论是：**样式纪律目前完全靠人自觉**。

```

**C. 收敛（删）**

| 动作 | 对象 | 收益 |
|---|---|---|
| 删 | **146 个死 token**（其中 `--xterm-*` 22 个其实有消费，需逐一确认后删） | 大幅降低认知负担 |
| 删 | `--breakpoint-*` 8 档（桌面端无流式断点，0 消费） | — |
| 删 | `--bg-glass` / `--backdrop-blur`（0 消费，或真实现） | — |

| 合 | `--sep-*` 27 个 → 改为指向语义层的 `var()` 别名 | 消灭平行体系 |
| 定义 | 16 个未定义引用（§2.1） | 修静默失效 |

**D. 架构层（真正要改的那一条）**

```
primitive（色阶原始值，只此一处硬编码）
    ↓ var()
semantic（--text-* / --bg-* / --border-* / --color-*）
    ↓ var()
component（组件只允许用 semantic）
```

配套约束：
- `themePresets.ts` **只许产出 primitive**，语义层必须由 `tokens.css` 派生 → 消灭 §2.2 的 209 处平行调色板；
- `oklchColorGuard` 改为返回 `{value, isDark}`，不再字符串反推、不再写死 secondary/tertiary → 修 §2.3；
- 组件 CSS 禁止直接引用 primitive（当前 `--brand` 86 次、`--accent-color` 70 次、`--accent-orange` 44 次…合计约 400 次，这是主题化失效的直接原因）。
